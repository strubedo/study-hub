## Two jobs: authentication and encryption

Anyone in range can receive a wireless frame, so a WLAN must do two things that a cable does physically:

* **Authenticate**: decide who is allowed to join (a shared passphrase, or per-user credentials/certificates).
* **Encrypt and protect integrity**: keep frames private and detect tampering, using keys derived freshly for each client session.

Every security "generation" below is a combination of an authentication method and an encryption cipher.

## The generations

| Protocol | Year | Encryption | Integrity | Status |
|---|---|---|---|---|
| WEP | 1999 | RC4 with static 40/104-bit keys | CRC-32 (weak) | Broken in minutes; never use |
| WPA | 2003 | **TKIP** (RC4 with per-packet key mixing) | Michael MIC | Interim fix, deprecated |
| WPA2 | 2004 | **AES-CCMP** (128-bit) | CBC-MAC | Still widely deployed |
| WPA3 | 2018 | AES-CCMP-128; **GCMP-256** in 192-bit Enterprise mode | | Current standard; required on 6 GHz |

WPA2 is the Wi-Fi Alliance certification of IEEE **802.11i**. WPA3 keeps AES but replaces the weakest part of WPA2 (the PSK handshake) and makes **Protected Management Frames (PMF, 802.11w)** mandatory, which blocks spoofed deauthentication/disassociation attacks.

> **Exam tip:** Match the cipher to the generation: WEP = RC4, WPA = TKIP, WPA2 = AES-CCMP, WPA3 = AES (CCMP or GCMP) plus SAE. An answer pairing WPA2 with TKIP as its native cipher is wrong (TKIP was only kept for backward compatibility).

## Personal vs Enterprise mode

Each of WPA, WPA2, and WPA3 comes in two modes:

| | Personal | Enterprise |
|---|---|---|
| Credential | One passphrase shared by every user | Per-user credentials or certificates |
| WPA2 method | PSK (pre-shared key) | 802.1X/EAP |
| WPA3 method | **SAE** | 802.1X/EAP (optional 192-bit mode) |
| Server needed | No | Yes, a **RADIUS** authentication server |
| Revoking one user | Change the passphrase for everyone | Disable that one account or certificate |
| Typical use | Home, small office, IoT | Corporate WLANs |

### WPA2-Personal and its weakness

In WPA2-Personal the passphrase (with the SSID) derives the **PMK**, and the client and AP then run the **4-way handshake** to prove they both know it and to derive per-session keys (the PTK for unicast and the GTK for broadcast/multicast). An attacker who captures one 4-way handshake can try passphrases **offline** at high speed until one matches, so short or common passphrases fall quickly.

### WPA3-Personal: SAE

**SAE (Simultaneous Authentication of Equals)**, based on the Dragonfly key exchange, replaces PSK authentication:

* Each attempt to guess the password requires a live exchange with the AP, so **offline dictionary attacks are not possible** from a captured handshake.
* It provides **forward secrecy**: learning the password later does not decrypt previously captured traffic.
* The 4-way handshake still runs afterward, but it uses a strong PMK produced by SAE.

**WPA3 transition mode** lets WPA2-PSK and WPA3-SAE clients share one SSID during migration, at the cost of keeping WPA2's weakness for the older clients.

### Enhanced Open (OWE)

For open guest networks, **OWE (Opportunistic Wireless Encryption)**, marketed as Wi-Fi Enhanced Open, encrypts each client's traffic with a per-client key from a Diffie-Hellman exchange, with no password. It provides privacy but **no authentication**. On 6 GHz, an "open" SSID must use OWE.

## 802.1X / EAP (Enterprise mode)

802.1X is a port-based access control framework. Three roles:

| Role | Who plays it in a WLAN | Talks to |
|---|---|---|
| **Supplicant** | The client device (its 802.1X software) | Authenticator, using EAP over LAN (**EAPOL**) |
| **Authenticator** | The AP (autonomous) or the **WLC** (controller-based) | Supplicant via EAPOL; server via **RADIUS** |
| **Authentication server** | A RADIUS server such as Cisco ISE | Authenticator via RADIUS (UDP 1812/1813) |

The authenticator does not check credentials itself. It relays EAP messages between the supplicant and the RADIUS server. When the server returns **Access-Accept**, both the client and the server have derived keying material; the server passes its copy to the authenticator inside the Access-Accept, both sides derive the PMK from it, and the 4-way handshake then creates the session keys. Each user ends up with unique keys.

### EAP methods

| Method | Server certificate | Client credential | Notes |
|---|---|---|---|
| **EAP-TLS** | Yes | **Client certificate** | Strongest; needs a PKI to issue client certs |
| **PEAP** (PEAPv0/EAP-MSCHAPv2) | Yes | Username/password inside a TLS tunnel | Very common with Active Directory |
| **EAP-TTLS** | Yes | Username/password (various inner methods) in a tunnel | Common on non-Windows clients |
| **EAP-FAST** | Optional | Uses a PAC (Protected Access Credential) to build the tunnel | Cisco-developed |
| LEAP | No | Username/password | Cisco legacy, vulnerable; do not use |

> **Watch out:** In PEAP and EAP-TTLS, the client must **validate the server certificate**. A client configured to "accept any certificate" will happily send its credentials to a rogue AP running its own RADIUS server.

## Things that are not security

* **Hiding the SSID**: the SSID still appears in probe requests and responses; trivial to discover.
* **MAC address filtering**: MAC addresses are sent in clear text and are easy to spoof.
* **WPS PIN**: the 8-digit PIN can be brute-forced; disable WPS on business networks.

## Troubleshooting security mismatches

| Symptom | Likely cause |
|---|---|
| Client associates, then fails during the 4-way handshake, repeatedly prompts for a password | Wrong passphrase (WPA2-PSK / WPA3-SAE) |
| Older client cannot see or join a WPA3-only SSID | Client lacks WPA3/SAE support; use transition mode or upgrade the client |
| Client cannot join a 6 GHz SSID | Client lacks 6 GHz radio, or the SSID is configured with WPA2 (not allowed on 6 GHz) |
| 802.1X clients fail; WLC logs "RADIUS server not responding" | Wrong RADIUS server IP, UDP 1812 blocked, or the **shared secret** on WLC and server do not match |
| PEAP users prompted to trust a certificate, or failing after a cert renewal | Server certificate untrusted or expired on the client |
| EAP-TLS user fails while others work | That user's client certificate is expired, revoked, or missing |
| Client stuck on "obtaining IP address" after successful auth | Not a security issue: VLAN/DHCP problem behind the WLAN |

On Windows, `netsh wlan show interfaces` shows the **Authentication** (for example WPA2-Personal, WPA3-Personal, WPA2-Enterprise) and **Cipher** (CCMP, GCMP-256) actually negotiated, which is the fastest way to confirm what security the client is using.

## Key takeaways

* WEP = RC4 (broken), WPA = TKIP, WPA2 = AES-CCMP (802.11i), WPA3 = AES-CCMP/GCMP-256 plus SAE and mandatory PMF.
* Personal = one shared secret (PSK in WPA2, **SAE** in WPA3); Enterprise = per-user 802.1X/EAP with a RADIUS server.
* SAE blocks offline dictionary attacks and provides forward secrecy; WPA2-PSK handshakes can be cracked offline if the passphrase is weak.
* 802.1X roles: supplicant (client), authenticator (AP/WLC), authentication server (RADIUS such as ISE).
* EAP-TLS uses client and server certificates; PEAP uses a server certificate and a username/password inside a TLS tunnel.
* OWE encrypts open networks without authenticating users; 6 GHz requires WPA3 or OWE.
* SSID hiding and MAC filtering are not security controls.
