## What a working IPv4 host needs

Every IPv4 host needs four pieces of configuration, either static or from DHCP:

| Setting | Used for | Symptom if wrong |
|---|---|---|
| IP address | Identity on the subnet | Nothing works, or conflicts with another device |
| Subnet mask | Deciding "local or remote?" | Some destinations work, others do not |
| Default gateway | Reaching anything off-subnet | Local hosts work, remote hosts fail |
| DNS server(s) | Resolving names | Ping by IP works, ping by name fails |

The mask drives a decision the host makes for **every** packet: it ANDs its own address and the destination with its own mask. If the results match, the destination is **local** and the host ARPs for the destination directly. If they differ, the destination is **remote** and the host ARPs for its **default gateway** instead.

## Checking the configuration on IOS

```ios
R1# show ip interface brief | exclude unassigned
Interface              IP-Address      OK? Method Status                Protocol
GigabitEthernet0/0/0   192.168.10.1    YES NVRAM  up                    up
GigabitEthernet0/0/1   10.0.12.1       YES NVRAM  up                    up

R1# show ip interface GigabitEthernet0/0/0 | include Internet
  Internet address is 192.168.10.1/24

R1# show ip route connected
      10.0.0.0/8 is variably subnetted, 2 subnets, 2 masks
C        10.0.12.0/30 is directly connected, GigabitEthernet0/0/1
L        10.0.12.1/32 is directly connected, GigabitEthernet0/0/1
      192.168.10.0/24 is variably subnetted, 2 subnets, 2 masks
C        192.168.10.0/24 is directly connected, GigabitEthernet0/0/0
L        192.168.10.1/32 is directly connected, GigabitEthernet0/0/0
```

`show ip interface brief` shows the address but **not the mask**; use `show ip interface`, `show running-config interface`, or the connected routes to confirm the prefix length.

IOS refuses some mistakes outright:

```ios
R1(config)# interface GigabitEthernet0/0/2
R1(config-if)# ip address 192.168.10.0 255.255.255.0
% Bad mask /24 for address 192.168.10.0
R1(config-if)# ip address 192.168.10.129 255.255.255.128
% 192.168.10.128 overlaps with GigabitEthernet0/0/0
```

The first is the network address itself; the second overlaps the existing 192.168.10.0/24 on Gi0/0/0. A router will not put two of its own interfaces in overlapping subnets (outside of VRFs).

## Fault 1: the wrong subnet mask

Suppose the real design is 192.168.10.0/25 (hosts .1-.126, gateway .1) and 192.168.10.128/25 is a different VLAN behind the same router.

**Mask too short.** PC-A is 192.168.10.20 with mask 255.255.255.0 instead of /25. When PC-A sends to 192.168.10.200 (in the other VLAN), it believes the destination is local and ARPs for it directly. No host on its segment owns that address, so the traffic fails. Remote destinations outside 192.168.10.0/24 still work because PC-A correctly sends those to the gateway.

> **Watch out:** IOS enables **proxy ARP** by default on Ethernet interfaces. If the router has a route to the destination out a *different* interface, it answers the misdirected ARP with its own MAC, and the "broken" mask appears to work. That hides the misconfiguration until someone disables proxy ARP. On the exam, assume the mask fault breaks connectivity unless the question mentions proxy ARP.

**Mask too long.** PC-B is 192.168.10.20/28. It thinks its subnet is 192.168.10.16/28 (hosts .17-.30). The gateway .1 is now **outside** its subnet, so PC-B has no reachable default gateway: it can talk only to .17-.30, and Windows warns that the gateway is not on the same network segment. (Some stacks, Windows included, may still try to ARP for an off-subnet gateway, so the exact symptom varies by OS; the fix is the same: correct the mask.)

## Fault 2: the wrong default gateway

* Gateway in another subnet: the host cannot ARP for it, so nothing off-subnet works.
* Gateway is a valid address in the subnet but is not the router (a typo such as .10 instead of .1): the host ARPs for .10 and either gets no reply or reaches a non-router host, so off-subnet traffic fails while on-subnet traffic is fine.
* Gateway is correct but the router interface is shut down, in the wrong VLAN, or has a different address/mask than documented.

The signature of a gateway problem: **ping to hosts on the same subnet works, ping to anything remote fails**, and `tracert` dies at the first hop.

## Fault 3: overlapping subnets

Overlaps across *different* routers are not rejected by IOS. Two branches that both use 10.10.10.0/24, or a VLSM plan that hands out 172.16.4.0/22 and 172.16.6.0/24, produce routing confusion: the more specific route wins, so traffic for some hosts goes to the wrong site. Check with:

```ios
R1# show ip route 172.16.6.25
```

and compare the matched prefix with the documented location of that host. Fix by readdressing one side (or by NAT when merging networks you cannot renumber).

## Fault 4: duplicate IP addresses

Two devices using the same address cause intermittent, confusing failures because the ARP caches of other hosts flip between two MAC addresses.

Evidence:

* Windows: a pop-up "Windows has detected an IP address conflict", and `ipconfig /all` may show the address marked `(Duplicate)`.
* IOS logs a message when another device claims one of its own addresses:

```ios
%IP-4-DUPADDR: Duplicate address 192.168.10.1 on GigabitEthernet0/0/0, sourced by 0050.56b2.11a4
```

* `show ip arp` (or `arp -a` on a host) showing the expected IP mapped to an unexpected MAC.

Find the offender by tracing that MAC: `show mac address-table address 0050.56b2.11a4` on the switches. Common causes: a static address configured inside a DHCP pool, a device restored from an old backup, or a second DHCP server.

> **Exam tip:** DHCP clients usually detect conflicts themselves: after receiving an address they ARP for it, and if someone answers they send **DHCPDECLINE**. An IOS DHCP server also pings an address before offering it and records conflicts in `show ip dhcp conflict`.

## Fault 5: APIPA (169.254.x.x)

A Windows, macOS, or Linux host configured for DHCP that hears no reply assigns itself an address from **169.254.0.0/16** (Automatic Private IP Addressing / IPv4 link-local) with **no default gateway**. It can reach only other 169.254 hosts on the same link.

An APIPA address means "DHCP failed", so check, in order:

1. Physical link and switch port status (is the port up, in the right VLAN?).
2. Whether a DHCP server or relay (`ip helper-address`) exists for that VLAN.
3. Whether the pool is exhausted or the server is unreachable from the relay.

## Fault 6: using reserved addresses

* Assigning the network or broadcast address to a host: most OSs refuse; IOS gives `Bad mask`.
* Assigning a host an address from the wrong VLAN's subnet: it may get a link but nothing beyond.
* Using 127.x.x.x or 169.254.x.x as a static address: not routable.

## A systematic workflow

1. **Verify the host config**: address, mask, gateway, DNS (`ipconfig /all`, `ip addr`, `ifconfig`).
2. **Calculate** the host's subnet from its address/mask. Is the gateway inside it? Is the address the network or broadcast address?
3. **Ping the loopback** (127.0.0.1) to test the local stack, then **ping the gateway**, then **a remote IP**, then **a remote name**. The first failure tells you which layer to fix.
4. **Check the router side**: interface up/up, correct address and mask, correct VLAN, no overlap.
5. **Look for duplicates**: ARP tables, IOS logs, `show ip dhcp conflict`.

## Key takeaways

* A host uses its own mask to decide local versus remote; a wrong mask breaks some destinations but not others.
* Gateway faults: same-subnet traffic works, everything remote fails, traceroute dies at hop 1.
* IOS rejects overlapping subnets on its own interfaces (`overlaps with`), but not across different routers.
* Duplicate IPs cause intermittent failures; look for `%IP-4-DUPADDR`, ARP entries with unexpected MACs, and DHCPDECLINE.
* 169.254.0.0/16 on a client means DHCP failed; the host has no gateway.
* Proxy ARP on IOS can hide a wrong mask on a host.
* Use `show ip interface` or `show ip route connected` to see the mask; `show ip interface brief` does not show it.
