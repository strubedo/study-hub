## A layered workflow

When "the network is down" for one user, work up the stack and stop at the first failure:

1. **Link / association**: Is the cable connected and the port up? On Wi-Fi, is the client associated to the right SSID, with what security and what signal?
2. **IP configuration**: Address, mask, default gateway, DNS. Is the address an APIPA 169.254.x.x? Is the gateway inside the client's subnet?
3. **Local reachability**: Ping the default gateway. Check the ARP/neighbor table for the gateway's MAC.
4. **Remote reachability**: Ping a remote IP; traceroute to see where packets stop.
5. **Name resolution**: Resolve a name with nslookup/dig. If IP works but names do not, it is DNS.
6. **Application**: Test the actual TCP port (for example 443).

The commands differ per OS; the logic does not.

## Command map

| Task | Windows | macOS | Linux |
|---|---|---|---|
| Show IP config | `ipconfig /all` | `ifconfig en0`, `ipconfig getifaddr en0`, `networksetup -getinfo "Wi-Fi"` | `ip addr` (`ip -br a`) |
| Routes / gateway | `route print`, `ipconfig` | `netstat -rn`, `route -n get default` | `ip route` |
| Renew DHCP | `ipconfig /release`, `ipconfig /renew` | `sudo ipconfig set en0 DHCP` | `nmcli connection up <name>`, `dhclient` (distro-dependent) |
| ARP / neighbors | `arp -a` | `arp -a` | `ip neigh` |
| Path | `tracert` (ICMP) | `traceroute` (UDP by default) | `traceroute` (UDP by default), `tracepath` |
| DNS lookup | `nslookup` | `nslookup`, `dig`, `scutil --dns` | `dig`, `nslookup`, `resolvectl status`, `/etc/resolv.conf` |
| Flush DNS cache | `ipconfig /flushdns` | `sudo dscacheutil -flushcache` | `resolvectl flush-caches` (systemd-resolved) |
| Wi-Fi details | `netsh wlan show interfaces` | `sudo wdutil info`, Option-click the Wi-Fi icon | `nmcli device wifi list`, `iw dev wlan0 link` (older: `iwconfig`) |
| Port test | `Test-NetConnection host -Port 443` (PowerShell) | `nc -vz host 443` | `nc -vz host 443` |

Things to read in `ipconfig /all`:

* **Autoconfiguration IPv4 Address 169.254.x.x** with a 255.255.0.0 mask and no gateway: DHCP failed.
* **DHCP Server** shows which server (or, with a relay, which server behind the relay) granted the lease; a surprising value can reveal a rogue DHCP server.
* **(Duplicate)** after the address: an IP conflict was detected.
* **Default Gateway** blank: nothing off-subnet will work.

This output answers the wireless questions in one shot: which SSID and BSSID (which AP), which band and channel, which **authentication and cipher** were negotiated, and how strong the signal is. Field names vary by Windows version: Windows 11 adds the **Band** line, and only very recent Windows 11 builds add the **Rssi** line in dBm; older builds show signal only as a vendor-scaled percentage. `netsh wlan show profiles` lists saved networks, and `netsh wlan show profile name="CORP"` shows the security a saved profile expects.

> **Exam tip:** Windows `tracert` sends ICMP Echo Requests; macOS and Linux `traceroute` send UDP probes to high ports by default. A firewall that blocks one may allow the other, so the two tools can show different results for the same path.

```
	nd6 options=201<PERFORMNUD,DAD>
	media: autoselect

192.168.10.47

% networksetup -getinfo "Wi-Fi"
DHCP Configuration
IP address: 192.168.10.47
Subnet mask: 255.255.255.0
Router: 192.168.10.1
Client ID:
IPv6: Automatic
IPv6 IP address: none
IPv6 Router: none
Wi-Fi ID: a4:83:e7:5c:19:2b
```

* macOS `ifconfig` prints the **mask in hex**: `0xffffff00` = 255.255.255.0 (/24), `0xfffffe00` = 255.255.254.0 (/23), `0xffffffc0` = 255.255.255.192 (/26).
* `en0` is usually Wi-Fi on laptops (on some desktops it is Ethernet); `networksetup -listallhardwareports` maps names to hardware.
* `networksetup -getdnsservers "Wi-Fi"` shows manually set DNS servers; `scutil --dns` shows the resolvers actually in use.
* For Wi-Fi details, `sudo wdutil info` shows SSID, BSSID, RSSI, noise, channel, and security. The older `airport -I` utility was deprecated in macOS 14.4 (Sonoma) and no longer reports Wi-Fi details; Apple points users to `wdutil` and the Wireless Diagnostics app. Recent versions may also redact the SSID/BSSID in `wdutil` output.

## Linux

```
$ ip -br addr
lo               UNKNOWN        127.0.0.1/8 ::1/128
wlan0            UP             10.20.30.88/24 fe80::5a2f:1bff:fe40:7c11/64

$ ip route
default via 10.20.30.1 dev wlan0 proto dhcp src 10.20.30.88 metric 600
10.20.30.0/24 dev wlan0 proto kernel scope link src 10.20.30.88 metric 600

$ iw dev wlan0 link
Connected to 70:6d:15:a2:4c:40 (on wlan0)
	SSID: CORP
	freq: 5180
	signal: -58 dBm
	rx bitrate: 433.3 MBit/s VHT-MCS 9 80MHz short GI VHT-NSS 1
	tx bitrate: 390.0 MBit/s VHT-MCS 8 80MHz short GI VHT-NSS 1

$ nmcli -f NAME,TYPE,DEVICE connection show --active
NAME  TYPE      DEVICE
CORP  wifi      wlan0
```

* `ip addr` shows addresses in CIDR form; `ip route` shows the default gateway (`default via`). `proto dhcp` means it was learned from DHCP.
* `iw dev wlan0 link` shows the BSSID, SSID, frequency (5180 MHz = channel 36), and signal in dBm. `iwconfig` is the deprecated wireless-tools equivalent.
* NetworkManager: `nmcli device status`, `nmcli device wifi list` (SSIDs, channels, signal, security), and `nmcli connection show CORP | grep key-mgmt` shows `wpa-psk` (WPA2-Personal), `sae` (WPA3-Personal), or `wpa-eap` (Enterprise).
* DNS: `/etc/resolv.conf` lists `nameserver` entries. On systemd-resolved systems it usually shows `nameserver 127.0.0.53` (the local stub resolver); run `resolvectl status` to see the real upstream servers.

```
$ dig www.corp.example +short
10.10.60.25
$ dig @10.10.50.53 www.corp.example
;; ->>HEADER<<- opcode: QUERY, status: NOERROR, id: 40112
;; ANSWER SECTION:
www.corp.example.	300	IN	A	10.10.60.25
;; SERVER: 10.10.50.53#53(10.10.50.53)
```

`status: NXDOMAIN` means the name does not exist; a timeout ("connection timed out; no servers could be reached") means the DNS server is unreachable.

## Interpreting results

| Evidence | Points to |
|---|---|
| 169.254.x.x address, no gateway | DHCP failure (VLAN, relay, server, pool) |
| Valid IP, ping to gateway fails, ARP entry for gateway missing or "incomplete" | Wrong VLAN, gateway down, wrong gateway address, or Wi-Fi client isolation |
| Gateway pings, remote IP fails, traceroute stops after hop 1 | Routing or ACL beyond the gateway, or the gateway lacks a route/NAT |
| Remote IP pings, name does not resolve | DNS server setting or DNS server problem |
| Name resolves to the wrong address | Stale cache (flush it), hosts file entry, or wrong DNS server |
| Wi-Fi: associated but prompted again for password | Wrong PSK / SAE password |
| Wi-Fi: strong signal (e.g., -50 dBm) but slow, many retries | Interference / low SNR, co-channel congestion |
| Wi-Fi: weak signal (e.g., -80 dBm) | Coverage problem: distance, obstacles, sticky client roaming poorly |
| Wi-Fi: authentication shows WPA2-Personal on a corporate laptop | Joined the wrong SSID (for example guest) |

> **Watch out:** "Ping works but the web page will not load" is not a Layer 3 problem. Check DNS, the proxy configuration, and whether the TCP port is reachable (`Test-NetConnection -Port 443` or `nc -vz`).

> **Real world:** Many firewalls (including Windows Defender Firewall by default) block inbound ICMP Echo. A failed ping to a *host* is weak evidence; a failed ping to the *router* is stronger.

## Key takeaways

* Troubleshoot bottom-up: link/association, IP config, gateway, remote IP, DNS, application.
* Windows: `ipconfig /all`, `netsh wlan show interfaces`, `arp -a`, `tracert` (ICMP), `nslookup`.
* macOS: `ifconfig` (hex mask), `ipconfig getifaddr en0`, `networksetup -getinfo`, `traceroute` (UDP), `wdutil info`.
* Linux: `ip addr`, `ip route`, `ip neigh`, `nmcli`, `iw dev wlan0 link`, `dig`, `/etc/resolv.conf` / `resolvectl`.
* 169.254.x.x = DHCP failure; blank gateway = no off-subnet access; IP works but names fail = DNS.
* Wireless checks: SSID/BSSID, band/channel, authentication/cipher, RSSI in dBm, and SNR.
