## Why network engineers care about virtualization

Most servers you connect to a switch port today are not one operating system on one box. They are hypervisor hosts running dozens of virtual machines, or container hosts running hundreds of containers. The access port facing that host carries traffic for many workloads in many VLANs, and part of the "network" (the virtual switch) lives in software inside the server. Topic 1.2 asks you to **describe** these building blocks, so focus on roles, differences, and how they attach to the physical network.

## Virtualization basics

Server virtualization lets one physical server (the **host**) run several isolated **guest** operating systems. The software layer that makes this possible is the **hypervisor**, also called a virtual machine monitor (VMM). It:

* Presents each VM with virtual hardware: vCPUs, virtual RAM, virtual disks, and virtual NICs (vNICs)
* Schedules the real CPUs and memory among the VMs
* Isolates VMs from one another, so a crash in one guest does not take down the others

Benefits: better hardware utilization (consolidation), fast provisioning from templates, snapshots, and live migration of running VMs between hosts (for example vMotion) for maintenance and load balancing.

## Type 1 vs type 2 hypervisors

| | Type 1 (bare-metal / native) | Type 2 (hosted) |
|---|---|---|
| Runs on | Directly on the server hardware | On top of a conventional host OS |
| Examples | VMware ESXi, Microsoft Hyper-V, Xen, KVM (see note) | Oracle VirtualBox, VMware Workstation/Fusion, Parallels Desktop |
| Performance | High; no general-purpose OS in the path | Lower; host OS adds overhead |
| Typical use | Data centers, production servers, cloud | Labs, desktops, testing, running another OS on a laptop |
| Management | Often centrally managed (for example vCenter) | Managed through the desktop application |

> **Watch out:** KVM is a Linux kernel module that turns the Linux kernel itself into the hypervisor, so it is generally classed as type 1 even though a full Linux OS is present. Hyper-V is also type 1: when the role is enabled, Windows itself runs as a privileged partition on top of the hypervisor.

> **Exam tip:** If the question mentions a laptop or desktop user running a VM inside an application window, it is type 2. If it mentions a server booting straight into the virtualization layer, it is type 1.

## Virtual machines vs containers

A **virtual machine** virtualizes the hardware. Each VM boots its own complete guest OS, with its own kernel.

A **container** virtualizes the operating system. Containers share the host's kernel and package only the application plus its libraries and dependencies. Kernel features (on Linux, namespaces for isolation and cgroups for resource limits) keep each container separate.

| Attribute | Virtual machine | Container |
|---|---|---|
| What is virtualized | Hardware | Operating system (user space) |
| Includes | Full guest OS + kernel + app | App + libraries/dependencies only |
| Kernel | Each VM has its own | Shared with the host |
| Typical size | Gigabytes | Megabytes |
| Startup time | Tens of seconds to minutes (OS boot) | Sub-second to seconds (process start) |
| Isolation | Strong (hardware-level boundary) | Weaker (shared kernel) |
| Mixed OS on one host | Yes (Windows and Linux VMs side by side) | Containers must match the host kernel type (Linux containers need a Linux kernel) |
| Density per host | Lower | Much higher |

The key phrase to remember: **VMs carry an OS; containers carry an application.** Containers are portable because the image includes everything the app needs, so "it works on my machine" becomes "it works on every machine with a container runtime".

### Container terms

* **Image**: a read-only template (layers of files) from which containers are created. Stored in a **registry** (for example Docker Hub or a private registry).
* **Container**: a running instance of an image.
* **Container runtime / engine**: software that pulls images and runs containers on a host, for example Docker Engine, containerd, CRI-O, Podman.
* **Orchestration**: software that manages many containers across a cluster of hosts: scheduling, scaling, restarting failed containers, rolling upgrades, and service discovery. **Kubernetes** is the dominant orchestrator; Docker Swarm is a simpler alternative. In Kubernetes, containers run inside **pods** on worker **nodes**.

> **Real world:** Cisco uses containers on network devices too. Catalyst 9000 switches can run Docker-format containers through application hosting (IOx), and many network automation tools ship as container images.

## Virtual switching

VMs need network connectivity, so the hypervisor includes a **virtual switch (vSwitch)**, a software Layer 2 switch inside the host.

* Each VM's vNIC connects to a port (or **port group**) on the vSwitch.
* The vSwitch's **uplinks** are the server's physical NICs, which connect to physical switch ports.
* Traffic between two VMs on the same host and same VLAN/port group is switched inside the host and **never touches the physical network**.
* Port groups are usually mapped to VLANs, and the vSwitch tags frames with 802.1Q on its uplinks. The physical switch port facing the host is therefore usually an **802.1Q trunk** allowing those VLANs, often bundled into an EtherChannel or NIC team for redundancy.

| Platform | Virtual switch |
|---|---|
| VMware ESXi | Standard vSwitch (per host), Distributed Switch (vDS) managed centrally by vCenter |
| Microsoft Hyper-V | Hyper-V Virtual Switch (external, internal, private) |
| Linux / KVM | Linux bridge, Open vSwitch (OVS) |

Containers also get virtual networking: by default a Docker host creates a Linux bridge (`docker0`), gives each container a private IP behind it, and uses NAT/port mapping to expose services on the host's IP.

> **Watch out:** When a VM cannot reach the network but other VMs on the same host can, think about the virtual layer: wrong port group/VLAN on the vNIC, or the VLAN not allowed on the physical trunk to that host.

## Network functions virtualization

The same idea applies to network devices. **NFV** replaces dedicated appliances with software versions running as VMs or containers: virtual routers (Cisco Catalyst 8000V), virtual firewalls, virtual WLAN controllers (Catalyst 9800-CL), and load balancers. In public cloud, these are the only option because you cannot install your own hardware.

## Putting it together

A typical data center rack might look like this:

1. A physical server boots a **type 1 hypervisor**.
2. The hypervisor runs several **VMs**, each with its own guest OS.
3. One VM is a Linux host running a **container runtime**, and an orchestrator such as Kubernetes schedules containers across many such VMs.
4. VM vNICs attach to **port groups on a virtual switch**, which tags frames with VLAN IDs.
5. The server's physical NICs uplink to **802.1Q trunk ports** on the top-of-rack switch.

## Key takeaways

* A hypervisor creates and runs VMs, presenting virtual hardware and isolating guests.
* **Type 1** runs on bare metal (ESXi, Hyper-V, KVM, Xen); **type 2** runs on a host OS (VirtualBox, Workstation, Fusion).
* VMs include a full guest OS and kernel; containers share the host kernel and include only the app and its dependencies.
* Containers are smaller and start faster; VMs give stronger isolation and can run different OS types on one host.
* Container runtimes (Docker Engine, containerd, CRI-O) run containers; orchestrators (Kubernetes) manage them at scale.
* A vSwitch connects vNICs to the host's physical NICs; VM-to-VM traffic on the same host and VLAN stays inside the host.
* The physical switch port facing a virtualization host is usually an 802.1Q trunk.
