## What AAA adds

Local usernames work, but they do not scale. With 300 switches, changing one admin's password means 300 config changes, and you have no central record of who ran which command. AAA moves those decisions to a server:

* **Authentication** – who are you? (username/password, certificate, token)
* **Authorization** – what may you do? (privilege level, which commands)
* **Accounting** – what did you do? (login/logout times, commands entered)

The network device is the **AAA client** (Cisco also calls it the NAS, network access server). It forwards credentials to an AAA server such as Cisco ISE, which answers accept or reject.

## TACACS+ vs RADIUS

| Feature | TACACS+ | RADIUS |
|---------|---------|--------|
| Transport | TCP port 49 | UDP 1812 (authentication) and 1813 (accounting); legacy 1645/1646 |
| Encryption | Entire packet body (header stays clear) | Only the user password attribute |
| AAA functions | Separate authentication, authorization and accounting | Authentication and authorization combined in one Access-Accept |
| Per-command authorization | Yes, every command can be checked | Not natively |
| Origin | Cisco-developed, documented in RFC 8907 | Open standard (RFC 2865/2866) |
| Typical use | **Device administration** (CLI access to routers, switches, firewalls) | **Network access** (802.1X, VPN users, wireless) |

> **Exam tip:** Remember the pairings: TACACS+ = TCP 49, full-body encryption, separates AAA, device admin. RADIUS = UDP 1812/1813, password-only encryption, combines authN and authZ, network access.

Because TACACS+ runs over TCP, the client knows quickly whether the server is reachable (the TCP session either opens or does not). RADIUS over UDP relies on retransmit timers.

## Turning AAA on safely

`aaa new-model` is the master switch. The moment you enter it, the old line-level `login`/`login local` commands stop being used for VTY lines and AAA method lists take over. With no method list defined, IOS falls back to the local database for VTY logins, but it is easy to lock yourself out if you build the server pieces in the wrong order. A safe sequence:

1. Create a local privilege 15 account first (break-glass).
2. Keep a console session open while you work.
3. Enter `aaa new-model`.
4. Define servers and a server group.
5. Build method lists that end in `local`.
6. Test with a second SSH session before closing the first.

## Defining servers and groups (IOS XE syntax)

Current IOS XE uses named server blocks. The older single-line `tacacs-server host 10.1.1.10 key ...` form is deprecated.

```ios
R1(config)# username breakglass privilege 15 algorithm-type scrypt secret L0cal!Only
R1(config)# aaa new-model
R1(config)# tacacs server ISE-1
R1(config-server-tacacs)# address ipv4 10.1.100.10
R1(config-server-tacacs)# key T@cacsK3y
R1(config-server-tacacs)# exit
R1(config)# tacacs server ISE-2
R1(config-server-tacacs)# address ipv4 10.1.100.11
R1(config-server-tacacs)# key T@cacsK3y
R1(config-server-tacacs)# exit
R1(config)# aaa group server tacacs+ TACACS-GRP
R1(config-sg-tacacs+)# server name ISE-1
R1(config-sg-tacacs+)# server name ISE-2
R1(config-sg-tacacs+)# ip tacacs source-interface Loopback0
R1(config-sg-tacacs+)# exit
```

RADIUS looks almost identical:

```ios
R1(config)# radius server RAD-1
R1(config-radius-server)# address ipv4 10.1.100.20 auth-port 1812 acct-port 1813
R1(config-radius-server)# key R@diusK3y
R1(config-radius-server)# exit
R1(config)# aaa group server radius RAD-GRP
R1(config-sg-radius)# server name RAD-1
```

The shared **key** must match the key configured for this client on the server. A key mismatch makes the server unable to decrypt the request, so the login fails.

> **Real world:** The AAA server identifies the client by the request's **source IP address**. Pin it with `ip tacacs source-interface` (or `ip radius source-interface`) so it is always the loopback that is registered on ISE, regardless of which interface the packet leaves.

## Method lists

A method list is an ordered list of places to check. The `default` list applies automatically to every line that does not reference a named list.

```ios
R1(config)# aaa authentication login default group TACACS-GRP local
R1(config)# aaa authorization exec default group TACACS-GRP local
R1(config)# aaa accounting exec default start-stop group TACACS-GRP
R1(config)# aaa accounting commands 15 default start-stop group TACACS-GRP
```

* `aaa authentication login` – who may log in.
* `aaa authorization exec` – whether the user gets an EXEC shell and at what privilege level (the server can return privilege 15 so the user skips `enable`).
* `aaa accounting exec` / `commands` – logs session start/stop and commands.

You can also build a named list and apply it to specific lines:

```ios
R1(config)# aaa authentication login VTY-AUTH group TACACS-GRP local
R1(config)# line vty 0 15
R1(config-line)# login authentication VTY-AUTH
```

### The fallback rule: ERROR vs FAIL

This is the most tested AAA behavior.

* The router tries the **first** method (the TACACS+ group). Inside the group it tries each server in order.
* If a server **answers** with a reject (wrong password, unknown user), that is a **FAIL**. Authentication stops. The user is denied. The `local` method is **not** tried.
* Only if **no server in the group responds** (timeout, unreachable, TCP refused) is it an **ERROR**, and the router moves on to the next method (`local`).

> **Watch out:** Typing a local username while the TACACS+ server is up does **not** work unless that same account exists on the server. The server rejects it, which is a FAIL, so `local` is never consulted.

Order also expresses intent. `aaa authentication login default local group TACACS-GRP` checks the local database before the server is ever consulted, which defeats central control. The normal design is server group first and `local` last, so the local database is used only when every server is unreachable.

### `local` vs `local-case`

`local` uses the local username database with case-insensitive usernames; `local-case` makes usernames case-sensitive. Passwords are always case-sensitive.

## Verification and troubleshooting

```ios
R1# show aaa servers
RADIUS: id 1, priority 1, host 10.1.100.20, auth-port 1812, acct-port 1813
     State: current UP, duration 86312s, previous duration 0s
...
TACACS+: id 2, priority 1, host 10.1.100.10, port 49
     State: current UP, duration 86290s, previous duration 0s
R1# test aaa group TACACS-GRP jdoe P@ss1234 new-code
User was successfully authenticated.
R1# debug aaa authentication
R1# debug tacacs
```

| Symptom | Likely cause |
|---------|-------------|
| Everyone rejected, server logs show "invalid shared secret" | Key mismatch between router and server |
| Server never sees the request | Wrong server IP, ACL/firewall blocking TCP 49 or UDP 1812, wrong source interface not registered on server |
| Login works but user lands at `>` | No `aaa authorization exec`, or server not returning privilege 15 |
| Local account rejected while server is up | Expected: server reject = FAIL, no fallback |
| Locked out after `aaa new-model` | No working method; use the console with a local account |

## TACACS+ authorization for commands

With TACACS+ you can authorize each command:

```ios
R1(config)# aaa authorization commands 15 default group TACACS-GRP local
```

Now every privilege 15 command is sent to the server before it runs. The server can allow `show` commands but deny `reload` or `configure terminal` for a helpdesk group. RADIUS cannot do this per command, which is the main reason TACACS+ is preferred for device administration.

> **Exam tip:** If a question asks which protocol lets you control **which commands** an administrator can run, the answer is TACACS+.

## Key takeaways

* `aaa new-model` enables AAA and replaces line-level `login local` with method lists.
* TACACS+: TCP 49, encrypts the whole body, separates authN/authZ/accounting, per-command authorization, device admin.
* RADIUS: UDP 1812/1813, encrypts only the password, combines authN and authZ, network access.
* Current IOS XE uses `tacacs server NAME` / `radius server NAME` blocks plus `aaa group server`.
* Methods are tried in order; the next method is used only on ERROR (no server response), never on FAIL (server rejected).
* Put `local` last and keep a local break-glass account; set the AAA source interface so the server recognizes the client.
