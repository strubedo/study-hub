## Why syslog matters

Syslog is the device's running diary. Every interface flap, neighbor loss, configuration change, login and port-security violation produces a message. Blueprint 5.6 says *interpret*: you will be shown log lines and asked what happened, how severe it is, and whether a given message reaches a given destination. With AI assistants summarizing logs, you also need to know enough to catch a summary that gets it wrong.

## Anatomy of an IOS log message

```ios
*Mar  1 00:01:23.456: %LINK-3-UPDOWN: Interface GigabitEthernet0/0/1, changed state to down
```

| Part | Value | Meaning |
|---|---|---|
| Sequence number | (absent) | Present only with `service sequence-numbers` |
| Timestamp | `*Mar  1 00:01:23.456` | Date/time with milliseconds (`service timestamps log datetime msec`) |
| Leading `*` | `*` | The clock is **not authoritative** — not set or not synchronized (e.g., no NTP) |
| Facility | `LINK` | The IOS subsystem that generated the message |
| Severity | `3` | Errors |
| Mnemonic | `UPDOWN` | Short code identifying the specific message |
| Description | `Interface GigabitEthernet0/0/1, changed state to down` | Human-readable detail |

The core format is **`%FACILITY-SEVERITY-MNEMONIC: description`**. With sequence numbers enabled the line starts with a counter such as `000113:`.

> **Exam tip:** "Mar 1 00:00:xx" with an asterisk is the classic sign of a router whose clock was never set and is not synced to NTP — it starts counting from a default date at boot. Unsynchronized clocks make correlating logs across devices nearly impossible.

## Severity levels

| Level | Keyword (IOS) | Typical examples |
|---|---|---|
| 0 | emergencies | System unusable |
| 1 | alerts | Immediate action needed (e.g., some temperature alarms) |
| 2 | critical | Critical condition (e.g., `%PORT_SECURITY-2-PSECURE_VIOLATION`) |
| 3 | errors | Error condition (e.g., `%LINK-3-UPDOWN`) |
| 4 | warnings | Warning (e.g., `%PM-4-ERR_DISABLE`, `%SEC_LOGIN-4-LOGIN_FAILED`) |
| 5 | notifications | Normal but significant (e.g., `%LINEPROTO-5-UPDOWN`, `%OSPF-5-ADJCHG`, `%SYS-5-CONFIG_I`) |
| 6 | informational | Informational messages |
| 7 | debugging | Output of `debug` commands |

Mnemonic for the order: **E**very **A**wesome **C**isco **E**ngineer **W**ill **N**eed **I**ce cream **D**aily.

**Lower number = more severe.** Setting a level on a destination sends **that level and every more severe (lower-numbered) level**:

* `logging trap 4` (or `logging trap warnings`) sends levels 0–4 to the syslog server.
* `logging trap informational` (the default for remote syslog) sends 0–6.
* `logging console debugging` sends everything, 0–7.

> **Watch out:** `%LINK-3-UPDOWN` (physical layer, severity 3) and `%LINEPROTO-5-UPDOWN` (line protocol, severity 5) are two different messages. With `logging trap warnings`, the server gets the LINK message but **not** the LINEPROTO one.

## Common messages to recognize

```ios
000112: Oct 23 14:02:11.207 EDT: %LINK-3-UPDOWN: Interface GigabitEthernet0/0/1, changed state to down
000113: Oct 23 14:02:11.211 EDT: %OSPF-5-ADJCHG: Process 1, Nbr 2.2.2.2 on GigabitEthernet0/0/1 from FULL to DOWN, Neighbor Down: Interface down or detached
000114: Oct 23 14:02:12.207 EDT: %LINEPROTO-5-UPDOWN: Line protocol on Interface GigabitEthernet0/0/1, changed state to down
```

Read it as a story: the physical link dropped, OSPF immediately tore down the adjacency because the interface went down (not because the dead timer expired — that reason would say `Dead timer expired`), and the line-protocol message followed about a second later, which is the usual gap between the LINK and LINEPROTO messages.

| Message | What it tells you |
|---|---|
| `%LINK-5-CHANGED: Interface ..., changed state to administratively down` | Someone (or something) issued `shutdown` |
| `%SYS-5-CONFIG_I: Configured from console by admin on vty0 (10.1.1.5)` | A configuration change, who made it and from where |
| `%PM-4-ERR_DISABLE: bpduguard error detected on Gi1/0/5, putting Gi1/0/5 in err-disable state` | Port error-disabled; the cause is named |
| `%PORT_SECURITY-2-PSECURE_VIOLATION: Security violation occurred, caused by MAC address ... on port ...` | Port-security violation by that MAC |
| `%OSPF-5-ADJCHG: ... from LOADING to FULL, Loading Done` | Adjacency came up |
| `%SEC_LOGIN-4-LOGIN_FAILED` / `%SEC_LOGIN-5-LOGIN_SUCCESS` | Login failure / success (logged when `login on-failure log` / `login on-success log` are configured) |

## Destinations

| Destination | Command | Notes |
|---|---|---|
| Console | `logging console <level>` | Default level debugging; can slow a router under heavy logging |
| Terminal lines (VTY) | `logging monitor <level>` + `terminal monitor` | Each SSH/Telnet session must run `terminal monitor` (exec command) to see logs |
| Buffer (RAM) | `logging buffered <size> <level>` | View with `show logging`; lost on reload |
| Syslog server | `logging host <ip>` + `logging trap <level>` | UDP 514 by default; default level informational |

```ios
R1(config)# service timestamps log datetime msec localtime show-timezone
R1(config)# service sequence-numbers
R1(config)# logging buffered 16384 informational
R1(config)# logging host 10.10.50.30
R1(config)# logging trap warnings
R1(config)# logging source-interface Loopback0
R1(config)# logging facility local5
R1(config)# line vty 0 4
R1(config-line)# logging synchronous
```

* `logging source-interface` makes every message come from a stable address, which helps the server identify the device.
* `logging synchronous` (line config) stops log messages from interrupting what you are typing.
* `show logging` shows the configured destinations and levels plus the buffer contents.

> **Exam tip:** You SSH into a router, run `debug ip ospf adj` and see nothing. The usual fix is `terminal monitor` — log output goes to VTY sessions only when the session asks for it.

## Facilities — two different meanings

The word "facility" is used in two ways, and exam questions exploit the confusion:

1. **IOS message facility** — the `LINK`, `OSPF`, `SYS` in `%OSPF-5-ADJCHG`. It names the software subsystem that produced the message. You cannot change it.
2. **Syslog protocol facility** — a field in the syslog packet that the *server* uses to sort messages. Network devices conventionally use **local0–local7** (codes 16–23). IOS sends **local7** by default; change it with `logging facility local5`. Every message from that router — OSPF, LINK, SYS alike — is then tagged local5.

The syslog packet's priority value combines both fields: PRI = facility code × 8 + severity. A severity 3 message sent with facility local7 (23) carries PRI `<187>`.

> **Real world:** Teams often give each device class a different local facility (e.g., local5 for routers, local6 for firewalls) so the syslog server can file messages into separate logs. That works only because the syslog facility is independent of the IOS message facility.

## Interpreting under pressure

When you read a log exhibit:

1. Check the timestamp and whether the clock is trustworthy (`*`).
2. Read facility and severity: what subsystem, how bad?
3. Order events: what happened first? Later messages are often consequences.
4. Read the reason text: `administratively down` vs plain `down`; `Dead timer expired` vs `Interface down or detached`.
5. Ask whether the destination's level would even include the message.

> **Watch out:** If an AI assistant summarizes logs, verify its severity reading against the number in the message. A summary claiming "severity 2 is less important than severity 4" has it backwards.

## Key takeaways

* Format: `seq: timestamp: %FACILITY-SEVERITY-MNEMONIC: description`; a leading `*` means the clock is not authoritative.
* Levels 0–7: emergencies, alerts, critical, errors, warnings, notifications, informational, debugging.
* A configured level includes itself and everything more severe: `logging trap 4` sends 0–4.
* Destinations: console, monitor (needs `terminal monitor`), buffer (`show logging`), host (UDP 514, default level informational).
* `service timestamps log datetime msec` adds date/time with milliseconds; NTP makes the times trustworthy.
* IOS message facility (OSPF, LINK) differs from the syslog facility (local0–local7; IOS default local7).
* `%LINK-3-UPDOWN` = physical state change (severity 3); `%LINEPROTO-5-UPDOWN` = line protocol (severity 5).
