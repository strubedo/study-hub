## Prompts are change requests for a model

A generative AI system answers the prompt it is given — no more. A vague prompt gets a generic, often wrong, answer; a prompt with secrets in it leaks those secrets. Blueprint 5.2 asks you to **select** the best prompt, weighing **data classification, output format, persona and instructions**. In exam terms that usually means comparing four candidate prompts and choosing the one that is specific, grounded in sanitized data, constrained, and asks for a usable format.

## The components of a good prompt

| Component | Purpose | Example |
|---|---|---|
| **Persona / role** | Sets expertise and point of view | "You are a senior enterprise network engineer reviewing a change for a hospital network." |
| **Instruction / task** | States exactly what to do | "Identify which access ports are missing port security." |
| **Context** | Supplies the facts the model needs | "Below is sanitized `show running-config | section interface` output from ACC-SW2, a Catalyst 9200 running IOS-XE 17.9." |
| **Constraints** | Sets boundaries | "Use only IOS-XE commands. Do not modify trunk ports. If the data is insufficient, say so." |
| **Output format** | Shapes the answer for its consumer | "Return a table: Interface, Issue, Recommended command." |
| **Examples (few-shot)** | Shows the pattern you want | "Example row: Gi1/0/3, no port security, switchport port-security" |

Not every prompt needs all six, but the strongest candidate in an exam question will normally have a clear task, relevant sanitized context and an explicit output format.

### Persona

A persona focuses the model on the right vocabulary and depth. "You are a Cisco network engineer" makes IOS syntax more likely than Junos or Linux commands. A persona alone is not enough — "Act as an expert and tell me everything" is still a bad prompt.

### Instructions

Good instructions are specific and verifiable: *what device*, *what problem*, *what deliverable*. Compare:

* Weak: "Why is my network slow?"
* Strong: "Using the interface counters below, identify the most likely cause of the input errors on Gi0/0/1 and list up to three show commands to confirm it."

### Context — grounding the answer

Pasting relevant **sanitized** output (show commands, log excerpts, the platform and software version) grounds the answer in your network instead of generic internet knowledge and reduces hallucination. It does not make the answer guaranteed correct, and it does not retrain the model — it only informs this conversation.

Include what matters: platform, software version, the specific outputs that show the symptom, what has already been tried. Leave out what doesn't.

### Constraints

Constraints prevent unsafe or irrelevant answers:

* "Diagnose only — do not propose configuration changes yet."
* "Use the `add` keyword so no existing VLANs are removed from the trunk."
* "Do not touch interfaces other than Gi1/0/49 and Gi1/0/50."
* "If you are not certain a command exists on IOS-XE 17.9, say so."
* "Include verification commands and a rollback."

> **Watch out:** `switchport trunk allowed vlan 40` *replaces* the allowed list; `switchport trunk allowed vlan add 40` appends. A prompt that doesn't constrain this — or that dictates the wrong command — can turn an AI-drafted change into an outage.

### Output format

Ask for the format the next step needs:

| Consumer | Format to request |
|---|---|
| A human comparing findings | Markdown table with named columns |
| A script or ticketing system | JSON with an explicit schema; "return only JSON, no prose" |
| A device or change ticket | A single IOS configuration block, plus separate verification and rollback blocks |
| Automation tooling | YAML (e.g., Ansible variables or a playbook) |
| A manager or shift handoff | Short bullet summary with impact and next steps |

Example JSON instruction:

```text
Return only a JSON array. Each element must have exactly these keys:
"device" (string), "interface" (string), "severity" (integer 0-7),
"summary" (string). Do not include any text outside the JSON.
```

## Data classification and redaction

Before any data goes into a prompt, classify it. A typical enterprise scheme:

| Class | Examples in network data | AI rule (typical policy) |
|---|---|---|
| **Public** | Published documentation, generic questions | Any tool |
| **Internal** | Hostnames, private IP plans, routing config, interface descriptions without personal data | Approved enterprise AI tools only |
| **Confidential / Restricted** | Passwords and secret hashes, `enable secret`, type 7 strings, SNMP community strings, SNMPv3 keys, pre-shared keys, private keys/certificates, API tokens, customer data, personal data (names, emails, phone numbers) | Never in a prompt — redact first |

Rules of thumb:

* **Never paste credentials or keys** — enable secrets, username secrets, type 7 passwords (trivially reversible), SNMP communities, TACACS+/RADIUS keys, VPN PSKs, API tokens.
* **Never paste personal data** — customer or employee names, emails, phone numbers found in descriptions or logs.
* **Don't paste whole configs** when a section will do. `show running-config | section interface` or the specific show output is usually enough, and it is easier to sanitize.
* **Redact consistently** — replace secrets with placeholders (`<REDACTED>`), and if you must anonymize IPs or hostnames, do it consistently so the analysis still makes sense.
* **Use approved tools.** Public consumer AI services may retain prompts or use them for training, outside your organization's control. Enterprise-approved assistants come with contractual data-handling terms, but the "no secrets in prompts" rule still applies.

> **Exam tip:** If one candidate prompt contains a password, community string, key or full unredacted config — eliminate it immediately, however good the rest of it looks.

## Selecting the best prompt

When an exam question shows four prompts, rank them quickly:

1. **Eliminate data violations** — secrets, PII, unapproved tools.
2. **Eliminate unsafe instructions** — "push this to all switches now", commands that would cause an outage, removal of protections.
3. **Eliminate vague prompts** — no context, no task, "tell me everything".
4. **Prefer** the prompt with a relevant persona, a precise task, sanitized context (platform/version/output), constraints and an explicit output format that fits the use.

Example of a strong prompt:

```text
You are a network engineer preparing a change for tonight's maintenance window.
Context: Catalyst 9300 switches running IOS-XE 17.9. Sanitized
"show interfaces trunk" output from DIST-SW1 is below.
Task: produce the commands to add VLAN 40 to trunks Gi1/0/49 and Gi1/0/50
without removing any VLANs already allowed.
Constraints: use the "add" keyword; do not change any other interface.
Output: one IOS configuration block, then a list of verification commands,
then a rollback block.
<sanitized show interfaces trunk output>
```

## Reviewing what comes back

A good prompt improves the odds; it does not remove the need for review. Check commands against the platform, check the reasoning against the data you supplied, and test changes in a lab or with a dry run where possible. If the answer ignores your output format or constraints, tighten the prompt rather than accept a messy answer.

> **Real world:** Save prompts that work as team templates ("interface-error triage", "change draft with rollback"). Consistent prompts give consistent, reviewable output — the same idea as configuration templates.

## Key takeaways

* Prompt components: persona/role, instructions/task, context, constraints, output format, examples.
* Grounding the prompt with sanitized, relevant show output reduces generic or hallucinated answers but never guarantees correctness.
* Ask for the format the consumer needs: table for humans, JSON for scripts, a CLI block for devices, YAML for automation.
* Classify data first: never include secrets, keys, community strings or personal data; send internal data only to approved tools.
* Send the relevant section, not the full config; redact with clear placeholders.
* To pick the best prompt: remove data violations, then unsafe instructions, then vague prompts; choose the specific, constrained, well-formatted one.
