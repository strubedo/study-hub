## What Ansible is

Ansible is an open-source configuration management and automation tool written in Python. You describe tasks in YAML, and Ansible connects to devices and carries them out. Blueprint 5.5 uses the verb **Use**, so expect to read inventories and playbooks, predict what they do and spot what is wrong with them.

Three properties define Ansible for the exam:

* **Agentless** — nothing is installed on the managed devices. For Cisco IOS/IOS-XE, Ansible logs in over **SSH** just like you would.
* **Push model** — the control node initiates the connection and pushes tasks when you run a playbook. Nothing on the device polls for changes.
* **YAML** — inventories (optionally) and playbooks are human-readable YAML.

## Architecture

| Component | What it is |
|---|---|
| **Control node** | The Linux/macOS host where Ansible is installed and from which you run `ansible`/`ansible-playbook` |
| **Managed nodes** | The routers, switches and servers being configured |
| **Inventory** | The list of managed nodes, grouped, with variables (INI or YAML) |
| **Playbook** | A YAML file containing one or more **plays** |
| **Play** | Maps a group of hosts to an ordered list of **tasks** |
| **Task** | One call to a **module** with arguments |
| **Module** | The unit of work (e.g., `cisco.ios.ios_config`) |
| **Collection** | A package of modules and plugins (e.g., `cisco.ios`, `ansible.netcommon`) |

For servers, Ansible copies Python modules to the target and runs them there. Network devices cannot run Python, so network modules run **on the control node** and use a persistent CLI connection (`network_cli`) to send commands over SSH.

## Inventory

INI format:

```ini
[core_switches]
CORE-SW1 ansible_host=10.0.0.11
CORE-SW2 ansible_host=10.0.0.12

[core_switches:vars]
ansible_network_os=cisco.ios.ios
ansible_connection=ansible.netcommon.network_cli
ansible_user=netauto
ansible_become=true
ansible_become_method=enable
```

The same thing in YAML:

```yaml
all:
  children:
    core_switches:
      hosts:
        CORE-SW1:
          ansible_host: 10.0.0.11
        CORE-SW2:
          ansible_host: 10.0.0.12
      vars:
        ansible_network_os: cisco.ios.ios
        ansible_connection: ansible.netcommon.network_cli
        ansible_user: netauto
        ansible_become: true
        ansible_become_method: enable
```

Key variables:

* `ansible_connection: ansible.netcommon.network_cli` — use a persistent SSH CLI session (instead of the default `ssh` connection, which expects to run Python on the target).
* `ansible_network_os: cisco.ios.ios` — tells `network_cli` which platform's prompts, privilege handling and terminal settings to use.
* `ansible_become` / `ansible_become_method: enable` — enter privileged EXEC mode.
* Passwords belong in **Ansible Vault** (encrypted) or an external secret store, never in plain text in the inventory.

> **Watch out:** If `ansible_connection` and `ansible_network_os` are missing for IOS devices, the `cisco.ios` modules fail before running any commands — the default connection type is not valid for network CLI modules.

## Playbooks

```yaml
---
- name: Collect interface status from branch routers
  hosts: branch_routers
  gather_facts: false
  tasks:
    - name: Run show commands
      cisco.ios.ios_command:
        commands:
          - show ip interface brief
          - show version | include uptime
      register: result

    - name: Display output
      ansible.builtin.debug:
        var: result.stdout_lines
```

Reading it:

* `---` starts the YAML document; the file is a **list** of plays (the `-` before `name`).
* `hosts: branch_routers` — run against every host in that inventory group (Ansible works on several hosts in parallel; the default is 5 at a time, set by `forks`).
* `gather_facts: false` — skip the default fact gathering (common for network plays).
* Each task names a module and its arguments; indentation is significant and must use spaces, not tabs.
* `register: result` stores the module's return data; `debug` prints it.

## The cisco.ios modules you should know

| Module | Purpose | Changes config? |
|---|---|---|
| `cisco.ios.ios_command` | Run EXEC commands (show, ping) and return output; can wait for conditions | No — it is for EXEC mode; configuration-mode commands are not supported |
| `cisco.ios.ios_config` | Ensure configuration lines are present, optionally under `parents` | Yes |
| `cisco.ios.ios_facts` | Collect structured device facts (version, interfaces, etc.) | No |

```yaml
    - name: Ensure syslog server is configured
      cisco.ios.ios_config:
        lines:
          - logging host 10.10.50.30
          - logging trap warnings

    - name: Set description on uplink
      cisco.ios.ios_config:
        parents: interface GigabitEthernet1/0/48
        lines:
          - description Uplink to DIST-SW1
```

`parents` gives the configuration context (the mode you would enter first); `lines` are the commands inside it.

> **Exam tip:** "Use `ios_command` to push `configure terminal` and config lines" is a classic wrong approach. Configuration goes through `ios_config` (or resource modules such as `cisco.ios.ios_vlans`).

## Idempotence, check mode and the recap

**Idempotent** means running the same playbook again produces the same end state and makes no further changes. `ios_config` compares the requested lines with the running configuration and sends only what is missing.

```text
TASK [Ensure syslog server is configured] *********************************
changed: [ACC-SW1]
ok: [ACC-SW2]

PLAY RECAP ****************************************************************
ACC-SW1 : ok=1  changed=1  unreachable=0  failed=0  skipped=0  rescued=0  ignored=0
ACC-SW2 : ok=1  changed=0  unreachable=0  failed=0  skipped=0  rescued=0  ignored=0
```

* `changed` — the task modified the device (ACC-SW1 was missing the lines).
* `ok` — the task succeeded; the device already matched (ACC-SW2). In the recap, `ok` counts all successful tasks, including changed ones.
* `unreachable` — Ansible could not connect (SSH, credentials, IP).
* `failed` — the task ran but errored.

**Check mode** (`--check`, short form `-C`) is a dry run: modules that support it report what *would* change without changing anything. Add `--diff` to see the differences.

```text
$ ansible-playbook -i inventory.ini syslog.yml --check --diff
```

## Ad-hoc commands

For a one-off task you don't need a playbook:

```text
$ ansible core_switches -i inventory.ini -m cisco.ios.ios_command -a "commands='show clock'"
```

`-m` names the module, `-a` passes its arguments, and the first argument is the host pattern (a group, a host, or `all`).

## Ansible vs Puppet, Chef and Terraform

| Tool | Agent? | Model | Language | Typical use |
|---|---|---|---|---|
| **Ansible** | Agentless (SSH, APIs) | Push | YAML playbooks | Device config, orchestration |
| **Puppet** | Agent on node (agentless options exist for some devices) | Pull — agent checks in with the Puppet server | Puppet DSL manifests | Server config management |
| **Chef** | Agent (chef-client) | Pull | Ruby recipes/cookbooks | Server config management |
| **Terraform** | Agentless (provider APIs) | Push (plan/apply) | HCL, declarative | Provisioning infrastructure, IaC |

> **Real world:** Ansible's lack of an agent is why it dominates network automation: you cannot install arbitrary agents on most routers and switches, but every one of them speaks SSH.

## Troubleshooting checklist

* `unreachable` → check IP (`ansible_host`), SSH reachability, credentials, `ip ssh` settings on the device.
* Fails before commands run → check `ansible_connection` and `ansible_network_os`.
* Config task "changed" on every run → the lines don't match how IOS stores them in the running-config (e.g., abbreviations), so the comparison never matches.
* YAML errors → indentation, tabs, missing `-` for list items, missing colon.

## Key takeaways

* Ansible is agentless (SSH), push-based, Python-powered and uses YAML playbooks.
* Control node + inventory (INI/YAML) + playbook (plays → tasks → modules).
* IOS needs `ansible_connection: ansible.netcommon.network_cli` and `ansible_network_os: cisco.ios.ios`.
* `ios_command` runs EXEC commands; `ios_config` makes configuration changes; `ios_facts` gathers facts.
* Idempotent runs report `ok` (no change) when the device already matches; `changed` when they modify it.
* `--check` (dry run) and `--diff` let you preview changes safely.
* Puppet and Chef are agent-based pull tools; Terraform is declarative IaC using HCL and provider APIs.
