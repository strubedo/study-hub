## Seeing what you have: lsblk and blkid

Disks appear as block devices: `/dev/sda` (SCSI/SATA/USB), `/dev/vda` (VirtIO in a VM), `/dev/nvme0n1` (NVMe, with partitions named `nvme0n1p1`). Two commands tell you the layout:

- **`lsblk`** shows the tree of disks, partitions, LVM and RAID devices and where they are mounted. `lsblk -f` adds filesystem type, label, UUID and free space.
- **`blkid`** prints the UUID, label, filesystem `TYPE` and partition UUID of each device. It reads on-disk signatures, so it normally needs root for fresh results. UUIDs are what `/etc/fstab` should use, because `/dev/sdb` can become `/dev/sdc` after a reboot.

```text
srv01$ lsblk
NAME               MAJ:MIN RM  SIZE RO TYPE MOUNTPOINTS
vda                252:0    0   20G  0 disk
├─vda1             252:1    0    1G  0 part /boot
└─vda2             252:2    0   19G  0 part /
vdb                252:16   0   50G  0 disk
└─vdb1             252:17   0   50G  0 part
  ├─vg_data-lv_db  253:0    0   25G  0 lvm  /var/lib/db
  └─vg_data-lv_web 253:1    0   15G  0 lvm  /var/www

srv01# blkid /dev/vdb1 /dev/mapper/vg_data-lv_web
/dev/vdb1: UUID="Xk3dR2-aaaa-bbbb-cccc-dddd-eeee-FFFFFF" TYPE="LVM2_member" PARTUUID="6f1c2d3e-01"
/dev/mapper/vg_data-lv_web: UUID="5b0a1c2e-7d4f-4a6b-9e10-2f3a4b5c6d7e" BLOCK_SIZE="512" TYPE="xfs"
```

## Partitioning: fdisk, gdisk, parted, growpart

| Tool | Table types | Behaviour |
|---|---|---|
| `fdisk` | MBR and GPT (modern util-linux) | Interactive. Nothing changes on disk until you press **w**. `n` new, `d` delete, `t` change type, `p` print, `g` new GPT, `o` new MBR |
| `gdisk` | GPT only | `fdisk`-like, for GPT. Type codes are four hex digits: `8300` Linux filesystem, `8e00` Linux LVM, `fd00` Linux RAID, `ef00` EFI System |
| `parted` | MBR and GPT | Can run non-interactively. **Changes are applied immediately**, there is no write step. `parted -s /dev/vdb mklabel gpt mkpart primary 1MiB 100%` |
| `growpart` | Grows one partition to fill free space | From `cloud-utils-growpart` (RPM) / `cloud-guest-utils` (Debian). `growpart /dev/vda 2` takes the disk and the partition **number** as separate arguments |

**MBR** supports disks up to 2 TiB and four primary partitions (or three plus an extended partition). **GPT** supports huge disks and up to 128 partitions by default, keeps a backup table at the end of the disk, and is the normal choice for UEFI boot (UEFI can also boot an MBR disk with an ESP, but GPT is standard). After partitioning, the kernel may need to re-read the table: `partprobe /dev/vdb` (or `partx -u`).

A partition (or whole disk) is a container. To use it you must put a filesystem on it with `mkfs`, or make it an LVM physical volume or RAID member.

## Filesystems

| Filesystem | Strengths | Limits and tools |
|---|---|---|
| **ext4** | Journaling, mature, default on Debian/Ubuntu | Grows online, **shrinks only offline**. `mkfs.ext4`, `e2fsck`, `resize2fs`, `tune2fs` |
| **xfs** | High performance with large files and parallel I/O, default on RHEL | Grows online with `xfs_growfs`; **cannot be shrunk**. `mkfs.xfs`, `xfs_repair`, `xfs_info` |
| **btrfs** | Copy-on-write, snapshots, subvolumes, checksums, built-in multi-device RAID | `btrfs subvolume`, `btrfs scrub`, `btrfs filesystem resize`. Default on Fedora Workstation and openSUSE; not supported by RHEL |
| **tmpfs** | Lives in RAM (and swap), very fast, **contents are lost** on unmount or reboot | Size limit by `-o size=`; default is half of RAM. Used for `/run`, `/dev/shm` and often `/tmp` |

```text
srv01# mkfs.xfs -L web /dev/mapper/vg_data-lv_web
srv01# mkfs.ext4 -L logs /dev/vdc1
srv01# mount -t tmpfs -o size=512m tmpfs /mnt/ramdisk
```

The generic `mkfs` command is a front end: `mkfs -t ext4 /dev/vdc1` runs `mkfs.ext4`. Making a filesystem destroys what was on the device; `mkfs.xfs` refuses to overwrite an existing filesystem unless you add `-f`.

## LVM: the three layers

**Logical Volume Manager** separates the filesystem from the physical disks so volumes can be resized, spanned and moved online.

```text
Physical volumes (PV)   /dev/vdb1  /dev/vdc1         <- partitions or whole disks, initialised with pvcreate
Volume group (VG)       vg_data                       <- a pool of space, divided into extents (default 4 MiB)
Logical volumes (LV)    lv_db  lv_web                 <- the block devices you format and mount
```

Each layer has a family of commands. The short forms (`pvs`, `vgs`, `lvs`) print one line per object; the long forms (`pvdisplay`, `vgdisplay`, `lvdisplay`) print a full report; `pvscan`/`vgscan` rescan devices for LVM metadata.

| | Physical volumes | Volume groups | Logical volumes |
|---|---|---|---|
| Create | `pvcreate /dev/vdb1` | `vgcreate vg_data /dev/vdb1` | `lvcreate -n lv_web -L 15G vg_data` |
| Show | `pvs`, `pvdisplay`, `pvscan` | `vgs`, `vgdisplay`, `vgscan` | `lvs`, `lvdisplay` |
| Grow | `pvresize /dev/vdb1` (after the partition grew) | `vgextend vg_data /dev/vdc1` | `lvextend` / `lvresize` |
| Activate/modify | | `vgchange -ay` / `-an` | `lvchange -ay` / `-an`, `lvchange -p r` |
| Move data | `pvmove /dev/vdb1` | | |
| Remove | `pvremove /dev/vdb1` | `vgremove vg_data` | `lvremove vg_data/lv_web` |
| Move to another host | | `vgexport` / `vgimport` | |

```text
srv01# pvs
  PV         VG      Fmt  Attr PSize   PFree
  /dev/vdb1  vg_data lvm2 a--  <50.00g 10.00g
srv01# vgs
  VG      #PV #LV #SN Attr   VSize   VFree
  vg_data   1   2   0 wz--n- <50.00g 10.00g
srv01# lvs
  LV     VG      Attr       LSize  Pool Origin Data%  Meta%  Move Log Cpy%Sync Convert
  lv_db  vg_data -wi-ao---- 25.00g
  lv_web vg_data -wi-ao---- 15.00g
```

In the `lvs` `Attr` column (`-wi-ao----`), the fifth character `a` means the LV is active and the sixth, `o`, means the device is open (for example mounted). `VFree` in `vgs` is the number you check before extending an LV.

### Building and growing

```text
srv01# pvcreate /dev/vdb1
srv01# vgcreate vg_data /dev/vdb1
srv01# lvcreate -n lv_web -L 15G vg_data
srv01# mkfs.xfs /dev/vg_data/lv_web
srv01# mount /dev/vg_data/lv_web /var/www

srv01# lvextend -r -L +5G /dev/vg_data/lv_web        # grow by 5 GiB and the filesystem
srv01# lvextend -r -l +100%FREE /dev/vg_data/lv_web  # use every remaining extent
```

`-L` sets the size in bytes-style units (`+5G` adds 5 GiB, `5G` sets exactly 5 GiB); `-l` counts extents or a percentage (`+100%FREE`, `50%VG`). **`-r` (`--resizefs`) grows the filesystem in the same step**; without it you must run the filesystem tool yourself: `xfs_growfs /var/www` (xfs, takes the **mount point**; recent xfsprogs also accept the device of the mounted filesystem) or `resize2fs /dev/vg_data/lv_web` (ext4, takes the **device**). `lvresize` does the same job as `lvextend` or `lvreduce` depending on the sign.

To add space to the VG first: partition the new disk, `pvcreate /dev/vdc1`, `vgextend vg_data /dev/vdc1`, then extend the LV.

Shrinking is the dangerous direction and is filesystem-dependent: ext4 must be unmounted, checked and shrunk *before* `lvreduce` (`lvreduce -r` automates this); xfs cannot be shrunk at all. Reducing the LV first destroys data.

### Replacing a disk and moving a VG

To retire a PV while the system is running: `pvmove /dev/vdb1` migrates its extents to the other PVs in the VG, then `vgreduce vg_data /dev/vdb1` removes it from the VG and `pvremove /dev/vdb1` wipes the label.

To move a whole VG to another server:

```text
srv01# umount /var/www
srv01# vgchange -an vg_data        # deactivate
srv01# vgexport vg_data            # mark exported
# move the disks, then on srv02:
srv02# pvscan                      # find the PVs
srv02# vgimport vg_data
srv02# vgchange -ay vg_data        # activate
srv02# mount /dev/vg_data/lv_web /var/www
```

### Growing a disk in a VM or cloud instance

If the virtual disk was enlarged, the order is: grow the **partition** (`growpart /dev/vda 2`), then, for LVM, tell LVM the PV grew (`pvresize /dev/vda2`), then extend the LV (`lvextend -r -l +100%FREE ...`); without LVM, grow the filesystem directly (`xfs_growfs /` or `resize2fs /dev/vda2`).

> **Exam tip:** "Extend a mounted xfs logical volume by 5 GiB" is `lvextend -r -L +5G /dev/vg_data/lv_web`, or `lvextend` followed by `xfs_growfs <mountpoint>`. `resize2fs` on an xfs volume fails, and `xfs_growfs` on ext4 fails.

> **Watch out:** `parted` writes immediately and `mkfs`, `pvcreate -ff` and `dd` destroy data without confirming. Always confirm the device with `lsblk` first.

## Lab it yourself

Use two spare loopback files, so no real disk is touched (as root, in the lab VM; use a full VM rather than WSL 2):

```text
# truncate -s 1G /root/d1.img /root/d2.img
# losetup -f --show /root/d1.img     # prints a name such as /dev/loop0; substitute the names it prints below
# losetup -f --show /root/d2.img     # /dev/loop1
# pvcreate /dev/loop0 && vgcreate vg_lab /dev/loop0
# lvcreate -n lv_a -L 300M vg_lab && mkfs.xfs /dev/vg_lab/lv_a
# mkdir -p /mnt/a && mount /dev/vg_lab/lv_a /mnt/a
# vgextend vg_lab /dev/loop1 && lvextend -r -L +600M /dev/vg_lab/lv_a
# df -h /mnt/a; pvs; vgs; lvs
# pvmove /dev/loop0 && vgreduce vg_lab /dev/loop0
# umount /mnt/a; lvremove -y vg_lab/lv_a; vgremove vg_lab; pvremove /dev/loop[01]
# losetup -d /dev/loop0 /dev/loop1; rm /root/d1.img /root/d2.img
```

## Key takeaways

- `lsblk` shows the device tree; `blkid` shows UUIDs and filesystem types, which are what `/etc/fstab` should reference.
- `fdisk` and `gdisk` buffer changes until `w`; `parted` applies them immediately. GPT for big disks and UEFI, MBR limited to 2 TiB and four primaries.
- ext4 grows online and shrinks offline; xfs grows only (`xfs_growfs <mountpoint>`); btrfs has snapshots and subvolumes; tmpfs is RAM and volatile.
- LVM layers: PV (`pvcreate`) into VG (`vgcreate`, `vgextend`) into LV (`lvcreate`, `lvextend -r`).
- `lvextend -r` grows the filesystem too; otherwise run `xfs_growfs` (mount point) or `resize2fs` (device).
- `pvmove` then `vgreduce` then `pvremove` retires a disk; `vgchange -an`, `vgexport`, `vgimport`, `vgchange -ay` moves a VG between hosts.
- After growing a virtual disk: `growpart`, `pvresize` (LVM), then the LV and filesystem.
