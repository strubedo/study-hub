## The pieces: KVM, QEMU, libvirt

Linux virtualization is a stack, and the exam tests who does what.

| Component | Role |
|---|---|
| **KVM** (Kernel-based Virtual Machine) | Kernel modules (`kvm` plus `kvm_intel` or `kvm_amd`) that use the CPU's hardware virtualization (Intel **VT-x**, flag `vmx`; AMD **AMD-V**, flag `svm`). They expose `/dev/kvm`. Because the hypervisor is in the Linux kernel itself, Linux acts as the hypervisor |
| **QEMU** | A user-space program that emulates the rest of the machine: firmware, disk and network controllers, display. Run with KVM acceleration it gives near-native CPU speed; without it, QEMU emulates the CPU in software (slow, but can emulate other architectures) |
| **libvirt** | A management layer and API (`libvirtd`, or the modular `virtqemud`) that defines VMs as XML, manages storage pools and virtual networks, and is used by every tool below |
| **`virsh`** | libvirt's command-line shell |
| **`virt-manager`** | The GUI front end (the objectives' "vit-manager" is a typo). Its siblings: `virt-install` (create VMs from the CLI), `virt-clone`, `virt-viewer` |

Check support with `lscpu | grep Virtualization` (shows `VT-x` or `AMD-V`), `grep -E -c 'vmx|svm' /proc/cpuinfo`, `lsmod | grep kvm`, and `ls -l /dev/kvm`. Virtualization can be disabled in the firmware (BIOS/UEFI) even when the CPU supports it, and inside a VM it requires nested virtualization.

```text
srv01$ lsmod | grep kvm
kvm_intel             548864  0
kvm                  1585152  1 kvm_intel
srv01$ ls -l /dev/kvm
crw-rw----+ 1 root kvm 10, 232 Nov 22 09:12 /dev/kvm
```

Users who run VMs need access to `/dev/kvm` (group `kvm`) and to libvirt (group `libvirt`). System VMs are managed at `qemu:///system` (root-owned, shared networks); `qemu:///session` is per-user with no privileged networking.

## Bare metal versus virtual machines

| | Bare metal | Virtual machine |
|---|---|---|
| Performance | Full hardware, no overhead | Small CPU overhead, I/O depends on drivers and contention |
| Density / cost | One OS per server | Many VMs per host, better utilisation |
| Isolation | Physical | Hypervisor-enforced, separate kernels |
| Flexibility | Hardware changes are physical | Resize, snapshot, clone, live-migrate |
| Hardware access | Direct (GPUs, specialised cards) | Needs passthrough (PCI/GPU passthrough, SR-IOV) |
| Failure domain | One server | Every VM on a failed host (without HA) |

Containers are a third model: they share the host kernel rather than running their own, covered in domain 2.

## VirtIO and paravirtualized drivers

An **emulated** device (an Intel e1000 NIC or an IDE disk) works without special guest drivers but is slow, because every I/O operation is trapped and imitated. **Paravirtualized** devices use drivers that know they are in a VM and talk to the hypervisor through shared memory queues. **VirtIO** is the standard: `virtio-blk` and `virtio-scsi` for disks, `virtio-net` for networking, `virtio-balloon` (reclaim guest memory), `virtio-rng` and `virtio-gpu`. Linux guests include the drivers in the kernel. Windows guests need the separate `virtio-win` driver package. If the root disk is moved to VirtIO, the guest's initramfs must contain `virtio_blk`, or it cannot find root (see the `dracut --add-drivers` example in lesson 1.2).

## Disk images and qemu-img

VM disks are files. **raw** is a plain byte-for-byte image; **qcow2** is QEMU's format with thin provisioning, snapshots, compression and backing files; other formats you may meet are VMDK (VMware), VDI (VirtualBox) and VHDX (Hyper-V). `qemu-img` is the tool:

| Command | Purpose |
|---|---|
| `qemu-img create -f qcow2 web01.qcow2 20G` | Create a new, sparse image |
| `qemu-img info web01.qcow2` | **Properties**: format, virtual size, actual disk size, backing file |
| `qemu-img convert -f vmdk -O qcow2 in.vmdk out.qcow2` | Convert between formats (`-f` source, `-O` output) |
| `qemu-img resize web01.qcow2 +10G` | Grow (or set) the virtual size; shrinking needs `--shrink` and is dangerous |
| `qemu-img create -f qcow2 -b base.qcow2 -F qcow2 web02.qcow2` | Overlay image that reads unchanged data from a **backing file** |
| `qemu-img check`, `qemu-img snapshot -l` | Verify integrity; list internal snapshots |

```text
srv01$ qemu-img create -f qcow2 web01.qcow2 20G
Formatting 'web01.qcow2', fmt=qcow2 cluster_size=65536 extended_l2=off compression_type=zlib size=21474836480 lazy_refcounts=off refcount_bits=16
srv01$ qemu-img info web01.qcow2
image: web01.qcow2
file format: qcow2
virtual size: 20 GiB (21474836480 bytes)
disk size: 196 KiB
cluster_size: 65536
```

Note the two sizes: **virtual size** is what the guest sees; **disk size** is what the file really uses. Resizing the image does not resize the guest's partition or filesystem: inside the guest you still run `growpart` and `resize2fs`/`xfs_growfs` (lesson 1.3). Do not resize an image while the VM is running or while snapshots depend on it, unless the tooling supports it.

## VM states and operations

A libvirt domain is in one of several states: **running**, **paused** (frozen in memory, still allocated), **shut off**, **in shutdown**, **crashed**, and **pmsuspended** (guest power-management suspend).

```text
srv01$ virsh list --all
 Id   Name    State
-----------------------
 1    web01   running
 -    db01    shut off
```

| Task | Command |
|---|---|
| Start / graceful shutdown | `virsh start web01`, `virsh shutdown web01` (ACPI request to the guest) |
| **Hard power-off** | `virsh destroy web01`. It does **not** delete the VM; it is like pulling the plug |
| Remove the definition | `virsh undefine web01` (add `--remove-all-storage` to delete disks) |
| Start at host boot | `virsh autostart web01` |
| Pause / resume | `virsh suspend web01`, `virsh resume web01` |
| Edit / view definition | `virsh edit web01`, `virsh dumpxml web01` |
| vCPUs and RAM | `virsh setvcpus web01 4 --config`, `virsh setmem web01 4G --config` (limits set by `maxvcpus`/`setmaxmem`) |
| Add a disk | `virsh attach-disk web01 /var/lib/libvirt/images/data.qcow2 vdb --persistent` |
| Console | `virsh console web01` |

**Resources**: CPU (vCPUs), RAM (can be ballooned within the maximum), storage (images or LVM/block devices in storage pools under `/var/lib/libvirt/images` by default) and network (virtual NICs attached to a virtual network or bridge).

**Templates and clones.** Build a **baseline (golden) image** once, generalise it (`virt-sysprep` removes SSH host keys, machine ID, logs; cloud-init personalises it at first boot), then stamp out copies. `virt-clone --original web01 --name web02 --auto-clone` makes a **full clone** (independent copy of the disk); a **linked clone** uses a qcow2 overlay on a read-only backing file, which is quick and small but depends on that base image.

**Snapshots** capture a VM's disk (and optionally memory) at a point in time: `virsh snapshot-create-as web01 pre-patch`, `virsh snapshot-list web01`, `virsh snapshot-revert web01 pre-patch`, `virsh snapshot-delete web01 pre-patch`. They are a short-term safety net before a change, **not backups**: they live with the original image, and long snapshot chains slow I/O.

**Migration** moves a VM between hosts. **Cold** migration shuts the VM down first. **Live** migration keeps it running while memory is copied: `virsh migrate --live --persistent web01 qemu+ssh://kvm02.example.com/system`. It requires compatible CPUs, the same network reachable from both hosts, and either **shared storage** (NFS, SAN, Ceph) or `--copy-storage-all` to move the disk too.

**Nested virtualization** runs a hypervisor inside a VM, useful for labs and CI. It needs the host module option enabled (`/sys/module/kvm_intel/parameters/nested` reads `Y` or `1`; to enable set `options kvm_intel nested=1` in `/etc/modprobe.d/`, or `kvm_amd`), and the VM given the host's CPU features (CPU mode `host-passthrough` in libvirt). Nested guests run slower.

## Virtual network types

libvirt virtual networks are described by their forward mode:

| Type | How it works | Reachability |
|---|---|---|
| **Bridged** | A host Linux bridge (`br0`) joins the VM NIC to the physical LAN; the VM has its own MAC and a LAN IP | VM is a peer on the LAN; reachable from outside |
| **NAT** | libvirt's `default` network (`virbr0`, `192.168.122.0/24`, DHCP and DNS by dnsmasq); outbound traffic is masqueraded | VMs reach out; inbound only via port forwarding |
| **Host-only / isolated** | A virtual switch with no forwarding to the outside | VMs and host can talk to each other only |
| **Routed** | Forwarded to the physical network **without NAT**; the upstream network needs a route to the VM subnet | Reachable if routes exist |
| **Open** | Like routed, but libvirt adds **no firewall rules**: the administrator supplies them | Same as routed, with your own filtering |

`virsh net-list --all` and `virsh net-dumpxml default` show them. NAT is the default because it works with no network changes; bridged is what you want when other machines must reach the VM directly.

> **Exam tip:** `virsh shutdown` asks nicely; `virsh destroy` forces power off but keeps the definition; `virsh undefine` deletes the definition. KVM needs hardware support (`vmx` or `svm`); QEMU provides device emulation; libvirt manages them both.

> **Watch out:** Resizing a qcow2 image only changes the *virtual disk*. The partition, LVM PV and filesystem inside the guest still have to be grown.

## Lab it yourself

In the lab VM. Running KVM guests inside it needs nested virtualization from your hypervisor: on a Linux host, the `nested` parameter of kvm_intel or kvm_amd; on Windows, nested virtualization enabled for that Hyper-V VM; in VirtualBox, the nested VT-x/AMD-V setting; on a Mac, support depends on the chip, the macOS version and the hypervisor. If step 1 shows no `/dev/kvm`, step 2 still works (qemu-img needs no KVM), and for steps 4-5 you can create a small guest with `virt-install --virt-type qemu`, which uses slow software emulation.

1. `lscpu | grep -i virtualization`, `lsmod | grep kvm`, `ls -l /dev/kvm`.
2. `qemu-img create -f qcow2 test.qcow2 5G`, `qemu-img info test.qcow2`, `qemu-img resize test.qcow2 +2G`, `qemu-img convert -O raw test.qcow2 test.raw`, and compare `ls -ls` with `qemu-img info` for each file.
3. Install `libvirt`/`virt-manager` (or `libvirt-daemon-system virtinst virt-manager`), then `sudo virsh net-list --all` and `sudo virsh net-dumpxml default`.
4. Create a small VM with `virt-install` or `virt-manager`, then run `virsh list --all`, `virsh dominfo <name>`, `virsh snapshot-create-as <name> s1`, `virsh snapshot-list <name>`.
5. Compare `virsh shutdown`, `virsh destroy` and `virsh undefine` on a disposable VM.

## Key takeaways

- KVM = kernel hardware acceleration (`vmx`/`svm`, `/dev/kvm`); QEMU = device emulation in user space; libvirt (`virsh`, `virt-manager`, `virt-install`) = management.
- VirtIO drivers are paravirtualized and much faster than emulated devices; Windows guests need `virtio-win`.
- `qemu-img info/create/convert/resize`: virtual size versus disk size; resizing the image does not resize the guest filesystem.
- `virsh shutdown` is graceful, `destroy` is a hard stop (not a delete), `undefine` removes the definition.
- Snapshots are not backups; templates are generalised baseline images; clones are full or linked.
- Live migration needs compatible hosts and shared storage (or `--copy-storage-all`); nested virtualization needs the `nested` module option.
- Networks: bridged (on the LAN), NAT (default `virbr0`, 192.168.122.0/24), host-only/isolated, routed (no NAT), open (no auto firewall rules).
