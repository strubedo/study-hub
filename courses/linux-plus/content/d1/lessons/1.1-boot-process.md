## The boot sequence in one picture

Every Linux boot follows the same chain, whatever the distribution:

1. **Firmware** (UEFI, or legacy BIOS) runs its power-on self-test and finds a boot target.
2. The **bootloader** (almost always GRUB 2) loads from that target and presents a menu.
3. The bootloader loads the **kernel** image and an **initramfs** (the "initrd") into memory and passes the **kernel parameters** (the command line).
4. The kernel starts, unpacks the initramfs as a temporary root filesystem and runs its `/init`.
5. Code in the initramfs loads the drivers needed to reach the real root filesystem (storage controller, RAID, LVM, LUKS, filesystem), mounts it, and switches to it.
6. The initramfs hands over (`switch_root`) to the real root's init, which runs as **PID 1** and is `systemd` on every mainstream distribution; systemd brings the system to its default target.

Knowing which stage failed is the core troubleshooting skill. A firmware error message means stage 1; a `grub>` or `grub rescue>` prompt means stage 2 (the config or the kernel path is wrong); a kernel panic that mentions "unable to mount root fs" or a drop to a `dracut:/#` or `(initramfs)` shell means stage 4 or 5 (missing driver, wrong `root=`, broken LVM or RAID); and a failed unit after the root filesystem is mounted is systemd's problem (stage 6).

## UEFI versus BIOS

| | Legacy BIOS | UEFI |
|---|---|---|
| Bootloader location | First 440 bytes of the MBR, plus a "BIOS boot" partition when the disk is GPT | A file on the **EFI System Partition (ESP)**, a FAT32 partition mounted at `/boot/efi` |
| Partition table | MBR (or GPT with a BIOS boot partition) | GPT normally (UEFI can also boot an MBR disk that has an ESP) |
| Boot entries | None: boots the first disk in the boot order | NVRAM entries, viewed and edited with `efibootmgr` |
| Secure Boot | No | Yes: firmware checks signatures, usually through a signed `shim` that then loads GRUB |

On UEFI systems the loader lives in a distribution-specific folder such as `/boot/efi/EFI/ubuntu/` or `/boot/efi/EFI/redhat/` (files like `shimx64.efi` and `grubx64.efi`). Check which mode you booted in with `[ -d /sys/firmware/efi ] && echo UEFI || echo BIOS`.

## GRUB 2 and its configuration files

GRUB's menu is generated, not hand-written. You edit the *inputs* and then regenerate the output:

- `/etc/default/grub`: global settings such as `GRUB_TIMEOUT`, `GRUB_DEFAULT` and, most importantly, `GRUB_CMDLINE_LINUX` (parameters for every entry).
- `/etc/grub.d/`: scripts that generate menu entries (`10_linux`, `30_os-prober`, `40_custom`).
- The generated config: **`/boot/grub/grub.cfg`** on Debian and Ubuntu, **`/boot/grub2/grub.cfg`** on RHEL, Fedora and SUSE. Never edit this file by hand; the next kernel update overwrites it.

| Task | Debian / Ubuntu (dpkg-based) | RHEL / Fedora (RPM-based) |
|---|---|---|
| Regenerate the config | `update-grub` (wrapper for `grub-mkconfig -o /boot/grub/grub.cfg`) | `grub2-mkconfig -o /boot/grub2/grub.cfg` |
| Reinstall to a BIOS disk | `grub-install /dev/sda` | `grub2-install /dev/sda` |
| Add/remove a kernel parameter | edit `GRUB_CMDLINE_LINUX`, then `update-grub` | `grubby --update-kernel=ALL --args="quiet"` or `--remove-args=` |

> **Real world:** RHEL 9 and 10 (and Fedora) use Boot Loader Specification snippets: one small file per kernel in `/boot/loader/entries/*.conf`. That is why `grubby` exists, and why `grub2-mkconfig` is needed less often there. On RHEL 8 with UEFI the real config lived on the ESP (`/boot/efi/EFI/redhat/grub.cfg`); from RHEL 9 the ESP copy is a small stub that points at `/boot/grub2/grub.cfg`.

At the GRUB menu you can press **e** to edit an entry for one boot only: change the `linux` line, then press **Ctrl+x** to boot. This is how you reach rescue mode (add `systemd.unit=rescue.target`), or break into the initramfs (`rd.break` on RHEL-family) when you have lost the root password.

## The kernel and its parameters

The kernel image is `/boot/vmlinuz-<version>` (the name comes from "virtual memory" + "z" for compressed). Parameters are space-separated words on the `linux` line. See what the running kernel was given:

```text
$ cat /proc/cmdline
BOOT_IMAGE=/vmlinuz-6.8.0-45-generic root=UUID=3f1e9b52-0a4c-4f3e-9d2b-6c1d1e5b7a10 ro quiet splash
```

| Parameter | Meaning |
|---|---|
| `root=` | The device (or `UUID=`/`LABEL=`) of the root filesystem |
| `ro` / `rw` | Mount root read-only (normal: fsck runs, then it is remounted rw) or read-write |
| `quiet`, `splash` | Suppress boot messages, show a graphical splash |
| `systemd.unit=rescue.target` | Boot to single-user rescue mode (also `emergency.target`, `multi-user.target`) |
| `init=/bin/bash` | Replace PID 1 with a shell (last-resort recovery; no systemd) |
| `rd.break` | dracut: stop in the initramfs before the root switch (RHEL-family) |
| `nomodeset` | Do not load kernel video drivers (graphics troubleshooting) |
| `modprobe.blacklist=nouveau` | Keep a module from loading |
| `ip=dhcp`, `netroot=` | Network configuration during early boot (dracut; used with network root or PXE) |

`/proc/cmdline` shows what is running; the files above show what will be used on the *next* boot.

## initrd and initramfs

The "initrd" is a compressed archive that GRUB places in memory next to the kernel. Modern ones are **initramfs** images (a compressed `cpio` archive), though everyone still says initrd. Its job is to contain just enough modules and tools to find the real root filesystem, because the kernel cannot hold every storage driver built in. The files are `/boot/initrd.img-<version>` on Debian/Ubuntu and `/boot/initramfs-<version>.img` on RHEL-family. Rebuilding it is covered in the device-management lesson (`dracut`, `update-initramfs`).

## PXE network boot

**PXE** (Preboot eXecution Environment) lets a machine boot with no local disk, which is how fleets are installed and diskless clients run:

1. The NIC firmware broadcasts a **DHCP** request. The DHCP server replies with an IP address, a **next-server** (the TFTP server address, carried in the DHCP header's `siaddr` field or as a server name in option 66) and a **boot file name** (the `file` field or option 67).
2. The firmware downloads the boot file by **TFTP** (UDP 69). It is a bootloader: `pxelinux.0` for BIOS, `shimx64.efi` or `grubx64.efi` for UEFI.
3. That bootloader fetches its own config, then the kernel and initrd (TFTP or HTTP).
4. The kernel boots from them, then either installs an OS (Kickstart, preseed, autoinstall) or mounts a network root.

UEFI also supports **HTTP boot**, which skips TFTP. PXE is a boot-time protocol: if the machine will not PXE, check the DHCP options, TFTP reachability (UDP 69) and that the boot file matches the firmware type (a BIOS file served to a UEFI client fails).

> **Exam tip:** Remember the pairing "bootloader config file + regeneration command". Debian family: `/boot/grub/grub.cfg` and `update-grub`. RHEL family: `/boot/grub2/grub.cfg` and `grub2-mkconfig -o ...`. Changing `/etc/default/grub` has no effect until you regenerate.

> **Watch out:** `/proc/cmdline` always shows the *running* kernel's parameters. If you edit `/etc/default/grub` and do not regenerate and reboot, `/proc/cmdline` will not change.

## Lab it yourself

In the lab VM described on the Exam guide page (Debian-family or RHEL-family). Use a full VM, not WSL 2: WSL starts its kernel without GRUB, so steps 3-5 have nothing to change. The steps are the same on an x86_64 or an ARM64 (aarch64) VM; ARM64 VMs normally boot through UEFI.

1. Run `[ -d /sys/firmware/efi ] && echo UEFI || echo BIOS` and `cat /proc/cmdline`.
2. Run `ls -l /boot` and identify the `vmlinuz`, `initrd`/`initramfs` and GRUB directory.
3. Read `/etc/default/grub`. Add `GRUB_TIMEOUT=10`, regenerate (`update-grub` or `grub2-mkconfig -o /boot/grub2/grub.cfg`), reboot and confirm the longer menu.
4. At the menu press **e**, append `systemd.unit=rescue.target` to the `linux` line, press **Ctrl+x**, and see the rescue shell. Then `systemctl default` to continue.
5. On RHEL-family, list `/boot/loader/entries/` and run `grubby --info=ALL | head`.

## Key takeaways

- Boot order: firmware, bootloader, kernel + initramfs, real root, PID 1 (systemd).
- UEFI loads a file from the FAT32 ESP (`/boot/efi`); BIOS loads from the MBR; both usually run GRUB 2.
- Edit `/etc/default/grub` and `/etc/grub.d/`, then regenerate: `update-grub` (Debian family) or `grub2-mkconfig -o /boot/grub2/grub.cfg` (RHEL family). Do not edit `grub.cfg`.
- `/proc/cmdline` shows the running kernel's parameters; `e` at the GRUB menu edits them for one boot.
- The initramfs holds the drivers needed to mount the real root; a missing driver there causes an initramfs shell or a "cannot mount root" panic.
- PXE: DHCP supplies an address plus a boot file, TFTP (UDP 69) or HTTP delivers the bootloader, kernel and initrd.
