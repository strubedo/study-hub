## Netfilter: the hooks inside the kernel

**Netfilter** is the kernel framework that every Linux firewall programs. It places **hooks** on the packet path, and filtering, NAT and mangling code registers at those hooks:

```text
             +--> INPUT -----> local process ----> OUTPUT --+
             |                                              |
 NIC --> PREROUTING --> routing decision --> FORWARD --> POSTROUTING --> NIC
```

| Hook | Sees | Typical use |
|---|---|---|
| prerouting | Every packet as it arrives, before routing | **DNAT** (port forwarding), raw/notrack |
| input | Packets addressed to this host | Host firewall |
| forward | Packets routed through the host | Router or container-host filtering |
| output | Packets generated locally | Egress filtering, DNAT of local traffic |
| postrouting | Every packet about to leave | **SNAT** and **masquerade** |

The pieces are kernel modules: `nf_tables` (the nftables engine), `nf_conntrack` (connection tracking), `nf_nat`, protocol helpers such as `nf_conntrack_ftp`, and for the legacy API `x_tables` plus `xt_*` match modules. `lsmod | grep -E '^nf_|^nft_|^xt_'` shows which are loaded; they load on demand when a rule needs them.

## Stateful vs stateless filtering

**Connection tracking** (conntrack) records each flow, so a rule can match on state:

| State | Meaning |
|---|---|
| `new` | First packet of a connection not yet seen |
| `established` | Part of a connection that has seen traffic in both directions |
| `related` | A new connection that belongs to an existing one (FTP data, ICMP errors) |
| `invalid` | Does not fit any known connection; drop it |

A **stateful** ruleset accepts `established,related` first and then decides only about `new` packets, so you never write rules for return traffic. A **stateless** filter judges each packet alone, the way a basic router ACL does: to let a host browse the web you would have to allow inbound packets *from* source port 443, which also admits anything an attacker sends from port 443. Linux filters are stateful whenever a rule matches `ct state` (nftables) or `-m conntrack --ctstate` (iptables). Stateless rules still have uses, for example `notrack` for very high-rate DNS or for DDoS mitigation before conntrack fills (`net.netfilter.nf_conntrack_max`). `conntrack -L` (package conntrack-tools) lists tracked flows.

## nftables

**nftables** replaced iptables, ip6tables, arptables and ebtables with one tool, `nft`, and one rule language. Nothing is predefined: you create **tables** (with a family: `ip`, `ip6`, `inet` for both, `arp`, `bridge`, `netdev`), **base chains** attached to a hook with a priority and policy, and **rules**.

```text
srv01# cat /etc/nftables.conf
#!/usr/sbin/nft -f
flush ruleset

table inet filter {
  set mgmt_v4 {
    type ipv4_addr
    flags interval
    elements = { 198.51.100.0/24 }
  }

  chain input {
    type filter hook input priority filter; policy drop;
    ct state established,related accept
    ct state invalid drop
    iif "lo" accept
    ip saddr @mgmt_v4 tcp dport 22 accept
    tcp dport { 80, 443 } accept
    icmp type echo-request limit rate 5/second accept
    icmpv6 type { nd-neighbor-solicit, nd-router-advert, nd-neighbor-advert, echo-request } accept
  }

  chain forward {
    type filter hook forward priority filter; policy drop;
  }
}
```

Rules are evaluated in order; `accept` ends evaluation in that base chain and `drop` ends it for good. The chain **policy** applies to packets that match nothing. Note the ICMPv6 line: an IPv6 host that drops neighbor discovery loses connectivity.

Everyday commands:

```text
srv01# nft list ruleset                               # everything
srv01# nft -a list chain inet filter input            # with rule handles
srv01# nft add rule inet filter input tcp dport 8443 accept       # append
srv01# nft insert rule inet filter input tcp dport 8443 accept    # prepend
srv01# nft delete rule inet filter input handle 12
srv01# nft add element inet filter mgmt_v4 { 192.0.2.10 }
srv01# nft -c -f /etc/nftables.conf                   # syntax check only
srv01# nft -f /etc/nftables.conf                      # load the file
```

Commands typed with `nft add` are runtime only. Persist them by putting the ruleset in **`/etc/nftables.conf`** (Debian; loaded by `nftables.service`) or `/etc/sysconfig/nftables.conf` (RHEL), and enable the service. `nft list ruleset > file` is a convenient way to capture a working ruleset.

## iptables and iptables-nft

The `iptables` command still exists, but on RHEL 8 and later, Debian 10 and later and current Ubuntu it is **`iptables-nft`**: the familiar syntax, translated into nftables rules in tables named `ip filter`, `ip nat` and so on. `iptables -V` shows which one you have:

```text
srv01$ iptables -V
iptables v1.8.11 (nf_tables)
```

`(legacy)` would mean the old x_tables back end. Do not mix the two back ends, or two separate rule sets end up active and neither tool shows the other's rules. `iptables-translate` converts a rule to nft syntax:

```text
srv01$ iptables-translate -A INPUT -p tcp --dport 22 -m conntrack --ctstate NEW -j ACCEPT
nft 'add rule ip filter INPUT tcp dport 22 ct state new counter accept'
```

iptables keeps its fixed tables (`filter`, `nat`, `mangle`, `raw`) and built-in chains (`INPUT`, `FORWARD`, `OUTPUT`, `PREROUTING`, `POSTROUTING`).

```text
srv01# iptables -A INPUT -m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT
srv01# iptables -A INPUT -i lo -j ACCEPT
srv01# iptables -A INPUT -p tcp --dport 22 -s 198.51.100.0/24 -j ACCEPT
srv01# iptables -P INPUT DROP
srv01# iptables -L INPUT -n -v --line-numbers
srv01# iptables -D INPUT 3          # delete rule 3
srv01# iptables -I INPUT 1 ...      # insert at the top
srv01# iptables-save > /etc/iptables/rules.v4        # Debian iptables-persistent
srv01# iptables-save > /etc/sysconfig/iptables       # RHEL iptables-services
```

`-A` appends, `-I` inserts, `-D` deletes, `-P` sets the chain policy, `-F` flushes, `-L -n -v` lists numerically with counters. `-j DROP` discards silently; `-j REJECT` sends an error back. IPv6 needs the same rules again with `ip6tables`, one more reason `inet` tables are nicer.

## ipset

Thousands of single-address rules are slow and unreadable. **ipset** stores addresses, networks or address-port pairs in a kernel hash that one rule can match:

```text
srv01# ipset create blocklist hash:net
srv01# ipset add blocklist 203.0.113.0/24
srv01# ipset add blocklist 192.0.2.66
srv01# iptables -I INPUT -m set --match-set blocklist src -j DROP
srv01# ipset list blocklist
srv01# ipset save > /etc/ipset.conf      # restore with: ipset restore < /etc/ipset.conf
```

Set types include `hash:ip`, `hash:net`, `hash:ip,port` and `bitmap:port`; `timeout` makes entries expire. nftables has sets built in (`@mgmt_v4` above), and firewalld exposes ipsets with `--new-ipset` and `--add-source=ipset:blocklist`, so standalone ipset matters mostly with iptables.

## Address translation

| Term | What changes | Where it happens |
|---|---|---|
| **SNAT** | Source address (and maybe port) to a fixed address | postrouting (nftables also allows input) |
| **Masquerade** | Source address to whatever the outgoing interface has | postrouting; for DHCP or PPP uplinks |
| **PAT** (NAT overload) | Many inside hosts share one address; ports keep flows apart | What SNAT and masquerade do by default |
| **DNAT** | Destination address and/or port (port forwarding, publishing a server) | prerouting (and output for locally generated packets) |
| **Redirect** | Destination to the local host itself (transparent proxy) | prerouting, output |

Only the first packet of a flow goes through the NAT rules; conntrack applies the same translation to every later packet and reverses it for replies. DNAT happens before the routing decision, so the **forward** filter sees the *translated* (inside) address and port, and your forward rules must allow those.

```text
table ip nat {
  chain prerouting {
    type nat hook prerouting priority dstnat; policy accept;
    iifname "eth0" tcp dport 8080 dnat to 10.0.0.10:80
  }
  chain postrouting {
    type nat hook postrouting priority srcnat; policy accept;
    oifname "eth0" ip saddr 10.0.0.0/24 masquerade
  }
}
```

The same in iptables and firewalld:

```text
srv01# iptables -t nat -A PREROUTING -i eth0 -p tcp --dport 8080 -j DNAT --to-destination 10.0.0.10:80
srv01# iptables -t nat -A POSTROUTING -o eth0 -s 10.0.0.0/24 -j MASQUERADE
srv01# iptables -t nat -A POSTROUTING -o eth0 -j SNAT --to-source 203.0.113.5
srv01# firewall-cmd --permanent --zone=external --add-forward-port=port=8080:proto=tcp:toport=80:toaddr=10.0.0.10
srv01# firewall-cmd --permanent --zone=external --add-masquerade
```

## IP forwarding

A Linux box only routes between interfaces when **`net.ipv4.ip_forward`** is 1 (and `net.ipv6.conf.all.forwarding` for IPv6). Without it, NAT rules exist but nothing is forwarded.

```text
srv01# sysctl net.ipv4.ip_forward
net.ipv4.ip_forward = 0
srv01# sysctl -w net.ipv4.ip_forward=1                         # now, lost at reboot
srv01# echo 'net.ipv4.ip_forward = 1' > /etc/sysctl.d/90-router.conf
srv01# sysctl --system                                          # load all sysctl.d files
```

`/proc/sys/net/ipv4/ip_forward` is the same setting. On Ubuntu with ufw, forwarding is set in `/etc/ufw/sysctl.conf` instead, because ufw applies its own sysctl file. Container engines and libvirt switch forwarding on themselves, which is why a host that "is not a router" may still forward packets.

> **Exam tip:** A NAT gateway needs three things: forwarding enabled, a postrouting SNAT or masquerade rule, and a forward-chain policy or rule that accepts the traffic. Port forwarding adds a prerouting DNAT and a forward rule for the inside address.

## Lab it yourself

Two VMs on an isolated network, one acting as the router (ruleset changes need root and a real network namespace, so not a plain unprivileged container):

1. `iptables -V`, `nft list ruleset`, `lsmod | grep -E '^nf_|^nft_'`.
2. Load the `inet filter` ruleset above from a file with `nft -c -f`, then `nft -f`, then confirm SSH still works. Add and delete a rule by handle.
3. On the router: enable forwarding, add the masquerade rule, and from the inside VM `ping 192.0.2.1` (or any outside address) while watching `conntrack -L` or `tcpdump -n -i eth0` on the router.
4. Add a DNAT for port 8080 to an inside web server and test from outside; then set the forward policy to drop and see it break until you allow `ip daddr 10.0.0.10 tcp dport 80`.
5. `iptables-translate -t nat -A POSTROUTING -o eth0 -j MASQUERADE`.

## Key takeaways

- Netfilter hooks: prerouting, input, forward, output, postrouting; modules `nf_tables`, `nf_conntrack`, `nf_nat`, helpers.
- Stateful rules accept `established,related` and decide on `new`; stateless rules judge each packet alone and need explicit return-traffic rules.
- nftables: tables (`inet` covers IPv4 and IPv6), base chains with hook, priority and policy; persist in `/etc/nftables.conf` (Debian) or `/etc/sysconfig/nftables.conf` (RHEL).
- Current `iptables` is usually `iptables-nft` (`iptables -V` shows `nf_tables`); `iptables-save` to persist; don't mix legacy and nft back ends.
- ipset (`hash:net`, `--match-set name src`) matches large address lists with one rule.
- DNAT in prerouting/output, SNAT and masquerade in postrouting; PAT is many-to-one with port translation; forward rules see post-DNAT addresses.
- Routing needs `net.ipv4.ip_forward=1`, made persistent in `/etc/sysctl.d/*.conf` and loaded with `sysctl --system`.
