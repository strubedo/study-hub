## Three jobs for cryptography

| Goal | Protects against | Linux tools |
|---|---|---|
| **Data at rest** | Stolen disks, laptops, backups, decommissioned drives | GPG for files, LUKS2 (dm-crypt) for block devices |
| **Data in transit** | Sniffing and tampering on the network | TLS (OpenSSL, LibreSSL), SSH, WireGuard, IPsec |
| **Integrity** | Silent modification, forged downloads | Hashes (SHA-256), HMAC, digital signatures |

Two building blocks recur. **Symmetric** ciphers (AES, ChaCha20) use one shared key and are fast; **asymmetric** algorithms (RSA, ECDSA, Ed25519, X25519) use a key pair and solve key exchange and signatures. Real protocols use asymmetric crypto to agree on or protect a symmetric key, then encrypt the data symmetrically.

## Data at rest: GPG file encryption

GnuPG (`gpg`) encrypts and signs individual files.

```text
alice@srv01:~$ gpg -c --cipher-algo AES256 payroll.csv        # symmetric: passphrase, writes payroll.csv.gpg
alice@srv01:~$ gpg -d payroll.csv.gpg > payroll.csv          # decrypt
alice@srv01:~$ gpg --full-generate-key                        # create a key pair
alice@srv01:~$ gpg --import bob.asc                            # import bob's public key
alice@srv01:~$ gpg -e -r bob@example.com report.pdf           # encrypt to bob's public key
alice@srv01:~$ gpg --armor --detach-sign release.tar.gz       # writes release.tar.gz.asc
bob@web01:~$   gpg --verify release.tar.gz.asc release.tar.gz
```

`-c` (symmetric) needs only a shared passphrase. `-e -r` (public key) needs the recipient's public key, and only their private key decrypts. `--armor` produces ASCII instead of binary output. Signing proves who produced a file and that it is unchanged; it is how package repositories and release tarballs are verified (3.6).

## Data at rest: LUKS2 and Argon2

**LUKS** (Linux Unified Key Setup) is the on-disk format for dm-crypt full-disk or partition encryption. **LUKS2** is the default format of current `cryptsetup`. The data is encrypted with a random **master (volume) key**; each of up to 32 **keyslots** stores a copy of the master key encrypted with a key derived from a passphrase or key file. That is why you can add, change or remove passphrases without re-encrypting the data.

The key derivation function makes each passphrase guess expensive. LUKS1 used PBKDF2; **LUKS2 defaults to Argon2id**, a memory-hard KDF (winner of the 2015 Password Hashing Competition) that forces an attacker to spend memory, not just CPU, on every guess, which defeats cheap GPU and ASIC cracking.

```text
srv01# cryptsetup luksFormat --type luks2 /dev/vdb1          # destroys existing data; asks YES
srv01# cryptsetup open /dev/vdb1 data                        # creates /dev/mapper/data
srv01# mkfs.xfs /dev/mapper/data && mount /dev/mapper/data /srv/data
srv01# cryptsetup luksDump /dev/vdb1
LUKS header information
Version:       	2
...
Data segments:
  0: crypt
	offset: 16777216 [bytes]
	length: (whole device)
	cipher: aes-xts-plain64
	sector: 4096 [bytes]

Keyslots:
  0: luks2
	Key:        512 bits
	Priority:   normal
	Cipher:     aes-xts-plain64
	Cipher key: 512 bits
	PBKDF:      argon2id
	Time cost:  4
	Memory:     1048576
	Threads:    4
...
srv01# cryptsetup luksAddKey /dev/vdb1                       # add a second passphrase
srv01# cryptsetup luksHeaderBackup /dev/vdb1 --header-backup-file /root/vdb1.hdr
srv01# umount /srv/data && cryptsetup close data
```

To unlock at boot, add the device to **`/etc/crypttab`** (`data UUID=<luks-uuid> none luks`) and the filesystem `/dev/mapper/data` to `/etc/fstab`; `none` means "ask for the passphrase". `cryptsetup luksConvertKey --pbkdf argon2id` upgrades a slot that still uses PBKDF2, and `cryptsetup convert --type luks2` converts a LUKS1 header. LUKS protects a powered-off disk only: once unlocked, the data is readable by anyone with access to the running system.

> **Watch out:** Lose every passphrase or damage the header and the data is gone; there is no recovery. Back up the header (`luksHeaderBackup`) and store it as carefully as the passphrase, because anyone with the header and an old passphrase can decrypt.

## Data in transit

### TLS and its versions

TLS secures HTTPS, SMTP with STARTTLS, LDAPS, IMAPS and much more.

| Version | Status |
|---|---|
| SSL 2.0, SSL 3.0 | Broken (POODLE); prohibited |
| TLS 1.0, TLS 1.1 | **Deprecated by RFC 8996** (2021); disabled by default in current OpenSSL security levels, browsers and RHEL crypto policies |
| TLS 1.2 (RFC 5246) | Acceptable with AEAD cipher suites (AES-GCM, ChaCha20-Poly1305) and ECDHE key exchange |
| TLS 1.3 (RFC 8446) | Preferred: removed RSA key exchange, CBC and other legacy options; forward secrecy always; faster handshake |

```text
srv01$ openssl s_client -connect web01.example.com:443 -tls1_3 </dev/null 2>/dev/null | grep -E 'Protocol|Cipher'
srv01$ openssl s_client -connect web01.example.com:443 -tls1_1 </dev/null     # should fail
srv01$ nmap --script ssl-enum-ciphers -p 443 web01.example.com
```

In Nginx, `ssl_protocols TLSv1.2 TLSv1.3;`; in Apache, `SSLProtocol -all +TLSv1.2 +TLSv1.3`.

### OpenSSL and LibreSSL

**OpenSSL** is the TLS library and the `openssl` command-line toolkit used by nearly every Linux distribution (OpenSSL 3.x today). **LibreSSL** is a fork created by the OpenBSD project in 2014, after Heartbleed, to clean up and simplify the code; it is the default on OpenBSD and macOS and is available on Linux, but mainstream distributions ship OpenSSL. Both provide `libssl`/`libcrypto` and an `openssl` command with largely the same subcommands.

Useful `openssl` subcommands:

```text
srv01$ openssl version
srv01$ openssl x509 -in /etc/pki/tls/certs/web01.crt -noout -subject -issuer -dates -ext subjectAltName
srv01$ openssl req -new -newkey rsa:3072 -nodes -keyout web01.key -out web01.csr -subj "/CN=web01.example.com"
srv01$ openssl verify -CAfile chain.pem web01.crt
srv01$ openssl rand -base64 32
```

### WireGuard

**WireGuard** is a VPN in the Linux kernel (since 5.6) with a deliberately small design: fixed modern primitives (Curve25519 key exchange, ChaCha20-Poly1305, BLAKE2s), UDP only (commonly port 51820), one key pair per peer and no cipher negotiation, so there is nothing to downgrade.

```text
srv01# wg genkey | tee /etc/wireguard/srv01.key | wg pubkey > /etc/wireguard/srv01.pub
srv01# cat /etc/wireguard/wg0.conf
[Interface]
Address = 10.99.0.1/24
ListenPort = 51820
PrivateKey = <contents of srv01.key>

[Peer]
PublicKey = <peer public key>
AllowedIPs = 10.99.0.2/32
srv01# wg-quick up wg0          # or: systemctl enable --now wg-quick@wg0
srv01# wg show
```

`AllowedIPs` is both the routing table (what goes to that peer) and an inbound filter (what source addresses are accepted from it). The private key file must be readable by root only.

## Hashing: SHA-256 and HMAC

A **hash** maps any input to a fixed-length digest; changing one bit changes the digest completely, and you cannot find another input with the same digest. **SHA-256** (256-bit, SHA-2 family) is the everyday choice; SHA-512 and SHA-3 are also fine. **MD5** and **SHA-1** have practical collision attacks and must not be used for signatures or integrity against an attacker.

```text
srv01$ sha256sum rocky-9.6-x86_64-dvd.iso
srv01$ sha256sum -c CHECKSUM            # verify a list of "digest  filename" lines
srv01$ openssl dgst -sha256 file.bin
```

A plain hash proves integrity only if the expected digest came from a trusted place (a signed `CHECKSUM` file, an HTTPS page): an attacker who replaces the file can replace an unsigned checksum next to it.

**HMAC** (hash-based message authentication code, RFC 2104) mixes a **secret key** into the hash, `HMAC-SHA256(key, message)`. Only holders of the key can produce or check the value, so it proves both integrity and authenticity. TLS, SSH, IPsec, JWTs and API request signing all use it.

```text
srv01$ openssl dgst -sha256 -hmac 'shared-secret' message.txt
```

Password storage is a third, different use: there you want a slow, salted algorithm (yescrypt, SHA-512 crypt, Argon2), never a single fast SHA-256.

## Removing weak algorithms

Disable what is broken before it is exploited:

- **Protocols**: SSLv3, TLS 1.0/1.1, SSH protocol 1, SMB1, Telnet/FTP.
- **Ciphers and modes**: RC4, DES, 3DES, export ciphers, NULL ciphers, CBC suites in TLS where possible.
- **Hashes**: MD5 and SHA-1 in signatures and certificates.
- **Keys**: RSA below 2048 bits, DSA. OpenSSH 8.8 disabled `ssh-rsa` (RSA with SHA-1) signatures by default, and current OpenSSH no longer supports DSA keys at all.

On RHEL, **system-wide crypto policies** apply one setting to OpenSSL, GnuTLS, NSS, OpenSSH, Kerberos and Java:

```text
srv01# update-crypto-policies --show
DEFAULT
srv01# update-crypto-policies --set FUTURE        # stricter; LEGACY loosens, FIPS for FIPS mode
```

Elsewhere, configure each service: `ssh -Q cipher` and `sshd -T | grep -E '^(ciphers|macs|kexalgorithms)'` show what SSH offers, and `Ciphers`, `MACs`, `KexAlgorithms` in `sshd_config` restrict it. OpenSSL's `MinProtocol` and `CipherString = DEFAULT@SECLEVEL=2` in `openssl.cnf` set library defaults on Debian and Ubuntu.

## Certificate management

A TLS certificate binds a name to a public key and is signed by a **certificate authority**. Clients trust a certificate if they can build a chain from it to a **trusted root** in their store.

| Task | RHEL / Fedora | Debian / Ubuntu |
|---|---|---|
| System trust store | `/etc/pki/ca-trust/` (bundle in `/etc/pki/tls/certs/ca-bundle.crt`) | `/etc/ssl/certs/` (bundle `/etc/ssl/certs/ca-certificates.crt`) |
| Add an internal root CA | Copy to `/etc/pki/ca-trust/source/anchors/`, run `update-ca-trust` | Copy as `*.crt` to `/usr/local/share/ca-certificates/`, run `update-ca-certificates` |

Where certificates come from:

- **No-cost CAs** such as Let's Encrypt issue **domain-validated** certificates automatically through the **ACME** protocol (`certbot`, `acme.sh`, built into Caddy and some web servers), with short lifetimes that make automated renewal mandatory.
- **Commercial CAs** sell DV, **OV** (organization validated) and **EV** (extended validation) certificates, plus support, warranties, longer-established tooling and certificates for cases ACME cannot do easily. The encryption is identical; the difference is validation, support and policy.
- **Internal CAs** (FreeIPA/Dogtag, step-ca, AD Certificate Services) for internal names, with the root distributed to every client's trust store.

Public certificate lifetimes are shrinking (the CA/Browser Forum has set a schedule down to 47 days by 2029), so automate renewal and monitor expiry (`openssl x509 -enddate`, `certbot renew --dry-run`).

### Avoid self-signed certificates

A self-signed certificate is signed by its own key, so no client can verify it: every user sees a warning, learns to click through warnings, and can no longer tell your server from an attacker's man-in-the-middle certificate. Use them only for quick lab tests. In production, use a public CA for public names and an **internal CA whose root you deploy** for internal ones; never disable verification (`curl -k`, `verify=False`) to make a self-signed certificate "work".

## Lab it yourself

In a throwaway VM or container:

1. `gpg -c` a file, decrypt it; create two key pairs (`--quick-generate-key alice@example.com`) and encrypt from one to the other.
2. Create a 64 MiB image file, `cryptsetup luksFormat` it, `luksDump` (look for `argon2id`), `luksAddKey`, `open`, `mkfs`, mount, then `close`. Run `cryptsetup erase` on it and try to open it again.
3. `openssl req -x509 -newkey rsa:3072 -nodes -keyout lab.key -out lab.crt -days 7 -subj /CN=lab.example.com`, inspect it with `openssl x509 -noout -text`, and note that subject and issuer are the same.
4. `openssl s_client -connect example.com:443 -tls1_2` and `-tls1_1`.
5. `sha256sum` a file, change one byte, compare; compute an HMAC with two different keys.
6. Two VMs: generate WireGuard keys, write `wg0.conf` on each, `wg-quick up wg0`, ping across, `wg show`.
7. RHEL family: `update-crypto-policies --show`.

## Key takeaways

- At rest: `gpg -c` (passphrase) or `gpg -e -r` (public key) for files; LUKS2 (`cryptsetup luksFormat/open/close`, `/etc/crypttab`) for devices.
- LUKS2 keyslots wrap one master key; the default KDF is Argon2id (memory-hard); back up the header.
- TLS 1.0 and 1.1 are deprecated (RFC 8996); use TLS 1.2 with AEAD suites or, preferably, TLS 1.3.
- OpenSSL is the standard library and toolkit; LibreSSL is OpenBSD's fork. WireGuard: kernel VPN, UDP 51820, Curve25519 + ChaCha20-Poly1305, no negotiation.
- SHA-256 for integrity; HMAC adds a secret key for authenticity; MD5 and SHA-1 are broken for security use.
- Remove weak protocols, ciphers, hashes and short keys; RHEL `update-crypto-policies` does it system-wide.
- Trust stores: `update-ca-trust` (RHEL) and `update-ca-certificates` (Debian); no-cost ACME CAs vs commercial OV/EV; internal CA instead of self-signed.
