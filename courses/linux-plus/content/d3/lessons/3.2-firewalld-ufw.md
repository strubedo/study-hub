## Front ends over one kernel firewall

Every Linux packet filter is **Netfilter**, the hook framework inside the kernel (next lesson). What differs between distributions is the tool you use to program it:

| Tool | Default on | Model |
|---|---|---|
| **firewalld** (`firewall-cmd`) | RHEL, Fedora, Rocky, Alma, SUSE | Zones with services, ports and rich rules; runtime and permanent configurations; nftables back end |
| **ufw** (`ufw`) | Ubuntu (installed but **inactive** until `ufw enable`) | Simple allow/deny list, first match wins; iptables rules under `/etc/ufw` |
| **nftables** (`nft`) | Debian (package installed, empty ruleset) | Raw tables, chains and rules |
| **iptables** (`iptables`) | Legacy scripts everywhere | Now usually `iptables-nft`, a compatibility layer that writes nftables rules |

Run only one manager. firewalld flushing ufw's rules (or a hand-written `nft -f` wiping firewalld's tables) is a classic "the firewall changed by itself" incident.

## firewalld zones

A **zone** is a trust level with its own allowed services, ports and rules. Each incoming connection is assigned to exactly one zone:

1. If its **source** address matches a source bound to a zone (`--add-source=192.0.2.0/24`), that zone.
2. Otherwise the zone of the **interface** it arrived on (`--change-interface=eth1`, or the NetworkManager connection's `connection.zone`).
3. Otherwise the **default zone** (`public` on a fresh install).

| Zone | Meant for |
|---|---|
| `drop` | Silently drop everything inbound; only replies to outgoing connections get in |
| `block` | Reject inbound with an ICMP prohibited message |
| `public` | Untrusted networks; default allows `ssh`, `dhcpv6-client` (and `cockpit` on RHEL) |
| `external` | Internet side of a NAT router; masquerading enabled |
| `dmz`, `work`, `home`, `internal` | Progressively more trusted LANs with more services allowed |
| `trusted` | Accept everything |

Traffic that no rule in the zone accepts hits the zone's **target**: `default` (reject, but let ICMP through), `ACCEPT`, `DROP` or `REJECT`.

```text
srv01# firewall-cmd --get-default-zone
public
srv01# firewall-cmd --get-active-zones
internal
  interfaces: eth1
public
  interfaces: eth0
srv01# firewall-cmd --zone=public --list-all
public (active)
  target: default
  icmp-block-inversion: no
  interfaces: eth0
  sources:
  services: cockpit dhcpv6-client ssh
  ports: 8443/tcp
  protocols:
  forward: yes
  masquerade: no
  forward-ports:
  source-ports:
  icmp-blocks:
  rich rules:
```

(Output format from firewalld 1.x on RHEL 9; newer releases add a few lines such as zone priorities.) Without `--zone`, a command acts on the default zone.

## Runtime vs permanent

firewalld keeps **two configurations**, and this is the most tested idea in the topic.

| Command | Running firewall | Saved config (`/etc/firewalld/`) |
|---|---|---|
| `firewall-cmd --add-service=http` | Changed now | Not saved; lost at `--reload`, restart or reboot |
| `firewall-cmd --permanent --add-service=http` | **Not changed** | Saved |
| `firewall-cmd --reload` | Replaced by the saved config; runtime-only changes are discarded; established connections keep their state | Unchanged |
| `firewall-cmd --runtime-to-permanent` | Unchanged | Overwritten with the current runtime config |
| `--complete-reload` | Rebuilt from scratch, connection state lost | Unchanged |

Two safe workflows:

```text
# A: change both, no reload needed
srv01# firewall-cmd --add-service=https
srv01# firewall-cmd --permanent --add-service=https

# B: experiment at runtime, then save what works
srv01# firewall-cmd --add-port=8443/tcp
srv01# firewall-cmd --runtime-to-permanent

# Temporary rule that removes itself after 10 minutes (runtime only)
srv01# firewall-cmd --add-port=9090/tcp --timeout=10m
```

> **Exam tip:** "The rule worked until the reboot" means it was runtime only. "I added it with `--permanent` but it does not work" means the runtime was never updated: run `firewall-cmd --reload`. `--timeout` cannot be combined with `--permanent`.

Permanent zone files are written to `/etc/firewalld/zones/<zone>.xml`; shipped defaults live in `/usr/lib/firewalld/`. `firewall-cmd --check-config` validates the permanent configuration, and `firewall-offline-cmd` edits it while the daemon is stopped (for kickstart or image builds).

## Ports vs services

A **service** is a named XML definition (`/usr/lib/firewalld/services/*.xml`; your own in `/etc/firewalld/services/`) that can list several ports and protocols, plus conntrack **helper** modules and destination restrictions. A **port** rule opens exactly one port or range.

```text
srv01# firewall-cmd --info-service=ftp
ftp
  ports: 21/tcp
  protocols:
  source-ports:
  modules:
  destination:
  includes:
  helpers: ftp
srv01# firewall-cmd --permanent --add-service=ftp        # port 21 plus the FTP conntrack helper
srv01# firewall-cmd --permanent --add-service=samba      # 139/tcp, 445/tcp + samba-client (138/udp + netbios-ns: 137/udp and its helper)
srv01# firewall-cmd --permanent --add-port=8443/tcp      # one port
srv01# firewall-cmd --permanent --add-port=60000-60100/udp
```

Prefer services: they are self-documenting (`services: ssh https` reads better than a list of numbers), they bring along helpers such as the FTP one that tracks data connections, and if a port changes the service file changes once. Use `--add-port` for an application that has no service definition, or create one (`firewall-cmd --permanent --new-service=myapp`, then `firewall-cmd --permanent --service=myapp --add-port=9000/tcp` and `--reload`). Note that moving SSH to port 2222 means opening `2222/tcp`; the `ssh` service still means 22.

## Rich rules

Rich rules express what plain service and port rules cannot: per-source access, logging, rate limits, explicit reject or drop.

```text
srv01# firewall-cmd --permanent --zone=public --add-rich-rule='rule family="ipv4" source address="198.51.100.0/24" service name="ssh" accept'
srv01# firewall-cmd --permanent --add-rich-rule='rule family="ipv4" source address="203.0.113.50" drop'
srv01# firewall-cmd --permanent --add-rich-rule='rule service name="http" log prefix="HTTP " level="info" limit value="5/m" accept'
srv01# firewall-cmd --permanent --add-rich-rule='rule family="ipv4" forward-port port="8080" protocol="tcp" to-port="80" to-addr="10.0.0.10"'
srv01# firewall-cmd --reload
srv01# firewall-cmd --list-rich-rules
```

Element options go immediately after their element, and `family=` is required whenever an address appears. Within a zone, rich rules of the default priority are evaluated in a fixed order: **log** rules, then **deny** (reject and drop) rules, then **allow** rules, which include the zone's services and ports. So a rich rule that drops 203.0.113.50 wins even though `ssh` is allowed in the zone. Use `priority=` (negative runs earlier) when you need a different order.

To limit SSH to a management subnet, remove the open service and allow it only from that source: `--remove-service=ssh` plus a rich rule with `source address=... service name="ssh" accept`. (Alternatively bind the subnet as a source of a zone that allows ssh.)

Other things firewalld does: `--add-masquerade` and `--add-forward-port` for NAT (next lesson), `--new-ipset` / `--add-source=ipset:<name>` for large address lists, policy objects (`--new-policy`) for filtering traffic forwarded between zones, and `--panic-on` to drop all traffic in an emergency (do not run it over SSH).

## ufw

ufw (Uncomplicated Firewall) is Ubuntu's front end. Its default policy is deny incoming, allow outgoing, and its rules are evaluated **in order, first match wins**.

```text
srv01# ufw default deny incoming
srv01# ufw allow OpenSSH                    # application profile from /etc/ufw/applications.d
srv01# ufw allow 443/tcp                    # port and protocol
srv01# ufw allow http                       # service name looked up in /etc/services (80/tcp)
srv01# ufw allow 53                         # no protocol: both tcp and udp
srv01# ufw allow from 198.51.100.0/24 to any port 22 proto tcp
srv01# ufw limit ssh/tcp                    # deny a source that opens 6+ connections in 30 s
srv01# ufw deny from 203.0.113.50
srv01# ufw enable
srv01# ufw status numbered
Status: active

     To                         Action      From
     --                         ------      ----
[ 1] OpenSSH                    ALLOW IN    Anywhere
[ 2] 443/tcp                    ALLOW IN    Anywhere
[ 3] 80/tcp                     ALLOW IN    Anywhere
[ 4] 22/tcp                     ALLOW IN    198.51.100.0/24
[ 5] Anywhere                   DENY IN     203.0.113.50
...
srv01# ufw delete 5
srv01# ufw insert 1 deny from 203.0.113.50
```

Ports vs services in ufw: `ufw allow 80/tcp` names a port; `ufw allow http` names a service from `/etc/services`; `ufw allow 'Nginx Full'` names an **application profile** (`ufw app list`, `ufw app info 'Nginx Full'`), which can bundle several ports. Because the first match wins, rule 5 above never blocks 203.0.113.50 on 443 or 80: the earlier allows match first. That is why the fix is `ufw insert 1 deny ...`.

`ufw status verbose` also shows default policies and logging; `ufw show added` lists rules even while ufw is disabled. ufw changes are applied and saved at once (no runtime/permanent split). For routing, ufw has `ufw route allow in on eth1 out on eth0`, the `DEFAULT_FORWARD_POLICY` in `/etc/default/ufw`, and NAT rules in `/etc/ufw/before.rules`.

> **Watch out:** Before `ufw enable` on a remote server, make sure SSH is allowed, or the next new connection is refused. Existing sessions usually survive because ufw allows established traffic.

## Lab it yourself

Use two throwaway VMs (firewalls need a real kernel network stack, not an unprivileged container):

1. Rocky or Alma: `firewall-cmd --list-all`, then `firewall-cmd --add-service=http`, `firewall-cmd --reload` and see the service vanish. Repeat with `--permanent` and see it stay hidden until `--reload`. Finish with `--runtime-to-permanent`.
2. Add the rich rule allowing ssh only from your lab subnet, remove the `ssh` service, and check from another host with `nc -vz srv01 22`.
3. `firewall-cmd --info-service=ftp`, `ls /usr/lib/firewalld/services | wc -l`, `cat /etc/firewalld/zones/public.xml`.
4. Ubuntu: `ufw status verbose`, `ufw allow OpenSSH`, `ufw enable`, add an allow then a deny for one host, test, then fix the order with `ufw insert 1`.

## Key takeaways

- One kernel firewall (Netfilter); firewalld on RHEL, ufw on Ubuntu, nft on Debian. Use only one manager.
- firewalld picks a zone by source, then interface, then the default zone (`public`).
- Without `--permanent`, changes are runtime only; with it, only the saved config changes. `--reload` loads permanent into runtime; `--runtime-to-permanent` saves runtime.
- Services bundle ports and helpers; `--add-port=N/proto` opens one port. Moving a daemon's port means opening the new port.
- Rich rules give per-source, log, limit, reject/drop and forward-port rules; in a zone, log then deny then allow.
- ufw: deny incoming by default, first match wins (`ufw insert 1`), `limit` for brute force, ports (`443/tcp`) vs services (`http`) vs app profiles (`OpenSSH`).
