## Privilege escalation done properly

Hardening starts with how administrators become root. Logging in directly as root leaves no record of which person acted, so the norm is: log in as yourself, escalate for specific tasks, and let the logs and the audit trail (`auid`) record who did what.

### su and su -

`su` starts a shell as another user (root by default) after asking for **that user's** password.

| Command | Result |
|---|---|
| `su` | Root shell, but keeps most of your environment and your current directory (your `PATH` may not include `/usr/sbin`) |
| `su -` (or `su -l`, `su --login`) | Full **login shell** as root: root's environment, `PATH` and home directory, as if root had logged in |
| `su - bob` | Login shell as bob (bob's password) |
| `su -c 'systemctl restart nginx'` | Run one command as root |

To restrict `su` to administrators, uncomment the `pam_wheel` line in `/etc/pam.d/su` (`auth required pam_wheel.so use_uid` on RHEL; Debian and Ubuntu ship a similar commented line). It then allows only members of the `wheel` group, or of GID 0 if no `wheel` group exists, or of the group named with `group=`, for example `group=sudo` on Ubuntu.

### sudo

`sudo` runs a single command as root (or another user) after asking for **your own** password, checks a policy, and logs every use (in the journal and in `/var/log/secure` or `/var/log/auth.log`). It caches the authentication for a few minutes (`timestamp_timeout`: 5 minutes by default in classic sudo, 15 in sudo-rs); `sudo -k` forgets it.

| Command | Meaning |
|---|---|
| `sudo cmd` | Run cmd as root |
| `sudo -u bob cmd` | Run as bob |
| `sudo -i` | Root **login** shell (reads root's profile, `cd`s to `/root`) |
| `sudo -s` | Root shell that keeps your environment and directory |
| `sudo -l` | List what you may run |
| `sudoedit /etc/nginx/nginx.conf` (`sudo -e`) | Edit a copy with your own editor as you, then copy it back as root |

The admin group differs by family: **`wheel`** on RHEL and Fedora (`%wheel ALL=(ALL) ALL`), **`sudo`** on Debian and Ubuntu (`%sudo ALL=(ALL:ALL) ALL`). Making someone an administrator is `usermod -aG wheel alice` or `usermod -aG sudo alice`, followed by a fresh login.

> **Real world:** Ubuntu 25.10 and later use **sudo-rs**, a memory-safe reimplementation, as the default `sudo`. It reads the same `/etc/sudoers` syntax for the features covered here.

### /etc/sudoers, /etc/sudoers.d and visudo

Never edit `/etc/sudoers` with a plain editor: a syntax error can leave nobody able to use sudo. **`visudo`** locks the file, opens it in your editor, and refuses to save a file that does not parse. `visudo -c` checks every sudoers file; `visudo -f /etc/sudoers.d/webops` edits a drop-in safely.

Drop-ins go in **`/etc/sudoers.d/`**, pulled in by `@includedir /etc/sudoers.d` (older files say `#includedir`, which is not a comment despite the `#`). Files whose names contain a `.` or end in `~` are **skipped**, so `webops.conf` is silently ignored while `webops` works. Use mode 0440, owner root.

A rule is `who where = (as_whom) [TAGS:] commands`:

```text
srv01# cat /etc/sudoers.d/webops
Cmnd_Alias NGINX = /usr/bin/systemctl reload nginx, /usr/bin/systemctl restart nginx
%webops     ALL=(root) NGINX
svc_backup  ALL=(root) NOPASSWD: /usr/bin/rsync --server --sender *
bob         ALL=(root) NOEXEC: /usr/bin/less /var/log/messages
```

| Tag | Effect |
|---|---|
| `NOPASSWD:` | No password prompt for those commands (automation and service accounts; keep the command list tight) |
| `NOEXEC:` | The command cannot start other programs, which blocks shell escapes such as `!sh` inside `less`, `vi` or `man`. Classic sudo preloads a shared library through `LD_PRELOAD` (on Linux that library installs a seccomp filter), so only dynamically linked programs are covered; sudo-rs applies its own seccomp filter, which also covers static binaries |
| `PASSWD:` | Re-enable the prompt after a `NOPASSWD` |

When several entries match, **the last match wins**, so put general rules first and exceptions later. Always give full paths (`/usr/bin/systemctl`, not `systemctl`). Granting editors, pagers, `find`, `tar`, interpreters or `ALL` effectively grants a root shell; for editing files, grant `sudoedit /path` instead.

## Permissions: chmod, chown and chgrp

Each file has an owner, a group and three permission triplets. On directories, `r` lists names, `w` creates, deletes and renames entries (together with `x`), and `x` lets you traverse into the directory. Deleting a file needs write permission on the **directory**, not on the file.

```text
srv01# chown alice:webdev /srv/app/report.txt     # owner and group
srv01# chown :webdev /srv/app/report.txt          # group only (same as chgrp)
srv01# chgrp -R webdev /srv/app                   # recursive group change
srv01# chmod 640 report.txt                       # rw-r-----
srv01# chmod u=rw,g=r,o= report.txt               # same, symbolic
srv01# chmod g+w,o-rwx report.txt                 # add and remove
srv01# chmod -R u+rwX,g+rX,o-rwx /srv/app         # X = execute only on dirs and already-executable files
```

Octal digits are sums of r=4, w=2, x=1 for user, group and other. A user can `chgrp` only to a group they belong to; only root can change the owner.

### setuid, setgid and the sticky bit

A fourth, leading octal digit holds the special bits:

| Bit | Octal | On a file | On a directory | Shown as |
|---|---|---|---|---|
| setuid | 4000 | Runs with the **owner's** UID (`/usr/bin/passwd` is `4755 root`) | Ignored on Linux | `s` in user execute (`S` if no x) |
| setgid | 2000 | Runs with the file's group | New files **inherit the directory's group** (shared project directories) | `s` in group execute |
| sticky | 1000 | (no effect on Linux files) | Only a file's owner, the directory owner or root may delete or rename it (`/tmp` is `1777`) | `t` in other execute (`T` if no x) |

```text
srv01$ stat -c '%a %A %n' /usr/bin/passwd /tmp
4755 -rwsr-xr-x /usr/bin/passwd
1777 drwxrwxrwt /tmp
srv01# chmod 2775 /srv/projects          # drwxrwsr-x: shared group directory
srv01# chmod g+s,o+t /srv/drop           # symbolic forms; u+s for setuid
```

A capital `S` or `T` (bit set, execute missing) is almost always a mistake. Unneeded setuid programs are a privilege-escalation risk; finding and removing them is covered in Hardening 3.

### umask

New files start from 666 and new directories from 777; the **umask** removes bits. With umask `022` files are created 644 and directories 755; with `027`, 640 and 750; with `002` (the user-private-group default for normal users on RHEL and Ubuntu), 664 and 775. The umask never *adds* execute: a file is never created executable however permissive it is.

```text
srv01$ umask
0002
srv01$ umask -S
u=rwx,g=rwx,o=rx
srv01$ umask 027; touch f; mkdir d; stat -c '%a %n' f d
640 f
750 d
```

The value is per process and inherited. Set the system default in `/etc/login.defs` (`UMASK`, applied by `pam_umask`) or `/etc/profile.d/`, per user in `~/.bashrc`, and per service with `UMask=0027` in the systemd unit.

## File attributes: chattr and lsattr

Below permissions, ext4, XFS and Btrfs support attributes that even root must remove before acting. Only root (`CAP_LINUX_IMMUTABLE`) can set or clear `i` and `a`.

| Attribute | Effect |
|---|---|
| `i` immutable | No writes, no delete, no rename, no hard links, no metadata changes |
| `a` append only | Can only be opened for appending; cannot be truncated, overwritten or deleted (log files) |

```text
srv01# chattr +i /etc/resolv.conf
srv01# lsattr /etc/resolv.conf
----i---------e------- /etc/resolv.conf
srv01# rm -f /etc/resolv.conf
rm: cannot remove '/etc/resolv.conf': Operation not permitted
srv01# chattr -i /etc/resolv.conf
srv01# chattr +a /var/log/app/audit.log
srv01# lsattr -d /srv/app                 # the directory itself
```

(`e` is ext4's extent flag, present on almost every file.) "Operation not permitted" for root on a file with ordinary permissions is the signature of an attribute; check `lsattr` before anything else. Attackers use `+i` too, to keep their changes from being undone.

## ACLs: setfacl and getfacl

Permissions allow one owner and one group. **POSIX ACLs** add entries for more named users and groups.

```text
srv01$ setfacl -m u:bob:rw report.txt              # add or modify an entry
srv01$ setfacl -m g:auditors:r report.txt
srv01$ getfacl report.txt
# file: report.txt
# owner: alice
# group: alice
user::rw-
user:bob:rw-
group::rw-
group:auditors:r--
mask::rw-
other::r--

srv01$ ls -l report.txt
-rw-rw-r--+ 1 alice alice 0 Nov 22 08:30 report.txt
```

The `+` after the mode means an ACL exists. Key ideas:

- The **mask** is the maximum for named users, named groups and the owning group. `ls -l` shows the mask in the group position, and `chmod g=r` changes the mask, after which `getfacl` prints `#effective:r--` beside entries that are now limited.
- **Default ACLs** on a directory (`setfacl -d -m g:webdev:rwx dir` or `-m d:g:webdev:rwx`) are inherited by files and subdirectories created in it later; they do not change existing files (add `-R` for those).
- `setfacl -x u:bob file` removes one entry, `-b` removes all ACL entries, `-k` removes the default ACL.
- Back up and restore: `getfacl -R /srv/app > acl.txt`, `setfacl --restore=acl.txt`. `cp -a`, `rsync -A` and `tar --acls` preserve ACLs; plain `cp` does not.

## Lab it yourself

In a throwaway VM or container (as root, with an `alice` and a `bob` account):

1. `visudo -f /etc/sudoers.d/lab` and add `bob ALL=(root) NOEXEC: /usr/bin/less /etc/hosts`; as bob run `sudo less /etc/hosts` and try `!sh`. Rename the file to `lab.conf`, run `sudo -l` as bob and see the rule disappear.
2. Compare `su` and `su -`: `echo $PATH; pwd` in each.
3. `mkdir /srv/share; chgrp users /srv/share; chmod 2775 /srv/share`; create a file as alice and check its group. Then `chmod 1777 /srv/share` and try to delete alice's file as bob.
4. `umask 077; touch x; ls -l x`.
5. `chattr +i` a test file, try to delete it as root, `lsattr`, then `chattr -i`. Try `+a` and `echo more >> file` vs `echo new > file`.
6. `setfacl -m u:bob:rw` on a file, `getfacl`, `chmod g=r` and read the `#effective` comment; set a default ACL on a directory and create a file inside it.

## Key takeaways

- `su -` is a full login shell as the target user (their password); `sudo` runs one command with your password and logs it; `sudo -i` is a root login shell.
- Admin group: `wheel` on RHEL, `sudo` on Debian/Ubuntu; `pam_wheel` can restrict `su`.
- Edit with `visudo` (`-c` checks, `-f` for drop-ins); `/etc/sudoers.d` files containing `.` or ending in `~` are ignored; last matching rule wins.
- `NOPASSWD:` skips the prompt; `NOEXEC:` blocks shell escapes from the command.
- Special bits: setuid 4000, setgid 2000 (directory: inherit group), sticky 1000 (only owners delete); `S`/`T` mean no execute.
- umask removes bits from 666 (files) and 777 (dirs): 022 gives 644/755, 027 gives 640/750.
- `chattr +i` immutable, `+a` append only, checked with `lsattr`; they stop root until removed.
- `setfacl -m u:bob:rw`, `-d` defaults, `-x`, `-b`; the mask caps named entries; `+` in `ls -l` marks an ACL.
