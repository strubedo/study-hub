## Why compliance and audit

Hardening is only useful if you can show that it is in place and notice when it drifts. Compliance frameworks (PCI DSS, HIPAA, SOC 2, government baselines) translate into concrete checks: is the host patched, is it configured to a benchmark, have system files changed, is data destroyed properly when hardware leaves, and do users see the required legal banner. This lesson covers the tools the objectives name for each.

## Detection and response

**Anti-malware** on Linux servers is mostly about stopping the server from storing or relaying malware for others (mail and file servers) and about detecting known-bad files. **ClamAV** is the common open-source engine:

```text
srv01# freshclam                          # update signatures (clamav-freshclam service does it regularly)
srv01# clamscan -r -i /srv/uploads        # recursive, print infected files only
srv01# clamdscan --multiscan /home        # same through the clamd daemon, faster for repeated scans
```

Commercial EDR (endpoint detection and response) agents add behaviour monitoring, central alerting and response actions.

**Indicators of compromise** (IoCs) are evidence that a system has been breached. On Linux, look for:

- Unknown **listening ports** or outbound connections (`ss -tulpn`, `ss -tnp state established`), especially to unusual countries or on odd ports.
- New **accounts**, extra accounts with UID 0 (`awk -F: '$3 == 0' /etc/passwd`), unexpected entries in `authorized_keys` or `/etc/sudoers.d/`.
- New **setuid** files, executables in `/tmp`, `/var/tmp` or `/dev/shm`, files with the immutable attribute that should not have it.
- Unknown **cron jobs** or systemd units and timers (`crontab -l -u <user>`, `ls /etc/cron.*`, `systemctl list-timers`).
- System binaries whose hashes no longer match the package (`rpm -Va`, `debsums -c`), processes hidden from `ps` but visible in `/proc`.
- Gaps or truncation in logs, a stopped `auditd`, cleared shell history.
- Unexplained CPU load (cryptominers), and known-bad hashes, IP addresses or domains published in threat-intelligence feeds.

Response follows the usual order: contain (isolate from the network, but keep it running if you need memory evidence), preserve evidence (copies of logs, disk images), eradicate, and rebuild from known-good media rather than "cleaning" a rooted host.

## Vulnerability scanning

| Term | Meaning |
|---|---|
| **CVE** | Common Vulnerabilities and Exposures: a unique ID for one publicly known vulnerability, such as `CVE-2024-6387` (regreSSHion in OpenSSH) |
| **CVSS** | Common Vulnerability Scoring System: a 0.0-10.0 severity score. v3.1 ratings: 0.1-3.9 Low, 4.0-6.9 Medium, 7.0-8.9 High, 9.0-10.0 Critical. v4.0 (2023) is the current version |
| **Backporting** | The distribution applies a fix to the version it already ships instead of upgrading to the upstream version that contains the fix |

Backporting confuses version-based scanners. RHEL 9 shipped OpenSSH 8.7p1 from its first release until Red Hat rebased it to 9.9p1 in 2025, patching each security fix into 8.7p1 in the meantime; a scanner that reads the banner `OpenSSH_8.7` and compares it with upstream release notes reports dozens of CVEs that Red Hat has already fixed. Check the package instead:

```text
srv01$ rpm -q --changelog openssh-server | grep CVE-2024-6387
srv01$ dnf updateinfo list --security            # pending security errata
srv01# dnf upgrade --security                    # install only security updates
srv01$ apt changelog openssh-server | grep CVE   # Debian / Ubuntu
```

Distribution security trackers (Red Hat CVE pages, the Debian security tracker, Ubuntu CVE tracker) state which package release fixes each CVE.

Scanner types:

- **Vulnerability scanners** (Greenbone/OpenVAS, Nessus, Qualys) probe services and, with credentials, read installed package lists. Authenticated scans are much more accurate.
- **Service misconfigurations** are a separate class from missing patches: an anonymous FTP login, a database listening on all interfaces, default credentials, a world-readable private key, directory listing on a web server. Benchmarks (below) catch many of them.
- **Port scanners**: `nmap` shows what an attacker sees.

```text
srv01# nmap -sS -sV -p- 192.0.2.10       # SYN scan of all TCP ports with version detection (root)
srv01$ nmap -sT -p 22,80,443 192.0.2.10  # TCP connect scan, no root needed
srv01# nmap -sU --top-ports 50 192.0.2.10
```

- **Protocol analyzers** capture and decode traffic to prove what is actually on the wire, for example that a "secure" app sends credentials in clear or still negotiates TLS 1.0: `tcpdump -nn -i eth0 port 389 -w ldap.pcap`, then Wireshark or `tshark -r ldap.pcap`.

Only scan systems you are authorised to test.

## Standards and audit: OpenSCAP and CIS Benchmarks

**CIS Benchmarks** (Center for Internet Security) are consensus hardening guides per product: "CIS Red Hat Enterprise Linux 9 Benchmark", "CIS Ubuntu Linux 24.04 LTS Benchmark". Each recommendation has a rationale, an audit command and a remediation. **Level 1** profiles are practical baselines with little operational impact; **Level 2** adds defence-in-depth settings that may break things. Separate profiles exist for servers and workstations.

**SCAP** (Security Content Automation Protocol) is the NIST standard format for machine-readable checklists (XCCDF) and checks (OVAL). **OpenSCAP** (`oscap`) evaluates a host against SCAP content; the **SCAP Security Guide** (`scap-security-guide` package) provides content for RHEL, Ubuntu and others with profiles for CIS, DISA STIG, PCI DSS, ANSSI and more.

```text
srv01# dnf install openscap-scanner scap-security-guide
srv01$ oscap info /usr/share/xml/scap/ssg/content/ssg-rhel9-ds.xml          # list profiles
srv01# oscap xccdf eval --profile xccdf_org.ssgproject.content_profile_cis_server_l1 \
         --results /root/scan.xml --report /root/scan.html \
         /usr/share/xml/scap/ssg/content/ssg-rhel9-ds.xml
```

The HTML report lists every rule as pass, fail or not applicable, with remediation. `oscap xccdf generate fix --fix-type ansible` turns failed rules into an Ansible playbook, and `--remediate` fixes during the scan (test first). Run scans regularly, keep the reports as audit evidence, and document justified exceptions.

## File integrity

### AIDE

**AIDE** (Advanced Intrusion Detection Environment) records hashes, permissions, owners, inode data, ACLs, SELinux labels and extended attributes of the files selected in its configuration, then reports any differences.

```text
srv01# aide --init                                           # build the baseline
srv01# mv /var/lib/aide/aide.db.new.gz /var/lib/aide/aide.db.gz
srv01# aide --check                                          # compare now vs baseline
srv01# aide --update                                         # after approved changes, then move the new db into place
```

That is the RHEL layout (`/etc/aide.conf`). Debian and Ubuntu use `/etc/aide/aide.conf`, the `aideinit` helper and a daily cron job. Initialise the database on a known-clean system, and keep a copy off the host (or on read-only media): an attacker who can rewrite the database can hide anything.

### rkhunter

**rkhunter** (Rootkit Hunter) checks for known rootkit files, suspicious strings in binaries, hidden files, wrong permissions on system commands and dangerous settings such as `PermitRootLogin yes`.

```text
srv01# rkhunter --update        # update its data files
srv01# rkhunter --propupd       # record the current file properties as good (after install or updates)
srv01# rkhunter --check --sk    # run all checks, skip the "press enter" pauses; log in /var/log/rkhunter.log
```

Expect some false positives after package updates until you run `--propupd` again. `chkrootkit` is a similar tool.

### Signed package verification

Repositories sign packages (RPM) or repository metadata (APT `InRelease`/`Release.gpg`), and the package manager refuses unsigned or badly signed content when checking is on (`gpgcheck=1` for dnf, `signed-by=` for apt; Domain 2).

```text
srv01$ rpm -K nginx-1.26.3-1.el9.x86_64.rpm
nginx-1.26.3-1.el9.x86_64.rpm: digests signatures OK
srv01# rpm --import https://repo.example.com/RPM-GPG-KEY-example
srv01$ rpm -q gpg-pubkey --qf '%{NAME}-%{VERSION}-%{RELEASE}\t%{SUMMARY}\n'
```

### Installed file verification

The package database stores the digest, size, mode, owner and timestamp of every packaged file, so you can check the installed system against it:

```text
srv01# rpm -V openssh-server
S.5....T.  c /etc/ssh/sshd_config
srv01# rpm -Va                  # every package
srv01# dpkg --verify openssh-server
??5?????? c /etc/ssh/sshd_config
srv01# debsums -c               # Debian: changed files (package debsums)
```

Each position is one test: `S` size, `M` mode, `5` digest, `D` device, `L` symlink, `U` user, `G` group, `T` mtime, `P` capabilities; `.` passed and `?` could not be tested (dpkg only checks digests). The `c` marks a configuration file, which you expect to differ. A `5` on a binary such as `/usr/bin/ls` or `/usr/sbin/sshd` is a serious finding. The check is only as trustworthy as the RPM database and the `rpm` binary themselves, so after a suspected root compromise verify from trusted boot media.

## Secure data destruction

| Method | Use | Caveats |
|---|---|---|
| `shred -v -n 3 -z -u file` | Overwrite a file 3 times, add a final zero pass, then delete it | Ineffective on journaling, copy-on-write and log-structured filesystems and on SSDs, where the old blocks may survive elsewhere |
| `shred -v -n 1 /dev/sdb` | Overwrite a whole HDD | Fine for magnetic disks |
| `dd if=/dev/urandom of=/dev/sdb bs=4M status=progress` | One random pass over a whole device | Same; make **very** sure of `of=` |
| `badblocks -w -s /dev/sdb` | Destructive write-mode test: writes 0xaa, 0x55, 0xff, 0x00 to every block and reads them back | A disk test that also overwrites everything (four passes); never on a disk with data you need |
| **Cryptographic destruction** | Destroy the key, and the ciphertext is useless: `cryptsetup erase /dev/sdb1` wipes all LUKS keyslots; self-encrypting drives and NVMe support a crypto erase (`nvme format -s 2`) | Fast and the only reliable software method for SSDs; requires the data to have been encrypted from the start |
| Physical destruction | Shredding, degaussing (HDD), incineration | For media that held highly sensitive data or that cannot be erased |

SSDs remap writes (wear levelling, over-provisioned spare area), so overwriting the logical device does not reach every physical cell. For flash, use the drive's own sanitize or secure-erase command, or crypto erase, and follow NIST SP 800-88 (clear, purge, destroy) for policy.

## Software supply chain

Your system is only as trustworthy as everything you install on it.

- Install from **trusted, signed repositories**; avoid `curl ... | sudo bash` and random binaries.
- **Pin and verify**: lock dependency versions, verify checksums and signatures, and pull container images by **digest** (`image@sha256:...`), not by a movable tag.
- Keep a **software bill of materials** (SBOM, in SPDX or CycloneDX format) so you can answer "do we run the vulnerable library?" within minutes of a new CVE.
- **Sign your own artifacts** (GPG, Sigstore `cosign`) and verify signatures in CI/CD before deployment.
- Scan dependencies and images for known CVEs, and watch for typosquatted package names.

The 2024 **xz-utils backdoor** (CVE-2024-3094, CVSS 10.0) showed the risk: a malicious maintainer shipped a backdoor in xz 5.6.0 and 5.6.1 that targeted sshd through systemd-linked builds; it was caught in Debian unstable and Fedora development branches before reaching stable releases.

## Security banners

| File | Shown | By |
|---|---|---|
| `/etc/issue` | Before login on **local** consoles | `agetty`, which expands escapes such as `\n` (hostname), `\l` (tty), `\r` (kernel release), `\S` (OS name) |
| `/etc/issue.net` | Before login for **network** logins | Telnet daemons; sshd shows a file only if `Banner /etc/issue.net` is set (sshd sends it verbatim, no escapes) |
| `/etc/motd` | **After** a successful login | `pam_motd` or sshd `PrintMotd`; Ubuntu also builds a dynamic MOTD from `/etc/update-motd.d/` |

Pre-login banners carry the legal notice: authorised use only, activity is monitored, consent to monitoring. That warning is what many organisations' legal teams require before they can act on intrusion evidence. Do not put the OS name, version or hostname in pre-login banners: that helps attackers fingerprint the system. Keep `/etc/motd` for post-login operational notices (maintenance windows, the owning team).

```text
srv01# cat /etc/issue.net
WARNING: This system is for authorized use only. Activity is monitored and
logged. Unauthorized access is prohibited and may be prosecuted.
srv01# echo 'Banner /etc/issue.net' > /etc/ssh/sshd_config.d/20-banner.conf && sshd -t && systemctl reload sshd
```

## Lab it yourself

In a throwaway VM:

1. RHEL family: install `openscap-scanner scap-security-guide`, run `oscap info` on the datastream, then an `xccdf eval` with a CIS profile, and open the HTML report. Fix two failed rules and scan again.
2. Install AIDE, `aide --init`, move the database into place, change `/etc/hosts`, run `aide --check`.
3. `rpm -V openssh-server` (or `dpkg --verify openssh-server`) before and after editing `sshd_config`; `rpm -Va | grep '^..5' | grep -v ' c '`.
4. `nmap -sV localhost` from the VM and from a second VM; compare with `ss -tulpn`.
5. Create a file on ext4, `shred -v -n 1 -z -u` it; create a LUKS image file and `cryptsetup erase` it.
6. Set `/etc/issue.net` and the sshd `Banner`, then SSH in from another host. Edit `/etc/issue` with `\n` and `\l` and look at a text console.

## Key takeaways

- IoCs: unknown listeners and connections, new UID 0 or authorized keys, new setuid files, unknown cron/systemd jobs, changed binaries, log gaps. ClamAV (`freshclam`, `clamscan -r -i`) for known malware.
- CVE identifies a vulnerability, CVSS (0-10) rates it; backported fixes keep old version numbers, so check changelogs and errata, not banners.
- `nmap` for port scans (`-sS` root, `-sT` unprivileged, `-sV` versions); `tcpdump`/Wireshark as protocol analyzers.
- CIS Benchmarks (Level 1, Level 2) and OpenSCAP (`oscap xccdf eval --profile ... --report`) with SCAP Security Guide content.
- AIDE (`--init`, `--check`) and rkhunter (`--propupd`, `--check`) detect changes; `rpm -K` checks package signatures; `rpm -V`/`dpkg --verify`/`debsums` check installed files.
- Destruction: `shred`, `dd if=/dev/urandom`, `badblocks -w` for HDDs; crypto erase for SSDs and encrypted volumes; physical destruction for the most sensitive media.
- Supply chain: signed repos, pinned versions and digests, SBOMs, signed artifacts (xz backdoor lesson).
- `/etc/issue` local pre-login, `/etc/issue.net` network pre-login (sshd `Banner`), `/etc/motd` after login; banners warn, they do not advertise versions.
