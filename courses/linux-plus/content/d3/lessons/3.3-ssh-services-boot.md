## Hardening sshd

SSH is the front door of almost every Linux server, so its configuration matters more than any other. The server reads **`/etc/ssh/sshd_config`**, and on current RHEL, Debian and Ubuntu that file begins with `Include /etc/ssh/sshd_config.d/*.conf`. For most keywords **the first value obtained wins**, so a setting in a drop-in such as `/etc/ssh/sshd_config.d/50-cloud-init.conf` beats a later line in the main file. Put your policy in an early drop-in (for example `10-hardening.conf`) and check the result rather than the files:

```text
srv01# sshd -t                                   # syntax check; silent if OK
srv01# sshd -T | grep -Ei 'permitrootlogin|passwordauth|x11forwarding|allowgroups'
permitrootlogin no
passwordauthentication no
x11forwarding no
allowgroups sshusers
allowgroups wheel
srv01# systemctl reload sshd                     # Debian/Ubuntu unit: ssh
```

A hardened drop-in:

```text
# /etc/ssh/sshd_config.d/10-hardening.conf
PermitRootLogin no
PasswordAuthentication no
KbdInteractiveAuthentication no
PubkeyAuthentication yes
X11Forwarding no
AllowGroups sshusers wheel
MaxAuthTries 3
LoginGraceTime 30
ClientAliveInterval 300
ClientAliveCountMax 2
```

| Keyword | Notes |
|---|---|
| `PermitRootLogin` | `yes`, `prohibit-password` (the upstream default: root may log in with a key but not a password), `forced-commands-only`, `no` |
| `PasswordAuthentication` / `KbdInteractiveAuthentication` | Turn both off for key-only logins (keyboard-interactive can also prompt for a password through PAM) |
| `X11Forwarding` | Upstream default `no`, but Debian and Ubuntu ship `X11Forwarding yes` in their `sshd_config`; set `no` on servers |
| `AllowUsers alice bob@198.51.100.*` | Only these users (optionally from these hosts) may log in |
| `AllowGroups sshusers` | Only members of these groups (primary or supplementary) |
| `DenyUsers`, `DenyGroups` | Explicit exclusions, checked first |
| `AllowTcpForwarding`, `AllowAgentForwarding`, `DisableForwarding` | Restrict tunnels; `DisableForwarding yes` turns off every kind |

sshd checks DenyUsers, AllowUsers, DenyGroups and then AllowGroups, and a user must pass every one that is set: with both `AllowUsers` and `AllowGroups` present, a user must match both.

> **Watch out:** Keep your current session open, test a *new* login from a second terminal, and only then close the first. `sshd -t` catches syntax errors but not "I just locked out my own group".

### Keys vs passwords

Key authentication proves possession of a private key without sending any secret to the server, cannot be guessed by a password-spraying bot, and can be restricted per key. Passwords can be phished, reused and brute-forced.

```text
alice@ws01:~$ ssh-keygen -t ed25519 -C "alice@ws01"
Generating public/private ed25519 key pair.
Enter file in which to save the key (/home/alice/.ssh/id_ed25519):
Enter passphrase for "/home/alice/.ssh/id_ed25519" (empty for no passphrase):
Enter same passphrase again:
Your identification has been saved in /home/alice/.ssh/id_ed25519
Your public key has been saved in /home/alice/.ssh/id_ed25519.pub
The key fingerprint is:
SHA256:EXAMPLE0fingerprint0not0a0real0key0000000000 alice@ws01
alice@ws01:~$ ssh-copy-id alice@srv01.example.com
```

`ssh-copy-id` appends the public key to `~/.ssh/authorized_keys` on the server. With the default `StrictModes yes`, sshd ignores that file if the home directory, `~/.ssh` (use 700) or `authorized_keys` (use 600) is writable by group or others, a common reason why "the key is there but it still asks for a password". Options in front of a key restrict it: `from="198.51.100.0/24",command="/usr/local/bin/backup",no-port-forwarding ssh-ed25519 AAAA...`.

### SSH agent

Protect private keys with a passphrase, and let **ssh-agent** hold the decrypted key in memory so you type the passphrase once per session:

```text
alice@ws01:~$ eval "$(ssh-agent -s)"
alice@ws01:~$ ssh-add ~/.ssh/id_ed25519
alice@ws01:~$ ssh-add -l
alice@ws01:~$ ssh -A jump01        # agent forwarding: use only to hosts you trust
```

Agent forwarding (`-A`, `ForwardAgent yes`) lets anyone with root on the remote host use your agent while you are connected. To reach an inner host through a bastion, prefer `ssh -J jump01 srv01` (ProxyJump), which needs no forwarding.

### SSH tunneling

| Option | Direction | Example |
|---|---|---|
| `-L [bind:]lport:host:hport` | **Local** forward: a port on your machine reaches host:hport *from the server's side* | `ssh -L 5432:db01:5432 jump01`, then connect to `localhost:5432` |
| `-R [bind:]rport:host:hport` | **Remote** forward: a port on the server reaches host:hport *from your side* | `ssh -R 8080:localhost:80 srv01` exposes your local web server on srv01's port 8080 |
| `-D [bind:]port` | **Dynamic** SOCKS proxy | `ssh -D 1080 jump01` |
| `-N`, `-f` | No remote command; go to background | `ssh -fN -L ...` |

Forwarded ports bind to loopback by default; `GatewayPorts` controls whether remote forwards may listen on other addresses. Tunnels are also an exfiltration path, which is why servers that do not need them set `AllowTcpForwarding no`.

### SFTP

SFTP is a file-transfer subsystem inside SSH (port 22), unrelated to FTP. `Subsystem sftp internal-sftp` (or the external `sftp-server` binary) enables it. To give a group file transfer only, jailed in a directory:

```text
Match Group sftponly
    ChrootDirectory /srv/sftp/%u
    ForceCommand internal-sftp
    DisableForwarding yes
```

sshd requires the `ChrootDirectory` and every directory above it to be owned by root and not writable by group or others, so give the user a writable subdirectory inside it.

## chroot

`chroot /srv/jail /bin/bash` runs a program with `/srv/jail` as its `/`. The program can no longer name files outside, which reduces what a compromised service can reach (sshd's `ChrootDirectory`, BIND's and Postfix's optional jails). The new root must contain everything the program needs (binaries, libraries from `ldd`, `/dev` nodes). `chroot` is also the rescue tool for repairing an installed system from live media: mount it on `/mnt/sysroot`, bind-mount `/dev`, `/proc` and `/sys`, then `chroot /mnt/sysroot` and run `grub2-install` or `passwd`.

A chroot is not a security boundary against root: a process with root inside it can escape. Namespaces (containers) and SELinux are stronger isolation.

## fail2ban

**fail2ban** watches logs (or the journal) for repeated failures and bans the source address with a firewall rule for a while. It is in EPEL on RHEL and in the main archive on Debian and Ubuntu. Never edit `jail.conf`; override in `/etc/fail2ban/jail.local` or `jail.d/*.local`:

```text
# /etc/fail2ban/jail.local
[DEFAULT]
bantime  = 1h
findtime = 10m
maxretry = 5
ignoreip = 127.0.0.1/8 ::1 198.51.100.0/24

[sshd]
enabled = true
backend = systemd
```

`maxretry` failures within `findtime` cause a ban lasting `bantime` (upstream defaults: 5, 10 minutes, 10 minutes). `ignoreip` keeps your management network from banning itself. The ban action matches your firewall (`banaction = firewallcmd-rich-rules`, `nftables`, `iptables-multiport`, `ufw`).

```text
srv01# fail2ban-client status sshd
Status for the jail: sshd
|- Filter
|  |- Currently failed:	1
|  |- Total failed:	42
|  `- Journal matches:	_SYSTEMD_UNIT=sshd.service + _COMM=sshd
`- Actions
   |- Currently banned:	1
   |- Total banned:	6
   `- Banned IP list:	203.0.113.50
srv01# fail2ban-client set sshd unbanip 203.0.113.50
```

## Avoid insecure services

| Service | Port | Problem | Replacement |
|---|---|---|---|
| Telnet | TCP 23 | Everything, including the password, in clear text | SSH |
| FTP | TCP 21 (data 20 or passive ports) | Clear-text credentials and data | SFTP or SCP over SSH; FTPS (FTP over TLS) if FTP is mandatory |
| TFTP | UDP 69 | No authentication at all, clear text | Keep only where required (PXE, network device firmware), bound to a management VLAN and read-only |

Find and remove them: `ss -tulpn` for listeners, `systemctl list-unit-files | grep -Ei 'telnet|ftp|tftp'`, then `systemctl disable --now` and remove the packages (`telnet-server`, `vsftpd`, `tftp-server` on RHEL; `telnetd`, `vsftpd`, `tftpd-hpa` on Debian). The `telnet` client is harmless and handy for testing ports, but `nc -vz` does the same job.

## Disable unused filesystems

Every filesystem driver the kernel can load is attack surface: rarely used ones have had memory-corruption bugs that an unprivileged user could trigger by mounting a crafted image (a USB stick, or a file through a desktop automounter). CIS benchmarks list `cramfs`, `freevxfs`, `hfs`, `hfsplus`, `jffs2`, `udf` and `usb-storage` among others (keep `squashfs` if you use Snap packages, which are squashfs images).

```text
# /etc/modprobe.d/disable-filesystems.conf
install cramfs /bin/false
blacklist cramfs
install hfsplus /bin/false
blacklist hfsplus
install usb-storage /bin/false
blacklist usb-storage
```

`blacklist` stops automatic loading by alias; `install ... /bin/false` also makes an explicit `modprobe` fail (Domain 1). Check with `modprobe -n -v cramfs`, and `rmmod` any that are already loaded. Mount options harden what is mounted: `nodev,nosuid,noexec` on `/tmp`, `/var/tmp`, `/dev/shm` and removable media.

## Remove unnecessary SUID

Every setuid-root binary is a program that an ordinary user can run as root; a bug in any one is a local root exploit (PwnKit in `pkexec` is the famous example). Inventory them, compare with what the distribution ships, and remove what you do not use.

```text
srv01# find / -xdev -type f -perm -4000 -ls 2>/dev/null
srv01# find / -xdev -type f -perm -2000 -ls 2>/dev/null       # setgid
srv01# rpm -qf /usr/bin/pkexec        # or: dpkg -S /usr/bin/pkexec
srv01# chmod u-s /usr/bin/pkexec      # or remove the package
```

Package updates can restore a removed bit, so either remove the package or enforce the change with configuration management. An unexpected setuid file, especially one owned by root in `/tmp`, a home directory or `/dev/shm`, is an indicator of compromise. `nosuid` on data filesystems makes any setuid bit there ineffective.

## Secure boot: UEFI

**UEFI Secure Boot** lets firmware run only bootloaders signed by a key in its database (`db`). Linux distributions use a chain:

1. Firmware verifies **shim**, which is signed by Microsoft's third-party UEFI CA.
2. shim verifies **GRUB** (or systemd-boot) with the distribution's key built into shim, or a **MOK** (Machine Owner Key) the administrator enrolled.
3. GRUB verifies the **kernel**, and the kernel verifies **modules** (unsigned modules are refused when Secure Boot is on).

```text
srv01$ mokutil --sb-state
SecureBoot enabled
srv01# mokutil --import /root/mok.der      # enrol your own key; confirm in MokManager at the next boot
srv01$ mokutil --list-enrolled
```

Third-party kernel modules built by DKMS (NVIDIA, VirtualBox, out-of-tree NIC drivers) must be signed with a MOK or they fail to load with "Key was rejected by service". With Secure Boot on, many distributions also put the kernel in **lockdown** mode, which blocks things like writing `/dev/mem` or loading unsigned kexec images. Secure Boot protects the boot chain from bootkits; it does not encrypt anything and does not protect a running system, so it complements a firmware password, LUKS and measured boot (TPM).

## Lab it yourself

Throwaway VM (use a VM console so a mistake cannot lock you out):

1. Create `/etc/ssh/sshd_config.d/10-hardening.conf` with the settings above but `AllowGroups wheel sshusers` (RHEL) or `sudo sshusers` (Ubuntu); `sshd -t`, `sshd -T | grep -i allowgroups`, reload, and test from another terminal.
2. `ssh-keygen -t ed25519`, `ssh-copy-id`, then `chmod 777 ~/.ssh` on the server and watch key login fail; check the auth log for the `bad ownership or modes` message. Fix it.
3. `ssh -L 8080:localhost:80 srv01` and browse `http://localhost:8080`.
4. Install fail2ban, enable the sshd jail, fail some logins from a second VM, and read `fail2ban-client status sshd`; unban yourself.
5. `find / -xdev -perm -4000 -type f 2>/dev/null` and identify each file's package.
6. `modprobe -n -v cramfs` before and after adding the modprobe.d file.
7. `mokutil --sb-state` on a UEFI VM with and without Secure Boot enabled in the VM firmware.

## Key takeaways

- sshd: first value wins, drop-ins in `sshd_config.d/` come first; verify with `sshd -t` and `sshd -T`; reload, and test a new login before closing your session.
- Set `PermitRootLogin no`, `PasswordAuthentication no`, `X11Forwarding no`, and `AllowUsers` / `AllowGroups`.
- Key auth: `ssh-keygen`, `ssh-copy-id`, `~/.ssh` 700 and `authorized_keys` 600; `ssh-agent`/`ssh-add` for passphrases; prefer `-J` over `-A`.
- Tunnels: `-L` local, `-R` remote, `-D` SOCKS. SFTP is SSH; `ChrootDirectory` + `ForceCommand internal-sftp` jails transfer-only users.
- chroot changes the apparent `/`; useful for jails and rescue, but not a boundary against root.
- fail2ban: `jail.local`, `maxretry`/`findtime`/`bantime`, `ignoreip`, `fail2ban-client status sshd`.
- Replace Telnet (23), FTP (21) and TFTP (69/udp) with SSH, SFTP/SCP or FTPS.
- Disable unused filesystem modules in `/etc/modprobe.d`; audit setuid files with `find -perm -4000`.
- Secure Boot chain: firmware, shim (Microsoft CA), GRUB, kernel, modules; MOK via `mokutil`.
