## Password policy: what actually helps

Passwords remain the weakest link, and the guidance changed a lot in the last decade. **NIST SP 800-63B** (the US digital identity guideline most policies now cite) says, in short: favour **length** over composition rules, allow long passphrases and all characters, **check new passwords against lists of breached and common passwords**, do **not** force periodic changes without evidence of compromise, and add a second factor. Older rule sets ("8 characters, one of each class, change every 90 days") produce `Summer2026!` followed by `Autumn2026!`. The exam still asks about all the classic controls, so know both what they are and where Linux sets them.

| Control | Where it is set on Linux |
|---|---|
| Length and complexity | `pam_pwquality` with `/etc/security/pwquality.conf` (and `pwquality.conf.d/`) |
| Expiration (aging) | `/etc/login.defs` defaults for new accounts (`PASS_MAX_DAYS`, `PASS_MIN_DAYS`, `PASS_WARN_AGE`); `chage` per account (Domain 2) |
| Reuse and history | `pam_pwhistory` (`remember=N`, history in `/etc/security/opasswd`), or `remember=N` on `pam_unix` |
| Lockout after failures | `pam_faillock` (current) or `pam_tally2` (legacy) |
| Hashing algorithm | `ENCRYPT_METHOD` in `login.defs` and the `pam_unix` option: yescrypt (Debian, Ubuntu, Fedora) or SHA-512 (RHEL 9) |

### Complexity and length: pam_pwquality

`pam_pwquality` runs in the `password` stack when a user changes their password (Domain 3.1 showed it in `system-auth`). Settings live in `/etc/security/pwquality.conf`:

```text
# /etc/security/pwquality.conf
minlen = 14
minclass = 3
dcredit = 0
ucredit = 0
maxrepeat = 3
dictcheck = 1
usercheck = 1
difok = 5
enforce_for_root
```

| Option | Meaning |
|---|---|
| `minlen` | Minimum length (character-class credits can count toward it unless the credits are 0 or negative) |
| `minclass` | How many of the four classes (digits, upper, lower, other) are required |
| `dcredit`, `ucredit`, `lcredit`, `ocredit` | Positive: credit toward `minlen` for that class. **Negative**: at least that many of the class are required (`dcredit = -1` means one digit minimum) |
| `maxrepeat`, `maxsequence` | Limit repeated characters and sequences such as `12345` |
| `dictcheck`, `usercheck` | Reject dictionary words (cracklib) and passwords containing the user name |
| `difok` | Characters that must differ from the old password |
| `enforce_for_root` | Apply the checks when root sets a password too (otherwise root only gets a warning) |

On Debian and Ubuntu install `libpam-pwquality`, which adds the module to `common-password` through `pam-auth-update`. The policy applies when passwords are **changed**; existing passwords are not rechecked, which is why policy changes are usually paired with forced expiry (`chage -d 0 user`).

### Expiration

Aging works as Domain 2 showed: `PASS_MAX_DAYS` and friends in `/etc/login.defs` set defaults for **new** accounts only, and `chage -M 365 -W 14 alice` changes an existing account. Current guidance is to use a long maximum (or none) for human users with MFA, and to expire immediately when a breach is suspected (`passwd -e alice` or `chage -d 0 alice`).

### Reuse and history

```text
password    requisite     pam_pwquality.so local_users_only
password    required      pam_pwhistory.so remember=5 use_authtok enforce_for_root
password    sufficient    pam_unix.so sha512 shadow use_authtok
```

`pam_pwhistory` keeps the last N password hashes in `/etc/security/opasswd` (root-only) and rejects a new password that matches any of them; newer versions also read `/etc/security/pwhistory.conf`. Combine it with `PASS_MIN_DAYS` (for example 1), otherwise a user can cycle through five quick changes and return to the old password.

## Account lockout: pam_faillock and the legacy pam_tally2

The objectives name **`pam_tally2`**. Know it, but know that it is gone: it was deprecated and then **removed from Linux-PAM in version 1.5.0 (2020)**, so RHEL 8 and 9, Debian 11 and later and current Ubuntu do not have it. Its replacement is **`pam_faillock`**.

| | pam_tally2 (legacy) | pam_faillock (current) |
|---|---|---|
| PAM lines | `auth required pam_tally2.so deny=5 unlock_time=900 onerr=fail` plus `account required pam_tally2.so` | `pam_faillock.so preauth` before the password module, `pam_faillock.so authfail` after it, and `account required pam_faillock.so` |
| Settings | Module arguments | `/etc/security/faillock.conf` (`deny`, `unlock_time`, `fail_interval`, `even_deny_root`) or module arguments |
| Tally storage | `/var/log/tallylog` | One file per user in `/var/run/faillock/` (cleared at reboot) |
| Show failures | `pam_tally2 --user bob` | `faillock --user bob` |
| Unlock | `pam_tally2 --user bob --reset` | `faillock --user bob --reset` |

```text
# /etc/security/faillock.conf
deny = 5
fail_interval = 900
unlock_time = 600
# even_deny_root
```

The defaults are `deny = 3`, `fail_interval = 900` (15 minutes) and `unlock_time = 600` (10 minutes); `unlock_time = 0` means "locked until an administrator resets it". Root is exempt unless `even_deny_root` is set, to avoid a denial-of-service lockout of the only admin. On RHEL turn it on with `authselect enable-feature with-faillock`; on Debian and Ubuntu add the three lines to `common-auth` and `common-account` (or a `pam-auth-update` profile).

```text
srv01# faillock --user bob
bob:
When                Type  Source                                           Valid
2026-11-22 09:14:02 RHOST 203.0.113.50                                         V
2026-11-22 09:14:06 RHOST 203.0.113.50                                         V
2026-11-22 09:14:11 RHOST 203.0.113.50                                         V
srv01# faillock --user bob --reset
```

> **Watch out:** Lockout and SSH keys: `pam_faillock` sits in the `auth` stack, which a public-key login does not go through, so a locked user with a valid key can still log in by key. Lockout throttles password guessing; it is not a way to disable an account (use `usermod -L` plus `chage -E 0`, as in Domain 2).

## Multifactor authentication

MFA combines factors from different categories: something you **know** (password, PIN), something you **have** (phone authenticator, hardware key, smart card) and something you **are** (fingerprint). Two passwords are still one factor. On Linux, MFA is again a PAM matter:

| Method | How |
|---|---|
| TOTP (authenticator apps) | `pam_google_authenticator` (package `libpam-google-authenticator` or `google-authenticator` from EPEL); each user runs `google-authenticator` to create `~/.google_authenticator` |
| FIDO2 / U2F hardware keys | `pam_u2f` for local logins and sudo; for SSH, `ssh-keygen -t ed25519-sk` makes a key that needs the token to be touched |
| Smart cards / PIV | SSSD with `pam_cert_auth` |
| Central MFA | FreeIPA/IdM OTP, RADIUS (`pam_radius`), or an identity provider at the SSH bastion |

For SSH, require both a key and a one-time code with:

```text
AuthenticationMethods publickey,keyboard-interactive
KbdInteractiveAuthentication yes
UsePAM yes
```

The comma means "both, in this order"; a space-separated list would mean "any one of these".

## Checking existing breach lists

Billions of real passwords have leaked, and attackers try them first. A **breach list check** rejects any new password that appears in a corpus of compromised passwords (NIST requires this). Services such as Have I Been Pwned's *Pwned Passwords* use **k-anonymity**: the client sends only the first five hex characters of the password's SHA-1 hash and compares the returned suffixes locally, so neither the password nor its full hash leaves the host. Locally, `pam_pwquality`'s `dictcheck` and `badwords` and cracklib dictionaries cover common words; enterprise directories (FreeIPA, AD with add-ons) can check against downloaded breach corpora. Also check whether your users' **accounts** (email addresses) appear in breach notifications, and force resets for those.

## Restricted shells

| Shell | Effect |
|---|---|
| `/sbin/nologin` (`/usr/sbin/nologin`) | Prints "This account is currently not available." (or the text of `/etc/nologin.txt`) and exits 1. For service accounts that must exist but never log in interactively |
| `/bin/false` | Exits 1 silently; same purpose |
| `/bin/rbash` (`bash -r`) | A **restricted bash**: no `cd`, no changing `PATH`, `SHELL`, `ENV` or `BASH_ENV`, no command names containing `/`, no output redirection (`>`, `>>`), no `exec` |

```text
srv01# usermod -s /sbin/nologin svc_backup
srv01# usermod -s /bin/rbash kiosk1
```

A nologin shell blocks interactive shells, but not necessarily everything: if an SSH key exists, port forwarding and SFTP may still work unless sshd also restricts the account (`ForceCommand`, `DisableForwarding`, `Match`). rbash is easily escaped if `PATH` contains programs with shell escapes (`vi`, `less`, `python`), so give the user a `PATH` pointing to a directory of a few safe symlinks, make the startup files root-owned, and treat it as a convenience, not a jail.

## Avoid running as root

- Log in as yourself and use `sudo` for specific commands; disable direct root SSH (`PermitRootLogin no`) and consider locking root's password (`passwd -l root`) where console access is otherwise handled, as Ubuntu does by default.
- Run services as dedicated unprivileged accounts (`User=` in the systemd unit, `useradd -r`), or `DynamicUser=yes`, and drop capabilities (`CapabilityBoundingSet=`, `NoNewPrivileges=yes`).
- Run containers rootless or with `--user` (Domain 2), and never run a web application, a build or `pip install` as root.
- Use groups and ACLs (Hardening 1) to grant access instead of making everything world-writable or root-only.

The point is blast radius: a bug in a process running as `svc_app` exposes `svc_app`'s files; the same bug as root exposes the whole machine.

## Lab it yourself

In a throwaway RHEL-family VM (adapt the PAM files on Debian):

1. Set `minlen = 14` and `dcredit = -1` in `/etc/security/pwquality.conf`; as a test user, try `passwd` with short and digit-free passwords and read the messages.
2. `authselect enable-feature with-faillock` (RHEL) and set `deny = 3` in `faillock.conf`; fail three `ssh` password logins, run `faillock --user testuser`, try the correct password (refused), then `faillock --user testuser --reset`.
3. Add `pam_pwhistory.so remember=3` and try to reuse a password.
4. `usermod -s /sbin/nologin testuser; su - testuser`; then `usermod -s /bin/rbash testuser` and try `cd /`, `/bin/ls` and `echo x > f` as that user.
5. On a Debian VM, check `apt-cache policy libpam-modules` and `ls /usr/lib/x86_64-linux-gnu/security/ | grep -E 'tally|faillock'` to see that only pam_faillock exists.

## Key takeaways

- Modern guidance (NIST SP 800-63B): length over composition, breach-list checks, no forced periodic changes without cause, MFA.
- Complexity: `pam_pwquality` and `/etc/security/pwquality.conf` (`minlen`, `minclass`, negative credits = required count, `enforce_for_root`).
- History: `pam_pwhistory remember=N` with `/etc/security/opasswd`, plus a minimum age. Aging: `login.defs` for new accounts, `chage` for existing ones.
- `pam_tally2` is legacy (removed in Linux-PAM 1.5.0); use `pam_faillock` with `faillock.conf` and `faillock --user bob --reset`. Defaults: deny 3, unlock after 600 s.
- MFA = factors from different categories; on Linux via PAM (TOTP, FIDO2, smart cards) and `AuthenticationMethods publickey,keyboard-interactive` for SSH.
- `/sbin/nologin` for service accounts; `/bin/rbash` restricts but is escapable.
- Do work as yourself with sudo; run services and containers as unprivileged users.
