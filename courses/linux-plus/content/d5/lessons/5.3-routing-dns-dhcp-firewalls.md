## When the link is fine but traffic still fails

The previous lesson covered the link and the address. Here the interface is up with the right address, and the fault is further along: the route, the DHCP exchange, name resolution or a firewall. The client's error message is the fastest clue, so learn to read it.

| Client error | What happened on the wire | Usual cause |
|---|---|---|
| `Network is unreachable` | Nothing sent; no route matches | No default route, interface down |
| `No route to host` | ICMP host/admin-prohibited came back, or ARP for the next hop failed | Firewall `REJECT` (firewalld's default), host down on the local subnet |
| `Connection refused` | TCP RST came back | Nothing listening on that port, or `REJECT --reject-with tcp-reset` |
| Hangs, then `Connection timed out` | No answer at all | Firewall `DROP`, routing black hole, server down beyond a router |
| `Name or service not known` / `Could not resolve host` | DNS answered NXDOMAIN or no DNS answer | Wrong name, resolver or search domain |
| `Temporary failure in name resolution` | No DNS server reachable | Resolver down, port 53 blocked, wrong `nameserver` |

## Routing issues: gateway and server unreachable

```text
[root@web01 ~]# ip route
192.0.2.0/24 dev enp1s0 proto kernel scope link src 192.0.2.10 metric 100
[root@web01 ~]# ping -c1 203.0.113.50
ping: connect: Network is unreachable
```

There is no `default via ...` line, so only the local subnet is reachable. Typical reasons: the DHCP lease did not include a router option, the static profile has no gateway (`nmcli connection modify enp1s0 ipv4.gateway 192.0.2.1`, or `routes: - to: default via: 192.0.2.1` in Netplan), or `ipv4.never-default yes` is set on that profile.

`ip route get` shows the decision the kernel makes for one destination, which settles most routing questions:

```text
[root@web01 ~]# ip route get 198.51.100.25
198.51.100.25 via 10.10.0.1 dev enp2s0 src 10.10.0.10 uid 0
    cache
```

If that is not the path you expected, look for a more specific route or a second default route with a lower metric (`ip route show default`). Other routing faults:

- **Two default routes** on two interfaces: replies leave by the lower metric while requests arrived on the other one. With strict reverse-path filtering (`net.ipv4.conf.*.rp_filter=1`) the kernel drops the asymmetric packets. Fix with one default route, policy routing (`ip rule`), or loose mode (`rp_filter=2`).
- **Missing static route** to a management or storage network behind a different router: add it to the profile (`ipv4.routes "10.20.0.0/16 10.10.0.254"`), not only with `ip route add`, which is lost at reboot.
- **Server unreachable beyond the gateway**: use `traceroute -n`, `tracepath -n` or `mtr -n 203.0.113.50` to see the last hop that answers. In traceroute, `!H`, `!N` and `!X` mean host unreachable, network unreachable and administratively prohibited; `* * *` from some hop onwards is a drop or a hop that does not send ICMP. A routing loop shows the same two addresses repeating until the TTL runs out.
- **Return path missing**: the remote server has no route back to your subnet. `tcpdump -ni enp1s0 host 203.0.113.50` showing your SYNs going out and nothing coming back, while the remote side sees them arrive, proves it.
- **Forwarding host**: a Linux router with `net.ipv4.ip_forward = 0` (lesson 3.2) drops transit traffic.

## DHCP issues

A DHCP client that gets no lease leaves the interface without an IPv4 address (NetworkManager keeps retrying; link-local 169.254.0.0/16 addresses appear only if configured).

| Check | Command |
|---|---|
| Client state and lease | `nmcli device show enp1s0` (`DHCP4.OPTION` lines), `nmcli -f IP4 device show enp1s0`; `networkctl status enp1s0` on systemd-networkd and Netplan servers |
| Client log | `journalctl -u NetworkManager -g dhcp4` (look for request timed out); `journalctl -u systemd-networkd` |
| Is it on the wire | `tcpdump -ni enp1s0 -e port 67 or port 68` |
| Retry | `nmcli connection up enp1s0`; `networkctl renew enp1s0`; legacy `dhclient -v enp1s0` |

The capture tells you which side is broken. `DHCPDISCOVER` (shown as `BOOTP/DHCP, Request`) leaving with no `Offer` back means the server never saw it or cannot answer: no DHCP relay (`ip helper-address`) on the VLAN's router interface, wrong VLAN, server down, or the scope is **exhausted**. An Offer that the client ignores points to the client side (firewall on the client, MAC changed so a reservation does not match). On the server (ISC Kea or the legacy ISC dhcpd, lesson 2.4) look for "no free leases" messages. A host that gets an address but the **wrong gateway or DNS** is a scope-option problem on the server, or a rogue DHCP server; the capture shows which server answered.

## DNS issues

Know which component answers. On Ubuntu, Fedora and many others, `/etc/resolv.conf` points at the **systemd-resolved** stub `127.0.0.53`, and the real upstream servers are shown by `resolvectl status`. On RHEL, NetworkManager normally writes the upstream servers straight into `/etc/resolv.conf`. `/etc/nsswitch.conf` decides the order (`hosts: files dns` means `/etc/hosts` first).

```text
alice@web01:~$ getent hosts db01.example.com
alice@web01:~$ dig +short db01.example.com
192.0.2.40
alice@web01:~$ grep db01 /etc/hosts
alice@web01:~$ grep hosts: /etc/nsswitch.conf
hosts:          files myhostname
```

`dig` queries DNS directly and ignores `/etc/hosts` and NSS; `getent hosts` (and every normal application) uses NSS. Here `dns` (or `resolve` for systemd-resolved) is missing from the `hosts:` line, so applications never ask DNS. When `dig` and applications disagree, look at NSS and `/etc/hosts`.

| Symptom (`dig` status) | Meaning | Next step |
|---|---|---|
| `status: NXDOMAIN` | The name does not exist in that zone | Spelling, search domain (`search example.com`), missing record, split-horizon view |
| `status: SERVFAIL` | The resolver could not get an answer | Upstream or authoritative server broken, DNSSEC validation failure; try `dig +cd` and another resolver |
| `status: REFUSED` | Server will not answer you | Recursion not allowed for your address (ACL) |
| `connection timed out; no servers could be reached` | No reply from any server | `nameserver` wrong, port 53 UDP/TCP blocked, resolver down |
| Old address returned | Caching | TTL; `resolvectl flush-caches`, wait for TTL |

Compare resolvers to locate the problem: `dig @192.0.2.53 db01.example.com` (internal) versus `dig @127.0.0.53 ...` (local stub). Slow SSH logins with a long pause after the password often come from reverse lookups of the client address timing out; fix the PTR records, or the resolver (`UseDNS` is `no` by default in current OpenSSH).

## Misconfigured firewalls

Lesson 3.2 taught firewalld, ufw and nftables. Diagnosis follows three questions.

**1. Is the service listening, and on which address?**

```text
[root@web01 ~]# ss -tlnp | grep -E ':(80|8080)\b'
LISTEN 0      511        127.0.0.1:8080      0.0.0.0:*    users:(("node",pid=2210,fd=19))
LISTEN 0      511          0.0.0.0:80        0.0.0.0:*    users:(("nginx",pid=1802,fd=6))
```

Port 8080 is bound to `127.0.0.1` only, so remote clients get `Connection refused` even when the firewall allows the port (if the firewall rejects or drops it, they see that instead); change the application's bind address. Port 80 is on all IPv4 addresses.

**2. What does the firewall allow?**

```text
[root@web01 ~]# firewall-cmd --get-active-zones
public
  interfaces: enp1s0
[root@web01 ~]# firewall-cmd --zone=public --list-all
public (active)
  target: default
  interfaces: enp1s0
  services: cockpit dhcpv6-client ssh
  ports:
  ...
```

HTTP is not allowed, and the zone's default target rejects it, so clients see `No route to host`. Fix with `firewall-cmd --zone=public --add-service=http --permanent` followed by `firewall-cmd --reload`, or add it at runtime and then `firewall-cmd --runtime-to-permanent`. The classic mistake is the reverse: `--add-service` without `--permanent` works until the next reload or reboot. Other common errors: the interface is in a different zone than the one you edited, the rule allows the wrong protocol (`--add-port=53/tcp` when DNS needs UDP too), or a rich rule with a source address is in a zone that never sees that traffic.

On Ubuntu, `ufw status verbose` shows the rules and default policy; `ufw allow 80/tcp` or `ufw allow 'Nginx Full'`. With raw nftables or iptables, **order matters**: a rule appended after a catch-all `drop` or `reject` never matches. `nft list ruleset` and `iptables -L -n -v --line-numbers` show the order and per-rule packet counters; a counter that increases while you test identifies the rule that is hitting your traffic. Docker and Podman insert their own NAT and filter rules, so published container ports can bypass ufw rules.

**3. Does the traffic reach the host?** `tcpdump -ni enp1s0 port 80` on the server while the client connects: no packets means the block is upstream (a network firewall, security group or ACL), packets in but no reply means the host firewall or the application.

> **Exam tip:** "Connection refused" = something answered with RST (port closed or tcp-reset). "No route to host" with the host clearly up = an ICMP reject from a firewall. A timeout = DROP or no path.

## Lab it yourself

1. In the lab VM (on its console, not over SSH from another network), delete the default route with `ip route del default`, try `ping 203.0.113.50`, then restore it with `nmcli connection up <profile>`.
2. Run `python3 -m http.server 8080 --bind 127.0.0.1` and try to reach it from another VM; then bind to `0.0.0.0`, test again with firewalld blocking it, and finally allow `8080/tcp` with and without `--permanent` across a `firewall-cmd --reload`.
3. Compare the client errors for `REJECT` and `DROP`: add `nft add rule inet filter input tcp dport 9000 drop` in a lab table and test with `nc -zv`.
4. Remove `dns` from the `hosts:` line of `/etc/nsswitch.conf` in a throwaway container inside the lab VM (or in the VM itself after a snapshot) and compare `dig` with `getent hosts`.
5. Capture a DHCP exchange with `tcpdump -ni <if> -e port 67 or port 68` while running `nmcli connection up <profile>`.

## Key takeaways

- Read the client error: unreachable network = no route, refused = RST, no route to host = ICMP reject or ARP failure, timeout = drop.
- `ip route` and `ip route get <dest>` show the gateway decision; fix missing gateways and static routes in the NetworkManager or Netplan profile.
- `traceroute`/`tracepath`/`mtr` show where the path stops; `tcpdump` proves whether replies come back.
- DHCP: capture ports 67/68; Discover without Offer = relay, VLAN, server or exhausted scope.
- `dig` bypasses `/etc/hosts` and NSS, `getent hosts` does not; NXDOMAIN, SERVFAIL, REFUSED and timeouts each point to a different fault.
- Firewall checks: `ss -tlnp` bind address, zone and interface (`--get-active-zones`), `--permanent` plus `--reload`, rule order and counters.
