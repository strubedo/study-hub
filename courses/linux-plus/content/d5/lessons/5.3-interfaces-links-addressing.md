## Bottom-up, like on a switch

Network troubleshooting on Linux follows the same layered method you use on routers and switches: link first, then addressing, then the path, then names and policy. Lesson 1.4 introduced the tools (`ip`, `ethtool`, `nmcli`, `ping`, `tracepath`, `ss`, `tcpdump`); this lesson and the next apply them to the objective's list of faults.

| Layer | First command | Healthy output |
|---|---|---|
| Physical / link | `ip -br link`, `ethtool enp1s0` | `UP`, `Link detected: yes`, expected speed and duplex |
| Addressing | `ip -br addr`, `ip -6 addr` | Correct address and prefix length, no `dadfailed` |
| Local segment | `ping -c3 <gateway>`, `ip neigh` | Replies, neighbour `REACHABLE` |
| Path | `ip route get <dest>`, `tracepath`, `mtr` | Right gateway and interface |
| Names / service | `dig`, `resolvectl`, `ss -tlnp`, firewall | Lesson 5.3 (routing, DNS, DHCP and firewalls) |

## Link down

```text
[root@srv01 ~]# ip -br link
lo               UNKNOWN        00:00:00:00:00:00 <LOOPBACK,UP,LOWER_UP>
enp1s0           DOWN           52:54:00:3a:10:01 <NO-CARRIER,BROADCAST,MULTICAST,UP>
enp2s0           DOWN           52:54:00:3a:10:02 <BROADCAST,MULTICAST>
```

Read the flags carefully:

- **enp1s0**: `UP` inside the brackets means the administrator enabled it, but **`NO-CARRIER`** and state `DOWN` mean there is no link: cable, transceiver, switch port shut or err-disabled, wrong VLAN on a hypervisor port group, or a speed the two ends cannot agree on. `ethtool enp1s0` shows `Link detected: no`.
- **enp2s0**: no `UP` flag at all, so it is administratively down: `ip link set enp2s0 up` for a test, or `nmcli connection up <profile>` (or `netplan apply`) so the configuration manager brings it up properly.
- `LOWER_UP` is the carrier flag; a healthy interface shows `<BROADCAST,MULTICAST,UP,LOWER_UP>` and state `UP`.

The kernel log records every transition, which is how you spot a **flapping** link:

```text
[root@srv01 ~]# journalctl -k -g 'Link is' --no-pager | tail -4
Nov 22 08:14:02 srv01 kernel: e1000e 0000:00:1f.6 enp0s31f6: NIC Link is Down
Nov 22 08:14:05 srv01 kernel: e1000e 0000:00:1f.6 enp0s31f6: NIC Link is Up 1000 Mbps Full Duplex, Flow Control: Rx/Tx
Nov 22 08:16:41 srv01 kernel: e1000e 0000:00:1f.6 enp0s31f6: NIC Link is Down
Nov 22 08:16:44 srv01 kernel: e1000e 0000:00:1f.6 enp0s31f6: NIC Link is Up 1000 Mbps Full Duplex, Flow Control: Rx/Tx
```

The exact wording depends on the driver. Flapping points to the physical layer: cable, optic, switch port, or power management on the NIC.

## Link negotiation issues

```text
[root@srv01 ~]# ethtool enp0s31f6
Settings for enp0s31f6:
	Supported link modes:   10baseT/Half 10baseT/Full
	                        100baseT/Half 100baseT/Full
	                        1000baseT/Full
	Advertised link modes:  Not reported
	Speed: 100Mb/s
	Duplex: Full
	Auto-negotiation: off
	Port: Twisted Pair
	Link detected: yes
```

Classic **duplex mismatch**: someone forced the NIC to 100 Mb/s full duplex (`ethtool -s enp0s31f6 speed 100 duplex full autoneg off`, or a NetworkManager profile with `802-3-ethernet.auto-negotiate no`). If one side is forced and the other autonegotiates, the autonegotiating side can detect the speed but not the duplex and falls back to **half duplex**, so here the switch runs 100/half against the NIC's 100/full. Symptoms: the link is up and pings work, but throughput is terrible under load, and counters rise: late collisions on the half-duplex side, CRC/FCS errors on the full-duplex side. Check `ethtool -S enp0s31f6 | grep -iE 'crc|collision|error'` (counter names depend on the driver) and `ip -s link show enp0s31f6`, and compare with `show interface` on the switch.

Fix: set **both ends to autonegotiate** (required for 1000BASE-T anyway), or force both ends to the same values. Make it persistent in the configuration manager, not just with `ethtool`:

```text
[root@srv01 ~]# nmcli connection modify enp0s31f6 802-3-ethernet.auto-negotiate yes 802-3-ethernet.speed 0 802-3-ethernet.duplex ""
[root@srv01 ~]# nmcli connection up enp0s31f6
```

A gigabit port that negotiates only `100Mb/s` with autonegotiation **on** usually has a damaged cable or a pair fault (1000BASE-T needs all four pairs), so replace the cable before blaming the configuration.

## MTU mismatch

Both ends of a segment must agree on the MTU. A host set to 9000 (jumbo frames) on a switch path that only carries 1500 works for small packets (pings, SSH logins, DNS) and **hangs on large transfers**: an SSH session freezes on `ls -l` of a big directory, HTTPS pages half load, NFS stalls. Across routed paths, Path MTU Discovery relies on ICMP "fragmentation needed" (IPv4) or "packet too big" (IPv6) messages; when a firewall drops them you get a **PMTU black hole** with the same symptoms.

Test with the Don't Fragment bit set. The payload size is MTU − 28 (20-byte IPv4 header + 8-byte ICMP header), so 1472 for 1500 and 8972 for 9000:

```text
[root@srv01 ~]# ping -c2 -M do -s 1472 198.51.100.20
PING 198.51.100.20 (198.51.100.20) 1472(1500) bytes of data.

--- 198.51.100.20 ping statistics ---
2 packets transmitted, 0 received, 100% packet loss, time 1027ms

[root@srv01 ~]# ping -c2 -M do -s 1372 198.51.100.20
PING 198.51.100.20 (198.51.100.20) 1372(1400) bytes of data.
1380 bytes from 198.51.100.20: icmp_seq=1 ttl=61 time=4.12 ms
1380 bytes from 198.51.100.20: icmp_seq=2 ttl=61 time=4.07 ms
```

Full-size packets vanish without any error while 1400-byte packets pass: something on the path has an MTU of about 1400 (a tunnel, for example) and the ICMP that should report it never arrives. If the ICMP does arrive, ping prints `Frag needed and DF set (mtu = 1400)`; if your own interface is smaller than the packet, ping prints `ping: local error: message too long, mtu=1400`. `tracepath 198.51.100.20` reports the `pmtu` at each hop. Fixes: correct the MTU (`nmcli connection modify enp1s0 802-3-ethernet.mtu 1500`, or `mtu:` in Netplan), allow ICMP type 3 code 4 / ICMPv6 type 2 through the firewalls, or clamp the TCP MSS on the tunnel router.

## Bonding

```text
[root@srv01 ~]# cat /proc/net/bonding/bond0
Bonding Mode: IEEE 802.3ad Dynamic link aggregation
Transmit Hash Policy: layer3+4 (1)
MII Status: up
...
Slave Interface: ens1f0
MII Status: up
Speed: 10000 Mbps
Duplex: full
Aggregator ID: 1
...
Slave Interface: ens1f1
MII Status: up
Speed: 10000 Mbps
Duplex: full
Aggregator ID: 2
details partner lacp pdu:
    system mac address: 00:00:00:00:00:00
```

Both members have link, but they are in **different aggregators** and ens1f1's partner system MAC is all zeros: the switch is not sending LACP on that port (port not in the port-channel, or the channel is static `mode on` instead of `active`). Only one link carries traffic. Other bonding faults:

| Symptom | Cause |
|---|---|
| `802.3ad` bond, no LACP partner on any member | Switch side not configured for LACP |
| `balance-rr` (mode 0) or `balance-xor` across two independent switches | Out-of-order packets, MAC flapping on the switches; use `active-backup` (mode 1) or MLAG |
| Failover does not happen when the upstream switch fails but the link stays up | MII monitoring only sees local link; use ARP monitoring (`arp_ip_target`) or LACP |
| One member at 1000 Mb/s, the other at 10000 Mb/s | 802.3ad aggregates only members of equal speed and duplex |

Check with `cat /proc/net/bonding/bond0`, `ip -d link show bond0`, and `nmcli connection show` for the bond and its port profiles. NetworkManager profiles use `bond.options "mode=802.3ad,miimon=100"`.

## MAC spoofing

Changing the MAC address ("spoofing" or cloning) is sometimes deliberate and sometimes accidental, and it breaks things the network ties to MAC addresses:

- DHCP reservations and NAC/802.1X policies stop matching, so the host gets the wrong address or none.
- **Switch port security** sees a new MAC and err-disables or restricts the port.
- Hypervisors and clouds drop frames whose source MAC differs from the vNIC's assigned MAC (VMware "MAC address changes" / "Forged transmits" set to Reject, libvirt `clean-traffic` filters, cloud anti-spoofing). This also breaks bonding modes that change MACs and nested virtualization.

Confirm with `ip link show enp1s0`: when the current MAC differs from the hardware address, iproute2 prints `permaddr <hardware-MAC>` after `link/ether`, and `ethtool -P enp1s0` shows the permanent address. In NetworkManager look for `802-3-ethernet.cloned-mac-address` (`random`, `stable` or a fixed value) and Wi-Fi randomization (`wifi.cloned-mac-address`). Remove the clone, or update the reservation and port-security entry if the change is intentional.

## Subnet misconfiguration and "cannot ping server"

A wrong prefix length is one character in a config file and a confusing outage:

| Host config | Gateway | Effect |
|---|---|---|
| `192.0.2.130/25` (correct) | 192.0.2.129 | Works |
| `192.0.2.130/24` (too short) | 192.0.2.129 | Host thinks 192.0.2.1-.127 are on-link and ARPs for them; ping shows `From 192.0.2.130 icmp_seq=1 Destination Host Unreachable` |
| `192.0.2.130/26` (too long) | 192.0.2.129 | Hosts .192-.255 look remote, so traffic for them goes through the router (it may work, asymmetrically) |
| `192.0.2.130/25` | 192.0.2.1 (wrong) | `ip route add default via 192.0.2.1` gives `Error: Nexthop has invalid gateway.` because the gateway is not on a connected subnet |

`Destination Host Unreachable` coming **from your own address** means ARP failed: nothing answered on the local segment (wrong prefix, wrong VLAN, target down). Work through "cannot ping server" in order: own address (`ip -br addr`), gateway (`ping` it, `ip neigh show` shows `FAILED` or `REACHABLE`), server by IP, server by name. If ping fails but `nc -zv 192.0.2.20 443` or `curl` succeeds, ICMP is just filtered; ping is not a service test.

## IP conflicts

Two hosts with the same IPv4 address produce intermittent failures: connections reset, the other host's SSH key appears (`REMOTE HOST IDENTIFICATION HAS CHANGED`), and the neighbour cache on the router flips between two MACs. Test before using an address with duplicate address detection:

```text
[root@srv02 ~]# arping -D -I enp1s0 -c 2 192.0.2.10
ARPING 192.0.2.10 from 0.0.0.0 enp1s0
Unicast reply from 192.0.2.10 [52:54:00:7E:21:9C]  0.871ms
Sent 1 probes (1 broadcast(s))
Received 1 response(s)
[root@srv02 ~]# echo $?
1
```

In `-D` mode `arping` returns 0 only when nobody answers; a reply shows the MAC of the host already using the address (look it up in the switch MAC table). NetworkManager can do the same check before configuring an address (`ipv4.dad-timeout`). IPv6 has DAD built in: a duplicate is logged and the address is never used:

```text
kernel: IPv6: enp1s0: IPv6 duplicate address 2001:db8:10::10 used by 52:54:00:7e:21:9c detected!
[root@srv02 ~]# ip -6 addr show dev enp1s0 | grep 2001
    inet6 2001:db8:10::10/64 scope global tentative dadfailed
```

## Dual stack issues

On a dual-stack host, applications usually **prefer IPv6** (RFC 6724 address selection, tunable in `/etc/gai.conf`). If a name has an AAAA record but the IPv6 path is broken, clients either fail or wait for a timeout before trying IPv4, so "the site is slow" or "works with the IP, not the name" can be an IPv6 problem.

| Check | Command |
|---|---|
| What the resolver returns, in order | `getent ahosts www.example.com` |
| Test each family | `curl -4 -sI https://www.example.com`, `curl -6 -sI https://www.example.com`, `ping -4` / `ping -6` |
| IPv6 address and route | `ip -6 addr` (only `fe80::` = no global address, no router advertisement or DHCPv6), `ip -6 route` (no `default via fe80::...`) |
| Service bound to one family | `ss -tlnp`: `0.0.0.0:443` only, no `[::]:443` (or `*:443`) |
| Firewall for each family | `iptables` rules do not cover IPv6 (`ip6tables` does); nftables `inet` tables and firewalld cover both |

Fix the IPv6 path, router advertisements or firewall rules; as a temporary workaround prefer IPv4 for address selection with `precedence ::ffff:0:0/96 100` in `/etc/gai.conf`. Disabling IPv6 entirely (`net.ipv6.conf.all.disable_ipv6=1`) hides the problem and can break software that expects `::1`.

## Lab it yourself

1. In the lab VM, run `ip -br link`. To see both fault types without touching the hypervisor, create a veth pair: `ip link add vlab0 type veth peer name vlab1`, then `ip link set vlab0 up` and run `ip -br link` again: `vlab0` is `UP` with `NO-CARRIER` (its peer is down) and `vlab1` has no `UP` flag (administratively down). Remove it with `ip link del vlab0`. Optionally unplug the VM's virtual cable instead (virt-manager: NIC "Link state"; VirtualBox: "Cable Connected"; Hyper-V: set the adapter's virtual switch to "Not connected").
2. Find your path MTU: `ping -M do -s 1472 <gateway>`, then set the interface MTU to 1400 with `ip link set <if> mtu 1400` and repeat to see the local error. Restore it.
3. Install `iputils-arping` (Debian/Ubuntu) or `iputils` (RHEL), and run `arping -D -I <if> -c 2 <your own gateway>` to see a "conflict", then against an unused address.
4. In two lab VMs on an isolated virtual network (an isolated network in libvirt, an internal network in VirtualBox, a private switch in Hyper-V, a host-only network in UTM), configure the same IPv6 address on both and read `ip -6 addr` and `journalctl -k` on the second.
5. Run `getent ahosts` for a dual-stack name and compare `curl -4` with `curl -6`.

## Key takeaways

- `NO-CARRIER` with `UP` = enabled but no link (physical); no `UP` flag = administratively down. Flapping shows as repeated `Link is Down/Up` kernel lines.
- Forced speed/duplex on one side and autonegotiation on the other leads to half duplex, collisions and CRC errors; set both to auto and persist it in NetworkManager or Netplan.
- MTU and PMTU black holes: small packets work, large transfers hang; test with `ping -M do -s <MTU-28>` and `tracepath`.
- Check bonds in `/proc/net/bonding/bond0`: different aggregator IDs or a zero partner MAC mean LACP is not up on the switch.
- Cloned MACs break DHCP reservations, port security and hypervisor anti-spoofing; `permaddr` in `ip link` reveals them.
- Wrong prefix length gives `Destination Host Unreachable` from your own IP; `Nexthop has invalid gateway` means the gateway is off-subnet.
- `arping -D` detects IPv4 conflicts; IPv6 DAD marks duplicates `dadfailed`. Dual-stack faults: test `curl -4`/`-6`, check `ip -6 route`, listeners and IPv6 firewall rules.
