## "Permission denied" has many owners

When a user or service gets `Permission denied`, at least five independent layers can be responsible: classic permissions, ACLs, file attributes, mount options and the mandatory access control system (SELinux on RHEL, AppArmor on Ubuntu). Account problems add more: locked, expired or restricted accounts. Lessons 3.3 and 3.4 taught how each layer works; this lesson is about finding **which** layer said no.

| Layer | Quick check | Tell-tale sign |
|---|---|---|
| Mode and owner | `ls -l`, `namei -l /full/path` | A directory without `x` for that user somewhere on the path |
| ACL | `getfacl file` | `+` after the mode in `ls -l`; `#effective:` lower than the entry |
| Attributes | `lsattr file` | `i` (immutable) or `a` (append only); root also fails, with `Operation not permitted` |
| Mount options | `findmnt -no OPTIONS --target /path` | `noexec` (scripts and binaries cannot run), `ro`, `nosuid` |
| SELinux / AppArmor | `getenforce`, `ausearch -m AVC -ts recent`; `aa-status`, `journalctl -k -g apparmor` | AVC `denied` records; mode bits look correct |

## SELinux issues

When standard permissions look right and the service still gets denied on an enforcing RHEL host, suspect SELinux. The three causes the objective names are **context** (wrong label), **Booleans** (an optional permission turned off) and **policy** (the action is not allowed at all, including non-standard ports).

### Step 1: confirm it is SELinux

```text
[root@web01 ~]# getenforce
Enforcing
[root@web01 ~]# ausearch -m AVC,USER_AVC -ts recent
----
time->Sun Nov 22 10:00:12 2026
type=AVC msg=audit(1795341612.412:1187): avc:  denied  { read } for  pid=2311 comm="httpd" name="index.html" dev="dm-0" ino=3412010 scontext=system_u:system_r:httpd_t:s0 tcontext=unconfined_u:object_r:user_home_t:s0 tclass=file permissive=0
```

How to read an AVC record:

| Field | Here | Meaning |
|---|---|---|
| `denied { read }` | read | The permission that was refused |
| `comm=`, `pid=` | httpd, 2311 | Who tried |
| `name=`, `ino=` | index.html | The target object |
| `scontext` | `httpd_t` | The process's domain |
| `tcontext` | `user_home_t` | The target's type |
| `tclass` | file | Object class (`file`, `dir`, `tcp_socket`...) |
| `permissive=0` | 0 | It was enforced (1 = only logged) |

A quick test is `setenforce 0` (permissive) and retry: if it now works, SELinux was the cause. Turn it straight back on with `setenforce 1`; never fix a problem by disabling SELinux. To relax only one domain while you investigate, `semanage permissive -a httpd_t`.

### Step 2: let the tools explain it

```text
[root@web01 ~]# ausearch -m AVC -ts recent | audit2why
...
	Was caused by:
	The boolean httpd_read_user_content was set incorrectly.
	Description:
	Allow httpd to read user content

	Allow access by executing:
	# setsebool -P httpd_read_user_content 1
```

`audit2why` translates each denial into a cause: a Boolean that is off (it prints the `setsebool` command), a missing allow rule ("Missing type enforcement (TE) allow rule"), or a constraint violation. `sealert -a /var/log/audit/audit.log` (package `setroubleshoot-server`) gives longer advice including `restorecon` and `semanage` suggestions; with setroubleshootd running, a summary also appears in the journal (`journalctl -t setroubleshoot`).

Read the suggestion critically. `httpd_read_user_content` would let Apache read files in **every** user's home directory, and a custom policy module for `httpd_t` reading `user_home_t` would do the same. Neither is the fix here. The file carries the wrong label because it was created in a home directory and **moved** (`mv` keeps the label; `cp` creates a new file with the destination's label).

### Step 3: apply the right fix

| Cause | Typical AVC | Fix |
|---|---|---|
| **Wrong context** in a standard path | `tcontext=...user_home_t` or `tmp_t` on files under `/var/www/html` | `restorecon -Rv /var/www/html` |
| **Non-default path** | Content in `/srv/web` labelled `var_t` | `semanage fcontext -a -t httpd_sys_content_t "/srv/web(/.*)?"` then `restorecon -Rv /srv/web` |
| **Boolean** off | `httpd_t` `name_connect` to `postgresql_port_t`; audit2why names `httpd_can_network_connect_db` | `setsebool -P httpd_can_network_connect_db on` |
| **Port** not labelled | `denied { name_bind } ... src=8090 ... tcontext=...unreserved_port_t` | `semanage port -a -t http_port_t -p tcp 8090` |
| Genuinely new behaviour | Custom application doing something no Boolean covers | `audit2allow -a -M myapp` and review `myapp.te`, then `semodule -i myapp.pp` (last resort) |

`chcon -t httpd_sys_content_t file` changes a label too, but a relabel or `restorecon` reverts it, so use `semanage fcontext` for anything permanent. `getsebool -a | grep httpd` and `semanage boolean -l` list Booleans with descriptions; `-P` makes a Boolean change survive reboots. If no AVC appears but SELinux is still suspected, the denial may be hidden by a `dontaudit` rule: `semodule -DB` disables those temporarily, `semodule -B` restores them.

Labels also break after restoring files from backup without `--selinux`/`--xattrs`, or after running with SELinux disabled: `touch /.autorelabel` and reboot to relabel everything.

> **Real world:** On Ubuntu the equivalent layer is **AppArmor**. Denials appear as `apparmor="DENIED" operation="open" profile="/usr/sbin/mysqld" name="/data/mysql/..."` in the kernel log; fix the profile (or a local include under `/etc/apparmor.d/local/`), reload it with `apparmor_parser -r`, or test with `aa-complain`.

## File and directory permission issues

### Path traversal

Every directory on the path needs execute (`x`) permission for the user. `namei -l` shows the whole chain in one go:

```text
[root@srv01 ~]# sudo -u bob cat /srv/reports/q4/summary.txt
cat: /srv/reports/q4/summary.txt: Permission denied
[root@srv01 ~]# namei -l /srv/reports/q4/summary.txt
f: /srv/reports/q4/summary.txt
dr-xr-xr-x root    root     /
drwxr-xr-x root    root     srv
drwxr-x--- alice   finance  reports
drwxrwsr-x alice   finance  q4
-rw-rw-r-- alice   finance  summary.txt
```

The file is world-readable, but `reports` gives "other" no access at all, so bob (not in `finance`) cannot pass. Either add bob to the group (`usermod -aG finance bob`, then a new login, because group membership is read at login) or grant access with an ACL.

### ACLs and the mask

```text
[root@srv01 ~]# getfacl /srv/reports/q4/summary.txt
# file: srv/reports/q4/summary.txt
# owner: alice
# group: finance
user::rw-
user:bob:rw-			#effective:r--
group::rw-			#effective:r--
mask::r--
other::r--
```

bob has an ACL entry with `rw-`, but the **mask** limits named users and groups to `r--`, so bob cannot write. The mask is recalculated by `setfacl` and **changed by `chmod`'s group bits** on a file that has ACLs: someone ran `chmod 644` (or `chmod g-w`), which set the mask to `r--`. Fix with `setfacl -m m::rw file` (or `chmod g+w`). For new files in a directory, set default ACLs: `setfacl -d -m u:bob:rwX /srv/reports/q4`. Also remember the `+` in `ls -l` output is the only visual hint that an ACL exists.

### Attributes

```text
[root@srv01 ~]# echo "nameserver 192.0.2.53" > /etc/resolv.conf
-bash: /etc/resolv.conf: Operation not permitted
[root@srv01 ~]# lsattr /etc/resolv.conf
----i---------e------- /etc/resolv.conf
```

The immutable flag blocks writes, deletes, renames and new hard links, even for root. Someone set it to stop a manager from overwriting the file; remove it with `chattr -i` and fix the real conflict (NetworkManager or systemd-resolved configuration). The `a` flag allows only appending (`>>` works, `>` fails), a common setting for log files.

### Other permission traps

- **noexec mounts**: `./install.sh` in `/tmp` fails with `Permission denied` although the file is `rwx`; `bash install.sh` works because the script is then only read. Check `findmnt -no OPTIONS --target /tmp`.
- **umask**: files created by a service are `600` when the service runs with `UMask=0077`; collaborators cannot read them. Set `UMask=` in the unit or the setgid bit plus default ACLs on the shared directory.
- **Ownership after restore or migration**: UIDs differ between hosts, so files show a number or the wrong user. Compare `id alice` on both hosts and `chown -R` accordingly.

## Account access

| Symptom | Confirm | Fix |
|---|---|---|
| Password rejected although correct; account locked | `passwd -S alice` shows `LK` (RHEL) or `L` (Debian); `usermod -L` puts `!` before the hash in `/etc/shadow` | `passwd -u alice` / `usermod -U alice` |
| Locked after failed attempts | `faillock --user alice` lists the failures | `faillock --user alice --reset` (`pam_faillock`; the older `pam_tally2 --reset` is gone from current Linux-PAM) |
| "Your account has expired" | `chage -l alice` shows `Account expires` in the past | `chage -E -1 alice` (or a new date) |
| Forced to change password | `chage -l alice`: password expired, or `chage -d 0` was used | User changes it; adjust `-M` if the policy is wrong |
| "This account is currently not available." | `getent passwd alice` shows `/sbin/nologin` (or `/usr/sbin/nologin`) | `usermod -s /bin/bash alice` if the user should log in |
| SSH rejects only some users | `journalctl -u sshd` (`ssh` on Ubuntu): `User alice from 192.0.2.50 not allowed because not listed in AllowUsers` | Edit `AllowUsers`/`AllowGroups`, `sshd -t`, reload |
| Only root can log in | `/etc/nologin` or `/run/nologin` exists (`shutdown` with a time creates `/run/nologin` 5 minutes before; admins create `/etc/nologin` for maintenance) | Remove it, or cancel the shutdown (`shutdown -c`) |
| "Could not chdir to home directory" | Home missing or wrong owner | Create with `mkhomedir_helper alice` or fix owner |
| Directory user unknown | `getent passwd alice` empty, `id alice: no such user` | SSSD/realm: `sssctl domain-status example.com`, `sssctl user-checks alice`, time sync for Kerberos |
| sudo refused | `alice is not in the sudoers file` | Add to `wheel` (RHEL) or `sudo` (Debian/Ubuntu), check `/etc/sudoers.d` with `visudo -c` |

`/var/log/secure` (RHEL) or `/var/log/auth.log` (Debian/Ubuntu), or `journalctl _COMM=sshd` and `journalctl -t sudo`, give the reason the PAM stack refused. Restricted shells (`/bin/rbash`) and `pam_access` rules in `/etc/security/access.conf` are further places a login can be refused on purpose.

## Lab it yourself

1. In a RHEL-family VM: install `httpd`, create `~/index.html`, `mv` it to `/var/www/html/`, request it with `curl localhost`, then read `ausearch -m AVC -ts recent`, run `audit2why`, and fix with `restorecon -v`.
2. Configure `Listen 8090` in httpd, see the `name_bind` denial at start, and fix it with `semanage port -a -t http_port_t -p tcp 8090`.
3. Create `/srv/reports/q4` with mode `750` on `/srv/reports`, test as another user, then inspect with `namei -l`.
4. `setfacl -m u:bob:rw` a file, run `chmod 644` on it, and compare `getfacl` before and after.
5. `chattr +i` a test file, try to delete it as root, read `lsattr`, and remove the flag.
6. Lock a test account with `usermod -L`, check `passwd -S`, then cause `faillock` entries with wrong SSH passwords and reset them.

## Key takeaways

- Find which layer refused: mode and path (`namei -l`), ACL (`getfacl`, mask), attributes (`lsattr`), mount options (`findmnt`), then SELinux or AppArmor.
- SELinux workflow: `getenforce`, `ausearch -m AVC -ts recent`, `audit2why` or `sealert`, then fix the label (`restorecon`, `semanage fcontext`), Boolean (`setsebool -P`) or port (`semanage port -a`); `audit2allow` only for genuinely new behaviour.
- `mv` keeps SELinux labels and `cp` does not; `chcon` changes do not survive a relabel.
- `chmod` on a file with ACLs changes the mask and can silently reduce named entries; check `#effective:`.
- Immutable files refuse changes even from root with `Operation not permitted`.
- Account lockouts: `passwd -S`, `faillock --user`, `chage -l`, the login shell, sshd `AllowUsers`/`AllowGroups`, `/etc/nologin`, and the auth log.
