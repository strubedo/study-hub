## Storage, packages and processes: the everyday failures

The host boots, but something on it is broken: a filesystem will not mount or will not accept writes, a package will not install, a command is "not found", a unit fails, or a process crashes or hangs. Lessons 1.3 (storage), 2.3 (processes), 2.4 (packages) and 2.5 (systemd) taught the tools; this lesson is about reading the error and picking the right one.

## Filesystem will not mount

Read the error from `mount`, then the kernel log, which usually has the real reason:

```text
[root@srv01 ~]# mount /data
mount: /data: wrong fs type, bad option, bad superblock on /dev/sdb1, missing codepage or helper program, or other error.
       dmesg(1) may have more information after failed mount system call.
[root@srv01 ~]# dmesg | tail -2
[ 9123.004211] XFS (sdb1): Corruption warning: Metadata has LSN (1:4211) ahead of current LSN (1:3906).
[ 9123.004398] XFS (sdb1): log mount/recovery failed: error -117
```

| Cause | Confirm | Fix |
|---|---|---|
| Wrong device name or UUID in `/etc/fstab` | `blkid`, `lsblk -f`; `findmnt --verify` | Use the right `UUID=`; device names such as `/dev/sdb` can change between boots |
| Wrong filesystem type or missing helper | `blkid` shows `TYPE="xfs"` but fstab says `ext4`; NFS/CIFS needs `nfs-utils` / `cifs-utils` | Correct the type, install the helper |
| Bad mount option | `dmesg`: `unknown parameter` | Fix the option list |
| Already mounted or mount point missing | `findmnt /data`; `mount point does not exist` | `mkdir`, or unmount first |
| Filesystem damaged | `dmesg` shows corruption | Unmount, check and repair (below) |
| Network filesystem | Server unreachable, `_netdev` missing | Lesson 5.3; add `_netdev,nofail` |

After editing `/etc/fstab`, run `systemctl daemon-reload` (systemd generates mount units from it) and `mount -a` or `findmnt --verify` before rebooting. A bad fstab line is the classic reason a server stops in **emergency mode**; `nofail` lets boot continue when a non-essential filesystem is missing.

### Checking and repairing

Never repair a mounted filesystem. ext4 uses `e2fsck` (the same as `fsck` with an ext4 type); XFS uses **`xfs_repair`** (its `fsck.xfs` does nothing on purpose). Both have a read-only "tell me" mode first. Here are real runs against a scratch image whose primary superblock was overwritten:

```text
root@srv01:~# e2fsck -n /dev/vg_data/lv_app
e2fsck 1.47.4 (6-Mar-2025)
ext2fs_open2: Bad magic number in super-block
e2fsck: Superblock invalid, trying backup blocks...
...
/dev/vg_data/lv_app: ********** WARNING: Filesystem still has errors **********
root@srv01:~# echo $?
4

root@srv01:~# xfs_repair -n /dev/vg_data/lv_db
Phase 1 - find and verify superblock...
bad primary superblock - bad magic number !!!

attempting to find secondary superblock...
.found candidate secondary superblock...
verified secondary superblock...
would write modified primary superblock
Primary superblock would have been modified.
Cannot proceed further in no_modify mode.
Exiting now.
```

Exit status 4 from `e2fsck` means "errors left uncorrected" (it was run with `-n`); run `e2fsck -f` (or `-y` to answer yes to everything) to fix. `xfs_repair` without `-n` performs the repair; if it refuses because the log is dirty, mount and unmount the filesystem once to replay the log, and use `xfs_repair -L` (zero the log, losing recent metadata changes) only as a last resort. For the root filesystem, boot rescue media or use `fsck.mode=force` on the kernel command line.

## Partition not writable

`Read-only file system` and `Permission denied` look similar to users but are different problems.

| Error | Cause | Confirm | Fix |
|---|---|---|---|
| `Read-only file system` | Mounted `ro`, or the kernel remounted it read-only after errors | `findmnt -no OPTIONS /data`; `dmesg` shows `EXT4-fs error ...` and `Remounting filesystem read-only` | Find the cause (disk, corruption), unmount, `e2fsck`, remount; `mount -o remount,rw /data` only when it was mounted `ro` on purpose |
| `No space left on device` | Blocks **or inodes** exhausted | `df -h`, `df -i` | Below |
| `Disk quota exceeded` | User or group quota | `quota -s`, `repquota -a` | Below |
| `Permission denied` | Mode, owner, ACL, SELinux | `ls -l`, `namei -l`, `getfacl`, `ls -Z` | Lesson 5.4 |
| `Operation not permitted` (even root) | Immutable attribute | `lsattr` shows `i` | `chattr -i` (lesson 3.3) |

## OS filesystem full

```text
[root@srv01 ~]# df -h /var
Filesystem               Size  Used Avail Use% Mounted on
/dev/mapper/vg_sys-var    20G   20G   20K 100% /var
[root@srv01 ~]# du -xh --max-depth=1 /var | sort -h | tail -3
1.1G	/var/cache
18G	/var/log
20G	/var
```

`-x` keeps `du` on one filesystem. Find big directories with `du`, big files with `find /var -xdev -size +500M -ls`. Usual culprits: logs (`journalctl --disk-usage`, `journalctl --vacuum-size=500M`, logrotate from lesson 3.1), package caches (`dnf clean all`, `apt clean`), core dumps, container images (`podman system prune`, `docker system prune`).

When **`df` says full but `du` adds up to much less**, a process still holds a **deleted file** open. Its blocks are not freed until the last file descriptor closes. Reproduced in a container: a 150 MB log was deleted while a process kept it open for writing:

```text
root@srv01:~# df -h /data
Filesystem      Size  Used Avail Use% Mounted on
tmpfs           200M  150M   50M  75% /data
root@srv01:~# du -sh /data
0	/data
root@srv01:~# lsof +L1
COMMAND PID USER FD   TYPE DEVICE  SIZE/OFF NLINK NODE NAME
sleep   185 root 1w   REG  0,116 157286400     0    2 /data/app.log (deleted)
```

`lsof +L1` lists open files with a link count below 1. Restart the process (or `systemctl restart` its service) to release the space; in an emergency truncate it through `/proc`: `: > /proc/185/fd/1`. Prevention: rotate logs with `copytruncate` or send the service a HUP so it reopens its log, never just `rm` an open log.

Also remember the reserved blocks on ext4 (5% for root by default, `tune2fs -m 1` to reduce) explain why `Avail` can be lower than `Size - Used`.

## Inode exhaustion

Every file needs an inode (lesson 1.3). Millions of tiny files (session files, mail queues, cache shards) can use them all while blocks are free. Reproduced on a tmpfs created with only 64 inodes:

```text
root@srv01:~# touch /data/f64
touch: cannot touch '/data/f64': No space left on device
root@srv01:~# df -h /data
Filesystem      Size  Used Avail Use% Mounted on
tmpfs            20M     0   20M   0% /data
root@srv01:~# df -i /data
Filesystem     Inodes IUsed IFree IUse% Mounted on
tmpfs              64    64     0  100% /data
```

Same error text as a full disk, so always run both `df -h` and `df -i`. Find the directory with the most files: `du --inodes -x / | sort -n | tail` or `find /var -xdev -type f | cut -d/ -f2-4 | sort | uniq -c | sort -n | tail`. Delete or archive the files. ext4's inode count is fixed when the filesystem is made (`mkfs.ext4 -i` / `-N` sets it); XFS allocates inodes dynamically up to `imaxpct`, so it rarely runs out.

## Quota issues

```text
alice@srv01:~$ cp build.tar /home/alice/
cp: error writing '/home/alice/build.tar': Disk quota exceeded
alice@srv01:~$ quota -s
Disk quotas for user alice (uid 1001):
     Filesystem   space   quota   limit   grace   files   quota   limit   grace
/dev/mapper/vg_sys-home
                  5120M*  4096M   5120M   6days    1834       0       0
```

The `*` marks the exceeded limit. Above the **soft** quota (4096M) the user has a grace period; at the **hard** limit (5120M) writes fail immediately, and when grace expires the soft limit is enforced as hard. Administrators use `repquota -as` (ext4 with quota tools), `xfs_quota -x -c 'report -h' /home` on XFS, and change limits with `edquota alice`, `setquota` or `xfs_quota -x -c 'limit bsoft=4g bhard=5g alice' /home`. If quotas seem not to apply, check the mount options (`usrquota`/`grpquota`, or `uquota` for XFS) and that quota is on (`quotaon -p /home`).

## Package dependency issues

Low-level tools refuse to break dependencies; high-level tools try to resolve them from repositories. Real output from Rocky Linux 9 with a package that needs a library no repository provides:

```text
[root@srv01 ~]# rpm -ivh acme-agent-2.4.1-1.el9.noarch.rpm
error: Failed dependencies:
	libacme-client >= 3.0 is needed by acme-agent-2.4.1-1.el9.noarch
[root@srv01 ~]# dnf install ./acme-agent-2.4.1-1.el9.noarch.rpm
Error:
 Problem: conflicting requests
  - nothing provides libacme-client >= 3.0 needed by acme-agent-2.4.1-1.el9.noarch from @commandline
(try to add '--skip-broken' to skip uninstallable packages or '--nobest' to use not only best candidate packages)
```

And on Debian 13:

```text
root@srv01:~# dpkg -i acme-agent_2.4.1_all.deb
...
dpkg: dependency problems prevent configuration of acme-agent:
 acme-agent depends on libacme-client (>= 3.0); however:
  Package libacme-client is not installed.

dpkg: error processing package acme-agent (--install):
 dependency problems - leaving unconfigured
root@srv01:~# dpkg -l acme-agent | tail -1
iU  acme-agent     2.4.1        all          test
```

`iU` = selected for install, unpacked but not configured. `apt-get install -f` ("fix broken") either installs the missing dependencies or, as here where none exists, removes the half-installed package. Fixes: enable the repository that provides the dependency (EPEL, CRB/PowerTools, a vendor repo), install a version built for your release, or use `dnf provides libacme-client` / `apt-cache policy` to see what is available. Version conflicts after mixing repositories are solved by removing the third-party package, using `dnf distro-sync`, or pinning (exclusions from lesson 2.4). Avoid `rpm -i --nodeps` and `dpkg --force-depends`: they leave the package database inconsistent.

## PATH misconfiguration

Real messages from bash:

```text
$ PATH=/usr/local/bin
$ ls
bash: ls: command not found                    # exit status 127

$ # another shell, normal PATH; backup.sh was run from /usr/local/bin, then moved to /usr/bin
$ backup.sh
bash: /usr/local/bin/backup.sh: No such file or directory
$ type backup.sh
backup.sh is hashed (/usr/local/bin/backup.sh)
$ hash -r; backup.sh                            # now found in /usr/bin
```

`command not found` (status 127) means no directory in `$PATH` has the command: check `echo $PATH`, `type -a cmd`, `which cmd`, and where the variable is set (`~/.bash_profile`, `~/.bashrc`, `/etc/profile.d/*.sh`, lesson 1.5). A typical mistake is `PATH=/opt/app/bin` instead of `PATH=$PATH:/opt/app/bin`. The second message is bash's **hash table** remembering an old location after a binary moved; `hash -r` clears it (so does any assignment to `PATH`, which is why the two problems are shown in separate shells). Cron jobs and systemd units do **not** read your shell profile: cron uses a minimal PATH (often `/usr/bin:/bin`), so use full paths or set `PATH=` in the crontab, and systemd `ExecStart=` should use absolute paths. `sudo` replaces PATH with `secure_path` from `/etc/sudoers`.

## Systemd unit failures

Start with status, then the unit's journal:

```text
[root@srv01 ~]# systemctl --failed
  UNIT            LOAD   ACTIVE SUB    DESCRIPTION
● reportd.service loaded failed failed Nightly report generator
[root@srv01 ~]# systemctl status reportd.service
× reportd.service - Nightly report generator
     Loaded: loaded (/etc/systemd/system/reportd.service; enabled; preset: disabled)
     Active: failed (Result: exit-code) since Sun 2026-11-22 02:00:03 UTC; 7h ago
    Process: 4120 ExecStart=/opt/report/bin/reportd (code=exited, status=203/EXEC)
   Main PID: 4120 (code=exited, status=203/EXEC)
[root@srv01 ~]# journalctl -u reportd.service -b --no-pager -n 20
```

| Status / message | Meaning |
|---|---|
| `status=203/EXEC` | `ExecStart` binary missing, not executable, wrong path, or bad shebang |
| `status=217/USER` | `User=` names an account that does not exist |
| `status=200/CHDIR` | `WorkingDirectory=` missing |
| `status=1/FAILURE` (any normal code) | The program itself exited with that code; read its log lines |
| `Result: timeout`, `start operation timed out. Terminating.` | Did not finish starting within `TimeoutStartSec=` (often `Type=forking` / `notify` mismatch) |
| `Start request repeated too quickly` / `Result: start-limit-hit` | Crashed repeatedly; fix the cause, then `systemctl reset-failed unit` |
| `code=killed, status=9/KILL` | Killed with SIGKILL (OOM killer, `systemd-oomd`, `MemoryMax=`, or an admin) |
| `code=dumped, status=11/SEGV` | Crashed with a segmentation fault |
| `Unit ... not found` / `bad-setting` | Typo in the name or a syntax error: `systemd-analyze verify unit.service` |

After editing a unit file run `systemctl daemon-reload`; use `systemctl edit unit` for drop-ins (lesson 2.5). `systemctl cat unit` shows what systemd actually loaded, including drop-ins.

## Segmentation faults, killed processes, hangs and leaks

A shell reports a process killed by a signal as exit status **128 + signal number**. Real runs:

```text
bash: line 4:    75 Segmentation fault      (core dumped) sh -c "kill -SEGV \$\$"
segv exit=139                     # 128 + 11 (SIGSEGV)
bash: line 5:    76 Killed                  sh -c "kill -KILL \$\$"
kill exit=137                     # 128 + 9  (SIGKILL)
term exit=143                     # 128 + 15 (SIGTERM)
```

**Segmentation fault**: the program touched memory it may not. The kernel logs a line like `myapp[4211]: segfault at 0 ip ... error 4 in libfoo.so...`, and with `systemd-coredump` the core is kept: `coredumpctl list`, `coredumpctl info 4211`, `coredumpctl debug` (gdb). Causes: application bugs, mismatched libraries after a partial update (`rpm -Va`, `ldd ./myapp`), bad RAM if many unrelated programs crash. Report to the vendor with the core and versions.

**Killed processes**: exit 137 or `Killed` with no explanation is usually the **OOM killer**. Real kernel lines from a container limited to 64 MB:

```text
kernel: python3 invoked oom-killer: gfp_mask=0xcc0(GFP_KERNEL), order=0, oom_score_adj=0
kernel: Memory cgroup out of memory: Killed process 1897990 (python3) total-vm:72524kB, anon-rss:64976kB, file-rss:4620kB, shmem-rss:0kB, UID:0 pgtables:180kB oom_score_adj:0
```

A system-wide OOM says `Out of memory: Killed process ...` instead of `Memory cgroup out of memory`. Search with `journalctl -k -g 'killed process'` or `dmesg -T | grep -i oom`. Also check **`systemd-oomd`** (default on Fedora and Ubuntu desktops), which kills whole cgroups earlier, based on memory pressure (PSI) and swap use, and logs in `journalctl -u systemd-oomd`; `oomctl` shows what it monitors. Lesson 5.5 covers sizing and limits.

**Unresponsive process**: check its state with `ps -o pid,stat,wchan:20,cmd -p <pid>`. `R` using 100% CPU is a busy loop: `strace -p` / `perf top` then TERM it. `S` waiting on a lock or socket: `strace -p` shows the blocked syscall, `ls -l /proc/<pid>/fd` or `lsof -p` shows what it waits on. `D` (uninterruptible) usually cannot be killed, not even with SIGKILL, until the I/O returns: fix the storage or NFS server underneath (NFS waits are the exception: since kernel 2.6.25 SIGKILL, and only SIGKILL, can interrupt a pending NFS operation); the kernel logs `task ... blocked for more than 120 seconds`. `Z` (zombie) is already dead; its parent must reap it (lesson 2.3). Always try `kill -15` before `kill -9`.

**Memory leaks**: resident memory (RSS) grows steadily under constant load and never returns. Watch it with `ps -o pid,rss,cmd -p <pid>` or `pidstat -r -p <pid> 60` over hours, or `systemctl status` (`Memory:` line) for a service. Short-term: cap it with `MemoryMax=` / `MemoryHigh=` in the unit and schedule restarts; long-term: the developer fixes it (valgrind, heap profilers).

## Lab it yourself

1. In the lab VM, with Docker (or Podman, same options) installed, start a container: `docker run --rm -it --tmpfs /data:size=20m,nr_inodes=64 debian:13 bash`, then `touch /data/f{1..100}` and compare `df -h /data` with `df -i /data`.
2. In the same kind of container in the lab VM, install `lsof`, write a big file, keep it open with `sleep 600 >> /data/big &`, delete it, and compare `df`, `du` and `lsof +L1`; then `kill %1` and check `df` again.
3. In the lab VM, create `truncate -s 64M lab.img; mkfs.ext4 lab.img`, overwrite the first superblock with `dd if=/dev/zero of=lab.img bs=1k seek=1 count=1 conv=notrunc`, and run `e2fsck -n lab.img` then `e2fsck -fy lab.img`.
4. In a VM, write a unit with `ExecStart=/opt/none/app`, start it, and read the `203/EXEC` status; add `User=nosuch` and see `217/USER`.
5. In the lab VM, run `sh -c 'kill -SEGV $$'; echo $?` and `sh -c 'kill -KILL $$'; echo $?`.

## Key takeaways

- A mount failure's real reason is in `dmesg`; check UUIDs and types with `blkid`, test fstab with `findmnt --verify` and `mount -a`, use `nofail` for optional filesystems.
- Repair only unmounted filesystems: `e2fsck` for ext4, `xfs_repair` for XFS, both with `-n` first.
- `Read-only file system` after errors means the kernel protected the data: fix the disk or filesystem, do not just remount rw.
- "No space left on device" can be blocks (`df -h`) or inodes (`df -i`); `df` higher than `du` means deleted-but-open files (`lsof +L1`).
- Soft quotas have a grace period, hard limits fail immediately: `quota`, `repquota`, `xfs_quota`.
- `rpm`/`dpkg` report missing dependencies; `dnf`/`apt` resolve from repositories; `apt-get install -f` fixes half-installed packages.
- Exit 127 = command not found (PATH), 137 = SIGKILL (often OOM), 139 = SIGSEGV, 143 = SIGTERM; 203/EXEC and 217/USER are systemd's own exit codes.
