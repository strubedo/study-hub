## Why monitoring comes first in troubleshooting

Every other topic in this domain starts with a symptom. Monitoring is how you learn about the symptom before users do, and how you prove afterwards that the fix worked. Monitoring covers three things: **what you promise** (service levels), **how you collect data** (polling, agents, traps, logs, webhooks), and **what you do with it** (thresholds, alerts, notifications).

## Service levels: SLA, SLO and SLI

| Term | What it is | Example for an internal web portal on web01 |
|---|---|---|
| **SLI** (service level indicator) | A measured number that describes the service as users see it | Share of HTTP requests answered with a non-5xx status in under 300 ms |
| **SLO** (service level objective) | The internal target for an SLI over a window | 99.9% of requests good over 30 days |
| **SLA** (service level agreement) | The contract with customers, with consequences (credits, penalties) when missed | 99.5% monthly availability or a 10% service credit |

The SLO is stricter than the SLA so that the team reacts before the contract is breached. The gap between 100% and the SLO is the **error budget**: at 99.9% over 30 days that is about 43 minutes (30 × 24 × 60 × 0.001 = 43.2) of bad time. If the budget is used up, risky changes stop until reliability recovers.

Good SLIs measure what users feel (availability, latency, error rate, throughput) at the edge of the service, not internal details such as CPU percentage. CPU, memory and disk are still collected, but as **diagnostic metrics** that explain why an SLI moved.

> **Exam tip:** SLI = the measurement, SLO = the goal for that measurement, SLA = the agreement with a penalty. If a question mentions credits or a contract, it is the SLA.

## Data acquisition

### SNMP: polling, traps and MIBs

SNMP is the protocol you already use on switches and routers, and Linux speaks it through **Net-SNMP** (`snmpd` agent, `snmpwalk`/`snmpget` tools, `snmptrapd` receiver; packages `net-snmp` and `net-snmp-utils` on RHEL, `snmpd` and `snmp` on Debian/Ubuntu).

- **Polling:** the manager (NMS) sends GET/GETNEXT/GETBULK requests to the agent on **UDP 161** on a schedule.
- **Traps:** the agent sends an unsolicited message to the manager on **UDP 162** when something happens (link down, reboot). A trap is fire-and-forget; an **inform** is the acknowledged version (v2c and v3).
- **MIB** (Management Information Base): the schema that names the objects. Each object has an **OID**, for example `1.3.6.1.2.1.1.3.0` is `SNMPv2-MIB::sysUpTime.0`, and `IF-MIB::ifOperStatus` reports interface state. Without the MIB file the manager shows bare numeric OIDs.
- **Versions:** v1 and v2c authenticate with a clear-text **community string**; **v3** adds users with authentication and encryption (`authPriv`). Use v3, or at minimum a read-only community limited to the NMS address.

```text
# /etc/snmp/snmpd.conf (excerpt)
agentaddress  udp:161
rouser        nmsuser priv
trap2sink     192.0.2.50 Tr4pC0mm
```

```text
alice@nms01:~$ snmpget -v3 -l authPriv -u nmsuser -a SHA -A 'AuthPass#1' -x AES -X 'PrivPass#1' srv01 SNMPv2-MIB::sysUpTime.0
SNMPv2-MIB::sysUpTime.0 = Timeticks: (111628800) 12 days, 22:04:48.00
```

When polling fails, check the same things as on any network device: is `snmpd` running (`systemctl status snmpd`), is it listening on the right address (`ss -ulnp | grep 161`), is UDP 161 allowed by firewalld or ufw, and do the version, user and passphrases match.

### Agent vs agentless

| | Agent-based | Agentless |
|---|---|---|
| How | Software on the host collects and sends or exposes data (Zabbix agent, Prometheus `node_exporter`, Elastic Agent, Datadog agent) | The monitoring server reaches in with a standard protocol (SNMP, SSH commands, WMI, ICMP ping, HTTP checks, IPMI) |
| Pros | Rich data (per-process, logs, application metrics), works behind NAT when it pushes | Nothing to install or patch on the target; works on appliances |
| Cons | Software to deploy, update and secure on every host | Less detail, credentials stored centrally, more polling load |

The same split appears in automation (lesson 4.1: Ansible is agentless, Puppet uses agents). Collection is either **pull** (Prometheus scrapes `http://srv01:9100/metrics`) or **push** (an agent sends to the server).

### Webhooks

A **webhook** is an HTTP POST, usually with a JSON body, sent to a URL when an event happens. Monitoring tools use outgoing webhooks to notify chat systems (Slack, Teams, Mattermost), paging services (PagerDuty, Opsgenie) or an automation endpoint that runs a remediation job. Many systems also accept incoming webhooks, for example a CI pipeline posting a "deployment started" event so it appears on the graphs.

```text
alice@srv01:~$ curl -s -X POST -H 'Content-Type: application/json' \
  -d '{"text":"web01: disk / at 91% (threshold 90%)"}' \
  https://chat.example.com/hooks/T0EXAMPLE
```

Protect webhook URLs like passwords: whoever knows the URL can post.

### Health checks

A **health check** is a periodic test that a service actually works, not just that the process exists:

- **Load balancer checks** (HAProxy, Nginx, cloud load balancers) request `/healthz` and remove a backend that fails a set number of times in a row.
- **Container health checks**: a Dockerfile `HEALTHCHECK CMD curl -f http://localhost:8080/healthz || exit 1` makes `docker ps` show `(healthy)` or `(unhealthy)`; Kubernetes uses liveness and readiness probes (lesson 4.1, Automation 3).
- **systemd**: `Restart=on-failure` restarts crashed services, and `WatchdogSec=` restarts a service that stops sending keepalives (lesson 2.5).
- **Synthetic checks** from outside: an HTTP GET, a TLS handshake (which also catches certificate expiry, lesson 5.4), a DNS query.

A good health endpoint checks its dependencies (database reachable, disk writable) but responds quickly; a check that times out is itself a symptom.

### Log aggregation

Logs on the host that crashed are hard to read during the outage and easy for an intruder to erase. **Log aggregation** ships them to a central system where they can be searched and correlated across hosts:

- **rsyslog** forwarding (lesson 3.1): `*.* @@logs01.example.com:514` sends everything over TCP (`@` = UDP); RELP or TLS for reliable, encrypted delivery.
- **systemd-journal-remote / journal-upload** for journald.
- Central stacks: Elasticsearch/OpenSearch with Kibana (ELK), Grafana Loki, Graylog, Splunk, fed by agents such as Filebeat, Fluent Bit or Promtail.

Synchronized clocks (chrony, lesson 2.4) are essential: correlating events across hosts is impossible if timestamps differ by minutes.

## Configurations: thresholds, events, alerts, notifications, logging

| Term | Meaning |
|---|---|
| **Event** | Something that happened and was recorded: a service restart, a login, a trap, a metric crossing a line |
| **Threshold** | The value that turns a metric into a problem: warning at 80% disk, critical at 90% |
| **Alert** | A condition that needs attention, raised when a threshold is crossed (often only if it stays crossed for a set time) |
| **Notification** | Delivery of an alert to a person or system: e-mail, SMS, chat webhook, pager |
| **Logging** | Recording events and alert history for later analysis and audit |

Not every event is an alert, and not every alert should page someone. Good configuration:

- **Duration conditions** stop flapping: "load above 2 × CPU count for 10 minutes", not "load above 8 once".
- **Warning and critical levels** with different routes: warning to a ticket or chat channel, critical to the on-call pager.
- **Hysteresis**: clear the alert at a lower value than the one that raised it.
- **Rate-of-change** thresholds catch a disk that will be full in four hours even though it is only at 70% now.
- **Baselines** (lesson 5.5): a threshold that is normal for one host may be an incident on another.
- **Alert fatigue** is the main failure mode: if most alerts are noise, real ones are ignored. Every alert should be actionable.

A Prometheus alerting rule shows the pieces in one place:

```yaml
groups:
  - name: node
    rules:
      - alert: RootFilesystemAlmostFull
        expr: (1 - node_filesystem_avail_bytes{mountpoint="/"} / node_filesystem_size_bytes{mountpoint="/"}) * 100 > 90
        for: 10m
        labels:
          severity: critical
        annotations:
          summary: "{{ $labels.instance }}: / is above 90% for 10 minutes"
```

`expr` is the threshold, `for` the duration, `severity` drives routing in Alertmanager, which sends the notification (e-mail, webhook, PagerDuty).

## Lab it yourself

1. In a throwaway VM, install Net-SNMP (`dnf install net-snmp net-snmp-utils` or `apt install snmpd snmp`), set `rocommunity labonly 127.0.0.1` in `/etc/snmp/snmpd.conf`, restart `snmpd`, and run `snmpwalk -v2c -c labonly 127.0.0.1 SNMPv2-MIB::system`. Then try a wrong community and note the timeout (an agent does not answer bad communities).
2. Run `snmptrapd -f -Lo` in one terminal and `snmptrap -v2c -c labonly 127.0.0.1 '' SNMPv2-MIB::coldStart` in another (allow the community with `authCommunity log labonly` in `/etc/snmp/snmptrapd.conf`).
3. In the lab VM, run Prometheus `node_exporter` in a container or from the release tarball (the `linux-amd64` build on an x86_64 VM, `linux-arm64` on an ARM64 VM such as one on Apple silicon) and `curl -s localhost:9100/metrics | grep node_load1`.
4. Write a 10-line shell health check that curls a local web server, exits 1 on failure, and posts to a webhook test site you control; run it from a systemd timer (lesson 2.5).

## Key takeaways

- SLI is the measurement, SLO the internal target, SLA the contract with penalties; the error budget is 100% minus the SLO.
- SNMP polls on UDP 161 and sends traps (unacknowledged) and informs (acknowledged) to UDP 162; MIBs map OIDs to names; prefer SNMPv3 authPriv.
- Agents collect rich data but must be deployed and patched; agentless monitoring uses SNMP, SSH, ICMP, HTTP or IPMI.
- Webhooks are HTTP POSTs that deliver events to chat, paging or automation; health checks test real function, not just a running process.
- Aggregate logs centrally (rsyslog, journal-remote, ELK, Loki) with synchronized clocks.
- Events are recorded, thresholds decide, alerts need action, notifications deliver; use durations, severities and baselines to avoid alert fatigue.
