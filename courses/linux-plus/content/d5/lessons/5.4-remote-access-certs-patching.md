## Security faults that look like outages

The second half of objective 5.4 mixes two kinds of problem: things that are **broken** (SSH logins fail, TLS clients reject a certificate, a repository will not verify, two systems cannot agree on a cipher) and things that **work but should not** (unpatched packages, services exposed to the world). Both are found with the same tools from lessons 3.3, 3.5 and 3.6.

## Remote access issues

Start on the client with verbose output: `ssh -v` shows each step, `-vvv` shows everything, including the algorithm lists each side offers.

```text
alice@ws01:~$ ssh -v alice@srv01.example.com
...
debug1: Authentications that can continue: publickey,gssapi-keyex,gssapi-with-mic
debug1: Next authentication method: publickey
debug1: Offering public key: /home/alice/.ssh/id_ed25519 ED25519 SHA256:3qZ...example
debug1: Authentications that can continue: publickey,gssapi-keyex,gssapi-with-mic
debug1: No more authentication methods to try.
alice@srv01.example.com: Permission denied (publickey,gssapi-keyex,gssapi-with-mic).
```

The server does not offer `password` (so `PasswordAuthentication no`), and it refused alice's key. The reason is only on the **server**:

```text
[root@srv01 ~]# journalctl -u sshd -n 5 --no-pager
... sshd[4410]: Authentication refused: bad ownership or modes for directory /home/alice/.ssh
```

| Server-side cause | Confirm | Fix |
|---|---|---|
| `~/.ssh` or `authorized_keys` too open, or home group/world-writable (`StrictModes yes`) | Log line above; `ls -ld ~ ~/.ssh ~/.ssh/authorized_keys` | `chmod 700 ~/.ssh; chmod 600 ~/.ssh/authorized_keys; chmod go-w ~` |
| Wrong SELinux label on `authorized_keys` (copied in from elsewhere) | AVC for `sshd_t` reading the file | `restorecon -Rv ~/.ssh` |
| Key not in `authorized_keys` or pasted with line breaks | `ssh-keygen -lf ~/.ssh/authorized_keys` | Re-add with `ssh-copy-id` |
| User excluded by `AllowUsers`, `AllowGroups`, `DenyUsers`, `PermitRootLogin no` | `sshd -T \| grep -iE 'allow\|deny\|permitroot'` | Edit config or drop-in, `sshd -t`, reload |
| Config error after an edit | `sshd -t` prints the line | Fix and reload; keep a second session open while you test |
| sshd on a non-standard port blocked by SELinux or firewall | `name_bind` AVC; `ss -tlnp` | `semanage port -a -t ssh_port_t -p tcp 2222`; open the port |
| Client banned | `fail2ban-client status sshd` shows the IP | `fail2ban-client set sshd unbanip 192.0.2.50` |

`sshd -T` prints the **effective** configuration after all `Include` files in `/etc/ssh/sshd_config.d/` are applied, which matters because the first value found wins for most keywords. On the client side, `WARNING: REMOTE HOST IDENTIFICATION HAS CHANGED!` means the host key differs from `~/.ssh/known_hosts`: verify the new fingerprint out of band (rebuilt server, or an IP conflict, lesson 5.3) before `ssh-keygen -R srv01.example.com`.

## Obsolete or insecure protocols and cipher negotiation issues

SSH and TLS both negotiate algorithms: each side sends a list and the first match wins. When there is no overlap the connection fails before authentication. With SSH this happens daily with old network devices and appliances, because current OpenSSH no longer enables SHA-1 key exchange, `ssh-rsa` (RSA with SHA-1) signatures or CBC ciphers by default:

```text
alice@ws01:~$ ssh admin@192.0.2.30
Unable to negotiate with 192.0.2.30 port 22: no matching key exchange method found. Their offer: diffie-hellman-group1-sha1,diffie-hellman-group14-sha1
alice@ws01:~$ ssh -o KexAlgorithms=+diffie-hellman-group14-sha1 admin@192.0.2.30
Unable to negotiate with 192.0.2.30 port 22: no matching host key type found. Their offer: ssh-rsa
```

Each message names the category (`key exchange method`, `host key type`, `cipher`, `MAC`) and the server's offer. `ssh -Q kex`, `ssh -Q cipher`, `ssh -Q mac` and `ssh -Q key` list what the client supports at all. The right fix is to **upgrade or reconfigure the old device** (on Cisco IOS: a newer image, an RSA key of 2048 bits or more, `ip ssh version 2`, modern algorithms). If you must connect meanwhile, allow the legacy algorithm **for that host only** in `~/.ssh/config`, with `+` to append to the defaults:

```text
Host oldswitch 192.0.2.30
    KexAlgorithms +diffie-hellman-group14-sha1
    HostKeyAlgorithms +ssh-rsa
    PubkeyAcceptedAlgorithms +ssh-rsa
```

On RHEL the defaults come from the system-wide **crypto policy** (`update-crypto-policies --show` prints `DEFAULT`). Switching the whole host to `LEGACY` weakens every service; prefer the per-host exception, or on RHEL 9 a targeted subpolicy such as `update-crypto-policies --set DEFAULT:SHA1` only if many connections need it.

The same reasoning applies on the server side: if modern clients cannot connect to your server, someone restricted `Ciphers`, `KexAlgorithms` or `MACs` too far in `sshd_config`. Compare `sshd -T | grep -E '^(ciphers|kexalgorithms|macs)'` with the client's `ssh -vvv` lines `debug2: KEX algorithms:` and `debug2: ciphers ctos:`.

For TLS, a client and server with no common **protocol version** fail with errors such as `alert protocol version` or `no protocols available`. Test a specific version with `openssl s_client -connect www.example.com:443 -tls1_2` (or `-tls1_3`), and list what a server accepts with `nmap --script ssl-enum-ciphers -p 443 www.example.com`. TLS 1.0 and 1.1 are deprecated (RFC 8996); OpenSSL 3 refuses them at its default security level, and SSLv3 is gone. Insecure protocols such as Telnet, FTP and TFTP (lesson 3.3) should be replaced, not "fixed".

## Certificate issues

```text
alice@ws01:~$ curl -sS https://portal.example.com/
curl: (60) SSL certificate problem: certificate has expired
alice@ws01:~$ openssl s_client -connect portal.example.com:443 -servername portal.example.com </dev/null 2>/dev/null | openssl x509 -noout -subject -issuer -dates -ext subjectAltName
subject=CN=portal.example.com
issuer=C=US, O=Example CA, CN=Example Issuing CA R2
notBefore=Aug 20 00:00:00 2026 GMT
notAfter=Nov 18 23:59:59 2026 GMT
X509v3 Subject Alternative Name:
    DNS:portal.example.com, DNS:www.portal.example.com
```

`-servername` sends SNI, so a server with several sites returns the right certificate. The second command pulls out the fields that matter. Common problems:

| Error (curl / `openssl s_client` verify code) | Meaning | Fix |
|---|---|---|
| `certificate has expired` (10) | `notAfter` is in the past | Renew (`certbot renew`, ACME client, CA portal), reload the service |
| `certificate is not yet valid` (9) | `notBefore` in the future, usually a wrong clock on the client | Fix time sync (chrony, lesson 2.4) |
| `no alternative certificate subject name matches target host name` / hostname mismatch (62) | Name used is not in the SAN list (the CN is ignored by modern clients) | Reissue with the right SANs, or use the right name |
| `unable to get local issuer certificate` (20) | Chain incomplete: server does not send the intermediate, or the client does not trust the issuing CA | Configure the full chain (`fullchain.pem`, `SSLCertificateFile` with intermediates) or add the private CA to the trust store |
| `self-signed certificate` (18) / `self-signed certificate in certificate chain` (19) | Not issued by a trusted CA | Use a CA-issued certificate (lesson 3.5) or trust the internal root |

Adding an internal root CA to the system trust store:

| | RHEL / Fedora | Debian / Ubuntu |
|---|---|---|
| Copy to | `/etc/pki/ca-trust/source/anchors/example-root.pem` | `/usr/local/share/ca-certificates/example-root.crt` (must end in `.crt`) |
| Rebuild | `update-ca-trust` | `update-ca-certificates` |

Monitor expiry instead of discovering it from users: `openssl x509 -checkend 2592000 -noout -in /etc/pki/tls/certs/portal.crt` exits non-zero when the certificate expires within 30 days, which fits any monitoring check from lesson 5.1. Remember that Java, Python virtual environments and containers may bring their own CA bundles.

## Misconfigured package repository

```text
[root@srv01 ~]# dnf install acme-agent
...
Public key for acme-agent-2.4.1-1.el9.noarch.rpm is not installed
Error: GPG check FAILED
```

On Debian and Ubuntu the equivalent appears during `apt update`:

```text
W: GPG error: https://repo.example.com/apt stable InRelease: The following signatures were invalid: EXPKEYSIG 5E1A2B3C4D5E6F70 Example Repo Signing Key <repo@example.com>
E: The repository 'https://repo.example.com/apt stable InRelease' is not signed.
```

| Problem | Fix |
|---|---|
| Key not imported (dnf) | Import the vendor key after checking its fingerprint: `rpm --import https://repo.example.com/RPM-GPG-KEY-example`, or set `gpgkey=` in the `.repo` file so dnf offers it |
| `NO_PUBKEY` (apt) | Download the key to `/etc/apt/keyrings/example.gpg` (`gpg --dearmor` if it is ASCII-armoured) and reference it with `signed-by=` (`Signed-By:` in a deb822 `.sources` file); `apt-key` is deprecated |
| `EXPKEYSIG` / expired key | The vendor extended or replaced the key: download the new key and replace the old keyring; on RPM systems remove the old key with `rpm -e gpg-pubkey-<keyid>` and import the new one |
| `404` for `repomd.xml` or `Release` | Wrong `baseurl`, a release that reached end of life (moved to an archive such as `old-releases.ubuntu.com`), or a wrong `$releasever` |
| `Release file ... is not valid yet` | Client clock is behind |
| Repository disabled or duplicated | `dnf repolist all`, `dnf config-manager --set-enabled crb`; duplicates warn with "Repository ... is listed more than once" |

Never answer a signature failure with `gpgcheck=0` or `[trusted=yes]`: signature checking is what protects you from a tampered mirror (supply chain, lesson 3.6).

## Unpatched vulnerable systems

| Task | RHEL / Fedora | Debian / Ubuntu |
|---|---|---|
| What updates are pending | `dnf check-update` | `apt update && apt list --upgradable` |
| Security updates only | `dnf updateinfo list --security`; `dnf upgrade --security` | `unattended-upgrade --dry-run -d`; Ubuntu Pro `pro fix CVE-...` |
| Is a CVE fixed in the installed package | `rpm -q --changelog openssh-server \| grep CVE-2024-6387`, `dnf updateinfo list --cve CVE-2024-6387` | `apt changelog openssh-server`, distribution security tracker |
| Automatic updates | `dnf-automatic` timer | `unattended-upgrades` |
| Reboot or restart needed | `dnf needs-restarting -r`, compare `uname -r` with `rpm -q kernel` | `/var/run/reboot-required` exists; `needrestart` |

Two traps: a patched library is not in use until processes using it restart, and a new kernel is not running until reboot (or live patching with kpatch / Canonical Livepatch). And because distributions **backport** fixes, the upstream version number stays old: RHEL 9's `openssh-8.7p1` packages received the CVE-2024-6387 fix as a backport in July 2024 and were not vulnerable after that update, even though a banner-based scanner may flag them (Red Hat later rebased RHEL 9 to OpenSSH 9.9p1). Check the changelog or errata, not the version string.

## Exposed or misconfigured services

```text
[root@srv01 ~]# ss -tulpn | grep -v 127.0.0
Netid State  Recv-Q Send-Q Local Address:Port  Peer Address:Port Process
udp   UNCONN 0      0            0.0.0.0:111        0.0.0.0:*     users:(("rpcbind",pid=812,fd=5))
tcp   LISTEN 0      511          0.0.0.0:6379       0.0.0.0:*     users:(("redis-server",pid=1440,fd=6))
tcp   LISTEN 0      128          0.0.0.0:22         0.0.0.0:*     users:(("sshd",pid=1020,fd=3))
tcp   LISTEN 0      64           0.0.0.0:23         0.0.0.0:*     users:(("systemd",pid=1,fd=40))
```

Redis on all addresses (it should listen on `127.0.0.1` or a private interface, with authentication), rpcbind not needed on a host without NFS, and Telnet through a systemd socket. For each listener decide: needed? If not, `systemctl disable --now telnet.socket` (and `mask` it); if yes, bind it to the right address and restrict it with the firewall. Confirm from **another** host with `nmap -sV -p- srv01.example.com`, because local `ss` does not show what the network firewall allows. Misconfiguration also covers defaults left in place (sample pages, default passwords, directory listing, world-readable config files with credentials).

## Lab it yourself

1. In a VM, `chmod 777 ~/.ssh` for a test user, try key login, and read the server journal; restore `700`.
2. Run `ssh -Q kex` and `ssh -Q key` and compare with `sshd -T | grep -E '^(kexalgorithms|hostkeyalgorithms)'`. Add `KexAlgorithms curve25519-sha256` to a test sshd drop-in, reload, and connect with `ssh -o KexAlgorithms=ecdh-sha2-nistp256` to read the negotiation error.
3. Create a short-lived self-signed certificate (`openssl req -x509 -newkey rsa:2048 -nodes -days 1 -subj /CN=lab.example.com -keyout k.pem -out c.pem`), serve it with `openssl s_server -accept 8443 -cert c.pem -key k.pem`, and test `openssl s_client -connect localhost:8443 -servername wrong.example.com -verify_hostname wrong.example.com`. Then test `openssl x509 -checkend 172800 -noout -in c.pem` and `echo $?`.
4. List security errata with `dnf updateinfo list --security` or `apt list --upgradable` and check whether a reboot is pending.
5. Run `ss -tulpn` and justify each listener.

## Key takeaways

- SSH failures: `ssh -v`/`-vvv` on the client, `journalctl -u sshd` on the server; fix `~/.ssh` modes and labels, `AllowUsers`/`AllowGroups`, and test config with `sshd -t` and `sshd -T`.
- "no matching key exchange method / host key type / cipher found" lists the peer's offer; upgrade the peer, or add a per-host `+algorithm` exception rather than lowering the system crypto policy.
- Read certificates with `openssl s_client -servername` and `openssl x509 -noout -dates -subject -issuer -ext subjectAltName`; expired (10), hostname mismatch (62) and missing chain (20) are the usual causes.
- Trust an internal CA with `update-ca-trust` (RHEL) or `update-ca-certificates` (Debian/Ubuntu); monitor expiry with `-checkend`.
- Repository signature errors are fixed by importing the correct, current key (`rpm --import`, `signed-by=` keyrings), never by disabling checks.
- Patching is not finished until services restart or the host reboots; backported fixes keep old version numbers.
- Audit listeners with `ss -tulpn` and an external `nmap`; disable what is not needed and bind the rest narrowly.
