## A method for boot and hardware faults

Lesson 1.1 walked through the boot chain: firmware (UEFI or BIOS) → GRUB → kernel and initramfs → systemd → targets. Troubleshooting a host that does not come up means finding **the last stage that worked**. Each stage has its own symptom and its own console message, so the first question is always "what is on the console?" For a remote server that means the BMC (iDRAC, iLO, XClarity, generic IPMI with `ipmitool sol activate`), the hypervisor console (`virsh console vm01`, lesson 1.7) or a cloud serial console.

| Last thing you see | Failing stage | Go to |
|---|---|---|
| Nothing, no fans, no BMC | Power / hardware | Server not turning on |
| Firmware screen, "no bootable device" | Firmware boot order, disk, ESP | Device failure, GRUB |
| `grub>` or `grub rescue>` prompt, GRUB error | Bootloader | GRUB misconfiguration |
| `Kernel panic - not syncing` | Kernel / initramfs | Kernel panic |
| dracut emergency shell, "Entering emergency mode" | initramfs cannot find root | Missing drivers, root device |
| systemd emergency or rescue shell | fstab, filesystem, failed units | Lesson 5.2 (storage and processes) |
| Login prompt, but SSH fails | Network, sshd, firewall | Server inaccessible |

## Server not turning on

When nothing happens, work from the outside in:

1. **Power**: both PSUs cabled and lit, PDU outlet live, power button or BMC power state. From the BMC: `ipmitool -I lanplus -H 10.0.0.21 -U admin -P '...' chassis status` shows `System Power : off`, and `chassis power on` starts it.
2. **Hardware event log**: `ipmitool sel list` (or `sel elist`) shows PSU failures, thermal trips, memory errors and fan failures with timestamps. A host that powers off by itself under load is often thermal or PSU.
3. **POST**: beep codes, front-panel LEDs or the BMC's POST code. Reseat recently changed DIMMs or cards; remove non-essential hardware to isolate.
4. For a VM: `virsh list --all` shows `shut off`, `virsh start vm01`, and `virsh dominfo` or the libvirt log in `/var/log/libvirt/qemu/vm01.log` explains why it would not start (missing disk image, not enough host memory).

## Server inaccessible

The host is running (the BMC console shows a login prompt) but nobody can reach it. Log in on the console and split the problem:

| Check | Command | What it tells you |
|---|---|---|
| Has an address, link up | `ip -br addr`, `ip -br link` | Interface down or no IP (lesson 5.3) |
| Can reach gateway | `ping -c3 <gateway>` | Layer 2/3 path |
| sshd running and listening | `systemctl status sshd` (`ssh` on Debian/Ubuntu), `ss -tlnp \| grep :22` | Service problem |
| Firewall | `firewall-cmd --list-all`, `ufw status`, `nft list ruleset` | Port 22 not allowed |
| System overloaded | `uptime`, `free -h` | Hung by memory pressure (lesson 5.5) |

If the console itself is frozen, the kernel may be hung; check the BMC SEL and use SysRq if enabled (`echo 1 > /proc/sys/kernel/sysrq` beforehand; Alt+SysRq+t dumps tasks, +b reboots immediately).

## GRUB misconfiguration

GRUB reads its generated `grub.cfg` and on RHEL 8 and later also **BLS** (Boot Loader Specification) snippets in `/boot/loader/entries/*.conf`, one file per installed kernel. You never edit `grub.cfg` by hand: you edit `/etc/default/grub` and regenerate it.

| Task | RHEL / Fedora | Debian / Ubuntu |
|---|---|---|
| Regenerate config | `grub2-mkconfig -o /boot/grub2/grub.cfg` | `update-grub` (wrapper for `grub-mkconfig -o /boot/grub/grub.cfg`) |
| Change kernel arguments | `grubby --update-kernel=ALL --args="console=ttyS0"` (edits the BLS entries); or edit `GRUB_CMDLINE_LINUX` and run `grub2-mkconfig -o /boot/grub2/grub.cfg --update-bls-cmdline` (RHEL 9) | Edit `GRUB_CMDLINE_LINUX` in `/etc/default/grub`, then `update-grub` |
| Default kernel | `grubby --set-default /boot/vmlinuz-<ver>`, `grubby --default-kernel` | `GRUB_DEFAULT=` then `update-grub` |
| Reinstall on BIOS disk | `grub2-install /dev/sda` | `grub-install /dev/sda` |

On RHEL 9 UEFI systems `/boot/efi/EFI/redhat/grub.cfg` is a small stub that loads `/boot/grub2/grub.cfg`, so the same `grub2-mkconfig` command is used for BIOS and UEFI. Running `grub2-install` on a Secure Boot UEFI system is wrong: reinstall the `grub2-efi-x64` and `shim-x64` packages instead.

Typical GRUB symptoms:

```text
error: file `/vmlinuz-5.14.0-503.11.1.el9_5.x86_64' not found.
error: you need to load the kernel first.

Press any key to continue...
```

The menu entry points at a kernel that was removed, or `/boot` is a different partition than the config expects. The `grub rescue>` prompt with `error: unknown filesystem` means GRUB's core image cannot read the partition holding its modules, usually after partitions were moved or the disk order changed.

Recovery: at the menu press **e** to edit the entry for one boot (fix the `linux` line, or add a parameter), **Ctrl+x** to boot it, then make the fix permanent and regenerate. If no entry works, boot rescue media, mount the root filesystem under `/mnt/sysroot` (RHEL rescue mode does this for you), `chroot`, reinstall or regenerate, and exit.

## Kernel parameters for recovery

| Parameter (added to the `linux` line) | Effect |
|---|---|
| `systemd.unit=rescue.target` (or just `rescue` / `single` / `1`) | Single-user rescue shell with local filesystems mounted, root password required |
| `systemd.unit=emergency.target` (or `emergency`) | Minimal shell, root mounted read-only, nothing else started |
| `rd.break` | Stop inside the initramfs before switching to the real root (RHEL root password reset: `mount -o remount,rw /sysroot`, `chroot /sysroot`, `passwd`, `touch /.autorelabel`) |
| `init=/bin/bash` | Legacy: replaces systemd with a shell |
| `nomodeset`, `modprobe.blacklist=nouveau` | Work around a broken graphics driver |
| `rd.shell rd.debug` | Allow a dracut shell if mounting root fails, and trace the initramfs scripts (`set -x`, logged to the journal or `/run/initramfs/init.log`) |

> **Exam tip:** rescue.target mounts filesystems and needs the root password; emergency.target mounts only `/`, read-only. Use emergency when a bad `/etc/fstab` entry stops rescue from starting.

## Kernel panic

A **kernel panic** is the kernel stopping because it cannot continue safely. The first line after `Kernel panic - not syncing:` names the reason:

| Panic message | Likely cause | Fix |
|---|---|---|
| `VFS: Unable to mount root fs on unknown-block(0,0)` | No initramfs for this kernel, or it lacks the storage driver | Boot an older kernel; `dracut -f --kver <ver>` (`update-initramfs -u -k <ver>` rebuilds an existing image, `-c -k <ver>` creates a missing one) |
| `Attempted to kill init! exitcode=0x00000100` | PID 1 (systemd) died: corrupted `/usr`, broken glibc, wrong `init=` | Rescue media, `rpm -Va` / `debsums`, reinstall packages |
| `Fatal exception` / `Oops` followed by panic | Kernel or driver bug, bad RAM | Older kernel, update or remove the module, memory test |
| `softlockup: hung tasks` (only when `softlockup_panic=1` / `kernel.softlockup_panic = 1` is set) | CPU stuck in kernel code | Kernel update, hardware check |

Capture panics with **kdump** (`kexec-tools`, `systemctl enable --now kdump`, `crashkernel=` parameter; dumps land in `/var/crash/`), a serial console (`console=ttyS0,115200`), or netconsole. The kernel parameter `panic=10` reboots 10 seconds after a panic instead of hanging. Always keep at least two kernels installed (`installonly_limit=3` in `/etc/dnf/dnf.conf` is the RHEL default) so an older one is in the GRUB menu.

## Data and kernel corruption

**Kernel corruption** means the kernel image, modules or initramfs on disk are damaged or inconsistent (interrupted update, full `/boot`). Verify and reinstall:

```text
[root@srv01 ~]# rpm -V kernel-core-5.14.0-503.11.1.el9_5
S.5....T.    /lib/modules/5.14.0-503.11.1.el9_5.x86_64/vmlinuz
[root@srv01 ~]# dnf reinstall kernel-core-5.14.0-503.11.1.el9_5
```

`S` = size differs, `5` = digest differs, `T` = mtime differs, so the file has changed since installation (on Debian/Ubuntu: `dpkg --verify linux-image-<ver>` or `debsums`). A full `/boot` during an update is a classic cause; check `df -h /boot` before kernel updates.

**Data corruption** shows up as filesystem errors in the kernel log, I/O errors, or applications reading garbage. ext4 reacts according to its `errors=` behaviour (`continue`, `remount-ro` or `panic`, set as a mount option or stored in the superblock with `tune2fs -e`; Debian and Ubuntu installers put `errors=remount-ro` on the root entry in `/etc/fstab`), and a journal error aborts the journal and forces the filesystem read-only whatever the setting, unless it is `panic`. So the usual symptom is a filesystem that suddenly becomes read-only. Repair is covered in the next lesson: unmount, `fsck`/`e2fsck` for ext4, `xfs_repair` for XFS, and restore from backup (lesson 1.6) when the tool cannot recover the data. Check the disk before repairing the filesystem on it.

## Device failure

```text
[root@srv01 ~]# dmesg -T | grep -E 'ata2|sdb|md0' | tail -4
[Sun Nov 22 03:12:44 2026] ata2.00: exception Emask 0x0 SAct 0x0 SErr 0x0 action 0x0
[Sun Nov 22 03:12:44 2026] ata2.00: failed command: READ DMA EXT
[Sun Nov 22 03:12:44 2026] I/O error, dev sdb, sector 182334464 op 0x0:(READ) flags 0x0 phys_seg 1 prio class 0
[Sun Nov 22 03:12:44 2026] md/raid1:md0: sdb1: rescheduling sector 182332416
```

| Check | Command |
|---|---|
| Disk health and error counters | `smartctl -H /dev/sdb`, `smartctl -a /dev/sdb` (look at reallocated and pending sectors); `nvme smart-log /dev/nvme0` |
| RAID state | `cat /proc/mdstat` (`[U_]` = one mirror member missing), `mdadm --detail /dev/md0` |
| Device present at all | `lsblk`, `lsscsi`, `lspci`, `lsusb` (lesson 1.2) |
| Hardware log | `ipmitool sel list`, `journalctl -k -p err` |

Replace a failed md member with `mdadm /dev/md0 --fail /dev/sdb1 --remove /dev/sdb1`, swap the disk, copy the partition table, then `mdadm /dev/md0 --add /dev/sdc1` and watch the rebuild in `/proc/mdstat`. For a dying disk without redundancy, copy what you can with `ddrescue` (lesson 1.6) before anything else.

## Missing or disabled drivers

A device that `lspci` lists but that does not work usually has no driver bound:

```text
[root@srv01 ~]# lspci -k -s 03:00.0
03:00.0 Ethernet controller: Intel Corporation Ethernet Controller X710 for 10GbE SFP+ (rev 02)
	Subsystem: Intel Corporation Ethernet Converged Network Adapter X710-2
	Kernel modules: i40e
```

There is a `Kernel modules:` line (a module exists for it) but no `Kernel driver in use:` line, so nothing is bound. Check:

| Cause | How to confirm | Fix |
|---|---|---|
| Module not loaded | `lsmod \| grep i40e` empty | `modprobe i40e`, check `dmesg` for its messages |
| Blacklisted | `grep -r i40e /etc/modprobe.d/ /usr/lib/modprobe.d/` shows `blacklist i40e` or `install i40e /bin/false` | Remove the line; rebuild the initramfs if the module is loaded there |
| Module missing for this kernel | `modprobe: FATAL: Module i40e not found in directory /lib/modules/<ver>` | Install the matching `kernel-modules` / `linux-modules-extra-<ver>` package, or the vendor's DKMS/kmod package |
| Out-of-tree driver not rebuilt after a kernel update | `dkms status` shows the module only for the old kernel | `dkms autoinstall`, or boot the old kernel |
| Secure Boot rejects an unsigned module | `Key was rejected by service` in `modprobe` output | Sign it and enrol the key with `mokutil --import` (lesson 3.3) |
| Storage driver missing from the initramfs | Boot stops in dracut with `/dev/mapper/vg-root does not exist` | Boot an older kernel or rescue media, `dracut -f --kver <ver>` (`--add-drivers` if needed) |

## Lab it yourself

1. In a VM with a snapshot, press **e** at the GRUB menu, add `systemd.unit=rescue.target`, boot, and compare with `systemd.unit=emergency.target` (run `findmnt /` in each).
2. Run `grubby --info=ALL` (RHEL) or read `/boot/grub/grub.cfg` (Ubuntu), change a parameter with `grubby --update-kernel=ALL --args=quiet` or `/etc/default/grub` plus `update-grub`, and reboot to check `cat /proc/cmdline`.
3. Blacklist a harmless module such as `pcspkr` in `/etc/modprobe.d/lab.conf` (`pcspkr` exists only on x86_64 VMs; on an ARM64 VM pick a module from `lsmod` that the VM does not need), reboot, confirm `lsmod` no longer lists it and `modprobe pcspkr` still loads it by hand (blacklist stops only automatic loading), then remove the file.
4. Revert the snapshot, rename the current initramfs, reboot into that kernel to see the panic or dracut failure, then pick the older kernel and rebuild the broken kernel's image with `dracut -f --kver <newer-version>` (plain `dracut -f` would rebuild the running, older kernel's image; on Ubuntu use `update-initramfs -c -k <newer-version>`).

## Key takeaways

- Find the last boot stage that worked: firmware, GRUB, kernel/initramfs, systemd, network.
- Regenerate GRUB with `grub2-mkconfig -o /boot/grub2/grub.cfg` (RHEL, BLS entries edited with `grubby`) or `update-grub` (Debian/Ubuntu); fix one boot interactively with **e** and Ctrl+x.
- `systemd.unit=rescue.target` mounts filesystems; `systemd.unit=emergency.target` mounts only `/` read-only; `rd.break` stops in the initramfs.
- "Unable to mount root fs" means initramfs or storage driver problems; rebuild with `dracut -f` or `update-initramfs -u` and keep older kernels.
- Device failure evidence: `I/O error` in `dmesg`, SMART counters, `[U_]` in `/proc/mdstat`, the BMC SEL.
- An unbound device has no `Kernel driver in use:` in `lspci -k`; check `lsmod`, blacklists, the matching modules package, DKMS and Secure Boot signing.
