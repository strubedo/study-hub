## Two layers on each family

Each distribution family has a **low-level** tool that installs one package file and knows nothing about repositories, and a **high-level** tool that downloads from repositories and resolves dependencies.

| | RHEL / Fedora | Debian / Ubuntu |
|---|---|---|
| Package format | `.rpm` | `.deb` |
| Low-level | `rpm` | `dpkg` |
| High-level | `dnf` (`yum` is an alias on RHEL 8 and later; `zypper` on SUSE) | `apt` (interactive), `apt-get` / `apt-cache` (stable for scripts) |
| Repository files | `/etc/yum.repos.d/*.repo` | `/etc/apt/sources.list` and `/etc/apt/sources.list.d/*.list` or `*.sources` |
| Main config | `/etc/dnf/dnf.conf` | `/etc/apt/apt.conf.d/` |

## Install, update, remove

| Task | dnf | apt |
|---|---|---|
| Refresh metadata | automatic (`dnf makecache`) | `apt update` (required before installing) |
| Search / details | `dnf search nginx`, `dnf info nginx` | `apt search nginx`, `apt show nginx` |
| Install | `dnf install nginx` | `apt install nginx` |
| Install a local file with dependencies | `dnf install ./app-1.2.rpm` | `apt install ./app_1.2_amd64.deb` |
| List available updates | `dnf check-update` | `apt list --upgradable` |
| Update everything | `dnf upgrade` (`dnf update` is the same) | `apt upgrade`; `apt full-upgrade` may also remove packages to resolve changes |
| Remove | `dnf remove nginx` | `apt remove nginx` (keeps config), `apt purge nginx` (removes config too) |
| Remove unneeded dependencies | `dnf autoremove` | `apt autoremove` |
| Which package provides a file | `dnf provides /usr/sbin/semanage` | `apt-file search semanage` (after `apt-file update`) |
| History and rollback | `dnf history`, `dnf history undo 14` | `/var/log/apt/history.log`; no built-in undo |

The low-level tools query the local package database directly:

| Task | rpm | dpkg |
|---|---|---|
| Install a file (no dependency resolution) | `rpm -ivh pkg.rpm`; upgrade `rpm -Uvh` | `dpkg -i pkg.deb` |
| Remove | `rpm -e pkg` | `dpkg -r pkg`; `dpkg -P pkg` purges config |
| List installed | `rpm -qa` | `dpkg -l` |
| Files in a package | `rpm -ql pkg` | `dpkg -L pkg` |
| Which package owns a file | `rpm -qf /etc/ssh/sshd_config` | `dpkg -S /etc/ssh/sshd_config` |
| Info / dependencies of a file not yet installed | `rpm -qip pkg.rpm`, `rpm -qpR pkg.rpm` | `dpkg -I pkg.deb` |
| Verify installed files against the database | `rpm -V openssh-server` | `dpkg --verify openssh-server` (or `debsums`) |

### Dependencies and conflicts

`rpm -i` and `dpkg -i` refuse (or, for `dpkg`, leave the package unconfigured) when a dependency is missing; they never download anything. On Debian the fix after a failed `dpkg -i` is `apt -f install` (fix broken), which fetches what is missing. A **conflict** arises when two packages claim the same file or declare `Conflicts:`; the package managers stop rather than overwrite. `dnf` offers `--allowerasing` to replace a conflicting package, and `--skip-broken` to install what it can. Forcing with `rpm --nodeps` or `dpkg --force-all` leaves a broken system, so treat them as a last resort.

### Building from source

When no package exists, the classic sequence is:

```text
srv01$ tar -xzf tool-2.4.tar.gz && cd tool-2.4
srv01$ ./configure --prefix=/usr/local     # checks build dependencies, writes Makefile
srv01$ make                                # compile
srv01# make install                        # copy into /usr/local/bin, /usr/local/lib ...
```

You need a compiler and headers first: `dnf group install "Development Tools"` or `apt install build-essential`, plus the `-devel` (RPM) or `-dev` (Debian) packages of each library. Software installed this way is invisible to `rpm` and `dpkg`, gets no security updates, and is removed only with `make uninstall` if the project provides it; that is why `/usr/local` is used, to keep it apart from packaged files. Many projects now use `cmake` or `meson` instead of `./configure`.

## Repositories

A dnf repository is a section in a `.repo` file:

```text
srv01$ cat /etc/yum.repos.d/internal.repo
[internal]
name=Internal tools
baseurl=https://repo.example.com/el9/$basearch/
enabled=1
gpgcheck=1
gpgkey=https://repo.example.com/RPM-GPG-KEY-internal
```

| Task | RHEL 9 / 10 (DNF 4) | Debian / Ubuntu |
|---|---|---|
| List repos | `dnf repolist`, `dnf repolist --all` | `apt policy` (sources and priorities) |
| Enable / disable permanently | `dnf config-manager --set-enabled crb` / `--set-disabled` (dnf-plugins-core), or edit `enabled=` | Add or delete the source file (or comment out the line) |
| For one command only | `dnf --enablerepo=epel install htop`, `--disablerepo=` | No direct equivalent; use `-t <release>` for a specific suite |
| Add a third-party repo | Drop a `.repo` file, `dnf config-manager --add-repo <url>`, or install a release package (`dnf install epel-release` on RHEL-compatible systems) | Drop a source file plus its key; `add-apt-repository ppa:...` on Ubuntu |
| Import a signing key | `rpm --import KEY-FILE` (or `gpgkey=` imports on first use) | Save the key (dearmored) in `/etc/apt/keyrings/` and reference it with `signed-by=` |
| Check a package's signature | `rpm -K pkg.rpm` (`--checksig`) | apt checks the signed `Release`/`InRelease` file; individual `.deb` files are not normally signed |

> **Watch out:** Fedora 41 and later ship **DNF5**, where the syntax is `dnf config-manager setopt crb.enabled=1` (or `dnf config-manager enable crb`) and `addrepo --from-repofile=<url>` instead of `--add-repo`. RHEL 9 uses DNF 4 as shown in the table.

An apt source can be written two ways. The one-line format:

```text
deb [signed-by=/etc/apt/keyrings/example.gpg] https://apt.example.com/debian bookworm main
```

and the newer **deb822** format (Ubuntu 24.04 uses it for its own `/etc/apt/sources.list.d/ubuntu.sources`):

```text
Types: deb
URIs: https://apt.example.com/debian
Suites: bookworm
Components: main
Signed-By: /etc/apt/keyrings/example.gpg
```

> **Exam tip:** `apt-key` is deprecated (removed in newer releases) because a key added to the global trusted keyring could sign packages for *any* repository. The current practice is one keyring per repository, tied to it with `signed-by`. On the RPM side, `gpgcheck=1` makes dnf refuse unsigned or wrongly signed packages; disabling it to "make an error go away" is the wrong answer.

## Exclusions, holds and pins

Sometimes a package must not be upgraded (a kernel that a driver depends on, a database version an application supports).

| Goal | RHEL / Fedora | Debian / Ubuntu |
|---|---|---|
| Never consider certain packages from any repo | `excludepkgs=kernel* mysql*` in the `[main]` section of `/etc/dnf/dnf.conf` (`exclude=` is the older spelling) | `Pin-Priority: -1` in `/etc/apt/preferences.d/` |
| Exclude from one repo | `excludepkgs=` inside that `[repo]` section | A pin with `Pin: origin` or `Pin: release` for that source |
| One-off exclusion | `dnf upgrade --exclude=kernel*` | `apt upgrade` skips held packages |
| Ignore exclusions once | `dnf upgrade --disableexcludes=all` | |
| Freeze at the current version | `dnf versionlock add nginx` (versionlock plugin) | `apt-mark hold nginx`; `apt-mark unhold`, `apt-mark showhold` |

## Language-specific package managers

| Tool | Ecosystem | Common commands and where things go |
|---|---|---|
| `pip` | Python (PyPI) | `pip install requests`, `pip install -r requirements.txt`, `pip list`, `pip uninstall`. Use a virtual environment: `python3 -m venv .venv; . .venv/bin/activate` |
| `cargo` | Rust (crates.io) | `cargo build`, `cargo add serde` (edits `Cargo.toml`), `cargo install ripgrep` (puts the binary in `~/.cargo/bin`) |
| `npm` | Node.js (npm registry) | `npm install express` (into `./node_modules`, recorded in `package.json` and `package-lock.json`), `npm install -g` (global), `npm ci` (clean install from the lock file) |

> **Watch out:** On Debian 12+, Ubuntu 23.04+ and other distributions that mark the system Python as **externally managed** (PEP 668), `sudo pip install` fails with `error: externally-managed-environment`. That is deliberate: pip would overwrite files that `apt` owns. Use the distro package (`apt install python3-requests`), a venv, or `pipx` for applications. Never mix `sudo pip` with packaged Python.

## update-alternatives

When several programs can provide one command (`editor`, `java`, `python`, `iptables`), the **alternatives** system points a generic symlink through `/etc/alternatives/` to the chosen one.

```text
srv01$ update-alternatives --display editor
editor - auto mode
  link best version is /bin/nano
  link currently points to /bin/nano
  link editor is /usr/bin/editor
srv01# update-alternatives --config editor          # interactive menu
srv01# update-alternatives --set editor /usr/bin/vim.basic
srv01# update-alternatives --install /usr/bin/java java /opt/jdk21/bin/java 2100
```

In **auto** mode the highest-priority alternative wins; choosing one with `--config` or `--set` switches to **manual** mode until you run `--auto`. On RHEL the command is `alternatives` (`update-alternatives` also exists as a link), with the same subcommands.

## Software configuration after install

Packages put defaults in `/etc` and mark them as **configuration files**, so upgrades do not silently overwrite your edits. If an upgrade brings a new default for a file you changed, rpm keeps your file and writes the new default beside it as `file.rpmnew` (for files marked `%config(noreplace)`, which is most of them); for plain `%config` files, or when a package is removed, rpm saves your edited copy as `file.rpmsave`. dpkg instead asks interactively: keep yours and the new default lands in `file.dpkg-dist`, or take the new one and yours is kept as `file.dpkg-old`. After any upgrade, look for these and merge by hand (`find /etc -name '*.rpmnew'`). Many services read **drop-in directories** (`/etc/nginx/conf.d/`, `/etc/ssh/sshd_config.d/`, `/etc/sysctl.d/`); put local settings there instead of editing the vendor file. Debian also offers `dpkg-reconfigure <pkg>` to rerun a package's setup questions (`dpkg-reconfigure tzdata`).

## Sandboxed applications

Sandboxed formats ship an application with its own dependencies and run it isolated from the host, independent of the distribution's libraries.

| | Flatpak | Snap | AppImage |
|---|---|---|---|
| Backed by | Community; main remote is Flathub | Canonical; Snap Store | Single self-contained file |
| Sandbox | bubblewrap + namespaces; portals for files and devices | AppArmor + seccomp; `strict`, `classic` (unconfined) or `devmode` confinement | None by default |
| Install | `flatpak install flathub org.videolan.VLC` | `snap install vlc`; `snap install code --classic` | `chmod +x app.AppImage; ./app.AppImage` |
| Run, list, update | `flatpak run org.videolan.VLC`, `flatpak list`, `flatpak update` | `vlc`, `snap list`, `snap refresh` (automatic by default), `snap revert` | Download a new file |
| Permissions | `flatpak info --show-permissions`, `flatpak override --user --nofilesystem=home <app>` | `snap connections <snap>`, `snap connect` / `disconnect` | |
| Add a repo | `flatpak remote-add --if-not-exists flathub https://dl.flathub.org/repo/flathub.flatpakrepo` | Single store | |

Flatpak is mainly for desktop applications; Snap also packages server software and is preinstalled on Ubuntu (where some `apt install` commands, such as Firefox, install a snap).

## Lab it yourself

Inside the lab VM, in a Rocky/Alma container (`podman run -it rockylinux:9`) and a Debian container (`docker run -it debian:12`). Podman and Docker pull the image variant that matches the VM's CPU, so the same commands work on an x86_64 or ARM64 VM:

1. `dnf info nginx`, `dnf provides /usr/bin/dig`, `dnf repolist --all`; `apt update; apt show nginx; apt policy`.
2. Install `tree`, then `rpm -ql tree` / `dpkg -L tree` and `rpm -qf /usr/bin/tree` / `dpkg -S /usr/bin/tree`.
3. Add `excludepkgs=tree` to `/etc/dnf/dnf.conf` and run `dnf reinstall tree`; on Debian `apt-mark hold tree; apt-mark showhold`.
4. `dnf history`, then `dnf history undo last`.
5. In the Debian container `apt install python3-pip`, try `pip install requests` (externally managed error), then use `python3 -m venv /tmp/v`.
6. `update-alternatives --display editor` after installing `vim` and `nano`.

## Key takeaways

- `rpm` and `dpkg` handle single files without dependency resolution; `dnf` and `apt` use repositories and resolve dependencies; `apt update` refreshes metadata first.
- Know the query pairs: `rpm -qa`/`dpkg -l`, `rpm -ql`/`dpkg -L`, `rpm -qf`/`dpkg -S`, `dnf provides`/`apt-file search`.
- Repos live in `/etc/yum.repos.d/*.repo` and `/etc/apt/sources.list.d/`; keep `gpgcheck=1` and use `signed-by` keyrings rather than `apt-key`.
- `excludepkgs=` and `dnf versionlock` on RPM systems; `apt-mark hold` and pin priorities on Debian.
- Use virtual environments for `pip`; `cargo install` goes to `~/.cargo/bin`; `npm install` is per-project unless `-g`.
- `update-alternatives --config` (Debian) or `alternatives --config` (RHEL) chooses which implementation a generic command runs.
- Watch for `.rpmnew` and `.dpkg-dist` after upgrades; prefer drop-in directories for local settings.
- Flatpak, Snap and AppImage bundle dependencies and (except AppImage) run sandboxed.
