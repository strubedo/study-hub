## What a container is, and the runtime stack

A container is an ordinary Linux process isolated with **namespaces** (its own PID, mount, network, UTS, IPC and user view), limited with **cgroups**, and started from a read-only **image** with a thin writable layer on top. There is no guest kernel: every container on a host shares the host's kernel, which is the key difference from the VMs in Domain 1.

Several pieces cooperate, and the exam names four of them:

| Component | Role |
|---|---|
| **runC** | Low-level **OCI runtime**: given an unpacked root filesystem and a `config.json`, it creates the namespaces and cgroups and starts the process, then exits. `crun` (written in C) is an alternative and is the default for Podman on Fedora and RHEL 9 and later |
| **containerd** | High-level runtime **daemon**: pulls and stores images, manages container lifecycles and calls runC through a shim. Used by Docker and by Kubernetes (via its CRI plugin) |
| **Docker** | `docker` CLI talking to the **`dockerd`** daemon (root-owned socket `/var/run/docker.sock`), which uses containerd, which uses runC |
| **Podman** | **Daemonless** engine from Red Hat: each `podman` command forks the container directly (via `conmon` and crun or runC). Runs **rootless** by default for normal users, and its CLI is compatible with Docker's (`alias docker=podman` mostly works) |

Both Docker and Podman use **OCI** images and registries, so an image built with one runs on the other. On RHEL, `podman`, `buildah` (build images) and `skopeo` (copy and inspect images in registries) are the supported tools; Docker CE comes from Docker's own repository.

> **Exam tip:** "Which component actually creates the container's namespaces?" is runC (or crun). "Which runs as a long-lived daemon that Docker relies on?" is containerd. "Which needs no daemon and runs rootless by default?" is Podman.

## Images: names, tags and layers

An image reference is `[registry/][namespace/]name[:tag|@digest]`. `docker.io/library/nginx:1.27` is registry `docker.io`, namespace `library`, repository `nginx`, tag `1.27`. With no tag you get **`latest`**, which is only a convention, not "the newest". A **digest** (`nginx@sha256:...`) pins the exact content and never moves, while a tag can be re-pointed. Podman asks which registry to use for a short name unless it is listed in `/etc/containers/registries.conf`, so prefer fully qualified names.

```text
srv01$ podman pull docker.io/library/nginx:1.27
srv01$ podman images
REPOSITORY                TAG         IMAGE ID      CREATED      SIZE
docker.io/library/nginx   1.27        3b25b682ea82  2 weeks ago  196 MB
srv01$ podman tag docker.io/library/nginx:1.27 registry.example.com/web/nginx:prod
srv01$ podman push registry.example.com/web/nginx:prod
srv01$ podman rmi registry.example.com/web/nginx:prod     # removes the tag; the image stays while another tag points at it
```

An image is a stack of read-only **layers**, each the filesystem changes of one build instruction. Layers are shared: ten images built `FROM` the same base store the base once. When a container runs, the storage driver (**overlay2** for Docker, **overlay** for Podman, both using the kernel's OverlayFS) stacks the layers as the lower directories and adds a writable **upper** layer. Writes to an existing file copy it up first. Deleting the container deletes that upper layer, which is why data you care about belongs in a volume (next lesson). `docker history <image>` lists the layers and the instructions that made them; `docker image inspect` shows the layer digests under `RootFS`.

## Building an image: the Dockerfile

```text
# Dockerfile
FROM registry.access.redhat.com/ubi9/ubi-minimal:latest
RUN microdnf install -y python3 python3-pip && microdnf clean all
WORKDIR /app
COPY app.py requirements.txt ./
RUN python3 -m pip install -r requirements.txt
ENV APP_PORT=8080
EXPOSE 8080
USER 1001
ENTRYPOINT ["python3", "app.py"]
CMD ["--port", "8080"]
```

```text
srv01$ podman build -t registry.example.com/app:1.4 .     # . is the build context
srv01$ docker build -t app:1.4 -f Dockerfile.prod .
```

| Instruction | Meaning |
|---|---|
| **`FROM`** | Base image; must be first (except `ARG`). `FROM scratch` starts empty. Several `FROM` lines make a **multi-stage** build, copying only the result into a small final image |
| `RUN` | Run a command at **build** time and commit the result as a new layer. Chain and clean up in one `RUN` so the cache files do not stay in a lower layer |
| `COPY` / `ADD` | Copy files from the build context. `ADD` can also fetch URLs and unpack local tar files; prefer `COPY` |
| `WORKDIR`, `ENV`, `EXPOSE` | Working directory; environment variables baked into the image; documents the port (does **not** publish it) |
| **`USER`** | User (name or UID) for later `RUN` steps and for the running container. Without it (here or in the base image), the process runs as root inside the container |
| **`ENTRYPOINT`** | The executable that always runs |
| **`CMD`** | Default arguments to the `ENTRYPOINT`, or the default command if there is no `ENTRYPOINT` |

How `ENTRYPOINT` and `CMD` combine is a favourite question:

| Dockerfile | `run app:1.4` executes | `run app:1.4 --debug` executes |
|---|---|---|
| `CMD ["nginx", "-g", "daemon off;"]` only | `nginx -g daemon off;` | `--debug` (replaces CMD entirely) |
| `ENTRYPOINT ["python3", "app.py"]` + `CMD ["--port", "8080"]` | `python3 app.py --port 8080` | `python3 app.py --debug` (CMD replaced, ENTRYPOINT kept) |

`--entrypoint` on the command line replaces the entrypoint. Use the **exec form** (JSON array) so the program runs as PID 1 and receives `SIGTERM` from `docker stop`; the shell form (`CMD python3 app.py`) wraps it in `/bin/sh -c`, which does not forward signals.

## Running and managing containers

```text
srv01$ podman run -d --name web -p 8080:80 -e TZ=UTC --restart=always docker.io/library/nginx:1.27
srv01$ podman run -it --rm docker.io/library/debian:12 bash      # throwaway interactive shell
srv01$ podman ps            # running; -a includes stopped
srv01$ podman logs -f --tail 20 web
srv01$ podman exec -it web /bin/sh                               # a second process inside a running container
srv01$ podman stop web; podman start web; podman restart web
srv01$ podman inspect web --format '{{.State.Status}} {{.NetworkSettings.IPAddress}}'
srv01$ podman rm web        # -f stops it first
srv01$ podman container prune
```

| Option or command | Meaning |
|---|---|
| `-d`, `-it`, `--rm`, `--name` | Detached; interactive with a TTY; delete when it exits; a name instead of a random one |
| `-e VAR=value`, `--env-file app.env` | **Environment variables** for the process (the usual way to configure a containerised app); `inspect` shows them under `Config.Env` |
| `-p 8080:80` | Publish host port 8080 to container port 80 |
| `-v` / `--mount` | Volumes and bind mounts (next lesson) |
| `logs` | The container's stdout and stderr. An app that logs only to a file inside the container shows nothing here |
| `exec` | Run an extra command in an existing container; `run` always creates a new one |
| `stop` | SIGTERM, then SIGKILL after 10 seconds (`-t` changes the wait); `kill` sends SIGKILL immediately |
| `inspect` | Full JSON for a container or image: mounts, env, network, state, restart count |
| `rm`, `rmi` | Delete a container; delete an image (fails while a container uses it) |
| `container prune`, `image prune` | Delete all **stopped** containers; delete **dangling** images (untagged), or with `-a` every image no container uses |
| `system prune` | Stopped containers, unused networks, dangling images and build cache; add `-a` for all unused images and `--volumes` for volumes |

> **Watch out:** `docker run` with a name that already exists fails ("name is already in use"); `rm` the old container first or use `start`. And `docker stop` followed by `docker run` again creates a **second** container from the image, losing whatever was in the first one's writable layer.

## Lab it yourself

With Podman (rootless, no daemon) or Docker in the lab VM. The alpine and nginx images are published for both x86_64 and ARM64, and the engine pulls the one that matches the VM's CPU:

1. `podman pull docker.io/library/alpine:3.20`, `podman images`, `podman history docker.io/library/alpine:3.20`.
2. Write a two-line Dockerfile: `FROM docker.io/library/alpine:3.20` and `ENTRYPOINT ["echo", "hello"]` plus `CMD ["world"]`. Build it with `podman build -t hi .`, then `podman run --rm hi` and `podman run --rm hi there`.
3. Add `USER 1000` and `RUN id` (above the `USER` line and below it) and watch the build output.
4. `podman run -d --name web -p 8080:80 docker.io/library/nginx:1.27`, `curl localhost:8080`, `podman logs web`, `podman exec web nginx -v`, `podman inspect web | less`.
5. `podman stop web; podman ps -a; podman container prune; podman image prune -a`.

## Key takeaways

- Containers share the host kernel; namespaces isolate, cgroups limit, images supply the filesystem.
- runC/crun create containers; containerd is the daemon Docker builds on; Podman is daemonless and rootless by default.
- `name:tag` defaults to `latest`; tags move, digests do not; `tag` adds a name and `rmi` removes one.
- Images are shared read-only layers; overlay storage adds a per-container writable layer that disappears with the container.
- `FROM` first, `RUN` at build time, `USER` to stop running as root, `ENTRYPOINT` is fixed, `CMD` supplies defaults that run arguments replace.
- `run` creates, `start`/`stop` reuse, `exec` joins, `logs` reads stdout/stderr, `inspect` shows JSON, `rm`/`prune` delete.
