## Keeping data: volumes, bind mounts and tmpfs

A container's writable layer is deleted with the container and is slow for heavy writes, so persistent data goes in a mount. There are three kinds:

| Kind | Syntax | Lives in | Use for |
|---|---|---|---|
| **Named volume** | `-v dbdata:/var/lib/postgresql/data` | Managed by the engine: `/var/lib/docker/volumes/` (Docker), `/var/lib/containers/storage/volumes/` (rootful Podman), `~/.local/share/containers/storage/volumes/` (rootless Podman) | Databases and app data; survives `rm` of the container |
| **Bind mount** | `-v /srv/web/html:/usr/share/nginx/html:ro` (source starts with `/`) | Any host path you choose | Config files, source code, sharing host directories |
| **tmpfs** | `--tmpfs /run/cache` or `--mount type=tmpfs,destination=/run/cache` | RAM | Scratch data that must not hit disk |

The long form `--mount type=volume,source=dbdata,target=/data` (or `type=bind`) is more explicit and, unlike `-v`, errors out if a bind source does not exist instead of silently creating an empty directory. Add `:ro` (or `readonly` in `--mount`) to make a mount read-only. A `-v /data` with no source creates an **anonymous** volume with a random name.

```text
srv01$ podman volume create dbdata
srv01$ podman volume ls
DRIVER      VOLUME NAME
local       dbdata
srv01$ podman volume inspect dbdata --format '{{.Mountpoint}}'
/home/alice/.local/share/containers/storage/volumes/dbdata/_data
srv01$ podman run -d --name db -e POSTGRES_PASSWORD=change-me -v dbdata:/var/lib/postgresql/data docker.io/library/postgres:16
srv01$ podman volume rm dbdata          # fails while a container (even a stopped one) uses it
srv01$ docker volume prune              # Docker 23+: unused ANONYMOUS volumes only
srv01$ docker volume prune -a           # all unused volumes, named ones too
```

> **Watch out:** Prune behaviour has changed between versions. Since Docker 23, `docker volume prune` removes only anonymous volumes unless you add `-a`/`--all`, and `docker system prune` touches volumes only with `--volumes`. Check `--help` on the version in front of you before pruning on a server.

### SELinux context on bind mounts

On SELinux hosts (RHEL, Fedora), container processes run as `container_t` and can only use files labelled `container_file_t`. A bind mount of `/srv/web/html` (labelled, say, `var_t` or `httpd_sys_content_t`) gives **Permission denied** inside the container even though the Unix permissions are fine. The fix is a relabel option on the mount:

| Suffix | Effect |
|---|---|
| `:z` (lowercase) | Relabel with a **shared** label so **several** containers can use the content |
| `:Z` (uppercase) | Relabel with a **private** label for **this container only** (others are denied) |

```text
srv01$ podman run -d -p 8080:80 -v /srv/web/html:/usr/share/nginx/html:ro,Z docker.io/library/nginx:1.27
srv01$ ls -Zd /srv/web/html
system_u:object_r:container_file_t:s0:c214,c839 /srv/web/html
```

Never use `:Z` on system directories such as `/home` or `/etc`: relabelling them breaks other confined services. For those, disable separation for that one container with `--security-opt label=disable`. Named volumes are labelled correctly by the engine and need no suffix. `ausearch -m avc -ts recent` shows the denials (Domain 3). Docker honours `:z`/`:Z` too, when its SELinux support is enabled.

### Overlay

Overlay appears twice. First, the image and container storage itself is OverlayFS (`overlay2` in Docker, `overlay` in Podman's `/etc/containers/storage.conf`): image layers are the read-only **lower** directories and each container gets an **upper** directory for its changes. Second, Podman has an **overlay volume mount**, `-v /srv/cache:/var/cache:O`: the container sees the host directory and can write to it, but its writes go to a temporary upper layer and are discarded when the container stops, while the host directory stays unchanged. It is used, for example, to share a package cache read-mostly into build containers.

## Networking

### Port mapping

Containers on a bridge network get private addresses; to reach a service from outside, **publish** a port.

```text
srv01$ podman run -d -p 8080:80 nginx                 # host 8080 on all addresses -> container 80
srv01$ podman run -d -p 127.0.0.1:8443:443 nginx      # loopback only
srv01$ podman run -d -p 5353:53/udp dnsmasq-img       # UDP
srv01$ podman run -d -P nginx                         # every EXPOSEd port to a random high host port
srv01$ podman port <container>                        # show the mappings
```

The order is always **host:container**. `EXPOSE` in a Dockerfile only documents a port; without `-p` or `-P` nothing is published. Rootless containers cannot bind host ports below 1024 unless `net.ipv4.ip_unprivileged_port_start` is lowered. Docker publishes ports by inserting its own iptables/nftables NAT rules, which can bypass host firewall rules such as `ufw` that you expected to block them.

### Network types

| Driver | Behaviour | Typical use |
|---|---|---|
| **bridge** | Default. A virtual bridge (`docker0`, or `podman0` for Podman's default network) with NAT to the outside. **User-defined** bridges add DNS so containers reach each other by name | Most single-host apps |
| **host** | No network namespace: the container uses the host's interfaces and ports directly; `-p` is ignored | Maximum performance, or software that must see host interfaces |
| **none** | Only a loopback interface | Batch jobs that must have no network |
| **macvlan** | Each container gets its **own MAC address** on a host NIC's LAN and an address from that LAN | Containers that must look like physical hosts on the network. The host itself cannot reach its macvlan containers through the parent interface without extra configuration, and switches may limit MACs per port |
| **ipvlan** | Containers share the parent NIC's **MAC** but get their own IP addresses (L2 mode) or are routed (L3 mode) | Like macvlan where the switch or cloud provider allows only one MAC per port |
| **overlay** | A multi-host network over VXLAN tunnels between Docker hosts | **Docker Swarm** services spanning nodes (Kubernetes uses its own CNI plugins instead) |

```text
srv01$ docker network create --driver bridge appnet
srv01$ docker run -d --name api --network appnet app:1.4
srv01$ docker run -d --name web --network appnet -p 80:8080 nginx      # web reaches api at http://api:8080
srv01$ docker network create -d macvlan --subnet 10.0.30.0/24 --gateway 10.0.30.1 -o parent=eth0 lan30
srv01$ docker network create -d ipvlan --subnet 10.0.31.0/24 -o parent=eth0 -o ipvlan_mode=l2 lan31
srv01$ docker network ls
srv01$ docker network inspect appnet
srv01$ docker network prune                                             # remove networks no container uses
```

Podman uses the same commands (`podman network create`, `ls`, `inspect`, `prune`) with the netavark backend and supports bridge, macvlan and ipvlan. Rootless Podman containers do not get a real bridge on the host; their traffic goes through a user-mode network stack (`pasta` in Podman 5, `slirp4netns` before).

> **Exam tip:** Containers on the **default** `bridge` network in Docker cannot resolve each other by name; put them on a user-defined network. "Own MAC address on the physical LAN" is macvlan; "same MAC, different IPs" is ipvlan; "spans hosts" is overlay; "no isolation from the host network" is host.

## Privileged vs unprivileged

Two separate questions hide behind "privileged":

**1. Is the engine rootful or rootless?** Docker's daemon runs as root, and anyone who can use the Docker socket (members of the `docker` group) can start a container that mounts `/` from the host, so `docker` group membership is effectively root. **Rootless** Podman (or rootless Docker) runs everything as the normal user, using a **user namespace**: UID 0 inside the container maps to the user's own UID, and other container UIDs map to the subordinate ranges in **`/etc/subuid`** and **`/etc/subgid`** (for example `alice:100000:65536`). A container escape then lands as an unprivileged user. `podman unshare cat /proc/self/uid_map` shows the mapping.

**2. Does this container run with extra privileges?** By default an engine drops most Linux capabilities, applies a seccomp filter and an SELinux or AppArmor profile, and hides host devices. Root inside a default container is therefore much weaker than real root.

| Setting | Effect |
|---|---|
| `--privileged` | Gives **all** capabilities, access to all host devices, and disables seccomp and SELinux/AppArmor confinement. Needed for things like running a container engine inside a container; otherwise avoid it |
| `--cap-add NET_ADMIN`, `--cap-drop ALL` | Add or remove single capabilities: the least-privilege alternative to `--privileged` |
| `--user 1001:1001` / `USER` in the Dockerfile | Run the process as a non-root user **inside** the container |
| `--read-only` | Read-only root filesystem (pair with tmpfs mounts) |
| `--security-opt no-new-privileges` | Setuid binaries inside cannot raise privileges |
| `--device /dev/ttyUSB0` | Pass one device instead of all of them |

```text
srv01$ podman inspect web --format '{{.HostConfig.Privileged}} {{.Config.User}}'
false 1001
```

## Lab it yourself

In the lab VM, with Podman:

1. `podman volume create labvol; podman run --rm -v labvol:/data docker.io/library/alpine:3.20 sh -c 'echo hi > /data/f'`, then `podman run --rm -v labvol:/data docker.io/library/alpine:3.20 cat /data/f` (the data survived).
2. On the RPM-family lab VM (Rocky Linux or AlmaLinux, SELinux enforcing): `mkdir ~/web; echo ok > ~/web/index.html`; run nginx with `-v ~/web:/usr/share/nginx/html` (403 or permission denied), then with `:Z`, and compare `ls -Zd ~/web` before and after.
3. `podman network create labnet`; start two alpine containers on it and `ping` one from the other by name.
4. `podman run --rm --network none docker.io/library/alpine:3.20 ip a` (only `lo`) and `--network host` (the host's interfaces).
5. `grep $USER /etc/subuid`; `podman unshare cat /proc/self/uid_map`; `podman run --rm docker.io/library/alpine:3.20 id` (root inside), while `ps -o user,cmd -C sleep` on the host shows your own user for a container running `sleep`.
6. `podman run --rm docker.io/library/alpine:3.20 sh -c 'touch /tmp/x && chown nobody /tmp/x && echo ok'` (works: root in the container has `CAP_CHOWN`), then the same with `--cap-drop CHOWN` (Operation not permitted).

## Key takeaways

- Named volumes survive container removal; bind mounts map any host path; tmpfs lives in RAM; anonymous volumes come from `-v /path`.
- `volume create`, `ls`, `inspect`, `rm`, `prune`; in Docker 23+ `volume prune` needs `-a` to remove named volumes.
- On SELinux hosts, bind mounts need `:z` (shared) or `:Z` (private) or the container gets permission denied; never relabel system directories.
- Overlay is the layered storage driver, and Podman's `:O` gives a throwaway writable view of a host directory.
- `-p host:container`; `EXPOSE` publishes nothing; rootless engines cannot use host ports below 1024 by default.
- bridge (default, NAT; user-defined adds name resolution), host, none, macvlan (own MAC), ipvlan (shared MAC), overlay (multi-host, Swarm).
- Rootless engines map container root to the user via `/etc/subuid`; `docker` group membership equals root; `--privileged` removes almost all isolation, so prefer `--cap-add`, `--user` and `--read-only`.
