## PIDs, PPIDs and the process tree

Every process has a **PID** and a **PPID** (the PID of the parent that created it with `fork()`). PID 1 is `systemd`, the ancestor of everything in user space; kernel threads descend from `kthreadd` (PID 2) and show in brackets, such as `[kworker/0:1]`. If a parent exits first, its children are re-parented to PID 1 (or to a "subreaper" such as a `systemd --user` instance).

```text
srv01$ ps -o pid,ppid,user,stat,ni,%cpu,%mem,cmd -C nginx
    PID    PPID USER     STAT  NI %CPU %MEM CMD
   1412       1 root     Ss     0  0.0  0.1 nginx: master process /usr/sbin/nginx
   1413    1412 www-data S      0  0.2  0.4 nginx: worker process
   1414    1412 www-data S      0  0.1  0.4 nginx: worker process
srv01$ pstree -p 1412
nginx(1412)─┬─nginx(1413)
            └─nginx(1414)
```

`ps` has two option styles. **`ps aux`** (BSD style, no dash) and **`ps -ef`** (UNIX style) both list every process; `ps -eo pid,ppid,cmd --sort=-%mem` picks columns and sorts; `ps -u bob` and `ps -p 1412` filter. `pgrep -a nginx` finds PIDs by name. `pstree -p` draws the tree with PIDs.

## Process states

The `STAT` column (and `S` in `top`) uses one letter for the state, optionally followed by modifiers.

| Letter | State | Meaning |
|---|---|---|
| `R` | Running | On a CPU or ready to run |
| `S` | Sleeping (interruptible) | Waiting for an event, such as input or a timer; most processes |
| `D` | Uninterruptible sleep ("blocked") | Waiting in the kernel, usually on disk or NFS I/O. Signals, even KILL, are not acted on until it returns |
| `T` | Stopped | Paused by SIGSTOP or SIGTSTP (Ctrl+z); `t` is stopped by a debugger |
| `Z` | Zombie (defunct) | Has exited, but the parent has not yet read its exit status with `wait()` |
| `I` | Idle kernel thread | |

Modifiers: `s` session leader, `+` in the foreground process group, `<` high priority, `N` low priority (positive nice), `l` multi-threaded.

> **Exam tip:** A zombie uses no memory or CPU, only a process-table slot, and cannot be killed because it is already dead. Fix the **parent** (signal it so it reaps, or restart it); when the parent exits, PID 1 adopts and reaps the zombie. Many processes in `D` state point at storage or a hung NFS server, and they push the load average up without using CPU.

## Watching processes

| Tool | Use it for |
|---|---|
| `top` | Live view sorted by CPU. Keys: `P` CPU, `M` memory, `k` kill, `r` renice, `1` per-CPU, `q` quit. The summary shows load averages, task states and `%Cpu` broken into `us sy ni id wa hi si st` |
| `htop` | Friendlier `top` with a tree view (`F5`), search, and mouse support; usually a separate package |
| `atop` | Records system and per-process history to log files (`/var/log/atop/`) so you can replay what happened at 03:00 with `atop -r` |
| `mpstat -P ALL 2` | Per-CPU utilisation every 2 seconds (sysstat package); spots one pegged core |
| `pidstat -u -p 1412 2` | Per-process CPU every 2 seconds; `-r` memory, `-d` disk I/O (sysstat) |
| `lsof -p 1412` | Files, sockets and libraries a process has open |
| `strace -p 1412` | System calls a process is making right now; `strace -f -e trace=openat cmd` follows children and shows only file opens; `-c` prints a summary count |

> **Real world:** `wa` (I/O wait) high in `top` with idle CPUs means the bottleneck is storage, not CPU. `st` (steal) high on a VM means the hypervisor is giving your vCPUs to someone else.

### /proc/&lt;PID&gt;

Every process has a directory under `/proc`. The useful entries:

| Path | Contents |
|---|---|
| `/proc/1412/status` | Name, `State:`, `PPid:`, `Uid:`/`Gid:` (real, effective, saved, filesystem), `VmRSS:`, `Threads:` |
| `/proc/1412/cmdline` | Full command line, NUL-separated (`tr '\0' ' ' < /proc/1412/cmdline`) |
| `/proc/1412/environ` | Environment it started with (root or the owner only) |
| `/proc/1412/fd/` | Symlinks for each open file descriptor |
| `/proc/1412/cwd`, `exe` | Symlinks to the working directory and the executable |
| `/proc/1412/limits` | The resource limits actually in force |

## Priority: nice and renice

The Linux scheduler weighs normal processes by their **nice** value, from **-20** (highest priority) to **19** (lowest). The default is 0. `top` shows `PR` 20 for nice 0, because PR = 20 + NI for normal tasks.

```text
srv01$ nice -n 10 tar -czf /backup/home.tgz /home      # start at nice 10
srv01$ nice tar ...                                     # no -n means +10
srv01$ renice -n 5 -p 2210                              # change a running process
srv01# renice -n -5 -p 2210                             # negative: root only
srv01# renice -n 2 -u bob                               # all of bob's processes
```

Unprivileged users can only make their processes nicer (raise the value) and cannot lower it again, even back to where it was. Only root (strictly, `CAP_SYS_NICE`) can set negative values. Nice affects CPU only; for disk priority use `ionice`.

## Process limits

Per-process resource limits are set with **`ulimit`** (a bash builtin) and read from `/proc/<PID>/limits`. Each limit has a **soft** value (what is enforced; a user may raise it up to the hard value) and a **hard** ceiling (only root can raise it).

```text
srv01$ ulimit -n          # open files, soft
1024
srv01$ ulimit -Hn         # open files, hard
524288
srv01$ ulimit -u          # max user processes
srv01$ ulimit -a          # all
```

Persistent limits for login sessions go in **`/etc/security/limits.conf`** or `/etc/security/limits.d/*.conf` (applied by `pam_limits`):

```text
# <domain> <type> <item>  <value>
bob        soft   nofile  8192
bob        hard   nofile  65536
@webdev    hard   nproc   500
```

Services started by systemd do **not** read `limits.conf`; set `LimitNOFILE=` or `LimitNPROC=` in the unit (lesson 2.5).

## Job control

A **job** is a pipeline started from your interactive shell. Jobs belong to that shell and are listed by `jobs`.

| Action | Effect |
|---|---|
| `cmd &` | Start in the background; the shell prints `[1] 4321` (job number and PID) |
| Ctrl+c | Send **SIGINT** (2) to the foreground job, normally ending it |
| Ctrl+z | Send **SIGTSTP** (20) to the foreground job, stopping it (state `T`) |
| Ctrl+d | Not a signal: sends **end of file** on the terminal. A program reading stdin sees EOF; at an empty shell prompt it logs out |
| `jobs -l` | List jobs with PIDs; `+` is the current job, `-` the previous |
| `bg %1` | Resume stopped job 1 in the background (sends SIGCONT) |
| `fg %1` | Bring job 1 to the foreground |
| `kill %1` | Signal a job by job number |
| `nohup cmd &` | Ignore SIGHUP so the command survives logout; output goes to `nohup.out` if stdout is a terminal |
| `disown %1` | Remove a job from the shell's table so the shell will not send it SIGHUP |
| `exec cmd` | **Replace** the shell with `cmd` (same PID, no return). When `cmd` exits the session ends. `exec > file` without a command redirects the shell's own output |

```text
srv01$ sleep 600
^Z
[1]+  Stopped                 sleep 600
srv01$ bg %1
[1]+ sleep 600 &
srv01$ jobs -l
[1]+  4321 Running                 sleep 600 &
srv01$ fg %1
```

## Signals and killing processes

| Number | Name | Default action | Typical use |
|---|---|---|---|
| 1 | **SIGHUP** | Terminate | Terminal hung up; many daemons (nginx, sshd, rsyslog) re-read their configuration on HUP |
| 2 | SIGINT | Terminate | Ctrl+c |
| 9 | **SIGKILL** | Terminate, cannot be caught, blocked or ignored | Last resort; no cleanup, no flushing of buffers |
| 15 | **SIGTERM** | Terminate, can be caught | The **default** for `kill`; lets the program clean up |
| 18 / 19 / 20 | SIGCONT / SIGSTOP / SIGTSTP | Continue / stop (uncatchable) / stop (catchable) | Job control |

```text
srv01$ kill 2210                # SIGTERM
srv01$ kill -HUP 1412           # same as kill -1 1412 or kill -s HUP 1412
srv01$ kill -9 2210             # SIGKILL
srv01$ killall -u bob firefox   # by exact process name, here only bob's
srv01$ pkill -f 'python3 app.py'    # by pattern; -f matches the full command line
srv01$ kill -l                  # list signal names and numbers
```

`kill` takes PIDs (or `%job`), `killall` takes exact names, `pkill` takes patterns (same matching as `pgrep`, so test with `pgrep -a` first). The polite sequence is TERM, wait a few seconds, then KILL only if needed.

## Scheduling: at, cron and anacron

**`at`** runs a job **once** at a given time. `atd` must be running.

```text
srv01$ echo '/usr/local/bin/report.sh' | at 02:30 tomorrow
srv01$ at now + 15 minutes        # type commands, finish with Ctrl+d
srv01$ atq                        # list pending jobs
srv01$ atrm 7                     # remove job 7
```

`batch` runs a job when the load average drops. Access is controlled by `/etc/at.allow` (if it exists, only those listed may use `at`) and otherwise `/etc/at.deny`.

**cron** runs jobs **repeatedly**. `crontab -e` edits your table, `crontab -l` lists it, `crontab -r` removes it, and root can use `-u bob`. Each line has five time fields and a command:

```text
# min  hour  day-of-month  month  day-of-week   command
  30   2     *             *      *             /usr/local/bin/backup.sh
  */15 *     *             *      1-5           /usr/local/bin/poll.sh
  0    8     1             *      *             /usr/local/bin/monthly.sh
```

Day of week is 0-7 (0 and 7 are both Sunday). `*/15` means every 15. If both day-of-month and day-of-week are restricted, the job runs when **either** matches. System-wide tables are `/etc/crontab` and `/etc/cron.d/*`, which have an extra **user** field after the five time fields. Scripts dropped in `/etc/cron.hourly`, `cron.daily`, `cron.weekly` and `cron.monthly` are run by `run-parts`. `/etc/cron.allow` and `/etc/cron.deny` control who may use `crontab`. Cron jobs run with a minimal environment, so use absolute paths.

**anacron** is for machines that are not always on. It runs jobs that are due "once every N days" and catches up on missed runs at the next boot, keeping timestamps in `/var/spool/anacron/`. Its table, `/etc/anacrontab`, has four fields: **period in days** (or `@monthly`), **delay in minutes**, **job identifier**, **command**:

```text
1   5   cron.daily     run-parts --report /etc/cron.daily
7   10  cron.weekly    run-parts --report /etc/cron.weekly
```

Debian and Ubuntu run `cron.daily`, `weekly` and `monthly` through anacron when it is installed; RHEL's `cronie-anacron` does the same from `/etc/cron.hourly/0anacron`. systemd timers (lesson 2.5) are the modern alternative to all three.

## Lab it yourself

In a terminal on the lab VM:

1. `sleep 1000 &`, `jobs -l`, `ps -o pid,ppid,stat,cmd -p $!`, `fg`, Ctrl+z, `ps -o stat -p <PID>` (shows `T`), `bg`, `kill %1`.
2. `nice -n 15 sleep 500 &`, `ps -o pid,ni,cmd -p $!`, `renice -n 5 -p $!` (fails as a normal user), `renice -n 19 -p $!` (works).
3. `cat /proc/$$/status | grep -E 'State|PPid|Uid'` and `ls -l /proc/$$/fd`.
4. `strace -c ls /` and `strace -e trace=openat cat /etc/hostname`.
5. Create a zombie: `bash -c 'sleep 1 & exec sleep 60' &` and after a second run `ps -el | grep defunct`. (The `exec` replaces the parent with a program that never calls `wait()`.)
6. `ulimit -n; ulimit -n 512; ulimit -n` then try `ulimit -n 4096` beyond the hard limit.
7. `crontab -e` with `* * * * * date >> /tmp/cron.txt`, wait two minutes, `crontab -r`. `echo 'touch /tmp/at-ok' | at now + 1 minute; atq`.

## Key takeaways

- PID 1 is systemd; orphans are re-parented to it; `ps -ef`, `ps aux`, `ps -o`, `pstree -p` and `pgrep` show the tree.
- States: R running, S sleeping, D uninterruptible (blocked on I/O), T stopped, Z zombie (exited, not reaped; fix the parent).
- `top`, `htop`, `atop`, `mpstat`, `pidstat`, `lsof`, `strace` and `/proc/<PID>/` answer "what is it doing?"
- Nice runs from -20 (most favoured) to 19; users can only raise it; root can lower it.
- `ulimit` soft and hard limits; persist with `/etc/security/limits.conf` for logins and `Limit*=` for systemd services.
- `&`, Ctrl+z, `bg`, `fg`, `jobs`; Ctrl+c is SIGINT; Ctrl+d is EOF; `nohup` survives logout; `exec` replaces the shell.
- Signal 1 HUP (often reload), 9 KILL (uncatchable), 15 TERM (default, graceful); `kill` by PID, `killall` by name, `pkill` by pattern.
- `at` runs once, cron repeats on a five-field schedule, anacron catches up on daily/weekly jobs missed while the machine was off.
