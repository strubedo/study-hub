## Units and where they live

systemd manages everything as **units**: plain-text files named `name.type`. The exam names four types; you will also see `.socket`, `.path`, `.slice` and `.device`.

| Type | What it describes |
|---|---|
| `.service` | A daemon or one-shot command |
| `.timer` | When to start another unit (usually the `.service` of the same name); replaces cron jobs |
| `.mount` / `.automount` | A filesystem mount. Generated from `/etc/fstab` at boot, or written by hand |
| `.target` | A named group of units used as a synchronisation point: `multi-user.target`, `graphical.target`, `network-online.target`, `rescue.target` |

Unit files are read from three places, highest priority first:

| Directory | Purpose |
|---|---|
| `/etc/systemd/system/` | **Administrator** units and overrides. Yours |
| `/run/systemd/system/` | Runtime units (lost at reboot) |
| `/usr/lib/systemd/system/` (`/lib/systemd/system/` on older Debian) | Units shipped by **packages**. Do not edit; upgrades overwrite them |

A **drop-in** is a `.conf` file in `/etc/systemd/system/<unit>.d/` that overrides only the settings it lists. `systemctl cat <unit>` shows the file and every drop-in in effect.

## A service unit

```text
srv01$ systemctl cat app.service
# /etc/systemd/system/app.service
[Unit]
Description=Example application
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=svc_app
WorkingDirectory=/opt/app
EnvironmentFile=-/etc/sysconfig/app
ExecStart=/opt/app/bin/app --port 8080
ExecReload=/bin/kill -HUP $MAINPID
Restart=on-failure
RestartSec=5
LimitNOFILE=65536

[Install]
WantedBy=multi-user.target
```

- `[Unit]`: description and ordering. **`After=`/`Before=`** only order; **`Wants=`** (soft) and **`Requires=`** (hard) pull another unit in. You usually need both an ordering and a requirement.
- `[Service]`: `Type=` (`simple` default, `forking` for daemons that background themselves, `oneshot` for a command that exits, `notify` for daemons that signal readiness), `ExecStart=`, `User=`, `Restart=`, environment and limits.
- `[Install]`: used only by `systemctl enable`. `WantedBy=multi-user.target` makes enable create the symlink `/etc/systemd/system/multi-user.target.wants/app.service`.

## Unit states and the systemctl verbs

| Command | Effect | Survives reboot? |
|---|---|---|
| `systemctl start app` / `stop app` | Start or stop now | No |
| `systemctl restart app` | Stop then start (drops connections) | No |
| `systemctl reload app` | Ask the running process to re-read its config (`ExecReload=`), no downtime. Fails if the unit has no reload support | No |
| `systemctl reload-or-restart app` | Reload if supported, else restart | No |
| `systemctl enable app` / `disable app` | Create or remove the `[Install]` symlinks so it starts (or not) at boot. Add `--now` to also start or stop it | Yes |
| `systemctl mask app` | Link the unit to `/dev/null` in `/etc/systemd/system/`; it cannot be started at all, manually or as a dependency | Yes |
| `systemctl unmask app` | Remove that link | Yes |
| `systemctl status app` | State, main PID, cgroup, last log lines | |
| `systemctl edit app` | Open a drop-in (`/etc/systemd/system/app.service.d/override.conf`) in the editor and reload systemd when you save. `--full` edits a full copy of the unit in `/etc/systemd/system/` | Yes |
| `systemctl daemon-reload` | Re-read all unit files after you change them by hand | |

```text
srv01$ systemctl status app
● app.service - Example application
     Loaded: loaded (/etc/systemd/system/app.service; enabled; preset: disabled)
    Drop-In: /etc/systemd/system/app.service.d
             └─override.conf
     Active: active (running) since Sun 2026-11-22 09:14:02 UTC; 3min ago
   Main PID: 2211 (app)
      Tasks: 6 (limit: 22950)
     Memory: 38.4M
        CPU: 1.204s
     CGroup: /system.slice/app.service
             └─2211 /opt/app/bin/app --port 8080
```

The `Loaded:` line answers "is it enabled?" and "which file?"; `Active:` answers "is it running?". **Enabled** and **active** are independent: a unit can run now but not start at boot (`active`, `disabled`), or be enabled but currently dead. `systemctl is-active`, `is-enabled` and `is-failed` give one-word answers for scripts. Other states you will see: `failed` (exited with an error; `systemctl reset-failed` clears it), `static` (no `[Install]` section, so it can only be started as a dependency), `masked`.

> **Watch out:** If you edit a unit file directly (not with `systemctl edit`), systemd keeps using the old version, and `systemctl` warns that the unit file "changed on disk" and tells you to "Run 'systemctl daemon-reload' to reload units." Run `systemctl daemon-reload` and then restart the service. `daemon-reload` does not restart anything by itself.

Overriding a vendor unit safely:

```text
srv01# systemctl edit nginx
### Editing /etc/systemd/system/nginx.service.d/override.conf
[Service]
Restart=always
LimitNOFILE=100000
```

To **clear** a list setting such as `ExecStart=` in a drop-in, first assign it empty (`ExecStart=`) and then set the new value.

Targets replace runlevels: `systemctl get-default`, `systemctl set-default multi-user.target` (boot to text mode), `systemctl isolate rescue.target` (switch now). Logs come from the journal: `journalctl -u app -f`, `journalctl -u app --since "1 hour ago"`, `journalctl -b -p err`.

## Timers

A timer starts its matching service on a schedule.

```text
# /etc/systemd/system/backup.timer
[Unit]
Description=Nightly backup

[Timer]
OnCalendar=*-*-* 02:30:00
Persistent=true
RandomizedDelaySec=10m

[Install]
WantedBy=timers.target
```

`OnCalendar=` takes calendar expressions (`daily`, `Mon..Fri 08:00`, `*-*-01 00:00:00`); test one with `systemd-analyze calendar 'Mon..Fri 08:00'`. **`Persistent=true`** runs a missed job at the next boot, like anacron. Monotonic timers count from an event instead: `OnBootSec=5min`, `OnUnitActiveSec=1h`. Enable the **timer**, not the service: `systemctl enable --now backup.timer`; `systemctl list-timers` shows the next and last run. Advantages over cron: output goes to the journal, dependencies and resource limits apply, and runs can be randomised to avoid every host hitting a server at once.

## Mount units

A mount unit's name must be the mount point path with `/` turned into `-`: `/srv/data` is `srv-data.mount` (`systemd-escape -p --suffix=mount /srv/data` prints it).

```text
# /etc/systemd/system/srv-data.mount
[Unit]
Description=Data volume

[Mount]
What=/dev/vg_data/lv_data
Where=/srv/data
Type=xfs
Options=defaults,noatime

[Install]
WantedBy=multi-user.target
```

Entries in `/etc/fstab` become mount units automatically (generated by `systemd-fstab-generator`), which is why you run `systemctl daemon-reload` after editing `fstab`.

## The systemd utilities

| Command | Purpose |
|---|---|
| `hostnamectl` | Show the hostname, OS, kernel and hardware. `hostnamectl set-hostname web01.example.com` writes `/etc/hostname` (static), and there are also transient and `--pretty` names |
| `timedatectl` | Show local time, UTC, RTC, time zone and whether NTP is synchronised. `set-timezone America/Chicago`, `list-timezones`, `set-ntp true`, `set-time` (only with NTP off) |
| `resolvectl` | Client for **systemd-resolved**: `resolvectl status` (per-link DNS servers and domains), `resolvectl query www.example.com`, `resolvectl flush-caches`, `resolvectl statistics`, `resolvectl dns eth0 10.0.10.53` (runtime only) |
| `systemd-resolved` | The local caching stub resolver, listening on **127.0.0.53**. With it, `/etc/resolv.conf` is a symlink to `/run/systemd/resolve/stub-resolv.conf` containing `nameserver 127.0.0.53`; real upstream servers come from NetworkManager, Netplan or `/etc/systemd/resolved.conf`. Default on Ubuntu; optional on RHEL |
| `sysctl` | Read and set kernel parameters under `/proc/sys`: `sysctl net.ipv4.ip_forward`, `sysctl -w net.ipv4.ip_forward=1` (runtime). Persist in `/etc/sysctl.d/90-local.conf` and apply with `sysctl --system` (all files) or `sysctl -p <file>`. Strictly a procps tool, but `systemd-sysctl.service` applies the files at boot |
| `systemd-analyze` | Boot timing: total time split into firmware, loader, kernel and userspace |
| `systemd-analyze blame` | Units sorted by how long they took to start |
| `systemd-analyze critical-chain` | The chain of units that actually delayed reaching the default target |
| `systemd-analyze verify app.service` | Lint a unit file |

```text
srv01$ systemd-analyze
Startup finished in 2.118s (kernel) + 1.904s (initrd) + 9.731s (userspace) = 13.754s
multi-user.target reached after 9.702s in userspace.
srv01$ systemd-analyze blame | head -4
6.012s NetworkManager-wait-online.service
1.204s dnf-makecache.service
  842ms app.service
  611ms chronyd.service
```

> **Exam tip:** `blame` shows how long each unit took, but units start in parallel, so the slowest unit is not necessarily what delayed boot. `critical-chain` shows the real bottleneck. A long `*-wait-online.service` is the classic slow-boot culprit.

## Lab it yourself

In the lab VM (or, inside it, a container image that runs systemd, such as `podman run -d --name sd registry.access.redhat.com/ubi9/ubi-init`):

1. Create `/etc/systemd/system/hello.service` with `ExecStart=/bin/sh -c 'while true; do echo hi; sleep 10; done'`, `[Install] WantedBy=multi-user.target`; `systemctl daemon-reload; systemctl enable --now hello; systemctl status hello; journalctl -u hello -n 5`.
2. `systemctl edit hello` and add `Restart=always`; check with `systemctl cat hello`. `kill -9` the main PID and watch it come back.
3. `systemctl mask hello`, try `systemctl start hello`, then `unmask`.
4. Write `hello-once.service` (`Type=oneshot`) and `hello-once.timer` with `OnCalendar=*:0/2`; `systemctl enable --now hello-once.timer; systemctl list-timers`.
5. `systemd-analyze blame | head`, `systemd-analyze critical-chain`, `systemd-analyze calendar weekly`.
6. `hostnamectl`, `timedatectl`, `resolvectl status`, `sysctl net.ipv4.ip_forward`.

## Key takeaways

- Unit types: `.service`, `.timer`, `.mount`, `.target`; admin files in `/etc/systemd/system/` override package files in `/usr/lib/systemd/system/`.
- `start`/`stop`/`restart`/`reload` act now; `enable`/`disable` act at boot (`--now` does both); `mask` blocks every start.
- `systemctl edit` creates a drop-in and reloads automatically; after hand edits run `systemctl daemon-reload`.
- Enabled and active are independent; `status` shows both; `static` units have no `[Install]` section.
- Timers use `OnCalendar=` and `Persistent=true`; enable the `.timer`; mount unit names mirror the path.
- `hostnamectl`, `timedatectl`, `resolvectl` (systemd-resolved on 127.0.0.53) and `sysctl` (`/etc/sysctl.d/`, `sysctl --system`).
- `systemd-analyze`, `blame` and `critical-chain` diagnose slow boots.
