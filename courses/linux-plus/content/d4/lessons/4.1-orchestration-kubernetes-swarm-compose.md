## What orchestration adds to containers

Lesson 2.6 ran single containers with `podman run` and `docker run`. That works for one host. **Orchestration** runs many containers across many hosts and keeps them running: it schedules containers onto nodes, restarts or replaces failed ones, keeps a requested number of copies (**replicas**), gives them stable network names and load balancing, rolls out new versions gradually, and injects configuration and secrets. You declare the desired state ("three copies of web:1.4 behind port 80") and the orchestrator continuously reconciles toward it, the same declarative idea as IaC.

| Tool | Scope |
|---|---|
| **Docker/Podman Compose** | Several related containers on **one host**, described in one YAML file |
| **Docker Swarm** | Docker's built-in clustering: services across a few to dozens of Docker hosts |
| **Kubernetes** | The industry-standard orchestrator for clusters of any size (OpenShift, EKS, AKS, GKE, k3s are all Kubernetes) |

## Kubernetes

A cluster has a **control plane** (API server, etcd key-value store, scheduler, controller manager) and **worker nodes**, each running the **kubelet** agent and a container runtime such as containerd or CRI-O. You talk to the API server with **`kubectl`**, usually by applying YAML **manifests**.

| Object | Purpose |
|---|---|
| **Pod** | The smallest deployable unit: one or more containers that share a network namespace (one IP, talk over `localhost`) and can share volumes. Pods are disposable and get a new IP when recreated |
| **Deployment** | Declares a Pod template and a replica count. It manages a ReplicaSet that keeps that many Pods running, and performs rolling updates and rollbacks (`kubectl rollout undo`) |
| **Service** | A stable virtual IP and DNS name (`web.default.svc.cluster.local`) that load-balances to the Pods matching a **label selector**. Types: **ClusterIP** (default, inside the cluster), **NodePort** (a port 30000-32767 on every node), **LoadBalancer** (an external load balancer from the cloud provider) |
| **ConfigMap** | Non-confidential key-value configuration, injected as environment variables or mounted as files |
| **Secret** | Small confidential values (passwords, tokens, TLS keys), injected the same ways |
| **Volume** | Storage attached to a Pod: `emptyDir` (scratch space that lives as long as the Pod), `configMap`/`secret` (files from those objects), `hostPath` (a node directory, avoid), and `persistentVolumeClaim` (durable storage that outlives Pods) |
| **Namespace** | A name scope for objects, used to separate teams or environments |

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: web-config
data:
  LOG_LEVEL: info
---
apiVersion: v1
kind: Secret
metadata:
  name: db-cred
type: Opaque
data:
  password: UzNjcmV0UGFzcw==
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
        - name: web
          image: registry.example.com/web:1.4
          ports:
            - containerPort: 8080
          env:
            - name: LOG_LEVEL
              valueFrom:
                configMapKeyRef:
                  name: web-config
                  key: LOG_LEVEL
            - name: DB_PASSWORD
              valueFrom:
                secretKeyRef:
                  name: db-cred
                  key: password
          volumeMounts:
            - name: cache
              mountPath: /var/cache/web
      volumes:
        - name: cache
          emptyDir: {}
---
apiVersion: v1
kind: Service
metadata:
  name: web
spec:
  type: ClusterIP
  selector:
    app: web
  ports:
    - port: 80
      targetPort: 8080
```

**Variables** reach containers three ways: literal `env` entries (`name:` and `value:`), `valueFrom` with `configMapKeyRef` or `secretKeyRef` for single keys, and `envFrom` with `configMapRef` or `secretRef` to import every key of an object at once. Environment variables are read when the container starts, so changing a ConfigMap does not change the variables of running Pods; restart them (`kubectl rollout restart deployment/web`). ConfigMaps mounted as volumes are updated in place after a short delay.

```text
alice@srv01:~$ kubectl apply -f web.yaml
alice@srv01:~$ kubectl get pods -o wide
alice@srv01:~$ kubectl describe pod web-<id>                 # events: image pulls, scheduling, crashes
alice@srv01:~$ kubectl logs deployment/web
alice@srv01:~$ kubectl scale deployment/web --replicas=5
alice@srv01:~$ kubectl create configmap web-config --from-literal=LOG_LEVEL=debug --dry-run=client -o yaml
alice@srv01:~$ kubectl create secret generic db-cred --from-literal=password='S3cretPass'
alice@srv01:~$ kubectl get secret db-cred -o jsonpath='{.data.password}' | base64 -d
S3cretPass
```

> **Watch out:** The `data` values of a Secret are only **base64-encoded**, which is an encoding, not encryption: `echo UzNjcmV0UGFzcw== | base64 -d` prints `S3cretPass`. By default Secrets are stored **unencrypted in etcd**, and anyone who can read Secrets in a namespace, or create Pods there, can see them. Protect them with RBAC, enable encryption at rest (an `EncryptionConfiguration` on the API server, or a cloud KMS), and keep real values out of Git (Sealed Secrets, External Secrets Operator, Vault). `stringData` lets you write plain values in a manifest, which the API server encodes for you.

## Docker Swarm

**Swarm mode** is built into Docker Engine. `docker swarm init` turns a host into the first **manager**; others join with the token it prints.

| Term | Meaning |
|---|---|
| **Node** | A Docker host in the swarm. **Manager** nodes keep the cluster state with the **Raft** consensus protocol and schedule work; **worker** nodes run tasks. Managers also run tasks by default. Use an odd number of managers (3 or 5) so a majority survives a failure |
| **Service** | The desired state: image, replica count, published ports, networks. **Replicated** services run N copies; **global** services run one copy on every node |
| **Task** | One container of a service, assigned to a node. Tasks do not move: if a node fails, the manager starts replacement tasks elsewhere |
| **Overlay network** | A multi-host network (VXLAN, lesson 2.6) connecting a service's tasks across nodes. The built-in **ingress** overlay provides the **routing mesh**: a published port answers on every node and forwards to a running task |
| **Scale** | Changing the replica count: `docker service scale web=5` or `docker service update --replicas 5 web` |
| **Stack** | A group of services deployed from a Compose file: `docker stack deploy -c compose.yaml app` |

```text
mgr01# docker swarm init --advertise-addr 10.0.10.11
mgr01# docker swarm join-token worker                      # prints the docker swarm join command for workers
mgr01# docker node ls
mgr01# docker network create -d overlay app_net
mgr01# docker service create --name web --replicas 3 -p 8080:80 --network app_net docker.io/library/nginx:1.27
mgr01# docker service ls
mgr01# docker service ps web                                # lists the tasks and the node each runs on
mgr01# docker service scale web=5
```

## Docker Compose and Podman Compose

**Compose** describes a multi-container application on one host: services, networks and volumes. The preferred file name is **`compose.yaml`** (`compose.yml`, `docker-compose.yaml` and `docker-compose.yml` are also found). Checked with `docker compose config`:

```yaml
services:
  web:
    image: docker.io/library/nginx:1.27
    ports:
      - "8080:80"
    depends_on:
      - db
    restart: unless-stopped
  db:
    image: docker.io/library/postgres:16
    environment:
      POSTGRES_PASSWORD_FILE: /run/secrets/db_password
    volumes:
      - dbdata:/var/lib/postgresql/data
    secrets:
      - db_password

volumes:
  dbdata:

secrets:
  db_password:
    file: ./db_password.txt
```

Compose creates a project network (`<project>_default`) on which services reach each other by service name, so `web` connects to the database at host `db`. The top-level **`version:`** key is obsolete; current Compose ignores it with a warning ("the attribute `version` is obsolete").

| Command | Effect |
|---|---|
| `docker compose up -d` | Create the network and volumes, pull or build images, start every service in the background |
| `docker compose ps` | Containers of this project |
| `docker compose logs -f web` | Follow the logs of one service (all services without a name) |
| `docker compose down` | Stop and **remove** the containers and the project network. Named volumes are **kept** |
| `docker compose down -v` | Also remove the named volumes (the database data above) |
| `docker compose up -d --build` | Rebuild images from `build:` contexts first |

Versions matter on the exam and in real life:

- **`docker-compose`** (hyphen) is the legacy **Compose v1**, a separate Python program. It is end of life and no longer updated.
- **`docker compose`** (space) is the Go **CLI plugin** introduced as Compose v2 and current today (current releases report versions such as `Docker Compose version v5.6.1`). Same file format, same subcommands.
- **`podman compose`** is a thin wrapper in Podman that runs an external provider, **`docker-compose`** if installed, otherwise **`podman-compose`** (a separate Python project), and points it at the Podman socket. **`podman kube play`** runs Kubernetes Pod and Deployment YAML directly on Podman, and `podman kube generate` writes YAML from running containers.

> **Exam tip:** Match scope to tool: one host and a few related containers is Compose; built into Docker with services, tasks and a routing mesh is Swarm; Pods, Deployments, Services, ConfigMaps and Secrets is Kubernetes.

## Lab it yourself

1. In the lab VM with Docker CE (or Podman with `podman-compose`), save the Compose file above, create `db_password.txt`, and run `docker compose config`, `up -d`, `ps` and `logs db`. Then `down` and `docker volume ls` (volume still there), and `down -v` (gone).
2. Add `version: "3.8"` at the top of the file and run `docker compose config` to see the obsolete-attribute warning.
3. `docker swarm init`, then create the nginx service above, `docker service ps web`, `docker rm -f` one of its containers, and watch `docker service ps web` start a replacement task. Finish with `docker swarm leave --force`.
4. In the lab VM, install a single-node Kubernetes (k3s, kind or minikube), apply the manifest above with a public image such as `docker.io/library/nginx:1.27` and `containerPort: 80`, run `kubectl exec deploy/web -- env | grep -E 'LOG_LEVEL|DB_PASSWORD'`, and decode the Secret with `base64 -d`.

## Key takeaways

- Orchestrators keep declared state: replicas, restarts, rolling updates, service discovery and injected configuration.
- Kubernetes: Pods (shared network, disposable), Deployments (replicas, rollouts), Services (stable IP/DNS; ClusterIP, NodePort, LoadBalancer), ConfigMaps, Secrets, Volumes (emptyDir, PVC), variables through `env`, `valueFrom` and `envFrom`.
- Secrets are base64-encoded, not encrypted, and stored unencrypted in etcd unless encryption at rest is configured.
- Swarm: manager and worker nodes (Raft), services made of tasks, overlay networks and the ingress routing mesh, `docker service scale`.
- Compose: `compose.yaml` with services, volumes, networks; `up -d`, `logs -f`, `down` (keeps named volumes), `down -v`; `docker compose` replaces legacy `docker-compose`; `podman compose` wraps a provider.
