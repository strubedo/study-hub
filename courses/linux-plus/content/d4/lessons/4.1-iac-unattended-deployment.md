## Why automate, and what "infrastructure as code" means

Configuring one server by hand is fine. Configuring fifty the same way, every time, after every rebuild, is not: people skip steps, servers drift apart, and nobody can say exactly what changed last Tuesday. **Infrastructure as code (IaC)** describes servers, packages, files, users and cloud resources in text files that live in version control (Git, lesson 4.4). A tool reads those files and makes reality match them.

Three ideas recur in every IaC tool and on the exam:

| Idea | Meaning |
|---|---|
| **Declarative** | You describe the end state ("nginx installed and running"), not the steps. The tool works out what to do |
| **Idempotent** | Running the same code twice gives the same result; the second run changes nothing because the state already matches |
| **Desired state / drift** | The code is the source of truth. Anything changed by hand on the server is drift, and the next run puts it back |

Two families of tool cover different layers. **Configuration management** (Ansible, Puppet) configures the operating system inside machines that already exist. **Provisioning** (OpenTofu, Terraform) creates the machines, networks and other resources themselves by calling a cloud or virtualization **API**. Unattended installers (Kickstart, cloud-init) sit between them and get a fresh system to the point where configuration management can take over.

## Ansible

Ansible is **agentless**: the control node connects to each managed host over **SSH** (WinRM for Windows), copies small Python modules across, runs them and removes them. Managed Linux hosts need only `sshd` and Python; nothing is installed or left running. Ansible pushes changes when you run it, so there is no schedule unless you add one (cron, a CI pipeline, or AWX / Red Hat Ansible Automation Platform).

| Term | Meaning |
|---|---|
| **Inventory** | The list of managed hosts and groups, in INI or YAML (`/etc/ansible/hosts` by default, usually a project file passed with `-i`). Can also be dynamic, generated from a cloud API |
| **Module** | A unit of work: `ansible.builtin.package`, `dnf`, `apt`, `copy`, `template`, `service`, `user`, `file`, `command`, `shell` |
| **Task** | One call to a module with arguments |
| **Playbook** | A YAML file of **plays**; each play maps a host group to a list of tasks |
| **Handler** | A task that runs only when notified by a task that **changed** something (for example, reload nginx after its config changed) |
| **Facts** | Data gathered from each host at the start of a play (`ansible.builtin.setup`): OS family, IPs, memory, disks. Read as `ansible_facts['os_family']` |
| **Collection** | A distribution package of modules, plugins and roles, named `namespace.collection` (`ansible.builtin`, `community.general`, `ansible.posix`). Install with `ansible-galaxy collection install community.general` |
| **Ad hoc command** | A single module run from the command line, without a playbook |

An inventory and a playbook (checked with `ansible-playbook --syntax-check` and ansible-core 2.22):

```text
# inventory.ini
[web]
web01.example.com
web02.example.com

[db]
db01.example.com ansible_user=svc_ansible

[prod:children]
web
db
```

```yaml
---
- name: Configure web servers
  hosts: web
  become: true
  vars:
    http_port: 8080
  tasks:
    - name: Install nginx
      ansible.builtin.package:
        name: nginx
        state: present

    - name: Deploy site configuration
      ansible.builtin.template:
        src: templates/site.conf.j2
        dest: /etc/nginx/conf.d/site.conf
        mode: "0644"
      notify: Reload nginx

    - name: Start and enable nginx
      ansible.builtin.service:
        name: nginx
        state: started
        enabled: true

  handlers:
    - name: Reload nginx
      ansible.builtin.service:
        name: nginx
        state: reloaded
```

`become: true` uses sudo on the managed host. `ansible.builtin.package` picks dnf or apt from the facts, so the same task works on both families. The template uses **Jinja2** (`listen {{ http_port }};`).

```text
alice@srv01:~$ ansible web -i inventory.ini -m ansible.builtin.ping          # ad hoc: can we log in and run Python?
alice@srv01:~$ ansible all -i inventory.ini -m ansible.builtin.setup -a 'filter=ansible_os_family'
alice@srv01:~$ ansible db -i inventory.ini -b -m ansible.builtin.dnf -a 'name=chrony state=latest'
alice@srv01:~$ ansible-playbook -i inventory.ini site.yml --check --diff     # dry run, show changes
alice@srv01:~$ ansible-playbook -i inventory.ini site.yml
```

> **Exam tip:** "Agentless, YAML playbooks, push over SSH" is Ansible. A recap line of `changed=0` on a second run is idempotency in action. Prefer real modules over `command`/`shell`: those always report "changed" and are not idempotent unless you add `creates:` or `changed_when:`.

## Puppet

Puppet is the classic **agent-based**, **pull** model. A `puppet` agent runs on every node (a systemd service, every **30 minutes** by default), sends its **facts** to the **Puppet server** on TCP **8140**, receives a **catalog** compiled for that node, and applies it. Trust between agent and server is built on **certificates**: on its first run the agent creates a key pair and sends a certificate signing request, and the server's built-in CA must sign it (manually or through autosigning) before the node gets a catalog.

```text
web01# puppet agent --test                                   # -t: run once now, verbose
srv01# puppetserver ca list                                  # pending CSRs
srv01# puppetserver ca sign --certname web01.example.com
web01# facter os.family                                      # Facter supplies the facts
RedHat
```

Code is written in Puppet's own declarative language (`.pp` manifests). A **resource** (`package`, `file`, `service`, `user`) is the basic unit; a **class** groups resources; a **module** is a directory of classes, files and templates, shared on the Puppet Forge (`puppet module install puppetlabs-stdlib`):

```text
class profile::chrony {
  package { 'chrony':
    ensure => installed,
  }
  file { '/etc/chrony.conf':
    ensure  => file,
    source  => 'puppet:///modules/profile/chrony.conf',
    require => Package['chrony'],
    notify  => Service['chronyd'],
  }
  service { 'chronyd':
    ensure => running,
    enable => true,
  }
}

node 'web01.example.com' {
  include profile::chrony
}
```

Puppet can also work **without** an agent-server pair: `puppet apply site.pp` compiles and applies a manifest locally, and **Bolt** runs commands, scripts, tasks and plans over SSH or WinRM with no agent installed, much like Ansible ad hoc commands.

> **Real world:** In late 2024 Perforce stopped publishing open-source Puppet packages publicly and moved further development to internal forks. The community fork **OpenVox** (Vox Pupuli) continues the open-source code with the same language and commands. The concepts above apply to both.

## OpenTofu

**OpenTofu** is the open-source (MPL 2.0, Linux Foundation) **fork of Terraform**, created in 2023 after HashiCorp moved Terraform to the Business Source License. It reads the same **HCL** language, the same providers and the same state format as Terraform 1.5, and its CLI is `tofu` instead of `terraform`.

| Term | Meaning |
|---|---|
| **Provider** | A plugin that talks to one platform's **API** (AWS, Azure, libvirt, Proxmox, DNS, Kubernetes) and turns resource blocks into API calls |
| **Resource** | One managed object: a VM, network, DNS record or bucket |
| **State** | A JSON record of what OpenTofu created and the real IDs behind each resource (`terraform.tfstate` locally, or a remote backend with locking). It lets OpenTofu compute a diff. It often contains secrets, so protect it and never commit it to Git |

```text
terraform {
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"
    }
  }
}

provider "aws" {
  region = "us-east-2"
}

resource "aws_instance" "web" {
  ami           = "ami-0abcdef1234567890"
  instance_type = "t3.micro"
  tags = {
    Name = "web01"
  }
}
```

The workflow: `tofu init` (download providers, set up the backend), `tofu plan` (compare code with state and reality, show `+` create, `~` change, `-` destroy), `tofu apply` (make the changes and update the state) and `tofu destroy`. The `terraform {}` block name is kept for compatibility.

## Unattended deployment: Kickstart and cloud-init

**Kickstart** automates the Anaconda installer on RHEL, Fedora, Rocky and Alma. A Kickstart file answers every installer question. Anaconda writes the answers of each manual install to **`/root/anaconda-ks.cfg`**, a handy starting point, and **`ksvalidator`** (package `pykickstart`) checks a file before you use it. Point the installer at it with the boot option **`inst.ks=`** (HTTP, NFS, a local disk or a labelled volume), typically from a PXE menu (lesson 1.1):

```text
# web.ks (ksvalidator -v RHEL9 web.ks: no errors)
text
lang en_US.UTF-8
keyboard us
timezone America/Chicago --utc
network --bootproto=dhcp --hostname=web01.example.com --activate
rootpw --lock
user --name=alice --groups=wheel --iscrypted --password=$6$examplesalt$examplehash
zerombr
clearpart --all --initlabel
autopart --type=lvm
selinux --enforcing
firewall --enabled --service=ssh
reboot

%packages
@^minimal-environment
nginx
%end

%post --log=/root/ks-post.log
systemctl enable nginx
%end
```

Sections such as `%packages`, `%pre` and `%post` must end with `%end`. Debian uses **preseed** files and Ubuntu Server uses **autoinstall** (YAML, read by the Subiquity installer) for the same job.

**cloud-init** customises a cloud or VM image on its **first boot**. The platform supplies **user data** through a **datasource** (cloud metadata service, or a `NoCloud` ISO with `user-data` and `meta-data` files for local VMs). A cloud-config file must begin with the line **`#cloud-config`**:

```yaml
#cloud-config
hostname: web01
package_update: true
packages:
  - nginx
users:
  - name: alice
    sudo: "ALL=(ALL) NOPASSWD:ALL"
    shell: /bin/bash
    lock_passwd: true
    ssh_authorized_keys:
      - ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIExampleKeyOnly alice@example.com
write_files:
  - path: /etc/motd
    content: "Managed by cloud-init\n"
    permissions: "0644"
runcmd:
  - systemctl enable --now nginx
```

Check progress and errors with `cloud-init status --wait` (or `--long`), validate a file with `cloud-init schema -c user-data.yaml`, and read `/var/log/cloud-init.log` and `/var/log/cloud-init-output.log`. Most modules run once per instance, so editing user data on a running VM does nothing until cloud-init is reset (`cloud-init clean`) or a new instance is built.

| | Kickstart | cloud-init |
|---|---|---|
| When | During OS **installation** | On **first boot** of an already-installed image |
| Where | Anaconda (RHEL family) | Almost every cloud image, all major distributions |
| Typical delivery | `inst.ks=` boot option, PXE | Cloud metadata, NoCloud ISO |
| Format | Kickstart commands plus `%sections` | YAML starting with `#cloud-config` |

## Lab it yourself

1. In the lab VM, create a Python venv (lesson 4.3) and `pip install ansible-core`. Write the inventory above with one entry, `localhost ansible_connection=local`, and run `ansible all -i inventory.ini -m ansible.builtin.setup -a 'filter=ansible_distribution*'`.
2. Write a playbook that installs `tree` and creates `/srv/demo` with `ansible.builtin.file`; run it twice with `-b` and compare the `changed=` counts.
3. `pip install pykickstart`, copy `/root/anaconda-ks.cfg` from any RHEL-family install (or the file above), delete one `%end`, and run `ksvalidator -v RHEL9` on it.
4. Download an Ubuntu Server cloud image that matches your CPU (amd64 on an x86 host, arm64 on Apple silicon). In the lab VM, put the cloud-config above in `user-data` and an `instance-id` in `meta-data`, and build a NoCloud seed ISO (`cloud-localds seed.iso user-data meta-data`). Boot the cloud image with the ISO attached, either as a second VM in your own hypervisor or with libvirt inside the lab VM if your hypervisor supports nested virtualization, then run `cloud-init status --long` in it.

## Key takeaways

- IaC keeps desired state in version-controlled text; good tools are declarative and idempotent and correct drift.
- Ansible: agentless push over SSH; inventory, YAML playbooks of tasks, modules, handlers, facts, collections (`ansible-galaxy`), ad hoc `ansible -m`.
- Puppet: agent pulls a catalog from the server on 8140 every 30 minutes; the server CA signs agent certificates; classes, modules, resources and Facter facts; `puppet apply` and Bolt work without the agent.
- OpenTofu is the open-source Terraform fork: providers call APIs, resources describe objects, state records them; `tofu init`, `plan`, `apply`, `destroy`.
- Kickstart automates RHEL installs (`inst.ks=`, `%packages ... %end`, `ksvalidator`, `/root/anaconda-ks.cfg`); cloud-init configures images on first boot from `#cloud-config` user data.
