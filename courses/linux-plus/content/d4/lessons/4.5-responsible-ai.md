## AI as a junior colleague, not an oracle

Large language models (LLMs) and AI coding assistants are now part of everyday administration work. They are fast at producing first drafts of the things this domain is about: shell scripts (lesson 4.2), Python (4.3), playbooks and OpenTofu code (4.1), commit messages (4.4). They are also confidently wrong in ways that are hard to spot: options that do not exist, packages with plausible but fake names, a regex that misses edge cases, a command that is correct on Ubuntu and destructive on RHEL. Treat every answer the way you would treat a patch from a capable but unsupervised junior admin: useful, and never applied without review.

## Use cases

| Use case | Good for | What to check |
|---|---|---|
| **Generating code** | Script skeletons, argument parsing, loops, error handling, converting a shell script to Python | Run `shellcheck`, `bash -n`, linters and tests; read every line |
| **Regular expressions** | Building and explaining patterns for `grep -E`, `sed`, `[[ =~ ]]`, Python `re` | Test against real samples, including lines that must **not** match |
| **Infrastructure as code** | Drafting Ansible tasks, Kubernetes manifests, Compose files, OpenTofu resources | Module and field names against official docs; `--syntax-check`, `--check --diff`, `tofu plan`, `docker compose config` |
| **Documentation** | Runbooks, README files, comments, man-page summaries, commit messages | Facts, versions and paths; documentation must describe what the code really does |
| **Compliance recommendations** | Mapping settings to CIS or STIG controls, explaining a scan finding, drafting a hardening checklist (Domain 3) | Control IDs and wording against the actual benchmark; the scanner, not the model, decides compliance |
| **Security review** | A second pair of eyes on a script or config: injection, unquoted variables, world-writable files, secrets in code | Not a replacement for SAST, dependency scanning and human review (DevSecOps, lesson 4.1) |
| **Code optimization** | Replacing slow loops (`for f in $(cat ...)`), reducing forks, faster Python idioms | Measure before and after (`time`, profiling); keep behaviour identical |
| **Linting** | Explaining linter output, suggesting fixes for ShellCheck or pycodestyle warnings | Rerun the real linter; the model does not replace it |

## Best practices: never copy and paste without review

1. **Read and understand every line before running it.** If you cannot explain what a command does, you are not ready to run it, especially as root.
2. **Verify against the authority:** `man`, `--help`, the vendor documentation for your distribution and version. Models mix up `dnf` and `apt` options, RHEL and Debian paths, and old and new tool syntax.
3. **Test safely first:** a throwaway VM or container, a dry run (`--check`, `--dry-run`, `-n`, `tofu plan`, `rsync -n`, `find ... -print` before `-delete`), and non-production data.
4. **Check that packages and modules exist** and are the ones you expect before installing them. Attackers register package names that models tend to invent ("slopsquatting"), so a hallucinated `pip install` can install malware.
5. **Put AI-generated code through the same pipeline as human code:** version control, peer review, linting and tests.
6. **You own the result.** "The AI wrote it" is not an acceptable root cause in an incident review.

Option order is a good example of a subtle error that review catches. `find` evaluates its arguments as an expression from left to right, and its man page warns that putting `-delete` first deletes everything below the starting point. A real run in a scratch directory:

```text
alice@srv01:~/lab$ ls app
keep.conf
new.log
old.log
alice@srv01:~/lab$ find app -name '*.log' -mtime +30 -print            # preview first
app/old.log
alice@srv01:~/lab$ cp -a app app2
alice@srv01:~/lab$ find app2 -delete -name '*.log' -mtime +30          # -delete first: wrong
alice@srv01:~/lab$ ls -A app2
ls: cannot access 'app2': No such file or directory
alice@srv01:~/lab$ find app -name '*.log' -mtime +30 -delete           # tests first: correct
alice@srv01:~/lab$ ls app
keep.conf
new.log
```

Both commands look plausible and differ only in argument order; only the preview and a test directory reveal the difference.

## Data governance

Whatever you type into a hosted AI service leaves your control. Before pasting, ask what you are disclosing.

- **Never paste secrets**: passwords, API tokens, private keys, `.env` files, kubeconfigs, Kubernetes Secret manifests (base64 is not protection), database dumps. If one slips in, treat it as leaked and **rotate** it.
- **Sanitize** configs and logs: replace real hostnames, public IPs, user names, customer data and internal domains with placeholders (`srv01`, `alice`, `192.0.2.10`, `example.com`) before sharing.
- **Training and retention:** consumer AI services may keep prompts and may use them to train future models unless you opt out; business and enterprise agreements usually exclude training and limit retention. Read the terms for the specific service and plan, and assume a free public tool keeps what you send.
- **Private vs public:** a public (hosted, shared) service runs on the provider's infrastructure under its terms. A private deployment (an enterprise tenant with contractual data protection, or a model hosted in your own cloud account) keeps data within agreed boundaries.
- **Local models** (for example Ollama or llama.cpp running open-weight models on your own hardware) keep prompts entirely on your machine and work offline, which suits sensitive data; the trade-off is smaller models, lower accuracy and your own hardware and patching.
- **Human review** stays in the loop for anything that touches production, security decisions or personal data. The AI proposes; a person approves.
- Data classification still applies: information that may not be emailed outside the company may not be pasted into an outside AI service either.

## Follow corporate policy

Organisations increasingly publish an **acceptable use policy for AI**. It typically states:

- Which tools are **approved** (often a company-licensed assistant) and which are forbidden.
- Which **data classifications** may be used with which tools (public data anywhere, internal data only in the approved tenant, confidential and regulated data never, or only in local models).
- Rules on **licensing and intellectual property** of generated code, and whether AI assistance must be **disclosed** in commits or documentation.
- **Review requirements** (generated changes go through normal change management) and logging of usage.
- Legal and regulatory constraints such as GDPR, HIPAA, PCI DSS or the EU AI Act, which can apply to what you send and how decisions are made.

If no policy exists, ask before using AI on company data; "nobody said I couldn't" does not cover a data leak.

## Prompt engineering for administrators

The quality of the answer depends heavily on the question. Good prompts for system administration:

| Technique | Example |
|---|---|
| **State the environment** | "RHEL 9.4, bash 5.1, firewalld, SELinux enforcing" instead of "Linux" |
| **Give a role and a goal** | "Act as a senior Linux administrator. Write a bash script that..." |
| **State constraints** | "No external tools beyond coreutils; must be idempotent; must run under `set -euo pipefail`; must not need root" |
| **Specify the output** | "Return only the script, with comments", "as an Ansible task using `ansible.builtin` modules", "as a table" |
| **Provide sanitized examples** | Three sample log lines that should match and two that should not |
| **Ask for reasoning and risks** | "Explain each option and list what could go wrong" or "What would this do if `$1` is empty?" |
| **Iterate** | Paste the real error message or ShellCheck output back and ask for a fix; ask for tests |

A model cannot see your system. The more precise and sanitized context you give, the less it guesses, and the less you have to correct.

> **Exam tip:** Expect scenario questions where the "best" answer is the cautious one: review and test generated code before production, verify against documentation, never submit credentials or customer data to a public model, use an approved or local model for sensitive work, and follow the company's AI policy.

## Lab it yourself

1. In a throwaway directory in the lab VM, recreate the `find` example above (use `touch -d 2026-01-01 old.log` to make an old file) and confirm the difference between the two argument orders.
2. Ask an AI assistant for a regex that matches the host names `web01` to `web99` but not `web1`, `web100` or `db01`. Test it with `grep -E` against a file containing all six names, and with `[[ $h =~ ... ]]` in a loop.
3. Ask for a bash script that rotates logs in a directory, then run `shellcheck` on it and `bash -n`; feed any warnings back and compare the second answer.
4. Take a real config file, sanitize it (host names, IPs, users, secrets) as you would before sharing, and have a colleague check what you missed.
5. Find your organisation's AI acceptable use policy (or a public example) and list which data classes it allows in which tools.

## Key takeaways

- AI is useful for generating scripts, regexes and IaC, documentation, compliance mapping, security review, optimization and explaining lint output.
- Never copy and paste without review: understand each line, verify against man pages and vendor docs, dry-run and test in a lab first.
- Check that suggested packages and options actually exist; hallucinated names can be malicious.
- Do not paste secrets, credentials or personal or customer data into public models; sanitize, rotate anything leaked.
- Hosted services may retain prompts or train on them depending on the plan; private deployments and local models keep data under your control, with trade-offs.
- Keep human review in the loop and follow corporate AI policy on approved tools and data classes.
- Better prompts state the environment, constraints and output format, give sanitized examples, and iterate with real errors.
