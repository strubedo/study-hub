## From "it works on my machine" to pipelines

Lesson 4.1 (Automation 1) put infrastructure into text files. The next step is to treat those files like application code: store them in **version control**, test every change automatically, and deliver changes the same way every time. That is **CI/CD**.

| Term | Meaning |
|---|---|
| **Version control** | Every change is a commit in a Git repository (lesson 4.4) with an author, a time and a reason. Branches and merge (pull) requests let others review a change before it reaches the main branch |
| **Continuous integration (CI)** | Every push or merge request triggers an automatic build and test, so broken changes are caught within minutes, not at release time |
| **Continuous delivery (CD)** | Every change that passes CI produces a tested artifact that *can* be released at any time; a person approves the production step |
| **Continuous deployment** | The same, but changes that pass all checks go to production automatically with no manual gate |
| **Pipeline** | The ordered stages a change goes through (lint, test, build, scan, deploy), defined in a file inside the repository |
| **Runner / agent** | The machine or container that executes pipeline jobs (GitLab Runner, GitHub Actions runner, Jenkins agent) |
| **Artifact** | The output of a stage that later stages use: a package, a container image, a compiled playbook bundle, a test report |

The pipeline definition lives in the repository it tests, so changes to the pipeline are reviewed and versioned like everything else. Common formats: **`.gitlab-ci.yml`** (GitLab CI/CD), **`.github/workflows/*.yml`** (GitHub Actions) and **`Jenkinsfile`** (Jenkins).

```yaml
# .gitlab-ci.yml for an infrastructure repository
stages:
  - lint
  - test
  - build
  - deploy

shellcheck:
  stage: lint
  image: docker.io/koalaman/shellcheck-alpine:stable
  script:
    - shellcheck scripts/*.sh

ansible-syntax:
  stage: lint
  image: registry.example.com/ci/ansible:latest
  script:
    - ansible-playbook -i inventory.ini site.yml --syntax-check
    - ansible-lint site.yml

molecule:
  stage: test
  image: registry.example.com/ci/ansible:latest
  script:
    - molecule test

build-image:
  stage: build
  image: quay.io/podman/stable
  script:
    - podman build -t registry.example.com/web:$CI_COMMIT_SHORT_SHA .
    - podman push registry.example.com/web:$CI_COMMIT_SHORT_SHA

deploy-prod:
  stage: deploy
  image: registry.example.com/ci/ansible:latest
  script:
    - ansible-playbook -i inventory.ini site.yml
  environment: production
  rules:
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH
      when: manual
```

Jobs in the same stage run in parallel; a stage starts only when every job in the previous stage succeeded, and **any command that exits non-zero fails its job** (the same return-code rule as shell scripts in lesson 4.2). The `rules` block makes production deployment run only on the default branch and only when someone clicks it, which is continuous delivery; remove `when: manual` and it becomes continuous deployment.

## Shift-left testing

On a timeline drawn left (writing code) to right (production), traditional testing happened on the right: a QA phase just before release, or users finding bugs in production. **Shift-left testing** moves checks as far left as possible, because a problem found in the editor costs seconds while the same problem found in production costs an outage.

| Where | Examples |
|---|---|
| Editor and pre-commit hooks | `shellcheck`, `yamllint`, `ansible-lint`, `tofu fmt -check`, Python linters (lesson 4.3), secret scanners |
| CI on every push | Syntax checks (`ansible-playbook --syntax-check`, `tofu validate`, `ksvalidator`), unit tests, Molecule tests of Ansible roles in containers, `tofu plan` posted to the merge request |
| Before merge | Peer review of the diff, required passing pipeline, branch protection |
| Staging | Integration tests against a production-like environment |

A real linter run on a three-line cleanup script shows why this matters (ShellCheck 0.11):

```text
alice@srv01:~$ cat cleanup.sh
#!/bin/bash
dir=$1
cd $dir
rm -rf $dir/tmp/*
alice@srv01:~$ shellcheck cleanup.sh

In cleanup.sh line 3:
cd $dir
^-----^ SC2164 (warning): Use 'cd ... || exit' or 'cd ... || return' in case cd fails.
   ^--^ SC2086 (info): Double quote to prevent globbing and word splitting.

Did you mean:
cd "$dir" || exit


In cleanup.sh line 4:
rm -rf $dir/tmp/*
       ^--^ SC2086 (info): Double quote to prevent globbing and word splitting.

Did you mean:
rm -rf "$dir"/tmp/*
...
alice@srv01:~$ echo $?
1
```

If `$1` is empty, `cd $dir` becomes a bare `cd` (which changes to the home directory) and `rm -rf $dir/tmp/*` becomes `rm -rf /tmp/*`; if `cd` fails for any other reason, the script carries on in whatever directory it was started from. The linter flags it before it ever runs, and its exit status 1 fails the CI job.

> **Exam tip:** "Shift left" = test earlier in the development life cycle (linting, unit tests, security scans in CI), not "move testing to production" and not "remove testing".

## GitOps

**GitOps** applies the same idea to running systems: **the Git repository is the single source of truth for the desired state**, and the only way to change production is to change Git.

- The desired state is **declarative** (Kubernetes manifests, Helm charts, OpenTofu code, Ansible playbooks).
- Changes go through **merge requests**, so every change is reviewed, approved and recorded.
- An automated agent **reconciles** reality with Git. In the common **pull** model, an operator running inside the cluster (**Argo CD** or **Flux** for Kubernetes) watches the repository and applies any difference, and also reverts manual changes (drift) made outside Git.
- **Rollback** is `git revert` of the bad commit; the agent then applies the previous state.
- Nobody needs direct write credentials to production, because the agent does the applying.

A push-based pipeline that runs `kubectl apply` or `ansible-playbook` after a merge is also commonly called GitOps, but the pull model with continuous reconciliation is the defining pattern.

## DevSecOps

**DevOps** joins development and operations into one team and one automated pipeline. **DevSecOps** makes security part of every stage of that pipeline instead of a review at the end, which is shift-left applied to security:

| Practice | What it does | Example tools |
|---|---|---|
| **SAST** (static analysis) | Scans source code for insecure patterns | Semgrep, SonarQube, Bandit (Python) |
| **Secret scanning** | Blocks commits containing keys, tokens and passwords | gitleaks, GitLab/GitHub secret detection |
| **Dependency / SCA scanning** | Checks libraries against CVE databases | `pip-audit`, Dependabot, OWASP Dependency-Check |
| **Container image scanning** | Finds vulnerable packages in images before they are pushed | Trivy (`trivy image --severity HIGH,CRITICAL --exit-code 1 ...`), Grype |
| **IaC scanning** | Flags insecure settings in OpenTofu, Kubernetes and Ansible code | Checkov, Trivy config, KICS |
| **DAST** (dynamic analysis) | Attacks a running staging deployment | OWASP ZAP |
| **Supply chain** | Signed artifacts, SBOMs, pinned image digests | cosign, Syft |
| **Secrets management** | Pipelines read credentials at run time, never from the repo | CI masked variables, HashiCorp Vault, OpenBao |

Runners themselves are targets: they hold deployment credentials, so give each job the least privilege it needs, prefer short-lived tokens, and do not let untrusted merge requests from forks run jobs that can see production secrets.

> **Watch out:** Removing a secret in a later commit does not remove it from Git history. A leaked key must be **rotated**; rewriting history is cleanup, not remediation.

## Lab it yourself

1. In the lab VM, create a Git repository (lesson 4.4) with a `scripts/` directory and the `cleanup.sh` above. Install `shellcheck` (`dnf install ShellCheck` from EPEL on RHEL, `apt install shellcheck` on Debian/Ubuntu) and run it; fix every warning until it exits 0.
2. Add a Git pre-commit hook: create `.git/hooks/pre-commit` containing `#!/bin/bash` and `shellcheck scripts/*.sh`, `chmod +x` it, and try to commit a script with an unquoted variable. The commit is refused because the hook exits non-zero.
3. If you have a GitLab or GitHub account, push the repository and add the `shellcheck` job above (or a GitHub Actions workflow with `run: shellcheck scripts/*.sh`) and watch a failing commit turn the pipeline red.
4. In the lab VM, install Trivy and scan an old image tag, for example `trivy image docker.io/library/nginx:1.20`, then a current one, and compare the counts.

## Key takeaways

- CI builds and tests every change automatically; continuous delivery keeps every passing change releasable with a manual production gate; continuous deployment removes the gate.
- A pipeline is stages of jobs defined in the repository (`.gitlab-ci.yml`, `.github/workflows/`, `Jenkinsfile`); a non-zero exit fails the job.
- Shift-left testing runs linters, syntax checks, unit tests and scans as early as possible, in the editor, pre-commit hooks and CI.
- GitOps: Git is the single source of truth, changes arrive by merge request, and an agent (Argo CD, Flux) reconciles the live system and corrects drift; rollback is `git revert`.
- DevSecOps builds SAST, secret scanning, dependency and image scanning, IaC scanning and DAST into the pipeline; leaked secrets must be rotated.
