## How Git thinks

**Git** is a distributed version control system: every clone holds the full history, so you can commit, branch, diff and read the log offline, and synchronise with others through **remotes** (a server such as GitLab, GitHub, Gitea, or just another directory or SSH path). Everything in lesson 4.1, from Ansible playbooks to GitOps, assumes the code lives in Git.

A file moves through three areas:

| Area | Meaning | Move a change into it with |
|---|---|---|
| **Working tree** | The files you edit | (editing) |
| **Index** (staging area) | The snapshot that the next commit will contain | `git add` |
| **Repository** (`.git/`) | Commits: snapshots with author, date, message and a parent pointer, named by a hash | `git commit` |

A **branch** is just a movable pointer to a commit; **HEAD** points at the branch you are on. All output below comes from real runs of Git 2.55 in throwaway repositories (hashes will differ on your system).

## Setting up: config, init, clone

`git config` reads and writes settings at three levels; the more specific level wins:

| Level | Option | File |
|---|---|---|
| System | `--system` | `/etc/gitconfig` |
| User | `--global` | `~/.gitconfig` (or `~/.config/git/config`) |
| Repository | `--local` (default when inside a repo) | `.git/config` |

```text
alice@srv01:~$ git config --global user.name "Alice Admin"
alice@srv01:~$ git config --global user.email alice@example.com
alice@srv01:~$ git config --global init.defaultBranch main
alice@srv01:~$ git config --global --list
user.name=Alice Admin
user.email=alice@example.com
init.defaultbranch=main
```

Every commit records `user.name` and `user.email`, so set them before the first commit. `git config --list --show-origin` shows which file each value came from.

**`git init`** turns the current (or named) directory into a new repository by creating `.git/`. **`git clone URL`** copies an existing repository, checks out its default branch and records the source as the remote **`origin`**:

```text
alice@srv01:~$ git init infra
Initialized empty Git repository in /home/alice/infra/.git/
```

```bash
git clone https://git.example.com/ops/infra.git      # over HTTPS
git clone git@git.example.com:ops/infra.git          # over SSH, using your key
git clone /srv/git/infra.git infra-copy              # a local path works too
```

## .gitignore

`.gitignore` (committed in the repository root, or in subdirectories) lists patterns Git should not offer to track: build output, logs, virtual environments and, above all, secrets.

```text
# .gitignore
*.log
.venv/
secrets.env
__pycache__/
```

`*.log` matches in any directory, a trailing `/` matches directories only, a leading `/` anchors to the repository root, and `!pattern` re-includes something. `git check-ignore -v file` tells you which rule matched:

```text
alice@srv01:~/infra$ git status --short
?? .gitignore
?? backup.sh
alice@srv01:~/infra$ git check-ignore -v run.log secrets.env
.gitignore:1:*.log	run.log
.gitignore:3:secrets.env	secrets.env
```

> **Watch out:** `.gitignore` only affects **untracked** files. A file that was already committed stays tracked. Stop tracking it with `git rm --cached file` (the file stays on disk) and commit; if it contained a secret, the secret is still in history, so rotate it.

## add, commit, diff, log

```text
alice@srv01:~/infra$ git add .gitignore backup.sh                # stage (git add . stages everything not ignored)
alice@srv01:~/infra$ git commit -m "Add backup script"
[main (root-commit) da38419] Add backup script
 2 files changed, 5 insertions(+)
 create mode 100644 .gitignore
 create mode 100644 backup.sh
alice@srv01:~/infra$ git switch -c feature/logging
Switched to a new branch 'feature/logging'
alice@srv01:~/infra$ echo 'logger -t backup "done"' >> backup.sh
alice@srv01:~/infra$ git diff
diff --git a/backup.sh b/backup.sh
index 12928d0..951064a 100644
--- a/backup.sh
+++ b/backup.sh
@@ -1,2 +1,3 @@
 #!/bin/bash
 rsync -a /etc/ /backup/etc/
+logger -t backup "done"
alice@srv01:~/infra$ git commit -am "Log completion to syslog"   # -a stages modified tracked files
[feature/logging 8cc80d6] Log completion to syslog
 1 file changed, 1 insertion(+)
```

| Command | Shows |
|---|---|
| `git status` (`-s` / `--short`) | What is modified, staged and untracked. In short form the left column is the index and the right the working tree: `M ` staged, ` M` modified but unstaged, `??` untracked, `UU` conflict |
| `git diff` | Working tree vs index (unstaged changes) |
| `git diff --staged` (`--cached`) | Index vs last commit (what will be committed) |
| `git diff main feature` | Between two branches or commits |
| `git log` | History, newest first. `--oneline`, `--graph`, `--all`, `-n 5`, `-p` (patches), `--author=bob`, `-- path` |
| `git show <commit>` | One commit and its patch |

Write commit messages as a short imperative summary ("Add quota report", not "changes"), because the log is how the next administrator learns why something changed.

## Branches, checkout, switch and restore

```bash
git branch                     # list; * marks the current branch (-v adds the last commit)
git branch feature/quota       # create, without switching
git switch feature/quota       # switch to it
git switch -c hotfix           # create and switch
git branch -d hotfix           # delete; refuses if not merged ("not fully merged"); -D forces
```

**`git checkout`** is the older command that does two unrelated jobs: switching branches (`git checkout feature`, `git checkout -b new`) and restoring files (`git checkout -- file`). Git 2.23 split it into **`git switch`** (branches) and **`git restore`** (files). Both forms work and the exam names `checkout`:

| Task | Classic | Newer |
|---|---|---|
| Switch branch | `git checkout main` | `git switch main` |
| Create and switch | `git checkout -b feature` | `git switch -c feature` |
| Discard unstaged edits to a file | `git checkout -- file` | `git restore file` |
| Unstage a file (keep the edit) | `git reset HEAD file` | `git restore --staged file` |

## merge, squash and rebase

**Merge** joins another branch into the current one. If the current branch has not moved since the other branched off, Git simply moves the pointer forward: a **fast-forward**, with no new commit. If both have new commits, Git makes a **merge commit** with two parents:

```text
alice@srv01:~/infra$ git log --oneline --graph --all
* d3778fe Add rsync exclude list
| * 79db18a Add OWNERS
|/  
* 5c66616 Add syslog logging (squashed)
* da38419 Add backup script
alice@srv01:~/infra$ git merge --no-edit feature/exclude          # run on main
Merge made by the 'ort' strategy.
 rsync-excludes | 1 +
 1 file changed, 1 insertion(+)
 create mode 100644 rsync-excludes
alice@srv01:~/infra$ git log --oneline --graph
*   0143220 Merge branch 'feature/exclude'
|\  
| * d3778fe Add rsync exclude list
* | 79db18a Add OWNERS
|/  
* 5c66616 Add syslog logging (squashed)
* da38419 Add backup script
```

When both branches changed the same lines, the merge stops with a **conflict**. Edit the file to the correct content (remove the markers), `git add` it and `git commit`, or give up with `git merge --abort`:

```text
alice@srv01:~/infra$ git merge hotfix
Auto-merging retention.conf
CONFLICT (content): Merge conflict in retention.conf
Automatic merge failed; fix conflicts and then commit the result.
alice@srv01:~/infra$ git status --short
UU retention.conf
alice@srv01:~/infra$ cat retention.conf
<<<<<<< HEAD
retention=7
=======
retention=30
>>>>>>> hotfix
```

**Squash** turns a branch's commits into one. `git merge --squash feature` stages the combined changes of the branch but does **not** commit and does not record a merge; you commit once yourself:

```text
alice@srv01:~/infra$ git merge --squash feature/logging
Updating da38419..5115dfd
Fast-forward
Squash commit -- not updating HEAD
 backup.sh | 2 ++
 1 file changed, 2 insertions(+)
alice@srv01:~/infra$ git status --short
M  backup.sh
alice@srv01:~/infra$ git commit -m "Add syslog logging (squashed)"
alice@srv01:~/infra$ git branch -d feature/logging
error: the branch 'feature/logging' is not fully merged
```

Because no merge was recorded, Git does not consider the branch merged, so delete it with `-D`. (Squashing can also be done with `git rebase -i`, marking commits `squash` or `fixup`, and hosting platforms offer "squash and merge".)

**Rebase** replays your branch's commits on top of another branch, producing a straight line instead of a merge commit:

```text
alice@srv01:~/demo$ git log --oneline --graph --all
* b93a760 Add quota report
| * 9e2ab58 Document restore steps
|/  
* 540b048 Add backup script
* cd469f5 Add README
alice@srv01:~/demo$ git switch feature/quota
Switched to branch 'feature/quota'
alice@srv01:~/demo$ git rebase main
Successfully rebased and updated refs/heads/feature/quota.
alice@srv01:~/demo$ git log --oneline --graph --all
* 65f09a8 Add quota report
* 9e2ab58 Document restore steps
* 540b048 Add backup script
* cd469f5 Add README
alice@srv01:~/demo$ git switch main; git merge feature/quota
Switched to branch 'main'
Updating 9e2ab58..65f09a8
Fast-forward
```

The rebased commit has a **new hash** (`b93a760` became `65f09a8`): rebase rewrites history. That is fine for your own unpublished commits, but **never rebase commits that others have already pulled** (a shared branch such as `main`): their copies still contain the old commits, and pushing the rewritten branch needs a force push that discards their work. Merge (or revert) on shared branches; rebase only private ones.

## fetch, pull and push

| Command | Effect |
|---|---|
| `git remote -v` | List remotes and their URLs; `git remote add origin URL` adds one |
| `git fetch` | Download new commits from the remote and update remote-tracking branches (`origin/main`). Does **not** touch your branches or working tree |
| `git pull` | `git fetch` followed by a merge (or a rebase with `--rebase`, or the `pull.rebase` setting) into the current branch |
| `git push` | Upload your commits and move the remote branch. `git push -u origin feature` also sets the upstream so later `git push`/`pull` need no arguments |

A push is **rejected** if the remote branch has commits you do not have, because accepting it would throw them away:

```text
alice@srv01:~/infra$ git push origin main
To /home/alice/origin.git
 ! [rejected]        main -> main (fetch first)
error: failed to push some refs to '/home/alice/origin.git'
...
alice@srv01:~/infra$ git fetch origin
From /home/alice/origin
   0143220..d02ae78  main       -> origin/main
alice@srv01:~/infra$ git status -sb
## main...origin/main [ahead 1, behind 1]
alice@srv01:~/infra$ git log --oneline main..origin/main
d02ae78 Set retention to 14 days
alice@srv01:~/infra$ git pull --no-rebase --no-edit origin main
...
Merge made by the 'ort' strategy.
alice@srv01:~/infra$ git push origin main
To /home/alice/origin.git
   d02ae78..9439e8c  main -> main
```

`git push --force` overwrites the remote branch; if you must, `--force-with-lease` at least refuses when the remote has commits you have not seen.

## reset, stash and tag

**`git reset <commit>`** moves the current branch pointer back. The mode decides what happens to the changes from the commits you "undo":

| Mode | Branch pointer | Index | Working tree | Result |
|---|---|---|---|---|
| `--soft` | Moved | Kept | Kept | Changes are **staged**, ready to recommit (useful to redo the last commit) |
| `--mixed` (default) | Moved | Reset | Kept | Changes are **unstaged** in your files |
| `--hard` | Moved | Reset | **Reset** | Changes are **gone** from the files |

```text
alice@srv01:~/infra$ git reset --soft HEAD~1; git status --short
A  mail.conf
alice@srv01:~/infra$ git commit -qm "Add mail config"; git reset HEAD~1; git status --short
?? mail.conf
alice@srv01:~/infra$ git add mail.conf; git commit -qm "Add mail config"; git reset --hard HEAD~1
HEAD is now at 0143220 Merge branch 'feature/exclude'
alice@srv01:~/infra$ ls mail.conf
ls: cannot access 'mail.conf': No such file or directory
alice@srv01:~/infra$ git reflog | head -2
0143220 HEAD@{0}: reset: moving to HEAD~1
ac28acc HEAD@{1}: commit: Add mail config
```

(`mail.conf` shows as `??` after the mixed reset because it was a new file, so unstaging it makes it untracked.) Committed work lost by a hard reset can usually be found in **`git reflog`** and recovered with `git reset --hard ac28acc`; uncommitted edits destroyed by `--hard` cannot. Like rebase, reset rewrites history, so on shared branches undo a published commit with **`git revert <commit>`**, which adds a new commit that reverses it.

**`git stash`** shelves uncommitted changes so you can switch branches with a clean tree, then brings them back:

```text
alice@srv01:~/infra$ git status --short
 M backup.sh
alice@srv01:~/infra$ git stash push -m "wip: home backup"
Saved working directory and index state On main: wip: home backup
alice@srv01:~/infra$ git stash list
stash@{0}: On main: wip: home backup
alice@srv01:~/infra$ git stash pop
...
Dropped refs/stash@{0} (b3bb4767eae62b0aa0f29142eae597d3186c91ab)
```

`pop` applies and drops the entry, `apply` keeps it, `drop` deletes one, and `git stash -u` includes untracked files (plain `git stash` ignores them).

**`git tag`** names a commit permanently, typically a release. A **lightweight** tag (`git tag v0.1`) is just a name; an **annotated** tag (`git tag -a v1.0 -m "First release"`) is a full object with tagger, date and message, and is what releases should use. Tags are not pushed by default:

```text
alice@srv01:~/infra$ git tag -a v1.0 -m "First release"
alice@srv01:~/infra$ git push origin main v1.0
To /home/alice/origin.git
   5c66616..0143220  main -> main
 * [new tag]         v1.0 -> v1.0
```

(`git push --tags` pushes all tags.)

## Lab it yourself

Everything here runs offline in the lab VM (install Git with `dnf install git` or `apt install git` if it is missing):

1. `git init --bare /tmp/lab/origin.git`, then `git clone /tmp/lab/origin.git /tmp/lab/alice` and again to `/tmp/lab/bob`. Set `user.name` and `user.email` in each with `git config` (no `--global`).
2. In `alice`, add a `.gitignore`, a script and a `secrets.env`; confirm with `git status` and `git check-ignore -v` that the secret is ignored. Commit and `git push -u origin main`.
3. Commit a change in `bob` and push; then commit in `alice` and push to see the rejection; `git fetch`, `git log main..origin/main`, `git pull`, push again.
4. Create two branches that change the same line, merge them to produce a conflict, resolve it, and compare with `git merge --squash` and `git rebase` on fresh branches. Note how hashes change after the rebase.
5. Make three commits, then try `git reset --soft HEAD~1`, `git reset HEAD~1` and `git reset --hard HEAD~1`, checking `git status` after each, and recover with `git reflog`.

## Key takeaways

- Working tree -> `git add` -> index -> `git commit` -> repository; `git status`, `git diff` and `git diff --staged` show each gap.
- `git config` levels: `--system`, `--global` (`~/.gitconfig`), `--local`; set `user.name` and `user.email` first. `git init` creates, `git clone` copies and sets `origin`.
- `.gitignore` affects only untracked files; use `git rm --cached` for files already tracked, and rotate leaked secrets.
- `git switch`/`git restore` are the newer split of `git checkout`.
- Merge = fast-forward or merge commit; `git merge --squash` stages one combined change and you commit it; rebase rewrites commits with new hashes, so never rebase shared history.
- `fetch` downloads only; `pull` = fetch + merge (or rebase); a push is rejected when the remote has commits you lack.
- `reset --soft` keeps changes staged, `--mixed` (default) unstaged, `--hard` discards them; `reflog` finds lost commits; use `revert` on shared branches.
- `git stash` / `stash pop` shelve work; annotated tags (`git tag -a`) mark releases and need an explicit push.
