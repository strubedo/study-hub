## Start with the simplest thing that works

The most useful sentence in Anthropic's "Building effective agents" is a warning: find the simplest solution possible and add complexity only when it is needed, which "might mean not building agentic systems at all". The article adds that agentic systems often trade latency and cost for better task performance, and that for many applications a single, well-optimized model call with retrieval and good examples is enough.

Anthropic's "How tool use works" page makes the same point about tools. Tool use does not fit when the model can answer from what it already has (summarizing, translating), when the job is one-shot question and answer with nothing to run, or when the extra round trip of a tool call would cost more than the work itself.

This lesson turns that advice into a checklist and shows the arithmetic behind it.

## A decision checklist

Work down the list; the first "no" usually decides.

| Question | If yes | If no |
|---|---|---|
| Does the task need a model at all (judgment, language, messy input)? | Continue | Write a script. A regex, a parser or an API call is cheaper and exact |
| Is all the needed information available before you start? | A **single call** may do. Paste it in | The model must fetch things: workflow or agent |
| Can you list the steps and branches in advance? | Build a **workflow**. Code decides the path | Continue |
| Does the path depend on what earlier steps find, with no way to predict how many steps? | An **agent** may be justified | Rethink the task; you may be missing a step list |
| Can you tell whether a run succeeded (a test, a check, a human review)? | Continue | Do not automate it yet. Without a success check you cannot evaluate the agent |
| Are the tools read-only, or are changes reversible and gated by approval? | Continue | Redesign first: read-only tools, or a human approval step before any change |
| Can the use case tolerate variable time and cost per run? | Agent is acceptable | Prefer a workflow with fixed calls |

The Anthropic article sums up where agents fit: open-ended problems where it is hard or impossible to predict the number of steps and you cannot hardcode a path, in environments trusted enough to let the model make decisions. Its appendix adds that the best agent tasks have clear success criteria, feedback loops and meaningful human oversight.

> **Real world:** Most "build an agent for X" requests in IT operations turn out to be workflows with one or two model calls: fetch data, classify, write a note. Save the agent for the investigations where an engineer would genuinely say "it depends what I find".

## Cost: every iteration resends the conversation

The Claude Messages API is **stateless** by default: each request carries the whole conversation. (A beta message threads feature can keep it server-side; the tokens still count.) In a loop, each iteration therefore sends everything that came before plus the newest tool result. Input tokens grow with every step.

A worked example, with illustrative numbers:

- System prompt 800 tokens, tool definitions 400, the user's goal 100: **1,300 tokens** in the first request.
- Each iteration adds the model's tool call (about 100 tokens) and the tool result (about 1,500 tokens): **+1,600 tokens per iteration**.

| Request | Input tokens |
|---|---|
| 1 | 1,300 |
| 2 | 2,900 |
| 3 | 4,500 |
| 4 | 6,100 |
| 5 (final answer) | 7,700 |
| **Total input** | **22,500** |

The single-call design for the same task would send perhaps 1,300 to 3,000 tokens once. The agent spent roughly ten times as much input, before counting output tokens, and cost grows faster than linearly as runs get longer because each request carries all earlier results. Prompt caching cuts the price of the repeated prefix (Domain 3), and keeping tool results compact helps most (Domain 2), but the shape of the curve stays.

> **Watch out:** One verbose tool, such as a `show tech-support` dump or an unfiltered log search, can add tens of thousands of tokens in a single step and keep paying for them on every later request.

## Latency: the steps are sequential

Each iteration is a full round trip: the model generates its tool call, your code runs the tool (an SSH session, an API call), and the next request waits for both. If a model response takes about 4 seconds and a device query about 3, then five iterations take roughly 35 seconds, against a few seconds for one call. Parallel tool calls in one turn help (Domain 2), but the turns themselves are sequential. An agent does not suit a request where someone is waiting for an instant answer on a chat screen; a workflow or a single call does.

## Compounding errors

Anthropic's article notes that the autonomous nature of agents means higher costs and **the potential for compounding errors**. A simple model shows why. If each step succeeds with probability *p*, and a run needs *n* steps that must all succeed, then the run succeeds with probability *p* to the power *n*:

| Per-step success | 3 steps | 5 steps | 10 steps | 20 steps |
|---|---|---|---|---|
| 99% | 97.0% | 95.1% | 90.4% | 81.8% |
| 98% | 94.1% | 90.4% | 81.7% | 66.8% |
| 95% | 85.7% | 77.4% | 59.9% | 35.8% |
| 90% | 72.9% | 59.0% | 34.9% | 12.2% |

(Computed offline: for example 0.95 to the power 10 is 0.5987.) Two lessons follow:

- **Fewer steps is a reliability feature.** At 95% per step, cutting a 10-step path to 5 steps raises success from about 60% to about 77%.
- **High per-step reliability is needed for long runs.** To keep a 10-step run at 90% or better, each step must succeed about 99% of the time.

The model is deliberately simple. Real steps are not independent, and a good agent can **recover**: a tool result that says "interface not found" lets the model correct the name and try again. That recovery is the reason agents get ground truth from tools at every step. It also means error messages that tell the model what to do next (Domain 2) directly improve end-to-end success. The opposite also happens: an early wrong assumption can steer every later step, which the multiplication does not capture.

## Controls that make autonomy affordable

When the checklist says "agent", bound it:

- **Iteration and budget limits.** Cap the loop. The Claude Agent SDK, for example, has `max_turns` and `max_budget_usd` options; your own loop needs its own counter (Domain 4).
- **Read-only first.** Start with tools that cannot change anything. A wrong step then costs tokens, not an outage.
- **Approval before change.** If the agent may change configuration, a human approves each change (Domain 5).
- **Verification steps.** Add a check (a test, a second read, a validation tool) after risky steps so that errors are caught instead of compounded.
- **Test in a sandbox.** The Anthropic article recommends extensive testing in sandboxed environments with guardrails before trusting an agent.

The numbers above, the checklist and the "start simple" rule are this course's synthesis of the vendors' guidance; the per-step model is a teaching simplification, not a vendor formula.

## Try it yourself

A calculation and design exercise; no API key needed.

1. In a terminal, check one table cell: `python3 -c "print(0.95 ** 10)"` (on Windows, `py -c "print(0.95 ** 10)"` if `python3` is not found). Then compute how many steps at 98% you can afford before success drops under 90%.
2. Take the three designs you wrote in the last lesson's exercise. Run each through the checklist and note the first question that decides.
3. For your agent design, estimate tokens per request using the method above (fixed prompt plus a per-iteration increment) and total them for your iteration limit.
4. Rewrite the agent design to need fewer steps, for example a single tool that returns both interface status and recent errors, and recompute the success estimate.

## Key takeaways

- Start with a single call, move to a workflow when steps are known, and use an agent only when the path genuinely depends on what is found.
- A task needs a success check before it is automated, and changing tools need approval gates.
- Input tokens grow every iteration because each request resends the whole conversation; total cost grows faster than the number of steps.
- Loop steps are sequential round trips, so agents add latency.
- With independent steps, end-to-end success is the per-step rate to the power of the number of steps: 95% over 10 steps is about 60%.
- Recovery from tool feedback, fewer steps and verification steps are the main counters to compounding errors.
