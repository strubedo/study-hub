## Why the loop keys on `stop_reason`

Every successful Messages API response carries a `stop_reason` that says why the model stopped generating. It is the loop's steering signal: one value means "run my tools and come back", others mean "here is the answer", and the rest mean "something cut me short, decide what to do". A loop that ignores the field will, sooner or later, hand a truncated answer to a user or throw away a tool call.

## The seven stop reasons

The Claude Messages API reference lists exactly these values (checked 2026-11-23 on the API reference and the "Stop reasons and fallback" guide):

| `stop_reason` | What happened | What the loop does next |
|---|---|---|
| `end_turn` | The model finished its response naturally | Use the answer; leave the loop |
| `tool_use` | The model is calling one or more tools | Run each client tool, append the response and a `tool_result` message, send again |
| `max_tokens` | The response hit your `max_tokens` limit | Treat the output as incomplete: raise `max_tokens` or continue the response. If the last block is an incomplete `tool_use`, retry with a higher `max_tokens` |
| `stop_sequence` | The model produced one of your `stop_sequences` | Read the `stop_sequence` field to see which; usually a deliberate end |
| `pause_turn` | A **server-tool** loop (for example web search) hit its iteration limit; the guide gives a default of 10 iterations per request | Send the response's content back unchanged as an `assistant` message, with the same tools and no new user message, so the model continues |
| `refusal` | The model declined to respond (safety classifiers) | Read `stop_details` (a category and an explanation) and discard any partial output. Do not resend the same request to the same model unchanged; the guide's recommended handling is a retry on a fallback Claude model, except for the `reasoning_extraction` category, where you change the prompt instead |
| `model_context_window_exceeded` | Generation reached the model's context window limit | Treat the response as truncated; the conversation is too long to continue as is |

Two details worth remembering:

- `pause_turn` never appears for your own tools. When the model stops to call a tool *you* run, the stop reason is `tool_use`.
- The SDKs currently type `model_context_window_exceeded` in their beta namespace; the guide says the API returns it without a beta header on recent models.

> **Exam tip:** In a loop exhibit, look at `stop_reason` first, then at the last content block. `tool_use` with a `tool_use` block means run the tool. `max_tokens` with a half-written `tool_use` block means the call is incomplete and must not be run.

## Stop reasons are not errors

A stop reason arrives in a **successful** response (HTTP 200) with valid content. A **failed request** arrives as an HTTP 4xx or 5xx error with an error body instead of a message. A refusal is a stop reason, not an error: the documentation notes that safety classifiers return it as a normal 200 response. Your loop needs both kinds of handling: retries and backoff for errors such as rate limits (Domain 4), and the table above for stop reasons.

One case shows the boundary clearly. If the **input alone** is larger than the model's context window, the API rejects the request with a 400 `invalid_request_error` ("prompt is too long"). If the input fits but **generation** then reaches the window's limit, you get a successful response with `stop_reason: "model_context_window_exceeded"`.

## The same signals at OpenAI and Google

Neither has a field named `stop_reason`; the loop checks other things.

| Loop question | Claude Messages API | OpenAI Responses API | Gemini Interactions API |
|---|---|---|---|
| Did the model ask for a tool? | `stop_reason` is `tool_use` | `output` contains `function_call` items | `steps` contain `function_call` steps |
| Did it finish normally? | `end_turn` | `status` is `completed` and no function calls are pending | `status` is `completed` |
| Was the output cut short? | `max_tokens`, `model_context_window_exceeded` | `status` is `incomplete`; `incomplete_details.reason` such as `max_output_tokens` | `status` is `incomplete` (the reference's example: hitting max tokens) |
| Did the model refuse or get filtered? | `refusal` with `stop_details` | A `refusal` content part in the output message; `incomplete_details.reason` can be `content_filter` | No dedicated refusal status is documented; the request has `safety_settings`. Check the reference |

Gemini's Interactions reference also lists `requires_action` ("requires action/input from the user") and `requires_continuation` (send the returned `continuation_token` to finish a long decode). Its function-calling guide detects tool calls from the `function_call` steps, not from the status, so key your loop on the steps (checked 2026-11-23).

## A minimal loop in Python

This is the loop later domains build on. Every API name in it comes from Anthropic's tool-use documentation and Python SDK README as of 2026-11-23. It uses one read-only stub tool, a hard iteration cap, and returns every non-`tool_use` response to the caller to handle. It was compiled but not run while writing this course.

```python
import json
import anthropic

MODEL = "claude-haiku-5-5"   # model ids change: check the Claude models overview
MAX_ITERATIONS = 5           # hard cap on model calls per run
SYSTEM = "You diagnose network problems for Example Corp. You can only read device state."
TOOLS = [{
    "name": "get_interface_status",
    "description": "Read-only. Returns status and error counters for one interface on one switch.",
    "input_schema": {
        "type": "object",
        "properties": {"device": {"type": "string"}, "interface": {"type": "string"}},
        "required": ["device", "interface"],
    },
}]
client = anthropic.Anthropic()  # reads ANTHROPIC_API_KEY from the environment


def get_interface_status(device, interface):
    # Stub with fixed data: replace with a real read-only lookup later.
    return {"device": device, "interface": interface, "oper_status": "up",
            "duplex": "half", "input_errors": 18342}


def run_tool(name, tool_input):
    """Return (content, is_error). Model-supplied input is untrusted: validate it."""
    if name != "get_interface_status":
        return f"Unknown tool {name}. Use get_interface_status.", True
    try:
        return json.dumps(get_interface_status(**tool_input)), False
    except TypeError as exc:
        return f"Bad input: {exc}. Send device and interface only.", True
    except Exception as exc:  # any other tool failure goes back to the model, not up the stack
        return f"Tool failed: {exc}. Check the device and interface names, or report the failure.", True


def run_agent(goal):
    messages = [{"role": "user", "content": goal}]
    for _ in range(MAX_ITERATIONS):
        response = client.messages.create(model=MODEL, max_tokens=1024, system=SYSTEM,
                                          tools=TOOLS, messages=messages)
        if response.stop_reason != "tool_use":
            return response  # end_turn, max_tokens, refusal...: the caller decides
        messages.append({"role": "assistant", "content": response.content})
        results = []
        for block in response.content:
            if block.type == "tool_use":
                content, failed = run_tool(block.name, block.input)
                results.append({"type": "tool_result", "tool_use_id": block.id,
                                "content": content, "is_error": failed})
        messages.append({"role": "user", "content": results})
    raise RuntimeError(f"No final answer after {MAX_ITERATIONS} model calls")


if __name__ == "__main__":
    final = run_agent("Is GigabitEthernet1/0/48 on sw-access-12.example.com healthy?")
    print("stop_reason:", final.stop_reason)
    for block in final.content:
        if block.type == "text":
            print(block.text)
```

What to notice:

- The **`for` loop with `MAX_ITERATIONS`** replaces the documentation's `while True`. An agent without a cap can run, and bill, indefinitely.
- `response.content` goes back **unchanged** as the assistant message, then **one** user message holds every `tool_result`.
- `run_tool` treats the model's input as untrusted: an unknown tool name or wrong arguments become an `is_error` result with a hint, so the model can correct itself instead of the program crashing.
- The caller must still check `final.stop_reason`: `max_tokens` or `refusal` is not a finished answer. This loop has no server tools, so it never sees `pause_turn`.

## The context window is the agent's working memory

Anthropic's "Context windows" page calls the context window the model's "working memory": everything the model can reference when generating a response, including the response itself. It is separate from what the model learned in training.

**What counts** toward it on every request: the system prompt, the tool definitions, every message in `messages` (including tool results, images and documents), and the output being generated, including thinking. In a loop, that means:

| Iteration | What the request holds |
|---|---|
| 1 | System prompt + tool definitions + goal |
| 2 | All of the above + tool call 1 + result 1 |
| 3 | All of the above + tool call 2 + result 2 |
| *n* | Everything since the start |

On the current models the window is large (1M tokens on the models listed as latest on 2026-11-23; older models 200k), but that does not make long runs safe:

- **Quality degrades before the limit.** The documentation names the effect *context rot*: as token count grows, accuracy and recall degrade, so what you keep in context matters as much as how much fits.
- **Cost and latency grow** with every request, as the last lesson showed.
- **Hard stops arrive eventually**: a 400 error when the input no longer fits, or `model_context_window_exceeded` when generation runs into the limit.

The remedies (compaction, context editing, trimming tool results, keeping durable notes outside the window) are Domain 3's subject. For now, design tools to return only what the model needs.

## Key takeaways

- Seven Claude stop reasons: `end_turn`, `tool_use`, `max_tokens`, `stop_sequence`, `pause_turn`, `refusal`, `model_context_window_exceeded`.
- Continue the loop on `tool_use`; resend the content unchanged on `pause_turn` (server tools only); treat `max_tokens` and `model_context_window_exceeded` as truncation; on `refusal`, read `stop_details` and apply a refusal policy (Anthropic's guide: retry on a fallback model) instead of resending unchanged.
- Stop reasons come in successful responses; HTTP 4xx and 5xx are errors and need separate handling.
- OpenAI signals tool calls with `function_call` output items and truncation with `status: "incomplete"`; Gemini's Interactions API uses `function_call` steps and a `status` field.
- Always cap iterations, return a result for every tool call, and treat tool input from the model as untrusted.
- The context window holds everything sent and generated; it fills turn by turn, quality degrades as it grows (context rot), and it eventually stops the run.
