## Where the prompting course left off

The prompting course showed that a model cannot run anything itself. When it needs outside data or an action, it emits a structured **tool call**; something else carries it out and hands back a **tool result**. Anthropic's documentation calls this a contract: you say which operations exist and what shape their inputs take, the model decides when to call them, and "the model never runs anything on its own".

An agent is what you get when you put that exchange in a loop and let the model keep going until the job is done.

## The agent loop

Every agent, from a ten-line script to a hosted service, runs the same cycle:

1. **Your code sends a request** containing the goal (a user message), the system prompt and the **tool definitions**: names, descriptions and input schemas.
2. **The model replies.** Either it answers in text, or it asks for one or more tool calls. On the Claude Messages API, a tool request comes back with `stop_reason: "tool_use"` and one or more `tool_use` content blocks.
3. **Someone runs the tool.** For tools you define, *your code* runs them. For server tools such as web search, the provider runs them on its own infrastructure.
4. **The result goes back.** Your code appends the model's reply and a message containing the tool results to the conversation and sends the whole history again.
5. **Repeat** from step 2 until the model gives a final answer, or until a limit you set (iterations, tokens, time, money) is hit, or until the response stops for another reason your code must handle.

Anthropic's "How tool use works" page describes the canonical shape as a `while` loop keyed on `stop_reason`: keep running tools while the stop reason is `tool_use`, and leave the loop on any other value. The next lessons take that apart line by line.

| Step | Who does it | What can go wrong |
|---|---|---|
| Choose the next action | The model | Wrong tool, wrong arguments, gives up too early, loops |
| Validate and run the tool | Your code (or the provider, for server tools) | Bad input reaches a real system; the tool fails or times out |
| Return the result | Your code | Result too large, unclear, or carrying hostile text |
| Decide to stop | The model, bounded by your limits | Never stops, or stops before the job is done |

Anthropic's engineering article **"Building effective agents"** (December 2024) puts it plainly: agents "are typically just LLMs using tools based on environmental feedback in a loop". The same article stresses that an agent must get **ground truth from the environment at each step**, such as a tool result or the output of a command, to judge its own progress, and that it is common to add stopping conditions such as a maximum number of iterations.

> **Real world:** The loop is small. What makes an agent useful or dangerous is the tool set: what each tool can reach, whether it can change anything, and what it returns. Domain 2 covers tool design and Domain 5 covers safety.

## Workflows and agents: who decides the steps

Vendors use the word "agent" loosely, so this course uses the distinction Anthropic draws in "Building effective agents". Both kinds are **agentic systems**; the difference is who controls the path:

- **Workflows**: the model and tools are orchestrated through **predefined code paths**. Your code decides which step runs next. The model fills in each step (classify this, summarize that), but cannot add or skip steps.
- **Agents**: the model **dynamically directs its own process and tool use**. It decides which tool to call, in what order, how many times, and when it is finished.

Other vendors draw the same line in their own words:

- The **Claude Agent SDK** overview defines an agent as "an application that completes a task by planning its own steps and calling tools".
- **OpenAI**'s Agents guide says agents "can plan and complete tasks using tools, work with other agents, and maintain context across steps".
- **Google's Agent Development Kit (ADK)** builds the distinction into its classes: an `LlmAgent` uses a model to reason, while **workflow agents** (`SequentialAgent`, `ParallelAgent`, `LoopAgent`) are "deterministic controllers" of execution. As of 2026-11-23 the ADK documentation marks these template workflow agents **deprecated**: in ADK Python, TypeScript, Go and Kotlin they are superseded by graph-based workflows and dynamic workflows. The distinction they illustrate (code, not the model, fixes the control flow) is unchanged.

The building block for both is what the Anthropic article calls the **augmented LLM**: a model with retrieval, tools and memory available. A workflow wires several augmented-LLM calls together in code; an agent hands one augmented LLM a loop and a goal.

> **Watch out:** "Agentic" is not a quality mark. A workflow is often the better engineering choice: it is cheaper, faster, easier to test and does the same thing every time. The next lesson is about choosing.

## One task, three designs

Example Corp's service desk gets this ticket: *"Users on the third floor say the network is slow since this morning."* The goal is a short diagnosis note in the ticket. Here are three ways to build it.

### Design 1: a single model call

An engineer collects the evidence by hand (interface counters for the floor's uplink, the last hour of syslog for `sw-access-12.example.com`) and pastes it into one prompt: *"Here are the counters and logs. Summarize the likely cause in three sentences for the ticket."*

- One request, one response, no tools.
- Works well **when all the information is already in hand**. The model only reads and writes.
- Fails when the evidence needed is not the evidence pasted. The model cannot go and look.

### Design 2: a fixed workflow

A script does the collecting and uses the model for judgment at fixed points:

1. Code reads the switch name from the ticket's location field and fetches uplink counters and recent syslog for it.
2. **Model call 1** classifies the evidence: `physical`, `spanning-tree`, `congestion` or `unknown`.
3. Code branches on the label: for `physical` it fetches transceiver readings; for `congestion` it fetches top talkers from flow data; for `unknown` it stops and assigns the ticket to a human.
4. **Model call 2** writes the ticket note from everything collected.

- **Code decides every step.** The model fills two slots.
- Predictable cost (always two model calls), easy to test (feed each branch a known input), easy to explain.
- Fails when the problem falls outside the branches you wrote, for example a duplex mismatch on a downstream access port.

### Design 3: an agent

The model gets the ticket text, a system prompt (*"You diagnose network problems for Example Corp. You can only read; never suggest you made a change."*) and four **read-only** tools: `get_interface_status`, `search_syslog`, `get_config_section` and `get_lldp_neighbors`. Your loop allows at most 10 iterations.

A run might look like this:

| Iteration | Model asks for | Result (summarized) |
|---|---|---|
| 1 | `get_lldp_neighbors` on `sw-access-12` | Uplink Gi1/0/48 goes to `sw-dist-02` |
| 2 | `get_interface_status` for Gi1/0/48 on both switches | Input errors climbing on `sw-dist-02` |
| 3 | `search_syslog` for `sw-dist-02` | Duplex mismatch warnings since 07:42 |
| 4 | `get_config_section` for that port on both ends | One end hard-set to 100/full, the other auto |
| 5 | (no tool) | Final note: duplex mismatch, suggested fix for a human to apply |

- **The model decides the path.** It followed the cabling it discovered, which no fixed branch anticipated.
- Cost and duration vary from run to run; testing needs many sample tickets (Domain 4).
- The tools are read-only, so a wrong step wastes tokens but changes nothing. Letting an agent *apply* the fix is a different design with an approval gate (Domain 5).

| | Single call | Workflow | Agent |
|---|---|---|---|
| Who picks the next step | Nobody: there is one step | Your code | The model |
| Model calls per ticket | 1 | Fixed (2 here) | Varies (5 here, capped at 10) |
| Handles unexpected cases | Only if the evidence was pasted | Only branches you wrote | Yes, within its tools |
| Predictability and testing | Highest | High | Lowest; needs evaluation |

## Try it yourself

A paper exercise; no API key needed.

1. Pick a task from your own job, for example "find which switch port a MAC address is on" or "summarize last night's backup failures".
2. Write it three ways, as above: what you would paste into a single prompt; the fixed steps and branches of a workflow; and the tool list (names, one-line descriptions, read-only or not) and iteration limit for an agent.
3. For the agent version, trace one plausible run as a table: iteration, tool requested, result, and what the model would decide next.
4. Mark which design you would actually ship and why. Keep the page; the next lesson gives you a checklist to test that choice.

## Key takeaways

- An agent is a model calling tools in a loop: request with tools, tool call, tool runs, result returned, repeat until an answer or a limit.
- The model only asks. Your code runs client tools; the provider runs server tools.
- Anthropic's "Building effective agents": workflows run on predefined code paths; agents let the model direct its own process and tool use. Both are agentic systems.
- Google's ADK makes the same split in code: `LlmAgent` versus the deterministic workflow agents `SequentialAgent`, `ParallelAgent` and `LoopAgent` (now deprecated in favour of graph-based and dynamic workflows).
- The same task can be a single call, a workflow or an agent; the right choice depends on whether the steps are known in advance.
- Agents need ground truth from tools at each step, and stopping conditions such as an iteration cap.
