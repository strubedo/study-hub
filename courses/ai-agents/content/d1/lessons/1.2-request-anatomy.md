## The request carries the whole state

On the Claude **Messages API** (`POST /v1/messages`), your application sends everything the model needs on every call. The Messages API is stateless by default: the documentation says you always send the full conversational history. (A beta "message threads" feature can keep the history server-side; this course builds loops the standard way.) An agent request has five parts that matter at this level:

| Part | What it is | Changes during a run? |
|---|---|---|
| `model` | The model id, for example `claude-haiku-5-5` | Usually not |
| `max_tokens` | The most output tokens this response may use | Usually not |
| `system` | The system prompt: role, rules, output format | Usually not |
| `tools` | The tool definitions the model may call | Usually not |
| `messages` | The conversation so far, oldest first | **Grows every iteration** |

The SDKs add the HTTP headers for you. If you call the API directly, the documentation's examples send `x-api-key` (your key, read from an environment variable, never typed into code), `anthropic-version` and `content-type: application/json`.

> **Watch out:** Model ids change. The ids in this course were the current ones in the Claude models overview on 2026-11-23 (`claude-opus-5-5`, `claude-sonnet-5-5`, `claude-haiku-5-5` among others). Check the models overview before you run anything.

## System prompt

The `system` parameter is a top-level field, not a message. It accepts a string or an array of text blocks and applies from the first turn. For an agent, it says who the agent works for, what it may and may not do, and how to finish: *"You diagnose network problems for Example Corp. You can only read. When you know the cause, answer in at most five sentences."* Domain 3 covers writing system prompts for agents.

When you send `tools`, the API builds a special system prompt from the tool definitions, the tool configuration and your own system prompt, so the model knows what it can call. On the newest models, the documentation also allows a message with role `system` part-way through a conversation (placed right after a user turn) for instructions that become relevant later.

## Messages and roles

`messages` is a list of turns. Each has a `role` and `content`:

- **`user`**: what comes from your side: the human's goal, and also **tool results**.
- **`assistant`**: what the model produced: text and **tool calls**.

`content` can be a plain string or an array of **content blocks**. The documentation is explicit that Claude has no separate `tool` or `function` role: tool calls are `tool_use` blocks inside assistant messages, and tool results are `tool_result` blocks inside user messages.

## Tool definitions, at overview level

Anthropic's "Define tools" page lists three core fields for a user-defined tool. The Messages API reference marks `name` and `input_schema` as required and `description` as optional, but the guide expects a detailed one in practice: without it the model has only the name and schema to go on.

| Field | Meaning |
|---|---|
| `name` | Required. Must match `^[a-zA-Z0-9_-]{1,128}$` |
| `description` | Optional in the API, essential in practice: what the tool does, when to use it, how it behaves |
| `input_schema` | Required. A JSON Schema object for the tool's input |

Optional properties exist (examples, strict schema validation, caching, deferred loading); Domain 2 covers them and how to write definitions the model uses well. For now, notice that the model sees only the schema and the description, never your implementation.

## A complete request

Here is a first request for a read-only diagnostics agent. It is written from the documented shape, not captured from a live call.

```json
{
  "model": "claude-haiku-5-5",
  "max_tokens": 1024,
  "system": "You diagnose network problems for Example Corp. You can only read device state; never claim to have changed anything. Answer in at most five sentences.",
  "tools": [
    {
      "name": "get_interface_status",
      "description": "Read-only. Returns admin status, operational status, speed, duplex and error counters for one interface on one switch. Use it when the user asks whether a port is up or erroring.",
      "input_schema": {
        "type": "object",
        "properties": {
          "device": {"type": "string", "description": "Inventory hostname, for example sw-access-12.example.com"},
          "interface": {"type": "string", "description": "Full interface name, for example GigabitEthernet1/0/48"}
        },
        "required": ["device", "interface"]
      }
    }
  ],
  "messages": [
    {"role": "user", "content": "Is GigabitEthernet1/0/48 on sw-access-12.example.com healthy?"}
  ]
}
```

## The response

A response is a `message` object. The fields an agent loop reads are `content`, `stop_reason` and `usage`:

```json
{
  "id": "msg_01EXAMPLE",
  "type": "message",
  "role": "assistant",
  "model": "claude-haiku-5-5",
  "content": [
    {"type": "text", "text": "I'll check that interface."},
    {
      "type": "tool_use",
      "id": "toolu_01EXAMPLE",
      "name": "get_interface_status",
      "input": {"device": "sw-access-12.example.com", "interface": "GigabitEthernet1/0/48"}
    }
  ],
  "stop_reason": "tool_use",
  "stop_sequence": null,
  "stop_details": null,
  "usage": {"input_tokens": 652, "output_tokens": 74}
}
```

(The ids are placeholders and the token counts are illustrative.) Read it from the top:

- **`content`** is an array of blocks. Here a short `text` block is followed by a `tool_use` block with an `id`, the tool `name`, and an `input` object that should match the tool's `input_schema`.
- **`stop_reason: "tool_use"`** tells the loop the model is waiting for a tool result. The next lesson lists every stop reason.
- **`usage`** reports what the request consumed; with prompt caching, more fields appear (Domain 3 and 4).

Other block types you will meet: `thinking` blocks when extended or adaptive thinking is on, and `server_tool_use` blocks with their results when the provider runs a server tool such as web search. A single response can contain several `tool_use` blocks when the model calls tools in parallel.

## Sending the result back

Your code runs the tool, then sends a new request with the **same tools** and a `messages` array that has grown by two entries: the model's reply, unchanged, as an `assistant` message, and a `user` message holding one `tool_result` per `tool_use`:

```json
[
  {"role": "user", "content": "Is GigabitEthernet1/0/48 on sw-access-12.example.com healthy?"},
  {"role": "assistant", "content": [
    {"type": "text", "text": "I'll check that interface."},
    {"type": "tool_use", "id": "toolu_01EXAMPLE", "name": "get_interface_status",
     "input": {"device": "sw-access-12.example.com", "interface": "GigabitEthernet1/0/48"}}
  ]},
  {"role": "user", "content": [
    {"type": "tool_result", "tool_use_id": "toolu_01EXAMPLE",
     "content": "{\"admin_status\": \"up\", \"oper_status\": \"up\", \"speed\": \"1000\", \"duplex\": \"half\", \"input_errors\": 18342, \"crc_errors\": 17990}"}
  ]}
]
```

The rules the documentation states for this message:

- Each `tool_result` carries the `tool_use_id` of the call it answers.
- The tool-result message must come **immediately after** the assistant message with the calls; nothing in between.
- In that user message, the `tool_result` blocks come **first**. Any text must follow them.
- Return a result for **every** `tool_use` block, even one that failed. For a failure, set `"is_error": true` and put a useful error message in `content`.

> **Watch out:** Tool results are data from outside your control: a log line, a ticket body, a web page. Anthropic's documentation warns that they can carry instructions planted by an attacker and recommends keeping that content inside `tool_result` blocks rather than moving it into the system prompt. Domain 5 covers the defences.

## The same idea at OpenAI and Google

| Idea | Claude Messages API | OpenAI Responses API | Gemini Interactions API |
|---|---|---|---|
| System prompt | `system` parameter | `instructions` parameter (or a `developer` or `system` message) | `system_instruction` |
| Tool definition | `name`, `description`, `input_schema` | `type: "function"`, `name`, `description`, `parameters`, `strict` | `type: "function"`, `name`, `description`, `parameters` |
| Model's call | `tool_use` block in `content` (`id`, `name`, `input`) | `function_call` item in `output` (`call_id`, `name`, `arguments` as a JSON-encoded string) | `function_call` step (`id`, `name`, `arguments`) |
| Your result | `tool_result` block in a `user` message, matched by `tool_use_id` | `function_call_output` item with `call_id` and `output` | `function_result` input with `call_id`, `name` and `result` |
| Keeping history | Send the full `messages` list each time | Send the items yourself, or chain with `previous_response_id`, or use the Conversations API | Chain with `previous_interaction_id`, or send the full step history yourself with `store=false` (stateless mode) |

Google now documents the Interactions API (`client.interactions`) as the default and calls `generateContent` a legacy API; older Gemini examples use `generateContent` with function call and function response parts. Names checked on 2026-11-23.

## Try it yourself

A paper exercise, then an offline check.

1. Copy the request above into a file `request.json` and run `python3 -m json.tool request.json` (Windows: `py -m json.tool request.json`) to confirm it is valid JSON.
2. Suppose the next response contains two `tool_use` blocks: `get_interface_status` for the same port on `sw-access-12.example.com` and on its neighbour `sw-dist-02.example.com`. Write the `messages` array for the request after that, with both results in one user message. Validate it with `json.tool`.
3. Now suppose the second tool failed with a timeout. Change its result to use `is_error` and write an error message that tells the model what it can try next.
4. Rewrite the first request in the OpenAI Responses shape using the table above (`instructions`, `input`, a function tool with `parameters`).

## Key takeaways

- A Messages API request carries `model`, `max_tokens`, `system`, `tools` and the full `messages` history; only `messages` grows during a run.
- Roles are `user` and `assistant`. Tool calls are `tool_use` blocks from the assistant; tool results are `tool_result` blocks sent as the user.
- A tool definition needs `name` and `input_schema` and, in practice, a detailed `description`; the model sees only those, not your code.
- A response's `content` is an array of blocks; `stop_reason` says why it stopped; `usage` counts tokens.
- Return one `tool_result` per `tool_use`, immediately after the call, results first, with `is_error` for failures.
- OpenAI uses `function_call` and `function_call_output` items with `call_id`; Gemini's Interactions API uses `function_call` steps and `function_result` inputs.
