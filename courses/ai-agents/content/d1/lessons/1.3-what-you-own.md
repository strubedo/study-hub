## Five things someone has to own

Whatever you build, five jobs exist. The previous lesson's options differ in who does each one.

| Job | What it covers |
|---|---|
| **Loop** | Calling the model, reading the stop signal, running tools, appending results, enforcing limits |
| **Tools** | Definitions the model sees, the code that runs, credentials, input validation |
| **State** | The conversation history, sessions that survive a restart, memory across runs |
| **Sandbox** | Where commands and code execute, its file system and its network reach |
| **Permissions** | Which tool calls run automatically, which wait for a human, which are refused |

## Who owns what

This table is this course's summary of the vendors' descriptions read on 2026-11-23 (see the previous lesson for sources). "You" means your code and your infrastructure.

| | Own loop on a model API | SDK tool runner | Agent SDK or framework | Hosted (managed) agent |
|---|---|---|---|---|
| **Loop** | You | The SDK, in your process; you set limits | The library, in your process; you set limits | The provider |
| **Tools** | You define and run all | You write functions; the runner calls them | Built-in tools plus yours (functions, MCP) | Built-in tools and MCP run by the provider; custom tools still run in your application |
| **State** | You keep the message list | The runner keeps it during a run; you persist it | Library sessions (stored where you configure) | Provider-side sessions and event history |
| **Sandbox** | Whatever your tools touch: you build any isolation | Same as own loop | Your host or container; some SDKs integrate sandbox providers | Provider's cloud sandbox, or a self-hosted sandbox on your infrastructure |
| **Permissions** | You write every check | You add checks inside tool functions; use a manual loop for approval steps | Library permission modes and callbacks you configure | Provider permission policies you configure; check defaults |

## What you give up as you move right

Each step to the right saves work and hands something over.

- **Visibility.** With your own loop you can log every request byte for byte. Libraries and services add layers; Anthropic's "Building effective agents" warns that abstractions can obscure the underlying prompts and responses and make debugging harder.
- **Control points.** A manual loop lets you pause before any tool call for approval. The tool runner page itself tells you to use a manual loop for human-in-the-loop approval, custom logging or conditional execution. Hosted agents offer approval through their own mechanisms (for example Claude Managed Agents' `always_ask` policy), on their terms.
- **Data location and retention.** Hosted sessions are stored by the provider. Claude Managed Agents' overview states that it is not currently eligible for Zero Data Retention, apart from self-hosted Claude Managed Agents (the whole service on your infrastructure, not just a self-hosted sandbox), and that transcripts persist until you delete them. For device configurations and ticket data, that may decide the question by itself.
- **Portability.** Your own loop is about 50 lines per vendor. An agent built on one vendor's managed service or agent SDK is harder to move.
- **Defaults you did not choose.** Library and service defaults are tuned for getting started: Claude Managed Agents' agent toolset defaults to `always_allow`; Gemini's managed agent sandbox has unrestricted outbound network access by default.

What you gain is just as real: a hosted agent comes with a sandbox, long-running sessions, compaction and recovery you would otherwise build; an agent SDK gives you tested file and shell tools and a permission system on day one.

## Worked choices for Example Corp

**Scenario A.** A chat bot answers "is `sw-core-01.example.com` healthy?" using three read-only tools against the monitoring API. Requests must finish in seconds, and every tool call must be logged to the SIEM.
*Choice:* own loop or the tool runner. The job is small; logging every call is easiest when you run each tool yourself. Nothing needs a sandbox.

**Scenario B.** Every night, compare the running configuration of 200 switches with the golden templates and email a drift report.
*Choice:* **not an agent.** The steps are fixed (fetch, diff, summarize). A script with one model call per device or per report (a workflow) is cheaper, faster and testable. Lesson 1.1's checklist decides this before any build option comes up.

**Scenario C.** An engineer asks for a migration plan: read the documentation repository, the current IP plan spreadsheet and vendor release notes, run small scripts to cross-check addressing, and write a plan document. It may take an hour.
*Choice:* an agent SDK (file and shell tools, sessions) on an isolated workstation or container, or a hosted agent with a sandbox if company policy allows the documents to be processed there. Either way, no production credentials inside the sandbox.

**Scenario D.** An agent may shut down a port that is flooding a VLAN, but only after the on-call engineer approves the exact command.
*Choice:* own loop, or an agent SDK with an approval callback, so that your code shows the proposed change and waits for a human before anything runs. Domain 5 builds this.

## Which one should I start with?

This is the course's advice, not a vendor rule:

1. **Learn on your own loop.** Build the minimal loop from lesson 1.2 with one read-only tool. You will understand every later abstraction better, and you will know what a library is doing for you.
2. **Move to the tool runner** when your loop code is pure plumbing: no approvals, no special logging, tools that are plain functions.
3. **Use an agent SDK** when you need what it brings: file and shell tools, sessions you can resume, subagents, a permission system. Run it where its tools cannot reach anything you are not prepared to lose.
4. **Consider a hosted agent** for long-running, asynchronous work that needs a sandbox, once you have checked the data-handling terms, the permission defaults and the network defaults against your organization's rules.

At every level keep the same habits: an iteration or budget cap, read-only tools first, a human approval for changes, and tool results treated as untrusted.

## Key takeaways

- Someone must own the loop, the tools, the state, the sandbox and the permissions; the build options differ in who.
- Your own loop gives the most visibility and control points; the tool runner removes plumbing; an agent SDK adds tools, sessions and permissions; a hosted agent adds a sandbox and long-running sessions.
- Moving toward hosted options trades away visibility, data location, portability and some control over defaults.
- Check retention and defaults before choosing hosted: Claude Managed Agents is not currently ZDR-eligible (except the fully self-hosted service), its agent toolset defaults to `always_allow`, and Gemini's managed sandbox allows all outbound traffic by default.
- Fixed, repeatable jobs are workflows, whatever build option is fashionable.
- Start with your own loop and move up only when the next level solves a problem you actually have.
