## The question is who runs the loop

Every agent runs the loop from lesson 1.1. The ways to build one differ in **who writes and runs that loop**, and with it who runs the tools, keeps the history, provides a place to execute commands and decides what is allowed. This lesson walks from "you do everything" to "the provider does almost everything", using the names and descriptions in each vendor's documentation as read on 2026-11-23. Products in this space are renamed and change status often; the beta and preview labels below are part of the facts to re-check.

| | You write the loop | The provider runs the loop |
|---|---|---|
| **Fewest moving parts** | 1. Model API + your own loop | |
| | 2. SDK tool runner (the SDK's code runs it in your process) | |
| | 3. Agent SDK or framework (a library runs it in your process) | |
| **Most handed over** | | 4. Hosted (managed) agent |

## 1. A model API with your own tool loop

You call the model's HTTP API (usually through the vendor's client SDK) and write the loop yourself, as in the previous lesson.

- **Anthropic:** the **Messages API**. The Claude Managed Agents overview sums up the split: the Messages API is "direct model prompting access", best for "custom agent loops and fine-grained control". The Agent SDK overview calls the client libraries the **Client SDK**: "You write the tool loop yourself, or let the client SDK's beta tool runner drive it."
- **OpenAI:** the **Responses API**. OpenAI's Agents guide describes it as the option for "calling models directly or building an agent from scratch", with the agent running in your application and state kept as manual history, response chaining or Conversations.
- **Google:** the **Gemini API**, where the documentation now recommends the **Interactions API** (`client.interactions`) as the default and treats `generateContent` as legacy. Its function-calling guide shows the same four steps: declare functions, call the model, execute the function in your application, send the result back.

You see every request and response, can insert approval steps anywhere, and depend on nothing but the API. You also write and maintain all of it.

## 2. An SDK tool runner

A tool runner is a helper in a vendor's client SDK that runs the loop for you **in your own process**. Anthropic documents one as the **tool runner** (beta), available in its Python, TypeScript, C#, Go, Java, PHP and Ruby SDKs. According to the "Tool runner (SDK)" page, it:

- runs your tools when Claude calls them, handles the request and response cycle, and manages conversation state;
- in Python, takes functions decorated with `@beta_tool`, whose type hints and docstring become the JSON schema;
- is started with `client.beta.messages.tool_runner(...)` and either iterated (it yields each message from Claude) or finished with `until_done()`;
- loops until Claude replies without a tool call, or until an optional `max_iterations` is reached.

The same page draws the boundary: when you need **human-in-the-loop approval, custom logging or conditional execution**, use the manual loop instead (the page also documents ways to intercept tool errors and modify results). The stop-reason guide recommends the tool runner for most tool-use implementations.

Other vendors' client SDKs, as checked on 2026-11-23:

- **OpenAI:** the function-calling guide shows the manual loop for the Responses API and points to the Agents SDK when you want orchestration packaged around it. The Python SDK's helpers page documents parsing and streaming helpers for Responses but no automatic tool loop; it does run registered `tool_handlers` for your custom tools during sessions of OpenAI's hosted Agents API (option 4).
- **Google:** the Python SDK has **automatic function calling**: pass Python functions as tools and the SDK runs them and sends results back until a final text answer. The documentation marks it Python-only and shows it on the legacy `generateContent` API; the Interactions API examples use the manual loop.

## 3. Agent SDKs and frameworks

An agent SDK is a library that brings its own loop **plus** a set of agent features: built-in tools, sessions, permissions, multi-agent patterns. It still runs inside your process or service.

- **Claude Agent SDK** (Python package `claude-agent-sdk`, TypeScript `@anthropic-ai/claude-agent-sdk`). Its overview says it lets you "build production AI agents with Claude Code as a library": the same tools, agent loop and context management that power Claude Code. Listed capabilities include built-in tools (read, write and edit files, run commands, search the web), hooks, subagents, MCP, permissions, sessions, and skills loaded from `.claude/` directories. You call `query()` with a prompt and `ClaudeAgentOptions`; options include `allowed_tools`, `permission_mode`, `max_turns` and `max_budget_usd`. Both SDKs bundle a native Claude Code binary.
- **OpenAI Agents SDK** (Python `openai-agents`, TypeScript `@openai/agents`). OpenAI describes it as the track for when "your server owns deployment, tool implementations, state storage, and approval decisions, while the SDK runs the agent loop and invokes those tools". Core names are `Agent` and `Runner`; the runner handles the agent loop and handoffs between agents.
- **Google Agent Development Kit (ADK)** (Python `google-adk`), "an open-source, code-first toolkit for building, evaluating, and deploying" agents. Its primitives include `LlmAgent`, the workflow agents `SequentialAgent`, `ParallelAgent` and `LoopAgent` (marked deprecated in the ADK documentation as of 2026-11-23: in Python, TypeScript, Go and Kotlin these template workflows are superseded by graph-based and dynamic workflows), `FunctionTool`, `Session` and `State`, `Memory`, and a `Runner` that manages execution. It is optimized for Gemini but supports other models through its `BaseLlm` interface.

Anthropic's "Building effective agents" adds a caution that applies to every framework: they make it easy to start, but extra layers of abstraction can hide the underlying prompts and responses and make debugging harder. Its advice is to start with the API directly and, if you use a framework, understand the code underneath.

> **Real world:** The Claude Agent SDK inherits Claude Code's file and shell tools. That is a large capability to hand a model on a production server. Its `permission_mode` options include `default` (calls that need approval and match no allow rule go to your `can_use_tool` callback), `dontAsk` (any call that would prompt is denied instead, which suits headless agents paired with an `allowed_tools` list) and `bypassPermissions`, which approves tool calls without prompting and which the docs say to use only in controlled environments where you trust every possible operation.

## 4. Hosted (managed) agents

Here the provider runs the loop, the tool execution and usually a sandbox to work in. Your application creates an agent configuration, starts a session and exchanges events with it.

- **Claude Managed Agents** (beta; every endpoint needs a beta header that the SDK sets for you). Anthropic calls it a "pre-built, configurable agent harness that runs in managed infrastructure", best for "long-running tasks and asynchronous work". It has four concepts: **Agent** (model, system prompt, tools, MCP servers, skills), **Environment** (an Anthropic-managed cloud sandbox or a self-hosted sandbox on your infrastructure), **Session** (a running agent instance) and **Events** (messages between your application and the agent, streamed with server-sent events). Built-in tools cover bash, file operations, web search and fetch, and MCP servers. **Permission policies** (`always_allow`, `always_ask`, `auto`) control server-executed tools; the docs give `always_allow` as the default for the agent toolset and `always_ask` for MCP toolsets. **Custom tools** run in your application, outside those policies. Sessions are stateful and stored server-side, and the overview states that Managed Agents is not currently eligible for Zero Data Retention. The exception is self-hosted Claude Managed Agents, where the whole service runs on your infrastructure and you store the data; a self-hosted *sandbox* alone does not make it eligible.
- **OpenAI Agents API**: "access to the Codex harness through an OpenAI-managed API". OpenAI manages sessions, orchestration, context compaction and recovery; your application provides tools and chooses the execution environment: an OpenAI-hosted sandbox, a self-hosted sandbox, or none. Its concepts are agent, environment, session, and events and items.
- **Gemini managed agents** (Public Preview): "a configurable agent harness" where a single API call provisions a Linux sandbox in which the agent reasons, runs code, manages files and browses the web. The listed agents are the general-purpose **Antigravity agent** and **Deep Research**. The docs warn that the sandbox has **unrestricted outbound network access by default**, restrictable with an allowlist.

> **Watch out:** "Managed" moves the loop, not the responsibility. Defaults such as "agent tools run without asking" and "the sandbox can reach the internet" are safe for a demo and wrong for a network operations agent. Read the permission and network settings before the first real task.

## Key takeaways

- The four ways to build differ in who runs the loop: your code, an SDK helper, an agent library, or the provider's service.
- Model APIs with your own loop: Claude Messages API, OpenAI Responses API, Gemini Interactions API (`generateContent` is legacy).
- Anthropic's tool runner (beta) runs the loop in your process from `@beta_tool` functions; use a manual loop for approvals, custom logging or conditional execution.
- Agent SDKs: Claude Agent SDK (Claude Code as a library), OpenAI Agents SDK (`Agent`, `Runner`), Google ADK (`LlmAgent`, graph-based workflows, which supersede the deprecated workflow agents, `Runner`).
- Hosted agents: Claude Managed Agents (agent, environment, session, events), OpenAI Agents API (managed Codex harness), Gemini managed agents (Antigravity, Deep Research).
- Check permission and network defaults on any SDK or hosted agent before giving it real tools.
