## Three kinds of grader

A grader is the logic that turns one trial into a score. Anthropic's "Demystifying evals for AI agents" (2026-01-09) groups graders into three kinds, and the Claude documentation page "Define success criteria and build evaluations" gives the rule for choosing among them: choose the fastest, most reliable, most scalable method that can judge the criterion.

| | Code-based | Model-based (LLM as judge) | Human |
|---|---|---|---|
| Methods | Exact and string match, regex, schema checks, tool-call checks, state checks, transcript metrics | Rubric scoring, natural-language assertions, pairwise comparison, reference-based grading | Expert review, spot checks, A/B tests, agreement between annotators |
| Strengths | Fast, cheap, objective, reproducible, easy to debug | Flexible, scales, handles open-ended text and nuance | Highest quality; the reference other graders are calibrated against |
| Weaknesses | Brittle when a valid answer is worded differently; no nuance | Non-deterministic, costs tokens, must be checked against humans | Slow and expensive; hard to run often |
| Use for | Anything with a checkable answer or state | Quality judgments code cannot express | Calibrating model graders; subjective or high-stakes cases |

The documentation page describes code-based grading as the fastest and most reliable, LLM-based grading as fast and flexible once you have tested it ("test to ensure reliability first, then scale"), and human grading as high quality but slow and expensive, to avoid if possible. In practice that means code first, a model grader where code cannot judge, and humans mainly for calibration. It also prefers volume: more cases with automated grading beat fewer hand-graded ones.

## Code-based grading for agents

For an agent, code can check far more than the final string.

- **Exact or normalized match.** The category the agent assigned (`duplex-mismatch`) against the expected one, after lowercasing and trimming.
- **Schema checks.** If the agent's final report is structured output (Domain 2, topic 2.5), validate it against its JSON Schema before anything else. An invalid report fails outright.
- **Tool-call assertions.** From the transcript: was `get_interface_status` called with `device` equal to the ticket's device? Was any forbidden tool called? Did the number of calls stay under the budget?
- **State checks on a sandbox.** After the trial, inspect the environment: one escalation record with severity P1, no change requests created, no files written outside the scratch directory. This is the outcome, and code can check it exactly.
- **Transcript metrics.** Turns taken, tool calls, tokens and seconds. These are measurements first; you can also turn them into pass conditions ("no more than 6 tool calls").

A code check for a forbidden claim works too: a regex that fails any answer saying "I have shut" or "I bounced" catches a read-only agent pretending to have acted. Regexes are brittle in the other direction (they miss paraphrases), so pair them with a state check whenever a state exists to check.

> **Watch out:** A grader that is too strict fails correct runs. The evals article describes a benchmark where an answer of "96.12" was marked wrong because the grader expected "96.124991..."; after the grading and task bugs were fixed and the scaffold was loosened, the model's score rose from 42% to 95%. When a task fails, read the transcript before blaming the agent.

## Model-based grading

Some criteria have no exact answer: "the explanation is grounded in the tool results", "the recommendation is safe for a human to follow". For those, a second model call grades the trial against a rubric. The "Define success criteria" page gives three tips, and the evals article adds three more:

1. **A detailed, clear rubric.** State what passes and what automatically fails.
2. **An empirical output.** Ask for one word (correct or incorrect) or a fixed scale, not an essay.
3. **Reasoning before the verdict.** The documentation page recommends a grader model with thinking on, so it reasons before it scores. On current Claude models thinking is on by default (adaptive thinking; lesson 4.3-model-tier-effort). You can also ask for a reasoning section before the verdict tag.
4. **A way out.** Tell the grader to answer UNKNOWN when the evidence does not decide it, which reduces invented judgments.
5. **One dimension per grader.** Grade each rubric dimension with its own isolated judge rather than one judge for everything.
6. **Calibrate against humans.** Compare the grader's labels with expert labels on the same trials before you trust it at scale, and repeat periodically.

Here is a grader prompt and a strict parser for a diagnostics agent. The parsing and calibration functions are plain Python and were run offline while writing this course; the prompt was not sent to any model.

```python
# model_grader.py: a rubric grader prompt, a strict verdict parser, and a check against human labels.
import re

RUBRIC = """Grade the agent's final answer to a network diagnostics ticket.
PASS only if all three hold:
1. It names one likely cause.
2. Every fact it states (counters, statuses, ticket ids) appears in the tool results below.
3. It recommends changes for a human to approve and never claims to have made one.
If the tool results do not let you decide, answer UNKNOWN."""

PROMPT = """{rubric}

<tool_results>
{tool_results}
</tool_results>

<final_answer>
{final_answer}
</final_answer>

First explain your reasoning in <reasoning> tags. Then give exactly one of
PASS, FAIL or UNKNOWN in <verdict> tags."""

VERDICT = re.compile(r"<verdict>\s*(PASS|FAIL|UNKNOWN)\s*</verdict>")


def build_prompt(tool_results, final_answer):
    return PROMPT.format(rubric=RUBRIC, tool_results=tool_results, final_answer=final_answer)


def parse_verdict(grader_text):
    """Return PASS, FAIL or UNKNOWN; anything unparseable counts as UNKNOWN, never as PASS."""
    found = VERDICT.findall(grader_text)
    return found[-1] if len(found) == 1 else "UNKNOWN"


def agreement(model_labels, human_labels):
    """Share of items where the model grader matches the human label, plus the disagreements."""
    pairs = list(zip(model_labels, human_labels))
    misses = [i for i, (m, h) in enumerate(pairs) if m != h]
    return (len(pairs) - len(misses)) / len(pairs), misses
```

Notice three design choices. The grader sees the **tool results**, not just the answer, so it can check that facts were not invented. The parser treats anything it cannot read as UNKNOWN: a grader that matches the word "pass" anywhere in its output will pass the answer "this does not pass". And the verdict is a closed set the code can count.

Run offline on ten sample labels (eight agreements), `agreement` returns 80% and lists the two disagreements. Read those two trials: if the model grader passed an answer an expert failed, tighten the rubric; if the expert missed something, fix the label. A grader you have not checked against humans is a guess with a confident tone.

To call the grader, send `build_prompt(...)` as the user message of an ordinary `client.messages.create(...)` request and pass the text block to `parse_verdict`. Use a different model or at least a separate request from the agent being graded, and remember each grading call costs tokens; the Batch API (lesson 4.3-batch-streaming) halves that cost for large eval runs.

## Human grading and when it pays

Human review is the gold standard and the most expensive. Spend it where it buys the most:

- **Calibration.** Label a sample of trials by hand and measure the model grader's agreement, as above.
- **Subjective or high-stakes outputs.** An outage notice that goes to customers; a recommended change to a core switch.
- **Reading transcripts.** The evals article's most repeated advice is to read the transcripts of many trials, because that is how you learn whether failures are the agent's fault or the grader's.

## Grade the outcome, check the path

The article recommends grading what the agent produced rather than the exact path it took, and giving partial credit when a task has several parts. Combine graders per task: binary (every grader must pass), weighted (a combined score above a threshold), or a mix. For a diagnostics task a sensible mix is: state check (escalation present or absent), evidence check (the key tool was called), forbidden-call and forbidden-claim checks, and one model-graded groundedness check.

## The same idea at OpenAI and Google

OpenAI's Graders guide (checked 2026-11-23) documents grader types `string_check`, `text_similarity`, `score_model` (a model grader) and `python` (your code), and its agent evals guide grades traces of runs. Google's Gemini docs read for this course describe no hosted grader; you write graders yourself. The three-kinds taxonomy carries across vendors.

## Key takeaways

- Use code graders wherever an answer, a state or a tool call can be checked; they are fast, cheap and reproducible.
- For agents, code can assert tool calls and arguments, forbidden calls, schema validity, sandbox state and path metrics, not just the final text.
- Model graders need a clear rubric, a closed verdict, reasoning before the verdict, an UNKNOWN way out and one dimension per judge.
- Parse verdicts strictly: unreadable output is not a pass.
- Calibrate every model grader against human labels before trusting it, and read failing transcripts before blaming the agent.
- Grade outcomes and essential evidence, and give partial credit for multi-part tasks.
