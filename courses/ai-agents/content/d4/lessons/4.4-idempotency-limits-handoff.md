## Why calls repeat

The previous lesson made model calls safe to retry: a model call has no side effects, so sending it twice costs tokens and nothing else. Tool calls are different. An agent's tool call can be executed more than once in ordinary operation:

- **The model repeats itself.** A loop (lesson 4.2-reading-transcripts) calls the same tool with the same arguments several times.
- **Your code retries.** A tool call to the ticket system times out; your wrapper retries; the first attempt had in fact succeeded.
- **A run resumes.** The process crashes after a tool ran but before its result was saved, and the resumed run (Domain 3, sessions) asks for the same call again.
- **Parallel calls overlap.** Two subagents or two parallel tool calls ask for the same change.

For a read-only tool none of this matters: reading interface counters twice is harmless. For a tool that opens a ticket, pages the on-call engineer or pushes a config, a repeat is a second ticket, a second page or a second change. Make every state-changing tool **idempotent**: calling it twice with the same intent has the same effect as calling it once.

## Four ways to make a tool safe to repeat

| Technique | How it works | Example Corp example |
|---|---|---|
| **Read-only by design** | Nothing to duplicate | `get_interface_status`, `search_tickets`: the diagnostics agent's default |
| **Idempotency key** | Each intended action gets a key; the target system (or your tool wrapper) records the key and returns the earlier result on a repeat | Key = hash of run id + tool + stable fields (device, severity) |
| **Check-then-act** | Look for an existing effect before creating one | Search for an open incident on this device from this run before opening another |
| **Declarative actions** | Ask for a state, not a change: "ensure X", never "toggle X" | `set_port_admin_state(state="down")` is safe to repeat; `bounce_port` is not |

And one control that sits in front of all of them: a **dry-run flag** that defaults to on, so the tool returns what it *would* do and nothing happens until a human approves (below).

The sketch below combines a key, check-then-act and a dry run. It is pure Python with an in-memory store standing in for the ticket system, and it was run offline while writing this course.

```python
# safe_tools.py: an idempotent ticket tool and a per-run budget, both pure Python.
import hashlib
import json

TICKETS = {}          # stands in for the ticket system; key -> ticket


def idempotency_key(run_id, tool_name, stable_fields):
    """Same run, same tool, same stable fields -> same key, however often the call repeats."""
    raw = json.dumps([run_id, tool_name, stable_fields], sort_keys=True)
    return hashlib.sha256(raw.encode()).hexdigest()[:16]


def open_ticket(run_id, device, severity, summary, dry_run=True):
    # Key on stable fields only: a reworded summary on a retry must not open a second ticket.
    key = idempotency_key(run_id, "open_ticket", {"device": device, "severity": severity})
    if key in TICKETS:                                    # check ...
        return {"status": "already_open", **TICKETS[key]}
    if dry_run:
        return {"status": "dry_run", "would_open": {"device": device, "severity": severity, "summary": summary}}
    ticket = {"ticket_id": f"INC-{1000 + len(TICKETS)}", "device": device, "severity": severity}
    TICKETS[key] = ticket                                 # ... then act, once
    return {"status": "opened", **ticket}
```

Calling it three times for the same P1 on `sw-core-01.example.com` (once as a dry run, then twice for real with the summary reworded the second time) prints `dry_run`, then `opened` with `INC-1000`, then `already_open` with the same `INC-1000`. Three design points:

- **Key on stable fields, not free text.** The model rewords summaries between attempts. A key that included the summary would open a second ticket on the retry.
- **Tell the model what happened.** `already_open` with the ticket id is a result the model can act on; a silent success would invite it to try again.
- **Let the target enforce it where it can.** A check-then-act in your wrapper has a race when two runs act at the same moment. If the ticket system or device API accepts an idempotency key or enforces uniqueness itself, use that; your check is then a second line of defence. (This is general engineering practice, not a vendor rule.)

## Iteration, token and spend limits

Every agent needs limits it cannot talk its way past, because the failure shapes in lesson 4.2-reading-transcripts (loops, stalls) are exactly the ones that burn money. Combine your own counters with what the SDKs and platforms provide.

**Your own counters**, checked before each model call and charged after it:

```python
class BudgetExceeded(Exception):
    pass


class RunBudget:
    """Your own counters: checked before every model call, charged after it."""

    def __init__(self, max_steps=8, max_tokens=200_000, max_cost=0.50):
        self.limits = {"steps": max_steps, "tokens": max_tokens, "cost": max_cost}
        self.used = {"steps": 0, "tokens": 0, "cost": 0.0}

    def before_call(self):
        for name, limit in self.limits.items():
            if self.used[name] >= limit:
                raise BudgetExceeded(f"{name} limit reached: {self.used[name]} of {limit}")

    def charge(self, input_tokens, output_tokens, cost):
        self.used["steps"] += 1
        self.used["tokens"] += input_tokens + output_tokens
        self.used["cost"] += cost
```

Run offline with a 50,000-token limit and a growing history (calls charged 14,400, 16,400, 18,400, 20,400 and 22,400 tokens), it allowed calls 1 to 4 (49,200 tokens after call 3, 69,600 after call 4) and stopped before call 5. The overshoot is the point to notice: a check before each call can let the last call push past the limit, so leave headroom or estimate the next request first (`client.messages.count_tokens`, Domain 3). Add a repeated-call detector and a wall-clock limit per run for the same reason.

**Limits the SDKs and platforms provide** (checked 2026-11-23; Domains 1 and 3 confirmed the first three):

| Where | Limit | What happens |
|---|---|---|
| Anthropic SDK tool runner (beta) | `max_iterations` | The runner stops after that many iterations |
| Claude Agent SDK | `max_turns`, `max_budget_usd` in `ClaudeAgentOptions` | The result message has subtype `error_max_turns` or `error_max_budget_usd` |
| Messages API, per request | `max_tokens` | Hard cap on output, thinking included; `stop_reason: "max_tokens"` |
| Messages API task budgets (beta, header `task-budgets-2026-03-13`) | `output_config.task_budget: {"type": "tokens", "total": N}`; minimum 20,000 | **Advisory**: the model sees a countdown and paces itself; the page says it is a soft hint, not a hard cap |
| Claude Managed Agents sessions (beta) | A session `budget` in dollars | A hard stop, checked before each model request: the session goes idle with `stop_reason: budget_reached`; the request in flight still completes, so the cost can land a fraction past the cap |
| Claude Console | Organization and workspace spend limits | Requests return HTTP 400 when a limit you set is reached |
| OpenAI Agents SDK | `max_turns` on `Runner` | Raises `MaxTurnsExceeded` (or calls an error handler you register) |

Use them in layers: your counters and `max_tokens` inside each run, an SDK or platform limit as a second check, and a workspace spend limit as the backstop for everything.

## Handing off to a human

A limit stops the run; a hand-off makes the stop useful. Decide in advance when the agent must stop and ask, rather than leaving it to the model's judgment alone:

- the next action is irreversible or changes production (always, for a diagnostics agent: it has no such tool);
- the request is outside the agent's scope or permissions (a change request to a read-only agent);
- the severity calls for a person now (a site down, a security event);
- the same step has failed repeatedly, or a limit was reached;
- the evidence conflicts and more reads will not settle it.

Then hand over everything the engineer needs to continue without rerunning the agent: the goal, what was checked (with the tool results that matter), what was tried and failed (with errors and request ids), the current hypothesis and how confident the agent is, the proposed next step, what was **not** done, and where the full transcript is. A structured hand-off, written from this course's design (validated with `python3 -m json.tool`):

```json
{
  "run_id": "run-2026-11-23-0412",
  "status": "needs_human",
  "reason": "site_down_escalation",
  "goal": "Find why Site B lost connectivity",
  "checked": [
    {"tool": "get_interface_status", "device": "sw-core-01.example.com", "interface": "Te1/1/1", "finding": "oper_status down"},
    {"tool": "get_interface_status", "device": "sw-core-01.example.com", "interface": "Te1/1/2", "finding": "oper_status down"}
  ],
  "failed": [
    {"tool": "search_tickets", "error": "ticket system timeout after 2 retries", "request_id": null}
  ],
  "hypothesis": "Both uplinks down at once suggests upstream or power, not one optic",
  "confidence": "medium",
  "proposed_next_step": "Engineer to check the upstream provider status and the rack PDU",
  "not_done": ["No changes made", "No customer notice sent"],
  "transcript": "logs/run-2026-11-23-0412.jsonl"
}
```

### Approval gates before irreversible actions

When an agent can change things, put a gate in code, not in the prompt: the loop pauses before executing a state-changing tool call, shows a person the exact call (tool, arguments and the dry-run result), records who approved it, and only then runs it with `dry_run=False`. Domain 1 noted that the SDK tool runner documentation recommends a manual loop when you need human-in-the-loop approval. Domain 5 builds this properly: confirmation for irreversible actions (topic 5.1), permission and approval modes (topic 5.3) and a change agent with a human approval gate (topic 5.4).

## Key takeaways

- Model calls are safe to retry; tool calls with side effects are not unless the tool is idempotent.
- Read-only tools are naturally safe; for the rest use idempotency keys on stable fields, check-then-act, declarative "ensure state" actions and a dry-run default.
- Return "already done" with the existing id so the model does not try again; let the target system enforce uniqueness where it can.
- Layer limits: your own step, token, cost and time counters checked before each call; SDK limits (`max_iterations`, `max_turns`, `max_budget_usd`); `max_tokens` per request; spend limits as the backstop. Task budgets are advisory, not a cap.
- Stop and hand off for irreversible actions, out-of-scope requests, high severity, repeated failure or exhausted limits, with goal, evidence, failures, hypothesis, proposed next step and what was not done.
- Approval gates belong in the loop's code before any state-changing call (Domain 5).
