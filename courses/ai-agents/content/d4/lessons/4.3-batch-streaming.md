## Two levers that pull in opposite directions

**Batch processing** trades latency for price: you submit many requests, wait (minutes to hours), and pay half. **Streaming** trades nothing for perceived speed: the same request, the same price, but output arrives as it is generated instead of all at the end. An agent platform usually needs both, for different jobs. This lesson covers each as the Claude documentation describes it on 2026-11-23, then the other cost and latency levers the vendors document.

## The Message Batches API

From the "Batch processing" page and the Python SDK page:

- **Asynchronous.** You create a batch of Messages requests; each is processed independently; you poll until the batch's `processing_status` changes from `in_progress` to `ended`, then fetch results.
- **Discounted.** All usage in a batch is charged at 50% of standard prices, input and output. The pricing page says the batch discount stacks with prompt caching.
- **Completion window.** Most batches finish in under an hour. Results are available when every request has finished or after 24 hours, whichever comes first; requests not processed within 24 hours expire. Results stay downloadable for 29 days.
- **Size.** Up to 100,000 requests or 256 MB per batch, whichever comes first (a 413 `request_too_large` above that).
- **Matching results.** Each request carries a `custom_id` (1 to 64 letters, digits, hyphens and underscores). Results may come back in any order, so always match on `custom_id`.
- **Result types.** `succeeded`, `errored`, `canceled` and `expired`. You are not billed for the last three. The failure of one request does not affect the others.
- **What works inside.** Almost any Messages request: tool use including server tools (the batch worker runs the same server-side loop and may run more iterations before a `pause_turn`), system prompts, multi-turn histories, thinking, prompt caching (the page suggests the 1-hour cache lifetime, since batches can outlast five minutes).
- **What does not.** `stream: true`, fast mode's `speed`, server-side `fallbacks` and `max_tokens: 0` are rejected inside a batch.
- **Limits.** Batches have their own rate limits (requests per minute and requests waiting in the queue) and are not subject to ramp limits. They are not eligible for zero data retention.

### Which agent work suits batching

The cost-optimization page recommends routing every request nobody is waiting on through the Batch API and keeping the interactive path for the rest, and names evaluation runs, backfills and scheduled jobs. For an IT and network operations agent:

| Good fit | Poor fit |
|---|---|
| Running the eval suite: every case × every trial, and every model-grader call | An engineer waiting on a diagnosis |
| A nightly pass over yesterday's closed tickets to tag root causes | An outage, where minutes matter |
| Summarizing a week of syslog extracts per site | A multi-step loop with **client** tools: each iteration needs your tool results before the next request, so every step becomes a separate batch round trip |
| Re-scoring old transcripts after a rubric change | Anything that needs `stream`, fast mode or server-side fallback |

The last poor fit is this course's reasoning, not a vendor rule: a batch request is one Messages request. A single-step task, or one whose tools are all server tools, fits in one request; a client-tool loop does not.

Here is the eval run's grading step as a batch. It reuses the grader prompt from lesson 4.1-grading-methods; it was compiled, not run.

```python
# batch_grade.py: send model-grader calls for an eval run through the Message Batches API.
# Written from the batch processing page and the Python SDK page (compiled, not run).
import time

import anthropic

from model_grader import build_prompt, parse_verdict   # from lesson 4.1-grading-methods

client = anthropic.Anthropic()
GRADER_MODEL = "claude-haiku-5-5"   # ids change: check the models overview


def submit(trials):
    """trials: list of dicts with an id ("T3-trial-2"), tool_results and final_answer."""
    batch = client.messages.batches.create(requests=[
        {"custom_id": t["id"],      # 1-64 chars: letters, digits, hyphens, underscores
         "params": {"model": GRADER_MODEL, "max_tokens": 4096,
                    "messages": [{"role": "user",
                                  "content": build_prompt(t["tool_results"], t["final_answer"])}]}}
        for t in trials])
    return batch.id


def collect(batch_id, poll_seconds=60):
    while client.messages.batches.retrieve(batch_id).processing_status != "ended":
        time.sleep(poll_seconds)
    verdicts = {}
    for entry in client.messages.batches.results(batch_id):   # order is not guaranteed
        if entry.result.type == "succeeded":
            text = "".join(b.text for b in entry.result.message.content if b.type == "text")
            verdicts[entry.custom_id] = parse_verdict(text)
        else:                                  # errored, canceled or expired: not billed; resubmit
            verdicts[entry.custom_id] = "RETRY:" + entry.result.type
    return verdicts
```

The page's own advice applies: dry-run one request shape with the ordinary Messages API first, so a validation error does not fail thousands of requests.

## Streaming

Streaming returns the response as server-sent events: a `message_start`, then for each content block a `content_block_start`, any number of `content_block_delta` events (`text_delta`, `input_json_delta` for tool inputs, `thinking_delta`) and a `content_block_stop`, then one or more `message_delta` events (whose `usage` counts are cumulative) and a `message_stop`. `ping` events can appear anywhere.

Why an agent streams:

1. **Perceived latency.** A user watching a diagnosis sees text within the time to first token instead of waiting for the whole answer. The reduce-latency page names time to first token as the metric that matters when streaming.
2. **Long outputs.** The Python SDK raises a `ValueError` if a non-streaming request is expected to take longer than about 10 minutes, and the errors page recommends streaming (or batches) for long requests, because idle connections can be dropped by networks. With `max_tokens` at 64,000 for agentic work (lesson 4.3-model-tier-effort), stream.

You do not have to handle events yourself. The SDK can consume the stream and hand back the complete message:

```python
# stream_final.py: stream a long final report, showing text as it arrives (compiled, not run).
import anthropic

client = anthropic.Anthropic()


def write_report(messages, tools):
    with client.messages.stream(model="claude-opus-5-5", max_tokens=64000,
                                tools=tools, messages=messages) as stream:
        for text in stream.text_stream:
            print(text, end="", flush=True)    # the user sees progress at once
        return stream.get_final_message()      # same Message object as a non-streaming call
```

Three streaming details that matter for reliability:

- **Errors can arrive after HTTP 200.** The stream can carry an `error` event (for example `overloaded_error`, which would be a 529 without streaming). Your code must handle it, not only HTTP errors.
- **Partial recovery is limited.** The streaming page says tool use and thinking blocks cannot be partially recovered; you can resume from the last text block. On Claude 4.6 and later models, resume by sending a user message containing the partial text and asking the model to continue, not by prefilling an assistant message.
- **Streaming does not lower cost.** Same tokens, same price. With thinking, `display: "omitted"` shortens the time to the first text token, because no thinking text is streamed; you still pay for the thinking.

## Other levers the documentation describes

| Lever | What it saves | Where it is covered |
|---|---|---|
| Prompt caching | Input cost and time; cache reads do not count toward input-token rate limits | Domain 3, lesson 3.1-prompt-caching; costed in 4.3-token-accounting |
| Parallel tool calls | Wall-clock time: read-only lookups run concurrently, results go back in one message | Domain 2, lesson 2.2-robust-loop |
| Trimming tool results | Input tokens on every later call: filter, paginate, summarize, return references; defer rarely used tool definitions with tool search | Domain 3, lesson 3.1-context-budgets; "Optimizing for cost and intelligence" |
| Shorter answers | Output tokens, which cost five times input on current models and are re-sent as input every later turn | Ask for the answer you will read |
| Effort and model tier | Both cost and time | Lesson 4.3-model-tier-effort |
| Fast mode | Time only: up to 2.5× higher output tokens per second on supported models, set with `speed: "fast"`, at premium prices; it speeds output, not time to first token; not available in batches; switching speed mid-conversation misses the cache | "Fast mode" page |

Two things are deliberately absent. Priority Tier is documented as legacy: commitments are no longer sold. And no lever replaces measuring: the cost page reports that context editing made a short agent run cost more, while the same family of levers saved money on long runs. Check every change against your eval set's cost and pass rate.

## The same idea at OpenAI and Google

OpenAI's Batch API (checked 2026-11-23) also gives a 50% discount, takes a JSONL file of requests with `custom_id`, and supports only `completion_window: "24h"`; its Flex processing tier (`service_tier: "flex"`) is being wound down. Google's Gemini Batch API is likewise 50% off with a 24-hour target turnaround; its optimization page also lists a Flex tier (50% off, best-effort, minutes) and a Priority tier (75% to 100% more, for user-facing traffic).

## Try it yourself

Paper first; the optional step uses the API.

1. Sort every job your agent platform runs (or plans to run) into "someone waits" and "nobody waits". For the second list, which jobs are single-request and could be batched directly?
2. Estimate the saving if your nightly eval run (cases × trials × grader calls) went through batch at 50%.
3. Mark the calls in your agent whose output a person reads as it arrives. Those stream; check that your code handles an `error` event mid-stream.
4. Optional: with `pip install anthropic` and your key set (`export ANTHROPIC_API_KEY=<api-key>`; PowerShell `$env:ANTHROPIC_API_KEY = "<api-key>"`), submit a batch of three tiny grading requests on the small tier, poll every minute, and print the verdicts by `custom_id`.

## Key takeaways

- The Message Batches API is asynchronous, charges 50% on all tokens, usually finishes within an hour and expires unprocessed requests after 24 hours; match results by `custom_id`.
- Batch the work nobody waits for: eval runs, grader calls, nightly analysis, backfills. A client-tool loop would need one batch round trip per step (this course's reasoning: each batch item is one Messages request).
- `stream`, fast mode, server-side fallbacks and `max_tokens: 0` are not allowed inside a batch.
- Stream for perceived latency and for long outputs; the SDK insists on streaming for requests expected to exceed about 10 minutes.
- Streams can carry errors after HTTP 200, and tool-use and thinking blocks cannot be partially recovered.
- Other levers: caching, parallel read-only tool calls, trimmed tool results, shorter answers, effort and tier; fast mode buys speed at a premium. Measure each one.
