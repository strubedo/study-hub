## Two dials: which model, and how hard it works

Cost and latency in an agent come down to two choices per call: the **model tier** (a small, fast, cheap model or a large, capable, expensive one) and how much work that model does on the call (**effort** and **thinking**). The vendors now treat the second dial as at least as important as the first. Anthropic's "Choosing the right model" page (checked 2026-11-23) says plainly that tuning effort is often a better lever than switching models.

Model ids and per-model defaults below are as the documentation lists them on 2026-11-23. They change with every release, so check the models overview and the effort page before you rely on any of them.

## Choosing a tier per job

The choosing-a-model page describes two ways to start:

- **Efficiency-first.** Start on the small tier (today Claude Haiku 5.5), test thoroughly, and move up only where a capability gap shows. Best for prototypes, tight latency, cost-sensitive and high-volume straightforward tasks.
- **Capability-first.** Start on a strong model (the page says most workloads start with Claude Opus 5.5), get it working, then lower effort or move parts of the work to cheaper models.

Its selection matrix puts the small tier at "lowest latency and price" with subagent tasks among its uses, and Haiku 5.5's effort guidance names classification, extraction and routing as its home ground. For an agent that is a natural split:

| Job in the agent | Tier | Why |
|---|---|---|
| Routing an incoming ticket to the right workflow | Small, low effort | A classification with a checkable answer; runs on every ticket |
| Extracting fields from tool output (interface, counters, timestamps) | Small | Bounded, verifiable, high volume |
| Summarizing a large tool result before it enters the main context | Small | Cheap reduction of context for the expensive model |
| Subagent sub-tasks (check one device, read one runbook) | Small or medium | Many calls, narrow scope |
| Planning a multi-step investigation; weighing conflicting evidence | Large | Errors here compound through the rest of the run |
| The final diagnosis and recommendation a human acts on | Large | Highest cost of being wrong |

This is the course's own mapping built on the vendor guidance. The cost page's "Combine models" section adds a caution: tune one model (sweep its effort levels) before adding a second, and keep a pairing only if it beats the single model's whole curve of score against cost. It describes two pairings, an **advisor** (a cheaper model runs the loop and escalates hard decisions) and an **orchestrator** (a frontier model plans and delegates bulk work to cheaper workers), and reports that an advisor helps only when the executor actually consults it. Measure on your eval set, in cost per completed task (lesson 4.3-token-accounting).

> **Watch out:** Switching models mid-run costs more than the rate difference suggests. Prompt caches are per model, so the first call on the new model pays full price for the whole history. Route at the edges of a run (triage before, a summary or final call after), not back and forth inside the loop.

## Effort

The Messages API takes effort as `output_config.effort`. The effort page (checked 2026-11-23) documents five levels:

| Level | Documented use |
|---|---|
| `low` | Most efficient: simpler tasks that need the best speed and lowest cost, such as subagents |
| `medium` | Balanced; agentic tasks needing a mix of speed, cost and performance |
| `high` | As many tokens as the task needs: complex reasoning, difficult coding, agentic tasks |
| `xhigh` | Long-horizon agentic and coding work |
| `max` | Absolute maximum capability with no constraint on tokens |

Facts worth carrying into your design:

- **Defaults differ by model.** Most models default to `high`; the page lists Claude Opus 5.5 and Claude Haiku 5.5 as defaulting to `medium`. Setting the default explicitly behaves exactly like omitting it. Not every model supports `xhigh` or `max`.
- **Effort affects all output tokens**: text, tool calls and their arguments, and thinking. Lower effort means fewer and terser tool calls.
- **It is a behavioural signal, not a budget.** At low effort the model still thinks on hard problems, just less. For a hard per-request cap you have `max_tokens`; for spend across a run see lesson 4.4-idempotency-limits-handoff.
- **Changing the top-level effort between requests can cost you the prompt cache.** The resolved effort value is rendered into the prompt, so the prompt-caching page says a change can invalidate message blocks, and on some models the tool and system caches too. The thinking steering page includes a script whose third request switches to `low` effort and is expected to miss the cache. Some models support a per-message effort setting (beta) that preserves the cache; the effort page lists which.
- **Sweep it on your evals.** Every per-model recommendation on the page ends the same way: start at the default and step up or down where your evals show quality holds.

The cost page reports one useful pattern for checkable work: run every task at `low` and re-run only the failures at `high`. In Anthropic's measurement this cost a little over half of running everything at `high`, at about the same pass rate. It needs a reliable failure signal (a grader or test), and failures take two runs' worth of time.

```python
# Two calls in one agent, written from the effort and choosing-a-model pages (compiled, not run).
import anthropic

client = anthropic.Anthropic()  # reads ANTHROPIC_API_KEY from the environment


def route_ticket(ticket_text):
    response = client.messages.create(
        model="claude-haiku-5-5",            # small tier; ids change, check the models overview
        max_tokens=1024,
        output_config={"effort": "low"},
        system="Classify the ticket as one of: interface, routing, wireless, dns, other. Reply with the word only.",
        messages=[{"role": "user", "content": ticket_text}],
    )
    return next((b.text.strip() for b in response.content if b.type == "text"), "other")


def diagnose(messages, tools):
    return client.messages.create(
        model="claude-opus-5-5",             # large tier, at its default effort
        max_tokens=64000,                    # thinking counts toward this cap
        tools=tools,
        messages=messages,
    )
```

The routing call returns `"other"` if no text block comes back, which can happen when a small `max_tokens` is spent on thinking (the cost page warns about exactly this on Haiku 5.5). Validate the label against the allowed set before acting on it.

## Thinking

Thinking is where the model reasons in `thinking` blocks before or between tool calls. The Claude docs (checked 2026-11-23) describe two modes and several rules:

- **Adaptive thinking** (`thinking: {"type": "adaptive"}`) lets the model decide when and how much to think; effort is the recommended control for its depth. On Claude 5 and later models thinking is already on when you omit the `thinking` field.
- **Extended thinking with a fixed budget** (`thinking: {"type": "enabled", "budget_tokens": N}`) is marked **legacy and deprecated**. Claude 4.7 and later models reject it with a 400 error that points to `thinking.type.adaptive` and `output_config.effort`. Models that support only extended thinking (Claude 4.5 and earlier) still need it, and reject `adaptive`.
- **Turning thinking off varies by model.** Some current models reject `thinking: {"type": "disabled"}` with a 400 error; others accept it at `high` effort or below; one accepts a model-specific `between_tools` setting instead. Check the per-model table on the thinking page rather than assuming.
- **Cost.** Thinking tokens are billed as output and count toward `max_tokens`, even when not returned. The `display` field chooses whether you see a summary (`"summarized"`) or an empty `thinking` field (`"omitted"`, the default on the newest models); omitting reduces latency, not cost.
- **Size `max_tokens` for it.** The cost page recommends 64,000 for agentic work (128,000 when a cut-off attempt is costly), streaming responses that large, and treating `stop_reason: "max_tokens"` as a failure. Spend is better controlled with effort, which the model can see, than with a small `max_tokens`, which it cannot.

## The same idea at OpenAI and Google

| | Claude Messages API | OpenAI Responses API | Gemini Interactions API |
|---|---|---|---|
| Effort or thinking level | `output_config.effort`: `low` to `max` (model-dependent) | `reasoning.effort`: model-dependent, from `none` or `minimal` up to `xhigh` or `max` | `thinking_level`: model-dependent, `minimal` to `xhigh` |
| Fixed token budget | `budget_tokens` (deprecated; rejected on newer models) | Not a separate knob; cap total output with `max_output_tokens` | `thinking_budget` (deprecated on Gemini 4 models; maps to the nearest level with a warning) |
| Billing | Thinking billed as output | Reasoning tokens billed as output | Priced on the full thought tokens |

All three vendors converged on the same advice: pick the level per job and verify it on your evals.

## Try it yourself

Paper first; the optional step uses the API.

1. List every model call your agent makes (or the 2.2-robust-loop agent would make on a five-step run). Assign each a tier and an effort level, with a one-line reason.
2. Mark which of those calls has a checkable output. Those are candidates for "low first, re-run failures at high".
3. Find the place in your design where the model changes mid-run. Can you move it to the edge of the run?
4. Optional: with `pip install anthropic` ([Python SDK](https://github.com/anthropics/anthropic-sdk-python)) and your key set (`export ANTHROPIC_API_KEY=<api-key>`, or `$env:ANTHROPIC_API_KEY = "<api-key>"` in PowerShell), run `route_ticket` on ten made-up tickets on the small tier at `low` and at `medium`. Compare labels, `usage.output_tokens` and time. That is twenty small calls.

## Key takeaways

- Choose a tier per job: small and fast for routing, extraction, summaries and narrow sub-tasks; large for planning, conflicting evidence and the final answer.
- Tune effort before you switch models, sweep it on your evals, and remember per-model defaults differ.
- `output_config.effort` shapes all output (text, tool calls, thinking) but is not a hard budget; `max_tokens` is the hard cap per request.
- Adaptive thinking is the current mode; fixed `budget_tokens` is deprecated and rejected on newer Claude models.
- Thinking is billed as output and counts toward `max_tokens`; size `max_tokens` generously for agents and stream large responses.
- Changing the model or the effort level mid-conversation costs cache hits; route at the edges of a run.
