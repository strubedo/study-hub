## Errors are not stop reasons

Domain 1 drew the line: a stop reason arrives in a successful (HTTP 200) response; a failed request arrives as an HTTP error with an error body and no message. This lesson handles the second kind. An agent makes many calls per run, so even a small error rate means most long runs meet at least one error. The loop must survive the transient ones and stop cleanly on the rest.

## The Claude API's error classes

The "Errors" page (checked 2026-11-23) lists these HTTP errors. Every error body is JSON with a top-level `error` object holding `type` and `message`, plus a top-level `request_id`; the page warns that new `type` values can appear.

| Status | `error.type` | Meaning | Retry? |
|---|---|---|---|
| 400 | `invalid_request_error` | Something is wrong with the request's format or content. Also returned when usage reaches a **spend limit you set** | No: fix the request (or raise the limit) |
| 401 | `authentication_error` | API key malformed, revoked or expired | No |
| 402 | `billing_error` | Billing or payment problem | No |
| 403 | `permission_error` | The key cannot use this resource | No |
| 404 | `not_found_error` | Resource not found | No |
| 409 | `conflict_error` | Conflicts with the current state of a resource | After resolving the conflict (the SDKs retry it) |
| 413 | `request_too_large` | Request exceeds the size limit (Messages API 128 MB, Batch API 256 MB) | No: shrink it |
| 429 | `rate_limit_error` | A rate limit, a ramp limit, the tier's monthly spend cap, or a Claude Code workspace limit | Usually: wait for `retry-after`. **Not** for the spend cap |
| 500 | `api_error` | Unexpected internal error | Yes, with exponential backoff |
| 504 | `timeout_error` | Timed out while processing (the type can also come with other statuses, such as a 500) | Yes; for long requests, stream instead |
| 529 | `overloaded_error` | The API is temporarily overloaded across users | Yes, with backoff |

Two 429s need care. The rate-limits page says the **tier spend cap** returns `rate_limit_error` with no `retry-after` header and `error.details.error_code` set to `enforced_spend_limit_reached`; retrying fails until access resumes, including the SDK's automatic retries. A **ramp limit** (a sharp rise in usage) returns `rate_limit_error` with `error.details.error_code` set to `ramp_limit_exceeded`; wait at least `retry-after` and raise traffic gradually. Read `error_code` before deciding.

Streaming adds one more case: an error can arrive as an `error` event after the response has started with HTTP 200 (lesson 4.3-batch-streaming).

## What the SDK already does

From the errors page and the Python SDK page (checked 2026-11-23):

- **Automatic retries.** The official SDKs retry transient failures with exponential backoff, **twice by default**, and honour the `retry-after` header when present. The Python SDK retries connection errors, 408, 409, 429 and all 500-and-above statuses.
- **Configuration.** Pass `max_retries` to the client (`anthropic.Anthropic(max_retries=4)`) or per request with `client.with_options(max_retries=5)`; `max_retries=0` disables retries. TypeScript names it `maxRetries`.
- **Timeouts.** The default request timeout is 10 minutes. Set `timeout` on the client or per request with `with_options`; on timeout the SDK raises `APITimeoutError`, and timed-out requests are also retried twice by default.
- **Long requests.** The SDK raises a `ValueError` for a non-streaming request expected to take longer than about 10 minutes; passing `stream=True` or overriding `timeout` disables the check. The errors page recommends streaming or the Batch API for long-running requests, especially over 10 minutes, because some networks drop idle connections.
- **Typed exceptions.** `anthropic.APIConnectionError` (network; `APITimeoutError` is a subclass), `anthropic.RateLimitError` (429), `anthropic.APIStatusError` (any other non-2xx, with `status_code`), plus specific classes such as `BadRequestError`, `AuthenticationError`, `PermissionDeniedError`, `NotFoundError` and `InternalServerError`. The page's example catches `APIConnectionError` and `RateLimitError` before the general `APIStatusError`.

Reading the Python SDK source (`_exceptions.py`, `_constants.py` and `_base_client.py` on the `main` branch, checked 2026-11-23; not the documentation) shows more. `APIStatusError` also carries `request_id` (from the `request-id` header), `type` (`error.type`) and `error_code` (`error.details.error_code`), and its docstrings say to branch on `error_code` rather than on the message text, whose wording can change. The backoff it uses today is a 0.5-second initial delay doubling up to 8 seconds, each delay shortened at random by up to 25% (jitter), a server-sent `retry-after` (or `retry-after-ms`) taking precedence, and a non-standard `x-should-retry` header that can force or forbid a retry. Treat those numbers as an implementation detail that can change.

```python
# client_config.py: SDK retry and timeout settings, from the Python SDK page (compiled, not run).
import anthropic

# One place to decide retries: the SDK. Default is max_retries=2 and a 10-minute timeout.
client = anthropic.Anthropic(max_retries=4, timeout=120.0)


def quick_triage(ticket_text):
    # A short call that should fail fast: no retries, 20-second timeout, for this request only.
    return client.with_options(max_retries=0, timeout=20.0).messages.create(
        model="claude-haiku-5-5", max_tokens=1024,
        messages=[{"role": "user", "content": ticket_text}])


def call_with_handling(**params):
    try:
        return client.messages.create(**params)
    except anthropic.RateLimitError as exc:          # 429 that survived the SDK's retries
        # request_id and error_code are APIStatusError attributes in the SDK source, not on the docs page.
        if exc.error_code == "enforced_spend_limit_reached":
            raise RuntimeError(f"spend cap reached, alert a human; request_id={exc.request_id}") from exc
        raise RuntimeError(f"rate limited; request_id={exc.request_id}") from exc
    except anthropic.APIStatusError as exc:          # other 4xx/5xx: log status and request id
        if exc.status_code < 500:
            raise RuntimeError(f"fix the request: {exc.status_code} {exc.request_id}") from exc
        raise                                        # 5xx after retries: provider trouble, escalate
```

> **Watch out:** Do not wrap the SDK in your own retry loop without turning the SDK's off. Five attempts in your code around a client with `max_retries=2` can send each request 5 × 3 = 15 times, and a run of agents doing that during an overload makes the overload worse. Decide retries in one layer.

## Writing your own backoff

You need your own policy when you call the HTTP API directly, when you retry at a higher level (a whole agent step, a tool call to your own systems), or when you want different limits from the SDK's. The pattern every vendor recommends:

1. Retry only transient classes: 408, 409, 429 and 5xx, and connection errors. Never retry 400, 401, 402, 403, 404 or 413 without changing something.
2. If the response has `retry-after`, wait that many seconds (the rate-limits page says earlier retries might fail).
3. Otherwise wait an exponentially growing delay with random **jitter**, so many clients do not retry in lockstep, and cap both the delay and the number of attempts.
4. After the last attempt, stop and report, with the request id.

This sketch, run offline while writing this course, uses "full jitter" (a random delay between zero and the ceiling):

```python
# retry_policy.py: which API errors to retry, and capped exponential backoff with full jitter.
import random

RETRY_STATUSES = (408, 409, 429)  # plus every status >= 500: the same rule the SDKs document
BASE_SECONDS, CAP_SECONDS, MAX_ATTEMPTS = 1.0, 30.0, 5


def should_retry(status, error_code=None):
    if error_code == "enforced_spend_limit_reached":    # tier spend cap: fails until access resumes
        return False
    return status in RETRY_STATUSES or status >= 500


def delay(attempt, retry_after=None, rng=random):
    """Seconds to wait before retry number `attempt` (1, 2, ...)."""
    if retry_after is not None:
        return float(retry_after)                     # the server said how long: obey it
    return rng.uniform(0, min(CAP_SECONDS, BASE_SECONDS * 2 ** (attempt - 1)))
```

With these settings the ceilings for retries 1 to 5 are 1, 2, 4, 8 and 16 seconds; one run with `rng=random.Random(7)` drew 0.32, 0.30, 2.60, 0.58 and 8.57 seconds (rounded to two places). A `retry-after` of 12 returns 12.0. Note what is retried: the request, not the agent's decision. A retried model call is safe because it has no side effects; a retried **tool** call is only safe if the tool is idempotent (next lesson).

## Rate limits

The Claude API measures rate limits per model class in requests per minute, input tokens per minute and output tokens per minute, using a token bucket that refills continuously rather than resetting at fixed intervals. Responses carry headers such as `anthropic-ratelimit-requests-remaining`, `anthropic-ratelimit-input-tokens-remaining` and the matching `-reset` times (RFC 3339), which you can read with `with_raw_response` to slow down before you hit a 429. For agents three habits help: cache aggressively (cache reads do not count toward input-token limits), cap concurrency when you fan out subagents or eval trials, and start scheduled jobs slowly, as the ramp-limit guidance says.

## The same idea at OpenAI and Google

| | Claude API | OpenAI API | Gemini API |
|---|---|---|---|
| Rate limited | 429 `rate_limit_error` | 429 (`rate_limit_error`; codes such as `slow_down`) | 429 `rate_limit_exceeded` or `too_many_requests` (back off and retry); 429 `quota_exceeded` is the daily quota (wait for the reset) |
| Overloaded | 529 `overloaded_error` | 503 `service_unavailable_error`, code `server_is_overloaded` | 503 `service_unavailable` |
| Spend or credit exhausted | 429 with `enforced_spend_limit_reached`; 400 for your own limit | 429 with codes such as `credit_balance_exhausted`, `organization_spend_limit_exceeded` | 402 `payment_required` (prepaid credits depleted; the troubleshooting page says not to retry 400, 402 or 403) |
| SDK retries | 2 by default, `max_retries` | 2 by default, `max_retries` | Python SDK retries transient errors with backoff by default |
| Request id | `request-id` header, `_request_id` | `x-request-id` header, `_request_id` | Not covered here |

All three tell you the same thing: back off exponentially with jitter (Claude and OpenAI also document honouring a `retry-after` header), cap the attempts, and do not retry client errors.

## Key takeaways

- Retry transient errors (429, 500, 504, 529, connection errors, timeouts); fix, do not retry, 400, 401, 402, 403, 404 and 413.
- Read `error.details.error_code` on a 429: a spend-cap 429 has no `retry-after` and will not succeed on retry.
- The official SDKs retry twice by default with exponential backoff and honour `retry-after`; configure with `max_retries` on the client or `with_options`, and `timeout` likewise (default 10 minutes).
- Decide retries in one layer; stacked retry loops multiply traffic.
- Your own backoff: obey `retry-after`, otherwise exponential with jitter, capped delay and capped attempts; report the request id when giving up.
- Stream long requests; the SDK refuses non-streaming requests expected to exceed about 10 minutes.
