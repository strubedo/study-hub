## Measure before you tune

Every change you make to an agent (a sharper system prompt, a reworded tool description, a new model, a lower effort setting) changes its behaviour on some tasks for the better and on others for the worse. Without a fixed set of tasks to run before and after, you cannot tell which happened. You end up tuning against the last ticket that went wrong, fixing it, and breaking two others you never look at again.

Anthropic's engineering article "Demystifying evals for AI agents" (published 2026-01-09) describes exactly this trap: teams that skip evals end up debugging reactively, waiting for complaints and unable to tell a real regression from noise. Its advice is to start early, and it says 20 to 50 simple tasks drawn from real failures is a good first set. The Claude documentation page "Define success criteria and build evaluations" makes the same point from the other end: define success first, in terms specific and measurable enough to test, then build evaluations that check it.

So the order of work for this domain is: test set, then graders, then tuning. This lesson builds the test set.

## The vocabulary

The evals article defines a small set of terms. They are worth using exactly, because they separate things people often blur:

| Term | Meaning | In a network diagnostics agent |
|---|---|---|
| Task (test case) | One test with defined inputs and success criteria | "Users on sw-access-12 report slow transfers" plus what a correct run looks like |
| Trial | One attempt at a task; run several because outputs vary | Trial 1, 2, 3 of the same ticket |
| Grader | Logic that scores some aspect of a trial; a task can have several | "Called the interface tool on the right device", "answer names duplex" |
| Transcript (trace) | The complete record of a trial: outputs, tool calls, results | The list of model turns and tool calls your loop logged |
| Outcome | The final state of the environment, not what the agent said | Whether an escalation record exists, not "I have escalated" |
| Evaluation suite | A collection of tasks with a shared goal | All diagnostics tickets |

The outcome distinction matters most for agents. An agent can say "I've opened a P1 for the on-call engineer" while no ticket exists, or open one while saying nothing. Grade the state, and grade the words separately.

## Where test cases come from

Do not invent tasks at a desk. Pull them from work the agent is meant to do.

1. **Tickets you already handled by hand.** The NOC queue is a ready-made task list: the symptom the user reported, what an engineer checked, and what the cause turned out to be. Strip names, addresses and ticket text down to placeholders before they go into a test file.
2. **The checks you already run manually.** The evals article suggests starting from what you verify before each release. If you always try "an interface that is admin down" after a prompt change, write it down as a task.
3. **Failures.** Every bad run in production or in testing becomes a task, with the correct expected result. This is the cheapest way to make sure a bug stays fixed.

Then shape the set so it is balanced. The article warns that one-sided evals produce one-sided behaviour: if every task rewards calling a tool, you train an agent that calls tools for everything. For a diagnostics agent, include tasks where the right move is to stop early, to say the device is not in inventory, or to hand off.

## The four kinds of case to include

| Kind | Why it is there | Example Corp example |
|---|---|---|
| Representative | The everyday work, weighted by how often it happens | Slow transfers caused by a duplex mismatch; a port err-disabled by port security |
| Edge case | Inputs that break naive designs | A hostname typo (`sw-acces-99`), an interface name in a different format, a tool that times out, a huge syslog result |
| Must refuse or decline | Requests the agent must not carry out | "Shut down Gi1/0/12 on sw-core-01": a read-only agent must decline and pass it to a human |
| Must escalate | Situations where acting alone is wrong even if possible | Both core uplinks down at a site: open a P1 hand-off, do not keep investigating |

The "Define success criteria" page lists edge cases of the same kind for any LLM application: irrelevant or missing input, overly long input, and ambiguous cases where even humans disagree. If two experienced engineers would not agree on the right verdict for a case, rewrite it or drop it. The evals article states the test plainly: a good task is one where two domain experts would independently reach the same pass or fail verdict.

## What each case records

A chat-style test case needs an input and an expected answer. An agent test case needs more, because the agent acts:

| Field | What it holds | Example (case T5) |
|---|---|---|
| `id` | Stable identifier | `T5` |
| `input` | The user message or ticket, with placeholders | "Site B reports both uplinks on sw-core-01.example.com down" |
| `environment` | What the tools will return: fixtures, a sandbox, or recorded responses | Interface stub returns `oper_status: down` for Te1/1/1 and Te1/1/2 |
| `expected_outcome` | The end state or answer that counts as success | One escalation with severity P1 exists |
| `required_calls` | Evidence the agent must gather (tool and key arguments) | `get_interface_status` on `sw-core-01.example.com` |
| `forbidden_calls` | Calls that are wrong in this case | None here; in a routine case, `escalate_to_oncall` |
| `limits` | Path budget | At most 6 tool calls |
| `notes` | Why the case exists, so nobody "fixes" it away | "Added after run 2026-11-02 kept investigating a site outage" |

Two warnings about `required_calls`. First, the evals article cautions against checking an exact sequence of tool calls: agents often find valid paths the designer did not expect, so grading the precise order makes tests brittle. Require the evidence that matters (the agent must have looked at the interface before blaming it) and forbid what is unsafe, rather than scripting every step. Anthropic's "Writing effective tools for agents" (2025-09-11) says the same: you may list the tools you expect an agent to call, but there can be several valid paths, so do not overfit to one. Second, keep a reference solution for each task: a known-good run or answer that passes every grader. If no correct run can pass, the task or the grader is broken, not the agent.

## Make the environment repeatable

A read-only diagnostics agent is the easy case: its tools only read, so you can replay fixed responses. Give each task its own fixture data (interface state, ticket search results, runbooks) and start every trial from a clean copy. The evals article notes that shared state between trials (leftover files, cached data) causes correlated failures and can even inflate scores. For tools that change state, run against a sandbox and inspect it afterwards; never grade an agent against production devices.

> **Real world:** Store test cases as data (JSON or YAML files in the repository next to the agent), not inside test code. Engineers who know the network can then add a case from last night's incident without touching the grader.

## Capability sets and regression sets

The article distinguishes two kinds of suite. A **capability** suite holds tasks the agent still struggles with; its pass rate starts low and shows whether changes help. A **regression** suite holds tasks the agent already handles; its pass rate should stay near 100%, and any drop means something broke. Tasks graduate from the first to the second once they pass reliably. Lesson 4.1-eval-worked-example runs both kinds on every change.

## The same idea at OpenAI and Google

OpenAI's "Evaluate agent workflows" guide (checked 2026-11-23) starts from traces of individual runs for debugging and then moves to datasets and eval runs "when you need repeatability"; its platform hosts both. The Gemini API documentation lists its Batch API for "offline evals" but, in the pages read for this course, does not define its own agent evaluation method. The test-set design above is vendor-neutral.

## Try it yourself

A paper exercise, no API key needed.

1. Pick a workflow you run by hand, for example "a user says the Wi-Fi is slow in building C".
2. Write eight test cases in a table with the fields above: four representative, two edge cases, one the agent must decline, one it must escalate. Use placeholder hosts (`*.example.com`) and RFC 1918 addresses only.
3. For each case, write `required_calls` as evidence ("must read the AP's client count"), not as a script of steps.
4. Ask a colleague to grade a made-up final answer for two of your cases. If you disagree on pass or fail, the case is ambiguous: rewrite it.
5. Mark which cases are capability cases and which belong in the regression set.

## Key takeaways

- Build a fixed test set before you tune anything; without one you cannot tell an improvement from a regression.
- Start with 20 to 50 tasks taken from real tickets, manual checks and past failures, then grow the set from every new failure.
- Balance the set: representative cases, edge cases, cases the agent must decline and cases it must escalate.
- Record more than input and answer: the environment, the expected outcome (state), required evidence, forbidden calls and a path budget.
- Grade outcomes and essential evidence, not an exact tool-call sequence; keep a reference solution for each task.
- Keep a capability suite (low pass rate, room to climb) and a regression suite (near 100%, must not drop).
