## Read the transcript, not the summary

When an eval case fails or a user reports a bad run, the final answer tells you that something went wrong. The transcript tells you where. Anthropic's evals article (2026-01-09) calls reading transcripts "a critical skill for agent development", and "Writing effective tools for agents" (2025-09-11) adds a warning: what an agent leaves out of its own explanation often matters more than what it says, so read the raw tool calls and results, not just its reasoning.

Read a transcript in this order:

1. **The last response's `stop_reason`.** Did the run end on `end_turn`, or on something that means "cut short"?
2. **The tool calls, in order.** Name, arguments, and whether each result was an error.
3. **The first divergence.** The earliest step where a competent engineer would have done something different. Everything after it is usually consequence, not cause.
4. **What the model was shown at that step.** The tool description it chose from, and the exact result text it reacted to.

## A transcript to read

Here is a run of the diagnostics agent, written for this lesson from the documented message shapes (not captured), shown as one line per event:

```text
step 1  stop=tool_use  get_interface_status {"device": "sw-acces-12", "interface": "Gi1/0/48"}
        result is_error=false  "lookup failed"
step 2  stop=tool_use  get_interface_status {"device": "sw-acces-12", "interface": "Gi1/0/48"}
        result is_error=false  "lookup failed"
step 3  stop=tool_use  get_interface_status {"device": "sw-acces-12", "interface": "Gi1/0/48"}
        result is_error=false  "lookup failed"
step 4  stop=end_turn  "The interface appears to be healthy. No action is needed."
```

Step 1 is the first divergence: a hostname without the domain suffix and with a typo. But the model could not know that, because the tool's result said only "lookup failed" and was not marked as an error. Steps 2 and 3 are the same call again (a loop), and step 4 states a conclusion no tool result supports (a hallucinated result). The fix is in the tool: return `is_error: true` with "No device 'sw-acces-12' in inventory; use the full name, for example sw-access-12.example.com". Domain 2 (lesson 2.1-tool-results) shows how to write such errors.

## The common failure shapes

| Shape | What you see in the transcript | Usual cause | Fix first |
|---|---|---|---|
| **Loop** | The same tool with the same arguments, three or more times | Result gives no new information or no guidance; an error not marked as one | Make the result say what to do next; detect repeated identical calls in the loop and stop; keep the iteration cap |
| **Stall** | Many reads, no conclusion, until the cap ends the run | No achievable stopping rule; the task is open-ended ("check everything") | Stopping criteria in the system prompt; narrower tools that return what decides the question |
| **Premature stop** | `end_turn` after too little evidence, or a question to the user ("Shall I check the counters?") when the agent was allowed to read | Prompt does not say reads may proceed without asking; low effort setting | System prompt: read-only checks need no permission; raise effort on hard cases (the effort page notes that at `low`, Claude Haiku 5.5 is more likely to skip a search, stop early or skip a check in long agent prompts) |
| **Wrong tool** | A plausible but wrong tool (`search_tickets` to answer "is the port up?") | Overlapping or vague descriptions | Rewrite descriptions to say when to use each tool and when not to |
| **Wrong arguments** | Short hostnames, invented parameters, values outside a set | Ambiguous schema | `enum`, `strict: true`, `input_examples`, a format note in the description |
| **Ignored error** | An `is_error` result, then the next step proceeds as if it worked | Error text that does not say what failed or what to do | Actionable error text; `is_error: true` on every failure |
| **Hallucinated result** | A counter, ticket id or action in the answer that no tool result contains | Missing data treated as known; no tool for the claimed action | Ground the answer in tool results (system prompt and a groundedness grader); return explicit ids; never give the agent wording that suggests it acted |
| **Truncation** | `stop_reason: "max_tokens"`; the answer stops mid-sentence | `max_tokens` too small, often because thinking counts toward it | Raise `max_tokens` (stream large ones) or lower effort; treat the output as incomplete |
| **Truncated tool call** | `max_tokens` with an incomplete `tool_use` as the last block | A big tool input (a long config or query) hit the limit | Never run it; retry with a higher `max_tokens` (Domain 2's loop does this up to a ceiling) |
| **Context overflow** | HTTP 400 "prompt is too long", or `stop_reason: "model_context_window_exceeded"` | History grew past the window, usually through large tool results | Trim and paginate results; clear or compact old ones (Domain 3) |

Two stop reasons look like failures but are not. `pause_turn` means a **server-tool** loop paused and expects you to resend the content; `refusal` means the model declined and carries `stop_details`. Both are handled by the loop as Domain 1 describes. The full list of stop reasons (`end_turn`, `max_tokens`, `stop_sequence`, `tool_use`, `pause_turn`, `refusal`, `model_context_window_exceeded`) is in lesson 1.2-stop-reasons-context; a context overflow on the input side is an HTTP 400 error, not a stop reason.

> **Exam tip:** Thinking tokens count toward `max_tokens` and are billed as output, even when the thinking text is not returned. A run that stops on `max_tokens` with little visible text is often a run that spent its budget thinking. The thinking cost-control section says to either raise `max_tokens` or lower effort, depending on whether those requests needed the reasoning.

## Why the fix usually belongs in the tool

When a run goes wrong, the tempting fix is another sentence in the system prompt: "ALWAYS use the full hostname." It rarely holds. The model reads the system prompt once at the top of a growing context, but it reads the tool description every time it picks a tool and the tool result immediately before its next decision. A fix placed where the decision happens is more reliable than a general instruction far away.

The vendors' own guidance points the same way. "Writing effective tools for agents" recommends analyzing tool-calling metrics from evals: many redundant calls suggest adjusting pagination or token limits, and many invalid-parameter errors suggest clearer descriptions or better examples. It also describes a real case: Claude kept appending a year to web search queries, and the fix was a better tool description. Claude's tool-use troubleshooting page maps symptoms to fixes the same way: wrong tool chosen → sharpen descriptions by when to use them; wrong parameter types or invented parameters → `strict: true` or `input_examples`.

A practical order for fixes, this course's own:

1. **Tool result wording.** Errors marked `is_error` and saying what to do next; results that include the identifiers and units the answer needs.
2. **Tool description and schema.** When to use it, when not to, accepted formats, enums.
3. **Tool shape.** Split an overloaded tool, or add one that answers the real question directly.
4. **System prompt.** Run-wide policy: stopping rules, when to escalate, what never to claim.
5. **Limits.** Iteration caps, repeated-call detection, `max_tokens`, budgets. Limits contain a failure; they do not fix it.

After each fix, rerun the regression suite (lesson 4.1-eval-worked-example): a description that cures one case can break another.

## The same idea at OpenAI and Google

OpenAI's Responses API signals truncation with `status: "incomplete"` and `incomplete_details.reason` (for example `max_output_tokens`), and its reasoning guide notes this can happen before any visible output because reasoning tokens count toward `max_output_tokens`. Gemini's troubleshooting page lists "repetitive tool calling" as a known symptom and suggests instructing the model to keep state in its thought process. The failure shapes are the same everywhere.

A paper exercise.

1. Take the transcript above. Write the improved error result for step 1, and say what step 2 should then look like.
2. Write a check for your loop: if the last three tool calls have the same name and identical arguments, stop the run and report "repeated call". Where in the 2.2-robust-loop code would it go?

## Key takeaways

- Read a transcript from the last `stop_reason` back to the first divergence, and look at what the model was shown at that step.
- Learn the shapes: loops, stalls, premature stops, wrong tool or arguments, ignored errors, hallucinated results, truncation (including mid tool call) and context overflow.
- `max_tokens` with an incomplete `tool_use` block must never be executed; thinking counts toward `max_tokens`.
- Input that is too large is an HTTP 400 error; generation that fills the window is `model_context_window_exceeded`.
- Fix where the decision happens: tool results and descriptions first, then tool shape, then the system prompt; limits contain failures but do not fix them.
- Rerun the evals after every fix.
