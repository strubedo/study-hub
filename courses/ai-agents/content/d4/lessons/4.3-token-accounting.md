## Where the money goes in an agent

A single chat call costs its input plus its output. An agent run costs the sum over every model call in the loop, and each call resends the whole growing history (Domain 3, lesson 3.1-context-budgets). So the bill is dominated by three things: how many calls the run makes, how large the history gets, and how much of it is billed at full price rather than as a cache read. This lesson turns the `usage` object into a cost you can compute, then prices one diagnostics run three ways.

Prices change often, so this lesson uses **symbolic rates** and the **multipliers** the pricing page gives. Look up current prices on the Claude pricing page when you need real numbers.

## The four token counts

Domain 3 confirmed these fields of the Messages API `usage` object (2026-11-23):

| Field | What it counts | Billed at |
|---|---|---|
| `input_tokens` | Input after the last cache breakpoint: neither read from nor written to the cache | Base input rate |
| `cache_creation_input_tokens` | Input written to the cache by this request | Base input rate × write multiplier |
| `cache_read_input_tokens` | Input read from the cache | Base input rate × read multiplier |
| `output_tokens` | Everything generated, **thinking included** | Output rate |

Total input is the sum of the first three. `output_tokens_details.thinking_tokens` says how many of the output tokens were thinking; you pay for them at the output rate whether or not the thinking text is returned (the thinking page states this, and that with summarized thinking you are billed for the full thinking, not the summary). Earlier thinking blocks kept in the history are billed as input on later requests.

## The multipliers (Claude pricing page, 2026-11-23)

| Item | Multiplier | Applies to |
|---|---|---|
| 5-minute cache write | 1.25× base input | `cache_creation_input_tokens` (5-minute part) |
| 1-hour cache write | 2× base input | 1-hour part (`cache_creation.ephemeral_1h_input_tokens`) |
| Cache read | 0.1× base input on most models; lower (0.05× or 0.025×) on some of the newest | `cache_read_input_tokens` |
| Batch API | 0.5× on input and output | Every token of a batched request; stacks with caching |
| US-only inference (`inference_geo: "us"`) | 1.1× on all token categories | Claude 4.6 and later models |
| Fast mode (`speed: "fast"`) | Premium pricing (twice standard on the models listed today) | Supported models only; not available with batch |
| Output vs input | Output costs five times input on the current Haiku, Sonnet, Opus and Fable models | `output_tokens` |

The last row comes from Anthropic's "Optimizing for cost and intelligence" page, which also points out why it matters in agents: every token the model writes comes back as input on every later turn, so a verbose model pays for its own words again and again.

## The cost of one request

With base input rate `IN` and output rate `OUT` (per token, for one model):

```text
cost = IN × (input_tokens
             + 1.25 × cache_creation_input_tokens      (5-minute writes; 2 × for 1-hour writes)
             + 0.10 × cache_read_input_tokens)         (use the model's read multiplier)
     + OUT × output_tokens
```

Example, with illustrative rates IN = 1 unit and OUT = 5 units per million tokens, and the usage report from Domain 3 (412 uncached, 1,830 written, 37,600 read, 655 output):

```text
input  = 412 + 1.25 × 1,830 + 0.10 × 37,600 = 412 + 2,287.5 + 3,760 = 6,459.5 units per million
output = 5 × 655                                                     = 3,275   units per million
total  = 9,734.5 / 1,000,000                                         ≈ 0.00973 units
```

Without caching, the same 39,842 input tokens would have cost 39,842 + 3,275 = 43,117 per million: about 4.4 times as much.

## One run, priced three ways

The run: a diagnostics task that takes six model calls. The system prompt, tool definitions and goal are 6,400 tokens; each tool round trip adds 1,800 tokens to the history; each call outputs 300 tokens except the last, which writes a 700-token report. The rates are illustrative (a large model at 1 input and 5 output units per million tokens, a small model at a quarter of that). The script was run offline while writing this course.

```python
# cost_three_ways.py: one diagnostics run priced three ways. Rates are illustrative price units
# per million tokens, not real prices; the multipliers are the ones the pricing page lists (2026-11-23).
WRITE_5M, READ, BATCH = 1.25, 0.10, 0.50
LARGE = {"in": 1.00, "out": 5.00}
SMALL = {"in": 0.25, "out": 1.25}

PREFIX, STEP = 6_400, 1_800              # system + tools + goal; tokens each round trip adds
OUTPUTS = [300, 300, 300, 300, 300, 700]  # output tokens per request (thinking included)


def inputs():
    return [PREFIX + STEP * i for i in range(len(OUTPUTS))]


def price(rate, uncached=0, written=0, read=0, output=0):
    return (uncached * rate["in"] + written * rate["in"] * WRITE_5M
            + read * rate["in"] * READ + output * rate["out"]) / 1_000_000


def no_cache(rate, sizes, outs):
    return sum(price(rate, uncached=n, output=o) for n, o in zip(sizes, outs))


def auto_cache(rate, sizes, outs):
    total, previous = 0.0, 0
    for n, o in zip(sizes, outs):
        total += price(rate, written=n - previous, read=previous, output=o)
        previous = n
    return total


sizes = inputs()
a = no_cache(LARGE, sizes, OUTPUTS)
b = auto_cache(LARGE, sizes, OUTPUTS)
c = auto_cache(SMALL, sizes[:5], OUTPUTS[:5]) + no_cache(LARGE, sizes[5:], OUTPUTS[5:])
print("input tokens per request:", sizes, "total", sum(sizes), "| output total", sum(OUTPUTS))
for name, cost in [("A large model, no cache", a), ("B large model, cached", b),
                   ("C small model cached, large final call", c)]:
    print(f"{name:40s} {cost * 1000:7.3f} units per 1,000 runs  ({cost / a:.1%} of A)")
print(f"A with every request sent through the Batch API: {a * BATCH * 1000:.3f} units per 1,000 runs")
```

Output:

```text
input tokens per request: [6400, 8200, 10000, 11800, 13600, 15400] total 65400 | output total 2200
A large model, no cache                   76.400 units per 1,000 runs  (100.0% of A)
B large model, cached                     35.250 units per 1,000 runs  (46.1% of A)
C small model cached, large final call    25.935 units per 1,000 runs  (33.9% of A)
A with every request sent through the Batch API: 38.200 units per 1,000 runs
```

How to read it:

- **A** pays full price for 65,400 input tokens and 2,200 output tokens. Six calls of a growing history cost far more than six times the first call.
- **B** turns on automatic caching (Domain 3, lesson 3.1-prompt-caching). Each request writes only its new 1,800 tokens and reads the rest at 0.1×. Over half the bill disappears with no change in behaviour.
- **C** runs the five evidence-gathering calls on the small model and only the final diagnosis on the large one. The final call cannot reuse the small model's cache (caches are per model) and is sent without a cache breakpoint, because a one-off write at 1.25× would never be read. Model choice is lesson 4.3-model-tier-effort.
- **Batch** halves every token, but only fits work nobody waits for, and an agent loop with client tools would need a separate batch round trip per step (this course's reasoning; lesson 4.3-batch-streaming).

The figures assume every run succeeds. Real comparisons should be **cost per completed task**, which Anthropic's cost-optimization page recommends: a cheaper configuration that fails more often pays for the failed attempt, the retry and whatever the failure costs downstream. Use your eval set (lesson 4.1-eval-worked-example) to measure pass rate and cost together, and look at the expensive tail, not just the median run.

> **Exam tip:** When a question gives a usage object and rates, multiply each of the four counts by its own rate. The common mistakes are pricing `cache_read_input_tokens` at the full input rate, forgetting the write multiplier, and pricing thinking as anything other than output.

## Cache reads and rate limits

The rate-limits page adds one more reason to cache: for input-tokens-per-minute limits, `input_tokens` and `cache_creation_input_tokens` count but `cache_read_input_tokens` does not. A well-cached agent therefore fits more runs under the same limit as well as costing less.

## The same idea at OpenAI and Google

OpenAI reports `usage.input_tokens`, `input_tokens_details.cached_tokens`, `output_tokens` and `output_tokens_details.reasoning_tokens`; its reasoning guide says reasoning tokens are billed as output tokens. Gemini's Interactions API reports usage totals including `total_thought_tokens`, and its thinking page says pricing is based on the full thought tokens generated. In all three, reasoning is paid output and cached input is discounted.

## Key takeaways

- An agent's cost is the sum over every call, and each call resends a growing history; cost grows faster than the number of calls.
- Price each usage count separately: uncached input at the base rate, cache writes at 1.25× (5-minute) or 2× (1-hour), cache reads at the model's read multiplier, output at the output rate.
- Thinking tokens are output tokens: billed at the output rate, counted toward `max_tokens`, even when not returned.
- Multipliers stack: batch (0.5×) with caching, US-only inference (1.1×) on everything; fast mode costs a premium and cannot be batched.
- Caching usually gives the largest saving for agent loops; cache reads also do not count toward input-token rate limits.
- Compare configurations on cost per completed task, measured on your eval set.
