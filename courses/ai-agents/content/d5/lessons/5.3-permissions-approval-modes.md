## Who decides whether a tool call runs

Every agent framework answers one question for each tool call: run it, refuse it, or ask a person. The names differ by product and change often, so this lesson copies them from the documentation as it read on **2026-11-23**. Learn the ideas; re-check the strings before you configure anything.

## Claude Agent SDK: modes, rules, hooks and a callback

The Agent SDK's "Configure permissions" page evaluates each tool call in a fixed order. Each step can decide, pass the call on, or send it to your callback:

1. **Hooks.** A `PreToolUse` hook can deny the call (a hook deny holds even in `bypassPermissions`). A hook's `allow` does not skip the deny and ask rules.
2. **Deny rules** from `disallowed_tools` or settings files. A match denies the call in every mode.
3. **Ask rules** from settings files. A match goes to your callback, even in `bypassPermissions`.
4. **Permission mode** (table below).
5. **Allow rules** from `allowed_tools` and settings files. A match approves the call.
6. **The `can_use_tool` callback**, if nothing earlier decided. In `dontAsk` mode this step is skipped and the call is denied.

The six permission modes:

| Mode | What it does | Human approval? |
|---|---|---|
| `default` | No mode-based approvals; calls that need approval and match no allow rule go to `can_use_tool` | Yes, through your callback |
| `dontAsk` | Anything that would prompt is denied; pre-approved tools and calls that need no approval still run | None, but it **fails closed** |
| `acceptEdits` | Auto-approves file edits and filesystem commands (`mkdir`, `rm`, `mv` and others) inside the working directories | Removed for edits |
| `bypassPermissions` | Approves every call that reaches the mode step, apart from a short list of actions no mode auto-approves | **Removed** |
| `plan` | The agent explores and plans; file edits go to your callback (where auto mode is available, other shell commands and web fetches go to its classifier instead) | Yes, for edits |
| `auto` | A model classifier reviews actions such as shell commands and network requests and allows or blocks each | Replaced by a classifier |

Rules that catch people out, all stated on the permissions page:

- `allowed_tools` **pre-approves**; it does not restrict the agent to those tools. Unlisted tools still exist and fall through to the mode.
- `allowed_tools` **does not constrain `bypassPermissions`**: with `allowed_tools=["Read"]` and `bypassPermissions`, `Bash`, `Write` and `Edit` are approved too. Use `disallowed_tools` to block.
- A bare name in `disallowed_tools` (`"Bash"`) removes the tool from the request; a scoped rule (`"Bash(rm *)"`) denies matching calls as written, in every mode, but other forms of the same command can slip past.
- **Auto-approved calls never reach `can_use_tool`**, so checks you put only in the callback are silently skipped for tools in `allowed_tools`. Put checks that must always run in a `PreToolUse` hook.
- A hook with `matcher="Write|Edit"` does not fire when the agent writes the same file with `Bash`. Match every tool that can reach the resource, or use the sandbox's filesystem rules.

For a headless, read-only agent, the page recommends pairing `allowed_tools` with `dontAsk`. A sketch using the documented names (compiled, not run; `netops` is your own MCP server):

```python
import asyncio
from claude_agent_sdk import ClaudeAgentOptions, HookMatcher, query

READ_TOOLS = [
    "mcp__netops__get_device",
    "mcp__netops__run_show_command",
    "mcp__netops__search_tickets",
]


async def guard(input_data, tool_use_id, context):
    """PreToolUse hook: log every call; deny anything that is not a read tool."""
    tool = input_data["tool_name"]
    print(f"audit tool={tool} id={tool_use_id}")  # send to your log pipeline instead
    if tool not in READ_TOOLS:
        return {"hookSpecificOutput": {
            "hookEventName": input_data["hook_event_name"],
            "permissionDecision": "deny",
            "permissionDecisionReason": "This agent is read-only.",
        }}
    return {}


options = ClaudeAgentOptions(
    mcp_servers={"netops": {"type": "stdio", "command": "python", "args": ["netops_server.py"]}},
    permission_mode="dontAsk",
    allowed_tools=READ_TOOLS,
    disallowed_tools=["Bash", "Write", "Edit", "WebFetch"],
    hooks={"PreToolUse": [HookMatcher(hooks=[guard])]},
    max_turns=15,
)


async def main():
    async for message in query(prompt="Check sw-acc-b12 port Gi1/0/14 for errors.", options=options):
        print(message)


asyncio.run(main())
```

For an interactive agent that should ask, use `default` mode, leave the gated tools **out** of `allowed_tools`, and pass `can_use_tool`, an async function that receives the tool name, its input and a `ToolPermissionContext`, and returns `PermissionResultAllow` (optionally with `updated_input`) or `PermissionResultDeny` (with a `message`, and `interrupt=True` to stop the run).

## Claude Managed Agents: permission policies

Managed Agents (beta) sets a **permission policy** per toolset or per tool on its server-executed tools:

| Policy | Behaviour |
|---|---|
| `always_allow` | Runs with no confirmation |
| `always_ask` | The session pauses until you send a `user.tool_confirmation` event with `result` `allow` or `deny` (and an optional `deny_message`) |
| `auto` | The server evaluates each call and runs it, denies it, or pauses for approval |

Defaults matter: the agent toolset (`bash`, `read`, `write`, `edit`, `glob`, `grep`, `web_fetch`, `web_search`) defaults to `always_allow`, and MCP toolsets default to `always_ask`, so tools a server adds later wait for approval. Override per tool in `configs`, and disable tools you do not need rather than leaving them enabled with a policy.

Three points from the permission-policies and security pages:

- **`auto` is not a human checkpoint.** A call judged safe runs before anyone sees it. If a person must review a tool's calls, use `always_ask`.
- `auto` reads your intent from `user.message` events, including end-user text you relay, but not from tool results, fetched pages or MCP responses. Relaying untrusted user text can therefore get a call allowed; use `always_ask` on tools that user should not trigger unreviewed.
- **Custom tools are outside the policies.** Your application receives the call and decides. Every `agent.tool_use` and `agent.mcp_tool_use` event carries `evaluated_permission` (`allow`, `ask` or `deny`) for your audit log; custom-tool events do not, so log your own decision for those.

## OpenAI and Google, in brief

| Idea | OpenAI | Google ADK |
|---|---|---|
| Pause a tool for approval | Agents SDK: `function_tool(needs_approval=True)`; the run returns `interruptions` and a resumable `state`; you approve or reject each item (the guide's example calls `state.approve(...)`) and resume the same run | `FunctionTool(..., require_confirmation=True)`, or a confirmation request from inside the tool |
| Automatic checks | Input, output and tool **guardrails** (input guardrails run only for the first agent; output guardrails only for the final one) | `before_tool_callback` and plugins |
| Model-based approval | Agents API session `review`: `"auto_review"` (a reviewer model approves or denies) or `"none"` (the default; most actions execute directly) | Gemini used as a screening guardrail through callbacks |

## Which settings remove human approval

Say this plainly in every design review. These remove a person from the decision:

- Agent SDK `bypassPermissions` (everything), `acceptEdits` (file changes), `auto` (a classifier decides), and any tool listed in `allowed_tools`.
- Managed Agents `always_allow`, which is the agent toolset default, and `auto`.
- OpenAI Agents API `review: "none"` (actions execute directly; nothing is sent to you to approve) and `"auto_review"` (a model approves).
- Any approval client that answers "allow" without showing a person the exact call.

The Agent SDK page's own warning for `bypassPermissions` is to use it with extreme caution, because Claude has full system access in that mode, and only in controlled environments where you trust all possible operations; on Linux and macOS, Claude Code refuses to start in that mode as root or under `sudo` outside a recognised sandbox. The SDK reference adds that `bypassPermissions` together with `allowUnsandboxedCommands` lets the model leave the sandbox silently. This course's rule: such settings belong only in an **isolated, disposable environment** (a throwaway container or VM with no production credentials, no route to your management network and nothing you cannot delete), because the only thing then limiting the agent is the environment itself.

> **Exam tip:** `dontAsk` removes the human too, but by denying instead of allowing. That is why it suits unattended read-only agents and `bypassPermissions` never does.

## Key takeaways

- The Agent SDK evaluates hooks, deny rules, ask rules, the permission mode, allow rules, then `can_use_tool`; deny rules and hook denies hold in every mode.
- Six modes: `default`, `dontAsk`, `acceptEdits`, `bypassPermissions`, `plan`, `auto`; `allowed_tools` pre-approves but does not restrict, and does not constrain `bypassPermissions`.
- Checks that must always run belong in a `PreToolUse` hook, matched to every tool that can reach the resource.
- Managed Agents policies are `always_allow`, `always_ask` and `auto`; the agent toolset defaults to `always_allow`, MCP toolsets to `always_ask`; `auto` is not a human checkpoint; custom tools are yours to gate.
- OpenAI uses `needs_approval` and guardrails; ADK uses `require_confirmation` and callbacks.
- Settings that remove human approval belong only in isolated, disposable environments.
