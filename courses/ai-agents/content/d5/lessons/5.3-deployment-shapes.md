## Three ways an agent starts

How an agent is triggered changes what can go wrong and who notices.

| | Interactive | Scheduled | Event-driven |
|---|---|---|---|
| Started by | A person, in a chat, CLI or web page | A timer (cron) | A webhook, alert, new ticket, new email |
| Example | "Why is VLAN 20 slow at site B12?" | Nightly check of interface error counters across the access layer | A monitoring alert opens INC-5310 and the agent gathers diagnostics |
| Who is watching | The requester, usually | Nobody | Nobody, at first |
| Who can approve | The requester, in the moment | Nobody, unless you route approvals somewhere | Whoever is on call, if you route it |
| Input trust | The user's text plus what tools return | Fixed task text plus tool results | The triggering event itself is often outsider-written (a ticket, an email) |
| Typical failure | Wrong answer, noticed quickly | Silent failure, or a cost spike found at month end | A flood of events, each starting a run |

### What changes when nobody is watching

Interactive agents get a free safety net: a person sees each step. Remove the person and every control has to be explicit:

- **Approvals need somewhere to go.** A tool that waits for approval with nobody there either blocks forever or must fail closed. In Claude Managed Agents a paused session "waits indefinitely", so the security guide says an unattended session needs a client that answers paused calls or interrupts the session. In the Claude Agent SDK, `dontAsk` mode turns every would-be prompt into a denial, which is the right default for a headless run.
- **Limits must be in code.** Turn caps and spend caps (Domain 4) are the only thing between a loop and the invoice. Managed Agents lets you set a budget on each scheduled deployment, copied onto every session it starts; Anthropic's page warns that requests in progress can complete after the cap, so spend can pass it.
- **Someone must be told.** Failures, denials and sessions waiting for approval need alerts, not just log lines.
- **Triggers can be abused.** An event-driven agent that runs on every inbound email or new ticket lets outsiders start it, with input they wrote. Rate-limit triggers, deduplicate, and treat the triggering content as untrusted input (lesson 5.1).
- **Runs must be safe to repeat.** Schedulers retry and webhooks are delivered more than once; make tools idempotent (Domain 4).

### Scheduled agents in practice

Claude Managed Agents has **scheduled deployments** (documented 2026-11-23): a deployment names an agent and an environment, takes at least one initial event (the task message), and a `schedule` with a cron `expression` and an IANA `timezone`. The docs note a few operational details worth copying into any scheduler you build:

- Each attempt creates a **deployment run** record, so you can see a run that failed to start (an archived environment, rate limiting) separately from a session that started and failed.
- Execution has jitter (up to 15 percent of the interval, capped), so do not assume exact start times.
- Wall-clock schedules skip times that do not exist on a spring-forward day and fire twice for times that occur twice on a fall-back day; schedule outside 1–3 AM local time or use UTC when that matters.
- A deployment **pins an agent version**: after you change the agent, point the deployment at the new version.

## Self-hosted loops and hosted agents, with operations in mind

Domain 1 split ownership into loop, tools, state, sandbox and permissions. Running one in production adds four more questions.

| Concern | Self-hosted (your loop, or an agent SDK in your container) | Hosted (for example Claude Managed Agents) |
|---|---|---|
| **Scaling** | Yours. The Claude Agent SDK runs one CLI subprocess per session; its hosting page sizes hosts as (host RAM minus overhead) divided by per-session peak RAM, and pins long-running sessions to one container by hashing the session id | The provider runs the loop and the cloud sandboxes; your limits are rate limits, organization quotas (for example, 1,000 scheduled deployments per organization) and budgets |
| **State** | Local disk is lost on restart or rescheduling; the SDK's `SessionStore` adapter mirrors transcripts to durable storage (transcripts only, best-effort: alert on `mirror_error` messages) | Sessions and their history live with the provider until you delete them; sandbox state is kept 30 days after creation |
| **Upgrades** | You choose when. The SDK bundles a CLI binary pinned to the package version, follows semver, and Anthropic advises reading the changelog before taking a minor release; re-run your evaluation suite (Domain 4) after any upgrade | The service changes under you. Agent updates apply to new sessions only; running sessions keep their configuration; deployments and parent agents keep the versions they pinned |
| **Cost visibility** | Token usage from every response, which you aggregate; the hosting page notes token cost typically dominates container cost by an order of magnitude or more | Session and deployment budgets, plus the provider's usage reporting; budgets bound spend per session, not what the agent does before the cap |
| **Security responsibility** | All of it: isolation, egress, credentials, logs | The provider secures the cloud sandbox; you still own tool sets, permission policies, networking settings, vault scoping and your custom tools and MCP servers |
| **Data location** | Where you run it | Provider-side; check the retention terms (lesson 5.2) |

Neither is "more secure" by default. Self-hosting gives you the network controls and logs you already run; hosting gives you a tested sandbox and fewer moving parts, with defaults you must check (Managed Agents' agent toolset defaults to `always_allow`, and an environment created through the API without `networking` gets `unrestricted`).

> **Real world:** For network operations, the deciding question is usually reach. A hosted cloud sandbox cannot see your management network, which is a feature: put your device and inventory access behind custom tools or remote MCP servers you run, and let the hosted agent call those.

### Patterns for self-hosted SDK agents

The Agent SDK's hosting page names patterns by how long a container lives relative to its sessions. Two matter most here:

- **Ephemeral**: one container per task, destroyed when the task finishes. The example entrypoint reads the task from an environment variable and runs `query()` with `max_turns`. Good for scheduled and event-driven jobs: nothing persists between runs, which is also a security property.
- **Long-running**: persistent containers serving many sessions, for chat bots and agents that handle a continuous stream (the page's examples include an email triage agent). Needs session pinning, durable session storage and per-tenant isolation.

For multi-tenant containers the page warns that settings files and memory files on disk can leak one tenant's context into another's, and lists isolation steps (empty `setting_sources`, per-tenant working and config directories, per-tenant egress rules).

## Key takeaways

- Interactive, scheduled and event-driven agents differ in who is watching, who can approve and who writes the triggering input.
- Without a person present, approvals must route somewhere or fail closed (`dontAsk` in the Agent SDK); a paused Managed Agents session waits indefinitely.
- Unattended agents need caps and budgets in code, alerts on failures and pauses, rate-limited triggers and idempotent tools.
- Managed Agents scheduled deployments use cron plus timezone, record each attempt as a deployment run, apply jitter, have DST quirks and pin an agent version.
- Operating an agent adds scaling, state, upgrades and cost visibility to Domain 1's ownership table; self-hosted gives control and reach, hosted gives a managed sandbox with defaults to check.
- Re-run evaluations after every SDK, model or prompt change, whichever way you host.
