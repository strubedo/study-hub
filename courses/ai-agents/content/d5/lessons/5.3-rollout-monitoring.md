## Roll out an agent the way you roll out a routing change

You would not change OSPF costs across the whole network at once without a lab test, a pilot site and a back-out plan. An agent deserves the same discipline, for the same reason: its behaviour on real inputs is only partly predictable from tests. This course's rollout sequence has four stages, each with an exit criterion you write down before you start.

| Stage | What the agent can do | Who sees its output | Exit criterion (example) |
|---|---|---|---|
| **1. Read-only** | Read tools only, against real systems; answers go to its users | The engineers who asked | Evaluation suite passes (Domain 4); no secret in any log or transcript sample; injection test cases handled |
| **2. Shadow mode** | Runs on real inputs (every new ticket, every alert) and records what it **would** do; nothing is executed or posted | The team reviewing the shadow log | Over two weeks, proposed actions match what the on-call engineer actually did in an agreed share of cases, with no proposal you would call dangerous |
| **3. Pilot** | Takes real actions for a small scope: one site, one queue, one shift; write tools behind approval | The pilot team, plus approvers | Success and escalation rates stable; no incident caused; approvers are not rubber-stamping |
| **4. Widen** | Same controls, more scope, one step at a time | Everyone in scope | Metrics hold at each step; rollback rehearsed |

**Shadow mode** is the stage people skip and should not. It is the only way to see the agent meet the messy inputs that real tickets contain (half-written descriptions, pasted logs, a comment addressed to "the bot") without consequences. Implement it in your tool layer: write tools return "recorded, not executed" and log the exact call, so the model's behaviour is the same as it will be in production. Compare the log with what people did.

Go back a stage whenever something material changes: a new model, a new or edited system prompt, a new tool, a new data source. Those are changes to production behaviour and belong in your change process like any other.

## What to monitor

Pick a few numbers that show whether the agent is doing its job, failing quietly or drifting. This course suggests these, computed per day and per agent version:

| Metric | How to compute | What a change suggests |
|---|---|---|
| **Task success rate** | Runs whose outcome passed your check (a grader, a human review sample, or "the ticket stayed closed") divided by runs | A falling rate after an upgrade means drift; re-run the evaluation suite |
| **Tool error rate** | Tool results with `is_error` (or failures in your tool layer) divided by tool calls | A system it depends on changed, credentials expired, or the model is calling tools wrongly |
| **Cost per task** | Total token cost (input, output, cache reads and writes) divided by completed tasks | Longer loops, bigger tool results, a lost cache, a model change |
| **Escalation rate** | Runs handed to a human, or ending in "I can't determine this", divided by runs | Rising: harder inputs or a regression; falling to zero: check it is not guessing |
| **Approval and denial rates** | Calls that asked, were approved, were denied by a person, were denied by policy | Many denials: the agent is trying things it should not; near-100% approval at high volume: approvers may be rubber-stamping |
| **Turns and duration per run** | From the run's result message | Loops and stalls (Domain 4) |

**Drift after a model or prompt change** is the one that catches teams out. The model you call is a dependency; when its id, version or your prompt changes, behaviour changes. Pin the model id in configuration, change it deliberately, run the evaluation suite before and after, and compare the metrics above for the first days on the new version against the old one.

### Where the signals come from

- **Your own loop:** every response's `usage` and `stop_reason`, every tool call's arguments and result, timed and logged (lesson 5.2 says what to mask).
- **Claude Agent SDK:** the `ResultMessage` at the end of each run carries `num_turns`, `duration_ms`, `total_cost_usd`, `usage` and `permission_denials`; the SDK can export OpenTelemetry traces, metrics and events to your collector, with prompt text and tool inputs left out by default.
- **Claude Managed Agents:** the security monitoring page lists webhooks to watch, including `session.status_idled` (a session went idle, for example waiting for approval), `session.budget_reached`, `session.status_terminated`, `deployment_run.failed` and `deployment.paused`, and `vault_credential.refresh_failed`; and the `evaluated_permission` field on tool-use events for calls that were denied or paused. Deliveries can be missed, so it also recommends listing sessions on a schedule and checking idle ones. It suggests an optional **offline reviewer**: a separate job that has Claude read each session's events afterwards and flag behaviour beyond what you granted.

Alert on the things a person must act on: a session waiting for approval, a run that failed to start, a budget reached, a spike in denials, a credential that cannot refresh.

## The off switch

Decide, before launch, how you stop the agent in under a minute, and rehearse it. An off switch has three parts:

1. **Stop new work.** Disable the trigger: pause the scheduler, unsubscribe the webhook, set a feature flag your loop checks before every iteration.
2. **Stop work in progress.** Interrupt running sessions or kill the containers.
3. **Remove its power.** Revoke or rotate the credentials it holds, so even a run you missed cannot act.

Claude Managed Agents documents this sequence for its own agents: send `user.interrupt` by itself (it stops the model response; a running tool call can finish), pause the deployment for a scheduled agent (archiving ends the schedule permanently), rotate any key that might be exposed at the service that issued it, wait for the session to go `idle`, then archive it (keeps history) or delete it (permanent). Two warnings on the page apply everywhere: **an interrupt does not undo what the agent already did or sent**, and archiving an agent does not stop its running sessions.

> **Watch out:** IP allowlisting of your Claude API keys, where available, protects against a leaked key, but the Managed Agents guide notes that the people and scripts who stop an agent must be on the allowlist too, or they cannot interrupt a running session.

## Putting it together: a deployment plan checklist

When you review a deployment plan, look for each of these. A missing one is a finding.

- Read-only first, then shadow, then a scoped pilot, with written exit criteria.
- Least-privilege identity per agent and environment; no production write credentials in the agent's reach.
- Approval on every irreversible or outward-facing tool, with somewhere for approvals to go when unattended.
- Turn, time and spend caps in code.
- An evaluation suite, re-run on every model, prompt or tool change.
- Metrics and alerts: success, tool errors, cost per task, escalations, denials, paused sessions.
- Logs without secrets; transcripts retained and deleted per policy.
- A rehearsed off switch: stop triggers, stop runs, revoke credentials.

## Key takeaways

- Roll out in stages: read-only, shadow mode on real inputs, a scoped pilot with approvals, then widen, each with a written exit criterion.
- Shadow mode records exactly what the agent would do without executing it; compare it with what people did.
- Treat a model, prompt or tool change as a production change: pin versions, re-run evaluations, watch for drift.
- Monitor task success, tool error rate, cost per task, escalation rate, approval and denial rates, and run length.
- Use the platform's signals (usage fields, OpenTelemetry, Managed Agents webhooks and `evaluated_permission`) and alert on what needs a human.
- The off switch stops new triggers, stops running work and revokes credentials; an interrupt does not undo what was done.
