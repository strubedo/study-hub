## From diagnosis to change

Once the diagnostics agent is trusted, the next request is predictable: "it found the problem, can it fix it?" The safe answer is "it can **prepare** the fix". This lesson designs a change agent whose output is a change request, not a change. The step that touches a device is a separate, existing, audited mechanism that runs only after a person approves. This is the course's own design, applying OWASP's Excessive Agency mitigations (minimal functionality, minimal permissions, human approval, complete mediation) and the approval guidance of lesson 5.3. It includes no code that pushes configuration; it shows the design and the tools.

## The flow

1. **Draft.** From a diagnosis (for example "Gi1/0/14 on `sw-acc-b12` shows rising FCS errors; the patch lead was replaced but errors continue; move the user to spare port Gi1/0/22"), the agent drafts the exact configuration change, a **rollback plan** (the exact commands that restore the current state, taken from the current configuration, not from memory), the pre-checks and post-checks, and the risk and impact statement.
2. **Validate against policy.** Deterministic code, not the model, checks the draft: only allowed configuration sections (access-port settings, descriptions, VLAN membership from an approved list), no changes to management access, AAA, logging or routing protocols, no `shutdown` of uplinks, device in scope for this agent, change size under a limit. Failures go back to the agent as instructive errors.
3. **Open a change request.** The agent calls `create_change_request` with the validated draft. The change system stores the exact diff and computes a hash of it. This is the agent's last action.
4. **Human approval.** An engineer who is not the requester reviews the exact diff, rollback plan and checks in the change system and approves or rejects. If the agent was started by someone, that person cannot approve their own request.
5. **Apply, in a window, through the existing pipeline.** Your existing configuration automation (whatever already applies reviewed changes today) picks up only approved requests, checks that the current time is inside the approved maintenance window, checks that the diff it is about to apply has the approved hash, runs the pre-checks, applies, and logs every step. The agent has no access to this pipeline or its credentials.
6. **Verify.** The post-checks run (interface up, errors not increasing, the user's MAC learned on the new port). Results are attached to the change request.
7. **Roll back automatically on criteria agreed in advance.** If a post-check fails (for example the interface does not come up within five minutes, or the device stops responding to the monitoring poll), the pipeline applies the stored rollback and pages the on-call engineer.

The gate is in step 4, but steps 2, 5 and 7 are what make it safe: the policy check stops nonsense before a human spends time on it; the hash binding means what was approved is what runs; the window and the rollback criteria are enforced by code.

### Two kinds of write, two gates

Domain 4 built an in-loop approval gate: the loop pauses before a state-changing call, shows a person the exact call and its dry-run result, records the approval, then runs the tool. Domain 1's example of an agent that may shut a port flooding a VLAN after the on-call engineer approves fits that gate. This course uses it only for actions that are **narrow, single-target and easy to reverse**, through a purpose-built tool: for example `shutdown_access_port(device, interface)`, which refuses uplinks, trunks and anything not in inventory as an access port, uses a credential that can do only that, and always asks. Everything else (configuration changes, multi-device work, anything you could not undo with one command) goes through the change-request flow above, where the agent holds no production write credential at all.

> **Exam tip:** In a design question, the answer that gives the agent production write credentials "but asks for approval in chat first" is weaker than the one where the agent can only file a change request and a separate approved pipeline applies it. Approval enforced by a system beats approval promised by a prompt.

## Tools for devices, tickets and documentation

| Tool | Read or write | Approval | Where it should run |
|---|---|---|---|
| `get_device`, `get_device_config_section` | Read | None | Inventory and config-backup MCP server you run, read-only token |
| `run_show_command` (allowlisted checks) | Read | None | Device-access MCP server behind your jump host or automation broker |
| `search_tickets`, `get_ticket` | Read | None | Ticket MCP server, read scope |
| `get_runbook`, `search_docs` | Read | None | Documentation MCP server, read-only |
| `validate_change` | Read (runs policy checks) | None | Your policy service; deterministic code |
| `create_change_request` | Write (creates a record; outward-facing) | **Yes**, per call, showing the exact diff | Change-system MCP server with a scope that can create but never approve or implement |
| `add_ticket_comment` | Write (outward-facing) | Yes, or post as a draft for a person to publish | Ticket MCP server, comment scope only |
| Applying a change | Write (production) | Not an agent tool | Your existing change pipeline, after human approval |

**What belongs behind MCP servers:** each system of record (inventory, configuration backups, tickets, documentation, the change system, device access) as its own server, so that each has its own credential, its own scope, its own logs and its own owner. The lessons from Domain 2 and lesson 5.2 apply: remote servers use OAuth with minimal scopes and never pass tokens through; local servers run isolated with per-server credentials; tool lists are reviewed and re-reviewed when they change; and annotations are hints. In Claude Managed Agents, MCP toolsets default to `always_ask`; Anthropic's security guide recommends setting `auto` per tool only for MCP tools that read, enabling only the tools you need with `default_config.enabled: false`, and keeping write tools on `always_ask`.

Device access deserves its own server. Centralising it means the allowlist, the read-only device account, the session logging and the rate limit live in one place you control, instead of in every agent.

## What to keep out of an agent's reach

| Keep out | Why | Instead |
|---|---|---|
| **Credentials with write access to production** | Any steer or error becomes a production change | Read-only accounts for agents; writes through the approved pipeline, or at most one narrow, always-asking tool for an easily reversed action |
| **Bulk or destructive commands**: reload, erase or format storage, delete files on flash, clearing all sessions or all neighbours, shutting many ports, mass ticket closure | One bad call has a large, fast, hard-to-reverse blast radius | Not in any template or enum; denied by device authorization; if ever needed, a human runs them |
| **Security controls**: firewall policy, AAA and command authorization, logging and SIEM configuration, the agent's own permissions, the approval system | An agent that can loosen its own guardrails, or switch off the logs that would show it, has no guardrails | Separate team ownership; agents may read these only where needed for diagnosis |
| **Anything without an audit trail** | You cannot investigate or prove what happened | Every tool call logged with identity, arguments (masked), result and decision |
| **Approving its own work** | Approval by the requester is not approval | Approver must be a different person, enforced by the change system |
| **Raw shells and arbitrary URLs on hosts that can reach the management network** | Open-ended tools defeat every allowlist | Narrow tools; sandboxes with no route to management addresses |

Firewall teams will notice the parallel: this is separation of duties and least privilege, the same principles behind keeping policy authors from approving their own rule changes. The agent is one more principal in that model, and a less predictable one.

## Reviewing a change-agent design

When someone shows you a change agent, check:

- Can the agent's credentials, anywhere, modify production? If yes, stop there.
- Is the approval enforced by a system (change status, hash binding, window), or only by the model being told to ask?
- Does the approver see the exact diff and rollback, or a summary written by the agent?
- Are policy checks deterministic code, run before a human sees the request?
- Are rollback criteria specific and automatic?
- Can the agent reach any security control or audit log with write access?
- Does every step leave an audit record that names the agent, the requester and the approver?

## Key takeaways

- A change agent drafts the change and the rollback, validates them against policy, and opens a change request; it does not apply anything.
- A person who is not the requester approves the exact diff in the change system; an existing pipeline applies only approved, hash-matched changes inside the window, verifies, and rolls back on agreed criteria.
- Put each system of record behind its own MCP server with its own scoped credential; read tools run freely, write tools such as `create_change_request` ask every time.
- Keep production write credentials, bulk-destructive commands, security controls, self-approval and anything without an audit trail out of the agent's reach.
- Approval enforced by systems and credentials is stronger than approval requested in a prompt.
