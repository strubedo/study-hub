## Read-only by default

Start every agent with tools that can only read. A read-only agent that is manipulated or simply wrong produces a bad answer; a write-capable one produces an outage. Add a write tool only when a real task needs it, and then put it behind the approvals of lesson 5.3.

**Separate read tools from write tools.** A single `manage_ticket(action, ...)` tool whose `action` can be `get`, `comment` or `close` is convenient to write and hard to secure. Every control you have works per tool:

- Permission policies and allow rules name tools: Claude Managed Agents sets `always_allow`, `always_ask` or `auto` per tool, and the Claude Agent SDK's `allowed_tools` and `disallowed_tools` take tool names.
- Approval prompts are per tool call, so a reviewer sees "close_ticket" rather than having to inspect an argument.
- Logs, alerts and rate limits are easiest per tool.
- You can remove a tool from one agent and keep it on another.

So split it:

| Instead of | Define | Read or write |
|---|---|---|
| `manage_ticket(action=...)` | `get_ticket`, `search_tickets` | Read |
| | `add_ticket_comment` | Write (outward-facing) |
| | `close_ticket` | Write (irreversible in practice) |
| `device_cli(command=...)` | `run_show_command` (allowlisted read-only commands) | Read |
| | No write tool; changes go through the change process (lesson 5.4) | |
| `inventory(op=...)` | `get_device`, `list_devices_at_site` | Read |

Two traps. First, **"read" is not always harmless**: a read tool that returns secrets, or that fetches a URL the model chose, can leak data. Classify by consequence, not by verb. Second, **don't trust labels you did not set**. MCP lets servers mark tools with annotations such as `readOnlyHint` and `destructiveHint`, but the specification says clients must treat annotations as untrusted unless they come from trusted servers. They are hints for the user interface, not enforcement.

## Scoped credentials, per agent and per environment

The credential a tool uses decides what the tool can really do, whatever its name says. OWASP's Excessive Agency entry gives the classic failure: a tool meant to read a database connects with an identity that can also update and delete.

Rules this course recommends, built on OWASP LLM03:2026 and the vendors' deployment guides:

- **One identity per agent.** The diagnostics agent and the ticket triage agent have different service accounts, so you can see, limit and revoke each.
- **One identity per environment.** The lab agent's account does not exist in production. A prompt that confuses "lab" and "prod" then fails safely.
- **Least rights at the source.** On network devices that means a read-only account with command authorization enforced by your AAA server or a read-only admin profile on the firewall, not just a promise in the tool code. Anthropic's vault documentation puts it bluntly: the agent can do anything the key allows, so scope the key at the service that issued it.
- **Short-lived where possible.** OAuth access tokens with minimum scopes, or credentials issued at launch by a secrets broker, instead of a static token that lives for years. The MCP "Local Server Security" guide recommends short-lived credentials from a secrets manager, one narrowly scoped token per server, and rotating anything a server held when you remove it. Anthropic's Managed Agents guide recommends Workload Identity Federation (short-lived tokens for your application) over long-lived API keys where you can.
- **Act as the user when acting for a user.** OWASP recommends executing tools in the user's context with minimum scope, so an agent cannot read what the requesting engineer could not.

## Where secrets may live

| Place | OK for secrets? | Notes |
|---|---|---|
| Environment variables of the process that runs your tools | Yes, for your own loop, when the agent cannot run commands or code in that process | The Anthropic SDKs read `ANTHROPIC_API_KEY` from the environment; tool credentials can come the same way, scoped per server (the MCP local guide says pass secrets per server, not globally). If the agent has a shell or code execution in that environment, it can read the variables: the Agent SDK hosting page says to keep tool credentials out of the agent's environment and inject them with a proxy |
| A secrets manager or OS secret store | Yes, preferred | Fetch at start-up or per call; rotate centrally |
| A hosted platform's vault | Yes | Claude Managed Agents vaults, Gemini managed agents credentials (details below) |
| A proxy outside the agent's boundary that injects credentials | Yes, strongest | Anthropic's "Securely deploying AI agents" calls this the recommended approach: the agent never sees the credential |
| The system prompt, user messages or tool descriptions | **Never** | Everything there is sent to the model provider, can be repeated by the model, and ends up in transcripts |
| Tool results | **Never** | Redact before returning; a `show running-config` result is full of secrets |
| Logs and traces | **Never** | Mask arguments and results before writing |
| Agent memory and session transcripts | **Never** | Read back into every later session (Domain 3) |
| The repository, including `.mcp.json` and settings files | **Never** | Use variable references such as `${NETBOX_TOKEN}`, never values |

> **Watch out:** Anthropic's Managed Agents guide says not to give the agent a Claude API key or access token at all, even in a vault: code in the sandbox could call the Claude API directly, and the agent's tool settings, approvals and budget would not apply to those calls.

### Vaults in hosted agents (as documented on 2026-11-23)

Claude Managed Agents (beta) has **vaults**: a vault is a collection of credentials, usually per end user, referenced with `vault_ids` when you create a session. Credential types:

- **MCP credentials**, `mcp_oauth` or `static_bearer`, keyed by `mcp_server_url`. The token is injected when the agent connects to that server; it never enters the sandbox.
- **Environment variable credentials**, `environment_variable`, keyed by `secret_name`. Inside the sandbox the variable holds an opaque placeholder; the real secret is substituted only at egress, in outbound requests to the hosts in the credential's `allowed_hosts`, and only in the parts named by `injection_location` (`header`, `body`). The guide recommends header only and an exact host list. These are not yet supported with self-hosted sandboxes.

Secret values are write-only (never returned by the API), a vault holds at most 20 credentials, and archiving a credential purges the secret but keeps the record for audit. Two limits worth knowing: substitution is outbound only, so a token that code fetches with a stored secret arrives in the sandbox unredacted (fetch such tokens yourself and store them); and whoever can start sessions in a workspace can reference its vaults, so keep workloads with different trust levels in separate workspaces.

Gemini's managed agents have a similar feature called credentials: server-managed, write-only secrets that an egress proxy injects at request time, referenced from the environment's network allowlist. OpenAI's Agents SDK documentation recommends keeping auth and audit in the harness, outside the sandbox. The names differ; the pattern (the agent uses a credential it never sees) is the same.

## Secrets in tool results: the network engineer's special case

The commonest way a secret reaches a model is not a careless prompt but an honest tool result. A full running configuration contains enable secret hashes, SNMP communities, TACACS+ or RADIUS keys, VPN pre-shared keys and local user hashes. Hashes are still secrets: they can be attacked offline.

Design the tool, not the prompt:

- Return **the section the task needs** (`show running-config interface Gi1/0/14`) rather than the whole file.
- **Redact in the tool** before returning, with patterns for each platform you run (the next lesson has a small redactor to build).
- Return **a reference** to the full file in your configuration backup system when a person needs it.
- Tell the model in the tool description that values marked `<redacted>` are intentionally hidden, so it does not keep asking.

## Key takeaways

- Start read-only; split read and write into separate tools so permissions, approvals and logs can treat them differently.
- Classify tools by consequence: a read tool that returns secrets or fetches model-chosen URLs is not harmless.
- MCP annotations such as `readOnlyHint` are untrusted hints, not enforcement.
- One identity per agent and per environment, least rights enforced at the source system, short-lived where possible, acting as the user when acting for a user.
- Secrets live in environment variables, a secrets manager, a platform vault or an injecting proxy; never in prompts, tool descriptions, tool results, logs, memory or the repository.
- Claude Managed Agents vaults inject MCP tokens outside the sandbox and substitute environment-variable secrets only at egress, to allowed hosts and locations; keep Claude API keys away from the agent entirely.
- Redact device configurations inside the tool and return only the section the task needs.
