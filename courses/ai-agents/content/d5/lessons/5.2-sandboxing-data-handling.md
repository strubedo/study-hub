## Sandboxing code and command execution

If an agent can run code or shell commands, assume that one day it will run something you did not intend, because it was steered or because it was wrong. A sandbox decides what that something can reach. The requirements are the same whoever provides the sandbox:

| Requirement | What it means | Why |
|---|---|---|
| Isolation | A container, a provider sandbox or a VM, never the bare host or your laptop session | The command cannot read your SSH keys, browser cookies or cloud credentials |
| No network by default | Egress denied unless a task needs it; then an allowlist | Exfiltration needs an exit |
| A working-directory boundary | Only the project directory is mounted, read-only where possible | Mistakes and injections stay inside one folder |
| Resource limits | Memory, process count, CPU time and a wall-clock timeout | A runaway loop or fork bomb cannot take the host down |
| Non-root, minimal capabilities | An unprivileged user with Linux capabilities dropped | Escaping the sandbox gets harder |
| Disposable | Created per task or per session and thrown away | Nothing persists for the next run to inherit |

### What the vendors document (read 2026-11-23)

**Claude Agent SDK, self-hosted.** Anthropic's "Securely deploying AI agents" page compares isolation options: the open-source sandbox runtime (good isolation, very low overhead; OS primitives such as `bubblewrap` on Linux and `sandbox-exec` on macOS, plus a proxy that enforces a domain allowlist), Docker containers (strength depends on setup), gVisor and microVMs such as Firecracker (excellent with correct setup, more overhead). For containers it lists hardening flags including `--cap-drop ALL`, `--security-opt no-new-privileges`, `--read-only`, `--network none`, `--memory`, `--pids-limit`, `--user 1000:1000` and a read-only workspace mount, and warns never to mount `~/.ssh`, `~/.aws` or `~/.config`. Two caveats on the page matter: processes in the sandbox runtime share the host kernel, and its proxy does not inspect TLS by default, so techniques such as domain fronting could reach hosts outside the allowlist.

The SDK also has a built-in command sandbox, set with the `sandbox` option (`SandboxSettings` in the Python reference). Read its defaults before relying on it:

- `enabled` defaults to `False`.
- In Python, if the sandbox cannot start, commands **run unsandboxed with a warning** unless you set `failIfUnavailable`, in which case `query()` raises an error. Set it.
- `allowUnsandboxedCommands` defaults to `True`: the model can ask to run a command outside the sandbox (`dangerouslyDisableSandbox` in the tool input), which then falls back to the normal permission checks. Set it to `False` for an unattended agent.
- `network.allowedDomains` limits sandboxed Bash commands only; it does **not** restrict the WebFetch tool, which uses permission rules.
- Allowing a Unix socket such as the Docker socket (`allowUnixSockets`, a macOS-only setting) effectively grants full host access.
- Combining `bypassPermissions` with `allowUnsandboxedCommands` lets the model run commands outside the sandbox with no approval; the reference calls this an escape from sandbox isolation.

**Claude Managed Agents, hosted.** Each session in a cloud environment gets its own isolated Linux container, while the agent loop, session history and vault secrets stay outside the sandbox on Anthropic's servers. With a self-hosted sandbox, isolation and hardening are yours.

**OpenAI and Google.** OpenAI's Agents SDK has sandbox agents and recommends keeping the harness (loop, approvals, auth, audit) in trusted infrastructure, separate from the sandbox compute. Google's ADK safety page recommends sandboxed code execution and VPC Service Controls perimeters; Gemini's managed agent environments have unrestricted outbound network access by default, with a network allowlist you can set.

## Network egress control

For an operations agent, egress control has two halves: what the sandbox can reach on the internet, and whether it can reach your management network at all. It should not: give it tools that call your inventory or monitoring API, and route device access through those tools, never through a shell with a route to `10.0.0.0/8`.

Claude Managed Agents environments show the settings to look for in any platform:

- `networking` type `limited` restricts the sandbox to `allowed_hosts`; `unrestricted` allows everything except a general safety blocklist (which is not an allowlist). The docs state that an API create request that **omits `networking`** gets `unrestricted` (the Console form starts at Limited), so set it every time.
- In `limited` mode with no hosts listed, nothing is reachable. In `limited` mode, `allowed_hosts` also applies to the server-run `web_search` and `web_fetch` tools.
- In `allowed_hosts`, `example.com` matches only that host and `*.example.com` matches subdomains only; avoid `*.` wildcards and shared-hosting domains where anyone can publish.
- `allow_package_managers` opens public registries and code hosts including every repository on `github.com`, `gitlab.com` and `bitbucket.org`, where anyone can publish and where code in the sandbox can upload; leave it off unless the environment installs packages.
- Access is **by host, not by operation**: an allowed host can receive any request, including uploads, and any credential the command supplies.
- After tightening an environment, start new sessions; running sessions can keep the old limits.

On your own infrastructure the equivalent is an egress proxy or firewall policy with a domain allowlist, logging, and an alert on anything outside the list. The MCP project's "Local Server Security" guide says the same for MCP servers: no network for servers that need none (`--network=none`), an allowlist for the rest.

## Data handling: what leaves your environment

When your code calls a model API, **everything in the request leaves your environment**: the system prompt, the tool definitions, every message and every tool result in the history. If the agent read a configuration file, that file went to the provider. Server tools add a further hop: with web search and web fetch, queries and URLs go from the provider to third parties, and Anthropic's retention page notes that website publishers might retain fetched URLs and request metadata under their own policies.

### Retention options, as documented

Read your provider's current terms and contract; this is not legal advice, and features change. On 2026-11-23:

- Anthropic's "API and data retention" page describes three arrangements for the Claude API (Legacy ZDR, HIPAA readiness and Enterprise Frontier Safeguards), says ZDR is enabled per organization by agreement and does not extend automatically to other organizations, and gives a feature eligibility table for Legacy ZDR and HIPAA readiness. Anthropic's pages describe retention outside ZDR in different terms (the retention page says conversation content is not retained by default except for some designated models that require 30-day retention; the CMEK page names a workspace setting "Standard data retention (30 days)"), so do not assume a default: read the current terms for your organization and workspace. In the table, the Messages API is ZDR-eligible; code execution keeps container data up to 30 days and is not; the Files API, the MCP connector and batch processing are not; Claude Managed Agents is not (sessions persist until you delete them), except fully self-hosted Managed Agents. Anthropic's Managed Agents monitoring page adds that sandbox state is kept for 30 days after the sandbox is created.
- OpenAI's "Data controls" page says abuse monitoring logs are retained for up to 30 days by default, that Zero Data Retention and Modified Abuse Monitoring require OpenAI's approval, and that under ZDR the `store` parameter of the Responses API is always treated as false.

> **Watch out:** "ZDR" on one endpoint says nothing about the next feature you enable. Check the eligibility table for every tool and endpoint in the design, and re-check when you add one.

### Redact before sending

The cheapest control is to send less. Redact configurations and logs inside the tool, before the result enters the history. A small offline redactor in plain Python 3:

```python
import re

PATTERNS = [
    (re.compile(r"^(\s*enable (?:secret|password)(?: \d+)?) \S+", re.M), r"\1 <redacted>"),
    (re.compile(r"^(\s*username \S+ .*?(?:secret|password)(?: \d+)?) \S+", re.M), r"\1 <redacted>"),
    (re.compile(r"^(\s*snmp-server community) \S+", re.M), r"\1 <redacted>"),
    (re.compile(r"^(\s*(?:key|pre-shared-key)(?: \d+)?) \S+", re.M), r"\1 <redacted>"),
    (re.compile(r"^(\s*set (?:password|psksecret)) .+$", re.M), r"\1 <redacted>"),
    (re.compile(r"[\w.+-]+@[\w-]+\.[\w.]+"), "<email>"),
]


def redact(text):
    """Mask secrets and email addresses in device output before it leaves the tool."""
    for pattern, replacement in PATTERNS:
        text = pattern.sub(replacement, text)
    return text


SAMPLE = """hostname sw-acc-b12
enable secret 9 <hash-from-device>
username netops privilege 15 secret 9 <hash-from-device>
snmp-server community <community-string> RO
tacacs server tac-01
 key 7 <key-from-device>
 description owner alice@example.com"""

print(redact(SAMPLE))
```

Save it as `redact.py` and run it with `python3 redact.py` (or `py redact.py` on Windows); every secret value and the email address should come back masked. Patterns are platform-specific and incomplete by nature (OWASP's LLM02:2026 Sensitive Information Disclosure entry advises sanitizing with classifiers, not regular expressions alone, and lists tool-call arguments, logs and telemetry as disclosure channels alongside the answer), so test them against real (lab) output, prefer returning only the needed section, and fail closed: if a result is too large to redact reliably, return a reference instead.

### Logging without secrets or personal data

You need logs to investigate an agent, and logs are where secrets go to live forever. Log, per tool call: time, session or run id, agent identity, tool name, arguments with secrets masked, a result size or hash rather than the full body, the permission decision and who approved. The Claude Agent SDK's OpenTelemetry export, per its hosting page, leaves prompt text and tool inputs out of exports by default, with opt-in flags to include them; keep that default unless you have a reason and a retention policy. Apply the same redactor to log lines that you apply to tool results, and test it with a canary value (a fake secret such as `<canary-secret>` planted in a lab config) to prove it never appears in your log store.

2. Review a proposed environment: `networking` omitted, `allow_package_managers: true`, and the agent toolset on its default policy. Write the three changes you would make and why.
3. For one agent you plan to build, list everything that would leave your environment on a typical run (prompt, tool results, server-tool queries), and find each feature's row in your provider's retention table.

## Key takeaways

- Sandboxes need isolation, no network by default, a working-directory boundary, resource limits, a non-root user and disposability.
- Check sandbox defaults: in the Claude Agent SDK the sandbox is off by default, Python falls back to unsandboxed commands unless `failIfUnavailable` is set, and unsandboxed-command requests are allowed unless you turn them off.
- Control egress with an allowlist per host, remember allowlists are not per operation, and keep agent sandboxes off the management network.
- Every request to a model API carries the whole history out of your environment; server tools send queries and URLs on to third parties.
- Retention depends on the feature: read the provider's eligibility table and current terms for every endpoint and tool you use.
- Redact inside the tool before results enter the history, return sections or references instead of whole configs, and log calls without secrets or personal data.
