## Two kinds of remembering

People say an agent "remembers" two quite different things:

| | Conversation state | Durable memory |
|---|---|---|
| What it is | The message history you resend on each request | Information stored outside the context window that later runs can read |
| Lifetime | One run or session; gone when you discard the list | Survives the session, the process and a restart |
| Who holds it | Your code (Messages API), or an SDK or hosted service that keeps the transcript for you | Your files or database, a memory tool backend, a hosted memory store |
| Limit | The context window, and compaction losses | Storage you choose; the agent must read it back deliberately |
| Example | The tool calls and results of the current diagnostics run | "Site B's access switches uplink via sw-dist-02; known flapping optic replaced on 2026-11-02" |

The Claude Messages API is stateless (Domain 1): conversation state exists only because you send it. Compaction and context editing (topic 3.1) keep that state inside the window, but by summarizing or clearing. Anything that must survive those, or the end of the session, needs durable memory.

Google's ADK documentation draws the same line with its own names: `Session` and `State` for the current conversation thread, and `Memory`, managed by a `MemoryService`, as a searchable archive across sessions.

## Files as memory

The simplest durable memory is a file the agent reads at the start and updates at the end. Anthropic's article "Effective harnesses for long-running agents" (published 2025-11-26) describes the pattern for multi-session coding work: a first "initializer" session writes a progress file, a feature list and a setup script, and every later session starts by reading them, makes incremental progress and updates them before it ends. The prompting best practices page gives the same advice for any long task: structured formats (JSON) for state such as test status, free text for progress notes, and git as a log and checkpoint.

For an operations agent the same idea looks like this:

```text
# incident-notes/INC-4471.md  (written and read by the agent)
Status: open, investigating
Facts (each with source and time):
- 2026-11-23 09:12 get_interface_status sw-acc-b12 Gi1/0/48: up/up, half duplex
- 2026-11-23 09:14 get_interface_counters: 18,342 input errors, rising
Ruled out: DHCP (lease present, get_dhcp_lease 09:10)
Hypotheses (unverified): duplex mismatch with the IP phone on Gi1/0/48
Next step: ask a human to check the far-end duplex setting
```

The structure matters: facts carry their source and time, hypotheses are labelled as unverified, and nothing in it is a credential. A later session that reads it knows what is established and what is only a guess.

## The memory tool

Anthropic's **memory tool** (checked 2026-11-23; stable, no beta header for the tool itself) gives the model a file-style interface to a memory directory. It is an Anthropic-schema **client** tool: the model asks for file operations and **your application runs them** against storage you choose. Nothing is stored at Anthropic.

The whole configuration is one `tools` entry; you do not write an input schema:

```json
{"type": "memory_20250818", "name": "memory"}
```

The model issues commands on paths under `/memories`, a prefix your handler maps to real storage (a per-user directory, database keys, encrypted files):

| Command | Does |
|---|---|
| `view` | Lists a directory (two levels) or shows a file with line numbers; optional `view_range` |
| `create` | Creates a file (`file_text`); the reference behaviour errors if it exists |
| `str_replace` | Replaces unique text (`old_str`, `new_str`) |
| `insert` | Inserts `insert_text` after line `insert_line` |
| `delete` | Deletes a file or directory |
| `rename` | Moves `old_path` to `new_path`, refusing to overwrite |

When the tool is present, the API adds a memory protocol to the system prompt: view the memory directory before doing anything else, record progress as you go, and assume the context window may be reset at any moment. The SDKs ship helpers in their beta namespace: in Python (and C#) you subclass `BetaAbstractMemoryTool` to back memory with your own storage (TypeScript uses `betaMemoryTool`, Java `BetaMemoryToolHandler`), and Python and TypeScript also ship `BetaLocalFilesystemMemoryTool` for local files (Python: `from anthropic.tools import BetaLocalFilesystemMemoryTool`).

The documentation puts these safeguards on you, because your code runs every operation:

- **Path traversal.** A path such as `/memories/../../secrets.env` must be rejected. Resolve every path and check it stays inside the memory root.
- **Sensitive information.** The model usually refuses to write sensitive data, but for stronger guarantees strip it in your handler before writing.
- **Size and expiry.** Cap file sizes and how much `view` returns; delete files not accessed for a long time.

A path check in plain Python, testable offline:

```python
from pathlib import Path, PurePosixPath

MEMORY_ROOT = Path("agent-memory").resolve()   # real storage for the /memories prefix

def resolve_memory_path(virtual_path: str) -> Path:
    """Map '/memories/...' onto MEMORY_ROOT, or raise ValueError."""
    pure = PurePosixPath(virtual_path)
    if pure.parts[:2] != ("/", "memories"):
        raise ValueError(f"{virtual_path} is outside /memories")
    if any(part in ("..", ".") or "%" in part or "\\" in part for part in pure.parts):
        raise ValueError(f"{virtual_path} contains a traversal or encoded sequence")
    real = (MEMORY_ROOT / Path(*pure.parts[2:])).resolve()
    if real != MEMORY_ROOT and MEMORY_ROOT not in real.parents:
        raise ValueError(f"{virtual_path} resolves outside the memory root")
    return real
```

### Memory with compaction and context editing

The memory and context-editing pages describe how they combine. With tool result clearing on, Claude is warned as the threshold approaches, so it can copy what matters from tool results into memory files before they are cleared. With compaction, the summary keeps the active context small while memory preserves the facts that must survive summarization. A long diagnostics run can therefore work far past what one window holds: results come in, conclusions go to `/memories`, raw output is cleared.

## Equivalents elsewhere

- **Claude Agent SDK:** a subagent's `AgentDefinition` has a `memory` field (`"user"`, `"project"` or `"local"`) naming a memory source; with it set, the subagent also gets Read, Write and Edit. CLAUDE.md files loaded through setting sources act as persistent instructions.
- **Claude Managed Agents:** memory stores, covered in the next lesson with sessions.
- **OpenAI Agents SDK:** sessions (for example `SQLiteSession`) persist conversation history in storage you control; the docs call them the default when you want durable memory or resumable runs.
- **Google ADK:** `MemoryService` implementations ingest finished sessions (`add_session_to_memory`) and expose `search_memory`; the in-memory one is for testing only.

## Try it yourself

Offline, no API key needed.

1. Save `resolve_memory_path` and test it with: `/memories/sites/b.md`, `/memories/../etc/passwd`, `/memories/%2e%2e/x`, `/etc/hosts`, `/memories`. The first and last should pass; the others should raise.
2. Extend it into a tiny handler for `view` and `create` only, writing under a temporary directory created with Python's `tempfile.mkdtemp()`.
3. Rewrite the incident note above as JSON with keys `status`, `facts`, `ruled_out`, `hypotheses`, `next_step`. Which format would you rather have a later session parse?

## Key takeaways

- Conversation state is the history you resend; durable memory survives the session and must be read back on purpose.
- A progress file the agent reads first and updates last is the simplest durable memory; label facts with source and time, and hypotheses as unverified.
- The memory tool (`memory_20250818`, name `memory`) is client-side: your handler maps `/memories` to storage you control and runs `view`, `create`, `str_replace`, `insert`, `delete` and `rename`.
- Your handler must block path traversal, cap sizes, expire old files and strip sensitive data.
- Memory pairs with context editing and compaction: write conclusions to memory, let raw results be cleared or summarized.
