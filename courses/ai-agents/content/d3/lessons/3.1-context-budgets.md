## Everything counts, every time

Domain 1 called the context window the agent's working memory. This lesson turns that into a budget you can measure. Anthropic's "Context windows" page (checked 2026-11-23) lists what counts toward the window on every request: the system prompt, the tool definitions, every message (including tool results, images and documents) and the output generated for the turn, including thinking. Cached tokens count too: caching changes what you pay for tokens, not whether they occupy the window.

Because the Messages API is stateless, each loop iteration resends everything. The window fills turn by turn:

| Request | What it carries (illustrative sizes) | Input tokens |
|---|---|---|
| 1 | System prompt 1,500 + tool definitions 4,000 + goal 300 | 5,800 |
| 2 | Request 1 + assistant turn (tool call) 150 + tool result 9,000 | 14,950 |
| 3 | Request 2 + tool call 150 + tool result 600 | 15,700 |
| 4 | Request 3 + tool call 150 + tool result 24,000 | 39,850 |

Two large results, not the instructions, account for most of request 4. That pattern is typical.

### Thinking in the budget

With extended or adaptive thinking, thinking tokens are part of `max_tokens`, billed as output when generated, and count toward the window. Whether earlier thinking blocks stay in later requests depends on the model. The page lists the current Opus, Sonnet, Haiku 5.5, Fable and Mythos models as **keeping** previous thinking by default (it then counts as input on later requests); older models have it stripped automatically. Context editing can override this (next lesson).

### Hidden additions

Some tokens arrive without you typing them. When you send `tools`, the API builds a tool-use system prompt from them; certain tools and features (the memory tool, citations, web search) add their own instructions. Count them by measuring, not by guessing.

## Reading the usage report

Every response carries a `usage` object. The Messages API reference (checked 2026-11-23) lists these fields:

| Field | Meaning |
|---|---|
| `input_tokens` | Input tokens **after the last cache breakpoint**: not read from or written to the cache |
| `cache_creation_input_tokens` | Tokens written to the cache by this request |
| `cache_read_input_tokens` | Tokens read from the cache by this request |
| `cache_creation` | Breakdown of writes: `ephemeral_5m_input_tokens` and `ephemeral_1h_input_tokens` |
| `output_tokens` | Tokens generated, thinking included |
| `output_tokens_details.thinking_tokens` | How many output tokens were thinking |
| `server_tool_use` | Counts such as `web_search_requests` and `web_fetch_requests` |

The prompt caching page states the rule that trips people up: total input is **`cache_read_input_tokens + cache_creation_input_tokens + input_tokens`**. With caching on, `input_tokens` alone can be tiny while the request is huge.

Here is a usage report written from the documented shape (not captured from a live call):

```json
{
  "input_tokens": 412,
  "cache_creation_input_tokens": 1830,
  "cache_read_input_tokens": 37600,
  "output_tokens": 655,
  "output_tokens_details": {"thinking_tokens": 410}
}
```

Read it this way: total input is 412 + 1,830 + 37,600 = **39,842** tokens; the next request will carry at least 39,842 + 655 = 40,497 tokens of history before you add the new tool result. Of the 655 output tokens, 410 were thinking and 245 were the visible answer and tool call.

> **Exam tip:** In a usage exhibit, add the three input fields before you judge how full the window is. A small `input_tokens` with large cache fields means a big, mostly cached request, not a small one.

If you turn on a compaction beta (next lesson), the response also has `usage.iterations`, one entry per sampling step; the docs say to sum across it for billing, because the top-level fields exclude the compaction step.

### Measuring before you send

`client.messages.count_tokens(...)` (endpoint `POST /v1/messages/count_tokens`) takes the same inputs as a message request and returns `input_tokens`. Use it to check a large tool result or a new tool set before it goes into a live loop. A simple running estimate, which Anthropic's compaction page also uses, is to add the last response's total input and its output.

```python
def next_request_floor(usage):
    """Lower bound on the next request's input tokens: everything sent plus the reply.

    `usage` is a dict shaped like the Messages API usage object.
    """
    sent = (usage.get("input_tokens", 0)
            + (usage.get("cache_creation_input_tokens") or 0)
            + (usage.get("cache_read_input_tokens") or 0))
    return sent + usage.get("output_tokens", 0)


BUDGET = 200_000  # this course's example: your own working budget, well below the window

usage = {"input_tokens": 412, "cache_creation_input_tokens": 1830,
         "cache_read_input_tokens": 37600, "output_tokens": 655}
floor = next_request_floor(usage)
print(floor, "of", BUDGET, f"({floor / BUDGET:.0%})")
```

The budget in that sample is deliberately far below the 1M-token window of the current models. Quality degrades as context grows (the docs call this context rot), cost grows with every iteration, and a smaller working budget gives your compaction or summarizing logic room to act before a hard stop.

## Why tool results are the usual culprit

A tool result is paid for again on **every later request** in the run, not once. A 24,000-token `show running-config` returned in iteration 4 of a 20-iteration run is sent 17 times. Instructions are small and stable; tool output is large and grows without limit unless you design it not to.

Ways to shape results (Domain 2 lesson "Tool results the model can act on" covers the design rules; here the point is the budget):

| Technique | Network operations example | Effect |
|---|---|---|
| Filter at the source | `get_interface_counters(device, interface)` instead of `show interfaces` for all 48 ports | Returns the 10 lines that matter |
| Paginate with a cursor | `search_syslog(query, since, limit=20, page_token=...)` | Model asks for more only when needed |
| Summarize in code | Return "2 BGP neighbours down: 192.0.2.1 (Idle, 3h), 192.0.2.5 (Active, 12m)" instead of the full table | Same decision, a fraction of the tokens |
| Return a reference | Save the full config to `configs/sw-core-01/2026-11-23.txt` and return the path, line count and a section index | The agent reads only the section it needs, just in time |
| Cap and say so | "Showing 50 of 1,312 lines. Narrow with section=..." | Bounded, and the model knows how to get more |

Returning references instead of contents is what Anthropic's context-engineering article calls a "just in time" strategy: keep lightweight identifiers (paths, queries, links) and load data with tools when needed. Tool definitions themselves also cost tokens on every request; the "Manage tool context" page points to tool search (`defer_loading`) when an agent has many tools, prompt caching for stable definitions, and context editing for old results.

## What happens at the limit

As Domain 1 stated it (checked again on the "Context windows" page, 2026-11-23):

- If the **input alone** exceeds the window, the API returns HTTP 400 `invalid_request_error` ("prompt is too long").
- On Claude 4.5 and newer models, if the input fits but **generation** reaches the limit, the response is successful with `stop_reason: "model_context_window_exceeded"`, and it is truncated.
- Well **before** either, quality degrades as the window fills.

So a budget is a design decision you make early: a working ceiling, result shaping, and one of the techniques in the next lesson.

> **Real world:** Log `usage` for every iteration. When a run goes wrong, the jump in total input usually points straight at the tool call that flooded the context.

## Try it yourself

An offline exercise; no API key needed.

1. Copy `next_request_floor` into a file and run it with Python 3 on Windows, macOS or Linux.
2. Simulate a 12-iteration run: start at 5,800 tokens; each iteration adds a 150-token tool call, a tool result and 300 output tokens. Use results of 600 tokens, except iterations 3 and 7, which return 24,000 tokens.
3. Print the input size per iteration and the total input across the run. Then replace the two big results with 1,200-token summaries and compare both totals.
4. Decide at which iteration a 100,000-token working budget would be crossed in each version.

## Key takeaways

- System prompt, tool definitions, every message and tool result, and the generated output (thinking included) all count; cached tokens still occupy the window.
- The stateless loop resends everything, so input grows every iteration.
- Total input = `input_tokens` + `cache_creation_input_tokens` + `cache_read_input_tokens`; `input_tokens` alone is only what follows the last cache breakpoint.
- Large tool results dominate budgets because every later request repeats them: filter, paginate, summarize, return references, cap.
- At the limit: 400 "prompt is too long" for oversized input, `model_context_window_exceeded` when generation runs out of room, degraded quality before either.
- Set a working budget well below the window and measure with `usage` and `count_tokens`.
