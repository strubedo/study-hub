## What a subagent is

A subagent is a separate agent instance that a main agent starts for a focused piece of work. The Claude Agent SDK's "Subagents in the SDK" page (checked 2026-11-23) gives four reasons to use one: **context isolation** (the subagent's tool calls and results stay in its own conversation; only its final message returns to the parent), **parallelization**, **specialized instructions**, and **tool restrictions**. The first is the one that matters most for context budgets: a subagent can read forty device configs, and the parent's context grows by a summary, not by forty configs.

## Subagents in the Claude Agent SDK

You define subagents in the `agents` option of `query()`, keyed by name, each an `AgentDefinition`. Claude invokes them through the **`Agent`** tool (the page notes it appears as `"Task"` in the `system:init` tools list and in older versions, so detection code should match both).

```python
import asyncio
from claude_agent_sdk import query, ClaudeAgentOptions, AgentDefinition

AGENTS = {
    "config-auditor": AgentDefinition(
        description="Audits saved device configurations for one site against Example Corp "
                    "standards. Use for questions about how devices are configured.",
        prompt="You audit network device configurations under ./configs. Read only. "
               "Report each finding as device, section, issue, evidence line. "
               "Never print secrets; refer to them as <redacted>.",
        tools=["Read", "Grep", "Glob"],   # the subagent's whole tool set: read-only
        maxTurns=20,
    ),
}

async def main():
    async for message in query(
        prompt="Use the config-auditor agent to check site B for telnet on VTY lines.",
        options=ClaudeAgentOptions(
            allowed_tools=["Read", "Grep", "Glob", "Agent"],  # pre-approved, no prompt
            agents=AGENTS,
            max_budget_usd=1.0,
        ),
    ):
        if hasattr(message, "result"):
            print(message.result)

asyncio.run(main())
```

`AgentDefinition` fields from the page: `description` and `prompt` are required; optional fields include `tools`, `disallowedTools`, `model` (an alias such as `"sonnet"`, `"haiku"` or `"inherit"`, or a full id), `skills`, `memory`, `mcpServers`, `maxTurns`, `background`, `effort` and `permissionMode`. Python keeps the camelCase spelling of multi-word fields.

### What a subagent sees, and returns

A (non-fork) subagent starts with a **fresh context**: its own `prompt` as system prompt, the prompt string the parent passes in the Agent tool call, the project CLAUDE.md (unless configured otherwise) and its tool definitions. It does **not** get the parent's conversation, tool results or system prompt. So the parent must put every path, error message and decision the subagent needs into that one prompt string. The parent receives the subagent's final message, and may summarize it further. On 2026-11-23 the page says a spawned subagent runs **in the background by default**: the Agent tool result first reports `status: "async_launched"` and the report arrives in a later turn (the page explains how to run one in the foreground instead).

Since recent Claude Code versions, the final message is also scanned for instruction-shaped patterns (imitated control tags, turn markers) before the parent reads it, which is a reminder that a subagent's output is input to the parent, not authority over it.

### Scoping tools and permissions

Three rules from the page, each a common mistake:

1. **Omit `tools` and the subagent inherits every tool available to subagents.** A "read-only auditor" defined without a `tools` list is not read-only.
2. **Listing a tool in `tools` does not pre-approve it.** Approval comes from `allowed_tools` and the permission mode on the query; `tools` only limits what the subagent may use.
3. **`disallowedTools` removes tools,** including whole MCP servers with patterns like `mcp__server__*`.

Subagents can spawn subagents of their own, so one prompt can grow into a tree. The page lists three caps: nesting depth with the `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH` environment variable (default 3 layers), concurrency with `CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS` (default 20), and total spend with `max_budget_usd`, which counts subagent requests and ends the query with `error_max_budget_usd`. Claude may also use a built-in `general-purpose` subagent without any definition, and can start forks that copy the conversation; a deny rule such as `Agent(fork)` in `disallowed_tools` stops forks.

## Subagents in Claude Managed Agents

In Claude Managed Agents (beta), the "Multiagent orchestration" page describes a `multiagent` block on the agent definition, of type `multiagent_20261001` on 2026-11-23, that turns on **subagents**, **dynamic workflows** (a program that runs many agents in the background) and an **advisor** model. You list the agents it may delegate to in `subagents.predefined_agents`; `inline_agents` (on by default) lets the agent define unsaved ones, and setting it to disabled restricts delegation to your list.

Points to note:

- Each subagent runs in its own **session thread** with its own history; threads persist, so the lead can send follow-ups.
- Delegation is **one level deep**, and a session has at most 25 child threads at a time.
- **All agents in a session share the same sandbox, filesystem and vault credentials.** Specialized prompts and tool lists do not create a security boundary between them: give a session only credentials that every agent in it may safely hold, and put work that reads untrusted content in a separate session from work that holds change credentials.

## When more agents make things worse

Anthropic's guidance is unusually direct here.

- **"Building multi-agent systems: when and how to use them"** (Claude blog, 2026-01-23) says multi-agent systems are often used where a single agent would do better, and reports that in Anthropic's testing they typically use **3 to 10 times more tokens** than a single agent for equivalent tasks, from duplicated context, coordination messages and hand-off summaries. It names three situations where they pay off: context pollution, parallelizable work, and specialization (for example, too many tools for one agent). Outside those, coordination costs usually exceed the benefits.
- The same post warns against **problem-centric decomposition** (one agent plans, one implements, one tests, one reviews): each hand-off loses context, a "telephone game". It recommends splitting along **context boundaries** instead.
- **"How we built our multi-agent research system"** (2025-06-13) reports agents using about 4× the tokens of chat and multi-agent systems about 15×, describes early failures such as spawning 50 subagents for simple queries, and says errors compound and debugging needs tracing.
- The prompting best practices page warns that recent models delegate readily, sometimes spawning subagents where a direct grep would do, and offers a sample instruction: use subagents for parallel, isolated or independent work; work directly for simple, sequential or single-file tasks.

The costs, in summary:

| Cost | Why it happens | Mitigation |
|---|---|---|
| Tokens multiply | Every agent has its own system prompt, tools and context | Delegate only high-volume, separable work; cap concurrency and budget |
| Lost context at hand-offs | The subagent sees only its prompt string; the parent sees only a summary | Write complete hand-off prompts; split on context boundaries |
| Coordination errors | Overlapping work, contradictory findings, misrouting | Narrow, distinct descriptions; one owner for the final answer |
| Harder debugging | Behaviour is spread over several transcripts | Log every agent's run with a shared trace id (Domain 4) |
| Wider blast radius | Each agent has tools; hosted subagents may share credentials | Read-only tool lists; least privilege (Domain 5) |

## Key takeaways

- A subagent is a separate agent with a fresh context; its intermediate work stays isolated and only its final message returns.
- Agent SDK: `agents={name: AgentDefinition(description, prompt, tools, ...)}`, invoked via the `Agent` tool; pass everything it needs in the hand-off prompt.
- Omitting `tools` inherits every tool; `tools` restricts but does not pre-approve; cap depth, concurrency and budget.
- Managed Agents subagents run in session threads, one level deep, and share the sandbox and vault credentials.
- Anthropic reports multi-agent systems typically cost 3–10× the tokens of one agent; use them for context isolation, parallel work or specialization, split along context boundaries, and otherwise stay with one agent.
