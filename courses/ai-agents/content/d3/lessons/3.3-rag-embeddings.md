## The problem retrieval solves

An agent cannot use what is not in its context. Example Corp's knowledge lives in runbooks, device configuration backups and years of tickets: far more than a prompt should carry. Retrieval puts the few relevant pieces in front of the model at the moment it needs them. There are two broad ways to do it: **retrieval-augmented generation (RAG)** with an embeddings index, built ahead of time, and **agentic search**, where the agent finds things with tools as it works (next lesson).

First, the cheapest option. Anthropic's "Contextual Retrieval" article (published 2024-09-19) says that if a knowledge base is small enough (it gave about 200,000 tokens), you can put all of it in the prompt and skip retrieval. Today's larger windows and prompt caching make that option wider: a 60-page runbook set can sit, cached, behind the system prompt. Retrieval earns its complexity when the corpus is large, changes, or must be filtered by who is asking.

## The RAG pipeline

```text
Indexing (ahead of time)                Query time
-----------------------                 ----------
documents                               question
   |                                       |
chunk  (split into passages)            embed query
   |                                       |
embed  (vector per chunk)  ---------->  vector search (top-k by similarity)
   |                                       |  (+ keyword/BM25 search, merged)
store  (vector index + metadata)        rerank (best few of the top-k)
                                           |
                                        put passages in the prompt, with sources
                                           |
                                        model answers and cites
```

**Embeddings** turn text into vectors so that passages with similar meaning land near each other; similarity is usually cosine or dot product. Anthropic's "Embeddings" page (checked 2026-11-23) states that **Anthropic does not offer its own embedding model**. It names Voyage AI (by MongoDB) as one provider with general, multilingual, code, domain-specific, contextualized and multimodal models plus rerankers, and says to assess several vendors for your case. Its example embeds documents with `input_type="document"` and the query with `input_type="query"`, and notes that Voyage vectors are normalized, so dot product equals cosine similarity.

OpenAI and Google offer both embeddings models and **hosted** retrieval: OpenAI's `file_search` tool searches files you upload into vector stores (`vector_store_ids`), and Gemini's File Search tool imports, chunks and indexes files into a file search store (`file_search_store_names`). Hosted retrieval removes the pipeline work and also removes control over chunking, ranking and where the index lives.

## Chunking: where most RAG systems go wrong

A chunk is the unit you retrieve. Too large, and each one drags irrelevant text into the context; too small, and it loses the meaning around it.

Pitfalls, with network examples:

- **Chunks lose their context.** "Shut the interface, then replace the optic" retrieved alone does not say which device family or which runbook. The Contextual Retrieval article's fix is to prepend a short, chunk-specific context ("From runbook RB-112, 'Replacing optics on access switches', step 4") before embedding and keyword indexing; it reported 49% fewer failed retrievals, and 67% with reranking added, on its test sets.
- **Splitting across structure.** Cutting a configuration in the middle of an interface stanza or an access list separates lines that only mean something together. Split on structure: one stanza, one runbook step, one ticket comment.
- **Missing metadata.** Store device, site, document type, date and source with every chunk, so you can filter ("configs for site B only") and cite.
- **Stale and duplicate versions.** Twelve nightly copies of the same config rank equally; the model may quote last month's. Index the current version and keep history elsewhere.
- **Secrets in the corpus.** Configs contain password hashes, community strings and keys. Scrub before indexing; a vector index is a copy of your data.

## Ranking: what similarity misses

Semantic search is good at "how do I recover a switch that lost its config" and weak at **exact identifiers**: an error code, an interface name like Gi1/0/48, a ticket number, a MAC address. The Contextual Retrieval article recommends combining embeddings with **BM25** (lexical matching) for this reason, then **reranking**: a reranker reads the query with each of the top candidates (say 50) and keeps the best few (say 5) for the prompt.

Other ranking pitfalls: a top-k too small misses the answer, too large floods the context; one long document can crowd out others; and similarity is not authority, so a forum-style ticket comment can outrank the official runbook unless you boost by source.

## Putting retrieved text in the prompt with citations

Retrieved passages are data. Put them in the user turn or a `tool_result`, never in the system prompt, and give each a source so the answer can cite it.

Claude's **citations** feature (stable, checked 2026-11-23) does this in the API. You send documents with `"citations": {"enabled": true}`; plain text and PDFs are chunked into sentences, custom-content documents use your own blocks unchanged. Each text block of the answer can carry citations that point into the sources: `char_location` for plain text, `page_location` for PDFs, `content_block_location` for custom content. The `cited_text` field does not count toward output tokens. Within one request, documents must all have citations enabled or all disabled, and the page warns that citations are incompatible with structured outputs.

For RAG through a tool, the **search results** feature lets your retrieval tool return `search_result` blocks with a `source` and `title`; answers then cite them with `search_result_location`. A tool result written from the documented shape:

```json
{
  "type": "tool_result",
  "tool_use_id": "toolu_01EXAMPLE",
  "content": [
    {
      "type": "search_result",
      "source": "kb://runbooks/RB-112#step-4",
      "title": "RB-112 Replacing optics on access switches (rev 7)",
      "content": [
        {"type": "text", "text": "Step 4: shut the interface, replace the optic, then no shut and confirm the link with show interfaces status."}
      ],
      "citations": {"enabled": true}
    }
  ]
}
```

> **Watch out:** A citation proves the model's sentence came from a retrieved passage. It does not prove the passage is right, current or trustworthy. Retrieved text is untrusted input (Domain 5): a poisoned runbook page cited perfectly is still poisoned.

## Try it yourself

Offline first, then an optional paid step.

1. Write a Python function that chunks a text configuration on lines that start with `interface `, `router `, `ip access-list ` or `line `, and attaches metadata `{"device": ..., "section": ...}` to each chunk. Run it on a short made-up config for `sw-acc-b12.example.com` using 10.20.x.x addresses.
2. Write five questions a NOC engineer would ask. For each, say whether lexical search, semantic search or both would find the right chunk, and why.
3. Optional (needs a Voyage AI key from MongoDB Atlas and `pip install voyageai`; see Anthropic's [Embeddings page](https://platform.claude.com/docs/en/build-with-claude/embeddings)): embed your chunks with `input_type="document"`, embed one question with `input_type="query"` and rank by dot product. Set the key with `export VOYAGE_API_KEY=<api-key>` or `$env:VOYAGE_API_KEY = "<api-key>"`. A few dozen short chunks is a tiny spend.

## Key takeaways

- If the whole corpus fits comfortably (and caches), skip retrieval; use RAG for large, changing or permission-filtered corpora.
- RAG: chunk, embed, index with metadata; at query time embed, search, merge with keyword search, rerank, and insert passages with their sources.
- Anthropic offers no embedding model; its docs point to Voyage AI as one provider and advise comparing vendors. OpenAI and Gemini also offer hosted file search tools.
- Chunk on structure, add context and metadata, drop stale duplicates and scrub secrets.
- Embeddings miss exact identifiers: combine with BM25 and rerank.
- Claude citations (`citations.enabled`, `search_result` blocks) point answers at sources; a citation shows provenance, not truth.
