## Five patterns, one source

Anthropic's engineering article **"Building effective agents"** (published 2024-12-19; it now carries a note that much of the tooling landscape it describes has changed, while the five patterns are still described as originally written) names the building block, an *augmented LLM* with retrieval, tools and memory, and five workflow patterns built from it, before it describes autonomous agents. This lesson uses its names. The article's standing advice frames all of them: find the simplest solution, and add complexity only when it demonstrably improves outcomes.

In the diagrams, `[LLM]` is one model call and `(code)` is ordinary code.

## Prompt chaining

A fixed sequence of calls, each working on the previous output, with optional programmatic **gates** between steps.

```text
input -> [LLM 1] -> (gate: pass?) -> [LLM 2] -> [LLM 3] -> output
                         |
                         +-- fail -> stop / report
```

**Use it when** the task splits cleanly into fixed subtasks; you trade latency for accuracy by giving each call an easier job.

**Network example:** a change-request writer. Call 1 drafts an implementation plan from the engineer's notes; a gate (code) checks the plan names a rollback step and a maintenance window; call 2 writes the rollback plan; call 3 writes the CAB summary. Anthropic's prompting guide still recommends explicit chaining when you need to inspect intermediate outputs, with *self-correction* (draft, review, refine) as its most common form.

## Routing

Classify the input, then send it to a specialized follow-up with its own prompt, tools or model.

```text
                 +--> [LLM: routing/BGP prompt + tools]
input -> [LLM classify] --> [LLM: wireless prompt + tools]
                 +--> [LLM: "send to service desk" template]
```

**Use it when** inputs fall into distinct categories that are better handled separately and the classification is reliable (by a model or a conventional classifier). The article also notes routing easy questions to a small, cheap model and hard ones to a more capable model.

**Network example:** a NOC intake bot reads each new alert and routes BGP alerts to a routing-diagnostics prompt, Wi-Fi complaints to a wireless prompt, and password resets to a canned service-desk reply.

## Parallelization

Several calls run at once and code combines the results. Two variations:

```text
Sectioning                              Voting
input -> [LLM: aspect A] -+             input -> [LLM attempt 1] -+
      -> [LLM: aspect B] -+-> (merge)         -> [LLM attempt 2] -+-> (vote / threshold)
      -> [LLM: aspect C] -+                   -> [LLM attempt 3] -+
```

- **Sectioning:** independent subtasks in parallel. The article's examples include one call answering while another screens for inappropriate requests (guardrails), and evaluating different aspects in separate calls.
- **Voting:** the same task several times for confidence, such as several prompts reviewing code for vulnerabilities and flagging if any finds a problem.

**Use it when** subtasks are independent and you want speed, or you want several perspectives for a higher-confidence result. The article notes models generally do better when each consideration gets its own call.

**Network example (sectioning):** a pre-change review runs three checks at once on a proposed ACL change: security policy compliance, overlap with existing entries, and impact on the monitoring subnet. **(voting):** three independent reviews of a firewall rule set; block the change if two of three flag it.

```python
import asyncio
import anthropic

client = anthropic.AsyncAnthropic()  # reads ANTHROPIC_API_KEY from the environment
MODEL = "claude-haiku-5-5"           # model ids change: check the models overview

CHECKS = {
    "policy": "Does this ACL change violate Example Corp's policy that management "
              "access comes only from 10.20.0.0/24? Answer PASS or FAIL with one reason.",
    "overlap": "Does any new entry shadow or duplicate an existing entry? "
               "Answer PASS or FAIL with one reason.",
    "monitoring": "Could this change block SNMP or syslog from 10.20.5.0/24? "
                  "Answer PASS or FAIL with one reason.",
}

async def run_check(name, instruction, change_text):
    response = await client.messages.create(
        model=MODEL, max_tokens=300, system=instruction,
        messages=[{"role": "user", "content": change_text}],
    )
    text = "".join(block.text for block in response.content if block.type == "text")
    return name, text

async def review(change_text):
    results = await asyncio.gather(*(run_check(n, i, change_text) for n, i in CHECKS.items()))
    return dict(results)   # code, not a model, decides how to combine the verdicts
```

## Orchestrator and workers

A central model breaks the task down **at run time**, hands pieces to worker calls (subagents), and synthesizes their results.

```text
                +--> [worker: subtask 1] --+
input -> [LLM orchestrator] --> [worker: subtask 2] --> [orchestrator: synthesize] -> output
   (decides the subtasks)  +--> [worker: subtask n] --+
```

**Use it when** you cannot predict the subtasks in advance. The article's distinction from parallelization: it looks similar, but the subtasks are not predefined; the orchestrator decides them from the input.

**Network example:** "Audit site B for anything that would break during Saturday's core switch replacement." The orchestrator lists the dependent devices it finds, spawns a worker per device or per service (DHCP relay, HSRP, routing adjacencies), and merges their findings into one risk list. How many workers and which checks depend on what it discovers.

## Evaluator and optimizer

One call generates; another evaluates against criteria and gives feedback; repeat until the evaluator is satisfied or a limit is hit.

```text
input -> [LLM generator] -> draft -> [LLM evaluator] -> (meets criteria?) -> output
              ^                                |
              +-------- feedback --------------+   (cap the rounds in code)
```

**Use it when** there are clear evaluation criteria and iterating measurably helps. The article's two signs of fit: a human's feedback would demonstrably improve the output, and a model can give that kind of feedback.

**Network example:** generating a customer-facing outage notice. The evaluator checks it against a rubric: no internal hostnames or addresses, an estimated restore time, plain language, under 120 words. It sends specific failures back until the notice passes or three rounds are used.

> **Watch out:** An evaluator loop needs a code-side round limit, like any agent loop. Two models can disagree indefinitely.

## From workflows to agents

All five are workflows in the article's sense: code fixes the structure (orchestrator-workers lets the model choose the subtasks, but code still owns the shape). An **agent** is the model directing its own process and tools in a loop. The patterns combine: a routed request can land on an agent, and an agent can call a chained workflow as a tool.

Other vendors name the same shapes (checked 2026-11-23; the mapping of rows to patterns is this course's):

| Pattern | OpenAI Agents SDK | Google ADK |
|---|---|---|
| Chaining | Orchestrating in code: run one agent, feed its output to the next | `SequentialAgent` (deprecated, see below); a graph-based workflow |
| Routing | Handoffs (control moves to the specialist), or classify in code and pick the next agent | Coordinator `LlmAgent` with `sub_agents` (LLM-driven delegation); `RoutedAgent` (TypeScript, experimental) for a code router |
| Parallelization | Orchestrating in code, for example `asyncio.gather` | `ParallelAgent` (deprecated); a graph-based workflow |
| Orchestrator and workers | Agents as tools (`agent.as_tool()`; the manager keeps the final answer) | Coordinator agent with `sub_agents`, or specialists wrapped in `AgentTool` |
| Evaluator loop | Orchestrating in code: a `while` loop of task agent and evaluator agent | `LoopAgent` (deprecated); a graph-based workflow |

OpenAI's orchestration guide frames the main choice as who owns the final answer: with **handoffs** the specialist takes over; with **agents as tools** the manager stays in charge. The Agents SDK's own "Agent orchestration" page adds "orchestrating via code" for chaining, parallel runs and evaluator loops. In ADK, the template workflow agents (`SequentialAgent`, `ParallelAgent`, `LoopAgent`) are deprecated in Python and TypeScript on 2026-11-23 and superseded by graph-based and dynamic workflows; the patterns are the same, the class names are not.

## Key takeaways

- "Building effective agents" names five workflow patterns: prompt chaining, routing, parallelization (sectioning and voting), orchestrator-workers and evaluator-optimizer.
- Chaining: fixed steps with gates. Routing: classify, then specialize. Parallelization: independent pieces or repeated attempts, combined by code.
- Orchestrator-workers differs from parallelization because the orchestrator decides the subtasks at run time.
- Evaluator-optimizer needs clear criteria and a round limit in code.
- Start simple; add a pattern only when it measurably helps. OpenAI calls the delegation choice handoffs vs agents as tools; ADK expresses the fixed patterns as workflows (its older sequential, parallel and loop agents are deprecated).
