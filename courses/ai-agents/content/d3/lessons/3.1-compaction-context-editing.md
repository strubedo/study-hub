## Two ways to shrink a context

When a long run approaches its working budget you can do two different things:

- **Summarize** older turns into a short account and continue from it. This is *compaction*. It keeps the gist of everything and loses detail.
- **Remove** specific old content by rule, such as tool results the model has already used. This is *context editing*. It keeps everything else word for word and loses only what you clear.

Anthropic's Claude API offers both as server-side features, and you can also do either yourself. All the features below were **in beta on 2026-11-23**, each behind its own beta header; names and headers in beta change, so check the pages before you build.

## Compaction on the Claude API

The "Compaction" overview page describes two server-side kinds and recommends **compaction on demand** wherever it is available.

### Compaction on demand

Beta header `compact-2026-09-04`. Your code decides when to compact by sending a separate request with the top-level `compaction` parameter:

```python
import anthropic

client = anthropic.Anthropic()  # reads ANTHROPIC_API_KEY from the environment

def compact(history, system, tools, model):
    """Ask for a summary of `history`; return the new history, or None if no summary came back."""
    response = client.beta.messages.create(
        model=model,
        max_tokens=4096,
        system=system,       # same system prompt and tools as the conversation
        tools=tools,
        betas=["compact-2026-09-04"],
        messages=history,
        compaction={"type": "summarize",
                    "instructions": "Summarize this network diagnostics run. Keep every device, "
                                    "interface, finding and open question. Do not call tools."},
    )
    if response.stop_reason != "compaction":
        return None          # max_tokens, tool_use, refusal...: keep the history, try later
    return [{"role": "assistant", "content": response.content}]
```

What the page specifies:

- The response holds a single `compaction` block (summary text plus a `signature`) and `stop_reason` `"compaction"`; there is no reply.
- You **replace** the summarized messages with that block. It goes **first** in `messages`; send it exactly as returned, with the same beta header, on every later request. Messages left in front of it return 400 `compaction_block_misplaced`; a block left out, or summarized messages left after it, fail silently (no summary, or duplicated content).
- `instructions` (up to 16,384 characters) **replaces** the default summarization prompt. Tell the summarizer what to keep and not to call tools.
- Send the same `system` and `tools`. You cannot combine `compaction` with `context_management` on one request, and a turn that ends in a tool call must get its tool results before you compact.
- Billing appears in `usage.iterations` as a `compaction` entry; the top-level `input_tokens` and `output_tokens` are zero. Sending the block back later adds no compaction cost.
- Images, documents and fetched URLs inside the summarized range are gone afterwards, and `role: "system"` messages in that range stop applying. Restate anything a later turn needs.

Variants on separate pages: keep the last few turns word for word, compact in the background while work continues, and compact again later (the new block summarizes the old one).

> **Watch out:** In the beta API, `"compaction"` is an additional `stop_reason` value. The stable Messages API reference still lists the seven stop reasons from Domain 1. Check `stop_reason` before you look for the block.

### Compaction at a token threshold

Beta header `compact-2026-01-12`. You add an edit to an ordinary request and the API compacts inside that request when input reaches the trigger:

```json
{
  "context_management": {
    "edits": [
      {
        "type": "compact_20260112",
        "trigger": {"type": "input_tokens", "value": 150000},
        "instructions": "Summarize the diagnostics so far. Do not call any tools."
      }
    ]
  }
}
```

The documented defaults: trigger 150,000 input tokens (minimum 50,000), `pause_after_compaction` false. The `compaction` block appears at the start of the response; you append the response as usual and the API drops everything before the block on later requests. The summary is written by the request's own model, and when tools are defined the model occasionally calls a tool instead of summarizing (the block's content is then `null`), which is why the docs suggest instructions that forbid tool calls. Claude Managed Agents runs this kind of compaction automatically for every session.

## Context editing

Beta header `context-management-2025-06-27`. The "Context editing" page notes that for most long conversations compaction is the primary strategy; context editing is for finer control. Two server-side strategies:

| Strategy | What it clears | Main options (defaults) |
|---|---|---|
| `clear_tool_uses_20250919` | Oldest tool results first, replaced by placeholder text; optionally the tool inputs too | `trigger` (100,000 input tokens), `keep` (3 tool uses), `clear_at_least`, `exclude_tools`, `clear_tool_inputs` (false) |
| `clear_thinking_20251015` | Thinking blocks from earlier assistant turns | `keep` (`{"type": "thinking_turns", "value": 1}` when the strategy is included, or `"all"`) |

```json
{
  "context_management": {
    "edits": [
      {
        "type": "clear_tool_uses_20250919",
        "trigger": {"type": "input_tokens", "value": 60000},
        "keep": {"type": "tool_uses", "value": 4},
        "clear_at_least": {"type": "input_tokens", "value": 10000},
        "exclude_tools": ["get_change_ticket"]
      }
    ]
  }
}
```

Points from the page that matter in design:

- Editing happens **server-side before the prompt reaches the model**. Your application keeps the full, unmodified history; you do not sync anything.
- The response reports what happened in `context_management.applied_edits` (for example `cleared_tool_uses` and `cleared_input_tokens`).
- **Caching:** clearing tool results invalidates the cached prefix from the cleared point. `clear_at_least` makes sure each clearing is worth the new cache write. Kept thinking blocks preserve the cache; cleared ones invalidate it.
- **With the memory tool**, Claude gets a warning as the threshold approaches, so it can save important results to memory files before they are cleared (next topic, 3.2).

## In agent SDKs and other vendors

- **Claude Agent SDK** compacts automatically as the window fills and emits a `system` message with subtype `compact_boundary`. The docs warn that early instructions may not survive, so persistent rules belong in CLAUDE.md (re-injected every request); a `PreCompact` hook can archive the full transcript first, and sending `/compact` as a prompt triggers it manually.
- **OpenAI** Responses API: server-side compaction via `context_management` with `compact_threshold`, or a standalone compact endpoint; the returned compaction item is encrypted and not meant to be read.
- **Google ADK** (checked 2026-11-23): its "Context compression" page configures compaction with an `EventsCompactionConfig` on the `App`, either token-based (`token_threshold`, keeping the last `event_retention_size` events verbatim) or a sliding window over invocations (`compaction_interval`, `overlap_size`); token-based takes priority when both are set. (Whether the Gemini API itself offers server-side compaction was not checked for this course.)

## Doing it yourself

Your own summarizer is the third column in Anthropic's comparison: you write the summarization call and its prompt, and you rewrite the history. It is the portable option and the one to use when you need full control. Rules that keep it safe:

1. **Never split a tool call from its result.** The kept tail must not start with a `tool_result` whose `tool_use` was summarized away; the API rejects that history.
2. **Summarize into a structure,** not prose: goal, facts established (with source), things ruled out, open questions, next step.
3. **Keep the system prompt unchanged** so the cache for it survives.
4. **Know what you lose.** The overview notes that thinking in turns you keep after your own summary fails the prefix check on models with preserved thinking.

The split is pure Python and testable offline:

```python
def split_for_summary(messages, keep_last=4):
    """Return (to_summarize, to_keep) without separating a tool_use from its tool_result."""
    cut = max(0, len(messages) - keep_last)
    while 0 < cut < len(messages):
        first = messages[cut]
        content = first["content"] if isinstance(first["content"], list) else []
        starts_with_result = any(block.get("type") == "tool_result" for block in content)
        if not (first["role"] == "user" and starts_with_result):
            break            # safe start: an assistant turn or a plain user turn
        cut -= 1             # a tool_result needs its tool_use: keep one more message
    return messages[:cut], messages[cut:]
```

You then send `to_summarize` to the model with a summarization prompt and build a new history: one user message holding the structured summary, followed by `to_keep`. If `to_keep` starts with a user message, put the summary at the top of that message instead, so the roles still alternate.

## Try it yourself

Offline, no API key needed.

1. Build a list of nine messages by hand: a user goal, then three pairs of an assistant `tool_use` turn and a user `tool_result` turn, then an assistant answer and a new user question.
2. Run `split_for_summary` with `keep_last` from 1 to 9. Check that the kept tail never begins with a `tool_result`.
3. Write the structured summary you would want for a "site B cannot reach the HR portal" run, using the five headings above.
4. On paper, choose between on-demand compaction, threshold compaction and tool result clearing for: (a) a chat agent used all day by the NOC; (b) an overnight audit that reads 400 device configs; (c) a short run that must keep every result word for word.

## Key takeaways

- Compaction summarizes older context; context editing removes chosen content by rule. Both are server-side betas on the Claude API (2026-11-23).
- On-demand compaction (`compaction` parameter): you choose when; the returned `compaction` block replaces the summarized messages and goes first, exactly as returned.
- Threshold compaction (`compact_20260112` edit): the API compacts inside a request at the trigger and drops what came before the block.
- Tool result clearing (`clear_tool_uses_20250919`) replaces old results with placeholders; it invalidates the cache from that point, so set `clear_at_least`.
- Summaries lose detail, attachments and early instructions: keep lasting rules in the system prompt and write durable facts to memory.
- Your own summarizer must keep tool calls and results together and use a structured summary.
