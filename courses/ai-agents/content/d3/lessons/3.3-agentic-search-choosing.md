## Agentic search: let the agent look things up

In agentic search there is no index built in advance. The agent has tools (grep over a config repository, a file reader, a ticket-system query, a CMDB lookup, a documentation search API) and decides what to look for, reads the results, and looks again. Anthropic's "Effective context engineering for AI agents" (2025-09-29) calls this a **just-in-time** strategy: the agent keeps lightweight identifiers such as file paths, stored queries and links, and loads data into context only when it needs it. Each result guides the next step (*progressive disclosure*): a file name, its size or its date tells the agent where to look next.

The article gives Claude Code as the example of a **hybrid**: some context (its CLAUDE.md files) is loaded up front, while glob and grep let it find files just in time, which it says avoids stale indexes. Anthropic's tool-use docs point the same way for tool-heavy agents: return references and let the agent fetch details (lesson 3.1-context-budgets).

A short agentic-search run, written from the documented shapes (not captured):

```text
user:      Which access switches at site B still allow telnet on their VTY lines?
assistant: tool_use grep_configs(pattern="transport input .*telnet", site="B")
user:      tool_result  3 matches: sw-acc-b03, sw-acc-b07, sw-acc-b12 (line vty 0 4)
assistant: tool_use read_config_section(device="sw-acc-b07", section="line vty")
user:      tool_result  line vty 0 4 / transport input telnet ssh ... line vty 5 15 / transport input ssh
assistant: Three switches allow telnet on VTY 0-4: sw-acc-b03, sw-acc-b07, sw-acc-b12 ...
```

No embedding could have answered that as precisely: the question is an exact pattern over current data.

## Comparing the two

| | RAG with embeddings | Agentic search with tools |
|---|---|---|
| Freshness | As fresh as the last indexing run; needs a re-index pipeline | Reads the source of truth at query time |
| Recall on meaning ("how do we handle a flapping uplink?") | Strong: finds paraphrases and related wording | Depends on the agent guessing good search terms |
| Recall on exact identifiers | Weak without keyword search | Strong: grep and filters match exactly |
| Latency | One fast retrieval before the model call | Several model and tool round trips |
| Token cost per question | Predictable: top-k passages | Variable: every search result enters the context (shape results!) |
| Operational burden | Chunking, embedding, vector store, re-indexing, evaluation of retrieval | Tools and their permissions; no index to maintain |
| Access control | Must be enforced in the index (filter by user, tenant, site) | Enforced by the tools' own credentials and APIs |
| Failure mode | Confidently answers from a stale or wrong chunk | Gives up early, or loops over unproductive searches |

Neither is "the modern one". The context-engineering article expects agentic approaches to grow as models improve, while saying the hybrid may suit less dynamic content, and its standing advice is to do the simplest thing that works.

Both share one rule: **retrieved content is untrusted.** A runbook page, a ticket comment or a config description field can contain text written to steer the model. Domain 5 covers the defences; here, keep retrieved text in user or tool-result turns and never let it widen what the agent may do.

## A decision guide for an operations knowledge base

Example Corp wants one assistant that answers NOC questions from three sources. This course's recommendation, by source:

| Source | Character | Recommended retrieval | Why |
|---|---|---|---|
| **Runbooks** (about 300 pages, edited monthly) | Prose, stable, asked about in paraphrase | If it fits and caches, put the runbook index plus the most-used runbooks in the prompt; otherwise RAG with structure-aware chunks, hybrid search and reranking, re-indexed on every edit | Meaning-based questions; content changes slowly |
| **Device configurations** (2,000 devices, backed up nightly) | Structured, exact, changes daily, contains secrets | Agentic search: grep and section-read tools over the current backup repository or a config API, with secrets masked by the tool | Questions are exact ("which devices...", "what is on Gi1/0/48"); freshness matters; embedding configs copies secrets into an index |
| **Tickets** (400,000, growing) | Huge, time-bound, mixed quality | A ticket search tool with filters (site, device, date, status); optionally an embeddings index of resolved-ticket summaries for "have we seen this before?" | Filters do most of the work; similarity helps only for finding related past incidents |

Questions to ask for any source:

1. **Does it fit?** If the corpus fits comfortably in context and caches well, retrieval adds risk and work for little gain.
2. **Are questions about meaning or about exact strings?** Meaning favours embeddings; exact strings favour search tools (or hybrid search).
3. **How fresh must answers be?** Data that changes faster than you can re-index belongs behind a tool.
4. **Who may see what?** If permissions differ per user, the retrieval layer must enforce them; a tool calling an existing API with the user's scoped credentials often does this for free.
5. **Can you evaluate it?** Build a small set of real questions with known answers and measure retrieval before tuning prompts (Domain 4).

> **Real world:** A common good design is hybrid: a short, cached index of what exists ("runbook titles, config repo layout, ticket fields") in the system prompt or a tool description, plus tools to fetch. The agent knows where to look without carrying everything.

### Citations either way

With RAG, return passages as `search_result` blocks or documents with citations enabled (previous lesson). With agentic search, have each tool return the source it read (device and section, ticket id, runbook revision), and require the final answer to name it, as in the system prompt from lesson 3.1-agent-system-prompts. Either way, a reviewer can follow every claim back to its evidence.

## Key takeaways

- Agentic search loads data just in time with tools; RAG retrieves from an index built in advance.
- RAG wins on meaning-based questions over stable prose; agentic search wins on exact, fresh, structured data and needs no index.
- Agentic search costs more round trips and tokens per question; RAG costs a pipeline to build, re-index and evaluate.
- For an operations knowledge base: runbooks by RAG or in-context, configs by search tools with secrets masked, tickets by filtered search with optional similarity over summaries.
- Enforce access control where retrieval happens, cite sources either way, and treat all retrieved text as untrusted.
