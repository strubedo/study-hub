## What is cached

An agent sends the same tool definitions and system prompt on every iteration, plus a history that only grows at the end. Prompt caching lets the API reuse the work it already did on an identical **prefix** of the request instead of processing it again. Anthropic's "Prompt caching" page (checked 2026-11-23) states the order that defines the prefix: **`tools`, then `system`, then `messages`**, up to and including the block that carries the cache marker. A cache hit needs that prefix to be byte-for-byte identical. Caching changes cost and latency only; the page says the output is the same as without it.

Caches are isolated per organization, and on the Claude API also per workspace.

## Turning it on

There are two ways, and they can be combined.

**Automatic caching:** one top-level field. The API puts the breakpoint on the last cacheable block and moves it forward as the conversation grows, so each request reads what the previous one wrote. The page recommends starting here for multi-turn conversations.

**Explicit breakpoints:** a `cache_control` field on individual blocks, up to **four** per request (automatic caching uses one of the four slots). Use them when sections change at different rates, for example tools that never change and a system prompt that changes daily.

```python
import anthropic

client = anthropic.Anthropic()  # reads ANTHROPIC_API_KEY from the environment

TOOLS = [
    {"name": "get_interface_status",
     "description": "Read-only. Status and error counters for one interface.",
     "input_schema": {"type": "object",
                      "properties": {"device": {"type": "string"}, "interface": {"type": "string"}},
                      "required": ["device", "interface"]}},
    {"name": "search_syslog",
     "description": "Read-only. Search syslog for one device and time window.",
     "input_schema": {"type": "object",
                      "properties": {"device": {"type": "string"}, "query": {"type": "string"}},
                      "required": ["device", "query"]},
     "cache_control": {"type": "ephemeral"}},          # breakpoint 1: end of tools
]
SYSTEM = [{"type": "text",
           "text": "You are a read-only network diagnostics assistant for Example Corp...",
           "cache_control": {"type": "ephemeral"}}]     # breakpoint 2: end of system

def ask(messages, model):
    return client.messages.create(
        model=model, max_tokens=1024, tools=TOOLS, system=SYSTEM, messages=messages,
        cache_control={"type": "ephemeral"},            # automatic breakpoint on the history
    )
```

Three rules from the page explain most surprises:

1. **Writes happen only at a breakpoint.** A marker writes one entry: a hash of the prefix ending at that block.
2. **Reads look back up to 20 blocks** from each breakpoint for an entry an earlier request wrote. They do not discover stable content behind a changing block; they only find earlier writes.
3. So **put the breakpoint on the last block that is identical across requests.** A breakpoint on a block that changes every time (a timestamp, the new question) writes a new entry every time and never reads one.

## Lifetimes and minimum size

- The default lifetime is **5 minutes**, refreshed free each time the entry is read. It is measured from the *start* of the request, so a response that streams for 4 minutes leaves about a minute for the follow-up.
- A **1-hour** lifetime is available with `"cache_control": {"type": "ephemeral", "ttl": "1h"}` at a higher write price. When mixing, 1-hour entries must come before 5-minute ones. The page suggests 1 hour when requests come less often than every 5 minutes but more often than hourly, such as a subagent that runs longer than 5 minutes.
- There is a **minimum cacheable length that varies by model** (and by platform). Below it nothing is cached and no error is returned: both cache fields in `usage` are 0. Check the current table on the caching page rather than memorizing a number.
- A new entry is available only after the first response **starts**. Parallel requests sent at the same instant do not hit each other's entry.

## Reading cache activity in `usage`

| Field | Meaning |
|---|---|
| `cache_creation_input_tokens` | Written to the cache this request (split by lifetime in `cache_creation`) |
| `cache_read_input_tokens` | Read from the cache this request |
| `input_tokens` | After the last breakpoint, neither read nor written |

Total input is the sum of all three. A run that is caching well shows a large and growing `cache_read_input_tokens`, a small `cache_creation_input_tokens` (just the new turn) and a small `input_tokens`.

## What it costs

On 2026-11-23 the caching and pricing pages give these multipliers on the model's base input price: a 5-minute write costs **1.25×**, a 1-hour write **2×**, and a read **0.1×**, with lower read multipliers on some of the newest models (the page footnotes 0.05× and 0.025× for specific models). Breakpoints themselves cost nothing. Prices change, so the example below uses only the multipliers.

**Break-even.** A prefix of P tokens written once and read k times costs P × (1.25 + 0.1k); sending it uncached k + 1 times costs P × (k + 1). At k = 1 that is 1.35P against 2P: caching pays from the second request, which is what Anthropic's "Manage tool context" page says.

**A worked agent run.** Tools and system prompt: 8,000 tokens. The goal message: 500. Each iteration appends 1,500 tokens (tool call plus result). Ten requests within the 5-minute lifetime. Request *i* sends 8,500 + 1,500 × (*i* − 1) tokens, from 8,500 up to 22,000; 152,500 input tokens in all. Costs in "base-input-token units" (output tokens are the same in every case and left out):

| Strategy | How the ten requests are billed | Units | vs no cache |
|---|---|---|---|
| No caching | 152,500 × 1 | 152,500 | 100% |
| Breakpoint at end of system only | Request 1 writes 8,000 (×1.25) + 500; requests 2–10 read 8,000 (×0.1) and pay the history at ×1 | 89,700 | 58.8% |
| Automatic caching (breakpoint moves with the history) | Request 1 writes 8,500 (×1.25); each later request reads the previous request's whole input (×0.1) and writes its new 1,500 (×1.25) | 40,550 | 26.6% |

With a 0.05× read multiplier the last two rows become 86,100 and 34,025 units. The lesson is the shape, not the numbers: in an agent, the history soon outweighs the static prefix, so caching the growing history matters more than caching the system prompt alone. (These figures were computed offline for this course.)

## What silently breaks a cache

The prefix is hierarchical, so a change invalidates its own level and everything after it. From the caching page's invalidation table and its "Tool use with prompt caching" page:

| Change | Invalidates |
|---|---|
| Any change to tool definitions: a description edit, an added or removed tool, a **reordered** list, or schema JSON serialized with keys in a different order | Tools, system and messages: everything |
| Enabling or disabling web search or citations | System and messages |
| Switching the speed setting | System and messages |
| Changing `tool_choice` or `disable_parallel_tool_use`, or adding or removing images | Messages |
| Changing thinking parameters or effort | Messages always; tools and system too on some models |
| Different model | Everything (caches are per model) |
| Editing, truncating or re-serializing earlier messages | Messages from that point |
| Context editing clearing old tool results | Messages from the cleared point |

And the ones that are not a "change" at all:

- **A timestamp, request id or ticket number interpolated into the system prompt.** The system prompt differs every request. Put per-run values in the user message.
- **A breakpoint on a block that varies.** Move it to the end of the stable part.
- **Expiry.** A pause longer than the lifetime (a human approval that took 10 minutes) means the next request writes again.
- **Below the minimum length.** Silent: both cache fields stay 0.

On recent models, the caching page notes you can add an instruction mid-run as a `role: "system"` message in `messages` instead of editing the top-level `system`, which keeps the cached prefix intact. Compaction works with caching too: a `cache_control` on the `compaction` block caches the summary, and a breakpoint at the end of the system prompt keeps that part cached when compaction happens.

### Finding the cause

**Cache diagnostics** (stable on the Claude API, 2026-11-23): add `diagnostics={"previous_message_id": None}` on the first request and the previous response's `id` on each later one. The response's `diagnostics.cache_miss_reason.type` names the first divergence: `model_changed`, `system_changed`, `tools_changed`, `messages_changed`, or `previous_message_not_found` / `unavailable` when no comparison was possible. The SDK examples call it through `client.beta.messages.create`.

## Other vendors

- **OpenAI** caches prompt prefixes automatically; the Responses API reports reads in `usage.input_tokens_details.cached_tokens`, and newer models add explicit breakpoints and lifetimes (`prompt_cache_options`, `prompt_cache_breakpoint`) plus an optional `prompt_cache_key`. The same advice applies: stable content first, dynamic content last.
- **Gemini** implicit caching is on by default for 2.5 and newer models and reported in `usage.total_cached_tokens`; the Interactions API supports only implicit caching (explicit cache objects need `generateContent` on supported older models).

## Try it yourself

Offline, no API key needed.

1. Write a Python function `run_cost(n, prefix, goal, step, write=1.25, read=0.1)` that returns the three strategy totals above. Check that you reproduce 152,500, 89,700 and 40,550.
2. Change the step to 6,000 tokens (a chatty tool). How do the percentages move?
3. Find three cache-breakers in this design: tools loaded from a Python `set` (unordered), a system prompt that begins "Current time: ...", and a `tool_choice` that switches between `auto` and `any` every other iteration.

## Key takeaways

- The cached prefix is `tools`, then `system`, then `messages`, and must match exactly up to the breakpoint.
- Automatic caching is one top-level `cache_control`; explicit breakpoints are `cache_control` on blocks, up to four per request, with a 20-block lookback.
- Lifetimes: 5 minutes by default, refreshed on each read; 1 hour with `"ttl": "1h"`. Minimum cacheable length varies by model and fails silently.
- `usage` shows writes in `cache_creation_input_tokens`, reads in `cache_read_input_tokens`, the rest in `input_tokens`.
- Writes cost more than base input, reads far less (multipliers on the pricing page); caching pays from the second request, and caching the growing history matters most in agents.
- Tool changes break everything; toggles such as web search break system and messages; a timestamp in the system prompt or a breakpoint on a varying block means you never get a read.
