## Sessions: state someone else keeps for you

With the raw Messages API you hold the message list yourself. Agent SDKs and hosted agents keep it for you in a **session**, and give you ways to come back to it. Resuming a session restores the conversation, so the agent still "knows" what it read and decided. It does not restore the outside world.

### Claude Agent SDK

The "Work with sessions" page (checked 2026-11-23) says a session is the conversation history the SDK accumulates: your prompt, every tool call, every tool result and every response. The SDK writes it to disk automatically (Claude Code stores transcripts under `~/.claude/projects/<encoded-cwd>/`). Options on `ClaudeAgentOptions`:

| Need | Python option |
|---|---|
| Multi-turn chat in one process | `ClaudeSDKClient`: each `client.query()` continues the same session |
| Pick up the most recent session in this directory after a restart | `continue_conversation=True` |
| Return to a specific session | `resume=session_id` (read `session_id` from the `ResultMessage`) |
| Branch to try another approach without changing the original | `resume=session_id` plus `fork_session=True` |

Things the page is explicit about:

- **Sessions persist the conversation, not the filesystem.** Files the agent changed stay changed; a fork shares the same directory. Use file checkpointing to revert files.
- **Session files are local to the machine.** To resume on another host (CI workers, containers, serverless), mirror transcripts with a session store adapter, move the file, or, often more robust, don't rely on resume: capture the results you need as application state and pass them into a fresh session.
- **Recovering from a limit:** a run that ended with `error_max_turns` or `error_max_budget_usd` can be resumed with a higher limit.

### Claude Managed Agents

In Claude Managed Agents (beta, header `managed-agents-2026-04-01` on 2026-11-23), a session is a stateful resource on Anthropic's side: an agent running in an environment, with its conversation history kept across interactions. Session status moves between `idle`, `running`, `rescheduling` and `terminated`; a session that finishes its work goes `idle`, not `terminated`. Transcripts persist until you delete them, which is one reason the docs list sessions as not eligible for zero data retention (except fully self-hosted Managed Agents).

Durable memory across sessions comes from **memory stores** (beta header `agent-memory-2026-07-22`). The "Using agent memory" page describes them:

- A memory store is a workspace-scoped collection of text documents. Attached to a session in its `resources` (only at creation), it is **mounted as a directory in the session's sandbox**; the agent reads and writes it with its ordinary file tools, and a note describing the mount is added to the system prompt.
- Each change creates an immutable **memory version**, an audit trail with point-in-time recovery.
- Access is `read_write` by default, or `read_only`; up to 8 stores per session, so you can attach a shared read-only store of standards next to a per-team read-write store.

### Other vendors

OpenAI's Agents SDK offers sessions (`SQLiteSession` in Python), `previous_response_id` chaining and named conversations; the Responses API keeps state with `previous_response_id` or the Conversations API. Google ADK uses a `SessionService` for sessions and state and a `MemoryService` for cross-session memory. The names differ; the split between "this conversation" and "what survives it" is the same.

## What not to store

Durable memory is powerful because later sessions trust it. That is exactly why some things must never go into it.

| Don't store | Why | Instead |
|---|---|---|
| **Secrets**: passwords, API keys, SNMP communities, enable secrets, VPN pre-shared keys, session tokens | Memory files are read into context, logged, copied and backed up; a secret there is a secret everywhere | Keep secrets in a secret manager used by the tools, never in what the model reads or writes (Domain 5) |
| **Personal data** beyond the task's need: home phone numbers, personal addresses, HR details | Privacy and retention duties; memory outlives the task that justified it | Store role or ticket references; expire what you must keep |
| **Unverified claims recorded as facts** | A guess written as "Root cause: duplex mismatch" becomes truth for the next session | Label hypotheses; record facts with the tool, value and time that support them |
| **Instructions taken from untrusted content** | Text from a ticket, syslog line, email or web page that says "always…" or "ignore…" would become a standing order | Store observations about content, never directives copied from it |
| **Large raw tool output** | Memory is read back into context; dumps waste the budget you saved by clearing | Store the conclusion and a reference to where the raw data lives |

### Why stored memory is an injection path

Prompt injection (Domain 5) normally lasts one run: the poisoned web page or ticket text leaves the context when the session ends. Memory changes that. If an agent that reads untrusted content can also write memory, an injected instruction can be **saved** and then read by every later session as if it were the agent's own trusted note. Anthropic's memory-store page warns about exactly this: stores attach `read_write` by default, a successful injection could write malicious content into the store, and later sessions then read it as trusted memory; use `read_only` for reference material and any store the agent does not need to modify.

Controls, in order of strength (this course's summary; Domain 5 develops them):

1. **Separate trust levels.** Reference material in read-only stores; per-run notes in a store the agent may write. An agent that reads the internet should not write the store your change agent trusts.
2. **Validate at write time.** Your memory handler (or a hook) can reject writes that contain credential patterns, URLs to unknown hosts, or imperative "always/never" rules.
3. **Provenance.** Every memory entry records which session and source produced it, so you can find and remove a poisoned entry; Managed Agents memory versions give you this audit trail.
4. **Review and expiry.** Have a person review new standing rules; expire notes that nobody has read for a long time.

> **Exam tip:** When a memory exhibit asks what should not be there, look for four things: a credential, personal data, a guess stated as a fact, and an instruction that came from content the agent read.

## Key takeaways

- A session is conversation state kept by an SDK or hosted service; resuming restores the conversation, not files or devices.
- Agent SDK: `continue_conversation`, `resume=session_id`, `fork_session=True`; session files are local unless you use a session store.
- Managed Agents keep sessions server-side; memory stores are mounted into the sandbox, versioned, and attach `read_write` by default unless set `read_only`.
- Never store secrets, unneeded personal data, unverified claims as facts, instructions copied from untrusted content, or raw dumps.
- Writable memory turns a one-run injection into a persistent one: separate trust levels, validate writes, keep provenance, review and expire.
