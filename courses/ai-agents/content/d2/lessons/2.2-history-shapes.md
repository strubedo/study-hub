## The history is the loop's state

Domain 1 built a minimal loop and stated the rules for returning a tool result. This lesson goes deeper into the message history itself, because most tool-use errors you will see in development are history errors: a result in the wrong place, a call with no answer, results split across messages. The API checks the placement and pairing rules on every request and rejects a history that breaks them with a 400 `invalid_request_error`. Split results are subtler: the Messages API reference says consecutive messages with the same role are combined into one turn, so the request may be accepted, but the parallel tool use documentation calls it wrong because it teaches Claude to stop making parallel calls.

## The two block shapes

From Anthropic's "Handle tool calls" page, checked 2026-11-23.

A **`tool_use` block** appears in the `content` of an **assistant** message. It has:

- `type`: `"tool_use"`
- `id`: a unique id for this call (Anthropic's examples start with `toolu_`)
- `name`: the tool being called
- `input`: an object that should conform to the tool's `input_schema`

A **`tool_result` block** appears in the `content` of the next **user** message. It has:

- `type`: `"tool_result"`
- `tool_use_id`: the `id` of the call it answers
- `content` (optional): a string or a list of `text`, `image`, `document` or `search_result` blocks
- `is_error` (optional): `true` if the tool failed or the call was invalid

Claude has no `tool` or `function` role. Calls belong to the assistant, results to the user.

## The rules, stated as checks

The documentation's steps for continuing after a `tool_use` response translate into checks you can run on your own history before sending it:

1. **Keep the assistant content unchanged.** Append the response's `content` as an `assistant` message exactly as received. Editing it can break things in non-obvious ways: the troubleshooting page documents a 400 error when `thinking` blocks in the latest assistant message are modified.
2. **Answer immediately.** The user message with the results must come right after the assistant message with the calls. Nothing in between.
3. **Results first.** In that user message, every `tool_result` block comes before any `text` block. Text before a result is a 400 error.
4. **Answer every call.** One `tool_result` per `tool_use` block, matched by `tool_use_id`, even if the tool failed or you chose not to run it.
5. **Same tools.** Send the same `tools` array on the follow-up request.

Break rule 2, 3 or 4 and the error message reads: "`tool_use` ids were found without `tool_result` blocks immediately after", followed by the ids. That one message is worth recognizing on sight.

## Parallel tool calls

By default, Claude may put several `tool_use` blocks in one response. Anthropic's "Parallel tool use" page says the API does not prescribe an execution order: run the calls concurrently, sequentially, or in any mix. Its guidance: independent, read-only calls are usually safe to run in parallel for lower latency; calls with side effects, shared state or ordering requirements may be better run in sequence.

Whatever you choose, the results go back **together in one user message**. The parallel tool use page is specific about why: sending a separate user message per result is wrong, and it "teaches" Claude to avoid parallel calls on later turns. The symptom is quiet (calls made one at a time where parallel would be better), not a 400 error, so it is easy to miss.

If you run a batch sequentially and stop early (say the first call failed and the rest depend on it), you still owe a result for every call you skipped: `is_error: true` with a short explanation such as "Not executed: the preceding call failed." For the computer use and browser use toolsets the rule is stricter and documented on their pages: run member calls in order and stop at the first failure.

### Turning parallel calls off

Set `disable_parallel_tool_use: true` **inside** the `tool_choice` object. It is not a top-level parameter. The effect depends on the `tool_choice` type:

| `tool_choice` | With `disable_parallel_tool_use: true` |
|---|---|
| `{"type": "auto", ...}` | At most one tool call per response; plain text still allowed |
| `{"type": "any", ...}` or `{"type": "tool", ...}` | Exactly one tool call (on models that support forced tool use; lesson 2.2-tool-choice-runner) |

Set it on the request whose response you want limited; it has no effect on calls already made. When would you turn it off? When tools must run one at a time and you want the model to see each result before choosing the next, for example a sequence of dependent lookups. For read-only diagnostics, leaving parallel calls on usually saves time.

OpenAI's Responses API has a top-level `parallel_tool_calls` parameter (set it to `false` for zero or one call); Gemini documents parallel function calling, with results returned as `function_result` steps matched by `call_id`. Checked 2026-11-23.

## Worked example: three calls in one turn

The NOC agent gets "Users on sw-access-12 and sw-access-14 report slow file transfers since this morning." With three read-only tools available, a reasonable model response contains three `tool_use` blocks. Here is the history after your code runs them, written from the documented shapes (ids are placeholders; this is not captured output):

```json
[
  {"role": "user", "content": "Users on sw-access-12 and sw-access-14 report slow file transfers since this morning. Uplinks are GigabitEthernet1/0/48 on both."},
  {"role": "assistant", "content": [
    {"type": "text", "text": "I'll check both uplinks and look for recent changes."},
    {"type": "tool_use", "id": "toolu_01A", "name": "get_interface_status",
     "input": {"device_hostname": "sw-access-12.example.com", "interface_name": "GigabitEthernet1/0/48"}},
    {"type": "tool_use", "id": "toolu_01B", "name": "get_interface_status",

     "input": {"query": "sw-access-12", "ticket_type": "change", "status": "any", "limit": 5}}
  ]},
  {"role": "user", "content": [
    {"type": "tool_result", "tool_use_id": "toolu_01A",
```

Check it against the rules: the assistant content is unchanged, the results message follows immediately, it holds only `tool_result` blocks, and all three ids are answered, including the failure. Returning the results in a different order would also be fine: matching is by `tool_use_id`, not by position.

## When a server tool is waiting too

Topic 2.3 introduces server tools that Anthropic runs. One case touches the history rules: if the model calls a server tool and one of your client tools in the same turn, the response comes back with `stop_reason: "tool_use"` and a `server_tool_use` block that has no result yet. Your user message must then contain **only** `tool_result` blocks; text after them ends the turn early and the request fails with an error naming the unresolved server tool. Lesson 2.3-server-tools shows the full exchange.

## Try it yourself

An offline build: a history checker in plain Python 3, no SDK.

```python
def check_history(messages):
    """Return a list of rule violations in a Claude-style message history (dicts only)."""
    problems = []
    for i, msg in enumerate(messages):
        content = msg["content"] if isinstance(msg["content"], list) else []
        calls = [b["id"] for b in content if b.get("type") == "tool_use"]
        if msg["role"] != "assistant" or not calls:
            continue
        if i + 1 >= len(messages):
            continue  # last message: the results have not been added yet
        nxt = messages[i + 1]
        blocks = nxt["content"] if isinstance(nxt["content"], list) else []
        if nxt["role"] != "user":
            problems.append(f"message {i + 1}: tool calls must be answered by the next (user) message")
            continue
        kinds = [b.get("type") for b in blocks]
        if "tool_result" in kinds and any(k != "tool_result" for k in kinds[:kinds.count("tool_result")]):
            problems.append(f"message {i + 2}: text appears before a tool_result")
        answered = {b.get("tool_use_id") for b in blocks if b.get("type") == "tool_result"}
        for call_id in calls:
            if call_id not in answered:
                problems.append(f"message {i + 2}: no tool_result for {call_id}")
    return problems
```

1. Save it as `check_history.py`. Paste the worked-example history above into a file and load it with `json.load`, then call `check_history`. It should return an empty list.
2. Break it three ways and confirm each is caught: move a `text` block before the first result; delete the result for `toolu_01B`; split the three results into three user messages (caught because the message right after the calls answers only one of them). The checker is deliberately stricter than the API on the last one: the API combines consecutive user messages into one turn and may accept the split, but the documentation calls it wrong because it discourages parallel calls.
3. Extend the checker to flag a `tool_result` whose `tool_use_id` matches no call in the previous assistant message, a mistake that usually means ids were copied from the wrong turn.

## Key takeaways

- `tool_use` (assistant): `id`, `name`, `input`. `tool_result` (user): `tool_use_id`, optional `content`, optional `is_error`. No `tool` role.
- Append the assistant content unchanged; answer immediately; results before any text; one result per call; same `tools` array.
- "`tool_use` ids were found without `tool_result` blocks immediately after" means a missing, misplaced or late result.
- Parallel calls: you choose the execution order; return all results in one user message, including `is_error` results for calls you did not run. One message per result may be accepted but teaches Claude to stop calling tools in parallel.
- `disable_parallel_tool_use: true` goes inside `tool_choice`: at most one call with `auto`, exactly one with `any` or `tool`. OpenAI's equivalent is the top-level `parallel_tool_calls: false`.
- If a server tool is still waiting in the same turn, the user message must contain only `tool_result` blocks.
