## From tool definitions you write to tool definitions a server publishes

In topic 2.1 you wrote each tool definition into the request yourself. With MCP the **server** publishes its tools and the host fetches them. The model still sees a name, a description and an input schema, so everything from lesson 2.1-define-tools about good names and descriptions still applies; it is just written by the server author. This lesson follows one tool through the protocol, using revision 2026-07-28 of the specification (current on 2026-11-23). The tool messages are the same in the legacy revisions apart from the per-request metadata and the `resultType` field.

## The tool definition

The specification's `Tool` data type has these fields:

| Field | Required | Meaning |
|---|---|---|
| `name` | Yes | Unique identifier within the server |
| `title` | No | Human-readable display name for user interfaces |
| `description` | No in the schema, but you always want one | What the tool does; the specification's schema calls it a hint to the model |
| `icons` | No | Icons for user interfaces |
| `inputSchema` | Yes | A JSON Schema **object** (never `null`) with `"type": "object"` at the root; defaults to JSON Schema 2020-12 when there is no `$schema` |
| `outputSchema` | No | JSON Schema for the tool's structured result |
| `annotations` | No | Behaviour hints (below) |

Two details catch people out.

**A tool with no parameters still needs a schema.** The specification recommends `{"type": "object", "additionalProperties": false}`, which accepts only an empty object; `{"type": "object"}` also works but accepts anything. `null` is invalid.

**MCP names allow more characters than Claude names.** MCP says a tool name should be 1 to 128 characters of ASCII letters, digits, underscore, hyphen and **dot**, case-sensitive, with no spaces or commas; `admin.tools.list` is a valid MCP name. The Claude Messages API's tool name pattern (`^[a-zA-Z0-9_-]{1,128}$`, lesson 2.1-define-tools) has no dot. A host that hands MCP tools to Claude has to deal with that. This course's advice: when you write servers, stay inside the narrower set. Tool names are only unique **within one server**; the specification warns that hosts aggregating several servers can see collisions (two servers each exposing `search`) and should disambiguate, for example by prefixing a server identifier. That is the namespacing advice of lesson 2.1-define-tools applied across servers.

### Annotations are hints, not guarantees

`annotations` (type `ToolAnnotations`) can contain:

| Annotation | Meaning when true | Default |
|---|---|---|
| `readOnlyHint` | The tool does not modify its environment | `false` |
| `destructiveHint` | It may perform destructive updates (only meaningful when not read-only) | `true` |
| `idempotentHint` | Repeating the call with the same arguments has no extra effect (only meaningful when not read-only) | `false` |
| `openWorldHint` | It interacts with an open world of external entities, like web search | `true` |
| `title` | A display title | none |

Look at the defaults: a tool with no annotations is assumed to write, possibly destructively, to an open world. That is the cautious reading. More important is the specification's warning, repeated on the tools page and in the schema: clients **must** consider annotations untrusted unless they come from trusted servers, and should never make tool-use decisions based on annotations from untrusted servers. A server that says `readOnlyHint: true` about a tool that reboots switches is lying, and the protocol cannot catch it. Use annotations to drive the user interface (a confirmation prompt for anything not read-only), never as a security boundary.

## Listing tools: `tools/list`

A server that offers tools declares the `tools` capability and answers `tools/list`. A trimmed example for Example Corp's inventory server, written from the specification's shapes (not captured):

```json
{
  "jsonrpc": "2.0",
  "id": 2,
  "result": {
    "resultType": "complete",
    "tools": [
      {
        "name": "get_interface_status",
        "title": "Interface status",
        "description": "Read-only. Returns admin status, oper status, speed and error counters for ONE interface on ONE Example Corp switch. Use it when a user reports a slow, flapping or dead port. Does not return configuration.",
        "inputSchema": {
          "type": "object",
          "properties": {
            "device_hostname": {"type": "string", "description": "Inventory hostname, for example sw-access-12.example.com"},
            "interface_name": {"type": "string", "description": "Full interface name, for example GigabitEthernet1/0/24"}
          },
          "required": ["device_hostname", "interface_name"],
          "additionalProperties": false
        },
        "annotations": {"readOnlyHint": true, "openWorldHint": false}
      }
    ],
    "ttlMs": 300000,
    "cacheScope": "private"
  }
}
```

Points from the specification:

- The list supports **pagination**: the client passes `cursor`, and the server returns `nextCursor` while there are more pages.
- In 2026-07-28 the list result also carries **caching hints**: `ttlMs` (how long the client may treat it as fresh, in milliseconds) and `cacheScope` (`"public"` or `"private"`, whether shared intermediaries may cache it).
- The list **may change over time**, may vary with the authorization presented on the request (a token with fewer scopes may see fewer tools), and must not vary per connection. Servers should return tools in a **deterministic order**, which helps client caching and prompt caching.
- If the server declared `listChanged`, it sends `notifications/tools/list_changed` when the list changes. In 2026-07-28 a client receives it only after opening a `subscriptions/listen` stream with `toolsListChanged: true`; then it calls `tools/list` again.

That last point is a trust issue, covered in lesson 2.4-transports-auth: the tool you reviewed last week may not be the tool the server offers today.

## Calling a tool: `tools/call`

The client sends the tool `name` and the `arguments` object:

```json
{"jsonrpc": "2.0", "id": 3, "method": "tools/call", "params": {"name": "get_interface_status", "arguments": {"device_hostname": "sw-access-12.example.com", "interface_name": "GigabitEthernet1/0/24"}}}
```

(Every 2026-07-28 request also carries the `_meta` block from lesson 2.4-mcp-architecture; it is left out here, as the specification's own examples do.)

The result (`CallToolResult`) has:

- `content`: a list of content blocks for the model. Types: `text`, `image` (base64 `data` plus `mimeType`), `audio`, `resource_link` (a URI the client can fetch) and `resource` (an embedded resource).
- `structuredContent`: optional, any JSON value. If the tool declared an `outputSchema`, the server must conform to it and the client should validate against it. For backwards compatibility the server should also put the serialized JSON in a text block. The specification notes this is server-produced data, unrelated to a model's "structured outputs" (topic 2.5).
- `isError`: whether the call ended in an error. If it is absent, the call is treated as successful.

```json
{
  "jsonrpc": "2.0",
  "id": 3,
  "result": {
    "resultType": "complete",
    "content": [{"type": "text", "text": "{\"admin_status\": \"up\", \"oper_status\": \"down\", \"speed_mbps\": 1000, \"input_errors\": 0, \"crc_errors\": 0}"}],
    "structuredContent": {"admin_status": "up", "oper_status": "down", "speed_mbps": 1000, "input_errors": 0, "crc_errors": 0},
    "isError": false
  }
}
```

## Two kinds of error

The specification separates them, and the difference decides what the model sees.

| | Protocol error | Tool execution error |
|---|---|---|
| Causes | Unknown tool, a request that does not match the `tools/call` schema, server faults | API failures, invalid argument values, business-rule failures |
| Shape | JSON-RPC `error` with a `code` (for example `-32602`, "Unknown tool: ...") | A normal `result` with `isError: true` and an explanation in `content` |
| Who should see it | The client; it **may** pass it to the model, though the model is less likely to recover | The model: clients **should** pass it on so the model can correct itself and retry |

Implementations do not all draw the line in the same place: the official Python SDK v2, for example, returns an unknown tool name as a result with `isError: true` rather than a JSON-RPC error, so a host must handle both shapes.

That mirrors the `is_error` advice from lesson 2.1-tool-results: an error the model can read ("No device sw-acces-12.example.com; closest match sw-access-12.example.com") lets it fix the call. If you write the host yourself and forward an MCP result to Claude, carry `isError: true` across as `is_error: true` on the `tool_result` block (this course's mapping; the two specifications do not mention each other). Claude's MCP connector (lesson 2.4-build-server) shows the same mapping in its own blocks: `mcp_tool_use` for the call and `mcp_tool_result` with `is_error` for the result.

> **Watch out:** A server that returns an error message as normal text with `isError` false (or missing) tells the client the call **succeeded**. The model may then report "the device has no interfaces" instead of "the lookup failed". Always set the flag.

## Security duties on both sides

The tools page lists them. Servers **must** validate all tool inputs, implement access controls, rate-limit invocations and sanitize outputs. Clients **should** ask the user to confirm sensitive operations, show tool inputs before calling the server (to catch accidental or malicious data exfiltration), validate tool results before passing them to the model, set timeouts and log tool use for audit. Domain 5 builds these into a full design.

## Try it yourself

Paper and plain Python; no SDK needed.

1. Save the `tools/list` result above as `list.json` and the `tools/call` result as `call.json`. Validate both with `python3 -m json.tool` (Windows: `py -m json.tool`).
2. In `list.json`, add a second tool, `list_devices`, that takes no parameters. Write its `inputSchema` the way the specification recommends.
3. Write a ten-line Python function that takes a parsed `CallToolResult` dict and returns `("error", text)` when `isError` is true and `("ok", structuredContent or text)` otherwise. What should it do when `isError` is missing?
4. A third-party server publishes `reset_port` with `"annotations": {"readOnlyHint": true}`. Write two sentences for your team on why your host still asks for confirmation.
5. Rename one tool `inventory.list_devices`. Is that a valid MCP name? Is it a valid Claude tool name? What would you change?

## Key takeaways

- An MCP tool has `name`, `inputSchema` (an object schema, never `null`) and usually `title`, `description`, `outputSchema` and `annotations`.
- MCP tool names may contain dots; Claude tool names may not. Names are unique only per server, so hosts prefix or otherwise disambiguate.
- Annotations (`readOnlyHint`, `destructiveHint`, `idempotentHint`, `openWorldHint`) are untrusted hints with cautious defaults; use them for the UI, never as a security control.
- `tools/list` is paginated, can change over time, and in 2026-07-28 carries `ttlMs` and `cacheScope`; change notifications arrive through `subscriptions/listen`.
- `tools/call` returns `content`, optional `structuredContent` and `isError`. Unknown tools and malformed requests are JSON-RPC errors; failures the model can fix are results with `isError: true`.
- Servers validate inputs and sanitize outputs; clients confirm sensitive calls, show inputs and validate results.
