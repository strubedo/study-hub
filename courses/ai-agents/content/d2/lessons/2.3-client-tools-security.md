## Anthropic-defined, client-executed

Between your own tools and Anthropic's server tools sits a third bucket: tools whose **schema Anthropic defines** but whose **calls your application runs**. The "How tool use works" page explains why they exist: Claude has been trained on many successful runs with these exact signatures, so it calls them more reliably and recovers from errors better than it would with a home-made equivalent. The execution model is the same as for your own tools: a `tool_use` block arrives, your code does the work, you send a `tool_result`.

What "client-executed" means in practice: nothing happens on Anthropic's side except the model deciding what it wants. **Your** process runs the shell command, edits the file or moves the mouse, with **your** credentials, on **your** network. Every safety property of these tools is therefore yours to build.

## The tools, as documented on 2026-11-23

| Tool | Declared as | What the model can ask for | Notes |
|---|---|---|---|
| Bash | `{"type": "bash_20250124", "name": "bash"}` | A command to run in a bash session your app keeps alive between calls | State (working directory, variables, files) persists across commands |
| Text editor | `{"type": "text_editor_20250728", "name": "str_replace_based_edit_tool"}` | `view`, `str_replace`, `create`, `insert` on files | Version is model-keyed: `text_editor_20250124` is for earlier models; optional `max_characters` on the newer version |
| Memory | `{"type": "memory_20250818", "name": "memory"}` | `view`, `create`, `str_replace`, `insert`, `delete`, `rename` under `/memories` | Your handler maps `/memories` onto real storage and must reject paths outside it (Domain 3 covers memory) |
| Computer use | `{"type": "computer_toolset_20260801"}` (no `name`) | 17 member tools such as `screenshot`, `left_click`, `type`, `zoom` | A client toolset; calls carry `"toolset_name": "computer"`. Earlier beta versions (`computer_20251124`, `computer_20250124`) need beta headers and are limited to older models |
| Browser use | `{"type": "browser_toolset_20260801"}` (no `name`) | 27 default member tools such as `navigate`, `read_page`, `left_click`, `screenshot` | A client toolset; calls carry `"toolset_name": "browser"`. Runs in a browser your application drives |

You do not write an `input_schema` for any of these: the type string fixes it. The two toolsets are single entries that expand into many member tools; dispatch their calls on both `toolset_name` and `name`, return results that echo the `toolset_name`, and when several member calls arrive in one turn, run them in order and stop at the first failure. Neither toolset accepts `strict: true` or `input_examples`. As with server tools, the type strings are dated and change; copy them from each tool's page.

## Security: what each kind of tool can reach

The question that separates the three buckets is not "who wrote the schema" but **"whose environment does the work happen in, and what can it touch?"**

| | User-defined client tool | Anthropic-defined client tool | Server tool |
|---|---|---|---|
| Runs in | Your process | Your process (shell, files, desktop, browser) | Anthropic's infrastructure |
| Can reach | Exactly what your function does | Whatever the shell, file system, screen or browser can reach: often far more than intended | The public web (search, fetch) or an isolated container with no internet (code execution) |
| Can reach your internal network? | Only through what you code | Yes, if the host can | Web fetch: no (private addresses are blocked). Code execution: no outbound access at all |
| Credentials used | Yours, scoped to the function | Yours, of the user or session running the tool | Anthropic's; your secrets reach it only if you put them in the conversation or upload them |
| Main risk | A badly scoped function | A model-chosen command or click with your privileges | Untrusted web content entering the context; data leaving in queries and URLs |
| Your controls | Narrow, read-only functions; validation | Isolation, least-privileged user, allowlists, confirmation, logging | Domain filters, `max_uses`, `url_sources`, admin settings in the Console, choosing whether to enable the tool at all |

### Anthropic-defined client tools are the most powerful

A `bash` tool on a jump host is, in effect, a shell for the model. Anthropic's bash tool page says it plainly: your application runs whatever command Claude requests, so run the session in an isolated container or virtual machine as the least-privileged user that can do the work, and treat every command as untrusted input. It adds four controls: validate commands with an **allowlist** rather than a blocklist, set resource limits, **log every command and its output**, and **redact credentials** from output before returning it. The computer use page lists a dedicated VM or container with minimal privileges, no access to sensitive data such as logins, an allowlist of internet domains, and a **human confirmation** for anything with meaningful real-world consequences.

For network operations, this course's advice follows from that: prefer narrow user-defined tools like `get_interface_status` to a general shell, because a narrow tool cannot be talked into `configure terminal`. If you do use the bash or text editor tool, point it at a lab or a copy (a Git working tree of configurations, reviewed through a pull request), never at production devices, and see Domain 5 for approval gates.

### Fetched content is untrusted input

Everything a web page, a search result, a screenshot or a ticket body contains enters the model's context as data that someone else wrote. Anthropic's documentation warns that the model can be led by instructions embedded in such content (indirect prompt injection). The computer use page says screenshots and pages can carry instructions that conflict with yours, and describes classifiers that scan computer-use results for likely injections; those classifiers reduce the risk, they do not remove it. Practical consequences:

- Keep fetched content in result blocks; never paste it into the system prompt.
- Give an agent that reads the web **no** tool that can change something important in the same run, or put a human confirmation in front of that tool.
- **Citations help a human check the answer**, which is why web search always returns them and web fetch can. They show where a claim came from; they do not prove the source is honest.

### Domain allow and block lists

Server tools that access the web accept `allowed_domains` or `blocked_domains`, never both. The rules from the "Server tools" page: no scheme (`example.com`, not `https://example.com`); a domain includes its subdomains; a specific subdomain matches only itself; web search accepts paths, web fetch matches on domain only; wildcards are allowed only in the path, so `*.example.com` is rejected with a 400 error; request-level lists must fit inside any organization-level list set in the Claude Console. The docs also warn about homograph attacks (a Cyrillic letter that looks Latin): use ASCII-only domain names.

### Data leaving your environment

With server tools, your search queries and URLs go out from Anthropic's infrastructure to the web, and web fetch's documentation notes that website publishers may retain parameters in fetched URLs. That is also an **exfiltration path**: the web fetch page warns against enabling it where the model handles untrusted input alongside sensitive data, and lists mitigations (disable it, `max_uses`, `allowed_domains`, `url_sources`). Code execution containers retain data for up to 30 days and are not eligible for zero data retention; the basic web search and web fetch versions are. Your own client tools keep data where you keep it, which is one reason internal lookups belong in user-defined tools.

### Cost

Server tools can carry per-use charges on top of tokens (web search per search; code execution by container usage, with documented exceptions; web fetch only the tokens it adds). Client tools cost only the tokens of their definitions, calls and results, plus whatever your own infrastructure costs. Rates change: see the pricing page.

## The same idea at OpenAI and Google

Both vendors draw the same line between built-in tools and function calling. Names checked in their documentation on 2026-11-23:

| Idea | Claude | OpenAI (Responses API) | Gemini API |
|---|---|---|---|
| Your own tools | User-defined tools (`name`, `description`, `input_schema`) | Function calling (`type: "function"`) | Function calling (function declarations) |
| Provider runs a web search | `web_search` server tool | `web_search` built-in tool | Google Search (`google_search`) |

## Try it yourself

An offline build in plain Python 3 (any operating system): the allowlist check you would put in front of a bash tool. It only validates; it runs nothing.

The bash tool hands the whole string to a real shell, so the check must allow known-good characters rather than forbid known-bad ones. A list of forbidden operators (`;`, `|`, `&`, `$`, backticks) looks safe and is not: `ping {-f,192.0.2.10}` contains none of them, yet bash's brace expansion turns it into `ping -f 192.0.2.10`, a flood ping. Anthropic's bash tool page makes the same point about its own example check: it is a tripwire for obvious mistakes, not an enforcement boundary.

```python
import re

# Read-only diagnostics only. Each flag maps to the pattern its value must match (None: no value).
ALLOWED = {
    "ping": {"-c": r"[1-9]|10"},      # at most 10 echo requests
    "traceroute": {"-n": None},
    "dig": {"+short": None},
}
SAFE_COMMAND = re.compile(r"[A-Za-z0-9 .:+-]{1,200}")  # no quotes, braces, globs, $, ;, |, &, newlines
SAFE_TARGET = re.compile(r"[A-Za-z0-9][A-Za-z0-9.:-]*")  # a hostname or an IP address


def check_command(command):
    """Return (ok, reason). Allowlist of characters, programs, flags and flag values."""
    if not SAFE_COMMAND.fullmatch(command):
        return False, "Use only letters, digits, spaces and . : + - in one simple command."
    parts = command.split()
    if not parts or parts[0] not in ALLOWED:
        return False, f"Only these programs are allowed: {', '.join(sorted(ALLOWED))}."
    flags, args, targets = ALLOWED[parts[0]], iter(parts[1:]), []
    for arg in args:
        if arg in flags:
            if flags[arg] is not None and not re.fullmatch(flags[arg], next(args, "")):
                return False, f"Flag {arg} needs a value matching {flags[arg]}."
        elif arg.startswith(("-", "+")):
            return False, f"Flag {arg} is not allowed for {parts[0]}."
        elif SAFE_TARGET.fullmatch(arg):
            targets.append(arg)
        else:
            return False, f"'{arg}' is not a hostname or IP address."
    if len(targets) != 1:
        return False, "Give exactly one target hostname or IP address."
    return True, "ok"


for cmd in ["ping -c 4 192.0.2.10", "dig +short sw-core-01.example.com", "ping 192.0.2.10; rm -rf /",
            "ping {-f,192.0.2.10}", "ping -c 100000 192.0.2.10", "ssh admin@192.0.2.1"]:
    print(cmd, "->", check_command(cmd))
```

Even a strict check is a second line of defence. The first is not to give the model a shell at all: a user-defined `ping_host` tool that takes `host` as a schema parameter, checks it against a pattern like `SAFE_TARGET` (so a value such as `-f` cannot become a flag) and runs `subprocess.run(["ping", "-c", "4", host], shell=False, timeout=30)` never lets a shell interpret anything.

1. Save it as `allowlist.py` and run it (`python3 allowlist.py`, or `py allowlist.py` on Windows). Read why each command passes or fails, including the brace-expansion attempt.
2. The reasons are written for the model: they would go back as `is_error` results. Improve one so it also says what to do instead.
3. Write a one-page security review for a proposed agent that has `web_fetch`, `search_tickets` and a `bash` tool on a jump host: what each can reach, what data could leave, and which two controls you would add first.

## Key takeaways

- Anthropic-schema client tools (bash, text editor, memory, computer use, browser use) have schemas Anthropic defines and trains on, but your application runs every call, with your privileges.
- The real security question is where the work runs and what it can reach: your function, your whole host, or Anthropic's infrastructure.
- For shells and desktops: isolate, run as a least-privileged user, allowlist commands, log everything, redact secrets, and confirm consequential actions.
- Fetched pages, search results, screenshots and tickets are untrusted input; citations help people verify, they do not make content trustworthy.
- Domain filters take bare domains (subdomains included), one list type per request, wildcards only in paths; set `max_uses` and consider `url_sources` for web fetch.
- OpenAI and Gemini make the same split: built-in tools (web search, code execution, computer use, file search) versus function calling.
