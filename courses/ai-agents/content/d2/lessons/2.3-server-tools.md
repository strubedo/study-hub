## Where does the tool run?

Anthropic's "How tool use works" page sorts every tool by one question: where does the code run? Its answer has three buckets.

| Bucket | Who writes the schema | Who runs it | You send a `tool_result`? | Examples |
|---|---|---|---|---|
| User-defined client tools | You | Your code | Yes | `get_interface_status`, `search_tickets` |
| Anthropic-schema client tools | Anthropic | Your code | Yes | bash, text editor, memory, computer use, browser use |
| Server tools | Anthropic | Anthropic's infrastructure | No | web search, web fetch, code execution, tool search |

Everything in topics 2.1 and 2.2 was the first bucket. This lesson covers the third; the next lesson covers the second and compares the security of all three.

## The server tools Anthropic documents today

From the "Tool reference" page, checked 2026-11-23. Server tools are declared by a dated `type` string plus a fixed `name`:

| Tool | `type` values listed | `name` | Beta header |
|---|---|---|---|
| Web search | `web_search_20260318`, `web_search_20260209`, `web_search_20250305` | `web_search` | None |
| Web fetch | `web_fetch_20260318`, `web_fetch_20260309`, `web_fetch_20260209`, `web_fetch_20250910` | `web_fetch` | None |
| Code execution | `code_execution_20260521`, `code_execution_20260120`, `code_execution_20250825` | `code_execution` | None |
| Tool search | `tool_search_tool_regex_20251119`, `tool_search_tool_bm25_20251119` | (see its page) | None |
| Advisor | `advisor_20260301` | (see its page) | `advisor-tool-2026-03-01` |
| MCP connector | `mcp_toolset` | (not date-versioned) | `mcp-client-2025-11-20` |

The MCP connector belongs to topic 2.4, and tool search and the advisor tool are beyond this lesson. Two warnings about the strings themselves:

- **They change.** The reference explains that a new dated version appears when a tool's behaviour, schema or model support changes. Some versions add a capability (the `_20260209` web tools add dynamic filtering); others are tied to a model generation. Older versions usually stay available, but the code execution page warns that older tool versions are not guaranteed to work with newer models. Copy the type string from the tool's page when you build, not from this table.
- **Several versions can be current at once.** Choose by capability and data-handling needs. For example, the basic web tools (`web_search_20250305`, `web_fetch_20250910`) are eligible for zero data retention, while the dynamic-filtering versions are not by default because they run code execution internally. Otherwise follow the tool page's recommendation.

A minimal declaration looks like any other entry in `tools`:

```json
{"type": "web_search_20250305", "name": "web_search", "max_uses": 3, "allowed_domains": ["advisories.example.com"]}
```

## What a response with server tools looks like

When a server tool runs, the response's `content` contains a `server_tool_use` block (its `id` uses the `srvtoolu_` prefix) followed by the tool's result block, such as `web_search_tool_result`, paired by `tool_use_id`. You do not send a `tool_result` for them: the API ran the tool and fed the result to the model inside the same request. A shortened example for a search, written from the documented shape:

```json
{
  "role": "assistant",
  "stop_reason": "end_turn",
  "content": [
    {"type": "text", "text": "I'll look for a published advisory."},
    {"type": "server_tool_use", "id": "srvtoolu_01X", "name": "web_search",
     "input": {"query": "Example Corp switch OS advisory CRC errors"}},
    {"type": "web_search_tool_result", "tool_use_id": "srvtoolu_01X",
     "content": [{"type": "web_search_result", "url": "https://advisories.example.com/2026-17",
                  "title": "Advisory 2026-17", "encrypted_content": "<opaque>", "page_age": "November 3, 2026"}]},
    {"type": "text", "text": "Advisory 2026-17 describes CRC errors after a duplex auto-negotiation fault.",
     "citations": [{"type": "web_search_result_location", "url": "https://advisories.example.com/2026-17",
                    "title": "Advisory 2026-17", "encrypted_index": "<opaque>", "cited_text": "..."}]}
  ],
  "usage": {"input_tokens": 5120, "output_tokens": 310, "server_tool_use": {"web_search_requests": 1}}
}
```

Points the documentation makes about this shape:

- **Citations are always on for web search.** Text that relies on a result carries `citations`. If you show the output to end users, the docs say to include citations to the original source.
- **`encrypted_content` and `encrypted_index` must go back unchanged.** To continue the conversation, send the assistant content exactly as received; a missing or modified `encrypted_content` is a 400 error. This is another reason to append assistant content verbatim.
- **Errors arrive inside a 200 response.** A failed search returns a `web_search_tool_result` whose `content` is an error object with an `error_code` such as `max_uses_exceeded` or `too_many_requests`. An empty result list is not an error. You do not send `is_error` for server tools; the model reads the error and usually tries another approach.
- **Usage counts server tool calls** under `usage.server_tool_use`, which matters for cost.

## The server-side loop and `pause_turn`

A single request can run several searches or code executions before the response comes back: the API runs its own loop. That loop has an iteration limit (the stop-reason guide gives a default of 10 per request). If the model is still working when it hits the limit, the response ends with `stop_reason: "pause_turn"`. To continue, append the response content unchanged as an `assistant` message, send the same `tools` (and the same `container` id for code execution), and add **no** new user message. A continued turn can pause again, so cap continuations like any retry.

## Mixed turns: server and client tools together

If the model calls a server tool and one of your client tools in the same turn, the API does **not** run the server tool yet. The response comes back with `stop_reason: "tool_use"`, your client `tool_use` block, and a `server_tool_use` block with no result block. There is no other marker: you detect it by the missing result. You then:

1. run your client tool,
2. append the response content unchanged as `assistant`,
3. send a user message containing **only** the `tool_result` blocks for the client calls (no text, or the request fails naming the unresolved server tool),
4. keep the same `tools` array (drop the server tool and the request fails),
5. read the next response, which starts with the server tool's result block.

The robust loop from lesson 2.2-robust-loop already does this correctly, because it sends only `tool_result` blocks and reuses `TOOLS`.

## Web search

Settings on the tool object: `max_uses` (searches per turn; failed searches count), `allowed_domains` or `blocked_domains` (one or the other, never both, or the request fails), and `user_location` to localize results. From `web_search_20260209` on, **dynamic filtering** lets the model write code that filters results before they reach its context; it runs on code execution that the API provisions automatically. Cost: web search is charged per search on top of tokens, and results count as input tokens; see the pricing page for rates.

## Web fetch

Web fetch retrieves the full text of a page or PDF the model names. Its safety rules are worth knowing exactly:

- It can fetch only URLs that **already appeared in the conversation**: in user messages, in client tool results, or in earlier search or fetch results. Not URLs that appear only in the model's own output or only in the system prompt. The optional `url_sources` setting can switch any of these sources off.
- It refuses URLs that seem to contain a credential you did not supply, and the error list includes Anthropic-side blocks on **private addresses**: it is not a way to reach your intranet.
- `max_uses` has no default limit; set one. `max_content_tokens` truncates large pages.
- Citations are optional for web fetch and off by default (`"citations": {"enabled": true}`).
- It does not render JavaScript-built pages.

Cost: no charge beyond the tokens of the fetched content (see the pricing page).

## Code execution

Code execution gives the model a sandboxed Linux container in which it runs Bash commands and creates and edits files; the result blocks are `bash_code_execution_tool_result` and `text_editor_code_execution_tool_result`. The container has **no internet access**, only pre-installed libraries, and limited CPU, memory and disk. Each request gets a new container unless you pass the earlier response's `container` id back; containers are kept for up to 30 days. Your own files reach it through the Files API. Cost: billed by container usage, with documented free allowances and an exception when newer web tool versions are in the request; see the pricing page.

> **Watch out:** If you give the model code execution **and** a client-side shell tool, it now has two computers. The docs warn that it may run commands in the wrong one or assume they share files, and suggest a system-prompt note that says which environment is for what.

## Key takeaways

- Three buckets: user-defined client tools, Anthropic-schema client tools (you run them), server tools (Anthropic runs them; no `tool_result` from you).
- Current server tools include web search, web fetch, code execution, tool search and the advisor; the MCP connector is topic 2.4. Type strings are dated and change: copy them from each tool's page.
- Responses show `server_tool_use` (id `srvtoolu_...`) plus a result block paired by `tool_use_id`; errors come back inside a 200 response; web search citations are always on.
- `pause_turn`: append the content unchanged as `assistant` and continue, with the same tools and container, no new user message.
- In a mixed turn, the server tool waits until you return only `tool_result` blocks for the client calls, with the same `tools` array.
- Web fetch reaches only URLs already in the conversation and not private addresses; code execution has no internet access. Per-use charges differ by tool: check the pricing page.
