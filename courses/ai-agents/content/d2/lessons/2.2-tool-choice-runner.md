## Two controls on top of the loop

The previous lessons let the model decide whether to call a tool and wrote the loop by hand. This lesson covers the two levers on either side of that: `tool_choice`, which constrains the model's decision on a single request, and the SDK **tool runner**, which writes the loop for you. Both are documented on Anthropic's "Define tools" and "Tool runner (SDK)" pages, checked 2026-11-23.

## `tool_choice`: four values

`tool_choice` is a request parameter, an object with a `type`:

| `tool_choice` | Effect | Default when |
|---|---|---|
| `{"type": "auto"}` | The model decides whether to call any tool, and which | `tools` are provided |
| `{"type": "any"}` | The model must call one of the provided tools, any one | Never |
| `{"type": "tool", "name": "get_runbook"}` | The model must call that tool | Never |
| `{"type": "none"}` | The model must not call any tool | No `tools` are provided |

Each object can also carry `disable_parallel_tool_use` (lesson 2.2-history-shapes): with `auto` it means at most one call; with `any` or `tool`, exactly one.

### What forcing a tool changes

When `tool_choice` is `any` or `tool`, the API makes the response **start with a tool call**. Two documented consequences:

- **No preamble.** The model will not write explanatory text before the `tool_use` block, even if you ask for it. If you want the explanation and the call, use `auto` and say in the user message which tool to use.
- **No thinking.** On models that accept forced tool use, a forced call skips thinking: the response starts with the `tool_use` block and has no `thinking` block. To let the model think first, again use `auto` with a prompt instruction.

### Where forcing is not available

Not every model and setting supports forced tool use. Where it is unsupported, `any` and `tool` fail, while `auto` and `none` still work. As documented on 2026-11-23:

- With **manual extended thinking** (`thinking: {"type": "enabled"}` with a `budget_tokens` value), `any` and `tool` are not supported and return an error. Manual extended thinking is itself deprecated and rejected by newer models, which use adaptive thinking instead.
- **Adaptive thinking** does not by itself block forced tool use; the docs name models with thinking on by default that accept it.
- Several of the newest models **reject `any` and `tool` with a 400 error regardless of thinking settings**. The documentation's suggested alternatives: `auto` with **strict tool use** when you need schema-valid inputs, or **structured outputs** (topic 2.5) when you need a response in a fixed JSON shape.

Which models are in which group changes with each release, so check the "Forcing tool use" table on the "Define tools" page before you rely on `any` or `tool`. Design so that `auto` works: good descriptions and a clear system prompt are what make the model choose the right tool, and forcing is a convenience, not a foundation.

> **Watch out:** Changing `tool_choice` between requests invalidates cached message content when you use prompt caching (tool definitions and the system prompt stay cached). Keep it stable for a whole run unless you have a reason. Domain 3 covers caching.

### When to use each value

| Situation | Choice |
|---|---|
| Normal agent turn | `auto` |
| A pipeline step that must produce one tool call (for example, classify a ticket by calling `record_category`) on a model that supports forcing | `tool` naming it, or `any` with one tool; otherwise `auto` with strict mode, or structured outputs |
| The last turn of a run: "summarize what you found, no more lookups" | `none` (keep `tools` in the request so the history with earlier tool calls stays valid) |
| You want the model to explain, then call | `auto` plus an instruction in the user message |

The `none` row is this course's suggestion for closing a run gracefully when the iteration cap is near: one last request with `tool_choice: {"type": "none"}` asks for an answer from what has already been found.

OpenAI's Responses API uses `tool_choice` values `"auto"`, `"required"`, `"none"`, a specific function `{"type": "function", "name": ...}`, and an `allowed_tools` form that restricts the model to a subset. Gemini's function calling sets `tool_choice` in `generation_config` with modes `auto`, `any`, `none` and `validated`, and can restrict to named tools with `allowed_tools`. Checked 2026-11-23.

## The SDK tool runner

The tool runner, in beta in Anthropic's SDKs (Python, TypeScript, C#, Go, Java, PHP and Ruby as of 2026-11-23), removes the hand-written loop. According to its documentation it:

- runs your tools when Claude calls them,
- handles the request and response cycle,
- manages conversation state (appends the assistant message and the tool results),
- wraps errors: an exception in a tool becomes a `tool_result` with `is_error: true` carrying the exception's message (in Python, its type and message), not its stack trace,
- stops when Claude returns a message without a tool call, or at `max_iterations` if you set it.

The Python SDK's helper notes add that the runner sends a `pause_turn` turn back unchanged so the server can resume it, and stops after yielding any other final message.

In Python, you decorate functions with `@beta_tool`; the decorator builds the JSON schema from the type hints and the docstring. Here is the Example Corp interface tool on the runner, compiled but not run:

```python
import json

from anthropic import Anthropic, beta_tool
from anthropic.lib.tools import ToolError

client = Anthropic()  # reads ANTHROPIC_API_KEY from the environment


@beta_tool
def get_interface_status(device_hostname: str, interface_name: str) -> str:
    """Read-only. Returns the live state of one interface on one Example Corp switch: admin and
    operational status, speed, duplex and error counters. Use it when a user reports a slow,
    flapping or dead port. It does not return configuration and cannot change anything.

    Args:
        device_hostname: Fully qualified inventory hostname, for example sw-access-12.example.com.
        interface_name: Full interface name, for example GigabitEthernet1/0/48. Do not abbreviate.
    """
    if not device_hostname.endswith(".example.com"):
        raise ToolError(f"'{device_hostname}' is not an inventory hostname. Use the full name.")
    return json.dumps({"device_hostname": device_hostname, "interface_name": interface_name,
                       "oper_status": "up", "duplex": "half", "crc_errors": 17990})


runner = client.beta.messages.tool_runner(
    model="claude-haiku-5-5",   # model ids change: check the models overview
    max_tokens=1024,
    max_iterations=6,           # without it, the runner loops until Claude stops calling tools
    tools=[get_interface_status],
    messages=[{"role": "user", "content": "Is GigabitEthernet1/0/48 on sw-access-12.example.com healthy?"}],
)
final_message = runner.until_done()
for block in final_message.content:
    if block.type == "text":
        print(block.text)
```

Notes from the Python SDK's `tools.md`: by default the runner keeps its conversation in a (beta) message thread on the server side; pass `thread=False` to send the whole history with every request, the way your own loop does. A tool returns a string (or content blocks), so structured data is encoded with `json.dumps`; raising `ToolError` sends an intentional error back to the model without logging it as a failure, while a plain exception is sent as text and logged; `@beta_async_tool` is the async variant. Iterating `for message in runner:` instead of `until_done()` gives you each intermediate message.

### What the runner still leaves to you

The documentation says to use the manual loop instead when you need **human-in-the-loop approval, custom logging or conditional execution**. Even when the runner fits, these stay yours:

| Still yours | Why |
|---|---|
| The tool code and its input validation | The runner calls your function with what the model sent; the TypeScript docs note the input is not validated at runtime |
| `max_iterations` | It is optional; leave it out and nothing but the model bounds the run |
| What counts as a good ending | The final message can still be `max_tokens` or `refusal`; check `stop_reason` on what `until_done()` returns |
| Least privilege and approvals | A tool the runner can call, it will call. Keep state-changing tools out, or use the manual loop with an approval step (Domain 5) |
| Persistence and audit | The runner manages state during the run; storing transcripts is yours |

You can also intervene inside the loop: in Python, `runner.generate_tool_call_response()` returns the tool results before they are sent, so you can inspect them (for example, stop on an error), and `runner.append_messages()` or `set_messages_params()` change what goes out next. Once you find yourself doing that on every iteration, the manual loop from lesson 2.2-robust-loop is usually clearer.

OpenAI's Agents SDK and Google's ADK play a similar role at a higher level (lesson 1.3-build-options). Their plain client SDKs differ (checked 2026-11-23): the OpenAI Python SDK's helpers parse and stream Responses output but run no automatic tool loop, while Google's Python SDK offers automatic function calling, Python only and documented on the legacy `generateContent` API.

## Key takeaways

- `tool_choice` types: `auto` (default with tools), `any`, `tool` with a `name`, and `none` (default without tools).
- Forcing (`any` or `tool`) makes the response start with a tool call: no preamble text and no thinking.
- Forced tool use fails with manual extended thinking and on some newer models; there, use `auto` with strict tools or structured outputs. Check the docs' table for the current list.
- The tool runner (beta) runs tools, appends messages, wraps errors as `is_error` results and stops at a non-tool message or `max_iterations`.
- With the runner you still own tool validation, `max_iterations`, checking the final `stop_reason`, least privilege and persistence; use a manual loop for approvals and custom logging.
- OpenAI's `tool_choice` adds `"required"` and `allowed_tools`; Gemini's modes are `auto`, `any`, `none` and `validated`.
