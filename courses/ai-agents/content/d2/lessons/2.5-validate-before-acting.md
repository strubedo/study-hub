## Schema-valid is not the same as safe

Lesson 2.5-structured-output showed how to get JSON that matches a schema. That guarantee covers **shape**: the right keys, the right types, a value from the enum. It says nothing about whether the device exists, whether the window is in the past, or whether the ticket asked for something your team would never let automation do. And the guarantee itself has exceptions: refusals, truncation and enum case drift.

So model output is **untrusted input**, exactly like a tool result or a web page (lessons 2.1-tool-results and 2.3-client-tools-security). The OWASP Top 10 for LLM Applications 2026 lists this as **LLM10:2026 Improper Output Handling** (LLM05 in the 2025 edition): insufficient validation, sanitization and handling of model output before it is passed downstream to other components and systems. Its examples include output run in a shell, SQL executed without parameterization and output used to build file paths, and its first mitigation is to treat the model like any other user (zero trust) and validate its responses. The vendors say the same in their structured-output guides: OpenAI's tells you to handle refusals and incomplete responses and validate any business rules the schema does not express, and Gemini's says to always validate values in your application. The rule this course applies everywhere: **never pass model output straight into a command, a query or a configuration change.** Parse it, validate it, check it against your own sources of truth, and only then let a separate, deterministic step build the action, usually for a human to approve.

## The pipeline

1. **Check the stop reason.** `end_turn` only. `max_tokens` means possibly incomplete JSON: retry with more tokens. `refusal` means the output may not match the schema: do not parse it, hand off. Anything else is unexpected.
2. **Parse.** Exactly one text block; `json.loads` it; a parse failure is a retry.
3. **Validate against the schema in code**, even though the API constrained it. It costs microseconds, catches the documented exceptions, and protects you when someone changes the request and forgets the schema.
4. **Normalize.** Lower-case enum values (the documented case-drift caveat) and hostnames.
5. **Check business rules** the schema cannot express: the device and interface exist in inventory, the window is in the future and short enough, protected ports are excluded, free text is bounded and printable, and the model did not flag missing information.
6. **Decide**: accept (queue for approval), retry once with the errors, or hand off to a human.
7. **Act through a template**, never through text. The change system builds the command from validated fields (`interface {iface}` / `shutdown`), with a dry run and human approval for anything that changes state (Domain 5).

## Worked example: a change request from a free-text ticket

Example Corp's change tickets arrive as free text. This one, made up for the example:

```text
CHG-2291 from bob: Please shut down Gi1/0/24 on sw-access-12, it's the old print-room drop
and something keeps plugging into it. Tonight's window please, 3 Dec 2026, 22:00 to 23:00 UTC. Thanks!
```

### The schema

Every field is required (fewer optional parameters, predictable order); `new_description` uses a union with `null` so it can be "not applicable"; ranges and lengths are in descriptions because the API does not support `maxLength`; `missing_information` gives the model a legitimate place to say "the ticket does not tell me", which is better than guessing.

```json
{
  "type": "object",
  "properties": {
    "ticket_id": {"type": "string", "description": "Ticket number exactly as written, for example CHG-2291."},
    "device_hostname": {"type": "string", "description": "Full inventory hostname, for example sw-access-12.example.com."},
    "interface_name": {"type": "string", "description": "Full interface name; expand abbreviations such as Gi1/0/24 to GigabitEthernet1/0/24."},
    "action": {"type": "string", "enum": ["shutdown", "no_shutdown", "set_description"]},
    "new_description": {"type": ["string", "null"], "description": "Only for set_description: at most 64 characters. Otherwise null."},
    "window_start": {"type": "string", "format": "date-time", "description": "Maintenance window start in UTC, ISO 8601."},
    "window_end": {"type": "string", "format": "date-time", "description": "Maintenance window end in UTC, ISO 8601."},
    "missing_information": {"type": "array", "items": {"type": "string"}, "description": "Anything a change needs that the ticket does not state. Empty if nothing is missing. Do not guess."}
  },
  "required": ["ticket_id", "device_hostname", "interface_name", "action", "new_description", "window_start", "window_end", "missing_information"],
  "additionalProperties": false
}
```

It goes in `output_config.format` as in the previous lesson, with a system prompt such as "Extract the change request from the ticket. Use only facts in the ticket."

### A conforming output

What a good response's text block could contain (written for this lesson, not captured):

```json
{"ticket_id": "CHG-2291", "device_hostname": "sw-access-12.example.com", "interface_name": "GigabitEthernet1/0/24", "action": "shutdown", "new_description": null, "window_start": "2026-12-03T22:00:00Z", "window_end": "2026-12-03T23:00:00Z", "missing_information": []}
```

Notice that the model expanded `sw-access-12` and `Gi1/0/24`. The schema cannot tell you whether those expansions are right; the inventory check can.

### A truncated output

The same request with `max_tokens` set far too low. The response has `"stop_reason": "max_tokens"` and the text block ends mid-value:

```text
{"ticket_id": "CHG-2291", "device_hostname": "sw-access-12.example.com", "interface_name": "GigabitEthernet1/0/24", "act
```

`json.loads` would fail on this text, so the parse step would catch it anyway. Check `stop_reason` first all the same: it tells you **why** the output is bad and what fixes it (retry with a higher `max_tokens`), where a parse error only says that something went wrong.

### The validation code

Standard library only, so you can run it offline on any operating system. It takes a response as a dict (the shape of the Messages API response, or `response.model_dump()` from the Python SDK).

```python
"""Validate a model-extracted change request before anything acts on it. Standard library only."""
import json
from dataclasses import dataclass, field
from datetime import datetime, timedelta, timezone

SCHEMA = {
    "type": "object",
    "properties": {
        "ticket_id": {"type": "string"},
        "device_hostname": {"type": "string"},
        "interface_name": {"type": "string"},
        "action": {"type": "string", "enum": ["shutdown", "no_shutdown", "set_description"]},
        "new_description": {"type": ["string", "null"]},
        "window_start": {"type": "string"},
        "window_end": {"type": "string"},
        "missing_information": {"type": "array", "items": {"type": "string"}},
    },
    "required": ["ticket_id", "device_hostname", "interface_name", "action",
                 "new_description", "window_start", "window_end", "missing_information"],
    "additionalProperties": False,
}

# Read-only snapshot of inventory (made-up). Automation may never touch PROTECTED ports.
INVENTORY = {
    "sw-access-12.example.com": {"GigabitEthernet1/0/24", "GigabitEthernet1/0/48"},
    "sw-core-01.example.com": {"TenGigabitEthernet1/1/1", "TenGigabitEthernet1/1/2"},
}
PROTECTED = {("sw-core-01.example.com", "TenGigabitEthernet1/1/1")}
MAX_WINDOW = timedelta(hours=4)
JSON_TYPES = {"string": str, "array": list, "null": type(None)}


@dataclass
class Verdict:
    status: str  # "accept" (queue for human approval), "retry" or "handoff"
    errors: list[str] = field(default_factory=list)
    request: dict | None = None


def check_schema(data: object) -> list[str]:
    """Re-check the schema in code: never assume the constraint held."""
    if not isinstance(data, dict):
        return ["top level is not a JSON object"]
    errors = [f"missing field {k}" for k in SCHEMA["required"] if k not in data]
    errors += [f"unexpected field {k}" for k in data if k not in SCHEMA["properties"]]
    for key, rule in SCHEMA["properties"].items():
        if key not in data:
            continue
        allowed = rule["type"] if isinstance(rule["type"], list) else [rule["type"]]
        if not any(isinstance(data[key], JSON_TYPES[t]) for t in allowed):
            errors.append(f"{key}: expected {' or '.join(allowed)}")
        elif "enum" in rule and data[key].lower() not in rule["enum"]:
            errors.append(f"{key}: {data[key]!r} is not an allowed value")
        elif rule["type"] == "array" and not all(isinstance(i, str) for i in data[key]):
            errors.append(f"{key}: every item must be a string")
    return errors


def parse_time(value: str) -> datetime | None:
    try:
        moment = datetime.fromisoformat(value)
    except ValueError:
        return None
    return moment if moment.tzinfo is not None else None  # refuse times without a zone


def check_rules(req: dict, now: datetime) -> list[str]:
    """Business rules the schema cannot express."""
    errors = []
    host, iface, action = req["device_hostname"], req["interface_name"], req["action"]
    if host not in INVENTORY:
        errors.append(f"device {host} is not in inventory")
    elif iface not in INVENTORY[host]:
        errors.append(f"interface {iface} not found on {host}")
    if (host, iface) in PROTECTED:
        errors.append(f"{host} {iface} is protected; a human must plan this change")
    start, end = parse_time(req["window_start"]), parse_time(req["window_end"])
    if start is None or end is None:
        errors.append("window times must be ISO 8601 with a time zone")
    elif not (now < start < end and end - start <= MAX_WINDOW):
        errors.append("window must be in the future, end after start, and last at most 4 hours")
    desc = req["new_description"]
    if action == "set_description":
        if not desc or len(desc) > 64 or not desc.isprintable():
            errors.append("new_description must be 1 to 64 printable characters")
    elif desc is not None:
        errors.append("new_description must be null unless action is set_description")
    if req["missing_information"]:
        errors.append("ticket is incomplete: " + "; ".join(req["missing_information"]))
    return errors


def validate_response(response: dict, now: datetime) -> Verdict:
    stop = response.get("stop_reason")
    if stop == "refusal":
        return Verdict("handoff", ["model refused; do not parse"])
    if stop == "max_tokens":
        return Verdict("retry", ["output truncated; retry with a higher max_tokens"])
    if stop != "end_turn":
        return Verdict("handoff", [f"unexpected stop_reason {stop!r}"])
    texts = [b["text"] for b in response.get("content", []) if b.get("type") == "text"]
    if len(texts) != 1:
        return Verdict("retry", ["expected exactly one text block"])
    try:
        data = json.loads(texts[0])
    except json.JSONDecodeError as exc:
        return Verdict("retry", [f"not valid JSON: {exc}"])
    errors = check_schema(data)
    if errors:
        return Verdict("retry", errors)
    req = {**data, "action": data["action"].lower(), "device_hostname": data["device_hostname"].strip().lower()}
    errors = check_rules(req, now)
    return Verdict("handoff", errors, req) if errors else Verdict("accept", [], req)


if __name__ == "__main__":
    NOW = datetime(2026, 12, 3, 12, 0, tzinfo=timezone.utc)
    good = ('{"ticket_id": "CHG-2291", "device_hostname": "sw-access-12.example.com", '
            '"interface_name": "GigabitEthernet1/0/24", "action": "shutdown", "new_description": null, '
            '"window_start": "2026-12-03T22:00:00Z", "window_end": "2026-12-03T23:00:00Z", "missing_information": []}')
    samples = {
        "conforming": {"stop_reason": "end_turn", "content": [{"type": "text", "text": good}]},
        "truncated": {"stop_reason": "max_tokens", "content": [{"type": "text", "text": good[:120]}]},
        "valid but unsafe": {"stop_reason": "end_turn", "content": [{"type": "text", "text": good
            .replace("sw-access-12", "sw-core-01").replace("GigabitEthernet1/0/24", "TenGigabitEthernet1/1/1")}]},
    }
    for name, response in samples.items():
        verdict = validate_response(response, NOW)
        print(f"{name}: {verdict.status} {verdict.errors}")
```

Running it prints:

```text
conforming: accept []
truncated: retry ['output truncated; retry with a higher max_tokens']
valid but unsafe: handoff ['sw-core-01.example.com TenGigabitEthernet1/1/1 is protected; a human must plan this change']
```

The third sample is the point of the lesson: it is **perfectly schema-valid**, names a real device and a real interface, and would take down a core uplink. Only the business rules catch it.

Design choices worth copying:

- **Failures are split by who can fix them.** Shape problems (bad JSON, missing field, unknown enum) go back to the model once, with the errors in the next message. Fact problems (unknown device, protected port, past window, ticket incomplete) go to a human, because a retry would invite the model to invent a different answer.
- **"Accept" does not mean "execute".** It means the request is well-formed and plausible enough to put in front of an approver, with the original ticket text alongside.
- **Free text is bounded.** `new_description` is limited to 64 printable characters, so a description cannot smuggle a newline and a second command into a template.
- **Retries are capped.** One retry, then hand off; a loop that retries forever is an outage generator.

## Key takeaways

- A schema guarantees shape, not truth or safety. Treat model output as untrusted input (OWASP LLM10:2026 Improper Output Handling).
- Order of checks: stop reason, parse, schema (again, in code), normalize, business rules, then decide.
- `max_tokens` means retry with more tokens; `refusal` means hand off without parsing; compare enums case-insensitively.
- Send shape errors back to the model once; send fact and policy failures to a human.
- Never pass model output straight into a command, query or configuration change: build actions from validated fields through a template, with approval for state changes.
