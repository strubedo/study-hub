## Why ask for a schema

A lot of agent work ends in data, not prose: a ticket classified into one of six categories, a change request pulled out of an email, a list of affected sites for a status page. Asking the model to "reply in JSON" usually works and sometimes does not. Anthropic's "Structured outputs" page lists what goes wrong without a constraint: JSON that does not parse, missing required fields, wrong types and other schema violations that need error handling and retries.

**Structured outputs** remove that class of failure. You send a JSON Schema; the API compiles it into a grammar and uses **constrained decoding**, so the model can only produce text that matches. The page describes two features built on the same machinery:

- **JSON outputs** (`output_config.format`): the model's **answer** follows your schema. This lesson.
- **Strict tool use** (`strict: true` on a tool): a **tool call's input** follows the tool's schema. Lesson 2.1-schemas-strict.

They can be used separately or together in one request. Checked 2026-11-23: the page lists structured outputs as generally available on all current models, with no beta header.

## The request

Put the schema in `output_config.format` with `type: "json_schema"`:

```json
{
  "model": "claude-haiku-5-5",
  "max_tokens": 1024,
  "messages": [{"role": "user", "content": "Classify this ticket: 'Users on floor 3 of HQ cannot get an IP address since 09:10.'"}],
  "output_config": {
    "format": {
      "type": "json_schema",
      "schema": {
        "type": "object",
        "properties": {
          "category": {"type": "string", "enum": ["dhcp", "dns", "wifi", "switching", "routing", "other"]},
          "site": {"type": "string"},
          "urgent": {"type": "boolean"},
          "summary": {"type": "string", "description": "One sentence, under 25 words."}
        },
        "required": ["category", "site", "urgent", "summary"],
        "additionalProperties": false
      }
    }
  }
}
```

The JSON arrives as the text of the response's text content block, so you still `json.loads` it. In Python the documented, recommended route is the SDK's parse helper: pass a Pydantic model as `output_format` to `client.messages.parse()`, and read the validated object from `parsed_output`. The SDK converts the model's schema, sends it as `output_config.format` and validates the response.

```python
from typing import Literal

import anthropic
from pydantic import BaseModel


class TicketClass(BaseModel):
    category: Literal["dhcp", "dns", "wifi", "switching", "routing", "other"]
    site: str
    urgent: bool
    summary: str


client = anthropic.Anthropic()  # reads ANTHROPIC_API_KEY from the environment
response = client.messages.parse(
    model="claude-haiku-5-5",
    max_tokens=1024,
    messages=[{"role": "user", "content": "Classify this ticket: 'Users on floor 3 of HQ cannot get an IP address since 09:10.'"}],
    output_format=TicketClass,
)
print(response.stop_reason, response.parsed_output)
```

Older code used a top-level `output_format` parameter with a beta header; the page says it moved to `output_config.format`, is deprecated, and returns a 400 error without the old `structured-outputs-2025-11-13` header. A Pydantic model passed to `parse()` as `output_format` still works because the SDK sends it as `output_config`.

## What the schema may contain

Structured outputs support JSON Schema with limits, and **strict tool use shares exactly the same limits** (the table in lesson 2.1-schemas-strict). In short, as listed on 2026-11-23:

- **Supported:** all basic types; `enum` and `const` of simple values; `anyOf` and `allOf` (with exceptions); `$ref`, `$defs` and `definitions`; `default`; `required`; `additionalProperties: false` (required on every object); string `format` values `date-time`, `time`, `date`, `duration`, `email`, `hostname`, `uri`, `ipv4`, `ipv6`, `uuid`; array `minItems` of 0 or 1; simple regex `pattern`.
- **Not supported (400 error):** recursive schemas; `oneOf` (use `anyOf`); `not`; `anyOf` alongside `type` or `properties` in the same object; external `$ref`; numeric constraints (`minimum`, `maximum`, `multipleOf`); string length constraints (`minLength`, `maxLength`); array constraints beyond `minItems` 0 or 1; `additionalProperties` other than `false`; complex regex (backreferences, lookaround, word boundaries).
- **Complexity limits per request**, combined across JSON output and strict tool schemas: 20 strict tools, 24 optional parameters, 16 parameters with union types (`anyOf` or a type array such as `["string", "null"]`), plus internal grammar-size limits ("Schema is too complex for compilation") and a 180-second compilation timeout.

The SDK helpers soften this: they strip unsupported constraints, append them to the field description (for example `{minimum: 100}`), add `additionalProperties: false`, filter string formats to the supported list, and (in helpers that validate responses, such as Python's `parse()`) check the response against your **original** constraints in your code. With a raw schema you do that yourself: move the range into the description and check it after parsing (lesson 2.5-validate-before-acting).

Two behaviours to plan for. **Property order**: required properties come first, then optional ones, each group in schema order; make everything required if order matters. **Objects with unknown keys** cannot be expressed (an open map comes back as `{}`); use an array of `{key, value}` items.

## When the output still does not match

The guarantee has documented exceptions. Check `stop_reason` before you trust the JSON:

| Situation | `stop_reason` | What you get | What to do |
|---|---|---|---|
| Normal completion | `end_turn` | JSON that matches the schema | Parse, then validate business rules |
| Safety refusal | `refusal` | HTTP 200, billed tokens, output that may not match the schema | Do not parse blindly; hand off or report |
| Token limit | `max_tokens` | Possibly incomplete JSON | Retry with a higher `max_tokens` |
| Enum case drift | `end_turn` | A string enum value that differs only in capitalization, with no error | Compare enum values case-insensitively; never define values that differ only in case |

The page adds that a schema property asking for the model's step-by-step reasoning can trigger a `reasoning_extraction` refusal; ask for a short explanation instead.

Other notes from the page: the first request with a new schema is slower while the grammar compiles, and compiled grammars are cached for 24 hours from last use; the API injects a short system prompt describing the format, which costs input tokens, and changing `output_config.format` invalidates the prompt cache for that conversation; JSON outputs are **incompatible with citations** (400 error) and with **message prefilling**; they work with batch processing, token counting and streaming. With extended thinking, the grammar applies only to the final answer, not to thinking or tool calls.

## Structured output or tool use?

Both produce schema-shaped JSON, so which do you want?

- **You want data back** (classify, extract, summarize into fields) and your code consumes it: use **structured outputs**. The model's answer is the data.
- **You want something to happen** or need information the model does not have (look up an interface, open a ticket): use **tools**, with `strict: true` when malformed inputs would hurt. The model asks; your code acts and returns a result.
- **Both**, in an agent that uses tools and must end with a machine-readable report: the documentation's "Using both features together" pattern, strict tools during the loop and `output_config.format` for the final answer.

You will meet an older trick in existing code: define a fake tool such as `record_ticket_fields` whose `input_schema` is the shape you want, force it with `tool_choice`, and read the `tool_use` input as your data. Prefer the native feature where it exists. The schema then governs the answer itself, so there is no pretend call to strip from the history or answer with a `tool_result`; no forced `tool_choice`, which some newer models reject (lesson 2.2-tool-choice-runner, where the documentation names structured outputs as the alternative); and the model can still use real tools in the same request. That reasoning is this course's; the vendors' own split is the same: OpenAI's guide recommends function calling when connecting the model to your systems and its structured `text.format` when structuring the reply, and Gemini's guide describes structured output as formatting the final response and function calling as taking action.

## The same idea elsewhere

Checked against each vendor's documentation on 2026-11-23:

| | Claude Messages API | OpenAI Responses API | Gemini API |
|---|---|---|---|
| Request field | `output_config.format` with `type: "json_schema"` and `schema` | `text.format` with `type: "json_schema"`, a `name`, `strict: true` and `schema` (Chat Completions uses `response_format`) | Interactions API: `response_format` with `type: "text"`, `mime_type: "application/json"` and `schema`; `generateContent`: `response_mime_type` plus `response_json_schema` |
| SDK helper (Python) | `client.messages.parse(output_format=Model)` then `parsed_output` | `client.responses.parse(text_format=Model)` | Pass `Model.model_json_schema()` and validate with Pydantic |
| Tool-input equivalent | `strict: true` on a tool | `strict: true` on a function tool | `validated` function-calling mode |
| Refusal or truncation | `stop_reason` `refusal` or `max_tokens` | Refusal: a content part with `type: "refusal"` (and a `refusal` text) in the output message, on a `completed` response. Truncation: `status: "incomplete"` with `incomplete_details.reason` `max_output_tokens` | Refusal: no field documented on the structured outputs page. Truncation: the Interactions API's `status: "incomplete"` ("e.g. hitting max_tokens") |
| Unsupported keywords | Rejected with 400 (SDK helpers move them into descriptions) | See the guide's supported-schemas list | Some (`minLength`, `maxLength`, `uniqueItems` and others) are silently stripped; `minimum` and `maximum` are supported, `minItems` and `maxItems` enforced |

Each vendor supports a different JSON Schema subset, so a schema that works for one may need changes for another.

## Key takeaways

- Structured outputs use constrained decoding: put a JSON Schema in `output_config.format` (`type: "json_schema"`); the JSON arrives in the text block. In Python, `client.messages.parse(output_format=Model)` returns `parsed_output`.
- JSON outputs and strict tool use share one grammar pipeline and the same JSON Schema limits: no numeric or string-length constraints, no `oneOf` or `not`, `additionalProperties` must be `false`, plus per-request complexity limits.
- The guarantee has exceptions: `refusal`, `max_tokens` truncation and enum case drift. Always check `stop_reason` first.
- Incompatible with citations and prefilling; required properties come first in the output.
- Use structured outputs when you want data back, tools when you want an action, and both for an agent that must end with a report. Prefer the native feature over a forced fake tool.
- OpenAI: `text.format` (Responses) or `response_format` (Chat Completions). Gemini: `response_format` (Interactions) or `response_mime_type` with `response_json_schema`.
