## The problem MCP solves

Topics 2.1 to 2.3 wired tools straight into one agent: you wrote `get_interface_status`, described it in the request, and ran it in your own loop. That works for one agent and one system. It stops scaling when Example Corp has five AI applications (a chat assistant, an IDE, two in-house agents, a ticket bot) and eight systems they should reach (NetBox, the ITSM, the monitoring stack, the config archive and so on). Built pair by pair, that is up to forty integrations, each with its own tool definitions, authentication and bugs.

The **Model Context Protocol (MCP)** turns that grid into a plug. Each system is wrapped once as an **MCP server**; each AI application gains one **MCP client** implementation; any client can then use any server. The specification describes MCP as an open protocol that standardizes how applications share context with language models and expose tools to AI systems, and names the Language Server Protocol as its inspiration: one language server works in every editor, one MCP server in every AI application.

> **Real world:** MCP does not make a system safer or smarter. It moves the integration to a standard place. A badly scoped server is just as dangerous over MCP as a badly scoped function in your own loop, and now every connected application inherits it.

## Which revision this course follows

The specification is published in dated **revisions**. On 2026-11-23 the address `modelcontextprotocol.io/specification/latest` redirects to revision **2026-07-28**, and this course follows it. That revision removed the opening handshake and protocol-level sessions and made MCP **stateless**. The specification calls 2026-07-28 and later **modern**, the handshake-based revisions (2025-11-25 and older) **legacy**, and an implementation that speaks both **dual-era**. You will meet both, so this lesson teaches both and labels each.

What you will actually see, checked 2026-11-23 against each tool's own documentation:

- The official **Python SDK v2** server (`MCPServer`) answers both eras on stdio and HTTP, and its `Client` sends a `server/discover` probe and falls back to the handshake when the server is older. The **TypeScript SDK v2** implements 2026-07-28 too.
- The **MCP Inspector** has a per-server *Protocol Era* setting whose default is `legacy`: it opens with a plain `initialize` handshake, even against a modern server, until you choose `auto` (probe, then fall back) or `modern`.
- **Claude Code** (its v2 client runtime, the default on current versions) asks each server whether it supports 2026-07-28 and uses the handshake with servers that do not.
- Servers and clients built before the revision speak only the handshake. A legacy-only client cannot talk to a modern-only server.

Revisions and tool defaults change: check the changelog and each tool's documentation before relying on any detail here.

## Hosts, clients and servers

The specification's architecture has three roles:

| Role | What the specification says it does | Example Corp example |
|---|---|---|
| **Host** | The LLM application. It creates and manages the clients, controls their permissions and lifecycle, enforces security policies, consent and user authorization decisions, and aggregates context across clients. | Claude Desktop, Claude Code, an IDE, or your own Python agent |
| **Client** | A connector inside the host. Each client talks to **exactly one** server (a 1:1 relationship), attaches the protocol version and capabilities to every request, routes messages and keeps the boundaries between servers. | The part of the host that talks to the inventory server |
| **Server** | A service that provides context and capabilities through MCP primitives. It can be a local process or a remote service, and it must respect security constraints. | `example-netinv`, a read-only inventory server |

One host, many clients, one server per client. A host connected to the inventory server and the ITSM server runs two clients.

A design principle from the specification matters for security: servers should **not** be able to read the whole conversation or "see into" other servers. The full history stays with the host, which controls anything that crosses between servers; a server receives only what a request carries.

## The message layer: JSON-RPC 2.0

Every MCP message follows **JSON-RPC 2.0**. There are three kinds:

- **Request**: `jsonrpc: "2.0"`, an `id` (string or integer, never `null`, unique among the sender's outstanding requests), a `method` and optional `params`.
- **Response**: the same `id` and either a `result` or an `error` (with an integer `code` and a `message`). In revision 2026-07-28 every `result` also carries a `resultType`: `"complete"` for an ordinary result, `"input_required"` when the server needs more input first. A client must treat a missing `resultType` from an older server as `"complete"`.
- **Notification**: a `method` with no `id`. The receiver must not reply.

Standard JSON-RPC error codes cover malformed messages (for example `-32602`, invalid parameters). A request and its response, as the specification shows them (the per-request metadata is left out for brevity, as the specification's own examples do):

```json
{"jsonrpc": "2.0", "id": 1, "method": "tools/list", "params": {}}
```

```json
{"jsonrpc": "2.0", "id": 1, "result": {"resultType": "complete", "tools": [], "ttlMs": 300000, "cacheScope": "private"}}
```

## The lifecycle: two eras

### Legacy revisions (2025-11-25 and earlier): handshake, operate, shut down

The 2025-11-25 lifecycle page defines three phases:

1. **Initialization.** The first interaction must be the client's `initialize` **request**, carrying the protocol version it supports (its latest), its `capabilities` and its `clientInfo`. The server answers with the version it will use (the same one if supported, otherwise its own latest), its own `capabilities`, its `serverInfo` and optional `instructions`. If the client cannot speak the server's version, it should disconnect. The client then sends the `notifications/initialized` **notification**. The client should send no requests but pings until the server has answered `initialize`, and the server none but pings and logging until the `initialized` notification arrives.
2. **Operation.** Normal requests such as `tools/list` and `tools/call`, limited to the capabilities both sides declared.
3. **Shutdown.** No special message: the transport closes. On stdio the client closes the server's input stream and, if needed, terminates the process.

Capabilities are the negotiation. A server that does not declare `tools` will not be asked for tools; a client that does not declare `elicitation` will not be asked for user input.

### Revision 2026-07-28: no handshake

The current revision removed `initialize` and `notifications/initialized`. Instead:

- **Every request** carries its own metadata in `params._meta`: `io.modelcontextprotocol/protocolVersion` and `io.modelcontextprotocol/clientCapabilities` are required, `io.modelcontextprotocol/clientInfo` is recommended. A request missing a required field is rejected with `-32602`.
- A server **must** implement `server/discover`, which returns its `supportedVersions`, `capabilities`, optional `instructions` and identity. Calling it is optional for a client: it is a convenient way to learn the server's versions and capabilities in one request, and the probe a client uses on stdio to tell a modern server from a legacy one (below).
- If the requested version is unsupported, the server returns an `UnsupportedProtocolVersion` error listing the versions it does support, and the client retries with one of them.
- Servers must not keep per-connection state. Anything that spans calls (a long job, an open transaction) travels as an explicit handle that the client passes on each request.

Dual-era implementations interoperate with legacy peers. On stdio a dual-era client should probe with `server/discover` first: a `DiscoverResult` or a recognized modern error means a modern server; any other error, or silence, means a legacy server, and the client falls back to `initialize`.

## What servers offer: tools, resources and prompts

The server overview gives each primitive a **controller**, the party that decides when it is used:

| Primitive | Control | What it is | Methods |
|---|---|---|---|
| **Tools** | Model-controlled | Functions the model invokes to act or fetch information | `tools/list`, `tools/call` |
| **Resources** | Application-controlled | Data, addressed by URI, that the host decides to load as context | `resources/list`, `resources/templates/list`, `resources/read` |
| **Prompts** | User-controlled | Templates the user explicitly selects, such as a slash command | `prompts/list`, `prompts/get` |

The distinction is who pulls the trigger: the model calls `get_interface_status`, the host attaches `inventory://sites`, the operator picks the `/outage-summary` prompt. The specification adds that, for safety, a human should always be able to deny tool invocations.

## What clients offer: elicitation (and two deprecated features)

Clients can offer features to servers too. In revision 2026-07-28:

- **Elicitation** is the active client feature: a server asks the user for more information through the client, in **form** mode (structured data checked against a schema; never passwords, keys or tokens) or **URL** mode (sending the user to a web page for sensitive steps that must not pass through the client).
- **Sampling** (a server asking the client's model for a completion) and **roots** (the client telling a server which directories it may work in) are **deprecated** in 2026-07-28. They still work during the deprecation window, but new implementations should not add them. The suggested replacements: call an LLM provider directly instead of sampling; pass paths as tool parameters, resource URIs or server configuration instead of roots. The server-side Logging utility is deprecated in the same revision (log to stderr on stdio, or use OpenTelemetry).

How a server asks also changed. In legacy revisions the server sent its own request (`elicitation/create`) to the client. In 2026-07-28 it **returns** an `InputRequiredResult` (`resultType: "input_required"`) listing what it needs, and the client **retries the original request** with `inputResponses` and a new JSON-RPC `id`. The specification calls this the Multi Round-Trip Requests pattern.

## Try it yourself

A paper exercise; no software needed.

1. Draw Example Corp's set-up: one host (an IDE agent) connected to an inventory server and an ITSM server. Label the host, each client and each server. How many clients are there?
2. Write the three JSON-RPC messages that open a **legacy** session (request, response, notification). Use `"protocolVersion": "2025-11-25"`, empty capabilities on the client, and `"tools": {}` on the server. Validate each with `python3 -m json.tool` (Windows: `py -m json.tool`).
3. Rewrite the first `tools/list` request for revision 2026-07-28: add a `params._meta` object with the two required keys.
4. Classify each item as tool, resource or prompt, and name its controller: the running configuration of `sw-core-01.example.com` attached by the IDE when you open a change; a "bounce interface" action; a "draft a post-incident review" template in a slash-command menu.

## Key takeaways

- MCP replaces one custom integration per application-system pair with one server per system and one client per connection.
- The host coordinates and enforces consent; each client talks to exactly one server; servers stay isolated from the conversation and from each other.
- All messages are JSON-RPC 2.0 requests, responses and notifications; 2026-07-28 results carry `resultType`.
- Legacy revisions open with `initialize`, then `notifications/initialized`, then operate, and shut down by closing the transport. Revision 2026-07-28 has no handshake: every request carries its version and capabilities in `_meta`, and `server/discover` replaces the up-front exchange.
- Today's tools mix the eras: the Python SDK v2 and Claude Code negotiate either one, while the Inspector defaults to the legacy handshake until you change its Protocol Era setting.
- Tools are model-controlled, resources application-controlled, prompts user-controlled.
- Elicitation is the current client feature; sampling and roots are deprecated in 2026-07-28. Revision numbers change: check the changelog.
