## Two standard transports

JSON-RPC says what a message looks like; a **transport** says how it travels. Revision 2026-07-28 of the MCP specification (current on 2026-11-23) defines two standard transports, and the official SDKs speak both.

### stdio: the server is a child process

In the **stdio** transport the **client launches the server as a subprocess** and talks to it over the child's standard streams:

- The server reads JSON-RPC messages from **stdin** and writes them to **stdout**.
- Each message is one line: newline-delimited, with no embedded newlines.
- The server **may** write UTF-8 text to **stderr** for logging of any kind; the client may capture, forward or ignore it and should not assume stderr means an error.
- The server **must not** write anything to stdout that is not a valid MCP message, and the client must not write anything else to the server's stdin.

That third-from-last rule is the one that breaks first-time servers. stdout **is** the wire: the specification says the server **must not** write anything to stdout that is not a valid MCP message. A `print("Loaded 12 devices")` that reaches stdout is a line the client cannot parse as JSON-RPC; what a given client then does (skip it, log an error, drop the connection) is up to the client, so the symptom varies. Log to stderr instead: Python's `logging` module writes to stderr by default. The official Python SDK documentation adds a partial safety net: while it is serving, it diverts output that is *flushed* to stdout onto stderr, but output flushed before serving starts, or a buffered `print()` drained at exit, still lands on the wire. Because of that buffering, a stray `print()` may appear to do nothing in one run and corrupt the stream in another. Do not rely on the net; never print to stdout in a stdio server.

To shut down, the client closes the server's stdin, waits, and terminates the process if it lingers; a server should exit promptly when stdin closes. Credentials for a stdio server come from its **environment** (hosts let you set `env` values), not from MCP authorization.

### Streamable HTTP: the server is a web service

In **Streamable HTTP** the server is an independent process that can serve many clients:

- It exposes **one HTTP endpoint**, the MCP endpoint (for example `https://mcp.example.com/mcp`), that accepts **POST**.
- **Every** JSON-RPC message from the client is its own POST. The `Accept` header must list both `application/json` and `text/event-stream`.
- For a request, the server answers either with a single JSON object (`Content-Type: application/json`) or with a **server-sent events (SSE)** stream scoped to that request, which can carry progress notifications before the final response. The client must handle both. An accepted notification gets `202 Accepted`.
- Every POST carries an `MCP-Protocol-Version` header matching the version in the body's `_meta`, plus `Mcp-Method` and (for `tools/call`, `resources/read`, `prompts/get`) `Mcp-Name`, so gateways can route without parsing the body.
- Security: servers **must** validate the `Origin` header (to stop DNS rebinding attacks from web pages) and answer `403` to an invalid one; a server running locally **should** bind to `127.0.0.1`, not `0.0.0.0`; and servers should authenticate every connection.

**Sessions.** Legacy revisions (2025-03-26 to 2025-11-25) let a server assign a session with an `Mcp-Session-Id` header and offered a GET endpoint for server-initiated messages. Revision 2026-07-28 **removed both**: there are no protocol-level sessions, long-lived change notifications come over a `subscriptions/listen` request's response stream, and closing a request's SSE stream cancels that request. You will still see session IDs in servers built for the legacy revisions.

**The older HTTP+SSE transport** (from revision 2024-11-05, two endpoints) was replaced by Streamable HTTP in 2025-03-26 and is formally **Deprecated** in the 2026-07-28 registry, with migration to Streamable HTTP as the path. Some hosts still connect to it for compatibility.

| | stdio | Streamable HTTP |
|---|---|---|
| Who starts the server | The client, as a subprocess | Someone else; it is already running |
| Channel | stdin and stdout, one JSON message per line | POST to one endpoint; JSON or SSE response per request |
| Logging | stderr only | Your normal server logs |
| Clients served | One | Many |
| Credentials | Environment variables | MCP authorization (OAuth) or your own scheme |
| Typical use | A tool on your own machine | A shared or hosted service |

## Authorization for remote servers

Authorization is **optional** in MCP. When it is used, the specification's framework applies to HTTP transports only; stdio servers **should not** use it and should take credentials from the environment instead. The framework is built from existing OAuth standards (OAuth 2.1 and several RFCs), so the terms are OAuth terms:

| Role | Who | Job |
|---|---|---|
| Resource server | The MCP server | Accepts requests with access tokens; publishes **Protected Resource Metadata** (RFC 9728) naming its authorization server(s) |
| OAuth client | The MCP client | Discovers the authorization server, registers, runs the authorization flow and sends the token |
| Authorization server | An identity provider (may be part of the MCP server or separate) | Interacts with the user and issues tokens |

The flow at overview level, as the 2026-07-28 authorization page draws it:

1. The client calls the MCP server without a token and receives **401 Unauthorized** with a `WWW-Authenticate` header pointing to the resource metadata (and, ideally, the `scope` the request needs).
2. The client fetches the **Protected Resource Metadata**, picks an authorization server, and fetches that server's metadata (OAuth Authorization Server Metadata, RFC 8414, or OpenID Connect Discovery; clients must support both).
3. The client obtains a **client ID**. The specification's priority order: pre-registered client information if the client has it; otherwise a **Client ID Metadata Document** (an HTTPS URL used as the client ID) if the authorization server supports it; otherwise **Dynamic Client Registration** (RFC 7591), which 2026-07-28 deprecates and keeps for backwards compatibility; and as a last resort, asking the user.
4. The client runs the authorization code flow with **PKCE**, including the **`resource` parameter** (RFC 8707) that names the MCP server, and records the expected issuer. The user signs in and approves in a browser.
5. The client validates the returned issuer (`iss`, RFC 9207) where present, exchanges the code (with the code verifier and the `resource` parameter) for an access token, and sends it on **every** request as `Authorization: Bearer <access-token>`, never in the URL.

What the server must do: validate that each token was issued **for it** (the audience check), reject anything else, and **never pass the client's token through** to an upstream API. If the MCP server calls NetBox on the user's behalf, it obtains a separate token for NetBox as its own OAuth client. Token passthrough is explicitly forbidden because it creates a confused deputy: downstream systems would trust a token that was never meant for them.

Scopes carry least privilege into the protocol: the server advertises the minimum scopes in `scopes_supported` and challenges for more (step-up) only when an operation needs them, and the client requests only what the challenge asks for. A read-only inventory server should ask for something like `inventory:read`, nothing more.

## Local and remote: what each can reach

A **local** server runs on the user's machine with the user's privileges: it can read whatever the user can read, use the user's SSH keys and reach the management network if the laptop can. The MCP security best-practices page lists the local risks: arbitrary code execution through a malicious launch command or package, data exfiltration, data loss, and DNS rebinding against a local HTTP server. A **remote** server reaches what its own host can reach, authorized per user by tokens. Hosted features such as Claude's MCP connector reach only servers exposed on HTTPS (lesson 2.4-build-server), never a stdio server on your laptop. To reach a server inside a private network, Anthropic documents **MCP tunnels** (a research preview on 2026-11-23: an outbound-only tunnel from your network), which is itself a decision about what you expose.

## Connecting a server is a trust decision

Adding an MCP server to a host gives its author three channels into your agent: the **commands** your machine runs to start it (local servers), the **text** your model reads (tool names, descriptions, annotations, results), and the **actions** its tools take. Treat each as untrusted:

- **Descriptions and results are untrusted input.** Either can carry instructions aimed at the model: the prompt injection risk of lesson 2.3-client-tools-security through a new door. Claude Code's MCP documentation tells users to verify they trust each server. Annotations are claims, not facts.
- **A server can change its tools** at any time. Re-review on change; Claude's MCP connector offers a beta option to pin a server's tool list for this reason.
- **Least privilege.** Read-only servers first; a dedicated read-only service account; only the tools you need enabled (hosts and the connector support allowlists); state-changing tools behind human confirmation.
- **Review before enabling**: the exact launch command and arguments, the package source and the tool list. The best-practices page requires one-click installers to show the full command and get explicit consent.

Domain 5 turns these into a full defence: injection handling, approvals and audit.

## Key takeaways

- stdio: the client launches the server as a subprocess; newline-delimited JSON-RPC on stdin and stdout; nothing else on stdout; logs go to stderr.
- Streamable HTTP: one endpoint, every client message a POST, each response either JSON or an SSE stream; validate `Origin`, bind locally to `127.0.0.1`, authenticate.
- Revision 2026-07-28 removed `Mcp-Session-Id` sessions and the GET stream; HTTP+SSE is deprecated in favour of Streamable HTTP.
- MCP authorization is OAuth-based and for HTTP only: the server is a resource server publishing Protected Resource Metadata; the client discovers, registers, uses PKCE and the `resource` parameter, and sends `Authorization: Bearer` on every request.
- Servers check token audience and never pass tokens through; clients request minimal scopes. stdio servers take credentials from the environment.
- Connecting a server is a trust decision: read the launch command, prefer read-only servers and least-privilege credentials, treat descriptions and results as untrusted, and re-review when tools change.
