## A tool definition is a prompt

Domain 1 showed a tool definition at overview level. This lesson treats it as what it really is: text the model reads before it decides anything. When you send `tools`, the Messages API builds a special system prompt from your tool definitions, your tool configuration and your own system prompt. The model never sees your Python function, your API client or your database. It sees a name, a description and a schema, and from those alone it decides **whether** to call the tool, **which** tool, and **with what input**.

So every weakness in a definition shows up as a behaviour problem: the wrong tool chosen, a tool never chosen, an invented argument, a call that should not have happened. Anthropic's troubleshooting page for tool use lists exactly these symptoms and, for most of them, the fix is in the definition.

## The fields, as the documentation names them

Anthropic's "Define tools" page lists the fields of a user-defined tool, and the Messages API reference says which ones the API requires (both checked 2026-11-23):

| Field | Required? | What it does |
|---|---|---|
| `name` | Yes | Must match `^[a-zA-Z0-9_-]{1,128}$`: letters, digits, underscore and hyphen, 1 to 128 characters. No spaces, dots or slashes |
| `description` | Optional in the API, essential in practice | Plain text: what the tool does, when to use it and how it behaves. The API accepts a tool without one; the model then has only the name and schema to go on |
| `input_schema` | Yes | A JSON Schema object describing the input (next lesson) |
| `input_examples` | Optional | An array of example inputs; each must be valid against `input_schema` |

The API reference also accepts an optional `type: "custom"` on a user-defined tool. You never need it; dated `type` strings belong to Anthropic-provided tools (topic 2.3).

The "Tool reference" page adds optional properties that any tool in the `tools` array can carry:

| Property | Purpose |
|---|---|
| `strict` | Grammar-constrained sampling so the input always matches the schema (next lesson) |
| `cache_control` | Sets a prompt-cache breakpoint at this definition (Domain 3) |
| `defer_loading` | Keeps the tool out of the initial prompt until the tool search tool loads it |
| `allowed_callers` | Restricts who may call the tool: `"direct"` (the model, the default) or code running in the code execution sandbox |
| `eager_input_streaming` | Fine-grained streaming of the tool input; user-defined tools only |

Two combinations are rejected: `defer_loading: true` together with `cache_control`, and a strict user-defined tool that lists a code-execution caller in `allowed_callers`. You will rarely need the last three properties when you start; know that they exist so a definition you inherit does not surprise you.

`input_examples` deserves a word. The documentation recommends descriptions first and examples for complex inputs: nested objects, optional parameters, format-sensitive strings. Each example costs input tokens (the docs estimate about 100 for a flat example, 200 for a nested one), and an example that does not validate against the schema usually gets a 400 error.

## Writing the description

Anthropic calls detailed descriptions "by far the most important factor in tool performance" and asks for at least three or four sentences per tool. Its guidance, from "Define tools" and the engineering article "Writing effective tools for agents" (September 2025), reduces to five questions every description should answer:

1. **What does it do?** One sentence, concrete. "Reads the live status of one switch interface."
2. **When should the model use it?** Name the situations. The troubleshooting page says to differentiate tools by *when* to use them, not only *what* they do.
3. **When should it not?** Point to the alternative or say what the tool cannot answer.
4. **What does it return?** Field names and units, so the model knows whether the answer it needs will be there.
5. **What do the parameters mean?** Formats, accepted values, defaults and how each one changes the result.

The article adds a useful test: write the description as you would brief a new colleague. Spell out the conventions you carry in your head (hostname formats, ticket prefixes, what "open" means in your ticket system) and use unambiguous parameter names, `device_hostname` rather than `dev`, `ticket_id` rather than `id`.

One documented trap: if a parameter asks the model for its "step-by-step reasoning", the request can end in a `reasoning_extraction` refusal. Ask for a short explanation or the supporting evidence instead.

## Names and granularity

Two pieces of published guidance pull in the same direction:

- **Fewer, well-scoped tools.** "Define tools" recommends consolidating related operations rather than creating a tool for every action, because fewer tools reduce selection ambiguity. The engineering article warns against tools that merely wrap every API endpoint, and suggests tools shaped like the task: `search_logs` that returns relevant lines instead of `read_logs` that returns everything.
- **Namespacing.** When tools span services, prefix the name with the service, for example `netbox_get_device` and `itsm_search_tickets`. This matters more as you add MCP servers (topic 2.4), where tools from different authors share one list.

Consolidation has a limit that is this course's own advice: do not merge tools with **different risk levels**. A read-only `get_interface_status` and an `interface_action` that can shut a port must stay separate, so the read-only one can be offered freely while the other sits behind an approval gate (Domain 5).

## Worked example: three read-only network tools, first drafts

Example Corp's NOC wants an agent that diagnoses port and connectivity complaints. It needs three read-only tools: live interface state, the ticket history and the team's runbooks. Here are realistic first drafts, the kind written in five minutes from existing script names:

```json
[
  {"name": "intf", "description": "Gets interface info.",
   "input_schema": {"type": "object", "properties": {"dev": {"type": "string"}, "int": {"type": "string"}}}},
  {"name": "tickets", "description": "Search the ticket system.",
   "input_schema": {"type": "object", "properties": {"q": {"type": "string"}}}},
  {"name": "get_doc", "description": "Returns a document from the docs share.",
   "input_schema": {"type": "object", "properties": {"path": {"type": "string"}}}}
]
```

What the model is missing:

- `intf`: Which device names are valid? Short or full interface names? Does it return configuration, counters, neighbours? Is it safe to call?
- `tickets`: Searches what fields? Which ticket types? How many results? What is in a result?
- `get_doc`: The model must guess file paths, which invites made-up paths and, worse, paths you never meant to expose.

## Improved names and descriptions

```json
[
  {
    "name": "get_interface_status",
    "description": "Read-only. Returns the live state of ONE interface on ONE Example Corp switch or router: admin status, operational status, speed, duplex, input and output error counters, CRC errors and the time of the last state change. Use it when a user reports a slow, flapping or dead port, or to confirm whether a link is up. It does not return configuration, VLAN membership or neighbour information, and it cannot change anything. Call it once per interface; for several interfaces, make several calls in the same turn.",
    "input_schema": {"type": "object", "properties": {}}
  },
  {
    "name": "search_tickets",
    "description": "Read-only. Searches Example Corp incident and change tickets by keywords in the title and device fields and returns at most 'limit' matches, newest first. Each match has ticket_id (INC-nnnn or CHG-nnnn), title, status, opened_at and device. Use it before diagnosing a problem to find related incidents or recent changes on the same device or site. It does not return the full ticket body or comments; quote the ticket_id to the user instead.",
    "input_schema": {"type": "object", "properties": {}}
  },
  {
    "name": "get_runbook",
    "description": "Read-only. Returns one approved NOC runbook by its runbook_id: title, ordered steps, the commands each step uses and the last review date. Use it after you have identified the likely fault, to follow the approved procedure and cite it. Only the runbooks listed in the runbook_id enum exist; if none fits, say so instead of guessing. Runbook steps that change device configuration are for a human engineer to perform; describe them, never claim to have run them.",
    "input_schema": {"type": "object", "properties": {}}
  }
]
```

(The schemas are left empty here on purpose; the next lesson fills them in.) What changed, and why:

- **Names** now say the verb and the object: `get_interface_status`, `search_tickets`, `get_runbook`. A model scanning the list can tell them apart without reading every description.
- **"Read-only." first.** It tells the model the call is safe to make while investigating, and it reminds future maintainers what the tool is allowed to be.
- **When to use** is explicit and different for each tool: a symptom on a port, history before diagnosis, procedure after diagnosis. That separation is what prevents `search_tickets` being called when the user wants a runbook.
- **What it returns** lists fields, including identifiers the model can reuse (`ticket_id`, `runbook_id`).
- **Limits** are stated: no configuration, no ticket body, only known runbooks. The model learns what to do when the tool cannot help.
- **`get_doc` with a free-form path became `get_runbook` with an identifier** that will be an enum. That is better for accuracy and is also least privilege: the tool can only return documents you chose to expose.

## Try it yourself

A paper exercise; no API calls.

1. Take three scripts or API calls you already use at work (for example a DHCP lease lookup, a syslog search and a CMDB query). Write a first-draft definition for each in five minutes.
2. Rewrite each description so it answers the five questions above. Aim for three to six sentences.
3. Check every name against `^[a-zA-Z0-9_-]{1,128}$`. In Python: `import re; re.fullmatch(r"[a-zA-Z0-9_-]{1,128}", name)`.
4. Swap your descriptions with a colleague (or reread them tomorrow) and ask: for each likely user question, is it obvious which tool fits, and is it obvious when none does?
5. If any tool can change something, split it from the read-only ones and write down who must approve it before it runs.

## Key takeaways

- The model sees only `name`, `description` and `input_schema` (plus optional `input_examples`); your implementation is invisible to it. The API requires only `name` and `input_schema`, but a tool without a good `description` is a tool the model will misuse.
- Names must match `^[a-zA-Z0-9_-]{1,128}$`; make them verb plus object and namespace them by service when tools come from several systems.
- Descriptions are the biggest lever: say what the tool does, when to use it, when not to, what it returns and what each parameter means, in at least three or four sentences.
- Optional properties include `strict`, `cache_control`, `defer_loading`, `allowed_callers` and `eager_input_streaming`; check the tool reference for the current list.
- Prefer a few well-scoped, task-shaped tools over many overlapping endpoint wrappers, but never merge read-only and state-changing actions.
- Replace free-form paths and names with identifiers or enums where you can: it improves accuracy and limits what the tool can reach.
