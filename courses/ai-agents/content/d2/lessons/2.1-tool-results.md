## The result is the model's only view of the world

When your tool runs, its return value goes back to the model in a `tool_result` block, and that block is all the model learns about what happened. A result that is too long buries the one fact that matters; a result with cryptic codes leads to guesses; an error that says only "failed" leads to the same call again. Designing results is the half of tool design that people skip, and it is where many agent failures start.

## What a result can contain

Anthropic's "Handle tool calls" page defines the block: `type: "tool_result"`, the `tool_use_id` it answers, an optional `content`, and an optional `is_error`. `content` is either a string or a list of content blocks of type `text`, `image`, `document` or `search_result`. An empty result (no `content`) is valid, for a tool whose only output is "done".

Most tools return text. If your data is structured, serialize it (for example with `json.dumps`); the SDK tool runner documentation says the same, since a returned string becomes a single text block.

## Five rules for results

These rest on Anthropic's "Define tools" best practices and its engineering article "Writing effective tools for agents"; the network examples are this course's own.

1. **Return only high-signal fields.** "Define tools" says to include only the fields the model needs for its next step. The article adds that low-level technical fields (internal UUIDs, MIME types, image URLs at a given size) rarely help, while names and types do.
2. **Use identifiers the model can reuse.** Return stable, meaningful identifiers (`INC-4471`, `sw-access-12.example.com`, `interface-errors`) rather than opaque internal references. The article reports that resolving arbitrary IDs to meaningful names, or even a simple index, noticeably improved precision. If a later tool call needs a technical id, return it too, or offer a `response_format` choice of concise and detailed, as the article suggests.
3. **Bound the size, and say so.** Use pagination, filtering, range selection or truncation with sensible defaults. When you truncate, tell the model how to get the rest ("37 matches; 5 returned. Narrow the query or request page 2."). The article notes that Claude Code limits tool responses to 25,000 tokens by default; pick a limit for your own tools.
4. **Pick a format and test it.** The article found that JSON, Markdown or XML can each work better depending on task and model; there is no universal winner. Keep one format per tool so the model learns it.
5. **Make errors instructive.** Say what went wrong and what to try next, set `is_error: true`, and never return a stack trace. Anthropic's example of a good error is "Rate limit exceeded. Retry after 60 seconds." rather than "failed".

## Errors are results, not exceptions

When a client tool fails, your code should not crash the loop and should not send a fake success. Send a `tool_result` with `is_error: true` and a message the model can act on. The documentation describes the two common cases:

- **Execution errors** (the device timed out, the ticket API returned HTTP 500): return the error and let the model decide whether to retry, try something else, or tell the user.
- **Invalid calls** (a required parameter missing, an unknown hostname): return what was wrong. During development, the docs suggest treating frequent invalid calls as a sign the description needs work; strict mode removes the schema-level ones.

Because the model may call the tool again after an error, your loop needs a retry limit (lesson 2.2). A good error message makes the second attempt the right one:

| Situation | Weak result | Instructive result |
|---|---|---|
| Typo in hostname | `Error 404` | `No device 'sw-acces-12.example.com' in inventory. Closest match: sw-access-12.example.com. Use the full hostname.` |
| Abbreviated interface | `Invalid input` | `Interface 'Gi1/0/48' not found. Use the full name, for example GigabitEthernet1/0/48.` |
| Device unreachable | `Traceback (most recent call last): ...` | `sw-dist-02.example.com did not answer within 10 s. It may be down. Do not retry more than once; check search_tickets for an open outage.` |
| Not permitted | `403` | `This tool can only read access switches. Core routers are out of scope; tell the user to ask the network team.` |

The last row matters for safety: the message tells the model not to look for another way in, and to hand the question back to a person.

> **Watch out:** Tool results often carry text you do not control: ticket bodies, syslog lines, web pages. An attacker who can write a ticket can write instructions into it. Anthropic's documentation recommends keeping such content inside `tool_result` blocks, never copying it into the system prompt or a plain user `text` block. Domain 5 covers the defences in depth.

## Worked example, continued: the results

**Interface status, first draft:** the tool ran `show interfaces` and returned all 60 lines of CLI output for the port, plus a `request_uuid` and the collector's internal `poll_id`. The model can parse that, but most of it is noise, and the two internal ids invite the model to quote them to the user.

**Improved:**

```json
{
  "device_hostname": "sw-access-12.example.com",
  "interface_name": "GigabitEthernet1/0/48",
  "admin_status": "up",
  "oper_status": "up",
  "speed_mbps": 1000,
  "duplex": "half",
  "input_errors": 18342,
  "crc_errors": 17990,
  "last_state_change": "2026-11-23T08:52:10Z",
  "collected_at": "2026-11-23T09:15:02Z"
}
```

Changes: named fields with units in the key (`speed_mbps`), the identifiers the model will reuse echoed back, timestamps so the model can reason about recency, and nothing internal.

**Ticket search, improved, showing a bounded result:**

```json
{
  "query": "sw-access-12",
  "total_matches": 37,
  "returned": 2,
  "tickets": [
    {"ticket_id": "INC-4471", "title": "Building B users cannot reach HR portal", "status": "open", "opened_at": "2026-11-23", "device": "sw-access-12.example.com"},
    {"ticket_id": "CHG-1182", "title": "Replace uplink optics on sw-access-12", "status": "closed", "opened_at": "2026-11-21", "device": "sw-access-12.example.com"}
  ],
  "note": "Showing the 2 newest of 37 matches (limit 2). Add keywords or a date window to narrow the search."
}
```

The model now knows that more exists, how to get closer to it, and which ids to cite. The change ticket two days before the incident is exactly the kind of lead an engineer wants surfaced.

**Runbook, improved:** return `runbook_id`, `title`, `last_reviewed` and the steps as a numbered list, each marked `read-only` or `change (engineer only)`. That marking lets the agent recommend the change steps without pretending to run them.

## Implementing it: a stub with real error handling

This pure-Python stub runs offline on Windows, macOS and Linux with no SDK. It raises a dedicated exception with a message written for the model; the loop in lesson 2.2 turns that into an `is_error` result. It was run locally while writing this course.

```python
import json

MAX_LIMIT = 20
TICKETS = [
    {"ticket_id": "CHG-1182", "title": "Replace uplink optics on sw-access-12", "status": "closed",
     "opened_at": "2026-11-21", "device": "sw-access-12.example.com", "type": "change"},
    {"ticket_id": "INC-4471", "title": "Building B users cannot reach HR portal", "status": "open",
     "opened_at": "2026-11-23", "device": "sw-access-12.example.com", "type": "incident"},
    {"ticket_id": "INC-4398", "title": "DHCP scope full on vlan 210", "status": "closed",
     "opened_at": "2026-11-02", "device": "rtr-branch-03.example.com", "type": "incident"},
]


class ToolInputError(Exception):
    """Raised with a message written for the model, not for a developer."""


def search_tickets(query, ticket_type, status, limit, opened=None):
    words = query.lower().split()
    if not words:
        raise ToolInputError("query is empty. Send one or more keywords, such as a hostname or 'DHCP'.")
    limit = max(1, min(int(limit), MAX_LIMIT))  # strict schemas cannot express the range
    matches = [
        t for t in TICKETS
        if all(w in (t["title"] + " " + t["device"]).lower() for w in words)
        and ticket_type in ("any", t["type"])
        and status in ("any", t["status"])
        and (opened is None or opened["after"] <= t["opened_at"] <= opened["before"])
    ]
    matches.sort(key=lambda t: t["opened_at"], reverse=True)
    page = [{k: v for k, v in t.items() if k != "type"} for t in matches[:limit]]
    result = {"query": query, "total_matches": len(matches), "returned": len(page), "tickets": page}
    if len(matches) > len(page):
        result["note"] = f"Showing the {len(page)} newest of {len(matches)} matches. Narrow the query."
    elif not matches:
        result["note"] = "No matches. Try fewer keywords or ticket_type 'any'."
    return result


if __name__ == "__main__":
    print(json.dumps(search_tickets("sw-access-12", "any", "any", 1), indent=2))
    try:
        search_tickets("   ", "any", "any", 5)
    except ToolInputError as exc:
        print("is_error result:", exc)
```

Notice that "no matches" is **not** an error: the search worked and found nothing, and the note suggests a next step. Reserve `is_error` for calls that failed or were invalid.

## The same idea at OpenAI and Google

OpenAI returns a `function_call_output` item with `call_id` and `output`; its function-calling guide says the output is typically a string whose format (JSON, error codes, plain text) is up to you, so put an error clearly in that text. Gemini's Interactions API takes a `function_result` with `call_id`, `name` and `result`, and its API reference lists an optional `is_error` boolean, the same idea as Claude's flag. ## Key takeaways

- `tool_result` carries `tool_use_id`, optional `content` (string or `text`, `image`, `document`, `search_result` blocks) and optional `is_error`.
- Return only what the next step needs, with stable identifiers the model can reuse and units in the field names.
- Bound every potentially large result with pagination, filters or truncation, and tell the model how to get more.
- Report failures as results with `is_error: true` and a message that says what went wrong and what to try next; no stack traces, no internal ids.
- An empty search is a successful result, not an error.
- Tool results can carry attacker-written text; keep them in `tool_result` blocks and treat them as data, not instructions.
