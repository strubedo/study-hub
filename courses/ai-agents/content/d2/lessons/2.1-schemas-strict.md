## The schema is a contract for the input

`input_schema` is a JSON Schema object that describes what the model must send. It does two jobs at once: it tells the model what to produce (the schema is part of the prompt the model reads), and it tells your code what to expect. Anthropic's examples use a small, practical part of JSON Schema:

| Keyword | Use it for | Network example |
|---|---|---|
| `"type": "object"` with `properties` | The top level of every tool input | `{device_hostname, interface_name}` |
| `type` on each property | `string`, `integer`, `number`, `boolean`, `array`, `object`, `null` | `limit` is an `integer`, not a string |
| `description` on each property | Format, meaning and defaults of that one field | "Full interface name, not abbreviated" |
| `required` | Fields the model must always send | Hostname and interface |
| `enum` | A closed list of allowed values | `["open", "closed", "any"]` |
| `format` | Well-known string formats | `date`, `ipv4`, `hostname` |
| Nested `object` / `array` | Grouped or repeated values | A date range with `after` and `before` |
| `additionalProperties: false` | Reject keys you did not define | Stops an invented `site` argument |

Property descriptions matter as much as the tool description. A property called `interface_name` with no description leaves the model to guess between `Gi1/0/48`, `GigabitEthernet1/0/48` and `1/0/48`; one sentence ends the guessing.

## What `strict: true` adds

Without strict mode, the model's input usually matches your schema, but not always. Anthropic's "Strict tool use" page gives two failure cases, wrong types (`"2"` instead of `2`) and missing required fields, and its troubleshooting page adds a third: parameters that do not exist in the schema. Setting `"strict": true` on a tool definition, alongside `name`, `description` and `input_schema`, switches on **grammar-constrained sampling**: the model's token choices are restricted so that the `input` in the `tool_use` block always follows the schema, and the tool `name` is always one you provided.

What strict mode does **not** do:

- It does not make values **correct**. A strict schema guarantees a string in `device_hostname`, not a hostname that exists. Your tool still validates and returns a useful error.
- It does not make values **safe**. Input from the model is untrusted; a well-formed request can still ask for something it should not have (Domain 5).
- It does not fully guarantee **enum capitalization**. The structured outputs page warns that a string `enum` value can come back differing only in case, typically the first letter after a space, with no error. Compare enum values case-insensitively and never define two values that differ only in case.
- It cannot rescue a truncated call. If the response stops on `max_tokens` part-way through a `tool_use` block, the input is incomplete regardless of strict mode (lesson 2.2).

## Strict mode supports a subset of JSON Schema

Strict tool use compiles your schema into a grammar with the same pipeline as structured outputs (topic 2.5), so it shares their limits. As documented on 2026-11-23:

| Supported | Not supported (400 error) |
|---|---|
| All basic types; `enum` and `const` of simple values | Recursive schemas |
| `anyOf`, `allOf` (with exceptions); `$ref`, `$defs` | `oneOf` (use `anyOf`), `not` |
| `required`; `additionalProperties` set to `false` | `additionalProperties` set to anything but `false` |
| String `format`: `date-time`, `time`, `date`, `duration`, `email`, `hostname`, `uri`, `ipv4`, `ipv6`, `uuid` | Numeric constraints: `minimum`, `maximum`, `multipleOf` |
| Array `minItems` of 0 or 1 only | String length constraints: `minLength`, `maxLength` |
| Simple regex `pattern` | Backreferences, lookahead and lookbehind, word boundaries in `pattern` |

There are also explicit complexity limits per request: at most **20 strict tools**, **24 optional parameters** across all strict schemas, and **16 parameters using union types** (`anyOf` or a type array). Past those, or past internal grammar-size limits, the API returns a 400 error such as "Schema is too complex for compilation". The documentation's advice, in order: mark only the tools where schema violations hurt as strict, make parameters required where a sensible default exists, flatten nesting, and split tools across requests or subagents.

Two practical consequences for network tools:

- **Ranges move into the description and your code.** You cannot write `"minimum": 1, "maximum": 20` on a strict `limit`. Say "1 to 20" in the description and clamp the value in the tool.
- **Every object needs `additionalProperties: false`**, nested ones included, and an object can only return the keys you list. If you do not know the keys in advance, the docs suggest an array of `{key, value}` items instead of an open map.

Compiled grammars are cached for 24 hours from last use, so the first request with a new schema is slower than the rest.

> **Real world:** Turning on strict mode can expose schemas that relied on unsupported keywords and were silently tolerated before. Run each tool once in a test request after you add `strict: true`, before you ship.

## Worked example, continued: the three schemas

Lesson 2.1-define-tools gave the three Example Corp tools better names and descriptions. Here are their schemas. First draft of the interface tool:

```json
{"type": "object", "properties": {"dev": {"type": "string"}, "int": {"type": "string"}}}
```

Improved, with `strict: true` set on the tool:

```json
{
  "type": "object",
  "properties": {
    "device_hostname": {"type": "string", "description": "Fully qualified hostname from the Example Corp inventory, for example sw-access-12.example.com. Not an IP address."},
    "interface_name": {"type": "string", "description": "Full interface name as the device prints it, for example GigabitEthernet1/0/48. Do not abbreviate."}
  },
  "required": ["device_hostname", "interface_name"],
  "additionalProperties": false
}
```

Changes: unambiguous parameter names (the engineering article's `user` versus `user_id` point), a description with an example on each property, both fields required because the tool cannot work without them, and no extra keys.

The ticket search, improved:

```json
{
  "type": "object",
  "properties": {
    "query": {"type": "string", "description": "Keywords matched against ticket title and device fields, for example 'sw-access-12 GigabitEthernet1/0/48' or 'building B DHCP'."},
    "ticket_type": {"type": "string", "enum": ["incident", "change", "any"], "description": "incident for faults, change for planned work, any for both."},
    "status": {"type": "string", "enum": ["open", "closed", "any"], "description": "Ticket state to match. Use any when looking for history."},
    "limit": {"type": "integer", "description": "Maximum matches to return, 1 to 20. Use 5 unless the user asks for more."},
    "opened": {
      "type": "object",
      "description": "Optional date window on the ticket's open date. Omit it to search all dates.",
      "properties": {
        "after": {"type": "string", "format": "date", "description": "First day to include, YYYY-MM-DD."},
        "before": {"type": "string", "format": "date", "description": "Last day to include, YYYY-MM-DD."}
      },
      "required": ["after", "before"],
      "additionalProperties": false
    }
  },
  "required": ["query", "ticket_type", "status", "limit"],
  "additionalProperties": false
}
```

Changes: `q` became `query` with examples; ticket type and status are **enums**, so the model cannot invent a status your system does not have; `limit` is required with its range in the description (strict mode has no `maximum`, so the tool clamps it); the nested `opened` object shows how to group related values, and it carries its own `required` and `additionalProperties: false`. Making `ticket_type`, `status` and `limit` required follows the documentation's advice to reduce optional parameters: the model states the default explicitly instead of leaving it out. Only `opened` remains optional.

The runbook tool, improved:

```json
{
  "type": "object",
  "properties": {
    "runbook_id": {"type": "string", "enum": ["interface-errors", "interface-flapping", "dhcp-scope-exhaustion", "vpn-tunnel-down", "bgp-neighbor-down"], "description": "Identifier of the approved runbook. Choose the one that matches the diagnosed fault."}
  },
  "required": ["runbook_id"],
  "additionalProperties": false
}
```

The free-form `path` is gone. An enum of five identifiers means the model can only ask for documents you chose to publish, and a strict schema means a call for anything else cannot even be generated. The enum lives in the schema, so remember to update it when a runbook is added.

## The same idea at OpenAI and Google

OpenAI function tools also take `strict: true`; OpenAI's function-calling guide recommends always enabling it, and the Responses API tries to normalize a schema into strict mode when you omit the flag. Gemini's function calling has a `validated` mode in `tool_choice` that the docs describe as ensuring function schema adherence. Each vendor supports its own JSON Schema subset, so a schema that compiles for one may need changes for another. Checked 2026-11-23.

## Try it yourself

An offline check you can run with plain Python 3 on any operating system (no SDK, no API key). It walks a schema and flags things strict mode rejects.

```python
import json
import sys

UNSUPPORTED = {"minimum", "maximum", "multipleOf", "minLength", "maxLength", "oneOf", "not"}


def check(node, path="$"):
    problems = []
    if isinstance(node, dict):
        for key in UNSUPPORTED & node.keys():
            problems.append(f"{path}: '{key}' is not supported in strict mode")
        if node.get("type") == "object" and node.get("additionalProperties") is not False:
            problems.append(f"{path}: object needs additionalProperties: false")
        for key, value in node.items():
            problems.extend(check(value, f"{path}.{key}"))
    elif isinstance(node, list):
        for i, item in enumerate(node):
            problems.extend(check(item, f"{path}[{i}]"))
    return problems


if __name__ == "__main__":
    with open(sys.argv[1], encoding="utf-8") as f:
        schema = json.load(f)
    issues = check(schema)
    print("\n".join(issues) if issues else "No strict-mode problems found by this check.")
```

1. Save it as `strict_check.py` and save the ticket-search schema above as `tickets.json`.
2. Run `python3 strict_check.py tickets.json` (Windows: `py strict_check.py tickets.json`). It should report nothing.
3. Add `"minimum": 1` to `limit` and remove `additionalProperties` from `opened`. Run it again and read the two warnings.
4. This is a teaching check, not the API's validator: it does not count optional parameters or test regex patterns. List what else you would add.

## Key takeaways

- Use `type`, `required`, `enum`, `format`, a `description` on every property, nested objects where values belong together, and `additionalProperties: false`.
- `strict: true` constrains sampling so tool input always matches the schema and the tool name is always valid; it does not make values correct, safe or reliably capitalized.
- Strict mode supports a subset of JSON Schema: no `minimum`/`maximum`, no length constraints, no `oneOf`, `additionalProperties` only `false`; put ranges in the description and enforce them in code.
- Requests have complexity limits (20 strict tools, 24 optional parameters, 16 union-type parameters as of 2026-11-23); mark only the tools that need it as strict.
- Replace free-form strings with enums when the set of valid values is known: better accuracy and a smaller attack surface.
- OpenAI uses `strict: true` on function tools; Gemini has a `validated` function-calling mode.
