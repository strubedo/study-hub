## Why FortiAnalyzer

Local logs are limited by disk size, disappear when a unit is replaced, and cannot be correlated across devices. **FortiAnalyzer** (FAZ) is Fortinet's central log, analytics and reporting platform. It stores logs from many FortiGates, indexes them for fast search, runs FortiView and reports, raises alerts through event handlers, and feeds the Security Fabric (for example indicators of compromise and SOC automation).

| Term | Meaning |
|---|---|
| **ADOM** | Administrative domain on FortiAnalyzer: a container of devices, with its own storage quota, retention and admins. Devices are added to an ADOM when they are authorised. |
| **OFTP** | Fortinet's protocol between FortiGate and FortiAnalyzer, carried over **TCP 514**. It handles registration, status and file exchange, and the log stream when `reliable` is enabled (otherwise the log data itself is sent over UDP 514). |
| **Analytics vs Archive** | FortiAnalyzer keeps recent logs in its database (**analytics**, indexed and fast to query) and compressed raw logs (**archive**) for longer retention. Each ADOM's data policy sets how many days of each to keep. |
| **Device Manager** | The FortiAnalyzer page listing registered and unauthorised devices. |

## Registering a FortiGate on FortiAnalyzer

Registration is a two-sided handshake: the FortiGate must be configured to send to the FortiAnalyzer, and the FortiAnalyzer must **authorise** the FortiGate. Until the device is authorised, FortiAnalyzer does not store its logs.

### Method 1: start from the FortiGate (most common)

1. On the FortiGate, go to **Security Fabric > Fabric Connectors > FortiAnalyzer Logging** (or configure it from the CLI), enable it, enter the FortiAnalyzer IP and choose the upload option.
2. The FortiGate displays the FortiAnalyzer's certificate and serial number; verify and accept it.
3. On the FortiAnalyzer, the FortiGate appears in **Device Manager** as **Unauthorized**. Select it, click *Authorize*, choose the ADOM and give it a name.
4. Back on the FortiGate, the connector shows as connected and **Test Connectivity** reports the device as registered.

```text
FGT-HQ # config log fortianalyzer setting
FGT-HQ (setting) # set status enable
FGT-HQ (setting) # set server "10.0.20.15"
FGT-HQ (setting) # set upload-option realtime
FGT-HQ (setting) # set reliable enable
FGT-HQ (setting) # end
```

| Setting | Notes |
|---|---|
| `server` | FortiAnalyzer IP or FQDN. |
| `upload-option` | `realtime`, `1-minute`, `5-minute` (default), or `store-and-upload` (log to the local disk and upload on a schedule; needs a disk). |
| `reliable` | Default `disable`. Disabled, log data is sent in small UDP 514 datagrams; enabled, logs travel over the TCP 514 OFTP connection (larger buffers, compression, encryption with `enc-algorithm`). TCP 514 must be open either way. |
| `source-ip` | Source address for the connection; needed, for example, when logs cross an IPsec tunnel whose selectors include only certain subnets. |
| `certificate-verification` / `serial` | Verify the FortiAnalyzer's identity by its certificate; the serial number is filled in when you accept it. |

`config log fortianalyzer filter` controls severity and which log types are sent. Up to three FortiAnalyzers can be configured independently (`fortianalyzer2`, `fortianalyzer3`).

### Method 2: start from the FortiAnalyzer

In Device Manager, use **Add Device** and enter the FortiGate's serial number (and optionally its IP). The device is then pre-authorised in the chosen ADOM; when the FortiGate is pointed at the FortiAnalyzer, it is accepted without the manual authorise step. This suits zero-touch deployments where you know the serial numbers before the hardware arrives.

### Method 3: through the Security Fabric

When the Fabric root FortiGate is configured with a FortiAnalyzer, downstream FortiGates that join the Fabric inherit the FortiAnalyzer settings automatically and appear on the FortiAnalyzer for authorisation. FortiAnalyzer is a requirement for a Security Fabric (FortiAnalyzer or FortiAnalyzer Cloud / FortiGate Cloud logging).

### Verifying the connection

```text
FGT-HQ # execute log fortianalyzer test-connectivity
FortiAnalyzer Host Name: FAZ-HQ
FortiAnalyzer Adom Name: Branches
FortiGate Device ID: FGVM02TM26000101
Registration: registered
Connection: allow
Adom Disk Space (Used/Allocated): 3311845376B/53687091200B
Analytics Usage (Used/Allocated): 2451718144B/37580963840B
Analytics Usage (Data Policy Days Actual/Configured): 21/60 Days
Archive Usage (Used/Allocated): 860127232B/16106127360B
Archive Usage (Data Policy Days Actual/Configured): 21/365 Days
Log: Tx & Rx
IPS Packet Log: Tx & Rx
Content Archive: Tx & Rx
Quarantine: Tx & Rx
```

`Registration: registered` and `Connection: allow` mean the device is authorised and logs are accepted. Common failure states:

| Symptom | Likely cause |
|---|---|
| `Registration: unregistered` | The FortiGate has not been authorised yet on FortiAnalyzer (still in *Unauthorized* devices). |
| `Connection: deny` | Device not authorised, or FortiAnalyzer refusing logs because the ADOM disk quota is full. |
| `Failed to get FAZ's status. No response from server.` | Routing or firewall issue between the two; check TCP 514 with `execute telnet 10.0.20.15 514` and a sniffer. |
| `Failed to get FAZ's status. Authentication Failed.` | Not registered, or a certificate/serial mismatch. |
| `Log: Tx & Rx (log not received)` | The control channel works but logs are not arriving; check the log filters, `source-ip`, MTU on the path, and that the management VDOM can reach the FortiAnalyzer. |

> **Exam tip:** FortiAnalyzer should run the **same or a newer** firmware version than the FortiGates that log to it. A FortiAnalyzer older than its FortiGates may not parse new log fields correctly.

> **Watch out:** In an HA cluster, log traffic normally follows the cluster's data interfaces and routing table. If you want each member to log through its own reserved management interface, enable `ha-direct` in `config system ha` (see the FGCP lessons).

## Viewing logs on FortiAnalyzer

Once logs arrive:

* **Log View** shows logs per device or device group, with the same categories as the FortiGate (traffic, event, security). Filters use the same field names (`srcip`, `dstip`, `policyid`, `action`, `user`), and you can switch between formatted and raw views.
* **FortiView** on FortiAnalyzer gives top sources, destinations, applications, threats and so on across all devices in the ADOM.
* **Reports** run on schedules from predefined or custom templates.
* **Incidents & Events / event handlers** raise alerts when log patterns match (for example repeated failed admin logins, or an IoC match).

From the FortiGate GUI you can also browse logs stored on FortiAnalyzer: set the **log location** selector in *Log & Report* to *FortiAnalyzer*. The FortiGate queries FortiAnalyzer and shows the results in its own log pages; historical FortiView on the FortiGate can likewise use FortiAnalyzer as its data source.

> **Real world:** When a user says "my traffic was blocked yesterday", start on FortiAnalyzer with `srcip==` and `action==deny` (or `utmaction==blocked`) over the time window. The `policyid` and the security log's `eventtype`/`attack` fields usually tell you which rule or profile to change before you ever open the FortiGate.

## FortiAnalyzer Cloud and FortiGate Cloud

* **FortiAnalyzer Cloud** is a FortiAnalyzer operated by Fortinet. It needs a FortiAnalyzer Cloud subscription for the FortiGate; enable it with `config log fortianalyzer-cloud setting` and test with `execute log fortianalyzer-cloud test-connectivity`.
* **FortiGate Cloud** is a separate service for cloud management, logging (with basic retention free), sandboxing and reporting, configured with `config log fortiguard setting` and the FortiGate Cloud activation in the GUI.

## Lab it yourself

FortiAnalyzer-VM has its own trial license. With it on the same network as your trial FortiGate:

1. Configure `config log fortianalyzer setting` on the FortiGate and run `test-connectivity`; note `unregistered`.
2. Authorise the FortiGate on FortiAnalyzer into the root ADOM, then re-run the test.
3. Generate traffic (keep within the trial's three policies) and find it in FortiAnalyzer Log View with a `srcip` filter.
4. Switch the FortiGate log location to FortiAnalyzer and confirm you see the same logs from the FortiGate GUI.
5. Block TCP 514 between them with an ACL on a Cisco router in the path and watch the test-connectivity output change.

## Key takeaways

* FortiGate-to-FortiAnalyzer communication is OFTP over **TCP 514** (log data over UDP 514 unless `reliable` is enabled).
* Registration needs both sides: the FortiGate configured to log, and the FortiAnalyzer authorising it into an ADOM (or pre-adding it by serial number).
* `execute log fortianalyzer test-connectivity` should show `Registration: registered` and `Connection: allow`.
* `upload-option` can be real time, every 1 or 5 minutes, or store-and-upload.
* Up to three FortiAnalyzers per FortiGate; FortiAnalyzer should run the same or newer firmware.
* View FortiAnalyzer logs in Log View/FortiView on FortiAnalyzer, or from the FortiGate GUI by changing the log location.
