## Typical operation of an HA cluster

In steady state an FGCP cluster looks like one firewall:

* The **primary** owns the virtual MACs and IPs, answers ARP, runs routing protocols, processes traffic (A-P) or receives and distributes it (A-A), and pushes configuration and sessions to the secondaries.
* **Secondaries** keep their configuration in sync, receive session updates, and listen for the primary's heartbeat. The primary also passes FortiGuard database updates to them, so they are ready to take over.
* Every member sends its own heartbeat. Members compare configuration **checksums** regularly.

### What triggers a failover

| Trigger | Detection |
|---|---|
| **Device failure** (power, crash, reboot) | Heartbeats stop arriving for longer than the heartbeat-loss threshold. |
| **Monitored interface failure** | Link down on an interface in `set monitor`. The member with more monitored interfaces up wins the next election. |
| **Remote link failure** | A link-monitor target behind a `pingserver-monitor-interface` stops answering past `pingserver-failover-threshold`. |
| **Administrator action** | `execute ha failover set 1` on the primary forces a failover for testing (the cluster records the forced-failover flag; clear it with `execute ha failover unset 1`). With override disabled, `diagnose sys ha reset-uptime` on the primary makes it lose the uptime comparison; with override enabled, lowering the primary's priority does the same. |

When the primary changes, the new primary takes the virtual MACs and sends **gratuitous ARP** packets so the switches relearn which port the MACs are on. Sessions that were synchronised continue; others restart. Routing adjacencies restart unless graceful restart is configured on the neighbours.

> **Exam tip:** A failover caused by a monitored interface **resets the HA uptime** of the member that lost the link. With override disabled, when that link comes back the member does **not** become primary again, because the new primary now has the higher uptime (and more than the 300 s margin). This is the most common "why didn't it fail back?" question.

```text
global: 7c 21 9a 0e 44 b1 52 d8 3f a0 6e 19 c2 77 05 bd

all: 9f 30 4b c7 e5 18 a2 6d 3c 71 b4 0e 8a 25 d9 f6
```

The `global` checksums match but `root` (the root VDOM's configuration) differs, so `all` differs too. The difference is inside the root VDOM. Next steps:

1. `diagnose sys ha checksum show root` on both members to compare per-table checksums and find the table that differs.
2. Ask the cluster to recompute: `diagnose sys ha checksum recalculate`.
3. Force a full resync from the primary: `execute ha synchronize start` (run on the secondary).

Typical causes of persistent out-of-sync: a member-specific object that should not be synchronised was created as if it were, a certificate or license that exists on one member only, mismatched firmware builds after a partial upgrade.

## HA cluster firmware upgrade

FortiOS can upgrade a whole cluster from the primary in one operation. The behaviour is controlled by `upgrade-mode` under `config system ha`:

| `upgrade-mode` | Behaviour |
|---|---|
| `uninterruptible` (**default**) | The **secondaries are upgraded first**. When they are back, a new primary is elected from the upgraded secondaries (traffic fails over to it), then the **former primary is upgraded last** and rejoins. Primary selection then follows the normal rules, so with override enabled the preferred unit becomes primary again (a second failover). |
| `simultaneous` | All members upgrade and reboot at the same time. Faster, but traffic is **interrupted** for the duration of the reboot. |

There are additional modes for staged upgrades, but uninterruptible is the default and the one to know. (Before FortiOS 7.4.1 this was a yes/no setting called `uninterruptible-upgrade`.)

```text
FGT-A(Primary) # show system ha | grep upgrade
    set upgrade-mode simultaneous
```

Points to remember for uninterruptible upgrades:

* Enable **session pickup** beforehand so established sessions survive the failover(s).
* If all secondaries fail to come back, the primary keeps running the old firmware and is not upgraded until at least one secondary rejoins.
* Check the result: `get system status` on each member (via `execute ha manage`) and `get system ha status` for `in-sync`.


## Use cases

* **Preferred primary**: the DC has a "main" unit with redundant power. Give it `priority 200` and `override enable` on both units, accepting an extra failover when it returns.
* **Stability over preference**: a branch cluster on a flaky upstream link. Leave override disabled so the cluster does not flap back and forth.
* **Upstream router failure behind a healthy switch**: configure a link monitor to the ISP gateway and `pingserver-monitor-interface "port1"` so the cluster fails over when the gateway dies even though `port1` stays up.
* **Out-of-sync after a change window**: `get system ha status` shows `out-of-sync`; use the checksum commands to find and fix the difference before the next failover exposes it.

## Key takeaways

* Failover triggers: heartbeat loss, monitored interface down, remote link monitor failure, admin action.
* The new primary keeps the virtual MACs and sends gratuitous ARP; synchronised sessions continue.
* Uptime resets on monitored-interface failure, so with override disabled the cluster does not fail back automatically.
* `get system ha status` shows the election reason, sync status, heartbeat and monitored interfaces.
* `diagnose sys ha checksum cluster` compares global, per-VDOM and overall checksums; `checksum recalculate` and `execute ha synchronize start` fix stale sync.
* Default `upgrade-mode uninterruptible`: secondaries first, failover, then the old primary. `simultaneous` upgrades all at once with an outage.
