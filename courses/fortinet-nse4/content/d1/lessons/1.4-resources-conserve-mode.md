## Know what normal looks like

You cannot call CPU or memory usage "abnormal" without a baseline. On a healthy FortiGate you should know the usual CPU percentage, memory percentage, session count and session setup rate at busy and quiet times. FortiOS gives you several ways to collect them:

* **Dashboards and widgets** (CPU, Memory, Sessions, Session Rate) with historical graphs.
* **SNMP** polling (`config system snmp sysinfo` and communities/users) into your NMS, with traps for high CPU, low memory and conserve mode.
* **Event logs** for conserve mode entry/exit, high CPU and HA events, sent to FortiAnalyzer.
* **Automation stitches** with *High CPU* or *Conserve mode* triggers that run CLI diagnostics and email the output while the problem is happening.
* CLI snapshots, below.

Thresholds that drive these events live in `config system global`:

| Setting | Default | Meaning |
|---|---|---|
| `cpu-use-threshold` | 90 | CPU percentage at which the high-CPU event/trigger fires |
| `memory-use-threshold-red` | 88 | Memory percentage that **enters** conserve mode |
| `memory-use-threshold-green` | 82 | Memory percentage that **exits** conserve mode |
| `memory-use-threshold-extreme` | 95 | Memory percentage at which **new sessions are dropped** |

The memory thresholds are configurable from 70 to 97 percent of total RAM. These defaults are unchanged in FortiOS 8.0.

```text
Average NPU sessions: 0 sessions in last 1 minute, 0 sessions in last 10 minutes, 0 sessions in last 30 minutes
Maximal NPU sessions: 0 sessions in last 1 minute, 0 sessions in last 10 minutes, 0 sessions in last 30 minutes
Average nTurbo sessions: 0 sessions in last 1 minute, 0 sessions in last 10 minutes, 0 sessions in last 30 minutes
Maximal nTurbo sessions: 0 sessions in last 1 minute, 0 sessions in last 10 minutes, 0 sessions in last 30 minutes
Virus caught: 0 total in 1 minute
IPS attacks blocked: 0 total in 1 minute
Uptime: 9 days,  6 hours,  41 minutes
```

How to read it:

* **CPU states**: `user` is time in user-space processes (inspection daemons such as `ipsengine`, `wad`, `miglogd`); `system` is kernel time; `irq`/`softirq` is packet-processing interrupt load. High **user** CPU points to inspection or a busy daemon; high **softirq** points to packet volume being handled by the CPU (traffic not offloaded).
* **Memory**: `used`, `free` and `freeable` (cache that can be reclaimed). Conserve mode is decided on **used** memory against the thresholds.
* **Network usage, sessions and setup rate**: compare with your baseline. A sudden jump in session setup rate with modest throughput usually means a scan, a flood or a misbehaving client.
* **NPU sessions**: on hardware with NP processors, offloaded sessions; zero on a VM.

The example shows high user CPU (71%) with only 4,000 sessions and 80 Mbps: a single 1-vCPU VM doing inspection is CPU-bound, not memory-bound.

## Finding the process: `diagnose sys top`

```text
FGT-HQ # diagnose sys top 5 20
Run Time:  9 days, 6 hours and 42 minutes
71U, 0N, 18S, 11I, 0WA, 0HI, 0SI, 0ST; 2007T, 583F
       ipsengine      312      S <    58.4     9.6
            wad      288      S       9.1     6.8
        miglogd      201      S       4.0     2.4
         httpsd      276      S       1.2     1.9
         newcli    18810      R       0.4     0.6
```

Arguments are refresh interval (seconds) and the number of lines. Columns: process name, PID, state (`R` running, `S` sleeping, `Z` zombie, `D` uninterruptible), CPU %, memory %. Press `p` to sort by CPU, `m` to sort by memory, `q` to quit. Here `ipsengine` (the IPS/flow inspection engine) dominates.

| Process | Role | Typical cause of high CPU/memory |
|---|---|---|
| `ipsengine` | IPS, flow-based AV/web filter/app control | Large IPS sensors, flow inspection of heavy traffic, signatures without filters |
| `wad` | Proxy-based inspection, explicit proxy, deep inspection | Many proxy sessions, SSL deep inspection |
| `miglogd` | Logging daemon | `logtraffic all` on busy policies, slow remote log server |
| `httpsd` / `newcli` | GUI / CLI sessions | Large GUI pages (big FortiView queries), many admins |
| `cw_acd`, `forticron`, `updated`, `authd`, `fnbamd` | Wireless controller, scheduled tasks, FortiGuard updates, authentication | Feature-specific spikes |

Other useful commands:

* `diagnose sys session stat` and `diagnose sys session full-stat`: session table size, clash and ephemeral counters.
* `diagnose hardware sysinfo memory` and `diagnose hardware sysinfo shm`: kernel and shared memory detail.
* `diagnose debug crashlog read`: daemon crashes, which often precede memory problems.
* `get system performance top`: equivalent to `diagnose sys top` on many builds.

### Reducing load

* Offload where possible (NP/SoC on hardware), and avoid features that disable offloading on high-volume policies.
* Narrow IPS sensors to the operating systems and services you actually have; use flow-based inspection where it meets requirements.
* Log `utm` instead of `all` on noisy policies; send logs to FortiAnalyzer instead of disk.
* Find the source of floods with the session list and apply DoS policies or block the source.
* Upgrade to a release that fixes a known leak; check the release notes' resolved issues.

## Memory conserve mode

When **used memory reaches the red threshold (88%)**, FortiOS enters **conserve mode** to protect itself. While in conserve mode the FortiGate keeps forwarding traffic, but it limits functions that need new memory. It **exits at the green threshold (82%)**; the gap prevents flapping. At the **extreme threshold (95%)**, new sessions are dropped.

```text
FGT-HQ # diagnose hardware sysinfo conserve
memory conserve mode:                        on
total RAM:                                   2007 MB
memory used:                                 1792 MB   89% of total RAM
memory freeable:                               61 MB    3% of total RAM
memory used + freeable threshold extreme:    1906 MB   95% of total RAM
memory used threshold red:                   1766 MB   88% of total RAM
memory used threshold green:                 1645 MB   82% of total RAM
```

What happens to inspection depends on two settings:

| Inspection | Setting | Default | Behaviour in conserve mode |
|---|---|---|---|
| **Proxy-based** (AV proxy) | `config system global` > `set av-failopen` | `pass` | `pass`: bypass the antivirus proxy so traffic keeps flowing **uninspected** (proxy-dependent profiles are bypassed). `off`: new sessions that need the AV proxy are **blocked**; existing ones continue unless they need more memory. `one-shot`: like `pass`, but keeps bypassing even after leaving conserve mode until you change the setting or reboot. |
| **Flow-based** (IPS engine) | `config ips global` > `set fail-open` | `disable` | `disable`: the IPS engine **drops** new sessions that need flow inspection. `enable`: the IPS engine passes new packets without scanning. |

> **Exam tip:** The defaults lean in opposite directions: proxy-based AV fails **open** (`av-failopen pass`) while the flow-based IPS engine fails **closed** (`fail-open disable`). Know which setting controls which inspection type.

> **Watch out:** `av-failopen pass` keeps users online but means files are not being scanned. If security policy requires "never pass uninspected", set `av-failopen off` and accept that sessions will be blocked during conserve mode.

### Signs and first response

* GUI banner warning about conserve mode; event log entries; SNMP trap.
* `diagnose hardware sysinfo conserve` shows `on`.
* If the GUI is unresponsive: `execute log filter category 1` then `execute log display` to read system events, and `diagnose sys top` (sort with `m`) to find the process using memory.

Then fix the cause, not the symptom: reduce the session count (DoS/flood, short session TTLs, `tcp-halfopen-timer`), reduce proxy usage (flow-based profiles, narrower SSL deep inspection), trim large dynamic objects, fix a leaking process (upgrade). Raising thresholds (for example red 90 / green 85) buys margin but does not fix anything.

## Lab it yourself

The trial VM's 2 GB of RAM makes this easy to observe:

1. Record `get system performance status` and `diagnose sys top 5 20` at idle.
2. From a Linux host, generate many sessions through a policy (for example `hping3 --flood -S -p 80` towards a test server, only in your isolated lab) and watch session setup rate and CPU rise.
3. Run `diagnose hardware sysinfo conserve` and `diagnose sys session stat` during the test.
4. Note the idle `memory used` percentage. If it is above 72%, temporarily set `memory-use-threshold-green 70` and `memory-use-threshold-red 72` under `config system global` (the minimum is 70, and green must stay below red) to trigger conserve mode; otherwise combine the lowered thresholds with the session load from step 2. Check the GUI banner and event logs, then restore the defaults (88/82/95).

## Key takeaways

* Baseline CPU, memory, sessions and setup rate; monitor with dashboards, SNMP, logs and automation stitches.
* `get system performance status` is the first snapshot; `diagnose sys top` finds the process (`p` CPU, `m` memory).
* Conserve mode: enter at 88% used (red), exit at 82% (green), drop new sessions at 95% (extreme). Range 70–97.
* Proxy AV in conserve mode: `av-failopen pass` (default) bypasses scanning; `off` blocks; `one-shot` keeps bypassing until changed or reboot.
* Flow IPS in conserve mode: `fail-open disable` (default) drops new flow-inspected sessions; `enable` passes them unscanned.
* `diagnose hardware sysinfo conserve` shows state and thresholds; fix the cause rather than raising thresholds.
