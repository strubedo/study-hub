## What FGCP is

The **FortiGate Clustering Protocol (FGCP)** joins two or more identical FortiGates into one logical firewall. One member is the **primary**; the others are **secondaries**. The cluster presents one configuration, one set of interface IPs and **virtual MAC addresses**, and fails over automatically when the primary or one of its monitored links fails. (Fortinet's other HA protocol, **FGSP**, synchronises sessions between independent FortiGates behind a load balancer; NSE 4 focuses on FGCP.)

### Requirements

* Same **hardware model** (or same VM type and size), same **firmware** build, same licenses (FortiGuard, VDOM count).
* Same HA **group ID**, **group name** and **password**, and the same **mode**.
* At least one heartbeat link between every member (two recommended).
* Interfaces cabled identically (port1 to the same network on every member).

### Modes

| | **Active-Passive (A-P)** | **Active-Active (A-A)** |
|---|---|---|
| Traffic | Primary processes all traffic; secondaries are hot standbys | Primary receives all traffic and **load-balances sessions that use security profiles** to secondaries |
| Plain firewall sessions | Primary | Still processed by the primary by default (load balancing of all TCP is optional with `load-balance-all`) |
| Complexity | Simple, predictable | More throughput for UTM-heavy traffic, harder to troubleshoot |
| Session failover | With session pickup | With session pickup |

> **Exam tip:** In A-A the primary is still the only member that receives packets from the network (it owns the virtual MACs). It forwards selected sessions to a secondary over the internal cluster path. A-A therefore helps when **security inspection** is the bottleneck, not raw firewall throughput.

## The heartbeat

Members exchange **HA heartbeat** packets on the interfaces listed in `set hbdev`. Heartbeats carry hello/state information, and the same links carry **configuration synchronisation** and (unless you dedicate other links) **session synchronisation**.

* Heartbeat frames use Ethertype **0x8890** (NAT mode; `ha-eth-type`) or **0x8891** (`hc-eth-type`: the 7.6/8.0 Admin Guide calls it active-active traffic redistribution, the CLI Reference calls it the transparent-mode heartbeat). **0x8893** (`l2ep-eth-type`) carries configuration synchronisation and HA telnet sessions between members such as `execute ha manage`, and **0x8892** carries session synchronisation on dedicated `session-sync-dev` links. Switches between members must pass these Ethertypes: if 0x8890 is dropped the members cannot see each other and the cluster splits; if only 0x8893 is dropped the cluster forms but configuration never synchronises. The values can be changed if they clash with something else on the network (some Cisco Nexus switches use 0x8890 themselves).
* Each `hbdev` entry has a priority; the highest-priority link that is up carries the heartbeat, and the others are backups.
* If **all** heartbeat links fail while both units are still running, each member believes the other is dead and becomes primary: a **split brain**. Both then answer on the same virtual MACs and IPs. Use two heartbeat links on separate physical paths (for example direct cables between the units) to avoid it.
* In public clouds, where layer 2 broadcast/multicast is not available, heartbeats run as **unicast** (`set unicast-hb enable`, `set unicast-hb-peerip`).

## Virtual MAC addresses

Cluster interfaces use virtual MAC addresses derived from the HA **group ID** (and the VDOM cluster and interface index) rather than their burned-in MACs. When the primary fails, the new primary takes over the same virtual MACs and IPs, and sends gratuitous ARP so switches update their MAC tables. Hosts' ARP caches do not need to change.

> **Watch out:** Two FGCP clusters on the same broadcast domain with the **same group ID** generate identical virtual MACs and break each other. Give every cluster on a shared layer 2 a unique group ID.

## Primary election

When a cluster forms, or when an event forces renegotiation, FGCP compares members in a fixed order. The order depends on whether **override** is enabled.

**Override disabled (default):**

1. **Connected monitored interfaces**: the member with more monitored interfaces up wins.
2. **HA uptime**: the member that has been in the cluster longer wins, *if* the difference is more than the margin (`ha-uptime-diff-margin`, default 300 seconds). Differences smaller than that are treated as equal.
3. **Device priority**: higher `priority` wins (default 128).
4. **Serial number**: the higher serial number wins.

**Override enabled:**

1. Connected monitored interfaces
2. **Device priority**
3. HA uptime
4. Serial number

| Situation | Override disabled | Override enabled |
|---|---|---|
| Original primary fails, then returns | The former secondary keeps the primary role (it now has the higher uptime) | The higher-priority unit **takes the primary role back** when it rejoins (a second failover) |
| Reboot both units together | Uptimes are within the margin, so priority decides | Priority decides |
| Typical use | Stability: fewer failovers | Deterministic primary for a known "preferred" unit |

> **Exam tip:** Override is **not synchronised**: it is a per-member setting along with the priority and host name. If override is enabled on one member only, the behaviour is inconsistent; enable it on all members if you use it. HA uptime is reset when a monitored interface fails or the member reboots, which is why a member that lost a link and recovered does not take the primary role back when override is disabled.

## Configuration synchronisation

The primary synchronises its configuration to all secondaries: an administrator changes the configuration only on the primary (changes made on a secondary are also propagated, but working on the primary is the rule). Synchronisation is **incremental** for each change, with a periodic **checksum** comparison; if checksums differ, a full resynchronisation runs.

Not synchronised (each member keeps its own):

* Host name
* HA `priority`, `override` and some other member-specific HA settings
* Reserved HA management interface settings (`ha-mgmt-interfaces`)
* In-band management IP (`set management-ip` on an interface)
* Licenses (each member has its own FortiCare/FortiGuard entitlements)
* Logs (each member stores or sends its own)

## The 8.0 view of a cluster

FortiOS 8.0 shows the HA role in the CLI prompt (`FGT-A(Primary) #`, `FGT-B(Secondary) #`) and updates it automatically after a failover. The GUI adds HA actions, per-member health status and a **configuration diff** between members, which makes out-of-sync troubleshooting easier.

## Key takeaways

* FGCP requires identical model, firmware, licenses, group ID/name/password and mode.
* A-P: only the primary processes traffic. A-A: the primary still receives all traffic but load-balances security-profile sessions to secondaries.
* Ethertypes: 0x8890 heartbeat (NAT mode), 0x8891 (`hc-eth-type`; Admin Guide: A-A traffic redistribution, CLI Reference: transparent-mode heartbeat), 0x8892 session sync, 0x8893 configuration sync and HA telnet sessions. Use two heartbeat links to avoid split brain.
* Virtual MACs come from the group ID: unique group IDs per layer 2 domain.
* Election, override disabled: monitored interfaces > uptime (300 s margin) > priority > serial. Override enabled: monitored interfaces > priority > uptime > serial.
* Host name, priority, override and management interface settings are not synchronised.
