## The remote-work problem

The classic design backhauls every remote user over a VPN to the head-office FortiGate, inspects their traffic there, and sends it on to the internet or SaaS. That design struggles once most users and most applications are no longer in the office:

| Challenge | Effect |
|---|---|
| **Backhaul latency and capacity** | SaaS traffic (Microsoft 365, Salesforce, GenAI tools) hairpins through the data centre, which adds latency and consumes head-office bandwidth and VPN capacity. |
| **Split tunnelling trade-off** | Sending internet traffic directly from the laptop fixes performance but leaves that traffic uninspected and unlogged. |
| **Inconsistent policy** | Users in the office, at home and at a café get different security depending on where they connect. |
| **Implicit trust** | A traditional VPN puts the user "on the network"; once connected, they can often reach much more than they need, which helps lateral movement after a compromise. |
| **Device posture** | Unmanaged or out-of-date devices connect with valid credentials. |
| **Visibility** | Logs for remote users are scattered across VPN concentrators and endpoint tools. |
| **Data leakage** | Sensitive data flows to SaaS and GenAI services the security team cannot see. |

## SASE architecture

**Secure access service edge (SASE)** combines network access and security into a cloud-delivered service that sits close to the user. Gartner's model has two halves:

* **Network services**: SD-WAN, optimised routing to the nearest point of presence, connectivity for branches and users.
* **Security service edge (SSE)**: the security stack delivered from the cloud: **secure web gateway (SWG)**, **cloud access security broker (CASB)**, **zero trust network access (ZTNA)**, **firewall as a service (FWaaS)**, DLP, sandboxing and threat intelligence.

The user (or branch) connects to the nearest **security point of presence (PoP)**; inspection and policy happen there; traffic then continues to the internet, SaaS or, through a private connection, to the company's own applications. Policy is defined once and follows the user.

Fortinet groups the use cases as:

| Use case | Abbreviation | Traffic |
|---|---|---|
| **Secure internet access** | SIA | Users to the web and the internet, inspected in the FortiSASE PoP |
| **Secure SaaS access** | SSA | Users to SaaS, with inline and API-based CASB visibility and control |
| **Secure private access** | SPA | Users to private applications in the data centre or cloud, through FortiGate hubs (SD-WAN/IPsec) or ZTNA |

## FortiSASE components

| Component | Role |
|---|---|
| **FortiSASE cloud service** | Fortinet-operated, multi-tenant service with global **security PoPs** running FortiOS security. Each customer gets a FortiSASE instance, administered from the FortiSASE portal (FortiCloud). |
| **FortiClient** (agent) | Endpoint agent on Windows, macOS, Linux, iOS and Android. Establishes the tunnel to the nearest PoP, reports **security posture** (and receives posture **tags**), provides ZTNA, endpoint protection features and DEM telemetry. FortiSASE includes a built-in **Endpoint Management Service** (cloud EMS) that manages the FortiClients. |
| **Agentless access** | **SWG / proxy mode**: the browser or OS uses FortiSASE as an explicit web proxy (often via a **PAC file**), for unmanaged devices or where an agent cannot be installed. **Agentless ZTNA** publishes private web applications through a bookmark portal. |
| **Edge devices (thin edge)** | **FortiExtender**, **FortiAP** and small **FortiGate** units at a micro-branch or home office connect the site to FortiSASE so devices without an agent (printers, IoT, guests) are protected. |
| **Branch on-ramp** | An IPsec tunnel from a FortiGate (or third-party device) at a branch into FortiSASE, so a whole site uses FortiSASE for internet security. |
| **SPA hubs** | Existing FortiGates acting as hubs (SD-WAN/IPsec with BGP) or ZTNA access proxies, giving FortiSASE users private access to internal applications. |
| **Identity sources** | Local users, LDAP, RADIUS, and **SSO through a SAML identity provider** (Microsoft Entra ID, Okta, AD FS, FortiAuthenticator). Group membership from the IdP or directory drives policy. |
| **Logging and analytics** | FortiSASE stores logs and reports itself and can forward to **FortiAnalyzer** (on premises or Cloud), a SOC service or an external syslog/SIEM. |
| **FortiGuard** | The same threat intelligence as FortiGate: web, DNS, application, IPS, AV, sandbox, DLP patterns. |

> **Exam tip:** FortiSASE is the *same security engine* as FortiGate, delivered from the cloud. The security profiles (web filter, application control, IPS, antivirus, DNS filter, DLP, SSL inspection) work the way you already know from FortiOS; what changes is where they run and how users reach them.

## How users and sites connect

| Method | Who it suits | Notes |
|---|---|---|
| **FortiClient agent** | Managed corporate laptops and phones | Full tunnel or split tunnel to the nearest PoP; posture checks; ZTNA to private apps; always-on options and pre-logon tunnels. |
| **SWG (agentless proxy)** | Unmanaged devices, contractors, BYOD | Only web traffic (HTTP/HTTPS) through the proxy; configured by PAC file or browser/OS proxy settings; users authenticate (usually SSO). |
| **Thin edge** | Home offices and micro-branches with IoT/headless devices | FortiExtender/FortiAP/FortiGate connects the whole LAN. |
| **Branch on-ramp (IPsec)** | Existing branches | Site-to-PoP tunnel; the branch keeps its local network. |

## Administration basics

* FortiSASE is administered from its own portal, reached through FortiCloud. Administrators are FortiCloud/IAM users with roles.
* Security is configured as **policies** (for internet access and for private access) with **security profile groups**, much like FortiGate policies with profiles.
* **Licensing** is per user (and per edge device or branch for those use cases), in tiers (Standard, Advanced, Comprehensive for remote users). Some features are available only in the higher tiers; Fortinet's FortiSASE ordering guide and feature matrix list which ones, and they change between FortiSASE releases.
* FortiSASE can be centrally managed from **FortiManager** (policy packages) in larger estates, and MSSPs can manage tenants centrally.
* Fortinet also offers a **sovereign** FortiSASE option, where the service runs in infrastructure dedicated to an organisation or region for data residency.

## Key takeaways

* Backhauling remote users causes latency, capacity and visibility problems; split tunnelling without cloud inspection loses security.
* SASE = network services (SD-WAN) + SSE (SWG, CASB, ZTNA, FWaaS, DLP) delivered from cloud PoPs near the user.
* Fortinet use cases: secure internet access (SIA), secure SaaS access (SSA), secure private access (SPA).
* FortiSASE components: cloud PoPs, FortiClient with the built-in Endpoint Management Service, agentless SWG/ZTNA, thin edge (FortiExtender/FortiAP/FortiGate), branch on-ramp, SPA hubs, identity sources, logging to FortiAnalyzer.
* FortiSASE runs the same FortiOS security profiles you configure on a FortiGate.
