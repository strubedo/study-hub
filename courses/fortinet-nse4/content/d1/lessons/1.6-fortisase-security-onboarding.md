## Security features in FortiSASE

FortiSASE applies the FortiOS security stack in its PoPs. If you know the FortiGate profiles, you know most of FortiSASE:

| Feature | What it does for remote users |
|---|---|
| **SSL inspection** | Certificate inspection or full deep inspection, with the FortiSASE CA pushed to managed endpoints by FortiClient. Most other profiles depend on it for HTTPS. |
| **Web filter, DNS filter, video filter** | FortiGuard categories, URL filters, safe search, DNS-based blocking of malicious domains. |
| **Application control and inline CASB** | Identify and control applications, including SaaS tenant restrictions (for example allowing only the corporate tenant of a SaaS or GenAI service) and activity controls. |
| **API-based CASB / SSPM** | Scans SaaS tenants out of band for risky sharing and misconfiguration. |
| **Antivirus, file filter, sandbox, CDR** | Malware scanning, blocking file types (including password-protected files), FortiSandbox analysis, content disarm and reconstruction. |
| **IPS** | Signature-based protection for traffic through the PoP. |
| **DLP** | FortiGuard DLP patterns and dictionaries, exact data match (EDM), document fingerprinting (IDM), sensitivity labels. |
| **ZTNA** | Per-application access to private apps based on identity and device posture. |
| **Endpoint features** | Posture checks, vulnerability visibility and patching, endpoint quarantine, through FortiClient. |
| **DEM** | Digital experience monitoring of SaaS and network performance from the endpoint. |

## ZTNA integration

**Zero trust network access** replaces "connect to the network, then reach everything" with "prove who you are and what device you are on, for each application, every time". The pieces are the same on FortiSASE and FortiGate:

* **Identity**: the user authenticates (SSO with a SAML IdP is typical).
* **Device**: FortiClient is registered with EMS (on FortiSASE, the Endpoint Management Service) and reports posture.
* **Tags**: EMS evaluates **zero trust tagging rules** (OS version, AV running, domain joined, vulnerabilities, certificate present...) and assigns **security posture tags** to the endpoint.
* **Policy**: a ZTNA or private access policy allows a user group *and* a posture tag to reach a specific application, through an **access proxy** (FortiGate) or the FortiSASE PoP.

| Mode | How it works |
|---|---|
| **Agent-based ZTNA** | FortiClient intercepts traffic to the protected application, builds a TLS connection to the access proxy and presents its device certificate; the proxy checks the certificate, the user and the posture tags. Designed for TCP applications; FortiOS 7.6 and later can also carry UDP for recent FortiClient versions, so check the FortiSASE release notes before assuming UDP support there. |
| **Agentless ZTNA** | For unmanaged devices: the user signs in through a browser portal, and private web applications appear as **bookmarks**; access is by identity only (no posture from an agent). |

Improvements to know at the level the docs describe them:

* **FortiOS 8.0 ZTNA configuration simplification**: ZTNA objects are decoupled so they can be combined more freely in ZTNA policies (for example a separate ZTNA destination object, and an authentication portal setting on the VIP replacing per-access-proxy SAML settings), and a **ZTNA service connector** (reverse gateway and forwarder) for publishing applications.
* **Tags in dual-stack ZTNA policies**: posture tags can be used in IPv4/IPv6 ZTNA policies.
* **Posture tags as JWT**: in FortiOS 8.0, FortiClient can send its security posture tags directly to the FortiGate as a JSON Web Token during dial-up IPsec VPN setup, after the user authenticates (FortiClient 7.4.5 and EMS 7.4.4 or later). The FortiGate gets the endpoint's tags at tunnel setup instead of relying only on its EMS connector, and the phase 1 can match on them (`set remote-gw-match ztna` with `set remote-gw-ztna-tags`).
* **FortiSASE ZTNA destinations** can be expressed as IP ranges or subnets (optionally with port lists or ranges), not only as single hosts, when the instance's FortiClient version supports it.

## Identity and tagging enhancements

Identity decides *who*, tags decide *what state the device or object is in*. Recent releases add:

* **Custom tags** on FortiOS 8.0 for addresses and policies, and **dynamic tag address groups** whose membership follows the tag (covered in the policy domain).
* **SSO with FortiIdentity Cloud** (Fortinet's cloud identity and MFA service, which grew out of FortiToken Cloud) and SCIM group integration.
* **Security posture tags** from EMS used in firewall policies, ZTNA policies and FortiSASE private access policies, so a device that falls out of compliance loses access automatically when its tag changes.
* FortiSASE **zero trust tagging rules** in its Endpoint Management Service, so the same posture tags drive FortiSASE policies without a separate on-premises EMS.

> **Exam tip:** A posture tag is **dynamic**: when the endpoint changes state (for example its antivirus is disabled), EMS updates the tag, FortiOS/FortiSASE updates the matching dynamic address, and the policy decision changes without anyone editing the policy.

## Data protection: GenAI, FortiData labels and OCR

### DLP for GenAI chatbots

Users paste source code, customer lists and contracts into chatbots. The controls work in layers:

1. **Visibility**: application control and FortiView identify GenAI applications in use (shadow AI). FortiOS 8.0 adds GenAI-aware application control, including the MCP and A2A agentic protocols.
2. **Access control**: allow only sanctioned GenAI services, and with **inline CASB** restrict them to the corporate tenant (for example by inserting tenant-restriction headers).
3. **Content control**: with **SSL deep inspection**, a **DLP profile** inspects what is uploaded or posted to the GenAI service (patterns such as credit card numbers, EDM records, fingerprinted documents, sensitivity labels) and blocks or logs the upload while still allowing normal use of the tool.

Without deep inspection none of the content controls work, because the prompt and file upload are inside TLS.

### FortiData labels

**FortiData** is Fortinet's data security and classification product. It scans and classifies files and applies **labels**. FortiOS DLP can use those labels: you create a DLP label of type `fortidata` that references the FortiData label name, use it in a DLP profile, and apply the profile to a **proxy-based** policy. When a file passes through, FortiOS sends the file's **fingerprint** (a hash of the file, not the file itself) to FortiData to check whether that file was labelled; FortiData must have its *Label Query Service* enabled and the FortiGate added as a querying device, and the FortiGate must have the FortiData Fabric connector enabled and authorised. (Integration needs FortiOS 7.6.4 or later and FortiData 7.6.1 or later.) The DLP profile's `fortidata-error-action` (`block`, `log-only` or `ignore`) defines what happens if the label query fails. Fortinet documents this integration for FortiGate proxy-based policies; treat FortiSASE support as something to confirm in the current FortiSASE documentation.

### OCR on DLP

Text-based DLP misses sensitive data inside **images**: screenshots of a spreadsheet, a scanned contract, a photographed ID card. **Optical character recognition (OCR)** extracts text from images so the DLP patterns can be applied to it. FortiOS 8.0 introduces enhanced DLP with OCR-based content analysis (listed in the 8.0.1 new features). Treat it as an addition to DLP, which still needs deep inspection to see files inside TLS. Image analysis adds processing work, so scope it to the traffic where the risk justifies it. (Fortinet's FortiProxy has offered OCR in its image analysis profiles since FortiProxy 7.4.0.)

> **Watch out:** Fortinet documents these data-protection features at a high level and they are evolving quickly between releases. For the exam know *what each one detects and what it depends on* (deep inspection, proxy-based policy, FortiData's label query service), not specific limits or thresholds.

## User onboarding methods

| Method | Steps | Best for |
|---|---|---|
| **Invitation email** | The admin clicks *Onboard Users* in FortiSASE; users receive an email with a FortiClient download link and an **invitation code** unique to the FortiSASE deployment; they install FortiClient, enter the code (or follow the link) to register with the FortiSASE Endpoint Management Service, then authenticate. | Small deployments, pilots |
| **Automated deployment** | Push a preconfigured FortiClient installer (MSI/package) through an **MDM** or software distribution tool so it registers automatically. | Managed fleets |
| **SSO-based authentication** | Users sign in with their IdP credentials (Entra ID, Okta, ...) through SAML; group membership drives policy. | Most production deployments |
| **Local / LDAP / RADIUS users** | Users exist in FortiSASE or in a directory reachable from FortiSASE. | Existing directory without an IdP |
| **Agentless SWG** | Distribute a PAC file or proxy setting; users authenticate to the proxy (usually SSO). | BYOD, contractors |
| **Edge devices** | Register a FortiExtender/FortiAP/FortiGate to FortiSASE (zero-touch provisioning). | Home offices, micro-branches |

Registering FortiClient to the Endpoint Management Service only enrols the device; the user still needs to be provisioned in an authentication source to be allowed a tunnel.

## Use cases

* **Hybrid workforce**: replace head-office VPN backhaul with FortiClient tunnels to the nearest PoP for internet and SaaS; keep private apps reachable through SPA hubs on existing FortiGates.
* **Contractor access**: agentless ZTNA bookmarks to two internal web apps, SSO with the contractor's group, no network-level access.
* **Compliance-gated access**: a private access policy that requires the `Compliant` posture tag; devices with disabled antivirus lose access until fixed.
* **GenAI governance**: allow the corporate tenant of an approved chatbot, block unsanctioned ones by category, and DLP-block uploads of documents labelled *Confidential* in FortiData or containing card numbers, including in screenshots via OCR.
* **Micro-branch**: a FortiExtender at a retail kiosk sends all traffic through FortiSASE.

## Key takeaways

* FortiSASE delivers FortiOS security (SSL inspection, web/DNS filter, app control, CASB, AV, sandbox, IPS, DLP) from cloud PoPs.
* ZTNA = identity + device posture tags + per-application policy; agent-based uses FortiClient and certificates, agentless uses a browser bookmark portal.
* Posture tags are dynamic and change policy outcomes automatically; 8.0 adds custom tags and simplified ZTNA objects.
* GenAI data protection needs app control/inline CASB plus deep inspection plus DLP.
* FortiData labels: DLP label type `fortidata`, proxy-based policy, FortiOS queries FortiData with the file's fingerprint (hash).
* OCR extends DLP to text inside images.
* Onboarding: invitation code email, MDM-pushed FortiClient, SSO/SAML, LDAP/RADIUS/local, agentless PAC, edge devices.
