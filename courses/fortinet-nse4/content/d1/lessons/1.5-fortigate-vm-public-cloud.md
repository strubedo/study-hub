## Why the cloud changes the firewall problem

Moving workloads to AWS or Azure does not move security responsibility to the provider. Under the **shared responsibility model**, the provider secures the physical data centre, hypervisor and core services; the customer secures everything they build on top: operating systems, identities, network design, traffic inspection and data.

| Challenge | Why it hurts |
|---|---|
| **Misconfiguration** | A single open security group, storage bucket or route table entry exposes a workload. Changes happen through APIs and templates, often without a network team in the loop. |
| **Limited native inspection** | Security groups and network ACLs are layer 3/4 filters. They do not do IPS, application control, web filtering, antivirus or SSL inspection. |
| **East-west and lateral movement** | Traffic between subnets and VPCs/VNets is invisible unless you deliberately route it through an inspection point. |
| **Dynamic, elastic addressing** | Instances scale in and out and change IPs; static address objects go stale within hours. |
| **Hybrid and multicloud consistency** | Different native controls in each cloud and on premises make one policy hard to enforce. |
| **Visibility and compliance** | Logs are scattered across provider services; auditors want one record. |
| **Threats** | Credential theft, exposed management interfaces, ransomware and data exfiltration still apply, now with internet-facing workloads that scale. |

The rest of this lesson focuses on FortiGate-VM because it is what you configure as a FortiOS administrator.

## FortiGate-VM in the cloud

### Licensing

| Model | How it works |
|---|---|
| **PAYG** (pay as you go, on-demand) | Launch from the AWS or Azure **marketplace**; the hourly instance price includes the FortiGate license (and the FortiGuard services listed in the offer). Billed by the cloud provider. No license file. |
| **BYOL** (bring your own license) | Launch the BYOL marketplace image and apply a license bought from Fortinet: a license file, or a **FortiFlex** token (points-based, flexible vCPU and service sizing). |

PAYG is fast and elastic (good for autoscaling bursts); BYOL is usually cheaper for steady, long-running instances. The vCPU count of the license must match or exceed the instance size, or the extra vCPUs are not used.

8.0 improved VM **license grace period** monitoring, so you get clearer warning when a VM license is about to lapse, and FortiGate-VMs can **auto-register to FortiManager Cloud**.

### Deployment basics

* Pick an instance size with enough vCPUs and network interfaces (each interface is an ENI in AWS or a NIC in Azure). Typical design: `port1` public/untrust, `port2` private/trust, extra ports for HA sync and management.
* In AWS, **disable source/destination check** on the FortiGate's ENIs, otherwise AWS drops traffic the instance forwards for other hosts. In Azure, enable **IP forwarding** on the FortiGate's NICs.
* Steer traffic through the FortiGate with **route tables** (AWS) or **user-defined routes (UDRs)** (Azure) pointing the default route or inter-subnet routes at the FortiGate's private interface.
* The default admin password on cloud images is not blank: in AWS it is the **instance ID**, in Azure you set it in the deployment. Change it, restrict management to trusted sources, and never leave the GUI open to the internet on the public interface.

### High availability in the cloud

Public clouds do not provide layer 2 broadcast or gratuitous ARP, so FGCP works differently:

* **Unicast heartbeat** between the members (`set unicast-hb enable` and `set unicast-hb-peerip` in `config system ha`).
* On failover, the new primary calls the **cloud API** through its SDN integration to move the **public IP (Elastic IP / Azure public IP)** and to **update route tables/UDRs** to point at itself. In AWS, Fortinet calls this "automatic AWS SDN updates to EIPs and route targets": the `awsd` process makes the calls using the **IAM role** attached to the instances (Azure uses the SDN connector's managed identity or service principal). This takes longer than a hardware failover.
* A reserved **HA management interface** with its own route to the cloud API endpoints is typical, so each member can make API calls.
* Alternatives: put FortiGates behind a cloud load balancer (Azure Load Balancer "sandwich", AWS **Gateway Load Balancer** with GENEVE, Azure **Gateway Load Balancer** with VXLAN) for active-active scale-out, often with **FGSP** session sync.

### SDN connectors and dynamic addresses

An **SDN connector** (`config system sdn-connector`, types such as `aws` and `azure`) lets the FortiGate call the cloud API. The preferred authentication is the instance's own identity: an **IAM role** attached to the instance in AWS, a **managed identity** in Azure (or an access key/service principal). The FortiGate obtains those credentials from the cloud's instance metadata service at **169.254.169.254**, so it must be able to reach that link-local address.

With the connector in place you create **dynamic address objects** whose members are resolved from cloud metadata (tags, VPC/VNet, subnet, security group, region), and the FortiGate keeps them updated as instances scale:

```text
FGT-AWS # config firewall address
FGT-AWS (address) # edit "aws-web-servers"
FGT-AWS (aws-web-servers) # set type dynamic
FGT-AWS (aws-web-servers) # set sdn "aws-conn"
FGT-AWS (aws-web-servers) # set filter "Tag.Role=web"
FGT-AWS (aws-web-servers) # next
FGT-AWS (address) # end
```

Policies then reference `aws-web-servers`, and the object follows the autoscaling group. 8.0 adds **EKS filtering** for the AWS connector (an allow-list of EKS cluster names, so the connector resolves only those Kubernetes clusters) and a **Cloud SDN Orchestration VPN wizard for AWS** (*VPN > Cloud SDN Orchestration*), which builds IPsec tunnels to AWS virtual private gateways and transit gateways through the AWS API.

## Automation-ready configurations

Cloud FortiGates are rarely configured by hand. Ways to make them reproducible:

* **Bootstrapping (day 0):** pass a FortiOS configuration (and for BYOL, the license) as **user data** in AWS or **custom data** in Azure. At first boot the FortiGate reads it through the cloud's provisioning mechanism (in AWS, the user data served by the instance metadata service) and applies it, so the instance comes up already configured.
* **Infrastructure as code:** Fortinet-published **Terraform** modules and the `fortios` Terraform provider, AWS **CloudFormation** templates, Azure **ARM/Bicep** templates on Fortinet's GitHub.
* **Autoscaling:** Fortinet's autoscale solutions for AWS and Azure use cloud functions to add and remove FortiGate-VMs, license them (PAYG or BYOL/FortiFlex) and synchronise configuration from a primary.
* **Day-N automation:** the FortiOS **REST API**, **FortiManager** (and FortiManager Cloud), automation stitches, and Ansible collections for FortiOS.

> **Exam tip:** "Automation-ready" means the FortiGate can be deployed and configured without a human at the console: bootstrapped from user/custom data, licensed by PAYG or a FortiFlex token, and kept current by SDN connector dynamic objects instead of static IPs.

## Telemetry addresses

FortiOS includes a **telemetry** address type used with **FortiTelemetry**, Fortinet's digital experience monitoring agents. When the FortiGate acts as a **FortiTelemetry Controller** (enabled in *System > Feature Visibility*) and you authorise an agent, FortiOS automatically creates a **dynamic telemetry address** named after the agent's serial number and adds it to the default `TELEMETRY` address group (controlled by `set auto-group-telemetry-addr` under `config telemetry-controller global`). Telemetry addresses and telemetry address groups can be used in firewall policies, so policy follows the monitored endpoint rather than a fixed IP, the same idea as an SDN-connector dynamic address.

```text
FGT-AWS # show firewall address FTLWIN0000012345
config firewall address
    edit "FTLWIN0000012345"
        set type dynamic
        set sub-type telemetry
        set agent-id "FTLWIN0000012345"
    next
end
```

The `telemetryd` daemon keeps these objects updated, and Fortinet advises against renaming them. You can also build your own address groups with `set category telemetry` (members must be telemetry addresses or telemetry groups) and use them in policies. In FortiOS 7.6.3, agents were stored as plain `ipmask` addresses with `FT100G`/`FTLWIN` name prefixes; 7.6.4 and later (including 8.0) migrate them to the dynamic `telemetry` sub-type.

> **Watch out:** Fortinet's FortiOS 8.0 AWS guide does not define a cloud-specific "telemetry address". The FortiOS object with that name is the FortiTelemetry address above (*Telemetry addresses and address groups* in the Administration Guide). Do not confuse it with the cloud's **instance metadata address** (169.254.169.254), which a FortiGate-VM uses for IAM role or managed identity credentials (and, in AWS, to read its bootstrap user data). Both can turn up in cloud troubleshooting, but they are different things.

## Lab it yourself

The cloud labs need an AWS or Azure account and cost money; the free VM trial cannot be launched in a marketplace. Without spending anything you can:

1. Read a Fortinet Terraform example for a single FortiGate-VM in AWS and identify the user data, the source/destination check setting and the route table entries.
2. On the trial VM, create an SDN connector of type `aws` with dummy credentials and a dynamic address object to see the CLI structure (it will not resolve).

## Key takeaways

* Shared responsibility: the customer secures workloads, identities and traffic; native security groups are layer 3/4 only.
* FortiGate-VM runs full FortiOS in the cloud; FortiGate CNF is the managed cloud-native option in AWS.
* PAYG = marketplace hourly billing with the license included; BYOL = license file or FortiFlex token.
* Disable source/destination check (AWS) or enable IP forwarding (Azure), and steer traffic with route tables/UDRs.
* Cloud FGCP uses unicast heartbeat and cloud API calls (SDN integration with the instance's IAM role or managed identity) to move public IPs and routes on failover.
* SDN connectors use IAM roles/managed identity via 169.254.169.254 and feed dynamic address objects.
* Telemetry addresses are dynamic objects for authorised FortiTelemetry agents, grouped into `TELEMETRY` by default.
