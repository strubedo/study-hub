## Building the cluster

Cluster formation is simple once both units are prepared: same model and firmware, licenses applied, and each unit reachable on the console. Configure HA on each unit, cable the heartbeat links, and the members find each other, elect a primary and the secondaries take the primary's configuration.

```text
FGT-A # config system ha
FGT-A (ha) # set group-id 10
FGT-A (ha) # set group-name "HQ-CLUSTER"
FGT-A (ha) # set mode a-p
FGT-A (ha) # set password ********
FGT-A (ha) # set hbdev "port3" 50 "port4" 50
FGT-A (ha) # set monitor "port1" "port2"
FGT-A (ha) # set session-pickup enable
FGT-A (ha) # set override disable
FGT-A (ha) # set priority 200
FGT-A (ha) # end
```

Repeat on FGT-B with the same group ID, group name, mode, password and heartbeat interfaces, and a different priority (for example the default 128). The moment you leave `config system ha`, the unit starts sending heartbeats. Once the cluster is up, the prompt in 8.0 shows the role: `FGT-A(Primary) #`.

> **Watch out:** Make sure the unit whose configuration you want to keep wins the first election: give it the higher priority, and either bring it up in HA mode more than five minutes before the second unit (so it also wins on uptime) or enable override. If the blank unit wins instead (for example because it has the higher HA uptime, or the higher serial number with equal priorities), its empty configuration is synchronised over your production configuration.

### HA settings you modify most often

| Setting | Purpose |
|---|---|
| `mode` | `standalone`, `a-p`, `a-a` |
| `group-id`, `group-name`, `password` | Must match on all members. Group ID drives the virtual MACs. |
| `hbdev` | Heartbeat interfaces and their priorities. Use at least two. |
| `monitor` | Interfaces whose link failure triggers a failover. Monitor only interfaces that carry traffic and are cabled on every member. |
| `priority` | Member-specific election priority (default 128). Not synchronised. |
| `override` | Make priority take precedence over uptime. Not synchronised. |
| `ha-uptime-diff-margin` | Uptime difference treated as equal (default 300 s). |
| `pingserver-monitor-interface`, `pingserver-failover-threshold` | **Remote link monitoring**: fail over when a link-monitor target beyond the interface becomes unreachable, even though the local link is up (used with `config system link-monitor` and its `ha-priority`). |
| `session-pickup` and related | Session synchronisation, below. |
| `ha-mgmt-status`, `ha-mgmt-interfaces`, `ha-direct` | Reserved management interfaces, below. |
| `upgrade-mode` | How firmware upgrades are performed (see the next lesson). |

> **Exam tip:** Interface **monitoring** detects local link failure (cable pulled, switch port down). **Remote link (ping server) monitoring** detects a failure further away (the upstream router dead but the switch still up). Do not monitor heartbeat interfaces: heartbeat links have their own failure handling, and monitoring them causes needless failovers.

## Session synchronisation for seamless failover

Without session synchronisation, a failover keeps the cluster IPs and MACs alive, but the new primary has no session table: existing TCP connections are dropped and must be re-established by the applications. Enabling **session pickup** makes the primary synchronise its sessions to the secondaries so that most established sessions survive a failover.

| Setting | What it synchronises |
|---|---|
| `session-pickup enable` | TCP sessions (and the basis for the options below). IPsec SAs are synchronised by the cluster in any case so tunnels survive failover. |
| `session-pickup-connectionless enable` | Also UDP and ICMP sessions. |
| `session-pickup-expectation enable` | Expectation (pinhole) sessions created by session helpers, for example FTP data or SIP media. |
| `session-pickup-delay enable` | Only sessions older than 30 seconds, which cuts sync load caused by short-lived sessions (DNS, short HTTP). Sessions younger than 30 s are lost at failover. |
| `session-sync-dev "port5"` | Carry session sync on dedicated interfaces instead of the heartbeat links, for busy clusters. |

What is **not** failed over even with session pickup:

* Sessions handled by **proxy-based** inspection (proxy-mode security profiles, explicit web proxy): the proxy state cannot be synchronised, so those sessions restart.
* Sessions terminating on the FortiGate itself (admin GUI/SSH sessions, local-in traffic).
* Some multicast and other special session types unless their own sync options are enabled.

> **Real world:** Session pickup costs CPU and heartbeat bandwidth. On a firewall dominated by short web sessions, enable `session-pickup-delay` so you synchronise only the long-lived sessions (file transfers, RDP, database connections) that users would actually notice losing.

## HA management interfaces

In a cluster the secondaries do not own the cluster IPs, so you need a separate way to reach each member for monitoring and troubleshooting.

### Option 1: `execute ha manage`

From the primary's CLI you can open a CLI session on any other member over the heartbeat link:

```text
FGT-A(Primary) # execute ha manage 0 admin
```

`execute ha manage ?` lists the other members and their **cluster index** numbers (assigned by serial number, highest serial = 0, so FGT-B with the higher serial number is 0 here); you then log in to the chosen member with an admin account. Type `exit` to return to the primary. This needs no extra IP addressing but only gives you the CLI.

### Option 2: reserved HA management interface

A **reserved management interface** is removed from the cluster configuration: each member gives it its own IP address and gateway, it is not synchronised, and it can be used for GUI/SSH/SNMP access to that specific member.

```text
FGT-A(Primary) # show system ha
config system ha
    set group-id 10
    set group-name "HQ-CLUSTER"
    set mode a-p
    set password ENC ...
    set hbdev "port3" 50 "port4" 50
    set session-pickup enable
    set ha-mgmt-status enable
    config ha-mgmt-interfaces
        edit 1
            set interface "port5"
            set gateway 10.0.99.1
        next
    end
    set override disable
    set priority 200
    set monitor "port1" "port2"
end
```

Rules: the interface must not be referenced by anything else (no firewall policies, routes or VIPs), and each member sets its own IP on that interface. The interface lives in a separate, hidden management VDOM and uses its own gateway, which is why the `gateway` is set inside `ha-mgmt-interfaces` rather than in the routing table.

With `set ha-direct enable`, management services such as **logging to FortiAnalyzer/syslog, SNMP, RADIUS, FortiSandbox and NetFlow/sFlow** traffic from each member leave through that member's reserved management interface instead of following the cluster's data interfaces and routing table. (`ha-direct` also exists per SNMP host and SNMPv3 user if you want only SNMP to use the management interface.)

### Option 3: in-band management IP

Assign an extra **management IP** to an ordinary cluster interface on each member:

```text
FGT-B(Secondary) # show system interface port2
config system interface
    edit "port2"
        set vdom "root"
        set ip 10.0.1.1 255.255.255.0
        set management-ip 10.0.1.12 255.255.255.0
        set allowaccess ping https ssh
    next
end
```

The management IP must be in the same subnet as the interface's cluster IP. It is not synchronised, so each member gets its own, and an admin can browse directly to 10.0.1.12 to reach FGT-B. FortiOS 8.0 adds IPv6 support for in-band management IPs.

| Method | Separate subnet/port needed | GUI access to a secondary | Synchronised |
|---|---|---|---|
| `execute ha manage` | No | No (CLI only) | n/a |
| Reserved management interface | Yes, a dedicated port | Yes | No |
| In-band `management-ip` | No (same subnet as the cluster IP) | Yes | No |

## Lab it yourself

HA needs two VMs. If your trial license does not let you form a cluster, build the configuration anyway on one unit and study the outputs in this lesson; if it does, use `port1` (WAN), `port2` (LAN) and `port3` (heartbeat) to stay inside the three-interface limit:

1. Configure the commands above on both units with `hbdev "port3" 50` and `monitor "port2"`.
2. Run `get system ha status` and note which criterion selected the primary.
3. Start a long `ping` and an SSH session through the cluster, disconnect `port2` on the primary, and observe which survives with and without `session-pickup` (and `session-pickup-connectionless` for the ping).
4. Run `execute ha manage ?` to see the secondary's cluster index, then `execute ha manage <index> admin` to reach it.

## Key takeaways

* Configure identical group ID, group name, password and mode; set per-member priority and override.
* Protect your configuration when forming a cluster: the elected primary's configuration wins.
* Interface monitoring = local link; remote link monitoring = path beyond the link.
* `session-pickup` syncs TCP; add `session-pickup-connectionless` for UDP/ICMP and `session-pickup-expectation` for helper pinholes; `session-pickup-delay` syncs only sessions older than 30 s.
* Proxy-inspected sessions and local-in sessions do not survive failover.
* Reach individual members with `execute ha manage`, a reserved management interface (`ha-mgmt-interfaces`, plus `ha-direct` for logs/SNMP), or an in-band `management-ip`.
