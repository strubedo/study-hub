## Work up the stack

When "traffic doesn't pass", work from the bottom: is the link up and clean, does the FortiGate have layer 2/3 reachability, do packets arrive, and what does FortiOS decide to do with them? The FortiGate has a tool for each layer.

## Physical and network layer checks

### Link state, speed and duplex

```text
FGT-HQ # get system interface physical
== [onboard]
        ==[port1]
                mode: static
                ip: 203.0.113.10 255.255.255.0
                ipv6: ::/0
                status: up
                speed: 100Mbps (Duplex: half)
        ...
```

`status`, `speed` and duplex come straight from the PHY. A gigabit link that negotiated **100 Mbps half duplex** is a classic cause of slow transfers and late collisions; check the cable and the switch port, and make both ends either auto/auto or the same fixed setting (`set speed 1000full` on the FortiGate interface if you must fix it).

Error counters live in the NIC statistics:

```text
FGT-HQ # diagnose hardware deviceinfo nic port1
...
Rx_Errors              : 4893
Rx_CRC_Errors          : 4871
Rx_Frame_Errors        : 22
Tx_Errors              : 0
Collisions             : 0
...
```

The exact field list depends on the NIC driver (hardware ports and virtio VM ports differ), but rising **CRC/frame errors** mean a layer 1 problem (cable, optic, port, duplex mismatch), not a firewall problem. On the Cisco side, compare with `show interfaces` input errors and CRC.

### Layer 2 and layer 3

* `get system arp` (or `diagnose ip arp list`): is there an ARP entry for the next hop or the host? An incomplete entry means no layer 2 reachability.
* `get router info routing-table all`: is there a route to the destination, out of the expected interface?
* `get router info routing-table details 198.51.100.20`: which route is actually used for that destination.
* `execute ping` and `execute traceroute` from the FortiGate, with `execute ping-options source 10.0.1.1` to test from a specific interface address.
* `diagnose sys session list` (after setting `diagnose sys session filter`) to see whether a session exists and what NAT it used.

> **Exam tip:** `execute ping` tests from the FortiGate itself, so it uses the FortiGate's routing but **not** firewall policies. A ping from the FortiGate succeeding while users fail usually means a policy, NAT or return-route problem, not upstream reachability.

## The packet sniffer

The built-in sniffer shows whether packets actually arrive and leave, on which interface, before or after NAT.

```text
diagnose sniffer packet <interface> '<filter>' <verbose> <count> <timestamp>
```

| Argument | Values |
|---|---|
| interface | An interface name, or `any` to capture on all interfaces |
| filter | tcpdump/BPF-style expression in single quotes: `'host 10.0.1.10'`, `'net 10.0.1.0/24'`, `'host 10.0.1.10 and port 443'`, `'icmp'`, `'tcp[13] & 2 != 0'`, or `none` |
| verbose | 1–6, below |
| count | Number of packets to capture; `0` = until Ctrl+C |
| timestamp | `a` absolute UTC, `l` local time; omit for relative time |

| Verbose | Shows |
|---|---|
| 1 | Packet headers only |
| 2 | Headers and IP data |
| 3 | Headers and Ethernet data |
| 4 | Headers with **interface name and direction** |
| 5 | Headers, IP data and interface name |
| 6 | Headers, Ethernet data and interface name (convertible to pcap) |

```text
FGT-HQ # diagnose sniffer packet any 'host 198.51.100.20 and icmp' 4 6 l
interfaces=[any]
filters=[host 198.51.100.20 and icmp]
2026-10-29 10:02:11.481203 port2 in 10.0.1.10 -> 198.51.100.20: icmp: echo request
2026-10-29 10:02:11.481290 port1 out 203.0.113.10 -> 198.51.100.20: icmp: echo request
2026-10-29 10:02:12.482017 port2 in 10.0.1.10 -> 198.51.100.20: icmp: echo request
2026-10-29 10:02:12.482081 port1 out 203.0.113.10 -> 198.51.100.20: icmp: echo request
2026-10-29 10:02:13.483355 port2 in 10.0.1.10 -> 198.51.100.20: icmp: echo request
2026-10-29 10:02:13.483419 port1 out 203.0.113.10 -> 198.51.100.20: icmp: echo request
6 packets received by filter
0 packets dropped by kernel
```

Reading it: requests arrive on `port2` from 10.0.1.10 and leave `port1` source-NATed to 203.0.113.10, but no `echo reply` ever comes back in on `port1`. The FortiGate is forwarding correctly; the problem is upstream (the destination, the ISP, or a return path that does not lead back to 203.0.113.10).

> **Watch out:** Traffic that is **offloaded** to an NP processor after the first packets is not visible to the sniffer (or to debug flow). If a capture shows only the start of a session, disable offloading on the test policy (`set auto-asic-offload disable`) while troubleshooting. Also, verbosity 4 on `any` is the best starting point: without the interface name you cannot tell ingress from egress.

## Debug flow: what FortiOS decides

The sniffer shows packets; **debug flow** shows FortiOS's decisions about them: route lookup, policy match, NAT, session creation and drops, with a reason.

```text
FGT-HQ # diagnose debug reset
FGT-HQ # diagnose debug flow filter clear
FGT-HQ # diagnose debug flow filter addr 10.0.1.10
FGT-HQ # diagnose debug flow filter proto 1
FGT-HQ # diagnose debug flow show function-name enable
FGT-HQ # diagnose debug console timestamp enable
FGT-HQ # diagnose debug flow trace start 10
FGT-HQ # diagnose debug enable
```

* Filters: `addr`, `saddr`, `daddr`, `port`, `sport`, `dport`, `proto`, `vd`, `negate`. Always filter; an unfiltered debug on a busy unit is noisy and costs CPU.
* `trace start 10` traces the next 10 matching packets and then stops.
* Nothing prints until **`diagnose debug enable`**. Stop with `diagnose debug disable` (and `diagnose debug reset` to clear everything).

An allowed, NATed flow:

```text
id=65308 trace_id=1 func=print_pkt_detail line=6012 msg="vd-root:0 received a packet(proto=1, 10.0.1.10:1->198.51.100.20:2048) tun_id=0.0.0.0 from port2. type=8, code=0, id=1, seq=1."
id=65308 trace_id=1 func=init_ip_session_common line=6198 msg="allocate a new session-0002a41f"
id=65308 trace_id=1 func=iprope_dnat_check line=5480 msg="in-[port2], out-[]"
id=65308 trace_id=1 func=iprope_dnat_tree_check line=826 msg="len=0"
id=65308 trace_id=1 func=iprope_dnat_check line=5492 msg="result: skb_flags-02000000, vid-0, ret-no-match, act-accept, flag-00000000"
id=65308 trace_id=1 func=vf_ip_route_input_common line=2612 msg="find a route: flag=04000000 gw-203.0.113.1 via port1"
id=65308 trace_id=1 func=__iprope_fwd_check line=811 msg="in-[port2], out-[port1], skb_flags-02000000, vid-0, app_id: 0, url_cat_id: 0"
id=65308 trace_id=1 func=__iprope_tree_check line=530 msg="gnum-100004, use addr/intf hash, len=2"
id=65308 trace_id=1 func=fw_forward_handler line=987 msg="Allowed by Policy-1: SNAT"
id=65308 trace_id=1 func=__ip_session_run_tuple line=3572 msg="SNAT 10.0.1.10->203.0.113.10:62464"
```

The lines answer the questions in order: which interface the packet came in on, whether a **new session** was created (or an existing one matched: `Find an existing session, id-...`), whether a **VIP/DNAT** applied, the **route lookup** result, the **policy** that allowed it, and the **NAT** applied.

Messages you must recognise:

| Message | Meaning |
|---|---|
| `Denied by forward policy check (policy 0)` | No policy matched; the implicit deny dropped it. |
| `Denied by forward policy check (policy 7)` | An explicit **deny** policy (ID 7) matched. |
| `reverse path check fail, drop` | **RPF check** failed: the FortiGate has no route back to the source via the ingress interface. Fix routing (or the asymmetric design). |
| `find a route: flag=... gw-... via port1` | Route lookup result. |
| `iprope_in_check() check failed on policy 0, drop` | Traffic **to the FortiGate itself** was dropped by local-in (for example admin access not allowed on that interface). |
| `Find an existing session, id-...` | Packet matched an existing session (no policy lookup). |
| `Allowed by Policy-N: SNAT` / `Allowed by Policy-N:` | Policy N matched; with SNAT if NAT is enabled on it. |

> **Exam tip:** Debug flow traces the **first packets** of a session through policy lookup in detail; later packets just match the existing session. If you start the trace after the session already exists, you will see `Find an existing session` and not the policy decision. Clear the session (`diagnose sys session filter ...` then `diagnose sys session clear`) and retry.

## Use case: troubleshooting "users can't reach a web server"

1. Physical: `get system interface physical` shows up/1000full on both ports.
2. Sniffer: `diagnose sniffer packet any 'host 198.51.100.20 and port 443' 4` shows SYNs in on `port2` but nothing out of `port1`.
3. Debug flow with `filter addr 198.51.100.20` and `filter dport 443`: `Denied by forward policy check (policy 0)`.
4. The logs confirm `policyid=0 action="deny"` (if implicit deny logging is on).
5. Fix the policy (wrong destination address object or service), retest: debug shows `Allowed by Policy-3: SNAT`, the sniffer shows SYN out of `port1` and SYN-ACK back.

## Lab it yourself

1. Put a Linux host on `port2` and a Cisco router or second Linux host on `port1`. Create one policy port2→port1 with NAT.
2. Ping through and capture with verbosity 4 on `any`; then make the far side drop its echo replies (an inbound ACL on the Cisco router, or an `iptables` rule on Linux) and see requests leave with no replies.
3. Run debug flow while disabling the policy: compare the `Allowed` and `Denied ... (policy 0)` traces.
4. Add a more specific static route (for example the Linux host's /32) via `port1` so the route back to the source no longer points at the ingress interface, and trigger `reverse path check fail`. Delete it afterwards (the trial allows only 3 routes).
5. Speed/duplex labs need a physical port: on the trial VM, `get system interface physical` reports the virtual NIC, and changing the Cisco side's speed or duplex does not change what the FortiGate-VM shows. Practise reading the output instead, and compare with `show interfaces` on the Cisco side.

## Key takeaways

* Check layer 1 first: `get system interface physical` (speed/duplex) and `diagnose hardware deviceinfo nic` (CRC/frame errors).
* `execute ping` from the FortiGate bypasses firewall policies; use it to test routing, not policy.
* Sniffer: `diagnose sniffer packet <intf> '<filter>' <1-6> <count> <a|l>`; verbosity 4 adds interface and direction; 6 adds Ethernet data and interface (pcap-convertible).
* Debug flow: set filters, `trace start <n>`, then `diagnose debug enable`; stop with `diagnose debug disable`.
* `policy 0` = implicit deny; `reverse path check fail` = RPF/routing; `iprope_in_check() check failed` = local-in.
* Offloaded traffic is invisible to sniffer and debug flow after setup; disable offload while testing.
