## A troubleshooting order that works

Work up the stack, and confirm each layer before you move on:

1. **Underlay.** Can the gateways reach each other on UDP 500/4500 (or the TCP port)? Check with `execute ping`, a sniffer on the WAN, and upstream ACLs.
2. **Phase 1.** Is the IKE SA established? Check `diagnose vpn ike gateway list` and the IKE debug.
3. **Phase 2.** Are the IPsec SAs up for the right selectors? Check `diagnose vpn tunnel list` and `get vpn ipsec tunnel summary`.
4. **Routing.** Does the traffic route into the tunnel? Check `get router info routing-table details <dst>`.
5. **Policy.** Is there an accept policy LAN → tunnel and tunnel → LAN? Check `diagnose debug flow`.
6. **Return path, NAT and MTU.** Does the far side have a route back? Is NAT applied by mistake? Is fragmentation or the MSS a problem?

## The commands

| Command | Shows |
|---------|-------|
| `get vpn ipsec tunnel summary` | One line per tunnel: peer, `selectors(total,up)`, rx/tx packets and errors |
| `diagnose vpn ike gateway list [name <p1>]` | Phase 1 detail: IKE version, local → remote addr:port, `transport`, IKE SA and IPsec SA counters, proposal, lifetime/rekey, DPD counters, and (since 7.6) the `PQC-KEM` and `QKD` flags. In 8.0 a TCP/TLS tunnel also shows TCP rate and drop counters |
| `diagnose vpn tunnel list [name <p1>]` | Phase 2 detail per tunnel: `proxyid` and `src`/`dst` selectors, SPIs (`dec`/`enc`), packet counters, `dpd`, `natt`, NPU offload flags |
| `diagnose vpn ike log filter rem-addr4 <ip>` then `diagnose debug application ike -1` and `diagnose debug enable` | Real-time IKE negotiation |
| `diagnose vpn tunnel flush <p1>` / `diagnose vpn ike gateway clear` | Tear down IPsec SAs, or whole gateways, to force renegotiation |
| `diagnose vpn tunnel up <p2> <p1>` | Bring a phase 2 up without traffic |
| `diagnose debug flow filter …` / `trace start` | Routing and policy decisions for the data traffic |

## Common failures and their signatures

| Symptom | Likely cause | Where you see it |
|---------|--------------|------------------|
| No IKE packets come back | Underlay or ACL blocking UDP 500/4500, wrong `remote-gw`, peer not configured | Sniffer shows outbound only. IKE debug shows retransmits, then `negotiation timeout` |
| Phase 1 fails, "no proposal chosen" | Encryption, integrity or DH group mismatch | IKE debug. Log `reason="no proposal chosen"` or `peer SA proposal not match local policy` |
| Phase 1 fails at AUTH | **PSK mismatch** or bad certificate or peer ID | IKEv2 debug: `PSK auth failed: probable pre-shared key mismatch`. Log `reason="probable PSK mismatch"` |
| Phase 1 up, phase 2 down | **Selector (proxy ID) mismatch**, phase 2 proposal or PFS mismatch | `IPsec SA: created 0/1`. Log `reason="TS_UNACCEPTABLE received"` (IKEv2). Summary shows `selectors(total,up): 1/0` |
| Tunnel up, no traffic | Missing route or policy, NAT enabled on the VPN policy, far side missing a return route | `diagnose debug flow`. `tx` increments but `rx` stays at 0 in the tunnel summary |
| Tunnel flaps | DPD too aggressive, unstable underlay, duplicate tunnels to the same peer | Logs `reason="DPD timeout"`, repeated tunnel-up/down events |
| Large packets fail, small pings work | MTU/fragmentation, typically through NAT or PPPoE | Sniffer. Fix with `tcp-mss-sender` / `tcp-mss-receiver` on the policy, `tcp-mss` on the interface, or the interface MTU |

> **Watch out:** "Tunnel shows up, traffic from HQ reaches the branch, replies never return" is rarely an IPsec problem. Check the branch's **route back** to the HQ subnet and its **tunnel → LAN policy**. In `get vpn ipsec tunnel summary` the HQ side shows tx climbing and rx flat.

## VPN event logs

IPsec events are logged as `type="event" subtype="vpn"`. You can view them at **Log & Report > System Events > VPN Events**, or from the CLI with `execute log filter category 1`, `execute log filter field subtype vpn`, then `execute log display`. The log IDs you will meet:

| logid | logdesc |
|-------|---------|
| 0101037124 | IPsec phase 1 error |
| 0101037125 | IPsec phase 2 error |
| 0101037127 | Progress IPsec phase 1 (normal negotiation progress) |
| 0101037128 | Progress IPsec phase 1 (error level, with `result="ERROR"`) |
| 0101037129 / 0101037130 | Progress IPsec phase 2 (normal / error) |
| 0101037138 | IPsec connection status changed (`action="tunnel-up"` / `"tunnel-down"`) |
| 0101037139 | IPsec phase 2 status changed (`action="phase2-up"`) |
| 0101037133 | IPsec SA installed (with `in_spi` / `out_spi`) |
| 0101037134 | IPsec phase 1 SA deleted |
| 0101037141 | IPsec tunnel statistics |

FortiOS 8.0.1 adds a **`reason` field** to the existing phase 1 error, phase 2 error, connection status changed and progress logs, so the root cause is visible without debugging. Negotiation reasons include `probable PSK mismatch`, `authentication failed`, `no proposal chosen`, `peer SA proposal not match local policy` and `TS_UNACCEPTABLE received` (or `selectors mismatch`). Tunnel-down reasons include `DPD timeout`, `retransmission timeout`, `disconnected by peer`, `last phase1 down`, `gw flush` and `tunnel flush`. In 8.0 the user fields in these logs are `user`, `useralt`, `eapuser` and `eapauthgroup`. When an established tunnel goes down and the peer is a FortiGate or FortiClient, FortiOS also sends the cause in a vendor-specific IKEv2 notify (`IKEV2_DISCONNECT_REASON`), so the other side can log it too. No new log IDs were introduced.

```text
logid="0101037124" type="event" subtype="vpn" level="error" vd="root" logdesc="IPsec phase 1 error" msg="IPsec phase 1 error" action="negotiate" remip=198.51.100.20 locip=203.0.113.10 remport=500 locport=500 outintf="port1" vpntunnel="to-Branch" status="negotiate_error" reason="probable PSK mismatch"
```

## FortiOS 8.0: TLS 1.3-based VPN negotiation

FortiOS already supported **IKE and ESP over TCP** (RFC 8229, IKEv2). It helps where UDP 500/4500 is blocked. FortiOS 8.0 adds **TLS 1.3** as an option on top: IKE and ESP are carried inside a TLS 1.3 session over TCP, so the tunnel looks like ordinary TLS on the wire.

```text
FGT-Branch # config system settings
FGT-Branch (settings) # set ike-tcp-service enable
FGT-Branch (settings) # set ike-tls-service enable
FGT-Branch (settings) # set ike-tcp-port 443
FGT-Branch (settings) # end
FGT-Branch # config vpn ipsec phase1-interface
FGT-Branch (phase1-interface) # edit "to-HQ"
FGT-Branch (to-HQ) # set ike-version 2
FGT-Branch (to-HQ) # set transport auto
FGT-Branch (to-HQ) # next
FGT-Branch (phase1-interface) # end
```

* In the GUI: **VPN > VPN Tunnels > Settings** → *Allow VPN negotiation over TCP* → *Use TLS*. These are **per-VDOM** settings, and TCP encapsulation is disabled by default. `ike-tls-service` can only be set when `ike-tcp-service` is enabled. `ike-tcp-port` defaults to 443 (it was 4500 up to 7.6.0).
* `transport auto` tries UDP first and falls back to TCP or TLS. A static (site-to-site) phase 1 must be set to `auto` to use TCP or TLS. Dial-up phase 1s behave as auto when `ike-tcp-service` is enabled.
* Supported for **site-to-site and dial-up between FortiGates**. FortiClient supports plain IKE/ESP over TCP (RFC 8229) but not the TLS option yet.
* TCP transport needs IKEv2 and doesn't support ADVPN or NPU offloading, so expect more CPU load than a UDP tunnel. Leave `fortinet-esp` (Fortinet's proprietary ESP-in-TCP header format) disabled unless both ends are FortiGates that need it.
* Verify with `diagnose vpn ike gateway list`, which shows **`transport: TLS`**, with TCP rate and drop counters.

Don't confuse this with TLS 1.3 *inspection* (Domain 3). This feature is about the transport of the VPN itself.

## FortiOS 8.0: quantum-safe IPsec

The threat is **harvest now, decrypt later**: record IKE exchanges today, break the (EC)DH key exchange with a future quantum computer, and recover the session keys. FortiOS answers this in layers, all on **IKEv2**:

| Layer | Standard | FortiOS configuration |
|-------|----------|----------------------|
| **Hybrid PQC key exchange** | RFC 9370 (multiple key exchanges) using RFC 9242 IKE_INTERMEDIATE. ML-KEM = FIPS 203. | `set addke1` … `addke7` on phase 1 and phase 2. Up to 7 additional key exchange rounds, up to 3 groups each. ML-KEM-512/768/1024 are IDs **35/36/37**. Also offered: BIKE, HQC, FrodoKEM, though only ML-KEM is NIST standardized. Classical DH still runs. The extra KEM secret is mixed in. |
| **PQC signature authentication (new in 8.0)** | RFC 7427 digital signature auth. ML-DSA (FIPS 204), SLH-DSA (FIPS 205). | `set authmethod signature`, `set digital-signature-auth enable`, `signature-hash-alg` (`identity` per RFC 8420), using certificates with ML-DSA or SLH-DSA keys |
| **Post-quantum preshared key** | RFC 8784 | `set ppk {allow \| require}` with `ppk-secret` (per user for dial-up) |
| **QKD** (since 7.4.2) | ETSI standardized key-delivery API | `config vpn qkd` profile, then `set qkd {allow \| require}` and `qkd-profile` on phase 1, to retrieve keys from an external quantum key distribution system |

```text
FGT-HQ # config vpn ipsec phase1-interface
FGT-HQ (phase1-interface) # edit "to-Branch"
FGT-HQ (to-Branch) # set ike-version 2
FGT-HQ (to-Branch) # set addke1 36
FGT-HQ (to-Branch) # set childless-ike enable
FGT-HQ (to-Branch) # next
FGT-HQ (phase1-interface) # end
```

In the gateway list, `PQC-KEM (IKE): yes` and `PQC-KEM (all IPsec): yes` confirm that the additional key exchange was used. The IKE debug shows `type=ADDKE1, val=ML-KEM-768.` in the proposal, then on the initiator `processing KE group 36` and `KEM decapsulate okay` after the INTERMEDIATE response (the responder encapsulates, the initiator decapsulates). Phase 2 ADDKE rounds for child SAs appear as FOLLOWUP_KE messages. Both peers need matching ADDKE groups.

Practical notes from Fortinet's documentation:

* PQC changes only **key establishment and authentication** during IKE. ESP still uses AES-GCM and the like, so bulk throughput and NP offload are unchanged. Setup and rekey cost a little more CPU.
* ML-KEM public keys are large, so IKE messages may need fragmentation. That is one reason the extra exchanges happen in IKE_INTERMEDIATE after IKE_SA_INIT.
* The PQC key exchange itself predates 8.0. The PQC key-exchange configuration is already in the 7.6 Administration Guide. The new 8.0 item is PQC **signature** authentication, with the `digital-signature-auth` and `signature-hash-alg` (including `identity`) options documented in the 8.0 New Features guide.

## Key takeaways

* Troubleshoot underlay, then phase 1, phase 2, route, policy, and finally the return path.
* `created 0/1` on IPsec SAs, or `selectors 1/0`, means phase 2 is down. Suspect selectors, phase 2 proposals or PFS.
* `probable PSK mismatch`, `no proposal chosen` and `TS_UNACCEPTABLE` are the three classic negotiation failures. 8.0.1 puts them in the log `reason` field.
* Remember the main VPN log IDs: 0101037124/37125 (phase 1/2 error), 37138 (tunnel up/down), 37133 (SA installed).
* 8.0 TLS VPN: `ike-tcp-service` + `ike-tls-service` (per VDOM, `ike-tcp-port` default 443), static phase 1 `transport auto`, FortiGate-to-FortiGate only, no ADVPN or NPU offload, verified by `transport: TLS`.
* Quantum-safe IPsec needs IKEv2: `addke1-7` with ML-KEM (35/36/37), ML-DSA/SLH-DSA signatures (new in 8.0), PPK, QKD. Verify with the `PQC-KEM` lines.
