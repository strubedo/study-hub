## The VPN Wizard

In FortiOS 8.0 the wizard is at **VPN > VPN Wizard**. You name the tunnel, pick a template, and answer a few pages of questions. The template types are **Site to Site**, **Hub and Spoke** (including ADVPN), remote access and a fully **Custom** tunnel. 8.0.0 adds native OS client support to the remote access wizard, and 8.0.1 regroups the remote access entries into two top-level templates: **FortiClient remote access** (full tunnel with Secure Internet Access, or split tunnel) and **Native client remote access** (L2TP over IPsec or IKEv2 with the OS's built-in client). 8.0 also adds a separate Cloud SDN Orchestration VPN wizard for AWS.

The wizard is popular on the exam because it builds a complete, working set of objects. For a *Site to Site* tunnel named `HQ-to-BR1` to a FortiGate at 198.51.100.20, it creates:

| Object | What the wizard creates |
|--------|-------------------------|
| Phase 1 | `config vpn ipsec phase1-interface` → `HQ-to-BR1`, IKEv2, `wizard-type static-fortigate`, recommended proposals (AES-CBC/GCM and ChaCha20 with SHA-2) and ECP DH groups such as `dhgrp 20 21` |
| Phase 2 | `HQ-to-BR1` with named selectors `HQ-to-BR1_local` / `HQ-to-BR1_remote` |
| Addresses | `HQ-to-BR1_local_subnet_1`, `HQ-to-BR1_remote_subnet_1` and the address groups `HQ-to-BR1_local` / `HQ-to-BR1_remote`, all with `allow-routing enable` |
| Static routes | One route to `HQ-to-BR1_remote` via the tunnel interface, plus a **blackhole** route to the same destination at **distance 254** |
| Firewall policies | `vpn_HQ-to-BR1_local` (LAN → tunnel) and `vpn_HQ-to-BR1_remote` (tunnel → LAN), action accept, no NAT |

Wizard objects carry a comment such as `VPN: HQ-to-BR1 (Created by VPN wizard)`, which makes cleanup easy. Run the wizard on **both** FortiGates with mirrored subnets. You can then convert the tunnel to a custom tunnel to edit settings the wizard hides.

> **Exam tip:** Know what the wizard creates without being asked: phase 1/2, address objects and groups, a route plus a distance-254 blackhole route, and **two** policies. When a question shows a tunnel that is up but traffic fails in one direction, check whether one of the two policies was deleted or disabled.

### Transport and NAT settings in the wizard

* **NAT traversal** is enabled, with a 10 s keepalive.
* **Transport** is UDP unless *Allow VPN negotiation over TCP* is enabled in **VPN > VPN Tunnels > Settings**. With it enabled you can choose **Auto**: try UDP first, fall back to TCP or TLS.
* **IKE version** defaults to 2.

## Site-to-site checklist (route-based, manual)

1. Phase 1 on each side: `remote-gw` set to the peer's public IP, `interface` set to the local WAN, matching proposals, DH groups and PSK (or certificates).
2. Phase 2 with mirrored selectors. Leave them at 0.0.0.0/0 if both sides are FortiGates and routing does the selection.
3. Route the remote subnet into the tunnel: `set device "HQ-to-BR1"`. No gateway is needed on a tunnel interface.
4. Add a blackhole route for the remote subnet at distance 254.
5. Create two policies (LAN ↔ tunnel), with NAT normally disabled.
6. Bring it up: send traffic, or run `diagnose vpn tunnel up <phase2-name> <phase1-name>`, or set `auto-negotiate enable` on phase 2.

FortiGate tunnel interfaces have no IP address by default. That's fine for static routing. Give them `ip`/`remote-ip` (a /32 pair) under `config system interface` if you run a dynamic routing protocol over the tunnel or want to ping the far end of the tunnel.

## Dial-up VPN

**Dial-up** means the FortiGate (the server) doesn't know the peer's IP in advance. Phase 1 uses `set type dynamic`, and anyone presenting valid credentials can connect. Typical cases: a branch FortiGate behind a DHCP or CGNAT connection, and remote users with FortiClient.

When a dial-up client connects, the server creates a **dynamic instance** of the phase 1: `HQ-dialup_0`, `HQ-dialup_1`, and so on. In `diagnose vpn tunnel list` these show `mode=dial_inst`, and the parent template shows `mode=dialup`. The parent never carries traffic itself. Firewall policies reference the parent interface, and they apply to every instance.

| Dial-up feature | Purpose |
|-----------------|---------|
| `add-route enable` (default) | Install a route to each client's selector or assigned IP **while connected**. This is why dial-up servers often need no static routes for clients. |
| `mode-cfg enable` | Push an IP address (range, DHCP, or IPAM in 8.0), DNS servers, DNS suffix and split-tunnel networks to the client |
| `peertype` / `peerid` / IKEv2 `network-id` | Let one interface IP host several dial-up phase 1s. The responder picks the right one by ID. |
| `remote-gw-match` (IKEv2) | Select the dial-up gateway by the client's source subnet, range, country or ZTNA tag |
| `xauthtype` (IKEv1) / `eap enable` (IKEv2) | Per-user authentication against local, LDAP, RADIUS or SAML users |

A **FortiGate dial-up client** is a normal static phase 1 (`type static`) pointed at the server's public IP. Because only the client knows where the server is, **only the client can initiate**. The server can't bring the tunnel up towards a dial-up peer.

### Remote access with FortiClient

The FortiClient remote access template builds an IKEv2 dial-up phase 1 with mode-cfg and EAP user authentication against a user group, plus policies from the tunnel to the chosen internal networks. In 8.0 the wizard **defaults to IPAM addressing** for remote access clients (8.0.1 adds IPv6 IPAM addressing). The native client template builds either L2TP over IPsec or IKEv2 for the operating system's built-in VPN client.

FortiClient-specific points:

* **FortiClient 7.4.4 and later don't support IKEv1.** Use IKEv2 for FortiClient tunnels.
* **Split tunnelling** comes from the mode-cfg split-include networks. Without it, all client traffic goes into the tunnel, and you need a tunnel → WAN policy with NAT for internet access.
* Connected users appear in the GUI IPsec monitor/dashboard widget and in `diagnose vpn ike gateway list`, which shows each instance's EAP user name, FortiClient UID and assigned IPv4 address, so you can find a specific user.
* **EMS SN verification** can restrict tunnels to FortiClient endpoints managed by your EMS.

### What happened to SSL VPN

SSL VPN **tunnel mode was removed in FortiOS 7.6.3**, from both the GUI and CLI on all models, and its configuration (including its firewall policies) isn't upgraded. Fortinet's migration path is **IPsec dial-up VPN**, which can also run over TCP 443. SSL VPN **web mode** survives as **Agentless VPN**: a clientless browser portal. It is disabled and hidden by default (enable it with `config system global` → `set sslvpn-web-mode enable`, and show the menus with `config system settings` → `set gui-sslvpn enable`), and it isn't available on some smaller models such as the 40F, 60F and 90G series. On FortiOS 8.0, **remote access to the network means IPsec**, which is why the NSE 4 8.0 VPN domain covers only IPsec.

## Use cases

* **Branch with a static public IP to HQ.** Site to Site template on both sides. Routes and blackhole routes come from the wizard.
* **Branch behind CGNAT.** HQ runs a dial-up server (`type dynamic`) and the branch runs a static phase 1 towards HQ. NAT-T moves the tunnel to UDP 4500. With `add-route`, HQ learns the branch subnet when the tunnel comes up, as long as the branch's phase 2 selectors name its subnet.
* **Home workers.** Remote Access template with FortiClient over IKEv2 and EAP against an LDAP group. If UDP 500/4500 is blocked at hotels, enable *Allow VPN negotiation over TCP* (8.0 can also use TLS between FortiGates; FortiClient doesn't support the TLS option yet).

## Lab it yourself

This fits the FortiGate-VM trial. Port1 is the WAN to a Linux router, and port2 is the LAN.

1. Build a dial-up server with the FortiClient remote access template, using a local user group. Install the free FortiClient VPN on a laptop and connect over IKEv2. The trial is low-encryption only (in practice DES for IPsec, see the concepts lesson), so set `ike-proposal-visibility all` and change the phase 1 and phase 2 proposals to DES. Current FortiClient builds may not offer DES at all. If the client can't negotiate, this step needs a fully licensed FortiGate, and you can do the rest of the lab with a second trial VM as a FortiGate dial-up client instead.
2. Inspect what the wizard built with `show vpn ipsec phase1-interface`, `show firewall policy` and `show router static`. That is 2 policies and maybe 1 route, which fits the 3/3 limits.
3. While connected, run `diagnose vpn tunnel list` and find the `dial_inst` entry, the `add-route` flag and `natt: mode=keepalive` if your laptop is behind NAT.

## Key takeaways

* The site-to-site wizard creates phase 1/2, address objects and groups, a tunnel route, a **distance-254 blackhole** route and **two** policies.
* Wizard defaults: IKEv2 (since 7.6.0), NAT-T enabled, 10 s keepalive, ECP DH groups, recommended AES/ChaCha20 proposals.
* Dial-up = `type dynamic`. Each client gets a `_N` dynamic instance. Only the client side can initiate.
* `add-route` installs client routes only while the tunnel is up. `mode-cfg` pushes addressing, DNS and split networks.
* FortiClient 7.4.4+ is IKEv2 only.
* SSL VPN tunnel mode is gone since 7.6.3. Web mode is now Agentless VPN, disabled by default. Remote access is IPsec.
