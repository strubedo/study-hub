## The moving parts

IPsec on a FortiGate is the standard IETF suite:

| Component | Job | On the wire |
|-----------|-----|-------------|
| **IKE** (Internet Key Exchange) | Authenticates the peers, negotiates algorithms, creates keys, maintains the tunnel (rekey, DPD) | UDP **500**. UDP **4500** once NAT is detected (NAT-T). Optionally IKE/ESP over TCP (RFC 8229, TCP 443 by default since 7.6.1) or, new in 8.0, over TLS 1.3 on TCP (see the troubleshooting and 8.0 features lesson). |
| **ESP** (Encapsulating Security Payload) | Encrypts and authenticates user traffic | IP protocol **50**, or ESP inside UDP 4500 with NAT-T |
| **SA** (Security Association) | One negotiated set of keys and algorithms. ESP SAs are one per direction, identified by an SPI. | — |

FortiGate site-to-site and dial-up tunnels use **ESP in tunnel mode**: the whole original IP packet is encrypted and a new outer header carries it between the two gateways. FortiOS does not use AH. Transport mode appears only in special cases such as L2TP over IPsec.

## Phase 1 and phase 2

The two-phase model is the core of every IPsec troubleshooting question.

**Phase 1** builds the **IKE SA**, a secure, authenticated control channel between the gateways. The peers agree on:

* **Authentication**: pre-shared key or certificate (`authmethod psk | signature`), plus optional user authentication (XAuth in IKEv1, EAP in IKEv2).
* **Proposals**: encryption and integrity/PRF pairs (for example `aes256gcm-prfsha384`, `aes128-sha256`).
* **Diffie-Hellman group(s)**: `dhgrp 20 21`. Group 14 = MODP-2048, 19/20/21 = ECP-256/384/521.
* **IKE SA lifetime**: `keylife` defaults to 86400 seconds.
* **Identity**: local ID and peer ID. In IKEv2 also the Fortinet `network-id`.

**Phase 2** runs inside the protected phase 1 channel and builds the **IPsec (child) SAs** that carry data. The peers agree on:

* **Selectors** (quick-mode selectors in IKEv1, traffic selectors in IKEv2; Fortinet calls the pair a *proxy ID*). This is the local and remote subnet, protocol and port that the SA protects. The defaults are 0.0.0.0/0 to 0.0.0.0/0.
* **Phase 2 proposals** and **PFS**. PFS is on by default, so phase 2 does its own DH exchange using the phase 2 `dhgrp`.
* **Lifetime**: `keylifeseconds` defaults to 43200 seconds. **Replay detection** is on by default.
* **`auto-negotiate`**: bring the SA up without waiting for traffic. It is disabled by default, so a phase 2 with no interesting traffic can stay down.

Each side must offer at least **one matching proposal and DH group** in each phase. Selectors must **mirror** each other: my local is your remote. FortiOS accepts a peer's selector if it is a subset of the local one ("phase2 matched by subset"), but a mismatch outside that fails with **TS_UNACCEPTABLE** (IKEv2).

> **Exam tip:** `IKE SA: created 1/1 established 1/1` with `IPsec SA: created 0/1` in `diagnose vpn ike gateway list` means phase 1 is up and phase 2 is not. Look at selectors, phase 2 proposals and PFS settings, not the pre-shared key.

## IKEv1 versus IKEv2

| | IKEv1 | IKEv2 (RFC 7296) |
|--|-------|------------------|
| Phase 1 exchange | **Main mode**: 6 messages, identities encrypted. **Aggressive mode**: 3 messages, identity sent in clear, faster, and needed when a responder must select among several dial-up phase 1s by peer ID. | **IKE_SA_INIT** + **IKE_AUTH**: 4 messages that create the IKE SA *and* the first child SA |
| Phase 2 | Quick mode, 3 messages per SA | CREATE_CHILD_SA (also used for rekeys) |
| User auth | XAuth | EAP (EAP-TTLS, MSCHAPv2 and others) |
| Selecting a dial-up gateway | Peer ID (aggressive mode) | Peer ID or Fortinet **network-id**, which travels in the first message |
| Reliability features | DPD and NAT-T were add-ons | Liveness checks (DPD) and NAT-T built into the base RFC. Extensions add IKE fragmentation (RFC 7383), TCP/TLS transport, EAP and PQC key exchange |
| FortiClient | **Not supported from FortiClient 7.4.4** | Required for current FortiClient remote access |

**IKEv2 is the default** for new tunnels: the VPN Wizard has defaulted to IKE version 2 since 7.6.0 (it was version 1 up to 7.4.5), and the 8.0 custom tunnel page and CLI default to version 2 as well. IKEv1 remains configurable for legacy peers. Many newer features exist only with IKEv2: VPN over TCP/TLS, post-quantum key exchange and signatures, `network-id` overlays, remote gateway matching by subnet, geography or ZTNA tag, and EAP and SAML user authentication for FortiClient.

> **Real world:** The blueprint bullet "IPsec v2" doesn't match any feature name in the FortiOS 8.0 New Features guide (its IPsec section lists items such as TLS 1.3 based VPN over TCP, recommended-only IKE proposals and PQC signature authentication, but nothing called "IPsec v2") or the Administration Guide. The most likely reading is IPsec with **IKE version 2**, now the FortiOS default and the base for every 8.0 VPN feature. Treat that as an interpretation, not a Fortinet definition. Expect questions on IKEv2 behaviour and on why IKEv1 is no longer suitable for FortiClient.

Interoperability gotchas between the versions:

* Both ends must run the same IKE version. An IKEv1 initiator never matches an IKEv2 phase 1.
* IKEv1 aggressive mode with PSK exposes a hash that can be cracked offline. Avoid it unless you need it for peer-ID gateway selection.

## Route-based versus policy-based VPN

| | Route-based (interface mode) | Policy-based |
|--|------------------------------|--------------|
| Config | `config vpn ipsec phase1-interface` / `phase2-interface` | `config vpn ipsec phase1` / `phase2` |
| What it creates | A **virtual tunnel interface** named after phase 1 (max 15 characters) | No interface |
| Traffic selection | **Routing**: a static or dynamic route points at the tunnel interface | A firewall policy with `set action ipsec` and `set vpntunnel` |
| Policies | Normal accept policies, LAN → tunnel and tunnel → LAN | One IPsec policy covers both directions (`inbound`/`outbound` options) |
| Dynamic routing, SD-WAN, redundancy, ADVPN | Yes | No |
| Status | **Recommended and the default** | Legacy. Hidden until *Policy-based IPsec VPN* is enabled in *Feature Visibility*. |

Everything in the rest of this domain assumes route-based VPNs. A route-based tunnel needs **both** a route and a firewall policy. A missing route means traffic never reaches the tunnel. A missing policy means traffic is dropped by implicit deny (policy ID 0 in debug flow).

## Key phase 1 settings

```text
FGT-HQ # config vpn ipsec phase1-interface
FGT-HQ (phase1-interface) # edit "to-Branch"
FGT-HQ (to-Branch) # set interface "port1"
FGT-HQ (to-Branch) # set ike-version 2
FGT-HQ (to-Branch) # set peertype any
FGT-HQ (to-Branch) # set net-device disable
FGT-HQ (to-Branch) # set proposal aes256gcm-prfsha384 aes256-sha256
FGT-HQ (to-Branch) # set dhgrp 20 21
FGT-HQ (to-Branch) # set remote-gw 198.51.100.20
FGT-HQ (to-Branch) # set psksecret <key>
FGT-HQ (to-Branch) # set dpd on-demand
FGT-HQ (to-Branch) # next
FGT-HQ (phase1-interface) # end
```

| Setting | Notes |
|---------|-------|
| `type static \| dynamic \| ddns` | `dynamic` = dial-up server (remote peers with unknown IPs). `ddns` = peer identified by an FQDN. |
| `nattraversal enable \| disable \| forced` | Enabled by default. `forced` uses UDP-encapsulated ESP even without NAT. `keepalive` (NAT-T keepalive, default 10 s) keeps the NAT mapping alive. |
| `dpd disable \| on-idle \| on-demand` | **on-demand** (default) sends DPD probes only when outbound traffic gets no reply. on-idle also probes idle tunnels. `dpd-retrycount` (3) and `dpd-retryinterval` (20 s) set the timing. |
| `net-device` | Dial-up only. `enable` creates a separate interface per connected client. `disable` (the default) keeps one interface. |
| `add-route` | Dial-up: install a route to each client's selector or assigned IP while the tunnel is up |
| `mode-cfg` | Dial-up: push IP, DNS and split-tunnel networks to clients |
| `local-gw` | Source the tunnel from a secondary IP instead of the interface's primary address |

### 8.0 change: recommended proposals only

FortiOS 8.0 shows only **recommended** IKE proposals in the CLI by default (`ike-proposal-visibility recommended`, under `config system settings`). Encryption options are AES-128/192/256-CBC, AES-128/256-GCM and ChaCha20-Poly1305, integrity options are SHA-256/384/512, and DH groups 15–21 and 28–32 are offered. DES, 3DES, MD5, SHA-1, ARIA, SEED and SM4/SM3 disappear from the lists, and **DH groups 1, 2, 5, 14 and 27 are hidden.** The change applies to IKEv1 and IKEv2. To configure a legacy peer that needs them, change visibility:

```text
FGT-HQ # config system settings
FGT-HQ (settings) # set ike-proposal-visibility all
FGT-HQ (settings) # end
```

> **Watch out:** A Cisco or third-party peer still using DH group 14 or SHA-1 won't match the FortiGate's default proposals. On 8.0 you can't even select those values until `ike-proposal-visibility` is set to `all`.

## Lab it yourself

The FortiGate-VM permanent trial supports **low encryption only** (Fortinet's licensing docs). In practice, Fortinet support staff and lab users report that IPsec on the trial is limited to DES, so AES proposals are not offered and won't negotiate. Treat that as observed behaviour rather than a documented rule, and check what your own VM offers. On 8.0, DES is a non-recommended proposal, so first set `ike-proposal-visibility all`, then build a route-based IKEv2 tunnel to a strongSwan or Cisco IOS router using a DES proposal the peer accepts. Many current peers no longer offer or accept DES by default (newer Cisco IOS XE images and OpenSSL 3-based strongSwan builds may need extra steps or refuse it entirely). If yours does, run the lab between two trial VMs (each needs its own FortiCloud account). It fits the limits: 1 route to the remote LAN, 1 blackhole route, 2 policies. While it negotiates, run `diagnose debug application ike -1` and identify IKE_SA_INIT, IKE_AUTH and the child SA proposal in the output.

## Key takeaways

* IKE uses UDP 500, moving to UDP 4500 with NAT-T. ESP is IP protocol 50. FortiGate tunnels use ESP tunnel mode.
* Phase 1 = authenticated IKE SA (keylife 86400 s). Phase 2 = IPsec SAs per selector pair (43200 s, PFS on, replay detection on).
* IKEv1 has main mode (6 messages) and aggressive mode (3 messages, cleartext ID). IKEv2 uses IKE_SA_INIT + IKE_AUTH (4 messages) plus CREATE_CHILD_SA.
* IKEv2 is the FortiOS default. FortiClient 7.4.4 and later doesn't support IKEv1. Newer features need IKEv2.
* Route-based (phase1-interface) is the standard. It needs a route **and** a policy.
* Phase 1 up with phase 2 down points to selectors, phase 2 proposals or PFS.
* FortiOS 8.0 hides weak IKE proposals and DH groups 1, 2, 5, 14 and 27 unless `ike-proposal-visibility all` is set.
