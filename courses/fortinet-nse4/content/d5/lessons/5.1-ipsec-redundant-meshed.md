## Topologies: full mesh, partial mesh, hub and spoke

| Topology | Tunnels for *n* sites | Pros | Cons |
|----------|----------------------|------|------|
| **Full mesh** | n(n−1)/2 | Direct site-to-site paths. No single point of failure. | Configuration grows quadratically. Every site needs a stable public IP or dial-up roles. |
| **Hub and spoke** | n−1 | Simple. Central policy and inspection. Spokes can be dial-up. | Spoke-to-spoke traffic hairpins through the hub, which is a bottleneck and single point of failure unless you add a second hub |
| **Partial mesh / redundant hub-and-spoke** | Somewhere between | Critical sites get direct or redundant paths, the rest go through hubs | You must design routing carefully |

**ADVPN** (Auto-Discovery VPN) is Fortinet's answer to the hub-and-spoke versus mesh trade-off. Spokes keep permanent tunnels only to the hub(s). When spoke A sends traffic to spoke B through the hub, the hub tells them about each other (`auto-discovery-sender` on the hub, `auto-discovery-receiver` on the spokes), and A and B build a **shortcut tunnel** directly. It is normally combined with BGP and SD-WAN. At NSE 4 level, know what it solves. Detailed ADVPN design is NSE 7 material.

A *meshed or partially redundant* VPN between two FortiGates, the wording in the blueprint, applies the same idea at small scale: more than one tunnel between the same two sites, with routing deciding which one is used.

## Redundant VPN between two FortiGates

Picture FGT-HQ with two ISPs (port1, port2) and FGT-Branch with two ISPs (wan1, wan2). That gives four possible underlay paths. A **fully redundant** design builds a tunnel for each. A **partially redundant** design builds just two, for example HQ port1 ↔ Branch wan1 and HQ port2 ↔ Branch wan2.

A redundant design on each FortiGate needs:

1. **One phase 1 per path**, all route-based, each with **DPD enabled** so a dead path is detected. The phase 1 names must be unique.
2. **One phase 2 per phase 1.**
3. **One static route per tunnel** to the remote subnet, with distance and priority chosen to rank the tunnels.
4. **Policies for each tunnel interface**, both directions. To save policies, put the tunnels in a **zone** (or an SD-WAN zone) and write one pair of policies for the zone.
5. A **blackhole route** at distance 254 for the remote subnet, so traffic is dropped rather than leaked out the default route if every tunnel is down.

```text
FGT-HQ # show router static
config router static
    edit 10
        set dst 10.20.0.0 255.255.0.0
        set device "BR-p1"
    next
    edit 11
        set dst 10.20.0.0 255.255.0.0
        set priority 10
        set device "BR-p2"
    next
    edit 12
        set dst 10.20.0.0 255.255.0.0
        set blackhole enable
        set distance 254
    next
end
```

Both tunnel routes have distance 10, so both sit in the routing table. `BR-p1` (priority 1) is preferred. When DPD declares BR-p1's peer dead, the tunnel goes down, its route is withdrawn, and BR-p2 takes over. When BR-p1 recovers, its route comes back, and new sessions use it again.

> **Exam tip:** Should the backup tunnel route use a higher *distance* or a higher *priority*? Use **priority**, if traffic may arrive on the backup tunnel while the primary is still up. That happens when the remote FortiGate prefers a different tunnel, or during asymmetric failover. With a higher distance, the backup route isn't in the routing table, so packets arriving on the backup tunnel **fail the RPF check** and are dropped. With equal distance and a higher priority value, the route is present and RPF passes.

### Why DPD matters

A route-based tunnel's route stays installed as long as the tunnel interface is up. If the remote ISP fails silently, the IKE SA and IPsec SAs on your side live on until they expire, so traffic would keep blackholing into a dead tunnel. **DPD** detects the dead peer and tears the tunnel down:

| `dpd` | Behaviour | Typical use |
|-------|-----------|-------------|
| `on-demand` (default) | Probe only when outbound traffic is sent and no inbound traffic comes back | Most tunnels. Light on the IKE daemon. |
| `on-idle` | Also probe when the tunnel is idle | **Redundant/backup designs**, where you need to know a standby tunnel is dead *before* you fail over to it |
| `disable` | Never probe | Rarely appropriate |

`dpd-retryinterval` and `dpd-retrycount` control detection time. Fewer retries and shorter intervals mean faster failover but more false positives on lossy links.

### Backup tunnel with `monitor`

A CLI-only alternative keeps the backup phase 1 **down** until the primary fails:

```text
FGT-HQ # config vpn ipsec phase1-interface
FGT-HQ (phase1-interface) # edit "BR-backup"
FGT-HQ (BR-backup) # set interface "port2"
FGT-HQ (BR-backup) # set remote-gw 192.0.2.40
FGT-HQ (BR-backup) # set dpd on-demand
FGT-HQ (BR-backup) # set monitor "BR-p1"
FGT-HQ (BR-backup) # next
FGT-HQ (phase1-interface) # end
```

The monitoring tunnel comes up only when the monitored phase 1 goes down, and `monitor-hold-down-type` controls when it hands traffic back after the primary recovers. Use it with static (site-to-site) peers, and keep DPD enabled on the primary so a silent failure is actually detected.

### Dynamic routing and SD-WAN over redundant tunnels

Static priority works, but larger designs run **BGP** (or OSPF) across the tunnels. Each tunnel interface gets an IP, the protocol learns the remote subnets, and its own timers or BFD detect failures. Tunnel preference then comes from protocol attributes (OSPF cost, BGP local-preference or AS-path prepend) rather than static priority.

In current FortiOS designs, the redundant tunnels are usually **SD-WAN members in an overlay zone**. A performance SLA probes through each tunnel (`source` set on the member), and an SD-WAN rule (for example Lowest Cost (SLA)) picks the tunnel. That gives quality-based failover, not just dead/alive, and it uses the same tools as lesson 4.2, including the 8.0 option to steer overlays by underlay bandwidth utilization.

## Aggregate and redundant tunnels

FortiOS can also bundle several tunnels between the same two FortiGates into an **IPsec aggregate** (`config system ipsec-aggregate`). Phase 1s need `aggregate-member enable`, and the aggregate distributes traffic across members with an algorithm such as L3/L4 hashing, round-robin, weighted round-robin or redundant (active/standby). One interface carries traffic over several underlays. It is mostly used for bandwidth, and it requires FortiGate on both ends.

## HA and VPN

In an FGCP cluster, IKE and IPsec SAs are **synchronised** to the secondary, so after failover the new primary resumes the tunnels without negotiating new SAs. For IKEv2, FGCP also syncs the IKE message IDs, so the IKE SA stays up. Fortinet's HA guidance for uninterrupted IPsec traffic has two parts:

* `set session-pickup enable` under `config system ha`, so the sessions *through* the tunnels survive the failover.
* `set ha-sync-esp-seqno enable` on each phase1-interface (the default), which keeps ESP sequence numbers ahead on the secondary so the peer's anti-replay check doesn't drop traffic after failover.

This works only for tunnels that terminate on the cluster's own interfaces, whose IP and virtual MAC move to the new primary. Make sure your peers point at the cluster's interface IPs, not at a unit's HA management address.

> **Watch out:** FGCP and FGSP are different. FGCP syncs IPsec SAs within a cluster as part of normal operation. IPsec sync between FGSP peers is a separate feature with its own configuration (8.0.1 extends it to FGSP member join and failover). Don't mix the two up in exam answers.

## Use cases

* **Two ISPs at each site, simplest robust design.** Two tunnels (partial redundancy), equal distance, priority 1 and 10, DPD on-idle, blackhole at 254, tunnels in a zone so one policy pair covers both.
* **Branch must use the cheapest tunnel that still meets voice quality.** Make the tunnels SD-WAN overlay members and use a performance SLA through each tunnel with a Lowest Cost (SLA) rule.
* **Fifty branches with occasional branch-to-branch traffic.** Hub and spoke with ADVPN shortcuts, not a full mesh, which would need 1,225 tunnels.

## Lab it yourself

With two FortiGate-VM trials (two FortiCloud accounts), give each port1 and port2 as WANs and port3 as the LAN.

1. Build two tunnels between port1↔port1 and port2↔port2 with `dpd on-idle`. That is 2 tunnel routes plus a blackhole route: exactly 3 routes. Put both tunnels in a zone and use 2 policies (LAN↔zone).
2. Give the second tunnel route `priority 10`. Ping across while you shut the port1 link on one side. Time the failover against your DPD settings.
3. Change the backup route to `distance 20` instead. Then, on the far side, give the backup tunnel's route the better (lower) priority so that side sends into the backup tunnel. Start a new session from the far side and watch `diagnose debug flow` on the near side report the RPF failure.

## Key takeaways

* A redundant VPN uses one phase 1/phase 2 per path, one route per tunnel ranked by distance or priority, policies per tunnel or zone, and a blackhole at 254.
* Prefer **equal distance with different priority** for backup tunnel routes, so traffic arriving on the backup tunnel passes RPF.
* DPD is what turns a silent path failure into route withdrawal. `on-idle` suits standby tunnels.
* `monitor <phase1>` keeps a backup phase 1 down until the primary fails.
* Full mesh needs n(n−1)/2 tunnels. Hub and spoke with ADVPN shortcuts scales far better.
* Modern designs put the redundant tunnels in an SD-WAN overlay zone and steer by SLA.
