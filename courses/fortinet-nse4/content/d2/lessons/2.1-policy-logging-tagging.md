## Traffic logging is set per policy

Each firewall policy decides whether it writes **traffic logs** (type `traffic`, subtype `forward` for transit traffic). The CLI attribute is `logtraffic`:

| GUI label (accept policy) | CLI | What gets logged |
|---|---|---|
| **Security Events** (default) | `set logtraffic utm` | Only sessions that trigger a security profile event (AV, web filter, IPS, application control, and so on). Clean sessions produce no traffic log |
| **All Sessions** | `set logtraffic all` | Every session the policy accepts, plus the security events |
| Disabled | `set logtraffic disable` | No traffic logs from this policy. Security profile logs are still controlled by the profiles themselves |

For a **deny** policy, the GUI option is **Log Violation Traffic**, which maps to `logtraffic all`. The implicit deny (policy 0) is separate. It is enabled with `set fwpolicy-implicit-log enable` under `config log setting`, or from the implicit deny entry in the GUI. It is off by default.

Two more options matter:

- `set logtraffic-start enable` also writes a log when the session **starts**, not only when it closes. It is useful for long-lived sessions. It doubles the log volume, and it is `disable` by default.
- Long sessions also produce periodic **statistics** logs, so a multi-hour session doesn't stay invisible until it closes.

Where the logs go (memory or disk, FortiAnalyzer, FortiGate Cloud, syslog) is set under `config log ...`. That is lesson 1.2. The per-policy setting only decides *whether* the policy generates the log.

> **Real world:** When the Security Fabric is enabled, the GUI can lock policy logging to *All Sessions*. Fabric topology and FortiView rely on full session logs. If a policy's *Security Events* choice is greyed out, check the Fabric settings before you suspect a bug.

> **Watch out:** "I see web filter logs but no traffic logs for allowed sessions" is the expected result with the default `logtraffic utm`. Users who just browse without hitting a block or warning produce no traffic log. Use `all` when you need an audit trail of permitted sessions, such as compliance logs or troubleshooting.

## Reading a forward traffic log

A traffic log is a list of key=value fields. This is a typical accepted, source-NATed session:

```text
date=2026-10-27 time=09:14:52 logid="0000000013" type="traffic" subtype="forward" level="notice" vd="root" srcip=10.0.1.25 srcport=50433 srcintf="port2" srcintfrole="lan" dstip=198.51.100.80 dstport=443 dstintf="port1" dstintfrole="wan" sessionid=1772164 proto=6 action="close" policyid=10 policytype="policy" policyname="LAN-to-Internet" user="jsmith" group="Sales" authserver="TRAINING-AD" service="HTTPS" trandisp="snat" transip=203.0.113.2 transport=61002 duration=15 sentbyte=2210 rcvdbyte=10840 sentpkt=14 rcvdpkt=16 appcat="unscanned"
```

| Field | Meaning |
|---|---|
| `logid="0000000013"` | Forward traffic log message (ID 13 = end of a forwarded session) |
| `action` | `close` / `timeout` / `client-rst` / `server-rst` for accepted sessions that ended. `deny` for blocked sessions |
| `policyid` | The **policy ID** that matched. `0` means the implicit deny |
| `trandisp` | NAT disposition: `snat`, `dnat`, `snat+dnat` or `noop` |
| `transip` / `transport` | Translated **source** IP and port (SNAT) |
| `tranip` / `tranport` | Translated **destination** IP and port (DNAT/VIP) |
| `user`, `group`, `authserver` | Present when the session belongs to an authenticated user |
| `sentbyte` / `rcvdbyte` | Bytes from the originator's point of view |
| `appcat="unscanned"` | No application control profile examined the session |

A session blocked by the implicit deny looks like this (when implicit logging is enabled):

```text
date=2026-10-27 time=09:20:03 logid="0000000013" type="traffic" subtype="forward" level="notice" vd="root" srcip=10.0.1.40 srcport=41822 srcintf="port2" srcintfrole="lan" dstip=10.0.2.10 dstport=22 dstintf="port3" dstintfrole="dmz" sessionid=1772201 proto=6 action="deny" policyid=0 policytype="policy" service="SSH" trandisp="noop" duration=0 sentbyte=0 rcvdbyte=0 sentpkt=0 appcat="unscanned"
```

Traffic addressed to the FortiGate itself (for example SSH to its WAN IP) is **local** traffic. It is logged as subtype `local` and governed by local-in policies and `allowaccess`, not by forward policies.

> **Exam tip:** If an exhibit shows `action="deny" policyid=0`, the traffic matched **no** policy. The fix is a missing or misordered policy, or a wrong interface or route. It is not a security profile setting.

## FortiOS 8.0: custom tags for addresses and policies

FortiOS 8.0.0 adds **custom tags**, a lightweight way to label objects and policies so a large rule base can be filtered and read at a glance. Tags can be applied to:

- Firewall addresses and address groups (IPv4 and IPv6)
- Proxy addresses and proxy address groups
- Multicast addresses
- Firewall policies, NGFW security policies, multicast policies, DoS policies, local-in policies, proxy policies
- Central SNAT map entries

Create a tag (GUI: **Policy & Objects > Tags**):

```text
FGT-HQ # config firewall custom-tag
FGT-HQ (custom-tag) # edit "PCI"
FGT-HQ (PCI) # set abbreviation "PCI"
FGT-HQ (PCI) # set color 6
FGT-HQ (PCI) # set comment "Cardholder data environment"
FGT-HQ (PCI) # end
```

- `abbreviation` is a short label of uppercase letters and digits shown in lists. The 8.0 docs disagree on its maximum length (four characters in the CLI description, three in the GUI description), so three characters is the safe choice.
- `color` is a GUI colour index from **0 to 32**, default **1**.

Apply it with `set custom-tags`:

```text
FGT-HQ # config firewall address
FGT-HQ (address) # edit "POS-10.0.5.0"
FGT-HQ (POS-10.0.5.0) # set subnet 10.0.5.0 255.255.255.0
FGT-HQ (POS-10.0.5.0) # set custom-tags "PCI"
FGT-HQ (POS-10.0.5.0) # end
FGT-HQ # config firewall policy
FGT-HQ (policy) # edit 30
FGT-HQ (30) # set custom-tags "PCI"
FGT-HQ (30) # end
```

In the GUI, **policy tagging is hidden by default**. Enable it under **System > Feature Visibility**. The policy list can then show a Tags column and filter on tags in the search bar. The address list can display *All tags* or *First tag only* instead of the default coloured icon.

### Dynamic tag address groups

The bigger change is a new **address group type**. `config firewall addrgrp` now has `set type`:

| `type` | Membership |
|---|---|
| `default` | Normal group. Members are listed by name, and an address can be in many groups |
| `folder` | Organising folder. Its members cannot belong to any other group |
| `dynamic-tag` | **Members are every address that carries any of the configured tags.** No member list |

```text
FGT-HQ # config firewall addrgrp
FGT-HQ (addrgrp) # edit "GRP-PCI"
FGT-HQ (GRP-PCI) # set type dynamic-tag
FGT-HQ (GRP-PCI) # set custom-tags "PCI"
FGT-HQ (GRP-PCI) # end
```

Use `GRP-PCI` in a policy. When someone later creates another address tagged `PCI`, it joins `GRP-PCI` automatically and the policy covers it **with no policy edit**. Tagging an object becomes the change control, instead of editing group members or policies.

> **Exam tip:** Know the three group types and that `custom-tags` on an address group is available **only** when `type` is `dynamic-tag`. "Add the new server to the policy without editing the policy or the group" is the dynamic tag group use case.

### Colours and older organisation features

These existed before 8.0 and still matter:

- **Object colours**: addresses, services and VIPs have `set color 0–32`. The GUI shows them while `gui-object-colors` is enabled (the default).
- **Comments and names**: `set name` and `set comments` on policies. `log-policy-comment enable` under `config log setting` copies the policy comment into traffic logs.
- **Dynamic addresses from fabric connectors and EMS**: `config firewall address` with `set type dynamic` resolves membership from an SDN connector or FortiClient EMS (`sub-type ems-tag`, used in ZTNA tags). These are *dynamic addresses fed by external systems*. Custom tags are *administrator labels*. Don't mix them up.

## Use cases

- **Compliance scoping:** tag every PCI address and policy `PCI`, filter the policy list by that tag for the auditor, and log those policies with `logtraffic all`.
- **Self-maintaining server groups:** build a `dynamic-tag` group "WEB-SERVERS". New servers get the tag at creation and are immediately covered by the existing DMZ policy.
- **Troubleshooting a denied flow:** enable `fwpolicy-implicit-log`, reproduce the problem, and filter the forward log on `policyid=0` and the source IP.
- **Volume control:** keep `utm` on high-volume internet policies and use `all` on internal segmentation policies where you need full visibility.

## Lab it yourself

1. On your outbound policy, set `logtraffic all` and browse from the LAN host. In **Log & Report > Forward Traffic**, find `trandisp=snat` and the `transip` field. Switch to `utm` and confirm clean sessions stop appearing.
2. Enable `fwpolicy-implicit-log`, try a connection that no policy allows (for example, from the LAN host to a host on `port3` when no `port2` → `port3` policy exists), and find the `policyid=0` entry.
3. Create two tags, tag two host addresses, build a `dynamic-tag` group from one tag and use it as the source of a policy. Create a third address with that tag and confirm in the GUI that the group now includes it.
4. Enable policy tags in Feature Visibility and filter the policy list by tag.

## Key takeaways

- `logtraffic utm` (Security Events) is the default and logs only sessions with security events. `all` logs every accepted session. `disable` turns traffic logging off.
- Implicit deny logging is off by default. Enable it with `fwpolicy-implicit-log` under `config log setting`.
- In traffic logs, `policyid` is the policy **ID**, `trandisp` shows the NAT type, `transip` is the translated source and `tranip` the translated destination.
- FortiOS 8.0 adds `config firewall custom-tag` (abbreviation, comment, colour 0–32) and `set custom-tags` on addresses, groups, many policy types and central SNAT entries.
- Address groups now have `type default | folder | dynamic-tag`. Dynamic tag groups pick up any address carrying the tag, with no policy change.
- Policy tagging is hidden in the GUI until it is enabled in Feature Visibility.
