## Active and passive authentication

| | Active authentication | Passive authentication |
|---|---|---|
| How the user is identified | FortiGate **prompts** the user (login page or protocol challenge) and checks the credentials | FortiGate **learns** the user-to-IP mapping from another system. No prompt |
| Methods | Local users, LDAP, RADIUS, TACACS+, SAML | FSSO (Windows AD logons), RSSO (RADIUS accounting) |
| User experience | A login page appears in the browser (or an FTP/Telnet challenge) | Transparent |
| Policy-matching behaviour | Unauthenticated traffic can **fall through** to later policies (default) | The user is already known, so the **first** policy matching that user's group applies |

Many networks use both. FSSO identifies domain PCs silently, and an active-authentication policy below it catches devices FSSO can't identify (BYOD, non-domain Linux).

## Building an identity-based policy

A policy becomes identity-based when its source includes users or groups. The address is still required:

```text
FGT-HQ # config firewall policy
FGT-HQ (policy) # edit 40
FGT-HQ (40) # set name "Sales-Web"
FGT-HQ (40) # set srcintf "port2"
FGT-HQ (40) # set dstintf "port1"
FGT-HQ (40) # set action accept
FGT-HQ (40) # set srcaddr "LAN-10.0.1.0"
FGT-HQ (40) # set dstaddr "all"
FGT-HQ (40) # set schedule "always"
FGT-HQ (40) # set service "HTTP" "HTTPS"
FGT-HQ (40) # set groups "Sales-Users"
FGT-HQ (40) # set nat enable
FGT-HQ (40) # end
```

The source matches only when **both** the address and the user/group condition are true. The user must be authenticated, from an IP inside `LAN-10.0.1.0`, and a member of `Sales-Users`.

## How active authentication is triggered

When a session from an unauthenticated IP matches an identity-based policy, FortiGate needs a protocol it can intercept to show a login prompt. The protocols are set in `config user setting` → `set auth-type` (any of `http`, `https`, `ftp`, `telnet`).

- **HTTP:** FortiGate intercepts the request and redirects the browser to its authentication page. With `auth-secure-http enable` (the 8.0 default), the redirect goes to the HTTPS login page.
- **HTTPS:** the user is redirected to the FortiGate's HTTPS authentication page. The certificate is `auth-cert`, so use a certificate the clients trust to avoid warnings.
- **FTP/Telnet:** FortiGate challenges inside the protocol itself.
- The login pages listen on `auth-http-port` **1000** and `auth-https-port` **1003** (`config system global`).

Other traffic, such as DNS, ICMP or proprietary applications, **cannot trigger** a prompt. It is allowed only after the user has authenticated through one of the supported protocols.

> **Exam tip:** Browsers need **DNS** before they send any HTTP request. If the only policy allowing DNS from the LAN requires authentication, users never get the login page. Allow DNS in a policy **without** authentication (to your DNS servers), placed so it matches.

## Fall-through: `auth-on-demand`

```text
FGT-HQ # config user setting
FGT-HQ (setting) # set auth-on-demand implicitly
FGT-HQ (setting) # end
```

| `auth-on-demand` | Behaviour |
|---|---|
| `implicitly` (**default**) | If an unauthenticated session matches an identity policy, FortiGate keeps checking **lower policies**. If a later policy without authentication matches, the traffic uses it and **no prompt appears**. The prompt is triggered only when no non-authenticated policy would match |
| `always` | The first matching identity policy **forces** the login prompt, even if an open policy exists below it |

Example with the default:

```text
Seq 1: port2 -> port1  src LAN + group Sales-Users  service ALL  accept
Seq 2: port2 -> port1  src LAN                      service ALL  accept
```

An unauthenticated user matches nothing in seq 1 and falls through to seq 2. They browse without ever being asked to log in. To force authentication, remove or narrow seq 2, or set `auth-on-demand always`.

> **Watch out:** `auth-on-demand always` can break **passive** authentication. FSSO and RSSO users may no longer fall through between passive policies. In a debug flow this shows up as `__iprope_user_identity_check` returning `ret-stop`. Fortinet's guidance is to keep `implicitly` where FSSO is used.

Passive users behave differently. An FSSO user is already in FortiGate's user table, so their traffic matches the **first** policy whose group they belong to, from the top down, like any other match criterion.

## Captive portal on an interface

Instead of relying on policies to trigger the prompt, you can require authentication for **everything** arriving on an interface:

```text
FGT-HQ # config system interface
FGT-HQ (interface) # edit "port2"
FGT-HQ (port2) # set security-mode captive-portal
FGT-HQ (port2) # set security-groups "Sales-Users" "Guests"
FGT-HQ (port2) # end
```

- Every user on that interface must log in before any policy accepts their traffic.
- `security-exempt-list` lets devices that can't authenticate (printers, phones) skip the portal. A policy can also be exempted with `set captive-portal-exempt enable`.
- `security-redirect-url` sends users to a page after login.
- `auth-portal-timeout` (default 3 minutes, `config user setting`) is how long a captive portal user has before they must authenticate again on the portal.

## Timeouts and lockout

| Setting (`config user setting`) | Default | Meaning |
|---|---|---|
| `auth-timeout` | **5** minutes | How long an authentication lasts (1–1440) |
| `auth-timeout-type` | `idle-timeout` | `idle-timeout`: the timer resets while traffic flows. `hard-timeout`: absolute from login. `new-session`: existing sessions continue, but new ones need re-authentication after expiry |
| `auth-lockout-threshold` | 3 | Failed attempts before lockout |
| `auth-lockout-duration` | 0 | Lockout period in seconds |

- The GUI (**User & Authentication > Authentication Settings**) sets only the idle timeout. The hard and new-session types are CLI only.
- A user group can override the timeout with `set authtimeout` (0 = use the global value).
- `config system global` → `set auth-keepalive enable` keeps idle authenticated sessions from timing out. It is off by default.

## Monitoring firewall users

In FortiOS 8.0 the monitor is at **Dashboard > Assets and Identities > Firewall Users**:

- Lists authenticated firewall users (IP, user, group, method, duration, traffic).
- **Show all FSSO Logons** (top right) adds FSSO-learned users.
- The **Proxy** view shows users authenticated through ZTNA or explicit proxy.
- Select a user and click **Deauthenticate** (or right-click) to force a new login.

In the CLI:

```text
FGT-HQ # diagnose firewall auth list
10.0.1.25, jsmith
	type: fw, id: 0, duration: 184, idled: 12
	server: TRAINING-AD
	packets: in 1442 out 1189, bytes: in 1873320 out 166208
	group_id: 3
	group_name: Sales-Users

----- 1 listed, 0 filtered ------
```

`type: fw` is a firewall (active) authentication (FSSO-learned users also appear in this list, as `type: fsso`), `server` is the remote server that validated the credentials, and `group_name` is the FortiGate user group. To remove one user:

```text
FGT-HQ # diagnose firewall auth filter user jsmith
FGT-HQ # diagnose firewall auth clear
FGT-HQ # diagnose firewall auth filter clear
```

Deauthenticating a user doesn't delete their existing sessions. Clear those separately if access must stop immediately. Proxy users are listed with `diagnose wad user list`. Authentication events (login, logout, failure) appear in **Log & Report > System Events > User Events**, and traffic logs carry `user=`, `group=` and `authserver=`.

## Use cases

- **AD users browse, guests log in:** FSSO policy for domain groups at the top, an active-auth policy for the `Guests` group below it, and nothing open below that.
- **Kiosk VLAN:** captive portal on the VLAN interface, `hard-timeout` of 60 minutes.
- **Privileged segment:** policy to the server VLAN requires the `NetAdmins` group (RADIUS + FortiToken). `auth-on-demand always` in a VDOM without FSSO.

## Lab it yourself

1. Create a local user and a firewall group. Add the group to your outbound policy, and keep a separate policy allowing DNS to your resolver above it (you have 3 policies).
2. Browse to an `http://` site from the LAN host. You are redirected to the FortiGate login page on port 1003. Log in and check `diagnose firewall auth list` and the Firewall Users monitor.
3. Add a second open policy below the identity policy and watch the prompt disappear (`implicitly`). Set `auth-on-demand always` and test again.
4. Set `auth-timeout 1` with `hard-timeout` and observe re-prompting.

## Key takeaways

- **Active** authentication prompts (local, LDAP, RADIUS, TACACS+, SAML). **Passive** authentication learns identity silently (FSSO, RSSO).
- Only HTTP, HTTPS, FTP and Telnet can trigger the prompt (ports 1000/1003 for the HTTP/HTTPS pages). Allow **DNS** without authentication first.
- `auth-on-demand implicitly` (default) lets unauthenticated traffic fall through to lower non-auth policies. `always` forces the prompt but can break FSSO.
- Passive users match the first policy for their group. Put FSSO policies above active-auth fallbacks.
- `auth-timeout` defaults to 5 minutes, idle type. Hard and new-session types are CLI only. Groups can override with `authtimeout`.
- Monitor at **Dashboard > Assets and Identities > Firewall Users** (8.0) or `diagnose firewall auth list`. Deauthenticating doesn't clear existing sessions.
