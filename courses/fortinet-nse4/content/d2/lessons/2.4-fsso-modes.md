## What FSSO solves

**Fortinet Single Sign-On (FSSO)** gives FortiGate a user-to-IP table for Windows Active Directory users **without prompting them**. A user logs on to the domain once, and FortiGate applies group-based policies to that PC's traffic. FSSO is **passive** authentication. FortiGate never sees a password. It trusts logon events reported by an agent (or that it polls itself) and maps them to the workstation's IP address.

The information flow:

1. The user logs on to a domain workstation, and a domain controller records the logon.
2. An FSSO component learns about the logon: *user, domain, workstation name*.
3. The **collector agent** resolves the workstation name to an IP address through **DNS** and looks up the user's group memberships.
4. The collector agent sends *IP, user, groups* to the FortiGate (TCP **8000**, or **8001** with SSL).
5. FortiGate matches the IP's traffic against policies that use **FSSO groups**.

## The components

| Component | Where it runs | Job |
|---|---|---|
| **DC agent** (`dcagent.dll`) | On **every** domain controller you want to monitor. Installing it requires a DC reboot | Captures logon events as they happen and sends them to the collector agent over UDP **8002** (TCP **8003** when secure) |
| **Collector agent (CA)** | Windows service on a member server or a DC. FortiAuthenticator can also act as the collector | Receives events from DC agents or polls the DCs itself, resolves workstation IPs, checks group membership, verifies workstations, and serves the FortiGate(s) |
| **FortiGate** | – | Connects to the CA as a client, receives logon lists and group lists, and enforces policy |

## The deployment modes

### 1. DC agent mode

DC agents on every DC push logon events to the collector agent.

- **Most accurate and scalable.** Events arrive in near real time, and no logon is missed because of polling gaps.
- Requires software on every DC, plus a reboot of each DC. Every DC that can authenticate users must have the agent. A DC without it is a blind spot.
- The collector agent still does the DNS lookups, workstation checks and group lookups.

### 2. Collector agent polling mode (no DC agents)

The collector agent polls the DCs itself. Nothing is installed on the DCs. Three polling methods:

| Method | How | Trade-off |
|---|---|---|
| **NetAPI** | Calls the Windows `NetSessionEnum` API on each DC | Fast and light. It sees sessions, not logon events, so short sessions can be missed under load |
| **WinSecLog** | Reads the DCs' **Security event logs** for logon events | Catches all logons, as long as auditing is enabled. Slower on busy DCs because it reads more data |
| **WMI** | Subscribes to the DC's event logs through WMI | Less network traffic than WinSecLog. Needs WMI permissions on the DCs |

Polling mode is easier to deploy (no DC changes) and is common in small and medium networks. It needs a service account with rights to read event logs or sessions on each DC.

### 3. Agentless polling (FortiGate polls the DC)

FortiGate itself polls the domain controllers. There is no collector agent and no DC agent. GUI: **Security Fabric > External Connectors > Create New > Poll Active Directory Server**.

```text
FGT-HQ # config user fsso-polling
FGT-HQ (fsso-polling) # edit 1
FGT-HQ (1) # set server "10.0.1.5"
FGT-HQ (1) # set user "svc-fsso"
FGT-HQ (1) # set password <password>
FGT-HQ (1) # set default-domain "TRAINING"
FGT-HQ (1) # set ldap-server "TRAINING-AD"
FGT-HQ (1) # end
```

- FortiGate reads the security event log over SMB, **TCP 445**. `polling-frequency` defaults to **10 seconds** (range 1–30). `logon-history` defaults to 8 hours.
- Groups come from the referenced **LDAP server**.
- Limitations: WinSecLog-style polling only, **no workstation verification**, no NTLM support, it can miss logons during heavy bursts, it handles nested groups less well, and it uses FortiGate CPU. Fortinet positions it for small environments.
- `smbv1` is `disable` by default. Enable it only if a legacy DC requires SMBv1.

### Comparing the modes

| | DC agent | CA polling | Agentless (FortiGate) |
|---|---|---|---|
| Software on DCs | Yes (plus reboot) | No | No |
| Collector agent | Yes | Yes | No |
| Real-time accuracy | Best | Good (method dependent) | Fair |
| Workstation verification | Yes (by CA) | Yes (by CA) | **No** |
| Scale | Large, multi-DC | Small to medium | Small |
| FortiGate load | Low | Low | Higher |

## Configuring FortiGate for a collector agent

GUI: **Security Fabric > External Connectors > Create New > FSSO Agent on Windows AD**.

```text
FGT-HQ # config user fsso
FGT-HQ (fsso) # edit "TRAINING-CA"
FGT-HQ (TRAINING-CA) # set server "10.0.1.6"
FGT-HQ (TRAINING-CA) # set password <ca-password>
FGT-HQ (TRAINING-CA) # end
```

| Attribute | Default | Notes |
|---|---|---|
| `server` / `server2` … | – | Collector agents (up to five). FortiGate stays connected to one active agent |
| `port` | **8000** | TCP port of the CA |
| `password` | – | Must match the password set on the collector agent for FortiGate connections |
| `ssl` | `disable` | Encrypts the CA connection (with `ssl-trusted-cert`) |
| `ldap-server` | – | Optional. Lets the FortiGate browse AD groups itself (the CA's *Advanced* access method) |
| `logon-timeout` | 5 min | How long logons are kept after the CA connection is lost |

### Choosing groups

FortiGate doesn't receive *every* AD group, only the **monitored** groups:

- With the collector agent's **Standard** access method, the group filter is defined on the collector agent, and groups use the Windows convention (`DOMAIN\Group`, for example `TRAINING\SALES`). Nested groups are not resolved, so the user must be a direct member of a monitored group. Since FortiOS 6.2 the GUI calls this group source **Collector Agent**.
- With the **Advanced** access method, groups use LDAP DN format (`CN=Sales,OU=Groups,DC=training,DC=lab`). The FortiGate can choose its own group filter through the `ldap-server` attribute (GUI group source **Local**, which requires the collector agent to run in Advanced mode), and nested groups are supported. The collector agent and the FortiGate must use matching modes, or the groups don't line up.

Groups received from the CA appear under `get user adgrp`. Use them in a policy either directly (`set fsso-groups "CN=SALES,OU=GROUPS,DC=TRAINING,DC=LAB"`) or through a FortiGate user group of type **FSSO**:

```text
FGT-HQ # config user group
FGT-HQ (group) # edit "FSSO-Sales"
FGT-HQ (FSSO-Sales) # set group-type fsso-service
FGT-HQ (FSSO-Sales) # set member "CN=SALES,OU=GROUPS,DC=TRAINING,DC=LAB"
FGT-HQ (FSSO-Sales) # end
```

A logged-on user who belongs to **no monitored group** is placed in the predefined **`SSO_Guest_Users`** group. You can write a policy for that group, for example internet-only access for domain users outside the monitored departments.

## Keeping the table accurate

The collector agent keeps the mapping current with several timers. All of them can be set in the CA's configuration.

- **Workstation verification:** the CA periodically contacts each workstation (remote registry or WMI over TCP 445/139/135) to confirm the user is still logged on. If the workstation answers with no user logged on, the entry is removed.
- **Dead entry timeout:** if the workstation can't be verified (firewall blocks it, PC is off), the CA keeps the entry until this timer expires. The default is **8 hours** (480 minutes).
- **IP change verification:** the CA re-resolves workstation names through DNS so DHCP address changes are picked up.
- **Ignore user list:** service accounts (backup agents, SCCM, `administrator`) whose logons would overwrite the real user on a workstation IP.

> **Exam tip:** FSSO is **IP-based**. One IP maps to one user. Anything that puts several users behind one IP (terminal servers, Citrix, NAT before the FortiGate) breaks plain FSSO. Fortinet's Terminal Server agent handles multi-user hosts.

## Use cases

- **Transparent group policies on the LAN:** FSSO groups `Sales`, `Engineering` and `IT`, each with its own policy and web filter, plus `SSO_Guest_Users` with restricted access.
- **Multi-site AD:** DC agents on all DCs, two collector agents for redundancy, and every FortiGate pointing to both (`server`, `server2`).
- **Small office without a spare server:** agentless polling against the single DC.

## Lab it yourself

Lab setup: FortiGate-VM `port2` → a Windows Server DC (10.0.1.5) and a domain-joined Windows client. Optional collector agent on the DC (polling mode avoids the DC agent reboot).

1. Start with **agentless**: create the Poll Active Directory Server connector, reference an LDAP server, pick a group, and log on at the client. Check `diagnose debug fsso-polling detail` and `diagnose debug authd fsso list`.
2. Install the collector agent in polling mode (WinSecLog), configure a password for FortiGate connections, and create a `config user fsso` entry. Compare how quickly logons appear.
3. Use the FSSO group in your outbound policy (3-policy limit: one FSSO policy, one DNS policy, one fallback).
4. Log on with an account in no monitored group and confirm it appears as `SSO_Guest_Users`.

## Key takeaways

- FSSO is passive, **IP-based** identity built from AD logon events. FortiGate never sees passwords.
- **DC agent mode**: an agent on every DC sends events to the CA (UDP 8002). Most accurate, but needs DC installs and reboots.
- **CA polling mode**: NetAPI, WinSecLog or WMI. Nothing on the DCs.
- **Agentless**: FortiGate polls DCs over TCP 445, every 10 seconds by default. No workstation check, and suited to small sites.
- FortiGate connects to the collector agent on TCP **8000** (`config user fsso`), and groups are filtered by the Standard or Advanced access method.
- Users in no monitored group land in **SSO_Guest_Users**. The dead entry timeout defaults to 8 hours.
