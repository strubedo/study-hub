## A method for FSSO login issues

Most FSSO problems look the same to the user: "I'm logged on but I get the wrong access (or none)." Work the chain in order, because each link depends on the one before it:

1. **Did AD record the logon?** Check the DC Security log for logon events (for example 4624, or the Kerberos 4768 on the DC that authenticated the user). If the DC never logged it, FSSO can't see it. Check the audit policy and which DC the client used (`echo %logonserver%`).
2. **Did the FSSO component see it?** DC agent installed on **that** DC? DC monitored in the collector agent's polling list? Look in *Show Logon Users* on the collector agent, or in `CollectorAgent.log` at debug level.
3. **Is the IP right?** The collector agent resolves the workstation name through **DNS**. Stale or missing DNS records (no dynamic DNS updates, scavenging off) map users to the wrong IP or to none.
4. **Is the user in a monitored group?** If not, the user arrives as `SSO_Guest_Users`. Nested groups need the Advanced access method.
5. **Is the FortiGate connected to the CA and receiving the list?** Password, TCP 8000 reachability, and the active CA.
6. **Does the policy match?** The FSSO group in the right policy, in the right order, and `auth-on-demand` not set to `always`.

## FortiGate commands

| Command | Use |
|---|---|
| `diagnose debug authd fsso server-status` | Which collector agent(s) the FortiGate is connected to |
| `diagnose debug authd fsso list` | The FSSO logon table on the FortiGate: IP, user, groups, workstation |
| `diagnose debug authd fsso refresh-logons` | Ask the CA to resend its full logon list |
| `diagnose debug authd fsso refresh-groups` | Ask the CA to resend the monitored group list |
| `diagnose debug authd fsso clear-logons` | Clear FSSO logons on the FortiGate (use a filter, or it clears everything) |
| `get user adgrp` | Groups received from the CA (or polled) |
| `execute fsso refresh` | Manually refresh FSSO and AD group information |
| `diagnose debug application authd 8256` + `diagnose debug enable` | Authentication daemon debug for FSSO communication |
| `diagnose debug fsso-polling detail` | Agentless mode: per-DC status, poll success/fail counters, latest logon timestamp |
| `diagnose debug fsso-polling refresh-user` | Agentless mode: refresh polled users |
| `diagnose debug application fssod -1`, `smbcd -1` | Agentless mode: polling and SMB debug |

Sample logon table:

```text
FGT-HQ # diagnose debug authd fsso list
----FSSO logons----
IP: 10.0.1.31  User: JSMITH  Groups: CN=SALES,OU=GROUPS,DC=TRAINING,DC=LAB  Workstation: WS-031.TRAINING.LAB MemberOf: FSSO-Sales
IP: 10.0.1.44  User: AKHAN  Groups: CN=ENGINEERING,OU=GROUPS,DC=TRAINING,DC=LAB  Workstation: WS-044.TRAINING.LAB MemberOf: FSSO-Engineering
Total number of logons listed: 2, filtered: 0
----end of FSSO logons----
```

`Groups` is what the CA reported. `MemberOf` is the **FortiGate-side** group the logon was mapped into (the FSSO user group, or the FSSO group itself when a policy uses it directly in `fsso-groups`), which is what policies match. A user with an AD group but an empty or unexpected `MemberOf` points to the FortiGate group configuration.

Sample agentless polling status:

```text
FGT-HQ # diagnose debug fsso-polling detail
AD Server Status(connected):
ID=1, name(10.0.1.5),ip=10.0.1.5,source(security),users(37)
port=auto username=svc-fsso
read log eof=1, latest logon timestamp: Tue Oct 27 08:41:12 2026
polling frequency: every 10 second(s) success(18211), fail(0)
LDAP query: success(52), fail(0)
LDAP max group query period(seconds): 0
LDAP status: connected
```

A `fail` counter that keeps growing points to SMB connectivity (TCP 445), the polling account's rights or password, or an overloaded DC. If `latest logon timestamp` stops moving, the FortiGate isn't reading new events. If logons are read but users don't show up, check the group filter and the LDAP status.

## Common causes and fixes

| Symptom | Likely cause | Fix |
|---|---|---|
| User never appears on the FortiGate | Logon handled by a DC without a DC agent, or a DC missing from the CA polling list | Install the DC agent on every DC, or add the DC to polling |
| User appears with the **wrong IP** | Stale DNS for the workstation | Fix dynamic DNS and scavenging, and check the CA's IP change verification |
| User is replaced by `svcbackup` or `administrator` | Service account logons on the same workstation overwrite the mapping | Add those accounts to the CA's **ignore user list** |
| Many users share one IP (RDS/Citrix) | FSSO is one user per IP | Deploy the Terminal Server agent |
| User shows `SSO_Guest_Users` | Not in a monitored group | Add the group to the CA or FortiGate group filter |
| Users drop out after some time on a locked-down network | Workstation verification blocked (TCP 445/139/135) | Open the ports from the CA, or accept the dead entry timeout behaviour |
| FortiGate shows the CA disconnected | Wrong password, TCP 8000 blocked, or the CA service stopped | Match the passwords and check Windows Firewall on the CA |
| FSSO users prompted or not matching after a change | `auth-on-demand always` | Set it back to `implicitly` |

> **Exam tip:** UDP 8002 (DC agent → CA) can't be tested with a TCP tool such as `execute telnet`. TCP 8000 (FortiGate → CA) can. Exam questions like to ask which link to test from where.

## Positioning FSSO against ZTNA identity

FSSO and ZTNA both identify users, but they rest on different trust models:

| | FSSO | ZTNA (FortiGate + FortiClient EMS) |
|---|---|---|
| Identity is bound to | An **IP address**, learned from AD logon events | The **device and user in each session**. The client certificate from EMS proves the device, and the user authenticates (LDAP, SAML and others) |
| Device posture | None | EMS **ZTNA tags** (OS patch level, AV status, domain membership and so on) evaluated in policy |
| Location | Works on-net with AD visibility | Works the same on-net and off-net |
| Continuous checking | The mapping persists until logoff, a timer, or an overwrite | Tags are updated continuously, and access is re-evaluated when posture changes |
| User experience | Fully transparent | Transparent for posture. User authentication may prompt or use SSO (SAML) |
| Weak spots | Shared IPs, NAT, stale DNS, spoofed IPs | Needs FortiClient/EMS deployment and certificates |
| Policy objects | `fsso-groups`, FSSO user groups | `ztna-ems-tag`, ZTNA servers and rules, groups from LDAP/SAML (FortiOS 8.0 adds SCIM group integration) |

Positioning in short:

- **FSSO** is the practical way to get transparent, group-based policy for **existing on-prem Windows domains**, especially for internet access control and network segmentation.
- **ZTNA** is the zero-trust model: per-application access verified for **user plus device posture**, independent of IP and location.
- Most organisations run both during a transition. Rules on internal segments can combine an FSSO group with an EMS tag condition.

## FortiIdentity Cloud (FIC) and SSO

**FortiIdentity Cloud** is the new name (effective August 2025) of **FortiToken Cloud**. Existing tokens, licences and integrations kept working. The portal URL moved from `ftc.fortinet.com` to `fic.fortinet.com`, and the old URLs redirect. FIC is Fortinet's cloud identity service:

- **MFA**: FortiToken Mobile push or OTP, email and SMS for FortiGate users and admins (the FortiOS CLI keyword is still `fortitoken-cloud`).
- **Identity provider (IdP)**: a SAML and OIDC IdP for applications, or an **IdP proxy** that forwards authentication to an upstream IdP such as Microsoft Entra ID.

### FortiOS 8.0: SSO integration with FortiIdentity Cloud

FortiOS 8.0 adds a **FortiIdentity Cloud** type to the FortiGate SSO (SAML SP) configuration. GUI: **User & Authentication > Single Sign-On > Create New**, *Identity Provider Configuration* type **FortiIdentity Cloud**.

```text
FGT-HQ # config user saml
FGT-HQ (saml) # edit "fic-sso"
FGT-HQ (fic-sso) # set type fortiidentity-cloud
FGT-HQ (fic-sso) # set idp-cert "FIC_Default_Cert"
FGT-HQ (fic-sso) # set user-name "username"
FGT-HQ (fic-sso) # set group-name "group"
FGT-HQ (fic-sso) # set service-provider-address "203.0.113.2:8443"
FGT-HQ (fic-sso) # set user-source "training-entra"
FGT-HQ (fic-sso) # end
```

What the integration automates:

1. FortiGate pulls the existing **realms, user sources and certificates** from FIC, so the GUI fields are prefilled.
2. When you save, FIC automatically **creates an SSO application** with the same name.
3. SP and IdP **metadata is exchanged in the background**, and the FIC certificate is imported on the FortiGate as a remote certificate. Entity ID, SSO URL and logout URLs are filled in automatically (`show user saml` displays them).
4. The SSO server is then used by **remote access VPN, ZTNA** and other services that authenticate users. The 8.0 VPN wizard can use FIC settings for remote access VPN with standalone FortiClient, and the SAML settings it creates are pushed to FIC.

Prerequisites: FortiIdentity Cloud must already be set up for the FortiGate, with the realm, user source and certificate that the FortiGate retrieves. FortiGates with **FortiCare Premium or Elite** include three free FIC seats, and more seats can be bought. `type` defaults to `custom` (manual SAML setup with any IdP).

> **Watch out:** FIC SSO is **SAML**. The user is redirected to the IdP and authenticates there, possibly with MFA. It is not passive like FSSO. Don't answer "FortiIdentity Cloud" when a question asks how to identify domain users transparently from AD logons. That is FSSO.

## Use cases

- **"Users can browse but get the wrong web filter":** `diagnose debug authd fsso list` shows `MemberOf: SSO_Guest_Users`. The group isn't monitored. Fix the CA group filter.
- **"One user's identity keeps changing to `svc-sccm`":** add the account to the ignore user list.
- **Remote workforce SSO:** FortiClient remote access VPN authenticating through the FIC SSO type, with FIC proxying to Entra ID and enforcing FortiToken Mobile push.
- **Zero-trust roadmap:** keep FSSO for LAN internet policies and move application access to ZTNA with EMS tags.

## Lab it yourself

1. With your FSSO lab running, run `diagnose debug authd fsso list` and compare `Groups` and `MemberOf`.
2. Stop the collector agent service and watch the connector status. Logons are kept for `logon-timeout` (5 minutes by default), then removed.
3. Log on to the client with a service account, then as the real user, and watch the mapping change. Add the service account to the ignore list and repeat.
4. Delete the client's DNS record on the DC and log on again. In the CA log, find the lookup failure.
5. FIC needs FIC seats (included with FortiCare Premium/Elite, or bought), which the free VM trial doesn't have. On the free VM you can still explore the **Single Sign-On** page and the `type` options in `config user saml`.

## Key takeaways

- Troubleshoot FSSO in order: AD logon event → agent/CA sees it → DNS gives the right IP → monitored group → FortiGate connected → policy match.
- `diagnose debug authd fsso list` shows the logon table. `MemberOf` is the FortiGate group the policy matches.
- Agentless mode: `diagnose debug fsso-polling detail` (success/fail counters, latest logon timestamp).
- Common fixes: DC agent on every DC, clean DNS, an ignore list for service accounts, the TS agent for shared hosts, and `auth-on-demand implicitly`.
- FSSO is IP-bound, transparent AD identity. ZTNA is per-session user plus device posture (EMS tags) on- or off-net.
- FortiIdentity Cloud = renamed FortiToken Cloud (MFA plus SAML/OIDC IdP and IdP proxy). FortiOS 8.0 adds `config user saml` → `set type fortiidentity-cloud`, which auto-creates the SSO app and exchanges metadata.
