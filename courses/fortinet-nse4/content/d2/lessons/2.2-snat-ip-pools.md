## Two ways to configure source NAT

FortiGate has two NAT models, and a VDOM uses only one of them at a time:

| | Policy NAT (default) | Central NAT |
|---|---|---|
| Enabled by | Default behaviour (`central-nat disable`) | `config system settings` → `set central-nat enable`, or implicitly in NGFW **policy-based** mode |
| Where SNAT is configured | In each firewall policy: `set nat enable` (+ optional IP pool) | In the **central SNAT** table, `config firewall central-snat-map` |
| Where DNAT is configured | VIP objects referenced as the policy destination | VIPs/DNAT rules applied globally. Policies reference the **internal** address |
| Policy NAT toggle | Present | Ignored or hidden. The GUI points you to Central SNAT |

The rest of this lesson covers SNAT in both models. DNAT and VIPs are in the next lesson.

## Policy SNAT: the egress interface address

The simplest outbound NAT is one setting on the policy:

```text
FGT-HQ # config firewall policy
FGT-HQ (policy) # edit 10
FGT-HQ (10) # set nat enable
FGT-HQ (10) # end
```

With `nat enable` and no IP pool, FortiGate translates the source address to the **IP address of the outgoing interface** (the `dstintf` the route selected) and does port address translation (PAT), so many clients share one address. This is "hide NAT", equivalent to Cisco's `ip nat inside source list … interface … overload`.

Port behaviour:

- With `port-preserve enable` (the default on policies and central SNAT entries), FortiGate keeps the original source port if it is free. If it isn't, FortiGate picks a free port from its NAT port range (5117–65533). Only source ports inside 5117–65533 can be preserved. Lower source ports are always translated unless you use explicit port mapping.
- `set fixedport enable` on the policy forces the original source port to be kept. That is needed by a few protocols and appliances. It sharply reduces how many sessions can share one address, because two clients using the same source port to the same destination collide.

> **Exam tip:** `set nat enable` without `ippool` uses the **egress interface IP**. If the FortiGate has two WAN links, the translated address depends on which interface the route (or SD-WAN rule) chose for that session.

## IP pools

An IP pool (`config firewall ippool`) is a set of addresses FortiGate uses as the translated source instead of the interface IP. Attach it to a policy:

```text
FGT-HQ # config firewall ippool
FGT-HQ (ippool) # edit "POOL-WEB-OUT"
FGT-HQ (POOL-WEB-OUT) # set startip 203.0.113.20
FGT-HQ (POOL-WEB-OUT) # set endip 203.0.113.21
FGT-HQ (POOL-WEB-OUT) # end
FGT-HQ # config firewall policy
FGT-HQ (policy) # edit 10
FGT-HQ (10) # set nat enable
FGT-HQ (10) # set ippool enable
FGT-HQ (10) # set poolname "POOL-WEB-OUT"
FGT-HQ (10) # end
```

### The four IPv4 pool types

| `type` | Mapping | Port translation | Capacity / notes |
|---|---|---|---|
| `overload` (**default**) | Many internal IPs → the pool addresses | Yes (PAT) | About 60,416 ports per pool address per destination tuple. The address a client gets is chosen deterministically from its source IP |
| `one-to-one` | Each internal IP gets its own pool IP | **No** | A pool of N addresses serves only N concurrent internal hosts. When the pool is exhausted, new hosts can't be translated |
| `fixed-port-range` | A defined **internal range** (`source-startip`–`source-endip`) maps to the external range. Each internal IP gets a fixed, predictable block of ports | Yes (PAT, predictable) | Lets you work out which internal host used which external IP:port without per-session NAT logs |
| `port-block-allocation` (PBA) | Many-to-many. Each client is given **blocks** of ports on demand | Yes | `block-size` (default 128) × `num-blocks-per-user` (default 8) = ports per client. Logs record block allocation instead of every session, which suits carrier-grade log volumes |

How an **overload** pool picks the address: FortiGate takes the client's source IP as a number, computes it modulo the number of pool addresses, and uses that offset from `startip`. So a given client consistently gets the same public IP from the pool, which keeps sessions that care about the source address working.

Useful attributes (FortiOS 8.0 CLI reference):

| Attribute | Default | Purpose |
|---|---|---|
| `type` | `overload` | Pool type |
| `startip` / `endip` | – | External range |
| `source-startip` / `source-endip` | – | Internal range (fixed port range only) |
| `startport` / `endport` | 5117 / 65533 | Port range used for translation |
| `block-size` / `num-blocks-per-user` | 128 / 8 | PBA sizing |
| `pba-timeout` | 30 s | How long an idle block stays allocated |
| `permit-any-host` | `disable` | Full-cone NAT: accept inbound UDP to the mapping from any host |
| `arp-reply` | `enable` | Answer ARP for the pool addresses |

### ARP reply and "local" addresses

With `arp-reply enable` (the default), FortiGate answers ARP for every address in the pool on the egress segment. That is required when the pool addresses are in the WAN subnet and the upstream router just ARPs for them. The 8.0 Administration Guide says the pool does not have to be referenced by any policy before FortiGate starts answering ARP for it. (The one-line CLI help for `arp-reply` still says "when an IP Pool is added to a policy". Go by the Administration Guide, and check the upstream ARP table if in doubt.) In current releases (7.0.13, 7.2.6, 7.4.1 and later, and 8.0), pool and VIP addresses with ARP reply enabled are also treated as **local addresses** of the FortiGate, even when **no policy uses the pool**. Traffic *to* those IPs is then not routed onward. Delete unused pools and VIPs, or set `arp-reply disable` on them.

If the ISP **routes** a public block to your WAN IP instead (a routed subnet), ARP isn't needed for those addresses, and the pool still works because return traffic arrives by routing.

> **Watch out:** Two IP pools (or a pool and a VIP) with overlapping ranges are a common cause of strange SNAT or DNAT behaviour. Keep pool ranges distinct, and keep them separate from addresses used by real hosts on the WAN segment, because FortiGate will answer ARP for them.

Read the `hook=post dir=org act=snat` line as: original `src:port -> dst:port`, then **(translated source:port)**. The reply line reverses the translation. Here the client kept its source port (50433) and was translated to pool address 203.0.113.21. In the forward traffic log the same session shows `trandisp="snat" transip=203.0.113.21 transport=50433`.

Always scope `diagnose sys session clear` with a filter. Without one, it clears **every** session on the FortiGate.

## Central SNAT

When central NAT is enabled, SNAT comes from an **ordered table** that is independent of the firewall policies:

```text
FGT-HQ # config system settings
FGT-HQ (settings) # set central-nat enable
FGT-HQ (settings) # end
FGT-HQ # config firewall central-snat-map
FGT-HQ (central-snat-map) # edit 1
FGT-HQ (1) # set srcintf "port2"
FGT-HQ (1) # set dstintf "port1"
FGT-HQ (1) # set orig-addr "LAN-10.0.1.0"
FGT-HQ (1) # set dst-addr "all"
FGT-HQ (1) # set nat-ippool "POOL-WEB-OUT"
FGT-HQ (1) # next
FGT-HQ (central-snat-map) # edit 2
FGT-HQ (2) # set srcintf "port2"
FGT-HQ (2) # set dstintf "port1"
FGT-HQ (2) # set orig-addr "all"
FGT-HQ (2) # set dst-addr "all"
FGT-HQ (2) # end
```

Rules:

- The firewall **policy still decides whether traffic is allowed**. Central SNAT decides only **how it is translated**. The NAT is applied after the policy accepts the session.
- Entries are evaluated **top-down, first match**, and you can reorder them. Matching uses `srcintf`, `dstintf`, `orig-addr`, `dst-addr`, `protocol` and optionally `orig-port`/`dst-port`.
- `nat` defaults to `enable`. With no `nat-ippool`, the egress interface IP is used (entry 2 above). `set nat disable` creates an explicit "no NAT" exemption, for example for traffic into a VPN.
- If no entry matches, the session is not source-NATed.
- `orig-port`/`nat-port` port mapping is for TCP, UDP and SCTP with **overload** pools only.
- `port-preserve` (default `enable`) keeps the original source port when it is free.
- Central SNAT entries can carry 8.0 `custom-tags`.

> **Exam tip:** With central NAT on, a "the server sees the wrong source IP" question is answered in the **central SNAT table** (order and match fields), not in the policy. With central NAT off, it is answered in the **policy** (`nat`, `ippool`, `poolname`).

## Use cases

- **Different public IPs per department:** two policies (or two central SNAT rules) for different source subnets, each with its own overload pool.
- **Mail server identity:** the outbound SMTP server must leave as the IP its MX and SPF records name. Use a one-to-one pool or a static VIP (next lesson), not the shared interface IP.
- **Carrier or large campus:** PBA pools to cut NAT logging to one log per block.
- **Partner VPN with overlapping networks:** SNAT the LAN to a unique range on the tunnel-bound policy.

## Lab it yourself

1. On your outbound policy, enable `nat` with no pool. Browse from the LAN host and check `diagnose sys session list` for the `act=snat` line using the `port1` IP.
2. Create an overload pool using a spare address in your homelab WAN subnet (keep `arp-reply enable`). Attach it and confirm the translated address changes. Your upstream router must ARP for it, or have a route to it.
3. Change the pool to `one-to-one` with a single address and start traffic from two LAN hosts. The second host can't be translated while the first holds the address.
4. In your second VDOM, enable `central-nat`, recreate the same result with a `central-snat-map` entry, and note that the policy's NAT setting is gone.

## Key takeaways

- `set nat enable` without a pool translates to the **egress interface IP** with PAT.
- IP pool types: **overload** (default, PAT), **one-to-one** (no PAT, N addresses for N hosts), **fixed port range** (internal range mapped with predictable port blocks), **port block allocation** (blocks of `block-size` × `num-blocks-per-user` ports).
- Pool and VIP addresses with `arp-reply enable` (the default) are answered and treated as local, even if no policy uses them. Clean up unused ones.
- In `diagnose sys session list`, the `hook=post dir=org act=snat` line shows the translated source in parentheses.
- Central NAT (`set central-nat enable`) moves SNAT into `config firewall central-snat-map`: top-down, first match, applied after the policy allows the traffic. Policy-based NGFW mode always uses it.
- Never run `diagnose sys session clear` without a filter on a production unit.
