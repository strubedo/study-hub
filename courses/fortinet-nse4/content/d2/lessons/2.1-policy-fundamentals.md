## What a firewall policy is on FortiGate

Every packet that passes *through* a FortiGate (as opposed to traffic *to* the FortiGate itself, which local-in policies handle) has to be allowed by a firewall policy. A FortiGate in NAT mode with no policy passes no transit traffic at all. A Cisco ASA allows traffic from higher to lower security levels by default. FortiGate has no security levels: an interface pair with no matching policy is closed.

A policy has two jobs:

1. **Matching.** It decides which sessions it applies to, using interfaces, addresses, users, services and schedule.
2. **Action and treatment.** It accepts or denies the session. For accepted sessions it also controls NAT, the inspection mode, security profiles, traffic shaping and logging.

FortiOS evaluates policies only for the **first packet of a session**. When a policy accepts that packet, FortiGate creates a session table entry that records the matched `policy_id`, and every later packet in either direction follows that entry. This is why editing a policy does not change sessions that already exist. You have to clear them, or wait for them to expire, before the change applies.

## Matching criteria

A policy matches a packet only when **all** of its configured criteria match.

| Criterion | CLI attribute | Notes |
|---|---|---|
| Incoming interface | `srcintf` | Physical port, VLAN, aggregate, tunnel interface, zone, or `any` |
| Outgoing interface | `dstintf` | Found from the routing lookup, which happens *before* policy lookup |
| Source | `srcaddr` / `srcaddr6`, plus optional `users`, `groups`, `fsso-groups`, ISDB source, EMS tags | Addresses are mandatory, and identity is added on top of them |
| Destination | `dstaddr` / `dstaddr6`, ISDB destination, VIP objects | VIPs are matched before policy lookup (see lesson 2.2) |
| Service | `service` | Protocol and port. `ALL` matches everything |
| Schedule | `schedule` | `always` or a recurring or one-time schedule |

The outgoing interface is not something the policy chooses. FortiGate runs the route lookup first and then searches only the policies whose `dstintf` matches the egress interface it found. If a route is missing or points the wrong way, a correct-looking policy is never even evaluated.

> **Exam tip:** In `diagnose debug flow` output, the routing decision (`find a route: ... via port1`) always appears **before** the policy check (`iprope_fwd_check`). If the route points out the wrong interface, the debug ends with `Denied by forward policy check (policy 0)`, even though a policy for the right interface pair exists.

## Order: top-down, first match, implicit deny

FortiGate checks policies **from the top of the list down** and stops at the **first** one that matches. If nothing matches, the traffic hits the **implicit deny policy, policy ID 0**, which is always last and cannot be deleted or moved.

Two numbers describe every policy, and they are easy to confuse:

| | Policy ID | Sequence (position) |
|---|---|---|
| What it is | Permanent identifier given when the policy is created (`edit 10`) | The policy's place in the list |
| Changes when you move the policy? | No | Yes |
| Controls matching order? | **No** | **Yes** |
| Where you see it | `policy_id=` in sessions, `policyid=` in logs, `Allowed by Policy-10` in debug flow | The GUI sequence column and the order in `show firewall policy` |

You reorder policies in the CLI with `move`:

```text
FGT-HQ # config firewall policy
FGT-HQ (policy) # move 25 before 10
FGT-HQ (policy) # end
```

`edit 0` creates a policy with the next free ID, and FortiOS places a new policy at the **bottom** of the list. A new, specific rule can therefore be shadowed by an older, broader one above it. The GUI lets you drag policies or choose *Insert Above / Insert Below*. The CLI equivalent is `move`.

> **Watch out:** Low policy IDs do not mean high priority. Policy 47 can sit above policy 3. Exam exhibits often show a sequence like `2, 47, 3` and ask which policy matches. Read the order, not the numbers.

Policy 0 drops silently by default. To log its drops, enable logging on the implicit deny in the GUI, or use the CLI:

```text
FGT-HQ # config log setting
FGT-HQ (setting) # set fwpolicy-implicit-log enable
FGT-HQ (setting) # end
```

## One table for IPv4 and IPv6

Since FortiOS 6.4, IPv4 and IPv6 rules share one table, `config firewall policy`. A single policy can carry both `srcaddr`/`dstaddr` (IPv4) and `srcaddr6`/`dstaddr6` (IPv6). The old separate `config firewall policy6` table and the 6.2 "consolidated policy mode" no longer exist. The GUI can still filter the list to show IPv4 or IPv6 entries, but there is only one ordered table. NAT46 and NAT64 have also used regular firewall policies since 7.0.1.

## Views and organisation

The policy list has two main views:

- **Interface Pair View** groups policies by `srcintf` → `dstintf`. It is easy to read, but it hides the global order when policies use `any` or multiple interfaces.
- **By Sequence** shows the real top-down evaluation order. Use it whenever ordering matters.

A policy with `srcintf any` or `dstintf any`, or with several interfaces, is listed in the sequence view because it doesn't belong to a single pair. Multiple interfaces per policy are allowed in the CLI. The GUI shows that option only when `set gui-multiple-interface-policy enable` is configured under `config system settings` (default `disable`). Zones (`config system zone`) group interfaces so that one policy covers all of them. Once an interface is in a zone, policies must reference the zone, not the member.

FortiOS 8.0 adds **custom tags** and **dynamic tag address groups** to organise large rule bases. Those are covered in the logging and tagging lesson.

> **Real world:** FortiOS 8.0.1 adds an *Initial Policy Configuration* step to the setup wizard on desktop models and the FG-100F/200E series. On a new or factory-reset unit with an **empty** policy table, it can create a `lan` → `wan1` accept policy with NAT. It replaces the preconfigured outbound policy these models used to ship with, so the administrator now chooses whether that policy exists. `config system global` → `set gui-initial-firewall-policy-setup {enable|disable}` (default `enable`) controls whether the step appears. The FortiGate-VM starts with no policies.

## Anatomy of a policy in the CLI

`show` prints only **non-default** values. In the example below, `inspection-mode flow` and `logtraffic utm` are the defaults, so they are not shown.

```text
FGT-HQ # show firewall policy 10
config firewall policy
    edit 10
        set name "LAN-to-Internet"
        set uuid 9b3e6c2a-4f1d-51f0-8a6e-2c1d5e7f9a10
        set srcintf "port2"
        set dstintf "port1"
        set action accept
        set srcaddr "LAN-10.0.1.0"
        set dstaddr "all"
        set schedule "always"
        set service "ALL"
        set utm-status enable
        set ssl-ssh-profile "certificate-inspection"
        set av-profile "default"
        set webfilter-profile "default"
        set nat enable
    next
end
```

Key CLI defaults in FortiOS 8.0 (from the 8.0 CLI reference):

| Attribute | Default | Meaning |
|---|---|---|
| `action` | `deny` | You must set `accept` explicitly in the CLI |
| `status` | `enable` | `set status disable` keeps the policy but skips it during matching |
| `nat` | `disable` | Source NAT is off unless enabled (or central SNAT is used) |
| `inspection-mode` | `flow` | Per-policy choice between flow and proxy |
| `logtraffic` | `utm` | Logs only sessions that trigger a security event |
| `match-vip` | `enable` | Deny policies also match DNATed (VIP) traffic |
| `ssl-ssh-profile` | `no-inspection` | Shown when security profiles are enabled |

A deny policy can send a reply instead of dropping silently with `set send-deny-packet enable` (default `disable`). Policies can also expire automatically with `set policy-expiry enable` and `set policy-expiry-date`, which suits temporary vendor access.

## Finding which policy matches

- **Policy Lookup** (GUI, top of the policy list): enter the incoming interface, protocol, source, destination and port, and the GUI highlights the matching policy.
- `diagnose firewall iprope lookup <src_ip> <src_port> <dst_ip> <dst_port> <protocol> <incoming_interface>` is the CLI equivalent.
- `diagnose debug flow` shows the real decision for real packets:

```text
FGT-HQ # diagnose debug flow filter addr 10.0.1.25
FGT-HQ # diagnose debug flow show function-name enable
FGT-HQ # diagnose debug enable
FGT-HQ # diagnose debug flow trace start 10
id=65308 trace_id=1 func=print_pkt_detail line=5845 msg="vd-root:0 received a packet(proto=6, 10.0.1.25:50433->198.51.100.80:443) tun_id=0.0.0.0 from port2. flag [S], seq 2318801541, ack 0, win 64240"
id=65308 trace_id=1 func=init_ip_session_common line=6047 msg="allocate a new session-0001b2c4"
id=65308 trace_id=1 func=__vf_ip_route_input_rcu line=2012 msg="find a route: flag=00000000 gw-203.0.113.1 via port1"
id=65308 trace_id=1 func=__iprope_tree_check line=524 msg="gnum-100004, use addr/intf hash, len=3"
id=65308 trace_id=1 func=fw_forward_handler line=1014 msg="Allowed by Policy-10: SNAT"
id=65308 trace_id=1 func=__ip_session_run_tuple line=3625 msg="SNAT 10.0.1.25->203.0.113.2:61002"
```

Turn debugging off when you are done (`diagnose debug disable` and `diagnose debug reset`). A denied packet ends with `Denied by forward policy check (policy 0)` for the implicit deny, or with the ID of an explicit deny policy.

## Use cases

- **Outbound internet for a LAN:** `port2` → `port1`, source is the LAN subnet, destination `all`, NAT enabled, security profiles applied.
- **Segmentation between internal networks:** `port2` → `port3` with specific services and **no** NAT, so logs and servers see real client IPs.
- **Temporary access:** a policy with `policy-expiry`, or a one-time schedule.
- **Explicit deny with logging above a broad allow:** for example, block one subnet from SSH out, with `logtraffic all`, so the drops are visible.

## Lab it yourself

The permanent-trial FortiGate-VM allows **3 interfaces and 3 firewall policies**, which is enough for this lab.

1. Set `port1` as WAN (DHCP or static to your homelab router), and `port2` as LAN 10.0.1.254/24 with a Linux host behind it.
2. Create policy A: `port2` → `port1`, source `all`, service `ALL`, NAT on. Confirm the host can browse.
3. Create policy B **after** A: same interfaces, source = host 10.0.1.25/32, service `SSH`, action deny, `logtraffic all`. Try SSH out. It still works, because A matches first.
4. `move` B before A and test again. Then view the forward traffic log and watch the debug flow change from `Allowed by Policy-A` to `Denied by forward policy check (policy B)`.
5. Delete policy A and run `diagnose debug flow` again to see policy 0 take the traffic.

## Key takeaways

- Policies are checked top-down and the first match wins. Unmatched traffic hits implicit deny policy 0, which does not log by default (`fwpolicy-implicit-log`).
- The policy ID is a permanent label. The **sequence** sets the order. Reorder with `move <id> before|after <id>`.
- The route lookup happens before the policy lookup, so the policy's `dstintf` must match the route's egress interface.
- Policies are evaluated once per session, and existing sessions keep their original policy until cleared or expired.
- IPv4 and IPv6 share one `config firewall policy` table (since 6.4).
- CLI defaults worth knowing: `action deny`, `nat disable`, `inspection-mode flow`, `logtraffic utm`, `match-vip enable`.
- Policy Lookup in the GUI, `diagnose firewall iprope lookup`, and `diagnose debug flow` show which policy a packet matches.
