## Two separate decisions

Two settings are easy to confuse because both have "mode" in their name:

1. **Inspection mode** (`flow` or `proxy`) decides *how* security profiles inspect an accepted session. In profile-based NGFW mode it is set **per firewall policy**.
2. **NGFW mode** (`profile-based` or `policy-based`) decides *how you build the rule base*. It is set **per VDOM** in `config system settings`.

On a default FortiGate, every VDOM uses **profile-based** NGFW mode and every new policy uses **flow** inspection.

## Inspection mode per policy

Since FortiOS 6.2, the inspection mode has been a property of each policy, not of the whole VDOM:

```text
FGT-HQ # config firewall policy
FGT-HQ (policy) # edit 10
FGT-HQ (10) # set inspection-mode proxy
FGT-HQ (10) # end
```

| | Flow-based (default) | Proxy-based |
|---|---|---|
| How it works | Inspects packets as they pass, with a single-pass IPS engine and pattern matching on the stream | Terminates the session and buffers the content (or whole files) before releasing it |
| Latency and resource use | Lower. Many sessions can be offloaded or handled efficiently | Higher. Uses more memory and CPU per session |
| Thoroughness | Very good. Some features act on partial data | Most thorough. The full object is available, so it can be modified (for example, replacement messages inside a page or file) |
| Feature set | The common profiles: AV, web filter, DNS filter, application control, IPS, file filter, email filter | Everything in flow, plus some proxy-only options (for example ICAP, the web application firewall profile, and web filter options that need full proxy handling) |
| Typical use | Default for most traffic | When a profile option needs proxy, or when you need the most thorough AV or content handling |

Practical points:

- The mode affects only what **security profiles** do. The policy match, NAT and logging work the same way in both modes.
- When you change a policy to proxy mode, the profile lists filter to profiles that support proxy. Some profile options appear or disappear with the mode, and the GUI shows feature availability.
- The SSL/SSH inspection profile (`ssl-ssh-profile`) is separate from the inspection mode. Proxy mode does not turn on deep inspection. Encrypted traffic still needs `deep-inspection` (lesson 3.1) for content inspection.
- Content inspection in detail (web filter, AV and IPS per mode) is covered in Domain 3. For Domain 2, know where the setting is and what it decides.

> **Exam tip:** "Where do you configure flow or proxy inspection?" In profile-based mode the answer is **in each firewall policy**. Older material that says "set inspection mode for the VDOM under System > Settings" describes FortiOS 6.0 and earlier.

## NGFW profile-based mode (the default)

This is the traditional FortiGate model. A policy matches on interfaces, addresses, users and services, and you **attach security profiles** to it: an application control profile, a web filter profile, an IPS sensor, and so on. Application and URL category decisions happen *inside* those profiles, after the policy has matched.

## NGFW policy-based mode

Policy-based mode moves application and URL-category matching **into the policy itself**. A security policy can say "allow `Microsoft.Teams` and the `Business` URL category from Sales", with no application control or web filter profile.

Enable it per VDOM:

```text
FGT-HQ # config system settings
FGT-HQ (settings) # set ngfw-mode policy-based
FGT-HQ (settings) # end
```

What changes when a VDOM is in policy-based mode (per the FortiOS 8.0 Administration Guide):

| Area | Policy-based NGFW behaviour |
|---|---|
| Rule tables | Two tables. **SSL Inspection & Authentication** policies (`config firewall policy`) pre-match traffic and set the SSL inspection profile and user authentication. **Security policies** (`config firewall security-policy`) set applications, URL categories, users/groups, the action and the security profiles |
| SSL Inspection & Authentication policy | Has no schedule or action options. A default one with the `certificate-inspection` profile is created for you |
| NAT | **Central NAT is always on.** SNAT is configured in the central SNAT table, not per policy. If no central SNAT rule exists you must create one |
| Inspection | **Flow mode only.** Proxy-based inspection is not supported |
| Profiles in the GUI | AntiVirus, Web Filter, DNS Filter, IPS, File Filter, Email Filter and Virtual Patching. DLP is CLI-only |
| Default application ports | `default-app-port-as-service` (system settings) and `enforce-default-app-port` (security policy) can require an application to use its standard port |
| Learn mode | `set learning-mode enable` on a security policy records the traffic it sees, to help build rules |
| Limitations | No IPsec wizard, no HA session pickup on failover, no static URL filter directly in the security policy |
| Hit counts | `diagnose ips pme policy stats` |

```text
FGT-HQ # config firewall security-policy
FGT-HQ (security-policy) # edit 1
FGT-HQ (1) # set name "Sales-SaaS"
FGT-HQ (1) # set srcintf "port2"
FGT-HQ (1) # set dstintf "port1"
FGT-HQ (1) # set srcaddr "all"
FGT-HQ (1) # set dstaddr "all"
FGT-HQ (1) # set application 43541
FGT-HQ (1) # set groups "Sales"
FGT-HQ (1) # set action accept
FGT-HQ (1) # set schedule "always"
FGT-HQ (1) # end
```

(Application IDs come from the FortiGuard application database. Look the ID up in the GUI. The number above is only an example.)

### Choosing between the modes

| Choose profile-based when… | Choose policy-based when… |
|---|---|
| You need proxy inspection on some traffic | You want application or URL category as the match condition |
| You prefer per-policy NAT | You are comfortable with central SNAT |
| You rely on HA session pickup | Your security team thinks in "who may use which app" rules |
| You want the IPsec wizard and broad feature coverage | You want learn mode to build rules from observed traffic |

> **Watch out:** Switching a VDOM to policy-based mode changes the rule-base model. Plan it on a lab or new VDOM, not as a casual change on a production box. Review the policies afterwards, because NAT moves to the central SNAT table.

## Where inspection fits in the packet path

For an accepted first packet in profile-based mode, the high-level sequence is:

1. Ingress, then DoS/local-in checks where relevant.
2. **DNAT** (VIP lookup).
3. **Route lookup**, which picks the egress interface.
4. **Policy lookup**, which finds the first match. Authentication happens here when the policy has users or groups.
5. Session created, then **flow or proxy inspection** as the policy defines.
6. Egress. **SNAT** is applied as the packet leaves, using the translation the matching policy (or central SNAT rule) selected.

Knowing this order explains several "why" questions. A deny rule written against a public IP misses VIP traffic, because the destination was already translated in step 2, before the policy lookup in step 4. A wrong route gives policy 0. Inspection settings don't matter until a policy has accepted the traffic.

## Use cases

- **Mixed modes on one FortiGate:** most outbound traffic uses flow mode for performance. One policy for a sensitive server segment uses proxy mode with a stricter AV profile.
- **App-centric control:** a branch VDOM in policy-based mode allows only sanctioned SaaS applications per AD group, with one central SNAT rule for `port2` → `port1`.
- **Performance troubleshooting:** a high-throughput backup flow is moved to its own flow-mode policy without UTM, above the general policy, so it doesn't consume proxy resources.

## Lab it yourself

On the FortiGate-VM trial (3 policies max). FortiGuard isn't licensed, so the profiles have no live signatures, but the configuration and modes still work.

1. On your outbound policy, enable AV with the `default` profile and switch `inspection-mode` between `flow` and `proxy`. Watch which profile options change in the GUI.
2. Create a second VDOM (the trial allows 2), set `ngfw-mode policy-based` in it, and look at the two tables the GUI now shows. Note that the per-policy NAT toggle disappears and *Central SNAT* appears.

## Key takeaways

- Inspection mode (`flow`/`proxy`) is set **per firewall policy**. The default is `flow`.
- Proxy mode buffers and fully reconstructs content. It is more thorough and supports some proxy-only features, but uses more resources.
- NGFW mode (`profile-based`/`policy-based`) is a **per-VDOM** setting in `config system settings`. The default is `profile-based`.
- Policy-based mode puts applications and URL categories in **security policies**, uses a separate **SSL Inspection & Authentication** table, is **flow-only**, and always uses **central SNAT**.
- In policy-based mode there is no HA session pickup and no IPsec wizard. DLP is configured in the CLI only.
- DNAT and the route lookup happen before the policy lookup, and inspection happens only after a policy accepts the session.
