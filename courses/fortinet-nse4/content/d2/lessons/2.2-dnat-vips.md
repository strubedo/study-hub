## What a VIP does

A **virtual IP (VIP)** is FortiGate's destination NAT object. It maps an external address (and optionally a port) to an internal address (and port). Typical use: publish a DMZ web server at 203.0.113.10 while it really lives at 10.0.2.10.

```text
FGT-HQ # config firewall vip
FGT-HQ (vip) # edit "VIP-WEB-HTTPS"
FGT-HQ (VIP-WEB-HTTPS) # set extip 203.0.113.10
FGT-HQ (VIP-WEB-HTTPS) # set mappedip "10.0.2.10"
FGT-HQ (VIP-WEB-HTTPS) # set extintf "port1"
FGT-HQ (VIP-WEB-HTTPS) # set portforward enable
FGT-HQ (VIP-WEB-HTTPS) # set extport 443
FGT-HQ (VIP-WEB-HTTPS) # set mappedport 443
FGT-HQ (VIP-WEB-HTTPS) # end
```

Key attributes and their FortiOS 8.0 defaults:

| Attribute | Default | Meaning |
|---|---|---|
| `type` | `static-nat` | Plain DNAT. Other types include load balancing (virtual server), DNS translation, FQDN and access proxy |
| `extip` | – | External address or range that clients connect to |
| `mappedip` | – | Internal address or range (quoted list) |
| `extintf` | – | Interface where the traffic arrives. `any` is allowed |
| `portforward` | `disable` | Off means all ports and protocols are mapped. On means only `extport` → `mappedport` for `protocol` |
| `protocol` | `tcp` | Used with port forwarding (`tcp`, `udp`, `sctp`, `icmp`) |
| `arp-reply` | `enable` | Answer ARP for `extip` |
| `srcintf-filter` / `src-filter` | – | Apply the VIP only to traffic from certain interfaces or sources |
| `status` | `enable` | Turn the VIP on or off |
| `nat-source-vip` | `disable` | Force the external IP as the SNAT address for all traffic from the mapped server |

A static NAT VIP without port forwarding is a full 1:1 mapping. Use the policy's `service` to limit what is actually exposed. With port forwarding, one public IP can publish many servers on different ports, for example 203.0.113.10:443 to the web server and 203.0.113.10:2222 to 10.0.2.20:22.

## DNAT happens before the policy lookup

This is the most tested VIP fact. For the first packet of a session, the order is:

1. Packet arrives on `port1`, destined to 203.0.113.10:443.
2. **VIP/DNAT check:** the destination is rewritten to 10.0.2.10:443.
3. **Route lookup** on the *new* destination selects `port3`.
4. **Policy lookup** for `port1` → `port3`.

Consequences:

- In policy NAT mode (central NAT off), the policy's **destination must be the VIP object**: `set dstaddr "VIP-WEB-HTTPS"`. A policy with dstaddr `all` doesn't use the VIP for DNAT. A policy with dstaddr = the public IP as a normal address never matches, because the destination has already changed.
- The policy's **`dstintf` is the interface toward the mapped server** (`port3` here), not the WAN interface.
- The policy's **service must match the mapped (internal) port**, not the external port. With `extport 8443` → `mappedport 443`, the policy service must allow 443 (or `ALL`). A policy that allows only 8443 sends the session to policy 0.
- A VIP is used for DNAT only if an **enabled firewall policy references it**. A VIP that no policy uses is never matched for DNAT, although its `extip` still answers ARP when `arp-reply` is enabled.

```text
FGT-HQ # config firewall policy
FGT-HQ (policy) # edit 20
FGT-HQ (20) # set name "Inbound-WEB"
FGT-HQ (20) # set srcintf "port1"
FGT-HQ (20) # set dstintf "port3"
FGT-HQ (20) # set action accept
FGT-HQ (20) # set srcaddr "all"
FGT-HQ (20) # set dstaddr "VIP-WEB-HTTPS"
FGT-HQ (20) # set schedule "always"
FGT-HQ (20) # set service "HTTPS"
FGT-HQ (20) # set logtraffic all
FGT-HQ (20) # end
```

Inbound VIP policies normally have **NAT disabled**, so the server sees the real client IP. Enabling NAT here makes every client appear as the FortiGate's `port3` address. That is sometimes needed (see hairpin), but usually unwanted.

> **Exam tip:** In a debug flow, `find DNAT: IP-10.0.2.10, port-443` followed by `Denied by forward policy check (policy 0)` means the VIP matched but no policy allowed the **translated** traffic. Check the policy's service (mapped port), its `dstintf`, and the route to the mapped IP.

## VIPs and deny policies: `match-vip`

Because DNAT happens first, a deny policy with destination `all` above the VIP policy might not see the translated traffic as "VIP traffic". The `match-vip` option controls this. It is only available when the policy action is `deny`. In FortiOS 8.0 it defaults to `enable`, so a broad deny policy (for example a geo-block from `port1` to `port3`, destination `all`) also matches DNATed sessions. Releases before 7.2.3 defaulted to `disable` (Fortinet's KB articles date the change to 7.2.3), which is why many upgrade-era guides say "remember to set `match-vip enable`". Because the value is the default, `show firewall policy` doesn't print it. Run `show full-configuration` to see it.

## Order and overlap

VIPs and virtual servers share one hidden DNAT table (viewable with `diagnose firewall iprope list 100000`). FortiGate uses the **first matching VIP** in configuration order. Since FortiOS 7.2, overlapping VIPs are allowed, so order can matter. A static 1:1 VIP for 203.0.113.10 placed above a port-forward VIP for 203.0.113.10:2222 captures the traffic first.

**FortiOS 8.0.1** adds GUI tools for this:

- On **Policy & Objects > Virtual IPs**, drag a VIP to a new position, or right-click and choose **Insert > Above / Below**.
- **Security Rating Insights** flag overlapping VIPs (*Virtual IP Overlap*), highlight them in yellow, and can filter the list to show only the overlaps.
- Reordering applies only when **central NAT is disabled**, and only to **IPv4** VIPs.

## Hairpin NAT (internal clients using the public IP)

Internal users browsing to `https://203.0.113.10` reach `port2`, not `port1`. A VIP's `extintf` is the interface that the policy's source interface must match, so a VIP with `extintf "port1"` can only be used in policies from `port1`. It can't be used in a `port2` → `port3` policy. Options, from best to worst:

1. **Split DNS:** internal DNS returns 10.0.2.10. No NAT tricks.
2. **VIP with `extintf any`** (optionally narrowed with `set srcintf-filter "port1" "port2"`), plus a policy `port2` → `port3` with the VIP as destination.
3. If client and server are **on the same subnet and interface**, also enable **NAT** on the hairpin policy. Otherwise the server replies directly to the client, bypassing FortiGate, and the client drops the reply because it came from the wrong IP.

## Outbound traffic from a VIP-mapped server

For a **static NAT VIP without port forwarding**, FortiGate treats the mapping as bidirectional. When the mapped server (10.0.2.10) starts an outbound session through a policy with NAT enabled and leaves through the VIP's external interface, the session is translated to the VIP's external IP (203.0.113.10), not the interface IP. This keeps inbound and outbound identity aligned, which matters for mail servers. With central NAT disabled, it works only if the VIP is **referenced by at least one firewall policy** (normally the inbound one). An unreferenced VIP isn't loaded, so it is used neither for DNAT nor for this reverse SNAT. The SNAT address is chosen in this priority order:

1. The VIP's external IP, if the VIP has `nat-source-vip enable`. It is then used for all source-NATed traffic from the mapped server.
2. The IP pool configured on the outbound policy.
3. The static VIP's reverse mapping (`nat-source-vip disable`, the default), when the traffic leaves through the VIP's external interface.
4. The outgoing interface IP.

With port forwarding, the reverse mapping applies only to outbound traffic whose protocol and source port match the forwarded service. Ordinary outbound sessions from the server use random source ports, so they don't get the VIP address.

## DNAT when central NAT is enabled

With `central-nat enable`:

- DNAT is managed on **Policy & Objects > DNAT & Virtual IPs**, and every **enabled** VIP (`status enable`) is applied. It does not need a policy reference.
- The firewall policy's destination is the **mapped internal address** (an address object for 10.0.2.10), not the VIP.
- You cannot enable central NAT while policies still reference VIPs. Remove those references first.

## Use cases

- **Publish one server, one port:** port-forward VIP plus an inbound policy using the VIP and the mapped service.
- **Many services on one public IP:** several port-forward VIPs with the same `extip` and different ports, grouped in a VIP group (`config firewall vipgrp`) for one policy.
- **Restrict exposure by source:** `src-filter` or `srcintf-filter` on the VIP, or a narrower `srcaddr` in the policy.
- **Block a country from the VIP:** a deny policy above the VIP policy with a geography address as source (`match-vip enable`, the 8.0 default).

## Lab it yourself

Use `port1` (WAN), `port2` (LAN) and `port3` (DMZ, a Linux web server on 10.0.2.10). That's 3 interfaces and up to 3 policies.

1. Create a port-forward VIP from a spare WAN-subnet IP, port 8080, to 10.0.2.10:80, and a `port1` → `port3` policy using the VIP with service `HTTP`. Test from a homelab host on the WAN side.
2. Change the policy service to a custom TCP 8080 service. Run `diagnose debug flow` and find `find DNAT` followed by `policy 0`.
3. Inspect `diagnose sys session list` for `act=dnat`, and the forward log for `tranip`.
4. Create a second, static 1:1 VIP for the same external IP, place it above the port-forward VIP (8.0.1 GUI drag), and observe the Security Rating overlap insight.

## Key takeaways

- VIPs are DNAT objects. `type static-nat` is the default, and `portforward` (default off) limits the mapping to one protocol and port.
- DNAT happens **before** the route and policy lookups. The policy uses the VIP as `dstaddr`, the server-facing interface as `dstintf`, and the **mapped** port as its service.
- A VIP is used for DNAT only when an enabled policy references it (central NAT off), but `arp-reply` answers for its `extip` regardless.
- `match-vip` (deny policies only) defaults to `enable` in 8.0, so broad deny policies also catch VIP traffic.
- The first matching VIP wins. 8.0.1 adds GUI drag-and-drop and Insert Above/Below for IPv4 VIPs (central NAT off) and Security Rating overlap warnings.
- Hairpin: prefer split DNS. Otherwise use `extintf any` and enable NAT when client and server share a subnet.
- With central NAT, all enabled VIPs apply and policies reference the **mapped internal address**.
