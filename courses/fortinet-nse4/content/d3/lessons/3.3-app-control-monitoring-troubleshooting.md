## Where application events show up

Application control produces two kinds of evidence.

1. **Application control logs** (UTM type, `subtype="app-ctrl"`, `eventtype="signature"`). One is written when a matched entry has logging enabled: Monitor, Block, Reset, Quarantine, or an entry with `set log enable`. *Allow* entries do not log. Applications that matched no entry are logged only with `set other-application-log enable`, and unknown applications only with `set unknown-application-log enable`.
2. **Traffic logs** of policies that carry an application sensor. The forward traffic log gains `app`, `appcat` and `apprisk` fields, so even unlogged *Allow* traffic is visible there, as long as the policy logs traffic.

A typical application control log, as displayed by `execute log display`:

```text
date=2026-10-28 time=10:22:41 eventtime=1793200961000000000 tz="-0500"
type="utm" subtype="app-ctrl" eventtype="signature"
level="warning" vd="root" srcip=10.0.1.25 srcport=51544
srcintf="port2" srcintfrole="lan" dstip=203.0.113.80 dstport=443
dstintf="port1" dstintfrole="wan" proto=6 service="HTTPS" direction="outgoing"
policyid=10 sessionid=88412 applist="APP-Staff" action="block"
appcat="P2P" app="BitTorrent" hostname="tracker.example.net"
msg="P2P: BitTorrent" apprisk="high"
```

> **Exam tip:** In log exhibits, read the fields that answer the question: `applist` (which sensor), `policyid` (which policy), `action` (pass, block or reset), `app` and `appcat` (what was detected) and `apprisk`. Some fields are trimmed from the extracts in this course to keep them readable.

With 8.0 GenAI signatures, deep inspection and `set extended-log enable` in the sensor, the same log type carries `aiuser`, `model`, `dcgeo`, `usecase`, `prompt` and `cloudgenai`. For example, `app="OpenAI.ChatGPT_Post"`, `appcat="GenAI"` and `usecase="Conversational_Assistant"`.

## Traffic matching issues

Most "application control doesn't work" tickets fall into a handful of patterns.

### 1. The firewall policy decides first

In profile mode, the **firewall policy** is matched on the first packet using interfaces, addresses, service, user and schedule. The application is not known yet. The sensor only sees traffic that the policy already accepted:

- If the policy's `service` is `HTTPS`, an application running on TCP 8080 never reaches that policy's sensor. It matches another policy, or the implicit deny.
- If a **higher** policy without a sensor accepts the traffic, the sensor on a lower policy never sees it. Check the `policyid` in the logs and use `diagnose debug flow` to confirm.

### 2. Identification takes a few packets

Signatures need application data: the TLS Client Hello, the HTTP request, and so on. The TCP handshake and the first bytes are therefore always allowed before the application is identified. That is normal, and it is why a blocked application can show a few hundred bytes sent in the traffic log. In **policy-based NGFW** mode the same effect means a session can start on one security policy and be re-evaluated once the application is known.

### 3. The SSL profile hides the details

With **certificate inspection**, FortiGate identifies applications from SNI/certificate data, but sub-application actions (*File.Upload*, *Video.Play*, *Post*) are invisible. Entries targeting those signatures never match. The fix is deep inspection for that traffic, after checking the signature's *Requirements*.

### 4. QUIC goes around you

Browsers prefer **QUIC** (UDP 443) for Google, YouTube, Meta services and more. Many sensors, and the DLP/web filter designs that depend on them, block the **QUIC** application on purpose so the browser falls back to TCP/TLS, where full inspection works. The documented 8.0 GenAI DLP example applies an application control profile that blocks QUIC for this reason.

### 5. Entry order

Overrides are evaluated top-down before categories. A broad *Allow all of Cloud.IT* filter above a specific *Block Dropbox_File.Upload* override wins. Put specific overrides first.

### 6. Port enforcement surprises

After someone enables *Block applications detected on non-default ports*, an internal web application on TCP 8443 that FortiGuard identifies as *HTTPS.BROWSER* starts being blocked. Either add a specific override, or disable enforcement for that policy's sensor.

### 7. Stale or missing signatures

```text
FGT-HQ # diagnose autoupdate versions | grep -A 6 "Application Definitions"
Application Definitions
---------
Version: 33.00912 signed
Contract Expiry Date: Thu Jan  3 2030
Last Updated using scheduled update on Mon Oct 26 03:11:20 2026
Last Update Attempt: Wed Oct 28 03:12:04 2026
Result: No Updates
```

Check that the contract has not expired and the version is recent. For GenAI signatures, also check the **GenAI Application Definitions** entry. Version `0.00000` means it was never downloaded; it needs an application control profile in use and a valid firmware and general updates (FMWR) contract. If a **brand-new** application signature does not match even though the package is current, check 8.0.1's **signature hold timer** (`config system app` → `signature-hold-time`, default `0h`). While a newly added signature is on hold it is treated as disabled, writes no logs, and the traffic is matched by a more generic signature such as SSL.

### 8. Look up the signature

```text
FGT-HQ # get application name status | grep -A 10 'name: "FTP"'
```

This shows the ID, category, popularity, risk, weight and protocols, which helps you understand why one signature beat another.

## Use cases: controlling application traffic

| Requirement | Sensor design |
|---|---|
| Block peer-to-peer and proxy/anonymiser apps company-wide | Category P2P → Block; category Proxy → Block |
| Allow social media but stop posting | Category Social.Media → Monitor; override the *_Post* signatures → Block; deep inspection |
| Limit video streaming to a fixed bandwidth | Category Video/Audio → Allow with `set shaper "VIDEO-10M"` |
| Only approved AI tools | Override for the approved GenAI apps → Monitor; category GenAI → Block; deep inspection for visibility |
| Stop tunnelling apps on unusual ports | `enforce-default-app-port enable`; filter by behavior *Evasive* → Block |
| Find out what is on the network before writing rules | Every category → Monitor, `other-application-log enable`, then review FortiView |

> **Real world:** Start every application control project in **monitor** mode for a week. FortiView will show you applications nobody knew about, and you avoid an outage caused by blocking a category that a business system depends on.

## Lab it yourself

1. Apply a monitor-everything sensor to your outbound policy and generate traffic (web, DNS, NTP, SSH). Compare what appears in application control logs and in traffic logs.
2. Change one category to Block and watch the TCP handshake still complete before the block: the traffic log shows some bytes sent.
3. Add a narrow Allow override above a broad Block filter and confirm that the override wins. Then swap their order.
4. On the trial VM, run `diagnose autoupdate versions` and note the shipped Application Definitions version and the missing contract.

## Key takeaways

- App control logs are written for entries that log (Monitor/Block/Reset/Quarantine). *Allow* does not log. Use `other-application-log` / `unknown-application-log` for the rest.
- Traffic logs of policies with a sensor include `app`, `appcat` and `apprisk`.
- The policy is matched before the application is known. A wrong service, or an earlier policy, means the sensor never sees the traffic.
- The first packets always pass while the application is being identified.
- Sub-application actions and GenAI fields need deep inspection. Block QUIC to force TCP fallback.
- Check signatures with `diagnose autoupdate versions` and `get application name status`. Know the 8.0.1 signature hold timer for newly added signatures.
- Start with monitor, review FortiView, then enforce.
