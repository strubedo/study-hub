## Why encrypted traffic needs special handling

Nearly everything your users touch is TLS. A FortiGate that only sees TLS records can read the handshake, but it cannot see the URL path, the downloaded file or the HTTP POST body. Every security profile that works on content (antivirus, web filter content rules, DLP, most IPS signatures, many application control signatures) is effectively blind until the session is decrypted.

FortiOS handles this with a separate object: the **SSL/SSH inspection profile** (`config firewall ssl-ssh-profile`). It is attached to a firewall policy alongside the other security profiles. It does nothing on its own. It decides *how much* of the encrypted session the other profiles are allowed to see.

## Certificate inspection vs full SSL inspection

There are two inspection methods for outbound ("multiple clients connecting to multiple servers") traffic.

| | Certificate inspection | Full SSL inspection (deep inspection) |
|---|---|---|
| What FortiGate reads | The TLS handshake only: Client Hello (SNI) and, where visible, the server certificate | The decrypted payload |
| Session handling | The original TLS session passes end to end; FortiGate never holds the session keys | FortiGate terminates the client's TLS session and opens its own TLS session to the server |
| Certificate seen by the client | The real server certificate | A copy re-signed by a FortiGate CA |
| Client must trust a FortiGate CA | No (except to view HTTPS block pages without a warning) | Yes, or every site shows a warning |
| Web filtering | Domain/category only (from SNI or certificate CN) | Full URL, path, safe search, content |
| AV / DLP on HTTPS | Not possible | Yes |
| Privacy impact | Low | High: plan exemptions |
| CPU cost | Low | High: two TLS sessions per connection |

> **Exam tip:** If a question says the administrator wants to block a *category* or *domain* over HTTPS with minimum impact and no certificate deployment, the answer is certificate inspection. If it says *scan files*, *see the full URL*, *enforce safe search* or *inspect POST data*, the answer is full (deep) inspection.

## The built-in profiles

FortiOS ships four SSL/SSH inspection profiles. Three of them are read-only.

| Profile | Editable | Purpose |
|---|---|---|
| `certificate-inspection` | No | Certificate inspection on HTTPS port 443 |
| `deep-inspection` | No | Full inspection with Fortinet_CA_SSL and the default exemptions |
| `custom-deep-inspection` | Yes | A full inspection profile you are allowed to modify |
| `no-inspection` | No | No SSL inspection at all |

To change a read-only profile, you clone it or create a new one. The 8.0 documentation's own examples do exactly that. They clone `deep-inspection` to add extra HTTPS ports, because the built-in profile cannot be edited.

```text
FGT-HQ # show firewall ssl-ssh-profile custom-deep-inspection
config firewall ssl-ssh-profile
    edit "custom-deep-inspection"
        set comment "Customizable deep inspection profile."
        config https
            set ports 443
            set status deep-inspection
        end
        ...
        set caname "Fortinet_CA_SSL"
        set untrusted-caname "Fortinet_CA_Untrusted"
    next
end
```

The protocol sub-tables are `https`, `ftps`, `imaps`, `pop3s`, `smtps`, `dot` (DNS over TLS) and `ssh`. The `ssl` sub-table, with `set inspect-all`, applies one method to all ports. Under `https`, `status` can be `disable`, `certificate-inspection` or `deep-inspection`. The other TLS protocols only offer `disable` or `deep-inspection`, because certificate inspection is an HTTPS (web filtering) feature.

> **Watch out:** Protocol port mapping (for example, HTTPS on `443,8443`) only matters for **proxy-based** policies. In flow-based policies the IPS engine inspects TLS on all ports regardless of the port list.

## How full inspection works on outbound traffic

With deep inspection, FortiGate is a deliberate man-in-the-middle:

1. The client sends a Client Hello to the real server. The FortiGate intercepts it.
2. FortiGate opens its own TLS session to the server and receives the server's real certificate.
3. FortiGate validates that certificate against its trusted CA store. It checks the chain, the validity dates, revocation, and SNI against CN/SAN.
4. FortiGate generates a new certificate for the same subject and signs it with a local CA:
   - **`caname`** (default `Fortinet_CA_SSL`) when the real certificate was trusted.
   - **`untrusted-caname`** (default `Fortinet_CA_Untrusted`) when the real certificate failed validation and the action is to allow it as untrusted.
5. The client completes a TLS session with FortiGate using that re-signed certificate. FortiGate decrypts, hands the cleartext to the security profiles, then re-encrypts toward the server.

The setting that produces this behaviour is `set server-cert-mode re-sign` (the default). The alternative, `replace`, presents a certificate you uploaded (with its private key). That is used for **Protecting SSL Server**, the inbound case where you own the server's certificate. For outbound internet traffic you always re-sign, because you do not own google.com's private key.

## Fortinet_CA_SSL, Fortinet_CA_Untrusted and endpoint trust

The two built-in CAs exist for opposite reasons:

- **Fortinet_CA_SSL** signs certificates for sites FortiGate *did* trust. Once endpoints trust this CA, users browse normally with no warnings.
- **Fortinet_CA_Untrusted** signs certificates for sites FortiGate *did not* trust. Its job is to **keep** the browser warning, so that an expired or self-signed server certificate still looks wrong to the user even though FortiGate re-signed it.

> **Watch out:** Never install Fortinet_CA_Untrusted on endpoints. If you do, a man-in-the-middle on the internet side, or a broken certificate, becomes invisible to users.

### Getting a CA onto the endpoints

Without a trusted CA, deep inspection makes every HTTPS site show a certificate error. The options are:

1. **Download the FortiGate CA and distribute it.** In the GUI, open the SSL/SSH inspection profile and use *Download* next to the CA certificate. Import it into the client's **Trusted Root Certification Authorities** store. For a Windows domain, push it with Group Policy. For macOS and iOS, use an MDM profile. FortiClient EMS can also deploy it.
2. **Use your own enterprise PKI.** Issue a subordinate CA certificate (with CA basic constraints) from the corporate root, import it into the FortiGate with its private key, and set `caname` to it. Endpoints already trust the corporate root, so no extra deployment is needed. If you run several FortiGates, this also means you have one CA to manage instead of one per firewall.

> **Real world:** Some applications ignore the operating system store. Firefox can keep its own store unless enterprise roots are enabled by policy. Many mobile apps, and anything that **pins** its certificate (banking apps, some update agents), will refuse a re-signed certificate whatever CA you deploy. Those destinations need an exemption, not a CA.

## Exemptions

Exempt traffic is not decrypted: the profile treats it as certificate inspection. Plan exemptions for privacy (legal, HR, medical), for pinned applications, and for performance. In a full inspection profile you can exempt by:

- **FortiGuard web category** (`set type fortiguard-category`, the default type). The built-in deep inspection profiles exempt *Finance and Banking*, *Health and Wellness* and *Personal Privacy* (category IDs 31, 33 and 87).
- **Address** (`set type address` or `address6`). Firewall address objects or groups: IP, range, subnet, FQDN or geography. The address objects need interface *any*.
- **Wildcard FQDN** (`set type wildcard-fqdn`). These entries reference `config firewall wildcard-fqdn custom` (or `group`) objects, not ordinary address objects. The built-in profiles use this type for their long list of `g-…` entries (update and app-store servers for Apple, Microsoft, Google, Adobe and others).
- **Reputable websites.** FortiGuard's allowlist of well-known sites (`set allowlist enable`, disabled by default).

```text
FGT-HQ # config firewall wildcard-fqdn custom
FGT-HQ (custom) # edit "g-payroll-saas"
FGT-HQ (g-payroll-saas) # set wildcard-fqdn "*.payroll.example.net"
FGT-HQ (g-payroll-saas) # end
FGT-HQ # config firewall ssl-ssh-profile
FGT-HQ (ssl-ssh-profile) # edit "SSL-Deep-HQ"
FGT-HQ (SSL-Deep-HQ) # config ssl-exempt
FGT-HQ (ssl-exempt) # edit 1
FGT-HQ (1) # set type fortiguard-category
FGT-HQ (1) # set fortiguard-category 31
FGT-HQ (1) # next
FGT-HQ (ssl-exempt) # edit 2
FGT-HQ (2) # set type wildcard-fqdn
FGT-HQ (2) # set wildcard-fqdn "g-payroll-saas"
FGT-HQ (2) # end
FGT-HQ (SSL-Deep-HQ) # set ssl-exemption-log enable
FGT-HQ (SSL-Deep-HQ) # end
```

Exemptions are not logged by default (`ssl-exemption-log disable`). SSL anomalies, meaning invalid certificates, are logged by default (`ssl-anomaly-log enable`). You find both under the UTM log type, SSL subtype.

> **Exam tip:** An exemption by category still requires a FortiGuard rating lookup to know the category. If FortiGuard is unreachable, category exemptions cannot be matched reliably. Address-based exemptions do not depend on FortiGuard.

## Applying the profile

The profile is set per firewall policy in profile-based NGFW mode:

```text
FGT-HQ # config firewall policy
FGT-HQ (policy) # edit 10
FGT-HQ (10) # set utm-status enable
FGT-HQ (10) # set ssl-ssh-profile "SSL-Deep-HQ"
FGT-HQ (10) # set av-profile "default"
FGT-HQ (10) # set webfilter-profile "WF-Staff"
FGT-HQ (10) # end
```

Keep two points in mind:

- An SSL/SSH profile only changes what other profiles can see. A policy with deep inspection and no AV, web filter, IPS or application control profile decrypts traffic for no benefit.
- `no-inspection` should not be combined with other security profiles. They would only see encrypted bytes.

## Lab it yourself

The FortiGate-VM permanent trial has no FortiGuard services, but deep inspection itself works. A **static URL filter** is local and needs no license.

1. Use two interfaces: `port1` toward the internet and `port2` toward a Linux or Windows client. One outbound policy with NAT is enough.
2. Create a web filter profile with a static URL filter entry that blocks `*.example.com/blocked*` (a path match).
3. Apply the profile with `certificate-inspection` and browse to a matching HTTPS URL. The path is invisible, so the entry never matches.
4. Clone `deep-inspection`, apply the clone and retry. The page is now blocked, and the browser complains about Fortinet_CA_SSL.
5. Download the CA from the profile, import it into the client's trusted root store and retry. The block page now loads cleanly.
6. Inspect the certificate in the browser. The issuer is the FortiGate CA, not the public CA.

## Key takeaways

- Certificate inspection reads only the handshake (SNI or certificate CN). Full inspection decrypts the payload by terminating TLS on both sides.
- Built-in profiles: `certificate-inspection`, `deep-inspection` and `no-inspection` are read-only, and `custom-deep-inspection` is editable. Clone or create a profile to customise it.
- Outbound deep inspection uses `server-cert-mode re-sign`: trusted sites are signed by `caname` (Fortinet_CA_SSL) and untrusted ones by `untrusted-caname` (Fortinet_CA_Untrusted).
- Install Fortinet_CA_SSL, or better, an enterprise subordinate CA, on endpoints. Never install Fortinet_CA_Untrusted.
- Exempt by category (built-in defaults 31/33/87), address, wildcard-FQDN object (`config firewall wildcard-fqdn custom`) or reputable-site allowlist. Pinned apps need exemptions.
- Port mapping applies to proxy-mode policies. Flow mode inspects TLS on all ports.
- The SSL profile is useless without other security profiles on the same policy.
