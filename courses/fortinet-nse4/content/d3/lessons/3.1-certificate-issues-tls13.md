## Reading a certificate warning like a FortiGate engineer

When deep inspection is on and a user reports a certificate warning, **look at the issuer of the certificate the browser received** before anything else. That one field tells you which of two very different problems you have.

| Issuer shown to the user | Meaning | Fix |
|---|---|---|
| Fortinet_CA_SSL (or your `caname` CA) | The real server certificate was fine; the client does not trust the FortiGate CA | Deploy the CA to the endpoint (GPO, MDM, EMS) |
| Fortinet_CA_Untrusted | FortiGate could not validate the **real** server certificate (self-signed, unknown root, missing intermediate, name mismatch…) and the action is to allow it as untrusted | Investigate the server. Do **not** install this CA |
| The real public CA | The session was not deep-inspected (exempted, certificate inspection, or bypassed) | Check exemptions and which policy matched |

The browser can also complain about a block or warning **replacement page** served over HTTPS under certificate inspection. FortiGate has to sign that page with its own CA, so a client that does not trust the CA sees an error instead of the friendly block page.

## Invalid server certificate actions

A full inspection profile validates every server certificate it intercepts. You choose what happens for each failure type.

| Condition | CLI attribute (per protocol table) | Default | Options |
|---|---|---|---|
| Untrusted issuer | `untrusted-server-cert` | allow | allow / block / ignore |
| Expired | `expired-server-cert` | block | allow / block / ignore |
| Revoked | `revoked-server-cert` | block | allow / block / ignore |
| Validation timed out | `cert-validation-timeout` | allow | allow / block / ignore |
| Validation failed | `cert-validation-failure` | block | allow / block / ignore |

In the GUI, the deep-inspection choices read:

- **Keep Untrusted & Allow** (`allow`): the session passes, but the client gets a certificate signed by Fortinet_CA_Untrusted, so the user still sees a warning.
- **Trust & Allow** (`ignore`): the session passes and FortiGate re-signs with the trusted CA, so the warning is hidden. Use it only for a destination you have personally verified, such as an internal server with a private CA.
- **Block**: the session is dropped.

*Trust & Allow* only makes sense with deep inspection. With certificate inspection nothing is re-signed, so the client always sees the real certificate and there is no warning for FortiGate to hide or keep.

> **Exam tip:** "Users no longer get a warning for a server with a self-signed certificate, and the security team is unhappy" is the classic sign that `untrusted-server-cert` was set to `ignore` (Trust & Allow), or that someone installed Fortinet_CA_Untrusted on the endpoints.

### Server certificate SNI check

`sni-server-cert-check` compares the SNI in the Client Hello with the CN/SAN of the server certificate.

- `enable` (default): on a mismatch, FortiGate uses the certificate CN for URL filtering, so a forged SNI cannot sneak past the category check.
- `strict`: a mismatch closes the connection.
- `disable`: no check.

### Protocol compliance

- `unsupported-ssl-version` (default block), `unsupported-ssl-cipher` and `unsupported-ssl-negotiation` (default allow) control sessions FortiGate cannot proxy.
- `min-allowed-ssl-version` (default `tls-1.1` for HTTPS and FTPS) sets the lowest version accepted. It is unavailable in certificate inspection, because FortiGate does not negotiate the version in that mode.

### Client certificates

`client-certificate` for HTTPS defaults to **bypass**. When a server requests a client certificate (mutual TLS), FortiGate cannot present the user's certificate, because it does not hold the user's private key. Deep inspection of such sessions therefore breaks authentication, so the default is to let them through uninspected. Your other choices are `inspect` and `block`.

## Pinning, HSTS and QUIC

- **Certificate pinning.** The application only accepts one specific certificate or public key. A re-signed certificate always fails, whatever CA you deploy. The fix is an address or category exemption.
- **HSTS.** Browsers refuse to let the user click through a warning for HSTS sites. A missing CA on the endpoint therefore looks like a hard failure rather than a warning.
- **QUIC / HTTP/3.** QUIC runs TLS 1.3 over UDP 443. In a certificate inspection profile, HTTP/3 is fixed to *bypass*. In full inspection you choose `quic inspect | bypass | block` (default `inspect`, since 7.4.2). These three options govern proxy-mode policies; flow-mode policies inspect HTTP/3 in the IPS engine, with full inspection. Blocking QUIC makes browsers fall back to TCP/TLS, where the rest of your inspection applies. Application control signatures for QUIC are another common way to force that fallback.

## What TLS 1.3 changes

TLS 1.3 encrypts everything after the Server Hello, **including the server certificate**. A passive device can still read the SNI in the Client Hello, but it can no longer read the certificate.

- **Certificate inspection with TLS 1.3** relies on SNI for the hostname. To validate the certificate anyway, FortiGate can actively **probe** the server: it opens its own connection, fetches the certificate and checks it before the client-to-server HTTPS session is established. If the probe fails (TCP/TLS failure, misrouting, untrusted chain), `cert-probe-failure` decides the outcome. The default is `allow`, which bypasses the session; `block` drops it. This option applies to custom profiles in flow-mode policies when `inspect-all` is disabled. It is not available on models with 2 GB of RAM or less. The probe's source interface/IP is set under `config ips global` → `config tls-active-probe`.
- **Encrypted Client Hello (ECH)** goes one step further and hides the real SNI inside an encrypted inner Client Hello. That defeats certificate inspection completely. FortiOS can block sessions that carry ECH (`set encrypted-client-hello block` under `config https`, the default; Fortinet documents it for certificate inspection profiles), so the browser falls back to a normal Client Hello with a visible SNI. A DNS filter profile can also strip the ECH parameters from DNS (DoH) HTTPS records (`set strip-ech enable`), so the client never learns an ECH configuration. 8.0 also has an `ech-outer-sni` table in the SSL/SSH profile to match ECH sessions by their outer SNI.
- **Deep inspection with TLS 1.3** works normally. FortiGate is a TLS 1.3 endpoint on both legs.

### Post-quantum key exchange in 8.0

Browsers now offer **hybrid post-quantum key exchange groups** in TLS 1.3, most commonly `X25519MLKEM768`, which combines classical X25519 with ML-KEM. In FortiOS 8.0:

- **Proxy-mode deep inspection** can negotiate hybrid (X25519MLKEM768, SecP256r1MLKEM768, SecP384r1MLKEM1024) and pure ML-KEM groups (new in 8.0). Previously the proxy downgraded these handshakes to non-ML-KEM key exchange, and servers that insist on PQC became unreachable.
- **Flow-mode deep inspection** already gained hybrid key exchange support in 7.6.5, and 8.0 keeps it.
- **8.0.1** adds `tls-handshake-mode {sync | dual}` in the profile (`config ssl` or per `https`/`ftps`/`dot`).
  - `sync` (default): the FortiGate-to-server leg follows the server's choice of version, key exchange and signature.
  - `dual`: each leg is negotiated independently, so a classical-only client (X25519, even TLS 1.2) can still reach a PQC-only server.
- The SSL UTM log (`subtype="ssl"`, `eventtype="ssl-handshake"` when `ssl-handshake-log` is enabled) shows each leg separately, with fields such as `tlsver`, `kxproto`, `kxcurve` and `armtype="client-to-proxy"` / `"proxy-to-server"`.
- 8.0.1 also adds post-quantum certificate **authentication** support for deep inspection in flow mode.

### "TLS 1.3 VPN key negotiation"

Fortinet has not published any detail behind this 3.1 bullet, and the wording is ambiguous. The only 8.0 feature whose name combines TLS 1.3 and VPN is **TLS 1.3 based VPN over TCP**, which is also the 5.1 bullet "TLS 1.3-based VPN negotiation". Because this bullet sits under encrypted-traffic inspection, an exam item could just as well be about **TLS 1.3 key exchange** in SSL inspection, meaning the hybrid PQC groups and `tls-handshake-mode` above. Be ready for both. The VPN feature in short (Domain 5 covers it in depth):

- IPsec normally runs IKE on UDP 500/4500. Some networks block that, so FortiOS already supported IKE/ESP over **TCP**. In 8.0 that TCP transport can be wrapped in **TLS 1.3**. To a middlebox, the tunnel looks like ordinary TLS on the IKE TCP port (`ike-tcp-port` under `config system settings`, default 443 on new 7.6.1+ configurations).
- It is enabled per VDOM with `config system settings` → `set ike-tcp-service enable` and `set ike-tls-service enable`. `ike-tcp-service` is disabled by default. Site-to-site tunnels need `set transport auto` in phase 1, which tries UDP first and falls back to TCP/TLS. With `ike-tcp-service` enabled, dial-up gateways behave as if set to auto.
- It is supported FortiGate-to-FortiGate (site-to-site and dial-up). FortiClient does not support it yet.
- `diagnose vpn ike gateway list` shows `transport: TLS` for such a tunnel.
- IKEv2 still performs the actual IPsec key exchange (the SA keys are IKE-derived). TLS 1.3 protects and disguises the transport. Do not confuse this with SSL inspection: FortiGate is the TLS endpoint of its own tunnel, not intercepting anyone.

## A troubleshooting checklist

1. **Which policy matched, and which SSL profile is on it?** `diagnose debug flow` shows the policy ID. `diagnose sys session list` shows the session.
2. **What is the certificate issuer on the client?** Use the table at the top of this lesson.
3. **Is the destination exempt?** Check category exemptions (they need a working FortiGuard rating), address exemptions and reputable websites.
4. **Is it really TLS on a mapped port?** For proxy policies, a TLS service on 8443 is not inspected unless HTTPS ports include 8443 or `inspect-all` is used.
5. **Is the application pinning or using QUIC?** Exempt it, or block QUIC.
6. **Check the logs.** Look in Log & Report → Security Events for SSL logs. With `ssl-anomaly-log` enabled (the default), sessions with invalid certificates are recorded under the UTM log type, SSL subtype, together with the certificate problem.

## Lab it yourself

On the trial VM (no FortiGuard needed):

1. Stand up a Linux web server behind `port2` with a **self-signed** certificate, and browse to it through a deep-inspection policy. The issuer shown is Fortinet_CA_Untrusted.
2. Set `untrusted-server-cert block` in a cloned profile and retry. The session is blocked and an SSL anomaly log appears.
3. Set it to `ignore` and retry. The warning disappears. Discuss why this is dangerous.
4. Run `openssl s_client -connect <server>:443 -servername wrong.example.com` from a client to see the SNI check in action, then repeat with `sni-server-cert-check strict`.

## Key takeaways

- The issuer on the client tells you the fault: Fortinet_CA_SSL means a missing endpoint CA; Fortinet_CA_Untrusted means a bad server certificate.
- Invalid-certificate actions are allow / block / ignore. *Keep Untrusted & Allow* keeps the warning; *Trust & Allow* hides it.
- Defaults: untrusted allow, expired/revoked block, validation timeout allow, validation failure block, client-certificate bypass.
- TLS 1.3 hides the server certificate. Certificate inspection uses SNI plus an optional certificate probe (`cert-probe-failure`), and ECH is blocked by default so SNI stays visible.
- 8.0 proxy-mode deep inspection supports hybrid PQC key exchange (X25519MLKEM768); flow mode has had it since 7.6.5. 8.0.1 adds `tls-handshake-mode dual` (default `sync`) to translate between PQC and classical legs.
- "TLS 1.3 VPN key negotiation" is ambiguous: most likely 8.0's IKE/ESP over TCP wrapped in TLS 1.3 (`ike-tcp-service` + `ike-tls-service`), where IKE still negotiates the IPsec keys; possibly TLS 1.3 key exchange handling in inspection. Know both.
- Pinned apps and mutual-TLS sites need exemptions, not more certificates.
