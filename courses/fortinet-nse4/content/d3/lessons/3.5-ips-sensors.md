## The pieces of FortiGate IPS

FortiGate's intrusion prevention is built from several components:

- **IPS engine** (`ipsengine`). The same flow engine that runs application control and flow AV. It reassembles streams, decodes protocols and matches signatures.
- **Protocol decoders.** Parsers for HTTP, DNS, SMB, TLS and many others. Signatures match on decoded fields, not raw bytes alone, which is why IPS is resistant to simple evasion.
- **IPS signatures (Attack Definitions).** Delivered by FortiGuard with the **IPS subscription**. There are two database sizes: **regular** and **extended**. `config ips global` → `set database extended` is the default on most models. Entry-level models may differ, and models without a CP9 (and VMs with fewer than eight vCPUs) receive a "slim" extended set.
- **AI/Machine Learning IPS Definitions.** A separate FortiGuard package (also needs the IPS subscription) used when `machine-learning-detection` is enabled. It is enabled by default.
- **IPS sensor.** The profile you attach to a policy with `set ips-sensor`.

Anomaly-based protection against floods and scans (SYN flood, port scan, ICMP sweep) is configured in **DoS policies**, not in IPS sensors. Keep the two apart on the exam.

## What a signature carries

Every predefined signature has attributes you can filter on, plus built-in defaults:

| Attribute | Values (examples) |
|---|---|
| Severity | info, low, medium, high, critical |
| Target (location) | server, client |
| Protocol | HTTP, DNS, SMB, TCP, UDP… |
| OS | Windows, Linux, BSD, macOS, other… |
| Application | Apache, IIS, Microsoft Office, Exchange… |
| CVE | CVE references, filterable in a sensor entry with `set cve` |
| Default status | enabled / disabled |
| Default action | pass / block |

The **default action** is FortiGuard's recommendation. Many low-severity or noisy signatures default to **pass** (they only log). Others are **disabled** by default, so they are not even evaluated unless you enable them.

## Building an IPS sensor

A sensor (`config ips sensor`) is an ordered list of **entries**. Each entry is either:

- **Signatures**: specific rule IDs (`set rule 58322`).
- **Filter**: a dynamic selection by severity, location, protocol, OS, application, CVE and so on. A signature must match **all** of the selected attributes. New signatures that match the filter are included automatically.

For each entry you set:

| Setting | CLI | Notes |
|---|---|---|
| Action | `action pass | block | reset | default` | GUI: Allow, Monitor, Block, Reset, Default, Quarantine. `default` uses each signature's own default action |
| Status | `status enable | disable | default` | `default` keeps each signature's default status. `enable` turns on signatures that are disabled by default |
| Logging | `log enable` (default), `log-packet` | Packet logging stores the matching packets and needs a disk or FortiAnalyzer |
| Quarantine | `quarantine attacker`, `quarantine-expiry` (default 5m) | Bans the attacker's IP |
| Rate-based | `rate-count`, `rate-duration` (default 60 s), `rate-track src-ip/dest-ip/…`, `rate-mode` | Triggers only when the signature fires N times in the period. Signature entries only; filters have no rate settings |
| Exempt IPs | `config exempt-ip` with `src-ip` / `dst-ip` | Skip this entry for specific hosts (false positive handling). Offered on signature entries |

Entries are evaluated top-down and the **first entry that contains the signature decides** its action. Put specific signature entries (exceptions) above broad filters.

At the sensor level:

- `set scan-botnet-connections disable | block | monitor` checks outgoing connections against the FortiGuard **botnet C&C IP** database.
- `set block-malicious-url enable` blocks URLs in the local malicious URL database (drive-by exploits).
- `set extended-log enable` adds detail to IPS logs.

```text
FGT-HQ # show ips sensor "IPS-DMZ-Web"
config ips sensor
    edit "IPS-DMZ-Web"
        set block-malicious-url enable
        set scan-botnet-connections block
        config entries
            edit 1
                set rule 41582
                set status enable
                set action pass
                config exempt-ip
                    edit 1
                        set src-ip 192.0.2.50 255.255.255.255
                        set dst-ip 10.0.20.10 255.255.255.255
                    next
                end
            next
            edit 2
                set location server
                set severity medium high critical
                set protocol HTTP
                set os Linux
                set status enable
                set action block
            next
        end
    next
end
```

Entry 1 is an exception: one signature (ID 41582 is illustrative) is allowed (with logging) for traffic from a vulnerability scanner at 192.0.2.50 to the web server 10.0.20.10. Entry 2 blocks every server-targeted medium/high/critical HTTP signature for Linux, including signatures that are disabled by default, because the entry's status is `enable`.

FortiOS ships predefined sensors: **default** (critical, high and medium signatures, default actions), **all_default** (all signatures, default actions), **all_default_pass** (all signatures, pass/monitor), **high_security** (critical/high/medium set to block, low at default action), the role-specific **protect_client**, **protect_email_server** and **protect_http_server**, and **wifi-default**. They make a good starting point, but they are broad. Custom sensors that match the protected assets perform better and produce fewer false positives.

> **Exam tip:** "Protect a Linux web server in the DMZ" → a filter with **location server**, **OS Linux**, **protocol HTTP** and the relevant severities, applied to the **inbound** (WAN → DMZ) VIP policy. "Protect users browsing the internet" → **location client** on the outbound policy.

## IPS and encrypted traffic

IPS sees decoded TLS handshakes with any SSL profile. Exploits **inside** HTTPS can only be matched when the policy uses **deep inspection**. For an inbound web server you own, that is the *Protecting SSL Server* profile type, where you upload the server's certificate and key (`server-cert-mode replace`). For outbound traffic it is the usual re-signing profile.

## AI/ML-based detection

With `machine-learning-detection enable` (the default in `config ips global`) and the **AI/Machine Learning IPS Definitions** package installed, specific signatures act as a first-stage filter, and an ML classifier then decides whether the traffic really is malicious. The documented example is `Backdoor.Cobalt.Strike` (rule 57293). The ML database version appears in `get system status` as `IPS-MLDB`. You configure nothing new in the sensor: you include the ML-backed signatures like any others.

### DNS tunneling detection (8.0)

DNS tunnels hide C2 traffic or exfiltrated data in DNS queries and responses. FortiOS 8.0 detects them with an AI/ML model exposed as the IPS signature **`DNS.Tunnelling`** (rule ID **58322**, service UDP/DNS, severity **low**, default action **pass**).

- Requirements: an IPS subscription, `machine-learning-detection enable`, the AI/ML IPS Definitions package, and at least one policy using an IPS sensor so that the definitions download.
- Because the signature defaults to pass, **you must add it to a sensor with `action block`** if you want blocking.
- Deep inspection is **not** required: classic DNS is cleartext. Certificate inspection and proxy-mode policies are supported.
- A built-in allowlist of well-known domains (not viewable) reduces false positives. IPS debug output shows `exclude domain …` when it applies.
- The log is an ordinary IPS log: `subtype="ips"`, `attack="DNS.Tunnelling"`, `attackid=58322`, `msg="backdoor: DNS.Tunnelling"`, `action="dropped"`.

```text
FGT-HQ # config ips sensor
FGT-HQ (sensor) # edit "IPS-DNS"
FGT-HQ (IPS-DNS) # config entries
FGT-HQ (entries) # edit 1
FGT-HQ (1) # set rule 58322
FGT-HQ (1) # set status enable
FGT-HQ (1) # set action block
FGT-HQ (1) # end
FGT-HQ (IPS-DNS) # end
```

## FortiGuard Extended SaaS DB

Fortinet's 8.0 documentation does not use the blueprint phrase "FortiGuard Extended SaaS DB". The closest 8.0 feature, and the one this course maps it to, is the **Expanded CASB SaaS application database**. The FortiGuard database used by **inline CASB** grew to more than **2,700** SaaS applications, giving inline CASB profiles much broader coverage for controlling SaaS activity and tenants. Key facts:

- You view it under Security Profiles → Inline-CASB → **SaaS Application** tab.
- The CASB database is delivered from FortiGuard (FDS) to licensed devices. The 8.0 feature page lists it as available to customers with the Firmware & General Updates licence.
- Inline CASB is a **proxy-only** profile and generally needs deep inspection.
- 8.0.1 adds **SaaS application risk visibility**.

It is not an IPS feature, but it lives in this blueprint topic as part of "knowing which FortiGuard database does what".

## DLP and GenAI awareness

The same IPS engine also carries 8.0's GenAI application signatures (application control category **GenAI**, ID 36, from the **GenAI Application Definitions** package). Combined with DLP:

- Application control identifies **which** AI service is in use (and, with deep inspection and extended logging, the model, use case and prompt).
- DLP (proxy mode, deep inspection) decides whether **what is sent** to the chatbot contains sensitive data.
- 8.0 also adds visibility into **agentic AI protocols** such as MCP and agent-to-agent traffic.

## Use case: blocking known exploits

A new critical vulnerability is published for a product you expose (for example, a VPN appliance or web application behind a VIP):

1. Confirm FortiGuard has published a signature: check Security Profiles → IPS Signatures, or `get ips rule status`.
2. Add a **signature entry**, or an entry filtered by `set cve <CVE-ID>`, with `status enable` and `action block`, above the general filters of the sensor on the inbound policy.
3. Use deep inspection (*Protecting SSL Server*) if the exploit travels inside TLS.
4. Verify with an IPS log (`execute log filter category 4`) showing the attack name and `action="dropped"`.
5. This is a temporary shield (**virtual patching**). Patch the product anyway.

## Key takeaways

- IPS = IPS engine + protocol decoders + FortiGuard signatures (regular/extended) + optional AI/ML definitions. Floods and scans belong to DoS policies.
- A sensor is an ordered list of signature or filter entries. A filter must match all selected attributes. The first entry containing a signature wins.
- Entry actions: pass, block, reset, default (GUI adds Monitor and Quarantine). `status enable` turns on default-disabled signatures.
- Exempt IPs, rate-based thresholds, packet logging, botnet scanning and malicious URL blocking are sensor features.
- `DNS.Tunnelling` (58322) is ML-based, severity low and default pass, so add it with action block. No deep inspection is needed.
- "FortiGuard Extended SaaS DB" most likely means the 8.0 expanded inline CASB SaaS database (2,700+ apps, proxy-only CASB).
- Exploits inside TLS need deep inspection. Signatures are a virtual patch, not a substitute for patching.
