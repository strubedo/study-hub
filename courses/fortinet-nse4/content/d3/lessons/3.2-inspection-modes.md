## Two engines, two philosophies

Every firewall policy that carries security profiles is processed by one of two inspection paths. You choose the path per policy (in profile-based NGFW mode) with `set inspection-mode flow | proxy`. **Flow is the default.**

- **Flow-based inspection** is done by the **IPS engine** (`ipsengine` process). Packets keep moving while the engine reassembles streams and runs pattern matching on them. It is a single-pass architecture: IPS, application control, flow AV, flow web filter and DNS filter share the same engine.
- **Proxy-based inspection** is done by the proxy daemons (mainly **WAD** for HTTP/HTTPS and other protocols, with `scanunit` doing the AV scanning). FortiGate terminates the client's TCP session, opens a second TCP session to the server, and works on whole application-layer objects, such as complete HTTP requests and responses or whole files and emails.

| Aspect | Flow-based | Proxy-based |
|---|---|---|
| Daemon | IPS engine | WAD / proxy daemons + scanunit |
| TCP handling | One session, packets forwarded as inspected | Two sessions (client↔FortiGate, FortiGate↔server) |
| File handling | Stream-scanned while it passes | Buffered (up to the oversize limit), then scanned |
| Latency/throughput | Lower latency, higher throughput | Higher latency, more memory |
| User feedback on an AV block | If part of the file was already forwarded: session reset, and the block page appears on the **next** attempt (the IPS engine caches the URL). A detection at the very start of the response can get the block page at once | Replacement message immediately |
| Large downloads | Data flows continuously | Client comforting needed to stop timeouts |
| Feature set | Most features | Every feature, including proxy-only ones |
| Hardware offload | NTurbo can accelerate flow sessions | Proxy sessions are handled by the CPU |

> **Exam tip:** "The user downloads EICAR over HTTP through a flow-mode policy. The first attempt just fails and the browser shows a connection error. On the second attempt a block page appears." That is expected flow-mode behaviour, not a bug.

## What only proxy mode can do

The FortiOS 8.0 feature comparison lists these profiles as **proxy-only**:

- Video filter
- Inline CASB
- ICAP
- Web application firewall
- SSH filter
- WebSocket traffic inspection (new in 8.0)

Inside the profiles that both modes support, several features are proxy-only:

| Profile | Proxy-only features |
|---|---|
| Antivirus | Content disarm and reconstruction (CDR), client comforting, FortiNDR inline detection |
| Web filter | Category usage quota, web profile override, full proxy options (flow mode supports only HTTP POST action and remove cookies) |
| Email filter | HELO/EHLO DNS check, return-address DNS check, DNSBL/ORBL, phishing URL check, anti-spam IP check, spam checksum/URL checks, submit spam to FortiGuard |
| DLP | Fingerprint and watermark filters. DLP in flow mode is partial and CLI-only |

Some flow-mode limitations are worth memorising:

- In flow mode, **local and remote (external feed) categories** do not support the *warning* and *authenticate* actions and cannot be overridden.
- Flow web filtering does not support the file filter.
- The DNS filter works in both modes, but the conditional DNS forwarder works only in proxy mode.

> **Watch out:** On physical FortiGate models with **2 GB of RAM or less** (for example the 40F and 60F families), proxy-only profiles are not supported and the *Feature set* selector is hidden (since 7.4.4). Antivirus, web filter, file filter and email filter profiles there are flow-only. Proxy-based inspection of email protocols came back for 2 GB models in 7.6.5 and is supported in 8.0. If proxy features are missing on such a box, the cause is memory, not licensing. **FortiGate-VMs are exempt**: they keep proxy features whatever their memory size, although Fortinet recommends at least 4 GB.

## Matching profiles to the policy mode

Each of the antivirus, web filter, DLP, file filter and email filter profiles has a `feature-set` (`flow` or `proxy`), and it **must match** the policy's inspection mode. A proxy-feature-set AV profile cannot be selected on a flow policy. In the GUI, proxy-only options are marked with a "P" icon.

```text
FGT-HQ # config firewall policy
FGT-HQ (policy) # edit 20
FGT-HQ (20) # set inspection-mode proxy
FGT-HQ (20) # set ssl-ssh-profile "custom-deep-inspection"
FGT-HQ (20) # set av-profile "AV-Proxy"
FGT-HQ (20) # set webfilter-profile "WF-Proxy"
FGT-HQ (20) # set profile-protocol-options "PO-Staff"
FGT-HQ (20) # end
```

If the *Feature set* control does not appear in the GUI, enable it with:

```text
FGT-HQ # config system settings
FGT-HQ (settings) # set gui-proxy-inspection enable
FGT-HQ (settings) # end
```

IPS sensors and application control sensors have no feature set. They always run in the IPS engine, even on a proxy-mode policy. A proxy policy hands the decrypted stream to the IPS engine for those profiles.

## Profile-based vs policy-based NGFW mode

Separate from flow/proxy, each VDOM has an **NGFW mode** (`config system settings` → `set ngfw-mode profile-based | policy-based`).

| | Profile-based (default) | Policy-based |
|---|---|---|
| How applications/URL categories are controlled | Application control and web filter **profiles** attached to firewall policies | Applications and URL categories referenced **directly** in security policies |
| Policy tables | `config firewall policy` | `config firewall policy` (SSL inspection and authentication) + `config firewall security-policy` (security rules) |
| Inspection mode | Flow or proxy, per policy | Flow only |

Most NSE 4 scenarios assume profile-based mode. Know that policy-based mode exists, that it is flow-only, and that it lets you write rules such as "allow application X for group Y" without building a profile first.

## Choosing a mode based on security needs

Pick **flow** when:

- Throughput and latency matter most (data centre east-west, VoIP-heavy branches).
- The required features are IPS, application control, DNS filter, and category-level web filtering, all of which flow handles fully.
- The box is a small model with limited memory.

Pick **proxy** when:

- You need a proxy-only feature: CDR, WAF, ICAP, inline CASB, video filter, category quotas, web profile override, or DLP fingerprinting.
- You want immediate replacement messages and the most thorough file scanning, with complete buffering and archive handling.
- You need SMTP anti-spam checks (HELO/DNSBL) or SSH filtering.

A common design runs **flow** on most policies and **proxy** only on the specific policy that needs a proxy feature, for example the guest Wi-Fi policy with a video filter or the policy toward SaaS apps with inline CASB.

> **Real world:** Proxy mode is not "more secure" in a vague sense. Both modes rely on the FortiGuard AV engine and its signature databases. The practical differences are user experience (block pages, comforting), the proxy-only features, and resource cost. Do not move a whole site to proxy mode to fix a problem that a single profile setting would solve.

## How the two engines see a file

**Flow mode (AV engine 7.0 and later):** the IPS engine uses **stream-based scanning** for HTML and JavaScript, scanning partial buffers as data passes. Other supported files are scanned against the flow database. Some features force a **full scan**, where the whole file is cached and passed to `scanunit`: machine-learning detection, the extreme database, grayware checks, mobile malware, external blocklists, the EMS feed, outbreak prevention, DLP and file filter. The counters "FlowAV default scan" and "FlowAV legacy scan" in `diagnose test application ipsmonitor 24` show which path was used.

**Proxy mode:** WAD decides whether a file can be scanned **in-process** (stream-based, `scan-mode default`). DLP, quarantine, outbreak prevention, external blocklists, the EMS feed, CDR and AI scanning force a hand-off to `scanunit`. `set scan-mode legacy` in the AV profile turns stream-based scanning off, mainly for troubleshooting.

## Lab it yourself

On the trial VM (three policies maximum):

1. Create two policies from `port2` to `port1`: policy 1 for one client IP in **flow** mode, and policy 2 for a second client IP in **proxy** mode. Both use the same static URL filter (a local feature, no license needed) and `custom-deep-inspection`.
2. Browse to a blocked URL from each client and compare the block behaviour.
3. Run `diagnose sys session list` while a download is running and compare the session entries. The proxy-mode session shows proxy-related flags, and `diagnose wad session list` shows the WAD side.
4. If *Feature set* is missing in the GUI, run `set gui-proxy-inspection enable`. The 2 GB rule applies to physical models only, so the trial VM keeps its proxy features.

## Key takeaways

- Flow (default) = IPS engine, single pass, low latency. Proxy = WAD/scanunit, full buffering, two TCP sessions.
- Proxy-only profiles: video filter, inline CASB, ICAP, WAF, SSH filter, WebSocket inspection. Proxy-only features include CDR, client comforting, category quota, web profile override and DLP fingerprinting.
- Profile `feature-set` must match the policy `inspection-mode`. IPS and application control always run in the IPS engine.
- In flow mode an AV block on a partly forwarded file resets the session, and the replacement message is shown on the next attempt.
- Physical models with 2 GB RAM or less have no proxy-only features (except email proxy inspection, back since 7.6.5). FortiGate-VMs are exempt.
- Policy-based NGFW mode references applications and URL categories directly in security policies and is flow-only.
