## Reading IPS events

IPS detections are UTM logs with `subtype="ips"`. The CLI filter category is **4**.

```text
FGT-HQ # execute log filter category 4
FGT-HQ # execute log display
1: date=2026-10-28 time=16:41:09 eventtime=1793223669000000000 tz="-0500"
logid="0419016384" type="utm" subtype="ips" eventtype="signature"
level="alert" vd="root" severity="high" srcip=10.0.1.37 srcport=50812
srcintf="port2" dstip=203.0.113.77 dstport=443 dstintf="port1" proto=6
service="HTTPS" policyid=10 sessionid=120934 action="dropped"
attack="Backdoor.Cobalt.Strike" attackid=57293 profile="IPS-Client"
ref="http://www.fortinet.com/ids/VID57293"
msg="backdoor: Backdoor.Cobalt.Strike" crscore=30 craction=8192 crlevel="high"
```

Fields to read:

- `attack` and `attackid`: the signature name and ID. `ref` links to the FortiGuard encyclopedia entry.
- `action`: `dropped` for block, `reset` for reset, `detected` for Monitor (pass with logging). *Allow* (pass without logging) writes no IPS log.
- `srcip`/`srcintf` and `dstip`/`dstintf` show who opened the session. Here the internal client opened it toward the C2 server.
- `severity` comes from the signature. `crscore` and `crlevel` are the client-reputation contribution.
- `profile` and `policyid`: which sensor and policy acted.
- `service="HTTPS"` with a payload-level signature implies the session was deep-inspected.

The GUI equivalents are Log & Report → Security Events → Intrusion Prevention and the FortiView threat views. `get system performance status` also shows how many IPS attacks were blocked in the last minute.

## IPS high-CPU usage

Because IPS, application control, flow AV, flow web filter and DNS filter all run in the IPS engine, a busy `ipsengine` is the most common cause of high CPU on a FortiGate running security profiles.

### Step 1: confirm where the CPU goes

```text
FGT-HQ # get system performance status
CPU states: 91% user 6% system 0% nice 3% idle 0% iowait 0% irq 0% softirq
CPU0 states: 93% user 5% system 0% nice 2% idle 0% iowait 0% irq 0% softirq
CPU1 states: 89% user 7% system 0% nice 4% idle 0% iowait 0% irq 0% softirq
Memory: 4055272k total, 2433163k used (60.0%), 1216581k free (30.0%), 405528k freeable (10.0%)
Average network usage: 612044 / 598112 kbps in 1 minute, 588233 / 571021 kbps in 10 minutes, 540112 / 529023 kbps in 30 minutes
Average sessions: 48211 sessions in 1 minute, 47100 sessions in 10 minutes, 45022 sessions in 30 minutes
Average session setup rate: 412 sessions per second in last 1 minute, 398 sessions per second in last 10 minutes, 377 sessions per second in last 30 minutes
Virus caught: 0 total in 1 minute
IPS attacks blocked: 3 total in 1 minute
Uptime: 41 days,  2 hours,  17 minutes
```

A very high **user** percentage means user-space daemons are busy (the IPS engine, WAD, and so on). High **system** or **softirq** points to the kernel's packet handling instead. Next, find the process:

```text
FGT-HQ # diagnose sys top 2 10
Run Time:  41 days, 2 hours and 17 minutes
91U, 0N, 6S, 3I, 0WA, 0HI, 0SI, 0ST; 3960T, 1188F
       ipsengine     1844      R      88.4     6.1
       ipsengine     1845      R      85.9     5.9
         wad         1201      S       1.2     2.0
       miglogd       2210      S       0.8     0.9
```

The columns are process name, PID, state, CPU% and memory%. Two `ipsengine` processes near 90% confirm that the IPS engine is the bottleneck.

### Step 2: prove it with a bypass test

`diagnose test application ipsmonitor` controls the IPS engine:

| Option | Action |
|---|---|
| `1` | Display IPS engine information |
| `3` / `4` | Display / clear the engine restart log |
| `5` | **Toggle bypass**: the engine keeps running but stops inspecting |
| `10` | IPS queue length |
| `13` | IPS session list |
| `24` | Flow AV statistics |
| `97` / `98` | Start / stop all IPS engines |
| `99` | Restart all IPS engines and the monitor |

Run `diagnose test application ipsmonitor 5` to see `bypass: enable`. If CPU drops sharply, the inspected traffic volume is too high for the model with the current profile design. If CPU stays high, look elsewhere. Run it again to set `bypass: disable`. While bypass is on, **nothing** handled by the IPS engine is inspected, so treat it strictly as a short diagnostic.

### Step 3: reduce the load

- **Apply IPS only where it adds value.** For example, put the server-protection sensor on the inbound VIP policies and a client sensor on outbound internet policies. Do not put a full sensor on high-volume trusted flows such as backup traffic between two internal data centres.
- **Use targeted sensors.** Filters by location, OS, protocol and application load far fewer signatures than "all signatures, all severities, status enable". Enabling every disabled-by-default signature is a classic CPU killer.
- **Keep packet logging off** except while troubleshooting.
- **Leave hardware acceleration on.** `np-accel-mode basic` (NTurbo, the default) offloads flow-inspected sessions to the NP on capable models. `cp-accel-mode` uses the CP for pattern matching.
- **Leave `engine-count 0`** so FortiOS picks the number of engines.
- **Avoid unnecessary deep inspection.** Decryption is also CPU-heavy. Exempt trusted high-volume destinations.
- **Check for engine trouble.** Frequent restarts in `ipsmonitor 3`, or a memory leak, call for a firmware or engine upgrade and a support ticket.

## Fail-open

When the IPS engine cannot keep up and its socket buffer fills, `config ips global` → `set fail-open` decides what happens:

| fail-open | Behaviour when the buffer is full |
|---|---|
| `disable` (default) | New packets that need inspection are **dropped**. Security is kept, availability suffers |
| `enable` | Traffic **passes uninspected** until the engine recovers. Availability is kept, security suffers |

Two details matter:

- Sessions offloaded through **NTurbo** do not support fail-open. If the NTurbo path is overloaded, packets are dropped whatever the setting.
- `socket-size` (model-dependent default) sizes the buffer between the kernel and the IPS engine. A larger value uses more memory, and conserve mode becomes more likely. A smaller value makes fail-open events more frequent. Change it only with Fortinet's guidance.

The same `fail-open` setting also decides what happens to **flow-based** inspection while the unit is in **memory conserve mode** (`disable`: the IPS engine drops new sessions that need flow inspection; `enable`: they pass unscanned). Do not confuse it with `av-failopen` under `config system global`, which governs **proxy-based** inspection during conserve mode.

> **Exam tip:** "Users report that during peak hours some attacks are not logged, and the event log shows that IPS entered fail-open" means the engine is overloaded and `fail-open` is enabled. The fix is to reduce load or size the hardware. Disabling fail-open keeps security but drops traffic instead.

## Keeping signatures current

```text
FGT-HQ # diagnose autoupdate versions | grep -A 6 "Attack Definitions"
Attack Definitions
---------
Version: 35.00412 signed
Contract Expiry Date: Thu Jan  3 2030
Last Updated using scheduled update on Wed Oct 28 01:02:17 2026
Last Update Attempt: Wed Oct 28 13:02:22 2026
Result: No Updates
```

- The IPS engine (**IPS Attack Engine**), the signatures (**Attack Definitions**) and the **AI/Machine Learning IPS Definitions** update separately.
- FortiGuard only pushes IPS packages when **at least one policy uses an IPS sensor**. A new firewall that has none yet shows stale versions for that reason.
- `execute update-now` forces an update check.

## False positives

1. Find the signature (`attack`, `attackid`) and the hosts in the log.
2. Confirm with a packet capture or packet log that the traffic is legitimate.
3. Create a narrow exception: a signature entry above the filters with `action pass` (still logged), or a signature entry that keeps the blocking action but has an `exempt-ip` for the specific source/destination pair.
4. Report it to FortiGuard so the signature can be fixed.

Never disable the whole sensor or switch a broad filter to pass to "fix" one false positive.

## Use cases

- **Shield a vulnerable DMZ server:** a server/OS/protocol filter with block plus a specific CVE entry, on the inbound VIP policy, with *Protecting SSL Server* inspection.
- **Stop DNS tunnelling:** `DNS.Tunnelling` (58322) with block on the policies that carry user DNS. No deep inspection is needed.
- **Contain an infected host:** `quarantine attacker` on botnet or backdoor signatures to ban the source IP for a period.
- **Detect brute force:** rate-based settings (`rate-count`, `rate-duration`, `rate-track src-ip`) on login signatures.

## Lab it yourself

1. Apply a sensor with an entry `severity critical high`, `status enable`, `action block` to the outbound policy. Run `diagnose sys top 2 10` while generating traffic, and note `ipsengine`'s share.
2. Run `diagnose test application ipsmonitor 1` to see engine information, then toggle bypass with option `5`, compare CPU, and toggle it back.
3. Enable `fail-open` and confirm the value with `get ips global`. You will not be able to overload a lab easily, but know the trade-off.
4. Run `diagnose autoupdate versions` on the trial VM and note which packages show no contract.

## Key takeaways

- IPS logs: `subtype="ips"`, logid `0419016384` for signature events, category 4. `action` is dropped, reset or detected.
- High CPU: `get system performance status` (user vs system), `diagnose sys top` (find `ipsengine`), then `ipsmonitor 5` as a bypass test.
- Reduce load with targeted sensors on the right policies, packet logging off, NTurbo/CP acceleration on, and only the deep inspection you need.
- `fail-open` (default disable): disable drops traffic when the IPS buffer is full; enable passes it uninspected. NTurbo sessions cannot fail open.
- IPS packages update only when a policy uses IPS. Check them with `diagnose autoupdate versions`.
- Handle false positives with signature-level pass entries or exempt IPs, never by disabling the sensor.
