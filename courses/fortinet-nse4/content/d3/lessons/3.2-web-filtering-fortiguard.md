## The web filter profile at a glance

A web filter profile (`config webfilter profile`) is attached to a firewall policy with `set webfilter-profile`. It combines several independent tools:

- **Static URL filter.** A local list of URL patterns with block/allow/monitor/exempt actions.
- **FortiGuard category filter.** Cloud rating of every requested domain or URL into one of roughly 90 categories, with a per-category action.
- **Web content filter.** Banned words or patterns on the returned page (scored).
- **Search engine controls.** Safe search, YouTube restrictions, search keyword logging.
- **Rating, proxy and override options.**

FortiOS 8.0 ships three preloaded profiles: **default**, **monitor-all** (flow-based, logs every URL) and **wifi-default**. Like the AV and DLP profiles, a web filter profile has a `feature-set` (`flow` or `proxy`) that must match the policy's inspection mode.

## Order of operations

When a request arrives, the web filter applies its components in a fixed order:

1. **Static URL filter**
2. **FortiGuard web filtering** (category rating)
3. **Web content filter** (banned words)
4. **Web script filter** (ActiveX/Java/cookie removal, proxy options)
5. **Antivirus scanning** of the downloaded content (if an AV profile is on the policy)

This order explains many exam questions:

- A URL filter **block** stops the request before FortiGuard is ever consulted.
- A URL filter **exempt** skips FortiGuard, the content filter, the script filter, AV and DLP (by default all of them; the CLI `set exempt` can narrow the list).
- A URL filter **allow** only means "not blocked by the URL filter". The request **continues** to FortiGuard categories and can still be blocked there.
- A URL filter **monitor** behaves like allow but writes a log entry.

> **Exam tip:** "The administrator added `www.example.com` to the URL filter with action **allow**, but users are still blocked by category." That is expected. Use **exempt** to bypass the category check, or override the site's rating.

## FortiGuard category filtering

### How a rating is obtained

For each new URL, FortiGate sends a rating request to a FortiGuard rating server (or uses its local cache). The answer is a category ID, for example 52 for *Information Technology* or 100 for *Artificial Intelligence Technology*. FortiGate applies the action configured for that category in the profile. Categories are grouped in the GUI into sections such as *Potentially Liable*, *Adult/Mature Content*, *Bandwidth Consuming*, *Security Risk*, *General Interest – Personal*, *General Interest – Business* and *Unrated*. You need a **FortiGuard Web Filtering** licence for category ratings. `get webfilter categories` lists IDs and names.

### Category actions

| Action | Behaviour |
|---|---|
| **Allow** | Permit, no special log (unless logging all URLs) |
| **Monitor** | Permit and log every access. Monitored categories can also be given a category usage quota (proxy mode only) |
| **Block** | Deny with a replacement message (FortiGuard block page) |
| **Warning** | Show a warning page; the user may click *Proceed*. The warning is shown again after the warning interval |
| **Authenticate** | User must log in as a member of the selected user group(s) to proceed |
| **Disable** | Remove a **local or remote** category from the profile (local/remote categories only) |

```text
FGT-HQ # config webfilter profile
FGT-HQ (profile) # edit "WF-Staff"
FGT-HQ (WF-Staff) # set feature-set flow
FGT-HQ (WF-Staff) # config ftgd-wf
FGT-HQ (ftgd-wf) # config filters
FGT-HQ (filters) # edit 1
FGT-HQ (1) # set category 52
FGT-HQ (1) # set action warning
FGT-HQ (1) # next
FGT-HQ (filters) # edit 2
FGT-HQ (2) # set category 100
FGT-HQ (2) # set action authenticate
FGT-HQ (2) # set auth-usr-grp "AI-Approved"
FGT-HQ (2) # end
FGT-HQ (ftgd-wf) # end
FGT-HQ (WF-Staff) # end
```

> **Watch out:** In **flow** mode, local and remote categories cannot use *warning* or *authenticate*, and they cannot be overridden. If a design needs a warning page on a custom category, the policy must be proxy-based.

### HTTPS and the action pages

Block, warning and authentication pages for HTTPS sites must be injected into an HTTPS session. FortiGate signs those pages with its SSL inspection CA. A client that does not trust that CA sees a certificate error instead of the page, even with certificate inspection.

## Certificate inspection for web filtering

You do not need deep inspection to filter HTTPS by category. With **certificate inspection**, FortiGate rates the hostname from the **SNI** in the Client Hello (or the certificate CN, if the SNI check finds a mismatch). That gives you:

- Category filtering per **domain**
- Static URL filter entries that match on the **hostname**

It does **not** give you:

- Path-level matches (`example.com/games/*`)
- Safe search and YouTube restrictions (these rewrite the URL or headers)
- Content filtering, or AV on the downloaded content

TLS 1.3 does not hurt this: SNI is still cleartext. **ECH** does hurt it, which is why the SSL profile blocks ECH by default.

## Rating options

Configured under `config ftgd-wf` → `set options`:

| Option | Effect |
|---|---|
| `error-allow` | **Allow websites when a rating error occurs**: if FortiGuard cannot rate the URL (unreachable, licence issue), allow instead of block |
| `rate-server-ip` | **Rate URLs by domain and IP address**: also rate the server IP. If the two ratings differ, a hard-coded weighting decides |

Separately, `set options block-invalid-url` at the profile level blocks requests whose certificate CN does not contain a valid domain name, and URLs with raw spaces.

> **Exam tip:** "FortiGuard is unreachable and **all** web traffic through the policy is blocked" means *Allow websites when a rating error occurs* is disabled, which is the default. Enabling it fails open for rating errors. Fixing FortiGuard connectivity is the real cure.

## Overrides

**Web rating override (local rating).** Re-categorise a URL locally, either to another FortiGuard category or to a **local category** you created. Local categories (IDs from 140) are created under `config webfilter ftgd-local-cat`. Overrides are created under `config webfilter ftgd-local-rating`.

```text
FGT-HQ # config webfilter ftgd-local-cat
FGT-HQ (ftgd-local-cat) # edit "Partner-Portals"
FGT-HQ (Partner-Portals) # set id 140
FGT-HQ (Partner-Portals) # end
FGT-HQ # config webfilter ftgd-local-rating
FGT-HQ (ftgd-local-rating) # edit "portal.example.com"
FGT-HQ (portal.example.com) # set rating 140
FGT-HQ (portal.example.com) # end
```

When a URL belongs to several categories, the precedence is **local category → remote (external feed) category → FortiGuard category**. A URL in a local category follows only that local category's action.

New in 8.0, a URL filter table can be declared as a category source (`config webfilter urlfilter` → `set type category`) and linked to a local category (`set urlfilter-table` under `ftgd-local-cat`). That lets you build custom "FortiGuard-style" categories from a URL list and use them in profile mode or in policy-based security policies. A table of `type category` cannot also be used as a normal URL filter. 8.0 also lets **flow mode** detect local and external-feed categories **without** contacting FortiGuard, when **only** local or external categories are used (in the web filter profile, the URL-category policy or the SSL exemptions). Those categories then keep working with no licence or no rating server.

**Allow users to override blocked categories.** Selected users or groups can switch, for a limited time, to an alternative web filter profile (`set ovrd-perm fortiguard-wf-override …`, `config override`). The override profile cannot be the same profile that grants the override.

**Web profile override (proxy only).** Assigns a different web filter profile per user, group or IP.

## Search engines

- **Enforce safe search** on Google, Bing, Yahoo and Yandex (`set safe-search url header` under `config web`).
- **Restrict YouTube access** (strict or moderate).
- **Log all search keywords** (`set log-search enable`).

All of these need **deep inspection** for HTTPS search engines, because FortiGate must modify the request. With certificate inspection they silently do nothing.

## Lab it yourself

The trial VM has no FortiGuard Web Filtering licence, so category ratings will produce rating errors:

1. Apply a profile with a FortiGuard category set to block, and browse anywhere. Note the result with *Allow websites when a rating error occurs* off, then on.
2. Create a local category and a URL filter table of `type category` (8.0), link them, and block the category in a flow-mode profile. Check whether the trial still applies the local category without FortiGuard (the 8.0 FortiGuard-free rating for local categories). Record what you see.
3. Compare certificate inspection and deep inspection with safe search enabled on a search engine.

## Key takeaways

- Order: static URL filter → FortiGuard category → content filter → script filter → antivirus.
- URL filter *allow* still goes on to the FortiGuard check. *Exempt* skips the remaining web filter and other profiles. *Block* stops immediately.
- Category actions: allow, monitor, block, warning, authenticate (plus disable for local/remote categories).
- Category precedence: local → remote → FortiGuard. In flow mode, local/remote categories cannot warn, authenticate or be overridden.
- Certificate inspection filters HTTPS by domain from SNI. Paths, safe search and content filters need deep inspection.
- `error-allow` decides what happens when FortiGuard cannot rate a URL. The default blocks.
- 8.0: URL tables of `type category` feed local categories, and flow mode can rate local/external categories without FortiGuard when only such categories are in use.
