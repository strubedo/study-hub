## What application control actually does

Port numbers stopped describing applications a long time ago. Facebook, Teams, Dropbox and a BitTorrent client can all run on TCP 443. **Application control** identifies the application from the traffic itself and applies an action. It uses:

- **Application signatures** from the FortiGuard **Application Definitions** package. FortiGuard keeps it updated as long as the device has a valid support (firmware and general updates) contract.
- **Protocol decoders** in the IPS engine, which parse HTTP, TLS, DNS and other protocols so signatures can match on decoded fields such as the TLS SNI or HTTP host.

Application control always runs in the **IPS engine**, so it works identically on flow-mode and proxy-mode policies. It is applied by attaching an **application sensor** (`config application list`) to a firewall policy with `set application-list`. This is **profile mode**, the normal profile-based NGFW mode.

## Anatomy of an application sensor

In the GUI (Security Profiles → Application Control) a sensor has four parts.

### 1. Categories

Every signature belongs to one category (Social.Media, P2P, Proxy, Video/Audio, Network.Service, Cloud.IT, GenAI…). Setting a category action affects every signature in it, including signatures FortiGuard adds later.

### 2. Application and filter overrides

These are exceptions evaluated **before** the category settings:

- **Application override:** one or more specific signatures with their own action.
- **Filter override:** a dynamic set chosen by attributes: **behavior** (for example evasive, excessive bandwidth), **popularity** (1–5), **protocol**, **risk** (1–5), **technology** (browser-based, client-server, network-protocol, peer-to-peer), **vendor**, plus category and, new in 8.0, **classification**. New signatures that match the filter join automatically.

### 3. Actions

| GUI action | CLI (`config entries`) | Effect |
|---|---|---|
| Monitor | `action pass` + `log enable` | Allow and log |
| Allow | `action pass` + `log disable` | Allow, no log |
| Block | `action block` | Drop the session's traffic |
| Reset | `action reset` | Send TCP resets |
| Quarantine | `quarantine attacker` | Block and ban the source IP for `quarantine-expiry` (default 5m) |

Entries can also carry **traffic shaping** (`set shaper`, `set shaper-reverse`) and **rate-based** settings (`rate-count`, `rate-duration`, `rate-track`). The CLI default action of a new entry is **block**. Category settings appear in the CLI as entries too.

### 4. Options

| GUI option | CLI | Default |
|---|---|---|
| Block applications detected on non-default ports | `set enforce-default-app-port enable` | disable |
| Allow and log DNS traffic | `set options allow-dns` | — |
| Replacement messages for HTTP-based applications | `set app-replacemsg` | enable |
| Action for applications matching no entry | `set other-application-action pass/block` | pass |
| Action for unknown applications | `set unknown-application-action pass/block` | pass |
| Log those applications | `set other-application-log` / `set unknown-application-log` | disable |
| Deep application inspection | `set deep-app-inspection` | enable |

## How a sensor is evaluated

FortiOS groups a sensor's entries into **segments**. The overrides are segments evaluated in order (top-down, as listed in `config entries`), and the category settings form the default segment, evaluated last. Inside one segment, if several signatures match the same session, FortiOS breaks the tie by:

1. Segment order
2. Custom signatures before FortiGuard signatures
3. More pre/post-match actions
4. **Application weight** (set by FortiGuard, not configurable). Specific applications outweigh generic protocols, so *Facebook* (weight 10) beats *SSL* (weight 1)
5. Non-hidden before hidden signatures
6. More pattern/PCRE matches
7. Higher signature ID (assumed newer)

> **Exam tip:** "Category Social.Media is set to **block**, but there is an override above it that **monitors** Facebook. What happens to Facebook?" Facebook is allowed and logged, because overrides are evaluated before categories. Order your overrides from most specific to least specific.

```text
FGT-HQ # show application list "APP-Staff"
config application list
    edit "APP-Staff"
        set other-application-log enable
        set unknown-application-action block
        set enforce-default-app-port enable
        config entries
            edit 1
                set application 15896
                set action pass
            next
            edit 2
                set risk 5
                set action block
            next
            edit 3
                set category 23
                set action pass
                set log enable
            next
        end
    next
end
```

Here, entry 1 is an application override (FTP, ID 15896, allowed). Entry 2 is a filter override (risk 5, blocked). Entry 3 is a category setting (Social.Media, ID 23, monitored). Because `enforce-default-app-port` is enabled, FTP is allowed only on its default port. The documented example shows FTP on TCP 21 passing and FTP on TCP 2121 being blocked.

## Port enforcement and protocol enforcement

- **Port enforcement** (`enforce-default-app-port`): for applications set to monitor or allow, traffic detected on a **non-default port** (as defined by the FortiGuard signature) is **blocked**. Applications set to block are blocked on any port.
- **Network protocol enforcement** (`set control-default-network-services enable` with `config default-network-services`) works the other way round. You declare which protocol is allowed on a port (say, only DNS on 53, only HTTPS on 443), and `violation-action` (default block) applies when something else shows up there.

## SSL inspection and application control

Many signatures match on cleartext handshake data (SNI, certificate fields), so **certificate inspection** is enough to identify the application. Signatures that look inside the session, such as specific actions (*File.Upload*, *Post*, *Login*) or the AI-specific fields, need **deep inspection**. The signature's *Requirements* field in Security Profiles → Application Signatures shows whether SSL deep inspection is needed.

## Application control in NGFW policy-based mode

In **policy-based** NGFW mode you do not attach sensors. Instead, applications, application categories and application groups are referenced **directly** in `config firewall security-policy` (for example `set application 15896` or `set app-category 23`). SSL inspection is set in a separate SSL inspection & authentication policy. That mode is flow-only. The blueprint focuses on **profile mode**, but know the difference.

## GenAI and the 8.0 application classification

FortiOS 8.0 adds application control features aimed at generative AI:

- A **Generative AI** application category (`category 36`) and GenAI signatures, delivered in a separate database type, **GenAI Application Definitions** (AIAP), visible in `diagnose autoupdate versions`. A version of `0.00000` means it has never updated. Updates need an application control profile on at least one policy and a valid contract.
- With **deep inspection** and extended logging (`set extended-log enable` in the sensor, default disable), app control logs gain AI fields: `aiuser`, `model`, `dcgeo` (data centre location), `usecase`, `prompt` and `cloudgenai`.
- **FortiView AI Applications** and **AI Use Cases** widgets for dashboards.
- A new **classification framework** for application signatures (8.0.0), custom classifications (8.0.1), and an **application control signature hold timer** (8.0.1). With `config system app` → `set signature-hold-time` (default `0h`, so off), signatures that are *newly added* by an application package update stay disabled for the hold period: they match nothing and log nothing, and the traffic matches a more generic signature (such as SSL) instead. Updates to existing signatures are not held.
- Agentic AI protocol support: application control detects Model Context Protocol (MCP) and Agent-to-Agent (A2A) traffic, for example `app="Protocol.MCP"` in the GenAI category.

```text
FGT-HQ # config application list
FGT-HQ (list) # edit "GenAI"
FGT-HQ (GenAI) # set extended-log enable
FGT-HQ (GenAI) # config entries
FGT-HQ (entries) # edit 1
FGT-HQ (1) # set category 36
FGT-HQ (1) # set action pass
FGT-HQ (1) # end
FGT-HQ (GenAI) # end
```

## Lab it yourself

The trial VM has no FortiGuard updates, so the application database is whatever shipped with the image:

1. Create a sensor that monitors all categories with `other-application-log enable`. Apply it with `certificate-inspection` to your single outbound policy.
2. Browse to a few sites from the client and watch Log & Report → Security Events → Application Control, and the FortiView applications view.
3. Run an FTP server on TCP 2121 on a Linux host behind another interface, enable port enforcement with an FTP allow override, and verify the block.
4. Use `get application name status | grep -A 10 'name: "FTP"'` to read the FTP signature's ID, category and weight.

## Key takeaways

- Application control uses FortiGuard application signatures in the IPS engine and works in both inspection modes.
- Sensor parts: categories, application/filter overrides, actions, options. Overrides are evaluated before categories, top-down.
- GUI Monitor = `pass` + log, Allow = `pass` without log, plus Block, Reset, Quarantine. Shaping and rate limits are per entry.
- Port enforcement blocks allowed apps on non-default ports. Protocol enforcement restricts which protocol may use a port.
- Certificate inspection identifies many apps. Sub-application actions and GenAI detail need deep inspection.
- Policy-based NGFW mode references applications directly in security policies, with no sensor.
- 8.0 GenAI: category 36, the GenAI Application Definitions (AIAP) database, and extended-log AI fields.
