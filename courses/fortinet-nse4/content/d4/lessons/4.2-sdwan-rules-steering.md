## SD-WAN rules are policy routes

An SD-WAN rule (`config system sdwan` → `config service`) is a policy route with extra intelligence. Rules are evaluated **top-down, first match**, and they sit in the same lookup chain as ordinary policy routes:

1. Regular policy routes (`config router policy`)
2. ISDB static routes
3. **SD-WAN rules**, in order
4. The **implicit rule**: no SD-WAN rule matched, so the FIB decides, using ECMP across the members according to `load-balance-mode`

`diagnose firewall proute list` shows them all. SD-WAN rules and ISDB routes use internal IDs above 65535, and regular policy routes use low IDs. To prove which entry a flow hits, simulate it with `diagnose ip proute match <dst> <src> <in-intf> <proto> <dport>`, for example `diagnose ip proute match 10.100.0.10 10.1.1.50 port3 6 443`. The output gives the `id` and type of the matching entry. A low ID means a regular policy route. An ID above 65535 means an SD-WAN rule or ISDB route.

A rule matches on source (address, users or groups, input device), destination (address, protocol and port, **ISDB Internet Service**, **application control** signatures, BGP route tag, ToS/DSCP), then picks members using **interface/zone preference + strategy + SLA**.

> **Watch out:** An overly broad `config router policy` entry, or a policy route left over from before SD-WAN, wins over every SD-WAN rule. "SD-WAN rule is configured but traffic ignores it" often has this cause.

## Routing behaviour in an SD-WAN context

An SD-WAN rule doesn't get to ignore the routing table. By default, FortiOS performs two FIB checks before it uses a rule:

1. The **best route** to the destination must resolve to an SD-WAN member. If the best match points at a non-SD-WAN interface, such as a more specific static route out port5, SD-WAN rules aren't consulted and traffic follows that route.
2. The member chosen by the rule must itself have a **valid route** to the destination. A member with no route is skipped.

If none of a rule's members qualify (all dead, or none has a route), the rule is skipped and evaluation continues down the list, eventually reaching the implicit rule. Two CLI-only rule options relax these checks: `set default enable` skips check 1, and `set gateway enable` skips check 2 and sends traffic to the member's configured SD-WAN `gateway` instead (so the member needs a gateway configured). Both are disabled by default.

> **Exam tip:** A classic failure is a rule that sends traffic for a data-centre prefix to an overlay, but the overlay has no route to that prefix because BGP isn't up yet or no static route exists. The rule is skipped and traffic leaves through the implicit rule, usually out to the internet. `diagnose sys sdwan service4` and `get router info routing-table all` together show it.

## Strategies

| GUI strategy | CLI `mode` | Selection logic | Uses SLA? |
|--------------|-----------|-----------------|-----------|
| **Manual** | `manual` (default) | First **alive** member in configured preference order | No. Dead/alive only. |
| **Best Quality** | `priority` | Member with the best measured `link-cost-factor` (latency, jitter, packet-loss, bandwidth, custom profile) from a health check | Uses measurements, not SLA targets. Dead/alive only for eligibility. |
| **Lowest Cost (SLA)** | `sla` | Among members that **meet the SLA target**, the lowest `cost`. Ties go to preference order. If none meets the SLA, falls back to the lowest-cost alive member. | Yes |
| **Lowest Cost (SLA) + Load balancing** | `sla` + `set load-balance enable` | Load-balances across **all** members that meet the SLA. Cost is ignored. This was called *Maximize Bandwidth (SLA)* before 7.4.1. | Yes |
| **Manual + Load balancing** | `manual` + `set load-balance enable` | Load-balances across the listed members with no SLA targets | No |
| Automatic | `auto` (CLI only, legacy) | Picks the member at a quality rank (`quality-link`) | Uses measurements |

Details that show up in questions:

* **Best Quality's 10% bias.** `link-cost-threshold` (default 10) gives the first-listed member an advantage. With both links at 200 ms, the first member is treated as roughly 182 ms and keeps the traffic. This stops flapping between near-identical links.
* **Lowest Cost tie.** If two SLA-passing members have equal cost, the one listed first in `priority-members` wins.
* **Load-balance hash modes** (`set hash-mode`): `round-robin` (default, and the only one in the GUI), `source-ip-based`, `source-dest-ip-based`, `inbandwidth`, `outbandwidth`, `bibandwidth`. FortiOS 8.0.1 adds `spillover` and `weight-based-spillover`. The bandwidth modes pick the member with the most **available** bandwidth: estimated bandwidth (`estimated-upstream-bandwidth` / `estimated-downstream-bandwidth` on the interface, in kbps, or from a speed test) minus measured use.
* **`hold-down-time`** delays the move back to a recovered preferred member.
* **`minimum-sla-meet-members`** makes an SLA rule take effect only if enough members pass.

Lowest Cost (SLA) example:

```text
FGT-Branch # show system sdwan
config system sdwan
    set status enable
    config zone
        edit "virtual-wan-link"
        next
        edit "underlay"
        next
    end
    config members
        edit 1
            set interface "wan1"
            set zone "underlay"
            set gateway 203.0.113.1
            set cost 20
        next
        edit 2
            set interface "wan2"
            set zone "underlay"
            set gateway 198.51.100.1
            set cost 5
        next
    end
    config health-check
        edit "SaaS_SLA"
            set server "192.0.2.80"
            set members 1 2
            config sla
                edit 1
                    set latency-threshold 80
                    set jitter-threshold 20
                    set packetloss-threshold 2
                next
            end
        next
    end
    config service
        edit 1
            set name "SaaS"
            set mode sla
            set dst "SaaS_Servers"
            config sla
                edit "SaaS_SLA"
                    set id 1
                next
            end
            set priority-members 1 2
        next
    end
end
```

When both links meet SLA ID 1, wan2 wins (cost 5). If only wan1 meets it, wan1 wins despite its higher cost. If neither meets it, the lowest-cost alive member (wan2) is used.

```text
FGT-Branch # diagnose sys sdwan service4 1

 Tie break: cfg

 Members(2):
  1: Seq_num(2 wan2 underlay), alive, sla(0x1), gid(0), cfg_order(1), local cost(5), selected
  2: Seq_num(1 wan1 underlay), alive, sla(0x1), gid(0), cfg_order(0), local cost(20), selected
 Dst address(1):
       192.0.2.0-192.0.2.255
```

Members are listed **in current order of preference**, so member 1 in the list carries new sessions. `sla(0x1)` means SLA ID 1 passes, `sla(0x0)` means out of SLA, and a failed member shows `dead` instead of `alive` and has no `selected` flag.

## The implicit rule

When no SD-WAN rule matches, the FIB decides. The SD-WAN zone route is ECMP across all member gateways, distributed by `load-balance-mode`:

| GUI | `load-balance-mode` | Uses |
|-----|--------------------|------|
| Source IP (**default**) | `source-ip-based` | — |
| Sessions | `weight-based` | member `weight` |
| Spillover | `usage-based` | `spillover-threshold`, `ingress-spillover-threshold` |
| Source-Destination IP | `source-dest-ip-based` | — |
| Volume | `measured-volume-based` | member `volume-ratio` |

You can't exclude a member from the implicit rule with weight or volume-ratio: neither can be 0 (a 0 carried over from an older release is treated as 1). To keep a member out of the implicit rule, give it a higher `priority` value so its route is not preferred.

## SD-WAN based on underlay bandwidth utilization (FortiOS 8.0)

On a spoke, several overlays often ride the **same** underlay. For example, two IPsec tunnels to two hubs both cross wan1. Before 8.0, the bandwidth hash modes looked only at each overlay's own available bandwidth. Two tunnels could each look half-empty while their shared wan1 underlay was saturated.

FortiOS 8.0.0 adds a rule option for load-balanced rules:

```text
FGT-Branch # config system sdwan
FGT-Branch (sdwan) # config service
FGT-Branch (service) # edit 1
FGT-Branch (1) # set mode sla
FGT-Branch (1) # set load-balance enable
FGT-Branch (1) # set hash-mode bibandwidth
FGT-Branch (1) # set bandwidth-type underlay
FGT-Branch (1) # next
FGT-Branch (service) # end
FGT-Branch (sdwan) # end
```

* `bandwidth-type {overlay | underlay}` has a default of **overlay**. It applies only with `load-balance enable` and `hash-mode` set to `inbandwidth`, `outbandwidth` or `bibandwidth`.
* With `underlay`, each overlay is scored by the **available bandwidth of its underlay**: the underlay's estimated bandwidth minus traffic measured on it. Two overlays that share a busy port1 both score low, so new sessions move to overlays on a less-loaded port2.
* Estimated bandwidth comes from `estimated-upstream-bandwidth` / `estimated-downstream-bandwidth` (kbps) on the interfaces, or from the SD-WAN speed test.
* Verify with `diagnose sys sdwan service4`, which lists a per-member `bibandwidth: <n>Kbps`, and `diagnose sys sdwan intf-sla-log <intf>`, which shows used in/out/bi bandwidth over time.

Related 8.0 bandwidth features from the same release:

* **Stop duplication at a utilization threshold.** Per member, `duplication-threshold-upbandwidth`, `-dwbandwidth` and `-bibandwidth`, with `duplication-threshold-bandwidth {overlay | underlay}`. Packet duplication stops once the measured load exceeds the threshold.
* **Monthly volume quota.** Per member, `quota-limit` (GB), `billing-start-day`, and `overage enable` with `overage-cost`, `overage-weight` or `overage-volume-ratio`. Once the quota is used up, the member's cost, weight or ratio changes so traffic shifts elsewhere until the next billing day. Check usage with `diagnose sys sdwan bill member <id>`.

> **Real world:** Bandwidth-based steering is only as good as the estimated bandwidth values. Leave them unset and every member looks equally empty.

## Lab it yourself

Using the trial setup from the previous lesson:

1. Create a manual rule for one destination host with `priority-members 2 1`. Confirm with `diagnose ip proute match` and a sniffer on port2 that the traffic leaves port2. Make port2 dead and confirm failover.
2. Change the rule to `mode sla` with costs 20 (port1) and 5 (port2). Add netem delay on port2 above the SLA threshold and watch the order in `diagnose sys sdwan service4` flip.
3. Add a /32 static route for the test host via port3, the non-SD-WAN LAN interface, using a Linux host on the LAN as the gateway. That is your second static route. The rule stops matching because the FIB best route now points at a non-member. Confirm with `diagnose ip proute match`, then try `set default enable` on the rule and compare.

## Key takeaways

* Lookup order: policy routes, then ISDB routes, then SD-WAN rules (first match), then the implicit rule (FIB/ECMP).
* By default a rule needs the FIB best route to point at an SD-WAN member, and the chosen member needs its own route. If no member qualifies, the rule is skipped.
* Manual and Best Quality ignore SLA state. Lowest Cost (SLA) prefers members that pass the SLA, then the lowest cost.
* Maximize Bandwidth (SLA) is now `mode sla` + `load-balance enable`. Cost is ignored and all SLA-passing members are used.
* Best Quality gives the first member a 10% `link-cost-threshold` advantage by default.
* The implicit rule uses `load-balance-mode`, which defaults to source-ip-based.
* 8.0: `bandwidth-type underlay` makes bandwidth hash modes score overlays by their shared underlay's available bandwidth. 8.0 also adds duplication thresholds and monthly quotas.
