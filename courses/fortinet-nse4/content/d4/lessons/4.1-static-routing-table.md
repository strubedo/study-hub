## How a FortiGate picks a route

A FortiGate is a router before it is a firewall: firewall policy lookup can't happen until the FortiGate knows the **egress interface**, because every policy is written as *incoming interface → outgoing interface*. Routing is checked on the **first packet of a session** (and again for the first reply packet). The result is stored in the session, so later packets don't trigger a new lookup unless the routing table changes.

For each new session, FortiOS checks these in order:

1. **Policy routes.** This covers `config router policy` entries, then ISDB (Internet Service) static routes, then SD-WAN rules. The documented precedence is *policy-based routes > ISDB routes > SD-WAN routes*.
2. **The FIB** (the kernel forwarding table), which is built from the best routes in the routing table.
3. If nothing matches, the packet is dropped. In `diagnose debug flow` this appears as a route lookup failure.

If you come from Cisco IOS, the route-selection logic will feel familiar, with one extra tie-breaker:

| Step | Rule | Notes |
|------|------|-------|
| 1 | **Longest prefix match** | A /32 beats a /24, which beats 0.0.0.0/0. This holds whatever the distance. |
| 2 | **Lowest administrative distance** | Only routes to the *same* prefix compete on distance. A route that loses on distance stays in the routing **database** but never reaches the routing table. |
| 3 | **Lowest priority** (static routes) | All routes with equal distance go into the routing table. The one with the lowest `priority` value forwards traffic. |
| 4 | **ECMP** | Equal prefix, distance and priority means the routes share load using the ECMP algorithm. |

Default distances: connected 0, DHCP/PPPoE-learned default route **5**, static **10**, eBGP 20, OSPF 110, RIP 120, iBGP 200. The DHCP value catches people out. If `wan1` gets its address by DHCP with *Retrieve default gateway from server* enabled, the learned default route (distance 5) beats the static default route (distance 10) you just configured. SD-WAN zone static routes default to distance **1** (lesson 4.2).

> **Exam tip:** Distance and priority are not the same thing. A route that loses on **distance** disappears from `get router info routing-table all`. A route that loses only on **priority** stays in the routing table and is still used for reverse-path checks. Expect at least one question that depends on this difference.

## Configuring static routes

A static route needs a destination and an outgoing interface (`device`), plus a `gateway` unless it is a point-to-point interface such as an IPsec tunnel. Blackhole and SD-WAN zone routes take no `device`. The attributes you will see most often:

```text
FGT-HQ # config router static
FGT-HQ (static) # edit 1
FGT-HQ (1) # set dst 0.0.0.0 0.0.0.0
FGT-HQ (1) # set gateway 203.0.113.1
FGT-HQ (1) # set device "port1"
FGT-HQ (1) # set distance 10
FGT-HQ (1) # set priority 1
FGT-HQ (1) # next
FGT-HQ (static) # edit 2
FGT-HQ (2) # set dst 10.20.0.0 255.255.0.0
FGT-HQ (2) # set gateway 10.0.12.2
FGT-HQ (2) # set device "port3"
FGT-HQ (2) # next
FGT-HQ (static) # end
```

Useful facts:

* `edit 0` assigns the next free sequence number. The sequence number is just an ID and has no effect on preference.
* The destination can be a subnet, a **named address** (an address or address group with `set allow-routing enable`; FQDN addresses work too), or an **Internet Service** (ISDB) object. ISDB static routes behave like policy routes, not FIB routes.
* `set sdwan-zone "<zone>"` points a route at an SD-WAN zone instead of one interface (see 4.2).
* A static route is installed only while its interface is **up**. If the link goes down, the route is withdrawn. A failed upstream gateway behind a link that stays up is *not* detected unless you add a **link monitor** or an SD-WAN performance SLA (next lesson).
* `show router static` lists only values you changed from the default, so `distance 10` and `priority 1` don't appear.

### Blackhole routes

A blackhole route silently drops traffic to its destination:

```text
FGT-HQ # config router static
FGT-HQ (static) # edit 9
FGT-HQ (9) # set dst 10.20.0.0 255.255.0.0
FGT-HQ (9) # set blackhole enable
FGT-HQ (9) # set distance 254
FGT-HQ (9) # next
FGT-HQ (static) # end
```

The standard use is protecting VPN-bound traffic. While the tunnel route (distance 10) is up, it wins. When the tunnel drops and its route is withdrawn, the blackhole (distance 254) becomes the best route, so traffic for the remote LAN is discarded. Without it, that traffic would follow the default route out to the internet, possibly unencrypted and to a public next hop. The IPsec wizard adds exactly this route automatically, with distance 254. Blackhole route *priority* can be set only in the CLI.

## Reading the routing table

There are three views, and the exam expects you to know what each one shows.

| Command | What it shows |
|---------|---------------|
| `get router info routing-table all` | The **routing table (RIB)**: only the best route(s) per prefix. Routes that lost on distance are hidden. |
| `get router info routing-table database` | The **routing database**: every candidate learned from every source. `>` marks the selected route, `*` marks a route in the FIB. |
| `get router info kernel` | The **kernel/FIB** entries the forwarding engine actually uses. |
| `get router info routing-table details <ip>` | A lookup for one destination, showing the matching entry. |

Example routing table:

```text
FGT-HQ # get router info routing-table all
Codes: K - kernel, C - connected, S - static, R - RIP, B - BGP
       O - OSPF, IA - OSPF inter area
       N1 - OSPF NSSA external type 1, N2 - OSPF NSSA external type 2
       E1 - OSPF external type 1, E2 - OSPF external type 2
       i - IS-IS, L1 - IS-IS level-1, L2 - IS-IS level-2, ia - IS-IS inter area
       * - candidate default

Routing table for VRF=0
S*      0.0.0.0/0 [10/0] via 203.0.113.1, port1
                  [10/0] via 198.51.100.1, port2, [5/0]
C       10.0.1.0/24 is directly connected, port3
S       10.20.0.0/16 [10/0] via 10.0.1.254, port3
C       198.51.100.0/24 is directly connected, port2
C       203.0.113.0/24 is directly connected, port1
```

To read an entry: `[10/0]` is *[administrative distance/metric]*. The trailing `[5/0]` is *[priority/weight]*. Fortinet's own examples sometimes omit it when the route uses the default priority, and sometimes show it as `[1/0]`, so don't read anything into its absence. Here both default routes have distance 10, so both are in the table, but port1 (priority 1, the default) carries traffic and port2 (priority 5) is standby.

The database shows the loser routes that the table hides:

```text
FGT-HQ # get router info routing-table database
...
Routing table for VRF=0
S    *> 0.0.0.0/0 [10/0] via 203.0.113.1, port1
     *>           [10/0] via 198.51.100.1, port2, [5/0]
S       10.20.0.0/16 [20/0] via 198.51.100.7, port2
S    *> 10.20.0.0/16 [10/0] via 10.0.1.254, port3
```

The distance-20 route to 10.20.0.0/16 has no `>` and no `*`. It is a **floating** backup that will be installed only if the distance-10 route is withdrawn.

> **Real world:** When a route is in your config but traffic ignores it, run `get router info routing-table database` first. You will usually find the route there with no `>`. Either another route beat it on distance, or its interface is down.

## Reverse path forwarding (RPF) check

When the **first packet of a new session** arrives, FortiOS checks the *source* address against the routing table. This is anti-spoofing, and it runs before policy lookup.

* **Feasible-path mode (default).** The packet passes if *any* active route to the source exists through the **incoming interface**. That route can be the default route, and it can be a route that is in the table but not preferred (for example, the higher-priority-value default route above).
* **Strict mode** (`config system settings` → `set strict-src-check enable`). The packet passes only if the **best** route back to the source uses the incoming interface.

A failure shows up in `diagnose debug flow` as `reverse path check fail, drop`. Classic case: a branch subnet 10.30.0.0/24 sends traffic in on port3, but the FortiGate only has a route to 10.30.0.0/24 via port2, and its default route points out port1. With no route to the source via port3, the packet is dropped before any policy is evaluated.

You can disable the check on one interface with `set src-check disable` under `config system interface`. Treat this as a troubleshooting step, not a fix. The right fix is a correct route, or a backup route that is present in the table (same distance, higher priority), so RPF passes on the standby path.

> **Watch out:** This is why redundant links are usually built with **equal distance and different priorities** rather than different distances. A floating route (higher distance) is absent from the routing table, so return or inbound traffic arriving on the backup link fails RPF while the primary is up.

## Policy routes

Policy routes (`config router policy`) override the routing table for traffic that matches any combination of incoming interface, source, destination, protocol, ports, ToS, and users or groups:

```text
FGT-HQ # config router policy
FGT-HQ (policy) # edit 1
FGT-HQ (1) # set input-device "port3"
FGT-HQ (1) # set src "10.0.1.0/255.255.255.0"
FGT-HQ (1) # set dst "0.0.0.0/0.0.0.0"
FGT-HQ (1) # set protocol 6
FGT-HQ (1) # set start-port 443
FGT-HQ (1) # set end-port 443
FGT-HQ (1) # set gateway 198.51.100.1
FGT-HQ (1) # set output-device "port2"
FGT-HQ (1) # next
FGT-HQ (policy) # end
```

Key behaviours:

* Policy routes are evaluated **top-down, first match**. New entries go to the bottom; reorder them with `move <id> before|after <id>`.
* `set action deny` makes traffic that matches *skip policy routing* and fall through to the routing table. It does **not** drop the packet. This is the standard way to exempt internal destinations from a broad policy route.
* Even a matching policy route needs a usable route. If the gateway isn't reachable through the output device per the routing table, the entry is skipped and evaluation continues down the list, then to the FIB.
* Verify with `diagnose firewall proute list`, or test one flow with `diagnose ip proute match <dst> <src> <iif> <proto> <dport>`.

## Lab it yourself

This lab fits the FortiGate-VM permanent trial: 3 interfaces, 3 routes. Use port1 (WAN to a Cisco or Linux "ISP" router), port2 (second "ISP"), and port3 (LAN).

1. Add default route 1 via port1 and default route 2 via port2, with the same distance and `priority 5` on route 2. Check `get router info routing-table all` and note the `[5/0]` tag.
2. Change route 2 to `distance 20` and priority back to default. Confirm it vanishes from `routing-table all` but appears without `>` in `routing-table database`.
3. Use your third route as a blackhole for a fake remote LAN (distance 254), then run `get router info routing-table details` against an address in that LAN.
4. From a host behind the ISP router on port2, ping the LAN while the port2 route is a floating route. Watch `diagnose debug flow` show the RPF drop. Then switch back to equal distance with a higher priority value and repeat.

## Key takeaways

* Route selection goes longest prefix, then lowest distance, then lowest priority (static routes), then ECMP.
* Default static distance is 10 and default priority is 1. A DHCP-learned default route has distance 5.
* A route that loses on distance stays only in `routing-table database`. A route that loses on priority stays in the routing table and still satisfies RPF.
* Lookup order for a new session: policy routes, then ISDB routes, then SD-WAN rules, then the FIB.
* RPF runs on the first packet of a session. Feasible-path mode is the default; `strict-src-check` requires the best route.
* Blackhole routes at distance 254 keep VPN-bound traffic from leaking out the default route when a tunnel drops.
* A policy route with `action deny` means "don't policy-route this", not "drop it".
