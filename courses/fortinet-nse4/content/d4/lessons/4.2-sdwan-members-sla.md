## What SD-WAN is on a FortiGate

SD-WAN on FortiOS is not a separate product or licence. It is a layer on top of the routing engine. Here is what it adds:

* **Members.** Interfaces that SD-WAN manages: physical ports, VLANs, aggregates, IPsec tunnels (overlays), GRE tunnels, FortiExtender interfaces.
* **Zones.** Groups of members that you reference in **firewall policies** and **static routes**.
* **Performance SLAs.** Health checks that measure each member's latency, jitter and packet loss, and can mark a member **dead** or **out of SLA**.
* **SD-WAN rules** (`config service`). Policy routes that steer matching traffic to the best member according to a strategy. Unmatched traffic falls to the **implicit rule**, which is ECMP across the members (next lesson).

Common use cases:

| Use case | How SD-WAN helps |
|----------|------------------|
| **Dual ISP / DIA** | Both links active. A dead ISP is removed automatically. Applications go to the best link. |
| **Replace or augment MPLS** | Run IPsec overlays over cheap broadband. Steer only critical apps to MPLS or the best overlay. |
| **Application-aware steering** | Match ISDB services (Microsoft 365, Zoom) or application control signatures, and pick a link per app. |
| **Cost control** | Lowest Cost (SLA): use the cheap link while it meets the SLA. 8.0 adds volume quotas per member. |
| **Branch to hub resilience** | Overlay plus underlay zones, SLAs that probe through the tunnel, and ADVPN shortcuts. |

## Members and zones

```text
FGT-Branch # config system sdwan
FGT-Branch (sdwan) # set status enable
FGT-Branch (sdwan) # config zone
FGT-Branch (zone) # edit "underlay"
FGT-Branch (underlay) # next
FGT-Branch (zone) # edit "overlay"
FGT-Branch (overlay) # next
FGT-Branch (zone) # end
FGT-Branch (sdwan) # config members
FGT-Branch (members) # edit 1
FGT-Branch (1) # set interface "wan1"
FGT-Branch (1) # set zone "underlay"
FGT-Branch (1) # set gateway 203.0.113.1
FGT-Branch (1) # next
FGT-Branch (members) # edit 2
FGT-Branch (2) # set interface "wan2"
FGT-Branch (2) # set zone "underlay"
FGT-Branch (2) # set gateway 198.51.100.1
FGT-Branch (2) # set cost 10
FGT-Branch (2) # next
FGT-Branch (members) # edit 3
FGT-Branch (3) # set interface "HQ-VPN1"
FGT-Branch (3) # set zone "overlay"
FGT-Branch (3) # next
FGT-Branch (members) # end
FGT-Branch (sdwan) # end
```

Member settings you need to know:

| Attribute | Purpose | Default |
|-----------|---------|---------|
| `interface` | Interface the member represents | — |
| `zone` | Zone the member belongs to. Unassigned members go to **`virtual-wan-link`**. | virtual-wan-link |
| `gateway` | Next hop used by SD-WAN routes and rules (DHCP members learn it automatically) | 0.0.0.0 |
| `cost` | Used by **Lowest Cost (SLA)** rules. Lower is preferred. | 0 |
| `priority` | Priority of the static route created for the member. Lower is preferred. | 1 |
| `weight` / `volume-ratio` | Used by the weight-based / volume implicit load-balancing modes (can't be 0) | 1 |
| `spillover-threshold` / `ingress-spillover-threshold` | Egress and ingress thresholds for spillover (usage-based) | 0 |
| `source` | Source IP for health-check probes (common on overlays) | — |
| `status` | Enable or disable the member | enable |

Rules of the road:

* **Policies reference zones, not members.** An SD-WAN member can't be used directly as `srcintf`/`dstintf`. Put a member that needs its own policy into a zone by itself.
* An interface that is already referenced elsewhere, such as in a firewall policy or a static route, must have those references removed before it can become a member.
* One **static route** to the zone gives every member's gateway a default route:

```text
FGT-Branch # config router static
FGT-Branch (static) # edit 1
FGT-Branch (1) # set sdwan-zone "underlay"
FGT-Branch (1) # next
FGT-Branch (static) # end
FGT-Branch # get router info routing-table all
...
S*      0.0.0.0/0 [1/0] via 203.0.113.1, wan1
                  [1/0] via 198.51.100.1, wan2
```

With no `dst` the route is 0.0.0.0/0. Note the distance: a static route through an SD-WAN zone defaults to **distance 1**, not the usual 10, so it beats an ordinary static default route (10) and a DHCP-learned one (5). Change it with `set distance` in the CLI if you need to. Two equal routes form ECMP. That ECMP set *is* the implicit rule.

* `diagnose sys sdwan member` shows each member with its interface, gateway, source and route priority. `diagnose sys sdwan zone` lists the zones and their members.

> **Exam tip:** "How do you use two ISP links in a single firewall policy?" Answer: put both in an SD-WAN zone and use the zone as the policy's outgoing interface. You don't need two policies.

## Performance SLAs

A performance SLA (`config health-check`) has three parts: **health check** (what to probe and how), **SLA targets** (thresholds), and **link status** (timers).

```text
FGT-Branch # config system sdwan
FGT-Branch (sdwan) # config health-check
FGT-Branch (health-check) # edit "DC_SLA"
FGT-Branch (DC_SLA) # set server "10.100.0.10"
FGT-Branch (DC_SLA) # set protocol ping
FGT-Branch (DC_SLA) # set members 1 2
FGT-Branch (DC_SLA) # set interval 500
FGT-Branch (DC_SLA) # set failtime 5
FGT-Branch (DC_SLA) # set recoverytime 5
FGT-Branch (DC_SLA) # set update-static-route enable
FGT-Branch (DC_SLA) # config sla
FGT-Branch (sla) # edit 1
FGT-Branch (1) # set link-cost-factor latency packet-loss
FGT-Branch (1) # set latency-threshold 120
FGT-Branch (1) # set packetloss-threshold 2
FGT-Branch (1) # next
FGT-Branch (sla) # end
FGT-Branch (DC_SLA) # next
FGT-Branch (health-check) # end
FGT-Branch (sdwan) # end
```

**Probe mode** can be active (send probes), passive (measure real traffic in policies that have passive health measurement enabled), or prefer-passive (passive when traffic is flowing, probes when it isn't).

**Protocols** (`set protocol`) are ping, tcp-echo, udp-echo, http, https, twamp, dns, tcp-connect and ftp. The GUI exposes the common ones (ping, HTTP, DNS). A DNS probe can require a specific answer with `dns-match-ip`. You can define up to two servers, and **both** must fail for the member to be declared dead. A server can belong to only one performance SLA.

Five SLA profiles are predefined on new VDOMs or after a factory reset: DNS, FortiGuard, Gmail, Google Search and Office 365. You only add participants.

**SLA targets** default to latency 5 ms, jitter 5 ms and packet loss 0%. These are deliberately strict, so tune them to just under what the application tolerates. `link-cost-factor` chooses which metrics count. A member is **out of SLA** if any selected metric exceeds its threshold. You can define several SLA targets per health check, and rules reference them by ID.

**Link status** settings: `interval` defaults to 500 ms (HTTP/HTTPS probes are automatically raised to 120,000 ms). `failtime` and `recoverytime` both default to 5 consecutive probes.

Two independent states come out of every health check:

| State | Meaning | Used by |
|-------|---------|---------|
| **Alive / Dead** | Are probes answered? *Alive to Dead* takes `failtime × interval` (5 × 500 ms = 2.5 s by default). *Dead to Alive* takes `recoverytime × interval`. | All strategies. A dead member is never selected, and with `update-static-route enable` (default) its static routes are withdrawn. |
| **In SLA / Out of SLA** | Are the metrics within the SLA targets? A member can be alive *and* out of SLA. A dead member is always out of SLA. | **Lowest Cost (SLA)** and load balancing with SLA. **Manual and Best Quality rules ignore SLA state** and look only at dead/alive. |

Latency and jitter use a sliding window (`probe-count`, default 30 probes). Packet loss is always calculated over the last 100 probes.

### Reading the health check

```text
FGT-Branch # diagnose sys sdwan health-check DC_SLA
Health Check(DC_SLA):
Seq(1 wan1): state(alive), packet-loss(0.000%) latency(38.512), jitter(0.744), mos(4.383), bandwidth-up(98472), bandwidth-dw(97105), bandwidth-bi(195577) sla_map=0x1
Seq(2 wan2): state(alive), packet-loss(4.000%) latency(61.205), jitter(3.910), mos(4.170), bandwidth-up(48870), bandwidth-dw(49230), bandwidth-bi(98100) sla_map=0x0
```

`sla_map` is a bitmap of the SLA target IDs the member currently passes. Bit 0 is SLA ID 1 and bit 1 is ID 2, so `0x3` means it passes both. wan2 above is **alive but out of SLA**: 4% loss exceeds the 2% threshold.

SD-WAN events are logged under subtype `sdwan` (log ID 0113022923, "SDWAN status") with messages such as `Member status changed. Member out-of-sla.` and `Member link is unreachable or miss threshold. Stop forwarding traffic.` When a health check withdraws routes, you also get a system event "Routing information changed" (0100022921).

> **Watch out:** FortiOS sends each probe out the member it is testing, whatever the routing table says. What can break is the **return** path. The server must reply back along the same member. On overlays, set `source` on the member to an address the remote side routes back into that tunnel. Otherwise the member shows dead while the tunnel itself is fine.

## Lab it yourself

This fits the trial: port1 and port2 as members, port3 as the LAN. One static route (`sdwan-zone`), one firewall policy (port3 → zone, NAT).

1. Create the zone and members, then add the zone route and confirm ECMP in `get router info routing-table all`.
2. Create a ping health check to an address behind both "ISP" routers. On the port2 router, add delay with Linux `tc qdisc add dev eth0 root netem delay 150ms loss 5%` and watch `diagnose sys sdwan health-check` mark it out of SLA.
3. Block ICMP on the port2 router and watch the member go dead. Its route leaves the routing table after about 2.5 s.

## Key takeaways

* SD-WAN = members + zones + performance SLAs + rules. Policies and static routes reference **zones**.
* Unzoned members land in `virtual-wan-link`. One `sdwan-zone` static route installs an ECMP route via every member's gateway, at a default distance of **1**.
* SLA defaults: interval 500 ms, failtime and recoverytime 5, thresholds 5 ms latency, 5 ms jitter, 0% loss.
* Dead members are never used, and their routes are withdrawn (`update-static-route` enabled by default).
* A member can be alive and out of SLA. Only SLA-based rules care about SLA state. Manual and Best Quality rules look only at dead/alive.
* `sla_map` is a bitmap of the SLA target IDs the member passes.
* Key commands: `diagnose sys sdwan member`, `diagnose sys sdwan zone`, `diagnose sys sdwan health-check [name]`.
