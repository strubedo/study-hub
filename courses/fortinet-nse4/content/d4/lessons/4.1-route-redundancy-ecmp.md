## Three ways to use two links

Give a FortiGate two internet links, or two paths to a data centre, and you can configure them one of three ways. Each comes from a different combination of distance and priority.

| Design | Configuration | Routing table result | Traffic | RPF on backup link |
|--------|---------------|----------------------|---------|--------------------|
| **Floating (cold standby)** | Same prefix, **different distance** | Only the lower-distance route is installed. The other stays in the database. | Primary only | **Fails** for new inbound sessions while the primary is up |
| **Priority-based (warm standby)** | Same prefix and distance, **different priority** | Both installed. The lower priority value is preferred. | Primary only (outbound) | **Passes**, because a route via the backup exists in the table |
| **ECMP (active-active)** | Same prefix, distance **and** priority | Both installed and both preferred | Load-shared per session | Passes |

Failover in all three designs needs the failed route to be **withdrawn**. FortiOS does this automatically when the interface goes link-down. Most real ISP failures aren't link-down events, though: the modem stays up and the upstream path dies. That case needs **dead gateway detection**.

## Link monitor (dead gateway detection)

`config system link-monitor` sends probes out an interface. When the probes fail, it removes the static routes that use that interface's gateway.

```text
FGT-HQ # config system link-monitor
FGT-HQ (link-monitor) # edit "ISP1-check"
FGT-HQ (ISP1-check) # set srcintf "port1"
FGT-HQ (ISP1-check) # set server "198.51.100.53"
FGT-HQ (ISP1-check) # set gateway-ip 203.0.113.1
FGT-HQ (ISP1-check) # set protocol ping
FGT-HQ (ISP1-check) # set update-static-route enable
FGT-HQ (ISP1-check) # next
FGT-HQ (link-monitor) # end
```

* Probe a target **beyond** the ISP's first hop, such as a public resolver or your data centre. If you only ping the CPE, a dead upstream path will still look healthy.
* `update-static-route` (enabled by default) is the setting that withdraws the routes. With it disabled, the monitor only logs the failure.
* `failtime` and `recoverytime` count consecutive failed or successful probes before the state changes. Probe `interval` is in milliseconds.
* Once SD-WAN is enabled, use **SD-WAN performance SLAs** for the same job. They do the same thing per SD-WAN member, and they also measure latency, jitter and loss (lesson 4.2).

> **Exam tip:** "The ISP router is still up but upstream connectivity is lost, and traffic keeps using port1" means the route is never withdrawn. The answer is a link monitor (or an SD-WAN health check) with `update-static-route enable`, not a different distance.

## ECMP on FortiOS

ECMP applies only when routes match on **prefix, distance and priority** and come from the **same protocol**. Static, OSPF and BGP can form ECMP sets. BGP needs `ebgp-multipath` or `ibgp-multipath` enabled, and both are disabled by default. ECMP is evaluated **after** policy routes, so a matching policy route overrides it.

The algorithm is a per-VDOM setting. Without SD-WAN:

```text
FGT-HQ # config system settings
FGT-HQ (settings) # set v4-ecmp-mode source-ip-based
FGT-HQ (settings) # end
```

| `v4-ecmp-mode` | Behaviour |
|----------------|-----------|
| `source-ip-based` (**default**) | Hash on source IP, so one client always uses the same link |
| `source-dest-ip-based` | Hash on source and destination pair |
| `weight-based` | Sessions split according to each route's `weight` |
| `usage-based` | Spillover: fill the first link to its configured threshold, then use the next |

* When **SD-WAN is enabled**, `v4-ecmp-mode` disappears. The equivalent setting is `config system sdwan` → `set load-balance-mode`, which adds `measured-volume-based`.
* `set ecmp-max-paths` (under `config system settings`) caps how many next hops can be installed. A value of 1 effectively disables ECMP.
* Load sharing is **per session**, not per packet, so one large download can't span two links.

Weight-based example:

```text
FGT-HQ # show router static
config router static
    edit 11
        set dst 10.60.0.0 255.255.0.0
        set weight 80
        set device "DC-VPN1"
    next
    edit 12
        set dst 10.60.0.0 255.255.0.0
        set weight 20
        set device "DC-VPN2"
    next
end
```

With `v4-ecmp-mode weight-based`, about 80% of **new sessions** to 10.60.0.0/16 use `DC-VPN1`. Under the default source-IP mode the weights are ignored.

> **Watch out:** Give one of two ECMP routes a different priority and the ECMP set breaks. The table still shows both entries, but only the lower priority value forwards traffic. "Both routes appear in `routing-table all` but only port1 carries traffic" is usually a priority difference.

## What happens to existing sessions on a route change

Route changes don't just affect new sessions. FortiOS documents two defaults:

* **Without SNAT:** when the routing table changes, routing information is flushed from sessions and the next packet triggers a fresh lookup. `set preserve-session-route enable` on an interface pins existing sessions instead.
* **With SNAT:** sessions keep their original egress interface while the old route is still active. That avoids changing the source IP mid-session. `config system global` → `set snat-route-change enable` forces a new lookup and a new SNAT.

This explains why, after a primary link recovers, some NATed sessions stay on the backup link until they age out.

## Asymmetric routing

If replies return through a path that skips the FortiGate, or come back in on a different FortiGate interface than the stateful session expects, the FortiGate drops them as invalid. For example, a SYN/ACK arriving with no matching session, or a TCP ACK arriving when the SYN/ACK went around the firewall. `config system settings` → `set asymroute enable` makes the FortiGate tolerate this, but it then acts as a plain router for those flows with **no security inspection**. Fix the topology instead. Asymmetry usually comes from two default routes, or from a LAN router that knows a second way out.

## Use cases

**Dual ISP, primary/backup, with inbound services on both links.** Use the same distance with port1 at priority 1 and port2 at priority 10. Add a link monitor per ISP. Outbound traffic uses port1. A VIP published on port2's address still works, because RPF passes on port2.

**Dual ISP, active-active.** Use the same distance and priority and `v4-ecmp-mode source-ip-based`, so each user sticks to one public IP. That matters for sites that tie a session to the source address. Add link monitors so a dead path leaves the ECMP set.

**Two tunnels to the data centre, 80/20.** Use the same distance and priority, weights 80 and 20, and `weight-based` mode. Add a blackhole route for the DC prefix at distance 254.

**Backup over LTE that costs money.** Use a floating static route (distance 20) via the LTE interface. It isn't in the table until the primary is withdrawn, which is what you want when the backup link should attract no traffic at all, including new inbound sessions, while the primary is healthy.

## Lab it yourself

This lab fits the trial's 3-route limit. Use port1 and port2 to two Linux or Cisco "ISP" routers and port3 for a LAN client.

1. Configure two default routes with equal distance and priority. Generate traffic from two client IPs (add a secondary IP on the Linux client) and check `diagnose sys session list` to see which `gwy`/egress each session took under `source-ip-based`.
2. Switch `v4-ecmp-mode` to `weight-based`, set weights 3 and 1, and open many sessions (`curl` in a loop) to confirm the rough 75/25 split.
3. Add a link monitor on port1 that pings a loopback on the far side of the ISP router. Shut down that loopback (not the link) and watch the port1 route disappear from `get router info routing-table all`.
4. Give port2 a higher priority value and repeat. Note that the backup route remains in the table.

## Key takeaways

* Floating routes (different distance) are absent from the routing table. Priority-based backups are present but not preferred. ECMP needs equal prefix, distance and priority.
* A link-down event withdraws routes automatically. A dead upstream with the link still up needs a link monitor or an SD-WAN health check with `update-static-route enable`.
* `v4-ecmp-mode` defaults to `source-ip-based`. With SD-WAN enabled, `load-balance-mode` under `config system sdwan` takes over.
* Weights only matter in `weight-based` mode. ECMP is per session, not per packet.
* ECMP and the routing table are consulted only after policy routes.
* With SNAT, sessions stay on their old route after a change unless `snat-route-change` is enabled.
* `asymroute enable` disables security inspection for the affected flows. Fix the routing instead.
