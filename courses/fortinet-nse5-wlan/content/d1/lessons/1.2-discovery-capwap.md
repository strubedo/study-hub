## The integrated wireless controller

Every FortiGate (and FortiWiFi) includes a WiFi controller. FortiAPs are thin APs: they get their whole configuration — SSIDs, radio settings, security — from the controller over **CAPWAP** (Control And Provisioning of Wireless Access Points, RFC 5415). In the GUI this lives under **WiFi & Switch Controller**: *Managed FortiAPs*, *SSIDs*, *FortiAP Profiles*, *WiFi Settings*. On the CLI it is `config wireless-controller …`. The controller daemon is `cw_acd`.

A FortiAP reaches the controller in one of three topologies:

| Topology | Description | Discovery that works |
|----------|-------------|----------------------|
| Direct connection | AP plugged into a FortiGate port | Any; broadcast/DHCP are simplest |
| Switched connection | Through an L2 or L3 switch; needs a routed path and **UDP 5246 and 5247** open | DHCP option 138, DNS, static, multicast (with multicast routing) |
| Connection over WAN | Controller off-site (often across VPN) | **Static** controller IP (up to three for failover) or DHCP option 138 |

## Step 1: prepare the FortiGate interface

The interface that faces the APs needs an IP address, usually a DHCP server, and CAPWAP access:

```text
FGT-HQ # config system interface
FGT-HQ (interface) # edit "port5"
FGT-HQ (port5) # set ip 10.10.10.1 255.255.255.0
FGT-HQ (port5) # set allowaccess ping fabric
FGT-HQ (port5) # next
FGT-HQ (interface) # end
```

* **`fabric`** — shown in the GUI as **Security Fabric Connection** — is the administrative access that allows CAPWAP. Without it the AP's discovery requests are ignored.
* `ap-discover` (default **enable**) creates a *Managed FortiAPs* entry for every new AP that discovers this interface, waiting for authorization. Disable it and only APs whose serial numbers you pre-added are listed.
* `auto-auth-extension-device` (default **disable**) authorizes newly discovered FortiAPs (and FortiSwitches) automatically. It can be set per interface or under `config system global` for all dedicated interfaces.
* Optional DHCP hardening: `set vci-match enable` and `set vci-string "FortiAP"` in the DHCP server so only FortiAPs get leases.

## Step 2: discovery — how the AP finds the controller

With `AC_DISCOVERY_TYPE=0` (auto, the default), a FortiAP tries the methods in this order:

1. **Static** — unicast to `AC_IPADDR_1` (…`_2`, `_3`). Routing must work both ways.
2. **DHCP** — the controller address from **option 138** in the AP's DHCP lease, encoded in hex (10.10.10.1 = `0A0A0A01`). Several addresses can be concatenated; the first has highest priority. If option 138 is taken, change the code on the AP with `AC_DISCOVERY_DHCP_OPTION_CODE` (and match it on the server).
3. **DNS** — the AP resolves `fortinet-capwap-controller` plus the domain from DHCP option 15 (e.g. `fortinet-capwap-controller.example.com`). `AC_HOSTNAME_1..3` change the host part.
4. **FortiManagement Cloud** (formerly FortiLAN/FortiEdge Cloud) — DNS lookup of **`apctrl1.forticloud.com`**, then HTTPS to learn the cloud controller's address.
5. **Multicast** — to **224.0.1.140** by default. `config wireless-controller global` → `set discovery-mc-addr` on the FortiGate and `AC_DISCOVERY_MC_ADDR` on the AP must match. Works across subnets only with multicast routing.
6. **Broadcast** — the AP and controller must be in the same broadcast domain. No configuration.

Timing: for each method the AP sends a discovery request, waits `discovery-interval` (`config wireless-controller timers`, default **5 s**, range 2–180) and retries up to **three** times before moving on. When broadcast (the last method) fails, the AP enters the **SULKING** state, waits, then starts discovery again.

> **Watch out:** Fortinet's own pages disagree on the numeric `AC_DISCOVERY_TYPE` values for multicast and broadcast (5 and 6 are swapped between two pages). Static = 1, DHCP = 2, DNS = 3 and FortiCloud = 7 are consistent. Learn the order by name.

> **Exam tip:** If the AP is in a different subnet from the controller, broadcast discovery cannot work. Use DHCP option 138 (the most efficient remote method), DNS, static, or multicast with multicast routing.

FortiAP-side commands (SSH or console; default AP address 192.168.1.2/24, user `admin`, no password until you set one):

```text
FortiAP-231F # cfg -a AC_DISCOVERY_TYPE=1
FortiAP-231F # cfg -a AC_IPADDR_1=10.10.10.1
FortiAP-231F # cfg -c
```

`cfg -s` shows the variables, `cfg -a` adds or changes one, `cfg -c` commits to flash, `cfg -x` resets to factory defaults. The AP gets its own address by DHCP (`ADDR_MODE=DHCP`) unless you set `ADDR_MODE=STATIC` with `AP_IPADDR`, `AP_NETMASK` and `IPGW`. `AP_MGMT_VLAN_ID` tags the AP's own management traffic.

## Step 3: authorization

A discovered AP appears in **Managed FortiAPs** within about two minutes as waiting for authorization. Authorize it in the GUI (right-click > *Authorize*) or on the CLI:

```text
FGT-HQ # config wireless-controller wtp
FGT-HQ (wtp) # edit "FP231FTF20000001"
FGT-HQ (FP231FTF20000001) # set admin enable
FGT-HQ (FP231FTF20000001) # set wtp-profile "FAP231F-office"
FGT-HQ (FP231FTF20000001) # end
```

* `admin` values: `discovered` (known but not authorized — this is also how you **deauthorize**), `enable` (authorized and managed), `disable` (the controller refuses to provide service).
* On authorization the AP gets the **default FortiAP profile for its model** (e.g. `FAP231F-default`) unless you assign one.
* `get wireless-controller wtp` lists discovered and managed serial numbers.

### Pre-authorization

* **By serial number**: *Create New > Managed AP*, enter the serial, choose a profile. The AP is authorized the moment it connects.
* **By wildcard serial**: six-character model prefix + four asterisks + six characters, e.g. `FP231F****000001`. The first FortiAP-231F that connects takes over that entry — FortiOS renames the entry to the real serial (the UUID stays the same) and the AP is authorized with that entry's profile. Create `FP231F****000002`, `…000003` for the next units.

## Step 4: CAPWAP join

| Channel | Port | Protection |
|---------|------|-----------|
| Control | UDP **5246** (`AC_CTL_PORT`) | **Always DTLS** |
| Data | UDP **5247** | `dtls-policy` in the FortiAP profile: `clear-text` (default), `dtls-enabled`, `ipsec-vpn`, `ipsec-sn-vpn` — Domain 2 covers this |

The controller's state machine for each AP, as shown by a `wtp_filter` + `cw_acd` debug:

```text
DISCOVERY_REQ/RESP → CWAS_DTLS_SETUP → CWAS_DTLS_AUTHORIZE → CWAS_DTLS_CONN
→ CWAS_JOIN (JOIN_REQ) → CWAS_CONFIG (CFG_STATUS) → CWAS_DATA_CHAN_SETUP
→ CWAS_DATA_CHECK → CWAS_RUN
```

After RUN, the AP sends echo requests every `echo-interval` (default 30 s) and the controller pushes configuration updates (`CFG_UPDATE_RESP … rc 0 (Success)`).

To capture it on the FortiGate:

```text
FGT-HQ # diagnose wireless-controller wlac wtp_filter FP231FTF20000001 0-10.10.10.21:5246 2
FGT-HQ # diagnose debug console timestamp enable
FGT-HQ # diagnose debug application cw_acd 0x7ff
FGT-HQ # diagnose debug enable
```

A quicker first check is the sniffer: `diagnose sniffer packet port5 "port 5246" 4`. No packets from the AP means a network/discovery problem; packets in both directions but no RUN state points to authorization, DTLS or data-channel settings.

Typical join failures:

| Symptom | Likely cause |
|---------|-------------|
| No discovery requests reach the FortiGate | Wrong discovery method for the topology, routing/ACL, UDP 5246 blocked |
| Discovery request, no response | `fabric` not in `allowaccess`, or wrong interface/VDOM |
| AP listed but stays "waiting for authorization" | Not authorized and `auto-auth-extension-device` is disabled |
| Join ok, stuck before RUN at data channel | Data channel security mismatch or UDP 5247 blocked |

## FortiWiFi local radio

On a FortiWiFi, the built-in radio is managed like a FortiAP (*WiFi & Switch Controller > Local WiFi Radio*) with a profile whose platform is **FortiWiFi local radio**. It does **not** support bridge-mode SSIDs. With VDOMs, choose its VDOM with `config wireless-controller global` → `set local-radio-vdom`.

## Lab it yourself

* FortiGate-VM trial: configure `port2` with an IP, `allowaccess ping fabric` and a DHCP server with `vci-match`. Pre-authorize a wildcard serial (`edit "FP231F****000001"`, `set admin enable`) and look at the entry with `show`. Change `discovery-interval` and `discovery-mc-addr` and read them back.
* Needs a real FortiAP: watch the join with the `wtp_filter`/`cw_acd` debug, then break it on purpose (remove `fabric`, or set a static `AC_IPADDR_1` that is wrong) and compare the debug.

## Key takeaways

* `allowaccess fabric` (Security Fabric Connection) enables CAPWAP on the AP-facing interface; `ap-discover` default enable, `auto-auth-extension-device` default disable.
* Auto discovery order: static → DHCP (option 138, hex) → DNS (`fortinet-capwap-controller`) → FortiManagement Cloud (`apctrl1.forticloud.com`) → multicast (224.0.1.140) → broadcast; then SULKING.
* Each method: up to 3 requests, `discovery-interval` default 5 s.
* Authorize with `set admin enable`; `discovered` deauthorizes. New APs get their model's default profile.
* Wildcard serial `FP231F****000001` pre-authorizes the next AP of that model and is renamed to the real serial.
* CAPWAP control UDP 5246 is always DTLS; data UDP 5247 is clear text by default. The join ends in CWAS_RUN.
