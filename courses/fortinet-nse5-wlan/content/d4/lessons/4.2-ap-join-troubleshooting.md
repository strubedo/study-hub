## The join, step by step

A FortiAP goes through the same CAPWAP sequence every time it connects. Troubleshooting is finding the step where it stops.

| Step | What must be true |
|---|---|
| 1. AP has an IP address | DHCP on the AP's VLAN (or `ADDR_MODE=STATIC`), the right `AP_MGMT_VLAN_ID` if management is tagged |
| 2. Discovery | The AP learns or guesses the controller address: static `AC_IPADDR_1..3` → DHCP option 138 → DNS `fortinet-capwap-controller` → FortiManagement Cloud → multicast 224.0.1.140 → broadcast. Each method is tried with a few requests `discovery-interval` (default 5 s) apart; after the last one fails the AP waits in the **SULKING** state, then starts over |
| 3. FortiGate answers | The receiving interface has **Security Fabric Connection** administrative access (`allowaccess fabric`), which enables CAPWAP; `ap-discover` (default enable) creates an entry for the new AP |
| 4. DTLS on the control channel | UDP **5246**, always DTLS. Needs certificates to validate and the path to carry the handshake |
| 5. Join | Join request/response; the AP must be **authorised** (or pre-authorised by serial / wildcard serial) to get its configuration |
| 6. Configuration | Configuration status and change-state exchanges; the FortiAP profile is pushed |
| 7. Data channel | Data channel (UDP 5247 per RFC 5415) comes up with the agreed `dtls-policy` (clear text by default) and is verified by keep-alives |
| 8. RUN | Normal operation; echo requests every `echo-interval` (default 30 s) |

## First checks (no debug yet)

1. **Managed FortiAPs:** is the AP listed? Discovered-but-unauthorised APs appear within a couple of minutes; authorise them. An AP that never appears has a discovery or reachability problem (steps 1–3).
2. **The interface:** `show system interface port5` should include `fabric` in `set allowaccess`.
3. **The path:** can the AP subnet reach the controller IP and back? Any firewall, NAT device or ACL between them must pass UDP 5246 and 5247.
4. **The AP itself:** console or SSH in and check `cfg -s` for `AC_DISCOVERY_TYPE`, `AC_IPADDR_1`, `ADDR_MODE`; ping the controller from the AP.
5. **DHCP option 138:** if you use it, the value must be the controller IP **in hex** (10.10.10.1 = `0A0A0A01`).

> **Exam tip:** Broadcast and multicast discovery need the AP and controller in the same broadcast domain (or multicast routing for 224.0.1.140). An AP in a remote subnet must use static, DHCP option 138, DNS or FortiManagement Cloud.

## Is CAPWAP reaching the FortiGate?

The quickest test is the sniffer on the interface facing the APs:

```text
FGT-HQ # diagnose sniffer packet port5 "port 5246" 4
interfaces=[port5]
filters=[port 5246]
2.118203 port5 in 10.10.10.23.5246 -> 10.10.10.1.5246: udp 120
2.118511 port5 out 10.10.10.1.5246 -> 10.10.10.23.5246: udp 104
```

Read it as follows:

| Sniffer shows | Points to |
|---|---|
| Nothing from the AP | The AP never sends to this interface: AP addressing, discovery settings, routing, upstream firewall, wrong interface |
| Packets **in**, nothing **out** | The FortiGate is not answering: check `allowaccess fabric` on that interface, local-in restrictions, or an AP that is denied |
| Both directions, AP still not online | Move on to the CAPWAP debug to see the stage |

For a capture you can convert to PCAP and open in Wireshark, Fortinet uses verbosity 6: `diagnose sniffer packet port5 "port 5246" 6 0 l`.

## The CAPWAP debug

Filter on the AP, then enable the `cw_acd` debug:

```text
FGT-HQ # diagnose wireless-controller wlac wtp_filter FP431GTF20000002 0-10.10.10.22:5246 2
FGT-HQ # diagnose debug console timestamp enable
FGT-HQ # diagnose debug application cw_acd 0x7ff
FGT-HQ # diagnose debug enable
```

The filter takes the AP serial and `<vdom index>-<AP IP>:5246`. A healthy join prints messages (`<msg>`), events (`<aev>`) and state-machine transitions (`<fsm>`), in this order of states:

```text
<msg> DISCOVERY_REQ (12) <== ws (0-10.10.10.22:5246)
<msg> DISCOVERY_RESP (12) ==> ws (0-10.10.10.22:5246)
<fsm> old CWAS_IDLE(1) ev CWAE_LISTENER_THREAD_READY(1) new CWAS_DTLS_SETUP(4)
<fsm> old CWAS_DTLS_SETUP(4) ev CWAE_DTLS_PEER_ID_RECV(7) new CWAS_DTLS_AUTHORIZE(2)
<fsm> old CWAS_DTLS_AUTHORIZE(2) ev CWAE_DTLS_AUTH_PASS(3) new CWAS_DTLS_CONN(5)
<fsm> old CWAS_DTLS_CONN(5) ev CWAE_DTLS_ESTABLISHED(8) new CWAS_JOIN(7)
<msg> JOIN_REQ (14) <== ws (0-10.10.10.22:5246)
<fsm> old CWAS_JOIN(7) ev CWAE_CFG_STATUS_REQ(13) new CWAS_CONFIG(8)
<fsm> old CWAS_CONFIG(8) ev CWAE_CHG_STATE_EVENT_REQ_RECV(23) new CWAS_DATA_CHAN_SETUP(10)
<fsm> old CWAS_DATA_CHAN_SETUP(10) ev CWAE_DATA_CHAN_CONNECTED(32) new CWAS_DATA_CHECK(11)
<fsm> old CWAS_DATA_CHECK(11) ev CWAE_DATA_CHAN_VERIFIED(36) new CWAS_RUN(12)
```

`<==` is received from the AP, `==>` is sent to it. In RUN you then see periodic `ECHO_REQ` from the AP and status lines like `AC (2) -> WTP (0-10.10.10.22:5246) State: CWAS_RUN (12)`.

Where the trace stops tells you where to look:

| Last good stage | Likely area |
|---|---|
| `DISCOVERY_REQ` / `DISCOVERY_RESP` keep repeating and `CWAS_DTLS_SETUP` never appears | The AP is not proceeding to join this controller. A couple of discovery pairs before DTLS is normal; endless repeats suggest the responses are not getting back to the AP (asymmetric path, NAT, filtering) |
| Stuck in `CWAS_DTLS_SETUP` / `CWAS_DTLS_AUTHORIZE` | DTLS handshake: certificate problems, or large handshake packets lost on the path (fragmentation/MTU). Fortinet notes a slow DTLS response can mean a configuration or certificate issue |
| AP listed in Managed FortiAPs but never gets its configuration | Check authorisation first: an AP that is not authorised does not receive its FortiAP profile |
| Reaches `CWAS_DATA_CHAN_SETUP` but never `CWAS_RUN` | Data channel: UDP 5247 blocked or a **data channel security mismatch** between the profile's `dtls-policy` and the AP's `AC_DATA_CHAN_SEC` |
| RUN, then drops back to discovery | Keep-alive loss: unstable path, NAT session timeouts, controller daemon problems |

When finished: `diagnose debug disable` and `diagnose debug reset`, so the console is not flooded and filters do not linger.

To read control messages in a packet capture, turn off DTLS on the control channel temporarily with `diagnose wireless-controller wlac plain-ctl <SN> 1` on the FortiGate and `cw_diag plain-ctl 1` on the AP. Turn it back off afterwards.

## Intermittent disconnects

Fortinet's checklist for "one AP keeps dropping" or "all APs drop and come back":

* **Check the network** between the APs and the controller (switch ports, PoE budget, uplinks, VPNs).
* **Check authorisation** of the affected APs.
* **All APs at once** suggests the controller. Look for daemon crashes with `diagnose debug crashlog read`. Restarting `cw_acd` (`execute wireless-controller restart-acd`) may help, but it **drops every AP**.
* **APs behind NAT** (remote sites, home offices) can drop when the NAT device ages out the idle UDP session. CAPWAP echo requests run every `echo-interval` (default 30 s); if the NAT timeout is shorter, set `config wireless-controller timers` → `set nat-session-keep-alive <seconds>` (default 0, off) so the AP sends extra keep-alives. `cw_diag -c acs` on the AP shows `nat-sess-keep-alive` and `echo-interval`.
* **Fragmentation:** CAPWAP adds overhead, so full-size client packets become fragmented tunnel packets. The FortiAP profile's `ip-fragment-preventing` (default `tcp-mss-adjust`) and `tun-mtu-uplink`/`tun-mtu-downlink` (default 0 = AP's local MTU) control this; per-AP override with `override-ip-fragment` in `config wireless-controller wtp`.

> **Watch out:** `restart-acd` is not a fix for one AP. It disconnects every AP and every client on the FortiGate. Use `execute wireless-controller reset-wtp <SN>` to reboot only the affected AP.

## Lab it yourself

On the FortiGate-VM trial: confirm `allowaccess fabric` on an interface, configure a DHCP scope with option 138 in hex, pre-authorise a wildcard serial in `config wireless-controller wtp`, and set `nat-session-keep-alive`. Run `diagnose sniffer packet port2 "port 5246" 4` to see the command format (no CAPWAP traffic without an AP). The debug traces in this lesson need a real FortiAP; the cheapest lab is a used FortiAP and a PoE injector on a VM port bridged to a physical NIC.

## Key takeaways

* Join sequence: IP → discovery → DTLS (UDP 5246) → join → configuration → data channel → RUN.
* The FortiGate interface needs `allowaccess fabric`; unauthorised APs must be authorised before they get configuration.
* `diagnose sniffer packet <intf> "port 5246" 4` separates "AP never sends" from "FortiGate never answers".
* `wlac wtp_filter <SN> 0-<ip>:5246 2` + `diagnose debug application cw_acd 0x7ff` + `diagnose debug enable` shows the CAPWAP state machine; find the last good state.
* Stuck before RUN after data channel setup → check `dtls-policy` vs `AC_DATA_CHAN_SEC` and UDP 5247.
* NAT drops → `nat-session-keep-alive`; all APs flapping → crashlog; `restart-acd` drops all APs.
