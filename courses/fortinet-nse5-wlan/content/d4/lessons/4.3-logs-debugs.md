## Wireless event logs

Wireless events are FortiOS **event logs** with `type="event" subtype="wireless"`. In the GUI they are under **Log & Report > System Events**, in the **WiFi Events** log type (the 7.6 Administration Guide notes this log type is available on hardware devices when the WiFi controller is enabled in System > Feature Visibility).

Two settings decide what gets logged:

```text
FGT-HQ # config log eventfilter
FGT-HQ (eventfilter) # set wireless-activity enable
FGT-HQ (eventfilter) # end
FGT-HQ # config wireless-controller log
FGT-HQ (log) # set status enable
FGT-HQ (log) # set sta-event-log notification
FGT-HQ (log) # set rogue-event-log notification
FGT-HQ (log) # set wids-log notification
FGT-HQ (log) # end
```

* `wireless-activity` (default enable) turns wireless event logging on or off as a whole.
* `config wireless-controller log` sets the **lowest severity** logged per category: `sta-event-log`, `wtp-event-log`, `radio-event-log`, `rogue-event-log`, `wids-log`, `clb-log` (client load balancing), `dhcp-starv-log`, `ble-log`, `sta-locate-log`, `led-sched-log`, `addrgrp-log`, `wtp-fips-event-log`. All default to `notification`. Raise one to `information` or `debug` while troubleshooting, then put it back.

### Reading a wireless log

Wireless logs share a common set of fields. A client log from extended logging looks like:

```text
date=2026-10-20 time=08:41:12 logid="0104043677" type="event" subtype="wireless" level="notice" vd="root" logdesc="Association request from wireless station" sn="FP431GTF20000002" ap="AP-Floor2" vap="corp-wlan" ssid="Corp" radioid=2 stamac="02:1a:2b:3c:4d:5e" channel=36 security="WPA2 Personal" encryption="AES" action="assoc-req" reason="Reserved 0" msg="AP received association request frame from client 02:1a:2b:3c:4d:5e" remotewtptime="1203.551812"
```

| Field | Tells you |
|---|---|
| `logdesc` / `action` | The event (human and machine forms) |
| `sn` / `ap` | Which FortiAP reported it |
| `vap` / `ssid` / `radioid` / `channel` | Where on the AP |
| `stamac` | The client |
| `security` / `encryption` | SSID security in use |
| `level` | notice for normal steps, warning for failures |
| `remotewtptime` | The AP's own timestamp, useful to order events from one AP |

### Extended client logs

FortiAPs report each step of a client connection, so the controller can log the whole timeline without a debug:

| Stage | `action` values (successful path) | Failure examples |
|---|---|---|
| Probe | `probe-req`, `probe-resp` | |
| 802.11 authentication | `auth-req`, `auth-resp` | |
| Association | `assoc-req`, `assoc-resp` | |
| 4-way handshake | `WPA-1/4-key-msg` … `WPA-4/4-key-msg` | `WPA-invalid-2/4-key-msg`: "Probably wrong password entered, invalid MIC in 2/4 message" |
| 802.1X | `RADIUS-auth-success` | `RADIUS-auth-failure` |
| MAC authentication | `RADIUS-MAC-auth-success` | `RADIUS-MAC-auth-failure` |
| DHCP | `DHCP-DISCOVER`, `DHCP-OFFER`, `DHCP-REQUEST`, `DHCP-ACK` | `DHCP-NAK`, `DHCP-no-response`, `DHCP-no-ACK`, `DHCP-self-assigned-IP` |
| Group key | `WPA-group-1/2-key-msg`, `WPA-group-2/2-key-msg` | |
| 802.11r roam | `FT-action-req/resp`, `FT-reassoc-req/resp`, `FT-auth-req/resp` | `FT-invalid-action-req`, `FT-invalid-auth-req` |
| DNS | | `DNS-no-domain` (non-existent domain) |

Read them like a debug: the **last successful action** for a client locates the failure. A client whose log ends at `WPA-2/4-key-msg` followed by `WPA-invalid-2/4-key-msg` typed the wrong PSK. One that reaches `WPA-4/4-key-msg` and then shows `DHCP-DISCOVER` and `DHCP-no-response` has a DHCP problem, not a Wi-Fi problem. `DHCP-self-assigned-IP` means the client gave up and picked a 169.254.x.x address.

Other wireless logs to recognise: rogue and phishing events (`Fake AP detected`, `Fake AP on air`, `Offending AP detected`, `Rogue AP suppressed`), WIDS detections, and SAM results (`SAM ping test result`, `SAM iperf test result`). FortiAP syslog profiles can also send the AP's own logs to a syslog server.

## CAPWAP debug and sniffers

Lesson 4.2 covered the CAPWAP join trace. The essentials for reading one:

```text
FGT-HQ # diagnose wireless-controller wlac wtp_filter FP231FTF20000001 0-10.10.10.21:5246 2
FGT-HQ # diagnose debug console timestamp enable
FGT-HQ # diagnose debug application cw_acd 0x7ff
FGT-HQ # diagnose debug enable
```

* Message lines: `<msg> DISCOVERY_REQ (12) <== ws (0-10.10.10.21:5246)`. `<==` received from the AP, `==>` sent to it. The number in brackets is the CAPWAP sequence number.
* State machine lines: `<fsm> old CWAS_JOIN(7) ev CWAE_CFG_STATUS_REQ(13) new CWAS_CONFIG(8)`: old state, event, new state.
* States in order: IDLE → DTLS_SETUP → DTLS_AUTHORIZE → DTLS_CONN → JOIN → CONFIG → DATA_CHAN_SETUP → DATA_CHECK → RUN.
* In RUN: `ECHO_REQ` keep-alives, `WTP_EVENT_REQ` reports and `CFG_UPDATE_RESP ... rc 0 (Success)` replies to configuration pushes.

Capture options:

| Goal | Command |
|---|---|
| Is CAPWAP control traffic flowing? | `diagnose sniffer packet <intf> "port 5246" 4` |
| PCAP-convertible capture | `diagnose sniffer packet <intf> "port 5246" 6 0 l` |
| Read control messages in clear | `diagnose wireless-controller wlac plain-ctl <SN> 1` + `cw_diag plain-ctl 1` on the AP |
| Stream an AP's CAPWAP to a Wireshark host | `diagnose wireless-controller wlac sniff-cfg <host-ip> <port>` then `diagnose wireless-controller wlac sniff <intf> <SN> 2` (2 = control and data, 1 = control only, 0 = off); decode as IP in Wireshark |
| Capture 802.11 frames over the air | Radio `mode sniffer` with `ap-sniffer-chan`, `ap-sniffer-chan-width`, `ap-sniffer-addr`, `ap-sniffer-bufsize` (default 16 MB) and frame-type toggles (`ap-sniffer-mgmt-beacon`, `-mgmt-probe`, `-mgmt-other`, `-ctl`, `-data`) |

Notes on the over-the-air sniffer: it is configured in the CLI; one radio captures one channel at a time (two FortiAPs to capture two bands at once); the file is kept temporarily on the AP (`/tmp/wl_sniff.cap`) and is **deleted if you change the radio mode** or reboot before copying it off with TFTP. It is the only way to see 802.11 details such as data rates, retries and capabilities.

The CAPWAP data channel (UDP 5247) is clear text by default (`dtls-policy clear-text`): CAPWAP itself does not encrypt it, which is why a sniffer on the wire can see station association, EAP and key-exchange traffic in it. Where the path between AP and FortiGate is untrusted (internet, remote sites), use `dtls-enabled` or an IPsec data channel instead.

## Client debug: `sta_filter`

```text
FGT-HQ # diagnose wireless-controller wlac sta_filter 02:1a:2b:3c:4d:5e 2
FGT-HQ # diagnose debug application cw_acd 0x7ff
FGT-HQ # diagnose debug enable
```

A successful WPA2-Personal connection reads as three phases:

```text
<ih> IEEE 802.11 mgmt::assoc_req <== 02:1a:2b:3c:4d:5e vap corp-wlan rId 1 wId 0 04:d5:90:12:30:b8
<ih> IEEE 802.11 mgmt::assoc_resp ==> 02:1a:2b:3c:4d:5e vap corp-wlan rId 1 wId 0 04:d5:90:12:30:b8 resp 0
<dc> STA add 02:1a:2b:3c:4d:5e vap corp-wlan ws (0-10.10.10.21:5246) rId 1 wId 0 bssid 04:d5:90:12:30:b8 NON-AUTH
<eh> send 1/4 msg of 4-Way Handshake
<eh> recv EAPOL-Key 2/4 Pairwise replay cnt 1
<eh> send 3/4 msg of 4-Way Handshake
<eh> recv EAPOL-Key 4/4 Pairwise replay cnt 2
<dc> STA chg 02:1a:2b:3c:4d:5e vap corp-wlan ws (0-10.10.10.21:5246) rId 1 wId 0 bssid 04:d5:90:12:30:b8 AUTH
<eh> ***pairwise key handshake completed*** (RSN)
<dc> DHCP Request server 0.0.0.0 <== host LAPTOP-114 mac 02:1a:2b:3c:4d:5e ip 10.20.10.31
<dc> DHCP Ack server 10.20.10.1 ==> host mac 02:1a:2b:3c:4d:5e ip 10.20.10.31 mask 255.255.255.0 gw 10.20.10.1
```

1. **Association** (`<ih>` lines): `assoc_req` in, `assoc_resp` out with `resp 0` (success). The station is added as NON-AUTH.
2. **4-way handshake** (`<eh>` lines): the AP side sends message 1/4 (ANonce), receives 2/4 (SNonce plus MIC proving the client has the right PMK), sends 3/4 (GTK, install keys) and receives 4/4. The station changes to AUTH and the pairwise handshake completes.
3. **DHCP** (`<dc>` lines): request and ACK with the address, mask and gateway.

On an Enterprise SSID, EAP exchanges with the RADIUS server come **between** association and the 4-way handshake; the PMK comes from 802.1X instead of the passphrase.

Failure patterns:

| Trace ends after | Meaning |
|---|---|
| `assoc_req` with no successful response | Association refused (settings, capacity, load balancing) |
| `recv EAPOL-Key 2/4` with no `send 3/4` | The 2/4 MIC did not verify: **wrong PSK** (or wrong SAE password) |
| EAP exchange with no handshake | 802.1X failure: check RADIUS (reject, timeout, certificate) |
| `pairwise key handshake completed` but no `DHCP Ack` | Wi-Fi is fine; DHCP or the VLAN path is not |

The admin guide shows the same filter at level 1 catching a disconnect: `<ih> IEEE 802.11 mgmt::disassoc <==` from the client followed by `STA del`.

Clean up after every debug session: `diagnose debug disable` and `diagnose debug reset`.

> **Exam tip:** In a `sta_filter` exhibit, find the last line of each phase. Association good + 2/4 received + no 3/4 = wrong passphrase. Handshake complete + no DHCP Ack = DHCP. That covers most client-debug questions.

## Lab it yourself

On the FortiGate-VM trial you can set `config log eventfilter` and `config wireless-controller log`, and point `config log syslogd setting` at a Linux host to see log format. Whether the trial VM shows WiFi Events is uncertain (the admin guide says hardware devices). Debug traces and extended logs need a real FortiAP; a wrong-PSK attempt and a DHCP-scope-exhaustion test give you both failure patterns in ten minutes.

## Key takeaways

* Wireless events are `subtype="wireless"` event logs in Log & Report > System Events > WiFi Events; `wireless-activity` and `config wireless-controller log` control them.
* Extended logs trace probe → auth → assoc → 4-way handshake → RADIUS → DHCP → DNS per client; the last successful action locates the fault.
* `WPA-invalid-2/4-key-msg` = wrong password; `DHCP-no-response` = DHCP server unreachable.
* CAPWAP debug: `wtp_filter`, `cw_acd 0x7ff`, `debug enable`; read `<msg>` direction and `<fsm>` states up to CWAS_RUN.
* Client debug: `sta_filter <MAC> 2` shows association (`<ih>`), handshake (`<eh>`) and DHCP (`<dc>`).
* Over-the-air capture uses radio `mode sniffer`; the pcap is lost if the radio mode changes before you copy it.
