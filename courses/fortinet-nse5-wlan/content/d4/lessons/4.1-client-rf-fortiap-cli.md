## Reading client RF numbers correctly

Every wireless troubleshooting conversation comes back to four numbers. Get the units right; the exam and the owner of this site both check.

| Quantity | Unit | What it means | Typical FortiOS source |
|---|---|---|---|
| **Signal (RSSI)** | dBm (negative) | Received power. -45 dBm is strong, -67 dBm is a common design target for voice/data, below about -75 dBm clients struggle | `signal=` in `wlac -d sta online`, Signal Strength column |
| **Noise floor** | dBm | Background RF energy on the channel with nothing decodable in it. Quiet 5 GHz channels sit near -95 dBm | `noise=` in `wlac -d sta online`, `nf:` in `rf-sa` |
| **SNR** | dB (a ratio) | Signal minus noise floor. -60 dBm over a -95 dBm floor = 35 dB SNR. Higher SNR allows higher MCS (data rates) | Signal Strength / Noise column |
| **Data rate / MCS** | Mbps / index | The modulation and coding the link is using, together with channel width, spatial streams and guard interval | Rate columns, sniffer captures |

Two rules of thumb you will use constantly:

* **dB arithmetic is logarithmic.** +3 dB is double the power, +10 dB is ten times. A client that moves from -55 to -65 dBm receives one tenth of the power.
* **Signal alone is not enough.** -65 dBm next to a microwave oven with a -70 dBm noise floor is only 5 dB SNR and will barely work; the same -65 dBm on a clean channel (-95 dBm floor) gives 30 dB.

FortiOS turns these into the client **health** score covered in Domain 3: signal Good above -56 dBm, Fair to -75 dBm, Poor below; SNR Good above 39 dB, Fair 20–39, Poor below 20; 5 GHz Good, 2.4 GHz Fair.

### Data rates and why "the link says 866 Mbps" proves little

A client's PHY rate depends on the MCS it can sustain (a function of SNR), the channel width (`channel-bonding`), the number of spatial streams (`mimo=2` in `wlac -d sta online`) and the guard interval. Real throughput is always well below the PHY rate because of contention, retries, acknowledgements and protocol overhead. Fortinet's own throughput page makes the point with an 802.11g client: a 54 Mbps link (the standard's maximum) moving a file at a little over 24 Mbps. Other facts from the same page:

* WPA with **TKIP** limits 802.11n clients to legacy rates (at most 54 Mbps); use AES-CCMP.
* A ping from a wireless client with more than about **10 ms** delay suggests a problem: weak client signal, an overloaded AP, interference, or weak AP transmit power.
* Use iPerf (or a timed file copy) between two hosts to measure real throughput.

### Collecting the data

A practical sequence when someone says "Wi-Fi is slow in room 214":

1. **Who and where:** WiFi Clients monitor or `diagnose wireless-controller wlac -d sta online | grep <mac>` → AP, radio, channel, signal, noise, security, VLAN.
2. **The AP's view:** Managed FortiAPs > Diagnostics and Tools → radio health, channel utilisation, client count; `wlac -c vap` and `-c darrp` for BSSIDs and channels.
3. **The air:** Dashboard > WiFi (Channel Utilization, Interfering APs, Signal Strength widgets), `wlac -c ap-rogue` for co-channel neighbours, spectrum analysis for non-Wi-Fi noise.
4. **Real performance:** ping latency and iPerf from the client, or a SAM test from a FortiAP radio in `sam` mode (ping or iperf, results in the WiFi event log).
5. **History:** event logs, FortiAnalyzer, or FortiAIOps SLAs if you have it.

The controller refreshes these tables on timers under `config wireless-controller timers`: station reports every 10 s (`sta-stats-interval`), radio and VAP reports every 15 s (`radio-stats-interval`, `vap-stats-interval`), station capability reports every 30 s. Data on the dashboard is therefore seconds old, not instantaneous.

## Getting to the FortiAP CLI

Three ways in:

| Method | Notes |
|---|---|
| **GUI:** Managed FortiAPs → right-click → **Connect to CLI** | Opens a console window through the FortiGate. No password by default. |
| **SSH to the AP's IP** | The AP must allow SSH. From the controller: `config wireless-controller wtp` → `edit <SN>` → `set override-allowaccess enable` → `set allowaccess ssh` (or set `allowaccess` in the FortiAP profile). |
| **Factory-default AP on the bench** | Static `192.168.1.2/24` when no DHCP server answers: give your PC 192.168.1.3, SSH as `admin` with no password, then `passwd` to set one. |

Fortinet recommends enabling SSH to problem APs early in any troubleshooting session so you can run local commands. When the AP is behind NAT, use the controller's `wlac wtpcmd` instead.

## `cfg`: the AP's local variables

FortiAP stores its local settings as variables. The commands:

| Command | Does |
|---|---|
| `cfg -s` | Show the common variables and any that differ from default |
| `cfg -a VAR=value` | Add or change a variable (in memory) |
| `cfg -c` | **Commit** changes to flash. Without it, a reboot loses them |
| `cfg -r VAR` | Remove a variable |
| `cfg -e` | Export variables |
| `cfg -x` | Reset to factory defaults |
| `cfg -h` | Help and the full variable list |

Variables you meet in troubleshooting:

| Variable | Meaning |
|---|---|
| `AC_IPADDR_1..3` / `AC_HOSTNAME_1..3` | Static controller addresses or names |
| `AC_DISCOVERY_TYPE` | 0 = auto (try every method), 1 = static, 2 = DHCP, 3 = DNS, 7 = FortiCloud; 5 and 6 are broadcast and multicast (Fortinet's pages disagree on which is which) |
| `AC_DISCOVERY_DHCP_OPTION_CODE` | DHCP option carrying the controller IP (default 138) |
| `AC_DISCOVERY_MC_ADDR` | Multicast discovery address (default 224.0.1.140) |
| `AC_CTL_PORT` | CAPWAP control port (default 5246) |
| `AC_DATA_CHAN_SEC` | Data channel security the AP accepts: `clear`, `dtls`, `ipsec`, `ipsec-sn` |
| `ADDR_MODE` | `DHCP` (default) or `STATIC` with `AP_IPADDR`, `AP_NETMASK`, `IPGW` |
| `AP_MGMT_VLAN_ID` | Tag the AP's own management traffic with a VLAN (0 = untagged) |
| `ALLOW_HTTPS` / `ALLOW_SSH` | 0 off, 1 on, 2 controlled by the AC (default 2) |
| `MESH_AP_TYPE` | 0 Ethernet, 1 WiFi mesh, 2 Ethernet with mesh backup |
| `WANLAN_MODE` | `WAN-ONLY` (default), `WAN-LAN`, `AGGREGATE` |

Example: point an AP at a controller in another subnet and make it stick.

```text
FortiAP-231F # cfg -a AC_DISCOVERY_TYPE=1
FortiAP-231F # cfg -a AC_IPADDR_1=10.10.10.1
FortiAP-231F # cfg -c
```

## `cw_diag`: the AP's live state

| Command | Shows |
|---|---|
| `cw_diag help` | All diagnostics options on this firmware |
| `cw_diag -c wtp-cfg` | AP configuration received from the controller (control plane) |
| `cw_diag -c vap-cfg` | Current SSIDs (VAPs) |
| `cw_diag -c radio-cfg` | Current radio parameters |
| `cw_diag -c ap-scan` / `sta-scan` | APs and stations this AP has scanned |
| `cw_diag -c wids` | WIDS detections |
| `cw_diag -c ap-suppress` | APs being suppressed |
| `cw_diag -c darrp` | DARRP radio channel |
| `cw_diag -c mesh` | Mesh status |
| `cw_diag -c all-countries` | Country codes |
| `cw_diag -c temperature` | CPU temperature |
| `cw_diag -c syslog config` | Syslog profile pushed by the controller |
| `cw_diag plain-ctl [0|1]` | Clear-text control channel for captures |
| `cw_diag uptime` | Daemon uptime |
| `cw_diag debug ping_ac` | Periodic ping check to the AC (off by default) |
| `fap-tech` | Consolidated tech-support output for TAC |

`cw_diag -c acs` (used in Fortinet's NAT keep-alive example) shows a WTP configuration summary including `echo-interval`, `nat-sess-keep-alive` and LED, PoE and radio counts.

Linux tools also exist on the AP. `iwconfig wlan00` shows the **actual** transmit power and mode of a radio interface (`Tx-Power=` in dBm), which you compare with the controller's configured power to catch regulatory caps; `rcfg` prints the radio configuration including SAM settings.

> **Exam tip:** Changes made with `cfg -a` are lost at reboot unless followed by `cfg -c`. "The AP forgot its static controller IP after a power cut" = someone skipped the commit.

## Lab it yourself

All FortiAP CLI work needs a real FortiAP. If you have one on the bench, connect to its default address (192.168.1.2 with no DHCP present), run `cfg -s`, set `AC_IPADDR_1` toward your FortiGate and commit, then compare `cw_diag -c wtp-cfg` before and after authorisation. On the FortiGate-VM trial you can still practise `config wireless-controller wtp` with `override-allowaccess` and `allowaccess ssh` for a pre-authorised serial number.

## Key takeaways

* RSSI and noise are dBm; SNR is dB = signal minus noise. +3 dB doubles power, +10 dB is ten times.
* PHY rate depends on MCS (SNR), channel width, spatial streams and guard interval; real throughput is much lower. Avoid TKIP.
* `wlac -d sta online` gives signal, noise, channel, radio type and MIMO per client; health thresholds turn them into Good/Fair/Poor.
* Reach the AP via Connect to CLI, SSH (`override-allowaccess` + `allowaccess ssh`) or 192.168.1.2 on a factory-default unit.
* `cfg -s / -a / -c / -x`: show, change, commit, factory reset. Always commit.
* `cw_diag -c wtp-cfg | vap-cfg | radio-cfg | ap-scan | sta-scan | wids | ap-suppress | darrp` show the AP's live state; `fap-tech` collects everything.
