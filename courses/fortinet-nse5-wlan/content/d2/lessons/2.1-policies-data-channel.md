## Wireless traffic is just another interface to the firewall

For a **tunnel-mode** SSID, nothing leaves the SSID's subnet without a firewall policy, exactly as for a wired VLAN. FortiOS treats `corp-wlan` like `port2`: the implicit deny drops anything you have not allowed.

### Address objects

Create an address bound to the SSID interface so policies stay readable:

```text
FGT-HQ # config firewall address
FGT-HQ (address) # edit "corp-wlan-net"
FGT-HQ (corp-wlan-net) # set associated-interface "corp-wlan"
FGT-HQ (corp-wlan-net) # set subnet 10.20.10.0 255.255.255.0
FGT-HQ (corp-wlan-net) # end
```

### SSID-to-internet policy

```text
FGT-HQ # config firewall policy
FGT-HQ (policy) # edit 20
FGT-HQ (20) # set name "Corp-WiFi-to-Internet"
FGT-HQ (20) # set srcintf "corp-wlan"
FGT-HQ (20) # set dstintf "wan1"
FGT-HQ (20) # set srcaddr "corp-wlan-net"
FGT-HQ (20) # set dstaddr "all"
FGT-HQ (20) # set action accept
FGT-HQ (20) # set schedule "always"
FGT-HQ (20) # set service "ALL"
FGT-HQ (20) # set utm-status enable
FGT-HQ (20) # set ssl-ssh-profile "certificate-inspection"
FGT-HQ (20) # set webfilter-profile "default"
FGT-HQ (20) # set application-list "default"
FGT-HQ (20) # set nat enable
FGT-HQ (20) # end
```

Design points:

* **One policy set per SSID.** Guests get internet only (deny to internal subnets, often with a stricter web filter and traffic shaping); corporate users get internal and internet access; IoT gets only the specific servers it needs.
* **Zones** group SSID interfaces that share policy. VLAN pooling creates a zone automatically (`<ssid>.zone`).
* **User- and group-based policies**: for Enterprise SSIDs or captive portals, add `groups` (or `users`) to the policy to differentiate access by identity.
* **Device detection** is enabled by default on new SSID interfaces, so device type and OS can appear in logs and be matched.
* **Intra-SSID traffic**: by default clients on the same tunnel SSID can reach each other. `set intra-vap-privacy enable` blocks that.
* **Security profiles** (antivirus, web filter, application control, IPS, DNS filter) attach to these policies as on any interface. For **local-bridge** SSIDs the FortiGate never sees the traffic, so its policies do not apply; UTM-capable FortiAP models can enforce bridge-mode security profiles on the AP instead.

> **Exam tip:** "Clients connect and get an IP address but cannot reach the internet" on a tunnel SSID usually means no firewall policy from the SSID interface (or no NAT). DHCP is served by the FortiGate interface itself, so it works without any policy.

## Data channel security

The CAPWAP **control** channel (UDP 5246) is always DTLS. The **data** channel (UDP 5247) carries tunnel-mode client traffic and is configured in the FortiAP profile with `dtls-policy`:

| `dtls-policy` | Behaviour | Throughput |
|---------------|-----------|-----------|
| `clear-text` (default) | Data channel not encrypted (client frames are still protected over the air by the SSID's WPA2/WPA3 encryption) | Highest; FortiGates with hardware acceleration can offload it |
| `dtls-enabled` | DTLS-encrypted data channel; optional `dtls-in-kernel enable` lets the FortiAP kernel handle encryption | Much lower — DTLS cannot be hardware-accelerated on the FortiGate |
| `ipsec-vpn` | An automatic IPsec tunnel between FortiGate and FortiAP carries the CAPWAP data | Better than DTLS; NP6-class FortiGates can offload it; the AP (no crypto chip) is usually the bottleneck |
| `ipsec-sn-vpn` | Like `ipsec-vpn`, with the FortiAP serial number in the first IKE messages | As above |

```text
FGT-HQ # config wireless-controller wtp-profile
FGT-HQ (wtp-profile) # edit "FAP231F-remote"
FGT-HQ (FAP231F-remote) # set dtls-policy ipsec-vpn
FGT-HQ (FAP231F-remote) # end
```

* Use `clear-text` when the AP-to-controller path is on a trusted internal network; use DTLS or IPsec when it crosses an untrusted network (remote APs over the internet).
* The FortiGate's setting and the FortiAP's own data channel setting must **agree** or the AP cannot join. By default a FortiAP accepts either clear text or DTLS and lets the controller decide; if the controller also offers both, clear text is used.
* FortiOS 7.6.0 added **IKEv2** support for the FortiAP IPsec data channel.

> **Watch out:** Fortinet's documents spell the serial-number IPsec option two ways: the FortiAP guide writes `ipsec-vpn-sn`, the FortiOS 7.6.3 CLI Reference lists **`ipsec-sn-vpn`**. Use `set dtls-policy ?` on your own FortiGate to see the exact keyword.

### CAPWAP offloading

Mid-range and high-end FortiGates can offload tunnel-mode CAPWAP traffic to the NP:

* `dtls-policy` must be `clear-text` or `ipsec-vpn` (DTLS is never offloaded).
* `config system npu` → `set capwap-offload enable`.
* Fragmented CAPWAP traffic is not offloaded — another reason to manage MTU on the AP path (`ip-fragment-preventing` in the FortiAP profile).

## Other access controls on an SSID

| Setting (`config wireless-controller vap`) | Purpose |
|------------------------------------------|---------|
| `schedule` | Broadcast only during the schedule(s) |
| `max-clients`, `max-clients-ap` | Association limits |
| `intra-vap-privacy` | Block client-to-client traffic on the SSID |
| `broadcast-suppression` | Keep selected broadcasts (ARP, DHCP…) off the air |
| `local-lan` | For local-standalone NAT SSIDs: allow or deny access to private address ranges |
| `quarantine` | Allow quarantining stations (default enable) |

## Lab it yourself

On the FortiGate-VM trial (3 policies max): create `corp-wlan` and `guest-wlan`, an address per SSID, one SSID-to-WAN policy with web filtering, and one deny policy from `guest-wlan` to `corp-wlan`. Set `dtls-policy` to each value in a FortiAP profile and read the help (`set dtls-policy ?`) to confirm the keyword spelling on your build. Measuring DTLS versus clear-text throughput needs a FortiAP.

## Key takeaways

* A tunnel SSID needs a firewall policy (usually with NAT) to reach anything; DHCP works without one.
* Security profiles, user groups and device detection apply to tunnel SSIDs like any interface; local-bridge traffic bypasses FortiGate policies.
* `intra-vap-privacy` (default disable) blocks client-to-client traffic.
* `dtls-policy`: `clear-text` (default, fastest, offloadable), `dtls-enabled` (slowest), `ipsec-vpn`/`ipsec-sn-vpn` (offloadable on NP6-class); both sides must agree.
* CAPWAP offload needs `clear-text` or `ipsec-vpn`, `capwap-offload enable`, and unfragmented packets.
