## An SSID is an interface

When you create an SSID on a FortiGate (*WiFi & Switch Controller > SSIDs > Create New > SSID*, or `config wireless-controller vap`), FortiOS also creates a **network interface** with the same name. That interface is what you put in firewall policies, DHCP servers, zones and VLAN sub-interfaces. Two names matter:

| Field | Example | Notes |
|-------|---------|-------|
| Interface (VAP) name | `corp-wlan` | Up to 15 characters; appears in *Network > Interfaces* and policies |
| SSID | `Corp` | Up to 32 characters; what clients see; default `fortinet` |

A FortiAP radio can serve several SSIDs at once (one BSSID per SSID). Each SSID has its own security mode, traffic mode, VLAN, schedule and policies — that is how one AP carries corporate, guest and IoT networks side by side.

## The three traffic modes

| | **Tunnel** (default) | **Local bridge** | **Mesh** |
|--|--|--|--|
| GUI name | Tunnel to Wireless Controller | Local bridge with FortiAP's interface | Mesh downlink |
| CLI | default (`local-bridging disable`) | `set local-bridging enable` | the radio receives the WLAN over a mesh backhaul SSID (`mesh-backhaul enable` on the backhaul VAP) |
| Where client traffic goes | Inside the CAPWAP data channel to the FortiGate | Straight out of the AP's Ethernet port onto the local LAN/VLAN | Over a wireless backhaul to a root AP, then onward |
| Who routes and filters | FortiGate (firewall policy from the SSID interface) | The wired network; FortiGate policies never see the traffic (except FortiAP-S/U bridge-mode security profiles) | Depends on the user SSID's mode |
| SSID interface on the FortiGate | Has an IP address and usually a DHCP server | No IP; clients get addresses from the LAN | — |

### Tunnel mode

* Default traffic mode and the one Fortinet's exam scenarios assume unless told otherwise.
* The SSID interface is a Layer 3 interface on the FortiGate: give it an IP, run a DHCP server, write firewall policies with `srcintf` = the SSID interface, apply security profiles.
* All APs on the same controller deliver clients of that SSID into the same subnet, so clients **keep their IP address when they roam** between APs.
* Features such as **VLAN-pool load balancing** and many captive portal types work only in tunnel mode.
* Cost: all client traffic crosses the CAPWAP data channel to the FortiGate. For remote APs, **split tunnelling** (`set split-tunneling enable` on the SSID plus `split-tunneling-acl` in the FortiAP profile) keeps some destinations local.

```text
FGT-HQ # config wireless-controller vap
FGT-HQ (vap) # edit "corp-wlan"
FGT-HQ (corp-wlan) # set ssid "Corp"
FGT-HQ (corp-wlan) # set security wpa2-only-personal
FGT-HQ (corp-wlan) # set passphrase "Example-Only-PSK-1"
FGT-HQ (corp-wlan) # set schedule "always"
FGT-HQ (corp-wlan) # next
FGT-HQ (vap) # end
FGT-HQ # config system interface
FGT-HQ (interface) # edit "corp-wlan"
FGT-HQ (corp-wlan) # set ip 10.20.10.1 255.255.255.0
FGT-HQ (corp-wlan) # end
FGT-HQ # config system dhcp server
FGT-HQ (server) # edit 10
FGT-HQ (10) # set interface "corp-wlan"
FGT-HQ (10) # set default-gateway 10.20.10.1
FGT-HQ (10) # set netmask 255.255.255.0
FGT-HQ (10) # set dns-service default
FGT-HQ (10) # config ip-range
FGT-HQ (ip-range) # edit 1
FGT-HQ (1) # set start-ip 10.20.10.10
FGT-HQ (1) # set end-ip 10.20.10.250
FGT-HQ (1) # end
FGT-HQ (10) # end
```

In the GUI the DHCP server is enabled by default on a new tunnel SSID. Note that you **cannot delete an SSID interface that has DHCP enabled** — delete the DHCP server first.

### Local bridge mode

* `set local-bridging enable`. The AP bridges the SSID to its Ethernet port; with `set vlanid 100` it tags that SSID's frames with VLAN 100 on the uplink, so the switch port must be a trunk carrying those VLANs.
* The FortiGate still manages the AP (CAPWAP control), authenticates Enterprise clients and pushes configuration, but it does not see the data — so no FortiGate firewall policy or security profile applies to bridged traffic unless the upstream path routes through the FortiGate anyway. UTM-capable FortiAP models can run security profiles on bridge SSIDs; a Security Rating check (*FortiAP UTM SSID Compatibility*) flags UTM-incapable APs that broadcast bridge SSIDs with security profiles.
* The radio picks bridge SSIDs automatically only if its profile has `vap-all bridge`; otherwise list them with `vap-all manual`.
* A FortiWiFi's built-in radio does **not** support bridge-mode SSIDs.
* Use case: branch sites where traffic should stay local, or high-throughput designs that should not hairpin through the controller.

### Mesh

Mesh replaces the AP's Ethernet uplink with a radio link.

* At least three devices: the **controller** (FortiGate), a **mesh root AP** (wired, can be a FortiWiFi local radio) and one or more **mesh leaf APs**.
* The **backhaul SSID** is a VAP with `set mesh-backhaul enable`, security **WPA2-Personal or WPA3-SAE** (WPA3-SAE with H2E-only is mandatory for a 6 GHz backhaul; H2E-only is enabled by default with `wpa3-sae`). It must be unique per controller, or other controllers may see it as a fake or rogue AP.
* Typical profile: one radio carries **only** the backhaul SSID; another radio carries the user SSIDs.
* The leaf must be preconfigured before it can join wirelessly:

```text
FortiAP-231F # cfg -a MESH_AP_TYPE=1
FortiAP-231F # cfg -a MESH_AP_SSID=fgt-hq.mesh.root
FortiAP-231F # cfg -a MESH_AP_PASSWD=Example-Only-Mesh
FortiAP-231F # cfg -a MESH_AP_SECURITY=2
FortiAP-231F # cfg -c
```

`MESH_AP_TYPE`: 0 Ethernet (default), 1 WiFi mesh, 2 Ethernet with mesh backup. `MESH_AP_SECURITY` defaults to 0 (open) — set 1 for WPA/WPA2-Personal or 2 for WPA3-SAE to match the backhaul. `MESH_ETH_BRIDGE=1` bridges the leaf's Ethernet port onto the mesh (point-to-point bridge; only with `MESH_AP_TYPE=1`). `MESH_MAX_HOPS` defaults to 4.

* Leaf APs still need **authorization** on the controller; they appear (after up to about three minutes) as waiting for authorization.

## Deploying multiple SSIDs

* Create one VAP per network (`corp-wlan`, `guest-wlan`, `iot-wlan`), each with its own security, addressing and policies.
* Assign SSIDs to radios through the FortiAP profile: `vap-all tunnel` picks up every tunnel SSID automatically, `manual` with `vaps` (or **SSID groups**, `config wireless-controller vap-group`) chooses precisely. For example, an IoT SSID on 2.4 GHz only.
* Every extra SSID adds beacons and probe responses on that radio, consuming airtime; keep the count low per radio.
* `set schedule` on a VAP (firewall schedules, not schedule groups) controls when the SSID is broadcast; the default is `always`.
* `set broadcast-ssid disable` hides the name from beacons (not a security feature).
* `set max-clients` (per SSID) and `max-clients-ap` (per SSID per AP radio) cap associations; 0 = unlimited.
* `duplicate-ssid` under `config wireless-controller setting` is disabled by default: two VAPs in the same VDOM cannot use the same SSID name unless you enable it.
* `set intra-vap-privacy enable` (default disable) blocks client-to-client traffic within the same SSID — typical for guest networks.

## Key takeaways

* Each SSID is a FortiOS interface (VAP name ≤ 15 characters, SSID ≤ 32).
* Tunnel (default): traffic to the FortiGate in CAPWAP; FortiGate routes, NATs and inspects; clients keep their IP when roaming.
* Local bridge: traffic leaves at the AP's Ethernet port (tagged with `vlanid` if set); FortiGate policies do not see it. FortiWiFi local radio has no bridge mode.
* Mesh: backhaul VAP with `mesh-backhaul enable` (WPA2-Personal or WPA3-SAE); leaves preconfigured with `MESH_AP_*` and authorized on the controller.
* `vap-all tunnel` auto-assigns tunnel SSIDs; use `manual`/SSID groups for selective deployment.
* `intra-vap-privacy` blocks client-to-client traffic in an SSID; SSID schedules control when it broadcasts.
