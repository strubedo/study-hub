## Why roaming is slow

In 802.11 the **client decides** when to roam; the infrastructure can only make roaming faster or give better hints. A roam involves:

1. Finding a better AP (scanning channels, which takes time on the client).
2. Authenticating and reassociating to the new BSSID.
3. Deriving fresh keys: on WPA2/WPA3-Personal a new 4-way handshake; on Enterprise, unless keys are cached, a **full 802.1X/EAP exchange with the RADIUS server**, which can take hundreds of milliseconds.
4. Keeping the same IP address and sessions (a layer 2 / layer 3 question).

Real-time voice and video suffer when this takes long, so each feature below attacks one of these steps.

| Feature | Standard | Speeds up | FortiOS SSID setting (default) |
|---|---|---|---|
| **Neighbor reports** | 802.11k | Step 1: the AP gives the client a list of nearby APs and channels, so it scans fewer channels | `80211k` (enable) |
| **BSS Transition Management** | 802.11v | Step 1: the AP can suggest (or request) that a client move to a better AP | `80211v` (enable) |
| **Fast BSS Transition (FT)** | 802.11r | Step 3: keys are derived from a key hierarchy (PMK-R0/R1) shared within a mobility domain, so the roam folds key exchange into authentication/reassociation without a new EAP exchange or 4-way handshake | `fast-bss-transition` (disable) |
| **Opportunistic Key Caching (OKC)** | Not an IEEE standard; widely supported extension | Step 3: the PMK from the client's first 802.1X login is made available to the other APs, so a roam to an AP it has never visited skips the full EAP exchange | `okc` (enable) |
| **PMK caching** | 802.11i | Step 3, but only when returning to an AP the client already authenticated to | |

```text
FGT-HQ # config wireless-controller vap
FGT-HQ (vap) # edit "corp-wlan"
FGT-HQ (corp-wlan) # set fast-bss-transition enable
FGT-HQ (corp-wlan) # set ft-mobility-domain 1000
FGT-HQ (corp-wlan) # set ft-over-ds disable
FGT-HQ (corp-wlan) # set 80211k enable
FGT-HQ (corp-wlan) # set 80211v enable
FGT-HQ (corp-wlan) # set okc enable
FGT-HQ (corp-wlan) # end
```

* `ft-mobility-domain` (1–65535, default 1000) must match on every AP the client should FT-roam between.
* `ft-over-ds` sends the FT exchange through the current AP over the distribution system instead of over the air to the target AP; it is off by default.
* `ft-r0-key-lifetime` sets the PMK-R0 lifetime in minutes (default 480).
* OKC and FT matter most on **Enterprise** SSIDs, where a full EAP exchange is the expensive part. On a PSK SSID every client already knows the PMK.

> **Watch out:** Some older clients fail to associate when 802.11r is advertised. If a few legacy devices stop connecting after you enable `fast-bss-transition`, that is the first suspect; a separate SSID for them is the usual fix.

## Layer 2 and layer 3 roaming

**Layer 2 (intra-controller) roaming:** the client moves between FortiAPs managed by the same FortiGate, on the same SSID.

* **Tunnel-mode SSID:** traffic always lands on the same FortiGate SSID interface, so the client keeps its IP address wherever it roams.
* **Local-bridge SSID:** the client keeps its IP only if the APs bridge it into the same VLAN/subnet; otherwise it needs a new DHCP lease.

**Layer 3 (inter-controller) roaming:** the client moves to a FortiAP managed by a **different FortiGate**, whose copy of the SSID sits on a different subnet. With L3 roaming the two controllers build a mobility tunnel so the client keeps its original IP and its traffic is carried back to the home controller.

```text
FGT-HQ # config wireless-controller inter-controller
FGT-HQ (inter-controller) # set l3-roaming enable
FGT-HQ (inter-controller) # config inter-controller-peer
FGT-HQ (inter-controller-peer) # edit 1
FGT-HQ (1) # set peer-ip 192.0.2.40
FGT-HQ (1) # next
FGT-HQ (inter-controller-peer) # end
FGT-HQ (inter-controller) # end
FGT-HQ # config wireless-controller vap
FGT-HQ (vap) # edit "corp-wlan"
FGT-HQ (corp-wlan) # set l3-roaming enable
FGT-HQ (corp-wlan) # end
```

Requirements and behaviour:

* Both controllers need the **same SSID, security mode and passphrase**, `l3-roaming enable` globally and on the VAP, and each other as `inter-controller-peer` (`peer-port` default 5246).
* `diagnose wireless-controller wlac -c ha` shows the peer and its state (for example `l3r : enabled`, a peer line with `<serial> <ip>:5246 UP`).
* `diagnose wireless-controller wlac -d sta online` shows the client's `l3r=` field and the tunnel endpoints. On the foreign controller the client keeps the home subnet's `ip=`.
* When the roamed client stays idle longer than **`client-idle-rehome-timeout`** (`config wireless-controller timers`, default **20 s**), it is **rehomed**: it requests DHCP on the new controller's subnet and from then on its traffic is handled locally.

## Client load balancing (handoff)

Separate from roaming, the controller can steer **new** connections to spread load. Two mechanisms, both configured per FortiAP profile (GUI: **Client load balancing**: Frequency Handoff and/or AP Handoff):

| Mechanism | Trigger | What the controller does |
|---|---|---|
| **Frequency handoff** (band steering, `frequency-handoff`) | A dual-band client tries to join on 2.4 GHz and its 5 GHz signal is good enough | The AP **does not answer** the 2.4 GHz attempt, so the client times out and tries 5 GHz. If the 5 GHz RSSI is too weak, the next 2.4 GHz attempt is accepted. 2.4 GHz-only clients join normally. |
| **AP handoff** (`ap-handoff`) | An AP has more clients than its threshold | The busy AP does not answer a new client that has a sufficient signal at another AP, so it joins the less busy AP. It can also signal the weakest-signal client to move. |

Key settings:

```text
FGT-HQ # config wireless-controller wtp-profile
FGT-HQ (wtp-profile) # edit "FAP231F-office"
FGT-HQ (FAP231F-office) # set frequency-handoff enable
FGT-HQ (FAP231F-office) # set ap-handoff enable
FGT-HQ (FAP231F-office) # set handoff-rssi 25
FGT-HQ (FAP231F-office) # set handoff-sta-thresh 30
FGT-HQ (FAP231F-office) # end
```

* `frequency-handoff` and `ap-handoff` both default to **disable**.
* `handoff-rssi` (20–30, default **25**) is the minimum signal a client must have on the alternative (5 GHz band, or other AP) before the controller will steer it. It is a relative RSSI scale: higher means stronger.
* `handoff-sta-thresh` is the client count at which AP handoff starts.
* **Load balancing is not applied to roaming clients**; a client that is roaming is never refused for load reasons.
* The controller learns which clients are dual-band by watching their probe requests on both bands, so steering only works for clients it has already heard.

> **Watch out:** `handoff-sta-thresh` has three different documented values: the FortiAP 7.6 guide's load-balancing page says default 55 (range 5–60), its high-density page says 30 (range 5–35), and the 7.6.3 CLI Reference shows default 0 with range 5–60. Don't memorise a number; know that it is a client count per AP. The CLI Reference also lists `handoff-roaming` ("client load balancing during roaming") with a description saying default disable but a default column saying enable.

Related high-density tools you will meet in troubleshooting questions:

* `probe-resp-suppression` + `probe-resp-threshold` (default -80 dBm) on the SSID: ignore probe requests from clients weaker than the threshold, so far-away clients do not waste airtime.
* `sticky-client-remove` with `sticky-client-threshold-2g/5g/6g` (defaults -79/-76/-76 dBm): drop clients that hang on with a weak signal instead of roaming.
* Disabling the lowest basic rates (`rates-11bg`, `rates-11a`) to make clients roam sooner.

## Lab it yourself

All of this is controller-side configuration you can type on the FortiGate-VM trial: build an SSID with `fast-bss-transition`, `80211k`, `80211v` and `okc`, set `client-idle-rehome-timeout`, configure `inter-controller` with a peer, and set the handoff options in a custom FortiAP profile. Watching a client actually FT-roam, or seeing frequency handoff refuse a 2.4 GHz join, needs two real FortiAPs and a dual-band client; the extended wireless logs then show `FT-action-req`/`FT-reassoc-req` style events.

## Key takeaways

* 802.11k = neighbor reports, 802.11v = BSS transition management, 802.11r = fast key derivation on roam, OKC = shared PMK to skip full EAP.
* FortiOS defaults: `80211k` and `80211v` enable, `okc` enable, `fast-bss-transition` disable.
* Tunnel-mode SSIDs keep the client IP across APs on one controller; bridge-mode SSIDs only if the subnet is the same.
* L3 roaming between FortiGates: same SSID/security/passphrase, `inter-controller` peers, `l3-roaming` on VAP; rehome after `client-idle-rehome-timeout` (20 s).
* Frequency handoff refuses 2.4 GHz joins from strong dual-band clients; AP handoff refuses new clients on busy APs.
* `handoff-rssi` 20–30 (default 25); load balancing never applies to roaming clients.
