## From detection to action

Detecting a rogue gives you a location (which FortiAP hears it, on which channel, how loud) so someone can walk over and unplug it. Until then, FortiOS has two active countermeasures and one passive one:

| Tool | What it does | Where |
|---|---|---|
| **Rogue AP suppression** | The controller sends deauthentication frames so clients cannot stay associated to the rogue | Rogue AP monitor state, `ap-status`, WIDS `ap-auto-suppress` |
| **Fake / offending SSID suppression** | The same mechanism, triggered automatically for APs that broadcast your SSIDs or an SSID pattern you define | `config wireless-controller setting` |
| **WIDS detection** | Raises logs for over-the-air attacks (floods, spoofed deauth, weak WEP IVs...) | WIDS profile on a radio |

## How suppression works

When an AP is marked **Suppressed Rogue AP**, the FortiGate uses a FortiAP **monitoring radio** to transmit deauthentication frames in both directions: to the rogue's clients, pretending to be the rogue, and to the rogue, pretending to be each of its clients. Clients keep getting kicked off, so the rogue becomes useless.

Prerequisites, all of which appear in exam distractors:

1. **Rogue scanning with on-wire detection** must be enabled (WIDS profile with `ap-scan enable` and a sensor mode).
2. The radio doing the suppression must be in **Dedicated Monitor** mode (`set mode monitor`). A radio busy serving clients cannot spend its airtime attacking another BSS.
3. You must check that **local law allows it**. Transmitting deauthentication frames at someone else's network is illegal in many places (in the United States the FCC has fined operators for blocking guests' Wi-Fi). Suppress only APs on your own wired network, on premises you control.

To suppress from the GUI: **Dashboard > WiFi > Rogue APs**, select the entry (or several), hover over State, click the edit icon and choose **Suppressed Rogue AP**. To stop, pick another state. From the CLI:

```text
FGT-HQ # config wireless-controller ap-status
FGT-HQ (ap-status) # edit 2
FGT-HQ (2) # set bssid 9c:3d:cf:5a:11:20
FGT-HQ (2) # set ssid "Linksys-Lab"
FGT-HQ (2) # set status suppressed
FGT-HQ (2) # end
```

On the FortiAP, `cw_diag -c ap-suppress` lists the APs it is currently suppressing.

### Automatic suppression

A WIDS profile can suppress on-wire rogues without waiting for you:

```text
FGT-HQ # config wireless-controller wids-profile
FGT-HQ (wids-profile) # edit "wids-office"
FGT-HQ (wids-office) # set ap-auto-suppress enable
FGT-HQ (wids-office) # end
```

`ap-auto-suppress` (GUI: **Auto Suppress Rogue APs in Foreground Scan**) defaults to **disable**. Enable it only where the legal question is settled; an on-wire false positive would mean attacking a neighbour.

## Fake and offending SSIDs (stopping hotspot hackers)

An evil twin usually is not on your wire, so on-wire detection never flags it. FortiOS handles it separately as a **phishing SSID**:

* A **fake SSID** is one of the SSIDs defined on this FortiGate, broadcast by an AP the controller does not manage.
* An **offending SSID** matches a pattern you define, for example anything containing your company name.

```text
FGT-HQ # config wireless-controller setting
FGT-HQ (setting) # set phishing-ssid-detect enable
FGT-HQ (setting) # set fake-ssid-action log suppress
FGT-HQ (setting) # config offending-ssid
FGT-HQ (offending-ssid) # edit 1
FGT-HQ (1) # set ssid-pattern "corp*"
FGT-HQ (1) # set action log suppress
FGT-HQ (1) # next
FGT-HQ (offending-ssid) # end
FGT-HQ (setting) # end
```

* `phishing-ssid-detect` defaults to **enable**.
* `fake-ssid-action` and the offending entry's `action` default to **log**; add `suppress` to attack the AP as well. You can set one or both keywords.
* `ssid-pattern` is case-insensitive and accepts a `*` wildcard; the CLI Reference's examples are `word`, `word*`, `*word` and `wo*rd`. `corp*` therefore matches `Corp-Free` or `CORPORATE` but not `Free-Corp`.

In `wlac -c ap-rogue`, the fourth code letter shows the result: **F** for fake, **O** for offending. The logs use distinct descriptions you should recognise: `Fake AP detected` and `Fake AP on air` (repeated while the fake stays up, interval `fake-ap-log` in `config wireless-controller timers`, default 1 minute), `Offending AP detected`, `Offending AP on air`, and `Rogue AP suppressed` when suppression starts. All are `type="event" subtype="wireless"`.

> **Exam tip:** "A user reports an SSID named exactly like the corporate SSID in the parking lot, and on-wire shows no" is a fake-SSID scenario, not an on-wire rogue scenario. The fix is `phishing-ssid-detect` with `fake-ssid-action suppress` (plus a legal check), not MAC adjacency.

## Protected management frames as a defence

Suppression works because 802.11 deauthentication and disassociation frames are unauthenticated by default, so anyone can forge them. The same weakness lets attackers knock your clients off. **802.11w Protected Management Frames (PMF)** protects robust management frames, including deauthentication and disassociation, once a client has keys. On the SSID: `set pmf enable` (required for every client) or `set pmf optional` (used when the client supports it). WPA3 modes require PMF. Note the side effect: PMF-capable clients on a protected network ignore forged deauthentication frames, which is also why suppression is less effective against rogues that use PMF.

## Wireless Intrusion Detection (WIDS)

The WIDS profile does double duty: rogue scanning settings plus a long list of intrusion detections. All detections are **disabled by default**; you enable the ones you want and apply the profile to a radio (`set wids-profile` under `config radio-N`). When a detection fires, the FortiGate writes a wireless event log; it does not block anything by itself.

Detections you should be able to recognise by name (CLI keyword in brackets):

| Detection | What it flags |
|---|---|
| Asleap attack (`asleap-attack`) | Use of the asleap tool against Cisco LEAP |
| Association / authentication frame flooding (`assoc-frame-flood`, `auth-frame-flood`) | DoS by a flood of association or authentication requests. Defaults: `assoc-flood-thresh` 30 within `assoc-flood-time` 10 s; same values for auth |
| Broadcast deauthentication (`deauth-broadcast`) | Deauth frames sent to the broadcast address to kick every client |
| Spoofed deauthentication (`spoofed-deauth`) | Forged deauth frames that appear to come from your AP |
| EAPOL flooding (`eapol-start-flood`, `eapol-logoff-flood`, `eapol-succ-flood`, `eapol-fail-flood`, plus `eapol-pre-*` toward stations) | DoS with EAPOL frames; thresholds default 10 per 1-second interval |
| Invalid MAC OUI (`invalid-mac-oui`) | Source MACs whose first three bytes are not a valid IEEE OUI (random MACs) |
| Long duration attack (`long-duration-attack`) | Frames that reserve the medium too long via the duration field; `long-duration-thresh` 1000–32767 µs, default 8200 |
| Null SSID probe response (`null-ssid-probe-resp`) | Probe responses with an empty SSID that crash some client drivers |
| Weak WEP IV (`weak-wep-iv`) | Known weak WEP initialisation vectors in the air (a WEP-cracking indicator) |
| Wireless bridge (`wireless-bridge`) | Frames with both To DS and From DS set, which also catches bridges you built on purpose |
| AP spoofing / impersonation (`ap-spoofing`, `ap-impersonation`) | Another device transmitting as one of your BSSIDs |
| Others | `netstumbler`, `wellenreiter`, `fata-jack`, `air-jack`, `omerta-attack`, `beacon-wrong-channel`, `probe-flood`, `rts-flood`, `cts-flood`, `adhoc-network`, `valid-ssid-misuse`, `wpa-ft-attack`... |

```text
FGT-HQ # config wireless-controller wids-profile
FGT-HQ (wids-profile) # edit "wids-office"
FGT-HQ (wids-office) # set deauth-broadcast enable
FGT-HQ (wids-office) # set spoofed-deauth enable
FGT-HQ (wids-office) # set eapol-start-flood enable
FGT-HQ (wids-office) # set asleap-attack enable
FGT-HQ (wids-office) # set null-ssid-probe-resp enable
FGT-HQ (wids-office) # end
```

One WIDS option *does* act: when the controller mitigates a DoS it sends deauthentication frames to unknown source clients, and `deauth-unknown-src-thresh` caps that rate (per second, default **10**, 0 = no limit) so an aggressive attack does not stop the AP from processing valid clients.

On the FortiAP, `cw_diag -c wids` shows the WIDS detections it has made. On the controller, the events land in the wireless event log (level controlled by `wids-log` in `config wireless-controller log`, default notification).

> **Watch out:** `wireless-bridge` detection fires on legitimate mesh or point-to-point bridges too. Expect it in "why is WIDS alerting on our own link" questions.

## Lab it yourself

On the FortiGate-VM trial: build a WIDS profile with several detections, set `deauth-unknown-src-thresh`, configure `phishing-ssid-detect` and an `offending-ssid` pattern, and add an `ap-status` entry with `status suppressed`. Then run `show full-configuration` on the WIDS profile to compare defaults with this lesson. Seeing detections, suppression and the `Fake AP detected` log needs real FortiAPs; never test suppression against networks you do not own.

## Key takeaways

* Suppression = controller-generated deauthentication frames against the rogue and its clients, sent by a monitor radio.
* Requirements: on-wire rogue scanning enabled, monitoring radio in **Dedicated Monitor** mode, and legal clearance.
* Manual: rogue monitor state **Suppressed Rogue AP** or `ap-status` `set status suppressed`; automatic: WIDS `ap-auto-suppress` (default disable).
* Evil twins are handled by `phishing-ssid-detect` (default enable) with `fake-ssid-action` and `offending-ssid` patterns; default action is log.
* PMF (802.11w) protects deauth/disassoc frames and defeats spoofed deauthentication against your clients.
* WIDS detections are all off by default, log only, and are applied per radio through the WIDS profile.
* `deauth-unknown-src-thresh` (default 10/s) limits mitigation deauth rate.
