## What FortiAIOps is

FortiAIOps is a separate Fortinet product (a VM or the FortiAIOps 500G appliance) that collects data from FortiGate controllers and the FortiAPs, FortiSwitches and FortiExtenders they manage, and uses AI/ML models to spot problems that affect users. Where the FortiGate monitors show you *what is* (this client is at -78 dBm), FortiAIOps tries to tell you *what is wrong and why* (these 40 clients on floor 2 have slow roams because...), and suggests remediation.

This lesson follows the **FortiAIOps 3.2 User Guide**, the version the 7.6 course lists.

Main ideas:

* **Data sources:** the FortiGate controller's REST API (polled) plus FortiGate **logs forwarded** to FortiAIOps.
* **SLAs:** FortiAIOps evaluates wireless, switching and WAN service levels and reports **impacted SLAs**, **impacted clients** and **impacted devices**, grouped by classifier and sub-classifier (the likely cause).
* **Adaptive baselines:** thresholds can be static or computed per environment by ML; the model is re-evaluated weekly (each Saturday) against the past week's RF data and updated when accuracy can improve, with a local log entry recording the change.
* **AI-ARRP:** AI-driven channel planning that can push channel choices back to FortiGate.

## Deploying and connecting it

FortiAIOps 3.2 runs on VMware ESXi 7.0.3 and later, Microsoft Hyper-V or KVM (plus several public clouds and other hypervisors in the guide). The minimum VM size is 8 vCPU, 32 GB RAM, an 8 GB OS disk and a 500 GB data disk. First login on the console is `admin` with no password (you are forced to set one); the port gets a DHCP address by default and you can make it static with `config system interface` and add a default route with `config router static`, FortiOS-style.

It needs a licence. The licensing page counts three types: **Monitoring** and **Analytics** (consumed per switch or AP) and **SD-WAN** (consumed per FortiGate).

### Adding a FortiGate controller

**Inventory > Managed FortiGates > Add**:

| Field | Notes |
|---|---|
| Standalone or HA Cluster | Either can be added |
| IP address or FQDN | Must match the FortiGate certificate's **Subject Alternative Name** |
| Username / password | An administrator account on the FortiGate |
| ADOM | FortiAIOps groups controllers into ADOMs; a controller belongs to one ADOM at a time |
| HTTPS port | Default **443** |
| Timeout | Default 5000 ms |

The connection is HTTPS, so certificates are the usual failure point:

* The address you type must appear in the FortiGate certificate's SAN (IP if you added by IP, FQDN if by FQDN, both if you use both).
* A certificate from an unknown CA fails discovery. Install the issuing CA (your internal CA, the CA behind a self-signed FortiGate CA, or Let's Encrypt's) in FortiAIOps.
* After replacing the FortiGate certificate, re-add the FortiGate.

You can also import and export FortiGate lists in bulk.

### Forwarding logs

FortiAIOps needs FortiGate logs to populate many views and to identify issues. Two options:

```text
FGT-HQ # config log syslogd setting
FGT-HQ (setting) # set status enable
FGT-HQ (setting) # set server 10.0.1.60
FGT-HQ (setting) # end
```

* **Direct from FortiGate:** a syslog server pointing at the FortiAIOps address (GUI: Log & Report > Log Settings).
* **Through FortiAnalyzer:** if the FortiGate already logs to FortiAnalyzer, create a log-forwarding entry on FortiAnalyzer (System Settings > Advanced > Log Forwarding) to the FortiAIOps IP with the FortiGate in the device filter. Syslog uses UDP 514.

> **Exam tip:** If FortiAIOps lists the FortiGate but its event-driven views stay empty, think log forwarding. If the FortiGate never appears as discovered, think certificate SAN/CA, credentials, HTTPS port or reachability.

## Wireless SLAs

FortiAIOps monitors seven wireless SLAs:

| SLA | What it looks for |
|---|---|
| **Throughput** | Low throughput, classified by cause: noise, retries, discards, channel utilisation, client MCS/data rate... |
| **Coverage** | Coverage holes (clients with low RSSI) and crowded areas with too many overlapping FortiAPs |
| **Roaming** | Slow roams, their cause and a suggested fix |
| **Time to Connect** | Clients that take too long in **association**, **authentication** (including the 4-way handshake), **DHCP** or **DNS** |
| **Connection Failure** | Failed connections by stage: association (for example low RSSI), authentication (for example RADIUS unreachable), DHCP (for example server down), DNS (for example invalid domain) |
| **AP Health and Uptime** | AP CPU, memory and temperature against thresholds, reboots and related events (switch port down...) |
| **WIDS** | Wireless intrusion attempts, with recommended actions |

Switching SLAs are Throughput, Network, Switch Health and Uptime and Switch Connection Failure; WAN SLAs are Performance, FortiExtender Health and Interface Health. You only need to recognise those.

### SLA configuration

**AI Insights > SLA Config** has three pages: Device Health, Time To Connect and Roaming. For Time to Connect and Roaming you choose:

* **Dynamic baselines:** FortiAIOps computes thresholds from your clients' history. You set the **scope** (per ADOM, per FortiGate, per AP; Roaming also per SSID), the time window of data to learn from, when to compute, and how often to repeat.
* **Static thresholds:** you enter milliseconds per phase. Roaming has separate thresholds for **Fast BSS Transition (11r) roams** (default 55 ms), **PMK cache roams** (default 100 ms) and **OKC roams** (default 100 ms). The 11r threshold only helps if the SSID has `fast-bss-transition` enabled and clients support 802.11r.

> **Watch out:** The 3.2 guide's Time to Connect page lists default static thresholds of 1000 ms (association), 1000 ms (authentication), 300 ms (DHCP) and 2000 ms (DNS), but a note on the same page says the default is 300 ms for all of them. Learn the four phases, not the numbers.

### Reading the results

* **Dashboard / AI Insights:** overview widgets.
* **Impacted SLA:** impacted wireless, switching and WAN clients grouped by SLA > classifier > sub-classifier; select a row and **View Details**. Toggle Clients/Devices.
* **Impacted Devices:** the same from the device side.
* **Acknowledge:** suppress an alert you have reviewed (for example a known old 802.11b scanner that always trips Throughput) by sub-classifier, FortiGate, AP and SSID, for a chosen duration or forever. Acknowledged alerts stop notifying and stop counting against the devices' SLA metrics.
* **Channel Insights page:** per-channel utilisation and interfering-SSID severity (last 60 seconds), noise, clients and a health assessment per radio, with Trends.
* **Rogue APs page:** the same three widgets (Interfering APs, SSID, Vendor Info) and table as the FortiGate rogue monitor.
* **SAM:** service assurance tests (baseline and scheduled tests) built on FortiAP SAM-mode radios.

## AI-ARRP

Standard DARRP lets each FortiAP pick its channel from local scans and thresholds. **AI-ARRP** replaces the decision with FortiAIOps' channel scoring: it scores every channel for every radio using noise, channel utilisation, interfering APs, rogue APs and spectral RSSI, combining real-time data with **up to two weeks** of history.

How it runs:

1. **Collect** RF statistics for every channel on each radio every minute.
2. **Analyse** hourly and produce a daily per-radio channel forecast.
3. **Validate** during the FortiGate's DARRP schedule window: channels allowed by the FortiAP profile, regulatory rules (country code, indoor/outdoor), non-overlap and channel bonding, and channels with wireless SLA failures or radar detections.
4. **Push** the chosen channels to the FortiGate, and the FortiAPs use them in their next channel-planning cycle.

Enable it per radio in the FortiAP profile:

```text
FGT-HQ # config wireless-controller wtp-profile
FGT-HQ (wtp-profile) # edit "FAP431G-hd"
FGT-HQ (FAP431G-hd) # config radio-2
FGT-HQ (radio-2) # set darrp enable
FGT-HQ (radio-2) # set ai-darrp-support enable
FGT-HQ (radio-2) # end
FGT-HQ (FAP431G-hd) # end
```

| `darrp` | `ai-darrp-support` | Result |
|---|---|---|
| disable | enable | Local DARRP is off. FortiAIOps only **reads** telemetry through REST **GET** calls and cannot change channels. |
| enable | enable | FortiAIOps takes control: it collects data and **changes channels** through REST **POST** calls. |

`ai-darrp-support` defaults to **disable**, and Fortinet recommends enabling both. Disabling AI-ARRP is the same command set to `disable` per radio. In the FortiAIOps GUI the **AI ARRP** window sits under the Wireless menu.

> **Watch out:** The 3.2 guide states AI-ARRP is supported only on **FortiOS 7.6.5 with FortiAP 7.6.3**, and `ai-darrp-support` is not in the FortiOS 7.6.3 CLI Reference. Don't expect the keyword on earlier 7.6 builds.

FortiPresence (location analytics and guest presence) uses the same FortiAP scanning data but is not part of this exam's topic list; just know it is a separate product.

## Lab it yourself

FortiAIOps needs a licence and a hefty VM, so treat it as read-and-understand. On the FortiGate-VM trial you can still prepare the FortiGate side: a REST-capable admin account, a certificate whose SAN includes the address you would add, and `config log syslogd setting` pointed at a test syslog host (a Linux box running rsyslog will show what FortiAIOps would receive). The `darrp`/`ai-darrp-support` radio settings need FortiOS 7.6.5 per the guide.

## Key takeaways

* FortiAIOps polls FortiGate controllers over HTTPS (default port 443, admin credentials, ADOM) and needs FortiGate logs forwarded (directly via syslog or through FortiAnalyzer).
* Discovery fails if the configured IP/FQDN is not in the FortiGate certificate SAN or the CA is unknown.
* Wireless SLAs: Throughput, Coverage, Roaming, Time to Connect, Connection Failure, AP Health and Uptime, WIDS.
* SLA thresholds can be dynamic (ML baselines with a scope and schedule) or static per phase.
* Acknowledge suppresses reviewed alerts so they stop affecting SLA metrics.
* AI-ARRP: `darrp enable` + `ai-darrp-support enable` per radio lets FortiAIOps change channels; with only `ai-darrp-support` it just collects. Supported on FortiOS 7.6.5 / FortiAP 7.6.3.
