## Configuration synchronization

In FortiLink mode the FortiGate holds the configuration of every managed switch and pushes it down. Two things break that model:

- **Local edits on the switch.** Changes made directly on a managed switch are unknown to the FortiGate and are lost when the switch restarts. They can also leave the FortiGate and the switch disagreeing about the configuration.
- **A push that doesn't complete.** `get-conn-status` then shows the **E** (config sync error) flag on that switch.

Two commands handle sync:

```text
FGT-HQ # execute switch-controller get-sync-status all
FGT-HQ # execute switch-controller get-sync-status switch-id FSW-Access1
FGT-HQ # execute switch-controller get-sync-status serial S124EN5918000103
FGT-HQ # diagnose switch-controller trigger config-sync FSW-Access1
```

| Command | Purpose |
|---------|---------|
| `execute switch-controller get-sync-status {all \| group <group> \| serial <sn> \| switch-id <name>}` | Check managed switches for configuration synchronization errors. `switch-id` takes the user-defined name; `serial` takes the serial number |
| `diagnose switch-controller trigger config-sync <switch>` | Push the **full** FortiGate configuration for that switch again |

A sensible order: find the switch with `E` in `get-conn-status`, check its sync status, correct whatever is wrong, then trigger a full config sync and confirm the flag clears.

> **Watch out:** Don't "fix" a managed switch by logging in and changing its CLI. The FortiGate overwrites or forgets that change. Make the change under `config switch-controller` on the FortiGate.

## Physical topology, ISLs and the secure fabric

After discovery, every port of a FortiLink switch is enabled for FortiLink, and a second switch connected to any of them forms an **inter-switch link (ISL)** automatically. Topology checks:

| Command / page | Shows |
|----------------|-------|
| **WiFi & Switch Controller > Managed FortiSwitches**, Topology view | Links, ISLs, MCLAG pairs; dashed line + broken-link icon = down |
| **Security Fabric > Physical Topology** | The same switches in the fabric view; the Diagnostics and Tools pane opens from here too |
| `execute switch-controller get-physical-conn standard <FortiLink_interface>` | FortiLink connectivity graph as text |
| `execute switch-controller get-physical-conn dot <FortiLink_interface>` | The same graph in **dot** (Graphviz) format |
| `diagnose switch-controller switch-info trunk status <switch> <trunk>` | State of a trunk (ISL, ICL, FortiLink or user LAG) on a managed switch |
| `diagnose switch-controller switch-info lldp neighbors-summary <switch>` | LLDP neighbors the switch sees: the quickest way to prove what is cabled to what |

### FortiLink secure fabric

With the secure fabric (FortiOS 7.4.1 / FortiSwitchOS 7.4.1 and later), switches authenticate each other with their Fortinet factory certificates before an ISL carries user VLANs, and ISL members can be encrypted with MACsec. It is set in the LLDP profile:

| `auto-isl-auth` | If authentication succeeds | If it fails |
|-----------------|---------------------------|-------------|
| `legacy` (default) | No authentication at all | n/a |
| `relax` | Secure ISL | **Restricted** ISL: an ISL with **no user VLANs** |
| `strict` | Secure ISL | **No ISL** |

`auto-isl-auth-encrypt` is `none` (default), `mixed` (MACsec where the port supports it) or `must` (ports without MACsec are removed from the ISL but still work as user ports). Links between the FortiGate and the switches are never encrypted, static ISLs don't support authentication, and VXLAN isn't supported. `execute switch-controller get-physical-conn` shows which switch ports are **authenticated, secured or restricted**. On the switch, `diagnose switch fortilink-auth status <port>` and `get switch lldp auto-isl-status <port>` show the per-port state.

> **Exam tip:** A newly added switch that connects but carries no user VLANs on its ISL, in a fabric using `relax`, has a **restricted ISL**: its authentication failed.

## MCLAG and the ICL

An MCLAG pair (two switches maximum, ideally the same model and firmware) presents one LACP partner to dual-homed devices. The two peers are joined by the **ICL**; Fortinet recommends at least two ICL links. Checks from the FortiGate:

```text
FGT-HQ # diagnose switch-controller switch-info mclag icl FSW-Core1
FGT-HQ # diagnose switch-controller switch-info mclag list FSW-Core1 server1-lag
FGT-HQ # diagnose switch-controller switch-info mclag peer-consistency-check FSW-Core1 server1-lag
```

On the switch the same information comes from `diagnose switch mclag icl`, `diagnose switch mclag list` and `diagnose switch mclag peer-consistency-check`:

```text
FSW-Core1 # diagnose switch mclag icl
_FlInK1_ICL0_
icl-ports            49-50
egress-block-ports   1-4,51-52
interface-mac        70:4c:a5:12:34:01
local-serial-number  S248EPTF18000101
peer-mac             70:4c:a5:12:34:81
peer-serial-number   S248EPTF18000102
Local uptime         0 days 4h:12m:05s
Peer uptime          0 days 4h:11m:58s
MCLAG-STP-mac        70:4c:a5:12:34:00
keepalive interval   1
keepalive timeout    60
dormant candidate    Peer
split-brain          Disabled
```

Read it for: the ICL member ports, both serial numbers (the peer is really there), the MAC addresses (`interface-mac` is the local switch, `peer-mac` the peer; the lower MAC decides which peer you restart first during an upgrade), uptimes and the split-brain state.

Requirements that break MCLAG when missed: `mclag-stp-aware` enabled and STP on all ICL trunks (both default), and for IGMP snooping `mclag-igmpsnooping-aware` plus the flood settings (disabled on ISL and FortiLink trunks, enabled on ICL trunks) and IGMP proxy.

### Split interface vs MCLAG to the FortiGate

The FortiLink split interface must be **enabled before** MCLAG is formed on the switches. To move from split interface to a FortiLink MCLAG: give the ICL ports the `default-auto-mclag-icl` LLDP profile on both switches, **disable** `fortilink-split-interface`, make sure the aggregate uses `set lacp-mode active`, then check the LAG with `diagnose netlink aggregate name <aggregate>`. If you later disable the MCLAG ICL, you must enable the FortiLink split interface again.

## Firmware troubleshooting

FortiSwitch firmware must be compatible with the FortiOS version (FortiLink Compatibility table); mismatched firmware is one of the documented causes of a down link. Managed switches are upgraded **through the FortiGate**.

### Upload, stage, restart

```text
FGT-HQ # execute switch-controller switch-software upload tftp FSW_124E-v7-build1047-FORTINET.out 10.10.99.25
FGT-HQ # execute switch-controller switch-software list-available
FGT-HQ # execute switch-controller switch-software stage all S124EN-v7.6-build1047-IMG.swtp
FGT-HQ # execute switch-controller get-upgrade-status
FGT-HQ # execute switch-controller switch-action restart delay all
```

- Each model needs its own image. `stage all <image>` stages it on every managed switch of the matching model; `stage switch-id <switch> <image>` and `stage switch-group <group> <image>` narrow it down; `upgrade <switch> <image>` upgrades one switch.
- `https-image-push` (under `config switch-controller global`) is **enabled by default** and speeds up image transfer.
- `restart delay all` restarts all managed switches after a **2-minute delay**; `get-conn-status` shows the **D** flag until they reboot. Switch groups (`config switch-controller switch-group`) let you restart or stage per group.
- GUI: **System > Firmware & Registration > Upgrade all > FortiSwitches**, or select switches in **Managed FortiSwitches > Device > Upgrade**. FortiGuard upgrades every upgradable switch; File Upload uses one image at a time.

### Reading get-upgrade-status

```text
FGT-HQ # execute switch-controller get-upgrade-status
Device    Running-version                                Status      Next-boot
========================================================================================
VDOM : root
S124EN5918000103  S124EN-v7.4.4-build0861,240611 (GA)            (100/0/0)   S124EN-v7.4-build0861      (Staging)
S124EN5918000105  S124EN-v7.4.4-build0861,240611 (GA)            (0/100/100)   S124EN-v7.6-build1047    (Idle)
```

The Status triplet is **download % / erase % / save %**. The first switch has downloaded the whole image (100 %) but hasn't erased space or saved it yet, so staging is still in progress and Next-boot still shows the running build; the second has written it, and its Next-boot shows the new build with `(Idle)`, meaning staging is done and it waits for a restart. During a delayed restart the line reads "Prepping for delayed restart triggered". A switch actively upgrading shows `(Upgrading)`.

If a connectivity problem interrupts an upgrade, a switch can stay at **Upgrading**; `execute switch-controller switch-software cancel` cancels pending or downloading upgrades.

### Automatic provisioning on authorization

| Method | How | Limits |
|--------|-----|--------|
| Uploaded image (FortiOS 7.0.0+) | Per switch: `set firmware-provision enable` + `set firmware-provision-version <major.minor.build>` | FortiGate **with** a hard disk: up to 4 images per switch model; **without** a disk: 1 per model |
| Latest from FortiGuard, once (FortiOS 7.0.4+) | `config switch-controller global` → `set firmware-provision-on-authorization enable` | On authorization the switch's `firmware-provision-latest` becomes `once`; when the switch is `Authorized/Up` the FortiGate downloads the latest supported FortiSwitchOS from FortiGuard and upgrades it, then the setting returns to `disable` |

The two methods can't be combined: setting `firmware-provision-latest once` unsets `firmware-provision` and `firmware-provision-version`. An upgrade already running is paused until the one-time upgrade completes.

FortiOS 7.4.1 and later also include managed switches in **automatic federated upgrades** (`config system fortiguard` → `set auto-firmware-upgrade enable` with a day and hour window), following the compatibility matrix on FortiGuard. `diagnose test application forticldd 16` shows that matrix.

### Upgrading an MCLAG pair

To keep the outage short (Fortinet expects about 20 seconds of impact):

1. Disable MCLAG split-brain protection on both peers if it is enabled.
2. Run `diagnose switch mclag icl` to find which peer has the **lower MAC address**.
3. Stage the image on both switches.
4. Restart the switch with the lower MAC address first.
5. Wait until it is back and its links are up (LACP trunks can take a moment).
6. Restart the other switch.
7. Re-enable split-brain protection.

### Replacing a failed managed switch

Same model only. Deauthorize the failed switch (`set fsw-wan1-admin disable`), factory-reset the replacement if it isn't new, upgrade it **offline** to the failed switch's firmware, run `execute replace-device fortiswitch <failed_sn> <new_sn>` so it inherits the name and configuration, authorize it, then cable it. For an MCLAG member, connect only the ICL first and wait for FortiLink to come up.

## Lab it yourself

On the **FortiGate-VM** trial: list the `execute switch-controller switch-software` keywords, run `get-upgrade-status` (empty) and `get-sync-status all`, and look at `config switch-controller global` for `https-image-push` and `firmware-provision-on-authorization`. Uploads, staging, MCLAG and secure-fabric checks need **physical FortiSwitch units**; FortiGuard-based provisioning also needs FortiGuard, which the trial doesn't have.

## Key takeaways

- `E` flag = config sync error. Check with `get-sync-status`, fix, then `diagnose switch-controller trigger config-sync <switch>`.
- Local CLI changes on a managed switch are lost on restart; configure from the FortiGate.
- `get-physical-conn {standard | dot}` shows the FortiLink graph and authenticated/secured/restricted ports.
- Secure fabric: `relax` failure = restricted ISL without user VLANs; `strict` failure = no ISL.
- MCLAG checks: `switch-info mclag icl | list | peer-consistency-check`; on the switch `diagnose switch mclag ...`.
- Firmware: upload → list-available → stage → get-upgrade-status (download/erase/save %) → restart; `restart delay all` waits 2 minutes and sets the D flag.
- Provisioning on authorization: uploaded image (4 per model with disk, 1 without) **or** latest-from-FortiGuard once, not both.
- MCLAG upgrade: lower-MAC peer first; replacement: same model, offline upgrade, `execute replace-device fortiswitch`.
