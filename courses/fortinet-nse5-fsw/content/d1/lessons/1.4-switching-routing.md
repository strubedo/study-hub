## Ethernet switching and MAC learning

A FortiSwitch is a normal transparent learning bridge: it learns source MACs per VLAN and port, forwards known unicast, and floods unknown unicast, broadcast and (without IGMP snooping) multicast within the VLAN. What you control:

| Control | FortiGate (FortiLink) | FortiSwitchOS | Default |
|---|---|---|---|
| MAC aging | `config switch-controller global` → `set mac-aging-interval` | `config switch global` → `set mac-aging-interval` | **300 s** (10–1,000,000; **0 disables aging**) |
| Learning limit per port | port: `set learning-limit` | `config switch interface` → `set learning-limit` | **0 = no limit** (1–128) |
| Learning limit per VLAN | VLAN interface: `set switch-controller-learning-limit` | `config switch vlan` → `set learning-limit` | 0 = no limit |
| Disable learning on a port | — | `config switch physical-port` → `set l2-learning disable`, `set l2-sa-unknown {drop | forward}` | Learning enabled |
| Sticky (persistent) MAC | port: `set sticky-mac enable` | `config switch interface` → `set sticky-mac enable` | Disabled |
| MAC event logging | `set mac-event-logging enable` (global) | `set log-mac-event enable` (interface) | Disabled |

Points that come up in questions:

- **Static MAC entries do not count** toward a learning limit.
- Changing the learning setting flushes existing dynamic entries.
- With learning-limit violation logging enabled (`log-mac-limit-violations`), only the **first** violating MAC per interface or VLAN is recorded until the log is reset; view with `diagnose switch-controller switch-info mac-limit-violations {all | interface | vlan}`. On FortiSwitchOS 7.0.2+ you can also `set learning-limit-action shutdown` on a physical port.
- Sticky MACs survive link down/up, but are **lost at reboot** unless saved: `execute switch-controller switch-action sticky-mac save {all | interface} <sn> [<port>]`.

> **Real world:** sticky MAC plus a learning limit is the FortiSwitch counterpart of Cisco `switchport port-security maximum` with `mac-address sticky`. The difference: Fortinet saves sticky entries only when you explicitly save them.

## Link aggregation (802.3ad trunks)

FortiSwitch calls a LAG a **trunk** (careful: in Cisco-speak "trunk" means an 802.1Q port). From the FortiGate:

```text
FGT-HQ # config switch-controller managed-switch
FGT-HQ (managed-switch) # edit "S248EPTF18000101"
FGT-HQ (S248EPTF18000101) # config ports
FGT-HQ (ports) # edit "srv-lag1"
FGT-HQ (srv-lag1) # set type trunk
FGT-HQ (srv-lag1) # set mode lacp-active
FGT-HQ (srv-lag1) # set members "port21" "port22"
FGT-HQ (srv-lag1) # end
FGT-HQ (S248EPTF18000101) # end
```

| Setting | Options | Notes |
|---|---|---|
| `mode` | `static`, `lacp-passive`, `lacp-active` | `static` sends no LACPDUs and ignores received ones |
| `aggregator-mode` | `bandwidth` (default), `count` | If members negotiate different speeds, ports of the same speed form an aggregator; only **one** aggregator is used — the one with the most bandwidth, or the most ports |
| `min-bundle` / `max-bundle` | 1–24 | Minimum/maximum active members |
| `lacp-speed` | `slow` (default, every 30 s), `fast` (every second) | |
| `port-selection-criteria` | `src-ip`, `dst-ip`, `src-dst-ip`, `src-mac`, `dst-mac`, `src-dst-mac` | Hashing |
| `mclag` | enable/disable | Trunk with members on both MCLAG peers (lesson 1.3) |

**LACP fallback** (FortiSwitchOS 7.4.0, FortiOS 7.4.4): `set fallback-port <port>` keeps one member up when no LACPDUs arrive, for example a server PXE-booting before its OS runs LACP. Requirements: `lacp-active` mode; fallback starts **90 s** after LACPDUs stop with `lacp-speed slow`, **30 s** with `fast`; not with `min-bundle`/`max-bundle`; not during MCLAG split brain; on an MCLAG, configure it on only **one** peer (otherwise `peer-consistency-check` reports a mismatch).

Check on the switch with `diagnose switch trunk list`; from the FortiGate with `diagnose switch-controller switch-info trunk status <sn> <trunk>`.

## Layer 3 on a standalone FortiSwitch

In **standalone** mode a FortiSwitch routes on its own. Two Layer 3 interface types:

| | Switch virtual interface (SVI) | Routed VLAN interface (RVI) |
|---|---|---|
| What it is | Logical L3 interface for a VLAN (like a Cisco `interface Vlan10`) | A physical port or trunk turned into a routed port (like Cisco `no switchport`) |
| Config | `config system interface` → `set vlanid`, `set interface internal`, `set ip` | `config system interface` → `set type physical`, `set l2-interface <port>`, `set ip` |
| Layer 2 features | Normal switching continues on the VLAN | **Disabled** on the port: no 802.1X, DHCP snooping, DAI, IGMP snooping, STP guards, MCLAG, edge port, QinQ, PVLAN… |
| Internals | VLAN must be allowed on the `internal` (CPU) interface | All RVIs share VLAN **4095**; an RVI goes down when its port/trunk is admin down |

```text
FSW-Core1 # config switch interface
FSW-Core1 (interface) # edit "internal"
FSW-Core1 (internal) # set allowed-vlans 10,20
FSW-Core1 (internal) # end
FSW-Core1 # config system interface
FSW-Core1 (interface) # edit "vlan10"
FSW-Core1 (vlan10) # set ip 10.10.10.2 255.255.255.0
FSW-Core1 (vlan10) # set vlanid 10
FSW-Core1 (vlan10) # set interface "internal"
FSW-Core1 (vlan10) # set allowaccess ping ssh
FSW-Core1 (vlan10) # end
FSW-Core1 # config router static
FSW-Core1 (static) # edit 1
FSW-Core1 (1) # set dst 0.0.0.0 0.0.0.0
FSW-Core1 (1) # set gateway 10.10.10.1
FSW-Core1 (1) # set device "vlan10"
FSW-Core1 (1) # end
```

Static-route rules: a gateway must be in the same subnet as the device; the destination cannot match one of the switch's own interface subnets; up to **eight** ECMP paths (`config system settings` → `set ip-ecmp-mode`, source-IP based by default). On models with hardware L3 forwarding but no ECMP, only one route per destination is programmed in hardware. Fortinet recommends a link monitor or BFD to check static gateways.

**Dynamic routing** (OSPF, RIP, IS-IS, BGP) is available on supported models, but **OSPF requires an advanced features license**, as do several other advanced L3 features. Check routes with `get router info routing-table all`.

## Inter-VLAN routing in FortiLink mode

In FortiLink mode the managed switches are Layer 2 only by default. Each FortiLink VLAN's gateway is the **FortiGate VLAN interface**, so traffic between two VLANs goes up the FortiLink to the FortiGate, is routed there and **must match a firewall policy** (where it can be inspected), then comes back down. That is the security advantage of FortiLink — and the throughput cost on the FortiLink uplink.

**Inter-VLAN routing offload** (FortiOS 7.4.1 + FortiSwitchOS 7.4.1, **advanced features license** needed) lets the FortiGate program the switch closest to it to route *trusted* traffic between selected VLANs without FortiGate inspection:

- On each VLAN interface: `set switch-controller-offload enable` and `set switch-controller-offload-ip <ip>` (clients use the offload IP as their default gateway). On **one** VLAN interface also `set switch-controller-offload-gw enable` — that VLAN's FortiGate address becomes the switch's default route.
- On the managed switch: `set route-offload enable`; with MCLAG also `set route-offload-mclag enable` and `config route-offload` entries with a `router-ip` per VLAN (VRRP).
- The FortiGate then creates an SVI per VLAN on the switch and a default route in **vrf1** toward the gateway VLAN.

> **Exam tip:** offloaded traffic is **not** inspected by the FortiGate. Use it only for flows you trust.

## IGMP snooping

IGMP snooping lets the switch listen to IGMP between hosts and routers and send each group only to ports with listeners (plus mrouter ports).

FortiGate side:

```text
FGT-HQ # config system interface
FGT-HQ (interface) # edit "vlan10-data"
FGT-HQ (vlan10-data) # set switch-controller-igmp-snooping enable
FGT-HQ (vlan10-data) # set switch-controller-igmp-snooping-proxy enable
FGT-HQ (vlan10-data) # end
FGT-HQ # config switch-controller igmp-snooping
FGT-HQ (igmp-snooping) # set aging-time 300
FGT-HQ (igmp-snooping) # set flood-unknown-multicast disable
FGT-HQ (igmp-snooping) # end
```

| Setting | Default | Meaning |
|---|---|---|
| `aging-time` | 300 s (15–3600) | Life of a snooping entry with no reports; must exceed `query-interval` |
| `flood-unknown-multicast` | disabled | Disabled: unregistered multicast goes only to **mrouter ports**; enabled: flooded in the VLAN |
| `query-interval` | 125 s (10–1200) | How often the managed-switch querier sends queries |

The **querier** (version 2 or 3; default 2) is per managed switch: `config switch-controller managed-switch` → `config igmp-snooping` → `set local-override enable` → `config vlans` → `edit <vlan>` → `set querier enable`. The VLAN needs snooping and proxy enabled first. The per-port knobs `igmp-snooping-flood-reports` and `mcast-snooping-flood-traffic` are disabled on automatically formed ISLs and must be enabled on MCLAG ICLs. IGMP snooping cannot be used when NAC is enabled globally (`config switch-controller nac-settings` → `set mode global`).

## Lab it yourself

On the FortiGate-VM trial you can configure `switch-controller global` MAC settings, `switch-controller igmp-snooping`, and the offload attributes on a FortiLink VLAN interface. Inter-VLAN routing through the FortiGate can be modelled on the trial by putting two hosts on two VLAN interfaces and adding one firewall policy (the trial allows three). SVI/RVI and standalone routing need a FortiSwitch.

## Key takeaways

- MAC aging defaults to 300 s (0 disables); learning limits default to 0 (no limit), range 1–128; static MACs do not count.
- Sticky MACs survive link flaps but need an explicit save to survive a reboot.
- LAG modes: static, lacp-passive, lacp-active; `aggregator-mode bandwidth` is the default.
- LACP fallback needs lacp-active and kicks in after 90 s (slow) or 30 s (fast).
- SVI = VLAN interface on `internal`; RVI = routed port (`type physical` + `l2-interface`), VLAN 4095, no L2 features.
- In FortiLink mode, inter-VLAN traffic is routed by the FortiGate and needs a firewall policy; routing offload (licensed) bypasses inspection.
- IGMP snooping is enabled per FortiLink VLAN interface; unregistered multicast goes only to mrouter ports unless `flood-unknown-multicast` is enabled.
