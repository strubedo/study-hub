## QoS on FortiSwitch in one picture

FortiSwitch QoS has three parts, the same three you know from any switch:

1. **Classification** — decide a packet's priority, usually by *trusting* the 802.1p CoS or the DSCP value it arrives with.
2. **Marking** — rewrite CoS or DSCP (done with ACLs on FortiSwitch).
3. **Queuing** — put the packet in one of **eight egress queues** per port and schedule those queues.

What the switch supports: mapping 802.1p and Layer 3 values (DSCP, IP precedence) to an egress queue, eight egress queues per port, and policing the maximum rate of egress traffic. A FortiGate does **not** do switch QoS for its own hardware- or software-switch ports; this is about managed FortiSwitch ports.

## The FortiGate object chain

In FortiLink mode, QoS is built from four objects under `config switch-controller qos`, then attached to a port:

| Object | Purpose |
|---|---|
| `dot1p-map` | CoS 0–7 → queue. **Priorities you do not list map to queue 0** |
| `ip-dscp-map` | DSCP value, DiffServ class (`EF`, `AF41`, `CS3`…) or IP precedence → queue |
| `queue-policy` | Scheduling mode (`strict`, `round-robin`, `weighted`) and per-queue `min-rate`/`max-rate`, `weight`, `drop-policy`, `ecn`; `rate-by kbps` or `percent` |
| `qos-policy` | Ties it together: `trust-dot1p-map`, `trust-ip-dscp-map`, `queue-policy`, `default-cos` |

```text
FGT-HQ # config switch-controller qos qos-policy
FGT-HQ (qos-policy) # edit "campus-qos"
FGT-HQ (campus-qos) # set default-cos 0
FGT-HQ (campus-qos) # set trust-dot1p-map "campus-dot1p"
FGT-HQ (campus-qos) # set queue-policy "campus-egress"
FGT-HQ (campus-qos) # end
FGT-HQ # config switch-controller managed-switch
FGT-HQ (managed-switch) # edit "S248EPTF18000101"
FGT-HQ (S248EPTF18000101) # config ports
FGT-HQ (ports) # edit "port5"
FGT-HQ (port5) # set qos-policy "campus-qos"
FGT-HQ (port5) # end
FGT-HQ (S248EPTF18000101) # end
```

On a standalone FortiSwitch the same ideas live under `config switch qos dot1p-map`, `config switch qos ip-dscp-map` and `config switch qos qos-policy` (which there holds the scheduling and `config cos-queue` directly), with trust maps applied on the port under `config switch interface` (`set trust-dot1p-map`, `set trust-ip-dscp-map`, `set qos-policy`, `set default-cos`).

> **Watch out:** the FS-1xxE and FS-1xxF families support **one** QoS map; if more exist, the first configured map is used. These models also lack some per-queue options (for example `min-rate` and drop policy per queue).

## Which queue does a packet use?

Fortinet recommends trusting **either** 802.1p **or** DSCP on a port, not both. If you do trust both, DSCP wins whenever the packet has a DSCP value. The full decision:

| Packet carries | Port trusts | Queue chosen from |
|---|---|---|
| CoS and DSCP | DSCP and 802.1p | DSCP map |
| CoS and DSCP | 802.1p only | Dot1p map using the packet's CoS |
| CoS only (non-IP) | 802.1p | Dot1p map using the packet's CoS |
| DSCP only (untagged IP) | DSCP | DSCP map |
| DSCP only (untagged IP) | 802.1p only | Dot1p map using the port's **default CoS** |
| Anything | Neither | **Queue 0** |

A packet without a CoS value is treated as CoS 0 unless you set a different `default-cos` (0–7) on the port or policy.

> **Exam tip:** "untagged packet, port trusts only 802.1p" is the classic trick: the switch looks up the port's default CoS in the dot1p map, it does **not** read the DSCP.

## Scheduling the eight queues

| Mode | Behaviour |
|---|---|
| `strict` | Queues served in descending order: **queue 7 highest, queue 0 lowest**. Lowest latency for top classes, but lower queues can starve under congestion |
| `round-robin` | One packet from each backlogged queue in turn: fair share. Default scheduling when no egress policy is set on a FortiSwitch port |
| `weighted` | Weighted round robin; each queue has a weight (documented range 0–63). Higher weight, more bandwidth, nobody starves |

A queue with **weight 0** in a weighted policy is served **strictly**, ahead of all non-zero-weight queues; among several weight-0 queues the higher-numbered one wins. That lets you mix a strict priority queue (voice) with WRR for everything else — the equivalent of a Cisco priority queue plus CBWFQ.

FortiSwitch uses **queue 7** for network control and critical management traffic. Do not oversubscribe it or put data traffic in it.

### Drop policies and rate limits

- `taildrop` (default): when the queue is full, new packets are dropped.
- `weighted-random-early-detection` (WRED): drops start early, increasingly as the buffer fills; with WRED you can enable **ECN** marking instead of only dropping. (Some models offer RED; support varies by model.)
- `max-rate` / `max-rate-percent`: cap a queue's egress rate (rate limiting). `min-rate` / `min-rate-percent`: guarantee a minimum. `rate-by` chooses kbps or percent.
- On a **trunk**, an egress rate is applied to **each member port**; there is no aggregate rate for the whole trunk.

## The predefined voice QoS policy

FortiOS ships a VoIP policy based on common industry practice:

| Traffic | DSCP | CoS | Queue |
|---|---|---|---|
| VoIP data | 46 (EF) | 5 | 1 |
| VoIP control | 24, 26 | 3 | 2 |
| Routing protocol | 48 | 6 | 2 |
| STP BPDU | 56 | 7 | 2 |
| Real-time video | 34 | — | 3 |

Objects: `voice-dot1p`, `voice-dscp`, queue policy `voice-egress` (`schedule weighted`; **queue-1 weight 0**, queue-2 weight 6, queue-3 weight 37, queue-4 weight 12) and the QoS policy `voice-qos` that references all three. Because queue 1 has weight 0, voice media is served strictly ahead of everything else. Apply it to phone ports with `set qos-policy "voice-qos"` or through a dynamic port policy (next lesson).

## Marking with ACLs

FortiSwitchOS remarks CoS (0–7) and DSCP (0–63) with an ingress ACL action:

```text
FSW-Access1 # config switch acl ingress
FSW-Access1 (ingress) # edit 10
FSW-Access1 (10) # config classifier
FSW-Access1 (classifier) # set cos 2
FSW-Access1 (classifier) # end
FSW-Access1 (10) # config action
FSW-Access1 (action) # set remark-cos 4
FSW-Access1 (action) # set remark-dscp 48
FSW-Access1 (action) # set count enable
FSW-Access1 (action) # end
FSW-Access1 (10) # set ingress-interface "port1"
FSW-Access1 (10) # set status active
FSW-Access1 (10) # end
```

Remarking does **not** change queuing on this switch: the egress queue is still chosen from the trust maps and the **original** values. The new marking matters to the next hop. To force a queue for a whole VLAN, use an ACL action `set cos-queue <n>` with a `vlan-id` classifier.

On the egress side, `egress-pri-tagging` in a FortiSwitchOS dot1p map adds priority tagging (VLAN 0 with a valid priority) to untagged egress frames; it is disabled by default.

## Lab it yourself

The whole FortiGate object chain (`dot1p-map`, `ip-dscp-map`, `queue-policy`, `qos-policy`) can be built on a FortiGate-VM trial and inspected with `show`. Look at the predefined `voice-dot1p`, `voice-dscp`, `voice-egress` and `voice-qos` objects and confirm the weights above. Applying a policy to a port and reading `qos-stats` needs a real managed switch.

## Key takeaways

- Eight egress queues per port; strict scheduling serves queue 7 first and queue 0 last.
- Unlisted CoS values in a dot1p map go to queue 0; a port that trusts nothing uses queue 0.
- Trust 802.1p or DSCP, not both; if both, DSCP wins when present.
- Untagged IP on a port trusting only 802.1p uses the port's default CoS in the dot1p map.
- In weighted mode, weight 0 makes a queue strict-priority; `voice-egress` uses this for queue 1.
- Rate limits are per queue (`max-rate`/`min-rate`); on trunks they apply per member port.
- ACL remarking changes CoS/DSCP for the next hop but not this switch's queuing.
