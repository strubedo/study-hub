## From discovered to managed

A FortiSwitch that reaches the FortiGate over FortiLink is first **discovered**; it is not managed until it is **authorized**. Before you cable it, make sure the switch is in its factory-default configuration. If it isn't, log in to the switch console and run `execute factoryreset`. Converting a configured standalone switch to FortiLink mode erases its standalone configuration; Fortinet publishes a `fortilinkify.py` script if you want to turn standalone configurations into FortiGate-compatible switch-controller configuration first.

### Automatic or manual authorization

| Method | How |
|---|---|
| Automatic | FortiLink interface with **Automatically authorize devices** (`set auto-auth-extension-device enable`) |
| Manual, GUI | WiFi & Switch Controller > Managed FortiSwitches, select the switch, **Authorize** |
| Manual, CLI | `config switch-controller managed-switch` → `edit <serial>` → `set fsw-wan1-admin enable` |

`fsw-wan1-admin` has three values in the FortiOS 7.6.1 CLI Reference: `discovered` (the default for a newly seen switch), `enable` (authorized) and `disable`. `fsw-wan1-peer` names the FortiLink interface the switch hangs off.

```text
FGT-HQ # config switch-controller managed-switch
FGT-HQ (managed-switch) # edit S248EPTF18000102
FGT-HQ (S248EPTF18000102) # set fsw-wan1-peer "fortilink"
FGT-HQ (S248EPTF18000102) # set fsw-wan1-admin enable
FGT-HQ (S248EPTF18000102) # end
```

> **Watch out:** The 7.6.1 FortiLink pages disagree about whether the switch reboots when it becomes managed (some authorization pages say it does; the zero-touch page says a 7.2.0+ switch does not need a restart). Don't build your answer on the reboot.

### Pre-authorizing switches

You can create a managed-switch entry before the hardware arrives (GUI **Create New**: serial, model, description, Authorized slider). The switch is authorized as soon as it shows up, and you can assign port VLANs in advance. For a batch of identical switches, a **wildcard serial** works as a template: the first six characters of a real serial prefix, then one or more `*`, then optional characters, with the part after the prefix at most 10 characters long (for example `S248EP****000000`). When a matching switch is discovered, the wildcard entry is replaced by the real serial. Entries are matched top to bottom and each wildcard entry is consumed once.

### Naming and finding switches

Since FortiOS 7.4.0 a managed switch has a user-defined name (up to 16 characters) that is used in switch-controller CLI commands, the GUI and logs, and shows as the **SWITCH-ID** in status output. Rename a switch with `config switch-controller managed-switch` → `rename S248EPTF18000101 to FSW-Core1`; after that you `edit FSW-Core1`, and the serial number is kept in the read-only `sn` field (a pre-configured entry stores it with `set sn`). A switch you haven't renamed uses its serial number as its name, which is why a newly discovered switch is edited by serial. `sn-dns-resolution` (on by default under `config switch-controller global`) lets you ping a switch by serial number plus domain.

## Reading `get-conn-status`

The first command for any FortiLink question:

```text
FGT-HQ # execute switch-controller get-conn-status
Managed-devices in current vdom root:

FortiLink interface : fortilink
SWITCH-ID         VERSION           STATUS             FLAG   ADDRESS          JOIN-TIME                  SERIAL
FSW-Core1         v7.6.1 (1047)     Authorized/Up      2      10.255.1.2       Thu Oct 29 08:14:02 2026   S248EPTF18000101
FSW-Access1       v7.6.1 (1047)     Authorized/Down    -      0.0.0.0          N/A                        S124EN5918000103
S248EPTF18000102  N/A               Discovered/Down    2                       N/A                        S248EPTF18000102

         Flags: C=config sync, U=upgrading, S=staged, D=delayed reboot pending, E=config sync error, 2=L2, 3=L3, V=VXLAN, T=tunnel, X=External
         Managed-Switches: 3 (UP: 1 DOWN: 2 MAX: 32)
```

- **Authorized/Up**: managed and connected.
- **Authorized/Down**: authorized but the FortiGate isn't hearing from it (cabling, ISL, power, reboot in progress).
- **Discovered/Down**: seen but not authorized — a newly discovered switch keeps its serial as its SWITCH-ID until you name it.
- **MAX** is the managed-switch limit of that FortiGate model (for example 8 on a FortiGate 40F or FortiGate-VM01, 24 on FortiGate-VM02, 32 on a FortiGate 100F, 64 on FortiGate-VM04).

The flags you'll use most: **E** (configuration sync error), **U** (upgrading), **S** (new image staged), **D** (delayed reboot pending), **3** (FortiLink over layer 3) and **V** (managed over VXLAN).

## Configuration synchronization

```text
FGT-HQ # execute switch-controller get-sync-status all
FGT-HQ # execute switch-controller get-sync-status switch-id FSW-Core1
FGT-HQ # diagnose switch-controller trigger config-sync S248EPTF18000101
```

`get-sync-status {all | serial <sn> | switch-id <name>}` checks for synchronization errors; `trigger config-sync` pushes the full FortiGate configuration to that switch again. (The 7.6.1 guide shows `trigger config-sync` with a serial number on one page and with the user-defined switch name on its FortiOS 7.4.0 naming page; for a switch that was never renamed the two are the same.)

## Optional FortiLink settings worth knowing

**Admin password.** FortiSwitch admin accounts ship without a password. From the FortiGate you set one through a switch profile:

```text
FGT-HQ # config switch-controller switch-profile
FGT-HQ (switch-profile) # edit "default"
FGT-HQ (default) # set login-passwd-override enable
FGT-HQ (default) # set login-passwd <password>
FGT-HQ (default) # end
```

Assign other profiles per switch with `set switch-profile`. **New in FortiOS 7.6.1:** empty admin passwords are no longer allowed — if a switch has no password when it is authorized, the FortiGate generates one (switches that already have a password keep it). `set login {enable | disable}` in the profile controls console login (enabled by default). To clear a pushed password you must apply a profile with `login-passwd-override enable` and `unset login-passwd`; just disabling the override leaves the old password on the switch.

**What happens on deauthorization.** `config switch-controller global` → `set switch-on-deauth {no-op | factory-reset}`; the CLI default is `no-op` (the switch keeps its configuration and password). `set disable-discovery <switch-id>` (with `append` / `unselect` to edit the list) stops the FortiGate from discovering specific switches, and `execute switch-controller factory-reset <switch-id>` resets a managed switch remotely.

**Local access.** `config switch-controller security-policy local-access` sets `mgmt-allowaccess` and `internal-allowaccess` (https, ping, ssh, snmp, http, telnet, radius-acct) and is applied per switch with `set access-profile`.

**FortiLink over HTTPS** (FortiOS 7.4.2 + FortiSwitchOS 7.4.2): a switch uses either CAPWAP or HTTPS for FortiLink, never both, while the FortiGate can serve both at once.

## Firmware provisioning and upgrades

### Automatic upgrade at authorization

| Option | Since | How |
|---|---|---|
| Uploaded image | FortiOS 7.0.0 | Upload the image to the FortiGate, then per switch `set firmware-provision enable` and `set firmware-provision-version <ver>` (default `disable`). Models with a disk store up to four images per FortiSwitch model, others one. |
| Latest from FortiGuard, once | FortiOS 7.0.4 | `config switch-controller global` → `set firmware-provision-on-authorization enable` (default `disable`). Authorizing a switch sets its `firmware-provision-latest` to `once`; when it is **Authorized/Up**, the FortiGate downloads the latest compatible FortiSwitchOS from FortiGuard, upgrades it, then the setting reverts to `disable`. |

The two can't be combined: setting `firmware-provision-latest once` unsets `firmware-provision` and `firmware-provision-version`.

### Manual upgrades of a running fabric

GUI: **System > Firmware & Registration > Upgrade all > FortiSwitches**, or select switches in Managed FortiSwitches > **Device > Upgrade** (FortiGuard or one uploaded image). CLI, for a stack:

```text
FGT-HQ # execute switch-controller switch-software upload tftp FSW_248E_POE-v7-build1047-FORTINET.out 10.10.99.30
FGT-HQ # execute switch-controller switch-software list-available
FGT-HQ # execute switch-controller switch-software stage all <image-id>
FGT-HQ # execute switch-controller get-upgrade-status
FGT-HQ # execute switch-controller switch-action restart delay all
```

- `stage all <image>` stages the image on every switch of that model; `switch-software upgrade <switch-id> <image-id>` does one switch.
- `get-upgrade-status` shows the download, erase and save percentages. A completed stage shows the new image as next-boot; `get-conn-status` then shows the **S** flag.
- `switch-action restart delay all` reboots them; switches show **D** (delayed reboot pending) and briefly go **Authorized/Down** before returning **Authorized/Up** on the new version. You can restart by switch group instead of all at once.
- `https-image-push` (default `enable`) pushes images over HTTPS instead of CAPWAP, which is faster.

**Federated upgrades** (FortiOS 7.4.1+): with `config system fortiguard` → `set auto-firmware-upgrade enable`, the FortiGate's scheduled automatic upgrade also upgrades its managed FortiSwitch units, following the FortiOS/FortiSwitchOS compatibility matrix from FortiGuard.

> **Exam tip:** Know which flag means what during an upgrade: **U** while upgrading, **S** once an image is staged, **D** while a delayed reboot is pending. **E** is a configuration sync error and has nothing to do with firmware.

## Zero-touch provisioning automation

FortiOS 7.4.4 added switch-controller event-log triggers for automation stitches, so onboarding can be scripted: log IDs **32618–32624** cover a port exported to or returned from a virtual switch, a switch added to or removed from a virtual port pool, a switch added to or removed from a switch group, a switch connected over a layer-2 or layer-3 FortiLink network, a location change and a new switch peer (single peer or MCLAG). A stitch ties a trigger (`config system automation-trigger`, `event-type event-log`, `logid`, optional `config fields` that must all match, `*` wildcards allowed) to actions (`config system automation-action`, `action-type {alert | cli-script | email | webhook}`) — for example, a CLI script that adds every new 108-series switch to the `edge` switch group and sets its port VLANs.

## Lab it yourself

On the FortiGate-VM trial (no switch needed):

1. `config switch-controller global` → `get` and note `switch-on-deauth`, `firmware-provision-on-authorization`, `https-image-push`, `sn-dns-resolution`.
2. Create a pre-authorized entry: `config switch-controller managed-switch` → `edit S248EP****000000` and look at the settable fields (`fsw-wan1-peer`, `fsw-wan1-admin`, `switch-profile`, `access-profile`). Delete it afterwards. Confirm the trial accepts wildcard entries before relying on this step.
3. `config switch-controller switch-profile` → `edit default` → `get`.
4. Build a stitch with `config system automation-trigger` using `logid 32622`; it won't fire without a switch, but the tree is there.

## Key takeaways

- Factory-reset a switch before connecting it; authorization is automatic (`auto-auth-extension-device`) or manual (`fsw-wan1-admin enable`; default `discovered`).
- Pre-authorize by serial or wildcard serial; rename switches (`rename <serial> to <name>`, FortiOS 7.4.0+) so get-conn-status shows a readable SWITCH-ID; the name then becomes the `edit` key.
- get-conn-status statuses: Authorized/Up, Authorized/Down, Discovered/Down; flags C, U, S, D, E, 2, 3, V, T, X; MAX = model limit.
- Sync checks: `get-sync-status`; resync: `diagnose switch-controller trigger config-sync <sn>`.
- FortiOS 7.6.1 never leaves a managed switch with an empty admin password; `switch-on-deauth` defaults to `no-op`.
- Firmware: per-switch `firmware-provision`, or one-time latest from FortiGuard with `firmware-provision-on-authorization`; stage, check `get-upgrade-status`, then `switch-action restart delay`.
