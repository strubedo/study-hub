## Why MCLAG

A **multichassis link aggregation group (MCLAG)** groups two FortiSwitch units so that downstream and upstream devices see them as **one switch**. A device can then build a normal 802.3ad LAG with one link to each peer. If one peer fails, the LAG keeps forwarding on the other — no STP reconvergence and no blocked uplink. Cisco engineers will recognise the idea from vPC or StackWise Virtual; the FortiSwitch implementation uses an **inter-chassis link (ICL)** between the peers instead of a vPC peer-link, and the two peers keep separate control planes and separate managed-switch entries on the FortiGate.

| Term | Meaning |
|---|---|
| ISL | Inter-switch link: a trunk between two FortiSwitch units, formed automatically (auto-ISL) in FortiLink mode |
| ICL | Inter-chassis link: the trunk between the two **MCLAG peers** (`mclag-icl` on the switch trunk) |
| MCLAG peer group | The two switches joined by the ICL |
| MCLAG trunk | A trunk with `mclag enable` whose members are spread across both peers |

## MCLAG requirements

- **Maximum two FortiSwitch units** per MCLAG peer group. They should be the **same hardware model and the same FortiSwitchOS version** — mismatches "might work" but are unsupported.
- Use **at least two links** for the ICL, for redundancy.
- Devices attach to the peer group with an **802.3ad aggregate** that has links to **both** peers.
- **Routing isn't available within an MCLAG.**
- Globally on the switch, `mclag-stp-aware` must be enabled and **STP must be enabled on all ICL trunks** — both are on by default.
- If you combine `min_bundle` / `max_bundle` with MCLAG, the bundle limits apply only to the local aggregate.
- **With IGMP snooping:** `mclag-igmpsnooping-aware` enabled globally (default); `mcast-snooping-flood-traffic` and `igmp-snooping-flood-reports` **disabled** on ISL and FortiLink trunks but **enabled** on ICL trunks (they are enabled by default, so you disable them on the ISL/FortiLink trunks); IGMP proxy enabled.

## From FortiLink split interface to a FortiLink MCLAG

The usual tier-1 design starts as an HA pair (or single FortiGate) with a two-member FortiLink aggregate, one member to each core switch, and the two core switches joined by an ISL. Until the switches are MCLAG peers, they can't share a LAG, so the **split interface** keeps one link active.

The sequence is fixed:

1. **Split interface enabled** (the default) — management stays up through one link.
2. **Form the ICL.** From the FortiGate, assign the LLDP profile `default-auto-mclag-icl` to the ports that form the ICL on **both** core switches (port names can differ between the switches):

```text
FGT-HQ # config switch-controller managed-switch
FGT-HQ (managed-switch) # edit FSW-Core1
FGT-HQ (FSW-Core1) # config ports
FGT-HQ (ports) # edit port51
FGT-HQ (port51) # set lldp-profile default-auto-mclag-icl
FGT-HQ (port51) # next
FGT-HQ (ports) # edit port52
FGT-HQ (port52) # set lldp-profile default-auto-mclag-icl
FGT-HQ (port52) # end
FGT-HQ (FSW-Core1) # end
```

   From FortiOS 7.2.4 the GUI can do it: the Security Rating check **Enable MC-LAG** lists eligible pairs, and in the Managed FortiSwitches topology view you hover over the ISL and choose **Create MC-LAG pair**.
3. **Disable the split interface** on the FortiLink aggregate: `set fortilink-split-interface disable`.
4. **LACP active** on the aggregate if it isn't already: `set lacp-mode active` (`static` on FortiOS 6.2 and earlier).
5. **Verify** the bundle: `diagnose netlink aggregate name fortilink`.

All steps are done **from the FortiGate**; nothing is typed on the core switches. If you later remove the ICL, you must **re-enable** `fortilink-split-interface`.

> **Exam tip:** Order questions love this one: split interface on → ICL (LLDP profile `default-auto-mclag-icl`) → split interface off → LACP active → verify. Disabling the split interface first would put two active links into an aggregate whose far ends are not yet one logical switch.

Verify the MCLAG from the FortiGate:

```text
FGT-HQ # diagnose switch-controller switch-info mclag icl
FGT-HQ # diagnose switch-controller switch-info mclag list
```

On the switch itself the equivalents are `diagnose switch mclag list`, `diagnose switch mclag icl` and `diagnose switch mclag peer-consistency-check`.

## MCLAG trunks to servers and access switches

Once the peers exist, a dual-homed server gets a trunk on each peer with the same name, `mclag enable` and LACP. From the FortiGate, for example for a server on port10 of both core switches:

```text
FGT-HQ # config switch-controller managed-switch
FGT-HQ (managed-switch) # edit FSW-Core1
FGT-HQ (FSW-Core1) # config ports
FGT-HQ (ports) # edit "SRV1-MCLAG"
FGT-HQ (SRV1-MCLAG) # set type trunk
FGT-HQ (SRV1-MCLAG) # set mode lacp-active
FGT-HQ (SRV1-MCLAG) # set mclag enable
FGT-HQ (SRV1-MCLAG) # set members "port10"
FGT-HQ (SRV1-MCLAG) # end
```

(and the same on `FSW-Core2`). Access FortiSwitch units are different: in the documented MCLAG deployments you simply cable an access switch to both peers and wait for discovery and authorization — the inter-switch links form automatically, with no manual trunk configuration.

## Multi-tier MCLAG

A larger campus stacks MCLAG peer groups: a tier-1 core pair, tier-2 distribution pairs and optionally tier-3 pairs, all deployed from the FortiGate switch controller (FortiOS and FortiSwitchOS 6.2.3 GA or later).

- Fortinet recommends **fully meshed** connections between tiers: each peer has at least one link to each of its two upper-tier switches. Full meshing gives link and switch redundancy and lets the Security Rating detect candidate MCLAGs.
- On the upper-tier switches, each downstream peer group needs its own **auto-ISL port group**, and this is one of the few things configured **directly on the FortiSwitch** (or pushed with a custom script from the FortiGate):

```text
FSW-Core1 # config switch auto-isl-port-group
FSW-Core1 (auto-isl-port-group) # edit tier2-closet-1
FSW-Core1 (tier2-closet-1) # set members port1 port2
FSW-Core1 (tier2-closet-1) # end
```

- Build it closet by closet: wire one tier-2 pair, wait for discovery and authorization, assign `default-auto-mclag-icl` to its ICL ports, add the port groups, then connect the next layer.
- Since FortiOS 6.2.0 the FortiGate pair can be **active-passive or active-active** (before 6.2.0 only active-passive).

### HA-mode FortiGates in different sites

FortiOS/FortiSwitchOS 6.4.2+ support an FGCP pair split across two sites where FortiLink and the switch fabric also carry the **HA heartbeat** (heartbeat VLAN interfaces such as `vlanid 998` / `999` set as the native VLAN on the switch ports facing the heartbeat ports). Each site has an MCLAG core pair, and the inter-site links are grouped with `auto-isl-port-group`. Verify with `get system ha status` and `get-conn-status` on the primary.

### Interconnecting FortiLink fabrics

Two fabrics each managed by its own FortiGate can be joined with an **MCLAG trunk between their core pairs**. The interconnect ports look like access ports to each FortiGate and **no ISL forms between fabrics**:

- disable `auto-isl` on the interconnect links and use the `default` LLDP profile there;
- optionally stop each FortiGate discovering the other fabric's switches (`set disable-discovery` under `config switch-controller global`);
- native and allowed VLANs must match on both sides — **VLAN IDs must match, names may differ**.

## Upgrading an MCLAG

An MCLAG core is upgraded like any stack — stage images, check `get-upgrade-status`, then restart. The point of MCLAG is that dual-homed devices ride out the reboot of one peer, so reboot by switch group rather than all at once when you need traffic to keep flowing.

## Lab it yourself

MCLAG needs two physical FortiSwitch units of the same model. On the FortiGate-VM trial you can still rehearse the FortiGate commands: open `config switch-controller lldp-profile` and look at `default-auto-mclag-icl` and `default-auto-isl`, and on a FortiLink aggregate toggle `fortilink-split-interface` and `lacp-mode`. Treat every `diagnose switch mclag …` output as exhibit-reading practice.

## Key takeaways

- MCLAG = two FortiSwitch peers (same model and firmware) joined by an ICL that act as one switch to LAG partners; at least two ICL links; no routing within an MCLAG.
- `mclag-stp-aware` and STP on ICL trunks are required and on by default; IGMP snooping needs the flood settings disabled on ISL/FortiLink trunks and enabled on ICLs.
- Transition order: split interface on → `default-auto-mclag-icl` on ICL ports → split interface off → `lacp-mode active` → `diagnose netlink aggregate name`.
- Removing the ICL later means re-enabling the split interface.
- Multi-tier: fully mesh tiers; `auto-isl-port-group` is configured on the switch itself (or via custom script).
- Interconnected fabrics: MCLAG trunk, no auto-ISL, matching VLAN IDs.
