## The common rule behind every topology

Whatever the cabling, three ideas from the FortiLink Guide hold:

- The FortiGate needs an **active FortiLink interface** to manage the switches below it. Depending on the design you can also have a standby FortiLink.
- The managed switches behave as **one layer-2 stack**, but the FortiGate still manages **each switch individually** (one `managed-switch` entry per serial).
- The active FortiLink carries **both management and data traffic**. Inter-VLAN routing and firewall inspection happen on the FortiGate's FortiLink VLAN interfaces.

## Topologies with a single FortiGate

| Topology | Shape | Notes |
|---|---|---|
| Single switch | One FortiLink (single port or aggregate) to one switch | Simplest; an aggregate to one switch must have the split interface disabled |
| Stack of switches | FortiGate → first switch; other switches hang off it through **auto-ISLs** | Optionally a second FortiLink member to the last switch in a ring, held in standby by the split interface |
| Hardware or software switch interface | Each switch cabled to a separate FortiGate port, all ports in one FortiGate hardware/software switch with FortiLink enabled | **Not recommended in most cases**: traffic between the switches crosses the FortiGate, so it only suits very light traffic. **Do not create loops or rings.** Other 802.1Q-capable devices on that interface get layer-2 connectivity to switch ports |

> **Watch out:** Blocking intra-VLAN traffic isn't supported when the FortiLink interface is a hardware or software switch — another reason the aggregate is the recommended type.

## HA-mode FortiGate topologies

With an FGCP cluster (`FGT-A` / `FGT-B`), both units connect FortiLink to the switch layer and **the FortiLink port(s) and interface type must match on the two FortiGate units** (FGCP synchronizes the configuration, including the FortiLink interface and every switch-controller object). The topologies Fortinet documents:

1. **HA pair managing a single switch** — both FortiGates have FortiLink to the same switch.
2. **HA pair managing a stack** — both FortiGates connect to the stack, usually to different switches.
3. **HA pair managing a two-tier topology** — a distribution FortiSwitch layer connects to the active and passive FortiGates; access switches below it. In production this becomes the MCLAG design in the next lesson.
4. **HA pair using hardware-switch interfaces and STP** — each switch connects to one port of a FortiGate hardware-switch FortiLink interface, and an ISL between the switches gives redundancy. Enable STP on the hardware-switch interface:

```text
FGT-A # config system interface
FGT-A (interface) # edit "fortilink"
FGT-A (fortilink) # set stp enable
FGT-A (fortilink) # end
```

STP and STP forwarding are supported on a FortiLink **hardware switch**; a **software switch** is not supported for this design. Because neighbor detection uses LLDP, `lldp-transmission` must be enabled first. On FortiGate models without aggregate support, give the FortiGate the lowest STP priority (`config system stp` → `set switch-priority`) so it is the CIST root.

## FortiLink over a point-to-point layer-2 network

Sometimes two FortiSwitch units must form an ISL through a device that isn't a FortiSwitch — a wireless bridge or a provider layer-2 circuit. FortiSwitchOS 6.4.0 added a point-to-point mode for this. Enabled on the switch ports at each end, it changes the LLDP destination MAC address to the **broadcast** address so LLDP survives the intermediate layer-2 device:

```text
FSW-Access2 # config switch physical-port
FSW-Access2 (physical-port) # edit port52
FSW-Access2 (port52) # set fortilink-p2p enable
FSW-Access2 (port52) # end
```

`config switch global` → `set fortilink-p2p-tpid <0x0001-0xfffe>` (default **0x8100**, FortiLink mode only) must match on both switches. Several entry-level models (124E/148E/124F/148F series) only support the default TPID.

## FortiLink over a layer-3 network

A **FortiSwitch island** (one switch or several joined by auto-ISLs) can be managed by a FortiGate that is several routed hops away.

- **In-band** management uses the switch's `internal` interface; **out-of-band** uses its `mgmt` port. Different islands can use different methods on the same layer-3 network, but you can't mix both inside one island.
- **Discovery:** with **DHCP option 138** (the CAPWAP access-controller option) handed out by the DHCP server, the switch finds the FortiGate automatically. Otherwise use a different `ac-dhcp-option-code` or static discovery:

```text
FSW-Branch1 # config switch-controller global
FSW-Branch1 (global) # set ac-discovery-type static
FSW-Branch1 (global) # config ac-list
FSW-Branch1 (ac-list) # edit 1
FSW-Branch1 (1) # set ipv4-address 10.255.1.1
FSW-Branch1 (1) # end
FSW-Branch1 (global) # end
```

  plus a static ISL trunk (`config switch trunk` → `set static-isl enable`, `set static-isl-auto-vlan`, `set members`). Start from `execute factoryreset` and follow the steps in order.
- **Requirements:** every switch must be able to **ping the FortiGate**, and an **NTP server** must be reachable (configured or from DHCP).
- **FortiGate side:** since FortiOS 6.4.3 you can make the FortiLink interface the source IP of FortiGate-to-switch traffic: `set switch-controller-source-ip fixed` (the alternative is `outbound`).
- **Status:** the switch shows flag **3** (L3) in `get-conn-status`.

Limitations to remember:

| Limitation | |
|---|---|
| FortiSwitch NAC | Not supported over layer 3 |
| NAT between switch and FortiGate | Not supported |
| VLANs | No layer-2 data path (such as a VLAN) spans the layer-3 network between FortiGate and switch |
| Island membership | All switches in an island must connect to the same FortiGate |
| Mixing | Don't connect a layer-2 FortiGate and a layer-3 FortiGate to the same switch |
| `mgmt` port as uplink | Island limited to one switch |
| Downgrade | Downgrading FortiSwitchOS isn't supported after configuring this mode |

Starting in FortiOS 7.2.1, the old `set fortilink-l3-mode` is **deprecated** — static ISL trunks replace it. From FortiSwitchOS 7.4.1, when DHCP option 138 is used the top switch (the one with the `_FlinkDhcpDisc_` trunk) gets STP priority 24576 instead of 32768.

> **Real world:** For a Cisco engineer the closest analogy is a lightweight AP joining a WLC across a routed WAN: DHCP option (138 here, 43 for Cisco APs) or a static controller address, then a control tunnel. The difference is that the switch island still forwards user traffic locally; only management rides back to the FortiGate.

## Managing FortiSwitch units over VXLAN

Another way to cross a layer-3 network is to build a **VXLAN** overlay between the FortiGate and the switch and enable FortiLink on the FortiGate's VXLAN interface. By default **only management traffic uses the VXLAN tunnel**; user data stays local. Some models can additionally carry user VLANs over VXLAN (using a loopback trunk pair and `tunnel-loopback`) so FortiGate Security Fabric features apply to those devices. From **FortiOS 7.4.0 with FortiSwitchOS 7.4.0**, `get-conn-status` shows flag **V** for a switch controlled over VXLAN:

```text
FGT-HQ # execute switch-controller get-conn-status
Managed-devices in current vdom root:

FortiLink interface : flk-vxlan
SWITCH-ID         VERSION           STATUS             FLAG   ADDRESS          JOIN-TIME                  SERIAL
FSW-Branch2       v7.6.1 (1047)     Authorized/Up      V      10.255.2.2       Thu Oct 29 10:02:51 2026   S124EN5918000105

         Flags: C=config sync, U=upgrading, S=staged, D=delayed reboot pending, E=config sync error, 2=L2, 3=L3, V=VXLAN, T=tunnel, X=External
         Managed-Switches: 1 (UP: 1 DOWN: 0 MAX: 32)
```

FortiLink secure fabric (authenticated and MACsec-encrypted ISLs) is **not** supported over VXLAN.

## Choosing a topology

| Need | Pick |
|---|---|
| Small site, one closet | Single FortiGate + single switch or stack |
| No single point of failure at the firewall | HA pair; FortiLink ports and type identical on both units |
| No single point of failure at the core switch, both FortiLink links forwarding | MCLAG core (split interface → MCLAG) |
| Switches at a remote site across routed WAN | FortiLink over layer 3 (DHCP option 138 or static AC list) or VXLAN |
| Wireless bridge between two closets | FortiLink point-to-point layer 2 (`fortilink-p2p`) |

## Lab it yourself

On the FortiGate-VM trial you can build the FortiGate half of the layer-3 design: a DHCP server on a lab interface with option 138 pointing at the FortiLink IP, `set switch-controller-source-ip fixed` on the FortiLink interface, and a VXLAN interface (`config system vxlan`) on which you enable FortiLink. Check whether each extra interface counts against the 3-interface cap on your trial before planning the lab. Everything on the switch side (`fortilink-p2p`, `ac-list`, static ISL) needs physical FortiSwitch hardware.

## Key takeaways

- Every topology: one active FortiLink (optional standby), switches act as one layer-2 stack, the FortiGate manages each switch separately, FortiLink carries data and management.
- HA: FortiLink ports and interface type must match on both FortiGates.
- Hardware/software switch FortiLink: not recommended, no loops; STP is supported on a hardware-switch FortiLink, not a software switch.
- Layer-2 point-to-point: `fortilink-p2p enable` (broadcast LLDP), matching TPID (default 0x8100).
- Layer 3: DHCP option 138 or static `ac-list` + static ISL; switch must ping the FortiGate and reach NTP; no NAC, no NAT; flag 3; `fortilink-l3-mode` deprecated since 7.2.1.
- VXLAN: management-only by default, flag V from 7.4.0, no secure fabric.
