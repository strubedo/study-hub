## The multi-tenancy problem

A managed service provider, a shared office building or a campus with separate departments often runs one FortiGate split into **VDOMs**, each with its own policies, routing, authentication and VPNs. The FortiSwitch fabric, though, is physically shared. The FortiLink Guide offers three ways to divide it:

| Method | Who administers | Separation |
|---|---|---|
| **Dedicated (exported) ports** | Root VDOM owns the fabric; tenant VDOM administers its exported ports | Per port, with tenant-side administration |
| **VLANs from different VDOMs sharing ports** | Root VDOM admin creates and assigns everything | Per VLAN, no administrative separation |
| **VLAN stacking (QinQ)** | Each customer VDOM gets its own C-VLAN range inside an S-VLAN | Per customer, overlapping VLAN IDs allowed |

The FortiLink interface and the managed switches always live in one VDOM (here the **root** VDOM). Switches are **not visible in non-root VDOMs** unless ports are exported to them.

## Dedicating ports to a tenant VDOM

### Step 1 — the tenant's VLAN (tenant VDOM, CLI only)

In the tenant VDOM (`tenant-a`), create a VLAN interface whose **parent is the root VDOM's FortiLink interface**, and make it the tenant's default virtual-switch VLAN. Fortinet notes this VLAN step is **not supported in the GUI**.

```text
FGT-HQ # config vdom
FGT-HQ (vdom) # edit tenant-a
FGT-HQ (tenant-a) # config system interface
FGT-HQ (interface) # edit "ta-vlan110"
FGT-HQ (ta-vlan110) # set vdom "tenant-a"
FGT-HQ (ta-vlan110) # set interface "fortilink"
FGT-HQ (ta-vlan110) # set vlanid 110
FGT-HQ (ta-vlan110) # set ip 10.10.110.1 255.255.255.0
FGT-HQ (ta-vlan110) # next
FGT-HQ (interface) # end
FGT-HQ (tenant-a) # config switch-controller global
FGT-HQ (global) # set default-virtual-switch-vlan "ta-vlan110"
FGT-HQ (global) # end
```

### Step 2 — export ports (root VDOM)

Either export a port directly:

```text
FGT-HQ (root) # config switch-controller managed-switch
FGT-HQ (managed-switch) # edit S248EPTF18000102
FGT-HQ (S248EPTF18000102) # config ports
FGT-HQ (ports) # edit port10
FGT-HQ (port10) # set export-to "tenant-a"
FGT-HQ (port10) # end
```

or put ports in a **virtual port pool (VPP)** so the tenant can claim them later:

```text
FGT-HQ (root) # config switch-controller virtual-port-pool
FGT-HQ (virtual-port-pool) # edit "tenant-a-pool"
FGT-HQ (tenant-a-pool) # set description "ports tenant A may claim"
FGT-HQ (tenant-a-pool) # end
FGT-HQ (root) # config switch-controller managed-switch
FGT-HQ (managed-switch) # edit S248EPTF18000102
FGT-HQ (S248EPTF18000102) # config ports
FGT-HQ (ports) # edit port11
FGT-HQ (port11) # set export-to-pool "tenant-a-pool"
FGT-HQ (port11) # end
```

### Step 3 — the tenant claims a pooled port (tenant VDOM)

```text
FGT-HQ (tenant-a) # execute switch-controller virtual-port-pool request S248EPTF18000102 port11
```

The switch now appears in `tenant-a` **even though that VDOM has no FortiLink interface**. In the tenant VDOM the managed-switch entry shows `set type virtual` and `set owner-vdom "root"` (the CLI default `type` for a normal entry is `physical`). In the root VDOM, port11 now shows both `set export-to-pool "tenant-a-pool"` and `set export-to "tenant-a"`, and in the tenant VDOM both exported ports use the tenant's default virtual-switch VLAN `ta-vlan110`.

Useful extras:

- `execute switch-controller virtual-port-pool show` lists all pools; `show-by-pool <pool>` lists one.
- Custom export tags live under `config switch-controller switch-interface-tag`.
- Moving a port from one pool to another needs you to leave (or abort) the port's CLI context and re-enter it.
- FortiOS 7.4.4 automation triggers include log IDs for "port exported to / returned from a virtual switch" and "switch added to / removed from a virtual port pool".

### What works on shared (exported) ports

| Supported (since FortiOS 6.2.0) | Not supported |
|---|---|
| Pre-standard PoE detection (if the model supports it) | LLDP |
| Dynamic MAC address learning limits | STP, BPDU guard, root guard |
| QoS egress CoS queue policy | DHCP snooping, IGMP snooping |
| Port security policy (802.1X) | MCLAG, quarantines |

> **Exam tip:** If a tenant asks for DHCP snooping, BPDU guard or quarantine on an exported port, the answer is that shared ports don't support it. The root VDOM keeps the layer-2 control features.

## VLANs from different VDOMs sharing ports

When there is no need for tenant-side administration, the root administrator simply creates VLAN interfaces on the FortiLink interface, assigns each to a VDOM, then assigns those VLANs to switch ports (WiFi & Switch Controller > FortiSwitch Ports > Edit). Every VLAN still appears on the root VDOM's FortiSwitch Ports page, and traffic on each VLAN is processed by the policies of the VDOM that owns the VLAN interface.

## VLAN stacking (QinQ)

QinQ puts a second 802.1Q header on the frame: the outer **S-VLAN** (service provider) carries many inner **C-VLANs** (customer). An MSSP can give each customer its own VDOM and its own full C-VLAN range (1–4094) without collisions.

- Create a VDOM per customer, then the **S-VLAN** and the customers' C-VLANs. **The S-VLAN must be in the same VDOM as the FortiLink interface.**
- Enable QinQ on the customer-facing switch port with `set qnq "<S-VLAN interface>"`. Settings under `config qnq` apply to C-VLANs; `allowed-vlans`, `native-vlan` and `vlan-tpid` apply to the S-VLAN.
- `set allowed-vlans-all enable` pushes every C-VLAN of that VDOM that shares the QinQ parent.
- Up to **four VLAN TPID profiles** including the default **0x8100**, which is used to reach layer 3 and can't be changed or deleted.
- **Not supported with QinQ:** DHCP relay, DHCP snooping, IGMP snooping, IP source guard, private VLANs and STP.

```text
FGT-HQ (root) # config switch-controller managed-switch
FGT-HQ (managed-switch) # edit S248EPTF18000102
FGT-HQ (S248EPTF18000102) # config ports
FGT-HQ (ports) # edit port8
FGT-HQ (port8) # set qnq "svlan-c1"
FGT-HQ (port8) # set vlan "c1.vlan1"
FGT-HQ (port8) # set allowed-vlans "c1.vlan10" "c1.vlan20"
FGT-HQ (port8) # end
```

> **Real world:** On a Cisco switch you'd build this with `switchport mode dot1q-tunnel` and an access VLAN acting as the metro tag. FortiSwitch in FortiLink mode does the equivalent per port with `set qnq`, but the C-VLANs are real FortiGate VLAN interfaces in the customer's VDOM, so the FortiGate can route and inspect each customer's traffic.

## Lab it yourself

The FortiGate-VM permanent trial allows **2 VDOMs**, enough for root plus `tenant-a`:

1. `config system global` → `set vdom-mode multi-vdom`, create `tenant-a`.
2. In root, enable FortiLink on a spare port; in `tenant-a`, try creating a VLAN with `set interface "fortilink"` and set `default-virtual-switch-vlan`.
3. In root, create `config switch-controller virtual-port-pool` → `edit tenant-a-pool`.
4. Run `execute switch-controller virtual-port-pool show`.

Exporting a real port and the `request` command need a managed FortiSwitch. Confirm the VLAN interfaces fit under the trial's 3-interface limit before you start.

## Key takeaways

- Tenant VLAN: created in the tenant VDOM with the root FortiLink interface as parent (CLI only), then `default-virtual-switch-vlan` in the tenant VDOM.
- Root VDOM exports ports with `export-to <vdom>` or `export-to-pool <pool>`; the tenant claims pooled ports with `execute switch-controller virtual-port-pool request <sn> <port>`.
- In the tenant VDOM the switch shows `type virtual` and `owner-vdom "root"`.
- Shared ports support PoE pre-standard detection, MAC learning limits, egress CoS queue policy and port security policy; not LLDP, STP, BPDU/root guard, DHCP/IGMP snooping, MCLAG or quarantines.
- Shared VLANs without delegation: the root admin assigns VDOM-owned VLANs to ports; switches aren't visible in non-root VDOMs.
- QinQ: S-VLAN in the FortiLink interface's VDOM, `set qnq` on the port, max four TPID profiles (0x8100 fixed), no DHCP snooping/relay, IGMP snooping, IP source guard, PVLAN or STP.
