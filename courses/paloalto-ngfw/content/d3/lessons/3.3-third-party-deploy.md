## The idea

You rarely click through a UI for every firewall in a cloud estate. The blueprint expects you to deploy and configure NGFWs through the tools platform teams already use: Kubernetes manifests and Helm, hypervisor and cloud images, Terraform and Ansible. Each tool uses the same two building blocks you saw earlier: a **bootstrap** to bring up the VM and the **API** to configure it.

## Where each target plugs in

| Target | Package / mechanism | Integration |
|--------|---------------------|-------------|
| **Kubernetes** | CN-Series YAML or Helm chart (Helm 3.6+) | PAN-CNI, Panorama Kubernetes plugin, tags from labels |
| **VMware ESXi** | OVA | vSphere, Panorama VM-Series plugin; bootstrap via ISO |
| **KVM** | qcow2 | libvirt/OpenStack; bootstrap via ISO |
| **Hyper-V, Nutanix AHV** | VHD / AHV image | Platform tools; bootstrap via attached media |
| **AWS** | Marketplace AMI | Auto Scaling, Gateway Load Balancer, S3 bootstrap, CloudFormation/Terraform |
| **Azure** | Marketplace image | Load balancers, Azure Files bootstrap, ARM/Terraform |
| **Google Cloud** | Marketplace image | Instance groups, bucket bootstrap, Terraform |

In clouds, Panorama plugins (AWS, Azure, GCP, Kubernetes) read inventory and turn instance and label metadata into **tags** that feed **dynamic address groups**, so security rules follow workloads as they scale without editing addresses.

> **Exam tip:** A question about "policy must follow auto-scaled workloads" is answered by tags and dynamic address groups (via the Panorama cloud plugin or the VM-Series plugin), not by static address objects or scripts that edit rules.

## Terraform with the panos provider

Terraform describes the desired state. For PAN-OS use the **`PaloAltoNetworks/panos`** provider. The 2.x series (current releases are 2.0.x) is a rewrite generated from specifications; it requires Terraform 1.8 or later. Many older tutorials show the 1.x provider with different resource names, so read the version.

Authentication, in priority order: provider block, environment variables, then configuration file:

```text
provider "panos" {
  hostname = "10.0.0.5"
  api_key  = var.panos_api_key      # or username/password
}
```

Environment variables: `PANOS_HOSTNAME`, `PANOS_API_KEY` (or `PANOS_USERNAME`/`PANOS_PASSWORD`). Do not commit credentials; use a variable or a secret manager.

Every 2.x resource has a **`location`** that says where the object lives: a vsys, `shared`, a device group or template on Panorama, and so on. The same provider manages firewalls and Panorama.

```text
resource "panos_device_group" "branch" {
  location = { panorama = {} }
  name     = "Branch-DG"
}

resource "panos_address" "web1" {
  location = { device_group = { name = panos_device_group.branch.name } }
  name         = "web1"
  ip_netmask   = "10.0.1.10/32"
}

resource "panos_security_policy" "branch" {
  location = { device_group = { name = panos_device_group.branch.name } }
  rules = [
    {
      name = "allow-web", source_zones = ["trust"], destination_zones = ["untrust"],
      source_addresses = ["any"], destination_addresses = ["any"],
      applications = ["web-browsing", "ssl"], services = ["application-default"],
      action = "allow"
    }
  ]
}
```

Notes:

* `panos_security_policy` manages the **entire** rulebase for its location: rules not in the list are removed. Use `panos_security_policy_rules` to manage a subset.
* Other resources include `panos_template`, `panos_template_stack`, `panos_template_variable`, `panos_ethernet_interface`, `panos_zone`, `panos_nat_policy` and many more.
* Changes go to the candidate configuration. The 2.x provider adds a **`panos_commit` action** (options include `device_groups`, `templates`, `template_stacks`, partial commits by admin and a `push_configuration` block) and an ephemeral resource `panos_api_key` for short-lived keys. Terraform does not commit after `apply` by itself.
* A Terraform state records what Terraform created. Out-of-band UI changes are detected as drift at the next plan.

The typical pipeline: Terraform builds the cloud network and the VM-Series (using a bootstrap package), then the panos provider configures policy, and a commit finishes it. Separate Terraform providers deploy the platform: `cloudngfwaws` for Cloud NGFW on AWS, `azurerm` resources for Cloud NGFW on Azure, and the usual cloud providers for VMs and networks.

> **Watch out:** Two Terraform states managing the same rulebase fight each other. Keep ownership of an object or rulebase in one place.

## Ansible with the paloaltonetworks.panos collection

Ansible runs ordered tasks from a playbook against hosts. Install the collection from Galaxy:

```text
$ ansible-galaxy collection install paloaltonetworks.panos
$ pip install pan-os-python pan-python xmltodict
```

The modules use the Python libraries, so those must be on the control node. Connection settings go in a `provider` dictionary or as top-level arguments (`ip_address`, `username`, `password` or `api_key`):

```text
- name: Branch objects
  hosts: firewalls
  connection: local
  gather_facts: false
  vars:
    provider:
      ip_address: "{{ inventory_hostname }}"
      api_key: "{{ vault_panos_api_key }}"
  tasks:
    - name: Add web server
      paloaltonetworks.panos.panos_address_object:
        provider: "{{ provider }}"
        name: web1
        value: 10.0.1.10/32
        description: web
    - name: Commit
      paloaltonetworks.panos.panos_commit_firewall:
        provider: "{{ provider }}"
```

Useful modules: `panos_address_object`, `panos_security_rule`, `panos_commit_firewall`, `panos_commit_panorama`, `panos_op` (operational commands), `panos_software`, `panos_check` (wait until the device is ready), `panos_config_element` (generic xpath-based config). Store keys with **Ansible Vault**.

### Terraform or Ansible?

| Need | Better fit |
|------|-----------|
| Create and destroy cloud infrastructure, track state | Terraform |
| Ongoing config drift detection against declared state | Terraform |
| Procedural steps: wait for boot, upgrade software, run op commands, orchestrate commits | Ansible |
| Mix with other network gear in one workflow | Ansible |

Both are valid together: Terraform for the platform, Ansible for orchestration.

## Credential and safety practices

* One API account per automation tool with a least-privilege role, per Domain 2.
* Keep keys out of Git: environment variables, Vault, a secrets manager.
* Restrict the management interface with permitted IPs, and use a trusted certificate so you do not need `-k` or `skip_verify_certificate`.
* Run `plan` or `--check` first; commit in a controlled step.

## Lab it yourself

1. Install Terraform 1.8+ and a PAN-OS lab (VM-Series trial or evaluation).
2. Set `PANOS_HOSTNAME` and `PANOS_API_KEY` and write a `panos_address` in `location = { vsys = { name = "vsys1" } }`.
3. `terraform init && terraform plan`, then `apply`. Check the candidate config in the UI and commit it.
4. In Ansible, install the collection and run a `panos_op` task for `show system info`, then a `panos_commit_firewall` task.

## Key takeaways

* Platforms: Kubernetes (CN-Series, Helm), hypervisors (OVA, qcow2, VHD), CSPs (marketplace images), each with bootstrap.
* Panorama cloud plugins feed tags to dynamic address groups so policy follows auto-scaled workloads.
* The `panos` Terraform provider (2.x) requires Terraform 1.8+ and uses a `location` on every resource.
* `panos_security_policy` owns the whole rulebase; `panos_security_policy_rules` manages a subset.
* Terraform does not commit on its own; the 2.x provider has a commit action.
* The Ansible collection is `paloaltonetworks.panos` and needs `pan-os-python` on the control node.
* Terraform tracks state; Ansible is procedural and good for orchestration steps.
* Keep credentials in Vault or environment variables; use least-privilege API accounts.
