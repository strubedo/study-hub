## Device groups

A **device group** is a set of firewalls (and virtual systems) that share policy and objects. Create them under **Panorama > Device Groups**. A firewall belongs to one device group (per vsys).

### Hierarchy

Device groups form a tree below the implicit **Shared** location. The documentation allows up to four levels below Shared.

```text
Shared
 └── Global-DG
      ├── EMEA-DG
      │    ├── Paris-DG    (PA-Paris1)
      │    └── Berlin-DG   (PA-Berlin1)
      └── AMER-DG
           └── NYC-DG      (PA-NYC1, PA-NYC2)
```

Inheritance rules:

* A device group **inherits** objects and rules from its ancestors, up to Shared. A firewall in `Paris-DG` receives objects from `Paris-DG`, `EMEA-DG`, `Global-DG` and Shared.
* Objects are **not** inherited downward in reverse: a parent never sees a child's objects.
* An object with the **same name** in a descendant overrides the inherited one for that group (an *object override*). Panorama also has a setting that makes ancestor objects take precedence; know that precedence is configurable.
* An object used by a rule must be visible from that rule's location. A Shared rule can only reference Shared objects.

> **Watch out:** Putting a rule in Shared that references an address object defined only in a child group fails validation. Define the object at or above the rule's level.

### Where to place things

| Content | Place it |
|---------|---------|
| Corporate-wide objects and block rules | Shared or the top device group |
| Region-specific objects and rules | Regional device group |
| Site-specific exceptions | Site device group, or local rules on the firewall |

## Pre-rules, post-rules and local rules

Panorama policy is split into **pre-rules**, **post-rules** and **default rules**, in addition to the **local rules** that live on the firewall. Panorama-pushed rules cannot be edited or reordered on the firewall; the local administrator sees them but cannot change them.

Evaluation order, top to bottom (first match wins):

1. **Shared pre-rules**
2. **Parent device group pre-rules**, then **child device group pre-rules** (ancestors first)
3. **Local firewall rules**
4. **Child device group post-rules**, then **parent device group post-rules**
5. **Shared post-rules**
6. **Default rules** (`intrazone-default` allow, `interzone-default` deny), including any default rules defined centrally

```text
Panorama > Policies > Security > Pre Rules   (device group: EMEA-DG)
 1  block-bad-geo      any  any  deny
 2  allow-dns          any  any  allow
Local rulebase on PA-Paris1
 1  paris-legacy-app   trust dmz allow
Panorama > Policies > Security > Post Rules  (device group: EMEA-DG)
 1  cleanup-log        any  any  deny   (log at session end)
```

> **Exam tip:** Use **pre-rules** for rules that must apply first everywhere and that local admins must not override (block lists, mandatory allow rules). Use **post-rules** for cleanup rules that apply last. Use **local rules** when a site needs its own exceptions between them.

### Targeting

Each Panorama rule has a **Target** tab. By default a rule applies to every firewall in the device group (and descendants). Select specific firewalls or tags to apply it only to them, or tick **Target to all but these specified devices** to exclude firewalls.

### Rule visibility on the firewall

Pushed rules show on the firewall in a separate, read-only colour. **Policy Rule Hit Count** works on pushed rules; on Panorama, view rule usage across device groups. If a firewall is removed from the group (or an administrator uses **Disable Panorama Policy and Objects** under **Device > Setup > Management > Panorama Settings** on the firewall), the rules are removed from its running config.

## Commit and push

Panorama keeps its own candidate and running configuration. Pushing configuration to firewalls is a second step.

| Action | Where | What it does |
|--------|-------|--------------|
| **Commit to Panorama** | Commit > Commit to Panorama | Applies the candidate configuration on Panorama itself. Firewalls do not change |
| **Push to Devices** | Commit > Push to Devices | Sends the **running** Panorama config for the selected device groups, templates, collector groups, etc. to the firewalls, which commit |
| **Commit and Push** | Commit > Commit and Push | Does both in one operation |

Because Push uses Panorama's *running* config, uncommitted changes are never pushed.

Push scope options (the **Edit Selections** dialog):

| Option | Effect |
|--------|--------|
| **Device Groups** / **Templates** / **Collector Groups** | Which parts and which firewalls to push |
| **Merge with Candidate Config** | Commits the firewall's own pending (uncommitted) local changes together with the pushed configuration; clear it to keep them out |
| **Include Device and Network Templates** | Pushes template stacks together with the device group |
| **Force Template Values** | Overwrites local overrides with the template's values |
| **Validate Device Group Push** | Runs a validation without committing |

Each firewall in the push completes its own commit; the job list on Panorama (**Tasks**) shows per-device progress. A push can succeed on some firewalls and fail on others.

```text
admin@Panorama-HQ> show jobs all
```

The command lists commit and push jobs with their status (ACT, FIN) and result (OK, FAIL, PEND); the Tasks window in the web UI shows the same per device.

### Troubleshooting a failed push

| Symptom | Likely cause |
|---------|-------------|
| Device shows "Out of Sync" | Not pushed since the last Panorama commit; push again |
| Validation failure on one firewall | A template value is missing, an object is out of scope for the device group, or a feature is not supported on that platform or PAN-OS version |
| Firewall disconnected | Cannot reach Panorama on TCP 3978; check routing, service route and certificate |
| Local setting reverts | Force Template Values was used, or the setting is controlled by the template |
| Push is rejected for a firewall running an older PAN-OS | Panorama must run the same or a newer PAN-OS release than the firewalls it manages |

> **Real world:** After a failed push to a few devices, fix the cause and push only the failed devices. Re-pushing to everyone is slower and risks unrelated changes.

### Configuration backup and rollback

Panorama stores config versions (**Panorama > Setup > Operations > Load configuration version**). A **Commit to Panorama** adds a version; pushing creates a firewall commit with the Panorama job id in its description. To roll back, load the previous Panorama version, commit and push.

## Lab it yourself

1. Create `Global-DG` and a child `Lab-DG`, with your firewall in `Lab-DG`.
2. Add an address object `srv1` to `Global-DG` and another named `srv1` to `Lab-DG` with a different IP; reference it from a rule in `Lab-DG` and push. Observe which IP the firewall uses with `show config pushed-shared-policy`.
3. Create a Shared pre-rule that denies a test destination, a local rule on the firewall that allows it, and confirm that the pre-rule wins with `test security-policy-match`.
4. Make a change, **Commit to Panorama** only, then check Managed Devices for "Out of Sync" before pushing.

## Key takeaways

* Device groups hold policy and objects in a tree below Shared; children inherit from ancestors.
* A same-named object in a child group overrides the inherited object (precedence is configurable).
* Order: shared pre, parent pre, child pre, local, child post, parent post, shared post, default rules.
* Pre-rules cannot be overridden by local administrators; post-rules apply after local rules.
* Rules can be targeted to specific firewalls or tags, or exclude firewalls.
* Commit to Panorama does not change firewalls; Push to Devices sends Panorama's running config.
* Push options include Merge with Candidate Config, Force Template Values and Validate Device Group Push.
* Panorama must be at the same or a newer PAN-OS release than managed firewalls.
