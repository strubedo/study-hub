## CN-Series: the firewall for Kubernetes

CN-Series is the containerised NGFW. It inspects traffic between pods (east-west) and to and from the cluster (north-south), using Kubernetes constructs instead of VMs.

### Components

Per Palo Alto's documentation the management plane and dataplane are split into separate pods:

| Component | Kubernetes object | Role |
|-----------|-------------------|------|
| **CN-MGMT** | StatefulSet (persistent volume), exposed as a Kubernetes service | Management plane. A pair of CN-MGMT pods can manage up to 30 CN-NGFW pods in a cluster |
| **CN-NGFW** | DaemonSet, or deployed as a Kubernetes service | Dataplane that inspects traffic. In DaemonSet mode one pod per node secures up to 30 application pods on that node |
| **PAN-CNI** | DaemonSet | CNI plugin inserted into the CNI chain; reads pod annotations, allocates interfaces and redirects traffic to the CN-NGFW |
| **Panorama** | Outside the cluster | Required for licence and configuration management of CN-Series |
| **Kubernetes plugin on Panorama** | Panorama plugin | Connects to clusters with service-account credentials, retrieves labels and creates tags and service objects for dynamic address groups; manages licence token allocation |

Choose the deployment mode by node size and latency:

| Mode | Fits |
|------|------|
| **DaemonSet** | Larger nodes, low latency, high firewall capacity |
| **Kubernetes service** | Smaller nodes, more dynamic firewalling; app traffic is redirected to an available CN-NGFW on security nodes |

Workflow:

1. Create service accounts for cluster authentication and add the cluster to the Panorama Kubernetes plugin.
2. Create a device group and template stack on Panorama and get a **VM auth key** (the CN-Series registration key; it is needed for the lifetime of the deployment).
3. Push the images to your registry, edit the YAML manifests (or use **Helm 3.6+**) with the Panorama IP, template stack, device group and auth key, and apply them.
4. Annotate namespaces or pods so PAN-CNI redirects their traffic. Untagged pods are not inspected.
5. Write policy on Panorama using the tags the plugin creates (dynamic address groups).

> **Watch out:** CN-Series is Panorama-only. There is no standalone CN-Series web UI. The images and YAML versions must match the PAN-OS release.

## Cloud NGFW

**Cloud NGFW** is a managed NGFW service. Palo Alto Networks runs the infrastructure and PAN-OS; you set policy and attach it to your cloud network. There is no SSH or CLI to the firewall.

| | Cloud NGFW for AWS | Cloud NGFW for Azure |
|---|--------------------|----------------------|
| Offered as | AWS Marketplace pay-as-you-go service with its own console and API | Azure native ISV service (Azure portal and ARM/Terraform resources) |
| Traffic steering | Firewall endpoints in your VPC subnets, using AWS Gateway Load Balancer | Deployed into a virtual network or virtual WAN hub |
| Policy container | **Rulestack** (local), or a global rulestack with AWS Firewall Manager, or Panorama/Strata Cloud Manager | Local rulestack, or Panorama |
| Infrastructure as code | `cloudngfwaws` Terraform provider | `azurerm_palo_alto_next_generation_firewall_*` resources |

Key ideas:

* A **rulestack** holds rules, security profiles and the associated settings in one portable object, rather than a full PAN-OS configuration.
* Because you do not manage the OS, upgrades and scaling are the service's job. You pick a region and size for the endpoints.
* Logs go to destinations you configure in the cloud (for Cloud NGFW for AWS: Amazon CloudWatch, S3 or Kinesis, or Strata Logging Service, from which logs can also be viewed in Panorama).

> **Exam tip:** The deciding words are "managed service", "no PAN-OS to upgrade" and "native cloud billing". VM-Series is chosen when you need full PAN-OS control (GlobalProtect, VPN, custom routing) in the cloud.

## AI Runtime Security (now Prisma AIRS)

The exam datasheet names **AI Runtime Security**. In Palo Alto's current documentation the umbrella product is **Prisma AIRS**, an AI security platform with capabilities for AI Runtime Security, AI Gateway, AI Agent Identity, AI Supply Chain Security, AI Red Teaming and others. AI Runtime Security is the runtime enforcement capability, and the docs describe two forms:

| Form | How it works | Where you look |
|------|--------------|----------------|
| **Network Intercept** | A PAN-OS firewall (VM-Series) inspects AI traffic. You attach an **AI security profile** to a **Security policy rule**, optionally using **model groups** for customised protection. It protects VM workloads and Kubernetes clusters in AWS, Azure and GCP | Deployment profile in the customer support portal, Strata Cloud Manager or Panorama |
| **API Intercept** | An application calls a scanning API with an API key and an AI security profile before and after calling the model | Prisma AIRS API, Python SDK |

It aims to detect threats such as prompt injection, data exposure and unsafe agent behaviour in AI traffic.

Network Intercept deployment follows the usual VM-Series pattern:

1. Create a **deployment profile** for AI Runtime Security in the customer support portal (this is the licence).
2. Deploy the VM-Series firewall from Strata Cloud Manager (it can generate Terraform for you) or, for Panorama-managed firewalls, use the Panorama workflow.
3. Create an AI security profile and a security rule that references it.
4. Use **traffic objects** or zones to select AI traffic; harvest IP tags from Kubernetes clusters to enforce policy on pods.

> **Real world:** If a question uses the older name AI Runtime Security, treat it as the same capability. The datasheet's wording is the stable part; the product marketing has moved to Prisma AIRS.

## Choosing an option

| Requirement | Pick |
|-------------|------|
| Branch or campus perimeter, highest throughput | PA-Series |
| Same PAN-OS in a private cloud or public cloud, full feature set | VM-Series |
| Microservices, pod-level segmentation | CN-Series |
| Cloud-native, no firewall operations | Cloud NGFW |
| Inspect traffic to and from AI apps and models | AI Runtime Security (Prisma AIRS) |

## Lab it yourself

You can practise the CN-Series workflow without licences by reading the manifests:

1. Download a lightweight cluster tool such as kind or minikube.
2. In the CN-Series YAML download, list the objects: `kubectl apply --dry-run=client -f pan-cn-mgmt.yaml`.
3. Identify which objects are StatefulSets and DaemonSets and match them to the table above.
4. For Cloud NGFW, use the Terraform provider docs to write (not apply) a rulestack with one rule.

## Key takeaways

* CN-Series: CN-MGMT (StatefulSet), CN-NGFW (DaemonSet or service) and PAN-CNI; Panorama and its Kubernetes plugin are required.
* One CN-NGFW DaemonSet pod secures up to 30 application pods on its node; a pair of CN-MGMT pods manages up to 30 CN-NGFW pods.
* Cloud NGFW is a managed service on AWS and Azure; you manage policy through rulestacks, not PAN-OS.
* Cloud NGFW for AWS steers traffic with Gateway Load Balancer endpoints.
* Terraform: `cloudngfwaws` for AWS and `azurerm` resources for Azure.
* AI Runtime Security is part of Prisma AIRS; Network Intercept uses a firewall with an AI security profile, API Intercept uses an API scan.
* VM-Series and Cloud NGFW can both run in the cloud; choose by how much control you need.
