## What bootstrapping does

Bootstrapping lets a new VM-Series firewall configure itself on first boot: management address, licences, content, PAN-OS version and either a full configuration or a Panorama registration. No one logs in. It is the standard way to launch firewalls from an auto-scaling group, a Terraform run or a template.

Two inputs drive it:

* a **bootstrap package**: a fixed folder structure in a disk image or cloud storage
* optional **user data** (cloud) that carries the same parameters as `init-cfg.txt` or points to the storage

## The bootstrap package

Create these top-level folders:

```text
/config
/content
/software
/license
/plugins        (optional)
```

The documentation says `/config`, `/license`, `/software` and `/content` must exist but may be empty; `/plugins` is optional and only needed when you upgrade the VM-Series plugin independent of PAN-OS. **Do not add any other file or folder; extra items cause the bootstrap to fail.**

| Folder | Contents |
|--------|----------|
| `/config` | `init-cfg.txt` (management settings, Panorama registration) and optionally `bootstrap.xml` (a full configuration) |
| `/license` | An `authcodes` text file (no extension) or `.key` licence files |
| `/content` | Content packages (App/Threat, antivirus, WildFire) at the version the PAN-OS release requires |
| `/software` | A PAN-OS image to upgrade to during bootstrap |
| `/plugins` | One VM-Series plugin binary only |

Use an **auth code bundle** rather than several single auth codes. With individual codes in the `authcodes` file, the firewall retrieves only the first one.

> **Exam tip:** If the package must also carry the PAN-OS version, the content must satisfy that release's minimum content version, otherwise the firewall can lose features. Content and software folders are optional in practice (they can be empty), but the folders must exist.

## init-cfg.txt

`init-cfg.txt` is a plain text file of `key=value` lines. A typical Panorama-registered DHCP-managed firewall:

```text
type=dhcp-client
hostname=PA-Branch1
panorama-server=203.0.113.50
panorama-server-2=203.0.113.51
tplname=Branch-Stack
dgname=Branch-DG
vm-auth-key=755036225328715
dns-primary=198.51.100.53
dhcp-accept-server-hostname=yes
dhcp-accept-server-domain=yes
```

| Key | Purpose |
|-----|---------|
| `type` | `dhcp-client` or `static` for the management interface |
| `ip-address`, `default-gateway`, `netmask` | Static management settings (with `type=static`) |
| `hostname` | Firewall hostname |
| `panorama-server`, `panorama-server-2` | Panorama IPs or FQDNs |
| `tplname` | **Template stack** the firewall joins |
| `dgname` | **Device group** the firewall joins |
| `cgname` | Collector group (when using a dedicated Log Collector) |
| `vm-auth-key` | Authenticates the VM to Panorama |
| `dns-primary`, `dns-secondary` | Resolvers |
| `op-command-modes` | e.g. `mgmt-interface-swap` |

`tplname` names a template stack (or template), not an arbitrary label. Create the stack and the device group on Panorama **before** you boot the firewall, otherwise registration succeeds without the intended configuration.

### The VM auth key

Panorama issues a time-limited key that lets a new VM register:

```text
admin@Panorama-HQ> request bootstrap vm-auth-key generate lifetime 24
VM auth key 755036225328715 generated. Expires at: 2026/11/02 09:15:41
admin@Panorama-HQ> request bootstrap vm-auth-key show
```

The key must be valid when the firewall first connects (and, per the CN-Series documentation, is needed for the deployment's lifetime in that platform). Generate it with a lifetime that covers your rollout and rotate it.

### Where Panorama gets the licence

In the standard flow the firewall pulls its licence directly from the licensing service using the auth code, over its management interface. Panorama provides configuration (template stack and device group), not the base VM-Series licence. This is why DNS and outbound access matter in the bootstrap network.

## Bootstrap sources by platform

| Platform | Source of the package |
|----------|-----------------------|
| ESXi, KVM, Hyper-V | A virtual ISO/CD-ROM (build with `genisoimage` or similar) or a virtual disk attached at first boot |
| AWS | An S3 bucket named in user data: `vmseries-bootstrap-aws-s3bucket=<bucket>`; the instance needs an IAM role that reads it |
| Azure | An Azure Files share, referenced in custom data with `storage-account=`, `access-key=`, `file-share=` and `share-directory=` |
| Google Cloud | A bucket named in instance metadata: `vmseries-bootstrap-gce-storagebucket=<bucket>` |

You can also supply the `init-cfg.txt` parameters directly in the user data/metadata (for example `type=dhcp-client`, `panorama-server=`, `tplname=`, `dgname=`, `vm-auth-key=`) and skip the storage, when you only need Panorama registration and not a package. The firewall then still needs an auth code if it is not PAYG.

Folders inside a bucket: from VM-Series plugin 2.0.2, one bucket can hold several packages in subfolders (typically one per device group); point the user data at the full path.

## Verify and troubleshoot

```text
admin@PA-Branch1> show system bootstrap status
```

The command lists each stage of the bootstrap process (media detection and sanity check, config parsing, licensing, content) with a success or failure status. The exact stage names and layout vary by release, so read the output for the stage that failed. A completed bootstrap also logs a system message (`BOOTSTRAP : COMPLETE : Firewall Successfully Bootstrapped`), and a failure logs `BOOTSTRAP : FAIL`.

Common failures:

| Symptom | Likely cause |
|---------|-------------|
| Bootstrap does not start | The first-boot media or bucket was not attached, or the IAM role/storage key is wrong |
| Media sanity check fails | An extra file or folder in the package, or a missing top-level folder |
| Licensing fails | No outbound DNS/HTTPS from management; used a single auth code that was already consumed; wrong bundle |
| Firewall boots but is not in Panorama | Wrong `vm-auth-key` (expired), wrong Panorama IP, or Panorama unreachable on TCP 3978 |
| Registered but no policy | `tplname` or `dgname` does not match an existing stack/device group |

Panorama management traffic uses **TCP 3978**; the firewall initiates the connection to Panorama. Allow it from the firewall's management network.

> **Watch out:** Do not expect a bootstrapped firewall to receive its policy immediately after registration. After a successful connection, Panorama still needs a **Push to Devices** for the template stack and device group to land (unless a push is already scheduled). Many "empty firewall" tickets are just an unpushed commit.

## Lab it yourself

On a KVM or ESXi lab host without licensing:

1. Create a folder tree with the five names above and an `init-cfg.txt` containing `type=dhcp-client` and `hostname=PA-lab`.
2. Build an ISO: `genisoimage -o bootstrap.iso -r bootstrap/`.
3. Attach the ISO as a CD-ROM to a new VM-Series and power on.
4. When the CLI is available, run `show system bootstrap status` and `show system info | match hostname`.
5. Break it on purpose by adding a stray `notes.txt` at the top level and note the media sanity failure.

## Key takeaways

* A bootstrap package has `/config`, `/license`, `/software`, `/content` (must exist, can be empty) and optional `/plugins`.
* No additional files or folders are allowed in the package.
* `init-cfg.txt` carries management settings, `panorama-server`, `tplname`, `dgname` and `vm-auth-key`.
* Generate the key on Panorama with `request bootstrap vm-auth-key generate lifetime <hours>`.
* AWS uses an S3 bucket, Azure an Azure Files share, GCP a bucket and on-prem a virtual ISO.
* The firewall fetches licences itself from the auth code, so management needs internet access.
* Auth code bundles are retrieved together; individual codes retrieve only the first.
* `show system bootstrap status` shows progress; Panorama still needs a push for policy.
