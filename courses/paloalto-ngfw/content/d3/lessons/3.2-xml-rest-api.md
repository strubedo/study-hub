## Two APIs, one configuration

PAN-OS and Panorama expose two management APIs over HTTPS:

| | XML API | REST API |
|---|---------|----------|
| Entry point | `https://<host>/api/` | `https://<host>/restapi/<version>/` |
| Format | XML (xpath for config) | JSON (also XML) |
| Operations | Config, operational commands, commit, logs, reports, export/import, User-ID, keygen | Create, read, update, delete, move and rename for objects, policies, network and device settings |
| Commit | Yes (`type=commit`) | **No.** Changes land in the candidate config; commit through the XML API |

Both write to the **candidate configuration**. Nothing takes effect until a commit. Both require an administrator whose **Admin Role profile** enables the matching API (the XML API and REST API sections are separate switches, see Domain 2).

## API keys

Every call needs a key (or credentials). Generate it with `type=keygen`:

```text
$ curl -k -X POST 'https://PA-HQ/api/?type=keygen' -d 'user=apiadmin&password=S3cret!'
<response status="success"><result><key>LUFRPT14MW5xOEo1R09KVlBZNnpnemh0VHRBOWl6TGM9bW9iZXFHQ1hrR2I=</key></result></response>
```

Use `POST` so the password does not appear in URLs and logs. Then send the key as a header or a parameter:

```text
$ curl -k -H 'X-PAN-KEY: LUFRPT14...' 'https://PA-HQ/api/?type=op&cmd=<show><system><info></info></system></show>'
```

Key facts:

* A key belongs to one administrator. It carries that administrator's role. Use a dedicated API account with the narrowest role (for example, no CLI, only the XML sections it needs).
* If the administrator's password changes, the key stops working (this is also how you revoke an administrator's keys). Generate a new one. An XML API error code **403** means an authentication or authorization error, such as an invalid key or insufficient admin rights.
* **Device > Setup > Management > Authentication Settings** has an **API Key Lifetime** (minutes, 1 to 525600; the default 0 means the keys never expire). Short lifetimes limit damage from a leaked key.
* `-k` skips certificate validation. In production, install a trusted certificate on the management interface and omit it.

> **Watch out:** A GET keygen puts the password in the URL, which web and proxy logs retain. The exam's "secure" answer is POST, a dedicated account and an expiring key.

## XML API request types

Every XML API call is `https://<host>/api/?type=<type>&...`.

| `type=` | Purpose | Notes |
|---------|---------|-------|
| `keygen` | Return an API key | |
| `config` | Read or modify configuration | `action=get/show/set/edit/delete/rename/clone/move/override` |
| `op` | Run an operational command | `cmd=<show><system><info/></system></show>` |
| `commit` | Commit the candidate configuration | Returns a job id |
| `log` | Query logs | Asynchronous: returns a job id, then fetch results |
| `report` | Run reports | |
| `export` / `import` | Export or import files | Config, certificates, tech support |
| `user-id` | Send User-ID mappings | `<uid-message>` payload |
| `version` | Return the PAN-OS version | |

### config actions

* `get` returns the **candidate** configuration; `show` returns the **running** (active) configuration.
* `set` **adds** an element as a child of the xpath. `edit` **replaces** the node at the xpath. `delete` removes it.
* `rename` (`newname=`), `clone`, `move` (`where=` and `dst=`) manage entries; `override` is for template overrides.

The xpath names the node. For a firewall's `vsys1`:

```text
/config/devices/entry[@name='localhost.localdomain']/vsys/entry[@name='vsys1']/address
```

Create an address object:

```text
$ curl -k -H 'X-PAN-KEY: LUFRPT14...' -G 'https://PA-HQ/api/' \
  --data-urlencode 'type=config' --data-urlencode 'action=set' \
  --data-urlencode "xpath=/config/devices/entry[@name='localhost.localdomain']/vsys/entry[@name='vsys1']/address" \
  --data-urlencode 'element=<entry name="web1"><ip-netmask>10.0.1.10/32</ip-netmask></entry>'
<response status="success" code="20"><msg>command succeeded</msg></response>
```

On Panorama the same object under a device group lives at `/config/devices/entry[@name='localhost.localdomain']/device-group/entry[@name='Branch-DG']/address`, and shared objects under `/config/shared/address`.

> **Exam tip:** `set` merges into the node you name, so the xpath is the **parent** (`.../address`) and the element carries the entry. For `edit`, the xpath points at the entry itself (`.../address/entry[@name='web1']`) and the element replaces it.

### Operational commands

The `cmd` is the CLI command written as nested XML. To discover it, turn on `debug cli on` and run the CLI command; PAN-OS prints the XML:

```text
admin@PA-HQ> debug cli on
admin@PA-HQ> show system info
<request cmd="op" cookie="..."><operations><show><system><info></info></system></show></operations></request>
```

The web UI also has an API browser at `https://<host>/api`, and the REST API reference at `https://<host>/restapi-doc/`.

## Commit through the API

```text
$ curl -k -H 'X-PAN-KEY: LUFRPT14...' -G 'https://PA-HQ/api/' \
  --data-urlencode 'type=commit' --data-urlencode 'cmd=<commit><description>api change 1042</description></commit>'
<response status="success" code="19"><result><msg><line>Commit job enqueued with jobid 17</line></msg><job>17</job></result></response>
```

A commit is a **job**. Poll it:

```text
$ curl -k -H 'X-PAN-KEY: ...' -G 'https://PA-HQ/api/' \
  --data-urlencode 'type=op' --data-urlencode 'cmd=<show><jobs><id>17</id></jobs></show>'
```

The result has `<status>FIN</status>` and `<result>OK</result>` or `FAIL`. Look at `result`, not just status, because a finished job can have failed. A partial commit limits the scope: `<commit><partial><admin><member>apiadmin</member></admin></partial></commit>`.

On Panorama, committing to Panorama and pushing to devices are separate:

```text
type=commit&cmd=<commit></commit>
type=commit&action=all&cmd=<commit-all><shared-policy><device-group><entry name="Branch-DG"/></device-group></shared-policy></commit-all>
```

The `commit-all` call pushes the device group policy (`<shared-policy>`; add `<validate-only>` to only validate). Template and template-stack pushes use their own `commit-all` elements; use the API browser to find them. Through the XML API, a push to a parent device group goes only to firewalls directly in that device group, not to firewalls in its child device groups (the web interface handles children). The Panorama lesson covers commit versus push.

## REST API

URL pattern: `https://<host>/restapi/v11.2/<Category>/<Resource>?location=<location>&...`. Categories are `Objects`, `Policies`, `Network` and `Device`. Use the version matching your release (for example `v11.2`; `v12.1` for 12.1).

| Method | Meaning | Example |
|--------|---------|---------|
| GET | List or read | `GET .../Objects/Addresses?location=vsys&vsys=vsys1&name=web1` |
| POST | Create (the name is a query parameter) | `POST .../Objects/Addresses?location=vsys&vsys=vsys1&name=web2` |
| PUT | Replace | `PUT .../Objects/Addresses?location=vsys&vsys=vsys1&name=web2` |
| DELETE | Delete | `DELETE .../Objects/Addresses?location=vsys&vsys=vsys1&name=web2` |

Create an object:

```text
$ curl -k -X POST -H 'X-PAN-KEY: LUFRPT14...' -H 'Content-Type: application/json' \
  -d '{"entry":{"@name":"web2","ip-netmask":"10.0.1.11/32","description":"created by API"}}' \
  'https://PA-HQ/restapi/v11.2/Objects/Addresses?location=vsys&vsys=vsys1&name=web2'
{"@status":"success","@code":"20","message":"command succeeded"}
```

Locations: `vsys` (with `vsys=vsys1`), `shared`, and on Panorama `device-group` (with `device-group=Branch-DG`) and `panorama-pushed`. Firewall security rules live under `Policies/SecurityRules`; Panorama exposes pre and post rules as separate resources (`Policies/SecurityPreRules`, `Policies/SecurityPostRules`). Rules are ordered. Move one with `POST .../Policies/SecurityRules:move?location=...&name=<rule>&where=top|bottom|before|after` (add `&dst=<rule>` for before and after). Renaming uses `:rename` with `&newname=`.

> **Watch out:** A successful REST call changed the candidate configuration only. Commit through `type=commit`. Many "my API change did nothing" cases are a missing commit.

## Choosing and using

* Use the **XML API** for operational commands, commits, logs, reports, User-ID and anything the REST API does not model.
* Use the **REST API** for straightforward object and policy CRUD with JSON.
* SDKs and tools (the Python library pan-os-python, the Terraform provider and Ansible collection) call these APIs. The next lesson covers them.

## Lab it yourself

1. Create an administrator `apiadmin` with an Admin Role that enables the XML API and REST API tabs only.
2. Generate a key with the POST curl above.
3. Run `type=op` to read `show system info`, then `type=config&action=show` for your `vsys1` address objects.
4. Create an address object via REST, `GET` it back, then confirm it appears under **Objects > Addresses** in the candidate config with a pending commit.
5. Commit via `type=commit` and poll the job id until `FIN` and `OK`.

## Key takeaways

* The XML API is `/api/`, the REST API is `/restapi/<version>/`; both change only the candidate config.
* REST has no commit; use `type=commit` and poll the job id.
* Generate keys with `type=keygen` using POST; send them as `X-PAN-KEY` or `key=`.
* Keys are per administrator and invalidated by a password change; set an API Key Lifetime.
* `config` actions: `get` (candidate), `show` (running), `set` (merge into parent), `edit` (replace entry), `delete`.
* Use `debug cli on` to learn the XML for any CLI command.
* Panorama uses `commit-all` for pushing device group and template configuration.
* Give the API account a role that enables only the API sections it needs.
