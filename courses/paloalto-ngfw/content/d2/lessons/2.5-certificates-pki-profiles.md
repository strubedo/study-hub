## The certificate toolbox

Certificates on PAN-OS serve three separate jobs. Mixing them up is the main source of wrong answers.

| Job | Objects involved |
|-----|------------------|
| **The firewall proves its identity** to admins, GlobalProtect users, Authentication Portal users, syslog servers | Server certificate + **SSL/TLS Service Profile** |
| **The firewall verifies someone else's identity** (admin or GP client certificates, syslog servers, LDAP/RADIUS servers over TLS, SAML IdP) | **Certificate Profile** (CAs + revocation checking) |
| **The firewall decrypts traffic** (SSL Forward Proxy, SSL Inbound Inspection) | Forward Trust / Forward Untrust certificates, imported server certs, **Decryption profile** (next lesson) |

All of them live under **Device > Certificate Management** (Certificates, Certificate Profile, OCSP Responder, SSL/TLS Service Profile, SCEP, SSL Decryption Exclusion, SSH Service Profile). Use **Panorama > Certificate Management** or templates to deploy at scale.

## Certificates page

**Device > Certificate Management > Certificates** shows device certificates and **Default Trusted Certificate Authorities**. You can:

* **Generate** a certificate: *self-signed* (signer = none), or signed by another CA stored on the firewall. Fields include Common Name, Subject Alternative Names, key algorithm (RSA or ECDSA) and size, digest, expiry, and **Certificate Authority** checkbox (marks it as a CA, needed for forward trust).
* **Import** a certificate (PEM, PKCS#12, DER) with its private key.
* Generate a **CSR**, have a CA sign it, and import the result (the standard PKI flow).
* Set **usage flags** on a certificate after it is created: *Forward Trust Certificate*, *Forward Untrust Certificate*, *Trusted Root CA*, *Certificate for Secure Syslog*.
* Export a certificate (with or without private key) or **Revoke** one the firewall issued.
* **Block Private Key Export** on generate or import, to prevent private-key extraction.

> **Watch out:** A certificate must have the private key on the firewall to be used for decryption or for a server identity. A certificate without a private key can only be a trust anchor (for example a root CA imported so the firewall trusts it).

## PKI integration

Palo Alto firewalls integrate with an enterprise PKI in several ways.

* **CSR and import.** Generate a CSR on the firewall, sign it with an enterprise CA such as Microsoft AD CS or an external provider, and import it. The private key never leaves the firewall.
* **SCEP** (**Device > Certificate Management > SCEP**): a SCEP profile (server URL, challenge/password, CA-IDENT name, key size, fingerprint) lets the firewall request and renew certificates automatically from a SCEP server. In GlobalProtect, SCEP can also issue client certificates to endpoints.
* **OCSP responder** (**Device > Certificate Management > OCSP Responder**): defines an OCSP URL and host; referenced from a certificate profile.
* **CRL**: a CRL distribution point URL is read from the certificate or specified in the profile; the firewall downloads it.
* **HSM** (**Device > Setup > HSM**): store private keys in a Hardware Security Module (SafeNet Luna or Thales nShield) so forward-trust and server keys never reside on disk.
* **Panorama** as a CA is possible (self-signed root on Panorama pushed in templates) and is common for lab environments.

> **Real world:** Enterprise PKI integration is mostly one decision: let AD CS issue a subordinate CA certificate for forward trust (clients already trust the enterprise root), or make a self-signed forward trust and distribute that root to clients.

## Certificate profiles

A **Certificate Profile** (**Device > Certificate Management > Certificate Profile**) tells the firewall *how to validate a certificate presented to it*. Fields:

| Field | Purpose |
|-------|---------|
| **Username Field** | Where the user identity comes from: **Subject** (Common Name), **Subject Alt** (Email, Principal Name), or **None** |
| **User Domain** | Domain to prepend to the extracted name |
| **CA Certificates** | The CA(s) the client certificate must chain to; one entry may specify a **Default OCSP URL**, an **OCSP Verify CA** certificate, and a CRL |
| **Use CRL / Use OCSP** | Revocation checking methods (with both enabled, the firewall tries OCSP first and falls back to the CRL only if the OCSP responder is unavailable) |
| **CRL Receive Timeout / OCSP Receive Timeout / Certificate Status Timeout** | Seconds to wait for revocation information |
| **Block session if certificate status is unknown** | Fail closed if revocation cannot be determined |
| **Block session if certificate status cannot be retrieved within timeout** | Fail closed on timeout |
| **Block session if the certificate was not issued to the authenticating device** | Ties certificate to device |
| **Block sessions with expired certificates** | Reject expired certificates |

### Where a certificate profile is used

* Administrator certificate-based login (**Device > Setup > Management > Authentication Settings**)
* GlobalProtect portal/gateway client authentication (see lesson 1.5)
* Authentication Portal client certificate authentication
* Secure syslog (mutual TLS) and other TLS client/server verification
* Panorama and device secure communications

> **Exam tip:** "Admins log in with smart cards" means a **Certificate Profile** that maps the Subject or Principal Name to a username, with an **OCSP responder** or CRL. The username must still match a configured administrator, or the profile can be combined with an authentication profile.

### Certificate-based authentication in practice

Two common patterns:

1. **Certificate only**: Certificate Profile on the service, with Username Field set; no authentication profile. The username in the certificate becomes the user.
2. **Certificate plus password or MFA**: both a Certificate Profile and an Authentication Profile on the same service (GlobalProtect supports this). Both must pass.

If the Username Field is **None**, the certificate establishes only that the device or user holds a valid certificate; the username then must come from another factor, otherwise the user is unknown.

## SSL/TLS Service Profile

An **SSL/TLS Service Profile** (**Device > Certificate Management > SSL/TLS Service Profile**) binds a **server certificate** to a **minimum and maximum TLS version** for a service the firewall *terminates*. It is used by:

* The management web interface (**Device > Setup > Management > General Settings > SSL/TLS Service Profile**)
* GlobalProtect portals and gateways
* Authentication Portal (captive portal)
* Other services the firewall terminates, such as the User-ID agent connection (Connection Security) and device-to-Panorama secure communication settings, depending on release

If none is selected, the management interface uses a default self-signed certificate that browsers warn about. Replace it with an enterprise certificate and a profile with a minimum TLS version of 1.2 or higher.

```text
Device > Certificate Management > SSL/TLS Service Profile
Name         Certificate       Min Version   Max Version
mgmt-tls     mgmt.example.com  TLSv1.2       Max
gp-tls       vpn.example.com   TLSv1.2       Max
```

> **Watch out:** An SSL/TLS Service Profile does **not** control decrypted user traffic. Min/max TLS for decryption is configured in a **Decryption profile** (SSL Protocol Settings). If the question is about "the firewall's own web interface" or "GlobalProtect portal", it is the service profile; "traffic being decrypted" is the decryption profile.

## Revocation checking for the firewall's own decisions

Under **Device > Setup > Session > Decryption Settings > Certificate Revocation Checking** the firewall can check CRL/OCSP for server certificates it sees during decryption, with timeouts and a *block session if status unknown/timeout* option. This is separate from the certificate profile.

## Operational view

```text
PA-HQ> show system setting ssl-decrypt certificate
PA-HQ> show system setting ssl-decrypt setting
```

Both are real operational commands (certificate cache and decryption settings). For certificate storage and trust, the GUI is the main tool: sort by Expires, check the usage flags and the chain.

## Lab it yourself

1. Generate a self-signed root CA `Lab-Root-CA` on the firewall (check Certificate Authority). Generate a certificate `mgmt.lab.example.com` signed by it. Create an SSL/TLS Service Profile with TLS 1.2 minimum. Select it under Management and commit. Import `Lab-Root-CA` public cert into your browser and check the padlock.
2. Generate a client certificate for user `jsmith`, export it as PKCS#12, build a Certificate Profile with Username Field = Subject and the root as the CA, and set it as the admin Authentication Settings certificate profile with a local admin `jsmith`. Test certificate login.
3. Revoke the client certificate (Certificates > Revoke) and add Use CRL or OCSP in the profile; confirm login fails.

## Key takeaways

* Three jobs: present identity (service profile), verify identity (certificate profile), decrypt traffic (forward trust/untrust and decryption profile).
* A usage flag on a certificate (Forward Trust, Forward Untrust, Trusted Root CA, Secure Syslog) gives it a role; the Certificate Authority checkbox is needed for forward trust.
* PKI integration: CSR + enterprise CA, SCEP, OCSP responder, CRL, HSM.
* Certificate profiles extract the username from Subject or Subject Alt and check revocation with CRL or OCSP; they have fail-open and fail-closed options.
* SSL/TLS service profiles pair a certificate with a minimum/maximum TLS version for services the firewall terminates (management, GlobalProtect, Authentication Portal).
* Decryption TLS versions live in the Decryption profile, not in the service profile.
