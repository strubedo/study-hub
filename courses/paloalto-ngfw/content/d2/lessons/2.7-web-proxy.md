## What the PAN-OS web proxy is

Starting with PAN-OS 11.0, a NGFW can act as a **web proxy** for HTTP/HTTPS traffic, so one box provides both firewall and secure web gateway functions. The web proxy is configured under **Network > Proxy** and it comes in two modes, chosen with the **Proxy Type** in *Proxy Enablement*:

| Mode | Client awareness | How traffic reaches the proxy | User authentication |
|------|------------------|-------------------------------|---------------------|
| **Explicit proxy** | The browser (or OS/PAC/WPAD) is configured with the proxy address and sends HTTP `CONNECT` / proxied requests to it | Directly addressed to the proxy IP | Kerberos SSO, SAML, or Cloud Identity Engine (or none) |
| **Transparent proxy** | None: clients send traffic as if to the origin server | A **DNAT policy rule** redirects the client's web traffic to the proxy on the loopback address | None needed (it relies on the firewall's normal User-ID) |

Only one proxy type is active at a time (the choices are None, Explicit, or Transparent). PAN-OS web proxy supports **IPv4** only.

> **Exam tip:** Explicit proxy is easier to troubleshoot because the client knows about the proxy; transparent proxy requires no client configuration but depends on the DNAT redirect and does not authenticate users itself. WCCP is **not** supported for the transparent mode.

## Requirements

* **PAN-OS 11.0 or later** (explicit proxy on cloud-managed firewalls with the Advanced Routing Engine is supported from 11.2).
* A **Web Proxy licence**. It is required for the PA-1400, PA-3400, PA-5400 and PA-5450 series and for VM-Series; the **Proxy Type** dropdown shows only *None* until the licence is active. On VM-Series you add **Web Proxy** to the deployment profile in the Customer Support Portal and then retrieve licences on the firewall. Check the current support matrix for other platforms, since licensed models change.
* **Three Layer 3 interfaces in separate zones** (best practice), in the same virtual router and virtual system: one facing clients, one facing the internet, and a **loopback interface** for the proxy.
* A **DNS Proxy object** with **primary and secondary** DNS servers (both are required) and a bound interface.
* A **certificate** for decryption (self-signed root CA or one signed by the enterprise CA) so the proxy can decrypt (man-in-the-middle) HTTPS; clients must trust it.
* Security, NAT (for transparent), and **decryption** policy.
* For explicit proxy authentication, the pre-work for **Kerberos** (SPN, keytab), **SAML** (IdP profile), or **Cloud Identity Engine**. SAML for explicit proxy in the Prisma Access integration needs Panorama with the Cloud Services plugin and the web proxy add-on licence.

## Configuring explicit proxy

1. **Interfaces and zones**: client interface (its IP is the **Proxy IP**), internet interface, and loopback for the proxy. Put each in its own zone in the same vsys and VR.
2. **DNS proxy**: Network > DNS Proxy with primary and secondary servers and the interface for the proxy connection (the ingress interface or the loopback).
3. **Decryption certificate**: create or import the CA that signs the decrypted sessions' certificates, marked as the forward trust certificate.
4. **Network > Proxy > Proxy Enablement**: set the Proxy Type to **Explicit Proxy**.
5. **Explicit Proxy Configuration**:
   * **Connect Timeout** (seconds waiting for the origin server),
   * **Listening Interface** (the client-facing interface) and **Proxy IP**,
   * **Upstream Interface** (a loopback if used),
   * **DNS Proxy** object,
   * **Check domain in CONNECT & SNI are the same**, to block domain fronting,
   * **Authentication service** (Kerberos SSO or SAML/CAS) and an authentication profile.
6. **Policy**:
   * Decryption rule with the **upstream interface's zone as the source zone** to avoid decrypting twice,
   * A security rule from the client zone to the listening interface (so clients can reach the proxy),
   * A security rule from the upstream zone to the internet, and from the DNS proxy zone to the internet,
   * An Authentication rule using the authentication profile.
7. Commit. On the first proxy configuration, make a change to the DNS proxy and the interface config, then commit again so the proxy configuration is populated.
8. Point clients at the proxy with **PAC/WPAD** or browser settings (the proxy IP and port).

> **Watch out:** Decrypt on the **upstream** zone as the source zone, not the client zone, otherwise explicit-proxy traffic is decrypted twice (once on arrival, once on its way out).

Optionally use **Objects > Decryption Profile > Block sessions on SNI mismatch with Server Certificate (SAN/CN)** to deny sessions where the SNI does not match the server certificate.

### Explicit proxy authentication

* **Kerberos SSO**: transparent to domain users; needs SPN and keytab (firewall must be reachable by name from clients).
* **SAML**: redirects to the IdP; suitable for non-domain devices and MFA.
* **Cloud Identity Engine**: uses CIE's authentication.
* **Authentication exemptions**: **Configure Exemptions for Explicit Proxy Authentication** lets you bypass authentication for specific domains or applications, such as operating-system updates.
* No authentication is also valid; the proxy then cannot attribute traffic to users except from existing User-ID mapping.

## Configuring transparent proxy

1. Same interfaces, zones and DNS proxy as above. The **DNS proxy** is bound to the **loopback**.
2. **Network > Proxy > Proxy Enablement**: set the Proxy Type to **Transparent Proxy**.
3. **Transparent Proxy Configuration**: **Connect Timeout**; **Upstream Interface** (a loopback not associated with any other subnet); **Proxy IP** (the loopback's address); **DNS Proxy** object.
4. **DNAT policy rule** (this must match the documented settings or the proxy will not receive traffic):
   * Original packet: source zone = client zone, destination zone = the zone of the interface that contains the web proxy,
   * Translated packet: **no source translation**; destination translation type **Dynamic IP (with session distribution)**; translated address = the **proxy IP**; translated port **8080**,
   * The rule must be **above** the SNAT rule.
5. SNAT rule below it for traffic leaving through the internet interface.
6. Security rules: client to proxy, proxy to internet, DNS.
7. **Decryption policy** with the proxy zone as the source zone.
8. Commit as above.

```text
Network > Proxy
Proxy Type:       Transparent Proxy
Connect Timeout:  5 (s)
Upstream Interface: loopback.1
Proxy IP:         10.255.255.1
DNS Proxy:        DNSP-Proxy

Policies > NAT
Name      Source Zone  Dest Zone   Source Translation  Destination Translation
dnat-prx  trust        proxy-zone  none                dynamic-ip-and-port-distribution 10.255.255.1:8080
snat-out  proxy-zone   untrust     dynamic-ip-and-port 203.0.113.2    none
```

The DNAT rule precedes the SNAT rule. The session distribution method is not used by the web proxy, but the field is required by the NAT type.

> **Exam tip:** "Transparent proxy users see no proxy and need no setting, but the proxy relies on a *specific* DNAT rule ahead of the source NAT." If the symptom is "traffic bypasses the proxy", look at the NAT rule order and its translated port.

## Choosing between modes

| Requirement | Pick |
|-------------|------|
| Authenticate every web user, including non-domain devices, with SSO | Explicit proxy (Kerberos or SAML) |
| No client change possible | Transparent proxy |
| Easy per-client troubleshooting, PAC-based routing | Explicit proxy |
| Integrate with Prisma Access explicit proxy, SAML | Explicit proxy with Panorama and the Cloud Services plugin |
| WCCP redirection | Not supported on PAN-OS |

## Management and verification

* **Panorama**: web proxy settings are in a template; the policy in device groups.
* **Strata Cloud Manager** manages explicit and transparent proxy for cloud-managed NGFWs (Device Settings > Proxy).
* Check **Monitor > Logs** (traffic with the proxy zone), the **Decryption** log, and the **Authentication** log for explicit proxy.
* The proxy itself is not a replacement for the **Security policy** and **Decryption**: both still apply.

## Lab it yourself

You need a VM-Series with a Web Proxy licence (it is a promotional add-on in the portal, which you may not have in a lab). If you have it:

1. Build the three-interface layout with a loopback, DNS proxy and a forward trust CA.
2. Enable the explicit proxy with no authentication. Point a browser at the Proxy IP and port, browse to an HTTPS site and inspect the certificate.
3. Switch to transparent proxy and add the DNAT/SNAT pair. Remove the browser setting and see the same site work.
4. Reverse the NAT rule order and observe the failure.

Without the licence, read the configuration pages and rehearse the checklist above.

## Key takeaways

* The PAN-OS web proxy (11.0 and later) runs in either explicit or transparent mode, never both, and needs a Web Proxy licence on supported platforms.
* Both need a loopback interface for the proxy, a DNS proxy object with primary and secondary servers, and a decryption certificate.
* Explicit proxy: clients are configured; authentication can use Kerberos SSO, SAML or Cloud Identity Engine.
* Transparent proxy: clients are unaware; a DNAT rule to the proxy IP and port 8080 must precede the SNAT rule; WCCP is not supported.
* Decrypt using the upstream or proxy zone as the source zone to avoid double decryption.
* Web proxy supports IPv4 only.
