## What an admin role controls

Every administrator account on a firewall or Panorama is bound to exactly one **role**. The role decides which parts of the **web UI**, **XML API**, **REST API** and **CLI** the account can reach, and (on a multi-vsys firewall) which virtual systems it can see. Roles are configured under **Device > Admin Roles** on a firewall and **Panorama > Admin Roles** on Panorama; accounts live under **Device > Administrators** (or **Panorama > Administrators**).

There are two families of role.

| Family | What it is | Examples |
|--------|-----------|----------|
| **Dynamic role** (built in, fixed) | Predefined, cannot be edited, and automatically gains access to new features after an upgrade | `superuser`, `superuser (read-only)`, `deviceadmin`, `deviceadmin (read-only)`, `vsysadmin`, `vsysadmin (read-only)` |
| **Admin Role profile** (custom) | You choose, feature by feature, **Enable / Read Only / Disable** for web UI and XML/REST API areas, plus a CLI level | A "SOC-readonly" role, a "NOC can only commit" role, a "policy-only" role |

> **Exam tip:** Dynamic roles are the answer when the question says "automatically include new features". A custom Admin Role profile is the answer when it says "only some tabs", "no access to the Device tab", or "hide privacy-sensitive fields".

### Dynamic role meanings

* **superuser** and **superuser (read-only)** - everything, or everything read-only, across the whole firewall including all virtual systems.
* **deviceadmin** and **deviceadmin (read-only)** - everything *except* defining other administrators or virtual systems. A deviceadmin can still change policy, network and device settings.
* **vsysadmin** and **vsysadmin (read-only)** - limited to one or more **assigned virtual systems**. Cannot configure shared objects, network settings, or device-level items. Only exists on firewalls with multi-vsys capability enabled.

### Admin Role profile tabs

A custom profile has tabs for **Web UI**, **XML API**, **REST API**, **Command Line** and **Privacy**.

* The **Web UI** tab is a tree: each node (Dashboard, ACC, Monitor, Policies, Objects, Network, Device, ...) is Enable, Read Only or Disable.
* **XML API** and **REST API** are separate switches, so an account can be allowed to script without being allowed in the GUI, or the reverse.
* **Command Line** is a single level: `None`, `superuser`, `superreader`, `deviceadmin`, `devicereader`, and on multi-vsys firewalls `vsysadmin` / `vsysreader`.
* **Privacy** hides or shows private data (such as source user, source and destination IP) in logs and reports, and controls whether the admin can view PCAPs and packet captures. Use it to keep a helpdesk role away from user identities.

### Panorama roles

Panorama adds role types so that access can be limited to part of the managed estate:

* **Panorama** role (superuser, read-only, panorama-admin, or custom profile) - scope is the Panorama server itself and everything it manages.
* **Device Group and Template** role - limited by an **Access Domain** to specific device groups, templates, and (optionally) individual firewalls/vsys. An administrator can belong to several access domains, each with its own role.

> **Watch out:** An access domain is what limits a Panorama admin to certain device groups. A role alone does not. If a question says "restrict to the EMEA firewalls", look for the **Access Domain**.

## Creating administrators

Administrators can authenticate in four ways. Pick by what the account needs to prove:

| Method | How it is set | Typical use |
|--------|---------------|-------------|
| **Local password** | Name and password on the account; no authentication profile | Break-glass `admin` account |
| **Public key (SSH)** | Upload the key; **Use Public Key Authentication (SSH)** | Automation and CLI-only users |
| **Client certificate** | **Certificate Profile** is set on the account or globally; no password | Smart-card / CAC style web login |
| **External server** | An **Authentication Profile** (RADIUS, TACACS+, LDAP, Kerberos, SAML) on the account | Central identity |

You can also set the **authentication profile** globally under **Device > Setup > Management > Authentication Settings**, so any account that does not exist locally is authenticated against that server.

### Where the role comes from for external admins

* A **local administrator account** with a role pre-assigned and the authentication profile chosen: the external server only proves identity, the role comes from the local account. This is the only option for **LDAP and Kerberos**.
* **Role-based mapping from the server**: for **RADIUS** (and TACACS+ and SAML) the server can return the role, using Palo Alto vendor-specific attributes (VSAs) or SAML attributes. The account does not need to exist locally; the firewall creates the session with the returned role, optionally an access domain. A user with no valid role attribute is refused.

> **Exam tip:** "Admins log in with Active Directory credentials via LDAP and get different permissions by group" cannot be solved by LDAP alone. Either create local accounts with roles, or use RADIUS/TACACS+/SAML with role attributes. (Cloud Authentication Service and SAML carry attributes for group-based role assignment as well.)

## Hardening the admin plane

* **Device > Setup > Management > Minimum Password Complexity** applies to **local** accounts only: minimum length, upper/lower case, numbers, special characters, block username inclusion, password history, and **password change period/expiry**.
* **Authentication Settings > Idle Timeout** and **API Key Lifetime** limit stale GUI sessions and API keys.
* Lockout: **Failed Attempts** and **Lockout Time** are set per authentication profile (see the next lesson), and apply to the profile's users, including administrators.
* Use the **Management** interface profile / **Permitted IP Addresses** on management, restrict HTTPS/SSH to a management network, and never expose the management interface to the internet.
* Create a **break-glass local superuser** that is not tied to the external server, so a RADIUS or SAML outage never locks you out of the box.
* Use **commit locks** / config locks and the **Config log** to see who changed what.

```text
PA-HQ> test authentication authentication-profile RADIUS-Corp username noc1 password
Enter password :
Target vsys is not specified, user "noc1" is assumed to be configured with a shared auth profile.
Do allow list check before sending out authentication request...
name "noc1" is in group "all"

```

The output above is representative; exact wording varies by release. The command **tests the authentication profile** and the allow list, it does **not** test role assignment.

In configure mode the account and role binding looks like this:

```text
PA-HQ# set mgt-config users noc1 authentication-profile RADIUS-Corp
PA-HQ# set mgt-config users noc1 permissions role-based deviceadmin yes
PA-HQ# commit
```

## Lab it yourself

You can do the whole lab on a VM-Series trial or a hardware firewall, plus a Linux host.

1. Create an Admin Role profile **Helpdesk** with Monitor and Policies set to **Read Only**, everything else Disable, Privacy set to hide source user/IP, and Command Line `None`.
2. Create account `help1` using the **Helpdesk** role and a local password. Log in and note which tabs disappear.
3. Remove the XML API permission and try `curl -k "https://<fw>/api/?type=keygen&user=help1&password=..."` - key generation should be refused.
4. Stand up FreeRADIUS on Linux, add the Palo Alto dictionary, and return `PaloAlto-Admin-Role` for a user. Point an authentication profile at it and set the global Management authentication profile. Test with `test authentication authentication-profile`.

## Key takeaways

* A role is bound to the account and gates web UI, XML API, REST API and CLI independently.
* Dynamic roles are built in, not editable, and pick up new features automatically; custom Admin Role profiles are feature-by-feature.
* vsysadmin roles exist only with multi-vsys, and are scoped to assigned virtual systems.
* On Panorama, an Access Domain is what restricts an admin to selected device groups, templates and firewalls.
* LDAP and Kerberos authenticate only; roles must come from a local account. RADIUS, TACACS+ and SAML can return the role.
* Password complexity applies to local accounts; lockout is configured on the authentication profile.
* Keep one local break-glass superuser independent of any external server.
