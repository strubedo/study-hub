## What User-ID does

User-ID lets the firewall write policy and read logs in terms of **users and groups** instead of IP addresses. It needs two independent pieces of data:

1. **User-to-IP mapping**: which user is on which IP right now.
2. **Group mapping**: which users belong to which groups (and, with the Cloud Identity Engine, which attributes).

Policy uses them together: the firewall looks up the source IP in the mapping table, gets the user, and then checks that user's groups against the rule. This lesson covers group mapping and the Cloud Identity Engine (CIE); the next covers IP-user mapping sources and redistribution.

> **Exam tip:** Group mapping gives the firewall **membership**; it gives no IP addresses. A policy that uses a group but no mapping source will never match, and the reverse is also true.

## On-premises group mapping (LDAP)

Configure in **Device > User Identification > Group Mapping Settings**.

1. **LDAP server profile** (**Device > Server Profiles > LDAP**): type `active-directory`, server addresses, port (389 or 636 for LDAPS; 3268/3269 for the Global Catalog), **Base DN**, **Bind DN** and password (a read-only service account), and **Require SSL/TLS secured connection** with certificate verification where possible.
2. **Group mapping**: Add an entry with the **Server Profile**, **User Domain** (NetBIOS name, used to prefix `domain\user`), **Update Interval**, and the **Group Include List** (the groups to track).
3. **User Attributes** tab: **Primary Username** (normally `sAMAccountName`), **E-Mail**, **Alternate Username**s (`userPrincipalName`). All these formats resolve to the same user.
4. Optionally **Custom Group** entries built from an **LDAP filter** (for example, users where `department=Engineering`) and **Enabled** the mapping.
5. Commit.

Key behaviours:

* The firewall only learns the groups in the **Group Include List**; keep it focused to save memory.
* The default **Update Interval is 3600 seconds**; changes in AD appear after the next refresh. Force one now with `debug user-id refresh group-mapping all`.
* Nested group membership is resolved by the firewall from the directory data; very deep nesting is expensive. A group of groups is flattened.
* The mapping uses **User Domain**: if the mapping source reports `EXAMPLE\jsmith` and group mapping has a different domain value, the user and group never connect.
* Group mapping is **per virtual system**.
* One LDAP profile can be shared; multiple domains need multiple group-mapping entries.

## Directory sync and the Cloud Identity Engine

The **Cloud Identity Engine (CIE)** is Palo Alto's cloud service for identity data. It is part of the **hub**, and has two main functions:

| Component | Purpose |
|-----------|---------|
| **Directory Sync** | Reads users, groups and attributes from your directory and makes them available to firewalls and other Palo Alto products |
| **Cloud Authentication Service** | Authenticates users against a cloud IdP (SAML, OIDC) for GlobalProtect, Authentication Portal and the web proxy |

CIE can also act as a **mapping source** for IP-user data (see the next lesson).

### Why use it instead of LDAP

* Works with **cloud directories** (Microsoft Entra ID / Azure AD, Okta, Google) as well as on-prem AD.
* Firewalls **do not query the directory directly**; the Cloud Identity Agent syncs it to CIE and firewalls fetch from CIE. That means no LDAP reachability or bind account on every firewall, which scales well across many sites and Prisma Access.
* Provides **user attributes** in addition to groups, and reflects directory changes quickly.
* One CIE tenant serves many firewalls.

### How to set it up

1. In the **hub**, activate the **Cloud Identity Engine** app and create a tenant.
2. Create a **Directory** and install the **Cloud Identity Agent** (on-prem AD) or connect a cloud directory (Entra ID, Okta, Google) to complete the sync. The agent only needs outbound connectivity to the service plus access to the directory.
3. On the firewall, ensure the **device certificate** is installed (Device > Setup > Management > Device Certificate); the firewall authenticates to CIE with it.
4. **Device > User Identification > Cloud Identity Engine**: create a **Cloud Identity Engine profile** (region, instance, and the directory). Settings include an **update interval** (documented default: 60 minutes), the **primary, email and alternate username** formats, and the group name format.
5. Reference the profile in **Group Mapping Settings** (a CIE source instead of an LDAP server profile) and use the groups in policy.
6. Commit and check `show user group-mapping state all` again; the type shows a Cloud Identity Engine source.

The firewall collects attributes only for **users and groups referenced in policy**, not the whole directory. That keeps memory use predictable and is why a group "that exists in AD" can be missing from the firewall until a rule uses it.

> **Watch out:** CIE and on-prem LDAP mapping are alternatives. Pick one source per group/user domain; mixing two sources with different username formats creates duplicate users that do not match policy.

### Using the data in policy

* Security, Decryption, Authentication and other rules can use **groups** and (with CIE attributes) fine-grained user selections in **Source User**.
* **Dynamic User Groups** (**Objects > Dynamic User Groups**) match users by **tags** (applied by a log forwarding profile *Tagging* action or the User-ID API). Policy changes membership automatically; a user with a critical threat log is tagged and falls into a restricted group, for example.
* **User context**, i.e. the user, group and attribute information associated with a session, is what makes logs filterable by `(user.src eq ...)` and enables user-based reports in the ACC.

### Verification

```text
PA-HQ> show user group-mapping state all
PA-HQ> show user ip-user-mapping all
IP              Vsys   From    User                         IdleTimeout(s)  MaxTimeout(s)
10.0.1.25       vsys1  UIA     example\jsmith               2410            2410
Total: 1 users
```

Check that user names are in the same `domain\user` form on both sides.

## Panorama

User-ID settings (group mapping, CIE profile, user mapping) are **template** settings. Device groups reference the resulting users/groups in policy. Panorama can also run group mapping itself for policy it hosts, with its own LDAP profile (Panorama > User Identification).

## Lab it yourself

1. Install a Windows eval AD or OpenLDAP with a few users and groups. Create an LDAP server profile and a Group Mapping entry with `Engineering` in the include list.
2. Run `show user group-mapping state all` and `show user group list`; add a user to the group in AD and run `debug user-id refresh group-mapping all`, then check `show user group name`.
3. Add a security rule using that group as Source User. Without a mapping source the rule will not match. (Next lesson fixes that.)
4. A real CIE requires a Palo Alto account and hub access; read the CIE configuration pages if you have one.

## Key takeaways

* User-ID needs mapping (IP to user) and group membership; policy uses both.
* Group mapping uses an LDAP server profile, the Group Include List, a domain name and an update interval (default 3600 seconds).
* `show user group-mapping state all` and `show user group list` verify group mapping; `debug user-id refresh group-mapping all` forces a refresh.
* The Cloud Identity Engine syncs directories (AD, Entra ID, Okta, Google) via Directory Sync and removes the need for each firewall to query LDAP.
* CIE needs a device certificate on the firewall and a CIE profile; attributes are collected for users and groups used in policy.
* Dynamic User Groups use tags for automatic membership.
* Group mapping and User-ID are per virtual system; on Panorama they are template settings.
