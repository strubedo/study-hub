## Two kinds of update

| Kind | What changes | Where | Reboot? |
|------|-------------|-------|---------|
| **PAN-OS software** | The operating system | **Device > Software** | Yes |
| **Dynamic (content) updates** | App-ID and threat signatures, antivirus, WildFire, GlobalProtect data file, and similar | **Device > Dynamic Updates** | No (a commit applies it) |

Keep them separate in your head: content updates are frequent and low-risk; PAN-OS upgrades are planned changes with an upgrade path and a rollback plan.

## Dynamic content updates

Content packages in **Device > Dynamic Updates** include:

* **Applications and Threats** (needs a Threat Prevention licence for the threat part) or **Applications** only
* **Antivirus**
* **WildFire**
* **GlobalProtect Data File** and **GlobalProtect Clientless VPN**
* Device dictionary and other data files, depending on subscriptions

Each package shows the version installed, release date and a **Download / Install / Revert** action.

### Scheduling

Under **Schedule** you pick a recurrence (hourly, daily, weekly), a time, and an **Action**: *Download Only*, or *Download and Install*. Two settings matter for stability:

* **Threshold (hours)**: delays installing a content release until it has been published for the specified number of hours. It keeps a freshly published, possibly buggy release out of production.
* **New App-ID Threshold** / **Allow Extra Time to Review New App-IDs**: new applications included in a content update can change how traffic matches security rules. The firewall can **disable new App-IDs** until you review them (**Device > Dynamic Updates > Disable new apps in content update**), then you enable them and adjust policy.
* **Sync To Peer**: in HA, installs the content on the peer too.

> **Exam tip:** Content updates on an HA pair are installed on **both** peers (use *Sync To Peer* or install separately). Out-of-sync content does not break HA, but a different App-ID version can change how a session is handled after failover. Check `show system info | match app-version` on both.

### Content versions and PAN-OS

Each PAN-OS release has a **minimum content version** (stated in its release notes). Install it *before* upgrading PAN-OS; otherwise the firewall can lose features after the upgrade.

### Operational commands

```text
PA-A> request content upgrade check
PA-A> request content upgrade download latest
PA-A> request content upgrade install version latest
PA-A> request anti-virus upgrade check
PA-A> show system info | match app-version
app-version: 9100-9100
PA-A> show jobs all
```

`show jobs all` shows download and install job status; the final result appears as `FIN OK`.

### Reverting

If a content release breaks something, use **Revert** in Dynamic Updates (or from Panorama: Device Deployment > Dynamic Updates > Revert Content). Choose the previously installed version and commit.

## PAN-OS software upgrades

### Rules that always apply

1. **Follow the documented upgrade path.** Traditionally you cannot skip feature releases: for each feature release in the path you **download the base image** before you can install its maintenance release. The 11.1 upgrade guide adds a **Skip Software Version Upgrade** feature that lets you skip up to three releases on supported paths (for example from 10.1 straight to 11.1, or from a 10.2 release to 11.2). On Panorama, skipping requires the base and maintenance images on the same SCP server. Check the **upgrade path** table for your current and target release rather than assuming either rule.
2. **Back up first**: export the named configuration snapshot (Device > Setup > Operations) and generate a tech support file.
3. **Content first**: install the minimum content version required by the target release.
4. Read the **release notes** for known issues and changes to default behaviour, and the **Upgrade/Downgrade Considerations** table.
5. Downgrades follow similar rules (and may need a config restore from the older release).

### Standalone firewall steps

```text
PA-HQ> request system software check
PA-HQ> request system software download version 11.2.4
PA-HQ> show jobs all
PA-HQ> request system software install version 11.2.4
PA-HQ> request restart system
PA-HQ> show system info | match sw-version
```

In the GUI: **Device > Software > Check Now**, **Download**, **Install**, then reboot when prompted. The maintenance release number in the commands above is an example; choose the release recommended for your upgrade path.

### Upgrading a high availability pair

The goal is to upgrade one peer at a time without an extra outage. The official firewall-level procedure for **active/passive** and **active/active** pairs says:

1. **Disable preemption** on one peer (Device > High Availability > Election Settings), commit, and make sure the commit succeeded. This prevents a failback during the upgrade.
2. **Active/passive**: suspend the **active** (primary) peer so the passive peer takes over, then upgrade the suspended peer, then make the upgraded peer functional (`request high-availability state functional`). Then suspend the other peer so the upgraded peer becomes active again, and upgrade it.
3. **Active/active**: it does not matter which peer is upgraded first.
4. **Both peers must be on the same feature release before moving on.** When peers are two or more feature releases apart, the older one enters the **suspended** state with the message *Peer version too old*.
5. Re-enable preemption (if it was on) and verify.

The same upgrade guide's Panorama-based firewall procedure gives the other order for active/passive (update the **passive** peer first, suspend the active peer to fail over, update the former active peer, then return it to functional). Both orderings aim at a single failover; read the procedure for the method you use (manual on the firewall, or through Panorama) and your release. On the exam, the invariants are the safe ones: preemption off, one peer at a time, the same feature release on both, and a verification of state before continuing.

```text
PA-A> request high-availability state suspend
PA-A> request high-availability state functional
PA-A> show high-availability state
Group 1:
  Mode: Active-Passive
  Local Information:  Version: 1  Mode: Active-Passive  State: passive  Device Priority: 90
  Peer Information:   State: active
PA-A> show high-availability interface ha2
```

> **Watch out:** Config sync is blocked between peers on different feature releases for most changes; make no config changes in the middle of the upgrade.

### Upgrading through Panorama

Order for a Panorama-managed estate:

1. **Panorama** (and its HA peer) first.
2. **Dedicated Log Collectors** (follow the Panorama, Log Collector, firewall and WildFire version compatibility table for the release).
3. **Firewalls**, with Panorama's **Device Deployment > Software** (download, then **Install**, optionally "Reboot device after install" and "Upload only to device (do not install)").

Panorama's rule: the management server must run the same or a **later** feature release than the firewalls and Log Collectors it manages. A firewall can run a later maintenance release within Panorama's own release train (Panorama 11.1.4 can manage a firewall on 11.1.5), but not a later feature release such as 11.2. When upgrading Log Collectors to 11.1, upgrade all of them at the same time.

Panorama's **Device Deployment** section also deploys **Dynamic Updates** (with scheduling), **Licenses**, **GlobalProtect Client** packages and can **Revert Content**. It can only deploy a software image after it has downloaded it (internet connected) or you have uploaded it (offline Panorama).

### Offline firewalls

For firewalls without internet access: download the image on a computer from the support portal, upload it via **Device > Software > Upload** (or **Panorama > Device Deployment > Software > Upload**), then install. Content works the same way (**Device > Dynamic Updates > Upload**).

## Lab it yourself

1. On a VM-Series or hardware firewall, open Device > Dynamic Updates, **Check Now** and download the current Applications and Threats package. Set a schedule with a 24-hour threshold and **Download and Install**.
2. Practice the CLI path above on a lab appliance: check, download, install, restart.
3. With two PA-VMs in A/P HA, practice disabling preemption, suspending a peer, and un-suspending it. Observe the state changes in `show high-availability state`.
4. Read the release notes of a target release and write down its minimum content version and upgrade path.

## Key takeaways

* Software upgrades reboot; content updates do not.
* Install the minimum content version before a PAN-OS upgrade; download base images for each feature release in the path; skip feature releases only where the Skip Software Version Upgrade path allows it.
* The content Threshold delays new content installation; disabling new App-IDs lets you review them first.
* HA upgrades: disable preemption, upgrade one peer at a time, keep the same feature release on both, and verify state; two feature releases apart gives Peer version too old.
* Panorama upgrade order: Panorama, then Log Collectors, then firewalls; Panorama must be the same or newer.
* Back up the configuration and export a tech support file before upgrading.
* Panorama Device Deployment pushes software, content, licences and GlobalProtect client packages.
