## Where logs live and where they can go

A firewall writes logs to its **local** disk by default. Most deployments also forward them, because local storage is small, shared between all log types, and lost with the box. The destinations are:

| Destination | Notes |
|-------------|-------|
| **Panorama** (local log collector in Panorama, or **Dedicated Log Collector**) | Next lesson |
| **Strata Logging Service** (SLS; formerly **Cortex Data Lake**) | Palo Alto's cloud log store |
| **Syslog**, **email**, **SNMP trap**, **HTTP** (webhook) | Per log type via server profiles |

A firewall can forward to Panorama/SLS **and** to external syslog at the same time. Forwarding is configured with **log forwarding profiles** for traffic-triggered logs and **Device > Log Settings** for system-level logs.

## Log types and their forwarding path

| Log type | Forwarded through |
|----------|-------------------|
| Traffic, Threat, URL, WildFire, Data, Tunnel Inspection, Authentication, SCTP, GTP, Decryption | **Log Forwarding profile** attached to the relevant rule (security, authentication, DoS protection, tunnel inspection, decryption). The 11.1 help lists Authentication, Data, GTP, SCTP, Threat, Traffic, Tunnel, URL and WildFire as profile log types; the CLI also offers decryption |
| System, Configuration, User-ID, HIP Match, IP-Tag, GlobalProtect, Correlation | **Device > Log Settings** (and Panorama equivalents) |
| Authentication | Log forwarding profile on the Authentication rule |

> **Exam tip:** A rule with no log forwarding profile still **writes** to the local disk (when "Log at Session End" is on) but forwards **nothing**. The most common troubleshooting answer for "logs are not reaching Panorama/syslog" is a missing or mis-filtered log forwarding profile on the rule. The second is that the destination's server profile or connectivity is wrong.

## Log forwarding profiles

Created under **Objects > Log Forwarding**. A profile contains one or more **match list** entries. Each entry has:

* **Log Type** (traffic, threat, url, wildfire, data, tunnel, auth, sctp, decryption, gtp)
* A **Filter** (all logs, or a log filter such as `(severity geq high)` or `(action eq deny)`)
* **Forward Method**: *Panorama/Logging Service*, *SNMP*, *Email*, *Syslog*, *HTTP*
* **Built-in Actions**: *Tagging* (add a tag to the source or destination IP, or to the source user) and, on some profiles, cloud actions. Tagging feeds **dynamic address groups** and **dynamic user groups** so policy adapts automatically (for example, quarantine a host after a critical threat log).

```text
PA-HQ# set shared log-settings profiles LFP-Standard match-list ML-Threat log-type threat filter "(severity geq high)" send-to-panorama yes send-syslog [ Syslog-SIEM ]
PA-HQ# set rulebase security rules Internet-Out log-setting LFP-Standard log-end yes
PA-HQ# commit
```

Verify the exact object path on your release with `?` completion; the structure above (profile, match list, log type, filter, forward targets) is stable.

Key behaviours:

* **The profile name `default`**, if it exists, is automatically selected as the Log Forwarding setting on **new** security rules in the GUI. It is a convenience: it does not apply to existing rules.
* Rules log at **session end** by default; **Log at Session Start** is off and used for troubleshooting long sessions because it doubles log volume.
* Several match-list entries can match the same log; all matches fire (one entry could send critical threats to email while another sends everything to Panorama).

> **Watch out:** Forward Method "Panorama/Logging Service" sends logs to whichever destination the firewall is configured for. If both Panorama and SLS are enabled, the firewall sends to both (see duplicate logging below), unless you disable the Panorama option.

### Server profiles

Syslog, email, SNMP trap and HTTP destinations are **server profiles** (Device > Server Profiles, or in a Panorama template). A syslog server profile has transport (UDP, TCP or **SSL**), port, format (BSD or IETF), facility and a **Custom Log Format** per log type. For syslog over SSL the firewall verifies the server with a **certificate profile** (lesson 2.5), and can present a client certificate.

## Device > Log Settings (system-level logs)

System, configuration, User-ID, HIP match, IP-tag and GlobalProtect logs are not tied to a rule. Under **Device > Log Settings** you add match-list entries per log type with the same forward methods. Without them, those logs are only on the firewall. On Panorama, the same settings are applied to firewalls through a **template**.

## Strata Logging Service (SLS)

SLS is a cloud-based log repository. It replaces the older name **Cortex Data Lake (CDL)**; GUI labels, CLI and documentation in 11.x/12.1 refer to Strata Logging Service, and some older strings and log directories still show "CDL".

### What it needs

1. A **Strata Logging Service license/instance** activated in the **hub** (Palo Alto's common services app) with a region chosen when the instance is created.
2. A **Customer Support Portal** account and a **Device Certificate** on the firewall (**Device > Setup > Management > Device Certificate**, using a one-time password from the CSP) so the firewall can authenticate to cloud services. From PAN-OS 11.0, the device certificate is used for authentication with SLS ingestion and query endpoints; the older logging-service certificate is used only if no device certificate is installed.
3. The firewall associated with the instance (via license/auth code), and outbound connectivity to the SLS ingestion FQDNs for the region.
4. On the firewall (or the template): **Device > Setup > Management > Strata Logging Service**, tick **Enable Strata Logging Service**, choose the **Region**, and optionally **Enable Duplicate Logging (Cloud and On-Premises)** so the firewall also forwards to Panorama. Also available: **Enable Enhanced Application Logging**.

Then rules need a **log forwarding profile** with Forward Method *Panorama/Logging Service* as above.

```text
PA-HQ> request logging-service-forwarding certificate fetch
PA-HQ> request logging-service-forwarding customerinfo fetch
PA-HQ> show logging-status
```

The first fetches the logging-service certificate (older method), the second (note the single word `customerinfo`) pulls the customer ID/region, and `show logging-status` reports the connection state. Output formatting varies by release.

### Where you read the logs

* **Monitor > Logs** on a firewall shows the *local* logs by default; use the **Log Source** or **Cloud** selection (where available) to query SLS.
* **Panorama** can query SLS (Cortex Data Lake plugin / SLS integration) for centralised search and reports.
* Strata Cloud Manager and other cloud apps consume SLS directly.

> **Exam tip:** With **duplicate logging**, the firewall sends two copies: one to SLS, one to Panorama. It is the supported way to keep Panorama as a local collector while using SLS for cloud analytics. Without it, forwarding to "Panorama/Logging Service" goes to the cloud only when SLS is enabled.

### SLS or Panorama collectors?

| Factor | Strata Logging Service | Panorama log collectors |
|--------|------------------------|-------------------------|
| Storage | Subscription-based, cloud | Your disks (M-Series, VMs) |
| Capacity planning | Buy more quota | Add disks and collectors |
| Ingestion path | Internet, TLS | Internal network |
| Data residency | Region chosen at activation | On-prem |
| Used by | Cloud apps, Prisma Access, firewalls | On-prem firewalls |

## Troubleshooting checklist

1. Does the **rule** have a log forwarding profile? Is the log **type** and **filter** correct?
2. Did the traffic actually log (`Log at Session End`)? Check **Monitor > Logs** locally.
3. Is the destination reachable? Syslog: transport and port; Panorama/SLS: connectivity from the correct **service route**.
4. Is the **service route** for the logging service (Device > Setup > Services > Service Route Configuration, "Palo Alto Networks Services" and Panorama/log forwarding) using the right interface?
5. Check the **System** log for connection or certificate errors.

## Lab it yourself

1. Build a syslog server profile pointing at a Linux host running `rsyslog` (UDP 514, listen enabled).
2. Create a Log Forwarding profile `LFP-Lab` with two match-list entries: all traffic logs to syslog; threat logs with severity medium and up to syslog plus a Tagging action on the source address.
3. Attach `LFP-Lab` to a rule, generate traffic, and watch `tail -f /var/log/syslog` on the host.
4. Remove the profile from the rule and confirm syslog goes quiet while the local traffic log still fills.

SLS cannot be reproduced in a home lab without a subscription.

## Key takeaways

* A rule's log forwarding profile controls forwarding of traffic-triggered logs; Device > Log Settings controls system-level logs.
* Forward methods: Panorama/Logging Service, syslog, email, SNMP, HTTP; the Tagging built-in action feeds dynamic groups.
* Rules log at session end by default; session-start logging is for troubleshooting.
* Strata Logging Service is the current name for Cortex Data Lake and needs a device certificate and activated instance.
* Duplicate Logging sends logs to SLS and Panorama at once.
* Missing or filtered log forwarding profile is the first suspect when logs do not arrive.
