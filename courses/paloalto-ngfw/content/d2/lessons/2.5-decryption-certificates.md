## Why decryption needs certificates

When the firewall decrypts TLS, it sits in the middle of two TLS sessions. How it presents a certificate to the client depends on the direction.

| Mode | Direction | Certificate the firewall uses |
|------|-----------|-------------------------------|
| **SSL Forward Proxy** | Internal users to internet servers | A **generated impersonation certificate** for the site, signed by the **Forward Trust** or **Forward Untrust** CA |
| **SSL Inbound Inspection** | External clients to your own servers | The **real server certificate and private key**, imported onto the firewall |
| **SSH Proxy** | SSH sessions | No certificate: uses host keys |

This lesson is about forward proxy, which is where Forward Trust, Forward Untrust and subordinate CA come in.

## Forward Trust and Forward Untrust

In forward proxy the firewall terminates the client's TLS session and opens a separate TLS session to the server. For the client side it forges a certificate for the requested hostname, copying the Common Name and Subject Alternative Names from the real server certificate, signed by a CA that the firewall holds.

| Certificate | Used when | Client's expectation |
|-------------|-----------|----------------------|
| **Forward Trust** | The server's certificate is **valid** and chains to a CA the firewall trusts | The client **trusts** the forward trust CA, so the user sees no warning |
| **Forward Untrust** | The server's certificate is **not trusted** (expired, self-signed, unknown issuer) | The client does **not** trust this CA, so the user gets a browser warning, which is the point: it passes the problem on |

Both must have the **Certificate Authority** flag and a private key on the firewall; mark them with the **Forward Trust Certificate** and **Forward Untrust Certificate** checkboxes under Device > Certificate Management > Certificates. Only one certificate of each kind is marked at a time in a given scope; check the release notes for any newer multi-algorithm support.

> **Exam tip:** Never install the **Forward Untrust** CA as a trusted root on clients. If you do, clients will silently trust sites the firewall already knows are bad.

### What the firewall checks

Before forging the Forward Trust certificate, the firewall validates the server's certificate chain against its **Default Trusted Certificate Authorities** list (plus any CA you mark *Trusted Root CA*) and optionally CRL/OCSP. If the server's issuing CA is not in the list, the firewall falls back to Forward Untrust. So an **internal HTTPS server** signed by your private CA can produce warnings in decryption even though users trust that CA: import the CA and tick **Trusted Root CA**.

## Choosing the Forward Trust CA

You have two real choices.

**1. Self-signed forward trust CA**: generated on the firewall (Certificate Authority checked, no signer). Simple, but every client and application must be given this root. Devices without it show warnings; apps that use certificate pinning break regardless.

**2. Subordinate CA from the enterprise PKI**: generate a CSR on the firewall (or have the CA issue a certificate and key you import), have the **enterprise root/issuing CA sign it as a subordinate CA**, and import it as the Forward Trust certificate. Clients already trust the enterprise root through Group Policy, so no extra distribution is needed, and the chain to the root is valid.

Requirements for the subordinate CA:

* Basic Constraints `CA:TRUE`, and Key Usage including certificate signing (`keyCertSign`); an AD CS **Subordinate Certification Authority** template is the usual source.
* The **private key stays on the firewall** (or on an HSM). A firewall that cannot sign certificates cannot impersonate.
* Import the **intermediate and root** certificates so the firewall can send the full chain; if a client does not have the intermediate, it relies on the chain being delivered.
* The root must be trusted on clients (GPO, MDM). Browsers and OS stores ignore a Forward Trust root that has no path to a trusted root.

```text
Device > Certificate Management > Certificates
Name                  Subject            Issuer           CA   Key  Usage
Corp-Root             Corp Root CA       Corp Root CA     yes  no   Trusted Root CA
FwdTrust-SubCA        PA-HQ Decrypt CA   Corp Root CA     yes  yes  Forward Trust Certificate
FwdUntrust-CA         PA-HQ Untrust CA   PA-HQ Untrust CA yes  yes  Forward Untrust Certificate
```

Here the forward trust CA chains to the enterprise root, which clients trust through GPO. The untrust CA is a self-signed certificate that nobody trusts, deliberately.

> **Real world:** Certificate-pinned apps (many banking, update and developer tools), and sites in sensitive categories (health, financial) should be excluded from decryption with a **No Decrypt** rule or the **SSL Decryption Exclusion** list (Device > Certificate Management > SSL Decryption Exclusion).

## Policy and profiles that use the certificates

Certificates alone do nothing. Decryption needs:

1. **A Decryption policy rule** (Policies > Decryption) with Action **Decrypt**, Type **SSL Forward Proxy**, and a **Decryption Profile** (Objects > Decryption > Decryption Profile).
2. **A Decryption profile** with SSL Forward Proxy checks: block sessions with expired certificates, untrusted issuers, unknown certificate status, unsupported versions or cipher suites, **Restrict certificate extensions**, **Block sessions if HSM is unavailable**, and TLS version bounds (min/max protocol versions and cipher/algorithm lists).
3. **Forward Trust and Forward Untrust certificates** in place.
4. **A security policy** that allows the application after decryption (App-ID sees the decrypted application, such as `ssl` replaced by `web-browsing` or `facebook-base`).
5. **Clients that trust the forward trust root.**

```text
PA-HQ> show system setting ssl-decrypt setting
PA-HQ> show counter global filter delta yes | match ssl
```

Traffic logs carry a flag showing whether a session was decrypted. The **Decryption** log (enable it via the decryption rule's log settings) lists each failure with a reason such as unsupported cipher, untrusted issuer or client rejected the certificate.

### Common failure causes

| Symptom | Likely cause |
|---------|--------------|
| Browser says the certificate is not trusted on **every** HTTPS site | Forward Trust root not installed in the client's trust store |
| Warnings only on **some** sites | Those servers present untrusted certificates, so the firewall used Forward Untrust (correct behaviour) |
| One application fails completely while the browser works | Certificate pinning or client-certificate authentication; add a No-Decrypt rule |
| Chain validation errors with a subordinate CA | Intermediate not imported, or root not trusted |
| Decryption works for some clients only | Trust distribution (GPO/MDM) incomplete |
| After a CA renewal, everything fails | New forward trust cert was not distributed or not flagged |

## SSL Inbound Inspection (for contrast)

Import the **server's real certificate and private key** onto the firewall (or use an HSM) and set a Decryption rule of type **SSL Inbound Inspection** with that certificate. The firewall does not generate certificates, so no Forward Trust is needed, and the client sees the real server certificate. This only works for servers whose private key you control.

## Lab it yourself

1. On the firewall, generate `Lab-Root` (CA) and `Lab-FwdTrust` signed by it, both with Certificate Authority checked. Tick **Forward Trust Certificate** on `Lab-FwdTrust`. Generate `Lab-Untrust` self-signed and tick **Forward Untrust Certificate**.
2. Install `Lab-Root` in a test browser's trust store.
3. Create a Decryption policy: source `trust`, destination `untrust`, category any, Action Decrypt, Type SSL Forward Proxy, with a profile that blocks expired certificates.
4. Browse to an HTTPS site; look at the certificate: issuer should be your forward trust CA. Then browse to a site with an expired certificate (a test site such as a badssl subdomain, if allowed) and see the untrust warning.
5. Check the traffic log's decrypted column and the decryption log.

## Key takeaways

* Forward proxy: Forward Trust signs valid sites, Forward Untrust signs bad ones and must never be trusted by clients.
* Both need the CA flag and a private key on the firewall.
* A subordinate CA signed by the enterprise PKI avoids distributing a new root, but must have CA:TRUE, signing key usage, a chain, and the key on the firewall.
* Inbound inspection uses the server's real certificate and key, not Forward Trust.
* Decryption needs policy, profile, certificates and client trust; each can be the failure point.
* Certificate-pinned applications and sensitive categories belong in No-Decrypt rules.
* Min/max TLS for decrypted traffic is set in the Decryption profile, not the SSL/TLS service profile.
