## Two ways out of a vsys

By default a vsys is an island. Traffic between two vsys on the same firewall, and traffic from several vsys to the internet over one shared link, are separate designs:

| Need | Feature |
|------|---------|
| Tenant A talks to Tenant B on the same box | **Inter-vsys routing** with **external zones** and **visible virtual systems** |
| Many vsys share one internet-facing interface and IP | **Shared gateway** |
| Tenants use separate physical internet links | Nothing special: each vsys has its own external interface and router |

> **Watch out:** Traffic that leaves the firewall on a physical interface and comes back in on another is *not* inter-vsys traffic. It is ordinary routing plus two ordinary sessions, no external zones involved.

## Inter-vsys communication within the firewall

Traffic that stays inside the firewall passes through an **external zone** in each vsys. An external zone is a zone of type **External** (**Network > Zones**) that has no interfaces and instead points at one or more other virtual systems.

### Requirements, in order

1. **Make the vsys visible to each other.** In each vsys (**Device > Virtual Systems > General**) tick the other vsys under **Visible Virtual Systems**. Visibility is directional: vsys1 needs vsys2 ticked to build an external zone toward it.
2. **Create an external zone in each vsys**, pointing to the peer vsys. Zones: `to-vsys2` in vsys1 and `to-vsys1` in vsys2.
3. **Routing.** The packet must route toward the peer vsys:
   * If both vsys share **one virtual router**, the normal route lookup works; the destination subnet is connected or learned inside that router, and the egress zone is the external zone.
   * If each vsys has **its own virtual router**, add a **static route in each router whose next hop type is *Next VR*** pointing at the other router. (Overlapping IP ranges cannot do this without NAT.)
4. **Security policy in both vsys.** In vsys1: `trust` to `to-vsys2` allow. In vsys2: `to-vsys1` to `trust2` allow. Policy is evaluated independently by each vsys.
5. **Commit.**

### Behaviour to remember

* The traffic is processed by the **egress vsys' policy** and the **ingress vsys' policy**. Each vsys evaluates its own security rules; this produces **two sessions** (one in each vsys) for one conversation.
* **No security rule is needed between two external zones.** An external zone gets automatic access to the other external zones that it can see; only internal-to-external and external-to-internal policy is needed in each vsys.
* A packet cannot traverse **more than two** virtual systems or shared gateways.
* App-ID and Content-ID run in each vsys' policy for the portion of the path it sees, so inspection profiles apply on both sides.

```text
PA-HQ# set vsys vsys1 rulebase security rules A-to-B from trust to to-vsys2 source any destination any application any service application-default action allow
PA-HQ# set vsys vsys2 rulebase security rules A-to-B from to-vsys1 to trust2 source any destination any application any service application-default action allow
```

The visibility and external-zone steps are done in the GUI: Device > Virtual Systems (Visible Virtual Systems) and Network > Zones (Type External, Virtual Systems list). The CLI rules above assume those exist; use `?` completion to find the CLI nodes for them on your release, as they are not covered in the CLI quick start.

### Exhibit-style reading

```text
Device > Virtual Systems
Name   ID  Interfaces     Virtual Routers  Visible Virtual Systems
vsys1  1   ethernet1/2    vr-shared        vsys2
vsys2  2   ethernet1/5    vr-shared        (none)

Network > Zones (Location: vsys2)
Name      Type      Interfaces/Virtual Systems
trust2    layer3    ethernet1/5
to-vsys1  external  vsys1
```

Here vsys1 can build an external zone toward vsys2, but vsys2 cannot see vsys1: until vsys2 ticks vsys1 as visible, `to-vsys1` cannot be created or used.

> **Exam tip:** When inter-vsys traffic fails, check in this order: **Visible Virtual Systems** on both sides, **external zones** on both sides, **route** (shared VR or Next VR static routes), **security policy in both vsys**.

### Using separate virtual routers

```text
Network > Virtual Routers > vr-tenantA > Static Routes
Name   Destination    Interface  Next Hop        Next VR / Type
toB    10.20.0.0/24   (none)     vr-tenantB      next-vr
```

Select **Next Hop = Next VR** and pick the other virtual router. Create the mirror route in the other router for the return path.

## Shared gateway

A **shared gateway** (**Device > Shared Gateways**) lets multiple vsys share a **single external interface and IP address**, typically the internet-facing link.

* The shared gateway has its own **interface** (the shared external port) and its own **zone**, and one virtual router routes traffic for all vsys through it. A shared gateway is always visible to every vsys and appears as `sg<ID>`. The interface is placed in the gateway's zone, not a vsys' zone.
* Each vsys that uses it needs an **external zone** pointing at the shared gateway, plus normal security policy from its internal zone to that external zone.
* **Security policy and App-ID are not evaluated between a vsys and the shared gateway.** Policy is evaluated on the vsys side. The shared gateway supports **NAT** and **PBF** but not Security, DoS, QoS, Decryption, Application Override or Authentication policy of its own.
* Each vsys usually has its own **virtual router** with a default route whose next hop type is **Next VR** pointing to the shared gateway's router; the gateway's router has the real default route to the ISP and return routes back to each vsys.
* NAT is commonly done on the shared gateway side so all tenants' traffic exits behind the shared IP. (Overlapping tenant addresses need NAT before reaching the gateway.)

> **Real world:** The shared gateway is for conserving public IPs and sharing one ISP link. If tenants are required to keep separate internet links or separate public IPs, do not use it; give each vsys its own external interface instead.

### Shared gateway quick map

```text
vsys1 zone trust1  ->  vsys1 external zone to-gw  \
                                                    >  Shared gateway (zone shared-untrust, ethernet1/1, 203.0.113.2/24) -> ISP
vsys2 zone trust2  ->  vsys2 external zone to-gw  /
```

Troubleshooting checks:

* `show routing route` with `target-vsys` set to the vsys, to see the Next VR default.
* `show session all` in each vsys to see both session halves.
* `test security-policy-match from trust1 to to-gw source 10.10.0.5 destination 198.51.100.10 protocol 6 destination-port 443` inside the right vsys.

## Panorama and vsys

Vsys definitions, external zones, shared gateways and per-vsys policy are all **template** (network/device) and **device-group** (policy/objects) material. Device groups target individual vsys of a multi-vsys firewall (each vsys appears as a separate target in the device group), so one firewall can have several vsys in different device groups.

## Lab it yourself

1. On a multi-vsys firewall create vsys1 and vsys2, each with a Layer 3 interface (`ethernet1/2`, `ethernet1/5`) and **one shared virtual router**.
2. Tick Visible Virtual Systems both ways, add external zones, add the two security rules.
3. Ping from a host behind vsys1 to a host behind vsys2. Run `show session all filter` in each target-vsys to see two sessions.
4. Replace the shared router with two virtual routers and use Next VR routes.
5. Break it one step at a time (untick visibility, delete the route, remove a security rule) and note the symptom for each.

## Key takeaways

* Inter-vsys traffic that stays inside the box uses external zones in both vsys; visibility must be set in both directions for a two-way design.
* No policy is required between external zones; policy is internal zone to external zone in each vsys.
* One shared virtual router makes inter-vsys routing automatic; separate routers need Next VR static routes both ways.
* Inter-vsys traffic creates a session in each vsys and may not traverse more than two vsys or shared gateways.
* A shared gateway gives many vsys one external interface and IP; vsys reach it through external zones.
* The shared gateway supports NAT and PBF but does not run its own security policy.
* Overlapping addresses need separate routers and NAT, not a shared router.
