## What a virtual system is

A **virtual system (vsys)** is a logically separate firewall inside one physical or virtual PAN-OS device. Each vsys has its own:

* Security, NAT, decryption, QoS, PBF, authentication and DoS policy rule bases
* Zones and interfaces (each interface belongs to one vsys)
* Objects (addresses, services, profiles) scoped to that vsys
* Administrators (vsysadmin), log settings, and User-ID configuration
* Optionally its own resource limits, such as sessions and rules

What it does **not** have: its own dataplane, its own PAN-OS version, or its own management interface. All vsys share the device's hardware, software and management plane. Use vsys for **tenant separation, department separation, overlapping IP space**, or to give different administrators different scopes on one box.

> **Exam tip:** Virtual systems are a *policy and administration* boundary. They are not a performance boundary unless you set **resource limits**.

## Enabling multi-vsys

1. **Device > Setup > Management > General Settings**: tick **Multi Virtual System Capability** and commit. After this, the Device tab gains **Virtual Systems**, **Shared Gateways** and a **Location** selector (vsys1, vsys2, Shared).
2. Platform support varies: some models support multi-vsys out of the box with a base number of vsys, others need an additional license for more. Check the platform specification sheet; do not assume.

```text
PA-HQ> show system info | match multi-vsys
multi-vsys: on
```

On a multi-vsys firewall the CLI can target a vsys:

```text
PA-HQ> set system setting target-vsys vsys2
PA-HQ> show session all
```

Operational commands then run in the context of `vsys2` until you reset the target with `set system setting target-vsys none`.

> **Real world:** On Panorama, multi-vsys is a **template** setting (Multi Virtual System Capability on the template's Device > Setup > Management), and the vsys objects you define in the template then appear to every firewall in the stack. A template for single-vsys firewalls must not enable it.

## What belongs to a vsys

Open **Device > Virtual Systems > Add**.

| Tab / field | Purpose |
|-------------|---------|
| **ID / Name** | `vsys2`, `Tenant-A` (the display name; the ID cannot change) |
| **General > Interfaces, VLANs, Virtual Wires, Virtual Routers, Visible Virtual Systems** | The objects assigned to this vsys (see below) |
| **Allow forwarding of decrypted content** | Lets the vsys send decrypted traffic out to a mirror/forwarding target |
| **Resource** | Per-vsys limits: **Sessions**, **Security Rules**, **NAT Rules**, **Decryption Rules**, **Site to Site VPN tunnels**, **GlobalProtect tunnels**, and so on |

### Interfaces and zones

* An interface can be assigned to **one** vsys. The vsys then owns it and its zone. You can still split one physical port across vsys with **subinterfaces** (each subinterface assigned to its own vsys).
* Zones belong to a vsys. Two vsys can both have a zone named `trust` and they are unrelated.
* When you first create a vsys with interfaces, you must **create a zone** for the interface in that vsys; the interface is not usable until it is in a zone.

```text
PA-HQ# set network interface ethernet ethernet1/5 layer3 ip 10.20.0.1/24
PA-HQ# set vsys vsys2 import network interface ethernet1/5
PA-HQ# set vsys vsys2 zone trust2 network layer3 ethernet1/5
PA-HQ# set vsys vsys2 import network virtual-router vr-tenant2
PA-HQ# commit
```

The `import network` statements are what the GUI does for you when you pick the interface and virtual router in the vsys' General tab.

> **Watch out:** Moving an interface from vsys1 to vsys2 deletes it from its old zone. Zones and policy that referenced it in vsys1 stop matching, so plan a window.

### Virtual routers and logical routers

* **Virtual routers** (legacy engine) and **logical routers** (Advanced Routing Engine, covered in 1.4) are device-level routing instances. A vsys is **assigned** one or more routers. Several vsys can share one router, which is how inter-vsys traffic routes without extra static routes.
* **Separate router per vsys** gives complete routing isolation and lets tenants use **overlapping address space**; the price is that traffic between them needs explicit routes (see the next lesson).
* An interface attached to a vsys must also be attached to a router that is assigned to that vsys for Layer 3 forwarding.
* The ARE (logical routers) and legacy engine are mutually exclusive at the device level: the firewall runs one or the other. CLI differs: `show routing route` for virtual routers, `show advanced-routing route` for logical routers.

> **Exam tip:** "Two tenants must use the same 10.0.0.0/24 subnet" is the stock trigger for **separate virtual routers**, which are the isolation that makes overlapping addresses possible. They can only coexist if they are never routed between each other without NAT.

## Administration and per-vsys settings

* **vsysadmin** accounts are bound to one or more vsys and see a vsys-scoped GUI (no Device-wide settings, no network interfaces).
* Per-vsys services: **User-ID**, **Authentication Portal**, **log forwarding / Device > Log Settings**, **server profiles**, and **service routes** can be customised per vsys (Device > Setup > Services > Virtual Systems tab). Use per-vsys service routes when two tenants need separate DNS, syslog or authentication servers reached from different source interfaces.
* **Shared** location: objects in *Shared* are visible in every vsys. A shared object is overridden by a vsys object with the same name (a shadow warning appears).
* Log settings and Security policy hit counts are per vsys; the **Monitor** tab shows the selected vsys.

## Limits and sessions

Resource limits (**Device > Virtual Systems > Resource**) cap per-vsys consumption of sessions, rules, VPN tunnels and similar. Defaults and maximums differ by platform, so read the model's specification sheet rather than memorising numbers. `show session info` reports the session table; set `target-vsys` first to work in one tenant's context.

## Lab it yourself

On a VM-Series or hardware firewall that has multi-vsys capability:

1. Enable Multi Virtual System Capability and commit.
2. Create `vsys2`, assign `ethernet1/5`, a new virtual router and a new zone.
3. Create an administrator with the `vsysadmin` role bound to `vsys2` only. Log in and note the missing **Network > Interfaces** edit rights and Device-level settings.
4. Add an object named `web` in Shared and another named `web` in vsys2 with a different IP, and read the warning.
5. Use `set system setting target-vsys vsys2` and compare `show session all` with the default context.

## Key takeaways

* A vsys has its own policy, zones, objects, admins and (optionally) resource limits, but shares the dataplane and PAN-OS version.
* Multi-vsys must be enabled under Device > Setup > Management, and a Panorama template must enable it separately.
* An interface belongs to exactly one vsys; subinterfaces let one port serve several vsys.
* Separate routers per vsys give routing isolation and allow overlapping IP space; a shared router makes inter-vsys routing simple.
* Zones are vsys-scoped; policy is zone-to-zone inside the vsys.
* vsysadmin roles are limited to assigned vsys; Shared objects are visible everywhere.
* Resource limits (sessions, rules and so on) stop a tenant from consuming the whole box.
