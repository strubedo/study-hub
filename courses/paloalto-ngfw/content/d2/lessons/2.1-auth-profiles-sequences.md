## Authentication profiles

An **authentication profile** (**Device > Authentication Profile**, or in a Panorama template) tells the firewall *how and where* to verify a username and password. It is a reusable object. The same profile type is consumed by many features:

* Administrator login to the web UI, SSH and API (**Device > Setup > Management > Authentication Settings**, or per account)
* **GlobalProtect** portals and gateways
* **Authentication Portal** (captive portal) and **Authentication policy** rules (including MFA)
* Explicit web proxy authentication (see lesson 2.7)

### Profile types

| Type | Notes |
|------|-------|
| **None** | No authentication check (used by features that only need the group list) |
| **Local Database** | Users and groups defined in the firewall's own database (Device > Local User Database) |
| **RADIUS** | Server profile under Device > Server Profiles > RADIUS; supports Access-Challenge, so it can carry MFA |
| **TACACS+** | Server profile; TACACS+ VSAs for admin roles |
| **LDAP** | Server profile (base DN, bind DN, SSL/TLS); password is verified by an LDAP bind |
| **Kerberos** | Server profile (realm, domain, KDC); *or* **Kerberos single sign-on** with a keytab for transparent browser login |
| **SAML** | Needs a **SAML Identity Provider server profile** (IdP metadata/certificate); the user is redirected to the IdP |
| **Cloud Authentication Service** | Uses the Cloud Identity Engine's cloud authentication; the profile points at the CIE tenant and identity provider |

### Tabs worth knowing

* **Authentication tab**: Type, Server Profile, **Login Attribute** (LDAP: `sAMAccountName` or `userPrincipalName`), **Password Expiry Warning**, **User Domain** and **Username Modifier**, and Kerberos SSO realm/keytab.
* **Factors tab**: the MFA vendor server profiles to chain after the first factor (enable **Enable Additional Authentication Factors**).
* **Advanced tab**: the **Allow List** and the lockout settings.

> **Exam tip:** A user not in the profile's **Allow List** is rejected *even if the password is correct*. The default allow list is `all`. Entries can be individual users or groups that the firewall already knows from group mapping (or the local database).

### Account lockout

On the Advanced tab:

| Setting | Meaning |
|---------|---------|
| **Failed Attempts** | Consecutive failures before lockout (0 to 10; 0 means unlimited attempts, so no lockout) |
| **Lockout Time** | Minutes the account stays locked (0 to 60; default 0) |

Set **both** to non-zero values. The web interface help warns that Failed Attempts is ignored when Lockout Time is left at 0 (and Lockout Time is ignored when Failed Attempts is 0), so no lockout happens, although the same page also describes a 0 lockout time as locked until an administrator unlocks the account. Do not rely on a 0 lockout time; it is documented inconsistently. The docs recommend 5 or fewer attempts and a lockout of at least 30 minutes.

Lockout is per profile and per user, and counts failures against that profile.

### Username Modifier and domains

Many directories expect `user@example.com` or `EXAMPLE\user`, but users type a bare name. The **User Domain** and **Username Modifier** fields adapt what is sent upstream:

| Modifier | Sent to the server |
|----------|--------------------|
| `%USERINPUT%` (default) | Exactly what the user typed |
| `%USERDOMAIN%\%USERINPUT%` | `EXAMPLE\jsmith` |
| `%USERINPUT%@%USERDOMAIN%` | `jsmith@example.com` |

If the user already typed a domain, the firewall uses the typed domain instead of the configured one (it extracts it for sequence/domain matching). Do not stack a domain on top of one the user typed.

## Authentication sequences

An **authentication sequence** (**Device > Authentication Sequence**) is an **ordered list of authentication profiles**. The firewall tries them top to bottom and stops at the first success; if every profile fails, authentication fails.

Typical reasons for a sequence:

* Users live in different directories (local AD plus a partner LDAP, or AD plus a local-database fallback).
* A **fallback** for outages: RADIUS first, then a local database account.
* Multiple domains or forests, each with its own profile.

The sequence has one extra option: **Use domain to determine authentication profile**. When checked, if the user types `EXAMPLE\jsmith` or `jsmith@example.com`, the firewall strips the domain and selects the profile whose **User Domain** matches. If nothing matches (or no domain was typed), it falls back to trying the list in order.

> **Watch out:** A sequence is only a list. Allow-list and lockout are evaluated **per profile in the sequence**, so a user can be accepted by one profile and ignored by another. If the user does not appear in a profile's Allow List, that profile fails and the next one is tried.

### Where a sequence is accepted

Anywhere an authentication profile is accepted: admin Authentication Settings, GlobalProtect, Authentication Portal, and Authentication policy rules (Authentication Enforcement objects reference a profile or sequence). Not every field accepts a sequence in every release; read the dropdown on your PAN-OS.

## Configuring and testing

```text
PA-HQ# set shared server-profile ldap AD-LDAP ldap-type active-directory base "DC=example,DC=com" bind-dn "svc-pan@example.com" ssl yes server dc1 address 10.0.50.10 port 636
PA-HQ# set shared authentication-profile AD-Users method ldap server-profile AD-LDAP
PA-HQ# set shared authentication-profile AD-Users method ldap login-attribute sAMAccountName
PA-HQ# set shared authentication-profile AD-Users allow-list [ Domain-Users ]
PA-HQ# set shared authentication-profile AD-Users lockout failed-attempts 5 lockout-time 15
PA-HQ# set shared authentication-sequence Corp-Seq authentication-profiles [ AD-Users Local-Fallback ]
PA-HQ# commit
```

Use `?` completion in configure mode to confirm exact keywords on your release.

```text
PA-HQ> test authentication authentication-profile AD-Users username jsmith password
Enter password :
Target vsys is not specified, user "jsmith" is assumed to be configured with a shared auth profile.
Do allow list check before sending out authentication request...
name "jsmith" is in group "all"
Authentication to LDAP server at 10.0.50.10 for user "jsmith"
Egress: 10.0.50.1
Authentication succeeded for user "jsmith"
```

For deeper troubleshooting, tail `authd.log`:

```text
PA-HQ> tail follow yes mp-log authd.log
```

On Panorama, authentication profiles live in a **template** (or Shared in the template stack), not in a device group, because they are device settings. Server profiles are in the template too.

## Choosing the method for a use case

| Requirement | Pick |
|-------------|------|
| Admins log in with AD password, role by local account | LDAP (or Kerberos) profile on local accounts |
| Admin role delivered by the server | RADIUS/TACACS+ with VSAs, or SAML with attributes |
| Browser SSO to captive portal | Kerberos SSO, or SAML |
| MFA | RADIUS challenge, SAML IdP with MFA, or MFA vendor in the **Factors** tab |
| Two directories, one login box | Authentication **sequence** |
| Outage fallback | Sequence with a **Local Database** profile last |

> **Real world:** Put the **local database** profile last in a sequence for admin login. An attacker brute-forcing a user name will also be tried against the local database, so keep local accounts few, with strong passwords and lockout.

## Lab it yourself

1. Use a Linux host with OpenLDAP or a free Windows eval AD. Create an LDAP server profile, then an authentication profile with an Allow List of one group.
2. Run `test authentication` for a user in the group and a user outside it. Note the error from the allow list.
3. Create a second profile using the local database. Build a sequence with LDAP first, local second. Stop the LDAP server and confirm a local account still logs in to the web UI through the sequence.
4. Set the lockout to 3 attempts and observe the lockout message.

## Key takeaways

* An authentication profile is reusable: admin login, GlobalProtect, Authentication Portal, Authentication policy and the web proxy all use it.
* The Allow List (default `all`) rejects users outside it even with a correct password.
* Failed Attempts and Lockout Time are set on the profile; set both non-zero, because a zero in either one means no effective lockout.
* Username Modifier and User Domain adapt the name sent to the server.
* A sequence is an ordered list of profiles; first success wins; "use domain to determine authentication profile" selects the profile by typed domain.
* Kerberos SSO, SAML and Cloud Authentication Service are profile types too; SAML needs an IdP server profile.
* Authentication profiles are device settings, so on Panorama they belong in templates.
