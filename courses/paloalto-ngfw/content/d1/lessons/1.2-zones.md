## Zone fundamentals

A **security zone** is a logical group of one or more interfaces. Security policy is written *between zones*, not between interfaces. An interface can be in only one zone, and a zone can contain only interfaces of its own type (**Network > Zones**).

| Zone type | Accepts interfaces | Notes |
|-----------|--------------------|-------|
| **Tap** | Tap | Passive monitoring |
| **Virtual Wire** | vwire | Both wire ends need their own zone assignments (may be the same zone) |
| **Layer 2** | L2 | |
| **Layer 3** | L3, loopback, VLAN, tunnel | Most common |
| **Tunnel** | Used by tunnel content inspection | Zone for traffic decapsulated by Tunnel Inspection policy |
| **External** | Interfaces in another virtual system | Used only with VSYS to reach another vsys |

Zone settings that matter: **Log Setting** (forward zone-based logs), **Zone Protection Profile**, **Enable User Identification** (User-ID for traffic *entering* this zone), **Enable Packet Buffer Protection**, and the optional **User-ID ACL include/exclude lists** (which subnets User-ID should map).

## Default behaviour

* **Intrazone** traffic (same source and destination zone) is **allowed** by the default `intrazone-default` rule.
* **Interzone** traffic is **denied** by `interzone-default`.
* Both default rules log nothing until you enable logging on them (override them under Policies > Security).
* Return traffic is handled by the session; you do not need a rule for it.

> **Exam tip:** A rule with source zone `trust` and destination zone `trust` is intrazone. A "Universal" rule type (default) matches both intrazone and interzone; set the rule type to *interzone* or *intrazone* to restrict it.

## Zone Protection profile

Created under **Network > Network Profiles > Zone Protection** and attached to a **zone** (it protects traffic *ingressing* the zone). It is not security policy: it acts before policy lookup and primarily on new connections.

| Section | Defends against | Key settings |
|---------|-----------------|--------------|
| **Flood Protection** | SYN, ICMP, ICMPv6, UDP, other-IP floods | Alarm rate, Activate rate (start dropping), Maximum rate (drop all). SYN can use **Random Early Drop** or **SYN Cookies** |
| **Reconnaissance Protection** | TCP/UDP port scans, host sweeps | Interval and threshold, action: allow, alert, block, block-ip (source, source-and-destination) |
| **Packet Based Attack Protection** | Malformed or spoofed packets | IP drop (spoofed, strict source routing, fragmented), TCP drop (no SYN-flag mid-stream, mismatched overlapping segment), ICMP drop (large ICMP, ping-of-death), IPv6, ICMPv6 |
| **Protocol Protection** | Non-IP protocols on L2/vwire | Exclude/include lists by Ethertype |
| **Ethernet SGT Protection** | Cisco Security Group Tag frames | Where applicable |

Points to remember:

* Flood protection rates are measured in **packets per second** and are per zone. Pick thresholds from observed baselines; setting them too low drops legitimate bursts.
* **SYN cookies** let the firewall answer the SYN itself; **Random Early Drop** simply drops a growing share of SYNs once the activate rate is exceeded. SYN cookies protect servers better but cost firewall CPU.
* **DoS Protection** policies and profiles (Policies > DoS Protection) are a separate, rule-based tool that protects specific hosts (classified by source/destination), for example per-IP session limits. Zone protection is coarser and does not track per-source flows.
* Zone protection does not inspect application content; that is Security profiles.

```text
PA-HQ# set network profiles zone-protection-profile ZP-untrust flood tcp-syn enable yes
PA-HQ# set network profiles zone-protection-profile ZP-untrust flood tcp-syn red alarm-rate 10000
PA-HQ# set zone untrust network zone-protection-profile ZP-untrust
PA-HQ# commit
```

Detected scans and sweeps appear as threat log entries generated by the zone protection profile. Verify with `show zone-protection zone untrust` and `show counter global filter delta yes severity drop`.

## Design guidance

* Put interfaces with the same trust level in one zone; use more zones to enforce different policy, not for every VLAN.
* Always attach a Zone Protection profile to Internet-facing zones; use the Palo Alto best-practice flood and recon settings as a start.
* Enable User-ID on **internal** zones, not the untrust zone.
* For GlobalProtect and VPN, give the tunnel interfaces their own zones so policy can distinguish remote users and sites.

## Key takeaways

* Policy is zone-to-zone; an interface is in exactly one zone and the zone type must match the interface type.
* Intrazone is allowed by default; interzone is denied by default.
* The Zone Protection profile attaches to the ingress zone and protects against floods, reconnaissance, packet-based attacks and non-IP protocols.
* Flood thresholds are alarm, activate, maximum; SYN uses RED or SYN cookies.
* DoS Protection policy (per host/classified) is different from zone protection (per zone).
* Enable User-ID on the zone where the users originate traffic.
