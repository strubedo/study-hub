## Why quantum-resistant IPSec?

A "harvest now, decrypt later" attacker records IKE and ESP traffic today and decrypts it once a cryptographically relevant quantum computer exists. Classic Diffie-Hellman key exchange is vulnerable to Shor's algorithm, so the IKEv2 key exchange has to be strengthened. PAN-OS documentation covers two mechanisms, both **IKEv2 only**:

| | RFC 8784 (PPK) | RFC 9242 + RFC 9370 (hybrid keys) |
|-|----------------|-----------------------------------|
| Idea | Mix an out-of-band **post-quantum pre-shared key** into the IKEv2 key derivation | Add **additional key exchange rounds** using classical and post-quantum KEMs |
| PAN-OS | **11.1 or later** | **11.2 or later** |
| Crypto upgrade needed? | No | Yes (new algorithms) |
| Resource use | Low | Higher |
| GUI | IKE Gateway > Advanced Options > IKEv2 > **PQ PPK** | IKE Gateway > Advanced Options > IKEv2 > **PQ KEM**; IKE Crypto and IPSec Crypto profiles > Advanced Options > Additional Key Exchange rounds |

The documentation presents RFC 8784 as the easiest first step and RFC 9370 as the second step, and the two can be used together for defense in depth.

## RFC 8784 PPK configuration

1. IKE Gateway version **IKEv2 only** (or IKEv2 preferred, but the VPN must negotiate IKEv2).
2. Advanced Options > IKEv2 > PQ PPK > **Enable Post-Quantum Pre-Shared Key (PPK)** (disabled by default).
3. Choose the **Negotiation Mode**:
   * **Preferred** (default): try PQ PPK; if the peer does not support RFC 8784, fall back to classical key exchange.
   * **Mandatory**: the peer must support RFC 8784; otherwise the firewall aborts. Use it when you know the peer supports PPK.
4. Add and activate up to **10** PQ PPKs. Each is a **KeyID** (unique string of up to 31 characters) plus a **PPK Secret**. Only the KeyID crosses the wire; the secret is shared out-of-band or pushed by Panorama and must be identical on both peers.
5. With several active PPKs the firewall picks one at random. A KeyID missing on the responder, or a secret mismatch, aborts the connection. Do not define more PPKs than the peer supports.
6. Dynamic-peer IKE gateways sharing a local IP must share the same PPK setting and negotiation mode.

## RFC 9242 / 9370 hybrid keys

* IKE Gateway > Advanced Options > IKEv2 > **PQ KEM** > **Enable Post-Quantum Key Exchange** (disabled by default); optionally **Block IKEv2 if vulnerable cipher is used**, which blocks *new* peerings when a vulnerable KEM is configured; existing tunnels continue.
* **IKE Crypto profile**: set a strong classic exchange (documentation recommends DH group 20 or higher, AES-256-GCM, with frequent rekey), then Advanced Options > **Additional Key Exchange** rounds. RFC 9370 permits up to **seven** additional rounds, in addition to the default one (eight total). Rounds can be left blank or **None** (skipped). The order of KEMs in a round sets preference; put the strongest first.
* **IPSec Crypto profile**: Advanced Options with up to seven Additional Key Exchange rounds, **one PQC KEM per round**. Both peers must use the same KEM and strength per round, otherwise rekey fails.
* Documented algorithm families include ML-KEM, BIKE, HQC and Classic McEliece. Documentation recommends a security strength equivalent to Level 3 or higher for long-lived data. The documented example uses DH group 21 as the default exchange, ML-KEM-768 in round 1 and BIKE-L3 in round 2.
* Enable **IKEv2 fragmentation**, because PQC keys enlarge IKEv2 packets.
* Keep configuration identical on both sides because implementations vary.

> **Exam tip:** PPK = pre-shared secret, out of band, 11.1+, "Preferred" falls back, "Mandatory" does not. Hybrid = additional KEM rounds, 11.2+, needs IKEv2 fragmentation. Both need IKEv2.

> **Real world:** Treat the exact list of KEM names offered in the GUI for your release as something to check in the release's admin guide; this lesson only teaches the behaviours the documentation states. For example, the 11.1 CLI reference lists the lattice KEM as `kyber-512/768/1024` where later documentation uses the ML-KEM names.

## GRE tunnels

Generic Routing Encapsulation (IP protocol 47) carries any L3 payload in a simple tunnel with no encryption. Network > **GRE Tunnels**:

| Field | Meaning |
|-------|---------|
| Interface | Local L3 or loopback interface sourcing the tunnel |
| Local address | IP on that interface |
| Peer address | Remote tunnel endpoint |
| Tunnel interface | `tunnel.N`, in a zone and router |
| TTL | Outer TTL, default 64 |
| Copy ToS | Copy inner ToS to outer header |
| Enable Keepalive | Disabled by default. When enabled: interval 10 s, retry 3, hold timer 5 (defaults) |

The CLI hierarchy is `set network tunnel gre <name> ...` (use `?` completion on the firewall for the exact sub-nodes in your release). The GUI fields above map to it one for one.

* Needs a security policy allowing GRE between the outer zones (application `gre`) and policy for the inner traffic in the tunnel zone.
* GRE does not encrypt; for confidentiality send GRE inside IPSec or use IPSec tunnel mode directly.
* A **terminated** GRE tunnel (above) is a configured tunnel interface. **Transit** GRE that merely crosses the firewall is handled by **Tunnel Content Inspection** (Policies > Tunnel Inspection), which inspects the inner payload and can put it in a Tunnel zone.
* Verification: `show interface tunnel.2`, `show running tunnel flow all`, and `show routing route`.

## Key takeaways

* Quantum-resistant IPSec requires IKEv2.
* RFC 8784 PPK: 11.1+, up to 10 PPKs, KeyID up to 31 characters, Preferred (default) vs Mandatory.
* RFC 9242/9370: 11.2+, up to 7 additional key exchange rounds, ML-KEM and others, IKEv2 fragmentation recommended; IPSec profile allows one PQC KEM per round.
* PQ options are off by default; peers must match.
* GRE is unencrypted, protocol 47, with optional keepalive; terminating GRE differs from inspecting transit GRE.
