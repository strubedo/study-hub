## Building blocks

A route-based site-to-site VPN needs five objects plus routing and policy:

| Step | GUI path | Notes |
|------|----------|-------|
| 1. IKE Crypto profile | Network > Network Profiles > IKE Crypto | DH group, encryption, authentication (hash), key lifetime (**phase 1 / IKE SA**) |
| 2. IPSec Crypto profile | Network > Network Profiles > IPSec Crypto | ESP or AH, encryption, authentication, optional DH group (PFS), lifetime (**phase 2 / IPSec SA**) |
| 3. IKE Gateway | Network > Network Profiles > IKE Gateways | Version, local interface/IP, peer address (static, FQDN, dynamic), authentication (pre-shared key or certificate), identities, IKE crypto, DPD/liveness |
| 4. Tunnel interface | Network > Interfaces > Tunnel | Zone and router assignment |
| 5. IPSec Tunnel | Network > IPSec Tunnels | IKE gateway, IPSec crypto, tunnel interface, tunnel monitor, proxy IDs |
| 6. Routing | | Static route to remote subnet via `tunnel.N`, or a dynamic protocol over the tunnel |
| 7. Policy | | Rules between the internal zone and the `vpn` zone in both directions |

```text
PA-HQ# set network ike gateway GW-Branch1 protocol version ikev2
PA-HQ# set network ike gateway GW-Branch1 local-address interface ethernet1/1
PA-HQ# set network ike gateway GW-Branch1 peer-address ip 198.51.100.2
PA-HQ# set network ike gateway GW-Branch1 authentication pre-shared-key key <secret>
PA-HQ# set network tunnel ipsec Tun-Branch1 auto-key ike-gateway GW-Branch1
PA-HQ# set network tunnel ipsec Tun-Branch1 auto-key ipsec-crypto-profile Suite-B-GCM-128
PA-HQ# set network tunnel ipsec Tun-Branch1 tunnel-interface tunnel.1
PA-HQ# set network virtual-router default routing-table ip static-route Branch1-LAN destination 10.20.0.0/16 interface tunnel.1
```

## IKE details

* **IKEv1**: phase 1 main mode (default) or aggressive; phase 2 quick mode. **IKEv2**: single exchange pair, supports configuration payload, liveness check, and is required for quantum-resistant features. The gateway version can be IKEv1 only, IKEv2 only, or **IKEv2 preferred** (falls back to IKEv1).
* **Ports**: UDP 500 for IKE, UDP 4500 for NAT traversal; ESP is IP protocol 50. **NAT-T** is enabled on the gateway when a NAT sits between the peers.
* **Identification**: local and peer ID types (IP address, FQDN, user FQDN, key ID, distinguished name). Mismatched IDs are a common cause of failure behind NAT or with dynamic peers.
* **Dead Peer Detection** (IKEv1) and **Liveness Check** (IKEv2) detect a lost peer and tear down SAs.
* **Passive mode**: the gateway only responds, never initiates (useful for hub or dynamic-peer sites).
* **Default lifetimes** in the stock profiles: IKE 8 hours, IPSec 1 hour. Lifetimes do not have to match between peers, but mismatched lifetimes can cause rekey problems, so keep them aligned.
* **Certificate authentication**: the local certificate and a certificate profile validating the peer.
* **Proxy IDs** (IPSec Tunnel > Proxy IDs) define local and remote networks for **policy-based peers** (for example, a Cisco ASA with crypto ACLs). For route-based peers with `0.0.0.0/0` selectors they can be omitted; for IKEv2, the firewall sends the proxy ID as traffic selectors, and a mismatch fails phase 2.

## Tunnel monitor

IPSec Tunnel > **Enable Tunnel Monitor**: destination IP (usually the peer's tunnel IP), a **monitor profile** (Network > Network Profiles > Monitor) with interval (default 3 s), threshold (default 5 missed) and action: **wait-recover** (keep tunnel, keep trying) or **fail-over** (take the tunnel interface's routes out so the secondary path is used). Use fail-over together with a backup route or tunnel.

## Verification and troubleshooting

```text
PA-HQ> show vpn ike-sa gateway GW-Branch1
PA-HQ> show vpn ipsec-sa tunnel Tun-Branch1
PA-HQ> show vpn flow name Tun-Branch1
PA-HQ> test vpn ike-sa gateway GW-Branch1
PA-HQ> test vpn ipsec-sa tunnel Tun-Branch1
PA-HQ> less mp-log ikemgr.log
PA-HQ> debug ike global on debug
```

Work through the layers: (1) is UDP 500/4500 reaching the firewall (security policy for the IKE application, `ipsec`, and NAT exemption)? (2) Phase 1 proposals match? (3) Phase 2 proposals and proxy IDs match? (4) Route for remote subnet points to `tunnel.N`? (5) Policy permits both zones? (6) MTU/MSS: consider TCP MSS adjustment on the L3 interface (or a lower tunnel MTU) when large packets stall.

`ikemgr.log` records the negotiation. Look for a phase-1 failure that names no matching gateway configuration (peer IP or ID does not match any IKE gateway) or a phase-2 failure that reports no acceptable proposal (crypto mismatch). Exact message wording varies by release.

> **Exam tip:** Phase 1 up, phase 2 down is almost always crypto/PFS mismatch or proxy IDs/selectors. Both phases up but no traffic: routing, policy or NAT.

## Dynamic routing over the tunnel

Assign an IP to each `tunnel.N` (a /30) or use an unnumbered tunnel referencing a loopback, enable OSPF or BGP on the tunnel interface, and create policy for the routing protocol. For BGP over IPSec, the neighbor address is the remote tunnel IP.

## Key takeaways

* Route-based VPN = IKE gateway + IKE crypto + IPSec crypto + IPSec tunnel + tunnel interface/zone + route + policy.
* IKE = phase 1, IPSec = phase 2; IKEv2 is required for post-quantum features.
* NAT-T uses UDP 4500; proxy IDs matter for policy-based peers.
* Tunnel monitor with fail-over withdraws the tunnel's routes.
* Use `show vpn ike-sa`, `show vpn ipsec-sa`, `test vpn ...` and `ikemgr.log`.
