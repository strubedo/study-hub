## Requirements and HA links

Two firewalls form an HA pair when they have the **same model, PAN-OS version (and content/app version for a clean sync), licenses, interface types in the HA-relevant slots, and VSYS capability**. Configure under **Device > High Availability**.

| Link | Purpose | Notes |
|------|---------|-------|
| **HA1 (control)** | Hello, heartbeat, HA state, configuration sync, user and routing info | Layer 3. Clear-text TCP 28260/28769, encrypted TCP 28 (needs HA key export/import). Optional **HA1 backup** |
| **HA2 (data)** | Session and forwarding table sync (ARP, MAC, IPSec SAs) | Ethernet (Layer 2 reachable), IP (protocol 99) or UDP (port 29281). Optional **HA2 backup**; HA2 keep-alive |
| **HA3** | **Active/active only**: forwards packets to the session owner (asymmetric flows) | Layer 2 link (MAC-in-MAC encapsulation; no Layer 3 addressing or encryption); dedicate it, size it for the forwarded traffic and keep its MTU above the largest forwarded packet |
| **HA4** | Session cache synchronization between members of an **HA cluster** (NGFW clustering on supported platforms); also detects member connectivity failure with Layer 2 keepalives | Cluster designs only, with HA4 backup |
| Heartbeat backup | Keepalive sent over the management ports | Reduces split-brain risk |

Both firewalls use the same configuration (synced from HA1) except local items: management IP, HA settings, device priority, HA interface addressing.

> **Exam tip:** HA1 carries control, HA2 carries sessions, HA3 exists only in active/active. If a question mentions packet forwarding between peers for asymmetric routing, the answer is HA3.

## Active/passive

One firewall forwards traffic (**active**); the other (**passive**) syncs config and sessions and takes over on failure. Supported with **Layer 2, Layer 3 and virtual wire** deployments.

* Interface configuration is identical on both firewalls. On failover the new active firewall sends **gratuitous ARP** for its interface IPs, so neighbours learn the new MAC unless **virtual MAC** is used.
* **Passive link state**: `shutdown` (default; links down on the passive unit) or `auto` (link up but not forwarding). `auto` speeds failover when the passive side must have link up, but be careful in L3 with a switch that would see two active ports, and see the dynamic-routing note below.
* **Preemption**: when enabled on **both** peers, the higher-priority firewall (**lowest device priority number**) retakes the active role after recovery. Set a **preemption hold time** so a flapping peer does not cause repeated failovers. If preemption is off, the current active stays active.
* Dynamic routing with A/P: routing adjacencies exist only on the active firewall unless **graceful restart** is configured, which helps neighbours keep forwarding during failover.

## Active/active

Both firewalls forward traffic. Supported for **Layer 3 and virtual wire** interfaces (Layer 2 is an active/passive-only design), and typically used for asymmetric routing environments or to share load.

* Each firewall is device ID 0 or 1 and has its own **interface addresses**; a shared **floating IP** (or ARP load-sharing with a **virtual IP**) is used for the clients' default gateway.
* **Session owner** vs **session setup**: the owner handles Layer 7 (App-ID/Content-ID) processing; the setup firewall creates the session and NAT. Session owner defaults to the firewall that received the first packet, or the primary device. Session setup can be IP modulo, IP hash, primary device or first packet.
* Asymmetric return packets arriving at the other firewall go across **HA3** to the owner. Virtual MAC prevents ARP confusion with a floating IP.
* Dynamic routing: both firewalls peer independently; with floating IP, active-primary owns the address.
* Limitations: A/A requires **HA3**, has lower feature support (for example some features need the session to stay on one unit), and operational complexity is higher. Prefer A/P unless asymmetry is unavoidable.

| | Active/passive | Active/active |
|-|----------------|---------------|
| Forwarding | One unit | Both |
| Interface types | L2, L3, vwire | L3, vwire |
| Extra link | None | HA3 (HA4 only for clusters) |
| Addresses | Same on both | Unique per unit + floating/virtual |
| Complexity | Low | High |

## Election and states

The firewall with the **lower device priority number** is preferred. Typical states: `initial`, `tentative` (waiting), `passive`, `active` (or `active-primary`/`active-secondary` in A/A), `non-functional`, `suspended`.

Election in A/P: if preemption is off, the first firewall to become active stays active; if on, the priority decides. Failover events include link and path monitoring failures, HA1/hello loss, a dataplane or critical process failure, and a manual suspend.

```text
PA-A> show high-availability state
Group 1:
  Mode:  Active-Passive
  Local Information:
    Version: 1
    Mode: Active-Passive
    State: active
    Device Information:
      Management IPv4: 192.168.10.11/24
  Peer Information:
    Connection status: up
    State: passive
    Priority: 110
  Configuration Synchronization:
      Enabled: yes
      Running Configuration: synchronized
```

Useful commands: `show high-availability all`, `show high-availability link-monitoring`, `show high-availability path-monitoring`, `show high-availability control-link statistics`, `request high-availability state suspend` / `functional`, `request high-availability sync-to-remote running-config`.

> **Watch out:** `request high-availability sync-to-remote` copies from the *local* firewall to the peer. Running it on the wrong unit overwrites the good configuration.

## Config sync and commits

Commit on the active (or either) unit; the commit syncs to the peer when **Enable Config Sync** is on. Not synced: HA settings, management interface addressing, device priority. Upgrade: suspend or upgrade passive first, verify sessions, and fail over.

## Key takeaways

* HA1 control, HA2 data, HA3 A/A forwarding; keep HA1 and HA2 on dedicated links with backups.
* A/P supports L2, L3, vwire; A/A supports L3 and vwire and needs HA3.
* Lower device priority wins; preemption must be enabled on both and benefits from a hold time.
* Passive link state auto vs shutdown trades failover speed for network visibility.
* A/A has session owner and session setup roles, floating IP, and virtual MAC.
* `show high-availability state` is the first command in HA troubleshooting.
