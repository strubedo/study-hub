## What "convergence" means for BGP on FortiGate

After a failure, traffic is back on a working path only when three things have happened:

1. **Detection**: some mechanism notices the failure (link down, BFD, hold timer, DPD on the tunnel, SD-WAN health check).
2. **Propagation**: the routers that know send UPDATE/WITHDRAW messages, paced by each neighbor's `advertisement-interval`.
3. **Re-selection and installation**: every receiver reruns best-path selection and installs the new route in the RIB and kernel FIB; existing sessions then follow the new route (see the session lesson in 4.4).

Default BGP is slow at steps 1 and 2: a silent failure is detected only when the **180 s** hold timer expires, and updates to each neighbor are batched every **30 s**. Every knob below shortens one of those steps.

| Step | Knob | Default | Typical tuned value |
|---|---|---|---|
| Detect | `keepalive-timer` / `holdtime-timer` (global or per neighbor) | 60 / 180 s | e.g. 10 / 30 s (hold time is negotiated: the lower of both sides) |
| Detect | BFD (`set bfd enable` on the neighbor) | disabled | 250 ms x 3 = 750 ms with default BFD timers |
| Detect | `fast-external-failover` | enabled | Leave on: a directly connected eBGP session drops as soon as the link goes down |
| Detect | `link-down-failover` (neighbor) | disabled | Drop the session when the egress interface goes down |
| Propagate | `advertisement-interval` (neighbor or neighbor group) | 30 s (iBGP **and** eBGP) | 1 s on hub neighbor groups in SD-WAN designs |
| Reconnect | `connect-timer` | unset | 1 s in Fortinet SD-WAN examples, so spokes retry quickly |
| Keep forwarding during a restart | Graceful restart | disabled | Enable on HA clusters |
| Fewer paths to compute | Route reflectors, summaries | | Hubs as RRs; summarize toward spokes when ADVPN isn't used |

> **Exam tip:** In an SD-WAN overlay, the overlay itself is usually watched by **SD-WAN health checks** and **IPsec DPD**, and the routes resolve over several tunnels. Losing one tunnel then doesn't even need BGP to reconverge: the IKE route over that tunnel disappears and the recursive BGP routes simply lose a path. BGP timers matter most when the whole path to a peer (all tunnels, or the peer itself) is lost.

## BFD

BFD is a lightweight hello protocol that tells BGP, OSPF or static routes that a neighbor is gone, typically in under a second. FortiOS BFD runs in asynchronous mode only; **echo mode and authentication are not supported** for single-hop BFD on FortiGate (multihop templates support MD5).

Configuration is layered: each lower level overrides the one above.

```text
config system settings
    set bfd enable
    set bfd-desired-min-tx 250
    set bfd-required-min-rx 250
    set bfd-detect-mult 3
end
config system interface
    edit "port2"
        set bfd global
    next
end
config router bgp
    config neighbor
        edit "198.51.100.9"
            set bfd enable
        next
    end
end
```

- VDOM level (`config system settings`): `bfd` disable by default; timers default **250 ms / 250 ms / x3**.
- Interface level: `bfd {global | enable | disable}` (default `global`) plus per-interface timers.
- Protocol level: BGP `neighbor` → `set bfd enable`; OSPF → `set bfd enable` under `config router ospf` and `bfd` on the `ospf-interface` (default `global`); static routes → `set bfd enable` on the route, with a BFD neighbor under `config router bfd` → `config neighbor`.
- Multihop BFD (for example eBGP between loopbacks) uses `config router bfd` → `config multihop-template` with `src`/`dst` prefixes; when multihop BFD goes down the BGP session is reset and immediately retried.
- Both ends must run BFD. Verify with `get router info bfd neighbor` (OurAddress, NeighAddress, State UP/DOWN, Interface) and `get router info bfd requests` (which client asked for the session: `ct=08` is BGP, `04` OSPF, `02` static).

> **Watch out:** BFD over IPsec measures the tunnel, so the result depends on the tunnel's own health detection. For SD-WAN overlays, Fortinet relies on health checks and DPD for member health; BFD is most useful on directly connected eBGP peerings (ISP, data center core) and OSPF on the LAN.

## Graceful restart

Graceful restart (RFC 4724) lets a router's neighbors keep forwarding on its routes while its control plane restarts, for example during an HA failover where the new primary has to re-establish BGP. On FortiOS:

```text
config router bgp
    set graceful-restart enable
    set graceful-restart-time 120
    set graceful-stalepath-time 360
    set graceful-update-delay 120
    config neighbor
        edit "198.51.100.9"
            set capability-graceful-restart enable
        next
    end
end
```

| Setting | Default | Meaning |
|---|---|---|
| `graceful-restart` | disable | Enable GR capabilities on this router |
| `graceful-restart-time` | 120 s | Time the neighbors should wait for this router to come back |
| `graceful-stalepath-time` | 360 s | How long this router keeps a restarting neighbor's routes as stale |
| `graceful-update-delay` | 120 s | Route advertisement/selection delay after restart |
| neighbor `capability-graceful-restart` | disable | Advertise the GR capability to that neighbor |

Restarting manually: `execute router restart`. Stale routes show with `S` in the status codes of `get router info bgp network`.

For an **FGCP cluster**, routing runs only on the primary; graceful restart (BGP and OSPF `restart-mode graceful-restart`) together with session pickup keeps neighbors from tearing down routes during the failover. Both the FortiGate and the neighbor must support GR (the neighbor acts as helper).

## Route reflectors at scale

In an iBGP overlay the hubs are route reflectors for their spokes.

- Set `route-reflector-client enable` in the hub's neighbor group. `client-to-client-reflection` is enabled by default.
- With **two hubs reflecting the same spokes**, give them the same `cluster-id` if they are meant to be one redundant cluster (reflected updates with your own cluster ID are dropped as loops), or different IDs if each must also accept the routes the other reflects. Hub-to-hub routes (each hub's own DC prefixes) still need an iBGP session between the hubs.
- Reflectors don't change the next hop by default; `next-hop-self-rr enable` sets it to the hub for reflected routes.
- Additional paths (RFC 7911: `additional-path enable` and `additional-path-select` under `config router bgp`, plus `additional-path send|receive|both` and `adv-additional-path` on the neighbor or neighbor group) let a hub send several paths for one prefix, so spokes see alternatives instead of only the RR's single best. Fortinet uses this in ADVPN designs with several overlays.

Route reflection keeps the full mesh away (n spokes need n sessions per hub instead of n(n-1)/2), but every reflected change still has to reach every spoke. That is why `advertisement-interval` on the hub group matters so much.

## Use cases

| Requirement | Design |
|---|---|
| Sub-second failover between two ISPs that both speak BGP to the FortiGate | eBGP to both, BFD on both neighbors, `fast-external-failover` (default), local preference on the preferred ISP's inbound routes |
| Prefer ISP-A for inbound traffic | Outbound route map toward ISP-B with `set-aspath` prepend (`set-aspath-action prepend`), or MED toward a single ISP with two links |
| Hub-and-spoke SD-WAN with 300 spokes | Hub neighbor group + neighbor range on loopbacks, RR client, `advertisement-interval 1`, spokes `connect-timer 1`; overlay health by SD-WAN health checks |
| HA pair peering with a data-center core | Graceful restart enabled on the FortiGate and the core, session pickup, BFD with timers longer than the HA failover |
| Many spokes, no ADVPN, small tables | No RR; hub advertises a summary and a default with `capability-default-originate` |

> **Real world:** Aggressive BFD timers and graceful restart pull in opposite directions. If BFD declares the neighbor dead during an HA failover, the neighbor flushes routes before GR can help. Use BFD timers that tolerate the failover time, or rely on GR plus normal hold timers for HA peers.

## Lab it yourself

Inside the **FortiGate-VM trial** you can test BFD and timers on a single eBGP peering: port2 to a Cisco IOS router (`bfd interval 250 min_rx 250 multiplier 3`, `neighbor x fall-over bfd`), FortiGate neighbor `set bfd enable`, then shut the Cisco interface facing a switch (not the cable) and time the failover with and without BFD. Graceful restart needs a restarting peer that supports GR; an FRR container is the easiest helper. HA graceful restart needs two licensed FortiGates.

## Key takeaways

- Default BGP detection is the **180 s** hold timer; default update pacing is **30 s** per neighbor for iBGP and eBGP.
- BFD defaults: **250 ms tx, 250 ms rx, multiplier 3**; enable globally/per interface, then per neighbor; no echo mode or single-hop authentication on FortiGate.
- `get router info bfd neighbor` and `get router info bfd requests` verify BFD.
- Graceful restart: `graceful-restart enable` plus neighbor `capability-graceful-restart enable`; restart time **120 s**, stale path **360 s**, update delay **120 s**.
- Route reflectors (`route-reflector-client`) keep the remote next hop unless `next-hop-self-rr`; `cluster-id` matters with two reflectors.
- In SD-WAN overlays, health checks and recursive routing over several tunnels do most of the fast failover; BGP tuning matters when a whole peer is lost.
