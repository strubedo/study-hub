## Why BGP is the overlay protocol

Fortinet's SD-WAN designs run **iBGP between hubs and spokes** over the IPsec overlays. BGP scales to hundreds of peers with neighbor ranges, carries policy in attributes and communities, lets a hub reflect routes for ADVPN, and its routes can be tagged for SD-WAN rules. OSPF stays on the LAN. To design and troubleshoot those overlays you need the FortiOS BGP defaults cold, especially where they differ from IOS.

## Basic configuration

```text
config router bgp
    set as 65000
    set router-id 172.16.0.1
    config neighbor
        edit "172.16.0.254"
            set remote-as 65000
            set update-source "Branch-Lo"
        next
    end
    config network
        edit 1
            set prefix 10.1.1.0 255.255.255.0
        next
    end
    config redistribute "connected"
        set status enable
        set route-map "RM-LAN-ONLY"
    end
end
```

- `as` accepts asplain, asdot or asdot+; `as 0` disables BGP.
- A neighbor is identified by its IP; `remote-as` equal to the local AS makes it iBGP.
- `config network` advertises a prefix. With `network-import-check enable` (the global default) the prefix is advertised **only if a matching route exists in the routing table**, like the IOS `network` statement. Each network entry can override this with `network-import-check global|enable|disable`, and can point at a firewall address with `prefix-name` instead of a typed prefix.
- `config redistribute "<protocol>"` uses `route-map` (with a hyphen). In OSPF the same field is spelled `routemap`. Exam items like that detail.

## Defaults: FortiOS 7.6 versus IOS

From the 7.6.0 CLI Reference (`config router bgp` and `config neighbor`):

| Setting | FortiOS default | IOS default | Comment |
|---|---|---|---|
| `distance-external` | **20** | 20 | eBGP |
| `distance-internal` | **200** | 200 | iBGP |
| `distance-local` | **200** | 200 | Locally originated (aggregate/network) |
| `keepalive-timer` / `holdtime-timer` | **60 / 180** s | 60 / 180 | Per-neighbor values override |
| `advertisement-interval` (neighbor) | **30** s, for iBGP and eBGP | eBGP 30, iBGP 0 | A FortiOS iBGP peer waits up to 30 s between updates unless you lower it |

> **Exam tip:** Two defaults catch Cisco engineers: FortiOS **sends communities by default** (`send-community both`), and the neighbor **advertisement-interval is 30 s even for iBGP**. In large SD-WAN designs the hub's neighbor group often lowers `advertisement-interval` so spokes learn changes quickly.

## Best-path selection

FortiOS documents this order (after discarding paths with AS loops or an unreachable next hop):

1. Highest **weight** (local to the FortiGate; locally originated routes get 32768).
2. Highest **local preference**.
3. Route **originated by this router** (next hop 0.0.0.0).
4. Shortest **AS path**.
5. Lowest **origin** (IGP < EGP < incomplete).
6. Lowest **MED**.
7. **eBGP** over iBGP.
8. Closest **IGP** neighbor (lowest metric to the next hop).
9. Oldest route for eBGP paths.
10. Lowest neighbor **router ID**.
11. Lowest neighbor **IP address**.

This is the standard Cisco-style order. Knobs that change it: `always-compare-med`, `deterministic-med`, `bestpath-as-path-ignore`, `bestpath-med-missing-as-worst`, `bestpath-cmp-routerid` (all disabled by default).

```text
FGT-Hub # get router info bgp summary

172.16.0.2   4   65000     398     401       12    0    0 03:20:51        2
198.51.100.9 4   64512       0       0        0    0    0    never Active
```

A number in **State/PfxRcd** means Established with that many prefixes received. A word means the session is down: `Idle`, `Connect`, `Active`, `OpenSent`, `OpenConfirm`, or `Idle (Admin)` for a neighbor that is shut down. The admin guide's troubleshooting table: **Idle** = the FortiGate hasn't started BGP to that peer (for example eBGP multihop needed but not enabled); **Connect** = started but no TCP connection initiated, often a routing problem; **Active** = TCP connection attempted with no answer.

Other commands:

| Command | Use |
|---|---|
| `get router info bgp neighbors <ip>` | Session state, timers, capabilities, "Community attribute sent to this neighbor (both)", route maps applied, last reset reason |
| `get router info bgp neighbors <ip> advertised-routes` / `received-routes` / `routes` | What was sent; what was received before policy (needs `soft-reconfiguration enable`); what was accepted |
| `get router info bgp network <prefix>` | All paths for one prefix with attributes, communities and "route tag" |

## Filtering and policy

Inbound and outbound policy per neighbor (or per neighbor group): `prefix-list-in/out`, `distribute-list-in/out` (access lists), `filter-list-in/out` (AS path lists), `route-map-in/out`. Route maps can also be applied to a `config network` entry (`route-map`) and to redistribution.

A typical hub policy: accept only branch LAN /24s from spokes and tag them.

```text
config router prefix-list
    edit "PL-BRANCH-LANS"
        config rule
            edit 1
                set prefix 10.1.0.0 255.255.0.0
                set ge 24
                set le 24
            next
        end
    next
end
config router route-map
    edit "RM-FROM-SPOKES"
        config rule
            edit 10
                set match-ip-address "PL-BRANCH-LANS"
                set set-community "65000:10"
            next
        end
    next
end
```

A route map with only this rule **denies** anything else (implicit deny), so a spoke that also advertises its loopback /32 would have it dropped by this inbound map.

### Communities

```text
config router community-list
    edit "CL-DC"
        set type standard
        config rule
            edit 1
                set action permit
                set match "65000:100"
            next
        end
    next
end
config router route-map
    edit "RM-TAG-DC"
        config rule
            edit 1
                set match-community "CL-DC"
                set set-route-tag 100
            next
        end
    next
end
```

- `set-community` takes `AA:NN` or the well-known `internet`, `local-AS`, `no-advertise`, `no-export`. By default it **replaces** the existing communities; `set set-community-additive enable` appends instead. `set-community-delete <list>` removes matches.
- `match-community-exact enable` requires an exact community set.
- Because FortiOS sends communities by default, a community set on the hub reaches every spoke without extra neighbor configuration (unless someone set `send-community disable`).

## ECMP with BGP

BGP installs only one best path unless multipath is enabled:

```text
config router bgp
    set ebgp-multipath enable
    set ibgp-multipath enable
end
```

With multipath on, paths that tie through the RFC 4271 tie-breakers up to the IGP metric are installed together (`B 10.0.1.0/24 [200/0] via ... ` followed by a second `via` line), subject to `ecmp-max-paths` and hashed by `v4-ecmp-mode` or SD-WAN `load-balance-mode`. In SD-WAN overlays `ibgp-multipath` matters for another reason: an SD-WAN rule can only steer traffic to a member that has a route to the destination (lesson 4.4), so a spoke needs the hub's routes through **every** overlay, not just the best one.

When a next hop is itself reached through several equal routes (for example a hub loopback reached over two tunnels), FortiOS considers all of them during recursive resolution, so the BGP route inherits the ECMP set. The admin guide notes that either `ebgp-multipath` or `ibgp-multipath` must be enabled for that behaviour.

## iBGP and eBGP details that matter on FortiOS

- **next-hop-self**: iBGP peers don't change the next hop. A FortiGate that learns a route from an eBGP ISP and passes it to an iBGP peer needs `set next-hop-self enable` on that iBGP neighbor, or the peer needs a route to the ISP's next hop. On a route reflector, `next-hop-self-rr` applies the same to reflected routes.
- **Loop prevention**: `allowas-in-enable` / `allowas-in` (accept own AS, default count 3 when enabled), `as-override`, `remove-private-as`.
- **eBGP between loopbacks** needs `ebgp-enforce-multihop enable` plus `update-source`.
- iBGP routes are advertised to eBGP peers automatically. Fortinet's basic example uses an outbound route map (`match-origin igp`, `action deny`) to stop that toward an ISP.

## Lab it yourself

In the **FortiGate-VM trial**, peer port2 with a Cisco IOS router or an FRR container: one eBGP session, a `config network` entry for the FortiGate's LAN, and a couple of prefixes from the other side (stay at or under three routes in total). Try: removing the LAN route to see `network-import-check` withdraw the prefix; `set send-community disable` and compare `show ip bgp <prefix>` on the Cisco side; an inbound route map with `set-route-tag` and the RouteTag column in `get router info bgp network`.

## Key takeaways

- BGP distances: **eBGP 20, iBGP 200, local 200**, like IOS. Timers **60/180**.
- FortiOS **sends standard and extended communities by default**; IOS does not.
- Neighbor `advertisement-interval` defaults to **30 s for iBGP and eBGP**.
- `ebgp-multipath` and `ibgp-multipath` are **disabled** by default; ECMP is still capped by `ecmp-max-paths`.
- `network-import-check` is **enabled**: a `config network` prefix must exist in the routing table to be advertised.
- `recursive-next-hop` is **disabled**: BGP routes are not used to resolve BGP next hops unless you enable it.
- Route maps end in an implicit deny; `set-community` replaces unless `set-community-additive enable`.
