## Where OSPF fits in an SD-WAN architecture

In Fortinet's SD-WAN reference designs, BGP carries routes over the overlays and OSPF usually lives on the LAN side: a hub or data-center FortiGate peers with core switches and routers, and a branch FortiGate peers with an L3 switch stack. OSPF is also a valid choice for a small hub-and-spoke VPN or for two sites joined by redundant tunnels, as long as you understand how it behaves on IPsec interfaces (next lesson).

FortiOS's routing daemon is derived from ZebOS, so the OSPF state machine, LSA types, DR/BDR election and the `get router info ospf ...` outputs look very close to what you know from Cisco IOS. The configuration model and several defaults are different, and those differences are what the exam tests.

## The configuration model

OSPF lives under `config router ospf` (OSPFv3 under `config router ospf6`). There is one OSPF process per VDOM, shown as `OSPF process 0, VRF 0` in the outputs.

```text
FGT-Hub # config router ospf
FGT-Hub (ospf) # set router-id 172.16.0.254
FGT-Hub (ospf) # config area
FGT-Hub (area) # edit 0.0.0.0
FGT-Hub (0.0.0.0) # next
FGT-Hub (area) # end
FGT-Hub (ospf) # config network
FGT-Hub (network) # edit 1
FGT-Hub (1) # set prefix 10.0.1.0 255.255.255.0
FGT-Hub (1) # set area 0.0.0.0
FGT-Hub (1) # next
FGT-Hub (network) # end
FGT-Hub (ospf) # config ospf-interface
FGT-Hub (ospf-interface) # edit "core-port3"
FGT-Hub (core-port3) # set interface "port3"
FGT-Hub (core-port3) # set cost 10
FGT-Hub (core-port3) # set priority 255
FGT-Hub (core-port3) # next
FGT-Hub (ospf-interface) # end
FGT-Hub (ospf) # set passive-interface "port4"
FGT-Hub (ospf) # end
```

The pieces map onto IOS like this:

| FortiOS | Cisco IOS equivalent | Notes |
|---|---|---|
| `config area` / `edit <id>` | `area <id> ...` | `type` regular (default), stub or nssa; `stub-type summary` (default) or no-summary |
| `config network` / `set prefix` + `set area` | `network <addr> <wildcard> area <id>` | FortiOS uses a **subnet mask**, not a wildcard. An interface whose address falls inside the prefix runs OSPF in that area |
| `config ospf-interface` / `edit <name>` | `interface X` + `ip ospf ...` | A named entry that points at an interface with `set interface`. Holds cost, priority, timers, network type, authentication, BFD, MTU handling |
| `set passive-interface` | `passive-interface` | Top-level list of interface names |
| `config redistribute "<protocol>"` | `redistribute <protocol>` | One fixed entry per source protocol; `set status enable` turns it on |
| `set default-information-originate` | `default-information originate` | `enable` needs a default route in the routing table; `always` advertises one anyway |

> **Watch out:** An `ospf-interface` entry does not, by itself, put an interface into OSPF. The interface's address must still match a `config network` prefix. The `ospf-interface` entry only tunes how OSPF runs on that interface.

## Defaults you must know (and where they differ from IOS)

Values from the FortiOS 7.6.0 CLI Reference for `config router ospf`:

| Setting | FortiOS 7.6 default | Cisco IOS default | Exam consequence |
|---|---|---|---|
| `auto-cost-ref-bandwidth` | **1000** Mbps | 100 Mbps | A 1 Gbps port costs 1 on FortiOS; on IOS it also costs 1 (floor) but a 100 Mbps port costs 10 on FortiOS and 1 on IOS. Align the reference bandwidth across vendors |
| `ospf-interface` `cost` | **0 = auto-cost** | computed | Set an explicit cost on tunnels and anything without a meaningful speed |
| `distance`, `distance-intra-area`, `distance-inter-area`, `distance-external` | **110** each | 110 | Same as IOS; FortiOS lets you tune each type separately |
| `default-metric` | **10** | 20 for most sources (1 for BGP) | Redistributed routes with `metric 0` appear as E2 with cost 10 |
| `config redistribute` `metric-type` | **2** | E2 | Same idea: external type 2 unless you set 1 |
| `default-information-metric` / `-metric-type` | **10** / **2** | 1 / E2 | The injected default shows up as `O*E2 0.0.0.0/0 [110/10]` |
| `ospf-interface` `network-type` | **broadcast** | depends on media | That is the entry's default whatever the interface type, tunnels included, so set `point-to-point` on tunnel entries. A tunnel with no entry doesn't elect a DR (Fortinet's ADVPN-with-OSPF example shows `Full/ -`) |
| `ospf-interface` `priority` | **1** | 1 | `priority 0` = never DR |
| `hello-interval` / `dead-interval` | **0** in the CLI, meaning the protocol defaults (10/40 on broadcast) | 10/40 | Timers must match neighbors |
| `mtu-ignore` | **disable** | disabled | MTU mismatch blocks the adjacency in ExStart/Exchange |
| `rfc1583-compatible` | **disable** | enabled (`compatible rfc1583`) | Routers in one area can pick different external paths; align it in mixed networks |
| `bfd` (process) / `bfd` (interface) | **disable** / **global** | | See the BFD section of the BGP convergence lesson |
| `restart-mode` | **none** | | Graceful restart is opt-in |
| `log-neighbour-changes` | **enable** | | |

> **Exam tip:** A Cisco engineer's instinct says "redistributed routes default to metric 20". On FortiOS they arrive with the `default-metric` of **10** unless the redistribute entry or a route map sets a metric. The admin guide's own three-router example shows BGP routes redistributed with default settings as `O E2 ... [110/10]`.

The cost formula is the RFC 2328 one: reference bandwidth divided by interface speed, with a minimum of 1. With the default 1000 Mbps reference a 1 Gbps port is cost 1 and a 100 Mbps port is cost 10. Interfaces whose speed the kernel can't express well (software switches, some virtual and tunnel interfaces) can produce surprising auto costs, which is why Fortinet's own examples set `cost` explicitly on IPsec interfaces.

## Reading the OSPF outputs

The neighbor table looks like IOS with an extra header line naming the process and VRF:

```text
FGT-Hub # get router info ospf neighbor
OSPF process 0, VRF 0:
Neighbor ID     Pri   State           Dead Time   Address         Interface
10.255.0.1        1   Full/DR         00:00:36    10.0.1.1        port3
10.255.0.2        1   Full/Backup     00:00:31    10.0.1.2        port3
172.16.0.1        1   Full/ -         00:00:38    10.10.1.1       HUB1-VPN1
```

`Full/ -` means a full adjacency on a point-to-point network type, where no DR or BDR is elected. On a broadcast segment you see `Full/DR`, `Full/Backup` or `2-Way/DROther` between two DROthers, exactly as on IOS.

The interface output tells you the network type and the cost in use:

```text
FGT-Hub # get router info ospf interface port3
port3 is up, line protocol is up
  Internet Address 10.0.1.254/24, Area 0.0.0.0, MTU 1500
  Process ID 0, VRF 0, Router ID 172.16.0.254, Network Type BROADCAST, Cost: 10
```

Other commands worth knowing:

| Command | Shows |
|---|---|
| `get router info ospf status` | Router ID, ABR/ASBR role, SPF statistics, LSA counts per area |
| `get router info ospf database brief` / `... database router lsa` / `... external lsa` | The LSDB, summarized or per LSA type |
| `get router info routing-table ospf` | OSPF routes in the RIB (`O`, `O IA`, `O E1`, `O E2`, `O N1`, `O N2`) |
| `diagnose ip router ospf all enable` + `diagnose ip router ospf level info` + `diagnose debug enable` | Real-time OSPF debug (hello, NFSM state changes) |
| `diagnose sniffer packet any 'proto 89' 4` | OSPF packets on the wire |

## Adjacency problems, the FortiOS way

The OSPF neighbor state machine is standard, so the classic causes apply: mismatched area ID, hello/dead timers, authentication, area type (stub flag), duplicate router IDs and subnet/mask mismatch on broadcast networks keep a neighbor from reaching 2-Way. An **MTU mismatch** lets the neighbors see each other but stalls them in **ExStart/Exchange**, because the Database Description packets are rejected. On FortiOS you fix that by correcting the MTU or by `set mtu-ignore enable` on the `ospf-interface` entry.

Two FortiGate-specific causes are worth remembering:

- **No firewall policy is needed for OSPF to the FortiGate itself** (it is local-in traffic), but a **local-in policy** or a VDOM/VRF mismatch can still block it, and OSPF over an IPsec tunnel needs the tunnel interface to have an IP address that matches a `config network` prefix.
- **Network-type mismatch.** If one side of a tunnel is `point-to-point` and the other has an `ospf-interface` entry left at its default `broadcast`, the two routers describe the same link differently (one waits for a DR, the other doesn't elect one), so the adjacency or the resulting routes misbehave. Set both ends the same.

> **Real world:** Coming from IOS, the most common FortiGate OSPF ticket is a cost surprise: a FortiGate and a Cisco router on the same segment pick different paths because one uses a 1000 Mbps reference and the other 100 Mbps. Set `auto-cost-ref-bandwidth` (FortiOS) and `auto-cost reference-bandwidth` (IOS) to the same value everywhere, or set costs explicitly.

## Areas and summarization

FortiOS supports regular, stub (with `stub-type summary` or `no-summary` for totally stubby) and NSSA areas, ABR summarization with `config area` → `config range`, and ASBR summarization of redistributed routes with `config summary-address`. `abr-type` defaults to `standard`. An NSSA ABR is a translator `candidate` by default (`nssa-translator-role`).

For an SD-WAN architect, the main use of areas is containment: put each branch's LAN in its own area or keep OSPF strictly local to the branch, and let BGP carry routes between sites. A single OSPF area spanning dozens of spokes over IPsec floods every topology change to every site, which is one reason Fortinet's large designs use BGP on the overlay.

## Lab it yourself

What fits in the **FortiGate-VM permanent trial** (3 interfaces, 3 policies, 3 routes):

- port1 for management, port2 to a Cisco IOS router (or a Linux host running FRR), port3 as a LAN.
- Run OSPF area 0 on port2 and port3, advertise one or two loopbacks from the Cisco side, and watch `get router info ospf neighbor` reach `Full/DR`.
- Change `auto-cost-ref-bandwidth` on only one side and compare `get router info ospf interface` with `show ip ospf interface`.
- Set a deliberately different MTU on the Cisco side and watch the neighbor stall in ExStart, then fix it with `mtu-ignore`.

Keep the number of learned plus static prefixes at or below the trial's three-route cap so the cap never confuses your results. No firewall policy is needed for the OSPF adjacency itself.

## Key takeaways

- OSPF is configured under `config router ospf` with `config area`, `config network` (prefix with a **mask**, not a wildcard), `config ospf-interface` and `config redistribute`.
- Default reference bandwidth is **1000 Mbps** (IOS: 100); interface `cost 0` means auto-cost.
- OSPF distances default to **110** for intra-area, inter-area and external routes, and each can be tuned separately.
- Redistributed routes default to **E2 with metric 10** (`default-metric 10`, `metric-type 2`); the injected default route uses metric 10, type 2.
- `default-information-originate enable` needs a default route in the routing table; `always` does not.
- An `ospf-interface` entry's network type defaults to **broadcast**, tunnels included; set `point-to-point` on both ends of a tunnel.
- MTU mismatch stalls neighbors in ExStart/Exchange; fix the MTU or use `mtu-ignore enable`.
