## Two ways to run BGP over overlays

A spoke with two overlays to one hub (say `HUB1-VPN1` over an ISP link and `HUB1-VPN2` over a second ISP or MPLS) can peer with the hub in two ways:

| Design | BGP sessions per spoke per hub | Next hop of hub routes | How a failed overlay is handled |
|---|---|---|---|
| **BGP per overlay** | One per tunnel, sourced from the tunnel IPs (10.10.1.x, 10.10.2.x) | The hub's tunnel IP on that overlay | That session drops; its routes go with it. Needs `ibgp-multipath` so both overlays carry routes, and the hub has to tell the overlays apart (route maps, communities, SD-WAN neighbor) |
| **BGP on loopback** | **One** per hub, between loopbacks, whatever the number of overlays | The hub's (or remote spoke's) loopback, resolved **recursively** over every overlay that reaches it | The session survives as long as any overlay is up; the recursive routes simply lose one path |

Fortinet's current designs (FortiManager SD-WAN overlay template, the 7.6 SD-WAN Deployment Guide, ADVPN 2.0) default to **BGP on loopback**: fewer sessions, routing that doesn't care which overlay is up, and SD-WAN rules (not BGP) choose the overlay.

## Building BGP on loopback

The checklist below follows the Fortinet 7.6 examples (and the Reference page of this site).

### 1. Loopbacks

```text
config system interface
    edit "Branch-Lo"
        set vdom "root"
        set type loopback
        set ip 172.16.0.1 255.255.255.255
        set allowaccess ping
    next
end
```

The hub gets **two** loopbacks: `BGP-Lo` (for example 172.16.0.254) for BGP and `HUB-Lo` (172.16.0.253) as the spoke health-check target. The reason: an SD-WAN health check installs a dedicated kernel route to its server over each member, and that route is not removed when the probe fails. If the BGP session pointed at the same IP, it could keep following the probe route over a dead tunnel instead of the routing table.

### 2. Making loopbacks reachable: IKE routes

The tunnels don't need IP addresses. Each phase 1 tells the peer about the local loopback, and IKE installs a route to the peer's loopback over that tunnel:

```text
config vpn ipsec phase1-interface
    edit "HUB1-VPN1"
        set exchange-interface-ip enable
        set exchange-ip-addr4 172.16.0.1
    next
    edit "HUB1-VPN2"
        set exchange-interface-ip enable
        set exchange-ip-addr4 172.16.0.1
    next
end
```

On the spoke, the result is a static-type route to the hub loopback through **both** tunnels, with the IKE route distance (`distance`, default **15**) and priority (default **1**):

```text
S       172.16.0.254/32 [15/0] via HUB1-VPN1 tunnel 192.0.2.101, [1/0]
                        [15/0] via HUB1-VPN2 tunnel 192.0.2.102, [1/0]
```

`exchange-interface-ip` must be enabled before `exchange-ip-addr4` can be set. On the hub, each spoke's loopback arrives the same way on the hub's dial-up tunnels.

### 3. Location ID

`config system settings` → `set location-id <loopback IP>` gives each device a unique location identifier (used, for example, by IPsec aggregate dial-up distribution and by ADVPN 2.0 shared idle timeouts). Use the device's own loopback address.

### 4. Spoke BGP

```text
config router bgp
    set as 65000
    set router-id 172.16.0.1
    set ibgp-multipath enable
    set recursive-next-hop enable
    config neighbor
        edit "172.16.0.254"
            set remote-as 65000
            set interface "Branch-Lo"
            set update-source "Branch-Lo"
            set connect-timer 1
            set advertisement-interval 1
        next
    end
    config network
        edit 1
            set prefix 10.1.1.0 255.255.255.0
        next
    end
end
```

- `update-source` makes TCP/179 originate from the loopback.
- `ibgp-multipath` lets the spoke install several iBGP paths (for example the same prefix from two hubs).
- `recursive-next-hop enable` lets the spoke resolve a BGP next hop **through another BGP route**. Routes to other spokes' LANs carry the other spoke's loopback as next hop; that loopback is known to the spoke only through BGP (the hub advertises the loopback range), so without this option those routes would be unresolvable. The default is disable, and recursion resolves one level.
- `connect-timer 1` and `advertisement-interval 1` are common tuning values in Fortinet's examples; they aren't defaults (connect timer is unset, advertisement interval 30 s).

### 5. Hub BGP: neighbor groups and neighbor ranges

The hub can't list hundreds of spoke loopbacks one by one. It uses **dynamic neighbors**:

```text
config router bgp
    set as 65000
    set router-id 172.16.0.254
    set ibgp-multipath enable
    config neighbor-group
        edit "EDGE"
            set remote-as 65000
            set interface "BGP-Lo"
            set update-source "BGP-Lo"
            set route-reflector-client enable
            set soft-reconfiguration enable
            set advertisement-interval 1
        next
    end
    config neighbor-range
        edit 1
            set prefix 172.16.0.0 255.255.255.0
            set neighbor-group "EDGE"
        next
    end
    config network
        edit 1
            set prefix 10.0.1.0 255.255.255.0
        next
        edit 2
            set prefix 172.16.0.0 255.255.255.0
        next
    end
end
```

- **neighbor-group** holds everything a normal neighbor can hold (remote AS, update source, route maps, RR client, timers, BFD, password).
- **neighbor-range** maps a source prefix to a group. Any peer that opens a BGP session **from an address inside the range** is accepted with the group's settings. The hub is passive for those peers: it waits for spokes to connect. `max-neighbor-num` (1-1000) can limit how many peers a range accepts.
- `remote-as-filter <aspath-list>` (documented in the 7.6 Administration Guide) lets one group accept several remote ASs, for eBGP spokes in different ASs. It is mutually exclusive with `remote-as`.
- The hub advertises the loopback summary (here `network 172.16.0.0/24`, or an aggregate). That summary is what lets spokes resolve each other's loopbacks recursively. Because `network-import-check` is enabled by default, the summary must exist in the hub's routing table, for example as a blackhole static route for 172.16.0.0/24, or the hub won't advertise it.

The IOS equivalent is `bgp listen range 172.16.0.0/24 peer-group EDGE`, with the peer group doing the work of the FortiOS neighbor group.

> **Exam tip:** A neighbor-range prefix must cover the **source address the spoke uses**: the spoke loopback when BGP is on loopback, the spoke's tunnel IP when BGP is per overlay. A range of 10.10.0.0/16 on a loopback design accepts nobody.

## Route reflection versus no route reflection

All spokes and hubs are in one AS, so iBGP split horizon applies: a hub that learns Spoke1's LAN from Spoke1 won't send it to Spoke2 unless it is a **route reflector** (`route-reflector-client enable` on the neighbor group; `client-to-client-reflection` is enabled by default; `cluster-id` matters with two reflectors).

| Option | What spokes learn | Use when |
|---|---|---|
| Hub reflects routes (RR) | Each remote spoke LAN with the **remote spoke's loopback** as next hop (RR doesn't change next hop) | ADVPN: the spoke needs the real remote next hop so traffic triggers and then uses a shortcut |
| RR with `next-hop-self-rr` or a summary from the hub | Routes via the hub | Pure hub-and-spoke without shortcuts |
| No route reflection, hub advertises only summaries | A summary (for example 10.1.0.0/16) via the hub | Simple, small tables; with ADVPN 1.0 the shortcut then needs dynamic BGP or another mechanism to learn the specific route |

With BGP on loopback plus `recursive-next-hop`, the reflected route `10.1.2.0/24 via 172.16.0.2` resolves first to the loopback summary from the hub, which in turn resolves over the IKE routes through both overlays. When an ADVPN shortcut to Spoke2 comes up, IKE installs a more specific route to 172.16.0.2 over the shortcut and the same BGP route now resolves over it, with no BGP change at all. That is the main reason Fortinet pairs ADVPN with BGP on loopback. The ADVPN details (shortcuts, dynamic BGP, ADVPN 2.0) are covered in domain 5.

## Verifying the design

```text
FGT-Spoke1 # get router info routing-table all
...
B       10.0.1.0/24 [200/0] via 172.16.0.254 (recursive via HUB1-VPN1 tunnel 192.0.2.101), 00:41:12
                                             (recursive via HUB1-VPN2 tunnel 192.0.2.102), 00:41:12
C       10.1.1.0/24 is directly connected, port3
B       10.1.2.0/24 [200/0] via 172.16.0.2 (recursive via HUB1-VPN1 tunnel 192.0.2.101), 00:40:55
                                           (recursive via HUB1-VPN2 tunnel 192.0.2.102), 00:40:55
C       172.16.0.1/32 is directly connected, Branch-Lo
B       172.16.0.0/24 [200/0] via 172.16.0.254 (recursive via HUB1-VPN1 tunnel 192.0.2.101), 00:41:12
                                               (recursive via HUB1-VPN2 tunnel 192.0.2.102), 00:41:12
S       172.16.0.254/32 [15/0] via HUB1-VPN1 tunnel 192.0.2.101, [1/0]
                        [15/0] via HUB1-VPN2 tunnel 192.0.2.102, [1/0]
```

Read it from the bottom up: the IKE routes reach the hub loopback over both tunnels; the hub's loopback summary and DC LAN resolve over those; Spoke2's LAN resolves through Spoke2's loopback, which falls inside the summary (that resolution through another BGP route is what `recursive-next-hop` allows). SD-WAN rules then pick which tunnel each session uses, because every tunnel has a valid route.

Common faults and what they look like:

| Symptom | Likely cause |
|---|---|
| Hub `get router info bgp summary` shows no spoke peers | Neighbor range doesn't cover the spoke loopbacks; IKE routes missing (no `exchange-ip-addr4`); BGP blocked by a local-in policy; spoke `update-source` not set |
| Spoke has `10.1.2.0/24` in `get router info bgp network` but not in the routing table | Next hop 172.16.0.2 unresolvable: `recursive-next-hop` disabled or no loopback summary from the hub |
| Only one tunnel used for hub routes | Next hop learned through only one path; check IKE routes on both tunnels and `ibgp-multipath` |
| Health checks to the hub fail although BGP is up | Missing firewall policy for probes, or the member has no `source` (IP-less tunnels need `set source <loopback>` on the SD-WAN member) |

## Lab it yourself

BGP on loopback needs at least a hub and one spoke, two tunnels between them and a loopback on each: two FortiGate-VMs. The **permanent trial allows one VM per FortiCloud account**, so you need a second account for the second VM, and two tunnels plus a loopback plus underlay ports push against the 3-interface limit. A realistic way inside the trial: one FortiGate-VM as the spoke and a Linux VM running strongSwan + FRR as the "hub", with one tunnel, `exchange-ip-addr4`-style loopback reachability replaced by a static /32 on the Linux side, and iBGP between loopbacks. The dual-overlay recursive ECMP behaviour needs licensed VMs or the Fortinet on-demand labs.

## Key takeaways

- BGP on loopback = one iBGP session per hub regardless of overlays; routes resolve recursively over every tunnel.
- Loopback reachability comes from IKE: `exchange-interface-ip enable` + `exchange-ip-addr4 <loopback>`; IKE routes have distance **15**, priority **1** by default.
- Use separate hub loopbacks for BGP (`BGP-Lo`) and health checks (`HUB-Lo`).
- Spokes need `update-source`, `ibgp-multipath` and `recursive-next-hop enable` (default disable).
- Hubs use `neighbor-group` + `neighbor-range`; the range must cover the spokes' **source** addresses; the hub is passive for range peers.
- Route reflection keeps the remote spoke as next hop (needed for ADVPN); summaries or `next-hop-self-rr` pull traffic through the hub.
