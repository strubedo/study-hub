## Sessions remember the route

FortiGate is stateful: after the first packets, traffic is forwarded according to the **session table entry**, not a fresh route lookup per packet. The session stores the ingress/egress interfaces in both directions, the gateway, the NAT translation, the SD-WAN rule and member, and the offload state. Understanding when that stored decision is reused, flushed or re-evaluated is what turns "SD-WAN failed over, but users still lost the call" into a design decision.

| Field | Meaning |
|---|---|
| `proto` | IP protocol: 1 ICMP, 6 TCP, 17 UDP |
| `proto_state` | Protocol state, two digits for TCP (one per direction) |
| `duration` / `expire` / `timeout` | Age, seconds left before the idle timeout, the timeout for the current state |
| `state=` | Session flags (below) |
| `dev=7->19/19->7` | Ingress->egress interface index, original / reply direction |
| `gwy=` | Gateway in the original / reply direction |
| `hook=... act=snat|dnat|noop` | NAT actions and translated tuples |
| `policy_id` | Matching firewall policy |
| `sdwan_mbr_seq`, `sdwan_service_id` | SD-WAN member sequence number and rule ID chosen for the session |
| `npu_state`, `no_ofld_reason` | Hardware offload status |

### Protocol states

From the FortiOS 7.6 Administration Guide:

| Protocol | `proto_state` values |
|---|---|
| ICMP | Always `00` (no states) |
| UDP | `0` reply not seen, `1` reply seen |
| TCP (per direction) | `0` NONE, `1` ESTABLISHED, `2` SYN_SENT, `3` SYN & SYN/ACK, `4` FIN_WAIT, `5` TIME_WAIT, `6` CLOSE, `7` CLOSE_WAIT, `8` LAST_ACK, `9` LISTEN |

### Common session flags

| Flag | Meaning |
|---|---|
| `may_dirty` | The session may be altered (re-evaluated) if something changes |
| `dirty` | The session **has been** marked for re-evaluation (needs `may_dirty`); the next packet triggers a new lookup |
| `npu` / `npd` | Offloaded to an NPU / denied for offload |
| `local` | Attached to the FortiGate's own IP stack: traffic to or from the FortiGate, and proxy-redirected sessions (`redir local`) |
| `log`, `f00` | Traffic logging enabled |
| `ndr` / `nds` | IPS signature / anomaly inspection |
| `redir` | Redirected to a proxy |
| `os` / `rs` | Shaped in the original / reply direction |
| `synced` / `syn_ses` | HA session sync: sent to peers / received from the primary |
| `block` | Re-evaluated and now blocked after a policy change |
| `route_preserve` | Route information preserved (interface `preserve-session-route enable`) |
| `complex` | Handled by a session helper |
| `app_valid` / `url_cat_valid` | Application / URL category identified |

## Session re-evaluation and its triggers

| Trigger | What happens by default | Knob |
|---|---|---|
| **Routing change** (route added/removed, SD-WAN member dead, BGP update), session **without SNAT** | FortiOS flushes routing information from affected sessions; the next packet does a new lookup and can move to another interface | `config system interface` → `set preserve-session-route enable` keeps sessions on their route; only new sessions use the new one |
| **Routing change**, session **with SNAT** | The session **keeps** its outbound interface as long as the old route is still active (for example only its priority changed), so the NAT source address stays valid | `config system global` → `set snat-route-change enable` forces a new lookup and a new SNAT for those sessions |
| **SD-WAN rule preference change** (better member, SLA pass/fail) | The rule's policy route is regenerated; affected sessions are re-evaluated like a routing change (non-SNAT sessions move) | `sla-stickiness enable` on lowest cost (SLA) rules keeps sessions on a member that still meets SLA; `hold-down-time` delays the move back |
| **Firewall policy change** | Default `check-all`: sessions affected by the change are flushed and re-evaluated against the new policy | `config system settings` → `set firewall-session-dirty check-all \| check-new \| check-policy-option` |

> **Exam tip:** "After the primary ISP failed and recovered, new sessions use wan1 again but existing internet sessions stay on wan2" is **expected** behaviour for **SNAT** sessions: they keep their route while it is still valid, because moving them would change their source IP and break them anyway. `snat-route-change enable` changes that (and resets the source address the server sees).

### Routing changes in SNAT sessions, in practice

- Internet traffic from a branch is almost always SNATed to the WAN IP. Moving it to another WAN would change its source IP, which breaks TCP; so FortiOS leaves it unless forced.
- Overlay traffic between sites is usually **not** NATed. Those sessions can move between overlays on a routing or SD-WAN change without breaking, which is what you want for failover.
- If the old route disappears entirely (member dead, route withdrawn), SNAT sessions have to be re-routed; they then usually break at the application level because the source changed.

## Designing routing for SD-WAN

### Which protocol where

| Segment | Recommended | Why |
|---|---|---|
| Branch LAN behind the FortiGate | Connected routes, or OSPF with an L3 switch | Small, local, multi-vendor |
| Overlays hub ↔ spoke | **iBGP**, preferably **on loopback**, hub as RR with neighbor groups/ranges | Scales, carries communities/route tags, works with ADVPN; one session per hub regardless of overlays |
| Internet (DIA) | Static default routes through the WAN zones (`sdwan-zone`) | Members' gateways; health checks withdraw dead members |
| DC core behind the hub | OSPF or eBGP to the core, redistribute summaries into the overlay BGP | Keep spoke tables small |
| Between regions / large scale | eBGP between regional hubs or BGP with route reflection; see domain 5 multiregion | Policy at region borders |
| Very small, two sites | Static routes or OSPF over two tunnels | Simplicity |

### Routing considerations checklist

1. **Every member that a rule may use needs a route** to the rule's destinations: `ibgp-multipath` for BGP per overlay, or BGP on loopback with recursive resolution over all tunnels.
2. **Return path symmetry**: the hub must send replies back over the overlay the spoke chose, or stateful inspection on either side may drop asymmetric traffic. Fortinet's tools: hub SD-WAN rules matching the spoke's overlay, BGP communities/route-map-out-preferable from spokes, or embedded SLA in probes with `priority-in-sla` / `priority-out-sla` on the hub (domain 5).
3. **Distance and priority interplay**: IKE routes (distance 15) and static routes (10) beat iBGP (200). A static default through the WAN zone plus an iBGP default from the hub won't ECMP; decide which one you want for which traffic and use SD-WAN rules or priorities to express it.
4. **RPF**: FortiOS checks the reverse path for new sessions (feasible-path by default). A rule that sends traffic where the routing table has no route (`gateway`/`default` options) can produce replies that fail RPF on the way back.
5. **Health-check routes**: separate the health-check target from BGP peering and from user destinations.
6. **Local-out traffic**: management, logging and FortiGuard use the routing table unless set to `interface-select-method sdwan`.
7. **Session behaviour on failover**: SNAT sessions stay; non-SNAT sessions move; choose `snat-route-change`, `preserve-session-route`, `sla-stickiness` and `hold-down-time` deliberately.

> **Real world:** The classic "SD-WAN is not failing over" ticket is a session that was never supposed to move (SNAT), and the classic "SD-WAN fails over but traffic is one-way" ticket is a hub that keeps sending replies down the old overlay. Both are routing design issues, not SD-WAN rule issues.

## Lab it yourself

The **FortiGate-VM trial** is enough to see SNAT session behaviour: two WAN members (port1, port2), LAN on port3, one NAT policy, a default route through the WAN zone. Start a long download, raise the priority of the route through its member (keeping the route active), and check `diagnose sys session list` (`gwy=`, `dev=`, `sdwan_mbr_seq=`): the session stays. Repeat with `set snat-route-change enable`. Watching non-SNAT overlay sessions move needs a second FortiGate (hub) and tunnels, which needs another trial account or licensed VMs.

## Key takeaways

- The session stores the route, NAT, SD-WAN rule and member; `diagnose sys session list` shows `dev=`, `gwy=`, `sdwan_mbr_seq=`, `sdwan_service_id=`.
- TCP `proto_state` has two digits (per direction); `1` = ESTABLISHED; UDP `1` = reply seen; ICMP always `00`.
- `may_dirty` = can be re-evaluated; `dirty` = flagged for a new lookup.
- Routing change: non-SNAT sessions re-lookup (unless `preserve-session-route`); SNAT sessions keep their route while it is still active (unless `snat-route-change enable`, default disable).
- Policy changes re-evaluate sessions per `firewall-session-dirty` (default `check-all`).
- Use iBGP (on loopback) for overlays, static zone routes for DIA, OSPF/eBGP toward LAN and DC cores; make sure every member a rule may use has a route, and plan return-path symmetry.
