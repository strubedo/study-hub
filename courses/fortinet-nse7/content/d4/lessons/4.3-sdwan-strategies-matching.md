## Traffic matching criteria

An SD-WAN rule identifies traffic with any combination of the fields below (7.6 Administration Guide, "Fields for identifying traffic"). All configured fields must match.

| Side | GUI field | CLI | Notes |
|---|---|---|---|
| Source | Source address | `set src`, `set src-negate`, `start-src-port`/`end-src-port` | Ports are CLI only |
| Source | User / group | `set users`, `set groups` | Needs authenticated users (FSSO, captive portal ...) |
| Source | Source interface | `set input-device`, `set input-device-negate`; `set input-zone` | CLI only |
| Destination | Address | `set dst`, `set dst-negate`, `set protocol`, `start-port`/`end-port` | One protocol and one port range per rule; use a custom internet service for more |
| Destination | Internet Service | `set internet-service enable` + `internet-service-name` / `-group` / `-custom` / `-custom-group` | ISDB: IP/protocol/port tuples maintained by FortiGuard |
| Destination | Application | `set internet-service-app-ctrl` / `-app-ctrl-group` / `-app-ctrl-category` | Application control signatures; needs a learning phase |
| Destination | Route tag | address object `type route-tag` in `set dst` | Matches routes that carry a route tag (from a BGP route map) |
| Destination | TOS/DSCP | `set tos`, `set tos-mask` | CLI only; the mask selects the bits |

> **Watch out:** The 7.6 Administration Guide's field table lists a CLI-only `set route-tag` on the rule itself, but the CLI Reference syntax for `config service` (7.6.0, and still 7.6.3) doesn't list it, and the guide's worked example uses a `route-tag` **address object** in `set dst`. Use the address-object method.

### Internet services as destinations

ISDB entries (for example `Microsoft-Office365`, `Salesforce`, `Google-Gmail`) are lists of IP ranges, protocols and ports per service, kept current by FortiGuard. A rule matching an internet service can steer SaaS directly out of local DIA links without you maintaining address objects. Because the match is on the destination IP/port tuple, it works on the **first packet** of the session; no inspection is needed.

> **Lab note:** The FortiGate-VM permanent trial has no FortiGuard, so the ISDB on a trial VM is whatever the firmware shipped with and is never updated.

### Application steering and the learning phase

Application-based rules use application control signatures, which need traffic to be inspected before the application is known. The FortiOS 7.6 guide describes the sequence:

1. **First session**: no SD-WAN rule can match yet. The session is routed by a later rule or the implicit rule. The IPS engine inspects it (the firewall policy needs an application control profile) and identifies the application.
2. **Learning**: the IPS engine records the session's **destination IP, protocol and port** (a 3-tuple) against the application in the application control internet service list. View it with `diagnose sys sdwan internet-service-app-ctrl-list [app-id]`.
3. **Later sessions** to the same 3-tuple match the application rule from their first packet.
4. **Aging**: an entry with no hits for **eight hours** is removed.

Consequences for design: services with many IPs (large SaaS, CDNs) can keep hitting unlearned addresses and fall through to the next rule; ISDB matching is more predictable when an ISDB object exists for the service; and the fallback rule must be acceptable for those first sessions.

## Rule strategies

| Strategy (GUI) | CLI `mode` | Uses health checks | How the preferred member is elected |
|---|---|---|---|
| Manual | `manual` (default) | No | First alive member in `priority-members` / `priority-zone` order (with routes to the destination) |
| Best quality | `priority` | Yes, one `health-check` | Member with the best `link-cost-factor` measured by that health check: latency, jitter, packet-loss, inbandwidth, outbandwidth, bibandwidth or custom-profile-1 |
| Lowest cost (SLA) | `sla` | Yes, one or more SLA targets (`config sla`) | Among members that **meet the SLA**, the lowest member `cost`; equal cost → `tie-break` / configured order |
| Load balancing | `manual` or `sla` with `set load-balance enable` | Only under `sla` | All eligible members, distributed by `hash-mode` (round-robin default, source-ip-based, source-dest-ip-based, inbandwidth, outbandwidth, bibandwidth) |
| Automatic (legacy) | `auto` | Yes | Member with the configured quality rank (`quality-link`); CLI only |

Load balancing was called **maximize bandwidth (SLA)** before FortiOS 7.4.1. Under the lowest cost strategy it spreads traffic over every member that meets the SLA and **ignores cost**.

### Best quality: the advantage for the first member

Best quality doesn't simply pick the lowest number. To avoid flapping between nearly equal links, the **first** member in `priority-members` gets an advantage: its measured value is divided by (1 + `link-cost-threshold`/100). The default `link-cost-threshold` is **10** (percent).

Fortinet's worked example: both links at 200 ms latency, `priority-members 2 1`. Member 2 is treated as 200 / 1.1 ≈ 182 ms, so member 2 stays preferred. Member 1 only takes over when its latency is more than about 10% better than member 2's. Raising the threshold makes the rule stickier; `0` removes the bias.

```text
config system sdwan
    config service
        edit 2
            set name "VOICE-DC"
            set mode priority
            set dst "DC_NET"
            set health-check "HUB_HC"
            set link-cost-factor jitter
            set link-cost-threshold 10
            set priority-members 3 4
        next
    end
end
```

### Lowest cost (SLA): pass/fail, then cost

```text
config system sdwan
    config members
        edit 3
            set interface "HUB1-VPN1"
            set zone "HUB1"
            set source 172.16.0.1
            set cost 0
        next
        edit 4
            set interface "HUB1-VPN2"
            set zone "HUB1"
            set source 172.16.0.1
            set cost 10
        next
    end
    config service
        edit 1
            set name "CORP"
            set mode sla
            set dst "CORP_LAN"
            set src "BRANCH_LAN"
            config sla
                edit "HUB_HC"
                    set id 1
                next
            end
            set priority-members 3 4
        next
    end
end
```

Members meeting SLA 1 of `HUB_HC` are ranked first, by cost; members failing it drop below. If both meet the SLA, VPN1 (cost 0) wins; if only VPN2 meets it, VPN2 wins despite its higher cost. Related knobs:

| Knob | Effect |
|---|---|
| `tie-break` (rule) | When several members meet the SLA: `zone` (default, use the zone's `service-sla-tie-break`), `cfg-order`, `fib-best-match` (only members on the longest-match route), `input-device` |
| `service-sla-tie-break` (zone) | Default `cfg-order` |
| `minimum-sla-meet-members` | Rule takes effect only if at least this many members meet the SLA |
| `sla-compare-method` | `order` (default) or `number` of SLAs met |
| `hold-down-time` | Seconds to wait before moving back to the preferred member (default 0) |
| `sla-stickiness` | Keep existing sessions on their member while it still meets the SLA (default disable) |

> **Exam tip:** "Advantage" questions are usually about **best quality**: the first configured member wins ties and near-ties because of `link-cost-threshold` (10%). In **lowest cost**, order only matters among members with equal cost that meet the SLA.

## Choosing a strategy

| Traffic | Strategy | Reason |
|---|---|---|
| Voice/video to the DC over two overlays | Best quality on jitter or latency, or lowest cost with a tight SLA | React to quality, not just reachability |
| Bulk backups | Manual, MPLS last; or lowest cost with expensive links costed high | Predictable, cheap |
| SaaS on two DIA links | Lowest cost (SLA) with load balancing | Use both links while both are healthy |
| Guest Wi-Fi | Manual, one cheap link | No intelligence needed |
| Everything to the hub when any overlay is healthy | Lowest cost (SLA) over the overlay zone | Pass/fail, stable, cost expresses preference |

Best quality reorders members whenever the metric changes by more than the threshold, so it can move traffic more often than lowest cost, which only reacts when a member crosses its SLA. For most corporate traffic, lowest cost (SLA) gives the stablest behaviour.

## Lab it yourself

With the **FortiGate-VM trial** (two members on port1/port2, LAN on port3), build a best quality rule on latency, then add delay on one Linux gateway with `tc qdisc add dev eth1 root netem delay 30ms` and watch `diagnose sys sdwan service4` reorder the members only once the difference beats the 10% threshold. Swap to lowest cost (SLA) with a 50 ms latency threshold and repeat. Application steering needs an application control profile on the policy; without FortiGuard the trial's signatures are the ones bundled with the firmware, so use common applications.

## Key takeaways

- Rules match on source (address, user, input device), destination (address/port, ISDB, application, route tag, TOS) and protocol; all set fields must match.
- Application rules can't match the first session; the IPS engine learns a destination 3-tuple, and entries age out after **8 hours** without hits.
- ISDB destinations match from the first packet because they are IP/port lists.
- Strategies: manual (default), best quality (`priority`), lowest cost (`sla`), load balancing (`load-balance enable` under manual or sla), automatic (legacy).
- Best quality gives the first member a **10%** advantage (`link-cost-threshold 10`).
- Lowest cost: members meeting SLA, then lowest `cost`, then tie-break; load balancing under SLA ignores cost.
