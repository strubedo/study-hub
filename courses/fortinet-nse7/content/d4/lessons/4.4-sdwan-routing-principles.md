## The key principle: SD-WAN steers, routing permits

SD-WAN rules don't create reachability. They choose **among members that already have a route** to the destination. Keep three layers apart in your head:

| Layer | Built by | Answers |
|---|---|---|
| Routing table / FIB | Connected, static (including zone routes), IKE, BGP, OSPF routes | *Can* this member reach the destination? |
| SD-WAN rules (policy routes) | `config system sdwan` → `config service` | Which of the members that can reach it *should* carry this session? |
| Firewall policy | `config firewall policy` with SD-WAN zones as `dstintf` | *Is* the session allowed out of that zone? |

Every SD-WAN routing question on the exam is one of: a missing route, a route through the wrong member, a rule that never matches, or a session stuck on an old decision.

## Route lookup, step by step

For the first packet of a new session (and the first reply packet), FortiOS:

1. Checks **policy routes** in precedence order: `config router policy` > ISDB static routes > SD-WAN rules. A `config router policy` entry with `set action deny` means "do not search the policy route table" for matching traffic: it skips the remaining policy routes and SD-WAN rules and goes straight to the routing table.
2. For each SD-WAN rule that matches the traffic, applies the **FIB checks** for the member the strategy prefers: the best FIB match for the destination must be an SD-WAN member, and a FIB route to the destination must exist through that member. If no member qualifies, the rule is skipped.
3. Falls back to the **FIB**: longest prefix, then lowest distance, then lowest priority, then ECMP (the implicit rule for SD-WAN members).
4. Records the result in the session.

A regular policy route also needs a route: if only the outgoing interface is given, FortiOS looks up the gateway through that interface; if only the gateway is given, it looks up the interface; with both, the gateway must still be routable over the interface. If not, the policy route is skipped.

> **Exam tip:** Policy routes beat SD-WAN rules. A forgotten `config router policy` entry that matches the same traffic silently overrides your SD-WAN design. `diagnose firewall proute list` shows both, in evaluation order.

## Member static routes and zone static routes

In FortiOS 7.6, static routes toward SD-WAN reference **zones** with `sdwan-zone`:

```text
config router static
    edit 1
        set distance 1
        set sdwan-zone "WAN1" "WAN2"
    next
    edit 2
        set dst 10.0.0.0 255.0.0.0
        set sdwan-zone "HUB1"
    next
end
```

- A static route with `sdwan-zone` (no destination means 0.0.0.0/0) expands into one next hop **per member of the zone(s)**, using each member's `gateway` (or its DHCP/PPPoE dynamic gateway; IPsec members don't need one). In the kernel these appear as one route with several `gwy=... oif=...` entries.
- A route can still point at a **single member** (`set device "port1"` + `set gateway ...`). That makes only that member eligible for the destination, which is how you deliberately keep a member out of a rule's choices for some prefixes.
- Normal route selection still applies between members: equal distance + equal priority = ECMP across members; a worse priority keeps a member's route installed but out of ECMP.
- Each member also has `priority` (default 1), `priority-in-sla` / `priority-out-sla` (preferred route priority while the member is in or out of SLA, default 0) and `preferred-source` for the routes through that member.

### Health checks and route withdrawal

Under `config health-check`, `update-static-route` defaults to **enable**: when a member's health check declares it **dead** (not merely out of SLA), static routes through that member are removed from the routing table. `update-cascade-interface` (default enable) can bring other interfaces down with it when used with `fail-detect`. With static routes removed, rules and the implicit rule automatically stop using that member.

## Member probe routes

Health-check probes must leave through **each** member being measured, regardless of what the routing table prefers. SD-WAN therefore installs dedicated **kernel routes** to each health-check server through each member, using the member's interface IP or its `source` address. You see them with `diagnose ip route list` or `get router info kernel`, not in `get router info routing-table all`:

```text
FGT-Spoke1 # get router info kernel | grep 172.16.0.253
tab=254 vf=0 scope=0 type=1 proto=18 prio=0 172.16.0.1/255.255.255.255/0->172.16.0.253/32 pref=0.0.0.0 gwy=0.0.0.0 dev=19(HUB1-VPN1)
tab=254 vf=0 scope=0 type=1 proto=18 prio=0 172.16.0.1/255.255.255.255/0->172.16.0.253/32 pref=0.0.0.0 gwy=0.0.0.0 dev=20(HUB1-VPN2)
```

The `proto=` number isn't a reliable marker: the 7.6 guide shows these routes as `proto=18` in its BGP-on-loopback example and `proto=17` in its routing-concepts example. Recognize them by the source-specific prefix (`<source>/255.255.255.255/0-><server>/32`) and one entry per member.

Two consequences:

- Probe routes are **source-specific** (from the member's source IP) and stay in the kernel even when the probe fails. Any other traffic to the health-check server that happens to use the same source can follow them. That's why Fortinet puts the hub's health-check target (`HUB-Lo`) on a different loopback than the BGP peering address (`BGP-Lo`).
- IPsec tunnels in hub-and-spoke designs usually have no IP. Without `set source <loopback>` on the SD-WAN member, probes would leave with an unusable source; with it, the hub sees the probes from the spoke loopback and can route the replies.

## Rules and routes: the `gateway` and `default` options

Two CLI-only rule options change the FIB checks (both **disable** by default):

| `gateway` | `default` | FIB checks before the rule can use a member |
|---|---|---|
| disable | disable | Best match for the destination is an SD-WAN member **and** a route to the destination exists through the chosen member (normal behaviour) |
| enable | disable | Best match is an SD-WAN member **and** a route to the **member's gateway IP** exists over any interface |
| enable | enable | **No FIB checks**: matching traffic goes to the chosen member's configured `gateway`. Members must have a gateway configured |

```text
config system sdwan
    config service
        edit 5
            set name "PARTNER-VIA-WAN2"
            set dst "PARTNER_NET"
            set priority-members 2
            set gateway enable
            set default enable
        next
    end
end
```

Use them sparingly: they let a rule send traffic where the routing table has no route, which also means no RPF-friendly return path unless you build one.

## BGP with SD-WAN: route tags and communities

When the destination of a rule is learned dynamically (a data center whose prefixes change, or "everything the hub advertises with community X"), don't hard-code addresses. Tag the BGP routes and let the rule match the tag:

```text
config router community-list
    edit "CL-DC"
        config rule
            edit 1
                set action permit
                set match "65000:100"
            next
        end
    next
end
config router route-map
    edit "RM-HUB-IN"
        config rule
            edit 1
                set match-community "CL-DC"
                set set-route-tag 100
            next
            edit 2
            next
        end
    next
end
config router bgp
    config neighbor
        edit "172.16.0.254"
            set route-map-in "RM-HUB-IN"
        next
    end
end
config firewall address
    edit "DC_TAG_100"
        set type route-tag
        set route-tag 100
    next
end
config system sdwan
    config service
        edit 3
            set name "DC-APPS"
            set mode sla
            set dst "DC_TAG_100"
            config sla
                edit "HUB_HC"
                    set id 1
                next
            end
            set priority-members 3 4
        next
    end
end
```

- Rule 2 in the route map (no match, permit) passes untagged routes; without it the implicit deny would drop every route without the community.
- Check the tag with `get router info bgp network <prefix>` (`route tag 100`), the **RouteTag** column of `get router info bgp network`, `diagnose sys sdwan route-tag-list` (prefixes per tag and the rules reading them), and `diagnose firewall proute list` (the rule's destination now lists the tagged prefixes).
- The same `route-tag` address object can be used as the destination of a firewall policy.

Other BGP-to-SD-WAN couplings you should recognize (covered in domain 5): hubs signalling overlay health back to spokes with communities and `route-map-out-preferable` through `config system sdwan` → `config neighbor`, embedded SLA information in ICMP probes with `priority-in-sla`/`priority-out-sla` on the hub, and `recursive-inherit-priority` on BGP so recursive routes inherit the IKE route priority.

## Lab it yourself

On the **FortiGate-VM trial**, peer BGP with an FRR router behind port2, have FRR tag one prefix with community 65000:100, and match it into an SD-WAN rule with a `route-tag` address. Keep the learned prefixes to two so you stay within the three-route cap together with the default route. Delete the community on FRR and watch the prefix disappear from `diagnose sys sdwan route-tag-list` and the rule's proute entry.

## Key takeaways

- SD-WAN rules choose among members that have a route; missing routes are the first thing to check.
- Lookup order: policy routes > ISDB routes > SD-WAN rules > FIB (implicit rule).
- Static routes reference zones with `sdwan-zone`; one next hop per member using the member gateway.
- Health checks install source-specific kernel probe routes per member, which persist even when probes fail; use a separate hub loopback for health checks.
- `update-static-route` (default enable) removes a dead member's static routes.
- `gateway enable` changes the FIB check to "route to the member's gateway"; with `default enable` too, FIB checks are bypassed entirely.
- Match dynamic destinations with BGP communities → route map `set-route-tag` → `route-tag` address object in the rule.
