## FGCP in one paragraph

The FortiGate Clustering Protocol (FGCP) joins two or more FortiGates into one logical firewall. Members must be the **same model, same firmware and same hardware configuration** (for example the same number of disks), and should be registered to the **same FortiCare account**. Units find each other by sending heartbeat hellos; if **mode, group ID and password** match, they negotiate a cluster, elect a primary and synchronize configuration from it. All synchronization uses the heartbeat link (TCP/703 and UDP/703). The cluster shares virtual MAC addresses on the primary's interfaces so the network sees a single device.

## What is and is not synchronized

The primary pushes almost everything (incremental plus periodic sync, including the rest of `config system ha`). These are **not** synchronized:

| Not synchronized | Why it matters |
|------------------|----------------|
| Host name | Each member keeps its own name |
| HA device priority and virtual cluster priority | Lets you prefer one unit |
| HA override | Set it the same on every member yourself |
| Reserved management interface settings and `ha-mgmt-interface-gateway` | Each unit keeps its own out-of-band address |
| GUI dashboard widgets | Cosmetic |
| Most licences and subscriptions | Each unit is licensed individually (FortiToken Mobile is the exception). From 7.6.1, an A-P pair of 40F, 60F, 70F, 80F or 100F units bought with the HA SKU can share one FortiGuard bundle registered to a virtual serial number |

Check sync with `get system ha status` (Configuration Status: in-sync / out-of-sync) and `diagnose sys ha checksum cluster`, which prints global, per-VDOM and "all" checksums for each member.

## Primary unit election

Election runs when a cluster forms, a unit joins or leaves, or a monitored interface fails or recovers.

| Order | `override disable` (default) | `override enable` |
|-------|------------------------------|-------------------|
| 1 | Most connected monitored interfaces | Most connected monitored interfaces |
| 2 | HA uptime (age) | Device priority |
| 3 | Device priority | HA uptime (age) |
| 4 | Highest serial number | Highest serial number |

- `priority` is 0–255, default 128, and is not synchronized.
- Uptime only counts when the difference exceeds `ha-uptime-diff-margin` (default 300 s). Within the margin, uptime is a tie.
- A unit's HA uptime resets to zero when it reboots **or when one of its monitored interfaces fails**. That is why, with override disabled, a unit that had a link failure does not take the primary role back after the link recovers: the other unit is now "older".
- With override enabled, the highest-priority unit pre-empts whenever it can, which causes an extra failover each time it rejoins.

Fortinet recommends the same override setting on all members; mixed settings give unpredictable elections. The `Primary selected using` section of `get system ha status` records why each election went the way it did, and `diagnose sys ha dump-by group` shows the uptime difference used.

## Heartbeat interfaces and EtherTypes

| Setting | 7.6 detail |
|---------|-----------|
| `hbdev` | Interface plus priority pairs, for example `set hbdev "port3" 50 "port4" 50`. Default heartbeat ports have priority 50; a newly added one gets 0; range 0–512. The highest priority connected interface carries heartbeats; ties go to the lowest interface index |
| Count and type | Up to eight. Physical interfaces only, not switch ports, VLAN subinterfaces, IPsec interfaces, redundant or 802.3ad aggregate interfaces |
| Timers | `hb-interval` (units of 100 ms, default 2) × `hb-lost-threshold` = detection time. The Admin Guide shows a threshold of 20 (4 s); the 7.6.3 CLI Reference shows 6 and notes it varies by model, so check `get system ha` on your platform. `hb-interval-in-milliseconds 10` allows sub-second detection |
| `hello-holddown` | Seconds in hello state before work state (5–300, default 20); raise it for distant sites |
| Security | `authentication` and `encryption` (both off by default) protect heartbeats with SHA1 and AES-128 in ESP |
| `backup-hbdev` | New in 7.6.0: a backup heartbeat interface used only when a secondary hears nothing on the normal heartbeat links, to avoid split brain |

Heartbeat frames are layer 2 with non-IP EtherTypes:

| EtherType | Use | Change with |
|-----------|-----|-------------|
| 0x8890 | Heartbeat (discovery and status) | `ha-eth-type` |
| 0x8891 | Traffic redistribution from primary to subordinates in active-active (the CLI Reference calls it the transparent-mode heartbeat) | `hc-eth-type` |
| 0x8892 | Session synchronization over `session-sync-dev` interfaces | |
| 0x8893 | HA Telnet sessions: configuration sync and `execute ha manage` | `l2ep-eth-type` |

> **Real world:** 0x8892 is also the IEEE-registered EtherType of PROFINET, so a protocol analyzer such as Wireshark decodes FGCP session-sync frames as PROFINET. Do not let that mislead you when you capture a session-sync link, and keep these links off OT networks that carry real PROFINET.

> **Exam tip:** A switch between the units that filters unknown EtherTypes is a classic scenario. If the cluster forms but `execute ha manage` to the other unit fails, the switch is dropping 0x8893; change `l2ep-eth-type` on both units (for example to 889f) or fix the switch.

> **Watch out:** Two clusters on the same broadcast domain with the same `group-id` produce the same virtual MACs. Give every cluster in a layer 2 domain a unique group ID.

## Virtual MAC addresses

When a unit becomes primary, its interfaces take virtual MACs; secondaries keep their burned-in MACs (check with `diagnose hardware deviceinfo nic <port>`, where `Current_HWaddr` is the VMAC and `Permanent_HWaddr` the real MAC). On failover the new primary takes over the same VMACs and IPs and sends gratuitous ARPs (`arps` default 5, `arps-interval` default 8 s) so switches update their tables. If gratuitous ARPs are disabled, enable `link-failed-signal`, which bounces all interfaces for one second.

FortiOS 7.6.0 introduced the manual and hardware-MAC methods; the VMAC comes from the first method that applies:

1. Manual: `set virtual-mac` on the interface.
2. Automatic from the hardware MAC: `config system ha` → `set auto-virtual-mac-interface <ports>`; the primary's MAC with the locally administered bit set (00:... becomes 02:...).
3. Automatic from vcluster ID, group ID and physical index. For the common case (group ID below 256, vcluster 1 or 2, physical index below 128) the format is `00:09:0f:09:<group-id in hex>:<vcluster bit + physical index>`. The vcluster bit is 0 for vcluster 1 and adds 0x80 for vcluster 2. Group IDs above 255 and vclusters 3 to 30 (which need group ID 0–7) use an `e0:23:ff` prefix, and physical indexes above 127 use `70:4c:a5`.

Example: group ID 10, vcluster 1, port2 with physical index 2 (from `diagnose sys ha dump-by debug-zone`) gives `00:09:0f:09:0a:02`. VLAN subinterfaces inherit their parent's VMAC; redundant and aggregate interfaces use the VMAC of their first member; a reserved management interface keeps its own MAC.

## Session synchronization and sync optimization

Without session pickup, a failover is stateless: TCP sessions must be re-established.

| Option (`config system ha`) | Effect |
|-----------------------------|--------|
| `session-pickup enable` | Synchronizes TCP sessions (and is the prerequisite for the next options) |
| `session-pickup-connectionless enable` | Adds UDP and ICMP |
| `session-pickup-delay enable` | Only sessions older than 30 seconds are synchronized; cuts sync load from short-lived sessions |
| `session-sync-dev <ports>` | Moves session sync off the heartbeat link to dedicated interfaces, offloaded to the kernel. Uses EtherType 0x8892; if all of them fail, sync falls back to the heartbeat link |
| `sync-packet-balance enable` | Spreads sync packet processing over several CPUs (sync frames otherwise hash to one core because their MACs never change) |

Session sync always rides UDP/708 inside the layer 2 frame: 0x8892 when `session-sync-dev` is set, 0x8893 on the heartbeat interface otherwise. Most heartbeat bandwidth is session sync; it scales with connections per second and spikes when a unit joins because the whole session table is sent.

## Active-active load balancing

In `mode a-a` the primary owns the VMACs and receives **every** packet. It decides, per session, which member processes it, using `schedule` (default `round-robin`; also `none`, `leastconnection`, `weight-round-robin`, `random`, `ip`, `ipport`). Packets for a session handed to a subordinate are forwarded to it (EtherType 0x8891 redistribution) and the subordinate processes them without making its own load-balancing decisions.

What is actually load balanced:

| Load balanced | Always handled by the primary |
|---------------|-------------------------------|
| Proxy-based security profile sessions: proxy AV, proxy web filtering, email filtering, DLP over HTTP, FTP, IMAP(S), POP3(S), SMTP(S), NNTP | ICMP, multicast and broadcast |
| All TCP sessions only if `load-balance-all enable` (default disable; can reduce performance) | Flow-based inspection (IPS, application control, flow AV, flow web filter, flow DLP) |
| | IPsec VPN, agentless VPN, explicit web proxy, WAN optimization, WCCP, SSL offloading, VoIP, IM, P2P |
| | HTTPS through proxy inspection with certificate or deep inspection (and any custom HTTPS port in the SSL profile) |

Further limits: A-A cannot load balance sessions that cross regular or NPU VDOM links, does not support software switches, and does not appear in the mode list when an interface uses PPPoE (DHCP is fine). `schedule none` is for designs where external load-balancing switches spread traffic.

> **Exam tip:** "Active-active was enabled to double throughput, but the subordinate shows almost no sessions" usually means the traffic is flow-based or SSL-inspected in proxy mode, so it stays on the primary. A-A helps proxy-heavy designs; it is not a general throughput doubler.

## Lab it yourself

FGCP needs two FortiGates of the same model with licences. The FortiGate-VM permanent trial is limited to one VM per FortiCloud account, so a cluster lab needs two licensed VMs, two hardware units, or Fortinet's paid on-demand labs. On a single trial VM you can still:

- Read `show full-configuration system ha` to see the defaults (priority 128, `ha-eth-type 8890`, `hc-eth-type 8891`, `l2ep-eth-type 8893`, `ha-uptime-diff-margin 300`, schedule `round-robin`).
- Practice the VMAC calculation from `diagnose sys ha dump-by debug-zone` output on any lab or documentation capture.

## Key takeaways

- FGCP members need identical model, firmware and hardware; matching mode, group ID and password form the cluster.
- Override disabled: monitored interfaces, uptime (300 s margin), priority, serial. Override enabled: monitored interfaces, priority, uptime, serial.
- Hostname, HA priority, override and reserved management settings are not synchronized.
- Heartbeats use 0x8890 (heartbeat), 0x8891 (A-A redistribution), 0x8892 (session sync on session-sync-dev) and 0x8893 (HA Telnet/config sync); change them with ha-eth-type, hc-eth-type and l2ep-eth-type.
- The default VMAC is 00:09:0f:09:<group-id hex>:<vcluster bit + index>; unique group IDs avoid conflicts between clusters.
- Optimize sync with session-sync-dev, sync-packet-balance and session-pickup-delay.
- Active-active by default balances only proxy-based UTM sessions; flow inspection, IPsec and ICMP stay on the primary.
