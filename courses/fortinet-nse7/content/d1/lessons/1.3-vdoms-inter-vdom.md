## Multi-VDOM mode in FortiOS 7.6

A virtual domain (VDOM) is an independent firewall instance inside one FortiGate: its own interfaces, routing table, firewall policies, objects, VPNs and security profiles. FortiOS 7.6 has two VDOM modes:

```text
FGT-Hub # config system global
FGT-Hub (global) # set vdom-mode multi-vdom
FGT-Hub (global) # end
```

`vdom-mode` takes `no-vdom` or `multi-vdom` in 7.6 (the older split-task mode is not an option). You are logged out when the mode changes, all existing configuration moves into the **root** VDOM, and root can never be deleted. On FortiGate 90 series models and smaller, VDOMs can only be enabled from the CLI. FortiGate-VM supports at least two VDOMs (one admin type and one traffic type).

## VDOM types and the management VDOM

| Type | `config system settings` → `set vdom-type` | Purpose |
|------|---------------------------------------------|---------|
| Traffic | `traffic` | Normal firewall; passes traffic and can also allow admin access on its interfaces. Most VDOMs |
| Admin | `admin` | Only for administering the FortiGate from a management network. **Cannot pass traffic.** At most one admin VDOM per FortiGate; not available on FortiWiFi; cannot be in transparent mode |
| LAN extension | CLI only | Lets a remote FortiGate provide connectivity to a local FortiGate over a backhaul (FortiGate LAN extension) |

The **management VDOM** is a role, not a type. It is root by default, there is exactly one, and it sources the FortiGate's own management traffic: FortiGuard updates and queries, logs to remote servers, NTP and other local-out traffic. Change it in the global context:

```text
FGT-Hub # config global
FGT-Hub (global) # config system global
FGT-Hub (global) # set management-vdom "MGMT"
FGT-Hub (global) # end
```

If the management VDOM sits on a closed management network without internet access, FortiGuard breaks. Either give it internet access, or move FortiGuard to a traffic VDOM that has it:

```text
FGT-Hub (global) # config system fortiguard
FGT-Hub (fortiguard) # set vdom "root"
FGT-Hub (fortiguard) # end
```

That traffic VDOM also needs a route to the internet and DNS (per-VDOM DNS with `config system vdom-dns`, `set vdom-dns enable`).

> **Exam tip:** "FortiGuard updates fail after the root VDOM was moved to an isolated management network" → set `config system fortiguard` → `set vdom` to a VDOM with internet access (or change the management VDOM). Policies in other VDOMs do not help, because the traffic originates from the management VDOM.

## Global versus per-VDOM

| Global (`config global`) | Per VDOM (`config vdom` → `edit <name>`) |
|--------------------------|------------------------------------------|
| Physical interfaces, VLAN creation, interface-to-VDOM assignment | Firewall policies, addresses, services, VIPs, IP pools |
| HA, firmware, system DNS, global admin accounts | Static and dynamic routing, SD-WAN |
| VDOM links (`config system vdom-link`) | IPsec tunnels, security profiles, users |
| Global resources and per-VDOM resource limits | `config system settings` (opmode, `vdom-type`, central SNAT) |

- Per-VDOM resource limits are **unlimited by default**, so one VDOM can starve the others. Set maximums (and optionally guaranteed values) for sessions, policies, VPN tunnels and so on in Global > System > VDOM.
- An interface belongs to exactly one VDOM, and cannot be moved while it is referenced (the Ref. column in the interface list shows the references).
- **Global administrators** use `super_admin` and see everything. **Per-VDOM administrators** use `prof_admin` or a custom profile (`super_admin` cannot be used at VDOM level), can be assigned to several VDOMs only if created at global level, and can log in only through an interface of their VDOM (or the console).
- `set edit-vdom-prompt enable` in `config system global` asks for confirmation before editing a VDOM in the CLI.

## Inter-VDOM links

A VDOM link is a pair of virtual interfaces, one in each VDOM, like a crossover cable inside the box. It saves physical ports and keeps tenant traffic inside the FortiGate.

```text
FGT-Hub # config global
FGT-Hub (global) # config system vdom-link
FGT-Hub (vdom-link) # edit "TA-lnk"
FGT-Hub (TA-lnk) # end
FGT-Hub (global) # config system interface
FGT-Hub (interface) # edit "TA-lnk0"
FGT-Hub (TA-lnk0) # set vdom "Tenant-A"
FGT-Hub (TA-lnk0) # set ip 10.255.1.2 255.255.255.252
FGT-Hub (TA-lnk0) # next
FGT-Hub (interface) # edit "TA-lnk1"
FGT-Hub (TA-lnk1) # set vdom "root"
FGT-Hub (TA-lnk1) # set ip 10.255.1.1 255.255.255.252
FGT-Hub (TA-lnk1) # end
```

| Property | Detail |
|----------|--------|
| Interfaces | Creating link `X` creates `X0` and `X1`; assign each to a VDOM |
| Name | Up to 11 characters and must not match a VDOM name |
| Type | `ppp` (default, point-to-point) or `ethernet`; also `npupair` in the 7.6 CLI. Ethernet is needed when something requires layer 2 behaviour, for example an IPv6 link-local address for OSPFv3 neighbours, or DHCP client mode on the link |
| Offload | Regular VDOM links are not hardware accelerated. On NP6/NP7 models use the NPU VDOM links instead |
| HA | FGCP active-active cannot load balance sessions that cross regular or NPU VDOM links |
| Policies | Each VDOM the traffic crosses needs its own policy (and its own NAT decision) |

## Use case: internet access through inter-VDOM routing

In the **internet-access VDOM** topology one VDOM (often root) owns the internet connection; each tenant or department VDOM connects to it with a VDOM link. The internet VDOM controls all ingress and egress, and the tenant VDOMs cannot reach each other because there are no links between them.

```text
          Internet (203.0.113.0/24)
                |
              port1
        +--- root VDOM ---+
        |                 |
     TA-lnk1           TB-lnk1
   10.255.1.1/30     10.255.2.1/30
        |                 |
     TA-lnk0           TB-lnk0
   10.255.1.2/30     10.255.2.2/30
   Tenant-A VDOM     Tenant-B VDOM
   port2 10.1.0.0/16 port3 10.2.0.0/16
```

What each VDOM needs:

| VDOM | Route | Policy | NAT |
|------|-------|--------|-----|
| Tenant-A | `0.0.0.0/0` via 10.255.1.1 on `TA-lnk0` | port2 → TA-lnk0, with the tenant's own security profiles | Optional. If enabled, root only ever sees 10.255.1.2 |
| Root | `0.0.0.0/0` to the ISP on port1; routes back to 10.1.0.0/16 via 10.255.1.2 **if** Tenant-A does not NAT | TA-lnk1 → port1 | Required toward the internet (public address) |

The documented example enables NAT in both the tenant VDOM and the root VDOM, so root needs no routes to the tenant subnets. If you want per-host visibility and policies in root (for example a shared web filter that logs real user IPs), disable NAT on the tenant policy and add return routes in root instead.

Other topologies: **independent VDOMs** (no links, each with its own internet uplink; any of them can be the management VDOM if it has internet access), **meshed VDOMs** (full or partial mesh of links; the global admin creates links, tenants own the policies), and the **admin VDOM on a management network** with tenants in traffic VDOMs.

> **Watch out:** A ping from Tenant-A that reaches root but not the internet usually means the root VDOM policy (TA-lnk1 → port1) or its NAT is missing, or, when Tenant-A does not NAT, that root has no route back to the tenant subnet through TA-lnk1: root then drops the packets with `reverse path check fail, drop`, because its only route to the source is the default route through port1. A ping that never leaves Tenant-A means the tenant's own policy or default route is missing. Debug each VDOM separately: `diagnose debug flow` output is VDOM-aware.

## Virtual clustering link

When the FortiGate is an HA cluster, VDOMs are what virtual clustering partitions (previous topic). The root VDOM and the management VDOM must stay in virtual cluster 1.

## Lab it yourself

The FortiGate-VM permanent trial allows **two VDOMs, and root must be the admin type**. An admin VDOM cannot pass traffic, so the internet-access topology above (which needs at least two traffic VDOMs) does not fit in the trial. What does fit:

- Enable `multi-vdom`, observe that configuration moves into root, and create one traffic VDOM.
- Assign port2 and port3 to the traffic VDOM, keep port1 in root for management, and build one policy in the traffic VDOM (within the three-policy cap).
- Point `config system fortiguard` at the traffic VDOM and see where local-out traffic is sourced from (FortiGuard itself is not available in the trial, but the setting and the routing can be practised).
- Create a VDOM link between root and the traffic VDOM and give both ends addresses; you can ping across it, but root will not forward traffic. The link adds two interfaces (`<name>0`, `<name>1`); if they count against the trial's three-interface cap on your VM, drop port3 from the plan.

Inter-VDOM routing between traffic VDOMs and NPU VDOM links need a licensed FortiGate or hardware.

## Key takeaways

- 7.6 VDOM modes are no-vdom and multi-vdom; enabling multi-VDOM moves everything into root, which cannot be deleted.
- VDOM types: traffic (normal), admin (management only, no traffic, one per FortiGate), LAN extension (CLI only).
- The management VDOM sources FortiGuard, logging and other local-out traffic; move FortiGuard with `config system fortiguard` → `set vdom` if management is isolated.
- Per-VDOM resources are unlimited by default; per-VDOM admins use prof_admin or custom profiles and log in only through their VDOM's interfaces.
- VDOM links create X0 and X1, default to PPP, use Ethernet for layer 2 needs, and are not offloaded (use NPU VDOM links).
- In the internet-access topology each VDOM on the path needs its own policy; NAT in the tenant VDOM removes the need for return routes in root.
