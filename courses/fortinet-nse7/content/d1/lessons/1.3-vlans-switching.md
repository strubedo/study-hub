## VLANs on FortiGate

In NAT mode a FortiGate is a layer 3 device that terminates 802.1Q trunks. Each VLAN is a **VLAN subinterface** of a physical (or aggregate, or redundant) parent interface, with its own IP address, administrative access, role and VDOM. The FortiGate strips the tag on ingress, routes or inspects the packet, and tags it again (possibly with a different VLAN ID) on egress. Coming from Cisco, think "router on a stick with a firewall policy between every pair of subinterfaces".

```text
FGT-Hub # config system interface
FGT-Hub (interface) # edit "VLAN100-Users"
FGT-Hub (VLAN100-Users) # set vdom "root"
FGT-Hub (VLAN100-Users) # set interface "port2"
FGT-Hub (VLAN100-Users) # set type vlan
FGT-Hub (VLAN100-Users) # set vlanid 100
FGT-Hub (VLAN100-Users) # set ip 10.1.100.1 255.255.255.0
FGT-Hub (VLAN100-Users) # set allowaccess ping https
FGT-Hub (VLAN100-Users) # set role lan
FGT-Hub (VLAN100-Users) # next
FGT-Hub (interface) # edit "VLAN200-Servers"
FGT-Hub (VLAN200-Servers) # set vdom "root"
FGT-Hub (VLAN200-Servers) # set interface "port2"
FGT-Hub (VLAN200-Servers) # set type vlan
FGT-Hub (VLAN200-Servers) # set vlanid 200
FGT-Hub (VLAN200-Servers) # set ip 10.1.200.1 255.255.255.0
FGT-Hub (VLAN200-Servers) # end
```

Rules that show up in exam stems:

| Rule | Detail |
|------|--------|
| VLAN IDs | 1–4094. Two subinterfaces on the **same** physical interface cannot use the same VLAN ID; the same ID on **different** physical interfaces is allowed (they are separate broadcast domains to the FortiGate) |
| Untagged traffic | Handled by the parent physical interface itself |
| VDOMs | A VLAN subinterface can belong to a different VDOM than its parent. In multi-VDOM mode a VDOM administrator only sees the interfaces of their VDOM |
| Policies | Traffic between two VLANs is routed traffic and needs a firewall policy in each direction you want to allow. NAT is normally disabled between internal VLANs and enabled toward the internet |
| QinQ | `vlan-protocol 8021ad` on the outer subinterface, with 802.1Q subinterfaces under it |
| HA | VLAN subinterfaces use the parent's virtual MAC; they cannot be heartbeat interfaces |
| Transparent mode | The FortiGate bridges tagged frames between VLAN subinterfaces that share a VLAN ID on different ports (one policy per direction) and can still apply security profiles per VLAN; NAT is not available |

> **Watch out:** Interface addressing and VLAN IDs are not the only thing to match a Cisco trunk. If the switch's native VLAN is also carried as a tagged subinterface on the FortiGate, or vice versa, one side drops the frames. Decide whether the native VLAN maps to the physical interface (untagged) or not at all.

## Hardware switch, software switch and VLAN switch

Branch FortiGates have several copper ports in a default switch called `lan` or `internal`. Three ways exist to group ports:

| Feature | Hardware switch | Software switch | Virtual VLAN switch (VLAN switch mode) |
|---------|-----------------|-----------------|------------------------------------------|
| CLI | `config system virtual-switch` (interface `type hard-switch`) | `config system switch-interface` | `config system virtual-switch` with `set vlan <id>`, after `virtual-switch-vlan enable` |
| Processing | Switch chip / SPU in hardware | CPU | Switch chip, per-VLAN |
| Members | Ports of the internal switch chip | Any interfaces, including SSIDs and different physical ports | Ports of the internal switch chip |
| STP | Supported | Not supported | Built on the hardware switch |
| Wireless SSIDs | Not supported | Supported | Not supported |
| Intra-switch traffic | Allowed | Allowed by default; can require a policy | Allowed inside a VLAN; between VLANs needs routing and a policy |
| FGCP active-active load balancing | Supported | **Not supported** | Built on the hardware switch |
| One IP per | Switch | Switch | VLAN switch interface |

A port can join a hardware or software switch only if it is not referenced elsewhere and its IP is 0.0.0.0/0.0.0.0.

### Virtual VLAN switch

VLAN switch mode lets the hardware switch ports act as a real layer 2 switch with 802.1Q: ports are assigned to VLANs and one or more ports become trunks. In 7.6 it is supported on a defined list of models (among them the 40F, 60F, 70F, 80F, 90G, 100F, 120G, 200F, 400F, 600F, 900G and larger platforms; FortiWiFi 60F is not supported).

```text
FGT-Spoke1 # config system global
FGT-Spoke1 (global) # set virtual-switch-vlan enable
FGT-Spoke1 (global) # end

FGT-Spoke1 # config system virtual-switch
FGT-Spoke1 (virtual-switch) # edit "VLAN10"
FGT-Spoke1 (VLAN10) # set physical-switch "sw0"
FGT-Spoke1 (VLAN10) # set vlan 10
FGT-Spoke1 (VLAN10) # config port
FGT-Spoke1 (port) # edit "internal1"
FGT-Spoke1 (internal1) # next
FGT-Spoke1 (port) # edit "internal2"
FGT-Spoke1 (internal2) # end
FGT-Spoke1 (VLAN10) # end

FGT-Spoke1 # config system interface
FGT-Spoke1 (interface) # edit "VLAN10"
FGT-Spoke1 (VLAN10) # set ip 192.168.10.1 255.255.255.0
FGT-Spoke1 (VLAN10) # set type hard-switch
FGT-Spoke1 (VLAN10) # next
FGT-Spoke1 (interface) # edit "internal5"
FGT-Spoke1 (internal5) # set trunk enable
FGT-Spoke1 (internal5) # end
```

- `virtual-switch-vlan` is disabled when unset but enabled after a factory reset (CLI Reference note), and it must be enabled before VLAN switch settings appear in the GUI (System > Settings > VLAN switch mode).
- Remove ports from the default VLAN switch before reassigning them.
- Available ports and VLAN IDs depend on the model.

Two documented designs use it: **HA without external switches**, where each cluster member plugs both ISP routers into VLAN switch ports and a trunk port between the members carries the tagged ISP VLANs, giving a full mesh with no single point of failure; and **LAN extension**, where a branch FortiGate trunks its VLANs up to an upstream FortiGate that holds the matching VLAN subinterfaces.

> **Real world:** On a small branch the VLAN switch replaces a separate access switch: phones on one VLAN, PCs on another, the AP on a trunk port. If you need STP features beyond the switch chip, 802.1X or dozens of ports, use a managed FortiSwitch over FortiLink instead.

## Use case: segmentation through VLANs

A typical enterprise campus gives each trust zone its own VLAN and puts the FortiGate between them, which is internal segmentation (ISFW) in Security Fabric terms.

| VLAN | Subnet | Role | Allowed |
|------|--------|------|---------|
| 100 Users | 10.1.100.0/24 | lan | To servers on HTTPS/SMB; to internet with NAT and web filtering |
| 200 Servers | 10.1.200.0/24 | lan | Replies only; backups to 300 |
| 300 Backup | 10.1.250.0/24 | lan | Nothing initiated |
| 400 IoT | 10.1.40.0/24 | lan | Internet only, application control |

```text
FGT-Hub # show firewall policy 21
config firewall policy
    edit 21
        set name "Users-to-Servers"
        set srcintf "VLAN100-Users"
        set dstintf "VLAN200-Servers"
        set action accept
        set srcaddr "Users-Net"
        set dstaddr "Servers-Net"
        set schedule "always"
        set service "HTTPS" "SMB"
        set utm-status enable
        set ips-sensor "default"
        set logtraffic all
    next
end
```

Design points: use one firewall policy per allowed flow (implicit deny covers the rest), group VLANs into **zones** when several VLANs share the same policy set, keep the server VLAN's inbound inspection (IPS for server targets) separate from the user VLAN's outbound profiles, and remember that hosts on the same VLAN talk without crossing the FortiGate at all, so microsegmentation inside a VLAN needs FortiSwitch features or separate VLANs.

> **Exam tip:** "Two VLANs on the same FortiGate cannot reach each other although both gateways answer ping" is almost always a missing firewall policy (or one in only one direction for a protocol that needs return-initiated traffic), not a VLAN problem.

## Lab it yourself

The FortiGate-VM trial allows three interfaces, three policies and three routes. Plan around it:

- Use port1 for management/WAN and port2 as a trunk to a Cisco switch, with one VLAN subinterface (for example VLAN100). VLAN subinterfaces may count against the three-interface cap; check what your VM accepts and keep the total within three.
- Configure the Cisco side with `switchport mode trunk` and `switchport trunk allowed vlan 100`, put a Linux host in VLAN 100 and test with ping and `diagnose sniffer packet port2 'icmp' 4` to see the tagged frames arrive on the parent interface.
- One policy from VLAN100 to port1 with NAT uses one of your three policies.

Hardware switches and VLAN switch mode need a physical FortiGate model with an internal switch; FortiGate-VM has no switch chip.

## Key takeaways

- VLAN subinterfaces carry their own IP, access, role and VDOM; the same VLAN ID cannot repeat on one parent but can on different parents.
- Inter-VLAN traffic is routed through the FortiGate and needs firewall policies; zones simplify policy sets for many VLANs.
- Hardware switches are processed in hardware with STP; software switches are CPU-based, can include SSIDs, and do not support A-A load balancing.
- VLAN switch mode needs `virtual-switch-vlan enable`, assigns hardware switch ports to VLANs and supports trunk ports; it suits small branches and HA designs without external switches.
- VLAN subinterfaces inherit the parent's HA virtual MAC and cannot be HA heartbeat interfaces.
