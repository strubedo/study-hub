## Why the Security Fabric matters at architect level

The NSE 4 view of the Security Fabric is "join a downstream FortiGate to the root". At NSE 7 level the questions are about design: which device is root, what has to exist before the Fabric works, which integrations need a Fabric connector and which need an external connector, and what breaks when the pieces are missing. This lesson covers the Fabric skeleton, connector types, Fabric SAML SSO, FortiNAC dynamic addressing and FortiNDR. The next lesson covers automation stitches.

## Fabric roles and prerequisites

| Item | FortiOS 7.6 behaviour |
|------|------------------------|
| Root FortiGate | Usually the edge FortiGate. It shows the full Physical and Logical Topology; downstream units do not see devices upstream of them |
| Downstream FortiGates | Act as internal segmentation firewalls (ISFWs). Fortinet recommends no more than 35 downstream FortiGates |
| Small roots | FortiGate 40F and 60F series (2 GB RAM) can authorize at most five devices when they are the Fabric root. From 7.6.3 these 2 GB units lose the topology and Security Rating pages and do not appear in a root's topology (use `diagnose sys csf downstream`) |
| Operation mode | Every FortiGate in the Fabric must run in NAT mode |
| Logging | FortiAnalyzer, FortiAnalyzer Cloud or FortiGate Cloud is a **required** component. With several enrolled, the preference is FortiAnalyzer Cloud, then FortiAnalyzer, then FortiGate Cloud. With FortiGate Cloud, all downstream devices must belong to the same FortiCloud account |
| Fabric port | Downstream devices reach the upstream FortiGate on TCP 8013 by default (`upstream-port` under `config system csf`) |
| Name | All FortiGates in a Fabric use the same `group-name` |

The root is configured in **Security Fabric > Fabric Connectors > Security Fabric Setup** with the role *Serve as Fabric Root*, a Fabric name, and the interfaces that listen for join requests. Selecting a listening interface is the same as enabling **Security Fabric Connection** in that interface's administrative access. A downstream FortiGate uses *Join Existing Fabric* and the upstream IP or FQDN.

```text
FGT-Spoke1 # show system csf
config system csf
    set status enable
    set upstream "10.10.1.1"
    set group-name "Corp-Fabric"
end
```

Authorization happens on the root. A device can be **pre-authorized** by serial number or certificate in the trusted list (an entry can carry up to four HA member serials, so the secondary of a cluster is still trusted after a failover), or it can request to join and be approved later.

```text
FGT-Hub # diagnose sys csf authorization pending-list
FGT-Hub # diagnose sys csf authorization accept FGVM02TM00000002 Spoke1
```

A deauthorized device stays in `config trusted-list` with `set action deny`, which is why a "removed" FortiGate cannot simply rejoin until that entry is changed.

> **Exam tip:** If a scenario says the Fabric root shows no topology or the Fabric cannot be enabled, check the logging requirement first. No FortiAnalyzer or cloud logging means no Fabric.

> **Real world:** Branches commonly join the headquarters Fabric over their IPsec overlay. The hub's tunnel interface (or the loopback the branch targets) then needs Security Fabric Connection enabled, and the branch's upstream IP must be reachable through the tunnel.

## Fabric connectors versus external connectors

FortiOS 7.6 splits integrations into two GUI areas, and the exam likes to test which is which.

| | Fabric connectors | External connectors |
|---|---|---|
| GUI | Security Fabric > Fabric Connectors | Security Fabric > External Connectors |
| What they connect | Fortinet products that join the Fabric and exchange telemetry with the root | Third-party platforms, identity sources and threat feeds |
| Examples | Security Fabric Setup, Logging & Analytics (FortiAnalyzer, cloud logging), central management (FortiManager), FortiClient EMS, sandboxing, LAN edge devices (FortiAP, FortiSwitch, FortiExtender), supported connectors: FortiNAC, FortiNDR, FortiDeceptor, FortiMail, FortiMonitor, FortiTester, FortiVoice, FortiWeb | Public SDN (AWS, Azure, GCP, OCI, AliCloud, IBM Cloud), private SDN (Cisco ACI, VMware ESXi, NSX-T, Nutanix, OpenStack, Kubernetes), Endpoint/Identity (FSSO agent, Poll Active Directory, RADIUS SSO, Symantec endpoint, Exchange), threat feeds (FortiGuard category, IP address, domain name, MAC address, malware hash) |
| Visibility | Shown in the Physical and Logical Topology, can be logged in to from the topology | Feed objects (dynamic addresses, categories, hash lists) used in policies and profiles |
| Authorization | Device joins, then is authorized on the root (or pre-authorized) | Credentials or a URL configured on the FortiGate; no Fabric authorization |

The supported-connector workflow is the same for every Fortinet device: prepare the root, optionally pre-authorize, configure the device to join with the root's IP, then authorize it on the root and verify it in the topology. Some devices (the docs name FortiDeceptor, FortiMonitor and FortiNAC, plus the Fabric connector event trigger) also need **Allow downstream device REST API access** enabled on the root.

> **Watch out:** A threat feed is not a Fabric device. A question that describes an IP block list hosted on a web server is describing an external connector (IP address threat feed), not a Fabric connector.

## SAML single sign-on across the Fabric

Fabric SAML SSO lets an administrator log in once and move between Fabric members without re-entering credentials.

- **Only the root FortiGate can be the identity provider (IdP).** Downstream FortiGates are service providers (SPs).
- An SP must already be a Fabric member before SSO is configured on it.
- On the root: Security Fabric Setup card, enable **SAML Single Sign-On** (the mode fills in as IdP), set the **Management IP/FQDN** and **port** that SPs redirect users to, and choose the IdP certificate.
- On a downstream unit (from the root's topology or locally): *Auto* sets SP mode; *Manual* exposes the advanced SAML fields. Pick a default login page and a **default admin profile** for SSO users: from the root's Configure pane the choices are `prof_admin`, `super_admin` or `super_admin_readonly`; configured locally on the downstream unit, `admin_no_access` is also offered.
- The management IP/FQDN and port of the IdP and each SP must be reachable **from the administrator's browser**, not just from the other FortiGates.

```text
FGT-Hub # show system saml
config system saml
    set status enable
    set role identity-provider
    set cert "Fortinet_Factory"
    set server-address "10.10.1.1"
end

FGT-Spoke1 # config system sso-admin
FGT-Spoke1 (sso-admin) # edit "netops"
FGT-Spoke1 (netops) # set accprofile "prof_admin"
FGT-Spoke1 (netops) # set vdom "root"
FGT-Spoke1 (netops) # end
```

The CLI `role` default is `service-provider`, so on SPs the role line normally does not appear. SSO administrators appear under `config system sso-admin` on each SP; the access profile assigned there decides what they can do, not their rights on the root.

> **Exam tip:** "Users are redirected to the IdP but the browser times out" points at the Management IP/FQDN: the address the SP redirects to must be reachable from the client, for example a public or VPN-reachable address rather than an internal-only one.

## FortiNAC and dynamic firewall addresses

FortiNAC knows who and what is on each switch port or SSID. The Fabric integration turns that knowledge into firewall objects.

1. On the root FortiGate, enable the Fabric and **Allow downstream device REST API access** (FortiNAC requires REST API access to the FortiGate).
2. FortiNAC must have a license issued in 2020 or later that includes the additional certificate; older licenses cannot join.
3. On FortiNAC, configure telemetry with the root FortiGate's IP, then authorize FortiNAC on the root.
4. Verify with `diagnose sys csf downstream-devices fortinac`.

The **FortiNAC tag** dynamic address (a `type dynamic` address with `sub-type fortinac-tag`) holds the device IP, FortiNAC firewall tags and FortiNAC group information that FortiNAC sends through the REST API when it registers user logon and logoff events. You reference these objects in firewall policies like any address, and their membership changes as hosts come and go, so the policy follows the device rather than a fixed subnet. The same dynamic-address idea is used for FortiClient EMS tags (`ems-tag`), FortiVoice tags and FSSO groups; only the source of the IP-to-tag mapping differs.

> **Watch out:** The address object is only as current as the last logon or logoff event FortiNAC sent. If FortiNAC loses REST API access to the FortiGate (for example after an API admin trusted-host change), the object stops updating and policies keep matching stale IPs.

FortiNAC also works the other way round: the **FortiNAC Quarantine** automation action (next lesson) tells FortiNAC to quarantine a client and disable its MAC address. The 7.6 Admin Guide lists it for the Compromised Host and Incoming Webhook triggers.

## Adding FortiNDR (formerly FortiAI)

FortiNDR is Fortinet's network detection and response appliance; it was previously sold as FortiAI. Two separate integrations exist:

- **Fabric membership.** FortiNDR joins the Fabric (on FortiNDR: Security Fabric settings with the root FortiGate and FortiNDR addresses), is authorized on the root, then appears in the topology views and dashboard widgets. Make sure its pre-trained models (engines) are current.
- **Inline scanning with antivirus.** FortiNDR returns a verdict on high-risk files sent by the FortiGate antivirus profile.

```text
FGT-Hub # config system fortindr
FGT-Hub (fortindr) # set status enable
FGT-Hub (fortindr) # end

FGT-Hub # config antivirus profile
FGT-Hub (profile) # edit "av-ndr"
FGT-Hub (av-ndr) # set feature-set proxy
FGT-Hub (av-ndr) # config http
FGT-Hub (http) # set fortindr block
FGT-Hub (http) # end
FGT-Hub (av-ndr) # set fortindr-error-action log-only
FGT-Hub (av-ndr) # end
```

Key rules for inline inspection in 7.6:

| Rule | Detail |
|------|--------|
| Inspection mode | Proxy-based antivirus only; flow mode is not supported. FortiGate models with 2 GB RAM (40F and 60F series) have no proxy-based inspection from FortiOS 7.4.4, so they cannot use it |
| Licence | A licensed FortiNDR appliance is required |
| Actions | Per protocol (HTTP, FTP, IMAP, POP3, SMTP, MAPI, NNTP, CIFS, SSH): block, monitor, and so on |
| Error handling | `fortindr-error-action {log-only \| block \| ignore}` if FortiNDR fails |
| Precedence | The AV engine verdict always wins; if any AV method returns infected, the FortiNDR inspection is aborted |
| Logs | Virus logs with `eventtype="fortindr"`, `dtype="fortindr"`, message "Detected by FortiNDR." |

> **Exam tip:** "FortiNDR inline scanning is configured but no FortiNDR verdicts appear" with a flow-based AV profile has one answer: change the profile to proxy-based (`feature-set proxy`).

## Lab it yourself

The FortiGate-VM permanent trial is one VM per FortiCloud account and has no FortiGuard, so a real multi-FortiGate Fabric with a licensed FortiAnalyzer is beyond the free lab. What fits:

- On the trial VM, open Security Fabric > Fabric Connectors and External Connectors and walk through each card; note which require a device and which only need a URL or credentials.
- Create an IP address threat feed (external connector) pointing at a text file on a Linux web server in your lab, then reference it in one of your three firewall policies.
- Read `show full-configuration system csf` and `show full-configuration system saml` to see the defaults (`upstream-port 8013`, `role service-provider`).

A second FortiGate, FortiAnalyzer, FortiNAC or FortiNDR needs full licences, hardware or Fortinet's paid on-demand labs.

## Key takeaways

- The root FortiGate needs NAT mode and a logging component (FortiAnalyzer, FortiAnalyzer Cloud or FortiGate Cloud); downstream units join over TCP 8013 with the same group name.
- Fabric connectors integrate Fortinet devices that are authorized into the topology; external connectors pull data from SDN platforms, identity sources and threat feeds.
- In Fabric SAML SSO only the root can be the IdP; SPs must already be members, and every Management IP/FQDN must be reachable from the admin's browser.
- FortiNAC tag dynamic addresses are populated through the REST API on logon and logoff events, so the root must allow downstream REST API access.
- FortiNDR (formerly FortiAI) joins the Fabric for visibility and gives inline verdicts only to proxy-based antivirus profiles, with the AV engine verdict taking precedence.
- Pre-authorize Fabric devices by serial or certificate and include HA member serials so a failover does not break authorization.
