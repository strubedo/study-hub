## Stitch anatomy

An automation stitch is a **trigger** plus one or more **actions**. Triggers and actions are separate objects (Security Fabric > Automation, tabs *Stitch*, *Trigger*, *Action*; CLI `config system automation-trigger`, `config system automation-action`, `config system automation-stitch`), so one trigger can feed several stitches and one action can be reused.

| Property | FortiOS 7.6 behaviour |
|----------|------------------------|
| Where stitches are created | In a Security Fabric, **only on the root FortiGate**. Stitches also work on standalone FortiGates that are not in a Fabric |
| Fabric synchronization | `config automation setting` → `set fabric-sync {enable \| disable}` controls whether automation settings are synchronized to the Fabric |
| Execution | **Sequential** (default): actions run one after another, optional delay before each, and the chain **stops if an action fails**. **Parallel**: every action starts immediately |
| Delay | Up to 3600 seconds before an action (sequential only) |
| Concurrency | `max-concurrent-stitches` 32–256, default 128 |
| Variables | `%%log%%` and `%%log.<field>%%` from the trigger log; `%%results%%` (JSON) from the previous action, for example `%%results.x%%` |

```text
FGT-Hub # show system automation-stitch "HA-alert"
config system automation-stitch
    edit "HA-alert"
        set trigger "HA Failover"
        config actions
            edit 1
                set action "Email Notification"
                set required enable
            next
        end
    next
end
```

### Trigger types

Static triggers ship with FortiOS and need only a name and one setting; they can be edited but not deleted. Dynamic triggers need more settings.

| Trigger (GUI) | CLI `event-type` | Notes |
|---------------|------------------|-------|
| Compromised Host | `ioc` | An indicator of compromise is detected on a host endpoint. The trigger table says Access Layer Quarantine, FortiClient Quarantine, VMware NSX Security Tag and IP Ban are available only with this trigger (but see the webhook notes below) |
| High CPU | `high-cpu` | Fires at `config system global` → `cpu-use-threshold` (default 90 %, range 50–99) |
| Conserve Mode | `low-memory` | Memory crossed `memory-use-threshold-red` (default 88 %); exit at green (82 %); extreme 95 % drops new sessions |
| HA Failover | `ha-failover` | |
| Configuration Change | `config-change` | |
| Reboot | `reboot` | |
| License Expiry | `license-near-expiry` | Choose the licence type |
| FortiOS Event Log | `event-log` | One or more log IDs, optional field filters |
| Incoming Webhook | `incoming-webhook` | Called through the REST API with an API admin's key |
| FortiAnalyzer Event Handler | `faz-event` | A named FortiAnalyzer event handler fired |
| Fabric Connector Event | `fabric-event` | |
| Schedule | `trigger-type scheduled` | Hourly, daily (default), weekly, monthly or once |

FortiGate Cloud-Based IOC is a separate trigger that needs an IOC licence, a web filter licence and FortiCloud logging.

### Action types

| Action (GUI) | CLI `action-type` | Limits |
|--------------|-------------------|--------|
| Access Layer Quarantine | `quarantine` | Compromised Host, or Incoming Webhook with a `mac` in the payload. Quarantines the MAC on managed FortiSwitch and FortiAP |
| FortiClient Quarantine | `quarantine-forticlient` | Compromised Host, or Incoming Webhook with an `fctuid` (FortiClient UUID). EMS blocks the endpoint |
| IP Ban | `ban-ip` | Compromised Host in the Actions table (the Admin Guide's IP ban page also mentions an Incoming Webhook trigger). Blocks traffic from the flagged source; view in the Quarantine widget |
| VMware NSX Security Tag | `quarantine-nsx` | Compromised Host only |
| FortiNAC Quarantine | `quarantine-fortinac` | Compromised Host **or** Incoming Webhook. FortiNAC disables the host's MAC |
| System actions | `system-actions` + `system-action {backup-config \| reboot \| shutdown}` | Work even in conserve mode and skip CLI confirmation prompts. Reboot default minimum interval 300 s |
| CLI Script | `cli-script` | Needs an `accprofile`; output to the next action as `%%results%%` |
| Email, Slack, Microsoft Teams, FortiExplorer | `email`, `slack-notification`, `microsoft-teams-notification`, `fortiexplorer-notification` | Notifications |
| Webhook, AWS Lambda, Azure, Google Cloud, AliCloud functions | `webhook`, `aws-lambda`, ... | Cloud actions can be delayed after the previous action completes |
| Alert, Disable SSID | `alert`, `disable-ssid` | CLI only |

## Use case: automated quarantine with IoC detection

The default **Compromised Host Quarantine** stitch (disabled by default) chains the *Compromised Host* trigger to *Access Layer Quarantine* and *FortiClient Quarantine*. The flow at architect level:

1. Downstream FortiGates send logs to FortiAnalyzer.
2. FortiAnalyzer's Indicators of Compromise (IOC) service, a licensed FortiAnalyzer feature, checks the IPs, domains and URLs in those logs against the FortiGuard threat database and flags a host as compromised.
3. The root FortiGate's Compromised Host trigger fires with the host's IP and MAC.
4. Actions run: the MAC is quarantined on the managed FortiSwitch or FortiAP where the host connects, EMS isolates the endpoint, or the IP is banned. Stitches on the root can be relayed to other Fabric members (the `relayed to` / `relayed from` counters in autod output).
5. Quarantined hosts are flagged in the topology and listed in **Dashboard > Assets & Identities > Quarantine**, where an admin releases them.

```text
FGT-Hub # show system automation-stitch "Compromised Host Quarantine"
config system automation-stitch
    edit "Compromised Host Quarantine"
        set status enable
        set trigger "Compromised Host"
        config actions
            edit 1
                set action "Access Layer Quarantine"
            next
            edit 2
                set action "FortiClient Quarantine"
            next
        end
    next
end
```

> **Exam tip:** NSX tagging needs the Compromised Host trigger. A third-party SIEM or SOAR drives quarantine through an **Incoming Webhook**: the default *Incoming Webhook Quarantine* stitch (disabled by default) passes `mac` to Access Layer Quarantine and `fctuid` to FortiClient Quarantine, and FortiNAC Quarantine also accepts a webhook trigger. Pick the action that matches the access layer: FortiSwitch/FortiAP, EMS, or FortiNAC-controlled third-party switches.

> **Watch out:** The 7.6 Admin Guide contradicts itself here. Its Actions table describes Access Layer, FortiClient and IP Ban as Compromised Host only, yet the same guide ships the default Incoming Webhook Quarantine stitch that uses Access Layer and FortiClient Quarantine with a webhook, and its IP ban page names Incoming Webhook as a trigger for IP Ban. Trust the default stitch for Access Layer and FortiClient Quarantine; treat IP Ban with a webhook as unconfirmed until you test it.

> **Watch out:** Access Layer Quarantine needs the host to sit behind a managed FortiSwitch or FortiAP. A host on an unmanaged switch is not affected; use IP Ban or EMS for it.

## Use case: configuration backups

Three designs appear in the docs and in exam scenarios:

| Design | Trigger | Action | Result |
|--------|---------|--------|--------|
| Local revision on disk | Schedule (or Conserve Mode, Configuration Change) | System action **Backup Config Disk** | A revision on the FortiGate; listed under *Configuration > Revisions* and `execute revision list config` ("Autod backup config by stitch: ...") |
| Off-box backup | Schedule | CLI Script with `execute backup config ftp ...` or `tftp` | A file on an external server |
| Fabric-wide | Schedule on the root | CLI Script with `execute-security-fabric enable` | Every Fabric FortiGate runs the script |

```text
FGT-Hub # config system automation-trigger
FGT-Hub (automation-trigger) # edit "nightly-0200"
FGT-Hub (nightly-0200) # set trigger-type scheduled
FGT-Hub (nightly-0200) # set trigger-frequency daily
FGT-Hub (nightly-0200) # set trigger-hour 2
FGT-Hub (nightly-0200) # set trigger-minute 0
FGT-Hub (nightly-0200) # end

FGT-Hub # config system automation-action
FGT-Hub (automation-action) # edit "Backup Config Disk"
FGT-Hub (Backup Config Disk) # set action-type system-actions
FGT-Hub (Backup Config Disk) # set system-action backup-config
FGT-Hub (Backup Config Disk) # end
```

> **Watch out:** With `execute-security-fabric enable`, every Fabric member runs the same `execute backup config ftp` command at the same moment. If the file name is identical, the backups overwrite each other on the FTP server. Include a per-device file name, or run the stitch locally on each device.

System actions exist because a CLI script cannot answer confirmation prompts (for example the reboot "Do you want to continue? (y/n)"), and because they still run in conserve mode.

## Use case: CLI scripts for high CPU

When CPU crosses `cpu-use-threshold`, the High CPU trigger can run a diagnostic CLI script and mail the output, so you see the process list from the moment of the spike rather than after it has passed.

```text
FGT-Hub # config system automation-action
FGT-Hub (automation-action) # edit "cpu-debug"
FGT-Hub (cpu-debug) # set action-type cli-script
FGT-Hub (cpu-debug) # set script "diagnose sys top 5 20 2
get system performance status
diagnose sys session full-stat"
FGT-Hub (cpu-debug) # set accprofile "super_admin"
FGT-Hub (cpu-debug) # set timeout 60
FGT-Hub (cpu-debug) # next
FGT-Hub (automation-action) # edit "cpu-mail"
FGT-Hub (cpu-mail) # set action-type email
FGT-Hub (cpu-mail) # set email-to "noc@example.com"
FGT-Hub (cpu-mail) # set email-subject "High CPU on %%log.devname%%"
FGT-Hub (cpu-mail) # set message "%%results%%"
FGT-Hub (cpu-mail) # end
```

CLI script options worth knowing: `minimum-interval` (0 = no limit, default 0) limits how often the action runs; `output-size` defaults to 10 MB; `timeout` is 0–300 s (0 = none); `execute-security-fabric` defaults to disable; `accprofile` is required to give the script rights. Output that exceeds 64 KB is sent as an attachment by the following email action, and the email buffer for `%%results%%` is limited to 192K characters. Some diagnose commands that print from daemons produce no output in a CLI script.

## Testing and troubleshooting

| Command | Shows |
|---------|-------|
| `diagnose automation test <stitch>` | Fires the stitch now |
| `diagnose test application autod 1` | Toggles log dumping for autod |
| `diagnose test application autod 2` | Settings of every active stitch: trigger, actions, destinations |
| `diagnose test application autod 3` | Statistics: local hits, relayed hits, last trigger time, per-action done counts, next scheduled run |

```text
FGT-Hub # diagnose test application autod 3
stitch: nightly-backup (scheduled)
local hit: 0 relayed to: 0 relayed from: 0
last trigger:   last relay:
next scheduled trigger:Fri Oct 30 02:00:00 2026
actions:
Backup Config Disk:
done: 0 relayed to: 0 relayed from: 0
```

The GUI equivalent is the *Last Triggered* column on the Stitch tab, plus "Automation stitch triggered" event logs.

## Lab it yourself

Stitches fit the FortiGate-VM trial well because they need no extra interfaces, policies or routes:

- Build a Schedule trigger (frequency once, a few minutes ahead) with Backup Config Disk, then check `execute revision list config`.
- Build a High CPU stitch with a CLI script and an email action that uses your own SMTP relay (`config system email-server`); FortiGuard's default mail relay may not be usable without FortiGuard. Fire it with `diagnose automation test`.
- Build an Incoming Webhook trigger and call it with curl using a REST API admin key from a Linux host.

Compromised Host (needs a FortiAnalyzer licensed for the IOC service), Access Layer Quarantine (needs managed FortiSwitch/FortiAP), FortiClient and FortiNAC quarantine need licensed products beyond the trials.

## Key takeaways

- A stitch is trigger + actions; in a Fabric it is created only on the root, and sequential execution stops at the first failed action.
- NSX tagging requires the Compromised Host (IoC) trigger; Access Layer, FortiClient and FortiNAC Quarantine work with Compromised Host or an Incoming Webhook (the default Incoming Webhook Quarantine stitch). The docs disagree on whether IP Ban accepts a webhook.
- System actions (backup-config, reboot, shutdown) run in conserve mode and avoid confirmation prompts that CLI scripts cannot answer.
- Schedule triggers default to daily; backups can go to local revisions, to FTP/TFTP through a CLI script, or Fabric-wide with execute-security-fabric.
- High CPU fires at cpu-use-threshold (default 90 %); pair a CLI script with an email action that sends `%%results%%`.
- Verify with `diagnose automation test` and `diagnose test application autod 2/3`.
