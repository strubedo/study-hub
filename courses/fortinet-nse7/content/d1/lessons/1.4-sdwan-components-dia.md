## SD-WAN fundamentals

FortiOS SD-WAN bundles the physical and logical transports of a site (the **underlays**: broadband, MPLS, 4G/5G, satellite) and the VPNs built on top of them (the **overlays**) into one steering domain. Health checks measure every path, and rules steer each application or destination to the path that meets its needs. The routing table still decides *which* paths can reach a destination; SD-WAN rules decide *which of those* a session uses.

Fortinet describes three layers, of which only the middle one must be a FortiGate:

| Layer | Functions | Products |
|-------|-----------|----------|
| Management and orchestration | Templates, zero-touch provisioning, logging and analytics, REST API automation | FortiManager, FortiAnalyzer |
| Control, data plane and security | Underlays and overlays in zones, ADVPN, routing, NGFW, health checks, application-aware steering | FortiGate |
| Network access | Wired and wireless segmentation, built-in NAC | FortiSwitch, FortiAP (SD-Branch) |

The **five-pillar** design approach (from Fortinet's SD-WAN architecture guides) is a useful checklist for any design question:

| Pillar | Decide |
|--------|--------|
| Underlay | Which WAN links, their bandwidth, quality (loss, latency, jitter), reliability and cost |
| Overlay | Whether sites must talk to each other and how: hub-and-spoke IPsec, ADVPN for scale |
| Routing | Static for a few destinations; BGP (or OSPF) over overlays when many sites must exchange routes |
| Security | Firewall policies and profiles per path; group underlays and overlays into zones |
| SD-WAN | Members, zones, performance SLAs and rules: the steering intelligence |

## SD-WAN basic components

| Component | CLI | Key facts |
|-----------|-----|-----------|
| Member | `config system sdwan` → `config members` | Any interface type: physical, VLAN, LAG, IPsec, GRE, IPIP, FortiExtender. Must not be referenced elsewhere when added. `gateway`, `cost` (0–4294967295, default 0, lower preferred), `priority` (1–65535, default 1, lower preferred), `weight`, `volume-ratio`, spillover thresholds, `source` (health-check source IP, needed on IP-less tunnels) |
| Zone | `config zone` | Groups members; **zones, not members, are used in firewall policies**. Default zone `virtual-wan-link`. A member must be in a zone. Zones can also be used in static routes, SD-WAN rules, local-in, DoS and multicast policies and central SNAT |
| Performance SLA (health check) | `config health-check` | Probes servers over member interfaces; active, passive or prefer-passive. Removes routes from failed members (`update-static-route enable` default) |
| SD-WAN rule (service) | `config service` | Matches traffic and picks a member by strategy. When no rule matches, the **implicit rule** load balances using `load-balance-mode` (default `source-ip-based`) |

Architecture components around them: the static routes (usually a default route to an SD-WAN zone), firewall policies that reference zones, NAT on internet-bound policies, and for overlays the IPsec tunnels plus a dynamic routing protocol.

### Use case identification

| Requirement | Typical SD-WAN design |
|-------------|------------------------|
| Branch uses SaaS and the internet directly, two ISPs | DIA with underlays in zones, health checks to internet targets, rules per application |
| Branch reaches data centre apps | Overlays (IPsec to hubs) in an overlay zone, health checks to the hub loopback, lowest cost (SLA) rules preferring the primary DC |
| Internet must be inspected centrally, or the branch has only MPLS | Remote internet access (RIA) through the hub over the overlay |
| Internet locally, but fail over to the hub when local links fail | Hybrid: DIA preferred, RIA as backup member in the same rule |
| Many branches need branch-to-branch | ADVPN shortcuts (Domain 5) |

## Direct internet access (DIA)

### DIA topologies

| Topology | Path for internet traffic | Pros | Cons |
|----------|---------------------------|------|------|
| **Local breakout (DIA)** | Branch underlays straight to the internet | Lowest latency to SaaS, no hub bandwidth cost | Each branch must enforce security itself (NGFW profiles on the branch FortiGate) |
| **Remote internet access (RIA)** | Branch overlay to the hub, out of the hub's WAN | Central inspection and one egress IP | Hub bandwidth and latency; hub is a dependency |
| **Hybrid DIA + RIA** | DIA first, overlay to the hub as fallback (for example a branch with one ISP plus MPLS) | Survives ISP loss | Needs a policy to the overlay zone for internet destinations, and the hub must allow and NAT it |
| **Cloud security breakout** | Branch to a cloud security service (for example FortiSASE secure edge) | Central policy without hub backhaul | Separate service and licensing |

### DIA best practices and recommended settings

1. **Zones by purpose.** Keep internet underlays separate from private underlays (MPLS) and from overlays. A common DIA layout is one zone per ISP (`WAN1`, `WAN2`) or both ISPs in one internet zone; do not mix MPLS into the internet zone just because it is a WAN link.
2. **Default route to the zone(s), not to every member.** One static route with `set sdwan-zone "WAN1" "WAN2"` (or one route per zone). In mixed environments, pointing the default route at members that have no internet path (MPLS, overlays) creates black holes. A default route through an SD-WAN zone has distance 1 by default.
3. **Gateways on members.** Static members need `set gateway`; DHCP and PPPoE members learn it. DHCP interfaces install their own default route with distance 5 unless `defaultgw` is disabled or the distance is set to match.
4. **Health checks that reflect the path.** Probe something on the internet that represents the service, define **two servers** (both must fail before the member is declared dead), keep the defaults (`interval` 500 ms, `failtime` 5, `recoverytime` 5) unless you need faster or more stable behaviour, and remember each server IP can be used by only one health check. The five predefined SLAs (DNS, FortiGuard, Gmail, Google Search and Office 365, present on factory-reset units and new VDOMs) carry Fortinet's recommended settings; add the participants. HTTP and HTTPS probes automatically use a 120 000 ms interval.
5. **SLA targets close to the application's real limits.** Too tight and traffic flaps between links; too loose and the SLA adds nothing.
6. **Rules from specific to general.** Application or ISDB-based rules for critical SaaS (best quality on latency, or lowest cost with SLA), then broader rules, then let the implicit rule handle the rest.
7. **Policies reference zones and NAT to the egress interface.** One policy LAN → WAN zone(s) with NAT, security profiles and logging enabled (logging lets you verify steering in the traffic logs).
8. **Security for DIA.** Antimalware on all user traffic, web filtering on HTTP/HTTPS, application control everywhere, IPS for client targets on web traffic, and SSL inspection where the business allows it. Lock down inbound access.

> **Exam tip:** Members are never selected as the destination interface of a firewall policy; only zones are. A stem with "the policy uses port1 as the outgoing interface" on an SD-WAN member is a configuration that FortiOS does not allow.

> **Watch out:** `update-static-route` (enabled by default) withdraws every static route through a member whose health check fails, whether or not that traffic is steered by SD-WAN. On overlays this can also pull routes you still need; think about it before attaching a health check to tunnel members.

## Use case: basic SD-WAN DIA setup

Two ISPs on FGT-Spoke1: port1 (WAN1, static) and port2 (WAN2, DHCP), LAN on port3.

```text
FGT-Spoke1 # config system sdwan
FGT-Spoke1 (sdwan) # set status enable
FGT-Spoke1 (sdwan) # config zone
FGT-Spoke1 (zone) # edit "WAN1"
FGT-Spoke1 (WAN1) # next
FGT-Spoke1 (zone) # edit "WAN2"
FGT-Spoke1 (WAN2) # end
FGT-Spoke1 (sdwan) # config members
FGT-Spoke1 (members) # edit 1
FGT-Spoke1 (1) # set interface "port1"
FGT-Spoke1 (1) # set zone "WAN1"
FGT-Spoke1 (1) # set gateway 192.0.2.1
FGT-Spoke1 (1) # next
FGT-Spoke1 (members) # edit 2
FGT-Spoke1 (2) # set interface "port2"
FGT-Spoke1 (2) # set zone "WAN2"
FGT-Spoke1 (2) # end
FGT-Spoke1 (sdwan) # config health-check
FGT-Spoke1 (health-check) # edit "Internet"
FGT-Spoke1 (Internet) # set server "1.1.1.1" "8.8.8.8"
FGT-Spoke1 (Internet) # set protocol ping
FGT-Spoke1 (Internet) # set members 1 2
FGT-Spoke1 (Internet) # config sla
FGT-Spoke1 (sla) # edit 1
FGT-Spoke1 (1) # set latency-threshold 150
FGT-Spoke1 (1) # set jitter-threshold 30
FGT-Spoke1 (1) # set packetloss-threshold 2
FGT-Spoke1 (1) # end
FGT-Spoke1 (Internet) # end
FGT-Spoke1 (sdwan) # end

FGT-Spoke1 # config router static
FGT-Spoke1 (static) # edit 1
FGT-Spoke1 (1) # set sdwan-zone "WAN1" "WAN2"
FGT-Spoke1 (1) # end
```

Then the policy (port3 → WAN1 and WAN2 zones, NAT enabled, profiles, `logtraffic all`) and, if needed, a rule such as "Office 365 and Teams by best quality on latency" or "everything else lowest cost (SLA) preferring WAN1". Finally, align the DHCP member: the DHCP default route has distance 5 while the SD-WAN zone route has distance 1, so set the interface `distance` or let the zone route win; for a 50/50 implicit-rule split both members must end up with equal-cost routes.

```text
FGT-Spoke1 # get router info routing-table static
S*      0.0.0.0/0 [1/0] via 192.0.2.1, port1
                  [1/0] via 198.51.100.1, port2
```

Both default routes are installed with the same distance and priority, which is what lets the implicit rule (and rules with several members) use either link.

## Lab it yourself

This lab fits the FortiGate-VM trial exactly: three interfaces (port1 and port2 as ISPs, port3 as LAN), one policy (port3 → WAN zones), one static route to the zones. Use two Cisco IOS routers as "ISPs", each with a loopback (for example 192.0.2.254/32 and 198.51.100.254/32) as health-check targets reachable through both links, and a Linux host on port3. Break one ISP with `shutdown` on the Cisco interface or by adding loss with `tc qdisc` on a Linux router and watch the SLA change. FortiGuard-based items (ISDB application rules, the FortiGuard SLA profile) need FortiGuard, which the trial does not have; use address-based rules instead.

## Key takeaways

- SD-WAN = members in zones + performance SLAs + rules; the routing table supplies candidate paths and rules pick among them.
- Zones, not members, go in firewall policies; the default zone is virtual-wan-link.
- Member cost (default 0) and priority (default 1) are both "lower is preferred"; IP-less tunnels need a `source` for health checks.
- DIA breaks out locally; RIA backhauls through the hub; hybrid designs use DIA first and the overlay as fallback.
- Point the default route at internet zones, use two health-check servers per SLA, set realistic SLA targets and enable NAT and logging on the DIA policy.
- update-static-route (default enable) removes all static routes through a failed member.
