## Virtual clustering: FGCP per VDOM

Virtual clustering extends FGCP to multi-VDOM FortiGates. Each **virtual cluster** (vcluster) is its own active-passive FGCP cluster made of the same members, holding a set of VDOMs, with its own primary. So FGT-A can be primary for some VDOMs while FGT-B is primary for others, and both boxes forward traffic. This is **VDOM partitioning**, the standard answer when a multi-tenant or high-volume design needs both units busy without the limits of active-active.

```text
FGT-A # config system ha
FGT-A (ha) # set mode a-p
FGT-A (ha) # set group-id 5
FGT-A (ha) # set vcluster-status enable
FGT-A (ha) # config vcluster
FGT-A (vcluster) # edit 1
FGT-A (1) # set vdom "root" "Tenant-A"
FGT-A (1) # set override enable
FGT-A (1) # set priority 200
FGT-A (1) # next
FGT-A (vcluster) # edit 2
FGT-A (2) # set vdom "Tenant-B"
FGT-A (2) # set override enable
FGT-A (2) # set priority 50
FGT-A (2) # end
FGT-A (ha) # end
```

FGT-B mirrors this with the priorities reversed (50 for vcluster 1, 200 for vcluster 2). Rules for 7.6:

| Rule | Detail |
|------|--------|
| Mode | Each vcluster is an active-passive FGCP cluster |
| Number | Up to 30 virtual clusters (from FortiOS 7.2.0; earlier releases allowed two) |
| Group ID | 0–7 with virtual clusters (Admin Guide; the CLI Reference says with more than two vclusters); change it before enabling vclusters |
| Root and management VDOM | Can only be in virtual cluster 1 |
| Per vcluster | `vdom`, `priority` (default 128), `override`, `monitor`, `pingserver-monitor-interface` and related timers |
| Heartbeat | One set of heartbeat interfaces for all vclusters |
| Override | Typically enabled so the priorities pin each vcluster to its preferred unit; if you disable it, disable it on both units |
| Three or four members | The first and second units process traffic; the others stand by. Fortinet recommends as many vclusters as members |

On failover of a whole unit, the survivor becomes primary for every vcluster; when the unit returns, the configured split is restored. `get system ha status` lists `vcluster 1: work ...` and `vcluster 2: standby ...` per unit, and `get system ha status <n>` filters to one vcluster.

> **Exam tip:** "Both units must forward traffic for different customers, each customer's failover must be independent, and sessions cross inter-VDOM links" points to virtual clustering, not active-active: A-A cannot load balance sessions over VDOM links and only balances proxy UTM sessions.

## FGSP: session sync between peers

The FortiGate Session Life Support Protocol (FGSP) synchronizes **sessions only** between peers that each make their own forwarding decisions. An upstream load balancer, ECMP router or cloud fabric distributes traffic; if a peer fails, traffic moves to another peer that already has the sessions. If the balancer sends everything to one peer, the result resembles active-passive; if it spreads traffic, it resembles active-active.

Scale: 2 to 16 standalone FortiGates, or 2 to 16 FGCP clusters of two members each (FGCP over FGSP). In `config system ha` the peers stay in `mode standalone`.

### Sample FGSP standalone sync

```text
FGT-A # config system standalone-cluster
FGT-A (standalone-cluster) # set standalone-group-id 1
FGT-A (standalone-cluster) # set group-member-id 0
FGT-A (standalone-cluster) # config cluster-peer
FGT-A (cluster-peer) # edit 1
FGT-A (1) # set peerip 10.99.0.2
FGT-A (1) # end
FGT-A (standalone-cluster) # end

FGT-A # config system ha
FGT-A (ha) # set session-pickup enable
FGT-A (ha) # set session-pickup-connectionless enable
FGT-A (ha) # set session-pickup-nat enable
FGT-A (ha) # end
```

| Setting | Range / default | Meaning |
|---------|-----------------|---------|
| `standalone-group-id` | 0–255, default 0 | Must match on all peers |
| `group-member-id` | 0–15, default 0 | Unique per peer (or per FGCP cluster) |
| `peerip` | | Peer address; by default sync is layer 3 via the interface that routes to it, UDP-encapsulated |
| `peervd` / `syncvd` | `peervd` default root | In multi-VDOM mode: the peer VDOM holding the sync link and the VDOMs whose sessions are synchronized |
| `session-sync-dev` | | Dedicated directly connected link(s): layer 2, kernel-offloaded, no UDP encapsulation; falls back to layer 3 if they fail |
| `config session-sync-filter` | | Limit sync by `srcintf`, `dstintf`, `srcaddr`, `dstaddr`, IPv6 equivalents and `custom-service` port ranges |
| `ipsec-tunnel-sync` | default enable | Synchronize IPsec tunnels |
| `hb-interval` / `hb-lost-threshold` | 2 (×100 ms) / 10 | Peer heartbeat |
| `down-intfs-before-sess-sync` | | Keep named interfaces down at boot until sessions are synchronized (60 s timeout) |

Session tables only line up if names match: firewall policy IDs and interface names, IPsec interface names and VDOM names must be identical on the peers.

### Coverage and limits

| Synchronized | Condition |
|--------------|-----------|
| IPv4 and IPv6 TCP sessions, IPsec tunnels | By default |
| UDP and ICMP (connectionless) | `session-pickup enable` + `session-pickup-connectionless enable` |
| Expectation sessions (FTP data, SIP media) | `session-pickup enable` + `session-pickup-expectation enable` |
| NAT sessions | `session-pickup enable` + `session-pickup-nat enable` |
| SCTP, RSSO user logon information | Listed by the FGSP overview as supported |

Limits to remember: in NAT mode only sessions of route-mode firewall policies are synchronized (normal transparent policies in transparent mode). NAT sessions survive a failover only if they use an **IP pool** (overload type is the default) that the surviving peer also owns; sessions NATed to the failed peer's interface IP have nowhere to go. Same model and firmware is strongly recommended. Every extra peer costs CPU, memory and sync bandwidth.

### Standalone configuration sync

FGSP does not synchronize configuration. `standalone-config-sync` (under `config system ha`) is a separate feature that copies configuration from one standalone FortiGate to others over heartbeat interfaces, using the HA primary-selection logic (so set priority and override on the unit that should be the source). Settings that identify a device on the network (interface IPs, host name and similar) are not copied. `get system ha status` shows `Mode: ConfigSync`. Limits: all members upgrade firmware simultaneously (outage if they are the only gateways), unwanted objects may sync, and the wrong unit can win the election and overwrite good configuration. Fortinet recommends disabling it once the configuration has been copied. A layer 3 unicast variant (`unicast-status enable`, `config unicast-peers`, `unicast-gateway`) supports clouds without layer 2.

## Asymmetric traffic with inspection

Stateful inspection needs both directions of a session on one box. With FGSP, when return traffic lands on the "wrong" peer, FortiOS can forward it to the **session owner** (the peer that saw the first packet), which inspects it. Fortinet warns that this bouncing costs performance.

| Use case | Configuration | How traffic returns to the owner |
|----------|---------------|----------------------------------|
| Layer 2 (peers share subnets, back-to-back or switched) | `set layer2-connection available`, `unset session-sync-dev`, `peerip`, policy with `utm-status enable` | Re-sent to the owner's MAC address at layer 2 |
| Layer 3 / cloud (no shared layer 2, peers in different subnets) | `set layer2-connection unavailable` (default), `unset session-sync-dev`, `peerip` | Packed in UDP and sent between peer interfaces |
| Encrypted layer 3 | add `set encryption enable` and `set psksecret <key>` (the same key) on both peers | The Admin Guide presents it as encrypting the return traffic forwarded to the owner over layer 3; the CLI Reference describes `encryption` as "encryption when synchronizing sessions" |

Asymmetric UTM inspection applies to TCP; UDP and ICMP are not supported. From 7.6.0, if the owner becomes unavailable or unhealthy (device down, `monitor-interface` down, `pingsvr-monitor-interface` failing), peers stop bouncing to it and process the traffic themselves, without UTM scanning during the failover. From 7.6.4, `helper-traffic-bounce` and `utm-traffic-bounce` can be disabled, at the cost of asymmetric UTM support.

> **Real world:** Cloud load balancers (for example a sandwich of internal and external load balancers in a public cloud) often break symmetry. FGSP with `layer2-connection unavailable` and encryption is the documented way to keep inspection working without SNAT tricks.

## VRRP on FortiGate

VRRP (versions 2 and 3, IPv4 and IPv6) lets FortiGates and third-party routers share a virtual gateway IP. It is configured per interface:

```text
FGT-A # config system interface
FGT-A (interface) # edit "port2"
FGT-A (port2) # set vrrp-virtual-mac enable
FGT-A (port2) # config vrrp
FGT-A (vrrp) # edit 10
FGT-A (10) # set vrip 10.1.10.1
FGT-A (10) # set priority 200
FGT-A (10) # set vrdst 198.51.100.1
FGT-A (10) # set vrdst-priority 10
FGT-A (10) # end
FGT-A (port2) # end
```

| Point | Detail |
|-------|--------|
| Where | Physical or VLAN interfaces; not hardware switch interfaces |
| Virtual MAC | `vrrp-virtual-mac` is disabled by default (the primary's real MAC is used, with gratuitous ARP on failover). Enabled: `00-00-5E-00-01-<VRID hex>`, so VRID 10 is 00-00-5E-00-01-0a. Enable it on every member |
| Destination monitoring | `vrdst` takes up to two addresses; the primary stops advertising (or, with `vrdst-priority`, advertises a lower priority) when it cannot reach them |
| Preempt | Enabled by default. A router with priority 255 takes over even with preempt disabled (RFC 3768 owner rule) |
| VIPs and IP pools | `config proxy-arp` under the VRRP group maps those addresses to the VRRP virtual MAC |
| Sessions | A VRRP backup FortiGate has no session table for in-progress sessions, so they break on failover unless you add FGSP, which is compatible with VRRP |

## Effective HA: picking FGCP, FGSP or VRRP

| Requirement | Best fit | Why |
|-------------|----------|-----|
| Two identical FortiGates, one logical firewall, config sync, stateful failover | FGCP active-passive | Full config and session sync, VMACs, simplest operations |
| Proxy-heavy UTM and you want both units scanning | FGCP active-active | Distributes proxy UTM sessions; flow inspection stays on the primary |
| Multi-VDOM, tenants should run on different units, independent failover per tenant | FGCP virtual clustering | VDOM partitioning, up to 30 vclusters |
| External load balancer, ECMP or cloud distributes traffic; peers keep separate IPs and configs | FGSP | Session sync without a primary; asymmetric inspection options |
| Two data centres each with an FGCP pair, sessions must survive a site move | FGCP over FGSP | Up to 16 clusters share sessions |
| Gateway redundancy with a non-Fortinet router, or different FortiGate models | VRRP | Standards based; mixed vendors and models allowed |

> **Watch out:** FGCP requires the same model and firmware on every member. A requirement such as "a FortiGate 200F and a FortiGate 100F must share a gateway IP" rules FGCP out; VRRP is the answer (add FGSP only if sessions must survive and the platforms support it).

## Lab it yourself

The trial is one FortiGate-VM per FortiCloud account, so FGCP, virtual clustering and FGSP all need a second licensed FortiGate, hardware or Fortinet's paid on-demand labs. VRRP is the exception that fits: put the trial FortiGate and a Cisco IOS router on the same LAN segment, configure the same VRID and virtual IP (`vrrp 10 ip 10.1.10.1` on IOS), give the FortiGate priority 200, then shut its uplink with `vrdst` monitoring and watch the router take over (`show vrrp brief` on IOS). It uses two interfaces and needs no firewall policy for VRRP itself.

## Key takeaways

- Virtual clustering is per-VDOM active-passive FGCP: up to 30 vclusters, group ID 0–7, root and management VDOM in vcluster 1, VDOM partitioning keeps both units busy.
- FGSP synchronizes sessions only (TCP and IPsec tunnels by default; UDP/ICMP, expectation and NAT need session-pickup options) among 2–16 peers or FGCP clusters.
- standalone-group-id must match, group-member-id must be unique; session-sync-dev gives layer 2 kernel sync, otherwise sync is layer 3 over UDP.
- Use IP pools, not interface addresses, for NAT sessions that must survive an FGSP failover.
- Asymmetric UTM bounces return traffic to the session owner: layer2-connection available for shared layer 2, unavailable for cloud/L3, plus encryption and psksecret to protect it.
- VRRP suits mixed vendors and models; enable vrrp-virtual-mac on all members and remember sessions do not survive without FGSP.
