## Dual-hub topologies and use cases

A second hub removes the single point of failure of hub-and-spoke and is the normal design once branches depend on datacenter applications. Each branch builds overlays to **both** hubs (with two underlays per side, four tunnels: `HUB1-VPN1`, `HUB1-VPN2`, `HUB2-VPN1`, `HUB2-VPN2`). The SD-WAN rules on the branch decide which hub carries which traffic.

| Design | Behaviour | When to choose |
|---|---|---|
| **Primary/Secondary** | Hub 2 is a backup. In the overlay template, the secondary hub's overlays get a higher **cost**, and a lowest cost (SLA) rule prefers hub 1 while it meets SLA | Geo-redundant datacenters where the application lives mainly in one DC. Fortinet recommends lowest cost (SLA) for steering between datacenters because flow stability matters more than chasing the best metric |
| **Primary/Primary** | Both hubs are active with equal cost. Traffic is spread or steered per application | Both DCs host active workloads, or hubs are regional egress points |
| **Multi hub (3 or 4)** | The overlay template assigns a cost per hub | Larger estates and multi-PoP designs |

Fortinet's FortiManager documentation states that Primary/Secondary and Primary/Primary generate *the same* configuration. The only difference is the higher cost given to the secondary hub, which the SD-WAN rule then uses.

> **Real world:** In a dual-DC design the hubs also need a path to each other, through the DC core or a hub-to-hub tunnel. A branch that only reaches hub 1 (its hub-2 overlays down) can then still reach prefixes only hub 2 knows, and ADVPN shortcuts can be offered through either hub.

## Dual-hub options in the SD-WAN overlay template

In FortiManager's Overlay Orchestration wizard:

- **Topology**: Single HUB, Dual HUB (Primary/Secondary), Dual HUB (Primary/Primary), Multi HUB (3 or 4, with a Cost per hub that accepts metadata variables).
- **Advanced defaults**: loopbacks 172.16.0.0/16, overlays 10.10.0.0/16, BGP AS 65000.
- **BGP on Loopback** (one BGP peer per hub, whatever the number of overlays), **Dynamic BGP** (with an option to keep or drop route reflection), ADVPN Disabled / Legacy / 2.0, Segmentation Over Single Overlay, PSK or signature.
- **Hub network settings**: WAN underlays (with Private Link and Override IP), network advertisement (connected or static), advanced SD-WAN neighbors, neighbor groups and VRF, and **branch route maps** for self-healing.
- **Generated objects (dual hub)**: `HUB1_IPsec`, `HUB2_IPsec`, `BRANCH_IPsec` (four tunnels), `HUB1_BGP`, `HUB2_BGP`, `BRANCH_BGP`, CLI templates for loopbacks and router ID, template groups `HUB1`, `HUB2` and `BRANCH`, performance SLAs `HUB1_HC` and `HUB2_HC`, zones `HUB1` and `HUB2`, and the `branch_id` variable.

Fortinet's 7.6 architecture guide notes that from 7.6.3, **BGP on loopback is the official recommendation for overlays and the default in the Overlay Orchestrator**.

## Routing options for dual-hub topologies

| | BGP per overlay (legacy) | BGP on loopback (recommended) |
|---|---|---|
| Sessions per spoke | One iBGP session per overlay (four in the dual-hub example) | One iBGP session per hub, loopback to loopback |
| Tunnel addressing | Tunnels need IPs (overlay subnets) | Tunnels can stay unaddressed |
| Next hop | Tunnel IP of the hub/spoke | The loopback, resolved recursively over the overlays |
| Hub side | Neighbor group + range per overlay subnet | One neighbor group + range covering the spoke loopbacks |
| Route reflection between spokes | Required for ADVPN (or dynamic BGP) | Required for ADVPN (or dynamic BGP) |
| BGP add-path | Required (per Fortinet's comparison table) | Not required |
| ADVPN 2.0 | Fortinet's guide lists it as a limitation | Supported |

### BGP on loopback for two hubs

**Spoke** (`FGT-Spoke1`, `Branch-Lo` 172.16.0.1):

```text
config system settings
    set location-id 172.16.0.1
end
config vpn ipsec phase1-interface
    edit "HUB1-VPN1"
        set exchange-ip-addr4 172.16.0.1
    next
    ... (same on HUB1-VPN2, HUB2-VPN1, HUB2-VPN2)
end
config router bgp
    set as 65000
    set router-id 172.16.0.1
    set ibgp-multipath enable
    set recursive-next-hop enable
    config neighbor
        edit "172.16.255.252"
            set interface "Branch-Lo"
            set update-source "Branch-Lo"
            set remote-as 65000
        next
        edit "172.16.255.250"
            set interface "Branch-Lo"
            set update-source "Branch-Lo"
            set remote-as 65000
        next
    end
end
```

**Hub** (`FGT-Hub1`): a `BGP-Lo` (172.16.255.252) for peering and a **separate** `HUB-Lo` (172.16.255.251) used as the spokes' health-check server, plus `location-id`, `exchange-ip-addr4 172.16.255.252` on `VPN1`/`VPN2`, and:

```text
config router bgp
    set as 65000
    set ibgp-multipath enable
    set recursive-next-hop enable
    config neighbor-group
        edit "EDGE"
            set interface "BGP-Lo"
            set update-source "BGP-Lo"
            set remote-as 65000
            set next-hop-self enable
        next
    end
    config neighbor-range
        edit 1
            set prefix 172.16.0.0 255.255.224.0
            set neighbor-group "EDGE"
        next
    end
end
```

Why each piece matters:

- `exchange-ip-addr4` gives every device an IKE-injected /32 to the peer's loopback over **every** overlay, so BGP survives the loss of any single tunnel.
- `recursive-next-hop enable` (default disable) lets BGP resolve a next hop through another BGP route. `ibgp-multipath enable` (default disable) installs all equal iBGP paths, so the spoke sees the hub prefixes through both overlays and SD-WAN chooses between them.
- **Separate hub loopbacks.** A health check installs a kernel route to its server that is *not* removed when the check fails. If BGP peered with the health-check address, it would keep using the tunnel it first came up on even after that tunnel's SLA failed.
- `neighbor-range` + `neighbor-group` accept any spoke whose loopback falls in the range: zero touch on the hub. `max-neighbor-num` (1–1000) can cap them. Neighbor groups default to `passive enable` (they wait for spokes to connect).

> **Exam tip:** With BGP on loopback, both hubs can even share one `HUB-Lo` health-check address (Fortinet's dual-hub example does). Spokes then measure "a hub" over each overlay. Peering addresses must still be unique per hub.

## BGP routing and SD-WAN self-healing

*Self-healing* means the overlay network reacts to SLA changes on its own. Spokes measure overlay health (they already run the health checks), and BGP carries that health to the hubs, so hub-to-spoke traffic avoids bad overlays without SD-WAN rules on the hub. Fortinet documents several mechanisms.

### 1. SD-WAN neighbor + preferable route map (communities)

On the spoke, tie each BGP neighbor to SD-WAN members and a health check:

```text
config system sdwan
    config neighbor
        edit "10.10.1.254"
            set member 1
            set health-check "HUB1_HC"
            set sla-id 1
        next
    end
end
config router bgp
    config neighbor
        edit "10.10.1.254"
            set route-map-out "HUB_BAD"
            set route-map-out-preferable "HUB_CARRIER1"
        next
    end
end
```

While the member meets the SLA, FortiOS advertises with `route-map-out-preferable` (for example community 65000:1). When it fails, it switches to `route-map-out` (for example 65000:9999). The hub matches the communities in a `route-map-in` and uses `set-priority` (lower is preferred) to rank the routes, so its traffic to the spoke leaves on the healthy overlay. Fortinet's large-scale example shows the hub routes changing from `prio=100` to `prio=9999` when overlay 1 fails, with traffic moving to the overlay-2 tunnel.

Relevant `config neighbor` options: `member` (several allowed), `minimum-sla-meet-members` (default 1; below it, the default route map is used), `health-check` + `sla-id`, `mode sla|speedtest`, `role standalone|primary|secondary`, `route-metric preferable|priority`, and `service-id` (follow an SD-WAN rule's zone state instead).

### 2. Member priorities as BGP MED or embedded in probes

- `route-metric priority`: the spoke maps SD-WAN member priorities into the **MED** of routes advertised over iBGP. Hubs then advertise different MEDs to external eBGP peers, so the outside world enters through the hub with the best path to the spoke.
- **Embedded SLA priorities**: members carry `priority-in-sla` / `priority-out-sla` (0–65535). The spoke health check uses `embed-measured-health enable`, and the hub health check uses `detect-mode remote`. The hub sets priorities on the IKE routes per overlay, and BGP routes resolved through those IKE routes inherit them. This mechanism suits BGP on loopback, where there is only one BGP session but several overlays.

### 3. Hub route suppression

This is flagged *New* in the FortiOS 7.6.5 Administration Guide. A hub health check in `detect-mode remote` with `update-bgp-route enable` declares a spoke dead when its probes stop arriving (`failtime` controls how fast). The spoke's routes are then flagged as suppressed, and a hub `route-map-out` with `match-suppress enable` raises the MED toward external peers, so traffic enters through the other hub.

### FortiManager preconfigured route maps

The overlay template offers ready-made self-healing route maps: **`RM-VPN-Priority`** on hubs, and **`Priority_1` … `Priority_4`** plus **`Priority_999`** (catch-all) on branches. Hubs get five communities, each mapped to a priority, so a branch advertising the Priority_1 community is preferred over Priority_2.

## Configuration specifics for large topologies

| Concern | Setting |
|---|---|
| Hub CPU from failing shortcut offers | `auto-discovery-offer-interval` (1–300 s, default 5) on the hub phase 1 |
| Thousands of BGP peers | BGP on loopback (one session per spoke per hub), `neighbor-range` with a summarisable loopback plan, optional `max-neighbor-num` |
| Hub reflecting every spoke route to every spoke | Dynamic BGP over shortcuts, or IKE routes from phase 2 selectors (`mode-cfg` + `mode-cfg-allow-client-selector` + `add-route` on the spokes). See the ADVPN routing lesson |
| Kernel interfaces on the hub | `net-device disable` on hub dial-up phase 1s |
| Probe volume | Spokes probe the hubs only. Hubs check external services and signal through BGP (SD-WAN neighbor on the hub with a neighbor group) |
| Convergence | `link-down-failover`, short `advertisement-interval`, `graceful-restart`, DPD `on-idle` |

A dual-hub design needs at least three FortiGates (two hubs, one spoke), each with several tunnels, policies and routes, far beyond one FortiGate-VM trial per FortiCloud account and its 3-interface, 3-policy, 3-route caps. Use the paid Fortinet on-demand labs, licensed VMs or hardware. Within the trial, you can practise the single-hub half: one hub and one spoke (the second FortiGate from another trial account, if the terms allow) with one overlay, loopbacks, `exchange-ip-addr4` and an iBGP session on loopback. Even that tight setup uses tunnel, WAN and loopback interfaces, so check how the trial counts them. You can also model the dual-hub templates in the FortiManager trial without installing.

## Key takeaways

- Primary/Secondary and Primary/Primary overlay templates differ only in the secondary hub's cost. Use lowest cost (SLA) rules to keep a primary DC.
- BGP on loopback (one session per hub, unaddressed tunnels, recursive next hop, iBGP multipath) is the 7.6 recommendation and the 7.6.3 Overlay Orchestrator default.
- Keep separate hub loopbacks for BGP peering and for health checks, because health-check kernel routes persist when the check fails.
- Hubs accept spokes with `neighbor-group` + `neighbor-range`. Neighbor groups are passive by default.
- Self-healing: SD-WAN neighbor + `route-map-out-preferable` / `route-map-out` communities, hub `route-map-in` with `set-priority`, MED mapping, or SLA priorities embedded in probes.
- FortiManager ships `RM-VPN-Priority` (hubs) and `Priority_1`–`Priority_4` / `Priority_999` (branches) for BGP self-healing.
