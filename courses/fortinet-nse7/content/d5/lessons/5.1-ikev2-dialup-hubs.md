## Choosing an IPsec topology

| Topology | How it scales | Spoke-to-spoke path | When it fits |
|---|---|---|---|
| Static site-to-site pairs | Tunnel count grows with every pair (n×(n−1)/2 for a full mesh) | Direct | A handful of sites with fixed public IPs |
| Hub-and-spoke, hub with static phase 1s | One phase 1 per spoke on the hub | Through the hub | Small fixed estates |
| Hub-and-spoke, dial-up hub (`type dynamic`) | One phase 1 per hub underlay, however many spokes | Through the hub | The usual SD-WAN overlay: spokes can be added without touching the hub |
| ADVPN (dial-up hub + shortcuts) | As dial-up hub; shortcuts are built only on demand | Direct shortcut after discovery | Large estates that need low-latency spoke-to-spoke traffic |

The property Fortinet's SD-WAN architecture guide keeps coming back to is **zero touch**: with a dial-up hub, adding or removing a spoke changes nothing on the hub or on any other spoke. A static mesh breaks this, because every new site edits every other site. At architect level, the default answer for "many branches, a few datacenters" is a dial-up hub per datacenter with one dial-up phase 1 per hub underlay, plus ADVPN when spokes talk to each other.

> **Real world:** Fortinet's 7.6 SD-WAN architecture guide calls the one-tunnel-per-underlay-pair layout *one-to-one overlay mapping* (the most common design) and the any-to-any layout *full mesh overlay mapping* (more paths during outages, more configuration and troubleshooting).

## IKEv2 versus IKEv1 on FortiGate

`set ike-version 2` (the CLI default is still `1`) changes more than the packet format:

| Area | IKEv1 | IKEv2 |
|---|---|---|
| Phase 1 exchange | Main or aggressive mode (`set mode`) | IKE_SA_INIT + IKE_AUTH; `mode` does not apply |
| User authentication | XAuth (`xauthtype`) | EAP (`set eap enable`) |
| Several dial-up phase 1s on one interface | Aggressive mode + peer ID, or different interfaces | `network-overlay enable` + a unique `network-id` per phase 1 |
| Network IDs and overlay IDs | Not supported | Supported (0–255) |
| ADVPN 2.0 shared idle timeout | Not supported | Supported (needs `location-id` on both spokes) |

The **network ID** is the IKEv2 point that catches people out. When a hub has two IKEv2 dial-up phase 1s on the same interface and both use pre-shared keys, the hub cannot tell from IKE_SA_INIT which one an incoming spoke wants. Without network IDs, Fortinet's community articles note that dial-in peers are matched against the first IKEv2 dial-up phase 1. The fix is the same value on both ends:

```text
FGT-Hub # config vpn ipsec phase1-interface
FGT-Hub (phase1-interface) # edit "VPN1"
FGT-Hub (VPN1) # set ike-version 2
FGT-Hub (VPN1) # set network-overlay enable
FGT-Hub (VPN1) # set network-id 1
FGT-Hub (VPN1) # next
FGT-Hub (phase1-interface) # edit "VPN2"
FGT-Hub (VPN2) # set ike-version 2
FGT-Hub (VPN2) # set network-overlay enable
FGT-Hub (VPN2) # set network-id 2
FGT-Hub (VPN2) # end
```

Network IDs also let two FortiGates build more than one tunnel between the same pair of IP addresses. That is why FortiManager's IPsec template describes the Network Overlay toggle as required "to establish multiple IPsec VPN tunnels between the same two FortiGate IP addresses".

### EAP on IKEv2

`set eap enable` makes the dial-up gateway authenticate users with EAP, against the group in `authusrgrp`. Related options:

- `eap-identity use-id-payload` (default) takes the user identity from the IKEv2 IDi payload; `send-request` asks the peer with an EAP identity request.
- `eap-exclude-peergrp` lists peers that skip EAP. Use it when one phase 1 serves both FortiClient users and FortiGate spokes.
- `eap-cert-auth enable` (default disable) checks the FortiClient certificate first and then runs EAP: two-factor certificate plus user. With it enabled, a `peer` object restricts which certificates are trusted. With it disabled, the certificate is not validated even if `peer` is set.

In `diagnose debug application ike -1`, a certificate failure shows up before any EAP lines, for example `fnbam cert group matching failed` followed by `certificate validation failed`.

## Building a dial-up hub phase 1

```text
config vpn ipsec phase1-interface
    edit "VPN1"
        set type dynamic
        set interface "port1"
        set ike-version 2
        set peertype any
        set net-device disable
        set exchange-ip-addr4 172.16.255.252
        set add-route disable
        set dpd on-idle
        set auto-discovery-sender enable
        set network-overlay enable
        set network-id 1
        set psksecret <key>
    next
end
```

### type and peertype

`type dynamic` makes the phase 1 a dial-up server: any peer can connect, and each connection becomes a **dynamic instance** named after the parent with a suffix (`VPN1_0`, `VPN1_1`, …). In `diagnose vpn tunnel list`, instances show `mode=dial_inst/3` and `parent=VPN1 index=0`, while the parent shows `mode=dialup/2`. The CLI default for `peertype` is `peer` (one certificate peer). Pre-shared-key overlays usually set `any`; certificate designs use `peer` or `peergrp`.

### net-device

| `net-device` | What FortiOS builds | Routing consequence |
|---|---|---|
| `disable` (default) | No kernel interface per dial-up instance | Each instance gets a **tunnel ID** in the form of an IP address, used as the gateway of routes through that instance. All instances share the parent interface name in routes and policies |
| `enable` | A kernel device for every tunnel (`create_dev` in the tunnel options) | Each instance is its own interface (`VPN1_0`), so it can be an SD-WAN member and carry per-tunnel health checks |

Fortinet's ADVPN-with-BGP example requires `net-device disable` on the hub. Hundreds of dial-up instances then don't create hundreds of kernel interfaces, and routes to spokes resolve by tunnel ID. The spokes in the same examples use `net-device enable`, because shortcuts (`HUB1-VPN1_0`) must appear as separate interfaces that SD-WAN can steer to. The ADVPN 2.0 overlay placeholder also requires `net-device enable`. The old `tunnel-search` option was removed in FortiOS 7.0.0.

> **Exam tip:** Without mode-cfg, the tunnel ID of a dial-up instance is normally the peer's public IP. In Fortinet's IKEv2 mode-cfg example (EAP dial-up with `net-device disable`), it is the address the hub assigned to the client instead, so look for a `tun_id=` matching an address from the mode-cfg range. Fortinet's IKEv1 mode-cfg example still shows the peer's public IP, so check the IKE version before reading `tun_id`.

### add-route

`add-route` (default **enable**) adds a route to the peer's phase 2 destination selector when a dial-up tunnel comes up, with the phase 1 `distance` (default 15) and `priority` (default 1). That suits FortiClient and simple spokes with specific selectors. It is dangerous with wildcard selectors: if the peer offers 0.0.0.0/0, the wildcard route is installed with the phase 1 distance. The SD-WAN and ADVPN examples set `add-route disable` and let BGP carry the routes. The exception is the IKE-route design for large ADVPN networks in the 5.3 lessons, which turns `add-route` back on with `mode-cfg-allow-client-selector`.

### mode-cfg (IKE configuration method)

`set mode-cfg enable` lets the hub push configuration to the client: an IP address (`assign-ip`, default enable, from `assign-ip-from range` by default, or from a user group, DHCP or an address object), DNS servers, split-include subnets and the netmask. The pool comes from `ipv4-start-ip`, `ipv4-end-ip` and `ipv4-netmask`. Uses:

- FortiClient dial-up: a virtual IP per user.
- FortiGate spokes with IP-less overlays: the hub hands every spoke a tunnel address, so nobody configures per-spoke tunnel IPs.
- `mode-cfg-allow-client-selector enable`: the client proposes its own phase 2 selectors instead of wildcards, which the IKE-route ADVPN design relies on.

`ip-delay-interval` holds a released address before reuse, and `diagnose vpn ike gateway flush` releases them.

### exchange-interface-ip and exchange-ip-addr4

These are Fortinet IKE extensions. Both are off by default (`disable` / `0.0.0.0`).

- `exchange-interface-ip enable` sends the local tunnel interface IP to the peer.
- `exchange-ip-addr4 <IP>` sends a chosen IPv4 address, normally the device loopback. IKE then injects a /32 route to the peer's address over the tunnel on both sides.

The second option is what makes **BGP on loopback** work without an IGP. Every spoke learns a route to the hub BGP loopback, and the hub learns a route to each spoke loopback, all from IKE. Set it on every overlay toward the hub so the loopback stays reachable over all of them.

## DPD modes

| `dpd` | Behaviour | Typical use |
|---|---|---|
| `disable` | No dead peer detection | Rarely appropriate |
| `on-idle` | Probes when the tunnel is idle | SD-WAN overlays: a dead overlay is found before user traffic needs it. All of Fortinet's ADVPN examples use it, often with `dpd-retryinterval 5` |
| `on-demand` (default) | Probes only when traffic is sent and nothing comes back | Hubs with many mostly-idle dial-up clients: fewer probes, slower detection |

`dpd-retrycount` defaults to 3 (range 0–10). `diagnose vpn tunnel list` shows the effective values, for example `dpd: mode=on-idle on=1 idle=5000ms retry=3 count=0`. A tunnel brought down by DPD takes its routes with it. That is why fast DPD matters when BGP or SD-WAN must fail over.

> **Watch out:** DPD tells IKE the peer is gone, but SD-WAN still needs its own health checks to judge the quality of an overlay. The two complement each other.

## Reading a dial-up hub

```text
FGT-Hub # diagnose vpn ike gateway list name VPN1_0
vd: root/0
name: VPN1_0
version: 2
interface: port1 3
addr: 203.0.113.1:500 -> 192.0.2.10:500
tun_id: 10.10.1.1
remote_location: 172.16.0.1
created: 1832s ago
assigned IPv4 address: 10.10.1.1/255.255.255.0
IKE SA: created 1/1 established 1/1 time 10/10/10 ms
IPsec SA: created 1/1 established 1/1 time 0/0/0 ms
```

Read it from the top. The name is a dynamic instance of `VPN1`, version 2 is IKEv2, the tunnel ID equals the mode-cfg address, and `remote_location` is the spoke's `location-id` (from `config system settings`).

## Lab it yourself

The FortiGate-VM permanent trial fits a **one-hub, one-spoke** test if the spoke is not a second trial: one trial per FortiCloud account. Use a Linux strongSwan host or a Cisco IOS router as the dial-up client. Configure the trial as the hub with `type dynamic`, `ike-version 2`, `mode-cfg enable` and an address pool, then watch `diagnose vpn ike gateway list` and `diagnose vpn tunnel list` as the client connects. Stay inside the caps: WAN, LAN and the tunnel may all count toward the 3-interface limit. Use one policy each way and at most three routes. The trial offers low encryption only, so set the peer's proposals to match what `set proposal ?` lists on the trial. Two dial-up phase 1s with network IDs, a second FortiGate spoke or EAP against an external RADIUS server go beyond a single trial. Use a second FortiCloud account's trial (check the trial terms), the paid on-demand labs or hardware for those.

## Key takeaways

- Dial-up hubs (`type dynamic`) keep the zero-touch property. Each spoke connection is a dynamic instance such as `VPN1_0`.
- `net-device disable` (hub) routes by tunnel ID. `net-device enable` (spokes, placeholders) gives every tunnel its own interface. The ADVPN-with-BGP example needs the hub at `disable`.
- `add-route` defaults to enable and installs routes to the peer's selectors at distance 15. Disable it when BGP carries the routes.
- `mode-cfg` assigns tunnel IPs and other settings. `exchange-ip-addr4` injects /32 loopback routes for BGP on loopback.
- Network IDs (`network-overlay` + `network-id`, 0–255) are IKEv2 only and separate several dial-up gateways on one interface.
- IKEv2 brings EAP, optionally with `eap-cert-auth` for certificate plus user authentication.
- DPD `on-idle` finds dead overlays proactively. `on-demand` is the default and suits many idle clients.
