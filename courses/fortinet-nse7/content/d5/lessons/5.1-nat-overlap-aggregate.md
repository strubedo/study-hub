## IPsec interfaces with no IP address

Fortinet's recommended overlays (BGP on loopback, FortiManager overlay template) leave the tunnel interfaces **unaddressed**. The loopback carries BGP and health checks, so the tunnels need no IP plan. That is efficient, but FortiOS still needs a source address in two situations, and an architect has to know which one it picks.

### Local-out traffic (health checks, BGP, ping from the CLI)

Traffic generated by the FortiGate itself that leaves through an IP-less tunnel takes the IP of the **outgoing underlay (WAN) interface** as its source, according to Fortinet's support articles. That address is rarely inside the phase 2 selectors and rarely routed back by the hub. The documented fixes:

| Traffic | Fix |
|---|---|
| SD-WAN performance SLA probes | `set source <loopback IP>` on the SD-WAN **member** (`config system sdwan` → `config members`), or `set source` on the health check |
| BGP | `set update-source "Branch-Lo"` (plus `set interface`) on the neighbor |
| Return path | Allow PING and BGP between the loopback and the overlay zones in firewall policies. The loopback is reached through the `exchange-ip-addr4` /32 routes |

```text
config system sdwan
    config members
        edit 3
            set interface "HUB1-VPN1"
            set zone "HUB1"
            set source 172.16.0.1
        next
    end
end
```

### Outbound NAT on a policy whose egress is an IP-less tunnel

If a firewall policy toward the tunnel has `set nat enable` with no IP pool, FortiOS must borrow an address from another interface. Fortinet's support article on this case says it picks the **interface with the lowest index number**. Use `diagnose netlink interface list` to see the indexes. The result is unpredictable: it can be a management or DMZ address, outside the selectors and unroutable at the far end. The documented remedies are:

1. Give the IPsec interface an IP address, or
2. Use an **IP pool** in the policy. A pool holding the loopback address is the common choice, and Fortinet's MSSP guide uses a `Lo-Pool` for remote internet access through the hub.

> **Exam tip:** "Health checks fail on an IP-less overlay" → member `source`. "Users NATed to a strange address over the tunnel" → NAT took the lowest-index interface; use an IP pool or address the tunnel.

## Overlapping subnets and overlapping routes

### Two sites with the same LAN

When HQ and a branch both use 192.168.111.0/24, routing alone cannot work. Fortinet's documented route-based solution gives each side a **virtual subnet of the same size** and translates both directions:

| Direction | What happens | Objects |
|---|---|---|
| HQ host → branch | Destination is the branch virtual subnet (10.2.2.0/24). The HQ FortiGate source-NATs HQ hosts into the HQ virtual subnet (10.1.1.0/24) | IP pool (fixed port range or one-to-one mapping 192.168.111.x → 10.1.1.x) |
| Branch → HQ host | Arrives at 10.1.1.x; HQ destination-NATs back to 192.168.111.x | VIP mapping the HQ virtual subnet to the real one |

Order of operations matters for the selectors:

- **Outbound into the tunnel:** policy match → SNAT → phase 2 selector check. The selectors must therefore list the *virtual* subnets (local 10.1.1.0/24, remote 10.2.2.0/24).
- **Inbound from the tunnel:** selector check → policy match → DNAT.

Add a static route for the remote virtual subnet over the tunnel and a **blackhole route** for the same prefix at distance 254. That way traffic is dropped, not leaked to the default route, while the tunnel is down.

### Many customers or departments with overlapping space

Overlap that is planned rather than inherited calls for **VRFs**. With segmentation over a single overlay, each LAN sits in its own customer (CE) VRF, so two branches can use the same addresses in different VRFs without NAT. This is covered in the multiregion/MSSP lesson.

### Overlapping routes between remote VPN sites

On hub-and-spoke overlays, overlapping or summary routes arrive from several places: two spokes advertising the same prefix, a spoke summary versus a specific route, a default route via the hub versus a specific route via a shortcut. Watch for three things:

- With `add-route enable` on a dial-up hub, every spoke that offers the same selector gets a route at the same distance. With `net-device disable` the routes differ only by tunnel ID gateway, and traffic follows whichever route wins. Disable `add-route` and use BGP with route maps when spokes overlap.
- FortiManager VPN Manager gateways have a `route-overlap` advanced option (`allow`, `use-new` or `use-old`) that controls how overlapping protected subnets are handled when it generates routes.
- In SD-WAN rules for ADVPN traffic, Fortinet's MSSP guide recommends `set tie-break fib-best-match`, so a default or summary route through the hub doesn't make a hub overlay look like a valid path once a more specific route exists through a shortcut.

## IPsec aggregates

An IPsec aggregate bundles several tunnels into one logical interface for redundancy and load balancing, much like a LAG of tunnels.

```text
config vpn ipsec phase1-interface
    edit "pri_HUB"
        set interface "port1"
        set net-device disable
        set aggregate-member enable
        set remote-gw 203.0.113.1
    next
    edit "sec_HUB"
        set interface "port2"
        set net-device disable
        set aggregate-member enable
        set remote-gw 198.51.100.1
    next
end
config system ipsec-aggregate
    edit "agg_HUB"
        set member "pri_HUB" "sec_HUB"
        set algorithm round-robin
    next
end
```

Rules:

- Member tunnels must have **`net-device disable`** and **`aggregate-member enable`**.
- `algorithm`: `L3`, `L4`, `round-robin` (default, per packet), `weighted-round-robin` (`aggregate-weight` 1–100, default 1, on each phase 1) or `redundant` (first tunnel that is up carries everything).
- The aggregate gets the IP and the policies. Dynamic routing (OSPF, BGP) runs on the aggregate, and the aggregate can be an SD-WAN member.
- Check it with `diagnose sys ipsec-aggregate list`, which shows `agg_HUB algo=RR member=2 run_tally=2` and the member names.

For **dial-up** aggregates, each spoke sets a `location-id` (`config system settings`). The hub load-balances per packet across the tunnels that share a location ID. Fortinet notes that this traffic **cannot be offloaded to the NPU**, so per-packet aggregation trades throughput per CPU for link usage.

| Need | Aggregate | SD-WAN over separate tunnels |
|---|---|---|
| Per-packet spraying across links to one peer | Yes (round-robin, weighted) | No (per-session) |
| Per-application steering by SLA | No | Yes |
| Simple dynamic routing over "one" link | Yes | Needs BGP per overlay or on loopback |

> **Watch out:** Per-packet distribution reorders packets when the links have different latency. Use `redundant` or SD-WAN when the underlays are very different, such as fibre and LTE.

## OpenSSL for IPsec certificate authentication

Pre-shared keys don't scale well for large estates: one leaked key exposes every spoke on that phase 1. Certificate authentication (`set authmethod signature`) is the alternative, and many labs build the PKI with **OpenSSL** instead of a full CA product:

```text
# private lab CA
openssl req -x509 -newkey rsa:2048 -nodes -keyout ca.key -out ca.crt -days 3650 -subj "/CN=LAB-CA"
# spoke key + CSR, signed by the CA
openssl req -newkey rsa:2048 -nodes -keyout spoke1.key -out spoke1.csr -subj "/CN=FGT-Spoke1"
openssl x509 -req -in spoke1.csr -CA ca.crt -CAkey ca.key -CAcreateserial -out spoke1.crt -days 825
# bundle for import into the FortiGate
openssl pkcs12 -export -inkey spoke1.key -in spoke1.crt -certfile ca.crt -out spoke1.p12
# inspect what you built (subject, validity, extensions)
openssl x509 -in spoke1.crt -noout -text
```

On the FortiGates:

1. Import `ca.crt` as a CA certificate on hub and spokes (System > Certificates). Import each device's PKCS#12 bundle as its local certificate.
2. Phase 1: `set authmethod signature`, `set certificate "<local cert>"`.
3. Restrict who may connect: `set peertype peer` with `set peer "<user peer>"`, where `config user peer` names the trusted `ca` and optionally a `subject` to match. Use `peergrp` for a group.

> **Watch out:** The 7.6 documentation doesn't expand the blueprint bullet "OpenSSL for IPsec VPNs". Building and checking certificates for `authmethod signature`, as shown here, is the practical reading. The only OpenSSL topic in the FortiOS 7.6 Administration Guide is the OpenSSL FIPS provider used in FIPS-CC mode, and that topic isn't specific to IPsec.

The same OpenSSL commands help troubleshooting. Decode a certificate to check its subject, validity dates and issuer before blaming IKE. In `diagnose debug application ike -1`, a peer certificate that is trusted but doesn't match the `peer` object appears as a peer or group matching failure, not as a proposal mismatch.

## Key takeaways

- Local-out traffic over an IP-less tunnel uses the WAN IP. Fix it with SD-WAN member `source`, health-check `source` and BGP `update-source`.
- NAT toward an IP-less tunnel borrows the lowest-index interface's IP. Use an IP pool (often the loopback) or address the tunnel.
- Overlapping LANs need same-size virtual subnets: SNAT (IP pool) and DNAT (VIP), with selectors on the virtual subnets. VRFs avoid NAT when the overlap is by design.
- IPsec aggregate members need `net-device disable` and `aggregate-member enable`. The default algorithm is round-robin; `redundant` uses the first live tunnel.
- Dial-up aggregates balance tunnels that share a `location-id` and are not NPU-offloaded.
- OpenSSL can build the CA and device certificates for `authmethod signature`. Restrict peers with `config user peer`.
