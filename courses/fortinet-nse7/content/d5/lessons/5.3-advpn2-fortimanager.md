## ADVPN 1.0 challenges

Classic ADVPN works, but large SD-WAN estates hit its limits:

- **Shortcut path follows the overlay.** The shortcut is built over the overlay the first packets used. If Spoke1 sent over its ISP1 overlay, the shortcut is ISP1-based, even when the remote spoke's ISP1 link is bad or the best path is ISP2-to-ISP2. Hubs needed policy routes to keep shortcuts on matching overlays.
- **User traffic must trigger it.** Every new shortcut starts with packets hairpinning through the hub.
- **No knowledge of the remote side.** The local spoke cannot see the remote spoke's links, costs or health before choosing.
- **Routing design dependencies.** Correct behaviour relied on route reflection, recursive next-hop resolution, BGP per overlay or BGP on loopback, plus network-ID and crossover tuning for multi-overlay designs.
- **Transports the hub doesn't have.** Two spokes sharing an MPLS cloud the hub isn't connected to had no overlay over which a shortcut could even be offered.

## ADVPN 2.0 (FortiOS 7.4.2 and later)

ADVPN 2.0 moves shortcut intelligence into the spokes. It has two parts:

**Edge discovery.** The IKE shortcut-reply is extended, so the local spoke learns the remote spoke's WAN links: IP address, transport group, link quality, link cost and member configuration order. After the shortcut is up, this link information is refreshed over the shortcut **every 5 seconds** with UDP traffic.

**Path management.** The local spoke computes the best shortcut path **per SD-WAN rule** and tells IKE to build it. It sends the shortcut-query **directly to the remote spoke** once a path is chosen. For load-balancing rules it can build **several shortcuts over distinct underlay paths** and spread traffic over them. Fortinet's example builds one shortcut on the single unique port1-to-port1 underlay instead of four overlay-pair combinations.

Fortinet's ADVPN 2.0 page says it no longer **depends** on specific BGP designs such as route reflection, recursive resolution, BGP per overlay or BGP on loopback. The architecture guide adds one routing duty specific to 2.0: **all node loopbacks must be reachable** across the overlay. Its BGP comparison table also marks BGP per overlay as "Does not work with ADVPN 2.0", so pair ADVPN 2.0 with BGP on loopback. **ADVPN 2.0 currently supports IPv4 only.** The hub side is unchanged: ADVPN enabled (`auto-discovery-sender`) and spoke-to-spoke firewall policies.

### Configuration on the spokes

```text
config system sdwan
    config zone
        edit "HUB1"
            set advpn-select enable
            set advpn-health-check "HUB1_HC"
        next
    end
    config members
        edit 3
            set interface "HUB1-VPN1"
            set zone "HUB1"
            set source 172.16.0.1
            set transport-group 1
        next
        edit 4
            set interface "HUB1-VPN2"
            set zone "HUB1"
            set source 172.16.0.1
            set transport-group 2
        next
    end
    config service
        edit 1
            set name "Corp"
            set mode sla
            set shortcut-priority auto
            ...
        next
    end
end
```

| Setting | Where | Meaning |
|---|---|---|
| `advpn-select enable` | Zone (default disable) | Enables SD-WAN/ADVPN 2.0 path selection for that overlay zone |
| `advpn-health-check <name>` | Zone | The health check whose results this spoke sends to peer spokes about its own overlays |
| `transport-group <n>` | Member | Groups interconnected transports. The admin guide gives 1–255; the CLI Reference shows 0–255 with default 0. Path management **never** builds a shortcut between members of different transport groups |
| `shortcut-priority enable \| disable \| auto` | Rule | Gives shortcuts high priority over the parent overlays when the SLA or link-cost conditions are met. `auto` enables it when ADVPN 2.0 is on |
| `diagnose sys sdwan advpn-session` | CLI | On the local spoke: remote spoke WAN link info and the selected shortcut path. The name shown is the remote hostname, or HA group name |

### Transport groups

Internet links of any kind (broadband, LTE, a second ISP) are **interconnected transports**: a shortcut from one spoke's broadband to another spoke's LTE works. MPLS and the internet are **segregated transports**: no shortcut can join an internet link to an MPLS link. Put all internet overlays in one transport group (for example 1) and MPLS overlays in another (2). Path management then only pairs members within the same group. This replaces much of the network-ID and crossover tuning of ADVPN 1.0.

### Overlay placeholders

When spokes share a transport the hub isn't connected to, such as a private MPLS between branches, there is no hub overlay over which a shortcut could be offered. An **overlay placeholder** is a spoke phase 1 that never connects to the hub but stands in as an SD-WAN member:

```text
config vpn ipsec phase1-interface
    edit "Placeholder_MPLS"
        set type dynamic
        set interface "port3"
        set ike-version 2
        set net-device enable
        set exchange-ip-addr4 172.16.0.1
        set auto-discovery-receiver enable
        set auto-discovery-dialup-placeholder enable
        set network-overlay enable
        set network-id 250
    next
end
```

- `type dynamic` (no remote gateway), `net-device enable` and `auto-discovery-dialup-placeholder enable` (default disable: "only accept shortcut connections on this dial-up gateway").
- Add it to the overlay zone as a member with its own transport group, and include it in the health check and rules.
- Until a shortcut exists, the placeholder health check shows `state(dead)`. The first packets use the real overlay to the hub. The SHORTCUT_REPLY carries the remote spoke's eligible links, so the local spoke builds the regular shortcut **and** a shortcut between the placeholders (`Placeholder_MPLS_0`). Health checks then run on both, and the rule picks the better one.

### Shared idle timeout

`set idle-timeout enable` + `set shared-idle-timeout enable` on the overlays tears down **all** shortcuts to the same remote spoke together once no user traffic is seen for `idle-timeoutinterval`. It needs IKEv2 (the remote location is only exchanged in IKEv2) and `location-id` on both spokes.

## ADVPN on FortiManager

| Tool | How ADVPN is enabled |
|---|---|
| **IPsec templates** | Toggle *Enable ADVPN* when activating `HUB_IPSec_Recommended` / `Branch_IPSec_Recommended`, or set the ADVPN options in the advanced settings of any IPsec template (`auto-discovery-sender` on the hub template, `auto-discovery-receiver` on the branch template). Add the BGP templates (neighbor group/range, route reflection) and an SD-WAN template |
| **SD-WAN overlay template** | Auto-Discovery VPN: Disabled, **Legacy** (ADVPN 1.0) or **ADVPN 2.0**. With 2.0, each branch WAN underlay gets a **Transport Group** field (default 0, or 1 when Private Link is set). Combine with BGP on Loopback and Dynamic BGP (route reflection optional). The template generates IPsec, BGP and CLI templates, template groups and `branch_id`, and can add the overlay members, zones and hub health checks to an SD-WAN template (and health-check policies to policy packages). You still build the SD-WAN rules and the rest of the policy packages |
| **VPN Manager** | Community-based full-mesh, star or dial-up topologies. The 7.6 VPN community settings (topology wizard, phase 1/2 and advanced options) list no ADVPN toggle, so for SD-WAN ADVPN, Fortinet's FortiManager 7.6 guidance uses the template-based workflows above |

Whatever the tool, the hub policy package must contain the **spoke-to-spoke policy** (overlay zone to the same zone), or no shortcut is ever triggered.

> **Exam tip:** "Which FortiManager option builds ADVPN 2.0 with the fewest manual steps?" The SD-WAN overlay template with ADVPN 2.0, BGP on loopback and dynamic BGP, plus transport groups per underlay.

## Designing a network with SD-WAN and ADVPN (summary)

1. Dial-up hubs per datacenter (or per region), one phase 1 per hub underlay, `net-device disable`, `auto-discovery-sender`.
2. Spokes: one overlay per underlay per hub, `auto-discovery-receiver`, `net-device enable`, unaddressed tunnels, a loopback with `exchange-ip-addr4` and `location-id`.
3. Routing: BGP on loopback, ideally dynamic BGP (RR-less). Hubs advertise summaries and DC prefixes.
4. SD-WAN: overlay zones per hub, member `source` = loopback, health checks to the hub's `HUB-Lo`, rules with SLA modes. ADVPN 2.0: `advpn-select`, `advpn-health-check`, transport groups, `shortcut-priority`.
5. Stability: `hold-down-time`, `sla-stickiness`, `tie-break fib-best-match`, idle or shared idle timeout.
6. Self-healing toward the hub: SD-WAN neighbors with preferable route maps, or embedded SLA priorities.

## Key takeaways

- ADVPN 1.0: the shortcut follows the triggering overlay, needs user traffic through the hub, is blind to the remote spoke's links and depends on the routing design.
- ADVPN 2.0 (7.4.2+, IPv4 only): edge discovery (extended shortcut-reply, 5-second link updates) and path management per rule (direct shortcut-query, several shortcuts over distinct underlays).
- Spoke settings: zone `advpn-select` + `advpn-health-check`, member `transport-group`, rule `shortcut-priority`. The hub still needs `auto-discovery-sender` and spoke-to-spoke policies.
- Different transport groups never get a shortcut between them.
- Overlay placeholders: `type dynamic`, `net-device enable`, `auto-discovery-dialup-placeholder enable`, for transports the hub doesn't have.
- `shared-idle-timeout` needs IKEv2 and `location-id` on both spokes.
- FortiManager: Enable ADVPN in the hub/branch IPsec templates, or ADVPN Legacy / 2.0 (with transport groups) in the overlay template.
