## What ADVPN does

**Auto-Discovery VPN** lets the spokes of an ordinary hub-and-spoke VPN build direct, on-demand tunnels to each other, called **shortcuts**, so spoke-to-spoke traffic stops hairpinning through the hub. You get full-mesh behaviour without provisioning a full mesh: the hub keeps its zero-touch dial-up configuration, and shortcuts exist only while they are used.

For a DMVPN engineer, the closest analogue is DMVPN phase 3: hub-and-spoke control, with the hub telling a spoke that a better path exists. FortiOS does it differently underneath:

| | DMVPN phase 3 (Cisco) | FortiOS ADVPN 1.0 |
|---|---|---|
| Tunnel fabric | One mGRE interface per spoke, protected by IPsec | Route-based IPsec phase 1 interfaces. A shortcut is a new **dynamic instance** of the spoke's parent phase 1 (`HUB1-VPN1_0`) |
| Discovery protocol | NHRP (redirect, resolution request/reply) | **IKE** notifications over the existing IKE SAs: *shortcut offer*, *shortcut query*, *shortcut reply* |
| Trigger | Hub sees traffic hairpin and sends an NHRP redirect | Hub sees traffic hairpin between two `auto-discovery-sender` tunnels and sends a shortcut offer |
| Path of the answer | Resolution request goes via the hub; the destination spoke sends the resolution reply **directly** over the new spoke-to-spoke tunnel | Shortcut query **and** shortcut reply both travel via the hub over the existing IKE SAs; the spokes then run IKE directly |
| Spoke routing after discovery | NHRP shortcut/override routes | Normal routing: BGP next hops resolve over the shortcut (route reflection, BGP on loopback, dynamic BGP) or IKE-injected routes |
| NAT | NHRP and IPsec NAT-T | NAT-T, plus UDP hole punching between spokes behind NAT (the NAT device must support RFC 4787 endpoint-independent mapping) |

## Requirements

| Where | Requirement |
|---|---|
| Hub phase 1 (dial-up, `type dynamic`) | `set auto-discovery-sender enable` (default disable) |
| Spoke phase 1 | `set auto-discovery-receiver enable` (default disable) |
| Hub firewall policy | **Spoke-to-spoke must be allowed on the hub**, with srcintf and dstintf both the hub tunnel (or overlay zone). This applies to ADVPN 1.0 and 2.0. The first packets cross the hub, and that crossing is what triggers the offer |
| Hub phase 1 | `net-device disable` in Fortinet's ADVPN-with-BGP example. Spokes in the same example use `net-device enable` |
| Routing | In the BGP example, iBGP between hub and spokes with `neighbor-group` / `neighbor-range` on the hub. Before a shortcut exists, the remote spoke's prefixes must resolve through the hub. Once it exists, they must resolve through the shortcut |
| Spoke policies | Policies on the spoke's parent tunnel (or its SD-WAN zone) also cover the shortcut instances |
| Phase 1 routing knobs | `add-route disable` when BGP carries routes. DPD `on-idle` in Fortinet's examples |

Fortinet's admin guide notes that the GUI doesn't support options such as `auto-discovery-sender`, `auto-discovery-receiver` and `auto-discovery-forwarder` (or the iBGP neighbor group). The IPsec Wizard's Hub-and-Spoke template can build a basic ADVPN hub and spokes, but you set and tune the individual options in the CLI (or with FortiManager templates).

## Shortcut negotiation step by step

Spoke1 (LAN 10.1.1.0/24) sends traffic to Spoke2 (LAN 10.1.2.0/24). Both have tunnel `HUB1-VPN1` to `FGT-Hub`.

1. Spoke1's route to 10.1.2.0/24 points to the hub, so the first packets go over `HUB1-VPN1`.
2. The hub's spoke-to-spoke policy accepts them and forwards them to Spoke2 over the hub dial-up interface. Traffic has entered and left on the auto-discovery-sender phase 1, so the hub sends a **shortcut offer** to Spoke1. It repeats offers every `auto-discovery-offer-interval` seconds (default 5) while the shortcut isn't formed.
3. Spoke1 sends a **shortcut query** through the hub toward the destination.
4. Spoke2 answers with a **shortcut reply**, relayed by the hub, carrying its reachable address (and its NAT address/port, if any).
5. Spoke1 runs IKE directly with Spoke2 and creates the dynamic tunnel `HUB1-VPN1_0`, an instance of its parent `HUB1-VPN1`.
6. Routing moves Spoke2's prefixes onto the shortcut, and traffic flows directly.

What this looks like in `diagnose debug application ike -1` on the initiating spoke (an IKEv1 overlay, from Fortinet's NAT hole-punching example pattern):

```text
ike 0:HUB1-VPN1:35: notify msg received: SHORTCUT-OFFER
ike 0:HUB1-VPN1: shortcut-offer 10.1.1.10->10.1.2.20 psk 64 ppk 0 ver 1 mode 0
ike 0:HUB1-VPN1: send shortcut-query 1438189781753480593 d3fdd1bfbc94caee/0000000000000000 192.0.2.10 10.1.1.10->10.1.2.20 psk 64 ttl 32 nat 0 ver 1 mode 0
ike 0:HUB1-VPN1:35: notify msg received: SHORTCUT-REPLY
ike 0:HUB1-VPN1: recv shortcut-reply 1438189781753480593 d3fdd1bfbc94caee/16a1eb5b0f37ee23 192.0.2.20 to 10.1.1.10 psk 64 ppk 0 ver 1 mode 0
ike 0:HUB1-VPN1: adding new dynamic tunnel for 192.0.2.20:500
ike 0:HUB1-VPN1_0: added new dynamic tunnel for 192.0.2.20:500
```

And in `diagnose vpn tunnel list` on Spoke1:

```text
name=HUB1-VPN1_0 ver=1 serial=9 192.0.2.10:0->192.0.2.20:0 tun_id=192.0.2.20 ...
bound_if=7 lgwy=static/1 tun=intf/0 mode=dial_inst/3 encap=none/728 options[02d8]=npu create_dev no-sysctl rgwy-chg frag-rfc accept_traffic=1
 parent=HUB1-VPN1 index=0
proxyid_num=1 child_num=0 refcnt=17 ilast=4 olast=4 ad=r/2
```

`mode=dial_inst/3` with `parent=HUB1-VPN1 index=0` marks a shortcut instance. In Fortinet's ADVPN-with-BGP example, `ad=r/2` appears on the receiver spoke's established tunnels (the parent and its shortcut), while the backup tunnel, which also has `auto-discovery-receiver enable` but is down, shows `ad=/0`. Don't read `ad=/0` alone as "ADVPN not configured". `auto-discovery-psk` (default disable) uses pre-shared-key authentication for the shortcuts instead of the parent's `authmethod`.

## Shortcut lifetime: timeout, failback delay, dependent shortcuts

### Shortcut timeout

Shortcuts are torn down when idle. Enable `set idle-timeout enable` and set `idle-timeoutinterval` (minutes, 5–43200) on the spoke phase 1s. The CLI Reference gives the interval default as 15 minutes, while the ADVPN 2.0 admin-guide page says 5. Set it explicitly. Two details keep shortcuts from staying alive forever:

- SD-WAN creates dynamic link monitors for each shortcut. Their ICMP probes **don't count as user traffic** for keeping the shortcut alive.
- Control-plane traffic between spokes (health checks and spoke-to-spoke BGP) is matched by a dynamic IKE selector, so it **doesn't reset the idle timer** either.

ADVPN 2.0 adds `shared-idle-timeout` (IKEv2 only, `location-id` on both spokes), which tears down all shortcuts to the same remote spoke together.

### Delay for shortcut failback: hold-down-time

When a shortcut goes down and comes back, flapping can drag sessions back and forth. `set hold-down-time <seconds>` in an SD-WAN rule keeps a recovered shortcut (or a recovered parent overlay) at **low priority** until the timer expires. The default is 0 and the range 0–10000000. `diagnose sys sdwan service4` shows `Hold down time(15) seconds, Hold start at …`.

`set sla-stickiness enable` complements it. Existing sessions stay on an established shortcut while it remains in SLA, instead of being moved every time a preferred path reappears. New sessions still take the preferred path.

### Dependent vs independent shortcuts

`auto-discovery-shortcuts` controls what happens to shortcuts when their **parent** tunnel goes down:

| Value | Behaviour |
|---|---|
| `independent` (default) | Shortcuts stay up if the parent tunnel goes down |
| `dependent` | Shortcuts are brought down with the parent |

Independent is the default because a shortcut is a direct path that doesn't need the hub. Choose `dependent` when the shortcut's health is tied to the parent's underlay (same ISP), or when you want shortcut state to follow hub reachability.

## Network IDs and cross-overlay shortcuts

With two overlays per spoke (ISP1 and ISP2), shortcuts can form between the same overlays (ISP1↔ISP1) or across them (ISP1↔ISP2). IKEv2 `network-id` gives each overlay an ID, which also lets several shortcuts exist between the same two spokes. `auto-discovery-crossover` decides whether shortcuts may join **different** network IDs:

- `allow` (default): cross-overlay shortcuts are allowed, for example from an internet overlay to the other spoke's LTE overlay.
- `block`: shortcuts form only between tunnels with the same network ID. Use it to keep transports separate, such as never building an internet-to-MPLS shortcut that cannot work.

ADVPN 2.0 replaces much of this tuning with **transport groups** (next lessons).

## Troubleshooting checklist

| Symptom | Check |
|---|---|
| Spoke-to-spoke works but never shortcuts | Hub phase 1 `auto-discovery-sender`, spoke `auto-discovery-receiver`. Is traffic actually crossing the hub (spoke route via hub)? IKE debug for SHORTCUT-OFFER |
| Spoke-to-spoke fails entirely | Hub spoke-to-spoke policy (tunnel→same tunnel). Spoke inbound policy on the parent/zone |
| Offer and query seen, no tunnel | Reachability between spoke underlays. NAT (hole punching needs endpoint-independent mapping). Proposals and PSK/certificate on the parent phase 1s |
| Shortcut up, traffic still via hub | Routing: the remote prefix must resolve over the shortcut (BGP next hop, RR, recursive next hop). SD-WAN rule members and `shortcut` settings |
| Shortcuts flap | `hold-down-time`, `sla-stickiness`, idle timeout too short |

## Lab it yourself

ADVPN needs at least **three** FortiGates (one hub, two spokes), and the FortiGate-VM trial allows one VM per FortiCloud account, with 3 interfaces, 3 policies and 3 routes each. A hub alone needs WAN, LAN and tunnel interfaces plus spoke-to-hub, spoke-to-spoke and hub-to-spoke policies, so a working ADVPN lab needs full licences, the paid Fortinet on-demand labs or hardware. With the trial alone, you can configure the hub phase 1 (`auto-discovery-sender`) and the spoke-to-spoke policy and read the syntax, but no shortcut can form. For DMVPN comparison, build a Cisco IOS DMVPN phase 3 lab beside it and map each NHRP message to its IKE shortcut message.

## Key takeaways

- The hub needs `auto-discovery-sender` and a spoke-to-spoke policy. Spokes need `auto-discovery-receiver`. The BGP example uses hub `net-device disable` and iBGP with neighbor groups and ranges.
- Negotiation is IKE-based: the hub sends an offer, the spoke sends a query via the hub, the remote spoke replies, and the spokes run IKE directly to form `parent_0`.
- Shortcuts are dynamic instances (`mode=dial_inst/3`, `parent=…`). Policies on the parent or zone cover them.
- `idle-timeout` / `idle-timeoutinterval` tear down idle shortcuts. Health-check probes and spoke-to-spoke BGP don't keep them alive.
- `hold-down-time` delays failback to a recovered shortcut. `sla-stickiness` keeps sessions on an in-SLA shortcut.
- `auto-discovery-shortcuts dependent` drops shortcuts with the parent. `independent` is the default.
- `auto-discovery-crossover block` stops shortcuts between different network IDs. `allow` is the default.
