## What the routing must do

Fortinet's 7.6 architecture guide lists the routing duties for any ADVPN design:

1. **Reachability**: every LAN prefix is reachable across the overlay.
2. **Shortcut steering**: with no shortcut, a remote spoke's prefixes resolve through the hub. When a shortcut comes up, they resolve through it automatically. With several shortcuts, they resolve through all of them, so SD-WAN can choose. When the shortcuts go, routing reverts to the hub.
3. **Loopback reachability** (ADVPN 2.0): every node's loopback is reachable, so spokes can talk to each other, for example to trigger extra shortcuts.

Each design below meets these duties in a different way.

## Design 1: hub-and-spoke ADVPN with iBGP and route reflection (BGP per overlay)

This is the classic design from Fortinet's ADVPN-with-BGP example.

- Tunnels are addressed. The hub `VPN1` is 10.10.1.254/32 with `remote-ip 10.10.1.253 255.255.255.0`. Spoke1 `HUB1-VPN1` is 10.10.1.1/32 with `remote-ip 10.10.1.254 255.255.255.0`.
- The hub runs iBGP (AS 65000) with a `neighbor-group` (`route-reflector-client enable`, `remote-as 65000`) and a `neighbor-range` of 10.10.1.0/24. Each spoke has one neighbor, the hub's tunnel IP, per overlay.
- A route reflector **doesn't change the next hop**, unless you enable `next-hop-self-rr` on the hub neighbor group, which you must not do here. Spoke1 therefore learns Spoke2's LAN with Spoke2's overlay address (10.10.1.2) as next hop. Before a shortcut exists, that next hop is reached through the hub tunnel. Once `HUB1-VPN1_0` comes up toward Spoke2, the same next hop resolves through the shortcut:

```text
FGT-Spoke1 # get router info routing-table bgp
Routing table for VRF=0
B       10.0.1.0/24 [200/0] via 10.10.1.254, HUB1-VPN1, 00:23:57
B       10.1.2.0/24 [200/0] via 10.10.1.2, HUB1-VPN1_0, 00:00:42
```

Costs: one iBGP session per overlay per spoke. The hub reflects every spoke prefix to every spoke (CPU and memory on the hub, large tables on spokes), and the tunnel address plan grows with the overlays. Fortinet's comparison table (BGP per overlay versus BGP over loopback) also lists BGP add-path as required for this design and states that it does not work with ADVPN 2.0.

## Design 2: BGP on loopback with ADVPN

- Each spoke peers once per hub, `Branch-Lo` to the hub's `BGP-Lo`. Tunnels stay unaddressed.
- Every overlay sets `exchange-ip-addr4 <own loopback>`. When **any** tunnel comes up, including a shortcut, IKE installs a /32 to the peer's loopback over it.
- The hub reflects spoke routes with the **spoke loopback** as next hop. Spokes need `recursive-next-hop enable` (resolve the BGP next hop through another route) and `ibgp-multipath enable`.
- Result: before the shortcut, 172.16.0.2 (Spoke2's loopback) resolves over the hub overlays. Once `HUB1-VPN1_0` exists, IKE adds 172.16.0.2/32 over the shortcut, and Spoke2's prefixes follow it automatically:

```text
FGT-Spoke1 # get router info routing-table details 10.1.2.0/24
Routing table for VRF=0
Routing entry for 10.1.2.0/24
  Known via "bgp", distance 200, metric 0, best
  * vrf 0 172.16.0.2 priority 1 (recursive via HUB1-VPN1_0 tunnel 192.0.2.20)
```

With one BGP session per hub regardless of overlay count, this is the 7.6 recommendation, and it works with ADVPN 2.0.

## Dual hub-and-spoke ADVPN with iBGP and with eBGP

### iBGP (one AS for hubs and spokes)

Both hubs are route reflectors in AS 65000. Every spoke peers with both, through tunnels or loopbacks, and uses `ibgp-multipath`. Next hops are preserved through either hub, so shortcuts can be triggered through whichever hub the first packets cross. SD-WAN rules on the spoke (zones `HUB1`, `HUB2`) choose the hub, and BGP self-healing tells the hubs which overlay to use back. This is the straightforward dual-hub ADVPN design and what the overlay template builds.

### eBGP (spokes and hubs in different AS numbers)

eBGP is used when the design needs AS-path policy, for example per-region or per-customer AS numbers, or when hubs must apply eBGP policy toward a core. The ADVPN problem is the **next hop**. When a hub advertises a route to an eBGP peer, it normally sets the next hop to itself (its update-source loopback). Spokes would then always see the hub as next hop, and routing would never move onto a shortcut. On FortiOS, the hub's neighbor group needs:

- `set attribute-unchanged next-hop`, so routes reflected between spokes keep the originating spoke's address as next hop;
- `set ebgp-enforce-multihop enable` when peering loopback to loopback;
- on spokes sharing one AS, `allowas-in-enable` (with `allowas-in`, default 3) so routes carrying their own AS aren't rejected, or else a unique AS per spoke;
- `ebgp-multipath enable` where routes arrive from two eBGP hubs.

The same next-hop logic explains the multiregion rule. With **eBGP between regional hubs**, the next hop changes at the region boundary and regions exchange summaries, so shortcuts stay inside each region. Cross-regional shortcuts need **iBGP** with original next hops preserved.

> **Exam tip:** "Shortcut is up but traffic to the remote spoke still goes through the hub" in an eBGP design almost always means the next hop was rewritten to the hub. Check the BGP next hop of the remote prefix on the spoke.

## Design 3: ADVPN without BGP route reflection

Route reflection makes the hub process and send every spoke's routes to every spoke. With thousands of prefixes, that means high hub CPU and spokes learning routes they never use. Fortinet documents two RR-less designs.

### 3a. Dynamic BGP over the shortcut

- The hub has **route reflection disabled** (`route-reflector-client disable`, the default) and advertises **summary routes** covering all spokes, backed by blackhole static routes on the hub.
- Each spoke also has a `neighbor-group` + `neighbor-range` covering the **other spokes' loopbacks**, with **`set passive disable`**. Neighbor groups are passive by default, and two passive spokes would never open the session.
- Traffic follows the summary to the hub, the shortcut forms, and then the two spokes **actively open BGP to each other over the shortcut** and exchange their specific routes. Spokes learn only the routes of spokes they actually talk to.

```text
FGT-Spoke1 # get router info bgp summary
VRF 0 BGP router identifier 172.16.0.1, local AS number 65000
BGP table version is 6
1 BGP AS-PATH entries
0 BGP community entries

Neighbor        V         AS MsgRcvd MsgSent   TblVer  InQ OutQ Up/Down  State/PfxRcd
172.16.255.252  4      65000     252     254        3    0    0 00:17:22        3
172.16.0.2      4      65000       6       6        5    0    0 00:00:14        1

Total number of neighbors 2
```

The second neighbor is Spoke2, which appeared when the shortcut came up. Fortinet's 7.6 architecture guide calls dynamic BGP on loopback **best practice** over the RR design. Each spoke forms one session with each hub plus sessions only toward spokes it has shortcuts with, even when several shortcuts join the same pair. Spokes can also be added without touching other devices. The FortiManager overlay template exposes it as **Dynamic BGP**, with route reflection then optional.

### 3b. IKE-injected routes from phase 2 selectors

For large-scale networks, spokes can learn each other's LANs from IKE instead of BGP:

```text
config vpn ipsec phase1-interface
    edit "HUB1-VPN1"
        set ike-version 2
        set net-device enable
        set add-route enable
        set mode-cfg enable
        set mode-cfg-allow-client-selector enable
        set auto-discovery-receiver enable
    next
end
config vpn ipsec phase2-interface
    edit "HUB1-VPN1"
        set phase1name "HUB1-VPN1"
        set src-name "LAN_Net"
        set dst-name "all"
    next
end
```

The hub gives spokes only a default or summary route by BGP. When a shortcut forms, each spoke installs IKE routes (distance 15) to the other spoke's phase 2 source selectors over the shortcut, for example `S 10.1.2.0/24 [15/0] via HUB1-VPN1_0 tunnel 192.0.2.20`. No reflection is needed.

## SD-WAN support for ADVPN

- **Members**: list the parent overlays (`HUB1-VPN1`, `HUB1-VPN2`) as members. Shortcuts inherit the parent's member and health check and appear as `Seq(3 HUB1-VPN1_0)` in `diagnose sys sdwan health-check`. SD-WAN monitors each shortcut with dynamic ICMP link monitors.
- **Rules**: a new shortcut is inserted ahead of its parent in the rule's member list. Rule options: `set shortcut enable|disable` (use ADVPN shortcuts for this rule), `use-shortcut-sla` (include shortcuts in quality comparison) and, with ADVPN 2.0, `shortcut-priority`.
- **tie-break fib-best-match**: Fortinet's MSSP guide recommends it for ADVPN rules. When a shortcut falls out of SLA, the hub overlays would otherwise remain valid through a default or summary route. fib-best-match only considers members with the best (most specific) route, so traffic stays on the shortcut path until an alternative shortcut exists. It also enables load balancing across several shortcuts with `load-balance enable`.
- **Stability**: `hold-down-time` and `sla-stickiness`, from the previous lesson.

## Alternative overlay and routing designs

| Design | Notes |
|---|---|
| ADVPN with OSPF (or RIP) | Fortinet documents both. Simpler for small estates, but no BGP policy tools or self-healing communities |
| Static hub-and-spoke, no ADVPN | All spoke-to-spoke traffic through the hub. Hub bandwidth and latency are the cost |
| Full mesh of static tunnels | Direct paths, but every site change touches every site. Doesn't scale |
| Overlays optional | Fortinet notes SD-WAN can steer to underlays too, for example for DIA |

## Key takeaways

- The routing must resolve remote spoke prefixes via the hub without a shortcut and via the shortcut when it exists. ADVPN 2.0 also needs loopback reachability.
- iBGP route reflection preserves the remote spoke as next hop, so the route moves onto the shortcut when it forms.
- BGP on loopback relies on `exchange-ip-addr4` /32s and `recursive-next-hop`, with one session per hub.
- eBGP rewrites the next hop. ADVPN over eBGP needs `attribute-unchanged next-hop`, and eBGP between regions limits shortcuts to each region.
- RR-less ADVPN: dynamic BGP (spoke neighbor groups with `passive disable`, hub summaries) or IKE routes from phase 2 selectors with `mode-cfg-allow-client-selector` and `add-route`.
- SD-WAN uses shortcuts through the parent members. Use `tie-break fib-best-match` for ADVPN rules.
