## Why IPsec and MTU collide

ESP adds a new outer IP header, the ESP header and IV, padding, the ESP trailer and the integrity check value. NAT traversal adds a further 8-byte UDP header. A 1500-byte packet from a LAN host no longer fits a 1500-byte underlay once it is encrypted. Something must then fragment it, or the sender must send less.

FortiOS shows the result directly. In `diagnose vpn tunnel list`, the SA line carries an `mtu=` value, which is the largest inner packet the SA can carry:

```text
name=HUB1-VPN1 ver=2 serial=2 192.0.2.10:0->203.0.113.1:0 tun_id=203.0.113.1 ... dst_mtu=1500
...
natt: mode=none draft=0 interval=0 remote_port=0
 SA: ref=6 options=1a227 type=00 soft=0 mtu=1438 expire=1225/0B replaywin=1024
...
name=HUB1-VPN1_0 ver=2 serial=9 192.0.2.10:4500->192.0.2.20:4500 tun_id=192.0.2.20 ... dst_mtu=1500
...
natt: mode=keepalive draft=32 interval=10 remote_port=4500
 SA: ref=6 options=1a227 type=00 soft=0 mtu=1422 expire=447/0B replaywin=1024
```

Fortinet's ADVPN example shows exactly this pattern. With the same AES/SHA1 proposal, the parent tunnel without NAT-T reports `mtu=1438`, while the shortcut behind NAT (UDP 4500) reports `mtu=1422`. Stronger or different proposals change the number, so read it rather than memorising one value.

## TCP MSS: make the sender send less

For TCP, the clean fix is to lower the **maximum segment size** announced in the SYN, so that hosts never build oversized segments. On FortiGate this is done per firewall policy:

```text
config firewall policy
    edit 20
        set name "LAN-to-HUB1"
        set srcintf "port5"
        set dstintf "HUB1"
        ...
        set tcp-mss-sender 1380
        set tcp-mss-receiver 1380
    next
end
```

- `tcp-mss-sender` rewrites the MSS in packets from the session originator. `tcp-mss-receiver` rewrites it in packets from the responder. Both default to `0`, meaning no change. Range 0–65535.
- Size it from the tunnel MTU: MSS ≤ tunnel MTU − 40 for IPv4 (20-byte IP + 20-byte TCP headers). For `mtu=1422`, 1382 is the ceiling. Most designs leave margin for header options and for the worst underlay.

> **Exam tip:** From **FortiOS 7.6.1**, FortiGate no longer lowers the TCP MSS itself for traffic that is too large for an IPsec tunnel. It only sends ICMP "fragmentation needed" back to the sender so the sender can adjust. Earlier releases reduced the MSS *and* sent the ICMP message. If ICMP is filtered between the FortiGate and the host, path MTU discovery fails, so in 7.6.1+ explicit `tcp-mss-sender` / `tcp-mss-receiver` clamping matters more.

## Fragmentation: before or after encryption

UDP and other non-TCP traffic can't be fixed with MSS. For that traffic, the phase 1 option `ip-fragmentation` decides where an oversized packet is split:

| `ip-fragmentation` | Behaviour | Trade-off |
|---|---|---|
| `post-encapsulation` (default, RFC compliant) | Encrypt first, then fragment the ESP packet | The receiver must reassemble ESP fragments before decrypting. Some networks drop fragments |
| `pre-encapsulation` | Fragment the inner packet, then encrypt each fragment | Every fragment travels as a complete ESP packet. The far-end host reassembles the inner packet |

Fortinet documents a specific reason to choose `pre-encapsulation`. When IPsec is **NP-offloaded** and an encapsulated packet exceeds the MTU, the NPU cannot generate the ICMP "need to fragment" message. Only the CPU path can. The sender is never told, so packets are lost. Pre-encapsulation fragmentation avoids that loss.

### IKE fragmentation

IKE messages can be large too, typically IKE_AUTH carrying certificate chains. `set fragmentation enable` (default enable) fragments IKE messages on retransmission, and `fragmentation-mtu` (500–16000, default 1200) sets the size. This is separate from data-plane fragmentation. It helps when certificate-based tunnels fail to come up across networks that drop IP fragments.

## NPU offload of IPsec

On models with network processors (NP6, NP7, NP6XLite and so on), IPsec encryption and decryption is offloaded when `npu-offload` is enabled on the phase 1, which is the default. If the NPU can't do it, the content processor (CP) tries next, then the CPU. Fortinet lists the main reasons IPsec ends up on the CPU:

- the model has no NPU;
- NPU offload or CP processing was disabled (`npu-offload disable`; `config system global` → `ipsec-asic-offload` / `ipsec-hmac-offload disable` keep the CP out);
- the proposal uses a cipher the NPU and CP don't support: **SEED, ARIA, chacha20poly1305**.

### Reading offload state

| Where | Field | Meaning |
|---|---|---|
| `diagnose vpn tunnel list` (SA) | `npu_flag=03` | NPU processes the SA in both directions |
| | `npu_flag=00` | Not offloaded. Check the CP or software counters |
| | `dec_npuid` / `enc_npuid` | Which NPU handles decryption / encryption (0 when not offloaded) |
| `diagnose vpn ipsec status` | counters per engine (`NP6_0`, `NP6_1`, `CP8`, `SOFTWARE`) | Which engine is actually encrypting and decrypting. The ticking counter tells you |
| `diagnose sys session list` | `npu info: flag=0x81/0x82, offload=8/8` | Per direction: `0x81` regular traffic, `0x82` IPsec traffic. `offload=8/8` marks NP6 sessions |
| | `no_ofld_reason:` | Present instead when the session is not offloaded, with the reason (for example `local`) |

The two `flag=` values are the original and reply directions. A LAN-to-tunnel session therefore shows one direction as `0x82` (into or out of the tunnel) and the other as `0x81`.

> **Watch out:** Offloaded packets bypass the CPU, so `diagnose sniffer packet` doesn't show them. To capture, temporarily set `auto-asic-offload disable` on the policy (or `npu-offload disable` on the phase 1), then re-enable it.

## Forward error correction (FEC)

FEC sends redundant packets alongside the data so the receiver can rebuild lost packets without retransmission. It is useful for real-time UDP (voice, video) over lossy underlays such as LTE or broadband. **Adaptive FEC** ties the redundancy level to SD-WAN health-check results.

```text
config vpn ipsec fec
    edit "FEC-VOICE"
        config mappings
            edit 1
                set base 8
                set redundant 2
                set packet-loss-threshold 10
            next
        end
    next
end
config vpn ipsec phase1-interface
    edit "HUB1-VPN1"
        set fec-egress enable
        set fec-health-check "HUB1_HC"
        set fec-mapping-profile "FEC-VOICE"
        set fec-base 10
        set fec-redundant 1
    next
end
config firewall policy
    edit 30
        set service "ALL_UDP"
        set fec enable
        ...
    next
end
```

Key facts:

- `fec-egress` on the sending side and `fec-ingress` on the receiving side. Both default to disable.
- `fec-base` (1–20, default 10) and `fec-redundant` (1–5 for Reed-Solomon, 1 for XOR, default 1) set the static ratio. `fec-codec` is `rs` (default) or `xor`. With `xor`, the base and redundant values are not adapted.
- `fec-send-timeout` (default 5 ms) and `fec-receive-timeout` (default 50 ms) bound the latency FEC adds.
- Mappings in `config vpn ipsec fec` are evaluated top to bottom against the health check, for example `packet-loss-threshold` or `bandwidth-up-threshold`. The phase 1 base/redundant values apply while no mapping threshold is exceeded.
- **FEC does not support NPU offload.** That is why the policy-level `set fec enable` exists. Apply FEC only to the loss-sensitive UDP flows so everything else stays offloaded. In `diagnose sys session list`, a FEC session shows `fec` in its `state=` line, and the offloaded TCP session next to it shows `npu`. Fortinet also advises against using NPU offload and anti-replay together with FEC.

> **Real world:** FEC costs bandwidth: 1 redundant per 10 base packets is 10% overhead, and 2 per 8 is 25%. Use it where loss, not bandwidth, is the problem, and prefer SD-WAN steering when a better link exists.

## Lab it yourself

The FortiGate-VM trial has no NPU, so every tunnel shows `npu_flag=00` and the `SOFTWARE` counters in `diagnose vpn ipsec status` tick. That is still useful for practising the reading. MSS clamping fits in the trial: build one tunnel to a Linux strongSwan peer, set `tcp-mss-sender` / `tcp-mss-receiver` on the one outbound policy, and watch the SYN with `diagnose sniffer packet any 'tcp[13] & 2 != 0' 4`. You can also compare `ip-fragmentation` settings with large pings using the don't-fragment bit. FEC needs SD-WAN health checks on both ends and two FortiGates, and real offload testing needs NP-based hardware. Both go beyond the trial.

## Key takeaways

- The SA `mtu=` value in `diagnose vpn tunnel list` is the inner MTU. NAT-T lowers it (1438 vs 1422 in Fortinet's example).
- Clamp TCP with `tcp-mss-sender` / `tcp-mss-receiver` on the policy, at MSS ≤ tunnel MTU − 40.
- From 7.6.1, FortiGate stops reducing MSS itself and relies on ICMP "fragmentation needed".
- `ip-fragmentation post-encapsulation` is the RFC default. Use `pre-encapsulation` when NP-offloaded traffic can't signal the MTU.
- `npu_flag=03` means offloaded both ways. SEED, ARIA and chacha20poly1305 are not offloaded. Session flag `0x82` marks IPsec and `0x81` regular traffic.
- FEC (`fec-egress` / `fec-ingress`, adaptive mappings) isn't NPU-offloaded, so enable it per policy for UDP only.
