## What the SD-WAN overlay template is

The **SD-WAN overlay template** (SD-WAN Manager > **Overlay Orchestration** > Create New) is a wizard that builds a complete hub-and-branch overlay from Fortinet's recommended IPsec and BGP designs. You describe the topology, pick the hubs and the branch device groups, list the WAN underlays, and FortiManager generates:

- **IPsec, BGP and CLI provisioning templates** for each hub and for the branches,
- **template groups**, one per hub and one for the branches, **assigned automatically** to the devices you selected,
- the **`branch_id`** ADOM metadata variable,
- optionally SD-WAN zones, members, performance SLAs, normalized interfaces, health-check policies and a default route template.

What it does **not** give you is SD-WAN intelligence. It builds the tunnels and the routing. SD-WAN rules (which traffic goes where, by which strategy) still come from an **SD-WAN template**, and the traffic policies from a **policy package**.

> **Exam tip:** "The administrator finished the overlay wizard and installed it. Tunnels and BGP are up, but all traffic uses the implicit rule." That's expected: the overlay template doesn't create SD-WAN rules.

## Before you start

Prerequisites from the FortiManager 7.6 docs:

1. Hub and branch FortiGates are **added to FortiManager** (real or model devices).
2. Their **ISP links and other interfaces** are configured.
3. At least one **device group** for the branches exists.
4. **Underlay reachability** between hub and branches already works (static routes, BGP or a DHCP-provided route). The wizard builds overlays on top of a working underlay; it doesn't build the underlay.

The SD-WAN Devices page adds one more condition: a FortiGate must have **SD-WAN management enabled** before an overlay template can use it.

Network planning decisions: the **overlay** address space (default **10.10.0.0/16**), the **loopback** space (default **172.16.0.0/16**) and the **BGP AS** for the region (default **65000**).

## The wizard, step by step

| Step | What you decide |
|---|---|
| **Name** | Template name and description |
| **Region Settings** | **Topology**: Single HUB, Dual HUB (Primary/Secondary), Dual HUB (Primary/Primary), Multi HUB. **Advanced**: Loopback IP Address, Overlay Network, BGP-AS Number, **BGP on Loopback**, **Dynamic BGP** (then **Route Reflection** enable/disable), **Auto-Discovery VPN** (Disabled, Legacy, ADVPN 2.0), **Segmentation Over Single Overlay**, **Overlay Authentication Method** (Pre-shared Key, the default, or Signature) |
| **Role Assignment** | The hub devices or VDOMs (for Multi HUB: 3 or 4 hubs, each with a **Cost**, which can be a metadata variable), the **branch device group(s)**, and **Automatic Branch ID Assignment** |
| **Network Configuration** | Per hub and per branch group: **WAN Underlay** interfaces (with **Private Link**, hub **Override IP**, branch **Cost**, and with ADVPN 2.0 a **Transport Group**), **Network Advertisement** (Connected or Static), advanced neighbors/VRF, and branch route maps |
| **Template Options** | Toggles for overlay objects in an SD-WAN template, interfaces and zones, health-check servers as performance SLAs, **Normalize Interfaces**, health-check firewall policies in the hub/branch policy packages, and a default route to the SD-WAN zones in a static route template |
| **Summary** | Finish creates and assigns the provisioning templates |

### Topology choices

| Topology | Behaviour |
|---|---|
| **Single HUB** | One hub, one overlay per branch underlay |
| **Dual HUB (Primary/Secondary)** | Two hubs; the secondary hub's members get a **higher cost**, so SD-WAN rules prefer the primary |
| **Dual HUB (Primary/Primary)** | Two hubs with equal preference |
| **Multi HUB** | 3 or 4 hubs, with a cost per hub |

The only difference between the two dual-hub options is that cost. Which hub traffic actually uses is still decided by the SD-WAN rules in your SD-WAN template.

### Region advanced options

| Option | Effect |
|---|---|
| **BGP on Loopback** | One BGP session from each branch to each hub, **regardless of how many overlays** exist, sourced from loopbacks. Fewer sessions and fewer advertised routes than BGP per overlay |
| **Dynamic BGP** | ADVPN spokes form BGP sessions with each other dynamically over shortcuts, so hubs don't have to reflect routes. Turning it on reveals **Route Reflection** (enable or disable) |
| **Auto-Discovery VPN** | **Disabled**, **Legacy** (ADVPN 1.0) or **ADVPN 2.0** (spokes choose the shortcut underlay by link health) |
| **Segmentation Over Single Overlay** | VRF segmentation across one overlay using BGP, VRF and VPNv4; tunnels use `vpn-id-ipip` encapsulation and the wizard generates VPNv4, VRF and PE/CE BGP configuration |
| **Overlay Authentication Method** | Pre-shared key, or Signature with a certificate (a dynamic local certificate or a metadata variable) |

### Network Configuration details worth knowing

- **Private Link** marks an underlay (MPLS, for instance) on which **no overlay is created**. With ADVPN 2.0 a private-link branch underlay defaults to **Transport Group 1**; others default to **0**.
- **Override IP** (hub) replaces the hub underlay's IP address with the address you enter. Not available on a private link. The docs don't name a use case; the usual one is a hub whose WAN address is translated by an upstream NAT device, so branches must dial the public address.
- **Cost** on a branch underlay defaults to 0.
- **Network Advertisement**: *Connected* advertises interface subnets; *Static* advertises listed prefixes.
- Route maps: the wizard ships preconfigured maps for BGP self-healing. Hubs use **RM-VPN-Priority** (five communities, each matched to a route map); branches use **Priority_1** to **Priority_4** and **Priority_999** (catch-all), lower numbers preferred.

## What the wizard creates

For a dual-hub template:

```text
SD-WAN overlay template "EU-Overlay": objects created
Template groups ...... HUB1, HUB2, BRANCH
IPsec templates ...... HUB1_IPsec, HUB2_IPsec, BRANCH_IPsec
BGP templates ........ HUB1_BGP, HUB2_BGP, BRANCH_BGP
CLI templates ........ HUB1_CLI, HUB2_CLI, BRANCH_CLI
                       (CLI template groups HUB1_CLIGRP, HUB2_CLIGRP, BRANCH_CLIGRP)
Metadata variable .... branch_id (unique per branch)
With "Add Overlay Objects to SD-WAN Template":
  zones/members ...... WAN1 > port1, WAN2 > port2,
                       HUB1 > HUB1-VPN1, HUB1-VPN2, HUB2 > HUB2-VPN1, HUB2-VPN2
  performance SLA .... HUB1_HC, HUB2_HC
With "Normalize Interfaces":
  HUB-Lo (maps to HUB1-Lo / HUB2-Lo per device), HUB1, HUB2, VPN1, VPN2
Hub loopbacks ........ HUB1-Lo, HUB2-Lo (built by the hub CLI templates)
```

A single-hub template creates only the HUB1 objects; Multi HUB adds HUB3 and HUB4.

## Overlay IP design

The overlay range is split into **one subnet per underlay** across all hubs, rounded up to a power of two, with minimums of four subnets (single hub) or eight (dual hub). In a dual-hub design, HUB1 takes the first half of the subnets and HUB2 the second half.

| Underlays (total) | Subnet size from 10.10.0.0/16 | Usable addresses per overlay |
|---|---|---|
| 1–4 (single hub) | /18 | 16,382 |
| 5–8 (dual hub minimum) | /19 | 8,190 |
| 9–16 (multi hub) | /20 | 4,094 |

Example, dual hub with two underlays per hub: HUB1_VPN1 10.10.0.0/19, HUB1_VPN2 10.10.32.0/19, HUB2_VPN1 10.10.128.0/19, HUB2_VPN2 10.10.160.0/19, and four subnets left idle.

Each overlay supports as many FortiGates as its subnet has usable addresses, so the overlay range caps the branch count. **Automatic Branch ID Assignment** is limited the same way: with the default /19 overlays (5–8 underlays) it can hand out up to 8,190 IDs. A design with more branches than one overlay subnet can hold needs a bigger overlay network than /16 (for example 10.0.0.0/8).

> **Watch out:** Plan the overlay size before onboarding. A larger overlay network changes every overlay subnet, which means reinstalling every hub and branch.

## branch_id and onboarding

`branch_id` is the per-branch key the generated templates use. **Every branch needs a unique value.** Two ways:

- Set it per device (Edit Variable Mapping, or a `branch_id` column in the model device CSV).
- Enable **Automatic Branch ID Assignment** in Role Assignment. FortiManager then assigns IDs to devices in the branch group, including devices added later or through a ZTP blueprint.

Onboarding a new branch after the overlay exists:

1. Add the FortiGate as a model device (optionally from a blueprint, or in bulk from CSV).
2. Put it in the overlay template's **branch device group**. The branch templates are **assigned automatically**.
3. Set its metadata variables (`branch_id` unless automatic).
4. Assign a policy package and install with the **Install Wizard**.

## Editing the overlay template

Edit it in SD-WAN Manager > Overlay Orchestration. Saving **regenerates the provisioning templates** it owns; you then reinstall them. You may edit the generated templates directly, but **the next save of the overlay template overwrites any field the overlay manages** (for example a Local AS changed by hand in HUB1_BGP goes back to the overlay's AS). Fields the overlay doesn't set, such as descriptions, survive.

## The full workflow

1. Meet the prerequisites and plan addressing.
2. Run the overlay template wizard.
3. Assign `branch_id` values (or use automatic assignment) and any custom variables.
4. Create or edit an **SD-WAN template** that uses the overlay zones, members and SLAs, and write the **SD-WAN rules**.
5. Create the **policy packages** for hubs and branches.
6. **Install** with the Install Wizard and check the SD-WAN Monitor (Template View shows only the devices provisioned by the template you select).

## Use cases and design choices

| Requirement | Overlay template choice |
|---|---|
| Small estate, one data centre | Single HUB, BGP on Loopback, ADVPN Disabled |
| Two DCs, one preferred | Dual HUB (Primary/Secondary) |
| Two DCs, load shared | Dual HUB (Primary/Primary) |
| Branch-to-branch voice without hairpinning through the hub | ADVPN (2.0 for health-based shortcut path choice) |
| Large ADVPN estate where hubs shouldn't reflect every branch route | Dynamic BGP, Route Reflection disabled |
| MPLS link with no overlay, but used for ADVPN 2.0 path choice | Branch underlay marked Private Link (Transport Group 1) |
| Multi-tenant or departmental segmentation over one set of tunnels | Segmentation Over Single Overlay |
| Hub reachable only through a NAT address (typical use; the docs only say it overrides the underlay IP) | Override IP on the hub underlay |

## Lab it yourself

The overlay template needs at least one hub and one branch FortiGate. With one FortiGate-VM trial and the FortiManager-VM trial (3 devices):

- Add your FortiGate-VM as the hub and a **model device** as the branch (in a branch device group), run the wizard with Single HUB and BGP on Loopback, and study the generated templates, template groups and `branch_id`. The license count rules don't say whether a model device counts, so plan as if it takes one of the trial's three device slots.
- Look at Install Preview for the real hub. Expect the generated configuration to need more interfaces, routes and policies than the trial allows (3 each), so don't install it to the trial if you want to keep the VM usable.
- A working overlay needs a second real FortiGate (a licensed VM, another FortiCloud account's trial, or hardware) or Fortinet's on-demand labs.

## Key takeaways

- SD-WAN Manager > **Overlay Orchestration** generates IPsec, BGP and CLI templates and per-hub/branch **template groups**, assigned automatically, plus `branch_id`.
- It assumes working **underlay** reachability and adds **no SD-WAN rules**: you still need an SD-WAN template and policy packages.
- Defaults: overlays **10.10.0.0/16**, loopbacks **172.16.0.0/16**, **AS 65000**, authentication **pre-shared key**.
- Primary/Secondary vs Primary/Primary differ only in the secondary hub's **higher cost**.
- **BGP on Loopback** = one BGP session per branch per hub; **Dynamic BGP** lets spokes peer over shortcuts and makes **Route Reflection** optional.
- **Private Link** underlays get no overlay; with ADVPN 2.0 they default to **Transport Group 1**.
- Every branch needs a unique `branch_id` unless **Automatic Branch ID Assignment** is on; overlay subnet size caps branch count.
- Re-saving the overlay template overwrites hand edits to the fields it manages.
