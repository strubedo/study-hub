## Two ways FortiManager builds IPsec

FortiManager can build IPsec VPNs in two different ways, and the exam expects you to know which fits an SD-WAN design.

| | **VPN Manager** (IPsec VPN communities) | **IPsec tunnel templates** (provisioning templates) |
|---|---|---|
| Model | Pick a topology and add gateways: **Full Meshed**, **Star** or **Dial up** | Write one hub template and one branch template, assign them to devices or device groups |
| Enable | Central VPN management must be on (VPN checkbox under the ADOM's Central Management, or the VPN Management Mode when ADOMs are off) | Nothing extra: Device Manager / SD-WAN Manager provisioning templates |
| Output | Tunnels and the phase 1/2 objects generated per gateway pair | Exactly the phase 1/2 interfaces you defined, with per-device values from metadata variables |
| Fits | Classic policy-driven site-to-site VPNs, small meshes | SD-WAN overlays: named dial-up tunnels per WAN link that become SD-WAN members, BGP over them, ADVPN |

For SD-WAN, Fortinet's design path is the **template** path. The SD-WAN overlay template wizard itself builds IPsec templates (and BGP and CLI templates), never VPN Manager communities.

## Recommended IPsec templates

FortiManager ships three recommended IPsec templates. You don't edit them directly: select one in **Provisioning Templates > IPsec Tunnel**, click **Activate**, fill in the fields, and FortiManager creates a normal template from it that you can then edit, clone, add to a template group and assign.

| Template | For | Fields asked at activation |
|---|---|---|
| **HUB_IPSec_Recommended** | The hub in an SD-WAN design. Assumes **dial-up** spokes (Remote Device: Dynamic) | Template name, outgoing interface (the port branches connect to), IPv4 start IP, end IP and netmask (the range handed to dial-up spokes), pre-shared key; optional ADVPN |
| **Branch_IPSec_Recommended** | Branches in an SD-WAN design | Template name, outgoing interface, **Local ID** (so the hub can tell multiple tunnels apart), remote gateway (the hub interface IP), pre-shared key; optional ADVPN |
| **IPSec_Fortinet_Recommended** | General use, no assumption about the role | Template name, outgoing interface, remote gateway, pre-shared key |

Fields with the magnifying-glass icon accept metadata variables. Use one for the **Local ID** so each branch presents a unique ID even though all branches share the template.

> **Exam tip:** The hub template expects **dial-up** spokes and hands them overlay addresses from the start/end range (mode-cfg). The branch template needs the hub's **remote gateway** and a **Local ID**. If a question gives a branch template without a remote gateway, it can't be the branch template.

## Building a template by hand

Create New in the IPsec Tunnel template list, then add tunnels. Key fields:

| Field | Meaning |
|---|---|
| **Tunnel Name** | The phase 1 interface name created on every assigned device (use the same name everywhere, for example `HUB1-VPN1`) |
| **Routing** | **Automatic**: FortiManager creates **static routes to the remote subnets** you list. **Manual**: no routes are created; you route with BGP, a static route template or a CLI template |
| **Remote Device** | IP Address (static peer), Dynamic DNS (FQDN) or **Dynamic** (dial-up peers) |
| **IPv4 Start IP / End IP / Netmask** | Address range for dial-up peers (Dynamic only) |
| **Outgoing Interface** | Underlay port the tunnel uses |
| **Local ID** | Matches dial-up peers to the right phase 1 when several dial-up tunnels share an interface |
| **Network Overlay** | Network ID, needed when there are several tunnels between the same pair of FortiGate IPs |
| **Remote Subnet** | Only with Automatic routing; becomes the static routes |
| **Proposal**, **Authentication Method** (pre-shared key or signature) | Crypto and authentication |
| **FEC Health Check** | Health check used to adapt forward error correction redundancy to link quality |
| **Tunnel Interface Setup**, **Phase 2 Interface**, **Advanced Options** | Tunnel IPs, phase 2 selectors, and the rest of phase 1 (ADVPN can be enabled in advanced settings of any IPsec template) |

### IPsec template autorouting

"Autorouting" in an IPsec template is the **Routing: Automatic** choice. It suits a small hub-and-spoke with fixed LAN subnets: list the remote subnets once, and every assigned device gets static routes to them over the tunnel. Combine it with a metadata variable for the remote subnet when every spoke advertises a different LAN.

It does **not** scale for SD-WAN: a hub would need a static route per branch LAN, and routes wouldn't follow link failures or ADVPN shortcuts. Large designs use **Routing: Manual** plus a BGP template (BGP per overlay, or BGP on loopback), which is what the overlay template generates.

## A hub-and-spoke example with templates

Branches in device group `Branches`, hub in `HUB`. Two branch WAN links, so two overlays.

```text
IPsec template: HUB1_IPsec            (assigned to FGT-Hub)
Tunnel     Remote Device  Outgoing  Routing  Network Overlay  IPv4 range
HUB1-VPN1  Dynamic        port1     Manual   1                10.10.0.2 - 10.10.63.254
HUB1-VPN2  Dynamic        port2     Manual   2                10.10.64.2 - 10.10.127.254

IPsec template: BRANCH_IPsec          (assigned to device group Branches)
Tunnel     Remote Gateway  Outgoing  Routing  Network Overlay  Local ID
HUB1-VPN1  198.51.100.10   port1     Manual   1                $(branch_id)-VPN1
HUB1-VPN2  198.51.100.11   port2     Manual   2                $(branch_id)-VPN2

Metadata variable branch_id: FGT-Spoke1 = 1, FGT-Spoke2 = 2
```

What each device gets after install:

- **FGT-Hub**: two dial-up phase 1 interfaces that hand overlay addresses to spokes. No static routes, because routing is manual.
- **FGT-Spoke1**: tunnels `HUB1-VPN1` (Local ID `1-VPN1`) and `HUB1-VPN2` (Local ID `1-VPN2`) to the two hub addresses.
- Routing still has to come from a **BGP template** (or static route template). With Manual routing and no BGP template, the tunnels come up but nothing is routed over them.

## Configuring IPsec interfaces as SD-WAN members

The tunnels become useful for SD-WAN when they are members of an **SD-WAN zone** in the SD-WAN template:

1. Use the **same tunnel names** on every branch (the IPsec template guarantees this).
2. In the SD-WAN template, add `HUB1-VPN1` and `HUB1-VPN2` as members of zone `HUB1`, **by name**. Normalized interfaces can't be used for SD-WAN template members.
3. Add a **performance SLA** that probes a hub address through both members. If the tunnels carry no IP address (as in the FortiOS BGP-on-loopback examples), each overlay member needs a **source** (the branch loopback) for its health checks.
4. Write SD-WAN rules that steer corporate traffic across `HUB1-VPN1` and `HUB1-VPN2`.
5. In the policy package, use the zone `HUB1` (not the tunnels) in firewall policies, together with policies that allow the health check probes and BGP.

Normalized interfaces are still useful for the **policy packages**: the overlay wizard's *Normalize Interfaces* option creates normalized interfaces for the hub loopback (`HUB-Lo`), the hub zones (`HUB1`, `HUB2`) and the tunnels (`VPN1`, `VPN2`), mapped per device or platform, so one policy package works on hubs and branches with different underlying names.

> **Watch out:** A hand-written IPsec template plus an SD-WAN template that references `HUB1-VPN1` must agree on the name exactly. If one branch's template group carries an IPsec template with `HUB1_VPN1`, its SD-WAN template install fails on that device because the member doesn't exist.

## Single and dual hub with templates

- **Single hub**: one hub template, one branch template with one tunnel per WAN link.
- **Dual hub**: a second hub template (`HUB2_IPsec`) and branch tunnels `HUB2-VPN1`, `HUB2-VPN2` in zone `HUB2`. The SD-WAN rules then prefer HUB1 or HUB2 by order or cost. Domain 5 covers dual-hub routing.

Doing this by hand is possible but error-prone (tunnel names, network IDs, overlay ranges and BGP neighbor ranges have to line up across four templates). That's exactly what the overlay template wizard automates, which is the subject of the next lesson.

## Lab it yourself

You can build and assign an IPsec template on the FortiManager-VM trial and install it to one FortiGate-VM trial. A working tunnel needs a second FortiGate (a licensed VM, a second FortiCloud account's trial, or hardware); the trial's low-encryption limit also restricts the proposals you can pick, so choose a proposal the trial accepts.

1. Activate **Branch_IPSec_Recommended**, with Local ID `$(branch_id)-VPN1` and a remote gateway from 198.51.100.0/24.
2. Assign it to your FortiGate-VM and check Install Preview for the resolved Local ID.
3. Switch the tunnel to Routing: Automatic with one remote subnet and compare the preview (a static route appears, using one of the trial's 3 routes).

## Key takeaways

- **VPN Manager** builds communities (Full Meshed, Star, Dial up) and needs central VPN management; **IPsec templates** are the SD-WAN path.
- Recommended templates: **HUB_IPSec_Recommended** (dial-up spokes, address range), **Branch_IPSec_Recommended** (remote gateway and Local ID), **IPSec_Fortinet_Recommended** (no role assumption). Activate, then edit or clone.
- **Routing: Automatic** ("autorouting") creates static routes to the listed remote subnets; **Manual** creates none, so pair it with BGP or static route templates.
- **Network Overlay** gives each of several tunnels between the same IPs its own network ID.
- Metadata variables make shared templates unique per device, for example the **Local ID**.
- SD-WAN template members reference tunnels **by name**; policies use the **zone**.
