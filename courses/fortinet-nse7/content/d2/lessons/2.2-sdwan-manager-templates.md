## FortiManager features for SD-WAN

FortiManager is the control point for an SD-WAN estate: it holds the intended configuration, pushes it, and shows whether the result works. The pieces an architect combines:

| Feature | Role in an SD-WAN design |
|---|---|
| **ADOM** | Boundary for devices, templates, policy packages and metadata variables. One ADOM per SD-WAN estate (or per customer for an MSSP) |
| **Device groups** | Targets for templates, template groups, scripts and installs. The overlay template binds to a branch device group |
| **Model devices, blueprints, CSV import** | ZTP of new branches (2.1) |
| **Metadata variables** | Per-device values in shared templates: `$(name)` |
| **Provisioning templates** | IPsec tunnel, BGP, static route, system, CLI (and Jinja), SD-WAN, SD-WAN overlay, IPS, certificate templates |
| **Template groups** | Bundle one template of each type and assign them as one unit |
| **Normalized interfaces** | One name in policy packages that maps to different real interfaces per device or platform |
| **Policy packages** | Firewall policies per role (hub, branch) using SD-WAN zones as interfaces |
| **SD-WAN Monitor** | Health, SLA and template status of the managed SD-WAN devices |

## SD-WAN Manager (FortiManager 7.6)

FortiManager 7.6.0 introduced a separate **SD-WAN Manager** pane that gathers the SD-WAN work in one place. Its tree has four parts:

| Section | Contents |
|---|---|
| **Network** | *Devices*: the devices with SD-WAN management enabled, their assigned templates and firmware. *Monitor*: the SD-WAN charts and the Map, Template and Table views that used to live in Device Manager |
| **Templates** | The SD-WAN-related provisioning templates other than the SD-WAN and overlay templates: template groups, IPsec Tunnel, BGP, Static Route and CLI templates |
| **Overlay Orchestration** | The SD-WAN overlay template wizard (previously in Device Manager > Provisioning Templates) |
| **Rules** | SD-WAN templates: zones and members, performance SLAs, SD-WAN rules, neighbors, duplication |

A device appears in SD-WAN Manager only when **SD-WAN management is enabled** for it: either turn on *Managed by SD-WAN Manager* when you add a model device, or select an existing device in Device Manager and use **More > Enable SD-WAN Management** (**More > Disable SD-WAN Management** takes it out again). The *Managed by SD-WAN Manager* column shows the state. Overlay templates can only use devices with SD-WAN management enabled. In 7.6.0 to 7.6.2, SD-WAN templates are managed only in SD-WAN Manager > Rules and can be applied only to devices with SD-WAN management enabled. From **7.6.3**, SD-WAN templates and overlay templates can be managed in either SD-WAN Manager or Device Manager, SD-WAN templates can be applied to devices with or without SD-WAN management, the two panes share the IPsec, BGP, static route and CLI templates, and the SD-WAN Monitor is visible from both.

> **Exam tip:** On 7.6.0 to 7.6.2, "the new branch is managed and synchronized, but it doesn't appear in SD-WAN Manager and can't be selected for the SD-WAN template" points to SD-WAN management not being enabled for that device.

## SD-WAN core settings: the SD-WAN template

The **SD-WAN template** is where FortiManager holds the SD-WAN "intelligence" (this is the part the overlay wizard does **not** build). Create it in SD-WAN Manager > Rules. Required sections: **SD-WAN zones and interface members**, **performance SLAs** and **SD-WAN rules**. Optional: neighbors (the `config system sdwan` → `config neighbor` table that ties BGP neighbors to SLAs for self-healing), packet duplication, and advanced options.

```text
SD-WAN template: Branch-SDWAN            (SD-WAN Manager > Rules)
Interface members
  Zone      Member       Gateway          Status
  WAN1      port1        $(wan1_gw)       Enabled
  WAN2      port2        $(wan2_gw)       Enabled
  HUB1      HUB1-VPN1    -                Enabled
  HUB1      HUB1-VPN2    -                Enabled
Performance SLA
  HUB1_HC   server 172.16.255.253  members HUB1-VPN1, HUB1-VPN2
  DIA_HC    server 198.51.100.53   members port1, port2
SD-WAN rules
  1 Corp-Apps   dst Corp-Nets    Lowest Cost (SLA)  HUB1_HC   HUB1-VPN1, HUB1-VPN2
  2 SaaS        ISDB Office365   Best Quality       DIA_HC    port1, port2
Assigned to: device group Branches-DIA
```

Points FortiManager adds on top of FortiOS SD-WAN:

- **Members are bound by name.** The docs are explicit that normalized interfaces aren't supported for SD-WAN template members: you type the physical or VPN interface name. That works because every branch uses the same tunnel names (`HUB1-VPN1`, `HUB1-VPN2`) and the same WAN port names, which is one more reason to standardize hardware per blueprint.
- **Interface Member and Gateway IP accept metadata variables**, so one template serves branches with different ISP gateways.
- Firewall policies use **SD-WAN zones**, never individual members.
- **Import** builds a new SD-WAN template from a FortiGate's existing SD-WAN configuration; FortiManager prefixes the name with *Import*. That's the usual starting point when you convert an estate that already runs SD-WAN locally.
- Assign with **Assign to Device/Group**, then install. A template can target devices or whole device groups.

## Metadata variables in SD-WAN designs

Metadata variables are ADOM objects with a **default value** and per-device or per-device-group **mapped values**. Reference them as `$(name)` in templates, scripts, addresses, IP pools, VIPs and normalized interfaces; FortiManager resolves the value per device at install time.

```text
Metadata Variables (ADOM: SDWAN-EU)
Name         Type   Default          Per-Device Mapping
branch_id    Text   0                FGT-Spoke1 = 1
                                     FGT-Spoke2 = 2
wan1_gw      Text   192.0.2.1        FGT-Spoke2 = 203.0.113.1
lan_subnet   Text   10.1.0.0/24      FGT-Spoke1 = 10.1.1.0/24
                                     FGT-Spoke2 = 10.1.2.0/24
```

With this table, FGT-Spoke1 resolves `$(wan1_gw)` to **192.0.2.1** (the default, because it has no mapping) and FGT-Spoke2 to 203.0.113.1. A missing mapping never raises an error: the device silently gets the default. **Install Preview** shows the CLI FortiManager is about to send with the variables already resolved, which is the quickest proof that the mapping is right.

Where values come from:

- **Edit Variable Mapping** on a device or device group in Device Manager.
- The **CSV import** of model devices (one column per variable).
- **Automatic Branch ID Assignment** in the overlay template wizard, for `branch_id` only.

CLI templates come in two flavours. Plain CLI templates substitute `$(var)`. **Jinja** CLI templates use `{{ var }}` with filters and logic (`{% if %}`, `{% for %}`). Variables arrive as strings, so cast them with filters when you need a number (Fortinet's own example loops over `range(0, vm_interface_number|int)`). The overlay template's generated CLI templates are where much of the per-hub and per-branch logic lives.

> **Watch out:** FortiManager 7.6 **meta fields** (System Settings > Advanced > Meta Fields) are descriptive attributes, not template variables. If a question says a template uses a meta field to set a per-branch value, that's the wrong tool.

## Templates and template groups

A **template group** holds **one template of each type** (one IPsec, one BGP, one SD-WAN, one static route, one CLI and so on) and is assigned to devices or device groups in one action. FortiManager orders the install by dependency: for example, the IPsec template that creates the tunnel interfaces is applied before a template that addresses those interfaces. The Table View column *Provisioning Templates* shows which group a device has.

The overlay template wizard creates template groups for you: **BRANCH** and **HUB1** (plus HUB2, HUB3, HUB4 for dual and multi hub), each with its IPsec, BGP and CLI template. Because a group allows only one template per type, put extra branch CLI in a **CLI template group** rather than trying to add a second CLI template to the group.

## The install path and verification

Templates change the **device database** first. The device shows as *Modified*, and nothing reaches the FortiGate until an install. Use the **Install Wizard** (Install Policy Package & Device Settings, or Install Device Settings only), check **Install Preview** for the generated CLI, then install. After installing:

- Device Manager: config status *Synchronized*, policy package *Installed*.
- SD-WAN Manager > Network > Monitor: **Map View** (sites coloured by health), **Template View** (only the devices provisioned by the template selected in its toolbar; device colour from health checks on spokes and underlay status on hubs, link colour green for tunnel up, red for down) and **Table View**.

## Planning an SD-WAN deployment with FortiManager

Key deployment elements, in the order you decide them:

1. **ADOM and FortiManager placement.** A greenfield rollout can use a **dedicated FortiManager** (or a dedicated ADOM) built around the overlay template, ZTP and SD-WAN templates from the start. A brownfield estate already managed elsewhere usually has to be converted.
2. **Addressing plan**: overlay range (default 10.10.0.0/16), loopback range (default 172.16.0.0/16), BGP AS (default 65000), LAN summaries per region.
3. **Hardware and port standards** per blueprint, so member names match the SD-WAN template.
4. **Device groups** per branch type (for example by number or type of WAN links), because the overlay template assigns per group.
5. **Metadata variables** for everything that differs per branch.
6. **Templates**: overlay template for IPsec and BGP, SD-WAN template for rules and SLAs, policy packages per role.
7. **ZTP method** per site type, then install and monitor.

### Converting an existing topology

When branches already run IPsec and maybe SD-WAN configured locally:

- Add the devices and **import** their policies into policy packages, so FortiManager's database matches what runs.
- Use **Import** in SD-WAN Manager > Rules to turn a representative FortiGate's SD-WAN configuration into a template, then generalize it with metadata variables.
- Decide whether to keep the existing tunnels or **rebuild the overlays** with the overlay template. Rebuilding gives the standard names, BGP on loopback and ADVPN options, but it changes tunnel names, zones and routing, so plan it as a migration with a maintenance window per site.
- SD-WAN members can't be referenced directly in firewall policies (the FortiManager docs even tell you to delete a factory default policy that references a port before installing an SD-WAN template that uses it), so moving an existing tunnel into a zone means re-pointing those policies to the zone first. Review static routes that name the interface at the same time.

## Lab it yourself

On the FortiManager-VM trial with one FortiGate-VM trial:

1. Enable SD-WAN management for the FortiGate-VM and confirm it appears in SD-WAN Manager > Network > Devices.
2. Use **Import** in SD-WAN Manager > Rules to create an SD-WAN template from the FortiGate (configure a small SD-WAN on it first: two members fit the 3-interface limit if port1 is management).
3. Replace the gateway with `$(wan1_gw)`, map a per-device value, and check Install Preview.
4. Group the SD-WAN template with a CLI template in a template group and assign it.

A hub-and-spoke overlay needs a second FortiGate, which needs its own licence or another FortiCloud account's trial, so treat the overlay parts as read-only here.

## Key takeaways

- FortiManager 7.6 **SD-WAN Manager** has Network (Devices, Monitor), Templates, Overlay Orchestration and Rules; a device must have **SD-WAN management enabled** to appear there.
- The **SD-WAN template** holds zones, members, performance SLAs, rules and neighbors. Members are bound **by name**; normalized interfaces aren't supported there, but member and gateway fields accept metadata variables.
- **Import** creates an SD-WAN template from a device's configuration (name prefixed *Import*).
- Metadata variables resolve per device at install; an unmapped device gets the **default**. Install Preview shows resolved values.
- A **template group** takes one template per type; the overlay template creates BRANCH and HUBn groups.
- From **7.6.3**, SD-WAN templates, overlay templates and the SD-WAN Monitor are available in both SD-WAN Manager and Device Manager, and SD-WAN templates no longer require SD-WAN management on the device.
