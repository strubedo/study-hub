## Why ZTP matters to an SD-WAN architect

A large SD-WAN rollout fails or succeeds at the branch door. If every one of 400 branches needs an engineer on site to type a configuration, the project is slow, expensive and full of typos. **Zero-touch provisioning (ZTP)** moves all of the per-site work to FortiManager before the box ships. At the site, someone connects the WAN cable and powers the unit on. The FortiGate finds FortiManager, FortiManager recognizes it, and FortiManager pushes a complete configuration: interfaces, IPsec overlays, BGP, SD-WAN and the policy package.

Every Fortinet ZTP method rests on two FortiManager objects:

- a **model device**: a placeholder in the device database for a FortiGate that hasn't connected yet. You attach templates, a policy package and metadata variable values to it in advance.
- **auto-link**: what happens when the real unit connects and matches a model device.

## The auto-link sequence

All methods end the same way. Learn the order, because exam items like to scramble it.

1. The real FortiGate opens its management tunnel (FGFM, TCP 541) to FortiManager and authenticates with its **serial number** or a **pre-shared key**.
2. FortiManager matches the unit to an existing **model device**.
3. Optionally, FortiManager upgrades or downgrades the firmware to the version enforced on the model or blueprint.
4. The model device becomes a real managed device, and FortiManager pushes the full configuration (device settings, provisioning templates, policy package) through the tunnel.

> **Exam tip:** The model device has to exist **before** the FortiGate calls in. A FortiGate that connects with no matching model device just sits in the unauthorized device list in the root ADOM and gets nothing pushed.

## ZTP versus LTP

| | Zero-touch (ZTP) | Low-touch (LTP) |
|---|---|---|
| Site work | Plug in and power on. (The USB method also needs a USB stick inserted.) | Someone connects to the FortiGate and tells it where FortiManager is |
| Starting state | Factory default | Factory default, then a few lines of CLI |
| Authenticates with | Serial number | Serial number or a **pre-shared key** |
| Best when | Serial numbers are known before shipping, and the branch WAN gives DHCP | Units are picked from stock on site, serial unknown in advance, static WAN addressing |

Pre-shared key linking needs someone to run `execute central-mgmt register-device` on the FortiGate, so in practice it is a low-touch method. That matters when the warehouse ships "any FortiGate 70G" and nobody records which serial number went where.

## The three ZTP discovery methods

How does a factory-default FortiGate learn where FortiManager is? Fortinet documents three ways.

| Method | How the FortiGate learns the FortiManager address | Needs |
|---|---|---|
| **FortiCloud / FortiDeploy** | Gets internet access by DHCP, contacts FortiCloud, authenticates by serial number, and receives the FortiManager location from its FortiCloud registration | Internet access via DHCP (address and default gateway) on the ISP link; unit registered in FortiCloud and assigned to your FortiManager |
| **DHCP option 240 / 241** | The local DHCP server hands out the FortiManager address with the lease. No FortiCloud needed | A DHCP server you control (corporate sites, MPLS, closed networks) |
| **USB boot** | A USB stick with a minimal initial configuration (and optionally the target firmware) is inserted before the first boot | Shipping a stick to each site |

### DHCP options 240 and 241

- **Option 240** carries the FortiManager **IP address** (IP format).
- **Option 241** carries the FortiManager **FQDN** (string format; it travels hex-encoded in the DHCP packet).

On a FortiGate acting as the DHCP server for a staging network:

```text
FGT-Hub # config system dhcp server
FGT-Hub (server) # edit 5
FGT-Hub (5) # set interface "port3"
FGT-Hub (5) # set default-gateway 192.0.2.1
FGT-Hub (5) # set netmask 255.255.255.0
FGT-Hub (5) # config ip-range
FGT-Hub (ip-range) # edit 1
FGT-Hub (1) # set start-ip 192.0.2.100
FGT-Hub (1) # set end-ip 192.0.2.199
FGT-Hub (1) # next
FGT-Hub (ip-range) # end
FGT-Hub (5) # config options
FGT-Hub (options) # edit 1
FGT-Hub (1) # set code 240
FGT-Hub (1) # set type ip
FGT-Hub (1) # set ip "198.51.100.20"
FGT-Hub (1) # next
FGT-Hub (options) # end
FGT-Hub (5) # end
```

Rules that trip people up:

- It works **only on a factory-default FortiGate**. Change any setting first (a static IP on the WAN port, for example) and the unit no longer accepts option 240/241.
- Once a FortiGate has accepted a FortiManager address from DHCP, it marks its configuration as touched and **refuses different values from later DHCP offers** until you run `execute factoryreset`. This stops a rogue DHCP server redirecting a managed unit.
- Send **one** option, not both. The FortiGate creates a central management entry for each option it receives.
- Windows DHCP servers don't include codes 240/241 by default. Define them as predefined options first. Some third-party servers only send them if the client asks for them in option 55.
- The method depends on a port that is a DHCP client out of the box. Most models have a port labelled WAN that is; on models without one, the right port isn't a DHCP client by default, so DHCP-based ZTP can't start without touching the box.

Check what the FortiGate received:

```text
FGT-Spoke1 # diagnose fdsm fmg-auto-discovery-status
dhcp: fmg-ip=198.51.100.20, fmg-domain-name='', config-touched=1(/bin/dhcpcd)
```

`config-touched=0` with `fmg-ip=0.0.0.0` means no lease with the options has arrived yet. `config-touched=1` with `fmg-ip=0.0.0.0` means the unit was already touched, so it ignored the option. Factory-reset it.

### USB boot

The USB method suits sites where FortiCloud can't be reached and the local DHCP can't be changed. Keep the file on the stick to the **minimum** needed to reach FortiManager. Anything else is overwritten by the model device configuration when auto-link finishes. A local firmware image on the stick can be faster than a firmware download over a thin branch link.

## LTP: the operator tells the FortiGate

With low-touch, a local person (or a remote hand on a console cable) gives the FortiGate a WAN address if needed and points it at FortiManager:

```text
FGT-Spoke2 # config system central-management
FGT-Spoke2 (central-management) # set type fortimanager
FGT-Spoke2 (central-management) # set fmg "198.51.100.20"
FGT-Spoke2 (central-management) # end
```

To link by **pre-shared key** instead of serial number, the model device on FortiManager is created with *Link Device By: Pre-Shared Key*, and the operator runs:

```text
FGT-Spoke2 # execute central-mgmt register-device FMG-VMTM26000001 Br-0417-Key
```

The first argument is the **FortiManager serial number**, the second the key. Give every model device its own key.

## Model devices in short

Create them in **Device Manager > Device & Groups > Add Device > Add Model Device**, one at a time, or in bulk from a CSV file (next lesson). The fields that matter for ZTP:

| Field | Why it matters |
|---|---|
| Link Device By | Serial Number (ZTP) or Pre-Shared Key (LTP) |
| Automatically Link to Real Device | Without it, the real unit still needs an administrator to authorize it |
| Enforce Firmware Version | Upgrade or downgrade on link so the unit matches the ADOM version |
| Enforce Device Configuration | Pushes the model's management settings as-is. A wrong management interface here can cut the unit off from FortiManager |
| Device Blueprint | Pulls group, folder, templates, policy package and firmware settings from a reusable recipe |
| Managed by SD-WAN Manager (7.6) | Adds the device to SD-WAN Manager. SD-WAN overlay templates need it; in 7.6.0 to 7.6.2 SD-WAN templates need it too |

> **Watch out:** ZTP **overwrites** the real unit's configuration with the model's. That is what you want for a factory-default box, and a disaster if a technician "helpfully" pre-configured something important.

> **Real world:** The ZTP choice is usually forced by the WAN. Internet broadband with DHCP: FortiCloud/FortiDeploy is the cleanest. Private MPLS with no internet breakout: DHCP option 240 on the carrier CE or a local server. Static public IP from the ISP: no DHCP at all, so plan LTP or USB.

## Design checklist before the first box ships

- FortiManager must be **reachable from the branch WAN**: a public address or FQDN, TCP 541 open end to end, and the address the FortiGate learns must be the NATed public one if FortiManager sits behind NAT.
- The **ADOM version** must match the firmware you enforce.
- The model device must already carry what the branch needs on day one: templates (directly, through a template group or a blueprint), metadata variable values (`branch_id` for overlay templates), and a policy package.
- The underlay must come up on its own. ZTP over FortiCloud assumes the ISP link gives an address and default gateway by DHCP.

## Lab it yourself

What fits the trials: one FortiGate-VM permanent trial and the FortiManager-VM trial (3 devices/VDOMs, 2 ADOMs).

1. Back up the FortiGate-VM configuration, then factory-reset it. Use the LTP path: the documented ZTP methods target hardware units.
2. On FMG-HQ, run `config system global` / `set fgfm-allow-vm enable`, then create a model device with Link Device By: Serial Number and the VM's serial, auto-link on.
3. On the FortiGate, configure `config system central-management` with `type fortimanager` and the FortiManager IP. Watch it auto-link and receive the model's settings.
4. Repeat with *Link Device By: Pre-Shared Key* and `execute central-mgmt register-device`.
5. To see option 240 work you need a factory-default **hardware** FortiGate with a WAN port that is a DHCP client by default. FortiCloud/FortiDeploy ZTP needs a registered hardware unit and FortiCloud access, which the trials don't give.

## Key takeaways

- Every Fortinet ZTP or LTP method ends in **auto-link**: authenticate (serial or PSK), match a model device, optional firmware enforcement, push the full configuration.
- ZTP methods: **FortiCloud/FortiDeploy**, **DHCP option 240 (IP) / 241 (FQDN)**, **USB boot**. LTP needs local CLI; PSK linking (`execute central-mgmt register-device`) is therefore a low-touch method.
- DHCP option 240/241 works only on a **factory-default** unit; after the first accepted value (`config-touched=1`) it ignores new values until a factory reset.
- `diagnose fdsm fmg-auto-discovery-status` shows what the FortiGate learned from DHCP.
- `execute central-mgmt register-device <FortiManager serial> <key>` links a unit by pre-shared key.
- Model devices must exist before the unit calls home, and ZTP overwrites the unit's configuration.
