## From one model device to five hundred

Creating model devices one by one works for a pilot. For a rollout it doesn't: every manual model device is a chance to pick the wrong template group, forget the policy package or mistype a variable. FortiManager solves this with two features that work together:

- a **device blueprint**: a reusable recipe of everything a class of branch has in common.
- **Import Model Devices from CSV File**: one row per branch, holding only what differs (serial number, name, variable values).

## Device blueprints

Path: **Device Manager > Device & Groups > Add Device > Device Blueprint**, then Create New.

| Blueprint field | What it sets on each model device |
|---|---|
| **Name**, **Device Model** | The blueprint is tied to one platform. A CSV row must use a blueprint that matches the unit's model |
| **Automatically Link to Real Device** | Auto-link and authorize when the real unit connects (true zero-touch) |
| **Enforce Firmware Version** | Target firmware; with **Let Device Download Image from FortiGuard** the unit fetches the image from FortiGuard after auto-link instead of from FortiManager |
| **Enforce Device Configuration** | Push the device configuration during ZTP/LTP. A wrong management interface setting can make the unit unreachable |
| **Add to Device Group** | One or more device groups. For SD-WAN overlays this is the important one (see below) |
| **Add to Folder** | Display only. A folder isn't a template target |
| **Fabric Authorization Template** | Authorize downstream Fabric devices (FortiSwitch, FortiAP, FortiExtender) |
| **Pre-Run CLI Template** | A CLI template that runs **once** on the model device, **before** the provisioning templates |
| **Assign Policy Package** | The policy package to assign automatically |
| **Provisioning Template** | System, IPsec, SD-WAN, static route, BGP, CLI or IPS templates, or a **template group** |
| **HA** | Pre-provision an HA cluster: monitor interfaces, heartbeat interfaces and priorities, cluster password |

Two behaviours to remember:

1. **Edits to a blueprint only affect devices added after the edit.** Model devices already created from it keep what they got. If you fix a blueprint mid-rollout, fix the devices you already created separately.
2. **Pre-run CLI templates are for model devices only.** They run once, before the provisioning templates, against the model device's database in FortiManager (not on the FortiGate itself), and FortiManager unassigns them from the device after they've been applied. Use them for day-zero settings the other templates depend on, such as an interface mode or a VLAN that a template later references.

> **Exam tip:** Blueprint changes are not retroactive. A question that says "the administrator corrected the blueprint, but branches already imported still have the old policy package" is testing exactly that.

### Why the device group matters for SD-WAN

The SD-WAN overlay template (lesson 2.2) is assigned to a **branch device group**, not to individual devices. When a device joins that group, FortiManager automatically assigns the branch provisioning templates (the branch template group) to it. So the cleanest onboarding chain is:

```text
Device blueprint "BR-70G"
  Add to Device Group ......... Branches-DIA        <- the overlay template's branch group
  Assign Policy Package ....... Branch-PP
  Enforce Firmware Version .... 7.6.x (ADOM 7.6)
  Automatically Link .......... enabled
        |
        v
CSV row: serial, BR-70G, FGT-Spoke3, branch_id=3
        |
        v
Model device FGT-Spoke3 -> member of Branches-DIA -> BRANCH template group auto-assigned
```

## Importing model devices from a CSV file

Path: **Device Manager > Device & Groups > Add Device > Import Model Devices from CSV File**. Upload the file, check the table FortiManager shows (serial numbers, names, blueprints and metadata values), optionally choose a device to copy dashboards from, then Next and Finish. You can export a sample CSV from the Device Blueprint table to get the headers right.

| Column | Required? | Example |
|---|---|---|
| `Serial Number` (or `sn`) | Required | `FGT70GTK25000123` |
| `Device Blueprint` | Required; must match the platform | `BR-70G` |
| `Name` | Required; unique | `FGT-Spoke3` |
| `Cluster Id`, `Cluster Name`, `Priority`, `HA Mode` (`AP` or `AA`) | Required only for HA rows; the blueprint must also have HA enabled | `100`, `SPOKE3-HA`, `200`, `AP` |
| One column per metadata variable | Optional; the header is the variable name | header `branch_id`, value `3` |

A CSV for three branches with the overlay template's `branch_id` and a site-specific LAN variable:

```text
Serial Number,Device Blueprint,Name,branch_id,lan_subnet
FGT70GTK25000123,BR-70G,FGT-Spoke1,1,10.1.1.0/24
FGT70GTK25000456,BR-70G,FGT-Spoke2,2,10.1.2.0/24
FGT70GTK25000789,BR-70G,FGT-Spoke3,3,10.1.3.0/24
```

The metadata columns write **per-device mapping values** for the ADOM-level metadata variables. The variables themselves must already exist in the ADOM (Policy & Objects > Advanced > Metadata Variables). Any device without a value in the file gets the variable's **default value**, which is why an empty `branch_id` cell is dangerous: two branches with the same `branch_id` collide, unless the overlay template uses Automatic Branch ID Assignment.

> **Watch out:** Each row needs the blueprint that matches **that unit's** hardware. Mixing FortiGate 40F and 70G branches in one CSV is fine, but they need two blueprints, and each row must name the right one.

## Putting ZTP together: day-zero to day-one

1. **Design** the ADOM, device groups and metadata variables (`branch_id`, LAN subnet, local ID).
2. **Build** templates (or let the overlay template wizard build them), template groups, and the policy package.
3. **Create a blueprint** per hardware model with group, policy package, firmware and auto-link.
4. **Import the CSV** of serial numbers, names and per-site variable values.
5. **Ship** the factory-default FortiGates.
6. **Units call home** (FortiCloud/FortiDeploy, DHCP 240/241, USB or LTP), **auto-link**, upgrade to the enforced firmware, and receive the configuration.
7. **Verify** in Device Manager (config status and policy package status) and in SD-WAN Manager's monitor.

> **Real world:** Test the whole chain with one unit in a staging rack before the mass import. A wrong default value or a template that references an interface the 40F doesn't have turns into hundreds of failed installs.

## ZTP and HA branches

An HA pair is pre-provisioned as a model HA cluster: the blueprint has HA enabled (heartbeat and monitor interfaces, password) and each CSV row carries the cluster ID, name, the unit's priority and the HA mode. When the pair comes up, the unit with the higher priority becomes the primary. FortiManager manages the cluster as one device, talks to the primary, and FGCP synchronizes the configuration to the secondary.

## Lab it yourself

The FortiManager-VM trial manages 3 devices/VDOMs, which is enough to see blueprints and CSV import work. The FortiManager license count rules don't say whether a model device counts, so plan as if each one takes a slot.

1. Enable `fgfm-allow-vm` and create metadata variables `branch_id` and `lan_subnet` with defaults.
2. Create a device group `Branches` and a blueprint for the FortiGate-VM platform that adds devices to it and assigns a policy package.
3. Write a two-row CSV, one row with the real serial of your FortiGate-VM trial and one invented, and import it.
4. Check **Edit Variable Mapping** on each model device to see the per-device values.
5. Point the real FortiGate-VM at FortiManager (LTP) and watch it auto-link to its row. Delete the invented model device afterwards to free the slot.
6. An HA row needs two licensed FortiGate-VMs (one trial per FortiCloud account), so read rather than lab that part.

## Key takeaways

- A **device blueprint** holds what branches of one platform share: auto-link, firmware enforcement, device groups, folder, Fabric authorization template, pre-run CLI template, policy package, provisioning templates or a template group, and HA settings.
- Blueprint edits **apply only to devices added later**.
- **Pre-run CLI templates** run once on model devices, before the provisioning templates, and are then unassigned.
- The CSV import needs **Serial Number, Device Blueprint and Name**; HA rows add Cluster Id, Cluster Name, Priority and HA Mode; extra columns named after metadata variables set per-device values.
- Adding a device to the overlay template's **branch device group** automatically assigns the branch provisioning templates.
- A device without a mapped value receives the variable's **default**, so blank `branch_id` cells cause duplicates unless automatic branch IDs are used.
