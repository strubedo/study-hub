## IPS as a design decision

An IPS sensor with every signature enabled on every policy is the easiest configuration to write and the worst to run. It costs CPU on traffic that can't be attacked by most of those signatures, and it creates false positives that teach operators to ignore IPS logs. Design sensors per **target**: what you're protecting, which operating systems and applications it runs, and which direction attacks come from.

## Anatomy of an IPS sensor

**Security Profiles > Intrusion Prevention**. A sensor has:

| Part | Purpose |
|---|---|
| **IPS signatures and filters** (entries) | A **filter** is a set of attributes; every signature matching **all** of them is included automatically, including signatures FortiGuard adds later. A **signature** entry names individual signatures |
| Filter attributes | **Target** (server or client), **Severity**, **Protocol**, **OS**, **Application**; in the CLI also **CVE** patterns, default action, default status, vulnerability type, last-modified date |
| **Action** | Allow, Monitor, Block, Reset, Default (the signature's own default action), Quarantine (block, packet log and quarantine the attacker) |
| **Status** | Enable, Disable or Default |
| **Packet logging** | Saves the matching packets (needs FortiAnalyzer or a disk) |
| **Rate-based settings** | Threshold, duration and track-by (any, source IP, destination IP) on a signature entry |
| **Exempt IPs** | Source/destination pairs for which a signature entry doesn't apply (the GUI offers them on entries of type Signature, not on filters) |
| **Block malicious URLs** | Local malicious URL database against drive-by downloads |
| **Botnet C&C** | Scan outgoing connections to botnet sites: Disable, Block or Monitor |

Predefined sensors: `default`, `all_default`, `all_default_pass`, `high_security`, `protect_client`, `protect_email_server`, `protect_http_server` and `wifi-default` (used for offloading WiFi traffic). Clone them rather than editing in place.

## Protecting server targets versus client targets

Signatures carry a **location** (target) attribute:

| | Server-side signatures | Client-side signatures |
|---|---|---|
| Attack direction | Inbound requests that exploit a service (web server, mail server, VPN portal) | Responses or files that exploit the client (browser, PDF reader, Office) |
| Typical policy | Internet to DMZ/VIP | LAN to internet |
| Filter | Target **server**, OS and application of the server, protocols it serves | Target **client**, OS and applications of the desktops |
| Decryption needed for HTTPS | **Protecting SSL Server** profile with the server's certificate | Full (deep) inspection |

A web server running Linux and nginx doesn't need signatures for Windows SMB or for client-side browser bugs. A tight server sensor:

```text
FGT-Hub # config ips sensor
FGT-Hub (sensor) # edit "DMZ-Web-Srv"
FGT-Hub (DMZ-Web-Srv) # config entries
FGT-Hub (entries) # edit 1
FGT-Hub (1) # set location server
FGT-Hub (1) # set os Linux
FGT-Hub (1) # set protocol HTTP
FGT-Hub (1) # set severity medium high critical
FGT-Hub (1) # set action block
FGT-Hub (1) # set status enable
FGT-Hub (1) # next
FGT-Hub (entries) # end
FGT-Hub (DMZ-Web-Srv) # end
```

Fewer signatures means less work per packet for the IPS engine and fewer chances to match benign traffic: **better performance and fewer false positives**, at the cost of missing an attack on a component you forgot to list. Re-check the sensor whenever the server stack changes.

## IPS sensors built from CVE patterns

When a vulnerability bulletin lands, the question is "are we protected against CVE-2024-XXXX?", not "which signature ID is it?". FortiOS lets a sensor entry select signatures **by CVE ID** or by a **CVE wildcard** (a whole year):

```text
FGT-Hub # config ips sensor
FGT-Hub (sensor) # edit "Emergency-CVE"
FGT-Hub (Emergency-CVE) # config entries
FGT-Hub (entries) # edit 1
FGT-Hub (1) # set cve "cve-2021-44228"
FGT-Hub (1) # set status enable
FGT-Hub (1) # set log-packet enable
FGT-Hub (1) # set action block
FGT-Hub (1) # next
FGT-Hub (entries) # edit 2
FGT-Hub (2) # set cve "cve-2017"
FGT-Hub (2) # set action reset
FGT-Hub (2) # next
FGT-Hub (entries) # end
FGT-Hub (Emergency-CVE) # end
```

Entry 1 picks every signature tagged with that one CVE; entry 2 picks every signature tagged with any 2017 CVE. Because it's a filter, signatures FortiGuard adds later for the same CVE are included automatically after the next IPS update. That's the main advantage over listing signature IDs by hand.

> **Exam tip:** A CVE entry is still an entry: it needs an **action** and an **enabled status** that make sense. Many signatures ship with a default action of *pass* or a default status of *disabled*, so an entry left on Default may only monitor, or not match at all.

## Code injection over HTTP and HTTPS

SQL injection, cross-site scripting and command injection are application-layer attacks inside HTTP requests (and, for some XSS cases, responses). IPS has signatures for many of them, typically server-side web application signatures.

- **HTTP**: the IPS engine sees the request; a server-target sensor with the web application signatures catches it.
- **HTTPS inbound to your server**: invisible without decryption. Use an SSL/SSH profile with **Protecting SSL Server** (`server-cert-mode replace`) on the VIP policy, plus the server sensor.
- **HTTPS outbound** (clients receiving malicious scripts): needs **full inspection**; certificate inspection doesn't expose the payload.

## False positives

An IPS false positive is legitimate traffic that matches a signature. Work it like this:

1. **Read the log.** The IPS log gives the attack name and ID, the source and destination, the action, and the sensor/policy.

```text
date=2026-10-27 time=10:42:18 logid="0419016384" type="utm" subtype="ips"
eventtype="signature" level="alert" vd="root" severity="high"
srcip=10.1.2.25 dstip=10.20.0.40 srcintf="HUB1" dstintf="port3" policyid=12
sessionid=4417203 action="dropped" proto=6 service="HTTPS"
attack="Example.App.Admin.Command.Injection" attackid=51234
profile="DC-Servers" msg="web_app3: Example.App.Admin.Command.Injection,"
```

2. **Confirm** it's benign: a known application behaviour, a vulnerability scanner, a monitoring system.
3. **Narrow the exception**, from best to worst:
   - Add a **signature entry** for that one signature, ordered above the filter that also includes it, keep its action, and add **Exempt IPs** (source and destination) so only that pair is excused.
   - If the pair can't be pinned down, give that signature entry action *Monitor* (or *Allow*) in the affected policy's sensor.
   - Use a **separate sensor** on a separate policy for that traffic.
   - Disabling a whole filter or the sensor is the last resort.
4. **Report** genuine false positives to FortiGuard so the signature gets fixed.

> **Watch out:** Exempting by switching the whole policy to `all_default_pass` or removing the sensor "to make it work" is a design failure. The exam wants the narrowest change that stops the false positive.

## IPS engine settings that affect the design

`config ips global` (FortiOS 7.6 CLI Reference):

| Setting | Default | Effect |
|---|---|---|
| `fail-open` | disable | When the IPS buffer is full, traffic is **blocked** unless fail-open is enabled (then it passes uninspected). The same setting decides whether new flow-inspected sessions are dropped (disable) or passed unscanned (enable) in conserve mode |
| `database` | extended (may differ by model) | `extended` adds protection against legacy attacks; `regular` keeps the latest common and in-the-wild attacks |
| `engine-count` | 0 | 0 lets FortiOS choose the number of IPS engines from the CPU core count (recommended) |
| `np-accel-mode` | basic | NTurbo: offload sessions with flow-based profiles to NP6/NP7 processors; `none` disables it. The option exists only on models that support NTurbo |
| `cp-accel-mode` | advanced or basic, by model | IPSA: flow-based pattern matching on the content processor. `advanced` needs two or more CP8s or one or more CP9s/CP10s and is the default there; with one CP8 the default is `basic`. The option exists only on models that support IPSA |

`fail-open` is a security-versus-availability decision. A branch with one internet link and remote users may prefer to stay up; a PCI segment must fail closed.

## Lab it yourself

The FortiGate-VM trial has no FortiGuard, so only the IPS signatures bundled with the firmware are available, and there are no updates. It's still enough to:

1. Build a server sensor with `location server`, an OS and protocol filter, and see the signature count in the GUI drop compared with `all_default`.
2. Add a CVE entry (`set cve "cve-2021-44228"`) and check which signatures it pulls in.
3. Run a scanner (nikto, nmap scripts) from a Linux host on one side through a single policy to a test web server on the other, then add a signature entry with exempt IPs for the scanner and confirm the logs change.

Three interfaces and three policies are enough for a client, a server and management.

## Key takeaways

- IPS filters include every signature matching **all** attributes (target, severity, protocol, OS, application, CVE), including future ones.
- Use **server-target** sensors for inbound policies and **client-target** sensors for outbound ones; tighter sensors mean better performance and fewer false positives.
- `set cve "cve-YYYY-NNNNN"` or a year wildcard such as `"cve-2017"` builds an emergency sensor by CVE.
- HTTPS code-injection attacks need decryption: **Protecting SSL Server** inbound, full inspection outbound.
- Fix false positives narrowly: exempt IPs or a per-signature entry, not disabling the sensor.
- `config ips global`: `fail-open` disable (block when the buffer is full, and drop new flow-inspected sessions in conserve mode), `database` extended, `engine-count` 0, `np-accel-mode` basic on NTurbo-capable models.
