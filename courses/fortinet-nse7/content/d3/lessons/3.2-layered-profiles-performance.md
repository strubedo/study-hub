## Four controls, four layers

Web filtering, application control, IPS and the Internet Service Database (ISDB) overlap, but they decide at different points in a session and see different things. A good design uses each where it is strongest and cheapest.

| Control | Decides on | Earliest decision | Sees inside HTTPS without decryption? | Typical job |
|---|---|---|---|---|
| **ISDB** (internet service objects in policies and SD-WAN rules) | Destination (or source) IP, protocol and port, from FortiGuard's database of services | **First packet**, at policy match | Not needed: it never looks at payload | Match SaaS and cloud services in policies and SD-WAN rules; allow inbound only from a provider's ranges |
| **Application control** | L7 application signatures | After a few packets, once the application is identified | Handshake only; many signatures need deep inspection | Allow, block or steer applications regardless of port |
| **Web filter** | URL and FortiGuard category | When the HTTP request (or TLS SNI/certificate) is seen | Host and category from SNI/certificate; full URL needs deep inspection | Category policy, URL allow/block lists, safe search |
| **IPS** | Exploit signatures, anomalies, botnet C&C | Throughout the session | Not for payload attacks | Stop exploits against servers and clients |

### Why ISDB first

ISDB objects are matched when the policy is looked up, before any L7 inspection. So they're the cheapest way to split traffic into "trusted, high-volume, known destination" and "everything else":

```text
FGT-Spoke1 # config firewall policy
FGT-Spoke1 (policy) # edit 20
FGT-Spoke1 (20) # set name "O365-Direct"
FGT-Spoke1 (20) # set srcintf "port5"
FGT-Spoke1 (20) # set dstintf "WAN1" "WAN2"
FGT-Spoke1 (20) # set srcaddr "Branch-LAN"
FGT-Spoke1 (20) # set internet-service enable
FGT-Spoke1 (20) # set internet-service-name "Microsoft-Office365"
FGT-Spoke1 (20) # set action accept
FGT-Spoke1 (20) # set schedule "always"
FGT-Spoke1 (20) # set utm-status enable
FGT-Spoke1 (20) # set ssl-ssh-profile "certificate-inspection"
FGT-Spoke1 (20) # set ips-sensor "protect_client"
FGT-Spoke1 (20) # set nat enable
FGT-Spoke1 (20) # next
FGT-Spoke1 (policy) # end
```

Office 365 traffic is matched by ISDB, kept out of deep inspection (Microsoft recommends against TLS interception of its core endpoints, and the traffic is high volume), and still gets client-side IPS on what is visible. A policy below it handles general browsing with deep inspection, web filter and application control.

Other ISDB facts:

- Types: **predefined** (FortiGuard), **custom**, and **extension** (add your own IPs or ports to a predefined service).
- ISDB can be a **destination** and also a **source** (`set internet-service-src enable` with `internet-service-src-name`), which is useful to allow inbound webhooks only from a SaaS provider's address ranges.
- The same objects drive **SD-WAN rules** (internet services as destination), so the policy and the steering decision agree.
- Check an object with `diagnose internet-service id-summary <id>`, and find which services own an IP with `diagnose internet-service match <vdom> <ip> <netmask>`.

> **Exam tip:** ISDB answers "where is this going?" at L3/L4. Application control answers "what is this?" at L7. When the stem says the decision must be made **on the first packet** (policy match or SD-WAN steering before the application is identified), the answer is ISDB.

### Application control

```text
FGT-Spoke1 # config application list
FGT-Spoke1 (list) # edit "Branch-Apps"
FGT-Spoke1 (Branch-Apps) # set other-application-action pass
FGT-Spoke1 (Branch-Apps) # set unknown-application-action pass
FGT-Spoke1 (Branch-Apps) # set unknown-application-log enable
FGT-Spoke1 (Branch-Apps) # end
```

Design points:

- **Category actions** (`config entries` → `set category <id>` / `set action block`; list the IDs with `set category ?`) cover most needs; **application overrides** and **filter overrides** (by risk, popularity, technology, vendor) handle exceptions.
- **Unknown applications** (traffic no signature identifies) is a separate action: block it in a locked-down segment, monitor it elsewhere.
- Many cloud application signatures (individual features of a SaaS app, for example uploads) only match with **deep inspection**, because the identifying data is inside TLS.
- A false positive is a legitimate application identified as a blocked one: add an application override for the real application, and report the misidentification.

### Web filter

- **FortiGuard category** filtering (allow, monitor, block, warning, authenticate), **static URL filter** (exempt, block, allow, monitor), and **rating overrides** for sites FortiGuard rates in a way you disagree with.
- With **certificate inspection**, the web filter rates HTTPS by host (SNI, or the certificate CN if the SNI check finds a mismatch). It can't see paths: `example.com/finance` and `example.com/games` are one site. Blocking by path needs **deep inspection**.
- A web filter false positive (a legitimate site blocked by category) is fixed with a local **rating override** or a static URL filter exempt, then a rerating request to FortiGuard. Don't drop the whole category.
- Over HTTPS, the block page is FortiGate content signed by the FortiGate CA (see 3.1): untrusted CA means certificate warnings instead of the block page.

## Impact on firewall performance

Every security feature reduces throughput compared with plain firewalling. Fortinet's datasheets show it directly. Their footnotes define **NGFW** throughput as firewall + IPS + application control and **threat protection** throughput as firewall + IPS + application control + malware protection, measured on an enterprise traffic mix with logging enabled, next to **IPS** throughput and the much higher **firewall** throughput (large UDP packets). Firewall, IPS, NGFW and threat protection get lower as features are added. **SSL inspection** throughput is a separate measurement (IPS on an average of HTTPS sessions with different cipher suites), so don't assume it is lower than the threat protection figure; on some models it isn't. Size a FortiGate on the profile set it will really run, not the firewall number.

What drives the cost:

| Factor | Effect |
|---|---|
| **Deep SSL inspection** | The heaviest single feature: decrypt, inspect and re-encrypt, plus certificate generation. Inspect selectively |
| **Proxy-based inspection** | Buffers and reassembles content; sessions that need proxy-based features **can't be offloaded to NP processors** |
| **Flow-based inspection** | Lighter; on models with NP6/NP7 processors, **NTurbo** (`np-accel-mode basic`, the default where supported) offloads the firewall and NAT work of sessions with flow-based profiles to the NP, with a data path from the ingress interface to the IPS engine and on to the egress interface |
| **IPS sensor size** | More signatures, more pattern matching. Target sensors to the protected assets (3.2 IPS lesson) |
| **IPSA** (content processor pattern matching) | Offloads IPS pattern matching to CP8/CP9 where supported |
| **Logging** | `logtraffic all` on high-volume policies costs CPU and log bandwidth |

### Profile placement is a performance tool

The same FortiGate can handle very different loads depending on **where** profiles are applied:

1. Put **trusted, high-volume** flows (backups between data centres, update services, SaaS that must not be intercepted) in their own policies above the general ones, matched by address or ISDB, with **certificate inspection or no inspection**, and only the profiles that add value.
2. Apply **deep inspection, application control and the full web filter** to general user browsing, where the risk is.
3. Apply **server-target IPS** and **Protecting SSL Server** only to inbound policies for the servers.
4. Keep **flow-based** inspection unless a proxy-only feature is required.

### Device performance: what to watch

```text
FGT-Hub # get system performance status
CPU states: 2% user 61% system 0% nice 37% idle 0% iowait 0% irq 0% softirq
CPU0 states: 1% user 88% system 0% nice 11% idle 0% iowait 0% irq 0% softirq
Memory: 8165140k total, 6129320k used (75.1%), 1631028k free (20.0%), 404792k freeable (5.0%)
Average network usage: 1823540 / 1790214 kbps in 1 minute
Average sessions: 184215 sessions in 1 minute
```

- High **system** CPU with high session counts after enabling deep inspection points to SSL load.
- **Memory**: FortiOS enters **conserve mode** when memory use crosses the red threshold (`memory-use-threshold-red`, default 88%) and leaves it below green (default 82%). Proxy-based inspection then follows `av-failopen` under `config system global` (default `pass`: new sessions bypass the AV proxy and every profile that needs it; `off` blocks them), and flow-based inspection follows `fail-open` under `config ips global` (default `disable`: the IPS engine drops new sessions that need flow inspection). With the defaults, a memory-starved FortiGate silently stops proxy inspection. Check `diagnose hardware sysinfo conserve`.
- `diagnose sys top` shows which daemon is busy (`ipsengine`, `wad` for proxy and SSL work, `scanunitd` for AV).
- `diagnose sys session list` shows whether a session was offloaded (NPU fields and flags).
- The IPS engine's `fail-open` setting decides whether a full IPS buffer blocks traffic or lets it through uninspected.

> **Real world:** When a branch FortiGate is undersized, the fix is rarely "turn IPS off". Move SaaS and backup flows to light policies, narrow the IPS sensor, keep flow mode, and exempt categories you don't need to decrypt. Then re-measure.

## Use cases

| Scenario | Design |
|---|---|
| Protect a public web server | VIP policy with **Protecting SSL Server**, server-target IPS sensor (OS, application, HTTP), optionally ISDB source restrictions for admin paths |
| Protect users browsing | Deep inspection (with exemptions), client-target IPS, application control with unknown applications monitored, FortiGuard web categories |
| SaaS breakout at branches | ISDB policy and SD-WAN rule for the SaaS, certificate inspection, light profiles |
| Emergency vulnerability | CVE-based IPS entry added to the relevant sensors; virtual patching until the server is patched |
| False positive on a business-critical app | Narrowest exception: IPS exempt IPs or per-signature entry, application override, web rating override; report to FortiGuard |

## Lab it yourself

The FortiGate-VM trial has **no FortiGuard**: web categories won't rate and ISDB, application and IPS databases are only what ships with the firmware. With 3 interfaces and 3 policies:

1. Build two policies from the same LAN: one matched by an ISDB object (if the bundled database contains it) or an address object with certificate inspection, and a general policy with deep inspection and application control.
2. Compare `get system performance status` and `diagnose sys top` while you download a large file through each policy.
3. Use a **static URL filter** (no FortiGuard needed) to test HTTPS blocking with certificate versus deep inspection.

Throughput comparisons on a 1-vCPU trial don't tell you anything about hardware with NP and CP processors; use datasheets for sizing.

## Key takeaways

- ISDB matches at **L3/L4 on the first packet**; application control identifies at **L7** after a few packets; web filter rates URLs/categories; IPS catches exploits.
- Use ISDB policies to give trusted, high-volume SaaS light inspection, above general deep-inspection policies.
- With certificate inspection, web filter rates by **host**; paths and many app-control signatures need **deep inspection**.
- Datasheet throughput drops from firewall to IPS to NGFW to threat protection; SSL inspection is measured separately. Size on the profiles you'll run.
- **Proxy-based** sessions can't be NP-offloaded; **flow-based** sessions can be with **NTurbo** on NP6/NP7 models.
- Watch CPU, memory and **conserve mode**; `diagnose sys top` shows which engine is busy.
- Fix false positives with the narrowest override, and report them to FortiGuard.
