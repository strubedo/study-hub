## The design problem

Most traffic a FortiGate sees is TLS. Without decryption, IPS, antivirus, application control and URL filtering see only the handshake: the SNI, the certificate and the IP addresses. With decryption, they see everything, but you pay in CPU, in certificate management, and in applications that break. An architect has to decide, per traffic flow, **how much** to inspect, and design the exceptions.

## Two different jobs: outbound clients versus inbound servers

An SSL/SSH inspection profile does one of two jobs. In the GUI the choice is **Enable SSL Inspection of**:

| | Multiple Clients Connecting to Multiple Servers | Protecting SSL Server |
|---|---|---|
| Typical policy | Outbound: users to the internet, destination unknown | Inbound: internet clients to **your** server behind the FortiGate (VIP) |
| Certificate the client sees | A certificate the FortiGate **re-signs** on the fly with its CA | **Your server's own certificate**, imported on the FortiGate |
| CLI | `set server-cert-mode re-sign` (default) | `set server-cert-mode replace` with `set server-cert <local cert>` |
| What you must provide | A CA certificate (`caname`, default `Fortinet_CA_SSL`) that clients trust | The server's certificate **and private key** as a local certificate |
| Client trust problem | Clients must trust the FortiGate CA | None: clients already trust your server's public certificate |

```text
FGT-Hub # config firewall ssl-ssh-profile
FGT-Hub (ssl-ssh-profile) # edit "Protect-WebSrv"
FGT-Hub (Protect-WebSrv) # set server-cert-mode replace
FGT-Hub (Protect-WebSrv) # set server-cert "www-example-com"
FGT-Hub (Protect-WebSrv) # end
```

Protecting an SSL server lets IPS (and WAF-style signatures) see attacks hidden inside HTTPS requests to your web server, which is the inbound half of the "HTTP and HTTPS code injection" use case below.

> **Exam tip:** Re-sign is for many clients going to many unknown servers. Replace is for one known server whose certificate you own. A question that gives you "the FortiGate must inspect HTTPS to the company web portal, and clients must not see any certificate warning" wants **Protecting SSL Server** with the portal's certificate, not deep inspection with `Fortinet_CA_SSL`.

## Certificate inspection versus full (deep) inspection

| | Certificate inspection | Full SSL (deep) inspection |
|---|---|---|
| Decrypts? | **No**. Inspects only up to the TLS layer: client hello (SNI) and server certificate | **Yes**. FortiGate is a man in the middle, acting as a subordinate CA |
| Web filter | By host (SNI, or certificate CN/SAN): category and domain decisions | Full URL (path and query), safe search, content |
| Application control | Only what's visible in the handshake | Full signatures |
| IPS, AV, DLP on payload | Not on the encrypted payload | Yes |
| Certificate warnings | None for allowed traffic; block pages over HTTPS can still warn (see below) | Every site warns unless clients trust the FortiGate CA |
| Breaks | Very little | Certificate-pinned apps, mutual-TLS (client certificate) sites, some banking and health sites by policy |
| Cost | Low | High: decryption and re-encryption per session |

Predefined profiles: **certificate-inspection**, **deep-inspection** and **no-inspection** are read-only (clone them to change anything); **custom-deep-inspection** is editable. CLI: `config https` → `set status certificate-inspection | deep-inspection | disable`, `set ports 443 8443`; `config ssl` → `set inspect-all` to inspect every port.

Ports and inspection mode: with deep inspection in **proxy** mode only the mapped ports are inspected unless *Inspect all ports* is on; in **flow** mode, deep inspection scans all ports whatever the setting.

## The server certificate SNI check

Certificate inspection trusts the SNI that the client sends, and a client (or malware) can lie: send `SNI=www.allowed-bank.example` to reach a server that's really something else. The **Server certificate SNI check** compares the SNI in the client hello with the **CN or SAN** of the certificate the server returns.

| `sni-server-cert-check` | On mismatch |
|---|---|
| `enable` (default) | The FortiGate uses the **certificate CN** for URL filtering instead of the SNI |
| `strict` | The FortiGate **closes the connection** |
| `disable` | No check |

```text
FGT-Hub # config firewall ssl-ssh-profile
FGT-Hub (ssl-ssh-profile) # edit "Cert-Insp-Strict"
FGT-Hub (Cert-Insp-Strict) # config https
FGT-Hub (https) # set status certificate-inspection
FGT-Hub (https) # set sni-server-cert-check strict
FGT-Hub (https) # end
FGT-Hub (Cert-Insp-Strict) # end
```

`strict` is the safer choice against domain fronting and SNI spoofing, but it also blocks legitimate CDN and shared-hosting sites whose certificate doesn't list the requested name. `enable` keeps them working while still rating by the real certificate.

## Certificate handling options

The key CLI defaults in the `config https` block (FortiOS 7.6 CLI Reference):

| Option | Values | Default | Meaning |
|---|---|---|---|
| `untrusted-server-cert` | allow, block, ignore | **allow** | Server cert from an untrusted CA. *allow*: let it through; with deep inspection it is re-signed with **`Fortinet_CA_Untrusted`**, so the user still sees a warning; *ignore*: re-sign as trusted (deep inspection only); *block*: drop |
| `expired-server-cert` | allow, block, ignore | **block** | Expired certificate |
| `revoked-server-cert` | allow, block, ignore | **block** | Revoked certificate |
| `cert-validation-timeout` | allow, block, ignore | **allow** | The validation check timed out |
| `cert-validation-failure` | allow, block, ignore | **block** | The validation check failed |
| `client-certificate` | bypass, inspect, block | **bypass** | Server requests a client certificate (mutual TLS) |
| `unsupported-ssl-version` | allow, block | **block** | Below the inspected range |
| `min-allowed-ssl-version` | ssl-3.0 … tls-1.3 | **tls-1.1** | Lowest version accepted. Flow-based inspection doesn't support SSL version control |
| `encrypted-client-hello` | allow, block | **block** | TLS ECH hides the real SNI |
| `quic` | inspect, bypass, block | **inspect** | HTTP/3 over QUIC (fixed to bypass with certificate inspection) |

In the GUI, deep-inspection actions read *Keep Untrusted & Allow*, *Block* and *Trust & Allow*.

Two CA certificates matter:

- **`Fortinet_CA_SSL`** (`caname`): signs re-signed certificates for servers whose real certificate is trusted. Distribute it (or, better, your own enterprise subordinate CA) to every client.
- **`Fortinet_CA_Untrusted`** (`untrusted-caname`): signs re-signed certificates for servers whose real certificate is **not** trusted. **Never install it on clients**: its whole purpose is to keep the browser warning for genuinely bad certificates.

## Exemptions and false positives

Full inspection always needs exemptions. Exempt traffic is not decrypted:

- **Reputable websites** (FortiGuard list) and **web categories**. The GUI adds Finance and Banking, Health and Wellness, and Personal Privacy by default, usually for privacy or legal reasons.
- **Addresses** (address objects with interface *any*) and wildcard FQDNs: for certificate-pinned apps, update services, mutual-TLS partner sites.
- CLI: `config ssl-exempt` with `set type fortiguard-category | address | wildcard-fqdn ...`. Logging exemptions is off by default.

A **false positive** at the TLS layer is a session the FortiGate blocks or breaks although nothing is wrong. How to tell which cause applies:

| Symptom | Likely cause | Fix |
|---|---|---|
| Every HTTPS site shows an untrusted issuer `Fortinet_CA_SSL` | Clients don't trust the CA | Push the CA (GPO/MDM) or use an enterprise subordinate CA |
| One site shows issuer `Fortinet_CA_Untrusted` | The real server certificate is untrusted (self-signed, missing intermediate) | Usually correct behaviour. If the site is known-good, fix the server or exempt it; never trust the untrusted CA |
| A mobile or desktop app fails, browsers work | Certificate pinning | Exempt the app's domains or addresses |
| Partner portal with smart-card or client-cert login fails | Mutual TLS | Exempt it (the default `client-certificate bypass` handles many cases) |
| Sessions to a CDN site blocked after enabling strict SNI | Certificate doesn't list the SNI | Use `enable` instead of `strict`, or exempt |
| Old embedded device can't connect | TLS version below `min-allowed-ssl-version` or unsupported cipher | Separate profile for that destination |

Use the SSL anomaly logs (UTM log type, SSL subtype; *Log SSL anomalies* is on by default) to see why a session was blocked.

## HTTP and HTTPS code injection

The blueprint doesn't define this bullet further. Read it first as injection attacks carried in HTTP or HTTPS; the second angle is a closely related certificate trap.

1. **Attacks**: SQL injection, cross-site scripting, command injection in requests or responses. Over plain HTTP, IPS signatures see them directly. Over HTTPS they're invisible **unless the FortiGate decrypts**: full inspection for outbound clients, **Protecting SSL Server** for your own servers. Certificate inspection alone can't stop them.
2. **FortiGate-generated content**: block pages, warnings and authentication prompts are content the FortiGate inserts into the user's session. Over HTTPS the FortiGate has to present that page itself, signed by its CA, so users who don't trust `Fortinet_CA_SSL` see a **certificate warning instead of the block page**, even with certificate inspection. Installing the CA on clients fixes both this and deep-inspection warnings.

## Use case: certificate errors on FortiGate

A help-desk flood after enabling inspection is almost always one of these:

1. Deep inspection enabled before the CA was deployed: every HTTPS site warns.
2. HSTS sites can't be clicked through: browsers refuse to bypass the warning for HSTS-preloaded domains, so users can't work around a missing CA.
3. Untrusted server certificates: correctly signed with `Fortinet_CA_Untrusted`.
4. Pinned apps and mutual TLS: need exemptions.
5. Certificate inspection with web filter blocks: users see a warning instead of the block page until the CA is trusted.

> **Real world:** Use your own enterprise subordinate CA rather than the built-in `Fortinet_CA_SSL`. The FortiOS docs state that `Fortinet_CA_SSL` is unique to each FortiGate, so in a 300-branch estate you would otherwise distribute hundreds of CAs.

## Lab it yourself

On the FortiGate-VM trial (3 interfaces, 3 policies) with a Linux or Windows client behind it:

1. Create a policy with the read-only **certificate-inspection** profile and a web filter blocking one domain. Browse to it over HTTPS and note the certificate warning on the block page. Download `Fortinet_CA_SSL` from the profile, install it on the client, and retry.
2. Clone **custom-deep-inspection**, set `sni-server-cert-check strict`, and try `curl -k --resolve` tricks with a mismatched SNI.
3. The trial's low-encryption-only limit may stop full inspection of modern TLS sites from working, and without FortiGuard the category exemptions and web ratings won't work. Treat those parts as read-only and use a full licence or the on-demand labs to test them.

## Key takeaways

- **Re-sign** (multiple clients to multiple servers) uses the FortiGate CA; **replace** (Protecting SSL Server) uses your server's own certificate and key.
- Certificate inspection sees only the handshake (SNI, certificate); full inspection decrypts and enables payload inspection.
- **SNI check**: `enable` (default) falls back to the certificate CN for URL filtering, `strict` closes mismatched connections.
- Defaults: untrusted **allow** (re-signed with `Fortinet_CA_Untrusted`), expired **block**, revoked **block**, client certificate **bypass**, minimum TLS 1.1.
- Never deploy `Fortinet_CA_Untrusted` to clients.
- Exempt pinned apps, mutual-TLS sites and privacy categories; use SSL anomaly logs to diagnose false positives.
- HTTPS code-injection attacks are only visible with decryption; HTTPS block pages warn unless the FortiGate CA is trusted.
