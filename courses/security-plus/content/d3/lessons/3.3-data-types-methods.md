## Know the data before you protect it

Data protection starts with three questions: what kind of data is it, what state is it in, and how sensitive is it? The answers decide which of the eight protection methods in objective 3.3 apply. Domain 1 introduced obfuscation, tokenization and masking briefly as cryptographic-adjacent tools; this lesson compares all eight methods properly.

## Data types: structured and unstructured

| | Structured | Unstructured |
|---|---|---|
| What | Data in a fixed schema: rows and columns, defined fields | Data without a predefined model: documents, email, chat, images, audio, video, scanned PDFs |
| Examples | Customer database, ERP tables, CSV exports, log fields | Contracts in a file share, Teams/Slack messages, recorded calls |
| Discovery and classification | Easy: a column called `card_number` is card data | Hard: needs content inspection (pattern matching, fingerprints, machine learning) |
| Typical controls | Database permissions, column encryption, tokenization, masking views | DLP content inspection, sensitivity labels, file-level encryption, access reviews of shares |

Semi-structured data (JSON, XML, email headers) sits in between: it has tags but no fixed schema. Most of an organization's data volume is unstructured, which is why it is where sensitive data most often hides.

## Data states

| State | Where | Main protections |
|---|---|---|
| **At rest** | Stored: disks, databases, backups, object storage, removable media | Full-disk, volume, file, database or record encryption (Domain 1); access control; tokenization; secure disposal |
| **In transit** (in motion) | Moving across a network or bus | TLS, IPsec, SSH, E2EE; VPNs; network segmentation |
| **In use** | Being processed: in memory, CPU registers, on screen | Access control and least privilege, masking on display, memory protections, and **confidential computing**: hardware trusted execution environments (secure enclaves) that keep data encrypted in memory and isolated from the host OS and hypervisor |

Data in use is the hardest state: to process data, a program normally needs it in plaintext. Memory scraping malware (for example on payment terminals) attacks exactly this state.

## Data classifications

A classification scheme assigns each data set a label that determines its handling. The SY0-801 objectives list seven terms. They come from two traditions:

**Government (U.S. Executive Order 13526)** defines three classification levels by the damage unauthorized disclosure could reasonably be expected to cause to national security:

| Level | Damage |
|---|---|
| **Top secret** | Exceptionally grave damage |
| **Secret** | Serious damage |
| **Confidential** | Damage |

Information that is not classified is "unclassified" (it may still need protection, such as controlled unclassified information).

**Commercial** schemes are defined by each organization; there is no universal standard. A typical scheme, from most to least protected:

| Label | Typical meaning | Examples |
|---|---|---|
| **Restricted** | Severe harm or regulatory penalties if disclosed; access by named individuals only | Cardholder data, health records, merger plans, encryption keys |
| **Confidential** | Serious harm if disclosed; need-to-know | Customer PII, contracts, source code |
| **Sensitive** | Internal; limited harm if disclosed | Internal procedures, org charts, project plans |
| **Public** | Approved for release; no harm | Published marketing, press releases, public website |

**Critical** is different: it rates **availability and integrity** importance rather than secrecy. Critical data is what the business cannot operate without (production recipes, the order database, OT setpoints) and drives backup, redundancy and recovery priorities. Public data can be critical (the price list on a public website).

> **Exam tip:** Organizations order commercial labels differently (some put "confidential" above "restricted"). On the exam, use the scenario's own policy if it gives one. If it does not, top secret > secret > confidential for government, and restricted is the highest common commercial label.

## Methods used to secure data

| Method | What it does | Reversible? | Where the secret or mapping lives |
|---|---|---|---|
| **Encryption** | Transforms data with an algorithm and key | Yes, by anyone with the key | The key (KMS, HSM, TPM) |
| **Hashing** | Produces a fixed-length digest; one-way | No (but small input spaces can be brute-forced) | Nothing secret, unless a keyed hash (HMAC) or salt is used |
| **Tokenization** | Replaces a value with a surrogate token; in the classic vault model a random token that has no mathematical relationship to it (see below) | Only through the token vault | The token vault (mapping table), isolated and access-controlled |
| **Masking** | Hides part or all of a value (`****-****-****-4821`, `XXX-XX-6789`) | Static masking: no; dynamic masking: the original stays in the database and is shown to authorized users | The original data source |
| **Filtering** | Removes or blocks data elements from a flow, a query result or a report (DLP rules, API field filtering, row-level filtering) | n/a (the data is simply not passed on) | Policy rules |
| **Data transpose** | Rearranges the position of data elements (see below) | Yes, if the rearrangement pattern is known | The pattern (permutation) |
| **Deidentification** | Removes the association between identifying data and the data subject | Depends on technique (see below) | Any re-identification key, kept separately |
| **Obfuscation** | Makes data or code hard to understand without strong cryptography | Usually yes, with effort | The technique itself |

### Encryption versus tokenization versus hashing versus masking

These four are the classic comparison:

- **Encryption** is reversible math. Anyone who obtains the key recovers every value, so encrypted data is only as safe as the key management; protect the keys and store them separately from the data.
- **Tokenization** removes the real value from the systems that use the token. A stolen token is useless without the vault, which is why tokenization can shrink the set of systems that hold cardholder data (PCI DSS scope). Format-preserving tokens keep the length and format so legacy applications still work. The table describes the classic vault model with random tokens. The PCI SSC tokenization guidelines also allow tokens generated by a strong reversible cryptographic function or by a one-way function with a strong secret salt; whatever the method, recovering the PAN from the token alone must not be computationally feasible, and the guidelines warn that a hashed token kept alongside a truncated PAN can let an attacker reconstruct the number.
- **Hashing** is for verifying, not recovering: passwords (with salt and a slow algorithm, Domain 1) and integrity checks. Hashing a nine-digit SSN without a secret key is not protection; all billion possibilities can be computed.
- **Masking** is for display and for test data. NIST SP 800-188 warns that data masking tools alone should not be used to de-identify data sets for public release (nor as the sole confidentiality mechanism in non-public sharing), because they provide minimal privacy protection: they act on designated fields and can leave quasi-identifiers such as birth date and ZIP code in place.

### Data transpose

CompTIA does not publish a definition, and no NIST or standards source defines "data transpose" as a term. Read it as the objective's wording implies: **transposition**, protecting data by **changing the order or position of its elements** rather than substituting them. Examples:

- A **transposition cipher** rearranges characters by a key (the classic rail fence or columnar transposition). On its own it is weak; it is one building block inside modern ciphers, which combine substitution and permutation.
- **Swapping** values between records or columns in a data set. NIST SP 800-188 lists attribute or record swapping as a de-identification technique: values are exchanged between similar records so aggregate statistics stay correct but no record reliably belongs to a given person.
- **Reordering fields** (for example, storing parts of an identifier in a permuted order) so that a casual reader or a simple pattern-matching tool does not recognize the value.

Treat transposition as obfuscation-strength protection unless it is part of a real cipher: anyone who learns the pattern can reverse it.

### Deidentification, pseudonymization and anonymization

- **Deidentification** (NIST, from ISO/TS 25237) is the general term for any process that removes the association between identifying data and the data subject.
- **Pseudonymization** is a type of deidentification that replaces identifiers with pseudonyms (random IDs, keyed hashes, tokens). The GDPR defines it as processing so that data can no longer be attributed to a person **without additional information that is kept separately** and protected. Recital 26 says pseudonymized data that can be attributed with that additional information is still personal data.
- **Anonymization** removes the association irreversibly. Truly anonymous information is outside the GDPR's scope (Recital 26). NIST SP 800-188 prefers the term deidentification and cautions that there is no technical mechanism to guarantee de-identified data cannot be re-identified, because quasi-identifiers and outside data sets can be combined.

### Obfuscation

Obfuscation makes data or code harder to understand: code obfuscation, steganography, encoding (Base64 is encoding, not encryption), and simple transforms. It raises the effort for a casual attacker but must not be relied on against a determined one.

## Choosing a method: worked examples

| Requirement | Method |
|---|---|
| Call center agents need the last four digits of a card to verify the caller | Masking |
| The e-commerce platform must keep charging returning customers without storing card numbers | Tokenization (vault at the payment provider) |
| Store passwords so they can be checked but never recovered | Hashing (salted, slow) |
| Laptop drives must be unreadable if stolen | Encryption (full disk) |
| Share a research data set so individuals cannot be identified, while totals stay accurate | Deidentification, for example suppression plus record swapping |
| Stop reports leaving the HR system from including salary columns | Filtering |

## Key takeaways

- Structured data has a schema and is easy to classify; unstructured data needs content inspection.
- Data states: at rest (encrypt storage), in transit (TLS, IPsec), in use (access control, masking, confidential computing).
- Government levels (EO 13526): top secret, secret, confidential. Commercial labels are organization-defined: restricted, confidential, sensitive, public. Critical rates availability and integrity.
- Encryption is reversible with a key; tokenization is reversible only through the vault; hashing is one-way; masking hides for display.
- Data transpose means rearranging data (transposition, swapping); it is reversible if the pattern is known.
- Pseudonymized data is still personal data under the GDPR; anonymized data is not, but true anonymization is hard to guarantee.
