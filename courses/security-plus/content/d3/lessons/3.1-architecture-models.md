## Why architecture is a security decision

Every architecture model moves three things: **where the system runs**, **who operates each layer**, and **what an attacker can reach**. Objective 3.1 asks you to compare models by their security implications, not to memorize product names. This lesson covers the models themselves; the next lesson weighs them against the technical and business considerations the objectives list.

## Cloud: what NIST actually defines

NIST SP 800-145 defines cloud computing by five essential characteristics (on-demand self-service, broad network access, resource pooling, rapid elasticity and measured service), three **service models** and four **deployment models**. Keep the two lists apart: the exam objectives name only the deployment models, but responsibility questions depend on the service model.

### Deployment models (where it runs, and for whom)

| Model | SP 800-145 definition (paraphrased) | Security implications |
|---|---|---|
| **Public** | Provisioned for open use by the general public; exists on the provider's premises | Multitenant; the provider controls the physical and virtualization layers; the customer relies on the provider's attestations (SOC 2, ISO 27001) and configures its own tenant |
| **Private** | Exclusive use by a single organization; may be owned and run by the organization, a third party or both, on or off premises | Most control and isolation; the organization (or its contractor) carries the operational burden and cost |
| **Community** | Exclusive use by a specific community of organizations with shared concerns (mission, security requirements, policy, compliance) | Shared cost and a shared compliance baseline (for example, several agencies or hospitals); each member depends on the others' and the operator's controls |
| **Hybrid** | A composition of two or more distinct cloud infrastructures (private, community or public) that remain unique entities but are bound by technology that enables data and application portability, such as cloud bursting | The interconnect (VPN, private circuit), identity federation and consistent policy across both sides become the critical controls; data classification decides which workloads may move |

> **Watch out:** In everyday usage "hybrid" often means on-premises plus a public cloud. NIST's wording is strictly "two or more distinct cloud infrastructures", and an on-premises private cloud qualifies. **Multicloud** is a different idea: using services from more than one cloud *provider* (commonly two public clouds). A design can be both hybrid and multicloud.

### Service models and the shared responsibility idea

SP 800-145 describes what the consumer can and cannot control in each service model. That is the basis of the **shared responsibility model** that every provider publishes:

| Layer | On-premises | IaaS | PaaS | SaaS |
|---|---|---|---|---|
| Data, its classification, and user accounts and access | Customer | Customer | Customer | Customer |
| Application code and configuration | Customer | Customer | Customer | Provider (customer configures tenant settings) |
| Runtime, middleware | Customer | Customer | Provider | Provider |
| Guest operating system | Customer | Customer | Provider | Provider |
| Virtualization, servers, storage, network | Customer | Provider (the customer still has limited control of select networking, such as host firewalls and security groups) | Provider | Provider |
| Physical facility | Customer | Provider | Provider | Provider |

Two rows never move: the customer is always responsible for **its data and for who can access it**, and the provider is always responsible for the **physical** layer in public cloud. Most public cloud breaches come from the customer's side of the line: a storage bucket left public, an over-permissive role, an exposed management port.

### Serverless

Serverless (functions as a service such as AWS Lambda or Azure Functions, plus managed back ends) **still runs on servers**; the customer just never sees or manages them. The security effect:

- **Shifts to the provider:** patching the OS and the language runtime, capacity, scaling, host hardening.
- **Stays with the customer:** the function code and its third-party libraries, the permissions (IAM role) each function runs with, validation of every event that triggers it (an HTTP request, a queue message, a file upload), secrets handling, and logging.
- **New risks:** many small functions each with its own role invites over-permissive "one role for all" shortcuts; event-data injection; functions are short-lived, so forensic evidence vanishes unless logs are shipped centrally; and the bill is a denial-of-wallet target if invocation is not rate limited.

### Infrastructure as Code (IaC)

IaC describes infrastructure (networks, security groups, VMs, IAM policies) in machine-readable files (Terraform, CloudFormation, Bicep, Ansible) that a pipeline applies. Security gains: every environment is built the same way, changes go through version control and peer review (Domain 1 change management), templates can be **scanned before deployment** (policy as code), and **drift** from the declared state can be detected and reverted. Security risks: a mistake in a shared module is replicated everywhere it is used; secrets hard-coded in templates or held in state files leak through the repository; and whoever controls the pipeline controls production, so the CI/CD system and its credentials become high-value targets.

> **Exam tip:** When a scenario says a misconfiguration keeps "coming back" after someone fixes it in the console, the fix belongs in the IaC source; the pipeline overwrites manual changes.

## Operational technology (OT)

NIST SP 800-82 Rev. 3 defines OT as programmable systems and devices that **interact with the physical environment** (or manage devices that do): industrial control systems, building automation, transportation, physical access control and environmental monitoring. Domain 2 covered OT as an attack surface; the architectural implications are:

- **Priorities differ from IT.** SP 800-82 says OT security objectives typically prioritize integrity and availability, and that safety is an overarching priority. Rebooting to patch, an active scan or an IPS false positive can stop a process or create a hazard.
- **Long lifetimes and vendor certification.** Controllers run for decades; patches may need vendor approval and a planned outage, so compensating controls (segmentation, monitoring, strict remote access) carry more weight.
- **Segmentation by function.** SP 800-82 discusses reference models such as the Purdue model, with the enterprise network separated from the control network by a DMZ, and recommends controlled boundaries such as firewalls and **unidirectional gateways** (data diodes), which physically allow traffic in one direction only.
- **Safety systems** (for example a safety instrumented system) must keep working even when the control network is compromised.

## On-premises infrastructure

On-premises means the organization owns or leases the facility and operates every layer. It offers full control and visibility (you can tap any link, choose every component, keep data in a known building) at the price of full responsibility: physical security, power and cooling, patching, hardware refresh and capacity are all yours. It is the baseline the other models are compared with.

## Air-gapped networks

The NIST glossary (from RFC 4949) defines an air gap as an interface between two systems that are **not connected physically** and where any logical connection is **not automated**: data crosses only manually, under human control. Air gaps protect high-value systems (classified networks, some OT, offline backup and key-signing systems) from network-borne attack. Their limits are what the exam tests:

- Removable media, maintenance laptops and vendor equipment that cross the gap can carry malware in and data out.
- Updates and signatures must be carried in manually, so air-gapped systems often lag on patches.
- Insiders are not stopped by an air gap.
- The gap erodes quietly: an undocumented wireless interface, a "temporary" link for a vendor, or a dual-homed engineering workstation.
- SP 800-82 notes that as OT is increasingly connected to IT, relying on air gaps alone is not enough.

A data diode is **not** an air gap (it is an automated, one-way connection), but it is a common alternative when data must leave a protected network continuously.

## Microservices

NIST (from SP 800-190) describes microservices as a set of containers that work together to compose an application. Instead of one monolith, many small services talk to each other over APIs. Security implications:

- **More internal attack surface:** every service exposes an API, and east-west traffic dwarfs north-south. Controls move inside: mutual TLS between services, a distinct identity per service, authorization on every call, often through a service mesh and an API gateway.
- **Smaller blast radius** when each service has least-privilege access to only its own data store.
- **Supply chain and image hygiene:** dozens of images and dependencies to scan and patch.
- **Observability:** a request crosses many services, so centralized logging and tracing are needed to investigate anything.

## Logical versus physical segmentation

| | Logical segmentation | Physical segmentation |
|---|---|---|
| How | VLANs, VRFs, firewall zones and policies, cloud security groups, SDN and microsegmentation on shared hardware | Separate switches, cabling, firewalls or entire facilities |
| Strength | Flexible, cheap, quick to change; can be very granular | Isolation does not depend on a configuration being correct |
| Weakness | One misconfiguration, a switch or hypervisor flaw, or VLAN hopping (switch spoofing, double tagging) can bridge segments | Cost, space, cabling; harder to change; still bypassable by people and media |
| Typical use | Separating user, server, voice, guest and IoT traffic | Classified versus unclassified networks, safety systems, some OT and payment networks |

As a firewall engineer you already do logical segmentation daily: a FortiGate or PAN-OS zone per VLAN, with an inter-zone policy, is a logical boundary. The exam question is usually which one a constraint demands: if the requirement says isolation must hold even if the switching infrastructure is misconfigured or compromised, only physical separation meets it.

## Try it yourself

Paper exercise: draw your home or lab network. Label which parts are on-premises, which are SaaS (email, password manager), and which run on someone's IaaS. For each SaaS service, write one thing *you* are still responsible for (accounts, MFA, sharing settings). Then mark one place where you could add a logical segment (a guest VLAN or IoT SSID) and decide whether anything in your network justifies physical separation.

## Key takeaways

- Deployment models (SP 800-145): public, private, community (shared concerns, exclusive use), hybrid (two or more distinct infrastructures bound together). Service models (IaaS, PaaS, SaaS) set who manages which layer.
- The customer always owns its data and access management; the provider always owns the physical layer in public cloud.
- Serverless still runs on servers: OS and runtime patching move to the provider; code, dependencies, function permissions and event validation stay with the customer.
- IaC gives consistency, review and pre-deployment scanning, but replicates mistakes and makes the pipeline and its secrets critical.
- OT puts safety and availability first; air gaps are manual-only interfaces that removable media, insiders and quiet erosion can defeat.
- Microservices increase internal attack surface; use per-service identity, mTLS and authorization on every call.
- Logical segmentation is flexible but depends on correct configuration; physical segmentation holds even if the network gear fails.
