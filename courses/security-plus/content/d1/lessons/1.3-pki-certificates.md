## Public and private keys

Asymmetric cryptography uses a mathematically related **key pair**. The **public key** can be given to anyone; the **private key** must stay with its owner, ideally inside hardware that will not export it (a TPM, smart card or HSM).

| You want to... | Use whose key? |
|---|---|
| Encrypt something only Bob can read | **Bob's public** key (Bob decrypts with his private key) |
| Sign something so anyone can verify it came from you | **Your private** key (others verify with your public key) |
| Verify Alice's signature | **Alice's public** key |

The weak point is binding: how do you know a public key really belongs to `www.example.com` and not to an attacker on the path? **Public key infrastructure (PKI)** solves that with certificates, the authorities that issue them and the policies and systems around them.

## Certificates and certificate authorities

An X.509 v3 certificate (RFC 5280) is a public key plus identity information, **digitally signed by a certificate authority (CA)**. Fields you should recognize:

| Field / extension | Holds |
|---|---|
| Subject / Issuer | Distinguished names of the owner and of the CA that signed it |
| Serial number | Unique per issuing CA; used in revocation lists |
| Validity (notBefore, notAfter) | The lifetime |
| Subject public key info | The public key and its algorithm (RSA, EC) |
| Subject Alternative Name (SAN) | The DNS names and IP addresses the certificate is valid for |
| Key usage / Extended key usage | What the key may do: digitalSignature, keyEncipherment; serverAuth, clientAuth, codeSigning |
| Basic constraints | `CA:TRUE` for a CA certificate, `CA:FALSE` for an end-entity |
| CRL distribution points / Authority information access | Where to get the CRL; the OCSP responder and issuer certificate URLs |

Clients match the hostname against the **SAN**; RFC 9525 says the Common Name must not be used to identify a service.

### Chain of trust and root of trust

A typical public chain has three levels: a **root CA** (self-signed, kept offline), one or more **intermediate (subordinate) CAs** signed by the root, and the **end-entity (leaf)** certificate signed by an intermediate. A client validates each signature up the chain until it reaches a certificate it already trusts: a root in its **trust store** (shipped with the operating system or browser, or pushed by Group Policy or MDM for an internal CA).

That pre-installed root is the **root of trust** (also called the trust anchor) for PKI: trust in everything below it rests on it, and nothing above it can be checked. The term is also used for hardware: a TPM or secure boot ROM is a hardware root of trust that the rest of the boot chain is measured or verified against. Both meanings share the idea: a component that is trusted by design because it cannot be verified by something else, so it must be well protected.

> **Watch out:** A server must send its leaf **and** the intermediate certificates. Clients usually have only the root. A missing intermediate causes "unable to get local issuer certificate" errors on some clients and works on others that cached the intermediate, which makes it a confusing intermittent fault.

### Self-signed, internal and third-party

| Type | Signed by | Trusted by | Use for |
|---|---|---|---|
| **Self-signed** | Its own private key (subject = issuer) | Nobody, until someone manually trusts that exact certificate | Lab tests; root CA certificates are also self-signed by design |
| **Internal (private) CA** | Your organization's CA (for example AD Certificate Services) | Devices you have pushed the internal root to | Internal servers, 802.1X, VPN, device and user certificates |
| **Third-party (public) CA** | A commercial or no-cost public CA | Every mainstream browser and OS | Public-facing sites and services |

A self-signed server certificate trains users to click through warnings, and a user who clicks through cannot tell your server from an on-path attacker presenting their own certificate. An internal CA gives the same cost advantage with real validation.

Public CAs follow the **CA/Browser Forum Baseline Requirements**, which are shrinking maximum lifetimes for publicly trusted TLS certificates: 398 days before March 15, 2026; **200 days** from that date; 100 days from March 15, 2027; and 47 days from March 15, 2029. Automate renewal (for example with the ACME protocol).

## Certificate signing request (CSR) generation

To get a certificate you never send the CA your private key. Instead:

1. Generate a key pair on the server (or in its HSM).
2. Create a **CSR** (PKCS #10, RFC 2986). It contains the subject's distinguished name, the **public key** and attributes such as requested SANs, and it is **signed with the private key**, which proves to the CA that the requester holds the matching private key.
3. Submit the CSR. The CA (or its registration authority) validates the request: for public TLS certificates, **domain control** (for example a file served over HTTP or a random value in a DNS record; the remaining email-based methods SHOULD NOT be used from March 15, 2026 and are forbidden from March 15, 2028 under the Baseline Requirements); for OV and EV certificates, the organization as well.
4. The CA issues the certificate, signed with its private key.
5. Install the certificate and the intermediate chain on the server, next to the private key that never left it.

```text
admin@srv01:~$ openssl req -new -newkey rsa:3072 -nodes -keyout www.key -out www.csr \
    -subj "/O=Contoso/CN=www.example.com" -addext "subjectAltName=DNS:www.example.com"
admin@srv01:~$ openssl req -in www.csr -noout -verify
Certificate request self-signature verify OK
```

## Wildcard certificates

A wildcard certificate has a SAN such as `*.example.com`. Under RFC 9525 the `*` must be the entire left-most label, there may be only one, and it **matches exactly one label**:

| Name | Matches `*.example.com`? |
|---|---|
| `www.example.com`, `mail.example.com` | Yes |
| `example.com` (the apex) | **No**: add it as its own SAN |
| `a.b.example.com` | **No**: two labels where the wildcard covers one |

Wildcards simplify management but concentrate risk: the same private key sits on every server that uses the certificate, so one compromised server exposes them all. A certificate with an explicit list of SANs (a multi-domain or "SAN certificate") limits that.

## Revocation: CRL and OCSP

A certificate may need to be revoked before it expires: private key compromise, CA compromise, a change of name, or the server being decommissioned.

| | CRL | OCSP |
|---|---|---|
| Standard | RFC 5280 | RFC 6960 |
| What the client gets | A signed list of **all** revoked serial numbers from that CA, with *thisUpdate* and *nextUpdate* times and an optional reason code (keyCompromise, superseded, cessationOfOperation, certificateHold...) | A signed answer about **one** certificate: **good**, **revoked** or **unknown** |
| Freshness | Only as current as the last publication; delta CRLs carry changes since the base CRL | Near real time, depending on how often the responder is updated |
| Downsides | Large files; stale between publications | The CA learns which sites each client visits; an unreachable responder leaves the client to choose between failing open and failing closed |

**OCSP stapling** fixes the privacy and availability problems: the **server** fetches a signed, time-limited OCSP response for its own certificate and sends ("staples") it in the TLS handshake. The mechanism is the TLS `status_request` extension (RFC 6066); in TLS 1.3 (RFC 9846, which obsoleted RFC 8446) the response travels in the certificate entry. The client gets fresh status without contacting the CA.

> **Real world:** The CA/Browser Forum made OCSP optional and CRLs mandatory for public TLS CAs (ballot SC-063, effective March 2024), and Let's Encrypt, which announced the plan in 2024, switched its OCSP responders off on August 6, 2025. Expect CRL-based revocation for public certificates (browsers crawl CAs' CRLs and push the results to clients: Chrome's CRLSets carry a subset, Firefox's CRLite the full set), and both methods in enterprise PKIs.

## Key escrow vs key recovery

- **Key escrow** is "the retention of the private component of the key pair associated with a subscriber's encryption certificate to support key recovery" (CNSSI 4009, NIST glossary). A trusted party, often a separate escrow agent or a dual-controlled HSM, holds a copy so that encrypted data is not lost when an employee leaves or a key is destroyed, and so that the organization can meet legal access obligations.
- **Key recovery** is the set of "mechanisms and processes that allow authorized entities to retrieve or reconstruct keys" from backups or archives (NIST SP 800-57). Escrow is one way to make recovery possible; recovery is the act and its controls (for example *M of N* key recovery agents who must act together).

Escrow **encryption (decryption) keys**, never **signing keys**. SP 800-57 says private signature keys should generally not be backed up, because if a copy exists elsewhere "support for non-repudiation would be in question". This is why enterprise PKIs issue users separate signing and encryption certificates. The CA/Browser Forum similarly forbids anyone but the subscriber archiving a subscriber's private key without the subscriber's authorization.

## Try it yourself

Works on any OS with a browser. Open any HTTPS site, click the padlock (or "Connection is secure") and view the certificate: find the SAN list, the issuer, the validity period, the chain up to the root, and the CRL distribution point and OCSP URL (Authority Information Access) if present. Then open your OS trust store (Windows: `certmgr.msc` or "Manage computer certificates"; macOS: Keychain Access, System Roots; Linux: the files under `/etc/ssl/certs`) and find that root. If you have OpenSSL (most Linux distributions include it and Git for Windows bundles it; the `openssl` command on macOS is LibreSSL, which may reject newer options, so install OpenSSL with a package manager such as Homebrew if a flag is not recognised), generate a CSR with the command above and inspect it with `openssl req -in www.csr -noout -text`.

## Key takeaways

- Encrypt to the recipient's public key; sign with your own private key; verify with the signer's public key.
- A certificate binds a public key to names (in the SAN) and is signed by a CA; clients validate leaf to intermediate to a trusted root, the root of trust.
- A CSR holds the DN, the public key and requested attributes, signed with the private key; the private key never goes to the CA.
- Self-signed for labs only; internal CA for internal systems; third-party CA for public services. Public TLS lifetimes: 200 days now, 47 days by 2029.
- `*.example.com` matches exactly one label: not `example.com`, not `a.b.example.com`.
- CRL: full signed list, periodically published. OCSP: per-certificate good/revoked/unknown. Stapling: the server delivers its own OCSP response.
- Key escrow keeps a copy of encryption private keys for recovery; never escrow signing keys, or non-repudiation is lost.
