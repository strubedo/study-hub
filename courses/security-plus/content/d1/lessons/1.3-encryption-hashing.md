## Symmetric vs asymmetric encryption

| | Symmetric | Asymmetric |
|---|---|---|
| Keys | One shared secret key | Key pair: public and private |
| Speed | Fast; suited to bulk data | Slow; used for small values (keys, signatures) |
| Main problem | Getting the key to the other side securely; *n* users need *n(n-1)/2* pairwise keys | Binding a public key to an identity (PKI) |
| Algorithms | AES, ChaCha20 | RSA, elliptic-curve (ECDH, ECDSA, EdDSA), Diffie-Hellman, ML-KEM, ML-DSA |

Real protocols are **hybrid**: asymmetric cryptography authenticates the parties and establishes a shared secret, then symmetric encryption protects the data. TLS, IPsec, SSH and S/MIME all work this way.

## Algorithms and key lengths

Key length matters because brute-force effort doubles with every bit, but bits are not comparable across algorithm families. NIST SP 800-57 Part 1 gives the equivalences:

| Security strength | Symmetric | RSA / finite-field DH modulus | Elliptic curve key |
|---|---|---|---|
| 112 bits | (3TDEA, now disallowed for encryption) | 2048 | 224–255 |
| 128 bits | AES-128 | 3072 | 256–383 (for example P-256) |
| 192 bits | AES-192 | 7680 | 384–511 (P-384) |
| 256 bits | AES-256 | 15360 | 512+ (P-521) |

So a 256-bit ECC key is roughly as strong as a 3072-bit RSA key or AES-128; this is why ECC keys and signatures are much smaller. SP 800-131A Rev. 2 disallows anything below 112 bits of strength (RSA under 2048) for new protection.

| Algorithm | Type | Status |
|---|---|---|
| **AES** (FIPS 197) | Symmetric block cipher, 128-bit block, 128/192/256-bit keys | Approved; the default choice. Prefer authenticated modes such as GCM; avoid ECB, which leaks patterns |
| **ChaCha20-Poly1305** (RFC 8439) | Symmetric stream cipher with built-in authentication | Widely used in TLS 1.3 and WireGuard, especially on devices without AES hardware |
| **DES** | Symmetric, 56-bit key | Broken by brute force; FIPS 46-3 withdrawn in 2005 |
| **3DES / TDEA** | DES applied three times | Two-key disallowed; three-key encryption disallowed after 2023 (SP 800-131A Rev. 2); decryption of old data only |
| **RC4** | Stream cipher | Prohibited in TLS by RFC 7465 |
| **RSA** | Asymmetric (encryption, signatures) | 2048-bit minimum, 3072-bit for 128-bit strength |
| **ECDSA, EdDSA** (FIPS 186-5) | Elliptic-curve signatures | Approved; FIPS 186-5 no longer approves DSA for new signatures |
| **ML-KEM, ML-DSA, SLH-DSA** (FIPS 203, 204, 205, August 2024) | Post-quantum key encapsulation and signatures | NIST's first post-quantum standards |

A large quantum computer would break RSA, DH and ECC; symmetric algorithms are far less exposed, and NIST believes approved symmetric primitives with at least 128 bits of strength (AES-128 and up) remain adequate. NIST's transition plan (IR 8547, final October 2026) deprecates all quantum-vulnerable public-key algorithms (RSA, ECDSA, EdDSA, DH, ECDH) after 2030 and disallows them under NIST standards and guidelines after 2035. "Harvest now, decrypt later" (recording traffic today to decrypt in future) is the reason to adopt post-quantum key exchange first.

## Protocols, transport encryption and key exchange

**Transport / communication encryption** protects data in transit: **TLS** (HTTPS, LDAPS, SMTPS and FTPS, and the newer QUIC), **IPsec** (IKE negotiates keys; ESP encrypts, in transport mode between two hosts or tunnel mode between gateways), **SSH** (and SFTP over it), **WPA3** on Wi-Fi, and S/MIME or PGP for email messages end to end. TLS 1.0 and 1.1 are deprecated (RFC 8996); use TLS 1.2 with AEAD suites or TLS 1.3, whose suites are all AEAD (the common ones are TLS_AES_128_GCM_SHA256, TLS_AES_256_GCM_SHA384 and TLS_CHACHA20_POLY1305_SHA256; RFC 9846 (which obsoleted RFC 8446) also defines two AES-CCM suites).

**Key exchange** is how two parties agree a symmetric key over an untrusted network:

- **Key transport** (the client encrypts a random key with the server's RSA public key): simple, but anyone who later steals the server's private key can decrypt every recorded session.
- **Diffie-Hellman** key agreement (DH, or ECDH on elliptic curves): each side combines its own private value with the other's public value and both arrive at the same secret, which never crosses the wire. Done with fresh, **ephemeral** keys each session (DHE, ECDHE), it gives **forward secrecy** (often called perfect forward secrecy, PFS): compromising the server's long-term key later does not expose past sessions. RFC 9846 (which obsoleted RFC 8446) removed static RSA and static DH from TLS 1.3, so "all public-key based key exchange mechanisms now provide forward secrecy".
- **Key encapsulation** (ML-KEM): the post-quantum replacement; browsers and servers are already deploying hybrid exchanges that combine ECDH with ML-KEM.
- **Out-of-band**: delivering a pre-shared key by a separate channel (an IPsec PSK read over the phone). Workable for a few sites, unmanageable at scale.

> **Exam tip:** Diffie-Hellman establishes a key; it does not authenticate anyone. Without signatures or certificates, DH is open to an on-path attacker who runs one exchange with each side. TLS signs the exchange with the server's certificate key.

## Encryption levels (data at rest)

| Level | What is encrypted | Examples and notes |
|---|---|---|
| **Full disk** | The entire drive, including OS, swap and free space | BitLocker on the OS drive, FileVault, LUKS; self-encrypting drives. Protects a lost or stolen device that is powered off; once booted and unlocked, files are readable by anyone logged in |
| **Partition** | One partition on a disk | A data partition encrypted while the OS partition is not |
| **Volume** | A logical volume, which may span disks or be a container file | BitLocker on a data volume, a VeraCrypt container, an encrypted cloud block volume |
| **File** | Individual files or folders | EFS, GPG, a password-protected archive. A GPG-encrypted file or encrypted archive stays encrypted wherever it is copied; EFS works only on NTFS volumes, so a copy on a FAT or exFAT USB drive is not encrypted |
| **Database** | The whole database's files | Transparent data encryption (TDE): protects stolen database files and backups, but the application and DBA still see plaintext |
| **Record** | Individual rows, or fields within them (also called column- or field-level encryption) | Encrypting only the card-number or SSN field, often in the application, with separate keys, so even DBAs cannot read it |

The general rule: the finer the level, the narrower the exposure but the more key management and application work. Full disk encryption alone does nothing against an attacker with a session on the running system.

## Hashing algorithms

A cryptographic hash turns any input into a fixed-length digest. It is **one-way** (you cannot recover the input), **deterministic** (same input, same digest), and should be **collision resistant** (it should be infeasible to find two inputs with the same digest).

| Algorithm | Digest | Status |
|---|---|---|
| **MD5** | 128 bits | Collisions published in 2004; RFC 6151: not acceptable where collision resistance is required |
| **SHA-1** | 160 bits | Practical collisions (2017) and chosen-prefix collisions (2020). SP 800-131A Rev. 2 disallows it for new signatures; NIST plans to retire it completely by December 31, 2030 |
| **SHA-2** (FIPS 180-4) | SHA-224, SHA-256, SHA-384, SHA-512 | Approved; SHA-256 is the common default |
| **SHA-3** (FIPS 202) | SHA3-224 to SHA3-512 | Approved; different internal design, an alternative if SHA-2 weakens |

**Hashing is not encryption.** There is no key and no decryption. A hash proves integrity only if the attacker cannot replace the digest too; to bind a hash to a secret, use an **HMAC** (FIPS 198-1: hash plus a shared secret key), and to bind it to an identity, use a digital signature.

## Salting and key stretching

Passwords must be stored as hashes, but fast hashes fail in two ways: identical passwords produce identical hashes, and attackers can precompute hashes of likely passwords (rainbow tables).

A **salt** is a random, non-secret value generated per password and stored next to the hash. NIST SP 800-63B-4 requires salts of at least 32 bits. Salting:

- **defeats precomputed tables**, because the attacker would need a table for every salt;
- makes two users with the same password have different hashes;
- does **not** make a weak password strong. An attacker with the database still guesses `Summer2026!` against each account's salt; it just costs one guess per account rather than one for all.

**Key stretching** makes each guess expensive. Password-hashing schemes take a password, a salt and a **cost factor**: **PBKDF2** (RFC 8018, the one NIST SP 800-132 approves) iterates an HMAC many times; **bcrypt** is deliberately slow; **scrypt** (RFC 7914) and **Argon2** (RFC 9106, Argon2id) are also **memory-hard**, which blunts GPU and ASIC cracking. SP 800-63B-4 also recommends a **pepper**-style step: an extra keyed hash with a secret kept outside the database, ideally in an HSM.

## Digital signatures

1. The signer hashes the message (SHA-256, say).
2. The signer signs the digest with their **private key** (RSA, ECDSA, EdDSA or ML-DSA).
3. The verifier hashes the received message, and checks the signature with the signer's **public key** (from their certificate).

(This is the RSA and ECDSA flow. EdDSA and ML-DSA take the message itself as input and hash it inside the algorithm, but the key roles are the same.)

A valid signature gives **integrity**, **authentication of origin** and **non-repudiation**, because only the private-key holder could have produced it. It does not give confidentiality; sign *and* encrypt for both. Uses: code signing, S/MIME email, document signing, DNSSEC, and the certificates themselves.

## Obfuscation

Obfuscation makes data or code hard to understand without being strong cryptography:

- **Steganography**: hiding data inside other data (an image, audio, unused header fields). It conceals that a message exists; once found, it offers no protection unless also encrypted.
- **Tokenization**: replacing a value with a random token and keeping the mapping in a secured vault, so systems handle tokens instead of card numbers.
- **Data masking**: showing only part of a value (`****-****-****-4821`).
- **Code obfuscation**: renaming and restructuring code to slow reverse engineering.

Domain 3 (3.3) covers masking and tokenization as data protection methods in more depth.

## Tools

The objectives list "tools" without examples; the standard ones are:

| Tool | What it does |
|---|---|
| **TPM** (Trusted Platform Module) | A chip on the motherboard that stores keys and measurements; seals full-disk encryption keys to a known-good boot state; a hardware root of trust |
| **HSM** (hardware security module) | A dedicated, tamper-resistant appliance or card for generating and using keys (CA signing keys, payment keys); keys never leave it in plaintext |
| **Key management system (KMS)** | A service, often cloud-based, that creates, stores, rotates and audits keys and applies access policy to them |
| **Secure enclave** | An isolated processor or region (on phones and modern CPUs) that handles keys and biometric data apart from the main OS |
| Software toolkits | OpenSSL, GnuPG and OS certificate stores and command-line tools |

## Try it yourself

Any OS: compute a hash of a file, change one character, and hash it again. Windows PowerShell: `Get-FileHash .\notes.txt -Algorithm SHA256`; macOS: `shasum -a 256 notes.txt`; Linux: `sha256sum notes.txt`. Note that the digest length never changes and the new digest shares nothing recognizable with the old one. Paper exercise: two users both choose `Winter2026`; write out why their stored hashes differ with salts, and why an attacker with a wordlist still cracks both quickly if the hash is a single fast SHA-256 pass.

## Key takeaways

- Symmetric (AES, ChaCha20) for bulk data; asymmetric (RSA, ECC, DH, ML-KEM, ML-DSA) for key establishment and signatures; protocols combine both.
- Comparable strength (SP 800-57): AES-128 = RSA 3072 = ECC 256. Minimum today is 112 bits (RSA 2048). DES, 3DES encryption, RC4, MD5 and SHA-1 signatures are out.
- Ephemeral DH/ECDHE gives forward secrecy; every TLS 1.3 certificate-based handshake uses it (only PSK-only resumption lacks it). TLS 1.0/1.1 are deprecated.
- Encryption levels run from full disk down to individual records; finer levels narrow exposure at the cost of key management.
- Hashing is one-way and keyless; HMAC adds a shared key; signatures add a private key and non-repudiation.
- Salts defeat precomputed tables, not weak passwords; key stretching (PBKDF2, bcrypt, scrypt, Argon2) makes each guess costly.
- Obfuscation (steganography, tokenization, masking) hides meaning but is not encryption; TPM, HSM, KMS and secure enclaves protect keys.
