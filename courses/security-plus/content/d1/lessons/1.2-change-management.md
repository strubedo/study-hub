## Why change management is a security control

Most outages, and a surprising number of breaches, start with a change: a firewall rule opened "temporarily", a patch that restarted the wrong service, a certificate swapped without updating the chain. Change management makes every change to production deliberate, reviewed, reversible and recorded. NIST SP 800-53 Rev. 5 captures it in control **CM-3 Configuration Change Control**: decide which changes are controlled, review and approve or disapprove each one "with explicit consideration for security and privacy impact analyses", document the decision, implement only approved changes, keep records and monitor change activity, through a body such as a Change Advisory Board. CM-3's enhancements add testing, validating and documenting changes before finalizing them.

## Business processes

| Element | What it means | Security relevance |
|---|---|---|
| **Change advisory board (CAB)** | A group that reviews and authorizes changes | Brings security, operations and business views to each change |
| **Approval process** | The defined path a request follows to be approved, rejected or deferred | Stops unreviewed changes; creates an audit trail of who approved what |
| **Ownership** | One named change owner who is accountable for the change from request to closure | Someone answers for the risk and the result |
| **Stakeholders** | Everyone affected: system owners, users, support desk, security, vendors, sometimes customers | They must be consulted and told about downtime and risks |
| **Impact analysis** | Assessment of what the change affects and what could go wrong (NIST CM-4) | Finds security side effects: a rule change that exposes a port, a new dependency |
| **Test results** | Evidence from a non-production test that the change works and can be reversed | The CAB approves on evidence, not optimism |
| **Backout planning** | The documented steps to return to the previous known-good state | Limits outage and exposure if the change fails |
| **Fail forward** | Fixing a failed change by completing or correcting it in place rather than reverting | Used when backout is impossible or more dangerous |
| **Maintenance window** | A pre-agreed time when changes, and the disruption they cause, are allowed | Fewer users affected; staff on hand |
| **Standard operating procedures (SOPs)** | Step-by-step instructions for routine tasks | Repeatable, reviewed steps reduce human error |

Many organizations also sort changes into types (common ITIL usage, not an objective bullet): **standard** changes are pre-approved, low-risk and done by SOP (adding a user to a group); **normal** changes go to the CAB; **emergency** changes (patching an actively exploited flaw) use an expedited approval by a smaller emergency CAB and are reviewed afterwards. An emergency change still gets documented.

### Backout vs fail forward

A **backout plan** must be written and tested *before* the change, and it needs a decision point: "if validation has not passed by 01:30, start backout". Restoring the saved firewall configuration, reverting a VM snapshot or reinstalling the previous package version are typical backouts.

**Fail forward** means pushing on to a working state instead of going back. It is the right choice when reverting would cause more harm than fixing: a database schema migration that has already transformed data, a firmware upgrade that cannot be downgraded, or a security patch whose removal would re-expose an exploited flaw. Fail forward is a planned option, not an excuse to skip the backout plan; the CAB should know in advance which changes can only fail forward, because that raises their risk.

> **Exam tip:** If a scenario says the previous version "cannot be restored" or that rolling back would reintroduce a vulnerability, the answer is fail forward. If it says a change broke something and the old state is available, the answer is to execute the backout plan.

> **Real world:** On network gear, a timed automatic rollback is a cheap safety net: many network operating systems can apply a change and revert on their own unless the engineer confirms it within a few minutes, so a rule that cuts off your management session undoes itself.

## Technical implications

| Implication | What to plan for |
|---|---|
| **Allow lists / deny lists** | New software or a new version may be blocked by application allow-listing; a new service may need firewall, proxy or EDR exclusions. Each addition is itself a security decision and should be as narrow as possible. |
| **Restricted activities** | The approved scope limits what the implementer may do. Work outside the approved change (an extra "while I'm in there" rule) is unauthorized, even if harmless. Some activities, such as disabling logging or EDR, may be prohibited or need separate approval. |
| **Downtime** | Expected outage length, who is told, and whether it fits the maintenance window. Unplanned downtime is an availability incident. |
| **Service restart** | Restarting a daemon may drop sessions, reload configuration you did not intend to change, or fail to start, leaving the service down. |
| **Application restart** | An application may need restarting to load a patch or certificate; a patch that is installed but not loaded leaves the system vulnerable while scanners may report it fixed. |
| **Legacy applications** | Old software may break with new TLS settings, OS patches or libraries, and may not be supported by its vendor. These often need compensating controls rather than the change. |
| **Dependencies** | Other systems that rely on the changed one: DNS, authentication, certificates, APIs, licence servers, database connections. Map them before the change so the impact analysis is complete. |

> **Watch out:** Disabling TLS 1.0 and 1.1 (deprecated by RFC 8996) is the classic example of all of these at once: a legacy client on the factory floor stops connecting, a dependent service fails its health check, and the web server needs a restart before the new protocol settings take effect.

## Documentation and version control

After the change, the documentation must match reality, or the next responder works from a wrong picture.

- **Updating diagrams:** network, data-flow and rack diagrams. A new VLAN, firewall interface or cloud peering that is not on the diagram is invisible to incident responders and auditors.
- **Updating policies and procedures:** if the change alters how something is done (a new MFA method, a new backup target), the policy, SOP or runbook that describes it must be updated too.
- **Version control:** keep configurations, scripts, infrastructure-as-code and documents in a version control system (for example Git) or a configuration archive. Every change gets a commit tied to the change ticket, so you can see who changed what, compare versions (a `diff` of the firewall config before and after), and restore a known-good version as a backout.

> **Exam tip:** Version control answers "what changed, who changed it and how do we get back?". Updating diagrams and procedures answers "does our documentation still describe the environment?". Both are the last step of a change, before it is closed.

## A change, end to end

1. The **owner** raises a change request: what, why, scope, risk, affected **stakeholders**, implementation steps, **backout plan**, proposed **maintenance window**.
2. **Impact analysis** and testing in a non-production environment; **test results** are attached.
3. The **CAB** reviews the evidence and approves, rejects or asks for changes (**approval process**).
4. Stakeholders are notified of the window and expected **downtime**.
5. The change is implemented in the window, following the **SOP** and staying within scope (**restricted activities**).
6. The implementer validates the result; if it fails, the team executes the backout plan (or fails forward if that was the agreed plan).
7. **Diagrams, policies and procedures** are updated, configurations are committed to **version control**, and the ticket is closed with a review of any issues.

## Try it yourself

Paper exercise: write a one-page change request for a change you might make at home or work, such as replacing your router's firmware or moving your DNS to a new resolver. Include an owner, stakeholders (who in the house loses Wi-Fi?), impact analysis, a test you could run first, a backout plan with a decision time, whether the change could only fail forward (can the firmware be downgraded?), and what documentation you would update. If you use Git (any OS), put a configuration file in a repository, change it, and run `git diff` and `git log` to see the audit trail.

## Key takeaways

- Change management is a security control (NIST CM-3): every production change is requested, analyzed, approved, implemented, validated and recorded.
- CAB plus a defined approval process; one accountable owner; stakeholders consulted and informed.
- Impact analysis and test results come *before* approval; a backout plan with a decision point comes before implementation.
- Fail forward when reverting is impossible or more dangerous than fixing; back out when the known-good state is available.
- Plan for allow/deny list updates, restricted activities, downtime, service and application restarts, legacy apps and dependencies.
- Close the loop: update diagrams, policies and procedures, and keep configurations in version control.
