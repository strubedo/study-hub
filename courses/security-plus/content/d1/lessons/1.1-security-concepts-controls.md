## Defense in depth

NIST defines defense in depth as a strategy that integrates people, technology and operations "to establish variable barriers across multiple layers" of an organization. The point is not to have many firewalls; it is that the layers are *different*, so an attack that defeats one (a phishing email that gets past the mail filter) still meets another (MFA, EDR, segmentation, a user who reports it). Everything else in this lesson is a building block of those layers.

## The CIA triad

| Goal | Means | Typical controls | Opposite (attack outcome) |
|---|---|---|---|
| **Confidentiality** | Only authorized parties can read the data | Encryption, access control, data classification | Disclosure |
| **Integrity** | Data and systems are not changed without authorization, and changes are detectable | Hashing, digital signatures, change control, file integrity monitoring | Alteration |
| **Availability** | Authorized users can reach the system when they need it | Redundancy, backups, DDoS protection, patching, capacity planning | Destruction / denial |

Controls often trade one goal against another: encrypting a database protects confidentiality, but losing the key destroys availability. Exam scenarios frequently ask which element of CIA an event affected: a defaced web page is integrity, a ransomware outage is availability (and confidentiality, if data was also stolen), a leaked customer list is confidentiality.

## AAA and non-repudiation

| Piece | Question | Network examples |
|---|---|---|
| **Authentication** | Are you who you claim to be? (Identification is the claim; authentication is the proof) | Password plus OTP, certificate, 802.1X EAP-TLS |
| **Authorization** | What may you do? | RADIUS attributes assigning a VLAN, TACACS+ command authorization, firewall policy |
| **Accounting** | What did you do, and when? | RADIUS accounting start/stop records, TACACS+ command logs, syslog |

**Non-repudiation** is the assurance that a party cannot credibly deny an action. FIPS 186-5 defines it as assurance of integrity and origin that "can be verified and validated by a third party" as coming from the holder of a *private key*. That last part matters: non-repudiation comes from **digital signatures**. A symmetric MAC (such as HMAC) proves integrity and that the message came from *someone who holds the shared key*, but both sides hold that key, so either could have produced it. Logs support accountability, but a log the accused party could have edited is weak evidence; signed, centrally stored logs are stronger.

> **Exam tip:** "Prove that alice sent this" or "prevent the sender denying it" means digital signature (her private key). "Prove it was not modified in transit" alone can be a hash, a MAC or a signature.

## Least privilege and Zero Trust

**Least privilege** is NIST's principle that each entity gets "the minimum system resources and authorizations" needed for its function. It applies to people, service accounts, API tokens and network flows alike: a backup service that only needs read access should not be a domain admin, and a web server that only needs TCP 5432 to one database should not reach the whole server VLAN.

**Zero Trust** removes the idea that being inside the network grants trust. NIST SP 800-207 lists seven tenets, which can be summarized as:

1. All data sources and computing services are **resources** (an enterprise may also classify personally owned devices that can access enterprise resources as resources).
2. All communication is secured **regardless of network location**; being on the internal LAN earns nothing.
3. Access is granted **per session**, with the least privilege needed for that task.
4. Access is decided by **dynamic policy**: identity, device state, application, behavior and environment.
5. The enterprise **monitors the integrity and security posture** of all owned and associated assets.
6. Authentication and authorization are **dynamic and strictly enforced** before access is allowed (continuous re-evaluation, MFA).
7. The enterprise **collects as much information as possible** about assets, traffic and requests, and uses it to improve policy.

In 800-207's model, a **policy decision point** (made up of the **policy engine**, which decides, and the **policy administrator**, which sets up or tears down the session) controls a **policy enforcement point** that sits in front of the resource. Domain 3 covers the architecture; for this objective, know the principles: never trust by location, verify explicitly every time, grant least privilege, assume breach.

## Control categories: how a control is implemented

The SY0-801 objectives name four categories, each with a slash-alternative name:

| Category | What it is | Examples |
|---|---|---|
| **Technical / logical** | Implemented by hardware, software or firmware | Firewall rules, encryption, MFA, EDR, ACLs, file permissions |
| **Managerial / administrative** | Decisions and documents that direct the security program | Risk assessments, security policy, vendor due-diligence process, security planning |
| **Operational** | Carried out day to day by people following procedures | Awareness training, guards' patrol routine, log review, change management, configuration management |
| **Physical / environmental** | Protects the physical site and its conditions | Locks, fences, bollards, badge readers, CCTV, fire suppression, HVAC, flood sensors |

This four-way split is CompTIA's taxonomy. NIST SP 800-53 Rev. 5 organizes controls into 20 families (Access Control, Audit and Accountability, Configuration Management, Physical and Environmental Protection and so on) rather than these categories, so do not expect a NIST family to map to exactly one category.

> **Watch out:** The boundary between *managerial* and *operational* is about who and when. A policy requiring log review is managerial (a decision written down); the analyst actually reviewing the logs each morning is operational. A badge reader is physical even though it contains software; a SIEM correlation rule is technical even though people wrote it.

## Control types: what a control does

| Type | Purpose | Examples |
|---|---|---|
| **Preventive** | Stops the event from happening | Firewall deny rule, MFA, locked door, input validation, least-privilege permissions |
| **Deterring** | Discourages an attacker, without physically or logically stopping one who persists | Warning banner, "CCTV in operation" sign, visible guard, sanctions in a policy |
| **Detective** | Identifies and records an event during or after it occurs | IDS, SIEM alerts, CCTV recording, audit logs, file integrity monitoring |
| **Corrective** | Limits damage and restores normal operation after an event | Restoring from backup, reimaging a host, an IPS reset, patching the exploited flaw |
| **Compensating** | An alternative control used because the primary control cannot be | Isolating an unpatchable legacy host, extra monitoring where separation of duties is impossible |
| **Directive** | Tells people what they must or must not do | Policy, standard, SOP, "authorized personnel only" sign, mandatory training |

**Deterring vs preventive vs directive** is the most tested distinction. A login banner warning of prosecution *deters*; the password prompt behind it *prevents*. A sign reading "badge required beyond this point" is *directive* (it gives an instruction); the turnstile is *preventive*. A deterrent works on the attacker's motivation; a directive works on people who are expected to comply.

**Compensating** follows NIST's glossary sense: a control "employed in lieu of" a required one that provides comparable protection. It is chosen *because* of a constraint (cost, a legacy system, a vendor contract), so a scenario that mentions such a constraint is pointing at it.

### One control, several types

Type describes function, and a control can perform several functions. CCTV with a visible camera **deters** and **detects**. A guard can **deter**, **prevent** (refuse entry) and **detect**. An IPS **detects** and **prevents**. On the exam, pick the type the stem emphasizes: "reduce the likelihood that someone tries" is deterring; "identify who entered after hours" is detective.

## Worked example: category and type together

| Control at Contoso | Category | Type(s) |
|---|---|---|
| Firewall rule on fw01 blocking inbound RDP | Technical | Preventive |
| SIEM alert on 20 failed logins in 5 minutes | Technical | Detective |
| Restoring srv01 from last night's immutable backup | Technical (performed under an operational procedure) | Corrective |
| SSH login banner: "Unauthorized access is prohibited and prosecuted" | Technical | Deterring (also directive) |
| Information security policy approved by the board | Managerial | Directive |
| Acceptable use policy that names sanctions for misuse | Managerial | Directive and deterring |
| Security awareness training for all staff | Operational | Preventive (aims to stop users falling for phishing) |
| SOC analyst's daily review of VPN logs | Operational | Detective |
| Bollards in front of the data center entrance | Physical | Preventive |
| Visible camera with "CCTV in operation" sign | Physical | Deterring and detective |
| Fire suppression system | Physical / environmental | Corrective (limits damage) |
| Legacy HMI that cannot be patched, moved to an isolated VLAN with a jump host | Technical | Compensating (preventive in effect) |

Notice that the category column answers "what is it made of, and who runs it?" and the type column answers "what job does it do?". The two are independent: every category contains preventive and detective controls.

> **Real world:** Auditors usually record both, and a gap analysis looks for missing *types*. A segment with strong preventive rules but no detective logging means a successful bypass goes unnoticed.

## Try it yourself

Paper exercise (any computer, or a notepad): list ten controls you can see at your workplace or home network, for example your router's admin password, Wi-Fi WPA3, a smoke detector, your password manager, an "employees only" sign, the backup drive. For each, write one category and every type that applies, then mark which one a question stem would most likely emphasize. Finally, pick one control you cannot implement (say, MFA on an old NAS) and write a compensating control for it.

## Key takeaways

- Defense in depth layers different kinds of controls so one failure is caught by another.
- CIA: confidentiality (disclosure), integrity (alteration), availability (denial). AAA: authentication, authorization, accounting.
- Non-repudiation comes from digital signatures with a private key; a shared-key MAC cannot provide it.
- Least privilege: minimum access for the task. Zero Trust (SP 800-207): no implicit trust from location, per-session dynamic policy, continuous verification, monitor every asset.
- Category is *how* a control is implemented: technical/logical, managerial/administrative, operational, physical/environmental.
- Type is *what it does*: preventive, deterring, detective, corrective, compensating, directive; one control can be several types.
- Deterring discourages, preventive blocks, directive instructs; compensating replaces a control that cannot be implemented.
