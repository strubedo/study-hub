## Where these controls fit

Objective 4.1 asks you to *apply* mitigating controls to a scenario. The exam gives you a problem (an unpatchable controller, a lost phone, an unknown attachment, an attacker already inside) and expects you to pick the control that addresses that specific problem. This first lesson covers the general techniques: segmentation, access controls, hardening, sandboxing, deception and disruption technology, monitoring and alerting, mobile device management (MDM) and application control. The next two lessons cover network and endpoint products, then application, email and operating system controls.

Domain 1 classified controls by category and type; Domain 2 described the attacks. Here the question is always "which control fixes *this*?"

## Segmentation

Segmentation divides a network into zones so that a compromise in one zone cannot reach everything else. The mechanisms are familiar to any network engineer:

| Mechanism | Layer | Enforcement point |
|---|---|---|
| VLANs and subnets | 2/3 | Switches; inter-VLAN traffic forced through a router or firewall |
| Firewall zones and inter-zone policy | 3/4/7 | Firewall between zones (FortiGate zones, PAN-OS zones) |
| ACLs on routers or Layer 3 switches | 3/4 | Stateless permit/deny on interfaces |
| Microsegmentation | 3-7 | Host-based firewalls or hypervisor/cloud security groups per workload |
| Physical or air-gapped separation | 1 | No connection at all (Domain 3) |

A VLAN alone is not a security boundary unless traffic between VLANs passes through a policy enforcement point. Segmentation is also the standard **compensating control** for systems that cannot be patched or hardened: put the legacy controller in its own segment and allow only the one protocol and peer it needs.

> **Exam tip:** "The device cannot be patched and must stay online" is the cue for segmentation (isolate it and restrict what can reach it), not for replacing it or accepting the risk.

## Access controls

Access controls decide who or what may use a resource: file and share permissions, ACLs on network devices, firewall rules, database grants, cloud IAM policies. The principle is least privilege, granted through a model (role-based, rule-based, mandatory and so on, covered in lesson 4.5). In 4.1 scenarios, "access controls" usually means tightening permissions: removing Everyone/Full Control from a share, restricting management interfaces to an admin subnet, or limiting a service account to the one database it uses.

## Hardening

NIST defines hardening as a process intended to eliminate a means of attack by patching vulnerabilities and turning off nonessential services. In practice:

- Apply a **secure baseline** (CIS Benchmark, DISA STIG, vendor security guide) and keep it under configuration management.
- Remove or disable unneeded services, ports, protocols, sample content and default accounts; change default credentials.
- Patch the OS, firmware and applications.
- Enable host firewalls, logging, disk encryption and secure protocols (SSH instead of Telnet, SNMPv3 instead of v2c, HTTPS management only).
- Restrict administrative access (separate admin accounts, jump hosts, management VLAN).

Hardening reduces the attack surface of one system; segmentation reduces what an attacker can reach from it. Both are usually needed.

## Sandboxing

A sandbox runs code in an isolated environment where it cannot affect the real system. Two uses appear on the exam:

1. **Detonation sandbox (malware analysis):** an email gateway, firewall or EDR platform sends an unknown attachment or download to an instrumented virtual machine, watches what it does (files written, processes started, network connections, registry changes) and returns a verdict. This catches malware that has no signature yet.
2. **Application sandboxing:** the OS or browser confines an application so a compromise stays inside it: browser tab sandboxes, mobile app sandboxes, containers, Windows Sandbox.

Malware may detect a sandbox and stay dormant (sandbox evasion), which is why sandboxes are one layer among several.

## Deception and disruption technology

Deception places fake assets where only an attacker would touch them. Because no legitimate user should ever interact with them, **any** interaction is a high-fidelity alert with very few false positives. Disruption is the related goal of slowing the attacker down and wasting their time while defenders respond.

| Technique | What it is | Typical alert |
|---|---|---|
| **Honeypot** | A decoy system or service that looks attractive to attackers (NIST, from RFC 4949: "designed to be attractive to potential crackers and intruders") | Connection to the fake SSH or SMB server |
| **Honeynet** | A network of honeypots, often a whole fake segment, used to observe attacker behavior across several hosts | Lateral movement between decoys |
| **Honeyfile** | A decoy file with an enticing name (for example `passwords.xlsx`, `Payroll-2026.docx`) placed on a file share | The file is opened, copied or read |
| **Honeytoken** | Any decoy *data* that should never be used: fake credentials in memory or a config file, a fake API key, a fake database record, a tracking URL in a document | The fake key or record is used anywhere |
| **Canary account** | A decoy user account (a honeytoken in account form) that looks privileged but is never used legitimately | Any logon attempt or Kerberos ticket request for it |

The distinctions the exam tests: a honeypot is a *system*, a honeynet is *several systems*, a honeyfile is a *file*, a honeytoken is *data or a credential*, and a canary account is a *fake account*. Real-world products use "canary" loosely for several of these. Only "honeypot" has a NIST glossary definition; the other four descriptions are this course's reading of the objective terms in their common industry usage.

> **Watch out:** Deception is a detective control. It does not stop the attacker who has already reached the honeypot; it tells you they are there. Keep honeypots isolated from production so they cannot be used as a launch point.

## Monitoring and alerting

Every mitigation in this objective is weaker without monitoring: logs from firewalls, servers, EDR and identity systems feed a SIEM, which raises alerts when rules or analytics match. Lesson 4.4 covers the activities (aggregation, alerting, tuning) and tools in detail. In a 4.1 scenario, "monitoring/alerting" is the answer when the requirement is to *detect and notify*, not to block.

## Mobile device management (MDM)

MDM (today usually part of unified endpoint management, UEM) enrolls phones, tablets and laptops and pushes policy to them:

- Enforce a screen lock, PIN or biometric, and device encryption.
- Remote lock and **remote wipe** of a lost or stolen device (full wipe, or selective wipe of corporate data only on a personally owned device).
- Push or block apps, configure VPN, Wi-Fi and email profiles, distribute certificates.
- Detect jailbroken or rooted devices and block them from corporate resources.
- **Containerization** (work profile) to separate corporate apps and data from personal ones on BYOD devices.
- Geofencing and location tracking where policy and law allow.

> **Exam tip:** Lost phone with corporate email: MDM remote wipe. Personal phone where the company may only remove its own data: selective wipe of the corporate container.

## Application control: allow lists and block lists

Application control decides which software may run.

| Approach | Default | Strength | Weakness |
|---|---|---|---|
| **Allow list** (allowlist) | Deny everything not listed | Blocks unknown malware and unapproved software, including zero-days | Administrative effort; every update or new tool must be approved |
| **Block list** (denylist) | Allow everything not listed | Easy to deploy; blocks known-bad or banned apps | Misses anything new or renamed |

Allow-list rules can match on file path (weakest, since an attacker who can write to the path wins), file hash (exact but breaks on every update) or publisher certificate (survives updates, relies on code signing). Windows implements this with App Control for Business (formerly Windows Defender Application Control) and AppLocker; macOS uses Gatekeeper and notarization; MDM platforms apply app allow lists on mobile devices.

Allow lists suit fixed-function systems (kiosks, point-of-sale terminals, OT workstations, servers) where the software set rarely changes. Block lists suit general-purpose desktops where blocking a short list of risky tools is all that is practical.

> **Real world:** Changing an allow list is a change-management item (Domain 1.2): an application update that changes the binary's hash will stop running until the list is updated.

## Choosing among them

| Scenario cue | Control |
|---|---|
| Legacy system cannot be patched | Segmentation (compensating) plus strict access controls |
| New server going into production | Hardening to a baseline |
| Unknown attachment, no signature available | Sandbox detonation |
| Detect an intruder already inside, with few false positives | Deception (honeypot, honeyfile, honeytoken, canary account) |
| Lost or stolen phone | MDM remote wipe |
| Kiosk must run only one approved app | Application allow list |
| Stop a specific banned tool on all desktops | Application block list |

## Try it yourself

Paper exercise, any computer. Sketch a small office network: users, servers, a printer VLAN, a guest Wi-Fi and one old controller that cannot be patched. Draw the zones, then write three firewall policies between them (source zone, destination zone, service, action) so that the controller is reachable only from one engineering workstation on one port. Then decide where you would place a honeyfile and a canary account, and write what alert each would generate. On Windows you can look at your own application control options under Windows Security > App & browser control; on macOS look at System Settings > Privacy & Security for the Gatekeeper setting.

## Key takeaways

- Segmentation limits reach; it is the usual compensating control for unpatchable systems. A VLAN is a boundary only if inter-VLAN traffic passes through policy.
- Hardening removes attack surface on one system: baseline, patch, disable services, change defaults.
- Sandboxes detonate unknown code in isolation or confine applications.
- Honeypot = system, honeynet = network of them, honeyfile = file, honeytoken = data or credential, canary account = fake account. All are detective, high-fidelity, low false-positive.
- MDM enforces device policy and remote or selective wipe; containerization separates work and personal data.
- Allow lists deny by default and stop unknown software; block lists allow by default and stop only known-bad software.
