## The identity life cycle

**Provisioning** creates an account and grants its initial access; **deprovisioning** disables and eventually deletes it and removes its access. In between come changes (role moves, name changes) and reviews.

- **Joiner:** HR creates the person record; an identity governance or IAM system creates the directory account, mailbox and group memberships for the role. Automate from the HR system of record so accounts are created consistently (lesson 4.6).
- **Mover:** when someone changes role, *remove* the old role's access as well as adding the new one. Failing to remove it causes **privilege creep** (Domain 3, 3.2).
- **Leaver:** disable the account immediately at termination (for a hostile termination, before or during the exit meeting), revoke sessions and tokens, remove MFA devices, recover hardware, transfer data ownership, and delete the account after the retention period. Accounts left active after departure ("orphaned accounts") are a common breach path.

**Permission assignments and implications.** Assign permissions to groups or roles, not to individual users; grant the minimum needed (least privilege); avoid nested-group surprises (a group inside a privileged group inherits its rights); and remember the implications: every permission is attack surface if the account is compromised, broad permissions defeat separation of duties, and permissions granted directly to users are hard to review.

## Identity proofing

Before issuing credentials you must know the person is who they claim to be. NIST SP 800-63A-4 lists the expected outcomes of identity proofing: **identity resolution** (the claimed identity is one unique person), **evidence validation** (the documents are genuine), **attribute validation** (core attributes are accurate), **identity verification** (the applicant is the genuine owner of the evidence, for example by comparing a live photo with the document photo), **enrollment** and **fraud mitigation**. Its identity assurance levels range from IAL1 to IAL3; IAL3 proofing "SHALL only be delivered as on-site attended". In company terms: HR checks documents at hiring; the help desk verifies identity before resetting a password or MFA device (a classic social engineering target, Domain 2).

## Federation and single sign-on

**Single sign-on (SSO)** lets a user authenticate once and reach many applications without signing in again. **Federation** extends trust across organizational boundaries; NIST describes it as conveying identity and authentication information across a set of networked systems, between realms that have established trust. The core roles:

- **Identity provider (IdP):** authenticates the user and issues assertions or tokens (Microsoft Entra ID, Okta, AD FS, FortiAuthenticator acting as IdP).
- **Service provider (SP) / relying party (RP):** the application that trusts the IdP and grants access based on what it says.

### SAML

The Security Assertion Markup Language (OASIS SAML 2.0) is an **XML-based** framework for exchanging security information between an **asserting party** (the IdP) and a **relying party** (the SP). An **assertion** can carry three kinds of statements: **authentication** statements (who authenticated, when, by what method), **attribute** statements (email, department, group) and **authorization decision** statements. The common **SP-initiated web SSO** flow, from the OASIS technical overview:

1. The user requests a resource at the SP and has no session there.
2. The SP redirects the browser to the IdP's single sign-on service with a SAML `<AuthnRequest>`.
3. The IdP checks for an existing session; if none, it challenges the user for credentials (and MFA).
4. The user authenticates and the IdP creates its own session.
5. The IdP builds an assertion, **digitally signs** it, places it in a SAML `<Response>` and returns it to the browser in an HTML form that posts to the SP's **assertion consumer service**.
6. The SP validates the signature (with the IdP's certificate from the federation metadata), checks the audience, time window and recipient, creates a local session and serves the resource.

The browser carries the messages; the SP and IdP never need to talk directly. The trust is the exchange of metadata and signing certificates set up in advance. **IdP-initiated** SSO starts at the IdP's portal instead.

### OAuth 2.0 and OpenID Connect

**OAuth 2.0 (RFC 6749) is an authorization framework**: it lets a **client** application obtain an **access token** to call an API (**resource server**) on behalf of the **resource owner** (the user), with the **authorization server** issuing the token after authenticating the user and obtaining consent. Classic example: a scheduling app gets permission to read your calendar without ever seeing your password. The token carries **scopes** (for example `calendar.read`).

- The access token says what the client may do; it is **not** proof to the client of who the user is. Using OAuth access tokens as a login mechanism is a known anti-pattern.
- The **authorization code grant** (with PKCE) is the recommended flow. The OAuth 2.0 Security Best Current Practice (RFC 9700, January 2025) says clients SHOULD NOT use the implicit grant and that the resource owner password credentials grant MUST NOT be used.

**OpenID Connect (OIDC)** is "a simple identity layer on top of the OAuth 2.0 protocol" (OpenID Connect Core 1.0). The client requests the `openid` scope and receives an **ID token**, a signed JSON Web Token (JWT) containing claims about the authenticated user. So: OAuth = authorization (delegated API access), OIDC = authentication on top of OAuth, SAML = authentication and attributes in signed XML assertions, common for enterprise web SSO.

### LDAP

The **Lightweight Directory Access Protocol** is a protocol for querying and modifying a **directory** (Active Directory, OpenLDAP), on TCP/UDP **389**, or **636** for LDAPS (LDAP over TLS); StartTLS upgrades a 389 connection to TLS. Applications can authenticate users by performing an LDAP **bind** with the user's credentials, and IdPs use the directory as their user store. That is why the objectives list it under SSO: LDAP itself is not a federation protocol, but it is often the directory that backs SSO. A simple bind sends the password in cleartext unless the connection is protected by TLS. **Kerberos** (TCP/UDP 88) provides SSO inside an Active Directory domain with tickets.

## Account types

| Type | What it is | Key controls |
|---|---|---|
| **User** | A standard account for one person's daily work | Least privilege, MFA, no admin rights |
| **Privileged: global** | Administrative rights across the whole environment or domain: Domain Admins, Entra Global Administrator, cloud root/owner | Separate admin account, phishing-resistant MFA, PAM vaulting, just-in-time elevation, admin workstations |
| **Privileged: local** | Administrator on one machine only | Unique random password per machine (Windows LAPS), remove users from local Administrators |
| **Service** | Used by an application or service, not a person | No interactive logon, managed passwords (gMSA, Domain 3), least privilege, monitored |
| **Third-party** | Vendors, contractors, partners, MSPs | Expiry date, sponsor, limited scope, MFA, monitored sessions |
| **Emergency access** (break-glass) | Highly privileged account kept for when normal admin access fails (IdP outage, MFA failure) | Long random credential stored securely (sealed or vaulted, split knowledge), excluded from policies that could lock it out, alert on every use, regular testing |

## Multifactor authentication

MFA combines factors from different categories: something you **know** (password, PIN), something you **have** (token, phone, smart card) and something you **are** (biometric). Two passwords are still one factor.

| Objective term | What it is | Phishing-resistant? |
|---|---|---|
| **Hard token** | A physical device: OTP key fob, smart card (PIV/CAC), FIDO2 security key | FIDO2 keys and smart cards with certificate authentication: **yes**. OTP fobs: no |
| **Soft token** | Software on a phone or computer: authenticator app generating TOTP codes, push approvals, platform authenticators | TOTP and push: no. Passkeys in a platform authenticator: yes |
| **Biometrics** | Fingerprint, face, iris, voice | SP 800-63B-4: biometrics SHALL only be used as part of MFA with a physical authenticator; comparison is probabilistic and biometrics are not secrets |
| **OTP** | One-time password: **HOTP** (RFC 4226, counter-based) or **TOTP** (RFC 6238, time-based, 30-second default step); also codes by SMS or email | No: the user types the code, so a phishing proxy can relay it |
| **Backup code** | Pre-generated single-use codes (NIST "look-up secrets") for when the primary factor is lost | No; store them securely |

**Phishing resistance.** SP 800-63B-4 states that authenticators requiring manual entry of an output (OTP and out-of-band codes) SHALL NOT be considered phishing-resistant, because the code is not bound to the session; phishing resistance requires cryptographic authentication with **channel binding** (client-authenticated TLS, as PIV/CAC smart cards use) or **verifier name binding** (WebAuthn/FIDO2, where the credential is tied to the site's domain). SMS through the public telephone network is NIST's one **restricted** authenticator. Push notifications are vulnerable to fatigue attacks; number matching reduces but does not remove that risk.

## Try it yourself

Any OS with a browser. Sign in to an account you own that supports SSO (for example a service offering "Sign in with" another provider) and read the consent screen: which scopes does it request? That is OAuth/OIDC. Then, on paper, draw the six-step SAML SP-initiated flow with the browser in the middle and label which messages are signed. Finally, list the MFA methods each of your own accounts offers and mark which are phishing-resistant.

## Key takeaways

- Provision from HR, remove old access on moves, disable immediately on leave; assign permissions to groups with least privilege.
- Identity proofing (SP 800-63A-4): resolution, evidence and attribute validation, verification, enrollment, fraud mitigation.
- SAML = signed XML assertions from IdP to SP (authentication, attribute, authorization decision statements). OAuth = authorization with access tokens and scopes. OIDC = identity layer (ID token JWT) on OAuth. LDAP = directory protocol (389/636) that often backs SSO.
- Account types: user, privileged (global, local), service, third-party, emergency access (break-glass, alert on use).
- MFA terms: hard token, soft token, biometrics, OTP (HOTP counter, TOTP time), backup codes. Only FIDO2/passkeys and smart cards are phishing-resistant.
