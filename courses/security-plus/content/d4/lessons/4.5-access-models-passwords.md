## Access control models

An access control model is the rule set that decides whether a subject (user, process) may perform an action on an object (file, record, network resource). The objectives list six.

| Model | Who decides | How access is granted | Example |
|---|---|---|---|
| **Discretionary (DAC)** | The object's **owner** | Owner grants rights to others at their discretion; NIST: "the owner can determine who should have access rights to an object and what those rights should be" | NTFS and Linux file permissions; sharing a document from your own drive |
| **Mandatory (MAC)** | A **central authority** via policy; users cannot change it | Labels: subject clearance compared with object classification. NIST: "access control policy decisions are made by a central authority, not by the individual owner" | Military classification (secret, top secret); SELinux type enforcement and MLS |
| **Role-based (RBAC)** | Administrators define roles | Permissions are attached to **roles**, users are assigned roles; NIST: "permitted actions on resources are identified with roles rather than with individual subject identities" | "Accounts Payable Clerk" role grants the AP application and share |
| **Rule-based** | Administrators define rules | Global **rules** evaluated for every request, regardless of who the user is | Firewall ACLs; "deny all logons from outside the country"; a NAC rule placing devices without EDR in quarantine |
| **Time-based** | Policy | Access allowed only during defined windows | Contractors may sign in 07:00-19:00 weekdays; a scheduled maintenance account |
| **Just-in-time (JIT)** | An approval workflow or PAM system | Privilege is granted **only when needed, for a limited time**, then removed automatically; no standing privilege | Admin requests Domain Admin for 2 hours via PAM with manager approval |

Related: **attribute-based access control (ABAC)**, which NIST describes as access mediated by attributes of subjects and objects (department, location, time, device health, data classification) evaluated by policy. ABAC can express role, rule and time conditions in one policy and is the model behind most Zero Trust and conditional access engines. It is not in the objective's list, but it explains how modern systems combine the others.

> **Watch out:** "Role-based" and "rule-based" share the initials RBAC. Role-based depends on *the user's job*; rule-based applies *the same rule to everyone* (for example a firewall rule). If the stem says the same restriction applies to all users based on a condition (address, time, device state), it is rule-based (or time-based if the condition is time).

> **Exam tip:** Owner shares a file with a colleague: DAC. Classification label and clearance, user cannot override: MAC. Permissions follow job function: role-based. Elevation for two hours with approval: just-in-time.

## Access management

**Authentication** proves identity (factors, lesson 4.5 part 1); **authorization** decides what the authenticated identity may do; **accounting** records what it did. Access management ties these together with policy.

**Policies** come in two kinds that map to Domain 1's control categories:

- **Logical/technical policies** are enforced by systems: conditional access rules (require MFA from outside the corporate network, block legacy authentication, require a compliant device), Group Policy password settings, firewall rules, session timeouts, account lockout thresholds.
- **Administrative/business policies** are written rules that people follow and managers enforce: the access control policy, acceptable use policy, separation of duties, approval requirements for privileged access, onboarding and offboarding procedures.

A business policy ("contractors may not access production data") is implemented by technical policy (a conditional access rule and group membership).

## Access review

An **access review** (recertification, attestation) asks owners or managers to confirm, at intervals, that each person's access is still needed:

1. Export current access: group memberships, application roles, privileged roles, service accounts, third-party accounts.
2. Send each list to the right reviewer (the user's manager for job access, the application or data owner for that resource).
3. Reviewers approve or revoke each item; no response is treated as revoke in strict programs.
4. Revocations are carried out and the evidence is retained for auditors.

Reviews find privilege creep, orphaned accounts of people who left, service accounts with no owner, and toxic combinations that break separation of duties. Privileged accounts are reviewed more often (for example quarterly) than standard access.

## Password concepts

### Passkeys and passwordless

A **passkey**, in the FIDO Alliance's definition, is an authentication credential based on FIDO standards that can be stored on a phone or computer or in a hardware security key, letting the user sign in with the same gesture used to unlock the device (biometric, PIN or pattern). Under the hood it is a **public/private key pair per site**: the private key stays on the authenticator; the website stores only the public key; at sign-in the authenticator signs a challenge, and WebAuthn binds the credential to the site's domain, so a phishing site on a different domain cannot use it. FIDO distinguishes **synced passkeys** (copied between a user's devices through a cloud service such as a platform credential manager) and **device-bound passkeys** (never leave one device, such as a FIDO security key). NIST SP 800-63B-4 accepts syncable authenticators but, because their private keys are exportable, not at AAL3.

**Passwordless** authentication removes the password entirely: passkeys, FIDO2 security keys, Windows Hello for Business, smart cards with PIN, and (weaker) magic links or push-only sign-in. A PIN that unlocks a local key never travels to the server, so it is not a shared secret in the way a password is.

### Password managers

A password manager generates and stores a unique, random password for every site, and autofills only on the matching domain (some protection against phishing). SP 800-63B-4 says verifiers SHALL allow password managers and autofill and SHOULD allow pasting. The risk is concentration: the vault needs a strong master password and MFA.

### Password best practices: the objectives' list versus current NIST guidance

The objectives list **length, complexity, reuse, expiration, age, compromised credential monitoring, account auditing** and **policy report**. Know what each setting means *and* what NIST SP 800-63B-4 (July 2025) now says, because traditional settings and current guidance disagree on two of them.

| Concept | Meaning | SP 800-63B-4 |
|---|---|---|
| **Length** | Minimum (and maximum) characters | SHALL require at least **15** characters for single-factor passwords (at least 8 when the password is used only as part of MFA); SHOULD allow at least 64; accept all printing ASCII, spaces and Unicode |
| **Complexity** | Required mix of upper, lower, digits, symbols | SHALL **NOT** impose composition rules. Users respond to them predictably (`Password1!`), so they add little strength |
| **Reuse** | Whether old passwords may be used again (Windows "Enforce password history") | Not a 63B-4 requirement; the blocklist rejects compromised and common passwords instead. Reuse *across sites* is the real danger, which password managers solve |
| **Expiration** | Maximum password age; forced periodic change | SHALL **NOT** require periodic changes; SHALL force a change when there is evidence of compromise |
| **Age** | Minimum password age: how long before a user may change it again | Not addressed by NIST. In Windows it stops users from cycling through history in minutes to get back to an old password |
| **Compromised credential monitoring** | Checking passwords against lists of breached, common or expected values, and watching for the organization's credentials in breach data | SHALL compare new passwords against a **blocklist** of commonly used, expected or compromised values and reject matches, telling the user why |
| **Account auditing** | Reviewing accounts and authentication events: inactive, never-used, shared, non-expiring, privileged | Supports detection of compromise and stale accounts |
| **Policy report** | A report showing the password policy in force and compliance with it (for example from a directory audit tool: accounts with password never expires, weak or blank passwords, reused hashes) | Evidence for auditors and a driver for fixes |

NIST also says: no password hints accessible to unauthenticated users, no knowledge-based security questions, and rate-limit failed attempts.

> **Exam tip:** If a question asks what *current NIST guidance* recommends, choose long passwords, blocklist checks, no forced periodic rotation and no composition rules. If it asks which *setting* stops users from immediately cycling back to an old password, the answer is **minimum password age** together with password history.

> **Real world:** Many compliance frameworks and older audit checklists still demand complexity and 90-day expiry. When they conflict with SP 800-63B-4, document the decision; moving to MFA and passkeys removes most of the argument.

## Try it yourself

Any OS. On Windows (Pro or Enterprise), run `secpol.msc` and read Account Policies > Password Policy: note the history, maximum age, minimum age, minimum length and complexity values, and decide which you would change to align with SP 800-63B-4 (on Home editions, `net accounts` in a command prompt shows the same values). On macOS or Linux, read `man pwpolicy` or `man pam_pwquality` respectively. Then classify five accounts you use by access model (who decided your access, and how?).

## Key takeaways

- DAC = owner decides; MAC = central labels and clearances; role-based = permissions via job roles; rule-based = same rules for everyone; time-based = windows; JIT = temporary privilege on request. ABAC combines attributes.
- Policies: logical/technical (enforced by systems) and administrative/business (written, enforced by people).
- Access reviews by managers and owners find privilege creep, orphans and toxic combinations.
- Passkeys are per-site FIDO key pairs, synced or device-bound, phishing-resistant; passwordless removes the shared secret.
- SP 800-63B-4: 15+ characters single-factor, no composition rules, no periodic rotation, blocklist compromised passwords, allow password managers and paste.
- Minimum password age plus history stops password cycling; compromised credential monitoring, account auditing and policy reports keep the policy honest.
