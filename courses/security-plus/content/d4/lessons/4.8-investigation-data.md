## Matching the question to the evidence

Objective 4.8 is a *use* objective: given an investigation question, pick the data source that answers it, read it, and keep it trustworthy. Start every investigation by writing the question ("did bob's account sign in from outside the country?", "what left srv01 last night?"), then go to the source that records that kind of event.

## Log and trace data types

| Type | What it records | Example questions | Example sources |
|---|---|---|---|
| **Access and accounting: logical** | Who accessed which system or resource, and what they did with it (AAA accounting) | Which files did alice open on the share? How long was the VPN session? | File access auditing, RADIUS/TACACS+ accounting, VPN session logs |
| **Access and accounting: physical** | Entry to buildings, rooms, racks | Was bob's badge used at the data center door at 02:10? | Badge/door controller logs, visitor logs, rack lock logs |
| **Device** | Events on network and security devices | When did the firewall config change? Which rule denied the traffic? | Firewall, router, switch, WAP, IPS logs (syslog) |
| **Server** | OS and service events on servers | Which service crashed? Who logged on interactively? | Windows event logs, Linux journal and `/var/log` |
| **Application** | Events inside an application | Which user exported 50,000 records? Which API key made the calls? | Web server access logs, application audit trails, database logs |
| **Authentication** | Logon successes and failures, MFA events, ticket requests | Was this spraying? Did the attacker pass MFA? | Domain controller events (4624, 4625, 4740, 4768/4771), IdP sign-in logs, RADIUS |
| **Communication** | Email, chat, voice and collaboration activity | Who received the phishing email and who clicked? | Mail gateway and message trace logs, collaboration audit logs, call detail records |
| **Audit** | Security-relevant changes and privileged actions, often required by regulation | Who added alice to Domain Admins? Who cleared the log? | Windows Security log (4720, 4728, 4732, 1102), Linux `auditd`, cloud control-plane audit logs |
| **Endpoint** | Process, file, registry and network activity on workstations and servers | What did the malicious document launch? | EDR telemetry, Sysmon, AV logs, process creation (4688) |
| **Network** | Traffic and connections | Did ws01 contact the C2 address? How much data left? | Firewall connection logs, NetFlow/IPFIX, DNS query logs, proxy logs, packet captures |
| **Metadata** | Data about data: who, when, where, how big, which device | Who authored this document? Where was this photo taken? Which servers relayed this email? | File system timestamps, document properties, EXIF in images, email headers, flow records |

Windows event IDs worth knowing (Microsoft documentation): **4624** successful logon, **4625** failed logon, **4740** account locked out, **4720** user account created, **4726** user account deleted, **4728** member added to a security-enabled *global* group (Domain Admins is one), **4732** member added to a security-enabled *local* group, **4672** special privileges assigned to a new logon (an administrator logged on), **4688** new process created, **1102** audit log cleared.

## Data sources beyond logs

- **Vulnerability scans:** was the exploited host vulnerable, and since when? Was the finding open past its deadline?
- **Automated reports:** scheduled outputs from security tools (weekly EDR summary, patch compliance report) that establish what was normal and when something changed.
- **NetFlow/IPFIX:** who talked to whom, when and how much, across the whole network and for long periods, without payload (lesson 4.4).
- **Surveillance footage:** confirms or contradicts physical access logs: did the person who badged in look like the badge holder? Tailgating shows up here and nowhere else.
- **Security tools:** SIEM, EDR, IDS/IPS, DLP, email gateway consoles: their alerts, timelines and stored telemetry.
- **Dashboards:** quick view of when a metric changed (spike in denied connections, sudden outbound volume) to frame the timeline.
- **Packet captures:** full content of specific traffic: the exact request, the payload, the file transferred. Often the only source that shows *what* was sent, if it was not encrypted.

> **Exam tip:** Badge log says bob entered the server room at 02:10 while bob's manager says he was on leave: check **surveillance footage**. The firewall shows 4 GB to an unknown IP but you need to know what the data was: **packet capture** (if one exists) or endpoint/DLP data; flows alone have no content.

## File and log integrity

Evidence is useful only if you can show it has not changed:

- **Hashing:** compute a cryptographic hash (SHA-256) of an image, file or log export at collection and again before analysis or presentation; matching hashes show integrity. SP 800-86 says to compute message digests of original and copied data and compare them.
- **Write blockers:** hardware or software that prevents writes to the source media while it is imaged (SP 800-86).
- **Log protection:** forward logs off the host in near real time to a central system the attacker cannot reach; restrict who can delete or edit logs; use append-only or immutable (WORM) storage; protect the transport (syslog over TLS); and keep time synchronized (NTP) so timelines line up.
- **File integrity monitoring (FIM):** hashes system and application files and alerts on changes (a modified `web.config`, a replaced system binary).
- Alert on signs of tampering: event 1102 (audit log cleared), logging services stopped, gaps in sequence numbers or time.

## System images

| Image | What it captures | When to use |
|---|---|---|
| **Memory dump** | Contents of RAM: running processes, network connections, loaded modules, decrypted data, encryption keys, injected code | First, before shutdown: fileless malware and keys exist only in memory |
| **Bit-level copy** (bit-stream image, forensic image) | Every bit of the storage media, including deleted files, free space and slack space (SP 800-86: "a bit-for-bit copy of the original media") | When evidence may be needed for prosecution or discipline, or deleted data matters |
| **Snapshot** | Point-in-time state of a virtual machine or volume (cloud or hypervisor), sometimes including memory | Fast capture of VMs and cloud instances; preserve state before changes; less forensic detail than a bit-level copy of physical media |

A **logical backup** (copying files and folders) misses deleted data and slack space, so it is not a substitute for a bit-level copy when deleted material matters.

**Order of volatility.** Collect the most volatile evidence first. RFC 3227 gives an example order: registers and cache; routing table, ARP cache, process table, kernel statistics and memory; temporary file systems; disk; remote logging and monitoring data; physical configuration and network topology; archival media. SP 800-86's recommended order for volatile OS data is network connections, login sessions, contents of memory, running processes, open files, network configuration and operating system time.

## Stakeholders

Investigations are not only technical. The objectives name three stakeholder groups:

- **Human Resources (HR):** involved whenever an employee is a suspect or a victim: insider investigations, policy violations, disciplinary action, interviews, and making sure the process follows employment law and internal policy.
- **Accounts:** in this context, the finance/accounting function (the course's reading of the term): needed when an incident involves payments, invoices or funds: business email compromise that redirected a supplier payment, fraudulent transfers, cost of the incident, insurance claims. They hold the payment records and can try to recall or freeze funds through the bank.
- **Legal:** decides on legal hold and preservation, privilege over investigation documents, notification obligations, law enforcement contact, and whether evidence will be needed in court (which drives chain of custody and forensic standards).

## Log-parsing techniques

Most investigation time goes into reducing large logs to the relevant lines.

- **Filter** by time window, host, user, event ID or keyword (`grep`, `Select-String`, SIEM search, Event Viewer filters).
- **Extract fields** with delimiters or regular expressions (`awk`, `cut`, regex named groups, SIEM field extraction).
- **Aggregate and count**: `sort | uniq -c | sort -rn` to find top sources; SIEM `stats count by src_ip`.
- **Normalize timestamps** to one time zone (UTC) before building a timeline.
- **Correlate** across sources by common keys: IP, username, hostname, session ID, time.
- **Build a timeline** of the incident from the parsed events.

Example: count failed SSH logons per source IP in an OpenSSH log where lines look like `Failed password for invalid user admin from 203.0.113.50 port 52144 ssh2`. The IP is the fourth field from the end (`port`, the port number and `ssh2` follow it):

```text
grep "Failed password" auth.log | awk '{print $(NF-3)}' | sort | uniq -c | sort -rn
```

On Windows PowerShell, a similar result for event 4625 comes from `Get-WinEvent -FilterHashtable @{LogName='Security'; Id=4625}` and grouping on the source network address property.

## Try it yourself

Any OS. Create a small text file with ten made-up log lines in the format above (mix of `Failed password` and `Accepted password`, three source addresses from 203.0.113.0/24). On Linux or macOS, run the pipeline above against your own file. On Windows, use PowerShell: `Select-String -Path .\auth.log -Pattern 'Failed password' | ForEach-Object { ($_.Line -split ' ')[-4] } | Group-Object | Sort-Object Count -Descending`. Then hash your file before and after adding one line (`Get-FileHash` on Windows, `shasum -a 256` on macOS, `sha256sum` on Linux) and see the hash change.

## Key takeaways

- Pick the log by the question: logical and physical access/accounting, device, server, application, authentication, communication, audit, endpoint, network, metadata.
- Other sources: vulnerability scans, automated reports, NetFlow/IPFIX, surveillance footage, security tools, dashboards, packet captures.
- Integrity: hashes at collection and later, write blockers, off-host and immutable logs, FIM, NTP.
- Memory dump first; bit-level copy captures deleted and slack space; snapshot captures VM or volume state. Follow the order of volatility.
- Stakeholders: HR for people issues, accounts (finance) for money flows, legal for holds, privilege and notification.
- Parse logs by filtering, extracting fields, counting, normalizing time and correlating into a timeline.
