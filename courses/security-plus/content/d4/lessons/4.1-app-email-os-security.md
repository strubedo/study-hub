## Repositories: secrets scanning

Developers accidentally commit API keys, cloud access keys, database passwords, private keys and tokens to source repositories. Domain 2 covered hardcoded secrets as a vulnerability (CWE-798); here is the control. **Secrets scanning** searches code for strings that match known credential formats or have high entropy:

- **Pre-commit hooks** on the developer's machine block the commit before the secret leaves the laptop.
- **Push protection** on the hosting platform rejects a push that contains a recognized secret.
- **Pipeline and scheduled scans** check every branch *and the full commit history*, because deleting a secret in a later commit leaves it in history.

When a secret is found in a pushed commit, assume it is compromised: **revoke or rotate it first**, then remove it from history and move it into a secrets manager (vault, cloud key management, CI/CD secret store). Rewriting history alone is not enough because clones, forks and caches may already hold it.

## Application security

**Input validation.** OWASP's Input Validation Cheat Sheet says to validate both *syntax* (type and format) and *semantics* (whether the value makes sense, such as an end date after a start date), to prefer allowlists of what is acceptable over denylists of "bad" strings, and to validate on the **server**, because client-side checks are trivially bypassed and exist only for user feedback. Input validation reduces injection risk but is not a substitute for parameterized queries and output encoding.

**Secure cookies.** Session cookies are credentials. The attributes, as OWASP's Session Management Cheat Sheet describes them:

| Attribute | Effect | Protects against |
|---|---|---|
| `Secure` | Browser sends the cookie only over HTTPS | Session ID disclosure to an on-path attacker over HTTP |
| `HttpOnly` | Scripts cannot read the cookie through `document.cookie` | Session theft through XSS |
| `SameSite=Strict` or `Lax` | Browser withholds the cookie on cross-site requests (`Lax` still sends it on top-level navigations with safe methods) | CSRF (defense in depth; still use anti-CSRF tokens) |
| `__Host-` name prefix (browser accepts it only with `Secure`, `Path=/` and no `Domain`) | Cookie bound to one host | Cookie injection from sibling subdomains |

OWASP's example: `Set-Cookie: __Host-SessionID=<value>; Secure; HttpOnly; SameSite=Strict; Path=/`. OWASP also says never to rely on the browser's default SameSite value and never to store session tokens in `localStorage`.

**Static code analysis (SAST).** Tools that analyze source or compiled code without running it, finding injection flaws, unsafe functions, hardcoded secrets and similar. OWASP lists their strengths (scale, early in the life cycle, pinpointing the file and line) and weaknesses (high numbers of false positives, difficulty with code that cannot be compiled, blind spots for configuration and runtime issues). Dynamic testing (DAST) runs the application and attacks it from outside; the two complement each other.

**Code signing.** The publisher signs the software (or script, driver, container image) with a private key whose certificate chains to a trusted CA. Before running or installing it, the OS or user verifies the signature, proving **who** published it and that it **has not been modified** since signing (integrity and authenticity, via the Domain 1 digital signature process). Code signing does *not* prove the code is safe: signed malware exists when a publisher's signing key or build system is compromised. Application allow lists that trust a publisher certificate depend on code signing.

## Email security: SPF, DKIM, DMARC, BIMI

Email has two "from" identities, and the difference is the key to this topic:

- **RFC 5321.MailFrom** (envelope sender, return path): given in the SMTP `MAIL FROM` command; where bounces go; invisible to most users.
- **RFC 5322.From** (header From): the address the recipient sees in the mail client.

**SPF (Sender Policy Framework, RFC 7208).** The domain owner publishes a TXT record listing which hosts may send for the domain. The receiver checks the connecting IP against the record for the **MAIL FROM** domain (and optionally the HELO name). SPF does **not** check the visible From header.

```text
example.com.  TXT  "v=spf1 ip4:198.51.100.0/24 include:_spf.mailer.example.net mx -all"
```

- Mechanisms: `all`, `include`, `a`, `mx`, `ptr` (RFC 7208: SHOULD NOT be published), `ip4`, `ip6`, `exists`; modifiers `redirect` and `exp`.
- Qualifiers: `+` pass (the default if none is written), `-` fail, `~` softfail, `?` neutral. `-all` at the end means "everything not listed fails".
- Results: none, neutral, pass, fail, softfail, temperror, permerror.
- **The 10-lookup limit:** the terms that cause DNS queries (`include`, `a`, `mx`, `ptr`, `exists` and the `redirect` modifier) are limited to **10** during evaluation, counting nested includes; exceeding it MUST return **permerror**. `ip4`, `ip6` and `all` do not count. A domain must not publish more than one SPF record (that is also a permerror).
- Weakness: forwarding breaks SPF because the forwarder's IP is not in the original domain's record.

**DKIM (DomainKeys Identified Mail, RFC 6376).** The sending system signs selected **header fields and the body** with a private key and adds a `DKIM-Signature` header. The receiver fetches the public key from DNS at `<selector>._domainkey.<domain>` and verifies.

```text
DKIM-Signature: v=1; a=rsa-sha256; d=example.com; s=sel2026; c=relaxed/relaxed;
    h=from:to:subject:date:message-id; bh=<body hash>; b=<signature>
```

`d=` is the signing domain, `s=` the selector (lets a domain run several keys, for example one per mail vendor), `h=` the signed headers (the From header MUST be signed), `bh=` the body hash and `b=` the signature. RFC 8301 updated the algorithms: `rsa-sha1` MUST NOT be used for signing, keys MUST be at least 1024 bits and SHOULD be at least 2048; RFC 8463 added `ed25519-sha256`. DKIM survives forwarding as long as the signed content is not changed; mailing lists that modify the subject or body break it.

**DMARC (RFC 7489, obsoleted in May 2026 by RFC 9989; see the note below).** Published at `_dmarc.<domain>`. A message passes DMARC if **SPF or DKIM passes and the passing domain is aligned with the RFC 5322.From domain**. Alignment is **relaxed** by default (same organizational domain: `bounce.example.com` aligns with `example.com`) or **strict** (`aspf=s`, `adkim=s`: exact match).

```text
_dmarc.example.com.  TXT  "v=DMARC1; p=quarantine; sp=reject; adkim=r; aspf=r; rua=mailto:dmarc-agg@example.com; ruf=mailto:dmarc-forensic@example.com"
```

- `p=` policy for the domain: `none` (monitor only), `quarantine` (treat as suspicious, usually spam folder), `reject` (reject, ideally during the SMTP transaction).
- `sp=` policy for subdomains (defaults to `p`).
- `rua=` where to send **aggregate** reports (daily XML summaries by source IP and result); `ruf=` where to send **failure** (forensic) reports about individual messages.
- `pct=` the percentage of failing mail the policy applies to (default 100 in RFC 7489; RFC 9989 marks the tag historic).

DMARC is what finally ties authentication to the address users see: SPF can pass for an attacker's own envelope domain and DKIM can pass for an attacker's own `d=` domain, but neither will be *aligned* with your From domain.

> **Real world:** DMARC was revised as **RFC 9989** (Standards Track, May 2026), which obsoletes RFC 7489, with aggregate and failure reporting moved to RFC 9990 and RFC 9991. It keeps `p=none/quarantine/reject`, alignment, `rua` and `ruf`, makes `pct`, `rf` and `ri` historic, adds a `t=y` test-mode flag and an `np=` policy for non-existent subdomains, and replaces the public suffix list with a DNS "tree walk" to find the organizational domain. The exam objectives were written against the familiar tags; expect `p=`, `sp=`, `rua=` and alignment.

**BIMI (Brand Indicators for Message Identification).** Lets a brand's logo appear next to authenticated mail in supporting mailbox providers. The BIMI Group's implementation guide requires the domain's DMARC policy to be **at enforcement** (`p=quarantine` or `p=reject`, including subdomains, and not `pct` below 100), a logo in SVG Tiny Portable/Secure format and a TXT record such as:

```text
default._bimi.example.com.  TXT  "v=BIMI1; l=https://example.com/logo.svg; a=https://example.com/vmc.pem"
```

The optional `a=` tag points to a **Verified Mark Certificate (VMC)**, which requires a registered trademark, or a **Common Mark Certificate (CMC)**, for logos that are not trademarked, issued by a Mark Verifying Authority. Many mailbox providers display logos only with a certificate. BIMI adds no authentication of its own; it rewards domains that already enforce DMARC.

**Reading results.** Receivers record their verdicts in the `Authentication-Results` header (RFC 8601), added at the top of the message:

```text
Authentication-Results: mx.example.org;
    spf=pass smtp.mailfrom=bounce.example.com;
    dkim=pass header.d=example.com header.s=sel2026;
    dmarc=pass header.from=example.com
```

## Operating system security

**Group Policy** applies settings to Windows computers and users in an Active Directory domain through Group Policy Objects (GPOs): password and lockout policy, audit policy, user rights, firewall rules, AppLocker/App Control, software restriction, drive mappings, and the Microsoft security baselines. Microsoft documents the processing order as **local GPO, then GPOs linked to the site, the domain, then OUs** (parent OU before child). Later GPOs override earlier ones on conflict, so the closest OU usually wins, with two exceptions: **Block Inheritance** on a domain or OU stops higher-level GPOs from applying, and an **Enforced** link cannot be blocked and wins over lower-level conflicting settings. (Domain account password policy comes from GPOs linked at the domain level; fine-grained password policies are the per-group exception.) `gpupdate /force` refreshes policy; `gpresult /r` shows what applied.

**SELinux (Security-Enhanced Linux).** Red Hat's documentation describes standard Linux permissions as discretionary access control (DAC) and SELinux as **mandatory access control (MAC)**: every process and file has a label (`user:role:type:level`, for example `system_u:object_r:httpd_sys_content_t:s0`), and the policy decides which process types may access which object types. Even root cannot override it. Points to know:

- Modes: **enforcing** (default and recommended; denies and logs), **permissive** (logs AVC denials but does not deny; for troubleshooting), **disabled**. `getenforce` shows the mode; `setenforce 0` switches to permissive until reboot; `/etc/selinux/config` sets it persistently.
- The default policy on RHEL is the **targeted** policy, which confines selected services (web server, DNS, SSH and others).
- SELinux rules are checked **after** DAC: if file permissions already deny access, SELinux is never consulted.
- Denials appear as AVC messages in the audit log. The usual fix for a web server that cannot read its files is a wrong file label: correct it with `semanage fcontext` and `restorecon`, or toggle a documented boolean with `setsebool -P`, **not** by disabling SELinux.

## Try it yourself

Paper or any OS. Write the DNS TXT records for a fictional domain `example.com` that sends from its own servers at 198.51.100.0/24 and through one vendor (`include:_spf.vendor.example.net`): an SPF record ending in `-all`, a DKIM record name for selector `s2026`, a DMARC record starting at `p=none` with aggregate reports, and the version you would publish after a month of clean reports. Count the DNS-querying terms in your SPF record. To read real results, open any email you received in your mail client and view the original message or headers (Gmail: "Show original"; Outlook: message properties or "View source"); find the `Authentication-Results` header and identify the SPF, DKIM and DMARC verdicts and which domains they apply to.

## Key takeaways

- Secrets scanning in pre-commit, push and history; a leaked secret is revoked first, then removed.
- Validate input on the server with allowlists; cookies get `Secure`, `HttpOnly` and `SameSite`; SAST finds flaws without running code (with false positives); code signing proves publisher and integrity, not safety.
- SPF authorizes sending IPs for the envelope (MAIL FROM) domain, 10 DNS-querying terms maximum (else permerror). DKIM signs headers and body; key at `selector._domainkey.domain`.
- DMARC passes when SPF or DKIM passes *and aligns* with the visible From domain; `p=none/quarantine/reject`, `rua` aggregate, `ruf` failure reports. RFC 9989 (2026) now obsoletes RFC 7489.
- BIMI shows a logo only for DMARC at enforcement; VMC (trademark) or CMC.
- Group Policy order: local, site, domain, OU; Enforced beats Block Inheritance. SELinux is MAC with labels; enforcing/permissive/disabled; fix labels, do not disable it.
