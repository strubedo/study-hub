## What gets monitored

Objective 4.4 groups monitoring targets into three:

- **Systems:** servers, workstations, mobile devices: CPU, memory, disk, services, logons, process creation, security agent health, configuration drift.
- **Applications:** application and web server logs, error rates, authentication and authorization events within the app, API usage, transaction anomalies (for example a user exporting 100 times the usual number of records).
- **Infrastructure:** routers, switches, firewalls, wireless controllers, load balancers, hypervisors, cloud control planes: interface status and utilization, routing changes, configuration changes, denied traffic, VPN sessions.

Security monitoring and operations monitoring overlap: a sudden CPU spike may be a runaway job or a cryptominer; a link at 100 % may be a backup or exfiltration.

## Activities

| Activity | What it means | Security point |
|---|---|---|
| **Log aggregation** | Collecting logs from many sources into one place (SIEM, log platform), parsing them into common fields and normalizing time | Correlation is impossible when logs stay on each device; forwarding off the host in near real time also protects logs from an attacker who clears local logs |
| **Alerting** | Rules or analytics raise an alert when conditions match | Alerts must reach a person or a playbook with enough context to act |
| **Scanning** | Scheduled vulnerability and configuration compliance scans (lesson 4.3) | Results feed the same platform so a vulnerable host with suspicious activity stands out |
| **Archiving** | Moving older logs to cheaper storage while keeping them retrievable | Retention periods come from policy, regulation and investigation needs (lesson 4.8); archives must stay integrity-protected |
| **Reporting** | Periodic summaries: alert volumes, top sources, compliance status, trends | Turns monitoring into evidence for management and auditors |
| **Alert tuning** | Adjusting rules to reduce false positives without creating false negatives | The goal is alerts that are worth investigating |

### Alert tuning

An untuned SIEM produces thousands of alerts a day; analysts start ignoring them (alert fatigue), and the real one is missed. Tuning techniques:

- **Scope exceptions narrowly:** exclude one known service account from one rule, or one backup server during its backup window, rather than disabling the rule for everyone.
- **Adjust thresholds** using a baseline: "10 failed logons in 5 minutes" instead of "1 failed logon".
- **Correlate** several weak signals into one stronger alert (failed logons followed by a success from a new country).
- **Enrich** alerts with asset criticality, user role and threat intelligence so severity reflects context.
- **Review regularly:** every suppression should have an owner and a review date, and rules should be tested (for example by simulating the technique) so tuning has not created a blind spot.

> **Exam tip:** A rule that fires every night on a legitimate job is a **false positive** problem; tune it with a narrow exception or threshold. Deleting the rule entirely creates a **false negative** risk. A real attack that produced no alert is a false negative.

## Tools

| Tool | What it does | Where it sits |
|---|---|---|
| **Benchmarks** | Published secure-configuration standards (CIS Benchmarks, DISA STIGs, vendor baselines). Scanners check systems against them | Applied to hosts and devices; checked by compliance scans |
| **Agents / agentless** | Agent: software on the host that collects and forwards data, works off-network, sees local detail. Agentless: remote collection via APIs, WMI/WinRM, SSH, SNMP, syslog, flow export; nothing to install but less depth and depends on network reachability | Agents on endpoints and servers; agentless for network devices, appliances, cloud APIs |
| **SIEM** (security information and event management) | Aggregates, normalizes, correlates and stores logs; alerting, dashboards, search, reporting, retention | Central platform fed by every source |
| **Antivirus** | Detects and quarantines known malware; its detections are log events too | Endpoints, mail and file servers, gateways |
| **DLP** | Detects sensitive data movement; its alerts feed the SIEM | Network, endpoint, cloud (lesson 4.1) |
| **Vulnerability scanners** | Identify vulnerabilities and misconfigurations | Network-based or agent-based |
| **Orchestration** (SOAR) | Runs automated playbooks across tools: enrich, contain, ticket (lesson 4.6) | Integrates with SIEM, EDR, firewall, email, ticketing |
| **Packet analyzer** | Captures and decodes full packets (Wireshark, tcpdump) for deep troubleshooting and forensics | On a host, a mirrored switch port or a TAP |

## Automated alerts

Alerts should go where action happens: a SIEM incident queue, a ticketing system, chat or paging for critical issues, or straight to a SOAR playbook. Good automated alerts carry the evidence (raw events, affected host and user, asset owner) and a severity, and are deduplicated so one incident does not page someone 500 times. Network devices also generate their own automated alerts: SNMP traps or informs, syslog messages at a chosen severity, and threshold alerts from a network management system.

## Port mirroring

To give an IDS, packet analyzer or network detection tool a copy of traffic, a switch can **mirror** one or more ports or VLANs to a monitoring port. Cisco calls this **SPAN** (Switched Port Analyzer), with **RSPAN** carrying the copy across a dedicated VLAN to another switch and **ERSPAN** encapsulating it in GRE across a routed network. Other vendors use "port mirroring" (FortiSwitch and most others).

Limits of mirroring: the switch may drop mirrored packets when the destination port is oversubscribed (mirroring two 1 Gbit/s full-duplex ports can generate up to 4 Gbit/s of copies), some switches do not copy malformed frames or certain control traffic, and mirroring adds load to the switch. A **network TAP** is a passive hardware device that copies every frame on a link, including errors, without depending on switch resources; it is preferred for forensics and high-value links. Either way, the monitoring device is out of band, which is why it can detect but not block.

## Dashboards

Dashboards present live and summarized data: alert counts by severity, top talkers, failed logons by country, vulnerability counts by business unit, patch compliance percentages, EDR health. Dashboards serve different audiences: an analyst's dashboard shows what to investigate now; a management dashboard shows trends and risk posture. A dashboard is a data source in investigations too (lesson 4.8), for example to see when a spike began.

## Network management systems

A **network management system (NMS)** monitors the availability and performance of infrastructure: it polls devices with SNMP, receives traps and syslog, collects flow data, discovers topology, graphs interface utilization and alerts when a device or link goes down or crosses a threshold. Examples range from open-source tools to commercial suites; FortiManager, Panorama and Cisco Catalyst Center add central configuration management for their own platforms. From a security perspective an NMS gives you:

- An inventory of network devices and interfaces (asset management, lesson 4.2).
- Configuration backup and change detection (an unexpected config change on fw01 is a security event).
- Baselines of normal traffic, so anomalies stand out.

The NMS itself is a high-value target: it holds SNMP credentials and often device admin credentials, so it belongs in a protected management network with strong authentication.

## Try it yourself

On any OS, open the built-in log viewer and practice tuning on paper. Windows: Event Viewer > Windows Logs > System and Security. macOS: the Console app. Linux: `journalctl -p warning -b` (show warnings and above since boot; see `man journalctl`). Pick three recurring events and decide for each: would you alert on it, and if so with what threshold or exception? Write the rule in plain words ("alert when more than 10 failed logons for one account in 5 minutes, except account svc-backup on srv01 between 01:00 and 02:00").

## Key takeaways

- Monitor systems, applications and infrastructure; the same signal may be operational or security.
- Activities: aggregation (centralize and normalize), alerting, scanning, archiving (retention), reporting, alert tuning.
- Tune with narrow exceptions, thresholds and correlation; never "fix" noise by disabling detection wholesale.
- Tools: benchmarks, agents vs agentless, SIEM, AV, DLP, vulnerability scanners, orchestration (SOAR), packet analyzers.
- Port mirroring (SPAN/RSPAN/ERSPAN) copies traffic to out-of-band sensors and can drop packets under load; a TAP copies everything passively.
- Dashboards show status and trends; an NMS polls and receives SNMP, syslog and flows, and must itself be protected.
