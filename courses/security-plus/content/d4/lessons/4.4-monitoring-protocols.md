## Four protocols, four jobs

| Protocol | Carries | Question it answers |
|---|---|---|
| **NetFlow / IPFIX** | Flow records (metadata about conversations) | Who talked to whom, when, how much? |
| **SNMP** | Device status, counters, configuration values, traps | Is the device up, how busy is it, did something change? |
| **syslog** | Event messages from devices and hosts | What happened, at what severity? |
| **SCAP** | Machine-readable security content and results | Is this system configured and patched to the benchmark? |

## NetFlow and IPFIX

A router, switch or firewall that exports flows watches packets, groups them into **flows** and sends a summary record to a **collector** when the flow ends or times out. RFC 3954 (NetFlow version 9) defines a flow as "a unidirectional sequence of packets with some common properties that pass through a network device", and lists typical record contents: IP addresses, packet and byte counts, timestamps, type of service, application ports, and input and output interfaces.

- **NetFlow v5** is the older fixed-format IPv4 export. **NetFlow v9** (RFC 3954, Cisco, Informational) introduced **templates**, so the exporter describes which fields it sends.
- **IPFIX** (IP Flow Information Export, RFC 7011) is the IETF standard built on v9: its message header version number is 10 (`0x000a`), which RFC 7011 describes as one more than the NetFlow v9 version. IPFIX can run over SCTP, TCP or UDP; collectors listen on port **4739** by default (4740 for TLS/DTLS).
- NetFlow has no IANA-registered port; collectors are configured to whatever port the exporters use (UDP 2055 and 9995/9996 are common conventions).
- **sFlow** (UDP 6343) is a different, sampling-based technology often found on switches.

**Flows versus packet capture.** Flow records contain no payload. They show that 10.10.20.15 sent 4.2 GB to 203.0.113.77 on TCP 443 between 02:10 and 02:55, but not what was sent. Packet capture (pcap) records the full packets, including payload (readable unless encrypted), but is huge and usually covers only short periods or specific links.

| Need | Use |
|---|---|
| Spot exfiltration volume, beaconing, scanning, unusual destinations across the whole network for months | NetFlow/IPFIX |
| See the exact HTTP request, the malware download, the DNS query content | Packet capture (port mirror or TAP, packet analyzer) |

Flow data is also sampled on some high-speed devices (for example one packet in 1,000), so small flows may be missed or byte counts estimated.

## SNMP

The Simple Network Management Protocol lets a **manager** (NMS) read and write values on an **agent** (the device), organized in a **MIB** (management information base) and identified by **OIDs**. Operations: Get, GetNext, GetBulk, Set, and notifications sent by the agent: **traps** (unacknowledged) and **informs** (acknowledged).

| Port (IANA) | Use |
|---|---|
| UDP **161** | Agent listens: manager polls with Get/Set |
| UDP **162** | Manager listens: agent sends traps and informs |
| 10161 / 10162 | SNMP over TLS (TCP) or DTLS (UDP) (RFC 6353), agent and trap respectively |

**Versions:**

- **SNMPv1 and v2c** authenticate with a **community string** sent in cleartext. Anyone who sniffs it can read the device, and a read-write community lets them change configuration. Default communities `public` and `private` are well known.
- **SNMPv3** (RFC 3411-3418) adds the **User-based Security Model** (USM, RFC 3414) with per-user authentication and privacy (encryption), and the **View-based Access Control Model** (VACM, RFC 3415) to limit which parts of the MIB each user can see. RFC 3411 defines three security levels:

| Security level | Authentication | Encryption |
|---|---|---|
| `noAuthNoPriv` | No (username only) | No |
| `authNoPriv` | Yes (HMAC) | No |
| `authPriv` | Yes | Yes |

RFC 3414 originally specified HMAC-MD5-96 and HMAC-SHA-96 for authentication and DES for privacy; later RFCs added AES (RFC 3826) and HMAC-SHA-2 (RFC 7860). In practice, configure **SNMPv3 with `authPriv`, SHA-2 and AES**, use read-only views, restrict which source addresses can poll (ACL or trusted hosts), and disable v1/v2c.

## syslog

Syslog (RFC 5424, the current format; the older BSD format is described in RFC 3164) sends event messages from a device to a collector. Every message starts with a **PRI** value in angle brackets, computed as:

**PRI = facility × 8 + severity**

| Severity | Keyword | Meaning (RFC 5424) |
|---|---|---|
| **0** | Emergency | System is unusable |
| **1** | Alert | Action must be taken immediately |
| **2** | Critical | Critical conditions |
| **3** | Error | Error conditions |
| **4** | Warning | Warning conditions |
| **5** | Notice | Normal but significant condition |
| **6** | Informational | Informational messages |
| **7** | Debug | Debug-level messages |

Lower number = more severe. A device configured to log "at level 4" sends severities 0 through 4. Facilities range from 0 (kernel) to 23; codes 4 and 10 are security/authorization, 13 log audit, and **16-23 are local0 to local7**, which network devices commonly use. Example: `<190>` = 190 ÷ 8 = 23 remainder 6, so facility local7, severity 6 (Informational). RFC 5424's own example `<34>1 ...` is facility 4 (security/authorization), severity 2 (Critical); the `1` after the bracket is the syslog protocol version.

**Transport:**

| Transport | Port | Notes |
|---|---|---|
| UDP (RFC 5426) | **514** | Traditional; no delivery guarantee, no encryption, easy to spoof |
| TLS (RFC 5425) | TCP **6514** | Encrypted and authenticated; the recommended option for security logs |
| TCP (RFC 6587, Historic) | No port assigned for this framing | Widely used in practice, often on TCP 514 (which RFC 6587 notes is actually assigned to the `shell` service) or 601 (registered for the older BEEP-based reliable syslog, RFC 3195) |

Syslog over UDP can lose messages during exactly the events you most need (floods, link congestion), which is why critical sources should use TCP or TLS and why log gaps are themselves worth alerting on. Time synchronization (NTP) on every source is essential for correlation.

## SCAP

The **Security Content Automation Protocol** (NIST SP 800-126 Rev. 3, SCAP version 1.3) is a suite of specifications that let tools exchange security checklists and results in standard, machine-readable form. SP 800-126 Rev. 3 lists twelve component specifications in five categories:

| Category | Specifications |
|---|---|
| Languages | **XCCDF** (Extensible Configuration Checklist Description Format: the checklist/benchmark and its rules), **OVAL** (Open Vulnerability and Assessment Language: the technical tests), **OCIL** (Open Checklist Interactive Language: questions for things a tool cannot check) |
| Reporting formats | **ARF** (Asset Reporting Format), **Asset Identification** |
| Identification schemes | **CPE** (platform names), **SWID** tags (software identification), **CCE** (configuration item IDs), **CVE** (vulnerability IDs) |
| Measurement and scoring | **CVSS**, **CCSS** (Common Configuration Scoring System) |
| Integrity | **TMSAD** (Trust Model for Security Automation Data) |

How it is used: a benchmark (for example a CIS or DISA STIG benchmark published as SCAP content) is an XCCDF document whose rules point to OVAL checks. A SCAP-validated scanner (OpenSCAP's `oscap` on Linux, commercial scanners on Windows) evaluates the system, producing XCCDF/ARF results that any compliant tool can read. NIST's National Vulnerability Database supplies the reference data (CVE, CPE dictionaries). This is how "check 5,000 servers against the hardening benchmark every night" becomes automated.

> **Exam tip:** SCAP = automated *configuration and vulnerability compliance checking* with standard content. XCCDF is the checklist, OVAL the test logic, CVE/CPE/CCE the identifiers, CVSS the scores.

## Try it yourself

Paper or any OS. (1) Decode these PRI values into facility and severity: `<13>`, `<86>`, `<134>`, `<187>`. (Answers: user/notice; facility 10 authpriv/informational; local0/informational; local7/error.) (2) Write an SNMPv3 design for 20 switches on paper: which security level, which algorithms, which manager addresses may poll, which view a read-only monitoring user gets. (3) On Linux or macOS, read `man logger` and note how to set facility and priority on a test message; on Windows, read about `eventcreate` in Microsoft's documentation. Do not run scans or flow collectors on networks you do not own.

## Key takeaways

- NetFlow/IPFIX: unidirectional flow metadata (addresses, ports, bytes, times, interfaces), no payload. IPFIX = RFC 7011, version 10, port 4739. Packet capture has payload but limited scope.
- SNMP: agent UDP 161, traps/informs UDP 162. v1/v2c community strings are cleartext; SNMPv3 USM gives `authPriv` (authentication + encryption), VACM limits views.
- syslog severities 0 Emergency to 7 Debug; PRI = facility × 8 + severity; local0-local7 = 16-23. UDP 514; TLS 6514 for confidentiality and reliable delivery.
- SCAP (SP 800-126 Rev. 3): XCCDF checklists, OVAL tests, OCIL questions, ARF results, CPE/SWID/CCE/CVE identifiers, CVSS/CCSS scores, TMSAD integrity.
