## Vulnerabilities and attack surface

The **attack surface** is the sum of all the points where an attacker could try to get in or get data out: every open port, exposed service, application, account, device, API, wireless link and person. Reducing it (fewer services, fewer accounts, fewer exposed interfaces) removes vulnerabilities before anyone has to find them. This lesson covers weaknesses in systems, applications and code; the next covers identities, devices, wireless, cloud and AI-related surfaces.

## Lifecycle and management weaknesses

| Term | Meaning | Why it is a vulnerability |
|---|---|---|
| **Unsupported products** | The vendor has ended support (end of life / end of support): no more security patches | Every new flaw is permanent. Typical examples are an old OS still running a line-of-business app, or a switch past its end-of-support date |
| **Unpatched systems** | A patch exists but has not been applied | The patch itself tells attackers what to exploit; attacks against newly patched flaws often start within days |
| **Obsolete systems** | Outdated technology that has been superseded, may still be supported but no longer fits current security expectations | Old protocols, weak crypto, no modern security features (secure boot, MFA support, logging); spare parts and expertise disappear |
| **Unmanaged systems** | Devices not in the inventory or not under central management (no agent, no configuration management, no logging) | Nobody patches, monitors or hardens what nobody knows about. Unmanaged systems are frequently also unpatched |

> **Exam tip:** Unsupported means *no patch will ever come*: the fix is to replace, isolate or apply compensating controls (Domain 1). Unpatched means *a patch exists*: the fix is to apply it. If the scenario says the vendor stopped releasing updates, choose unsupported.

## Ports and services

Every listening port is attack surface. Typical findings:

- Unnecessary services left enabled by default (a web admin interface, a print spooler on a server that never prints, UPnP on a router).
- Insecure cleartext protocols: Telnet (23), FTP (21), HTTP (80) for logins, SNMPv1/v2c with default community strings, LDAP without TLS.
- Management and database ports exposed to the internet: SSH, RDP (3389), SMB (445), database listeners.
- Services running with excessive privileges.

The fix is hardening: disable what is not needed, replace insecure protocols with secure ones (SSH, SFTP, HTTPS, SNMPv3, LDAPS), restrict reachable ports with host and network firewalls, and scan regularly for drift (Domain 4).

## Applications

### Race conditions: time-of-check to time-of-use (TOC/TOU)

A **race condition** is a flaw whose outcome depends on the timing of events the program does not control. The classic security case is **TOCTOU**, which MITRE's CWE-367 describes as: the product checks the state of a resource before using it, but the state can change between the **check** and the **use** in a way that invalidates the check.

CWE's own example: a privileged program calls `access()` to check whether the user may write to a file, then calls `fopen()` on the same filename. Between the two calls, the attacker replaces the file with a **symbolic link** to a file they could not normally modify, and the program writes to it with root privileges.

The same pattern appears outside file systems:

- An application checks an account balance (time of check), then debits it (time of use); two simultaneous withdrawals both pass the check.
- A coupon is checked for "not yet used" by two parallel requests before either marks it used.

Fixes: make check and use a single atomic operation (open the file once and check the open handle; use database transactions and locks), avoid checking by name and then using by name, and drop privileges rather than checking permissions on the user's behalf.

### Malicious update

A **malicious update** is a software update that the user or system trusts because it comes from the legitimate update channel, but which contains malicious code. It can result from a compromised vendor build system or signing key, a compromised update server, an attacker taking over an abandoned open-source package or browser extension, or a hijacked developer account. Because it is signed or delivered by a trusted mechanism, allow lists and users accept it. Controls: verify signatures and hashes, use staged rollouts and monitoring after updates, pin and review dependency versions, and favour vendors with a secure software development process (supply chain, lesson 2.3).

## Code

**Hardcoded secrets.** Passwords, API keys, tokens, private keys or connection strings written into source code, scripts, configuration files or container images (CWE-798, Use of Hard-coded Credentials). Anyone who can read the code, decompile the binary or browse the repository gets the secret, and the secret is usually shared by every installation and hard to rotate. Fix: store secrets in a secrets manager or vault, inject them at run time, scan repositories for secrets (Domain 4) and rotate anything that was ever committed. Deleting a secret in a later commit does not remove it from version history.

**Unsafe exception handling.** How code behaves when something goes wrong. OWASP added **A10:2025 Mishandling of Exceptional Conditions** to its Top 10, covering improper error handling, logical errors and failing open. Two failure modes matter:

- **Leaking information:** detailed error pages and stack traces reveal file paths, framework versions, SQL queries or credentials (CWE-209, Generation of Error Message Containing Sensitive Information). Show users a generic message and log the detail server-side.
- **Failing open:** when an error occurs, the code falls back to a less secure state (CWE-636, Not Failing Securely, alternate term "Failing Open"), for example an authorization check that throws an exception and the code's catch block lets the request continue, or a license or signature check that is skipped when its server is unreachable. Security checks should fail closed: deny by default when something unexpected happens.

> **Watch out:** "Fail open" versus "fail closed" also describes devices (Domain 3 failure modes): a firewall that passes all traffic when its inspection engine crashes is failing open. In code, unsafe exception handling is the software version of the same mistake.

## Operating system (OS)-based vulnerabilities

Kernel and driver flaws that allow privilege escalation, insecure default configurations, unnecessary components installed by default, excessive local admin rights, weak file permissions (world-writable system paths, misconfigured SUID binaries on Linux) and missing OS updates. Because everything runs on the OS, an OS vulnerability undermines every control above it. Use hardening baselines (Domain 4), timely patching and least privilege.

## Virtualization vulnerabilities

- **VM escape:** code in a guest VM exploits a hypervisor flaw to run on the host or reach other guests, breaking the isolation that virtualization promises.
- **Resource reuse:** memory or disk released by one VM and allocated to another without being cleared can leak data across tenants.
- **VM sprawl:** VMs created and forgotten, never patched or monitored (the virtual form of unmanaged systems).
- **Management plane:** the hypervisor console or cloud control plane controls every VM; compromised admin credentials there are worse than any single VM compromise.
- **Snapshots and images:** snapshots preserve memory and disk, including secrets, and old templates spread old vulnerabilities to every new VM.

## Zero-day

A **zero-day** vulnerability is one that is unknown to the vendor, or known but without an available patch, when it is exploited; defenders have had "zero days" to fix it. NIST defines a zero-day attack as one that exploits a previously unknown hardware, firmware or software vulnerability. No signature or patch exists, so defense relies on layered controls: least privilege, segmentation, exploit protection, application allow listing, behavior-based detection (EDR) and fast incident response. Once a patch is released, the vulnerability is no longer a zero-day; systems that have not applied it are simply unpatched.

> **Exam tip:** "The vendor has not released a fix and attackers are already exploiting it" means zero-day. "The vendor released a fix last month and we have not installed it" means unpatched. "The vendor will never release a fix" means unsupported.

## Cryptographic vulnerabilities

Domain 1 covers algorithms; as vulnerabilities, look for:

- Weak or deprecated algorithms and protocols: DES, 3DES, RC4, MD5 or SHA-1 for signatures, SSL and TLS 1.0/1.1, small RSA keys.
- Poor implementation: ECB mode, reused nonces or IVs, home-grown crypto, weak random number generation, missing certificate validation.
- Poor key management: keys stored with the data, hardcoded keys, keys never rotated, private keys in public repositories.
- Expired, self-signed or mis-issued certificates that train users to click through warnings.
- Downgrade susceptibility: servers that still accept old protocol versions let an on-path attacker force a weak connection (lesson 2.5).

## Try it yourself

Works on any OS. List the listening ports on your own computer with the built-in tool: on Windows `netstat -ano | findstr LISTENING` (Command Prompt), on macOS `lsof -nP -iTCP -sTCP:LISTEN`, on Linux `ss -tlnp`. For each port, identify the program and decide whether it needs to listen at all. Paper exercise: for each scenario, write unsupported, unpatched, obsolete, unmanaged or zero-day: (1) a NAS whose vendor stopped firmware updates; (2) a laptop missing last month's OS update; (3) a Raspberry Pi someone plugged into the server VLAN; (4) a flaw exploited before the vendor knew about it.

## Key takeaways

- Unsupported = no patch will come; unpatched = patch exists but not applied; obsolete = superseded technology; unmanaged = not inventoried or centrally managed.
- Every unnecessary port and service is attack surface; replace cleartext protocols.
- TOC/TOU: the state changes between the check and the use (CWE-367); fix with atomic operations.
- Malicious updates abuse trusted, often signed, update channels.
- Hardcoded secrets live forever in history: vault them, scan for them, rotate them.
- Unsafe exception handling leaks details or fails open (OWASP A10:2025); security checks must fail closed.
- Virtualization: VM escape, resource reuse, sprawl, management plane. Zero-day = exploited before a patch exists.
