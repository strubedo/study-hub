## Identity, device, wireless and cloud attack surfaces

Modern breaches start less often with an exploit and more often with an account, an unknown device or a misconfigured cloud resource. This lesson covers the rest of objective 2.4.

## Unmanaged and stale credentials

- **Stale credentials:** accounts and keys that are no longer needed but still work: leavers' accounts, accounts of staff who changed roles, test and vendor accounts, service-account passwords set years ago, API keys for retired integrations, SSH keys in `authorized_keys` files nobody reviews.
- **Unmanaged credentials:** credentials outside the identity lifecycle: local admin accounts with the same password on every machine, shared accounts, default device passwords, keys created by developers outside any vault, personal access tokens with no expiry.

Attackers love them because nobody notices when they are used. Controls: joiner/mover/leaver processes and access reviews (Domain 4), disabling inactive accounts, unique local admin passwords managed centrally, secrets vaults with rotation, and alerting on logins to dormant accounts.

## Rogue devices

NIST defines a **rogue device** as an unauthorized node on a network: an employee's own wireless access point plugged into a wall port, a small computer hidden behind a printer, an unapproved switch, a rogue DHCP server. A rogue access point can bridge an open wireless network into the wired LAN, bypassing the firewall. Controls: 802.1X/NAC port authentication (Domain 4), switch port security, disabling unused ports, wireless intrusion prevention (WIPS) scanning for unknown APs, and DHCP snooping.

## Shadow IT

**Shadow IT** is hardware, software or cloud services used without the IT or security team's knowledge or approval: a team's own SaaS project tool, a personal file-sharing account used for work files, a cloud VM on a personal credit card, an unapproved AI chatbot. It is not usually malicious; it exists because people want to get work done. But it is unmanaged, unmonitored, outside data protection and contracts, and often protected only by a password. Discover it with CASB/SSE and DNS or proxy logs, and reduce it by offering approved alternatives.

## Wireless and low-powered communications

**Wireless LANs:** open networks with no encryption, WPA2-Personal with a weak passphrase (the handshake can be captured and the passphrase guessed offline), Wi-Fi Protected Setup (WPS), legacy WEP or TKIP, rogue and evil twin access points, and deauthentication floods. WPA3 adds SAE, which resists offline guessing, and protected management frames.

**Low-powered communications** are radio protocols for small, battery-powered devices: Bluetooth Low Energy, Zigbee, Z-Wave, LoRaWAN and similar. Their limits in power, memory and processing push designers toward lighter security: short or fixed keys, optional encryption, weak or absent authentication during pairing, and firmware that is rarely updated. The devices that use them (locks, sensors, medical devices, building controls) are often physically accessible.

## Large language models (LLMs)

An LLM-powered application is a new attack surface because its input is natural language that mixes instructions with data, and because it is often connected to documents, tools and other systems. As an attack surface, consider:

- **Inputs:** chat prompts, uploaded files, retrieved web pages and documents, emails the assistant reads. Any of them can carry injected instructions (prompt injection, lesson 2.6).
- **Outputs:** model output passed to a browser, shell, database or API without validation can become XSS, command execution or SQL injection (OWASP LLM05:2025 Improper Output Handling).
- **Connected tools and permissions:** an assistant or agent that can send mail, run code or change records with broad permissions (OWASP LLM06:2025 Excessive Agency).
- **Data:** what the model was trained or fine-tuned on, what is in its context window and what users paste into it (sensitive information disclosure, LLM02:2025).
- **Supply chain:** third-party models, plug-ins and datasets.

Lesson 2.6 covers the specific AI threats.

## Identity providers

An **identity provider (IdP)** authenticates users and issues assertions or tokens that other services trust (SAML, OpenID Connect, Domain 4). That makes it a single point of compromise: whoever controls the IdP, or can forge what it issues, can sign in to every federated application. Attack surface includes:

- IdP administrator accounts and help-desk staff who can reset passwords and MFA methods.
- The **token-signing keys and certificates**: a stolen signing key lets an attacker mint valid tokens for any user.
- Federation trust configuration: an attacker with admin rights can add a new trusted domain or IdP.
- MFA policy gaps: legacy protocols that bypass MFA, weak recovery flows, exclusions for "trusted" locations.
- Third-party applications granted OAuth consent to read mail or files.

Protect IdP administration with phishing-resistant MFA and privileged access management, store signing keys in HSMs, alert on changes to federation settings and MFA methods, and monitor sign-in logs (Domain 4).

## Mobile devices

Jailbroken or rooted devices that bypass the OS security model, sideloaded apps from outside official stores, out-of-date OS versions no longer receiving updates, malicious or over-permissioned apps, insecure Wi-Fi and Bluetooth, lost and stolen devices, and personal and work data on the same device (BYOD). Controls are mobile device management (MDM), containerization of work data, OS version requirements and remote wipe (Domain 4).

## Misconfiguration

Misconfiguration is consistently near the top of breach causes; OWASP ranks **A02:2025 Security Misconfiguration** second. Examples: default passwords, unnecessary features enabled, overly permissive firewall rules (`any any allow`), directory listing on web servers, verbose errors, permissive cloud IAM roles, disabled logging, missing security headers. Configuration baselines, infrastructure as code with review, and continuous posture scanning (CSPM, Domain 4) catch drift.

## Public repositories

Two different risks:

- **Your code in public:** source code pushed to a public Git repository (or a private repo later made public) exposes hardcoded secrets, internal hostnames, architecture details and vulnerabilities. Attackers scan public code hosting continuously for keys. MITRE ATT&CK lists searching code repositories as reconnaissance and finding credentials in files as credential access.
- **Their code in your build:** public package repositories (npm, PyPI and the like) host malicious packages: typosquatted names, takeovers of abandoned packages, and packages named after dependencies that AI coding assistants commonly hallucinate (OWASP's LLM09:2025 scenario).

Controls: secrets scanning before commit and on the platform, repository visibility reviews, dependency pinning and review, software composition analysis and private package mirrors.

## Public object storage

Cloud object storage (Amazon S3 buckets, Azure Blob containers, Google Cloud Storage buckets) holds files as objects reachable by URL. A bucket or container set to public read, or with a policy granting access to "everyone" or "all authenticated users" of the cloud provider, exposes its contents to anyone who finds the name, and attackers enumerate bucket names automatically. Public **write** is worse: ATT&CK notes adversaries modifying script files served to a website from a publicly writable cloud storage bucket. Controls: block public access settings at the account level, least-privilege bucket policies, pre-signed URLs for time-limited sharing, encryption and access logging, and posture scanning.

> **Exam tip:** Data exposed because a storage bucket allowed anonymous access is a *misconfiguration* of *public object storage*, not a hack of the cloud provider. Under the shared responsibility model (Domain 3), the customer configures access to their data.

## Try it yourself

Works on any OS and costs nothing. (1) If you have a GitHub, GitLab or similar account, review your repositories' visibility and search your own repos for words like `password`, `apikey` or `BEGIN PRIVATE KEY`. (2) Make a list of every cloud service you use for work or school that IT did not provide: that list is your personal shadow IT. (3) In your phone's settings, check the OS version and whether it is still receiving security updates from its maker.

## Key takeaways

- Stale and unmanaged credentials work silently; disable, vault, rotate and review them.
- Rogue device = unauthorized node (NIST); shadow IT = unapproved hardware, software or services. Control with NAC/802.1X, WIPS, CASB and approved alternatives.
- Wireless: weak PSKs, WPS, open networks, evil twins; low-powered protocols trade security for battery life.
- LLM apps are attack surface through inputs, outputs, connected tools and data (OWASP LLM Top 10 2025).
- Identity providers are a single point of compromise: protect admin accounts, signing keys and federation settings.
- Misconfiguration (OWASP A02:2025), public repositories (leaked secrets, malicious packages) and public object storage (anonymous read or write) are configuration failures by the customer.
