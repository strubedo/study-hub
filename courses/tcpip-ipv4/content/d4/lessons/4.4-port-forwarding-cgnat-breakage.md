## Port forwarding

Overloaded PAT creates mappings only for connections that start inside. To publish a service, say a web server at 10.1.1.20, behind a single public address, you add a **static port mapping** (port forwarding, also "static PAT" or destination NAT): traffic arriving at a chosen public address and port is rewritten to an inside address and port.

```text
! Cisco IOS: public 203.0.113.2:8080 -> inside 10.1.1.20:80
R1(config)# ip nat inside source static tcp 10.1.1.20 80 203.0.113.2 8080

R1# show ip nat translations
Pro Inside global      Inside local       Outside local      Outside global
tcp 203.0.113.2:8080   10.1.1.20:80       ---                ---
```

```text
# Linux: the same idea with iptables (the nat PREROUTING chain rewrites the destination)
sudo iptables -t nat -A PREROUTING -i eth1 -p tcp -d 203.0.113.2 --dport 8080 \
     -j DNAT --to-destination 10.1.1.20:80
# Only needed if the FORWARD chain default policy is not ACCEPT:
sudo iptables -A FORWARD -p tcp -d 10.1.1.20 --dport 80 -j ACCEPT
```

This was tested with a three-namespace lab: a client on the outside side connecting to 203.0.113.2:8080 reached the inside server, and the tracking table recorded the reply as coming from 10.1.1.20 port 80. Note the two points where beginners go wrong:

- The mapping is a **destination** rewrite on arrival; the return path must pass back through the same NAT device. If the inside server's default gateway is another router, replies bypass the NAT and the connection hangs (asymmetric routing).
- The **firewall** policy is a separate decision from the translation. Forwarding a port does not by itself permit it through a stateful firewall.

### Hairpinning (NAT loopback)

A client on the inside that connects to the server's **public** name or address 203.0.113.2:8080 sends the packet to the NAT device, which translates the destination to 10.1.1.20 and sends it back out the inside interface. The server sees the client's real inside source and replies directly, so the NAT never sees the return path and the connection fails. Solutions are hairpin NAT (rewrite the source as well; RFC 4787 describes the behaviour as hairpinning), or more simply **split-horizon DNS**, where internal clients resolve the service name to the inside address.

## Carrier-grade NAT

Address exhaustion led ISPs to deploy **carrier-grade NAT (CGN or CGNAT)**: the provider translates many customers' private addresses to a small public pool, so the customer's own router performs NAT a second time (**double NAT**). RFC 6598 reserved **100.64.0.0/10** as **shared address space** for the link between the customer's router and the CGN, specifically so it does not clash with a customer's RFC 1918 ranges. It is not private address space for use inside a site and is not globally routable; if your router's WAN address is in 100.64.0.0/10 you are behind a CGN. Requirements for a CGN are in RFC 6888.

Effects of CGN:

| Effect | Why |
|---|---|
| **No inbound connections** | The customer has no public address to forward ports on; the CGN holds the mapping. Hosting, remote access and many game or VoIP modes fail or need a relay. |
| **Port exhaustion** | Each public address supplies only a limited pool of ports for many subscribers, so providers cap ports per subscriber (RFC 6888 REQ-4) and a user opening many connections may see failures. |
| **Shared public address** | Thousands of users appear as one IP: reputation systems, rate limits, CAPTCHAs and geolocation treat them as one, and a block hits innocent users. |
| **Traceability** | Identifying a user requires logging the public address, port and timestamp, since the address alone does not identify a subscriber. |
| **Double NAT** | Two translations complicate UPnP/NAT-PMP, VPNs and peer-to-peer; ICE, STUN and TURN help applications cope. |
| **Larger state tables** | The CGN carries per-flow state for every subscriber; timers and limits matter. |

A 100.64.0.0/10 address in a traceroute hop indicates a CGN or ISP-internal device.

> **Exam tip:** 100.64.0.0/10 is "shared address space" (RFC 6598), not an RFC 1918 range. It is meant for the ISP-to-CPE link behind a CGN.

## Protocols that break through NAT

NAT only rewrites the IP and transport headers. Anything that carries addresses or ports **inside the payload**, or that depends on end-to-end header integrity, can break.

| Protocol / feature | Problem | Typical workaround |
|---|---|---|
| **Active FTP** | The PORT command in the control channel contains the client's IP and port; the server then connects back to that address. | A NAT **ALG** rewrites the payload, or use passive FTP, where the client opens both connections (a server behind NAT must still advertise its public address) |
| **SIP/RTP, H.323** | Signalling messages (SDP) carry IP addresses and RTP ports for media. | SIP ALG, STUN/TURN/ICE, session border controllers, outbound proxies |
| **IPsec ESP (IP protocol 50)** | ESP has no ports, so PAT cannot tell tunnels apart; AH (protocol 51) authenticates the IP header, so any rewrite invalidates it. | **NAT-T**: ESP is encapsulated in UDP port **4500** (RFC 3948) after IKE detects NAT (RFC 3947) |
| **PPTP** | The data channel is GRE (IP protocol 47), which has no ports. | Special-cased GRE call-ID handling |
| **ICMP errors** | They embed the original packet header, which must be translated back. | Correct NAT implementations rewrite the embedded header |
| **Fragmented packets** | Only the first fragment has a UDP/TCP header, so a port-based NAT cannot map the others without reassembly. | Reassemble before translating |
| **Peer-to-peer, inbound services** | No mapping exists until the inside host sends first. | UPnP IGD, NAT-PMP/PCP, hole punching |

An **application-layer gateway (ALG)** is NAT-device code that understands one protocol and rewrites its embedded addresses (RFC 3022 calls FTP the most popular ALG and explains that a changed payload length requires adjusting TCP sequence numbers). An ALG that guesses wrong or that is enabled for a protocol you use differently is a classic source of baffling failures; disabling a faulty SIP ALG is a routine fix.

Finally, NAT breaks the original end-to-end principle: a server cannot learn the client's real address from the packet (logs show the NAT's address), and anything signed or checked against source addresses is affected. IPv6 removes the need for NAT, though translation of other kinds still exists.

## Lab it yourself

1. Extend the three-namespace NAT lab from the previous lesson: start `python3 -m http.server 80` inside `lan`, add the DNAT rule above in `gw`, and `curl http://203.0.113.2:8080/` from `wan`. Look at `conntrack -L` and `tcpdump` on both gateway interfaces.
2. Break it: point `lan`'s default route away from the gateway and watch the connection hang with SYN-ACKs never returning through the NAT.
3. Test hairpinning: try `curl http://203.0.113.2:8080/` from `lan` itself. Fix it by removing `-i eth1` from the DNAT rule so it also matches inside traffic, and adding `iptables -t nat -A POSTROUTING -s 10.1.1.0/24 -d 10.1.1.20 -p tcp --dport 80 -j MASQUERADE`.
4. On a Cisco router, configure the port forward above and look at `show ip nat translations` and `show ip nat statistics` before and after a test connection.
5. Run `ip -4 addr` on a home router or phone hotspot: an address in 100.64.0.0/10 on the WAN side shows CGN. Compare the WAN address against what a "what is my IP" service reports.
6. Capture an active FTP session with Wireshark through a NAT and look for the PORT command (`ftp.request.command == "PORT"`).

## Key takeaways

- Port forwarding is static PAT or DNAT: a fixed mapping of public address:port to inside address:port, plus a separate firewall permit.
- Replies must return through the same NAT device; asymmetric routing breaks forwards.
- Inside clients using the public address need hairpin NAT or split DNS.
- CGN shares public addresses among subscribers; RFC 6598 reserves 100.64.0.0/10 for the ISP-to-customer link.
- CGN effects: no inbound connections, per-subscriber port limits, shared-IP reputation, logging needs, double NAT.
- Payload-embedded addresses (FTP PORT, SIP/SDP, H.323) need an ALG or a traversal technique such as STUN/ICE.
- ESP has no ports and AH covers the IP header; NAT-T wraps ESP in UDP 4500 (RFC 3947/3948).
- ICMP errors and fragments need special NAT handling.
