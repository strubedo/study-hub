## Capturing packets

When the host tools in the previous lesson do not explain a failure, look at the wire. **tcpdump** (command line, libpcap) and **Wireshark** (graphical, with the command-line twin `tshark`) capture frames from an interface; Wireshark adds decoding, reassembly and expert analysis.

### Capture filters versus display filters

This is the most commonly confused point.

| | Capture filter | Display filter |
|---|---|---|
| Applied | **While capturing**; non-matching frames are never stored | **After capture**; hides frames from the view only |
| Syntax | BPF (Berkeley Packet Filter), as used by tcpdump | Wireshark's own field language |
| Example | `host 192.0.2.10 and tcp port 443` | `ip.addr == 192.0.2.10 && tcp.port == 443` |
| Typical use | Limit volume on busy links | Explore a stored capture |

If you filter too tightly while capturing, the evidence is gone; capture broadly when you can, then narrow with display filters.

### tcpdump essentials

```text
sudo tcpdump -nn -i eth0 host 192.0.2.10 and tcp port 443      # numeric hosts and ports
sudo tcpdump -nn -i eth0 -c 20 icmp                              # stop after 20 packets
sudo tcpdump -nn -i eth0 -w /tmp/cap.pcap 'port 53'              # write a file for Wireshark
tcpdump -nn -r /tmp/cap.pcap                                     # read it back
sudo tcpdump -nn -e -i eth0 arp                                  # -e shows Ethernet headers
sudo tcpdump -nn -i eth0 'tcp[tcpflags] & tcp-syn != 0'          # SYN and SYN-ACK packets
sudo tcpdump -nn -i eth0 'tcp[tcpflags] == tcp-syn'              # SYN only (connection attempts)
sudo tcpdump -nn -i eth0 'udp port 67 or udp port 68'            # DHCP
sudo tcpdump -nn -i eth0 not port 22                             # hide your own SSH session
```

`-n` skips name resolution (use `-nn` to also skip port names); `-i any` captures on all interfaces; `-s 0` (default in current versions) captures whole packets; `-v`/`-vv` print more header detail. Useful primitives: `host`, `net 192.0.2.0/24`, `src`/`dst`, `port`, `portrange 6000-6010`, `ether host`, `vlan`, and the protocol names `tcp`, `udp`, `icmp`, `arp`, combined with `and`, `or`, `not`.

A sample TCP connection that never completes, as tcpdump prints it:

```text
10:41:02.120118 IP 192.0.2.10.50718 > 198.51.100.80.443: Flags [S], seq 3105121870, win 64240, options [mss 1460,sackOK,TS val 90812 ecr 0,nop,wscale 7], length 0
10:41:03.141233 IP 192.0.2.10.50718 > 198.51.100.80.443: Flags [S], seq 3105121870, win 64240, options [mss 1460,sackOK,TS val 91833 ecr 0,nop,wscale 7], length 0
10:41:05.157301 IP 192.0.2.10.50718 > 198.51.100.80.443: Flags [S], seq 3105121870, win 64240, options [mss 1460,sackOK,TS val 93849 ecr 0,nop,wscale 7], length 0
```

Repeated identical SYNs at roughly doubling intervals, with no SYN-ACK and no ICMP, mean silence from the far end or a filter on the path: a firewall drop, a routing problem on the return path, or a dead host. A `Flags [R.]` reply instead would mean a reset (closed port), and an ICMP unreachable would identify who refused.

### Wireshark display filters

```text
ip.addr == 192.0.2.10                       either source or destination
ip.src == 192.0.2.0/24                      source in a subnet
tcp.port == 443  /  udp.port == 53          either port
tcp.flags.syn == 1 && tcp.flags.ack == 0    connection attempts
tcp.flags.reset == 1                        resets
tcp.analysis.retransmission                 retransmissions (Wireshark's analysis)
tcp.analysis.flags                          all TCP expert warnings
tcp.stream eq 3                             one conversation
icmp.type == 3                              destination unreachable
icmp.type == 11                             time exceeded
dns.flags.rcode == 3                        NXDOMAIN responses
dhcp                                        DHCP (dhcp.option.dhcp == 1 for Discover)
arp                                         ARP (arp.duplicate-address-detected for conflicts)
frame contains "example"                    byte-string search
!arp && !dns                                exclusions
```

Operators: `==`, `!=`, `<`, `>`, `contains`, `&&`/`and`, `||`/`or`, `!`/`not`. A green bar means the filter is valid in the GUI. Right-click a packet and choose **Follow > TCP Stream** to read the application data; use **Statistics > Conversations** and **I/O Graphs** for an overview.

### Where and how to capture

- Capture **on the host itself** whenever possible. On a switched network a third machine sees only broadcast, multicast and its own traffic unless you configure a **SPAN/mirror port** (or tap) on the switch.
- Capturing on the sender can show **bad checksums** on outbound packets; that is usually checksum **offload** (the NIC fills in the checksum after the capture point) and not a real fault.
- Capture on both sides of a router, firewall or NAT device and compare: where does the packet last appear, and what changed (source address, TTL, MAC)?
- A capture file needs privileges (`sudo`, or the `wireshark` group, or Npcap on Windows). Capturing exposes passwords and personal data in clear-text protocols; handle the file accordingly.

## A layered troubleshooting method

Choose an order and stick to it. The usual bottom-up path walks the layers from the cable upward and stops at the first failure; a top-down path starts at the application when users report a specific symptom. When you can halve the search space (for example, "does it work from this other host?"), use divide-and-conquer.

| Step | Question | Tools | A failure here means |
|---|---|---|---|
| 1 Link | Is the interface up with carrier? | `ip link`, `ipconfig`, `show interfaces` | Cable, port, speed/duplex, VLAN, shutdown |
| 2 Address | Right IP, mask, gateway, DNS? Lease valid? | `ip addr`, `ipconfig /all`, `show ip dhcp binding` | DHCP failure (169.254.x.x), wrong static config, duplicate address |
| 3 Local reach | Can I reach the gateway and its MAC resolves? | `ping <gateway>`, `ip neigh`, `arp -a` | Layer 2 problem, VLAN, ACL, wrong mask |
| 4 Routing | Does a route exist; do I reach a remote IP? | `ip route get`, `traceroute`/`tracert`, `ping <remote IP>` | Missing route, return route, upstream down, NAT |
| 5 Name | Does the name resolve to the right address? | `dig`, `nslookup`, `Resolve-DnsName` | DNS server, search domain, stale cache, split DNS |
| 6 Transport | Is the port reachable? | `nc -vz`, `Test-NetConnection`, `ss`, `tcpdump` | Firewall, service not listening, wrong bind address |
| 7 Application | Does the service respond correctly? | `curl -v`, logs | Application or certificate problem |

Telling symptoms apart saves time:

- **Ping by IP works, by name fails:** DNS (step 5), not the network.
- **Gateway ping works, remote IP fails:** routing, NAT or upstream (step 4). Use `traceroute` to see where it stops, and check return routes.
- **Local subnet works, nothing else:** missing or wrong default gateway or mask.
- **Address 169.254.x.x:** DHCP never answered.
- **Intermittent loss, only to some hosts:** duplicate IP addresses (check `ip neigh` for the MAC changing), or an MTU black hole (small pings work, large transfers hang: see the MTU lesson).
- **Works for a few minutes, then fails:** lease or NAT-mapping expiry, ARP/neighbour changes, or a flapping link.
- **Refused versus timed out:** reset means a live host with no listener; silence means a drop.

Always change one thing at a time, note the result, and test from both ends where possible. On a Cisco router the same checklist reads `show ip interface brief`, `show ip route <dst>`, `show ip arp`, `ping` and `traceroute` (use the extended ping with a source interface to test a specific path), `show ip nat translations` and `show access-lists` for the filters.

## Lab it yourself

1. Capture while loading a web page: `sudo tcpdump -nn -i any -w /tmp/web.pcap 'port 53 or port 443'`, then open the file in Wireshark and follow the order DNS query, DNS reply, SYN, SYN-ACK, ACK, TLS hello. Mark each with a display filter.
2. Provoke the three failure fingerprints against a lab host: `nc -vz <ip> 9` (closed port, RST), a firewall DROP rule (`sudo iptables -A INPUT -p tcp --dport 8080 -j DROP`, repeated SYNs) and an unreachable network (ICMP unreachable). Capture each.
3. Break your lab on purpose, one fault at a time (wrong mask, wrong gateway, wrong DNS, missing return route), and write down which step of the table caught it first.
4. In Wireshark use `tcp.analysis.retransmission` and the Expert Information window on a capture taken from a lossy link (emulate with `sudo tc qdisc add dev eth0 root netem loss 5%` in a lab, and remove with `sudo tc qdisc del dev eth0 root`).
5. Use SPAN on a Catalyst (`monitor session 1 source interface Gi1/0/5` and `monitor session 1 destination interface Gi1/0/24`) to capture a neighbour's traffic.

## Key takeaways

- A capture filter (BPF, applied during capture) and a display filter (Wireshark syntax, applied afterwards) are different languages.
- `tcpdump -nn -i <if> <expr>` captures; `-w` writes a pcap, `-r` reads one; BPF expressions combine `host`, `net`, `port`, `tcp`, `udp`, `icmp`, `arp` with `and`/`or`/`not`.
- Repeated SYNs with no answer means a drop or dead path; RST means a closed port; ICMP unreachable names the refusing device.
- On switches you need a SPAN port or tap to see others' traffic; outbound bad checksums are usually offload.
- Troubleshoot in layers: link, address, gateway, routing, name, port, application; stop at the first failing step.
- Ping by IP versus ping by name separates routing problems from DNS problems.
- Change one variable at a time and test from both ends.
- Know the matching IOS commands: `show ip interface brief`, `show ip route`, `show ip arp`, `show ip nat translations`.
