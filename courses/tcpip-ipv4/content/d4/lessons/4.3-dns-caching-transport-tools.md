## TTL and caching

Every resource record carries a **time to live**, in seconds, set by the zone owner. A resolver may keep the record for that long and answer repeat queries from cache without asking again; when it hands the record to a client it reports the **remaining** TTL, which counts down. This is why `dig` shows 287 for a record published with 300.

Practical consequences:

- **Changing a record does not take effect everywhere at once.** Caches that already hold the old data keep serving it until the TTL runs out. Before a planned address change, lower the TTL (for example to 300 seconds) at least one old-TTL period ahead of the change, then raise it again afterwards.
- A long TTL reduces load and lookup latency; a short TTL gives fast failover but more queries.
- A zone's authoritative servers do not "push" changes to caches; secondaries learn of changes through SOA serial polling or `NOTIFY` (zone transfer machinery), which is separate from caching.
- Clients cache too: the Windows DNS Client service (`ipconfig /displaydns`, flush with `ipconfig /flushdns`), `systemd-resolved` on many Linux systems (`resolvectl statistics`, flush with `resolvectl flush-caches`), and browsers keep their own short caches.

## Negative caching

Failures are cached as well, so that a mistyped or nonexistent name does not hit the authoritative servers on every attempt. RFC 2308 defines two negative answers:

- **NXDOMAIN**: the name does not exist at all (response code 3).
- **NODATA**: the name exists but has no record of the requested type; response code `NOERROR` with an empty answer section, for instance asking for `AAAA` of a name that only has an `A`.

The authoritative server includes the zone's **SOA record in the authority section** of a negative response. The resolver caches the negative result for the **minimum of the SOA record's own TTL and the SOA MINIMUM field** (RFC 2308), and since that RFC the MINIMUM field is exactly this negative-caching value.

```text
$ dig nosuch.example.com A

;; ->>HEADER<<- opcode: QUERY, status: NXDOMAIN, id: 5521
;; flags: qr rd ra; QUERY: 1, ANSWER: 0, AUTHORITY: 1, ADDITIONAL: 1

;; AUTHORITY SECTION:
example.com.            900     IN      SOA     ns1.example.com. hostmaster.example.com. 2026103001 7200 900 1209600 300
```

Here the SOA TTL shown is 900 (counting down in this cache) and the MINIMUM field is 300, so the negative answer may be cached for at most 300 seconds. If you create the missing record, clients behind that resolver may keep getting NXDOMAIN until the negative entry expires. This is the source of the common "I just added the record and it still fails" complaint.

> **Exam tip:** NXDOMAIN means the **name** is absent; NODATA (NOERROR with an empty answer) means the name exists but the **type** does not. The TTL of a negative cache entry comes from the SOA, not from any record you created.

## Transport: UDP and TCP port 53

DNS servers listen on **port 53 for both UDP and TCP**. Most queries use UDP because a single small request and response is cheaper than a TCP handshake.

- RFC 1035 limits a classic UDP DNS message to **512 bytes**. EDNS0 (RFC 6891) lets a client advertise a larger UDP payload size in an OPT record, so bigger answers such as DNSSEC data can still fit.
- If the answer does not fit, the server sets the **TC (truncated) bit** and the client **retries over TCP**. RFC 7766 states that all DNS implementations (authoritative, recursive and stub) MUST support TCP, and that TCP is not just for zone transfers.
- **Zone transfers** (AXFR, IXFR) between primary and secondary servers use TCP.
- Encrypted transports use other ports: DNS over TLS uses **TCP 853** (RFC 7858); DNS over HTTPS uses HTTPS on 443.

> **Watch out:** A firewall that permits only UDP 53 will mostly appear to work, then fail on large responses and zone transfers. Permit both UDP and TCP 53 between resolvers and authoritative servers.

Force TCP with `dig +tcp example.com A` and watch the three-way handshake in a capture; the DNS message is prefixed by a 2-byte length field on TCP.

## Reverse lookups

A **reverse lookup** maps an address to a name using `PTR` records in the special domain `in-addr.arpa`. The four octets are written **in reverse order**, because DNS delegation runs from the right-hand (most general) label, while IP addresses become more specific to the right:

```text
192.0.2.10   ->   10.2.0.192.in-addr.arpa.

$ dig -x 192.0.2.10 +noall +answer
10.2.0.192.in-addr.arpa. 3600 IN PTR host10.example.com.
```

Delegation follows octet boundaries, so the owner of 192.0.2.0/24 controls `2.0.192.in-addr.arpa`. Whoever allocated you the addresses (your ISP or RIR) decides who runs the zone, which is why reverse zones are managed separately from forward zones and often point to a provider-chosen name. Allocations smaller than a /24 are delegated with a CNAME technique described in RFC 2317. Reverse DNS is used for readable log files, `traceroute` output and mail-server reputation checks (the forward and reverse names should agree).

A forward record and its PTR are **independent**: creating an `A` record does not create the `PTR`, and a name can resolve forward without resolving back.

## nslookup and dig

| Task | dig | nslookup |
|---|---|---|
| Default query | `dig example.com` | `nslookup example.com` |
| Ask one server | `dig @192.0.2.53 example.com` | `nslookup example.com 192.0.2.53` |
| Record type | `dig example.com MX` | `nslookup -type=MX example.com` |
| Short answer | `dig +short example.com` | (none) |
| Reverse | `dig -x 192.0.2.10` | `nslookup 192.0.2.10` |
| Full delegation walk | `dig +trace example.com` | (none) |
| Force TCP | `dig +tcp example.com` | `nslookup -vc example.com` |
| Do not request recursion | `dig +norecurse @server name` | `nslookup`, then `set norecurse` |

`dig` is the tool for troubleshooting: it shows the flags, sections, TTLs and which server answered. `nslookup` is installed on Windows by default and is fine for quick checks, but it uses its **own resolver code**, so it ignores the Windows `hosts` file and the DNS client cache, and it may report a different result from what applications see. On Windows, `Resolve-DnsName example.com` (PowerShell) uses the system's DNS client. On Linux, `getent hosts example.com` goes through the real name-service switch (`/etc/nsswitch.conf`, the `hosts` file, `systemd-resolved`), and `dig` bypasses all of that to ask DNS directly.

On Cisco IOS, point the router at a resolver with `ip name-server 192.0.2.53` and `ip domain name example.com`. A mistyped command at the exec prompt makes IOS try to resolve it as a host name and stall; `no ip domain-lookup` stops that. Static names are defined with `ip host R2 192.0.2.2`.

Always separate the two failure domains: if `ping 198.51.100.80` works but `ping www.example.com` does not, the problem is name resolution, not routing.

## Lab it yourself

1. `dig example.com A`, run it twice a few seconds apart and compare the TTLs. Then run `dig @<resolver> nosuchhost.example.com A` and read the SOA in the authority section to compute the negative-caching time.
2. `dig +tcp example.com A` while capturing with `tcpdump -nn -i any 'port 53'`; compare with the UDP version. To see the `tc` flag, query a lab server that holds a record set larger than 512 bytes with `dig +ignore +bufsize=512 +norecurse @<lab-server> <big-txt-name> TXT`; `+ignore` stops dig from retrying over TCP automatically.
3. `dig -x 192.0.2.10` and then work out by hand the reverse name of 198.51.100.77.
4. On Windows: `ipconfig /displaydns`, browse to a site, repeat, then `ipconfig /flushdns`; compare `nslookup name` to `Resolve-DnsName name` after adding an entry to the hosts file.
5. Wireshark filters: `dns.flags.rcode == 3` for NXDOMAIN, `dns.flags.truncated == 1` for truncation, `tcp.port == 53 || udp.port == 53` for all DNS.

## Key takeaways

- Caches keep each record until its TTL expires and report the remaining TTL; lower TTLs before planned changes.
- Negative answers (NXDOMAIN, or NODATA as NOERROR with no answer) are cached for the smaller of the SOA TTL and the SOA MINIMUM (RFC 2308).
- DNS uses UDP and TCP port 53: UDP up to 512 bytes unless EDNS0 is used, TCP after truncation and for zone transfers; TCP support is mandatory (RFC 7766).
- DNS over TLS uses TCP 853 (RFC 7858).
- Reverse lookups use PTR records in `in-addr.arpa` with the octets reversed: 192.0.2.10 is `10.2.0.192.in-addr.arpa`.
- Forward and reverse records are independent.
- `dig` shows flags, sections, TTLs and servers; `dig +trace` follows delegation; `nslookup` on Windows bypasses the hosts file and system cache.
- Test by IP first, then by name, to separate routing problems from DNS problems.
