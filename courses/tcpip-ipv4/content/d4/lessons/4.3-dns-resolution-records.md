## The namespace and who answers

The Domain Name System (RFC 1034 concepts, RFC 1035 implementation) is a distributed, hierarchical database. A name such as `www.example.com.` is read right to left: the empty root label (the trailing dot), the top-level domain `com`, the second-level `example`, and the host label `www`. Responsibility is **delegated** downward in **zones**; the servers that hold the definitive data for a zone are its **authoritative** servers, and an `NS` record in the parent zone points at them.

| Role | What it does |
|---|---|
| **Stub resolver** | The small client in the OS; sends one recursive query to the configured resolver and waits. |
| **Recursive resolver** | The server your DHCP lease points to (option 6). Does the work of chasing the answer and caches it. |
| **Root servers** | Know which servers handle each TLD. There are 13 named root server identities (`a.root-servers.net` to `m.root-servers.net`), each served by many anycast instances. |
| **TLD servers** | Know which servers handle each second-level domain under `com`, `org`, country codes and so on. |
| **Authoritative servers** | Hold the zone data and give the final answer with the `aa` flag set. |

## Recursive versus iterative resolution

The word pair describes **who does the work**, not the protocol.

- A **recursive query** (the `RD`, recursion desired, bit is set) asks the server to return the final answer or an error. A stub resolver sends this to its recursive resolver. A server that offers the service sets the `RA` (recursion available) flag.
- An **iterative query** asks only for the best information the server has. The server answers with the record, or with a **referral**: the `NS` records of a server closer to the answer, usually with **glue** (`A`/`AAAA` records of those name servers) in the additional section.

Resolving `www.example.com` with a cold cache looks like this:

```text
stub  -> resolver : www.example.com A ?              (recursive)
resolver -> root  : www.example.com A ?              referral: NS for com. (+ glue)
resolver -> com   : www.example.com A ?              referral: NS for example.com. (+ glue)
resolver -> ns1.example.com : www.example.com A ?   answer: 198.51.100.80, aa flag set
resolver -> stub  : 198.51.100.80                    (ra flag set, TTL counts down from here)
```

The resolver stores every record it learned (the `com` NS set, the `example.com` NS set and the final A record) under each record's own TTL, so later queries skip steps. `dig +trace www.example.com` makes `dig` perform this walk itself, printing each referral, and is the quickest way to see where delegation is broken.

> **Exam tip:** The client talks to its resolver recursively; the resolver talks to the hierarchy iteratively. "Recursive resolver" and "authoritative server" are different roles, though one software package may play both. An answer with `aa` came from an authoritative server; one with `ra` but no `aa` came from a cache.

## Resource record types

Every record has an owner name, TTL, class (`IN`), type and data. The type numbers are in the IANA DNS parameters registry.

| Type | Value | Contents | Notes |
|---|---|---|---|
| A | 1 | IPv4 address | RFC 1035 |
| NS | 2 | Authoritative name server for the zone | Target must be a name with an address record, not an alias |
| CNAME | 5 | Canonical name for an alias | An alias cannot coexist with other data at the same name, so it cannot sit at the zone apex (which needs SOA and NS) |
| SOA | 6 | Zone start of authority | One per zone |
| PTR | 12 | Name for an address | Used under `in-addr.arpa` |
| MX | 15 | Mail exchanger with preference | **Lower** preference is tried first; the target must not be an alias (RFC 2181) |
| TXT | 16 | Free text strings | SPF, DKIM keys, domain verification |
| AAAA | 28 | IPv6 address | RFC 3596 |
| SRV | 33 | Service location | `_service._proto.name`, priority, weight, port, target (RFC 2782) |

The SOA record has seven fields after the owner and TTL:

```text
example.com.  3600 IN SOA ns1.example.com. hostmaster.example.com. (
                  2026103001  ; serial
                  7200        ; refresh: secondary polls primary this often
                  900         ; retry: re-poll interval after a failure
                  1209600     ; expire: secondary stops answering after this
                  300 )       ; minimum: negative-caching TTL (RFC 2308)
```

The mailbox in the second name replaces the first dot with `@` (`hostmaster@example.com`). The serial must increase for secondaries to pick up changes. Since RFC 2308 the last field means the **negative-caching TTL**, not a default record TTL.

Example records:

```text
example.com.       3600 IN NS    ns1.example.com.
example.com.       3600 IN MX    10 mail1.example.com.
example.com.       3600 IN MX    20 mail2.example.com.
www.example.com.    300 IN CNAME web1.example.com.
web1.example.com.   300 IN A     198.51.100.80
web1.example.com.   300 IN AAAA  2001:db8::80
example.com.       3600 IN TXT   "v=spf1 mx -all"
_sip._tcp.example.com. 3600 IN SRV 10 60 5060 sip1.example.com.
```

For the SRV record: priority 10 (lower is tried first), weight 60 (share among equal priority), port 5060, target `sip1.example.com.`. A CNAME makes the resolver restart the lookup for the target, so `www` yields two answer records (the CNAME and the A). PTR records and the `in-addr.arpa` naming are covered in the next lesson.

## Reading a dig answer

```text
$ dig www.example.com A

;; ->>HEADER<<- opcode: QUERY, status: NOERROR, id: 41122
;; flags: qr rd ra; QUERY: 1, ANSWER: 2, AUTHORITY: 0, ADDITIONAL: 1

;; QUESTION SECTION:
;www.example.com.               IN      A

;; ANSWER SECTION:
www.example.com.        300     IN      CNAME   web1.example.com.
web1.example.com.       287     IN      A       198.51.100.80

;; Query time: 12 msec
;; SERVER: 192.0.2.53#53(192.0.2.53) (UDP)
```

The flags `qr` (this is a response), `rd` (client asked for recursion) and `ra` (server offers it) are set; `aa` is absent, so the answer is from a cache. The TTL of the A record (287) has counted down from 300, which shows a cached copy. The `status` field is the response code: `NOERROR`, `NXDOMAIN` (name does not exist), `SERVFAIL` (server could not complete, e.g. unreachable authoritative servers or a validation failure) or `REFUSED` (server will not answer you).

## Lab it yourself

1. Run `dig +trace example.com A` and identify the root referral, the TLD referral and the final authoritative answer. Look for the `aa` flag on the last step.
2. Compare `dig example.com MX +short`, `dig example.com NS +short` and `dig example.com SOA +noall +answer`; read the serial and minimum fields.
3. Query a specific server with `dig @192.0.2.53 www.example.com A` (a lab server), then `dig +norecurse @a.root-servers.net www.example.com A` to see a referral instead of an answer.
4. In Wireshark use `dns` and `dns.flags.response == 1`; add `dns.qry.name` and `dns.resp.ttl` as columns, and compare the TTL of the same record across two queries a few seconds apart.
5. Windows: `nslookup -type=MX example.com`, then `nslookup` interactively with `set type=SRV` and a query for `_ldap._tcp.dc._msdcs.<domain>` in an Active Directory lab.

## Key takeaways

- A stub resolver sends a recursive query to the recursive resolver, which iterates through root, TLD and authoritative servers using referrals and glue.
- `aa` marks an authoritative answer; `rd` and `ra` describe recursion asked and offered.
- Core record types: A 1, NS 2, CNAME 5, SOA 6, PTR 12, MX 15, TXT 16, AAAA 28, SRV 33.
- MX lowest preference wins; MX and NS targets must not be aliases; a CNAME cannot share a name with other data or sit at the apex.
- SRV carries priority, weight, port and target, under `_service._proto` names.
- SOA fields: serial, refresh, retry, expire and minimum (the negative-caching TTL since RFC 2308).
- Response codes: NOERROR, NXDOMAIN, SERVFAIL, REFUSED; NOERROR with an empty answer means the name exists but not that type.
- `dig +trace` walks the delegation chain itself and is the standard way to locate a broken delegation.
