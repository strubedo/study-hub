## Where routes come from

A routing table entry gets there from one of four sources.

| Source | Example | Notes |
|---|---|---|
| Connected / local | `C`, `L` | Created from an interface address that is up. |
| Static | `ip route 198.51.100.0 255.255.255.0 192.0.2.2` | Typed by an administrator; no failure detection by itself. |
| Default | `0.0.0.0/0` | A static or dynamic route that matches anything not matched more specifically. |
| Dynamic | OSPF, EIGRP, RIP, BGP | Learned from neighbours; adapts to link failure. |

A **default route** is not a special type; it is the prefix `0.0.0.0/0`, the shortest possible prefix, so it loses to every other match. Stub networks and almost all hosts use one. Static routes suit small or stub topologies, where they are predictable and cost nothing; dynamic protocols earn their keep when there are several paths and failures must be handled automatically.

Configuration for the same route on three platforms:

```text
R1(config)# ip route 198.51.100.0 255.255.255.0 192.0.2.2          ! Cisco IOS
$ sudo ip route add 198.51.100.0/24 via 192.0.2.2                    # Linux (not persistent)
C:\> route add 198.51.100.0 mask 255.255.255.0 192.0.2.2 -p         :: Windows, -p persists across reboots
```

## Administrative distance versus metric

Two different numbers decide between competing routes, and they work at different scopes.

- **Administrative distance (AD)** ranks the *trustworthiness of the source*. When two routing sources offer the **same prefix** (same network and length), the lower AD is installed. AD is a local value on one router and is not advertised.
- **Metric** ranks paths *within one routing protocol* (OSPF cost, RIP hop count, EIGRP composite metric). Lower is better, and metrics from different protocols are not comparable, which is exactly why AD exists.

Cisco IOS default administrative distances (confirmed against Cisco's "What Is Administrative Distance?" support document):

| Route source | Default AD |
|---|---|
| Connected interface | 0 |
| Static route | 1 |
| EIGRP summary route | 5 |
| External BGP | 20 |
| Internal EIGRP | 90 |
| IGRP | 100 |
| OSPF | 110 |
| IS-IS | 115 |
| RIP | 120 |
| EGP | 140 |
| ODR | 160 |
| External EIGRP | 170 |
| Internal BGP | 200 |
| Unknown | 255 (never installed) |

> **Exam tip:** In `[110/20]` the first number is the AD and the second is the metric. Other vendors use different defaults (for example Juniper preference values), so quote the Cisco numbers only for IOS.

### Floating static routes

Because a lower AD wins, giving a static route a **higher AD than the dynamic protocol** makes it a backup that sits out of the table until the dynamic route disappears:

```text
R1(config)# ip route 0.0.0.0 0.0.0.0 198.51.100.1 250
```

Here the trailing `250` is the AD (the default for a static route is 1). On Linux the equivalent is a second route to the same prefix with a higher `metric`; on Linux, routes to the same prefix are ranked by metric rather than AD.

### Equal-cost paths

If several routes to the same prefix come from the same protocol with the same metric, the router may install all of them and **load-balance** per flow (hash of addresses and ports) rather than per packet, which avoids reordering. IOS supports up to a platform-dependent number of equal-cost paths; do not memorise the number.

## Convergence and failure

A static route does not know whether its next hop is alive. If the next hop is on an interface that stays up (a switch port, say) while the neighbour is dead, the route stays installed and traffic is blackholed. Dynamic protocols detect this through hellos or loss of adjacency, and a floating static route only takes over once the primary route leaves the table. Tracking static routes to a probe (IP SLA with `track`) is the IOS answer, and is beyond this blueprint.

## What a router does to each packet

RFC 1812 lists the forwarding steps. Boiled down for an IPv4 unicast packet received on one interface:

1. **Validate** the frame and the IPv4 header (version, header length, total length). A router must verify the header checksum and discard packets with a bad one.
2. If the destination is the router's own address, deliver it locally.
3. **Decrement the TTL** by one. A packet that arrives with TTL 1 (so it would become 0) is discarded and the router sends ICMP Time Exceeded, type 11 code 0, to the source. This is what traceroute exploits (see the ICMP lesson).
4. **Look up** the destination in the table (longest prefix match) to find the next hop and egress interface. No match: drop and send ICMP Destination Unreachable.
5. Compare the packet size with the egress **MTU**. If it is larger and DF is clear, fragment; if DF is set, drop and send ICMP type 3 code 4 (fragmentation needed).
6. **Update the header checksum.** The TTL changed, so the checksum must change; implementations may adjust it incrementally rather than recomputing.
7. Resolve the next hop's **MAC** with ARP (cached after the first packet), build a **new Ethernet header** with the router's egress MAC as source and the next hop's MAC as destination, recompute the FCS, and transmit.

So at each hop these change: source and destination MAC, FCS, TTL and the IPv4 header checksum. The source and destination IP addresses, protocol and ports do not change (unless NAT rewrites them).

```text
Host A 192.0.2.10 -> Host B 203.0.113.9 through R1 and R2

Segment 1: eth src A-mac  dst R1-mac   ip 192.0.2.10 > 203.0.113.9  ttl 128
Segment 2: eth src R1-mac dst R2-mac   ip 192.0.2.10 > 203.0.113.9  ttl 127
Segment 3: eth src R2-mac dst B-mac    ip 192.0.2.10 > 203.0.113.9  ttl 126
```

A Windows sender starts at 128 and a Linux sender at 64. A routing loop does not circulate forever because every pass decrements the TTL; the packet dies when it reaches zero and the router that kills it sends Time Exceeded.

> **Watch out:** On Linux a machine does not forward between interfaces unless `net.ipv4.ip_forward=1` is set. If a Linux box with two NICs "does not route", check `sysctl net.ipv4.ip_forward` first. On Windows the equivalent is the per-interface `Forwarding` setting (`netsh interface ipv4 set interface "Ethernet" forwarding=enabled`) or the Routing and Remote Access role.

## Asymmetry and return routes

The most common cause of "ping works one way" is a missing **return route**. A packet can reach the destination via a static route, but the destination replies to an address it has no route for (or sends to a different default gateway). Always check both directions: the destination's table must contain a path back to the source network.

## Lab it yourself

1. Build two Linux network namespaces joined by a third acting as a router (`ip netns add`, `ip link add ... type veth`), enable `net.ipv4.ip_forward`, and add the routes by hand. Ping across and capture with `tcpdump -nei <veth>` on both sides to watch the MAC addresses change and the TTL fall by one.
2. On a Cisco router configure `ip route 198.51.100.0 255.255.255.0 192.0.2.2` and a second route with an AD of 200 to a different next hop. Use `show ip route 198.51.100.0` to see which is installed, shut the first next hop's interface, and watch the floating route appear.
3. Run `traceroute -n 203.0.113.9` (Linux) or `tracert -d 203.0.113.9` (Windows) and map each hop to the TTL that triggered the Time Exceeded.
4. Use `ping -i 1 203.0.113.9` on Windows or `ping -t 1 203.0.113.9` on Linux (iputils uses `-t` for TTL; on Windows `-t` means ping continuously) against a remote host and observe the Time Exceeded reply from the first router.

## Key takeaways

- Routes come from connected interfaces, static configuration or dynamic protocols; the default route is `0.0.0.0/0`.
- AD ranks route sources for the same prefix; metric ranks paths within one protocol. Prefix length is decided before either.
- Cisco defaults: connected 0, static 1, eBGP 20, EIGRP 90, OSPF 110, IS-IS 115, RIP 120, external EIGRP 170, iBGP 200.
- A floating static route is a static route with an AD higher than the dynamic route it backs up.
- Per hop a router checks the header, decrements TTL (sending Time Exceeded at zero), looks up the route, fragments or signals if over MTU, updates the checksum and builds a new L2 header.
- MACs, FCS, TTL and the IP checksum change per hop; addresses and ports do not, absent NAT.
- Linux needs `ip_forward=1` to route; a missing return route causes one-way connectivity.
- Static routes do not detect a dead next hop on an up interface.
