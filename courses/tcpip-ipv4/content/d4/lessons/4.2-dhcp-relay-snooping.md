## Why relays exist

DHCP discovery is a **broadcast**, and broadcasts do not cross routers. In a network with many VLANs you do not want a DHCP server in every one. A **relay agent** (usually the router or layer 3 switch that is the VLAN's default gateway) listens for client broadcasts and forwards them as **unicast** to a central DHCP server. RFC 2131 describes this as BOOTP relay behaviour.

On Cisco IOS the relay is configured on the interface facing the clients:

```text
R1(config)# interface Vlan10
R1(config-if)# ip address 10.10.10.1 255.255.255.0
R1(config-if)# ip helper-address 192.0.2.5
```

`ip helper-address` is not DHCP-specific. By default it also forwards several other UDP broadcast services: time (37), IEN-116 name service (42), TACACS (49), DNS (53), TFTP (69) and NetBIOS name (137) and datagram (138), in addition to BOOTP/DHCP (67 and 68). Unwanted ones are disabled globally with `no ip forward-protocol udp <port>` (IOS accepts keywords such as `domain` for DNS).

## The giaddr field and subnet selection

When the relay receives a client broadcast it:

1. Writes the IP address of the **receiving interface** into `giaddr` (the gateway address, 10.10.10.1 above).
2. Increments the `hops` field and may add option 82.
3. Sends the message **unicast** to the configured server, from its own address, UDP destination port 67. Cisco IOS relays also use 67 as the source port.

The server uses `giaddr` to choose the **pool**: it picks the scope that contains the relay address, so a single server hands out 10.10.10.0/24 addresses to VLAN 10 and 10.10.20.0/24 addresses to VLAN 20. Without a relay, `giaddr` is 0.0.0.0 and the server uses the pool matching the interface the request arrived on.

The server's reply goes **unicast to `giaddr`, UDP port 67**. The relay then delivers it to the client by broadcast or unicast to the client's hardware address on the client-facing interface (depending on the broadcast flag), because the client has no IP address yet.

```text
Client (0.0.0.0)                Relay 10.10.10.1                 Server 192.0.2.5
  DISCOVER  bcast 0.0.0.0:68 -> 255.255.255.255:67
                         DISCOVER  10.10.10.1:67 -> 192.0.2.5:67   giaddr=10.10.10.1
                         OFFER     192.0.2.5:67 -> 10.10.10.1:67   yiaddr=10.10.10.50
  OFFER   10.10.10.1:67 -> client MAC                              (via relay)
```

Renewals are different. A client in the RENEWING state already has an address and a server identifier, so its T1 request is unicast **directly** to the server, with no relay involved (the server must be routable from the client). Only REBINDING, being a broadcast, goes through the relay again.

> **Exam tip:** If clients in one VLAN get no lease while another VLAN works, check `ip helper-address` on the SVI and that the server has a **scope matching the relay's `giaddr`**. A missing scope makes the server stay silent.

## Option 82: relay agent information

RFC 3046 defines **option 82**, added by a relay agent and echoed by the server. It carries two sub-options:

| Sub-option | Name | Typical meaning |
|---|---|---|
| 1 | Agent Circuit ID | The switch port or VLAN the request entered on |
| 2 | Agent Remote ID | An identifier for the relay device (often its MAC or hostname) |

A server can use option 82 for policy (for example, always give the device on switch port Gi1/0/5 the same address, or restrict a pool to certain ports). Clients never see option 82: the relay strips it before forwarding the reply.

A recurring operational problem: a **DHCP snooping switch** that is *not* the gateway inserts option 82 into requests from the client but leaves `giaddr` at 0.0.0.0. A Cisco router acting as the downstream relay or server treats "option 82 present and giaddr zero" as suspicious and may drop the packet. Fixes are to disable insertion on the switch (`no ip dhcp snooping information option`) or to tell the router to accept it (`ip dhcp relay information trust-all` globally, or `ip dhcp relay information trusted` on the interface).

## Reservations in a relayed environment

A reservation still works across a relay because the server keys it on the client's MAC (`chaddr`) or client identifier (option 61), not on any IP address. The reserved address must lie inside the scope selected by `giaddr`, or the server will not use it. Remember that a reservation is configured on the server, whereas "static IP" is typed on the host.

## DHCP snooping

Because DHCP is unauthenticated and broadcast-based, any port can act as a server. A **rogue DHCP server** (for example a home router plugged into a wall jack) can hand out wrong gateways or DNS servers, enabling man-in-the-middle attacks. A **starvation attack** floods DISCOVERs with spoofed MAC addresses to exhaust the pool. **DHCP snooping** on a switch addresses both.

Snooping classifies each port as **trusted** (uplinks and legitimate server ports) or **untrusted** (all client ports, the default). On untrusted ports the switch:

- Drops server-originated messages (DHCPOFFER, DHCPACK, DHCPNAK), which stops rogue servers.
- Checks that the `chaddr` in a request equals the Ethernet source MAC, which defeats simple starvation (`ip dhcp snooping verify mac-address`, on by default on Catalyst).
- Can **rate-limit** DHCP packets per port.
- Builds a **binding table** of MAC address, IP address, lease time, VLAN and port from the ACKs it sees.

```text
SW1(config)# ip dhcp snooping
SW1(config)# ip dhcp snooping vlan 10
SW1(config)# interface GigabitEthernet1/0/48
SW1(config-if)# ip dhcp snooping trust
SW1(config)# interface range GigabitEthernet1/0/1 - 24
SW1(config-if-range)# ip dhcp snooping limit rate 15

SW1# show ip dhcp snooping binding
MacAddress          IpAddress       Lease(sec)  Type           VLAN  Interface
------------------  --------------- ----------  -------------  ----  --------------------
00:1A:2B:3C:4D:5E   10.10.10.50     85420       dhcp-snooping  10    GigabitEthernet1/0/5
```

The binding table is the foundation for two other protections: **Dynamic ARP Inspection** drops ARP packets whose sender IP and MAC disagree with a binding, and **IP Source Guard** filters traffic whose source IP does not match the binding for that port (both are described in the ARP lesson). A host with a static address needs a static binding or it is blocked by those features.

> **Watch out:** Snooping must be enabled on the VLAN as well as globally, and the port to the legitimate server or toward the relay must be **trusted**. Forgetting to trust the uplink is the classic reason that every client in a snooped VLAN suddenly stops getting leases. The router's own DHCP traffic also appears to come from an untrusted port if you trust the wrong interface.

Snooping protects only against rogue DHCP **servers** on its own switches and does not authenticate the real server. It is a layer 2 control; it does not replace port security or 802.1X.

## Lab it yourself

1. Use two Linux network namespaces (or two VMs) on different subnets with a router between them. Install `dnsmasq` on the server and configure a range for each subnet, then run a relay: `sudo dhcrelay -i <client-facing-if> <server-ip>` (ISC relay) and capture on the server link with `sudo tcpdump -nn -vv -i eth0 'udp port 67'`. Find `giaddr` in the packet.
2. On a Cisco router add `ip helper-address` to an SVI and run `debug ip dhcp server packet` on the server router to watch the pool selection.
3. On a Catalyst enable snooping on a VLAN, trust the uplink only, then plug in a second DHCP server on an access port and confirm clients still receive leases from the real server (`show ip dhcp snooping statistics` shows the drops).
4. In Wireshark filter `dhcp.option.type == 82` and `dhcp.ip.relay != 0.0.0.0` to find relayed messages.

## Key takeaways

- A relay agent converts client broadcasts into unicast to the server, stamps `giaddr` with its client-side interface address and sends from and to UDP port 67.
- The server selects the scope from `giaddr` and replies unicast to `giaddr`.
- T1 renewals are direct unicast to the server; T2 rebinding broadcasts and so passes through a relay again.
- `ip helper-address` also forwards other UDP broadcast services unless they are turned off.
- Option 82 carries circuit ID (sub-option 1) and remote ID (sub-option 2) per RFC 3046 and is invisible to the client.
- A reservation keys on MAC or client ID and must fall inside the scope chosen for the client.
- DHCP snooping drops OFFER, ACK and NAK from untrusted ports, validates `chaddr`, rate-limits, and builds the MAC/IP/VLAN/port binding table.
- The binding table feeds Dynamic ARP Inspection and IP Source Guard; trusting the uplink is mandatory.
