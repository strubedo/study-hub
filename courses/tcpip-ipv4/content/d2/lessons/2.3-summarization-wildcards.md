## Summarization (route aggregation)

**Summarization**, also called **supernetting** or aggregation, replaces several contiguous routes with one shorter-prefix route that covers exactly the same addresses. It is CIDR in reverse: instead of cutting a block into pieces, you combine pieces into one block. Benefits are smaller routing tables, less churn (a flapping /24 inside a summary is invisible beyond the summarising router) and faster convergence.

### When can a set of routes be summarized exactly?

Three conditions must hold together:

1. The networks are **contiguous** (no gaps).
2. The count of equal-sized blocks is a **power of two** (2, 4, 8, 16...).
3. The first network address is **aligned**: it is a multiple of the total size of the combined block.

If any condition fails, one summary would either leave addresses out or include addresses you don't own. In that case, you use several summaries or accept an over-summary.

### The longest-common-prefix method

Write the networks in binary and keep the leading bits they all share. The count of shared bits is the summary prefix length. Take `10.1.4.0/24`, `10.1.5.0/24`, `10.1.6.0/24`, `10.1.7.0/24`. The first two octets are identical (16 bits). The third octets in binary:

```text
4  00000100
5  00000101
6  00000110
7  00000111
   ------
   000001 -> first 6 bits identical
```

Shared bits: 16 + 6 = 22. Zero the rest: the summary is `10.1.4.0/22` (mask `255.255.252.0`). It covers 10.1.4.0-10.1.7.255, exactly the four /24s. Check with the block-size method: a /22 has block size 4 in the third octet and 4 is a multiple of 4.

A shortcut that skips the binary: size = number of /24s (4), so mask octet = 256 - 4 = 252 in the third octet, and the first network (4) is a multiple of 4. Same answer.

### More examples

| Networks | Single summary? | Result |
|---|---|---|
| 172.16.32.0/24 through 172.16.39.0/24 (8 blocks) | Yes (32 is a multiple of 8) | `172.16.32.0/21` |
| 10.8.0.0/16 through 10.11.0.0/16 (4 blocks) | Yes | `10.8.0.0/14` |
| 192.168.16.0/24 through 192.168.21.0/24 (6 blocks) | No: 6 is not a power of two | `192.168.16.0/22` + `192.168.20.0/23` |
| 10.1.3.0/24 through 10.1.6.0/24 (4 blocks) | No: 3 is not a multiple of 4 | `10.1.3.0/24`, `10.1.4.0/23`, `10.1.6.0/24` |
| 192.168.1.0/24 through 192.168.4.0/24 (4 blocks) | No: 1 is not a multiple of 4 | `192.168.1.0/24`, `192.168.2.0/23`, `192.168.4.0/24` |

The 192.168.16-21 case splits into the largest aligned pieces: 16-19 is a /22, and 20-21 is a /23. For the 10.1.3-6 case the only single route covering them all is `10.1.0.0/21` (10.1.0.0-10.1.7.255), which also claims 10.1.0.x, 10.1.1.x, 10.1.2.x and 10.1.7.x. That is an **over-summary**.

> **Watch out:** An over-summary advertises addresses you don't have. Traffic to an unused address inside the summary is attracted to your router and then dropped or looped. When the summarising router has a default route pointing back toward the sender, you get a routing loop until the TTL expires. Always add a **discard route** (below).

### Longest-prefix match and summaries

A router chooses the route with the longest matching prefix. A summary `10.1.4.0/22` and a more specific `10.1.5.0/24` can coexist: packets for 10.1.5.9 use the /24, everything else in 10.1.4.0-10.1.7.255 uses the /22. This is also how a **leak** works: advertising specific routes beside a summary overrides it for those prefixes (useful for traffic engineering, harmful when accidental).

### Summarising on Cisco IOS

```text
! Static summary with a discard route (stops loops for addresses with no specific route)
R1(config)# ip route 10.1.4.0 255.255.252.0 Null0

! OSPF area range on an ABR
R1(config-router)# area 1 range 10.1.4.0 255.255.252.0

! EIGRP interface summary
R1(config-if)# ip summary-address eigrp 100 10.1.4.0 255.255.252.0
```

OSPF's `area range` and EIGRP's `ip summary-address` automatically install a route to Null0 for the summary in the summarising router (administrative distance 110 for the OSPF discard route and 5 for EIGRP's), so packets to unreachable addresses inside the summary are dropped locally rather than looped. Verify with `show ip route 10.1.4.0 255.255.252.0` and look for `via Null0`.

## Wildcard masks

Cisco ACLs, OSPF `network` commands and EIGRP `network` commands use a **wildcard mask**, not a subnet mask. A wildcard bit of **0 means "this bit must match"** and **1 means "ignore this bit"**. For a contiguous subnet mask the wildcard is its inverse:

**wildcard = 255.255.255.255 - subnet mask**

| Prefix | Subnet mask | Wildcard |
|---|---|---|
| /32 | 255.255.255.255 | 0.0.0.0 (also `host`) |
| /30 | 255.255.255.252 | 0.0.0.3 |
| /27 | 255.255.255.224 | 0.0.0.31 |
| /26 | 255.255.255.192 | 0.0.0.63 |
| /24 | 255.255.255.0 | 0.0.0.255 |
| /22 | 255.255.252.0 | 0.0.3.255 |
| /21 | 255.255.248.0 | 0.0.7.255 |
| /0 | 0.0.0.0 | 255.255.255.255 (also `any`) |

In the interesting octet the wildcard is simply block size - 1. A /26 has block size 64, so 63; a /21 has block size 8 in the third octet, so 7.

An ACL entry matches an address when every bit the wildcard marks as "must match" equals the same bit of the stated address:

```text
R1(config)# access-list 10 permit 10.1.4.0 0.0.3.255
```

This permits 10.1.4.0 through 10.1.7.255 (third octet 4-7, any fourth octet): the same four /24s summarized above. The ACL form `10.1.4.0 0.0.3.255` is the inverse-mask spelling of `10.1.4.0/22`.

The same notation works in OSPF: `network 10.1.4.0 0.0.3.255 area 0` enables OSPF on every interface whose address falls inside 10.1.4.0/22.

> **Exam tip:** A wildcard mask is only "the inverted subnet mask" when the pattern is contiguous. The wildcard `0.0.0.254` on `192.168.10.1` is legal: bit 0 must be 1 and the other seven bits are ignored, so it matches every **odd** host in 192.168.10.0/24 (.1, .3, .5, ... .255). No subnet mask can express that. Wildcards are bit patterns, subnet masks are prefix lengths.

> **Watch out:** An inverted-mask mix-up silently changes meaning. `permit 10.1.4.0 255.255.252.0` (subnet mask instead of wildcard) says "ignore the first 22 bits, match the last 10", which is almost never what you want, and IOS will usually accept it without complaint. Check the third octet: wildcards carry small numbers (0, 1, 3, 7, 15...) in the interesting octet and 255s in the host part; masks do the reverse.

## Lab it yourself

Use Python to derive both a summary and its wildcard, then confirm that the ACL range you expect is the range you get:

```text
$ python3 -c "
import ipaddress as i
nets = [i.ip_network('10.1.%d.0/24' % k) for k in range(4, 8)]
s = list(i.collapse_addresses(nets))
print(s, s[0].netmask, s[0].hostmask)
print(list(i.summarize_address_range(i.ip_address('10.1.3.0'), i.ip_address('10.1.6.255'))))"
[IPv4Network('10.1.4.0/22')] 255.255.252.0 0.0.3.255
[IPv4Network('10.1.3.0/24'), IPv4Network('10.1.4.0/23'), IPv4Network('10.1.6.0/24')]
```

`hostmask` is Python's name for the wildcard. On two Cisco routers, put loopbacks `10.1.4.1/24` to `10.1.7.1/24` on R2 in OSPF area 1 and make R2 an ABR by also placing its link to R1 in area 0. R1 then lists four /24 inter-area (`O IA`) routes in `show ip route ospf`. Add `area 1 range 10.1.4.0 255.255.252.0` on R2 and the four routes collapse into one `10.1.4.0/22` on R1 (alternatively use an EIGRP `ip summary-address`). Check that R2 now shows a `Null0` route for the summary. Finally, add `access-list 10 permit 10.1.4.0 0.0.3.255` and test with `show access-lists 10` and `show ip route 10.1.6.99` to confirm which addresses would match.

## Key takeaways

- Summarization combines contiguous, aligned, power-of-two sets of routes into one shorter prefix.
- The summary prefix length equals the count of leading bits the networks share (longest common prefix).
- Six or three blocks, or a start that is not a multiple of the combined size, cannot be one exact summary.
- Over-summarising attracts traffic for addresses you don't own; use a Null0 discard route (OSPF and EIGRP add one automatically).
- Longest-prefix match lets a specific route override a summary.
- Wildcard mask = 255.255.255.255 minus the subnet mask for contiguous prefixes; 0 bit = must match, 1 bit = ignore.
- In the interesting octet wildcard = block size - 1; `host` = 0.0.0.0 and `any` = 255.255.255.255.
- Wildcards can be discontiguous (for example `0.0.0.254`); subnet masks cannot.
