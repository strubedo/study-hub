## Identification, flags and fragment offset

The second 32-bit word of the IPv4 header exists to support **fragmentation**: splitting a datagram that is too big for a link into pieces that each fit the MTU. Domain 3 covers the mechanics of path MTU discovery; here we decode the fields.

| Field | Size | Meaning |
|---|---|---|
| Identification | 16 bits | Chosen by the sender; **all fragments of one datagram carry the same value** |
| Flags | 3 bits | Bit 0 reserved (must be 0); bit 1 **DF** (Don't Fragment); bit 2 **MF** (More Fragments) |
| Fragment Offset | 13 bits | Position of this fragment's data in the original datagram, in **units of 8 bytes** |

In the 16-bit word that holds flags and offset, the flags are the top three bits. That makes the common values easy to recognise in hex:

| Flags/offset word | Meaning |
|---|---|
| `0x4000` | DF set, offset 0: do not fragment (typical for TCP and PMTUD-aware senders) |
| `0x0000` | Not fragmented, fragmenting allowed |
| `0x2000` | MF set, offset 0: first fragment |
| `0x20b9` | MF set, offset 0xb9 = 185 (byte offset 1480): a middle fragment |
| `0x0172` | MF clear, offset 0x172 = 370: last fragment |

A datagram is **unfragmented** when MF = 0 and offset = 0. A **last fragment** has MF = 0 and a non-zero offset.

### A worked fragmentation

A host sends an IP datagram with total length 4000 bytes (20-byte header + 3980 bytes of data) across a link with MTU 1500. Each fragment gets its own 20-byte header, leaving at most 1480 bytes of data, which is 185 units of 8 bytes. Every fragment except the last must carry a multiple of 8 data bytes, and 1480 qualifies.

| Fragment | Data bytes | Total length | MF | Offset field |
|---|---|---|---|---|
| 1 | 1480 | 1500 | 1 | 0 |
| 2 | 1480 | 1500 | 1 | 185 (byte 1480) |
| 3 | 1020 | 1040 | 0 | 370 (byte 2960) |

1480 + 1480 + 1020 = 3980, the original data. Three headers were sent instead of one, so fragmentation adds overhead of 20 bytes per extra fragment.

Key rules:

- **Reassembly happens only at the final destination.** Routers fragment but never reassemble. The receiver matches fragments by the tuple (source, destination, protocol, identification) and places them by offset.
- Losing **any one fragment** loses the whole datagram: the receiver times out reassembly and discards the rest. The ICMP time exceeded code 1 ("fragment reassembly time exceeded") may be sent.
- Only the first fragment carries the transport header, so a firewall or a stateful filter that matches on ports cannot classify later fragments without reassembling.
- The maximum offset is 8191 x 8 = 65 528 bytes, which is why the largest legal datagram is 65 535 bytes.
- A router that must forward a packet larger than the next link's MTU while **DF = 1** drops it and returns ICMP type 3, code 4 ("fragmentation needed and DF set"). Hosts use this to find the path MTU.
- Fragments can be fragmented further on a smaller-MTU link; offsets stay relative to the original datagram.

> **Watch out:** Many firewalls drop fragments or ICMP type 3 code 4, causing connections that work for small packets but hang on large ones. This is the PMTUD black hole; it is the commonest symptom of an MTU problem.

## TTL

The **Time to Live** field is 8 bits, so the maximum is 255. Its original meaning was seconds, but in practice it is a **hop count**: each router that forwards the packet decrements it by 1. If a router's decremented value would be 0, it discards the packet and sends an ICMP **Time Exceeded (type 11, code 0)** message to the source. That behaviour is what makes `traceroute` work and is the loop-breaker that stops misrouted packets from circulating forever. (Ethernet frames have no such field, so a layer 2 loop is far worse.)

A packet that arrives at a router with TTL 1 is therefore not forwarded. If it is addressed to the router itself, it is delivered normally.

Initial TTLs are chosen by the sending operating system:

| Source | Default initial TTL |
|---|---|
| Linux, macOS, Android | 64 |
| Windows | 128 |
| Cisco IOS routers (locally generated) | 255 |

A reply that arrives with TTL 117 most probably started at 128, so about 11 hops were crossed; a reply with TTL 57 probably started at 64. This is an estimate, since TTLs can be set by policy or modified by devices. The IPv6 equivalent is called the hop limit; IPv4 has TTL.

TTL is also used deliberately: the Generalized TTL Security Mechanism (GTSM, RFC 5082) has directly connected BGP peers send with TTL 255 and accept only packets that still arrive with TTL 255, and multicast applications use TTL 1 to stay on the local subnet.

## Protocol numbers

The 8-bit **Protocol** field tells the receiving IP layer which upper-layer protocol owns the payload. It plays the same role as EtherType does for Ethernet. Values are assigned by IANA in the Protocol Numbers registry:

| Number | Protocol | Reference |
|---|---|---|
| 1 | ICMP | RFC 792 |
| 2 | IGMP | RFC 1112 |
| 4 | IPv4 encapsulation (IP-in-IP) | RFC 2003 |
| 6 | TCP | RFC 9293 |
| 17 | UDP | RFC 768 |
| 41 | IPv6 encapsulation | RFC 2473 |
| 47 | GRE | RFC 2784 |
| 50 | ESP (IPsec) | RFC 4303 |
| 51 | AH (IPsec) | RFC 4302 |
| 89 | OSPF | RFC 2328 |
| 103 | PIM | RFC 7761 |
| 112 | VRRP | RFC 9568 |
| 132 | SCTP | RFC 9260 (IANA lists the registrant, not the RFC) |

Protocols 1, 6, 17, 47, 50 and 89 are the ones to know by heart. Note that ESP and GRE are not carried over TCP or UDP, so they have no ports; a firewall must permit them by protocol number. OSPF also runs directly over IP (protocol 89) with multicast destinations 224.0.0.5 and 224.0.0.6. BGP, in contrast, runs over TCP port 179.

## Header checksum

The **header checksum** protects only the IPv4 header, not the payload. It is the 16-bit one's complement of the one's complement sum of all 16-bit words in the header, computed with the checksum field set to zero.

Using the header from the previous lesson, `45 00 00 54 1c 46 40 00 40 01 [checksum] c0 00 02 0a c0 00 02 01`:

```text
0x4500 + 0x0054 + 0x1c46 + 0x4000 + 0x4001 + 0x0000
       + 0xc000 + 0x020a + 0xc000 + 0x0201
= 0x265a6   (sum of ten 16-bit words, with a carry out of bit 15)
fold the carry: 0x65a6 + 0x0002 = 0x65a8
checksum = ~0x65a8 = 0x9a57
```

The receiver sums every word including the checksum. A valid header gives `0xFFFF` (one's complement zero). Verification is cheap, so each router checks the header on arrival and silently discards a packet that fails.

Because **TTL changes at every hop**, every router must update the checksum. Here the TTL falls from 64 to 63, so the 16-bit word `0x4001` becomes `0x3f01`, a decrease of 0x0100, and the checksum rises by 0x0100 to `0x9b57`. Routers use an incremental update (RFC 1624) instead of a full recomputation. NAT also modifies addresses and therefore the IP checksum, plus the TCP or UDP checksum.

The TCP and UDP checksums are separate: they cover the segment plus a **pseudo-header** built from the IP source, destination, protocol and length. If a capture taken on the sending machine shows "checksum incorrect (maybe caused by checksum offload)", it is usually the NIC filling the checksum after the capture point; it is harmless.

## Source and destination addresses

Each address is **32 bits**. The router forwards using only the **destination** address, comparing it against the routing table. The source address is where replies and ICMP errors go. Neither changes in transit except through NAT. Because the source address is not authenticated, it can be forged, which is the basis of reflection attacks; ingress filtering (BCP 38) and unicast reverse path forwarding (`ip verify unicast source reachable-via rx` on Cisco, `rp_filter` on Linux) discard packets whose source address could not be reached back through the arrival interface. Address classes, subnetting and special ranges are the subject of Domain 2.

## Lab it yourself

1. Force fragmentation on Linux with a UDP-style ping that disables PMTUD: `ping -M dont -s 3000 192.0.2.1`. Capture with `sudo tcpdump -nn -v -i eth0 icmp` and observe fragments with `flags [+]` and increasing `offset` values (0, 1480, ...). On Windows use `ping -l 3000 192.0.2.1`; Windows does not set DF by default.
2. Set DF with `ping -M do -s 3000 192.0.2.1`; the ping fails locally with "message too long, mtu=1500". Add `-s 1472` to see it pass.
3. Use Wireshark filters: `ip.flags.mf == 1`, `ip.frag_offset > 0`, `ip.flags.df == 1`, `ip.ttl < 5`, `ip.proto == 47`, `ip.checksum.status == "Bad"`.
4. Run `traceroute -n 198.51.100.7` (Linux) or `tracert -d 198.51.100.7` (Windows) and capture. Each probe has a TTL from 1 upward, and each hop answers with ICMP type 11 code 0.
5. Compute the checksum of your own captured ping header with a short script (sum 16-bit words, fold carries, invert) and compare with Wireshark. Send with `ping -t 5` (Linux) to see TTL 5 expire.

## Key takeaways

- All fragments share the Identification value; MF = 1 on every fragment but the last; offset is in 8-byte units.
- Flags are reserved/DF/MF; `0x4000` means DF set and not fragmented.
- Routers fragment but only the destination reassembles; one lost fragment loses the datagram.
- DF = 1 plus a too-large packet yields ICMP type 3 code 4.
- TTL is decremented by every router; reaching 0 triggers ICMP type 11 code 0. Defaults: Linux 64, Windows 128, Cisco IOS 255.
- Know protocol numbers 1 ICMP, 6 TCP, 17 UDP, 47 GRE, 50 ESP, 89 OSPF; ESP, GRE and OSPF have no ports.
- The header checksum covers only the header, is the one's complement of the one's complement sum, and is recomputed at every hop because TTL changes.
- Routers forward on the destination address only; source addresses are unauthenticated.
