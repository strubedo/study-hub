## Why ARP exists

An IPv4 host that wants to send to 192.0.2.20 on its own subnet must build an Ethernet frame, which needs the destination **MAC** address. The **Address Resolution Protocol** (RFC 826) maps a protocol address (here IPv4) to a hardware address (here Ethernet MAC) on the local link. ARP is not carried in IP: it has its own EtherType, **0x0806**, which is why it is often placed between layer 2 and layer 3.

## ARP message format

RFC 826 designed ARP to be independent of both address types. The message is 28 bytes for IPv4 over Ethernet:

| Field | Size | Value for IPv4 over Ethernet |
|---|---|---|
| Hardware type (HTYPE) | 2 bytes | 1 (Ethernet) |
| Protocol type (PTYPE) | 2 bytes | 0x0800 (IPv4) |
| Hardware address length (HLEN) | 1 byte | 6 |
| Protocol address length (PLEN) | 1 byte | 4 |
| Operation (OPER) | 2 bytes | 1 = request, 2 = reply |
| Sender hardware address (SHA) | 6 bytes | Sender's MAC |
| Sender protocol address (SPA) | 4 bytes | Sender's IP |
| Target hardware address (THA) | 6 bytes | Ignored in a request (conventionally all zeros); the requester's MAC in a reply |
| Target protocol address (TPA) | 4 bytes | The IP being resolved |

The Ethernet header around it is 14 bytes, and the frame is padded to the 46-byte payload minimum, so ARP frames are 60 bytes in a capture (64 with FCS). Operation codes 3 and 4 belong to RARP (reverse ARP), a historical protocol; do not confuse them with ARP.

## The exchange

```text
Host A 192.0.2.10 (00:1a:2b:3c:4d:5e) wants 192.0.2.20

1  ARP request   Eth dst ff:ff:ff:ff:ff:ff  src 00:1a:2b:3c:4d:5e   type 0x0806
                 "Who has 192.0.2.20? Tell 192.0.2.10"   (SHA/SPA = A, THA = 00:00:00:00:00:00, TPA = 192.0.2.20)
2  ARP reply     Eth dst 00:1a:2b:3c:4d:5e  src 00:50:56:aa:bb:cc  type 0x0806
                 "192.0.2.20 is at 00:50:56:aa:bb:cc"
3  A caches the mapping and sends the queued IP packet.
```

Two details are easy to miss. The request is **broadcast** (all hosts in the broadcast domain examine it), but the reply is **unicast** straight to the requester. And the receiver of a request that names its own IP also learns the sender's mapping from the SHA/SPA fields, so A's entry for B and B's entry for A usually appear together after one exchange.

Wireshark shows this as `Who has 192.0.2.20? Tell 192.0.2.10` and `192.0.2.20 is at 00:50:56:aa:bb:cc`. The filter `arp.opcode == 1` shows requests and `arp.opcode == 2` replies.

## The ARP cache

Hosts keep resolved mappings in an **ARP cache** (the neighbour table on Linux) to avoid asking for every packet. Entries age out, because an IP address may move to a different NIC:

- **Linux** keeps the entry in states such as REACHABLE, STALE, DELAY, PROBE, INCOMPLETE and FAILED, with PERMANENT for static entries. A reachable entry lasts a randomised time centred on `base_reachable_time_ms` (default 30 000 ms, so roughly 15 to 45 seconds), after which it becomes STALE and is used but re-verified with a unicast probe when traffic needs it.
- **Windows** also uses a randomised reachable time based on 30 seconds for dynamic entries.
- **Cisco IOS** keeps dynamic ARP entries for **4 hours** (14 400 seconds) by default; change it per interface with `arp timeout`.

```text
$ ip neigh show
192.0.2.1 dev eth0 lladdr 00:50:56:aa:bb:cc REACHABLE
192.0.2.20 dev eth0 lladdr 00:50:56:11:22:33 STALE

C:\> arp -a
Interface: 192.0.2.10 --- 0x4
  Internet Address      Physical Address      Type
  192.0.2.1             00-50-56-aa-bb-cc     dynamic
```

**Static entries** do not age and are never overwritten by ARP traffic: `arp -s 192.0.2.50 00-11-22-33-44-55` (Windows, and Linux net-tools), `ip neigh replace 192.0.2.50 lladdr 00:11:22:33:44:55 dev eth0 nud permanent` (Linux iproute2), `arp 192.0.2.50 0011.2233.4455 arpa` (Cisco IOS global configuration). Delete with `arp -d`, `ip neigh del`, or `clear arp-cache` / `clear ip arp` on IOS.

## Local versus remote destinations

A host decides with its own address and subnet mask. If the destination is **inside** the local subnet, it ARPs for the destination itself. If it is **outside**, it sends to the **default gateway**, so it ARPs for the *gateway's* IP and puts the gateway's MAC in the frame while the IP destination remains the remote host.

```text
Host 192.0.2.10/24, gateway 192.0.2.1, ping 198.51.100.7
ARP request: Who has 192.0.2.1? (not 198.51.100.7)
Frame:  dst MAC = gateway MAC     IP dst = 198.51.100.7
```

If the gateway cannot be resolved, the ping fails with "Destination host unreachable" from the local host and the capture shows repeated ARP requests with no reply. A wrong mask is a common cause: a host with a /16 mask thinks 192.0.2.99 and 192.0.3.5 are both local and sends ARP requests nobody answers.

## Gratuitous ARP, probes and duplicate detection

Beyond the request/reply pair, ARP packets are used for announcements. The terms are defined in **RFC 5227** (IPv4 Address Conflict Detection):

| Packet | Sender IP | Target IP | Purpose |
|---|---|---|---|
| **ARP Probe** | 0.0.0.0 | The address being tested | Ask "is anyone using this?" without polluting caches |
| **ARP Announcement** (gratuitous ARP) | Own address | Same own address | Say "this is my address and MAC"; refresh neighbours' caches |

A standard-conforming host that gets a new address (manual, DHCP, link-local) sends **3 probes** (PROBE_NUM) spaced 1 to 2 seconds apart (after an initial random delay up to 1 second), waits **2 seconds**, then sends **2 announcements** 2 seconds apart. If anyone replies to a probe, or another host's probe targets the same address, the address is in conflict and must not be used. After the address is in use, a host that sees a conflicting ARP can defend once and should not defend more often than every 10 seconds (DEFEND_INTERVAL). RFC 5227 prefers ARP **requests** for both probes and announcements, though many stacks still send gratuitous ARP as a reply.

Uses of gratuitous ARP in the field: updating switch and neighbour caches after a first-hop redundancy failover (HSRP, VRRP), after a server NIC failover or VM live migration, and duplicate address detection when an interface comes up. Windows warns of address conflicts and Linux tools can test with `arping -D` (see lab).

### Proxy ARP

With **proxy ARP** (RFC 1027) a router answers ARP requests on behalf of hosts that are on another network, supplying its own MAC. The requester believes the remote host is on-link and sends frames to the router. It was used to hide subnetting from hosts without a gateway setting. It still appears with mis-masked hosts, VPN and some NAT designs. Cisco IOS enables it by default per interface (`ip proxy-arp`; disable with `no ip proxy-arp`); on Linux it is `sysctl net.ipv4.conf.eth0.proxy_arp=1`. Proxy ARP enlarges ARP caches and can mask configuration errors.

## ARP spoofing and mitigations

ARP has **no authentication**. A host can send an unsolicited reply claiming "192.0.2.1 is at my MAC" and neighbours that accept it will send traffic to the attacker, enabling man-in-the-middle or denial of service. Mitigations:

- **Dynamic ARP Inspection (DAI)** on switches checks ARP packets against the **DHCP snooping binding table** (or static ARP ACLs) and drops mismatches. Configure `ip dhcp snooping`, `ip dhcp snooping vlan 10`, `ip arp inspection vlan 10`, and trust uplinks with `ip arp inspection trust`.
- DHCP snooping, port security, and 802.1X to limit who can connect.
- Static ARP entries for critical hosts such as gateways (hard to scale).
- Segmentation with VLANs to shrink the broadcast domain, and monitoring tools such as arpwatch.

> **Exam tip:** ARP is link-local. It is never forwarded by a router (it is not routed IP), and the target of an ARP request is always on the sender's own broadcast domain.

## Lab it yourself

1. `ip neigh flush all` (Linux, root) or `arp -d *` (Windows, administrator), start a capture (`sudo tcpdump -nn -e -i eth0 arp`) and ping your gateway. Identify the broadcast request and unicast reply, and read the MACs.
2. `ping` a remote address and confirm the ARP request names the **gateway**, not the remote host.
3. Add a static entry for a nonexistent MAC and watch pings fail while no ARP traffic appears: `sudo ip neigh replace 192.0.2.99 lladdr 02:00:00:00:00:99 dev eth0 nud permanent`.
4. Send a gratuitous announcement: `sudo arping -U -c 2 -I eth0 -s 192.0.2.10 192.0.2.10`. Test for a duplicate with `sudo arping -D -c 3 -I eth0 192.0.2.10` (iputils arping; the exit status is 0 if no one replied).
5. In Wireshark use `arp.isgratuitous`, `arp.isprobe` and `arp.duplicate-address-detected`. On a Cisco device compare `show ip arp` with `show ip interface GigabitEthernet0/1 | include Proxy`.

## Key takeaways

- ARP (RFC 826, EtherType 0x0806) maps an IPv4 address to a MAC on the local link; requests are broadcast, replies are unicast.
- The IPv4/Ethernet ARP message is 28 bytes: HTYPE 1, PTYPE 0x0800, HLEN 6, PLEN 4, operation 1 (request) or 2 (reply).
- For remote destinations a host ARPs for its default gateway, not the destination.
- Dynamic entries age (Linux roughly 15 to 45 s reachable, IOS 4 hours); static entries do not.
- An RFC 5227 probe has sender IP 0.0.0.0; an announcement has sender and target IP equal to the new address.
- Probe sequence: 3 probes, wait 2 s, 2 announcements 2 s apart; defend at most every 10 s.
- Proxy ARP answers for off-link hosts with the router's MAC.
- ARP is unauthenticated; defend with DHCP snooping plus Dynamic ARP Inspection and port security.
