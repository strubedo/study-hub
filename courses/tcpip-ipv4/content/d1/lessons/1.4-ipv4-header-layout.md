## The header at a glance

RFC 791 defines the IPv4 header as a series of 32-bit words. The fixed part is **20 bytes** (five words); options may extend it to a maximum of 60 bytes.

| Field | Size | Notes |
|---|---|---|
| Version | 4 bits | Always 4 |
| IHL | 4 bits | Header length in 32-bit words; minimum 5 |
| DSCP | 6 bits | Differentiated services code point |
| ECN | 2 bits | Explicit congestion notification |
| Total Length | 16 bits | Header + data, in bytes |
| Identification | 16 bits | Groups fragments of one datagram |
| Flags | 3 bits | Reserved, DF, MF |
| Fragment Offset | 13 bits | In units of 8 bytes |
| TTL | 8 bits | Hop limit |
| Protocol | 8 bits | Payload protocol number |
| Header Checksum | 16 bits | Covers the header only |
| Source / Destination Address | 32 bits each | |
| Options | 0 to 320 bits | Padded to a multiple of 32 bits |

This lesson covers the first row group: version, length, options, DSCP and ECN. The next lesson, "Fragmentation, TTL, Protocol Numbers and the Header Checksum", covers the rest.

## Version, IHL and total length

**Version** is 4 for IPv4 (IPv6 uses 6). In a hex dump the first byte of an IPv4 packet is therefore `4x`, and `45` is by far the most common value: version 4, IHL 5.

**IHL** counts 32-bit words, not bytes. IHL 5 means 5 x 4 = 20 bytes (no options); the largest possible value, 15, means 60 bytes, leaving 40 bytes for options. Any IHL below 5 is invalid. To find where the payload starts, multiply IHL by 4. This is the standard offset trick in packet filters: `ip[0] & 0xf` yields IHL in tcpdump syntax.

**Total length** is the size in bytes of the whole IP datagram, header plus data, so the maximum is 2^16 - 1 = **65 535 bytes**. It does not include the Ethernet header, FCS or any Ethernet padding. This field is how a receiver discards the zero padding added to short frames: a 28-byte ARP message is padded, but a 40-byte TCP ACK in a minimum-size frame carries 6 bytes of padding that the IP total length (40) tells the stack to ignore.

Data length = total length - (IHL x 4). A packet with total length 84 and IHL 5 carries 64 bytes of payload, exactly an ICMP echo with the default 56-byte ping data.

### Options

Options are rare in modern traffic. They are variable length and must be padded to a 32-bit boundary with option bytes of 0 (end of option list) or 1 (no-operation). Examples from RFC 791 and later:

| Option | Type value | Use |
|---|---|---|
| End of Option List | 0 | Terminates the list |
| No Operation | 1 | Padding between options |
| Record Route | 7 | Each router records its address (limited to 9 addresses by the 40-byte space) |
| Timestamp | 68 | Routers record timestamps |
| Loose Source Route | 131 | Sender-specified path; routers may add hops |
| Strict Source Route | 137 | Sender-specified exact path |
| Router Alert | 148 | Tells routers to examine the packet closely (IGMP, RSVP; RFC 2113) |

Packets with options are often handled on a router's slow path (software) and are frequently dropped by firewalls, because source routing can be abused to bypass access controls. Cisco IOS disables it with `no ip source-route`; Linux defaults `net.ipv4.conf.all.accept_source_route` to 0 on modern distributions.

> **Real world:** The 40-byte option limit is why `ping -R` and `traceroute` cannot rely on Record Route: nine hops fill it. Traceroute uses TTL expiry instead.

## DSCP and ECN: the former ToS byte

The second byte of the header was originally the **Type of Service** field (RFC 791): 3 bits of precedence, then delay, throughput and reliability flags. RFC 2474 redefined its top 6 bits as the **DS field / DSCP** and RFC 3168 took the remaining 2 bits for **ECN**.

```text
bit:   7  6  5  4  3  2 | 1  0
       ----- DSCP ----- | ECN
```

### DSCP

The 6-bit **DSCP** value selects a per-hop behaviour (PHB) in routers and switches, meaning a queueing and drop treatment, for quality of service (QoS). Common code points:

| PHB | DSCP (decimal) | DSCP (binary) | Full byte (hex) | Typical use |
|---|---|---|---|---|
| Default (best effort) / CS0 | 0 | 000000 | 0x00 | Normal traffic |
| CS1 | 8 | 001000 | 0x20 | Scavenger / bulk |
| AF11 | 10 | 001010 | 0x28 | Low-priority data |
| AF21 | 18 | 010010 | 0x48 | Transactional data |
| AF31 | 26 | 011010 | 0x68 | Mission-critical |
| AF41 | 34 | 100010 | 0x88 | Interactive video |
| CS6 | 48 | 110000 | 0xC0 | Network control (routing protocols) |
| EF | 46 | 101110 | 0xB8 | Voice, low latency |

The class selector codepoints CS0 to CS7 have the pattern `xxx000` and preserve compatibility with old IP precedence (CS5 = DSCP 40 = precedence 5). Assured Forwarding AFxy has class x (1 to 4) and drop precedence y (1 to 3); the DSCP is 8x + 2y, so AF41 is 8 x 4 + 2 x 1 = 34. To convert DSCP to the legacy byte, shift left two bits (multiply by 4): EF 46 becomes 184 = 0xB8.

DSCP markings are advisory and are only honoured inside a domain that trusts them. Providers often re-mark or clear them at the edge, and routers do not need to read them to forward correctly.

### ECN

RFC 3168 gives the two ECN bits four values:

| ECN bits | Name | Meaning |
|---|---|---|
| 00 | Not-ECT | Transport does not support ECN |
| 01 | ECT(1) | ECN-capable transport |
| 10 | ECT(0) | ECN-capable transport |
| 11 | CE | Congestion Experienced, set by a router instead of dropping |

With ECN, a congested router can mark an ECN-capable packet CE instead of dropping it. The receiver echoes this to the sender in the transport protocol (TCP uses the ECE and CWR flags, covered in Domain 3), and the sender reduces its rate. Only Not-ECT packets are dropped to signal congestion. Linux enables ECN for incoming connections by default (`net.ipv4.tcp_ecn=2`) and for outgoing only when set to 1.

> **Exam tip:** Given a byte `0xB8` in the ToS/DS position: 0xB8 = 1011 1000, so DSCP = 101110 = 46 (EF) and ECN = 00. Given `0x03` in the low bits: ECN = 11 = CE.

## Reading a real header

```text
45 00 00 54 1c 46 40 00 40 01 9a 57 c0 00 02 0a c0 00 02 01
```

Byte by byte: version 4, IHL 5 (20 bytes), DSCP/ECN 0, total length 0x0054 = 84, identification 0x1c46, flags/offset 0x4000 (DF set, offset 0), TTL 0x40 = 64, protocol 1 (ICMP), checksum 0x9a57, source `c0 00 02 0a` = 192.0.2.10, destination `c0 00 02 01` = 192.0.2.1. This is an unfragmented ping from a Linux host (TTL 64, DF set).

## Lab it yourself

1. Capture one ping with `sudo tcpdump -nn -v -c 2 -i eth0 icmp`. The `-v` output prints `tos`, `ttl`, `id`, `offset`, `flags`, `proto`, `length`. Identify each field from the dump above.
2. Set a DSCP value on outgoing probes: `ping -Q 0xb8 192.0.2.1` on Linux (the value is the whole ToS byte, so 0xB8 = EF). In Wireshark expand Differentiated Services Field and check `ip.dsfield.dscp == 46` and `ip.dsfield.ecn`.
3. In tcpdump syntax, match EF traffic with `'ip[1] >> 2 == 46'`, and packets with options with `'ip[0] & 0xf > 5'`.
4. Open any capture, expand IPv4 and click Version, Header Length, Total Length. Verify that Wireshark's "Header Length: 20 bytes (5)" matches the first byte, and that Total Length equals the frame length minus 14 for untagged Ethernet.
5. On a Cisco IOS router, create a class map matching `ip dscp ef` and apply a policy map; use `show policy-map interface` to count matched packets while pinging with the extended `ping` command, setting its Type of Service field to 184 (the decimal ToS byte for EF).

## Key takeaways

- The IPv4 header is 20 bytes minimum, 60 maximum; IHL counts 32-bit words (5 to 15).
- Total length is the whole datagram in bytes (maximum 65 535) and lets the receiver strip Ethernet padding.
- Payload length = total length - IHL x 4.
- Options (Record Route 7, Timestamp 68, LSRR 131, SSRR 137, Router Alert 148) are rare and often dropped; at most 40 bytes.
- The ToS byte is now 6 bits of DSCP plus 2 bits of ECN.
- EF is DSCP 46 (byte 0xB8); AF41 is 34; CS6 is 48; AFxy has DSCP 8x + 2y.
- ECN values: 00 Not-ECT, 01 ECT(1), 10 ECT(0), 11 CE.
- DSCP is a marking, honoured only where the network trusts it.
