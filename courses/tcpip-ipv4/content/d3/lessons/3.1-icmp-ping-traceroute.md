## What ICMP is and is not

The Internet Control Message Protocol (RFC 792) is the IP layer's error-reporting and diagnostic companion. It is carried directly inside IPv4 as **protocol number 1** (no TCP or UDP header, so no ports). Every ICMP message starts with the same four bytes, followed by four type-specific bytes and then a body:

| Field | Size | Purpose |
|---|---|---|
| Type | 1 byte | Message class (echo, unreachable, time exceeded, ...) |
| Code | 1 byte | Sub-type within the type |
| Checksum | 2 bytes | One's complement checksum over the whole ICMP message (header and data) |
| Rest of header | 4 bytes | Depends on the type: identifier + sequence for echo, next-hop MTU for type 3 code 4, gateway address for redirect, pointer for parameter problem |

ICMP does not make IP reliable. It reports some problems, some of the time, and routers are free to rate-limit or suppress it. An error message carries the **original IP header plus at least the first 8 bytes** of the offending datagram's payload (enough to see the TCP/UDP ports), which is how the sending host matches the error to a socket. Hosts must never send an ICMP error about an ICMP error, about a broadcast or multicast destination, or about a non-first fragment, which prevents error storms.

## The types and codes to know

| Type | Name | Codes you should know |
|---|---|---|
| 0 | Echo Reply | 0 |
| 3 | Destination Unreachable | 0 net, 1 host, 2 protocol, **3 port**, **4 fragmentation needed and DF set**, 9/10 net/host administratively prohibited (RFC 1122), 13 communication administratively prohibited (RFC 1812) |
| 5 | Redirect | 0 network, 1 host, 2 TOS+network, 3 TOS+host |
| 8 | Echo (request) | 0 |
| 11 | Time Exceeded | **0 TTL exceeded in transit**, 1 fragment reassembly time exceeded |
| 12 | Parameter Problem | 0 pointer indicates the error, 1 missing required option, 2 bad length |

Type 4 (Source Quench) once asked a sender to slow down. It was ineffective and abusable, and RFC 6633 formally deprecates it: hosts must not act on it and routers must not send it. The IANA registry also marks Address Mask Request/Reply (17/18) as deprecated. Types 13/14 (Timestamp) and 9/10 (Router Advertisement/Solicitation) still exist but are rarely used.

> **Exam tip:** The big six from the blueprint are 0 (echo reply), 3 (unreachable), 5 (redirect), 8 (echo request), 11 (time exceeded) and 12 (parameter problem). The pair that matters most operationally: **3/4** (path MTU discovery) and **11/0** (traceroute).

The "unreachable" codes are often misread. Code 0/1 normally come from a router with no route or an ARP failure on the last hop. Code 2 and 3 come from the **destination host**: protocol or port not served. Code 13 (and 9/10) mean a filter is deliberately refusing, and it is the polite way for a firewall to reject rather than silently drop.

## Ping

Ping sends ICMP **Echo Request** (type 8, code 0) and expects **Echo Reply** (type 0). The identifier and sequence number let the sender match replies; the replier copies the payload back unchanged. Ping tests layer 3 reachability in both directions, and a `Request timed out` can mean the request was lost, the reply was lost, or something filtered ICMP.

```text
$ ping -c 2 192.0.2.1
64 bytes from 192.0.2.1: icmp_seq=1 ttl=63 time=0.412 ms
64 bytes from 192.0.2.1: icmp_seq=2 ttl=63 time=0.388 ms
```

The `ttl=63` is the TTL **in the reply as it arrived**, not the outbound TTL. Operating systems start TTL at different values: Linux and macOS 64, Windows 128, Cisco IOS 255. A reply that arrives with 63 most likely left a Linux host at 64 and crossed one router; 117 most likely left a Windows host at 128 and crossed 11. It is an inference, not proof, because TTLs are configurable and the return path may differ from the forward path.

Cisco IOS prints one character per probe:

| Character | Meaning |
|---|---|
| `!` | Reply received |
| `.` | Timed out |
| `U` | Destination unreachable received (type 3) |
| `M` | Could not fragment (type 3 code 4) |
| `Q` | Source quench received (legacy; no longer sent) |
| `?` | Unknown packet type |

IOS defaults to five 100-byte probes with a 2-second timeout. `ping 198.51.100.7 size 1500 df-bit` is the standard way to test an MTU.

## Traceroute

Traceroute discovers the routers on a path by deliberately sending packets that expire. It sends probes with **TTL 1**, then 2, then 3. The router that decrements the TTL to 0 drops the packet and returns **ICMP type 11 code 0** from one of its own addresses, which reveals the hop. Each hop is normally probed three times to give three round-trip times.

How the probe ends is what differs by platform:

| Platform | Probe type | Last hop answers with |
|---|---|---|
| Linux/Unix `traceroute` | UDP to a high port, starting at **33434** and incrementing per probe | ICMP type 3 code 3 (port unreachable) from the destination |
| Windows `tracert` | ICMP Echo Request | ICMP Echo Reply |
| Cisco IOS `traceroute` | UDP, starting at port 33434 | Port unreachable (`U` mark in the output) |
| `traceroute -I` (Linux), `-T` (TCP SYN) | ICMP echo or TCP | Echo reply, or SYN-ACK/RST |

Because the destination answers the final UDP probe with a port-unreachable, the destination does not need to run anything on that high port; it just needs to be allowed to reply.

```text
$ traceroute -n 203.0.113.50
 1  192.168.1.1  0.5 ms  0.4 ms  0.4 ms
 2  10.20.0.1    3.1 ms  3.0 ms  3.2 ms
 3  * * *
 4  203.0.113.50 14.9 ms 15.0 ms 14.8 ms
```

Reading it: hop 3 did not return Time Exceeded (filtered, rate limited, or the router does not generate it), but hop 4 answered, so traffic still flows through. A row of stars that continues to the end means probes (or their replies) are blocked beyond that point; it does not by itself say the forward path is broken. Note also that the address shown is typically the router's **ingress** interface, and the return path of the ICMP message may differ from the forward path.

## Redirects

A router sends **ICMP Redirect (type 5)** to tell a host that a better first hop exists on the same segment. Classic case: host H sends to its default gateway R1 for a destination that R2, also on H's subnet, reaches directly. R1 forwards the packet anyway and sends H a redirect naming R2 (type 5 code 1 for a host route, code 0 for a network). The host then installs a host route via R2.

A router sends one only when the packet arrives and would leave through the **same interface**, the source is on the same subnet as the better next hop, and the packet is not source-routed. Security-wise, redirects let anyone on the segment steer a host's traffic, so servers normally ignore them and many networks disable them. On Cisco, `no ip redirects` on the interface stops the router sending them (IOS sends them by default). On Linux the relevant sysctls are `net.ipv4.conf.all.accept_redirects` and `send_redirects`.

## ICMP filtering pitfalls

Blocking all ICMP is a classic mistake. The messages you must let through include:

- **Type 3 code 4**: without it, path MTU discovery breaks and large transfers hang (see the MTU lesson).
- **Type 11**: without it, traceroute shows stars.
- **Type 3 (others)**: hosts learn quickly that a destination is down instead of waiting for timeouts.
- **Type 0/8** at least from management networks, for diagnostics.

A sensible policy rate-limits ICMP instead of dropping it. Cisco routers rate-limit generated unreachables by default (`ip icmp rate-limit unreachable`, one per 500 ms), and `no ip unreachables` turns them off entirely. That suppresses the type 3 messages the router would originate, including code 4 (breaking PMTUD through it) and the port unreachable that ends a traceroute aimed at the router itself; time exceeded (type 11) is a separate message and is not affected. Linux rate-limits generated ICMP through `net.ipv4.icmp_ratelimit` (default 1000 ms, which applies to selected types). Control-plane policing also deprioritises ICMP addressed to the router, which is why a hop can show 200 ms in traceroute while traffic through it sees 2 ms.

> **Watch out:** A firewall that drops type 3 code 4 makes a working network look like it randomly stalls on large packets: small requests succeed, big responses hang.

## Lab it yourself

1. Capture while you ping: `sudo tcpdump -nn -i eth0 icmp` in one terminal, `ping -c 2 192.0.2.1` in another. Note type 8 then 0, the identifier and the incrementing sequence.
2. Run `traceroute -n 203.0.113.50` while capturing with `tcpdump -nn -i eth0 'udp or icmp'`. Confirm UDP destination ports starting near 33434 and the type 11 replies; the final reply is type 3 code 3.
3. Repeat with `traceroute -I` and with Windows `tracert`; in Wireshark use the display filter `icmp.type == 8 || icmp.type == 0 || icmp.type == 11`.
4. Cisco IOS: `traceroute 198.51.100.7`, then `debug ip icmp` on the middle router (and `terminal monitor`) while pinging through it. Then add `no ip unreachables` on the router's ingress interface and run `traceroute` to that router's own address: the last hop now shows stars because the port unreachable is no longer sent, while intermediate hops still answer with time exceeded.

## Key takeaways

- ICMP is IP protocol 1; every message has type, code and checksum, and errors quote the original IP header plus at least 8 bytes.
- Know types 0, 3, 5, 8, 11, 12 and the codes 3/3, 3/4, 11/0 above all.
- Source quench (type 4) is deprecated by RFC 6633; do not describe it as a working congestion mechanism.
- Ping reports the TTL of the arriving reply; use initial-TTL defaults (64, 128, 255) to estimate hop count with caution.
- Unix traceroute uses UDP probes from port 33434 and ends on a port unreachable; Windows tracert uses ICMP echo and ends on an echo reply.
- Redirects tell a host about a better first hop on its own segment; disable them where not needed.
- Never blanket-drop ICMP: allow 3/4 and 11, and rate-limit instead.
