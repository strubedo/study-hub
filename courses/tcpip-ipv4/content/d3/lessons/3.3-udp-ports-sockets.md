## The UDP header

UDP (RFC 768, IP protocol 17) is the thinnest transport: it adds ports and an optional integrity check to IP, and nothing else. The header is exactly **8 bytes**, four 16-bit fields:

| Field | Size | Notes |
|---|---|---|
| Source port | 16 bits | Optional "when meaningful"; may be 0 if no reply is expected |
| Destination port | 16 bits | Selects the receiving application |
| Length | 16 bits | UDP header + data in bytes; minimum 8 |
| Checksum | 16 bits | Over a pseudo-header (source IP, destination IP, protocol 17, UDP length), the UDP header and the data |

On IPv4 the checksum is optional: an all-zero checksum means the sender did not compute one. (If the computed value is zero it is transmitted as all ones.) On IPv6 the checksum is mandatory. The maximum IPv4 UDP payload is 65535 - 20 (IP) - 8 (UDP) = **65507 bytes**, though anything above the path MTU is fragmented unless the application keeps datagrams small.

UDP provides **no handshake, no sequencing, no retransmission, no flow control and no congestion control**. Each datagram is independent, and message boundaries are preserved (one `sendto` is one datagram, unlike TCP's byte stream). A datagram sent to a port nobody is listening on elicits **ICMP type 3 code 3** (port unreachable) from the destination host, which is the only built-in feedback.

## When to choose UDP

| Choose UDP when | Examples |
|---|---|
| A request and a reply each fit in one datagram and an extra handshake would double the latency | DNS queries, DHCP, NTP, SNMP, syslog |
| Late data is worthless, so retransmission is the wrong response | Voice and video (RTP), game state |
| The application wants to do its own reliability or congestion control | QUIC (HTTP/3) over UDP 443, TFTP's lock-step ACKs |
| Broadcast or multicast delivery is needed (TCP is unicast only) | DHCP discover, mDNS, routing protocols such as RIP and some multicast streaming |
| A tunnel carries traffic that already runs its own TCP | VXLAN, WireGuard, IPsec NAT traversal on UDP 4500 |

The trade-off is that the application must tolerate loss, duplication and reordering, and a UDP service that answers large replies to spoofed small requests (DNS, NTP) can be abused for amplification. UDP also has no congestion control of its own, so well-behaved UDP applications must limit their own sending rate.

> **Exam tip:** "UDP is unreliable" means the protocol gives no guarantees, not that datagrams usually get lost. DNS over UDP works fine because the application retries.

## Port numbers and their ranges

A port is a 16-bit number (0-65535) that identifies a service or a conversation endpoint on a host. TCP and UDP port spaces are independent: TCP 53 and UDP 53 are different endpoints. RFC 6335 and the IANA registry define three ranges:

| Range | Name | Notes |
|---|---|---|
| 0-1023 | **System Ports** (well-known) | Assigned by IANA through Standards Action or IESG review; on Unix, binding requires root (or the capability) |
| 1024-49151 | **User Ports** (registered) | Assigned by IANA on application; no OS privilege needed |
| 49152-65535 | **Dynamic / Private (ephemeral)** | Never assigned; intended for client-side source ports |

RFC 6335 recommends 49152-65535 for ephemeral ports but operating systems choose their own:

| OS | Default ephemeral range | Check with |
|---|---|---|
| **Linux** | **32768-60999** | `sysctl net.ipv4.ip_local_port_range` |
| **Windows** (Vista / Server 2008 and later) | **49152-65535** (the IANA range) | `netsh int ipv4 show dynamicport tcp` |
| Older Windows (XP / 2003) | 1025-5000 | |

The practical consequences: a Linux client appears to use source ports in the 32768-60999 band while a Windows client uses 49152 and up, and a firewall rule matching "source port > 1023" is looser than anything you should write. A NAT device allocates its own source ports, usually from a different range again.

## Sockets and the 5-tuple

A **socket** is an endpoint the operating system hands to an application: an IP address plus a port, for a particular protocol. A **flow** (a connection, or the UDP equivalent) is identified by the **5-tuple**:

`(protocol, source IP, source port, destination IP, destination port)`

This is why a single server port serves thousands of clients: 203.0.113.9:51000 and 203.0.113.9:51001 reaching 192.0.2.80:443 give two different 5-tuples. It is also the same tuple a stateful firewall, load balancer or NAT table uses as its key.

A **listening** socket is bound to a local address and port (`0.0.0.0:80` means any local IPv4 address) and has no remote tuple yet. For TCP, each accepted connection becomes a separate connected socket sharing the same local port. For UDP, a single unconnected socket receives datagrams from any peer, and the application learns each sender from the received packet's source address. A connected UDP socket (a `connect()` call on a datagram socket) merely filters to one peer.

```text
$ ss -ulnp
State   Recv-Q  Send-Q  Local Address:Port   Peer Address:Port  Process
UNCONN  0       0       0.0.0.0:68           0.0.0.0:*          users:(("dhclient",pid=612,fd=6))
UNCONN  0       0       127.0.0.53%lo:53     0.0.0.0:*          users:(("systemd-resolve",pid=540,fd=13))
UNCONN  0       0       192.0.2.10:123       0.0.0.0:*          users:(("chronyd",pid=701,fd=5))

$ ss -tn state established
Recv-Q Send-Q Local Address:Port   Peer Address:Port
0      0      192.0.2.10:44312     198.51.100.20:443
0      0      192.0.2.10:44314     198.51.100.20:443
```

UDP sockets show `UNCONN` (no connection state at all). In the second listing the two connections to the same server differ only in the client source port, which is what keeps their 5-tuples unique.

One UDP oddity worth knowing: TFTP clients send the first request to **server port 69**, and the server replies from a new ephemeral port (the transfer identifier), so a firewall must follow the exchange; a rule that only permits replies from port 69 breaks it.

## Common ports

| Service | Port | Transport | Notes |
|---|---|---|---|
| SSH | 22 | TCP | |
| Telnet | 23 | TCP | cleartext |
| SMTP | 25 | TCP | 587 for mail submission |
| DNS | 53 | UDP and TCP | TCP for large responses and zone transfers |
| DHCP | 67 server, 68 client | UDP | |
| TFTP | 69 | UDP | |
| HTTP | 80 | TCP | |
| NTP | 123 | UDP | |
| SNMP | 161 (polls), 162 (traps) | UDP | |
| HTTPS | 443 | TCP | UDP 443 is QUIC / HTTP/3 |
| Syslog | 514 | UDP | TCP and TLS variants exist (6514 for TLS) |
| BGP | 179 | TCP | |

> **Watch out:** DNS uses both. A UDP answer too large for the datagram sets the TC (truncated) bit and the client retries over TCP 53. Blocking TCP 53 breaks only some lookups, which is a maddening intermittent fault.

## Lab it yourself

1. List sockets: `ss -ulnp` (UDP listeners) and `ss -tlnp` (TCP listeners); on Windows `netstat -ano -p UDP` and `netstat -ano -p TCP`.
2. Send a UDP datagram with netcat: in one shell `nc -ul 5000`, in another `echo hi | nc -u 127.0.0.1 5000`. Capture with `sudo tcpdump -nn -i lo udp port 5000` and read the 8-byte header with `-X`.
3. Provoke port unreachable: `echo hi | nc -u 127.0.0.1 5999` with nothing listening, capture `icmp`, and find type 3 code 3 quoting the original header.
4. Check your ephemeral range, then open several connections (`curl` in a loop) and note the source ports with `ss -tn`. On Windows run `netsh int ipv4 show dynamicport tcp`.
5. In Wireshark, apply `udp` and open a DNS query: the Length field is 8 plus the DNS message length, and you can toggle the checksum verification preference.

## Key takeaways

- UDP is 8 bytes (source port, destination port, length, checksum) over IP protocol 17, with no state, ordering, retransmission or congestion control.
- The IPv4 UDP checksum is optional (0 = unused); on IPv6 it is mandatory.
- Use UDP for single-datagram exchanges, loss-tolerant real-time traffic, broadcast/multicast, and protocols that implement their own reliability (QUIC).
- Port ranges: 0-1023 System, 1024-49151 User, 49152-65535 Dynamic (RFC 6335); Linux defaults to 32768-60999 for ephemeral ports, modern Windows to 49152-65535.
- A flow is the 5-tuple (protocol, source IP, source port, destination IP, destination port); TCP and UDP port spaces are separate.
- A closed UDP port answers with ICMP type 3 code 3; a closed TCP port answers with RST.
- Know the standard ports: 22, 25, 53, 67/68, 69, 80, 123, 161/162, 179, 443, 514.
