## MTU versus MSS

Two numbers that are constantly confused:

| | MTU | MSS |
|---|---|---|
| Layer | Link / IP | TCP |
| What it limits | The largest **IP packet** (header + data) a link can carry in one frame | The largest **TCP payload** a receiver will accept in one segment |
| Ethernet value | 1500 | 1460 (= 1500 - 20 IP - 20 TCP) |
| Where it is set | Per interface or per route | Advertised in the TCP **MSS option** (kind 2, length 4), carried only in SYN and SYN-ACK segments |

The MSS excludes the IP and TCP headers, and it also excludes TCP options. If both ends negotiate timestamps (a 12-byte option once padded) every full segment holds 1448 bytes of data on a plain Ethernet path, even though the MSS shown in the handshake is still 1460. If no MSS option is received, RFC 9293 requires assuming 536 for IPv4 (576 - 40).

Each side announces the MSS it can **receive**, derived from its own outgoing interface MTU, and each sender uses the smaller of the peer's MSS and what its own path allows. MSS is therefore only aware of the two end hosts' interfaces. It does not know about a smaller link in the middle of the path; that is the job of path MTU discovery.

> **Exam tip:** MTU 1500 gives MSS 1460 for IPv4 TCP. The TCP MSS option appears only in SYN segments. Do not say "MSS is set per packet".

## Fragmentation recap

Domain 1 covered the header fields (Identification, DF and MF flags, 13-bit offset in 8-byte units). The operational rules are:

- A router that must forward a packet larger than the egress MTU **fragments it if DF is clear**. Each fragment gets its own IP header copy and the data is split on 8-byte boundaries.
- If **DF is set**, the router drops the packet and returns **ICMP type 3 code 4** (fragmentation needed and DF set).
- **Only the destination reassembles.** Routers do not reassemble, so a later router with a smaller MTU may fragment a fragment again, but the pieces are still reassembled only at the end host, matched on source, destination, protocol and Identification.
- Losing any one fragment loses the entire datagram: the receiver waits (Linux default `net.ipv4.ipfrag_time` is 30 seconds) and then discards; if it already holds the first fragment (offset 0) it may send ICMP type 11 code 1 (fragment reassembly time exceeded).
- Only the **first fragment** contains the TCP/UDP header. Stateless ACLs and firewalls that match on ports cannot match later fragments, and reassembly makes devices work harder, which is why fragmentation is avoided in practice.

Fragmentation also hurts performance (extra headers, extra processing, amplified loss), so modern TCP stacks set DF and size segments to fit instead.

## The DF bit and ICMP type 3 code 4

Path MTU discovery (PMTUD, RFC 1191) is how a sender learns the smallest MTU on the path, given the cooperation of routers:

1. The sender sets DF on every packet and starts by assuming the MTU of its first-hop interface (for example 1500).
2. A router whose egress MTU is smaller drops the packet and returns **type 3 code 4**. RFC 1191 added the **Next-Hop MTU** field to that message: the 16-bit lower half of the "unused" word, bytes 6 and 7 of the ICMP header.
3. The sender records the new path MTU for that destination (Linux caches it in the route cache, expiring after 600 seconds by default), shrinks its TCP segments (new MSS = PMTU - 40) and retransmits.
4. Periodically (RFC 1191 suggests 10 minutes) the sender tries a larger size to detect that the path improved.

Old routers that predate RFC 1191 set the Next-Hop MTU to 0. The host then walks a table of "plateau" MTU values (65535, 32000, 17914, 8166, 4352, 2002, 1492, 1006, 508, 296, 68) to guess the next lower size. A host must never reduce its PMTU estimate below 68.

```text
$ ip route get 198.51.100.7
198.51.100.7 via 192.0.2.1 dev eth0 src 192.0.2.10 uid 1000
    cache expires 586sec mtu 1400
```

That `mtu 1400` is the learned path MTU, created by a received type 3 code 4 reporting a next-hop MTU of 1400.

UDP is different: applications do not usually set DF, so large UDP datagrams are fragmented at the sender or by routers, unless the application opts in to PMTUD or limits its own datagram size (as DNS and QUIC do).

## PMTUD black holes

PMTUD needs the ICMP error to reach the sender. If a firewall drops type 3 code 4, or a router with `no ip unreachables` never generates it, the sender never learns anything. The result is a **PMTUD black hole**, with a very recognisable signature:

- The three-way handshake works (SYN segments are tiny).
- Small requests work. Interactive SSH works until a large screen refresh.
- Large transfers stall: the TLS server certificate, a big directory listing, an HTTP POST body, or anything larger than the path MTU never arrives, and the sender keeps retransmitting the same full-size segment.

Common causes are a blanket ICMP block, a tunnel endpoint (GRE, IPsec, VXLAN) that does not generate the ICMP error, a load balancer or ECMP path that delivers the ICMP message to a different server than the one sending, and NAT devices that do not translate the embedded packet inside the ICMP error.

Workarounds, roughly in order of preference:

1. Permit type 3 code 4 and rate-limit it instead of blocking.
2. **Clamp MSS** on the router that terminates the smaller link so that TCP never builds oversize segments (below).
3. Lower the interface or tunnel MTU so every hop agrees.
4. Enable **packetization-layer PMTUD (PLPMTUD, RFC 4821)**: TCP probes with larger segments and infers the limit from whether they are acknowledged, without relying on ICMP. On Linux `net.ipv4.tcp_mtu_probing` is 0 by default (off), 1 enables it only after a black hole is detected, and 2 always probes. RFC 8899 later defined the same idea for datagram transports (DPLPMTUD, used by QUIC).

## MSS clamping and tunnel overhead

Encapsulation adds headers, so the inner packet must be smaller than the physical MTU. The common overheads on a 1500-byte Ethernet underlay:

| Encapsulation | Added bytes | Largest inner IP packet | TCP MSS to clamp |
|---|---|---|---|
| PPPoE | 8 | 1492 | 1452 |
| IP-in-IP | 20 | 1480 | 1440 |
| GRE over IPv4 (no key) | 24 (20 outer IP + 4 GRE) | 1476 | 1436 |
| IPsec ESP tunnel mode | roughly 50-75, depends on cipher, padding and ICV | about 1425-1450 | about 1385-1410 |
| IPsec ESP with NAT-T | add 8 for UDP 4500 | lower still | |
| VXLAN | 50 (outer Ethernet 14 + IP 20 + UDP 8 + VXLAN 8) | underlay must be 1550 for an inner 1500 | |

The ESP figure is a range because it is 20 (outer IP) + 8 (SPI and sequence) + IV (16 for AES-CBC) + padding to the cipher block + 2 (pad length and next header) + ICV (for example 12 for HMAC-SHA1-96). Work it out from your own transform set.

**MSS clamping** rewrites the MSS option in transiting SYN segments so the two endpoints agree on a value that already fits, with no PMTUD needed. On Cisco IOS it is an interface command:

```text
interface Tunnel0
 ip mtu 1400
 ip tcp adjust-mss 1360
```

`1360` is 1400 minus 40. On Linux a router can clamp automatically to the egress path MTU:

```text
iptables -t mangle -A FORWARD -p tcp --tcp-flags SYN,RST SYN -j TCPMSS --clamp-mss-to-pmtu
```

Clamping only helps TCP; UDP and ICMP still rely on a correct interface MTU or on application behaviour. On IOS the knob `tunnel path-mtu-discovery` makes a GRE tunnel honour PMTUD for the outer packet, and `ip tcp path-mtu-discovery` enables PMTUD for TCP sessions the router itself originates (it is off by default).

> **Real world:** A tunnel with a correct `ip mtu` but no MSS clamp still black-holes if the ICMP can't reach the sender. Clamp on the tunnel and set the MTU; one fixes TCP, the other makes UDP behave.

## Lab it yourself

1. Find your path MTU: on Linux `ping -M do -s 1472 198.51.100.7` (1472 + 8 ICMP + 20 IP = 1500). Lower `-s` until it passes. On Windows the equivalent is `ping -f -l 1472 198.51.100.7`. On IOS: `ping 198.51.100.7 size 1500 df-bit`.
2. `tracepath 198.51.100.7` reports the discovered `pmtu` and the hop that reduced it.
3. In Wireshark, filter `icmp.type == 3 && icmp.code == 4` and expand the packet to read the Next-Hop MTU. Lower an intermediate router interface with `ip mtu 1400` (GRE tunnel or sub-interface) to provoke one.
4. Check the MSS in a handshake: filter `tcp.flags.syn == 1` and open the TCP options. Compare the value with and without `ip tcp adjust-mss 1360` on the path.
5. Linux: `ss -tin dst 198.51.100.7` shows `mss:` and `pmtu:` for live connections.

## Key takeaways

- MTU is the IP-level limit per link (1500 on Ethernet); MSS is the TCP payload limit announced in SYNs (1460 on Ethernet).
- Routers fragment only when DF is clear; if DF is set they drop and send ICMP type 3 code 4 with the Next-Hop MTU.
- Only the destination reassembles; losing any fragment loses the datagram, and later fragments have no L4 header.
- PMTUD relies on ICMP reaching the sender; a filtered type 3 code 4 yields a black hole where handshakes and small packets work but large transfers stall.
- PLPMTUD (RFC 4821) and DPLPMTUD (RFC 8899) probe instead of trusting ICMP; Linux `tcp_mtu_probing` defaults to 0.
- Encapsulation costs bytes: PPPoE 8, IP-in-IP 20, GRE 24, VXLAN 50, ESP variable.
- Clamp MSS on the device with the smaller MTU (`ip tcp adjust-mss`, `TCPMSS --clamp-mss-to-pmtu`) and keep ICMP type 3 code 4 and type 11 permitted.
