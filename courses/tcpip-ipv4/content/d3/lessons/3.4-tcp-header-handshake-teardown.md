## What TCP provides

TCP (RFC 9293, which obsoletes RFC 793; IP protocol 6) gives applications a **reliable, ordered byte stream** between two sockets. It numbers every byte, acknowledges what arrived, retransmits what did not, slows down when the receiver or the network cannot keep up, and checks integrity with a checksum covering a pseudo-header (addresses, protocol, length), the TCP header and the data. A connection is identified by the 5-tuple from the previous lesson. The cost is state at both ends and a handshake before data flows.

## The TCP header

The minimum header is **20 bytes**; the Data Offset field allows up to **60 bytes**, leaving up to 40 bytes of options.

| Field | Size | Purpose |
|---|---|---|
| Source port, destination port | 16 bits each | Endpoint selectors |
| Sequence number | 32 bits | Number of the first data byte in this segment (or the ISN on a SYN) |
| Acknowledgment number | 32 bits | Next sequence number the sender expects to receive; valid when ACK is set |
| Data offset | 4 bits | Header length in 32-bit words: 5 (20 bytes) to 15 (60 bytes) |
| Reserved | 4 bits | Must be zero (the historic NS bit lived here; RFC 9293 reserves these bits) |
| Flags | 8 bits | CWR, ECE, URG, ACK, PSH, RST, SYN, FIN |
| Window | 16 bits | Receive window: how many more bytes the sender of this segment will accept |
| Checksum | 16 bits | Pseudo-header + header + data |
| Urgent pointer | 16 bits | Meaningful only with URG; rarely used |
| Options | 0-40 bytes | MSS, window scale, SACK, timestamps, padded to 32 bits |

### Flags

| Flag | Bit value | Meaning |
|---|---|---|
| FIN | 0x01 | Sender has no more data; consumes one sequence number |
| SYN | 0x02 | Synchronise sequence numbers (open); consumes one sequence number |
| RST | 0x04 | Abort or reject the connection |
| PSH | 0x08 | Deliver buffered data to the application promptly |
| ACK | 0x10 | The acknowledgment field is valid; set on every segment after the first SYN |
| URG | 0x20 | Urgent pointer is valid |
| ECE | 0x40 | ECN-Echo: congestion experienced, or ECN capability in the handshake |
| CWR | 0x80 | Congestion Window Reduced |

So a SYN is `0x002`, a SYN-ACK is `0x012`, a plain ACK `0x010`, data with push `0x018` (PSH+ACK), a FIN-ACK `0x011` and a reset-with-ack `0x014`.

### Options

Options use kind/length/value encoding, except for the single-byte ones:

| Kind | Length | Option | Notes |
|---|---|---|---|
| 0 | 1 | End of option list | |
| 1 | 1 | No-operation (padding) | used to align others |
| 2 | 4 | **MSS** | SYN only |
| 3 | 3 | **Window scale** (RFC 7323) | SYN only; shift count 0-14 |
| 4 | 2 | **SACK permitted** (RFC 2018) | SYN only |
| 5 | variable | **SACK** blocks | 8 bytes per block, up to 4 blocks (3 when timestamps are in use) |
| 8 | 10 | **Timestamps** (RFC 7323) | RTT measurement and PAWS |

## Sequence and acknowledgment numbers

Each side picks a 32-bit **initial sequence number (ISN)** that is unpredictable (spoofing resistance) and not reused soon. The sequence number counts **bytes**, not segments. Two rules explain nearly every trace:

- The acknowledgment number is the **next byte expected**, so it equals the last in-order byte received plus one. It is cumulative: ACK 5001 means every byte through 5000 has arrived.
- SYN and FIN each consume **one sequence number** even though they carry no data. A pure ACK consumes none.

Wireshark shows **relative** sequence numbers by default (starting at 0 for each direction) to make traces readable; `tcpdump -S` and the raw hex show the true values.

## The three-way handshake

```text
Client 192.0.2.10:44312                      Server 198.51.100.20:443
  SYN       seq=1000 mss=1460 ws=7 SACK_PERM TS   --->
            <---   SYN,ACK  seq=9000 ack=1001 mss=1460 ws=8 SACK_PERM TS
  ACK       seq=1001 ack=9001                     --->
  PSH,ACK   seq=1001 ack=9001 len=517 (TLS ClientHello)  --->
            <---   ACK      seq=9001 ack=1518
```

1. **SYN**: the client sends its ISN (1000 here) and the options it supports. SYN consumes one number.
2. **SYN-ACK**: the server sends its own ISN (9000) and acknowledges 1001 (client ISN + 1). It echoes only the options it accepts.
3. **ACK**: the client acknowledges 9001. The connection is ESTABLISHED, and data may follow in the same or the next segment.

Both ISNs are independent; a connection is really two unidirectional streams. Options that appear only in SYNs (MSS, window scale, SACK permitted) are agreed here: **window scaling and SACK are used only if both SYNs carried them**, and the window field inside SYN segments is never scaled.

A closed port answers a SYN with `RST,ACK` (ack = SYN's sequence number + 1); a firewall that silently drops produces repeated SYN retransmissions instead. The initial retransmission timeout is 1 second (RFC 6298) and doubles each time. Linux's `tcp_syn_retries` default of 6 means roughly 127 seconds of retrying before `ETIMEDOUT` on classic kernels (retries at 1, 3, 7, 15, 31 and 63 s, then a final 64 s wait); recent kernels add `tcp_syn_linear_timeouts` (default 4), which keeps the first few retries at 1 s spacing and stretches the total slightly (the kernel documentation quotes about 131 s).

> **Exam tip:** SYN, SYN-ACK, ACK with sequence arithmetic: ISN + 1 in each acknowledgment. If a SYN with seq=X is sent, the reply is `ack = X + 1`.

## Normal teardown

Each direction closes separately with a FIN, so the classic close is a four-segment exchange:

```text
Active closer (A)                                Passive closer (B)
  FIN,ACK  seq=5000 ack=7000           --->     B: ESTABLISHED -> CLOSE_WAIT
           <---   ACK        seq=7000 ack=5001      A: FIN_WAIT_1 -> FIN_WAIT_2
           <---   FIN,ACK    seq=7000 ack=5001      B: CLOSE_WAIT -> LAST_ACK (app calls close)
  ACK      seq=5001 ack=7001           --->     B: -> CLOSED;  A: -> TIME_WAIT
```

If B has no more data and closes immediately, its ACK and FIN merge into one segment and the exchange is three segments. A can also send FIN while B continues sending data; that **half-close** state (A in FIN_WAIT_2, B in CLOSE_WAIT) can last indefinitely as long as B's application keeps the socket open.

Because FIN consumes a sequence number, the ACK of a FIN is one higher than the FIN's sequence number. In the trace above A's FIN carried seq=5000, so B acknowledges 5001.

## RST

A **reset** abruptly ends the connection or refuses it. It is not acknowledged and carries no data. Typical causes:

- A SYN to a port with no listener (the server answers `RST,ACK`).
- A segment for a connection the receiver does not know (for example after the server rebooted or a firewall dropped the state entry).
- An application that aborts (a socket closed with unread data in the receive buffer sends RST on Linux, or one closed with linger time 0).
- A firewall or IDS that injects a reset to both ends.

A receiver accepts an RST only if its sequence number falls within the receive window, and RFC 5961 tightens that: only an RST whose sequence number **exactly** equals the next expected value resets the connection; an in-window but inexact one provokes a "challenge ACK". This frustrates blind reset attacks.

## Lab it yourself

1. Capture a handshake: `sudo tcpdump -nn -S -i eth0 'host 198.51.100.20 and tcp port 443'`, then `curl -sI https://example.com`. Read the three flags fields (`[S]`, `[S.]`, `[.]`) and verify ack = ISN + 1. Repeat without `-S` to see relative values.
2. In Wireshark use `tcp.flags.syn == 1` and expand **Options** on the SYN; try `tcp.flags.reset == 1` for resets. Right-click a packet and **Follow > TCP Stream**.
3. Provoke an RST: `nc 192.0.2.10 5999` against a closed port, and watch `[R.]` come back. Then block the port with `iptables -j DROP` instead and watch the SYN retransmit (spacing roughly 1, 2, 4 s on classic kernels; recent kernels retry at 1 s intervals first).
4. Cisco IOS: `show tcp brief` lists the router's own connections with their states; `debug ip tcp transactions` shows segments (use with care).

## Key takeaways

- TCP is a reliable ordered byte stream; header is 20-60 bytes (data offset 5-15), options up to 40 bytes.
- Flags: CWR, ECE, URG, ACK, PSH, RST, SYN, FIN. SYN = 0x02, SYN-ACK = 0x12, FIN-ACK = 0x11.
- Sequence numbers count bytes; ACK is the next byte expected. SYN and FIN each consume one number.
- Three-way handshake: SYN, SYN-ACK, ACK. MSS, window scale and SACK-permitted are negotiated only in SYNs and need both sides.
- Teardown is FIN/ACK per direction (four segments, or three when merged); half-close is legal.
- RST aborts or rejects; RFC 5961 requires an exact sequence match to reset an established connection.
- Wireshark's relative sequence numbers hide the real ISNs; use `tcpdump -S` or turn the preference off for raw values.
