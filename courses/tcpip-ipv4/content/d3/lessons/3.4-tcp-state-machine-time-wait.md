## The TCP state machine

RFC 9293 defines eleven states. Knowing which side sits in which state, and how long it can stay there, is the foundation for reading `ss` or `netstat` output.

| State | Who | Meaning |
|---|---|---|
| CLOSED | both | No connection (a fictional state: no TCB exists) |
| LISTEN | server | Waiting for a SYN on a bound port |
| SYN-SENT | client | SYN sent, waiting for SYN-ACK |
| SYN-RECEIVED | server | SYN received, SYN-ACK sent, waiting for the final ACK |
| ESTABLISHED | both | Data transfer |
| FIN-WAIT-1 | active closer | FIN sent, waiting for its ACK (or the peer's FIN) |
| FIN-WAIT-2 | active closer | Own FIN acknowledged, waiting for the peer's FIN |
| CLOSE-WAIT | passive closer | Peer's FIN received and acknowledged; waiting for the local application to close |
| CLOSING | both (rare) | Both sides sent FIN at the same moment; waiting for the ACK of own FIN |
| LAST-ACK | passive closer | Own FIN sent after CLOSE-WAIT; waiting for the final ACK |
| TIME-WAIT | active closer | Waiting 2 x MSL after the final ACK so late segments die and the last ACK can be resent |

`ss` abbreviates and hyphenates (`ESTAB`, `SYN-SENT`, `TIME-WAIT`); `netstat` prints `ESTABLISHED`, `TIME_WAIT`. The states are the same.

### Opening

```text
Client: CLOSED -> SYN-SENT -(rcv SYN-ACK, send ACK)-> ESTABLISHED
Server: CLOSED -> LISTEN -(rcv SYN, send SYN-ACK)-> SYN-RECEIVED -(rcv ACK)-> ESTABLISHED
```

If the final ACK never arrives the server stays in SYN-RECEIVED and retransmits its SYN-ACK. A flood of SYNs from spoofed addresses fills the server's half-open queue; **SYN cookies** let Linux answer without keeping state until the ACK returns. A listener that is under a SYN flood shows many `SYN-RECV` entries in `ss`.

### Closing

```text
Active closer : ESTABLISHED -(send FIN)-> FIN-WAIT-1 -(rcv ACK)-> FIN-WAIT-2 -(rcv FIN, send ACK)-> TIME-WAIT -(2 MSL)-> CLOSED
Passive closer: ESTABLISHED -(rcv FIN, send ACK)-> CLOSE-WAIT -(app closes, send FIN)-> LAST-ACK -(rcv ACK)-> CLOSED
Simultaneous  : FIN-WAIT-1 -(rcv FIN, send ACK)-> CLOSING -(rcv ACK)-> TIME-WAIT
```

If the peer's ACK and FIN arrive together, FIN-WAIT-1 jumps straight to TIME-WAIT. Either side may be the active closer; it is simply whoever calls close first. In HTTP, servers often close, so busy servers collect TIME-WAIT sockets. For a client that connects once and closes, the client keeps them.

## TIME-WAIT

The side that sends the last ACK enters TIME-WAIT and holds the connection's 5-tuple for **2 x MSL** (Maximum Segment Lifetime) before releasing it. It exists for two reasons:

1. **Reliable close.** If the final ACK is lost, the peer retransmits its FIN. The TIME-WAIT side must still be there to ACK it again, otherwise it would answer with RST and make a clean close look like an error.
2. **Preventing old duplicates.** A delayed segment from the earlier connection must not be accepted by a new incarnation of the same 5-tuple. Waiting twice the maximum segment lifetime lets all such segments expire.

RFC 9293 takes MSL as **2 minutes**, which would give 4 minutes. Operating systems choose their own value:

| OS | TIME-WAIT duration |
|---|---|
| **Linux** | **60 seconds**, a compile-time constant (`TCP_TIMEWAIT_LEN`) that is not a sysctl; `tcp_fin_timeout` (default 60) is the separate limit for orphaned FIN-WAIT-2 sockets |
| **Windows** | Registry-tunable (`TcpTimedWaitDelay`, 30-300 seconds range); the default has differed between versions, so check the current documentation rather than quoting a single number |
| RFC 9293 | 2 x MSL where MSL is 2 minutes (4 minutes) |

TIME-WAIT is **normal**. It becomes a problem when a client opens huge numbers of short connections to a single server address and port: each closed connection holds a local source port for the whole period, so a Linux client with the default ephemeral range of roughly 28,200 ports (32768-60999) can exhaust ports at about 470 connection/sec to one destination (28,232 / 60 s). Mitigations include connection pooling and keep-alive, widening the ephemeral range, using more source or destination addresses, and `net.ipv4.tcp_tw_reuse` (client side, outbound connections only, which uses TCP timestamps to reject old segments). Tuning `tcp_tw_recycle` was removed from the kernel in 4.12 because it broke clients behind NAT, so it should not be recommended.

RFC 1337 describes "TIME-WAIT assassination": a stray RST (or old duplicate) that ends TIME-WAIT early can let a stale segment corrupt a new connection. Linux's `net.ipv4.tcp_rfc1337` defaults to 0, meaning an RST received in TIME-WAIT closes the socket immediately; setting it to 1 ignores such RSTs.

> **Exam tip:** TIME-WAIT is on the **active closer**, never on the passive one. CLOSE-WAIT is on the passive closer, and its cause is the local application not calling close.

## Reading ss output

```text
$ ss -tan
State       Recv-Q Send-Q  Local Address:Port    Peer Address:Port
LISTEN      0      128     0.0.0.0:22            0.0.0.0:*
ESTAB       0      0       192.0.2.10:22         203.0.113.9:50122
TIME-WAIT   0      0       192.0.2.10:44312      198.51.100.20:443
TIME-WAIT   0      0       192.0.2.10:44314      198.51.100.20:443
CLOSE-WAIT  54     0       192.0.2.10:8080       203.0.113.77:41200
SYN-SENT    0      1       192.0.2.10:44390      198.51.100.99:443
```

- `LISTEN`: for listeners, `Send-Q` is the backlog size, `Recv-Q` the number of connections waiting to be accepted.
- `ESTAB`: ordinary connection.
- `TIME-WAIT` rows from the local ephemeral port to a remote 443: this host closed those connections first.
- `CLOSE-WAIT` with data in `Recv-Q`: the peer closed, but the local application (port 8080) never read the rest and never closed the socket. Piles of CLOSE-WAIT are an **application bug** (a leaked socket), not a network problem, and they never time out by themselves.
- `SYN-SENT` that doesn't progress: the SYN is unanswered (filtered, wrong address, host down).

Counting states quickly: `ss -tan | awk 'NR>1{c[$1]++} END{for(s in c)print s,c[s]}'` or `ss -s`. On Windows the same states appear in `netstat -ano`; Cisco IOS shows its own TCP sessions with `show tcp brief`.

## Keepalives and idle connections

A TCP connection with no traffic stays ESTABLISHED indefinitely; the network does not track it, but stateful firewalls and NAT devices do and will silently expire idle entries. When the endpoint later sends, the middlebox has forgotten the flow and the packet is dropped or answered with an RST. TCP **keepalives** (optional per RFC 9293, defaulting to at least 2 hours when enabled) send an empty ACK probe and expect an ACK back. On Linux the defaults are `tcp_keepalive_time` 7200 seconds, `tcp_keepalive_intvl` 75 and `tcp_keepalive_probes` 9, and applications must opt in with `SO_KEEPALIVE`. To keep a NAT mapping alive, the interval must be shorter than the device's idle timeout.

## Lab it yourself

1. Watch the states change: in one shell `watch -n1 'ss -tan | grep 443'`, in another `curl -s https://example.com >/dev/null`. You will see ESTAB then TIME-WAIT, and the entry disappear after about 60 seconds on Linux.
2. Create CLOSE-WAIT on purpose with a server that never closes: `python3 -c "import socket;s=socket.socket();s.bind(('127.0.0.1',9001));s.listen();c,_=s.accept();input()"`. Connect with `nc 127.0.0.1 9001`, press Ctrl-C in nc, and run `ss -tan | grep 9001`: the server side sits in CLOSE-WAIT (and the nc side in FIN-WAIT-2) until you press Enter.
3. Capture the close with `tcpdump -nn 'tcp[tcpflags] & (tcp-fin|tcp-rst) != 0'` and identify the active closer by who sent the first FIN.
4. Wireshark: `tcp.flags.fin == 1 || tcp.flags.reset == 1`, and Statistics > Conversations > TCP.
5. Check the Linux numbers: `sysctl net.ipv4.tcp_fin_timeout net.ipv4.ip_local_port_range net.ipv4.tcp_tw_reuse`.

## Key takeaways

- The states: CLOSED, LISTEN, SYN-SENT, SYN-RECEIVED, ESTABLISHED, FIN-WAIT-1, FIN-WAIT-2, CLOSE-WAIT, CLOSING, LAST-ACK, TIME-WAIT.
- The active closer (first to send FIN) ends in TIME-WAIT; the passive closer passes through CLOSE-WAIT and LAST-ACK.
- TIME-WAIT lasts 2 x MSL: RFC 9293 text implies 4 minutes, Linux uses a fixed 60 seconds, Windows is configurable. It protects against old duplicates and lost final ACKs.
- Many TIME-WAIT sockets are normal; many CLOSE-WAIT sockets mean the application is not closing its sockets.
- A listener's accept backlog shows in `ss -ltn` Recv-Q/Send-Q; SYN-RECV buildup suggests a SYN flood or a one-way path.
- Idle connections are not signalled to the network; middlebox state timeouts are the usual cause of "hung after idle" problems, fixed with keepalives shorter than the timeout.
