## A layered approach

Most "it doesn't work" tickets can be narrowed down with a handful of commands, working up the stack: is the port up (L1/L2)? Is it in the right VLAN and is the MAC learned (L2)? Does ARP resolve and is there a route (L3)? Is something filtering (L4)? Topic 2.4 tests whether you can read the evidence each tool gives you.

## Interface state: show interfaces / show ip interface brief

```ios
SW1# show ip interface brief
Interface              IP-Address      OK? Method Status                Protocol
Vlan1                  unassigned      YES unset  administratively down down
Vlan10                 10.1.10.2       YES manual up                    up
GigabitEthernet1/0/1   unassigned      YES unset  up                    up
GigabitEthernet1/0/2   unassigned      YES unset  down                  down
GigabitEthernet1/0/3   unassigned      YES unset  administratively down down
```

| Status / Protocol | Meaning | First thing to check |
|---|---|---|
| up / up | Working at L1 and L2 | Move up the stack |
| administratively down / down | `shutdown` is configured | `no shutdown` (if intended) |
| down / down | No link (or err-disabled) | Cable, far end, optics; `show interfaces` for `(err-disabled)` |
| up / down | Physical link but line protocol failing | Keepalive/encapsulation mismatch on routers; on an SVI, see the autostate rules |

`show interfaces` adds the reason in parentheses on Catalyst switches — `(connected)`, `(notconnect)`, `(disabled)`, `(err-disabled)` — plus speed/duplex and error counters. Rising **CRC/input errors** point to cabling or interference; **late collisions** on a half-duplex port point to a duplex mismatch. `show interfaces status` gives a one-line-per-port view including VLAN, duplex and speed, and `show interfaces status err-disabled` lists err-disabled ports with the reason.

## Following a host through Layer 2

**show vlan brief** — which access ports are in which VLAN (trunks are not listed):

```ios
SW1# show vlan brief

VLAN Name                             Status    Ports
---- -------------------------------- --------- -------------------------------
1    default                          active    Gi1/0/3, Gi1/0/4
10   USERS                            active    Gi1/0/5, Gi1/0/6, Gi1/0/12
20   SERVERS                          active    Gi1/0/7
110  VOICE                            active    Gi1/0/12
```

A VLAN missing from this list does not exist on this switch — SVIs for it will be down and trunks won't carry it.

**show mac address-table** — where a MAC was learned:

```ios
SW1# show mac address-table address 0050.7966.6804
          Mac Address Table
-------------------------------------------

Vlan    Mac Address       Type        Ports
----    -----------       --------    -----
  20    0050.7966.6804    DYNAMIC     Gi1/0/24
Total Mac Addresses for this criterion: 1
```

If the port is a trunk or uplink, the host is somewhere beyond it; use `show cdp neighbors` to see which switch is on Gi1/0/24 and repeat there until the MAC shows up on an access port. Dynamic entries age out after **300 seconds** of silence by default, so a quiet host may not be listed.

**show ip arp** (routers and L3 switches) — IP-to-MAC bindings:

```ios
R1# show ip arp
Protocol  Address          Age (min)  Hardware Addr   Type   Interface
Internet  10.1.10.1               -   0c1a.2b3c.4d01  ARPA   GigabitEthernet0/0/1.10
Internet  10.1.10.25              3   0050.7966.6801  ARPA   GigabitEthernet0/0/1.10
Internet  10.1.10.50              0   Incomplete      ARPA
```

Age `-` is one of the router's own addresses. **Incomplete** means the router sent ARP requests and got no reply: the host is off, in the wrong VLAN, has a wrong IP, or the L2 path is broken. Routing is not the problem — the router already knows which interface to ARP out of.

## show logging

```ios
SW1# show logging | include 1/0/7
*Oct 24 09:12:03.114: %LINK-3-UPDOWN: Interface GigabitEthernet1/0/7, changed state to down
*Oct 24 09:12:04.115: %LINEPROTO-5-UPDOWN: Line protocol on Interface GigabitEthernet1/0/7, changed state to down
```

Format: `%FACILITY-SEVERITY-MNEMONIC: text`. Messages that matter for this domain: `%LINK-3-UPDOWN`, `%LINEPROTO-5-UPDOWN`, `%PM-4-ERR_DISABLE` (why a port was err-disabled), `%CDP-4-NATIVE_VLAN_MISMATCH`, `%EC-5-CANNOT_BUNDLE2`, `%SPANTREE-2-...` (guard actions), `%ILPOWER-...` (PoE). Use `| include` to filter, and make sure clocks are NTP-synced so timestamps line up across devices.

## Layer 3: does routing work at all?

On a multilayer switch, `show ip route` is a quick sanity check. If routing is disabled you get host-style output instead of a table:

```ios
DSW1# show ip route
Default gateway is not set

Host               Gateway           Last Use    Total Uses  Interface
ICMP redirect cache is empty
```

That means `ip routing` is off: hosts can reach their SVI gateway but nothing is routed between VLANs.

## Ping and extended ping

| Character | Meaning |
|---|---|
| `!` | Echo reply received |
| `.` | Timed out waiting for a reply (default timeout 2 s) |
| `U` | ICMP destination unreachable received |
| `M` | Could not fragment (DF set and a link's MTU is too small) |
| `Q` | Source quench |
| `&` | Packet lifetime (TTL) exceeded |
| `?` | Unknown packet type |

Two classic patterns:

- **`.!!!!`** on the first ping to a new destination: the first echo was lost while ARP resolved (the destination, or the next hop). Not a fault.
- **`U.U.U`** (or `M.M.M`): IOS rate-limits the ICMP unreachables it generates (by default one per 500 ms), so every other probe times out instead of receiving its unreachable. The unreachable itself is the real signal.

Extended ping, either interactive (`ping` then answer prompts) or one line:

```ios
R1# ping 10.9.9.9 source Loopback0 repeat 100 size 1500 df-bit
```

| Option | Why use it |
|---|---|
| `source <interface or IP>` | Tests the **return path** to that source subnet — e.g., proves the remote site has a route back to your LAN, not just to your WAN IP |
| `repeat N` | Exposes intermittent loss |
| `size N` | Tests larger packets |
| `df-bit` | With `size`, finds MTU problems: `M` means a hop needed to fragment but couldn't |
| `timeout N` | Slow links |

A plain ping from a router uses the outgoing interface's IP as source. If plain ping works but `ping ... source GigabitEthernet0/0/1` (LAN) fails, the far end lacks a route back to your LAN subnet.

## Traceroute

Cisco IOS traceroute sends **UDP probes** (destination ports starting at 33434), **three per hop**, increasing the TTL by one each round (default max TTL 30). Each router that decrements TTL to 0 returns **ICMP time exceeded**, revealing itself; the destination answers with **ICMP port unreachable**, ending the trace. (Windows `tracert` uses ICMP echo instead.)

```ios
R1# traceroute 10.50.1.10
Type escape sequence to abort.
Tracing the route to 10.50.1.10
VRF info: (vrf in name/id, vrf out name/id)
  1 10.0.12.2 1 msec 1 msec 1 msec
  2 10.0.23.3 2 msec 1 msec 2 msec
  3 * * *
  4 10.50.1.10 3 msec 3 msec 4 msec
```

| Output | Meaning |
|---|---|
| `* * *` | No reply within the timeout for that hop. If later hops answer, that device forwards traffic but doesn't send (or rate-limits/filters) time-exceeded messages. If every later hop is `*`, traffic is being dropped there or beyond. |
| `!H` | ICMP host unreachable returned by that hop |
| `!N` | ICMP network unreachable |
| `!P` | ICMP protocol unreachable |
| `!A` | Administratively prohibited (an ACL denied it) |
| `Q` | Source quench |

The last responding hop before the failure shows you **where to look next**: the problem is that router's forwarding decision, the link after it, or the return path.

## Reading packet capture summaries

You may be shown Wireshark/tcpdump-style summary lines (on Catalyst 9000 you can capture on-box with Embedded Packet Capture: `monitor capture`). Read source, destination, protocol and the info field:

```text
No. Time      Source         Destination    Proto Info
1   0.000000  0c:1a:2b:3c:4d:01 Broadcast   ARP   Who has 10.1.10.50? Tell 10.1.10.1
2   0.000390  00:50:79:66:68:05 0c:1a:2b:3c:4d:01 ARP 10.1.10.50 is at 00:50:79:66:68:05
3   0.001020  10.1.10.25     10.2.20.80     TCP   51544 → 443 [SYN] Seq=0 Win=64240 Len=0 MSS=1460
4   0.001811  10.2.20.80     10.1.10.25     TCP   443 → 51544 [RST, ACK] Seq=1 Ack=1 Win=0 Len=0
5   2.104552  10.1.10.1      10.1.10.25     ICMP  Destination unreachable (Communication administratively filtered)
```

| Pattern | Meaning |
|---|---|
| ARP request, no reply (repeated) | Target not on that L2 segment or not answering — check VLAN, host, cabling |
| ARP request + reply | L2 adjacency is fine |
| SYN → SYN/ACK → ACK | TCP handshake succeeded; any problem is above TCP |
| SYN → **RST, ACK** | Host (or a device answering for it) reachable but **nothing listening** on that port |
| SYN, SYN retransmissions, nothing back | Packets silently dropped: routing, a firewall drop rule, or a return-path problem |
| ICMP Destination unreachable (Port unreachable) | UDP port closed on the destination (also how traceroute ends) |
| ICMP Destination unreachable (Communication administratively filtered) | An ACL/firewall at the **ICMP source** denied the packet |

> **Exam tip:** Always note *who sent* the ICMP message. An unreachable from 10.1.10.1 (the gateway) is the gateway's verdict, not the destination's.

## Key takeaways

- `administratively down` = shut; `down/down` = no link or err-disabled; check the parenthetical in `show interfaces`.
- Chase a MAC with `show mac address-table` + `show cdp neighbors` until it lands on an access port.
- ARP `Incomplete` means ARP requests went unanswered — an L2/host problem, not routing.
- `.!!!!` is normal ARP delay; `U.U.U` / `M.M.M` alternate because IOS rate-limits ICMP unreachables.
- Extended ping `source` tests the return path; `size` + `df-bit` finds MTU problems.
- Traceroute `* * *` followed by working hops is a silent hop, not a failure; `!H`, `!N`, `!A` name the reason a hop refused.
- In captures, SYN → RST means reachable but closed; SYN with no answer means dropped.
