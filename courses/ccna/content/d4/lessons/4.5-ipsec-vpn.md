## What a VPN gives you

A VPN carries private traffic across an untrusted network (usually the internet) while providing:

* **Confidentiality** – encryption (AES).
* **Integrity** – a keyed hash (HMAC-SHA-256 and similar) proves the data was not modified.
* **Authentication** – each peer proves its identity (pre-shared key, digital certificate, or user credentials).
* **Anti-replay** – sequence numbers stop an attacker from re-sending captured packets.

IPsec is a framework of protocols that provides these at Layer 3. The blueprint verb for 4.5 is **describe**: know the building blocks and how they fit, not the full crypto configuration.

## Site-to-site vs remote access

| | Site-to-site | Remote access |
|--|-------------|---------------|
| Connects | Two networks (branch to HQ, HQ to cloud) | One user device to a network |
| Endpoints | Routers or firewalls at each site | Software on the laptop/phone to a VPN head-end (firewall or router) |
| Who builds the tunnel | Gateways, always on or on demand; hosts are unaware | The user (or an always-on client) |
| Typical protocols | IPsec (IKEv1/IKEv2), often GRE or VTI over IPsec | IKEv2/IPsec or TLS/DTLS (SSL VPN) |
| Authentication | PSK or certificates between gateways | User credentials (often via RADIUS/AAA + MFA) plus certificates |

### Remote access flavors

* **Client-based** – a VPN client such as **Cisco Secure Client** (formerly AnyConnect) creates a full tunnel. It can use TLS with DTLS for performance, or IKEv2/IPsec. The user gets an IP address from the head-end and can reach anything the policy allows.
* **Clientless SSL VPN** – the user opens a web browser to the VPN gateway's portal over HTTPS. Access is limited to web-based resources (and some proxied applications) presented by the portal. No software install is needed, which suits contractors and unmanaged devices.

> **Exam tip:** Clientless = browser, TLS, limited to what the portal exposes. Client-based = installed client, full network-layer tunnel.

## The IPsec protocol suite

### IKE: building the tunnel

**Internet Key Exchange** negotiates algorithms, authenticates the peers, and generates keys using **Diffie-Hellman**. It runs on **UDP 500**.

**IKEv1** has two phases:

* **Phase 1** – build a secure management channel, the **IKE (ISAKMP) SA**. Uses **main mode** (6 messages, protects identities) or **aggressive mode** (3 messages, faster, exposes identity). The peers agree on encryption, hash, authentication method, DH group and lifetime (the "policy" or proposal), run DH, and authenticate each other.
* **Phase 2** – under the protection of phase 1, negotiate the **IPsec SAs** that protect user data, using **quick mode** (3 messages). This sets ESP/AH, the encryption and integrity algorithms for data, and which traffic is protected.

**IKEv2** (RFC 7296) simplifies this:

* **IKE_SA_INIT** (one request/response) – negotiates algorithms and performs DH.
* **IKE_AUTH** (one request/response) – authenticates peers and creates the first **child SA** (the IPsec SA).
* That is **4 messages** total for a working tunnel. Additional child SAs use **CREATE_CHILD_SA**.
* Built-in NAT traversal, dead peer detection, EAP for user authentication, and the option for each peer to use a different authentication method.

> **Real world:** Prefer IKEv2 for new designs. IKEv1 aggressive mode with pre-shared keys is considered weak because the hashed key material can be captured and attacked offline.

### Security associations

An **SA** is a one-way agreement: algorithms, keys, lifetime, identified by an **SPI** (Security Parameter Index). Data traffic needs a **pair** of IPsec SAs, one in each direction. The IKE SA itself is bidirectional.

### ESP vs AH

| | ESP | AH |
|--|-----|-----|
| IP protocol number | **50** | **51** |
| Encryption | Yes | **No** |
| Integrity / origin authentication | Yes (payload; and in tunnel mode the whole original packet) | Yes, including immutable outer IP header fields |
| Works through NAT | Yes, with NAT-T | **No**, NAT changes the IP header and breaks the AH integrity check |
| Use today | Almost always | Rare |

> **Exam tip:** ESP is 50, AH is 51. If you need encryption, it must be ESP. These are IP **protocol** numbers, not TCP/UDP ports.

## Tunnel mode vs transport mode

**Tunnel mode** encrypts the **entire original IP packet** and adds a **new outer IP header** with the VPN gateways' addresses:

```text
[ New IP hdr (GW1 -> GW2) | ESP hdr | Original IP hdr (host -> host) | TCP | Data | ESP trailer | ESP auth ]
                                    \_____________________ encrypted ___________________/
```

The internet only sees gateway-to-gateway traffic. This is the default and the normal mode for **site-to-site** VPNs.

**Transport mode** keeps the **original IP header** and protects only the payload:

```text
[ Original IP hdr (host -> host) | ESP hdr | TCP | Data | ESP trailer | ESP auth ]
                                           \________ encrypted ________/
```

It saves 20 bytes per packet but only makes sense when the IPsec endpoints *are* the communicating hosts, for example host-to-host, or **GRE over IPsec** where the GRE tunnel endpoints are the same routers as the IPsec peers.

## GRE over IPsec

Plain IPsec (crypto-map based) protects **unicast IP** only. Routing protocols such as OSPF and EIGRP rely on multicast, so they cannot run directly over a policy-based IPsec tunnel.

**GRE** (Generic Routing Encapsulation, **IP protocol 47**) creates a virtual point-to-point tunnel interface that carries multicast, broadcast and even non-IP traffic, so routing protocols can form adjacencies across it. GRE provides **no encryption** and no integrity.

**GRE over IPsec** combines them: GRE encapsulates the packets (including routing protocol multicast), then IPsec encrypts the GRE packets. Because GRE already adds an outer IP header between the two routers, IPsec usually uses **transport mode** here to avoid a third header.

Modern alternatives: **VTI** (virtual tunnel interface, `tunnel mode ipsec ipv4`) gives a routable tunnel interface without GRE overhead, and **DMVPN** builds dynamic multipoint GRE/IPsec tunnels between spokes.

## NAT traversal

ESP has no ports, so a PAT device cannot multiplex it, and NAT breaks AH entirely. **NAT-T** solves this:

1. During IKE, the peers detect whether a NAT device sits between them (by exchanging hashes of their addresses and ports).
2. If NAT is detected, IKE moves from UDP 500 to **UDP 4500** and ESP packets are wrapped in **UDP 4500** as well.
3. Keepalives keep the NAT translation alive.

> **Exam tip:** A firewall in front of a VPN gateway must allow **UDP 500** (IKE), **UDP 4500** (NAT-T) and **IP protocol 50** (ESP). AH (51) only if you actually use it.

## Putting a site-to-site tunnel together (conceptual)

1. Interesting traffic (defined by an ACL or by routing into a tunnel interface) triggers the tunnel.
2. IKE phase 1 / IKE_SA_INIT + IKE_AUTH: peers agree on a proposal, run DH, authenticate.
3. IPsec SAs (phase 2 / child SA) are created, one per direction.
4. Data is encrypted with ESP in tunnel mode.
5. SAs are rekeyed before their lifetime expires.

Troubleshooting commands you may see in exhibits: `show crypto isakmp sa` (IKEv1, state `QM_IDLE` means phase 1 is up), `show crypto ikev2 sa` (`READY`), and `show crypto ipsec sa` (encaps/decaps counters; encaps rising with decaps at zero points to a problem on the far side or the return path).

## Key takeaways

* Site-to-site connects networks via gateways; remote access connects a user via a client (Cisco Secure Client) or clientless browser portal.
* IKE runs on UDP 500 (UDP 4500 with NAT-T). IKEv1: phase 1 (main/aggressive) builds the IKE SA, phase 2 (quick mode) builds IPsec SAs. IKEv2: IKE_SA_INIT + IKE_AUTH, 4 messages.
* ESP = IP protocol 50, encrypts and authenticates. AH = IP protocol 51, authenticates only and breaks with NAT.
* Tunnel mode adds a new IP header and protects the whole packet (site-to-site); transport mode protects only the payload (host-to-host, GRE over IPsec).
* GRE (IP 47) carries multicast/routing protocols but does not encrypt; GRE over IPsec adds encryption.
* IPsec SAs are unidirectional and identified by an SPI.
