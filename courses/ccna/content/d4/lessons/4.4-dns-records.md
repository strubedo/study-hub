## DNS in one minute

A client asks its configured **recursive resolver** (for example 10.10.1.53) for a name. The resolver walks the hierarchy (root, then `.com`, then the zone's **authoritative** servers), caches the answer for the record's **TTL**, and returns it. Most "the network is down" tickets that turn out to be DNS fall into a few patterns: a missing or wrong record, a stale cached answer, a broken delegation, or a client pointed at the wrong resolver.

The v2.0 blueprint verb is **diagnose**, so focus on reading `nslookup` and `dig` output and spotting which record is wrong.

## Record types you must know

| Type | Maps | Example | Used for |
|------|------|---------|----------|
| A | Name to IPv4 | `web01.example.com. 300 IN A 203.0.113.80` | Host and web access over IPv4 |
| AAAA | Name to IPv6 | `web01.example.com. 300 IN AAAA 2001:db8:10::80` | Host and web access over IPv6 |
| CNAME | Alias to canonical name | `www.example.com. 300 IN CNAME web01.example.com.` | Pointing several names at one host |
| MX | Domain to mail server name + preference | `example.com. 3600 IN MX 10 mail1.example.com.` | Where to deliver email for the domain |
| NS | Zone to authoritative server name | `example.com. 86400 IN NS ns1.example.net.` | Delegation and authority |
| PTR | IP (reverse name) to name | `80.113.0.203.in-addr.arpa. 3600 IN PTR web01.example.com.` | Reverse lookup, logging, mail checks |

Other types you will see in output: **SOA** (start of authority: primary server, serial, timers, negative-cache TTL) and **TXT** (SPF, domain verification).

### TTL

The TTL (seconds) tells resolvers how long they may cache a record. A change on the authoritative server is not seen by clients until cached copies expire. Before a planned migration, lower the TTL (for example to 300) a day ahead; after the move, raise it again.

> **Exam tip:** "I fixed the record but some users still reach the old server" almost always means caching. Check the TTL in the old answer; the remaining TTL counts down in a resolver's response.

## Rules that break things

### CNAME rules

* A name that has a CNAME **cannot have any other record** (no A, no MX, no TXT at the same name).
* Therefore a CNAME is **not allowed at the zone apex** (`example.com.` itself), because the apex must carry SOA and NS records. Use an A/AAAA record at the apex (some DNS providers offer a proprietary "ALIAS/ANAME" flattening feature, but that is not a standard record type).
* CNAMEs can chain, but every hop costs a lookup and loops break resolution.

### MX rules

* The MX target must be a **hostname**, not an IP address. `example.com. MX 10 203.0.113.25` is invalid.
* The MX target must have its own A and/or AAAA record, and it **must not be a CNAME** (RFC 2181). Many mail servers tolerate it, some do not.
* **Lower preference value = more preferred.** MX 10 is tried before MX 20. Equal values share load.

### NS rules

* NS targets are hostnames and must not be CNAMEs.
* The parent zone's NS records (the delegation) must match servers that actually answer authoritatively for the zone. A "lame delegation" points to a server that does not host the zone.

### PTR rules

* IPv4 reverse names reverse the octets under `in-addr.arpa`: 203.0.113.80 becomes `80.113.0.203.in-addr.arpa`.
* IPv6 reverse names reverse every **nibble** (hex digit) of the full 32-digit address under `ip6.arpa`.
* PTR records live in a reverse zone usually controlled by whoever owns the address block (often the ISP for public space). Many mail servers reject mail from an IP whose PTR is missing or does not match its forward A record.

## Reading `nslookup`

```text
C:\> nslookup www.example.com
Server:  dns1.corp.example.com
Address:  10.10.1.53

Non-authoritative answer:
Name:    web01.example.com
Addresses:  2001:db8:10::80
          203.0.113.80
Aliases:  www.example.com
```

* **Server/Address** – which resolver answered. If this is not the resolver you expect, the client's DNS settings are wrong.
* **Non-authoritative answer** – it came from a resolver's cache or recursion, not directly from the zone's server. That is normal.
* **Name** – the canonical name; **Aliases** – the CNAME you asked for. So `www` is a CNAME to `web01`, which has both A and AAAA records.

Other useful forms: `nslookup -type=mx example.com`, `nslookup 203.0.113.80` (PTR lookup), `nslookup www.example.com 1.1.1.1` (ask a specific server).

Errors:

* `*** dns1.corp.example.com can't find www.exmaple.com: Non-existent domain` – NXDOMAIN; the name does not exist (here, a typo).
* `DNS request timed out` – the resolver did not answer: reachability, ACL or the DNS service is down.

## Reading `dig`

```text
$ dig example.com MX

;; ->>HEADER<<- opcode: QUERY, status: NOERROR, id: 40711
;; flags: qr rd ra; QUERY: 1, ANSWER: 2, AUTHORITY: 0, ADDITIONAL: 1

;; ANSWER SECTION:
example.com.        3600    IN      MX      10 mail1.example.com.
example.com.        3600    IN      MX      20 mail2.example.com.

;; Query time: 18 msec
;; SERVER: 10.10.1.53#53(10.10.1.53) (UDP)
```

* **status** – `NOERROR` (fine), `NXDOMAIN` (name does not exist), `SERVFAIL` (resolver could not get an answer, often broken delegation or DNSSEC failure), `REFUSED` (server will not answer you).
* `NOERROR` with **ANSWER: 0** means the name exists but has no record of that type ("NODATA"), for example an A record exists but no AAAA.
* **flags** – `aa` means the answer is authoritative; `ra` means recursion is available.
* Useful options: `dig @ns1.example.net example.com NS` (ask a specific server), `dig -x 203.0.113.80` (reverse lookup), `dig +short`, `dig +trace`.

> **Watch out:** A dual-stack site can work for some users and fail for others when the **AAAA** record is wrong. Clients with IPv6 connectivity prefer IPv6 and try the bad address first. Test both `dig A` and `dig AAAA`.

## DNS on IOS XE

Routers and switches are DNS **clients** too (for `ping`, `traceroute`, `copy scp://host`, NTP by name).

```ios
R1(config)# ip domain name corp.example.com
R1(config)# ip name-server 10.10.1.53 10.10.2.53
R1(config)# ip domain lookup
R1# show hosts
Default domain is corp.example.com
Name servers are 10.10.1.53, 10.10.2.53
...
```

* `ip domain lookup` is **enabled by default**. The older form `ip domain-lookup` is still accepted.
* With lookup enabled and **no** `ip name-server`, IOS sends queries to the broadcast address 255.255.255.255.
* `ip domain name` is appended to unqualified names (`ping web01` tries `web01.corp.example.com`).
* `ip host NAME ADDRESS` adds a static entry to the local host table.

### The "Translating..." delay

When you mistype a command at the EXEC prompt, IOS assumes the word is a hostname you want to Telnet to and tries to resolve it:

```ios
R1# shwo ip route
Translating "shwo"...domain server (255.255.255.255)
% Unknown command or computer name, or unable to find computer address
```

You wait several seconds while it times out. Lab engineers configure `no ip domain lookup` to stop it. The trade-off is that the device can no longer resolve names through DNS. In production a better fix is configuring a reachable name server (the lookup then fails fast) and setting `transport preferred none` on the lines so typos are not treated as Telnet attempts.

## A diagnosis workflow

1. **Which resolver** is the client using? (`ipconfig /all`, `resolvectl status`, `show hosts`)
2. **Is the resolver reachable** on UDP/TCP 53? A timeout is a network/ACL problem, not a record problem.
3. **What does the resolver return?** NXDOMAIN, NODATA, or a wrong address?
4. **What does the authoritative server return?** `dig @ns1... name type`. If it differs from the resolver, you are looking at a cache; wait out the TTL or flush.
5. **Check the record rules**: CNAME conflicts, MX target is a name with an A/AAAA, PTR exists for mail servers.

## Key takeaways

* A = IPv4, AAAA = IPv6, CNAME = alias, MX = mail server name with preference (lower wins), NS = authoritative server, PTR = reverse lookup under in-addr.arpa / ip6.arpa.
* TTL controls caching; stale answers after a change are a TTL issue.
* No CNAME at the zone apex or alongside other records; MX and NS targets must be hostnames with address records, not IPs and not CNAMEs.
* `nslookup`: check the Server line, Name vs Aliases, and NXDOMAIN vs timeout. `dig`: check status, ANSWER count and the `aa` flag.
* IOS XE: `ip name-server`, `ip domain name`, `ip domain lookup` (default on); `no ip domain lookup` stops the typo delay but disables DNS resolution.
