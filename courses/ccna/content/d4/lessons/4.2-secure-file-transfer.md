## Why not TFTP or FTP?

Network engineers move two kinds of files constantly: **configurations** (backups, restores, templates) and **software images** (upgrades). For decades the default tool was TFTP. The CCNA v2.0 blueprint now explicitly asks you to manage these files with **SFTP and SCP**, and you should be able to explain why.

| Protocol | Transport | Authentication | Encryption | Notes |
|----------|-----------|----------------|------------|-------|
| TFTP | UDP 69 | None | None | Anyone who can reach the server can read or overwrite files; no directory listing |
| FTP | TCP 21 (control), 20 or ephemeral (data) | Username/password **in clear text** | None | Credentials and config contents visible to a sniffer |
| SCP | TCP 22 (runs over SSH) | SSH (password or public key) | Yes | Simple copy only, no directory browsing |
| SFTP | TCP 22 (an SSH subsystem) | SSH (password or public key) | Yes | Full file-management protocol: list, rename, delete, resume |

A running configuration contains SNMP communities, VPN pre-shared keys, AAA keys and password hashes. Sending it over TFTP or FTP exposes all of that. SCP and SFTP encrypt both the credentials and the file contents, and they authenticate the server (host key) so you know which device you are talking to.

> **Exam tip:** SCP and SFTP both ride on SSH, so both use **TCP 22**. Neither is FTP over TLS (that is FTPS, a different protocol).

## Two directions, two roles

Be clear about which side is the **server** and which is the **client**:

* **The router pulls or pushes from the CLI** (`copy ... scp:` or `copy scp: ...`). The router is the **client**. The PC or file server runs the SCP/SFTP server. No special server configuration is needed on the router beyond normal routing and (optionally) a source interface.
* **An admin pushes a file to the router from a PC** (`scp image.bin admin@10.1.1.1:flash:/image.bin`). The router is the **server**. You must enable the IOS SCP server.

## Enabling the IOS XE SCP server

The SCP server relies on SSH and on AAA. The authenticated user must land directly in privilege 15, because SCP does not give you a chance to type `enable`. That is why AAA **exec authorization** is required.

```ios
R1(config)# hostname R1
R1(config)# ip domain name corp.example.com
R1(config)# crypto key generate rsa modulus 2048
R1(config)# ip ssh version 2
R1(config)# username netadmin privilege 15 algorithm-type scrypt secret C0mpl3x!Pass
R1(config)# aaa new-model
R1(config)# aaa authentication login default local
R1(config)# aaa authorization exec default local
R1(config)# ip scp server enable
```

From a Linux or macOS workstation:

```text
$ scp isr4300-universalk9.17.12.04.SPA.bin netadmin@10.1.1.1:flash:/isr4300-universalk9.17.12.04.SPA.bin
```

> **Watch out:** The classic failure is "Administratively disabled" or the transfer closing immediately. Check for `ip scp server enable`, then check that `aaa authorization exec` is configured and the user has privilege 15. A privilege 1 user can SSH in but cannot use SCP.

## Copying with the router as the client

### Backing up the configuration

```ios
R1# copy running-config scp://netadmin@10.1.50.25/backups/R1-confg
Address or name of remote host [10.1.50.25]?
Destination username [netadmin]?
Destination filename [backups/R1-confg]?
Writing backups/R1-confg
Password:
!
2847 bytes copied in 0.623 secs (4570 bytes/sec)
```

The URL form is `scp://[user[:password]@]host/path`. Putting the password in the URL works but leaves it in command history, so let the router prompt for it.

SFTP uses the same pattern:

```ios
R1# copy running-config sftp://netadmin@10.1.50.25/backups/R1-confg
```

### Restoring or merging a configuration

```ios
R1# copy scp://netadmin@10.1.50.25/backups/R1-confg running-config
```

Copying **into** `running-config` **merges** the file with the current config; it does not replace it. To replace the running configuration atomically, IOS XE offers `configure replace`, which is beyond the CCNA but worth knowing exists.

### Pulling a new software image

```ios
R1# copy scp://netadmin@10.1.50.25/images/isr4300-universalk9.17.12.04.SPA.bin flash:
Destination filename [isr4300-universalk9.17.12.04.SPA.bin]?
Password:
!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!
756224416 bytes copied in 412.884 secs (1831581 bytes/sec)
```

Before copying, confirm there is room:

```ios
R1# show flash: | include bytes
7194652672 bytes total (5482115072 bytes free)
```

`dir flash:` gives the same information plus a file listing.

## Verifying image integrity

A corrupted or tampered image can brick a device or plant a backdoor. Compare the file hash with the value Cisco publishes on the download page.

```ios
R1# verify /md5 flash:isr4300-universalk9.17.12.04.SPA.bin
.....................................................Done!
verify /md5 (flash:isr4300-universalk9.17.12.04.SPA.bin) = 0b3c6e1f8a2d4b7c9e1f2a3b4c5d6e7f
```

You can also pass the expected hash so IOS does the comparison for you:

```ios
R1# verify /md5 flash:isr4300-universalk9.17.12.04.SPA.bin 0b3c6e1f8a2d4b7c9e1f2a3b4c5d6e7f
.....................................................Done!
Verified (flash:isr4300-universalk9.17.12.04.SPA.bin) = 0b3c6e1f8a2d4b7c9e1f2a3b4c5d6e7f
```

If the hashes do not match, IOS prints `%Error verifying` followed by the computed hash. Delete the file and copy it again.

> **Real world:** MD5 is fine for detecting accidental corruption. For tamper detection, Cisco also publishes SHA-512 hashes and signs images; the device checks the image signature at boot.

## Booting the new image

On routers running in **bundle mode** you point the boot variable at the `.bin` file:

```ios
R1(config)# no boot system
R1(config)# boot system flash:isr4300-universalk9.17.12.04.SPA.bin
R1(config)# end
R1# write memory
R1# show bootvar
BOOT variable = flash:isr4300-universalk9.17.12.04.SPA.bin,12;
```

`no boot system` removes old entries first; otherwise the router tries them in the order listed. If no `boot system` command exists, the device boots the first valid image it finds in flash.

> **Watch out:** Catalyst 9000 switches normally run in **install mode** and boot `flash:packages.conf`, upgrading with `install add file flash:<image> activate commit`. Do not point a switch in install mode at the `.bin` directly unless you intend to convert it to bundle mode.

## Typical workflow

1. `show version` and `show flash:` – current release and free space.
2. `copy running-config scp://...` – back up the config off the box.
3. `copy scp://.../image.bin flash:` – fetch the new image.
4. `verify /md5 flash:image.bin <published-hash>` – confirm integrity.
5. Update the boot variable (or use `install` on Catalyst 9000), then `write memory`.
6. `reload` in a maintenance window, then `show version` to confirm.

## Key takeaways

* TFTP (UDP 69) has no authentication or encryption; FTP sends credentials in clear text. SCP and SFTP run over SSH on TCP 22.
* When the router runs `copy ... scp:` it is the client; `ip scp server enable` is needed only when files are pushed **to** the router.
* The IOS SCP server needs SSH, `aaa new-model`, `aaa authentication login` and **`aaa authorization exec`**, and a privilege 15 user.
* Copying a file into `running-config` merges; it does not replace.
* Check free space with `show flash:`/`dir flash:` and integrity with `verify /md5 flash:file [hash]`.
* Routers in bundle mode use `boot system flash:<image>`; Catalyst 9000 in install mode uses `packages.conf` and `install` commands.
