## Why AI is on the CCNA now

CCNA v2.0 adds a whole domain on AI and states that candidates may have to **evaluate output and recommendations from agentic AI and digital network assistants** during operations and troubleshooting. That is the real skill being tested: not building AI models, but knowing what an AI system in the NOC is doing, what it is allowed to do, and when its answer is wrong.

Vendors are moving quickly here. Cisco, for example, describes its approach as **AgenticOps** — humans and AI agents working together, with people keeping oversight. It markets **AI Canvas** as a shared generative workspace where engineers and agents troubleshoot together, alongside the **Cisco AI Assistant**, and it describes both as backed by a networking-specific large language model it calls the **Deep Network Model**. Product names and features will change; the concepts in this lesson are what the exam tests.

## AI and ML vocabulary at CCNA depth

| Term | Meaning | Network example |
|---|---|---|
| **Artificial intelligence (AI)** | Systems performing tasks that normally need human judgment | Any of the below |
| **Machine learning (ML)** | Systems that learn patterns from data rather than following hand-written rules | Learning normal traffic baselines |
| **Supervised learning** | Trained on **labeled** examples (input + correct answer) | Classifying flows as "normal" or "attack" from a labeled dataset |
| **Unsupervised learning** | Finds structure in **unlabeled** data (clusters, outliers) | Spotting a device whose behavior deviates from its peers |
| **Predictive AI** | Forecasts a value or outcome from historical data | "Uplink Gi1/0/48 will exceed 90% utilization in about three weeks" |
| **Generative AI** | Produces new content (text, code, config) from a prompt | Drafting an ACL, summarizing 500 log lines |
| **Large language model (LLM)** | A generative model trained on huge amounts of text | The engine behind chat assistants |
| **Agentic AI** | An AI system that pursues a goal by planning and taking actions with tools, observing results and iterating | Investigating a ticket by running show commands, correlating telemetry, proposing a fix |

> **Exam tip:** Generative AI *answers*; agentic AI *acts*. A chatbot that writes a config block when asked is generative. A system that decides which devices to query, runs the commands itself, reads the output and decides what to do next is agentic.

## The agent loop

An AI agent wraps an LLM with tools, memory and rules. It repeats a loop until the goal is met or it needs a human:

1. **Perceive / gather** — read the goal (a ticket, an alert, an operator's request) and collect data through tools: telemetry, syslog, controller APIs, read-only show commands.
2. **Reason / plan** — form hypotheses ("the uplink is err-disabled"), decide what evidence is still needed, and choose the next action.
3. **Act** — call a tool: run another show command, query the controller's northbound API, open or update a ticket, or (if permitted and approved) push a configuration change.
4. **Observe** — read the tool's result and compare it with the expectation; update the plan; loop.

A good agent finishes by **verifying**: after a change it re-checks the same evidence that showed the problem (interface state, routing table, reachability) and records what it did.

### Tools are how an agent touches the network

The model itself only produces text. Everything it "does" goes through **tools** — functions or APIs it is allowed to call, such as:

* run an allow-listed show command on a device (SSH, RESTCONF);
* query a controller (Catalyst Center or Meraki dashboard API), monitoring system or syslog/SIEM;
* read and update tickets in an ITSM system;
* submit a change for approval or execute an approved one.

Open standards such as the Model Context Protocol (MCP) are emerging to describe tools to AI agents in a consistent way, but the principle is the same regardless of protocol: **the agent can do only what its tools and credentials permit.**

## Typical use cases

* **Troubleshooting assistants** — "users in VLAN 20 at Branch 7 can't reach the ERP server": the agent checks the access port, trunk, SVI, DHCP bindings and routing, and presents findings with evidence.
* **Config compliance and drift** — compare running configs against the golden template or IaC source of truth and propose remediation.
* **Ticket triage and enrichment** — read incoming tickets, attach relevant telemetry and logs, de-duplicate, set priority and route to the right team.
* **Log and alert summarization** — turn thousands of syslog lines into "Gi0/0/1 on BR7-RTR1 flapped 14 times after 02:00; OSPF adjacency reset each time."
* **Change preparation** — draft config, verification steps and rollback for a human to review.
* **Capacity and anomaly insight** — predictive and unsupervised models flag trends and outliers.

## Guardrails: keeping agents safe

| Guardrail | What it means in practice |
|---|---|
| **Least privilege** | Separate credentials for the agent; read-only (e.g., privilege level limited to show commands, or AAA command authorization) unless a task truly needs more |
| **Read-only vs change-making actions** | Diagnostics run freely; anything that changes state (config, `clear`, `reload`, port bounce) is a separate, gated action |
| **Human-in-the-loop approval** | A named engineer approves each change (or each class of change) before execution |
| **Scope limits** | Allow-lists of commands, devices and change windows; blast-radius limits (one device first, not all at once) |
| **Audit trail** | Every prompt, tool call, output, approval and change is logged with identity and timestamp — and ideally also captured in device logs via AAA accounting and syslog |
| **Verification and rollback** | Post-change checks plus a prepared rollback |

> **Watch out:** Never give an agent a shared admin account "so it never fails a command". If something goes wrong you lose both the safety boundary and the ability to tell who — person or agent — did what.

**Human-in-the-loop** means the agent pauses for a human decision before acting. Some organizations move routine, low-risk, pre-approved actions to **human-on-the-loop** (the agent acts, a human monitors and can intervene). The exam-safe default for production changes is human approval.

## Risks you must recognize

* **Hallucination** — the model produces fluent, confident content that is false: a show command that does not exist, a wrong default, an invented bug ID, or a conclusion the data doesn't support.
* **Ungrounded conclusions** — the summary contradicts the very evidence attached to it (e.g., "VLAN 30 is now forwarding" while the trunk output lists only VLANs 1, 10, 20).
* **Stale or partial data** — the agent saw one device, an old config backup, or a single poll.
* **Prompt injection** — untrusted text the agent reads (a ticket, an interface description, a log message, a web page) contains instructions that try to redirect it. Treat all such data as data, not as commands.
* **Over-broad action** — a "fix" that removes a protection (disabling BPDU Guard, `errdisable recovery cause all`, permit-any ACLs) instead of resolving the cause.
* **Data leakage** — sensitive data sent to an unapproved AI service (see lesson 5.2).

## Validating AI output

Treat AI output like a recommendation from a capable but unverified colleague:

1. **Check the evidence** — does the attached show output actually say what the summary claims? Read it yourself.
2. **Check the commands** — do they exist on this platform and version? Use `?` help on the device or vendor documentation. Watch for commands that look plausible but aren't real.
3. **Check the logic** — does the diagnosis explain *all* the symptoms? Would the proposed fix address the root cause or just the symptom?
4. **Check the risk** — is the action read-only or state-changing? What is the blast radius? Is there a rollback?
5. **Verify after** — confirm with independent show commands/telemetry that the change had the intended effect.

```ios
DIST-SW1# show interfaces GigabitEthernet1/0/48 trunk
DIST-SW1# show ip ospf neighbor
DIST-SW1# show logging | include UPDOWN
```

> **Exam tip:** In "evaluate the AI's recommendation" questions, the right answer is usually the one that (a) checks the claim against real device output, (b) approves read-only steps while gating or rejecting risky changes, or (c) fixes the root cause instead of disabling a safety feature. "Accept it because the AI has access to the devices" is almost never right.

> **Real world:** Agents are genuinely good at the tedious part — collecting the same ten show commands from forty devices and correlating them in seconds. Let them do that; keep the judgment about changes with a human.

## Key takeaways

* Predictive AI forecasts, generative AI creates content, agentic AI plans and acts with tools toward a goal.
* Supervised learning uses labeled data; unsupervised learning finds patterns in unlabeled data.
* Agent loop: perceive/gather → reason/plan → act with tools → observe/verify, repeat.
* Guardrails: least privilege, read-only by default, human-in-the-loop approval for changes, scope limits and a complete audit trail.
* Hallucinations are confident but false outputs — invented commands, wrong facts, conclusions the evidence doesn't support.
* Always validate AI conclusions against show commands and telemetry before acting, and verify after.
* Prefer fixes that address root cause over ones that disable protections.
