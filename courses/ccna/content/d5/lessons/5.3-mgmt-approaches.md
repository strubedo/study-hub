## Why management approaches matter

Every network has to be configured, monitored and changed. Blueprint 5.3 asks you to describe five ways of doing that. They are not mutually exclusive — most real networks mix several — but each has a distinct "where does the intelligence live, and how does a change reach the device?" answer. Keep that question in mind and the comparisons become easy.

| Approach | Where config/policy lives | How a change reaches the device | Typical example |
|---|---|---|---|
| Device-based | On each box | A human types CLI per device (console/SSH) | `ssh R1`, `configure terminal` |
| Cloud-based | Vendor-hosted dashboard | Device keeps an outbound tunnel to the cloud and pulls its config | Cisco Meraki dashboard |
| Controller-based | On-prem (or private cloud) controller | Controller pushes via southbound APIs | Cisco Catalyst Center (formerly DNA Center) |
| Automation-based | Scripts/playbooks | A tool connects to many devices (SSH, NETCONF, RESTCONF, APIs) | Python, Ansible |
| Infrastructure as code | Declarative files in version control | A pipeline applies the reviewed desired state | Git + Ansible/Terraform |

## Device-based (traditional) management

Each router and switch has its own management plane and its own running-config. An engineer logs in to one device at a time and types commands. This is the model most CCNA labs use, and it is still how you troubleshoot: `show` commands on the box are the ground truth.

Strengths: no extra infrastructure, works when everything else is broken, every engineer knows it.
Weaknesses: slow at scale, error-prone (typos, missed devices), configuration drift between "identical" devices, and no single place to see or enforce policy.

> **Watch out:** "Device-based" refers to how the network is *managed*. Every device still has its own control plane in traditional networks — routing protocols run on each router regardless of the management approach.

## Cloud-based management

Devices are claimed into an organization in a vendor-hosted portal. On boot they reach out (outbound HTTPS/tunnel) to the cloud, authenticate, and download their configuration. Engineers manage everything from a browser or the cloud's API.

Key points:

* **Zero-touch provisioning** — ship a device to a branch, someone plugs it in, it pulls its config. Ideal for many small sites with no local IT.
* **Management traffic goes to the cloud; user data traffic does not.** Client traffic is forwarded locally (or across your WAN/VPN) — the cloud is a management plane, not a data path. If the cloud is unreachable, already-configured devices keep forwarding traffic but you cannot make changes.
* Subscription licensing and dependence on Internet connectivity to the management service.

> **Exam tip:** If a scenario stresses "hundreds of small sites", "no on-site IT staff", "no servers in our data center" and "single web portal", the answer is cloud-based management.

## Controller-based management

A controller centralizes management (and sometimes parts of the control plane) for many devices. Cisco Catalyst Center (formerly Cisco DNA Center) is the CCNA example for enterprise campus and branch; wireless LAN controllers are another familiar controller.

### Northbound and southbound APIs

* **Southbound API (SBI)** — controller ↔ network devices. Examples: NETCONF, RESTCONF, SSH/CLI, SNMP, and (historically in SDN) OpenFlow. The controller uses these to push configuration and collect state.
* **Northbound API (NBI)** — applications/engineers ↔ controller. Usually a REST API over HTTPS with JSON. A Python script that asks Catalyst Center for the device inventory, or an ITSM system that opens a ticket from a controller event, uses the northbound API.

Memory trick: draw the controller in the middle; apps sit *above* it (north), devices sit *below* it (south).

### Underlay, overlay and fabric

In controller-based fabrics such as SD-Access:

* **Underlay** — the physical network and its routing (IP connectivity between fabric nodes).
* **Overlay** — virtual networks built on top with tunnels (for SD-Access, VXLAN encapsulation with LISP as the control plane).
* **Fabric** — the combination: underlay + overlay + the policy the controller applies.

### Traditional vs controller-based

| | Traditional (device-based) | Controller-based |
|---|---|---|
| Configuration | Per device, CLI | Centrally defined, pushed to many devices |
| Policy | Implemented box by box | Defined once (intent), translated per device |
| Visibility | Per-device show commands | Network-wide inventory, health, assurance |
| Programmability | Screen-scraping CLI | Northbound REST API |
| Consistency | Prone to drift | Templates and compliance checks |
| Data plane | Distributed on devices | Still distributed on devices |

> **Watch out:** A controller does **not** forward user traffic. The data plane stays on the switches and routers. Answers that say "all user traffic is sent to the controller" are wrong.

## Automation-based management

Here the "controller" is a tool you run: Python scripts (Netmiko, NAPALM, ncclient, requests), Ansible playbooks, or vendor SDKs. The tool logs in to many devices and runs the same tasks consistently.

### Model-driven programmability: NETCONF and RESTCONF

| | NETCONF | RESTCONF |
|---|---|---|
| Transport | SSH, TCP port 830 | HTTPS (TCP 443) |
| Encoding | XML | JSON or XML |
| Operations | `<get>`, `<get-config>`, `<edit-config>`, etc. | HTTP GET, POST, PUT, PATCH, DELETE |
| Data model | YANG | YANG |

**YANG** is the modeling language that describes what configuration and operational data a device exposes. NETCONF and RESTCONF are the *protocols* that carry YANG-modeled data. On IOS-XE you enable them with `netconf-yang` and `restconf` (RESTCONF also needs the HTTPS server).

```ios
R1(config)# netconf-yang
R1(config)# ip http secure-server
R1(config)# restconf
```

> **Real world:** Screen-scraping CLI output with regex breaks when output formats change between releases. Structured data (JSON/XML from RESTCONF/NETCONF, or parsed output) is far more reliable for automation.

## Infrastructure as code (IaC)

IaC treats network configuration like software:

1. The **desired state** is written in files (YAML variables, templates, Terraform HCL).
2. The files live in **version control** (Git) — every change has an author, a timestamp, a message and a diff.
3. Changes go through a **branch → commit → pull/merge request → peer review → automated checks → merge** workflow.
4. A **pipeline** (CI/CD) applies the merged desired state to the network and verifies it.

### Declarative vs imperative

* **Imperative** — you specify the steps ("type these 12 commands in this order").
* **Declarative** — you specify the end state ("VLAN 30 named USERS must exist on these switches") and the tool works out what to change. Running it again when the network already matches produces **no changes** (idempotent).

**Terraform** is the classic declarative IaC tool: you write HCL describing resources, `terraform plan` shows what would change, `terraform apply` makes it so, and a **state file** records what Terraform manages. It is strongest at provisioning (cloud networks, controller objects via providers). Ansible is often used for day-2 device configuration and can be run in an IaC style when its playbooks and variables live in Git and run from a pipeline.

### Benefits

* Peer review before anything touches production.
* Full history and easy rollback (revert the commit, re-run the pipeline).
* Repeatable builds: the same files build the lab and production.
* **Drift detection** — compare the live network with the files in Git; manual "quick fixes" show up as differences.

> **Watch out:** IaC does not make drift impossible. Someone can still SSH in and change a device. IaC makes drift *detectable* and *correctable* by re-applying the source of truth.

## Choosing an approach

* One or two devices, emergency troubleshooting → device-based CLI.
* Many small sites, no local IT, OK with SaaS → cloud-based.
* Large campus with policy/segmentation and assurance needs → controller-based.
* Repetitive tasks across mixed devices → automation (scripts, Ansible).
* Teams that want review, history and repeatability for every change → IaC on top of automation.

> **Exam tip:** Expect "which approach fits this scenario?" and "which statement about controller-based networking is true?" questions. Look for the keywords: *per-device CLI*, *dashboard/zero-touch*, *southbound/northbound*, *scripts/playbooks*, *desired state in Git*.

## Key takeaways

* Device-based = per-box CLI; cloud-based = vendor dashboard (e.g., Meraki) with devices pulling config; controller-based = central controller (Catalyst Center, formerly DNA Center).
* Southbound APIs connect the controller to devices (NETCONF, RESTCONF, SSH, SNMP); northbound APIs (REST/JSON) connect apps and scripts to the controller.
* Controllers centralize management and policy; the data plane stays on the devices.
* NETCONF = SSH/TCP 830 + XML; RESTCONF = HTTPS + JSON/XML; both carry YANG-modeled data.
* IaC = declarative desired state in Git, reviewed via pull requests, applied by a pipeline; idempotent runs and drift detection.
* Terraform is a declarative IaC tool using HCL, plan/apply and a state file.
