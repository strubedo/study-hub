## What SNMP does

Simple Network Management Protocol lets a central system **read** device state (interface counters, CPU, uptime, temperature), **receive notifications** when something happens (link down, reboot, authentication failure) and — if permitted — **write** values. It is the workhorse behind most monitoring and graphing tools, and it is still everywhere even as streaming telemetry grows.

## Components

| Component | Role |
|---|---|
| **SNMP manager** (NMS) | The monitoring server. Polls agents and receives notifications. |
| **SNMP agent** | Software on the router/switch/AP that answers the manager and sends notifications. |
| **MIB** (Management Information Base) | The structured, tree-shaped definition of every object an agent can expose. |
| **OID** (Object Identifier) | The dotted-number address of one object in the MIB tree. |

OIDs form a hierarchy. Standard objects live under `1.3.6.1.2.1` (MIB-2); vendor objects live under `1.3.6.1.4.1.<enterprise>` — Cisco is enterprise `9`, so Cisco-specific objects start with `1.3.6.1.4.1.9`.

| OID | Object | Meaning |
|---|---|---|
| `1.3.6.1.2.1.1.3.0` | sysUpTime.0 | Time since the agent (re)started |
| `1.3.6.1.2.1.1.5.0` | sysName.0 | Device hostname |
| `1.3.6.1.2.1.2.2.1.10.<ifIndex>` | ifInOctets | Bytes received on an interface |

The trailing `.0` identifies the single instance of a scalar object; table objects use an index such as the interface's ifIndex instead.

> **Exam tip:** MIB = the database definition (the "schema"); OID = the address of one variable in it. The manager asks for an OID; the agent answers with its value.

## Message types

| Message | Direction | Purpose | Version |
|---|---|---|---|
| **Get** | Manager → agent | Read the value of specific OID(s) | v1+ |
| **GetNext** | Manager → agent | Read the *next* OID in the tree — used to walk tables | v1+ |
| **GetBulk** | Manager → agent | Read many OIDs in one request (efficient table walks) | v2c+ |
| **Set** | Manager → agent | Change a value on the agent | v1+ |
| **Response** | Agent → manager (manager → agent when acknowledging an Inform) | Answer to Get/GetNext/GetBulk/Set; also the Inform acknowledgment | all |
| **Trap** | Agent → manager | Unsolicited notification, **not acknowledged** | v1+ |
| **Inform** | Agent → manager | Unsolicited notification, **acknowledged**; resent if no ack | v2c+ |

### Ports

* Agents listen on **UDP 161** for Get/GetNext/GetBulk/Set.
* Managers listen on **UDP 162** for Traps and Informs.

> **Watch out:** SNMP runs over UDP. Traps can be lost silently; that is why Informs (acknowledged) exist. Informs cost the device more memory because it must hold them until acknowledged.

### Polling vs notifications

Polling (Get every 1–5 minutes) gives trends — utilization graphs come from polling interface octet counters and computing the delta. Notifications give near-real-time alerts for events between polls. Good monitoring uses both.

## Versions and security

| Version | Security | Notes |
|---|---|---|
| SNMPv1 | Community string, cleartext | Original; 32-bit counters only |
| SNMPv2c | Community string, cleartext | Adds GetBulk, Inform, 64-bit counters (Counter64) |
| SNMPv3 | User-based Security Model (USM) | Authentication, encryption, per-user access; View-based Access Control (VACM) |

A **community string** is effectively a shared password sent in **cleartext** in every packet. A read-only (RO) community allows Get operations; a read-write (RW) community also allows Set. Anyone who captures traffic can read it.

### SNMPv3 security levels

| Level | Authentication | Encryption (privacy) |
|---|---|---|
| **noAuthNoPriv** | Username match only | No |
| **authNoPriv** | HMAC (MD5 or SHA) | No |
| **authPriv** | HMAC (MD5 or SHA) | Yes (DES, 3DES or AES) |

Prefer **SHA** and **AES** — MD5 and DES are legacy. authPriv is the only level that protects both the integrity and the confidentiality of SNMP data.

## IOS configuration

### SNMPv2c (read-only, restricted by ACL)

```ios
R1(config)# access-list 10 permit host 10.10.50.20
R1(config)# snmp-server community N3tM0nRO RO 10
R1(config)# snmp-server location HQ-Bldg2-IDF3
R1(config)# snmp-server contact noc@example.com
R1(config)# snmp-server host 10.10.50.20 version 2c N3tM0nRO
R1(config)# snmp-server enable traps
```

* `snmp-server community <string> RO <acl>` — only hosts permitted by ACL 10 may poll with this community.
* `snmp-server host` — where to send notifications (traps by default; add the `informs` keyword for informs).
* `snmp-server enable traps` — enables notification types (you can list specific ones, e.g. `snmp-server enable traps snmp linkdown linkup`).

### SNMPv3 authPriv

```ios
R1(config)# snmp-server group NMSGRP v3 priv
R1(config)# snmp-server user nms1 NMSGRP v3 auth sha Auth#Key2026 priv aes 128 Priv#Key2026
R1(config)# snmp-server host 10.10.50.20 version 3 priv nms1
R1(config)# snmp-server enable traps
```

* `snmp-server group <name> v3 {noauth | auth | priv}` — sets the minimum security level for the group (and optionally read/write views and an ACL).
* `snmp-server user` — creates the user in the group with auth and privacy keys.
* `snmp-server host ... version 3 priv <user>` — send notifications using that user at authPriv.

> **Watch out:** SNMPv3 users do **not** appear in `show running-config` (the keys are localized and stored separately). Use `show snmp user` to verify them, and remember a config restored from a text backup will be missing them.

### Verification

```ios
R1# show snmp
R1# show snmp community
R1# show snmp group
R1# show snmp user
R1# show snmp host
```

## Good practice

* Use SNMPv3 authPriv; if v2c is unavoidable, use RO, a non-default community and an ACL.
* Never use well-known communities such as `public`/`private`.
* Grant RW (Set) only if a tool truly needs it — monitoring and graphing never do.
* Allow UDP 161 to devices only from the NMS subnet.

> **Real world:** Streaming telemetry (model-driven, push-based) is increasingly used for high-frequency data, but SNMP remains the most widely supported way to poll and alert, and you will meet it on almost every network.

## Key takeaways

* Manager (NMS) polls agents; agents send Traps/Informs to the manager.
* MIB defines the objects; an OID such as `1.3.6.1.2.1.1.5.0` (sysName.0) addresses one.
* Get/GetNext/GetBulk/Set go to the agent on UDP 161; Traps/Informs go to the manager on UDP 162.
* Traps are unacknowledged; Informs (v2c+) are acknowledged.
* v1/v2c use cleartext community strings; v2c adds GetBulk, Inform and 64-bit counters.
* SNMPv3 levels: noAuthNoPriv, authNoPriv, authPriv — only authPriv encrypts.
* `snmp-server community ... RO <acl>`, `snmp-server group ... v3 priv`, `snmp-server user ... auth sha ... priv aes 128 ...`, `snmp-server host`, `snmp-server enable traps`.
