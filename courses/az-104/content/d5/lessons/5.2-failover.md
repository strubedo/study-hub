## The failover lifecycle

For an Azure VM replicating from East US (primary) to West US (secondary), the full cycle is:

1. **Test failover** (drill) into an isolated network, then **Cleanup test failover**.
2. **Failover** to West US when you need it, choosing a recovery point.
3. Optionally **Change recovery point**, then **Commit**.
4. **Re-protect**: replicate the West US VM back to East US.
5. **Fail back**: fail over again, from West US to East US, commit.
6. **Re-protect** again so East US replicates to West US as before.

Learn also says to run a successful **test failover at least once every 180 days**; otherwise Site Recovery raises a failover-readiness health issue.

## Test failover

A test failover creates VMs in the target region from a recovery point **without stopping replication** and without touching the source VMs. It's how you prove DR works and how you meet audit requirements for DR drills.

**Portal:** vault > **Replicated items** > the VM (or **Recovery Plans** > the plan) > **Test failover** > recovery point > **Azure virtual network** > **OK**.

Choose an **isolated, non-production** virtual network in the target region: Learn recommends not using the network Site Recovery created for real failover, so the test VM doesn't clash with production IP addresses, domain controllers or DNS. You can preconfigure per-NIC **test failover settings** (subnet, IP, public IP, NSG, load balancer).

When you're done: **Cleanup test failover** > add notes > select **Testing is complete. Delete test failover virtual machines** > **OK**. The test VMs and their disks are removed; replication was never interrupted.

```powershell
$rpi = Get-AzRecoveryServicesAsrReplicationProtectedItem -ProtectionContainer $pc -FriendlyName vm-web-01
$job = Start-AzRecoveryServicesAsrTestFailoverJob -ReplicationProtectedItem $rpi -AzureVMNetworkId $testVnet.Id -Direction PrimaryToRecovery
# validate, then
Start-AzRecoveryServicesAsrTestFailoverCleanupJob -ReplicationProtectedItem $rpi
```

## Choosing a recovery point

| Option | What happens | Trade-off |
|---|---|---|
| **Latest** | Site Recovery first **processes all data** already sent to the service, creates a point from it, then fails over | **Lowest RPO**; slower (processing time adds to RTO) |
| **Latest processed** | Uses the most recent point Site Recovery has **already processed**; the timestamp is shown | **Lowest RTO**; may lose the last few minutes |
| **Latest app-consistent** | Most recent **app-consistent** point | Apps start cleanly; may be an hour or more old (needs app-consistent snapshots enabled) |
| **Latest multi-VM processed / app-consistent** | For recovery plans with multi-VM consistency: common point across the replication group | Only for plans with multi-VM consistency enabled |
| **Custom** | Any point in the retention window | **Single VM only**: not available for recovery plans |

> **Exam tip:** "Minimise data loss" → Latest. "Bring it up as fast as possible" → Latest processed. "The database must start in a consistent state" → Latest app-consistent. "Go back to 03:15, before the bad deployment" → Custom (one VM).

## Failover

**Portal:** **Replicated items** > the VM > **Failover** > recovery point > optionally **Shut down machine before beginning failover** > **OK**. For several VMs, run **Failover** on the **recovery plan** instead.

- **Shut down machine before beginning failover**: Site Recovery tries to shut down the source VM first so no new writes are lost; failover continues even if the shutdown fails (for example, the source region is down).
- Learn's Azure-to-Azure tutorials have one **Failover** action. A separate **planned failover** (shut down, sync, zero data loss) is documented for **Hyper-V** to Azure. In an Azure-to-Azure drill, selecting the shutdown option on a healthy source gets you the same effect.
- The failover job has steps: **Prerequisites check**, **Failover** (process data; for **Latest** this creates the point), and **Start** (create the Azure VM). **Don't cancel** a failover in progress: replication has already stopped and can't simply restart.

After failover the VM runs in West US, in the target resource group and VNet. Check it, then:

- **Change recovery point** if it isn't right (still possible before commit).
- **Commit**: confirms the failover and **deletes all the other recovery points** for the VM; you can no longer change the point. For Azure-to-Azure, commit is required before you can re-protect.

```powershell
$rp  = Get-AzRecoveryServicesAsrRecoveryPoint -ReplicationProtectedItem $rpi
$job = Start-AzRecoveryServicesAsrUnplannedFailoverJob -ReplicationProtectedItem $rpi -Direction PrimaryToRecovery -RecoveryPoint $rp[-1]
Start-AzRecoveryServicesAsrCommitFailoverJob -ReplicationProtectedItem $rpi
```

The Azure CLI equivalent is in the `site-recovery` extension (installed on first use). The names come from the vault's Site Recovery fabric, protection container and replicated item (list them with `az site-recovery fabric list`, `az site-recovery protection-container list` and `az site-recovery protected-item list`); the shape below follows the CLI reference examples:

```bash
az site-recovery protected-item unplanned-failover -g rg-dr-wus --vault-name rsv-contoso-wus \
  --fabric-name <source-fabric> --protection-container <source-container> -n <replicated-item> \
  --failover-direction PrimaryToRecovery --provider-details '{a2a:{}}' --source-site-operations NotRequired
az site-recovery protected-item failover-commit -g rg-dr-wus --vault-name rsv-contoso-wus \
  --fabric-name <source-fabric> --protection-container <source-container> -n <replicated-item>
```

`az site-recovery protected-item reprotect` reverses replication afterwards. Learn's Azure-to-Azure tutorials use the portal and PowerShell, so expect the CLI path to need more lookup work.

## Re-protect and fail back

After a committed failover, the West US VM isn't protected. **Re-protect** reverses replication so West US replicates to East US:

**Portal:** **Replicated items** > the VM (status **Failover committed**) > **Re-protect** > review or **Customize** the target resource group, VNet, cache storage account and availability options in East US > **OK**.

What re-protect does, per Learn:

- If the original VM still exists in East US, Site Recovery turns it off, creates `-ASRReplica` copies of its disks, deletes the original disks and uses the copies as the replication target, then sends only the **delta**. A **read-only lock** is placed on the original resources until failback completes.
- If the original is gone, it seeds the target from scratch.
- The target VNet can't be changed during re-protect (redo the network mapping instead).

To **fail back**: when replication from West US to East US is healthy, run **Failover** again (direction now West US to East US), **Commit**, then **Re-protect** once more so the normal direction resumes.

```powershell
Update-AzRecoveryServicesAsrProtectionDirection -ReplicationProtectedItem $rpi -AzureToAzure `
  -ProtectionContainerMapping $wusToEusMapping -LogStorageAccountId $cacheWus.Id -RecoveryResourceGroupID $rgEus.ResourceId
```

## After failover

Things Site Recovery doesn't do for you unless you script them in a recovery plan:

- Update public DNS records or Traffic Manager / Front Door endpoints.
- Attach public IPs, NSGs and load balancers (unless preconfigured in the NIC settings).
- Fix application connection strings that point at region-specific names.

## Try it yourself

Continue the lab from the Site Recovery lesson (vm-lab-01 replicating East US to West US, status Protected). Cost: a few more cents for the test VM.

1. In West US, create an isolated VNet for the drill:

```bash
az network vnet create -g rg-lab-d5asr-wus -n vnet-dr-test -l westus --address-prefix 10.90.0.0/16 \
  --subnet-name snet-test --subnet-prefix 10.90.1.0/24
```

2. **Replicated items** > vm-lab-01 > **Test failover** > **Latest processed** > `vnet-dr-test` > **OK**. Watch the job steps, then find the test VM in West US (Site Recovery normally gives it a `-test` suffix).
3. **Cleanup test failover** > notes > **Testing is complete** > **OK**. Confirm the test VM is gone and replication is still Protected.
4. Optional, longer: run a real **Failover** with **Latest** and the shutdown option, **Commit**, and **Re-protect**, then fail back.

Clean up: **Disable Replication** on the item, then delete `rg-lab-d5asr`, `rg-lab-d5asr-wus` and any `-asr` resource groups.

## Key takeaways

- Test failover into an isolated VNet; it doesn't interrupt replication; clean up with "Testing is complete"; drill at least every 180 days.
- Recovery points: Latest (lowest RPO), Latest processed (lowest RTO), Latest app-consistent, multi-VM options for plans, Custom (single VM only).
- Failover can first shut down the source VM; don't cancel a running failover.
- Commit deletes the other recovery points and is needed before re-protect.
- Re-protect reverses replication; fail back = failover in the other direction, commit, re-protect again.
