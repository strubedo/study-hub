## Two vault types

Azure Backup stores backup data and policies in a **vault**. There are two kinds, and the workload decides which one you need:

| | **Recovery Services vault** | **Backup vault** |
|---|---|---|
| Resource provider | `Microsoft.RecoveryServices/vaults` | `Microsoft.DataProtection/backupVaults` |
| Azure Backup workloads (Learn's list) | **Azure VMs**, **SQL Server in Azure VMs**, **SAP HANA in Azure VMs**, **Azure Files**, on-premises and hybrid through the **MARS agent**, **Azure Backup Server (MABS)** and **System Center DPM** | **Azure Disks** (managed disks), **Azure Blobs**, **Azure Database for PostgreSQL**, Kubernetes (AKS); Learn also lists newer workloads such as Azure Data Lake Storage and Azure Cosmos DB for some features |
| Also used by | **Azure Site Recovery** (disaster recovery replication) | Not used by Site Recovery |
| Identity | Optional managed identity (for CMK, private endpoints and some restores) | **Managed identity** that needs RBAC roles on the data source and snapshot resource group |
| CLI | `az backup vault ...` | `az dataprotection backup-vault ...` (extension) |
| PowerShell | `Az.RecoveryServices` (`New-AzRecoveryServicesVault`) | `Az.DataProtection` (`New-AzDataProtectionBackupVault`) |

Both are managed from **Resiliency** (the portal's current name for what was Backup center, then Azure Business Continuity Center), from the vault itself, and with Azure RBAC. Up to 500 vaults of either type per subscription.

> **Exam tip:** "Back up a VM, an Azure Files share or SQL Server in a VM" → Recovery Services vault. "Back up a managed disk, blobs or Azure Database for PostgreSQL" → Backup vault. "Replicate a VM to another region" → Recovery Services vault (Site Recovery).

## Region rules

For **backup**, the vault must be in the **same region as the data source**. You can't back up across regions; if you have VMs in East US and West Europe, you need a vault in each region. The vault can be in a different subscription from an Azure VM it protects (cross-subscription backup), and you can move a vault between resource groups and subscriptions, but **never to another region**.

For **Site Recovery**, it's the opposite: the vault must **not** be in the source region; you normally create it in the **target** region (covered in the Site Recovery lesson).

## Storage redundancy: choose it first

Each vault has a **backup storage redundancy**:

| Setting | Copies | Notes |
|---|---|---|
| **Geo-redundant (GRS)** | Primary region + paired region | **Default** for a new Recovery Services vault; required for **Cross Region Restore** |
| **Locally redundant (LRS)** | One datacenter in the primary region | Cheapest; for non-critical or secondary copies |
| **Zone-redundant (ZRS)** | Three zones in the primary region | Data residency with zone resilience; only in regions where Azure Backup supports ZRS |

Learn's rule: **change the redundancy before you protect any item**. Once a backup is configured the setting is locked. To move a GRS vault's items to LRS afterwards you stop protection and reconfigure the items in a new LRS vault.

### Cross Region Restore

On a **GRS** Recovery Services vault you can enable **Cross Region Restore (CRR)**: you can restore VMs, SQL and SAP HANA databases and (per the support matrix) Azure Files from the **paired secondary region** at any time, for drills or outages, without waiting for Microsoft to declare a disaster. Points to remember:

- GRS only, and enabling it costs extra.
- It can take up to 48 hours after enabling before items are available in the secondary region.
- Once protection has started, CRR can't be turned back off (you can't revert the vault to plain GRS or LRS).
- Only vault-tier recovery points replicate; instant restore snapshots don't.

Backup vaults support CRR for PostgreSQL backups.

## Security settings

### Soft delete (secure by default)

When backup data is deleted (for example **Stop backup** with **Delete backup data**), it is kept in a **soft-deleted** state for the soft-delete retention period, **14 days by default**, configurable up to **180 days**. The first 14 days cost nothing; longer retention is billed. During that time you can **undelete** the item, which returns it to **Stop protection with retain data**, and then restore or resume.

Learn now calls this **secure by default**: soft delete is **enforced** for Recovery Services vaults (the region table lists general availability in all public regions and national clouds, although one sentence on the same page still says preview), so it **can't be disabled**; for Backup vaults it is GA in Australia East, West Central US and East Asia and in preview elsewhere, where the portal still lets you disable it. With secure by default, deleting a vault **from the portal** while it holds soft-deleted items moves the **vault itself** into a soft-deleted state (vault soft delete is in preview) instead of removing it. Older documentation called the configurable version "enhanced soft delete" with an "always-on" (irreversible) option; you'll still see `AlwaysOn` as a value in the CLI.

Soft delete also protects recovery points that would be pruned when someone shortens a policy's retention.

### Immutable vault

An **immutable vault** blocks operations that could lose recovery points before they expire: for example reducing retention, stop protection with delete data, or deleting the vault's data early. States: **Disabled**, **Enabled** (reversible, shown as `Unlocked` in the CLI) and **Enabled and locked** (`Locked`, **irreversible**, and backed by WORM storage where available). Test with Unlocked, then lock.

### Multi-user authorization (MUA)

**Multi-user authorization** protects critical operations (disabling soft delete or immutability, reducing retention, stopping protection with delete) by requiring permission on a separate resource, a **Resource Guard**, owned by a different person (ideally in another subscription or tenant). A backup admin alone can't perform the protected operation.

### Encryption and networking

Data is encrypted at rest with platform-managed keys by default; you can use **customer-managed keys** from Key Vault, but you must set them **before** protecting any item and can't revert. Private endpoints are supported (public network access must be disabled first).

## Create a Recovery Services vault

**Portal:** **Recovery Services vaults** (or **Resiliency** > **+ Vault**) > **+ Create** > subscription, resource group, **vault name**, **region** (same as the data) > optionally Redundancy, Vault properties (immutability), Networking > **Review + create**. Then, before protecting anything: vault > **Properties** > **Backup configuration** > **Update** to set redundancy and CRR, and **Security settings** for soft-delete retention.

**Azure CLI:**

```bash
az backup vault create -g rg-bcdr-eus -n rsv-contoso-eus -l eastus
az backup vault backup-properties set -g rg-bcdr-eus -n rsv-contoso-eus \
  --backup-storage-redundancy GeoRedundant --cross-region-restore-flag True
az backup vault backup-properties set -g rg-bcdr-eus -n rsv-contoso-eus --soft-delete-duration 30
az backup vault update -g rg-bcdr-eus -n rsv-contoso-eus --immutability-state Unlocked
```

**Azure PowerShell:**

```powershell
$v = New-AzRecoveryServicesVault -Name rsv-contoso-eus -ResourceGroupName rg-bcdr-eus -Location eastus
Set-AzRecoveryServicesBackupProperty -Vault $v -BackupStorageRedundancy GeoRedundant -EnableCrossRegionRestore
Set-AzRecoveryServicesVaultProperty -VaultId $v.ID -SoftDeleteRetentionPeriodInDays 30
Set-AzRecoveryServicesVaultContext -Vault $v    # later Az.RecoveryServices backup cmdlets use this vault
```

## Create a Backup vault

**Portal:** **Backup vaults** (or **Resiliency** > **+ Vault** > **Backup vault**) > **+ Create** > resource group, name, region, **Backup storage redundancy** (GRS, LRS or ZRS) > Vault properties (soft delete, immutability) > **Review + create**.

**Azure CLI** (the `dataprotection` extension installs on first use):

```bash
az dataprotection backup-vault create -g rg-bcdr-eus --vault-name bv-contoso-eus -l eastus \
  --type SystemAssigned \
  --storage-setting "[{type:'LocallyRedundant',datastore-type:'VaultStore'}]"
```

**Azure PowerShell:**

```powershell
$ss = New-AzDataProtectionBackupVaultStorageSettingObject -DataStoreType VaultStore -Type LocallyRedundant
New-AzDataProtectionBackupVault -ResourceGroupName rg-bcdr-eus -VaultName bv-contoso-eus -Location eastus `
  -StorageSetting $ss -EnableSystemAssignedIdentity
```

The vault's **system-assigned managed identity** then needs roles on what it protects, such as **Disk Backup Reader** on a disk and **Disk Snapshot Contributor** on the snapshot resource group, or **Storage Account Backup Contributor** on a storage account for blobs. The portal offers to assign the missing roles during configure backup.

## Deleting a vault

You can't delete a vault that still has protected items, registered servers, Site Recovery replicated items or private endpoints. With soft delete enforced, the clean path is:

1. **Stop backup** on every item with **Delete backup data**: items move to the soft-deleted state.
2. Unregister servers and storage accounts, disable Site Recovery replication, remove private endpoints.
3. Delete the vault.

What happens at step 3 depends on how you delete, and Learn's two pages differ:

- The **secure-by-default** page (updated October 2026, the most recent) says a delete **started in the portal** moves a vault that holds soft-deleted items into a **soft-deleted state** (preview), which you can recover during the retention period.
- The **delete-vault** page (updated January 2026) says a vault that contains soft-deleted backup data **can't be deleted**, quotes the error ("...there are backup items in soft deleted state in the vault... try vault deletion after the backup items are permanently deleted"), and tells you to disable soft delete, which an enforced vault no longer allows.

So treat both outcomes as possible. A delete through the API (CLI, PowerShell, or deleting the resource group) may be refused until the soft-deleted items expire after the soft-delete retention (14 days by default); the vault isn't removed automatically after that, so you start the delete again. Soft-deleted data for the first 14 days costs nothing. For labs: back up as little as possible, delete the source resources straight away, and plan to finish the cleanup two weeks later.

## Try it yourself

Cloud Shell. Cost: nothing for empty vaults.

```bash
rg=rg-lab-d5vault; loc=eastus
az group create -n $rg -l $loc
az backup vault create -g $rg -n rsv-lab-eus -l $loc
az backup vault backup-properties show -g $rg -n rsv-lab-eus -o jsonc
az backup vault backup-properties set -g $rg -n rsv-lab-eus --backup-storage-redundancy LocallyRedundant
az dataprotection backup-vault create -g $rg --vault-name bv-lab-eus -l $loc --type SystemAssigned \
  --storage-setting "[{type:'LocallyRedundant',datastore-type:'VaultStore'}]"
az dataprotection backup-vault show -g $rg --vault-name bv-lab-eus --query "properties.securitySettings"
```

1. Compare the two vaults in the portal: **Backup items** and **Site Recovery** on the Recovery Services vault, **Backup instances** on the Backup vault.
2. Open each vault's **Properties** > security settings and note the soft-delete state and retention.
3. Try to set the redundancy back to GeoRedundant: it works now, because nothing is protected yet.

Clean up: nothing is protected, so the resource group deletes normally: `az group delete -n $rg --yes --no-wait`.

## Key takeaways

- Recovery Services vault: Azure VMs, SQL and SAP HANA in VMs, Azure Files, MARS, MABS, DPM, and Site Recovery. Backup vault: managed disks, blobs, PostgreSQL, AKS and newer workloads.
- Backup vaults must be in the same region as the data; vaults can't move between regions.
- Default redundancy is GRS; set GRS, LRS or ZRS and Cross Region Restore before protecting anything.
- Soft delete keeps deleted backup data 14 days by default (up to 180); it is now enforced (secure by default) for Recovery Services vaults.
- Immutable vault: Disabled, Enabled (Unlocked), Enabled and locked (irreversible); MUA adds a Resource Guard owned by someone else.
- `az backup vault create`, `New-AzRecoveryServicesVault`; `az dataprotection backup-vault create`, `New-AzDataProtectionBackupVault`.
