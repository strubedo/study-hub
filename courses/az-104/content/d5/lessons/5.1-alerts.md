## The moving parts

| Object | What it does | Resource type |
|---|---|---|
| **Alert rule** | Watches a **scope** for a **condition** and fires an alert | `metricAlerts`, `scheduledQueryRules`, `activityLogAlerts` |
| **Alert** | One fired instance: severity, monitor condition (Fired / Resolved), user response (New / Acknowledged / Closed) | Stored **30 days** |
| **Action group** | Who to notify and what to run | `actionGroups` |
| **Alert processing rule** | Changes fired alerts on the way out: **suppress** their action groups or **add** action groups | `actionRules` (formerly "action rules") |

An alert rule = **scope** (the resources) + **condition** (signal, logic, threshold) + **actions** (zero or more action groups) + **details** (name, severity, description, resource group for the rule).

## Alert types

| Type | Signal | Typical scenario | Notes |
|---|---|---|---|
| **Metric** | Platform, custom or guest metrics | CPU > 85% for 5 minutes | Near real time; static or **dynamic** thresholds; multiple conditions on one resource; one rule can cover many resources of one type **in one region**; stateful by default |
| **Log search** | A KQL query on a workspace (or Application Insights) | More than 5 failed logons in 15 minutes; any VM missing heartbeats | Counts rows or measures a numeric column; split by dimensions such as `_ResourceId`; can be stateful or stateless |
| **Simple log search** | Each row evaluated individually | Alert on every failed backup job row | Near real time at scale |
| **Activity log** | A new activity log event | Someone deletes an NSG; a VM is stopped | **Stateless**; never auto-resolves |
| **Service Health** | Activity log Service Health category | Azure incident or planned maintenance in East US affecting your services | An activity log alert; its action group must be in the **Global** region |
| **Resource Health** | Activity log Resource Health category | vm-sql-01 becomes Unavailable or Degraded | An activity log alert |
| Prometheus, smart detection | Prometheus metrics; Application Insights | AKS and app monitoring | Mention-level for AZ-104 |

**Classic alerts** are retired for the public cloud (Learn's archived page says so; the sovereign clouds followed on February 29, 2024). Everything you create today is one of the types above.

## Severity

Severity is a number on the rule, copied to each alert:

| Sev | Meaning |
|---|---|
| 0 | Critical |
| 1 | Error |
| 2 | Warning (the CLI default) |
| 3 | Informational |
| 4 | Verbose |

Lower number = worse. Alert processing rules and the Alerts page filter on it.

## When the rule evaluates

For **metric** rules you set:

- **Check every** (evaluation frequency): how often the rule runs, for example 1 minute.
- **Lookback period** (window size): how much data each check aggregates, for example 5 minutes.
- **Aggregation**: Average, Maximum, Minimum, Total, Count.
- **Operator and threshold**.

"Every 1 minute, look back 5 minutes, Average Percentage CPU > 85" means: every minute, average the last five minutes of CPU; if that average is above 85, the condition is met. In the CLI, defaults are `--evaluation-frequency 1m` and `--window-size 5m`.

**Static threshold**: you type the number. **Dynamic threshold**: machine learning learns the metric's normal pattern (it uses 10 days of history to find hourly and daily seasonality, and weekly patterns after three weeks), and you choose **sensitivity** High, Medium or Low (Medium and Low are less noisy) plus "number of violations out of evaluation periods". A new dynamic rule won't fire until it has **at least three days and 30 samples** of data. Use dynamic thresholds when "normal" changes over the day or week, or when you monitor hundreds of series with one rule.

**Log search** rules add the query, a **measurement** (table rows, or an aggregation of a numeric column), the aggregation granularity, optional **split by dimensions** (one alert per resource), and "number of violations".

## Stateful and stateless

- **Stateful** alerts fire once, stay **Fired** while the condition holds, send no more notifications, and change to **Resolved** (with a resolved notification) when it clears. Metric alerts resolve after the condition isn't met for **three consecutive checks**. Portal option: **Automatically resolve alerts** (CLI `--auto-mitigate`).
- **Stateless** alerts fire every time the condition is met. All activity log alerts are stateless; their monitor condition stays Fired, and you close them with the user response.

## Action groups

An action group is a reusable list of **notifications** and **actions**, saved in a resource group, with a **display name** and a **short name** (up to 12 characters, shown in SMS and emails).

| Notifications | Actions |
|---|---|
| Email Azure Resource Manager role (members of a role such as Owner) | Automation runbook |
| Email | Azure Functions |
| SMS (country code and number; recipients can reply to unsubscribe) | Event hubs |
| Azure app push notification | ITSM (needs an ITSM connection) |
| Voice call | Logic apps (for example to post to Microsoft Teams) |
| | Secure webhook (Microsoft Entra ID authentication) |
| | Webhook |

Region: **Global** (stored in at least two regions; required for Service Health alerts) or **Regional** (processed in one listed region). SMS, voice, push and email are **rate limited** per recipient across subscriptions; webhooks and other actions are not. Use **Test action group** to send a sample before relying on it. The **common alert schema** gives every action one consistent payload.

**Portal:** **Monitor** > **Alerts** > **Action groups** > **+ Create** > Basics (subscription, resource group, region, action group name, display name) > **Notifications** > **Actions** > **Create**.

```bash
az monitor action-group create -g rg-mon-prod -n ag-ops --short-name ops -l Global \
  --action email ops-mail ops@contoso.com \
  --action webhook ops-hook https://hooks.example.com/alerts usecommonalertschema
agid=$(az monitor action-group show -g rg-mon-prod -n ag-ops --query id -o tsv)
vmid=$(az vm show -g rg-web-prod -n vm-web-01 --query id -o tsv)
az monitor metrics alert create -g rg-mon-prod -n alert-web01-cpu --scopes $vmid \
  --condition "avg Percentage CPU > 85" --window-size 5m --evaluation-frequency 1m \
  --severity 2 --action $agid --description "CPU above 85 percent"
```

```powershell
$email = New-AzActionGroupEmailReceiverObject -Name ops-mail -EmailAddress ops@contoso.com
$ag = New-AzActionGroup -Name ag-ops -ResourceGroupName rg-mon-prod -Location Global -GroupShortName ops -EmailReceiver $email
$vm = Get-AzVM -ResourceGroupName rg-web-prod -Name vm-web-01
$crit = New-AzMetricAlertRuleV2Criteria -MetricName "Percentage CPU" -TimeAggregation Average -Operator GreaterThan -Threshold 85
Add-AzMetricAlertRuleV2 -Name alert-web01-cpu -ResourceGroupName rg-mon-prod -TargetResourceId $vm.Id `
  -Condition $crit -WindowSize 00:05:00 -Frequency 00:01:00 -Severity 2 -ActionGroupId $ag.Id
```

The CLI reference says `--location` falls back to the resource group's location when omitted, so pass `-l Global` (as the PowerShell example does with `-Location Global`) when you want a Global action group, for example one used by Service Health alerts. A dynamic condition in the CLI: `--condition "avg Percentage CPU > dynamic medium 2 of 4"`. A log search rule uses `az monitor scheduled-query create`; an activity log rule uses `az monitor activity-log alert create --condition category=ServiceHealth and level=Error` (that example comes from the CLI reference).

## Alert processing rules

Alert processing rules act **after** an alert fires. They:

- **Suppress** notifications: remove **all** action groups from matching alerts, for example during a maintenance window. The alerts still fire and are still listed; they just don't notify. Suppression wins if another rule would add action groups.
- **Apply action groups**: add one or more action groups to matching alerts, including alerts that don't come from your alert rules (Azure Backup built-in alerts, for example). This is how you route "every Sev0 and Sev1 alert in the subscription" to the on-call group without editing every rule.

A rule has a **scope** (resources, a resource group or a whole subscription, all in the **same subscription** as the rule), optional **filters** (severity, resource type, resource group, alert rule name or ID, monitor service, monitor condition, description, alert context; filters are ANDed, up to five values per filter ORed), and a **schedule** (always, a one-time window, or daily/weekly/monthly recurrence with a time zone). Changes can take up to **30 minutes** to apply. They don't affect Service Health alerts.

**Portal:** **Monitor** > **Alerts** > **Alert processing rules** > **+ Create** > Scope > Rule settings (Suppress notifications or Apply action group) > Scheduling > Details.

```bash
az monitor alert-processing-rule create -g rg-mon-prod -n apr-sat-maintenance \
  --rule-type RemoveAllActionGroups --scopes "/subscriptions/<subscription-id>/resourceGroups/rg-web-prod" \
  --schedule-recurrence-type Weekly --schedule-recurrence Saturday \
  --schedule-recurrence-start-time "22:00:00" --schedule-recurrence-end-time "23:59:00" \
  --schedule-time-zone "Eastern Standard Time" --description "Saturday patch window"
```

The `alert-processing-rule` commands are an Azure CLI extension (installed automatically on first use, marked Preview in the reference).

| | Action group | Alert processing rule |
|---|---|---|
| Is | A list of receivers and automations | A filter-and-modify rule for fired alerts |
| Attached to | Alert rules (or added by a processing rule) | A scope: resources, resource group, subscription |
| Use for | "Email the DBA team and call a runbook" | "Silence rg-web-prod on Saturdays", "Add ag-oncall to all Sev0 alerts" |
| Stops the alert? | No | No: suppression only removes notifications |

## Try it yourself

Cloud Shell. Cost: cents for a small VM for an hour; metric alert rules are billed per monitored time series, which is small for one VM.

```bash
rg=rg-lab-d5alerts; loc=eastus
az group create -n $rg -l $loc
az vm create -g $rg -n vm-lab-01 --image Ubuntu2204 --size Standard_B1s --admin-username azureuser --generate-ssh-keys --public-ip-address ""
az monitor action-group create -g $rg -n ag-lab --short-name lab --action email me <your-email-address>
vmid=$(az vm show -g $rg -n vm-lab-01 --query id -o tsv); agid=$(az monitor action-group show -g $rg -n ag-lab --query id -o tsv)
az monitor metrics alert create -g $rg -n alert-lab-cpu --scopes $vmid --condition "avg Percentage CPU > 50" --action $agid --severity 3
az vm run-command invoke -g $rg -n vm-lab-01 --command-id RunShellScript --scripts "timeout 900 sh -c 'while :; do :; done' >/dev/null 2>&1 &"
```

Use your own address for the email receiver. Within about ten minutes the alert should fire; open **Monitor** > **Alerts**, set the user response to **Acknowledged**, and watch it change to **Resolved** after the load stops. Then add an alert processing rule that suppresses the resource group and run the load again: the alert appears but no email arrives.

Clean up: `az group delete -n $rg --yes --no-wait`.

## Key takeaways

- Alert rule = scope + condition + action groups + severity (0 Critical to 4 Verbose); alerts are kept 30 days.
- Metric alerts: frequency and lookback window, static or dynamic thresholds, stateful by default, resolve after three clean checks.
- Log search alerts run KQL on a schedule; activity log, Service Health and Resource Health alerts are stateless.
- Action groups hold notifications (email, ARM role email, SMS, push, voice) and actions (runbook, function, event hub, ITSM, logic app, webhooks); short name up to 12 characters; Global region for Service Health.
- Alert processing rules suppress or add action groups on fired alerts by scope, filter and schedule; suppression wins.
