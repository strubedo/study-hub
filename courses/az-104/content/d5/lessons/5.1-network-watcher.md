## Network Watcher, monitoring side

**Azure Network Watcher** is a regional service that is enabled automatically in a region when you create or update a virtual network there (it appears as `NetworkWatcher_<region>` in the `NetworkWatcherRG` resource group, one instance per region per subscription). Domain 4 covered its **diagnostic** tools: IP flow verify, NSG diagnostics, next hop, effective security rules, connection troubleshoot, packet capture and VPN troubleshoot, which answer "why does this fail right now?". This lesson covers the **monitoring** side, which answers "how has it behaved over time?":

| Tool | Question it answers |
|---|---|
| **Connection monitor** | Is A still reaching B, with what packet loss and latency, and where on the path does it break? |
| **Flow logs** (virtual network flow logs) | Which flows passed through this network, allowed or denied, and how many bytes? |
| **Traffic analytics** | Who talks to whom, which ports are open to the internet, which rules block most? |
| **Topology** | How are my VNets, subnets, gateways and resources connected? |

## Connection monitor

Connection monitor runs **continuous, scheduled** tests from sources to destinations and records reachability, **checks failed %** and **round-trip time (RTT)**, plus hop-by-hop topology. The old **Connection monitor (classic)** is deprecated and no longer available; Learn points to migration to the current Connection monitor.

### Building blocks

| Item | What it is |
|---|---|
| **Connection monitor** | A **regional** resource (up to 100 per subscription per region) |
| **Test group** | A set of sources, destinations and test configurations (up to 20 per monitor); can be disabled as a unit |
| **Source endpoint** | Azure VMs, scale sets, subnets or VNets (with a coverage level), or Azure Arc-enabled on-premises machines |
| **Destination endpoint** | Azure VMs or scale sets, Arc-enabled machines, URLs, FQDNs, IP addresses, Microsoft 365 or Dynamics 365 URLs; destinations need no agent |
| **Test configuration** | Protocol **TCP**, **HTTP** or **ICMP**, port, test frequency, and success thresholds for checks failed % and RTT (up to 20 per monitor) |
| **Test** | One source + one destination + one test configuration: the level at which results are stored |

Every combination in a test group becomes a test: **sources x destinations x configurations**. Three sources, two destinations and two configurations make 12 tests.

### Agents

- **Azure VMs and scale sets** need the **Network Watcher Agent** VM extension (`NetworkWatcherAgentWindows` / `NetworkWatcherAgentLinux`). The portal installs it when you create the monitor.
- **On-premises machines** must be **Azure Arc-enabled**, with the **Azure Monitor Agent** installed. Connection monitor no longer supports the Log Analytics agent for on-premises machines.

### Checks and states

- **TCP and ICMP**: checks failed % comes from packet loss; RTT from the time to the ACK. Traceroute data gives per-hop loss and latency.
- **HTTP**: a check fails unless the response code is in the valid list (configurable with the CLI or PowerShell); RTT is the time from request to response.

Test states, as Learn defines them:

| State | When |
|---|---|
| **Pass** | Checks failed % and RTT are both within the thresholds |
| **Warning** | You set a threshold and checks failed % is above **80% of** it; or you set no threshold and the automatic one is crossed: **750 ms** RTT for TCP or ICMP, **10%** checks failed |
| **Fail** | Checks failed % **or** RTT exceeds the threshold; with no threshold, a test fails only when **100%** of checks fail |
| **Indeterminate** | No data in the Log Analytics workspace |
| **Not running** | The test group is disabled |

Data goes to a **Log Analytics workspace** you pick when you create the monitor (tables **NWConnectionMonitorTestResult** and **NWConnectionMonitorPathResult**) and to **Azure Monitor metrics**, where you can create metric alerts on checks failed % and RTT.

### Create a connection monitor

**Portal:** **Network Watcher** > **Connection monitor** > **+ Create** > Basics (name, region, workspace) > **Test groups** (add sources, test configurations, destinations) > **Create alert** (optional metric alert with an action group) > **Review + create**.

**Azure CLI** (one test group, one TCP test configuration):

```bash
vmid=$(az vm show -g rg-web-prod -n vm-web-01 --query id -o tsv)
az network watcher connection-monitor create --name cm-web-to-sql --location eastus \
  --endpoint-source-name vm-web-01 --endpoint-source-resource-id $vmid \
  --endpoint-dest-name sql-01 --endpoint-dest-address 10.20.2.4 \
  --test-config-name tcp1433 --protocol Tcp --tcp-port 1433 --frequency 30 \
  --threshold-failed-percent 5 --threshold-round-trip-time 50 \
  --test-group-name tg-web-sql --workspace-ids <workspace-resource-id>
```

**Azure PowerShell** builds the objects first:

```powershell
$vm   = Get-AzVM -ResourceGroupName rg-web-prod -Name vm-web-01
$src  = New-AzNetworkWatcherConnectionMonitorEndpointObject -AzureVM -Name vm-web-01 -ResourceID $vm.Id
$dst  = New-AzNetworkWatcherConnectionMonitorEndpointObject -ExternalAddress -Name sql-01 -Address 10.20.2.4
$tcp  = New-AzNetworkWatcherConnectionMonitorProtocolConfigurationObject -TcpProtocol -Port 1433
$cfg  = New-AzNetworkWatcherConnectionMonitorTestConfigurationObject -Name tcp1433 -TestFrequencySec 30 `
          -ProtocolConfiguration $tcp -SuccessThresholdChecksFailedPercent 5 -SuccessThresholdRoundTripTimeMs 50
$tg   = New-AzNetworkWatcherConnectionMonitorTestGroupObject -Name tg-web-sql -TestConfiguration $cfg -Source $src -Destination $dst
New-AzNetworkWatcherConnectionMonitor -NetworkWatcherName NetworkWatcher_eastus -ResourceGroupName NetworkWatcherRG `
  -Name cm-web-to-sql -TestGroup $tg
```

> **Exam tip:** "Monitor latency from four VMs to an on-premises server every 30 seconds and alert when it degrades" is Connection monitor. "Check right now whether port 1433 is reachable" is connection troubleshoot (Domain 4).

## Flow logs

Learn's NSG flow logs page states that **network security group (NSG) flow logs retire on September 30, 2027**, and that because the feature is retiring, **new NSG flow logs can no longer be created**. After the retirement date Azure stops supporting traffic analytics on NSG flow logs and deletes the existing NSG flow log resources (records already in storage stay, under their retention policy). The replacement is **virtual network flow logs**.

Virtual network flow logs:

- Can be enabled on a **virtual network**, a **subnet** or a **network interface**. If several levels are configured, the most specific wins: **NIC > subnet > VNet**.
- Record every flow through the network with the NIC, 5-tuple, direction, **flow state** (`B` begin, `C` continuing, `E` end, `D` deny), encryption state and bytes and packets, and identify traffic allowed or denied by NSG rules **and** Azure Virtual Network Manager security admin rules.
- Cover traffic NSG flow logs couldn't, such as VPN and ExpressRoute gateways, Application Gateway and API Management.
- Write JSON blobs to a **storage account** that must be in the **same region** as the VNet and must be a **Standard** account (premium isn't supported). Set retention in days (0 keeps logs until you delete them; retention needs a Standard general-purpose v2 account).
- Are billed per GB collected (Learn lists a free tier of 5 GB a month per subscription), plus storage; traffic analytics has no free tier.

```bash
lawid=$(az monitor log-analytics workspace show -g rg-mon-prod -n log-contoso-prod --query id -o tsv)
az network watcher flow-log create --location eastus --resource-group rg-net-prod --name fl-vnet-hub \
  --vnet vnet-hub --storage-account stcontosoflowlogs \
  --traffic-analytics true --workspace $lawid --interval 10
```

The workspace is in another resource group, so pass its resource ID (a bare name is looked up in `--resource-group`). The CLI reference says `--interval` accepts 10 or 60 and that the workspace must be in the flow log's region.

```powershell
$vnet = Get-AzVirtualNetwork -ResourceGroupName rg-net-prod -Name vnet-hub
$st   = Get-AzStorageAccount -ResourceGroupName rg-net-prod -Name stcontosoflowlogs
$law  = Get-AzOperationalInsightsWorkspace -ResourceGroupName rg-mon-prod -Name log-contoso-prod
New-AzNetworkWatcherFlowLog -Enabled $true -Name fl-vnet-hub -NetworkWatcherName NetworkWatcher_eastus -ResourceGroupName NetworkWatcherRG `
  -StorageId $st.Id -TargetResourceId $vnet.Id -FormatVersion 2 -EnableTrafficAnalytics -TrafficAnalyticsWorkspaceId $law.ResourceId -TrafficAnalyticsInterval 10
```

**Portal:** **Network Watcher** > **Flow logs** > **+ Create** > flow log type **Virtual network** > select the VNet, subnet or NIC > storage account and retention > **Analytics** tab: enable traffic analytics, processing interval and workspace.

## Traffic analytics

**Traffic analytics** reads the flow log blobs, aggregates them, enriches them with topology, geography and threat information, and stores the result in a **Log Analytics workspace** in the **NTANetAnalytics** table (it replaces `AzureNetworkAnalytics_CL`, used for NSG flow logs). The **processing interval** is **60 minutes** by default or **10 minutes** if you choose it. It answers questions such as most-talkative hosts, top application protocols, allowed and blocked flows, **open ports reachable from the internet**, **most-blocking NSG rules**, and traffic to malicious IPs. There's no free tier for traffic analytics processing.

```kusto
NTANetAnalytics
| where TimeGenerated > ago(1d)
| summarize DeniedFlows = sum(DeniedInFlows + DeniedOutFlows) by AclRule
| top 5 by DeniedFlows
```

In `NTANetAnalytics`, **AclRule** is the NSG rule (or Virtual Network Manager security admin rule) that allowed or denied the flow; the table reference describes the `NsgRule` column as a placeholder for NSG flow logging, so don't group virtual network flow log data by it.

## Topology

**Topology** (in **Network Watcher** or **Monitor** > **Insights** > **Networks**) draws VNets, subnets, gateways, peerings and connected resources across **subscriptions, resource groups and regions**, and lets you drill into a resource for its health, metrics and the diagnostic tools. It is drawn from **Azure Resource Graph**, so a change can take up to **30 hours** to appear. Use it to document an estate or to spot a missing peering before you start packet-level troubleshooting.

## Try it yourself

Cloud Shell. Cost: cents for two small VMs for an hour, a few cents of flow log data, and workspace ingestion.

```bash
rg=rg-lab-d5nw; loc=eastus
az group create -n $rg -l $loc
az network vnet create -g $rg -n vnet-lab --address-prefix 10.50.0.0/16 --subnet-name snet-a --subnet-prefix 10.50.1.0/24
az vm create -g $rg -n vm-a --image Ubuntu2204 --size Standard_B1s --vnet-name vnet-lab --subnet snet-a --admin-username azureuser --generate-ssh-keys --public-ip-address ""
az vm create -g $rg -n vm-b --image Ubuntu2204 --size Standard_B1s --vnet-name vnet-lab --subnet snet-a --admin-username azureuser --generate-ssh-keys --public-ip-address ""
az monitor log-analytics workspace create -g $rg -n log-lab-nw -l $loc
az storage account create -g $rg -n stlabfl$RANDOM -l $loc --sku Standard_LRS --kind StorageV2
```

1. In the portal, create a connection monitor in East US with source **vm-a**, destination **vm-b** (Azure VM), a TCP test on port 22 every 30 seconds, and the workspace `log-lab-nw`. Note that the portal adds the Network Watcher Agent extension to vm-a.
2. After 10 minutes the test should be **Pass**. Add a second test configuration on TCP 3389 (nothing listens): watch it go to **Fail**, and count the tests (1 source x 1 destination x 2 configurations = 2).
3. Create a virtual network flow log on `vnet-lab` to the new storage account with traffic analytics (10-minute interval) to `log-lab-nw`. After about an hour, open the storage account container `insights-logs-flowlogflowevent` and the **Traffic analytics** dashboard.
4. Open **Topology** for the resource group.

Clean up: the flow log and connection monitor resources live in `NetworkWatcherRG`, not in the lab resource group, so delete them first (portal: **Network Watcher** > **Flow logs** and **Connection monitor**; or `az network watcher flow-log delete --location eastus --name <flow-log-name>` and `az network watcher connection-monitor delete --location eastus --name <monitor-name>`), then `az group delete -n $rg --yes --no-wait`. Leave the Network Watcher instance itself. Deleting a flow log doesn't delete blobs already written; they go with the storage account.

## Key takeaways

- Connection monitor: regional resource > test groups > sources, destinations, test configurations; tests = sources x destinations x configurations.
- Azure sources need the Network Watcher Agent extension; on-premises sources need Azure Arc plus the Azure Monitor Agent.
- States: Pass, Warning (above 80% of your threshold, or 750 ms / 10% defaults), Fail, Indeterminate, Not running; data in a Log Analytics workspace and in metrics.
- NSG flow logs retire September 30, 2027 and can't be newly created; use virtual network flow logs (VNet, subnet or NIC; NIC > subnet > VNet) to a same-region Standard storage account.
- Traffic analytics processes flow logs every 60 minutes (or 10) into NTANetAnalytics in a workspace.
- Topology comes from Resource Graph and spans subscriptions and regions.
