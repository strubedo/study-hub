## Azure Monitor in one picture

**Azure Monitor** is the platform that collects, stores and acts on monitoring data for Azure, other clouds and on-premises machines. For the exam, sort everything into a few buckets:

| Data | What it is | Collected by default? | Where it lives |
|---|---|---|---|
| **Platform metrics** | Numeric time series from each Azure resource (CPU, transactions, bytes) | **Yes**, no configuration, normally every minute | Azure Monitor Metrics (time-series database) |
| **Activity log** | Control plane events for the subscription (who created, changed, deleted what) | **Yes** | Activity log, kept 90 days |
| **Resource logs** | Data plane logs from inside a resource (Key Vault audit, storage reads, NSG events) | **No**: needs a diagnostic setting | Wherever the diagnostic setting sends them |
| **Guest OS data** | Performance counters, Windows events, Syslog from inside a VM | **No**: needs the **Azure Monitor Agent** and a data collection rule | Log Analytics workspace or Azure Monitor workspace |

Metrics are cheap, fast and near real time, so they suit charts and quick alerts. Logs are richer records you query with KQL, so they suit investigation and correlation. Alerts, Insights, workbooks and dashboards are built on top of both. This lesson covers metrics; the next three cover logs, queries and alerts.

## What a metric is made of

Each metric value has:

- A **timestamp** and a **value**.
- A **resource** it belongs to.
- A **namespace**, which works like a category. Platform metrics for a VM sit in `Microsoft.Compute/virtualMachines`; guest metrics sent by an agent or custom metrics sit in their own namespaces. In metrics explorer you pick the namespace before the metric.
- Optional **dimensions**: name/value pairs that split one metric into series. Storage `Transactions` has dimensions such as `ResponseType` and `ApiName`; a load balancer's metrics can be split by frontend IP or backend port. Dimension names and values are case-insensitive.

Azure collects platform metrics at a **one-minute** frequency unless a metric's definition says otherwise. Some resource providers sample faster internally (VM CPU is captured every 15 seconds and rolled up), some slower (some SQL storage metrics every 20 minutes). The smallest **time granularity** you can chart is **one minute**.

## The five aggregations

When metrics explorer draws a chart it groups the raw values into buckets of the chosen **time granularity** (also called **time grain**) and reduces each bucket to one number with an **aggregation**:

| Aggregation | Result per bucket | Typical use |
|---|---|---|
| **Sum** (shown as Total in some APIs) | Sum of all values | Bytes sent, number of requests |
| **Count** | Number of measurements, ignoring their values | How many samples arrived |
| **Average** | Sum / Count for most metrics | CPU percentage, latency |
| **Min** | Smallest value | Lowest available memory |
| **Max** | Largest value | Worst latency, CPU spikes |

Metrics explorer hides aggregations that make no sense for a metric. Missing data is recorded as **NULL**, not zero, and NULLs aren't counted, so an Average uses fewer points when data is missing.

Worked example: a VM reports `Percentage CPU` once a minute. Over a 5-minute bucket the values are 20, 40, 90, 30, 20.

| Aggregation | Value for that bucket |
|---|---|
| Sum | 200 |
| Count | 5 |
| Average | 40 |
| Min | 20 |
| Max | 90 |

Granularity changes what you see: over a 24-hour range, a 30-minute granularity gives 48 points, 15 minutes gives 96, 5 minutes gives 288 and 1 minute gives 1,440. Larger buckets smooth out spikes; that is why an alert that evaluates CPU averaged over 5 minutes fires less often than one on 1-minute data.

> **Exam tip:** "The chart shows Max 90 but Average 40 for the same interval" is not a bug: Max reports the single highest sample in the bucket, Average the mean. A short spike shows on Max and disappears in Average.

## Retention

Microsoft Learn states that **platform and custom metrics are stored for 93 days**. In the portal you can chart at most **30 days on a single chart**, then pan across the 93-day window. Exceptions worth knowing:

- Guest OS metrics collected by the Azure Monitor Agent into Azure Monitor Metrics: 93 days.
- Classic guest metrics written to a storage account by the Windows or Linux diagnostic extension: at least 14 days.
- Log-based metrics follow the retention of the underlying logs.

To keep metrics longer, send them to a Log Analytics workspace with a diagnostic setting (they land in the `AzureMetrics` table) and set that table's retention.

## Guest OS metrics need an agent

Host metrics for a VM (CPU, disk and network throughput and operations, VM availability) come from the Azure host with no agent. Anything that needs to look **inside** the operating system does not: memory used per process, logical disk free space, Windows performance counters, Linux `/proc` data. For those, install the **Azure Monitor Agent** and associate a **data collection rule** that lists the counters and the destination. (The old Log Analytics agent was retired on August 31, 2024; Learn says not to deploy it.) VM insights, covered later in this domain, sets this up for you.

## Metrics explorer

**Portal:** **Monitor** > **Metrics**, or **Metrics** on any resource's menu.

1. **Scope**: one resource, or several resources of a compatible type in the **same subscription and region**. Querying across resources needs at least **Monitoring Reader** at the subscription.
2. **Metric namespace**, **Metric**, **Aggregation**.
3. **Time range** and **time granularity** (Automatic picks a grain from the range).
4. **Add filter**: keep only some dimension values, for example `ResponseType = ServerOtherError`.
5. **Apply splitting**: draw one line per dimension value, for example one line per `ApiName`, with a limit on how many series to show.
6. **Pin to dashboard**, **Save to workbook**, **New alert rule**, or **Share** (download to Excel or copy a link).

Filtering answers "how much of the total is from this segment?". Splitting answers "which segment is responsible?". Both need a metric that has dimensions.

> **Watch out:** Splitting is not available for metrics without dimensions, and multi-resource charts work only for resource types listed as compatible in the scope picker.

## Read metrics from the command line

**Azure CLI** (`--interval` is the time grain in `##h##m` form, default `1m`):

```bash
vmid=$(az vm show -g rg-web-prod -n vm-web-01 --query id -o tsv)
az monitor metrics list-definitions --resource $vmid --query "[].name.value" -o tsv
az monitor metrics list --resource $vmid --metrics "Percentage CPU" \
  --aggregation Average Maximum --interval 5m --offset 1h -o table
```

**Azure PowerShell:**

```powershell
$vm = Get-AzVM -ResourceGroupName rg-web-prod -Name vm-web-01
Get-AzMetricDefinition -ResourceId $vm.Id | Select-Object -ExpandProperty Name
Get-AzMetric -ResourceId $vm.Id -MetricName "Percentage CPU" -TimeGrain 00:05:00 `
  -AggregationType Maximum -StartTime (Get-Date).AddHours(-1)
```

Storage metrics with a dimension filter (the `--filter` syntax is OData, as in the REST API):

```bash
said=$(az storage account show -g rg-data-prod -n stcontosodata01 --query id -o tsv)
az monitor metrics list --resource $said --metrics Transactions --aggregation Total \
  --interval 1h --filter "ResponseType eq '*'" -o table
```

## Try it yourself

Azure Cloud Shell (Bash) in any browser. Cost: a few cents for a small Linux VM running for under an hour; delete it at the end.

```bash
rg=rg-lab-d5metrics; loc=eastus
az group create -n $rg -l $loc
az vm create -g $rg -n vm-lab-01 --image Ubuntu2204 --size Standard_B1s \
  --admin-username azureuser --generate-ssh-keys --public-ip-address ""
# Make some CPU load for ten minutes without logging in
az vm run-command invoke -g $rg -n vm-lab-01 --command-id RunShellScript \
  --scripts "timeout 600 sh -c 'while :; do :; done' >/dev/null 2>&1 &"
```

Wait about ten minutes, then:

1. In the portal, open **vm-lab-01** > **Metrics**. Choose **Percentage CPU** with **Avg**, then add the same metric with **Max**. Set the range to the last hour and the granularity to 1 minute, then 15 minutes, and watch the spike flatten.
2. Add **Network In Total** with **Sum**, then try **Count** and note it counts samples, not bytes.
3. Run the CLI `az monitor metrics list` command above with `--interval 1m` and compare one bucket's Average and Maximum with the chart.

Clean up: `az group delete -n $rg --yes --no-wait`.

## Key takeaways

- Platform metrics and the activity log are collected automatically; resource logs need a diagnostic setting; guest OS data needs the Azure Monitor Agent and a DCR.
- A metric has a namespace, optional dimensions, and is collected every minute by default; the smallest chart grain is one minute.
- Aggregations: Sum, Count (number of samples), Average, Min, Max; NULL is not zero.
- Platform metrics are kept 93 days; one chart shows at most 30 days; send them to a workspace (`AzureMetrics`) to keep them longer.
- Filtering keeps some dimension values; splitting draws one series per value.
- `az monitor metrics list --metrics --aggregation --interval`, `Get-AzMetric -MetricName -TimeGrain -AggregationType`.
