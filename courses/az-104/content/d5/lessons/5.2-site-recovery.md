## Backup vs disaster recovery

| | **Azure Backup** | **Azure Site Recovery** |
|---|---|---|
| Purpose | Keep **copies** of data for days to years | Keep a **running replica** in another region so the workload can **fail over** |
| Recovery point frequency | Hours to a day (VMs: daily, or every 4 hours with Enhanced) | Crash-consistent points every **5 minutes**, app-consistent every 1 hour or more |
| Retention | Days to 99 years | Up to **15 days** of recovery points (managed disks) |
| Restores | Files, disks, VMs, shares, databases, often to the same region | The whole VM (or a recovery plan) started in the target region |
| Typical question | "Recover a file deleted three weeks ago" | "Bring the app up in West US within an hour if East US fails" |

They complement each other: Site Recovery replicates corruption and deletions within minutes, so you still need backups.

Two metrics frame every DR design:

- **RPO** (recovery point objective): how much data you can afford to lose, measured in time. With Site Recovery, failing over to **Latest** loses almost nothing that reached the service; **Latest processed** may lose a few minutes.
- **RTO** (recovery time objective): how long until the service is back. Site Recovery's SLA, per Learn's FAQ, is an RTO of **one hour** for the failover itself; your app's start-up and DNS changes add to that.

## Azure-to-Azure architecture

When you enable replication for an Azure VM from a **source region** to a **target region**:

| Component | Where | Notes |
|---|---|---|
| **Recovery Services vault** | **Any region except the source**; normally the **target** region | Holds the replication settings, policies and recovery plans |
| **Mobility service extension** | Installed **automatically** on the source VM | Captures disk writes and sends them to the cache |
| **Cache storage account** | **Source** region | Writes are staged here before going to the target, so production isn't slowed |
| **Replica managed disks** | Target region | Named with an `-ASRReplica` suffix |
| **Target resource group** | Target region | Created with an `-asr` suffix unless you pick one |
| **Target virtual network and subnet** | Target region | Created with an `-asr` suffix unless you pick one; a **network mapping** links source and target VNets |
| Target availability set / zone, size | Target region | Site Recovery picks the same or closest size; can be changed while replicating |

Nothing runs in the target region until you fail over: you pay for Site Recovery per protected instance, the replica disks and the cache storage, not for target VMs.

The source VMs need **outbound** HTTPS (443) to Site Recovery, Azure Storage (the cache account), Microsoft Entra ID and Service Bus; with NSGs, allow the **AzureSiteRecovery**, **Storage**, **AzureActiveDirectory** and **EventHub** service tags (plus **GuestAndHybridManagement** if the Mobility agent should auto-upgrade). Learn notes that Site Recovery doesn't support an authentication proxy.

Permissions: creating the vault needs Owner or Contributor on the subscription; managing replication needs the **Site Recovery Contributor** role; creating the target VMs needs **Virtual Machine Contributor** (or equivalent) in the target.

## Replication policy

Each replicated VM uses a **replication policy**. When you enable replication without choosing one, Site Recovery creates a policy with these defaults (from Learn's architecture page):

| Setting | Meaning | Default |
|---|---|---|
| **Recovery point retention** | How far back you can fail over | **1 day** (portal shows hours; up to **15 days** for managed disks) |
| **App-consistent snapshot frequency** | How often an app-consistent point is taken (VSS on Windows, scripts on Linux) | **0 hours (disabled)**; minimum 1 hour when enabled |

**Crash-consistent** recovery points are created every **five minutes** regardless. Longer retention keeps more points and costs more storage; beyond the last two hours, points are thinned (one per hour for a 1-day retention, one every two hours for 2 to 7 days, and so on).

**Multi-VM consistency** puts VMs in a **replication group** so they share crash- and app-consistent points (for example the tiers of one application). It affects performance and needs specific ports open between the VMs, so use it only when an app requires it.

## Enable replication

**Portal (from the VM):** **VM** > **Backup + disaster recovery** > **Disaster recovery** > **Target region** > **Advanced settings** (subscription, VM resource group, VNet, availability, cache storage, replication policy, extension auto-update) > **Review + start replication**.

**Portal (from the vault):** **Recovery Services vault** in the target region > **Site Recovery** > **Enable replication** > Source (region, subscription, resource group) > Virtual machines > Replication settings > Manage (replication policy, multi-VM consistency) > **Enable replication**.

Watch the **Enable replication** job and then the **Replicated items** list until the status is **Protected** (initial replication can take a while for large disks).

**Azure PowerShell** is the scripted path; the flow from Learn's Azure-to-Azure PowerShell article is:

```powershell
$v = Get-AzRecoveryServicesVault -ResourceGroupName rg-dr-wus -Name rsv-contoso-wus
Set-AzRecoveryServicesAsrVaultContext -Vault $v
# Fabrics represent regions; containers live in fabrics
$primary = New-AzRecoveryServicesAsrFabric -Azure -Location eastus -Name asr-eus     # returns a job; then Get-AzRecoveryServicesAsrFabric
$recovery = New-AzRecoveryServicesAsrFabric -Azure -Location westus -Name asr-wus
# ... New-AzRecoveryServicesAsrProtectionContainer for each fabric ...
New-AzRecoveryServicesAsrPolicy -AzureToAzure -Name pol-a2a -RecoveryPointRetentionInHours 24 -ApplicationConsistentSnapshotFrequencyInHours 4
# ... New-AzRecoveryServicesAsrProtectionContainerMapping (primary to recovery, and back) ...
# ... New-AzRecoveryServicesAsrNetworkMapping, New-AzRecoveryServicesAsrAzureToAzureDiskReplicationConfig ...
# ... New-AzRecoveryServicesAsrReplicationProtectedItem -AzureToAzure -AzureVmId $vm.Id ...
```

The Azure CLI has an `az site-recovery` command group in an extension (installed on first use); the portal and PowerShell are what Learn's tutorials use.

## Recovery plans

A **recovery plan** groups replicated machines so they fail over as one application, in order:

- Up to **100** protected instances per plan.
- Machines are placed in **groups** (Group 1, Group 2, ...). Machines in one group fail over **in parallel**; groups run **in order**, so Group 2 starts only after Group 1's machines have failed over and started. Put databases in Group 1, middle tiers in Group 2, web front ends in Group 3.
- Add **scripts** (Azure Automation runbooks, for example to attach a public IP, an NSG or a load balancer, or to update DNS) and **manual actions** (a pause with instructions, like "confirm the DBA has checked the database") before or after a group.
- Run test failovers, failovers and failbacks on the whole plan.

**Portal:** vault > **Site Recovery** > **Recovery Plans** > **+ Recovery plan** > name, source, target > select items > **Create**; then **Customize** to add groups, scripts and manual actions.

> **Exam tip:** "Ensure the SQL VM is running before the web VMs start after failover, with the least effort" is a recovery plan with two groups. A script would be extra work; separate failovers wouldn't be ordered.

## Try it yourself

Cloud Shell plus the portal. Cost: a small VM, the Site Recovery per-instance charge, and cache and replica disk storage for an hour or two: a few dollars at most; check the Site Recovery pricing page if you keep it longer.

```bash
rg=rg-lab-d5asr; loc=eastus
az group create -n $rg -l $loc
az vm create -g $rg -n vm-lab-01 --image Ubuntu2204 --size Standard_B1s --admin-username azureuser --generate-ssh-keys --public-ip-address ""
az group create -n rg-lab-d5asr-wus -l westus
az backup vault create -g rg-lab-d5asr-wus -n rsv-lab-asr-wus -l westus
```

1. Open **vm-lab-01** > **Disaster recovery**, choose **West US** as the target and the vault `rsv-lab-asr-wus`, keep the defaults, and start replication.
2. While it replicates, list what was created: the cache storage account in East US, the `-asr` resource group and VNet in West US, and the `-ASRReplica` disks. Open the vault > **Site Recovery** > **Replication policies** and note retention and app-consistent frequency.
3. Create a recovery plan containing the VM. Keep the environment for the failover lesson's lab, or clean up now.

Clean up: in the vault, **Replicated items** > the VM > **Disable Replication**, wait for the job to finish, then:

```bash
az group delete -n $rg --yes --no-wait
az group delete -n rg-lab-d5asr-wus --yes --no-wait
```

Also delete any `-asr` resource group Site Recovery created in West US, and check East US for the cache storage account Site Recovery created (it's in the source region; delete it if it wasn't in `rg-lab-d5asr`). Nothing in this vault was backed up, so it holds no soft-deleted backup items; Learn's deletion prerequisites for it are disabling replication and cleaning up Site Recovery dependencies. If the vault delete is refused, open the vault's **Replicated items** and **Site Recovery infrastructure** to see what's left.

## Key takeaways

- Site Recovery replicates running VMs to another region; Backup keeps copies. Use both.
- The vault goes in any region except the source (usually the target); the Mobility service extension is installed automatically; the cache storage account is in the source region.
- Site Recovery creates `-asr` resource groups and VNets and `-ASRReplica` disks in the target.
- Replication policy defaults: 1-day retention, app-consistent snapshots off; crash-consistent points every 5 minutes; up to 15 days.
- Recovery plans: up to 100 instances, groups fail over in order, scripts and manual actions between groups.
