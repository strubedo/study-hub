## Enable backup for an Azure VM

**Portal**, two ways:

- From the VM: **VM** > **Operations** > **Backup** > pick or create a Recovery Services vault (same region) and a policy > **Enable backup**.
- From the vault or **Resiliency**: **+ Backup** > datasource **Azure virtual machines** > policy > **Add** VMs > **Enable backup**.

**Azure CLI:**

```bash
az backup protection enable-for-vm -g rg-bcdr-eus --vault-name rsv-contoso-eus \
  --vm $(az vm show -g rg-web-prod -n vm-web-01 --query id -o tsv) --policy-name pol-vm-prod
```

If the VM is in a different resource group from the vault, pass its resource ID (as above) rather than its name.

**Azure PowerShell:**

```powershell
$v   = Get-AzRecoveryServicesVault -ResourceGroupName rg-bcdr-eus -Name rsv-contoso-eus
$pol = Get-AzRecoveryServicesBackupProtectionPolicy -Name pol-vm-prod -VaultId $v.ID
Enable-AzRecoveryServicesBackupProtection -Policy $pol -Name vm-web-01 -ResourceGroupName rg-web-prod -VaultId $v.ID
```

You can include or exclude data disks by LUN (`--diskslist` with `--disk-list-setting`, or `-InclusionDisksList` / `-ExclusionDisksList`).

### What happens on the first backup

For agent-based (application- or file-system-consistent) backups, the VM needs the **Azure VM agent**, and on the first backup Azure Backup installs a **backup extension** if the VM is running: **VMSnapshot** on Windows, **VMSnapshotLinux** on Linux. The VM needs outbound access to Azure Backup and Azure Storage. On Windows the extension coordinates with **Volume Shadow Copy Service (VSS)**; on Linux you can add pre- and post-scripts.

### Consistency levels

| Consistency | How it's taken | After a restore |
|---|---|---|
| **Application-consistent** | Windows: all VSS writers succeed. Linux: your pre/post scripts ran and succeeded | VM boots, apps start in a consistent state; no data loss |
| **File-system consistent** | Windows: some VSS writers failed. Linux: the default when no pre/post scripts are configured (or they failed) | VM boots with no corruption; apps must fix up their own data |
| **Crash-consistent** | VM shut down during backup, the extension or agent is unavailable or failed, or you opted into agentless multi-disk crash-consistent backup | Like a power cut: disk check at boot; in-memory data lost |

> **Exam tip:** A Linux VM with no pre/post scripts gets **file-system consistent** recovery points, not application-consistent. A VM that was **deallocated** at backup time gets **crash-consistent** points.

### On-demand backup and jobs

**Backup now** takes an extra recovery point outside the schedule, with its own expiry ("retain until"). It is the usual way to get a first full point immediately after enabling protection.

```bash
az backup protection backup-now -g rg-bcdr-eus --vault-name rsv-contoso-eus \
  --container-name vm-web-01 --item-name vm-web-01 --backup-management-type AzureIaasVM --retain-until 23-12-2026
az backup job list -g rg-bcdr-eus --vault-name rsv-contoso-eus -o table
```

`--retain-until` uses the **dd-mm-yyyy** format in UTC; for VMs it defaults to 30 days if omitted.

```powershell
$c = Get-AzRecoveryServicesBackupContainer -ContainerType AzureVM -FriendlyName vm-web-01 -VaultId $v.ID
$i = Get-AzRecoveryServicesBackupItem -Container $c -WorkloadType AzureVM -VaultId $v.ID
Backup-AzRecoveryServicesBackupItem -Item $i -VaultId $v.ID -ExpiryDateTimeUTC (Get-Date).ToUniversalTime().AddDays(30)
Get-AzRecoveryServicesBackupJob -VaultId $v.ID -Status InProgress
```

## Restore options for a VM

**Portal:** vault > **Backup items** > **Azure Virtual Machine** > the VM > **Restore VM** > choose a **restore point** (the list shows its consistency and tier: snapshot, vault, or both) > **Restore configuration**:

| Option | What it does | Requirements |
|---|---|---|
| **Create new** > **Create virtual machine** | Builds a new VM from the point with a name, resource group, VNet and subnet you choose | Same region as the source (or the secondary region with CRR); a staging storage account |
| **Create new** > **Restore disk** | Restores managed disks to a resource group and writes a VM configuration and **ARM template** to the staging storage account, so you can customise and deploy the VM yourself or attach the disks | Target resource group, staging storage account |
| **Replace existing** | Replaces the disks of the **existing** VM; Azure Backup first takes a snapshot of the current disks and keeps it per the policy | The VM must still exist; same subscription |
| **Cross Region Restore** | Restores a VM or disks in the **paired secondary region** from a vault-tier point | GRS vault with CRR enabled; staging storage account in the secondary region |
| **Cross Subscription / Cross Zonal Restore** | Restore to another subscription in the same tenant, or to another availability zone | Supported points and RBAC as Learn lists |

Use **Restore disk** when you need something the simple **Create virtual machine** path can't do: a different size, availability set, custom networking, or to attach a disk to another VM.

```bash
rp=$(az backup recoverypoint list -g rg-bcdr-eus --vault-name rsv-contoso-eus --backup-management-type AzureIaasVM \
     --container-name vm-web-01 --item-name vm-web-01 --query "[0].name" -o tsv)
az backup restore restore-disks -g rg-bcdr-eus --vault-name rsv-contoso-eus \
  --container-name vm-web-01 --item-name vm-web-01 --rp-name $rp \
  --storage-account stcontosorestore --target-resource-group rg-restore-eus
```

Add `--use-secondary-region` (with a staging account in the secondary region) for Cross Region Restore. In PowerShell: `Get-AzRecoveryServicesBackupRecoveryPoint`, then `Restore-AzRecoveryServicesBackupItem -RecoveryPoint $rp -StorageAccountName ... -StorageAccountResourceGroupName ... -TargetResourceGroupName ... -VaultId $v.ID`.

### File-level recovery

To get a few files back without restoring a VM: **Backup items** > the VM > **File Recovery** > pick a recovery point > **Download Executable** (Windows) or **Download Script** (Linux, a Python script) and copy the **password** shown. Run it on a machine with a compatible OS (the source VM or another one): it connects to the recovery point over **iSCSI** (outbound TCP **3260**, plus 443 to Azure) and mounts its volumes as local drives, **read-only**. Copy what you need, then **Unmount Disks** in the portal. The connection is valid for **12 hours**. Don't run it on the same VM when it has Windows Storage Spaces or very large or many disks.

## Azure Files restore

**Portal:** vault > **Backup items** > **Azure Storage (Azure Files)** > the share:

- **Restore Share**: the **full share**, to the **original location** or an **alternate location** (another share, even in another storage account), choosing **Overwrite** or **Skip** on conflicts.
- **File Recovery**: individual files or folders (item-level), to original or alternate location; Learn's limit is 99 items per restore from the snapshot tier.

Recovery points from the snapshot tier are share snapshots in the storage account, so restores are quick. Vaulted points support **full share** recovery (to an alternate location when the snapshot is gone).

## Stop protection

| Option | Recovery points | Billing |
|---|---|---|
| **Stop backup** > **Retain backup data** | Kept indefinitely (or per policy with "retain as per policy"); no new backups | Storage is still billed (and protected instance fees per Learn's pricing rules) |
| **Stop backup** > **Delete backup data** | Moved to **soft-deleted** state for the soft-delete period (14 days by default), then permanently deleted | Free for the first 14 days of soft delete |

While an item is soft-deleted you can **Undelete** it, which returns it to "stop protection with retain data"; from there you can restore or **Resume backup**. You can't re-protect a soft-deleted item in the **same** vault until you undelete it.

```bash
az backup protection disable -g rg-bcdr-eus --vault-name rsv-contoso-eus --container-name vm-web-01 \
  --item-name vm-web-01 --backup-management-type AzureIaasVM --delete-backup-data true --yes
```

```powershell
Disable-AzRecoveryServicesBackupProtection -Item $i -VaultId $v.ID -RemoveRecoveryPoints -Force
```

## Outside Azure: MARS, MABS and DPM

| Tool | Protects | Destination | Max frequency to Azure |
|---|---|---|---|
| **MARS agent** (Microsoft Azure Recovery Services agent) | **Windows** files, folders, volumes and system state, on-premises or in an Azure VM | Recovery Services vault directly; data encrypted with a passphrase you keep | **Three** backups a day |
| **MABS** (Microsoft Azure Backup Server) | App-aware: Hyper-V and VMware VMs, SQL Server, Exchange, SharePoint, file servers, Windows clients | Local disk for short-term, then a Recovery Services vault | **Two** a day |
| **System Center DPM** | As MABS, for System Center customers | Local disk, then a Recovery Services vault | Two a day |

MARS doesn't back up Linux; protect Linux file data with MABS or by backing up the whole VM. All three register with a vault using **vault credentials** downloaded from the vault.

## Try it yourself

Cloud Shell. Cost: a small VM for about an hour and backup storage for a few GB. **Read the clean-up first**: soft delete keeps the backup data for 14 days.

```bash
rg=rg-lab-d5backup; loc=eastus
az group create -n $rg -l $loc
az vm create -g $rg -n vm-lab-01 --image Ubuntu2204 --size Standard_B1s --admin-username azureuser --generate-ssh-keys --public-ip-address ""
az backup vault create -g $rg -n rsv-lab-bk -l $loc
az backup vault backup-properties set -g $rg -n rsv-lab-bk --backup-storage-redundancy LocallyRedundant
az backup protection enable-for-vm -g $rg --vault-name rsv-lab-bk --vm vm-lab-01 --policy-name DefaultPolicy
az backup protection backup-now -g $rg --vault-name rsv-lab-bk --container-name vm-lab-01 --item-name vm-lab-01 --backup-management-type AzureIaasVM
az backup job list -g $rg --vault-name rsv-lab-bk -o table
```

1. Watch the job until the **Take Snapshot** phase completes; open **Backup items** and note the consistency of the recovery point (file-system consistent for this Linux VM without scripts) and the VMSnapshotLinux extension on the VM.
2. Open **File Recovery**, download the script, and read its instructions (running it is optional).
3. Clean up in this order:

```bash
az backup protection disable -g $rg --vault-name rsv-lab-bk --container-name vm-lab-01 --item-name vm-lab-01 \
  --backup-management-type AzureIaasVM --delete-backup-data true --yes
az vm delete -g $rg -n vm-lab-01 --yes
az group delete -n $rg --yes --no-wait
```

**Expect the last command to fail on the vault.** Soft delete is enforced on Recovery Services vaults, so the backup item stays soft-deleted for 14 days, and Learn's delete-vault page says a vault holding soft-deleted items can't be deleted (the error names the soft-deleted items). The other resources in the group are usually removed, but the vault and the resource group stay. What to do:

- **Wait it out (always works):** the soft-deleted data costs nothing for its 14 days. After that, run `az backup vault delete -g $rg -n rsv-lab-bk --yes` and then `az group delete -n $rg --yes`. The vault isn't deleted for you when the period ends.
- **Or delete the vault from the portal:** Learn's secure-by-default page says a portal delete moves a vault with soft-deleted items into a **soft-deleted vault** state (preview). Learn doesn't say whether the resource group can then be deleted straight away, so if `az group delete` still fails, use the first option.

There's no supported way to skip the 14 days on an enforced vault; don't try to disable soft delete. Afterwards, check **Resource groups** for a leftover `AzureBackupRG_<region>_1` group that holds restore point collections (instant restore snapshots), and delete it once it's empty.

## Key takeaways

- Enable VM backup from the VM or the vault; the first backup installs VMSnapshot (Windows) or VMSnapshotLinux.
- App-consistent needs VSS (Windows) or successful pre/post scripts (Linux); otherwise file-system consistent; crash-consistent when the VM is off or the extension fails.
- Restore: Create new VM, Restore disks (plus ARM template), Replace existing (VM must exist), Cross Region Restore (GRS + CRR), file recovery by mounting the point over iSCSI for 12 hours.
- Azure Files: full share or item-level restore to original or alternate location, overwrite or skip.
- Stop backup with retain data keeps points; with delete data they are soft-deleted for 14 days first.
- MARS: Windows files, folders, system state, three times a day; MABS and DPM: app-aware, twice a day to Azure.
