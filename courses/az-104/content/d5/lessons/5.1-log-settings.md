## Three kinds of log data

| Log | Scope | Collected by default? | Default retention |
|---|---|---|---|
| **Activity log** | Subscription (and management group) control plane events | Yes | **90 days**, no charge |
| **Resource logs** | Operations inside a resource (data plane) | **No** | Only what you configure at the destination |
| **Guest OS logs** | Windows event logs, Syslog, IIS and text logs inside VMs | No | Workspace table retention |

The objective "configure log settings" covers all three: diagnostic settings for the activity log and resource logs, the workspace and its tables, and agents with data collection rules for guest logs.

## The activity log

The activity log records **control plane** operations sent through Azure Resource Manager: creating a VM, changing an NSG rule, assigning a role, failed deployments. Each event belongs to a **category**:

| Category | Records |
|---|---|
| **Administrative** | Create, update, delete and action operations, including role assignment changes |
| **Service Health** | Azure service incidents, maintenance, security and information notices that affect your resources |
| **Resource Health** | Health changes of your resources: Available, Unavailable, Degraded, Unknown |
| **Alert** | Activations of Azure alerts |
| **Autoscale** | Autoscale engine operations |
| **Security** | Alerts raised by Microsoft Defender for Cloud |
| **Recommendation** | Azure Advisor recommendations |
| **Policy** | Azure Policy effect actions (such as deny and audit) |

Azure keeps activity log events for **90 days** at no charge. It doesn't record data plane actions (reading a blob, signing in to a VM) and it doesn't record requests rejected before the operation started. To keep events longer, query them with KQL or stream them, create a **diagnostic setting on the subscription** (portal: **Monitor** > **Activity log** > **Export Activity Logs**; CLI: `az monitor diagnostic-settings subscription create`). In a workspace the events land in the **AzureActivity** table. Learn notes the activity log is the only place that records **who created** a resource, which is a common reason to export it.

## Diagnostic settings

A **diagnostic setting** is attached to one resource (or to a subscription for the activity log) and says **which categories** to collect and **where** to send them.

Destinations:

| Destination | Use it for | Constraints |
|---|---|---|
| **Log Analytics workspace** | KQL queries, log alerts, workbooks, Insights | Any region; choose collection mode (below) |
| **Storage account** | Cheap archive, audit, immutable storage | **Same region** as a regional resource; Standard accounts only (no premium); if the account has a firewall, allow trusted Microsoft services |
| **Event hub** | Stream to a SIEM or third-party tool | **Same region** as a regional resource; not a compacted event hub |
| **Azure Monitor partner solution** | Partner observability platforms (Azure Native ISV Services) | Partner resource must exist |

Rules Learn states:

- The destination must **already exist**.
- A setting can have **one of each** destination type; to send to two workspaces, create two settings.
- Each resource can have up to **five** diagnostic settings.
- The destination can be in another subscription if you have rights to both.
- The portal won't let a storage account or Event Hubs namespace be its own destination (it would loop); Learn notes the block is only in the portal, and the CLI, PowerShell or a template can still do it at your own risk.
- Data starts flowing within about **90 minutes**; the workspace table is created when the first records arrive.

**Resource logs are not collected until a diagnostic setting exists.** No setting, no Key Vault audit log, no storage read log, no NSG event history: this is the classic exam trap. Platform metrics and the activity log are always collected; the diagnostic setting only routes them elsewhere.

### Categories, category groups and collection mode

In a setting you either tick individual **categories** (they differ per resource type, such as `AuditEvent` for Key Vault or `StorageRead` for blob services) or choose a **category group**: `allLogs` (everything, including categories Microsoft adds later) or `audit` (logs that record interactions with data or settings). You can't mix a group with individual categories. `AllMetrics` sends platform metrics to the destination too.

When the destination is a Log Analytics workspace, the service may offer two **collection modes**:

- **Azure diagnostics**: all resources write to one shared table, **AzureDiagnostics**, with many sparse columns.
- **Resource-specific**: each category gets its own table (for example `StorageBlobLogs`, `AzureFirewallNetworkRule`, or the Azure Backup tables such as `AddonAzureBackupJobs`). Learn recommends resource-specific mode where it is offered: tables are easier to query and can have their own retention and plan.

### Create a diagnostic setting

**Portal:** resource > **Monitoring** > **Diagnostic settings** > **+ Add diagnostic setting** > name > pick categories or a category group > pick destinations > **Save**.

**Azure CLI:**

```bash
kvid=$(az keyvault show -n kv-contoso-prod --query id -o tsv)
lawid=$(az monitor log-analytics workspace show -g rg-mon-prod -n log-contoso-prod --query id -o tsv)
az monitor diagnostic-settings create --name kv-to-law --resource $kvid --workspace $lawid \
  --logs '[{"categoryGroup":"allLogs","enabled":true}]' \
  --metrics '[{"category":"AllMetrics","enabled":true}]'
```

Add `--storage-account <id>` or `--event-hub-rule <rule-id>` for other destinations and `--export-to-resource-specific true` for resource-specific mode where the service supports it.

**Azure PowerShell:**

```powershell
$kv  = Get-AzKeyVault -ResourceGroupName rg-sec-prod -VaultName kv-contoso-prod
$law = Get-AzOperationalInsightsWorkspace -ResourceGroupName rg-mon-prod -Name log-contoso-prod
$log    = New-AzDiagnosticSettingLogSettingsObject -Enabled $true -CategoryGroup allLogs
$metric = New-AzDiagnosticSettingMetricSettingsObject -Enabled $true -Category AllMetrics
New-AzDiagnosticSetting -Name kv-to-law -ResourceId $kv.ResourceId -WorkspaceId $law.ResourceId -Log $log -Metric $metric
```

`New-AzDiagnosticSetting` can't create the subscription-level activity log setting; Learn says to deploy an ARM template for that from PowerShell.

## The Log Analytics workspace

A **Log Analytics workspace** is a regional store of **tables**. Learn's design guidance: **start with a single workspace** and add more only for a clear reason, such as separate Microsoft Entra tenants, data residency in a region, separate billing, or resilience across regions. Access is controlled two ways:

- **Access mode**: *workspace-context* (you query everything you have rights to in the workspace) or *resource-context* (you open **Logs** from a VM or resource group and see only records for those resources).
- **Access control mode** on the workspace: **Use resource or workspace permissions** lets a user who has read access to a VM read that VM's logs without workspace rights; **Require workspace permissions** doesn't. Table-level RBAC can narrow access further.

### Table plans

Each table has a **plan**:

| Plan | For | Queries | Alerts | Retention |
|---|---|---|---|---|
| **Analytics** (default for Azure tables) | Continuous monitoring, alerts, Insights | Full KQL, price included | Yes | Analytics retention 30 days by default (90 for Microsoft Sentinel and Application Insights data), up to **2 years**; total up to **12 years** |
| **Basic** | Troubleshooting, incident response | Full KQL, billed per query | Simple log alerts only | 30 days of queries, then long-term; total up to 12 years |
| **Auxiliary / Lake** | Verbose, rarely used, audit data | Full KQL, slower, billed per query | No | Queryable for the whole total retention, up to 12 years |

Azure tables default to Analytics; support for Basic and Auxiliary varies by table (AzureActivity, for example, supports neither). You can switch a table's plan **once a week**.

### Retention

Learn now describes two states: **analytics retention** (interactive) and **long-term retention** (low cost; Analytics and Basic data is retrieved with a **search job**). **Total retention** = analytics + long-term.

- The workspace default analytics retention applies to every Analytics table that hasn't been given its own. It is 30 days unless you change it; 31 days are included in the ingestion price, so going lower saves nothing.
- Per table you can set analytics retention up to 730 days and total retention up to 4,383 days (12 years).
- Shortening total retention waits 30 days before deleting data, so you can undo a mistake.
- Activity log data in **AzureActivity** has no ingestion charge, and retention up to 90 days is free.

```bash
az monitor log-analytics workspace create -g rg-mon-prod -n log-contoso-prod -l eastus --retention-time 30
az monitor log-analytics workspace table update -g rg-mon-prod --workspace-name log-contoso-prod \
  --name AzureActivity --retention-time 90 --total-retention-time 730
```

```powershell
New-AzOperationalInsightsWorkspace -ResourceGroupName rg-mon-prod -Name log-contoso-prod -Location eastus
Update-AzOperationalInsightsTable -ResourceGroupName rg-mon-prod -WorkspaceName log-contoso-prod `
  -TableName AzureActivity -RetentionInDays 90 -TotalRetentionInDays 730
```

## Guest logs: Azure Monitor Agent and data collection rules

The **Log Analytics agent** (also called MMA or OMS agent) was **retired on August 31, 2024**. Its replacement is the **Azure Monitor Agent (AMA)**, a VM extension (`AzureMonitorWindowsAgent` or `AzureMonitorLinuxAgent`, publisher `Microsoft.Azure.Monitor`). For machines outside Azure, connect them with **Azure Arc** first, then install AMA.

AMA collects nothing until a **data collection rule (DCR)** is **associated** with the machine. A DCR lists data sources (performance counters, Windows event logs with XPath filters, Syslog facilities and levels, text logs), optional transformations, and destinations (a Log Analytics workspace, or an Azure Monitor workspace for metrics). One DCR can be associated with many machines and one machine with many DCRs.

**Portal:** **Monitor** > **Data Collection Rules** > **+ Create** > Basics (platform type Windows, Linux or All) > **Resources** (add VMs; the portal installs AMA) > **Collect and deliver** (add data sources, each with a destination) > **Create**.

**CLI** (DCR from a JSON file, then associate it):

```bash
vmid=$(az vm show -g rg-web-prod -n vm-web-01 --query id -o tsv)
az vm identity assign --ids $vmid    # AMA authenticates with a managed identity
az vm extension set --ids $vmid --name AzureMonitorLinuxAgent --publisher Microsoft.Azure.Monitor --enable-auto-upgrade true
az monitor data-collection rule create -g rg-mon-prod -n dcr-linux-syslog -l eastus --rule-file dcr-syslog.json
dcrid=$(az monitor data-collection rule show -g rg-mon-prod -n dcr-linux-syslog --query id -o tsv)
az monitor data-collection rule association create --name vm-web-01-syslog --rule-id $dcrid --resource $vmid
```

With no identity settings, as here, AMA uses the VM's system-assigned managed identity; pass `--settings` to use a user-assigned identity instead. Windows events land in **Event**, Syslog in **Syslog**, counters in **Perf**, and AMA's heartbeat in **Heartbeat**.

## Try it yourself

Cloud Shell. Cost: cents (a workspace with very little data and a key vault).

```bash
rg=rg-lab-d5logs; loc=eastus; kv=kv-lab-$RANDOM
az group create -n $rg -l $loc
az monitor log-analytics workspace create -g $rg -n log-lab-d5 -l $loc
az keyvault create -g $rg -n $kv -l $loc
lawid=$(az monitor log-analytics workspace show -g $rg -n log-lab-d5 --query id -o tsv)
kvid=$(az keyvault show -n $kv --query id -o tsv)
az monitor diagnostic-settings create --name kv-audit --resource $kvid --workspace $lawid \
  --logs '[{"categoryGroup":"audit","enabled":true}]'
az monitor diagnostic-settings list --resource $kvid -o table
az keyvault secret list --vault-name $kv   # generates an audit event
```

`az keyvault create` now defaults to the Azure RBAC permission model (CLI reference: `--enable-rbac-authorization` defaults to true), and creating the vault doesn't give you a data-plane role, so the last command may return **Forbidden**. That's fine for this lab: the refused request is still an audit event.

1. After 15 to 90 minutes, open the workspace > **Logs** and run `AzureDiagnostics | where ResourceProvider == "MICROSOFT.KEYVAULT" | take 10` (or the resource-specific Key Vault table if your setting used that mode).
2. Open **Tables** in the workspace and look at the **Plan** and retention columns for AzureActivity and AzureDiagnostics.
3. In **Monitor** > **Activity log**, filter on the resource group and find the `Create or Update Vault` event and its caller.

Clean up: `az group delete -n $rg --yes --no-wait`. Key Vault soft delete keeps the vault name reserved for its retention period; that costs nothing.

## Key takeaways

- Activity log: control plane, eight categories, 90 days free; export with a subscription diagnostic setting to AzureActivity.
- Resource logs need a diagnostic setting; destinations are a workspace, a storage account and an event hub (same region for regional resources), or a partner; one of each type per setting, five settings per resource.
- Category groups `allLogs` and `audit`; Azure diagnostics mode (AzureDiagnostics) vs resource-specific tables.
- Start with one workspace; table plans Analytics, Basic, Auxiliary / Lake; analytics retention up to 2 years, total up to 12 years.
- The Log Analytics agent retired on August 31, 2024; use the Azure Monitor Agent with data collection rules (Azure Arc for non-Azure machines).
