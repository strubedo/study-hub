## Two keys, full control

When you create a storage account, Azure generates **two 512-bit access keys**, called **key1** (primary) and **key2** (secondary). Either key gives **full access to all data** in the account through **Shared Key** authorization, and either one can sign service and account SAS tokens. A connection string is the account name plus one of the keys:

```text
DefaultEndpointsProtocol=https;AccountName=stcontosodata01;AccountKey=<storage-account-key>;EndpointSuffix=core.windows.net
```

Treat a key like a root password for the account's data. Microsoft's guidance, in order of preference:

1. Authorize with **Microsoft Entra ID** and managed identities (Azure RBAC data roles such as Storage Blob Data Reader). For Azure Files over SMB, use **Kerberos** identity-based access.
2. If you need delegated, time-limited access, use a **user delegation SAS**.
3. If you must use keys, keep them in **Azure Key Vault** and **rotate them regularly**.
4. If nothing needs Shared Key, **disallow it** on the account.

## Who can see and rotate keys

Viewing keys needs `Microsoft.Storage/storageAccounts/listkeys/action`. Regenerating them needs `Microsoft.Storage/storageAccounts/regeneratekey/action`. Built-in roles that include both: **Owner**, **Contributor** and **Storage Account Key Operator Service Role**. Reader cannot list keys.

> **Exam tip:** Because `listkeys` effectively grants full data access, a user with **Contributor** on the account can read every blob, even without any "Storage Blob Data" role. The portal uses the key on that user's behalf unless the account is set to default to Microsoft Entra authorization.

**Portal:** storage account > **Security + networking** > **Access keys** > **Show keys**.

```bash
az storage account keys list --resource-group rg-data-prod --account-name stcontosodata01
```

```powershell
(Get-AzStorageAccountKey -ResourceGroupName rg-data-prod -Name stcontosodata01).Value[0]
```

## Rotating keys without downtime

Two keys exist precisely so that applications never lose access during rotation. Microsoft's documented procedure:

1. Update every application's connection string to use **key2** (secondary).
2. **Regenerate key1**.
3. Update the applications to the **new key1**.
4. **Regenerate key2** in the same way.

| Tool | Regenerate key1 | Regenerate key2 |
|---|---|---|
| Portal | Access keys > **Regenerate** next to key1 | Same for key2 |
| Azure CLI | `az storage account keys renew -g rg-data-prod --account-name stcontosodata01 --key primary` | `--key secondary` |
| PowerShell | `New-AzStorageAccountKey -ResourceGroupName rg-data-prod -Name stcontosodata01 -KeyName key1` | `-KeyName key2` |

> **Watch out:** Pick one key for all applications. If some apps use key1 and others key2, you cannot regenerate either without breaking someone.

What regeneration revokes:

- Every client that authorizes with that key (connection strings, Storage Explorer connections that used the key, mounted Azure file shares that use the key, scripts).
- Every **service SAS and account SAS signed with that key**. Regenerating the key is the **only** way to revoke an ad hoc service or account SAS before it expires.
- **Not** user delegation SAS tokens, which are signed with a Microsoft Entra-derived key.

## Key Vault and key expiration policy

Microsoft recommends managing the keys with **Azure Key Vault** (for example, storing the key or connection string as a secret that applications read at run time) so that rotation is done in one place without interrupting applications. Better still, remove the need for keys with Microsoft Entra ID.

A **key expiration policy** sets a reminder interval in days. When the interval passes and a key hasn't been rotated, the portal flags it, and the built-in Azure Policy definition "Storage account keys should not be expired" can report non-compliance. The policy does **not** rotate anything by itself.

- Portal: Access keys > **Set rotation reminder** (if it is greyed out, typically on older accounts whose `KeyCreationTime` is null, rotate each key once first).
- CLI: `az storage account update -g rg-data-prod -n stcontosodata01 --key-exp-days 90`
- PowerShell: `Set-AzStorageAccount -ResourceGroupName rg-data-prod -Name stcontosodata01 -KeyExpirationPeriodInDay 90`

## Disallowing Shared Key authorization

Setting **Allow storage account key access** to **Disabled** (property `AllowSharedKeyAccess = false`) makes the account reject every request authorized with an account key:

| Request | Allowed when AllowSharedKeyAccess is false? |
|---|---|
| Microsoft Entra ID (OAuth) token | Yes |
| User delegation SAS | Yes (signed with an Entra-derived key) |
| Service SAS or account SAS | **No** (signed with the account key) |
| Connection string / account key | **No** |

```bash
az storage account update -g rg-data-prod -n stcontosodata01 --allow-shared-key-access false
az storage account show -g rg-data-prod -n stcontosodata01 --query allowSharedKeyAccess
```

```powershell
Set-AzStorageAccount -ResourceGroupName rg-data-prod -Name stcontosodata01 -AllowSharedKeyAccess $false
```

Facts to remember:

- The property is **null** (unset) on new accounts until you set it; null behaves like **true**.
- To protect a storage account with **Microsoft Entra Conditional Access**, Shared Key must be disallowed (otherwise key-based requests bypass Conditional Access).
- **Azure Files caution:** the portal and many tools use Shared Key for file shares by default. Disallowing it on an account that holds file shares, without RBAC in place, breaks access to those shares. Microsoft suggests moving file shares to a separate account or leaving the setting alone on accounts used for Azure Files.
- Newer API versions also expose per-service switches (`--allow-shared-key-access-for-blob`, `-for-file` and so on); the classic exam answer is the account-wide setting.
- Before disabling, check the **SAS authorization type** in storage logs (Azure Monitor) to find clients that still use keys.
- Trusted Azure services that access the account can still show Shared Key in logs after you disable it; that is expected.

Related account switches:

- **Default to Microsoft Entra authorization in the Azure portal**: the portal uses your Entra identity (and therefore your data roles) instead of fetching the key.
- **Permitted scope for copy operations** (`--allowed-copy-scope AAD` or `PrivateLink`) limits which source accounts copies can come from.

## Try it yourself

Azure Cloud Shell, any browser. Cost: a fraction of a cent.

```bash
rg=rg-lab-d2key; sa=stlabkey$RANDOM
az group create -n $rg -l eastus
az storage account create -g $rg -n $sa --sku Standard_LRS --kind StorageV2
key1=$(az storage account keys list -g $rg -n $sa --query [0].value -o tsv)
az storage container create --account-name $sa --account-key $key1 -n lab
az storage container list --account-name $sa --account-key $key1 -o table   # works

az storage account keys renew -g $rg --account-name $sa --key primary -o none
az storage container list --account-name $sa --account-key $key1 -o table   # old key now fails

az storage account update -g $rg -n $sa --key-exp-days 30
az storage account update -g $rg -n $sa --allow-shared-key-access false
newkey=$(az storage account keys list -g $rg -n $sa --query [0].value -o tsv)
az storage container list --account-name $sa --account-key $newkey -o table # rejected: Shared Key off
```

In the portal, open **Access keys** and **Configuration** and find the same settings. Note the "Set rotation reminder" button and the "Allow storage account key access" switch. Clean up with `az group delete -n $rg --yes --no-wait`. The error text you see is not reproduced here; read it yourself.

## Key takeaways

- Two 512-bit keys; either grants full data access and can sign service or account SAS.
- Rotate one key at a time: move apps to key2, regenerate key1, move apps back, regenerate key2.
- Regenerating a key revokes all service and account SAS signed with it, not user delegation SAS.
- Owner, Contributor and Storage Account Key Operator Service Role can list and regenerate keys.
- A key expiration policy (`--key-exp-days`, `-KeyExpirationPeriodInDay`) is a reminder plus Azure Policy reporting, not automatic rotation.
- `AllowSharedKeyAccess = false` blocks keys, connection strings, service SAS and account SAS; Entra tokens and user delegation SAS still work. It is required for Conditional Access and needs care with Azure Files.
