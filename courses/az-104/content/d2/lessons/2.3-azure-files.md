## Azure Files in one paragraph

**Azure Files** provides fully managed file shares that clients mount over **SMB** (Windows, Linux, macOS) or **NFS 4.1** (Linux only). A share replaces or extends an on-premises file server; it can also be cached on Windows Servers with **Azure File Sync**, which is outside this objective. Shares can also be reached over the FileREST API (portal, Storage Explorer, AzCopy).

## Media tiers, billing models and protocols

Microsoft Learn now describes Azure Files with two **media tiers** and three **billing models**:

| | **SSD (premium)** | **HDD (standard)** |
|---|---|---|
| Storage account kind | `FileStorage` | `StorageV2` (pay-as-you-go) or `FileStorage` (provisioned v2) |
| Billing models | Provisioned v2 (`PremiumV2_*` SKUs), provisioned v1 (`Premium_LRS`, `Premium_ZRS`) | Provisioned v2 (`StandardV2_*` SKUs), **pay-as-you-go** (`Standard_*` SKUs on GPv2) |
| Protocols | **SMB and NFS** | SMB (NFS on HDD is in preview, provisioned v2 and LRS only) |
| Redundancy | LRS, ZRS | LRS, ZRS, GRS, GZRS (no RA- options for Files) |
| Latency | Single-digit milliseconds | Higher |

- **Provisioned v2** (recommended for new deployments): you provision storage, IOPS and throughput separately and pay for what you provision.
- **Provisioned v1** (SSD): you provision storage; IOPS and throughput follow from it.
- **Pay-as-you-go** (HDD, GPv2 account): you pay for used storage plus transactions, and each share has an **access tier**.

You **can't move a share between media tiers**: copy the data to a new share instead.

A newer **Microsoft.FileShares** resource provider lets you create NFS file shares as top-level resources without a storage account. The classic model (shares inside a storage account) is what the AZ-104 objective describes.

### NFS requirements

- **SSD** (`FileStorage`) account for production NFS; HDD NFS is preview.
- **Linux clients only**; no Windows NFS support, no NFS ACLs.
- **No identity-based authentication**: NFS relies on network controls, so the account must be reached through a **private endpoint** or a **service endpoint with virtual network rules**.
- NFS shares support LRS and ZRS (SSD) only; no geo-redundancy.
- Encryption in transit uses TLS through the **AZNFS mount helper**. Older guidance required disabling secure transfer for NFS; current classic accounts have a separate "Require encryption in transit for NFS" setting.

A share uses **one** protocol: you can't reach the same share over SMB and NFS.

### Pay-as-you-go access tiers (HDD)

| Tier | Storage price | Transaction price | Use for |
|---|---|---|---|
| **Transaction optimized** (portal default) | Highest | Lowest | Heavy transaction workloads, migrations |
| **Hot** | Middle | Middle | General-purpose team shares |
| **Cool** | Lowest | Highest; plus a data retrieval charge when moving out of cool | Online archive |

All three use the same HDD hardware; you can change a share's tier at any time, paying transaction (and for cool, retrieval) charges for the move. These are **file share** tiers and are not the same as blob tiers (hot, cool, cold, archive).

## Quotas and size

- **Quota** (`--quota`, in GiB) is the share's maximum size on pay-as-you-go; on provisioned models it is the **provisioned storage** you pay for.
- Pay-as-you-go and provisioned v1 shares can grow to **100 TiB**; provisioned v2 shares (SSD or HDD) up to **256 TiB**. Microsoft Learn now calls the **large file shares** account setting a legacy option: today every pay-as-you-go share can reach 100 TiB, and only some older accounts need the quota raised.
- Maximum file size: **4 TiB**.
- Share names: 3 to 63 characters; lowercase letters, numbers and single hyphens; start and end with a letter or number.

## Create a share

**Portal** (pay-as-you-go): storage account > **Data storage** > **Classic file shares** > **+ Classic file share** (older portal builds and older docs say **File shares** > **+ File share**) > name, **access tier**, then the **Backup** tab (Azure Backup is enabled by default for SMB shares; clear **Enable backup** for a lab) > **Review + create**.

**Azure CLI** (management plane, works with Microsoft Entra credentials):

```bash
# Pay-as-you-go HDD share on a StorageV2 account
az storage share-rm create -g rg-files-prod --storage-account stcontosofiles01 \
  --name finance --quota 1024 --access-tier TransactionOptimized

# SSD provisioned share on a FileStorage account, NFS
az storage share-rm create -g rg-files-prod --storage-account stcontosonfs01 \
  --name builds --quota 1024 --enabled-protocols NFS

# Change quota or tier later
az storage share-rm update -g rg-files-prod --storage-account stcontosofiles01 --name finance --quota 2048 --access-tier Hot
```

**PowerShell:**

```powershell
New-AzRmStorageShare -ResourceGroupName rg-files-prod -StorageAccountName stcontosofiles01 `
  -Name finance -QuotaGiB 1024 -AccessTier TransactionOptimized
Update-AzRmStorageShare -ResourceGroupName rg-files-prod -StorageAccountName stcontosofiles01 `
  -Name finance -QuotaGiB 2048 -AccessTier Hot
```

## Mounting an SMB share

Every SMB client needs **outbound TCP 445** to `<account>.file.core.windows.net`. Many ISPs and corporate firewalls block 445. If it is blocked, connect through a **point-to-site or site-to-site VPN** or **ExpressRoute** (usually to a private endpoint), or use Azure File Sync. Outside the Azure region, the client must support **SMB 3.x** (encryption): Windows 8.1 / Server 2012 R2 and later.

Credentials are either identity-based (Kerberos, lesson 2.1) or the **storage account key** with user name `localhost\<account>` (older docs use `AZURE\<account>`).

**Windows** (portal: share > **Connect** generates this script):

```powershell
Test-NetConnection -ComputerName stcontosofiles01.file.core.windows.net -Port 445
cmd.exe /C "cmdkey /add:`"stcontosofiles01.file.core.windows.net`" /user:`"localhost\stcontosofiles01`" /pass:`"<storage-account-key>`""
New-PSDrive -Name Z -PSProvider FileSystem -Root "\\stcontosofiles01.file.core.windows.net\finance" -Persist
```

or `net use Z: \\stcontosofiles01.file.core.windows.net\finance` after `cmdkey`.

**Linux** (needs `cifs-utils`; check the port with `nc -zvw3 stcontosofiles01.file.core.windows.net 445`):

```bash
sudo mkdir -p /mnt/finance
sudo mount -t cifs //stcontosofiles01.file.core.windows.net/finance /mnt/finance \
  -o vers=3.1.1,credentials=/etc/smbcredentials/stcontosofiles01.cred,serverino,nosharesock,actimeo=30,mfsymlinks
```

Use a credentials file (mode 600) rather than putting the key on the command line, and add an `/etc/fstab` entry for persistence. The portal's **Connect** pane generates the exact script for your share.

**macOS**: Finder > **Go** > **Connect to Server** > `smb://stcontosofiles01.file.core.windows.net/finance`, user `stcontosofiles01`, password = account key; or `open smb://...` from Terminal. Port 445 must be open here too.

**NFS** (Linux, from an allowed virtual network):

```bash
sudo mount -t nfs stcontosonfs01.file.core.windows.net:/stcontosonfs01/builds /mnt/builds -o vers=4,minorversion=1,sec=sys,nconnect=4
```

Microsoft now recommends the AZNFS mount helper (`-t aznfs`) for encryption in transit; check the portal's Connect pane for the current command.

## Other share settings

- **Soft delete for shares**, **share snapshots** and **Azure Backup**: next lesson.
- **SMB security settings** on the account: SMB versions, Kerberos ticket encryption, channel encryption, SMB Multichannel (SSD only).
- **Networking**: the account firewall applies to SMB; private endpoints give a stable private IP for on-premises clients.

## Try it yourself

Azure Cloud Shell plus, optionally, your own computer. Cost: a few cents for a small HDD share.

```bash
rg=rg-lab-d2files; sa=stlabfiles$RANDOM
az group create -n $rg -l eastus
az storage account create -n $sa -g $rg --sku Standard_LRS --kind StorageV2
az storage share-rm create -g $rg --storage-account $sa -n team --quota 5 --access-tier Hot
az storage share-rm show -g $rg --storage-account $sa -n team --query "{quota:shareQuota, tier:accessTier, protocol:enabledProtocols}"
az storage share-rm update -g $rg --storage-account $sa -n team --access-tier Cool
```

In the portal, open the share and select **Connect**: look at the Windows, Linux and macOS scripts. From your own machine, test port 445 (`Test-NetConnection` on Windows, `nc -zv` on Linux or macOS) to see whether your network blocks it. If it is open, mount the share with the script. Clean up: `az group delete -n $rg --yes --no-wait`.

## Key takeaways

- SSD (premium, `FileStorage`) or HDD (standard); provisioned v2, provisioned v1 or pay-as-you-go billing.
- NFS: SSD `FileStorage` account (HDD preview), Linux only, no identity auth, private or service endpoint required.
- Pay-as-you-go shares have tiers transaction optimized (default), hot and cool; quotas up to 100 TiB.
- Create with `az storage share-rm create` / `New-AzRmStorageShare` (`--quota`, `--access-tier`, `--enabled-protocols`).
- SMB needs outbound TCP 445 and SMB 3.x from outside Azure; use VPN or ExpressRoute when 445 is blocked.
- Mount with the portal's Connect script: `New-PSDrive` or `net use` on Windows, `mount -t cifs` on Linux, Finder `smb://` on macOS.
