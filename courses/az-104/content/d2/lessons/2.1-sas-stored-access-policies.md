## What a SAS is

A **shared access signature (SAS)** is a set of query parameters that you append to a storage URL. The parameters say what the holder may do, on which resource, for how long and from where. One of them, `sig`, is an HMAC signature computed over the others with a secret key. Azure Storage recomputes the signature on every request; if any parameter was altered, or the key that signed it no longer exists, the request fails with **403 Forbidden**.

Azure Storage does not keep a list of the SAS tokens you issue. You can create as many as you like, nobody can audit how many exist, and you cannot delete one individually. That fact drives everything about **revocation**.

## The three kinds of SAS

| | User delegation SAS | Service SAS | Account SAS |
|---|---|---|---|
| Signed with | A **user delegation key** obtained with Microsoft Entra credentials | Storage account key | Storage account key |
| Services | Blob (and Data Lake), Queue, Table, Azure Files | One service | One or more services (`ss`) |
| Scope | Container, directory or blob (Blob); share or file (Files) | One resource (container/blob, share/file, queue, table) | Service, container and object levels (`srt`), including service-level operations such as Get/Set Service Properties |
| Stored access policy | Not supported | **Supported** | Not supported |
| Works when Shared Key is disallowed | Yes | No | No |
| Revoke early by | `az storage account revoke-delegation-keys` (revokes all user delegation keys on the account), or remove the principal's role | Delete or change its stored access policy, or regenerate the key that signed it | Regenerate the key that signed it |

Microsoft recommends the **user delegation SAS** whenever a SAS is needed: no account key is involved, and the signer must hold an Azure role that includes the `Microsoft.Storage/storageAccounts/<service>/generateUserDelegationKey` action (for Blob: `blobServices/generateUserDelegationKey`) at storage account, resource group or subscription scope. Built-in roles that include it: Storage Blob Data Owner, Storage Blob Data Contributor and Storage Blob Data Reader, Contributor, Storage Account Contributor, and the Storage Blob, Queue, Table and File **Delegator** roles. The signer also needs data permissions that cover what the SAS grants. A user delegation key is valid for at most **seven days**, so a user delegation SAS can never be usable for longer than that.

> **Exam tip:** Microsoft Learn's SAS overview now lists Queue, Table and Azure Files as well as Blob for user delegation SAS. Older study material says "Blob only"; follow the current documentation.

## The signed fields

Here is an account SAS laid out field by field (signature replaced):

```text
https://stcontosodata01.blob.core.windows.net/?sv=2022-11-02&ss=b&srt=co&sp=rl&st=2026-11-23T08:00:00Z&se=2026-11-23T20:00:00Z&sip=203.0.113.0-203.0.113.255&spr=https&sig=<signature>
```

| Field | Name | Meaning in this token |
|---|---|---|
| `sv` | Signed version | Storage REST version used to interpret the token |
| `ss` | Signed services | `b` = Blob only (`f` Files, `q` Queue, `t` Table) |
| `srt` | Signed resource types | `c` container-level and `o` object-level operations (`s` would add service-level) |
| `sp` | Signed permissions | `r` read, `l` list. No write, create, add or delete |
| `st` | Signed start | Optional. Leave it out (or set it 15 minutes in the past) to avoid clock-skew failures |
| `se` | Signed expiry | Required (unless a stored access policy supplies it) |
| `sip` | Signed IP | Optional single IPv4 address or range written with a hyphen |
| `spr` | Signed protocol | `https` or `https,http`. HTTP-only is not allowed |
| `sig` | Signature | HMAC-SHA256 over the string to sign |

A **service SAS** uses `sr` (signed resource: `b` blob, `c` container, `bs` snapshot, `bv` version, `d` directory; `f` file and `s` share for Azure Files) instead of `ss` and `srt`, and can carry `si`, the **signed identifier** of a stored access policy. A user delegation SAS adds `skoid`, `sktid`, `skt`, `ske` and related fields that describe the delegation key.

How to evaluate a request against a token, which is what exhibit questions ask you to do:

1. Is the service in `ss` (account SAS) or the resource covered by `sr` (service SAS)?
2. Is the operation's resource type in `srt`? Listing blobs is a **container**-level operation, while reading a blob is **object**-level.
3. Is the operation covered by `sp`? Uploading a new blob needs `c` or `w`, and deleting needs `d`.
4. Is the request time between `st` and `se`?
5. Is the client address inside `sip`, and the protocol allowed by `spr`?
6. Separately, does the storage firewall admit the client? A SAS never overrides the firewall.

> **Watch out:** `sip` holds public addresses. For a client in the same Azure region as the account, Microsoft Learn says not to set `sip` to its outbound public IP: same-region requests don't arrive from that address, so they fail.

## Generating a SAS

**Portal:** storage account > **Security + networking** > **Shared access signature** builds an account SAS. For a container or blob, open it and choose **Generate SAS**. You pick the **signing method**: Account key or **User delegation key**. With Account key you can also pick a stored access policy.

**Azure CLI (user delegation SAS for a container):**

```bash
az storage container generate-sas --account-name stcontosodata01 --name reports \
  --permissions rl --expiry 2026-11-24T00:00:00Z --https-only \
  --auth-mode login --as-user
```

`--auth-mode login` plus `--as-user` makes it a user delegation SAS. Without them, the CLI signs with the account key (service SAS). The token comes back without the leading `?`.

**PowerShell (user delegation SAS):**

```powershell
$ctx = New-AzStorageContext -StorageAccountName stcontosodata01 -UseConnectedAccount
New-AzStorageContainerSASToken -Context $ctx -Name reports -Permission rl `
  -ExpiryTime (Get-Date).AddHours(8) -Protocol HttpsOnly
```

A context created with `-UseConnectedAccount` (Microsoft Entra) yields a user delegation SAS. A context created with `-StorageAccountKey` yields a service SAS.

## Stored access policies

A **stored access policy** lives on a **blob container, file share, queue or table**. It holds a start time, an expiry time and permissions under a name (the signed identifier, up to 64 characters). A **service SAS** that references the policy (`si=<name>`) inherits those values. The rules:

- **Maximum of five** stored access policies per container, share, queue or table. A sixth returns 400 Bad Request.
- Each of start, expiry and permissions must be specified **either** in the policy **or** in the SAS, never in both.
- Only **service SAS** can use them, never account SAS or user delegation SAS.
- A new or changed policy can take up to **30 seconds** to apply.

**Revoking** all tokens tied to a policy, without touching the account keys:

- **Delete the policy**, or
- **Change its expiry** to a time in the past, or
- **Rename it** (change the signed identifier).

> **Watch out:** If you delete a policy and later re-create one with the **same name**, every old SAS that referenced it works again (if its own fields still allow). Use a new name when you re-create a policy after a leak.

Changing a policy's permissions (for example, from `rwl` to `rl`) immediately changes what every linked SAS can do. That is the reason to use policies: you can adjust or kill a whole family of tokens centrally.

```bash
# Policy on the container, then a service SAS that references it
az storage container policy create --account-name stcontosodata01 --account-key <storage-account-key> \
  --container-name invoices --name read-partners --permissions rl --expiry 2027-11-01T00:00:00Z
az storage container generate-sas --account-name stcontosodata01 --account-key <storage-account-key> \
  --name invoices --policy-name read-partners --https-only
```

```powershell
$ctx = New-AzStorageContext -StorageAccountName stcontosodata01 -StorageAccountKey '<storage-account-key>'
New-AzStorageContainerStoredAccessPolicy -Context $ctx -Container invoices -Policy read-partners `
  -Permission rl -ExpiryTime (Get-Date).AddYears(1)
New-AzStorageContainerSASToken -Context $ctx -Name invoices -Policy read-partners
```

In the portal: container > **Access policy** > **Add policy** under **Stored access policies**.

## SAS expiration policy

Separately from stored access policies, an account can have a **SAS expiration policy** (`--sas-expiration-period`, format `DD.HH:MM:SS`). It applies to service and account SAS: by default a longer token only raises a warning and a log entry (`Log`), and with `--sas-expiration-action Block` such tokens are rejected.

## Try it yourself

Azure Cloud Shell (Bash), any browser. Cost: well under one US cent; deleted at the end.

```bash
rg=rg-lab-d2sas; sa=stlabsas$RANDOM
az group create -n $rg -l eastus
az storage account create -g $rg -n $sa --sku Standard_LRS --kind StorageV2
key=$(az storage account keys list -g $rg -n $sa --query [0].value -o tsv)
az storage container create --account-name $sa --account-key $key --name lab
echo "hello" > hello.txt
az storage blob upload --account-name $sa --account-key $key -c lab -f hello.txt -n hello.txt
az storage container policy create --account-name $sa --account-key $key -c lab --name lab-read \
  --permissions r --expiry 2030-01-01T00:00:00Z
sas=$(az storage blob generate-sas --account-name $sa --account-key $key -c lab -n hello.txt \
  --policy-name lab-read --https-only -o tsv)
sleep 30
curl -s -o /dev/null -w "%{http_code}\n" "https://$sa.blob.core.windows.net/lab/hello.txt?$sas"
az storage container policy delete --account-name $sa --account-key $key -c lab --name lab-read
sleep 30
curl -s -o /dev/null -w "%{http_code}\n" "https://$sa.blob.core.windows.net/lab/hello.txt?$sas"
```

Expect 200 before the delete and 403 after it. Then re-create the policy with the same name and watch the old token come back to life. Clean up with `az group delete -n $rg --yes --no-wait`.

## Key takeaways

- User delegation SAS (Entra-signed, preferred), service SAS and account SAS (both key-signed).
- Read the fields in order: service, resource type, permissions, time window, IP, protocol; the firewall is a separate check.
- Stored access policies: container, share, queue or table; **max five**; service SAS only; delete, expire or rename to revoke.
- Regenerating an account key revokes every service and account SAS signed with it; it doesn't touch user delegation SAS.
- Revoke user delegation SAS with `az storage account revoke-delegation-keys`; the key lives at most seven days.
- A SAS expiration policy warns (`Log`) or rejects (`Block`) over-long key-signed tokens.
