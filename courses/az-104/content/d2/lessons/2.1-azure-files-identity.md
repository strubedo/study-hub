## Why identity-based access

An SMB Azure file share can be mounted with the **storage account key** as the password (`localhost\stcontosofiles01`, key). That gives every user full control and leaves you with no per-user audit trail. **Identity-based access** works like a Windows file server instead: users authenticate with **Kerberos** under their own identity, and access is checked at two layers.

1. **Share-level permissions**, assigned with **Azure RBAC** roles on the share (or a default for all authenticated identities).
2. **Directory- and file-level permissions**, enforced with **Windows ACLs** (NTFS-style DACLs) on the files and folders.

The effective access is the **more restrictive** of the two layers, exactly as with share permissions and NTFS permissions on a Windows server. Identity-based access applies to **SMB** shares only; NFS shares rely on network rules instead.

There is no extra charge for enabling identity-based authentication.

## Choose one identity source

A storage account uses **one** identity source for all of its file shares. All three need **Kerberos** enabled in the account's SMB security settings.

| Identity source | Best fit | Identities and clients | Key requirements |
|---|---|---|---|
| **On-premises AD DS** | An existing Active Directory; clients can reach domain controllers | AD DS users on Windows (and Linux, with extra setup) | The storage account is joined to AD DS as a computer or service logon account, usually with the **AzFilesHybrid** module's `Join-AzStorageAccount`. Users must be **synced** to Microsoft Entra ID (Microsoft Entra Connect Sync or Cloud Sync) to receive share-level RBAC |
| **Microsoft Entra Domain Services** | You already use, or need, a managed domain in Azure | Cloud-only or hybrid users, Windows and Linux | Clients **joined to the managed domain** with network line of sight to its domain controllers. Non-Azure machines can't join it |
| **Microsoft Entra Kerberos** | Cloud-first or hybrid; Microsoft Entra joined or hybrid joined clients; FSLogix; no line of sight to DCs | **Hybrid** identities, and **cloud-only** identities (Azure Public cloud regions only; clients must be Windows 11 24H2 or later with the March 2026 update, or Windows Server 2025), on Windows; macOS in preview. **Linux users not supported** | Microsoft Entra ID issues the Kerberos ticket, so clients need no DC connectivity. For hybrid users you still need AD DS plus sync. Exclude the storage account's app from MFA Conditional Access policies |

> **Exam tip:** For the AZ-104 objective as published in 2023, the Microsoft Entra Kerberos source was described as "for hybrid identities". Microsoft Learn now also documents cloud-only identities for it. Expect scenario wording such as "Microsoft Entra joined devices, users synced from on-premises AD DS, no VPN to the domain controllers": that is Microsoft Entra Kerberos.

Enabling each source:

| Source | Portal | Azure CLI | PowerShell |
|---|---|---|---|
| AD DS | Storage account > **Data storage** > **File shares** > **Identity-based access** > Active Directory | `--enable-files-adds true` plus domain values (`--domain-name`, `--domain-guid`, `--domain-sid`, `--forest-name`, `--net-bios-domain-name`, `--azure-storage-sid`), or `Join-AzStorageAccount` | `Join-AzStorageAccount` (AzFilesHybrid) |
| Microsoft Entra Domain Services | Same blade, Microsoft Entra Domain Services | `az storage account update -g rg-files-prod -n stcontosofiles01 --enable-files-aadds true` | `Set-AzStorageAccount ... -EnableAzureActiveDirectoryDomainServicesForFile $true` |
| Microsoft Entra Kerberos | Same blade, Microsoft Entra Kerberos | `az storage account update -g rg-files-prod -n stcontosofiles01 --enable-files-aadkerb true` | `Set-AzStorageAccount ... -EnableAzureActiveDirectoryKerberosForFile $true` |

For Microsoft Entra Kerberos you also **grant admin consent** to the new app registration that represents the storage account. To switch sources, disable the current one first.

## Layer 1: share-level permissions with Azure RBAC

Assign one of these built-in roles at the **file share** scope (or higher: account, resource group, subscription) to a Microsoft Entra user, group or service principal:

| Role | What it grants over SMB | Windows analogy |
|---|---|---|
| **Storage File Data SMB Share Reader** | Read files and directories | Share permission Read |
| **Storage File Data SMB Share Contributor** | Read, write, delete | Share permission Change (without changing ACLs) |
| **Storage File Data SMB Share Elevated Contributor** | Read, write, delete **and modify ACLs** | Change plus permission management |
| **Storage File Data SMB Admin** | Admin access equivalent to the storage account key over SMB | Full control |
| **Storage File Data SMB Take Ownership** | Take ownership of files and directories | Take ownership privilege |
| Storage File Data Privileged Reader / Privileged Contributor | Read (or read, write, modify ACLs) **overriding** existing ACLs, used by tools over REST | Backup-operator style |

Portal: file share > **Access Control (IAM)** > **Add role assignment**. CLI:

```bash
az role assignment create --role "Storage File Data SMB Share Contributor" \
  --assignee grp-finance@contoso.com \
  --scope "/subscriptions/<subscription-id>/resourceGroups/rg-files-prod/providers/Microsoft.Storage/storageAccounts/stcontosofiles01/fileServices/default/fileshares/finance"
```

PowerShell:

```powershell
New-AzRoleAssignment -SignInName User1@contoso.com -RoleDefinitionName "Storage File Data SMB Share Reader" `
  -Scope "/subscriptions/<subscription-id>/resourceGroups/rg-files-prod/providers/Microsoft.Storage/storageAccounts/stcontosofiles01/fileServices/default/fileshares/finance"
```

Notes:

- For **hybrid** users, assign the role to the **synced** identity (`user1@contoso.com`), not to an on-premises-only account. With **AD DS** authentication, users who aren't synced can still get access through a **synced AD DS group** that holds the role, because Azure Files authorizes from the group SIDs in the Kerberos ticket.
- Share-level changes usually take effect within **30 minutes**.
- **Owner** and **Contributor** are management-plane roles; they do **not** grant SMB data access by themselves.

### Default share-level permission

Instead of per-identity assignments, you can set a **default share-level permission** on the storage account that applies to **all authenticated identities** and all shares in the account. It starts as **None**, and you can set it only on an account that already has an identity source enabled. Use it when:

- On-premises AD DS **isn't synced** to Microsoft Entra ID, or is synced to a different tenant.
- Identities have no Entra counterpart: **computer accounts**, gMSAs and sMSAs.
- You want to manage access only with Windows ACLs.

Values: `StorageFileDataSmbShareReader`, `StorageFileDataSmbShareContributor`, `StorageFileDataSmbShareElevatedContributor` or `None`.

```bash
az storage account update -g rg-files-prod -n stcontosofiles01 --default-share-permission StorageFileDataSmbShareContributor
```

```powershell
Set-AzStorageAccount -ResourceGroupName rg-files-prod -Name stcontosofiles01 -DefaultSharePermission StorageFileDataSmbShareContributor
```

An explicit RBAC assignment and the default can coexist; a user gets the higher of the two share-level grants.

## Layer 2: directory and file ACLs

Once share-level access exists, set Windows ACLs the way you would on a file server:

1. Mount the share with admin-level access from a Windows machine that can reach the domain controllers. Microsoft recommends mounting with your own identity holding **Storage File Data SMB Admin**; mounting with the **storage account key** also works but is less secure.
2. Use **File Explorer** (Properties > Security) or `icacls` to grant groups the right NTFS permissions. With Microsoft Entra Kerberos and cloud-only identities, Microsoft Learn says to use the Azure portal or the RestSetAcls tool instead.

```text
C:\> net use Z: \\stcontosofiles01.file.core.windows.net\finance /user:localhost\stcontosofiles01 <storage-account-key>
C:\> icacls Z:\Budget /grant "CONTOSO\grp-finance:(OI)(CI)M"
```

### Working out effective access

| Share-level (RBAC) | NTFS on the folder | Effective |
|---|---|---|
| SMB Share Reader | Modify | **Read** (share layer caps it) |
| SMB Share Contributor | Read | **Read** (NTFS caps it) |
| SMB Share Contributor | Modify | Read, write, delete |
| SMB Share Elevated Contributor | Full control | Read, write, delete, change permissions |
| None (no role, no default) | Full control | **No access** (can't mount) |

## Try it yourself

A full Kerberos lab needs a domain or Microsoft Entra joined Windows client, which Cloud Shell cannot provide. This lab practises the Azure side; it costs a few cents.

```bash
rg=rg-lab-d2filesid; sa=stlabfid$RANDOM
az group create -n $rg -l eastus
az storage account create -g $rg -n $sa --sku Standard_LRS --kind StorageV2
az storage share-rm create -g $rg --storage-account $sa -n finance --quota 10
# A default share-level permission can be set only after an identity source is enabled,
# so this lab skips it (Cloud Shell can't act as a Kerberos client anyway).
scope=$(az storage account show -g $rg -n $sa --query id -o tsv)/fileServices/default/fileshares/finance
me=$(az ad signed-in-user show --query id -o tsv)
az role assignment create --role "Storage File Data SMB Share Contributor" --assignee-object-id $me \
  --assignee-principal-type User --scope $scope
az role assignment list --scope $scope -o table
```

In the portal, open the account > **File shares** and look at **Identity-based access** (not configured): the default share-level permission setting appears there once a source is enabled. If you have a Microsoft Entra joined Windows 11 PC, try enabling Microsoft Entra Kerberos and follow the Learn article for the client settings. Clean up with `az group delete -n $rg --yes --no-wait`.

## Key takeaways

- Identity-based access is for **SMB** shares, uses **Kerberos**, and allows one identity source per account: AD DS, Microsoft Entra Domain Services, or Microsoft Entra Kerberos.
- Microsoft Entra Kerberos: no DC line of sight needed; Entra joined or hybrid joined Windows clients; no Linux users.
- Share level = RBAC roles (SMB Share Reader / Contributor / Elevated Contributor / Admin); file level = Windows ACLs; effective = most restrictive.
- Hybrid users must be synced to Microsoft Entra ID to receive RBAC; otherwise use the **default share-level permission**, which also covers computer accounts.
- Owner and Contributor don't grant SMB data access.
- Set ACLs with File Explorer or `icacls` after mounting with the key or an admin-level identity.
