## Containers and blobs

Blob Storage is organised as **account > container > blob**. A **container** groups blobs, like a top-level folder or an S3 bucket. An account can hold any number of containers, and a container any number of blobs. Without a hierarchical namespace there are no real directories: a slash in a blob name (`2026/11/report.pdf`) creates a **virtual directory** that tools display as a folder.

Container naming rules:

- **3 to 63 characters**.
- **Lowercase letters, numbers and hyphens**; must start with a letter or number; no consecutive hyphens.
- Special containers: `$root` (default container, blobs addressable without a container name), `$web` (static website), `$logs` (classic Storage Analytics logs).

Blob URL: `https://stcontosodata01.blob.core.windows.net/<container>/<blob-name>`.

## Blob types

| Type | Built from | Max size (Microsoft Learn) | Use for | Tiering |
|---|---|---|---|---|
| **Block blob** | Blocks committed with Put Block List | About **190.7 TiB** | Documents, images, video, backups, almost everything | Hot / cool / cold / archive |
| **Append blob** | Blocks that can only be **appended** | Limited by block count and size (see the blob types article) | Logs, audit trails | No tiering |
| **Page blob** | 512-byte pages, random read/write | **8 TiB** | VHDs for unmanaged VM disks | No tiering (premium page blobs use performance tiers instead) |

You choose the type when the blob is created, and it can't be changed afterwards (copy it to a new blob instead). Managed disks are page blobs that Azure manages for you.

## Creating a container

**Portal:** storage account > **Data storage** > **Containers** > **+ Container** (labelled **+ Add container** in some portal builds) > name, **anonymous access level**, and under **Advanced** an optional default **encryption scope** and **version-level immutability support**.

**Azure CLI.** Two command groups exist:

```bash
# Management plane (Azure Resource Manager): authorized by your Azure RBAC role on the account
az storage container-rm create -g rg-data-prod --storage-account stcontosodata01 --name reports --public-access off

# Data plane: authorized with Microsoft Entra ID (needs a Storage Blob Data role) or a key/SAS
az storage container create --account-name stcontosodata01 --name reports --auth-mode login
```

**PowerShell:**

```powershell
$ctx = New-AzStorageContext -StorageAccountName stcontosodata01 -UseConnectedAccount
New-AzStorageContainer -Name reports -Context $ctx -Permission Off
```

## Anonymous (public) read access

Two settings work together:

1. **Account level**: **Allow Blob anonymous access** (`allowBlobPublicAccess`). New accounts have it set to **false**, and Microsoft recommends leaving it off.
2. **Container level**: the container's **anonymous access level**:
   - **Private (no anonymous access)**: the default. Every request needs authorization.
   - **Blob (anonymous read access for blobs only)**: anyone can read a blob **if they know its URL**, but can't list the container.
   - **Container (anonymous read access for containers and blobs)**: anyone can read blobs **and list** the container's contents.

| Account setting | Container = Private | Container = Blob | Container = Container |
|---|---|---|---|
| Anonymous access **disallowed** | No anonymous access | **No anonymous access** (account overrides) | **No anonymous access** (account overrides) |
| Anonymous access **allowed** | No anonymous access | Read blobs by URL, no listing | Read blobs and list container |

Key points:

- You can only set a container to Blob or Container when the account allows anonymous access.
- Anonymous access is **read only**. Uploads and deletes always need authorization.
- If a request carries an Authorization header, the service ignores anonymous access and authorizes the request with those credentials.
- Setting the access level on an existing container with the data-plane command (`az storage container set-permission`, `Set-AzStorageContainerAcl`) needs the account key, a connection string or a SAS: the underlying Set Container ACL operation doesn't accept Microsoft Entra authorization. The `container-rm` commands use Azure Resource Manager instead.

```bash
az storage account update -g rg-web-prod -n stcontosoweb01 --allow-blob-public-access true
az storage container-rm create -g rg-web-prod --storage-account stcontosoweb01 --name images --public-access blob
az storage container-rm update -g rg-web-prod --storage-account stcontosoweb01 --name images --public-access off
```

```powershell
Set-AzStorageAccount -ResourceGroupName rg-web-prod -Name stcontosoweb01 -AllowBlobPublicAccess $true
$ctx = New-AzStorageContext -StorageAccountName stcontosoweb01 -StorageAccountKey '<storage-account-key>'
Set-AzStorageContainerAcl -Name images -Permission Blob -Context $ctx
```

> **Exam tip:** "Anonymous users must download images by URL but must not enumerate the container" is the **Blob** level. "Users must be able to list and download" is **Container**. If the account-level setting is off, neither works, whatever the container says.

## Immutable storage (WORM), at a high level

**Immutable storage** keeps blobs in a **write once, read many** state: they can be created and read but not modified or deleted while a policy is in effect. It supports regulatory requirements such as SEC 17a-4(f).

Two policy types, which can coexist:

- **Time-based retention**: blobs can't be modified or deleted until the retention interval (from **1 day to 146,000 days**) has passed since creation. A policy starts **unlocked** for testing (you can shorten, extend or delete it) and should then be **locked**. A **locked** policy can't be deleted or shortened, only extended (a limited number of times). An optional **allow protected append writes** setting lets append blobs keep growing.
- **Legal hold**: a tag-based hold with no end date. Data stays immutable until **every** legal hold tag is cleared.

Scope:

- **Container-level WORM**: the policy applies to every blob in the container.
- **Version-level WORM**: needs **blob versioning**; policies can be set at account, container or individual blob version level.

Immutability interacts with other features: lifecycle management can't delete blobs in an immutable container, and object replication may fail to apply changes to an immutable destination. After a time-based policy on a container is locked, the container can be deleted only when it is empty.

**Portal:** container > **Settings** > **Access policy** > **Add policy** under **Immutable blob storage**, choose **Time-based retention** or **Legal hold**.

```bash
az storage container immutability-policy create -g rg-data-prod --account-name stcontosodata01 \
  --container-name audit --period 365
az storage container legal-hold set -g rg-data-prod --account-name stcontosodata01 \
  --container-name audit --tags case2026
```

## Try it yourself

Azure Cloud Shell. Cost: cents.

```bash
rg=rg-lab-d2cont; sa=stlabcont$RANDOM
az group create -n $rg -l eastus
az storage account create -n $sa -g $rg --sku Standard_LRS --kind StorageV2
az storage account show -n $sa -g $rg --query allowBlobPublicAccess
az storage container-rm create -g $rg --storage-account $sa -n images --public-access blob   # fails: account disallows
az storage account update -n $sa -g $rg --allow-blob-public-access true
az storage container-rm create -g $rg --storage-account $sa -n images --public-access blob
key=$(az storage account keys list -g $rg -n $sa --query [0].value -o tsv)
echo "public test" > hello.txt
az storage blob upload --account-name $sa --account-key $key -c images -f hello.txt -n hello.txt
curl -s "https://$sa.blob.core.windows.net/images/hello.txt"                                   # works anonymously
curl -s -o /dev/null -w "%{http_code}\n" "https://$sa.blob.core.windows.net/images?restype=container&comp=list"   # listing denied
az storage account update -n $sa -g $rg --allow-blob-public-access false
sleep 30; curl -s -o /dev/null -w "%{http_code}\n" "https://$sa.blob.core.windows.net/images/hello.txt"         # now denied
```

Then switch the container to `container` level (after re-allowing at the account) and repeat the listing request. Clean up: `az group delete -n $rg --yes --no-wait`. The exact status codes and messages are not reproduced here; observe them.

## Key takeaways

- Container names: 3 to 63 characters, lowercase letters, numbers and hyphens.
- Block blobs (general data, tierable), append blobs (logs), page blobs (VHDs, 8 TiB); type is fixed at creation.
- Anonymous read needs the account setting **allowed** *and* the container at **Blob** (read by URL) or **Container** (read and list); new accounts disallow it.
- `az storage container-rm` works through Azure Resource Manager; `az storage container` works on the data plane.
- Immutable storage: time-based retention (unlocked, then locked) and legal holds, at container or version level.
