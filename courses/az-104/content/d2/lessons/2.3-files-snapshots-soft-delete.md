## Two features, two different problems

| Problem | Feature |
|---|---|
| A user overwrote or deleted **a file or folder** inside a share | **Share snapshot** (restore the earlier version) |
| Someone deleted **the whole share** | **Soft delete for file shares** (undelete the share) |
| Someone deleted the **storage account** | Neither: use a **resource lock** (Domain 1) |
| Long-term, policy-driven retention and reporting | **Azure Backup** for Azure Files, which schedules and manages snapshots (Domain 5) |

Remember the split: **snapshots work inside a share; soft delete protects the share itself**.

## Share snapshots

A **share snapshot** is a **read-only, point-in-time copy of an entire file share**. You can't snapshot a single file or directory: the snapshot is always share-level, although you restore individual files from it.

Facts from Microsoft Learn:

- **Incremental**: only data changed since the previous snapshot is stored, and you pay only for that changed content. You still need just the snapshot you want to restore from; deleting an older snapshot keeps everything the newer ones need.
- **Up to 200 snapshots per share.** At 200 you must delete old ones before creating more. Snapshots can be kept for up to **10 years**.
- Snapshots **don't count toward the share's quota**.
- A snapshot has the share's URI plus a timestamp: `https://stcontosofiles01.file.core.windows.net/finance?sharesnapshot=2026-11-22T02:00:00.0000000Z`.
- Snapshots are deleted **with the share**. You can't delete a share and keep its snapshots, and Microsoft Learn states that share snapshots don't prevent accidental deletion of the share. (The portal's delete removes the snapshots too; `az storage share-rm delete` refuses a share that has snapshots unless you add `--include snapshots`, which is a safety check, not protection.)
- Supported for **SMB and NFS** shares (NFS snapshots through the management APIs).
- You can't modify a snapshot; you can read it, copy from it or delete it.

### Taking snapshots

**Portal:** file share > **Operations** > **Snapshots** > **+ Add snapshot** (optional comment).

```bash
# Data plane
az storage share snapshot --name finance --account-name stcontosofiles01
az storage share list --account-name stcontosofiles01 --include-snapshots
```

```powershell
# Management plane
New-AzRmStorageShare -ResourceGroupName rg-files-prod -StorageAccountName stcontosofiles01 -Name finance -Snapshot
Get-AzRmStorageShare -ResourceGroupName rg-files-prod -StorageAccountName stcontosofiles01 -IncludeSnapshot
```

For scheduled snapshots with retention, configure **Azure Backup** for the share (Recovery Services vault, backup policy). Azure Backup's snapshot-based protection for file shares creates share snapshots for you, so plan the 200-per-share limit with both in mind.

### Restoring from a snapshot

- **Windows, Previous Versions**: right-click the mounted share or a folder > **Properties** > **Previous Versions**. Each share snapshot appears as a version. **Open** it to browse, **Copy** to a different location, or **Restore** over the current content. Robocopy against the snapshot path works for bulk restores.
- **Portal**: open the snapshot, browse to the file, select **Restore** and choose to overwrite the original or restore to a new name.
- **Copy** with AzCopy, the CLI or PowerShell from the snapshot URL (`?sharesnapshot=...`) back to the base share.
- **Azure Backup**: item-level or full-share restore, to the original or an alternate location.

Restoring copies data back; the snapshot is **not promoted** and stays unchanged. Restored files count as changed content for the next snapshot.

> **Exam tip:** To pick the right snapshot, find the newest one taken **after** the version you want was saved and **before** the bad change. A snapshot taken before the file was last saved holds an older version; one taken after the deletion doesn't hold the file at all.

## Soft delete for file shares

**Soft delete** keeps a deleted **file share** (with all its files and snapshots) in a soft-deleted state for a retention period, during which you can **undelete** it.

- Configured at the **storage account** level (file service properties) and applies to every share in the account.
- **Enabled by default** on new storage accounts, with a default retention of **7 days**. Retention can be **1 to 365 days** and changed at any time; the clock starts when the share is deleted.
- Protects **shares only**, not individual files or directories. A deleted file inside a share can't be undeleted with share soft delete; use snapshots or Azure Backup.
- Soft-deleted shares still consume capacity, so check the pricing page for how they are billed under your billing model.
- To **permanently** delete a soft-deleted share early: undelete it, disable soft delete, delete the share, then re-enable soft delete.
- Works for SMB and NFS **classic** shares (shares in a storage account). Microsoft Learn says it doesn't apply to shares created with the newer Microsoft.FileShares resource provider.

**Portal:** storage account > **Data management** > **Data protection** (or the **File shares** blade **Soft delete** link) > **Enable soft delete for file shares**, retention in days. To restore: **File shares** > **Show deleted shares** > select the share > **Undelete**.

```bash
az storage account file-service-properties update -g rg-files-prod --account-name stcontosofiles01 \
  --enable-delete-retention true --delete-retention-days 14
az storage share-rm list -g rg-files-prod --storage-account stcontosofiles01 --include-deleted
az storage share-rm restore -g rg-files-prod --storage-account stcontosofiles01 \
  --name finance --deleted-version <deleted-version>
```

```powershell
Update-AzStorageFileServiceProperty -ResourceGroupName rg-files-prod -StorageAccountName stcontosofiles01 `
  -EnableShareDeleteRetentionPolicy $true -ShareRetentionDays 14
Get-AzRmStorageShare -ResourceGroupName rg-files-prod -StorageAccountName stcontosofiles01 -IncludeDeleted
Restore-AzRmStorageShare -ResourceGroupName rg-files-prod -StorageAccountName stcontosofiles01 `
  -Name finance -DeletedShareVersion <deleted-version>
```


## Putting it together: a protection baseline

| Layer | Setting |
|---|---|
| Account deletion | `CanNotDelete` lock on the storage account |
| Share deletion | Soft delete for file shares, 14 to 30 days |
| File-level mistakes | Azure Backup policy (daily snapshots) or manual snapshots before risky changes |
| Ransomware within retention | Snapshots are read-only and can't be modified over SMB; with Azure Backup, enable soft delete for backups too |

Blob Storage has parallel but separate features (blob soft delete, container soft delete, versioning, blob snapshots), covered in the blob lessons. Don't mix them up: **blob soft delete protects individual blobs, file share soft delete protects whole shares**.

## Try it yourself

Azure Cloud Shell. Cost: cents.

```bash
rg=rg-lab-d2snap; sa=stlabsnap$RANDOM
az group create -n $rg -l eastus
az storage account create -n $sa -g $rg --sku Standard_LRS --kind StorageV2
key=$(az storage account keys list -g $rg -n $sa --query [0].value -o tsv)
az storage share-rm create -g $rg --storage-account $sa -n team --quota 5
echo "version 1" > plan.txt
az storage file upload --account-name $sa --account-key $key -s team --source plan.txt
snap=$(az storage share snapshot --account-name $sa --account-key $key -n team --query snapshot -o tsv)
echo "version 2" > plan.txt
az storage file upload --account-name $sa --account-key $key -s team --source plan.txt
az storage file download --account-name $sa --account-key $key -s team -p plan.txt --dest v1.txt --snapshot $snap
cat v1.txt     # version 1 comes back from the snapshot
az storage account file-service-properties show -g $rg --account-name $sa --query shareDeleteRetentionPolicy
az storage share-rm delete -g $rg --storage-account $sa -n team --include snapshots --yes
az storage share-rm list -g $rg --storage-account $sa --include-deleted -o table
```

In the portal, open **File shares** > **Show deleted shares** and **Undelete** `team`; confirm `plan.txt` and its snapshot are back. Clean up: `az group delete -n $rg --yes --no-wait`.

## Key takeaways

- Share snapshots: share-level, read-only, incremental, up to 200 per share, kept up to 10 years, deleted with the share.
- Restore files from a snapshot with **Previous Versions** in Windows, the portal Restore option, a copy from the snapshot URL, or Azure Backup.
- Soft delete for file shares: account-level setting, on by default, 7 days default, 1 to 365 days, protects **shares not files**.
- Undelete from **Show deleted shares** or `az storage share-rm restore` / `Restore-AzRmStorageShare`.
- Protect the account itself with a resource lock.
