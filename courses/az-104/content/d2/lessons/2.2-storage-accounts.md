## The storage account is the container for everything

A **storage account** is an Azure Resource Manager resource (`Microsoft.Storage/storageAccounts`) that gives your data a globally unique namespace. Its name becomes part of every endpoint:

| Service | Endpoint |
|---|---|
| Blob | `https://stcontosodata01.blob.core.windows.net` |
| Data Lake Storage (hierarchical namespace) | `https://stcontosodata01.dfs.core.windows.net` |
| Azure Files | `https://stcontosodata01.file.core.windows.net` (SMB: `\\stcontosodata01.file.core.windows.net\share`) |
| Queue | `https://stcontosodata01.queue.core.windows.net` |
| Table | `https://stcontosodata01.table.core.windows.net` |
| Static website | `https://stcontosodata01.z13.web.core.windows.net` (zone part varies) |

Settings such as redundancy, network rules, encryption and the default access tier are configured **per account**, so you group data that shares those requirements into one account and create more accounts when requirements differ.

## Naming rules

- **3 to 24 characters**, **lowercase letters and numbers only**: no hyphens, underscores, dots or uppercase.
- **Globally unique** across all of Azure, because the name is a DNS label.
- Microsoft's naming abbreviation is `st`, for example `stcontosodata01`.

## Account types and performance

The **performance** tier is chosen at creation: **Standard** (HDD-backed, all services) or **Premium** (SSD-backed, one service per account type). You **cannot change the account type** later; you create a new account and copy the data.

| Account type (portal) | `--kind` / `-Kind` | Performance | Services | Redundancy (Microsoft Learn) |
|---|---|---|---|---|
| **Standard general-purpose v2** | `StorageV2` | Standard | Blob (incl. Data Lake), Files, Queue, Table | LRS, ZRS, GRS, RA-GRS, GZRS, RA-GZRS |
| **Premium block blobs** | `BlockBlobStorage` | Premium | Block and append blobs (incl. Data Lake) | LRS, ZRS |
| **Premium file shares** (now "SSD file shares") | `FileStorage` | Premium | Azure Files only, **SMB and NFS** | LRS, ZRS |
| **Premium page blobs** | `StorageV2` with a `Premium_LRS` SKU | Premium | Page blobs only (unmanaged VM disks) | LRS |
| Legacy general-purpose v1 | `Storage` | Standard | All, no access tiers | LRS, GRS, RA-GRS |
| Legacy Blob Storage | `BlobStorage` | Standard | Blobs | LRS, GRS, RA-GRS |

Guidance: use **general-purpose v2** for almost everything; use a premium type for low latency or high transaction rates; use **premium file shares** when you need **NFS** file shares. Upgrade legacy v1 and Blob Storage accounts to v2 (`az storage account update --set kind=StorageV2` or `Set-AzStorageAccount -UpgradeToStorageV2`); the upgrade can't be undone.

> **Watch out:** Learn's storage account overview lists ZRS for premium page blobs, while the redundancy and redundancy-change pages list premium page blobs as LRS only. Treat premium page blobs as LRS for the exam.

Azure Files also has **provisioned v2** SKUs such as `PremiumV2_LRS` and `StandardV2_LRS` (kind `FileStorage`) and a newer **Microsoft.FileShares** resource type for NFS shares that needs no storage account. Lesson 2.3 covers those.

## The settings on the create blade

Portal path: **Storage accounts** > **+ Create**. The tabs and what matters on each:

**Basics**: subscription, resource group, **name**, **region**, **preferred storage type** (a hint that tailors the guidance), **performance** (Standard or Premium, and for Premium the account type), **redundancy**.

**Advanced**:

- **Require secure transfer for REST API operations**: on by default. HTTP requests are rejected; SMB without encryption is rejected. Property `supportsHttpsTrafficOnly` (`--https-only`, `-EnableHttpsTrafficOnly`).
- **Allow enabling anonymous access on individual containers**: **off** by default for new accounts (`allowBlobPublicAccess = false`).
- **Enable storage account key access**: on by default (Shared Key allowed).
- **Default to Microsoft Entra authorization in the Azure portal**.
- **Minimum TLS version**: the portal sets **TLS 1.2**. Created by CLI, PowerShell or a template, the property is left unset unless you specify it. Microsoft Learn's TLS migration page states that Azure Blob Storage stopped supporting TLS 1.0 and 1.1 on **February 3, 2026**, making TLS 1.2 the minimum for all accounts. The minimum-TLS configuration page still carries the older sentence that an unset property permits TLS 1.0 or later; treat that as superseded and always set `TLS1_2` explicitly. TLS 1.3 is supported for connections but can't be set as the minimum.
- **Permitted scope for copy operations**.
- **Hierarchical namespace**: turns the account into **Azure Data Lake Storage** (directories are real objects with POSIX-like ACLs). Some blob features (for example object replication and, today, blob versioning) are not supported with it. Set it at creation; existing accounts can be upgraded through a validation and migration process, not by a simple toggle.
- **SFTP**, **NFS v3** (both need hierarchical namespace).
- **Access tier**: the **default access tier** for new block blobs, **Hot** (default), **Cool** or **Cold**. Archive can't be the default.
- **Large file shares**: historically needed for standard pay-as-you-go shares over 5 TiB; Microsoft Learn now describes it as a legacy setting, because all pay-as-you-go shares can grow to 100 TiB.

**Networking**: public network access and private endpoints (lesson 2.1).

**Data protection**: point-in-time restore, soft delete for blobs, containers and file shares (Microsoft recommends at least 7 days of retention for each), versioning, change feed.

**Encryption**: Microsoft-managed or customer-managed keys, encryption scope support for queues and tables, **infrastructure encryption** (creation time only).

## Creating an account from the command line

**Azure CLI.** Note the defaults: if you omit `--sku`, the CLI uses **`Standard_RAGRS`**; if you omit `--kind`, it uses **`StorageV2`**. Always state both.

```bash
az storage account create \
  --name stcontosodata01 \
  --resource-group rg-data-prod \
  --location eastus \
  --kind StorageV2 \
  --sku Standard_ZRS \
  --access-tier Hot \
  --https-only true \
  --min-tls-version TLS1_2 \
  --allow-blob-public-access false \
  --tags env=prod
```

**Azure PowerShell:**

```powershell
New-AzStorageAccount -ResourceGroupName rg-data-prod -Name stcontosodata01 -Location eastus `
  -SkuName Standard_ZRS -Kind StorageV2 -AccessTier Hot `
  -EnableHttpsTrafficOnly $true -MinimumTlsVersion TLS1_2 -AllowBlobPublicAccess $false
```

**ARM template** resource (validate your own copy with `python3 -m json.tool`):

```json
{
  "type": "Microsoft.Storage/storageAccounts",
  "apiVersion": "2023-05-01",
  "name": "stcontosodata01",
  "location": "eastus",
  "kind": "StorageV2",
  "sku": { "name": "Standard_ZRS" },
  "properties": {
    "accessTier": "Hot",
    "supportsHttpsTrafficOnly": true,
    "minimumTlsVersion": "TLS1_2",
    "allowBlobPublicAccess": false,
    "allowSharedKeyAccess": false,
    "isHnsEnabled": false
  }
}
```

SKU names combine performance and redundancy: `Standard_LRS`, `Standard_ZRS`, `Standard_GRS`, `Standard_RAGRS`, `Standard_GZRS`, `Standard_RAGZRS`, `Premium_LRS`, `Premium_ZRS`.

## Changing an existing account

| Change | Possible after creation? |
|---|---|
| Account type / kind (except v1 or Blob Storage to v2) | No: new account and copy |
| Performance (Standard to Premium) | No |
| Name, region | No: new account (Microsoft documents moving data to another region with a manual copy) |
| Redundancy | Often: lesson 2.2 redundancy |
| Default access tier (Hot, Cool, Cold) | Yes (re-tiering existing blobs that inherit it can incur charges) |
| Secure transfer, minimum TLS, anonymous access, Shared Key | Yes |
| Hierarchical namespace | Upgrade only, through a migration process |
| Infrastructure encryption | No |

**Portal:** account > **Settings** > **Configuration**. **CLI:** `az storage account update`. **PowerShell:** `Set-AzStorageAccount`.

## Try it yourself

Azure Cloud Shell, any browser. Cost: cents; delete at the end.

```bash
rg=rg-lab-d2acct; sa=stlabacct$RANDOM
az group create -n $rg -l eastus
az storage account create -n $sa -g $rg -l eastus
az storage account show -n $sa -g $rg --query "{kind:kind, sku:sku.name, tier:accessTier, https:enableHttpsTrafficOnly, tls:minimumTlsVersion, anon:allowBlobPublicAccess}"
```

Look at what you get when you omit `--sku`, `--kind` and `--min-tls-version`. Then fix it:

```bash
az storage account update -n $sa -g $rg --sku Standard_LRS --min-tls-version TLS1_2 --access-tier Cool
az storage account show -n $sa -g $rg --query primaryEndpoints
```

In the portal, create a second account through the wizard and compare the defaults on the **Advanced** and **Data protection** tabs before you select **Create** (you can stop at **Review + create**). Try the name `stLab-01` to see the validation message. Clean up: `az group delete -n $rg --yes --no-wait`.

## Key takeaways

- Names: 3 to 24 lowercase letters and digits, globally unique.
- General-purpose v2 for nearly everything; premium block blob, premium file shares (needed for NFS) and premium page blobs are SSD-based single-service types.
- Account type and performance are fixed; redundancy, default tier and security settings can change.
- Default access tier: Hot, Cool or Cold, never Archive.
- Secure transfer is on and anonymous access is off by default; the portal sets minimum TLS 1.2, other tools leave it unset.
- `az storage account create` defaults to `Standard_RAGRS` and `StorageV2` when you omit `--sku` and `--kind`.
- Hierarchical namespace turns the account into Data Lake Storage and limits some blob features.
