## What versioning does

With **blob versioning** enabled on a storage account, Azure Storage automatically keeps the previous state of a blob every time it is **overwritten or deleted**. Each state is a **version** with a **version ID**, which is a timestamp such as `2026-11-23T09:14:02.1234567Z`. You can read, download, tier or delete any version, and restore an older one by copying it over the current blob.

Versioning protects against **accidental or malicious overwrites and deletes of blobs**. It doesn't protect against deleting a whole **container** (use **container soft delete**) or the **account** (use a resource **lock**).

Support: standard general-purpose v2, premium block blob and legacy Blob Storage accounts. **Not** supported with a **hierarchical namespace** (Data Lake Storage).

## Current and previous versions

- A blob has **at most one current version** and any number of **previous versions**.
- **Creating** a blob creates a version that is the current version.
- **Modifying** it (Put Blob, Put Block List, Copy Blob, Set Blob Metadata) turns the current version into a **previous version** and creates a new current version.
- **Deleting** the blob without a version ID turns the current version into a previous version and leaves **no current version**. The blob disappears from normal listings, but all its versions remain. Writing the blob again creates a new current version.
- Deleting a **specific version** (by version ID) removes that version; with blob soft delete enabled it is soft-deleted instead. Deleting a previous version needs its own permission: the RBAC data action `.../blobs/deleteBlobVersion/action` (in **Storage Blob Data Owner**, not Contributor) or `x` in a SAS.
- Put Block on its own doesn't create a version (the commit with Put Block List does), and for page and append blobs Put Page and Append Block don't create versions: take snapshots if you need those states.
- A blob created **before** versioning was enabled has no version ID until its next modification.
- Microsoft recommends keeping **fewer than 1,000 versions per blob**, because large numbers slow down listing.

```text
Upload v1           current: v1
Overwrite (v2)      current: v2   previous: v1
Overwrite (v3)      current: v3   previous: v1, v2
Delete blob         current: none previous: v1, v2, v3
Copy v2 over blob   current: v4 (= v2's content)  previous: v1, v2, v3
```

## Enable versioning

**Portal:** storage account > **Data management** > **Data protection** > **Tracking** > **Enable versioning for blobs** (optionally with an automatic delete of versions older than N days, which creates a lifecycle rule).

```bash
az storage account blob-service-properties update -g rg-data-prod --account-name stcontosodata01 --enable-versioning true
```

```powershell
Update-AzStorageBlobServiceProperty -ResourceGroupName rg-data-prod -StorageAccountName stcontosodata01 -IsVersioningEnabled $true
```

ARM / Bicep: `Microsoft.Storage/storageAccounts/blobServices` property `isVersioningEnabled: true`.

**Disabling** versioning doesn't delete existing versions; it only stops new ones. You **can't disable** it while an **object replication** policy uses the account.

## Restoring a previous version

To make an older version current again, **copy that version over the base blob** (Copy Blob with the version ID as source). The version you copied from stays; the base blob becomes a new current version with that content.

- **Portal:** blob > **Versions** tab > select the version > **Make current version**.
- **Storage Explorer:** Manage History > Manage Versions > **Promote Version**.
- **CLI:**

```bash
az storage blob copy start --account-name stcontosodata01 --auth-mode login \
  --destination-container reports --destination-blob budget.xlsx \
  --source-uri "https://stcontosodata01.blob.core.windows.net/reports/budget.xlsx?versionid=<version-id>"
```

- **PowerShell:** list versions with `Get-AzStorageBlob -Container reports -Prefix budget.xlsx -IncludeVersion -Context $ctx`, then copy the chosen version over the base blob with `Copy-AzStorageBlob` or the blob client's copy methods.

The base blob must be in an online tier for the promotion copy.

## Versioning with soft delete and snapshots

Microsoft's recommended data-protection baseline enables **both versioning and blob soft delete** (plus container soft delete).

| Action | Versioning only | Versioning + blob soft delete |
|---|---|---|
| Overwrite a blob | New current version; old one is a previous version | Same; no soft-deleted snapshot is created |
| Delete a blob | Current version becomes a previous version | Same; the previous versions are not soft-deleted |
| Delete a **previous version** | Gone permanently | **Soft-deleted**; recoverable with Undelete during retention |

**Undelete Blob** restores **all** soft-deleted versions of a blob at once, and never promotes one to current; you then copy the version you want over the base blob.

**Snapshots** are the manual, older mechanism: you create a read-only copy of a blob on demand. Microsoft recommends you **stop taking snapshots** once versioning is on. If you do take one on a versioned blob, a new version is created at the same time. Object replication copies versions but **not** snapshots.

| | Snapshot | Version |
|---|---|---|
| Created | Manually (Snapshot Blob) | Automatically on every write or delete |
| Identifier | Snapshot timestamp (`?snapshot=`) | Version ID (`?versionid=`) |
| Scope | One blob | One blob |
| Restore | Copy snapshot over base blob | Copy version over base blob |

## Cost

Previous versions are billed like active data.

- If you never set a tier explicitly on the blob or its versions, you pay for **unique blocks** across the current version, previous versions and snapshots. Blocks shared between versions are billed once.
- Overwriting a whole blob with Put Blob makes every block unique, so a 1 GB blob overwritten five times costs about 6 GB.
- If you **explicitly set the tier** of a version or the blob, that object is billed at its **full content length**, even if it shares blocks.
- Soft-deleted versions are billed until permanently deleted.

Control the cost with a **lifecycle management** rule on `version`, for example tier previous versions to cool after 30 days and delete them after 365 days:

```json
{
  "rules": [
    {
      "enabled": true,
      "name": "version-cleanup",
      "type": "Lifecycle",
      "definition": {
        "filters": { "blobTypes": ["blockBlob"] },
        "actions": {
          "version": {
            "tierToCool": { "daysAfterCreationGreaterThan": 30 },
            "delete": { "daysAfterCreationGreaterThan": 365 }
          }
        }
      }
    }
  ]
}
```

## Try it yourself

Azure Cloud Shell. Cost: cents.

```bash
rg=rg-lab-d2ver; sa=stlabver$RANDOM
az group create -n $rg -l eastus
az storage account create -n $sa -g $rg --sku Standard_LRS --kind StorageV2
az storage account blob-service-properties update -g $rg --account-name $sa --enable-versioning true \
  --enable-delete-retention true --delete-retention-days 7
key=$(az storage account keys list -g $rg -n $sa --query [0].value -o tsv)
az storage container create --account-name $sa --account-key $key -n docs
for v in 1 2 3; do echo "draft $v" > plan.txt; az storage blob upload --account-name $sa --account-key $key -c docs -f plan.txt -n plan.txt --overwrite -o none; done
az storage blob list --account-name $sa --account-key $key -c docs --include v --query "[].{name:name, version:versionId, current:isCurrentVersion}" -o table
az storage blob delete --account-name $sa --account-key $key -c docs -n plan.txt
az storage blob list --account-name $sa --account-key $key -c docs --include v -o table
```

Now open the container in the portal, turn on **Show deleted blobs** (or versions), open `plan.txt` > **Versions**, pick "draft 2" and select **Make current version**. Download it to confirm. Clean up: `az group delete -n $rg --yes --no-wait`.

## Key takeaways

- Versioning keeps a previous version on every overwrite and delete; one current version, many previous versions, each with a timestamp version ID.
- Deleting a blob leaves no current version but keeps all previous versions.
- Restore by copying a version over the base blob ("Make current version" / "Promote Version").
- Not supported with hierarchical namespace; required by object replication (which blocks disabling it).
- Combine with blob soft delete: deleted previous versions become recoverable; Undelete restores all versions and promotes none.
- Versions cost money: billed for unique blocks (full length if tier set explicitly); trim them with lifecycle `version` actions.
