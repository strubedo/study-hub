## Encryption at rest is always on

Every storage account encrypts data when it is written to disk with **service-side encryption (SSE)**: **256-bit AES** (AES-GCM for uploaded objects), FIPS 140-2 compliant. It covers all services (blobs including archive, files, queues, tables, disks), all performance and access tiers, all redundancy options and both regions of a geo-redundant account, plus object metadata. **You can't disable it**, it costs nothing, and applications don't change.

What you choose is **who manages the key** that protects the data.

## Key management options

Azure Storage encrypts data with data encryption keys that are themselves protected by a root key for the account. You decide what protects that root key:

| | Microsoft-managed keys | Customer-managed keys (CMK) | Customer-provided keys (CPK) |
|---|---|---|---|
| Default | **Yes** | No | No |
| Where the key lives | Microsoft key store | **Azure Key Vault** or **Key Vault Managed HSM** | Your own store; sent with each request |
| Services | All | Blob and Azure Files; Queue and Table only if the account was created with that support | Blob Storage only |
| Who rotates | Microsoft | You (Azure Storage can pick up new versions automatically) | You |
| Scope | Account, or per encryption scope | Account, or per encryption scope | Per request |

### Customer-managed keys

With CMK, Azure Storage **wraps** the account's root encryption key with your key in Key Vault. Data is never re-encrypted when you switch or rotate; only the wrapping changes, so there is no downtime.

Requirements:

1. A key vault or Managed HSM with **soft delete** and **purge protection** both enabled. (Soft delete is always on for new vaults; **purge protection is not on by default**, so it is the setting people forget.)
2. An RSA or RSA-HSM key (2048, 3072 or 4096 bits).
3. A **managed identity** for the storage account with permission on the key: the **Key Vault Crypto Service Encryption User** role (RBAC vaults), or get, wrapKey and unwrapKey key permissions (access policy vaults).
   - Configuring CMK **while creating** the account requires a **user-assigned** managed identity (the system-assigned one doesn't exist yet).
   - On an **existing** account you can use a system-assigned or user-assigned identity.
4. The vault can be in a different region, subscription or even tenant (cross-tenant CMK uses a user-assigned identity plus a multi-tenant app).

**Key version updates:**

- Omit the key version, and Azure Storage checks the vault **daily** and uses the newest version automatically. After rotating, wait 24 hours before disabling the old version.
- Specify a version, and you must update the configuration manually after each rotation.

> **Watch out:** If the key is deleted, disabled or the identity loses access, the account's data becomes **inaccessible** until access is restored. That is also how you can deliberately revoke access to data.

**Portal:** storage account > **Security + networking** > **Encryption** > **Customer-managed keys** > select the vault and key (or enter a key URI) and the identity.

**Azure CLI** (existing account, system-assigned identity, automatic version updates):

```bash
az storage account update -n stcontosodata01 -g rg-data-prod --assign-identity
principalId=$(az storage account show -n stcontosodata01 -g rg-data-prod --query identity.principalId -o tsv)
kvid=$(az keyvault show -n kv-contoso-prod -g rg-sec-prod --query id -o tsv)
az role assignment create --assignee-object-id $principalId --assignee-principal-type ServicePrincipal \
  --role "Key Vault Crypto Service Encryption User" --scope $kvid
az storage account update -n stcontosodata01 -g rg-data-prod \
  --encryption-key-source Microsoft.Keyvault \
  --encryption-key-vault https://kv-contoso-prod.vault.azure.net \
  --encryption-key-name cmk-storage --encryption-key-version ""
```

**PowerShell:**

```powershell
$sa = Set-AzStorageAccount -ResourceGroupName rg-data-prod -Name stcontosodata01 -AssignIdentity
New-AzRoleAssignment -ObjectId $sa.Identity.PrincipalId -RoleDefinitionName "Key Vault Crypto Service Encryption User" `
  -Scope (Get-AzKeyVault -VaultName kv-contoso-prod).ResourceId
Set-AzStorageAccount -ResourceGroupName rg-data-prod -Name stcontosodata01 -KeyvaultEncryption `
  -KeyName cmk-storage -KeyVaultUri https://kv-contoso-prod.vault.azure.net -KeyVersion ""
```

An empty key version (`--encryption-key-version ""` or `-KeyVersion ""`) is how Microsoft Learn turns on automatic key version updates.

To enable purge protection on the vault: `az keyvault update -n kv-contoso-prod --enable-purge-protection true` (it can't be turned off again).

### Customer-provided keys

A client sends an AES-256 key in the `x-ms-encryption-key` header (with its SHA-256 hash) on each Blob request, **over HTTPS only**. Azure uses the key to encrypt or decrypt and then discards it, storing only the hash. Anyone reading the blob must provide the same key. Note that object replication doesn't support blobs encrypted this way.

## Encryption scopes

By default one key protects the whole account. An **encryption scope** is a named key setting **within** the account, backed by a Microsoft-managed key or a customer-managed key. You can then:

- Set a **default encryption scope on a container** when you create it, and choose whether blobs may **override** it. With override prohibited, every blob in the container uses that key.
- Upload an individual blob with a specific scope.

Use it to separate customers or departments that share one account. Facts: an encryption scope **can't be deleted** (only disabled; disabling it makes its blobs unreadable), a container's default scope must be set when the container is created, and blobs that use an encryption scope **can't be moved to the archive tier**.

```bash
az storage account encryption-scope create -g rg-data-prod --account-name stcontosodata01 \
  -n scope-customer-a --key-source Microsoft.Storage
az storage container-rm create -g rg-data-prod --storage-account stcontosodata01 -n customer-a \
  --default-encryption-scope scope-customer-a --deny-encryption-scope-override true
```

```powershell
New-AzStorageEncryptionScope -ResourceGroupName rg-data-prod -StorageAccountName stcontosodata01 `
  -EncryptionScopeName scope-customer-a -StorageEncryption
```

## Infrastructure encryption (double encryption)

**Infrastructure encryption** adds a second layer of 256-bit AES encryption at the storage infrastructure level, with a different algorithm and a separate **Microsoft-managed** key. The service-level layer can still use Microsoft-managed or customer-managed keys.

- Enable it **only at account creation** (`--require-infrastructure-encryption`, `-RequireInfrastructureEncryption`, or the **Encryption** tab). You can't turn it on or off later; to add it, create a new account and copy the data.
- Supported on general-purpose v2, premium block blob and premium page blob accounts (Azure Files has its own article).
- An encryption scope can also require infrastructure encryption; it is automatic for scopes in an account that has it.
- Use it when compliance demands double encryption. Microsoft notes that most scenarios gain nothing from it.

## Encryption in transit

Separate from encryption at rest: **secure transfer required** (HTTPS and encrypted SMB only) and **minimum TLS version** (lesson 2.2 storage accounts). Azure Files also has "require encryption in transit" settings for SMB and NFS.

## Try it yourself

Azure Cloud Shell. Cost: a few cents for the storage accounts and a key vault key.

```bash
rg=rg-lab-d2enc; sa=stlabenc$RANDOM; kv=kv-lab-enc-$RANDOM
az group create -n $rg -l eastus
az storage account create -n $sa -g $rg -l eastus --sku Standard_LRS --kind StorageV2 --require-infrastructure-encryption
az storage account show -n $sa -g $rg --query encryption
az storage account encryption-scope create -g $rg --account-name $sa -n scope-lab --key-source Microsoft.Storage
az storage container-rm create -g $rg --storage-account $sa -n lab --default-encryption-scope scope-lab --deny-encryption-scope-override true
az keyvault create -n $kv -g $rg -l eastus --enable-purge-protection true
```

Creating a vault key and switching the account to CMK needs a data-plane role on the vault (Key Vault Crypto Officer) for yourself. Follow the CLI steps above if you want to finish the exercise. Then look at the account's **Encryption** blade in the portal: infrastructure encryption shows as enabled and can't be changed.

Clean up: `az group delete -n $rg --yes --no-wait`. Because purge protection is on, the deleted vault **name** stays reserved until its soft-delete retention period ends, which is why the lab adds random digits to it.

## Key takeaways

- SSE with 256-bit AES is always on, free and can't be disabled.
- Microsoft-managed keys by default; customer-managed keys in Key Vault or Managed HSM; customer-provided keys per Blob request.
- CMK needs soft delete **and purge protection** on the vault plus a managed identity with **Key Vault Crypto Service Encryption User** (user-assigned if configured at creation).
- Omit the key version for automatic daily pickup of new versions.
- Encryption scopes give different keys per container or blob in one account; they can't be deleted and block archiving.
- Infrastructure encryption (double encryption) is chosen at creation only.
