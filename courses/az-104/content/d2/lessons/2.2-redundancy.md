## Redundancy is about hardware and disasters, not mistakes

Azure Storage always keeps multiple copies of your data. **Redundancy** decides where those copies live: in one datacenter, across availability zones, and optionally in a second region. All copies receive every write, delete and overwrite at once, so redundancy protects against **hardware and site failures, not against a user deleting or corrupting data**. For that you use soft delete, versioning, snapshots and backups (lessons 2.3).

## The six options

Within the primary region the data is replicated in one of two ways:

- **LRS (locally redundant storage)**: copies in a **single datacenter** in the primary region. Microsoft Learn's disaster recovery guidance describes this as **three copies**. Durability: **at least 99.999999999% (11 nines)** of objects over a year. Protects against drive, server and rack failure, not against the loss of the datacenter.
- **ZRS (zone-redundant storage)**: data written **synchronously across three or more availability zones** in the primary region. Durability: **at least 99.9999999999% (12 nines)**. Data stays readable and writable if a zone fails. Microsoft recommends ZRS in the primary region for high availability and for Azure Files.

The geo options add an **asynchronous** copy in the **paired secondary region**, which is fixed by the primary region and can't be chosen. Inside the secondary region the data is always kept with **LRS**.

- **GRS (geo-redundant storage)**: LRS in the primary + async copy to the secondary (kept with LRS there). Often described as six copies in total. Durability: **at least 99.99999999999999% (16 nines)**.
- **GZRS (geo-zone-redundant storage)**: ZRS in the primary + async copy to the secondary (LRS there). Durability: **at least 16 nines**. Needs a region that has both availability zones and a pair.
- **RA-GRS** and **RA-GZRS**: the same as GRS and GZRS, plus **read access to the secondary region at all times** through the secondary endpoint.

| | LRS | ZRS | GRS / RA-GRS | GZRS / RA-GZRS |
|---|---|---|---|---|
| Copies in primary | One datacenter | Three or more zones | One datacenter | Three or more zones |
| Secondary region copy | No | No | Yes (async, LRS) | Yes (async, LRS) |
| Durability (per year, Microsoft Learn) | 11 nines | 12 nines | 16 nines | 16 nines |
| Survives datacenter loss | No | Yes | Yes (after failover) | Yes |
| Survives zone outage without failover | No | Yes | No | Yes |
| Survives region loss | No | No | Yes (after failover) | Yes (after failover) |
| Read secondary without failover | No | No | RA-GRS only | RA-GZRS only |
| Archive tier supported | Yes | **No** | Yes | **No** |

Availability SLAs (99.9%, 99.99% for read-access options, lower for cool and cold tiers) are on the SLA page and in the redundancy article; don't memorise them as fixed numbers.

### Which account types support which options

| Account type | LRS | ZRS | GRS / RA-GRS | GZRS / RA-GZRS |
|---|---|---|---|---|
| Standard general-purpose v2 | Yes | Yes | Yes | Yes |
| Premium block blobs | Yes | Yes | No | No |
| Premium file shares (SSD) | Yes | Yes | No | No |
| Premium page blobs | Yes | No | No | No |
| Legacy GPv1, legacy Blob Storage | Yes | No | Yes | No |

Availability also varies by **region**: ZRS and GZRS exist only in regions with availability zones.

> **Exam tip:** **Azure Files doesn't support RA-GRS or RA-GZRS.** A standard GPv2 account can be RA-GRS for its blobs, but its file shares get only GRS-level protection and no secondary read access. SSD (premium) file shares support only LRS and ZRS.

## Reading from the secondary

With RA-GRS or RA-GZRS, every service endpoint has a twin with **`-secondary`** appended to the account name:

```text
Primary:   https://stcontosodata01.blob.core.windows.net
Secondary: https://stcontosodata01-secondary.blob.core.windows.net
```

The same account keys (and the same Entra roles) work on both. The secondary is read-only and is usually behind the primary, so applications must tolerate slightly stale data.

**Last Sync Time** tells you how far behind: every write made **before** that time is in the secondary; writes after it may not be. Check it before an unplanned failover to estimate data loss.

```bash
az storage account show -n stcontosodata01 -g rg-data-prod --expand geoReplicationStats \
  --query geoReplicationStats.lastSyncTime -o tsv
```

```powershell
(Get-AzStorageAccount -ResourceGroupName rg-data-prod -Name stcontosodata01 -IncludeGeoReplicationStats).GeoReplicationStats.LastSyncTime
```

## Failover

For geo-redundant accounts there are three kinds of failover:

| Type | Who starts it | When | Data loss | After it completes |
|---|---|---|---|---|
| **Customer-managed planned failover** | You | Both regions healthy: DR drills, proactive moves | None expected | Regions **swap**; geo-redundancy is kept |
| **Customer-managed (unplanned) failover** | You | Primary endpoints unavailable | Writes after the Last Sync Time can be lost | Secondary becomes primary; account is **LRS** in the new primary until you reconfigure geo-redundancy |
| **Microsoft-managed failover** | Microsoft | Only in a catastrophic, region-wide disaster | Possible | Same as unplanned |

Microsoft-managed failover is done for a whole region or datacenter, **never for an individual account on request**, and Microsoft tells you not to rely on it in your plans.

- Portal: account > **Data management** > **Redundancy** > **Prepare for failover**.
- CLI: `az storage account failover -g rg-data-prod -n stcontosodata01 --failover-type Planned` (omit the type for **Unplanned**, the default).
- PowerShell: `Invoke-AzStorageAccountFailover -ResourceGroupName rg-data-prod -Name stcontosodata01 -FailoverType Planned` (omit `-FailoverType` for **Unplanned**, the default; use a current Az.Storage version).

During failover the endpoint DNS records are updated to point to the new primary; applications keep using the same names.

## Changing redundancy

Microsoft documents three ways:

1. **Add or remove geo-replication or read access** (LRS ↔ GRS ↔ RA-GRS, ZRS ↔ GZRS ↔ RA-GZRS): just change the setting in the portal, CLI or PowerShell. Adding geo-redundancy incurs a one-time egress charge for the initial copy.
2. **Add or remove zone redundancy** (LRS ↔ ZRS, GRS ↔ GZRS): a **conversion**, started by you (customer-initiated, in most regions) or by a support request. No downtime or data loss, but **no SLA for completion**; it typically starts within 72 hours.
3. **Manual migration**: copy data to a new account (AzCopy and similar). Needed for a different **region**, a **premium block blob** account, or when you don't want to rehydrate archived blobs; also when you need a guaranteed finish date.

A change that involves **both** zone redundancy and geo redundancy is done in **two steps**, in either order: for example LRS → GRS (setting change) then GRS → GZRS (conversion).

```bash
# Geo / read-access change (no conversion)
az storage account update -g rg-data-prod -n stcontosodata01 --sku Standard_RAGRS
# Zone conversion (customer-initiated)
az storage account migration start -g rg-data-prod --account-name stcontosodata01 --sku Standard_ZRS --no-wait
az storage account migration show -g rg-data-prod --account-name stcontosodata01 --name default
```

```powershell
Set-AzStorageAccount -ResourceGroupName rg-data-prod -Name stcontosodata01 -SkuName Standard_RAGRS
Start-AzStorageAccountMigration -ResourceGroupName rg-data-prod -AccountName stcontosodata01 -TargetSku Standard_ZRS -AsJob
```

Limitations to remember:

- **Archive tier**: ZRS, GZRS and RA-GZRS don't support it. An account holding archived blobs must have them **moved to an account that supports archive** (or rehydrated) before converting to a zone-redundant option. Microsoft Learn's conversion page also says an LRS account containing archived blobs can be switched to GRS or RA-GRS only after rehydrating them to hot or cool, or by a manual migration, and recommends avoiding redundancy changes on accounts that hold archived data.
- An LRS account that is the **result of a failover** can't be converted to ZRS or GZRS.
- LRS → ZRS conversion isn't supported when NFSv3 for blobs is enabled, or when the account has NFS Azure file shares with public endpoints.

## Try it yourself

Azure Cloud Shell. Cost: cents (a geo-redundant account with a few KB is negligible); delete at the end.

```bash
rg=rg-lab-d2red; sa=stlabred$RANDOM
az group create -n $rg -l eastus
az storage account create -n $sa -g $rg -l eastus --kind StorageV2 --sku Standard_LRS
az storage account update -n $sa -g $rg --sku Standard_RAGRS
az storage account show -n $sa -g $rg --query "{sku:sku.name, primary:primaryLocation, secondary:secondaryLocation, endpoints:secondaryEndpoints.blob}"
az storage account show -n $sa -g $rg --expand geoReplicationStats --query geoReplicationStats
```

Right after the change, the geo-replication status and Last Sync Time may take a while to populate. In the portal, open **Redundancy** and look at the map and the **Prepare for failover** button (don't run it). Clean up: `az group delete -n $rg --yes --no-wait`.

## Key takeaways

- LRS (one datacenter, 11 nines), ZRS (three or more zones, 12 nines), GRS and GZRS (plus async secondary, 16 nines); RA- adds secondary read access via `<account>-secondary`.
- The secondary is always LRS inside its region, and the paired region can't be chosen.
- Premium block blob and premium file shares: LRS or ZRS only; premium page blobs: LRS. Azure Files never offers secondary read access.
- Archive tier only works with LRS, GRS and RA-GRS.
- Last Sync Time bounds the data loss of an unplanned failover; after it the account is LRS.
- Changing geo or read access is a setting; adding or removing zones is a conversion; region changes need a manual migration.
