## What lifecycle management does

A **lifecycle management policy** is a JSON document attached to a storage account that tells Azure Storage to **move blobs to cooler tiers** and **delete them** when they reach a given age. It can act on **current versions**, **previous versions** and **snapshots**, and it can move blobs from cool back to hot when they are read again. The policy itself is free; you pay the normal Set Blob Tier transaction charges (deletes are free).

Supported in **general-purpose v2**, **premium block blob** and legacy Blob Storage accounts, for **block blobs and append blobs**. Tiering actions apply only to block blobs in non-premium accounts; append blobs can only be deleted. Page blobs are not supported, and system containers such as `$logs` and `$web` are ignored.

## Policy structure

A policy holds up to **100 rules**. Each rule has a `name` (unique, case-sensitive), `enabled` (default true), `type` (always `Lifecycle`) and a `definition` made of **filters** and **actions**.

```json
{
  "rules": [
    {
      "enabled": true,
      "name": "logs-tiering",
      "type": "Lifecycle",
      "definition": {
        "filters": {
          "blobTypes": ["blockBlob"],
          "prefixMatch": ["logs/app"]
        },
        "actions": {
          "baseBlob": {
            "tierToCool": { "daysAfterModificationGreaterThan": 30 },
            "tierToArchive": { "daysAfterModificationGreaterThan": 90, "daysAfterLastTierChangeGreaterThan": 7 },
            "delete": { "daysAfterModificationGreaterThan": 365 }
          },
          "snapshot": {
            "delete": { "daysAfterCreationGreaterThan": 90 }
          },
          "version": {
            "tierToCold": { "daysAfterCreationGreaterThan": 30 },
            "delete": { "daysAfterCreationGreaterThan": 180 }
          }
        }
      }
    }
  ]
}
```

### Filters

| Filter | Required | Rules |
|---|---|---|
| `blobTypes` | **Yes** | `blockBlob` and/or `appendBlob` |
| `prefixMatch` | No | Up to 10 prefixes per rule. Each prefix **starts with the container name**: `logs/app` matches blobs in container `logs` whose names begin with `app`. **Case-sensitive**, no wildcards (`*` is a literal). Omit it and the rule covers every container |
| `blobIndexMatch` | No | Up to 10 blob index tag conditions, such as `{"name": "Retention", "op": "==", "value": "Short"}`. Flat-namespace accounts only |

When several filters are present they are **ANDed**. Filters can only include blobs; there is no exclude.

### Actions and which objects they apply to

| Action | `baseBlob` (current version) | `snapshot` | `version` (previous versions) |
|---|---|---|---|
| `tierToCool` | Yes | Yes | Yes |
| `tierToCold` | Yes | Yes | Yes |
| `tierToArchive` | Yes | Yes | Yes |
| `enableAutoTierToHotFromCool` | Yes (with last-access condition only) | No | No |
| `delete` | Yes | Yes | Yes |

Limits on the actions:

- Tiering doesn't apply to append blobs, page blobs or premium block blob accounts.
- `tierToArchive` doesn't work in **ZRS, GZRS or RA-GZRS** accounts or for blobs that use an **encryption scope**.
- `delete` doesn't work for blobs in an **immutable** container. With blob soft delete on, a policy delete leaves the blob soft-deleted for the retention period.
- A policy **won't delete a current version that still has previous versions or snapshots**: include `version` and `snapshot` delete actions too.
- If several actions are due on the same blob in one run, the **cheapest** one wins: delete beats tierToArchive, which beats tierToCold and tierToCool.
- Lifecycle management **can't rehydrate** from archive.

### Conditions (run conditions)

All conditions are integer days and mean **strictly greater than**:

| Condition | Measured from | Valid for |
|---|---|---|
| `daysAfterModificationGreaterThan` | Last modified time | Current version (`baseBlob`) |
| `daysAfterCreationGreaterThan` | Creation time | Current version, previous versions, snapshots |
| `daysAfterLastAccessTimeGreaterThan` | Last access time (requires **access time tracking**) | Current version |
| `daysAfterLastTierChangeGreaterThan` | Last tier change | `tierToArchive` only (keeps rehydrated blobs online for N days) |

For previous versions, creation time is when that version was first written; for snapshots, when the snapshot was taken.

> **Exam tip:** "Greater than 30" means day 31 onward. A blob modified exactly 30 days ago is **not** yet eligible for a `daysAfterModificationGreaterThan: 30` action. Exhibit questions use this.

### Last access time tracking

To base actions on reads, first **enable access time tracking** on the account. Once on, the `LastAccessTime` property updates on reads and writes (Get Blob, Put Blob), but not on Get Blob Properties, metadata or tag reads, and at most once per 24 hours per blob to limit cost (each update is billed as an "other" transaction). If tracking was never enabled, or a blob has no access time yet, the policy uses **the date tracking was enabled** instead.

```bash
az storage account blob-service-properties update -g rg-data-prod --account-name stcontosodata01 \
  --enable-last-access-tracking true
```

```powershell
Enable-AzStorageBlobLastAccessTimeTracking -ResourceGroupName rg-data-prod -StorageAccountName stcontosodata01 -PassThru
```

A typical read-based rule:

```json
{
  "rules": [
    {
      "enabled": true,
      "name": "cool-when-idle",
      "type": "Lifecycle",
      "definition": {
        "filters": { "blobTypes": ["blockBlob"], "prefixMatch": ["media/"] },
        "actions": {
          "baseBlob": {
            "enableAutoTierToHotFromCool": true,
            "tierToCool": { "daysAfterLastAccessTimeGreaterThan": 30 }
          }
        }
      }
    }
  ]
}
```

`enableAutoTierToHotFromCool` moves a blob back to hot when it is accessed, **at most once every 30 days**, and only for blobs that **this rule** moved to cool (not blobs that were already cool).

## When rules run

- After you add or change a policy, it can take **up to 24 hours** for the changes to take effect and for the first run to start.
- An active policy then processes objects **periodically**. Microsoft Learn doesn't promise a fixed schedule (in practice runs are roughly daily), and run time grows with the number of blobs. Each object is evaluated once per run; an object that becomes eligible after it was evaluated is handled in a later run. A run can take longer for accounts with many blobs.
- Disabling every rule makes the policy inactive (a running pass stops within 24 hours). Deleting the policy lets a run in progress finish.
- Watch results with the **LifecyclePolicyCompleted** Event Grid event, and metrics and logs.

So exam answers say a blob "becomes eligible" on a given day and "is moved by the next policy run", not "is moved at midnight on day 31".

## Configure a policy

**Portal:** storage account > **Data management** > **Lifecycle management** > **Add a rule** (wizard: scope, blob types, base blobs / snapshots / versions, conditions, filters) or the **Code view** tab to paste JSON. The **Enable access tracking** checkbox is on the same page.

**Azure CLI** (the policy is always written in full; partial updates aren't supported):

```bash
az storage account management-policy create -g rg-data-prod --account-name stcontosodata01 --policy @policy.json
az storage account management-policy show -g rg-data-prod --account-name stcontosodata01
```

**PowerShell:**

```powershell
$action = Add-AzStorageAccountManagementPolicyAction -BaseBlobAction TierToCool -daysAfterModificationGreaterThan 30
$action = Add-AzStorageAccountManagementPolicyAction -InputObject $action -BaseBlobAction TierToArchive -daysAfterModificationGreaterThan 90
$action = Add-AzStorageAccountManagementPolicyAction -InputObject $action -BaseBlobAction Delete -daysAfterModificationGreaterThan 365
$action = Add-AzStorageAccountManagementPolicyAction -InputObject $action -SnapshotAction Delete -daysAfterCreationGreaterThan 90
$filter = New-AzStorageAccountManagementPolicyFilter -PrefixMatch logs/app -BlobType blockBlob
$rule   = New-AzStorageAccountManagementPolicyRule -Name logs-tiering -Action $action -Filter $filter
Set-AzStorageAccountManagementPolicy -ResourceGroupName rg-data-prod -StorageAccountName stcontosodata01 -Rule $rule
```

## Working an exhibit

Apply the first policy above to an LRS account on a given day:

| Blob | Type | Days since last modified | Result on the next run |
|---|---|---|---|
| `logs/app01/a.log` | Block | 400 | **Deleted** (delete is due, and it is the cheapest action) |
| `logs/app02/b.log` | Block | 120 | **Archive** (over 90, not over 365; assumes its tier hasn't changed in the last 7 days, because the rule also sets `daysAfterLastTierChangeGreaterThan: 7`) |
| `logs/app01/c.log` | Block | 31 | **Cool** |
| `logs/app02/d.log` | Block | 30 | No change (not greater than 30) |
| `logs/web01/e.log` | Block | 200 | No change (prefix `logs/app` doesn't match `web01/...`) |
| `logs/App04/f.log` | Block | 200 | No change (prefix is case-sensitive) |
| `logs/app03/g.log` | Append | 200 | No change (`blobTypes` is blockBlob only) |

If the account were **ZRS**, `b.log` would stay where it is: archive isn't available.

## Try it yourself

Azure Cloud Shell. Cost: cents. Policy runs take up to a day, so check back tomorrow.

```bash
rg=rg-lab-d2lcm; sa=stlablcm$RANDOM
az group create -n $rg -l eastus
az storage account create -n $sa -g $rg --sku Standard_LRS --kind StorageV2
cat > policy.json <<'EOF'
{ "rules": [ { "enabled": true, "name": "lab-rule", "type": "Lifecycle",
  "definition": { "filters": { "blobTypes": ["blockBlob"], "prefixMatch": ["lab/old"] },
  "actions": { "baseBlob": { "tierToCool": { "daysAfterCreationGreaterThan": 0 } } } } } ] }
EOF
python3 -m json.tool policy.json > /dev/null && echo "valid JSON"
az storage account management-policy create -g $rg --account-name $sa --policy @policy.json
key=$(az storage account keys list -g $rg -n $sa --query [0].value -o tsv)
az storage container create --account-name $sa --account-key $key -n lab
echo x > x.txt
az storage blob upload --account-name $sa --account-key $key -c lab -f x.txt -n old/x.txt
az storage blob upload --account-name $sa --account-key $key -c lab -f x.txt -n new/x.txt
```

A creation age "greater than 0" makes the blob eligible from day 1. Within one to two days, `old/x.txt` should show **Cool** while `new/x.txt` stays **Hot**. Open **Lifecycle management** > **Code view** in the portal to see your JSON. Clean up: `az group delete -n $rg --yes --no-wait`.

## Key takeaways

- Rules = filters (`blobTypes` required, `prefixMatch` starting with the container name, `blobIndexMatch`) + actions on `baseBlob`, `snapshot`, `version`.
- Actions: `tierToCool`, `tierToCold`, `tierToArchive`, `delete`, and `enableAutoTierToHotFromCool` (last-access only, once per 30 days).
- Conditions are strictly "greater than": modification, creation, last access (needs tracking), last tier change.
- Prefixes are case-sensitive literals; multiple filters are ANDed; no excludes.
- No rehydration, no archive in ZRS/GZRS accounts, no delete in immutable containers; cheapest due action wins.
- Changes take up to 24 hours to take effect; after that the policy runs periodically (no fixed schedule is documented).
