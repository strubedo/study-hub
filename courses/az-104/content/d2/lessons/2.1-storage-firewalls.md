## Two doors into a storage account

Every storage account has a **public endpoint** (for blobs, `https://stcontosodata01.blob.core.windows.net`) that resolves to a public IP address owned by Azure. You can also add **private endpoints**, which give the account a private IP address inside one of your virtual networks. The storage firewall controls only the public endpoint. Traffic that arrives through a private endpoint is not filtered by firewall rules.

Two separate checks apply to every request:

1. **Network**: is the source allowed to reach the endpoint at all? (firewall rules, private endpoint)
2. **Authorization**: does the request carry valid credentials? (Microsoft Entra token, Shared Key, SAS)

Passing one never satisfies the other. A client on an allowed subnet still needs a role assignment or a SAS, and a perfectly valid SAS is refused (HTTP 403) when it comes from a network the firewall blocks.

> **Exam tip:** A SAS can carry its own allowed IP range (`sip`). That range only narrows who can use the token. It never opens the firewall: Microsoft Learn states that SAS IP restrictions don't grant access beyond the configured network rules.

## Public network access settings

In the portal: storage account > **Security + networking** > **Networking**, then **Manage** under public network access. The choices are:

| Portal choice | What it does | CLI / PowerShell property |
|---|---|---|
| **Enable**, **Enabled from all networks** | Any source can reach the public endpoint (still needs authorization) | default action `Allow` |
| **Enable**, **Enabled from selected networks** | Only the rules you add are allowed; everything else gets 403 | default action `Deny` |
| **Disable** | Public endpoint closed; use private endpoints | `publicNetworkAccess` = `Disabled` |
| **Secured by perimeter** | Access governed by a network security perimeter | `publicNetworkAccess` = `SecuredByPerimeter` |

New accounts accept connections from all networks by default. The most important rule on this page: **network rules have no effect until the default action is `Deny`**. Adding an IP rule to an account that still allows all networks changes nothing.

```bash
# Turn on "selected networks" (default action Deny)
az storage account update --resource-group rg-data-prod --name stcontosodata01 --default-action Deny

# Close the public endpoint entirely (private endpoints only)
az storage account update --resource-group rg-data-prod --name stcontosodata01 --public-network-access Disabled
```

```powershell
Update-AzStorageAccountNetworkRuleSet -ResourceGroupName rg-data-prod -Name stcontosodata01 -DefaultAction Deny
Set-AzStorageAccount -ResourceGroupName rg-data-prod -Name stcontosodata01 -PublicNetworkAccess Disabled
```

> **Watch out:** Changes can take up to a minute to apply. Set up the allowed networks (or the private endpoint) **before** you flip the default action to Deny, or your own applications lose access.

Firewall rules apply to **data plane** operations (reading and writing blobs, files, queues, tables), over every protocol including REST and SMB. **Control plane** operations through Azure Resource Manager (creating the account, changing its settings, listing keys) are not blocked by the storage firewall. That is why you can still open the account in the portal from home but get an authorization or network error when you browse a container's contents.

## Four kinds of rules

You can mix all four on one account.

### Virtual network rules (service endpoints)

A virtual network rule allows a **subnet**. The subnet must have a **service endpoint** for storage enabled. The portal creates the endpoint for you when you pick a subnet; with the CLI and PowerShell you enable it yourself.

- `Microsoft.Storage` reaches storage accounts **in the same region** as the virtual network (and Microsoft Learn notes it also covers RA-GRS access in the paired region).
- `Microsoft.Storage.Global` (cross-region service endpoint) reaches storage accounts **in any region**.
- A subnet can have only one of the two at a time.
- Up to **400** virtual network rules per account. The subnet can be in another subscription or another Microsoft Entra tenant (other tenants only through CLI, PowerShell or REST, not the portal).
- With a service endpoint, traffic from the subnet reaches storage with its **private** source address, so an IP rule for that subnet's public IP no longer matches.

```bash
az network vnet subnet update --resource-group rg-net-prod --vnet-name vnet-hub --name snet-app \
  --service-endpoints Microsoft.Storage
subnetid=$(az network vnet subnet show --resource-group rg-net-prod --vnet-name vnet-hub \
  --name snet-app --query id --output tsv)
az storage account network-rule add --resource-group rg-data-prod --account-name stcontosodata01 --subnet $subnetid
```

```powershell
$subnet = Get-AzVirtualNetwork -ResourceGroupName rg-net-prod -Name vnet-hub |
  Get-AzVirtualNetworkSubnetConfig -Name snet-app
Add-AzStorageAccountNetworkRule -ResourceGroupName rg-data-prod -Name stcontosodata01 -VirtualNetworkResourceId $subnet.Id
```

To add a rule, you need permission to join the subnet through a service endpoint (`Microsoft.Network/virtualNetworks/subnets/joinViaServiceEndpoint/action`). If you delete a subnet that has a rule and re-create one with the same name, the new subnet has **no** access until you add it again.

### IP network rules

IP rules allow **public** IPv4 addresses or CIDR ranges, typically an office NAT address. The restrictions are a favourite exam topic:

- **Public addresses only.** RFC 1918 ranges (10.x, 172.16–31.x, 192.168.x) are rejected.
- **IPv4.** The Learn limitations page says only IPv4 is supported for firewall rules. The current Azure CLI reference lists an `--ipv6-address` parameter on `network-rule add`, but marks it **Preview**; for the exam, think IPv4.
- **/31 and /32 ranges are not supported**: enter those as individual addresses (`203.0.113.10`, not `203.0.113.10/32`).
- **No effect on clients in the same Azure region** as the account. Those requests use private Azure addresses, so use a virtual network rule instead.
- Up to **400** IP rules per account.
- With ExpressRoute Microsoft peering, allow the NAT addresses used for the peering.

```bash
az storage account network-rule add --resource-group rg-data-prod --account-name stcontosodata01 --ip-address 203.0.113.0/27
```

```powershell
Add-AzStorageAccountNetworkRule -ResourceGroupName rg-data-prod -Name stcontosodata01 -IPAddressOrRange "203.0.113.0/27"
```

### Resource instance rules

Some Azure services cannot be placed in your subnet and have no fixed public IP, for example an Azure AI Search service, a Data Factory or a Synapse workspace. A **resource instance rule** lets one specific instance (or all instances of that type in a resource group, subscription or tenant) through the firewall. The instance must be in the **same tenant** as the account. The rule opens the network path only: the instance's managed identity still needs an Azure role (such as Storage Blob Data Reader) for data access.

```powershell
Add-AzStorageAccountNetworkRule -ResourceGroupName rg-data-prod -Name stcontosodata01 `
  -TenantId 00000000-0000-0000-0000-000000000000 `
  -ResourceId /subscriptions/<subscription-id>/resourceGroups/rg-search/providers/Microsoft.Search/searchServices/srch-contoso
```

### Exceptions (trusted services, logging, metrics)

Under **Exceptions** you can tick **Allow Azure services on the trusted services list to access this storage account**, plus read access to storage logging and metrics. The CLI and PowerShell call this setting **bypass**: `AzureServices`, `Logging`, `Metrics` or `None`. Microsoft Learn now recommends resource instance rules over the broad trusted-services exception for granting a specific resource access.

```bash
az storage account update --resource-group rg-data-prod --name stcontosodata01 --bypass AzureServices Logging Metrics
```

> **Watch out:** Trusted-service access takes precedence over other network restrictions. If you set Public network access to **Disabled** after configuring exceptions and resource instance rules, those exceptions remain in effect.

## Private endpoints: the alternative

A private endpoint is a network interface in your subnet with a private IP address that maps to one storage service (blob, file, queue, table, dfs or web, one endpoint per service). It is the right answer when:

- Clients on premises reach Azure over **site-to-site VPN or ExpressRoute private peering** with private addresses. You cannot write an IP rule for 10.50.0.0/16, but those clients can reach a private endpoint.
- You want the public endpoint **disabled** entirely.
- You need to block exfiltration to other storage accounts. A service endpoint allows the subnet to reach the service's public endpoints, while a private endpoint maps to **one** account.

Private endpoints need DNS so that `stcontosodata01.blob.core.windows.net` resolves to the private IP, usually through the private DNS zone `privatelink.blob.core.windows.net`. They cost an hourly charge plus data processing; service endpoints are free. Private endpoints are taught in depth in Domain 4.

| | Service endpoint + VNet rule | Private endpoint |
|---|---|---|
| Account address seen by client | Public IP | Private IP in your subnet |
| Reachable from on premises over VPN/ER private peering | No | Yes |
| Works with public access disabled | No | Yes |
| Scope | Subnet to the whole service (filter with the firewall) | One account, one service |
| Cost | Free | Hourly + per GB |

## Try it yourself

Runs from **Azure Cloud Shell** (Bash) in any browser on Windows, macOS or Linux. Cost: a few US cents; everything is deleted at the end.

1. Create a resource group, a virtual network and a Standard LRS account (the name must be globally unique, so add your initials and digits):

   ```bash
   rg=rg-lab-d2fw; loc=eastus; sa=stlabfw$RANDOM
   az group create --name $rg --location $loc
   az network vnet create -g $rg -n vnet-lab --address-prefixes 10.20.0.0/16 --subnet-name snet-app --subnet-prefixes 10.20.1.0/24
   az storage account create -g $rg -n $sa -l $loc --sku Standard_LRS --kind StorageV2
   # Create a container through Resource Manager (control plane), so no data role is needed
   az storage container-rm create -g $rg --storage-account $sa -n lab
   ```

2. In the portal, open the account > **Networking**. Note "Enabled from all networks".
3. Add the service endpoint and the rule, then deny everything else:

   ```bash
   az network vnet subnet update -g $rg --vnet-name vnet-lab -n snet-app --service-endpoints Microsoft.Storage
   az storage account network-rule add -g $rg --account-name $sa --vnet-name vnet-lab --subnet snet-app
   az storage account update -g $rg -n $sa --default-action Deny
   az storage account network-rule list -g $rg --account-name $sa
   ```

4. Try `az storage account network-rule add -g $rg --account-name $sa --ip-address 10.1.0.0/16` and read the error: private ranges are refused. (Output is not reproduced here; check it yourself.)
5. In the portal, open **Containers**. Microsoft Learn notes that listing containers in the portal can still succeed, because that operation is also available through the control plane. Now open the **lab** container: listing its blobs is a data plane call from your browser, which is outside the allowed subnet, so it is refused while the account settings still load.
6. Clean up: `az group delete --name $rg --yes --no-wait`

## Key takeaways

- The storage firewall filters the **public endpoint** and **data plane** only; private endpoint traffic and Resource Manager operations are not filtered by it.
- Rules do nothing until the default action is **Deny** ("Enabled from selected networks"); "Disabled" closes the public endpoint.
- Virtual network rules need a `Microsoft.Storage` (same region) or `Microsoft.Storage.Global` service endpoint on the subnet.
- IP rules: public IPv4 only, no RFC 1918, no /31 or /32 (use single addresses), no effect for clients in the same region.
- Resource instance rules admit specific Azure resources from the same tenant; their managed identity still needs a data role.
- Use a **private endpoint** for on-premises clients over VPN or ExpressRoute private peering, or when public access must be off.
- A SAS `sip` range never bypasses the firewall; both checks must pass.
