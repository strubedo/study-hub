## What object replication does

**Object replication** copies **block blobs** asynchronously from a container in a **source** account to a container in a **destination** account, according to rules you define. Unlike GRS, you choose the destination account (any region, any subscription, even another Microsoft Entra tenant), you choose which containers and which blobs by prefix, and the destination copy is readable at all times.

Typical uses:

- **Lower read latency**: keep a copy near users or compute in another region.
- **Compute efficiency**: process the same data set in several regions.
- **Data distribution**: process data once at a central site and fan the results out.
- **Cost optimization**: replicate, then tier the destination copy to cool, cold or archive with lifecycle management.

It is **not** a backup: deletes replicate too (as the version state described below), and the copy is not point-in-time.

## Prerequisites

| Requirement | Source account | Destination account |
|---|---|---|
| Account type | General-purpose v2 or premium block blob (both the same family) | General-purpose v2 or premium block blob |
| **Blob versioning** | **Enabled** | **Enabled** |
| **Change feed** | **Enabled** | Not required |
| Hierarchical namespace | Not supported | Not supported |
| Containers | Must exist before you add the rule | Must exist before you add the rule |

Other limits and behaviour from Microsoft Learn:

- **Block blobs only.** Append blobs and page blobs are not replicated.
- **Blob snapshots are not replicated.** Blob versions are: the current version and previous versions are copied (they get new version IDs at the destination).
- Blobs encrypted with a **customer-provided key** are not supported. Microsoft-managed and customer-managed keys are fine.
- **Customer-managed failover** isn't supported on either account in a policy.
- Replication fails for blobs moved to the **archive** tier on either side; rehydrating a source blob doesn't trigger replication until the blob changes again.
- Changing the tier of a source blob doesn't change the destination blob's tier.
- While a policy is active you **can't disable versioning** on those accounts.
- Immutability policies at the destination can cause replication of updates or deletes to fail.

## Policies and rules

- A **replication policy** names one source account and one destination account. There is **one policy per source and destination pair**.
- Microsoft Learn currently states that a source account can replicate to **no more than two** destination accounts (one policy each), and an account can be the destination of no more than two policies.
- A policy holds **rules**, up to **1,000** per policy. Each rule maps **one source container to one destination container**; a container can be in only one rule.
- A rule can have **filters**: one or more **prefixes** (`prefixMatch`), and a **copy scope**. By default only blobs created **after** the rule are copied; you can choose to copy **everything**, or blobs created after a **custom date and time** (`minCreationTime`).
- Optionally, blob index tags can be replicated as well.

After you create a policy, the **destination container becomes read-only for writes**: uploads to it fail with **409 Conflict**. Reads and deletes are still allowed. To write there again you must delete the rule or the whole policy.

Replication is **asynchronous**. Azure Storage reads the source's change feed periodically and copies writes and deletes; latency depends on blob size and load, so the destination is not instantly in sync. An optional **priority replication** feature adds an SLA for most objects within 15 minutes when both accounts are on the same continent.

### The policy ID handshake

The policy is created on the **destination** account first. Azure assigns a **policy ID**, and the same policy (same ID, same rules) must then be created on the **source** account. Replication happens only when both sides hold the matching policy.

- In the **portal**, you work from the **source** account (Data management > **Object replication** > **Create replication rules**); the portal creates the destination side for you. Up to 10 container pairs per policy in the portal; use a JSON file for more.
- With **CLI or PowerShell**, you create it on the destination, then on the source using the ID or the policy object.
- **Cross-tenant**: someone with rights on the destination creates the policy, downloads the JSON definition and hands it to an administrator in the source tenant, who uploads it.

### Cross-tenant replication setting

The account property **AllowCrossTenantReplication** controls whether policies may involve accounts in different Microsoft Entra tenants. For accounts created on or after **December 15, 2023**, it defaults to **false** (the CLI help also says false for new accounts). Set it to true on both accounts only when you really need cross-tenant replication. When it is false, policies must use **full resource IDs** for the accounts, not just names.

```bash
az storage account update -g rg-data-prod -n stcontososrc01 --allow-cross-tenant-replication false
```

## Configure it from the command line

**Azure CLI:**

```bash
# 1. Versioning on both, change feed on the source
az storage account blob-service-properties update -g rg-data-prod --account-name stcontososrc01 \
  --enable-versioning true --enable-change-feed true
az storage account blob-service-properties update -g rg-data-dr --account-name stcontosodst01 \
  --enable-versioning true

# 2. Policy and first rule on the DESTINATION account. Use full resource IDs: when
#    AllowCrossTenantReplication is false (the default for new accounts), Azure needs them
#    to confirm both accounts are in the same tenant.
srcId=$(az storage account show -g rg-data-prod -n stcontososrc01 --query id -o tsv)
dstId=$(az storage account show -g rg-data-dr -n stcontosodst01 --query id -o tsv)
az storage account or-policy create -g rg-data-dr --account-name stcontosodst01 \
  --source-account $srcId --destination-account $dstId \
  --source-container reports --destination-container reports-replica --prefix-match 2026/

# 3. Same policy on the SOURCE account, piping the destination policy in
az storage account or-policy show -g rg-data-dr --account-name stcontosodst01 --policy-id <policy-id> |
  az storage account or-policy create -g rg-data-prod --account-name stcontososrc01 --policy "@-"
```

**PowerShell:**

```powershell
Update-AzStorageBlobServiceProperty -ResourceGroupName rg-data-prod -StorageAccountName stcontososrc01 `
  -EnableChangeFeed $true -IsVersioningEnabled $true
Update-AzStorageBlobServiceProperty -ResourceGroupName rg-data-dr -StorageAccountName stcontosodst01 `
  -IsVersioningEnabled $true
$srcId = (Get-AzStorageAccount -ResourceGroupName rg-data-prod -Name stcontososrc01).Id
$dstId = (Get-AzStorageAccount -ResourceGroupName rg-data-dr -Name stcontosodst01).Id
$rule = New-AzStorageObjectReplicationPolicyRule -SourceContainer reports `
  -DestinationContainer reports-replica -PrefixMatch 2026/
$destPolicy = Set-AzStorageObjectReplicationPolicy -ResourceGroupName rg-data-dr `
  -StorageAccountName stcontosodst01 -PolicyId default -SourceAccount $srcId `
  -DestinationAccount $dstId -Rule $rule
Set-AzStorageObjectReplicationPolicy -ResourceGroupName rg-data-prod -StorageAccountName stcontososrc01 `
  -InputObject $destPolicy
```

**Policy definition file** (the JSON you hand to the other tenant; `policyId` "default" tells Azure to assign one on the destination):

```json
{
  "properties": {
    "policyId": "default",
    "sourceAccount": "/subscriptions/00000000-0000-0000-0000-000000000000/resourceGroups/rg-data-prod/providers/Microsoft.Storage/storageAccounts/stcontososrc01",
    "destinationAccount": "/subscriptions/00000000-0000-0000-0000-000000000000/resourceGroups/rg-data-dr/providers/Microsoft.Storage/storageAccounts/stcontosodst01",
    "rules": [
      {
        "ruleId": "",
        "sourceContainer": "reports",
        "destinationContainer": "reports-replica",
        "filters": {
          "prefixMatch": ["2026/"],
          "minCreationTime": "2026-01-01T00:00:00Z"
        }
      }
    ]
  }
}
```

You can check the replication status of each blob on the source account (portal blob properties, client libraries) to see whether it completed or failed.

## Object replication versus geo-redundancy

| | GRS / GZRS | Object replication |
|---|---|---|
| Granularity | Whole account | Chosen containers and prefixes |
| Destination | Fixed paired region, managed by Azure | Any account you choose |
| Read the copy | Only with RA-GRS / RA-GZRS | Always (it is an ordinary account) |
| Blob types | All data including files, queues, tables | Block blobs only |
| Failover | Account failover | None; point apps at the other account |
| Requirements | None | Versioning both sides, change feed on the source |

## Try it yourself

Azure Cloud Shell. Two small accounts; cost a few cents. Replication can take a few minutes.

```bash
rg=rg-lab-d2or; src=stlabsrc$RANDOM; dst=stlabdst$RANDOM
az group create -n $rg -l eastus
az storage account create -n $src -g $rg -l eastus --sku Standard_LRS --kind StorageV2
az storage account create -n $dst -g $rg -l westus --sku Standard_LRS --kind StorageV2
az storage account blob-service-properties update -g $rg --account-name $src --enable-versioning true --enable-change-feed true
az storage account blob-service-properties update -g $rg --account-name $dst --enable-versioning true
az storage container-rm create -g $rg --storage-account $src -n reports
az storage container-rm create -g $rg --storage-account $dst -n reports-replica
```

Now use the **portal**: open the source account > **Object replication** > **Create replication rules**, pick the destination account and the container pair, and save. Upload a small file into `reports` (portal **Upload**), wait a few minutes and look in `reports-replica`. Try uploading straight into `reports-replica` and note the failure. Clean up: `az group delete -n $rg --yes --no-wait`.

## Key takeaways

- Asynchronous copy of **block blobs** between containers in two accounts (GPv2 or premium block blob).
- Needs **versioning on both** accounts and **change feed on the source**; no hierarchical namespace; snapshots aren't copied.
- One policy per account pair, up to 1,000 rules, one container pair per rule, optional prefix and creation-time filters.
- Create the policy on the destination, then the source with the same policy ID (the portal does both from the source).
- The destination container rejects writes while a rule targets it.
- `AllowCrossTenantReplication` defaults to false for accounts created since December 15, 2023.
