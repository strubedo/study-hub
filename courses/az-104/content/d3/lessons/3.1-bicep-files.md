## Bicep in one paragraph

**Bicep** is a domain-specific language that compiles to ARM template JSON. Everything an ARM template can do, Bicep can do, with less punctuation: no `[ ]` expressions, no `parameters('x')` wrappers, no hand-written `dependsOn` in most cases. When you deploy a `.bicep` file, the Azure CLI or Azure PowerShell transpiles it to JSON first and Resource Manager deploys that JSON, so deployment scopes, modes, what-if and history work exactly as for ARM templates. The Azure CLI installs the Bicep CLI automatically when needed; Azure PowerShell needs the Bicep CLI installed separately (Cloud Shell has both).

## The building blocks

```bicep
targetScope = 'resourceGroup'

@description('Deployment environment')
@allowed([
  'dev'
  'prod'
])
param environment string = 'dev'

@minLength(3)
@maxLength(11)
param prefix string

@secure()
param adminPassword string

param location string = resourceGroup().location

var storageName = '${prefix}${uniqueString(resourceGroup().id)}'
var isProd = environment == 'prod'

resource vnet 'Microsoft.Network/virtualNetworks@2025-01-01' = {
  name: 'vnet-app-${environment}'
  location: location
  properties: {
    addressSpace: {
      addressPrefixes: [
        '10.20.0.0/16'
      ]
    }
    subnets: [
      {
        name: 'snet-app'
        properties: {
          addressPrefix: '10.20.1.0/24'
        }
      }
    ]
  }
}

resource nic 'Microsoft.Network/networkInterfaces@2025-01-01' = {
  name: 'nic-app-01'
  location: location
  properties: {
    ipConfigurations: [
      {
        name: 'ipconfig1'
        properties: {
          privateIPAllocationMethod: 'Dynamic'
          subnet: {
            id: vnet.properties.subnets[0].id
          }
        }
      }
    ]
  }
}

output nicId string = nic.id
output storageNameOut string = storageName
```

| Element | Syntax | ARM JSON equivalent |
|---|---|---|
| Scope | `targetScope = 'resourceGroup'` (default), `'subscription'`, `'managementGroup'`, `'tenant'` | The `$schema` URL plus the deployment command |
| Parameter | `param name type = default` | `parameters` section |
| Decorators | `@allowed([...])`, `@minLength()`, `@maxLength()`, `@minValue()`, `@maxValue()`, `@secure()`, `@description()`, `@metadata()` | `allowedValues`, `minLength`, `type: securestring`, `metadata.description` |
| Variable | `var name = expression` (type inferred) | `variables` section |
| Resource | `resource symbolicName 'Namespace/type@apiVersion' = { ... }` | An object in `resources` |
| Output | `output name type = value` | `outputs` section |
| Interpolation | `'vm-${environment}-01'` | `[concat('vm-', parameters('environment'), '-01')]` or `format()` |
| Property access | `nic.id`, `vnet.properties.subnets[0].id` | `resourceId()` / `reference()` |

Strings use **single quotes**. In the multi-line form used throughout this lesson, arrays and objects have one item or property per line and no commas; the single-line form separates items with commas (`[ 'dev', 'prod' ]`, `{ name: 'Standard_LRS', tier: 'Standard' }`), and you can mix the two. Comments are `//` or `/* */`.

The **symbolic name** (`vnet`, `nic`) is how you refer to a resource inside the file; it isn't the Azure resource name, which comes from `name:`.

### Implicit dependencies

`nic` uses `vnet.properties.subnets[0].id`, so Bicep knows the NIC depends on the VNet and emits a `dependsOn` in the compiled JSON. You only write `dependsOn: [ vnet ]` when there is no property reference but order still matters. This is the biggest source of ARM template bugs that Bicep removes.

> **Exam tip:** In an exhibit, trace references between symbolic names to find the deployment order. A resource that never references another can deploy in parallel with it.

### Decorators

Decorators sit on the line(s) above a `param` (some also apply to `var`, `resource`, `module` and `output`). `@secure()` works on `string` and `object` parameters and keeps the value out of logs and the deployment history. Don't give a secure parameter a hard-coded default (the Bicep linter flags it); supply the value at deployment time or from Key Vault.

## Loops and conditions

A `for` expression creates several resources:

```bicep
param count int = 3

resource logs 'Microsoft.Storage/storageAccounts@2025-06-01' = [for i in range(1, count): {
  name: 'stcontosologs0${i}'
  location: resourceGroup().location
  sku: {
    name: 'Standard_LRS'
  }
  kind: 'StorageV2'
}]
```

`range(start, count)` returns `count` integers beginning at `start`, so `range(1, 3)` is `[1, 2, 3]`: three accounts ending in 01, 02 and 03. You can also loop over an array (`for site in sites:`), or get the index as well (`for (site, i) in sites:`). Add `@batchSize(2)` above the resource to deploy serially in batches.

An `if` expression makes a resource conditional:

```bicep
param deployPublicIp bool = false

resource pip 'Microsoft.Network/publicIPAddresses@2025-01-01' = if (deployPublicIp) {
  name: 'pip-app-01'
  location: resourceGroup().location
  sku: {
    name: 'Standard'
  }
  properties: {
    publicIPAllocationMethod: 'Static'
  }
}
```

Bicep also has the ternary operator for values: `sku: { name: isProd ? 'Standard_GRS' : 'Standard_LRS' }`.

## existing, modules and scope

Refer to a resource that's already deployed, without redeploying it, with `existing`:

```bicep
resource kv 'Microsoft.KeyVault/vaults@2024-11-01' existing = {
  name: 'kv-contoso-prod'
  scope: resourceGroup('rg-security-prod')
}

output vaultUri string = kv.properties.vaultUri
```

A **module** deploys another Bicep file as a nested deployment and passes parameters to it:

```bicep
module network './network.bicep' = {
  name: 'networkDeploy'
  params: {
    location: location
    vnetName: 'vnet-hub'
  }
}

output hubId string = network.outputs.vnetId
```

The module's `name` is the deployment name you see in the history. A module can target a different scope with `scope:`, for example a resource group in a subscription-scope file:

```bicep
targetScope = 'subscription'

resource rg 'Microsoft.Resources/resourceGroups@2025-04-01' = {
  name: 'rg-web-prod'
  location: 'eastus'
}

module web './web.bicep' = {
  name: 'webDeploy'
  scope: rg
  params: {
    location: rg.location
  }
}
```

## Reading a Bicep file: checklist

1. **Scope**: `targetScope` (default resource group). It decides which `az deployment ... create` you run.
2. **Parameters**: which have no default (must be supplied), which are constrained, which are secure.
3. **Variables**: evaluate interpolations and ternaries with the parameter values.
4. **Resources**: type, API version, name, conditions and loops; count the instances.
5. **Dependencies**: symbolic references, explicit `dependsOn`, modules.
6. **Outputs**: what the deployment returns.

## Tools

**Portal:** the portal can't edit Bicep, but **Deploy a custom template** accepts the compiled JSON, and you can export Bicep from a resource group (see the export lesson).

**Azure CLI:** `az bicep build --file main.bicep` compiles to `main.json`; `az bicep version` and `az bicep upgrade` manage the Bicep CLI; `az bicep lint --file main.bicep` reports linter warnings.

**Azure PowerShell:** `bicep build main.bicep` (Bicep CLI) and `New-AzResourceGroupDeployment -TemplateFile ./main.bicep` (compiles on the fly).

Visual Studio Code with the Bicep extension gives IntelliSense for every resource type and API version, on Windows, macOS and Linux.

## Try it yourself

Azure Cloud Shell (Bash). Cost: a few cents at most for the two empty storage accounts, nothing for the compile steps.

```bash
rg=rg-lab-d3bicep
az group create -n $rg -l eastus
cat > main.bicep <<'EOF'
@allowed([
  'dev'
  'prod'
])
param environment string = 'dev'
param count int = 2

var suffix = take(uniqueString(resourceGroup().id), 6)

resource st 'Microsoft.Storage/storageAccounts@2025-06-01' = [for i in range(1, count): {
  name: 'stlab${suffix}${i}'
  location: resourceGroup().location
  sku: {
    name: environment == 'prod' ? 'Standard_ZRS' : 'Standard_LRS'
  }
  kind: 'StorageV2'
}]

output names array = [for i in range(0, count): st[i].name]
EOF
az bicep build --file main.bicep        # writes main.json
grep -c copyIndex main.json             # the loop became an ARM copy loop
az deployment group create -g $rg --template-file main.bicep --parameters environment=dev count=2 --query properties.outputs
```

Open `main.json` and match each Bicep line to the JSON it produced: the `copy` element, the `[if(equals(...))]` expression for the SKU, and the `dependsOn` (none here). Try `--parameters environment=test` and read the validation error. Clean up: `az group delete -n $rg --yes --no-wait`.

## Key takeaways

- Bicep compiles to ARM JSON; scopes, modes, what-if and history are the same.
- `param`, `var`, `resource symbolic 'type@apiVersion'`, `output`, `module`, `existing`, `targetScope`.
- Decorators replace JSON constraints: `@allowed`, `@secure`, `@minLength`/`@maxLength`, `@minValue`/`@maxValue`, `@description`, `@batchSize`.
- `'${x}'` interpolation replaces `concat()`; symbolic references (`vnet.id`) create implicit dependencies.
- `[for i in range(start, count): {...}]` loops; `= if (condition) {...}` conditions; `range(1, 3)` is 1, 2, 3.
- `existing` reads a resource without deploying it; modules are nested deployments with their own name and optional scope.
