## Retirement first

Microsoft Learn (checked November 2026) carries this notice on every Azure Disk Encryption page: **Azure Disk Encryption is scheduled for retirement on September 15, 2028.** Until that date you can keep using it without disruption. On September 15, 2028, ADE-enabled workloads keep running, but **encrypted disks will fail to unlock after VM reboots**, causing service disruption. Microsoft says to use **encryption at host** for new VMs (or Confidential VM sizes with OS disk encryption for confidential workloads), and that all ADE-enabled VMs, including backups, must be migrated to encryption at host before the retirement date. Migration isn't in place: you create new disks and VMs.

The AZ-104 objective (written in 2023) still says "Configure Azure Disk Encryption", so you need to know how ADE works, what it requires and how it differs from the other options. For any new design, the answer Microsoft wants is encryption at host.

## The encryption options for VM disks

| Option | Where encryption happens | Covers | Keys | Notes |
|---|---|---|---|---|
| **Server-side encryption (SSE)** with platform-managed keys | Azure Storage, when data is persisted | OS and data disks, snapshots, images | Microsoft-managed | **Always on**, no cost, 256-bit AES. Doesn't cover temp disks or host caches |
| **SSE with customer-managed keys (CMK)** | Azure Storage | Same as above | Yours, in Key Vault or Managed HSM, through a **disk encryption set** | Purge protection required on the vault; key rotation and revocation are under your control |
| **Encryption at host** | The VM host (the server the VM runs on) | Adds **temp disks, ephemeral OS disks and OS/data disk caches**; data flows encrypted to storage | Temp and ephemeral: platform-managed. Caches: same key type as the disk (PMK or CMK) | End to end; no guest CPU used; subscription feature `EncryptionAtHost` must be registered; VM size must support it |
| **Azure Disk Encryption (ADE)** | **Inside the guest OS**: BitLocker on Windows, DM-Crypt on Linux | OS and data volumes; temp disk on Windows with `VolumeType All` | Disk encryption key (secret) in **Key Vault**, optionally wrapped with a key encryption key (KEK) | Retiring September 15, 2028. Uses guest CPU. Extension-based |
| **Confidential disk encryption** | Bound to the VM's vTPM on confidential VM sizes | OS disk | Platform or customer key | For confidential computing |

The two that look alike on the exam are **SSE** (Azure encrypts at rest, transparent to the VM, always on) and **ADE** (the guest encrypts its own volumes, visible as BitLocker or dm-crypt inside the OS).

> **Exam tip:** "Encrypt the temp disk and disk caches", "end-to-end", "no performance impact on the VM", "no agent in the guest": encryption at host. "Encrypt volumes with BitLocker and store keys in Key Vault": ADE.

## ADE requirements

From the ADE overview and prerequisites pages:

- **Key Vault in the same region and subscription as the VM** (Learn also says same tenant). Secrets mustn't cross regions.
- The vault must have the **disk encryption** access policy setting enabled (`--enabled-for-disk-encryption`, `-EnabledForDiskEncryption`). Soft delete must be on (it is on by default for new vaults).
- **Not supported** on Basic VMs, the A series, v6, v7 and newer series, or VMs with **less than 2 GB of memory**. Gen1 and Gen2 are both supported.
- Windows: any version that supports BitLocker; group policy mustn't force TPM protectors; ADE doesn't store recovery keys.
- Linux: supported distributions and versions only, with extra memory needs for OS disk encryption on some distributions; disabling encryption is supported for data volumes only.
- The VM needs outbound access to Key Vault and the Azure extension repository.
- Can't be combined with encryption at host on the same VM, can't be used on ephemeral OS disks or on shared disks.
- The current ADE release doesn't need a Microsoft Entra app; VMs encrypted with the older Entra-app version must keep using that method.

## Enable ADE

**Portal:** VM > **Settings** > **Disks** > **Additional settings** > **Disks to encrypt** (OS disk, or OS and data disks), choose or create the key vault and optionally a key, then **Save**. The VM must be running.

**Azure CLI:**

```bash
az keyvault create -g rg-security-prod -n kv-contoso-prod -l eastus --enabled-for-disk-encryption
az vm encryption enable -g rg-app-prod -n vm-app-01 \
  --disk-encryption-keyvault kv-contoso-prod --volume-type All
# optional KEK
az keyvault key create --vault-name kv-contoso-prod -n kek-ade --protection software
az vm encryption enable -g rg-app-prod -n vm-app-01 --disk-encryption-keyvault kv-contoso-prod \
  --key-encryption-key kek-ade --key-encryption-keyvault kv-contoso-prod --volume-type All
az vm encryption show -g rg-app-prod -n vm-app-01
```

`--disk-encryption-keyvault` takes the vault name (same resource group) or its full resource ID; `--volume-type` is `All`, `OS` or `Data`.

**Azure PowerShell:**

```powershell
$kv = Get-AzKeyVault -VaultName kv-contoso-prod -ResourceGroupName rg-security-prod
Set-AzVMDiskEncryptionExtension -ResourceGroupName rg-app-prod -VMName vm-app-01 `
  -DiskEncryptionKeyVaultUrl $kv.VaultUri -DiskEncryptionKeyVaultId $kv.ResourceId -VolumeType All
Get-AzVMDiskEncryptionStatus -ResourceGroupName rg-app-prod -VMName vm-app-01
Disable-AzVMDiskEncryption -ResourceGroupName rg-app-prod -VMName vm-app-01 -VolumeType Data
```

Take a snapshot or a backup before encrypting. Never decrypt an ADE volume directly with BitLocker inside the guest; use the Azure commands.

ADE also affects other operations: moving an ADE VM to another subscription requires disabling encryption first (moving it to another resource group requires it to be deallocated), and Azure Backup and Site Recovery need extra configuration for ADE VMs.

## Encryption at host (the replacement)

```bash
az feature register --namespace Microsoft.Compute --name EncryptionAtHost
az feature show --namespace Microsoft.Compute --name EncryptionAtHost --query properties.state
az provider register --namespace Microsoft.Compute

az vm create -g rg-app-prod -n vm-app-02 --image Ubuntu2204 --size Standard_D2s_v5 \
  --generate-ssh-keys --encryption-at-host true

# existing VM: deallocate, update, start
az vm deallocate -g rg-app-prod -n vm-app-01
az vm update -g rg-app-prod -n vm-app-01 --set securityProfile.encryptionAtHost=true
az vm start -g rg-app-prod -n vm-app-01
```

```powershell
Register-AzProviderFeature -FeatureName EncryptionAtHost -ProviderNamespace Microsoft.Compute
$vm = Get-AzVM -ResourceGroupName rg-app-prod -Name vm-app-01
Stop-AzVM -ResourceGroupName rg-app-prod -Name vm-app-01 -Force
Update-AzVM -ResourceGroupName rg-app-prod -VM $vm -EncryptionAtHost $true
Start-AzVM -ResourceGroupName rg-app-prod -Name vm-app-01
```

Restrictions Learn lists: it can't be enabled on VMs or scale sets that **currently have or ever had** ADE enabled; ADE can't be enabled on disks with encryption at host; existing VMs must be **deallocated** to turn it on; on existing scale sets only new instances are encrypted; the VM size must support it (resizing checks this).

**Portal:** at creation, **Disks** tab > **Encryption at host**. For an existing VM, stop (deallocate) it, then **Disks** > **Additional settings** > **Encryption at host** > **Yes**.

## Try it yourself

Azure Cloud Shell (Bash). Cost: under a dollar if you delete it within an hour. The lab uses encryption at host because ADE is retiring; the commented lines show ADE for comparison if you want to try it on a separate VM.

```bash
rg=rg-lab-d3enc; az group create -n $rg -l eastus
az feature register --namespace Microsoft.Compute --name EncryptionAtHost
az feature show --namespace Microsoft.Compute --name EncryptionAtHost --query properties.state -o tsv  # wait for Registered
az provider register --namespace Microsoft.Compute
az vm create -g $rg -n vm-enc-01 --image Ubuntu2204 --size Standard_D2s_v5 \
  --generate-ssh-keys --public-ip-address "" --encryption-at-host true
az vm show -g $rg -n vm-enc-01 --query securityProfile.encryptionAtHost
az disk list -g $rg --query "[].{name:name,encryption:encryption.type}" -o table
# ADE comparison (separate VM, not combinable with encryption at host):
# kv=kv-lab-$RANDOM; az keyvault create -g $rg -n $kv -l eastus --enabled-for-disk-encryption
# az vm create -g $rg -n vm-ade-01 --image Ubuntu2204 --size Standard_D2s_v5 --generate-ssh-keys --public-ip-address ""
# az vm encryption enable -g $rg -n vm-ade-01 --disk-encryption-keyvault $kv --volume-type Data
```

The disk list shows `EncryptionAtRestWithPlatformKey`: SSE is always on regardless. Clean up: `az group delete -n $rg --yes --no-wait` (a key vault you created goes to soft-deleted state; purge it with `az keyvault purge -n <name>` if you want the name back).

## Key takeaways

- ADE retires **September 15, 2028**; after that, ADE disks fail to unlock on reboot. Microsoft recommends **encryption at host** for new VMs.
- SSE (always on, at rest in storage) vs encryption at host (adds temp disk, ephemeral OS disk and caches, at the host) vs ADE (BitLocker/DM-Crypt inside the guest, keys in Key Vault).
- ADE needs a Key Vault in the same region and subscription with disk encryption enabled; no Basic, A-series, v6+ sizes or VMs under 2 GB.
- `az vm encryption enable --disk-encryption-keyvault ... --volume-type All|OS|Data`; `Set-AzVMDiskEncryptionExtension`.
- Encryption at host needs the `EncryptionAtHost` feature registered, a supporting size, deallocation for existing VMs, and no ADE history on the VM.
