## Serverless containers with an orchestrator underneath

**Azure Container Apps** runs containerized apps, APIs, background workers and jobs on a managed platform built on Kubernetes, KEDA, Dapr and Envoy, without exposing the Kubernetes API. Compared with ACI you get HTTPS ingress, revisions with traffic splitting, event-driven autoscaling including **scale to zero**, built-in secrets, managed identities and service discovery between apps. Compared with AKS you give up direct cluster access in exchange for not running a cluster.

## Environments

Every container app lives in a **Container Apps environment** (`Microsoft.App/managedEnvironments`), a secure boundary around a group of apps and jobs. Apps in the same environment share a virtual network and a logging destination (by default a Log Analytics workspace) and can call each other by name. Use separate environments when apps must never share compute, or to separate test from production.

When you create an environment you either let Azure create a virtual network with limited networking features, or bring your own subnet for full control (private endpoints, user-defined routes, NAT gateway).

Learn describes two **environment types** today:

| Environment type | Plans | Notes |
|---|---|---|
| **Workload profiles** (default, "v2") | **Consumption** and **Dedicated** | Every environment includes a **Consumption** profile. You can add **Dedicated** workload profiles (for example D4–D32 general purpose, E4–E32 memory optimized, GPU) billed per profile instance plus a plan management fee. A **Flexible** profile is in preview |
| **Consumption only** (legacy, "v1") | Consumption | Max 2 vCPU and 4 GiB per app; Learn recommends workload profiles environments for new deployments |

The **Consumption** plan is serverless: apps scale in and out on demand, can scale to zero, and you pay for the vCPU-seconds and GiB-seconds your replicas use. **Dedicated** profiles give you reserved, single-tenant compute with larger sizes and more predictable cost for steady workloads; several apps can share one profile.

On the Consumption profile, a replica's containers must add up to one of the allowed CPU/memory pairs, from **0.25 vCPU / 0.5 GiB** up to **4 vCPU / 8 GiB** in steps of 0.25 vCPU and 0.5 GiB (memory is always twice the vCPU number).

> **Watch out:** Learn says Container Apps environments are **deleted automatically** after 90 days idle (no active apps or jobs) or after 90 days in a failed state. A forgotten lab environment disappears; a forgotten production environment with no apps does too.

## Apps, revisions and revision modes

A **revision** is an immutable snapshot of a container app's template. Changes fall into two scopes:

| Change scope | Examples | Effect |
|---|---|---|
| **Revision-scope** (`properties.template`) | Image or tag, container CPU/memory, environment variables, **scale rules**, revision suffix | Creates a **new revision** |
| **Application-scope** (`properties.configuration`) | **Secret values**, revision mode, **ingress** settings and **traffic split**, registry credentials, Dapr settings | Applied to all revisions; **no new revision** (restart revisions to pick up new secret values) |

Revision modes:

- **Single** (default): one active revision. A new revision is provisioned, scaled and health-checked, then receives 100% of traffic, and the old one is deactivated (zero-downtime update). If the new revision fails, traffic stays on the old one.
- **Multiple**: several revisions active at once; you decide how traffic is split by weight and when old revisions are deactivated. Used for blue-green and canary releases.
- **Labels** (preview): named pointers such as `staging` or `prod` assigned to revisions.

**Traffic splitting** (multiple mode, ingress enabled) assigns percentage weights that must total 100, by revision name or label, for example `az containerapp ingress traffic set -n ca-api -g rg-aca-prod --revision-weight ca-api--v1=80 ca-api--v2=20`. A **label** gives a revision its own stable URL for testing without sending it production traffic. Container Apps keeps up to 100 inactive revisions, which you can reactivate to roll back.

## Ingress

Ingress is application-scope and optional:

- **External**: reachable from the internet (or from the VNet if the environment is internal) through the environment's public endpoint, HTTPS on 443 with an automatic `https://<app>.<unique-env-id>.<region>.azurecontainerapps.io` FQDN. HTTP on port 80 is redirected to HTTPS unless you allow insecure connections.
- **Internal**: the FQDN gains an `.internal.` segment and is directly reachable only from other apps in the same Container Apps environment; requests from outside, including from the environment's own VNet, get a 404 from the environment proxy. Learn's one exception is an environment-level HTTP route configuration that targets the app.
- **Target port** is the port your container listens on. **Transport** is `auto`, `http`, `http2` or `tcp` (TCP ingress uses an exposed port other than 80 and 443).
- Ingress also supports IP security restrictions, session affinity, custom domains with certificates and client certificate (mTLS) modes.

No ingress means no HTTP endpoint at all, typical for queue-processing workers.

## Scaling

Container Apps scales **horizontally** by adding **replicas** of a revision. Vertical scaling isn't supported: to give a replica more CPU or memory you change the container resources, which creates a new revision.

- **Limits**: `minReplicas` defaults to **0** and `maxReplicas` to **10**; both can be set up to **1,000**.
- **Rules** (implemented with KEDA): **HTTP** (concurrent requests per replica, default 10), **TCP** (concurrent connections, default 10) and **custom** rules for any KEDA scaler: CPU, memory, Azure Service Bus, Event Hubs, Storage queues, Kafka, Redis and more. Custom rules authenticate with secrets or a managed identity.
- If several rules exist, the app scales out when **any** rule's condition is met.
- With no rule defined, a default HTTP rule with 0–10 replicas applies. If ingress is disabled, set `minReplicas` to 1 or add a custom rule, otherwise the app scales to zero with nothing to wake it.
- Behaviour: KEDA polls event sources every 30 seconds; scale-in to zero waits for a 300-second cool-down; replicas are added in steps of 1, 4, 8, 16, 32 up to the maximum; desired replicas are roughly the metric value divided by the target, rounded up.
- **Scale to zero** means no usage charges for that app. Set `--min-replicas 1` or higher when cold starts are unacceptable.

## Secrets and managed identity

Secrets are defined at application scope (`--secrets db-pass=<password>`) and referenced from environment variables with `secretref:` (`--env-vars DB_PASSWORD=secretref:db-pass`). A secret can also be a **Key Vault reference** retrieved with a managed identity. Container Apps supports system-assigned and user-assigned **managed identities**, used to pull from ACR (`--registry-identity system` or a user-assigned identity resource ID; the CLI tries to create the AcrPull assignment for you), to authenticate scale rules and to call other Azure services.

## Create a container app

**Portal:** **Create a resource** > **Container App** > **Create**. **Basics**: resource group, **Container app name**, deployment source (container image), region, and **Container Apps environment** (create new: environment type **Workload profiles**, zone redundancy, monitoring, networking). **Container**: image source (ACR with **Authentication type** managed identity or secret, or another registry), image and tag, **Workload profile** (Consumption) and **CPU and memory**, environment variables. **Ingress**: **Enabled**, traffic **Limited to Container Apps Environment** (internal) or **Accepting traffic from anywhere** (external), target port. **Review + create**. Scale rules are edited later under **Application** > **Scale**; revisions under **Revisions and replicas**.

**Azure CLI** (the `containerapp` extension installs on first use):

```bash
az containerapp env create -g rg-aca-prod -n cae-contoso-prod -l eastus
az containerapp create -g rg-aca-prod -n ca-api --environment cae-contoso-prod \
  --image mcr.microsoft.com/k8se/quickstart:latest \
  --ingress external --target-port 80 \
  --cpu 0.5 --memory 1.0Gi --min-replicas 0 --max-replicas 5 \
  --scale-rule-name http-rule --scale-rule-type http --scale-rule-http-concurrency 50 \
  --secrets db-pass=<password> --env-vars DB_PASSWORD=secretref:db-pass \
  --revisions-mode single --query properties.configuration.ingress.fqdn -o tsv
az containerapp update -g rg-aca-prod -n ca-api --image mcr.microsoft.com/k8se/quickstart:latest --revision-suffix v2
az containerapp revision list -g rg-aca-prod -n ca-api -o table
```

`az containerapp up` is the one-command shortcut: it creates (or reuses) the resource group, environment, Log Analytics workspace and, when building from source, a registry, then deploys the app (`az containerapp up -n ca-api --image <image> --ingress external --target-port 80`). Use `az containerapp revision set-mode --mode multiple` to switch modes and `az containerapp ingress traffic set` to split traffic.

**Azure PowerShell** (Az.App): build a workload profile object and environment with `New-AzContainerAppWorkloadProfileObject` and `New-AzContainerAppManagedEnv`, a container object with `New-AzContainerAppTemplateObject -Image <image> -Name api -ResourceCpu 0.5 -ResourceMemory 1Gi`, then `New-AzContainerApp -Name ca-api -ResourceGroupName rg-aca-prod -Location eastus -EnvironmentId <environment-id> -TemplateContainer $container -ScaleMinReplica 0 -ScaleMaxReplica 5`. Ingress and secrets go in a configuration object (`-Configuration`). For day-to-day work the CLI is the practical route; Learn's Container Apps how-to pages are CLI-first.

## Try it yourself

Azure Cloud Shell (Bash). Cost: on the Consumption profile an app that scales to zero costs nothing while idle; this lab costs a few US cents. The environment also creates a Log Analytics workspace with small ingestion charges. Delete the resource group at the end.

```bash
rg=rg-lab-d3aca; env=cae-lab; app=ca-lab
az group create -n $rg -l eastus
az containerapp env create -g $rg -n $env -l eastus
fqdn=$(az containerapp create -g $rg -n $app --environment $env \
  --image mcr.microsoft.com/k8se/quickstart:latest --ingress external --target-port 80 \
  --min-replicas 0 --max-replicas 3 --revisions-mode multiple --revision-suffix v1 \
  --query properties.configuration.ingress.fqdn -o tsv)
curl -s https://$fqdn | head -n 5
az containerapp update -g $rg -n $app --revision-suffix v2 --set-env-vars RELEASE=v2
az containerapp revision list -g $rg -n $app --query "[].{name:name, active:properties.active, weight:properties.trafficWeight}" -o table
az containerapp ingress traffic set -g $rg -n $app --revision-weight $app--v1=80 $app--v2=20
az containerapp show -g $rg -n $app --query "properties.template.scale" -o json
```

In the portal, open **Revisions and replicas** to see both revisions and their traffic weights, and **Scale** to see the replica range. Clean up: `az group delete -n $rg --yes --no-wait`.

## Key takeaways

- An environment is the boundary for a group of apps: shared VNet, logging and service discovery. Workload profiles environments (default) offer the Consumption profile plus optional Dedicated profiles.
- Revisions are immutable; template changes (image, resources, env vars, scale rules) create revisions, configuration changes (secrets, ingress, traffic, revision mode) don't.
- Single revision mode (default) swaps to the new revision when it's ready; multiple mode allows weighted traffic splitting and labels.
- Ingress external or internal, target port, HTTPS by default; no ingress for background workers.
- Scale rules: HTTP, TCP and custom KEDA scalers; min replicas default 0, max default 10, up to 1,000; scale to zero means no usage charges.
- Secrets are referenced with `secretref:`; managed identities pull from ACR (`--registry-identity`).
- `az containerapp create`, `up` and `update`; `az containerapp ingress traffic set` for weights.
