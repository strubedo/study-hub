## The plan is the server farm

Every App Service app (web app, API app, Web App for Containers, and function apps on a Dedicated plan) runs in an **App Service plan** (`Microsoft.Web/serverfarms`). The plan defines:

- **Operating system**: Windows or Linux.
- **Region**.
- **Pricing tier** and **instance size** (for example S1, P1v3).
- **Number of instances** (VM workers).

All apps in a plan run on the **same instances** and share their CPU and memory. Deployment slots, WebJobs, backups and diagnostic logs also consume those instances. You pay for the plan's instances whether one app or ten run on them (Free costs nothing; Shared charges per app). Learn's guidance table suggests roughly 8 apps on a B1/S1/P1v2 instance, 16 on P1v3, 32 on P2v3, as a starting point for density.

The OS and region are chosen when you create the plan; to run Windows and Linux apps, or apps in two regions, you need separate plans. You can **move an app to another plan** only if both plans are in the same resource group and region and have the same OS; in addition, Learn notes that each plan lands in an internal deployment unit called a *webspace*, and an app can move only between plans in the same webspace (disable VNet integration on the app first).

## Pricing tiers and what they add

| Tier category | Tiers | Compute | Highlights from Learn's App Service limits table |
|---|---|---|---|
| Shared compute | **Free (F1)**, **Shared (D1)** | Shared VMs with other customers; CPU minutes quota per app; **no scale-out** | Free: no custom domains (azurewebsites.net only), Linux supported. Shared: Windows only, custom domains allowed but **no TLS binding** for them |
| Dedicated compute | **Basic (B1–B3)** | Dedicated VMs for your plan | Custom domains + **SNI TLS**, **App Service managed certificates**, manual scale to **3** instances, **backups**, **VNet integration**, **private endpoints**, hybrid connections (5 per plan), Always On |
| | **Standard (S1–S3)** | | Everything in Basic plus **autoscale**, **deployment slots (5 staging slots)**, 1 IP-based TLS binding included, up to **10** instances |
| | **Premium v3 (P0v3–P3v3, P1mv3–P5mv3)**, **Premium v4 (P0v4–P3v4, P1mv4–P5mv4)**, older Premium v2 | Newer, faster VM families | Everything in Standard plus **20 staging slots**, up to **30** instances, **automatic scaling**, zone redundancy |
| Isolated | **Isolated v2 (I1v2–I6v2)** | Single-tenant **App Service Environment v3** in your virtual network | Network isolation, up to **100** instances (more on request), 20 slots |

Other points from the same table: the Basic, Standard, Premium and Isolated tiers carry a 99.95% SLA, and Windows containers need Premium or Isolated. The CLI SKU list for `az appservice plan create` (read November 2026) also includes **IsolatedV4** SKUs (I1v4 and up) for App Service Environments; the exam outline names Isolated v2.

> **Exam tip:** Map each requirement to the **cheapest tier that has it**: custom domain + TLS = Basic; deployment slots or rule-based autoscale = Standard; more than 5 slots, more than 10 instances or automatic scaling = Premium v3/v4; network isolation in your own VNet = Isolated v2.

## Create a plan

**Portal:** **Create a resource** > **App Service Plan** (or create one inline while creating a web app). **Basics**: subscription, resource group, **Name**, **Operating System** (Linux or Windows), **Region**, **Pricing plan** (with **Explore pricing plans** to compare), and for Premium tiers **Zone redundancy**. **Review + create**.

**Azure CLI:**

```bash
az appservice plan create -g rg-web-prod -n asp-web-prod -l eastus \
  --sku S1 --is-linux --number-of-workers 2
az appservice plan create -g rg-web-prod -n asp-win-prod -l eastus --sku P0V3 --is-linux false
```

> **Watch out:** The current CLI reference says `--is-linux` **defaults to true** unless you use `--hyper-v` or `--is-managed-instance`, and shows `--is-linux false` to create a Windows plan. Older articles and scripts assume Windows is the default. Always pass the OS explicitly.

**Azure PowerShell:**

```powershell
New-AzAppServicePlan -ResourceGroupName rg-web-prod -Name asp-web-prod -Location eastus `
  -Tier Standard -WorkerSize Small -NumberofWorkers 2 -Linux
```

## Scale up and scale out

| | Scale **up** (vertical) | Scale **out** (horizontal) |
|---|---|---|
| What changes | Tier and/or instance size (S1 to P1v3) | Number of instances (1 to 4) |
| Gives you | More CPU, memory, disk per instance and tier features (slots, autoscale) | More instances behind the built-in load balancer |
| Affects | Every app in the plan | Every app in the plan (unless per-app scaling) |
| CLI | `az appservice plan update -g <rg> -n <plan> --sku P1V3` | `az appservice plan update -g <rg> -n <plan> --number-of-workers 4` |
| PowerShell | `Set-AzAppServicePlan -ResourceGroupName <rg> -Name <plan> -Tier PremiumV3 -WorkerSize Small` | `Set-AzAppServicePlan -ResourceGroupName <rg> -Name <plan> -NumberofWorkers 4` |
| Portal | Plan or app > **Scale up (App Service plan)** | **Scale out (App Service plan)** |

Scaling up or down doesn't require redeploying the apps. Scaling down fails if the target tier lacks something you use: for example Learn notes you can't scale to Standard if an app has more than five slots. Changing to a different VM family (for example Standard to Premium v3) can change the app's **outbound IP addresses**.

Scale-out has three modes, and Learn says only one should be active for a plan:

| | **Manual** | **Autoscale** (rule-based) | **Automatic scaling** |
|---|---|---|---|
| Tiers | Basic and up | **Standard** and up | **Premium v2, v3, v4** |
| How | You set the instance count | Azure Monitor autoscale rules on metrics (CPU percentage, memory percentage, HTTP queue length) and schedules, with min/max/default | Platform scales on HTTP traffic; you set **Maximum burst** (plan, up to 30), **Always ready instances** and optional **maximum scale limit** per app; prewarmed instances |
| Scope | Plan | Plan | Plan, with per-app minimum and maximum |

Rule-based autoscale works exactly like the VM scale set autoscale covered in 3.2 (scale out if any rule fires, scale in only if all scale-in rules fire), targeting the plan resource:

```bash
az monitor autoscale create -g rg-web-prod --resource asp-web-prod \
  --resource-type Microsoft.Web/serverfarms --name as-web --min-count 2 --max-count 6 --count 2
az monitor autoscale rule create -g rg-web-prod --autoscale-name as-web \
  --condition "CpuPercentage > 70 avg 10m" --scale out 1
az monitor autoscale rule create -g rg-web-prod --autoscale-name as-web \
  --condition "CpuPercentage < 30 avg 10m" --scale in 1
```

Automatic scaling (Premium v2 and later) is turned on at plan level:

```bash
az appservice plan update -g rg-web-prod -n asp-web-prem --elastic-scale true --max-elastic-worker-count 10
az webapp update -g rg-web-prod -n app-contoso-web --minimum-elastic-instance-count 2
```

Learn notes that automatic scaling disables ARR affinity on existing apps, isn't used for deployment slot traffic, and is disabled if the plan also hosts function apps.

**Per-app scaling** (`--per-site-scaling` on the plan, then a per-app worker count) lets a high-density plan run each app on only a subset of the plan's instances. The plan's instance count and billing stay at plan level.

## Try it yourself

Azure Cloud Shell (Bash). Cost: a B1 plan, then S1 for a few minutes; under one US dollar if you delete it within the hour.

```bash
rg=rg-lab-d3plan; plan=asp-lab
az group create -n $rg -l eastus
az appservice plan create -g $rg -n $plan --sku B1 --is-linux --number-of-workers 1
az appservice plan show -g $rg -n $plan --query "{sku:sku.name, tier:sku.tier, workers:sku.capacity, kind:kind, linux:reserved}" -o table
az appservice plan update -g $rg -n $plan --number-of-workers 2      # scale out (Basic max 3)
az appservice plan update -g $rg -n $plan --sku S1                   # scale up to get autoscale and slots
az monitor autoscale create -g $rg --resource $plan --resource-type Microsoft.Web/serverfarms \
  --name as-lab --min-count 1 --max-count 3 --count 2
az monitor autoscale rule create -g $rg --autoscale-name as-lab --condition "CpuPercentage > 70 avg 5m" --scale out 1
az monitor autoscale show -g $rg -n as-lab --query "profiles[0].capacity" -o json
```

Try `az monitor autoscale create` before the scale up to S1 and note the error. In the portal, open the plan's **Scale out (App Service plan)** blade to see **Rules Based** selected, and **Scale up (App Service plan)** to compare tiers. Clean up: `az group delete -n $rg --yes --no-wait`.

## Key takeaways

- A plan fixes OS, region, tier, size and instance count; all apps and slots in it share the instances.
- Free/Shared: shared compute, no scale-out. Basic: custom domains with TLS, managed certificates, backups, VNet integration, up to 3 instances. Standard: autoscale, 5 slots, 10 instances. Premium v3/v4: 20 slots, 30 instances, automatic scaling. Isolated v2: App Service Environment.
- Scale up = change tier or size; scale out = change instance count; both affect every app in the plan.
- Manual scale-out from Basic; rule-based autoscale from Standard; automatic scaling on Premium v2–v4 only.
- `az appservice plan create --sku --is-linux --number-of-workers`; pass `--is-linux` explicitly because the current CLI defaults to Linux.
