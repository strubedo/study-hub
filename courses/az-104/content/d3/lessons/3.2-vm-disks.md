## Disk roles

| Disk | Persistent? | Notes |
|---|---|---|
| **OS disk** | Yes (managed disk) | Holds the OS; created from the image. Maximum 4,095 GiB usable (4 TiB), and MBR-partitioned images are limited to 2 TiB. Default host caching ReadWrite |
| **Temporary disk** | **No** | Local storage on the host, on sizes with `d` (or older sizes). `D:` on Windows, `/dev/sdb1` or `/mnt` on Linux. Lost on deallocation, redeploy, resize to another host or host failure. Never put data you need there |
| **Data disks** | Yes (managed disks) | Attached at a LUN; the number allowed depends on the VM size. Hold applications and data |
| **Ephemeral OS disk** | No | OS disk placed on local storage (cache, temp or NVMe); see below |

All new VMs use **managed disks**: Azure manages the storage account behind them, places disks in fault domains aligned with the VM, and provides three local copies (LRS) or zone-redundant copies (ZRS, for Premium SSD and Standard SSD).

## Disk types

From Learn's managed disk types page:

| | Ultra Disk | Premium SSD v2 | Premium SSD | Standard SSD | Standard HDD |
|---|---|---|---|---|---|
| SKU name | `UltraSSD_LRS` | `PremiumV2_LRS` | `Premium_LRS`, `Premium_ZRS` | `StandardSSD_LRS`, `StandardSSD_ZRS` | `Standard_LRS` |
| Max size | 65,536 GiB | 65,536 GiB | 32,767 GiB | 32,767 GiB | 32,767 GiB |
| Max IOPS | 400,000 | 80,000 | 20,000 | 6,000 | 2,000 (3,000 with performance plus) |
| Max throughput | 10,000 MB/s | 2,000 MB/s | 900 MB/s | 750 MB/s | 500 MB/s |
| OS disk? | **No** | **No** | Yes | Yes | Yes, retiring September 8, 2028 |
| Sizing | Any size; set IOPS and throughput separately | Any size; baseline 3,000 IOPS and 125 MB/s free, adjust any time | Fixed tiers P1 to P80 | Fixed tiers E1 to E80 | Fixed tiers S4 to S80 |
| Host caching | No | No | Yes | Yes | Yes |
| Notes | Data disks only, not in Azure Compute Gallery, no availability sets, no ZRS; performance changes up to 4 per 24 h (up to an hour to take effect) | Data disks only; most zonal regions require a zonal VM; up to 4 performance changes per 24 h | Needs a size with `s`; bursting | Any VM size; bursting | Latency-tolerant workloads only |

Choosing:

- **OS disk for production**: Premium SSD (Ultra and Premium SSD v2 can't be OS disks).
- **Dev/test, light web servers**: Standard SSD.
- **Backups, infrequently accessed data**: Standard HDD.
- **Databases on data disks, best price-performance, adjustable without fixed tiers**: Premium SSD v2.
- **Highest IOPS and sub-millisecond latency (SAP HANA, top-tier databases)**: Ultra Disk.

The **single-instance VM SLA** depends on disks: Learn's high-availability guidance says the highest single-VM uptime SLA needs **Premium SSD** for the OS disk and Premium SSD, Premium SSD v2 or Ultra Disk for every data disk (Microsoft's SLA document gives 99.9% for that configuration).

Disks are billed by **provisioned** size, rounded up to the next tier for Premium, Standard SSD and Standard HDD: a 200 GiB Standard SSD is billed as E15 (256 GiB).

## Host caching

| Setting | Use for |
|---|---|
| **ReadWrite** | OS disks (default), only for data disks whose application handles write-back correctly |
| **ReadOnly** | Read-heavy and mixed data disks (Learn's premium performance guidance lists it as the default for data disks) |
| **None** | Write-heavy or write-only disks, such as log disks |

Caching isn't available for Ultra Disk, Premium SSD v2, shared disks or disks of 4 TiB and larger. Changing the cache setting detaches and reattaches the disk; on the OS disk it restarts the VM.

## Attach, detach, expand

**Portal:** VM > **Settings** > **Disks** > **Create and attach a new disk** or **Attach existing disks**, set LUN, type, size and host caching, **Apply**. Detach with the X next to a data disk.

**Azure CLI:**

```bash
az vm disk attach -g rg-db-prod --vm-name vm-db-01 --name disk-db-data01 --new --size-gb 256 --sku Premium_LRS --caching ReadOnly --lun 0
az vm disk attach -g rg-db-prod --vm-name vm-db-01 --name disk-db-logs01                         # existing disk
az vm disk detach -g rg-db-prod --vm-name vm-db-01 --name disk-db-logs01
az disk update -g rg-db-prod -n disk-db-data01 --size-gb 512
```

**Azure PowerShell:**

```powershell
$vm = Get-AzVM -ResourceGroupName rg-db-prod -Name vm-db-01
$cfg = New-AzDiskConfig -Location eastus -CreateOption Empty -DiskSizeGB 256 -SkuName Premium_LRS -Zone 1
$disk = New-AzDisk -ResourceGroupName rg-db-prod -DiskName disk-db-data01 -Disk $cfg
$vm = Add-AzVMDataDisk -VM $vm -Name disk-db-data01 -ManagedDiskId $disk.Id -Lun 0 -CreateOption Attach -Caching ReadOnly
Update-AzVM -ResourceGroupName rg-db-prod -VM $vm
$vm = Remove-AzVMDataDisk -VM $vm -Name disk-db-logs01
Update-AzVM -ResourceGroupName rg-db-prod -VM $vm
```

A disk attached to a zonal VM must be in the same zone. After attaching, initialize and format it in the OS (Disk Management or `Initialize-Disk` on Windows; `parted`, `mkfs` and `/etc/fstab` with the UUID on Linux).

**Expanding** a disk is one-way: **shrinking isn't supported**. You then extend the partition and file system inside the OS. Learn's "expand without downtime" rules:

- Supported for **data disks** only; OS disks need the VM deallocated.
- A Standard HDD, Standard SSD or Premium SSD of **4 TiB or less** must be deallocated *and detached* to grow **beyond 4 TiB**; one already larger than 4 TiB can grow online.
- Premium SSD v2 and Ultra Disk data disks can grow online (not during a background copy).
- **Shared disks** (`maxShares` > 1) can't be expanded online.

## Snapshots and images

A **snapshot** is a point-in-time, read-only copy of one managed disk. **Incremental** snapshots store only changes since the previous one and are billed on used size; they can be copied to another region.

```bash
az snapshot create -g rg-db-prod -n snap-db-data01-20261123 --source disk-db-data01 --incremental true
az disk create -g rg-db-prod -n disk-db-restore --source snap-db-data01-20261123
```

```powershell
$disk = Get-AzDisk -ResourceGroupName rg-db-prod -DiskName disk-db-data01
$snapCfg = New-AzSnapshotConfig -SourceUri $disk.Id -Location eastus -CreateOption Copy -Incremental
New-AzSnapshot -ResourceGroupName rg-db-prod -SnapshotName snap-db-data01-20261123 -Snapshot $snapCfg
```

An **image** captures a whole VM (OS disk plus data disks) to create more VMs. Generalize it first (`sysprep` on Windows, `waagent -deprovision+user` on Linux) for a reusable image, or capture it **specialized** to keep the identity. Store images as versions in an **Azure Compute Gallery** (replication across regions, versioning, Trusted launch support); legacy **managed images** still exist.

## Shared disks (high level)

A managed disk with `maxShares` greater than 1 can be attached to several VMs at once for clustered applications (Windows Server Failover Cluster, Pacemaker), which coordinate access with SCSI persistent reservations. Supported on Ultra Disk, Premium SSD v2, Premium SSD and Standard SSD, as **data disks only**; no host caching; `maxShares` can only change while the disk is detached from all VMs; ADE isn't supported (SSE is). Premium and Standard SSD sizes limit `maxShares` (3, 5 or 10 depending on tier); Ultra and Premium SSD v2 allow up to 15. ZRS disks can be shared across zones.

```bash
az disk create -g rg-db-prod -n disk-cluster01 --size-gb 1024 --sku Premium_LRS --max-shares 2
```

## Ephemeral OS disks (high level)

An ephemeral OS disk lives on the VM's local storage (cache, temp disk or NVMe placement) and isn't saved to Azure Storage. It gives faster reads and writes and faster reimaging, with no OS disk storage cost. Limits from Learn: chosen **only at creation**; **no stop-deallocate** (delete or reimage instead); data on it is lost on resize, redeploy and host healing; **no** image capture, snapshots, Azure Disk Encryption, Azure Backup, Site Recovery or OS disk swap. It suits stateless scale set instances.

```bash
az vm create -g rg-web-prod -n vm-stateless-01 --image Ubuntu2204 --size Standard_D4ds_v5 \
  --ephemeral-os-disk true --ephemeral-os-disk-placement ResourceDisk --generate-ssh-keys
```

## Try it yourself

Azure Cloud Shell (Bash). Cost: under a dollar if deleted within an hour (VM plus two small disks and a snapshot).

```bash
rg=rg-lab-d3disk; az group create -n $rg -l eastus
az vm create -g $rg -n vm-disk-01 --image Ubuntu2204 --size Standard_D2s_v5 \
  --generate-ssh-keys --public-ip-address "" --nsg ""
az vm disk attach -g $rg --vm-name vm-disk-01 --name disk-data01 --new --size-gb 32 --sku StandardSSD_LRS --caching ReadOnly
az disk update -g $rg -n disk-data01 --size-gb 64                     # online expansion of a data disk
az vm run-command invoke -g $rg -n vm-disk-01 --command-id RunShellScript --scripts "lsblk"
az snapshot create -g $rg -n snap-data01 --source disk-data01 --incremental true
az disk create -g $rg -n disk-from-snap --source snap-data01
az disk list -g $rg --query "[].{name:name,sku:sku.name,size:diskSizeGB,state:diskState}" -o table
```

Note `diskState`: **Attached** for the data disk, **Unattached** for the disk restored from the snapshot. Try `az disk update -g $rg -n disk-data01 --size-gb 32` and read the error (no shrinking). Clean up: `az group delete -n $rg --yes --no-wait`.

## Key takeaways

- OS disk (persistent), temp disk (lost on deallocation), data disks (persistent, count limited by size), ephemeral OS disk (local, stateless).
- Ultra and Premium SSD v2: data disks only, no host caching, performance set independently; Premium SSD: production OS and data; Standard SSD: dev/test and light loads; Standard HDD: backups (OS use retiring September 8, 2028).
- Caching: ReadWrite for OS, ReadOnly for read-heavy data, None for write-heavy.
- Expand only (never shrink); OS disks need deallocation; crossing 4 TiB on Premium/Standard needs deallocate and detach; shared disks can't expand online.
- Incremental snapshots copy one disk; images (Azure Compute Gallery) capture a VM for reuse.
- Shared disks: `maxShares` > 1, data disks only, no caching; ephemeral OS disks: no deallocation, no snapshots, no ADE, no backup.
