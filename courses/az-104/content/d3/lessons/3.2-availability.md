## What can fail, and what protects against it

| Failure | Protection |
|---|---|
| A host, rack switch or power unit | Fault domains (availability set or scale set spreading) |
| Planned platform maintenance that reboots hosts | Update domains (availability sets); fault-domain-by-fault-domain maintenance (Flexible scale sets) |
| A whole datacenter (power, cooling, network) | Availability zones |
| A whole region | A second region (Site Recovery, geo-redundant data, traffic routing) |

Availability sets and zones are chosen **when the VM is created**.

## Availability sets

An availability set is a logical grouping that tells Azure to spread its VMs over separate hardware in one datacenter:

- **Fault domains (FDs)**: groups of hosts sharing a power source and network switch. An availability set has up to **3** FDs (the managed-disk maximum per region is 2 or 3; check with `az vm list-skus --resource-type availabilitySets`). The CLI default is 2.
- **Update domains (UDs)**: groups of VMs that can be rebooted together during planned maintenance. Up to **20**; if you don't set it the platform picks a value such as 5. **Only one UD is rebooted at a time**, and a rebooted UD gets 30 minutes to recover before the next one starts.
- Update domains are assigned round-robin: Learn's example is that with five UDs the sixth VM lands in the same UD as the first, the seventh with the second, and so on. The platform also spreads VMs across the fault domains; Learn doesn't spell out the FD order, so the FD row below is an even spread for illustration (Learn also notes two VMs can end up sharing an FD, for example if you stop or deallocate VMs between deployments).
- Managed disks of each VM are aligned with its fault domain.
- FD and UD counts **can't be changed** after the set is created.
- No extra cost; you pay for the VMs.
- **SLA**: two or more VMs in an availability set, 99.95% (Learn's availability set overview).

A **VM can be added to an availability set only when it is created**. To put an existing VM into a set (or move it to another set), delete the VM keeping its disks and re-create it in the set; Learn publishes a PowerShell script for this.

Availability sets can't use availability zones and can't use Ultra Disks. Microsoft now recommends **Virtual Machine Scale Sets with Flexible orchestration** for new high-availability designs, and documents a preview migration from availability sets to Flexible scale sets.

### Working the numbers

Availability set with 3 FDs and 5 UDs, 8 VMs created in order:

| VM | 1 | 2 | 3 | 4 | 5 | 6 | 7 | 8 |
|---|---|---|---|---|---|---|---|---|
| UD | 0 | 1 | 2 | 3 | 4 | 0 | 1 | 2 |
| FD | 0 | 1 | 2 | 0 | 1 | 2 | 0 | 1 |

- During planned maintenance at most **2** VMs are down at once (UDs 0, 1 and 2 hold two each).
- With an even spread, one fault domain failure takes down at most **3** VMs (FDs 0 and 1 hold three each).
- With 2 FDs, a rack failure could take out half the VMs.

> **Exam tip:** Divide the VM count by the UD count and round up to get the maximum number of VMs that planned maintenance can take down at once; do the same with FDs for an unplanned hardware failure.

## Availability zones

An availability zone is one or more physically separate datacenters within a region, with independent power, cooling and networking. Regions that support zones have three. VMs and their managed disks are **zonal**: pinned to one zone you choose (zone 1, 2 or 3). Some resources are **zone-redundant**: replicated across zones automatically, such as Standard public IPs created zone-redundant, Standard Load Balancer frontends, ZRS managed disks and ZRS storage accounts.

- **SLA**: two or more VMs deployed **across two or more zones** in the same region, **99.99%** (Learn's SLA summaries; the binding text is Microsoft's SLA document).
- Two VMs in the **same** zone get no zone-level protection.
- Zone numbers are logical per subscription: zone 1 in one subscription isn't necessarily zone 1 in another.
- A VM can't be moved into a zone by changing a setting; you re-create it (or use Resource Mover or the zone move feature).
- Zones and availability sets are mutually exclusive for a VM.

```bash
az vm create -g rg-web-prod -n vm-web-01 --image Ubuntu2204 --size Standard_D2s_v5 --zone 1 --generate-ssh-keys
az vm create -g rg-web-prod -n vm-web-02 --image Ubuntu2204 --size Standard_D2s_v5 --zone 2 --generate-ssh-keys
```

Place a zone-redundant Standard Load Balancer in front of zonal VMs to survive a zone outage.

## The availability ladder

| Configuration | Protects against | SLA (as Learn summarizes Microsoft's SLA) |
|---|---|---|
| Single VM, Premium SSD (or Ultra / Premium SSD v2) on every disk | Nothing beyond the host's own recovery | 99.9% |
| Two or more VMs in an availability set, or a regional Flexible scale set spread across fault domains | Host, rack and maintenance failures in one datacenter | 99.95% |
| Two or more VMs across two or more availability zones (or a zone-spanning scale set) | Datacenter failure | 99.99% |

Microsoft's SLA document (Service Level Agreements for Online Services) is the authority; it also lists lower figures for single VMs on Standard SSD or Standard HDD. Don't memorize prices; do memorize the three numbers above.

## Proximity placement groups (high level)

A **proximity placement group** (PPG) keeps VMs, availability sets and scale sets physically close (same datacenter) for the lowest network latency between them, for example for tightly coupled application tiers. It trades availability and capacity for latency: the more constraints, the more likely an allocation fails. A PPG can be combined with an availability set (and with a zone, by pinning the PPG's first resource to it). Create it with `az ppg create -n ppg-app -g rg-app-prod -l eastus` and reference it with `--ppg` in `az vm create` or `az vm availability-set create`.

## Create an availability set: portal, CLI, PowerShell

**Portal:** **Availability sets** > **Create**: name, region, fault domains, update domains, proximity placement group > **Review + create**. Then create each VM with **Availability options** = **Availability set** and pick the set. Or choose **Availability zone** and tick one or more zones in the VM wizard; the portal can create one VM per selected zone.

**Azure CLI:**

```bash
az vm availability-set create -g rg-app-prod -n avail-app --platform-fault-domain-count 2 --platform-update-domain-count 5
az vm create -g rg-app-prod -n vm-app-01 --image Win2022Datacenter --size Standard_D2s_v5 \
  --availability-set avail-app --admin-username azureadmin --admin-password '<password>'
az vm availability-set list-sizes -g rg-app-prod -n avail-app -o table
```

**Azure PowerShell:**

```powershell
New-AzAvailabilitySet -ResourceGroupName rg-app-prod -Name avail-app -Location eastus `
  -PlatformFaultDomainCount 2 -PlatformUpdateDomainCount 5 -Sku Aligned
New-AzVM -ResourceGroupName rg-app-prod -Name vm-app-02 -Location eastus -Image Win2022Datacenter `
  -Size Standard_D2s_v5 -Credential (Get-Credential) -AvailabilitySetName avail-app
```

`-Sku Aligned` is required for VMs with managed disks.

## Try it yourself

Azure Cloud Shell (Bash). Cost: two small VMs for under an hour, about a dollar or less. Delete promptly.

```bash
rg=rg-lab-d3avail; az group create -n $rg -l eastus
az vm availability-set create -g $rg -n avail-lab --platform-fault-domain-count 2 --platform-update-domain-count 5
for i in 1 2; do
  az vm create -g $rg -n vm-avs-0$i --image Ubuntu2204 --size Standard_D2s_v5 \
    --availability-set avail-lab --generate-ssh-keys --public-ip-address "" --nsg "" --no-wait
done
az vm wait -g $rg -n vm-avs-01 --created
az vm wait -g $rg -n vm-avs-02 --created
for i in 1 2; do
  az vm get-instance-view -g $rg -n vm-avs-0$i --query "{vm:name, fd:instanceView.platformFaultDomain, ud:instanceView.platformUpdateDomain}" -o table
done
az vm create -g $rg -n vm-zone-01 --image Ubuntu2204 --size Standard_D2s_v5 --zone 1 \
  --generate-ssh-keys --public-ip-address "" --nsg ""
az vm show -g $rg -n vm-zone-01 --query zones
```

Confirm the two set members have different fault and update domains, and that the zonal VM shows `["1"]`. In the portal, open **avail-lab** and look at the **Fault domain** and **Update domain** columns. Then try to add `vm-zone-01` to the set (you can't). Clean up: `az group delete -n $rg --yes --no-wait`.

## Key takeaways

- Availability set: up to 3 FDs and 20 UDs, fixed at creation; one UD rebooted at a time; 99.95% with two or more VMs; VMs join only at creation.
- Round-robin placement: VM count divided by UD (or FD) count, rounded up, is the worst case.
- Availability zones: separate datacenters; VMs are zonal; 99.99% for two or more VMs across two or more zones.
- Single VM with Premium SSD (or better) on all disks: 99.9%.
- Zone-redundant services (Standard public IP, Standard Load Balancer, ZRS disks) complement zonal VMs.
- Proximity placement groups minimize latency at the cost of allocation flexibility.
