## Two very different scaling models

The objective "manage sizing and scaling for containers, including Azure Container Instances and Azure Container Apps" contrasts a service with **no autoscale** (ACI) and one where **autoscale is the default behaviour** (Container Apps). Questions usually give you a workload pattern and ask which setting or service meets it with the least cost or effort.

## Sizing and scaling Azure Container Instances

ACI has **vertical sizing only, fixed at creation**, and **no built-in horizontal autoscale**. Learn's FAQ is explicit: scaling isn't available for containers or container groups; to run more instances you create more container groups.

**Sizing** a container group:

- Each container declares CPU and memory **requests**; the group gets the sum. A group needs at least 1 CPU and 1 GB.
- Optional **limits** let a container burst above its request into capacity the group already has.
- Keep a small buffer: Learn notes that the platform uses a small part of the group's resources, so containers get most but not all of what you allocate.
- Very large groups (above 4 vCPU and 16 GB) are available, but deployment can fail when the region is short of capacity; retry with smaller values, later, or in another region.

**Changing** the size: CPU, memory and GPU resources are properties that **can't be updated in place**. You delete the group and create it again with new values (same for restart policy, OS type and zone). That recreation pulls the image again and can change the group's IP address.

```bash
az container export -g rg-aci-prod -n ci-report -f ci-report.yaml   # keep the definition
# edit cpu/memoryInGB in ci-report.yaml, then:
az container delete -g rg-aci-prod -n ci-report --yes
az container create -g rg-aci-prod -f ci-report.yaml
```

**Scaling out** ACI is your job:

- Create several container groups (script, template copy loop or pipeline) and put them behind something that distributes traffic. Learn documents placing VNet-deployed groups in the backend pool of a **Standard Load Balancer** or behind **Application Gateway**.
- **NGroups** (preview) lets you declare a desired count of identical container groups from a **container group profile**, with rolling upgrades and zone spreading; you still own load balancing.
- **Standby pools** keep pre-provisioned groups ready to hand out for faster start; they're about start-up time, not resiliency.
- AKS **virtual nodes** run Kubernetes pods as ACI container groups, letting the cluster scale burst workloads onto ACI.

> **Exam tip:** If a scenario says "ACI" and "scale automatically on demand", the answer is not a hidden ACI setting. It's usually "move to Azure Container Apps (or AKS)", or "deploy additional container groups".

## Sizing and scaling Azure Container Apps

**Vertical sizing** is per container in the app template:

- Consumption profile: CPU/memory pairs from 0.25 vCPU / 0.5 GiB to 4 vCPU / 8 GiB per replica (memory twice the vCPU value).
- Dedicated workload profiles: you pick a profile size (for example D4 with 4 vCPU and 16 GiB per node) and pack apps onto profile instances; each profile has its own minimum and maximum instance count.
- Changing CPU or memory is a revision-scope change: it creates a new revision, which in single mode replaces the old one without downtime.

**Horizontal scaling** is declarative:

```bash
az containerapp update -g rg-aca-prod -n ca-orders \
  --min-replicas 1 --max-replicas 20 \
  --scale-rule-name queue-rule --scale-rule-type azure-servicebus \
  --scale-rule-metadata "queueName=orders" "namespace=sb-contoso-prod" "messageCount=20" \
  --scale-rule-auth "connection=sb-connection"
```

Here `sb-connection` is an existing app secret holding the Service Bus connection string; a managed identity (`--scale-rule-identity`, listed in the reference for the `containerapp` CLI extension version of the command, which the CLI installs on first use) avoids storing it.

| Setting | Default | Range | Notes |
|---|---|---|---|
| `minReplicas` | 0 | 0–1,000 | 0 allows scale to zero (no usage charges); 1+ avoids cold starts |
| `maxReplicas` | 10 | 1–1,000 | Hard ceiling for the revision |
| HTTP rule `concurrentRequests` | 10 | 1+ | Concurrent HTTP requests per replica before adding another |
| TCP rule `concurrentConnections` | 10 | 1+ | Concurrent TCP connections per replica |
| Custom (KEDA) rule | Scaler-specific | | CPU, memory, Service Bus, Event Hubs, Kafka, Redis, Storage queues and more |

How the numbers combine:

- Desired replicas are calculated roughly as `ceil(metric value / target)`, then kept between `minReplicas` and `maxReplicas`. Example: an HTTP rule with a target of 50 concurrent requests and 400 concurrent requests wants 8 replicas; with `maxReplicas` 5 it runs 5.
- Multiple rules: scale-out starts as soon as **any** rule's condition is met.
- Scale-out adds replicas in steps (1, then 4, 8, 16, 32...) rather than jumping straight to the target; scale-in waits for a 300-second stabilization window, and the last replica is removed only after the 300-second cool-down.
- Replica counts are a target, not a guarantee; during platform upgrades you might briefly see extra replicas.
- In multiple revision mode, each active revision has its own scale settings and replicas.

**Portal:** container app > **Application** > **Scale** (or **Revisions and replicas** > **Create new revision** > **Scale** tab) > set the **Min / max replicas** slider > **Add** a scale rule (HTTP scaling, Azure Queue, Custom) > **Create**.

**Azure PowerShell:** scale settings are parameters of `New-AzContainerApp` and `Update-AzContainerApp` (`-ScaleMinReplica`, `-ScaleMaxReplica`, `-ScaleRule` with objects from `New-AzContainerAppScaleRuleObject`).

## Choosing a container platform

| Requirement | Best fit | Why |
|---|---|---|
| Run one container or a small sidecar group quickly, no orchestration; batch or task that runs to completion | **Azure Container Instances** | Per-second billing, restart policy `OnFailure`/`Never`, no cluster |
| HTTP microservices or event-driven workers that scale on demand, including to zero; revisions and traffic splitting; Dapr | **Azure Container Apps** | Serverless KEDA-based autoscale, managed ingress, revisions |
| Full Kubernetes API, custom operators and CRDs, node-level control, service mesh choice | **Azure Kubernetes Service (AKS)** | You manage the cluster (node pools, upgrades); most control, most effort |
| Web apps and APIs, code or a container, with deployment slots, built-in authentication, custom domains and certificates, autoscale by plan | **Azure App Service** (Web App for Containers) | Mature web hosting features; scale is per App Service plan |
| Store and distribute images for all of the above | **Azure Container Registry** | Private registry with ACR Tasks, geo-replication (Premium) |

Signals the exam uses:

- "Least administrative effort" plus "no need to manage Kubernetes" rules out AKS.
- "Scale to zero" or "event-driven scaling from a queue" points to Container Apps (or Functions, which is outside this objective).
- "Runs for a few minutes once a night" points to ACI with a non-`Always` restart policy, or a Container Apps **job**.
- "Deployment slots" or "swap" points to App Service; Container Apps uses revisions and traffic weights instead.

## Try it yourself

Azure Cloud Shell (Bash). Cost: a few US cents for a short-lived ACI group and a Consumption Container App; delete the resource group at the end.

```bash
rg=rg-lab-d3scale; az group create -n $rg -l eastus
# ACI: resizing means recreate
az container create -g $rg -n ci-size --image mcr.microsoft.com/azuredocs/aci-helloworld:latest \
  --os-type Linux --cpu 1 --memory 1 --ports 80 --ip-address Public
az container export -g $rg -n ci-size -f ~/ci-size.yaml
sed -i 's/memoryInGB: 1.0/memoryInGB: 2.0/' ~/ci-size.yaml; grep -n memoryInGB ~/ci-size.yaml
az container delete -g $rg -n ci-size --yes
az container create -g $rg -f ~/ci-size.yaml
az container show -g $rg -n ci-size --query "containers[0].resources.requests" -o json
# Container Apps: declarative scale settings
az containerapp env create -g $rg -n cae-scale -l eastus
az containerapp create -g $rg -n ca-scale --environment cae-scale \
  --image mcr.microsoft.com/k8se/quickstart:latest --ingress external --target-port 80 \
  --min-replicas 0 --max-replicas 5 --scale-rule-name http-rule --scale-rule-type http \
  --scale-rule-http-concurrency 20
az containerapp show -g $rg -n ca-scale --query properties.template.scale -o json
az containerapp replica list -g $rg -n ca-scale -o table
```

If `grep` shows a different number format in the exported YAML, edit the file by hand. After a few idle minutes, `az containerapp replica list` returns no replicas: the app has scaled to zero. Clean up: `az group delete -n $rg --yes --no-wait`.

## Key takeaways

- ACI: no autoscale. Size by container requests (group = sum); change CPU or memory by deleting and recreating the group; scale out by creating more groups (or NGroups, preview) behind a load balancer.
- Container Apps: vertical size per container (Consumption up to 4 vCPU / 8 GiB per replica); horizontal scale by rules within min/max replicas.
- Replica defaults: min 0, max 10, up to 1,000; HTTP and TCP rules default to 10 concurrent requests or connections per replica.
- Any rule can trigger scale-out; replicas are capped by `maxReplicas`; scale to zero means no usage charges.
- ACI for simple or run-to-completion containers, Container Apps for serverless microservices, AKS for full Kubernetes control, App Service for web apps with slots.
