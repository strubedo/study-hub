## Two ways to get a template from Azure

The objective reads "export a deployment as an ARM template or convert an ARM template to a Bicep file". Azure offers two different exports, and the exam tests which one fits a scenario.

| | Export from resource group or resource | Save from deployment history |
|---|---|---|
| Source | The **current state** of the resources | The **exact template** used by one past deployment |
| Includes changes made in the portal after deployment | **Yes** | **No** |
| Choose which resources | Yes (whole group, a selection, or one resource) | No: everything that deployment contained |
| Parameters | Few; most values hard-coded; resource names parameterized by default | The author's original parameters |
| Readability | Verbose: read-only and default properties included | Clean, ready to redeploy |
| Formats | ARM JSON or Bicep | ARM JSON only (decompile it afterwards if you want Bicep) |
| Works for resources created by hand | Yes | No (there is no deployment) |

Limits that apply to export from a resource group:

- **200 resources**: a larger group fails with "Export template is not supported for resource groups more than 200 resources".
- Export isn't guaranteed to succeed for every resource type; unsupported types produce a warning and are left out (Azure Data Factory, for example). Classic resources must be migrated to Resource Manager first.
- **Secrets aren't exported**: password parameters may be missing, so a VM template usually needs an `adminPassword` parameter added before it deploys.
- The API version comes from published schemas and may not be the newest.

Microsoft's own guidance: export is a learning and starting tool, not a reliable way to produce production templates.

> **Exam tip:** "Capture the current configuration, including the NSG rule an admin added in the portal last week" = export from the resource group. "Redeploy exactly what was deployed in March, with its parameters" = save from deployment history.

## Export from a resource group or resource

**Portal:**
- Whole group: resource group > **Automation** > **Export template** (left menu).
- Selection: tick resources in the group's list, then **Export template** on the toolbar.
- One resource: open it > **Automation** > **Export template**.

Choose the **ARM Template** or **Bicep** tab, untick **Include parameters** if you'd rather write your own, then **Download** or **Deploy**.

**Azure CLI:**

```bash
az group export --name rg-web-prod > rg-web-prod.json
az group export --name rg-web-prod --export-format bicep > rg-web-prod.bicep
az group export --name rg-web-prod --resource-ids $(az network nsg show -g rg-web-prod -n nsg-web --query id -o tsv)
az group export --name rg-web-prod --include-parameter-default-value
az group export --name rg-web-prod --skip-resource-name-params
```

By default resource names become parameters with no default. `--include-parameter-default-value` gives them the current value as default; `--skip-resource-name-params` hard-codes the names; `--skip-all-params` removes all parameterization.

**Azure PowerShell:**

```powershell
Export-AzResourceGroup -ResourceGroupName rg-web-prod -Path ./rg-web-prod.json
Export-AzResourceGroup -ResourceGroupName rg-web-prod -OutputFormat Bicep -Path ./rg-web-prod.bicep
Export-AzResourceGroup -ResourceGroupName rg-web-prod -Resource $nsg.Id -IncludeParameterDefaultValue
```

## Save from deployment history

**Portal:** resource group > **Settings** > **Deployments** > select a deployment > **Template** > **Download**.

**Azure CLI:**

```bash
az deployment group list -g rg-web-prod --query "[].name" -o tsv
az deployment group export -g rg-web-prod -n deploy-web > deploy-web.json
```

Other scopes: `az deployment sub export`, `az deployment mg export`, `az deployment tenant export`.

**Azure PowerShell:**

```powershell
Save-AzResourceGroupDeploymentTemplate -ResourceGroupName rg-web-prod -DeploymentName deploy-web -Path ./deploy-web.json
```

The saved template is the compiled JSON. If the original was a Bicep file, what you get back is the JSON Bicep generated (with Bicep's generator metadata), not the `.bicep` source.

## Converting between ARM JSON and Bicep

| Direction | Command | Result |
|---|---|---|
| JSON to Bicep | `az bicep decompile --file main.json` (Bicep CLI: `bicep decompile main.json`) | Writes `main.bicep` next to the JSON; `--force` overwrites an existing one |
| Bicep to JSON | `az bicep build --file main.bicep` (Bicep CLI: `bicep build main.bicep`) | Writes `main.json`; `--outfile` or `--stdout` to redirect |
| JSON parameter file to `.bicepparam` | `az bicep decompile-params --file main.parameters.json` | Writes a `.bicepparam` file |
| Bicep parameters to JSON | `az bicep build-params --file main.bicepparam` | Writes a JSON parameter file |
| Paste JSON as Bicep | Visual Studio Code Bicep extension | Runs decompile on the clipboard |

**Decompilation is best-effort.** There is no guaranteed one-to-one mapping from JSON to Bicep, so the result can contain warnings or errors to fix, and decompiling fails if no accurate conversion exists. Common clean-up:

- Rename symbolic names the decompiler invented (it often reuses resource names or adds suffixes).
- Replace `concat()` and `format()` with interpolation where it reads better.
- Remove `dependsOn` entries that Bicep now infers from references.
- Parameter names with periods become underscores (Bicep identifiers allow only letters, digits and underscores), so update parameter files.
- Lint the result: `az bicep lint --file main.bicep`.

A round trip (JSON to Bicep to JSON) produces a template that deploys the same result but can differ in syntax from the original.

A typical "convert an existing environment to Bicep" flow chains the two features:

```bash
az group export --name rg-web-prod > main.json
az bicep decompile --file main.json
az bicep lint --file main.bicep
```

or, in one step, `az group export --name rg-web-prod --export-format bicep`.

> **Watch out:** `az bicep build` goes the *other* way (Bicep to JSON). Exam distractors swap the two.

## Try it yourself

Azure Cloud Shell (Bash). Cost: cents. You create a resource with a template, change it by hand, then compare the two exports.

```bash
rg=rg-lab-d3export; az group create -n $rg -l eastus
cat > nsg.json <<'EOF'
{
  "$schema": "https://schema.management.azure.com/schemas/2019-04-01/deploymentTemplate.json#",
  "contentVersion": "1.0.0.0",
  "parameters": {
    "nsgName": { "type": "string", "defaultValue": "nsg-web" }
  },
  "resources": [
    {
      "type": "Microsoft.Network/networkSecurityGroups",
      "apiVersion": "2025-01-01",
      "name": "[parameters('nsgName')]",
      "location": "[resourceGroup().location]",
      "properties": { "securityRules": [] }
    }
  ]
}
EOF
az deployment group create -g $rg -n deploy-nsg --template-file nsg.json
# a manual change after deployment
az network nsg rule create -g $rg --nsg-name nsg-web -n allow-https --priority 100 \
  --direction Inbound --access Allow --protocol Tcp --destination-port-ranges 443
az deployment group export -g $rg -n deploy-nsg > from-history.json
az group export -n $rg > from-group.json
grep -c allow-https from-history.json from-group.json
az bicep decompile --file from-group.json
cat from-group.bicep
```

`from-history.json` has no `allow-https` rule (it is the original template); `from-group.json` does (it is the current state). Read the decompiled Bicep and note what you'd rename. In the portal, open the group's **Export template** and compare the ARM Template and Bicep tabs. Clean up: `az group delete -n $rg --yes --no-wait`.

## Key takeaways

- Export from resource group/resource = current state, selectable, verbose, JSON or Bicep, max 200 resources, secrets missing.
- Save from deployment history = exact original template with its parameters, JSON only, no later manual changes.
- CLI: `az group export` (`--export-format bicep`, `--resource-ids`, `--include-parameter-default-value`, `--skip-resource-name-params`), `az deployment group export`.
- PowerShell: `Export-AzResourceGroup` (`-OutputFormat Bicep`), `Save-AzResourceGroupDeploymentTemplate`.
- `az bicep decompile` converts JSON to Bicep (best-effort, review it); `az bicep build` compiles Bicep to JSON.
