## Why "modify" is its own objective

Administrators rarely write templates from nothing. They take a quickstart, an exported template or a colleague's file and change it: expose a hard-coded value as a parameter, add a resource, return an output, turn one resource into several. The exam shows a template and asks which line to change or what to add. This lesson does the same edits in ARM JSON and in Bicep side by side, then covers parameter files.

The starting point is a template that deploys one storage account with everything hard-coded:

```json
{
  "$schema": "https://schema.management.azure.com/schemas/2019-04-01/deploymentTemplate.json#",
  "contentVersion": "1.0.0.0",
  "resources": [
    {
      "type": "Microsoft.Storage/storageAccounts",
      "apiVersion": "2025-06-01",
      "name": "stcontosodata01",
      "location": "eastus",
      "sku": { "name": "Standard_LRS" },
      "kind": "StorageV2"
    }
  ]
}
```

```bicep
resource st 'Microsoft.Storage/storageAccounts@2025-06-01' = {
  name: 'stcontosodata01'
  location: 'eastus'
  sku: {
    name: 'Standard_LRS'
  }
  kind: 'StorageV2'
}
```

## Edit 1: add a parameter with allowed values

Requirement: the SKU must be chosen at deployment time, limited to LRS or GRS, defaulting to LRS; the location must follow the resource group.

ARM JSON: add a `parameters` section and replace the literals with expressions.

```json
{
  "$schema": "https://schema.management.azure.com/schemas/2019-04-01/deploymentTemplate.json#",
  "contentVersion": "1.0.0.0",
  "parameters": {
    "skuName": {
      "type": "string",
      "defaultValue": "Standard_LRS",
      "allowedValues": [ "Standard_LRS", "Standard_GRS" ]
    },
    "location": {
      "type": "string",
      "defaultValue": "[resourceGroup().location]"
    }
  },
  "resources": [
    {
      "type": "Microsoft.Storage/storageAccounts",
      "apiVersion": "2025-06-01",
      "name": "stcontosodata01",
      "location": "[parameters('location')]",
      "sku": { "name": "[parameters('skuName')]" },
      "kind": "StorageV2"
    }
  ]
}
```

Bicep: add `param` lines with a decorator and reference them by name.

```bicep
@allowed([
  'Standard_LRS'
  'Standard_GRS'
])
param skuName string = 'Standard_LRS'
param location string = resourceGroup().location

resource st 'Microsoft.Storage/storageAccounts@2025-06-01' = {
  name: 'stcontosodata01'
  location: location
  sku: {
    name: skuName
  }
  kind: 'StorageV2'
}
```

> **Watch out:** In ARM JSON, `"location": "parameters('location')"` without the square brackets is a literal string, and the deployment fails because no region has that name. Every expression needs `[ ]`.

## Edit 2: add a resource that depends on another

Requirement: add a blob container named `invoices`. A container is a child of the blob service, which is a child of the account.

ARM JSON: the child type and name have one segment per level, and you must add `dependsOn` because nothing else tells Resource Manager to wait for the account.

```json
{
  "type": "Microsoft.Storage/storageAccounts/blobServices/containers",
  "apiVersion": "2025-06-01",
  "name": "stcontosodata01/default/invoices",
  "dependsOn": [
    "[resourceId('Microsoft.Storage/storageAccounts', 'stcontosodata01')]"
  ],
  "properties": { "publicAccess": "None" }
}
```

Bicep: use the `parent` property, which also creates the dependency.

```bicep
resource blobSvc 'Microsoft.Storage/storageAccounts/blobServices@2025-06-01' = {
  parent: st
  name: 'default'
}

resource invoices 'Microsoft.Storage/storageAccounts/blobServices/containers@2025-06-01' = {
  parent: blobSvc
  name: 'invoices'
  properties: {
    publicAccess: 'None'
  }
}
```

The rule for child names: in JSON, a child resource declared at the top level has `name` = `parent/child` (and for grandchildren `parent/child/grandchild`), and `type` has as many segments after the namespace as `name` has parts.

## Edit 3: add an output

Requirement: return the account's blob endpoint so a pipeline can use it.

```json
"outputs": {
  "blobEndpoint": {
    "type": "string",
    "value": "[reference(resourceId('Microsoft.Storage/storageAccounts', 'stcontosodata01')).primaryEndpoints.blob]"
  }
}
```

```bicep
output blobEndpoint string = st.properties.primaryEndpoints.blob
```

Never output a secret (a key or connection string): outputs are stored in the deployment history and readable by anyone with read access to the deployment.

## Edit 4: turn one resource into a loop

Requirement: create a configurable number of accounts named with a prefix and a number.

ARM JSON: add a `copy` element and use `copyIndex()` in the name.

```json
{
  "type": "Microsoft.Storage/storageAccounts",
  "apiVersion": "2025-06-01",
  "name": "[concat(parameters('prefix'), string(copyIndex(1)))]",
  "location": "[parameters('location')]",
  "sku": { "name": "[parameters('skuName')]" },
  "kind": "StorageV2",
  "copy": {
    "name": "stLoop",
    "count": "[parameters('count')]"
  }
}
```

Bicep: wrap the body in a `for` expression and square brackets.

```bicep
param prefix string = 'stcontosoapp'
param count int = 2

resource accounts 'Microsoft.Storage/storageAccounts@2025-06-01' = [for i in range(1, count): {
  name: '${prefix}${i}'
  location: location
  sku: {
    name: skuName
  }
  kind: 'StorageV2'
}]
```

After the change, any reference to the old single symbolic name must use an index (`accounts[0].id`) or a loop of its own.

## Edit 5: make a resource optional

Add `"condition": "[parameters('deployContainer')]"` to the container resource in JSON (and a `deployContainer` bool parameter); in Bicep add `if (...)`:

```json
{
  "condition": "[parameters('deployContainer')]",
  "type": "Microsoft.Storage/storageAccounts/blobServices/containers",
  "apiVersion": "2025-06-01",
  "name": "stcontosodata01/default/invoices",
  "dependsOn": [
    "[resourceId('Microsoft.Storage/storageAccounts', 'stcontosodata01')]"
  ]
}
```

```bicep
param deployContainer bool = true

resource invoices 'Microsoft.Storage/storageAccounts/blobServices/containers@2025-06-01' = if (deployContainer) {
  parent: blobSvc
  name: 'invoices'
}
```

## Where to make the edits

**Portal:** search **Deploy a custom template** (or **Create a resource** > **Template deployment** > **Create**) > **Build your own template in editor**, paste or edit the JSON, **Save**, then **Review + create**. For a quickstart, choose **Load a GitHub quickstart template** > **Edit template** to change it before deploying. The portal editor works on ARM JSON only; edit Bicep in Visual Studio Code with the Bicep extension, or in the Cloud Shell editor (`code main.bicep`).

**Azure CLI / PowerShell:** check an edited file before deploying with `az deployment group what-if -g <rg> --template-file main.bicep` or `New-AzResourceGroupDeployment -ResourceGroupName <rg> -TemplateFile ./main.bicep -WhatIf` (the deploy lesson covers both).

## Parameter files

A parameter file keeps per-environment values out of the template. Two formats exist.

**JSON parameter file** (works with ARM JSON and Bicep templates):

```json
{
  "$schema": "https://schema.management.azure.com/schemas/2019-04-01/deploymentParameters.json#",
  "contentVersion": "1.0.0.0",
  "parameters": {
    "skuName": { "value": "Standard_GRS" },
    "count": { "value": 3 },
    "adminPassword": {
      "reference": {
        "keyVault": {
          "id": "/subscriptions/00000000-0000-0000-0000-000000000000/resourceGroups/rg-security-prod/providers/Microsoft.KeyVault/vaults/kv-contoso-prod"
        },
        "secretName": "vmAdminPassword"
      }
    }
  }
}
```

Each parameter is an object with `value`, or `reference` to a Key Vault secret (the vault must allow template deployment, `enabledForTemplateDeployment`). The file may only contain parameters the template defines; an extra one fails the deployment.

**Bicep parameter file** (`.bicepparam`), Bicep only:

```bicep
using 'main.bicep'

param skuName = 'Standard_GRS'
param count = 3
param adminPassword = az.getSecret('00000000-0000-0000-0000-000000000000', 'rg-security-prod', 'kv-contoso-prod', 'vmAdminPassword')
```

The `using` statement ties the file to its Bicep file, so the CLI command doesn't take `--template-file`:

```bash
az deployment group create -g rg-app-prod --parameters main.prod.bicepparam
```

```powershell
New-AzResourceGroupDeployment -ResourceGroupName rg-app-prod -TemplateFile ./main.json -TemplateParameterFile ./main.parameters.json
New-AzResourceGroupDeployment -ResourceGroupName rg-app-prod -TemplateFile ./main.bicep -TemplateParameterFile ./main.prod.bicepparam
```

Learn's PowerShell examples pass `-TemplateFile` together with the `.bicepparam` file, so do the same in PowerShell; the "omit it" rule below is an Azure CLI rule. (`az.getSecret()` is the parameters-file function; the `az.` namespace is optional.)

> **Exam tip:** With the Azure CLI, a `.bicepparam` file goes in `--parameters` and you **omit** `--template-file`; adding it gives an error that only a .bicep file is allowed with a .bicepparam file. A JSON parameter file needs `--template-file` alongside it.

Precedence: when you pass a parameter file and then `key=value` pairs, later values win, so supply the file first and override selectively.

## Try it yourself

Azure Cloud Shell (Bash). Cost: cents for one storage account.

```bash
rg=rg-lab-d3mod; az group create -n $rg -l eastus
sfx=$(echo $RANDOM$RANDOM | cut -c1-6)
cat > main.bicep <<'EOF'
@allowed([
  'Standard_LRS'
  'Standard_GRS'
])
param skuName string = 'Standard_LRS'
param name string
param deployContainer bool = true

resource st 'Microsoft.Storage/storageAccounts@2025-06-01' = {
  name: name
  location: resourceGroup().location
  sku: {
    name: skuName
  }
  kind: 'StorageV2'
}

resource blobSvc 'Microsoft.Storage/storageAccounts/blobServices@2025-06-01' = {
  parent: st
  name: 'default'
}

resource invoices 'Microsoft.Storage/storageAccounts/blobServices/containers@2025-06-01' = if (deployContainer) {
  parent: blobSvc
  name: 'invoices'
}

output blobEndpoint string = st.properties.primaryEndpoints.blob
EOF
cat > main.lab.bicepparam <<EOF
using 'main.bicep'
param name = 'stlabmod$sfx'
param skuName = 'Standard_LRS'
EOF
az deployment group create -g $rg --parameters main.lab.bicepparam --query properties.outputs
az deployment group create -g $rg --template-file main.bicep --parameters main.lab.bicepparam   # Learn documents an error here; read what your CLI version prints
```

Then add `param deployContainer = false` to the parameter file, redeploy with the first command, and confirm the `invoices` container is still there (incremental mode doesn't delete it). Clean up: `az group delete -n $rg --yes --no-wait`.

## Key takeaways

- Replace literals with `[parameters('x')]` (JSON) or the parameter name (Bicep); constrain with `allowedValues` / `@allowed`.
- Child resources: JSON `name` is `parent/child` with `dependsOn`; Bicep uses `parent:` and gets the dependency for free.
- Outputs use `reference(...)` in JSON and `symbol.properties...` in Bicep; never output secrets.
- Loops: JSON `copy` + `copyIndex()`; Bicep `[for i in range(start, count): {...}]`.
- JSON parameter files hold `value` or a Key Vault `reference`; `.bicepparam` files start with `using` and replace `--template-file` on the CLI.
