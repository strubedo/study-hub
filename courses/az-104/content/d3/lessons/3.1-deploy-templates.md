## The deployment model

A deployment is itself an Azure resource (`Microsoft.Resources/deployments`) created at a **scope**: a resource group, a subscription, a management group or the tenant. The scope decides which resources the template may declare at its top level, which command you run and where the deployment history is kept. ARM JSON templates and Bicep files use the same commands; for a `.bicep` file the CLI or PowerShell compiles it first.

## Deployment scopes and commands

| Scope | Typical content | Azure CLI | Azure PowerShell | Bicep `targetScope` |
|---|---|---|---|---|
| Resource group | VMs, VNets, storage accounts | `az deployment group create -g <rg>` | `New-AzResourceGroupDeployment -ResourceGroupName <rg>` | `'resourceGroup'` (default) |
| Subscription | Resource groups, policy and role assignments, budgets | `az deployment sub create -l <location>` | `New-AzSubscriptionDeployment -Location <location>` (alias `New-AzDeployment`) | `'subscription'` |
| Management group | Policy definitions and assignments, role assignments | `az deployment mg create -m <mg> -l <location>` | `New-AzManagementGroupDeployment -ManagementGroupId <mg> -Location <location>` | `'managementGroup'` |
| Tenant | Management groups, tenant-wide role assignments | `az deployment tenant create -l <location>` | `New-AzTenantDeployment -Location <location>` | `'tenant'` |

Subscription, management group and tenant deployments need a **location**: not for the resources, but for storing the deployment metadata. Resource group deployments use the group's location.

A template at a higher scope can still deploy resource-group resources through nested deployments (Bicep modules with `scope: resourceGroup('rg-name')`). A classic pattern is a subscription-scope Bicep file that creates `rg-web-prod` and then deploys a module into it.

## Deploying: portal, CLI and PowerShell

**Portal:** search **Deploy a custom template** > **Build your own template in editor** (paste the JSON there), **Save**, choose subscription, resource group and parameter values, then **Review + create**. You can also redeploy an entry from a resource group's **Deployments** blade with **Redeploy**.

**Azure CLI** (Cloud Shell or a local install on Windows, macOS or Linux):

```bash
# inline parameters
az deployment group create -g rg-web-prod -n deploy-web --template-file main.bicep --parameters environment=prod count=3

# JSON parameter file, then an override (later values win)
az deployment group create -g rg-web-prod --template-file main.json --parameters @main.parameters.json --parameters count=4

# Bicep parameter file (no --template-file)
az deployment group create -g rg-web-prod --parameters main.prod.bicepparam

# subscription scope
az deployment sub create -l eastus --template-file rg.bicep
```

**Azure PowerShell** (PowerShell 7 on any OS, or Cloud Shell):

```powershell
New-AzResourceGroupDeployment -Name deploy-web -ResourceGroupName rg-web-prod `
  -TemplateFile ./main.json -TemplateParameterFile ./main.parameters.json

New-AzResourceGroupDeployment -ResourceGroupName rg-web-prod -TemplateFile ./main.bicep -environment prod

New-AzSubscriptionDeployment -Location eastus -TemplateFile ./rg.bicep
```

The deployment **name** defaults to the template file name (for example `main`). Reusing a name replaces that history entry, so give important deployments distinct names.

## Incremental and complete mode

| | Incremental (default) | Complete |
|---|---|---|
| Resources in the template | Created or updated | Created or updated |
| Resources in the resource group but **not** in the template | **Left alone** | **Deleted** |
| Conditional resource whose condition is false | Left alone if it exists | Deleted (API 2019-05-10 and later, current CLI and PowerShell) |
| Where supported | All scopes | Root-level resource group deployments only; not for subscription-level deployments, not for nested or linked templates; not in the portal |
| Locked resource group | n/a | A lock stops the deletions |

Set it with `--mode Complete` (CLI) or `-Mode Complete` (PowerShell).

Two incremental-mode subtleties matter:

- **Properties aren't merged.** When a resource in the template already exists, *all* its properties are reapplied. A property you leave out is reset to its default; it isn't "kept as is". Always describe the full desired state of each resource.
- **Subnets.** Redeploying a VNet without its `subnets` array can try to remove the subnets. Define subnets inside the VNet resource, not only as separate child resources.

Microsoft Learn now marks complete mode as **not recommended** and says it will be gradually deprecated; to have deployments delete what's no longer in the file, it points you to **deployment stacks** (below). The exam can still ask what complete mode deletes, so know the table.

> **Exam tip:** Resource group contains A, B, C. Template contains A, B, D. Incremental leaves A, B, C, D. Complete leaves A, B, D and deletes C.

## Preview changes with what-if

What-if compares the template with the current state and predicts changes, without deploying:

```bash
az deployment group what-if -g rg-web-prod --template-file main.bicep --parameters environment=prod
az deployment group create -g rg-web-prod --template-file main.bicep --confirm-with-what-if   # preview, then prompt
```

```powershell
New-AzResourceGroupDeployment -ResourceGroupName rg-web-prod -TemplateFile ./main.bicep -WhatIf
Get-AzResourceGroupDeploymentWhatIfResult -ResourceGroupName rg-web-prod -TemplateFile ./main.bicep
```

The change types are **Create**, **Delete** (only in complete mode), **Ignore** (exists but not in the template), **NoChange**, **NoEffect**, **Modify** and **Deploy** (redeployed, can't tell whether properties change). Some property changes are reported as noise; read Modify results critically. Run what-if before every complete-mode deployment.

## Deployment history

Each scope keeps up to **800** deployments. Azure deletes the oldest automatically once you pass 700, down to 600; if a `CanNotDelete` lock prevents that, new deployments can fail at 800. Deleting a history entry never deletes the deployed resources.

```bash
az deployment group list -g rg-web-prod -o table
az deployment group show -g rg-web-prod -n deploy-web --query properties.provisioningState
az deployment operation group list -g rg-web-prod -n deploy-web -o table   # per-resource results and errors
```

```powershell
Get-AzResourceGroupDeployment -ResourceGroupName rg-web-prod
Get-AzResourceGroupDeploymentOperation -ResourceGroupName rg-web-prod -DeploymentName deploy-web
```

In the portal: resource group > **Settings** > **Deployments**. Each entry shows inputs, outputs, the template and a correlation ID for support. `--rollback-on-error` (CLI) or `-RollbackToLastDeployment` (PowerShell) redeploys the last successful deployment if this one fails.

## Template specs and deployment stacks (high level)

**Template specs** (`Microsoft.Resources/templateSpecs`) store a template as a versioned Azure resource. Teams with read access to the spec can deploy it without having the file, and you control access with Azure RBAC.

```bash
az ts create -g rg-templates -n ts-storage -v 1.0 -l eastus --template-file main.json
id=$(az ts show -g rg-templates -n ts-storage -v 1.0 --query id -o tsv)
az deployment group create -g rg-web-prod --template-spec $id
```

**Deployment stacks** (`Microsoft.Resources/deploymentStacks`) manage the resources a template creates as one unit. When you update a stack and a resource is gone from the file, the `actionOnUnmanage` setting decides whether it is detached or deleted, and **deny settings** can block changes or deletion of managed resources outside the stack. Commands: `az stack group create` / `New-AzResourceGroupDeploymentStack` (also `sub` and `mg` scopes). This is Microsoft's recommended replacement for complete mode.

## Permissions

To deploy you need `Microsoft.Resources/deployments/*` at the scope plus write permission on every resource type in the template; **Contributor** on the resource group covers both. A template that creates role assignments also needs `Microsoft.Authorization/roleAssignments/write` (Owner, User Access Administrator or Role Based Access Control Administrator).

## Try it yourself

Azure Cloud Shell (Bash). Cost: cents. This lab shows complete mode deleting something.

```bash
rg=rg-lab-d3deploy; az group create -n $rg -l eastus
# an "unmanaged" resource created by hand
az network nsg create -g $rg -n nsg-manual
cat > vnet.bicep <<'EOF'
resource vnet 'Microsoft.Network/virtualNetworks@2025-01-01' = {
  name: 'vnet-lab'
  location: resourceGroup().location
  properties: {
    addressSpace: {
      addressPrefixes: [
        '10.50.0.0/16'
      ]
    }
    subnets: [
      {
        name: 'snet-a'
        properties: {
          addressPrefix: '10.50.1.0/24'
        }
      }
    ]
  }
}
EOF
az deployment group what-if -g $rg --template-file vnet.bicep                 # nsg-manual: Ignore
az deployment group what-if -g $rg --template-file vnet.bicep --mode Complete # nsg-manual: Delete
az deployment group create -g $rg -n lab1 --template-file vnet.bicep --mode Complete --confirm-with-what-if
az resource list -g $rg --query "[].name" -o tsv
az deployment group list -g $rg -o table
```

Answer `y` at the prompt and confirm that `nsg-manual` is gone. Clean up: `az group delete -n $rg --yes --no-wait`.

## Key takeaways

- Four scopes, four command families: `az deployment group|sub|mg|tenant create`; `New-AzResourceGroupDeployment`, `New-AzSubscriptionDeployment`, `New-AzManagementGroupDeployment`, `New-AzTenantDeployment`. Non-RG scopes need a location.
- Incremental (default) never deletes; complete deletes resources in the group that aren't in the template (including false-condition resources), root RG deployments only, blocked by locks.
- Incremental still resets omitted properties to defaults.
- What-if previews Create, Delete, Modify, NoChange, Ignore, Deploy, NoEffect; `--confirm-with-what-if` prompts first.
- History: 800 per scope, auto-cleanup; deleting history doesn't delete resources.
- Template specs share versioned templates; deployment stacks manage and protect resource sets and replace complete mode.
