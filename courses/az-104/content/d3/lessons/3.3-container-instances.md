## Containers without servers or orchestrators

**Azure Container Instances (ACI)** runs Linux or Windows containers on demand without VMs to manage and without a Kubernetes cluster. You ask for CPU and memory, ACI pulls the image and starts it, and you pay per second for what you requested while the container group runs. It suits simple web apps and APIs, scheduled or event-driven tasks, build agents and burst capacity. It doesn't give you autoscale, rolling upgrades or service discovery across many groups; those belong to Container Apps or AKS.

ACI supports only **x64** images; ARM64-only images aren't supported.

## The container group

The top-level ACI resource is the **container group** (`Microsoft.ContainerInstance/containerGroups`), a set of containers scheduled **on the same host**, similar to a Kubernetes pod. The containers in a group share:

- **Lifecycle**: they're deployed, restarted and deleted together. Updating the group restarts all its containers; you can't restart one container on its own.
- **Network**: one IP address (public or private) and one optional DNS name label; containers reach each other on `localhost` on any port.
- **Storage volumes**: Azure Files shares, `emptyDir`, secret and git repo volumes are defined at group level and mounted into each container that needs them.
- The **restart policy** and the **OS type**.

Learn's limits: **multi-container groups are Linux only** (Windows groups hold one container); up to 60 containers and 20 volumes per group and 5 ports per IP address.

> **Exam tip:** "An app container and a log-shipping sidecar must share a local network and a volume, and start and stop together": put both in one container group. "Scale the web tier independently from the worker": separate groups, or a different service.

## Sizing: requests and limits

Each container declares a **resource request** (`cpu`, `memoryInGB`). The group is allocated the **sum of the requests** of its containers: two containers each requesting 1 CPU make a 2-CPU group. A container can also set a **limit** at or above its request, up to the group total, so it can borrow spare capacity. A group needs at least **1 CPU and 1 GB** in total; individual containers can request less. The standard maximum per group in Learn's current resource table is 31 vCPU and 240 GB, and Learn advises that groups above 4 vCPU and 16 GB may hit regional capacity limits.

## OS type, restart policy and IP addressing

- **OS type** (`--os-type Linux|Windows`) is fixed for the group.
- **Restart policy** applies to every container in the group:

| Policy | Behaviour |
|---|---|
| **Always** (default) | Containers are restarted whenever they exit. Use for long-running services |
| **OnFailure** | Restarted only when the process exits with a non-zero code; runs at least once |
| **Never** | Not restarted after a successful (exit code 0) exit. Learn notes the platform might still restart a container after a non-zero exit |

When a container with `OnFailure` or `Never` finishes, its state becomes **Terminated** and you stop paying for compute. You read the output with `az container logs`.

- **Public IP with DNS name label**: `--ip-address Public --ports 80 --dns-name-label contoso-hello` gives an FQDN of the form `<label>.<region>.azurecontainer.io`. The IP address can change when the group restarts, so clients should use the FQDN.
- **Virtual network deployment**: `--vnet vnet-app --subnet snet-aci` puts the group on a private IP in a subnet **delegated to Microsoft.ContainerInstance/containerGroups** that holds only container groups (Learn recommends at least a /24). In a virtual network the group **can't have a public IP or DNS name label**, outbound internet traffic must use a **NAT gateway**, global VNet peering isn't supported, and the subnet must be in the same subscription.

## Environment variables, secure values and volumes

`--environment-variables KEY=value` sets plain values that appear in the container group's properties. `--secure-environment-variables DB_PASSWORD=<password>` (YAML `secureValue`) sets values that are **not returned** when you view the group's properties, only inside the container.

Mounting an **Azure Files share** gives a stateless container persistent storage. Learn's limitations: Linux containers only, the container must run as root, SMB (CIFS) only, and the mount hides any files already at the mount path.

```bash
az container create -g rg-aci-prod -n ci-files-01 --image mcr.microsoft.com/azuredocs/aci-hellofiles \
  --os-type Linux --cpu 1 --memory 1.5 --ports 80 --dns-name-label contoso-files01 \
  --azure-file-volume-account-name stcontosodata01 --azure-file-volume-account-key <storage-account-key> \
  --azure-file-volume-share-name acishare --azure-file-volume-mount-path /aci/logs/
```

## Pulling from Azure Container Registry with a managed identity

ACI can pull private images with registry credentials (`--registry-login-server`, `--registry-username`, `--registry-password`) or with a **managed identity**. Learn states that ACI **doesn't support system-assigned identities for ACR image pulls**: use a **user-assigned managed identity** with **AcrPull** on the registry, and pass it both as the group's identity and as the registry identity.

```bash
az identity create -g rg-aci-prod -n id-aci-pull
idId=$(az identity show -g rg-aci-prod -n id-aci-pull --query id -o tsv)
idPrincipal=$(az identity show -g rg-aci-prod -n id-aci-pull --query principalId -o tsv)
acrId=$(az acr show -n crcontosoprod --query id -o tsv)
az role assignment create --assignee-object-id $idPrincipal --assignee-principal-type ServicePrincipal \
  --role AcrPull --scope $acrId
az container create -g rg-aci-prod -n ci-web-01 --image crcontosoprod.azurecr.io/web/frontend:1.0 \
  --os-type Linux --cpu 1 --memory 1.5 --ports 80 --dns-name-label contoso-web01 \
  --assign-identity $idId --acr-identity $idId
```

## Create a container group

**Portal:** **Create a resource** > **Container Instances** > **Create**. **Basics**: resource group, **Container name**, region, availability zone (optional), **Image source** (quickstart images, Azure Container Registry or another registry), image, **OS type** and **Size** (CPU cores, memory). **Networking**: **Public**, **Private** (virtual network) or **None**, DNS name label and ports. **Advanced**: **Restart policy**, environment variables (with a **Secure** column) and command override. **Review + create**. The portal creates a single-container group; multi-container groups need YAML, an ARM/Bicep template or code.

**Azure CLI:**

```bash
az container create -g rg-aci-prod -n ci-hello-01 \
  --image mcr.microsoft.com/azuredocs/aci-helloworld:latest \
  --os-type Linux --cpu 1 --memory 1.5 --restart-policy Always \
  --ip-address Public --ports 80 --dns-name-label contoso-hello01
az container show -g rg-aci-prod -n ci-hello-01 --query "{fqdn:ipAddress.fqdn, state:instanceView.state}" -o table
az container logs -g rg-aci-prod -n ci-hello-01
az container exec -g rg-aci-prod -n ci-hello-01 --exec-command "/bin/sh"
```

`az container exec` opens an interactive command in a running container (add `--container-name` in multi-container groups); `az container attach` streams output; `az container export -f group.yaml` saves the configuration as YAML.

**Azure PowerShell** (Az.ContainerInstance builds in-memory objects first):

```powershell
$port = New-AzContainerInstancePortObject -Port 80 -Protocol TCP
$ctr  = New-AzContainerInstanceObject -Name hello -Image mcr.microsoft.com/azuredocs/aci-helloworld:latest `
          -RequestCpu 1 -RequestMemoryInGb 1.5 -Port @($port)
New-AzContainerGroup -ResourceGroupName rg-aci-prod -Name ci-hello-01 -Location eastus -Container $ctr `
  -OsType Linux -RestartPolicy Always -IPAddressType Public -IPAddressDnsNameLabel contoso-hello01 -IPAddressPort @($port)
Get-AzContainerInstanceLog -ResourceGroupName rg-aci-prod -ContainerGroupName ci-hello-01 -ContainerName hello
```

## YAML deployment

YAML is the concise way to define multi-container groups; `az container create -g <rg> -f group.yaml` deploys it (there's no PowerShell YAML equivalent; PowerShell uses objects or `-JsonFilePath`). In this example the group is allocated **1.5 CPU and 2 GB** (the sum of the requests):

```yaml
apiVersion: '2021-10-01'
location: eastus
name: ci-web-sidecar
properties:
  osType: Linux
  restartPolicy: Always
  containers:
  - name: web
    properties:
      image: mcr.microsoft.com/azuredocs/aci-helloworld:latest
      ports:
      - port: 80
      resources:
        requests:
          cpu: 1.0
          memoryInGB: 1.5
      environmentVariables:
      - name: APP_MODE
        value: production
      - name: DB_PASSWORD
        secureValue: <password>
  - name: log-agent
    properties:
      image: mcr.microsoft.com/azuredocs/aci-tutorial-sidecar
      resources:
        requests:
          cpu: 0.5
          memoryInGB: 0.5
  ipAddress:
    type: Public
    dnsNameLabel: contoso-websidecar
    ports:
    - protocol: TCP
      port: 80
type: Microsoft.ContainerInstance/containerGroups
```

Note that a port must be listed both on the container and under the group's `ipAddress.ports` to be reachable from outside.

## Updating a group

You update a running group by re-running `az container create` (or redeploying YAML) with the same name and at least one changed property; all containers restart. Learn lists properties that **can't be updated in place** and require deleting and recreating the group: **OS type, CPU, memory or GPU resources, restart policy**, network profile (network profiles are retired from API version 2021-07-01) and **availability zone**. A terminated or deleted group is always deployed as new.

## Try it yourself

Azure Cloud Shell (Bash). Cost: a 1 vCPU / 1.5 GB Linux group for half an hour costs a few US cents; a task container that terminates stops billing.

```bash
rg=rg-lab-d3aci; label=contosolab$RANDOM
az group create -n $rg -l eastus
az container create -g $rg -n ci-lab-web --image mcr.microsoft.com/azuredocs/aci-helloworld:latest \
  --os-type Linux --cpu 1 --memory 1.5 --ports 80 --dns-name-label $label \
  --environment-variables APP_MODE=lab --secure-environment-variables LAB_SECRET='<password>'
az container show -g $rg -n ci-lab-web --query "{fqdn:ipAddress.fqdn,ip:ipAddress.ip}" -o table
curl -s http://$label.eastus.azurecontainer.io | head -n 5
az container show -g $rg -n ci-lab-web --query "containers[0].environmentVariables"   # secure value not shown
# A run-to-completion task
az container create -g $rg -n ci-lab-task --image mcr.microsoft.com/azuredocs/aci-wordcount:latest \
  --os-type Linux --cpu 1 --memory 1.5 --restart-policy OnFailure
az container show -g $rg -n ci-lab-task --query "containers[0].instanceView.currentState.state" -o tsv
az container logs -g $rg -n ci-lab-task
az container export -g $rg -n ci-lab-web -f ~/ci-lab-web.yaml && head -n 20 ~/ci-lab-web.yaml
```

Run the state query again until it shows `Terminated`, then read the logs. In the portal, open **ci-lab-web** > **Containers** to see **Events**, **Properties**, **Logs** and **Connect**. Clean up: `az group delete -n $rg --yes --no-wait`.

## Key takeaways

- The container group is the unit of deployment: same host, shared lifecycle, IP, DNS label, volumes, restart policy and OS type; multi-container groups are Linux only.
- Group size is the sum of container requests; minimum 1 CPU and 1 GB per group; limits let a container borrow up to the group total.
- Restart policies: **Always** (default), **OnFailure**, **Never**; finished task containers show **Terminated**.
- Public IP plus DNS label gives `<label>.<region>.azurecontainer.io`; VNet deployment uses a delegated subnet, no public IP or DNS label, NAT gateway for outbound.
- Secure environment variables aren't shown in properties; Azure Files mounts are Linux-only and need root.
- ACR pulls with a managed identity need a **user-assigned** identity with AcrPull (`--assign-identity` and `--acr-identity`).
- CPU, memory, restart policy, OS type and zone changes require deleting and recreating the group.
