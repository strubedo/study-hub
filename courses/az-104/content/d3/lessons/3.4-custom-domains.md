## Requirements

Mapping an existing domain such as `www.contoso.com` or `contoso.com` to an App Service app needs:

- A **paid tier**: Learn's prerequisite is "not the Free (F1) tier". The limits table allows custom domains from **Shared** upward, but Shared can't bind a TLS certificate to them, so production HTTPS starts at **Basic**.
- Permission to edit the domain's **public** DNS zone (Azure DNS or any registrar). Private DNS zones aren't supported for custom domains.
- Two DNS records per host name: the **mapping** record and the **ownership verification** record.

If you don't own a domain, you can buy an **App Service domain** in Azure, which creates and manages the DNS zone for you.

## Which records

| Host name | Mapping record | Verification record | Notes |
|---|---|---|---|
| **Apex / root** (`contoso.com`) | **A** record, host `@`, value = the app's **inbound IP address** | **TXT**, host **`asuid`**, value = the **custom domain verification ID** | Don't use a CNAME at the zone apex (RFC 1912) |
| **Subdomain** (`www.contoso.com`) | **CNAME**, host `www`, value = `<app>.azurewebsites.net` (recommended) | **TXT**, host **`asuid.www`** | An A record also works but the app's IP can change; the CNAME follows the app |
| **Wildcard** (`*.contoso.com`) | **CNAME**, host `*` | **TXT**, host `asuid` | Needs a wildcard certificate for HTTPS |

The **domain verification ID** is shown in the **Add custom domain** dialog (and on the app's **Custom domains** page) and is exposed as the app's `customDomainVerificationId` property. You can read it with:

```bash
az webapp show -g rg-web-prod -n app-contoso-web --query customDomainVerificationId -o tsv
```

> **Watch out:** The verification TXT record's host is **`asuid.` followed by the subdomain**: `asuid.www` for `www.contoso.com`, `asuid.shop` for `shop.contoso.com`, and plain `asuid` for the apex. A TXT record named `asuid` doesn't verify `www.contoso.com`. Learn calls the TXT record optional but "highly recommended" because it prevents **subdomain takeover**; validation of a host name that's already in use elsewhere depends on it.

A real-world wrinkle: if you add the TXT record but not yet the A or CNAME, App Service treats it as a **domain migration** (move a live domain to App Service without downtime) and lets validation succeed, but the domain doesn't resolve to the app until you change the mapping record.

## Map the domain

**Portal:** app > **Settings** > **Custom domains** > **Add custom domain**:

1. **Domain provider**: **All other domain services** (or App Service Domain).
2. **TLS/SSL certificate**: **App Service Managed Certificate** (Basic and up) or **Add certificate later**.
3. **TLS/SSL type**: **SNI SSL** or **IP Based SSL** (Standard and up).
4. **Domain**: the FQDN. The dialog fills **Hostname record type** (A for apex, CNAME for subdomains) and shows the exact records to create.
5. Create the records at your DNS provider, then select **Validate**, then **Add**.

The domain then shows in the list as **Secured** (if a certificate was bound) or with **No binding** until you add one.

**Azure CLI:** create the DNS records first (here in Azure DNS), then add the host name:

```bash
verifyId=$(az webapp show -g rg-web-prod -n app-contoso-web --query customDomainVerificationId -o tsv)
az network dns record-set cname set-record -g rg-dns-prod -z contoso.com -n www \
  -c app-contoso-web.azurewebsites.net
az network dns record-set txt add-record -g rg-dns-prod -z contoso.com -n asuid.www -v $verifyId
az webapp config hostname add -g rg-web-prod --webapp-name app-contoso-web --hostname www.contoso.com
az webapp config hostname list -g rg-web-prod --webapp-name app-contoso-web -o table
```

For the apex, get the app's inbound IP (`az webapp show --query inboundIpAddress` or the **Custom domains** page) and create an A record `@` plus a TXT record `asuid`.

**Azure PowerShell:** Learn's current sample adds the host name binding through the REST API with `Invoke-AzRestMethod -Method PUT` on `.../sites/<app>/hostNameBindings/<hostname>`. The long-standing cmdlet approach also works: pass the full list of host names, including the default one, to `Set-AzWebApp`:

```powershell
Set-AzWebApp -ResourceGroupName rg-web-prod -Name app-contoso-web `
  -HostNames @('www.contoso.com', 'app-contoso-web.azurewebsites.net')
```

Then add a certificate and binding as described in the certificates lesson (`az webapp config ssl create --hostname www.contoso.com` followed by `az webapp config ssl bind`, or the portal's **Add binding**).

## Troubleshooting

| Symptom | Likely cause |
|---|---|
| Validation fails on the TXT record | TXT host wrong (`asuid` vs `asuid.www`), value isn't the verification ID, or DNS hasn't propagated |
| Validation fails on the CNAME | CNAME points to another name or the record hasn't propagated; check with `nslookup -type=cname www.contoso.com` |
| Browser shows a 404 from App Service for the custom domain | Host name added in DNS but not on the app (or vice versa), or the client cached an old IP |
| Browser warns "not secure" | Domain mapped but no TLS binding yet |
| Apex stopped working after adding an IP-based binding | IP SSL assigned a new dedicated IP; remap the A record |
| Managed certificate won't issue for `www` | CNAME goes through an intermediate name instead of pointing straight at `<app>.azurewebsites.net` |

Also remember that custom domain names are **slot-specific**: they stay with the production slot during swaps, which is exactly what you want.

## Try it yourself

Azure Cloud Shell (Bash). Cost: a B1 plan for under an hour, a few US cents, plus the small monthly charge Azure DNS applies to a hosted zone (see the Azure DNS pricing page). Without your own domain you can still create an Azure DNS zone for `contoso.com`, build the exact records and watch validation fail at the last step because the public internet doesn't delegate `contoso.com` to your zone. With a domain you own, use it instead and the last command succeeds.

```bash
rg=rg-lab-d3dns; plan=asp-lab-dns; app=app-lab-dns-$RANDOM$RANDOM; zone=contoso.com
az group create -n $rg -l eastus
az appservice plan create -g $rg -n $plan --sku B1 --is-linux
az webapp create -g $rg -p $plan -n $app --container-image-name mcr.microsoft.com/azuredocs/aci-helloworld:latest
verifyId=$(az webapp show -g $rg -n $app --query customDomainVerificationId -o tsv)
inboundIp=$(az webapp show -g $rg -n $app --query inboundIpAddress -o tsv)
az network dns zone create -g $rg -n $zone
az network dns record-set cname set-record -g $rg -z $zone -n www -c $app.azurewebsites.net
az network dns record-set txt add-record -g $rg -z $zone -n asuid.www -v $verifyId
az network dns record-set a add-record -g $rg -z $zone -n @ -a $inboundIp
az network dns record-set txt add-record -g $rg -z $zone -n asuid -v $verifyId
az network dns record-set list -g $rg -z $zone --query "[].{name:name, type:type}" -o table
az webapp config hostname add -g $rg --webapp-name $app --hostname www.$zone   # fails: public DNS can't see your zone
```

Compare the record set list with the table in this lesson. In the portal, open the app's **Custom domains** > **Add custom domain** and enter `www.contoso.com` to see the records the dialog asks for. Clean up: `az group delete -n $rg --yes --no-wait`.

## Key takeaways

- Custom domains need a paid tier (not Free); HTTPS for them needs Basic or higher.
- Apex: A record `@` to the app's inbound IP plus TXT `asuid`. Subdomain: CNAME to `<app>.azurewebsites.net` plus TXT `asuid.<subdomain>`.
- The TXT value is the custom domain verification ID (`customDomainVerificationId`); it proves ownership and prevents subdomain takeover.
- Add the host name with the portal's **Add custom domain**, `az webapp config hostname add`, `Set-AzWebApp -HostNames` or the hostNameBindings REST call; then bind a certificate.
- IP-based TLS changes the inbound IP, so the apex A record must be updated; custom domains don't swap between slots.
