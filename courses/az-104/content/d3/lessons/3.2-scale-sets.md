## What a scale set gives you

**Azure Virtual Machine Scale Sets** manage a group of VMs as one resource: they create instances from a model, spread them across fault domains or zones, add and remove instances automatically (**autoscale**), and roll out model changes. The scale set itself is free; you pay for the VMs, disks and networking it creates. A scale set holds up to **1,000** VMs from Marketplace or Azure Compute Gallery images (600 from a legacy managed image).

## Orchestration modes

| | **Flexible** (recommended, default) | **Uniform** |
|---|---|---|
| Instances | Standard Azure VMs (`Microsoft.Compute/virtualMachines`) managed with the normal VM APIs, CLI and portal | Scale set VMs managed only through scale set VM APIs |
| Mix of sizes, Spot plus regular | Yes | No (identical instances) |
| Add an existing VM / create without a scaling profile | Yes (VMs created into the set) | No |
| Zones and fault domains | Specify 1, 2 or 3 zones; max spreading or fixed FD count; you can place a VM in a specific zone or FD | Zones; FD spreading |
| Update domains | **Deprecated**: maintenance runs FD by FD | 5 UDs per placement group |
| SLA (per Learn's comparison) | 99.95% spread across FDs; 99.99% across zones | 99.95% (FD > 1); 99.99% across zones |
| Outbound internet | **No default outbound access**: add a NAT gateway, load balancer outbound rule or public IPs | Plan explicit outbound too |

Learn says VM scale sets created with **PowerShell and Azure CLI default to Flexible orchestration** when you don't specify a mode (since November 2023), and calls Flexible the recommended mode. The orchestration mode is set at creation and **can't be changed later**.

> **Exam tip:** "Run different VM sizes in one set", "combine Spot and on-demand", "manage instances with ordinary VM commands", "place an instance in a specific fault domain": Flexible. "Older template that relies on the scale set VM API or automatic OS image upgrades on identical instances": Uniform.

## Create a scale set

**Portal:** **Virtual machine scale sets** > **Create**: resource group, name, region, **availability zones**, **orchestration mode** (Flexible preselected), security type, scaling (manual or autoscale with min/max), image, size, authentication; **Networking** (VNet, NIC, load balancer); **Management** (upgrade policy, scale-in policy, instance protection), **Review + create**.

**Azure CLI:**

```bash
az vmss create -g rg-web-prod -n vmss-web \
  --orchestration-mode Flexible \
  --image Ubuntu2204 --vm-sku Standard_D2s_v5 \
  --instance-count 2 \
  --zones 1 2 3 \
  --admin-username azureuser --generate-ssh-keys \
  --vnet-name vnet-hub --subnet snet-web \
  --lb lb-web --upgrade-policy-mode Manual \
  --scale-in-policy NewestVM
```

**Azure PowerShell:**

```powershell
New-AzVmss -ResourceGroupName rg-web-prod -VMScaleSetName vmss-web -Location eastus `
  -OrchestrationMode Flexible -ImageName Win2022Datacenter -VmSize Standard_D2s_v5 `
  -InstanceCount 2 -Zone 1,2,3 -Credential (Get-Credential) `
  -VirtualNetworkName vnet-hub -SubnetName snet-web -UpgradePolicyMode Manual -ScaleInPolicy NewestVM
```

Scale manually with `az vmss scale -g rg-web-prod -n vmss-web --new-capacity 4` or `Update-AzVmss -ResourceGroupName rg-web-prod -VMScaleSetName vmss-web -SkuCapacity 4`.

## Zones and fault domains

- **Zone-spanning** (zones 1, 2, 3): instances spread across zones for the 99.99% SLA. By default the spread is best effort; `zoneBalance: true` enforces strict balance.
- **Zonal** (one zone): lower latency between instances, no zone protection.
- **Regional** (no zones): instances spread over fault domains (`--platform-fault-domain-count`).

You can add zones to an existing regional scale set (one way only; new instances go to the new zones), but you can't go back to regional.

## Autoscale

Autoscale is an Azure Monitor feature that adjusts the instance count of the scale set. Its settings:

| Element | Meaning |
|---|---|
| **Profile** (portal: scale condition) | Default, recurring (for example weekdays) or fixed-date; up to 20 per setting. Fixed-date profiles win over recurring, which win over default |
| **Instance limits** | **Minimum**, **maximum**, **default**. Autoscale never goes outside min/max; if metrics can't be read it scales out to the default when below it |
| **Rules** | Up to 10 per profile. Metric, time grain statistic, operator, threshold, **duration** (time window), time aggregation, action (increase or decrease by a count or percent, or to a count), **cool down** |
| Notifications | Email and webhooks |

Rule evaluation, from Learn's autoscale settings page:

- **Scale out if any scale-out rule is met.** If several scale-out rules trigger together, autoscale uses the one that gives the **highest** capacity.
- **Scale in only if all scale-in rules are met.** If several scale-in rules apply, it removes the fewest instances.
- After a scale action, each rule waits for its own **cool down** (5 minutes is the common default) before it can act again.
- Autoscale avoids **flapping**: it may defer or reduce a scale-in that would immediately trigger a scale-out.
- The autoscale job runs every 30 to 60 seconds.
- Manually setting a capacity outside min/max is reset by autoscale on its next run.

Worked example: min 2, max 10, default 2, current 4 instances. Rule A: Percentage CPU > 70 (average, 10 minutes), increase by 2. Rule B: Network In Total > threshold, increase by 3. Rule C: Percentage CPU < 30, decrease by 1. Rule D: Network In Total < lower threshold, decrease by 1.

| Situation | Result |
|---|---|
| Rule A and Rule B both met | Scale to **7** (4 + 3, the higher of 6 and 7) |
| Only Rule A met | 6 |
| CPU 25%, network above the lower threshold | **No change**: rule D isn't met, and scale-in needs all scale-in rules |
| Both scale-in rules met | 3 |
| Rule A met while at 9 | 10 (capped at max) |

**Portal:** scale set > **Availability + scale** > **Scaling** > **Custom autoscale** > set instance limits > **Add a rule** (scale out) and **Add a rule** (scale in) > **Save**.

**Azure CLI:**

```bash
az monitor autoscale create -g rg-web-prod --resource vmss-web \
  --resource-type Microsoft.Compute/virtualMachineScaleSets \
  --name autoscale-web --min-count 2 --max-count 10 --count 2
az monitor autoscale rule create -g rg-web-prod --autoscale-name autoscale-web \
  --condition "Percentage CPU > 70 avg 10m" --scale out 2 --cooldown 5
az monitor autoscale rule create -g rg-web-prod --autoscale-name autoscale-web \
  --condition "Percentage CPU < 30 avg 10m" --scale in 1 --cooldown 5
```

**Azure PowerShell** (Az.Monitor): build rules with `New-AzAutoscaleScaleRuleObject`, a profile with `New-AzAutoscaleProfileObject`, then `New-AzAutoscaleSetting`.

## Scale-in policy and instance protection

When autoscale (or you) reduce the capacity, the **scale-in policy** chooses which VMs go:

- **Default**: balance across zones first, then across fault domains, then delete the VM with the highest instance ID.
- **NewestVM**: delete the newest VM (after zone balancing).
- **OldestVM**: delete the oldest VM (after zone balancing).

In a zone-imbalanced set, VMs in the over-populated zones are removed first; the policy then applies inside those zones. **Instance protection** exempts a specific VM from scale-in, or from scale-in and model updates (scale set actions).

```bash
az vmss update -g rg-web-prod -n vmss-web --scale-in-policy OldestVM
```

## Upgrade policy

The upgrade policy decides how instances pick up changes to the scale set model (new image, extension, size):

- **Manual** (default when not set): nothing changes until you update instances (`az vmss update-instances` for Uniform, or reimage/update the VMs).
- **Automatic**: all instances may be updated at once, in no guaranteed order.
- **Rolling**: in batches, with a pause and health checks; optional MaxSurge creates new instances before removing old ones.

Learn's upgrade policy page documents Manual, Automatic and Rolling for Flexible scale sets (an older tutorial still says upgrade modes aren't supported on Flexible; the newer page is the reference).

## Try it yourself

Azure Cloud Shell (Bash). Cost: two small instances for under an hour, about a dollar or less. Delete promptly.

```bash
rg=rg-lab-d3vmss; az group create -n $rg -l eastus
az vmss create -g $rg -n vmss-lab --orchestration-mode Flexible --image Ubuntu2204 \
  --vm-sku Standard_D2s_v5 --instance-count 2 --zones 1 2 3 \
  --admin-username azureuser --generate-ssh-keys --upgrade-policy-mode Manual --scale-in-policy NewestVM
az vm list -g $rg --query "[].{name:name, zone:zones[0]}" -o table      # Flexible instances are normal VMs
az monitor autoscale create -g $rg --resource vmss-lab --resource-type Microsoft.Compute/virtualMachineScaleSets \
  --name as-lab --min-count 2 --max-count 4 --count 2
az monitor autoscale rule create -g $rg --autoscale-name as-lab --condition "Percentage CPU > 70 avg 5m" --scale out 1
az monitor autoscale rule create -g $rg --autoscale-name as-lab --condition "Percentage CPU < 20 avg 5m" --scale in 1
az monitor autoscale show -g $rg -n as-lab --query "profiles[0].{min:capacity.minimum,max:capacity.maximum,rules:length(rules)}"
```

`az vm list` shows the scale set's instances because Flexible instances are ordinary VMs. In the portal, open the scale set's **Scaling** blade to see your rules and **Instances** to see the zones. Clean up: `az group delete -n $rg --yes --no-wait`.

## Key takeaways

- Flexible orchestration is the default for CLI and PowerShell (since November 2023) and the recommended mode; the mode can't change after creation.
- Flexible: standard VMs, mixed sizes and Spot, FD-by-FD maintenance (UDs deprecated), no default outbound access, up to 1,000 VMs.
- Zone-spanning sets give 99.99%; regional sets spread across fault domains give 99.95%.
- Autoscale: min/max/default limits; scale out if any rule fires (highest capacity wins); scale in only when all scale-in rules fire; per-rule cool down.
- `az vmss create --orchestration-mode --zones --scale-in-policy --upgrade-policy-mode`; `az monitor autoscale create` and `rule create --condition "Percentage CPU > 70 avg 10m" --scale out 2`.
- Scale-in policies: Default, NewestVM, OldestVM (after zone balancing); upgrade policies: Manual, Automatic, Rolling.
