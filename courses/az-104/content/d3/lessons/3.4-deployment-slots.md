## What a slot is

A **deployment slot** is a live app with its own host name (`<app>-<slot>.azurewebsites.net`), its own content and configuration, running on the **same App Service plan instances** as the production app. You deploy a new version to a slot such as `staging`, test it, warm it up, then **swap** it with production. The swap switches routing, so production gets an already-warmed app with no downtime, and the previous production version lands in the staging slot, ready for an immediate swap back if something is wrong.

| Tier | Staging slots per app (besides production) |
|---|---|
| Free, Shared, Basic | None |
| **Standard** | **5** |
| **Premium (v2, v3, v4)** | **20** |
| **Isolated v2** | **20** |

Slots cost nothing extra; they consume the plan's resources. You can't scale a plan down to a tier that supports fewer slots than an app already uses (for example to Standard with more than five slots). Slot names are limited (site name up to 40 characters, slot name up to 19, combined under 59).

## Create a slot

**Portal:** app > **Deployment** > **Deployment slots** > **Add**. Enter a **Name** and choose whether to **clone settings** from an existing slot (app settings, connection strings, framework versions, web sockets, HTTP version, platform bitness). New slots have **no content** and **0%** traffic. Learn notes that private endpoints aren't cloned.

**Azure CLI:**

```bash
az webapp deployment slot create -g rg-web-prod -n app-contoso-web --slot staging --configuration-source app-contoso-web
az webapp deployment slot list -g rg-web-prod -n app-contoso-web -o table
```

**Azure PowerShell:**

```powershell
New-AzWebAppSlot -ResourceGroupName rg-web-prod -Name app-contoso-web -Slot staging -AppServicePlan asp-web-prod
```

Deploy to a slot like to any app, for example `az webapp deploy -g rg-web-prod -n app-contoso-web --slot staging --src-path app.zip --type zip`.

## What swaps and what sticks

**Swapped** (follow the content):

- Language framework versions, 32/64-bit, web sockets
- **App settings** and **connection strings** (unless marked as slot settings)
- Mounted storage accounts (unless marked as slot settings)
- Handler mappings, public certificates, WebJobs content
- Hybrid connections, service endpoints, Azure CDN, path mappings

**Not swapped** (stay with the slot):

- **Custom domain names**, publishing endpoints
- Non-public certificates and **TLS/SSL bindings**
- **Scale settings**, **WebJobs schedulers**
- **Managed identities**, **VNet integration**
- **Protocol settings** (HTTPS Only, TLS version, client certificates)\*, **IP restrictions**\*, **Always On**\*, **diagnostic log settings**\*, **CORS**\*
- Settings ending in `_EXTENSION_VERSION` and settings created by Service Connector

\* Learn notes these can be made swappable again by adding the app setting `WEBSITE_OVERRIDE_PRESERVE_DEFAULT_STICKY_SLOT_SETTINGS=0` to every slot; it's all-or-nothing for that group.

**Slot settings (sticky settings):** an app setting or connection string marked **Deployment slot setting** stays with its slot. Use it for values that differ by environment: the staging database connection string, an `ENVIRONMENT=staging` flag, test API keys.

```bash
az webapp config appsettings set -g rg-web-prod -n app-contoso-web --slot staging \
  --settings FEATURE_X=on --slot-settings ENVIRONMENT=staging
az webapp config connection-string set -g rg-web-prod -n app-contoso-web --slot staging \
  --connection-string-type SQLAzure --slot-settings MainDb="Server=tcp:sql-contoso-test.database.windows.net;Password=<password>"
```

In this example `FEATURE_X` is swappable and `ENVIRONMENT` and `MainDb` are sticky. In PowerShell, `Set-AzWebAppSlotConfigName -ResourceGroupName rg-web-prod -Name app-contoso-web -AppSettingNames ENVIRONMENT -ConnectionStringNames MainDb` marks names as slot settings.

> **Exam tip:** A question that shows settings in two slots and asks what production has **after** the swap: sticky settings keep the production value; every other setting comes from the source (staging) slot.

## How a swap runs

When you swap a source slot (staging) into a target slot (production), App Service:

1. Applies the **target's** slot-specific settings (sticky app settings and connection strings, continuous deployment and authentication settings) to every instance of the **source**, which restarts the source instances. A **swap with preview** pauses here.
2. Waits for every source instance to restart; any failure reverts the source and stops the swap.
3. Initializes local cache if enabled.
4. **Warms up** each source instance with an HTTP request to the root (or your **custom warm-up**: `applicationInitialization` in `web.config`, or the app settings `WEBSITE_SWAP_WARMUP_PING_PATH` and `WEBSITE_SWAP_WARMUP_PING_STATUSES`). Any HTTP response counts as warm unless you restrict the status codes.
5. Swaps the routing rules: production now serves the warmed app.
6. Applies the settings to the old production app (now in staging) and restarts it.

The target stays online throughout. Always make **production the target** so all preparation happens on the staging side. Each warm-up request waits up to 90 seconds and retries up to five times.

**Swap** in the portal: **Deployment slots** > **Swap** > choose **Source** and **Target**, review **Source slot changes** and **Target slot changes**, then **Start Swap** (or select **Perform swap with preview**).

```bash
az webapp deployment slot swap -g rg-web-prod -n app-contoso-web --slot staging --target-slot production
# Swap with preview (multi-phase)
az webapp deployment slot swap -g rg-web-prod -n app-contoso-web --slot staging --target-slot production --action preview
az webapp deployment slot swap -g rg-web-prod -n app-contoso-web --slot staging --target-slot production --action swap
az webapp deployment slot swap -g rg-web-prod -n app-contoso-web --slot staging --target-slot production --action reset   # cancel
```

```powershell
Switch-AzWebAppSlot -ResourceGroupName rg-web-prod -Name app-contoso-web -SourceSlotName staging -DestinationSlotName production
Switch-AzWebAppSlot -ResourceGroupName rg-web-prod -Name app-contoso-web -SourceSlotName staging -DestinationSlotName production `
  -SwapWithPreviewAction ApplySlotConfig      # then CompleteSlotSwap or ResetSlotSwap
```

Swap with preview isn't available when App Service authentication is enabled on either slot.

## Auto swap

**Auto swap** swaps a slot into its target automatically after each deployment to the slot finishes and warms up. Configure it on the **source** slot: **Configuration** > **General settings** > **Auto swap enabled** = On and **Auto swap deployment slot** = production; or `az webapp deployment slot auto-swap -g rg-web-prod -n app-contoso-web --slot staging`; or `Set-AzWebAppSlot ... -AutoSwapSlotName production`. Learn states auto swap **isn't supported for web apps on Linux or Web App for Containers**.

## Routing a percentage of traffic

**Testing in production** sends a share of production traffic to another slot without swapping: on **Deployment slots**, set **Traffic %** for the slot. A routed client is pinned to its slot for the session with the `x-ms-routing-name` cookie (`self` means production). Users can opt in or out with `?x-ms-routing-name=staging` or `?x-ms-routing-name=self`.

```bash
az webapp traffic-routing set -g rg-web-prod -n app-contoso-web --distribution staging=10
az webapp traffic-routing clear -g rg-web-prod -n app-contoso-web
```

PowerShell uses `Add-AzWebAppTrafficRouting` with a routing rule (`ActionHostName`, `ReroutePercentage`, `Name`).

## Try it yourself

Azure Cloud Shell (Bash). Cost: an S1 plan (slots need Standard) for under an hour costs well under one US dollar. Delete promptly.

```bash
rg=rg-lab-d3slot; plan=asp-lab-slot; app=app-lab-slot-$RANDOM$RANDOM
az group create -n $rg -l eastus
az appservice plan create -g $rg -n $plan --sku S1 --is-linux
az webapp create -g $rg -p $plan -n $app --container-image-name mcr.microsoft.com/azuredocs/aci-helloworld:latest
az webapp config appsettings set -g $rg -n $app --settings FEATURE_X=off --slot-settings ENVIRONMENT=production
az webapp deployment slot create -g $rg -n $app --slot staging --configuration-source $app
az webapp config appsettings set -g $rg -n $app --slot staging --settings FEATURE_X=on --slot-settings ENVIRONMENT=staging
az webapp deployment slot swap -g $rg -n $app --slot staging --target-slot production
az webapp config appsettings list -g $rg -n $app --query "[?name=='FEATURE_X' || name=='ENVIRONMENT'].{name:name,value:value,sticky:slotSetting}" -o table
az webapp config appsettings list -g $rg -n $app --slot staging --query "[?name=='FEATURE_X' || name=='ENVIRONMENT'].{name:name,value:value,sticky:slotSetting}" -o table
az webapp traffic-routing set -g $rg -n $app --distribution staging=20
```

After the swap, production should show `FEATURE_X=on` (swapped) and `ENVIRONMENT=production` (sticky), and staging the opposite for `FEATURE_X`. In the portal, open **Deployment slots** to see the 20% traffic split and try **Swap** > **Perform swap with preview**. Clean up: `az group delete -n $rg --yes --no-wait`.

## Key takeaways

- Slots need Standard (5 staging slots), Premium (20) or Isolated (20); they share the plan's instances at no extra charge.
- Swaps: app settings and connection strings (unless sticky), framework settings, handler mappings, WebJobs content, hybrid connections. Stays: custom domains, TLS bindings, scale settings, managed identities, VNet integration, protocol settings, IP restrictions, Always On, CORS, diagnostic settings.
- Mark environment-specific values as **Deployment slot settings** (`--slot-settings`).
- Swap sequence: apply target settings to source, restart, warm up, switch routing; swap with preview pauses after step one (`--action preview`, then `swap` or `reset`).
- Auto swap isn't supported on Linux or containers; traffic routing (`az webapp traffic-routing set --distribution staging=10`) pins clients with the `x-ms-routing-name` cookie.
