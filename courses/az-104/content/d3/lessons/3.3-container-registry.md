## What a container registry does

A container registry stores container images (and other OCI artifacts such as Helm charts) so that compute services can pull them. **Azure Container Registry (ACR)** is Azure's private, managed registry. You push images to it from a workstation or pipeline, or let ACR build them for you, and then Azure Container Instances, Azure Container Apps, App Service, AKS or a VM pulls them.

A few terms the exam uses precisely:

| Term | Meaning | Example |
|---|---|---|
| **Registry** | The Azure resource. Its name is globally unique, 5–50 alphanumeric characters (no hyphens) | `crcontosoprod` |
| **Login server** | The DNS name clients use: `<registry-name>.azurecr.io` in the Azure public cloud (lowercase) | `crcontosoprod.azurecr.io` |
| **Repository** | A collection of images with the same name, which can contain a namespace path | `web/frontend` |
| **Tag** | A label on one image version inside a repository | `web/frontend:1.4.2` |
| **Manifest / digest** | The image description and its SHA-256 hash; an image pulled by digest is immutable | `web/frontend@sha256:<digest>` |

The full image reference you give to a compute service is `login-server/repository:tag`, for example `crcontosoprod.azurecr.io/web/frontend:1.4.2`.

> **Watch out:** `az acr login` and `Connect-AzContainerRegistry` take the **registry name** (`crcontosoprod`), not the login server. Image references in YAML, `az container create --image` or `az containerapp create --image` use the **login server**.

Learn also documents an optional **domain name label (DNL) scope** at creation (`--dnl-scope`), which appends a hash to the login server name (`registryname-<hash>.azurecr.io`) to prevent another tenant from reusing a deleted registry's DNS name. The CLI reference marks the parameter as preview and its default as `Unsecure` (no hash).

## Service tiers (SKUs)

All three SKUs have the same data-plane APIs, Microsoft Entra authentication, webhooks, image deletion and zone redundancy by default in supported regions. They differ in included storage, throughput and a set of Premium-only features. The SKU table on Learn (read November 2026) gives:

| Feature | Basic | Standard | Premium |
|---|---|---|---|
| Included storage | 10 GiB | 100 GiB | 500 GiB |
| Webhooks | 2 | 10 | 500 |
| Anonymous pull access | No | Yes | Yes |
| Artifact cache rules | No | Yes | Yes |
| **Geo-replication** | No | No | **Yes** |
| **Private endpoints (Private Link)** | No | No | **Yes** |
| Public IP network rules (registry firewall) | No | No | **Yes** |
| Customer-managed keys, connected registries, dedicated data endpoints | No | No | Yes |
| **Retention policy for untagged manifests** | No | No | Yes (preview) |
| Tokens and scope maps (non-Entra repository permissions) | Yes | Yes | Yes |

You can change SKU at any time with no downtime (`az acr update --sku Premium` or `Update-AzContainerRegistry -Sku Premium`). Moving down from Premium requires you to remove Premium-only resources first, such as geo-replications.

> **Exam tip:** "Pull images from a registry replica close to each region", "reach the registry only from a virtual network through a private IP", "restrict the registry to listed public IP ranges": all **Premium**. Any requirement that fits in Basic or Standard is answered with the cheapest SKU that has the feature.

## Create a registry

**Portal:** **Create a resource** > **Container Registry** > **Create**. On **Basics** choose the subscription, resource group, **Registry name**, **Location**, **Pricing plan** (Basic, Standard, Premium) and **Role assignment permissions mode** (Learn's portal quickstart now selects **RBAC Registry + ABAC Repository Permissions**; see Authentication below). **Networking** (public access or private endpoint) is only selectable with Premium. **Review + create** > **Create**. The **Overview** blade shows the **Login server**.

**Azure CLI:**

```bash
az group create -n rg-containers-prod -l eastus
az acr create -g rg-containers-prod -n crcontosoprod --sku Standard
az acr show -n crcontosoprod --query loginServer -o tsv
```

**Azure PowerShell:**

```powershell
New-AzResourceGroup -Name rg-containers-prod -Location eastus
New-AzContainerRegistry -ResourceGroupName rg-containers-prod -Name crcontosoprod `
  -Sku Standard -Location eastus
```

The admin user is **disabled** by default (`--admin-enabled` default false; `-EnableAdminUser` is a switch you would have to add).

## Getting images into the registry

| Method | Command | Needs a local Docker engine? |
|---|---|---|
| Build and push locally | `docker build`, `docker tag`, `docker push` after `az acr login` | Yes |
| **Quick task: build in Azure** | `az acr build -r crcontosoprod -t web/frontend:1.0 .` | No: the context is uploaded and ACR Tasks builds and pushes |
| **Import** from another registry | `az acr import -n crcontosoprod --source docker.io/library/nginx:latest -t base/nginx:latest` | No: registry-to-registry copy |

`az acr import` copies from Docker Hub, Microsoft Container Registry, another ACR (in the same or another subscription or tenant, using `-r <resource ID>` or credentials) or any other registry with `-u`/`-p`. The PowerShell equivalent is `Import-AzContainerRegistryImage -RegistryName crcontosoprod -ResourceGroupName rg-containers-prod -SourceRegistryUri docker.io -SourceImage library/nginx:latest -TargetTag base/nginx:latest`.

**ACR Tasks** is the build engine behind `az acr build`. Besides quick tasks, you can create tasks with `az acr task create` that run automatically on a **source commit** (GitHub or Azure Repos), a **base image update** (OS and framework patching) or a **timer** (`--schedule` with a cron expression), and multi-step tasks defined in YAML and run with `az acr run`. Learn currently warns that **ACR Tasks runs are paused for subscriptions funded by Azure free credits**; on such a subscription `az acr build` is rejected and you use `az acr import` instead.

Manage content with `az acr repository list -n crcontosoprod`, `az acr repository show-tags -n crcontosoprod --repository web/frontend`, `az acr repository untag` and `az acr repository delete`.

## Authentication

| Method | How | Use it for |
|---|---|---|
| **Individual Microsoft Entra identity** | `az acr login -n <registry>` or `Connect-AzContainerRegistry -Name <registry>`; token valid about **3 hours** | Interactive push and pull by people |
| **Service principal** | `docker login` with app ID and secret, or tooling settings | Headless pipelines outside Azure |
| **Managed identity** | The Azure service authenticates as its identity | Unattended pulls by ACI, Container Apps, App Service, AKS, VMs |
| **Admin user** | `docker login` with the registry name and one of two passwords | Single-user testing only |
| **Tokens and scope maps** | `docker login` with a token name and password | Repository-scoped access for devices or external systems without Entra identities |

**Roles.** In a registry using the default **RBAC Registry Permissions** mode, grant **AcrPull** (pull), **AcrPush** (pull and push) or **AcrDelete** at registry scope. Learn now also documents an optional **RBAC Registry + ABAC Repository Permissions** mode (`az acr update --role-assignment-mode rbac-abac`) for repository-scoped Entra permissions. In that mode AcrPull, AcrPush and AcrDelete are **not honored**; you use **Container Registry Repository Reader**, **Repository Writer**, **Repository Contributor** and **Repository Catalog Lister** instead. The CLI's default for new registries is still `rbac` (`--role-assignment-mode`), but Learn says ABAC-enabled mode will become the default in the future and recommends migrating, so always check which mode a registry uses before you assign roles. Exam questions in this course state the mode when the answer depends on it.

**Admin user.** One account per registry with **full push and pull rights**, two regenerable passwords, and no per-user audit: everyone using it appears as the same identity. Learn recommends enabling it only when necessary, and notes the portal's quick "deploy image from registry" flows to ACI and Container Apps still rely on it. Prefer managed identities with AcrPull.

```bash
az acr update -n crcontosoprod --admin-enabled true     # only if you must
az acr credential show -n crcontosoprod                 # shows username and passwords
```

**Tokens and scope maps** (all SKUs): a scope map lists actions (`content/read`, `content/write`, `content/delete`, `metadata/read`, `metadata/write`) on repositories; a token is bound to one scope map and has its own passwords. Example: `az acr token create -n tok-sensor -r crcontosoprod --repository sensors/agent content/read` creates a token and scope map that can only pull `sensors/agent`.

> **Real world:** In Azure Cloud Shell there is a Docker CLI but no Docker daemon, so plain `az acr login` fails. Use `az acr login -n <registry> --expose-token` to get an access token, or simply use `az acr build` and `az acr import`, which don't need Docker at all.

## Retention and purge

Untagged manifests (left behind when you push a new image with the same tag) consume storage. Two clean-up options:

- **Retention policy** (Premium, preview): `az acr config retention update -r crcontosoprod --status enabled --days 30 --type UntaggedManifests`. The default period is 7 days (0–365 allowed). It applies only to manifests untagged **after** the policy is enabled, and Learn lists it as supporting Docker manifest media types only.
- **`acr purge`** (preview), which runs as an ACR task in any SKU: `az acr run -r crcontosoprod --cmd "acr purge --filter 'web/frontend:.*' --ago 30d --untagged" /dev/null`, or scheduled with `az acr task create --schedule`. Add `--dry-run` first; deleted data can't be recovered.

## Try it yourself

Azure Cloud Shell (Bash) in any browser. Cost: a Basic registry is billed per day; this lab costs a few US cents if you delete it the same day.

```bash
rg=rg-lab-d3acr; acr=crlab$RANDOM$RANDOM
az group create -n $rg -l eastus
az acr create -g $rg -n $acr --sku Basic
az acr show -n $acr --query "{login:loginServer, sku:sku.name, admin:adminUserEnabled}" -o table
# Copy a public image without Docker
az acr import -n $acr --source mcr.microsoft.com/azuredocs/aci-helloworld:latest -t demo/hello:v1
az acr repository list -n $acr -o table
az acr repository show-tags -n $acr --repository demo/hello -o table
# Optional: build in Azure with ACR Tasks (not available on free-credit subscriptions)
mkdir -p ~/acrlab && cd ~/acrlab
printf 'FROM mcr.microsoft.com/azuredocs/aci-helloworld:latest\n' > Dockerfile
az acr build -r $acr -t demo/hello:v2 . || echo "ACR Tasks not available on this subscription"
az acr login -n $acr --expose-token --query loginServer -o tsv
```

In the portal, open the registry: **Repositories** shows `demo/hello` and its tags, **Access keys** shows the admin user disabled, **Properties** shows the pricing plan. Clean up: `az group delete -n $rg --yes --no-wait`.

## Key takeaways

- Login server is `<registry>.azurecr.io`; image references are `loginserver/repository:tag`; registry names are 5–50 alphanumeric characters.
- Basic, Standard and Premium share the same APIs; Premium adds geo-replication, private endpoints, IP firewall rules, customer-managed keys and the untagged-manifest retention policy.
- `az acr build` (ACR Tasks) and `az acr import` get images into ACR without a local Docker engine; tasks can also trigger on commits, base image updates or timers.
- Pull with managed identities holding **AcrPull**; push with **AcrPush**. In ABAC mode use the Container Registry Repository roles instead.
- The admin user is disabled by default, grants full rights to anyone with the password and is for single-user testing only.
- Tokens with scope maps give repository-scoped access without Entra identities; retention policies and `acr purge` clean up old content.
