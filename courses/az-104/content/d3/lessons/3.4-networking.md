## Inbound and outbound are different features

In the multitenant App Service, your app runs on **worker** VMs behind shared **front ends** that receive HTTP(S) requests. You can't attach the App Service network to your virtual network directly, so App Service offers separate features for each direction. Learn's rule of thumb: features that control traffic **to** your app can't solve problems with calls **from** your app, and the reverse.

| Direction | Feature | What it does | Tiers |
|---|---|---|---|
| **Inbound** | **Access restrictions** | Allow/deny rules evaluated at the front ends by priority: IPv4/IPv6 ranges, service tags, VNet subnets (service endpoints), optional HTTP header filters | All tiers; up to 512 rules per app |
| **Inbound** | **Service endpoints** (as an access restriction source) | Lets you allow traffic from specific subnets of your VNets | All tiers |
| **Inbound** | **Private endpoint** | Gives the app a private IP in your subnet through Private Link; can be the only way in | Basic and up (Isolated v2 enabled at ASE level) |
| **Inbound** | **App-assigned address** | Dedicated inbound IP via an IP-based TLS binding | Standard and up |
| **Outbound** | **Virtual network integration** (regional) | App's outbound calls enter your VNet from a dedicated delegated subnet | Basic and up |
| **Outbound** | **Gateway-required VNet integration** | Older point-to-site VPN method to a VNet gateway, Windows plans only | Legacy; Learn recommends regional integration |
| **Outbound** | **Hybrid Connections** | Outbound TCP to one host:port anywhere via Azure Relay and the Hybrid Connection Manager agent | Basic and up (5 per plan in Basic, 25 in Standard, 220 per app in Premium) |
| Both | **App Service Environment v3** (Isolated v2) | The whole App Service deployment runs inside your VNet | Isolated v2 |

> **Exam tip:** "Reach a VM or private endpoint in a VNet **from** the app" = VNet integration. "Make the app reachable **only** from the VNet or on-premises over a private IP" = private endpoint (optionally with public access disabled). "Allow only Front Door or a list of public IP ranges to reach the app" = access restrictions. "Reach an on-premises server with no VPN or ExpressRoute" = Hybrid Connections.

## Access restrictions

Access restrictions behave like an NSG in front of the app, but they run on the App Service front ends:

- **App access** (`publicNetworkAccess`) first decides whether the public endpoint is enabled at all. If you never set it, access is enabled unless the app has a private endpoint.
- **Site access rules** are evaluated in **priority order (lowest number first)**; the first match wins.
- Rule types: **IPv4/IPv6 CIDR**, **service tag** (for example `AzureFrontDoor.Backend`), **virtual network subnet** (needs a `Microsoft.Web` service endpoint on that subnet), and **multi-source** rules with up to eight ranges or tags. Any rule can add **HTTP header filters** (`X-Forwarded-For`, `X-Forwarded-Host`, `X-Azure-FDID`, `X-FD-HealthProbe`).
- **Unmatched rule action**: if no rules exist, unmatched traffic is allowed; once **any** rule exists, unmatched traffic is **implicitly denied**. You can set the unmatched action explicitly to Allow or Deny.
- The **advanced tools site** (SCM/Kudu, `<app>.scm.azurewebsites.net`) has its **own** rule list and unmatched action, or you can tell it to use the main site's rules.
- Access restrictions **don't apply to traffic arriving through a private endpoint**; control that with NSGs on the private endpoint's subnet.
- IP-based rules can't filter private VNet address ranges in the multitenant service; use service endpoint rules for subnets.

**Portal:** app > **Settings** > **Networking** > **Inbound traffic configuration** > **Public network access** (Enabled from all networks, Enabled from select virtual networks and IP addresses, Disabled) > **Site access and rules** > **Add** (name, action, priority, type, source) and **Unmatched rule action**. The **Advanced tool site** tab holds the SCM rules.

**Azure CLI:**

```bash
az webapp config access-restriction add -g rg-web-prod -n app-contoso-web --rule-name office \
  --action Allow --ip-address 203.0.113.0/24 --priority 100
az webapp config access-restriction add -g rg-web-prod -n app-contoso-web --rule-name frontdoor \
  --action Allow --service-tag AzureFrontDoor.Backend --http-headers x-azure-fdid=<front-door-id> --priority 200
az webapp config access-restriction add -g rg-web-prod -n app-contoso-web --rule-name appgw \
  --action Allow --vnet-name vnet-hub --subnet snet-appgw --priority 300
az webapp config access-restriction set -g rg-web-prod -n app-contoso-web --default-action Deny --scm-default-action Deny
az webapp config access-restriction show -g rg-web-prod -n app-contoso-web
```

**Azure PowerShell:**

```powershell
Add-AzWebAppAccessRestrictionRule -ResourceGroupName rg-web-prod -WebAppName app-contoso-web `
  -Name office -Priority 100 -Action Allow -IpAddress 203.0.113.0/24
Add-AzWebAppAccessRestrictionRule -ResourceGroupName rg-web-prod -WebAppName app-contoso-web `
  -Name build -Priority 100 -Action Allow -IpAddress 198.51.100.0/27 -TargetScmSite
```

## Private endpoints

A private endpoint is a NIC with a private IP in a subnet you choose; it carries **inbound** traffic only. To make the app private:

1. Create the private endpoint for the app (sub-resource `sites`) in a subnet of your VNet.
2. Link the **privatelink.azurewebsites.net** private DNS zone (created by the portal wizard) so that clients in the VNet resolve `<app>.azurewebsites.net` to the private IP. On-premises clients need DNS forwarding, for example through Azure DNS Private Resolver.
3. Set **public network access** to **Disabled** if the public endpoint must not be used.

Slots need their own private endpoints (they aren't cloned to new slots). Private endpoints also prevent data exfiltration because the endpoint reaches only that one app.

## Virtual network integration (outbound)

Regional VNet integration places virtual interfaces on the workers with addresses from a **dedicated subnet** in a VNet **in the same region** as the app:

- The subnet is **delegated to `Microsoft.Web/serverFarms`** and can't contain other resources. Minimum size **/28** (a **/26** for multi-plan subnet join, and the portal requires /27 when it creates the subnet). Each plan instance uses one IP, and scale operations temporarily double usage, so Learn recommends a /26 to cover a plan's maximum scale. The subnet size can't be changed after assignment.
- A plan can have **two** VNet integrations; one app uses one at a time.
- Integration reaches resources in the VNet, **peered VNets (including global peering)**, over **ExpressRoute or site-to-site VPN**, **service endpoint**-secured services and **private endpoints** (resolve them through private DNS zones linked to the VNet).
- **Outbound internet traffic (route all)**: by default only private (RFC 1918) traffic and service endpoint traffic go into the VNet; internet-bound traffic leaves directly. Turning on outbound internet traffic routing (the portal checkbox sets the site property `outboundVnetRouting.applicationTraffic`; `outboundVnetRouting.allTraffic` also routes configuration traffic; the legacy `vnetRouteAllEnabled` property and `WEBSITE_VNET_ROUTE_ALL=1` app setting still work) sends **all** outbound app traffic through the VNet, where **NSGs** and **route tables** on the integration subnet apply (for example to force it through Azure Firewall).
- A **NAT gateway** on the integration subnet gives the app a **dedicated, static outbound IP** and more SNAT ports.
- Configuration traffic such as container image pulls, backup/restore to storage and Key Vault references can also be routed over the integration.
- It doesn't provide inbound access, drive mounts, AD domain join or NetBIOS.

**Portal:** app > **Networking** > **Outbound traffic configuration** > **Virtual network integration** > **Add virtual network integration** > choose VNet and subnet > **Connect**; then set **Outbound internet traffic**.

```bash
az network vnet subnet create -g rg-net-prod --vnet-name vnet-hub -n snet-appsvc-int \
  --address-prefixes 10.10.8.0/26 --delegations Microsoft.Web/serverFarms
az webapp vnet-integration add -g rg-web-prod -n app-contoso-web --vnet <vnet-resource-id> --subnet snet-appsvc-int
az resource update -g rg-web-prod -n app-contoso-web --resource-type Microsoft.Web/sites \
  --set properties.outboundVnetRouting.allTraffic=true
```

Learn recommends `outboundVnetRouting.allTraffic` (application and configuration traffic, auditable with a built-in policy); use `properties.outboundVnetRouting.applicationTraffic=true` to route only the app's own traffic.

PowerShell: set the app's `VirtualNetworkSubnetId` (for example with `Set-AzResource` on the site properties); Learn's how-to uses the portal, CLI and ARM, so the CLI is the practical route.

## Hybrid Connections

Hybrid Connections let the app open outbound **TCP** connections to a single **host and port** (for example `sql01.corp.contoso.com:1433`) on a private network that has outbound HTTPS to Azure. You install the **Hybrid Connection Manager** on a host that can reach the target: Windows Server 2012 or later, or Linux (CLI only) with the current version; it connects outbound on port 443 to **Azure Relay**. No inbound firewall openings or VPN are needed. Use it for a handful of on-premises dependencies; it isn't designed for high connection counts.

## Try it yourself

Azure Cloud Shell (Bash). Cost: a B1 plan for under an hour, a few US cents; the VNet and subnet are free.

```bash
rg=rg-lab-d3net; plan=asp-lab-net; app=app-lab-net-$RANDOM$RANDOM
az group create -n $rg -l eastus
az appservice plan create -g $rg -n $plan --sku B1 --is-linux
az webapp create -g $rg -p $plan -n $app --container-image-name mcr.microsoft.com/azuredocs/aci-helloworld:latest
curl -s -o /dev/null -w "%{http_code}\n" https://$app.azurewebsites.net   # 200: no rules, unmatched = allow
az webapp config access-restriction add -g $rg -n $app --rule-name office --action Allow --ip-address 203.0.113.0/24 --priority 100
az webapp config access-restriction show -g $rg -n $app --query "ipSecurityRestrictions[].{name:name,action:action,priority:priority,ip:ipAddress}" -o table
curl -s -o /dev/null -w "%{http_code}\n" https://$app.azurewebsites.net   # 403: one rule exists, so unmatched = deny
az network vnet create -g $rg -n vnet-lab --address-prefixes 10.50.0.0/16
az network vnet subnet create -g $rg --vnet-name vnet-lab -n snet-int --address-prefixes 10.50.1.0/26 \
  --delegations Microsoft.Web/serverFarms
az webapp vnet-integration add -g $rg -n $app --vnet vnet-lab --subnet snet-int
az webapp vnet-integration list -g $rg -n $app -o table
```

The second request is refused because Cloud Shell's address isn't in 203.0.113.0/24 (a documentation range) and the implicit deny now applies. Your browser gets the same 403 page; add your own public IP as a second rule (or run `az webapp config access-restriction set -g $rg -n $app --default-action Allow`) and refresh. Changes can take a minute to apply. In the portal, open **Networking** to see inbound and outbound settings side by side. Clean up: `az group delete -n $rg --yes --no-wait`.

## Key takeaways

- Inbound: access restrictions (priority order, implicit deny once any rule exists, separate SCM rules), service endpoint rules, private endpoints (Basic and up; bypass access restrictions), app-assigned address.
- Outbound: regional VNet integration (Basic and up, same-region VNet, dedicated subnet delegated to Microsoft.Web/serverFarms, /28 minimum, two per plan), gateway-required integration (legacy), Hybrid Connections (single host:port via Azure Relay).
- Route all sends every outbound call through the VNet so NSGs, UDRs and a NAT gateway (static outbound IP) apply.
- VNet integration never makes an app reachable from the VNet; a private endpoint never lets the app call into the VNet.
