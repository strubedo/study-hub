## Three kinds of "move"

| Move to | Tool | What actually happens |
|---|---|---|
| Another **resource group** (same subscription) | Resource move (portal **Move**, `az resource move`, `Move-AzResource`) | Metadata change only: the resource ID changes, nothing is copied, the VM keeps running |
| Another **subscription** (same Microsoft Entra tenant) | Resource move, with `--destination-subscription-id` / `-DestinationSubscriptionId` | Metadata change; the VM and its dependent resources must move together |
| Another **region** | **Azure Resource Mover** (or Azure Site Recovery) | A new copy is built in the target region by replication and templates, then you commit and delete the source |

Resource move **never changes the region**. If a question needs the VM in West Europe instead of East US, resource move is the wrong answer.

## Moving between resource groups and subscriptions

### What Learn says about the operation

- Both the source and target resource groups are **locked** during the move: you can't create, update or delete resources in them (for up to four hours, usually much less). The VM itself keeps running; there's no downtime.
- The **resource ID changes**, because it contains the subscription and resource group. Update scripts, dashboards, alert rules and templates that use the old ID.
- **Role assignments** on the moved resource don't move; they become orphaned and must be re-created.
- You move **top-level resources**; child resources (such as VM extensions) move with their parent.
- A **ReadOnly lock** on the source or destination resource group or subscription blocks the move.
- Across subscriptions, both subscriptions must be **active** and in the **same Microsoft Entra tenant**, the destination must have the resource providers registered (`Microsoft.Compute`, `Microsoft.Network`) and enough quota.

Permissions: `Microsoft.Resources/subscriptions/resourceGroups/moveResources/action` on the source group and `Microsoft.Resources/subscriptions/resourceGroups/write` on the destination group (Contributor on both works).

### What must move together

For a **cross-subscription** move, a resource and its dependent resources must be in the same resource group and move in one operation. For a VM that means the VM, its managed disks, NICs and public IPs, and the virtual network it uses (with every other resource attached to that VNet). If those are spread over several groups, first consolidate them into one group in the source subscription, then move them together, then redistribute if you want.

### VM-specific blockers (Learn's VM move guidance)

| Situation | Effect |
|---|---|
| VM in an **availability set** | Can't be moved individually; move the set with all its VMs |
| VM with **Azure Disk Encryption** | To another resource group: allowed when the VM is **deallocated**. To another subscription: **disable encryption first** |
| VM from a **Marketplace image with a plan** | Can't move across subscriptions; re-create it in the target from its disk after accepting the plan terms there |
| VM protected by **Azure Backup** | Stop backup (keep data) and delete the restore point collection first, or the move fails; with soft delete, wait or disable it |
| **Scale set** with a Standard Load Balancer or Standard public IP | Can't be moved |
| Spot (low-priority) VMs and scale sets | Can't be moved across resource groups or subscriptions |
| VMs using scheduled patching (maintenance configurations) | Can't be moved |

> **Exam tip:** Read exhibits for availability sets, ADE, Marketplace plans and backup. Each one adds a prerequisite; with none of them present, a VM simply moves with its dependencies.

### Doing the move

**Portal:** resource group > select the resources > **Move** > **Move to another resource group** or **Move to another subscription** > choose the destination > the portal **validates** the move > acknowledge that IDs change > **Move**. You can also open the VM's **Overview** and select **Move** next to the resource group.

**Azure CLI:**

```bash
ids=$(az resource list -g rg-app-old --query "[?contains(name,'vm-app-01')].id" -o tsv)
az resource move --destination-group rg-app-prod --ids $ids
# another subscription
az resource move --destination-group rg-app-prod \
  --destination-subscription-id 00000000-0000-0000-0000-000000000000 --ids $ids
```

**Azure PowerShell:**

```powershell
$res = Get-AzResource -ResourceGroupName rg-app-old | Where-Object Name -like '*vm-app-01*'
Move-AzResource -DestinationResourceGroupName rg-app-prod -ResourceId $res.ResourceId
Move-AzResource -DestinationSubscriptionId 00000000-0000-0000-0000-000000000000 `
  -DestinationResourceGroupName rg-app-prod -ResourceId $res.ResourceId
```

To test without moving, call the validate-move operation: `az resource invoke-action --action validateMoveResources` on the source group, `Invoke-AzResourceAction` in PowerShell, or the REST `validateMoveResources` API (202 accepted, then 204 on success).

The name filter in the example catches the VM, its OS disk, NIC and public IP if they follow the default naming; check the list before moving.

## Moving to another region

### Azure Resource Mover

Resource Mover is the portal-driven tool for moving VMs and related resources (VNets, NICs, public IPs, NSGs, load balancers, Azure SQL) between regions. It replicates VMs with the Site Recovery engine and re-creates stateless resources from generated ARM templates. The flow and the states you'll see:

1. **Select resources**: in **Azure Resource Mover** > **Move across regions** (or from the resource group's **Move** > **Move to another region**), choose source and target regions and add the VM.
2. **Validate dependencies** and add the dependent resources it reports (NIC, VNet, NSG, public IP...).
3. **Move the source resource group**: prepare, initiate move and commit, so a target resource group exists.
4. **Prepare** the VM and other resources: VM replication starts; state becomes *Initiate move pending*.
5. **Initiate move**: a replica VM is created in the target region, the source VM is shut down (a few minutes of downtime). State *Commit move pending*.
6. **Commit** the move (or **Discard** to roll back while testing). State *Delete source pending*.
7. **Delete the source** resources when the target is verified.

Before preparing, the VM must be running with its disks attached and initialized, and have outbound access to the Site Recovery URLs or service tags. Some settings aren't copied (for example, a public IP's DNS label and load balancer NAT rules), and RBAC assignments must be re-created.

PowerShell has the full cycle in the Az.ResourceMover module (`New-AzResourceMoverMoveCollection`, `Add-AzResourceMoverMoveResource`, `Invoke-AzResourceMoverPrepare`, `Invoke-AzResourceMoverInitiateMove`, `Invoke-AzResourceMoverCommit`, `Invoke-AzResourceMoverDiscard`).

### Azure Site Recovery

Site Recovery replicates a VM to another region continuously for disaster recovery. You can also use it to move a VM: enable replication, run a **failover**, **commit**, then disable replication and clean up the source. Site Recovery and failover are covered in Domain 5.

### Re-create from a copy

For simple cases you can snapshot the disks, copy the snapshots to the target region (incremental snapshots support cross-region copy) and build a new VM, or redeploy from a template. Moving a VM into an **availability zone** in the same region is a separate operation (Resource Mover or the VM's availability settings), not a resource move.

## Try it yourself

Azure Cloud Shell (Bash). Cost: under a dollar if deleted within an hour. The lab moves a VM and its dependencies to another resource group and shows the ID change.

```bash
az group create -n rg-lab-d3mv-a -l eastus
az group create -n rg-lab-d3mv-b -l eastus
az vm create -g rg-lab-d3mv-a -n vm-mv-01 --image Ubuntu2204 --size Standard_D2s_v5 \
  --generate-ssh-keys --public-ip-address "" --nsg ""
az vm show -g rg-lab-d3mv-a -n vm-mv-01 --query id -o tsv
ids=$(az resource list -g rg-lab-d3mv-a --query "[].id" -o tsv)
az resource move --destination-group rg-lab-d3mv-b --ids $ids
az vm show -g rg-lab-d3mv-b -n vm-mv-01 --query "{id:id, location:location, state:provisioningState}"
```

Note that the VM was never stopped, that its location is unchanged, and that the resource ID now contains `rg-lab-d3mv-b`. In the portal, try **Move** > **Move to another region** on the group to see Resource Mover's first screen (cancel before preparing). Clean up: `az group delete -n rg-lab-d3mv-a --yes --no-wait; az group delete -n rg-lab-d3mv-b --yes --no-wait`.

## Key takeaways

- Resource move changes resource group or subscription (same tenant), never region; the resource ID changes and role assignments don't follow.
- Source and target groups are locked during the move, but the VM keeps running.
- Cross-subscription: VM, disks, NICs, public IPs and the VNet move together from one resource group.
- Blockers: availability set members individually, ADE across subscriptions (disable first), Marketplace plans across subscriptions, Azure Backup restore points, Spot VMs.
- `az resource move --destination-group [--destination-subscription-id] --ids`; `Move-AzResource -DestinationResourceGroupName [-DestinationSubscriptionId] -ResourceId`.
- Region moves: Azure Resource Mover (select, validate dependencies, prepare, initiate, commit or discard, delete source) or Site Recovery failover.
