## Two separate jobs: a certificate and a binding

Securing a custom domain such as `www.contoso.com` with HTTPS takes two steps in App Service:

1. **Get a private certificate into the app's certificate store** (one of four sources below).
2. **Create a TLS/SSL binding** that ties the certificate to a custom domain already added to the app.

The default host name `<app>.azurewebsites.net` is already covered by Microsoft's wildcard certificate on every tier, Free included. Custom-domain certificates need the app's plan in **Basic, Standard, Premium or Isolated**.

## Certificate sources

| Source | What it is | Key facts |
|---|---|---|
| **App Service managed certificate** | Free certificate that App Service creates and **renews automatically** for a custom domain on the app | Basic tier and up; **no wildcard**; **not exportable**; not in App Service Environment; no private DNS; one per custom domain; domain up to 64 characters. Apex domain needs an A record to the app (and no IP restrictions blocking the validation); subdomain needs a CNAME **directly** to `<app>.azurewebsites.net` (or Traffic Manager) |
| **App Service certificate** | A certificate you **buy** in Azure (Standard or wildcard), stored in Key Vault and then imported into apps | Exportable, renewable, usable by other services such as Application Gateway; annual charge |
| **Import from Key Vault** | A PKCS #12 certificate you manage in Azure Key Vault | Grant the App Service resource provider (**Microsoft.Azure.WebSites**) the **Key Vault Certificate User** role (RBAC vault) or Get on secrets and certificates (access policy). Renewed versions sync to the app within 24 hours |
| **Upload a private certificate** | A PFX from any public CA | Password-protected PFX with the full chain, Server Authentication EKU, signed by a trusted CA; no automatic renewal |

A **public certificate** (.cer) can also be uploaded, but only for the app's code to call remote resources; it doesn't secure a custom domain.

Learn notes that DigiCert issues the managed certificates, so a domain with a DNS CAA record must allow `digicert.com`, and that managed-certificate issuance and renewal behaviour changed on July 28, 2025 for some scenarios (for example apps that aren't publicly reachable). Uploaded and imported private certificates are stored per **webspace** (resource group + region + OS), so other apps in the same webspace can bind them.

> **Exam tip:** "Free", "auto-renew" and a single host name: App Service managed certificate. "Wildcard (`*.contoso.com`)", "export the certificate", or "reuse it on Application Gateway": App Service certificate or your own certificate (Key Vault or PFX upload).

## TLS bindings: SNI versus IP-based

| Binding type | How it works | Tier | Notes |
|---|---|---|---|
| **SNI SSL** | The client sends the host name in the TLS handshake; many certificates share one IP | Basic and up | Unlimited, free; all modern clients support SNI |
| **IP SSL** (IP-based) | A dedicated inbound IP address for the app, one certificate per address | **Standard** and up | Learn's binding article allows one IP SSL binding; the limits table shows one IP SSL connection included in Standard and above, and the plans page says IP-based connections otherwise carry an hourly charge. After you bind it, **remap the A record** to the new dedicated IP |

The IP-based binding is also how you get an **app-assigned address**, an inbound IP used only by your app.

**Portal:** app > **Settings** > **Certificates**: **Managed certificates** > **Add certificate** (pick the custom domain, **Validate**, **Add**), or **Bring your own certificates (.pfx)** > **Add certificate** with source **Upload certificate**, **Import from Key Vault** or **Import App Service Certificate**. Then **Custom domains** > the domain > **Add binding**, choose the certificate and **TLS/SSL type** (SNI SSL or IP based SSL) > **Add**.

**Azure CLI:**

```bash
# Free managed certificate for a domain already added to the app
az webapp config ssl create -g rg-web-prod -n app-contoso-web --hostname www.contoso.com
# Or upload a PFX / import from Key Vault
az webapp config ssl upload -g rg-web-prod -n app-contoso-web \
  --certificate-file ./www-contoso.pfx --certificate-password <password>
az webapp config ssl import -g rg-web-prod -n app-contoso-web \
  --key-vault kv-contoso-prod --key-vault-certificate-name www-contoso
# Bind it
az webapp config ssl bind -g rg-web-prod -n app-contoso-web \
  --certificate-thumbprint <thumbprint> --ssl-type SNI --hostname www.contoso.com
```

**Azure PowerShell:**

```powershell
New-AzWebAppSSLBinding -ResourceGroupName rg-web-prod -WebAppName app-contoso-web -Name www.contoso.com `
  -CertificateFilePath ./www-contoso.pfx -CertificatePassword '<password>' -SslState SniEnabled
# Free managed certificate
New-AzWebAppCertificate -ResourceGroupName rg-web-prod -WebAppName app-contoso-web -Name www-contoso `
  -HostName www.contoso.com -AddBinding -SslState SniEnabled
```

When you renew an uploaded certificate, upload the new one and **update the existing binding** before deleting the old certificate. Deleting an IP-based binding first can change the app's inbound IP address.

## Protocol settings: HTTPS Only, minimum TLS version, client certificates

| Setting | Default | Change it with |
|---|---|---|
| **HTTPS Only** (redirect HTTP to HTTPS) | Sources disagree: Learn's binding FAQ says App Service forces the HTTP-to-HTTPS redirect by default, while the CLI reference gives `az webapp create --https-only` a default of `False`. Check the setting and set it explicitly | `az webapp update --https-only true`; `Set-AzWebApp -HttpsOnly $true`; portal **Configuration** > **General settings** |
| **Minimum inbound TLS version** | **1.2** for new apps; **1.3** is supported; 1.0 and 1.1 are legacy | `az webapp config set --min-tls-version 1.2`; portal **Minimum Inbound TLS Version** |
| Minimum TLS cipher suite | Platform default | `az webapp config set --min-tls-cipher-suite <suite>` (TLS 1.3 suites are fixed and can't be customized) |
| **SCM site** minimum TLS | 1.2 | Set separately for the Kudu (SCM) endpoint |
| **Client certificates** (mutual TLS) | Ignored | Modes **Required**, **Optional** (client prompted), **Optional Interactive User** (not prompted), plus exclusion paths; `az webapp update --set clientCertEnabled=true` |

Learn announces that **TLS 1.0 and 1.1 are retired for inbound connections on May 31, 2027**: any app or slot explicitly set to 1.0 or 1.1 must move to 1.2 or later before then. Learn also notes that client-certificate settings that need TLS renegotiation (Optional Interactive User, exclusion paths) don't work with TLS 1.3 or HTTP/2. App Service passes a validated client certificate to the app in the `X-ARR-ClientCert` header; checking it is the app's job.

All protocol settings (HTTPS Only, TLS version, client certificates) are **slot-specific**: they don't move during a slot swap.

## Try it yourself

Azure Cloud Shell (Bash). Cost: a B1 plan for under an hour, a few US cents. Without a domain you own, you can't create a managed certificate, but you can practise every protocol setting and see the certificate commands' requirements.

```bash
rg=rg-lab-d3tls; plan=asp-lab-tls; app=app-lab-tls-$RANDOM$RANDOM
az group create -n $rg -l eastus
az appservice plan create -g $rg -n $plan --sku B1 --is-linux
az webapp create -g $rg -p $plan -n $app --container-image-name mcr.microsoft.com/azuredocs/aci-helloworld:latest
az webapp show -g $rg -n $app --query "{httpsOnly:httpsOnly, clientCert:clientCertEnabled}" -o table
az webapp update -g $rg -n $app --https-only true
az webapp config set -g $rg -n $app --min-tls-version 1.2
az webapp config show -g $rg -n $app --query "{minTls:minTlsVersion, scmMinTls:scmMinTlsVersion}" -o table
curl -sI http://$app.azurewebsites.net | head -n 3        # expect a 301 redirect to https
curl -s --tlsv1.2 --tls-max 1.2 -o /dev/null -w "%{http_code}\n" https://$app.azurewebsites.net
az webapp config ssl list -g $rg --query "[].{name:name, subject:subjectName}" -o table
# If you own a domain mapped to this app (next lesson), add: az webapp config ssl create --hostname <your-host>
```

In the portal, open **Certificates** to see the three certificate tabs and **Configuration** > **General settings** for HTTPS Only, minimum TLS version and client certificate mode. Clean up: `az group delete -n $rg --yes --no-wait`.

## Key takeaways

- Custom-domain HTTPS = a private certificate in the app plus a TLS binding; needs Basic tier or higher.
- Managed certificate: free, auto-renewing, Basic and up, no wildcard, not exportable, one per domain; CNAME must point directly at the app.
- App Service certificate (purchased, exportable, wildcard possible), Key Vault import (grant the App Service resource provider access; syncs in 24 hours) or PFX upload (password-protected, full chain).
- SNI SSL: Basic and up, unlimited. IP SSL: Standard and up, dedicated IP, remap the A record.
- HTTPS Only, minimum TLS 1.2 (default; 1.3 supported; 1.0/1.1 retire May 31, 2027) and client certificate modes are slot-specific protocol settings.
