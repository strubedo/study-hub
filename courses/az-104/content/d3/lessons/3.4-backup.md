## Built-in backup and restore

App Service has its own backup feature, separate from Azure Backup vaults. Learn states that backup and restore is supported in the **Basic, Standard, Premium and Isolated** tiers (not Free or Shared), and that in **Basic only the production slot** can be backed up and restored. There are two kinds of backup, and the exam likes to contrast them.

## Automatic versus custom backups

| | **Automatic backups** | **Custom backups** |
|---|---|---|
| Configuration | None: created for every app in a supported tier | You configure a **storage account and blob container** (same subscription), then run on demand or on a schedule |
| Frequency | **Hourly**, not configurable | On demand, or scheduled; Learn's backup page gives a minimum of every 2 hours and up to 12 backups a day (manual plus scheduled) |
| Retention | **30 days**, not configurable (hourly for days 1–3, every third hour for days 4–14, every sixth hour for days 15–30) | 0–30 days or indefinite; you can keep at least one backup; on-demand backups are kept indefinitely |
| Maximum size | **30 GB** | **10 GB** total, of which up to **4 GB** can be the linked database |
| Linked database | Not backed up | Supported databases can be included (see the deprecation below) |
| Where stored | Platform storage in the same datacenter; not downloadable | Your storage account as a `.zip` plus an `.xml` manifest; downloadable |
| Partial backups (`_backup.filter`) | No | Yes |
| Backup to a firewall-protected storage account over VNet integration | No | Yes |

You can't stop automatic backups, and Learn warns not to rely on them as a disaster recovery plan because they live in the same datacenter as the app.

> **Watch out:** Learn's App Service limits table still says Premium and Isolated allow custom scheduled backups every hour and 50 per day, while the backup article says every 2 hours and 12 per day for custom backups. Learn the backup article's figures for custom backups, and don't build an answer on the difference.

### What a backup contains

Both types back up app content (the `/home` directory on Linux, `%HOME%` on Windows, persistent storage for custom containers) and the app configuration. Restoring configuration brings back settings such as app settings, log settings, Application Insights configuration and health check. Learn lists what **isn't** restored with the configuration: networking features (private endpoints, hybrid connections, VNet integration), authentication, managed identities, TLS bindings, scale-out settings, alerts, backup settings and deployment slots. Custom domains are a special case: a custom backup's manifest lists them, and the restore adds them to the target if they don't conflict. Content from **run-from-package** ZIPs and **custom-mounted Azure Storage** (Azure Files) isn't backed up.

### Linked databases and their deprecation

A database is **linked** when the app has a valid **connection string** for it in **Connection strings**. Custom backups have been able to include Azure SQL Database, Azure Database for MySQL and PostgreSQL (Learn excludes the Flexible Server options) and MySQL in-app. Learn now announces that **starting March 31, 2028, custom backups will no longer back up linked databases**, and the option to include them in new configurations was removed for MySQL and PostgreSQL in November 2025 and for Azure SQL and SQL Server in April 2026. Existing configurations keep backing up their databases until March 2028. Use each database service's native backups instead.

A custom backup **fails** if the total exceeds 10 GB or the database exceeds 4 GB. Database backup also isn't possible when the backup runs over a virtual network, or for TLS-enforced Azure Database for MySQL or PostgreSQL.

## Configure custom backups

**Portal:** app > **Backups** > **Configure custom backups**: select or create a **Storage account** and **Container** > (optionally **Next: Advanced** > **Include database**) > **Configure**. Then **Backup Now** for an on-demand backup, or **Set schedule** to configure frequency, start time and retention. The storage account must allow **SAS** authorization: Learn notes that managed identity authentication to the storage account isn't supported for backup and restore.

**Azure CLI** uses a container URL with a SAS token:

```bash
end=$(date -u -d "1 year" '+%Y-%m-%dT%H:%MZ')
sas=$(az storage container generate-sas --account-name stcontosobackup01 -n webbackups \
  --permissions racwdl --expiry $end --account-key <storage-account-key> -o tsv)
url="https://stcontosobackup01.blob.core.windows.net/webbackups?$sas"
az webapp config backup create -g rg-web-prod --webapp-name app-contoso-web --container-url "$url" --backup-name manual-01
az webapp config backup update -g rg-web-prod --webapp-name app-contoso-web --container-url "$url" \
  --frequency 1d --retention 14 --retain-one true
az webapp config backup list -g rg-web-prod --webapp-name app-contoso-web -o table
```

**Azure PowerShell:**

```powershell
$url = "https://stcontosobackup01.blob.core.windows.net/webbackups?sv=<version>&sig=<signature>"
New-AzWebAppBackup -ResourceGroupName rg-web-prod -Name app-contoso-web -StorageAccountUrl $url -BackupName manual-01
Edit-AzWebAppBackupConfiguration -ResourceGroupName rg-web-prod -Name app-contoso-web -StorageAccountUrl $url `
  -FrequencyInterval 1 -FrequencyUnit Day -RetentionPeriodInDays 14 -KeepAtLeastOneBackup
```

## Partial backups with `_backup.filter`

To keep a custom backup under 10 GB, or to skip logs and static content that never changes, create a file named **`_backup.filter`** in `%HOME%\site\wwwroot` (Windows path; `/home/site/wwwroot` on Linux) listing one folder or file per line, written from the root without `%HOME%`:

```text
\site\wwwroot\Images\2014
\site\wwwroot\Images\2013
\site\wwwroot\Images\brand.png
```

Listed items are excluded from future custom backups. On restore, content covered by the filter is **left in place** rather than deleted. Automatic backups ignore the filter.

## Restore

App Service **stops the target app or slot** during a restore. To limit production downtime, restore into a **deployment slot** and swap it in.

**Portal:** app > **Backups** > pick an automatic or custom backup > **Restore**. **Choose a destination**: the same app (overwrite), an **existing or new app**, or an **existing or new deployment slot**. Under **Advanced options** choose whether to restore the site configuration and (for custom backups) the database. Restoring to an existing slot erases its file system first.

**Azure CLI:**

```bash
# Automatic backups (CLI calls them snapshots)
az webapp config snapshot list -g rg-web-prod -n app-contoso-web -o table
az webapp config snapshot restore -g rg-web-prod -n app-contoso-web --time "<snapshot-time>"
az webapp config snapshot restore -g rg-web-dr -n app-contoso-restore --source-resource-group rg-web-prod \
  --source-name app-contoso-web --time "<snapshot-time>" --restore-content-only
# Custom backup
az webapp config backup restore -g rg-web-prod --webapp-name app-contoso-web --container-url "$url" \
  --backup-name manual-01 --overwrite
```

**Azure PowerShell:** `Restore-AzWebAppBackup -ResourceGroupName rg-web-prod -Name app-contoso-web -StorageAccountUrl $url -BlobName <backup-blob-name>.zip -Overwrite` (the blob name is the `.zip` you see in the container).

Learn also covers restoring to **another region** in the same subscription (select the target app in the portal, provided it can reach the backup storage) and to **another subscription** (download the `.zip` and `.xml`, upload them to a storage account there, and restore from **Storage**). The target must be the same OS platform as the source.

## Try it yourself

Azure Cloud Shell (Bash). Cost: a B1 plan for under an hour and a few megabytes of blob storage, a few US cents.

```bash
rg=rg-lab-d3bak; plan=asp-lab-bak; app=app-lab-bak-$RANDOM$RANDOM; st=stlabbak$RANDOM$RANDOM
az group create -n $rg -l eastus
az appservice plan create -g $rg -n $plan --sku B1 --is-linux
az webapp create -g $rg -p $plan -n $app --container-image-name mcr.microsoft.com/azuredocs/aci-helloworld:latest
az storage account create -g $rg -n $st -l eastus --sku Standard_LRS
key=$(az storage account keys list -g $rg -n $st --query "[0].value" -o tsv)
az storage container create --account-name $st -n webbackups --account-key $key
end=$(date -u -d "2 days" '+%Y-%m-%dT%H:%MZ')
sas=$(az storage container generate-sas --account-name $st -n webbackups --permissions racwdl --expiry $end --account-key $key -o tsv)
url="https://$st.blob.core.windows.net/webbackups?$sas"
az webapp config backup create -g $rg --webapp-name $app --container-url "$url" --backup-name lab-01
az webapp config backup list -g $rg --webapp-name $app --query "[].{name:backupName, status:status, size:sizeInBytes}" -o table
az storage blob list --account-name $st -c webbackups --account-key $key --query "[].name" -o tsv
az webapp config snapshot list -g $rg -n $app -o table     # automatic backups appear after about an hour
```

Run the backup list again until the status is **Succeeded**, then look at the `.zip` and `.xml` blobs. In the portal, open the app's **Backups** blade to see custom and automatic backups side by side and the **Restore** options. Clean up: `az group delete -n $rg --yes --no-wait`.

## Key takeaways

- Backup and restore: Basic, Standard, Premium, Isolated; Basic backs up only the production slot.
- Automatic: hourly, 30-day retention, 30 GB, no configuration, no database, not downloadable.
- Custom: your storage account and container (SAS), on demand or scheduled, 10 GB including up to 4 GB of linked database, partial backups, downloadable.
- Linked database backups are deprecated (no new configurations; ends March 31, 2028); use native database backups.
- `_backup.filter` in `site\wwwroot` excludes files and folders from custom backups.
- Restore overwrites the same app or targets another app or slot; restoring to a slot then swapping limits downtime.
