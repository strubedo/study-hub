## How Resource Manager decides

When a principal calls Resource Manager, the decision runs in this order:

1. The caller gets a token for Resource Manager; it includes their **group memberships, including transitive (nested) ones**.
2. Resource Manager collects every **role assignment** and **deny assignment** that applies to the target resource, at its own scope and every parent scope.
3. If a **deny assignment** applies to the caller and the action, the request is **blocked**. Nothing else matters.
4. Otherwise Resource Manager keeps the role assignments for this caller (direct or through groups) and checks whether any of their roles contains the action, after subtracting each role's `NotActions` (or `NotDataActions` for data operations).
5. If no role contains the action, access is denied (Azure RBAC is deny-by-default).
6. If the matching assignment has a **condition**, the condition must also be true.

So **effective access = the union of every role the principal holds at this scope or above, each role computed as Actions minus NotActions, minus anything a deny assignment blocks**. Two consequences:

- **More roles only add.** Reader at the subscription plus Contributor on `rg-web-prod` gives Contributor in `rg-web-prod` and Reader everywhere else in the subscription.
- **NotActions do not cross roles.** Contributor's `NotActions` exclude role assignment, but a second role that grants `Microsoft.Authorization/roleAssignments/write` restores it.

## Working through an access question

Treat every "what can User1 do" question as a table. Example:

```text
Group membership: User1 is a member of sg-web-ops. sg-web-ops is a member of sg-all-it.

Role assignments
Principal     Role                          Scope
------------  ----------------------------  -------------------------------------------
sg-all-it     Reader                        Subscription Contoso-Prod
sg-web-ops    Virtual Machine Contributor   Resource group rg-web-prod
User1         Network Contributor           Virtual network vnet-hub (in rg-net-prod)
```

| Target | Roles that reach it | Effective result |
|---|---|---|
| A VM in rg-web-prod | Reader (via nesting, inherited) + VM Contributor (via group) | Manage the VM; read anything |
| A storage account in rg-web-prod | Reader + VM Contributor | View it but not change it. (VM Contributor does include `listKeys` on storage accounts, so User1 could read the keys: one more reason to prefer Microsoft Entra authorization for data) |
| vnet-hub | Reader + Network Contributor | Manage the VNet |
| A subnet of vnet-hub | Same, inherited from the VNet | Manage the subnet |
| Another VNet in rg-net-prod | Reader | Read only |
| Assign roles anywhere | None of the roles has `roleAssignments/write` | Cannot |

Steps: list every group the user belongs to (directly and through nesting), list every assignment to the user or those groups, keep those whose scope is the target or a parent of it, union the roles, then check deny assignments.

## Check access in the portal

On any scope, **Access control (IAM)** has:

- **Check access > View my access**: your own assignments at this scope **and inherited from above**.
- **Check access > Check access**: pick a user, group, service principal or managed identity and see the **role assignments** and **deny assignments** that apply at this scope and above. Assignments at **child scopes are not listed**: checking a subscription will not show a Contributor assignment on one of its resource groups.
- **Role assignments** tab: all assignments at this scope, with a **Scope** column showing *This resource* or *(Inherited)* from a parent. Filter by role, type or scope.
- **Deny assignments** tab: deny assignments that apply here.
- **Eligible assignments** (with PIM): assignments a user can activate.

Command line equivalents:

```bash
az role assignment list --assignee user1@contoso.com --all --include-inherited --include-groups -o table
az role assignment list --scope /subscriptions/00000000-0000-0000-0000-000000000000/resourceGroups/rg-web-prod --include-inherited -o table
```

```powershell
Get-AzRoleAssignment -SignInName 'user1@contoso.com' -ExpandPrincipalGroups
Get-AzRoleAssignment -ResourceGroupName 'rg-web-prod'
Get-AzDenyAssignment -ResourceGroupName 'rg-web-prod'
```

`--include-groups` and `-ExpandPrincipalGroups` add the assignments the user holds through group membership; without them you see only direct assignments and may wrongly conclude a user has no access.

## Deny assignments

A **deny assignment** attaches a set of **denied actions** to principals at a scope, and it **wins over any role assignment**. Unlike role assignments:

- You **cannot create them directly** in the generally available product (customer-managed deny assignments are in private preview). Azure creates and manages them, for example when a **deployment stack** is created with deny settings, or to protect the resources of a managed application.
- They can **exclude principals** (for example the deployment stack's own identity) and can be set not to apply to child scopes.
- They appear in **Check access** and on the **Deny assignments** tab.

> **Exam tip:** If a question asks you to "create a deny assignment" to stop one user deleting a VM, that is not something you can do directly. The tools that block actions regardless of role are a **resource lock** (blocks everyone, including Owners), **Azure Policy** with `deny` or `denyAction`, or removing the role.

## Classic subscription administrators: retired

Before Azure RBAC there were three **classic administrator** roles: **Account Administrator**, **Service Administrator** and **Co-Administrator**. Their status on Microsoft Learn today:

- Since **August 31, 2024**, the Co-Administrator and Service Administrator roles (with classic resources and Azure Service Manager) are **retired and not supported**.
- Starting **December 2025**, Azure automatically gave the **Owner role at subscription scope** to public-cloud users still holding Co-Administrator or Service Administrator; the assignment's description says it was converted because of the classic administrator retirement.
- As of **May 2026** classic administrator roles are **fully retired** and the **Classic administrators** tab is gone from the portal. Manage all access with Azure RBAC.
- **Account Administrator** is the billing account's primary user and is **not** deprecated; it is a billing role, not a resource access role.

If an exam item asks for the Azure RBAC equivalent of a Co-Administrator, the answer is **Owner at subscription scope**, though Microsoft recommends a narrower job-function role where possible.

## Elevate access for a Global Administrator

Microsoft Entra roles and Azure roles are separate, so a Global Administrator may see no subscriptions at all, for example after the only subscription Owner left the company. The fix:

1. Sign in to the Azure portal as a Global Administrator (activate the role first if you use PIM).
2. **Microsoft Entra ID > Manage > Properties**.
3. Set **Access management for Azure resources** to **Yes** and **Save**.
4. Sign out and back in. You now hold **User Access Administrator at root scope (`/`)**: you can see every subscription and management group in the tenant and assign roles in any of them.
5. Assign what is needed (for example Owner on the orphaned subscription to the right person).
6. Set the toggle back to **No**.

Facts that appear in questions:

- The toggle is **per user**: it elevates only the signed-in Global Administrator; you cannot elevate all Global Administrators at once. The same user normally turns it off, but another Global Administrator who is also elevated can remove it (the portal has a **Remove elevated access for users** option for this).
- Only **Global Administrators** see the toggle.
- Elevation grants **User Access Administrator** (manage access), not Owner. To manage resources the administrator assigns themselves or someone else a role, then removes the elevation.
- The root-scope assignment cannot be removed on an IAM page; use the toggle, Azure PowerShell, the Azure CLI or the REST API. List it with `az role assignment list --role "User Access Administrator" --scope "/"`.

## Common "why can't they" diagnoses

| Symptom | Likely cause |
|---|---|
| User has Owner but gets 403 reading blobs in the portal with Microsoft Entra auth | Owner is control plane only; needs a Storage Blob Data role |
| Contributor cannot delete a resource | A resource lock (CanNotDelete or ReadOnly) at that scope or above, or a `denyAction` policy |
| Contributor cannot give a colleague access | Contributor lacks `Microsoft.Authorization/*/write`; needs Owner, User Access Administrator or Role Based Access Control Administrator |
| Global Administrator sees no subscriptions | Entra roles do not grant Azure access; elevate access |
| User added to a group still lacks access | Token not refreshed: sign out and in; or the group assignment is at a sibling scope |
| New access works for one user but not another | Check direct versus group assignments with `--include-groups` / `-ExpandPrincipalGroups` |

## Try it yourself

Cost: nothing.

1. Cloud Shell: create `rg-access-a` and `rg-access-b`; create group `sg-access-lab` and add a test user; assign the group **Reader** at the subscription and the user **Contributor** on `rg-access-a`.
2. Portal: open `rg-access-a > Access control (IAM) > Check access > Check access`, choose the test user, and read both assignments (one inherited). Repeat on the subscription: the Contributor on `rg-access-a` is not shown there.
3. Run `az role assignment list --assignee <test-upn> --all --include-groups -o table` with and without `--include-groups` and compare.
4. If you are a Global Administrator in your own tenant, view **Microsoft Entra ID > Properties > Access management for Azure resources**. Do not turn it on unless you need to; if you try it, turn it off again in the same session.
5. Clean up: remove the subscription-level Reader assignment (`az role assignment delete --assignee-object-id <group-id> --role Reader --scope /subscriptions/<subscription-id>`), delete both resource groups (`az group delete -n rg-access-a --yes`, same for `rg-access-b`), the group and the user. Nothing in this lab is billed.

## Key takeaways

- Effective access = union of roles assigned to the principal and its groups (including nested) at the scope and above, each as Actions minus NotActions, minus deny assignments.
- Deny assignments override role assignments; Azure creates them (deployment stacks, managed apps); you cannot create them directly.
- Check access shows assignments at this scope and inherited ones, never those at child scopes; use `--include-groups` or `-ExpandPrincipalGroups` on the command line.
- Classic administrators: Co-Administrator and Service Administrator retired August 31, 2024; converted to Owner from December 2025; fully retired May 2026. Account Administrator remains a billing role.
- Elevate access (Entra ID > Properties > Access management for Azure resources = Yes) gives the signed-in Global Administrator User Access Administrator at root `/`; turn it off afterwards.
