## Resource groups

A **resource group** is a logical container for resources that share a lifecycle: you deploy, secure, tag, lock, monitor and delete them together. Rules:

- Every resource is in **exactly one** resource group. Resource groups cannot be nested.
- A resource group has a **location**, but that is only where its **metadata** (the list of resources, deployment history) is stored. Resources in it can be in **any region**. Choose the group's location for compliance when metadata must stay in a geography. Resource Manager can reroute management requests to another zone or a backup region during a regional outage, but data plane access to resources in an unavailable region is still affected.
- A resource group **cannot be renamed**. To "rename", create a new one and move the resources.
- Group by lifecycle and ownership (for example `rg-web-prod`, `rg-web-dev`, `rg-net-hub`), not by resource type.

### Creating and listing

Portal: **Resource groups > Create**, pick **Subscription**, **Resource group** name and **Region**, add tags, **Review + create**.

```bash
az group create --name rg-web-prod --location eastus --tags Environment=Production
az group list --query "[?location=='eastus'].name" -o tsv
az group show --name rg-web-prod
```

```powershell
New-AzResourceGroup -Name 'rg-web-prod' -Location 'eastus' -Tag @{ Environment = 'Production' }
Get-AzResourceGroup | Where-Object Location -eq 'eastus'
```

### Deleting

Deleting a resource group deletes **every resource in it**. Resource Manager works out the order (child and dependent resources first) and issues the deletes.

```bash
az group delete --name rg-web-prod --yes --no-wait
```

```powershell
Remove-AzResourceGroup -Name 'rg-web-prod' -Force
```

The delete fails if any **lock** applies (a delete lock on one resource blocks the whole group delete) and can fail when backup data protects items inside (for example a Recovery Services vault with protected items). Remove locks and backup data first.

## Moving resources

You can move resources to **another resource group** in the same subscription or to **another subscription** in the **same Microsoft Entra tenant**. Moving never changes the resource's **region**; region moves use Azure Resource Mover or redeployment.

What happens:

- The **resource ID changes** (it contains the subscription and group). Update scripts, dashboards and templates that reference it.
- Both **source and target groups are locked** for writes during the move (no create, update or delete in either), although the resources keep running.
- **Role assignments on the moved resource do not move**; they become orphaned and must be re-created. Assignments inherited from the new parent scopes apply automatically.
- Only **top-level resources** are moved; child resources (VM extensions, subnets) go with their parent.

Before moving, check:

1. The resource type supports the move. Microsoft's **move support table** lists each type with *Resource group*, *Subscription* and *Region move* columns. For example, as listed on Microsoft Learn when this lesson was written: VMs, managed disks, virtual networks and storage accounts can move between groups and subscriptions; **Azure Bastion** can move between groups but not subscriptions; **Application Gateway**, **Azure Firewall** and **virtual network gateways** are shown as not movable. Check the table for the current answer; it changes.
2. Both subscriptions are **active** and in the **same tenant** (compare `az account show --subscription <name> --query tenantId`).
3. The destination subscription has the resource **provider registered** and enough **quota**.
4. For a cross-subscription move, the resource and its **dependents** (for example a VM with its disks, NIC and public IP) are in **one resource group** and move **together**. If they are spread out, consolidate them into one group first, move, then redistribute.
5. No **ReadOnly** lock on the source or destination group or subscription.
6. Permissions: `Microsoft.Resources/subscriptions/resourceGroups/moveResources/action` on the source group and `Microsoft.Resources/subscriptions/resourceGroups/write` on the destination (Contributor on both works).

Portal: select resources in the source group > **Move** > **Move to another resource group** or **Move to another subscription** (a third option, **Move to another region**, opens Resource Mover). The portal **validates** the move before running it. Command line:

```bash
vm=$(az resource show -g rg-app-old -n vm-app-01 --resource-type Microsoft.Compute/virtualMachines --query id -o tsv)
az resource move --destination-group rg-app-new --ids $vm <disk-id> <nic-id>
# to another subscription in the same tenant:
az resource move --destination-group rg-app-new --destination-subscription-id 00000000-0000-0000-0000-000000000000 --ids $vm <disk-id> <nic-id>
```

```powershell
$ids = (Get-AzResource -ResourceGroupName 'rg-app-old').ResourceId
Move-AzResource -DestinationResourceGroupName 'rg-app-new' -ResourceId $ids
Move-AzResource -DestinationSubscriptionId '00000000-0000-0000-0000-000000000000' `
  -DestinationResourceGroupName 'rg-app-new' -ResourceId $ids
```

A validation-only check exists too: `az resource invoke-action --action validateMoveResources ...` or `Invoke-AzResourceAction -Action validateMoveResources ...`.

## Subscriptions

A **subscription** is a billing and management boundary: an agreement with Microsoft, a container for resource groups, a scope for RBAC and Policy, and a unit for **quotas and limits**. Each subscription trusts exactly **one** Microsoft Entra tenant; a tenant can hold many subscriptions.

Common offer types: **Free account** (credit plus free services for a limited time), **Pay-As-You-Go** (Microsoft Online Services Program), **Enterprise Agreement (EA)**, **Microsoft Customer Agreement (MCA)**, **Cloud Solution Provider (CSP)** through a partner, and **Visual Studio** subscriptions with monthly credit for developers. Reasons to use several subscriptions: separate billing, separate administrative boundaries (prod and dev), and staying under per-subscription limits.

### Two different "transfers"

| You want to | Operation | Effect on access |
|---|---|---|
| Change **who pays** (billing owner) | **Transfer billing ownership** (Subscriptions > subscription > **Transfer billing ownership**); only the billing account administrator can send it; the request is valid for **15 days** | If the subscription stays in its tenant, RBAC is unchanged. If you also tick **Move subscription tenant**, all role assignments are permanently removed |
| Change **which tenant** the subscription trusts | **Change directory** (Subscriptions > subscription > **Change directory**) | **All role assignments and custom roles are permanently deleted**; managed identities must be re-created or re-enabled; Key Vaults need their tenant ID updated |

Changing directory requires that you have the **Owner role on the subscription, assigned directly** (not through a group, condition or PIM) and an account in the target tenant. It is not supported for CSP subscriptions. Plan it like a migration: export role assignments, custom roles, Key Vault access policies and managed identity uses first, and expect downtime for services that depend on identities.

> **Exam tip:** "Move all resources from Contoso-Dev to Contoso-Prod" (same tenant) is a **resource move**, not a subscription transfer. "Fabrikam acquired Contoso and wants the subscription to trust the fabrikam.com tenant" is **Change directory**, and you must re-create role assignments afterwards.

### Moving subscriptions between management groups

Moving a subscription under a different **management group** changes which inherited policies and roles apply, but changes nothing about billing or tenant. It needs **Owner** on the subscription and write permission on the target and current parent management groups (see the management groups lesson).

### Resource providers

Each Azure service is a **resource provider** (`Microsoft.Compute`, `Microsoft.Network`, `Microsoft.Storage`...). A subscription must be **registered** for a provider before it can create that provider's resources. The portal and ARM deployments usually register providers automatically, but a first-time resource type through the CLI, or a **cross-subscription move**, can fail with "the subscription is not registered to use namespace...".

- Registering needs `*/register/action`, included in **Contributor** and **Owner**.
- Register only what you are ready to use: Microsoft treats this as least privilege, because nobody can create resources from an unregistered provider.
- You cannot unregister a provider while resources of its types exist.

```bash
az provider list --query "[].{Provider:namespace, Status:registrationState}" -o table
az provider register --namespace Microsoft.ContainerInstance
az provider show --namespace Microsoft.ContainerInstance --query registrationState
```

```powershell
Get-AzResourceProvider -ListAvailable | Select-Object ProviderNamespace, RegistrationState
Register-AzResourceProvider -ProviderNamespace Microsoft.ContainerInstance
```

Portal: **Subscriptions > subscription > Settings > Resource providers > Register**.

## Try it yourself

Cost: nothing; resource groups, VNets and NSGs are free.

1. Create `rg-move-a` in `eastus` and `rg-move-b` in `westeurope`. In `rg-move-a` create `vnet-move` with `az network vnet create -g rg-move-a -n vnet-move -l eastus --address-prefix 10.60.0.0/16` and an NSG `nsg-move` in `eastus`.
2. Note the VNet's resource ID. Move both resources: `az resource move --destination-group rg-move-b --ids <vnet-id> <nsg-id>`. Check the new resource IDs and that the region is still `eastus` even though `rg-move-b` is in `westeurope`.
3. Add a ReadOnly lock to `rg-move-b` and try moving the NSG back: it fails. Remove the lock.
4. Run `az provider list --query "[?registrationState=='Registered'].namespace" -o tsv` and compare with the full list.
5. In the portal open your subscription and find **Change directory** and **Transfer billing ownership** (do not run them).
6. Clean up: `az group delete -n rg-move-a --yes` and `az group delete -n rg-move-b --yes`.

## Key takeaways

- A resource group's location stores only metadata; its resources can be in any region. Groups cannot be renamed or nested; every resource is in exactly one group.
- Deleting a group deletes everything in it; locks and backup data block the delete.
- Moves change resource IDs, not regions; require the same tenant, a supported type, registered providers, no ReadOnly locks, and moving dependents together across subscriptions.
- Role assignments on a moved resource do not move.
- Transfer billing ownership changes who pays; Change directory changes the trusted tenant and permanently deletes role assignments and custom roles.
- Register resource providers with `az provider register` or `Register-AzResourceProvider` (Contributor or Owner).
