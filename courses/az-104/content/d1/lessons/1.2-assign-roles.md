## The scope hierarchy

Azure resources sit in a four-level hierarchy, and a role assignment at any level **inherits down** to everything below it:

```text
Tenant Root Group               /providers/Microsoft.Management/managementGroups/<tenant-id>
└── Management group            /providers/Microsoft.Management/managementGroups/mg-contoso-prod
    └── Subscription            /subscriptions/00000000-0000-0000-0000-000000000000
        └── Resource group      /subscriptions/00000000-0000-0000-0000-000000000000/resourceGroups/rg-web-prod
            └── Resource        /subscriptions/00000000-0000-0000-0000-000000000000/resourceGroups/rg-web-prod/providers/Microsoft.Compute/virtualMachines/vm-web-01
```

- Above the root management group sits the **root scope** `/`, which only the elevated-access assignment of a Global Administrator normally uses (see the "interpret access" lesson).
- Assign at the **narrowest scope that covers every target**, and no broader. Reader for auditors on a management group is sensible; Contributor for one developer on a whole subscription usually is not.
- Inheritance cannot be blocked by a child scope. A resource group owner cannot remove access that comes from the subscription; it shows as **(Inherited)** on the child's IAM page and can only be removed at the scope where it was created.
- Some resources accept sub-resource scopes, for example a single blob container: `.../storageAccounts/stcontosodata01/blobServices/default/containers/invoices`.
- The scope string is the resource ID. Get it with `az group show -n rg-web-prod --query id -o tsv`, `az resource show ... --query id` or `(Get-AzResourceGroup -Name rg-web-prod).ResourceId`.

Limits that decide some designs (fixed, cannot be raised):

| Limit | Value |
|---|---|
| Role assignments per subscription (all scopes in it, excluding management group assignments) | 5,000 |
| Role assignments per management group | 500 |

Hitting the limit is a sign you are assigning to users instead of groups.

> **Exam tip:** Assign roles to **groups**, not individual users, wherever a role is shared. Adding a person to `sg-web-operators` is one directory change; a role assignment per person multiplies administration and eats the 5,000 limit.

## Who can assign roles

Creating a role assignment needs `Microsoft.Authorization/roleAssignments/write` at the target scope. That comes from **Owner**, **User Access Administrator** or **Role Based Access Control Administrator** at that scope or above. **Contributor cannot assign roles.** Group owners who can add people to a group indirectly grant whatever roles the group holds, so protect privileged groups (role-assignable groups and PIM for Groups exist for this).

## Assigning in the portal

1. Open the scope (management group, subscription, resource group or resource) and select **Access control (IAM)**.
2. **Add > Add role assignment**.
3. **Role** tab: pick a role. Job function roles (Reader, Virtual Machine Contributor...) are on one tab and **Privileged administrator roles** (Owner, Contributor, User Access Administrator, Role Based Access Control Administrator) on another.
4. **Members** tab: **Assign access to** *User, group, or service principal* or *Managed identity*, then **Select members**.
5. **Conditions** tab (shown for some roles): add a condition, for example to constrain which roles a Role Based Access Control Administrator may assign.
6. **Assignment type** (tenants with Microsoft Entra ID P2 or Governance and PIM): **Eligible** or **Active**, with optional duration.
7. **Review + assign**.

## Assigning with the Azure CLI

```bash
# Group at resource group scope
grpId=$(az ad group show --group "sg-web-operators" --query id -o tsv)
rgId=$(az group show --name rg-web-prod --query id -o tsv)
az role assignment create \
  --assignee-object-id $grpId --assignee-principal-type Group \
  --role "Virtual Machine Contributor" \
  --scope $rgId

# User at subscription scope
az role assignment create --assignee user1@contoso.com --role "Reader" \
  --scope "/subscriptions/00000000-0000-0000-0000-000000000000"

# Managed identity at a single storage account
az role assignment create --assignee 00000000-0000-0000-0000-000000000000 \
  --role "Storage Blob Data Contributor" \
  --scope "/subscriptions/00000000-0000-0000-0000-000000000000/resourceGroups/rg-data/providers/Microsoft.Storage/storageAccounts/stcontosodata01"

# Management group scope
az role assignment create --assignee user1@contoso.com --role "Reader" \
  --scope "/providers/Microsoft.Management/managementGroups/mg-contoso-prod"

# List and remove
az role assignment list --assignee user1@contoso.com --all --include-inherited --output table
az role assignment delete --assignee user1@contoso.com --role "Reader" \
  --scope "/subscriptions/00000000-0000-0000-0000-000000000000"
```

`--assignee` accepts a UPN, an object ID or a service principal's app ID and looks the principal up in Microsoft Entra ID. `--assignee-object-id` with `--assignee-principal-type` skips that lookup; use it for a service principal or managed identity created seconds ago, whose object may not yet have replicated, and in automation that has no directory read permission. `--role` takes the role name or the role definition ID. `--role` and `--scope` are both **required** on `az role assignment create` in the current CLI reference, and `create` no longer accepts `--resource-group`: pass the resource group's full ID to `--scope` (older examples that use `--resource-group` fail on a current Cloud Shell). `az role assignment list` and `delete` still accept `--resource-group`.

## Assigning with Azure PowerShell

```powershell
# Group at resource group scope
$grp = Get-AzADGroup -DisplayName 'sg-web-operators'
New-AzRoleAssignment -ObjectId $grp.Id -RoleDefinitionName 'Virtual Machine Contributor' `
  -ResourceGroupName 'rg-web-prod'

# User at subscription scope
New-AzRoleAssignment -SignInName 'user1@contoso.com' -RoleDefinitionName 'Reader' `
  -Scope '/subscriptions/00000000-0000-0000-0000-000000000000'

# A single resource by name and type
New-AzRoleAssignment -SignInName 'user1@contoso.com' -RoleDefinitionName 'Reader' `
  -ResourceName 'vm-web-01' -ResourceType 'Microsoft.Compute/virtualMachines' `
  -ResourceGroupName 'rg-web-prod'

# Service principal by application ID
New-AzRoleAssignment -ApplicationId '00000000-0000-0000-0000-000000000000' `
  -RoleDefinitionName 'Storage Blob Data Contributor' `
  -Scope '/subscriptions/00000000-0000-0000-0000-000000000000/resourceGroups/rg-data/providers/Microsoft.Storage/storageAccounts/stcontosodata01'

Get-AzRoleAssignment -SignInName 'user1@contoso.com' -ExpandPrincipalGroups
Remove-AzRoleAssignment -SignInName 'user1@contoso.com' -RoleDefinitionName 'Reader' `
  -Scope '/subscriptions/00000000-0000-0000-0000-000000000000'
```

Principal parameters: `-SignInName` (user UPN), `-ObjectId` (any principal), `-ApplicationId` (service principal). Scope parameters: `-Scope` (any ID) or the `-ResourceGroupName` / `-ResourceName` / `-ResourceType` shortcuts. Role: `-RoleDefinitionName` or `-RoleDefinitionId`.

> **Watch out:** In ARM templates and Bicep a role assignment is a resource of type `Microsoft.Authorization/roleAssignments` whose **name must be a GUID**; the role is referenced by its definition ID (Reader is `acdd72a7-3385-48ef-bd42-f606fba81ae7`), not by its display name.

## Role assignment conditions

A **condition** is an extra check attached to a role assignment that narrows what it allows. Two uses matter at AZ-104 level:

- **Storage data conditions (Azure ABAC)**: on roles with blob or queue data actions, for example "Storage Blob Data Reader, but only for blobs tagged `Project=Cascade`" or "only in container `invoices`". Conditions are added at the same scope as the assignment and need the same permission to add.
- **Delegating role assignment with conditions**: assign **Role Based Access Control Administrator** with a condition such as "may only assign Backup Contributor or Backup Reader, and only to the Marketing and Sales groups". The delegate can then manage those assignments without being able to grant Owner.

In the portal this is the **Conditions** tab; on the command line `az role assignment create` has `--condition` and `--condition-version`, and `New-AzRoleAssignment` has `-Condition` and `-ConditionVersion`. The condition language is beyond AZ-104 detail.

## Managed identities in role assignments

A system-assigned or user-assigned **managed identity** is a service principal, so it is assigned roles exactly like a user. A typical pattern: a VM's managed identity gets **Storage Blob Data Reader** on one storage account so a script on the VM can read blobs with no stored secret. In the portal choose **Managed identity** under **Assign access to**.

## Try it yourself

Cost: nothing; resource groups and role assignments are free.

1. Cloud Shell (Bash):

```bash
az group create --name rg-rbac-lab --location eastus
az ad group create --display-name sg-rbac-lab --mail-nickname sg-rbac-lab
grp=$(az ad group show --group sg-rbac-lab --query id -o tsv)
az role assignment create --assignee-object-id $grp --assignee-principal-type Group \
  --role "Reader" --scope $(az group show --name rg-rbac-lab --query id -o tsv)
az role assignment list --resource-group rg-rbac-lab --output table
```

2. In the portal open **rg-rbac-lab > Access control (IAM) > Role assignments** and find the Reader assignment for the group. Open the subscription's IAM page and note that the assignment does **not** appear there: assignments flow down, not up.
3. Repeat the assignment with PowerShell for a test user at the same scope using `New-AzRoleAssignment -SignInName ... -ResourceGroupName rg-rbac-lab`, then remove it with `Remove-AzRoleAssignment`.
4. Try to delete the group's assignment from a child resource's IAM page (create any free resource, such as an empty network security group `nsg-rbac-lab`, first): the assignment shows as inherited and cannot be removed there.
5. Clean up: remove the assignment first (`az role assignment delete --assignee-object-id $grp --resource-group rg-rbac-lab`), then `az group delete --name rg-rbac-lab --yes` and `az ad group delete --group sg-rbac-lab`. Deleting a resource group does not touch role assignments made at higher scopes.

## Key takeaways

- Scope hierarchy: management group > subscription > resource group > resource; assignments inherit downward and can only be removed where they were made.
- Assign to groups at the narrowest scope that covers the need; 5,000 assignments per subscription and 500 per management group, both fixed.
- Owner, User Access Administrator and Role Based Access Control Administrator can create assignments; Contributor cannot.
- CLI: `az role assignment create --assignee | --assignee-object-id --assignee-principal-type --role --scope` (`--role` and `--scope` required; `create` takes no `--resource-group`).
- PowerShell: `New-AzRoleAssignment -SignInName | -ObjectId | -ApplicationId -RoleDefinitionName -Scope | -ResourceGroupName`.
- Conditions narrow an assignment: storage data attribute conditions, and constraining which roles a delegated RBAC administrator may assign.
