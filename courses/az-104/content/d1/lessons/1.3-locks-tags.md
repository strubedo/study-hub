## Resource locks

A **management lock** protects a subscription, resource group or resource from accidental change **for everyone**, whatever their role. It is the opposite of RBAC: RBAC grants per principal, a lock restricts all principals, including Owners, until someone removes the lock.

| Portal name | CLI and PowerShell name | Users can |
|---|---|---|
| **Delete** | `CanNotDelete` | Read and modify, but not delete |
| **Read-only** | `ReadOnly` | Read only: no update and no delete (similar to everyone having only Reader) |

### Inheritance

- A lock at a parent scope applies to **every resource inside**, including resources created later.
- If several locks apply, the **most restrictive** wins. A ReadOnly lock on a resource group overrides a CanNotDelete lock on a resource in it.
- Extension resources (for example a diagnostic setting on a storage account) inherit the lock of the resource they extend.
- Deleting a resource group that contains **any** resource with a delete lock fails as a whole; no partial deletion happens.

### Locks apply to the control plane only

Locks stop requests to `management.azure.com`, not data operations. A ReadOnly lock on a SQL server does not stop inserts in its databases; a CanNotDelete lock on a storage account does **not** protect the blobs, files or queue messages inside it from deletion through the data plane.

### Surprising side effects

Because many harmless-looking operations are POST requests to Resource Manager, ReadOnly locks break more than you expect. Examples from Microsoft Learn:

- ReadOnly on a **storage account** stops **listing the account keys** (a POST). Users without the keys must use Microsoft Entra credentials for blob and queue data. It also blocks creating blob containers through the control plane and blocks Azure role assignments scoped to the account.
- ReadOnly on a resource group containing **VMs** stops anyone **starting or restarting** them.
- ReadOnly on a resource group containing an **App Service plan** stops scaling the plan up or out.
- ReadOnly on the source or destination **resource group**, or on the **subscription**, stops **moving resources** in or out. Microsoft notes that a resource carrying its own ReadOnly lock can still be moved to another resource group; it is the resource group lock that blocks the move.
- ReadOnly on a **subscription** stops Azure Advisor storing its results.
- CanNotDelete on a resource group stops Resource Manager pruning **deployment history**; at 800 deployments, new deployments fail.
- CanNotDelete on a resource or group prevents deleting **role assignments** there.
- CanNotDelete does **not** block cancelling a subscription.

> **Exam tip:** "Prevent accidental deletion of vnet-hub while still allowing administrators to add subnets" is **CanNotDelete** (Delete) on the VNet. "Nobody may change the production firewall configuration" is **ReadOnly**. If a question says users can no longer start VMs or list storage keys, look for a ReadOnly lock.

### Who can manage locks

Creating or deleting a lock needs `Microsoft.Authorization/locks/*` (or `Microsoft.Authorization/*`). **Owner** and **User Access Administrator** have it; **Contributor does not** (its NotActions exclude `Microsoft.Authorization/*/Write` and `/Delete`). A Contributor can be blocked by a lock they are not allowed to remove, which is exactly the point.

Locks created by managed applications (for example the managed resource group behind Azure Databricks) are owned by the system application and cannot be removed by you; delete the service to delete them.

### Creating locks

Portal: open the subscription, resource group or resource, then **Settings > Locks > Add**, give a **Lock name**, **Lock type** (Read-only or Delete) and optional notes.

```bash
az lock create --name lock-rg-net --lock-type CanNotDelete --resource-group rg-net-prod
az lock create --name lock-vnet --lock-type ReadOnly --resource-group rg-net-prod \
  --resource-name vnet-hub --resource-type Microsoft.Network/virtualNetworks
az lock list --resource-group rg-net-prod -o table
az lock delete --name lock-rg-net --resource-group rg-net-prod
```

```powershell
New-AzResourceLock -LockName 'lock-rg-net' -LockLevel CanNotDelete -ResourceGroupName 'rg-net-prod'
New-AzResourceLock -LockName 'lock-vnet' -LockLevel ReadOnly -ResourceGroupName 'rg-net-prod' `
  -ResourceName 'vnet-hub' -ResourceType 'Microsoft.Network/virtualNetworks'
Get-AzResourceLock -ResourceGroupName 'rg-net-prod'
Remove-AzResourceLock -LockName 'lock-rg-net' -ResourceGroupName 'rg-net-prod'
```

In ARM templates and Bicep a lock is a `Microsoft.Authorization/locks` resource with `level` set to `CanNotDelete` or `ReadOnly`.

## Tags

A **tag** is a name/value pair of metadata such as `Environment = Production` or `CostCenter = 1234`. Tags drive cost reports, automation and policy.

### Where tags apply and the limits

- Resources, resource groups and subscriptions can be tagged. **Management groups cannot.**
- Not every resource type supports tags; classic resources do not.
- **50** tag name/value pairs per resource, resource group or subscription. Need more? Store a JSON string in one tag's value.
- Tag name up to **512** characters, value up to **256** (storage accounts: name 128).
- Tag names cannot contain `<`, `>`, `%`, `&`, `\`, `?`, `/`. Some services add further restrictions (Azure DNS zones, Traffic Manager, Front Door), and a few services allow only 15 tags.
- Tag **names** are case-insensitive for operations; tag **values** are case-sensitive.
- Tags are **plain text**: never put secrets in them.

### Tags are not inherited

A tag on a resource group or subscription is **not** copied to the resources in it. To get inheritance, assign a policy:

| Need | Built-in policy | Effect |
|---|---|---|
| Copy the RG's `CostCenter` tag to resources that lack it | **Inherit a tag from the resource group if missing** | modify |
| Force resources to carry the RG's value even if they have another | **Inherit a tag from the resource group** | modify |
| Same from the subscription | **Inherit a tag from the subscription (if missing)** | modify |
| Block creation of resources without a tag | **Require a tag on resources** | deny |
| Add a fixed tag and value | **Add a tag to resources** | modify |

Modify policies change **new and updated** resources automatically; existing resources need a **remediation task**, and the assignment needs a **managed identity**. Remember that the "Require a tag" definitions for resources do not apply to resource groups.

> **Watch out:** **Cost Management** shows the tags as they were on each usage record. Adding a tag today does not retag last month's costs, and costs only appear under a tag for resources that actually carry it, which is why tag inheritance via policy matters for chargeback.

### Permissions for tagging

Two routes:

- **Write access to the resource itself**, for example **Contributor** (any resource) or **Virtual Machine Contributor** (only VMs).
- **Tag Contributor**, which grants write on `Microsoft.Resources/tags` and lets you tag entities **without any access to the entities themselves**. Microsoft notes that with this role you cannot apply tags to resources or resource groups **through the portal**, but you can apply tags to subscriptions in the portal and do every tag operation with PowerShell or the REST API.

Reader can see tags but not change them.

### Managing tags

Portal: any resource, resource group or subscription has a **Tags** page; the **Tags** service lists every tag in use across subscriptions.

Azure CLI (`az tag` works on any resource ID):

```bash
rgId=$(az group show -n rg-web-prod --query id -o tsv)
az tag create --resource-id $rgId --tags Environment=Production CostCenter=1234   # replaces all tags
az tag update --resource-id $rgId --operation Merge --tags Owner=ops@contoso.com   # adds or changes
az tag update --resource-id $rgId --operation Replace --tags Environment=Production  # only this tag remains
az tag update --resource-id $rgId --operation Delete --tags Owner=ops@contoso.com    # removes listed tag
az tag list --resource-id $rgId
az resource list --tag CostCenter=1234 --query "[].name" -o tsv
az group update --name rg-web-prod --set tags.Environment=Production   # alternative for a resource group
```

Azure PowerShell:

```powershell
$rg = Get-AzResourceGroup -Name 'rg-web-prod'
New-AzTag -ResourceId $rg.ResourceId -Tag @{ Environment = 'Production'; CostCenter = '1234' }   # replaces
Update-AzTag -ResourceId $rg.ResourceId -Tag @{ Owner = 'ops@contoso.com' } -Operation Merge
Update-AzTag -ResourceId $rg.ResourceId -Tag @{ Environment = 'Production' } -Operation Replace
Update-AzTag -ResourceId $rg.ResourceId -Tag @{ Owner = 'ops@contoso.com' } -Operation Delete
Get-AzTag -ResourceId $rg.ResourceId
Get-AzResource -TagName 'CostCenter' -TagValue '1234'
```

**Merge** keeps existing tags and adds or updates the listed ones (a tag name has one value, so merging `Status=Green` overwrites `Status=Normal`). **Replace** removes all tags not listed. `az tag create` and `New-AzTag` also replace everything. The older pattern `Set-AzResourceGroup -Tag @{...}` likewise **replaces** the whole tag set, a classic way to lose tags by accident.

## Try it yourself

Cost: nothing; a resource group, a VNet and a network security group are free.

1. `az group create -n rg-lock-lab -l eastus` and `az network vnet create -g rg-lock-lab -n vnet-lab --address-prefix 10.50.0.0/16`.
2. Add a **CanNotDelete** lock to the resource group. Try `az network vnet delete -g rg-lock-lab -n vnet-lab` and read the `ScopeLocked` error. Add a subnet: it works.
3. Change to **ReadOnly** (delete the lock, create a ReadOnly one). Try adding a subnet: blocked.
4. Remove the lock. Tag the resource group with `CostCenter=1234`, then run `az tag list --resource-id $(az network vnet show -g rg-lock-lab -n vnet-lab --query id -o tsv)`: the VNet has no tag, proving tags are not inherited.
5. Use `az tag update --operation Merge` and `--operation Replace` on the VNet and compare results.
6. Clean up: confirm `az lock list -g rg-lock-lab` is empty, then `az group delete -n rg-lock-lab --yes`.

## Key takeaways

- Locks: **CanNotDelete** (portal Delete) allows read and modify; **ReadOnly** allows read only. They apply to everyone, inherit downward, and the most restrictive wins.
- Locks protect the control plane only; data inside a locked storage account or database can still change.
- ReadOnly side effects: no listing storage keys, no starting VMs, no scaling App Service plans, no moving resources into or out of a ReadOnly-locked resource group.
- Only Owner, User Access Administrator or a role with `Microsoft.Authorization/locks/*` can manage locks; Contributor cannot.
- Tags: 50 per resource, group or subscription; not on management groups; values case-sensitive; not inherited unless a modify policy copies them.
- `Merge` adds, `Replace` and `az tag create` / `New-AzTag` overwrite, `Delete` removes listed tags.
- Tag Contributor tags resources without access to them (command line, or subscriptions in the portal).
