## B2B collaboration in one paragraph

**Microsoft Entra B2B collaboration** (part of Microsoft Entra External ID) lets people from outside your organization use their own identity (another Microsoft Entra tenant, a Microsoft account, Google, or a one-time email passcode) to access your apps and Azure resources. You do not create or manage their passwords. Instead, inviting them creates a **user object in your tenant** that points back to their home identity. You assign that object to groups, apps and Azure roles like any other user, and you can remove it when the project ends.

The guest's user principal name in your tenant is built from their email: `john@fabrikam.com` invited into Contoso becomes `john_fabrikam.com#EXT#@contoso.onmicrosoft.com`. If you see `#EXT#` in a UPN, you are looking at an external user.

## User type versus where the account lives

Two separate properties describe a user, and exam questions mix them deliberately:

| | Authenticates in your tenant (internal) | Authenticates elsewhere (external) |
|---|---|---|
| **UserType = Member** | Internal member: an employee | External member: for example a user from a sister tenant in a multitenant organization |
| **UserType = Guest** | Internal guest: a legacy partner account you created with a password and marked Guest | External guest: the normal B2B invited user |

- An invited B2B user is created with **UserType Guest** by default.
- **UserType** only describes the relationship to your organization. It drives the default directory permissions (guests are more restricted) and lets you target policies, for example a dynamic group rule `(user.userType -eq "Guest")`. It does not change how the user signs in.
- You can convert UserType between Member and Guest in the user's properties, but only do it when the relationship really changed.
- An invited user's **Invitation state** shows *Pending acceptance* until they redeem the invitation, then *Accepted*.

> **Exam tip:** Guests can be granted **Azure RBAC roles** exactly like members. "A consultant from Fabrikam must manage VMs in rg-app-dev" is solved by inviting the consultant as a guest and assigning Virtual Machine Contributor at the resource group scope. You do not create a Contoso account with a password for them.

## Inviting external users

Who can invite depends on the **external collaboration settings** (below); by default all users, including guests, can invite. Administrators with **User Administrator** or **Guest Inviter** can always invite unless invitations are turned off entirely.

Portal: **Microsoft Entra admin center > Entra ID > Users > New user > Invite external user**. Enter the email, optionally a display name and a personal message, and on the **Assignments** tab add groups or roles. The user receives an email with a redemption link; you can also send them a direct link to an app or the My Apps portal, and they redeem by signing in.

For many users at once: **Users > Bulk invite** with the CSV template (email address and redirect URL are required columns).

Microsoft Graph PowerShell:

```powershell
Connect-MgGraph -Scopes "User.Invite.All"
New-MgInvitation -InvitedUserEmailAddress 'john@fabrikam.com' `
  -InvitedUserDisplayName 'John (Fabrikam)' `
  -InviteRedirectUrl 'https://myapps.microsoft.com' `
  -SendInvitationMessage:$true
```

Without `-SendInvitationMessage:$true` the guest object is created but **no email is sent**; you then give the user the redeem URL from the command output yourself. Add `-InvitedUserType Member` to create an external member instead of a guest.

Azure CLI has no invitation command; you can call Graph through `az rest`:

```bash
az rest --method post --url "https://graph.microsoft.com/v1.0/invitations" \
  --body '{"invitedUserEmailAddress":"john@fabrikam.com","inviteRedirectUrl":"https://myapps.microsoft.com","sendInvitationMessage":true}'
```

Once the guest exists, Azure role assignment is ordinary: `az role assignment create --assignee <guest object ID> --role "Reader" --scope <scope>`. Use the object ID rather than the `#EXT#` UPN to avoid quoting problems.

## External collaboration settings

**Entra ID > External Identities > External collaboration settings** controls the B2B experience tenant-wide:

**Guest user access** (what guests can see in your directory):

| Setting | Effect |
|---|---|
| Guest users have the same access as members | Most inclusive |
| Guest users have limited access to properties and memberships of directory objects | **Default**. Guests cannot enumerate users and groups but can see membership of non-hidden groups |
| Guest user access is restricted to properties and memberships of their own directory objects | Most restrictive: guests see only their own profile |

**Guest invite settings** (who can send invitations):

| Setting | Who can invite |
|---|---|
| Anyone in the organization can invite guest users including guests and non-admins | Most inclusive |
| Member users and users assigned to specific admin roles can invite guest users including guests with member permissions | Members, admins |
| Only users assigned to specific admin roles can invite guest users | User Administrator, Guest Inviter (and higher) |
| No one in the organization can invite guest users including admins | Invitations off |

Microsoft Learn says that by default all users, including B2B guests, can invite external users; check your tenant's current selection on the page.

**Collaboration restrictions** let you either **allow invitations only to** listed domains (allowlist) or **deny invitations to** listed domains (blocklist), not both at once. These restrictions apply to new invitations; they do not remove guests who already exist.

**Enable guest self-service sign up via user flows** lets your own applications offer a sign-up page that creates guest accounts.

> **Exam tip:** "Only partner domain fabrikam.com may ever be invited" is **Collaboration restrictions > Allow invitations only to the specified domains**. "Help desk staff must invite guests but not hold an admin role" is the **Guest Inviter** role.

## Cross-tenant access settings

**Entra ID > External Identities > Cross-tenant access settings** controls collaboration with **other Microsoft Entra tenants** in more detail than the external collaboration settings, which treat all external domains alike.

- **Default settings** apply to every external Microsoft Entra organization. Out of the box, **B2B collaboration is allowed** inbound and outbound, and **B2B direct connect** (used for Teams shared channels) is **blocked**.
- **Organizational settings** let you add a specific tenant (by domain or tenant ID) and override the defaults for it. Organizational settings take precedence over the defaults.
- **Inbound** settings control which external users can reach your resources; **outbound** settings control whether your users can be invited into other tenants. Both can be scoped to specific users, groups and applications.
- **Trust settings** (inbound) decide whether your Conditional Access policies accept **MFA**, **compliant device** and **Microsoft Entra hybrid joined device** claims from the guest's home tenant, so a guest who already did MFA at Fabrikam is not asked again in Contoso.

Use external collaboration settings for "which domains and who may invite", and cross-tenant access settings for "how we treat users from one particular Microsoft Entra tenant".

## Managing guests over time

- Remove guests when they no longer need access. With Microsoft Entra ID Governance you can use access reviews and reports of inactive guests; without it, review the **Users** list filtered by **User type = Guest** and the last sign-in date.
- Guests count toward the External ID monthly active user billing model; the first tier of monthly active users is free (see the External ID pricing page for the current numbers).
- Deleting a guest removes their access in your tenant only; their home account is unaffected.

## Try it yourself

Cost: nothing. You need a second email address you can read (a personal mailbox works).

1. In the Entra admin center, open **External Identities > External collaboration settings** and note the current **Guest invite settings** and **Guest user access** selections.
2. Invite your second address: **Users > New user > Invite external user**. Check the new user's **User type** (Guest), UPN (`#EXT#`) and **Invitation state**.
3. Redeem the invitation from the email in a private browser window and confirm the state changes to *Accepted*.
4. In the Azure portal create a resource group `rg-guest-lab` (Cloud Shell: `az group create --name rg-guest-lab --location eastus`) and assign the guest **Reader** on it: `az role assignment create --assignee <guest-object-id> --role Reader --scope $(az group show -n rg-guest-lab --query id -o tsv)`. Sign in as the guest at portal.azure.com, switch directory to your tenant, and confirm they see only that resource group.
5. Optional: set **Collaboration restrictions** to deny `example.com` and try inviting `someone@example.com` to see the block. Set it back afterwards.
6. Clean up: `az group delete --name rg-guest-lab --yes`, delete the guest user, and restore any setting you changed. An empty resource group costs nothing.

## Key takeaways

- B2B collaboration creates a user object in your tenant (UPN contains `#EXT#`) that authenticates at the guest's home identity provider.
- UserType (Member or Guest) and internal or external authentication are independent; invited users default to Guest.
- Guests can be added to groups and given Azure roles like any user.
- Invite in the portal (**Users > New user > Invite external user**), in bulk with **Bulk invite**, or with `New-MgInvitation` (`-SendInvitationMessage:$true` to send email).
- External collaboration settings control guest directory access (default: limited access), who can invite, and allow or deny lists of domains.
- Guest Inviter lets non-admins invite when invitations are limited to admin roles.
- Cross-tenant access settings control inbound and outbound B2B collaboration and B2B direct connect per Microsoft Entra organization, and whether to trust another tenant's MFA and device claims.
