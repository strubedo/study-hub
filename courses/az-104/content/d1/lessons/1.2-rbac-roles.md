## Azure RBAC in three parts

**Azure role-based access control (Azure RBAC)** is the authorization system of **Azure Resource Manager**. Every request to manage a resource (create a VM, delete a subnet, list storage keys) goes to Resource Manager, which checks whether the caller has a **role assignment** that allows the action. A role assignment has exactly three parts:

| Part | Question it answers | Examples |
|---|---|---|
| **Security principal** | Who? | A user, a group, a service principal (an app), a managed identity |
| **Role definition** | What can they do? | Owner, Reader, Virtual Machine Contributor, a custom role |
| **Scope** | Where? | A management group, subscription, resource group or single resource |

Access is granted by creating a role assignment and removed by deleting it. Azure RBAC is **additive**: a principal's effective permissions are the union of all their role assignments, including those inherited from groups (group membership is transitive, so nested group members get the access too). Azure RBAC is included with every subscription; it has no license cost.

## Role definitions

A role definition is a JSON document listing permissions as **operation strings** of the form `{Provider}/{resourceType}/{action}`, for example `Microsoft.Compute/virtualMachines/start/action`. Its key properties:

| Property | Meaning |
|---|---|
| `Actions` | Control plane (management) operations the role allows. Wildcards allowed: `*`, `*/read`, `Microsoft.Compute/*` |
| `NotActions` | Operations **subtracted** from a wildcard in `Actions` |
| `DataActions` | Data plane operations allowed, such as reading blob contents |
| `NotDataActions` | Data operations subtracted from `DataActions` |
| `AssignableScopes` | Where the role can be assigned. Built-in roles use `/` (everywhere) |

**Effective permissions of one role** = `Actions - NotActions` (control plane) and `DataActions - NotDataActions` (data plane).

Here is the built-in **Contributor** role as Azure PowerShell shows it (abbreviated description):

```json
{
  "Name": "Contributor",
  "Id": "b24988ac-6180-42a0-ab88-20f7382dd24c",
  "IsCustom": false,
  "Actions": [ "*" ],
  "NotActions": [
    "Microsoft.Authorization/*/Delete",
    "Microsoft.Authorization/*/Write",
    "Microsoft.Authorization/elevateAccess/Action",
    "Microsoft.Blueprint/blueprintAssignments/write",
    "Microsoft.Blueprint/blueprintAssignments/delete",
    "Microsoft.Compute/galleries/share/action",
    "Microsoft.Purview/consents/write",
    "Microsoft.Purview/consents/delete",
    "Microsoft.Resources/deploymentStacks/manageDenySetting/action",
    "Microsoft.Subscription/cancel/action",
    "Microsoft.Subscription/enable/action"
  ],
  "DataActions": [],
  "NotDataActions": [],
  "AssignableScopes": [ "/" ]
}
```

`*` allows every management action, including actions added in future. The `Microsoft.Authorization/*/Write` and `/Delete` exclusions are why a Contributor **cannot create or delete role assignments** (and cannot create or delete resource locks, which are also `Microsoft.Authorization` resources).

> **Watch out:** **NotActions is not a deny.** If a user has Contributor and also has User Access Administrator, the second role grants `Microsoft.Authorization/*` and the user *can* assign roles. Only a **deny assignment** blocks an action that another role grants.

## Control plane and data plane

- **Control plane** (`Actions`): managing the resource through `management.azure.com`: create a storage account, change its firewall, delete a container, list the account keys.
- **Data plane** (`DataActions`): working with the data inside: read a blob, write a queue message, read a Key Vault secret.

Roles with `*` in `Actions` do **not** get data plane access. An **Owner** of a subscription can delete a storage account but cannot read a blob with Microsoft Entra authentication unless they also have a data role such as **Storage Blob Data Reader**. (An Owner or Contributor *can* list the storage account keys, a control plane action, and then read data with the key. That loophole is why storage accounts can disable Shared Key access.)

## Built-in roles you must know

Microsoft groups five as fundamental; the first three apply to every resource type.

| Role | What it allows | What it does not |
|---|---|---|
| **Owner** | Everything, including assigning roles | |
| **Contributor** | Create and manage all resources | Assign roles, manage Blueprints assignments, share image galleries, change deployment stack deny settings, cancel or re-enable the subscription |
| **Reader** | View all resources | Make any change; read data plane content |
| **User Access Administrator** | Manage access: `Microsoft.Authorization/*`, plus `*/read` | Create or change resources |
| **Role Based Access Control Administrator** | Create and delete role assignments (`roleAssignments/write` and `/delete`), plus `*/read` | Manage access by other means such as Azure Policy; can be limited by **conditions** to specific roles or principals |

User Access Administrator and Role Based Access Control Administrator can both assign the Owner role (to others or themselves) unless a condition restricts them. Microsoft positions **Role Based Access Control Administrator** as the least-privilege choice for delegating role assignment, because it lacks the broader `Microsoft.Authorization/*` rights (such as managing policy assignments and locks) that User Access Administrator has.

Service-specific roles follow the pattern *Service* Contributor or Reader and are the usual least-privilege answer:

| Role | Scope of rights |
|---|---|
| **Virtual Machine Contributor** | Create and manage VMs, their disks and NICs, run extensions; join VMs to subnets, NSGs, public IPs and load balancer pools in its scope. **No** management of the virtual network or storage account the VM connects to, and no role assignment |
| **Network Contributor** | Manage networks (VNets, NSGs, load balancers...). Not VMs |
| **Storage Account Contributor** | Manage storage accounts, including access to the account keys |
| **Storage Blob Data Owner / Contributor / Reader** | Data plane access to blob containers and blobs (Owner adds POSIX ACL management for Data Lake) |
| **Virtual Machine Administrator Login / User Login** | Sign in to a VM with Microsoft Entra credentials as admin or standard user |
| **Tag Contributor** | Manage tags on entities without access to the entities themselves |
| **Resource Policy Contributor** | Create and modify policy definitions and assignments |
| **Cost Management Contributor / Reader** | View costs; Contributor also manages budgets and exports |
| **Key Vault Administrator** and other Key Vault data roles | Data plane on vaults using the Azure RBAC permission model |

> **Exam tip:** In a least-privilege question, pick the narrowest role that covers *every* requirement at the narrowest scope that contains *every* target. Watch where the targets live: Virtual Machine Contributor includes `Microsoft.Network/virtualNetworks/subnets/join/action`, but only at the scope where it is assigned. A user with Virtual Machine Contributor on `rg-app` who must connect new VMs to `vnet-hub` in `rg-net` also needs a join permission at the VNet (or its resource group) scope.

## Azure roles versus Microsoft Entra roles

| | Azure roles (Azure RBAC) | Microsoft Entra roles |
|---|---|---|
| Control | Azure resources | Directory objects: users, groups, apps, domains, licenses |
| Examples | Owner, Contributor, Reader, Virtual Machine Contributor | Global Administrator, User Administrator, Groups Administrator, Helpdesk Administrator, Billing Administrator |
| Scope | Management group, subscription, resource group, resource | Tenant, administrative unit, or a single object (for example one app) |
| Where assigned | **Access control (IAM)** on the scope | **Entra ID > Roles & admins** |
| Custom roles | Yes | Yes (needs P1) |

They do not overlap by default: a **Global Administrator** has no access to Azure resources, and a subscription **Owner** cannot create users. The bridge is **elevated access**: a Global Administrator can set **Access management for Azure resources** to Yes, which assigns them **User Access Administrator at root scope (`/`)**. That is covered in the "interpret access" lesson.

## Custom roles

When no built-in role fits, create a custom role. Start from a built-in role (portal: **Access control (IAM) > Add > Add custom role > Clone a role**) or write JSON:

```json
{
  "Name": "Contoso VM Operator",
  "IsCustom": true,
  "Description": "Start, restart and deallocate VMs and read compute, network and storage.",
  "Actions": [
    "Microsoft.Compute/*/read",
    "Microsoft.Network/*/read",
    "Microsoft.Storage/*/read",
    "Microsoft.Compute/virtualMachines/start/action",
    "Microsoft.Compute/virtualMachines/restart/action",
    "Microsoft.Compute/virtualMachines/deallocate/action",
    "Microsoft.Resources/subscriptions/resourceGroups/read"
  ],
  "NotActions": [],
  "DataActions": [],
  "NotDataActions": [],
  "AssignableScopes": [
    "/subscriptions/00000000-0000-0000-0000-000000000000"
  ]
}
```

```bash
az role definition create --role-definition @vm-operator.json
```

```powershell
New-AzRoleDefinition -InputFile ./vm-operator.json
```

Rules to remember:

- Creating or updating a custom role needs `Microsoft.Authorization/roleDefinitions/write` on **all** its assignable scopes: in practice **Owner** or **User Access Administrator** there.
- `AssignableScopes` may list management groups, subscriptions and resource groups, but **only one management group**. `/` is reserved for built-in roles.
- A custom role with **DataActions cannot be assigned at management group scope** (it can still list a management group in `AssignableScopes` and be assigned on the subscriptions below it).
- A tenant supports up to **5,000 custom roles**.
- The role name must be unique in the tenant. Delete a custom role only after removing its assignments.

## Try it yourself

Cost: nothing. Role definitions and assignments are free.

1. In the portal open a subscription > **Access control (IAM) > Roles**. Search for **Virtual Machine Contributor**, open **View** and read its **Permissions** and **JSON** tabs. Note what it excludes.
2. In Cloud Shell (Bash): `az role definition list --name "Contributor" --output json` and compare `actions` and `notActions` with the JSON above.
3. In Cloud Shell (PowerShell): `Get-AzRoleDefinition -Name "Storage Blob Data Reader" | ConvertTo-Json` and find `DataActions`.
4. Save the custom role JSON above to `vm-operator.json` with your own subscription ID (`az account show --query id -o tsv`), then run `az role definition create --role-definition @vm-operator.json`. Find it in **Roles** with type **CustomRole**.
5. Clean up: `az role definition delete --name "Contoso VM Operator"`. No resource group is created in this lab; nothing is billed.

## Key takeaways

- A role assignment = security principal + role definition + scope; permissions are additive across assignments and nested groups.
- Effective permissions of a role: `Actions - NotActions` and `DataActions - NotDataActions`. NotActions is a subtraction, not a deny.
- Owner, Contributor and Reader cover every resource type; Contributor cannot assign roles. User Access Administrator and Role Based Access Control Administrator manage access; the latter is narrower and supports conditions.
- `*` management rights do not include data plane access; use data roles such as Storage Blob Data Contributor.
- Azure roles manage resources at management group, subscription, resource group or resource scope; Microsoft Entra roles manage the directory at tenant, administrative unit or object scope.
- Custom roles: JSON with AssignableScopes (one management group at most), `az role definition create` or `New-AzRoleDefinition`, DataActions roles cannot be assigned at management group scope, 5,000 per tenant.
