## Policy versus RBAC

Azure RBAC answers **who** may perform an action. **Azure Policy** answers **what state resources may be in**, whoever creates them. An Owner can be stopped by policy from creating a VM in `westeurope`; a Reader is not given any extra rights by policy. Use both: RBAC limits people, Policy limits configurations.

## Building blocks

| Object | What it is |
|---|---|
| **Policy definition** | A JSON rule: an `if` condition on resource properties and a `then` **effect**. Hundreds are built in; you can write custom ones |
| **Initiative** (policy set definition) | A group of policy definitions assigned and tracked as one, for example a regulatory compliance set. Microsoft recommends using initiatives even for one policy so you can add more later without new assignments |
| **Assignment** | A definition or initiative applied to a **scope** (management group, subscription, resource group or resource), with parameter values, optional **exclusions** (`notScopes`), an **enforcement mode** and, for some effects, a **managed identity** |
| **Exemption** | Removes a specific scope or resource from an assignment's evaluation with a reason (Waiver or Mitigated) and optional expiry, while keeping it visible in compliance |

The assignment applies to all resources in its scope and below. Definitions are stored at a management group or subscription and can be assigned at that level or below.

A custom definition (this one denies public IP addresses with the Basic SKU, as an illustration):

```json
{
  "properties": {
    "displayName": "Deny Basic SKU public IP addresses",
    "mode": "Indexed",
    "parameters": {},
    "policyRule": {
      "if": {
        "allOf": [
          { "field": "type", "equals": "Microsoft.Network/publicIPAddresses" },
          { "field": "Microsoft.Network/publicIPAddresses/sku.name", "equals": "Basic" }
        ]
      },
      "then": { "effect": "deny" }
    }
  }
}
```

`mode` is `All` (resource groups, subscriptions and all resource types) or `Indexed` (only types that support tags and location). Tag and location policies normally use `Indexed`.

## Effects

Each definition has exactly one effect (often a parameter so the assignment can choose). The current list on Microsoft Learn: `addToNetworkGroup`, `append`, `audit`, `auditIfNotExists`, `deny`, `denyAction`, `deployIfNotExists`, `disabled`, `manual`, `modify`, `mutate`. The ones AZ-104 expects you to know:

| Effect | New or updated resource | Existing resource during an evaluation cycle | Needs managed identity |
|---|---|---|---|
| **disabled** | Not evaluated | Not evaluated | No |
| **append** | Adds fields to the request (for example IP rules); if that would change a value already in the request, it acts as deny | Marked non-compliant; not changed | No |
| **modify** | Adds, replaces or removes properties or **tags** in the request | Marked non-compliant; fixed by a **remediation task** | **Yes** |
| **deny** | Request fails with **403 Forbidden** | Marked non-compliant; not changed or deleted | No |
| **audit** | Allowed; warning in the Activity log; marked non-compliant | Marked non-compliant | No |
| **auditIfNotExists** | After success, checks a **related** resource (for example a VM's antimalware extension); non-compliant if missing | Same | No |
| **deployIfNotExists** | After success, **deploys a template** if the related resource is missing (default delay `PT10M`) | Marked non-compliant; fixed by a **remediation task** | **Yes** |
| **denyAction** | Blocks the **delete** action on matching resources | n/a | No |

Order of evaluation on a create or update: **disabled** first, then **append** and **modify** (which can change the request), then **deny**, then **audit**, and after the resource provider succeeds, **auditIfNotExists** and **deployIfNotExists**.

> **Watch out:** **deny never deletes or fixes existing resources.** Assign "Allowed locations" with deny to a subscription that already has VMs in `westus`, and those VMs keep running; they are simply reported as non-compliant. Only new or updated resources are blocked.

Several assignments affecting one resource are evaluated **independently**; the result is cumulative and the most restrictive wins. A resource must satisfy every deny assignment that applies to it. To let one resource group escape a subscription-wide deny, add the group to that assignment's **exclusions** or create an **exemption**.

## Built-in definitions worth knowing by name

| Definition | Effect | Note |
|---|---|---|
| Allowed locations | Deny (parameterised) | **Excludes resource groups** and global resources; use "Allowed locations for resource groups" for the groups themselves |
| Allowed locations for resource groups | Deny | Applies to resource groups only |
| Allowed virtual machine size SKUs | Deny | |
| Not allowed resource types | Deny | Audit and Disabled also allowed |
| Require a tag on resources / Require a tag and its value on resources | Deny | Do **not** apply to resource groups |
| Require a tag on resource groups | Deny | |
| Inherit a tag from the resource group if missing | Modify | Copies the RG's tag onto resources that lack it |
| Inherit a tag from the resource group | Modify | Adds or replaces the tag from the RG |
| Add a tag to resources | Modify | |

## Assigning a policy

Portal: **Policy > Authoring > Assignments > Assign policy**:

1. **Basics**: **Scope** (management group or subscription, optionally a resource group), **Exclusions**, **Policy definition**, assignment name, **Policy enforcement** (**Enabled** or **Disabled**).
2. **Parameters**: for example the list of allowed locations.
3. **Remediation**: for modify and deployIfNotExists, **Create a remediation task** for existing resources, and the **managed identity** (system-assigned in a chosen location, or user-assigned).
4. **Non-compliance messages**: custom text shown when a request is denied.

Azure CLI (built-in "Allowed locations", by definition name):

```bash
rgId=$(az group show --name rg-web-prod --query id -o tsv)
az policy assignment create --name allowed-locations-web \
  --display-name "Allowed locations for rg-web-prod" \
  --policy e56962a6-4747-49cd-b67b-bf8b01975c4c \
  --scope $rgId \
  --params '{ "listOfAllowedLocations": { "value": [ "eastus", "eastus2" ] } }'
```

Azure PowerShell:

```powershell
$def = Get-AzPolicyDefinition -Name 'e56962a6-4747-49cd-b67b-bf8b01975c4c'
$rg  = Get-AzResourceGroup -Name 'rg-web-prod'
New-AzPolicyAssignment -Name 'allowed-locations-web' -PolicyDefinition $def `
  -Scope $rg.ResourceId -PolicyParameterObject @{ listOfAllowedLocations = @('eastus','eastus2') }
```

For a modify or deployIfNotExists definition add a managed identity: `--mi-system-assigned --location eastus` (CLI) or `-IdentityType SystemAssigned -Location eastus` (PowerShell). Exclusions are `--not-scopes` / `-NotScope`. Enforcement off is `--enforcement-mode DoNotEnforce` / `-EnforcementMode DoNotEnforce`.

## Enforcement mode

`enforcementMode` on the assignment is **Default** (enforce) or **DoNotEnforce**. With DoNotEnforce, resources are still **evaluated and compliance is reported**, but the effect is not applied and no deny entries are written to the Activity log: deny does not block, modify does not change. It is the safe way to test a new assignment's impact ("what if") before enforcing. Remediation tasks can still be started for deployIfNotExists while in DoNotEnforce. (A third value, `Enroll`, supports staged rollout and is outside AZ-104.)

## Remediation

Existing non-compliant resources are fixed only by a **remediation task**, and only for **modify** and **deployIfNotExists**:

- The assignment's **managed identity** performs the change. The definition lists the roles it needs in `roleDefinitionIds`; when you assign in the portal with a system-assigned identity, the portal grants those roles automatically. With the CLI or PowerShell, or if you later change `roleDefinitionIds`, you must grant them yourself.
- Granting roles to the identity needs `Microsoft.Authorization/roleAssignments/write`, so the person assigning such a policy typically needs **Owner** or **User Access Administrator** (or Role Based Access Control Administrator) in addition to policy rights.
- Each assignment can have only **one** managed identity.

```bash
az policy remediation create --name remediate-tags \
  --policy-assignment "/subscriptions/00000000-0000-0000-0000-000000000000/providers/Microsoft.Authorization/policyAssignments/inherit-costcenter"
```

By default (`--resource-discovery-mode ExistingNonCompliant`) the task fixes the resources already recorded as non-compliant.

```powershell
Start-AzPolicyRemediation -Name 'remediate-tags' `
  -PolicyAssignmentId '/subscriptions/00000000-0000-0000-0000-000000000000/providers/Microsoft.Authorization/policyAssignments/inherit-costcenter'
```

## Who can manage policy

**Resource Policy Contributor** includes most policy operations; **Owner** has all. **Contributor** and **Reader** can read policy objects; Contributor can trigger remediation but cannot create or update definitions or assignments.

## Compliance evaluation timing

- A resource created or updated in a scope with an assignment: its compliance result appears about **15 minutes** later.
- A new or updated assignment is evaluated against existing resources; this takes time and has no fixed completion guarantee.
- The **standard evaluation cycle** reevaluates all assignments **once every 24 hours**.
- **On-demand scan**: `az policy state trigger-scan [--resource-group rg]` or `Start-AzPolicyComplianceScan [-ResourceGroupName rg]`; asynchronous and can take a while.

View results in **Policy > Compliance**, or `az policy state summarize` and `az policy state list`.

## Try it yourself

Cost: nothing; Policy for Azure resources is free and no billable resources are created.

1. `az group create -n rg-policy-lab -l eastus`.
2. Assign **Allowed locations** to `rg-policy-lab` with only `eastus` (CLI above, using the lab group).
3. Wait a few minutes, then try `az network nsg create -g rg-policy-lab -n nsg-test -l westus`. Read the `RequestDisallowedByPolicy` error. Repeat with `-l eastus`: it succeeds.
4. Change the assignment to DoNotEnforce (`az policy assignment update --name <name> --scope <rg-id> --enforcement-mode DoNotEnforce`), retry the `westus` NSG and see that it is created and later reported non-compliant.
5. Clean up: `az policy assignment delete --name <name> --scope <rg-id>` and `az group delete -n rg-policy-lab --yes`.

## Key takeaways

- Definition (rule + effect) > initiative (set of definitions) > assignment (scope, parameters, exclusions, enforcement mode, identity).
- deny blocks new and updated requests with 403; existing resources are only flagged non-compliant.
- modify and deployIfNotExists need a managed identity and are the only effects with remediation tasks for existing resources.
- append and modify run before deny; auditIfNotExists and deployIfNotExists run after the resource is created.
- DoNotEnforce evaluates and reports but applies no effect: test before enforcing.
- Compliance for a changed resource appears in about 15 minutes; full reevaluation every 24 hours; on-demand with `az policy state trigger-scan` or `Start-AzPolicyComplianceScan`.
- "Allowed locations" does not cover resource groups; "Require a tag" definitions do not apply to resource groups.
