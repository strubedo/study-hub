## Where identities live

Every Azure subscription trusts exactly one **Microsoft Entra ID** tenant (Microsoft Entra ID is the product formerly called Azure Active Directory, or Azure AD). The tenant holds the users, groups, devices and applications that sign in to Azure, Microsoft 365 and any app you connect to it. When you create an Azure account, a tenant is created for you (for example `contoso.onmicrosoft.com`) and you become its first Global Administrator.

You manage the tenant in the **Microsoft Entra admin center** (entra.microsoft.com) or in the Azure portal under **Microsoft Entra ID**; both edit the same directory. From the command line you have two choices:

| Tool | Module or command group | Notes |
|---|---|---|
| Azure CLI | `az ad user`, `az ad group`, `az ad group member` | Covers the common user and group tasks |
| PowerShell | **Microsoft Graph PowerShell** (`Connect-MgGraph`, `New-MgUser`, `New-MgGroup`) | The supported module for directory work |
| PowerShell (Az) | `New-AzADUser`, `New-AzADGroup` | Part of Az.Resources; fine for basic objects |

> **Watch out:** The old **AzureAD** and **MSOnline** PowerShell modules are retired. Scripts that use `New-AzureADUser` or `Set-MsolUser` are legacy; write new automation with Microsoft Graph PowerShell.

Directory work needs **Microsoft Entra roles**, not Azure roles. Creating and editing users and groups needs at least **User Administrator** (or **Groups Administrator** for groups only). An Azure Owner on a subscription cannot create a user unless they also hold an Entra role; this split is tested often and is covered again in the RBAC lessons.

## User accounts

A user object has a **user principal name (UPN)** such as `user1@contoso.com`, a display name, a password (cloud users) or a link to on-premises Active Directory (synchronized users), and dozens of optional properties. The ones that matter most to an Azure administrator:

| Property | Why it matters |
|---|---|
| **User type** (`Member` or `Guest`) | Describes the user's relationship to your organization; guests get more limited default directory permissions |
| **Account enabled** | Unchecking it blocks sign-in without deleting the account (it used to be called *Block sign in*) |
| **Usage location** | A two-letter country code; required before a license can be assigned directly to the user |
| **Department, Job title, Company name, Manager** | Organisational data, and the attributes most dynamic group rules use |
| **Source** | Cloud-created, synchronized from Windows Server AD, or an external (B2B) identity |

Synchronized users are mastered on-premises: change their name or department in Active Directory, not in the cloud. Cloud-only users are edited in the admin center or with `Update-MgUser`.

**Deleting** a user moves it to **Deleted users**, where it can be restored for **30 days**; after that it is removed permanently. Groups: a deleted **Microsoft 365 group** can be restored from **Groups > Deleted groups** for 30 days. Soft delete and restore of **cloud security groups** is in **preview** (public cloud only); distribution groups can't be restored, and without that preview a deleted security group has to be re-created.

### Creating a user

Portal: **Microsoft Entra admin center > Entra ID > Users > New user > Create new user**. The Basics tab takes the UPN, display name and password; **Properties** adds the user type, job info and usage location; **Assignments** can add the user to groups, one administrative unit or a role at creation time.

Azure CLI:

```bash
az ad user create \
  --display-name "Ben Smith" \
  --user-principal-name ben@contoso.onmicrosoft.com \
  --password "<password>" \
  --force-change-password-next-sign-in true
```

Microsoft Graph PowerShell:

```powershell
Connect-MgGraph -Scopes "User.ReadWrite.All","Group.ReadWrite.All"
$pw = @{ Password = '<password>'; ForceChangePasswordNextSignIn = $true }
New-MgUser -DisplayName 'Ben Smith' -UserPrincipalName 'ben@contoso.onmicrosoft.com' `
  -MailNickname 'ben' -AccountEnabled -PasswordProfile $pw -UsageLocation 'US'
```

### Bulk operations

For many users at once use the bulk options on **Entra ID > Users**: **Bulk create**, **Bulk invite** (guests), **Bulk delete** and **Download users**. Bulk create gives you a CSV template; keep the header rows exactly as downloaded. The only required columns are **Name**, **User name** and **Initial password**. Bulk create makes internal member accounts and sends no email, so you must hand out the passwords yourself. Bulk invite is the one that sends B2B invitations. Groups have the same idea for membership: **Bulk operations > Import members** with a CSV of UPNs.

> **Exam tip:** "Create 500 users from an HR spreadsheet with the least administrative effort" points at **Bulk create** with the CSV template (or a script that loops over a CSV). "Invite 200 partner users" points at **Bulk invite**.

## Groups

### Group types

| | Security group | Microsoft 365 group |
|---|---|---|
| Purpose | Access to resources: Azure RBAC assignments, app access, licenses, policies | Collaboration: shared mailbox, calendar, SharePoint site, Teams |
| Members | Users, devices, service principals, and other groups (nesting) | Users only |
| Can be nested in another group | Yes | No |
| Used for Azure role assignments | Yes | Yes (but use security groups for access control) |

Two further options appear when you create a security group:

- **Microsoft Entra roles can be assigned to the group** (role-assignable group). This must be chosen at creation, cannot be changed later, and forces the membership type to **Assigned**.
- Groups synchronized from on-premises AD, and mail-enabled security groups or distribution lists, cannot be edited here; manage them at their source or in the Exchange or Microsoft 365 admin center.

### Membership types

| Membership type | How members get in | Licensing |
|---|---|---|
| **Assigned** | An owner or administrator adds them | Free |
| **Dynamic user** | A rule on user attributes, for example `(user.department -eq "Sales")` | **Microsoft Entra ID P1** (or Intune for Education) for each unique user who is a member of any dynamic group |
| **Dynamic device** | A rule on device attributes, for example `(device.deviceOSType -eq "Windows")` | No license needed for devices |

Dynamic group facts that appear in questions:

- A rule targets users **or** devices, never both, and a device rule cannot use the owner's user attributes.
- You cannot add or remove members by hand in a dynamic group; change the attribute or the rule.
- You can switch an existing group between Assigned, Dynamic User and Dynamic Device in the group's **Properties**; the group keeps its name and object ID. Converting a static group to dynamic keeps only the existing members who match the rule, removes the rest and adds anyone else who matches.
- Microsoft 365 groups can be dynamic too, but only with user rules.
- Processing is not instant after an attribute changes; check the **Dynamic membership rules** and membership processing status on the group.

> **Watch out:** "The **Membership type** list only shows **Assigned**" has two usual causes: the tenant has no Microsoft Entra ID P1 licenses, or the group is being created as role-assignable.

Rule syntax uses `-eq`, `-ne`, `-startsWith`, `-contains`, `-match`, `-in` and `-and` / `-or`:

```text
(user.department -eq "Sales") -and (user.usageLocation -eq "US")
(user.jobTitle -startsWith "Network")
(device.deviceOSType -eq "Windows") -and (device.accountEnabled -eq true)
```

### Creating groups

Portal: **Entra ID > Groups > All groups > New group**, then choose **Group type**, name, **Membership type** and (for assigned groups) owners and members.

Azure CLI (assigned security group, then add a member by object ID):

```bash
az ad group create --display-name "sg-network-admins" --mail-nickname "sg-network-admins"
userId=$(az ad user show --id ben@contoso.onmicrosoft.com --query id -o tsv)
az ad group member add --group "sg-network-admins" --member-id $userId
```

Microsoft Graph PowerShell (a dynamic security group):

```powershell
New-MgGroup -DisplayName 'dyn-sales-users' -MailEnabled:$false -MailNickname 'dyn-sales-users' `
  -SecurityEnabled -GroupTypes 'DynamicMembership' `
  -MembershipRule '(user.department -eq "Sales")' -MembershipRuleProcessingState 'On'
```

`-GroupTypes 'Unified'` makes a Microsoft 365 group instead; a dynamic Microsoft 365 group lists both `Unified` and `DynamicMembership`.

### Group properties you manage

Owners (who manage membership without any Entra role), description, membership rule, **expiration policy** (Microsoft 365 groups) and group-based license assignments.

## Administrative units

An **administrative unit (AU)** is a container of users, groups or devices used to **scope Microsoft Entra roles**. A regional help desk can hold **User Administrator** or **Helpdesk Administrator** scoped to the `AU-Europe` unit and reset passwords only for those users.

- Create them in **Entra ID > Roles & admins > Admin units** (Privileged Role Administrator or Global Administrator).
- AUs cannot be nested.
- Adding a group to an AU puts the **group object** in scope, not its members; add users directly if the scoped admin must manage them.
- Licensing: creating AUs is free; each **administrator assigned a role scoped to an AU needs Microsoft Entra ID P1**; members need only Free, unless you use dynamic membership rules for the AU, in which case each member needs P1.

AUs have nothing to do with Azure RBAC scopes. Azure resources are scoped by management group, subscription, resource group and resource.

## Try it yourself

Cost: nothing. Microsoft Entra ID Free comes with every Azure subscription. The dynamic group step needs P1; if you have none, read it and skip it (a free P1 trial can be activated in the Microsoft 365 or Entra admin center, but remember to let it lapse).

1. In the Microsoft Entra admin center, open **Entra ID > Overview** and note your tenant's initial domain (`<yourtenant>.onmicrosoft.com`).
2. Create a user **Ben Smith** with **Department** `Sales` and **Usage location** United States.
3. Open **Azure Cloud Shell** (Bash) from the portal toolbar and create a second user and an assigned group with the CLI commands above, replacing the domain. Confirm with `az ad group member list --group "sg-network-admins" --query "[].userPrincipalName"`.
4. In Cloud Shell (PowerShell), run `Connect-MgGraph -Scopes "User.ReadWrite.All","Group.ReadWrite.All"` and then `Get-MgUser -Filter "department eq 'Sales'"`. If the Graph module is not loaded, run `Install-Module Microsoft.Graph -Scope CurrentUser` first.
5. With P1 only: create `dyn-sales-users` with the rule `(user.department -eq "Sales")`, wait a few minutes and check that Ben appears.
6. Try **Users > Bulk create**, download the template and look at the required columns. You do not need to upload it.
7. Clean up: delete both users and the groups (`az ad user delete --id <upn>`, `az ad group delete --group sg-network-admins`), then open **Deleted users** and permanently delete them. This lab creates no resource group and no billable resource.

## Key takeaways

- Manage the tenant in the Entra admin center, with `az ad`, or with Microsoft Graph PowerShell (AzureAD and MSOnline are retired); directory tasks need Entra roles such as User Administrator, not Azure roles.
- Deleted users restore for 30 days. Bulk create (Name, User name, Initial password) sends no email; Bulk invite sends B2B invitations.
- Security groups hold users, devices, service principals and groups; Microsoft 365 groups hold users only. Role-assignable groups are fixed at creation and always Assigned.
- Dynamic membership needs P1 per member user, targets users or devices but not both, and blocks manual changes.
- Administrative units scope Entra roles; scoped admins need P1, and adding a group does not add its members.
