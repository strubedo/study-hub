## What is licensed and what is not

Two billing systems meet in the same tenant, and the exam expects you to keep them apart:

- **Azure resources** (VMs, storage, networks) are paid for through the **subscription**. Nobody needs a per-user license to be granted an Azure role or to use a VM.
- **Per-user products** such as Microsoft 365 E3, Microsoft Entra ID P1 or P2, Intune or Enterprise Mobility + Security are bought as a number of **licenses** in the tenant and then **assigned to users**. A feature that "requires Microsoft Entra ID P1" usually means each user who benefits needs a P1 license (or a bundle that includes P1, such as Microsoft 365 E3 or E5 or Microsoft 365 Business Premium).

Some premium Entra features met in this domain, with the license Microsoft Learn lists for each:

| Feature | License needed |
|---|---|
| Dynamic membership groups | Microsoft Entra ID P1 for each unique user member |
| Administrative unit scoped role holders | P1 for each scoped administrator |
| SSPR for cloud users (reset a forgotten password) | Microsoft 365 Business Standard or higher, or Microsoft Entra ID P1 or P2 |
| SSPR with on-premises password writeback | Microsoft Entra ID P1 or P2, or Microsoft 365 Business Premium |
| Conditional Access | P1 |
| Privileged Identity Management, ID Protection risk policies | P2 |
| Custom Microsoft Entra roles | P1 for each user with a custom role assignment |

A tenant shows its purchased products and how many licenses are assigned and available. A license only does something when it is assigned.

## Where you assign licenses

Microsoft now documents license assignment for users and groups in the **Microsoft 365 admin center**: **Billing > Licenses** (by product), or **Users > Active users > select a user > Licenses and apps**. The Microsoft Entra licensing page states that user and group license assignments are managed there. You may still find a **Licenses** blade in the Microsoft Entra admin center (under **Entra ID > Billing > Licenses**) in some tenants; treat it as the same data.

> **Real world:** Older AZ-104 material describes license assignment entirely in the Azure portal under Azure Active Directory. The task is the same, only the console moved. Read the question for the action being tested (assign to a group, fix usage location), not the blade name.

### Direct assignment

Assigning a product to one user at a time. Simple and immediate: if it fails (no licenses left, usage location missing) you see the error right away. It does not scale, and it leaves licenses behind when people change jobs.

### Group-based licensing

You assign one or more products to a **group**; every member gets them, new members get them automatically and members who leave lose them. Points to know:

- Works with **security groups** and **Microsoft 365 groups**, including **dynamic** groups. Combine a dynamic group (for example all users with `department -eq "Sales"`) with group-based licensing and licensing follows HR data with no manual work.
- **Nested groups are not supported**: only the direct members of the licensed group receive licenses.
- You can turn individual service plans off per group assignment (for example, assign Microsoft 365 E3 without Yammer or Sway).
- Errors are **not shown at assignment time**. Processing happens in the background, and failures are recorded on the user and shown later on the product's **Errors & issues** tab. After fixing the cause, **Reprocess** the assignment.
- A user can have the same product from a direct assignment and one or more groups; Microsoft counts it once. An inherited license cannot be removed from the user's page; remove the user from the group (or remove the product from the group).
- When moving a user between two licensed groups, **add the user to the new group first**, confirm the license, then remove them from the old one, otherwise they may be briefly unlicensed.

> **Watch out:** Older documentation stated that group-based licensing itself requires Microsoft Entra ID P1 (or a product that includes it, such as Microsoft 365 E3). The current Microsoft Learn pages describing group-based licensing in the Microsoft 365 admin center do not state a license prerequisite. If a question says group-based licensing requires P1, it follows the older wording; check the current Microsoft Entra licensing page before you rely on either.

## Usage location

Some Microsoft services are not offered in every country, so a license cannot be assigned to a user until the user's **Usage location** (a two-letter country code such as `US` or `GB`) is set.

- **Direct assignment** to a user with no usage location fails.
- **Group-based licensing** uses the **tenant's location** for members with no usage location, and fails for a member whose usage location is set to a country where a product is not available (error: *usage location isn't allowed*).
- Set it on the user: **Entra ID > Users > user > Properties > Edit** (Settings section) or in the Microsoft 365 admin center, or with `Update-MgUser -UserId <upn> -UsageLocation 'US'`.

## License assignment errors

| Error | Cause | Fix |
|---|---|---|
| Not enough licenses | More members than purchased licenses | Buy more, remove unused direct assignments, or free licenses elsewhere |
| Conflicting service plans | A plan in one product cannot coexist with a plan in another product the user already has (for example two different Exchange Online plans) | Disable one of the conflicting plans in the group assignment or remove the redundant direct license |
| Other products depend on this license | Removing a plan another product needs | Remove the dependent product first |
| Usage location isn't allowed | Missing or unsupported country | Set a valid usage location |
| Duplicate proxy addresses | Exchange Online cannot provision a mailbox | Fix the duplicate address, then reprocess |

> **Exam tip:** "Some users in the group did not receive the license and the others did" is almost always one of: no licenses left, a service plan conflict with something directly assigned, or the user's usage location. "None of the nested group's users received it" is the nested-groups limitation.

## Command line

Microsoft Graph PowerShell is the supported way to script license work. First find the SKU ID of the product:

```powershell
Connect-MgGraph -Scopes "User.ReadWrite.All","Organization.Read.All","Group.ReadWrite.All"
Get-MgSubscribedSku | Select-Object SkuPartNumber, SkuId, ConsumedUnits
$sku = Get-MgSubscribedSku | Where-Object SkuPartNumber -eq 'ENTERPRISEPACK'

# Direct assignment: set usage location first
Update-MgUser -UserId 'ben@contoso.com' -UsageLocation 'US'
Set-MgUserLicense -UserId 'ben@contoso.com' -AddLicenses @{SkuId = $sku.SkuId} -RemoveLicenses @()

# Group-based assignment
$grp = Get-MgGroup -Filter "displayName eq 'lic-m365-e3'"
Set-MgGroupLicense -GroupId $grp.Id -AddLicenses @{SkuId = $sku.SkuId} -RemoveLicenses @()
```

`Set-MgUserLicense` needs both `-AddLicenses` and `-RemoveLicenses` even when one is empty. The SKU part number (`ENTERPRISEPACK` is Office 365 E3) differs from the product's friendly name; always look it up with `Get-MgSubscribedSku` rather than guessing.

The Azure CLI has no dedicated license command. You can call the Microsoft Graph API with `az rest`, which signs the request with your Cloud Shell token:

```bash
az rest --method patch \
  --url "https://graph.microsoft.com/v1.0/users/ben@contoso.com" \
  --body '{"usageLocation":"US"}'
az rest --method post \
  --url "https://graph.microsoft.com/v1.0/users/ben@contoso.com/assignLicense" \
  --body '{"addLicenses":[{"skuId":"00000000-0000-0000-0000-000000000000"}],"removeLicenses":[]}'
```

Replace the zero GUID with your real SKU ID from `Get-MgSubscribedSku` or `az rest --url https://graph.microsoft.com/v1.0/subscribedSkus`.

## Try it yourself

Cost: nothing extra, but you need at least one per-user product in the tenant. A personal Azure free account has none; a Microsoft 365 developer or trial tenant does. If you have no licenses, do steps 1 and 2 only.

1. In the Microsoft 365 admin center open **Billing > Licenses** and note which products exist and how many are available.
2. Create a test user **without** a usage location. Try to assign a license directly and read the error. Set **Usage location** and try again.
3. Create a security group `lic-test`, assign one product to it under **Billing > Licenses > (product) > Groups > Assign licenses**, and add the test user. Watch the license appear on the user as *inherited from group*.
4. From Cloud Shell (PowerShell) run `Get-MgUserLicenseDetail -UserId <upn>` to see the assigned SKUs.
5. Clean up: remove the product from the group, delete the group and the user, and permanently delete the user from **Deleted users** so the license returns to the pool. No Azure resources or resource group are created.

## Key takeaways

- Azure resources are billed per subscription; per-user products such as Microsoft Entra ID P1 or P2 and Microsoft 365 are licenses assigned to users.
- Microsoft documents user and group license assignment in the Microsoft 365 admin center (**Billing > Licenses**).
- Direct assignment shows errors immediately; group-based licensing processes in the background and surfaces errors later on **Errors & issues**.
- Group-based licensing ignores nested groups; combine it with dynamic groups for automatic licensing.
- A user needs a usage location before a direct license assignment; group licensing falls back to the tenant location.
- Common failures: not enough licenses, conflicting service plans, missing or unsupported usage location.
- Script licenses with Microsoft Graph PowerShell (`Get-MgSubscribedSku`, `Set-MgUserLicense`, `Set-MgGroupLicense`) or Graph calls through `az rest`.
