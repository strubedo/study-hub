## Peering in network-engineer terms

Virtual network peering joins two VNets so that their address spaces become mutually reachable over the Microsoft backbone. There is no tunnel, no gateway, no encryption and no bandwidth cap beyond each VM's own limit; within a region the latency is the same as inside one VNet. Azure simply injects a **system route** for each address range of the remote VNet into every subnet, with next hop type **Virtual network peering**.

| Type | Meaning |
|---|---|
| **Regional (local) peering** | Both VNets in the same region |
| **Global peering** | VNets in different regions of the same cloud (you can't peer Azure public to Azure operated by 21Vianet, for example) |

Both types support gateway transit. Global peering has one extra constraint: resources can't reach the frontend of a **Basic** load balancer (retired SKU) across a global peering; Standard load balancers work over both.

## The rules the exam tests

1. **Non-overlapping address spaces.** You can't peer VNets whose ranges overlap, and you can't later add an overlapping range.
2. **Two peering links.** A peering is created on **each** VNet. After the first link the status is **Initiated**; when the second link exists both show **Connected**. Traffic doesn't flow until both are Connected. (The portal creates both links in one dialog when you have rights on both sides.)
3. **Not transitive.** If VNet1 peers with VNet2 and VNet2 with VNet3, VNet1 can't reach VNet3. Either peer VNet1 with VNet3 directly or route through an NVA (or Azure Firewall) in the hub with UDRs.
4. **Cross-subscription and cross-tenant** peering is supported. You need rights on both VNets (Network Contributor or a custom role with the peering actions); cross-tenant, the portal asks you to authenticate to the other directory.
5. **You can't move** a VNet to another resource group or subscription while it is peered: delete the peering, move, re-create.
6. **Name resolution doesn't follow peering.** Azure-provided DNS doesn't resolve names in the peered VNet; use a private DNS zone linked to both, or your own DNS servers.
7. When VNets are connected by both peering and a VPN gateway connection, traffic uses the **peering**.

## Peering settings

Each link has four settings. In the portal they appear twice, once for each direction ("remote virtual network peering settings" and "local virtual network peering settings").

| Portal wording (Learn) | CLI parameter | Default in the portal | What it does |
|---|---|---|---|
| Allow the peered VNet to access *this* VNet | `--allow-vnet-access` | Selected | Lets traffic from the remote address space in. Clearing it blocks the peering without deleting it. The VirtualNetwork service tag then no longer includes the remote space. |
| Allow *this* VNet to receive forwarded traffic from the peered VNet | `--allow-forwarded-traffic` | Not selected | Accept packets that originated **outside** the peered VNet but were forwarded by something in it (an NVA, for example). Needed for hub-and-spoke through an NVA. |
| Allow gateway or route server in *this* VNet to forward traffic to the peered VNet | `--allow-gateway-transit` | Not selected | Set on the **hub** side; the hub must have a VPN/ExpressRoute gateway or Route Server. |
| Enable *this* VNet to use the peered VNet's remote gateway or route server | `--use-remote-gateways` | Not selected | Set on the **spoke** side; requires the hub to allow gateway transit. A VNet that uses a remote gateway can't have its own gateway, and only one of its peerings can use remote gateways. |

> **Watch out:** The current CLI reference lists `--allow-vnet-access` with a default of **False**, while the portal pre-selects it. Always pass `--allow-vnet-access` explicitly in scripts, as Learn's own examples do. In PowerShell the switch is the opposite: access is on unless you add `-BlockVirtualNetworkAccess`.

## Hub and spoke

The standard pattern: a **hub** VNet holds shared services (VPN or ExpressRoute gateway, Azure Firewall or a third-party NVA, Bastion, DNS), and each **spoke** peers only with the hub.

- **Spoke to on-premises through the hub gateway**: hub link `--allow-gateway-transit`, spoke link `--use-remote-gateways`. The spoke then learns the on-premises prefixes, and the hub gateway advertises the spoke ranges to on-premises.
- **Spoke to spoke**: peering is non-transitive, so give each spoke subnet a UDR for the other spoke's range (or 0.0.0.0/0) with next hop **Virtual appliance** = the firewall's private IP. Enable **IP forwarding** on the NVA NIC, and **allow forwarded traffic** on each **spoke's** link to the hub (the setting on a VNet's own link decides whether that VNet accepts packets that a device in the peered VNet forwarded from elsewhere). Learn's hub designs simply enable it in both directions.
- At scale, Azure Virtual Network Manager can build hub-and-spoke or mesh connectivity configurations for you.

## Resizing the address space of a peered VNet

You can add, remove or change address ranges on a peered VNet **without downtime**. Afterwards each remote peering must be **synced** so the other side learns the new prefixes. Learn lists three actions that require a sync: modifying the prefix of an existing range (for example 10.1.0.0/16 to 10.1.0.0/18), adding a range, and deleting a range. Learn recommends syncing after **each** resize rather than batching several resizes, and notes resizing is supported cross-tenant. The portal shows the peering as needing a sync; select it and choose **Sync**.

```bash
az network vnet update -g rg-net-prod -n vnet-spoke1 --address-prefixes 10.21.0.0/16 10.121.0.0/16
az network vnet peering sync -g rg-net-prod --vnet-name vnet-spoke1 -n spoke1-to-hub
az network vnet peering sync -g rg-net-prod --vnet-name vnet-hub -n hub-to-spoke1
```

```powershell
Sync-AzVirtualNetworkPeering -ResourceGroupName rg-net-prod -VirtualNetworkName vnet-hub -Name hub-to-spoke1
```

## Create a peering

**Portal**: open vnet-hub > **Settings** > **Peerings** > **+ Add**. Fill in the remote VNet (or tick **I know my resource ID** if you can't browse the other subscription), both link names and both sets of settings, then **Add**.

```bash
# Link 1: hub to spoke (allow gateway transit from the hub)
az network vnet peering create -g rg-net-prod -n hub-to-spoke1 \
  --vnet-name vnet-hub --remote-vnet vnet-spoke1 \
  --allow-vnet-access --allow-forwarded-traffic --allow-gateway-transit

# Link 2: spoke to hub (use the hub's gateway)
az network vnet peering create -g rg-net-prod -n spoke1-to-hub \
  --vnet-name vnet-spoke1 --remote-vnet vnet-hub \
  --allow-vnet-access --allow-forwarded-traffic --use-remote-gateways

az network vnet peering list -g rg-net-prod --vnet-name vnet-hub -o table
```

For a VNet in another subscription or resource group, pass its full resource ID to `--remote-vnet`.

```powershell
$hub    = Get-AzVirtualNetwork -Name vnet-hub -ResourceGroupName rg-net-prod
$spoke1 = Get-AzVirtualNetwork -Name vnet-spoke1 -ResourceGroupName rg-net-prod
Add-AzVirtualNetworkPeering -Name hub-to-spoke1 -VirtualNetwork $hub `
  -RemoteVirtualNetworkId $spoke1.Id -AllowForwardedTraffic -AllowGatewayTransit
Add-AzVirtualNetworkPeering -Name spoke1-to-hub -VirtualNetwork $spoke1 `
  -RemoteVirtualNetworkId $hub.Id -AllowForwardedTraffic -UseRemoteGateways
```

`--use-remote-gateways` fails if the hub has no gateway yet; in a lab without a gateway, leave both gateway settings off.

## Reading a peering exhibit

When an exam item shows a table of VNets and peerings, check in this order:

1. Do any address spaces overlap? Then that peering can't exist.
2. Is there a link in **both** directions, and is each **Connected**?
3. Is the destination one hop away? If not, is there an NVA with UDRs and forwarded traffic allowed?
4. For on-premises reachability from a spoke: hub allows gateway transit, spoke uses remote gateways.
5. Does the question ask about names? Peering doesn't carry Azure-provided DNS.

## Try it yourself

Azure Cloud Shell (Bash) in any browser. Cost: peering bills a small per-GB charge for traffic that crosses it; this lab sends almost none and creates no VMs, so expect **no meaningful cost**.

```bash
rg=rg-lab-d4peer; az group create -n $rg -l eastus
az network vnet create -g $rg -n vnet-hub    --address-prefixes 10.60.0.0/16 --subnet-name snet-shared --subnet-prefixes 10.60.1.0/24
az network vnet create -g $rg -n vnet-spoke1 --address-prefixes 10.61.0.0/16 --subnet-name snet-app --subnet-prefixes 10.61.1.0/24
az network vnet create -g $rg -n vnet-spoke2 --address-prefixes 10.62.0.0/16 --subnet-name snet-app --subnet-prefixes 10.62.1.0/24
az network vnet peering create -g $rg -n hub-to-spoke1 --vnet-name vnet-hub --remote-vnet vnet-spoke1 --allow-vnet-access
az network vnet peering show -g $rg -n hub-to-spoke1 --vnet-name vnet-hub --query peeringState   # Initiated
az network vnet peering create -g $rg -n spoke1-to-hub --vnet-name vnet-spoke1 --remote-vnet vnet-hub --allow-vnet-access
az network vnet peering show -g $rg -n hub-to-spoke1 --vnet-name vnet-hub --query peeringState   # Connected
```

1. Peer the hub with spoke2 the same way. Spoke1 and spoke2 still have no path to each other.
2. Try to create a VNet `vnet-overlap` with 10.61.128.0/17 and peer it with spoke1; read the overlap error.
3. Add 10.161.0.0/16 to spoke1, look at the hub-to-spoke1 peering in the portal (its sync status should show that the remote address space changed; the exact label is documentation-based), then run `az network vnet peering sync` on both links.
4. Clean up: `az group delete -n $rg --yes --no-wait`

## Key takeaways

- Peering uses the Microsoft backbone with no gateway; regional or global; across subscriptions and tenants.
- Address spaces must not overlap; a peering needs a link on each side and is up only when both are Connected.
- Peering is **not transitive**: use direct peerings or a hub NVA with UDRs, IP forwarding and allow forwarded traffic.
- Gateway transit: hub `--allow-gateway-transit`, spoke `--use-remote-gateways`; the spoke can't have its own gateway.
- After any address space change on a peered VNet, **sync** each peering (`az network vnet peering sync`, `Sync-AzVirtualNetworkPeering`).
- Azure-provided DNS doesn't cross peerings; use private DNS zones or custom DNS.
