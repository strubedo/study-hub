## What a private endpoint is

A **private endpoint** is a network interface, created and managed by Azure, with a **private IP from your subnet**, that is wired through **Azure Private Link** to **one** specific resource (one storage account's blob service, one SQL logical server, one key vault) or to a customer's Private Link service. To clients it looks like the PaaS resource has moved into your VNet:

- Reachable from the VNet, **peered VNets**, and **on-premises** over VPN or ExpressRoute private peering, because it's just a private IP.
- Works when the resource's **public network access is disabled**.
- Maps to one resource, not to the whole service, so it also closes the data-exfiltration gap that service endpoints leave open.
- Billed per hour per endpoint plus per GB processed (service endpoints are free).

Facts from Learn's overview: the NIC is **read-only** and lives for the endpoint's lifetime; its IP is assigned **dynamically** from the subnet by default (a static IP can be specified for most services) and doesn't change for the lifetime of the endpoint; the endpoint must be in the **same region and subscription as its VNet**, but the target resource can be in **another region**.

## Target sub-resource (group ID)

When you create the endpoint you choose the **target sub-resource**, called the **group ID** in CLI and PowerShell. One endpoint serves one sub-resource:

| Resource type | Sub-resources (group IDs) |
|---|---|
| Storage account `Microsoft.Storage/storageAccounts` | `blob`, `file`, `queue`, `table`, `web`, `dfs` (and `_secondary` variants) |
| Azure SQL Database `Microsoft.Sql/servers` | `sqlServer` |
| Key Vault `Microsoft.KeyVault/vaults` | `vault` |
| App Service `Microsoft.Web/sites` | `sites` |
| Cosmos DB `Microsoft.DocumentDB/databaseAccounts` | `Sql`, `MongoDB`, `Cassandra`, `Gremlin`, `Table`, ... |

A storage account that clients use for blobs **and** files needs **two** endpoints (`blob` and `file`), and two private DNS zones.

## DNS: the part that breaks

Clients keep using the normal name, for example `stcontosodata01.blob.core.windows.net`. When a private endpoint is created, Azure's **public** DNS answers with a **CNAME** into a `privatelink` subdomain:

```text
stcontosodata01.blob.core.windows.net
   CNAME  stcontosodata01.privatelink.blob.core.windows.net
```

What happens next depends on who resolves it:

- **Inside a VNet linked to the private DNS zone `privatelink.blob.core.windows.net`** (using Azure DNS, 168.63.129.16): the zone holds an A record `stcontosodata01` > **10.10.5.4**. The client connects privately.
- **On the internet**: public DNS follows the CNAME on to the public endpoint IP. (If public access is disabled, the connection is refused, but resolution still returns the public IP.)

Recommended zone names come from Learn's table, for example `privatelink.blob.core.windows.net`, `privatelink.file.core.windows.net`, `privatelink.database.windows.net` (SQL), `privatelink.vaultcore.azure.net` (Key Vault), `privatelink.azurewebsites.net` (App Service). Learn warns that automatic DNS configuration only works with the recommended names, and not to override the public zone (`blob.core.windows.net`) itself.

The simplest wiring is a **private DNS zone group** on the endpoint: Azure then creates and maintains the A record in the zone for you. In the portal, the **DNS** tab of the private endpoint wizard ("Integrate with private DNS zone: Yes") does this.

### DNS from peered VNets and on-premises

- **Peered VNets**: link the same private DNS zone to each VNet whose clients use Azure DNS (or point them at a central DNS forwarder). Peering doesn't share DNS.
- **On-premises**: on-premises DNS can't query 168.63.129.16 directly (it's reachable only from inside Azure). Deploy something in a VNet linked to the zone that can: an **Azure DNS Private Resolver inbound endpoint**, or a DNS forwarder VM, or Azure Firewall DNS proxy. Then add an on-premises **conditional forwarder for the public zone name** (`blob.core.windows.net`, `database.windows.net`), not the `privatelink` name, pointing to that inbound endpoint. Learn is explicit that the conditional forwarder targets the public DNS zone.

> **Exam tip:** "VMs connect to the storage account's public IP even though a private endpoint exists" = DNS. Either the private DNS zone isn't linked to the client's VNet, the A record is missing, or the client uses a custom DNS server that doesn't forward to Azure DNS.

## Approval workflow

- **Automatic**: if you have the right permission on the target (`Microsoft.<Provider>/<type>/privateEndpointConnectionsApproval/action`, included in Owner/Contributor of the resource), the connection is approved at creation.
- **Manual**: without that permission (or for another tenant's resource or a Private Link service by alias), the connection is created as **Pending**; the resource owner approves or rejects it under the resource's **Networking** > **Private endpoint connections**. States: **Pending**, **Approved**, **Rejected**, **Disconnected**. Only **Approved** endpoints pass traffic.

## Network policies for private endpoints

By default, NSGs and UDRs **don't apply** to private endpoints in a subnet (network policies are **disabled** for private endpoints). To have NSG rules and route tables apply to private endpoint traffic, enable **private endpoint network policies** on the subnet: `NetworkSecurityGroupEnabled`, `RouteTableEnabled` or both (`Enabled`). This setting only affects private endpoints; other resources in the subnet are always filtered.

A private endpoint injects a **/32** route for its IP. With route table policies enabled, Learn says a UDR overrides that only if its prefix is the VNet address space or more specific: a 0.0.0.0/0 UDR does **not** catch private endpoint traffic, longest prefix wins. When routing private endpoint traffic through an NVA, Learn recommends SNAT on the NVA for symmetric return traffic. Effective routes and effective security rules aren't displayed for a private endpoint NIC.

## Create a private endpoint

**Portal**: resource (for example the storage account) > **Networking** > **Private endpoint connections** > **+ Private endpoint**: name, region; **Resource** tab: target sub-resource `blob`; **Virtual Network** tab: VNet and subnet, dynamic or static IP, optional ASG; **DNS** tab: integrate with private DNS zone. Then set **Public network access** to **Disabled** if required.

```bash
said=$(az storage account show -g rg-data-prod -n stcontosodata01 --query id -o tsv)
az network private-endpoint create -g rg-net-prod -n pe-stcontosodata01-blob \
  --vnet-name vnet-hub --subnet snet-pe \
  --private-connection-resource-id $said --group-id blob --connection-name pec-blob
az network private-dns zone create -g rg-net-prod -n privatelink.blob.core.windows.net
az network private-dns link vnet create -g rg-net-prod -z privatelink.blob.core.windows.net \
  -n link-vnet-hub -v vnet-hub --registration-enabled false
az network private-endpoint dns-zone-group create -g rg-net-prod --endpoint-name pe-stcontosodata01-blob \
  -n default --private-dns-zone privatelink.blob.core.windows.net --zone-name blob
az network vnet subnet update -g rg-net-prod --vnet-name vnet-hub -n snet-pe --private-endpoint-network-policies Enabled
```

```powershell
$sa = Get-AzStorageAccount -ResourceGroupName rg-data-prod -Name stcontosodata01
$conn = New-AzPrivateLinkServiceConnection -Name pec-blob -PrivateLinkServiceId $sa.Id -GroupId blob
$vnet = Get-AzVirtualNetwork -Name vnet-hub -ResourceGroupName rg-net-prod
$subnet = $vnet.Subnets | Where-Object Name -eq snet-pe
New-AzPrivateEndpoint -Name pe-stcontosodata01-blob -ResourceGroupName rg-net-prod -Location eastus `
  -Subnet $subnet -PrivateLinkServiceConnection $conn
```

## Service endpoints vs private endpoints

| | Service endpoint | Private endpoint |
|---|---|---|
| Where the service is reached | Its **public** IP, over the backbone | A **private IP in your subnet** |
| Scope | Subnet to the **whole service** (narrow with the resource firewall or endpoint policies) | **One resource** and sub-resource |
| On-premises and peered-VNet clients | Not covered | Covered (with DNS) |
| Public access can be disabled | No (it relies on the public endpoint) | Yes |
| DNS changes | None | Private DNS zone (privatelink) needed |
| Cost | Free | Hourly + per GB |
| Configure on | Subnet + resource firewall VNet rule | Endpoint in a subnet + DNS (+ approval) |

## Try it yourself

Azure Cloud Shell (Bash), any browser. Cost: one private endpoint and one private DNS zone for under an hour; a few US cents. No VM.

```bash
rg=rg-lab-d4pe; sa=stlabpe$RANDOM; az group create -n $rg -l eastus
az network vnet create -g $rg -n vnet-lab --address-prefixes 10.97.0.0/16 --subnet-name snet-pe --subnet-prefixes 10.97.5.0/24
az storage account create -g $rg -n $sa --sku Standard_LRS --kind StorageV2 --public-network-access Disabled
said=$(az storage account show -g $rg -n $sa --query id -o tsv)
az network private-endpoint create -g $rg -n pe-lab --vnet-name vnet-lab --subnet snet-pe \
  --private-connection-resource-id $said --group-id blob --connection-name pec-lab
az network private-dns zone create -g $rg -n privatelink.blob.core.windows.net
az network private-dns link vnet create -g $rg -z privatelink.blob.core.windows.net -n link-lab -v vnet-lab -e false
az network private-endpoint dns-zone-group create -g $rg --endpoint-name pe-lab -n default \
  --private-dns-zone privatelink.blob.core.windows.net --zone-name blob
az network private-dns record-set a list -g $rg -z privatelink.blob.core.windows.net -o table
```

1. Confirm the A record for your account name points to an address in 10.97.5.0/24 (the first free one is normally 10.97.5.4).
2. In the portal, open the storage account > **Networking** > **Private endpoint connections**: the state is **Approved** because you own the account.
3. Clean up: `az group delete -n $rg --yes --no-wait`

## Key takeaways

- A private endpoint is a read-only NIC with a private IP from your subnet, mapped through Private Link to **one** resource sub-resource (group ID such as `blob`, `sqlServer`, `vault`).
- Public DNS returns a CNAME to `<name>.privatelink.<suffix>`; a linked private DNS zone of that name returns the private A record.
- On-premises: conditional forwarder for the **public** zone name to a resolver inside Azure (Private Resolver inbound endpoint or forwarder VM).
- Connections are auto-approved with permission, otherwise Pending until the owner approves.
- NSG and UDR support for private endpoints needs **private endpoint network policies** enabled on the subnet; 0.0.0.0/0 doesn't override the /32 route.
- Private endpoint: private, per resource, on-premises friendly, paid. Service endpoint: public endpoint, per subnet, free.
