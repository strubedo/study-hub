## What an NSG is, in firewall terms

A network security group is a **stateful, distributed 5-tuple ACL** enforced by the Azure host for every NIC it applies to. There is no appliance, no zone, no NAT and no application inspection. If you think "Palo Alto security policy without App-ID, applied per interface by the hypervisor", you're close. Stateful means you write the rule for the direction the connection is **initiated**; return traffic for an allowed flow is permitted automatically, and removing a rule doesn't break flows already established (Learn: rule changes apply to new connections).

An NSG can be associated with **subnets** and **NICs** (each subnet or NIC has at most one NSG; one NSG can be reused on many subnets and NICs; Learn's subnet settings page says the NSG must be in the same subscription and location as the virtual network).

## Rule properties

| Property | Details from Learn |
|---|---|
| Name | Unique in the NSG, up to 80 characters |
| **Priority** | **100 to 4096**. Lower number = processed first; processing **stops at the first match**. Two rules can't share a priority and direction. |
| Source / destination | Any, an IP, a CIDR, a **service tag** or an **application security group**. Use the resource's **private** IP. |
| Protocol | TCP, UDP, ICMP, ESP, AH or Any (ESP and AH only through templates/CLI, not the portal) |
| Port ranges | Single port, range (10000-10005) or a comma list; with Any for ICMP |
| Direction | Inbound or Outbound |
| Action | Allow or Deny |

**Augmented rules**: one rule can hold several IPs/CIDRs and several port ranges, which keeps rule counts down. Service tags and ASGs do the same job by name.

> **Watch out:** NSG limits change; Learn's networking limits table currently lists 5,000 NSGs per subscription and 2,000 rules per NSG for Resource Manager. Don't memorise them for the exam; know where to find them.

### Default rules

Every NSG has six rules you can't delete, at priorities above 4096 so your rules always win:

| Direction | Priority | Name | Source | Destination | Access |
|---|---|---|---|---|---|
| Inbound | 65000 | AllowVNetInBound | VirtualNetwork | VirtualNetwork | Allow |
| Inbound | 65001 | AllowAzureLoadBalancerInBound | AzureLoadBalancer | Any | Allow |
| Inbound | 65500 | DenyAllInBound | Any | Any | Deny |
| Outbound | 65000 | AllowVnetOutBound | VirtualNetwork | VirtualNetwork | Allow |
| Outbound | 65001 | AllowInternetOutBound | Any | Internet | Allow |
| Outbound | 65500 | DenyAllOutBound | Any | Any | Deny |

All ports, all protocols. The practical effect: inside the VNet (and peered VNets, and on-premises over a gateway) everything is allowed, load balancer probes are allowed, inbound from the internet is denied, outbound to the internet is allowed.

## Service tags you must know

| Tag | Represents |
|---|---|
| **VirtualNetwork** | The VNet address space, **peered** VNets, VNets connected through a gateway, **on-premises** ranges known to the gateway, the host virtual IP 168.63.129.16 and address prefixes used in UDRs. Much wider than "my VNet". |
| **AzureLoadBalancer** | The Azure infrastructure load balancer, which Learn translates to the host IP **168.63.129.16** where health probes originate. Probe traffic only, not client traffic through the load balancer. |
| **Internet** | Address space outside the VNet reachable by the public internet, **including Azure-owned public IPs** |
| **Storage**, **Sql**, **AzureKeyVault**, **AzureMonitor**, **AzureCloud** ... | Public prefixes of a service. Many can be scoped to a region: `Storage.EastUS`, `Sql.WestEurope` |
| **GatewayManager** | Azure control plane for gateways and Bastion; used in the AzureBastionSubnet rule set |

A classic pattern: deny outbound to Internet at priority 4000, allow outbound to `Storage.EastUS` on 443 at priority 200. Because service tags cover public prefixes and Microsoft maintains them, you never edit IP lists.

## Application security groups

An ASG is a named group of **NIC IP configurations**. You put NICs in ASGs (`asg-web`, `asg-sql`) and write rules such as "allow asg-web to asg-sql on 1433" instead of listing IPs. Membership follows the VM, so scaling out needs no rule changes.

Constraints from Learn:

- All NICs in an ASG must be in the **same virtual network** as the first NIC added to it.
- If a rule uses ASGs as **both** source and destination, both ASGs' NICs must be in the same VNet.
- A NIC can be a member of several ASGs (Learn's limits page: up to 20 per IP configuration).
- ASGs don't filter anything by themselves; they are only names that NSG rules reference.

## Where to associate and in which order rules run

Learn's evaluation order:

- **Inbound**: the **subnet** NSG first, then the **NIC** NSG.
- **Outbound**: the **NIC** NSG first, then the **subnet** NSG.
- Traffic must be allowed by **every** NSG on its path. A deny in the first NSG stops evaluation; the second never sees the packet.
- **Intra-subnet** traffic is evaluated the same way: VM-to-VM traffic in one subnet passes the subnet NSG (outbound from the source, inbound to the destination), so a subnet-level "deny all" breaks it.
- Learn's tip: prefer associating an NSG with the subnet **or** the NIC, not both, unless you need it, because overlapping rules at two levels cause filtering problems that are hard to troubleshoot (the classic "I opened the port and it's still blocked").

NSG rules see traffic **after** inbound public-to-private translation and **before** outbound translation, so always use private IPs and the backend port. For traffic through a load balancer, the source is the original client, not the load balancer.

Platform traffic to 168.63.129.16 and 169.254.169.254 (DHCP, DNS, IMDS, health) isn't filtered by NSGs unless you target it with service tags (Learn names `AzurePlatformDNS` for blocking Azure DNS).

## Flow logs

NSG flow logs **retire on September 30, 2027** and Learn says new NSG flow logs can no longer be created; migrate to **virtual network flow logs** (see the troubleshooting lesson).

## Create an NSG, rules and ASGs

**Portal**: **Network security groups** > **+ Create**. Then **Settings** > **Inbound security rules** > **+ Add**, choosing Source (Any, IP addresses, My IP address, Service Tag, Application security group), ports, protocol, action, priority. Associate under **Settings** > **Subnets** or **Network interfaces**. ASGs: **Application security groups** > **+ Create**, then on the VM: **Networking** > **Application security groups** > **Add application security groups**.

```bash
az network asg create -g rg-app-prod -n asg-web
az network asg create -g rg-app-prod -n asg-sql
az network nsg create -g rg-app-prod -n nsg-app
az network nsg rule create -g rg-app-prod --nsg-name nsg-app -n allow-https-in --priority 100 \
  --direction Inbound --access Allow --protocol Tcp \
  --source-address-prefixes Internet --destination-asgs asg-web --destination-port-ranges 443
az network nsg rule create -g rg-app-prod --nsg-name nsg-app -n allow-web-to-sql --priority 110 \
  --direction Inbound --access Allow --protocol Tcp \
  --source-asgs asg-web --destination-asgs asg-sql --destination-port-ranges 1433
az network vnet subnet update -g rg-app-prod --vnet-name vnet-app -n snet-app --nsg nsg-app
az network nic ip-config update -g rg-app-prod --nic-name nic-web-01 -n ipconfig1 --asgs asg-web
```

> **Watch out:** `az network nsg rule create` defaults to Inbound, Allow, protocol `*`, and destination port **80** if you omit `--destination-port-ranges`. Always pass every field.

```powershell
$web = New-AzApplicationSecurityGroup -ResourceGroupName rg-app-prod -Name asg-web -Location eastus
$rule = New-AzNetworkSecurityRuleConfig -Name allow-https-in -Priority 100 -Direction Inbound -Access Allow `
  -Protocol Tcp -SourceAddressPrefix Internet -SourcePortRange * `
  -DestinationApplicationSecurityGroup $web -DestinationPortRange 443
New-AzNetworkSecurityGroup -Name nsg-app -ResourceGroupName rg-app-prod -Location eastus -SecurityRules $rule
```

## Try it yourself

Azure Cloud Shell (Bash), any browser. Cost: NSGs and ASGs are free; no VMs. **Nothing billed.**

```bash
rg=rg-lab-d4nsg; az group create -n $rg -l eastus
az network nsg create -g $rg -n nsg-lab
az network nsg rule list -g $rg --nsg-name nsg-lab --include-default -o table
az network asg create -g $rg -n asg-web
az network nsg rule create -g $rg --nsg-name nsg-lab -n allow-web --priority 100 --protocol Tcp \
  --source-address-prefixes Internet --destination-asgs asg-web --destination-port-ranges 80 443
az network nsg rule create -g $rg --nsg-name nsg-lab -n dup --priority 100 --protocol Tcp --destination-port-ranges 22
```

1. Read the six default rules and their priorities in the first listing.
2. The last command reuses priority 100 in the same direction: read the error.
3. In the portal, open nsg-lab and look at how the augmented rule shows two ports and an ASG.
4. Clean up: `az group delete -n $rg --yes --no-wait`

## Key takeaways

- NSGs are stateful 5-tuple ACLs on subnets and NICs; priority 100–4096, lowest first, first match wins.
- Defaults: inbound 65000 AllowVNetInBound, 65001 AllowAzureLoadBalancerInBound, 65500 DenyAllInBound; outbound 65000 AllowVnetOutBound, 65001 AllowInternetOutBound, 65500 DenyAllOutBound.
- VirtualNetwork includes peered VNets and on-premises; AzureLoadBalancer is 168.63.129.16 for probes; Internet includes Azure public IPs.
- Inbound: subnet NSG then NIC NSG. Outbound: NIC NSG then subnet NSG. Both must allow.
- ASGs group NICs from **one VNet** and are used as rule source or destination.
- Rules match private IPs and backend ports; NSG flow logs retire September 30, 2027 (use VNet flow logs).
