## The method

Exam items on NSGs give you two rule tables (subnet and NIC), a packet and a direction, and ask whether it gets through and which rule decides. Treat it like reading two ACLs in series on a firewall. Use this procedure every time:

1. **Direction decides the order.** Inbound: **subnet NSG, then NIC NSG**. Outbound: **NIC NSG, then subnet NSG**. If one of the two isn't associated, skip it (no NSG means no filtering at that point).
2. In each NSG, walk the rules for that direction in **ascending priority**, **including the default rules** (65000, 65001, 65500).
3. For each rule, check all five fields: source, source port, destination, destination port, protocol. Service tags and ASGs must contain the actual address or NIC.
4. **First match decides** for that NSG. Deny: the packet is dropped and the second NSG is never evaluated. Allow: move to the next NSG.
5. The packet passes only if **both** NSGs (where present) allow it.
6. For return traffic of an allowed connection, nothing is evaluated: NSGs are stateful.

Remember what NSGs see: private IPs after inbound NAT, the backend port behind a load balancer, and the original client IP as source.

## Worked example 1: inbound from the internet

VM `vm-web-01` (10.1.1.4, NIC in `asg-web`) in subnet `snet-web` 10.1.1.0/24 of `vnet-app` (10.1.0.0/16). It has a Standard public IP 203.0.113.10.

```text
nsg-snet-web (associated with snet-web)
Priority  Name             Port  Protocol  Source          Destination  Action
100       allow-https      443   TCP       Internet        asg-web      Allow
200       allow-mgmt-ssh   22    TCP       198.51.100.0/24 Any          Allow
4000      deny-internet    Any   Any       Internet        Any          Deny
65000     AllowVNetInBound ...  (defaults follow)

nsg-nic-web01 (associated with the NIC of vm-web-01)
Priority  Name             Port  Protocol  Source          Destination  Action
100       deny-ssh         22    TCP       Any             Any          Deny
65000     AllowVNetInBound ...  (defaults follow)
```

**Packet A**: 192.0.2.50:51000 to 203.0.113.10:443 TCP. Translated to destination 10.1.1.4:443 before the NSGs see it.

- Subnet NSG: rule 100 matches (Internet contains 192.0.2.50; asg-web contains the NIC; 443/TCP). **Allow**, go on.
- NIC NSG: rule 100 is port 22, no match. Default 65000 AllowVNetInBound: is 192.0.2.50 in VirtualNetwork? No. 65001 AllowAzureLoadBalancerInBound: source isn't 168.63.129.16. 65500 DenyAllInBound matches. **Deny.**
- Result: **blocked by DenyAllInBound in the NIC NSG.** The fix is an allow rule for 443 in nsg-nic-web01, or removing the NIC NSG.

**Packet B**: 198.51.100.20 to 10.1.1.4:22 TCP (admin over the public IP).

- Subnet NSG: rule 100 is 443, no. Rule 200 matches. Allow.
- NIC NSG: rule 100 deny-ssh matches. **Deny.** The admin is blocked by the NIC NSG even though the subnet NSG allows it.

**Packet C**: 10.1.2.7 (another subnet in the same VNet) to 10.1.1.4:22.

- Subnet NSG: 100 no; 200 no (source isn't 198.51.100.0/24); 4000 deny-internet: is 10.1.2.7 in Internet? No. 65000 AllowVNetInBound: yes, allow.
- NIC NSG: rule 100 deny-ssh matches: **Deny.**

## Worked example 2: outbound

Same VM, outbound to 198.51.100.80:443 TCP.

```text
nsg-nic-web01 outbound
Priority  Name               Port  Protocol  Destination      Action
100       allow-storage      443   TCP       Storage.EastUS   Allow
65000     AllowVnetOutBound
65001     AllowInternetOutBound
65500     DenyAllOutBound

nsg-snet-web outbound
Priority  Name               Port  Protocol  Destination      Action
300       deny-internet-out  Any   Any       Internet         Deny
65000 ...
```

- Outbound starts at the **NIC** NSG: rule 100 matches only Storage.EastUS prefixes; 198.51.100.80 isn't one of them. 65000: not VirtualNetwork. 65001 AllowInternetOutBound: **Allow**.
- Then the **subnet** NSG: rule 300 matches Internet: **Deny**. Blocked by deny-internet-out.

A request from the same VM to a storage account in East US on 443: NIC rule 100 allows; subnet rule 300 matches too, because **the Internet tag includes Azure-owned public IPs**, so it is **denied**. To allow it you need an allow rule for Storage.EastUS at a priority lower than 300 **in the subnet NSG** as well.

> **Exam tip:** The trap in most items is either the wrong evaluation order for the direction, or forgetting that a default rule can be the deciding match. Write down "NSG 1 result, NSG 2 result" before you look at the options.

## Ties, overlaps and odd cases

- Within one NSG, a **deny at 200 beats an allow at 300** for the same traffic, regardless of how specific the allow is. Priority is all that counts, not prefix length.
- A rule whose source is an ASG matches only NICs in that ASG. A packet from an on-premises IP never matches an ASG.
- Load balancer health probes come from 168.63.129.16 (AzureLoadBalancer). A custom "deny all inbound" at priority 4000 blocks probes before 65001 is reached, and every backend shows unhealthy.
- If **no NSG** is associated at either level, Azure doesn't filter the traffic. But a NIC with a **Standard** public IP and no NSG stays closed to inbound traffic from the internet ("secure by default"); you need an NSG that allows it.
- Intra-subnet traffic goes through the subnet NSG twice in effect: outbound rules (from the source NIC's point of view) and inbound rules (destination NIC).

## Effective security rules view

Portal: VM > **Networking** > select the NIC > **Effective security rules** (or Network Watcher > **Effective security rules**, or NIC > **Help** > **Effective security rules**). It needs a **running** VM. It shows the rules from the subnet NSG and the NIC NSG separately and the aggregate, grouped inbound and outbound; selecting a rule shows the prefixes behind a service tag, and you can download a CSV. Learn notes effective rules aren't shown for a **private endpoint** NIC.

```bash
az network nic list-effective-nsg -g rg-web-prod -n nic-web-01
```

```powershell
Get-AzEffectiveNetworkSecurityGroup -NetworkInterfaceName nic-web-01 -ResourceGroupName rg-web-prod
```

To test a single packet instead of reading rules, use **IP flow verify** (TCP/UDP; returns Allow/Deny and the deciding rule name, such as `securityRules/deny-ssh` or `defaultSecurityRules/DenyAllInBound`) or **NSG diagnostics** (also ICMP and service-tag sources, shows each NSG's decision).

```bash
az network watcher test-ip-flow -g rg-web-prod --vm vm-web-01 --direction Inbound \
  --protocol TCP --local 10.1.1.4:22 --remote 198.51.100.20:50000
```

## Try it yourself

Azure Cloud Shell (Bash), any browser. Cost: one Standard_B1s VM for under an hour (a few US cents).

```bash
rg=rg-lab-d4eff; az group create -n $rg -l eastus
az network vnet create -g $rg -n vnet-lab --address-prefixes 10.90.0.0/16 --subnet-name snet-web --subnet-prefixes 10.90.1.0/24
az network nsg create -g $rg -n nsg-subnet
az network nsg rule create -g $rg --nsg-name nsg-subnet -n allow-ssh --priority 200 --protocol Tcp \
  --source-address-prefixes 198.51.100.0/24 --destination-address-prefixes '*' --destination-port-ranges 22
az network vnet subnet update -g $rg --vnet-name vnet-lab -n snet-web --nsg nsg-subnet
az network nsg create -g $rg -n nsg-nic
az network nsg rule create -g $rg --nsg-name nsg-nic -n deny-ssh --priority 100 --access Deny --protocol Tcp \
  --source-address-prefixes '*' --destination-address-prefixes '*' --destination-port-ranges 22
az vm create -g $rg -n vm-lab --image Ubuntu2204 --size Standard_B1s --vnet-name vnet-lab --subnet snet-web \
  --private-ip-address 10.90.1.4 --public-ip-address "" --nsg nsg-nic --admin-username azureuser --generate-ssh-keys
az network watcher test-ip-flow -g $rg --vm vm-lab --direction Inbound --protocol TCP --local 10.90.1.4:22 --remote 198.51.100.20:50000
```

1. Predict the result and the rule name before you run the last command (Deny, `securityRules/deny-ssh`).
2. Delete the NIC rule (`az network nsg rule delete -g $rg --nsg-name nsg-nic -n deny-ssh`) and run it again: now the NIC NSG falls through to `DenyAllInBound` because nothing allows 22 from the internet. Add an allow in nsg-nic to fix it.
3. Open the effective security rules view in the portal and compare.
4. Clean up: `az group delete -n $rg --yes --no-wait`

## Key takeaways

- Inbound: subnet NSG then NIC NSG; outbound: NIC NSG then subnet NSG; the first deny ends evaluation.
- In each NSG, walk rules by priority including 65000, 65001 and 65500; priority wins, not specificity.
- The Internet tag includes Azure public IPs, so a deny-Internet rule also blocks PaaS public endpoints unless a service-tag allow sits above it.
- A custom deny-all above 65001 blocks load balancer probes.
- Effective security rules (running VM) shows both NSGs and the aggregate; IP flow verify names the deciding rule for one packet.
