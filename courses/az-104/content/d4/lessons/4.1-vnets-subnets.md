## What is different about an Azure virtual network

A virtual network (VNet) is a software-defined layer 3 domain. There is no layer 2 you can touch: no VLANs, no ARP you can influence, no broadcast and no multicast. Microsoft Learn is explicit that multicast, broadcast, IP-in-IP and GRE packets are blocked inside a VNet, and that Azure itself provides DHCP to VMs: unicast DHCP (UDP 68 to UDP 67) is intercepted by the platform, so you can't replace Azure's DHCP for VMs in the VNet (Learn now allows a DHCP server VM that serves on-premises clients through a relay agent). Every packet is delivered host to host by the Azure fabric, which is why things like gratuitous ARP failover or VRRP between two VMs don't work the way they do on your switches.

The rules that matter for design and for the exam:

| Property | Azure behaviour |
|---|---|
| Scope | One region, one subscription. A VNet **spans all availability zones** in its region; subnets are not zonal. |
| Address space | One or more CIDR ranges. Learn recommends RFC 1918 and also accepts RFC 6598 (100.64.0.0/10). Public ranges you don't own "might work" but cause side effects. |
| Ranges you can't add | 224.0.0.0/4, 255.255.255.255/32, 127.0.0.0/8, 169.254.0.0/16, 168.63.129.16/32 |
| Subnet sizes | IPv4 smallest **/29**, largest /2. IPv6 subnets must be exactly **/64**. |
| Subnet overlap | Subnets in one VNet can't overlap; VNets you want to connect must not overlap each other. |
| Gateway | There is no router VM. Each subnet's first usable address is the "default gateway", implemented by the host. |

### The five reserved addresses

Azure reserves the first four and the last address of every subnet. For 10.10.1.0/24:

| Address | Used for |
|---|---|
| 10.10.1.0 | Network address |
| 10.10.1.1 | Default gateway |
| 10.10.1.2, 10.10.1.3 | Map the Azure DNS IPs into the VNet space |
| 10.10.1.255 | "Broadcast" (reserved even though broadcast isn't supported) |

So usable hosts = 2^(32 − prefix) − 5. A /29 gives 3 usable addresses, a /28 gives 11, a /27 gives 27, a /26 gives 59, a /24 gives 251. The first VM normally gets .4. Exam items like "how many VMs fit in 10.0.5.0/28" want **11**, not 14.

> **Exam tip:** "Smallest subnet you can create" is /29 (3 usable). "Smallest subnet that supports *service X*" is a different question: see the special subnets table below.

## Special subnet names and sizes

Several Azure services only deploy into a subnet with an exact, case-sensitive name:

| Subnet name | Used by | Size requirement on Learn |
|---|---|---|
| `GatewaySubnet` | VPN Gateway and ExpressRoute gateways | /27 or larger for every gateway SKU except the Basic VPN SKU (the only one that can use /29). Learn suggests going bigger for coexistence and future needs. Learn says NSGs and 0.0.0.0/0 UDRs on it aren't supported, and gateway route propagation must stay enabled. |
| `AzureBastionSubnet` | Azure Bastion (Basic, Standard, Premium) | /26 or larger for deployments since November 2, 2021 |
| `AzureFirewallSubnet` | Azure Firewall | /26 (Learn: "sufficient for all scaling scenarios") |

Nothing else may be deployed into these subnets.

## Adding and changing address ranges

You can add more address ranges to a VNet at any time (portal: VNet > **Settings** > **Address space**). A subnet's range can be changed only if **no resources are deployed in it**; otherwise move or delete them first. If the VNet is peered, every address space change requires a **peering sync** (covered in the peering lesson).

## Subnet settings you configure

Each subnet carries settings that live on the subnet, not on the VM:

- **Network security group** (one per subnet) and **route table** (one per subnet).
- **NAT gateway** (one per subnet).
- **Service endpoints** (per service, per subnet).
- **Subnet delegation**: hands the subnet to a PaaS service that injects instances into it (for example `Microsoft.Sql/managedInstances`, `Microsoft.Web/serverFarms` for App Service VNet integration, `Microsoft.Network/dnsResolvers`). The service can then apply its own "network intent policies". You can't change the delegation while that service's resources exist in the subnet.
- **Private endpoint network policies** (NSG and/or route table support for private endpoints).
- **Private subnet** (`defaultOutboundAccess` = false), explained next.

## Default outbound access and private subnets

Historically a VM with no explicit outbound method still reached the internet through a Microsoft-owned **default outbound access IP** that you don't control and that can change. Explicit methods are: a NAT gateway on the subnet, a Standard public load balancer with outbound rules, a public IP on the NIC (and a Basic public load balancer, now retired).

What Microsoft Learn states today (default-outbound-access page, updated 2026-09):

- For the API version released **after March 31, 2026**, subnets in **new** virtual networks have `defaultOutboundAccess` set to **false** by default: they are **private subnets**, and VMs in them need an explicit outbound method to reach the internet or Microsoft public endpoints. The **Azure portal already defaults** to private subnets.
- **Existing** virtual networks aren't changed. Existing and new VMs in them can still get default outbound IPs unless you make the subnet private.
- Deployments that use older API versions (older templates, some tools) keep the old behaviour (`defaultOutboundAccess` null, which implicitly allows it).
- Learn calls this a "retirement of default outbound access" in scope only for this default change, and points to the official announcement for the timeline; it is "not a blanket shutdown" for existing VNets.

Private subnet facts worth remembering: Windows activation and Windows Update fail without explicit egress; UDRs with next hop **Internet** stop working; VMs can still reach **Azure Storage in the same region**; delegated subnets aren't affected. To fully remove an already-assigned default outbound IP you must make the subnet private **and** stop (deallocate) the VMs.

```bash
az network vnet subnet update -g rg-net-prod --vnet-name vnet-hub -n snet-app --default-outbound false
```

```powershell
$vnet = Get-AzVirtualNetwork -ResourceGroupName rg-net-prod -Name vnet-hub
Set-AzVirtualNetworkSubnetConfig -VirtualNetwork $vnet -Name snet-app -AddressPrefix 10.10.1.0/24 -DefaultOutboundAccess $false
$vnet | Set-AzVirtualNetwork
```

### NAT gateway in one paragraph

A NAT gateway gives every VM in its subnets outbound SNAT through up to 16 public IPv4 addresses (or a public IP prefix), with no route table changes. It never accepts unsolicited inbound connections. Learn's precedence for outbound traffic is: **UDR to a virtual appliance or VPN/ExpressRoute gateway > NAT gateway > instance-level public IP > load balancer outbound rules > default route to the internet**. One NAT gateway per subnet, it can serve several subnets of one VNet but not span VNets, and it can't go in the GatewaySubnet. The **Standard** SKU is zonal; the newer **StandardV2** is zone-redundant, supports IPv6 and needs StandardV2 public IPs.

## Create a VNet

**Portal**: **Virtual networks** > **+ Create** > Basics (subscription, resource group, name, region) > **IP addresses** tab (address space, subnets) > **Review + create**.

```bash
az network vnet create \
  --resource-group rg-net-prod --name vnet-hub --location eastus \
  --address-prefixes 10.10.0.0/16 \
  --subnet-name snet-app --subnet-prefixes 10.10.1.0/24

az network vnet subnet create -g rg-net-prod --vnet-name vnet-hub \
  -n AzureBastionSubnet --address-prefixes 10.10.250.0/26

# Add a second address range to the VNet
az network vnet update -g rg-net-prod -n vnet-hub --address-prefixes 10.10.0.0/16 10.20.0.0/16
```

```powershell
$app = New-AzVirtualNetworkSubnetConfig -Name snet-app -AddressPrefix 10.10.1.0/24
$gw  = New-AzVirtualNetworkSubnetConfig -Name GatewaySubnet -AddressPrefix 10.10.255.0/27
New-AzVirtualNetwork -Name vnet-hub -ResourceGroupName rg-net-prod -Location eastus `
  -AddressPrefix 10.10.0.0/16 -Subnet $app, $gw
```

Note that `az network vnet update --address-prefixes` replaces the list, so include the existing range. The CLI also has `az network vnet subnet update --delegations Microsoft.Web/serverFarms` and `--service-endpoints`, and `New-AzVirtualNetworkSubnetConfig` has `-Delegation`, `-ServiceEndpoint` and `-DefaultOutboundAccess`.

> **Watch out:** VNets and subnets are free, but anything you put in them may not be. Name special subnets exactly; `gatewaysubnet` in a template typo is a classic deployment failure.

## Try it yourself

Runs in **Azure Cloud Shell** (Bash) from any browser on Windows, macOS or Linux. Cost: **nothing** (VNets and subnets aren't billed).

1. Create the lab:

   ```bash
   rg=rg-lab-d4vnet; az group create -n $rg -l eastus
   az network vnet create -g $rg -n vnet-lab --address-prefixes 10.50.0.0/16 \
     --subnet-name snet-web --subnet-prefixes 10.50.1.0/28
   ```

2. Try a /30: `az network vnet subnet create -g $rg --vnet-name vnet-lab -n snet-tiny --address-prefixes 10.50.2.0/30`. Read the error (Azure's minimum is /29).
3. Create `AzureBastionSubnet` as a /27 (`az network vnet subnet create -g $rg --vnet-name vnet-lab -n AzureBastionSubnet --address-prefixes 10.50.3.0/27`), then, because it's empty, resize it to the /26 that a Bastion Basic, Standard or Premium deployment requires: `az network vnet subnet update -g $rg --vnet-name vnet-lab -n AzureBastionSubnet --address-prefixes 10.50.3.0/26`.
4. Make snet-web private and read the property back:

   ```bash
   az network vnet subnet update -g $rg --vnet-name vnet-lab -n snet-web --default-outbound false
   az network vnet subnet show -g $rg --vnet-name vnet-lab -n snet-web --query defaultOutboundAccess
   ```

5. In the portal, open vnet-lab > **Subnets** and check the available IP count for snet-web (a /28 shows 11).
6. Clean up: `az group delete -n $rg --yes --no-wait`

## Key takeaways

- A VNet is regional, spans zones, and has no broadcast, multicast or customer DHCP.
- Every subnet loses five addresses: network, .1 gateway, .2 and .3 DNS, and the last address. /29 is the smallest IPv4 subnet (3 usable).
- GatewaySubnet /27 or larger (only the Basic VPN SKU allows /29), AzureBastionSubnet /26 or larger, AzureFirewallSubnet /26.
- You can add address ranges any time; you can resize a subnet only when it's empty; peered VNets need a sync afterwards.
- Subnet delegation hands a subnet to a PaaS service; NSG, route table, NAT gateway and service endpoints are per-subnet settings.
- New VNets created with API versions after March 31, 2026 (and the portal) get private subnets: plan NAT gateway or another explicit egress.
