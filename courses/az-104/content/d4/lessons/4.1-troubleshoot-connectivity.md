## Network Watcher: the toolbox

Azure Network Watcher is a regional service for IaaS network diagnostics. Learn states that it is **enabled automatically** in a region when you create or update a VNet there (no charge for enabling it), unless you opted out. It lives in a resource group called `NetworkWatcherRG` by default, as an instance named `NetworkWatcher_<region>`. Some tools work agentless; **packet capture** needs the Network Watcher agent VM extension (`AzureNetworkWatcherExtension`).

Learn groups the tools as monitoring (Topology, Connection monitor), seven diagnostic tools, and traffic tools (flow logs, traffic analytics). For the exam you must pick the right tool for a question:

| Question you're asking | Tool | Input / output |
|---|---|---|
| "Will an NSG allow this 5-tuple to or from this VM, and which rule decides?" | **IP flow verify** | VM (NIC), direction, protocol TCP or UDP, local IP:port, remote IP:port. Returns Allow or Deny and the rule name. TCP and UDP only. |
| Same, but for ICMP, a service tag or prefix as the remote, a scale set or Application Gateway, or "add a rule to fix it" | **NSG diagnostics** | Shows each NSG evaluated and the matching rule, and can add a higher-priority rule |
| "Where does the packet go next from this VM?" | **Next hop** | VM, source IP, destination IP. Returns next hop type, next hop IP and the route table ID (or "System Route") |
| "What rules actually apply to this NIC, subnet NSG plus NIC NSG?" | **Effective security rules** | The aggregated inbound and outbound rules from both NSGs (and admin rules); select a rule to see the prefixes behind a tag; download as CSV |
| "What routes apply to this NIC?" | **Effective routes** (NIC blade, not strictly a Network Watcher tool) | Full route table with Source and State |
| "Can VM A reach this FQDN/IP:port right now, and where does it fail?" | **Connection troubleshoot** | Source VM, scale set, Application Gateway or Bastion host; destination VM, FQDN, URI or IPv4. Returns reachable/unreachable, hops, latency and the fault (NSG, UDR, guest firewall, DNS). Now agentless. |
| "I need packets" | **Packet capture** | Captures on a VM or scale set to storage or local file, with filters and time/size limits; needs the agent extension |
| "Why is my site-to-site tunnel down?" | **VPN troubleshoot** | Runs against a virtual network gateway or connection; writes logs to a storage account |
| "Show me how everything is connected" | **Topology** | Interactive diagram across subscriptions, resource groups and regions |
| "Alert me when latency or reachability degrades over time" | **Connection monitor** | Continuous tests (taught in Domain 5) |
| "Record every flow" | **Flow logs** (+ traffic analytics) | VNet flow logs to a storage account; analytics to Log Analytics |

> **Exam tip:** IP flow verify answers "**which NSG rule**". Next hop answers "**which route**". Connection troubleshoot answers "**does the whole path work, and where does it break**". If the stem says the packet is ICMP, IP flow verify is out.

## A troubleshooting sequence that maps to the tools

For "VM-A can't reach VM-B on TCP 1433":

1. **Is the destination up and listening?** Check the VM is running and the service listens (guest tools). Azure tools can't see inside the OS except through connection troubleshoot's result codes.
2. **Routing**: run **next hop** from VM-A to VM-B's IP. Expect `VirtualNetwork` or `VirtualNetworkPeering`. `None` means a null route or a non-transitive path; `VirtualAppliance` means the firewall is in the path, so check it.
3. **Filtering at the source**: IP flow verify **Outbound** from VM-A (local VM-A:any, remote VM-B:1433).
4. **Filtering at the destination**: IP flow verify **Inbound** on VM-B (local VM-B:1433, remote VM-A:any). Remember inbound goes subnet NSG then NIC NSG.
5. **End to end**: connection troubleshoot from VM-A to VM-B port 1433. If it reports the guest firewall, the Azure configuration is fine.
6. **Evidence**: packet capture on VM-B filtered to port 1433 to see whether SYNs arrive.

## Reading tool output

IP flow verify (CLI):

```bash
az network watcher test-ip-flow -g rg-app-prod --vm vm-sql-01 \
  --direction Inbound --protocol TCP --local 10.20.2.10:1433 --remote 10.20.1.4:50000
```

```text
{
  "access": "Deny",
  "ruleName": "securityRules/deny-app-to-sql"
}
```

The `ruleName` tells you which rule and therefore which NSG to change. A result of `defaultSecurityRules/DenyAllInBound` means **no** custom rule matched and the default deny caught it.

Next hop:

```bash
az network watcher show-next-hop -g rg-app-prod --vm vm-app-01 \
  --source-ip 10.20.1.4 --dest-ip 10.30.1.5
```

```text
{
  "nextHopIpAddress": "10.10.3.4",
  "nextHopType": "VirtualAppliance",
  "routeTableId": "/subscriptions/<subscription-id>/resourceGroups/rg-net-prod/providers/Microsoft.Network/routeTables/rt-spokes"
}
```

A `routeTableId` of `System Route` means no UDR matched.

PowerShell equivalents (all need the Network Watcher object or its name and resource group):

```powershell
$nw = Get-AzNetworkWatcher -Location eastus
$vm = Get-AzVM -ResourceGroupName rg-app-prod -Name vm-sql-01
Test-AzNetworkWatcherIPFlow -NetworkWatcher $nw -TargetVirtualMachineId $vm.Id -Direction Inbound `
  -Protocol TCP -LocalIPAddress 10.20.2.10 -LocalPort 1433 -RemoteIPAddress 10.20.1.4 -RemotePort 50000
Get-AzNetworkWatcherNextHop -NetworkWatcher $nw -TargetVirtualMachineId $vm.Id `
  -SourceIPAddress 10.20.2.10 -DestinationIPAddress 10.30.1.5
Get-AzEffectiveRouteTable -NetworkInterfaceName nic-sql-01 -ResourceGroupName rg-app-prod
Get-AzEffectiveNetworkSecurityGroup -NetworkInterfaceName nic-sql-01 -ResourceGroupName rg-app-prod
```

**Portal**: search **Network Watcher**, then under **Network diagnostic tools** pick **IP flow verify**, **NSG diagnostics**, **Next hop**, **Effective security rules**, **Connection troubleshoot**, **Packet capture** or **VPN troubleshoot**. Effective routes and effective security rules are also on each NIC under **Help**.

## Common causes and the tool that shows them

| Symptom | Likely cause | Tool that proves it |
|---|---|---|
| Spoke1 VM can't reach Spoke2 VM, both peered to the hub | Peering isn't transitive | Next hop returns None, or no peering route in effective routes |
| Traffic to on-premises goes to the internet | Spoke not using remote gateway, or gateway route propagation disabled with no UDR | Effective routes |
| Packets reach the NVA but go no further | IP forwarding off on the NVA NIC, or OS forwarding off | Packet capture on the NVA; NIC IP configuration blade |
| Return traffic missing through a firewall | Asymmetric routing: one direction via NVA, the other direct | Next hop from both ends |
| Inbound RDP to a Standard public IP times out | No NSG rule allows it (secure by default) | IP flow verify Inbound |
| Works by IP, fails by name | DNS: private zone not linked, custom DNS can't resolve | Connection troubleshoot (DNS result), `nslookup` in the VM |
| New VM in a new VNet can't reach the internet | Private subnet (no default outbound access) and no NAT gateway | Connection troubleshoot to an internet FQDN; subnet properties |

## Flow logs today

Learn's NSG flow logs page states: **"Network security group (NSG) flow logs retire on September 30, 2027."** Because the feature is retiring, **new NSG flow logs can no longer be created**; after the retirement date Azure stops supporting traffic analytics on NSG flow logs and deletes existing NSG flow log resources (records already in storage are kept per their retention). The replacement is **virtual network flow logs**, which you enable on a **virtual network, subnet or network interface** (if set at several levels, NIC > subnet > VNet), record every flow through the VNet whether or not an NSG is involved (including Azure Virtual Network Manager security admin rule decisions and encryption state), write JSON to a Standard storage account in the **same region** every minute, and feed **traffic analytics** in a Log Analytics workspace.

```bash
az network watcher flow-log create --location eastus -g rg-net-prod --name fl-vnet-hub \
  --vnet vnet-hub --storage-account stcontosoflow01
```

## Try it yourself

Azure Cloud Shell (Bash), any browser. Cost: one Standard_B1s VM for under an hour, a few US cents.

```bash
rg=rg-lab-d4nw; az group create -n $rg -l eastus
az network vnet create -g $rg -n vnet-lab --address-prefixes 10.80.0.0/16 --subnet-name snet-app --subnet-prefixes 10.80.1.0/24
az network nsg create -g $rg -n nsg-app
az network nsg rule create -g $rg --nsg-name nsg-app -n deny-https-out --priority 200 --direction Outbound \
  --access Deny --protocol Tcp --destination-address-prefixes Internet --destination-port-ranges 443
az network vnet subnet update -g $rg --vnet-name vnet-lab -n snet-app --nsg nsg-app
az vm create -g $rg -n vm-lab --image Ubuntu2204 --size Standard_B1s --vnet-name vnet-lab --subnet snet-app \
  --private-ip-address 10.80.1.4 --public-ip-address "" --nsg "" --admin-username azureuser --generate-ssh-keys
az network watcher test-ip-flow -g $rg --vm vm-lab --direction Outbound --protocol TCP --local 10.80.1.4:60000 --remote 198.51.100.10:443
az network watcher test-ip-flow -g $rg --vm vm-lab --direction Outbound --protocol TCP --local 10.80.1.4:60000 --remote 198.51.100.10:80
az network watcher show-next-hop -g $rg --vm vm-lab --source-ip 10.80.1.4 --dest-ip 198.51.100.10
```

1. Predict both IP flow verify results before running them (Deny by deny-https-out; Allow by AllowInternetOutBound).
2. In the portal, open **Network Watcher** > **Topology** and select the resource group.
3. Clean up: `az group delete -n $rg --yes --no-wait`

## Key takeaways

- IP flow verify: allow/deny and the deciding NSG rule for TCP/UDP to or from a VM. NSG diagnostics adds ICMP, service tags and fix-it rules.
- Next hop: the route chosen (type, IP, route table ID). Effective routes and effective security rules show the full picture for one NIC of a running VM.
- Connection troubleshoot tests the real path at a point in time; connection monitor watches over time.
- Packet capture needs the Network Watcher agent extension; VPN troubleshoot targets gateways and connections.
- NSG flow logs retire on September 30, 2027 and can't be newly created; use **virtual network flow logs** (VNet, subnet or NIC scope).
