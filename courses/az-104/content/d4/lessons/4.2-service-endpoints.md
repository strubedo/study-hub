## The problem service endpoints solve

PaaS services such as Azure Storage, Azure SQL Database and Key Vault have public endpoints. Their firewalls can allow public IP ranges, but your VMs talk to them from **private** addresses that are meaningless to the service (and overlap across customers). A **virtual network service endpoint** extends the identity of your **subnet** to the service:

- You enable an endpoint **per subnet, per service** (for example `Microsoft.Storage` on snet-app).
- Azure adds routes for that service's public prefixes to the subnet with next hop type `VirtualNetworkServiceEndpoint`. Traffic to the service goes **straight over the Microsoft backbone**, even if the subnet has a forced-tunnelling 0.0.0.0/0 to an NVA or on-premises (Learn: service endpoint routes override BGP and UDRs for those prefixes).
- Requests reach the service with the VM's **private IP** as the source, plus the VNet and subnet identity, so the service can write a **virtual network rule** that says "allow snet-app of vnet-hub".
- The service keeps its **public endpoint**, public IP and public DNS name. Nothing changes in DNS.

Service endpoints are **free**.

## Services and endpoint names

Learn's list of generally available endpoints includes:

| Service | Endpoint name |
|---|---|
| Azure Storage (same region; Learn's storage docs add RA-GRS secondary access) | `Microsoft.Storage` |
| Azure Storage, any region (cross-region) | `Microsoft.Storage.Global` |
| Azure SQL Database, Synapse dedicated SQL pools, Azure Database for MariaDB | `Microsoft.Sql` |
| Azure Cosmos DB | `Microsoft.AzureCosmosDB` |
| Azure Key Vault | `Microsoft.KeyVault` |
| Service Bus, Event Hubs | `Microsoft.ServiceBus`, `Microsoft.EventHub` |
| App Service | `Microsoft.Web` |
| Azure AI services | `Microsoft.CognitiveServices` |
| Container Registry | `Microsoft.ContainerRegistry` |

Learn also says that for **Azure SQL** the VNet must be in the **same region** as the server, while other services can be secured to VNets in any region; and that the VNet and the service resource can be in different subscriptions.

## It takes two steps

A service endpoint alone allows nothing new. It's half of a pair:

1. **Subnet side**: enable the service endpoint on the subnet.
2. **Service side**: add a **virtual network rule** for that subnet in the resource's firewall (storage account **Networking**, SQL server **Networking**, Key Vault **Networking**), and set the resource to deny other public traffic (for storage: "Enabled from selected networks", default action Deny).

If you only do step 1, the subnet still reaches the service as before (the firewall may even start rejecting it: see below). If you only do step 2, the rule has nothing to match: requests from the subnet still arrive from a public address. Enable the endpoint first, as Learn's storage steps do.

## Side effects to plan for

- **Source IP switch**: when you enable the endpoint, traffic from that subnet to the service switches from the VM's public IP (or NAT/SNAT address) to its **private** IP. Any existing service firewall **IP rule** that allowed your public egress address stops matching for that subnet. Learn also warns that open TCP connections to the service are closed during the switch.
- **On-premises traffic isn't covered.** Endpoints apply to traffic from Azure subnets only. On-premises clients must be allowed by their public NAT IP (IP rule), or use a **private endpoint**.
- **NSGs still apply**: outbound to the service must be allowed (the default AllowInternetOutBound does; if you deny Internet outbound, allow the service tag, for example `Storage.EastUS`).
- **DNS is unchanged**: the service name still resolves to its public IP.
- **Data exfiltration**: a storage endpoint lets the subnet reach **every** storage account in scope, including someone else's. To restrict that, use a service endpoint policy.

## Service endpoint policies

A **service endpoint policy** is attached to a subnet that has the `Microsoft.Storage` endpoint and lists **which storage accounts** (by resource ID, or all accounts in a resource group or subscription) the subnet may reach through the endpoint. Once a policy is attached, access to any storage account **not** listed is denied from that subnet. Learn's constraints: currently Azure Storage only; multiple policies on a subnet combine (anything in any of them is allowed); the policy must be in the same region and subscription as the VNet; classic storage accounts aren't supported.

```bash
az network service-endpoint policy create -g rg-net-prod -n sep-allow-prod --location eastus
az network service-endpoint policy-definition create -g rg-net-prod --policy-name sep-allow-prod -n prod-accounts \
  --service Microsoft.Storage \
  --service-resources /subscriptions/<subscription-id>/resourceGroups/rg-data-prod/providers/Microsoft.Storage/storageAccounts/stcontosodata01
az network vnet subnet update -g rg-net-prod --vnet-name vnet-hub -n snet-app --service-endpoint-policy sep-allow-prod
```

## Configure an endpoint and a VNet rule

**Portal**: VNet > **Subnets** > select the subnet > **Service endpoints**: pick `Microsoft.Storage` > **Save**. Then storage account > **Security + networking** > **Networking** > **Enabled from selected networks** > **+ Add existing virtual network** > choose the VNet and subnet.

```bash
az network vnet subnet update -g rg-net-prod --vnet-name vnet-hub -n snet-app --service-endpoints Microsoft.Storage Microsoft.KeyVault
subnetid=$(az network vnet subnet show -g rg-net-prod --vnet-name vnet-hub -n snet-app --query id -o tsv)
az storage account network-rule add -g rg-data-prod --account-name stcontosodata01 --subnet $subnetid
az storage account update -g rg-data-prod -n stcontosodata01 --default-action Deny
```

```powershell
$vnet = Get-AzVirtualNetwork -Name vnet-hub -ResourceGroupName rg-net-prod
Set-AzVirtualNetworkSubnetConfig -VirtualNetwork $vnet -Name snet-app -AddressPrefix 10.10.1.0/24 `
  -ServiceEndpoint Microsoft.Storage, Microsoft.KeyVault | Set-AzVirtualNetwork
$subnet = (Get-AzVirtualNetwork -Name vnet-hub -ResourceGroupName rg-net-prod).Subnets | Where-Object Name -eq snet-app
Add-AzStorageAccountNetworkRule -ResourceGroupName rg-data-prod -Name stcontosodata01 -VirtualNetworkResourceId $subnet.Id
Update-AzStorageAccountNetworkRuleSet -ResourceGroupName rg-data-prod -Name stcontosodata01 -DefaultAction Deny
```

> **Watch out:** `Set-AzVirtualNetworkSubnetConfig -ServiceEndpoint` replaces the list. Include every endpoint you want to keep and the subnet's current address prefix.

## Verifying it

- **Effective routes** on a NIC in the subnet show routes with next hop type `VirtualNetworkServiceEndpoint` and Source **Default**.
- The service's logs show the **private** client IP for requests from the subnet.
- **Next hop** for a storage public IP returns `VirtualNetworkServiceEndpoint` instead of `Internet` or `VirtualAppliance`.

## Service endpoint or private endpoint?

Learn now **recommends private endpoints** for secure private access to PaaS. Service endpoints are still valid and are what this objective asks you to configure; the next lesson compares the two in detail. Quick rule: service endpoint = free, subnet-to-service, public endpoint stays; private endpoint = paid, private IP for one resource, works from on-premises and peered VNets.

## Try it yourself

Azure Cloud Shell (Bash), any browser. Cost: no VMs; a Standard LRS storage account with no data costs a fraction of a cent. **Effectively free.**

```bash
rg=rg-lab-d4se; sa=stlabse$RANDOM; az group create -n $rg -l eastus
az network vnet create -g $rg -n vnet-lab --address-prefixes 10.95.0.0/16 --subnet-name snet-app --subnet-prefixes 10.95.1.0/24
az storage account create -g $rg -n $sa --sku Standard_LRS --kind StorageV2
az network vnet subnet update -g $rg --vnet-name vnet-lab -n snet-app --service-endpoints Microsoft.Storage
az storage account network-rule add -g $rg --account-name $sa --vnet-name vnet-lab --subnet snet-app
az storage account update -g $rg -n $sa --default-action Deny
az storage account show -g $rg -n $sa --query networkRuleSet
```

1. Read the network rule set: one virtual network rule, default action Deny.
2. Remove the endpoint from the subnet (`--service-endpoints ""`), then look at the storage account's **Networking** page and at `--query networkRuleSet.virtualNetworkRules` again. The rule still exists but can no longer match traffic from that subnet. (Whether the portal or the CLI shows a warning, or refuses the removal, is documentation-based: note what you see.)
3. Clean up: `az group delete -n $rg --yes --no-wait`

## Key takeaways

- A service endpoint is enabled per subnet per service; it adds `VirtualNetworkServiceEndpoint` routes and sends the subnet's identity and private source IP to the service.
- It must be paired with a **virtual network rule** on the PaaS resource firewall (and default action Deny).
- The service keeps its public endpoint and public DNS; on-premises clients aren't covered.
- Enabling it switches the source IP to private, so IP rules for your public egress stop matching for that subnet.
- `Microsoft.Storage` = same region; `Microsoft.Storage.Global` = any region; SQL endpoints need the same region.
- Service endpoint policies limit a subnet to specific storage accounts (anti-exfiltration).
