## Name resolution inside a VNet

Every VNet starts with **Azure-provided DNS**. VMs receive the DNS server **168.63.129.16** through DHCP, a static virtual IP of the host that Learn documents as never changing and present in every region. It gives you:

- Resolution of public internet names (recursive).
- Hostname resolution of VMs **in the same VNet**, under the DHCP-supplied suffix `<something>.internal.cloudapp.net`, plus Azure-managed reverse (PTR) records in that zone.
- Resolution of names in **private DNS zones linked** to the VNet, which is how private endpoints work.

What it doesn't give you: names of VMs in **other** VNets (peered or not), on-premises names, or anything you control. Learn also notes 168.63.129.16 serves health probes, DHCP and the VM agent, so never block it with a guest firewall unless you mean to.

The two ways to go beyond that are **Azure Private DNS zones** and **custom DNS servers**.

## Azure Private DNS zones

A private DNS zone (`Microsoft.Network/privateDnsZones`) is a zone visible only to VNets you **link** to it. You can use any name, including a name that also exists publicly (`contoso.com`): that's **split-horizon**. Inside linked VNets, the private zone answers; outside, public DNS answers. Because the private zone is authoritative for its name inside the linked VNets, a name that exists only in the public copy doesn't resolve there unless you add it to the private zone too. Learn's private endpoint DNS guidance describes the same effect for `privatelink` zones and documents a link **resolution policy** (`NxDomainRedirect`, "fallback to internet") that forwards unanswered queries to public resolution.

### Virtual network links

A **virtual network link** connects one VNet to one zone. Two kinds:

| | Registration link (auto-registration enabled) | Resolution link |
|---|---|---|
| VMs can query the zone | Yes | Yes |
| Azure creates/deletes **A records** for VMs in the VNet automatically | Yes | No |
| Per VNet | **Only one** registration zone per VNet | Up to **1,000** zones per VNet |
| Per zone (Learn's limits page) | Up to **100** registration VNets | Up to **1,000** VNet links in total |

Auto-registration facts from Learn:

- Records are created for **virtual machines only**, for the **primary NIC** only, and as **A records** (no PTR). Other resources (internal load balancers, private endpoints) need manual records or a DNS zone group.
- When a VM is **deleted or stopped**, its auto-registered records are removed.
- You can create only **one link** between a given zone and a given VNet.
- Deleting a VNet deletes its links and auto-registered records.
- The link's **Link Status** must reach *Completed* before it works (a few minutes for large VNets).

A link can cross subscriptions; the VNet and zone don't need to be in the same region (private zones are global resources).

### A typical design

- `corp.contoso.com` private zone, linked with **auto-registration** to `vnet-hub` and each spoke (each VNet has only one registration zone, so use the same one), so VMs find each other by name across peerings.
- `privatelink.blob.core.windows.net`, `privatelink.database.windows.net`, ... linked as **resolution** links to the hub and spokes (or only to the hub when spokes use a hub DNS resolver).

## Custom DNS servers on a VNet

Set **DNS servers** on the VNet (VNet > **Settings** > **DNS servers** > **Custom**) to point VMs at your own resolvers, typically domain controllers or a DNS forwarder in the hub. You can also set DNS servers per NIC. Rules:

- Learn: after changing DNS servers, VMs pick up the new list only after a **DHCP lease renewal** (for example `ipconfig /renew`, or restart the VM).
- Your DNS servers must forward what they can't answer to **168.63.129.16** (for private zones and Azure names) or to on-premises resolvers. 168.63.129.16 is reachable only from inside Azure, so on-premises servers can't use it directly.
- NSGs must allow UDP/TCP 53 to your DNS servers.
- Learn's name resolution page says that if Azure VPN Gateway is used together with custom DNS server IPs on the VNet, 168.63.129.16 must be added to the list "to maintain undisrupted service".
- DNS servers set on a **NIC** take precedence over those set on the VNet.

## Azure DNS Private Resolver (high level)

The **Azure DNS Private Resolver** is a managed resolver deployed into a VNet, replacing DNS forwarder VMs:

- **Inbound endpoint**: a private IP in a dedicated subnet (delegated to `Microsoft.Network/dnsResolvers`) that on-premises DNS servers conditionally forward to. Queries arriving there are resolved by Azure DNS in the context of that VNet, so linked private zones work for on-premises clients.
- **Outbound endpoint** + **DNS forwarding ruleset**: lets Azure VNets conditionally forward domains (say `onprem.contoso.com`) to on-premises DNS servers. A ruleset is linked to VNets.

For the exam: "on-premises clients must resolve private endpoint names without managing VMs" = Private Resolver **inbound** endpoint; "Azure VMs must resolve an on-premises domain" = **outbound** endpoint with a forwarding rule (or a custom DNS server).

## Configure a private zone and links

**Portal**: **Private DNS zones** > **+ Create** (name, resource group). In the zone: **DNS Management** > **Virtual Network Links** > **+ Add**: link name, VNet, **Enable auto registration**. Records: **+ Record set** as with public zones.

```bash
az network private-dns zone create -g rg-dns-prod -n corp.contoso.com
az network private-dns link vnet create -g rg-dns-prod -z corp.contoso.com -n link-hub \
  -v /subscriptions/<subscription-id>/resourceGroups/rg-net-prod/providers/Microsoft.Network/virtualNetworks/vnet-hub \
  --registration-enabled true
az network private-dns link vnet create -g rg-dns-prod -z corp.contoso.com -n link-spoke1 \
  -v <vnet-spoke1-resource-id> --registration-enabled false
az network private-dns record-set a add-record -g rg-dns-prod -z corp.contoso.com -n ilb-app -a 10.21.1.100
az network vnet update -g rg-net-prod -n vnet-spoke2 --dns-servers 10.10.2.4 10.10.2.5
```

```powershell
New-AzPrivateDnsZone -Name corp.contoso.com -ResourceGroupName rg-dns-prod
$hub = Get-AzVirtualNetwork -Name vnet-hub -ResourceGroupName rg-net-prod
New-AzPrivateDnsVirtualNetworkLink -ResourceGroupName rg-dns-prod -ZoneName corp.contoso.com `
  -Name link-hub -VirtualNetworkId $hub.Id -EnableRegistration
New-AzPrivateDnsRecordSet -ResourceGroupName rg-dns-prod -ZoneName corp.contoso.com -Name ilb-app `
  -RecordType A -Ttl 3600 -PrivateDnsRecord (New-AzPrivateDnsRecordConfig -IPv4Address 10.21.1.100)
```

`--registration-enabled` is **required** on `az network private-dns link vnet create`.

## Troubleshooting name resolution

| Symptom | Check |
|---|---|
| VM in spoke can't resolve `vm-db01.corp.contoso.com` | Spoke VNet not linked to the zone, or spoke uses custom DNS that doesn't forward to 168.63.129.16 |
| New VM has no record in the zone | Its VNet link isn't registration-enabled, or it's a second NIC, or the VNet already has another registration zone |
| Private endpoint resolves to public IP | `privatelink` zone missing, not linked to the client's VNet, or no A record (no DNS zone group) |
| On-premises can't resolve private endpoint | No conditional forwarder for the **public** zone name to an inbound endpoint/forwarder in a linked VNet |
| DNS server change "didn't work" | VMs haven't renewed their DHCP lease |

## Try it yourself

Azure Cloud Shell (Bash), any browser. Cost: a private zone is billed monthly per zone (prorated pricing isn't stated here; check the pricing page) and the B1s VM a few cents for an hour.

```bash
rg=rg-lab-d4pdns; az group create -n $rg -l eastus
az network vnet create -g $rg -n vnet-lab --address-prefixes 10.98.0.0/16 --subnet-name snet-app --subnet-prefixes 10.98.1.0/24
az network private-dns zone create -g $rg -n corp.contoso.com
az network private-dns link vnet create -g $rg -z corp.contoso.com -n link-lab -v vnet-lab --registration-enabled true
az vm create -g $rg -n vm-lab01 --image Ubuntu2204 --size Standard_B1s --vnet-name vnet-lab --subnet snet-app \
  --public-ip-address "" --nsg "" --admin-username azureuser --generate-ssh-keys
az network private-dns record-set a list -g $rg -z corp.contoso.com -o table
az vm run-command invoke -g $rg -n vm-lab01 --command-id RunShellScript --scripts "getent hosts vm-lab01.corp.contoso.com"
```

1. The record set list should show `vm-lab01` registered automatically.
2. Try to create a second registration link for vnet-lab to another zone (`az network private-dns zone create ... -n corp2.contoso.com`, then link with `--registration-enabled true`) and read the error.
3. Clean up: `az group delete -n $rg --yes --no-wait`

## Key takeaways

- Azure-provided DNS is 168.63.129.16: internet names, same-VNet VM names, and linked private zones. It doesn't cross peerings by itself.
- Private DNS zones are visible only to linked VNets; a zone can have the same name as a public zone (split-horizon).
- Auto-registration: VMs only, primary NIC, A records, removed when the VM is stopped or deleted; a VNet can have **one** registration zone; a zone up to **100** registration VNets and 1,000 links.
- Custom DNS servers on the VNet need a DHCP lease renewal on VMs and should forward to 168.63.129.16.
- DNS Private Resolver: inbound endpoint for on-premises-to-Azure, outbound endpoint plus forwarding ruleset for Azure-to-on-premises.
- CLI: `az network private-dns zone create`, `az network private-dns link vnet create --registration-enabled`.
