## Think like the data path

A Standard load balancer problem is almost always one of four things: the **probe** marks backends down, the **data path** to a healthy backend is filtered, the **flow pattern** isn't supported, or **outbound** SNAT is the real issue. Work through them in that order, the same way you'd check VIP health, ACLs, then NAT on any ADC.

## 1. Backends unhealthy (probe failures)

Learn's troubleshooting article lists the causes of probe failures; here they are with what to check:

| Cause | How it looks | Fix |
|---|---|---|
| **NSG blocks the probe** | All or some backends down; IP flow verify from 168.63.129.16 to the probe port shows Deny | Allow source **AzureLoadBalancer** to the probe port above any custom deny. A rule such as `deny-all-inbound` at 4000 hides **AllowAzureLoadBalancerInBound** (65001). |
| **Guest OS firewall** blocks it | NSG allows, IP flow verify allows, still down | Open the probe port in Windows Firewall / iptables / nftables for 168.63.129.16 |
| **App not listening** on the probe port | `netstat -an` / `ss -lnt` shows no LISTEN | Start the service or change the probe port |
| **Wrong path or non-200** (HTTP/HTTPS probes) | Service listening, browser works on `/`, probe path returns 404, 301 or 401 | Point the probe at a path that returns **200** without authentication or redirects; or use a TCP probe |
| **Wrong protocol** | HTTP probe against a non-HTTP service (LDAP, SQL) | Use a **TCP** probe on a port that reflects service health |
| **UDR sends probe traffic elsewhere** | Packet capture on the VM shows no probe packets arriving | Check effective routes; Learn lists forced routes as a cause |
| **VM itself unhealthy** | Can't reach it from another VM either | Fix the VM |

Floating IP rules add one more: the service must listen on the **frontend IP** configured on a loopback as well as on the NIC IP.

## 2. Healthy backends, no data traffic

Learn's "VMs not responding on the data port" article gives these causes:

- **Not listening on the data port** (probe port and data port differ, and only the probe port is open).
- **NSG blocks the data port** for the real **client** source. For a public load balancer, NSG rules must allow the **client's** IP (or Internet) to the **backend** port: the load balancer doesn't SNAT inbound traffic. AllowAzureLoadBalancerInBound covers **probes only**, not client traffic.
- **A backend calls the frontend of its own internal load balancer** and the flow hashes back to itself: unsupported, intermittent timeouts. Same for an app calling another app on the same NIC through the ILB. Fix: separate VMs per tier, a second NIC, or a proxy (Application Gateway).
- **Standard public IP or Standard LB without an NSG allowing inbound**: secure by default means nothing comes in until an NSG allows it.

Also check the SKU and placement rules:

- A Standard load balancer's backend pool must be in **one VNet**; VMs in another VNet (even peered) can't join it by NIC. (IP-based pools also reference addresses in the pool's VNet.)
- **Standard and Basic can't be mixed**: a VM with a **Basic** public IP on its NIC can't be in a Standard load balancer's pool, and a Standard LB needs Standard public IPs.
- Global peering to a **Basic** ILB frontend doesn't work; Standard ILBs work over global peering.

## 3. Outbound problems

### Backends behind an internal Standard load balancer can't reach the internet

By design. Learn: unlike the retired Basic ILB, a Standard ILB provides **no outbound connectivity**. Add an explicit method: **NAT gateway** on the backend subnet (Learn's recommended option), a public IP on each NIC, or a separate **Standard public load balancer with outbound rules** (an "outbound-only" configuration). New private subnets make this even more likely to appear.

### Intermittent outbound failures under load (SNAT exhaustion)

Each backend gets a fixed share of the 64,000 ports per frontend IP. Symptoms: outbound connections to the same destination IP:port fail or time out at peak while others work. Evidence: the **SNAT Connection Count** metric with **Connection State = failed** above zero, and **Used SNAT Ports** reaching **Allocated SNAT Ports** for an instance. Fixes: move to a **NAT gateway**; or use outbound rules with manual port allocation and more frontend IPs; reuse connections (HTTP keep-alive, connection pooling).

## 4. Idle connections dropped

Long-lived idle TCP sessions (database connections, SSH) die after **4 minutes** by default and the client only finds out on its next write. Raise the **idle timeout** (up to 100 minutes on load-balancing rules), enable **TCP reset** so both ends get a RST, or use TCP keepalives.

## Metrics and insights

Standard Load Balancer publishes multi-dimensional metrics in Azure Monitor (portal: load balancer > **Monitoring** > **Metrics**):

| Metric | Answers | Notes |
|---|---|---|
| **Data Path Availability** | Is the frontend-to-host data path in the region working? | Average aggregation. Platform synthetic test; if it drops while probes are fine, suspect the platform or the frontend |
| **Health Probe Status** | Do backends pass my probe? | Average, split by backend IP. 100 = all up |
| **SYN Count** | Are clients even arriving? | Sum. SYNs arriving but no healthy backends = probe issue; no SYNs = upstream (DNS, client firewall) |
| **SNAT Connection Count** | Outbound flows, successful vs failed | Sum, split by Connection State; failed > 0 = SNAT exhaustion |
| **Allocated SNAT Ports**, **Used SNAT Ports** | Per-instance SNAT budget and usage | Public LB |
| **Byte Count**, **Packet Count** | Throughput per frontend | Sum |

Learn notes Data Path Availability can take up to 10 minutes to appear after a load balancer is created or updated.

**Load Balancer insights** (Azure Monitor for networks, from the load balancer's **Insights** blade) adds a **functional dependency view** (frontends, rules, probes, backends, with health coloured) and a **pre-configured metrics dashboard**. It needs the **Standard** SKU for the load balancer metrics.

Also use **Resource health** on the load balancer, **Network Watcher** IP flow verify and connection troubleshoot from a test VM, and packet capture on a backend.

From the CLI, the metric names used by `az monitor metrics list` can differ from the portal display names; list them first:

```bash
az monitor metrics list-definitions --resource <lb-resource-id> --query "[].{name:name.value, display:name.localizedValue}" -o table
```

## A worked scenario

lb-web (Standard, public) has two backends; Health Probe Status is 0 for both; SYN Count is non-zero.

```text
nsg-snet-web (subnet), inbound
100   allow-https    TCP 443   Internet       > Any   Allow
4000  deny-all       Any       Any            > Any   Deny
65001 AllowAzureLoadBalancerInBound ...

Probe hp-http: HTTP port 80 path /health
```

1. Probes come from AzureLoadBalancer to TCP 80. Rule 100 doesn't match (port 443). Rule 4000 matches: **deny**. 65001 is never reached.
2. Fix: add `allow-lb-probe` at priority 110: source AzureLoadBalancer, destination port 80, Allow. Clients would still only reach 443 through rule 100.
3. Then confirm the app returns 200 for `/health` on port 80, and the guest firewall allows it.

## Try it yourself

Reuse the load balancer lab from the previous lesson (same cost: the load balancer, public IP and two VMs bill by the hour, a few dimes for an hour), then:

1. Block the probes with a rule that can only match probe traffic: `az network nsg rule create -g rg-lab-d4lb --nsg-name nsg-web -n deny-probes --priority 90 --access Deny --protocol '*' --source-address-prefixes AzureLoadBalancer --destination-address-prefixes '*' --destination-port-ranges '*'`. Watch **Health Probe Status** fall to 0 within a few minutes and the site stop answering, even though rule 100 still allows port 80 from Internet for clients. (In exam exhibits the same effect usually comes from a custom deny-all such as priority 4000 that sits above 65001; this lab uses an explicit AzureLoadBalancer source so the result doesn't depend on how the Internet tag in rule 100 treats 168.63.129.16.)
2. Delete it (`az network nsg rule delete -g rg-lab-d4lb --nsg-name nsg-web -n deny-probes`) and watch probes recover.
3. Change the probe to HTTP with path `/nothing` (`az network lb probe update -g rg-lab-d4lb --lb-name lb-lab -n hp --protocol Http --path /nothing`): the Python server returns 404, so backends go down although port 80 is open. Change `--path` to `/` and the backends return to healthy, because `/` returns 200.
4. Open the load balancer's **Insights** blade and look at the dependency view.
5. Clean up: `az group delete -n rg-lab-d4lb --yes --no-wait`

## Key takeaways

- Probe failures: NSG blocking AzureLoadBalancer (often a custom deny above 65001), guest firewall, app not listening, HTTP path not returning 200, wrong probe protocol.
- Client traffic keeps the client source IP: NSGs must allow the clients to the backend port; AllowAzureLoadBalancerInBound covers probes only.
- A backend calling its own ILB frontend and hashing to itself is unsupported.
- Standard backends must be in one VNet and can't use Basic public IPs.
- Standard ILB backends have no outbound internet: add a NAT gateway (preferred), instance public IPs or an outbound-rule public LB.
- SNAT exhaustion shows as failed SNAT connections and Used = Allocated SNAT ports; fix with NAT gateway or outbound rules with more IPs.
- Metrics: Data Path Availability (platform path), Health Probe Status (your probes), SYN Count, SNAT Connection Count; Insights gives a dependency view.
