## Azure Load Balancer is layer 4

Azure Load Balancer distributes **TCP and UDP flows**. It doesn't terminate connections, doesn't look at HTTP, has no certificates and no WAF. Think of it as a distributed, stateless-to-you L4 VIP implemented in the host SDN: packets keep the **client's source IP** (no SNAT on inbound), and the backend answers the client directly through the same platform path. Because there's no proxy, you can't "see" the load balancer in a traceroute, and its health probes come from **168.63.129.16**.

## SKUs and the Basic retirement

Learn's SKU page: **"On September 30, 2025, Basic Load Balancer was retired."** Existing Basic load balancers keep running but are unsupported and have no SLA; Microsoft directs you to upgrade to Standard (with a documented PowerShell upgrade script). Cloud Services Extended Support is the documented exception. A **Gateway** SKU exists for chaining third-party NVAs and is out of scope here.

| | **Standard** | Basic (retired) |
|---|---|---|
| Backend pool | Any VMs or scale sets in **one VNet**, by **NIC or IP address** | VMs in one availability set or scale set, by NIC |
| Health probes | TCP, **HTTP, HTTPS** | TCP, HTTP |
| Inbound by default | **Closed** unless an NSG allows (secure by default); internal traffic from the VNet to an internal LB is allowed | Open |
| Zones | Zone-redundant or zonal frontends | No |
| HA ports, outbound rules, TCP reset on idle, multiple frontends for outbound | Yes | No |
| Metrics (Azure Monitor multi-dimensional) | Yes | No |
| SLA | 99.99% | None |
| Public IP | Must be **Standard** | Basic |

## Public vs internal

- **Public load balancer**: frontend is a public IP (or prefix for outbound). Balances internet traffic to VMs and can provide **outbound** SNAT.
- **Internal load balancer (ILB)**: frontend is a **private IP** in a subnet. For multi-tier apps, SQL Always On listeners, NVAs behind **HA ports**, and services reached from on-premises over VPN/ExpressRoute. It provides **no outbound internet** for its backends.

## Components

| Component | What it is |
|---|---|
| **Frontend IP configuration** | The VIP: public IP or private IP (zonal or zone-redundant). A load balancer can have several. |
| **Backend pool** | NIC IP configurations (NIC-based) or IP addresses in the VNet (IP-based). VMs, scale sets. |
| **Health probe** | TCP, HTTP or HTTPS check on a port (and path for HTTP/S) at an interval |
| **Load-balancing rule** | Frontend IP + protocol + frontend port > backend pool + backend port, with a probe, distribution mode, idle timeout, TCP reset, floating IP, outbound SNAT setting |
| **Inbound NAT rule** | Port forwarding from the frontend to **one** VM (v1) or to a pool with a frontend port range (v2), e.g. 50001 > VM1:3389 |
| **Outbound rule** | Explicit SNAT for the backend pool through chosen frontend IPs, with allocated ports and idle timeout |

## Health probes

- **TCP** probe: success = three-way handshake completes. Fails on no answer or a **RST**.
- **HTTP / HTTPS** probe: `GET` on a relative path; only **HTTP 200** counts as healthy. Any other code (301, 401, 404, 500) marks the instance **down** immediately. HTTP/S probes time out after 30 seconds. HTTPS probes add TLS; Learn requires certificates with at least a SHA-256 signature hash across the chain.
- **Interval**: seconds between probes (Learn: every 5 seconds by default in the portal). **Threshold**: consecutive successes or failures needed to change state. Learn notes that for HTTP probes, explicit 200 / non-200 answers change state immediately; the threshold only matters for timeouts. (Learn's probe page is not fully consistent on thresholds, and the CLI marks `--probe-threshold` as preview; don't build exam answers on exact threshold arithmetic.)
- **Probe down behaviour (Standard)**: an instance that fails stops getting **new** flows; established TCP flows to it continue. If **all** instances are down, no new flows are sent; Learn says established TCP flows continue when the pool has more than one instance (UDP flows end). The probe's **no healthy backends behavior** setting (`-NoHealthyBackendsBehavior AllProbedUp` in PowerShell) can change this to "treat every instance as up"; the default is what this course describes.
- The **probe port doesn't have to be the data port**: probe a `/health` page on 8080 while serving 443.

NSGs must allow the probe: the default rule **AllowAzureLoadBalancerInBound (65001)** does, unless a custom deny with a lower number blocks it first. Guest firewalls must allow 168.63.129.16.

## Load-balancing rules

```text
frontend fe-web (203.0.113.40):TCP/443  >  pool bep-web :443   probe hp-https   distribution: None (5-tuple)
```

Key settings:

- **Session persistence** (distribution mode): **None** = 5-tuple hash (`Default` in CLI); **Client IP** = 2-tuple (source IP, destination IP) (`SourceIP`); **Client IP and protocol** = 3-tuple (`SourceIPProtocol`). Use Client IP when an app keeps server-side state per client; note many clients behind one NAT then land on one VM.
- **Idle timeout**: 4–100 minutes for load-balancing and inbound NAT rules (4–120 for outbound rules); default **4 minutes**. By default idle flows are **silently dropped**.
- **TCP reset**: when enabled, the load balancer sends **bidirectional RSTs** at idle timeout so both ends know the flow is gone (Standard only).
- **Floating IP** (direct server return): the backend receives packets with the **frontend IP** as the destination, so it must have a loopback with the frontend IP (weak host model on Windows). Needed for SQL Server Always On listeners and to reuse the same backend port in several rules.
- **HA ports**: an **internal** Standard LB rule with protocol **All** and frontend/backend port **0** balances **every TCP and UDP flow on every port**. The standard pattern for an NVA pair behind an ILB in a hub; point UDRs at the ILB frontend.
- **Outbound SNAT**: a load-balancing rule can implicitly give its backends outbound SNAT through the frontend IP ("default port allocation"), which Learn says not to use in production; prefer **outbound rules** or a **NAT gateway**.

## Outbound rules and SNAT exhaustion

Each public frontend IP gives **64,000** SNAT ports. With default allocation, each backend gets a share based on pool size (1,024 ports per IP for up to 50 instances, 512 for 51–100, down to 32 for 801–1,000). Every outbound connection to the same destination IP and port consumes a SNAT port; when an instance uses all of its ports, **new outbound connections fail** even if other instances have spare ports. Fixes in Learn's order of preference: use a **NAT gateway** (dynamic allocation, recommended), use **outbound rules** with manual allocation (multiples of 8) and more frontend IPs or a public IP prefix, enable connection reuse/pooling in the app.

## Zones and cross-region

- A Standard public or internal frontend can be **zone-redundant** (survives a zone failure) or **zonal** (pinned to one zone). Backends can be spread across zones.
- **Global (cross-region) load balancer**: a Standard public LB in the **Global** tier with a static **anycast** public IP, whose backends are regional public Standard load balancers. It routes to the closest healthy region (geo-proximity) and fails over when a region's probe availability drops to 0. Layer 4 only, like regional LB.

## Choosing the right Azure load balancer

| Requirement | Pick |
|---|---|
| TCP/UDP, any port, regional, lowest latency, NVA HA | **Azure Load Balancer** (internal or public) |
| HTTP(S) in one region: URL path routing, TLS termination, WAF, cookie affinity | **Application Gateway** |
| HTTP(S) globally: anycast edge, caching, WAF, fast failover between regions | **Azure Front Door** |
| Any protocol, global, **DNS-based** endpoint selection (priority, weighted, performance, geographic) | **Traffic Manager** |
| TCP/UDP across regions with a single static anycast IP | **Global (cross-region) Load Balancer** |

## Create a Standard public load balancer

**Portal**: **Load balancers** > **+ Create**: SKU Standard, type Public or Internal, tier Regional or Global > **Frontend IP configuration** > **Backend pools** (add VMs) > **Inbound rules** (load-balancing rule with a new health probe, inbound NAT rules) > **Outbound rules** > **Review + create**.

```bash
az network public-ip create -g rg-web-prod -n pip-lb-web --sku Standard --zone 1 2 3
az network lb create -g rg-web-prod -n lb-web --sku Standard \
  --public-ip-address pip-lb-web --frontend-ip-name fe-web --backend-pool-name bep-web
az network lb probe create -g rg-web-prod --lb-name lb-web -n hp-http --protocol Http --port 80 --path /health --interval 5
az network lb rule create -g rg-web-prod --lb-name lb-web -n rule-http --protocol Tcp \
  --frontend-ip fe-web --frontend-port 80 --backend-pool-name bep-web --backend-port 80 \
  --probe hp-http --idle-timeout 15 --enable-tcp-reset true --disable-outbound-snat true
az network lb outbound-rule create -g rg-web-prod --lb-name lb-web -n ob-web \
  --frontend-ip-configs fe-web --address-pool bep-web --protocol All --outbound-ports 10000
az network nic ip-config address-pool add -g rg-web-prod --nic-name nic-web-01 --ip-config-name ipconfig1 \
  --lb-name lb-web --address-pool bep-web
```

For an internal LB, replace the public IP with `--vnet-name vnet-app --subnet snet-app --private-ip-address 10.1.1.100`. The CLI's `--sku` default is Standard.

```powershell
$pip = Get-AzPublicIpAddress -Name pip-lb-web -ResourceGroupName rg-web-prod
$fe = New-AzLoadBalancerFrontendIpConfig -Name fe-web -PublicIpAddress $pip
$be = New-AzLoadBalancerBackendAddressPoolConfig -Name bep-web
$hp = New-AzLoadBalancerProbeConfig -Name hp-http -Protocol Http -Port 80 -RequestPath /health -IntervalInSeconds 5 -ProbeCount 2
$rule = New-AzLoadBalancerRuleConfig -Name rule-http -FrontendIpConfiguration $fe -BackendAddressPool $be `
  -Probe $hp -Protocol Tcp -FrontendPort 80 -BackendPort 80 -IdleTimeoutInMinutes 15 -EnableTcpReset -DisableOutboundSNAT
New-AzLoadBalancer -ResourceGroupName rg-web-prod -Name lb-web -Location eastus -Sku Standard `
  -FrontendIpConfiguration $fe -BackendAddressPool $be -Probe $hp -LoadBalancingRule $rule
```

## Try it yourself

Azure Cloud Shell (Bash), any browser. Cost: the Standard load balancer (its rules), the Standard public IP and the two Standard_B1s VMs all **bill by the hour** while they exist; about an hour costs well under one US dollar. Delete promptly.

The backends need **no outbound internet access**: the custom-data script installs nothing, it writes a page and runs it with the `python3` interpreter that is already in the Ubuntu 22.04 image, as a small systemd service so it also survives a restart. That matters because the subnet may be private (no default outbound access) and the VMs have no public IP.

```bash
rg=rg-lab-d4lb; az group create -n $rg -l eastus
az network vnet create -g $rg -n vnet-lab --address-prefixes 10.110.0.0/16 --subnet-name snet-web --subnet-prefixes 10.110.1.0/24
az network nsg create -g $rg -n nsg-web
az network nsg rule create -g $rg --nsg-name nsg-web -n allow-http --priority 100 --protocol Tcp \
  --source-address-prefixes Internet --destination-address-prefixes '*' --destination-port-ranges 80
az network vnet subnet update -g $rg --vnet-name vnet-lab -n snet-web --nsg nsg-web
cat > web.sh <<'EOF'
#!/bin/bash
mkdir -p /srv/www && hostname > /srv/www/index.html
cat > /etc/systemd/system/labweb.service <<'UNIT'
[Unit]
Description=Lab web server
After=network-online.target
[Service]
ExecStart=/usr/bin/python3 -m http.server 80 --directory /srv/www
Restart=always
[Install]
WantedBy=multi-user.target
UNIT
systemctl daemon-reload
systemctl enable labweb.service
systemctl start --no-block labweb.service
EOF
for i in 1 2; do az vm create -g $rg -n vm-web$i --image Ubuntu2204 --size Standard_B1s --vnet-name vnet-lab \
  --subnet snet-web --public-ip-address "" --nsg "" --custom-data web.sh --admin-username azureuser --generate-ssh-keys; done
az network public-ip create -g $rg -n pip-lb --sku Standard
az network lb create -g $rg -n lb-lab --sku Standard --public-ip-address pip-lb --frontend-ip-name fe --backend-pool-name bep
az network lb probe create -g $rg --lb-name lb-lab -n hp --protocol Tcp --port 80
az network lb rule create -g $rg --lb-name lb-lab -n r80 --protocol Tcp --frontend-ip fe --frontend-port 80 \
  --backend-pool-name bep --backend-port 80 --probe hp
for i in 1 2; do
  nicid=$(az vm show -g $rg -n vm-web$i --query "networkProfile.networkInterfaces[0].id" -o tsv)
  ipc=$(az network nic show --ids $nicid --query "ipConfigurations[0].name" -o tsv)
  az network nic ip-config address-pool add -g $rg --nic-name ${nicid##*/} --ip-config-name $ipc --lb-name lb-lab --address-pool bep
done
ip=$(az network public-ip show -g $rg -n pip-lb --query ipAddress -o tsv); for n in 1 2 3 4 5 6; do curl -s http://$ip; done
```

1. The loop reads each VM's NIC and IP configuration names instead of guessing them. If `curl` returns nothing at first, wait a minute for cloud-init to finish on both VMs and for the probe to mark them healthy.
2. Repeated requests should return both host names (5-tuple hash). Set `--load-distribution SourceIP` on the rule with `az network lb rule update` and try again.
3. Stop vm-web1 and watch the portal's **Monitoring** > **Metrics** > **Health Probe Status**.
4. Clean up: `az group delete -n $rg --yes --no-wait`

## Key takeaways

- Azure Load Balancer is layer 4 (TCP/UDP), keeps the client source IP and probes from 168.63.129.16.
- Basic Load Balancer was retired on September 30, 2025 (Learn); Standard is secure by default, zone-aware, supports HTTPS probes, HA ports, outbound rules, TCP reset and metrics.
- HTTP/S probes need HTTP 200; failed instances get no new flows.
- Session persistence: None (5-tuple), Client IP (2-tuple), Client IP and protocol (3-tuple). Idle timeout 4–100 min (default 4); TCP reset optional.
- Floating IP = backend sees the frontend IP (loopback needed). HA ports = internal LB, protocol All, port 0.
- SNAT: 64,000 ports per frontend IP shared across the pool; fix exhaustion with NAT gateway or outbound rules with more IPs.
- L7 regional = Application Gateway; L7 global = Front Door; DNS-based global = Traffic Manager.
