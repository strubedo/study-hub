## diff: three comparisons

After the commits in the previous lesson, `sw01.cfg` was edited (VLAN 20 added), staged, and then edited again (VLAN 30 added) without staging, so the file appears twice in `git status`:

```text
alice@devbox:~/netconfigs$ git status
On branch main
Your branch is ahead of 'origin/main' by 2 commits.
  (use "git push" to publish your local commits)

Changes to be committed:
  (use "git restore --staged <file>..." to unstage)
	modified:   sw01.cfg

Changes not staged for commit:
  (use "git add <file>..." to update what will be committed)
  (use "git restore <file>..." to discard changes in working directory)
	modified:   sw01.cfg

alice@devbox:~/netconfigs$ git diff
diff --git a/sw01.cfg b/sw01.cfg
index 6701f41..a9d2fdc 100644
--- a/sw01.cfg
+++ b/sw01.cfg
@@ -4,3 +4,5 @@ vlan 10
  name USERS
 vlan 20
  name VOICE
+vlan 30
+ name PRINTERS
alice@devbox:~/netconfigs$ git diff --staged
diff --git a/sw01.cfg b/sw01.cfg
index 149054d..6701f41 100644
--- a/sw01.cfg
+++ b/sw01.cfg
@@ -2,3 +2,5 @@ hostname sw01
 !
 vlan 10
  name USERS
+vlan 20
+ name VOICE
```

| Command | Compares | Shows |
|---|---|---|
| `git diff` | Working tree vs staging area | Edits you have **not staged** yet (VLAN 30) |
| `git diff --staged` (same as `--cached`) | Staging area vs last commit (`HEAD`) | What the **next commit** will contain (VLAN 20) |
| `git diff HEAD` | Working tree vs last commit | Everything not yet committed (both) |
| `git diff main..feature/ntp` (same as `git diff main feature/ntp`) | The tip of one branch or commit vs another | How the second differs from the first |

Reading a unified diff: `---` is the old side (`a/`), `+++` the new side (`b/`); `@@ -4,3 +4,5 @@` means "starting at line 4, 3 old lines became 5 new lines"; lines starting with `+` were added, `-` removed, and a space are unchanged context.

## Branch and merge

A branch is a cheap, movable pointer, so create one for every change. `git switch -c` (or the older `git checkout -b`) creates and switches in one step. (Before this, Alice committed both VLAN edits as "Add VLANs 20 and 30" and pushed; on the new branch she appends `ntp server 10.10.20.5` to `sw01.cfg` before committing.)

```text
alice@devbox:~/netconfigs$ git switch -c feature/ntp
Switched to a new branch 'feature/ntp'
alice@devbox:~/netconfigs$ git commit -qam "Add NTP server"
alice@devbox:~/netconfigs$ git diff main..feature/ntp
diff --git a/sw01.cfg b/sw01.cfg
index a9d2fdc..295a302 100644
--- a/sw01.cfg
+++ b/sw01.cfg
@@ -6,3 +6,4 @@ vlan 20
  name VOICE
 vlan 30
  name PRINTERS
+ntp server 10.10.20.5
alice@devbox:~/netconfigs$ git switch main
Switched to branch 'main'
Your branch is up to date with 'origin/main'.
alice@devbox:~/netconfigs$ git merge feature/ntp
Updating bfe9a39..822dd2d
Fast-forward
 sw01.cfg | 1 +
 1 file changed, 1 insertion(+)
alice@devbox:~/netconfigs$ git branch -d feature/ntp
Deleted branch feature/ntp (was 822dd2d).
```

You always merge **into the branch you are on**: switch to `main`, then `git merge feature/ntp`. Because `main` had not moved since the branch was created, Git simply moved the `main` pointer forward to the branch tip: a **fast-forward** merge, with no merge commit. (`git merge --no-ff` forces a merge commit anyway.)

If **both** branches have new commits, Git performs a **three-way merge** (using the two tips and their common ancestor) and records a **merge commit** with two parents:

```text
alice@devbox:~/netconfigs$ git merge --no-edit feature/snmp
Merge made by the 'ort' strategy.
 sw01.cfg | 1 +
 1 file changed, 1 insertion(+)
alice@devbox:~/netconfigs$ git log --oneline --graph -5
*   1cfa8c8 Merge branch 'feature/snmp'
|\  
| * aa27b1a Add SNMP location
* | d619722 Add sw02 placeholder
|/  
* 822dd2d Add NTP server
* bfe9a39 Add VLANs 20 and 30
```

(`ort` is Git's default merge strategy; `--no-edit` accepts the default merge message instead of opening an editor.)

## Merge conflicts

A conflict happens when both branches changed **the same lines** (or one deleted a file the other changed). Here `main` renamed VLAN 10 to EMPLOYEES while `feature/rename-vlan` renamed it to STAFF:

```text
alice@devbox:~/netconfigs$ git merge feature/rename-vlan
Auto-merging sw01.cfg
CONFLICT (content): Merge conflict in sw01.cfg
Automatic merge failed; fix conflicts and then commit the result.
alice@devbox:~/netconfigs$ git status
On branch main
Your branch is ahead of 'origin/main' by 5 commits.
  (use "git push" to publish your local commits)

You have unmerged paths.
  (fix conflicts and run "git commit")
  (use "git merge --abort" to abort the merge)

Unmerged paths:
  (use "git add <file>..." to mark resolution)
	both modified:   sw01.cfg

no changes added to commit (use "git add" and/or "git commit -a")
alice@devbox:~/netconfigs$ cat sw01.cfg
hostname sw01
!
vlan 10
<<<<<<< HEAD
 name EMPLOYEES
=======
 name STAFF
>>>>>>> feature/rename-vlan
vlan 20
 name VOICE
vlan 30
 name PRINTERS
ntp server 10.10.20.5
snmp-server location DC1-ROW3
```

Between `<<<<<<< HEAD` and `=======` is **your current branch's** version (the branch you are merging into, here `main`); between `=======` and `>>>>>>> feature/rename-vlan` is the **incoming** branch's version. Everything outside the markers merged cleanly. In `git status --short` the file shows as `UU` (unmerged, both modified).

To resolve:

1. Open the file and make it say what it should: keep one side, the other, or a combination. **Delete all three marker lines.**
2. `git add sw01.cfg` to mark it resolved.
3. `git commit` to complete the merge (Git proposes the message `Merge branch 'feature/rename-vlan'`).

Here Alice keeps the incoming ` name STAFF` line, so after `git add` the short status shows `M ` (staged, different from `HEAD`). Had she kept her own ` name EMPLOYEES` line, the file would match `HEAD` and `git status --short` would print nothing for it, while `git status` says "All conflicts fixed but you are still merging."

```text
alice@devbox:~/netconfigs$ git add sw01.cfg
alice@devbox:~/netconfigs$ git status --short
M  sw01.cfg
alice@devbox:~/netconfigs$ git commit --no-edit
[main d34459c] Merge branch 'feature/rename-vlan'
alice@devbox:~/netconfigs$ git push
To /home/alice/repos/netconfigs.git
   bfe9a39..d34459c  main -> main
```

To give up instead, `git merge --abort` restores the state before the merge started.

> **Exam tip:** Conflict markers in an exhibit: `HEAD` is the branch you were on when you ran `git merge`; the name after `>>>>>>>` is the branch being merged in. A file is not resolved until you `git add` it, and the merge is not finished until you commit.

## Key takeaways

- `git diff` = working tree vs index (unstaged); `git diff --staged` (`--cached`) = index vs `HEAD` (the next commit); `git diff a..b` = between two branches or commits, same as `git diff a b`.
- A branch is a movable pointer; `git switch -c name` (or `git checkout -b name`) creates and switches; you merge **into** the branch you are on.
- Fast-forward: the current branch had no new commits, so the pointer just moves and no merge commit is made. Three-way: both moved; Git makes a merge commit with two parents.
- Conflict markers: `<<<<<<< HEAD` (current branch), `=======`, `>>>>>>> other-branch` (incoming); `UU` in short status.
- Resolve: edit the file, remove the markers, `git add`, `git commit`; or `git merge --abort` to start over.
