## From one long script to organised code

Most automation starts as one file that logs in, pulls data and prints it, top to bottom. That works until you copy the same twenty lines for the second switch, the third API and the fourth colleague. Python gives you three levels of organisation, and the exam asks why each helps:

| Level | What it groups | Main benefits |
|---|---|---|
| **Function** (a **method** when it belongs to a class) | A block of statements behind a name, with inputs (parameters) and an output (return value) | Reuse, no duplication, readability, testability, one place to fix a bug |
| **Class** | Data (attributes) and the functions that act on it (methods) | Models a real thing (a device, a session), keeps state together, encapsulation, many instances from one definition, inheritance |
| **Module** (and **package**) | Functions, classes and constants in a `.py` file (a package is a directory of modules) | Reuse across scripts, namespaces that prevent name clashes, separate files that people can own, test and version independently |

All output below was produced by running the code with Python 3.14.

## Functions

Here is the "before": the same logic pasted twice, with the second copy already drifting from the first.

```python
devices = [{"hostname": "sw01", "vlans": [10, 20]}, {"hostname": "sw02", "vlans": [10]}]

print("sw01 VLANs:", ", ".join(str(v) for v in devices[0]["vlans"]))
print("SW02 vlans: " + ", ".join(str(v) for v in devices[1]["vlans"]))
```

And the "after":

```python
def vlan_summary(device):
    """Return 'hostname VLANs: 10, 20' for one inventory record."""
    vlans = ", ".join(str(v) for v in device["vlans"])
    return f"{device['hostname']} VLANs: {vlans}"


for device in devices:
    print(vlan_summary(device))
```

The benefits are exactly what Cisco's topic wording asks you to explain:

- **Reuse (DRY, "don't repeat yourself").** Write it once, call it everywhere. Fix a bug or change the format in one place.
- **Abstraction and readability.** The loop reads as "print a VLAN summary for each device"; the details live in one named block with a docstring.
- **Testability.** A function with inputs and a return value can be unit-tested in isolation (lesson 1.3). `vlan_summary` returns a string rather than printing, which is what makes it easy to test.
- **Scope.** Variables created inside a function are local, so they cannot accidentally overwrite names elsewhere.

Parameters can have defaults (`def connect(host, port=830)`), and callers can pass by keyword (`connect("sw01", port=22)`), which keeps calls self-documenting.

## Classes and objects

A **class** is a blueprint; each **object** (instance) created from it has its own data. Functions defined inside a class are **methods**, and receive the instance as their first parameter, by convention `self`. `__init__` runs when an instance is created.

```python
class Switch:
    vendor = "Cisco"

    def __init__(self, hostname, ports=48):
        self.hostname = hostname
        self.ports = ports
        self.vlans = []

    def add_vlan(self, vlan_id):
        if vlan_id not in self.vlans:
            self.vlans.append(vlan_id)
        return len(self.vlans)


sw1 = Switch("sw01")
sw2 = Switch("sw02", ports=24)
sw1.add_vlan(10)
print(sw1.add_vlan(10), sw1.add_vlan(20))
print(sw2.ports, sw2.vlans, Switch.vendor, sw2.vendor)
```

```text
1 2
24 [] Cisco Cisco
```

Read the output carefully: adding VLAN 10 a second time does not duplicate it (the method enforces a rule), so the count stays 1; adding 20 makes it 2. `sw2` has its own empty `vlans` list, because `self.vlans` is an **instance attribute** created in `__init__`. `vendor` is a **class attribute**, shared by every instance and readable through the class or any instance.

Why organise code into classes?

- **Data and behaviour together.** The VLAN list and the rule that prevents duplicates live in one place; callers use `add_vlan()` instead of manipulating the list directly. This is **encapsulation**: the object protects its own state. (Python has no enforced `private`; a leading underscore, as in `self._vlans`, marks something as internal by convention.)
- **Many independent instances.** One class, a thousand switch objects, each with its own state.
- **Inheritance.** `class NexusSwitch(Switch):` reuses everything in `Switch` and overrides or adds only what differs. Polymorphism means calling code can treat both the same way.
- **A natural model of the domain.** SDKs you meet in domain 3 are built this way: you create a client or session object once (holding the base URL, credentials and HTTP session) and call methods on it.

## Modules and packages

A **module** is simply a `.py` file. `import inventory` runs `inventory.py` once and gives you a namespace (`inventory.SITE`, `inventory.device_count`); `from inventory import device_count` binds one name directly. A **package** is a directory of modules (traditionally with an `__init__.py`), imported as `import mytools.parsers`.

Two files in one folder:

```python
# inventory.py
SITE = "dc1"


def device_count(devices):
    return len(devices)


print("inventory loaded")

if __name__ == "__main__":
    print("running as a script")
```

```python
# report.py
import inventory
from inventory import device_count

print(inventory.SITE, device_count(["sw01", "sw02"]))
print(__name__, inventory.__name__)
```

```text
alice@devbox:~/modtest$ python3 report.py
inventory loaded
dc1 2
__main__ inventory
alice@devbox:~/modtest$ python3 inventory.py
inventory loaded
running as a script
```

Three lessons in that output:

1. Module-level code runs **once**, on first import. `inventory` was imported twice but printed "inventory loaded" once, because Python caches imported modules in `sys.modules`.
2. `__name__` is `"__main__"` in the file you run directly and the module's name (`"inventory"`) when it is imported. The `if __name__ == "__main__":` guard lets one file be both an importable library and a runnable script, without the script part running on import.
3. Top-level side effects such as `print` (or, worse, connecting to a device) in a module run on every import, which is why well-behaved modules keep that work inside functions or the main guard.

Benefits of modules:

- **Reuse across scripts and people.** Your parsing helpers live in one module that every script imports.
- **Namespaces.** `inventory.device_count` and `audit.device_count` can coexist without clashing.
- **Maintainability and collaboration.** Smaller files with one purpose are easier to read, review, test and change; different people can own different modules, and Git diffs stay focused.
- **Ecosystem.** The standard library (`json`, `xml.etree.ElementTree`, `unittest`) and third-party packages (`requests`, `ncclient`, `netmiko`, Cisco SDKs) are themselves modules and packages you install with `pip`.

> **Exam tip:** If a question asks for the benefit of a function, think *reuse and less duplication*; of a class, think *bundling state with behaviour, multiple instances, inheritance*; of a module, think *reuse across programs, namespaces and separate files that can be maintained independently*.

## Key takeaways

- Functions: name a reusable block with parameters and a return value; less duplication, one place to fix, easier to read and test. A function defined in a class is a method.
- Classes: bundle state (attributes) with behaviour (methods); `__init__` sets up each instance, `self` is the instance, class attributes are shared, instance attributes are per object; inheritance reuses and extends.
- Modules: a `.py` file imported by name; packages are directories of modules. They give reuse across programs, namespaces and independently maintained files.
- A module's top-level code runs once, on first import; `if __name__ == "__main__":` runs code only when the file is executed directly.
