## What test-driven development is

**Test-driven development (TDD)** is a way of writing code in which you write an automated test for a small piece of behaviour **before** you write the code that provides it. You then write just enough code to make that test pass, clean the code up, and repeat. Kent Beck popularised it as part of Extreme Programming. The point is not "having tests" (any method can have tests); it is that **the test comes first and drives the design**.

The loop has three steps, usually named after the colours a test runner shows:

| Step | What you do | What you expect to see |
|---|---|---|
| **Red** | Write one small test for behaviour that does not exist yet, and run it | The new test **fails** (or errors because the function does not exist). A test that passes now proves nothing. |
| **Green** | Write the **simplest** code that makes the test pass, nothing more | All tests pass |
| **Refactor** | Improve the code (names, duplication, structure) without changing behaviour | All tests **still** pass |

Then you pick the next small behaviour and go round again. Each cycle takes minutes, not days.

> **Exam tip:** The order is red, green, refactor. "Write the code, then write tests for it" is test-*after* development, not TDD. And the first run of a new test is expected to **fail**: that failure shows the test can actually detect the missing behaviour.

## A worked cycle with `unittest`

Say you need a helper that expands short Cisco interface names (`Gi1/0/1`) to full ones (`GigabitEthernet1/0/1`) before you compare them with what a RESTCONF reply returns. Python's built-in **`unittest`** framework is enough (domain 4 covers writing unit tests in more depth). A test case is a class that subclasses `unittest.TestCase`; each method whose name starts with `test` is one test; assertion methods such as `assertEqual`, `assertTrue` and `assertRaises` check results.

**Red: write the tests first.** `test_netutils.py`:

```python
import unittest

from netutils import expand_intf


class TestExpandIntf(unittest.TestCase):
    def test_gigabit(self):
        self.assertEqual(expand_intf("Gi1/0/1"), "GigabitEthernet1/0/1")

    def test_tengig(self):
        self.assertEqual(expand_intf("Te1/1/1"), "TenGigabitEthernet1/1/1")


if __name__ == "__main__":
    unittest.main()
```

The progress line `.F` means one pass (`.`) and one failure (`F`); an error would be `E`. Note the difference unittest draws: a **failure** is an assertion that did not hold, an **error** is any other exception (here, the import).

**Green: make it pass.**

```python
PREFIXES = {
    "Gi": "GigabitEthernet",
    "Te": "TenGigabitEthernet",
}


def expand_intf(name):
    """Expand a short Cisco interface name such as Gi1/0/1."""
    for short, full in PREFIXES.items():
        if name.startswith(short) and not name.startswith(full):
            return full + name[len(short):]
    return name
```

**Refactor.** With the tests green you can safely restructure, for example adding `Fa`, `Hu` or `Po` to the table, or moving `PREFIXES` to a shared module, rerunning the tests after each change. If a refactor breaks something, the suite tells you within seconds.

The next cycle starts with another failing test: what should `expand_intf("gi1/0/1")` (lower case) return? Writing that test forces you to decide the behaviour before you code it.

## Why teams use TDD

- **Requirements become executable.** Each test is a precise statement of what the code must do, written while the requirement is fresh. Tests double as usage examples.
- **Fast feedback and fewer regressions.** The suite runs on every change (and in CI on every push), so a change that breaks old behaviour is caught immediately instead of in a maintenance window.
- **Confidence to refactor.** You can clean up code because the tests prove behaviour did not change.
- **Better design.** Code that is easy to test tends to be made of small functions with clear inputs and outputs and few hidden dependencies, which is also code that is easy to reuse.
- **High test coverage as a by-product.** Every piece of behaviour exists because a test demanded it.

The costs are real too: more code to write up front, tests that must be maintained when requirements change, and a learning curve. Tests that call real devices or APIs are slow and fragile, so unit tests usually replace those dependencies with **mocks** or recorded responses (`unittest.mock` in the standard library) and keep the network for separate integration tests.

> **Real world:** TDD fits network automation well. Parsing a `show` command, normalising interface names, building a RESTCONF payload or validating an inventory file are all pure functions you can test with a saved sample of device output, without touching a device.

## Lab it yourself

Any computer with Python 3; no network or extra packages needed.

1. Create a folder with `test_netutils.py` exactly as above and run `python -m unittest -v` (`python3` on macOS and Linux). Confirm you get an error, which is your red.
2. Write the one-line `replace()` version of `netutils.py`, run again, and read the `.F` result.
3. Write the dictionary version, run again and get `OK`.
4. Add a red test of your own, for example that `expand_intf("Po10")` returns `"Port-channel10"`. See it fail, make it pass, then refactor.
5. Add a test that `expand_intf("")` returns `""`, and decide whether a `None` input should raise `TypeError` (`self.assertRaises(TypeError, expand_intf, None)`).

## Key takeaways

- TDD writes the test **before** the code: red (failing test), green (simplest code that passes), refactor (clean up with tests still passing), repeat in small steps.
- A new test should fail first; if it passes immediately it is not testing new behaviour.
- In `unittest`, tests are `test_*` methods on a `unittest.TestCase` subclass; `.` = pass, `F` = failed assertion, `E` = error (another exception).
- Benefits: executable requirements, fast feedback, safe refactoring, testable modular design, built-in regression suite.
- Costs: up-front effort and test maintenance; isolate devices and APIs with mocks so unit tests stay fast and repeatable.
