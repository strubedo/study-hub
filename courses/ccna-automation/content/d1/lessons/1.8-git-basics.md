## The everyday Git workflow

This lesson walks one repository, `netconfigs`, through every operation in exam topic 1.8: clone, add and remove, commit, push and pull, branch, merge (including conflicts) and diff. All output is real (Git 2.55 in a throwaway directory). The shared "server" is a bare repository at `/home/alice/repos/netconfigs.git`; with GitHub or GitLab only the URL changes. Your commit hashes will differ.

| Task | Command |
|---|---|
| Copy a remote repository | `git clone <url> [dir]` |
| Start a new repository | `git init` |
| See what changed | `git status`, `git status --short` |
| Stage new or changed files | `git add <file>`, `git add .` |
| Delete a file and stage the deletion | `git rm <file>` |
| Stop tracking but keep the file on disk | `git rm --cached <file>` |
| Unstage (keep the edit) | `git restore --staged <file>` |
| Record the staged snapshot | `git commit -m "message"` |
| Upload commits | `git push`, first time `git push -u origin <branch>` |
| Download only | `git fetch` |
| Download and integrate | `git pull` (= fetch + merge, or rebase) |
| Branches | `git branch`, `git branch <name>`, `git switch <name>` / `git checkout <name>`, `git switch -c <name>` / `git checkout -b <name>`, `git branch -d <name>` |
| Merge another branch into the current one | `git merge <branch>` |
| Compare | `git diff`, `git diff --staged`, `git diff <a>..<b>` |
| History | `git log --oneline --graph` |

## Clone

`git clone` copies the whole repository, history included, creates a **remote named `origin`** that points at the source URL, and checks out the remote's default branch.

```text
alice@devbox:~$ git clone /home/alice/repos/netconfigs.git netconfigs
Cloning into 'netconfigs'...
warning: You appear to have cloned an empty repository.
done.
alice@devbox:~$ cd netconfigs
```

(Cloning an empty repository warns; cloning one with commits just prints `Cloning into...` and `done.`) Here is what a clone of the repository looks like once it has commits on `main`, made later by a colleague, Bob, in his own clone:

```text
bob@devbox:~/netconfigs$ git remote -v
origin	/home/alice/repos/netconfigs.git (fetch)
origin	/home/alice/repos/netconfigs.git (push)
bob@devbox:~/netconfigs$ git branch -a
* main
  remotes/origin/HEAD -> origin/main
  remotes/origin/main
```

**main or master?** A clone takes whatever default branch the remote has. A brand-new repository from `git init` uses the `init.defaultBranch` setting; if that is not set, Git 2.x still uses **`master`** and prints a hint (Git's documentation says the default will change to `main` in Git 3.0). GitHub and GitLab create new repositories with `main`. So never assume: check with `git branch` or `git status`.

```text
alice@devbox:~/plain$ git init
hint: Using 'master' as the name for the initial branch. This default branch name
hint: will change to "main" in Git 3.0. To configure the initial branch name
...
Initialized empty Git repository in /home/alice/plain/.git/
alice@devbox:~/plain$ git config --global init.defaultBranch main     # choose main for future repos
```

## Add, commit and push

```text
alice@devbox:~/netconfigs$ git status
On branch main

No commits yet

Untracked files:
  (use "git add <file>..." to include in what will be committed)
	README.md
	sw01.cfg

nothing added to commit but untracked files present (use "git add" to track)
alice@devbox:~/netconfigs$ git add sw01.cfg README.md
alice@devbox:~/netconfigs$ git status --short
A  README.md
A  sw01.cfg
alice@devbox:~/netconfigs$ git commit -m "Add sw01 baseline config"
[main (root-commit) ba44c21] Add sw01 baseline config
 2 files changed, 5 insertions(+)
 create mode 100644 README.md
 create mode 100644 sw01.cfg
alice@devbox:~/netconfigs$ git push -u origin main
To /home/alice/repos/netconfigs.git
 * [new branch]      main -> main
branch 'main' set up to track 'origin/main'.
```

`git add` copies the file's current content into the staging area; edit the file again after adding and you must add again. In `git status --short` the **left** column is the staging area and the **right** column the working tree: `A ` new and staged, `M ` modified and staged, ` M` modified but not staged, `??` untracked. `-u` (`--set-upstream`) on the first push links local `main` to `origin/main`, so later a bare `git push` or `git pull` knows where to go. `git commit -a` stages modified *tracked* files and commits in one step (it does not add new files).

## Remove: `git rm` vs `git rm --cached`

In the next commit (not shown) Alice committed `old-notes.txt` and, by mistake, `secrets.txt`. She now wants the first gone completely and the second kept on her disk but out of the repository:

```text
alice@devbox:~/netconfigs$ git rm old-notes.txt
rm 'old-notes.txt'
alice@devbox:~/netconfigs$ git rm --cached secrets.txt
rm 'secrets.txt'
alice@devbox:~/netconfigs$ git status
On branch main
Your branch is ahead of 'origin/main' by 1 commit.
  (use "git push" to publish your local commits)

Changes to be committed:
  (use "git restore --staged <file>..." to unstage)
	deleted:    old-notes.txt
	deleted:    secrets.txt

Untracked files:
  (use "git add <file>..." to include in what will be committed)
	secrets.txt

alice@devbox:~/netconfigs$ ls
README.md
secrets.txt
sw01.cfg
alice@devbox:~/netconfigs$ echo secrets.txt > .gitignore
alice@devbox:~/netconfigs$ git add .gitignore
alice@devbox:~/netconfigs$ git commit -m "Remove old notes, stop tracking secrets.txt"
[main de79f11] Remove old notes, stop tracking secrets.txt
 3 files changed, 1 insertion(+), 2 deletions(-)
 create mode 100644 .gitignore
 delete mode 100644 old-notes.txt
 delete mode 100644 secrets.txt
```

- **`git rm file`** deletes the file from the working tree **and** stages the deletion.
- **`git rm --cached file`** removes it **from the index only**: the file stays on disk, now untracked. Pair it with `.gitignore` so it is not added again.
- Deleting a file with your OS (`rm`, Explorer) and then `git add file` (or `git add -A`) also stages a deletion.
- `git restore --staged file` is the opposite of `git add`: it unstages without touching your edit.

> **Watch out:** `git rm --cached` stops tracking from the next commit onward. The earlier commit that contained `secrets.txt` is still in the history, and it reaches the remote with Alice's next push (or is already there if it was pushed), so rotate the secret.

## Fetch vs pull, and a rejected push

Later (after the branch work in the next lesson), a colleague, Bob, pushed a commit ("Add syslog server") to the same remote, and Alice committed a change of her own. Her push is refused because it would discard Bob's commit:

```text
alice@devbox:~/netconfigs$ git push
To /home/alice/repos/netconfigs.git
 ! [rejected]        main -> main (fetch first)
error: failed to push some refs to '/home/alice/repos/netconfigs.git'
hint: Updates were rejected because the remote contains work that you do not
hint: have locally. This is usually caused by another repository pushing to
hint: the same ref. If you want to integrate the remote changes, use
hint: 'git pull' before pushing again.
hint: See the 'Note about fast-forwards' in 'git push --help' for details.
alice@devbox:~/netconfigs$ git fetch
From /home/alice/repos/netconfigs
   d34459c..f9f8155  main       -> origin/main
alice@devbox:~/netconfigs$ git status -sb
## main...origin/main [ahead 1, behind 1]
alice@devbox:~/netconfigs$ git log --oneline main..origin/main
f9f8155 Add syslog server
alice@devbox:~/netconfigs$ git pull --no-rebase --no-edit
Merge made by the 'ort' strategy.
 sw01.cfg | 1 +
 1 file changed, 1 insertion(+)
alice@devbox:~/netconfigs$ git push
To /home/alice/repos/netconfigs.git
   f9f8155..69eaad7  main -> main
```

- **`git fetch`** downloads new commits and updates the **remote-tracking branches** (`origin/main`) only. Your `main` and your files are untouched, so it is always safe; inspect with `git log main..origin/main` (commits on `origin/main` that `main` lacks).
- **`git pull`** is `git fetch` **followed by integrating** the upstream branch into your current branch: a merge with `--no-rebase`, or a rebase with `--rebase`. With neither option and no `pull.*` setting, current Git only fast-forwards (the git-pull documentation lists `--ff-only` as the default); older Git versions merged by default.
- So when both sides have new commits, current Git refuses a plain `git pull` until you choose: it prints `fatal: Need to specify how to reconcile divergent branches.` and suggests `git config pull.rebase false` (merge), `pull.rebase true` (rebase) or `pull.ff only`. Pass `--no-rebase`, `--rebase` or `--ff-only`, or set the option once.
- **`git push`** uploads your commits and moves the remote branch, but only as a fast-forward; a rejected push means "pull first". `git push --force` overwrites the remote branch and destroys other people's commits; avoid it on shared branches.

## Lab it yourself

Any computer with Git (Linux, macOS, or Git for Windows / WSL 2); everything is local, no account needed:

1. `git init --bare ~/lab/netconfigs.git`, then `git clone ~/lab/netconfigs.git ~/lab/alice` and again to `~/lab/bob` (on Windows use paths such as `C:/lab/...`). In each clone set `user.name` and `user.email` with `git config` (no `--global`), and run `git remote -v`.
2. In `alice`, add a config file, check `git status` and `git status --short` before and after `git add`, commit, and `git push -u origin main` (if your branch is called `master`, either push `master` or rename it with `git branch -m main`).
3. Commit a `secrets.txt` by mistake, then fix it with `git rm --cached secrets.txt`, a `.gitignore` entry and a commit; confirm with `ls` that the file is still on disk and with `git log --stat` that it is still in the earlier commit.
4. Delete another file with `git rm` and compare.
5. Commit and push from `bob`, then commit in `alice` and push to see the rejection; `git fetch`, `git status -sb`, `git log main..origin/main`, then try a plain `git pull` (note the divergent-branches message) and `git pull --no-rebase`, and push again.

## Key takeaways

- `git clone` copies the full history, names the source remote `origin` and checks out its default branch; `git init` uses `init.defaultBranch` or falls back to `master` (with a hint) in Git 2.x.
- `git add` stages, `git commit` records the staged snapshot, `git push` uploads (`-u origin <branch>` the first time sets the upstream).
- `git status --short`: left column = staging area, right column = working tree (`A `, `M `, ` M`, `??`).
- `git rm` deletes and stages the deletion; `git rm --cached` untracks but keeps the file; history still holds committed secrets, so rotate them.
- `git fetch` only downloads to `origin/*`; `git pull` = fetch + merge (or rebase); with divergent branches you must choose `--no-rebase`, `--rebase` or `--ff-only` (or set `pull.rebase`).
- A push is rejected when the remote has commits you do not have: fetch or pull, then push again. Avoid `--force` on shared branches.
