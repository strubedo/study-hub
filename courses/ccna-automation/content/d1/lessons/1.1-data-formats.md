## Why three formats?

Every API you will touch on this exam sends structured data: a Meraki Dashboard API v1 reply, a RESTCONF reply from IOS XE, a NETCONF `<rpc-reply>`, an Ansible inventory. Underneath they all describe the same few things: **key/value pairs**, **ordered lists**, and **scalars** (strings, numbers, booleans, null). XML, JSON and YAML are three ways of writing those structures as text.

| | XML | JSON | YAML |
|---|---|---|---|
| Full name | Extensible Markup Language (W3C XML 1.0) | JavaScript Object Notation (RFC 8259) | YAML Ain't Markup Language (YAML 1.2.2 spec) |
| Structure from | Nested start and end tags | Braces `{}` and brackets `[]` | Indentation with spaces (plus optional `{}` / `[]` flow style) |
| Comments | `<!-- like this -->` | **None** | `# to end of line` |
| Data types | None built in: everything is text unless a schema (XSD, YANG) says otherwise | object, array, string, number, `true`, `false`, `null` | Mappings, sequences, scalars; plain scalars are resolved to int, float, bool, null or string |
| Where you meet it | NETCONF (RFC 6241), SOAP-era APIs such as CUCM AXL, RESTCONF with `application/yang-data+xml` | Almost every REST API (Meraki, Catalyst Center, Webex), RESTCONF with `application/yang-data+json` | Ansible playbooks and inventories, Docker Compose, CI pipeline files, Kubernetes manifests |
| Strength | Attributes, namespaces, mature schema and validation tooling | Simple, strict, maps directly onto programming-language types | Easiest for humans to read and write, supports comments |
| Weakness | Verbose | No comments, unforgiving punctuation | Whitespace-sensitive; implicit typing surprises |

## The same switch, three ways

Here is one inventory record for access switch `sw01` in each format. Read them side by side; the questions on this topic usually hand you one of these and ask what is valid or what a field means.

**JSON**

```json
{
  "hostname": "sw01",
  "mgmt_ip": "10.10.20.11",
  "model": "C9300-48P",
  "managed": true,
  "uptime_days": 42,
  "cpu_load": 7.5,
  "location": null,
  "interfaces": [
    {"name": "GigabitEthernet1/0/1", "enabled": true, "vlan": 10},
    {"name": "GigabitEthernet1/0/2", "enabled": false, "vlan": 20}
  ]
}
```

**YAML**

```yaml
---
# Inventory record for one access switch
hostname: sw01
mgmt_ip: 10.10.20.11
model: C9300-48P
managed: true
uptime_days: 42
cpu_load: 7.5
location: null
interfaces:
  - name: GigabitEthernet1/0/1
    enabled: true
    vlan: 10
  - name: GigabitEthernet1/0/2
    enabled: false
    vlan: 20
```

**XML**

```xml
<?xml version="1.0" encoding="UTF-8"?>
<device managed="true">
  <hostname>sw01</hostname>
  <mgmt_ip>10.10.20.11</mgmt_ip>
  <model>C9300-48P</model>
  <uptime_days>42</uptime_days>
  <cpu_load>7.5</cpu_load>
  <location/>
  <interfaces>
    <interface name="GigabitEthernet1/0/1" enabled="true">
      <vlan>10</vlan>
    </interface>
    <interface name="GigabitEthernet1/0/2" enabled="false">
      <vlan>20</vlan>
    </interface>
  </interfaces>
</device>
```

Notice what changes. JSON and YAML have a real list (`[...]` or `- ` items). XML has no list type: a list is simply **repeated sibling elements** with the same name, usually wrapped in a container element (`<interfaces>`). JSON and YAML know that `42` is a number and `true` is a boolean; in XML, `42` and `true` are just characters until something (a schema, a YANG model, your code) interprets them. XML also lets you choose between child **elements** and **attributes**, which the other two formats do not have.

## JSON rules that trip people up

RFC 8259 defines a small grammar, and parsers enforce it exactly:

- A JSON text is one value; in APIs it is nearly always an **object** `{}` or an **array** `[]`.
- Object **keys are always strings in double quotes**. `{'hostname': 'sw01'}` (single quotes) is a Python dict literal, not JSON.
- Strings use **double quotes only**; escape `"` and `\` with a backslash.
- **No comments** of any kind. `//` and `#` are syntax errors.
- **No trailing commas**: `[10, 20,]` and `{"a": 1,}` are invalid.
- Literals are lowercase: `true`, `false`, `null`. `True`, `None` and `NULL` are invalid.
- Numbers are decimal, with no leading zeros (`010` is invalid) and no `NaN` or `Infinity`. JSON does not distinguish integer from float types; `7.5` and `42` are both "number".
- Names within an object **SHOULD be unique** (RFC 8259 section 4); with duplicates, behaviour is unpredictable (Python keeps the last one).
- Whitespace between tokens is insignificant, so a one-line response and a pretty-printed one are the same document.

Python's parser reports each mistake precisely (Python 3.14 output):

```text
{"hostname": "sw01", "vlans": [10, 20],}       -> Illegal trailing comma before end of object: line 1 column 39 (char 38)
{'hostname': 'sw01'}                           -> Expecting property name enclosed in double quotes: line 1 column 2 (char 1)
{"managed": True}                              -> Expecting value: line 1 column 13 (char 12)
{"vlan": 010}                                  -> Expecting ',' delimiter: line 1 column 11 (char 10)
```

> **Exam tip:** If an exhibit shows JSON with single quotes, `True`/`None`, a comment or a trailing comma, it is not valid JSON. If it shows `True` and `None`, you are probably looking at a printed Python dict.

## YAML rules that trip people up

- **Indentation is the structure.** Use spaces only: the YAML spec forbids tab characters in indentation. Children must be indented more than their parent, and siblings exactly the same amount.
- `key: value` needs a **space after the colon**. A plain (unquoted) value cannot itself contain `": "`, so `description: Uplink: core` is a parse error; quote it: `description: "Uplink: core"`.
- `- ` starts a **sequence** (list) item. A list item can itself be a mapping, as in `interfaces` above.
- **Scalars are typed by how they look.** `10` is an integer, `7.5` a float, `true` a boolean, `null` or `~` (or an empty value) null, and almost anything else a string. Quote a value to force a string: `vlan: "10"`.
- **The "Norway problem".** YAML 1.1 treated words such as `yes`, `no`, `on` and `off` (in several capitalisations) as booleans, so `country: NO` became `false`. YAML 1.2's core schema dropped that: only `true`/`false` (and `True`, `TRUE`, `False`, `FALSE`) are booleans. But the most widely used Python library, **PyYAML, implements YAML 1.1**, so in Python `no`, `on` and `off` still turn into booleans. The next lesson shows the real output. Quote values like `"no"`, version strings like `"17.10"` and IDs with leading zeros.
- `---` marks the start of a document (optional for one document; one file can hold several). `...` can end one.
- Flow style is allowed too: `vlans: [10, 20]` and `ntp: {server: 10.10.20.5, prefer: true}`. Because of this, a JSON document is also valid YAML 1.2 in practice (the 1.2.2 spec says the primary focus of YAML 1.2 was making YAML a strict superset of JSON).
- **Multi-line strings:** `|` keeps newlines (literal block, good for a banner), `>` folds lines into spaces.
- **Anchors and aliases** (`&name` and `*name`) let you reuse a block, and the merge key `<<: *name` copies a mapping in. You only need to recognise them.

> **Watch out:** YAML is a superset of JSON, not the reverse. Comments, anchors and indentation-based structure have no JSON equivalent, so converting YAML to JSON loses comments.

## XML rules that trip people up

A document that follows the W3C rules is **well-formed**; one that also matches a schema (XSD, DTD, or a YANG model in NETCONF) is **valid**. Parsers refuse documents that are not well-formed.

- Exactly **one root element** wraps everything (`<device>` above). Two top-level elements is an error ("junk after document element").
- Every start tag has a matching end tag, or is self-closing (`<location/>`). Elements must **nest properly**: `<a><b></a></b>` is invalid.
- Names are **case-sensitive**: `<Hostname>sw01</hostname>` is a mismatched tag.
- Attribute values are always **quoted** (single or double): `name="Gi1/0/1"`.
- `<` and `&` cannot appear raw in text; write `&lt;` and `&amp;` (`R&amp;D lab`).
- The XML declaration `<?xml version="1.0" encoding="UTF-8"?>` is optional but, if present, must be first.

**Elements vs attributes.** An attribute is a name/value pair inside a start tag; it holds one string and cannot contain child structure or repeat. An element can contain text, other elements, or both, and can repeat. A common convention is to use attributes for metadata or identifiers (`name="..."`) and elements for data, but nothing forces it. In NETCONF and YANG-modelled XML, data is almost always in elements; attributes carry protocol information such as `message-id` and `operation="delete"`.

**Namespaces.** Two vendors can both define an `<interface>` element. A namespace, declared with `xmlns`, ties element names to a URI so they cannot collide:

```xml
<interfaces xmlns="urn:ietf:params:xml:ns:yang:ietf-interfaces">
  <interface>
    <name>GigabitEthernet1</name>
  </interface>
</interfaces>
```

`xmlns="..."` sets the **default** namespace for that element and its descendants; `xmlns:ios="..."` binds a **prefix**, used as `<ios:interface>`. The URI is an identifier, not a web page that is fetched. NETCONF uses `urn:ietf:params:xml:ns:netconf:base:1.0` for its own elements and each YANG module's namespace for the data.

## Lab it yourself

Works on Windows, macOS and Linux with the Python 3 install from the Exam guide lab; no network needed.

1. Save the three `sw01` documents above as `device.json`, `device.yaml` and `device.xml`.
2. Check the JSON: `python -m json.tool device.json` (use `python3` on macOS and Linux). Then add a trailing comma or a `// comment` and run it again to read the error.
3. Check the XML: `python -c "import xml.etree.ElementTree as ET; ET.parse('device.xml'); print('well-formed')"`. Change `<hostname>` to `<Hostname>` on one side only and run again.
4. If you have PyYAML (`pip install pyyaml` in a virtual environment), run `python -c "import yaml; print(yaml.safe_load(open('device.yaml')))"`, then replace two spaces of indentation with a tab and compare the error.
5. In a RESTCONF-capable DevNet Sandbox (IOS XE), request the same resource with `Accept: application/yang-data+json` and then `application/yang-data+xml` and compare the two bodies.

## Key takeaways

- All three formats express mappings, lists and scalars; XML has no native list or types, JSON and YAML do.
- JSON (RFC 8259): double-quoted keys and strings, lowercase `true`/`false`/`null`, no comments, no trailing commas.
- YAML: indentation with spaces (never tabs), `key: value` with a space, `- ` for list items, `#` comments, quote anything ambiguous.
- PyYAML follows YAML 1.1, so `yes`/`no`/`on`/`off` become booleans in Python (the Norway problem); YAML 1.2 only treats `true`/`false` as booleans.
- XML must be well-formed: one root, matching case-sensitive tags, proper nesting, quoted attributes, escaped `<` and `&`.
- Attributes hold single string values in the start tag; elements can nest and repeat. Namespaces (`xmlns`) keep names from different models apart.
- JSON dominates REST APIs, XML dominates NETCONF, YAML dominates Ansible and CI files.
