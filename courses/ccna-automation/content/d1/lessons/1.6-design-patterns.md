## What a design pattern is

A **design pattern** is a named, reusable solution to a problem that keeps coming up in software design. It is not a library you install; it is a shape for your code that other developers recognise. The idea was popularised by the 1994 "Gang of Four" book *Design Patterns: Elements of Reusable Object-Oriented Software*, which catalogued 23 patterns, including **Observer**. **MVC** (Model-View-Controller) is older still, from Smalltalk in the late 1970s, and is usually called an architectural pattern because it shapes a whole application.

Why use patterns at all?

- **Proven solutions.** You reuse a design that has been tested by many teams instead of inventing one under pressure.
- **Shared vocabulary.** "The alerting is an observer on the device model" says a great deal in one sentence to anyone who knows the pattern.
- **Loose coupling and separation of concerns**, which is what both patterns in this lesson are about: parts of the program depend on each other as little as possible, so you can change, replace or test one part without rewriting the others.

The exam asks for the **advantages** of MVC and Observer, so focus on what problem each one solves.

## MVC: Model, View, Controller

MVC splits an application with a user interface into three roles:

| Component | Responsibility | Must not |
|---|---|---|
| **Model** | The data and the business rules: device inventory, validation ("hostname required"), reading and writing the database or API | Know how the data is displayed |
| **View** | Presentation: renders the model's data for the user (HTML page, CLI table, JSON output) | Contain business rules or change data itself |
| **Controller** | Handles input (a web request, a button, a CLI command), tells the model what to do, and chooses which view to render | Hold the data or format the output |

A typical request flow in a web application:

```text
user ---(HTTP request: add sw02)---> Controller
Controller ---(add("sw02", ip))----> Model      (validates, stores)
Controller ---(get all devices)----> Model
Controller ---(devices)------------> View       (renders a table)
View ------(HTML/text response)----> user
```

Variants differ in whether the view reads the model directly or the controller passes data to it, but the separation is the same. Many web frameworks are organised this way: Django calls its version MTV (model, template, view), and Flask applications are often structured as models, templates and route handlers.

A minimal Python illustration:

```python
# Model: data and rules, no printing
class InventoryModel:
    def __init__(self):
        self._devices = {}

    def add(self, hostname, ip):
        if not hostname:
            raise ValueError("hostname required")
        self._devices[hostname] = ip

    def all(self):
        return dict(self._devices)


# View: presentation only
class TextView:
    def show(self, devices):
        for name, ip in sorted(devices.items()):
            print(f"{name:<8}{ip}")


# Controller: takes input, updates the model, picks the view
class InventoryController:
    def __init__(self, model, view):
        self.model = model
        self.view = view

    def add_device(self, hostname, ip):
        self.model.add(hostname, ip)
        self.view.show(self.model.all())


app = InventoryController(InventoryModel(), TextView())
app.add_device("sw02", "10.10.20.12")
app.add_device("rtr01", "10.10.20.1")
```

```text
sw02    10.10.20.12
rtr01   10.10.20.1
sw02    10.10.20.12
```

(The second call re-renders the whole table, sorted, so `rtr01` appears before `sw02`.)

**Advantages of MVC:**

- **Separation of concerns.** Each component has one job, so code is easier to understand and change.
- **Multiple views of the same model.** Swap `TextView` for an `HtmlView` or a `JsonView` (for an API) without touching the model or its rules.
- **Parallel development.** A front-end developer can work on views while someone else works on the model.
- **Testability.** The model's rules can be unit-tested without any UI; the view can be tested with fake data.
- **Reuse.** The same model serves a web UI, a REST API and a CLI tool.

## Observer: publish and subscribe inside a program

The **Observer** pattern defines a one-to-many relationship: when one object (the **subject**, sometimes called the observable or publisher) changes state, all registered **observers** (subscribers) are notified automatically. The subject keeps a list of observers and calls a known method on each; it does not need to know what they are or what they do.

```python
class Device:
    """Subject: keeps a list of observers and notifies them of changes."""

    def __init__(self, hostname):
        self.hostname = hostname
        self.status = "up"
        self._observers = []

    def attach(self, observer):
        self._observers.append(observer)

    def set_status(self, status):
        if status != self.status:
            self.status = status
            for observer in self._observers:
                observer.update(self)


class SyslogAlert:
    def update(self, device):
        print(f"syslog: {device.hostname} is {device.status}")


class WebexAlert:
    def update(self, device):
        print(f"webex: {device.hostname} changed to {device.status}")


sw = Device("sw01")
sw.attach(SyslogAlert())
sw.attach(WebexAlert())
sw.set_status("down")
sw.set_status("down")
sw.set_status("up")
```

```text
syslog: sw01 is down
webex: sw01 changed to down
syslog: sw01 is up
webex: sw01 changed to up
```

Only two state *changes* happened (the second `"down"` was not a change), so each observer was notified twice, in the order they were attached.

**Advantages of Observer:**

- **Loose coupling.** `Device` knows nothing about syslog or Webex; it only knows that observers have an `update()` method. New alert types need no change to `Device`.
- **Add or remove subscribers at run time** (`attach`, and usually a `detach`).
- **Consistency and event-driven design.** Every interested party learns of a change the moment it happens, instead of polling.
- **Broadcast.** One change reaches any number of observers.

Watch for the trade-offs: observers are called in turn, so a slow or failing observer delays the rest unless you handle it; notification order should not be relied on; and with many observers the flow of control is harder to trace.

> **Real world:** You will see the same idea at network scale. **Webhooks** (domain 2) are Observer across HTTP: you register a URL (attach), and the platform (subject) POSTs an event to it when something changes. Model-driven **telemetry** subscriptions on IOS XE follow the same publish/subscribe model. And in MVC, views are often observers of the model, redrawing themselves when it changes.

> **Exam tip:** "Notify many dependent objects when one object changes, without tight coupling" is Observer. "Separate data, presentation and input handling" is MVC.

## Key takeaways

- A design pattern is a named, proven solution to a recurring design problem; it gives teams a shared vocabulary and encourages loose coupling.
- **MVC**: Model (data and rules), View (presentation), Controller (input handling, coordinates model and view).
- MVC advantages: separation of concerns, several views over one model, parallel development, easier testing and reuse.
- **Observer**: a subject keeps a list of observers and notifies each one when its state changes; one-to-many, event-driven.
- Observer advantages: loose coupling, observers added or removed at run time, immediate consistent notification without polling. Webhooks and telemetry subscriptions apply the same idea across the network.
