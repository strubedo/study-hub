## The problem version control solves

Every network engineer has seen a folder like this:

```text
sw01-config.txt
sw01-config-OLD.txt
sw01-config-2025-03-14.txt
sw01-config-alice-fixed.txt
sw01-config-FINAL-v2.txt
```

Which one is running? Who changed the SNMP community, and why? What did the file look like before last Tuesday's outage? A **version control system (VCS)** answers those questions for every file in a project. It records each change as a snapshot with **who** made it, **when**, and a message saying **why**, and it lets several people change the same files without overwriting each other.

## Advantages of version control

These are the points the exam topic asks you to explain:

| Advantage | What it means in practice |
|---|---|
| **Complete history** | Every committed version of every file is kept. `git log` shows what changed, `git log -p` shows the exact lines |
| **Accountability and audit** | Each commit records an author, timestamp and message: you can answer "who changed the ACL, when and why" for change management and compliance |
| **Roll back** | Return a file or the whole project to any earlier state when a change breaks something |
| **Compare versions** | See precisely what differs between two versions (`git diff`), the basis of code review |
| **Collaboration** | Many people work on the same project at once; the VCS merges their work and flags real conflicts instead of letting the last save win |
| **Branching** | Develop a feature or test a risky change in isolation, then merge it when it is ready, while the main line stays stable |
| **Backup and redundancy** | With a distributed VCS every clone is a full copy of the history; a central server (GitHub, GitLab, Bitbucket, Gitea) adds an off-machine copy |
| **Foundation for automation** | Code review (pull or merge requests), CI/CD pipelines, GitOps and infrastructure as code all trigger from commits in a repository |

> **Exam tip:** If a scenario says "the team cannot tell who changed the script or restore last week's working version", the answer is version control. If it says "two engineers keep overwriting each other's edits on a shared drive", the answer is also version control, specifically its collaboration and merge features.

## Centralised vs distributed

| | Centralised (for example Subversion, CVS) | Distributed (for example **Git**, Mercurial) |
|---|---|---|
| Where the history lives | One central server; clients have a working copy | Every clone holds the full repository and history |
| Committing | Needs the server | Local, offline; you share later with push |
| Branching and merging | Possible, historically heavier | Cheap and central to everyday work |
| If the server is lost | History may be lost unless backed up | Any clone can restore it |

**Git** is the system the exam names, and it is by far the most widely used. It was created by Linus Torvalds in 2005 for Linux kernel development. Git is a distributed VCS: **GitHub, GitLab and Bitbucket are hosting services built around Git**, not version control systems themselves. Teams still usually agree on one shared remote repository as the "source of truth" that everyone pushes to and pulls from.

## How Git stores your work

Git moves changes through three areas, and most Git commands are about moving changes between them:

| Area | What it holds | You move changes in with |
|---|---|---|
| **Working tree** (working directory) | The files you see and edit | Editing |
| **Staging area** (the **index**) | The exact snapshot that the next commit will contain | `git add` |
| **Local repository** (the `.git` directory) | All commits: snapshots linked to their parent commit, each named by a hash | `git commit` |
| **Remote repository** | A shared copy on a server, usually called `origin` | `git push` (and back with `git fetch` / `git pull`) |

A **commit** is a snapshot of the whole project (not just a diff) plus metadata: author name and email, date, message, and a pointer to the parent commit or commits. Its ID is a hash of all that (SHA-1 by default, shown abbreviated as seven or more hex digits such as `ba44c21`), so history cannot be changed silently. A **branch** is just a movable label pointing at a commit; `HEAD` points at the branch you are on.

Because the staging area sits between your edits and the commit, you choose exactly what goes into each commit: two unrelated fixes in the same file session can become two commits with clear messages.

## What to put under version control

In network automation, version control is not only for Python:

- Scripts and modules, unit tests, and `requirements.txt`.
- Ansible playbooks and inventories, Terraform files, Jinja2 templates.
- Device configuration backups and intended ("golden") configurations, so a diff shows configuration drift.
- Documentation, a `README.md`, CI pipeline files.

What **not** to commit: passwords, API keys and tokens, private keys, virtual environments and other generated files. List them in a **`.gitignore`** file. A secret that was ever committed stays in the history even after you delete the file, so it must be rotated (lesson 1.8 shows `git rm --cached`).

> **Watch out:** Version control is not a substitute for testing or change approval, and it does not back up anything you never committed. Commit small, related changes often, with messages that explain *why* ("Raise VLAN 20 MTU for the storage cluster"), not just *what* ("update").

## Lab it yourself

Any computer: install Git (built in on most Linux distributions; `xcode-select --install` on macOS; Git for Windows or WSL 2 on Windows), then in a terminal:

1. Identify yourself to Git: `git config --global user.name "Alice Admin"` and `git config --global user.email alice@example.com` (use your own details; they are recorded in every commit).
2. Create a folder, `git init`, add a copy of a switch configuration and commit it.
3. Edit two lines, run `git status` and `git diff`, commit again with a meaningful message, and run `git log` to see both versions with author and time.
4. Run `git log -p` to see exactly what changed, then `git show HEAD~1:sw01.cfg` (use your file name) to print the old version without changing anything.
5. Optionally create a free private repository on GitHub or GitLab to use as a remote in lesson 1.8.

## Key takeaways

- Version control records every change with author, time and reason, so you get history, accountability, rollback and comparison.
- It lets teams collaborate on the same files, merging work and surfacing conflicts, and isolate work on branches.
- Git is distributed: every clone has the full history and commits are local; GitHub, GitLab and Bitbucket host Git repositories.
- Changes move working tree -> staging area (`git add`) -> local repository (`git commit`) -> remote (`git push`).
- A commit is a snapshot plus metadata, identified by a hash; a branch is a movable pointer to a commit.
- Keep code, templates, playbooks and configurations in Git; keep secrets out with `.gitignore` and rotate any that leak.
