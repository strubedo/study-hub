## The DevNet toolbox

Cisco DevNet (developer.cisco.com) is Cisco's developer programme. Topic 3.7 is a "which resource fits this need?" topic, so learn each resource by the problem it solves. The deciding detail in an exam scenario is usually **what the person needs to do next**: read, try, copy, learn, ask, or escalate.

| Resource | Use it when you need to... | Key facts |
|---|---|---|
| **API documentation** | Find the exact endpoint, parameters, request body, response schema, auth method or SDK call | developer.cisco.com/docs (and developer.webex.com for Webex); reference pages per operation, often with an OpenAPI spec to download and a "try it" console |
| **DevNet Sandbox** | Run code against a **real Cisco product** without owning it | Free with a Cisco.com account; **always on** or **on demand**; see below |
| **Learning Labs** | Learn a technology step by step with guided, hands-on tutorials | Interactive tutorials on developer.cisco.com; many tell you which sandbox to use |
| **Code Exchange** | Find existing **code**: sample scripts, SDKs, tools, Ansible and Terraform content, MCP servers and AI agents for Cisco platforms | A curated index of GitHub repositories from Cisco and the community, searchable by product (Meraki, Catalyst Center, Webex, Catalyst SD-WAN, IOS XE, NX-OS, ...) |
| **Forums (DevNet community)** | Ask other developers and Cisco staff a question, search answers, report a broken sandbox | Community discussion boards per technology, including a DevNet Sandbox forum |
| **Support** | Get help when community answers are not enough, for example an API defect | The support pages on developer.cisco.com. For sandboxes, the Sandbox FAQ says help is best-effort through the DevNet Sandbox community forum (no SLA, not tied to paid Cisco support) |

## DevNet Sandbox in detail

The Sandbox documentation (2026) describes it this way:

- Sandboxes are **free**, run by the DevNet team, and need only a **Cisco.com account**. No licence, hardware or support contract.
- Every sandbox is **always on** or **on demand**, and **both now require a reservation**: even an always-on sandbox is reserved, because the reservation generates credentials scoped to your session.

| | Always on | On demand |
|---|---|---|
| Environment | **Shared** with other users | **Private** to your reservation |
| Admin rights | Restricted | Full admin access to the devices |
| Ready in | A few minutes | Longer (built for you) |
| Best for | Quick read-only API tries: "does this call return what I expect?" | Changing configuration, testing a full workflow, running a demo |
| Length | Set per sandbox | Set per sandbox: each has its own default and maximum (no global limit), and each decides whether and by how much a reservation can be extended |

- You can hold **one active reservation at a time** across all sandboxes.
- Neither type keeps state: when the session ends, the environment and your changes are removed, so export what you need.
- Many sandboxes are reached over a **VPN** whose connection details arrive with the reservation. Sandboxes run on **Stack Automation by Quali**, where your reservation's addresses and credentials appear.
- Because always-on sandboxes are shared, changing management settings there can break them for everyone; if you need to change config, reserve an on-demand one. If you find a broken shared sandbox, report it on the **DevNet Sandbox community forum**.

> **Watch out:** Older study material says always-on sandboxes need no reservation and publish fixed credentials. The current Sandbox documentation says otherwise: reserve, then use the credentials your reservation shows.

## Choosing the right resource

| Scenario | Resource |
|---|---|
| "Which query parameter limits the Catalyst Center device list to 50 records, and is offset 0- or 1-based?" | API documentation |
| "I want to test a NETCONF `edit-config` against a real IOS XE router this afternoon but have no lab." | Sandbox (on demand, because you change config) |
| "I just want to see what `GET /organizations` returns from Meraki." | Sandbox (always on is enough) |
| "Is there already a Python script that backs up Meraki configurations?" | Code Exchange |
| "I'm new to model-driven programmability and want a guided, hands-on introduction." | Learning Labs |
| "My script gets an odd error from the SD-WAN Manager API and I want to know if others have seen it." | Forums |
| "The community forum has no answer to an API defect that blocks our integration." | Support |

## How the resources fit together

```text
Learn           Learning Labs  ──▶ concepts, guided steps
Look up         API documentation ──▶ exact calls and fields
Try             Sandbox ──▶ a real device or controller to call
Reuse           Code Exchange ──▶ working code to start from
Ask             Forums ──▶ peers and Cisco staff
Escalate        Support ──▶ case-style help
```

A realistic workflow: follow a Learning Lab on RESTCONF, reserve the IOS XE sandbox it points to, check field names in the API (YANG model) documentation, start from a Code Exchange repository, and post in the forum when the sandbox behaves unexpectedly.

## Lab it yourself

1. Log in to developer.cisco.com with a Cisco.com account (create one free if needed).
2. Open the Sandbox catalog, filter by "always on", and open two sandbox cards. Note the session length, whether VPN is needed, and the credentials section after you reserve one.
3. In Code Exchange, search for "Catalyst Center" and pick a repository. Check its README for the SDK and Python versions it targets and when it was last updated.
4. Open the Learning Labs catalog and find a lab on NETCONF or RESTCONF; note which sandbox it uses.
5. Find the DevNet Sandbox forum in the Cisco community and read how people report broken shared sandboxes.

## Key takeaways

- API documentation: the exact endpoint, parameters, schema and auth for a call.
- Sandbox: free real Cisco environments; **always on** (shared, restricted, quick, read-mostly) or **on demand** (private, admin, longer to build); session length is set per sandbox; both need a reservation; one active reservation at a time; nothing persists.
- Learning Labs: guided, hands-on tutorials.
- Code Exchange: curated GitHub code, SDKs, tools and AI/MCP projects for Cisco platforms.
- Forums: community questions and answers, including the Sandbox forum for broken shared sandboxes.
- Support: escalation when community help is not enough.
