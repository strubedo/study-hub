## Three more platforms

| | ACI (APIC) | Catalyst SD-WAN (SD-WAN Manager) | NSO |
|---|---|---|---|
| Domain | Data-centre fabric (spine/leaf Nexus 9000 in ACI mode) | WAN overlay of WAN edge routers and controllers | Multivendor service orchestration across any network |
| Controller | APIC cluster | SD-WAN Manager (formerly vManage) | NSO server (Linux) |
| API | APIC REST API over the managed object model, JSON or XML | REST under `/dataservice`, JSON | RESTCONF, NETCONF, JSON-RPC, CLI and Web UI northbound |
| Login | `POST /api/aaaLogin.json` → token as `APIC-cookie` | JWT (`/jwt/login`, 20.18.1 and later) or session (`/j_security_check` → `JSESSIONID` + XSRF token) | HTTP Basic on each RESTCONF request (in the documented examples) |

## ACI and the APIC REST API

### Everything is a managed object

The APIC stores the whole fabric (tenants, VRFs, bridge domains, EPGs, contracts, switches, interfaces, faults) as **managed objects (MOs)** in one tree, the **Management Information Tree (MIT)**. Every MO has:

- a **class**, such as `fvTenant` (tenant), `fvAEPg` (endpoint group), `fvCEp` (a learned endpoint), `topSystem` (a switch or APIC) or `aaaUser`;
- a **distinguished name (DN)** that is its path from the root `uni` or `topology`, built from relative names: `uni/tn-ExampleCorp/ap-web/epg-frontend`, `topology/pod-1/node-101/sys`.

The REST API is a thin layer over that tree, so two URL forms cover almost everything:

| Query | URL | Returns |
|---|---|---|
| **MO query** (one object by DN) | `GET /api/mo/uni/tn-ExampleCorp.json` | That tenant |
| **Class query** (every object of a class) | `GET /api/class/fvTenant.json` | All tenants |
| Endpoints learned by the fabric | `GET /api/node/class/fvCEp.json` | MAC, IP and encapsulation of each endpoint |
| Fabric switches and controllers | `GET /api/class/topSystem.json` (or the `fabricNode` class) | Name, role (`leaf`, `spine`, `controller`), address, serial |

The suffix chooses the encoding: `.json` or `.xml`. Options go in the query string: `query-target=subtree`, `target-subtree-class=fvAEPg`, `query-target-filter=eq(fvTenant.name,"ExampleCorp")`, `rsp-subtree=full`, and paging with `page-size` and `page` (pages start at 0). Writes are a `POST` of the object to `/api/mo/...`.

### Authentication: aaaLogin and the APIC-cookie

```text
POST https://apic.example.com/api/aaaLogin.json
{"aaaUser": {"attributes": {"name": "alice", "pwd": "example-password"}}}
```

```json
{
  "totalCount": "1",
  "imdata": [
    {"aaaLogin": {"attributes": {
      "token": "example-token-not-real",
      "refreshTimeoutSeconds": "600"
    }}}
  ]
}
```

The APIC REST API guide says the token comes back **both** as the `token` attribute and in a `Set-Cookie` header, and later requests authenticate by sending it as the cookie **`APIC-cookie`**. The default session timeout is 600 seconds; `aaaRefresh` (GET, no body) resets the timer and returns a new token, and `aaaLogout` ends the session. With `requests.Session()`, the cookie from the login response is stored and sent automatically.

Every reply has the same envelope: `totalCount` and an `imdata` list in which each item is `{"<className>": {"attributes": {...}}}`.

```json
{"totalCount": "2", "imdata": [
  {"topSystem": {"attributes": {"dn": "topology/pod-1/node-101/sys", "name": "leaf-101", "role": "leaf", "address": "10.0.72.64", "serial": "FDO0000AAAA"}}},
  {"topSystem": {"attributes": {"dn": "topology/pod-1/node-201/sys", "name": "spine-201", "role": "spine", "address": "10.0.72.65", "serial": "FDO0000BBBB"}}}
]}
```

> **Exam tip:** ACI = everything is an MO in the MIT; class query `/api/class/<class>.json`, MO query `/api/mo/<dn>.json`; login with `aaaLogin`, then send `APIC-cookie`; reply = `imdata` list.

## Catalyst SD-WAN Manager API

SD-WAN Manager (the old name, vManage, still appears in older material and in some paths and fields such as `"aud": "vmanage"`) is the management plane of Catalyst SD-WAN. Its REST API sits under `https://<manager>/dataservice/...` and covers device inventory and status, templates and configuration groups, policies, monitoring (alarms, events, statistics) and administration. The documented examples use HTTPS, some with port 8443.

### Session-based authentication (all releases)

```text
1. POST /j_security_check
     Content-Type: application/x-www-form-urlencoded
     j_username=alice&j_password=example-password
   -> Set-Cookie: JSESSIONID=<session hash>       (body empty on success)
2. GET  /dataservice/client/token        Cookie: JSESSIONID=...
   -> body is the XSRF token as plain text
3. GET  /dataservice/device              Cookie: JSESSIONID=...   (+ X-XSRF-TOKEN, optional for GET)
   POST /dataservice/...                 Cookie: JSESSIONID=...  X-XSRF-TOKEN: <token>
4. POST /logout                          Cookie: JSESSIONID=...
```

Points the documentation stresses:

- A failed login does not return a clean error: the body contains an **HTML login page**, so check for `<html>` in the response.
- The **XSRF token** (`X-XSRF-TOKEN` header) is required for POST and other changing operations; since release 19.2 the docs show both the session cookie and the token on API requests. For GET it is optional and ignored if not needed.
- **Log out** at the end to free the session.

### JWT authentication (20.18.1 and later)

`POST /jwt/login` with a JSON body (`username`, `password`, optional `duration` in seconds; default 1,800 seconds) returns `token` (the access token), `refresh` and `csrf`. Send `Authorization: Bearer <token>` on every call and `X-XSRF-TOKEN: <csrf>` on POSTs; renew with `POST /jwt/refresh`. There is no logout call, so request short durations.

### Listing devices

`GET /dataservice/device` lists every device in the overlay, controllers and WAN edges. Records include `deviceId`, `system-ip`, `host-name`, `device-type`, `device-model`, `personality`, `reachability`, `site-id` and `version`. The list is returned in a `data` array inside the JSON reply.

## NSO: Network Services Orchestrator

NSO sits **above** the network and its controllers and does **service orchestration**: you model a service (an L3VPN, a VLAN across a campus, a firewall rule set) once, and NSO turns each service instance into the device configuration, pushes it in one network-wide transaction, and can roll it back.

Building blocks:

- **CDB**, the configuration database, holds the configuration of every managed device (under `devices device <name> config`) plus every service instance. `sync-from` reads a device's real config into CDB; `check-sync` compares them.
- **NEDs (Network Element Drivers)** translate between NSO's YANG view and each device. The docs list four kinds: **NETCONF NED** (device speaks NETCONF, for example Junos), **CLI NED** (Cisco-style CLIs such as IOS, IOS XR, NX-OS), **Generic NED** (proprietary REST or non-Cisco CLIs) and **SNMP NED**.
- **YANG service models** plus templates or Python/Java code define what a service instance means in device terms.
- **Northbound interfaces**: RESTCONF, NETCONF, JSON-RPC (used by the Web UI), the CLI and the Web UI.

RESTCONF on NSO uses the standard `/restconf/data` root (discoverable at `/.well-known/host-meta`). The device list lives at the `tailf-ncs` module's `devices` container:

```bash
curl -s -u alice:example-password \
  -H "Accept: application/yang-data+json" \
  "http://nso.example.com:8080/restconf/data/tailf-ncs:devices/device?fields=name;address"
```

```json
{
  "tailf-ncs:device": [
    {"name": "rtr01", "address": "10.10.30.1"},
    {"name": "sw01", "address": "10.10.30.2"}
  ]
}
```

The port is whatever `ncs.conf` configures; the NSO RESTCONF guide's examples use 8080 over plain HTTP on a lab install, which is fine on a laptop and wrong in production (enable TLS). One device is `/restconf/data/tailf-ncs:devices/device=rtr01`.

> **Watch out:** NSO is not "another controller for one product line". If a scenario mentions multiple vendors, NEDs, a YANG service model, or one transaction across many device types, the answer is NSO.

## Choosing among the three

| Scenario detail | Platform |
|---|---|
| Tenants, EPGs, bridge domains, contracts in a data-centre fabric | ACI (APIC REST) |
| `fvCEp`, `topSystem`, `imdata`, `APIC-cookie` in an exhibit | ACI |
| WAN edge routers, OMP/BFD, `system-ip`, `/dataservice` | Catalyst SD-WAN Manager |
| `JSESSIONID` and `X-XSRF-TOKEN` together | Catalyst SD-WAN Manager |
| Same service pushed to Cisco and Juniper gear with rollback | NSO |
| `tailf-ncs:devices`, NED, `sync-from` | NSO |

## Lab it yourself

1. Reserve an ACI sandbox from the DevNet Sandbox catalog. With curl or Postman, `POST /api/aaaLogin.json`, then `GET /api/class/topSystem.json` and `GET /api/class/fvTenant.json` sending the `APIC-cookie`. Try the same class query with `.xml`.
2. In the APIC GUI, open **Visore** (the object store browser) or turn on the GUI's API Inspector to watch the REST calls the GUI makes.
3. Reserve a Catalyst SD-WAN sandbox. Log in with `/j_security_check` using `curl -c cookies.txt` (in Windows PowerShell type `curl.exe`, because `curl` is an alias there), fetch `/dataservice/client/token`, list `/dataservice/device`, then `POST /logout`.
4. Reserve an NSO sandbox if the catalog lists one, and query `/restconf/data/tailf-ncs:devices/device` with `Accept: application/yang-data+json`.

## Key takeaways

- ACI: the APIC exposes the managed object tree; class queries `/api/class/<class>.json`, MO queries `/api/mo/<dn>.json`; JSON or XML; replies are `totalCount` + `imdata`.
- APIC login: `POST /api/aaaLogin.json` with `aaaUser` `name`/`pwd`; the token returns as an attribute and a cookie, and later calls send `APIC-cookie`; `aaaRefresh` before the 600-second default timeout.
- SD-WAN Manager (formerly vManage): session login `/j_security_check` → `JSESSIONID`; XSRF token from `/dataservice/client/token` in `X-XSRF-TOKEN` for writes; `POST /logout`. JWT (`/jwt/login`, Bearer + `csrf`) from 20.18.1.
- SD-WAN device list: `GET /dataservice/device`, records in `data`.
- NSO: service orchestration with YANG service models, NEDs (NETCONF, CLI, generic, SNMP) and CDB; RESTCONF device list at `/restconf/data/tailf-ncs:devices/device`.
