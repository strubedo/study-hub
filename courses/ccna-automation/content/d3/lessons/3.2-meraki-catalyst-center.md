## Two controllers, two styles

Topic 3.2 names five network management platforms. This lesson covers the two campus and branch platforms; the next covers ACI, Catalyst SD-WAN and NSO.

| | Meraki dashboard | Catalyst Center (formerly DNA Center) |
|---|---|---|
| Where it runs | Cisco cloud (SaaS) | Appliance or virtual appliance you run on premises |
| Manages | Meraki wireless (MR), switches (MS), security and SD-WAN appliances (MX), cameras (MV), sensors (MT), cellular gateways (MG) and endpoint management | Catalyst switches, routers and wireless controllers; also SD-Access fabrics |
| Northbound API | Dashboard API v1 (REST, JSON, OpenAPI spec published) | Intent API (REST, JSON) plus events/webhooks and integration APIs |
| Authentication | API key (or OAuth 2.0 grant) sent as `Authorization: Bearer` | Basic auth to a token endpoint, then `X-Auth-Token` |
| Long operations | Mostly synchronous; action batches for bulk changes | Asynchronous: `202` plus a task to poll |

## Meraki Dashboard API v1

**Base URL:** `https://api.meraki.com/api/v1` (regional clouds use their own hosts, such as `api.meraki.ca` or `api.meraki.cn`).

**Authentication.** Two access methods are documented:

- **API keys** (admin-scoped): generated in the dashboard (Organization > API & Webhooks > API keys and access); the key has exactly the rights of the admin who owns it in each organisation. An identity can hold at most two keys at a time. Keys do not expire until revoked.
- **OAuth 2.0 grants** (app-scoped): for third-party applications; access tokens last 60 minutes and are refreshed automatically.

Either one goes in the standard header:

```http
GET /api/v1/organizations HTTP/1.1
Host: api.meraki.com
Authorization: Bearer <YOUR_API_KEY>
Accept: application/json
```

The v0 API used a custom header, `X-Cisco-Meraki-API-Key`. The v1 documentation tells you to use `Authorization: Bearer` instead ("and not v0's X-Cisco-Meraki-API-Key"), although the v1 OpenAPI spec still lists the old header as a security scheme. New code should use Bearer. In curl, add `-L` and `--location-trusted` as the Meraki docs advise, so a redirect does not drop the header.

**Object hierarchy.** Almost every call hangs off this chain:

```text
organization (id "500123")
  └── network (id "N_1001", productTypes ["appliance", "switch", "wireless"])
        └── device (serial "Q2AA-1111-AAAA", model, lanIp, networkId)
              └── clients seen on the network or the device
```

| Task | Request |
|---|---|
| Organisations the key can see | `GET /organizations` |
| Networks in an organisation | `GET /organizations/{organizationId}/networks` |
| All devices in an organisation | `GET /organizations/{organizationId}/devices` |
| Online/offline status of devices | `GET /organizations/{organizationId}/devices/availabilities` (the older `/devices/statuses` is deprecated) |
| Devices in one network | `GET /networks/{networkId}/devices` |
| Clients seen on a network | `GET /networks/{networkId}/clients?timespan=86400` |
| Clients seen on one device | `GET /devices/{serial}/clients` |

A device record from `GET /organizations/{organizationId}/devices` looks like this (fields from the API reference, values invented):

```json
[
  {
    "name": "hq-ap-01",
    "serial": "Q2AA-1111-AAAA",
    "mac": "00:11:22:33:44:55",
    "networkId": "N_1001",
    "model": "MR46",
    "lanIp": "10.10.20.11",
    "firmware": "wireless-31-1",
    "productType": "wireless",
    "tags": ["floor-2"]
  }
]
```

**Rate limits** (from the Rate Limit page):

- **10 requests per second per organisation**, shared by every application using that organisation, with a burst allowance of 10 extra in the first second (at most 30 in two seconds).
- **100 requests per second per source IP address.**
- Over the limit the API returns **`429`** with a **`Retry-After`** header; wait that long, then retry. The Python library does this automatically, and **action batches** bundle many POST/PUT/DELETE operations into one call to save budget.

**Pagination** follows RFC 5988/8288 web linking. Paginated GETs accept `perPage`, `startingAfter` and `endingBefore`; the response carries a `Link` header with up to four links, `first`, `prev`, `next` and `last`. Follow `rel=next` until it disappears. Each operation sets its own `perPage` range and default: the org-wide device list accepts 3 to 5000 (default 1000), network clients 3 to 5000 (default **10**), so always set it.

```http
Link: <https://api.meraki.com/api/v1/organizations/500123/devices?perPage=1000&startingAfter=Q2AA-1111-AAAA>; rel=next
```

**Clients.** `GET /networks/{networkId}/clients` takes either `t0` or `timespan` (seconds, at most 31 days; default one day). Each client has `id`, `mac`, `ip`, `description`, `vlan`, `ssid` or `switchport`, `status` and `usage` (`sent`/`recv`).

Other capabilities worth knowing: **webhooks** for alerts (covered in Domain 2), an **OpenAPI spec** you can download, organisation-wide **API analytics** in the dashboard, and product-specific operations for appliances, switches, wireless, cameras and sensors grouped under scopes of the same names.

> **Exam tip:** Meraki = cloud, organisation → network → device, Bearer API key, 10 req/s per org, `429` + `Retry-After`, `Link` header paging with `perPage`/`startingAfter`.

## Catalyst Center Intent API

Catalyst Center exposes a northbound REST **Intent API** under `/dna/intent/api/v1/...` (plus newer data APIs under `/dna/data/api/v1/...`). "Intent" means you state the outcome (provision this site, run this template, upgrade these images) and the controller works out the device changes.

Capability groups you should recognise: **Sites** and **Topology**, **Devices** (inventory), **Clients** and **Users** (assurance), **Issues**, **Network Settings**, **Software Image Management (SWIM)**, **Configuration Templates**, **Plug and Play** (zero-touch), **Discovery**, **Path Trace**, **Command Runner** and **SDA**. Catalyst Center also pushes **events** to webhooks and ITSM systems.

### Authentication: token then `X-Auth-Token`

```text
1. POST https://catalyst.example.com/dna/system/api/v1/auth/token
     Authorization: Basic <base64 of user:password>
     Content-Type: application/json
2. 200 OK  {"Token": "example-token-not-real"}
3. GET  https://catalyst.example.com/dna/intent/api/v1/network-device
     X-Auth-Token: example-token-not-real
```

The API reference says the token "remains valid for 1 hour" and must be sent in the `X-Auth-Token` header. Note the token endpoint is under `/dna/system/`, not `/dna/intent/`, and the response key is `Token` with a capital T. A wrong or expired token gives `401`.

### Listing devices

`GET /dna/intent/api/v1/network-device` returns the inventory. It filters with query parameters (`hostname`, `managementIpAddress`, `family`, `platformId`, `reachabilityStatus`, `role`, ...; `.*` works as a wildcard) and pages with `offset` (1-based) and `limit` (up to 500 per page). `GET /dna/intent/api/v1/network-device/count` gives the total.

```json
{
  "response": [
    {
      "hostname": "sw01.example.com",
      "managementIpAddress": "10.10.1.11",
      "platformId": "C9300-48P",
      "softwareVersion": "17.12.4",
      "family": "Switches and Hubs",
      "role": "ACCESS",
      "reachabilityStatus": "Reachable",
      "serialNumber": "FOC0000X0AA",
      "id": "6a49c827-9b28-490b-8df0-8b6c3b582d8a"
    }
  ],
  "version": "1.0"
}
```

Most Intent API replies wrap their payload in `response`, so your code reads `data["response"]`; check each operation's schema, because some differ (the token reply is `{"Token": ...}`, and `client-detail` returns `detail`).

### Clients and hosts

- `GET /dna/data/api/v1/clients` lists clients with filtering and sorting (`type` wired or wireless, `siteId`, `macAddress`, `ipv4Address`, `ssid`, ...), `startTime`/`endTime` in epoch **milliseconds**, and `limit`/`offset` (1-based) paging. The reply has `response`, a `page` object (`limit`, `offset`, `count`) and `version`.
- `GET /dna/intent/api/v1/client-detail?macAddress=...` returns one client's detail, including `hostType` (wired or wireless), `hostName`, `hostIpV4` and connection status.
- `GET /dna/intent/api/v1/client-health` returns overall client health counts.

### Asynchronous operations

Many write calls return `202 Accepted` with a task:

```json
{"response": {"taskId": "c0ffee00-0000-4000-8000-000000000001", "url": "/api/v1/task/c0ffee00-0000-4000-8000-000000000001"}, "version": "1.0"}
```

Poll `GET /dna/intent/api/v1/task/{taskId}` until `endTime` appears, then read `isError`, `progress` and `failureReason`. That is the asynchronous REST pattern from topic 2.8.

## Choosing between them

| Requirement | Platform |
|---|---|
| Cloud-managed branch with no on-premises controller; script must list every MR and MS in the organisation | Meraki Dashboard API |
| On-premises campus with SD-Access; push a day-0 template and upgrade images across sites | Catalyst Center Intent API |
| Script fails with `429` and a `Retry-After: 1` header after a burst of calls | Meraki rate limit (10/s per organisation) |
| A POST returns `202` and a `taskId` | Catalyst Center asynchronous task |

## Lab it yourself

1. Reserve the Meraki sandbox from the DevNet Sandbox catalog (the catalog card says whether it is always on or on demand; both need a reservation). Store the API key it issues in `MERAKI_DASHBOARD_API_KEY` and run `curl -L --location-trusted -H "Authorization: Bearer $MERAKI_DASHBOARD_API_KEY" https://api.meraki.com/api/v1/organizations` (PowerShell: use `$env:MERAKI_DASHBOARD_API_KEY` and `curl.exe`).
2. Walk the hierarchy: take an organisation id, list its networks, then its devices with `?perPage=3`, and read the `Link` header with `curl -i`.
3. Reserve the Catalyst Center sandbox, request a token from `/dna/system/api/v1/auth/token` with `curl -u`, and list devices with `X-Auth-Token`. Add `?limit=2&offset=3` and compare.
4. Open the Catalyst Center API reference on developer.cisco.com and find the `network-device` and `clients` operations; note which use 1-based `offset`.

## Key takeaways

- Meraki is cloud: base URL `https://api.meraki.com/api/v1`, `Authorization: Bearer <API key>` (v0's `X-Cisco-Meraki-API-Key` is the old form), organisation → network → device → clients.
- Meraki limits: 10 req/s per organisation (shared), 100 req/s per source IP; `429` with `Retry-After`; pagination with `perPage`, `startingAfter`, `endingBefore` and a `Link` header.
- Catalyst Center: POST Basic auth to `/dna/system/api/v1/auth/token`, read `Token`, send it as `X-Auth-Token`; it lasts one hour.
- Devices: `GET /dna/intent/api/v1/network-device` with filters, `offset` (1-based) and `limit` (max 500); data sits under `response`.
- Clients: `GET /dna/data/api/v1/clients` (epoch-millisecond times, `page` metadata) or `client-detail?macAddress=`.
- Catalyst Center writes are asynchronous: `202`, `taskId`, poll `/dna/intent/api/v1/task/{taskId}`.
