## From screen-scraping to model-driven interfaces

Before device APIs, automation meant sending CLI over SSH and parsing the text that came back. Modern IOS XE and NX-OS releases expose **programmatic interfaces**: structured data in, structured data out, mostly defined by YANG models (lesson 3.8). Topic 3.6 asks you to describe what each platform offers and how it is switched on. "Dynamic interfaces" here means interfaces that push or stream data and run code on the box: telemetry, on-box Python and shells.

## IOS XE

| Interface | Transport and port | What it is for | Enable with |
|---|---|---|---|
| **NETCONF** | SSH, TCP **830** by default | Configuration and operational data via YANG; transactions, candidate datastore, locking | `netconf-yang` |
| **RESTCONF** | HTTPS, **443** | The same YANG data through HTTP methods and URLs, JSON or XML | `restconf` and `ip http secure-server` |
| **gNMI** | gRPC over HTTP/2 with TLS, secure port **9339** by default | Get, Set, Capabilities and Subscribe (streaming) on YANG paths | `gnxi`, `gnxi secure-trustpoint <tp>`, `gnxi secure-server` |
| **Model-driven telemetry** | NETCONF (dial-in), gRPC/gNMI (dial-in or dial-out) | Push operational data periodically or on change instead of polling SNMP | Dynamic subscriptions from a client, or configured `telemetry ietf subscription` entries |
| **Guest Shell** | Local Linux container | Run Python 3 and Linux tools on the device; scripts can call NETCONF or the CLI | `iox`, then `guestshell enable` |
| **On-box Python `cli` module** | Inside Guest Shell | `cli()`, `clip()`, `configure()`, `configurep()`, `execute()` run IOS commands from Python | Available in Guest Shell |
| **EEM with Python** | Local | Run Python scripts as Embedded Event Manager actions | EEM policy configuration |

All the model-driven interfaces require a **privilege 15** user, and Cisco's guide shows AAA set up for them (`aaa new-model`, `aaa authentication login default local`, `aaa authorization exec default local`).

### Enabling NETCONF and RESTCONF

```text
rtr01# configure terminal
rtr01(config)# username netops privilege 15 secret example-password
rtr01(config)# aaa new-model
rtr01(config)# aaa authentication login default local
rtr01(config)# aaa authorization exec default local
rtr01(config)# netconf-yang
rtr01(config)# restconf
rtr01(config)# ip http secure-server
rtr01(config)# end
rtr01# show netconf-yang datastores
rtr01# show platform software yang-management process
```

Details from the IOS XE programmability guide:

- After `netconf-yang`, the model-based processes may take **up to 90 seconds** to start.
- IOS XE's NETCONF writes to the **running** datastore by default (`:writable-running`). `netconf-yang feature candidate-datastore` enables the **candidate** datastore; then running is no longer writable through NETCONF and every change goes through `<commit>`. Changing this restarts the NETCONF and RESTCONF processes.
- The guide does not describe a startup datastore to edit; saving is done with the `cisco-ia:save-config` RPC (the equivalent of `copy running-config startup-config`).
- RESTCONF needs the internal **NGINX** web server process, which runs when `ip http secure-server` (or `ip http server`) is configured; NETCONF does not need it.

### Telemetry: dial-in and dial-out

- **Dial-in (dynamic)**: the collector connects to the device (NETCONF `establish-subscription`, or gNMI `Subscribe`) and the subscription lives as long as that session.
- **Dial-out (configured)**: the subscription is in the device configuration and the device connects to the receiver (for example a gRPC collector), surviving reboots.
- Updates are **periodic** or **on-change**, defined against an XPath into a YANG model (for example a node of an IOS XE `-oper` model such as CPU utilisation or CDP neighbours).

### On-box Python

```text
rtr01# guestshell run python3
>>> from cli import cli, configure
>>> print(cli("show ip interface brief"))
>>> configure(["interface Loopback100", "description set-from-guestshell"])
```

## NX-OS

| Interface | What it is | Enable with |
|---|---|---|
| **NX-API CLI** | Send CLI commands (show, config, even Bash) in an HTTP/HTTPS POST to **`/ins`**; responses in JSON or XML. Message types: `cli_show`, `cli_show_array`, `cli_show_ascii`, `cli_conf`, `bash` in an `ins_api` envelope, or **JSON-RPC 2.0** (`Content-Type: application/json-rpc`) | `feature nxapi` (ports with `nxapi http port` / `nxapi https port`) |
| **NX-API REST** | REST access to the **DME** (Data Management Engine) object model, the same managed-object idea as ACI: `GET /api/mo/sys/bgp.json`, class queries, `PUT` for config replace | `feature nxapi` |
| **NX-API Developer Sandbox** | A web page on the switch that converts CLI into NX-API CLI or NX-API REST (DME) requests and Python; links to Visore, the model browser | Enabled with NX-API |
| **NETCONF** | SSH port **830**, YANG models (native "device" models and OpenConfig) | `feature netconf` |
| **RESTCONF**, **gNMI** | Model-driven interfaces like IOS XE | `feature restconf`, `feature grpc` |
| **Bash shell** | Linux Bash on the switch | `feature bash-shell`, then `run bash` |
| **Python** | Interactive or scripted Python with the `cli` module: `cli()`, `clid()` (JSON output), `clip()` | `python3` from the CLI |
| **Guest Shell** | Linux container for third-party tools | `guestshell enable` |

An NX-API CLI request in JSON-RPC form, as in the NX-OS programmability guide:

```python
import requests

url = "https://sw01.example.com/ins"
payload = [{"jsonrpc": "2.0", "method": "cli",
            "params": {"cmd": "show version", "version": 1}, "id": 1}]
resp = requests.post(url, json=payload,
                     headers={"Content-Type": "application/json-rpc"},
                     auth=("netops", "example-password"), timeout=30)
print(resp.json())
```

(The guide sets `Content-Type: application/json-rpc`. `json=` would otherwise set `application/json`, so the explicit header matters.)

And the `ins_api` form:

```json
{"ins_api": {"version": "1.0", "type": "cli_show", "chunk": "0",
             "sid": "1", "input": "show switchname", "output_format": "json"}}
```

On-box Python on NX-OS:

```text
sw01# python3
>>> from cli import *
>>> import json
>>> intfs = json.loads(clid("show interface brief"))
>>> intfs["TABLE_interface"]["ROW_interface"][0]["interface"]
```

> **Exam tip:** NX-API CLI = CLI wrapped in HTTP POST to `/ins` (JSON, XML or JSON-RPC). NX-API REST = the DME object model, URLs like `/api/mo/sys/...`. Both need `feature nxapi`. NETCONF needs `feature netconf`; Bash needs `feature bash-shell`.

## Comparing the two

| | IOS XE | NX-OS |
|---|---|---|
| NETCONF | `netconf-yang`, port 830 | `feature netconf`, port 830 |
| RESTCONF | `restconf` + `ip http secure-server` | `feature restconf` |
| gNMI | `gnxi` (secure port 9339 default) | `feature grpc` |
| CLI over HTTP | (RESTCONF only; no NX-API equivalent) | NX-API CLI at `/ins` |
| Object-model REST | | NX-API REST (DME) |
| On-box Linux | Guest Shell (`iox`, `guestshell enable`) | Bash (`feature bash-shell`), Guest Shell |
| On-box Python | In Guest Shell, `cli` module | `python3` on the CLI, `cli` module |

## Lab it yourself

1. Reserve an IOS XE sandbox from the DevNet Sandbox catalog and check its page for which interfaces are enabled. From your computer, run `ssh -p 830 -s <user>@<host> netconf` (OpenSSH is built into Windows 10 and later, macOS and Linux) and watch the server's `<hello>` with its capabilities; end with Ctrl+C.
2. Against the same device, `curl -k -u <user> -H "Accept: application/yang-data+json" https://<host>/restconf/data/ietf-interfaces:interfaces` (PowerShell: `curl.exe`).
3. If you have your own IOS XE node (Cisco Modeling Labs free tier or an on-demand sandbox with admin rights), configure the commands above and check `show netconf-yang datastores` before and after `netconf-yang feature candidate-datastore`.
4. Reserve an NX-OS (Nexus 9000) sandbox if the catalog lists one, browse to the switch's management address to reach the NX-API Developer Sandbox, type `show version`, and copy the Python it generates.

## Key takeaways

- IOS XE: NETCONF (`netconf-yang`, SSH 830), RESTCONF (`restconf` + `ip http secure-server`, HTTPS 443), gNMI (`gnxi`, secure port 9339), model-driven telemetry (dial-in dynamic, dial-out configured), Guest Shell with on-box Python.
- IOS XE NETCONF writes running by default; `netconf-yang feature candidate-datastore` switches to candidate + commit; save with `cisco-ia:save-config`.
- Model-driven interfaces need a privilege 15 user and AAA.
- NX-OS: `feature nxapi` gives NX-API CLI (POST to `/ins`, JSON/XML/JSON-RPC) and NX-API REST (DME objects at `/api/mo/...`); `feature netconf`; `feature bash-shell` and `run bash`; `python3` with `cli()`/`clid()`.
- Telemetry pushes data periodically or on change instead of SNMP polling.
