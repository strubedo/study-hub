## The three pieces

- **YANG** (RFC 7950, YANG 1.1) is a **data modelling language**. It describes what configuration and state a device has, their types and constraints, as a tree.
- **NETCONF** (RFC 6241, over SSH per RFC 6242) is an **RPC protocol** that reads and writes YANG-modelled data as **XML**, with transactions and multiple datastores.
- **RESTCONF** (RFC 8040) is an **HTTP API** that exposes the same YANG data as URLs, in **JSON or XML**.

The model is the contract; NETCONF, RESTCONF and gNMI are three ways to carry data that conforms to it.

## YANG

### Building blocks

```yang
module example-vlans {
  yang-version 1.1;
  namespace "urn:example:vlans";
  prefix vl;

  container vlans {
    list vlan {
      key "id";
      leaf id {
        type uint16 {
          range "1..4094";
        }
      }
      leaf name {
        type string;
      }
      leaf enabled {
        type boolean;
        default "true";
      }
      leaf-list tagged-ports {
        type string;
      }
      leaf oper-status {
        type enumeration {
          enum up;
          enum down;
        }
        config false;
      }
    }
  }
}
```

| Statement | Meaning | Example above |
|---|---|---|
| `module` | The unit of definition, with a unique `namespace` and a short `prefix` | `example-vlans`, prefix `vl` |
| `container` | A node that groups other nodes; one instance | `vlans` |
| `list` | A sequence of entries identified by a **key** | `vlan`, key `id` |
| `leaf` | One value with a type | `name` (string), `id` (uint16 with a range) |
| `leaf-list` | A sequence of values of one type | `tagged-ports` |
| `config false` | State (operational) data, not configuration | `oper-status` |
| `typedef`, `grouping`/`uses`, `augment`, `import` | Reuse types, reuse node sets, add nodes to another module's tree, refer to other modules | `ietf-ip` augments `ietf-interfaces` |

### Reading a YANG tree (RFC 8340)

`pyang -f tree` turns a module into a tree diagram. You must read these on the exam:

```text
module: example-vlans
  +--rw vlans
     +--rw vlan* [id]
        +--rw id              uint16
        +--rw name?           string
        +--rw enabled?        boolean
        +--rw tagged-ports*   string
        +--ro oper-status?    enumeration
```

- `rw` = configuration, `ro` = state (`config false`).
- `*` = a list or leaf-list; `[id]` = the list key.
- `?` = optional leaf; `!` = presence container.
- Nodes added by another module appear as `prefix:name`.

The real interface model, `ietf-interfaces` (RFC 8343), with `ietf-ip` (RFC 8344) augmenting it:

```text
module: ietf-interfaces
  +--rw interfaces
     +--rw interface* [name]
        +--rw name           string
        +--rw description?   string
        +--rw type           identityref
        +--rw enabled?       boolean
        +--ro oper-status    enumeration
        +--rw ip:ipv4!
           +--rw ip:address* [ip]
              +--rw ip:ip               inet:ipv4-address-no-zone
              +--rw (ip:subnet)
                 +--:(ip:prefix-length)
                 |  +--rw ip:prefix-length?   uint8
                 +--:(ip:netmask)
                    +--rw ip:netmask?         yang:dotted-quad
```

(Abridged; `(subnet)` is a **choice**: an address has either a prefix length or a netmask.)

### Native, IETF and OpenConfig models

| Family | Written by | Covers | Example on IOS XE |
|---|---|---|---|
| **Native** (vendor) | Cisco | Everything the platform's CLI can do, mirroring its structure | `Cisco-IOS-XE-native` (config), `Cisco-IOS-XE-*-oper` (state) |
| **IETF** | IETF working groups (RFCs) | Common, vendor-neutral features | `ietf-interfaces`, `ietf-ip`, `ietf-routing` |
| **OpenConfig** | Network operators' group | Vendor-neutral, operationally focused, strong on telemetry | `openconfig-interfaces`, `openconfig-bgp` |

Trade-off: IETF and OpenConfig models make one script work across vendors but cover less; native models cover every feature but tie you to the platform. The device tells you what it supports in its NETCONF capabilities and its YANG library, and Cisco publishes its models in the YangModels GitHub repository.

## NETCONF

### Layers and the session

| Layer | NETCONF |
|---|---|
| Content | YANG-modelled configuration and state data, in XML |
| Operations | `<get>`, `<get-config>`, `<edit-config>`, `<copy-config>`, `<delete-config>`, `<lock>`, `<unlock>`, `<commit>`, `<close-session>`, `<kill-session>` |
| Messages | `<hello>`, `<rpc>`, `<rpc-reply>`, `<notification>` |
| Secure transport | **SSH**, the `netconf` subsystem on TCP **830** (RFC 6242) |

A session runs in this order:

1. The client opens SSH to port 830 and requests the `netconf` subsystem (`ssh -p 830 -s alice@rtr01.example.com netconf`).
2. **Both** sides send `<hello>` with their **capabilities** (`urn:ietf:params:netconf:base:1.1`, `...:capability:candidate:1.0`, the YANG modules supported). The server's hello also carries the `session-id`.
3. The client sends `<rpc message-id="...">` requests; the server answers each with `<rpc-reply>` carrying the same `message-id`, containing `<data>`, `<ok/>` or `<rpc-error>`.
4. The client ends with `<close-session/>`.

With base:1.0 every message ends with the delimiter `]]>]]>`; when both sides advertise base:1.1, messages use **chunked framing** (`#<length>` chunks ending in `##`).

### get versus get-config

```xml
<rpc message-id="101" xmlns="urn:ietf:params:xml:ns:netconf:base:1.0">
  <get-config>
    <source><running/></source>
    <filter type="subtree">
      <interfaces xmlns="urn:ietf:params:xml:ns:yang:ietf-interfaces">
        <interface>
          <name>GigabitEthernet1</name>
        </interface>
      </interfaces>
    </filter>
  </get-config>
</rpc>
```

```xml
<rpc-reply message-id="101" xmlns="urn:ietf:params:xml:ns:netconf:base:1.0">
  <data>
    <interfaces xmlns="urn:ietf:params:xml:ns:yang:ietf-interfaces">
      <interface>
        <name>GigabitEthernet1</name>
        <description>uplink to core</description>
        <type xmlns:ianaift="urn:ietf:params:xml:ns:yang:iana-if-type">ianaift:ethernetCsmacd</type>
        <enabled>true</enabled>
      </interface>
    </interfaces>
  </data>
</rpc-reply>
```

| | `<get-config>` | `<get>` |
|---|---|---|
| Returns | **Configuration only** | Running configuration **plus state** (counters, oper-status) |
| Datastore | Required `<source>`: `running`, `candidate` or `startup` | No source: always running + state |
| Filter | Optional subtree or XPath filter | Same |

### edit-config and datastores

```xml
<rpc message-id="102" xmlns="urn:ietf:params:xml:ns:netconf:base:1.0">
  <edit-config>
    <target><running/></target>
    <config>
      <interfaces xmlns="urn:ietf:params:xml:ns:yang:ietf-interfaces">
        <interface>
          <name>GigabitEthernet2</name>
          <description>to sw01</description>
        </interface>
      </interfaces>
    </config>
  </edit-config>
</rpc>
```

Success is `<rpc-reply message-id="102" ...><ok/></rpc-reply>`. The default operation is **merge**; an `operation` attribute on an element (`merge`, `replace`, `create`, `delete`, `remove`) overrides it for that subtree. `create` fails if the data exists, `delete` fails if it does not, `remove` does not care.

| Datastore | Capability | Notes |
|---|---|---|
| **running** | Always present; writable if `:writable-running` | The active configuration |
| **candidate** | `:candidate` | A scratch copy; changes take effect only on `<commit>`; `<discard-changes>` throws them away; `<lock>` it first so nobody else edits at the same time |
| **startup** | `:startup` | The configuration loaded at boot; `<copy-config>` from running saves it |

On **IOS XE**, NETCONF edits **running** by default; `netconf-yang feature candidate-datastore` adds the **candidate** datastore (running then becomes read-only through NETCONF), and the programmability guide documents no startup datastore to edit: you save with the `cisco-ia:save-config` RPC. Check the `<hello>`: a datastore is only there if its capability (`:candidate`, `:startup`) is listed.

### ncclient

```python
from ncclient import manager

FILTER = """
<interfaces xmlns="urn:ietf:params:xml:ns:yang:ietf-interfaces">
  <interface><name>GigabitEthernet1</name></interface>
</interfaces>"""

with manager.connect(host="rtr01.example.com", port=830,
                     username="alice", password="example-password",
                     hostkey_verify=False,          # lab only
                     device_params={"name": "iosxe"}) as m:
    print([c for c in m.server_capabilities if "candidate" in c])
    reply = m.get_config(source="running", filter=("subtree", FILTER))
    print(reply.data_xml)
```

## RESTCONF

### URLs

```text
https://rtr01.example.com/restconf/data/ietf-interfaces:interfaces/interface=GigabitEthernet1
        └────host──────┘└─root─┘└data┘└──module:top node──────┘└list┘└──key value───┘
```

- **Root discovery**: `GET /.well-known/host-meta` returns an XRD document whose `rel='restconf'` link gives the root, normally `/restconf`.
- `/restconf/data` is the datastore resource (configuration and state combined); `/restconf/operations` lists RPCs you invoke with POST.
- The **first** node after `data/` is qualified with its **module name** (`ietf-interfaces:interfaces`); child nodes in the same module are not.
- A **list entry** is addressed as `list=key` (`interface=GigabitEthernet1`); several keys are comma-separated.
- Key values are **percent-encoded**, so `GigabitEthernet1/0/1` becomes `interface=GigabitEthernet1%2F0%2F1`. The IOS XE guide shows the native form: `Cisco-IOS-XE-native:native/interface/GigabitEthernet=0%2F0%2F2`.
- Query parameters: `depth`, `fields` (`?fields=name;description`), `content` (`config`, `nonconfig` or `all`), `with-defaults`.

### Media types and methods

Send `Accept` and `Content-Type` as **`application/yang-data+json`** or **`application/yang-data+xml`**.

| HTTP method | NETCONF equivalent (RFC 8040) | Typical success |
|---|---|---|
| `GET` / `HEAD` | `<get-config>` / `<get>` | `200 OK` |
| `POST` | `<edit-config>` with `operation="create"` (child resource), or invoke an RPC | `201 Created` + `Location`; `409 Conflict` if it already exists |
| `PUT` | `<edit-config>` with `operation="create/replace"` (or `<copy-config>` on the datastore) | `201 Created` if new, `204 No Content` if replaced |
| `PATCH` | `<edit-config>`; a plain patch is a **merge** (the target resource must already exist) | `200 OK` with a body, `204 No Content` without |
| `DELETE` | `<edit-config>` with `operation="delete"` | `204 No Content` |

```http
GET /restconf/data/ietf-interfaces:interfaces/interface=GigabitEthernet1 HTTP/1.1
Host: rtr01.example.com
Authorization: Basic <base64 of alice:example-password>
Accept: application/yang-data+json
```

```json
{
  "ietf-interfaces:interface": [
    {
      "name": "GigabitEthernet1",
      "description": "uplink to core",
      "type": "iana-if-type:ethernetCsmacd",
      "enabled": true
    }
  ]
}
```

The JSON encoding (RFC 7951) qualifies top-level members with the module name and encodes a list entry as an array.

```python
import requests

URL = ("https://rtr01.example.com/restconf/data/"
       "ietf-interfaces:interfaces/interface=GigabitEthernet2")
HEADERS = {"Accept": "application/yang-data+json",
           "Content-Type": "application/yang-data+json"}
body = {"ietf-interfaces:interface": [{"name": "GigabitEthernet2",
                                       "description": "to sw01"}]}
resp = requests.patch(URL, json=body, headers=HEADERS,
                      auth=("alice", "example-password"),
                      verify="lab-ca.pem", timeout=30)
print(resp.status_code)        # 204 when the merge succeeds
```

The explicit `Content-Type` matters: `json=` alone would send `application/json`, which a RESTCONF server may reject with `415`.

## NETCONF, RESTCONF and gNMI compared

| | NETCONF | RESTCONF | gNMI |
|---|---|---|---|
| Transport | SSH, TCP 830 | HTTPS, TCP 443 | gRPC over HTTP/2 + TLS (IOS XE secure default 9339) |
| Encoding | XML | JSON or XML | Protobuf, with JSON / JSON_IETF values |
| Operations | RPCs: get, get-config, edit-config, lock, commit, ... | HTTP methods on resource URLs | `Capabilities`, `Get`, `Set`, `Subscribe` |
| Datastores and transactions | Multiple datastores, candidate + commit, locks | Single unified datastore view | Set is a transaction of updates/replaces/deletes |
| Streaming | Notifications (dynamic subscriptions) | Event streams | `Subscribe` in `STREAM`, `ONCE` or `POLL` mode: built for telemetry |

## Lab it yourself

1. Install `pyang` on your computer (`pip install pyang`), clone the YangModels `yang` repository from GitHub, change to its `standard/ietf/RFC` folder (it also holds the modules these import), and run `pyang -p . -f tree ietf-interfaces.yang ietf-ip.yang`. Find the `augment` that adds `ipv4`. On Windows, run this step in WSL: in that folder `ietf-interfaces.yang` and `ietf-ip.yang` are symbolic links to the dated files, and Git checks symbolic links out as small plain-text files when `core.symlinks` is false (git-config documentation), as it can be on Windows.
2. Reserve an IOS XE sandbox, connect with `ssh -p 830 -s <user>@<host> netconf`, and read the capabilities in the server hello. Is `:candidate` listed?
3. `pip install ncclient` and run the script above against the sandbox (set `hostkey_verify=False` only in the lab).
4. With curl or Postman, `GET /.well-known/host-meta`, then `GET /restconf/data/ietf-interfaces:interfaces` with `Accept: application/yang-data+json`, then a single interface with `interface=<name>` (encode any `/` as `%2F`).
5. On an on-demand sandbox where you have admin rights, PATCH a description, GET it back, then DELETE it and read the status codes.

## Key takeaways

- YANG models data as a tree: module → container → list (with key) → leaf / leaf-list; `config false` marks state. Tree diagrams: `rw`/`ro`, `*` lists, `[key]`, `?` optional.
- Native models (`Cisco-IOS-XE-native`) cover everything; IETF (`ietf-interfaces`) and OpenConfig models are vendor-neutral.
- NETCONF: SSH port 830, `<hello>` capabilities exchange, XML RPCs; `<get>` = config + state, `<get-config>` = config from a chosen datastore; `<edit-config>` defaults to merge.
- Datastores: running, candidate (`<commit>`), startup. IOS XE: running by default, candidate when enabled, save with `cisco-ia:save-config`.
- RESTCONF: HTTPS 443, root from `/.well-known/host-meta`, `/restconf/data/<module>:<node>/list=key`, `%2F` for `/` in keys, `application/yang-data+json` or `+xml`.
- Methods: GET → get; POST → create (`201`, `409` if it exists); PUT → create or replace; PATCH → merge; DELETE → delete (`204`).
- Enable on IOS XE with `netconf-yang`, `restconf` and `ip http secure-server`, plus a privilege 15 user and AAA.
