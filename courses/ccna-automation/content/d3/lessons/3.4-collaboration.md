## The collaboration APIs at a glance

| Interface | Product | Style | Auth | Use it to |
|---|---|---|---|---|
| Webex REST API | Webex cloud (messaging, meetings, calling, admin) | REST, JSON, `https://webexapis.com/v1` | `Authorization: Bearer <access token>` | Create spaces, add people, post and read messages, register webhooks |
| xAPI | Webex RoomOS devices (Room, Board, Desk series) | Commands, statuses and configurations; reachable through the cloud REST API and on the device | Bearer token for the cloud xAPI | Query device status, run commands like volume or call control |
| AXL | Cisco Unified Communications Manager (CUCM) | SOAP over HTTPS, XML | HTTP Basic, user with an AXL role | Provision and read the CUCM configuration database: phones, lines, users |
| UDS | CUCM | REST, XML | User credentials (or none for public resources) | End-user data: directory search, a user's devices, speed dials, call forwarding |

## Webex REST API

### Tokens and app types

Every call carries an access token:

```http
GET /v1/rooms?max=50 HTTP/1.1
Host: webexapis.com
Authorization: Bearer <YOUR_WEBEX_TOKEN>
```

Where the token comes from depends on what you build:

- **Personal access token**: copied from developer.webex.com after you log in. Good for trying calls; it is short-lived and acts as **you**.
- **Bot**: a separate Webex identity with its own long-lived token, created on developer.webex.com. People add it to spaces or message it directly. In group spaces a bot only sees messages in which it is **@mentioned**; in a 1:1 space it sees everything sent to it. It does not act on behalf of a user.
- **Integration**: an **OAuth 2.0** client that acts **on behalf of a user** who grants it permission. The user is sent to `https://webexapis.com/v1/authorize` with `response_type=code`, `client_id`, `redirect_uri`, `scope` and `state`; your server exchanges the returned code at `POST https://webexapis.com/v1/access_token` (`grant_type=authorization_code`) for an access token and a refresh token, and later uses `grant_type=refresh_token` to renew. Use the expiry values in the response rather than assuming fixed lifetimes.
- **Service App**: a machine account authorised by an organisation's full admin, for org-wide automation independent of any one user.
- **Guest access** (people without Webex accounts, for example in a customer-facing widget) used to be built with a **Guest Issuer** app and a shared JWT secret. That Guest Issuer model is now **deprecated**; new guest integrations use **Service App Guest Management**, and existing Guest Issuers must migrate.

> **Exam tip:** Bot = its own identity, sees only messages that mention it in group spaces. Integration = OAuth on behalf of a user, with scopes. Guest issuer = guest users without accounts (legacy, now replaced by Service App guest management).

### Spaces, memberships, messages

In the API a space is a **room**. The core resources:

| Task | Request | Key fields |
|---|---|---|
| List spaces | `GET /v1/rooms` | `type` (`direct`/`group`), `teamId`, `sortBy`, `max` |
| Create a space | `POST /v1/rooms` | `title` (required), `teamId`, `isLocked` |
| Rename / delete a space | `PUT` / `DELETE /v1/rooms/{roomId}` | |
| List members | `GET /v1/memberships?roomId=...` | |
| Add a person | `POST /v1/memberships` | `roomId` (required) and `personEmail` or `personId`, `isModerator` |
| Remove a person | `DELETE /v1/memberships/{membershipId}` | |
| Post a message | `POST /v1/messages` | `roomId` **or** `toPersonEmail`/`toPersonId`; `text`, `markdown`, `files`, `attachments` (cards), `parentId` (thread reply) |
| List messages | `GET /v1/messages?roomId=...` | `roomId` is required; `mentionedPeople=me` for bots |
| Who am I | `GET /v1/people/me` | |

IDs are long opaque base64 strings; you always get them from a previous call (create a room, read its `id`, use it as `roomId`). Lists are paged with `max` and an RFC 5988 `Link` header containing `rel="next"`, the same pattern as Meraki. A `429` comes with `Retry-After`.

### Webhooks

`POST /v1/webhooks` with `name`, `targetUrl`, `resource` (for example `messages`, `memberships`, `rooms`) and `event` (`created`, `updated`, `deleted`, and meeting events such as `started` or `joined`), plus an optional `filter` (such as `roomId=...`) and `secret`. With a secret, Webex signs each notification with HMAC-SHA1 in `X-Spark-Signature`. The notification for a new message carries the message **id** but not its text; your bot then calls `GET /v1/messages/{messageId}` to read it (Domain 2 covered the receiver side).

## Webex devices and the xAPI

RoomOS devices expose the **xAPI**: a tree of **commands** (do something: `Audio.Volume.Set`, `Dial`, `Standby.Activate`), **statuses** (read state: `Audio.Volume`, `SystemUnit.Uptime`, call status) and **configurations** (persistent settings). Two ways to reach it:

- **Cloud xAPI** through the Webex REST API, for cloud-registered devices:
  - `GET /v1/xapi/status?deviceId=<id>&name=audio.volume` queries statuses (up to 10 expressions);
  - `POST /v1/xapi/command/{commandName}` (for example `/v1/xapi/command/Audio.Volume.Set`) runs a command with a JSON body holding `deviceId` and `arguments`;
  - `deviceId` comes from `GET /v1/devices`; scopes `spark:xapi_statuses` and `spark:xapi_commands` control access.
- **On the device**: the same xAPI through the device's local interfaces, and **macros**, scripts edited in the device's local web portal (Macro Editor) that run on the device and react to xAPI events.

Persistent settings can also be read and changed in bulk through the cloud `deviceConfigurations` API.

## CUCM: AXL and UDS

### AXL (Administrative XML)

AXL is a **SOAP/XML** web service for **inserting, retrieving, updating and removing** data in the CUCM configuration database: the provisioning API for phones, lines, users, partitions, route patterns and so on.

- Endpoint: `https://<cucm>:8443/axl/`, over **HTTPS only** (non-HTTPS requests are redirected).
- Authentication: **HTTP Basic**. Create a dedicated application user in a group with the **Standard AXL API Access** role (read/write) or the read-only AXL roles; a read-only user that tries to write gets `401`.
- The **`SOAPAction`** header names the AXL version and operation, and the XML namespace in the envelope must match the version.

```bash
curl -u axluser -H 'Content-Type: text/xml' \
  -H 'SOAPAction: "CUCM:DB ver=15.0 getPhone"' \
  -d @request.xml https://cucm.example.com:8443/axl/
```

```xml
<soapenv:Envelope xmlns:soapenv="http://schemas.xmlsoap.org/soap/envelope/"
                  xmlns:ns="http://www.cisco.com/AXL/API/15.0">
  <soapenv:Header/>
  <soapenv:Body>
    <ns:getPhone>
      <name>SEP001122334455</name>
    </ns:getPhone>
  </soapenv:Body>
</soapenv:Envelope>
```

The WSDL (downloadable from CUCM) describes every operation (`addPhone`, `getPhone`, `updateLine`, `listUser`, `executeSQLQuery`, ...), which is why Python users often drive AXL with a SOAP library such as `zeep` loaded with that WSDL.

### UDS (User Data Services)

UDS is a **REST** API on every CUCM node (installed and activated by default) that returns **XML** about **end users** and their resources: the CUCM version and servers, **directory search** (`GET https://<cucm>:8443/cucm-uds/users?displayname=Bill`), a user's devices, speed dials, call forwarding, remote destinations and IP phone service subscriptions. Cisco's own clients use it for user-level data.

| Need | AXL or UDS |
|---|---|
| Bulk-create 200 phones and lines | AXL |
| Read the system's route patterns | AXL |
| Let a user search the corporate directory from an app | UDS |
| Let a user change their own call-forward destination | UDS |

> **Watch out:** AXL is SOAP even though it runs over HTTPS. If the exhibit shows `soapenv:Envelope`, a `SOAPAction` header and `/axl/`, it is AXL. If it shows `/cucm-uds/` URLs and simple GETs, it is UDS.

## Lab it yourself

1. Create a free Webex account, open developer.webex.com, copy your personal access token and call `GET https://webexapis.com/v1/people/me` with curl or Postman.
2. Create a space, add a second test address of your own as a member, post a markdown message, list messages, then delete the space (lesson 3.9 has the Python).
3. Create a bot on developer.webex.com, add it to a space, and confirm with `GET /v1/messages?roomId=...&mentionedPeople=me` using the bot's token that it only sees messages that @mention it.
4. If the DevNet Sandbox catalog lists a Unified CM (collaboration) sandbox, reserve it, download the AXL WSDL from the CUCM administration pages, and send the `getPhone` envelope above with curl (change the version to the sandbox's CUCM version).
5. In the same sandbox, try `GET https://<cucm>:8443/cucm-uds/version` and a user search.

## Key takeaways

- Webex REST API: `https://webexapis.com/v1`, `Authorization: Bearer <token>`; rooms (spaces), memberships (participants), messages; `Link` paging with `max`.
- Bots are their own identity and see only messages that @mention them in group spaces; integrations use OAuth 2.0 (`/v1/authorize`, `/v1/access_token`) on behalf of a user; Guest Issuer is deprecated in favour of Service App guest management.
- Webhooks: `POST /v1/webhooks` with `name`, `targetUrl`, `resource`, `event`; signed with `X-Spark-Signature`; fetch the message by id.
- Webex devices: xAPI commands, statuses and configurations, via `/v1/xapi/status` and `/v1/xapi/command/{commandName}` or locally, plus on-device macros.
- CUCM AXL: SOAP/XML provisioning at `https://<cucm>:8443/axl/`, Basic auth with an AXL role, `SOAPAction` names the version and operation.
- CUCM UDS: REST/XML end-user data at `/cucm-uds/...` (directory, devices, speed dials, call forward).
