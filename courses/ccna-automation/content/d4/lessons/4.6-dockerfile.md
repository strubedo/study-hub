## What a Dockerfile is

A **Dockerfile** is a text file of instructions that `docker build` executes in order to produce an **image**: a read-only, layered filesystem plus metadata (the default command, environment, user, exposed ports). Topic 4.6 asks you to *interpret* one: say what each line does, what the resulting container will run, and what is wrong with it.

Here is the Dockerfile for a small inventory API, `app.py`, that listens on a port given with `--port` and reads its site name from the `SITE` environment variable:

```dockerfile
# syntax=docker/dockerfile:1
FROM python:3.14-slim

ARG APP_VERSION=dev
LABEL org.opencontainers.image.version=$APP_VERSION

ENV PYTHONUNBUFFERED=1 \
    SITE=lab

WORKDIR /app

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY . .

RUN useradd --create-home --uid 10001 appuser
USER appuser

EXPOSE 8000

ENTRYPOINT ["python", "app.py"]
CMD ["--port", "8000"]
```

## Instruction by instruction

| Instruction | What it does | In the example |
|---|---|---|
| `# syntax=` | Parser directive (a special first-line comment) choosing the Dockerfile syntax version | Use the stable version 1 syntax |
| `FROM` | Starts a build stage from a base image. A valid Dockerfile must start with `FROM` (only `ARG` may come before it) | Debian-based slim image with Python 3.14 |
| `ARG` | Declares a **build-time** variable, set with `docker build --build-arg NAME=value`; it has a default here | Version label, `dev` unless overridden |
| `LABEL` | Adds metadata key-value pairs to the image | OCI version label |
| `ENV` | Sets environment variables for later build steps **and for the running container** | Unbuffered Python output (so `docker logs` shows prints immediately) and a default `SITE` |
| `WORKDIR` | Sets the working directory for following `RUN`, `CMD`, `ENTRYPOINT`, `COPY` and `ADD`; creates it if missing. Relative paths are relative to the previous `WORKDIR` | Everything happens in `/app` |
| `COPY` | Copies files from the **build context** (or another stage or image) into the image | First only `requirements.txt`, later the rest of the source |
| `RUN` | Executes a command **at build time** and commits the result as a new layer | Installs dependencies; creates a user |
| `USER` | Sets the user (and optionally group) for the rest of the stage: later `RUN` steps and the container's `ENTRYPOINT` and `CMD` | The app runs as `appuser`, not root |
| `EXPOSE` | **Documents** the port the app listens on (TCP by default). It does **not** publish it | Port 8000 |
| `ENTRYPOINT` | The executable the container always runs | `python app.py` |
| `CMD` | Default arguments for `ENTRYPOINT`, or the default command if there is no `ENTRYPOINT` | `--port 8000` |

Other instructions you may meet: `ADD` (below), `VOLUME` (declares a mount point), `HEALTHCHECK` (a command Docker runs to test the container), `STOPSIGNAL`, `SHELL` and `ONBUILD`.

## RUN vs CMD

`RUN` happens **while building** the image; its output (installed packages, created users) is baked into a layer. `CMD` does **nothing at build time**: it records what the container should run when it **starts**. The Dockerfile reference makes exactly this point: `RUN` "actually runs a command and commits the result", while `CMD` "specifies the intended command for the image". Only the last `CMD` (and the last `ENTRYPOINT`) in a Dockerfile takes effect.

## CMD and ENTRYPOINT together

Arguments after the image name in `docker run` **replace `CMD`** and are **appended to an exec-form `ENTRYPOINT`**. `docker run --entrypoint` replaces the entrypoint itself.

| Command | Result with the example image |
|---|---|
| `docker run netinv:1.0` | `python app.py --port 8000` |
| `docker run netinv:1.0 --port 9000` | `python app.py --port 9000` (CMD replaced) |
| `docker run --entrypoint sh netinv:1.0 -c "id"` | `sh -c id` (both replaced) |

If the image had only `CMD ["python", "app.py", "--port", "8000"]` and no `ENTRYPOINT`, then `docker run netinv:1.0 --port 9000` would try to execute `--port 9000` as the command and fail: with no entrypoint, the arguments replace the whole command.

The Dockerfile reference summarises every combination:

| | No ENTRYPOINT | `ENTRYPOINT exec_entry p1_entry` (shell form) | `ENTRYPOINT ["exec_entry", "p1_entry"]` |
|---|---|---|---|
| **No CMD** | error, not allowed | `/bin/sh -c exec_entry p1_entry` | `exec_entry p1_entry` |
| **`CMD ["exec_cmd", "p1_cmd"]`** | `exec_cmd p1_cmd` | `/bin/sh -c exec_entry p1_entry` | `exec_entry p1_entry exec_cmd p1_cmd` |
| **`CMD exec_cmd p1_cmd`** | `/bin/sh -c exec_cmd p1_cmd` | `/bin/sh -c exec_entry p1_entry` | `exec_entry p1_entry /bin/sh -c exec_cmd p1_cmd` |

Rule of thumb: `ENTRYPOINT` (exec form) for the program the image *is*, `CMD` for its default, overridable arguments.

## Exec form vs shell form

`RUN`, `CMD` and `ENTRYPOINT` each have two forms:

- **Exec form**, a JSON array: `CMD ["python", "app.py"]`. Double quotes are required (it is JSON). No shell is started, so there is no variable expansion: `CMD ["echo", "$HOME"]` prints `$HOME` literally.
- **Shell form**, a plain string: `CMD python app.py`. Docker runs it as `/bin/sh -c "python app.py"`, so shell features (variables, `&&`, pipes) work.

The difference matters at **stop** time. `docker stop` sends `SIGTERM` to the container's main process (PID 1), waits a grace period (10 seconds by default for Linux containers), then sends `SIGKILL`. With exec form, `python` *is* PID 1 and the `SIGTERM` is delivered to it, so it can shut down cleanly. With a shell-form `ENTRYPOINT`, the reference warns, the command runs as a subcommand of `/bin/sh -c`, "which does not pass signals", so the application never sees `SIGTERM` and is killed after the timeout. A shell-form `ENTRYPOINT` also ignores `CMD` and any `docker run` arguments.

One Linux detail completes the picture: the kernel delivers a signal to a namespace's PID 1 only if that process has installed a handler for it, so a PID 1 that relies on the *default* "terminate on `SIGTERM`" action (a plain Python script does) still waits out the timeout. Either handle `SIGTERM` in the application (most web servers do) or start the container with `docker run --init`, which runs a small init process as PID 1 that forwards signals.

> **Exam tip:** Use exec form for `CMD` and `ENTRYPOINT`. Shell form is normal for `RUN`, where you want `&&` and line continuations. If you must use shell form for a long-running process, start it with `exec` (`ENTRYPOINT exec python app.py`) so it replaces the shell as PID 1.

## COPY vs ADD

Both copy files into the image. `COPY` copies from the build context, another build stage or an image, and nothing more. `ADD` can also fetch remote HTTPS URLs and Git repositories, and it **automatically extracts a local tar archive** (including gzip, bzip2 and xz compressed ones) into the destination. Remote archives are downloaded without extracting unless you use `ADD --unpack=true`.

Docker's best-practices guide says the two are functionally similar, tells you to use `COPY` to include files from the build context in the final image, and says `ADD` is best when you need to download a remote artifact as part of the build. Prefer **`COPY`** because it does only what it says; use `ADD` deliberately when you want its extra behaviour (extracting a local tarball, or a remote file pinned with `--checksum`).

> **Watch out:** `ADD rootfs.tar.gz /opt/` does not put a `.tar.gz` file in `/opt`: it unpacks the archive there. If you wanted the file itself, use `COPY` (or `ADD --unpack=false`).

## Layers and the build cache

Each instruction becomes a step, and filesystem-changing steps (`RUN`, `COPY`, `ADD`) add a **layer** on top of the previous ones. When you rebuild, Docker reuses a cached layer if the instruction is unchanged and, for `COPY` and `ADD`, the files' contents and metadata are unchanged (modification time alone does not count). Once one layer misses the cache, **every layer after it is rebuilt**, even if nothing about those later steps changed. For a `RUN` step only the command string is compared, so `RUN apt-get update` stays cached until something above it changes or you build with `--no-cache`.

That is why the example copies `requirements.txt` and installs dependencies **before** copying the rest of the code:

```dockerfile
# Slow: any edit to app.py invalidates this COPY, so pip reinstalls every time
COPY . .
RUN pip install --no-cache-dir -r requirements.txt

# Fast: pip only reruns when requirements.txt changes
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
```

Docker's guidance: order instructions from least frequently changed to most frequently changed. Also combine related shell commands in one `RUN` (`apt-get update && apt-get install -y ...`) so a cached `update` layer never pairs with a fresh `install`, and clean up in the same `RUN`, because files deleted in a later layer still occupy space in the earlier one.

## .dockerignore

`docker build .` sends the **build context** (the directory `.`) to the builder, and `COPY . .` copies all of it. A `.dockerignore` file in the context root excludes paths, which speeds up builds and keeps junk and secrets out of the image:

```text
.git
.venv
__pycache__/
*.pyc
.env
*.pem
tests/
```

## ENV, ARG and secrets

- `ENV` values **persist into the running container**: you can see them with `docker inspect` and override them with `docker run -e`.
- `ARG` values exist only **during the build** (and are passed to `RUN` steps as environment variables); they are not in the final container's environment.
- **Neither is safe for secrets.** The Dockerfile reference warns that build arguments are visible in `docker history` and in provenance attestations, and Docker's build-secrets page says build arguments and environment variables persist in the final image. Anything `COPY`'d into a layer stays in that layer even if a later `RUN rm` deletes it.

For a secret needed **during the build** (a private package index token), use a secret mount: `RUN --mount=type=secret,id=pypi_token ...` with `docker build --secret id=pypi_token,src=token.txt .`; the secret is available only to that `RUN` step and is not written into the image. For a secret needed **at run time** (an API key), inject it when the container starts, from a secret manager or an orchestrator's secret store (lesson 4.8).

```dockerfile
# Never do this: the token ends up in image metadata and history
ARG API_TOKEN
ENV API_TOKEN=$API_TOKEN
```

## Reading a Dockerfile in the exam

Ask in order: what is the base image and tag? Where is `WORKDIR`? What is copied, and in which order (cache)? What runs at build time (`RUN`) versus at start (`CMD`, `ENTRYPOINT`)? What does the container run by default, and what happens to `docker run` arguments? Which user does it run as? Which port does the app listen on (and remember that `EXPOSE` does not publish it)? Is anything secret in `ENV`, `ARG` or a copied file?

## Lab it yourself

Needs **Docker Desktop** on Windows or macOS, or **Docker Engine** or **Podman** on Linux (with Podman, replace `docker` with `podman`). You run these steps on your own computer.

1. Make a folder `netinv` with an empty `requirements.txt`, the Dockerfile above, a `.dockerignore`, and this `app.py`:

   ```python
   import argparse
   import json
   import os
   from http.server import BaseHTTPRequestHandler, HTTPServer

   SITE = os.environ.get("SITE", "lab")
   DEVICES = ["sw01", "rtr01"]


   class Handler(BaseHTTPRequestHandler):
       def do_GET(self):
           body = json.dumps({"site": SITE, "devices": DEVICES}).encode()
           self.send_response(200)
           self.send_header("Content-Type", "application/json")
           self.send_header("Content-Length", str(len(body)))
           self.end_headers()
           self.wfile.write(body)


   if __name__ == "__main__":
       parser = argparse.ArgumentParser()
       parser.add_argument("--port", type=int, default=8000)
       args = parser.parse_args()
       print(f"netinv listening on port {args.port}, site {SITE}")
       HTTPServer(("0.0.0.0", args.port), Handler).serve_forever()
   ```

2. Build it: `docker build -t netinv:1.0 .` Then change one line of `app.py` and build again: the `pip install` step should show as cached, and only the steps from the second `COPY` onwards rerun.
3. Swap the order (`COPY . .` before `RUN pip install`), edit `app.py`, rebuild, and watch `pip install` rerun.
4. Run `docker history netinv:1.0` to see one row per step, then `docker build --build-arg APP_VERSION=1.0.1 -t netinv:1.0.1 .` and find the value in `docker image inspect netinv:1.0.1`.
5. Show what the image will run: `docker image inspect --format "{{.Config.Entrypoint}} {{.Config.Cmd}}" netinv:1.0`. Then run `docker run --rm netinv:1.0 --port 9000` and read the first log line: the argument replaced `CMD` but `ENTRYPOINT` stayed. Press Ctrl+C to stop it (if it does not stop, run `docker ps` and `docker stop` with its name from another terminal). Lesson 4.7 covers these run commands.

## Key takeaways

- `FROM` starts the build; `WORKDIR` sets the directory; `COPY` brings in files; `RUN` executes at build time and creates a layer; `ENV` persists into containers; `ARG` is build-time only; `USER` drops root; `EXPOSE` only documents a port.
- `CMD` supplies defaults that `docker run` arguments replace; an exec-form `ENTRYPOINT` always runs and receives those arguments; `--entrypoint` overrides it.
- Exec form (JSON array) runs the program as PID 1 so `docker stop`'s `SIGTERM` reaches it (it must handle it, or use `--init`); shell form wraps it in `/bin/sh -c`, which does not pass signals.
- Prefer `COPY`; `ADD` also fetches URLs and auto-extracts local tar archives.
- A changed layer invalidates every layer after it: copy dependency lists and install them before copying source code, and use `.dockerignore`.
- Never put secrets in `ENV`, `ARG` or copied files; use build secret mounts at build time and inject secrets at run time.
