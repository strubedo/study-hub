## OWASP and the Top 10

**OWASP**, the Open Worldwide Application Security Project, is a non-profit that publishes free application security guidance. Its best-known document, the **OWASP Top 10**, is "a standard awareness document for developers and web application security" listing the most critical web application risks. The current edition is the **OWASP Top 10:2025**:

| Rank | Category |
|---|---|
| A01:2025 | Broken Access Control (includes **CSRF**, CWE-352) |
| A02:2025 | Security Misconfiguration |
| A03:2025 | Software Supply Chain Failures |
| A04:2025 | Cryptographic Failures |
| A05:2025 | **Injection** (includes **SQL injection**, CWE-89, and **XSS**, CWE-79) |
| A06:2025 | Insecure Design |
| A07:2025 | Authentication Failures |
| A08:2025 | Software or Data Integrity Failures |
| A09:2025 | Security Logging and Alerting Failures |
| A10:2025 | Mishandling of Exceptional Conditions |

Injection fell from third place in the 2021 edition to fifth in 2025. Cross-site scripting has not had its own category since the 2017 edition; it is part of Injection. CSRF is listed under Broken Access Control, as it was in 2021. The exam names three threats: **XSS**, **SQL injection** and **CSRF**. For each, know what the attacker does, what the victim experiences and the standard defence.

## SQL injection

**SQL injection** happens when untrusted input is pasted into the **text** of a SQL statement, so the input can change the statement's structure instead of being treated as a value. A lookup written with an f-string (real output, Python 3.14 with the standard `sqlite3` module and an in-memory table of three devices):

```python
name = request_args["hostname"]       # attacker sends: nosuch' OR '1'='1
query = f"SELECT hostname, mgmt_ip FROM devices WHERE hostname = '{name}'"
cur.execute(query)
```

```text
SELECT hostname, mgmt_ip FROM devices WHERE hostname = 'nosuch' OR '1'='1'
[('sw01', '10.10.20.11'), ('rtr01', '10.10.20.1'), ('fw01', '10.10.20.254')]
```

The quote in the input closed the string, and `OR '1'='1'` made the condition true for every row, so the query returned the whole table. With other payloads an attacker can read other tables, bypass a login (`admin'--` comments out the password check in a naive query), or modify and delete data.

**Defence: parameterised queries** (prepared statements). The SQL text is fixed, with placeholders, and the values are passed separately through the database driver, which never interprets them as SQL:

```python
cur.execute("SELECT hostname, mgmt_ip FROM devices WHERE hostname = ?", (name,))
```

```text
[]                                    # the attack string is just a hostname that does not exist
[('sw01', '10.10.20.11')]             # the same call with name = "sw01"
```

The placeholder style depends on the driver: `sqlite3` uses `?` (its `paramstyle` is `qmark`), `psycopg` for PostgreSQL uses `%s`, and ORMs such as SQLAlchemy and Django parameterise for you.

Why not just escape quotes? The OWASP SQL Injection Prevention Cheat Sheet's primary defences are parameterised queries and, for parts that cannot be parameters (table or column names, `ASC`/`DESC`), mapping the user's choice to a fixed allow-list of values; it calls manual escaping "error-prone" and "strongly discouraged". Escaping depends on the database, the character set and the context, and one missed case is enough. Parameterisation removes the problem rather than trying to neutralise every dangerous character. Least-privilege database accounts limit the damage if something slips through.

## Cross-site scripting (XSS)

**XSS** is injection into a **web page**: the application includes untrusted data in HTML it sends to a browser without encoding it, so the browser runs attacker-supplied script **in the context of the trusted site**. That script can read what the page shows, act as the user, steal session tokens that are readable from JavaScript, or rewrite the page (a fake login form). The victim is the user's browser; the server is only the delivery vehicle.

OWASP describes three types:

| Type | Where the payload lives | Example |
|---|---|---|
| **Stored** (persistent, Type II) | Saved on the server (database, comment, device description field) and served to **everyone** who views it | A device "location" field set to `<script>...</script>` runs in every admin's browser that opens the inventory page |
| **Reflected** (non-persistent, Type I) | In the **request** (usually a link's query string) and immediately echoed back in the response | `https://inv.example.com/search?q=<script>...</script>` sent to a victim in a phishing email |
| **DOM-based** (Type 0) | Never reaches the server's HTML: the page's own JavaScript reads attacker-controlled data (such as `location.hash`) and writes it into the page unsafely (`innerHTML`) | `https://inv.example.com/#<img src=x onerror=...>` |

Stored XSS needs no further action from the attacker once planted and hits every viewer; reflected XSS needs each victim to open a crafted link.

**Defences** (OWASP XSS Prevention Cheat Sheet):

1. **Output encoding** for the context the data lands in. In HTML body text, `<`, `>`, `&`, `"` and `'` become entities, so the browser shows them as text. Python's `html.escape('<script>alert(1)</script>')` returns `&lt;script&gt;alert(1)&lt;/script&gt;`. HTML attributes, JavaScript, CSS and URLs each need their own encoding.
2. **Use a framework that encodes automatically**, such as Jinja2 with autoescaping, Django templates or React, and avoid the escape hatches that switch it off (`|safe`, `mark_safe`, `dangerouslySetInnerHTML`).
3. For DOM-based XSS, use safe sinks: `textContent` instead of `innerHTML`.
4. If users must submit HTML, sanitise it with a proven library rather than your own regex.
5. **Content Security Policy (CSP)** as defence in depth: a response header such as `Content-Security-Policy: default-src 'self'` tells the browser which sources may load scripts and other resources, blocking injected inline script. MDN states that CSP is not an alternative to proper input and output handling, and the OWASP cheat sheet says it should not be the primary defence.
6. Mark session cookies `HttpOnly` so script cannot read them (this limits the damage of XSS; it does not prevent it).

Input validation helps (a VLAN name should match `^[A-Za-z0-9_-]{1,32}$`), but encoding on output is the defence that matters, because the same data may be safe in one context and dangerous in another.

## Cross-site request forgery (CSRF)

**CSRF** tricks a user's **already authenticated browser** into sending a request the user did not intend. The attack works because browsers automatically attach the site's cookies (including the session cookie) to requests sent to that site, even when the request was started by a page on another site.

```text
1. Alice logs in to https://inv.example.com; her browser stores the session cookie.
2. In another tab she opens a page on attacker.example.net containing:
     <form action="https://inv.example.com/devices/sw01/delete" method="POST"></form>
     <script>document.forms[0].submit()</script>
3. Her browser sends the POST to inv.example.com WITH her session cookie.
4. The server sees a valid session and deletes sw01.
```

Key points:

- The attacker never sees the response or the cookie; CSRF makes the victim **perform an action**, it does not steal data.
- It needs the victim's authenticated session in the browser, and it only matters for **state-changing** requests. As the OWASP cheat sheet says, the attack can only do what the user is permitted to do.
- APIs authenticated by an `Authorization` header that the client script sets explicitly (a bearer token or API key) are not exposed in the same way, because the browser does not attach that header automatically. Cookie-authenticated web apps and APIs are.

**Defences** (OWASP CSRF Prevention Cheat Sheet, MDN):

1. Use the framework's **built-in CSRF protection** if it has one.
2. **Anti-CSRF tokens.** The server puts an unpredictable token, tied to the user's session, in each form (or a custom header for JavaScript requests) and rejects state-changing requests without the right token. The attacker's page cannot read the token, so it cannot forge the request (the *synchronizer token pattern*; stateless apps use the signed *double-submit cookie* pattern).
3. **`SameSite` cookies.** `Set-Cookie: session=...; Secure; HttpOnly; SameSite=Lax` (or `Strict`). With `Strict` the browser sends the cookie only on requests that originate from the same site; with `Lax` it also sends it on cross-site top-level navigations that use a safe method (a clicked link), but not on cross-site `POST`s, `fetch()` calls, or image and frame loads. Some browsers default to `Lax` when the attribute is missing; `SameSite=None` requires `Secure`. OWASP treats SameSite as defence in depth alongside tokens.
4. **Never change state with `GET`**, and check `Origin`/`Referer` or the `Sec-Fetch-Site` header on sensitive requests. Require re-authentication for the most sensitive actions.

> **Watch out:** XSS defeats CSRF defences. The OWASP cheat sheet is explicit: script injected into the site runs as the site, so it can read the anti-CSRF token and send a valid request. Fix XSS first.

## The three side by side

| | SQL injection | XSS | CSRF |
|---|---|---|---|
| Target | The database behind the app | Other users' browsers | The app, through a logged-in user's browser |
| Attacker supplies | Input that becomes SQL code | Input that becomes HTML or script | A page or link that makes the browser send a request |
| Needs a victim's session | No | No (but steals or uses it) | Yes |
| Primary defence | Parameterised queries (plus allow-lists) | Context-aware output encoding (plus CSP, safe frameworks) | Anti-CSRF tokens (plus SameSite cookies, no state-changing GETs) |
| OWASP Top 10:2025 | A05 Injection | A05 Injection | A01 Broken Access Control |

> **Exam tip:** Look at the scenario's verb. Input changes a **query** = SQL injection. Input ends up **running in other people's browsers** = XSS (saved for everyone = stored; bounced off a link = reflected; the page's own JavaScript = DOM). Another site makes a **logged-in user's browser submit an action** = CSRF.

## Lab it yourself

Any computer with Python 3; everything stays on your machine.

1. In Python, create an in-memory database: `import sqlite3; con = sqlite3.connect(":memory:"); cur = con.cursor()`, create the `devices` table, and insert three rows.
2. Run the f-string query with `name = "nosuch' OR '1'='1"` and print the rows, then run the parameterised version with the same value and compare.
3. Try `name = "sw01'; DROP TABLE devices; --"` with the f-string version. `sqlite3`'s `execute` refuses to run more than one statement and raises an error, but other drivers and APIs may not; the parameterised version simply finds nothing.
4. Print `html.escape("<img src=x onerror=alert(1)>")` and paste the result into an `.html` file opened in your browser: the tag is shown as text, not run.
5. Install the free **OWASP Juice Shop** practice application (it runs from a container image or with Node.js) and use its scoreboard to try a reflected XSS and a login SQL injection in a safe target you own.

## Key takeaways

- OWASP Top 10:2025 is current: Injection (A05) includes SQL injection and XSS; CSRF sits under Broken Access Control (A01).
- SQL injection: input changes the query's structure; defend with parameterised queries and allow-lists, not manual escaping.
- XSS: untrusted data rendered as HTML runs as script in victims' browsers; stored (saved, hits every viewer), reflected (echoed from a crafted request), DOM-based (client-side JavaScript); defend with contextual output encoding, auto-escaping templates and CSP as defence in depth.
- CSRF: another site makes a logged-in user's browser send a state-changing request with its cookies; defend with anti-CSRF tokens and `SameSite` cookies, and never change state with GET.
- XSS defeats CSRF tokens, so XSS must be fixed for CSRF defences to hold.
