## Three areas

Topic 4.8 names three security issues every application, including every automation script, has to handle: **secret protection**, **encryption** (in storage and in transport) and **data handling**. The OWASP Top 10:2025 lists *A04 Cryptographic Failures* (weak or missing encryption, exposed sensitive data) and *A02 Security Misconfiguration* among the most common web risks, and leaked credentials are behind many real breaches.

## Secret protection

A **secret** is anything that grants access: API keys and tokens, passwords, SSH and TLS private keys, SNMP communities, webhook signing secrets, database connection strings.

### Where secrets must never go

- **Source code.** `TOKEN = "..."` in a script is copied to every clone, fork, laptop and backup.
- **Git history.** Deleting the line in a later commit does not help: the old commit still holds it, and anyone with the repository can read it. Public repositories are scanned for keys by attackers within minutes of a push.
- **Container images.** Values in `ENV` or `ARG`, or files `COPY`'d in, are readable by anyone who can pull the image (`docker history`, `docker inspect`, or by unpacking the layers), even if a later layer deletes the file (lesson 4.6).
- **Logs, error messages, tickets and chat.** A debug line that prints request headers prints the `Authorization` header too.
- **URLs.** Query strings end up in proxy and server logs and browser history (lesson 2.7).

### Where secrets should come from

| Method | How it works | Notes |
|---|---|---|
| **Environment variables** | The script reads `os.environ["MERAKI_API_KEY"]`; the value is set outside the code | Good for local use and CI. Values are visible to the process and its children, so keep them out of logs |
| **Local `.env` file** | A `KEY=value` file loaded at start-up (for example with `python-dotenv`) | Must be in **`.gitignore`**; commit a `.env.example` with placeholders instead |
| **CI/CD secret variables** | The pipeline injects protected, masked variables into jobs at run time | Never echo them; restrict them to protected branches |
| **Secret manager** | The application fetches secrets at run time from HashiCorp Vault, a cloud secrets manager or similar, authenticated by its own identity | Central storage, access control, audit logs, automatic rotation and short-lived credentials |
| **Orchestrator secrets** | Docker or Kubernetes secrets mounted into the container as files | Keeps them out of the image |

The OWASP Secrets Management Cheat Sheet recommends centralising secrets, granting least privilege, automating rotation, and auditing every access.

```python
import os

API_KEY = os.environ.get("MERAKI_API_KEY")
if not API_KEY:
    raise SystemExit("Set MERAKI_API_KEY first (see README)")
```

> **Watch out:** `.gitignore` only stops **untracked** files from being added. If the file was already committed, Git keeps tracking it: run `git rm --cached .env` (lesson 1.8), commit, and treat the secret as leaked, because it is still in history.

### When a secret leaks

1. **Revoke or rotate it immediately** at the issuing system (regenerate the API key, change the password, revoke the token). This is the only step that actually stops misuse; assume it has already been copied.
2. Update everything that legitimately uses it with the new value, ideally from a secret manager.
3. Check the issuer's logs for use of the old secret.
4. Then clean up: remove it from the code, rewrite history if needed (for example with `git filter-repo`) and add scanning (pre-commit hooks or the hosting platform's secret scanning) so it does not happen again.

Making the repository private or deleting the commit afterwards does not un-leak a secret.

## Encryption in transit

Data crossing a network should be encrypted with **TLS** (TLS 1.2 or, preferably, TLS 1.3). TLS provides **confidentiality** (encryption), **integrity** (tampering is detected) and **server authentication** (the certificate proves you reached the real server, not a man in the middle).

- Use `https://` for every API call and webhook; use SSH, not Telnet, for device access; NETCONF runs over SSH and RESTCONF over HTTPS.
- **Validate certificates.** `requests` does by default; `verify=False` turns the protection off and allows a man-in-the-middle to read the token you send. For a private CA, point `verify` at the CA bundle instead.
- Behind a load balancer or reverse proxy that terminates TLS (lesson 4.9), decide whether the internal hop also needs TLS; regulated data usually requires it.
- **Mutual TLS** (client certificates) authenticates the client as well, common between services.

## Encryption at rest

Data stored on disk, in databases, backups and object storage should be encrypted so that a stolen disk, laptop or backup tape is useless: full-disk encryption (BitLocker, FileVault, LUKS), database or storage-level encryption, and encrypted backups. The protection is only as good as the **key management**: keep keys in a key management service or hardware security module, separate from the data, with rotation and access logging.

**Passwords are a special case.** An application that checks user passwords must not store them encrypted (encryption is reversible) and must never store them in plain text or base64. Store a **salted, slow, one-way hash**. The OWASP Password Storage Cheat Sheet recommends **Argon2id**; if it is not available, **scrypt**; **bcrypt** for legacy systems; and **PBKDF2** where FIPS-140 compliance is required. It explains that password hashes should be deliberately slow, unlike general-purpose hashes such as MD5 and SHA-1 that were designed to be fast (SHA-256 is fast too), because speed lets attackers try guesses quickly. To check a login, hash the submitted password with the stored salt and compare.

> **Exam tip:** "Protect data in transit" means TLS (HTTPS, SSH). "Protect data at rest" means disk, database or backup encryption with managed keys. "Store user passwords" means a salted slow hash such as Argon2id or bcrypt, not encryption and never base64.

## Data handling

How an application collects, stores, logs and deletes data is a security control in itself:

- **Minimisation.** Collect and keep only what the function needs. A network inventory needs hostnames and IP addresses, not the home addresses of the people who own the laptops.
- **Classification and PII.** Know which fields are personal data (names, emails, phone numbers, client MAC and IP addresses tied to a person) or otherwise sensitive, and apply stricter access, encryption and retention to them. Laws such as GDPR set rules on how personal data is processed and kept.
- **Least privilege.** Give scripts and service accounts read-only API keys when they only read, and scope tokens to what they need.
- **Logging without secrets.** Never log passwords, tokens, full `Authorization` headers or session cookies; mask or redact sensitive fields (`token=****abcd`) and keep PII out of logs unless it is essential. Logs travel to many systems and people.
- **Validate input.** Treat every external input (API responses, files, form fields) as untrusted; this is what prevents the injection attacks in lesson 4.10.
- **Retention and disposal.** Delete data when it is no longer needed, including copies in backups, test environments and exports.

```python
# Bad: the token ends up in the log file and in every log pipeline it feeds
log.info("Calling %s with headers %s", url, headers)

# Better: log what you need to troubleshoot, never the credential
log.info("GET %s -> %s in %.2fs", url, resp.status_code, elapsed)
```

## Lab it yourself

Any computer with Python 3 and Git.

1. In a new Git repository, create `.env` containing `MERAKI_API_KEY=example-token-not-real` and a `.gitignore` containing `.env`. Run `git status`: `.env` is not listed.
2. Write a script that reads the key with `os.environ.get` and exits with a clear message if it is missing. Run it without the variable, then set it for one run: `MERAKI_API_KEY=example-token-not-real python3 script.py` on macOS and Linux, or `$env:MERAKI_API_KEY="example-token-not-real"; python script.py` in PowerShell.
3. Commit a file containing a fake key, then "remove" it in a second commit. Run `git log -p` and find the key in history. That is why a leaked key must be rotated.
4. Run `python3 -c "import hashlib; print(hashlib.sha256(b'example-password').hexdigest())"` twice: same output every time, and computed in microseconds. That speed and lack of salt are why a plain SHA-256 is not a password hash.

## Key takeaways

- Secrets never go in code, Git history, images, URLs or logs; load them from environment variables, an ignored `.env`, CI secret variables or a secret manager.
- A leaked secret must be revoked and rotated first; deleting the commit or making the repository private is not enough.
- In transit: TLS (HTTPS, SSH) with certificate validation; at rest: disk, database and backup encryption with properly managed keys.
- Passwords are stored as salted slow hashes (Argon2id, bcrypt, PBKDF2), never encrypted or encoded.
- Handle data with minimisation, classification of PII, least privilege, redacted logs, input validation and defined retention.
