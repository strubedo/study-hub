## What a pipeline is for

A **CI/CD pipeline** is an automated sequence that takes a change from a commit in version control to a running application, checking it at every step. Each run is triggered by an event (usually a push or a merge request), runs the same steps the same way every time, and stops at the first step that fails. The goal is that every change is small, tested and deployable, and that nobody builds or deploys by hand.

Domain 1 covered Git (lesson 1.8) and test-driven development (lesson 1.3); the pipeline is where those two meet. Domain 5 (topic 5.4) applies the same ideas to network configuration.

## The components

```text
 Source       Build            Test              Artifact repository     Deploy
 (Git)   -->  (compile,   -->  (unit, lint,  -->  (image registry,   -->  staging --> production
 push or      package,         integration,       package repo)           (automatic or
 merge        build image)     security scans)    versioned artifact      approved)
   ^                                                                         |
   +------------------- feedback: pass/fail, logs, notifications <-----------+
```

| Component | What it does | Typical tools |
|---|---|---|
| **Source repository** | Holds the code, tests, Dockerfile and the pipeline definition itself; a push or merge triggers the pipeline | GitHub, GitLab, Bitbucket |
| **CI server / runner** | Reads the pipeline definition and runs each job in a clean environment, often a container | GitLab CI, GitHub Actions, Jenkins |
| **Build** | Turns source into something runnable: installs dependencies, compiles, builds a container image | `pip`, `docker build` |
| **Test** | Unit tests (lesson 4.5), linting and style checks, integration tests, dependency and image vulnerability scans | `python -m unittest`, `pytest`, `pylint`, scanners |
| **Artifact repository** | Stores the built, versioned output so the **same** artifact is promoted through every environment | Container registry, PyPI-style package repo, Artifactory, Nexus |
| **Deploy** | Releases the artifact to staging, then production, ideally with the same automated method each time | Ansible, Terraform, Kubernetes, `docker` on a host |
| **Feedback and monitoring** | Reports results to the author and watches the running app | Pipeline status, chat or email notifications, dashboards |

Two principles hold the pipeline together:

- **Build once, deploy many.** The image tested in staging is the exact image deployed to production, identified by a version tag or digest, not rebuilt.
- **Fail fast.** Cheap checks (lint, unit tests) run first; a failure stops the run before anything is published or deployed, and the author hears about it within minutes.

## CI, continuous delivery and continuous deployment

| Practice | What is automated | Where it stops |
|---|---|---|
| **Continuous integration (CI)** | Every push is merged into a shared branch frequently, built and tested automatically | At a tested build; the team fixes a broken build immediately |
| **Continuous delivery** | CI plus automatic packaging and deployment to staging; every passing build is **ready** to release | A **manual approval** (a person or a business decision) releases to production |
| **Continuous deployment** | Everything, including production | Nowhere: every change that passes all stages goes live **automatically** |

Martin Fowler's summary is the clearest: continuous deployment means every change goes through the pipeline and automatically gets put into production, while continuous delivery means you are *able* to deploy frequently but may choose not to. You must be doing continuous delivery to do continuous deployment.

> **Exam tip:** The only difference between continuous delivery and continuous deployment is the **production release gate**: a manual approval means delivery; no human step means deployment. Both share the "CD" abbreviation, so read the scenario.

## Reading a pipeline definition

Pipelines are defined as code in the repository, usually YAML. This GitLab CI example builds, tests, publishes and deploys an inventory API:

```yaml
stages:
  - test
  - build
  - publish
  - deploy

unit-tests:
  stage: test
  image: python:3.14-slim
  script:
    - python -m unittest -v

build-image:
  stage: build
  script:
    - docker build -t registry.example.com/netops/netinv:$CI_COMMIT_SHORT_SHA .

publish-image:
  stage: publish
  script:
    - docker push registry.example.com/netops/netinv:$CI_COMMIT_SHORT_SHA

deploy-staging:
  stage: deploy
  script:
    - ./deploy.sh staging $CI_COMMIT_SHORT_SHA

deploy-production:
  stage: deploy
  script:
    - ./deploy.sh production $CI_COMMIT_SHORT_SHA
  when: manual
```

How to read it:

- `stages` sets the order. Jobs in a stage run after every job in the previous stage succeeds (GitLab's default `when: on_success`), so a failed unit test means no image is built, pushed or deployed.
- `$CI_COMMIT_SHORT_SHA` is a predefined variable holding the first eight characters of the commit SHA, so each image tag points back to the exact commit: traceable and never overwritten by the next build.
- `when: manual` puts `deploy-production` in the pipeline as a job that waits for someone to start it. This pipeline is therefore **continuous delivery**. Remove that line and every passing commit would reach production: **continuous deployment**.
- Credentials for the registry and the deploy script are not in the file; they come from the CI system's protected secret variables (lesson 4.8).

The same structure appears in GitHub Actions (`jobs`, `steps`, environment protection rules for approvals) and in Jenkins (`stages` in a Jenkinsfile, an `input` step for approval).

> **Real world:** Order cheap checks first and keep the unit-test stage under a few minutes. A pipeline that takes an hour gets bypassed. Mocks (lesson 4.5) keep unit tests independent of real devices and APIs so they run anywhere, including the CI runner.

## Benefits

- Every change is built and tested the same way, so "it worked on my machine" disappears.
- Small changes reach users quickly, and a failing change is caught minutes after it was written, when it is cheapest to fix.
- Releases become routine and low-risk, and rolling back means redeploying the previous artifact.
- The pipeline definition, test results and artifact tags form an audit trail of what was deployed, when and from which commit.

## Lab it yourself

Any computer with Git and a free GitHub or GitLab account:

1. Create a repository containing the `netutil.py` and `test_netutil.py` files from lesson 4.5.
2. Add a minimal pipeline. On GitLab, a `.gitlab-ci.yml` with a single `unit-tests` job like the one above. On GitHub, `.github/workflows/test.yml` with a job that uses `actions/setup-python` and runs `python -m unittest -v`.
3. Push and watch the pipeline run. Then break a test on purpose, push, and confirm the pipeline turns red and later stages do not run.
4. Add a `deploy` job that only prints "deploying" and mark it manual (`when: manual` on GitLab, or an environment with required reviewers on GitHub). You now have continuous delivery.

## Key takeaways

- Pipeline components: source repository (trigger), CI runner, build, test, artifact repository, deploy, and feedback.
- Build once and promote the same versioned artifact through staging to production; fail fast on the cheapest checks.
- CI = frequent merges built and tested automatically. Continuous delivery = always releasable, with a manual production gate. Continuous deployment = no manual gate.
- Pipelines are code in the repository (`.gitlab-ci.yml`, GitHub Actions workflow, Jenkinsfile); stages run in order and a failure stops later stages.
- Secrets come from the CI system's protected variables, never from the pipeline file.
