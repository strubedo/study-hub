## What edge computing is

**Edge computing** means running application code close to where data is produced or used (in a branch, a factory, a store, a vehicle or a cell site) instead of sending everything to a central data centre or public cloud region. The "edge" is a location, not a product: it can be a small server rack in a branch, an industrial gateway on a factory floor, or the compute module inside a router or switch you already manage.

A useful picture has three tiers:

```text
  Devices and sensors          Edge                         Cloud or data centre
  (cameras, PLCs, meters)  ->  (gateway, router, small   ->  (central apps, long-term
                               server at the site)           storage, analytics, ML training)
  produce raw data             filter, decide, act locally   aggregate, store, report
```

Cisco's IoT material also uses the word **fog computing** for the same idea of a layer of compute between devices and the cloud; for the exam, treat "fog" and "edge" as closely related terms for computing near the data source.

Edge does not replace the cloud. Typically the edge handles what must be fast or local, and the cloud keeps what benefits from being central: dashboards, history, model training and fleet management.

## The benefits

| Benefit | What it means | Example |
|---|---|---|
| **Lower latency** | A decision made on site does not wait for a round trip to a distant region | A vision system on a production line must reject a faulty part within milliseconds; a 60 ms round trip to a cloud region is too slow |
| **Less bandwidth** | Raw data is processed locally and only results or summaries go upstream | 40 cameras produce gigabits per second; the edge sends "3 defects in the last hour" instead of the video |
| **Data locality and sovereignty** | Sensitive or regulated data can stay on site or in-country | Patient monitoring data is analysed in the hospital; only anonymised statistics leave |
| **Resilience and autonomy** | The site keeps working when the WAN link is down | A store keeps processing payments and stock updates offline and syncs when the link returns |
| **Lower cost of backhaul and cloud processing** | Fewer bytes sent and stored centrally | Metered cellular links at remote sites carry only alerts |
| **Context awareness** | Local code can react to local conditions | A branch router app reads a local sensor and changes a QoS policy |

> **Exam tip:** When a question describes strict response times, huge volumes of raw sensor data, limited or expensive uplinks, a requirement that data must not leave a site, or a site that must keep working offline, the answer is edge computing. "Unlimited elastic capacity" and "no hardware to manage" are public cloud benefits, not edge benefits.

## Applications on network devices: Cisco IOx

Network devices already sit at every site, so running small applications on them avoids deploying extra servers. Cisco's application hosting framework for this is **Cisco IOx**. The Cisco DevNet IOx documentation describes it as an application environment that lets you run IoT applications "in the fog" with secure connectivity to Cisco IOS software, and it hosts **Docker-based** applications on supported Cisco gateways and routers.

Key points about IOx worth knowing:

- Applications are packaged from a Docker image with Cisco's **ioxclient** tool and deployed through a local manager or a cloud-based one.
- The platform handles the application lifecycle at scale: install, start, stop, upgrade, back up data and view logs.
- **Application signing** lets the device run only trusted applications.
- Typical uses: reading Modbus or other industrial sensor data on an industrial router, filtering telemetry, protocol translation, or a local monitoring agent.

So the "edge" in a Cisco network can literally be the router: the app runs next to IOS on the same box and talks to local sensors and to the cloud.

> **Real world:** Cisco IOS XE switches and routers also support application hosting (for example running a Docker container on a Catalyst switch with spare compute). The idea is the same: use the device that is already at the site as the edge compute node.

## The trade-offs

Edge is not free. Running code at hundreds of sites brings its own problems:

- **Many small locations to manage.** Software must be deployed, patched and monitored everywhere, so automation (CI/CD, lesson 4.4) and central management are essential.
- **Limited resources.** A gateway or router has a fraction of a server's CPU, memory and storage; applications must be small, which is one reason containers are popular at the edge.
- **Physical security.** Edge hardware sits in cabinets, kiosks and vehicles where people can touch it; disk encryption and signed software matter more than in a locked data centre.
- **Consistency.** Data processed in many places must be reconciled centrally, and versions can drift between sites.

## Lab it yourself

You do not need edge hardware to see the idea; any computer with Python 3 is enough.

1. Write a small Python script that generates 10,000 fake temperature readings (for example `random.gauss(21, 2)`), then "sends" them by writing them to a file. Note the file size.
2. Change the script to process the readings locally and write only a summary: count, minimum, maximum, mean and any readings above 27. Compare the sizes. That reduction is the bandwidth benefit.
3. Add a simulated outage: if a variable `wan_up` is false, keep summaries in a local list and "send" them all when it becomes true. That is the resilience benefit.
4. Optional: in the DevNet Learning Labs, find the Cisco IOx labs (they use the DevNet Sandbox) and read how an application is packaged from a Docker image with `ioxclient`.

## Key takeaways

- Edge computing runs code near the data source; the cloud keeps central storage, analytics and management.
- The main benefits are lower latency, less bandwidth, data locality, and resilience when the WAN fails.
- Cisco IOx hosts (Docker-based) applications on Cisco routers and gateways, so the network device becomes the edge compute node; applications can be signed so only trusted code runs.
- Edge trades central simplicity for many small, resource-limited, physically exposed sites, so it depends on automation.
- Scenario words to spot: "milliseconds", "huge raw data", "expensive or unreliable uplink", "data must stay on site", "keep working offline".
