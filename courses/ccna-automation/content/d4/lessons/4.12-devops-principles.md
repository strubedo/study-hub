## What DevOps is

**DevOps** is a set of cultural principles and technical practices that bring the people who **build** software (development) and the people who **run** it (operations) into one way of working, so changes reach users quickly, safely and repeatedly. It grew out of agile and lean thinking (lesson 1.4) in the late 2000s, when fast development cycles kept colliding with slow, manual, risk-averse release processes: developers were measured on shipping change, operations on stability, and each blamed the other when a release failed.

DevOps is not a job title, a team you hire or a tool you buy. A team with a CI server but quarterly releases and hand-offs over a wall is not doing DevOps.

## Two ways to describe the principles

### CALMS

The CALMS acronym, credited to Jez Humble (co-author of *The DevOps Handbook* and *Continuous Delivery*), gives five dimensions:

| Letter | Principle | What it looks like |
|---|---|---|
| **C**ulture | Shared ownership and blameless collaboration | One team owns a service from code to production ("you build it, you run it"); post-incident reviews look for causes, not culprits |
| **A**utomation | Automate repetitive, error-prone work | CI/CD pipelines (lesson 4.4), automated tests (4.5), container builds (4.6), infrastructure as code |
| **L**ean | Small batches, limit work in progress, remove waste | Small, frequent releases; short-lived branches; fewer hand-offs and approval queues |
| **M**easurement | Decide with data | Pipeline and deployment metrics, monitoring and alerting, the DORA metrics below |
| **S**haring | Share knowledge, tools and responsibility | Shared dashboards and runbooks, code review, the same pipeline for dev and ops changes |

### The Three Ways

*The Phoenix Project* and *The DevOps Handbook* (Gene Kim and others) describe three principles:

1. **Flow** (left to right, development to operations to the customer): optimise the whole system, not one silo; make work visible; small batches; never pass a known defect downstream.
2. **Feedback** (right to left): shorten and amplify feedback loops, such as tests that fail within minutes, monitoring and alerts that reach the team that wrote the code, and user feedback.
3. **Continual learning and experimentation**: a culture that takes calculated risks, learns from failure and treats practice and repetition as the route to mastery.

## The practices that follow

- **Automation everywhere.** Builds, tests, security scans, deployments, environment creation and rollbacks are scripted and run by the pipeline, so they are fast, repeatable and auditable.
- **Small, frequent releases.** A change of ten lines is easy to review, test and roll back; a quarterly release of 400 changes makes every failure a hunt. Frequent small releases lower risk instead of raising it.
- **Continuous integration and delivery.** Everyone merges to a shared branch at least daily, and every passing build is deployable (lesson 4.4).
- **Shared ownership.** Developers carry some operational responsibility (on-call, dashboards for their service), and operations engineers work in code and version control.
- **Monitoring, observability and feedback.** Metrics, logs and traces show how each release behaves in production, and alerts go to the people who can fix the code.
- **Infrastructure as code (IaC).** Servers, networks and cloud resources are defined in version-controlled files (Ansible playbooks, Terraform configurations) and changed through the same review and pipeline as application code. For a network engineer this is where DevOps lands: device configuration as code, tested in a pipeline, deployed automatically. Domain 5 covers IaC (topic 5.5), CI/CD for infrastructure (5.4) and the tools (5.6).
- **Security built in** (sometimes called DevSecOps): dependency scanning, secret scanning and image scanning are pipeline stages, not a review at the end.

## Measuring it: the DORA metrics

The DORA research programme (DevOps Research and Assessment, whose site dora.dev is published by Google Cloud) identified software delivery metrics that predict organisational performance. Its current guidance (dora.dev) uses **five** metrics, grouped as throughput and instability:

| Group | Metric | Measures |
|---|---|---|
| Throughput | **Change lead time** | Time from a commit in version control to running in production |
| Throughput | **Deployment frequency** | How often the team deploys to production |
| Throughput | **Failed deployment recovery time** | How long it takes to recover from a deployment that needs immediate intervention |
| Instability | **Change fail rate** | Share of deployments that need immediate intervention (rollback or hotfix) |
| Instability | **Deployment rework rate** | Share of deployments that were unplanned, made because of a production incident |

Older material lists the original **four keys** (deployment frequency, lead time for changes, change failure rate, time to restore service); DORA replaced MTTR with failed deployment recovery time and added rework rate. DORA's key finding is that **speed and stability are not trade-offs**: the best performers do well on all of them, and the usual way to improve all of them is to make each change smaller.

> **Exam tip:** DevOps questions are about principles: break down silos and share ownership, automate the delivery pipeline, release small changes often, measure, and use feedback from production. If an option says DevOps means "a separate DevOps team that deploys for developers", "releasing less often to reduce risk" or "buying a specific tool", it is wrong.

## Lab it yourself

Any computer with Git and a free GitHub or GitLab account.

1. Take the repository from the lesson 4.4 lab (unit tests plus a pipeline). Make five small commits over an hour, each with a passing test, and push each one. Note how quickly the pipeline tells you whether each change is good.
2. Compute two DORA metrics for that hour: deployment frequency (passing pipeline runs that reached your manual "deploy" job) and change lead time (commit time to deploy-job time).
3. Write a one-page blameless review of a past outage you know (no names): what happened, what the timeline was, why the system allowed it, and two automated checks that would have caught it.

## Key takeaways

- DevOps unites development and operations around shared ownership of a service, from commit to production.
- CALMS: Culture, Automation, Lean, Measurement, Sharing. The Three Ways: flow, feedback, continual learning and experimentation.
- Core practices: automate the pipeline, release small changes frequently, integrate continuously, monitor and feed results back, build security in.
- Infrastructure as code applies the same practices to servers and networks (Domain 5).
- DORA measures delivery with change lead time, deployment frequency, failed deployment recovery time, change fail rate and deployment rework rate; speed and stability improve together.
