## Following one request

An application in production is rarely one server with a public IP address. A request passes through several network components, each with its own job. Topic 4.9 asks you to explain the role of four of them: **DNS**, **firewalls**, **load balancers** and **reverse proxies**. You already know them as a network engineer; here the angle is what each one means for the application and for whoever deploys it.

```text
 Client (203.0.113.50)
   |  1. DNS: inv.example.com ?  -> A 198.51.100.10
   v
 [ Firewall ]  2. permit tcp any -> 198.51.100.10 eq 443, deny the rest
   v
 [ Load balancer VIP 198.51.100.10:443 ]   3. TLS terminated here (certificate for inv.example.com)
   |   method: least connections        health check: GET /health every 5 s, expect 200
   |   adds X-Forwarded-For: 203.0.113.50
   +--------------------+--------------------+
   v                    v                    v
 web1 10.0.20.11:8000  web2 10.0.20.12:8000  web3 10.0.20.13:8000   4. app servers (or containers)
   \____________________|____________________/
                        v
 [ Firewall ]  5. permit 10.0.20.0/24 -> db 10.0.30.5 eq 5432 only
                        v
                  PostgreSQL 10.0.30.5
```

## DNS

**DNS** turns the name users and scripts know (`inv.example.com`) into the address of the entry point, usually the load balancer's virtual IP. For the application it provides:

- **Indirection.** Clients use a stable name while addresses change behind it: you can move the service to a new data centre, a cloud region or a new load balancer by changing a record.
- **Simple distribution and failover.** Several A/AAAA records give rough round-robin; DNS-based global load balancing returns the address of the nearest or healthiest site.
- **Service discovery.** Inside container platforms, DNS names resolve to services and containers.
- **Timing.** The **TTL** decides how long resolvers cache an answer; lower it before a planned migration so clients pick up the new address quickly. A wrong or stale record is a classic "the app is down for some users only" cause.

Record types worth recognising: `A` (IPv4), `AAAA` (IPv6), `CNAME` (alias to another name), `MX` (mail), `TXT` (verification, SPF), `SRV` (service and port), `PTR` (reverse lookup).

## Firewalls

A **firewall** enforces which flows are allowed between zones: internet to DMZ, DMZ to application tier, application tier to database. For deployment this means:

- Only the ports the application actually serves are open, ideally only to the load balancer or reverse proxy, never directly to the app servers or database.
- Rules must be updated as part of the deployment: a new service on TCP 8443, a new database replica, or an API the application calls out to (egress rules). A forgotten rule is a common reason a correctly deployed app is unreachable (lesson 6.8).
- Stateful inspection lets return traffic back without separate rules; next-generation firewalls add application identification, IPS and URL filtering.
- Host firewalls and cloud **security groups** apply the same idea per server or per instance.

> **Watch out:** Publishing a container port with `docker run -p 8080:8000` binds to all host interfaces by default, and Docker's documentation notes that on Linux it manages its own iptables rules, so the port can be reachable even if a host firewall tool such as UFW was configured to block it. Bind to `127.0.0.1` when only the host should reach it.

## Load balancers

A **load balancer** presents one address (the **virtual IP**, VIP) and spreads requests across a **pool** of identical servers. It gives the application:

- **Scale-out**: add servers to handle more load without changing what clients connect to.
- **High availability**: a failed server is taken out of rotation automatically.
- **Zero-downtime deployments**: drain one server, upgrade it, put it back (rolling deployment), or switch the pool from the old version to the new (blue/green).

**Health checks** make this work. The load balancer polls each server (a TCP connect, or better an HTTP request such as `GET /health` expecting `200`) at an interval. After a number of failures it marks the server down and sends it no new requests; when checks pass again it returns the server to the pool. A good `/health` endpoint checks the application's own dependencies, not just that the process is alive. (Some load balancers, such as open-source nginx, also do *passive* checks: they mark a server failed when real requests to it fail.)

Common **load-balancing methods**:

| Method | How it chooses | Good for |
|---|---|---|
| Round robin | Each server in turn (the nginx default) | Similar servers, short similar requests |
| Weighted round robin | In turn, but in proportion to configured weights | Servers of different sizes |
| Least connections | Server with the fewest active connections | Requests of uneven length |
| Source IP hash | Hash of the client address picks the server, so a client keeps the same server | Simple **session persistence** ("sticky" sessions) |

**Layer 4** load balancers forward TCP or UDP connections by address and port. **Layer 7** load balancers understand HTTP: they can route by host name or URL path, insert headers and terminate TLS, which overlaps with what a reverse proxy does.

## Reverse proxies

A **reverse proxy** sits in front of one or more **servers** and accepts client connections on their behalf. The client thinks it is talking to the server; the proxy opens its own connection to the backend and relays the response. nginx, HAProxy, Apache httpd and Envoy are common, and many load balancers are reverse proxies with load-balancing features.

What it gives the application:

- **TLS termination.** The proxy holds the certificate and decrypts HTTPS, so backends can speak plain HTTP on a trusted internal network (or re-encrypt if policy requires). Certificates are managed in one place.
- **Hiding and protecting backends.** Clients never learn the internal addresses; only the proxy is exposed. A web application firewall (WAF) can be added here.
- **Routing.** One public name can serve `/api/` from one service and `/` from another.
- **Caching and compression** of static content, and connection reuse to backends.

Because the backend now sees the **proxy's** address as the source of every connection, the proxy passes the real client address in a header. The de facto standard is **`X-Forwarded-For`**: `X-Forwarded-For: <client>, <proxy1>, <proxy2>`, where the leftmost address is the original client and each proxy appends the address it received the request from (nginx: `proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;`). RFC 7239 standardises the same idea as the `Forwarded` header. `X-Forwarded-Proto: https` tells the backend the original request was HTTPS.

> **Watch out:** Clients can send their own `X-Forwarded-For`. MDN's guidance is to trust only the addresses added by proxies you control, and to treat none of it as trustworthy if the server can also be reached directly. Never base access control on an unverified header.

### Reverse proxy vs forward proxy

| | Forward proxy | Reverse proxy |
|---|---|---|
| Acts for | **Clients** | **Servers** |
| Configured by | The client side (browser or OS settings, PAC file, or transparently by the network) | The service owner, as the public endpoint of the site |
| Typical job | Filter and log users' outbound web access, cache, hide internal clients | TLS termination, load distribution, caching, protecting backends |
| Example | Corporate web proxy employees must use | nginx in front of an API |

> **Exam tip:** Match the clue: name to address, TTL, migration = **DNS**; which ports and zones may talk = **firewall**; spread over identical servers, health checks, VIP, sticky sessions = **load balancer**; terminate TLS, hide backends, route by path, `X-Forwarded-For` = **reverse proxy**; controls users' outbound access = **forward proxy**.

## Lab it yourself

Any computer with Docker (Docker Desktop on Windows and macOS, Docker Engine or Podman on Linux) and the `netinv` image from lesson 4.7.

1. Start two app containers on a user-defined network: `docker network create labnet`, then `docker run -d --name web1 --network labnet -e SITE=web1 netinv:1.0` and the same for `web2` with `SITE=web2`. Publish no ports.
2. Create `nginx.conf` containing a `http` block with `upstream app { server web1:8000; server web2:8000; }` and a `server { listen 80; location / { proxy_pass http://app; proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for; } }`, plus an empty `events {}` block.
3. Run the proxy as the only published container: `docker run -d --name lb --network labnet -p 8080:80 -v "$(pwd)/nginx.conf:/etc/nginx/nginx.conf:ro" nginx:stable`.
4. Request `http://localhost:8080/` several times: the `site` value alternates between `web1` and `web2` (round robin). Run `docker stop web2` and request again: nginx's passive checks send everything to `web1`.
5. Run `dig example.com` (macOS, Linux) and note the TTL, the number before `IN A` in the answer section. Plain `nslookup` does not print the TTL; on Windows use `nslookup -debug example.com` and look for `ttl =`.
6. Clean up: `docker rm -f lb web1 web2` and `docker network rm labnet`.

## Key takeaways

- DNS maps the service name to its entry point; TTLs control how fast changes take effect; it also enables simple distribution and service discovery.
- Firewalls permit only the flows the application needs between zones; update rules as part of every deployment.
- Load balancers present a VIP, spread requests with methods such as round robin, least connections or source-IP hash, and remove failed servers using health checks.
- Reverse proxies act for servers: TLS termination, hiding backends, path routing and caching; they pass the client address in `X-Forwarded-For` (leftmost = client), which is only trustworthy when added by your own proxies.
- A forward proxy acts for clients; a reverse proxy acts for servers.
