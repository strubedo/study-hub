## Three ways to run the same application

Once you know *where* an application runs (lesson 4.2), you decide *how* it is packaged on a server. The exam names three deployment types: **bare metal**, **virtual machines** and **containers**. They differ in what each application gets to itself and what it shares.

```text
 Bare metal              Virtual machines                 Containers
 +-----------+           +---------+ +---------+          +-------+ +-------+ +-------+
 |   App     |           |  App A  | |  App B  |          | App A | | App B | | App C |
 +-----------+           +---------+ +---------+          | libs  | | libs  | | libs  |
 | Libraries |           |  Libs   | |  Libs   |          +-------+ +-------+ +-------+
 +-----------+           +---------+ +---------+          |   Container engine      |
 |  Host OS  |           | Guest OS| | Guest OS|          +-------------------------+
 | (kernel)  |           | (kernel)| | (kernel)|          | Host OS (one shared kernel)
 +-----------+           +---------+ +---------+          +-------------------------+
 | Hardware  |           |     Hypervisor      |          |        Hardware         |
 +-----------+           +---------------------+          +-------------------------+
                         |      Hardware       |
                         +---------------------+
```

## Bare metal

The operating system is installed directly on the physical server, and the application runs on that OS. There is no virtualisation layer.

- **Performance:** the best and most predictable. The application gets every core, all memory and direct access to devices such as GPUs, NVMe disks and NICs that support SR-IOV or DPDK.
- **Isolation:** physical. Nothing else runs on the box unless you put it there.
- **Density:** one OS per server, so utilisation is often low.
- **Provisioning:** slow (hours to days: rack, cable, install), although tools like PXE boot and server profiles (for example Cisco Intersight with UCS) automate it.
- **Portability:** tied to the hardware; moving it means reinstalling.

Use it for large databases, high-performance or latency-sensitive workloads, licensing tied to physical cores, and as the host that runs hypervisors or container platforms.

## Virtual machines

A **hypervisor** divides one physical server into many virtual machines. Each VM has virtual CPUs, memory, disks and NICs, and runs its **own complete guest operating system with its own kernel**.

- **Type 1** hypervisors run directly on the hardware (VMware ESXi, Microsoft Hyper-V, KVM as part of Linux). **Type 2** hypervisors run as an application on a desktop OS (VMware Workstation, Oracle VirtualBox) and are used for labs.
- **Isolation:** strong. The hypervisor enforces the boundary, so a crash or kernel bug in one guest does not affect the others (only a flaw in the hypervisor itself can cross that boundary).
- **Mixed operating systems:** a Windows VM and a Linux VM can share one host, because each brings its own kernel.
- **Density:** good, but each VM carries a full OS (often gigabytes of disk and hundreds of megabytes of memory before the app does anything).
- **Start time:** a full OS boot, typically tens of seconds to minutes.
- **Portability:** a VM image can move between hosts running the same hypervisor; live migration moves a running VM.

Cisco network appliances are often delivered this way too: Catalyst 8000V, Secure Firewall Threat Defense Virtual, Catalyst Center and SD-WAN Manager all ship as VM images.

## Containers

A **container** packages an application with its libraries and dependencies, but **not** a kernel. All containers on a host **share the host's kernel**; the kernel's namespaces give each container its own view of processes, network interfaces, mounts and hostname, and control groups (cgroups) limit how much CPU and memory it can use.

- **Size and start time:** images are often tens to a few hundred megabytes and a container starts in about the time its process takes to start (often under a second), because there is no OS to boot.
- **Density:** many more containers than VMs fit on one host.
- **Portability:** the image runs the same way on a laptop, a CI runner and a production host, which removes most "works on my machine" problems. It must still match the host's **OS and CPU architecture**: a Linux image needs a Linux kernel, and an `amd64` image needs an `amd64` CPU or emulation.
- **Isolation:** weaker than a VM. Containers are separated by kernel features, so a kernel vulnerability can affect every container on the host. Run containers as non-root, keep the host patched, and use VMs where tenants do not trust each other.
- **Immutability:** you do not patch a running container; you build a new image and replace the container.

> **Watch out:** On Windows and macOS, **Docker Desktop** runs Linux containers inside a small Linux VM, because those containers need a Linux kernel. That is why Linux images "just work" on a Mac: there is a VM underneath. On Apple silicon, images built for `linux/arm64` run natively, while `linux/amd64` images run under emulation.

## Side by side

| Attribute | Bare metal | Virtual machine | Container |
|---|---|---|---|
| Kernel | One, on the hardware | One per VM (guest OS) | Shared with the host |
| Isolation | Physical | Strong (hypervisor) | Process level (namespaces, cgroups) |
| Typical size | Whole server | Gigabytes | Megabytes to hundreds of megabytes |
| Start time | Minutes (boot hardware and OS) | Tens of seconds to minutes | Usually under a second to seconds |
| Density per server | One workload stack | Tens | Tens to hundreds |
| Performance overhead | None | Small (virtualised hardware) | Near native |
| Mixed OS on one host | No | Yes | Same kernel family only |
| Portability | Low | Image moves between same-hypervisor hosts | High: same image everywhere with the same OS and CPU architecture |
| Typical use | Databases, HPC, hypervisor and container hosts | Mixed OS, strong multi-tenancy, legacy and vendor appliances | Microservices, CI jobs, edge apps, scale-out web tiers |

They are combined all the time: containers usually run **inside VMs**, which run on bare metal. A public cloud Kubernetes node is typically a VM.

> **Exam tip:** "Own kernel", "different OS", "strong isolation between tenants" means VM. "Shares the host kernel", "starts in seconds", "lightweight", "same image from laptop to production" means container. "No hypervisor overhead", "direct hardware access" means bare metal.

## Lab it yourself

On any computer:

1. Install a desktop hypervisor (VirtualBox runs on Windows, Intel macOS and Linux; on Apple silicon use UTM or Parallels) and time how long a small Linux VM takes to boot. Note its disk size.
2. Install **Docker Desktop** on Windows or macOS, or **Docker Engine** or **Podman** on Linux. Run `docker run --rm alpine:3.20 uname -r` and compare the kernel version with the one your host or Docker Desktop VM reports. Then time `docker run --rm alpine:3.20 echo hello`.
3. Run `docker images alpine` and compare the image size with the VM's disk.
4. Run `docker run --rm alpine:3.20 cat /etc/os-release` and `docker run --rm debian:12-slim cat /etc/os-release`: two different distributions, one shared kernel.

## Key takeaways

- Bare metal: OS on the hardware, best performance and isolation, lowest density and slowest provisioning.
- VMs: a hypervisor runs many guests, each with its own kernel; strong isolation and mixed operating systems, but each carries a full OS.
- Containers: application plus dependencies sharing the host kernel; small, fast to start, dense and portable, with weaker isolation than VMs.
- A container image must match the host's OS kernel family and CPU architecture; Docker Desktop provides a Linux VM on Windows and macOS.
- Real deployments layer them: containers in VMs on bare metal.
