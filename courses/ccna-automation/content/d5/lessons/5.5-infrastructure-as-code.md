## What infrastructure as code means

**Infrastructure as code (IaC)** manages servers, networks and cloud resources through **machine-readable definition files** kept in version control, applied by tools, instead of through manual console or CLI sessions. Lesson 4.12 placed it among the DevOps practices; this lesson covers the principles you must be able to describe.

## Principle 1: declarative versus imperative

| | Imperative ("how") | Declarative ("what") |
|---|---|---|
| You write | The steps, in order | The desired end state |
| The tool | Runs the steps as written | Compares desired with actual and works out the steps |
| Running twice | Repeats the steps (may fail or duplicate) | Changes nothing if the state already matches |
| Examples | A Bash script of `useradd` and `apt-get` lines; a list of CLI commands sent over SSH | Terraform HCL; an Ansible task with `state: present`; NSO service instances; a RESTCONF PUT of the full desired subtree |

Imperative, as a list of steps:

```text
conf t
 vlan 30
  name cameras
 end
```

Declarative, as a desired state that Terraform's IOS XE provider reconciles over NETCONF:

```hcl
resource "iosxe_vlan" "cameras" {
  vlan_id = 30
  name    = "cameras"
}
```

The CLI lines say *do this*; the resource says *this must exist*. If VLAN 30 already exists with that name, Terraform plans no change; if someone renamed it, Terraform plans an update back to `cameras`.

> **Watch out:** Ansible is often called declarative, but a playbook is an ordered list of tasks. Each module is declarative about its own resource (`state: present`, `state: started`), while the play is procedural. Terraform and NSO are declarative about the whole configuration.

## Principle 2: idempotency

An operation is **idempotent** if applying it once or many times leaves the system in the same state. IaC tools check before they act:

```python
def ensure_vlan(vlans, vlan_id, name):
    """Make sure vlan_id exists with this name; report whether anything changed."""
    if vlans.get(vlan_id) == name:
        return vlans, False
    return {**vlans, vlan_id: name}, True

state = {10: "users", 20: "voice"}
state, changed = ensure_vlan(state, 30, "cameras")
print(changed, state)
state, changed = ensure_vlan(state, 30, "cameras")
print(changed, state)
```

```text
True {10: 'users', 20: 'voice', 30: 'cameras'}
False {10: 'users', 20: 'voice', 30: 'cameras'}
```

The second run reports `False`: nothing to do. This is the `changed` versus `ok` you see in Ansible output (lesson 5.8) and the "No changes" you see from `terraform plan`. Idempotency is what makes it safe to re-run automation after a partial failure, or on a schedule to enforce state.

## Principle 3: version control is the source of truth

- The **repository**, not the running device, holds the intended configuration. A change is a commit, reviewed in a merge request (lesson 5.13) and applied by the pipeline (lesson 5.4).
- History gives an **audit trail** (who changed what, when, and why) and **rollback** (redeploy the previous commit).
- Branches let you prepare and test a change without touching production.
- **Secrets stay out of the repository**: reference them from a vault or environment variables (Ansible Vault, CI variables, a secrets manager).

## Principle 4: immutability

**Immutable infrastructure** replaces rather than modifies: to change a server, build a new image and swap it in; never patch the running one by hand. Every instance then matches a known, tested build, and rolling back means redeploying the previous image. It suits virtual machines, containers and cloud resources. Network devices are usually changed in place (you do not replace a core switch to change a VLAN), so for the network the principle shows up as **no manual changes**: every change goes through code, the pipeline and a full rendered configuration, so the device always matches a version in Git.

## Principle 5: detect and correct drift

**Configuration drift** is any difference between the intended state in code and the actual state on the device, usually caused by out-of-band changes ("a quick fix at 2 a.m.") or failed partial deployments. IaC tools detect it:

| Tool | How it shows drift |
|---|---|
| Terraform | `terraform plan` refreshes state from the real resources and proposes changes back to the code; `terraform plan -refresh-only` shows what changed outside Terraform |
| Ansible | `ansible-playbook --check --diff` reports what *would* change |
| NSO | `devices check-sync` and `compare-config` compare its database (CDB) with each device |
| pyATS | `pyats learn` then `pyats diff` against a saved baseline |

Corrective action is either to **re-apply the code** (the code wins) or to **update the code** to accept the change, and commit it. Either way, code and device agree again.

## Benefits

Consistency across sites, speed and scale, fewer manual errors, repeatable test environments (the same code builds a lab and production), reviewable changes, easy rollback and documentation that cannot go stale because it *is* the configuration.

## Lab it yourself

1. Run the `ensure_vlan` example above in Python on any computer and add a third call that changes the name to `cctv`; confirm it reports `True` once and `False` after.
2. In a Git repository, create `vars/sw01.yml` with three VLANs, commit it, change one name, and run `git diff` (lesson 5.12) to see the reviewable change.
3. Install Terraform (it runs on Windows, macOS and Linux), create a folder with an empty `main.tf`, and run `terraform init` and `terraform plan` to see the "No changes" message of an already-converged configuration.

## Key takeaways

- IaC defines infrastructure in version-controlled files applied by tools, not by hand.
- Declarative code states the end state; imperative code lists steps. Terraform and NSO are declarative; Ansible modules are declarative per task inside an ordered play.
- Idempotent: applying the same code again changes nothing (`ok`, "No changes").
- Git is the source of truth: review, audit trail, rollback; secrets stay out.
- Immutability replaces instead of patching; on the network it means no manual changes.
- Drift is code versus reality; detect it (plan, check mode, check-sync, pyATS diff) and reconcile it.
