## What code review is

**Code review** is the practice of having someone other than the author examine a change before it is merged. In infrastructure automation the "code" includes playbooks, Terraform files, Jinja2 templates, YANG payloads, Python scripts and the YAML variables that describe the network, so a review is often the last human check before a change reaches devices.

The usual mechanism is a **pull request** (GitHub, Bitbucket) or **merge request** (GitLab): the author pushes a branch, opens a request to merge it into `main`, and the platform shows the unified diff (lesson 5.12), runs the pipeline (lesson 5.4) and collects comments and approvals. **Branch protection** rules can require passing checks and a set number of approvals before the merge button works.

```text
 branch: add-camera-vlan
   commit -> push -> open merge request
                          |
          automated checks run (lint, render, lab tests)
                          |
          reviewers read the diff, comment, request changes
                          |
          author pushes fixes -> checks re-run -> approval
                          |
                  merge to main -> deploy pipeline
```

## Automated checks first, people second

Let machines do what machines do well, so reviewers spend their attention on what only people can judge:

| Caught by automation | Caught by a reviewer |
|---|---|
| YAML and Python syntax, formatting, style (`yamllint`, `ansible-lint`, linters, `terraform fmt`) | Whether the change does what the ticket asked for |
| Failing unit tests and lab tests | Design: is this the right approach, in the right place? |
| Known-bad patterns, secret scanners | Risk and timing: blast radius, rollback plan, change window |
| Schema validation (YANG, JSON schema) | Readability, naming, comments that explain *why* |
| Rendered-config diffs | Missing cases: other sites, IPv6, the second data centre |

A merge request with a red pipeline is not ready for review.

## What reviewers look for

- **Correctness**: the logic, the values (VLAN ids, prefixes, ACL order), edge cases, error handling.
- **Intent**: the change matches its description and its ticket, and nothing unrelated sneaked in.
- **Security**: no credentials or API keys in the diff (they belong in a vault or CI variables), no `verify=False` left in, least privilege, input validated.
- **Idempotency and safety**: tasks that report `changed` every run, `state: restarted` instead of a handler, commands without checks, missing `--check` path.
- **Maintainability**: clear names, no duplicated blocks that should be a template or a function, tests for new behaviour.
- **Operational impact**: what happens to traffic during the change, how to verify it, how to roll it back.

Comments should be specific and about the code, not the author: "this `ios_config` block sends `ntp server` without `save_when`, so a reload loses it" helps; "this is wrong" does not.

## Keep changes small

Small changes are reviewed faster and better. A 40-line diff gets read line by line; a 4,000-line diff gets skimmed and approved. Small changes also isolate problems: if a merge breaks something, the cause is obvious and the revert is clean. Split work into steps that each make sense on their own (add the VLAN variables; then the template; then the rollout to the first site).

## Benefits

| Benefit | Why |
|---|---|
| **Defects found early** | A typo in a prefix list costs a comment in review, an outage in production |
| **Knowledge sharing** | More than one person understands each part of the automation; reviewers learn the code base and authors learn from feedback |
| **Consistency** | Shared conventions for naming, structure and style are enforced across the team |
| **Security** | A second pair of eyes catches secrets, unsafe defaults and over-broad permissions |
| **Accountability and audit** | The merge request records who changed what, who approved it, and why; useful for change management and compliance |
| **Better design** | Explaining a change to a reviewer often improves it before anyone comments |

> **Exam tip:** Code review questions reward the answers *find defects early*, *share knowledge*, *improve quality and consistency*, *enforce standards*, *keep changes small* and *automate the mechanical checks*. Distractors such as "replaces testing", "lets you skip the pipeline" or "makes the author personally liable" are wrong: review complements testing and automation, and it is about the code, not blame.

## Lab it yourself

1. Create a free GitHub or GitLab repository. On a branch, change a YAML variable file and open a pull or merge request against `main`.
2. Turn on branch protection for `main` (required approval, required status check) and see that you cannot merge your own request until the rules are met.
3. Add a review comment on a specific line of the diff, push a fix, and see the comment marked as outdated.
4. Review a classmate's or your own older script with the checklist above and write three specific comments.

## Key takeaways

- Code review means someone other than the author examines a change before it merges, usually in a pull or merge request.
- Automated checks run first; reviewers focus on intent, design, risk, security and readability.
- Small, focused changes are reviewed better and are easier to revert.
- Benefits: early defect detection, knowledge sharing, consistency, security, an audit trail and better design.
- Branch protection enforces passing checks and approvals before merging.
- Review is about the code, not the person, and complements testing rather than replacing it.
