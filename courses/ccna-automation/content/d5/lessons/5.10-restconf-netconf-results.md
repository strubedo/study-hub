## Reading replies, not building requests

Lesson 3.8 showed how to send NETCONF RPCs and RESTCONF requests. Topic 5.10 gives you the **reply** and asks what it means: did it work, what value does a leaf have, which interface is down, why did the edit fail. The examples use the IETF interface model, `ietf-interfaces` (RFC 8343), with `ietf-ip` (RFC 8344) augmenting it, so every name here can be checked against the RFCs.

## The map: reply to model

Every reply is an instance of a YANG tree. Keep the tree beside you (lesson 5.11):

```text
module: ietf-interfaces
  +--rw interfaces
     +--rw interface* [name]
        +--rw name           string
        +--rw description?   string
        +--rw type           identityref
        +--rw enabled?       boolean
        +--ro oper-status    enumeration
        +--ro phys-address?  yang:phys-address
        +--ro speed?         yang:gauge64
        +--ro statistics
        |  +--ro in-octets?   yang:counter64
        |  +--ro in-errors?   yang:counter32
        |  ...
        +--rw ip:ipv4!
           +--rw ip:address* [ip]
              +--rw ip:ip               inet:ipv4-address-no-zone
              +--rw ip:prefix-length?   uint8
```

(Abridged: `ietf-ip` really places `prefix-length` inside a `(subnet)` choice, shown in lesson 3.8; choice and case nodes never appear in data, so the reply looks the same.) Containers become JSON objects or XML elements, lists become JSON arrays or repeated XML elements, leaves become values.

## RESTCONF results

### A successful GET

```http
GET /restconf/data/ietf-interfaces:interfaces/interface=GigabitEthernet2 HTTP/1.1
Host: rtr01.example.com
Accept: application/yang-data+json
```

```http
HTTP/1.1 200 OK
Content-Type: application/yang-data+json

{
  "ietf-interfaces:interface": [
    {
      "name": "GigabitEthernet2",
      "description": "to sw01",
      "type": "iana-if-type:ethernetCsmacd",
      "enabled": true,
      "oper-status": "down",
      "phys-address": "00:00:5e:00:53:02",
      "speed": "1000000000",
      "statistics": {
        "in-octets": "48213097",
        "in-errors": 12
      },
      "ietf-ip:ipv4": {
        "address": [
          {
            "ip": "10.10.12.1",
            "prefix-length": 30
          }
        ]
      }
    }
  ]
}
```

How to read it, rule by rule (RFC 7951, the JSON encoding of YANG data):

| What you see | Rule | Here |
|---|---|---|
| `"ietf-interfaces:interface"` | A **top-level** member is qualified with its **module name** (not the YANG prefix) | The target was one entry of the `interface` list in module `ietf-interfaces` |
| `[ { ... } ]` | A **list** is a JSON array, even with one entry | One interface |
| `"name"`, `"enabled"` without a prefix | Children in the **same module** as their parent use the simple name | |
| `"ietf-ip:ipv4"` | A member from a **different module** (an augment) is qualified again | `ipv4` comes from `ietf-ip` |
| `"type": "iana-if-type:ethernetCsmacd"` | An **identityref** value carries its module name | Ethernet |
| `"speed": "1000000000"`, `"in-octets": "48213097"` | **64-bit** integer types (`int64`, `uint64`, `counter64`, `gauge64`) and `decimal64` are JSON **strings** | 1 Gbit/s; about 48 MB received |
| `"in-errors": 12`, `"prefix-length": 30` | 32-bit and smaller integers are JSON numbers | 12 input errors |
| `"enabled": true` | Booleans are JSON `true`/`false` | Administratively up |
| `"oper-status": "down"` | Enumerations are strings | Operationally down |

**Interpretation:** GigabitEthernet2 is configured and administratively enabled, but operationally **down**, with 12 input errors since the counters last reset. That points at the physical layer or the far end (`sw01`), not at a shutdown. Reading `oper-status` and `enabled` together is the classic interpretation question: `enabled: false` means someone shut it down; `enabled: true` with `oper-status: down` means it should be up but is not.

In Python, the path to the address is `reply["ietf-interfaces:interface"][0]["ietf-ip:ipv4"]["address"][0]["ip"]`.

> **Exam tip:** Whatever node the URL ends at becomes the single top-level member of the reply, qualified with its module name. `GET .../ietf-interfaces:interfaces` returns `{"ietf-interfaces:interfaces": {"interface": [...]}}`; `GET .../interfaces/interface=Gi2` returns `{"ietf-interfaces:interface": [{...}]}`.

### Status codes and empty bodies

| Reply | Meaning |
|---|---|
| `200 OK` with a body | GET succeeded (also PATCH when the server returns the result) |
| `201 Created` with a `Location` header | POST or PUT created the resource |
| `204 No Content` | PUT, PATCH or DELETE succeeded; no body to parse |
| `400 Bad Request` | Malformed body, unknown element, or a value that fails the model's type or range |
| `401` / `403` | Not authenticated / not authorised (`access-denied`) |
| `404 Not Found` | The resource in the URL does not exist (for example `interface=Gi9`) |
| `409 Conflict` | `data-exists` (POST of something that exists), `lock-denied`, `in-use` |
| `415 Unsupported Media Type` | Wrong `Content-Type` (for example `application/json` where the server wants `application/yang-data+json`) |

### Error replies

```http
HTTP/1.1 409 Conflict
Content-Type: application/yang-data+json

{
  "ietf-restconf:errors": {
    "error": [
      {
        "error-type": "application",
        "error-tag": "data-exists",
        "error-path": "/ietf-interfaces:interfaces/interface[name='Loopback10']",
        "error-message": "object already exists"
      }
    ]
  }
}
```

The body is the RESTCONF `errors` container: a list of `error` entries carrying the same fields as a NETCONF `<rpc-error>`. This one says a POST tried to create `Loopback10`, which already exists; a PATCH (merge) or PUT (replace) would have updated it instead.

## NETCONF results

Every NETCONF reply is an `<rpc-reply>` in the base namespace `urn:ietf:params:xml:ns:netconf:base:1.0`, carrying the same **`message-id`** as the `<rpc>` it answers. Inside is exactly one of three things:

| Inside `<rpc-reply>` | Answers | Meaning |
|---|---|---|
| `<data>...</data>` | `<get>`, `<get-config>` | The requested configuration (and state, for `<get>`), filtered |
| `<ok/>` | `<edit-config>`, `<lock>`, `<unlock>`, `<commit>`, `<copy-config>`, `<close-session>` | Success, nothing to return |
| One or more `<rpc-error>` | Any operation | Failure (or a warning); read the fields |

### Data

A `<get>` with a subtree filter:

```xml
<rpc message-id="201" xmlns="urn:ietf:params:xml:ns:netconf:base:1.0">
  <get>
    <filter type="subtree">
      <interfaces xmlns="urn:ietf:params:xml:ns:yang:ietf-interfaces">
        <interface>
          <name/>
          <oper-status/>
        </interface>
      </interfaces>
    </filter>
  </get>
</rpc>
```

The filter's `<interfaces>` and `<interface>` are **containment nodes**, the `xmlns` is a **namespace selection**, and the empty `<name/>` and `<oper-status/>` are **selection nodes**: return only those leaves. A leaf with a value, such as `<name>GigabitEthernet2</name>`, would be a **content match node** selecting one entry.

```xml
<rpc-reply message-id="201" xmlns="urn:ietf:params:xml:ns:netconf:base:1.0">
  <data>
    <interfaces xmlns="urn:ietf:params:xml:ns:yang:ietf-interfaces">
      <interface>
        <name>GigabitEthernet1</name>
        <oper-status>up</oper-status>
      </interface>
      <interface>
        <name>GigabitEthernet2</name>
        <oper-status>down</oper-status>
      </interface>
      <interface>
        <name>Loopback0</name>
        <oper-status>up</oper-status>
      </interface>
    </interfaces>
  </data>
</rpc-reply>
```

Read it like the tree: one `interfaces` container, three `interface` list entries (keyed by `name`), and the one leaf the filter asked for. The XML namespace `urn:ietf:params:xml:ns:yang:ietf-interfaces` is the module's `namespace` statement, so it identifies the model as surely as the module name does in JSON. `oper-status` is state data (`ro`), so this needed `<get>`; `<get-config>` returns configuration only and would not include it.

### ok

```xml
<rpc-reply message-id="202" xmlns="urn:ietf:params:xml:ns:netconf:base:1.0">
  <ok/>
</rpc-reply>
```

The `<edit-config>` with `message-id="202"` succeeded. If its target was the **candidate** datastore, nothing is live yet: a `<commit>` must follow. If the target was **running**, the change is active (and on IOS XE still needs saving to survive a reload).

### rpc-error

```xml
<rpc-reply message-id="203" xmlns="urn:ietf:params:xml:ns:netconf:base:1.0">
  <rpc-error>
    <error-type>application</error-type>
    <error-tag>invalid-value</error-tag>
    <error-severity>error</error-severity>
    <error-path xmlns:ip="urn:ietf:params:xml:ns:yang:ietf-ip"
                xmlns:if="urn:ietf:params:xml:ns:yang:ietf-interfaces">
      /if:interfaces/if:interface[if:name="GigabitEthernet2"]/ip:ipv4/ip:address[ip:ip="10.10.12.1"]/ip:prefix-length
    </error-path>
    <error-message xml:lang="en">"33" is not a valid value.</error-message>
  </rpc-error>
</rpc-reply>
```

| Field (RFC 6241 section 4.3) | Values | Here |
|---|---|---|
| `error-type` | The layer: `transport`, `rpc`, `protocol` (the operation), `application` (the content) | `application`: the data was wrong, not the RPC |
| `error-tag` | The condition, from a fixed list: `invalid-value`, `data-exists`, `data-missing`, `missing-element`, `unknown-element`, `access-denied`, `lock-denied`, `in-use`, `operation-failed`, `malformed-message`, ... | `invalid-value` |
| `error-severity` | `error` or `warning` | `error`: the operation failed |
| `error-app-tag` | Optional model- or vendor-specific tag | absent |
| `error-path` | XPath to the offending node | The `prefix-length` of 10.10.12.1 on Gi2 |
| `error-message` | Human-readable text | 33 is outside the `uint8` range the model allows for IPv4 (`0..32`) |
| `error-info` | Extra detail, such as `<bad-element>` or the `<session-id>` holding a lock | absent |

Other combinations worth knowing: `data-missing` (application) when `operation="delete"` targets something that does not exist; `data-exists` (application) when `operation="create"` targets something that does; `lock-denied` (protocol) with the holder's `<session-id>` in `error-info`; `unknown-element` when the payload names a node the model does not have (often a namespace typo).

## Lab it yourself

1. On an IOS XE sandbox, `GET /restconf/data/ietf-interfaces:interfaces` with `Accept: application/yang-data+json`. Which counters are strings and which are numbers? Compare with the YANG types in the RFC 8343 tree. If the reply holds only configuration (no `oper-status` or `statistics`), the device is serving state in the older, deprecated `ietf-interfaces:interfaces-state` tree, which RFC 8343 (section 1.1) still allows for servers that do not implement NMDA: GET that URL instead.
2. Fetch a non-existent interface (`interface=Loopback999`) and read the status and the `ietf-restconf:errors` body.
3. With `ncclient` (lesson 3.8), send the `<get>` filter above and print `reply.data_xml`. Then send an `<edit-config>` with `prefix-length` 33 and print the error's `tag`, `type` and `message` (ncclient raises `RPCError` with those attributes).

## Key takeaways

- A reply is an instance of the YANG tree: containers are objects or elements, lists are arrays or repeated elements, leaves are values.
- RESTCONF JSON: the top-level member is `module-name:node`; augmented nodes are qualified again (`ietf-ip:ipv4`); lists are arrays even with one entry.
- 64-bit integers and `decimal64` are JSON strings; identityrefs carry a module name (`iana-if-type:ethernetCsmacd`).
- RESTCONF status: `200` with data, `201` created, `204` no body, `404` missing resource, `409` conflict; errors come in `ietf-restconf:errors`.
- NETCONF `<rpc-reply>` matches the request's `message-id` and holds `<data>`, `<ok/>` or `<rpc-error>`.
- `<rpc-error>`: `error-type` (layer), `error-tag` (condition), `error-severity`, optional `error-path`, `error-message`, `error-info`.
- `enabled` is configuration; `oper-status` is state: read both before concluding why an interface is down.
