## Three tools, three shapes

| | Ansible | Terraform | Cisco NSO |
|---|---|---|---|
| Made by | Red Hat (open source `ansible-core` plus collections) | HashiCorp | Cisco (Crosswork Network Services Orchestrator) |
| Style | Ordered **tasks** in YAML playbooks; each module is declarative about its own resource | **Declarative** HCL describing resources | **Model-driven** service and device data in YANG, applied as **transactions** |
| Agent | **Agentless**: SSH for servers, network connection plugins or HTTPS APIs for devices | No agent: **providers** call the platform's API | No agent: **NEDs** talk to each device's CLI, NETCONF, SNMP or API |
| Remembers state? | No: it inspects the target on every run | Yes: the **state file** maps resources to real objects | Yes: the **CDB** holds every device configuration and every service instance |
| Change preview | `--check --diff` | `terraform plan` | `commit dry-run` |
| Undo | Write and run the reverse change | Apply the previous version of the code; `terraform destroy` removes everything it manages | **Rollback** files, or delete the service instance and NSO removes exactly what it created |
| Best at | Configuration management of servers and devices, ad hoc tasks, multi-step workflows | Provisioning and lifecycle of API-driven resources (cloud, controllers, fabrics) | Multivendor service orchestration with network-wide transactions |

## Ansible

**Architecture.** Ansible runs on a **control node** (Linux, macOS or WSL; not natively on Windows). It reads an **inventory** of managed hosts and groups, then runs **playbooks**: lists of **plays**, each mapping a group of hosts to a list of **tasks**, each task calling a **module**. Ansible is **agentless**: nothing is installed on the managed nodes. For Linux servers it copies a small Python module over SSH and runs it there. Network devices cannot run Python, so **network modules execute on the control node** and talk to the device through a **connection plugin**:

| `ansible_connection` | Protocol | Typical modules |
|---|---|---|
| `ansible.netcommon.network_cli` | CLI over SSH | `cisco.ios.ios_config`, `cisco.ios.ios_command`, resource modules such as `cisco.ios.ios_vlans` |
| `ansible.netcommon.netconf` | NETCONF (XML over SSH) | `ansible.netcommon.netconf_config`, `netconf_get` |
| `ansible.netcommon.httpapi` | HTTP/HTTPS API | NX-API modules, RESTCONF modules |

```yaml
# inventory.yml
all:
  children:
    branch_switches:
      hosts:
        sw01:
          ansible_host: 192.0.2.21
        sw02:
          ansible_host: 192.0.2.22
      vars:
        ansible_connection: ansible.netcommon.network_cli
        ansible_network_os: cisco.ios.ios
        ansible_user: alice
        ansible_password: "{{ vault_switch_password }}"
```

```yaml
# vlans.yml
- name: Camera VLAN on branch switches
  hosts: branch_switches
  gather_facts: false
  tasks:
    - name: Ensure VLAN 30 exists
      cisco.ios.ios_vlans:
        config:
          - vlan_id: 30
            name: cameras
        state: merged
```

Run it with `ansible-playbook -i inventory.yml vlans.yml`. **Resource modules** such as `ios_vlans` take structured data and a `state` (`merged`, the default, `replaced`, `overridden`, `deleted` and, for `ios_vlans`, `purged`, plus `gathered`, `rendered` and `parsed` that change nothing on the device), so they are idempotent: the second run reports `ok`, not `changed`. Platform integrations beyond IOS exist as collections for NX-OS, IOS XR, Meraki, ACI, Catalyst Center and others. Lesson 5.8 reads full playbooks.

## Terraform

**Architecture.** You write `.tf` files in **HCL** declaring **resources**. A **provider** plugin, downloaded from the Terraform Registry by `terraform init`, translates resources into API calls. Terraform records what it created in **state** (`terraform.tfstate` locally, or a remote backend with locking for teams), because it needs a one-to-one map between each resource block and the real object, plus metadata such as dependencies.

The workflow:

1. `terraform init`: download providers, set up the backend.
2. `terraform plan`: refresh state from the real objects, compare with the configuration, propose create, update or destroy actions. Nothing changes. `-out=tfplan` saves the plan.
3. Review the plan (in the merge request).
4. `terraform apply tfplan`: perform exactly the saved plan. Without a saved plan, `apply` makes a new plan and asks for approval; `-auto-approve` skips the prompt.

Cisco publishes providers in the `CiscoDevNet` namespace of the Registry: **`aci`** (APIC objects such as `aci_tenant`), **`meraki`** (Dashboard API, for example `meraki_appliance_vlan`), **`catalystcenter`** (Catalyst Center) and **`iosxe`** (IOS XE devices, over NETCONF in current releases), among others such as NX-OS and SD-WAN.

```hcl
terraform {
  required_providers {
    aci = {
      source = "CiscoDevNet/aci"
    }
  }
}

provider "aci" {
  url = "https://apic.example.com"
  # username and password come from the ACI_USERNAME and ACI_PASSWORD
  # environment variables, not from this file
}

resource "aci_tenant" "web" {
  name        = "web-prod"
  description = "Managed by Terraform"
}
```

A plan for it reads (abridged; `+` means create, `~` update in place, `-` destroy, `-/+` replace):

```text
Terraform will perform the following actions:

  # aci_tenant.web will be created
  + resource "aci_tenant" "web" {
      + description = "Managed by Terraform"
      + name        = "web-prod"
      ...
    }

Plan: 1 to add, 0 to change, 0 to destroy.
```

> **Watch out:** State can hold sensitive values in plain text and is the only record of what Terraform owns. Store it in a remote backend with encryption, access control and locking, never in Git. If someone deletes the tenant in the APIC GUI, the next `plan` shows it will be created again: that is drift detection.

## Cisco NSO

**Architecture.** NSO keeps a **configuration database (CDB)** containing the full configuration of every managed device, modelled in YANG, plus every **service instance**. **NEDs** (Network Element Drivers: CLI, NETCONF, SNMP and generic) translate between the CDB model and each device, so NSO works with Cisco and non-Cisco equipment alike. Northbound, NSO offers a CLI, Web UI, RESTCONF, NETCONF and JSON-RPC.

What sets it apart:

- **Service models**: a YANG service model (for example an L3VPN with a customer, sites and a VLAN) plus a template or Python/Java code define the **service mapping** from inputs to device configuration. NSO's **FASTMAP** algorithm derives the minimal device changes for any create, modify or delete of a service instance from that one create definition.
- **Network-wide transactions**: a commit touching ten devices succeeds on all of them or is rolled back on all of them, even on devices that have no native rollback, such as IOS CLI. Devices are configured in parallel.
- **Rollback files**: every commit writes one, and `rollback-files apply-rollback-file` restores it.
- **Device sync**: `devices sync-from` reads device configurations into the CDB; `check-sync` and `compare-config` find out-of-band changes; `sync-to` pushes the CDB copy back.

```text
admin@ncs# devices sync-from
admin@ncs# config
admin@ncs(config)# devices device rtr01 config ios:interface GigabitEthernet 2 description to-sw01
admin@ncs(config-if)# commit dry-run outformat native
native {
    device {
        name rtr01
        data interface GigabitEthernet2
              description to-sw01
             exit
    }
}
admin@ncs(config-if)# commit
Commit complete.
```

## Choosing

| Scenario | Tool |
|---|---|
| Install packages, push NTP and syslog settings and restart a service on 200 Linux servers and IOS switches, with no software on the targets | Ansible |
| Create ACI tenants, VRFs and EPGs from code, preview every change, and track what the code owns | Terraform |
| Provision an L3VPN across Cisco and Juniper routers as one service, all-or-nothing, removable later as a unit | NSO |
| Run a one-off command across all switches and collect the output | Ansible (ad hoc or a short playbook) |
| Detect that someone changed a device outside the orchestrator and resolve it | NSO `check-sync` (or Terraform plan for resources it manages) |

> **Exam tip:** Ansible: agentless, YAML playbooks, inventory, modules, SSH, no state file. Terraform: providers, HCL, declarative, **state**, plan then apply. NSO: YANG service models, NEDs, CDB, transactions across devices, rollback, `sync-from`.

## Lab it yourself

1. On Linux, macOS or WSL 2, `pip install ansible-core` and run `ansible-galaxy collection install cisco.ios`. Point the inventory above at an IOS XE sandbox and run the playbook twice: `changed` the first time, `ok` the second.
2. Install Terraform on any OS, write the ACI example against the ACI sandbox (credentials in environment variables), run `terraform plan`, `terraform apply`, then `plan` again to see "No changes". Finish with `terraform destroy`.
3. If the DevNet catalog lists an NSO sandbox, run `devices sync-from`, make a change, `commit dry-run outformat native`, commit, and roll it back.

## Key takeaways

- Ansible: agentless, inventory plus YAML playbooks of tasks and modules; network modules run on the control node through `network_cli`, `netconf` or `httpapi`; no state file.
- Terraform: declarative HCL, providers from the Registry (CiscoDevNet `aci`, `meraki`, `catalystcenter`, `iosxe`), state maps code to real objects; `init`, `plan`, `apply`.
- NSO: YANG service models, NEDs, CDB, FASTMAP, network-wide all-or-nothing transactions, rollback files, `sync-from` and `check-sync`.
- Pick Ansible for configuration tasks and workflows, Terraform for API-driven resource lifecycle, NSO for multivendor service orchestration.
- Preview every change: `--check --diff`, `terraform plan`, `commit dry-run`.
