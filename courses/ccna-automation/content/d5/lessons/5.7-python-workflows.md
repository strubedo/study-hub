## The skill being tested

Topic 5.7 hands you a Python script that calls a Cisco API and asks what it **does**: which workflow it automates, which device it changes, what it prints, what happens on an error. You do not have to write it. Lessons 3.2 and 3.9 covered the APIs; this lesson gives you a method for reading any such script and applies it to one script per named platform: ACI, Meraki, Catalyst Center and RESTCONF.

## A method: authenticate, request, parse, act

Almost every API script has four parts. Find each one and the workflow falls out.

| Step | Look for | It tells you |
|---|---|---|
| **1. Authenticate** | The login call or header: `aaaLogin` and `APIC-cookie` (ACI), `Authorization: Bearer` with an API key (Meraki), `POST .../auth/token` then `X-Auth-Token` (Catalyst Center), `auth=(user, password)` Basic auth (RESTCONF) | **Which platform** |
| **2. Request** | Method and URL path of each call: `GET` reads, `POST` creates or runs, `PUT` replaces, `PATCH` merges, `DELETE` removes | **What is read or changed, and where** |
| **3. Parse** | How the reply is unpacked: `["imdata"]`, `["response"]`, a top-level list, `["ietf-interfaces:interface"]`; any `if` filters | **Which objects the script cares about** |
| **4. Act** | What happens with the result: `print`, write a file, a second write call, `raise_for_status()`, `sys.exit(1)` | **The outcome** |

Then answer the exam question in one sentence: *"It logs in to X, reads Y, keeps those that Z, and then does W."* Check every option against a specific line: a distractor that says "creates" when every call is a `GET`, or "all devices" when an `if` filters them, is ruled out by that line.

> **Exam tip:** The URL path is the strongest clue. `/api/class/` or `/api/mo/` is ACI. `/api/v1/organizations` or `/networks/` is Meraki. `/dna/intent/api/v1/` is Catalyst Center. `/restconf/data/<module>:<node>` is RESTCONF on a device.

## ACI: locate an endpoint in the fabric

```python
import os
import sys
import requests

APIC = "https://apic.example.com"
TARGET_IP = sys.argv[1]                              # for example 10.20.1.25

session = requests.Session()
session.verify = "apic-ca.pem"
login = {"aaaUser": {"attributes": {"name": os.environ["APIC_USER"],
                                    "pwd": os.environ["APIC_PASSWORD"]}}}
session.post(f"{APIC}/api/aaaLogin.json", json=login, timeout=30).raise_for_status()

resp = session.get(f"{APIC}/api/node/class/fvCEp.json",
                   params={"query-target-filter": f'eq(fvCEp.ip,"{TARGET_IP}")'},
                   timeout=30)
resp.raise_for_status()

matches = resp.json()["imdata"]
if not matches:
    print(f"{TARGET_IP} not learned in the fabric")
    sys.exit(1)
for item in matches:
    ep = item["fvCEp"]["attributes"]
    print(ep["mac"], ep["encap"], ep["dn"])
```

| Step | Lines | Meaning |
|---|---|---|
| Authenticate | `POST /api/aaaLogin.json` with `aaaUser` | APIC login; the `requests.Session` keeps the `APIC-cookie` for later calls |
| Request | `GET /api/node/class/fvCEp.json` with `query-target-filter` | A **class query** for client endpoints, filtered to one IP address |
| Parse | `["imdata"]`, then `item["fvCEp"]["attributes"]` | The standard APIC reply envelope |
| Act | Print MAC, VLAN encapsulation and DN, or exit 1 | The DN (`uni/tn-.../ap-.../epg-.../cep-...`) shows the tenant, application profile and EPG |

**Workflow:** find where a host with a given IP address is attached in the ACI fabric. It changes nothing: every call after the login is a `GET`.

## Meraki: report offline devices

```python
import csv
import os
import requests

BASE = "https://api.meraki.com/api/v1"
HEADERS = {"Authorization": f"Bearer {os.environ['MERAKI_DASHBOARD_API_KEY']}",
           "Accept": "application/json"}

orgs = requests.get(f"{BASE}/organizations", headers=HEADERS, timeout=30)
orgs.raise_for_status()

rows = []
for org in orgs.json():
    resp = requests.get(f"{BASE}/organizations/{org['id']}/devices/availabilities",
                        headers=HEADERS,
                        params={"statuses[]": ["offline"], "perPage": 1000},
                        timeout=30)
    resp.raise_for_status()
    for dev in resp.json():
        rows.append([org["name"], dev["name"], dev["serial"], dev["productType"]])

with open("offline.csv", "w", newline="") as f:
    csv.writer(f).writerows([["org", "name", "serial", "type"], *rows])
print(f"{len(rows)} offline devices written to offline.csv")
```

- **Authenticate:** `Authorization: Bearer` with the Dashboard API key from `MERAKI_DASHBOARD_API_KEY`.
- **Request:** `GET /organizations` (every organisation the key can see), then for each one `GET /organizations/{id}/devices/availabilities` filtered with `statuses[]=offline`.
- **Parse:** the replies are top-level JSON lists (no envelope).
- **Act:** writes a CSV and prints a count.

**Workflow:** an offline-device report across all organisations. Note what it does *not* do: it does not follow the `Link` header, so an organisation with more than 1,000 offline devices would be truncated. (The Meraki OpenAPI spec now marks the older `/devices/statuses` operation as deprecated in favour of `/devices/availabilities`.)

## Catalyst Center: software compliance check

```python
import os
import requests
from requests.auth import HTTPBasicAuth

CC = "https://catalyst.example.com"
GOLDEN = "17.12.4"

auth = requests.post(f"{CC}/dna/system/api/v1/auth/token",
                     auth=HTTPBasicAuth(os.environ["CC_USER"], os.environ["CC_PASSWORD"]),
                     verify="cc-ca.pem", timeout=30)
auth.raise_for_status()
headers = {"X-Auth-Token": auth.json()["Token"], "Accept": "application/json"}

resp = requests.get(f"{CC}/dna/intent/api/v1/network-device",
                    headers=headers, params={"family": "Switches and Hubs"},
                    verify="cc-ca.pem", timeout=30)
resp.raise_for_status()

for dev in resp.json()["response"]:
    if dev["softwareVersion"] != GOLDEN:
        print(f"{dev['hostname']:<24} {dev['softwareVersion']:<10} needs upgrade")
```

- **Authenticate:** Basic auth to `/dna/system/api/v1/auth/token`, then the `Token` value in `X-Auth-Token`.
- **Request:** `GET /dna/intent/api/v1/network-device` with `family=Switches and Hubs`.
- **Parse:** the list under `["response"]`; keep devices whose `softwareVersion` is not the golden release.
- **Act:** print each non-compliant switch.

**Workflow:** list switches that are not on the approved software release. It reports only; an upgrade would need the SWIM (image management) API and would return a task to poll.

## RESTCONF: label unused interfaces

```python
import os
import requests

ROUTER = "https://rtr01.example.com"
URL = f"{ROUTER}/restconf/data/ietf-interfaces:interfaces"
HEADERS = {"Accept": "application/yang-data+json",
           "Content-Type": "application/yang-data+json"}
AUTH = (os.environ["RTR_USER"], os.environ["RTR_PASSWORD"])

resp = requests.get(URL, headers=HEADERS, auth=AUTH, verify="lab-ca.pem", timeout=30)
resp.raise_for_status()

for intf in resp.json()["ietf-interfaces:interfaces"]["interface"]:
    if not intf.get("enabled", True) and "description" not in intf:
        name = intf["name"]
        body = {"ietf-interfaces:interface": [{"name": name, "description": "UNUSED"}]}
        r = requests.patch(f"{URL}/interface={requests.utils.quote(name, safe='')}",
                           json=body, headers=HEADERS, auth=AUTH,
                           verify="lab-ca.pem", timeout=30)
        print(name, "labelled" if r.status_code == 204 else f"failed: {r.status_code}")
```

- **Authenticate:** HTTP Basic on every request (`auth=AUTH`) to the router itself: device-level management.
- **Request:** `GET .../ietf-interfaces:interfaces`, then a `PATCH` (merge) per selected interface; the interface name is percent-encoded, so `GigabitEthernet0/0/1` becomes `GigabitEthernet0%2F0%2F1`.
- **Parse:** the RFC 7951 JSON: the top-level member is module-qualified (`ietf-interfaces:interfaces`), the list is an array. Keep interfaces that are disabled (`enabled` false; the YANG default is `true`, hence `.get("enabled", True)`) **and** have no description.
- **Act:** set the description to `UNUSED`; `204 No Content` means the merge succeeded.

**Workflow:** find administratively disabled interfaces without a description on one router and label them `UNUSED`. Interfaces that are enabled, or already described, are untouched.

## Common traps in the options

- **Read versus write.** Count the methods. Only `POST`, `PUT`, `PATCH` and `DELETE` change anything (the ACI login is a `POST` but changes no configuration).
- **Scope.** A filter (`family=`, `statuses[]=`, `query-target-filter`, an `if`) narrows the set; "all devices" is wrong when one exists.
- **Error handling.** `raise_for_status()` stops the script on any `4xx` or `5xx`; a script without it carries on with an error body.
- **Pagination.** One `GET` with no paging loop returns one page only.
- **Asynchronous calls.** A Catalyst Center write typically returns a task id (with `202 Accepted`, or `200` for some operations); the work is not finished until the script polls the task and sees `endTime`.

## Key takeaways

- Read any API script as authenticate, request, parse, act.
- Platform fingerprints: `aaaLogin` and `imdata` (ACI); Bearer API key and `/organizations` (Meraki); `/dna/system/api/v1/auth/token`, `X-Auth-Token` and `response` (Catalyst Center); `/restconf/data/module:node` with `application/yang-data+json` (RESTCONF).
- The HTTP methods decide whether the script reads or changes anything.
- Filters and `if` statements decide which objects are affected; rule out options with those lines.
- Watch for missing pagination, missing error handling and asynchronous tasks.
