## Two places to automate

Every automation script has to decide **what it talks to**:

- **Device-level management**: the script (or Ansible, or Terraform) connects to **each device** and uses that device's own interfaces: SSH and the CLI, NETCONF, RESTCONF, gNMI, NX-API. Domain 3 lesson 3.6 covered these for IOS XE and NX-OS.
- **Controller-level management**: the script talks to **one controller**, which owns the devices and exposes a **northbound API**. The controller then configures the devices itself over its **southbound** protocols. Meraki dashboard, Catalyst Center, the ACI APIC and SD-WAN Manager are controllers (lessons 3.2); NSO orchestrates across controllers and devices.

```text
 Controller-level                              Device-level

   script / Ansible / Terraform                  script / Ansible / Terraform
            |  northbound REST API                  |        |        |
            v  (one endpoint, one token)            |  SSH, NETCONF, RESTCONF
   +------------------------+                       |  (one session per device)
   | controller             |                       v        v        v
   | intent, inventory,     |                    sw01     sw02     rtr01
   | policy, assurance      |
   +------------------------+
     |  southbound: NETCONF, CLI, SNMP, vendor protocols
     v        v        v
   sw01     sw02     rtr01
```

## Controller-level management

The controller holds a **single source of intent**: you describe the desired outcome ("VLAN 30 for cameras at every branch", "this SSID with WPA3 on all floor-2 APs", "this EPG may talk to that EPG on TCP 443"), and the controller works out and pushes the per-device configuration.

**Strengths**

- **Scale and consistency**: one API call can change hundreds of devices, and the controller applies the same policy everywhere.
- **Abstraction**: the API speaks in networks, sites, SSIDs, tenants and policies rather than per-platform syntax; the controller handles model and release differences.
- **One endpoint, one credential**: a single token (Catalyst Center `X-Auth-Token`, Meraki API key, APIC cookie) instead of a login on every box.
- **Network-wide view**: inventory, topology, health, assurance and events in one place, often with webhooks.
- **Built-in workflow**: templates, image management, zero-touch provisioning, audit logs and role-based access.

**Costs**

- **Coverage lags the device**: the API exposes what the controller models; a feature the device supports but the controller does not expose is out of reach (or needs a template or a CLI pass-through).
- **Dependency**: the controller must be licensed, reachable and healthy; its rate limits apply (Meraki: 10 requests per second per organisation).
- **Asynchronous behaviour**: many writes return a task id to poll instead of the finished result (Catalyst Center; often with `202 Accepted`, though some operations document `200`).
- **Less granularity**: you change what the controller lets you change, in its units.

## Device-level management

**Strengths**

- **Full granularity**: every feature the device supports, through its native YANG models or CLI.
- **No extra system**: works on a standalone router, a lab node, or a device the controller does not support.
- **Direct, immediate feedback**: a synchronous reply from the device itself; good for troubleshooting a single box.
- **Fine control of change order** per device, useful for staged rollouts and maintenance windows.

**Costs**

- **Per-device sessions**: N devices means N connections, N credentials to manage and N failure points; your tool has to handle concurrency, retries and partial failure.
- **Per-platform differences**: different OSs, models and releases need different payloads or templates.
- **No global view**: you build inventory, consistency checks and drift detection yourself (or with tools such as Ansible, Terraform, pyATS or NSO).

## Side by side

| | Controller-level | Device-level |
|---|---|---|
| Talks to | One controller's northbound API | Each device's own API or CLI |
| Unit of change | Intent: site, network, policy, template | Configuration of one device |
| Scale | High: the controller fans out | Your tool fans out, one session each |
| Granularity | What the controller models | Everything the device supports |
| Authentication | One token or API key | Credentials for every device |
| Typical replies | REST/JSON, often asynchronous tasks | NETCONF `<rpc-reply>`, RESTCONF JSON, CLI text |
| Examples | Meraki Dashboard API, Catalyst Center Intent API, APIC REST, SD-WAN Manager API | RESTCONF/NETCONF on IOS XE, NX-API on NX-OS, SSH CLI with Ansible `network_cli` |

## When each fits

| Scenario | Better fit | Why |
|---|---|---|
| Change the SSID password on 600 cloud-managed access points tonight | Controller (Meraki Dashboard API) | One call per network; the cloud pushes it |
| Read one router's BGP neighbour table while troubleshooting | Device (RESTCONF or NETCONF on the router) | Immediate, full detail from the device itself |
| Roll out a QoS template to every campus switch at 40 sites | Controller (Catalyst Center templates) | Consistent intent, site hierarchy, asynchronous task tracking |
| Configure a feature the controller does not expose on a lab router | Device | Controller coverage gap |
| Automate a network with no controller | Device, possibly orchestrated by NSO or Ansible | There is no northbound API to use |

> **Exam tip:** "Single point of management", "intent", "abstraction", "northbound API", "consistent policy at scale" → controller. "Per-device session", "full feature coverage", "no controller", "the device's own NETCONF/RESTCONF" → device level.

> **Watch out:** Do not configure the same device both directly and through its controller. The controller treats its intent as the truth and may overwrite the direct change, or report the device as out of compliance. Make the change through the controller, or take the device out of its management.

## Lab it yourself

1. With a reserved Catalyst Center sandbox, get a token and call `GET /dna/intent/api/v1/network-device`: one call, every device.
2. With a reserved IOS XE sandbox, call `GET /restconf/data/ietf-interfaces:interfaces` on the device itself. Compare the scope and detail of the two replies.
3. Write down how many logins and API calls each approach needs to read the interface descriptions of 50 switches.

## Key takeaways

- Controller-level: one northbound API, intent-based, scales and stays consistent, but is limited to what the controller models and depends on it.
- Device-level: one session per device, full granularity and immediate feedback, but you handle scale, credentials and platform differences.
- Meraki, Catalyst Center, APIC and SD-WAN Manager are controllers; NETCONF, RESTCONF, gNMI, NX-API and the CLI are device-level interfaces.
- Pick the controller for fleet-wide policy and the device for gaps, troubleshooting and networks without a controller.
- Avoid changing a controller-managed device directly: the controller may overwrite or flag the change.
