## The same pipeline, applied to the network

Lesson 4.4 built a CI/CD pipeline for an application: source, build, test, artifact, deploy. Infrastructure automation uses the same machinery, but what flows through it is **intended network state**: YAML variables, Jinja2 templates, Ansible playbooks, Terraform files or NSO service instances, all stored in Git. A change starts as a branch and a merge request, and the pipeline decides whether it is safe to reach production.

```text
 push / merge request
        |
        v
 1 Lint and syntax  -->  2 Render configs  -->  3 Test in simulation  -->  4 Review gate
   yamllint,              templates + vars       CML lab + pyATS            merge request
   ansible-lint,          -> per-device           (disposable lab)           approval,
   terraform validate     configs / payloads                                 human sign-off
                                                                                 |
        +------------------------------------------------------------------------+
        v
 5 Staged deploy  -->  6 Verify  -->  pass: done, record state
   canary site,         pyATS learn/diff,          fail: 7 Rollback
   then waves           health checks              (previous commit, NSO rollback,
                                                    config archive, Terraform state)
```

## The components

| Stage | What happens | Typical tools | Catches |
|---|---|---|---|
| **Source control** | Intended state and code live in Git; every change is a commit on a branch | GitHub, GitLab, Bitbucket | Untracked, unreviewed changes |
| **Lint and syntax check** | Fast static checks on every push | `yamllint`, `ansible-lint`, `ansible-playbook --syntax-check`, `terraform fmt -check`, `terraform validate`, `pyang` for YANG, Python linters | Bad indentation, unknown modules, typos, invalid HCL |
| **Render** | Templates plus variables produce the exact device configuration or API payload for each device | Jinja2, the Ansible `template` module, Terraform plan, NSO `commit dry-run` | Missing variables, wrong values per site |
| **Test in simulation** | Deploy the rendered change to a disposable lab and run tests | Cisco Modeling Labs plus pyATS/Genie | A config that applies but breaks routing, reachability or policy |
| **Review gate** | People read the diff and the test results and approve the merge request; branch protection blocks merging until checks pass (lesson 5.13) | Merge/pull requests, required approvals | Design errors, risky timing, wrong intent |
| **Staged deploy** | Push to a canary device or site first, then in waves, often in a change window; a dry run first | Ansible `--check --diff` then a real run with `serial`, `terraform plan` then `apply`, NSO commit | Problems that only show on real hardware or at scale |
| **Verify** | Compare state after the change with the expected state | pyATS `learn`/`diff`, health checks, telemetry | Silent failures, unexpected side effects |
| **Rollback** | Return to the last good state if verification fails | Revert the commit and redeploy, NSO rollback files, `configure replace` of an archived config, Terraform apply of the previous version | Leaving the network broken |

Two rules carry over from application pipelines: **fail fast** (cheap checks first, and any failure stops the run) and **the same artifact everywhere** (the configuration tested in the lab is the configuration deployed, rendered from the same commit).

## Reading a pipeline definition

```yaml
workflow:
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
    - if: $CI_COMMIT_BRANCH == "main"

stages:
  - lint
  - render
  - test
  - deploy
  - verify

lint:
  stage: lint
  image: python:3.13-slim
  script:
    - pip install yamllint ansible-core ansible-lint
    - yamllint .
    - ansible-lint playbooks/
    - ansible-playbook --syntax-check playbooks/site.yml

render:
  stage: render
  image: python:3.13-slim
  script:
    - pip install jinja2 pyyaml
    - python render.py --vars vars/ --out build/
  artifacts:
    paths:
      - build/

lab-test:
  stage: test
  image: python:3.13-slim
  script:
    - pip install "pyats[library]" virl2_client
    - python ci/cml_up.py --topology ci/topology.yaml
    - python ci/push_configs.py build/
    - pyats run job tests/job.py --testbed-file ci/testbed.yaml
    - python ci/cml_down.py
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"

deploy-canary:
  stage: deploy
  script:
    - ansible-playbook playbooks/site.yml --limit canary --check --diff
    - ansible-playbook playbooks/site.yml --limit canary
  environment:
    name: production
  rules:
    - if: $CI_COMMIT_BRANCH == "main"
      when: manual

verify:
  stage: verify
  script:
    - pyats run job tests/job.py --testbed-file inventory/canary-testbed.yaml
  rules:
    - if: $CI_COMMIT_BRANCH == "main"
```

How to read it:

- `workflow: rules` creates a pipeline for merge requests and for the `main` branch only (in GitLab, jobs run in merge request pipelines only when job or workflow rules match `merge_request_event`).
- `stages` fixes the order; a job runs only when every job in the earlier stages passed.
- Lint and render have no `rules` of their own, so they run in both kinds of pipeline. `artifacts` hands the rendered `build/` directory to later jobs, so the lab tests exactly what will be deployed.
- `lab-test` runs only for merge requests (`$CI_PIPELINE_SOURCE == "merge_request_event"`): the review gate sees test results before anyone approves.
- `deploy-canary` runs only on `main`, after the merge, and only when a person clicks it (`when: manual`): that is **continuous delivery**, not continuous deployment (lesson 4.4). It does a dry run (`--check --diff`) first, then the real run, against the canary group only.
- `verify` re-runs the pyATS tests against production devices. Because a `when: manual` job inside `rules` does not allow failure by default, the pipeline waits at the deploy job and `verify` runs only after someone has run it. A verify failure is the trigger for rollback and stops later waves.

> **Exam tip:** Each benefit of infrastructure CI/CD maps onto a stage: consistency (same templates everywhere), fewer human errors (automated checks and no hand-typed CLI), faster and smaller changes, test before production (simulation), an audit trail (Git history and pipeline logs) and fast recovery (rollback to a known-good commit).

## Benefits

- **Fewer outages from typos and drift**: every change is linted, rendered from source and tested before it touches a device.
- **Speed with control**: small changes flow quickly; the review gate and manual deploy keep a human decision where it matters.
- **Repeatability**: the same pipeline builds every site, so sites stay consistent.
- **Traceability**: each device change links to a commit, a merge request, an approver and a pipeline log.
- **Safe recovery**: the last good state is a commit away.

1. Create a free GitHub or GitLab repository with a `vars/` folder of YAML and a Jinja2 template for a switch VLAN block.
2. Add a pipeline (GitHub Actions or GitLab CI) with two jobs: `yamllint .` and a Python render step that writes `build/sw01.cfg`. Push a commit with a YAML indentation error and watch the lint job stop the pipeline.

## Key takeaways

- Infrastructure CI/CD moves intended network state from Git to devices through automated gates.
- Stages: lint and syntax check, render from templates, test in simulation (CML plus pyATS), review gate, staged deploy, verify, rollback.
- Fail fast: cheap checks first; a failed stage stops the pipeline.
- Deploy what you tested: render once and pass the artifact on.
- A manual production step means continuous delivery; staged waves and dry runs limit the blast radius.
- Verification and rollback are part of the pipeline, not an afterthought.
