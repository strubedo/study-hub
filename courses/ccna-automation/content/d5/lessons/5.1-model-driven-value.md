## The problem it solves

Lesson 3.8 taught the mechanics: YANG models, NETCONF RPCs, RESTCONF URLs. This lesson is about *why* an automation team would choose them over the CLI.

Classic CLI automation sends the commands a person would type and reads back text meant for a person. A script that wants interface state runs `show interfaces`, then scrapes the output with regular expressions or TextFSM templates. That works until something changes:

- a new software release adds a column or rewords a line, and the regex silently stops matching;
- a different platform (IOS XE versus NX-OS) prints the same fact in a different layout;
- an error comes back as free text (`% Invalid input detected at '^' marker.`) that the script has to recognise;
- a configuration push of 40 lines fails at line 23, leaving the device half changed.

**Model-driven programmability** replaces that text with **structured data defined by a schema**. The device publishes YANG models that say exactly which nodes exist, their types and constraints; NETCONF, RESTCONF or gNMI carry data that conforms to those models as XML, JSON or protobuf.

## What you gain

| Benefit | CLI screen scraping | Model-driven (YANG + NETCONF/RESTCONF/gNMI) |
|---|---|---|
| **Data format** | Human-oriented text; layout can change between releases | Structured XML/JSON defined by a published model; parse with `json` or `ElementTree`, no regex |
| **Contract** | None; the output format is not a promise | The YANG module is a machine-readable contract with a namespace and a revision date |
| **Validation** | The device rejects bad input line by line, after you send it | Types, ranges, patterns, `mandatory` and `must` rules are known up front; the server validates the whole edit and the client can validate before sending |
| **Transactions** | Each line applies as typed; a failure mid-way leaves partial config | NETCONF `<edit-config>` on the candidate datastore plus `<commit>` applies all or nothing; `<lock>` stops concurrent edits; `:confirmed-commit` reverts automatically if not confirmed |
| **Errors** | Free text | Structured `<rpc-error>` with `error-type`, `error-tag`, `error-severity` and the path to the failing node (lesson 5.10) |
| **Multivendor** | One parser per platform and release | IETF and OpenConfig models (for example `ietf-interfaces`, `openconfig-interfaces`) give one schema across vendors that implement them |
| **State collection** | Poll and parse `show` output, or SNMP | **Model-driven telemetry**: the device streams YANG-modelled data on a schedule or on change |
| **Tooling** | Hand-written parsers | Generated code and tools: `pyang` trees, `ncclient`, Ansible `netconf`/`restconf` modules, Terraform providers, NSO NEDs |

> **Exam tip:** When a question asks for the *value* of model-driven programmability, look for the words structured data, schema or model, validation, transactions (candidate plus commit), vendor neutrality and telemetry. "Faster CLI" or "no authentication needed" are never the answer.

## The model is the contract

The key idea is separation: the **model** (what the data is) is independent of the **protocol** (how it moves) and the **encoding** (XML, JSON, protobuf). One `ietf-interfaces` model can be read with NETCONF as XML, with RESTCONF as JSON, or streamed with gNMI. A script written against the model keeps working when the protocol changes, and the same data can feed a configuration tool and a monitoring system.

Because a module carries a `revision` date and the device advertises the modules and revisions it supports (in its NETCONF hello and its YANG library), a tool can check up front whether a device supports what it needs instead of discovering it by trial and error.

## Configuration as data

Once configuration is structured data, the infrastructure-as-code practices of Domain 5 become natural:

- **Intended state lives in files** (YAML or JSON variables, or the payload itself) under version control (lesson 5.5).
- **Rendering** a payload from variables is a template or a dictionary, not string concatenation of CLI lines.
- **Comparing** intended and actual state is a data comparison: fetch the subtree, diff the two dictionaries, push only what differs. That makes tasks **idempotent**: running twice changes nothing the second time.
- **Validation in a pipeline**: a CI job can check a payload against the YANG schema before any device sees it (lesson 5.4).

## Telemetry: push instead of poll

Model-driven telemetry (covered for IOS XE in lesson 3.6) streams the same YANG data out of the device. **Dial-in** means the collector connects and subscribes (gNMI `Subscribe`, or NETCONF dynamic subscriptions); **dial-out** means the device is configured to connect to the collector and push. Subscriptions are **periodic** (every *n* centiseconds on IOS XE) or **on-change**. Compared with SNMP polling, the data arrives with the same schema the configuration uses, at finer granularity, without the collector asking every few minutes.

## Where it does not help

Be accurate about limits:

- **Model coverage varies.** IETF and OpenConfig models cover common features only; anything platform-specific needs the vendor's native model (`Cisco-IOS-XE-native`), which ties the script to that platform.
- **Older or low-end devices** may not offer NETCONF or RESTCONF at all, so CLI automation (Ansible `network_cli`, Netmiko) is still common.
- **Payloads are verbose**, and the learning curve (YANG, namespaces, filters) is real.

> **Real world:** Most networks run both. Model-driven APIs handle the devices and features that support them; CLI automation covers the rest, ideally with parsers such as Genie (lesson 5.3) that turn `show` output into dictionaries so the rest of the code still works with structured data.

## Lab it yourself

1. Reserve an IOS XE sandbox from the DevNet Sandbox catalog (or use a Cisco Modeling Labs IOS XE node). SSH in and run `show interfaces GigabitEthernet1`. Note how much parsing you would need to pull out the description and the input packet counter.
2. Fetch the same interface with RESTCONF using curl or Postman: `GET https://<host>/restconf/data/ietf-interfaces:interfaces/interface=GigabitEthernet1` with `Accept: application/yang-data+json`. Load the reply with Python's `json` module and print `["ietf-interfaces:interface"][0]["description"]`.
3. Send a PATCH with an invalid value, for example `"enabled": "maybe"`, and read the structured error that comes back.
4. Compare the two approaches in a short note: which one would survive a software upgrade unchanged?

## Key takeaways

- Model-driven programmability replaces human-oriented CLI text with structured data defined by YANG models.
- The model is a contract: typed, validated, versioned by revision date, and independent of protocol and encoding.
- NETCONF adds transactions: candidate datastore, `<commit>`, `<lock>` and confirmed commit; errors are structured `<rpc-error>` elements.
- IETF and OpenConfig models give vendor-neutral scripts; native models cover everything on one platform.
- Model-driven telemetry streams the same modelled data, dial-in or dial-out, periodic or on-change.
- Structured configuration makes idempotent, version-controlled, pipeline-tested automation practical.
