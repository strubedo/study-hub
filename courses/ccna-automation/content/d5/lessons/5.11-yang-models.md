## What "interpret a YANG model" means

You will be shown a YANG module (or part of one) or its tree diagram and asked what data it allows: which node is the list key, which leaves are configuration and which are state, what is optional, what type and range a value must have, what a valid JSON or XML instance or RESTCONF URL looks like. Lesson 3.8 introduced the statements; this lesson reads a whole module and its tree side by side. The module follows YANG 1.1 (RFC 7950) and the tree follows the YANG tree diagram format (RFC 8340).

## A complete small module

```yang
module example-ntp {
  yang-version 1.1;
  namespace "urn:example:ntp";
  prefix ntp;

  import ietf-inet-types {
    prefix inet;
  }

  organization "Example Corp network automation team";
  description "NTP client configuration and state, for course examples.";

  revision 2026-11-22 {
    description "Initial revision.";
  }

  typedef stratum-type {
    type uint8 {
      range "1..16";
    }
  }

  container ntp {
    leaf enabled {
      type boolean;
      default "true";
    }
    leaf source-interface {
      type string;
    }
    list server {
      key "address";
      leaf address {
        type inet:host;
      }
      leaf prefer {
        type boolean;
        default "false";
      }
      leaf version {
        type uint8 {
          range "3..4";
        }
        default "4";
      }
      leaf-list key-ids {
        type uint16;
      }
      leaf stratum {
        type stratum-type;
        config false;
      }
      leaf reachable {
        type boolean;
        config false;
      }
    }
    container statistics {
      config false;
      leaf packets-sent {
        type uint64;
      }
      leaf packets-received {
        type uint64;
      }
    }
  }
}
```

### The header

| Statement | Value | What it gives you |
|---|---|---|
| `module` | `example-ntp` | The module name. RESTCONF URLs and JSON use it: `example-ntp:ntp` |
| `yang-version` | `1.1` | YANG 1.1 (RFC 7950); without it the module is YANG 1.0 (RFC 6020) |
| `namespace` | `urn:example:ntp` | A globally unique URI; NETCONF XML uses it as `xmlns="urn:example:ntp"` |
| `prefix` | `ntp` | A short name used **inside YANG** (in paths, augments, XPath) and in tree diagrams for nodes augmented in from elsewhere. JSON does not use it |
| `import` | `ietf-inet-types` with prefix `inet` | Lets this module use that module's types as `inet:...` (here `inet:host`, an IP address or a domain name) |
| `revision` | `2026-11-22` | The version date; a device advertises the revisions it implements |
| `typedef` | `stratum-type` | A reusable named type: a `uint8` restricted to 1 to 16 |

### The body

- `container ntp` groups everything; there is exactly one of it. It is a non-presence container, so it exists as long as something inside it does.
- `leaf enabled` is a boolean that defaults to `true` if not set.
- `list server` with `key "address"`: any number of servers, each identified uniquely by its `address`. The key leaf is **mandatory** in each entry and cannot be changed in place (delete and recreate instead).
- `leaf version` is a `uint8` restricted to 3 or 4, default 4. A value of 2 is rejected.
- `leaf-list key-ids`: a list of plain `uint16` values, such as `[1, 7]`.
- `stratum` and `reachable` have `config false`: **state data** the device reports, which you cannot configure.
- `container statistics` has `config false`, so **everything under it** is state.

## The same module as a tree

```text
module: example-ntp
  +--rw ntp
     +--rw enabled?            boolean
     +--rw source-interface?   string
     +--rw server* [address]
     |  +--rw address      inet:host
     |  +--rw prefer?      boolean
     |  +--rw version?     uint8
     |  +--rw key-ids*     uint16
     |  +--ro stratum?     stratum-type
     |  +--ro reachable?   boolean
     +--ro statistics
        +--ro packets-sent?       uint64
        +--ro packets-received?   uint64
```

| Symbol | Meaning (RFC 8340) | Example |
|---|---|---|
| `+--` | A node; children are indented three spaces | |
| `rw` | Configuration data (read-write) | `enabled` |
| `ro` | State data (read-only, `config false`) | `stratum`, `statistics` |
| `?` | Optional leaf (or choice, anydata, anyxml) | `prefer?` |
| no `?` on a leaf | Mandatory, or a list key | `address` |
| `*` | A list or a leaf-list | `server*`, `key-ids*` |
| `[address]` | The list's key(s) | `server* [address]` |
| `!` | Presence container (its existence means something) | `ip:ipv4!` in `ietf-ip` |
| `(name)` and `:(name)` | Choice and case | `(subnet)` in `ietf-ip` |
| `prefix:name` | Node added by another module (augment) | `ip:ipv4` |
| `-x`, `-w`, `-n` | RPC or action, its input, a notification | under `rpcs:` and `notifications:` |
| `{feature}?` | Exists only if the server supports that feature | `{if-mib}?` in `ietf-interfaces` |
| `|` | Connects siblings when a node above has children printed between them | the line beside `server`'s children |
| `x` or `o` instead of `+` | Deprecated or obsolete node | |

To tell a list from a leaf-list, look at what follows: `server* [address]` has a key and children, so it is a list; `key-ids*   uint16` has a type and no children, so it is a leaf-list. A leaf shows its type at the end; a container and a list do not.

## From the model to data

A valid configuration instance, as RESTCONF JSON (RFC 7951):

```json
{
  "example-ntp:ntp": {
    "enabled": true,
    "source-interface": "Loopback0",
    "server": [
      {"address": "192.0.2.10", "prefer": true, "key-ids": [1, 7]},
      {"address": "time.example.com", "version": 3}
    ]
  }
}
```

The same as NETCONF XML:

```xml
<ntp xmlns="urn:example:ntp">
  <enabled>true</enabled>
  <source-interface>Loopback0</source-interface>
  <server>
    <address>192.0.2.10</address>
    <prefer>true</prefer>
    <key-ids>1</key-ids>
    <key-ids>7</key-ids>
  </server>
  <server>
    <address>time.example.com</address>
    <version>3</version>
  </server>
</ntp>
```

Note the leaf-list: a JSON array, but repeated elements in XML. With state included (a `<get>`, or RESTCONF GET without `content=config`), each `server` would also carry `stratum` and `reachable`, and `statistics` would hold `"packets-sent": "1520"`: a **string**, because `uint64` is a 64-bit type.

URLs follow the tree: the container is `/restconf/data/example-ntp:ntp`, one server is `/restconf/data/example-ntp:ntp/server=192.0.2.10` (list name, `=`, key value), one leaf is `.../server=192.0.2.10/prefer`.

Instances that this model **rejects**:

| Instance | Why |
|---|---|
| `"version": 2` | Outside `range "3..4"` |
| A `server` entry without `address` | Every list entry needs its key |
| Two entries with `"address": "192.0.2.10"` | Keys must be unique |
| Configuring `"stratum": 2` in a PUT or PATCH | `stratum` is `config false`; you cannot write state |
| `"enabled": "yes"` | `boolean` takes `true` or `false` |
| `"ntp:ntp"` as the top-level member | JSON uses the module name, not the prefix |

## Other statements you may meet

- `grouping` and `uses`: a named, reusable set of nodes copied in where `uses` appears.
- `augment "/if:interfaces/if:interface"`: adds nodes to another module's tree (how `ietf-ip` adds `ipv4` to `ietf-interfaces`).
- `choice` and `case`: mutually exclusive alternatives (`prefix-length` or `netmask`).
- `identity` and `type identityref`: extensible named values (`iana-if-type:ethernetCsmacd`).
- `mandatory true`, `must "..."` (an XPath constraint), `when "..."` (a node exists only if a condition holds), `enumeration`, `pattern`, `length`, `units`.
- `rpc` and `action`, with `input` and `output`; `notification`.

## Lab it yourself

1. On Linux, macOS or Windows, create a Python virtual environment, `pip install pyang`, and save the module above as `example-ntp@2026-11-22.yang`. Download `ietf-inet-types` from the YangModels GitHub repository into the same folder, then run `pyang -p . -f tree example-ntp@2026-11-22.yang` and compare its output with the tree above.
2. Introduce an error (`range "3..4"` on a leaf of type `string`) and run `pyang` again to see the validation error.
3. Run `pyang -f tree` on `ietf-interfaces.yang` from the same repository and find every `ro` node and every `{if-mib}?` feature.

## Key takeaways

- Module header: name (used in JSON and RESTCONF), `namespace` (used in XML), `prefix` (used inside YANG), `import`, `revision`.
- Body: `container` (one), `list` with `key` (many, unique by key), `leaf` (one typed value), `leaf-list` (many values), `typedef` (named type).
- `config false` makes a node and everything below it state data; it shows as `ro` in the tree.
- Tree symbols: `rw`/`ro`, `?` optional, `*` list or leaf-list, `[key]`, `!` presence, `prefix:` augmented node.
- Types and restrictions (`range`, `default`) decide which values are valid; 64-bit integers appear as JSON strings.
- URLs and payloads follow the tree: `module:top-node/list=key/leaf`.
