## What a sequence diagram shows

A **sequence diagram** shows **who sends which message to whom, in what order**. API documentation uses them to explain authentication flows, asynchronous jobs and webhooks; the exam shows one and asks what happens, in which order, or why. The notation comes from UML 2.5 (the Interactions chapter), usually drawn with tools such as PlantUML or Mermaid. Here they are drawn as text.

## The notation

| Element | UML 2.5 notation | In the text diagrams below |
|---|---|---|
| **Participant** (lifeline head) | A rectangle with the participant's name at the top | `[ Script ]`, `[ Catalyst Center ]` |
| **Lifeline** | A vertical line, often dashed, below the head: the participant's lifetime | `|` |
| **Time** | Flows **downward**: a message lower on the page happens later | |
| **Synchronous message** | Solid line, **filled** arrowhead: the sender waits for the reply | `------->` |
| **Asynchronous message** | Solid line, **open** arrowhead: the sender does not wait | `------->>` |
| **Reply (return) message** | **Dashed** line back to the caller | `<- - - - -` |
| **Activation** (execution specification) | A thin rectangle on a lifeline while the participant is busy | `#` on the lifeline |
| **Combined fragment** | A box with an operator in its corner, a **guard** in brackets: `alt` (if / else, at most one operand runs), `opt` (if), `loop` (repeat while the guard holds), `par` (in parallel) | `+-- loop [guard] --+` |

An HTTP call drawn as a synchronous arrow plus a dashed reply is the normal REST pattern: the client sends the request and waits for the status code and body.

## Reading method

1. **List the participants** left to right. Which are clients, controllers, devices, external services?
2. **Number the arrows** top to bottom. That is the order of events.
3. For each arrow: **sender, receiver, method and path, headers that matter** (tokens), and for replies the **status code** and key fields.
4. Note **synchronous versus asynchronous**: does the sender wait?
5. Read every **fragment**: what repeats (`loop`) and what is conditional (`alt`, `opt`), and their guards.
6. Map it to what you know: token flows (lesson 2.7), asynchronous tasks (2.8), webhooks (2.2), pagination.

## Example 1: a Catalyst Center job with a task to poll

```text
     [ Script ]                         [ Catalyst Center ]                [ sw01 ]
         |                                       |                            |
 (1)     |------- POST /dna/system/api/v1/auth/token ------->|               |
         |        Authorization: Basic <base64 user:password>                 |
 (2)     |<- - - - 200 {"Token": "..."} - - - - - - - - - - -|               |
         |                                       |                            |
 (3)     |------- PUT /dna/intent/api/v1/network-device/sync ---->|          |
         |        X-Auth-Token: <token>   body: ["<device id>"]               |
 (4)     |<- - - - 202 {"response": {"taskId": "..."}} - - - - -|          |
         |                                       |                            |
 (5)     |                                       |----- collect inventory --->>
         |                                       |      (CLI over SSH, SNMP)  #
  +-- loop [task has no endTime] ------------------------------+              #
  | (6)  |------- GET /dna/intent/api/v1/task/{taskId} ------->|              #
  | (7)  |<- - - - 200 {"response": {"progress": ...}} - - - -|              |
  |      |  wait 5 s if no endTime yet           |             |              |
  +------------------------------------------------------------+              |
  +-- alt [isError is false] ----------------------------------+              |
  | (8)  |  print "sync complete"                |             |              |
  |-- [else] --------------------------------------------------|              |
  | (9)  |  print failureReason, exit 1          |             |              |
  +------------------------------------------------------------+              |
```

Reading it:

- **Participants**: the script, the Catalyst Center controller, and a switch the controller manages. The script never talks to `sw01` directly: this is controller-level management (lesson 5.2).
- **(1)-(2)**: a synchronous token request with Basic authentication; the reply carries `Token`.
- **(3)-(4)**: the write call (a device resync) sends the token in `X-Auth-Token`. The controller replies at once with a `taskId`, before the work is done. The diagram shows **202 Accepted**; the Catalyst Center 3.1.6 reference documents this reply body under `200` and also lists `202`, so a script should accept either and rely on the `taskId`.
- **(5)**: the controller contacts the switch on its own, **asynchronously** (open arrowhead, `>>`), and the switch's lifeline is active (`#`) while it works: the script is not part of that exchange.
- **(6)-(7)** inside a **loop**: the script polls the task until `endTime` appears.
- **alt**: if the finished task has `isError` false the script reports success; otherwise (`else`) it prints `failureReason` and exits with status 1.

So the order of API calls is: token, PUT sync, then repeated GET task; the call to the switch happens in parallel with the polling and is not an API call the script makes.

## Example 2: a webhook

```text
 [ Meraki cloud ]            [ Webhook receiver ]            [ Webex API ]
       |                              |                             |
  (1)  |--- POST /alerts ------------>>                             |
       |    {"alertType": "Appliance went down", ...}               |
       |                              #                             |
  (2)  |<- - - 200 OK - - - - - - - - |                             |
       |                              |                             |
       |   +-- opt [alertType contains "went down"] ---------------+ |
       |   |(3)|--- POST /v1/messages ------------------------------->|
       |   |   |    Authorization: Bearer <bot token>               | #
       |   |(4)|<- - - 200 {"id": "..."} - - - - - - - - - - - - - -  |
       |   +--------------------------------------------------------+ |
```

- The flow starts at the **platform**, not the client: Meraki **pushes** an event to the receiver's URL. That is a webhook (lesson 2.2), an event-driven, asynchronous notification. The receiver answers quickly with `200` so Meraki knows it was delivered.
- The **opt** fragment means messages (3) and (4) happen only when the guard is true: only "went down" alerts are forwarded to a Webex space, using the bot's Bearer token.
- A receiver that is slow to answer risks the sender treating the delivery as failed, so a good receiver acknowledges first and does slow work afterwards.

## Example 3: pagination as a loop

```text
 [ Script ]                                   [ Meraki Dashboard API ]
     |--- GET /organizations/{id}/devices?perPage=1000 ---->|
     |<- - - 200 [1000 devices]  Link: <...>; rel=next - - -|
 +-- loop [response has a Link rel=next] ------------------------+
 |   |--- GET <the rel=next URL> ------------------------------->|
 |   |<- - - 200 [up to 1000 devices]  Link: ... - - - - - - - - |
 +---------------------------------------------------------------+
     |   write inventory.csv                                    |
```

With 2,300 devices: one initial GET (1,000), then the loop runs twice (1,000 and 300); the last reply has no `rel=next` link, so the loop ends. Three GETs in total.

## Common questions about a diagram

- **"What is the first call after authentication?"** Number the arrows and skip the token exchange.
- **"Which header does call N carry?"** Read the annotation under the arrow; token flows put the token from reply N-1 into request N.
- **"Why does the script poll?"** Because a reply carried a task id (often with `202 Accepted`) instead of the result: asynchronous processing.
- **"Which messages might not happen?"** Those inside `opt`, or in the non-taken operand of `alt`.
- **"Which participant initiates?"** The source of the first arrow: in a webhook it is the platform.
- **"Is it controller or device level?"** Check whether the client's arrows go to a controller or straight to devices.

## Key takeaways

- Participants across the top, lifelines down, time flows downward; number the arrows to get the order.
- Synchronous message: solid line, filled arrowhead, the sender waits. Asynchronous: open arrowhead, no wait. Reply: dashed line.
- Fragments: `loop` repeats while the guard holds, `alt` picks one branch (`else` for the rest), `opt` may not happen, `par` runs in parallel.
- A reply carrying a task id (often `202`) followed by a loop of GETs is asynchronous task polling.
- A webhook flow starts at the platform and needs a quick `200` from the receiver.
- Arrows straight to devices mean device-level management; arrows only to a controller mean controller-level.
