## Five services every application depends on

Topic 6.6 names five IP services: **DHCP**, **DNS**, **NAT**, **SNMP** and **NTP**. An application rarely talks to them on purpose, but it fails in recognisable ways when any of them is wrong. For each one, learn what it does, its transport and port, and what breaks.

| Service | Job | Transport and port (IANA) |
|---|---|---|
| DHCP | Give hosts an address, mask, gateway, DNS servers | UDP 67 (server), UDP 68 (client) |
| DNS | Turn names into addresses and other records | UDP 53 and TCP 53 |
| NAT | Rewrite addresses (and ports) as packets cross a boundary | Not a port: a function of a router or firewall |
| SNMP | Poll and receive alerts from devices | UDP 161 (agent, polling), UDP 162 (manager, traps and informs) |
| NTP | Synchronise clocks | UDP 123 |

## DHCP

The **Dynamic Host Configuration Protocol** (RFC 2131) leases configuration to hosts so nobody types addresses by hand. A new client goes through **DORA**:

1. **Discover.** The client, which has no address yet, broadcasts from `0.0.0.0` port 68 to `255.255.255.255` port 67: "any DHCP servers?"
2. **Offer.** A server offers an address and options.
3. **Request.** The client broadcasts a request for the offer it chose (naming that server), which also tells other servers their offers were declined.
4. **Acknowledge.** The server confirms with a DHCPACK; the lease starts.

The lease includes the address, mask and options such as the **router** (default gateway, option 3), **DNS servers** (option 6), domain name (option 15), **vendor-specific information** (option 43) and the TFTP server and boot file (options 66 and 67) that zero-touch provisioning uses to give a new switch or router its first configuration or script.

**Leases expire.** By default a client tries to **renew** with its server (unicast) at **T1 = 50%** of the lease and, failing that, **rebinds** with any server (broadcast) at **T2 = 87.5%**.

**Relay.** Broadcasts do not cross routers, so a central DHCP server needs a **relay agent** on each client subnet's gateway, configured on Cisco IOS with `ip helper-address 10.50.0.10` on the SVI or interface. The relay forwards the request as unicast to the server and writes its own interface address in the `giaddr` field; the server uses `giaddr` to choose the right scope.

**What breaks:** no DHCP answer leaves the host with no address or a `169.254.x.x` link-local address, so nothing beyond the local link works. Wrong options are subtler: a wrong option 6 makes every name lookup fail while IP connectivity is fine; a wrong option 3 lets the host reach its own subnet only. A missing `ip helper-address` on a new VLAN is the classic cause when only that VLAN's hosts fail.

## DNS

The **Domain Name System** (RFC 1034 and 1035) maps names to data. When your script calls `requests.get("https://api.example.com/...")`, the resolution path is:

1. The application asks the operating system's **stub resolver** (via `getaddrinfo`).
2. The OS checks its **hosts file** and **cache**.
3. If needed it asks the **recursive resolver** it was given (by DHCP option 6, VPN settings or manual configuration).
4. The recursive resolver, if it has no cached answer, queries **iteratively**: a **root** server refers it to the `.com` **TLD** servers, which refer it to the **authoritative** servers for `example.com`, which return the answer.
5. The recursive resolver **caches** the answer for its **TTL** and returns it to the client, which also caches it.

DNS uses **UDP 53** for most queries and **TCP 53** for zone transfers and for responses too large for UDP (the server sets the truncation bit and the client retries over TCP). RFC 7766 requires DNS servers and resolvers to support TCP, so a firewall that allows only UDP 53 causes intermittent failures on large answers.

| Record | Holds | Example |
|---|---|---|
| A | IPv4 address | `api.example.com. 300 IN A 198.51.100.20` |
| AAAA | IPv6 address (RFC 3596) | `api.example.com. 300 IN AAAA 2001:db8:20::20` |
| CNAME | Alias to another name | `www.example.com. 3600 IN CNAME web.example.net.` |
| MX | Mail server, with preference (lower preferred) | `example.com. 3600 IN MX 10 mail.example.com.` |
| PTR | Reverse lookup: address to name | `20.100.51.198.in-addr.arpa. IN PTR api.example.com.` |
| TXT | Free text: domain verification, SPF | `example.com. IN TXT "v=spf1 -all"` |
| SRV | Service location: priority, weight, port, target (RFC 2782) | `_sip._tcp.example.com. IN SRV 10 60 5060 sip1.example.com.` |
| NS / SOA | Delegation and zone authority | |

The **TTL** (seconds) controls how long resolvers may cache a record. Lower it before a planned migration; after a change, clients may keep the old answer until their cached copy expires.

**What breaks:** a lookup failure surfaces in Python `requests` as a `ConnectionError` caused by `NameResolutionError` ("Failed to resolve 'api.example.com' ([Errno -2] Name or service not known)" on Linux; Windows reports `getaddrinfo failed`). An internal name that resolves only on the internal DNS fails from home unless the VPN supplies that DNS server (lesson 6.8). A stale record sends some clients to an old address.

## NAT

**Network Address Translation** rewrites IP addresses, and with PAT also ports, as packets pass through a router or firewall (RFC 2663 terminology; RFC 3022 for traditional NAT). It lets RFC 1918 hosts reach the internet and hides internal addressing.

| Type | Mapping | Typical use |
|---|---|---|
| **Static NAT** | One inside address to one fixed outside address, both directions | Publishing a server; inbound connections work |
| **Dynamic NAT** | Inside addresses take a free address from a pool, one-to-one while in use | Rare today |
| **PAT** (NAPT, Cisco "overload") | Many inside addresses share one outside address, told apart by **source port** | Every home router and most office internet access |

Cisco's four address terms, from the point of view of the NAT device:

- **Inside local:** the inside host's real address (for example 10.1.10.25).
- **Inside global:** how the inside host appears outside (203.0.113.2).
- **Outside local:** how the outside host appears to the inside (usually its real address).
- **Outside global:** the outside host's real address.

```text
rtr01# show ip nat translations
Pro  Inside global         Inside local          Outside local         Outside global
tcp  203.0.113.2:51012     10.1.10.25:51012      198.51.100.20:443     198.51.100.20:443
tcp  203.0.113.2:1024      10.1.10.26:51012      198.51.100.20:443     198.51.100.20:443
---  203.0.113.5           172.16.50.10          ---                   ---
```

The first two lines are PAT: two inside hosts happen to use the same source port, so the second is given port 1024 on the shared address. The last line is a static NAT entry.

**What breaks:** inbound connections to a PAT-only host fail because no mapping exists until the inside host starts the flow; a server sees the NAT address, not the client's real one (log analysis and allow-lists must use the translated address); protocols that carry IP addresses inside the payload (FTP active mode, SIP) need help from the NAT device; and heavy PAT can run out of ports. Lesson 6.8 covers NAT faults in detail.

## SNMP

The **Simple Network Management Protocol** (architecture in RFC 3411, operations in RFC 3416, transport in RFC 3417) lets a **manager** (the monitoring system) read and sometimes write values held by an **agent** on each device.

- The **MIB** (Management Information Base) defines the objects; each object has an **OID**, a dotted number in a global tree. Examples from the standard MIBs: `sysDescr` `1.3.6.1.2.1.1.1`, `sysUpTime` `1.3.6.1.2.1.1.3`, `sysName` `1.3.6.1.2.1.1.5`, and `ifDescr` `1.3.6.1.2.1.2.2.1.2` in the interfaces table (append the instance, such as `.0` for a scalar).
- **Polling:** the manager sends Get, GetNext, GetBulk or Set to the agent on **UDP 161**.
- **Notifications:** the agent sends **traps** (unacknowledged) or **informs** (acknowledged, resent until confirmed) to the manager on **UDP 162**.

| Version | Security |
|---|---|
| SNMPv1 | Community string, sent in clear text |
| SNMPv2c | Community string in clear text; adds GetBulk and informs |
| SNMPv3 | Users with authentication and encryption (USM): `noAuthNoPriv`, `authNoPriv`, `authPriv` |

**Model-driven telemetry** is the modern alternative. Instead of the manager polling OIDs on a timer, the device **streams** data defined by **YANG** models to a collector, either periodically or **on change**, over gRPC (gNMI) or NETCONF subscriptions. It scales better (no per-poll request), gives finer-grained timing and uses the same data models as NETCONF and RESTCONF configuration. SNMP is still everywhere for basic monitoring.

**What breaks:** SNMP runs on UDP, so a wrong community string, an ACL or a blocked port just produces **no reply** and the manager times out. Traps are fire-and-forget: if UDP 162 is blocked or the collector is down, the alert is lost silently.

## NTP

The **Network Time Protocol** (RFC 5905) synchronises clocks over **UDP 123**. Servers form a hierarchy by **stratum**: stratum 1 servers are attached to a reference clock such as GPS; each level that synchronises from the one above adds one; **16 means unsynchronised**.

Why an automation engineer cares:

- **Logs.** Correlating syslog from fifty devices with your script's log only works if every clock agrees.
- **Certificates.** TLS checks a certificate's *not before* and *not after* dates against the local clock. A device or container whose clock is years off rejects valid certificates as "not yet valid" or "expired", which shows up as an `SSLError` in Python.
- **Tokens.** API tokens and JWTs carry issue and expiry times (`iat`, `exp`, `nbf`). A client or server with a skewed clock sees fresh tokens as expired, producing `401` responses that look like an authentication bug. Kerberos and one-time-password codes are similarly time-sensitive.

On Cisco IOS: `ntp server 10.50.0.20` and `show ntp status`. On hosts: `w32tm /query /status` (Windows), `sntp` or the Date and Time settings (macOS), `timedatectl` or `chronyc tracking` (Linux).

## Lab it yourself

Read-only commands on your own computer:

1. **DHCP:** `ipconfig /all` (Windows) shows the DHCP server, lease obtained and expires times, gateway and DNS servers. macOS: `ipconfig getpacket en0`. Linux: `nmcli device show` or `resolvectl status`.
2. **DNS:** look up the documentation domain. Windows: `nslookup -type=MX example.com` or `Resolve-DnsName example.com -Type AAAA` (PowerShell). macOS and Linux: `dig example.com AAAA` and `dig example.com TXT`. Note the TTL in each answer, then run the query again and watch it count down from your resolver's cache.
3. **NAT:** compare your computer's address (step 1) with the public address your home router has on its status page. The difference is PAT.
4. **NTP:** `w32tm /query /status` (Windows), `timedatectl` (Linux), System Settings > General > Date & Time (macOS). Find your time source.
5. **SNMP:** read the `system` group of RFC 3418 and find the OIDs above; no device needed.

## Key takeaways

- DHCP: DORA over UDP 67/68; leases renew at 50% and rebind at 87.5%; `ip helper-address` relays across routers using `giaddr`. Failure: no address or `169.254.x.x`.
- DNS: stub resolver, recursive resolver, then root, TLD and authoritative servers; answers cached for the TTL. UDP and TCP 53. Know A, AAAA, CNAME, MX, PTR, TXT and SRV.
- NAT: static (one-to-one, inbound works), dynamic (pool), PAT (many-to-one by port). Inside local is the real inside address; inside global is how it appears outside.
- SNMP: manager polls the agent on UDP 161; traps and informs go to UDP 162; v3 adds authentication and encryption; streaming telemetry pushes YANG-modelled data instead of polling.
- NTP: UDP 123, stratum 1 is closest to the reference clock, 16 is unsynchronised; wrong time breaks log correlation, certificate validation and token expiry.
