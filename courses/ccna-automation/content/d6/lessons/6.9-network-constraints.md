## The network is not free, instant or reliable

Code that works against a sandbox on the same LAN can crawl, stall or fail against 500 branch routers over a WAN. Topic 6.9 asks you to explain how **network constraints** affect applications. The five to know are **bandwidth**, **latency**, **jitter**, **packet loss** and **MTU**. For each, know what it is, how it shows up in an API client, and which design choice reduces its impact.

| Constraint | Definition | Shows up as |
|---|---|---|
| **Bandwidth** | Capacity of the link, in bits per second | Large transfers take long; one big job crowds out others |
| **Latency** | Time for a packet to travel one way; round-trip time (RTT) is there and back | Every request waits at least one RTT; chatty code is slow even on fast links |
| **Jitter** | Variation in latency from packet to packet | Uneven response times; choppy voice and video; streaming data arrives in bursts |
| **Packet loss** | Share of packets that never arrive | TCP retransmits: stalls and lower throughput; UDP data is simply missing |
| **MTU** | Largest packet a link carries without fragmentation (1,500 bytes on Ethernet) | Large packets dropped on tunnels when path MTU discovery fails |

## Bandwidth

Bandwidth limits how much data per second can move. A 200 MB software image over a 20 Mbit/s branch link takes at least 200 × 8 / 20 = **80 seconds**, before any protocol overhead, and while it runs it competes with users' traffic. Design responses:

- **Ask for less.** Filter on the server (`?status=offline`, a YANG XPath or subtree filter) rather than downloading everything and filtering in Python. Request only the fields you need when the API supports it.
- **Compress.** HTTP clients advertise `Accept-Encoding: gzip`; `requests` sends `gzip, deflate` by default (plus `br` and `zstd` when those Python packages are installed) and decompresses transparently. JSON and XML compress very well.
- **Schedule and throttle** bulk jobs (image distribution, full backups) outside business hours, or stage files close to the devices.

## Latency

Latency adds a fixed cost to **every** round trip, no matter how fast the link. That makes the number of round trips, not the amount of data, the main cost of most API automation.

Example: collecting one value from each of **500** devices over a WAN with an **80 ms** RTT, one request at a time.

| Approach | Round trips per device | Time |
|---|---|---|
| New TCP + TLS 1.3 connection for every request | TCP handshake 1 + TLS 1 + request 1 = 3 | 500 × 3 × 80 ms = **120 s** |
| One `requests.Session` reusing connections (keep-alive) | About 1 | 500 × 80 ms = **40 s** |
| One controller call returning all 500 (a bulk endpoint, with pagination) | A few pages | **Under 1 s** of round-trip time |

(TLS 1.2 needs two round trips for its handshake instead of one, which makes the first row worse.)

Latency also caps the throughput of a single TCP connection: it can send at most one **window** of data per round trip. With a 64 KB window and a 100 ms RTT that is 65,535 × 8 / 0.1 ≈ **5.2 Mbit/s**, whatever the link speed. Modern stacks scale the window up, but loss shrinks it again (below).

Design responses: avoid **chatty** APIs (many tiny calls) in favour of bulk or batch endpoints; reuse connections with a `Session`; run independent requests **concurrently** (threads or `asyncio`) within the API's rate limit; and put automation close to what it manages (an on-premises controller, edge compute; lesson 4.1).

## Jitter

Jitter is the variation in delay. TCP-based request/response APIs tolerate it: you see uneven response times, which matter only when timeouts are set too tight. It hurts **real-time** traffic most: voice and video need packets at a steady rate, so receivers keep a **jitter buffer** (adding delay), and Webex or other media drop quality when jitter is high. For streaming telemetry and event feeds, jitter means data arrives in bursts, so collectors should use the **timestamps in the data**, not arrival time. QoS on the network (prioritising voice) is the usual fix.

## Packet loss

- **TCP** detects loss and **retransmits**, so the data arrives, but each loss costs at least one RTT and congestion control **cuts the sending rate**. A few percent loss can reduce a transfer's throughput many times over and produce sudden multi-second stalls that hit your read timeout.
- **UDP** applications get no help. SNMP polls simply go unanswered (the manager retries and times out); SNMP traps and syslog messages are **lost**; DNS queries are retried by the resolver.

Design responses: set realistic **timeouts** and **retry** idempotent requests with **exponential backoff and jitter** (randomised waits so many clients do not retry in lockstep); prefer acknowledged mechanisms where loss matters (SNMP informs rather than traps, TCP or TLS syslog, model-driven telemetry over TCP).

## MTU

Ethernet carries up to **1,500 bytes** of IP packet; after a 20-byte IPv4 header and a 20-byte TCP header that leaves a 1,460-byte TCP payload (the **MSS**). Tunnels (IPsec, GRE, VXLAN, VPN clients) add headers, so less fits. IPv4 routers can fragment packets unless the Don't Fragment bit is set; IPv6 routers never fragment (only the source does), and every IPv6 link must carry at least 1,280 bytes (RFC 8200).

Path MTU discovery (RFC 1191 for IPv4, RFC 8201 for IPv6) relies on ICMP messages ("fragmentation needed", "packet too big") telling the sender to send smaller packets. If a firewall blocks them, you get a **PMTUD black hole**: the TCP handshake and small requests work, but full-size packets vanish, so large responses hang until a `ReadTimeout`. It looks like an application bug and is not. Fixes are on the network: permit those ICMP types, clamp the TCP MSS on the tunnel, or set a lower MTU (lesson 6.8).

## API design choices that follow

| Choice | Helps with | How |
|---|---|---|
| **Pagination** | Bandwidth, timeouts, memory | Fetch in pages (`perPage`/`limit` and `offset`, a cursor, or a `Link: rel="next"` header; Domain 2) so no single response is huge |
| **Compression** | Bandwidth | `Accept-Encoding: gzip`; servers compress JSON |
| **Filtering and field selection** | Bandwidth | Let the server send only what you asked for |
| **Bulk or batch endpoints** | Latency, chattiness | One call does many operations (for example Meraki action batches) |
| **Keep-alive and connection reuse** | Latency | A `requests.Session` reuses TCP and TLS connections automatically |
| **Timeouts** | Loss, outages | `timeout=(connect, read)`; `requests` has none by default |
| **Retries with backoff** | Loss, transient errors, rate limits | Retry idempotent methods; honour `Retry-After` on `429` and `503` |
| **Asynchronous jobs and webhooks** | Latency, long operations | Submit, get a task ID, poll or receive a callback instead of holding one request open |
| **Caching** | Latency, bandwidth | Keep data that rarely changes (inventory, site lists) locally; use `ETag` where supported |

A client that applies several of these:

```python
import requests
from requests.adapters import HTTPAdapter
from urllib3.util.retry import Retry

retry = Retry(
    total=5,
    backoff_factor=1,                       # sleeps grow as 1 x 2**(n-1) seconds
    backoff_jitter=0.5,                     # plus up to 0.5 s random
    status_forcelist=[429, 500, 502, 503, 504],
    allowed_methods={"GET", "PUT", "DELETE"},   # idempotent only, never POST
)                                           # Retry-After is honoured by default

session = requests.Session()                # keep-alive: connections are reused
session.mount("https://", HTTPAdapter(max_retries=retry))
session.headers["Authorization"] = "Bearer <YOUR_API_TOKEN>"

url = "https://api.example.com/api/v1/devices?perPage=500"
devices = []
while url:
    r = session.get(url, timeout=(5, 30))   # 5 s to connect, 30 s between bytes
    r.raise_for_status()
    devices.extend(r.json())
    url = r.links.get("next", {}).get("url")    # follow Link: <...>; rel="next"
print(len(devices))
```

In urllib3 2.x the backoff for the *n*th consecutive retry is `backoff_factor × 2^(n−1)` seconds, with no sleep before the first retry and a cap of `backoff_max` (120 s by default). The read timeout is the longest wait **between** bytes, not for the whole response.

> **Exam tip:** Match the constraint to the fix: high latency → fewer round trips (bulk calls, keep-alive, concurrency); low bandwidth → pagination, filtering, compression; loss → timeouts and retries with backoff; MTU → a network fix, not a code fix; jitter → QoS and buffering for real-time traffic.

## Lab it yourself

1. Measure latency to your gateway. Windows: `ping -n 10 <your-gateway>`; macOS and Linux: `ping -c 10 <your-gateway>`. The spread between minimum and maximum is a rough view of jitter.
2. See your MTU. Windows: `netsh interface ipv4 show subinterfaces`. macOS: `ifconfig en0 | grep mtu`. Linux: `ip link`. On a VPN, compare the tunnel interface's MTU with the physical one.
3. Feel the cost of round trips without any network: in Python, simulate 500 calls with `time.sleep(0.08)` in a loop, then the same with `concurrent.futures.ThreadPoolExecutor(max_workers=20)`, and compare total times.
4. Against the DevNet Meraki or Catalyst Center sandbox, time a loop of single calls with plain `requests.get` versus a `Session`, then read the API's pagination section and fetch a list in pages.

## Key takeaways

- Bandwidth limits volume; latency adds a cost to every round trip; jitter varies delay; loss forces retransmission or loses UDP data; MTU limits packet size, especially in tunnels.
- Round trips, not bytes, dominate most API automation: use bulk endpoints, keep-alive sessions and concurrency.
- Pagination, filtering and compression handle large datasets on limited links.
- Always set timeouts; retry only idempotent requests, with exponential backoff, jitter and respect for `Retry-After`.
- An MTU black hole lets small requests through and stalls large ones; the fix is in the network (ICMP, MSS clamping), not in the code.
