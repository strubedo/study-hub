## Three jobs inside every network device

A router or switch does three different kinds of work, and topic 6.5 asks you to describe each. The split matters to an automation engineer because your scripts, controllers and APIs live on one plane, the routing protocols they configure live on another, and the user traffic you are trying to influence lives on the third.

| Plane | Question it answers | Examples | Where it runs |
|---|---|---|---|
| **Management** | How do people and systems configure and monitor this device? | SSH, Telnet, HTTPS GUI, NETCONF, RESTCONF, gNMI, SNMP, syslog, NTP, AAA (TACACS+, RADIUS) | Device CPU |
| **Control** | Where should traffic go? | OSPF, EIGRP, BGP, IS-IS, STP, LACP, CDP and LLDP, ARP, IPv6 ND, building the routing table | Device CPU |
| **Data** (forwarding) | Move this packet now | Forwarding by FIB lookup, MAC table lookup, applying ACLs, NAT, QoS, encryption | Hardware (ASICs) or a fast software path |

## Data plane

The **data plane** forwards transit traffic: packets that arrive on one interface and leave by another. For each packet it looks up the destination in the forwarding table (the **FIB**, built by Cisco Express Forwarding from the routing table) or the MAC table, rewrites the Layer 2 header, and sends it out. Features applied per packet, such as ACLs, NAT, QoS marking and queuing, and IPsec encryption, are data-plane functions.

On switches and most routers the data plane is in hardware so it runs at line rate. Your application's traffic, an HTTPS request from a client to a server through the device, is **data-plane** traffic.

## Control plane

The **control plane** decides where traffic should go. It runs the routing protocols that exchange reachability with neighbours, chooses the best paths, and fills the routing table (RIB), which is then programmed into the FIB for the data plane. Layer 2 control protocols, such as spanning tree preventing loops, LACP building port channels, and CDP or LLDP discovering neighbours, also belong here. ARP and IPv6 neighbour discovery resolve next-hop MAC addresses for the forwarding tables.

Control-plane packets are addressed **to** the device or are protocol multicasts it must process, so they are sent ("punted") to the CPU.

## Management plane

The **management plane** is how the device is configured, monitored and operated:

- **Configuration and operation:** SSH and Telnet CLI, HTTPS web UI, and the programmable interfaces: **NETCONF** (TCP 830 over SSH), **RESTCONF** (HTTPS), **gNMI** (gRPC).
- **Monitoring:** SNMP polling and traps, syslog, streaming telemetry, NetFlow export configuration.
- **Supporting services:** NTP for accurate timestamps, AAA for logins, DNS for resolving names in commands.

Every Domain 3 topic, from the IOS XE APIs to Catalyst Center, Meraki and NSO, works on the management plane: a controller or script logs in over SSH, NETCONF or HTTPS and reads or writes configuration. The configuration then changes how the control plane behaves (a new OSPF network statement) or how the data plane forwards (a new ACL).

```text
 your script / controller --NETCONF, RESTCONF, SSH, SNMP-->  [ management plane ]
                                                                     | writes config
                                                                     v
 OSPF / BGP neighbours <--routing protocol packets-->         [ control plane ]
                                                                     | programs RIB -> FIB
                                                                     v
 user traffic in  ==================================>         [ data plane ]  ====> out
```

## Controllers and planes

In traditional networks each device runs all three planes itself. **Software-defined networking** moves some of this into controllers:

- Most controllers you will automate (**Catalyst Center**, formerly DNA Center; **Meraki** dashboard) are **centralised management**: they push configuration and collect telemetry, while each device still runs its own control plane (OSPF, STP).
- **Cisco Catalyst SD-WAN** separates them explicitly: **SD-WAN Manager** (formerly vManage) is the management plane, the **SD-WAN Controller** (formerly vSmart) is a centralised control plane that distributes routes and policy with OMP, the **SD-WAN Validator** (formerly vBond) handles orchestration and authentication, and the **WAN Edge** routers are the data plane.
- **Cisco ACI**: the APIC controller is the management and policy point; the leaf and spine switches run the control and data planes.

So an API call to a controller is a management-plane action, even when its effect is to change control-plane behaviour across hundreds of devices.

## Why the planes matter when automating

- **Separate paths.** Many networks give the management plane its own network (out-of-band management, a management VRF or a dedicated management port, which on Catalyst 9000 switches is `GigabitEthernet0/0` in the `Mgmt-vrf` VRF). Your automation host must reach that network, which may not be the one user traffic uses.
- **Protecting the CPU.** Control and management traffic share the device CPU. **Control Plane Policing (CoPP)** rate-limits traffic punted to the CPU so a flood cannot starve routing protocols. A strict CoPP or management ACL can also slow or drop your SSH, SNMP or NETCONF sessions; if a script gets timeouts only when it polls many devices quickly, CoPP is one thing to check. (CoPP configuration is beyond this exam; know that it exists and what it protects.)
- **Failure domains.** A data-plane failure (a bad ACL) drops user traffic while management still works. A control-plane failure (a lost OSPF neighbour) removes routes. A management-plane failure (NETCONF disabled, wrong AAA) stops your automation while traffic still flows. Telling these apart is the first step in troubleshooting.

> **Exam tip:** Match by purpose. Configuring, monitoring, logging in: **management**. Exchanging routes, building tables, loop prevention: **control**. Forwarding the packet, applying ACL, NAT and QoS to it: **data**.

## Lab it yourself

1. In the always-on IOS XE sandbox on DevNet, connect over SSH (management plane), run `show ip protocols` and `show ip route` (control-plane results) and `show ip cef` (the data plane's forwarding table). Compare the route and CEF entries for the same prefix.
2. Still on the sandbox, run `show running-config | include netconf|restconf|ip http|snmp` to see which management-plane interfaces are enabled.
3. From your computer, check that the management plane is reachable on the NETCONF port without opening a session: on Windows PowerShell `Test-NetConnection <sandbox-host> -Port 830`; on macOS or Linux `nc -vz <sandbox-host> 830`. Use the host name the sandbox page gives you.

## Key takeaways

- Management plane: configure and monitor (SSH, NETCONF, RESTCONF, gNMI, SNMP, syslog, NTP, AAA). APIs and controllers live here.
- Control plane: decide paths (OSPF, BGP, EIGRP, STP, LACP, CDP/LLDP, ARP) and build the RIB that programs the FIB.
- Data plane: forward transit packets and apply ACLs, NAT, QoS and encryption, usually in hardware.
- Catalyst SD-WAN maps cleanly: SD-WAN Manager = management, SD-WAN Controller = control, WAN Edge = data, SD-WAN Validator = orchestration.
- CoPP protects the CPU that runs the control and management planes; it can also throttle aggressive automation.
