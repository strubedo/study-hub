## The error message is your first clue

Topic 6.8 asks you to **diagnose** application connectivity problems caused by four things: **NAT**, a **blocked transport port**, a **proxy** and a **VPN**. The skill is reading the symptom precisely. A timeout, a refusal, a certificate error and a `407` each point to a different layer, and Python `requests` tells you which one you hit if you read the exception class and its last line.

## A layered method

Work up the stack and stop at the first layer that fails:

1. **Read the exact error.** Exception class, the "Caused by" part, the HTTP status code. Do not paraphrase it.
2. **Name resolution.** Does the name resolve, and to the address you expect? Windows: `nslookup api.example.com` or `Resolve-DnsName api.example.com`; macOS and Linux: `dig api.example.com`.
3. **Route and path.** Which interface and gateway does the traffic use, and is a VPN involved? Windows: `route print`, `tracert -d`; macOS: `netstat -rn`, `route get <ip>`; Linux: `ip route get <ip>`, `traceroute -n`.
4. **Transport.** Can a TCP connection be opened to the port? Windows PowerShell: `Test-NetConnection api.example.com -Port 443`; macOS and Linux: `nc -vz api.example.com 443`. Note whether it **times out** or is **refused**.
5. **Proxy.** Are `HTTP_PROXY`, `HTTPS_PROXY` or `NO_PROXY` set, and should this destination go through the proxy or bypass it?
6. **TLS.** Who issued the certificate the client receives? `curl -v https://api.example.com/` prints the subject and issuer.
7. **HTTP and application.** Status codes such as `401`, `403`, `407`, `502` and the response body (Domain 2).

## What each failure looks like from Python

`requests` wraps the low-level error. The last line of each traceback (urllib3 2.x wording; host and path are the same in each case):

| Symptom (last line) | What happened on the network | Likely cause |
|---|---|---|
| `ConnectTimeout: ... (Caused by ConnectTimeoutError(..., 'Connection to api.example.com timed out. (connect timeout=5)'))` | SYNs sent, nothing came back | A firewall **dropping** the port, no route back, wrong address, asymmetric path, or a proxy that must be used |
| `ConnectionError: ... (Caused by NewConnectionError("...: Failed to establish a new connection: [Errno 111] Connection refused"))` | A TCP **RST** came back | Host reachable but **nothing listening** on that port, or a firewall **rejecting** with a reset |
| `ConnectionError: ... (Caused by NameResolutionError("...: Failed to resolve 'api.example.com' ([Errno -2] Name or service not known)"))` | DNS gave no address | Wrong or unreachable DNS server, internal name looked up on public DNS (VPN) |
| `SSLError: ... (Caused by SSLError(SSLCertVerificationError(1, '[SSL: CERTIFICATE_VERIFY_FAILED] certificate verify failed: self-signed certificate in certificate chain ...')))` | TCP worked; the certificate did not verify | **TLS inspection** by a proxy or firewall, a self-signed device certificate, or a wrong clock |
| `ProxyError: ... (Caused by ProxyError('Unable to connect to proxy', OSError('Tunnel connection failed: 407 Proxy Authentication Required')))` | The proxy refused the CONNECT | Proxy needs credentials |
| `ConnectionError: ('Connection aborted.', ConnectionResetError(104, 'Connection reset by peer'))` | Connected, then reset | An IPS or firewall killing the session, a server or load balancer closing it |
| `ReadTimeout: HTTPSConnectionPool(host='api.example.com', port=443): Read timed out. (read timeout=10)` | Connected and sent; no response in time | Slow server, or large responses lost to an **MTU** problem |

Errno values are from Linux. Windows reports a refusal as `[WinError 10061] No connection could be made because the target machine actively refused it` and a lookup failure as `[Errno 11001] getaddrinfo failed`. In the class hierarchy, `ConnectTimeout`, `SSLError` and `ProxyError` are all subclasses of `ConnectionError`, so catch the specific ones first.

> **Watch out:** `requests` has **no default timeout**. Without `timeout=`, a dropped SYN waits for the operating system's own connect timeout (often 20 seconds to over two minutes), and a stalled response can hang forever. Always pass `timeout=(connect, read)`.

## Transport port blocked

The decisive question is **timeout or refused**.

- **Closed port.** The host is up but no process listens. RFC 9293: a segment arriving for a connection that does not exist (no RST in it) is answered with a **reset**. The client fails **immediately** with "connection refused".
- **Firewall drop** (deny silently). The SYN disappears; the client retransmits and eventually reports a **timeout**. Most perimeter firewalls drop by default because it reveals less.
- **Firewall reject.** The firewall answers on the server's behalf with a TCP reset (looks like "refused") or an ICMP destination-unreachable, administratively prohibited (Linux reports `No route to host`). Fast failure, but the server never saw the packet.

```text
Firewall fw01, rules evaluated top to bottom:
 10  permit tcp 10.1.10.0/24 -> 10.30.0.10   eq 443
 20  reject tcp 10.1.10.0/24 -> 10.30.0.10   eq 22     (send TCP reset)
 30  deny   ip  any          -> any                    (drop, log)
```

From 10.1.10.25: TCP 443 connects; TCP 22 is refused at once by the firewall even if sshd is running; TCP 830 times out because rule 30 drops it. The fix for NETCONF is a rule for TCP 830, not a change on the switch.

## NAT problems

NAT failures look like routing or firewall problems unless you think about which address each end sees.

- **The server sees a different source address.** Behind PAT, every client appears as the NAT address. An API with a source allow-list returns `403` (or the firewall in front of it drops you) because your request arrives from `203.0.113.2`, not `10.1.10.25`. Add the translated address to the allow-list.
- **The server returns an address you cannot reach.** An application behind static NAT puts its internal address in a redirect or a link (`Location: https://10.30.0.10/login`); the outside client follows it and times out. Configure the application's external URL or have the proxy rewrite it.
- **No inbound mapping.** A webhook (Domain 2) from a cloud service to `10.1.10.25:5000` cannot work: the address is private and PAT creates mappings only for outbound flows. Use a static NAT or port forward, a public reverse proxy, or a tunnelling service.
- **Asymmetric path.** The request leaves through firewall A but the reply returns through router B (or firewall B). A stateful firewall that sees only half the conversation drops it, and NAT translated on A cannot be reversed on B. The symptom is a **timeout** on connect, often only for some subnets. Fix the routing so both directions use the same stateful device.
- **Hairpin.** An inside client resolves `shop.example.com` to the public static NAT address `203.0.113.5` of a server that is also inside. The packet goes to the firewall, which must translate it and send it back out the interface it came in on. Many devices do not do that "U-turn" by default, so the inside client times out while outside users are fine. Fix with split DNS (internal answer is the real address) or hairpin NAT.
- **Port exhaustion.** Thousands of short connections through one PAT address can run out of source ports; new connections fail intermittently. Reuse connections with a `requests.Session`.

## Proxy problems

Many enterprises send outbound web traffic through an **explicit forward proxy**. For HTTPS the client sends `CONNECT api.example.com:443` to the proxy, then runs TLS through the tunnel.

- **Settings.** `requests` reads `http_proxy`, `https_proxy`, `no_proxy` and `all_proxy` in lowercase or uppercase. curl reads the same variables, except that the HTTP one must be lowercase `http_proxy`. A browser using the operating system's proxy or a PAC file works, while a script with no proxy variables tries to connect directly and **times out** at the firewall.
- **Bypass list.** With a proxy set, requests to internal devices go to the proxy too, which usually cannot reach `sw01.corp.example.com` and answers `502` or `403`. Add internal domains to `NO_PROXY` (for example `NO_PROXY=.corp.example.com,10.0.0.0/8`), not a parent domain that also holds the external APIs you reach through the proxy. In `requests`, CIDR entries only match when the URL contains an IP address, not a name.
- **407 Proxy Authentication Required** (RFC 9110). The proxy wants credentials; its response carries `Proxy-Authenticate` and the client must send `Proxy-Authorization`. For an HTTPS URL, `requests` raises `ProxyError` (the CONNECT failed); for a plain HTTP URL you simply get a response with status 407.
- **TLS inspection.** A proxy or NGFW that decrypts traffic presents **its own certificate**, issued on the fly by the company's inspection CA. Browsers trust it because IT installed that CA in the operating system store. `requests` uses the `certifi` bundle by default, not the OS store, so it raises `SSLError: CERTIFICATE_VERIFY_FAILED`. Fix by pointing `verify=` or `REQUESTS_CA_BUNDLE` at a file that includes the corporate CA, or by having the destination exempted from inspection. `verify=False` is not a fix.

```text
$ curl -v https://api.example.com/v1/status
* Uses proxy env variable HTTPS_PROXY == 'http://proxy.example.com:3128'
...
> CONNECT api.example.com:443 HTTP/1.1
> Host: api.example.com:443
>
< HTTP/1.1 407 Proxy Authentication Required
< Proxy-Authenticate: Basic realm="corp-proxy"
...
* CONNECT tunnel failed, response 407
```

## VPN problems

- **Split tunnel vs full tunnel.** With **split tunnelling**, only the prefixes the VPN pushes (for example `10.0.0.0/8`) go through the tunnel and everything else uses the local internet connection. With a **full tunnel**, everything goes through the VPN (`0.0.0.0/0`). A lab subnet missing from the split list (say `172.20.0.0/16`) leaves the client's routing table pointing at the home router, and the connection times out. Check with `route print` or `ip route get 172.20.1.10`.
- **Overlapping subnets.** The home LAN is `192.168.1.0/24` and so is a remote site. The client's connected route for its own LAN is used instead of the tunnel, so the remote devices are unreachable (or the wrong local device answers). Renumber, or have the VPN push more specific routes or use NAT.
- **MTU and fragmentation.** Tunnel headers (IPsec, GRE, TLS-based VPNs) reduce the payload that fits in a 1,500-byte link. Path MTU discovery (RFC 1191 for IPv4, RFC 8201 for IPv6) needs ICMP "fragmentation needed" or "packet too big" messages to reach the sender. When a firewall blocks them, the **handshake and small requests succeed but large responses never arrive**: SSH logs in, then `show running-config` or a big `GET` hangs and ends in a `ReadTimeout`. Fixes: allow the ICMP messages, clamp the TCP MSS on the tunnel (`ip tcp adjust-mss 1360` on IOS), or lower the MTU.
- **DNS not following the tunnel.** The tunnel carries `10.0.0.0/8`, but the client still uses the home router's DNS, which has never heard of `sw01.corp.example.com`. Result: `NameResolutionError`, even though `ping 10.30.0.10` works. The VPN must push its DNS servers or a split-DNS rule for the internal domain.

## Symptom to cause, at a glance

| Clue | First suspect |
|---|---|
| Immediate "connection refused" | Nothing listening, or a firewall reject |
| Connect timeout, other ports to the same host work | Firewall dropping that port |
| Connect timeout to everything at one site, through VPN | Missing split-tunnel route, overlapping subnet, asymmetric path |
| Works by IP, fails by name only on VPN | VPN DNS |
| `SSLError` only on the corporate network, browser fine | TLS inspection CA missing from the Python bundle |
| `407` or `ProxyError` | Proxy credentials or proxy settings |
| Small calls fine, large responses hang | MTU / PMTUD black hole |
| `403` from an API that allow-lists sources | Source NAT changed your address |
| Inside users fail to reach a server's public name, outside users fine | Hairpin NAT |

## Lab it yourself

1. Print your proxy settings. Windows: `netsh winhttp show proxy` and `Get-ChildItem Env: | Where-Object Name -like '*proxy*'` (PowerShell). macOS: `scutil --proxy` and `env | grep -i proxy`. Linux: `env | grep -i proxy`.
2. See a refusal: start a tiny local server with `python -m http.server 8000`, then run `python -c "import requests; requests.get('http://127.0.0.1:8001', timeout=3)"` and read the `Connection refused` (or `WinError 10061`) line. Then request port 8000 and see it succeed. Stop the server with Ctrl+C.
3. Practise reading certificates: `curl.exe -v https://example.com/ -o NUL` (Windows; type `curl.exe`, because `curl` in Windows PowerShell 5.1 is an alias for `Invoke-WebRequest`) or `curl -v https://example.com/ -o /dev/null` (macOS and Linux) and find the `issuer:` line. On a network with TLS inspection, the issuer is your company's CA.
4. If you use a VPN, compare `route print` / `netstat -rn` / `ip route` before and after connecting to see which prefixes it adds (split) or whether it replaces the default route (full).

## Key takeaways

- Read the exception: `ConnectTimeout` = silence (drop, routing, missing proxy); `Connection refused` = RST (closed port or reject); `NameResolutionError` = DNS; `SSLError` = certificate or TLS inspection; `ProxyError` 407 = proxy credentials.
- A filtered port times out; a closed port returns a TCP reset; a firewall reject looks like a refusal although the server never saw the packet.
- NAT faults: wrong source address at the server, internal addresses leaked in responses, no inbound mapping, asymmetric return paths, missing hairpin.
- Proxy faults: missing `HTTPS_PROXY`, missing `NO_PROXY` for internal hosts, `407`, and TLS inspection presenting the proxy's certificate.
- VPN faults: split-tunnel lists, overlapping subnets, MTU black holes and DNS not following the tunnel.
- Always set `timeout=` in `requests`; it has none by default.
