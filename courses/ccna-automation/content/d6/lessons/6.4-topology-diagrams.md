## Why a topology diagram matters to a developer

Topic 6.4 asks you to **interpret** a basic topology diagram: switches, routers, firewalls, load balancers and port values. On the exam you will get a drawing and a question such as "which device translates the address?", "which port must be open on the firewall?" or "why can the application reach one server but not another?". The skill is to read the diagram as a set of decisions along a path, not as a picture.

## A reading method

Use the same five steps on any diagram:

1. **Identify each device and its role.** Switch (Layer 2, VLANs), Layer 3 switch or router (routes between subnets), firewall (policy, often NAT), load balancer (VIP in front of a pool). Note the interface names and addresses on each.
2. **Write down the subnets.** For each link or VLAN, work out the prefix from the address and mask (lesson 6.2). Two addresses in the same subnet talk directly; anything else goes through a gateway.
3. **Trace the path** for the flow in the question, hop by hop, from the source's default gateway onward. At each hop ask: what decides here, and with what information?
4. **Read the labels.** Port values (`tcp/443`, `:8443`), VLAN labels (`access vlan 20`, `trunk allowed 10,20`, `native 99`), and notes such as "PAT", "static NAT", "VIP" or "health check".
5. **Find where addresses change and where filtering happens.** NAT changes IP addresses (usually at the firewall or edge router); a load balancer changes the destination to a pool member and often the source to itself; a firewall or ACL can stop the flow. Everything else keeps the IP addresses and only rewrites Layer 2.

## Worked example

```text
                              Internet
                                 |
                        ISP router 203.0.113.1
                                 |
            outside 203.0.113.2/29
     +------------------------------+   NAT: inside users -> PAT to 203.0.113.2
     |  fw01  (stateful firewall)   |   NAT: static 203.0.113.5 <-> 172.16.50.10
     +------------------------------+
       inside 10.0.1.1/30     dmz 172.16.50.1/24
            |                        |
            |                  +-------------------------------+
            |                  | lb01  VIP 172.16.50.10 tcp/443 |  TLS terminated here
            |                  | SNAT to 172.16.50.5            |  health check GET /health
            |                  +-------------------------------+
            |                        |  pool tcp/8443
            |              +---------+---------+
            |           web01 172.16.50.21  web02 172.16.50.22
            |
     Gi1/0/1 10.0.1.2/30
     +------------------------------+
     |  core01  (Layer 3 switch)    |   SVI Vlan10 10.1.10.1/24 (users)
     |  default route -> 10.0.1.1   |   SVI Vlan20 10.1.20.1/24 (servers)
     +------------------------------+
       Gi1/0/48 trunk: allowed 10,20  native 99
            |
     +------------------------------+
     |  acc01  (access switch)      |
     +------------------------------+
       Gi1/0/5  access vlan 10 -- dev-pc   10.1.10.25/24  gw 10.1.10.1
       Gi1/0/12 access vlan 20 -- inv-api  10.1.20.30/24  gw 10.1.20.1  listens tcp/5000
```

### Step 1 and 2: devices and subnets

| Device | Role | Subnets it touches |
|---|---|---|
| acc01 | Layer 2 access switch | VLAN 10 and 20 (no IP routing) |
| core01 | Layer 3 switch, gateway for both VLANs | 10.1.10.0/24, 10.1.20.0/24, 10.0.1.0/30 |
| fw01 | Stateful firewall and NAT | 10.0.1.0/30, 172.16.50.0/24, 203.0.113.0/29 |
| lb01 | Load balancer in the DMZ | 172.16.50.0/24 |

### Step 3 to 5: three flows

**dev-pc calls an internet API on tcp/443.**
dev-pc (VLAN 10) sees the destination is not in 10.1.10.0/24 and sends the frame to its gateway's MAC. acc01 carries it, tagged VLAN 10, over the trunk to core01. core01 routes it with its default route to fw01 inside (10.0.1.1). fw01 checks its rule base, creates a session, and **PATs** the source to 203.0.113.2 with a new source port. The ISP router forwards it. The reply comes back to 203.0.113.2, matches the session, is translated back to 10.1.10.25 and returned. Address changes: one, at fw01. Filtering: fw01.

**A customer opens `https://shop.example.com` (A record 203.0.113.5).**
The packet arrives at fw01 outside with destination 203.0.113.5:443. fw01's **static NAT** changes the destination to 172.16.50.10 and a rule must permit tcp/443 to it. lb01 terminates TLS on the VIP, picks a healthy pool member, and opens a new connection to web01 **on tcp/8443** with source 172.16.50.5 (its SNAT address). So: the firewall rule is for **443**, the web servers listen on **8443**, and web01's logs show **172.16.50.5** as the client unless lb01 adds `X-Forwarded-For`. Address changes: two (fw01 destination NAT, lb01 destination and source).

**dev-pc calls inv-api on tcp/5000.**
Both are inside, in different VLANs. core01 routes between its two SVIs directly. The flow **never reaches fw01**, so no firewall rule applies to it and no NAT happens. If it fails, look at core01 (an ACL on an SVI), the host firewall on inv-api, or whether the service is listening.

> **Exam tip:** A diagram question often hinges on one label. "Pool tcp/8443" behind a VIP on tcp/443 means the firewall needs 443 to the VIP, not 8443 to the servers. "Native 99" on a trunk means untagged frames land in VLAN 99. "PAT" on a firewall means many inside hosts share one public address with different source ports.

## Common symbols and labels

Exam diagrams use Cisco icons: a **switch** is a box with arrows, a **router** a round cylinder with arrows, a **firewall** a brick wall, a **load balancer** a box with branching arrows, the internet or WAN a cloud. Text diagrams like the one above say the role in words. Labels you should be able to read at a glance:

| Label | Meaning |
|---|---|
| `Gi1/0/48`, `Gi0/0`, `Eth1/1` | Interface names (Cisco GigabitEthernet, Ethernet) |
| `10.1.10.1/24` on an SVI or interface | The device's address; with the prefix it gives the subnet |
| `access vlan 10` / `trunk allowed 10,20` | Port mode and VLANs (lesson 6.1) |
| `tcp/443`, `:8443`, `udp/161` | Transport protocol and port (lesson 6.7) |
| `VIP` | Virtual IP of a load balancer |
| `PAT`, `static NAT`, `SNAT` | Where and how addresses are translated |
| `gw 10.1.10.1` | A host's default gateway |

## Checks that catch mistakes

- **Is each host's gateway in its own subnet?** A gateway of 10.1.20.1 on a 10.1.10.0/24 host is a misconfiguration.
- **Do both ends of a trunk agree** on allowed VLANs and native VLAN?
- **Does the port in the firewall rule match the port the client uses** (the VIP or public port), not the internal one?
- **Is there a return path?** With NAT or a load balancer doing SNAT, replies come back to the translated address; without it, the server must route replies back through the same firewall (lesson 6.8, asymmetric routing).

## Lab it yourself

1. Copy the diagram above into a text file and annotate each hop for a fourth flow: web01 downloading an update from the internet. Which NAT applies? (fw01 needs a rule and a NAT for DMZ-to-outside traffic; the diagram does not show one, which is exactly the kind of gap an exam question tests.)
2. Draw your own home or lab network the same way: your computer, the home router (which is a switch, router, firewall, NAT device and DHCP server in one box), the ISP. Find your gateway with `ipconfig` (Windows) or `ip route` / `netstat -rn` (Linux and macOS).
3. In the DevNet Sandbox catalogue, open the topology of a Catalyst Center or SD-WAN sandbox and list each device, its role and its management address.

## Key takeaways

- Read a diagram in five steps: roles, subnets, path, labels, where addresses change and where filtering happens.
- Only NAT devices and load balancers change IP addresses; switches and routers do not.
- A VIP port and a pool port can differ; firewall rules follow the address and port the packet has when it reaches the firewall.
- Inter-VLAN traffic routed on a Layer 3 switch does not cross a firewall that sits elsewhere.
- Check gateways, trunk VLAN labels and the return path; missing pieces in a diagram are often the answer.
