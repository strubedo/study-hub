## Four boxes, four jobs

Topic 6.3 asks you to describe what **switches**, **routers**, **firewalls** and **load balancers** do. The exam stays at the level of "which device makes which decision, using what information". For an automation engineer the useful question is: when my request fails, which of these devices could have caused it, and which API or CLI would show me?

| Device | Layer it decides at | Decides using | Main table |
|---|---|---|---|
| Switch | 2 (data link) | Destination MAC within a VLAN | MAC address table |
| Router | 3 (network) | Destination IP prefix | Routing table (RIB) and forwarding table (FIB) |
| Firewall | 3 and 4, and up to 7 for next-generation | Source and destination address, protocol, port, connection state, application, user | Rule base and session (state) table |
| Load balancer | 4 or 7 | Virtual IP and port, then a balancing method and health of pool members | Pool members, health status, persistence table |

## Switches

A **switch** connects hosts in the same LAN. It learns which MAC address is behind which port and forwards frames only where they need to go, flooding when it does not know (lesson 6.1). It separates traffic into **VLANs**, each a broadcast domain, and connects to other switches with **trunks**.

- Every port is its own collision domain and runs full duplex; the old shared-hub problems are gone.
- A **Layer 3 switch** also routes between VLANs in hardware using SVIs. In a campus, the "router" between user VLANs is usually the distribution or core switch.
- What it shows an automation engineer: interface status, errors and counters, VLAN membership, the MAC table (which port a device is on), and neighbor data from CDP or LLDP. Those are common API reads.

## Routers

A **router** connects different IP networks and forwards packets between them by **destination IP address**, using **longest prefix match** against its routing table (lesson 6.2). It:

- separates broadcast domains (it does not forward broadcasts);
- rewrites the Layer 2 header at each hop and decrements the TTL;
- learns routes statically or with routing protocols (OSPF, EIGRP, BGP);
- often also performs **NAT**, terminates **VPNs**, applies **ACLs** and **QoS**, and provides DHCP relay or other IP services (lesson 6.6).

## Firewalls

A **firewall** enforces security policy between zones (inside, outside, DMZ, data centre segments) by permitting or denying flows.

### Stateless packet filters

A stateless filter, such as a classic router ACL, evaluates **each packet on its own** against an ordered rule list (first match wins, with an implicit deny at the end on Cisco IOS ACLs). It has no memory of connections, so return traffic needs its own rule. Rules such as Cisco's `established` keyword only check whether the TCP ACK or RST bit is set, which an attacker can forge.

### Stateful firewalls

A **stateful** firewall keeps a **session (connection) table**. When an allowed packet opens a connection (for TCP, a SYN that matches a rule), the firewall records the 5-tuple (source IP, destination IP, protocol, source port, destination port) and automatically permits **return traffic** for that session. Packets that do not belong to a known session and do not match a rule are dropped. This is the default behaviour of Cisco Secure Firewall, FortiGate, Palo Alto and cloud security groups.

| | Stateless filter | Stateful firewall |
|---|---|---|
| Unit of decision | Each packet | Each connection, then its packets |
| Return traffic | Needs an explicit rule | Allowed automatically for known sessions |
| Memory | None | Session table with timeouts |
| Typical place | Router ACLs, simple edge filtering | Perimeter and internal segmentation |

### Next-generation firewalls

A **next-generation firewall (NGFW)** is stateful and adds:

- **Application identification**: policy by application (for example "allow Webex, block file sharing") rather than only by port.
- **User identity**: rules for groups learned from a directory or identity service.
- **Intrusion prevention (IPS)**, **URL filtering** and malware inspection.
- **TLS decryption**, which lets it inspect encrypted traffic but makes clients see the firewall's certificate (lesson 6.8).

Cisco Secure Firewall (Firepower Threat Defense, managed by Secure Firewall Management Center) is Cisco's NGFW; the ASA is its classic stateful firewall.

> **Real world:** A firewall that **drops** a blocked packet gives your client nothing, so the connection attempt times out. One that **rejects** sends a TCP reset or an ICMP unreachable, so the client fails at once. Lesson 6.8 shows how each looks from Python.

## Load balancers

A **load balancer** presents one **virtual IP (VIP)** and port to clients and spreads requests across a **pool** of servers, removing failed servers with **health checks**. Layer 4 load balancers forward TCP or UDP connections; Layer 7 load balancers understand HTTP and can route by host name or path, terminate TLS and add headers such as `X-Forwarded-For`. Lesson 4.9 covers load-balancing methods, health checks and the reverse-proxy role in detail; for topic 6.3, remember the job: **scale out and high availability behind one address**.

What a developer notices:

- The server sees the load balancer's address as the source unless the load balancer passes the client address in a header, or preserves it at Layer 4.
- **Persistence** ("sticky sessions") matters if the application keeps session state on one server.
- A health check that only tests "port open" can keep sending traffic to an application that is up but broken.

## Putting them in a path

```text
client 10.1.10.25 -- [access switch] -- [L3 core switch] -- [router] -- [firewall] -- [load balancer VIP] -- web servers
          L2: VLAN 10        routes between VLANs   routes to WAN   permits tcp/443   picks a healthy server
```

When an API call fails, walk this path: the switch decides by MAC within a VLAN, the router by destination prefix, the firewall by rule and state, the load balancer by VIP and pool health.

## Lab it yourself

1. On any computer, show the path your traffic takes to a documentation address without sending data to a real service: run `tracert -d -h 3 192.0.2.1` (Windows) or `traceroute -n -m 3 192.0.2.1` (macOS and Linux). The first hop is your default gateway, which is a router (often your home router or a Layer 3 switch). The remaining hops usually time out because 192.0.2.0/24 is not routed; that is expected.
2. Read a Catalyst or Meraki API reference on DevNet and list which calls return switch data (ports, VLANs, MAC or client tables), router data (routes), and firewall data (rules). Notice that each device type exposes the table it decides with.
3. In the free DevNet Sandbox (a Catalyst 8000V or IOS XE always-on instance), run `show ip route` and `show mac address-table` (on a switch image) and match each output to the device role it represents.

## Key takeaways

- Switches forward frames by destination MAC within a VLAN and flood unknown unicast; Layer 3 switches also route between VLANs.
- Routers forward packets between networks by longest prefix match, separate broadcast domains and often do NAT, VPN and ACLs.
- Stateless filters judge each packet alone and need return-traffic rules; stateful firewalls track sessions and allow return traffic automatically.
- Next-generation firewalls add application and user awareness, IPS, URL filtering and TLS decryption.
- Load balancers expose a VIP, spread requests over a pool and use health checks; see lesson 4.9 for methods and reverse proxies.
- When troubleshooting, ask which device's decision could have stopped the request, and read that device's table.
