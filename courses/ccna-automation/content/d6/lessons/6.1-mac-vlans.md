## Why a developer meets Layer 2

Automation code rarely sends Ethernet frames, but it reads and writes Layer 2 objects all the time: a MAC address in an inventory record or an ARP table, a switch port in an API payload with `"type": "access"` and `"vlan": 20`, a trunk with an allowed-VLAN list. Topic 6.1 asks you to describe what MAC addresses and VLANs are for and how they are used. You know this from the CLI; the exam adds the developer's angle: recognising the formats and fields in data.

## MAC addresses

A **MAC address** identifies an interface on a local network segment. Ethernet MAC addresses are **48 bits** (6 octets), written in hexadecimal. The same address looks different depending on who prints it:

| Source | Format |
|---|---|
| Linux, macOS, most APIs | `00:00:5e:00:53:1a` |
| Windows `ipconfig /all` | `00-00-5E-00-53-1A` |
| Cisco IOS | `0000.5e00.531a` |

Code that compares MACs from different systems should normalise them first (strip separators, lowercase).

### Structure

- The first **24 bits** are the **OUI** (Organizationally Unique Identifier), assigned by the IEEE Registration Authority to a manufacturer. The holder assigns the remaining 24 bits. (The IEEE also issues longer prefixes, called MA-M and MA-S, that leave the holder fewer bits.) The OUI is why a script can guess the vendor from a MAC.
- Two bits in the **first octet** have special meaning (RFC 9542, which replaced RFC 7042):
  - **Group bit** (value `0x01`, the least significant bit). `0` = **unicast** (one interface); `1` = **multicast** (a group).
  - **Local bit** (value `0x02`). `0` = **globally unique** (burned in under an OUI); `1` = **locally administered** (set by software or an administrator).
- **Broadcast** is all ones: `ff:ff:ff:ff:ff:ff`. Every station on the segment accepts it.

Reading the first octet:

| Address | First octet in binary | Meaning |
|---|---|---|
| `00:00:5e:00:53:1a` | `0000 0000` | Global unicast |
| `02:00:5e:00:53:1a` | `0000 0010` | Locally administered unicast |
| `01:00:5e:00:00:fb` | `0000 0001` | Multicast (IPv4 multicast maps into `01:00:5e`) |
| `33:33:00:00:00:01` | `0011 0011` | Multicast (IPv6 multicast maps into `33:33`) |
| `ff:ff:ff:ff:ff:ff` | `1111 1111` | Broadcast |

A quick rule for unicast addresses: if the **second hex digit** is `2`, `6`, `A` or `E`, the local bit is set. Phones and laptops use locally administered random MACs for Wi-Fi privacy, so the "same" device can show a different MAC per network. Do not treat a MAC as a permanent device identity in inventory code without checking.

> **Exam tip:** MAC = 48 bits, Layer 2, meaningful only on the local segment. IP = Layer 3, end to end. A router replaces the source and destination MAC on every hop; the IP addresses stay the same (unless NAT changes them).

The RFC 9542 documentation range `00:00:5e:00:53:00` to `00:00:5e:00:53:ff` is reserved for examples, which is why this course uses it.

### How a switch learns and forwards

A switch builds a **MAC address table** (often called the CAM table) of *MAC address, VLAN, port* entries:

1. **Learn.** For every frame received, it records the **source** MAC against the ingress port and VLAN. Entries age out if not refreshed (300 seconds by default on Cisco Catalyst switches).
2. **Forward.** It looks up the **destination** MAC in that VLAN:
   - Known unicast: send out only the port in the table.
   - **Unknown unicast**, **broadcast** and multicast (without IGMP snooping): **flood** out every port in the same VLAN except the one it arrived on.
   - Destination on the same port it came in on: filter (drop).

The switch does not change the frame. It never looks at IP addresses to make this decision (a Layer 3 switch doing routing is a different function).

How the sender learns the destination MAC in the first place: IPv4 uses **ARP** (a broadcast "who has 10.1.20.15?" and a unicast reply); IPv6 uses Neighbor Discovery. A host only ARPs for addresses **on its own subnet**; for anything else it ARPs for its default gateway (lesson 6.2).

## VLANs

A **VLAN** splits one physical switch (or a group of switches) into several **separate broadcast domains**. Hosts in VLAN 10 do not receive VLAN 20's broadcasts or floods, and they cannot reach VLAN 20 at Layer 2 at all. Each VLAN normally maps to one IP subnet. Uses: separating users, voice, servers, management and guests; limiting broadcast scope; applying different security policy between them.

### Access and trunk ports

| | Access port | Trunk port |
|---|---|---|
| VLANs carried | One (plus an optional voice VLAN) | Many |
| Frames on the wire | Untagged | Tagged with 802.1Q, except the native VLAN |
| Connects to | End hosts: PCs, printers, servers, phones | Other switches, routers, hypervisors, wireless APs |

### The 802.1Q tag

On a trunk, the switch inserts a **4-byte 802.1Q tag** between the source MAC address and the EtherType:

```text
| Dest MAC | Src MAC | TPID 0x8100 | PCP | DEI | VID     | EtherType | Payload | FCS |
|  6 bytes | 6 bytes |   16 bits   |  3  |  1  | 12 bits |  2 bytes  |         |     |
```

- **TPID** `0x8100` identifies the frame as tagged.
- **PCP** (3 bits) is the 802.1p priority (class of service 0 to 7). **DEI** (1 bit, formerly CFI) marks frames eligible to drop under congestion.
- **VID** (12 bits) is the VLAN ID: 4,096 values, of which **0 and 4095 are reserved**, so usable VLANs are **1 to 4094**. VID 0 means a priority-tagged frame with no VLAN.
- On Cisco switches, VLANs 1 to 1005 are the normal range (1002 to 1005 are reserved for legacy Token Ring and FDDI) and 1006 to 4094 the extended range.

The tag makes the frame 4 bytes larger (a maximum standard frame grows from 1,518 to 1,522 bytes).

### Native VLAN

Frames in the **native VLAN** cross an 802.1Q trunk **untagged**, and an untagged frame received on the trunk is placed in the native VLAN. On Cisco switches it defaults to VLAN 1. Both ends must agree: a native VLAN mismatch silently joins two different VLANs together (Cisco's CDP logs a "native VLAN mismatch" message). Security practice is to set the native VLAN to an unused VLAN and not carry user traffic in it.

### Inter-VLAN routing

Because each VLAN is its own broadcast domain and subnet, traffic between VLANs must be **routed**:

- **Router on a stick:** one router interface trunked to the switch, with a subinterface per VLAN (`interface Gi0/0.20`, `encapsulation dot1Q 20`, `ip address 10.1.20.1 255.255.255.0`).
- **Layer 3 switch:** a switched virtual interface (SVI) per VLAN (`interface Vlan20`) acting as the hosts' default gateway, routing in hardware. This is the usual design today.
- A **firewall** with VLAN subinterfaces, when traffic between segments must be inspected.

## VLANs and MACs in API payloads

Interface and VLAN objects appear in almost every network API. In the Meraki Dashboard API, updating a switch port takes fields such as:

```json
{
  "name": "Printer 3F",
  "type": "access",
  "vlan": 20,
  "voiceVlan": 30
}
```

and for a trunk:

```json
{
  "type": "trunk",
  "vlan": 99,
  "allowedVlans": "10,20,30,99"
}
```

The API documentation states that for a trunk, `vlan` is the **native VLAN**, and that `allowedVlans` applies only to trunk ports. The same ideas appear as YANG leaves in RESTCONF and NETCONF payloads (an interface with a switchport mode, an access VLAN, a trunk allowed list) and in Ansible modules. Validating input before you send it is cheap: a VLAN ID outside 1 to 4094 is wrong whatever the platform, and a script that sets `allowedVlans` on a trunk uplink without the management VLAN can cut off the device it is configuring.

> **Watch out:** Replacing a trunk's allowed list (for example, a PUT, or `switchport trunk allowed vlan 30` on IOS) removes every VLAN not listed. Adding one VLAN needs the full list, or the IOS `add` keyword.

## Lab it yourself

Works on any computer; you only read your own machine's settings.

1. Find your interface MAC addresses. Windows: `ipconfig /all` (look for "Physical Address") or `Get-NetAdapter` in PowerShell. macOS: `ifconfig en0 | grep ether`. Linux: `ip link`. Is the second hex digit 2, 6, A or E? On Wi-Fi it often is (a private random address).
2. Look at your ARP cache. Windows: `arp -a`. macOS: `arp -a`. Linux: `ip neigh`. Your default gateway's MAC should be there.
3. Write a Python function that takes a MAC in any of the three formats above, normalises it to `00:00:5e:00:53:1a` form, and reports unicast or multicast and global or local by testing `int(first_octet, 16) & 0x01` and `& 0x02`.
4. In the Meraki documentation on DevNet, open "Update Device Switch Port" and find the `type`, `vlan` and `allowedVlans` fields.

## Key takeaways

- A MAC address is 48 bits: a 24-bit OUI plus 24 bits assigned by the holder; written as `aa:bb:cc:dd:ee:ff`, `AA-BB-...` or `aabb.ccdd.eeff`.
- First octet: group bit `0x01` (1 = multicast), local bit `0x02` (1 = locally administered). Broadcast is `ff:ff:ff:ff:ff:ff`.
- Switches learn source MACs per port and VLAN and forward on the destination MAC; they flood unknown unicast, broadcast and multicast (unless IGMP snooping constrains it) within the VLAN.
- A VLAN is a broadcast domain, usually one subnet. Access ports carry one untagged VLAN; trunks carry many with 802.1Q tags.
- 802.1Q: 4-byte tag, TPID `0x8100`, 12-bit VID, usable VLANs 1 to 4094; the native VLAN is untagged and must match on both ends.
- Traffic between VLANs needs a router, Layer 3 switch SVI or firewall.
- In APIs, ports and VLANs are objects with fields such as `type`, `vlan` and `allowedVlans`; validate VLAN ranges and remember that replacing an allowed list removes what is not listed.
