## The API is not yours

When you consume someone else's API, the provider sets the rules: how fast you may call, how much data comes back per call, how long a token lasts, how big a request may be, and when old versions disappear. Scripts that ignore these work in the lab and fail at scale. Topic 2.3 asks you to describe these constraints; lesson 2.5 uses them for troubleshooting.

| Constraint | What you see when you hit it | What your code should do |
|---|---|---|
| Rate limit | `429 Too Many Requests`, often with `Retry-After` | Wait the indicated time, then retry; throttle in advance |
| Pagination | Only part of the data comes back, plus a next link or cursor | Loop until there is no next page |
| Timeouts | Your client waits forever, or the server or a proxy gives up (`504`, `408`) | Always set a client timeout; retry idempotent calls carefully |
| Payload size | `413 Content Too Large`, `414 URI Too Long` | Split the work; use batch endpoints |
| Versioning | `404` or changed fields after an upgrade; deprecation notices | Pin a version in the URL or header; watch release notes |
| Authentication expiry | `401 Unauthorized` on a script that worked an hour ago | Detect 401, get a new token once, retry |
| Network path | Connection refused, TLS errors, proxy blocks | Check reachability and certificates first |

## Rate limiting and 429

Providers cap the number of requests per client, per organisation or per source address in a time window, to protect the service. When you exceed it, the server answers **`429 Too Many Requests`** (defined in RFC 6585). The response **may** include a **`Retry-After`** header, whose value is either a number of seconds or an HTTP date (RFC 9110):

```http
HTTP/1.1 429 Too Many Requests
Content-Type: application/json
Retry-After: 2

{"errors": ["API rate limit exceeded for organization"]}
```

Real numbers from Cisco documentation, as published on the Meraki Dashboard API rate-limit page at the time of writing: **10 requests per second per organisation** (with a short burst allowance) shared by every application using that organisation, plus **100 requests per second per source IP**; exceeding them returns `429` with `Retry-After`. Other APIs publish their own limits, sometimes per minute or per day, and some return headers such as `X-RateLimit-Remaining` (vendor-specific, not standardised).

How to behave:

1. Read `Retry-After` and sleep that long before retrying.
2. If there is no `Retry-After`, back off **exponentially** (1 s, 2 s, 4 s, ...) with a little random jitter and a cap on attempts.
3. Throttle proactively: spread calls out, cache results you reuse, and prefer one bulk or organisation-wide call over hundreds of per-device calls.

`429` is the 4xx code you will meet most often that is fixed by retrying later without changing the request (RFC 9110 also lets a client repeat a request after `408 Request Timeout`). `503 Service Unavailable` may also carry `Retry-After` when the server is overloaded or in maintenance.

## Pagination

Collections can hold thousands of items, so APIs return them a page at a time. Three styles are common:

| Style | Request | How you get the next page | Watch out |
|---|---|---|---|
| **Offset / limit** | `GET /devices?offset=0&limit=100`, then `offset=100`, `offset=200` | Add `limit` to `offset` until a page comes back short or empty | Items inserted or deleted between calls shift the pages, so you can skip or repeat items. Some APIs use `page=2&per_page=100` instead |
| **Cursor (token)** | `GET /devices?limit=100` returns a `next` cursor; send `?cursor=<value>` | Pass the opaque cursor from the previous response until none is returned | Treat the cursor as opaque: do not build or decode it yourself |
| **Link header (RFC 8288)** | Any of the above, but the server puts ready-made URLs in a `Link` response header | Follow the URL with `rel="next"` until there is no `next` | The header value is a list: parse it, do not split on commas by hand |

An RFC 8288 `Link` header:

```http
Link: <https://api.example.com/api/v1/devices?perPage=100&startingAfter=Q2XX-0100>; rel="next", <https://api.example.com/api/v1/devices?perPage=100>; rel="first"
```

The whole value sits on one header line: HTTP/1.1 forbids senders from folding a header across lines (RFC 9112).

The Meraki Dashboard API uses this standard (its pagination page cites RFC 5988, which RFC 8288 replaced): paginated GETs accept `perPage`, `startingAfter` and `endingBefore`, and the `Link` header carries `first`, `prev`, `next` and `last` URLs. In Python, `requests` parses the header for you into `response.links["next"]["url"]` (lesson 2.9 has a full loop).

> **Exam tip:** If a script "only ever returns the first 1,000 devices" or "always returns exactly 100 items", the cause is pagination: the script never asked for the next page.

## Timeouts

Two kinds:

- **Client timeouts.** Your script decides how long to wait for a connection and for data. The Python `requests` library has **no default timeout**: without `timeout=` a hung server hangs your script forever. Set one on every call, for example `timeout=(5, 30)` (connect, read).
- **Server and gateway timeouts.** A load balancer or API gateway in front of the application gives up on a slow back end and returns `504 Gateway Timeout`; a server tired of waiting for your request returns `408 Request Timeout`. Long operations are often made **asynchronous** to avoid this: the server answers `202 Accepted` with a task id at once (lesson 2.8).

Retrying after a timeout is safe for idempotent methods (GET, PUT, DELETE). A POST that timed out may have succeeded on the server; check before you send it again, or you may create the object twice.

## Payload and URL size limits

Servers cap request bodies (`413 Content Too Large`, formerly "Payload Too Large") and URL length (`414 URI Too Long`, usually from huge query strings). Responses are capped by page size, and some APIs limit the number of items per batch. The remedies are to split large changes into several requests, use the provider's batch or bulk endpoint where it has one (Meraki action batches, for example), and move large filters into a POST query body if the API documents one.

## Versioning

APIs change. Providers version them so existing clients keep working:

| Where the version lives | Example |
|---|---|
| URL path (most common) | `/api/v1/organizations`, `/dna/intent/api/v1/network-device` |
| Header | `Accept: application/vnd.example.v2+json` or a custom version header |
| Query parameter | `?api-version=2026-01-01` |

Constraints that follow from it: a script written for an old version breaks when that version is retired (Meraki's v1 API replaced v0, and v1 uses a different authentication header from v0's `X-Cisco-Meraki-API-Key`); fields get deprecated before removal; and the same product can expose different API versions per software release (Catalyst Center documentation is published per release). Pin the version you tested, read deprecation notices, and test before upgrading the platform.

## Authentication expiry

Tokens expire. Catalyst Center tokens, for example, last **60 minutes**; after that every call returns `401 Unauthorized` until you request a new token. OAuth access tokens typically last minutes to hours and are renewed with a refresh token. API keys usually do not expire on their own but can be revoked or rotated. A long-running script should catch `401`, re-authenticate **once**, and retry the request; if it fails again, stop and report rather than looping.

## Other practical limits

- **Network path**: proxies, firewalls and TLS inspection between you and the API. A corporate proxy can block or alter requests before they reach the API.
- **Certificates**: lab appliances often use self-signed certificates; the fix is to trust the CA, not to disable verification in production (lesson 2.9).
- **Consistency**: after a write, a read may briefly return the old value on eventually consistent platforms.
- **Terms of use and quotas**: licences can cap API access or daily volume.

## Lab it yourself

Any computer with curl or Postman, plus a free Cisco account for the DevNet Sandbox:

1. `curl -i https://httpbin.org/status/429` and look at the status line. Then `curl -i "https://httpbin.org/response-headers?Retry-After=3"` to see how a server returns a header you choose.
2. `curl -i https://httpbin.org/delay/5 --max-time 2` and read curl's timeout error; repeat with `--max-time 10`.
3. Read the Meraki Dashboard API "Rate Limit" and "Pagination" pages on developer.cisco.com and note the limits and the three pagination parameters.
4. With the Meraki or Catalyst Center sandbox, call a list endpoint with a small page size (`perPage=3` on Meraki, `limit=3&offset=1` on Catalyst Center's network-device list, whose `offset` is 1-based, so the next page is `offset=4`) and follow the next page by hand. On Meraki, run curl with `-i` and find the `Link` header.

## Key takeaways

- Rate limits return `429 Too Many Requests`; honour `Retry-After` (seconds or a date), otherwise back off exponentially with jitter.
- Pagination styles: offset/limit, opaque cursor, and RFC 8288 `Link` headers with `rel="next"`; loop until there is no next page.
- `requests` has no default timeout; always set one. Retry only idempotent calls blindly.
- Size limits show up as `413` (body) and `414` (URL); split the work or use batch endpoints.
- Versions usually live in the path (`/api/v1/`); pin them and watch deprecations.
- Tokens expire (Catalyst Center: 60 minutes, then `401`); re-authenticate once and retry.
