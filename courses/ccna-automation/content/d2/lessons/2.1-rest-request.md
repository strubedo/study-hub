## From documentation to a working request

Topic 2.1 gives you an API documentation excerpt and asks you to build the request: which method, which URL, which headers, which body. Every REST call is assembled from the same five parts, and good documentation tells you each one:

| Part | Where the documentation shows it | Example |
|---|---|---|
| **Method** | Next to the endpoint: `GET`, `POST`, `PUT`, `PATCH`, `DELETE` | `POST` |
| **URL** | Base URL + resource path, with **path parameters** filled in and **query parameters** appended | `https://api.example.com/api/v1/networks/N_1001/vlans` |
| **Headers** | Authentication section, plus `Content-Type` and `Accept` | `Authorization: Bearer <YOUR_API_KEY>` |
| **Body** | "Request body" or "payload" schema; only for methods that send data | `{"vlanId": 30, "name": "voice"}` |
| **Expected response** | "Responses" table: status codes and body schema | `201 Created` |

Here is an excerpt in the style you will see in Cisco and other vendor references. The API is invented for this course.

```text
Create a VLAN
POST /networks/{networkId}/vlans

Base URL:        https://api.example.com/api/v1
Authentication:  Authorization: Bearer <API key>

Path parameters
  networkId   string   required   Network identifier, for example N_1001

Request body (application/json)
  vlanId      integer  required   1-4094
  name        string   required   Up to 32 characters
  subnet      string   optional   CIDR, for example 10.30.0.0/24

Responses
  201  Created. Location header points to the new VLAN; body is the VLAN object
  400  Body is not valid JSON or a required field is missing
  401  Missing or invalid API key
  409  A VLAN with this vlanId already exists in the network
```

Reading it as a recipe:

1. **Method:** `POST`, because you are creating a new item in a collection.
2. **URL:** base URL + path, with `{networkId}` replaced: `https://api.example.com/api/v1/networks/N_1001/vlans`. The braces are a placeholder and are not sent.
3. **Headers:** the authentication header from the documentation; `Content-Type: application/json` because you send a JSON body; `Accept: application/json` to say what you want back.
4. **Body:** a JSON object with the required fields `vlanId` and `name`, and the optional `subnet` if you want it.

## The URL: base URL, path parameters and query parameters

```text
https://api.example.com/api/v1/networks/N_1001/clients?timespan=3600&perPage=50
\___/   \_____________/\_____/\________________________/\_______________________/
scheme  host            base   resource path             query string
                        path   (N_1001 is a path param)   (two query params)
```

- **Path parameters** identify *which* resource: `/networks/N_1001`, `/devices/42`. They are part of the path and are usually required.
- **Query parameters** follow `?`, are separated by `&`, and **filter, sort or page** the result: `?status=offline`, `?limit=50&offset=100`. They are usually optional.
- Characters with a special meaning in a URL must be **percent-encoded** inside a query value: a space becomes `%20` (or `+` in form-style encoding), `&` becomes `%26`, `#` becomes `%23`. Libraries such as `requests` do this for you when you pass `params=` (they also encode `/` as `%2F`, which is allowed but not required in a query string).

> **Exam tip:** "Which device?" belongs in the path; "which of them, how many, in what order?" belongs in the query string. If the documentation writes `/devices/{deviceId}`, the id goes in the path, not in `?deviceId=`.

## Headers you must recognise

| Header | Sent by | Meaning |
|---|---|---|
| `Content-Type` | Whoever sends a body | The media type of **this message's body**: `application/json`, `application/xml`, `application/yang-data+json` (RESTCONF), `application/x-www-form-urlencoded` |
| `Accept` | Client | The media types the client **wants back**. If the server cannot produce any of them it may answer `406 Not Acceptable` |
| `Authorization` | Client | Credentials: `Basic ...`, `Bearer ...` (see lesson 2.7) |
| Custom auth headers | Client | Vendor-specific, for example `X-Auth-Token` on Catalyst Center |
| `Host` | Client | The server name; mandatory in HTTP/1.1 (curl and `requests` add it) |
| `User-Agent` | Client | Identifies the client software |

`Content-Type` describes what you are **sending**; `Accept` describes what you want to **receive**. A GET has no body, so it needs `Accept` but not `Content-Type`. Sending XML while labelling it `application/json`, or sending a body type the endpoint does not support, typically earns `415 Unsupported Media Type` or `400 Bad Request`.

## Methods, safety and idempotency

RFC 9110 defines two properties that the exam tests directly:

- **Safe**: the client asks for no change on the server (read-only). GET, HEAD, OPTIONS and TRACE are safe.
- **Idempotent**: sending the same request once or ten times has the same *intended* effect on the server. PUT, DELETE and all safe methods are idempotent.

| Method | Typical REST use | Safe | Idempotent | Body sent | Typical success |
|---|---|---|---|---|---|
| `GET` | Read a resource or a collection | Yes | Yes | No | `200 OK` |
| `POST` | Create an item in a collection (server picks the id), or trigger an action | No | **No** | Yes | `201 Created` (with `Location`), or `200`/`202` for actions |
| `PUT` | **Replace** the whole resource at a known URL (or create it at that URL) | No | Yes | Yes (full representation) | `200 OK` or `204 No Content`; `201` if it created it |
| `PATCH` | **Modify** part of a resource (RFC 5789) | No | Not guaranteed | Yes (only the changes) | `200 OK` or `204 No Content` |
| `DELETE` | Remove a resource | No | Yes | Usually no | `204 No Content` or `200 OK` |
| `HEAD` | Same as GET but headers only | Yes | Yes | No | `200 OK` |
| `OPTIONS` | Ask which methods a resource supports | Yes | Yes | No | `200`/`204` with an `Allow` header |

What idempotency means in practice:

- Two identical `POST /vlans` requests can create **two** VLANs (or the second fails with `409 Conflict`). That is why a client must not blindly retry a POST after a timeout.
- Two identical `PUT /vlans/30` requests leave VLAN 30 in the same final state. Safe to retry.
- Two `DELETE /vlans/30` requests: the first removes it, the second probably returns `404`. The *response* differs, but the server state (VLAN 30 gone) is the same, so DELETE is still idempotent.
- `PATCH` is "neither safe nor idempotent" per RFC 5789, although a particular PATCH (set `name` to `voice`) can be idempotent. A PATCH like "increment a counter" or "append to a list" is not.

**PUT replaces, PATCH modifies.** If VLAN 30 is `{"vlanId": 30, "name": "voice", "subnet": "10.30.0.0/24"}` and you `PUT` `{"vlanId": 30, "name": "voip"}`, a strict PUT leaves the VLAN without the omitted `subnet` (or the API rejects the incomplete body, or resets the field to its default). A `PATCH` with `{"name": "voip"}` changes only the name. Many APIs document PUT as a partial update anyway, so read the documentation, but for the exam PUT means full replacement.

> **Watch out:** "Create" is not always POST. If the client chooses the URL (`PUT /vlans/30` creates VLAN 30 if it does not exist) PUT can create, and RFC 9110 says the server then answers `201 Created`.

## The same request in curl and as raw HTTP

The VLAN creation from the documentation, as a curl command:

```bash
curl -i -X POST "https://api.example.com/api/v1/networks/N_1001/vlans" \
  -H "Authorization: Bearer <YOUR_API_KEY>" \
  -H "Content-Type: application/json" \
  -H "Accept: application/json" \
  -d '{"vlanId": 30, "name": "voice", "subnet": "10.30.0.0/24"}'
```

- `-X POST` sets the method. `-d` alone would already make curl use POST, but `-d` on its own labels the body `application/x-www-form-urlencoded`, which is why the explicit `Content-Type` header matters. Since curl 7.82.0, `--json '<body>'` sets both `Content-Type: application/json` and `Accept: application/json` for you.
- `-H` adds a header; repeat it for each header.
- `-i` prints the response status line and headers before the body. `-v` shows the request headers too.
- Single quotes around the JSON stop a Unix shell from touching the double quotes inside it. In Windows `cmd.exe` use `-d "{\"vlanId\": 30}"` or put the body in a file and use `-d @vlan.json`.

What actually goes over the connection (inside TLS) is plain text:

```http
POST /api/v1/networks/N_1001/vlans HTTP/1.1
Host: api.example.com
User-Agent: curl/8.11.1
Authorization: Bearer <YOUR_API_KEY>
Content-Type: application/json
Accept: application/json
Content-Length: 57

{"vlanId": 30, "name": "voice", "subnet": "10.30.0.0/24"}
```

The **request line** holds the method, the path with its query string, and the HTTP version; the host moves to the `Host` header. Headers are `Name: value`, one per line, names case-insensitive. A blank line ends the headers; the body follows, and `Content-Length` is its size in bytes (57 here). The scheme and port are not in the request line: they decided where the connection went.

And a typical answer:

```http
HTTP/1.1 201 Created
Location: /api/v1/networks/N_1001/vlans/30
Content-Type: application/json
Content-Length: 71

{"vlanId": 30, "name": "voice", "subnet": "10.30.0.0/24", "id": "V_30"}
```

Lesson 2.6 takes a response apart line by line.

A read with query parameters:

```bash
curl -s "https://api.example.com/api/v1/networks/N_1001/vlans?name=voice&limit=10" \
  -H "Authorization: Bearer <YOUR_API_KEY>" \
  -H "Accept: application/json"
```

```http
GET /api/v1/networks/N_1001/vlans?name=voice&limit=10 HTTP/1.1
Host: api.example.com
Authorization: Bearer <YOUR_API_KEY>
Accept: application/json
```

No body, so no `Content-Type` and no `Content-Length`. Quote URLs that contain `&`, or the shell treats `&` as "run in the background".

## Mapping tasks to requests

| Task (from the documentation) | Request |
|---|---|
| List all VLANs in network N_1001 | `GET /networks/N_1001/vlans` |
| List only the first 10 VLANs named voice | `GET /networks/N_1001/vlans?name=voice&limit=10` |
| Read VLAN 30 | `GET /networks/N_1001/vlans/30` |
| Create a VLAN (server assigns the id) | `POST /networks/N_1001/vlans` with a JSON body |
| Replace VLAN 30's whole configuration | `PUT /networks/N_1001/vlans/30` with the full object |
| Rename VLAN 30 only | `PATCH /networks/N_1001/vlans/30` with `{"name": "voip"}` |
| Remove VLAN 30 | `DELETE /networks/N_1001/vlans/30` |

## Lab it yourself

Works from any computer with curl (built in on Windows 10 and later, macOS and Linux) or Postman. The public echo service httpbin.org returns whatever request it receives, so you can see exactly what you built without needing an account.

On Windows, the curl commands in this course's labs need three adjustments. In Windows PowerShell 5.1, type `curl.exe`, because plain `curl` there is an alias for `Invoke-WebRequest` (PowerShell 7 and `cmd.exe` run the real curl). Put each command on one line: a trailing `\` continues a line in bash and zsh only (PowerShell uses a backtick, `cmd.exe` uses `^`). Shell quoting also differs, so for JSON bodies save the body in a file and send it with `-d @body.json` (or `--json @body.json`).

1. `curl -i "https://httpbin.org/get?name=voice&limit=10" -H "Accept: application/json"` and find your query parameters under `args` and your headers under `headers` in the reply.
2. Send the VLAN body to `https://httpbin.org/anything` with `-X POST`, `-H "Content-Type: application/json"` and `-d`. Check that it appears under `json`. Repeat without the `Content-Type` header and see it land under `form` instead, because curl labelled it as form data.
3. Repeat with `-X PUT`, `-X PATCH` and `-X DELETE` and compare the `method` field.
4. Add `-v` and read the request line and headers curl sent (lines starting with `>`).
5. In the DevNet Sandbox, open the always-on Catalyst Center or Meraki sandbox page and its API reference, pick one GET endpoint, and write down its method, full URL, required headers and success code before you try it in Postman.

## Key takeaways

- A request = method + URL (base URL, path with path parameters, query string) + headers + optional body; the documentation tells you each.
- Path parameters identify the resource; query parameters filter, sort and page it, and must be percent-encoded.
- `Content-Type` labels the body you send; `Accept` says what you want back. A GET needs no `Content-Type`.
- Safe: GET, HEAD, OPTIONS. Idempotent: those plus PUT and DELETE. POST is neither, and PATCH is not guaranteed to be idempotent.
- POST creates in a collection (`201` plus `Location`), PUT replaces at a known URL, PATCH changes only the fields sent, DELETE removes.
- In curl: `-X` method, `-H` header, `-d` body (form-labelled unless you set `Content-Type`), `--json` for JSON, `-i` to see response headers.
- On the wire: request line, headers, blank line, body; `Host` is mandatory in HTTP/1.1.
