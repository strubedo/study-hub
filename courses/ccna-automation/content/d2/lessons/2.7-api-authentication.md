## Authentication versus authorisation

- **Authentication** answers "who are you?" Credentials travel with the request; if they are missing or wrong the answer is `401 Unauthorized`.
- **Authorisation** answers "what may you do?" It is decided from your identity, role or the scopes of your token; if you are not allowed the answer is `403 Forbidden`.

Topic 2.7 names three mechanisms: **Basic**, **custom token** and **API keys**. A fourth, **Bearer tokens**, is the common modern form and appears throughout Cisco APIs, so it is covered at the end, marked as going beyond the topic's list.

All of them send a secret with the request, so **all of them need TLS** (HTTPS). Anyone who can read the traffic can reuse the credential.

## Basic authentication (RFC 7617)

The client joins the user name and password with a colon, **base64-encodes** the result, and sends it in the `Authorization` header with the scheme word `Basic`:

```text
user-pass        alice:example-password
base64           YWxpY2U6ZXhhbXBsZS1wYXNzd29yZA==
header           Authorization: Basic YWxpY2U6ZXhhbXBsZS1wYXNzd29yZA==
```

You can check that value yourself, which also proves the point that matters most:

```python
>>> import base64
>>> base64.b64encode(b"alice:example-password").decode()
'YWxpY2U6ZXhhbXBsZS1wYXNzd29yZA=='
>>> base64.b64decode("YWxpY2U6ZXhhbXBsZS1wYXNzd29yZA==").decode()
'alice:example-password'
```

**Base64 is an encoding, not encryption.** There is no key; anyone can decode it in one line. RFC 7617 says the scheme is not secure unless used with an external secure system such as TLS.

How a server asks for Basic, and how clients send it:

```http
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Basic realm="api", charset="UTF-8"
```

```bash
curl -u alice:example-password https://api.example.com/api/v1/devices
```

```python
requests.get(url, auth=("alice", "example-password"), timeout=10)   # a tuple means Basic
```

Properties: simple and universally supported, but the real password goes with **every** request, nothing expires, and a user name containing a colon is not allowed (RFC 7617: the receiver splits the pair at the first colon). In practice, many APIs use Basic **only once**, to obtain a token.

## Custom token authentication

The client logs in once (often with Basic or a JSON body containing the user name and password), receives a **token**, and sends that token on every later request in a header the vendor defines. The token stands in for the password and **expires**.

Cisco Catalyst Center is the textbook example:

```text
1. POST https://catalyst.example.com/dna/system/api/v1/auth/token
     Authorization: Basic YWxpY2U6ZXhhbXBsZS1wYXNzd29yZA==
2. 200 OK   {"Token": "example-token-not-real"}
3. GET  https://catalyst.example.com/dna/intent/api/v1/network-device
     X-Auth-Token: example-token-not-real
4. 200 OK   {"response": [...], "version": "1.0"}
     ... 60 minutes later the token expires ...
5. GET  ... with the old token  ->  401 Unauthorized: repeat step 1
```

In curl:

```bash
curl -s -X POST "https://catalyst.example.com/dna/system/api/v1/auth/token" \
  -u "alice:example-password" -H "Content-Type: application/json"

curl -s "https://catalyst.example.com/dna/intent/api/v1/network-device" \
  -H "X-Auth-Token: example-token-not-real" -H "Accept: application/json"
```

In Python:

```python
import requests

BASE = "https://catalyst.example.com"
resp = requests.post(f"{BASE}/dna/system/api/v1/auth/token",
                     auth=("alice", "example-password"), timeout=10)
resp.raise_for_status()
token = resp.json()["Token"]

devices = requests.get(f"{BASE}/dna/intent/api/v1/network-device",
                       headers={"X-Auth-Token": token, "Accept": "application/json"},
                       timeout=30)
```

Other variations you will meet: a session **cookie** returned by a login call (APIC's `aaaLogin` returns a token that clients usually send back as the `APIC-cookie` cookie), and login endpoints that take the credentials in a JSON body instead of a Basic header. Common features: the password is sent once, the token is time-limited (a stolen one stops working), and your code must handle expiry by logging in again.

> **Watch out:** "Token" alone does not say *where* it goes. The documentation decides: `X-Auth-Token: <token>`, `Authorization: Bearer <token>`, or a cookie. Sending the right token in the wrong header gives `401` just like a wrong token.

## API keys

An **API key** is a long random string generated in the platform's portal for a user or an application. The client sends it with every request. It does not expire on its own in most platforms, but can be revoked and regenerated.

Where the key goes is set by the API:

| Placement | Example | Notes |
|---|---|---|
| Standard `Authorization` header | `Authorization: Bearer <YOUR_API_KEY>` (Meraki Dashboard API v1) | Preferred |
| Custom header | `X-API-Key: <YOUR_API_KEY>`; Meraki's older v0 header was `X-Cisco-Meraki-API-Key` | Common |
| Query string | `GET /v1/devices?api_key=<YOUR_API_KEY>` | **Avoid** |

**Why API keys in the query string are a bad idea:** the full URL, including the query string, ends up in web-server and proxy access logs, browser history, monitoring tools, and the `Referer` header sent to other sites. RFC 6750 gives the same warning for bearer tokens in URLs. A header is not logged by default. If an API only accepts keys in the URL, treat those logs as sensitive.

Handling keys and tokens in code:

- Never write them into the script or commit them to Git. Read them from an environment variable (`os.environ["MERAKI_API_KEY"]`) or a secrets manager.
- Give each application its own key with the least privilege it needs, and rotate keys.
- Do not print request headers in logs.

## Bearer tokens (beyond the three the topic names)

RFC 6750 defines a standard way to send a token: `Authorization: Bearer <token>`. "Bearer" means whoever holds (bears) the token can use it, exactly like cash. It came from OAuth 2.0, where an authorisation server issues short-lived access tokens with specific **scopes**, but many APIs simply put an API key or a login token after the word `Bearer`, as Meraki v1 does with its API key.

```http
GET /api/v1/organizations HTTP/1.1
Host: api.example.com
Authorization: Bearer example-token-not-real
Accept: application/json
```

When a bearer token is rejected, RFC 6750 tells the server to say why in `WWW-Authenticate`: `error="invalid_token"` (expired, revoked or malformed: `401`) or `error="insufficient_scope"` (valid token without the needed permission: `403`).

## Comparison

| | Basic | Custom token | API key | Bearer (OAuth or key) |
|---|---|---|---|---|
| What is sent each time | `Authorization: Basic base64(user:password)` | Token in a vendor header (`X-Auth-Token`) or cookie | The key, in a header or (badly) the query string | `Authorization: Bearer <token>` |
| How you get it | You already have the password | A login call, often using Basic | Generated in the portal | A login or OAuth flow, or the API key itself |
| Expires | No | Yes (Catalyst Center: 60 minutes) | Usually not; revocable | Access tokens yes; keys no |
| Main risk | Password exposed on every call; base64 is trivially reversed | Stolen token valid until expiry | Long-lived secret; leaks via URLs and code | Anyone holding it can use it |
| Cisco examples | Catalyst Center token request; many device REST APIs; RESTCONF on IOS XE | Catalyst Center `X-Auth-Token`; APIC cookie | Meraki API key | Meraki v1 header; Webex access tokens |

> **Exam tip:** Basic = `base64(username:password)` in `Authorization: Basic`; decoding it gives the password back, so it needs HTTPS. Custom token = log in once, send the token in a vendor-named header until it expires. API key = static secret from a portal, sent with every request, best in a header.

## Lab it yourself

Any computer with Python 3 and curl:

1. Run the `base64` snippet above with your own made-up pair, and decode a value someone else produced.
2. `curl -v -u alice:example-password https://httpbin.org/basic-auth/alice/example-password` and find the `Authorization: Basic ...` line curl sent (it starts with `>`). Decode it.
3. `curl -i https://httpbin.org/bearer -H "Authorization: Bearer example-token-not-real"` (httpbin accepts any bearer value) and then without the header to see the `401`.
4. Reserve the always-on Catalyst Center sandbox on DevNet (always-on sandboxes also need a reservation, which issues your credentials), take the credentials the reservation shows, request a token with curl, and use it in an `X-Auth-Token` header to list network devices.
5. Generate a Meraki API key in the Meraki DevNet sandbox (or use the key your sandbox reservation issues), store it in an environment variable, and call `GET /api/v1/organizations` with `Authorization: Bearer $MERAKI_API_KEY` (bash and zsh; in PowerShell the variable is `$env:MERAKI_API_KEY`, in `cmd.exe` `%MERAKI_API_KEY%`).

## Key takeaways

- 401 = authentication failed or missing; 403 = authenticated but not authorised.
- Basic sends `Authorization: Basic ` + base64 of `user:password`; base64 is reversible encoding, so Basic requires TLS.
- Custom token: authenticate once (often with Basic), receive a token, send it in a vendor header such as `X-Auth-Token`; it expires (Catalyst Center: 60 minutes) and then you get 401.
- API keys are long-lived secrets from a portal; send them in a header, never in a query string, because URLs are logged.
- Bearer (RFC 6750) is the standard header form, `Authorization: Bearer <token>`, used by OAuth and by Meraki v1 for API keys.
- Keep every credential out of code and Git: environment variables or a secrets manager.
