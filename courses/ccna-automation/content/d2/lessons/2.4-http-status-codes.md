## Five classes, decided by the first digit

Every HTTP response starts with a three-digit status code. RFC 9110 defines the classes by the first digit, and a client that does not recognise a specific code must treat it like the `x00` code of its class (an unknown `432` is handled as `400`).

| Class | Meaning | Whose problem |
|---|---|---|
| **1xx** Informational | Interim response; the real one follows | Nobody; rarely seen in API work |
| **2xx** Successful | The request was received, understood and accepted | Nobody: it worked |
| **3xx** Redirection | Further action is needed, usually going to another URL | Nobody yet: follow the `Location` header |
| **4xx** Client error | The client seems to have erred | **The client**: fix the request; retrying the same request will not help (except `429` and `408`) |
| **5xx** Server error | The server failed to fulfil a valid-looking request | **The server** or something behind it: retry later with backoff, or contact the provider |

Each code comes with a short **reason phrase** (`404 Not Found`). Code reads the number; the phrase is for humans and is not even sent in HTTP/2.

## 2xx: success, but which kind

| Code | Meaning | Typical REST use |
|---|---|---|
| **200 OK** | Success; the body is the result | GET returning data; PUT or PATCH returning the updated object; POST that ran an action |
| **201 Created** | One or more new resources were created | POST to a collection (or PUT to a new URL). The new resource's URL is in the **`Location`** header; the body usually describes it |
| **202 Accepted** | Accepted for processing, but **not finished** | Asynchronous jobs: the body points at a task or status URL to check later (lesson 2.8). It does not promise the job will succeed |
| **204 No Content** | Success and **no body** | DELETE, or a PUT/PATCH that returns nothing. A 204 cannot contain a body, so `response.json()` on it fails |

> **Watch out:** A `202` only means "queued". Catalyst Center's documentation gives the example of a duplicate discovery name: the POST returns `202 Accepted`, and only the task shows the failure.

## 3xx: go somewhere else

API clients usually follow redirects automatically, so you meet 3xx when that goes wrong:

| Code | Meaning | Method on the redirected request |
|---|---|---|
| **301 Moved Permanently** | New permanent URL in `Location` | Clients may change POST to GET (historical behaviour) |
| **302 Found** | Temporarily at another URL | Clients may change POST to GET |
| **304 Not Modified** | Your cached copy is still valid (after a conditional GET with `If-None-Match` or `If-Modified-Since`) | No body; use your cache |
| **307 Temporary Redirect** | Temporarily at another URL | **Must not** change the method: a POST stays a POST |
| **308 Permanent Redirect** | New permanent URL | **Must not** change the method |

The practical case: an API moved from `http://` to `https://` or to a new host. A POST that is redirected with 301 or 302 may arrive as a body-less GET at the new URL and fail in a confusing way. Fix the base URL in your script. Some clients also drop the `Authorization` header when a redirect goes to a different host, which turns into a `401` at the new location.

## 4xx: the request needs fixing

These are the ones to know cold. The pairs that look alike are the ones the exam uses.

| Code | Meaning (RFC 9110 unless noted) | Typical cause in an API script |
|---|---|---|
| **400 Bad Request** | The server will not process the request because of a client error | Malformed JSON, missing required field, wrong type, bad query parameter |
| **401 Unauthorized** | The request **lacks valid authentication** credentials. The server must send `WWW-Authenticate` | No credentials, wrong password, expired or mistyped token. Despite the name it means **not authenticated** |
| **403 Forbidden** | The server understood the request and **refuses** it; credentials, if sent, are **insufficient** | Authenticated, but the account's role or the key's scope does not allow this action (a read-only admin trying to write) |
| **404 Not Found** | No current representation for the target resource (or the server will not reveal that one exists) | Wrong path, typo, wrong id, wrong API version in the URL, or the item was deleted |
| **405 Method Not Allowed** | The method is known but **not supported by this resource**. The server must send an **`Allow`** header listing the methods that are | `POST` to `/devices/42` when only GET, PUT and DELETE are allowed |
| **406 Not Acceptable** | Nothing matches your `Accept` header | `Accept: application/xml` to a JSON-only API |
| **409 Conflict** | Conflicts with the current state of the resource | Creating something that already exists; editing an object someone else changed |
| **413 Content Too Large** | The request body is bigger than the server accepts | Huge upload or batch |
| **415 Unsupported Media Type** | The body's format is not supported by this method on this resource | Wrong or missing `Content-Type`, for example form data or `text/plain` sent to a JSON endpoint |
| **422 Unprocessable Content** | Media type understood, syntax correct, but the instructions cannot be processed | Well-formed JSON with a semantically invalid value (VLAN 5000, end date before start date). Formerly "Unprocessable Entity" |
| **429 Too Many Requests** (RFC 6585) | Rate limit exceeded | Too many calls; wait for `Retry-After` |

Telling the look-alikes apart:

- **401 vs 403**: "Who are you?" vs "I know who you are, and no." A 401 is fixed by sending correct or fresh credentials. A 403 is fixed by using an account with the right permissions; re-sending the same credentials will not help.
- **404 vs 405**: 404 means the URL points at nothing. 405 means the URL is fine but this method is not allowed on it; the `Allow` header tells you which methods are.
- **400 vs 422 vs 415**: 415 is about the **format** label (`Content-Type`); 400 is about **syntax** (broken JSON) or a generally bad request; 422 is about **meaning** (valid JSON, impossible values). Many APIs use 400 for all of them, so read the error body; but when an API distinguishes them, this is how.
- **404 vs 403**: a server may answer 404 to hide that a forbidden resource exists, which RFC 9110 explicitly allows.

## 5xx: the server side failed

| Code | Meaning | What to do |
|---|---|---|
| **500 Internal Server Error** | Unexpected condition on the server | Retry later with backoff; if it repeats for one specific request, report it with the request details |
| **501 Not Implemented** | The server does not support the functionality (for example an unknown method) | Use a supported method or endpoint |
| **502 Bad Gateway** | A gateway or proxy got an invalid response from the upstream server | Usually transient; retry with backoff |
| **503 Service Unavailable** | Temporarily overloaded or in maintenance; may include `Retry-After` | Wait and retry |
| **504 Gateway Timeout** | A gateway or proxy did not get a timely response from upstream | Retry with backoff; consider async APIs or smaller requests |

5xx codes are the server's fault, so the same request may succeed later: retry with exponential backoff and a limit, and only retry automatically if the method is idempotent or you know the first attempt did not take effect.

> **Exam tip:** Know these cold: 200, 201, 202, 204, 400, 401, 403, 404, 405, 409, 415, 422, 429, 500, 502, 503, 504. Then learn who fixes each: 4xx = change the request (or wait, for 429), 5xx = wait or call the provider.

## Error bodies

Most APIs put details in the body of a 4xx or 5xx response, and those details usually tell you exactly what to fix. Formats vary by vendor (`{"errors": [...]}` on Meraki, a `response` object on Catalyst Center). RFC 9457 standardises one format, **problem details**, with media type `application/problem+json`:

```http
HTTP/1.1 422 Unprocessable Content
Content-Type: application/problem+json

{
  "type": "https://api.example.com/problems/invalid-vlan",
  "title": "VLAN id out of range",
  "status": 422,
  "detail": "vlanId 5000 is outside 1-4094",
  "instance": "/api/v1/networks/N_1001/vlans"
}
```

## Lab it yourself

Any computer with curl or Postman:

1. httpbin.org returns any code you ask for: `curl -i https://httpbin.org/status/201`, then `204`, `401`, `403`, `404`, `418` and `503`. Note which ones have a body.
2. `curl -i -X POST https://httpbin.org/get` returns `405`. Find the `Allow` header in the response.
3. `curl -i "https://httpbin.org/redirect-to?url=/get&status_code=307"` (the quotes stop the shell treating `&` as a command separator) shows a 307 with a `Location` header; add `-L` to follow it.
4. In the Meraki or Catalyst Center DevNet sandbox, call a list endpoint once with a valid key or token and once with a wrong one, and compare the codes and bodies.

## Key takeaways

- 2xx success, 3xx redirect, 4xx client must fix the request, 5xx server problem; unknown codes are treated as `x00` of their class.
- `201` means created, with `Location`; `202` means accepted but not finished; `204` means success with no body.
- `401` = not authenticated (missing, wrong or expired credentials); `403` = authenticated but not allowed.
- `404` = no such resource; `405` = method not allowed on it (see `Allow`); `415` = wrong `Content-Type`; `400` = malformed request; `422` = valid syntax, invalid values; `409` = state conflict.
- `429` = rate limited: wait for `Retry-After`. It is the main 4xx that retrying later fixes (`408 Request Timeout` is the other).
- 5xx can be retried with backoff; only retry automatically when the method is idempotent.
