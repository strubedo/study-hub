## Two separate questions

Topic 2.8 mixes two different ways of classifying an API, and the exam expects you to keep them apart:

1. **What is the interface built around?** **REST** (resources and HTTP methods) or **RPC** (remote procedure calls: named operations with parameters).
2. **When does the client get the result?** **Synchronous** (in the response to the same request) or **asynchronous** (later, by checking a task or receiving a callback).

Any combination is possible: a REST API can have asynchronous endpoints (Catalyst Center), and an RPC API can be synchronous (NETCONF `<get-config>`).

## REST: resources and uniform methods

REST (Representational State Transfer, from Roy Fielding's 2000 dissertation) is an architectural style. A REST API over HTTP exposes **resources** identified by URLs and manipulates them with the **standard methods**:

```text
GET    /api/v1/devices          list devices
POST   /api/v1/devices          create a device
GET    /api/v1/devices/42       read device 42
PUT    /api/v1/devices/42       replace device 42
PATCH  /api/v1/devices/42       modify device 42
DELETE /api/v1/devices/42       delete device 42
```

The constraints that define REST:

| Constraint | Meaning |
|---|---|
| Client-server | UI and data storage are separated and evolve independently |
| **Stateless** | Each request carries everything needed (including credentials); the server keeps no client session between requests |
| Cacheable | Responses say whether they can be cached |
| **Uniform interface** | Resources identified by URIs, manipulated through representations (JSON, XML), self-descriptive messages, links to related resources |
| Layered system | Proxies, gateways and load balancers can sit in between without the client knowing |
| Code on demand (optional) | The server may send code for the client to run |

The **nouns are in the URL, the verbs are the HTTP methods**, and the status code carries the result. Most Cisco controller APIs are REST-style: Meraki Dashboard, Catalyst Center Intent API, SD-WAN Manager, Webex, and RESTCONF (RFC 8040) on IOS XE.

## RPC: call a procedure on another machine

In RPC the client calls a **named operation** and passes parameters, as if calling a local function. The **verb is in the message**, not in the HTTP method; RPC over HTTP usually sends everything as a POST to one endpoint, and a `200 OK` only means the message was delivered; the result or error is inside the body.

| RPC flavour | Encoding and transport | Where you meet it |
|---|---|---|
| **XML-RPC** | XML over HTTP POST | Older APIs; Python's standard library has `xmlrpc.client` |
| **JSON-RPC** (2.0) | JSON over HTTP POST (or other transports) | Cisco NX-API offers a JSON-RPC format alongside its CLI-style formats |
| **SOAP** | XML envelopes, usually over HTTP, described by WSDL | Cisco Unified CM AXL |
| **gRPC** | Protocol Buffers over HTTP/2, with streaming | Model-driven telemetry dial-out from IOS XE and NX-OS; gNMI |
| **NETCONF** (RFC 6241) | XML `<rpc>` messages over SSH (port 830) | Configuration of IOS XE, IOS XR, NX-OS, Junos |

A JSON-RPC 2.0 call and reply:

```json
{"jsonrpc": "2.0", "method": "cli", "params": {"cmd": "show version", "version": 1}, "id": 1}
```

```json
{"jsonrpc": "2.0", "result": {"body": {"...": "..."}}, "id": 1}
```

The method name (`cli`) and its parameters are in the body; the `id` pairs the reply with the request.

**NETCONF** is the RPC example network engineers already know. Every operation is an `<rpc>` element naming a procedure: `<get-config>`, `<edit-config>`, `<commit>`, `<lock>`:

```xml
<rpc message-id="101" xmlns="urn:ietf:params:xml:ns:netconf:base:1.0">
  <get-config>
    <source><running/></source>
  </get-config>
</rpc>
```

The device answers with an `<rpc-reply>` carrying the same `message-id`, containing `<data>`, `<ok/>` or `<rpc-error>`. Domain 3 covers NETCONF in depth; here it matters as a style. Compare the same idea in REST: RESTCONF reads the running configuration with a `GET` on a resource URL such as `/restconf/data/ietf-interfaces:interfaces`.

| | REST | RPC |
|---|---|---|
| Built around | Resources (nouns in URLs) | Operations (verbs in the message) |
| HTTP methods | GET, POST, PUT, PATCH, DELETE with their standard meaning | Usually POST for everything (or not HTTP at all, as with NETCONF over SSH) |
| Endpoints | Many URLs, one per resource | Often one endpoint |
| Result and errors | HTTP status code plus body | Inside the reply body (`result`/`error`, `<rpc-error>`, SOAP fault) |
| Caching and idempotency | Built on HTTP semantics (GETs cacheable, PUT idempotent) | Defined per operation |
| Fits | CRUD on objects, web and controller APIs | Actions and commands, tightly specified operations, high-performance streaming (gRPC) |

## Synchronous APIs

The client sends a request and **waits**; the response contains the result. `GET /devices` returns the list; `PATCH /vlans/30` returns the updated VLAN. Simple to program, one round trip, but the client blocks, and if the operation takes longer than the client, proxy or gateway timeout, the call fails (`504`) even though the server may still be working.

## Asynchronous APIs

For long-running work (discovering a network, pushing templates to 200 devices, generating a report), the server **accepts** the job and answers at once, and the client gets the result **later**. The usual HTTP pattern is **202 Accepted plus a task id**:

```text
1. POST /dna/intent/api/v1/discovery  {...}                    client -> server
2. 202 Accepted {"response": {"taskId": "<id>",
                  "url": "/dna/intent/api/v1/task/<id>"}}      server -> client
3. GET  /dna/intent/api/v1/task/<id>                            client polls
4. 200 OK {"response": {"progress": "...", "isError": false}}   no endTime yet: wait, poll again
5. GET  /dna/intent/api/v1/task/<id>
6. 200 OK {"response": {"endTime": 1764000000000, "isError": false, ...}}   finished
```

Three ways the client learns the outcome:

- **Polling a task or status URL** (above): simple; poll at a sensible interval with a time limit.
- **Callback / webhook**: the client supplies a URL and the server POSTs the result when the job ends (lesson 2.2).
- **Status in a header**: some APIs return `Location` or a custom header with the status-monitor URL.

> **Watch out:** `202 Accepted` means "queued", not "succeeded". Catalyst Center's documentation shows a POST that returns `202` while the task itself fails (a duplicate discovery name). Always check the task's final state: in Catalyst Center, `isError` and `failureReason`, with `endTime` present once it has finished.

Inside a program, "asynchronous" can also mean **non-blocking client code** (Python `asyncio` with an async HTTP library), where your code sends many requests and handles responses as they arrive. That is a client-side technique; the API itself can still be synchronous.

| | Synchronous | Asynchronous |
|---|---|---|
| Response contains | The result | An acknowledgement (`202`) and a way to get the result |
| Client during the work | Waits (blocks) | Free; checks back or is called back |
| Good for | Quick reads and small changes | Long jobs, bulk changes, reports |
| Failure mode | Timeouts on slow operations | Forgetting to check the task, or polling too fast |
| Examples | Meraki `GET /organizations`; RESTCONF `GET` | Catalyst Center tasks (discovery, template deployment); Meraki action batches submitted without `synchronous: true` (synchronous batches are limited to 20 actions) |

> **Exam tip:** "The verb is in the URL path or body and everything is a POST to one endpoint" is RPC. "Resources with GET/POST/PUT/DELETE" is REST. "Returns `202` with a task id" is asynchronous. "Client waits for the answer in the same response" is synchronous.

## Lab it yourself

Any computer with Python 3 and curl; the DevNet Sandbox for the Cisco steps:

1. In Python, build a JSON-RPC 2.0 request dictionary with `jsonrpc`, `method`, `params` and `id`, and print it with `json.dumps()`. Then build the REST equivalent as a method plus URL. Note where the verb lives in each.
2. `curl -i https://httpbin.org/delay/3` is a synchronous call that takes three seconds; add `--max-time 1` to see what a client timeout does to it.
3. In the always-on Catalyst Center sandbox, read the "Asynchronous API" page in the Catalyst Center documentation, then call any endpoint that returns a `taskId` that the read-only sandbox allows (or study the example in the documentation), and poll `/dna/intent/api/v1/task/<taskId>` until `endTime` appears.
4. If you have an IOS XE sandbox reservation, compare a NETCONF `<get-config>` (RPC) with a RESTCONF `GET` (REST) for the same interface data.

## Key takeaways

- REST: resources in URLs, standard HTTP methods as verbs, stateless, results in status codes.
- RPC: named operations with parameters, usually one endpoint and POST; XML-RPC, JSON-RPC, SOAP, gRPC and NETCONF (`<rpc>` over SSH) are RPC styles.
- Synchronous: the result arrives in the response; simple but limited by timeouts.
- Asynchronous: `202 Accepted` plus a task id or status URL; poll it, or receive a callback; always check the final status.
- REST vs RPC and synchronous vs asynchronous are independent choices.
