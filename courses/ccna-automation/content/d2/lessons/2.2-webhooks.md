## Polling versus webhooks

There are two ways for your code to learn that something changed on a platform, such as a switch going offline in Meraki or a new message arriving in a Webex space:

- **Polling.** Your script asks on a timer: `GET /devices/availabilities` every 60 seconds. Simple, works through any firewall because you open the connection, but wasteful: most polls return "nothing new", every poll counts against the rate limit (lesson 2.3), and an event that happens just after a poll waits up to a full interval.
- **Webhooks.** You register a URL with the platform once. When the event happens, the **platform** sends an HTTP request (almost always a `POST` with a JSON body) **to your URL**. No wasted calls and near-real-time delivery, but you must run a web server that the platform can reach.

A webhook is an **event-driven callback over HTTP**: a "reverse API" where the roles flip and the platform becomes the client. It is the Observer pattern from lesson 1.6 across the network: registering is `attach`, the POST is `notify`.

| | Polling | Webhook |
|---|---|---|
| Who opens the connection | Your script | The platform |
| Latency | Up to one polling interval | Seconds |
| API calls used | One per interval, even when nothing changes | One per event, made by the platform |
| What you must run | A script with a timer | An HTTPS listener reachable from the platform |
| Works behind NAT without changes | Yes | No: needs a public URL, a reverse proxy or a tunnel |
| Missed events | You see current state next poll | Possible if your receiver is down and retries give up |

## The usage pattern

```text
1. Your app  --- POST /webhooks {targetUrl, resource, event, secret} --->  Platform
2. Platform  --- 200 OK {"id": "<webhook id>"} -------------------------->  Your app
      ... later, the event happens on the platform ...
3. Platform  --- POST https://hooks.example.com/meraki  (JSON payload) -->  Receiver
4. Receiver checks the secret or signature, queues the work
5. Receiver  --- 200 OK (quickly, little or no body) -------------------->  Platform
6. Your code may call the API for full details  (GET /messages/{id}, ...)
```

The parts:

- **Receiver URL** (Webex calls it `targetUrl`): an HTTPS endpoint you own, such as `https://hooks.example.com/meraki`. It must be reachable from the platform's cloud, so a laptop on a private network needs a reverse proxy or a tunnelling service for testing.
- **Subscription or registration**: you choose which events. Webex registers webhooks through its API with a `resource` (for example `messages`) and an `event` (for example `created`) plus an optional filter. Meraki configures webhook receivers ("HTTP servers") per network and sends alerts that you enable in the alert settings or through the API.
- **Payload**: a JSON document describing the event. It is often a **notification, not the full data**. Webex message webhooks, for example, carry the message id but not the encrypted message text: your code must `GET` the message with its own token.
- **Acknowledgement**: answer with a `2xx` status quickly. Do the slow work (calling other APIs, opening a ticket) afterwards, from a queue or background task. A receiver that takes too long or answers with an error looks like a failed delivery.

## Verifying that the request really came from the platform

Your receiver URL is public, so anyone can POST to it. Platforms give you a way to prove the sender:

| Method | How it works | Example |
|---|---|---|
| **Shared secret in the payload** | You set a secret when you configure the receiver; the platform includes it in each payload and you compare it | Meraki webhooks carry a `sharedSecret` field in the JSON body |
| **HMAC signature header** | You set a secret; the platform computes an HMAC of the **raw body** with it and sends the result in a header; you recompute it and compare | Webex sends `X-Spark-Signature`, an HMAC-SHA1 of the raw body keyed with the secret you registered |
| **Transport controls** | HTTPS only, optionally allow-listing the platform's source addresses or using mutual TLS | Common in addition to one of the above |

An HMAC signature is stronger than a secret in the payload because the secret itself never travels; an attacker who sees one delivery cannot forge the next, and any change to the body breaks the signature. Rules for checking it:

1. Compute the HMAC over the **exact raw bytes** received, before parsing the JSON. Re-serialising changes spacing and key order and breaks the comparison.
2. Compare with a **constant-time** function (`hmac.compare_digest` in Python), not `==`.
3. Reject with `401` or `403` (or just drop) when it does not match, and process nothing.

A receiver check for an HMAC-SHA1 header, standard library only:

```python
import hashlib
import hmac

WEBHOOK_SECRET = b"example-secret-not-real"   # load from an environment variable in real code

def signature_is_valid(raw_body: bytes, received_signature: str) -> bool:
    expected = hmac.new(WEBHOOK_SECRET, raw_body, hashlib.sha1).hexdigest()
    return hmac.compare_digest(expected, received_signature)
```

Payload with a shared secret, using the common fields Meraki documents for its webhook alerts (values invented):

```json
{
  "version": "0.1",
  "sharedSecret": "example-secret-not-real",
  "sentAt": "2026-11-22T14:05:11.123456Z",
  "organizationId": "123456",
  "organizationName": "Example Corp",
  "networkId": "N_1001",
  "networkName": "HQ",
  "alertId": "0000000000000001",
  "alertType": "Settings changed",
  "occurredAt": "2026-11-22T14:05:10.000000Z",
  "alertData": {}
}
```

Meraki also requires the receiver URL to be HTTPS on a public server with a valid certificate, and its optional payload templates let you reshape the body or move the secret into a header.

## Retries, duplicates and ordering

Delivery is **at least once**, not exactly once:

- If your receiver is down, times out, or answers with a non-`2xx` status, most platforms **retry** a few times with increasing delays, and some disable a webhook that keeps failing. Check the platform's documentation for its exact policy rather than assuming one.
- A retry after a lost acknowledgement means you can receive the **same event twice**. Make processing **idempotent**: record the event id and ignore repeats.
- Events can arrive **out of order**. Use the timestamp in the payload (`sentAt`, `created`), not arrival order.
- A webhook tells you something happened; if you must not miss anything, combine it with an occasional reconciliation poll.

> **Exam tip:** "Get notified as soon as an event happens without repeatedly calling the API" is a webhook. "The platform sends an HTTP POST to a URL you registered" is a webhook. If the stem says the script asks every N seconds, that is polling.

> **Real world:** For a quick test receiver you can paste the URL from a request-inspection service into the platform, or run a small Flask app behind a tunnel. Never point a production webhook at a service that logs your payloads publicly.

## Lab it yourself

Any computer with Python 3 and curl, entirely on your own machine:

1. Save the `signature_is_valid` function in a file, then compute a signature for a test body in Python: `hmac.new(b"example-secret-not-real", b'{"event":"created"}', hashlib.sha1).hexdigest()`.
2. Call `signature_is_valid` with that body and signature (it returns `True`), then change one character of the body (it returns `False`).
3. Write a receiver with `http.server.BaseHTTPRequestHandler` that reads `Content-Length` bytes in `do_POST`, checks the `X-Spark-Signature` header with your function, and answers `200` or `401`. Run it on `127.0.0.1:8000`.
4. From a second terminal, `curl -i -X POST http://127.0.0.1:8000/hook -H "Content-Type: application/json" -H "X-Spark-Signature: <the hex value>" -d '{"event":"created"}'` and then repeat with a wrong signature. On Windows, use `curl.exe` and send the body from a file with `-d @body.json` (see lesson 2.1); the file must contain exactly the bytes you signed, with no trailing newline.
5. Optional, with a Webex developer account: read the Webex webhooks guide and register a `messages`/`created` webhook pointing at a test URL to see a real payload.

## Key takeaways

- A webhook is an HTTP callback: you register a URL and the platform POSTs a JSON payload to it when an event happens.
- Compared with polling: near-real-time, far fewer API calls, but you must run a receiver the platform can reach.
- The payload is often a notification; fetch full details with the API if needed.
- Answer `2xx` quickly and do the slow work afterwards.
- Verify the sender: a shared secret in the payload (Meraki `sharedSecret`) or an HMAC signature header over the raw body (Webex `X-Spark-Signature`), compared in constant time.
- Expect retries, duplicates and reordering: make processing idempotent and keyed on the event id.
