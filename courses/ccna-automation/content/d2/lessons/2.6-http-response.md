## Three parts

An HTTP response has the same shape as a request (lesson 2.1):

1. **Status line**: protocol version, **status code**, reason phrase.
2. **Headers**: `Name: value` lines describing the response and its body, ending with a blank line.
3. **Body** (RFC 9110 calls it *content*): the data itself, if any.

Topic 2.6 asks you to read each part and say what it tells you.

## A fully annotated response

The response to `GET /api/v1/networks/N_1001/devices?perPage=2`:

```http
HTTP/1.1 200 OK
Date: Sun, 22 Nov 2026 14:05:11 GMT
Content-Type: application/json; charset=utf-8
Content-Length: 178
Cache-Control: no-cache
Link: <https://api.example.com/api/v1/networks/N_1001/devices?perPage=2&startingAfter=Q2XX-0002>; rel="next"
X-Request-Id: 7f3c9a2e-0000-4000-8000-000000000001

[
  {"serial": "Q2XX-0001", "name": "sw01", "model": "MS250-48", "lanIp": "10.10.20.11"},
  {"serial": "Q2XX-0002", "name": "sw02", "model": "MS250-48", "lanIp": "10.10.20.12"}
]
```

| Line | Part | What it tells you |
|---|---|---|
| `HTTP/1.1 200 OK` | Status line | Version `HTTP/1.1`, code `200`, reason phrase `OK`. Your code tests the number; the phrase is informational |
| `Date` | Header | When the server generated the response (always GMT) |
| `Content-Type: application/json; charset=utf-8` | Header | The body is JSON encoded as UTF-8, so parse it with `json.loads()` or `response.json()` |
| `Content-Length: 178` | Header | The body is 178 bytes long |
| `Cache-Control: no-cache` | Header | Caches must revalidate before reusing this response |
| `Link: <...>; rel="next"` | Header | There is another page; this is its URL (RFC 8288, lesson 2.3) |
| `X-Request-Id` | Header | Vendor-specific correlation id; quote it when you open a support case |
| (blank line) | | End of the headers |
| `[ {...}, {...} ]` | Body | The data: a JSON array of two device objects |

## The status line

```text
HTTP/1.1  404  Not Found
version   code reason phrase
```

The code is the machine-readable result (lesson 2.4). In HTTP/2 and HTTP/3 the reason phrase is not sent at all, and libraries invent it, which is another reason to test the number. In `requests` it is `response.status_code`, with `response.reason` for the phrase.

## Headers worth recognising

| Header | Appears with | Meaning |
|---|---|---|
| `Content-Type` | Any response with a body | Media type of the body: `application/json`, `application/xml`, `application/yang-data+json`, `application/problem+json`, `text/html` |
| `Content-Length` | Most responses with a body | Body size in bytes (not characters) |
| `Location` | `201`, `3xx` | URL of the new resource (201) or where to go (3xx) |
| `Allow` | `405` (required), `OPTIONS` | Methods the resource supports |
| `WWW-Authenticate` | `401` (required) | The authentication scheme expected, for example `Basic realm="api"` or `Bearer error="invalid_token"` |
| `Retry-After` | `429`, `503`, `3xx` | Seconds to wait, or an HTTP date |
| `ETag`, `Last-Modified` | Cacheable responses | Version identifiers for conditional requests (`If-None-Match`, `If-Modified-Since`) and safe concurrent updates |
| `Cache-Control` | Any | Caching rules (`no-store`, `max-age=60`) |
| `Link` | Paginated lists | `rel="next"`, `rel="prev"`, `rel="first"`, `rel="last"` URLs |
| `Set-Cookie` | Session-based logins | A session cookie to send back (some APIs authenticate this way) |
| `X-...` headers | Vendor-specific | Rate-limit counters, request ids and similar. The `X-` prefix is a convention, not a standard |

Header **names are case-insensitive** (`content-type` and `Content-Type` are the same header; HTTP/2 sends them in lower case). `requests` stores them in a case-insensitive dictionary, so `response.headers["content-type"]` works.

## The body

- Its format is whatever `Content-Type` says. Do not assume JSON: an error page from a proxy or load balancer in front of the API is often `text/html`, and calling `.json()` on it raises an exception.
- It can legitimately be **empty**: always for `204 No Content` and `304 Not Modified`, always for responses to `HEAD`, and often for `202` or `DELETE`.
- Error responses usually have a body explaining the problem: read it before you guess.
- Cisco APIs often wrap the data: Catalyst Center returns `{"response": [...], "version": "1.0"}`, so the list is at `body["response"]`, while Meraki returns the bare list or object.

A `201` and a `204` side by side:

```http
HTTP/1.1 201 Created
Location: /api/v1/networks/N_1001/vlans/30
Content-Type: application/json
Content-Length: 57

{"vlanId": 30, "name": "voice", "subnet": "10.30.0.0/24"}
```

```http
HTTP/1.1 204 No Content
Date: Sun, 22 Nov 2026 14:07:42 GMT
```

The 204 ends after its headers: there is nothing to parse.

> **Exam tip:** Expect "Refer to the exhibit" items that ask what a header means (`Location` after a POST, `Allow` after a 405, `Retry-After` after a 429), what type the body is, or how many items it contains. Read the status line first, then `Content-Type`, then the body.

## Seeing the parts yourself

| Tool | Status line and headers | Body |
|---|---|---|
| `curl -i URL` | Printed before the body | After the blank line |
| `curl -I URL` | Sends HEAD and shows headers only | None |
| `curl -v URL` | Request lines start with `>`, response with `<` | After the headers |
| Python `requests` | `r.status_code`, `r.reason`, `r.headers` | `r.text` (string), `r.content` (bytes), `r.json()` (parsed) |
| Postman | Status and Headers tabs | Body tab (Pretty or Raw) |

## Lab it yourself

Any computer with curl and Python 3:

1. `curl -i https://httpbin.org/json` and label the status line, each header and the body. Check `Content-Length` against the body.
2. `curl -I https://httpbin.org/json` and compare: same headers, no body.
3. `curl -i https://httpbin.org/status/204` and confirm the response stops after the headers.
4. `curl -i https://httpbin.org/html`: note the `Content-Type`. In Python, `requests.get("https://httpbin.org/html", timeout=10).json()` raises an exception; that is what happens when a proxy returns an HTML error page to your script.
5. In the Catalyst Center sandbox, call the network-device list and find where the list sits inside the body.

## Key takeaways

- A response is status line (version, code, reason phrase), headers, blank line, body.
- The code is what your code tests; the reason phrase is cosmetic and absent in HTTP/2.
- `Content-Type` says how to parse the body; `Content-Length` is its size in bytes.
- Know the headers that carry instructions: `Location` (201, 3xx), `Allow` (405), `WWW-Authenticate` (401), `Retry-After` (429, 503), `Link` (pagination).
- Header names are case-insensitive; `X-` headers are vendor-specific.
- The body can be empty (204, 304, HEAD) and is not always JSON: check `Content-Type` before calling `.json()`.
