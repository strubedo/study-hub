## Three pieces of evidence

Topic 2.5 hands you a failed call and asks for the cause and the fix. You always have three things to compare:

1. **The response**: the status code first, then the headers (`WWW-Authenticate`, `Allow`, `Retry-After`, `Location`, `Content-Type`) and the error body, which often names the problem outright.
2. **The request** that was actually sent: method, full URL, headers and body. Not the one you meant to send; the one in the exhibit or in `curl -v` output.
3. **The documentation** for that endpoint: required method, path and query parameters, headers, body schema and the documented responses.

The cause is almost always a difference between 2 and 3, and the code in 1 tells you which part of the request to look at.

## A method that works every time

1. **Read the class.** 4xx: the request is wrong, keep reading. 5xx: the server is struggling; check the provider's status, retry with backoff, and only then suspect the request (a malformed request can crash a buggy server into a 500). No status code at all (connection refused, DNS failure, TLS error, timeout) means the request never got an HTTP answer: troubleshoot the network path, the host name, the port, the certificate and proxies.
2. **Map the code to the part of the request** (table below).
3. **Compare that part with the documentation**, character by character: path spelling and case, version segment, path parameter value, header name, media type.
4. **Read the error body and the diagnostic headers.**
5. **Change one thing and resend**, ideally with curl `-v` or Postman so you see exactly what goes out.

| Code | Look at | Usual suspects |
|---|---|---|
| 400 | Body and query parameters | Invalid JSON (single quotes, trailing comma), missing required field, wrong data type, unknown parameter |
| 401 | Authentication header | Missing header, wrong scheme (`Bearer` vs `Basic`), wrong header name, typo or whitespace in the token, expired token |
| 403 | The account or key, not the request syntax | Read-only role, key without the needed scope, organisation or tenant the user cannot see, IP not allowed |
| 404 | The URL | Typo, case, missing or wrong version (`/v1/`), wrong path parameter (id from another environment), resource deleted, trailing path segment |
| 405 | The method | POST where the documentation says PUT, or a method sent to the collection URL instead of the item URL. Read `Allow` |
| 406 | `Accept` | Asking for a media type the endpoint cannot produce |
| 409 | Current state | Object already exists; someone else changed it |
| 415 | `Content-Type` | Missing, misspelt, or a type the endpoint does not accept (form data to a JSON endpoint; `application/json` to a RESTCONF endpoint that wants `application/yang-data+json`) |
| 422 | Field values | Value out of range, invalid combination |
| 429 | Call rate | Loop without throttling; several scripts sharing one key or organisation; honour `Retry-After` |
| 5xx | Server and path | Outage, maintenance, overloaded back end, gateway timeouts on large queries |

## Worked troubleshooting table

| Symptom (request and response) | Likely cause | Fix |
|---|---|---|
| `GET /api/v1/organizations` with header `Authorization: <YOUR_API_KEY>` returns `401` | Scheme word missing; the server expects `Bearer <key>` | Send `Authorization: Bearer <YOUR_API_KEY>` |
| Catalyst Center script worked for an hour, then every call returns `401` | Token expired (60-minute lifetime) | Request a new token from `/dna/system/api/v1/auth/token` and retry once |
| `X-Auth-Token` header sent to an API whose documentation says `Authorization: Bearer` returns `401` | Wrong header name: the server sees no credentials | Use the header the documentation names |
| Valid key, `PUT /networks/N_1001/vlans/30` returns `403`, GET on the same URL works | The key belongs to a read-only administrator | Use an account or key with write permission |
| `GET /api/v1/network/N_1001/vlans` returns `404`; documentation says `/networks/{networkId}/vlans` | Path typo (`network` vs `networks`) | Correct the path |
| `GET /api/v2/devices` returns `404` on a platform that only offers v1 | Wrong version segment | Use the documented version |
| `POST /api/v1/devices/42` returns `405` with `Allow: GET, PUT, PATCH, DELETE` | POST is for the collection; to change item 42 use PUT or PATCH | Use PATCH (or PUT with the full object) on the item, or POST to `/devices` to create |
| `POST /devices` with a JSON body returns `415`; request shows `Content-Type: application/x-www-form-urlencoded` | curl `-d` (or `requests` `data=` with a dict) labelled the body as form data | Add `Content-Type: application/json` (curl `--json`, `requests` `json=`) |
| `POST /devices` returns `400` with `{"error": "Expecting property name enclosed in double quotes"}` | The body is not valid JSON (single quotes or a trailing comma) | Build the body with `json.dumps()` or `json=`, never by hand |
| `POST /vlans` with `{"vlanId": 5000, "name": "x"}` returns `422` with "vlanId must be 1-4094" | Valid JSON, invalid value | Correct the value |
| Second run of a create script returns `409` | The object was created by the first run | Check for existence first or switch to an idempotent PUT if the API supports it |
| Loop over 500 devices starts returning `429` after about 10 calls a second | Rate limit | Sleep for `Retry-After`; throttle; use an organisation-wide endpoint |
| Script lists exactly 1,000 of 2,400 devices, all calls `200` | Pagination ignored | Follow `Link rel="next"` or the cursor until none remains |
| `POST` to `http://` URL is redirected (`301`) and the follow-up fails or returns the collection | The redirected request was turned into a GET | Use the `https://` URL directly |
| Intermittent `502`/`504` on a huge report query, small queries fine | Back end too slow for the gateway timeout | Narrow the query (time span, filters, page size) or use the async/report API |
| Every call fails with no status code: "certificate verify failed" | Self-signed or private-CA certificate on a lab appliance | Trust the CA (`verify="/path/ca.pem"`); do not use `verify=False` outside a lab |

## Reading a full exchange

```http
PATCH /api/v1/networks/N_1001/vlans/30 HTTP/1.1
Host: api.example.com
Authorization: Bearer <YOUR_API_KEY>
Content-Type: text/plain
Content-Length: 16

{"name": "voip"}

HTTP/1.1 415 Unsupported Media Type
Accept: application/json, application/merge-patch+json
Content-Type: application/json
Content-Length: 50

{"error": "Content-Type must be application/json"}
```

The code points at the body's format label. The request labels JSON as `text/plain`; the server even lists, in an `Accept` response header (RFC 9110 suggests exactly this for 415), the types it would take. The method, path and authentication are fine: a wrong path would be `404`, a bad key `401`. Fix: `Content-Type: application/json`.

> **Exam tip:** Start from the code, then find the one line in the request that the code is about. 401: the auth header. 403: the account. 404: the path. 405: the method. 415: `Content-Type`. 400 and 422: the body. 429: the call rate.

> **Real world:** When a call works in Postman but not in your script, compare the two requests side by side. Postman's console shows the exact headers it sent; in Python, `response.request.headers`, `response.request.url` and `response.request.body` show what `requests` actually sent.

## Lab it yourself

Any computer with curl or Postman:

1. Send `curl -i -X POST https://httpbin.org/post -d '{"name": "voip"}'` and look at the `headers` echoed back: the `Content-Type` is form data, which is the root cause of many 415s. (On Windows use `curl.exe` and `-d @body.json`, as lesson 2.1 explains.)
2. `curl -i https://httpbin.org/basic-auth/alice/example-password` (no credentials) returns `401` with a `WWW-Authenticate` header; add `-u alice:example-password` and get `200`; use a wrong password and get `401` again.
3. `curl -i -X DELETE https://httpbin.org/get` and read the `405` and its `Allow` header.
4. In a DevNet sandbox, break one thing at a time in a working call (header name, path, method, body) and record the code each mistake produces. Build your own symptom table.

## Key takeaways

- Compare three things: the response, the request actually sent, and the documentation.
- The code tells you which part of the request to inspect: 401 auth header, 403 permissions, 404 path, 405 method, 415 `Content-Type`, 400/422 body, 429 rate.
- Diagnostic headers matter: `WWW-Authenticate` (401), `Allow` (405), `Retry-After` (429, 503), `Location` (201, 3xx), `Accept` (415).
- Read the error body before guessing.
- A 200 with missing data usually means pagination; no status code at all means a network, DNS, TLS or timeout problem.
- Change one thing at a time, and look at the real request with `curl -v`, Postman's console or `response.request`.
