## The three service types

Cloud services are grouped by how much of the stack the provider manages for you. The more the provider manages, the less control and responsibility you have, and the less administration work you do.

| | IaaS | PaaS | SaaS |
|---|---|---|---|
| What you get | Virtualized compute, storage and network | A managed platform to build and run apps | A finished application |
| You manage | OS, middleware/runtime, applications, data, identities | Applications and data, configuration, identities | Your data, users/identities, how it is configured and used |
| Provider manages | Physical datacenter, hosts, network (and the virtualization layer) | Everything IaaS does plus the OS and runtime | Nearly everything |
| Control | Most | Moderate | Least |
| Azure examples | Azure Virtual Machines, virtual networks, Azure Disk Storage | Azure App Service, Azure SQL Database, Azure Functions, Azure Storage | Microsoft 365, Dynamics 365 |

(The service examples above are the ones Microsoft uses when explaining the shared responsibility model.)

## Infrastructure as a service (IaaS)

IaaS is the closest to running your own datacenter, minus the hardware. You rent virtual machines, disks and virtual networks and then you are responsible for the guest operating system (patching, hardening), installed software and applications, and data.

**Use cases:**

- **Lift and shift** migration: move existing servers to Azure with minimal change.
- **Test and development** environments you can create and delete quickly.
- **Hosting workloads that need OS-level control**: custom software, specific OS versions or third-party agents.
- **Extending capacity** or running a **disaster recovery** copy of on-premises servers.
- Storage, backup and recovery, and high-performance computing.

**Trade-off:** most flexibility, most administrative work. You pay for the VM while it is allocated and you own patching.

## Platform as a service (PaaS)

PaaS gives you a managed environment to deploy applications. The provider handles the underlying servers, operating system, patching, and runtime; you focus on your code, configuration and data. Many PaaS services scale and provide high availability features built in.

**Use cases:**

- **Web and mobile app hosting** on Azure App Service without managing web servers.
- **Managed databases** such as Azure SQL Database where Microsoft handles patching and backups.
- **Development frameworks and DevOps:** developers build on a consistent platform.
- **Serverless and event-driven code** with Azure Functions.
- Analytics and business-intelligence platforms.

**Trade-off:** faster development and less administration, but less OS-level control and some platform constraints.

> **Exam tip:** "You want to deploy a web application without managing servers or the operating system" is PaaS. "You need to install custom software on a specific OS version" is IaaS.

## Software as a service (SaaS)

SaaS delivers a complete application, usually through a browser or client, from the provider. You do not manage the infrastructure, OS or application code. You manage your tenant: user accounts and licenses, configuration, your data, and the devices that access it.

**Use cases:** email and collaboration (Microsoft 365), customer relationship management and business applications (Dynamics 365), and any standard off-the-shelf application where you want to avoid maintaining software.

**Trade-off:** least administration and quickest to adopt, but limited ability to customize beyond what the vendor allows.

## Choosing a type and responsibility

The model you pick determines who is responsible for what (see lesson 1.1):

- **IaaS:** customer owns OS, applications, data, identities, devices.
- **PaaS:** Microsoft owns the OS and runtime; customer owns applications, data, identities.
- **SaaS:** Microsoft owns almost all; customer still owns data, identities and devices.

Many solutions mix types: for example an IaaS VM running a legacy app, a PaaS database, and SaaS email. A rough decision rule:

| Requirement | Pick |
|---|---|
| Maximum control over the OS and installed software | IaaS |
| Focus on code, no server administration | PaaS |
| Just use an existing business application | SaaS |
| Migrate quickly with the fewest changes | IaaS (lift and shift) |

> **Watch out:** Serverless (Azure Functions) is not a separate service type. Treat it as a PaaS-style offering. Also, "Azure Storage" is PaaS in Microsoft's shared responsibility listing, while Azure Disk Storage attached to a VM is IaaS.

## Try it in the portal

In the portal's **Create a resource** page, create nothing, but compare the options: a **Virtual machine** (IaaS: you choose image, size, disk, and administer the OS), an **App Service web app** (PaaS: you choose a runtime stack, not an OS to patch), and **SQL Database** (PaaS: no server OS to manage). Then open the Microsoft 365 admin center, if you have a trial tenant, as a SaaS example: you manage users and licenses, not servers. Delete anything you create.

## Key takeaways

- IaaS = virtual infrastructure; you manage the OS and above. Examples: Virtual Machines, virtual networks.
- PaaS = managed platform; you manage apps and data. Examples: App Service, Azure SQL Database, Azure Functions.
- SaaS = finished application; you manage data, identities, settings and devices. Examples: Microsoft 365, Dynamics 365.
- More provider management means less control and less admin work.
- IaaS fits lift-and-shift and OS-level control; PaaS fits app hosting and managed databases; SaaS fits standard business applications.
- Data, devices and identities remain the customer's responsibility in every model.
