## What cloud computing is

Cloud computing is the delivery of computing services (servers, storage, databases, networking, software, analytics) over the internet from a provider's datacenters, on demand and billed for what you use. You do not buy and rack hardware: you provision a resource, use it, and stop paying when you delete it. The provider owns, houses and maintains the physical infrastructure; you consume the service through a portal, API or command line.

Two properties define the experience. **On-demand self-service** means a resource exists minutes after you ask for it. **Consumption-based billing** means you pay for what you use rather than for capacity you might need one day. Both flow from the provider operating huge shared datacenters (economies of scale).

## The shared responsibility model

Security and operations are split between the cloud provider and the customer, and the split moves with the service type. Microsoft's framing is a stack of layers, from the physical datacenter at the bottom to data and identities at the top.

**Always the customer's responsibility, in every model including on-premises:**

- Information and data
- Devices (the endpoints and clients that access the service); Microsoft's matrix marks client devices as shared only for SaaS, because Microsoft can offer some device management, but protecting endpoints stays with you
- Accounts and identities (users, access management, MFA, role assignments)

**Always Microsoft's in any cloud model:** the physical datacenter, the physical network and the physical hosts. In an on-premises datacenter you own those too.

**Moves by service type:**

| Layer | On-premises | IaaS | PaaS | SaaS |
|---|---|---|---|---|
| Information and data | Customer | Customer | Customer | Customer |
| Accounts and identities | Customer | Customer | Customer | Customer |
| Devices (clients) | Customer | Customer | Customer | Shared |
| Applications | Customer | Customer | Shared | Shared |
| Network controls | Customer | Customer | Shared | Microsoft |
| Operating system | Customer | Customer | Microsoft | Microsoft |
| Physical hosts, network, datacenter | Customer | Microsoft | Microsoft | Microsoft |

The pattern: moving from on-premises toward SaaS, responsibility transfers to Microsoft from the bottom of the stack upward, but the top layers (data, identities and, in practice, endpoint devices) never fully transfer.

> **Exam tip:** "Who is responsible for patching the guest operating system?" The customer in IaaS, Microsoft in PaaS and SaaS. "Who is responsible for the physical security of the datacenter?" Microsoft, in any cloud model. "Who is responsible for the data?" The customer, always.

> **Watch out:** In a hybrid design the shared responsibility model applies per workload, not per organization. The on-premises half is fully the customer's.

## Cloud models: public, private, hybrid

| Model | Who owns the infrastructure | Typical use case |
|---|---|---|
| **Public cloud** | A cloud provider (such as Microsoft), shared by many customers (tenants) over the internet | Variable workloads, new apps, dev/test, no upfront hardware, rapid scale |
| **Private cloud** | The organization itself (on-premises) or hosted for it alone; cloud-like self-service and virtualization, single organization | Strict control or regulatory needs, existing hardware investment |
| **Hybrid cloud** | A combination of public and private (on-premises) connected so workloads can use both | Keep sensitive or legacy systems on-premises while using the cloud for burst capacity, new services or disaster recovery |

Key differences: in a **public** cloud you have no capital expenditure for hardware and the provider maintains it; in a **private** cloud the organization keeps full control but pays for and maintains the hardware (unless hosted); **hybrid** offers the most flexibility to place each workload where it fits. Azure services that support hybrid designs include Azure Arc, VPN Gateway and ExpressRoute (covered later in the course).

**Multi-cloud** means using more than one public cloud provider. It is not a synonym for hybrid.

> **Exam tip:** "Keep customer records in your own datacenter but run the web front end on Azure and burst for peak load" is hybrid. "Meet a requirement to run entirely in your own facility with self-service" is private.

## The consumption-based model and pricing

In the consumption-based model there is no upfront purchase and no fixed capacity: you pay for what you use, and prices are per unit (per second, hour, GB, execution, and so on). Compare the two accounting views:

- **CapEx (capital expenditure):** a large upfront spend on physical assets (servers, networking, datacenter space), recorded as an asset and depreciated. Typical of on-premises.
- **OpEx (operational expenditure):** ongoing spend on services as you use them. Typical of the cloud; you can scale spending up or down with demand and there is no capacity to write off.

Benefits of consumption-based pricing: no upfront cost, no paying for idle capacity you can switch off, no need to forecast capacity years ahead, and you can stop paying when you stop using.

### Pricing models (concepts)

| Model | Idea | Best for |
|---|---|---|
| **Pay-as-you-go** | Pay the standard rate for what you consume, no commitment | Unpredictable or short-lived workloads, experiments |
| **Reservations** | Commit to a specific resource configuration (such as a VM size in a region) for one or three years in return for a discount | Steady, predictable workloads that won't change |
| **Savings plan** | Commit to a fixed hourly spend for one or three years; discount applies flexibly across eligible services and regions | Dynamic or evolving workloads that still have a steady baseline of spend |
| **Spot** | Use Azure's spare capacity at a deep discount; Azure can evict you when it needs the capacity back, with no availability guarantee | Interruptible work: batch jobs, rendering, dev/test |

> **Watch out:** Reservations and savings plans trade flexibility for a lower rate; you pay the commitment whether or not you use it. Spot is the only one whose workloads can be taken away.

## Serverless

Serverless computing lets you run code or a workflow without provisioning or managing servers. Servers still exist; the provider manages them. Characteristics:

- You do not manage the infrastructure or operating system.
- It **scales automatically** with demand, including down to zero.
- Billing is consumption-based, often per execution and resource time, so idle time can cost nothing (depends on the plan).
- It is event-driven: a trigger such as an HTTP request, a queue message or a timer starts the code.

Azure examples: **Azure Functions** (code) and **Azure Logic Apps** (workflows). Serverless sits at the more-managed end of PaaS.

> **Exam tip:** "Run a small piece of code in response to an event, pay only when it runs, no servers to manage" is Azure Functions / serverless.

## Try it in the portal

With a free account (or the Learn sandbox) open the Azure portal and choose **Create a resource**. Note that creating a virtual machine asks you for a size and region (IaaS, you manage the OS), then look at **Function App** (serverless; no VM size, consumption-style plan option). Open **Cost Management + Billing** to see that charges appear per resource as consumed. Delete what you create.

## Key takeaways

- Cloud computing is on-demand delivery of computing services over the internet with consumption-based billing.
- Data, devices and accounts/identities are always the customer's responsibility; the physical datacenter, hosts and network are always Microsoft's in the cloud.
- OS responsibility: customer in IaaS, Microsoft in PaaS and SaaS. Applications and network controls are shared in PaaS.
- Public = provider-owned shared; private = single organization; hybrid = both connected; multi-cloud = several public providers.
- Cloud shifts spending from CapEx to OpEx.
- Pricing concepts: pay-as-you-go (no commitment), reservations (specific config, 1 or 3 years), savings plan (hourly spend commitment, flexible), spot (evictable spare capacity).
- Serverless: no server management, automatic scale, event-driven, pay for use. Azure Functions and Logic Apps.
