## Four tools, four different jobs

Governance questions on the exam are mostly "which tool?" questions. Separate them by what they control.

| Tool | Controls | Question it answers |
|---|---|---|
| Azure RBAC | Which **identities** can do which **actions** at a scope | Who is allowed to do this? |
| Azure Policy | Which **resource configurations** are allowed or required | Is this resource set up the way we require? |
| Resource locks | Whether a resource can be **deleted or changed at all**, whoever you are | Can anyone accidentally delete this? |
| Microsoft Purview | How **data** is discovered, classified, protected and audited | Where is our sensitive data and is it governed? |

RBAC and the management hierarchy were covered in domain 2. This lesson covers the other three.

## Microsoft Purview

**Microsoft Purview** is a family of data governance, risk and compliance solutions that gives you a unified view of your data across Azure, on-premises, multicloud and software-as-a-service sources, including Microsoft 365. Know the purpose rather than product detail:

- **Data governance:** discover and map data sources, scan them, classify sensitive data, and publish a searchable catalog with lineage so people can find trusted data and owners can manage it.
- **Data security and protection:** sensitivity labels and information protection, data loss prevention and insider-risk tooling help protect data wherever it lives.
- **Risk and compliance:** audit, eDiscovery, communication compliance and **Compliance Manager**, which gives a compliance score and recommended improvement actions against regulations and standards (for example ISO 27001 or GDPR).

Purview is the answer when the requirement is about **data**: "find and classify sensitive data across the estate", "understand where data came from", "assess regulatory compliance posture". It does not enforce resource settings and it does not block someone from deleting a VM.

> **Watch out:** Purview governs data and compliance posture. **Microsoft Defender for Cloud** (domain 2) assesses and hardens the security posture of Azure resources. **Azure Policy** enforces resource rules. Do not swap them.

## Azure Policy

**Azure Policy** evaluates resources against rules you define and either reports non-compliance or enforces the rule. A policy definition has an `if` condition on resource properties and a `then` effect. You **assign** a definition to a scope (management group, subscription or resource group) and child scopes inherit the assignment; you can exclude sub-scopes or grant exemptions.

Typical rules: allow only certain regions, allow only certain VM sizes, require a tag, require encryption or HTTPS, restrict resource types.

### Effects to recognise

| Effect | What it does |
|---|---|
| Audit | Allows the resource, flags it as non-compliant (warning in the activity log) |
| Deny | Blocks the create or update request |
| Append / Modify | Adds or changes properties such as tags during create or update (Modify can be remediated for existing resources) |
| DeployIfNotExists | Deploys a related resource when it is missing (for example a diagnostic setting or extension) |
| AuditIfNotExists | Flags a resource when a related resource is missing |
| Disabled | Turns the rule off (useful for testing) |

Other effects exist (such as denyAction and manual); the first six are what to remember. Microsoft recommends starting new policies with Audit to see their impact before enforcing.

### Initiatives, compliance and remediation

- An **initiative** (policy set) bundles many policy definitions into one assignable goal, such as a regulatory standard. Assign one initiative instead of fifty policies.
- The **compliance** view shows the percentage of compliant resources per assignment. Evaluation runs when resources are created or changed and on a periodic cycle (about every 24 hours), plus on demand.
- **Remediation tasks** bring existing non-compliant resources into line for DeployIfNotExists and Modify. Deny and Audit do not change existing resources; Deny affects only new or updated ones.
- Azure Policy has **built-in** definitions and supports custom ones. It is free to use for Azure resources.

> **Exam tip:** "Prevent users from creating VMs outside West Europe" or "ensure every storage account has a CostCenter tag" is Azure Policy. The user may *have* the RBAC permission to create the VM; Policy still denies a non-compliant one.

### Policy versus RBAC

RBAC controls what a **user** can do (actions). Policy controls what a **resource** may look like (properties), regardless of who is acting, even an Owner. They complement each other: an Owner can create VMs (RBAC) but not in a forbidden region (Policy).

## Resource locks

A **resource lock** prevents accidental deletion or modification. You can place a lock on a subscription, resource group or resource, and child resources **inherit** it; the most restrictive lock wins. There are two lock levels:

| Level (portal name) | Read | Modify | Delete |
|---|---|---|---|
| CanNotDelete (Delete) | Yes | Yes | No |
| ReadOnly | Yes | No | No |

Key points:

- Locks apply to **all users and roles**, including **Owners**. They override RBAC permissions. To delete a locked resource you must first remove the lock, which requires `Microsoft.Authorization/locks/*` permission (held by Owner and User Access Administrator).
- A lock applies only to **management-plane** operations sent to Azure Resource Manager. It does not stop data-plane activity: a ReadOnly lock on a storage account does not prevent reading or writing blobs through data APIs, and a lock on a SQL server does not stop SQL statements. (Some read-only side effects exist; for example a ReadOnly lock on a storage account blocks listing account keys because that is a POST management action.)
- A ReadOnly lock on a resource group stops adding, changing or deleting resources in it, so it can break things that need to write, such as an App Service that must update settings or a VM that must be started.
- A lock on a resource group stops deleting the group and the resources in it, even if the resource itself has no lock.

> **Exam tip:** "Make sure an administrator cannot accidentally delete the production resource group" = **CanNotDelete lock**. RBAC alone does not help, because the administrator may be an Owner.

> **Watch out:** Locks are not a security boundary against someone who is allowed to remove the lock. They protect against accidents.

## Choosing between them

| Requirement | Use |
|---|---|
| Only the network team can edit virtual networks | RBAC |
| All resources must be in East US or West Europe | Policy (deny) |
| Every resource must carry an Environment tag | Policy (deny or modify) |
| Nobody, including Owners, may delete the hub network | Lock (CanNotDelete) |
| Classify and map sensitive data across Azure and on-premises | Purview |
| Show compliance against a regulatory standard for resource settings | Policy initiative |

## Try it in the portal

1. Search for **Policy**, open **Definitions**, and find the built-in "Allowed locations". Select **Assign**, scope it to a test resource group, pick a single region, and keep the enforcement mode on. Then try to create a resource in a different region and read the denial.
2. Open **Compliance** to see how assignments are evaluated. Delete the assignment when finished.
3. On the same test resource group choose **Locks**, add a **Delete** lock, then try to delete the group and read the error. Remove the lock afterwards.
4. Search for **Microsoft Purview** to see how its portal is organised (some features need a licence or a Microsoft 365 tenant, so reading the overview is enough).

## Key takeaways

- RBAC answers who can act; Policy answers what resources may look like; locks stop deletion or change regardless of role; Purview governs data.
- Policy effects: audit reports, deny blocks, modify and append change properties, deployIfNotExists deploys missing companions, disabled turns it off.
- An initiative groups many policies into one assignment; remediation tasks fix existing resources for modify and deployIfNotExists.
- Policy applies even to Owners; assignments inherit down the hierarchy.
- CanNotDelete blocks deletion only; ReadOnly blocks changes and deletion.
- Locks apply to every user including Owners, are inherited, and cover the management plane only.
- Purview provides data discovery, classification, lineage, protection and compliance tooling across hybrid and multicloud sources.
