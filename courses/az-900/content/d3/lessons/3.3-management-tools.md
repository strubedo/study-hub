## Every tool talks to Azure Resource Manager

**Azure Resource Manager (ARM)** is the deployment and management layer for Azure. Whatever you use (the portal, Azure CLI, Azure PowerShell, REST API, SDKs, ARM templates, Bicep, Terraform), your request goes to ARM, which authenticates and authorizes it (Microsoft Entra ID and RBAC), then hands it to the right resource provider. Because every tool uses the same layer, the result is **consistent**: a resource created in the portal behaves the same as one created from a script, and RBAC, Policy, locks and tags apply to all of them.

ARM also lets you:

- Group resources in **resource groups** and manage them as a unit.
- Deploy, update and delete a set of related resources in one operation.
- Apply access control, tags, policies and locks at the group, subscription or resource level.
- Re-run the same deployment repeatedly with the same result (idempotent).

> **Exam tip:** If a question asks why the portal and a script produce the same permissions and policy behaviour, the answer is Azure Resource Manager.

## The Azure portal

The **Azure portal** (portal.azure.com) is a web-based graphical console for creating, configuring and monitoring resources. It is good for exploration, one-off tasks, dashboards and learning, and it needs no installation. It is also **not repeatable**: clicking through the same screens fifty times is slow and error-prone. Highlights:

- Customisable dashboards and favourites, plus global search.
- Wizards with validation, cost estimates and links to templates ("Download a template for automation" before creating a resource).
- Built-in access to Cloud Shell, Advisor, Cost Management, Monitor and Service Health.
- The same content is available in a mobile app.

## Azure Cloud Shell, Azure CLI and Azure PowerShell

**Azure Cloud Shell** is a browser-based, authenticated shell you start from the portal (or shell.azure.com or the mobile app). It comes preinstalled with Azure CLI, Azure PowerShell, Git, editors and other tools, and runs on Azure Linux. You pick **Bash** or **PowerShell** and can switch. Because it is already signed in as you, nothing is installed on your computer.

Cloud Shell can run with a storage account (an Azure Files share mounted as `clouddrive` that keeps your `$HOME` files across sessions) or as an **ephemeral session** with no storage account, where files vanish when the session ends. Machine state outside your home directory is never kept.

Both command-line tools manage Azure from a terminal, and both also run **locally** on Windows, macOS and Linux:

| | Azure CLI | Azure PowerShell |
|---|---|---|
| Command style | `az group create ...` | `New-AzResourceGroup ...` (Verb-Noun cmdlets, Az module) |
| Output | Text/JSON, works well with Bash tools | .NET objects passed down the pipeline |
| Typical user | Linux and cross-platform scripters | Windows admins and PowerShell users |
| Capability | Both manage the same Azure resources; choose by preference | |

```text
# Azure CLI
az group create --name rg-web-prod --location westeurope

# Azure PowerShell
New-AzResourceGroup -Name rg-web-prod -Location westeurope
```

> **Watch out:** Cloud Shell is not "the CLI". It is the *environment*; Azure CLI and Azure PowerShell are the tools inside it. Cloud Shell offers Bash and PowerShell, not the Windows command prompt.

Command-line tools are **scriptable and repeatable**, which the portal is not: put commands in a script and you can run them again, in a pipeline, on a schedule.

## Azure Arc

**Azure Arc** extends Azure management to resources that live **outside Azure**: on-premises datacenters, other clouds and edge locations. Arc projects those resources into Azure Resource Manager so they appear in the portal with an Azure resource ID, in a resource group, and can use Azure management features. What you can connect:

- **Arc-enabled servers:** physical or virtual Windows and Linux machines (install the Connected Machine agent).
- **Arc-enabled Kubernetes clusters:** any CNCF-conformant cluster.
- **Arc-enabled data services and SQL Server.**
- Arc-enabled VMware vSphere and System Center VMM environments, and Azure Local.

Once connected you can apply **Azure Policy**, **RBAC**, **tags**, Azure Monitor, Microsoft Defender for Cloud and Update Manager to those resources using the same tools as native Azure resources. The idea is one control plane for hybrid and multicloud.

> **Exam tip:** "Manage on-premises servers and an AWS Kubernetes cluster from the Azure portal, with Azure Policy" = **Azure Arc**. Arc does not migrate the workload to Azure; it manages it where it is.

## Infrastructure as code

**Infrastructure as code (IaC)** means defining infrastructure in text files that are deployed by a tool instead of being clicked together. Benefits: repeatable and consistent environments, fewer manual errors, version control and peer review (store files in Git), fast rebuilds for dev, test and disaster recovery, and self-documenting environments.

Two styles:

- **Declarative:** you describe the *desired end state*; the tool works out how to reach it. ARM templates, Bicep and Terraform are declarative.
- **Imperative:** you write the *steps* to run in order. Azure CLI and PowerShell scripts are imperative.

Declarative deployments are **idempotent**: running the same template twice leaves the same result and does not create duplicates.

## ARM templates and Bicep

An **ARM template** is a JSON file that declares resources. Its main sections: parameters (inputs), variables, resources (what to deploy), and outputs. You deploy it to a resource group, subscription, management group or tenant scope through the portal, CLI, PowerShell or a pipeline; ARM validates it and can deploy resources **in parallel** where there are no dependencies.

**Bicep** is a domain-specific language that is a cleaner way to author the same thing. It is **transpiled to an ARM template** at deployment, has the same capabilities as ARM templates, and is shorter and easier to read. Microsoft recommends Bicep over raw JSON for new work.

```text
resource stg 'Microsoft.Storage/storageAccounts@2023-05-01' = {
  name: 'stcontosoprod001'
  location: 'westeurope'
  sku: { name: 'Standard_LRS' }
  kind: 'StorageV2'
}
```

**Terraform** is a popular third-party open-source IaC tool that also targets Azure through ARM; it is not an Azure service.

## Which tool when?

| Need | Tool |
|---|---|
| Explore, learn, one-off change, dashboards | Portal |
| Quick commands from anywhere with nothing installed | Cloud Shell |
| Scripted tasks on Linux/Bash or cross-platform | Azure CLI |
| Scripted tasks with PowerShell objects and pipelines | Azure PowerShell |
| Repeatable, versioned, declarative deployments | ARM template or Bicep |
| Manage on-premises or other-cloud servers and clusters with Azure tools | Azure Arc |

## Try it in the portal

1. Start **Cloud Shell** (the `>_` icon), choose Bash, and run `az group list --output table`. Switch to PowerShell and run `Get-AzResourceGroup`.
2. Create a resource group in the portal, then in Cloud Shell run `az group show --name <name>`: same object, different tool.
3. Start creating a storage account in the portal, go to **Review + create**, and choose **Download a template for automation** to see the ARM template the portal would deploy.
4. Open **Azure Arc** in the portal to see what it can connect; you do not need to onboard anything.

## Key takeaways

- All Azure tools go through Azure Resource Manager, which gives consistent management, RBAC, Policy, locks and tags.
- The portal is graphical and best for exploring and one-off tasks; it is not repeatable.
- Cloud Shell is a browser-based shell with Bash or PowerShell and Azure CLI and Azure PowerShell preinstalled; storage is optional (ephemeral sessions).
- Azure CLI and Azure PowerShell do the same job with different syntax and run locally or in Cloud Shell.
- Azure Arc brings servers, Kubernetes clusters and data services outside Azure under Azure management.
- IaC makes deployments declarative, repeatable, idempotent and version-controlled.
- Bicep compiles to ARM templates (JSON) and is the recommended authoring language; Terraform is third-party.
