## Microsoft Entra ID

**Microsoft Entra ID** (formerly Azure Active Directory) is Microsoft's cloud-based identity and access management service. It authenticates users, devices and applications for Microsoft 365, Azure and thousands of SaaS and custom apps.

- A **tenant** is a dedicated instance of Microsoft Entra ID that holds your users, groups, devices and app registrations. An Azure subscription trusts one tenant.
- Entra ID uses modern protocols (OAuth 2.0, OpenID Connect, SAML) over HTTPS. It is not an LDAP or Kerberos directory.
- **Microsoft Entra Connect** (and cloud sync) synchronizes on-premises Active Directory identities to Entra ID for a hybrid identity.
- Features such as Conditional Access and Privileged Identity Management require paid Microsoft Entra ID P1 or P2 licensing.

## Microsoft Entra Domain Services

Some legacy apps need a traditional domain: domain join, Group Policy, LDAP, NTLM or Kerberos. **Microsoft Entra Domain Services** provides **managed domain services** in Azure so you can use these without deploying and patching domain controllers yourself.

| | Microsoft Entra ID | Microsoft Entra Domain Services |
|---|---|---|
| Protocols | OAuth, OpenID Connect, SAML | LDAP, Kerberos, NTLM |
| Structure | Flat tenant (users, groups) | Managed AD domain with OUs, Group Policy |
| Use | Cloud identity, SSO, MFA | Lift-and-shift apps needing domain join or LDAP |
| Management | Fully managed SaaS | Managed domain controllers in a VNet; you do not manage the DCs |

Microsoft Entra Domain Services synchronizes identities from Entra ID into the managed domain (one way), so it is not a replacement for Entra ID but an add-on to it.

> **Exam tip:** "Legacy app needs LDAP/Kerberos, but we don't want to run domain controllers in Azure VMs" points to Microsoft Entra Domain Services.

## Authentication: SSO, MFA and passwordless

- **Single sign-on (SSO)** lets a user sign in once with one set of credentials and access multiple apps without signing in again. It reduces password fatigue and the number of credentials to manage and attack.
- **Multifactor authentication (MFA)** requires two or more of: something you **know** (password, PIN), something you **have** (phone, authenticator app, hardware token), something you **are** (fingerprint, face). Passing an extra factor blocks most account-takeover attacks even when a password is stolen. Security defaults enable MFA registration and requirements for free tenants.
- **Passwordless authentication** removes the password entirely. Common methods: **Windows Hello for Business**, the **Microsoft Authenticator** app, and **FIDO2 security keys**. It is more convenient and more resistant to phishing and password spray.

Authentication methods run from least to most secure roughly: password only, password plus MFA, passwordless.

## External identities

**Microsoft Entra External ID** covers working with people outside your organization, letting them use their own identities:

- **B2B collaboration**: invite partners and guests into your workforce tenant. They sign in with their own work, school or social identity and appear as guest user objects in your directory. You control what they can access.
- **External tenant (customer identity, CIAM)**: a separate tenant configuration for consumer or customer-facing apps, with branded sign-up and sign-in using email, social providers and so on.
- **B2B direct connect** is a mutual trust between two Entra tenants for Teams shared channels.

Guests keep their own credentials, so you do not manage their passwords or lifecycle.

## Conditional Access

**Conditional Access** is Microsoft Entra's policy engine that evaluates **signals** at sign-in and applies **decisions**. Think "if this, then that".

- **Signals**: user or group, IP location, device state, application, real-time risk.
- **Decisions**: block access, grant access, or grant access with requirements such as MFA, a compliant device, or an approved app.
- Typical policies: require MFA for admins, block sign-in from certain countries, require a compliant device for sensitive apps.
- It is the core Zero Trust policy point for Entra ID, and requires Entra ID P1 or higher.

> **Watch out:** Conditional Access is evaluated after first-factor authentication. It does not replace MFA; it decides when MFA (or something else) is required.

## Try it in the portal

1. Sign in to the Microsoft Entra admin center (or Azure portal > **Microsoft Entra ID**) and open **Overview** to see your tenant name and ID.
2. Under **Users**, create a test user and a security group; add the user to the group.
3. Under **Protection > Conditional Access**, select **Create new policy** to inspect the signal and control options (new policies can be left in report-only mode or not saved; some options may need P1).
4. Under **Users > Authentication methods**, review the methods available (Microsoft Authenticator, FIDO2, and so on).
5. Search **Microsoft Entra Domain Services** and open the create wizard to see the managed-domain requirements (VNet, domain name). Don't deploy; it bills hourly.

## Key takeaways

- Microsoft Entra ID is the cloud identity service (formerly Azure AD), not an LDAP/Kerberos directory.
- Microsoft Entra Domain Services gives a managed AD domain (domain join, LDAP, Kerberos, NTLM, Group Policy) without running your own domain controllers.
- SSO reduces repeated sign-ins; MFA adds a second factor; passwordless removes the password using Windows Hello, Authenticator or FIDO2 keys.
- External ID lets guests use their own identities (B2B) and powers customer-facing sign-in via external tenants.
- Conditional Access combines signals (user, location, device, risk) into decisions (block, allow, require MFA).
- Conditional Access and Privileged Identity Management need paid Entra ID licensing.
