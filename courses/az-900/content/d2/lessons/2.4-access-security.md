## Azure role-based access control (RBAC)

**Azure RBAC** controls who can do what on Azure resources. A **role assignment** has three parts: a **security principal** (user, group, service principal or managed identity), a **role definition** (a set of permissions), and a **scope** (where it applies).

Common built-in roles:

| Role | Permissions |
|---|---|
| **Owner** | Full access, including assigning roles to others |
| **Contributor** | Create and manage everything, but **cannot** assign roles |
| **Reader** | View only |
| **User Access Administrator** | Manage access (role assignments) only, no resource management |

- **Scope** levels from broadest to narrowest: management group, subscription, resource group, resource.
- **Inheritance**: a role assigned at a scope applies to all child scopes. Owner on a subscription means Owner on every resource group and resource inside it. A narrower assignment adds to, it does not remove, inherited permissions (Azure RBAC is additive; deny assignments are a separate, specialized feature).
- Follow **least privilege**: grant the narrowest role at the narrowest scope that does the job, and prefer groups over individuals.
- Do not confuse Azure RBAC (permissions on Azure resources) with **Microsoft Entra roles** (administering the directory itself, such as Global Administrator or User Administrator).

> **Exam tip:** Contributor can do everything except grant access; only Owner (or User Access Administrator) can assign roles.

## Zero Trust

**Zero Trust** is a security model that assumes the network is already compromised. It has three guiding principles:

1. **Verify explicitly**: always authenticate and authorize using all available signals (identity, location, device health, workload, data classification, anomalies).
2. **Use least-privilege access**: limit users to just-in-time and just-enough access, with risk-based adaptive policies and data protection.
3. **Assume breach**: minimize blast radius, segment access, verify end-to-end encryption, and use analytics to detect and respond.

The old model trusted anything inside the corporate network perimeter ("trust but verify"); Zero Trust trusts nothing by location alone ("never trust, always verify"). Conditional Access, MFA, network segmentation and device compliance are all Zero Trust building blocks.

## Defense in depth

**Defense in depth** uses layers of protection so that if one layer fails, others still protect the data. Microsoft describes seven layers, from outside in:

| Layer | Examples |
|---|---|
| Physical security | Datacenter access controls, badge systems |
| Identity and access | MFA, Conditional Access, RBAC |
| Perimeter | DDoS protection, firewalls at the network edge |
| Network | Segmentation, NSGs, limiting connectivity |
| Compute | Patching, endpoint protection, secure VM access |
| Application | Secure coding, secrets in Key Vault, vulnerability scanning |
| Data | Encryption at rest and in transit, access controls |

The goal is to slow an attacker and reduce the chance that a single failure exposes data. The layered picture usually places **data** at the center.

> **Watch out:** Zero Trust is a *strategy* (verify, least privilege, assume breach) and defense in depth is a *layering* approach. They complement each other; one does not replace the other.

## Microsoft Defender for Cloud

**Microsoft Defender for Cloud** is a cloud-native application protection platform (CNAPP) that spans Azure, AWS, Google Cloud and on-premises or hybrid resources (through Azure Arc). It has two major jobs:

- **Cloud security posture management (CSPM)**: continuously assesses resources against standards such as the Microsoft cloud security benchmark, issues **security recommendations**, and computes a **secure score** (higher score means lower identified risk). **Foundational CSPM** is free; the paid **Defender CSPM** plan adds capabilities like attack path analysis and agentless scanning.
- **Cloud workload protection (CWPP)**: optional paid **Defender plans** for specific workloads, such as Defender for Servers, Containers, Storage, and databases, providing threat detection and alerts.

It surfaces recommendations such as "enable MFA on accounts" or "close management ports on VMs", and offers regulatory compliance views. Remember: Defender for Cloud **detects and recommends**; it does not by itself replace Azure Policy (which enforces) or RBAC (which authorizes).

## Try it in the portal

1. Open a resource group > **Access control (IAM)** > **Role assignments** and view the inherited assignments (the Scope column says *This resource* or *Inherited*).
2. Select **Add > Add role assignment**, browse the **Reader**, **Contributor** and **Owner** definitions, and read their descriptions (you can cancel without saving).
3. Use **Check access** to see the effective roles for your own account.
4. Search **Microsoft Defender for Cloud**, open **Overview**, then **Recommendations** and **Environment settings** to see the free CSPM and the optional Defender plans (leave plans off to avoid cost).
5. Open **Regulatory compliance** to see the built-in standards.

## Key takeaways

- RBAC = security principal + role + scope; permissions inherit down management group, subscription, resource group, resource.
- Owner can assign roles; Contributor manages resources but cannot assign roles; Reader is view only.
- Zero Trust: verify explicitly, use least-privilege access, assume breach.
- Defense in depth has seven layers: physical, identity and access, perimeter, network, compute, application, data.
- Defender for Cloud gives secure score and recommendations (free foundational CSPM) plus paid workload protection plans.
- Defender for Cloud covers Azure, other clouds and hybrid resources; it recommends and detects, while Azure Policy enforces.
