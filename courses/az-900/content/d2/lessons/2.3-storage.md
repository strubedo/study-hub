## Azure Storage services compared

A **storage account** provides a unique namespace for your data, reachable over HTTP/HTTPS. The account name must be 3 to 24 characters, lowercase letters and numbers only, and unique across Azure. Data in Azure Storage is encrypted at rest by default.

| Service | What it stores | Typical use |
|---|---|---|
| **Blob Storage** | Unstructured objects (text, binary, media) in containers | Images, video, backups, logs, data lakes |
| **Azure Files** | Managed file shares over SMB (and NFS on premium shares) | Replace on-premises file servers, lift-and-shift apps needing shared drives |
| **Queue Storage** | Messages (up to 64 KB each) | Decouple components, asynchronous processing |
| **Table Storage** | Schemaless NoSQL key-attribute data | Simple structured data, device information |
| **Managed disks** | Block-level volumes for VMs (backed by page blobs) | VM OS and data disks |

There are three blob types: **block blobs** (files, media), **append blobs** (log files) and **page blobs** (random read/write, the basis for VM disks).

## Storage account types and options

| Account type | Supports | Redundancy |
|---|---|---|
| Standard general-purpose v2 | Blobs, files, queues, tables | LRS, ZRS, GRS, RA-GRS, GZRS, RA-GZRS |
| Premium block blobs | Block and append blobs, low latency | LRS, ZRS |
| Premium file shares | Azure Files only (SMB and NFS), SSD | LRS, ZRS |
| Premium page blobs | Page blobs only | LRS |

- General-purpose v2 is the recommended standard type for most scenarios.
- Premium accounts use SSDs for low latency and high throughput.
- You cannot change a storage account's type after creation; to switch, create a new account and copy the data.
- Account options at creation include region, performance tier (standard or premium), redundancy, and default access tier (hot or cool).
- Access to data can be controlled with Microsoft Entra ID, shared access signatures (SAS), account keys, firewall and virtual network rules, and private endpoints.

## Access tiers (blob data)

| Tier | Intended for | Minimum recommended retention | Latency |
|---|---|---|---|
| **Hot** | Frequently accessed or modified data | None | Milliseconds |
| **Cool** | Infrequently accessed data | 30 days | Milliseconds |
| **Cold** | Rarely accessed data that still needs fast retrieval | 90 days | Milliseconds |
| **Archive** | Rarely accessed data with flexible latency | 180 days | Hours (offline) |

- Moving data out of a tier before its minimum period triggers an **early deletion charge** for the remaining days.
- Cooler tiers have lower storage cost but higher access and transaction cost.
- Archive is **offline**: you must **rehydrate** a blob to an online tier (hot, cool or cold) before reading it; this can take hours.
- Tiers are set at the blob (block blob) level, and the account has a default tier of hot or cool. **Lifecycle management** policies can move blobs between tiers or delete them automatically based on age or last access.
- Archive is supported for LRS, GRS and RA-GRS accounts only, not for ZRS, GZRS or RA-GZRS.
- Smart tier can move data between hot, cool and cold automatically based on usage.

> **Exam tip:** Match the number to the tier: cool 30, cold 90, archive 180. Archive is the only offline tier.

## Redundancy options

Azure always keeps multiple copies of your data so it survives hardware failures.

| Option | Copies | Where | Protects against |
|---|---|---|---|
| **LRS** (locally redundant) | 3 | One datacenter in the primary region | Drive/rack failures; not a datacenter disaster |
| **ZRS** (zone-redundant) | 3 | Three availability zones in the primary region | Zone/datacenter outage |
| **GRS** (geo-redundant) | 6 | LRS in primary + LRS in secondary region | Regional outage |
| **GZRS** (geo-zone-redundant) | 6 | ZRS in primary + LRS in secondary region | Zone and regional outage |
| **RA-GRS / RA-GZRS** | 6 | Same as GRS/GZRS, secondary readable | As above, plus read access to the secondary |

- Replication to the secondary region is **asynchronous**, so a failover can lose very recent writes.
- With GRS and GZRS the secondary is not readable until a failover; **RA-GRS and RA-GZRS** allow reads from the secondary at any time.
- The secondary region is the paired region and cannot be changed.
- Durability is at least 11 nines for LRS, 12 for ZRS and 16 for the geo options.

## Moving files and migrating data

| Tool | What it does |
|---|---|
| **AzCopy** | Command-line utility to copy blobs and files to, from and between storage accounts; scriptable |
| **Azure Storage Explorer** | Free GUI app (Windows, macOS, Linux) to manage blobs, files, queues, tables and disks |
| **Azure File Sync** | Syncs on-premises Windows file servers with an Azure file share; the server keeps a local cache of hot files (cloud tiering) while Azure holds the full copy |
| **Azure Migrate** | Central hub to discover, assess and migrate on-premises servers, databases, web apps and VDI to Azure |
| **Azure Data Box** | Physical devices Microsoft ships to you for offline transfer of large data sets, which you send back to be loaded into Azure |

- The Data Box family has a small option, **Data Box Disk** (SSDs, for smaller transfers), and the **Data Box** rugged appliance for larger ones. Data Box Heavy, once the petabyte-scale option, has been retired and can no longer be ordered, and Microsoft is also retiring the 80 TB Data Box in regions where next-generation devices are available, so expect questions to focus on the offline-shipping concept rather than device sizes. Data is encrypted on the devices and they are wiped after upload.
- Use Data Box when network transfer would take too long or the bandwidth is limited; use AzCopy for online transfer.
- Azure Migrate provides discovery, assessment (sizing and cost estimates) and migration tools in one place; it focuses on moving workloads, whereas Data Box focuses on moving bulk data offline.

> **Watch out:** Azure File Sync syncs a file server **with** Azure Files; AzCopy is a one-off or scripted copy; Storage Explorer is a GUI. Don't swap them in "which tool" questions.

## Try it in the portal

1. Create a storage account in `rg-lab-storage`: Standard performance, **LRS**. In the **Redundancy** drop-down, note which options are available.
2. Open the account > **Containers** > create `docs`, upload a file, then select the blob and **Change tier** between Hot, Cool, Cold and Archive; read the warnings.
3. Under **Data management > Redundancy**, see the current option; under **Lifecycle management**, review the rule builder.
4. Create a file share under **File shares** and read the connect instructions.
5. Optionally install Storage Explorer and attach the account, or download AzCopy and run `azcopy --help`. Delete the resource group afterwards.

## Key takeaways

- Blobs hold objects, Files hold managed shares, Queues hold messages, Tables hold NoSQL key-attribute data, and disks back VMs.
- General-purpose v2 is the standard account type; account type cannot be changed after creation.
- Tier retention: cool 30 days, cold 90 days, archive 180 days; archive is offline and needs rehydration.
- LRS has 3 copies in one datacenter; ZRS 3 copies across zones; GRS and GZRS have 6 copies across two regions; RA variants add read access to the secondary.
- AzCopy is the command-line copier, Storage Explorer is the GUI, and File Sync extends file servers into Azure Files.
- Azure Migrate discovers, assesses and migrates workloads; Data Box moves large datasets offline.
