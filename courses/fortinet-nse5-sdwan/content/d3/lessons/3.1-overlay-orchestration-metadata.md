## What overlay orchestration is for

Most SD-WAN designs need overlays: IPsec tunnels from every branch to one or more hubs, BGP over those tunnels, loopbacks for health checks and a lot of matching values on both ends. FortiManager's **SD-WAN overlay template** is a wizard that builds all of that from Fortinet's recommended IPsec and BGP templates.

Two limits are stated plainly in the FortiManager guide and are favourite exam material:

1. The overlay template provides **no SD-WAN intelligence**. It doesn't create the SD-WAN rules that steer traffic; you still need an **SD-WAN template** for that. (Its Template Options step can add the overlay members, zones and a hub health-check SLA to an SD-WAN template, but the steering logic is yours.)
2. It **assumes the hub and branches can already reach each other** over the underlay (static routes, BGP or a DHCP-provided route), because the tunnels are built over that connectivity.

The wizard is at **SD-WAN Manager > Overlay Orchestration > Create New**. It can be run again later to regenerate its templates.

## Before you start

Prerequisites:

* Add the hub and branch FortiGates to FortiManager (real or model devices) and **enable SD-WAN management** on them.
* Configure the ISP links and other interfaces on those devices.
* Create one or more **device groups** for the branches.

Network planning, with the wizard's defaults:

| Item | Default |
|---|---|
| Overlay network (tunnel addressing) | `10.10.0.0/16` |
| Loopback address space | `172.16.0.0/16` |
| BGP AS for the region | `65000` |

## The wizard, step by step

| Step | Key settings |
|---|---|
| **Region Settings** | Name; topology (**Single HUB**, **Dual HUB (Primary/Secondary)**, **Dual HUB (Primary/Primary)**, **Multi HUB**); overlay authentication **Pre-shared Key** (default) or **Signature** (certificate, which can be a metadata variable); Advanced: loopback range, overlay network, BGP AS, BGP on Loopback, Dynamic BGP (with optional route reflection), Auto-Discovery VPN (Disabled, Legacy, ADVPN 2.0), Segmentation Over Single Overlay |
| **Role Assignment** | Hub devices/VDOMs (3 or 4 for Multi HUB, each with a cost); branch **device group(s)**; **Automatic Branch ID Assignment** |
| **Network Configuration** | Per hub and per branch group: WAN underlay interfaces (Private Link, Override IP, Cost, Transport Group with ADVPN 2.0), network advertisement (connected interfaces or static prefixes), neighbors, route maps |
| **Template Options** | Add overlay objects to a branch and a hub SD-WAN template; add overlay interfaces and zones; add each hub's health-check server as a performance SLA; normalize interfaces; add health-check firewall policies to a policy package; add a default route to the SD-WAN zones in a static route template |
| **Summary** | Review, then **Finish** generates and assigns the templates |

By default the wizard turns on three recommended settings: **BGP on Loopback**, **Dynamic BGP** and **ADVPN 2.0**. With BGP on loopback a branch has a single BGP peering to each hub however many overlays exist, and the overlay network setting isn't used.

Dual HUB Primary/Secondary and Primary/Primary build the same configuration. The difference is that the secondary hub gets a higher **cost**, which the SD-WAN rule then uses.

> **Exam tip:** The **Template Options** step is the bridge to SD-WAN intelligence: it can drop the overlay members, zones and hub health checks into a new or existing SD-WAN template. You still write the SD-WAN rules yourself.

## What the wizard generates

For a single-hub design with two underlays, the wizard creates:

| Category | Generated objects |
|---|---|
| IPsec templates | `BRANCH_IPsec` (tunnels `HUB1-VPN1`, `HUB1-VPN2` from the branch to the hub) and `HUB1_IPsec` (`VPN1`, `VPN2` on the hub) |
| BGP templates | `BRANCH_BGP` (router ID built from `branch_id`) and `HUB1_BGP` |
| CLI templates | Branch CLI templates for interfaces and BGP router ID (grouped in a branch CLI template group), `HUB1_CLI` for the hub loopback `HUB1-Lo` |
| Template groups | `HUB1` (hub templates) and `BRANCH` (branch templates, applied to every device in the branch device group) |
| SD-WAN template content | When Template Options are on: branch zones such as `WAN1`, `WAN2`, `HUB1`, hub zone `OVERLAYS`, and a hub performance SLA |
| Metadata variables | **`branch_id`** |
| Normalized interfaces | When enabled: `HUB1-Lo`, the `HUB1` zone mapped per-platform, and `VPN1`/`VPN2` for the tunnel templates |

Dual-hub and multi-hub designs add `HUB2_IPsec`, `HUB2_BGP`, `HUB2-VPN1/2` and so on.

### branch_id

The wizard creates the **`branch_id`** metadata variable, and **every branch must have a unique value**: the branch provisioning templates use it for per-branch settings such as the BGP router ID. Either set it per device, or enable **Automatic Branch ID Assignment** so FortiManager assigns IDs to every device in the branch device group, including devices added later or through a zero-touch device blueprint. The usable range depends on how the overlay network is split (for example the default `/16` split into `/19` subnets for 5-8 overlays allows up to 8190 branch IDs).

### Editing and re-running

Editing the overlay template and finishing the wizard again **updates the provisioning templates it generated**, ready to reinstall. You can edit the generated templates directly, but fields the wizard owns are overwritten next time the wizard runs (for example a changed Local AS in the hub BGP template). Fields the wizard doesn't manage, such as descriptions, are left alone.

## Onboarding a new branch

Because the generated branch templates are assigned through the branch **device group**, onboarding is mostly membership:

1. Add the new FortiGate (often as a model device, optionally from a device blueprint or a CSV import that can include `branch_id`).
2. Put it in the overlay template's branch device group. The branch provisioning templates are assigned automatically.
3. Give it a unique `branch_id` (or let automatic assignment do it) and any other metadata values.
4. Assign the branch policy package and install with the Install Wizard.

## ADOM-level metadata variables

Metadata variables are named values that FortiManager substitutes per device at install time. They let one template, script or object serve many FortiGates.

### Where they are configured

**Policy & Objects > Advanced > Metadata Variables** (turn the feature on first under Policy & Objects > Tools > Feature Visibility). Each ADOM has its own list. The toolbar's More menu clones, groups, imports and exports variables (JSON or CSV) and shows where each is used.

| Field | Notes |
|---|---|
| Name, Description | The name is what you reference |
| Type | **Text** (plain, usable anywhere variables are supported) or **Password** (stored encrypted; can't be revealed after saving; for passwords in provisioning templates) |
| Default Value | Used whenever no mapping exists for the device |
| Per-Device Mapping | Device **or device group** plus value; not available in the Global Database ADOM |
| Per-ADOM Mapping | Only in the Global Database ADOM: one value for all devices in a chosen ADOM |

You can also set values from Device Manager: right-click a device > **Edit Variable Mapping** (shows the default and the device's mapping), or edit a device group's **Metadata Variables** field. A device group value applies to every device in the group, **but a device with its own per-device value keeps that value**.

### Which value does a device get?

| Mapping that exists for the device | Value used |
|---|---|
| Per-device value | Per-device value |
| No per-device value, member of a mapped device group | Device-group value |
| Neither | Default value |

Example, ADOM `Branches`:

```text
Policy & Objects > Advanced > Metadata Variables

Name       Type   Default Value   Per-Device Mapping
wan1_gw    Text   203.0.113.1     FGT-Branch2 = 203.0.113.9
lan_net    Text   10.0.0.0/24     Group East-Stores = 10.20.0.0/24
                                  FGT-Branch1 = 10.1.0.0/24
```

If `FGT-Branch1` and `FGT-Branch2` are both in `East-Stores`, then `FGT-Branch1` gets `lan_net` = `10.1.0.0/24` (its own value beats the group), `FGT-Branch2` gets `10.20.0.0/24` (group) and `wan1_gw` = `203.0.113.9`, and `FGT-Branch1` gets `wan1_gw` = `203.0.113.1` (default).

> **Watch out:** A device without a mapping silently receives the **default**. If the default is a real-looking IP, a forgotten mapping becomes a wrong gateway on a live FortiGate rather than an error. Check Install Preview, or run Validate on CLI templates.

### Where you can use them

Scripts, provisioning templates (including SD-WAN, IPsec, BGP, CLI and overlay templates), firewall addresses and address groups, IP pools, VIPs, normalized interfaces, virtual wire pairs, FortiAP SSIDs, FortiSwitch VLANs, and FortiClient EMS connectors. Fields that accept a variable show the metadata variable icon, and **typing `$`** in such a field lists the ADOM's variables.

Where the selector isn't offered (CLI templates, scripts, some mapping fields), type the reference yourself as **`$(variable_name)`**:

```text
config system interface
    edit "port3"
        set ip 10.$(branch_id).1.1 255.255.255.0
    next
end
config router bgp
    set router-id 172.16.0.$(branch_id)
end
```

Jinja scripts can also use metadata variables (create the variables before the script), but FortiManager notes that most objects only support substitution in the `$(var)` form, not Jinja's `{{var}}`.

### Checking substitution

* **Validate** (CLI templates only: More > Validate on an assigned CLI template) lists each device's resolved value and can filter on devices missing a value; you can edit a value, preview the script and re-validate. An OK result only means the variables resolve, not that the values are sensible (two branches with the same `branch_id` both pass).
* **Install Preview** shows the **real resolved value** for the target device.
* **Preview CLI Configuration** on a provisioning template shows the **variable name**, not the value.

## Lab it yourself

The overlay wizard needs at least a hub and one branch. With the FortiManager-VM trial (3 devices), use model devices: `FGT-HQ` (hub) and `FGT-Branch1`/`FGT-Branch2` (branches) in device group `Branches`, all with SD-WAN management enabled.

1. Run the wizard with Single HUB and the defaults, then list what it created under SD-WAN Manager > Templates and Policy & Objects > Advanced > Metadata Variables.
2. Set `branch_id` to 1 and 2 (or enable automatic assignment and check the values).
3. Open Install Preview for each branch and find where `branch_id` was substituted.
4. Create `lan_net` with a default and a device-group value, then give one branch its own value and confirm which value each branch resolves.

Because the devices are models, nothing is installed; Install Preview still shows the CLI.

## Key takeaways

* The SD-WAN overlay template (SD-WAN Manager > Overlay Orchestration) generates IPsec, BGP and CLI templates, template groups and the `branch_id` variable.
* It gives no SD-WAN intelligence: the steering rules come from an SD-WAN template (Template Options can only seed it with overlay members, zones and hub health checks). It also assumes hub-branch underlay reachability.
* Defaults: overlay `10.10.0.0/16`, loopbacks `172.16.0.0/16`, AS `65000`; BGP on Loopback, Dynamic BGP and ADVPN 2.0 on.
* Every branch needs a unique `branch_id`, set manually or by Automatic Branch ID Assignment; new devices join through the branch device group.
* Metadata variables are per ADOM: default value, per-device or device-group mapping (per-ADOM only in the Global Database).
* Per-device value beats device-group value, which beats the default.
* Type `$` to pick a variable; type `$(name)` by hand in CLI templates and scripts. Install Preview shows resolved values.
