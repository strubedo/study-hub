## A layered workflow

SD-WAN problems usually look the same from the user's chair ("the app is slow", "the site is down", "traffic goes out the wrong ISP"), but the cause sits at one of a few layers. Work through them in order, and prove each layer with a command before moving on:

| Step | Question | Proof |
|---|---|---|
| 1 Member | Is the interface up, with the right IP and gateway? | `get system interface physical`, `diagnose sys sdwan member` |
| 2 Health | Is the member alive and in SLA for the health check the rule uses? | `diagnose sys sdwan health-check <name>`, `sla-log` |
| 3 Rule | Which rule matches, and which member does it pick? | `diagnose sys sdwan service4 <id>`, `diagnose firewall proute list` |
| 4 Routing | Does the FIB allow that rule and member? What does the routing table hold? | `get router info routing-table all`, `... details <ip>`, `... database` |
| 5 Policy | Does a firewall policy allow the traffic out of that zone? NAT? | `diagnose debug flow`, policy hit counts |
| 6 Session | What did the existing session actually do? Does it need re-evaluation? | `diagnose sys session filter` / `list`, sniffer, traffic logs |

## Routing checks

### The routing table and the database

```text
FGT-Branch1 # get router info routing-table all
Codes: K - kernel, C - connected, S - static, R - RIP, B - BGP
       O - OSPF, IA - OSPF inter area
       N1 - OSPF NSSA external type 1, N2 - OSPF NSSA external type 2
       E1 - OSPF external type 1, E2 - OSPF external type 2
       i - IS-IS, L1 - IS-IS level-1, L2 - IS-IS level-2, ia - IS-IS inter area
       * - candidate default

Routing table for VRF=0
S*      0.0.0.0/0 [1/0] via 203.0.113.1, port1
                  [1/0] via 198.51.100.1, port2
C       10.0.1.0/24 is directly connected, port3
C       198.51.100.0/30 is directly connected, port2
C       203.0.113.0/30 is directly connected, port1
```

The default route is an ECMP pair because both members carry the same distance and priority: that's the path set the **implicit rule** load-balances over. `get router info routing-table database` also shows routes that lost the selection (`>` selected, `*` in the FIB), and `get router info routing-table details <ip>` resolves one destination.

When a member's health check fails and `update-static-route` is enabled (the default), the member's static routes are removed (log 0100022921), so the ECMP pair shrinks to one path. A static route can point at a whole zone with `set sdwan-zone`, which expands into a route per member.

### The two FIB checks behind every SD-WAN rule

An SD-WAN rule is a policy route, and policy routes are checked before the routing table. But FortiOS only uses an SD-WAN rule member after two FIB checks:

1. The **FIB best match** for the destination must be an **SD-WAN member** (any member).
2. A **FIB route** to the destination must exist **over the chosen member**.

If check 1 fails, the rule is skipped and the packet follows the routing table. If check 2 fails for a member, that member can't be used and the next one in order is tried.

Classic failure: a more specific static route for `198.51.100.0/24` via the LAN-side interface `port3` (a non-member) means the best match for that destination is not an SD-WAN member, so a `Critical-DIA` rule for `198.51.100.0/24` never matches. Its hit count stays at 0 and the trace shows a plain route lookup instead of a policy-routing match.

The CLI-only `set gateway enable` and `set default enable` options on a rule change these checks: with both enabled, FortiOS skips the FIB checks and sends matching traffic straight to the member's configured gateway, which must exist. Both default to `disable`.

> **Exam tip:** "The rule is configured correctly but never matches" is almost always one of three things: a rule higher in the list matches first, the traffic doesn't match the rule's criteria (source, destination, protocol, application not yet learned), or the FIB checks fail. `proute list` hit counts plus a debug flow trace tell them apart.

## Firewall policy checks

SD-WAN steering and firewall policy are separate. A rule can pick `port2`, and the session still dies if no policy allows LAN to the zone that contains `port2`.

* Policies reference **zones** (`virtual-wan-link`, `underlay`, `overlay`), never the individual members.
* A policy to zone `underlay` does not cover a member in zone `overlay`. Moving a member to another zone needs matching policies.
* NAT: Internet-bound policies normally `set nat enable`; the source address then follows the egress member.

## Debug flow

```text
FGT-Branch1 # diagnose debug reset
FGT-Branch1 # diagnose debug flow filter clear
FGT-Branch1 # diagnose debug flow filter addr 198.51.100.80
FGT-Branch1 # diagnose debug flow show function-name enable
FGT-Branch1 # diagnose debug enable
FGT-Branch1 # diagnose debug flow trace start 10
```

Stop it with `diagnose debug flow trace stop` and `diagnose debug disable`. A first packet steered by an SD-WAN rule looks like this:

```text
id=65308 trace_id=1 func=print_pkt_detail line=6143 msg="vd-root:0 received a packet(proto=6, 10.0.1.25:52114->198.51.100.80:443) tun_id=0.0.0.0 from port3. flag [S], seq 2731045522, ack 0, win 64240"
id=65308 trace_id=1 func=init_ip_session_common line=6354 msg="allocate a new session-0001595c"
id=65308 trace_id=1 func=rpdb_srv_match_input line=1182 msg="Match policy routing id=2130706433: to 198.51.100.80 via ifindex-4"
id=65308 trace_id=1 func=vf_ip_route_input_common line=2615 msg="find a route: flag=04000000 gw-198.51.100.1 via port2"
id=65308 trace_id=1 func=fw_forward_handler line=1003 msg="Allowed by Policy-1: SNAT"
id=65308 trace_id=1 func=__ip_session_run_tuple line=3517 msg="SNAT 10.0.1.25->198.51.100.2:52114"
```

* `Match policy routing id=2130706433`: the policy-route ID. Find it in `diagnose firewall proute list` (`id=2130706433(0x7f000001) vwl_service=1(Critical-DIA)`).
* `via ifindex-4`: the egress interface index (`oif=4(port2)` in the proute list).
* `find a route ... via port2`: the gateway lookup for that member.
* `Allowed by Policy-1: SNAT`: the firewall policy and NAT.

If no SD-WAN rule matches, there is no `Match policy routing` line; the first route line comes straight from the FIB (the implicit rule's ECMP choice). If no policy allows the traffic, the trace ends with:

```text
id=65308 trace_id=4 func=fw_forward_handler line=874 msg="Denied by forward policy check (policy 0)"
```

Policy 0 is the implicit deny: no policy matched the incoming interface, egress zone, addresses and service.


| Field | Meaning |
|---|---|
| `dev=5->4/4->5` | Ingress->egress interface indexes, original/reply (`port3`->`port2`) |
| `gwy=198.51.100.1/10.0.1.25` | Next hop for original/reply direction |
| `act=snat ... (198.51.100.2:52114)` | Source NAT to the egress member's address |
| `policy_id=1` | Firewall policy |
| `sdwan_mbr_seq=2 sdwan_service_id=1` | SD-WAN member sequence 2 chosen by SD-WAN rule 1 |
| `proto_state=01` | TCP established (see Domain 2 for protocol states) |

Sessions keep their path after a route or SLA change unless something re-evaluates them (Domain 2). In particular, **SNAT sessions keep their original egress while the old route is still valid**, unless `set snat-route-change enable` is set under `config system global`. To test a new rule without waiting for sessions to expire, clear only the sessions you filtered:

```text
FGT-Branch1 # diagnose sys session clear
```

> **Watch out:** `diagnose sys session clear` clears the sessions that match the **current filter**. Run it with no filter set and it clears every session on the VDOM, including your own SSH session. Always `filter clear`, set a filter, `list`, then clear.

## Symptom table

| Symptom | Most likely cause | Prove it with |
|---|---|---|
| All traffic on `port1`, rule says Lowest Cost (SLA) with `port2` cheaper | `port2` out of SLA (`sla(0x0)`), or `port1` has lower cost | `service4`, `health-check` |
| Rule hit count 0 | Earlier rule matches, wrong criteria, FIB check fails | `proute list`, `debug flow` |
| Member alive in GUI but never used by a rule | Out of SLA for the rule's required target | `sla_map`, log `Member out-of-sla` |
| Member dead, route missing from table | Health check failed, `update-static-route` removed routes | `health-check`, log 0100022921, `routing-table all` |
| After recovery, old sessions still on the backup link | Sessions not re-evaluated (SNAT sessions sticky) | `session list` (`sdwan_mbr_seq`), `snat-route-change` |
| `Denied by forward policy check (policy 0)` | No policy for the new egress zone | `debug flow`, policy list |
| Health check dead on one member only, link works | Probe can't reach server through that member: missing route to the server, wrong source, or server drops probes | `sla-log`, `diagnose sniffer packet port2 'host 198.51.100.10' 4` |

## Lab it yourself

FortiGate-VM trial: `port3` LAN, `port1`/`port2` WAN in zone `underlay`, one LAN-to-`underlay` policy, one default route to the zone (`set sdwan-zone "underlay"`).

1. Build `Critical-DIA` for a test server; confirm `Match policy routing` in a debug flow and `sdwan_service_id` in the session list.
2. Add a static route for the server via `port3` (a second route uses your third route slot) and confirm the rule stops matching; remove it.
3. Fail `port2`'s health check with netem and compare `routing-table all` before and after.
4. Change the rule to prefer `port1`, then clear only that test session and confirm it re-routes.

## Key takeaways

* Work member → health → rule → routing → policy → session, and prove each step.
* SD-WAN rules need two FIB checks: the best match must be an SD-WAN member, and a route must exist over the chosen member.
* No `Match policy routing` line in debug flow means no SD-WAN rule (or other policy route) matched.
* `Denied by forward policy check (policy 0)` means no firewall policy allows the traffic to that zone.
* Session list `sdwan_mbr_seq` and `sdwan_service_id` show the member and rule a session used.
* SNAT sessions stay on their old path unless `snat-route-change` is enabled; clear only filtered sessions to test.
* Policies use zones; a member moved to another zone needs a policy for that zone.
