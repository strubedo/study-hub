## The SD-WAN diagnose toolkit

The exam shows CLI output and asks what it means. These are the commands FortiOS 7.6 documents for SD-WAN, and the question each one answers:

| Command | Answers |
|---|---|
| `diagnose sys sdwan health-check [<name>]` | Is each member alive, what are its loss/latency/jitter, which SLA targets does it meet? |
| `diagnose sys sdwan sla-log <health-check> <seq>` | What did the last 10 minutes of probes look like for one member? |
| `diagnose sys sdwan intf-sla-log <interface>` | How much bandwidth did this member use over the last 15 minutes? |
| `diagnose sys sdwan member` | Gateway, priority and weight of each member, plus per-mode load-balance state |
| `diagnose sys sdwan service4 [<id>]` | For each IPv4 rule: strategy, member order, member state, which are selected (`service6` for IPv6) |
| `diagnose firewall proute list` | The policy-route table the kernel actually uses, including SD-WAN rules and their hit counts |
| `diagnose sys sdwan internet-service-app-ctrl-list` | Which IP/protocol/port tuples have been learned for application-based rules |
| `diagnose sys sdwan route-tag-list` | Route tags (from BGP) used as rule destinations and the prefixes behind them |
| `diagnose sys link-monitor-passive admin list by-interface` | Passive (real-traffic) health measurements per interface |

> **Watch out:** Since FortiOS 7.4.4, `diagnose sys sdwan service` is split into `service4` and `service6`. On 7.6, use `service4` for IPv4 rules.

## health-check

```text
FGT-Branch1 # diagnose sys sdwan health-check DC_HC
Health Check(DC_HC):
Seq(3 HUB1-VPN1): state(alive), packet-loss(0.000%) latency(31.402), jitter(0.812) sla_map=0x3
Seq(4 HUB1-VPN2): state(alive), packet-loss(3.000%) latency(29.877), jitter(1.025) sla_map=0x2
```

* `Seq(3 HUB1-VPN1)`: member sequence number and interface.
* `state(alive|dead)`: dead after `failtime` consecutive probe failures (default 5), alive again after `recoverytime` successes (default 5).
* `packet-loss`, `latency`, `jitter`: the health check's current measurements, in % and ms.
* `sla_map`: a **bitmap of SLA targets the member meets**. Bit 0 (`0x1`) is SLA entry 1, bit 1 (`0x2`) is entry 2, and so on. `0x3` means it meets entries 1 and 2; `0x0` means it meets none.

Here `HUB1-VPN2` meets SLA 2 but not SLA 1. If SLA 1 requires 0% loss and SLA 2 allows 5%, that fits the 3% loss shown. A rule that requires `DC_HC` SLA 1 will avoid `HUB1-VPN2`; a rule that requires SLA 2 can use either.

A dead member shows only loss:

```text
Seq(2 port2): state(dead), packet-loss(100.000%) sla_map=0x0
```

Without a name, the command lists every health check. A member can appear under several health checks with different results, because each health check probes its own server.

## sla-log and intf-sla-log

```text
FGT-Branch1 # diagnose sys sdwan sla-log Internet_HC 1
Timestamp: Wed Oct 28 09:20:38 2026, vdom root, health-check Internet_HC, interface: port1, status: up, latency: 61.208, jitter: 4.117, packet loss: 0.000%.
Timestamp: Wed Oct 28 09:20:39 2026, vdom root, health-check Internet_HC, interface: port1, status: up, latency: 163.554, jitter: 22.906, packet loss: 0.000%.
Timestamp: Wed Oct 28 09:20:39 2026, vdom root, health-check Internet_HC, interface: port1, status: up, latency: 171.020, jitter: 21.317, packet loss: 0.000%.
```

The arguments are the **health-check name and the member sequence number**. The SD-WAN daemon keeps about **10 minutes** of this history. Use it to see when latency jumped and whether the member stayed up.

`intf-sla-log <interface>` keeps about **15 minutes** of per-interface usage: used inbandwidth, outbandwidth, bibandwidth, tx and rx bytes, with one sample roughly every 10 seconds.

## member

The first line is the same in every mode: member number, interface, gateway(s), priority (IPv4 then IPv6) and weight. Extra lines depend on the implicit rule's `load-balance-mode`:

```text
FGT-Branch1 # diagnose sys sdwan member
Member(1): interface: port1, gateway: 203.0.113.1, priority: 1 1024, weight: 0
Member(2): interface: port2, gateway: 198.51.100.1, priority: 1 1024, weight: 0
```

| load-balance-mode | Extra lines |
|---|---|
| `source-ip-based` (default), `source-dest-ip-based` | None |
| `weight-based` | `Session count: N` per member; weight is the configured weight |
| `measured-volume-based` | `Config volume ratio`, `last reading`, and **`volume room`** or **`overload volume`** |
| `usage-based` (spillover) | `Egress-spillover-threshold`, `ingress-spillover-threshold`, `Egress-overbps`, `ingress-overbps` |

Spillover example: `port1` has crossed its egress threshold, so new sessions spill to `port2`:

```text
Member(1): interface: port1, gateway: 203.0.113.1, priority: 1 1024, weight: 255
  Egress-spillover-threshold: 400kbit/s, ingress-spillover-threshold: 300kbit/s
  Egress-overbps=1, ingress-overbps=0
Member(2): interface: port2, gateway: 198.51.100.1, priority: 1 1024, weight: 254
  Egress-spillover-threshold: 0kbit/s, ingress-spillover-threshold: 0kbit/s
  Egress-overbps=0, ingress-overbps=0
```

`Egress-overbps=1` is the flag that matters. In volume mode, a member showing `overload volume` instead of `volume room` has used more than its share; it enters the "conservative status" with limited ability to take new sessions (that's when log 0113022924 fires).

> **Exam tip:** `diagnose sys sdwan member` describes the **implicit rule** only. It doesn't tell you what an SD-WAN rule chose; that's `service4`.

## service4

The header is common to every strategy:

```text
Service(1): Address Mode(IPV4) flags=0x200
  Gen(1), TOS(0x0/0x0), Protocol(0: 1->65535), Mode(sla), sla-compare-order
```

`Service(1)` is the rule ID, `Mode(...)` the strategy, and `Members(N)` lists members **in their current order of preference**. The member lines change with the mode:

| Mode in output | Strategy | Member line shows |
|---|---|---|
| `Mode(manual)` | Manual | `alive`, `selected` |
| `Mode(priority), link-cost-factor(latency), link-cost-threshold(10), health-check(DC_HC)` | Best Quality | `alive`, the measured value (`latency: 31.402`), `selected` |
| `Mode(sla), sla-compare-order` | Lowest Cost (SLA) | `alive`, `sla(0x1)`, `gid`, `cfg_order`, `cost`, `selected` |
| `Mode(load-balance hash-mode=round-robin)` | Lowest Cost (SLA) rule with `load-balance enable` | `alive`, `sla(0x1)`, `gid`, `num of pass`, `selected` |
| `Mode(manual hash-mode=round-robin)` | Manual rule with `load-balance enable` (no SLA targets) | `alive`, `gid`, `selected` |
| `Mode(auto)` | Legacy automatic | as priority mode, but only the best member is `selected` |

### Lowest Cost (SLA)

```text
FGT-Branch1 # diagnose sys sdwan service4 1
Service(1): Address Mode(IPV4) flags=0x200
  Gen(3), TOS(0x0/0x0), Protocol(0: 1->65535), Mode(sla), sla-compare-order
  Members(2):
    1: Seq_num(2 port2), alive, sla(0x1), gid(0), cfg_order(1), cost(10), selected
    2: Seq_num(1 port1), alive, sla(0x0), gid(0), cfg_order(0), cost(0), selected
  Dst address(1):
        0.0.0.0-255.255.255.255
```

Member 1 (`port1`, cost 0, listed first in the config) would normally win. It's now second because `sla(0x0)`: it fails the required SLA target. `port2` meets SLA and moves to the top despite its higher cost. Both are alive, so both show `selected`; the **first** line is the one in use. `Gen(...)` and `gid(...)` are internal values you can ignore for the exam.

### Manual and Best Quality

In manual mode all alive members are marked `selected` but traffic uses the **first** in configured order. In Best Quality the order is by the link-cost factor, with the `link-cost-threshold` (default 10%) giving the **first-configured** member an advantage: another member must be more than 10% better to move above it. Here `HUB1-VPN1` is configured first, but `HUB1-VPN2` is clearly more than 10% faster, so it leads:

```text
Service(2): Address Mode(IPV4) flags=0x200
  Gen(7), TOS(0x0/0x0), Protocol(0: 1->65535), Mode(priority), link-cost-factor(latency), link-cost-threshold(10), health-check(DC_HC)
  Members(2):
    1: Seq_num(4 HUB1-VPN2), alive, latency: 29.877, selected
    2: Seq_num(3 HUB1-VPN1), alive, latency: 48.210, selected
  Dst address(1):
        10.100.0.0-10.100.255.255
```

With 29.877 ms against 31.402 ms (under 5% better), `HUB1-VPN1` would have stayed on top.

A dead member is shown as `dead` and is never `selected`. The bottom lines (`Dst address`, `Internet Service`, `Src address`) show the rule's match criteria.

## proute list

`diagnose firewall proute list` shows what the kernel uses: policy routes, SD-WAN rules and Internet Service routes, checked in order **before** the routing table.

```text
FGT-Branch1 # diagnose firewall proute list
list route policy info(vf=root):

id=2130706433(0x7f000001) vwl_service=1(Critical-DIA) vwl_mbr_seq=2 1 dscp_tag=0xff 0xff flags=0x0 tos=0x00 tos_mask=0x00 protocol=0 sport=0-65535 iif=0 dport=1-65535 oif=4(port2) oif=3(port1)
destination(1): 0.0.0.0-255.255.255.255
source(1): 10.0.1.0-10.0.1.255
hit_count=4127 last_used=2026-10-28 09:24:02
```

* `vwl_service=1(Critical-DIA)`: SD-WAN rule ID and name. User-defined policy routes have no `vwl_service`.
* `vwl_mbr_seq=2 1` and `oif=4(port2) oif=3(port1)`: the member sequence numbers and egress interfaces **in current preference order**. This order changes when SLA or quality changes; it matches `service4`.
* `hit_count`, `last_used`: whether traffic is actually matching.
* For load-balancing rules the flags show `load-balance hash-mode=...` and each path has `num_pass`.

## Application and route-tag lists

```text
FGT-Branch1 # diagnose sys sdwan internet-service-app-ctrl-list
YouTube(31077 4294838537): 142.250.136.119 6 443 Wed Oct 28 09:02:11 2026
```

Each line is application name (ID), then a learned destination IP, protocol and port with the time it was learned. Application-based rules only match traffic to tuples in this list. `route-tag-list` shows route tags learned from BGP routes used as rule destinations and the prefixes and interfaces behind each tag.

## Lab it yourself

All of these run on the FortiGate-VM trial without FortiGuard (application lists stay empty without application signatures):

1. Configure `Internet_HC` with two SLA entries (100 ms; 300 ms) and check `sla_map` as you add netem delay on one WAN.
2. Run `diagnose sys sdwan sla-log Internet_HC 1` and find the second the delay started.
3. Change `load-balance-mode` to `usage-based` with a low `spillover-threshold` on `port1`, generate traffic and watch `Egress-overbps`.
4. Build `Critical-DIA` as Lowest Cost (SLA) and compare `service4 1` with `proute list` before and after the SLA failure.

## Key takeaways

* `health-check`: `state(alive|dead)`, loss/latency/jitter, `sla_map` bitmap (0x1 = SLA 1, 0x2 = SLA 2, 0x3 = both).
* `sla-log <hc> <seq>` keeps ~10 minutes of probes; `intf-sla-log <intf>` ~15 minutes of bandwidth.
* `member` shows gateway, priority and weight, plus session count, volume room/overload or spillover flags depending on `load-balance-mode`; it's about the implicit rule.
* `service4` lists members in current preference order; the first `selected` member is used (all selected members are used only with load balancing).
* Lowest Cost (SLA) lines show `sla()`, `cfg_order`, `cost`; Best Quality lines show the measured metric.
* `proute list`: `vwl_service=<id>(<name>)`, `vwl_mbr_seq` and `oif` in current order, `hit_count`.
* `service` became `service4`/`service6` in 7.4.4.
