## What SD-WAN rules are for

Without rules, SD-WAN only gives you ECMP. The default route points at the SD-WAN zone and the **implicit rule** spreads sessions over every member that has an active route. That gives you redundancy and some load sharing, but it ignores the application. Voice and a backup job get the same treatment.

An **SD-WAN rule** (also called a *service*, from the `config service` table) does two jobs:

1. **Identify traffic of interest**, using source and destination criteria.
2. **Choose an outgoing member** using an interface or zone preference, a **strategy**, and optionally a **performance SLA** that measures link quality.

Under the hood each enabled rule becomes a **policy route**. That has consequences you will meet throughout this domain:

* Rules are evaluated **top-down, first match**, like firewall policies. Put specific rules above broad ones.
* Rules sit *after* regular policy routes and ISDB routes in the lookup (lesson 2.2).
* A rule only steers traffic that the routing table could also send through an SD-WAN member. A rule can't create reachability that the FIB doesn't have.
* When nothing matches, the implicit rule (the routing table plus `load-balance-mode`) decides.

> **Exam tip:** "SD-WAN rule" and "SD-WAN service" are the same object. The CLI says `config service`, the GUI says **SD-WAN Rules**, and diagnose output says `Service(1)`.

## Building a rule in the GUI

Go to **Network > SD-WAN > SD-WAN Rules** and click **Create New**. After the name, the page has three sections: **Source** and **Destination** identify the traffic, and **Outgoing Interfaces** holds the WAN intelligence:

| GUI section | What you set | CLI under `config system sdwan` → `config service` → `edit <id>` |
|-------------|--------------|------------------------------------------------------------------|
| Name | Free text. It doesn't have to match the traffic, but good names help in logs | `set name` |
| Source | Address, user group | `set src`, `set users`, `set groups`, `set input-device` (CLI only) |
| Destination | Address with protocol and port, **Internet Service**, **Application** | `set dst`, `set protocol`, `set start-port`/`end-port`, `set internet-service enable` + `internet-service-name`/`-group`/`-custom`, `internet-service-app-ctrl…` |
| Outgoing interfaces | Interface/zone preference, strategy, SLA, load balancing | `priority-members`, `priority-zone`, `mode`, `health-check`, `config sla`, `load-balance` |

The rule ID is assigned when you create it in the GUI. You can choose the ID only from the CLI (1–4000). A rule can be disabled without deleting it with `set status disable`.

The implicit rule appears at the bottom of the GUI list as **sd-wan**. You edit it to change the load-balancing algorithm, but you can't delete it or move it.

### Rule status

The GUI rule list shows each rule's members and which member is currently in use. The authoritative view is the CLI:

```text
FGT-Branch1 # diagnose sys sdwan service4 2

Service(2): Address Mode(IPV4) flags=0x200
  Gen(1), TOS(0x0/0x0), Protocol(0: 1->65535), Mode(manual)
  Members(2):
    1: Seq_num(3 HUB1-VPN1), alive, selected
    2: Seq_num(4 HUB1-VPN2), alive, selected
  Dst address(1):
        10.10.0.0-10.10.255.255
```

Members are listed in the order the rule currently prefers them. The first `alive` and `selected` member carries new sessions. A dead member shows `dead`. Since FortiOS 7.4.4 the command is `service4` for IPv4 rules and `service6` for IPv6 rules.

## Traffic matching criteria

| Criterion | Source | Destination | Notes |
|-----------|:------:|:-----------:|-------|
| IPv4/IPv6 address, address group | ✓ | ✓ | `src-negate` / `dst-negate` invert the match |
| MAC address and FABRIC_DEVICE dynamic addresses | ✓ | ✓ | Address objects of those types |
| Users and user groups | ✓ | | `users`, `groups` |
| Input interface | ✓ | | `input-device` (CLI only), negate with `input-device-negate` |
| Protocol and port range | (`start-src-port`/`end-src-port`, CLI only) | ✓ | **One** protocol and **one** port range per rule |
| Internet Service (ISDB) | | ✓ | Predefined, custom, groups |
| Application, application group, category | | ✓ | Application-aware routing |
| BGP route tag | | ✓ | `route-tag`, CLI only, replaces `dst` |
| DSCP / ToS | | ✓ | `tos` + `tos-mask`, CLI only |

Two details catch people:

* **One protocol, one port range.** A rule can't list "TCP 443 and UDP 3478". Either create two rules or use a custom Internet Service that holds several protocol/port entries.
* **ToS matching uses a mask.** `set tos-mask 0xf0` compares only the upper four bits, so `set tos 0x70` matches any packet whose ToS byte starts with 0111.

```text
FGT-Branch1 # config system sdwan
FGT-Branch1 (sdwan) # config service
FGT-Branch1 (service) # edit 1
FGT-Branch1 (1) # set name "Critical-DIA"
FGT-Branch1 (1) # set src "LAN-Voice"
FGT-Branch1 (1) # set dst "all"
FGT-Branch1 (1) # set protocol 17
FGT-Branch1 (1) # set start-port 5060
FGT-Branch1 (1) # set end-port 5061
FGT-Branch1 (1) # set priority-members 1 2
FGT-Branch1 (1) # end
```

## Internet services as destination

Most cloud applications don't live at addresses you can type into an address object. The **Internet Service Database** (ISDB, maintained by FortiGuard) maps well-known services such as `Microsoft-Office365` or `Google-Gmail` to IP addresses, protocols and ports. In a rule:

```text
FGT-Branch1 (service) # edit 3
FGT-Branch1 (3) # set name "SaaS-O365"
FGT-Branch1 (3) # set internet-service enable
FGT-Branch1 (3) # set internet-service-name "Microsoft-Office365"
FGT-Branch1 (3) # set priority-members 2 1
FGT-Branch1 (3) # end
```

With `internet-service enable`, the rule matches on the ISDB entries rather than on a destination address object. In `service4` output the rule lists `Internet Service: <name>(<id>…)` instead of `Dst address`.

Because an ISDB entry contains protocol and port as well as IP ranges, it is precise. "Office 365 on 443" won't catch an unrelated service that happens to share an address.

> **Watch out:** The ISDB is a FortiGuard service. FortiOS firmware ships only a small built-in package of Fortinet objects (so rules for FortiGuard traffic keep working after an upgrade). Without a FortiGuard subscription, as on the FortiGate-VM trial, most third-party services aren't populated and rules that use them never match.

## Applications as destination

Application control signatures can also be rule destinations (`internet-service-app-ctrl`, `-app-ctrl-group`, `-app-ctrl-category`). The GUI hides the option until you enable **System > Feature Visibility > Application Detection Based SD-WAN** (`config system global` → `set gui-app-detection-sdwan enable`).

Routing happens on the first packet, but an application is only recognised after a few packets. FortiOS solves this with a learned table:

1. The firewall policy that accepts the traffic must have an **application control profile** (and SSL inspection where the app is encrypted).
2. When the IPS engine identifies an application, FortiOS records its destination IP, protocol and port (the "3-tuple").
3. **Later** sessions to that 3-tuple match the application rule.

So the **first** session to a new application destination doesn't match the rule. It follows the routing table or a later rule. List the learned entries with:

```text
FGT-Branch1 # diagnose sys sdwan internet-service-app-ctrl-list
Gmail(15817 4294836957): 142.250.128.83 6 443 Tue Oct 27 10:12:41 2026
```

> **Exam tip:** "The application rule doesn't match even though the app is in the rule" usually means the matching firewall policy has no application control profile, so nothing is learned.

## SD-WAN for local-out traffic

**Local-out** traffic is traffic the FortiGate originates itself: DNS queries, FortiGuard updates, logs to FortiAnalyzer or syslog, RADIUS, LDAP, NTP, SNMP traps and so on. By default it uses the **routing table only** to find the egress interface, and SD-WAN rules don't apply.

Many services have an `interface-select-method` option:

| Value | Behaviour |
|-------|-----------|
| `auto` (default) | Routing table lookup |
| `sdwan` | Use SD-WAN and policy routing rules |
| `specify` | Use the interface set with `set interface` |

```text
FGT-Branch1 # config log fortianalyzer setting
FGT-Branch1 (setting) # set interface-select-method sdwan
FGT-Branch1 (setting) # end
```

The GUI equivalent is **Network > Local Out Routing**. It is hidden by default, so enable it in **Feature Visibility** first. For each service you choose **Auto**, **SD-WAN** or **Specify**, plus a source IP. Some services are CLI-only. Pings and traceroutes run from the CLI can opt in with `execute ping-options use-sdwan yes` and `execute traceroute-options use-sdwan yes`.

> **Real world:** A classic DIA design puts FortiAnalyzer logging on the overlay. If the overlay rule exists but logging still leaves the internet link, check whether `log fortianalyzer setting` is still at `interface-select-method auto`.

## Use cases

* **Voice to the best link.** Match SIP/RTP by address, port or DSCP, then use Best Quality on jitter or Lowest Cost (SLA) with a strict SLA.
* **SaaS breakout.** Match by ISDB (Office 365, Salesforce) and send it out the local internet links.
* **Data-centre apps over the overlay.** Match the DC prefixes (or a BGP route tag) and prefer `HUB1-VPN1` and `HUB1-VPN2`.
* **Guest or recreational traffic on the cheap link.** Match by source subnet or application category with a Manual rule.

## Lab it yourself

On the FortiGate-VM trial with port1 and port2 as WAN members and port3 as LAN:

1. Create a Manual rule that matches one test host's /32 and prefers port2. Confirm with `diagnose sys sdwan service4` and a `diagnose sniffer packet any 'host <ip>' 4` that its traffic leaves port2, while other traffic still follows the implicit rule.
2. Change the rule to match only UDP/53 and test with `nslookup` and `curl` from the LAN host. Only the DNS packets should move.
3. Set `config system dns` → `set interface-select-method sdwan`. Create a rule for your DNS server's address and watch the FortiGate's own queries follow it. Set it back to `auto` and compare.
4. ISDB and application rules need FortiGuard. On the trial, configure one to learn the syntax, but don't expect it to match.

## Key takeaways

* An SD-WAN rule identifies traffic and then picks a member with preference + strategy + SLA. Each rule is a policy route, checked top-down, first match.
* Match criteria: addresses (negatable), users/groups, input device, one protocol and port range, ISDB, applications, BGP route tag, ToS/DSCP.
* ISDB matching needs `internet-service enable` and a populated ISDB, which means FortiGuard.
* Application rules work on learned 3-tuples, so the policy needs application control, and the first session isn't steered.
* Local-out traffic ignores SD-WAN rules unless the service uses `interface-select-method sdwan`.
* `diagnose sys sdwan service4 <id>` shows a rule's mode, member order and which member is selected.
