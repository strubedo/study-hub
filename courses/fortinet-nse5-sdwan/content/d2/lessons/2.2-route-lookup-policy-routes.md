## Key routing principles in SD-WAN

SD-WAN doesn't replace routing. It works inside it. Five principles explain most "why did that packet go there?" questions:

1. **Route lookup happens per session, not per packet.** FortiOS looks up a route for the first packet in the original direction and for the first reply packet, and stores the result in the session. Later packets follow the session until something marks it for re-evaluation (lesson 2.3).
2. **Policy routes are checked before the routing table.** SD-WAN rules are policy routes.
3. **SD-WAN rules still need the routing table.** A rule can only send traffic out of a member that has a usable route to the destination.
4. **Only active routes count.** The routing table (and the kernel FIB built from it) contains only the best routes. A route that loses on distance sits in the routing *database* and is invisible to SD-WAN.
5. **New sessions must pass the reverse-path check.** When the first packet of a session arrives, FortiOS drops it if there is no active route back to its source through the incoming interface (feasible-path RPF by default; `set strict-src-check enable` in `config system settings` makes it strict, requiring the *best* route back to use that interface). This matters for inbound sessions on a backup member.

### Routing table selection, quickly

Among routes to the same destination, the routing table installs routes in this order of preference:

1. **Longest prefix**. A /24 beats a /0, whatever the distance.
2. **Lowest administrative distance**. Static default 10. Higher-distance routes are not installed.
3. If distances tie, **all** of them are installed, and **priority** (static default 1, lower wins) and cost/metric decide which ones are preferred.
4. If everything ties: **ECMP**.

This is why SD-WAN designs use **priority, not distance,** for backup members. A backup member with a higher distance has no active route, so no SD-WAN rule can use it. With a higher priority, the route is still active and rules can use it, while the implicit rule's ECMP set excludes it.

## Policy routes

Regular policy routes (PBR) live in **Network > Policy Routes** (`config router policy`). They match on incoming interface, source and destination address, protocol and port range, ToS/mask, and, since 7.6.3, **users and groups** (`set users`, `set groups`). The action is either:

| GUI action | CLI `action` | Effect |
|------------|--------------|--------|
| Forward Traffic | `permit` (default) | Send the packet to `output-device` / `gateway` |
| Stop Policy Routing | `deny` | **Stop searching the policy route table** and use the routing table |

A `permit` policy route needs enough information to forward the packet: an outgoing interface, a gateway, or both, and FortiOS must be able to resolve the rest from the routing table. With only an interface, it looks up the gateway via that interface. With only a gateway, it looks up the interface. With both, the gateway must be routable over that interface. If any of this fails, the policy route doesn't match and the search continues down the list.

```text
FGT-Branch1 # config router policy
FGT-Branch1 (policy) # edit 1
FGT-Branch1 (1) # set input-device "port3"
FGT-Branch1 (1) # set src "10.1.50.0/255.255.255.0"
FGT-Branch1 (1) # set dst "0.0.0.0/0.0.0.0"
FGT-Branch1 (1) # set output-device "port2"
FGT-Branch1 (1) # set gateway 198.51.100.1
FGT-Branch1 (1) # end
```

> **Watch out:** A policy route forgotten from before SD-WAN, or a broad "Stop Policy Routing" entry, overrides **every** SD-WAN rule for the traffic it matches. A `deny` route skips the rest of the policy route table, and that table includes the SD-WAN rules. The packet goes straight to the FIB and the implicit rule.

## The route lookup process

FortiOS resolves the egress for a new session in this order:

1. **Policy-based routes.** Within the policy route table, the precedence is:
   1. Regular policy routes (`config router policy`), top-down
   2. **ISDB routes** (static routes whose destination is an Internet Service)
   3. **SD-WAN rules**, top-down, first match
2. **The FIB** (the kernel routing table). For SD-WAN destinations this is where the **implicit rule** and `load-balance-mode` apply.
3. **No match: drop.**

An **ISDB route** is configured as a static route (**Network > Static Routes**, Destination = Internet Service, or `set internet-service <id>` in `config router static`). FortiOS treats it as a special kind of policy route, so it appears in the policy route list rather than the routing table.

```text
FGT-Branch1 # diagnose firewall proute list
list route policy info(vf=root):
id=1(0x01) dscp_tag=0xfc 0xfc flags=0x0 tos=0x00 tos_mask=0x00 protocol=0 port=src(0->0):dst(0->0) iif=9(port3)
path(1): oif=4(port2) gwy=198.51.100.1
source wildcard(1): 10.1.50.0/255.255.255.0
destination wildcard(1): 0.0.0.0/0.0.0.0
hit_count=12 rule_last_used=2026-10-27 09:14:02

id=2131820545(0x7f110001) vwl_service=1(Critical-DIA) vwl_mbr_seq=1 2 dscp_tag=0xff 0xff flags=0x0 tos=0x00 tos_mask=0x00 protocol=0 sport=0-65535 iif=0 dport=1-65535 path(2) oif=3(port1) oif=4(port2)
destination(1): 192.0.2.0-192.0.2.255
source wildcard(1): 0.0.0.0/0.0.0.0
hit_count=388 last_used=2026-10-27 09:15:40
```

How to read it:

* The **low ID** (`id=1`) is the user policy route.
* The entry with `vwl_service=1(Critical-DIA)` is SD-WAN rule 1. `vwl_mbr_seq=1 2` is the current member order and `oif=` lists the egress interfaces in that order. SD-WAN rules and ISDB routes get large internal IDs.
* `hit_count` tells you whether anything is actually matching.

In the GUI, **Dashboard > Network > Static & Dynamic Routing** has a **Policy** toggle that lists the active policy routes, which include your policy routes, SD-WAN rules and Internet Service static routes.

## The two FIB checks behind every SD-WAN rule

Before an SD-WAN rule may steer a packet, FortiOS performs two FIB lookups:

1. **The FIB best match for the destination must be an SD-WAN member.** If the most specific route points somewhere else, such as a /24 through a non-SD-WAN interface, the rule is not used for that destination.
2. **A route to the destination must exist through the chosen member.** Members without such a route are skipped. If no member of the rule qualifies, the whole rule is skipped and evaluation continues with the next rule.

Two CLI-only rule options (both `disable` by default) change this:

| Setting | Effect |
|---------|--------|
| `set gateway enable` (with `default disable`) | Check 1 still applies. Check 2 becomes "a route to the member's **gateway IP** must exist over any interface", and traffic is sent to the member's configured `gateway` |
| `set default enable` + `set gateway enable` | **Both** checks are bypassed. Matching traffic goes to the chosen member's configured gateway. Members must have a `gateway` configured |

> **Exam tip:** Typical symptom: a DC rule prefers `HUB1-VPN1`, but traffic for 10.10.0.0/16 still leaves through port1 to the internet. The overlay has no route to 10.10.0.0/16 (BGP isn't up, or the static route is missing), so check 2 fails for every member. The rule is skipped, and the implicit rule sends the traffic out of the default route. Check `get router info routing-table all` before you blame the rule.

## Putting it together

```text
FGT-Branch1 # get router info routing-table all
...
Routing table for VRF=0
S*      0.0.0.0/0 [1/0] via 203.0.113.1, port1, [1/0]
                  [1/0] via 198.51.100.1, port2, [1/0]
C       10.1.50.0/24 is directly connected, port3
S       10.10.0.0/16 [1/0] via HUB1-VPN1 tunnel 10.255.1.1, [1/0]
C       198.51.100.0/29 is directly connected, port2
C       203.0.113.0/29 is directly connected, port1
```

* Traffic to 10.10.1.20 matching a rule with `priority-members 3 4` (`HUB1-VPN1`, `HUB1-VPN2`) uses `HUB1-VPN1`. If only `HUB1-VPN2` were left, it would fail check 2, because there is no route to 10.10.0.0/16 through it.
* Traffic to 8.8.8.8 with no matching rule uses the default route ECMP set through port1 and port2, spread by `load-balance-mode`.

## Lab it yourself

With the trial's three-route limit, use one zone default route plus one or two specific routes:

1. Configure `Critical-DIA` for one test host, preferring port2. Add a user policy route above it that sends the same host out of port1. Check `diagnose firewall proute list` and a sniffer. The policy route wins.
2. Change the policy route action to **Stop Policy Routing** (`set action deny`). Traffic now ignores the SD-WAN rule too and follows the implicit rule.
3. Delete the policy route. Add a /32 static route for the test host through port3 (a non-member) using a LAN-side Linux gateway. The rule stops applying (check 1). Try `set default enable` and `set gateway enable` on the rule and watch the traffic return to port2.

## Key takeaways

* Lookup order: policy routes (user PBR → ISDB routes → SD-WAN rules), then the FIB (where the implicit rule applies), then drop.
* A policy route with `action deny` (Stop Policy Routing) skips the rest of the policy table, SD-WAN rules included.
* Routing table preference: longest prefix, distance, then priority (routes stay active), then ECMP.
* Use **priority**, not distance, for backup SD-WAN members. A higher-distance route isn't active, so rules can't use it.
* An SD-WAN rule needs (1) the FIB best match to be an SD-WAN member and (2) a route through the chosen member. `gateway` and `default` relax these checks.
* `diagnose firewall proute list` shows policy routes and SD-WAN rules (`vwl_service`, member order, hit count).
