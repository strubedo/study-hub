## Why SD-WAN needs static routes at all

Enabling SD-WAN and adding members creates **no route**. Each member's `gateway` is just data in the SD-WAN configuration until a route uses it. You still have to tell the routing table which destinations are reachable through SD-WAN. There are three building blocks:

| Route type | How it is configured | Result in the routing table |
|------------|---------------------|-----------------------------|
| **Static route to a zone** | `config router static` → `set sdwan-zone "<zone>"` | One route per member of the zone, through each member's gateway, using each member's `priority` |
| **Member static route** | `config router static` → `set device "<member>"` + `set gateway` | A normal static route through that one member |
| **Dynamic routes** | BGP or OSPF over overlays | Learned routes, often via ADVPN overlays (NSE 7 level) |

Plus one type you don't configure: the **probe routes** that SD-WAN adds for its health checks.

## Static routes for zones

The usual DIA design is one default route pointing at the underlay zone:

```text
FGT-Branch1 # config router static
FGT-Branch1 (static) # edit 1
FGT-Branch1 (1) # set distance 1
FGT-Branch1 (1) # set sdwan-zone "underlay"
FGT-Branch1 (1) # end
```

No `dst` means 0.0.0.0/0, and no gateway is needed, because FortiOS takes each member's `gateway` from `config system sdwan`. The GUI equivalent is **Network > Static Routes > Create New** with **Interface** set to the zone. You can list several zones in one route (`set sdwan-zone "underlay" "overlay"`), and the same works for IPv6 in `config router static6`.

```text
FGT-Branch1 # get router info routing-table all
...
S*      0.0.0.0/0 [1/0] via 203.0.113.1, port1, [1/0]
                  [1/0] via 198.51.100.1, port2, [1/0]
```

The trailing `[1/0]` on each next hop is the route's **priority/weight**. The zone route copies the member's priority. Add a member to the zone and it joins the route automatically. Remove it and it disappears.

> **Exam tip:** The zone route takes its next hops from the members' `gateway` settings. IPsec tunnel members don't need one, and DHCP/PPPoE interfaces can learn it dynamically. When a zone route shows an unexpected or missing next hop, check the member's `gateway` first.

## Member priority and the member static route

Each member has a **priority** (`set priority`, 1–65535, **default 1**). The guide describes it as being used "in the static route created for the SD-WAN member" and in SD-WAN rules, including the implicit rule. Lower is better.

```text
FGT-Branch1 # config system sdwan
FGT-Branch1 (sdwan) # config members
FGT-Branch1 (members) # edit 2
FGT-Branch1 (2) # set priority 10
FGT-Branch1 (2) # end
FGT-Branch1 (sdwan) # end

FGT-Branch1 # get router info routing-table all
...
S*      0.0.0.0/0 [1/0] via 203.0.113.1, port1, [1/0]
                  [1/0] via 198.51.100.1, port2, [10/0]
```

Both next hops stay in the routing table (same distance), so:

* The **implicit rule** uses only port1, because only the lowest-priority routes form the ECMP set.
* **SD-WAN rules** can still send matching traffic to port2. Its route is active, so FIB check 2 passes.
* **Inbound** sessions to port2 (for example to a VIP on port2's address) pass RPF, because there is an active route back through port2.

Had port2 been given a **higher distance** instead, its route would drop out of the routing table. Rules couldn't use port2, and inbound traffic on port2 would fail RPF while port1 is up.

A **member static route** points at one member directly, for example a route to a partner network that is only reachable through one ISP:

```text
FGT-Branch1 # config router static
FGT-Branch1 (static) # edit 2
FGT-Branch1 (2) # set dst 192.0.2.0 255.255.255.0
FGT-Branch1 (2) # set device "port2"
FGT-Branch1 (2) # set gateway 198.51.100.1
FGT-Branch1 (2) # end
```

Members can be used in static routes and SD-WAN rules. What members **can't** be used in is **firewall policies**, which reference the zone. A member that needs its own policy has to be in its own zone.

## Update static route: when routes are withdrawn

A health check with `set update-static-route enable` (the default) withdraws a member's static routes when it declares the member **dead**, and restores them on recovery. With several health checks on one member, all of them have to fail. The event is logged as `logid="0100022921"`, "Routing information changed":

```text
logid="0100022921" type="event" subtype="system" level="critical" vd="root" logdesc="Routing information changed" name="Internet_HC" interface="port1" status="down" msg="Static route on interface port1 may be removed by health-check Internet_HC. Route:  (203.0.113.2->198.51.100.10 ping-down)"
```

Route withdrawal drives the whole failover. The zone route loses port1's next hop, the implicit rule stops using port1, and SD-WAN rules skip port1 because FIB check 2 now fails. Individual routes can opt out with `set link-monitor-exempt enable` in `config router static`.

## Member probe routes

Health-check probes must leave through **each** member to measure it, whatever the routing table prefers. If probes to 198.51.100.10 followed the normal default route, every probe would leave through port1 and port2's measurement would be meaningless.

SD-WAN solves this by adding **dedicated kernel routes** for each health-check server through each member. They are host routes, sourced from the member's IP address (or from the member's `source` setting, if configured), through the member's gateway. They live in the **kernel FIB** (`proto=17`), not in the routing table:

```text
FGT-Branch1 # get router info kernel
...
tab=254 vf=0 scope=0 type=1 proto=17 prio=0 203.0.113.2/255.255.255.255/0->198.51.100.10/32 pref=0.0.0.0 gwy=203.0.113.1 dev=3(port1)
tab=254 vf=0 scope=0 type=1 proto=17 prio=0 198.51.100.2/255.255.255.255/0->198.51.100.10/32 pref=0.0.0.0 gwy=198.51.100.1 dev=4(port2)
```

Each entry matches **source** = member IP and **destination** = probe server, so it only affects probes, not user traffic to the same server. `get router info routing-table all` doesn't show these routes. Use `get router info kernel` or `diagnose ip route list`.

Consequences worth knowing:

* Probes **aren't steered by SD-WAN rules**. A rule whose destination includes 198.51.100.10 doesn't redirect health-check traffic. The probes are local-out traffic tied to the member they measure.
* A probe server reachable only through one member makes the other member look dead. Pick a server every member can reach, and remember that a health-check server can be used in only one health check.

## Use cases

* **Active/active DIA.** Both underlay members at the same priority in the zone default route, `source-ip-based` implicit rule, and rules for specific apps.
* **Primary/backup DIA with rules that still reach the backup.** Backup member `priority 10`. The implicit rule uses only the primary, while a Lowest Cost (SLA) rule can still choose the backup when the primary fails the SLA.
* **Overlay for DC, underlay for internet.** Zone route for `overlay` to the DC summary (for example 10.10.0.0/16), zone default route for `underlay`, plus a blackhole route for 10.10.0.0/16 with a high distance so DC traffic never leaks to the internet when both tunnels are down.

## Lab it yourself

This fits the three-route trial limit:

1. Route 1: default route to the `underlay` zone (port1 + port2). Check that `routing-table all` shows two next hops with `[1/0]`.
2. Set port2's member priority to 10 and check the `[10/0]`. Confirm with `diagnose sys session list` that new implicit-rule sessions use only port1, while a Manual rule preferring port2 still works.
3. Run `get router info kernel | grep proto=17` and find the probe routes for your health-check server.
4. Make port1's probe server unreachable (block ICMP on the upstream Linux router). Watch the `0100022921` log, the port1 next hop leaving the zone route, and the implicit rule moving to port2.

## Key takeaways

* SD-WAN members create no routes by themselves. Add a static route to the zone (`sdwan-zone`) or to a member, or learn routes dynamically.
* A zone route expands into one next hop per member, using each member's gateway and `priority` (default 1, lower preferred).
* Use priority for backup members: their route stays active for rules and RPF, but the implicit rule ignores them.
* Members work in static routes and SD-WAN rules. Firewall policies need zones.
* `update-static-route` (default enable) withdraws a dead member's routes. That withdrawal is what moves traffic.
* Probe routes are kernel-only (`proto=17`) host routes per member and probe server, so probes always leave through the member being measured.
