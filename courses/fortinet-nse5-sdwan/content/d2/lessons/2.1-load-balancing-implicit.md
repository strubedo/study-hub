## Two kinds of load balancing

SD-WAN can spread sessions over several members in two places:

1. **Inside an SD-WAN rule**, with `set load-balance enable`. Only traffic that matches the rule is spread, over the rule's members, using the rule's `hash-mode`.
2. **In the implicit rule**, which handles everything no rule matched. It spreads sessions over the ECMP routes using the global `load-balance-mode`.

Both work **per session**, not per packet. One large download always stays on one member.

## Load balancing in an SD-WAN rule

Before FortiOS 7.4.1 this was a separate strategy, **Maximize Bandwidth (SLA)**. In 7.6 it is a toggle:

| Rule mode | With `load-balance enable` | Members used |
|-----------|---------------------------|--------------|
| `manual` | Load balancing **without** SLA targets | All listed members that can forward the traffic |
| `sla` | Load balancing **with** SLA targets (the old Maximize Bandwidth (SLA)) | All members that **meet the SLA**. **Cost is ignored** |

Under `sla`, if no member meets the SLA but members are still alive, they tie and the rule balances over all of them. Adding `minimum-sla-meet-members` makes the rule step aside instead, as in the previous lesson.

```text
FGT-Branch1 # show system sdwan
config system sdwan
    ...
    config service
        edit 5
            set name "Bulk-Web"
            set mode sla
            set load-balance enable
            set hash-mode source-ip-based
            set dst "all"
            set protocol 6
            set start-port 443
            set end-port 443
            config sla
                edit "Internet_HC"
                    set id 1
                next
            end
            set priority-members 1 2
        next
    end
end
```

```text
FGT-Branch1 # diagnose sys sdwan service4 5

Service(5): Address Mode(IPV4) flags=0x200
  Gen(2), TOS(0x0/0x0), Protocol(6: 443->443), Mode(load-balance hash-mode=source-ip-based)
  Members(2):
    1: Seq_num(1 port1), alive, sla(0x1), gid(2), num of pass(1), selected
    2: Seq_num(2 port2), alive, sla(0x1), gid(2), num of pass(1), selected
  Dst address(1):
        0.0.0.0-255.255.255.255
```

Both members pass SLA 1, so both are `selected` and share the sessions. Note that diagnose still reports the mode as `load-balance` even though the configured mode is `sla`.

### Hash modes

| `hash-mode` | Behaviour |
|-------------|-----------|
| `round-robin` (**default**) | Sessions go to the selected members in turn. The **only option in the GUI** |
| `source-ip-based` | One source IP always uses the same member |
| `source-dest-ip-based` | One source/destination pair always uses the same member |
| `inbandwidth` | The member with the most available inbound bandwidth |
| `outbandwidth` | The member with the most available outbound bandwidth |
| `bibandwidth` | The member with the most available bandwidth in both directions |

The bandwidth modes compare **configured** link sizes (`estimated-upstream-bandwidth` / `estimated-downstream-bandwidth` on each interface, in kbps, or speed-test results) against measured use. Without those values they have nothing to compare.

> **Real world:** Round-robin can send consecutive sessions from one user out of different public IPs. Some websites and banking portals treat that as a hijack and log the user out. Use `source-ip-based` for user-facing internet traffic, or keep such sites in a non-balanced rule.

## The implicit rule

When no rule matches, or every matching rule is skipped, the FortiGate falls back to the **routing table**. In a typical SD-WAN design, the default route points at the SD-WAN zone, so there is an ECMP route through every member's gateway. How sessions are spread across those routes is set once, globally:

```text
FGT-Branch1 # config system sdwan
FGT-Branch1 (sdwan) # set load-balance-mode weight-based
FGT-Branch1 (sdwan) # end
```

| GUI (Load Balancing Algorithm) | `load-balance-mode` | Member settings used |
|--------------------------------|---------------------|----------------------|
| **Source IP** (default) | `source-ip-based` | None. A hash of the source IP picks the member |
| Sessions | `weight-based` | `weight` (1–255, default 1): share of sessions |
| Spillover | `usage-based` | `spillover-threshold` (egress) and `ingress-spillover-threshold`, in kbit/s |
| Source-Destination IP | `source-dest-ip-based` | None. Hash of source and destination |
| Volume | `measured-volume-based` | `volume-ratio` (1–255, default 1): share of bytes |

In the GUI, edit the **sd-wan** entry at the bottom of the SD-WAN Rules list. With SD-WAN enabled, `config system settings` → `v4-ecmp-mode` is no longer available. `load-balance-mode` replaces it and adds the Volume mode, which plain ECMP doesn't have.

### Rules of the implicit rule

* **You can't exclude a member with weight or volume.** Neither can be 0. A 0 carried over from an older release is treated as 1.
* **To keep a member out of the implicit rule, give it a higher `priority` value.** Its static route stays in the routing table, but only the lowest-priority routes form the ECMP set. Rules can still use that member, because its route is still active.
* **Spillover fills the first member up to its thresholds, then moves new sessions to the next member.** It can only measure the traffic if it sees it, which is why the guide's spillover example disables `auto-asic-offload` on the firewall policy.
* **Weights apply only to static ECMP routes.** With dynamic routing (BGP, OSPF) the sessions are spread equally regardless of weight.

```text
FGT-Branch1 # diagnose sys sdwan member
Member(1): interface: port1, gateway: 203.0.113.1, priority: 1 1024, weight: 3
  Session count: 241
Member(2): interface: port2, gateway: 198.51.100.1, priority: 1 1024, weight: 1
  Session count: 79
```

That output is `weight-based` with weights 3:1. It prints per-member session counts, and 241:79 is roughly the expected 3:1 split. The two `priority` values are the IPv4 priority and the IPv6 `priority6` (default 1024). The other modes print other details. `measured-volume-based` shows the configured volume ratio and remaining "volume room", and `usage-based` shows the spillover thresholds and whether each member is over them.

## Use cases: picking the strategy

| Requirement | Strategy |
|-------------|----------|
| "Always use the MPLS overlay for DC traffic, internet VPN only if MPLS is down" | Manual, overlay first |
| "Voice must use whichever link has the least jitter right now" | Best Quality, `link-cost-factor jitter` |
| "Use the free broadband link unless it is worse than 150 ms / 2% loss" | Lowest Cost (SLA), broadband cost 0 |
| "Use both internet links for web traffic, but never a link that is out of SLA" | Lowest Cost (SLA) + load balancing |
| "Spread guest traffic over both links, quality doesn't matter" | Manual + load balancing |
| "Everything else: 80% of sessions on fibre, 20% on cable" | Implicit rule, `weight-based`, weights 80/20 |
| "Use the fixed-price link up to 50 Mbps, then the metered link" | Implicit rule, `usage-based` (spillover) |

> **Exam tip:** A requirement that mentions **cost** is not the same as one that mentions **bandwidth**. "Cheapest link that meets the SLA" means Lowest Cost (SLA). "Use every good link" means load balancing, which ignores cost.

## Lab it yourself

1. Remove all rules so only the implicit rule is left. Generate traffic from two LAN source IPs (add a secondary IP on the Linux client) and check with `diagnose sys session list` that each source sticks to one member under `source-ip-based`.
2. Switch to `weight-based` with weights 3 and 1. Open a few hundred sessions (for example `for i in $(seq 300); do curl -s -o /dev/null https://198.51.100.10/; done`) and compare the counts in `diagnose sys sdwan member`.
3. Give member 2 `priority 10`. Confirm in `get router info routing-table all` that both default routes are still there, and that new implicit-rule sessions use only port1.
4. Create a Manual rule with `load-balance enable` for one destination and watch round-robin alternate members session by session.

## Key takeaways

* Load balancing in a rule is `set load-balance enable` under `manual` (no SLA) or `sla` (only in-SLA members, cost ignored). It replaced Maximize Bandwidth (SLA) in 7.4.1.
* `hash-mode` default is `round-robin`, the only GUI option. The bandwidth modes need estimated bandwidth values.
* The implicit rule handles unmatched traffic with `load-balance-mode`: `source-ip-based` (default), `weight-based`, `usage-based`, `source-dest-ip-based`, `measured-volume-based`.
* Weight and volume ratio can't be 0. Exclude a member from the implicit rule with a higher route priority.
* All SD-WAN load balancing is per session.
