## Lowest Cost (SLA) in one sentence

A Lowest Cost (SLA) rule (`set mode sla`) uses **the cheapest member that meets the required SLA target**. If members tie on cost, the one listed first in the preference order wins.

Three inputs feed the election:

| Input | Where it is set | Notes |
|-------|-----------------|-------|
| SLA state | Health check SLA target(s), referenced in the rule's `config sla` | Pass/fail per member, re-evaluated with every probe |
| Cost | `config members` → `set cost` | 0–4294967295, **default 0**, lower is preferred. Only `sla` mode uses it |
| Configured order | `priority-members` / `priority-zone` | Tie-breaker (shown as `cfg_order` in diagnose output) |

## Configuring the rule

The GUI calls the SLA reference **Required SLA target**: pick a performance SLA and one of its targets. In the CLI, `config sla` inside the rule names the health check and the target ID:

```text
FGT-Branch1 # show system sdwan
config system sdwan
    set status enable
    config zone
        edit "virtual-wan-link"
        next
        edit "underlay"
        next
    end
    config members
        edit 1
            set interface "port1"
            set zone "underlay"
            set gateway 203.0.113.1
            set cost 20
        next
        edit 2
            set interface "port2"
            set zone "underlay"
            set gateway 198.51.100.1
            set cost 5
        next
    end
    config health-check
        edit "Internet_HC"
            set server "198.51.100.10"
            set members 1 2
            config sla
                edit 1
                    set latency-threshold 100
                    set jitter-threshold 30
                    set packetloss-threshold 2
                next
            end
        next
    end
    config service
        edit 1
            set name "Critical-DIA"
            set mode sla
            set dst "SaaS-Net"
            config sla
                edit "Internet_HC"
                    set id 1
                next
            end
            set priority-members 1 2
        next
    end
end
```

Port1 is listed first, but port2 is cheaper (cost 5 against 20). The election goes like this:

| SLA state | Member used | Why |
|-----------|-------------|-----|
| Both members meet SLA 1 | **port2** | Lowest cost among members that pass |
| Only port1 meets SLA 1 | **port1** | A passing member always beats a failing one, whatever the cost |
| Only port2 meets SLA 1 | **port2** | Only passing member |
| Neither meets SLA 1, both alive | **port2** | No member passes, so cost decides among the alive members |
| Both pass, equal cost | **port1** | Tie goes to the configured order |

> **Exam tip:** A member that fails the SLA isn't removed from the rule. It moves *below* the members that pass and stays available as a backup. Only a **dead** member (failed probes up to `failtime`) stops being a candidate.

## SLA target maps

A health check can define several SLA targets (`config sla` → `edit 1`, `edit 2`, …), for example a strict one for voice and a relaxed one for web. For each member, FortiOS keeps a **bitmap of the targets it currently meets**, printed as `sla_map`:

| Bit | Value | Target ID |
|-----|-------|-----------|
| 0 | 0x1 | 1 |
| 1 | 0x2 | 2 |
| 2 | 0x4 | 3 |

So `sla_map=0x3` means the member meets targets 1 **and** 2, `0x2` means only target 2, and `0x0` means none.

```text
FGT-Branch1 # diagnose sys sdwan health-check Internet_HC
Health Check(Internet_HC):
Seq(1 port1): state(alive), packet-loss(0.000%) latency(18.402), jitter(1.115) sla_map=0x1
Seq(2 port2): state(alive), packet-loss(4.000%) latency(22.730), jitter(2.904) sla_map=0x0
```

Port2 loses 4% of probes, which is over the 2% target, so its map is 0x0. Port1 passes target 1. The rule output reflects the same thing per member:

```text
FGT-Branch1 # diagnose sys sdwan service4 1

Service(1): Address Mode(IPV4) flags=0x200
  Gen(7), TOS(0x0/0x0), Protocol(0: 1->65535), Mode(sla), sla-compare-order
  Members(2):
    1: Seq_num(1 port1), alive, sla(0x1), gid(0), cfg_order(0), cost(20), selected
    2: Seq_num(2 port2), alive, sla(0x0), gid(0), cfg_order(1), cost(5), selected
  Dst address(1):
        192.0.2.0-192.0.2.255
```

Port1 is first despite cost 20, because it is the only member in SLA. When port2 recovers, the order flips back and FortiOS logs it:

```text
logid="0113022923" type="event" subtype="sdwan" level="notice" logdesc="SDWAN status" eventtype="Service" serviceid=1 service="Critical-DIA" seq="2,1" msg="Service prioritized by SLA will be redirected in sequence order."
```

Two more `0113022923` messages appear when a health check's SLA results change: `"Number of pass member changed."` (with `oldvalue`/`newvalue`) and `"Member status changed. Member out-of-sla."` / `"… Member in sla."`. The periodic `0113022925` "SDWAN SLA information" log carries `slamap="0x…"`.

> **Watch out:** `sla_map` in the health-check output describes the **health check's** targets. A Best Quality or Manual rule ignores it completely. Only `sla` rules (and load balancing under `sla`) act on it.

### Several SLA targets in one rule

A rule's `config sla` can list more than one health check. With the default `sla-compare-method order`, the health checks are compared in the order they are listed. `sla-compare-method number` instead ranks members by **how many** of the listed checks they pass. The `sla-compare-order` tag in the `service4` header shows the default method in use.

## The minimum-sla-meet-members parameter

By default a Lowest Cost rule applies **even when no member meets the SLA**. It simply uses the best of the bad links. Sometimes you would rather the rule step aside so a different rule can handle the traffic. That is what `minimum-sla-meet-members` in `config service` does:

```text
FGT-Branch1 (service) # edit 4
FGT-Branch1 (4) # set name "DC-Apps"
FGT-Branch1 (4) # set mode sla
FGT-Branch1 (4) # set dst "DC-Net"
FGT-Branch1 (4) # set priority-members 3 4
FGT-Branch1 (4) # set minimum-sla-meet-members 1
FGT-Branch1 (4) # end
```

* Default **0**: the rule always applies, whatever the SLA state.
* Set to *N*: if fewer than *N* members meet the SLA, the rule **does not take effect**. Matching traffic falls through to the next rule, and finally to the implicit rule.

In the example, if both overlay tunnels fall out of SLA, `DC-Apps` is skipped. A lower rule (for instance one that sends DC traffic over an internet IPsec tunnel through a different hub) or the implicit rule takes over.

> **Watch out:** `minimum-sla-meet-members` also exists under `config zone` (range 1–255, default 1). There it is part of the **BGP neighbor / SD-WAN neighbor** feature: the number of members of the zone that must meet SLA for the neighbor to be considered preferred. It doesn't control whether a rule applies. Questions about a *rule* refer to the `config service` setting.

## Tie-breaks and failback

* `set tie-break` (rule) controls which member wins when several meet the SLA at equal cost. The default `zone` uses the zone's `service-sla-tie-break`, which defaults to `cfg-order` (configured order). The other choices in the 7.6.4 CLI Reference are `fib-best-match` (the member with the longest-prefix route to the destination) and `input-device` (the member that matches the input device).
* `set hold-down-time <s>` (default 0) delays the move back to a recovered member. It helps when a link oscillates around the threshold.
* Health-check timers matter too. With the defaults, a member needs 5 failed probes (`failtime`) to be marked dead and 5 good ones (`recoverytime`) to come back, at a 500 ms `interval`. SLA latency and jitter targets are calculated over the last 30 probes and packet loss over the last 100, so SLA state responds to sustained degradation, not to one bad probe.

## Use cases

* **Cheap link first, if it is good enough.** Broadband cost 0, LTE cost 100, Lowest Cost on a moderate SLA. Broadband carries traffic unless it fails the SLA and LTE passes.
* **Primary overlay with a quality floor.** Overlay tunnels in an `sla` rule with `minimum-sla-meet-members 1`. When neither tunnel is usable, the rule is skipped and a backup rule sends the traffic through direct internet with a different security path.
* **Two SLA classes on one probe.** One health check with target 1 (voice: 150 ms, 30 ms, 1%) and target 2 (web: 250 ms, 50 ms, 5%). The voice rule requires target 1 and the web rule requires target 2. One set of probes serves both.

## Lab it yourself

1. Use the configuration above with `Internet_HC` pointing at a Linux host on each side. Confirm port2 is selected while both are in SLA.
2. Add 5% loss on port2's path (`tc qdisc add dev eth0 root netem loss 5%`). Within about 100 probes the `sla_map` drops to 0x0, the rule order flips, and a `0113022923` log appears in **Log & Report > System Events** (SD-WAN events).
3. Add loss to port1 as well and confirm that the rule falls back to port2 (lowest cost) with nobody in SLA.
4. Set `minimum-sla-meet-members 1` and repeat step 3. Now traffic follows the implicit rule. Check with `diagnose sys sdwan service4 1` and a sniffer.

## Key takeaways

* Lowest Cost (SLA) = `mode sla`: members in SLA first, then lowest `cost` (default 0), then configured order.
* Failing the SLA moves a member down the list. Only dead members disappear.
* With nobody in SLA, the rule still applies by default and uses the lowest-cost alive member.
* `sla_map` is a bitmap of the SLA targets a member meets: 0x1 = target 1, 0x2 = target 2, 0x3 = both.
* `minimum-sla-meet-members` (rule, default 0) makes the rule step aside when too few members are in SLA. The `config zone` setting of the same name belongs to the BGP neighbor feature.
* Logs: `0113022923` for SLA and rule changes, `0113022925` for periodic SLA information.
