## Sessions outlive decisions

Every SD-WAN decision (rule match, member choice, route lookup) is made when a session starts and is then cached in the session. Link conditions change all the time, though. A member falls out of SLA, a tunnel recovers, an administrator edits a rule or a policy. What happens to the sessions that already exist depends on **what changed** and on **whether the session is source-NATed**.

FortiOS uses the `may_dirty` / `dirty` session flags for this. A session marked **dirty** is re-evaluated when its next packet arrives.

## Re-evaluation triggers

| Trigger | Default effect on existing sessions | Controls |
|---------|-------------------------------------|----------|
| **Firewall policy change** | Affected sessions are re-evaluated against the new policy set (`check-all`) | `config system settings` → `set firewall-session-dirty` (`check-all`, `check-new` or `check-policy-option`) |
| **Routing change, no SNAT** | Route information is flushed from sessions. The next packet triggers a new route lookup | `config system interface` → `set preserve-session-route enable` |
| **Routing change, SNAT session** | The session **keeps its outbound interface** as long as the old route is still active | `config system global` → `set snat-route-change enable` |
| FQDN, dynamic address or external resource updates | Optional dirty checks | `fqdn-session-check`, `dyn-addr-session-check`, `ext-resource-session-check` in `config system settings` (all three default to disable) |

What counts as a **routing change** in an SD-WAN context:

* A member's static routes are withdrawn or restored by a health check (`update-static-route`, logid `0100022921`).
* A route's priority or distance changes, or a dynamic route is added or removed.
* An SD-WAN rule's member order changes because of SLA or quality measurements (logid `0113022923`, "…will be redirected in sequence order"). The rule's policy route is regenerated. `link-cost-threshold` is literally defined as the change that "will result in policy route regeneration". Fortinet's `sla-stickiness` documentation confirms the effect on existing sessions: when the preferred member goes out of SLA, existing sessions switch to the next member, and `sla-stickiness` exists precisely to stop that.

## firewall-session-dirty

| Value | Behaviour |
|-------|-----------|
| `check-all` (**default**) | All sessions affected by a policy change are flushed and re-evaluated when their next packet arrives. A session the new policies deny is blocked (`block` flag) |
| `check-new` | Established sessions continue unaffected. Only new sessions see the change |
| `check-policy-option` | Decided per firewall policy |

On a busy FortiGate, `check-all` can cause a CPU spike after every policy edit. `check-new` avoids that, but then a policy you tightened doesn't cut existing sessions.

## Route changes without SNAT

Typical case: branch-to-DC traffic over the overlay without NAT. When a route changes, FortiOS flushes the routing information from the sessions, and the next packet of each session takes a fresh route. That means existing flows **follow the new best path immediately**. Because the source address doesn't change, TCP sessions survive the move.

`set preserve-session-route enable` (an interface setting) marks existing session routes as persistent. Only new sessions use the new route. Use it when moving flows mid-stream is worse than leaving them where they are, for example on a stateful device downstream that would drop mid-session packets arriving from a new path.

## Route changes with SNAT

Typical case: direct internet access, where traffic is NATed to the member's address. Moving such a session to another member would change its public source IP. The server would see packets from an unknown address, and a TCP session would break anyway. So by default FortiOS does the opposite of the non-SNAT case:

* **If the old route is still active** (for example a priority changed, or an `sla` rule now prefers the other member because the current member is out of SLA but still alive), the SNAT session **stays on its original member** until it ends.
* **If the old route is gone** (the member is dead and `update-static-route` withdrew its routes), the condition behind the default ("as long as the old route is still active") no longer holds. The session can't stay on a route that doesn't exist, and if it ends up on another member it needs that member's SNAT, so a TCP session generally breaks.

`set snat-route-change enable` in `config system global` (default `disable`) makes SNAT sessions take a new route lookup on routing changes, with a new SNAT applied.

```text
FGT-Branch1 # config system global
FGT-Branch1 (global) # set snat-route-change enable
FGT-Branch1 (global) # end
```

An SNAT session after a Lowest Cost (SLA) rule has switched from port2 (out of SLA) to port1:

```text
FGT-Branch1 # diagnose sys session filter dst 192.0.2.80
FGT-Branch1 # diagnose sys session list
session info: proto=17 proto_state=01 duration=412 expire=178 timeout=180 refresh_dir=both flags=00000000 socktype=0 sockport=0 av_idx=0 use=3
...
state=log may_dirty
...
orgin->sink: org pre->post, reply pre->post dev=9->4/4->9 gwy=198.51.100.1/10.1.50.21
hook=post dir=org act=snat 10.1.50.21:5004->192.0.2.80:5004(198.51.100.2:5004)
...
```

With the default `snat-route-change disable`, this UDP media flow stays on port2 (`dev=…->4`, SNAT to 198.51.100.2) even though new sessions now go to port1. The out-of-SLA path keeps hurting the call until the session ends. With `snat-route-change enable`, the next packet is re-routed through port1 and NATed to port1's address. For UDP media that the far end accepts from a new address, the call recovers.

> **Exam tip:** "After a failback, some users' sessions are still on the backup link." If the sessions are SNAT (DIA) and the old link is still up, that's the default behaviour. The fix is `snat-route-change enable`, or simply waiting for the sessions to end. `preserve-session-route` does the opposite: it *keeps* sessions where they are.

> **Watch out:** `snat-route-change` is global (`config system global`). `preserve-session-route` is per interface (`config system interface`). Don't mix them up in a "which command" question.

## Rule-level stickiness

Two SD-WAN rule options also shape how quickly traffic moves:

* `set hold-down-time <s>` (default 0) is the waiting period before the rule switches from the backup member back to the recovered primary, so the rule's preference (and with it new sessions) doesn't bounce.
* `set sla-stickiness enable` (default disable) works on **existing** sessions: they stay on their original path while that path is still within SLA, even if another member is now preferred. New sessions still follow the rule's current preference. With it disabled, traffic switches to the best path regardless of the SLA.

## Use cases

| Situation | Setting |
|-----------|---------|
| DIA voice or VDI must leave a degraded link immediately, and users accept a reconnect | `snat-route-change enable` |
| Overlay traffic without NAT should follow every rule change | Default behaviour, nothing to change |
| A downstream stateful device drops sessions that change path | `preserve-session-route enable` on the interface |
| Frequent policy edits on a busy unit cause CPU spikes | `firewall-session-dirty check-new` (accept that tightened policies don't affect existing sessions) |
| Traffic flaps between two members that hover around the SLA threshold | `hold-down-time`, or `sla-stickiness` |

## Lab it yourself

1. Use a Lowest Cost (SLA) rule with port2 preferred (lower cost) for a test server. Start a long `ping` (ICMP, SNATed) and a UDP stream (`iperf3 -u -t 600`) from the LAN client.
2. Add 10% loss on port2 with netem so it falls out of SLA but stays alive. New sessions use port1, but the existing SNAT sessions stay on port2 (`diagnose sys session list`, check `dev=` and the SNAT IP).
3. Enable `snat-route-change` and repeat. The existing sessions move to port1 with a new NAT address.
4. Disable NAT on the policy and route the test server through a Linux router (so the lab works without SNAT). Repeat step 2: the sessions now move immediately. Then set `preserve-session-route enable` on the interfaces involved and confirm they stay.

## Key takeaways

* Sessions cache the route and SNAT decision. Re-evaluation needs a trigger: a policy change, a routing change (including a change of SD-WAN member order), or optional address/FQDN checks.
* `firewall-session-dirty` defaults to `check-all`, so policy changes re-evaluate affected sessions.
* Without SNAT: route info is flushed and sessions move on the next packet. `preserve-session-route enable` (interface) keeps them.
* With SNAT: sessions keep their interface while the old route is still active. `snat-route-change enable` (global) forces a new lookup and new SNAT.
* Moving an SNAT session changes its source IP, so TCP sessions break. That is why the default is to leave them.
* `hold-down-time` and `sla-stickiness` reduce flapping at rule level.
