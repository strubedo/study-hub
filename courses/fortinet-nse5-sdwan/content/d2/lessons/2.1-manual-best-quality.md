## Strategies at a glance

A rule's **strategy** (CLI `set mode`) decides how the member order changes as link conditions change. FortiOS 7.6 has these:

| GUI name | CLI | Uses a performance SLA? | How the preferred member is chosen |
|----------|-----|-------------------------|------------------------------------|
| **Manual** | `manual` (default) | No | Configured interface/zone order. The first usable member wins |
| **Best Quality** | `priority` | Yes, as a *measurement* (one metric) | Best value of the chosen `link-cost-factor`, with a bias towards the first-listed member |
| **Lowest Cost (SLA)** | `sla` | Yes, as *pass/fail targets* | Members that meet the SLA target, then lowest `cost`, then configured order |
| Load balancing | `set load-balance enable` inside `manual` or `sla` | Only under `sla` | Spreads sessions across all eligible members (next lessons) |
| Automatic | `auto` (CLI only, legacy) | Yes | Ranks members by quality and uses the member at rank `quality-link` |

> **Exam tip:** The CLI names don't match the GUI names. **Best Quality = `priority`** and **Lowest Cost (SLA) = `sla`**. Manual is the default, so `set mode manual` never appears in `show` output.

"Maximize Bandwidth (SLA)" was a separate strategy before FortiOS **7.4.1**. In 7.6 it is the **load balancing** option inside a Manual or Lowest Cost (SLA) rule. There is no `mode load-balance` in the 7.6 CLI. `diagnose sys sdwan service4` still prints `Mode(load-balance hash-mode=…)` for such a rule.

## Interface and zone preference

Every strategy starts from the **preference list**:

* `set priority-members <seq> <seq> …` lists individual members by sequence number.
* `set priority-zone <zone> …` (GUI **Zone preference**) adds every member of the zone.

The rule's base order is: members in `priority-members` first, in the listed order, then members pulled in through `priority-zone`. Zone members come after explicit interfaces.

Example: port1 and port3 are in `virtual-wan-link`, and port2 is in `Zone1`. A rule with interface preference `port3 port1` and zone preference `Zone1` orders them **port3, port1, port2**.

## Manual: preferred member selection

Manual rules behave like a policy route with extras such as application, ISDB and BGP-tag matching. No health check feeds into the decision:

* Traffic uses the **first member in the preference list** that is usable.
* A member drops out when it can't forward the traffic: the interface is down, or its route to the destination has gone (for example, a health check with `update-static-route enable` withdrew it). The next member in the list takes over.
* Degraded quality (high latency, jitter, partial packet loss) **never** moves traffic in a Manual rule. Only losing the ability to forward does.

```text
FGT-Branch1 # show system sdwan
config system sdwan
    ...
    config service
        edit 2
            set name "Guest-Web"
            set src "Guest-Net"
            set dst "all"
            set priority-members 2 1
            set hold-down-time 60
        next
    end
end
```

Guest traffic prefers member 2. If member 2 becomes unusable, member 1 takes over. `hold-down-time 60` makes the rule wait 60 seconds after member 2 recovers before moving traffic back (default 0, so failback is immediate).

## Best Quality: quality metrics

Best Quality (`mode priority`) measures one metric from the health check named in `set health-check` (GUI **Measured SLA**) and prefers the member with the best value. The metric is `set link-cost-factor`:

| GUI quality criterion | `link-cost-factor` | Better means |
|-----------------------|--------------------|--------------|
| Latency (**default**) | `latency` | Lower round-trip delay |
| Jitter | `jitter` | Lower delay variation |
| Packet Loss | `packet-loss` | Lower loss |
| Downstream | `inbandwidth` | More available inbound bandwidth |
| Upstream | `outbandwidth` | More available outbound bandwidth |
| Bandwidth | `bibandwidth` | More available bandwidth in both directions |
| Customized profile | `custom-profile-1` | Weighted mix: `packet-loss-weight`, `latency-weight`, `jitter-weight`, `bandwidth-weight` |

The bandwidth factors need to know how big each link is. Set `estimated-upstream-bandwidth` and `estimated-downstream-bandwidth` (kbps) on each member interface, or fill them in with the interface speed test. With no values configured, every link looks the same.

Best Quality compares measurements **only**. SLA thresholds don't take part, so a link that is far outside any target is still used if it is the *least bad*. Only members the health check reports as **alive** compete. A dead member drops to the bottom.

Matching the metric to the application:

* Voice and video: jitter, or a custom profile mixing jitter and loss.
* Interactive apps (VDI, SSH): latency.
* File transfers and backups: packet loss, or a bandwidth factor.

## The advantage given to higher-priority members

If two links are almost identical, a strict "best value wins" rule would move traffic back and forth every time the measurements wobble. FortiOS avoids this with `link-cost-threshold` (default **10**, percent). The member listed **first** in the preference order gets a 10% advantage:

```text
FGT-Branch1 # show system sdwan
config system sdwan
    ...
    config service
        edit 3
            set name "VDI"
            set mode priority
            set dst "VDI-Servers"
            set health-check "DC_HC"
            set link-cost-factor latency
            set priority-members 3 4
        next
    end
end
```

Member 3 (`HUB1-VPN1`) is listed first. If both tunnels measure 40 ms, member 3 is evaluated as 40 / 1.1 ≈ 36.4 ms and keeps the traffic. Member 4 only takes over once its latency is clearly better, below about 36.4 ms while member 3 sits at 40 ms.

* `link-cost-threshold 0` removes the bias. The best measurement always wins, with more flapping.
* A larger value makes the first member "stickier".
* `link-cost-threshold` isn't shown in `show` output while it is at its default of 10.

> **Exam tip:** Questions often give two latencies and ask which member is used. Divide the **first-listed** member's value by 1.1 before comparing. The other member's value stays as measured.

## Reading Best Quality status

```text
FGT-Branch1 # diagnose sys sdwan health-check DC_HC
Health Check(DC_HC):
Seq(3 HUB1-VPN1): state(alive), packet-loss(0.000%) latency(40.112), jitter(1.204) sla_map=0x0
Seq(4 HUB1-VPN2): state(alive), packet-loss(0.000%) latency(37.950), jitter(0.988) sla_map=0x0

FGT-Branch1 # diagnose sys sdwan service4 3

Service(3): Address Mode(IPV4) flags=0x200
  Gen(5), TOS(0x0/0x0), Protocol(0: 1->65535), Mode(priority), link-cost-factor(latency), link-cost-threshold(10), health-check(DC_HC)
  Members(2):
    1: Seq_num(3 HUB1-VPN1), alive, latency: 40.112, selected
    2: Seq_num(4 HUB1-VPN2), alive, latency: 37.950, selected
  Dst address(1):
        10.20.0.0-10.20.255.255
```

Member 4 measures 37.950 ms, but member 3's effective value is 40.112 / 1.1 ≈ 36.47 ms, so member 3 stays on top. The `sla_map=0x0` is irrelevant here: Best Quality doesn't use SLA targets.

When the order does change, FortiOS logs an event such as:

```text
logid="0113022923" type="event" subtype="sdwan" level="notice" logdesc="SDWAN status" eventtype="Service" serviceid=3 service="VDI" metric="latency" seq="4,3" msg="Service prioritized by performance metric will be redirected in sequence order."
```

`seq="4,3"` is the new member order.

## Automatic (legacy)

`mode auto` ranks the members by quality using a health check and its SLA, then uses the member at the rank given by `set quality-link` (1 = best). It exists for backward compatibility. It is **CLI only**, and if you open and save the rule in the GUI, the GUI replaces the mode. New designs use Best Quality or Lowest Cost (SLA).

## Lab it yourself

1. Create a health check `DC_HC` to a Linux host behind each WAN link (or one host reachable through both) with both members.
2. Build a Best Quality rule on latency with `priority-members 1 2`. On the Linux router behind port1, add delay with `tc qdisc add dev eth0 root netem delay 30ms`. Watch `service4` and note how far port1's latency has to rise before port2 takes over. Compare that point with your 10% calculation.
3. Set `link-cost-threshold 0` and repeat. Traffic now flips as soon as port2 is better.
4. Change the rule to Manual. Add 300 ms of delay and 20% loss on port1 and confirm that traffic stays on port1.

## Key takeaways

* Manual = `manual` (default), Best Quality = `priority`, Lowest Cost (SLA) = `sla`. Automatic = `auto` is legacy and CLI only. Load balancing is an option, not a mode, since 7.4.1.
* Preference order: `priority-members` first, then members from `priority-zone`.
* Manual ignores quality. It only moves when the preferred member can't forward (down or no route).
* Best Quality compares one `link-cost-factor` (default latency) from one health check. SLA targets don't take part.
* Bandwidth factors need estimated bandwidth values on the interfaces.
* `link-cost-threshold` (default 10%) favours the first-listed member. Divide its value by 1.1 before comparing.
* `hold-down-time` (default 0 s) delays the move back to a recovered preferred member.
