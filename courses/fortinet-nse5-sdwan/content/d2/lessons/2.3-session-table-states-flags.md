## Why the session table matters for SD-WAN

SD-WAN decisions are made **per session**. Once a session exists, its egress interface, gateway, NAT translation and policy are stored in the session entry, and later packets follow the entry. When you want to know which member a flow *actually* uses, as opposed to which member a rule *would* choose for a new session, the session table is the source of truth.

## Viewing and filtering sessions

The GUI view is **Dashboard > FortiView Sessions**. It can filter by column and shows the destination interface, which is a quick way to see the member a flow left through. The CLI gives the full detail:

```text
FGT-Branch1 # diagnose sys session filter clear
FGT-Branch1 # diagnose sys session filter src 10.1.50.21
FGT-Branch1 # diagnose sys session filter dport 443
FGT-Branch1 # diagnose sys session list
```

Each filter is entered on its own line, and they combine. Useful filter keys: `src`, `dst`, `sport`, `dport`, `proto`, `policy`, `sintf`, `dintf`, `nsrc` / `nport` (NAT'd source), `proto-state`, `negate`, and `clear`. `diagnose sys session clear` deletes **every session that matches the current filter**, or every session on the VDOM if no filter is set. Always set a filter first.

## Anatomy of an SD-WAN session

```text
FGT-Branch1 # diagnose sys session list

session info: proto=6 proto_state=11 duration=184 expire=3415 timeout=3600 refresh_dir=both flags=00000000 socktype=0 sockport=0 av_idx=0 use=3
origin-shaper=
reply-shaper=
per_ip_shaper=
class_id=0 ha_id=0 policy_dir=0 tunnel=/ vlan_cos=0/255
state=log may_dirty npu f00
statistic(bytes/packets/allow_err): org=18342/41/1 reply=402115/297/1 tuples=2
tx speed(Bps/kbps): 99/0 rx speed(Bps/kbps): 2185/17
orgin->sink: org pre->post, reply pre->post dev=9->4/4->9 gwy=198.51.100.1/10.1.50.21
hook=post dir=org act=snat 10.1.50.21:51544->192.0.2.80:443(198.51.100.2:51544)
hook=pre dir=reply act=dnat 192.0.2.80:443->198.51.100.2:51544(10.1.50.21:51544)
misc=0 policy_id=1 pol_uuid_idx=571 auth_info=0 chk_client_info=0 vd=0
serial=0004a1f3 tos=ff/ff app_list=0 app=0 url_cat=0
...
```

| Field | Meaning here |
|-------|--------------|
| `proto=6` | TCP (1 = ICMP, 17 = UDP) |
| `proto_state=11` | TCP state, one digit per direction (both established) |
| `duration=184` | Seconds since the session was created |
| `timeout=3600`, `expire=3415` | Idle timeout for this state, and the countdown since the last packet |
| `state=…` | Session flags (below) |
| `dev=9->4/4->9` | Ingress→egress interface index, original/reply. Map indexes with `diagnose netlink interface list` |
| `gwy=198.51.100.1/10.1.50.21` | Next hop in the original / reply direction. Here the original direction leaves through port2's ISP gateway |
| `act=snat … (198.51.100.2:51544)` | Source NAT to port2's address |
| `policy_id=1` | Firewall policy that accepted the session |

For SD-WAN troubleshooting, `dev=` and `gwy=` in the `orgin->sink` line tell you which member the session uses, and the `snat` address confirms it.

## Protocol states

FortiOS tracks protocol state so it can reject packets that don't fit the conversation.

**TCP (proto 6)**: `proto_state` is two digits because the FortiGate tracks both directions. Each digit uses this table:

| Value | State |
|-------|-------|
| 0 | NONE |
| 1 | ESTABLISHED |
| 2 | SYN_SENT |
| 3 | SYN & SYN/ACK |
| 4 | FIN_WAIT |
| 5 | TIME_WAIT |
| 6 | CLOSE |
| 7 | CLOSE_WAIT |
| 8 | LAST_ACK |
| 9 | LISTEN |

**UDP (proto 17)**: UDP has no handshake, but FortiOS still records whether a reply has been seen. 0 means the reply has not been seen and 1 means it has. A DNS query that was answered shows `proto_state=01`. One that went unanswered (for example because the member's upstream is broken) stays at `00`.

**ICMP (proto 1)**: no states. Always `proto_state=00`.

> **Exam tip:** A UDP session stuck at reply-not-seen on one member while the same flow works on another member points at the path, not at the FortiGate policy. The policy already accepted the session, otherwise there would be no entry.

The `timeout` depends on the state. Established TCP sessions use the TCP session TTL (3600 seconds by default), while half-open and closing states use much shorter timers. That is why a session list "cleans itself" quickly after connections close.

## Common session flags

The `state=` line lists flags. These are the ones you will meet most in SD-WAN work:

| Flag | Meaning |
|------|---------|
| `log` | Session is logged (traffic logging on the policy) |
| `log-start` | Also logged at session start (two logs per session) |
| `local` | Session is attached to the FortiGate's own IP stack (local-in or local-out traffic; proxy-inspected sessions show it too, next to `redir`) |
| `may_dirty` | Session details are allowed to change (it can be re-evaluated) |
| `dirty` | Session has been marked as changed and is re-evaluated on the next packet (requires `may_dirty`) |
| `npu` | Session is offloaded to an NP (hardware acceleration) |
| `npd` | Session is denied hardware acceleration |
| `redir` | Session is redirected to a FortiGate proxy (proxy-based inspection) |
| `os` / `rs` | Shaped in the origin / reply direction |
| `auth` / `authed` | Subject to / passed user authentication |
| `block` | Session was re-evaluated to block after a policy change |
| `complex` | Handled by a session helper |
| `app_valid` | Application control identified the application (`app=` is set) |
| `url_cat_valid` | Web filter identified the category (`url_cat=` is set) |
| `synced` / `syn_ses` | HA session-pickup: synced to peers / received from the primary |
| `f00` | Traffic logging enabled on the policy |

Other lines matter too. `npu_state` and `no_ofld_reason` explain offload decisions (for example `redir-to-av`). The `statistic` line counts bytes and packets each way. An original direction counting up while the reply stays at 0 is a broken return path.

> **Watch out:** The `npu` flag means the NP processor, not the CPU, forwards the session's packets. Fortinet's spillover (`usage-based`) example states that `auto-asic-offload` must be disabled on the firewall policy, so check offload when spillover thresholds seem to be ignored.

## A troubleshooting flow

1. Find the session: `diagnose sys session filter src <client>` + `dport`, then `diagnose sys session list`.
2. Check `dev=`/`gwy=`: which member is it on?
3. Compare with what the rule wants now: `diagnose sys sdwan service4 <id>`.
4. If they differ, the session was created before the rule's preference changed and hasn't been re-evaluated. That is the topic of the next lesson.

## Lab it yourself

1. Start a long-lived TCP session from the LAN client (`ssh` to a host on the far side of port2, or `curl --limit-rate 10k` on a big file). Find it with filters and identify `dev=`, `gwy=` and the SNAT address.
2. Run `dig @198.51.100.10 example.com` through a member whose upstream drops UDP/53 and look for `proto=17 proto_state=00`. Fix the upstream and compare with a new query (`proto_state=01`).
3. Enable traffic logging on the policy and confirm that `log` appears in `state=`.
4. Run `diagnose sys session clear` **with** a filter set, and confirm that only the filtered sessions disappear.

## Key takeaways

* SD-WAN decisions are stored per session. The session's `dev=` and `gwy=` show the member in use.
* Filter with `diagnose sys session filter …` (one key per line) before listing, and always before clearing.
* TCP `proto_state` has two digits (one per direction): 1 = ESTABLISHED, 2 = SYN_SENT, 5 = TIME_WAIT, and so on. UDP uses 0 (no reply seen) and 1 (reply seen). ICMP is always 00.
* Key flags: `may_dirty`/`dirty` (re-evaluation), `local`, `log`, `npu`/`npd`, `redir`, `block`, `app_valid`.
* `statistic` with reply bytes stuck at 0 points to a return-path problem on that member.
