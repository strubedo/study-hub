## Underlay and overlay links

| | Underlay | Overlay |
|---|----------|---------|
| What it is | The transport itself: fibre/cable/DSL internet, MPLS, LTE/5G, satellite | A tunnel built over one or more underlays, usually IPsec from branch to hub/DC (GRE and IPIP are also possible members) |
| Typical role | DIA (local internet breakout), carrying the overlays | Corporate traffic to the DC or other sites, RIA through the hub |
| Gateway | ISP next hop (static or learned via DHCP/PPPoE) | A point-to-point tunnel interface. The member normally needs no `gateway`, and the route points into the tunnel. |
| Health check target | A reliable public server (for internet traffic) | A server or dedicated loopback at the hub/DC, probed *through* the tunnel |
| Typical zone | `underlay` | `overlay` |

Fortinet's standard practice is to make **every** underlay and overlay interface an SD-WAN member. SD-WAN intelligence can then be applied to both DIA and site-to-site traffic.

## SD-WAN members

A member is a reference to an existing interface. Adding one doesn't change the interface itself. It lets SD-WAN health checks, rules and zone routes use the interface. Members can be physical ports, VLANs, aggregates (LAGs), IPsec tunnels, GRE and IPIP tunnels, and FortiExtender interfaces. The interface must not be referenced elsewhere (policies, static routes and so on) when you add it.

```text
FGT-Branch1 # show system sdwan
config system sdwan
    set status enable
    config zone
        edit "virtual-wan-link"
        next
        edit "underlay"
        next
        edit "overlay"
        next
    end
    config members
        edit 1
            set interface "port1"
            set zone "underlay"
            set gateway 203.0.113.1
        next
        edit 2
            set interface "port2"
            set zone "underlay"
            set gateway 198.51.100.1
            set cost 10
        next
        edit 3
            set interface "HUB1-VPN1"
            set zone "overlay"
            set source 10.255.1.1
        next
        edit 4
            set interface "HUB1-VPN2"
            set zone "overlay"
            set source 10.255.1.1
        next
    end
end
```

Member attributes (FortiOS 7.6 CLI Reference defaults):

| CLI | GUI | Purpose | Default |
|-----|-----|---------|---------|
| `interface` | Interface | The interface the member stands for | — |
| `zone` | SD-WAN Zone | The zone it belongs to (one zone per member) | `virtual-wan-link` |
| `gateway` / `gateway6` | Gateway | Next hop used by the zone static route and by SD-WAN rules. Learned automatically on DHCP/PPPoE interfaces. | 0.0.0.0 / :: |
| `cost` | Cost | Used **only** by Lowest Cost (SLA) rules. Lower is preferred (0–4294967295). | 0 |
| `priority` | Fallback priority | Priority of the member's static route, and used in SD-WAN rules including the implicit rule. Lower is preferred (1–65535). | 1 (`priority6` 1024) |
| `weight` | — | Share for the *Sessions* (`weight-based`) implicit mode (1–255) | 1 |
| `volume-ratio` | — | Share for the *Volume* (`measured-volume-based`) mode (1–255) | 1 |
| `spillover-threshold` / `ingress-spillover-threshold` | — | Egress / ingress kbit/s thresholds for *Spillover* (`usage-based`) mode | 0 |
| `source` / `source6` | — | Source IP of **health-check probes** sent on this member | 0.0.0.0 |
| `preferred-source` | — | Source IP for **local-out** traffic routed through this member | 0.0.0.0 |
| `status` | Status | Enable or disable the member | enable |

Sequence numbers (`edit 1`, `edit 2`, …) identify members everywhere else: in `set members 1 2` of a health check, in `priority-members` of a rule, and as `Seq(1 port1)` in diagnose output.

> **Watch out:** `cost` and `priority` are separate settings. `cost` matters only to Lowest Cost (SLA) rules and never changes the routing table. `priority` is written into the member's route. Two members with different priority values **do not** form ECMP, and the route with the higher value stays in the table as a standby.

## SD-WAN zones

A zone is a named group of members. FortiOS always has the default zone **`virtual-wan-link`**. You can add more, and the order you create zones and members in doesn't matter.

Where you can use them:

* **Firewall policies.** Zones are valid as source or destination interfaces. **Individual members are not.** A policy to a zone applies to every member in that zone.
* **Static routes.** `set sdwan-zone <zone> [<zone> ...]` creates one route with a next hop through each member of the zone(s).
* **SD-WAN rules.** `set priority-zone` (GUI *Zone preference*) as well as, or instead of, individual members.
* **Other policy types.** Local-in, DoS, multicast and TTL policies, and central SNAT maps.

So if one member needs a **policy of its own**, put it in a zone by itself. An example is MPLS that must skip the internet security profiles. Members can be moved between zones later.

```text
FGT-Branch1 # config router static
FGT-Branch1 (static) # edit 2
FGT-Branch1 (2) # set dst 10.100.0.0 255.255.0.0
FGT-Branch1 (2) # set sdwan-zone "overlay"
FGT-Branch1 (2) # next
FGT-Branch1 (static) # end

FGT-Branch1 # get router info routing-table static
Routing table for VRF=0
S*      0.0.0.0/0 [1/0] via 203.0.113.1, port1
                  [1/0] via 198.51.100.1, port2
S       10.100.0.0/16 [1/0] via HUB1-VPN1 tunnel 172.16.1.1 vrf 0
                      [1/0] via HUB1-VPN2 tunnel 172.16.2.1 vrf 0
```

Routes through IPsec members are printed as `via <tunnel> tunnel <peer address> vrf <n>`, because the next hop is the tunnel rather than a gateway on a subnet.

The default route goes to `underlay` only, and the DC prefix goes to `overlay` only. Each zone route defaults to **distance 1**, which you can change with `set distance`.

> **Exam tip:** "How can one firewall policy allow LAN traffic out of both ISPs?" Put both ISPs in one SD-WAN zone and use the zone as the outgoing interface. "Why can't I select port1 in the policy any more?" Because port1 is now an SD-WAN member, and only zones can be used.

Zones also have SD-WAN-specific settings, covered in Domain 2: `service-sla-tie-break` (`cfg-order` default, `fib-best-match`, `priority`, `input-device`) and `minimum-sla-meet-members` (default 1: the number of members that must meet the SLA when the SD-WAN **neighbor** feature prefers a BGP neighbor; not to be confused with the SD-WAN rule setting of the same name under `config service`, default 0), plus the ADVPN options (`advpn-select`, `advpn-health-check`).

## Traffic distribution across members

Before any SD-WAN rule exists, traffic to a zone route is spread by the **implicit rule**, which is ECMP across the member next hops. Its algorithm is the global `load-balance-mode`:

| GUI name | `set load-balance-mode` | Member setting it uses |
|----------|-------------------------|------------------------|
| Source IP (**default**) | `source-ip-based` | — (hash of source IP) |
| Sessions | `weight-based` | `weight` |
| Spillover | `usage-based` | `spillover-threshold`, `ingress-spillover-threshold` |
| Source-Destination IP | `source-dest-ip-based` | — (hash of source + destination IP) |
| Volume | `measured-volume-based` | `volume-ratio` |

Rules for the implicit rule (details in Domain 2):

* You **can't exclude** a member by setting weight or volume to 0. Both have a minimum of 1, and a 0 carried over from an older release is treated as 1.
* Only members that have a **route** to the destination take part. A member whose route has a higher priority value, or was withdrawn by a health check, isn't in the ECMP set.
* With dynamic routing, sessions are spread equally regardless of weight.

`diagnose sys sdwan member` adds mode-specific counters. In `weight-based` mode it shows session counts. This unit also has IPv6 gateways, which are listed after the IPv4 gateway, and `priority: 1 1024` is the IPv4 and IPv6 priority:

```text
FGT-Branch1 # diagnose sys sdwan member
Member(1): interface: port1, gateway: 203.0.113.1 2001:db8:a::1, priority: 1 1024, weight: 66
  Session count: 41
Member(2): interface: port2, gateway: 198.51.100.1 2001:db8:b::1, priority: 1 1024, weight: 33
  Session count: 20
```

In `measured-volume-based` mode it shows `Config volume ratio`, `last reading` and `volume room` (or `overload volume`). In `usage-based` mode it shows the egress and ingress spillover thresholds and `Egress-overbps` / `ingress-overbps` flags (1 = over the limit, so new sessions spill to the next member).

## Member health in this picture

A member's health comes from the performance SLAs (next lessons). Two facts link it to members and zones:

* A **dead** member is never chosen by any rule. With `update-static-route` enabled (the default), its routes are also withdrawn, so it drops out of the zone ECMP route and the implicit rule.
* An **alive but out-of-SLA** member keeps its routes. Only SLA-aware rules avoid it.

## Use cases

| Requirement | Member/zone design |
|-------------|--------------------|
| Two ISPs, both active, one internet policy | port1 + port2 in `underlay`, default route to `underlay`, one LAN → `underlay` policy |
| Use LTE only when both wired ISPs are gone | Put LTE in `underlay` with `priority 10` (wired members keep 1). Its route stays out of the ECMP set until the others are withdrawn. |
| MPLS needs different inspection from internet | MPLS in its own zone (`mpls`), with its own policy |
| Corporate traffic over tunnels, internet locally | Tunnels in `overlay`, DC prefixes routed to `overlay`. DIA policy to `underlay`, DC policy to `overlay`. |
| 70/30 split between a 700 Mbps and a 300 Mbps link | `load-balance-mode weight-based` (or `measured-volume-based`) with `weight` (or `volume-ratio`) 70 and 30 |

## Lab it yourself

1. Starting from the DIA lab, set `set load-balance-mode weight-based` and give port1 `weight 3` and port2 `weight 1`. Generate many sessions from the client (for example `for i in $(seq 1 40); do curl -s -o /dev/null http://198.51.100.10/; done`) and compare `Session count` in `diagnose sys sdwan member`. Fortinet notes that in weight-based mode, sessions with the same source and destination IP can stick to one path when the platform supports a route cache. If the split looks wrong, add a second destination (for example a secondary address on the upstream host).
2. Change port2 to `priority 10` and run `get router info routing-table all`. The default route still lists both next hops, but port2's line now ends with `, [10/0]` (`[priority/weight]`). New sessions use only port1, and port2 takes over if port1's route is withdrawn.
3. Try to select port1 as the outgoing interface of a new policy and confirm that only the zone is offered. The trial allows only three policies, so delete the test policy afterwards.

## Key takeaways

* Underlays are the transports. Overlays are tunnels over them. Make both SD-WAN members.
* Members reference existing, unreferenced interfaces. Defaults: zone `virtual-wan-link`, cost 0, priority 1, weight 1, volume-ratio 1, status enable.
* `cost` is used only by Lowest Cost (SLA) rules. `priority` goes into the member route, and a different priority value means no ECMP.
* Firewall policies use **zones, never members**. Put a member in its own zone when it needs its own policy.
* `set sdwan-zone` static routes create one next hop per member, at distance 1 by default.
* The implicit rule spreads traffic with `load-balance-mode`: source-ip-based (default), weight-based, usage-based, source-dest-ip-based or measured-volume-based. A member can't be excluded with weight 0.
* `source` sets the probe source address, and `preferred-source` sets the source for local-out traffic.
