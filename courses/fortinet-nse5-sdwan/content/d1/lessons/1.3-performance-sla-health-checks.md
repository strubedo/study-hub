## The three parts of a performance SLA

A performance SLA (CLI `config health-check`, GUI **Network > SD-WAN > Performance SLAs**) has three parts:

1. **Health check.** *What* is probed and *how*: probe mode, protocol, server(s) and participants.
2. **SLA targets.** The latency, jitter and packet-loss thresholds that rules can require.
3. **Link status.** The timers that decide when a member is declared dead or alive again.

```text
FGT-Branch1 # show system sdwan
config system sdwan
    ...
    config health-check
        edit "DC_HC"
            set server "10.100.0.10"
            set members 3 4
            config sla
                edit 1
                    set latency-threshold 150
                    set jitter-threshold 30
                    set packetloss-threshold 2
                next
                edit 2
                    set link-cost-factor latency
                    set latency-threshold 60
                next
            end
        next
    end
end
```

Unset values take their defaults: `detect-mode active`, `protocol ping`, `interval 500`, `failtime 5`, `recoverytime 5`, `update-static-route enable`.

## Health check: participants, protocol and servers

**Participants** (`set members`) must be SD-WAN members, but they don't have to be in the same zone. Include only the members you expect that service to use. `DC_HC` above probes the data centre through the two overlays (members 3 and 4), not through the raw ISP links.

**Protocols** (`set protocol`, default `ping`):

| Protocol | Notes |
|----------|-------|
| `ping` | ICMP echo, the default. Also the protocol that can carry embedded SLA information to a hub (next lesson). |
| `tcp-echo`, `udp-echo` | Echo service (port 7 by default) |
| `http`, `https` | HTTP(S) GET. `http-get`, `http-match` and `http-agent` refine it. |
| `dns` | Query for `dns-request-domain`. `dns-match-ip` sets the address the answer must contain. |
| `tcp-connect` | Full TCP connect. Latency is SYN to SYN-ACK (`half-open`, default) or FIN to FIN-ACK (`half-close`). |
| `twamp` | Two-Way Active Measurement Protocol (port 862) |
| `ftp` | FTP transfer in passive (default) or port mode |

The GUI offers only **Ping, HTTP and DNS**. The others are CLI-only.

**Servers:** an IP address or FQDN, **up to two** per health check. The FortiGate probes the first server and moves to the second only if the first stops answering. The health check fails only when **both** servers fail, which stops a single dead server from making a good link look dead. A given server can be used in **only one** performance SLA. If one server must be judged against different thresholds, define several SLA targets in the same health check.

**Predefined profiles:** new VDOMs and factory-reset units ship with five SLAs: **DNS, FortiGuard, Gmail, Google Search and Office 365** (FortiGuard, Google Search and Office 365 probe with HTTPS). You only add participants. With an *SD-WAN Underlay and Application Monitoring* licence, the GUI can also pick targets from the **FortiGuard SLA database** (`set fortiguard enable`, `set fortiguard-name <target>`).

## Active and passive monitoring

| `detect-mode` | How health is measured | Requirements and trade-offs |
|---------------|------------------------|-----------------------------|
| `active` (default) | The FortiGate sends probes of the chosen protocol to the server through each participant. | Needs a server. Adds probe traffic, but measures constantly, even on idle links, which also gives good history. |
| `passive` | Latency, jitter and loss are derived from real sessions in firewall policies with **`passive-wan-health-measurement enable`** | No server and no probe traffic. Measures real application paths. The policy's outgoing interface must be an SD-WAN zone, and enabling the option disables hardware offload (`auto-asic-offload`) for that policy. An idle link has no data. |
| `prefer-passive` | Passive while traffic flows. If a member sees **no traffic for three minutes**, active probes are sent to the configured server. | Needs a server (and protocol) for the fallback probes. |
| `remote` | Link health is learned from remote peers (the hub side of embedded SLA probes) | NSE 7 level. See next lesson. |
| `agent-based` | Health measured from fabric connectors | Out of scope for Core |

Passive measurements are visible with:

```text
FGT-Branch1 # diagnose sys link-monitor-passive admin list by-interface
Interface port2 (6):
  Default(0x00000000): latency=24.0    10:21:07, jitter=2.0    10:21:07, pktloss=0.0  % 10:20:58
Interface port1 (5):
  Default(0x00000000): latency=12.0    10:21:07, jitter=1.0    10:21:07, pktloss=0.0  % 10:20:58
```

Rules can also measure per application. With an SD-WAN rule that matches ISDB entries or applications, a passive or prefer-passive SLA and `set passive-measurement enable` in the rule, metrics are kept per internet service or application instead of per link.

## SLA targets

Each SLA target (`config sla`, `edit <id>` where the ID is 1–32) sets:

| Setting | Default | Window |
|---------|---------|--------|
| `latency-threshold` (ms) | 5 | Average over the last `probe-count` probes (default 30) |
| `jitter-threshold` (ms) | 5 | Last `probe-count` probes (default 30) |
| `packetloss-threshold` (%) | 0 | Always the last **100** probes |
| `link-cost-factor` | Latency, jitter and packet loss are all checked (the 7.6.4 CLI Reference also lists `custom-profile-1` in the default; custom profiles for health-check SLAs arrived in 7.6.4) | Choose which of `latency`, `jitter`, `packet-loss`, `mos`, `custom-profile-1` and `remote` count |

A member **meets** an SLA target only when every metric selected in `link-cost-factor` is within its threshold. In SLA target 2 above, only latency counts.

The GUI shows one SLA target per health check. Add a second in the CLI and the GUI then lets you manage several. Rules refer to a target as `<health-check>#<id>`, for example `DC_HC#1`.

**The SLA target map.** `diagnose sys sdwan health-check` prints `sla_map`, a bitmask of the targets the member currently meets. Bit 0 (value 0x1) is SLA ID 1, bit 1 (0x2) is ID 2, bit 2 (0x4) is ID 3, and so on.

```text
FGT-Branch1 # diagnose sys sdwan health-check DC_HC
Health Check(DC_HC):
Seq(3 HUB1-VPN1): state(alive), packet-loss(0.000%) latency(41.336), jitter(2.154) sla_map=0x3
Seq(4 HUB1-VPN2): state(alive), packet-loss(1.000%) latency(98.720), jitter(6.301) sla_map=0x1
```

HUB1-VPN1 meets both targets (0x3 = 0x1 + 0x2). HUB1-VPN2 meets target 1 (98.7 ms < 150, jitter 6.3 < 30, loss 1% < 2%) but not target 2 (98.7 ms > 60), so its map is 0x1. A dead member shows `state(dead), packet-loss(100.000%)` and `sla_map=0x0`.

> **Exam tip:** SLA targets are optional for link monitoring. A health check with no SLA target still detects dead members and withdraws routes. Targets are needed when a rule's strategy is Lowest Cost (SLA) or load balancing with SLA.

## Link status: alive, dead, in SLA, out of SLA

| Setting | Meaning | Default |
|---------|---------|---------|
| `interval` | Time between probes, ms (20–3 600 000). The 7.6 guide says HTTP/HTTPS checks are raised to 120 000 ms automatically. | 500 |
| `failtime` | Consecutive failed probes before the member is **dead** (GUI *Failures before inactive*) | 5 |
| `recoverytime` | Consecutive successful probes before it is **alive** again (GUI *Restore link after*) | 5 |
| `probe-timeout` | How long to wait before a probe counts as lost, ms | 500 |

So by default *alive → dead* takes about `failtime × interval` = 5 × 0.5 s = **2.5 s**, and *dead → alive* takes `recoverytime × interval` = 2.5 s. Raising `failtime`/`recoverytime` dampens flapping, at the cost of slower reactions.

A member therefore has **two independent states**:

| State | Decided by | Who reacts |
|-------|------------|------------|
| **Alive / dead** | Probe replies vs `failtime` / `recoverytime` | Every SD-WAN rule skips a dead member. The implicit rule and plain routing avoid it only because its routes are withdrawn, which needs `update-static-route` enabled (the default). |
| **In SLA / out of SLA** (per target) | Measured metrics vs thresholds | Only SLA-aware logic: Lowest Cost (SLA) rules and load balancing with SLA targets. Manual and Best Quality rules ignore SLA state. |

A member can be alive *and* out of SLA, for example 4% loss against a 2% target. That member stays in the routing table and still carries traffic for any rule that doesn't require that SLA.

> **Watch out:** *Alive again* is not the same as *in SLA again*. `recoverytime` only decides when a dead member is alive. Whether it meets an SLA target depends on its measured metrics, and packet loss is calculated over the last 100 probes, so a strict loss target can take longer to pass than the alive state takes to return.

## Member status and performance in the GUI and CLI

* **GUI:** the Performance SLAs tab lists each health check with its server, current packet loss, latency and jitter per member, and a green (up) or red (down) arrow. Select a health check for live charts. The arrow reports alive/dead, **not** whether the SLA is met.
* **`diagnose sys sdwan health-check [<name>]`:** current state, loss, latency, jitter and `sla_map` per member.
* **`diagnose sys sdwan sla-log <health-check> <seq>`:** the last 10 minutes of per-probe history for one member.

```text
FGT-Branch1 # diagnose sys sdwan sla-log DC_HC 4
Timestamp: Tue Oct 27 10:31:02 2026, vdom root, health-check DC_HC, interface: HUB1-VPN2, status: up, latency: 97.884, jitter: 6.118, packet loss: 1.000%.
Timestamp: Tue Oct 27 10:31:03 2026, vdom root, health-check DC_HC, interface: HUB1-VPN2, status: up, latency: 98.720, jitter: 6.301, packet loss: 1.000%.
```

* **`diagnose sys sdwan intf-sla-log <interface>`:** 15 minutes of per-interface bandwidth history (used in/out/bi bandwidth, tx/rx bytes).

## Member state change actions

What happens when a member changes state is controlled by the health check:

**Update static route** (`set update-static-route enable`, the default, GUI *Actions when Inactive > Update static route*). When a participant becomes **dead**, the FortiGate withdraws **all static routes on that interface**, including its next hop in the zone route, and restores them on recovery. The routing change affects every flow, not just SD-WAN-steered traffic, and it logs `0100022921 Routing information changed`. Note the following:

* If a member is in **several health checks**, its routes are withdrawn only when **all** of them fail.
* With `update-static-route disable`, a dead member is still skipped by SD-WAN rules, but its routes stay. Traffic handled by the **implicit rule** (ECMP) or by plain routing can still be hashed to the dead link.
* Out-of-SLA never withdraws routes. It only changes the decisions of SLA-aware rules.
* Fortinet's guide says to think carefully about the consequences for **overlay tunnels**. Withdrawing a tunnel's static routes affects every flow that relies on them, not just SD-WAN traffic.

**Update cascade interface** (`set update-cascade-interface`, default enable) works with the SD-WAN-level `set fail-detect enable` and `set fail-alert-interfaces <port>`. When the health check finds all its members dead, the alert interfaces (for example the LAN port) are brought down, and they come back up when a member recovers. Use this when a downstream device must notice that the WAN is gone, for example to fail over to another gateway.

**Events.** Every SLA change is logged as `0113022923` (`Member status changed. Member out-of-sla.` / `in sla.`, `Number of pass member changed.`). A member that stops being used in a rule because it is dead logs `Member link is unreachable or miss threshold. Stop forwarding traffic.`

## Lab it yourself

1. Add `Internet_HC` (server 198.51.100.10, members 1 2) with SLA target 1: `latency-threshold 100`, `packetloss-threshold 2`.
2. On the ISP-B Linux router run `tc qdisc add dev eth0 root netem delay 150ms`. Latency is averaged over the last 30 probes (15 s at the default 500 ms interval), so within roughly 10–15 s port2 shows `sla_map=0x0` but stays `state(alive)`, its route stays, and a `Member out-of-sla` event appears.
3. Replace it with `netem loss 100%`. Now port2 goes `state(dead)`, a `0100022921` event appears and the default route loses port2.
4. Set `update-static-route disable`, repeat step 3 and confirm that port2 stays in the routing table.

## Key takeaways

* A performance SLA has a health check (mode, protocol, servers, participants), SLA targets and link-status timers.
* Up to two servers per health check: the first is used, both must fail, and a server can be in only one SLA. The GUI offers only Ping, HTTP and DNS.
* Active (default) sends probes. Passive uses real traffic from policies with `passive-wan-health-measurement` (zone as egress, no hardware offload). Prefer-passive probes after 3 minutes without traffic.
* Defaults: interval 500 ms, failtime 5, recoverytime 5, latency 5 ms, jitter 5 ms, loss 0%. Latency/jitter use the last 30 probes, and loss the last 100.
* `sla_map` is a bitmask, with bit 0 = SLA ID 1. Alive/dead and in/out of SLA are separate states.
* `update-static-route` (default enable) withdraws a dead member's static routes. All health checks on that member must fail, and out-of-SLA never withdraws routes.
* Cascade interfaces (`fail-detect`, `fail-alert-interfaces`, `update-cascade-interface`) bring down chosen interfaces when every member of a health check is dead.
