## SD-WAN on a FortiGate in one paragraph

A traditional WAN edge chooses paths with the routing table: one best route per prefix, maybe a floating backup, and a dead-gateway detector. SD-WAN keeps the routing table for **reachability** but moves the **path choice** to a separate layer that knows how each link is performing. Each link stays up and in use. The FortiGate measures latency, jitter and packet loss on every link and then picks a link for each type of traffic from that data and from business rules.

On FortiOS the whole feature is built into the firewall. There is no separate SD-WAN appliance or controller, and the configuration lives under one CLI tree, `config system sdwan`, or in the GUI under **Network > SD-WAN**. The same FortiGate that steers the traffic also runs NGFW inspection on it. Fortinet calls this "Secure SD-WAN".

Two terms appear in every exam question:

* **Underlay**: the physical or provider transports, such as broadband, fibre DIA, MPLS, LTE/5G or satellite.
* **Overlay**: a virtual network built *on top of* the underlays, usually IPsec tunnels from branches to a hub or data centre. Overlays exist only when traffic has to reach another site.

## Architecture components

Fortinet's design material splits an SD-WAN solution into three layers:

| Layer | What it does | Fortinet products |
|-------|--------------|-------------------|
| Management and orchestration | Central management, templates, zero-touch provisioning, logging and reporting, REST API automation | FortiManager, FortiAnalyzer |
| Control, data plane and security | Groups underlays and overlays into zones, routing, health checks, application-aware steering, NGFW policy | **FortiGate** (this layer can only run on a FortiGate) |
| Network access | Wired and wireless access, segmentation, NAC at the branch (SD-Branch) | FortiSwitch, FortiAP |

You can build SD-WAN with only the middle layer, using one FortiGate managed on its own. The other two layers help you scale. FortiManager pushes the same SD-WAN template to hundreds of branches (Domain 3), and FortiAnalyzer keeps the SLA and traffic logs for long-term reporting.

Inside the FortiGate, SD-WAN has four configuration objects plus one built-in rule:

| Object | CLI | Role |
|--------|-----|------|
| **Members** | `config members` | Interfaces that SD-WAN may use (physical, VLAN, LAG, IPsec, GRE, IPIP, FortiExtender). At least one is required. |
| **Zones** | `config zone` | Groups of members. Firewall policies and static routes refer to zones. |
| **Performance SLAs** | `config health-check` | Measure each member's quality, detect dead links and define the SLA targets. |
| **SD-WAN rules** | `config service` | Policy routes that choose a member for matching traffic using a strategy. |
| **Implicit rule** | `set load-balance-mode` | Applies when no rule matches: ECMP across the routes (Domain 2). |

Two ordinary FortiOS objects complete the picture. A **static route** to the zone gives every member a route, and a **firewall policy** to the zone allows the traffic. If either is missing, nothing flows, however good the SD-WAN rules are.

## Use cases

| Use case | What SD-WAN contributes |
|----------|-------------------------|
| Direct internet access (DIA) | Local breakout for SaaS and web traffic over two or more ISPs. Both links are active, and a link that fails or degrades stops being used. |
| Redundant branch connectivity | A mix of broadband, MPLS, LTE/5G or satellite. The secondary link is used rather than sitting idle. |
| Dynamic application steering | Voice to the lowest-latency link, bulk traffic to the cheapest link, a SaaS application to whichever link meets its SLA. |
| Reduce WAN OPEX | Replace or shrink MPLS by running IPsec overlays over cheaper broadband. |
| Secure site-to-site connectivity | Overlays from branches to hubs and data centres, with SD-WAN choosing the best tunnel. |
| Multi-cloud and cloud on-ramp | Steering to IaaS/SaaS locations. |
| Application performance improvement | Best-link steering, QoS and WAN remediation. Packet duplication and FEC are covered at the NSE 7 level. |

## DIA topologies

DIA means the branch reaches the internet **through its own WAN links** rather than backhauling to a hub. Overlays are usually irrelevant to a pure DIA design. The common shapes are:

```text
1) Single FortiGate, dual ISP (the classic DIA design)

   LAN 10.1.1.0/24 --- port3 [FGT-Branch1] port1 --- ISP-A (gw 203.0.113.1)
                                           port2 --- ISP-B (gw 198.51.100.1)
   port1 + port2 = members of zone "underlay"; one default route to the zone

2) Broadband plus LTE/5G backup

   port1 = fibre (priority 1), lte1/port2 = cellular (higher priority value or
   higher cost) so the cellular link carries traffic only when it is needed

3) FGCP HA pair at the branch

   Two FortiGates acting as one SD-WAN device; each ISP reaches both units
   through a switch (or the units' built-in virtual switch features); the
   SD-WAN configuration is synchronised like any other config

4) DIA with remote internet access (RIA) as backup

   SaaS/web leaves locally on the underlay zone (DIA). If the local ISPs
   fail, internet traffic follows the overlay zone to FGT-HQ and breaks out
   there (RIA). Each path needs its own firewall policy
```

**RIA** (remote internet access) is the opposite of DIA: the branch sends internet traffic across the overlay and the hub or data centre breaks it out. It is used when a site has only private links (for example MPLS), when central inspection is mandated, or as a fallback for DIA.

> **Exam tip:** A question that describes "local breakout" or "SaaS directly from the branch" is DIA. If the internet traffic crosses an IPsec tunnel to the hub first, the design is RIA. The difference shows up in the firewall policy: DIA uses the **underlay** zone as the outgoing interface, and RIA uses the **overlay** zone.

## Design recommendations: the five pillars

Fortinet recommends a five-pillar approach for designing a secure SD-WAN solution:

| Pillar | Questions to answer |
|--------|---------------------|
| **Underlay** | Which WAN links? Bandwidth, cost, typical latency/jitter/loss of each? Static or DHCP addressing, VLAN tags, LAGs? These baselines drive SLA targets later. |
| **Overlay** | Is site-to-site traffic needed? How many tunnels per site, and how will they scale (manual tunnels are fine for a few sites; ADVPN at scale)? |
| **Routing** | How does each site learn all possible paths? Static routes to zones are enough for DIA. Dynamic routing (usually BGP) is used across overlays when there are many sites. |
| **Security** | Which zones and policies? Which inspection does each path need? Underlays often provide DIA, and overlays provide corporate access or RIA. |
| **SD-WAN** | Which SLAs and rules express the business intent: which traffic, which links, which thresholds? |

The routing pillar has a principle that the exam likes. For DIA, each member's default route must have the **same distance and priority** so that all of them are installed as ECMP routes. The routing table must not make the decision, because the SD-WAN rules do.

## Best practices

* **Group members by purpose.** Put the internet underlays in one zone (for example `underlay`) and the tunnels in another (`overlay`). One policy per zone then covers every member. If a link needs different inspection, such as MPLS that should not get the same profile as the internet, give it its **own zone**, because policies can't reference members.
* **Probe the resource, not just the link.** A health check measures the *path to a server*. For corporate apps, probe a server or loopback at the DC through the overlays. For internet traffic, probe a reliable public target through the underlays only.
* **Only add participants that will carry that traffic.** A DC health check normally includes only the overlay members.
* **Tune SLA targets just below what the application tolerates.** If the app breaks at 100 ms, set about 90 ms. Targets that are too strict cause needless flapping between links. Targets that are too loose mean SD-WAN never reacts. The defaults (5 ms latency, 5 ms jitter, 0% loss) are placeholders, not recommendations.
* **Put specific rules above generic ones.** An application- or ISDB-based rule must sit above a rule for `all` destinations, because rules are evaluated top-down (Domain 2).
* **Standardise.** Define a few site profiles, such as dual-broadband or broadband-plus-LTE, and configure every site in a profile the same way. Manage them with FortiManager templates once there are more than a handful of sites.
* **Secure every path.** Any member a rule might choose must be covered by a policy with the right security profiles. Otherwise a failover changes the traffic's security posture.

> **Real world:** The most common reason for "SD-WAN failover didn't work" is not SD-WAN at all. Usually the backup member has no policy, or the zone route is missing, or the health check server is reachable from only one ISP. Check routes and policies before you change rules.

## Lab it yourself

Plan the lab now, and the later lessons build on it. On the FortiGate-VM permanent trial (FortiOS 7.6, three interfaces, three policies, three routes) use:

```text
port3  LAN 10.1.1.1/24          <-- Linux client 10.1.1.10
port1  "ISP-A" 203.0.113.2/29   <-- Linux/Cisco router 203.0.113.1
port2  "ISP-B" 198.51.100.2/29  <-- Linux/Cisco router 198.51.100.1
```

Both "ISP" routers forward to a shared upstream host that plays the probe server (198.51.100.10 in this course's examples). Keep the ISP links as small subnets (/29 here) so that the probe server isn't on a subnet that's directly connected to the FortiGate. With port2 at 198.51.100.2/24, the server would be on port2's own segment and the lab wouldn't test a routed path. On the Linux routers, `tc qdisc ... netem delay 120ms loss 5%` lets you degrade one ISP on demand. This uses all three interfaces, one route (the zone default route) and one policy. That leaves two policies and two routes for the later labs. The trial has no FortiGuard, so the SD-WAN Setup wizard and the FortiGuard SLA database aren't available. Build everything by hand.

## Key takeaways

* FortiOS SD-WAN is built into the FortiGate (`config system sdwan`). The routing table provides reachability, and SD-WAN rules choose the path.
* Underlays are the transports. Overlays are tunnels built on them for site-to-site traffic.
* The three layers are management/orchestration (FortiManager, FortiAnalyzer), control/data/security (FortiGate only) and network access (FortiSwitch, FortiAP).
* The building blocks are members, zones, performance SLAs, rules and the implicit rule, plus a static route and a firewall policy to the zone.
* DIA is local breakout through the branch's underlays. RIA backhauls internet traffic over the overlay to the hub.
* Design in five pillars: underlay, overlay, routing, security, SD-WAN. For DIA, give member default routes equal distance and priority (ECMP).
* Best practices: zones by purpose (single-member zone for special treatment), probe the real resource, tune SLA targets just under application limits, specific rules first, standardise sites.
