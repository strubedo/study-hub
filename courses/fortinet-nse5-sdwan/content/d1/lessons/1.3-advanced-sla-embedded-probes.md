## Advanced performance SLA settings

The basic health check covers most needs. The CLI (`config system sdwan` > `config health-check` > `edit <name>`) has more options. These are the ones to know, with FortiOS 7.6 defaults:

| Setting | What it does | Default |
|---------|--------------|---------|
| `probe-count` | Number of most recent probes used to calculate latency and jitter (5–30) | 30 |
| `probe-timeout` | Time before an unanswered probe counts as lost (ms) | 500 |
| `probe-packets` | Turns sending of probes on or off (for example to pause active probes) | enable |
| `sla-fail-log-period` / `sla-pass-log-period` | Seconds between periodic `0113022925` SLA logs while a member fails / passes the SLA (0–3600, 0 = no periodic logs) | 0 / 0 |
| `diffservcode` | DSCP value on probe packets, so probes get the same upstream QoS as the traffic they represent | not set |
| `class-id` | Traffic-shaping class for probes, so probes keep guaranteed bandwidth during congestion and links don't flap | 0 |
| `source` / `source6` | Probe source address set on the health check. Members also have their own `source`, which is the usual place to set it per overlay | 0.0.0.0 / :: |
| `vrf` | VRF used for the probes | 0 |
| `system-dns` | For `dns` probes, use the system DNS servers as the probe targets | disable |
| `dns-request-domain` / `dns-match-ip` | Name to resolve and the address the answer must contain | `www.example.com` / 0.0.0.0 |
| `http-get` / `http-match` / `http-agent` | URL, expected response string and User-Agent for HTTP probes | `/` / — / browser string |
| `quality-measured-method` | `tcp-connect`: measure SYN→SYN-ACK (`half-open`) or FIN→FIN-ACK (`half-close`) | half-open |
| `mos-codec` + SLA `mos-threshold` | Calculate a **Mean Opinion Score** (1–5) for the codec `g711`, `g722` or `g729`, and require a minimum MOS in the SLA target (`link-cost-factor mos`) | g711 / 3.6 |
| `threshold-warning-*` / `threshold-alert-*` | Warning and alert levels for latency, jitter and packet loss (separate from SLA targets) | 0 |
| `update-static-route` / `update-cascade-interface` | Member state change actions (previous lesson) | enable / enable |
| `embed-measured-health` | Embed SLA information in ICMP probes (this lesson) | disable |
| `fortiguard` / `fortiguard-name` | Use a target from the FortiGuard SLA database (licensed) | disable |

A DSCP-marked voice health check that also produces periodic SLA logs:

```text
FGT-Branch1 # config system sdwan
FGT-Branch1 (sdwan) # config health-check
FGT-Branch1 (health-check) # edit "Voice_HC"
FGT-Branch1 (Voice_HC) # set server "10.100.0.20"
FGT-Branch1 (Voice_HC) # set members 3 4
FGT-Branch1 (Voice_HC) # set diffservcode 101110
FGT-Branch1 (Voice_HC) # set mos-codec g729
FGT-Branch1 (Voice_HC) # set sla-fail-log-period 30
FGT-Branch1 (Voice_HC) # set sla-pass-log-period 300
FGT-Branch1 (Voice_HC) # config sla
FGT-Branch1 (sla) # edit 1
FGT-Branch1 (1) # set link-cost-factor mos
FGT-Branch1 (1) # set mos-threshold "4.0"
FGT-Branch1 (1) # next
FGT-Branch1 (sla) # end
FGT-Branch1 (Voice_HC) # next
FGT-Branch1 (health-check) # end
FGT-Branch1 (sdwan) # end
```

`101110` is DSCP 46 (EF). The periodic `0113022925` logs appear every 30 s while a member fails the SLA and every 300 s while it passes. Fortinet positions these logs for long-term monitoring of remote sites and for FortiAnalyzer reports and views. In 7.6, `diagnose sys sdwan health-check` shows a `mos(...)` value on each member line (calculated with the configured `mos-codec`), and `sla-log` adds `mos:` to each entry. Fortinet notes that MOS can be used in Lowest Cost (SLA) rules but **not** in Best Quality (`priority`) rules. The highest MOS a link can reach depends on the codec.

> **Exam tip:** "The SD-WAN SLA report in FortiAnalyzer is empty, although members fail their SLA." Check `sla-fail-log-period` and `sla-pass-log-period`. At their default of 0, no periodic SLA information logs are generated.

## How probes leave the FortiGate

A health check sends each probe **out of the member it is testing**, whatever the main routing table says. SD-WAN installs dedicated kernel routes for the probes, so `HUB1-VPN2` is probed through `HUB1-VPN2` even if the best route to the server is through `HUB1-VPN1`. What can break is the **return path**:

* On the internet, the reply comes back to the member's public (NAT) address, so it returns naturally.
* On overlays, the server (usually a dedicated **loopback on the hub**) must route the reply back into the same tunnel. Set the member `source` to an address that the hub routes back through that tunnel, such as the branch loopback or tunnel IP. Otherwise the member looks dead even though the tunnel is up.
* A probe server that's reachable only through one zone must not be used for members of another zone. A DC server probed through a raw ISP link with no route back will fail.

## ICMP probes with embedded SLA information

**The problem.** In hub-and-spoke SD-WAN the *spoke* knows which of its overlays is in SLA. The *hub* sends return traffic to the spoke and doesn't know. If the spoke steers voice to HUB1-VPN2 because HUB1-VPN1 is out of SLA, but the hub keeps sending the replies down HUB1-VPN1, the flow is asymmetric and still crosses the bad path in one direction. The older fix was to run BGP per overlay and signal health with the SD-WAN *neighbor* feature and `route-map-out-preferable`. That means more BGP sessions and community-based route maps.

**The FortiOS solution.** The spoke puts its SLA measurements **into the ICMP health-check probes** it already sends to the hub. The hub reads them per spoke and per overlay, and sets the **priority of the IKE routes** (the routes to the spoke's addresses created by the tunnels): a low priority value for overlays that are in SLA and a higher value for overlays that are out of SLA. If BGP is used (for example BGP on loopback), the BGP routes resolve through those IKE routes and can inherit their priority. Hub-to-spoke traffic then follows the healthy overlay, with no per-overlay BGP needed.

Spoke side:

```text
FGT-Branch1 # show system sdwan
config system sdwan
    ...
    config health-check
        edit "DC_HC"
            set server "10.255.0.1"
            set embed-measured-health enable
            set members 3 4
            config sla
                edit 1
                    set link-cost-factor latency
                    set latency-threshold 100
                next
            end
        next
    end
end
```

Hub side (`FGT-HQ`), one health check per overlay member:

```text
FGT-HQ # show system sdwan
config system sdwan
    ...
    config health-check
        edit "SPOKES_VPN1"
            set detect-mode remote
            set sla-id-redistribute 1
            set members 1
            config sla
                edit 1
                    set link-cost-factor latency
                    set latency-threshold 100
                    set priority-in-sla 10
                    set priority-out-sla 20
                next
            end
        next
    end
end

FGT-HQ # config router bgp
FGT-HQ (bgp) # set recursive-inherit-priority enable
FGT-HQ (bgp) # end
```

| Setting | Where | Purpose |
|---------|-------|---------|
| `embed-measured-health enable` | Spoke health check | Embed SLA information in the ICMP probes (default disable) |
| `detect-mode remote` | Hub health check | Take link health from the remote peers' embedded information instead of probing |
| `priority-in-sla` / `priority-out-sla` | Hub SLA target | Route priority applied to the IKE routes of an overlay that is in / out of SLA (0–65535) |
| `sla-id-redistribute <id>` | Hub health check | Which SLA entry's priorities are pushed into the routing table (0–32, default 0) |
| `recursive-inherit-priority enable` | Hub `config router bgp` | Recursively resolved BGP routes inherit the priority of the IKE route they resolve through (default disable) |

Variants in FortiOS 7.6:

* **Embedded SLA status.** The spoke sends its own *in SLA / out of SLA* verdict. On the hub, `set link-cost-factor remote` in the SLA target uses that verdict directly instead of re-judging the metrics.
* **Embedded SLA priorities.** The spoke sets `priority-in-sla` / `priority-out-sla` on its **members**, and the hub applies the priorities the spoke sends.

On the hub, `diagnose sys sdwan health-check remote [<name> [<seq>]]` replaces the normal command when `detect-mode remote` is used:

```text
FGT-HQ # diagnose sys sdwan health-check remote
Remote Health Check: SPOKES_VPN1(1)
Passive remote statistics of EDGE_VPN1(21):
EDGE_VPN1_0(172.16.1.2): timestamp=10-27 11:02:40, latency=38.104, jitter=1.221, pktloss=0.000%
```

> **Watch out:** This feature is a Core-exam topic only at the concept level: *spokes embed their SLA in ICMP probes, and the hub uses it to set route priorities for return traffic*. ADVPN, BGP on loopback and multi-hub designs are NSE 7 material.

## Use cases

| Need | Advanced setting |
|------|------------------|
| Voice must move when call quality drops | SLA target with `link-cost-factor mos`, suitable `mos-codec` and `mos-threshold` |
| Probes are dropped during congestion, so links flap | `class-id` with a high-priority, guaranteed shaping class, and/or `diffservcode` |
| A SaaS check must test the real service, not just reachability | `protocol https` with `http-get`/`http-match`, or `protocol dns` with `dns-match-ip` |
| Long-term SLA reporting in FortiAnalyzer | `sla-fail-log-period` / `sla-pass-log-period` above 0 |
| Symmetric hub-to-spoke routing without BGP per overlay | `embed-measured-health` on spokes, `detect-mode remote` + `priority-in-sla`/`priority-out-sla` on the hub |
| Overlay members appear dead although the tunnel is up | Correct member `source` so replies return through the same tunnel |

## Lab it yourself

The trial VM can't host a full hub-and-spoke lab within three interfaces, so practise the single-box items:

1. Add `set sla-fail-log-period 10` and `set sla-pass-log-period 60` to `Internet_HC`, then degrade ISP-B with netem. Under Log & Report > System Events > SD-WAN Events, check that the `0113022925` *SDWAN SLA information* entries arrive every 10 s with `status`, `latency`, `packetloss`, `slamap` and `metric`.
2. Set `link-cost-factor mos` on a second SLA target and compare `mos(...)` in `diagnose sys sdwan health-check` before and after adding 80 ms of jitter.
3. Change the protocol to `dns` with `dns-request-domain` pointing at a name the probe server resolves, then set a wrong `dns-match-ip` and watch the member go dead even though ping still works.

## Key takeaways

* Advanced settings: `probe-count` (latency/jitter window, default 30), `probe-timeout` (500 ms), `diffservcode`, `class-id`, `source`, `vrf`, protocol-specific match options, MOS (`mos-codec` g711 default, `mos-threshold` 3.6 default).
* `sla-fail-log-period` and `sla-pass-log-period` default to 0, which means no periodic `0113022925` SLA logs.
* Probes always leave through the member being tested. On overlays, set `source` so replies return through the same tunnel.
* Embedded SLA in ICMP probes: spokes `embed-measured-health enable`, and the hub uses `detect-mode remote` to set IKE route priorities (`priority-in-sla` / `priority-out-sla`, `sla-id-redistribute`) for symmetric return traffic.
* BGP routes can inherit those priorities with `recursive-inherit-priority enable`.
* The hub's verification command is `diagnose sys sdwan health-check remote`.
