## The automation chain

Once security events arrive (previous lesson), four objects under **Logs > Security Incidents** decide what happens:

| Object | Question it answers |
|---|---|
| **Trigger** | Do the incoming events look like *this* pattern, within *this* time? |
| **Security rule** | If the trigger is satisfied, does the host match (or not match) a user/host profile? Then create an alarm and associate an action |
| **Action** | What to do, as an ordered list of activities, run automatically or by an administrator |
| **Security alarm** | The record that a rule matched, with its action state; actions can be undone from here |

The flow, in the documentation's terms: when an event satisfies a trigger, every security rule that uses that trigger is evaluated **in rank order**. The **first** rule that also matches its optional user/host profile creates the security alarm. If no rule matches, **no alarm is created**. The alarm carries the rule's action, which runs automatically if the rule says so.

## Triggers

A trigger is a named set of **security filters** plus two controls.

| Setting | Meaning |
|---|---|
| Time Limit | The window in which the incoming events must satisfy the filters |
| Filter Match | **All**: every filter must be matched. **Any**: you set the *minimum number* of filters that must match |
| Security filters | Each filter can test Vendor, Type, Sub Type, Threat ID, Description, Severity (a range) and custom fields, and has a **Frequency**: how many times the event must occur |

Examples:

- *One AV detection from FortiGate is enough*: one filter (Vendor = Fortinet, Type = utm, Sub Type = virus), Frequency 1.
- *Three IPS events of high severity within 10 minutes*: one filter with Severity range high, Frequency 3, Time Limit 10 minutes.
- *Any two of four indicators within an hour*: four filters, Filter Match = Any with a minimum of 2, Time Limit 1 hour.

A trigger is shared. If you edit it from inside a rule, the change applies to **every rule** that uses it. The trigger list shows whether it is in use and by how many rules.

> **Watch out:** "Filter Match: Any" is not "at least one" by default. Any means *a minimum number* that you set. "All" means every filter must be satisfied inside the time limit.

## Security rules

| Field | Meaning |
|---|---|
| Rule Enabled | Only enabled rules are evaluated |
| Rank | Order of evaluation; lower rank number is checked first. **Set Rank** jumps a rule to a position |
| Trigger | The trigger that activates the rule |
| User/Host Profile | **=** the host must match the profile; **≠** the host must *not* match it; **None** = no profile test |
| Action | The action to associate, set to run **automatically** or **manually**; None = alarm only |
| Send Email when Rule is Matched | Email an administrator group when the rule creates an alarm (**Rule Match Email Group**) |
| Send Email when Action is Taken | Email an administrator group when the action runs (**Action Taken Email Group**) |

Because the first matching rule wins, put the narrow rules first:

| Rank | Rule | Trigger | User/Host Profile | Action |
|---|---|---|---|---|
| 1 | Servers-AV-Notify | FGT-AV-Detect | = Data Center Servers | Email security team (manual) |
| 2 | Contractor-AV-Disable | FGT-AV-Detect | = Contractors | Disable host, re-enable after 60 min (automatic) |
| 3 | Any-AV-Remediate | FGT-AV-Detect | None | Mark host at risk (automatic) |

A server that raises an AV event matches rank 1 and is only reported; the contractor laptop matches rank 2 and is disabled; everything else is marked at risk by rank 3. If rank 3 were moved to the top, it would catch every host first and ranks 1 and 2 would never create alarms for this trigger.

Using **≠** is handy for exclusions: "disable any host that triggers this, **≠** Medical Devices" keeps a clinical device from being cut off automatically.

> **Exam tip:** The user/host profile in a security rule is the same object used by network access, endpoint compliance, authentication, Supplicant EasyConnect and portal policies. Security rules are one of the places it can be used, but only when Security Incidents is enabled.

## Actions and activities

An action is a named, ranked list of **activities**. Activity choices in the 7.6 guide:

| Activity | Effect |
|---|---|
| Disable Host | Disconnects the host from the network (secondary task: re-enable it later) |
| Disable Port | Disables the switch port (secondary task: re-enable it) |
| Mark Host At Risk | Fails a selected scan so the host goes to remediation the next time it connects (secondary task: mark safe) |
| Mark Host Safe | Passes a selected scan (secondary task: mark at risk) |
| Host Role Action | Changes the host's role (secondary task: change it back) |
| Run Endpoint Compliance Configuration | Runs another endpoint compliance configuration (chained scans) |
| Email User Action / Email Group Action / SMS User Action | Notify the user/owner or an administrator group |
| Send Message to Desktop | Pop-up on a host running the Persistent Agent |
| Send Alarm to External Log Hosts | Forward the alarm to configured log receivers |
| Send Alarm to Custom Script / Command Line Script Action | Run a script (custom scripts live in `/home/cm/scripts`) |

Action-level settings:

- **On Activity Failure**: **Continue Running Activities** runs the next activity even if a higher-ranked one fails; **Stop Running Activities** stops the rest.
- **Perform Secondary Tasks After** (the *Secondary Task Delay*): when enabled, activities whose Secondary Task box is checked are automatically undone after the delay, for example *re-enable the host 15 minutes after it was disabled*. If it is not enabled, an administrator undoes the action manually from the Security Alarms view.

When an administrator re-enables a host that a security alarm disabled (Users & Hosts > Hosts > Enable), FortiNAC-F asks whether to **undo the security alarm** (undoing its actions and running enabled secondary tasks) or just enable the host and leave the alarm and its actions in place.

## Manual versus automatic

| Rule action mode | What happens when the rule matches |
|---|---|
| Automatic | The alarm is created and the action runs immediately |
| Manual | The alarm is created with the action associated; an administrator runs it from the alarm |
| None | Alarm only (plus any emails). Good for tuning a new rule |

## Validating a new rule (the "security rule validation" use case)

Fortinet's own procedure is cautious, and the exam likes it:

1. Confirm events arrive (**Logs > Security Incidents > Events**). The guide even suggests a catch-all trigger and rule just to log what is being received.
2. Create the trigger from fields seen in a real event (vendor, type, subtype, threat ID).
3. Create the rule with **User/Host Profile = None**, **Action = None**, and **Send Email when Rule is Matched** to an admin group. The administrator must have an email address set (Users & Hosts > Administrators).
4. Generate the event (EICAR through the FortiGate) and confirm an **alarm** appears under Logs > Security Incidents and the email arrives.
5. Only then add a profile and an automatic action, and test again on a lab host.

| Observation | Meaning |
|---|---|
| Event listed, no alarm | No enabled rule's trigger was satisfied, or the matching rule's profile test failed (= profile not matched, or ≠ profile matched) |
| Alarm, no email | Admin group has no email address, or email settings are missing |
| Alarm, action not executed | Action set to manual, or an activity failed and Activity Failure = Stop |

## Related: quarantine from the FortiGate side

The Security Fabric gives a second path into the same result. On FortiGate, an automation stitch with the **Quarantine via FortiNAC** action (trigger: Compromised Host or Incoming Webhook) tells FortiNAC-F to quarantine the client: its MAC address is **disabled** in FortiNAC-F. That requires FortiNAC-F to be connected to the Fabric (lesson 2.4). Security rules are FortiNAC-F's own engine; the stitch is FortiGate's.

## Key takeaways

- Event → **trigger** (filters, Time Limit, Filter Match Any minimum or All) → **rules by rank** → first match creates the **alarm** → **action**.
- No matching rule means no alarm.
- Rules can require the host to match (**=**) or not match (**≠**) a user/host profile.
- Actions are ranked activities; Activity Failure decides continue or stop; secondary tasks undo an activity after the Secondary Task Delay.
- Notifications: Rule Match Email Group (alarm created) and Action Taken Email Group (action ran).
- Validate with Action = None and an email first, then automate.
- Re-enabling a host disabled by a security alarm offers to undo the alarm and its actions.
