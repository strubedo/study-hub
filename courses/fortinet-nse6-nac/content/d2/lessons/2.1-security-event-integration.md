## What security automation means in FortiNAC-F

FortiNAC-F knows *who* and *what* is on the network and *where* each endpoint connects. Security devices such as FortiGate, FortiAnalyzer, FortiSIEM, FireEye or Palo Alto Networks know when something on the network *behaves badly*. The **Security Incidents** feature (the docs also call it *Automated Threat Response*) joins the two:

1. A security device sends an alert, usually as a syslog message.
2. FortiNAC-F normalises the alert into a common **security event** format and ties it to a host it knows (by IP address, then the host's MAC, user, location and so on).
3. **Security rules** decide whether the event matters, and can run an **action** such as disabling the host or moving it to remediation.

The payoff is containment time. Instead of an analyst reading a FortiAnalyzer alert, finding the switch port and shutting it, FortiNAC-F can isolate the endpoint seconds after the alert arrives, at the access edge, whatever switch or AP vendor it is on.

> **Exam tip:** Security Incidents is a licensed feature. If the licence is not present, the Security Incidents views (Events, Alarms, Rules, Triggers, Actions) are not available, and neither are features that depend on it, such as Advanced Scan Controls in endpoint compliance configurations.

This lesson covers the integration side (getting events in and parsed). The next lesson covers triggers, rules and actions.

## Where things live in the GUI

| Item | Menu path (FortiNAC-F 7.6) |
|---|---|
| Security events, alarms, rules, triggers and actions | **Logs > Security Incidents** (Events, Alarms, Rules, Triggers, Actions) |
| Security event parsers | **System > Settings > System Communication > Security Event Parsers** |
| The sending device | **Network > Inventory**, modeled as a pingable device (or a full device model) |
| Syslog files and Trap MIB files (event/alarm route, not security events) | System > Settings > System Communication |

Keep the two inbound-syslog features apart. **Syslog Files** turn syslog into ordinary FortiNAC *events* that you map to *alarms* (Domain 3). **Security Event Parsers** turn syslog into *security events* for the Security Incidents engine (this domain). They are independent and don't feed each other.

## Step 1: let syslog reach port1

FortiNAC-OS only accepts the services listed in each interface's `allowaccess`. Security event syslog arrives on the management interface, so port1 needs `syslog` (UDP 514):

```text
FNAC-CA1 # show system interface
...
FNAC-CA1 # config system interface
FNAC-CA1 (interface) # edit port1
FNAC-CA1 (port1) # append allowaccess syslog
FNAC-CA1 (port1) # end
```

`set allowaccess` replaces the whole list, so if you use `set` you must repeat every service already there (`https-adminui ssh ping snmp nac-ipc …`). `append allowaccess` adds to the list. Forgetting this is the classic reason a perfectly built parser never sees a message.

> **Watch out:** The parser page in the 7.6 guide states the FortiNAC-OS requirement explicitly: the `syslog` option must be in `allowaccess`. A FortiGate or FortiAnalyzer that shows "log sent" while FortiNAC-F shows no security events usually means a port1 access, routing or firewall problem, not a rule problem.

## Step 2: build a security event parser

A parser tells FortiNAC-F how to read one vendor's message. Settings:

| Field | What it does |
|---|---|
| Enabled | Only enabled parsers are offered when you configure a device in Topology |
| Name / Vendor | Your label and the vendor that generates the event |
| Format | **CSV** (fields separated by a delimiter), **TAG/VALUE** (`srcip=10.0.10.25`) or **CEF** (fixed header positions plus tag/value extensions) |
| CSV Delimiter | Character between fields (space, comma, pipe …). Not used for TAG/VALUE |
| Tag Delimiter | Character between a tag and its value. Not used for CSV |
| Source/IP Column | The field name or column number holding the **source IP**, the endpoint FortiNAC-F will act on |
| Destination IP, Type, Subtype, Threat ID, Description, Severity columns | Where to find the other normalised fields |
| Data fields: Entire or Partial Column/Tag | Use the whole value, or a regular expression that extracts part of it |
| Severity mappings | Map the vendor's severity values (single value or **Add Range**) to FortiNAC-F severity values |

Two helpers save time:

- **Populate from Received Syslog** builds the parser from a message FortiNAC-F has already received. You still have to choose the right **Format**.
- **Test** (right-click on a parser) lets you paste a syslog message and see how it parses before you rely on it. **In Use** shows which modeled devices use the parser; **Copy** clones it.

FortiGate and FortiAnalyzer logs are key=value text, so TAG/VALUE is the natural format. The Fortinet "Configure Security Incidents" guide notes that FortiAnalyzer 6.4.1 uses a **space** as the delimiter; other systems may use commas, so check a real message.

> **Real world:** Start with a message copied from the source. For a FortiGate AV event you need at least `srcip` (source), `dstip`, `type` (for example `utm`), `subtype` (for example `virus`) and a severity field such as `level`. The type/subtype values become the fields you filter on in triggers.

## Step 3: model the sender and attach the parser

Security events are only accepted from a device FortiNAC-F knows. In **Network > Inventory**, right-click a container and **Add Pingable Device** (or use the existing model of a FortiGate):

| Field | Example |
|---|---|
| IP Address | The address the device sends syslog **from**, e.g. FortiAnalyzer `10.0.20.15` |
| Physical Address | Device MAC |
| Device Type | Firewall |
| Incoming Events | **Security Events**, with the parser you created |

If the source IP of the syslog does not match the modeled device, the message is not associated with that device and its parser. On a multi-interface FortiAnalyzer or FortiGate, check which interface actually sources the log traffic.

## Step 4: send something and prove it arrived

The documented validation is to make the security device log a real event (the guide uses the EICAR test file through a FortiGate with AV and deep inspection, forwarded by FortiAnalyzer), then check FortiNAC-F in two places.

On the wire, with the FortiNAC-OS packet capture:

```text
FNAC-CA1 # execute tcpdump -i=port1 -c=5 port 514
```

A matching packet shows the FortiAnalyzer address sending to port1 on UDP 514, with the FortiGate log fields (`type="utm" subtype="virus" … srcip=10.0.10.25 dstip=…`) in the message.

In the GUI, open **Logs > Security Incidents > Events**. A parsed event appears with its vendor, type, subtype, source IP and the host FortiNAC-F resolved. If the packet arrives but no event appears, the parser or the device association is wrong. If neither appears, fix the path (allowaccess, routing, the sender's syslog settings).

| Symptom | Likely cause |
|---|---|
| No packets in `execute tcpdump` | Sender not configured, firewall in the path, wrong destination IP |
| Packets arrive, no security event | `syslog` missing from `allowaccess`, sender not modeled (source IP mismatch), Incoming Events not set to Security Events, parser disabled or wrong format/delimiter |
| Events appear, no alarm | No rule matches (see next lesson). This is normal: an alarm is only created when a rule matches |

> **Exam tip:** "Security device integration" questions usually test the chain *device modeled → parser enabled and selected → port1 accepts syslog → events visible*. Pick the missing link the exhibit shows.

## Lab it yourself (optional)

A FortiNAC-F VM needs a licence (POC, partner or employer lab); there is no free self-service trial. If you have one:

1. Use a FortiGate-VM permanent trial as the event source: enable AV on a policy and send syslog directly to FortiNAC-F port1 (FortiAnalyzer is optional).
2. Add `syslog` to port1 `allowaccess`, build a TAG/VALUE parser with a space delimiter, model the FortiGate with Incoming Events = Security Events.
3. Download the EICAR file from a client behind the FortiGate and watch `execute tcpdump -i=port1 port 514` and Logs > Security Incidents > Events.

Reading-only path: walk the menu paths above in the Administration Guide and match each parser field to a real FortiGate log line.

## Key takeaways

- Security Incidents (Automated Threat Response) is licensed; it normalises alerts from security devices into security events.
- Security event parsers live under **System > Settings > System Communication > Security Event Parsers** and support CSV, TAG/VALUE and CEF.
- The Source/IP column identifies the endpoint to act on; severity mappings translate vendor severities.
- The sender must be modeled in Inventory with **Incoming Events = Security Events** and the parser selected.
- FortiNAC-OS port1 must allow `syslog` in `allowaccess`, or nothing is received.
- Validate with `execute tcpdump -i=port1 port 514` and **Logs > Security Incidents > Events**; no matching rule simply means no alarm.
