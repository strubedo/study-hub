## A note on the words "hot standby"

The exam topics say "HA functions with FortiNAC-F — hot standby mode" and contrast it with "N+1". The FortiNAC-F 7.6 documentation does not define a feature called *hot standby mode*. What it describes is:

- **1+1 high availability**: a primary and a secondary appliance in an **active/passive** pair. The F 7.6.3 release notes call it *High Availability Active-Stand-by Mode*, and from **F 7.6.3** the secondary keeps its services running at all times to cut failover time.
- **N+1 failover groups** (next lesson): one secondary CA for up to five primaries, managed by FortiNAC-M, new in 7.6.
- In **F 7.6.7**, a five-layer *CA Clustering Failover Health Check Mechanism*, which the release notes label **"True Hot Standby"**, feeding both 1+1 and N+1 failover decisions.

So on this site, "hot standby" questions mean the **1+1 primary/secondary pair**. Where a behaviour depends on the build, the stem names it.

## How 1+1 HA works

| Component | Role |
|---|---|
| Primary server | In control by default |
| Secondary server | Standby; takes control on failover |
| Management process (control process) | Runs on **both** appliances. Mirrors critical data, controls services, decides who is in control |
| Loaders | The FortiNAC-F application processes. Run **only on the appliance in control** |
| Database replication | Primary → secondary only. The secondary never replicates back (resume control copies data back explicitly) |
| Idle | A state in which the secondary's management process runs but it will **not** take control even if it loses the primary |

Since 7.2.4, **port2 is disabled on the appliance that is not in control**, so only one appliance answers DHCP, DNS and the captive portal for isolated hosts. Since 7.6.0 the secondary's GUI is available in standby with a limited menu (certificates, Config Wizard settings).

### What triggers a failover

1. **A required service fails** on the primary. The primary tries to restart it every 30 seconds; after the **fourth failed restart attempt** it hands control to the secondary.
2. **The secondary cannot contact the primary.**

| Required service | CA (FortiNAC Server) | FortiNAC Manager |
|---|---|---|
| mysql | Yes | Yes |
| SSHd | Yes | Yes |
| dhcpd | Yes (only when port2 has an IP address) | No |
| httpd | Yes | No |
| named | Yes | No |

Each failure raises a *Service Down* event (for example *Service Down - dhcpd*); a restart raises *Service Started*. The *System Failover* event marks a failover and *Database Replication Error* warns that the secondary is not up to date.

### The secondary's decision logic

The secondary polls the primary **every 30 seconds**. After a missed poll it retries **5 more times** by default (the *Ping Retry Count*, changeable but not too low). The `output.processManager` log on the secondary shows it:

```text
sendPacket() 10.0.1.21 verb Ping retval = Running - In Control
sendPacket() 10.0.1.21 verb Ping retval = null
**** Failed to talk to Primary **** PingRetryCnt = 1 pingRetries = 5
**** Failed to talk to Primary **** PingRetryCnt = 2 pingRetries = 5
**** Failed to talk to Primary **** PingRetryCnt = 3 pingRetries = 5
**** Failed to talk to Primary **** PingRetryCnt = 4 pingRetries = 5
**** Failed to talk to Primary **** PingRetryCnt = 5 pingRetries = 5
**** Failed to talk to Primary **** PingRetryCnt exceeded!
```

Then:

1. The secondary pings the **Secondary Appliance Gateway IP Address** configured on the HA page.
2. **F 7.6.3+**: if the pair is managed by **FortiNAC-M**, the secondary asks the Manager about the primary. If the Manager says the primary is running, the secondary does **not** promote itself (split-brain prevention).
3. Gateway **reachable** → the primary is assumed isolated, so the secondary takes control. (If the secondary's management process has been up for less than 10 minutes, it first waits 10 minutes for the primary.)
4. Gateway **unreachable** → the secondary assumes *it* is the isolated one and does **not** take control.
5. An **Idle** secondary never takes control.

Network-split scenarios (mostly L3 HA):

| Scenario | Result |
|---|---|
| Primary ↔ secondary link down, both gateways reachable | Without FortiNAC-M: both run (split brain); when the link returns, the primary's loaders stop and the secondary stays in control. With FortiNAC-M reaching the primary: nothing changes |
| Link down and primary's gateway unreachable | Primary shuts down, secondary takes control |
| Link down and secondary's gateway unreachable | Primary stays active; secondary does not start loaders; replication restarts when the network returns |

To stop a WAN failure from causing split brain, the guide suggests setting each appliance's gateway IP to the **other site's** gateway, so an isolated secondary fails the gateway test.

### Timing

| Build | Detection + failover |
|---|---|
| Before F 7.6.3 | About **10–15 minutes** |
| F 7.6.3 and later | About **1–5 minutes** |

The failover step itself is about 2 seconds (4 seconds if managed by FortiNAC-M); detection takes the rest. The guide quotes availability between 99% and 99.5%: HA, not fault tolerance.

## Design: Layer 2 or Layer 3

| | L2 HA | L3 HA |
|---|---|---|
| Location | Same subnet | Different subnets/sites (DR data centre) |
| Shared IP (VIP) | Optional; not on Azure | Not used |
| Config Wizard network type | Either | **Layer 3** required (L3 HA is not supported with Layer 2 isolation) |
| port2 isolation addresses | Secondary uses the **same** isolation IPs as the primary | Secondary uses **its own** subnet; configure DHCP helpers to **both** port2 addresses; hosts get two DNS servers |

Common rules for both:

- Infrastructure devices send **traps to both port1 addresses**, never the shared IP.
- Devices using FortiNAC-F as RADIUS server: primary RADIUS = primary port1, secondary RADIUS = secondary port1 (not the shared IP). Consider a real RADIUS server as a last-resort fallback.
- Persistent Agent: use the primary and secondary server FQDNs.
- With a VIP, GUI access goes through the shared IP; direct UI access to the members isn't supported (it can be enabled temporarily for the Config Wizard).
- Requirements: same appliance type (CA with CA, Manager with Manager), same OS (no FortiNAC-OS/CentOS mix), same version, port1 gateways pingable, SSH between the appliances. From F 7.6.3 (and 7.2.9, 7.4.1) some mixed platforms are supported, for example primary VMware with secondary AWS. HA is included in Base, Plus and Pro licences.

## Configuration steps (FortiNAC-OS)

1. Back up the primary database (System > Scheduler > Database Backup > Run Now).
2. Exchange SSH keys:

```text
FNAC-CA1 # get system public-key
FNAC-CA2 # config system ha
FNAC-CA2 (ha) # set public-key add <FNAC-CA1 key>
FNAC-CA2 (ha) # end
FNAC-CA2 # get system public-key
FNAC-CA1 # config system ha
FNAC-CA1 (ha) # set public-key add <FNAC-CA2 key>
FNAC-CA1 (ha) # end
```

3. Make sure port1 `allowaccess` on both includes **`ping`**, **`ssh`** and **`nac-ipc`** (`show system interface`).
4. Record both serial numbers (`get system status`) and add them to the **allowed serial numbers** list on the primary (in the shell: `globaloptiontool -name security.allowedserialnumbers -setRaw "<primary SN>,<secondary SN>"`).
5. `execute reboot` both.
6. In the primary GUI: **System > Settings > System Management > High Availability**: optional shared IP, mask and host name (L2); primary IP and gateway; secondary IP, host name and gateway. Apply; the appliances restart.

## Validation, failover test and recovery

| Check | Where |
|---|---|
| Status | Dashboard **System Summary**: primary *Running - In Control*, secondary *Running - Not In Control* |
| Licences | System > Settings > System Management > License Management, select the secondary (from 7.6.3 its licence fields read INHERITED FROM PRIMARY) |
| Replication | Logs > Events & Alarms: *Database Replication Succeeded*; F 7.6.2 and earlier `diagnose tail -F output.processManager` shows `replica is active`; F 7.6.3+ uses `RunClient FailoverConsole checkDBSyncUpToDate primary` / `secondary` in the shell (no output = in sync) |
| Who is in control (CLI) | `diagnose tail -F output.processManager`: `(Primary) Primary In Control Idle(false)` |

**Test**: create a container named TEST in Inventory, tail `output.processManager` on both, then force a failover (`execute ha failover` on the primary, or unplug port1). Don't use `halt`/`poweroff`: a clean shutdown idles the control process and the secondary won't take over. When done, the secondary shows *Running - In Control* and the TEST container exists on it.

**Maintenance without failover**: in the shell, `shutdownNAC` stops the loaders and sets the secondary to **Idle**. `shutdownNAC -kill` stops the management process; running it on the primary **without** `shutdownNAC` first **causes a failover**. `startupNAC` starts things again.

**Resume control is always manual.** The primary never takes control back by itself. After fixing the cause, use the **Resume Control** button in the System Summary widget (grayed out until a failover has happened). The primary restarts, the database and configuration files are copied from the secondary, the primary's processes start and the secondary relinquishes control. If the secondary's copy looks incomplete, recovery offers to keep the primary's older database.

## F 7.6.7: the five-layer health check ("True Hot Standby")

| Layer | Default cadence | Monitors |
|---|---|---|
| L1 Infrastructure | 10 s | CPU, memory, disk, network latency |
| L2 Database | 15 s | Connections, query time, slow SQL, disk I/O wait, MariaDB status, data syncer |
| L3 Cache | 15 s | Redis connection, memory, response |
| L4 Services | 20 s | Master loader, DHCP, DNS, FreeRADIUS, Apache, CLI, NTP |
| L5 Custom components | 30 s | Custom health checks |

Each component is HEALTHY, WARNING or CRITICAL; rules combine them into an overall status that drives 1+1 and N+1 promotion. Configure it with `diagnose system health-check …` (for example `diagnose system health-check display layer`, or the cluster keys such as `primary-check-interval` and `enable-witness-node`, where the witness is always the NCM). Changes are picked up within 5 seconds, no restart.

## Key takeaways

- 1+1 = active/passive primary/secondary; loaders run only on the appliance in control; replication is primary → secondary.
- Failover: a required service (mysql, SSHd, dhcpd, httpd, named on a CA) can't be restarted after four tries, or the secondary loses the primary.
- Secondary polls every 30 s, 5 retries by default, then pings its gateway; unreachable gateway or Idle = no takeover. F 7.6.3+ asks FortiNAC-M first.
- Detection + failover: ~10–15 min before F 7.6.3, ~1–5 min from F 7.6.3.
- L3 HA needs the Layer 3 network type and no shared IP; traps and RADIUS always point at both port1 addresses.
- Configure: SSH keys (`config system ha` / `set public-key add`), `nac-ipc` in allowaccess, allowed serial numbers, then the HA page.
- Resume control is manual (System Summary > Resume Control).
