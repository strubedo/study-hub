## Users, hosts and adapters

FortiNAC-F stores endpoints in a three-level hierarchy:

| Level | What it is | Where to see it |
|---|---|---|
| User | A person (directory, local, guest, contractor). Owns zero or more hosts | Users & Hosts > User Accounts |
| Host | A device that needs network services: PC, phone, printer, camera, card reader | **Users & Hosts > Hosts** |
| Adapter | A network interface on a host, with its MAC, IP, location (switch port or SSID) and online/offline status | **Users & Hosts > Adapters** |

Searching for an IP address in the Hosts view really searches the *adapters* and shows the host that owns the matching adapter. Quick Search accepts IP, MAC (use colons in MAC wildcards, for example `00:09:0F:*`), host name, user name and user ID; the drop-down beside it builds and saves custom filters. Hover over a status icon for a tooltip with the details, and expand a host to see its adapters.

The **Displayed / Total** counters in the title bar compare what the current filter shows with what the database holds.

## Host records and how they get there

| Source | Result |
|---|---|
| A new MAC is seen (trap, poll, RADIUS, DHCP) | A **rogue** host record (unknown, unregistered) |
| Captive portal registration, Persistent Agent, Passive Agent | Host **registered to a user** |
| Device profiling rule with Registration = Automatic | Host registered **as a device** (with type, role and optional group) |
| Device profiling rule with Registration = Manual | Device listed under **Profiled Devices** for an administrator to approve |
| Administrator: Add/Modify Host, Register As Host, Register As Device | Registered host or device |
| Import (CSV) | Bulk hosts, users or devices |

A host registered to a user inherits network access parameters from that user and counts toward the user's **Allowed Hosts**. Each registered host or device that is online consumes one endpoint licence.

> **Watch out:** Device profiling (rule methods, fingerprints, confirming rules) is Domain 4. In Domain 2 the point is the *outcome*: the profiling rule registers the device and can add it to a group (for example *IP Cameras*), and that group is what your access policy matches.

## Register As Device

Printers, servers, lab boxes and IoT devices plugged into managed ports start as rogues and get isolated like any other unknown MAC. **Register As Device** (Hosts or Adapters view, right-click) fixes that. The **Create In** choice matters:

| Create In | Behaviour |
|---|---|
| Host View | Stays in the Hosts view: connection history kept, can be associated with a user |
| Device in Topology | Moved to **Network > Inventory** and removed from the Hosts view: can be **polled** and its contact status monitored. Needs an IP address and a container |
| Host View and Topology | Shown in both: history and user association kept, but it **cannot be polled** |

You also choose the **Device Type** (icon and type used by policies) and the **Role**. If you register an access point in Host View, it is moved to Inventory after the first poll and stops counting as a concurrent licence once recognised as an AP.

The reverse exists too: non-SNMP devices (pingables) in Inventory can be **converted to hosts** (Convert To Host, or Convert Pingables To Hosts on a container). Converted devices become subject to host **aging** rules, and their IP is filled in by the next L3 poll. Wireless APs added as pingables can't be converted.

## Enable, disable, delete

| Action | Effect |
|---|---|
| Disable Hosts | All of the host's adapters are disabled; the host gets dead-end/no access |
| Enable Hosts | Restores access. If a **security alarm** disabled it, you are asked whether to undo the alarm (and its actions) or keep it |
| Delete Hosts | Removes the record. Deleting from Hosts also removes it from Inventory; deleting from Inventory does not delete the host record |
| Set Host Expiration | Sets when the record ages out |

Disabling can be automated: map an event (for example *Possible MAC address spoof*) to an alarm with a Disable Hosts action, or use a security rule action.

Other right-click options worth knowing: **Policy Details**, **Host Properties**, **Group Membership**, **Add Hosts To Groups**, **Scan Hosts** (needs a Persistent Agent; otherwise the host is marked at risk for the closest scan), **Send Message** (Persistent or Mobile Agent), **Go To Logged On User(s)** and **Go To Registered User(s)**. You can act on at most **200** hosts at once.

## Which policy applies right now? Policy Details and the simulator

**Policy Details** (right-click a host or user) evaluates the host *at the moment you open it* and shows one tab per policy type. The Network Access tab lists:

| Field | Meaning |
|---|---|
| Profile Name | The user/host profile that matched |
| Policy Name | The network access policy that applies |
| Configuration Name | The network access configuration (VLAN, CLI or VPN group) |
| Access Value/VLAN | The value that would be applied |
| CLI | CLI configuration, if any |
| Tags | Firewall tags (defined in a logical network configuration in a device's model configuration) |
| Debug Log | The evaluation trace, useful for support |

Because profiles have a *When* part and hosts move, the answer can change tomorrow. **Edit Test** opens the **policy simulator**: you fill in Adapter, User, Host, Applications, Tests and Date & Time tabs (or populate them from existing records) and FortiNAC-F shows which policy and profile *would* match, without a real device connecting.

> **Exam tip:** "How can the administrator verify which network access policy a registered host matches without reconnecting it?" Policy Details. "…for a host at a different location or time?" The policy simulator (Edit Test).

## Portal pages

Hosts in isolation see the **captive portal**. In FortiNAC-F 7.6 the portal is edited in **Portal > Portal Configuration** (7.6.0 introduced a redesigned portal configuration UI). The FortiNAC-OS requirement is that `allowaccess` includes `http` and `https` (both listed as portal services in the CLI reference) on the interface that serves the portal, normally port2 for isolated hosts.

Portal Pages settings decide which login options appear in each context:

| Context | Examples of options |
|---|---|
| Global | Success Page Type, Show Usage Policy Before Registration, MDM Registration redirect for mobile user agents |
| Isolation | **Portal Selector** (let the user pick a portal) |
| Registration | Standard User Login, Guest Login, Self-Registration Guest Login, Anonymous Authentication, Game Console Registration, Custom Login, optional approval |
| Authentication | Standard User Login, Guest Login, Request New Credentials, Custom Login |
| VPN | Download page and login instructions |

### Several portals: portal policies

Default portals shipped with FortiNAC-F include **Portal** (generic), **RegistrationPortal** (employee, BYOD and guest self-registration) and **RestrictedPortal** (no registration: tells the user the device isn't a company device, for "friend or foe" networks).

Which portal a host sees is chosen by **portal policies** (Policy & Objects > Portal Policy): a user/host profile plus a portal configuration, evaluated by rank, first match wins. Because the host is unregistered when it hits the portal, FortiNAC-F knows very little about it. The profile used in a portal policy can only usefully match **location** (port/device/SSID group), **IP address**, **MAC address** or **operating system**, never user groups. If no portal policy matches, the **default portal** is used. Assigning a portal to an SSID under SSID Mappings creates the matching profile and portal policy automatically.

The **Portal Selector** (Isolation section) shows a list of portals when FortiNAC-F can't decide, and the **Host Inventory** portal page lets users see and register their own devices (Register Enabled, Require Valid Vendor OUI, Delete Enabled).

## Key takeaways

- Users own hosts; hosts have adapters. IP/MAC searches find adapters and show their hosts.
- Register As Device: **Host View** (history, user), **Device in Topology** (pollable, removed from Hosts), **both** (history, not pollable).
- Disable Hosts disables every adapter; re-enabling a host disabled by a security alarm offers to undo the alarm.
- **Policy Details** shows the matching profile, policy, configuration, access value, CLI and tags now; **Edit Test** simulates other scenarios.
- Portal policies pick a portal by rank using only location, IP, MAC or OS; otherwise the default portal is used.
- The portal needs `http` and `https` in `allowaccess` on the interface that serves it (port2 for isolation).
