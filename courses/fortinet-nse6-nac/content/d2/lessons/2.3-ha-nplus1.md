## Why N+1

A 1+1 pair doubles the hardware: every CA needs its own idle twin. FortiNAC-F **7.6** adds **N+1 failover groups**: **one secondary CA protects one or more primary CAs**. Before 7.6, FortiNAC only had 1+1. You can build several groups to get *N+M* redundancy, for example ten site CAs protected by two secondaries.

| | 1+1 HA | N+1 failover group |
|---|---|---|
| Ratio | One secondary per primary | One secondary for up to **5** primaries |
| Who manages it | The pair itself (HA page on the primary); FortiNAC-M optional | **FortiNAC-M**: System > CA Management |
| Who runs health checks | Secondary pings primary; primary checks its own services | The **secondary CA**, not FortiNAC-M |
| Failover decision | Missed polls + gateway test (+ Manager check from 7.6.3) | **Direct** and **indirect** checks both fail |
| Status names | Running - In Control / Running - Not In Control | **Running**, **Standby**, **Promoted**, **Failed** (on FortiNAC-M) |
| Resume | Manual: System Summary > Resume Control | Manual: right-click the primary in CA Management > **Resume Control** |

> **Exam tip:** N+1 failover groups are managed by FortiNAC-M, but the **secondary CA** does the health checking. "FortiNAC-M detects the failure and promotes the secondary" is the classic wrong answer.

## The failover process

The secondary CA checks each primary in its group in two ways:

1. **Direct check**: the secondary connects to the primary itself.
2. **Indirect check**: if the direct check fails, the secondary asks **another primary** in the group to check the failed one.

Only when **both** fail does the secondary start the failover. It starts running and its status on FortiNAC-M changes from **Standby** to **Promoted**. Fortinet quotes about 5 minutes (the validation section says 5–10 minutes for the promotion to show), depending on hardware and network.

| Scenario | Direct check | Indirect check | Result |
|---|---|---|---|
| Neither the secondary nor Primary 2 can reach Primary 1 | Fail | Fail | **Failover** of Primary 1 |
| Secondary can't reach Primary 1, Primary 2 can | Fail | Pass | No failover |
| Primary 2 can't reach Primary 1, the secondary can | Pass | (not needed) | No failover |

From **F 7.6.3** the secondary also health-checks the primary automatically before promotion, replacing the older gateway-check logic, and the custom health check types were trimmed to **ICMP** and **TCP** (specific port); RADIUS and TCP Echo were removed. The 7.6.0 guide still documents RADIUS and TCP Echo, so be careful which build a question names.

## Traffic redirection: FortiADC or backup IP

When the secondary takes over a primary, the network has to send that primary's traffic to it. N+1 gives two options.

### Option 1: a load balancer (FortiADC)

For each primary, a virtual server per port, each with two real servers (the primary's port and the secondary's port). The load balancer health-checks the servers and sends traffic to the secondary if the primary fails.

- RADIUS, NAS and DHCP relay configuration then only needs the VIP, not two addresses.
- Protocols with no built-in failover (syslog, SNMP queries and traps, NetFlow) reach the right server; without a load balancer, devices often send to both and the secondary handles unnecessary traffic.
- On each primary, point the port2 isolation networks at the port2 VIP so DNS answers for the portal and agent return the load-balanced address:

```text
FNAC-CA1 # config system vip
FNAC-CA1 (vip) # edit registration
FNAC-CA1 (registration) # set virtual-ip 192.168.100.5
FNAC-CA1 (registration) # next
FNAC-CA1 (vip) # edit remediation
FNAC-CA1 (remediation) # set virtual-ip 192.168.100.5
FNAC-CA1 (remediation) # end
FNAC-CA1 (vip) # end
```

The `config system vip` context exists only on an in-control CA; isolation names are `isolation`, `registration`, `authentication`, `remediation`, `deadend` and `vpn`. The `named` service restarts when you leave with `end`, and the settings sync to the secondary.

- Config Wizard settings are **not** replicated to the secondary. Configure the isolation scopes of **all primaries** on the secondary before building the group, with static routes under Additional Routes (next hop FortiADC) as the design needs.

### Option 2: backup IP (no load balancer)

| Mode | Layout | How it works |
|---|---|---|
| **Independent IP** | Layer 3: each primary has its own dedicated backup IP | When a primary fails, the secondary brings up that primary's backup IP as its port1 service address (same subnet as the secondary's port1), plus the port2 L3 settings you define for it. When the primary recovers, the secondary releases it |
| **Shared IP** | Layer 2: primary and secondary port1 in the same network | A shared IP (with a VLAN ID, so switch ports facing port1 must trunk) moves to whichever appliance is active; the secondary clones the primary's port2 configuration |

Independent IPs can also be set from the CLI on F 7.6.3+ (`RunClient FailoverConsole setIndependentAddress <ip>,<mask>` on a primary).

## Building the group (FortiNAC-M)

Order matters: **secondary first, then primaries**.

1. **System > CA Management > Add New**: name, eth0 (port1) IP and serial number of each CA. You can add several at once.
2. Edit the **secondary**: enable **N+1 Failover**, Failover Role **Secondary**, choose the Backup IP type (None, Independent or Shared). Its status changes from *Running* to **Standby**.
3. Edit each **primary**: enable N+1 Failover, Failover Role **Primary**, select the secondary CA, fill the backup IP fields if used.
4. The primary joins the group. The secondary **ignores a primary whose firmware version differs**, so match versions first.

Limits and notes:

- At most **5** primary servers per secondary.
- Custom health checks are created on the NCM leader at **System > Custom Health Check** (type ICMP to a gateway, for example, Retry and Timeout) and attached per primary under CA Management > Edit > Custom Health Check. A failing custom check triggers failover, which shortens detection.
- To move from 1+1 to N+1: remove the HA configuration first, then build the N+1 group (maintenance window, services restart).

## Validate, fail over, resume

| Step | What you should see |
|---|---|
| Normal state | CA Management: primaries **Running**, secondary **Standby**; the standby's UI has a limited menu |
| Trigger | On the primary: `execute ha failover` and answer `y`, or unplug its port1 |
| Logs on the secondary | `diagnose tail -F output.processManager \| grep -i failover` shows `begin failover` … `CA health check status change from null to PROMOTED` |
| After failover | Secondary **Promoted**, primary **Standby** (or Failed); TEST container visible on the secondary; licence matches FortiNAC-M |
| Resume | CA Management, right-click the primary > **Resume Control**. Success: primary **Running**, secondary **Standby**. Failure: primary back to **Failed**, secondary stays **Promoted** |
| Logs on resume | `isCampusManagerCheckOK system true, in control true` on the primary, `… in control false` on the secondary |

After a primary is repaired it comes back in **Standby** and the secondary **stays Promoted**: nothing fails back automatically.

## CLI for N+1 (F 7.6.3+, run on the CAs, not on FortiNAC-M)

From the shell (`execute enter-shell`):

| Command | Purpose |
|---|---|
| `RunClient FailoverConsole getFailoverGroup` | Show the group's primaries and secondary |
| `RunClient FailoverConsole setFailoverGroup <ip,sn,…,secondary_ip,secondary_sn>` | Define the group; the last pair is the secondary |
| `RunClient FailoverConsole forceFailover <primary_sn>` | Fail a primary over; **secondary only**, and it must be in standby |
| `RunClient FailoverConsole forceResumeControl` | Return control to a standby primary; **secondary only**, must be promoted |
| `RunClient FailoverConsole removeFailoverGroup` | Remove failover settings on this CA |

## Use case: N+1 load balancing for a campus

Four building CAs (`FNAC-CA1`, `FNAC-CA2` and two more) share one standby `FNAC-CA3` at the data centre. FortiADC publishes a RADIUS/syslog/SNMP VIP and a port2 VIP per CA. Switches and controllers point at the VIPs. If the building 1 CA dies, `FNAC-CA3` sees both its direct check and the indirect check (through another building's CA) fail, is promoted, and FortiADC's health checks steer building 1's traffic to it. A fifth building could still join this group; a sixth would need a second group.

## Key takeaways

- N+1 (new in 7.6): one secondary CA for up to five primaries, managed in **FortiNAC-M > System > CA Management**.
- The **secondary CA** runs the checks: direct, then indirect via another primary; both must fail.
- Statuses: Running → primary, Standby → secondary; on failover the secondary is **Promoted**. Resume Control is manual.
- Add the secondary first; firmware must match; Config Wizard isolation scopes aren't replicated, so configure them on the secondary.
- Redirect traffic with FortiADC (VIPs, `config system vip` for port2) or backup IP (Independent L3 or Shared L2 with VLAN).
- F 7.6.3: custom checks ICMP/TCP only, automatic pre-promotion check, FailoverConsole CLI, independent IP CLI.
