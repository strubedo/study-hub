## Why send identity to FortiGate

Switch VLANs give coarse segmentation. A FortiGate can do much finer work (application control, per-group policies, east-west inspection) if it knows *who and what* each IP address is. FortiNAC-F knows exactly that, so it sends FortiGate one of three labels for each online registered host:

| Label | Defined in | Example |
|---|---|---|
| **User group** or **administrator group** | FortiNAC-F groups (local or directory) | *Contractors* |
| **Host group** | FortiNAC-F host groups | *IP Cameras* |
| **Firewall tag** | A simple label created in FortiNAC-F, not tied to group membership | *Cameras*, *Production* |

The FortiGate uses the label in a firewall policy. As the host connects, changes state or disconnects, FortiNAC-F updates the FortiGate and the policy follows the host. Firewall tags are useful when groups don't fit: the tag is chosen by **policy**, not by membership.

## Two integration methods

| | **Connector Based FSSO Tag** | **Dynamic Address Tag** |
|---|---|---|
| How FortiGate connects | An **external connector** (FSSO agent) pointing at FortiNAC-F; FortiNAC-F acts as a **collector agent** | FortiNAC-F **joins the Security Fabric**; the Fabric root authorises it |
| Port | TCP **8000** (FortiNAC-F `allowaccess fsso`) | **8013** |
| FortiNAC-F sends | Logon/logoff events: device IP, user ID (or MAC if no user), group filter = user group, host group or firewall tag | REST API: device IP, FortiNAC group information, firewall tag |
| Used in FortiGate as | **FSSO user groups** in the policy's source user field (address use is possible too) | **Dynamic address objects** (*FortiNAC Tag (IP Address)*), named after the FortiNAC-F serial number + tag or group, usable as **source or destination** |
| FortiGate requirement | FortiOS 7+, FortiGate **not** joined to the Fabric | FortiOS 7.2.4+, FortiGate is the **Fabric root** |

Rules that apply to both:

- **Use only one method** if FortiNAC-F manages several FortiGates. Mixing them has caused tags to stop being sent or dynamic tags to disappear.
- FortiGate accepts only **one FSSO agent's** tags per endpoint IP; other agents reporting the same IP overwrite FortiNAC-F's entries, so exclude those IPs from the other agents.
- If FortiNAC-F is disconnected for **300 seconds**, the FortiGate removes all its SSO logons (hard-coded on FortiGate).
- FortiNAC-F resynchronises with FortiGate every 15 minutes and re-adds missing sessions.
- From FOS 7.4.8 and 7.6.4, FortiNAC-F needs a **REST API administrator token** for the FortiGate (entered when modeling the device or later on its Credentials tab).

Logon triggers: a registered device connects, a user logs on, the IP changes, the device status changes. Logoff triggers: user logoff, device disconnect.

> **Exam tip:** Network access policies don't match **rogues** or **offline** hosts, so those never produce a tag or group logon. And host status wins over policy: an **at-risk** registered host gets the **Quarantine** access defined in the FortiGate model, not its policy's tag.

## Step 1: model the FortiGate

**Network > Inventory**, add or discover the FortiGate: IP, SNMP credentials (read), CLI administrator credentials, and the **API key**. Then **Resync Interfaces**; the **Virtualized Devices** tab lists the VDOMs, and FortiLink-managed FortiSwitches appear once CLI credentials are set. On FOS 7.4.8+ set the Telnet/SSH and CLI command timeouts to 30 on the Credentials tab. F 7.6.5+ can use SSH public key authentication (System > Settings > System Communication > SSH Key Management).

FortiGate **wired interfaces** are controlled by applying firewall policy to the session: **no VLAN is assigned**. FortiWiFi/FortiAP clients get VLANs through RADIUS, and policies on top.

## Step 2: decide the label in FortiNAC-F

There are two places, matching the two exam use cases.

### A. Through the network access configuration

The network access policy's configuration (the SSO guide's *Direct Configuration*) can say what to send:

- **Send User and Host Groups to the Firewall**, and pick the groups; and/or
- **Firewall Tags**: type the tag name.

Firewall tags themselves are created at **System > Settings > System Communication > Firewall Tags** (Add, tag name). Then rank the policy.

### B. Through the FortiGate model configuration (logical networks)

Use the policy's **logical network**, and let the FortiGate's model decide the tag:

1. Create the logical network, for example `Cameras` (Network > Logical Networks).
2. Network access configuration → logical network `Cameras`; policy *IP Cameras* → that configuration.
3. **Network > Inventory** > FortiGate > **Virtualized Devices** tab > right-click the VDOM > **Model Configuration**.
4. For logical network `Cameras`, create or choose the **firewall tag(s)** to send, for example tag `Cameras`.

This is the same abstraction as VLANs: on a switch `Cameras` means VLAN 40, on the FortiGate VDOM it means tag `Cameras`. **Policy Details** shows the result in its **Tags** field ("firewall tags defined in a logical network configuration as part of a device's model configuration").

The FortiGate model also defines the **Quarantine** (and other state) access for at-risk hosts, and **SSO Addresses** / **VPN Addresses** (address groups of the IP scope to manage; a resync is needed after changes).

## Step 3a: FSSO connector (Connector Based FSSO Tag)

FortiNAC-F:

1. **System > Settings > System Communication > Fortinet FSSO Settings**: Enable FSSO Communication, port **8000**, password.
2. In the FortiGate VDOM's Model Configuration set the **Source IP Address** the FortiGate uses to talk to FortiNAC-F.
3. Add **`fsso`** to port1 `allowaccess`.

FortiGate (7.2.4+): **Security Fabric > External Connectors > Create New > FSSO Agent on Windows AD**: primary FSSO agent = FortiNAC-F port1, the password, and `config user fsso` / `edit "<name>"` / `set source-ip <FortiGate IP>` to match FortiNAC-F's Source IP. **Refresh** imports the FortiNAC-F tags and groups; build FSSO user groups from them and use those in policies. In HA, add the secondary's port1 as an additional FSSO agent, not the shared IP.

```text
FGT-HQ # diagnose debug authd fsso list
----FSSO logons----
IP: 10.0.40.31  User: 00:09:0F:4C:21:7A  Groups: CAMERAS  Workstation:  MemberOf: Cameras
Total number of logons listed: 1, filtered: 0
----end of FSSO logons----
```

A camera has no user, so its **MAC** is the user field; the group is the tag the matching policy produced. On FortiNAC-F, logon messages are written to `output.master` by default (`diagnose tail -F output.master`); `diagnose debug plugin enable SSOManager` adds detail, and `diagnose network sso session-list ip=<FortiGate IP>` lists what FortiNAC-F holds for a device.

## Step 3b: Security Fabric (Dynamic Address Tag)

1. On every managed FortiGate: Security Fabric > Fabric Connectors > Security Fabric Setup: enable **Allow downstream device REST API access**; note the Fabric root's management IP.
2. FortiNAC-F: **Network > Service Connectors > Create New > Security Fabric Connection**: IP = **root FortiGate**, Port = **8013**. Status: *Waiting for Authorization*.
3. On the root FortiGate, **Authorize** FortiNAC-F in the Fabric topology (CLI: `config system csf` > `config trusted-list` > `edit "<FortiNAC serial>"` > `set action accept`).
4. Confirm *Connected* in FortiNAC-F's service connector and FortiNAC-F in the FortiGate's physical and logical topology. `diagnose sys csf downstream-devices fortinac` on FortiGate lists it.

FortiGate then shows **FortiNAC Tag (IP Address)** dynamic addresses under Policy & Objects > Addresses. Each holds the current IPs of hosts with that tag or group; addresses with no current members get a red exclamation mark. Use them as source or destination; *View Matched Addresses* on the policy shows the live members, which change as users log on and off.

> **Watch out:** The Fabric integration is with the FortiGate **physical topology** view, and FortiNAC-F must point at the **root** FortiGate on port **8013**. Pointing at a downstream FortiGate, or using 8000, is the FSSO method.

## FortiNAC-F in the Security Fabric: quarantine from FortiGate

With the Fabric connection in place, FortiGate's automation can act through FortiNAC-F. An automation stitch with the **Quarantine via FortiNAC** action and a **Compromised Host** or **Incoming Webhook** trigger quarantines the client: FortiNAC-F **disables its MAC address**. FortiNAC-F then isolates it at the switch or AP, wherever it is. Combine that with FortiNAC-F's own security rules (lesson 2.1) for a closed loop.

F 7.6.7 adds sending **remote groups** (for example directory groups) to FortiGate and Palo Alto firewalls (Remote Group Integration Guide).

The FortiGate side fits a FortiGate-VM permanent trial (3 interfaces, 3 policies): one LAN, one WAN, one interface to FortiNAC-F; policies *Cameras → Internet deny*, *Corp → Internet allow*, *FortiNAC-F management*. ## Key takeaways

- FortiNAC-F sends user/host groups or **firewall tags** to FortiGate; FortiGate policies use them.
- **FSSO tag**: external connector, TCP **8000**, FSSO user groups, FortiGate not in the Fabric. **Dynamic Address Tag**: Fabric root, **8013**, dynamic address objects. Use one method only.
- Tags come from the network access configuration (send groups / Firewall Tags) or from the **FortiGate VDOM model configuration** per **logical network**.
- Firewall tags are created at System > Settings > System Communication > Firewall Tags.
- Only online registered hosts that match a policy produce logons; at-risk hosts get the FortiGate model's Quarantine access.
- Fabric join: Network > Service Connectors > Security Fabric Connection → root FortiGate IP, port 8013 → authorise on the root.
- **Quarantine via FortiNAC** (Compromised Host or Incoming Webhook trigger) disables the host's MAC in FortiNAC-F.
