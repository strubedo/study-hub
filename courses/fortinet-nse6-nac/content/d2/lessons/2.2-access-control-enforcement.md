## The access control model in one paragraph

FortiNAC-F is **out of band**. It does not sit in the data path; it tells the network infrastructure what to do with each endpoint. When a host connects, FortiNAC-F learns *where* (switch port, SSID, VDOM interface), works out the host's **state** (unknown, registered, at risk, disabled, needs authentication), and then either **isolates** it (registration, remediation, authentication or dead-end treatment) or gives it **production access** chosen by policy. The infrastructure device enforces the decision: a switch changes the port VLAN, a wireless controller or switch applies RADIUS attributes, a FortiGate applies a firewall policy.

## Host states drive isolation

| Host state | Typical treatment | Isolation network (Config Wizard scope) |
|---|---|---|
| Rogue (unknown, not registered) | Registration isolation until registered (captive portal, agent, device profiling, admin) | Registration |
| Registered, user must authenticate | Authentication isolation until the user logs in | Authentication |
| At risk (failed an endpoint compliance scan, or marked at risk by a security action) | Remediation (quarantine) isolation until it passes | Remediation |
| Disabled | Dead End: little or no connectivity | Dead End |
| Registered, trusted, enabled | Production: the network access policy (or device role) decides the VLAN, role, CLI or tag | — |

Host status takes precedence over policy. A registered host that is **at risk** gets the quarantine treatment, not the production access its network access policy would give it. Network access policies only ever apply to **registered** hosts.

## Which ports and devices are enforced: enforcement groups

FortiNAC-F only switches ports and SSIDs that you tell it to control. In the classic model this is done with system **port groups** (enforcement groups). Put a port, or a group of ports, in a group and FortiNAC-F enforces that function there:

| Enforcement group | Rule it enforces |
|---|---|
| Forced Authentication | The user must be authenticated; otherwise the port goes to an isolation VLAN |
| Forced Registration | The device must be known (registered); rogues go to isolation |
| Forced Remediation | The device must be trusted; at-risk hosts go to isolation |
| Physical Address Filtering | Disabled devices get no access (isolation/dead end) |
| Role-Based Access | Known devices get the VLAN chosen by a **network access policy** (registered hosts) or a **network device role** (devices in Inventory) |
| Reset Forced Default | The port returns to its default VLAN when the host disconnects |

A port that is in no enforcement group is visible but not controlled. That is how you run FortiNAC-F in visibility-only mode first and "go live" per closet or per floor later.

> **Exam tip:** Without Role-Based Access on a port, a registered host stays in the port's current/default VLAN even though a network access policy matches it. "Policy Details shows the right policy but the VLAN never changes" points at enforcement scope, not the policy.

### 7.6.7: State Based Access Control Rules

FortiNAC-F **7.6.7** adds a selector-based architecture (introduced with RADIUS-only device support). In it, the same six enforcement functions appear as **State Based Access Control Rules** at **Network > Configuration > State Based Access Control Rules**:

- The table has **six predefined entries**, one per **membership action**: Forced Authentication, Forced Registration, Forced Remediation, Role-Based Access, Roaming Guest Interfaces and Physical Address Filtering.
- In 7.6.7 you can **edit** these (description, status on/off, conditions) but **cannot create new states**, and an entry can't be saved without at least one condition.
- Conditions are typed **RADIUS** (an attribute such as NAS-Identifier), **Device** (for example Vendor), **Container** (for example Container Name) or **Port and SSID** (for example SSID, Port Group). The **+** at the right of a condition adds an **AND** condition in the same group; the **+** at the bottom adds another group with **OR** logic.

Example: Forced Registration with Group 1 = Port Group equals *Legacy Forced Registration* OR Group 2 = Ethernet Wired Port equals *No*.

The selector model also brings **Configuration Selectors**: ranked rules (rank 1 highest, first match wins, like policies) that apply a configuration object to a device model when it is added or discovered. The 7.6.7 selectors are the **RADIUS Server Selector**, **Response Attribute Selector**, **Logical VLAN Mapping Selector** and **SSO/VPN Configuration Selector**. If no selector matches, that part of the model is configured by hand.

> **Watch out:** Questions written for 7.6.0–7.6.6 talk about port groups such as Forced Registration. Questions that name 7.6.7, "selectors" or "membership actions" mean the new pages. Read the build in the stem.

## Per-device treatment: the model configuration

Every modeled infrastructure device has a **Model Configuration** (Network > Inventory > right-click the device). It is stored in the FortiNAC-F database and is *not* pushed to the device. Key access-control parts:

- **VLAN ID / Network Access**: the Default, Dead End, Registration, Quarantine (remediation), Authentication and Voice values for this device. **Read VLANs** pulls the VLAN list from the device where supported.
- **Logical network access values**: what each logical network means on this device (next lessons).
- For RADIUS-managed models, a **Host State / Access Enforcement / Access Value** table per state (Default, Dead End, Registration, Quarantine, Authentication, Roaming Guest):

| Access Enforcement | Result for a host in that state |
|---|---|
| Enforce | Place the host in the **Access Value** VLAN or role given here |
| Bypass | Let the host on, in the default VLAN/role configured on the device for that port or SSID |
| Deny | Reject the connection (the endpoint may keep retrying, which costs resources) |

For example, *Registration = Bypass* on a guest SSID lets unknown hosts straight onto the SSID's default VLAN, with no captive portal. *Quarantine = Enforce, 110* sends at-risk hosts to the remediation VLAN 110.

## Enforcement methods

| Method | How the change is made | Typical devices |
|---|---|---|
| VLAN switching (SNMP or CLI) | FortiNAC-F writes the port's VLAN with SNMP set or over SSH/Telnet. It learns connections from **link up/down and MAC notification traps** and L2 polling | Wired switches (Cisco, FortiSwitch standalone, …) |
| RADIUS | FortiNAC-F (local RADIUS or proxy) returns the VLAN/role attributes in the Access-Accept. To change a connected host it sends **RFC 5176 CoA or Disconnect** (default UDP **3799**), so the device re-authenticates | 802.1X/MAB switches, wireless controllers, FortiAPs via FortiGate, RADIUS-only devices in 7.6.7 |
| CLI configurations | Saved command sets with **Set** and **Undo** parts sent to the device (ACLs, port settings). Substitution variables `%port%`, `%vlan%`, `%ip%`, `%mac%` | Port-based or host-based ACLs, rate limits, special devices |
| FortiGate firewall policy | FortiNAC-F sends the host's group or firewall tag to FortiGate (FSSO or dynamic address); FortiGate's policy decides | FortiGate wired interfaces (no VLAN change), VPN |
| VPN group policy | The access value is the VPN group policy name returned to the VPN concentrator | VPN headends |

For **FortiGate wired interfaces**, the FortiGate integration guide is explicit: access is provisioned by applying a firewall policy to the session, and **VLANs are not assigned**. FortiWiFi wireless clients get VLANs during RADIUS authentication, and firewall policies can be applied on top.

Two diagnose commands let you test enforcement by hand (FortiNAC-F CLI, base context):

```text
FNAC-CA1 # diagnose network vlan change 10.0.30.11 port5 100
FNAC-CA1 # diagnose network radius send-coa disconnect 10.0.30.21 00:09:0f:aa:10:21
```

The first moves one port of the modeled switch at `10.0.30.11` to VLAN 100. The second asks the NAS at `10.0.30.21` to disconnect the session of that MAC so it re-authenticates and picks up a new decision.

> **Real world:** "Modeled devices for enforcement" means every switch, controller or FortiGate you want to control must be in **Network > Inventory** with working credentials: SNMP (read/write where VLAN switching uses SNMP), CLI credentials where the device is driven over SSH, RADIUS secret and **Enable RADIUS authentication for this device** for RADIUS devices, and API token for FortiGate. A device that only shows contact status is visible, not controllable.

## Access control use cases at a glance

| Goal | Building blocks |
|---|---|
| Keep unknown devices off production wired ports | Ports in Forced Registration (or the 7.6.7 Forced Registration rule), Registration VLAN in each switch model, captive portal |
| Quarantine non-compliant laptops | Endpoint compliance policy, Forced Remediation, Quarantine VLAN |
| Put each department in its own VLAN | Ports in Role-Based Access + network access policies (lesson 2.4) |
| Printers and servers in Inventory to a fixed VLAN | Network device roles (lesson on logical networks) |
| Guest SSID with no portal | Model configuration: Registration = Bypass for that SSID |

## Key takeaways

- FortiNAC-F is out of band: it decides, the switch/controller/FortiGate enforces.
- Host state wins over policy: rogue → registration, at risk → remediation, disabled → dead end; policies only apply to registered hosts.
- Enforcement groups (Forced Authentication/Registration/Remediation, Physical Address Filtering, Role-Based Access, Reset Forced Default) define where FortiNAC-F enforces.
- 7.6.7 moves these to **State Based Access Control Rules** (Network > Configuration): six predefined membership actions, editable but no new states; plus ranked Configuration Selectors.
- Model configuration per device: isolation VLANs and Access Enforcement **Enforce / Bypass / Deny** per host state.
- Methods: SNMP/CLI VLAN switching, RADIUS attributes with RFC 5176 CoA/Disconnect on UDP 3799, CLI configurations (Set/Undo), FortiGate firewall policies via groups/tags.
