## What the database holds

Almost everything FortiNAC-F knows lives in its database: modeled devices and ports, users, hosts, adapters, groups, policies, profiles, guest accounts, fingerprints and the last known state of each element (online/offline, enabled/disabled, location, VLAN). The backup documentation puts it simply: everything you see in the administration GUI is in the database **except alarms and events, connection logs and scan results**, which are archived and purged separately.

The data model is hierarchical:

- A **user** owns or is associated with one or more **hosts**.
- A **host** has one or more **adapters** (network interfaces), each with a MAC address, last known IP, location (device and port) and media type (wired/wireless).
- Adapters of the same host are **siblings**. FortiNAC-F can only tie several adapters to one host when an **agent** reports them; without an agent, a laptop seen on wired and Wi-Fi becomes **two host records**.

| Question | Where to look |
|---|---|
| What is this endpoint and who owns it? | Users & Hosts > Hosts, Host Properties |
| Which switch port or SSID is the MAC on, and with which IP? | Users & Hosts > Adapters, Adapter Properties |
| Who is the user and which hosts do they have? | Users & Hosts > User Accounts |
| What did it connect to, when, and with which logical network? | Network > Network events |
| What traffic did it have through a FortiGate? | Users & Hosts > Network Sessions |
| What is it, according to its fingerprints? | Endpoint Fingerprints view |

## The Hosts and Adapters views

Hosts, Adapters and Users share one search engine. Searching a host by IP actually searches the IP of its adapters; switching from Hosts to Adapters or Users re-runs the search and keeps the relationship. **Quick Search** accepts an IP address, MAC address, host name, user name or user ID, with wildcards such as `10.10.10.*`. A **MAC wildcard must keep its colons** (`00:09:0F:*`), or FortiNAC-F can't tell it's a MAC. The title bar shows **Displayed** versus **Total** records.

Custom filters (the drop-down at the end of the search field, or **Add Filter** on filter panels) combine fields. Common filter types: **Host Type** (Registered / Rogue), **Registered**, Enabled/Disabled, IP address, Physical Address, Location, Group, Container, Authentication Type, and time filters (**Last**, **Between**, **Month**, **After**, **Before**). Wildcards in text fields:

| Pattern | Meaning |
|---|---|
| `192.*` | Begins with 192 |
| `[a,b,c]` | Any of the listed values |
| `!192.` | Does not contain 192. |
| `![x,y]` | Contains none of the listed values |
| `<esc>!` | Literal exclamation mark |

The **Status** column icon tells you the host state at a glance (rogue, registered, at risk, disabled, online/offline), and hovering over it shows a tooltip with the details. Useful right-click options on a host: **Host Properties**, **Policy Details** (which network access, endpoint compliance, portal and supplicant policies would apply right now), **Show Events**, **Show Network Sessions**, **Register As Host / As Device**, **Enable/Disable Hosts**, **Set Host Expiration**, **Group Membership**, **Show Audit Log**. Deleting a host from the Host View also removes it from the Inventory, but deleting from the Inventory doesn't remove it from the Host View.

**Host Properties** shows Host Name, Hardware Type, Operating System, Serial Number, Host Status (Enabled/Disabled), **Created**, **Expiration Date**, **Inactivity Date**, **Inactivity Limit**, **Last Connected** (the time the online/offline status last changed), Role, Agent Version, Security And Access Attribute Value, plus Adapters, Applications, Health and Notes tabs. Guest data with no database field ends up on the Notes tab.

The **Host Summary** dashboard widget counts registered hosts by state (Safe & Authenticated, At Risk, Pending at Risk, Not Authenticated and combinations), each split into Online/Offline × Enabled/Disabled, plus counts of unregistered hosts and IP phones.

## Reports

**Logs > Reports** has three tabs:

- **Templates**: standard Guest Registration, Registration (successes, failures by reason, OS) and Scan Results reports, with preview.
- **Custom**: registrations, registration failures, scan results and connection logs with your own parameters and filters; output to HTML, CSV, Excel, XML, RTF or PDF.
- **Archives**: output of scheduled runs.

Both kinds can be **scheduled** and emailed to an **administrator group**; members need an email address and the mail server must be set. Report size is capped by **Local Reporting** settings (Preview and Scheduled Report Record Limit, default 10,000 each). Every table view can also be exported (CSV, Excel, PDF, RTF).

## Enhanced visibility from FortiGate sessions

FortiNAC-F can poll a modeled FortiGate for its session table. In **Network > Inventory**, right-click the FortiGate > **Set Firewall Session Polling** (only offered on FortiGate models): **Enabled**, **Frequency** (default **5 minutes**), optional **Create Rogues from Session Data**, **Poll Now**. FortiNAC-F reads the sessions through the FortiOS REST API (`api/v2/monitor/firewall/session/select`), so some sessions the FortiGate GUI shows may not appear.

The results appear in **Users & Hosts > Network Sessions** (NetFlow is the other source). Filters: Country, Destination address, Destination MAC, Destination port, Device, Firewall, Hostname, Protocol, Source address, Source MAC, Source port (one of each type). From a session you can **Create Device Profiling Rule**, and **Show Network Sessions** on a host or adapter opens its sessions directly.

Why it matters on the exam:

- It gives visibility behind a FortiGate where no switch is modeled, and **Create Rogues from Session Data** puts those endpoints in the database.
- The device profiling methods **Active** and **FortiGate** use network-session data and **require firewall session polling**; **Network Traffic** needs session polling and/or NetFlow.

## User and host aging

Without expiration dates, host and user records stay **indefinitely**. Global age times are set in the **Aging** settings (the 7.6 guide gives **Users & Hosts > Settings > Aging** on the Aging page and **System > Settings > User/Host Management > Aging** elsewhere; same settings):

| Setting | Effect |
|---|---|
| Days Valid | Days a host record stays after creation |
| Days Inactive | Days a host may be offline before deletion |
| Days Valid / Days Inactive (Users) | Same for user records |
| Delete hosts registered to user upon expiration | Removes a user's hosts when the user ages out |
| Clear Unregistered / Clear Registered / Clear Aging Values for All Users | Wipes calculated dates so new values can apply |
| Randomized-MAC settings | Separate Days Valid / Days Inactive for hosts whose adapters all use randomized MACs, matched by a vendor-code regex |

Rules worth memorising:

- Global settings apply to **new** records and to existing records **with no aging values**. Records that already have dates aren't changed until you **Clear** them. Records set to **Never** expire are never changed.
- Applying aging to old records can delete them **immediately**: a host created 1 January with Days Valid 5, aged on 2 February, gets an expiration date of 6 January and is removed straight away.
- **Group aging** (System > Groups > right-click a host group > **Set Aging**) overrides existing values for every member (except Never); with several groups the last group applied wins.
- Per-host or per-user values (**Set** on Properties, **Set Host Expiration**) override the rest. Directory **Time To Live** mappings can also set them.
- Host age times are evaluated **every ten minutes**. The **Inactivity Date** is recalculated each time the host goes offline and cleared while it is online. The user inactivity timer starts when **all** of the user's hosts are offline.
- Leaving the fields empty disables global aging; **0** removes records at the next poll. Administrators with the System Administrator profile are never aged out.
- Guests: the user expires per the template/end date and takes the host with them; the host itself follows global aging for registered hosts.

> **Exam tip:** before switching on global aging in a live system, work out the expiration date for your oldest records. Days Valid counts from the record's **creation** date, so a long-standing database can lose thousands of hosts the moment you click Save Settings.

Aging a large population at once causes a wave of re-registrations, so stagger the values. A related limit, **Allowed Hosts** (System > Settings > User/Host Management), caps how many hosts one user can register (default 1000).

## Key takeaways

- The database holds everything in the GUI except alarms/events, connection logs and scan results.
- User → hosts → adapters; without an agent each adapter of a multi-NIC laptop becomes its own host.
- Quick Search and filters (Host Type Registered/Rogue, wildcards, `!`, `[…]`) find hosts; MAC wildcards need colons.
- Policy Details on a host shows which policies would apply right now.
- Firewall session polling (default 5 minutes) feeds Network Sessions and is required by the Active and FortiGate profiling methods.
- Aging: global settings fill empty records only; group aging overrides; Never is never touched; age checks run every ten minutes; retroactive aging can delete records immediately.
- Reports: Templates, Custom and Archives under Logs > Reports, schedulable to administrator groups.
