## Rogues and classified devices

When something with an unknown MAC address connects, FortiNAC-F creates a **rogue** host record: a host in the database with no registration (no owner, not a known device). Rogues are what forced-registration and isolation act on. Printers, cameras, card readers and IP phones can't log in to a portal, so FortiNAC-F uses **device profiler** to classify them automatically.

**Device profiler** runs continuously. It takes rogues that have an IP address, compares what is known about them with the **device profiling rules** in rank order, and on a match assigns the rule's **device type** and **role**, optionally registers the device, and places it in the Host View, the Inventory or both. A device that has matched a rule and been given a type is what the exam calls a **classified** device; a device that matched nothing (or matched a rule set not to register) is still a rogue.

| Term | Meaning in FortiNAC-F |
|---|---|
| Rogue | Unregistered host record (Host Type = Rogue in filters) |
| Profiled/classified device | Host associated with a device profiling rule and given that rule's type and role; registered automatically or manually, or left as a rogue if the rule doesn't register |
| Registered host | Known host with an ID: registered to a user (portal, agent, import) or as a device |

> **Exam tip:** device profiler only looks at **rogues**. Once a host is registered, new or changed rules are never applied to it. To re-classify a registered device you modify it by hand, or delete it so it reconnects as a rogue and is evaluated again.

## How a device gets profiled

1. A device connects and FortiNAC-F learns about it (traps, polling, DHCP, RADIUS, firewall sessions …).
2. If the MAC is unknown, a rogue record is created with whatever is known. Device profiler waits up to **30 minutes** for the IP address to be resolved by normal IP-to-MAC (L3) polling.
3. Once there is an IP address, the rogue is compared with each **enabled** rule from rank 1 down. Disabled rules are ignored.
4. The first rule whose criteria all match wins. The device gets the rule's type and role (these override any type or role from the vendor OUI table; with no role, NAC-Default applies).
5. If **Notify Sponsor** is set, device managers responsible for that rule get an email.
6. Registration: **Automatic** registers immediately (when *Register as* is set); **Manual** leaves the device in **Profiled Devices** for someone to register.
7. If nothing matches, the device is associated with the **Catch All** rule, which has no methods and no type, and remains a rogue unless that rule is configured otherwise.

If the concurrent licence count is exceeded, matching hosts are listed in Profiled Devices but **not** registered. When licences free up, register them manually (**Register As Device**) or delete them so they are re-profiled.

## Building a rule

Rules are under **Users & Hosts > Device Profiling Rules**. Default rules ship **disabled** and set not to register, and upgrades don't add or change default rules, so profiling does nothing until you enable rules.

**General tab**

| Field | Purpose |
|---|---|
| Enabled, Name, Notify Sponsor | Basic identity and email to device managers |
| Registration | **Automatic** or **Manual** |
| Type / Role | Device type and role assigned on match (F 7.6.3 expanded the type list to FortiGuard categories and subcategories) |
| Register as | **Device in Host View**, **Device in Topology** (pick a container), **Device in Host View and Topology**, **Host to User**, **Host to Logged In User (If Present)** |
| Add to Group | Only for devices placed in the Host View |
| Access Availability | Always, or a time window (devices outside it are marked At Risk for the Guest No Access scan; Host View placement only) |
| Rule confirmation | **Confirm Device Rule On Connect**, **Confirm Device Rule On Interval** (minutes, hours or days), **Disable Device If Rule No Longer Matches Device** |

**Methods tab.** Select one or more methods. The device must satisfy **every selected method** to match the rule. Within some methods, extra values are alternatives: several vendor OUI entries, several credentials or several response strings match if **any** one matches. TCP and UDP are the exception: if you list several ports, **all** must be open.

| Method | What it checks |
|---|---|
| Vendor OUI | Vendor code, name or alias (wildcards allowed) or device type in the OUI database; ignores the rule's type and uses the entries |
| DHCP Fingerprinting | The last DHCP packet seen (parameter list, hostname, vendor class, option list, message type) |
| IP Range | Address ranges, wildcards allowed |
| Location | Containers in the Inventory |
| TCP / UDP | Open ports |
| Passive | Passive OS fingerprinting |
| Persistent Agent | OS reported by the FortiNAC agent |
| RADIUS Requests | Fingerprints from local RADIUS Access-Requests |
| SNMP, SSH, Telnet, HTTP/HTTPS, WinRM, WMI Profile | Active queries with credentials or requests; optional match strings |
| Active, FortiGate | Data from network sessions; **requires firewall session polling** |
| Network Traffic | Flows by protocol and destination port; requires firewall session polling and/or NetFlow (`netflow` in `set allowaccess`) |
| ONVIF | ONVIF profiles A, C, G, Q, S, T supported by cameras and access control systems |
| FortiGuard | FortiGuard IoT Service lookup by MAC (needs a FortiCare support contract) |
| Script | Script in `/home/cm/scripts`, matches on exit status 0 |

## Rank and best practice

Rules are checked by **rank**, so order matters twice: for correctness and for speed.

- Put **OUI** rules first (no outside data needed, fastest), **DHCP** rules next, and Active, TCP/UDP, IP Range and Location rules last.
- Put a **specific** rule above a **general** one. Example: an iPhone rule that checks a TCP port goes above a generic macOS DHCP rule, because their fingerprints look alike.
- **Missing data stops evaluation.** If a rule needs information FortiNAC-F doesn't have (no DHCP fingerprint, no IP address), the device is **not** skipped to the next rule; its evaluation ends there and a *Device Profiling Rule Missing Data* event is logged. That's why DHCP rules belong at the bottom where static-IP devices exist, and why IP helpers should point DHCP at the FortiNAC-F.
- Rules that need an IP address take longer: device profiler uses the newest entry in its IP-to-MAC cache (not the possibly stale Adapter View IP) and, if missing, starts an IP-to-MAC lookup on L3 devices. Without working L3 polling those rules fail.
- The **Catch All** rule is always last and can't be moved; new rules are inserted just above it.
- On a CA managed by FortiNAC Manager, **local rules rank above global rules** and global rule rank can only be changed on the Manager.

## Re-evaluating rogues and confirming rules

After adding or changing rules, click **Run** on the Device Profiling Rules view: every rogue that is still connected and not yet categorized is added to the **Rogue Evaluation Queue** (its size is shown on the view, with a Detail button and a **Flush** option). Offline rogues are ignored, already-categorized devices are not touched, and Notify Sponsor emails are sent again.

**Rule confirmation** re-checks devices that were profiled earlier, on connect and/or on an interval. A failure logs *Device Rule Confirmation Failure* and, if configured, disables the device (Confirmation Failure Action = Disable Device). Confirmation can be set per rule or per device (**Rule Settings** in Profiled Devices), and **Confirm Rule** runs it on demand for an online device.

From the CLI:

```text
FNAC-CA1 # diagnose host device-profiling rules display all
FNAC-CA1 # diagnose host device-profiling rules scan mac 00:09:0f:aa:10:21
FNAC-CA1 # diagnose host device-profiling rules scan size
FNAC-CA1 # diagnose host device-profiling host display rule-name "IP Cameras"
```

These list the rules, queue one MAC for evaluation, show the scan queue size, and list hosts associated with a named rule. `rules scan all` scans all rogues and `rules scan flush` empties the queue. In the GUI, **Test Device Profiling Rule** (Adapters and Endpoint Fingerprints views) tests a host against a rule using the data already in the database, and **Reprofile Rogue(s)** runs the rules against selected rogues.

## Events to watch

| Event | Meaning |
|---|---|
| Device Profile | Device profiling updated a rogue |
| Device Profile Rule Match | A rogue matched a rule and got a type |
| Device Profiling Automatic Registration | A rogue was registered by a rule |
| Device Profiling Rule Missing Data | Not enough data to compare the rogue with a rule; processing of that rogue stopped |
| Device Rule Confirmation Success / Failure | Result of rule confirmation |
| Device Fingerprint Changed | A host is seen with a different OS than it registered with (for example a dual-boot host) |

## Key takeaways

- Device profiler evaluates rogues with an IP address against enabled rules in rank order; the first full match assigns type and role.
- Every selected method in a rule must match; multiple OUI entries or credentials are alternatives, but multiple TCP/UDP ports must all be open.
- Missing data ends evaluation of that rogue at that rule, so rank OUI → DHCP → active/port/IP/location, and keep DHCP rules low where static IPs exist.
- Registered hosts are never re-profiled; Run re-evaluates connected, uncategorized rogues only.
- Register as decides Host View, Inventory (Topology) or both; Manual registration leaves devices in Profiled Devices.
- Active, FortiGate and Network Traffic methods depend on firewall session polling (or NetFlow).
- Default rules ship disabled; Catch All is always last; local rules rank above FortiNAC Manager global rules.
