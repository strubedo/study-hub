## From account to network access

Once templates and sponsor profiles exist, every visitor follows the same chain: **account created → credentials delivered → host lands in registration isolation → guest logs in on the portal → (optional) compliance scan → host registered to the guest user and moved to production**. This lesson walks each way of creating accounts, then the policies, events, reports and CLI checks that make guests and contractors manageable.

## Creating accounts

Sponsors land on the Guest/Contractor Accounts view; administrators use **Users & Hosts > Guests & Contractors > Users** and click **Add**. Which buttons appear depends on the sponsor's **Account Types**.

| Method | How it works | Points to remember |
|---|---|---|
| Single Account | Pick a template, enter the email (the only required personal data), start and end date | Password is generated (or typed). With an LDAP template there is no password field. The end date is capped by the sponsor's *Create Accounts Active For Days* |
| Bulk Accounts | Pick a Guest or Contractor template, type one comma-separated record per line or **Import From File** (CSV/TXT) | **No header row**, a comma for every field, a line break after every record, email mandatory. With **Import Passwords** on, the password must be the **last** field of every row |
| Conference | Pick a conference template, choose the conference type, name, number of attendees, start/end | Types: *Individual User Names/Individual Passwords*, *Individual User Names/Shared Password*, *Shared User Name/Shared Passwords*. The conference name becomes the user name. Only the password can be changed afterwards. No email or SMS until an address or number is added to each user |
| Self registration | The guest requests access from the portal | Account is created when a sponsor approves (or immediately if approval isn't required) |
| Kiosk | A kiosk sponsor logs in on a lobby PC; guests create their own accounts | Accounts use the kiosk template and never last past **11:59 PM** the same day |

After **OK**, the View Accounts screen offers **Print**, **Print Badge**, **Send Email** and **Send SMS**, depending on the profile and template.

> **Watch out:** generated passwords are only visible during the GUI session in which they were created. Later, **Print** or **Print Badge** generates a **new** password and the old one stops working. Administrators can't view passwords that conference users created.

The fields an account still lacks (marked with an asterisk in the template's Data Fields) are collected from the guest at first login: "required" means required before network access, not required at creation.

## Self-registration in detail

1. The guest connects, opens a browser and is redirected to the Registration page in the isolation network.
2. They choose **Self Registration**, fill in the form and click **Request Guest Access**. Depending on the portal settings they may have to enter a sponsor's email.
3. FortiNAC-F emails the sponsor. The email contains either **Approve/Deny** links or a **Login** link to the admin GUI (**Sponsor Approval Link Requires Login**).
4. The guest waits on a pending page and can cancel. If nobody answers within **Guest Request Expiration (minutes)**, which defaults to **20**, the request expires.
5. On approval, the account is created with the **Self-Registered Guest** template chosen in the portal (a default template named *GuestSelfRegistration* exists, and it must have an account duration). Credentials appear on the portal page, by email and/or SMS, according to the portal settings.

Pending and past requests are listed in **Users & Hosts > Registration Requests** with a **State** of Accepted, Canceled, Denied, Error, Expired or Pending, plus the IP address, MAC address and location (device and port) of the requesting host. An administrator can approve or deny any pending request from there.

**Require Sponsor Approval** decides who may approve: options include an administrator with self-registration permissions, any administrator, any user (or any user in a group), or email addresses from an allowed domain. If no approval is required, guests simply create their own accounts with the portal's template.

## Placing guests and contractors with policy

Guest accounts carry a **role** and a **Security & Access Value** from the template, and the registered host inherits the role. That is what user/host profiles match:

- **Network access policy.** User/host profile *Who/What by Attribute* = Role `Contractor` (or Security & Access Value `Contractor`) → network access configuration with the `Contractor` logical network. Put it above any broader policy, because policies are checked top down and the first match wins.
- **Endpoint compliance policy.** Same idea: a profile that only guests match (by role or Security & Access Value), with its own scan and agent, ranked **above** the general policies. Guests who fail are sent to remediation; guests who pass see the success page.
- **Time limits.** Login Availability on the template marks the host At Risk outside the window. A guest who connects outside the window sees a page saying network access has been disabled because they are outside the allowed time window.

> **Real world:** contractors usually need more than Internet access but less than staff. A per-template role (*Use A Unique Role Based On This Template Name*) lets you write one user/host profile per contractor template, so a "Contractor-Facilities" template can land on a different logical network from "Contractor-IT" without touching the accounts.

## Use cases

| Scenario | Configuration |
|---|---|
| Day visitors, front desk creates accounts | Guest template (Local auth, short duration, Send Email); sponsor profile with Individual + Bulk, Own Accounts, that template only |
| Three-month contractors, office hours only | Contractor template with Account Duration, Login Availability *Specify Time*, unique role; network access policy on that role |
| Two-day conference | Conference template with Max Number Of Accounts; Conference account *Individual User Names/Shared Password*; badges printed at registration |
| Wireless visitors approve themselves through their host | Self-Registered Guest template; portal Self Registration Login with Default Sponsor Email and approval links; SSID mapped for Guest Management |
| Lobby self-service | Kiosk template + kiosk sponsor profile; kiosk browser on the PC; accounts expire at 11:59 PM |

## Visibility: events, reports and CLI

- **Events:** *Guest Account Created*, *Guest Account Deleted* and *Conference Created* (with the number of accounts) appear in **Logs > Events & Alarms > Events** when enabled, and can be mapped to alarms. Licence events warn when guest licences in use pass the configurable thresholds.
- **Guest Registrations report** (**Logs > Reports**, Templates): sponsor, type, user, start/end, availability, role, **Max Registrations** and **Total Registrations** per account, with details of each registered host (location, host name, OS).
- **Users view:** guest users appear in **Users & Hosts > User Accounts**; *Guest Account Details* shows the template-derived settings, sponsor and account status.
- **CLI** (base context):

```text
FNAC-CA1 # diagnose user guest-templates list all
FNAC-CA1 # diagnose user list email=visitor1@example.net
FNAC-CA1 # diagnose host list owner=visitor1@example.net
```

The first lists the templates, the second confirms the guest user record exists, and the third looks for hosts registered to that user (the `owner=` selector matches the owner name).

## Troubleshooting guests quickly

| Symptom | Likely cause |
|---|---|
| Guest never reaches the login page | Port or SSID not in a forced registration group, or the host is already registered |
| "Outside of your allowed time window" page | Template Login Availability; host marked At Risk for Guest No Access |
| Request shows **Expired** | No sponsor answered within the Guest Request Expiration time (default 20 minutes) |
| Sponsor cannot pick a template | Template not in the profile's Allowed Templates |
| Sponsor can't email credentials | Template without Send Email, server email settings missing, or a conference account with no email address |
| Guest's old password no longer works | Someone used Print/Print Badge in a later session, which regenerates the password |

## Lab it yourself (optional)

Needs a POC/partner FortiNAC-F with the portal working. Reading-only path: follow the self-registration steps in the Administration Guide and note each setting's location.

1. Enable **Self Registration Guest Login** in the portal Login Menu and set a Default Sponsor Email with approval links.
2. Connect a test laptop to a forced-registration port, request access and approve it from the email.
3. Check **Users & Hosts > Registration Requests** for the Accepted request, then confirm the host in **Users & Hosts > Hosts** is registered to the guest.
4. Run the Guest Registrations report for today.

## Key takeaways

- Accounts are created as Single, Bulk, Conference, Self-registration or Kiosk; the sponsor profile decides which are available.
- Bulk guest import uses a CSV with **no header row**; with Import Passwords enabled the password is the last field.
- Conference accounts: Local authentication only, the conference name is the user name, only passwords can be changed.
- Self-registration requests go to a sponsor and expire after 20 minutes by default; track them in Users & Hosts > Registration Requests.
- Kiosk accounts expire at 11:59 PM; a kiosk sponsor can't do anything else.
- Guests and contractors get policy through the role and Security & Access Value set by their template, matched in user/host profiles that must rank above broader policies.
- Use the guest events, the Guest Registrations report and `diagnose user list` / `diagnose host list owner=` to see who has an account and which hosts they registered.
