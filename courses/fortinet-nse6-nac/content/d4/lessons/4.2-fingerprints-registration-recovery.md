## Endpoint fingerprints

FortiNAC-F keeps collecting identity data while hosts connect: DHCP options, agent reports, RADIUS attributes, FortiGuard IoT answers, Nmap and port results, SNMP/SSH/HTTP replies, the vendor OUI. Each piece is stored as an **endpoint fingerprint**, and the **Endpoint Fingerprints** view lists them. A **new record is added every time a new fingerprint is heard for a MAC**: an adapter that moves from the registration VLAN to production and asks DHCP for a new address produces another record. Two records for the same MAC and port with different operating systems usually mean a dual-boot host and raise *Device Fingerprint Changed*.

| Column | Meaning |
|---|---|
| Physical Address, IP Address, Host Name | Identity of the endpoint (host name from the DHCP packet) |
| Device Type, Operating System, Vendor, Vendor OUI | What the fingerprint says the endpoint is |
| Source | Which method produced the fingerprint |
| Rule Name | Device profiling rule the endpoint matched |
| Device Registered | Registered or rogue (the counts are shown above the table) |
| Creation Time / Last Heard | First and most recent time this fingerprint was seen |

**Set Source Rank** orders the sources used to fill in the host record (for example Agent first, then DHCPv4, then Vendor OUI). Right-click options include **Show Attributes** (the raw attributes per source, such as DHCP `PARAMLIST`, `VENDORCLASS`; FortiGuard `CAT`, `SUBCAT`, `CONFIDENCE`; RADIUS `Calling-Station-Id`, `NAS-IP-Address`), **Create Device Profiling Rule**, **Test Device Profiling Rule**, **Run FortiGuard IoT Scan**, **Register as Device** and enable/disable host.

Fingerprints alone don't register anything: the rogue record is filled from fingerprint data, and the device is only registered automatically if it matches a rule set to register. If its **vendor OUI isn't known** yet, FortiNAC-F can't register it.

> **Watch out (FortiNAC-OS):** many fingerprint sources need the matching service allowed on the interface with `set allowaccess` (for example `dhcp` for DHCP fingerprints, `radius`/`radius-local` for RADIUS, `snmp`, `ssh`, `http`/`https`, `nac-agent` for the agent). No allowaccess, no fingerprint.

Device profiler settings are under **System > Settings > User/Host Management > Device Profiler**: **Create Rogues from DHCP packets** (default enabled; quickly learns hosts but can add many rogues from unmanaged areas), **Perform Active (NMAP) profiling without ICMP ping**, the FortiGuard IoT query and collect services, and *proactive* Active and FortiGuard profiling that create fingerprints without a rule.

## Automated registration

Automatic registration is a device profiling rule with **Registration = Automatic** and a **Register as** option. The result depends on that option:

| Register as | Where it ends up | Consequence |
|---|---|---|
| Device in Host View | Host View (and Profiled Devices) | Connection history, can be added to a host group, can be associated with a user; uses a licence |
| Device in Topology | Inventory container only | Polled for contact status (red when unreachable), contact events; **not** shown in Profiled Devices; can't be managed by device managers |
| Device in Host View and Topology | Both | History plus Inventory placement |
| Host to User / Host to Logged In User (If Present) | Host View, registered to a user | Leaves Profiled Devices once associated with a user |

An access point registered in the Host View is moved to the Inventory after the first poll and stops counting against the concurrent licence. Event: *Device Profiling Automatic Registration*.

Other automatic paths exist outside device profiler: portal registration by users, agents (Persistent/Passive agent registration), and MDM integration; this lesson focuses on devices.

## Manual registration

| Where | Option | Result |
|---|---|---|
| Users & Hosts > Profiled Devices | **Register As Device** (right-click) | Registers devices matched by a Manual rule (or held back by licence limits) |
| Users & Hosts > Hosts or Adapters | **Register As Device** | Choose **Create In**: Host View, Device in Topology, or Host View and Topology; set Device Type, Role, container and IP (IP is required for Inventory) |
| Users & Hosts > Hosts or Adapters | **Register As Host** | Opens Modify Host to register the rogue to a user |
| Network > Inventory | **Convert To Host** / **Convert Pingables To Hosts** | Non-SNMP (pingable) devices also appear in the Host View and become subject to host aging |

Registering selected rogues as devices is how you stop them being treated as unknown (isolated or disabled) when they are legitimate printers, servers or lab hosts. Host registration ties a host to a user; device registration has no user and the host is known by its name.

## Host and device records from CSV files

**Users & Hosts > Hosts > Import** loads hosts, adapters, users and IP phones from a `.csv` file. Unlike the guest bulk file, this file **must start with a header row** of database field names (order doesn't matter, names are case-sensitive):

```text
adap.mac,siblings,adap.ip,host.owner,host.devType
00:09:0F:5A:10:01,00:09:0F:5A:10:01,10.10.10.21,jdoe,Windows
00:09:0F:5A:10:02,00:09:0F:5A:10:02,,,IP Phone
```

| Field | Notes |
|---|---|
| `adap.mac` | **Required** for host records; the MAC is the key. Importing an existing MAC **updates** that record |
| `siblings` | All adapter MACs of the host, `;`-separated; single-adapter devices list their own MAC |
| `host.owner` | Registered user ID; created if it doesn't exist |
| `host.devType` | One of the listed device types (Camera, Card Reader, IP Phone, Printer …) |
| `host.topo` | Inventory container: puts the device in both Host View and Inventory |
| `host.role`, `user.role` | Must exist with the same spelling; blank = NAC-Default |
| `host.expireDate` / `host.inact` | Aging; `Never` prevents aging, `host.inact` uses the form `1825 Days` |
| `user.uid` | Required for user records |

FortiNAC-F shows an **Import Results** preview; if required columns are missing or data is badly formatted, the import stops with an error.

For **infrastructure-style devices into the Inventory**, there is the CLI tool `DeviceImport` in the shell:

```text
FNAC-CA1 # execute enter-shell
DeviceImport printers.csv -type printer
```

One CSV per device type (for example printers and vending machines in separate files), lines `CONTAINER,IP,NAME,MAC,na,na,na,Role` for non-SNMP devices, and a line break after the last line. The CLI Reference notes that SNMP imports with this tool only support SNMPv1-managed devices; an existing device with the same IP is removed before the new one is created, so back up the database first. iOS and Android devices can't be imported this way; use the Host View import.

## Data preservation and system recovery

What gets backed up:

| Component | Contents | Scheduled task / GUI |
|---|---|---|
| Database | Everything you see in the GUI **except** alarms and events, connection logs and scan results | **Database Backup** · System > Settings > System Management > Database Backup/Restore |
| System files | Config Wizard settings and files needed to run the appliance (licence key, web server config …) | **System Backup** · System Management > System Backups |
| Alarms, events, scan results | Archived and purged by age | **Database Archive and Purge** · System Management > Database Archive (Event/Alarms Age Time default **7 days**) |

All three run from **System > Scheduler** (**Run Now** for an on-demand backup). Files are stored locally (for example `/bsc/backups/database/FortiNAC_DataBase_BackUp_<date>_<hostname>.gz`); **Remote Backup Configuration** copies them to an FTP, SSH or SFTP server (the FortiNAC-F public key goes into the server's `authorized_keys`; in HA add both nodes' keys). *Remove local backups older than* deletes only local copies: keep it longer than the backup interval or you can end up with none.

Restoring:

- GUI: Database Backup/Restore > select a backup > **Restore Database**. The server restarts.
- CLI: `execute restore database local <filename>` or `execute restore database scp <host> <username> <password> <backup-path>`; system/config backups with `execute restore backup local <hostname> <date>` or `execute restore config …`; `execute backup config local|scp|ftp|tftp` takes a configuration backup.
- Archived **events and alarms** are re-imported from their views with **Import**; this adds records and doesn't overwrite. They can only be restored from the local disk.

High availability is the other half of recovery: after a failover you fix the cause, then use **Resume Control** on the Summary panel so files and the database are copied back from the secondary to the primary (covered in Domain 2).

## Key takeaways

- Every new fingerprint for a MAC adds an Endpoint Fingerprints record; differing OSes for one MAC raise Device Fingerprint Changed.
- Fingerprints populate rogue records, but registration only happens through a rule set to register, or manually; an unknown vendor OUI blocks registration.
- Register as decides Host View, Inventory (Topology) or both; Inventory-only devices leave Profiled Devices and are polled for contact.
- Manual registration: Register As Device / Register As Host from Hosts, Adapters or Profiled Devices; Convert To Host from the Inventory.
- Host CSV import needs a header row with field names (adap.mac required, MAC is the key and existing records are updated); guest bulk CSV has no header.
- The database backup excludes alarms/events, connection logs and scan results; those are archived and purged (7 days by default) and restored by Import.
- Back up with the scheduled tasks or Run Now, copy off-box with remote backup, restore with Restore Database or `execute restore database`.
