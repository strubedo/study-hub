## Three questions about any host

Almost every "this device has no network" ticket starts with the same three questions. Answer them in order.

| Question | GUI | CLI |
|---|---|---|
| **Is the host in the database?** | Quick Search the MAC in Users & Hosts > Hosts or Adapters | `diagnose host list mac=<mac>` (add `-adapters` for adapter details, `-format=json` for JSON) |
| **Is it a rogue?** | Filter Host Type = Rogue; the Status icon; Network Events **Type** column (Registered/Rogue) | `diagnose host list mac=<mac>` lists the host record FortiNAC-F holds; check its registration details there or in the GUI |
| **Is it classified?** | Users & Hosts > Profiled Devices (**Rule Name**, Type, Registered); Endpoint Fingerprints (**Rule Name**, **Device Registered**) | `diagnose host device-profiling host display rule-name <rule>`; re-test with `diagnose host device-profiling rules scan mac <mac>` |

What each answer tells you:

- **Not in the database:** FortiNAC-F never learned the MAC. Look at how it learns: is the switch or AP **modeled**, does SNMP work, do traps arrive, is polling running? A host that FortiNAC-F has never seen can't be isolated, profiled or registered.
- **In the database as a rogue:** FortiNAC-F knows it but doesn't trust it. Unknown hosts on forced-registration ports go to the registration network. Fix with registration (portal, profiling rule, manual registration, import).
- **Rogue associated with a rule but not registered:** the rule is **Manual**, has no *Register as*, or the licence count was exceeded. Register from Profiled Devices.
- **Registered but wrong access:** now it's policy, not identity. Use **Policy Details** on the host and the **Logical Network** / **CLI Config Name** columns in Network Events to see what was applied.

## Troubleshooting a host connectivity issue

A practical order for a wired host that stays in the wrong VLAN or never gets access:

1. **Find the host** (Hosts/Adapters search or `diagnose host list mac=`). Note its state, location (device and port) and last connected time.
2. **Check the infrastructure device:** `diagnose network device display ip=<switch>` (what FortiNAC-F has modeled) and `diagnose network device test-snmp ip=<switch>` (do the SNMP credentials still work).
3. **Check how connections are learned:** `diagnose network mac-notification-stats all` (MAC notification traps handled per device or MAC; `num-devs=` / `num-macs=` show the busiest). If you rely on link traps, look for *Port Link Up/Down* and *MAC Learned/Removed* events. `diagnose network device read-forwarding-table ip=<switch>` reads the MAC table now (`-a` applies the result to host and adapter records). `diagnose network arp-cache find-mac <mac>` resolves the IP and triggers an L3 poll unless `--cacheOnly` is used.
4. **Capture if traffic is in doubt:** `execute tcpdump -i=port1 -c=20 udp port 162` proves traps reach the appliance; `udp port 514` for syslog; `port 67 or port 68` on port2 for DHCP in isolation. `-w=<file>` writes a pcap to your home directory.
5. **Turn on targeted debug and watch the main log:** `diagnose debug plugin list` to find the plugin, `diagnose debug plugin enable <name>`, then `diagnose tail -F output.master`. Disable the plugin afterwards (`diagnose debug plugin disable <name>`).
6. **Fix and verify:** correct the model or credentials, register the host, or fix the policy; watch Network Events for the connect and the applied logical network.

> **Exam tip:** MAC notification traps and link up/down traps overlap. If MAC notification traps are enabled on a device, **disable link up/down traps**: they are redundant, add load and stop the *MAC Learned* events from being generated. With link-up traps alone, FortiNAC-F waits *Minimum Trap Period* (default 10 s) × *Max Number of Trap Periods* (default 4) before reading the switch's forwarding table, and retries up to seven times. Polling (wireless default 10 minutes, wired default 1 hour) is the safety net for missed traps.

## Logging inside FortiNAC-F

| Log | Where | What it records |
|---|---|---|
| **Events** | Logs > Events & Alarms > Events | Audit trail of network and system incidents, **only for enabled events**. Columns include Date, Event, Element, Message; you can add notes and **Import** archived events |
| **Event management** | Logs > Events & Alarms > Management | Per event: **Disabled**, **Internal**, **External**, **Internal & External**; optionally limited to a **group**; **Event Thresholds** for licence, memory, threads, disk |
| **Alarms** | Logs > Events & Alarms > Alarms (and the dashboard widget) | Alarms created from events by **event-to-alarm mappings**; severity Critical, Minor, Warning, Informational; acknowledge (keeps it) or delete (clears it) |
| **Network events** | Network > Network events | Connection log: Timestamp, Event Type (adapter connected/disconnected, applied role/policy), IP, MAC, **Type** (Registered/Rogue), Location, **Logical Network**, Net ID, CLI Config Name, RADIUS flags |
| **Audit logs** | Logs > Audit Logs; **Show Audit Log** on most objects | Who added, modified or deleted what and when. Changes made through the CLI are logged with the user ID **CLI Tool**. A few items, such as adapters, alarms and certificates, aren't audited |
| **Authentication logs** | Logs > Authentication Logs | Live authentication attempts for RADIUS, LDAP, Local, SAML and Social, with details and **View Steps** |
| **Security events** | Logs > Security Incidents > Events | Incoming security events that satisfy a trigger (Domain 2) |

Events are generated for every element unless you restrict them to a group. Limiting an event to a group is a classic trick: put a stolen laptop's adapters in a group, enable *Host Connected* only for that group, map it to an alarm, and you are notified when it reappears, with the port in the Host View.

Alarm **trigger rules** in the mapping: **One Event to One Alarm**, **All Events to One Alarm** (one alarm until it clears), **Event Frequency** (N events from the same element within a time) and **Event Lifetime** (no clearing event within a time). The mapping can also notify an administrator group and send the alarm to an external log host.

Retention: events and alarms are kept for the **Event/Alarms Age Time** (default 7 days), then archived and purged by the **Database Archive and Purge** task. Archived records can be imported back into the view.

## Appliance logs and debug (CLI)

The FortiNAC-F processes write their main log to **output.master**. On FortiNAC-OS you don't browse `/bsc/logs` from a root shell; you use the base-context commands:

```text
FNAC-CA1 # diagnose tail -F output.master
FNAC-CA1 # diagnose debug plugin list
FNAC-CA1 # diagnose debug plugin enable <plugin>
FNAC-CA1 # diagnose debug plugin list-debug-enabled
FNAC-CA1 # diagnose debug logger list
FNAC-CA1 # diagnose debug logger set DEBUG <log name>
FNAC-CA1 # diagnose debug logger unset <log name>
```

- `diagnose tail` options: **`-F`** follows the file even when it is rotated/replaced, **`-f`** follows but stops if the file is replaced, **`-k <numKB>`** shows only the last N KB. Tab completion lists the files you can tail; Ctrl-C stops.
- Plugin debug adds detail for one component; the plugin list shows each plugin, its loader and debug status.
- Logger levels, most to least verbose: **TRACE**, **DEBUG**, **INFO**, **WARN**, **ERROR**. `unset` returns the logger to **INHERIT**. The CLI Reference says to set logger levels under Support's advice.
- `diagnose system event [after <date>] [before <date>] [name <name>]` lists events from the CLI.
- `diagnose system bridge-performance debug device enable <ip>` adds L2/VLAN-switching debug for one switch to output.master.
- To hand logs to Support: **Download Logs** from the GUI help menu (choose HA peer or Manager, ZIP/Tar-GZIP/Tar-XZ, optional password), or `sudo grab-log-snapshot` in `execute enter-shell`.

> **Watch out:** `diagnose debug enable`, `diagnose debug flow` and `diagnose sniffer packet` are **FortiOS** commands. On FortiNAC-F the equivalents are plugin/logger debug plus `diagnose tail -F output.master`, and `execute tcpdump`.

## Upstream logging: syslog, SNMP traps and FortiAnalyzer

To send events and alarms off the box:

1. **System > Settings > System Communication > Log Receivers > Add**. Type: **Syslog CSV**, **Syslog CEF** (Common Event Format), **SNMP Trap** or **FortiAnalyzer**. Default port 514 for syslog, 162 for traps; syslog **Facility** default **4** (security/authorization); traps carry a **Security String**.
2. In **Logs > Events & Alarms > Management**, set each event to **External** or **Internal & External**. Only events set this way are forwarded. (*External* alone gives the event a database ID of `-1`, which some log servers reject.)
3. For alarms, enable sending to the external log host in the event-to-alarm mapping.

The CSV syslog message has a fixed field order after the syslog header: log time, **log type** (1 Event, 2 Alarm, 3 Security Alarm), database ID, **event name**, **severity** (0 Normal, 1 Minor, 2 Major, 3 Critical), entity ID, user ID, entity name, entity IP, entity MAC, message. An illustrative message built on that layout (the message text is made up):

```text
<37>Oct 30 09:14:02 : 2026/10/30 09:14:02 EDT,1,48211,Host Connected,0,5521,,LAB-PC07,10.10.10.57,00:09:0F:5A:10:07,Host LAB-PC07 connected
```

`<37>` is facility 4 (security) with severity 5 (notice): 4 × 8 + 5 = 37.

**FortiAnalyzer** receives events, alarms, endpoint data and network infrastructure data over **TCP 514** and has FortiNAC report templates. Requirements: a FortiNAC-F licence key that contains certificates, TCP 514 open between the two, and FortiAnalyzer must recognise the FortiNAC-F serial number as a device (Fortinet's integration guide lists "serial number not recognized by FortiAnalyzer" as the first troubleshooting item).

## Use cases

| Use case | Steps |
|---|---|
| Filters on the hosts page | Host Type = Rogue + Location = `FSW-Access1` → every unknown device on that switch; `![Windows]` in Operating System → everything that isn't Windows |
| Troubleshoot a host connectivity issue | Database? → rogue? → classified? → device modeled and SNMP OK? → traps/polling? → policy details and network events |
| Upstream logging | Log receiver (Syslog CSV/CEF, SNMP trap or FortiAnalyzer) + events set to External/Internal & External + alarm mapping to external host |

## Lab it yourself (optional)

Needs a POC/partner FortiNAC-F; any Linux host running rsyslog can be the log receiver. Reading-only path: rebuild the CSV syslog field order from memory and label each field of the example above.

1. Add the Linux host as a **Syslog CSV** log receiver, then set *Host Connected* and *Admin User Login Success* to **Internal & External**.
2. Log out and back in to the GUI and confirm the syslog line arrives; on FortiNAC-F, `execute tcpdump -i=port1 -c=5 udp port 514` shows it leaving.
3. Pick a test MAC and run `diagnose host list mac=<mac>`, then find the same host with a Host Type filter in the GUI.

## Key takeaways

- Ask: in the database? rogue? classified? Then check the infrastructure, then policy.
- `diagnose host list mac=`, `diagnose network device test-snmp ip=`, `diagnose network mac-notification-stats all`, `execute tcpdump -i=` and `diagnose tail -F output.master` are the core CLI tools.
- Only enabled events are logged; each event is Disabled, Internal, External or Internal & External, optionally per group.
- Network Events is the connection log, with Registered/Rogue and the applied logical network per event.
- Audit logs show CLI changes as user "CLI Tool".
- Log receivers: Syslog CSV, Syslog CEF, SNMP Trap, FortiAnalyzer; events must be set to External or Internal & External to leave the box.
- FortiNAC-F debug is plugin/logger based with output.master, not FortiOS `diagnose debug flow`.
