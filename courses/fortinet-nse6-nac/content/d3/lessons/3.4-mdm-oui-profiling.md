## Three ways to know what a device is

When an unknown MAC address appears on a port or SSID, FortiNAC-F creates a **rogue** host record and has to decide what it is and whether to register it. Domain 3 looks at three sources of identity that work together:

| Source | What it gives FortiNAC-F | Typical use |
|---|---|---|
| **MDM service connector** | The MDM's inventory: device MAC, owner/user, OS, ownership, compliance, passcode, encryption, compromised state | Corporate and BYOD phones, tablets and laptops already enrolled in Intune, Jamf, Workspace ONE … |
| **Vendor OUI database** | The vendor behind the first three bytes of the MAC, an optional alias, role and registration type | Recognising cameras, card readers, game consoles; validating MACs |
| **Device profiling rules** | Classification of rogues by methods (Vendor OUI, DHCP fingerprint, ports, FortiGuard IoT …) and automatic registration | Headless devices without an MDM or agent |

## MDM integration

### What it does

FortiNAC-F polls the MDM server's API (**MDM polling**) and uses the host data to **register devices automatically**. Devices found on the MDM and registered by FortiNAC-F are flagged **Managed by MDM**. That attribute, plus compliance data, can then be used in user/host profiles. If the integration is removed later, the hosts and users it created **stay** in the database.

Supported connectors in 7.6 include AirWatch/Workspace ONE, Citrix Endpoint Management, Fortinet EMS, Google GSuite, Jamf, MaaS360, Microsoft Intune, MobileIron and ServiceNow CMDB, plus OT connectors such as Nozomi, Claroty and Armis. **Proxy communication to the MDM is not supported.**

### Configuring a connector

Go to **Network > Service Connectors > Create New** and choose the vendor. Fields vary by vendor (Intune uses tenant ID, application ID and a secret or certificate; Jamf uses a client ID and secret; AirWatch uses an API key as the **Identifier** plus a user ID). The behaviour options are common:

| Option | Effect | Default/notes |
|---|---|---|
| **Enable On Demand Registration** | When an **unknown host reaches the captive portal**, FortiNAC-F queries the MDM for it and registers it if found | Without it, the host waits for the next poll |
| **Enable Automatic Registration Polling** + interval | Poll the whole MDM inventory; every device returned is **registered** and marked managed by MDM, existing rogue record or not; existing records are updated | No filtering of which devices are processed. Each poll costs one query per 100 entries plus one per device; Fortinet suggests **1 day** if MDM notifications are configured |
| **Revalidate Health Status On Connect** | Query the MDM for compliance each time the host connects | **Disabled by default**; can overload the MDM. Daily polling also refreshes health status |
| **Remove Hosts Deleted from MDM Server** | Delete hosts from FortiNAC-F when they are removed or disabled in the MDM | Needed for the MDM Host Destroyed event |
| **Update Applications** / Enable Application Updating | Pull application inventory | **Disabled by default**; heavy |
| **Update Hosts Role** | Set the host role from the MDM **Ownership** value, only for hosts with role **NAC-Default** or no role | F 7.2.9+, 7.4.2+, **7.6.3+**; not on every connector |

Right-click a connector to **Test Connection**, **Poll** now, or edit it.

> **Exam tip:** On Demand Registration is triggered by the **captive portal**. A device that never reaches the portal (because it is isolated to a network without portal redirection, or never opens a browser) is registered only by the scheduled poll.

### How MDM hosts are registered

* If the MDM's user matches a FortiNAC-F user, the host is **registered to that user**. If not, it's registered **as a device**, role **NAC-Default**.
* AirWatch/Workspace ONE hosts get roles such as **Employee Owned**, **Corporate - Shared** or **Corporate - Dedicated** (NAC-Default if undefined). These roles are usable in user/host profiles but aren't added to FortiNAC-F's role lists. Jamf hosts get **NAC-Default**.
* User/host profile attributes from MDM: **Managed by MDM** (all vendors), **Compliant**, **Passcode Enabled**, **Data Encryption** and **Compromised** (vendor-dependent). F 7.6.7 also adds a service connector column and profile criterion, so you can tell which connector manages a host.

A network access policy then places the device: for example iOS devices managed by MDM and compliant go to logical network `Corp`, while non-compliant ones go to `Contractor`.

### Devices without the MDM agent

To push unenrolled phones to enrol, enable **MDM Registration** in the portal's Global settings. Every browser with a mobile user agent is then sent to the **MDM Registration** page, whose content should link to the MDM agent download. Add the download sites to **Allowed Domains** (Network > Settings > Control > Allowed Domains), because isolated hosts can only reach listed domains. Wildcards such as `*` aren't accepted, but a parent domain covers its subdomains.

### MDM events

**MDM Host Created**, **MDM Host Destroyed**, **MDM Poll Success**, **MDM Poll Failure**, **MDM Host Compliance Passed** and **MDM Host Compliance Failed**. Map them to alarms like any other event: email the mobile team on MDM Poll Failure, or mark a host At Risk on MDM Host Compliance Failed.

### Where to configure it with FortiNAC-F Manager

Configure the connector on the **Manager** when all CAs need the MDM data (the Manager polls and copies records to the CAs: one point of contact, fewer queries). Configure it on **individual CAs** when only some need it (each CA polls separately).

## Vendor OUI tables

**System > Settings > Identification > Vendor OUIs** holds the IEEE OUI database plus your own entries. The **AutoDef Synchronization** scheduled task keeps it current. Adding or removing an entry raises **Vendor OUI Added/Removed** events.

What the OUI table does:

* **Validates MACs.** A MAC whose OUI isn't in the database is treated as an **invalid physical address**, so keeping the database current prevents errors with new hardware. The Intune connector guide states that devices whose MAC OUI FortiNAC-F doesn't recognise are **skipped** during the MDM import and counted as invalid devices.
* **Labels devices.** The **Vendor Alias** (e.g. `IP Camera`) is shown as the host name in the Hosts view, so you can filter rogue cameras or consoles by alias.
* **Pre-sets registration.** **Role** applies to devices registered **manually through the portal** (device profiler roles take precedence). **Registration Type** comes from AutoDef updates (camera, card reader, gaming device …), and **Registration Type Override** replaces it.

| Field | Example |
|---|---|
| Vendor OUI | `00:09:0F` (format `##:##:##`) |
| Vendor Name | Fortinet |
| Vendor Alias | Lab Appliance |
| Role | NAC-Default |
| Registration Type Override | Manual or a device type |

The documented manual workflow for game consoles and similar devices: add the OUI with an alias and the right Registration Type Override, let the device connect (rogue), then in Users & Hosts > Hosts right-click and choose **Register As Device**.

F 7.6.7 adds **regular-expression vendor codes** so randomized (locally administered) MACs, whose first three bytes aren't a real OUI, can still be matched, with their own aging policy.

## Device profiling rules in the MDM picture

Device profiling rules (Users & Hosts > Device Profiling Rules, covered fully in 4.2) classify **rogues only**. Domain 3 cares about how they meet MDM and OUIs:

* A host already **registered by the MDM** is not a rogue, so device profiler doesn't evaluate it. The MDM connector and profiling rules complement each other: MDM for enrolled devices, profiling for everything else.
* The **Vendor OUI** method matches on **Vendor Code**, **Vendor Name** or **Vendor Alias** (wildcard `*` at the start and end allowed) or **Device Type**. Rules are checked in order, and within one rule **every selected method must match**. Vendor OUI alone is weak (a camera vendor also sells NVRs), so pair it with DHCP fingerprinting, TCP ports or FortiGuard IoT.
* Device profiler **does not check whether a MAC is valid**: a host that matches a rule is registered even if its OUI is missing from the database.
* After adding OUIs or rules, re-evaluate the current rogues with **Run** in Device Profiling Rules. Only online, unregistered hosts are evaluated.

## Use case: corporate iPads in Intune, cameras by OUI

1. Intune connector on FNAC-M with Automatic Registration Polling every 1 day, On Demand Registration on, and Remove Hosts Deleted from MDM Server on.
2. User/host profile "Corp-iPad": Host **Managed by MDM** = Yes, **Compliant** = Yes, OS iOS. Network access policy → logical network `Corp`.
3. A second profile with Managed by MDM = Yes and Compliant = No, used by a network access policy ranked below the first → logical network `Contractor`, plus an alarm on **MDM Host Compliance Failed**.
4. Vendor OUI entries for the camera vendor with alias `IP Camera`. A device profiling rule with Vendor OUI (alias `IP Camera`) and TCP 554 registers matches as devices in group `IP Cameras` → logical network `Cameras`.

## Lab it yourself (optional)

Needs a POC/partner FortiNAC-F. An Intune developer tenant or a Jamf trial can act as the MDM. Reading-only path: compare the connector fields above with the Network > Service Connectors screenshots in the MDM/OT integration guide.

1. Create the connector, **Test Connection**, then **Poll** and watch for MDM Poll Success and MDM Host Created events.
2. Filter Hosts on Managed by MDM and check the roles assigned.
3. Add a Vendor OUI alias for a lab device's OUI, reconnect it and see the alias as its host name.

## Key takeaways

* MDM connectors live in **Network > Service Connectors**. Polling registers MDM devices as **Managed by MDM**; proxy isn't supported; records stay if the connector is deleted.
* **On Demand Registration** fires at the **captive portal**. **Revalidate Health Status On Connect** and **Update Applications** are off by default because they load the MDM.
* MDM attributes (Managed by MDM, Compliant, Passcode, Encryption, Compromised) and MDM roles drive **user/host profiles**. An unmatched user means registration as a device with NAC-Default.
* The **Vendor OUI** table validates MACs, supplies aliases (shown as host name), roles for portal registration and registration types. AutoDef Synchronization updates it; F 7.6.7 adds regex OUIs for randomized MACs.
* Device profiling rules evaluate **rogues only**, require **all** selected methods to match, and don't validate MACs. Use **Run** to re-evaluate rogues after changes.
* Put the MDM connector on **FortiNAC-M** when every CA needs the data, on individual CAs otherwise.
