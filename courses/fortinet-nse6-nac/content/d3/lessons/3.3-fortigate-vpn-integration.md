## The problem VPN integration solves

On a wired or wireless network, FortiNAC-F enforces at the switch or controller: it moves the port to a VLAN or answers RADIUS. A remote-access VPN user has no switch port. Their "port" is the tunnel, and the only enforcement point is the **FortiGate**. FortiNAC-F's answer is to **restrict every new VPN session at the FortiGate by default**, check the device (agent, registration, compliance), and then **lift the restriction by telling the FortiGate who the session belongs to**, using FSSO groups or tags.

## How a managed VPN session works

1. The user connects to the FortiGate VPN (IPsec, or SSL VPN tunnel mode where the FortiOS build still has it) and authenticates as usual.
2. The FortiGate sends FortiNAC-F a **syslog** message about the new session (user, assigned IP). FortiNAC-F also learns session data through the **FortiGate API**.
3. The client's address comes from a **VPN pool that FortiNAC-F manages**. FortiGate policies allow that pool to reach **only the FortiNAC-F VPN interface**. The VPN client gets FortiNAC-F's VPN interface as a DNS server, and FortiNAC-F answers DNS so that web requests land on the **VPN captive portal**.
4. Without an agent, the portal offers the configured agent (Persistent, Dissolvable or Mobile). The session stays restricted until an agent runs.
5. The agent reports the device's IP and MAC. FortiNAC-F **correlates** them with the FortiGate's session data, marks the host online, evaluates **endpoint compliance**, and finds the matching **network access policy**.
6. The policy's **logical network** maps (on the FortiGate model) to **firewall tags or groups**. FortiNAC-F sends them through **FSSO**: a logon event with IP, user and group. FortiGate policies that use those FSSO groups now match the session.
7. On disconnect the FortiGate sends another syslog message. FortiNAC-F ends the connection and sends a logoff, the tags disappear, and the restrictive policies apply again.

So FortiNAC-F needs **three channels** with the FortiGate: syslog (FortiGate → FortiNAC-F), SSH/API/SNMP for modeling (FortiNAC-F → FortiGate) and FSSO or Security Fabric for tags (FortiNAC-F → FortiGate).

> **Exam tip:** FortiNAC-F never terminates the VPN and never pushes a VLAN for VPN users. Enforcement is the FortiGate firewall policy matching an FSSO group/tag that FortiNAC-F supplies.

## FortiGate side

### Accounts, API and SNMP

* **SNMP** (System > SNMP) with FortiNAC-F's port1 address as a host that can query and receive traps. If the FortiGate is an HA cluster, enable the HA cluster status and member up/down events.
* Interface **administrative access**: HTTPS, HTTP, SNMP and SSH on the interface FortiNAC-F talks to.
* An **administrator account** for SSH/API. **Read-only** to all VDOMs is enough for visibility; **read/write** to all VDOMs is needed for control.
* A **REST API admin** and its API key. The VPN guide makes this **required from FortiOS 7.4.8 and 7.6.4**. Paste the key into the FortiGate model's **FortiGate API Token** field and set `set rest-api-key-url-query enable` under `config system global` so the key can be sent as a URL parameter.
* **Address objects** for the VPN pool(s), e.g. `FNAC_IPsec_ADDR` = 10.200.80.100–10.200.80.200.

### Syslog to FortiNAC-F

FortiNAC-F listens for syslog on UDP 514. The `source-ip` must be the address FortiNAC-F uses to model the FortiGate, or the messages are not tied to the device. Send only the VPN log IDs FortiNAC-F needs:

```text
FGT-HQ # config log syslogd setting
FGT-HQ (setting) # set status enable
FGT-HQ (setting) # set server "10.10.10.20"
FGT-HQ (setting) # set source-ip "10.10.10.1"
FGT-HQ (setting) # set format csv
FGT-HQ (setting) # end
FGT-HQ # config log syslogd filter
FGT-HQ (filter) # set forward-traffic disable
FGT-HQ (filter) # set local-traffic disable
FGT-HQ (filter) # set multicast-traffic disable
FGT-HQ (filter) # set sniffer-traffic disable
FGT-HQ (filter) # set ztna-traffic disable
FGT-HQ (filter) # set anomaly disable
FGT-HQ (filter) # set voip disable
FGT-HQ (filter) # config free-style
FGT-HQ (free-style) # edit 1
FGT-HQ (1) # set category event
FGT-HQ (1) # set filter "(logid 0101039947 0101039948 0101037139)"
FGT-HQ (1) # next
FGT-HQ (free-style) # end
FGT-HQ (filter) # end
FGT-HQ # config log eventfilter
FGT-HQ (eventfilter) # set event enable
FGT-HQ (eventfilter) # set vpn enable
FGT-HQ (eventfilter) # end
```

| Log ID | Used for |
|---|---|
| 0101039947, 0101039948 | SSL VPN tunnel up/down |
| 0101037129, 0101037134 | IPsec (recommended for FortiNAC-F 7.4 and earlier; supported on all) |
| **0101037139** | IPsec, **recommended for FortiNAC-F 7.6+** |

The guide also warns against flooding FortiNAC-F with unneeded logs, which can delay or drop message processing.

### The tunnel: DNS and domain

The VPN guide asks for **DNS server 1 = production DNS** and **DNS server 2 = FortiNAC-F VPN interface**, plus a **DNS suffix (domain)** that matches the domain configured in FortiNAC-F's VPN scope. Agents locate FortiNAC-F with a DNS SRV lookup, and FortiNAC-F only answers SRV queries from that domain. All VPN scopes must use the same domain, and `.local` should be avoided because of macOS/Linux problems. For IPsec dial-up:

```text
FGT-HQ # config vpn ipsec phase1-interface
FGT-HQ (phase1-interface) # edit "RA-IPsec"
FGT-HQ (RA-IPsec) # set mode-cfg enable
FGT-HQ (RA-IPsec) # set assign-ip-from name
FGT-HQ (RA-IPsec) # set ipv4-name "FNAC_IPsec_ADDR"
FGT-HQ (RA-IPsec) # set ipv4-dns-server1 10.10.10.53
FGT-HQ (RA-IPsec) # set ipv4-dns-server2 10.10.50.22
FGT-HQ (RA-IPsec) # set domain "corp.example.com"
FGT-HQ (RA-IPsec) # end
```

DHCP relay for VPN addressing is not supported; the FortiGate assigns from the pool, and the same range is defined in FortiNAC-F.

> **Watch out:** **FortiOS 7.6.3 removed SSL VPN tunnel mode.** On a FortiOS 7.6.3+ headend, FortiNAC-F VPN management is an IPsec story. Older material (and the SSL sections still in the guide) apply to FortiOS builds that still have tunnel-mode SSL VPN. Applying SSL VPN settings also disconnects every SSL VPN user, so on those builds do it in a maintenance window.

### Firewall policies

Two sets, ranked in this order:

1. **Authorized**: source = VPN pool **+ the FSSO group/tag FortiNAC-F sends** (e.g. `VPN_AUTH`). Allow the production destinations. Also **deny DNS (or everything) to the FortiNAC-F VPN interface**, so authorized clients resolve through production DNS instead of the portal.
2. **Unauthorized (default)**: source = VPN pool. Allow **only** the FortiNAC-F VPN interface (DNS, portal, agent) and deny everything else.

A session that does not carry the FSSO group falls through to the restrictive policies.

## FortiNAC-F side

| Step | Where | Notes |
|---|---|---|
| VPN interface and scope | System > **Configuration Wizard** > Virtual Private Network | Interface IP on the isolation port; scope with gateway, mask, **lease pool = FortiGate VPN pool**, **Domain = FortiGate DNS suffix**. Scope labels can't start with `REG_`, `REM_`, `AUTH_`, `DE_`, `ISOL_`, `VPN_` or `HUB_`. In HA, repeat on the secondary |
| Accept syslog | CLI, port1 | `set allowaccess ... syslog`. FortiNAC-OS does its own policy-based routing for the VPN sub-interface; legacy CentOS appliances needed `setupAdvancedRoute` |
| Model the FortiGate | Network > Inventory | IP, SNMP, CLI admin credentials, API token; **Validate Credentials**; **Resync Interfaces**; the VDOMs appear under **Virtualized Devices** |
| VPN interface connection state | Ports tab of the model | The VPN interface must be **Device** or **Multiple Hosts**, never **Uplink**. Raise **System Defined Uplink Count** (Network > Settings > Network Device) above the maximum concurrent VPN users, or the interface auto-converts to Uplink and every client goes offline. Set real uplinks to **Always Uplink** |
| Address objects/groups | System > Settings > System Communication > **Addresses** | Same ranges as the FortiGate pool objects |
| Model Configuration of the VDOM | Inventory > FortiGate > Virtualized Devices > VDOM > Model Configuration | **VPN Addresses** = the address group; **Source IP** for the connector if the VDOM doesn't own the modeled IP; **Logical Network → Firewall Tags** and/or **Send Groups to Firewall** |
| Captive portal | Portal > Portal Configuration, **VPN** context | Index (redirect), Download, Login (in-line), Success pages; use the default portal for VPN |
| Persistent Agent | System > Settings > Persistent Agent > Properties | If **Require Connected Adapter** is on, add the VPN pool to **Allowed IP Subnets** (FortiNAC-F can't see VPN adapters as online) |
| Endpoint compliance (optional) | Policy & Objects | User/host profile with Host **VPN Client: Yes** for the PA |
| Network access policy | Policy & Objects | Profile with Host **VPN Client: Yes** (+ Security Status Safe, Access Enabled) → configuration whose **logical network** maps to the tag |
| Tag delivery | **FSSO** or **Security Fabric** | See below |

### Getting the tags to the FortiGate

**Connector-based FSSO.** On FortiNAC-F, System > Settings > System Communication > **Fortinet FSSO Settings**: enable FSSO communication, port **8000** by default, and a password. Add `fsso` to port1 `allowaccess`. On the FortiGate, the FortiNAC-F guide creates an **External Connector > FSSO Agent on Windows AD** (FortiOS 7.2.4+) pointing at FortiNAC-F port1 with the same password. Whatever the GUI tile, the connector is stored as a `config user fsso` entry. The FortiOS 7.6 CLI Reference lists `server`, `port` (default **8000**), `password`, `source-ip` and a `type` option of `default` or `fortinac`:

```text
FGT-HQ # config user fsso
FGT-HQ (fsso) # edit "FortiNAC"
FGT-HQ (FortiNAC) # set server "10.10.10.20"
FGT-HQ (FortiNAC) # set password <FSSO password set on FortiNAC-F>
FGT-HQ (FortiNAC) # set source-ip 10.10.10.1
FGT-HQ (FortiNAC) # end
```

The connector's `source-ip` must match the **Source IP** in the FortiNAC-F VDOM model configuration (the guide sets it from the CLI when the GUI doesn't offer the field). After it connects, the FortiGate imports FortiNAC-F's tags and groups, which you place in FSSO user groups for the policies.

**Security Fabric.** On FortiNAC-F, Network > Service Connectors > Create New > **Security Fabric Connection** with the **root FortiGate's IP** and port **8013**, then **Authorize** FortiNAC-F on the root FortiGate. Fortinet warns against combining connector-based FSSO and dynamic address tags for the same FortiGates.

Constraints from the guides:

* A FortiGate keeps only **one FSSO agent's** information per endpoint IP. Block other collector agents from reporting the VPN pool, or they overwrite FortiNAC-F's entries.
* If the collector (FortiNAC-F) is disconnected for **300 seconds**, the FortiGate drops its SSO logins. The FortiNAC-F guide calls this 5-minute window hard-set; the FortiOS 7.6 CLI Reference shows a `logon-timeout` on `config user fsso` with a default of 5 minutes.
* A remote client on a FortiNAC-managed VPN can't also be connected to a local network managed by FortiNAC-F in the same management domain.
* In 1+1 HA where the two VPN interfaces sit in different subnets, the FortiGate's second DNS entry must be changed to the secondary's VPN interface after failover.

F 7.6.7 adds a selector-based alternative: **Network > Configuration > SSO/VPN Configuration** objects (SSO and VPN address groups plus logical-network-to-tag mappings, including remote groups) assigned through an **SSO/VPN Configuration Selector**.

## Verifying and troubleshooting

On the FortiGate, `diagnose debug authd fsso list` shows the FSSO logons and the groups FortiNAC-F supplied:

```text
FGT-HQ # diagnose debug authd fsso list
----FSSO logons----
IP: 10.200.80.104  User: JSMITH  Groups: VPN_AUTH  Workstation:  MemberOf: VPN_AUTH
Total number of logons listed: 1, filtered: 0
----end of FSSO logons----
```

On FortiNAC-F, turn on the relevant plugins and follow the log:

```text
FNAC-CA1 # diagnose debug plugin enable FortinetVPN
FNAC-CA1 # diagnose debug plugin enable RemoteAccess
FNAC-CA1 # diagnose debug plugin enable SSOManager
FNAC-CA1 # diagnose tail -F output.master
```

`diagnose network remote-access list all` lists the remote-host probe objects FortiNAC-F holds for VPN sessions, and `diagnose network sso session-list ip=<FortiGate IP>` shows SSO session information for the device. Turn debug plugins off with `diagnose debug plugin disable <name>` when finished; they also clear on a service restart.

Checklist when a VPN user stays restricted: Did syslog arrive from the modeled source IP with the right log IDs? Is the pool inside FortiNAC-F's VPN scope and address group? Did an agent run? Does the host match a policy with **VPN Client: Yes**? Is the logical network mapped to a tag on that **VDOM's** model configuration? Is the FSSO connector up, and does the FortiGate policy use the matching group?

## Key takeaways

* VPN sessions start **restricted at the FortiGate**. FortiNAC-F lifts the restriction by sending an **FSSO group/tag** once the host is identified (agent) and compliant.
* FortiGate → FortiNAC-F syslog (UDP 514, `source-ip` = modeled IP, log IDs 0101039947/48 SSL, 0101037129/34 and **0101037139** IPsec for F 7.6+). API key required from FortiOS 7.4.8/7.6.4.
* Tunnel DNS: server 1 production, **server 2 FortiNAC-F VPN interface**, and a **domain matching the FortiNAC-F VPN scope**. FortiOS 7.6.3 removed SSL VPN tunnel mode.
* FortiNAC-F: VPN scope in the Config Wizard, `syslog` and `fsso` in `allowaccess`, VPN interface never **Uplink** (raise **System Defined Uplink Count**), VDOM model configuration (VPN Addresses, Source IP, logical network → tags).
* Policies match **Host VPN Client: Yes**. FSSO uses port **8000** (`config user fsso` with a matching `source-ip`); the Security Fabric connection uses port **8013** to the root FortiGate.
* Verify with `diagnose debug authd fsso list` on FortiGate and the `FortinetVPN`, `RemoteAccess` and `SSOManager` plugins on FortiNAC-F.
