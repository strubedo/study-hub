## From event to alarm

Every significant thing FortiNAC-F notices (a trap, a parsed syslog line, a failed poll, a rogue, an MDM poll) is an **event**. Events are written to the event log (Logs > Events) if logging is enabled for them. An event on its own notifies nobody. To get attention, or an automatic reaction, the event must be **mapped to an alarm**.

| Object | Where | Purpose |
|---|---|---|
| Event management | Logs > Events & Alarms > **Management** | Turn each event's logging on or off: **Internal**, **External**, **Internal & External**, or Disable Logging; optionally limit an event to one group |
| Alarm mapping | Logs > Events & Alarms > **Mappings** | Trigger event → alarm, severity, clear event, who to notify, trigger rule, optional action |
| Event thresholds | Management view > **Event Thresholds** | Self-monitoring events (licence usage, disk, memory, process threads) |

Some events are mapped by default. A mapping can be disabled temporarily without deleting it; Fortinet's own examples are suppressing Device Contact Lost/Established during switch maintenance, or Rogue User Detected during an open day.

## Building an alarm mapping

Add a mapping in Logs > Events & Alarms > Mappings. The fields fall into five groups.

### 1. Alarm definition

* **Trigger Event**: the event that creates the alarm (the alarm name fills in automatically).
* **Severity**: Critical, Minor, Warning or Informational.
* **Clear on Event**: an event that clears the alarm automatically. If it's left unchecked (the default), someone must clear the alarm by hand.
* **Send Alarm to External Log Hosts**: forward the alarm to the configured log receivers. Default off.
* **Send Alarm to Custom Script**: run a script from `/home/cm/scripts`. The field is only available if a script exists there.

### 2. Apply To

**All** elements, one **Group**, or a **Specific** element. Scope a "Device Contact Lost" alarm to the core switches group and leave the access switches alone, for example.

### 3. Notify Users: the administrative group

This is the "administrative group for alarm notification" in the exam topics. Notification goes to an **administrator group**, never to individual admins:

| Option | Effect | Prerequisite |
|---|---|---|
| **Notify** | Members of the selected admin group are notified when the alarm occurs | Admin group exists |
| **Send Email** | Members get an email | Each admin has an **email address** in their account; an **email server** is configured (System > Settings > System Communication > Email Settings, also under Network > Service Connectors > Email Server) |
| **Send SMS** | Members get an SMS | Each admin has a **Mobile Number** and **Mobile Provider** |

FortiNAC-F has a system administrator group called **All Management**. It initially holds `admin` and `root`, new administrators are added to it automatically, and it is the **default group for alarm-triggered email**. To send network alarms only to the network team, create an admin group (Users & Hosts > Administrators, select the admins, Options > **Add Admin Users To Groups**, or **Create Group** there) and pick it in the mapping.

> **Watch out:** Removing an admin from the email list means removing them from the group the mapping uses. If the mapping still points at All Management and the admin is still in All Management, the email keeps coming.

Security Incidents rules use the same idea separately: a rule has **Send Email when Rule is Matched** and **Send Email when Action is Taken**, each with its own admin group drop-down. A security rule's email goes to the group named in the rule, not to the alarm mapping's group.

### 4. Trigger rule

| Trigger rule | When an alarm is created |
|---|---|
| **One Event to One Alarm** | Every occurrence creates its own alarm |
| **All Events to One Alarm** | The first occurrence creates the alarm; later occurrences don't, while that alarm is still active. After it clears, the next event creates a new one |
| **Event Frequency** | *N* occurrences from the **same element** within a sliding time window |
| **Event Lifetime** | The event happens and its clearing event does **not** follow within the set time |

Event Frequency counts per element and uses a sliding window. With "3 times in 10 minutes", host A connecting at minutes 1, 8 and 12 does **not** alarm (no three in any 10-minute span), but adding a connection at minute 14 **does** (8, 12, 14). Two connections each from hosts A and B never alarm, because the count is per host.

### 5. Action

Enabling **Action** runs a built-in reaction when the alarm asserts. Most actions have a primary task and an optional **secondary task** after a delay (minutes, hours or days) that reverses it:

| Action | What it does |
|---|---|
| Host Access Action | Disable the host, re-enable after the delay |
| Host Role | Change the host's role, revert later (a directory sync can also revert a directory-based role) |
| Host Security Action | Mark the host **At Risk**, then Safe |
| Port State Action | Disable the switch port, re-enable later |
| Command Line Script | Run a script from `/home/cm/scripts` with the host's IP and MAC as arguments |
| Email User / SMS User | Message the user associated with the host (`%host%` and `%event%` insert details) |
| Send Message to Desktop | Pop-up through the Persistent Agent or Mobile Agent |

This is FortiNAC-F's basic automated response: a third-party device sends a trap or syslog line, FortiNAC-F turns it into an event, the mapping raises an alarm, emails the security admins and disables the host for an hour. For correlation across vendors, threat IDs and user/host profiles, use Security Incidents rules instead (2.1).

## FortiNAC-F syslog messages: sending events out

The other half of "syslog for automated response" is **outbound**: FortiNAC-F forwards its events and alarms to a SIEM, FortiAnalyzer or an SNMP manager, which can then correlate them and act (for example a FortiSIEM rule or a FortiAnalyzer handler).

### Log receivers

**System > Settings > System Communication > Log Receivers** > Add:

| Type | Default port | Extra field |
|---|---|---|
| Syslog CSV | 514 | **Facility** (default **4**, security/authorization) |
| Syslog Command Event Format (CEF) | 514 | Facility |
| SNMP Trap | 162 | **Security String** (community sent with the trap) |
| FortiAnalyzer | 514 (TCP) | Security String/Serial Number = FortiAnalyzer serial number |

Adding a receiver is only half the job. An event goes out only if its logging option is **External** or **Internal & External** (Logs > Events & Alarms > Management > Options), and an alarm goes out only if its mapping has **Send Alarm to External Log Hosts** checked.

> **Exam tip:** "Receiver added, nothing arrives at the SIEM" is almost always event logging still set to **Internal**. Each event has its own logging option.

### Reading a FortiNAC-F CSV syslog line

```text
<37>Oct 30 09:14:02 : 2026/10/30 09:14:02 EDT,2,58213,Device Contact Lost,2,1127,,Cisco-Access1,10.10.20.11,,Contact lost with device Cisco-Access1
```

| Column | Value | Meaning |
|---|---|---|
| 1 | `<37>` | PRI: facility 4 × 8 + severity 5 (notice) |
| 3 | timestamp | Log time |
| 4 | `2` | Log type: **1 Event, 2 Alarm, 3 Security Alarm** |
| 5 | `58213` | Database ID |
| 6 | `Device Contact Lost` | Event/alarm name |
| 7 | `2` | Severity: **0 Normal, 1 Minor, 2 Major, 3 Critical** |
| 8 | `1127` | Entity ID |
| 9 | empty | User ID |
| 10–12 | `Cisco-Access1`, `10.10.20.11`, empty | Entity name, IP, MAC |
| 13 | text | Message |

The CEF version uses `CEF:0|Fortinet|NAC Control Server|<version>|<signature ID>|<name>|<severity>|` followed by extensions such as `rt=`, `cat=` and `msg=`. The SNMP trap version uses varbinds under `1.3.6.1.4.1.16856.1.1`.

### FortiAnalyzer

FortiAnalyzer gets events, alarms, endpoint and network-infrastructure data from FortiNAC-F over **TCP 514** (Fortinet's OFTP-based logging) and builds its FortiNAC report templates from them. Configure a **FortiAnalyzer** log receiver with the FortiAnalyzer serial number, then add the FortiNAC-F appliance in FortiAnalyzer's Device Manager (FortiNAC ADOM) using its port1 IP and serial number. F 7.6.7 sends more endpoint data and adds the Hostname field to syslog sent to FortiAnalyzer.

## Lab it yourself (optional)

Needs a POC/partner FortiNAC-F; any Linux box can be the syslog receiver.

1. Create an admin group `NetOps-Alerts`, put one admin with an email address in it, configure Email Settings and send a test email.
2. Map **Device Contact Lost** to an alarm with Apply To = a group holding one lab switch, Notify + Send Email to `NetOps-Alerts`, Clear on Event = Device Contact Established.
3. Add a Syslog CSV log receiver pointing at the Linux box (`nc -klu 514` or rsyslog), set the event's logging to Internal & External, and tick Send Alarm to External Log Hosts.
4. Unplug the switch's management link and read the CSV line: confirm log type `1` for the event and `2` for the alarm.

## Key takeaways

* Events are logged; only **alarm mappings** notify or act. Mappings live in Logs > Events & Alarms > **Mappings**.
* Notification targets an **administrator group**. **All Management** is the default email group; admins need an email address (or mobile number and provider for SMS) and FortiNAC-F needs an email server.
* Trigger rules: **One Event to One Alarm**, **All Events to One Alarm**, **Event Frequency** (per element, sliding window), **Event Lifetime** (no clearing event in time).
* Actions (host disable, role change, At Risk, port disable, script, messages) can reverse themselves through a delayed **secondary task**.
* Outbound logging needs a **log receiver** (Syslog CSV/CEF 514, SNMP Trap 162, FortiAnalyzer TCP 514) **and** per-event **External** logging or **Send Alarm to External Log Hosts**.
* In the CSV syslog format, column 4 is the log type (1 Event, 2 Alarm, 3 Security Alarm) and column 7 the severity (0–3).
