## What FortiNAC-F Manager is for

A single FortiNAC-F CA (Control and Application server) handles one site or one capacity block. Large or multi-site estates run several CAs: one per campus, one for wireless and one for wired, or one per region. Each CA has its own database, its own modeled switches and its own hosts. **FortiNAC-F Manager** (FortiNAC-M, models such as FNC-MX-VM and FNC-M-550F) sits above them as the central point for policy, licensing and search. It does **not** enforce anything itself; switches and APs stay modeled on the CA that controls them.

| | FortiNAC-F CA | FortiNAC-F Manager |
|---|---|---|
| Enforces access (VLANs, RADIUS, CLI, FSSO) | Yes | No |
| Models infrastructure devices | Yes | No |
| Owns global objects (profiles, policies' building blocks, rules) | Receives them read-only | Creates and pushes them |
| Licence pool | Draws from the pool | Holds the maximum, counts usage |
| Typical admin task | Troubleshoot a port, a host | Change policy once for every site, find a host anywhere |

### Key features

* **Global synchronization** of shared objects to every managed CA.
* **Global license management**: one concurrent-licence pool across CAs.
* **Global Find** (the **Locate** view): search for hosts, users and devices across selected CAs by MAC, IP, name, user ID, role and more.
* **Seamless registration**: a user registers once and the record follows them to other managed sites.
* **Global version control** and **global scan management** (endpoint compliance scans built once and copied).
* An **Import** button on global views pulls an object that already exists on a CA up to the Manager, where it becomes global.
* New in 7.6: **Cluster Management** of Managers, **CA Management**, custom health checks for CAs and management of **N+1 failover groups**.

## Prerequisites and connecting a CA

The Manager guide lists the requirements:

* Manager(s) and every managed CA run the **same FortiNAC-F version**. Otherwise functions such as server synchronization are not supported.
* Members of the same Manager cluster, 1+1 HA pair or N+1 failover group must match **version, model and hypervisor** (two FNC-CAX-VM on AWS: yes; one on AWS and one on KVM: no).
* If a proxy is configured, the port1 addresses of the Manager and CAs go in the proxy exclusions.
* Inter-server ports must be open between the **port1** interfaces: TCP 8443 for management, and the inter-server channel TCP 1050 and 5555 (CORBA) plus 9443 and 18090 (gRPC).

On FortiNAC-OS that channel is the `nac-ipc` keyword. Both the Manager and every CA need it in port1's `allowaccess`, along with `ssh`:

```text
FNAC-M # config system interface
FNAC-M (interface) # edit port1
FNAC-M (port1) # set allowaccess https-adminui ssh nac-ipc
FNAC-M (port1) # end
```

Then each appliance gets an **allowed serial numbers** list, set from the shell with `globaloptiontool`. On the Manager, list the serials of the Manager(s) **and** all CAs. On each CA, list the Manager serial(s). Restart services afterwards:

```text
FNAC-M # execute enter-shell
> globaloptiontool -name security.allowedserialnumbers -setRaw "FNVM-MXXXXXX01,FNVM-CAXXXXX11,FNVM-CAXXXXX12"
> shutdownNAC
> startupNAC
```

A "There is no known option with name" warning on first use is normal. In a 1+1 pair only the primary needs the command, because database replication copies it. Finally, add the CA by IP address in the Manager dashboard's **CA Management** widget.

> **Exam tip:** A Manager that can't add a CA is usually missing `nac-ipc` on one side, has an incomplete allowed-serials list on one side, or is talking to a CA on a different build.

## What is synchronized, and how

### Global objects

These objects are **shared globally** between the Manager and its CAs:

* Admin Profiles
* Guest Templates
* Device Profiling Rules
* Device Types
* Groups
* Roles
* User/Host Profiles
* Endpoint Compliance Policies, Configurations and Scans
* Security Actions used by Endpoint Compliance configurations

**Logical networks** can also be created on the Manager and pushed to the managed CAs. Each CA then maps the logical network to its own device access values (VLAN ID, firewall tag and so on), which is how one policy design works on sites with different VLAN numbering.

Rules for global objects:

* The **Manager owns them**. On a CA, global information is **read-only**. Create or edit it on the Manager.
* With **Global Object Synchronization** enabled (System > Settings > Network Control Manager > Server Synchronization), the Manager synchronizes every managed CA on a **10-minute** interval. Anything on a CA that is older than the Manager's copy is overwritten.
* **Synchronize Now** (or the CA Management widget's Synchronize) pushes immediately and **overwrites all globally shared information** on the CA.
* Groups changed through the REST API are synchronized immediately.

> **Watch out:** The Key Features page says automatic synchronization happens "once per minute", while the Server Synchronization page says global objects synchronize every 10 minutes. Use the 10-minute figure, which is the documented setting.

### Host and user records

Host records are **not** global objects; they belong to the CA where the host connects. How they move changed during 7.6:

| Build | Behaviour |
|---|---|
| F 7.6.0–7.6.1 | The Manager periodically collects host records from the CAs. When a host connects to a CA that doesn't know it, that CA asks the Manager and receives a copy. Other CAs' copies are not updated |
| F 7.6.2 | Changes to a host record are synchronized among all CAs that **already hold** that host |
| **F 7.6.3 and later** | **Automatic host and user propagation**: the Manager runs synchronization every **5 minutes**, keyed on **MAC** for hosts and **user ID** for users; all attributes of the record are synchronized. Controlled by **On Demand Host Propagation** (default enabled) |

For a host registered to a user to propagate, the user record's **Propagate Hosts** option must be enabled (it is by default). Endpoint compliance results are synchronized separately and may lag behind the host record. An older page in the Manager guide still says host records are "never synchronized" after the first copy; for 7.6.3+ the Server Synchronization page is the current behaviour. Name the build if a question depends on it.

### Guests

Guest accounts are **not** replicated. When a guest tries to register at a CA that doesn't hold the account, the Manager searches the other CAs and **copies** the account (plus the guest's hosts, if Propagate Hosts is set). Consequences: no central list of guests, reports differ between CAs, deleting an account on one CA doesn't delete the copies, and **if the Manager is down, guests can't register on a CA that doesn't already hold their account**. Fortinet's advice is to create all guest accounts on the same appliance.

## Licensing with a Manager

* Each appliance has its own licence key working **together with** the Manager's key.
* A feature (device profiler, guest manager, endpoint compliance …) included in the **Manager's** key is enabled on **all** managed appliances. To enable a feature on **one** appliance only, include it in that appliance's key and **not** in the Manager's key.
* **Concurrent licences are pooled.** The Manager holds the maximum (say 1000). CAs draw from it in any proportion, and every dashboard shows the same total, in-use and available figures.
* A host uses a licence while connected and releases it on disconnect. A host connected to a wired CA and a wireless CA at the same time uses **two**.
* If the Manager goes down, the CAs **keep running** on the licence counts they have.

## Manager clustering and CA status (7.6)

F 7.6.0 replaced FortiNAC-M HA pairs with **Cluster Management** (System > Cluster Management). A cluster has one **leader** node (Admin UI, cluster and CA management, heartbeats to workers) and one or more **worker** nodes (UI limited to the Config Wizard; they feed information to the leader). Upgrading a pre-7.6 Manager HA pair makes **both Managers active** in a cluster and **removes the VIP**. CA HA is not affected by that change.

The **CA Management** widget lists every managed CA with its role (primary or secondary in a 1+1 pair or N+1 group), port1 IP, serial number, firmware, managing node and status:

| Status | Meaning |
|---|---|
| Running | Normal |
| Unreachable Reconnecting | Manager lost the CA and is retrying |
| Failed | Disconnected; an admin must check and reconnect |
| Stand By | A secondary not running for any primary, or a repaired primary whose secondary is still promoted |
| Promotion In Progress | N+1 secondary taking over for a failed primary |
| Promoted | Secondary running on behalf of a primary |

**Open UI** on a CA (right-click) opens that CA's Admin UI, but only if the administrator account exists on **both** the Manager and the CA. In general, any admin created on the Manager must also exist on each CA the admin needs to reach.

## MDM connectors in a Manager environment

An MDM service connector can live on the Manager or on individual CAs:

* **On the Manager:** every managed CA gets the MDM host data; the Manager polls the MDM once and copies the records to the CAs after each poll. One point of contact, fewer queries against the MDM.
* **On selected CAs:** only those CAs get the data, and each polls the MDM itself.

## Lab it yourself (optional)

Needs a Manager and two CAs from a POC or partner. Reading-only path: follow the CLI above and the tables.

1. Add `nac-ipc` on port1 of all three, set the allowed serials and restart services.
2. Add both CAs in CA Management and confirm **Running**.
3. Create a host group and a user/host profile on the Manager, wait for the sync (or Synchronize Now) and try to edit them on a CA (read-only).
4. Use **Locate** on the Manager to find a host connected to the second CA.

## Key takeaways

* FortiNAC-M centralizes **global objects, licences and search**. CAs still model devices and enforce.
* Connecting a CA: same build, `nac-ipc` + `ssh` in port1 `allowaccess` on both, **security.allowedserialnumbers** via `globaloptiontool`, restart, add in **CA Management**.
* Global objects (admin profiles, guest templates, device profiling rules, device types, groups, roles, user/host profiles, endpoint compliance) are **read-only on CAs**. Auto-sync every **10 min**; Synchronize Now overwrites.
* F 7.6.3+ propagates host (by MAC) and user (by user ID) records every **5 min** under **On Demand Host Propagation**. Guest accounts are copied on demand, never synchronized.
* The licence pool is shared. A feature in the Manager key applies everywhere. CAs keep working if the Manager is down.
* 7.6 replaced Manager HA with **leader/worker clusters** (VIP removed). Watch CA status, including **Promoted** for N+1 secondaries.
