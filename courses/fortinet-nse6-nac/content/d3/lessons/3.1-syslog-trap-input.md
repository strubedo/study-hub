## Why third-party input matters

FortiNAC-F learns most of what it knows by asking: SNMP and CLI polling of switches, RADIUS requests, agent check-ins. Integration with third-party devices turns that around. Firewalls, IPS/IDS sensors, analyzers and switches **push** information to FortiNAC-F as syslog messages or SNMP traps, and FortiNAC-F turns each recognised message into an **event**. Events can then raise alarms, notify administrators and run actions, or feed the Security Incidents engine (covered in 2.1).

Three things must be true before any pushed message is processed:

| Requirement | Why |
|---|---|
| The listener is open on **port1** (`set allowaccess ... syslog` and/or `snmp`) | FortiNAC-OS only accepts the protocols listed in `allowaccess`; there is no implicit listener |
| The **sending device is modeled** in Network > Inventory | FortiNAC-F matches the message's source IP to a modeled device; messages from unknown sources are not processed |
| A **definition** exists that tells FortiNAC-F how to read the message | Syslog Files or Security Event Parsers for syslog; Trap MIB Files for custom traps; built-in support for MIB-2 link traps and vendor MAC notification traps |

### Opening the listeners on FortiNAC-OS

The `allowaccess` list on an interface is replaced, not merged, when you use `set`. Copy the existing list and add to it:

```text
FNAC-CA1 # show system interface
config system interface
    edit port1
        set allowaccess https-adminui ssh snmp
    next
end
FNAC-CA1 # config system interface
FNAC-CA1 (interface) # edit port1
FNAC-CA1 (port1) # set allowaccess https-adminui ssh snmp syslog
FNAC-CA1 (port1) # end
```

Typing `set allowaccess syslog` alone would remove the GUI and SSH access. The 7.6 CLI Reference also lists `append allowaccess <list>` in the interface context, which adds items instead of replacing them. The CLI Reference describes the `snmp` keyword as UDP 161 and 162, so it covers polling replies and traps. The integration guides say FortiNAC-F listens for syslog on UDP 514.

> **Watch out:** The CLI Reference prints "UDP port 53" next to the `syslog` keyword. That is a documentation slip; every integration guide (FortiGate VPN, Security Incidents, log receivers) uses 514. Don't build a firewall rule from the typo.

## Modeling the sender: the pingable device

A switch that sends traps is normally modeled already (discovery or Add Device). A firewall, IPS, FortiAnalyzer or SIEM that only *sends* information is added as a **pingable device**: Network > Inventory, right-click a container, **Add Pingable Device**. Give it a unique name, the IP address it sources its messages from, and a MAC address if FortiNAC-F can't resolve IP to MAC from ARP.

The Element tab has an **Incoming Events** field with three choices:

| Incoming Events | What FortiNAC-F does with the device's syslog |
|---|---|
| Not Applicable | Nothing is parsed |
| **Syslog** | Pick one of the enabled **Syslog Files**; matching lines become ordinary events (and alarms if mapped) |
| **Security Events** | Pick an enabled **Security Event Parser**; lines become security events for the Security Incidents rules. Only offered when Security Incidents is set up (licensed) |

The same tab can also make the device an **SSO agent** source (Palo Alto User-ID, RADIUS accounting, iboss or a custom script). That's a different integration, but it explains why the dialog is so busy.

> **Real world:** The IP you model must be the address the device actually sources syslog from. Firewalls and multi-homed analyzers often send from an interface you didn't expect. Capture first, then model: from `execute enter-shell`, the Security Incidents guide uses `tcpdump -vnni any port 514` to see who is really talking.

## Syslog Files: legacy event generation from syslog

**System > Settings > System Communication > Syslog Files** holds definitions that convert IPS/IDS syslog into named events. FortiNAC-F ships definitions for FireEye, FortiOS4, FortiOS5, Palo Alto Networks Firewall, Sourcefire IPS, StoneGate IPS, TippingPoint SMS and Top Layer IPS. You can add your own if the device speaks one of three formats:

| Format | How fields are found | Delimiter |
|---|---|---|
| **CSV** | By column number | space, comma or pipe |
| **TAG/VALUE** | By tag name, e.g. `cip=192.168.10.182` | Always a space; values containing spaces must be in double quotes |
| **CEF** | Fixed header `CEF:Version|Device Vendor|Device Product|Device Version|Signature ID|Name|Severity|` then tagged extensions such as `src=` | Header uses pipes |

Each definition names the column or tag that holds the **source IP** (the host that caused the alert), a **filter** column/tag and the **filter value** that a line must contain to be used, the **severity** column/tag and which raw values map to Low, Medium and High, and an **Event Format** built from chosen columns. When you add a definition, the matching events and alarms appear in the event list.

Two behaviours are worth memorising:

* If the source IP belongs to a host with **several adapters**, FortiNAC-F generates an event **per adapter**, so one syslog line can produce several events and alarms.
* A line for a host FortiNAC-F does not manage raises **Syslog Error** rather than a host event.

### Syslog Files vs Security Event Parsers

| | Syslog Files | Security Event Parsers |
|---|---|---|
| Path | System Communication > Syslog Files | System Communication > Security Event Parsers |
| Output | Standard events and alarms | Security events for Security Incidents rules |
| Licence | Base event system | Security Incidents licence |
| Extra fields | Source IP, filter, severity, event text | Source IP, destination IP, type, subtype, threat ID, description, severity, plus **severity mappings** from vendor values to FortiNAC values |
| Helpers | — | **Populate from Received Syslog**, **Test** a pasted message, partial-column regex |

Both depend on the pingable device's Incoming Events selection. Fortinet publishes vendor severity equivalents; for example Fortinet `WARNING` maps to FortiNAC 5 and `CRITICAL` to 8, and Palo Alto `HIGH` maps to 7.

## SNMP trap input

FortiNAC-F handles three families of traps.

### 1. MIB-2 link traps and MAC notification traps

`linkUp`/`linkDown` (SNMPv1 generic types, or `1.3.6.1.6.3.1.1.5.4`/`.5.3` in v2) tell FortiNAC-F a port changed state, after which it reads the switch's forwarding table. **MAC notification traps** carry the MAC address, port and add/remove action inside the trap, so FortiNAC-F doesn't have to read the forwarding table at all. Fortinet recommends them for large deployments and for ports where hosts sit behind IP phones or unmanaged hubs (the link never goes down when a PC is unplugged from the phone).

The Administration Guide's SNMP trap support table lists the MAC notification OIDs per vendor; for Cisco, the v2/v3 trap is `1.3.6.1.4.1.9.9.215.2.0.1` (Cisco's `cmnMacChangedNotification`). The MAC notification guide states that FortiNAC-F accepts **SNMPv1, v2 and v3** for these traps.

A Cisco IOS access switch configured the way the FortiNAC-F guide describes:

```text
Cisco-Access1(config)# mac address-table notification change
Cisco-Access1(config)# mac address-table notification mac-move
Cisco-Access1(config)# snmp-server enable traps mac-notification change move
Cisco-Access1(config)# snmp-server host 10.10.10.20 version 2c FNAC-RO mac-notification
Cisco-Access1(config)# snmp-server source-interface traps Vlan10
Cisco-Access1(config)# interface range GigabitEthernet1/0/1 - 46
Cisco-Access1(config-if-range)# snmp trap mac-notification change added
Cisco-Access1(config-if-range)# snmp trap mac-notification change removed
Cisco-Access1(config-if-range)# no snmp trap link-status
```

Points the guide makes:

* Configure the traps on **access ports and AP ports only**; not on uplinks, aggregates or ports FortiNAC-F treats as uplinks. Traps from those ports only create processing load and **MAC change on uplink** events.
* **Remove linkUp/linkDown** on ports that send MAC notification traps.
* The trap's **source IP must be the address the switch is modeled with**, which is why L3 switches need `snmp-server source-interface traps`. Otherwise FortiNAC-F ignores the traffic.
* Trap version is independent of the polling version: a switch modeled with SNMPv3 may send v2c traps.
* SNMPv3 switches also need context (per-VLAN) access so FortiNAC-F can read the bridge MIB.
* By default FortiNAC-F **ignores MAC notification traps for IP phones** (Network > Settings > Network Device), to save processing.

Verify with the Ports tab of the switch model, the MAC Add/Remove events, and `diagnose network mac-notification-stats all`, which prints the trap-handling statistics the running process keeps. `diagnose network device test-snmp ip=<ip>` checks the polling credentials, which a trap-driven lookup still relies on.

### 2. Custom traps: Trap MIB Files

For applications that send their own enterprise traps (an IDS, an antivirus server, a monitoring tool), **System > Settings > System Communication > Trap MIB Files** defines how to read them. Each MIB entry holds one or more **custom traps**:

| Field | Meaning |
|---|---|
| Label | Name used for the event/alarm |
| Enterprise OID | The vendor subtree, e.g. `1.3.6.1.4.1.9` for Cisco |
| Specific Type | The vendor-specific trap number |
| IP address OID / MAC address OID / User ID OID | Varbinds that identify the host or user; **any one** is enough |
| Alarm Cause | Text describing the probable cause |
| Event Format | Message text; `{n}` inserts varbind *n*, counting from **0** (so `{4}` is the fifth varbind) |

The Trap MIB Files page states that FortiNAC-F receives these traps over **SNMPv1 and SNMPv2** only, that the sender must be modeled with an IP address, and that you should capture a real trap first so you enter the right OIDs. When a received trap matches, an event is generated; if the event is mapped to an alarm, the alarm fires too.

> **Exam tip:** Keep the two trap stories apart. MAC notification traps from switches are built-in and accept v1/v2/v3. Custom application traps need a Trap MIB File and are documented as v1/v2 only.

### 3. Traps that FortiNAC-F sends

FortiNAC-F can also *send* events as traps to a manager (Log Receivers, next lesson), and it answers SNMP queries for its own MIB (`enterprises.16856`) when SNMP is enabled.

## Lab it yourself (optional)

There is no free FortiNAC-F VM licence, so this lab needs a POC, partner or employer appliance. Reading-only path: walk through the GUI paths above and the Cisco example.

1. On `FNAC-CA1`, add `syslog` and `snmp` to port1 `allowaccess`, keeping the existing items.
2. Create a CSV Syslog File of your own (source IP in column 3, a filter value such as `LABTEST` in column 1), then model a Linux host as a pingable device with Incoming Events = Syslog and that definition.
3. From the Linux host send `logger -n 10.10.10.20 -P 514 -d "LABTEST,High,<a managed host IP>"`, and look for the event in Logs > Events (or **Syslog Error** if the IP isn't a managed host). `logger` puts a syslog header in front of your text, so capture one line first and count the columns from what actually arrives. Disable the Syslog File and resend: nothing is generated.
4. If you have a Cisco switch in the lab, configure MAC notification traps as above and compare the Ports view update with link traps.

## Key takeaways

* Pushed input needs three things: `allowaccess` on port1 (`syslog`, `snmp`), a **modeled sender** whose IP matches the message source, and a definition to parse it.
* Non-switch senders are modeled as **pingable devices**; **Incoming Events** selects **Syslog** (Syslog Files → events) or **Security Events** (parsers → Security Incidents).
* Syslog Files support **CSV, TAG/VALUE and CEF**; one line for a multi-adapter host creates one event **per adapter**.
* **MAC notification traps** carry MAC and port data, accept SNMPv1/v2/v3, belong on access ports only, and replace link traps on those ports.
* **Trap MIB Files** decode custom enterprise traps (Enterprise OID + Specific Type + IP/MAC/User OID, varbinds counted from 0) and are documented as SNMPv1/v2 only.
* Use `diagnose network mac-notification-stats all`, `diagnose network device test-snmp ip=<ip>` and a shell `tcpdump` on port 514 to prove what arrives.
