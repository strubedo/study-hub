## Why logs, and how applications log

Logs are timestamped records of events. Metrics tell you **that** something is wrong; logs help explain **why**. Good practice for application logging:

- Write one event per line, preferably **structured** (JSON or key=value) with a timestamp, level, message and context (request ID, user, service).
- Use levels consistently: DEBUG, INFO, WARNING, ERROR, FATAL/CRITICAL.
- In containers, **log to stdout/stderr** and let the platform collect it (twelve-factor style). Docker's default `json-file` driver stores it per container (`docker logs`); in Kubernetes the node keeps it under `/var/log/pods` and `/var/log/containers`, read with `kubectl logs`. Do not write log files inside the container filesystem.
- Never log secrets or personal data, and include a correlation (trace or request) ID so lines from different services can be tied together.
- Rotate and expire logs (logrotate or journald limits) so the disk does not fill.

```text
{"ts":"2026-10-30T09:14:02.418Z","level":"error","service":"webshop","msg":"payment declined","order":4711,"trace_id":"0af7651916cd43dd8448eb211c80319c"}
```

## syslog and rsyslog

**syslog** is the traditional Unix logging protocol and daemon family (`syslogd`, today usually **rsyslog**). Each message has a **facility** (the kind of source) and a **severity** (importance). The priority value is `facility * 8 + severity`. Messages are sent locally via `/dev/log` or over the network to port **514** (UDP, or TCP for reliability), configured in `/etc/rsyslog.conf` and `/etc/rsyslog.d/`.

| Severity | Name | | Facility | Meaning |
|---|---|---|---|---|
| 0 | emerg | | 0 `kern` | kernel |
| 1 | alert | | 1 `user` | user-level |
| 2 | crit | | 2 `mail` | mail system |
| 3 | err | | 3 `daemon` | system daemons |
| 4 | warning | | 4 `auth` / 10 `authpriv` | security / authorisation |
| 5 | notice | | 9 `cron` | scheduler |
| 6 | info | | 16-23 `local0`-`local7` | free for local use |
| 7 | debug | | | |

Lower number = more severe. A selector in rsyslog is `facility.severity` and matches that severity **and more severe**:

```text
auth,authpriv.*              /var/log/auth.log
*.info;mail.none;authpriv.none  /var/log/syslog
local3.err                   @@logs.example.com:514     # @@ = TCP, @ = UDP
```

## systemd-journald

On systemd systems, **systemd-journald** collects logs from the kernel, services' stdout/stderr, syslog calls and the journal API into a **binary, indexed journal** with structured fields (`_SYSTEMD_UNIT`, `PRIORITY`, `_PID`, ...). Read it with **`journalctl`**:

```bash
journalctl -u nginx.service            # one unit
journalctl -u nginx -f                 # follow, like tail -f
journalctl -p err                      # priority err and worse
journalctl -b                          # current boot; -b -1 = previous boot
journalctl --since "1 hour ago" --until now
journalctl -k                          # kernel messages
journalctl -o json-pretty -n 5         # structured output
```

The journal is volatile (`/run/log/journal`) unless the directory `/var/log/journal` exists or `Storage=persistent` is set in `/etc/systemd/journald.conf`. journald can forward to rsyslog (`ForwardToSyslog`), which is how the two coexist. Size limits come from `SystemMaxUse=` and similar settings.

> **Exam tip:** syslog = text files + facility.severity + port 514; journald = binary journal read only with `journalctl`.

## Why a logging stack

With many hosts and containers, logging into each machine is impractical. A **logging stack** collects, processes, stores and searches logs centrally. The stages are always the same: **collect/ship** (agent on each node), **process/parse** (optional), **store/index**, **search/visualise**.

| Tool | Role |
|---|---|
| **Elasticsearch** / **OpenSearch** | Distributed search and analytics engine; stores logs as JSON documents in indices with full-text indexing. OpenSearch is the Apache-licensed fork of Elasticsearch |
| **Logstash** | Server-side pipeline: **input -> filter -> output** plugins (parse with `grok`, enrich, route) |
| **Filebeat** | Lightweight shipper from the Beats family; tails files and forwards to Logstash or Elasticsearch |
| **Kibana** | Web UI for searching and dashboards over Elasticsearch (OpenSearch Dashboards is the fork) |
| **Fluentd** | Open source data collector with a large plugin ecosystem (CNCF); routes by tags |
| **Fluent Bit** | Very light, fast Fluentd sibling for nodes and containers; often the Kubernetes log agent |
| **Loki** | Grafana's log store, "like Prometheus, but for logs": indexes only **labels**, keeps log content compressed in chunks |
| **Promtail** | Loki's agent that tails files and journals and pushes to Loki with labels. **Deprecated** in favour of **Grafana Alloy** (its OpenTelemetry-based collector) |
| **Grafana** | Visualisation and exploration; has Loki as a data source |
| **Graylog** | Self-contained log management platform (web UI, streams, alerts) with MongoDB for configuration and OpenSearch/Elasticsearch for storage |

Common combinations:

- **ELK**: Elasticsearch + Logstash + Kibana (with Beats, sometimes called the Elastic Stack).
- **EFK**: Elasticsearch + **Fluentd** (or Fluent Bit) + Kibana, popular on Kubernetes.
- **PLG / Grafana stack**: Promtail (now Alloy) + Loki + Grafana.

### Loki in more detail

Loki keeps a small index over **labels** (for example `{app="webshop", env="prod"}`) and stores the log text unindexed, which makes it cheaper than full-text indexing but means queries first select a stream by labels. **LogQL** queries start with a stream selector using the same matchers as PromQL, then filter text:

```text
{app="webshop", env="prod"} |= "error" != "healthcheck"
sum by (app) (rate({env="prod"} |= "error" [5m]))
```

`|=` contains, `!=` does not contain, `|~` regex match. The second query turns logs into a metric. Keep label cardinality low: do not use request IDs as labels.

### Where each tool sits

```text
files / journal / stdout --> [Filebeat | Fluent Bit | Promtail/Alloy]
                         --> [Logstash | Fluentd]   (optional parse/enrich)
                         --> [Elasticsearch/OpenSearch | Loki | Graylog]
                         --> [Kibana | Grafana | Graylog UI]
```

> **Watch out:** Elasticsearch/Logstash/Kibana, Loki/Promtail and Graylog are separate stacks. Kibana does not read Loki; Grafana is the front end for Loki.

## Lab it yourself

1. `logger -p local3.err -t webshop "payment failed"` then find the line in `/var/log/syslog` or with `journalctl -t webshop`.
2. `journalctl -u ssh -p warning --since today`.
3. Run Loki + Grafana (or Alloy) in Docker Compose, ship `/var/log`, and query `{job="varlogs"} |= "error"`.

## Key takeaways

- Log to stdout in containers, use structured lines, include correlation IDs, rotate logs.
- syslog messages have a facility and severity (0 emerg to 7 debug); network port 514; rsyslog is the usual daemon.
- journald stores a binary journal read with `journalctl` (`-u`, `-f`, `-p`, `-b`, `--since`); persistent only with `/var/log/journal`.
- ELK = Elasticsearch, Logstash, Kibana (Filebeat ships); EFK uses Fluentd or Fluent Bit; OpenSearch is the Elasticsearch fork.
- Loki indexes labels only and is queried with LogQL from Grafana; Promtail is deprecated in favour of Grafana Alloy.
- Graylog is an integrated platform that stores in OpenSearch/Elasticsearch and keeps config in MongoDB.
