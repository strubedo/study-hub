## Where the risk lives

Cloud native systems are stacks of components, and each layer has its own attack surface. The exam expects you to name the threat and the standard mitigation.

| Layer | Typical threat | Mitigation |
|---|---|---|
| Host / node OS | Unpatched kernel or packages, exposed SSH | Security updates, minimal images, key-only SSH, no direct node access |
| Network | Open ports, lateral movement, **denial of service** | **Packet filtering** (firewall, security groups, Kubernetes NetworkPolicy), segmentation, rate limits |
| Edge | Direct access to back ends, overload | **Load balancers** and **application gateways** (reverse proxy / API gateway / WAF) terminate TLS, filter and throttle before traffic reaches services |
| Services and APIs | **Service exploits** of known flaws, **brute force** against logins | Patch quickly, lockouts and rate limits, strong authentication |
| Containers | Root containers, vulnerable base images, secrets in images | Non-root users, minimal images, image scanning, read-only filesystems |
| Data and secrets | Hard-coded credentials, over-broad permissions | Secret stores, least privilege, encryption at rest and in transit |

A **denial-of-service (DoS)** attack exhausts capacity so legitimate users are refused; a distributed one (DDoS) comes from many sources. Mitigations are layered: upstream filtering or a CDN, **rate limits** per client or API key, autoscaling and timeouts. A **brute-force attack** tries many passwords or tokens; counter it with rate limiting, account lockout or back-off, MFA and long, hashed passwords. A **service exploit** abuses a bug in a running service; the cure is **security updates** applied quickly plus reducing exposed services.

> **Exam tip:** "Update the software" (security updates), "filter the traffic" (packet filtering), "put a gateway in front" (load balancer / application gateway) and "limit requests" (rate limits) are the four stock infrastructure answers.

## Supply chain security

Modern applications are mostly **foreign code**: open source libraries, base images, build tools and CI actions. An attacker who compromises one dependency reaches every consumer. Typical attacks: a malicious or hijacked package, **typosquatting** (a package named almost like a popular one), a compromised build system, a tampered image in a registry.

Mitigations you should be able to list:

- Pin dependencies and base images to versions or digests (`image@sha256:...`); commit lock files.
- Pull from trusted registries and mirrors; verify checksums and **signatures** (for example signing images and verifying them before deployment).
- Scan dependencies and images for known vulnerabilities in CI and keep updating.
- Produce and keep a **software bill of materials (SBOM)** so you can answer "are we affected?" when a new CVE appears.
- Protect the build pipeline itself: least-privilege CI credentials, reproducible builds, reviewed changes.

## Application security risks

These are the classic web and API flaws in the term list. Know the mechanism and the standard fix.

| Risk | What happens | Main mitigation |
|---|---|---|
| **Cross-site scripting (XSS)** | Attacker-supplied script is delivered to other users' browsers inside a page and runs with that site's privileges | Escape/encode output for its context, validate input, **Content-Security-Policy** header, `HttpOnly` cookies |
| **SQL injection** | User input is concatenated into a SQL statement so the input becomes part of the query | **Parameterised queries / prepared statements**, least-privilege DB accounts |
| **Cross-site request forgery (CSRF)** | A malicious site makes the victim's browser send an authenticated request (cookies go along automatically) to another site | **CSRF tokens** (unpredictable per-session value checked by the server), `SameSite` cookies, re-authentication for sensitive actions |
| **Buffer overflow** | Writing past the end of a fixed-size buffer (typical in C/C++) overwrites adjacent memory and can give code execution | Memory-safe languages, bounds checking, compiler protections (stack canaries, ASLR), patching |
| **Verbose error reports** | Stack traces, SQL errors or version banners shown to users leak internals | Generic client errors; detail only in server-side logs; debug mode off in production |
| **Weak API access control** | Missing authentication, over-broad permissions, no rate limit, chatty responses | API authentication on every call, least-privilege **permissions**, rate limits, return only needed fields (limit **verbosity**) |

SQL injection example: with the code `"SELECT * FROM users WHERE name='" + name + "'"`, the input `x' OR '1'='1` changes the query logic. A prepared statement sends the query and the value separately, so the value is never parsed as SQL.

### CORS versus CSRF

Browsers apply the **same-origin policy**: a script from `https://shop.example.com` may not read responses from another origin. **Cross-Origin Resource Sharing (CORS)** is the controlled way for a server to relax that restriction for reading. The server answers with headers:

```text
HTTP/1.1 200 OK
Access-Control-Allow-Origin: https://shop.example.com
Access-Control-Allow-Methods: GET, POST
Access-Control-Allow-Headers: Authorization, Content-Type
Vary: Origin
```

`Access-Control-Allow-Origin` names the single origin that may read the response (or `*` for any, which is wrong for credentialed APIs). For non-simple requests the browser first sends an `OPTIONS` **preflight**. CORS is enforced by the browser, not by the server, and it does not stop requests from being sent; it controls whether a page may read the answer. That is why CORS is **not** a CSRF defence: CSRF is stopped with tokens and `SameSite` cookies.

> **Watch out:** `Access-Control-Allow-Origin: *` together with credentials is rejected by browsers. Never reflect an arbitrary `Origin` header back without an allow-list.

## CVE IDs and scores

The **Common Vulnerabilities and Exposures (CVE)** programme gives each publicly disclosed vulnerability a unique identifier of the form `CVE-YYYY-NNNN`, where `YYYY` is the year it was assigned or published and the sequence number has **four or more digits** (for example `CVE-2021-44228`, `CVE-2024-100000` is valid). A CVE record is a short description plus references; the identifier itself carries no severity.

Severity comes from the **Common Vulnerability Scoring System (CVSS)**, maintained by FIRST, which scores from **0.0 to 10.0**:

| Rating | Score |
|---|---|
| None | 0.0 |
| Low | 0.1 to 3.9 |
| Medium | 4.0 to 6.9 |
| High | 7.0 to 8.9 |
| Critical | 9.0 to 10.0 |

The base score reflects attack vector, complexity, privileges and user interaction required, and the impact on confidentiality, integrity and availability. Scanners report the CVE ID, the CVSS score and the fixed version. Use the score to prioritise, but also consider exposure: a High flaw in an internet-facing service can matter more than a Critical in an isolated one.

> **Exam tip:** CVE = the name; CVSS = the 0.0-10.0 severity; a score of 9.8 is Critical, 7.5 is High.

## Lab it yourself

1. Scan an image: `trivy image nginx:1.27` (or Grype) and note a CVE ID, its score and the fixed version.
2. Run `curl -si -H 'Origin: https://shop.example.com' https://api.example.com/items` and look for `Access-Control-Allow-Origin` in the response.
3. In a throwaway SQLite database, compare a string-concatenated query with a parameterised one using the input `x' OR '1'='1`.

## Key takeaways

- Defend infrastructure in layers: updates, packet filtering, gateways/load balancers, rate limits.
- Supply chain risk is foreign code: pin, verify, scan, sign and keep an SBOM.
- XSS: escape output + CSP. SQLi: parameterised queries. CSRF: tokens + SameSite. Buffer overflow: bounds-checked, memory-safe code.
- Verbose errors leak internals; show generic messages and log details server-side.
- CORS is a browser mechanism configured with `Access-Control-Allow-Origin` and related headers; it is not a CSRF defence.
- CVE ID format is `CVE-YYYY-NNNN` with at least four digits; CVSS scores 0.0-10.0 and 9.0-10.0 is Critical.
