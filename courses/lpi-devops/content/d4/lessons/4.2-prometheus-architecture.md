## Why monitor: operations goals and indicators

IT operations aims to keep services available and fast. The **non-functional properties** to watch are **availability** (is it up and answering?), **latency** (how long a request takes), **responsiveness**, throughput and error rate, plus saturation of resources (CPU, memory, disk, connections). Two well-known checklists:

- **RED** for request-driven services: **R**ate, **E**rrors, **D**uration.
- **USE** for resources: **U**tilisation, **S**aturation, **E**rrors.

Metrics split into two groups the objectives call out:

- **Technical functionality**: CPU, memory, disk, network, request latency, error rates, queue depth, container restarts.
- **Logical (business) functionality**: whether the service does its job, such as orders placed per minute, payments completed, items in a processing queue, or the result of a synthetic end-to-end check. A server can be "up" while orders silently fail, so logical indicators matter.

A **service level indicator (SLI)** is a measured value (for example the share of requests answered in under 300 ms); a **service level objective (SLO)** is the target for it.

## Prometheus architecture

Prometheus is an open source monitoring system with a time-series database. Its defining design choice is the **pull model**: the Prometheus server **scrapes** (HTTP GET) the `/metrics` endpoint of each target at a regular interval and stores the samples. Each series is identified by a metric name plus **labels** and holds timestamp/value samples.

```text
 targets (apps, exporters)  <--scrape-- Prometheus server --rules--> Alertmanager --> email/Slack/pager
        ^                                   |  TSDB, PromQL, :9090
 short-lived jobs --push--> Pushgateway     +--> Grafana (queries via PromQL)
```

| Component | Role | Default port |
|---|---|---|
| **Prometheus server** | Scrapes, stores, evaluates rules, serves PromQL and a web UI | **9090** |
| **Exporters** | Expose metrics for things that do not speak Prometheus. **Node Exporter** for host metrics | **9100** |
| **Blackbox Exporter** | Probes endpoints from outside (HTTP, HTTPS, TCP, ICMP, DNS) | 9115 |
| **Pushgateway** | Holds metrics pushed by short-lived **batch jobs**, which Prometheus then scrapes | 9091 |
| **Alertmanager** | Receives alerts from Prometheus and handles grouping, deduplication, inhibition, silencing and routing | 9093 |
| **Grafana** | Dashboards; uses Prometheus as a data source | 3000 |

Exposition format: plain text, one sample per line, with optional `# HELP` and `# TYPE` lines.

```text
# HELP http_requests_total Total HTTP requests.
# TYPE http_requests_total counter
http_requests_total{method="GET",code="200"} 10234
http_requests_total{method="POST",code="500"} 7
```

### The four metric types

| Type | Behaviour | Example |
|---|---|---|
| **Counter** | Only goes up (resets to 0 on restart). Query it with `rate()`/`increase()` | `http_requests_total` |
| **Gauge** | Goes up and down; a current value | `node_memory_MemAvailable_bytes`, queue length |
| **Histogram** | Counts observations in cumulative buckets: series `_bucket{le="..."}`, `_sum`, `_count`. Quantiles are computed on the server with `histogram_quantile()` and can be aggregated across instances | `http_request_duration_seconds_bucket` |
| **Summary** | Calculates quantiles on the client and exposes `{quantile="0.99"}` plus `_sum` and `_count`. Quantiles cannot be aggregated across instances | `rpc_duration_seconds` |

> **Exam tip:** pull is the default; **Pushgateway** is only for service-level batch jobs that are too short-lived to be scraped. It is not a way to turn Prometheus into a push system, and it never forgets pushed series until deleted.

## Configuration and scraping

Prometheus is configured with `prometheus.yml`. Global settings include `scrape_interval` (default **1m**), `scrape_timeout` (default **10s**) and `evaluation_interval` (default **1m**). Targets are defined under `scrape_configs`, each with a `job_name`.

```yaml
global:
  scrape_interval: 15s
  evaluation_interval: 15s

rule_files:
  - /etc/prometheus/rules/*.yml

alerting:
  alertmanagers:
    - static_configs:
        - targets: ['10.0.0.20:9093']

scrape_configs:
  - job_name: prometheus
    static_configs:
      - targets: ['localhost:9090']
  - job_name: node
    static_configs:
      - targets: ['10.0.0.11:9100', '10.0.0.12:9100']
```

Prometheus adds the labels `job` (from `job_name`) and `instance` (the `host:port`) to every scraped series, and a synthetic metric `up` per target: `1` when the scrape succeeded, `0` when it failed. Run it with `prometheus --config.file=prometheus.yml`; reload configuration with SIGHUP, or `POST /-/reload` when started with `--web.enable-lifecycle`.

### File-based service discovery

Hand-edited `static_configs` do not scale. **`file_sd_configs`** reads target lists from JSON or YAML files that other tooling (Ansible, scripts, templates) can update; Prometheus watches the files and applies changes without a restart.

```yaml
scrape_configs:
  - job_name: webshop
    file_sd_configs:
      - files:
          - /etc/prometheus/targets/*.json
        refresh_interval: 5m
```

```json
[
  { "targets": ["10.0.0.31:8080", "10.0.0.32:8080"],
    "labels": { "env": "prod", "team": "shop" } }
]
```

`files` is a list of paths (patterns allowed). `refresh_interval` is the periodic fallback re-read (default **5m**); file changes are normally picked up immediately. Each group has `targets` and optional `labels` applied to those targets. The YAML form is a list of `- targets: [...]` / `labels:` entries. Other discovery mechanisms exist (Kubernetes, DNS, Consul, EC2, HTTP SD) and all produce the same target-plus-labels model; `relabel_configs` rewrites labels before scraping.

## Alerting

Alerting rules live in files named in `rule_files` and are evaluated every `evaluation_interval`.

```yaml
groups:
  - name: webshop
    rules:
      - alert: InstanceDown
        expr: up == 0
        for: 5m
        labels:
          severity: page
        annotations:
          summary: "{{ $labels.instance }} is down"
```

An alert is **pending** until its expression has been true for the `for` duration, then **firing**; firing alerts are sent to **Alertmanager**. Alertmanager does:

- **Grouping**: combines related alerts (by labels in `group_by`) into one notification. Timers: `group_wait` (default 30s), `group_interval` (5m), `repeat_interval` (4h).
- **Inhibition**: suppresses certain alerts while another, more important alert is firing (for example mute service alerts while the whole node is down).
- **Silences**: temporarily mute alerts matching label matchers, set in the UI or with `amtool`.
- **Routing** to receivers (email, Slack, PagerDuty, webhook) by a tree of label-matching routes.

Prometheus decides **when** an alert fires; Alertmanager decides **who is told and how**. Recording rules (`record:`) precompute expensive expressions.

## Monitoring containers and microservices

- **cAdvisor** (or the kubelet's built-in cAdvisor endpoint) exposes per-container CPU, memory, network and filesystem metrics such as `container_cpu_usage_seconds_total`.
- On Kubernetes use **Kubernetes service discovery** (`kubernetes_sd_configs`) so Pods and Services appear automatically, **kube-state-metrics** for object state (desired vs. available replicas) and Node Exporter as a DaemonSet. The Prometheus Operator adds `ServiceMonitor` and `PodMonitor` resources.
- Dynamic, short-lived instances are exactly why service discovery and labels matter; use stable labels such as `service`, not IP addresses.
- **Node Exporter** (port 9100) exposes host metrics: `node_cpu_seconds_total`, `node_memory_MemAvailable_bytes`, `node_filesystem_avail_bytes`, `node_network_receive_bytes_total`. **Blackbox Exporter** probes targets from the outside via `/probe?target=https://example.com&module=http_2xx` and reports `probe_success` and `probe_duration_seconds`, which measures what a user sees.

## Instrumentation and Thanos

**Application instrumentation** means adding metrics to your own code with an official **client library** (Go, Java, Python, Ruby and more), which provides Counter, Gauge, Histogram and Summary types and an HTTP `/metrics` handler. Name metrics with a base unit and suffix (`_total` for counters, `_seconds`, `_bytes`), and keep label values low-cardinality (never user IDs or URLs with ids), since each label combination is a separate series.

**Thanos** extends Prometheus for **long-term storage** and a **global view**. A Sidecar next to each Prometheus uploads its data blocks to object storage; the **Store Gateway** serves old blocks; the **Querier** fans out PromQL across many Prometheus servers and the store (giving one global view and deduplicating HA replicas); the **Compactor** downsamples and compacts; the Ruler evaluates rules globally.

## Lab it yourself

1. Run Prometheus and Node Exporter in containers, scrape `localhost:9100`, and open `http://localhost:9090/targets`.
2. Switch the node job to `file_sd_configs`, add a target to the JSON file, and watch it appear without a restart.
3. Stop Node Exporter and see `up == 0` become an alert.

## Key takeaways

- Prometheus pulls metrics from `/metrics` endpoints on a schedule; port 9090. Node Exporter is 9100, Pushgateway 9091, Alertmanager 9093.
- Metric types: counter (only up), gauge, histogram (buckets, aggregatable), summary (client-side quantiles).
- `scrape_configs` hold `job_name` plus `static_configs` or `file_sd_configs` (`files`, `refresh_interval`).
- Pushgateway is for short-lived batch jobs; Blackbox Exporter probes from outside.
- Alertmanager groups, inhibits, silences and routes; Prometheus rules decide when alerts fire.
- Thanos adds long-term storage and a global query view; instrument code with client libraries and keep labels low-cardinality.
