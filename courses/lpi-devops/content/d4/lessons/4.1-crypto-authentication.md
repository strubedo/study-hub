## Asymmetric cryptography and certificates

**Asymmetric cryptography** uses a key pair: a **public key** that anyone may have and a **private key** that never leaves its owner. Two uses matter:

- **Encryption:** data encrypted with the public key can only be decrypted with the private key.
- **Digital signatures:** data signed with the private key can be verified by anyone with the public key, proving origin and integrity.

It is slow compared with **symmetric** encryption (one shared key, such as AES), so real protocols use asymmetric crypto to authenticate and agree on a key, then symmetric crypto for the bulk data.

An **X.509 certificate** binds a public key to an identity (a host name, an organisation). It contains the subject, the subject's public key, the issuer, validity dates, extensions such as the Subject Alternative Name (SAN) list, and the issuer's signature. A **certificate authority (CA)** is a trusted party that signs certificates. Clients hold a store of trusted **root CAs**; a server presents its certificate plus intermediate certificates, and the client validates the **chain** up to a trusted root, checks the validity dates, checks that the name matches, and checks revocation where configured.

```text
$ openssl x509 -in server.crt -noout -subject -issuer -dates
subject=CN = shop.example.com
issuer=C = US, O = Example CA, CN = Example Issuing CA 1
notBefore=Oct  1 00:00:00 2026 GMT
notAfter=Dec 30 23:59:59 2026 GMT
```

**TLS** (Transport Layer Security, successor to SSL) provides **transport encryption**: confidentiality, integrity and server authentication (optionally client authentication, which is **mutual TLS**). The handshake authenticates the server by its certificate and derives session keys. HTTPS is HTTP over TLS. Use TLS 1.2 or 1.3; SSL and TLS 1.0/1.1 are obsolete.

> **Watch out:** the private key proves identity. If it leaks, the certificate must be revoked and replaced. A self-signed certificate is valid cryptographically but untrusted unless clients are told to trust it.

## Single sign-on and the standards

**Single sign-on (SSO)** lets a user authenticate once to an **identity provider (IdP)** and then access many applications (relying parties / service providers) without logging in again. Three standards appear on the exam; learn which problem each solves.

| Standard | Purpose | Token / document | Typical use |
|---|---|---|---|
| **OAuth 2.0** | **Authorisation / delegated access**: an app gets limited access to a resource on behalf of a user | Access token (opaque or JWT), optional refresh token | "Let this app read my calendar" |
| **OpenID Connect (OIDC)** | **Authentication** layer on top of OAuth 2.0 | **ID token**, a signed **JWT**, plus an access token | "Log in with ..." for web and mobile apps |
| **SAML 2.0** | Authentication/SSO using XML **assertions** exchanged between IdP and service provider | Signed XML assertion | Enterprise SSO to SaaS apps |

### OAuth 2.0 roles and flows

Four roles: the **resource owner** (the user), the **client** (the application), the **authorization server** (issues tokens) and the **resource server** (the API that accepts access tokens).

The recommended flow for browser, mobile and server apps is the **authorization code flow**, with **PKCE** (Proof Key for Code Exchange) for public clients and now recommended for all:

1. The client sends the user's browser to the authorization server's authorisation endpoint with `response_type=code`, `client_id`, `redirect_uri`, `scope`, `state` and a PKCE `code_challenge`.
2. The user authenticates and consents.
3. The authorization server redirects back to the `redirect_uri` with a short-lived **authorization code**.
4. The client calls the token endpoint (back channel) with the code and the PKCE `code_verifier` and receives an **access token** (and possibly a refresh token, and in OIDC an ID token).
5. The client calls the API with `Authorization: Bearer <access token>`.

The **client credentials** flow is for machine-to-machine access without a user. The old **implicit** flow and the **resource owner password** flow are discouraged. Scopes limit what a token may do. `state` protects against CSRF on the redirect.

```text
GET /authorize?response_type=code&client_id=webshop
    &redirect_uri=https%3A%2F%2Fshop.example.com%2Fcb&scope=openid%20profile
    &state=af0ifjsldkj&code_challenge=E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM
    &code_challenge_method=S256 HTTP/1.1
Host: auth.example.com
```

### OpenID Connect

OAuth 2.0 alone does not say who the user is. OIDC adds the `openid` scope and an **ID token**: a **JSON Web Token** with three base64url parts (`header.payload.signature`), signed by the IdP. Standard claims include `iss` (issuer), `sub` (subject, the stable user id), `aud` (the client it is for), `exp` (expiry), `iat` and often `email`. The client verifies the signature, issuer, audience and expiry. A UserInfo endpoint returns more profile claims.

```json
{ "iss": "https://auth.example.com", "sub": "248289761001", "aud": "webshop",
  "exp": 1793000000, "iat": 1792996400, "email": "ana@example.com" }
```

> **Exam tip:** OAuth 2.0 = authorisation (access token). OIDC = authentication (ID token, JWT). SAML = authentication with XML assertions. Mixing these up is the classic trap.

### SAML

In **SAML**, the service provider redirects the user to the IdP with an authentication request; the IdP authenticates the user and returns a digitally signed XML **assertion** (statements about the user: identity, attributes, authentication time) via the browser to the service provider's assertion consumer service. Metadata documents exchange endpoints and certificates. SAML is older and verbose but common in enterprises.

## Credentials: MFA, OTP and hashing

**Multi-factor authentication (MFA)** combines factors from different categories: something you **know** (password), **have** (phone, hardware key) and **are** (biometric). **Two-factor authentication (2FA)** is MFA with exactly two. Two passwords are not two factors.

A **one-time password (OTP)** is valid for a single login. **HOTP** (RFC 4226) is counter-based. **TOTP** (RFC 6238) is **time-based**: client and server share a secret and derive a short code from the secret and the current time step, by default **30 seconds**; codes are usually six digits. **Authenticator applications** (for example Google Authenticator, Aegis, FreeOTP) store the shared secret, enrolled by scanning a QR code, and display the current code. Because the code derives from the clock, device and server clocks must be roughly in sync, and servers often accept one step either side. TOTP codes can still be phished in real time; hardware keys (FIDO2/WebAuthn) resist that.

### Password hashing and salting

Servers must never store passwords in plain text or encrypted reversibly. They store a **hash**. Plain fast hashes (MD5, SHA-1, plain SHA-256) are unsuitable because attackers test billions of guesses per second. Use a purpose-built **slow, salted** password hash: **bcrypt**, **scrypt** or **Argon2** (Argon2id is the current recommendation).

A **salt** is a unique random value stored with each hash and mixed into it. It ensures identical passwords produce different hashes and defeats precomputed **rainbow tables**; it does not make guessing a single hash slower. A **work factor** (cost) makes each guess expensive, and can be raised over time. A **pepper** is an additional secret kept outside the database.

```text
$2b$12$KIXQ3m9yXU5v0q1sPzJk8.8u3Ym5h1d0nL2cWqP7r8tG6bZxA1B2C
 |   |  |<-- 22-char salt + 31-char hash -->|
 |   +-- cost factor 12 (2^12 rounds)
 +------ bcrypt version
```

> **Real world:** also protect APIs with authentication on every request (tokens or mutual TLS), keep tokens short-lived, and store secrets in a vault rather than in images or Git.

## Lab it yourself

1. `openssl s_client -connect example.com:443 -servername example.com </dev/null | openssl x509 -noout -issuer -dates`.
2. Decode the middle part of any JWT: `echo "<payload>" | base64 -d` (add `=` padding if needed) and read the claims.
3. Generate a TOTP code from a test secret with `oathtool --totp -b JBSWY3DPEHPK3PXP` and watch it change every 30 seconds.
4. Hash a password: `python3 -c "import bcrypt;print(bcrypt.hashpw(b'pw',bcrypt.gensalt()))"` twice and note the salts differ.

## Key takeaways

- Public key encrypts/verifies, private key decrypts/signs; TLS uses asymmetric crypto to set up symmetric session keys.
- An X.509 certificate binds a public key to an identity and is signed by a CA; clients validate the chain to a trusted root.
- OAuth 2.0 delegates authorisation (access tokens); OIDC adds authentication (ID token = JWT); SAML uses signed XML assertions.
- Authorization code flow with PKCE is the recommended OAuth 2.0 flow; client credentials is for machine-to-machine.
- MFA needs different factor categories; TOTP (RFC 6238) uses a shared secret and 30-second time steps.
- Store passwords as salted, slow hashes (bcrypt, scrypt, Argon2), never as plain text or fast hashes.
