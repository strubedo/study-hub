## Why tracing

In a microservice system one user request crosses many services. Metrics show an overall slowdown and logs show per-service events, but neither shows **where the time went for one request**. **Distributed tracing** records the path of a request through all services, with timing for each step.

## Concepts

- A **trace** is the complete journey of one request. It has a **trace ID**: 16 bytes, written as **32 hexadecimal characters**.
- A **span** is one unit of work within a trace (an incoming HTTP request, a database query, a call to another service). A span has a **span ID** of 8 bytes (**16 hex characters**), the ID of its **parent span** (empty for the **root span**), a name, start time and duration.
- Spans form a tree (or DAG): the root span is the entry point; children are the calls made while handling it.
- **Context** is the set of identifiers (trace ID, span ID, flags) carried along with the request. **Context propagation** moves it between processes, typically in HTTP headers, so the next service can create child spans in the same trace.

### Span details

| Element | Meaning |
|---|---|
| **Attributes** | Key/value metadata on a span (`http.request.method`, `http.response.status_code`, `db.system`, `service.name` as a resource attribute) |
| **Events** | Timestamped annotations inside a span (an exception, "cache miss") |
| **Links** | References to spans in the same or other traces without a parent/child relation (for example a batch job processing many queued messages) |
| **Status** | `Unset` (default), `Ok`, `Error`. Instrumentation normally sets `Error` on failure; leaving `Unset` means "no error was recorded" |
| **Kind** | `CLIENT` (outgoing synchronous call), `SERVER` (handling an incoming call), `PRODUCER` (creating a message/async job), `CONSUMER` (processing one), `INTERNAL` (default, no remote counterpart) |

An example span in OTLP-style JSON:

```json
{
  "traceId": "0af7651916cd43dd8448eb211c80319c",
  "spanId": "b7ad6b7169203331",
  "parentSpanId": "00f067aa0ba902b7",
  "name": "POST /checkout",
  "kind": "SPAN_KIND_SERVER",
  "startTimeUnixNano": "1793000000000000000",
  "endTimeUnixNano":   "1793000000250000000",
  "attributes": [ { "key": "http.response.status_code", "value": { "intValue": "500" } } ],
  "status": { "code": "STATUS_CODE_ERROR" }
}
```

### W3C Trace Context

The standard propagation header is **`traceparent`** (W3C Trace Context). Format: `version-trace-id-parent-id-trace-flags`, each lower-case hex:

```text
traceparent: 00-0af7651916cd43dd8448eb211c80319c-b7ad6b7169203331-01
             |  |                                |                |
             |  trace ID (32 hex = 16 bytes)     parent span ID   flags (01 = sampled)
             version 00                           (16 hex = 8 bytes)
```

A companion header **`tracestate`** carries vendor-specific data. OpenTelemetry also supports **baggage** (key/value pairs propagated with the request, header `baggage`). The caller's span ID in `traceparent` becomes the parent of the span the callee creates. **Sampling** decides which traces are recorded (head sampling at the start, tail sampling in a collector after seeing the whole trace) because tracing everything is costly.

## OpenTelemetry

**OpenTelemetry (OTel)** is a CNCF, vendor-neutral set of APIs, SDKs, tools and specifications for generating, collecting and exporting telemetry: **traces, metrics and logs** (the "signals"). It standardises instrumentation so you can change the back end without changing application code. It is not itself a storage or UI back end.

Parts:

- **API and SDK** per language (Java, Go, Python, JavaScript, .NET, ...). The API is what code calls; the SDK implements sampling, processing and exporting.
- **Instrumentation**: **automatic** (agents or libraries that instrument frameworks without code changes, such as the Java agent) and **manual** (you create spans with the API for business logic). Many libraries are covered by instrumentation libraries.
- **OTLP**, the OpenTelemetry Protocol: **gRPC on port 4317** and **HTTP (protobuf or JSON) on port 4318**, with paths such as `/v1/traces`.
- The **Collector**, a vendor-neutral service that receives, processes and exports telemetry.
- Standard environment variables: `OTEL_SERVICE_NAME`, `OTEL_EXPORTER_OTLP_ENDPOINT`, `OTEL_TRACES_SAMPLER`.

### The Collector pipeline

A collector configuration defines **receivers** (how data comes in), **processors** (what is done to it) and **exporters** (where it goes), then wires them into **pipelines** in the `service` section:

```yaml
receivers:
  otlp:
    protocols:
      grpc:          # 4317
      http:          # 4318
processors:
  batch:
exporters:
  otlp/tempo:
    endpoint: tempo.example.com:4317
    tls:
      insecure: true
service:
  pipelines:
    traces:
      receivers: [otlp]
      processors: [batch]
      exporters: [otlp/tempo]
```

Defining a component in its top-level block is not enough; it only runs if a pipeline in `service.pipelines` lists it. Common processors: `batch`, `memory_limiter`, `attributes`, tail-sampling. Extensions (health check, zpages) sit beside pipelines. Deployment patterns: an **agent** (collector as a sidecar or DaemonSet next to the app) and/or a central **gateway** collector.

## Analysis back ends

| Tool | What it is |
|---|---|
| **Jaeger** | Open source distributed tracing platform (CNCF graduated) with collector, storage and a web UI (default UI port 16686); accepts OTLP |
| **Grafana Tempo** | Cost-efficient trace store using object storage and indexing mainly by trace ID; searched in Grafana, with **TraceQL** for queries and links from logs and metrics (via exemplars and trace IDs) |

Typical flow: application with OTel SDK -> OTLP -> Collector -> Jaeger or Tempo -> view in the Jaeger UI or Grafana. Putting the `trace_id` into log lines (as in the logging lesson) lets you jump from a log to the trace.

> **Exam tip:** know which side is which: Prometheus (metrics, pull), Loki/ELK (logs), Jaeger/Tempo (traces); OpenTelemetry is the instrumentation and collection standard across all three, not a database.

## Lab it yourself

1. Run Jaeger in Docker (image `jaegertracing/jaeger`; UI on 16686, OTLP on 4317/4318) and send a test span with an OTel SDK or `telemetrygen`.
2. Read the `traceparent` header on a call between two instrumented services (`curl -v`) and match the trace ID in both services' logs.
3. Write a collector config with the `otlp` receiver, `batch` processor and a debug exporter; confirm spans are printed.

## Key takeaways

- A trace is a request's path; spans are its timed steps with parent/child links.
- Trace ID = 16 bytes (32 hex); span ID = 8 bytes (16 hex).
- `traceparent: 00-<trace-id>-<parent-id>-<flags>` is the W3C context propagation header.
- Span kinds: CLIENT, SERVER, PRODUCER, CONSUMER, INTERNAL. Status: Unset, Ok, Error. Attributes, events and links add detail.
- OpenTelemetry standardises instrumentation (API/SDK), OTLP (4317 gRPC, 4318 HTTP) and the Collector (receivers, processors, exporters wired in pipelines).
- Jaeger and Grafana Tempo store and show traces; OTel itself is not a back end.
