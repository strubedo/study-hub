## Kustomize

**Kustomize** customises plain YAML **without templates**: you keep a *base* of ordinary manifests and layer *overlays* that patch them for each environment. It is built into kubectl (`kubectl apply -k`, `kubectl kustomize`) and also exists as the standalone `kustomize` binary (the one built into kubectl can lag behind it).

```text
webshop/
  base/
    deployment.yaml
    service.yaml
    kustomization.yaml
  overlays/
    dev/kustomization.yaml
    prod/
      kustomization.yaml
      replicas-patch.yaml
```

```yaml
# base/kustomization.yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
resources:
- deployment.yaml
- service.yaml
```

```yaml
# overlays/prod/kustomization.yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
namespace: prod
namePrefix: prod-
labels:
- pairs:
    env: prod
  includeSelectors: true
resources:
- ../../base
images:
- name: registry.example.com/example/webshop
  newTag: 1.4.3
patches:
- path: replicas-patch.yaml
configMapGenerator:
- name: webshop-config
  literals:
  - LOG_LEVEL=warn
```

```yaml
# overlays/prod/replicas-patch.yaml  (strategic merge patch)
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 5
```

```bash
kubectl kustomize overlays/prod        # render to stdout (same as: kustomize build overlays/prod)
kubectl apply -k overlays/prod         # render and apply
kubectl delete -k overlays/prod
```

Common fields: `resources`, `namespace`, `namePrefix`/`nameSuffix`, `labels`/`commonLabels` (older), `commonAnnotations`, `images` (retag without editing manifests), `patches` (strategic-merge or JSON 6902), `configMapGenerator`/`secretGenerator` (generated names carry a content hash, so a changed ConfigMap triggers a rollout).

| | Helm | Kustomize |
|---|---|---|
| Approach | Go **templates** plus values, packaged as charts | Template-free **patching** of base YAML |
| Distribution | Repositories, versioned charts, dependencies | A Git directory |
| Lifecycle | Tracks **releases**: history, rollback, uninstall | None; relies on `kubectl apply` (and `--prune`) or GitOps |
| Tooling | `helm` CLI | `kubectl apply -k`, `kustomize` |

They combine: GitOps tools can render a Helm chart and then patch the output with Kustomize.

## GitOps and continuous delivery tools

**GitOps** means Git is the single source of truth for the desired cluster state, and an agent **inside the cluster pulls** from Git and reconciles continuously. Benefits: audited changes (pull requests), easy rollback (`git revert`), automatic **drift correction**, no CI credentials for the cluster. This contrasts with CI-driven *push* deployments, where a pipeline runs `kubectl apply` or `helm upgrade` from outside.

| | Flux CD | Argo CD |
|---|---|---|
| Model | A set of controllers (the GitOps Toolkit) with CRDs | A server with API, web UI and CLI (`argocd`) plus controllers |
| Main resources | `GitRepository`/`OCIRepository`/`HelmRepository` (sources), `Kustomization` (apply a path), `HelmRelease` | `Application` (repo path or chart -> destination cluster/namespace), `AppProject` |
| Controllers | source-controller, kustomize-controller, helm-controller, notification-controller | application-controller, repo-server, API server |
| Setup | `flux bootstrap github ...` installs Flux and commits its own manifests to Git | Install manifests/Helm chart, then create `Application` objects |
| Status | `flux get kustomizations` | UI and `argocd app get`; **Synced/OutOfSync** and **Healthy/Degraded** |
| Renders | Plain YAML, Kustomize, Helm | Plain YAML, Kustomize, Helm, Jsonnet |

Both are CNCF graduated projects, work with Helm and Kustomize, support automated sync, pruning of resources deleted from Git, and self-healing of manual changes (Argo CD: `syncPolicy.automated` with `selfHeal` and `prune`).

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: webshop
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://git.example.com/platform/webshop-config.git
    targetRevision: main
    path: overlays/prod
  destination:
    server: https://kubernetes.default.svc
    namespace: prod
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
```

> **Exam tip:** Remember the keywords: **Flux** = GitOps Toolkit controllers (`flux` CLI, `Kustomization`, `HelmRelease`); **Argo CD** = `Application` CRD, UI, sync status. Both are *pull-based*, the cluster side agent fetches from Git.

> **Watch out:** With GitOps, `kubectl edit` on a live object is reverted by self-heal. Change Git instead.

## Lab it yourself

Create the base/overlay layout above for a trivial nginx Deployment. Run `kubectl kustomize overlays/prod` and read the output, then `kubectl apply -k overlays/prod` and check that names carry the prefix and the replica count is 5. For GitOps, install Argo CD in a kind cluster (`kubectl create namespace argocd` and apply the project's install manifest) or `flux bootstrap` against a private Git repo, and make a change by pushing a commit rather than touching the cluster.

## Key takeaways

- Kustomize patches plain YAML using a `kustomization.yaml` with bases and overlays; no templating language.
- `kubectl kustomize DIR` renders, `kubectl apply -k DIR` applies.
- Helm is template + release management; Kustomize is overlay patching; they can be combined.
- GitOps: Git holds desired state and an in-cluster agent pulls and reconciles it, correcting drift.
- Flux CD: toolkit controllers with `GitRepository`, `Kustomization`, `HelmRelease`; Argo CD: `Application` objects with UI and sync status.
- Both Flux and Argo CD are CNCF graduated and deploy plain YAML, Kustomize and Helm.
