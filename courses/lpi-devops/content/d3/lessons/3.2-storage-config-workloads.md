## Persistent storage

Container filesystems vanish with the Pod. Persistent data uses three objects:

* **PersistentVolume (PV):** a piece of storage in the cluster (cluster-scoped), created by an admin or **dynamically provisioned**.
* **PersistentVolumeClaim (PVC):** a namespaced *request* for storage by size and access mode. A Pod uses the PVC, never the PV directly.
* **StorageClass:** describes a class of dynamically provisioned storage ("fast-ssd", "standard"). A PVC naming a `storageClassName` makes the provisioner create a matching PV; one PVC binds to one PV (1:1).

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: db-data
  namespace: prod
spec:
  accessModes: [ReadWriteOnce]
  storageClassName: standard
  resources:
    requests:
      storage: 10Gi
```

Using it from a Pod template:

```yaml
    spec:
      containers:
      - name: db
        image: postgres:16
        volumeMounts:
        - name: data
          mountPath: /var/lib/postgresql/data
      volumes:
      - name: data
        persistentVolumeClaim:
          claimName: db-data
```

| Access mode | Short | Meaning |
|---|---|---|
| `ReadWriteOnce` | RWO | Read-write by a single **node** (several Pods on that node can share it) |
| `ReadOnlyMany` | ROX | Read-only by many nodes |
| `ReadWriteMany` | RWX | Read-write by many nodes (needs NFS, CephFS or similar) |
| `ReadWriteOncePod` | RWOP | Read-write by a single **Pod** in the whole cluster |

```text
$ kubectl get pvc,pv
NAME                            STATUS   VOLUME      CAPACITY   ACCESS MODES   STORAGECLASS
persistentvolumeclaim/db-data   Bound    pvc-3a1f..  10Gi       RWO            standard
```

PVC status: `Pending` (no matching PV or provisioner yet), `Bound`, `Lost`. The PV **reclaim policy** decides what happens after the claim is deleted: `Delete` (default for dynamic provisioning, storage removed) or `Retain` (data kept for manual cleanup). Other volume kinds: `emptyDir` (scratch space that lives as long as the Pod), `configMap`, `secret`, `hostPath` (node directory; avoid in production).

> **Exam tip:** Deleting a Pod does not delete its PVC; data survives. RWO is a *node*-level restriction, not a Pod one.

## ConfigMaps

A **ConfigMap** (`v1`) stores non-confidential configuration as key/value pairs (up to 1 MiB), decoupling configuration from the image.

```bash
kubectl create configmap webshop-config --from-literal=LOG_LEVEL=info --from-file=app.properties
```

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: webshop-config
data:
  LOG_LEVEL: info
  app.properties: |
    cache.ttl=60
```

Consumption in a Pod spec:

```yaml
    env:
    - name: LOG_LEVEL
      valueFrom:
        configMapKeyRef: {name: webshop-config, key: LOG_LEVEL}
    envFrom:
    - configMapRef: {name: webshop-config}     # every key becomes a variable
    volumeMounts:
    - {name: cfg, mountPath: /etc/webshop}     # each key becomes a file
  volumes:
  - name: cfg
    configMap: {name: webshop-config}
```

Files projected from a mounted ConfigMap are refreshed eventually when the ConfigMap changes; **environment variables are fixed when the container starts**, so a restart (`kubectl rollout restart`) is needed for them.

## Secrets

A **Secret** (`v1`) has the same shape as a ConfigMap but is meant for passwords, tokens and keys. The `data` field holds **base64-encoded** values; `stringData` accepts plain text and is converted on write. Common `type`s: `Opaque` (default), `kubernetes.io/tls`, `kubernetes.io/dockerconfigjson` (registry pull credentials, used via `imagePullSecrets`), `kubernetes.io/basic-auth`.

```bash
kubectl create secret generic db-cred --from-literal=password='S3cret!'
kubectl get secret db-cred -o jsonpath='{.data.password}' | base64 -d
```

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: db-cred
type: Opaque
data:
  password: UzNjcmV0IQ==
```

Pods consume Secrets like ConfigMaps (`secretKeyRef`, `secretRef`, or a `secret` volume).

> **Watch out:** **Base64 is encoding, not encryption.** Anyone with API read access to the Secret (or who reads etcd) can decode it. Real protection: RBAC limiting `get`/`list` on Secrets, **encryption at rest** for etcd (an `EncryptionConfiguration` on the API server), an external secret store or sealed/encrypted GitOps secrets, and never committing Secret manifests with real values.

## Other workload controllers (awareness)

| Kind (apiVersion) | Purpose | Key points |
|---|---|---|
| **DaemonSet** (`apps/v1`) | One Pod on every (or each selected) node | Log collectors, node monitoring agents, CNI/storage agents. No `replicas` field; new nodes automatically get a Pod |
| **StatefulSet** (`apps/v1`) | Stateful apps needing stable identity | Pods named `name-0`, `name-1`, ... with stable DNS (via a headless Service named in `serviceName`), ordered start/stop, and a separate PVC per Pod from `volumeClaimTemplates` |
| **Job** (`batch/v1`) | Run to completion | `completions`, `parallelism`, `backoffLimit` (retries, default 6); `restartPolicy` must be `OnFailure` or `Never` |
| **CronJob** (`batch/v1`) | Jobs on a schedule | `schedule` in cron syntax (`"0 2 * * *"`), `concurrencyPolicy` (`Allow` default, `Forbid`, `Replace`), `successfulJobsHistoryLimit` 3 and `failedJobsHistoryLimit` 1 by default; `timeZone` optional |

```yaml
apiVersion: batch/v1
kind: CronJob
metadata:
  name: nightly-report
spec:
  schedule: "0 2 * * *"
  concurrencyPolicy: Forbid
  jobTemplate:
    spec:
      backoffLimit: 3
      template:
        spec:
          restartPolicy: OnFailure
          containers:
          - name: report
            image: registry.example.com/example/webshop-report:1.4.2
            command: ["/bin/report", "--daily"]
```

A CronJob creates a Job per run, and the Job creates the Pod. Trigger one manually with `kubectl create job manual-1 --from=cronjob/nightly-report`.

## Lab it yourself

Create a PVC and a Deployment of `postgres:16` mounting it (set `POSTGRES_PASSWORD` from a Secret created with `kubectl create secret generic`). Write data, delete the Pod, and confirm the data survived. Decode the Secret with `base64 -d` to prove it is not encrypted. Create a CronJob with schedule `"* * * * *"` running `busybox:1.36` `date`, watch `kubectl get jobs -w`, then delete it.

## Key takeaways

- A PVC requests storage and is bound to a PV (often dynamically via a StorageClass); Pods reference the PVC with `claimName`.
- Access modes: RWO (one node), ROX, RWX, RWOP (one Pod). Deleting a Pod does not delete the PVC.
- ConfigMaps hold plain configuration; Secrets hold sensitive values, base64-encoded but **not encrypted** by default.
- ConfigMaps and Secrets are injected as env vars (`valueFrom`, `envFrom`) or mounted as files; env vars need a restart to update.
- DaemonSet = Pod per node; StatefulSet = stable names and storage; Job = run to completion; CronJob = Job on a schedule.
- Jobs require `restartPolicy` `OnFailure` or `Never`.
