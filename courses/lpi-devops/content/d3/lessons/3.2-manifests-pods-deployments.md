## Declaring resources in YAML

Every manifest has four top-level fields. Several objects can live in one file separated by `---`.

| Field | Meaning |
|---|---|
| `apiVersion` | API group and version (`v1`, `apps/v1`, `batch/v1`, `networking.k8s.io/v1`) |
| `kind` | The resource type (`Pod`, `Deployment`, ...), case-sensitive |
| `metadata` | `name` (unique per kind and namespace), `namespace`, `labels`, `annotations` |
| `spec` | The desired state; fields depend on the kind (`status` is written by the cluster, never by you) |

**Labels** are key/value pairs used to *select* objects. **Annotations** hold non-identifying metadata that nothing selects on. Selectors link objects together: a Deployment finds its Pods and a Service finds its endpoints by label, not by name.

## Pods

A **Pod** is the smallest deployable unit: one or more containers that share a network namespace (one IP, containers reach each other on `localhost`) and can share volumes. Pods are **ephemeral and disposable**: when a Pod dies it is replaced by a new one with a new name and IP, never repaired in place. Do not run bare Pods for real applications because nothing recreates them; use a controller.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: webshop
  labels:
    app: webshop
spec:
  containers:
  - name: webshop
    image: registry.example.com/example/webshop:1.4.2
    ports:
    - containerPort: 8080
    resources:
      requests: {cpu: 100m, memory: 128Mi}
      limits: {memory: 256Mi}
    readinessProbe:
      httpGet: {path: /healthz, port: 8080}
  restartPolicy: Always
```

* `containerPort` is documentation; it does not publish anything. 
* **requests** are what the scheduler reserves; **limits** are enforced ceilings (exceeding the memory limit gets the container OOM-killed, CPU is throttled). `100m` is 0.1 CPU.
* `restartPolicy` (`Always` default, `OnFailure`, `Never`) is handled by the kubelet and applies to all containers in the Pod.
* **Probes:** `livenessProbe` failing makes the kubelet restart the container; `readinessProbe` failing removes the Pod from Service endpoints without restarting; `startupProbe` holds off the other two for slow starters.
* Multi-container patterns: **sidecar** (log shipper, proxy), **init containers** (`initContainers:` run to completion in order before the app containers start).
* Pod phases: `Pending`, `Running`, `Succeeded`, `Failed`, `Unknown`.

## ReplicaSets

A **ReplicaSet** keeps a stated number of identical Pods running by comparing Pods matching its `selector` with `replicas`. You rarely write one; a Deployment creates and manages ReplicaSets for you.

## Deployments

A **Deployment** (`apps/v1`) manages ReplicaSets to give declarative updates, scaling and rollback for stateless apps.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
  namespace: prod
spec:
  replicas: 3
  selector:
    matchLabels:
      app: webshop
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 25%
      maxUnavailable: 25%
  template:
    metadata:
      labels:
        app: webshop
    spec:
      containers:
      - name: webshop
        image: registry.example.com/example/webshop:1.4.2
        ports:
        - containerPort: 8080
```

Key rules:

* `spec.selector.matchLabels` **must match** `spec.template.metadata.labels`, otherwise the API server rejects the Deployment. The selector is **immutable** after creation (in `apps/v1`).
* `template` is the Pod blueprint. **Only a change to the template** (image, env, resources) creates a new ReplicaSet and a rollout. Changing `replicas` alone does not.
* Pods are named `<deployment>-<ReplicaSet hash>-<random>`, for example `web-6d8f9c7b5-x2k4p`.
* `replicas` defaults to 1.

### Scaling

```bash
kubectl scale deployment web --replicas=5      # imperative
# or edit spec.replicas in the file and: kubectl apply -f web.yaml
```

A HorizontalPodAutoscaler (`kubectl autoscale deployment web --min=2 --max=10 --cpu-percent=70`) adjusts replicas automatically from metrics (awareness only).

### Rolling updates

The default strategy is **RollingUpdate**: the Deployment creates a new ReplicaSet, scales it up and the old one down in steps.

| Field | Default | Meaning |
|---|---|---|
| `maxSurge` | 25% | Extra Pods allowed above `replicas` during the update (percentage rounds **up**, or an absolute number) |
| `maxUnavailable` | 25% | Pods allowed below `replicas` that may be unavailable (percentage rounds **down**) |

With 4 replicas and defaults: at most 5 Pods exist (surge 1) and at least 3 are available (unavailable 1). `strategy.type: Recreate` kills all old Pods first, then creates new ones (downtime; use when two versions must never run together). Readiness probes make rolling updates safe because a new Pod only counts as available once ready.

```bash
kubectl set image deployment/web webshop=registry.example.com/example/webshop:1.4.3
kubectl rollout status deployment/web      # blocks until done or failed
kubectl rollout history deployment/web     # revisions (add --revision=2 for detail)
kubectl rollout undo deployment/web        # back to the previous revision
kubectl rollout undo deployment/web --to-revision=1
kubectl rollout pause deployment/web       # also: resume
kubectl rollout restart deployment/web     # new Pods with the same spec
```

```text
$ kubectl get rs
NAME             DESIRED   CURRENT   READY   AGE
web-5c7d4b9f66   0         0         0       12m     <- old, kept for rollback
web-6d8f9c7b5    3         3         3       2m      <- current
```

Old ReplicaSets (scaled to 0) are kept for rollback, up to `revisionHistoryLimit` (default 10). The CHANGE-CAUSE column in `rollout history` is empty unless the annotation `kubernetes.io/change-cause` is set.

> **Exam tip:** `kubectl rollout undo` rolls back to the previous ReplicaSet; it is the Kubernetes counterpart of `helm rollback`. A stuck rollout (new Pods never ready) stops at the surge/unavailable limit, leaving the old Pods serving traffic.

> **Watch out:** `kubectl delete pod` on a Deployment's Pod only triggers a replacement. To remove the app, delete the Deployment.

## Lab it yourself

Write the Deployment above (use `nginx:1.27` and port 80) and `kubectl apply -f`. Run `kubectl get rs,pods --show-labels`, then `kubectl set image` to `nginx:1.27.1` while running `kubectl get pods -w` in a second terminal to see surge and unavailable behaviour. Break it with a non-existent tag (`nginx:nope`), watch `rollout status` hang and the old Pods keep running, then `rollout undo`.

## Key takeaways

- A manifest is `apiVersion`, `kind`, `metadata`, `spec`; the cluster writes `status`.
- Labels and selectors connect objects; the Deployment selector must match its template labels.
- A Pod is one or more containers sharing network and volumes; Pods are replaceable, so use controllers.
- Requests are scheduling reservations; limits are enforced ceilings; readiness removes from Services, liveness restarts.
- A Deployment manages ReplicaSets; only template changes cause a rollout.
- Default RollingUpdate with `maxSurge` and `maxUnavailable` both 25%; `Recreate` is the alternative.
- `scale`, `set image`, `rollout status|history|undo|restart` are the day-to-day commands.
