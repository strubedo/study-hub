## What Kubernetes does

Kubernetes (K8s) is a container orchestrator. You **declare the desired state** (three replicas of `example/webshop:1.4.2`, reachable on port 80) and the cluster runs **control loops** that continuously compare the actual state with the desired state and correct the difference. Everything is an object in the Kubernetes API, and every object has a `spec` (what you want) and a `status` (what exists, written by the cluster).

## Cluster components

A cluster is a set of **nodes**. The **control plane** decides; **worker nodes** run the workloads.

| Component | Where | Job |
|---|---|---|
| `kube-apiserver` | control plane | The only front door: a REST API that authenticates, authorises, validates and persists every request. Every other component and `kubectl` talk to it (HTTPS, default port 6443) |
| `etcd` | control plane | Consistent key-value store holding all cluster state. **Only the API server talks to etcd** (client port 2379) |
| `kube-scheduler` | control plane | Watches for Pods with no node and picks a node, using resource requests, node selectors, affinity, taints and tolerations |
| `kube-controller-manager` | control plane | Runs the built-in controllers (Deployment/ReplicaSet, Node, Job, EndpointSlice, ...) as reconcile loops |
| `cloud-controller-manager` | control plane (cloud setups) | Integrates with a cloud provider: load balancers, node lifecycle, routes |
| `kubelet` | every node | Agent that makes the containers described in assigned Pod specs actually run, and reports status. Talks to the runtime through the **CRI** |
| `kube-proxy` | every node | Programs iptables/IPVS (or nftables) rules that implement Service virtual IPs |
| Container runtime | every node | **containerd** or **CRI-O**. Docker Engine itself is not a Kubernetes runtime since `dockershim` was removed in 1.24 (images built with Docker still run fine) |

```text
kubectl / controllers / kubelets  -->  kube-apiserver  <-->  etcd
                                            ^
                scheduler (assigns Pods to nodes), controller-manager (reconciles)
node:  kubelet --> containerd/CRI-O --> containers      kube-proxy --> Service rules
```

> **Exam tip:** The scheduler only *decides* where a Pod goes (it writes the node name through the API server); the **kubelet** on that node starts the containers. The controller manager makes the Deployment's ReplicaSet and Pods exist; it does not place them.

> **Watch out:** Losing etcd without a backup loses the cluster's state, not the running containers. Back up etcd (`etcdctl snapshot save`) on self-managed clusters.

## Namespaces and API basics

Most objects live in a **namespace** (`dev`, `prod`), which scopes names, quotas and access rules. Namespaces: `default`, `kube-system` (cluster components), `kube-public`, `kube-node-lease`. Some objects are cluster-scoped (Nodes, PersistentVolumes, StorageClasses, Namespaces themselves). Every object has `apiVersion`, `kind`, `metadata` (name, namespace, labels, annotations) and usually `spec`. The group/version tells you where the kind lives:

| Kind | apiVersion |
|---|---|
| Pod, Service, ConfigMap, Secret, PersistentVolumeClaim, Namespace | `v1` |
| Deployment, ReplicaSet, StatefulSet, DaemonSet | `apps/v1` |
| Job, CronJob | `batch/v1` |
| Ingress | `networking.k8s.io/v1` |

## Connecting kubectl: kubeconfig and contexts

`kubectl` learns which cluster to call, and as whom, from a **kubeconfig** file. The default is **`~/.kube/config`**. The `KUBECONFIG` environment variable can instead hold a colon-separated list of files (merged), and `--kubeconfig <file>` overrides both. A kubeconfig has three lists plus a pointer:

```yaml
apiVersion: v1
kind: Config
clusters:
- name: prod-cluster
  cluster:
    server: https://192.0.2.10:6443
    certificate-authority-data: LS0tLS1CRUdJTi...
users:
- name: alice
  user:
    client-certificate-data: LS0tLS1CRUdJTi...
    client-key-data: LS0tLS1CRUdJTi...
contexts:
- name: prod-admin
  context:
    cluster: prod-cluster
    user: alice
    namespace: prod
current-context: prod-admin
```

A **context** = cluster + user + (optional default) namespace. `current-context` selects the active one. The file contains credentials, so keep it mode `0600` and never commit it.

| Command | Effect |
|---|---|
| `kubectl config get-contexts` | List contexts; `*` marks the current one |
| `kubectl config current-context` | Print the active context name |
| `kubectl config use-context prod-admin` | Switch the active context (edits `current-context`) |
| `kubectl config set-context --current --namespace=dev` | Change the default namespace of the active context |
| `kubectl config set-context dev-alice --cluster=prod-cluster --user=alice --namespace=dev` | Create or modify a context |
| `kubectl config view` | Show the merged config (secrets redacted; `--raw` shows them) |
| `kubectl config set-cluster / set-credentials / delete-context` | Edit the other sections |

```text
$ kubectl config get-contexts
CURRENT   NAME         CLUSTER        AUTHINFO   NAMESPACE
          dev-alice   prod-cluster   alice     dev
*         prod-admin   prod-cluster   alice     prod
$ kubectl config use-context dev-alice
Switched to context "dev-alice".
```

Per command you can override with `--context`, `-n/--namespace` or `-A/--all-namespaces`.

> **Exam tip:** `use-context` changes which context is current; `set-context` creates or edits a context but does not switch to it (unless you use `--current` to edit the current one).

## Lab it yourself

Install `kind` or `minikube` (or k3s) for a throwaway cluster. Then run `kubectl cluster-info`, `kubectl get nodes`, `kubectl get pods -n kube-system` and identify the apiserver, etcd, scheduler and controller-manager Pods (on kubeadm/kind they run as static Pods on the control-plane node). Open `~/.kube/config` and find the three lists. Create a second context for namespace `dev` and switch with `use-context`.

## Key takeaways

- You declare desired state; controllers reconcile actual state toward it.
- The API server is the only component that talks to etcd, and everyone else talks to the API server.
- Scheduler picks the node, controller manager runs the control loops, kubelet runs the containers, kube-proxy implements Services.
- Kubernetes runs containers through a CRI runtime (containerd, CRI-O); dockershim is gone since 1.24.
- apiVersions: `v1` (Pod, Service, ConfigMap, Secret, PVC), `apps/v1` (Deployment, ReplicaSet, StatefulSet, DaemonSet), `batch/v1` (Job, CronJob), `networking.k8s.io/v1` (Ingress).
- kubeconfig default `~/.kube/config`; `KUBECONFIG` env var or `--kubeconfig` override it.
- A context bundles cluster, user and namespace; `use-context` switches, `current-context` prints, `get-contexts` lists.
