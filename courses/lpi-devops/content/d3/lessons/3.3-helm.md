## Concepts

**Helm** is the package manager for Kubernetes. Since Helm 3 it is a client-only CLI (the server-side Tiller of Helm 2 is gone); it talks to the cluster with your kubeconfig and the permissions of your user.

> **Helm 3 vs Helm 4:** Helm 4 was released in late 2025 and is the current major version. The commands in this lesson work in both. The differences to know: Helm 4 renames `--atomic` to `--rollback-on-failure` and `--force` to `--force-replace` (the old flags still work but print a deprecation warning), applies new releases with server-side apply by default (upgrades follow the release's previous apply method), adds a WebAssembly plugin system, and installs OCI charts by digest. Existing v2 charts keep working. The LPI objectives were written against Helm 3, so expect `--atomic` in exam wording.

| Term | Meaning |
|---|---|
| **Chart** | A package: a directory or `.tgz` of templates plus defaults |
| **Release** | One installed instance of a chart in a cluster, with a name and a revision number. The same chart can be installed many times under different release names |
| **Values** | The configuration that fills the chart's templates; defaults come from the chart's `values.yaml` |
| **Repository** | An HTTP server (or OCI registry) hosting charts, with an index |
| **Revision** | Each install/upgrade/rollback of a release creates a new revision; Helm stores release state as Secrets (type `helm.sh/release.v1`) in the release's namespace |

Chart layout:

```text
webshop/
  Chart.yaml        # name, version (chart), appVersion, description, dependencies
  values.yaml       # default values
  templates/        # Go templates: deployment.yaml, service.yaml, _helpers.tpl, NOTES.txt
  charts/           # dependency sub-charts
```

A template reads values with `{{ .Values.image.tag }}`, release data with `{{ .Release.Name }}` and chart data with `{{ .Chart.AppVersion }}`:

```yaml
# templates/deployment.yaml (excerpt)
spec:
  replicas: {{ .Values.replicaCount }}
  template:
    spec:
      containers:
      - name: {{ .Chart.Name }}
        image: "{{ .Values.image.repository }}:{{ .Values.image.tag | default .Chart.AppVersion }}"
```

```yaml
# values.yaml
replicaCount: 2
image:
  repository: registry.example.com/example/webshop
  tag: ""
service:
  type: ClusterIP
```

## Working with repositories

```bash
helm repo add example https://charts.example.com
helm repo update
helm search repo webshop              # search added repositories
helm show values example/webshop      # print the chart's default values.yaml
helm pull example/webshop --untar     # download and unpack
```

## Install, list, upgrade, uninstall

```bash
helm install shop example/webshop -n prod --create-namespace      # release "shop"
helm install shop ./webshop -f prod-values.yaml --set replicaCount=3
helm list -n prod                     # releases in a namespace (-A all, --all adds failed/uninstalled)
helm status shop -n prod
helm upgrade shop example/webshop -n prod -f prod-values.yaml
helm upgrade --install shop example/webshop -n prod -f prod-values.yaml   # idempotent: install if absent
helm history shop -n prod
helm rollback shop 1 -n prod          # new revision with revision 1's content
helm uninstall shop -n prod           # remove the release and its resources
```

```text
$ helm list -n prod
NAME  NAMESPACE  REVISION  UPDATED                  STATUS    CHART          APP VERSION
shop  prod       2         2026-10-30 09:14:02 UTC  deployed  webshop-0.3.1  1.4.2
$ helm history shop -n prod
REVISION  UPDATED                  STATUS      CHART          APP VERSION  DESCRIPTION
1         2026-10-30 09:01:40 UTC  superseded  webshop-0.3.0  1.4.1        Install complete
2         2026-10-30 09:14:02 UTC  deployed    webshop-0.3.1  1.4.2        Upgrade complete
```

Notes:

* The **release name** is the first argument after `install` (or use `--generate-name`). Release names are unique per namespace.
* Without `-n`, Helm uses the namespace of the current kube context. `--create-namespace` creates a missing namespace.
* `helm rollback RELEASE [REVISION]` without a revision goes to the previous one; the rollback itself becomes a **new** revision.
* `helm uninstall` removes the release history too, unless `--keep-history` is given. (Helm 3 removed Helm 2's `delete --purge` and `install --name` forms.)
* Useful safety flags: `--dry-run` (render and validate without applying), `--atomic` (roll back automatically if the upgrade fails; implies wait; named `--rollback-on-failure` in Helm 4), `--wait`, `--timeout`.
* Debug without a cluster: `helm template shop ./webshop -f values.yaml` renders manifests locally; `helm lint ./webshop` checks the chart; `helm get values shop` shows the user-supplied values of a release; `helm get manifest shop` the rendered YAML.

## Custom values

Values merge from lowest to highest priority:

1. The chart's `values.yaml` (defaults)
2. Files passed with `-f`/`--values`, applied **left to right** (the last file wins)
3. `--set key=value` (and `--set-string`, `--set-file`), which beat any `-f` file

```bash
helm upgrade --install shop example/webshop -f base.yaml -f prod.yaml \
  --set image.tag=1.4.3 --set service.type=NodePort
helm upgrade shop example/webshop --reuse-values --set replicaCount=5
```

`--set` uses dotted paths (`image.tag=1.4.3`), lists as `{a,b}` or `key[0]=a`, and escapes commas with a backslash. Maps merge key by key between layers; lists are replaced as a whole.

> **Exam tip:** On `helm upgrade`, values you passed during install are **not** remembered unless you give them again (or use `--reuse-values`). Keeping all overrides in a Git-tracked `-f` file avoids that trap.

> **Watch out:** `helm install` fails if the release name already exists; `helm upgrade` fails if it does not. That is why CI pipelines use `helm upgrade --install`.

## Lab it yourself

Install Helm (3 or 4) and use a kind/minikube cluster. `helm create webshop` generates a sample chart. Run `helm lint webshop`, `helm template shop webshop`, then `helm install shop webshop` and `helm list`. Upgrade with `--set replicaCount=3`, check `kubectl get pods`, `helm history shop`, then `helm rollback shop 1` and `helm uninstall shop`. Package it with `helm package webshop`.

## Key takeaways

- Chart = package, release = installed instance, values = configuration, repository = chart source.
- Chart contents: `Chart.yaml`, `values.yaml`, `templates/`, optional `charts/`.
- `helm install NAME CHART`, `helm list`, `helm upgrade`, `helm rollback NAME REV`, `helm uninstall NAME`.
- `helm upgrade --install` installs or upgrades in one idempotent command.
- Value precedence: `values.yaml` < `-f` files (in order) < `--set`.
- Release history is kept as Secrets in the namespace; rollback creates a new revision.
- `--dry-run`, `helm template` and `helm lint` check a chart without changing the cluster.
