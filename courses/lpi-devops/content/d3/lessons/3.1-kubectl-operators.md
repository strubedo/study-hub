## kubectl command shape

`kubectl [command] [TYPE] [NAME] [flags]`. Types have short names (`po`, `deploy`, `svc`, `cm`, `pvc`, `ns`, `ing`, `rs`, `ds`, `sts`, `cj`). Useful global flags: `-n <ns>`, `-A`, `-o <format>`, `-l <selector>`, `--context`.

## Getting information

| Command | Use |
|---|---|
| `kubectl get pods` | Table of Pods in the current namespace |
| `kubectl get pods -n dev -o wide` | Another namespace; adds node and Pod IP |
| `kubectl get pods -A` | All namespaces |
| `kubectl get pods -l app=webshop --show-labels` | Filter by label selector |
| `kubectl get deploy web -o yaml` (`-o json`, `-o name`, `-o jsonpath='{.status.podIP}'`) | Full object or one field |
| `kubectl get pods -w` | Watch changes |
| `kubectl get all` | Common namespaced workload kinds (not literally everything; ConfigMaps and Secrets are excluded) |
| `kubectl describe pod web-6d8f9c7b5-x2k4p` | Human-readable detail **and the Events** at the bottom: first stop for troubleshooting scheduling and image-pull errors |
| `kubectl logs web-6d8f9c7b5-x2k4p` | Container STDOUT/STDERR. `-f` follow, `--tail 50`, `--previous` (last crashed instance), `-c <container>` for multi-container Pods, `-l app=webshop` for a selector |
| `kubectl exec -it web-6d8f9c7b5-x2k4p -- sh` | Run a command in a container; `--` separates kubectl options from the command; `-c` picks the container |
| `kubectl explain pod.spec.containers` | Built-in schema documentation for any field (`--recursive` for the whole tree) |
| `kubectl api-resources` | Every kind, short name, scope and apiVersion the cluster serves |
| `kubectl top pods` | CPU/memory (needs metrics-server) |

```text
$ kubectl get pods -n prod -o wide
NAME                   READY   STATUS    RESTARTS   AGE   IP           NODE
web-6d8f9c7b5-8hq7z    1/1     Running   0          5m    10.244.1.7   node-a
web-6d8f9c7b5-x2k4p    1/1     Running   0          5m    10.244.2.4   node-b
db-0                   0/1     Pending   0          2m    <none>       <none>
```

`READY 1/1` is ready containers over total containers. Common `STATUS` values: `Pending` (not scheduled or pulling images), `ContainerCreating`, `Running`, `Completed`, `CrashLoopBackOff` (container keeps exiting; check `logs --previous`), `ImagePullBackOff`/`ErrImagePull` (wrong image name, tag or credentials), `Error`, `Terminating`.

## Creating and changing resources

**Imperative** commands act directly; **declarative** commands apply files.

| Command | Behaviour |
|---|---|
| `kubectl create deployment web --image=example/webshop:1.4.2 --replicas=3` | Creates a Deployment |
| `kubectl create namespace dev`, `create configmap`, `create secret generic`, `create job`, ... | Create specific kinds imperatively |
| `kubectl create -f web.yaml` | Creates from file; **fails with AlreadyExists** if the object exists |
| `kubectl apply -f web.yaml` (or a directory, `-f dir/`, or a URL) | Creates the object or **updates it to match the file**; the declarative workflow. Records the last applied config in an annotation for three-way merging; `--server-side` uses server-side apply |
| `kubectl apply -k overlays/prod` | Apply a Kustomize directory (lesson 3.3) |
| `kubectl run tmp --image=busybox:1.36 -it --rm -- sh` | **Creates a single Pod** (not a Deployment, no replicas, since 1.18) |
| `kubectl expose deployment web --port=80 --target-port=8080` | Creates a **Service** selecting that Deployment's Pod labels. `--type=NodePort|LoadBalancer`, `--name` |
| `kubectl scale deployment web --replicas=5` | Change replica count (works on Deployments, ReplicaSets, StatefulSets) |
| `kubectl set image deployment/web web=example/webshop:1.4.3` | Change a container image: `CONTAINER=IMAGE`; triggers a rolling update. Also `set env`, `set resources` |
| `kubectl edit deployment web` | Opens the live object in `$EDITOR` (`KUBE_EDITOR`); saved changes are applied immediately |
| `kubectl label pod web-x app=webshop`, `annotate` | Edit labels/annotations |
| `kubectl delete -f web.yaml`, `delete pod web-x`, `delete deploy web` | Delete. A Pod owned by a ReplicaSet is recreated; delete the Deployment to stop it |
| `kubectl rollout status\|history\|undo\|restart deployment/web` | Manage rollouts (lesson 3.2) |
| `kubectl diff -f web.yaml` | Show what `apply` would change |
| `--dry-run=client -o yaml` | Generate a manifest without creating anything |

```bash
kubectl create deployment web --image=example/webshop:1.4.2 --replicas=2 \
  --dry-run=client -o yaml > web.yaml        # scaffold a manifest
kubectl apply -f web.yaml
kubectl expose deployment web --port=80 --target-port=8080 --type=NodePort
kubectl scale deployment web --replicas=4
kubectl set image deployment/web webshop=example/webshop:1.4.3
kubectl rollout status deployment/web
```

> **Exam tip:** `kubectl run` makes only a **Pod**. If an item says "create a Deployment" the answer is `kubectl create deployment`. `apply` is idempotent; `create` is not.

> **Watch out:** `kubectl edit` and `kubectl set` change live objects. If the manifest in Git is not updated, the next `kubectl apply` of the old file overwrites the change (configuration drift).

## Troubleshooting order

1. `kubectl get pods` for the status. 2. `kubectl describe pod` and read the Events. 3. `kubectl logs` (add `--previous` after a crash). 4. `kubectl exec -it ... -- sh` to look inside. 5. `kubectl get events --sort-by=.metadata.creationTimestamp` for the namespace timeline.

## Operators

An **Operator** is a pattern that encodes a human operator's knowledge for a stateful application as software. It consists of a **CustomResourceDefinition (CRD)**, which adds a new kind to the API (for example `Postgres` or `Prometheus`), plus a **custom controller** running in the cluster that watches those custom resources and reconciles real Pods, Services, backups and upgrades to match. You then create an application with a short manifest and the operator handles the details:

```yaml
apiVersion: db.example.com/v1
kind: Postgres
metadata:
  name: webshop-db
spec:
  version: "16"
  replicas: 3
  backup:
    schedule: "0 2 * * *"
```

`kubectl get crd` lists the custom kinds; they then work with `get`, `describe`, `apply` like built-in ones. Operators are installed from manifests, Helm charts or OperatorHub-style catalogs. For the exam you need awareness only: operator = CRD + controller.

## Lab it yourself

On a kind or minikube cluster: `kubectl create deployment web --image=nginx:1.27 --replicas=2`, `kubectl expose deployment web --port=80 --type=NodePort`, `kubectl get svc,pods -o wide`, `kubectl scale deployment web --replicas=4`, `kubectl set image deployment/web nginx=nginx:1.27.1`, `kubectl explain deployment.spec.strategy`. Use `kubectl run tmp --rm -it --image=busybox:1.36 -- wget -qO- web` to prove the Service DNS name works.

## Key takeaways

- `get` lists, `describe` shows detail and Events, `logs` reads container output, `exec -it ... -- cmd` runs commands inside, `explain` documents fields.
- `-n`, `-A`, `-l`, `-o wide|yaml|json|jsonpath` shape the output.
- `apply -f` is declarative and repeatable; `create -f` fails if the object exists.
- `kubectl run` creates just a Pod; `create deployment` creates a Deployment.
- `expose` creates a Service, `scale` sets replicas, `set image CONTAINER=IMAGE` triggers a rolling update, `edit` changes the live object.
- Troubleshoot with get, describe (Events), logs (`--previous`), exec.
- An Operator is a CRD plus a custom controller that automates running an application.
