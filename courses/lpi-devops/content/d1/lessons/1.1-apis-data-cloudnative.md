## APIs: REST and JSON

An **API** is the contract through which services and clients interact. The exam's reference style is **REST** (Representational State Transfer) over HTTP carrying **JSON**.

| REST idea | Detail |
|-----------|--------|
| Resources | Nouns identified by URLs, e.g. `/orders/1042` |
| Methods | `GET` read (safe, idempotent), `POST` create/non-idempotent action, `PUT` replace (idempotent), `PATCH` partial update, `DELETE` remove (idempotent) |
| Stateless | Each request carries everything needed; the server keeps no client session between requests |
| Representations | Usually JSON, selected with `Content-Type` / `Accept` headers |
| Status codes | `200 OK`, `201 Created`, `204 No Content`, `400 Bad Request`, `401 Unauthorized`, `403 Forbidden`, `404 Not Found`, `409 Conflict`, `429 Too Many Requests`, `500 Internal Server Error`, `503 Service Unavailable` |
| Versioning | In the URL (`/v2/orders`) or a header; never break existing clients silently |

```text
POST /v1/orders HTTP/1.1
Host: api.example.com
Content-Type: application/json

{"sku": "WS-100", "quantity": 2}

HTTP/1.1 201 Created
Location: /v1/orders/1042
```

**JSON** (JavaScript Object Notation) has objects `{}`, arrays `[]`, strings (double quotes only), numbers, `true`/`false` and `null`. No comments, no trailing commas. Other styles to recognise: SOAP (XML envelopes, older SOA), gRPC (HTTP/2 + Protocol Buffers), GraphQL (client chooses fields from a single endpoint). Machine-readable API descriptions use the OpenAPI specification.

> **Watch out:** `PUT` and `DELETE` are idempotent (repeating them leaves the same state); `POST` is not. This matters for safe retries.

## Data storage, status and sessions

Services should be **stateless**: no instance holds data that another instance or a restarted instance would need. Where state lives instead:

| State | Where it belongs |
|-------|------------------|
| Business data | Database (relational or NoSQL) |
| Files and uploads | Object storage |
| User session | Signed token on the client (e.g. a JWT) or a shared session store such as Redis; avoid sticky sessions if you can |
| Caches | Shared cache (Redis, Memcached); losing it must not lose data |
| Service status | Health endpoints (`/healthz`, `/ready`) that orchestrators and load balancers poll |

**Sticky sessions** (the load balancer pins a client to one instance) work, but if that instance dies the session is lost and scaling becomes uneven. A stateless service with an external session store scales and recovers freely.

## Cloud native applications

Cloud native applications are built to exploit elastic, automated platforms. Characteristics you should know:

* Built from loosely coupled services, packaged in **containers**.
* Dynamically orchestrated and **scalable horizontally**.
* Configuration from the **environment**, not baked into the image (the twelve-factor app: *config in the environment*, *logs as event streams to stdout*, *stateless processes*, *disposable processes with fast start-up and graceful shutdown*, *dev/prod parity*, backing services as attached resources).
* Observable (metrics, logs, traces) and automated (CI/CD, declarative infrastructure).
* Resilient: designed to tolerate the failure of any instance.

### Designing software for containers

* One main process per container; log to stdout/stderr and let the platform collect it.
* Read configuration and secrets from environment variables or mounted files, never from a hard-coded path.
* Keep the filesystem disposable; write persistent data to a volume or an external service.
* Handle `SIGTERM` and shut down gracefully; start quickly; expose a health check.
* Build small, versioned, immutable images.

### Designing for cloud services

Use managed services (databases, queues, object storage) instead of running your own where practical, authenticate with roles/identities rather than long-lived keys, expect transient errors (retry with back-off), and avoid assumptions about the instance's IP or hostname.

## Database schema updates and migrations

A **schema migration** is a versioned, scripted change to the database structure (add a column, create an index). Tools such as Flyway, Liquibase, Alembic or Rails migrations store ordered migration files in the repository and record applied versions in a table, so every environment reaches the same schema.

Awareness points:

* Keep migrations in source control and run them in the pipeline, not by hand.
* With multiple instances deploying in rolling fashion, old and new code run at once against one schema. Use the **expand/contract** pattern: first *expand* (add the new nullable column, keep the old one), deploy code that handles both, migrate data, then *contract* (drop the old column) in a later release.
* Destructive changes (drop/rename) break the previous version and make rollback hard; large table rewrites can lock the table.
* Always take or verify a backup, and test migrations on a copy of production-like data.

## Lab it yourself

1. Start a throwaway API: `python3 -m http.server` for static, or a small Flask/Express app. Call it with `curl -i -X POST -H 'Content-Type: application/json' -d '{"sku":"WS-100"}' http://192.0.2.10:8080/v1/orders`.
2. Pipe a JSON response through `jq .` and extract a field with `jq -r .sku`.
3. With SQLite, write `001_create.sql` and `002_add_email.sql` and a script that applies unapplied files in order while recording them in a `schema_version` table.

## Key takeaways

* REST: resources as URLs, standard HTTP methods, stateless requests, JSON bodies and meaningful status codes.
* GET/PUT/DELETE are idempotent; POST is not.
* Stateless services keep data in databases, files in object storage and sessions in tokens or a shared store.
* Cloud native = containerised, loosely coupled, orchestrated, observable, automated; config comes from the environment.
* Containers: one process, logs to stdout, graceful SIGTERM, disposable filesystem.
* Migrations are versioned scripts in source control; use expand/contract so old and new code can coexist.
