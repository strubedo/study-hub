## From monolith to services

A **monolith** is built, deployed and scaled as one unit: one codebase, usually one process, one database. It is simple to develop and debug at first, but every change redeploys everything, one hot component forces you to scale the whole thing, and one bug can take it all down.

A **service-based application** splits functionality into separately deployable services that talk over the network. Related terms the exam uses:

| Term | Meaning |
|------|---------|
| **SOA** (Service Oriented Architecture) | Older, enterprise style: coarse-grained services that expose contracts and are often wired together through a central integration layer such as an enterprise service bus (ESB), commonly with SOAP/XML |
| **Microservices** | Small services, each owning one business capability and its own data, deployed independently, usually communicating through lightweight HTTP/REST APIs or messaging |
| **Loose coupling** | A service depends only on another service's published interface, not on its internals, its database or its deployment details |
| **High cohesion** | Things that change together live together inside one service |
| **Immutable server** | A server or container is never patched in place; to change it you build a new image and replace the old instance |

> **Exam tip:** SOA and microservices both decompose an application into services. The usual distinction: SOA favours reusable, coarse services with shared middleware; microservices favour small, independently deployable services, each with its own data store and lifecycle ("smart endpoints, dumb pipes").

## Properties a service must have

LPI expects you to reason about how services handle:

* **Persistence**: state that must survive a restart belongs in a database or object store, never on the instance's local disk.
* **Sessions and status**: see the next lesson (stateless design).
* **Transactions**: inside a monolith one database transaction keeps data consistent. Across services there is no shared transaction; you use patterns such as sagas (a sequence of local transactions with compensating actions) and accept **eventual consistency**.
* **Concurrency**: many requests hit the same service at once; shared mutable state needs locking or optimistic concurrency (for example version numbers/ETags).
* **Availability and scaling**: run several instances behind a **load balancer**; *horizontal* scaling (more instances) is the cloud native default, *vertical* scaling (a bigger machine) has a ceiling.
* **Failure handling**: timeouts, retries with back-off, circuit breakers and health checks keep one failing dependency from cascading.
* **Messaging**: asynchronous communication through a queue or broker decouples producer and consumer in time (see 1.2).
* **Monitoring**: every service exposes health, metrics and logs (domain 4).

> **Watch out:** Microservices are not free. You trade code complexity for operational complexity: network latency, distributed debugging, versioned APIs, many deployments. Do not claim "microservices are always better".

## Immutable servers and infrastructure

With **immutable infrastructure** you never SSH in to fix a running instance. You change the image or definition, build a new artifact, deploy it, and discard the old one. Benefits: no configuration drift, reproducible environments, trivial rollback (redeploy the previous image), identical staging and production. Containers are the typical vehicle; the opposite is a **mutable server** (a "snowflake") that accumulates manual changes.

## Migrating monolithic legacy software

The exam asks for *awareness of risks* in migration and integration:

* **Big-bang rewrite** is risky: long time without value, requirements drift, and the old system keeps changing underneath you.
* The **strangler fig** approach routes selected functions (via a proxy/API gateway) to new services while the monolith keeps running, and shrinks the monolith step by step.
* Risks: tangled shared database (many modules write the same tables), hidden dependencies, distributed transactions replacing one local transaction, data migration and dual-write inconsistency, performance loss from in-process calls becoming network calls, and loss of institutional knowledge.
* An **anti-corruption layer** or adapter translates between the legacy model and the new service model so the legacy design does not leak in.
* Integration options: wrap the legacy system behind an API, use messaging, or share data (the last one couples you most tightly and is the most fragile).
* Often the first step is not splitting but **containerising the monolith** ("lift and shift"), which gives repeatable deployment without a redesign.

## Lab it yourself

1. Write a tiny two-endpoint HTTP service in any language that reads its listen port from the environment variable `PORT`.
2. Start two instances on different ports and put `nginx` or `haproxy` in front as a round-robin load balancer. Kill one instance and watch requests keep working.
3. Note what would break if the service stored uploads on local disk: the second instance cannot see them. That is why persistent state moves to external storage.

## Key takeaways

* A monolith deploys and scales as one unit; services deploy and scale independently.
* SOA = coarse, reusable services plus central middleware; microservices = small, independently deployable, own their data.
* Loose coupling means depending on interfaces, not internals.
* Immutable servers are replaced, never modified; this removes drift and simplifies rollback.
* Across services there are no shared transactions: expect eventual consistency and design for failure.
* Prefer horizontal scaling behind a load balancer.
* Migrate legacy systems incrementally (strangler fig), and watch the shared database and added network latency.
