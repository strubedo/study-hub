## Branches

```text
$ git branch                     # list local branches (* = current)
$ git branch -a                  # include remote-tracking branches
$ git branch -vv                 # with upstream and last commit
$ git switch -c feature/login    # create and switch (older: git checkout -b)
$ git switch main                # switch to an existing branch
$ git switch -                   # back to the previous branch
$ git switch --detach v1.4.2     # detached HEAD at a tag or commit
$ git branch -m old-name new-name
$ git branch -d feature/login    # delete if fully merged
$ git branch -D feature/login    # force delete, even if unmerged
```

## Tags

A **tag** is a fixed name for a commit, normally a release.

| Kind | Create | Notes |
|------|--------|-------|
| Lightweight | `git tag v1.4.2` | Just a ref to a commit |
| Annotated | `git tag -a v1.4.2 -m "Release 1.4.2"` | Full object with tagger, date, message; can be signed (`-s`); preferred for releases |

```text
$ git tag                        # list
$ git tag -a v1.4.2 -m "Release 1.4.2" 3f2a1c9    # tag an older commit
$ git show v1.4.2
$ git push origin v1.4.2         # tags are NOT pushed by a normal git push
$ git push origin --tags         # push all tags
$ git tag -d v1.4.2              # delete locally
$ git push origin --delete v1.4.2   # delete on the remote
```

## Merging

`git merge <branch>` integrates that branch into the **current** branch.

* **Fast-forward**: if the current branch is an ancestor of the other, Git just moves the pointer; no merge commit.
* **Three-way merge**: when both branches have diverged, Git uses the common ancestor and creates a **merge commit** with two parents.
* `git merge --no-ff feature` forces a merge commit even when a fast-forward is possible, preserving the fact that a feature branch existed.
* `git merge --squash feature` stages the combined changes without a merge commit or a link to the branch; you then run `git commit`.
* `git merge --abort` cancels a merge that stopped on conflicts.

```text
$ git switch main
$ git merge --no-ff feature/login -m "Merge feature/login"
Merge made by the 'ort' strategy.
```

### Conflicts

When both sides changed the same lines, the merge stops, files are marked `UU` (both modified) in `git status`, and Git writes conflict markers:

```text
<<<<<<< HEAD
timeout = 30
=======
timeout = 60
>>>>>>> feature/login
```

Between `<<<<<<< HEAD` and `=======` is your current branch's version; between `=======` and `>>>>>>> feature/login` is the incoming version. Resolve by editing the file to the final text and **removing all markers**, then:

```text
$ git add config.ini
$ git commit            # concludes the merge (or: git merge --continue)
```

`git checkout --ours file` / `--theirs file` (or `git restore --ours file`) pick a whole side; `git mergetool` launches a visual tool. With `merge.conflictStyle=diff3` the markers also show the base version.

## Rebase and cherry-pick

**Rebase** replays your commits on top of another base, giving a linear history:

```text
$ git switch feature/login
$ git rebase main                # replay feature commits onto the tip of main
# on conflict: fix, git add <file>, then
$ git rebase --continue          # or: git rebase --abort
$ git rebase -i HEAD~3           # interactively squash, reword, reorder, drop
```

Rebase **rewrites** commits (new hashes). Golden rule: do not rebase commits that others have already pulled. After rebasing a branch you had pushed, you need `git push --force-with-lease` (safer than `--force`: it refuses if the remote moved).

**Cherry-pick** copies the change made by one commit onto the current branch as a new commit:

```text
$ git cherry-pick 3f2a1c9         # one commit
$ git cherry-pick -x 3f2a1c9      # also record "(cherry picked from commit ...)"
$ git cherry-pick A..B            # range (excludes A)
$ git cherry-pick --continue      # / --abort after a conflict
```

Typical use: backport a bug fix to a release branch.

## Remote repositories

A **remote** is a named URL. `origin` is the default name given by `git clone`. **Remote-tracking branches** such as `origin/main` are local read-only copies recording where the remote branch was at your last fetch.

```text
$ git remote add origin https://git.example.com/example/webshop.git
$ git remote -v
$ git remote rename origin upstream
$ git remote set-url origin git@git.example.com:example/webshop.git
$ git remote remove upstream
$ git fetch origin               # download new objects and update origin/*; changes nothing in your branches
$ git fetch --prune              # also delete remote-tracking refs for branches removed on the remote
$ git pull                       # = git fetch + git merge (of the upstream branch)
$ git pull --rebase              # = git fetch + git rebase
$ git push -u origin main        # -u / --set-upstream links local main to origin/main
$ git push origin --delete feature/login
$ git branch --set-upstream-to=origin/main main
```

> **Exam tip:** `git fetch` never modifies your working tree or local branches; `git pull` does (it merges or rebases). A rejected push ("non-fast-forward") means the remote has commits you lack: fetch/pull first, do not force.

## Submodules

A **submodule** embeds another repository at a path inside yours, pinned to one specific commit.

```text
$ git submodule add https://git.example.com/example/shared-ui.git libs/shared-ui
$ git commit -m "Add shared-ui submodule"       # records .gitmodules + the gitlink (mode 160000)
$ git clone --recurse-submodules https://git.example.com/example/webshop.git
$ git submodule update --init --recursive       # after a plain clone: fetch and check out the pinned commits
$ git submodule update --remote libs/shared-ui  # move to the tracked remote branch tip
```

`.gitmodules` (tracked) holds each submodule's path and URL. The parent stores only the commit hash, so a submodule checkout is a **detached HEAD**; after changing it you must commit inside the submodule, then commit the new pointer in the parent. A plain `git clone` leaves submodule directories empty until `git submodule update --init`.

## Lab it yourself

```text
$ git init --bare /tmp/origin.git
$ git clone /tmp/origin.git a && cd a
$ echo v1 > f && git add f && git commit -m one && git push -u origin HEAD
$ git switch -c topic && echo t >> f && git commit -am topic
$ git switch main && echo m >> f && git commit -am main
$ git merge topic            # conflict in f: edit, git add f, git commit
$ git tag -a v1.0.0 -m "first" && git push origin v1.0.0
```

## Key takeaways

* `git switch -c` creates a branch; `git switch --detach` checks out a commit; `-d` vs `-D` for deleting.
* Annotated tags (`git tag -a ... -m`) hold metadata; tags must be pushed explicitly.
* Fast-forward moves the pointer; `merge --no-ff` always makes a merge commit; `--squash` makes none.
* Conflict markers: `<<<<<<<` (current), `=======`, `>>>>>>>` (incoming); remove them, `git add`, then commit.
* Rebase rewrites history; never rebase shared commits. Cherry-pick copies single commits.
* `fetch` only downloads; `pull` = fetch + merge (or rebase with `--rebase`).
* Submodules pin a commit; use `git submodule add` and `git submodule update --init` (`--recursive` for nested).
