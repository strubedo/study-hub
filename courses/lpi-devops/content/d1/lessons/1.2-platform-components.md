## Service models: IaaS, PaaS, SaaS, FaaS

| Model | You manage | Provider manages | Examples |
|-------|------------|------------------|----------|
| **IaaS** (Infrastructure) | OS, runtime, application, data, network config | Hardware, virtualisation, physical network | Virtual machines, block storage, virtual networks (EC2-style, OpenStack) |
| **PaaS** (Platform / application runtime) | Application code and its data | OS, runtime, scaling, patching | App platforms (Cloud Foundry, Heroku-style), managed Kubernetes at the edge of PaaS |
| **SaaS** (Software) | Only your configuration and data | Everything else | Hosted email, CRM, hosted Git service |
| **FaaS** (Function) | Individual functions | Servers, scaling to zero, per-invocation billing | AWS Lambda-style, OpenFaaS, Knative |

FaaS ("serverless") runs short, event-triggered, stateless functions; you pay per execution. Watch for cold-start latency, execution time limits and no local persistent state. The higher the abstraction, the less you control and the less you operate.

## Object storage

Object storage keeps data as **objects** (data + metadata + unique key) in flat **buckets**, accessed over an HTTP API rather than a filesystem. **S3** is the de-facto API (Amazon S3 and compatible open source servers such as MinIO and Ceph RGW).

* Objects are written whole (replaced, not edited in place); access is by key like `images/logo.png` (the "folders" are just key prefixes).
* Very scalable and durable, cheap; ideal for backups, static assets, build artifacts, logs and data lakes.
* **ACLs** and bucket policies control access; buckets should be private by default. Pre-signed URLs grant time-limited access.
* Versioning and lifecycle rules (expire or archive old objects) are common features.

## Relational and NoSQL databases

**Relational (RDBMS)**: tables with a fixed schema, SQL, joins and **ACID** transactions. Open source: **MariaDB, MySQL, PostgreSQL**. Best for structured, consistent, related data. Scale mostly vertically, and read-scale with replicas.

**NoSQL**: umbrella for non-relational stores with flexible schemas and easier horizontal scaling, often trading strict consistency for availability (BASE, eventual consistency).

| Type | Example | Typical use |
|------|---------|-------------|
| Key-value | **Redis** | Cache, sessions, counters, queues |
| Document | **MongoDB** | JSON-like documents with varying structure |
| Time series | **InfluxDB** | Metrics and sensor data with timestamps |
| Search / analytics | **Elasticsearch**, **OpenSearch** | Full-text search, log analytics |
| Wide-column, graph | Cassandra, Neo4j | Large distributed writes; relationship queries |

> **Exam tip:** OpenSearch is the Apache 2.0 fork of Elasticsearch created after Elastic changed its licence; both appear in the LPI term list.

## Message brokers and queues

A **message broker** sits between producers and consumers so they are decoupled in time and load: a producer publishes and moves on, consumers process at their own pace, and the broker buffers bursts.

* **Queue** (point to point): each message is consumed by one consumer, which allows work distribution across workers.
* **Publish/subscribe (topic)**: each message is delivered to every subscriber.
* **Apache Kafka**: distributed, partitioned, durable **log**; consumers track an offset and can replay history; very high throughput, event streaming.
* **MQTT**: lightweight publish/subscribe protocol for IoT and constrained devices, with broker examples such as Mosquitto; has QoS levels 0, 1 and 2.
* Others: RabbitMQ (AMQP).
* Delivery semantics: at-most-once, at-least-once (consumers must be idempotent because duplicates occur), exactly-once (hard, limited).

## Big data services

Big data services process data too large or fast for one machine: distributed storage and processing (Hadoop/HDFS, Apache Spark), stream processing (Kafka, Flink), data warehouses and search/analytics engines (Elasticsearch/OpenSearch), often fed from object storage. Key concepts: volume, velocity, variety; batch vs stream processing; scale-out on commodity nodes; managed offerings run these as services.

## Content delivery networks (CDN)

A CDN caches content on **edge servers** geographically close to users. Benefits: lower latency, offloaded origin servers, absorbing traffic spikes and some DDoS protection, TLS termination at the edge. Static content is cached according to `Cache-Control` headers and TTLs; dynamic content can be accelerated too. Cached objects must be **invalidated/purged** when updated, or you use versioned filenames (`app.3f2a1c.js`).

## Identity and access management (IAM) in cloud services

IAM controls **who** (identity: user, group, service account/role) can do **what** (actions) on **which** resources, under which conditions.

* Authentication (who are you) vs authorization (what may you do).
* **Policies** attach permissions to identities or roles; apply **least privilege**.
* Workloads should use **roles** or short-lived credentials rather than embedded long-lived access keys.
* Enable MFA for human users; audit with access logs.

## Key takeaways

* IaaS: you run OS and up; PaaS: you run code; SaaS: you run configuration; FaaS: you run functions, billed per execution.
* Object storage = buckets and keys over an HTTP/S3 API, objects replaced whole, access via ACLs/policies.
* RDBMS gives SQL and ACID; NoSQL types: key-value (Redis), document (MongoDB), time series (InfluxDB), search (Elasticsearch/OpenSearch).
* Queues deliver each message to one consumer; pub/sub to all subscribers; Kafka is a replayable log; MQTT is for light IoT messaging.
* CDNs cache at the edge; invalidate or version assets.
* IAM: least privilege, roles instead of long-lived keys, MFA.
