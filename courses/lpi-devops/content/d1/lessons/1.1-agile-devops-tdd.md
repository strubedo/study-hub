## Agile software development

**Agile** (from the 2001 Agile Manifesto) favours working software, collaboration with the customer, responding to change and individuals/interactions over heavy process. In practice:

* Short **iterations** (sprints in **Scrum**, typically 1 to 4 weeks) delivering a usable increment.
* A prioritised **backlog** of user stories; regular review and **retrospective**.
* **Kanban** visualises work on a board and limits work in progress instead of using fixed iterations.
* Frequent feedback from users replaces long up-front specification.

Agile shortens the cycle from idea to code; it does not by itself get that code reliably to production. DevOps closes that gap.

## DevOps

**DevOps** is a culture and set of practices that unites development and operations so software is built, tested, released and operated with shared responsibility. Typical elements:

| Practice | Purpose |
|----------|---------|
| Continuous integration / delivery | Small changes integrated and releasable at all times |
| Infrastructure as code | Environments defined in version-controlled files and created repeatably |
| Automation of build, test, deploy | Fewer manual, error-prone steps |
| Monitoring and feedback | Production data drives the next iteration |
| Shared ownership ("you build it, you run it") | Developers care about operability; operations care about delivery speed |
| Blameless post-mortems | Learn from incidents without blaming individuals |

Implications for **developers**: code must be deployable, configurable, observable and testable; developers take part in on-call and incident review. For **operators**: they work with version control, pipelines and code, and provide platforms that developers use self-service. The classic "wall of confusion" (developers throw code over the wall; operations resist change) is what DevOps removes.

> **Exam tip:** DevOps is not a tool or a job title. Questions describing "developers and operations sharing responsibility, automation, fast feedback" point to DevOps; "iterative delivery with sprints and backlog" points to agile.

## Test-driven development (TDD)

TDD writes the test first. The cycle, often called **red-green-refactor**:

1. **Red**: write a small automated test for behaviour that does not exist yet; run it and watch it fail.
2. **Green**: write the simplest code that makes it pass.
3. **Refactor**: clean up the code (and tests) while keeping all tests green.

Benefits: a regression safety net, design pressure toward small testable units, and living documentation. Related terms: **unit tests** (one component in isolation, fast), **integration tests** (components together, e.g. service plus database), **acceptance tests** (does the system meet the requirement, often end-to-end), and the **test pyramid** (many unit tests, fewer integration tests, fewest end-to-end tests). **BDD** (behaviour-driven development) phrases tests as readable Given/When/Then scenarios.

```text
def test_total_applies_discount():          # RED: fails, total() does not exist yet
    assert total([10, 20], discount=0.5) == 15

def total(prices, discount=0):               # GREEN: simplest passing code
    return sum(prices) * (1 - discount)
```

## Lab it yourself

1. In an empty directory write a failing `pytest` test first (`pytest -q` shows red), then the function, then run again for green.
2. Add the test run to a `Makefile` target `make test` so the same command can later run in a CI job.

## Key takeaways

* Agile: iterations, backlog, feedback; Scrum uses sprints, Kanban limits work in progress.
* DevOps: shared responsibility between development and operations, supported by automation, CI/CD, infrastructure as code and monitoring.
* DevOps removes the hand-off wall; it is a culture, not a tool.
* TDD = red (failing test), green (minimal code), refactor.
* Test pyramid: many unit tests, fewer integration tests, fewest end-to-end tests.
