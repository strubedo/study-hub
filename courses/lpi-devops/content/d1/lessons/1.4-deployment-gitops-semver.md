## Environments

A release usually flows through **development** (developers integrate and experiment), **staging** (a production-like environment for final tests and acceptance), and **production** (real users). Staging should mirror production in configuration and data shape so that findings transfer. Configuration (URLs, credentials, feature settings) is injected per environment; the artifact is identical.

## Deployment strategies

| Strategy | How it works | Pros | Cons |
|----------|--------------|------|------|
| **Recreate** | Stop the old version, start the new one | Simple | Downtime |
| **Rolling update** | Replace instances gradually, a few at a time | No downtime, little extra capacity | Old and new versions run side by side; slower rollback |
| **Blue-green** | Two identical environments; deploy to the idle one (green), test it, then switch all traffic from blue to green | Instant switch and rollback, no mixed versions | Double the infrastructure; database changes must suit both |
| **Canary** | Send a small share of traffic (e.g. 5%) to the new version, watch metrics, then increase or roll back | Limits blast radius, real-traffic validation | Needs routing and good monitoring |
| **A/B testing** | Show different variants to different user groups to compare a business metric | Data-driven product decisions | It is an experiment on user behaviour, not primarily a release safety technique |

> **Watch out:** Canary and A/B testing both split traffic, but the goal differs: canary asks "is the new version healthy?", A/B testing asks "which variant performs better for users?".

**Feature toggles (feature flags)** switch functionality on or off at runtime without redeploying. They separate *deployment* from *release*: unfinished code can be merged and deployed dark, enabled for a subset of users, and turned off instantly if it misbehaves. Remove stale toggles to avoid clutter.

**Preview releases** are early builds (alpha, beta, release candidates, or per-branch preview environments) for testers or early adopters before the stable release; in semantic versioning they carry a pre-release suffix such as `2.0.0-rc.1`.

Best practices: automate everything, make deployments repeatable and small, have a tested rollback path, use health checks and automated smoke tests after rollout, keep database changes backward compatible, and observe the release with metrics.

## GitOps

**GitOps** manages infrastructure and application deployment through Git:

* The desired state of the system is described **declaratively** (Kubernetes manifests, Helm charts, Kustomize) in a Git repository, the **single source of truth**.
* Changes happen only by commit or pull request, which gives review, history and audit trail; **rollback is a `git revert`**.
* An agent inside the environment (Argo CD or Flux) **pulls** the desired state and applies it, rather than a CI job pushing credentials into the cluster.
* The agent runs a **reconciliation loop**: it continually compares actual state with desired state, corrects **drift** and reports status. This is the same control-loop idea Kubernetes controllers use.

CI builds and tests the artifact and updates the image tag in the configuration repository; GitOps (the reconcile loop) performs the deployment.

## Semantic versioning (SemVer 2.0.0)

A version has the form **MAJOR.MINOR.PATCH**:

| Increment | When |
|-----------|------|
| MAJOR | Incompatible (breaking) API changes |
| MINOR | Backward-compatible new functionality |
| PATCH | Backward-compatible bug fixes |

Rules from the specification:

* Versions are non-negative integers without leading zeros; incrementing MAJOR resets MINOR and PATCH to 0, incrementing MINOR resets PATCH.
* `0.y.z` is for initial development: anything may change at any time. `1.0.0` declares the public API.
* A **pre-release** is appended with a hyphen (`1.0.0-alpha.1`, `2.0.0-rc.1`) and has **lower precedence** than the associated normal version.
* **Build metadata** is appended with a plus (`1.0.0+20241030`) and is **ignored** when determining precedence.
* Once a version is released, its contents must not be modified; publish a new version.

Precedence example: `1.0.0-alpha < 1.0.0-alpha.1 < 1.0.0-alpha.beta < 1.0.0-beta < 1.0.0-beta.2 < 1.0.0-beta.11 < 1.0.0-rc.1 < 1.0.0`. (Numeric identifiers compare as numbers, so `beta.2 < beta.11`; alphanumeric ones compare in ASCII order.)

```text
1.4.2  -> fix a bug, same API              -> 1.4.3
1.4.3  -> add a new optional endpoint       -> 1.5.0
1.5.0  -> remove an endpoint (breaking)     -> 2.0.0
```

Dependency managers use version ranges built on SemVer (npm `^1.4.2` means `>=1.4.2 <2.0.0`; `~1.4.2` means `>=1.4.2 <1.5.0`). In Git, a release is conventionally marked with an annotated tag such as `v1.4.2`. Container images use the same scheme (`example/webshop:1.4.2`).

## Lab it yourself

1. Tag a commit `git tag -a v0.1.0 -m "first"`, add a feature and tag `v0.2.0`, make a breaking change and tag `v1.0.0`.
2. Sort versions with `printf '1.10.0\n1.9.0\n1.2.0\n' | sort -V` to see why plain text sorting is wrong.
3. With two containers behind nginx, simulate blue-green by editing an `upstream` block and running `nginx -s reload`.

## Key takeaways

* Strategies: recreate (downtime), rolling, blue-green (two environments, switch), canary (small share first), A/B testing (compare variants).
* Feature toggles decouple deployment from release.
* GitOps: declarative state in Git, pull-based agent, reconciliation loop, drift correction, rollback by revert.
* SemVer: MAJOR breaking, MINOR compatible feature, PATCH compatible fix; `0.y.z` unstable.
* Pre-release has lower precedence than the release; build metadata (`+`) is ignored in ordering.
* Build once and promote the same artifact through development, staging, production.
