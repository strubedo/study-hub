## Applications are built from components

Modern applications are assembled from your own code plus **software libraries**, frameworks, runtimes, base images and services written by others. Most of the code you ship is typically third-party. Consequences: you inherit their bugs, vulnerabilities and licence obligations. **Direct dependencies** are the ones you declare; **transitive dependencies** are what those pull in.

**Dependency managers** resolve, download and pin dependencies:

| Tool | Ecosystem | Declaration file | Lock file / location |
|------|-----------|------------------|----------------------|
| **npm** | JavaScript / Node.js | `package.json` | `package-lock.json`, installs to `node_modules/` |
| **Gradle** | JVM (Java, Kotlin) | `build.gradle` / `build.gradle.kts` | Dependencies fetched from repositories such as Maven Central; optional lock files |
| **Composer** | PHP | `composer.json` | `composer.lock`, installs to `vendor/` |

Commit lock files so builds are reproducible. Version ranges (for example npm `^1.4.2`) allow compatible updates; pinning exact versions gives repeatability at the cost of manual upgrades.

### Software Bill of Materials (SBOM)

An **SBOM** is a machine-readable inventory of the components (names, versions, suppliers, licences, hashes, relationships) in a piece of software, like an ingredients list. Uses: find out whether you are affected when a new vulnerability (CVE) is published, check licence compliance, and support supply-chain security. Common formats: **SPDX** and **CycloneDX**; tools such as Syft and Trivy generate them from source trees or container images. Generate the SBOM in the pipeline and attach it to the release artifact.

## Proprietary, open source and free software

* **Proprietary software**: the owner keeps the source closed and restricts use, copying, modification and redistribution via a licence (EULA).
* **Free software** (FSF definition): users have four freedoms: run the program (freedom 0), study and change it (1), redistribute copies (2), distribute modified versions (3). Source access is a precondition.
* **Open source** (Open Source Initiative, Open Source Definition): licences that grant free redistribution, source code availability, derived works, no discrimination against persons, groups or fields of use, and so on. In practice the two terms cover nearly the same licences; "free" refers to freedom, not price.

A licence is a grant of permissions by the **copyright holder**. Without one, the default is "all rights reserved", so code on a public repository without a licence is not open source.

## Two families of open source licences

| | Permissive | Copyleft |
|---|-----------|----------|
| Idea | Do almost anything, keep the notice | Derived works must stay under the same terms |
| Can be used in proprietary products | Yes | Only within the licence's limits |
| Examples | MIT, BSD, Apache 2.0 | GPL, LGPL (weak), AGPL |

**Copyleft** uses copyright to guarantee freedom: if you distribute a covered work or a derivative, you must offer the **corresponding source** under the same licence. **Strong copyleft** (GPL) extends to the whole combined work; **weak copyleft** (LGPL, MPL) restricts only the library itself or the modified files.

## The licences you must know

| Licence | Type | Key points |
|---------|------|------------|
| **MIT** | Permissive | Very short; keep copyright and permission notice; no warranty; no explicit patent grant |
| **BSD 2-clause** ("Simplified"/"FreeBSD") | Permissive | Retain copyright notice and disclaimer in source **and** in the documentation/materials of binary distributions |
| **BSD 3-clause** ("New"/"Modified") | Permissive | The 2-clause terms **plus** a ban on using the authors' names to endorse derived products without permission |
| **Apache 2.0** | Permissive | Keep notices and the `NOTICE` file, state significant changes; **explicit patent licence** from contributors; the patent licence **terminates** for anyone who sues claiming the work infringes a patent; no trademark grant |
| **GPLv2** | Strong copyleft | Distributed derivative works must be GPL with source; no "further restrictions" |
| **GPLv3** | Strong copyleft | Adds an explicit patent grant, protection against "tivoization" (locked-down hardware; installation information required for user products), clearer termination (cure periods), compatibility with Apache 2.0 |
| **LGPL** (2.1, 3) | Weak copyleft | Intended for libraries: a proprietary program may link to an LGPL library, but changes to the library must be released under the LGPL and users must be able to replace/relink the library (dynamic linking makes this easy) |
| **AGPLv3** | Strong copyleft + network clause | GPLv3 plus section 13: if you modify the program and let users interact with it **remotely over a network**, you must offer them the corresponding source. Closes the "SaaS loophole" |

> **Watch out:** GPL obligations are triggered by **distribution** (conveying), not by private use. Running modified GPL software purely on your own servers triggers nothing, but with the AGPL, **network use by others** triggers the source-offer duty.

## Licence compatibility and multi-licensing

Two licences are **compatible** when code under both can legally be combined in one work and distributed, because all conditions can be met at once.

* Permissive code (MIT, BSD, Apache 2.0) can be included in a GPL project, because the combined work can be distributed under the GPL. The reverse is not allowed: you cannot relicense GPL code as MIT.
* **Apache 2.0 and GPLv3 are compatible**: Apache 2.0 code may be included in a GPLv3 work (the combination is then governed by GPLv3).
* **Apache 2.0 and GPLv2-only are not compatible**: the Apache patent-termination terms are treated as a "further restriction" GPLv2 does not allow. Code licensed "GPLv2 **or later**" can be used under v3 and therefore combined with Apache 2.0.
* Two *different* copyleft licences generally cannot be combined unless one explicitly allows it (GPLv3 and AGPLv3 can be combined through special provisions).
* The combined work must satisfy the **most restrictive** terms of its parts.

**Multi-licensing (dual licensing)**: the copyright holder offers the same code under more than one licence. Either the user *chooses* (SPDX expression `MIT OR Apache-2.0`, common in the Rust ecosystem), or an open licence is offered alongside a **commercial licence** for those who cannot accept copyleft (for example GPL + commercial). Only the copyright holder (or someone with their permission) can do this, which is why projects with many contributors ask for a contributor licence agreement.

SPDX identifiers are short, standard names for licences: `MIT`, `BSD-2-Clause`, `BSD-3-Clause`, `Apache-2.0`, `GPL-2.0-only`, `GPL-3.0-or-later`, `LGPL-2.1-only`, `AGPL-3.0-only`. The `-only` / `-or-later` suffix expresses exactly the GPLv2-only question above.

## Lab it yourself

1. In a Node project run `npm ls --all` to see the transitive tree, then `npm install --package-lock-only`.
2. Install Syft (or Trivy) and generate an SBOM of a container image: `syft example/webshop:1.4.2 -o spdx-json`.
3. Pick three dependencies and read their `LICENSE` files; classify each as permissive or copyleft.

## Key takeaways

* Applications mix your code with direct and transitive third-party components; dependency managers (npm, Gradle, Composer) resolve them and lock files make builds repeatable.
* An SBOM lists components, versions and licences (SPDX, CycloneDX).
* Open source and free software grant rights to use, study, modify and share; proprietary software restricts them.
* Permissive: MIT, BSD, Apache 2.0. Copyleft: GPL (strong), LGPL (weak, library-level), AGPL (network use counts).
* Apache 2.0 has an explicit patent grant; BSD 3-clause adds the no-endorsement clause.
* Apache 2.0 is compatible with GPLv3 but not with GPLv2-only.
* Multi-licensing lets the copyright holder offer alternative licences (for example GPL or commercial).
