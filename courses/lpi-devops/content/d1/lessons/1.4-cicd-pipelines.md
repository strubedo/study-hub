## CI and CD concepts

**Continuous Integration (CI)**: developers merge small changes into the shared mainline frequently (at least daily); every change triggers an automated build and test run, so integration problems surface within minutes rather than at release time. A broken build is fixed first.

**Continuous Delivery**: every change that passes the pipeline is *releasable* at any moment; the final push to production is a **manual decision** (a button or approval).

**Continuous Deployment**: goes one step further; every change that passes all stages is deployed to production **automatically**, with no human approval.

| | Release to production |
|---|------------------------|
| Continuous integration | Not covered; ends at tested build |
| Continuous delivery | Ready at any time, triggered manually |
| Continuous deployment | Automatic after the pipeline passes |

> **Exam tip:** The only difference between delivery and deployment is the manual gate before production. Do not mix them up.

## Pipeline components

A pipeline is an automated, versioned sequence of **stages**, each made of **jobs**/steps. A common layout:

1. **Source**: a commit, merge request or tag triggers the run (webhook or polling).
2. **Build**: compile/package; produce a versioned **build artifact** (binary, JAR, wheel, container image).
3. **Unit tests**: fast, isolated tests of single components; static analysis and linting often run here.
4. **Integration tests**: components together, e.g. the service plus a real database in containers.
5. **Acceptance tests**: verify the system against business requirements, often end-to-end in a staging environment.
6. **Artifact management**: publish the artifact to a repository.
7. **Delivery / deployment**: roll out to staging, then production.

Fail fast: put the quickest checks first, stop the pipeline on the first failure, and report back to the commit/merge request. **Build once, deploy many**: the same artifact moves through environments (development, staging, production); only configuration differs. Never rebuild per environment, or what you tested is not what you ship.

### Build artifacts and caches

* **Artifacts** are the *outputs* you want to keep: versioned, immutable and traceable to a commit. They are passed between stages and stored in an **artifact/repository manager**.
* **Caches** speed up repeated runs by reusing *inputs* such as downloaded dependencies (`~/.m2`, `node_modules`, a package cache) or Docker build layers. A cache is an optimisation and may be missing or stale; a pipeline must still work without it. Key caches on the lock file's hash so they invalidate when dependencies change.

| | Artifact | Cache |
|---|----------|-------|
| Purpose | Deliverable result | Speed-up |
| Must be reliable | Yes | No, optional |
| Typically holds | Binaries, images, test reports | Dependencies, layers |

### Artifactory and Nexus

**JFrog Artifactory** and **Sonatype Nexus Repository** are universal repository managers: they store your own artifacts (Maven, npm, PyPI, Docker/OCI images, generic files), proxy and cache public registries (Maven Central, npmjs) and group repositories behind one URL. Benefits: reproducible builds, faster downloads, control over which dependencies are allowed, promotion of artifacts from snapshot to release repositories, and scanning.

## Jenkins and GitLab CI

**Jenkins** is a self-hosted automation server with a large plugin ecosystem; controllers schedule work on **agents**. Pipelines live in a `Jenkinsfile` in the repository. The **Declarative Pipeline** syntax has a fixed structure:

```text
pipeline {
    agent any
    stages {
        stage('Build') {
            steps { sh 'make build' }
        }
        stage('Test') {
            steps { sh 'make test' }
        }
        stage('Deploy') {
            when { branch 'main' }
            steps { sh './deploy.sh staging' }
        }
    }
    post {
        always  { junit 'reports/*.xml' }
        failure { echo 'Build failed' }
    }
}
```

(Scripted Pipeline, written in Groovy, is the older, more flexible alternative.)

**GitLab CI/CD** is built into GitLab. Pipelines are defined in `.gitlab-ci.yml`; **runners** execute jobs.

```text
stages: [build, test, deploy]

build-job:
  stage: build
  script:
    - make build
  artifacts:
    paths: [dist/]
  cache:
    key:
      files: [package-lock.json]
    paths: [node_modules/]

deploy-staging:
  stage: deploy
  script: ./deploy.sh staging
  rules:
    - if: $CI_COMMIT_BRANCH == "main"
```

Jobs in one stage run in parallel; stages run in order. Both tools: pipeline as code in the repository, triggered by pushes and merge requests.

## Lab it yourself

1. Run Jenkins in a container (`docker run -p 8080:8080 jenkins/jenkins:lts`), create a Pipeline job from a `Jenkinsfile` in a small repository, and make the Test stage fail on purpose.
2. Or register a GitLab Runner against a free project, commit the `.gitlab-ci.yml` above and look at the artifact download.
3. Observe the difference between cache and artifact: delete the cache and confirm the pipeline still passes, only slower.

## Key takeaways

* CI = frequent merging with automated build and test. Delivery = always releasable, manual release. Deployment = automatic release.
* Typical stages: build, unit, integration, acceptance tests, artifact publication, deployment.
* Build once, promote the same artifact through environments.
* Artifacts are deliverables; caches are optional speed-ups keyed on dependency lock files.
* Artifactory and Nexus are repository managers (hosted, proxy, group repositories).
* Jenkins uses a `Jenkinsfile` (declarative: `pipeline`, `agent`, `stages`, `stage`, `steps`, `post`); GitLab CI uses `.gitlab-ci.yml` with runners.
