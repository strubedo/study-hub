## Network drivers

`docker network ls` shows the built-in networks `bridge`, `host` and `none`. Drivers:

| Driver | Behaviour |
|---|---|
| `bridge` | Default. Private network on one host behind a Linux bridge; NAT to the outside; ports need `-p` to be reachable from outside |
| `host` | Container shares the host's network stack; no isolation, `-p` is ignored |
| `none` | Only loopback; no external connectivity |
| `overlay` | Spans **multiple Docker hosts** using VXLAN; needs **swarm mode** (`docker swarm init` / `join`) |
| `macvlan` / `ipvlan` | Container gets an address directly on the physical LAN |

```text
docker network create appnet                         # user-defined bridge (default driver)
docker network create --driver bridge --subnet 10.20.0.0/16 appnet2
docker network create -d overlay --attachable meshnet   # swarm manager only
docker network ls
docker network inspect appnet
docker container run -d --name db --network appnet postgres:16
docker network connect appnet existing-container      # attach a running container
docker network disconnect appnet existing-container
docker network rm appnet                              # fails while containers are attached
docker network prune
```

**Overlay networks** are a concept-level topic: they let containers on different hosts talk as if on one L2 segment, encapsulated in VXLAN. The Docker Engine must be part of a swarm (even a single-node swarm) before `docker network create -d overlay` works. Containers started with plain `docker run` can join one only if it was created with `--attachable`. Kubernetes uses its own CNI plugins instead.

### Default bridge versus user-defined bridge

| | Default `bridge` (docker0) | User-defined bridge |
|---|---|---|
| DNS by container name | **No**, IP addresses only (legacy `--link` is deprecated) | **Yes**, automatic |
| Isolation | All containers without `--network` share it | Only attached containers |
| Attach/detach live | Must recreate | `network connect` / `disconnect` |
| Configuration | Daemon-wide | Per network (subnet, options) |

> **Exam tip:** "Container `web` cannot reach `db` by name" on the default bridge: create a user-defined network and attach both.

## DNS service discovery

On a user-defined network Docker runs an **embedded DNS server** at `127.0.0.11` inside each container (`/etc/resolv.conf` points to it). It resolves the **container name**, any `--network-alias`, and (in Compose) the **service name**. Names not known to Docker are forwarded to the host's resolvers. Resolution is scoped per network: two containers on different networks cannot resolve each other unless one is attached to both. If several containers share an alias, DNS returns all their addresses (round-robin).

```text
$ docker network create appnet
$ docker container run -d --name db --network appnet --network-alias database postgres:16
$ docker container run --rm --network appnet alpine:3.20 ping -c1 database
PING database (172.19.0.2): 56 data bytes
```

Podman 4+ with Netavark/aardvark-dns provides the same name resolution on user-defined networks (`podman network create`); the default `podman` network has DNS disabled in the same way as Docker's default bridge. Containers in one Podman **pod** share `localhost` instead.

## Publishing ports

`-p 8080:80` creates a NAT rule (host port to container port). Containers on the same user-defined network reach each other on the container's own port (80) without any publishing. Do not publish a database port unless something outside needs it; `-p 127.0.0.1:5432:5432` limits it to the host.

## Storage and volumes

A container's writable layer disappears with the container, so persistent or shared data goes into a mount.

| Type | Created with | Managed by | Typical use |
|---|---|---|---|
| **Named volume** | `-v dbdata:/var/lib/postgresql/data`, `--mount type=volume,src=dbdata,dst=...` | Docker (`/var/lib/docker/volumes/<name>/_data`) | Databases, persistent app data, sharing between containers |
| **Anonymous volume** | `-v /data` or a `VOLUME` instruction | Docker (random name) | Scratch data, easily orphaned |
| **Bind mount** | `-v /srv/site:/usr/share/nginx/html:ro`, `--mount type=bind,src=...,dst=...` | The host filesystem path you choose | Source code in development, host config files |
| **tmpfs mount** | `--tmpfs /run`, `--mount type=tmpfs,dst=/run` | Host memory only | Secrets or scratch that must never reach disk; Linux only |

Key behaviours:

* A new named volume mounted over a non-empty image directory is **populated with the image's content**; a bind mount **hides** whatever the image had there.
* `-v` with a missing host path **creates a directory** for it; `--mount type=bind` **errors** instead.
* `:ro` (or `readonly`) makes the mount read-only. `--mount` is explicit and key-based (`type=`, `src=`/`source=`, `dst=`/`target=`); `-v` is positional `SRC:DEST[:opts]`.
* tmpfs data is lost when the container stops.

```text
docker volume create dbdata
docker volume ls
docker volume inspect dbdata
docker container run -d --name db -v dbdata:/var/lib/postgresql/data postgres:16
docker volume rm dbdata        # fails while a container uses it
docker volume prune            # remove unused local (anonymous) volumes
```

Sharing: two containers can mount the same named volume (`--volumes-from other` copies another container's mounts). Backing up a volume is done by running a throwaway container that mounts the volume and a host directory and runs `tar`. `podman volume *` works the same.

> **Watch out:** `docker container rm` does not delete named volumes; `docker compose down -v` does.

## Rootless containers

In a **rootless** setup neither the engine nor the containers run as host root. The user's container "root" is mapped by a **user namespace** to an unprivileged UID range configured in `/etc/subuid` and `/etc/subgid`. Podman works this way by default; Docker has an optional rootless mode (`dockerd-rootless-setuptool.sh install`). Benefits: a container escape yields only an unprivileged user. Limits: binding host ports below 1024 needs `sysctl net.ipv4.ip_unprivileged_port_start`, some storage drivers and network features are restricted, and no host device access without extra configuration. "Rootless" is different from the `USER` instruction, which merely changes the user *inside* a container that may still be run by a root daemon.

## Lab it yourself

1. Create `appnet`, start `db` (`postgres:16`, `-e POSTGRES_PASSWORD=...`) on it, then `docker container run --rm --network appnet postgres:16 pg_isready -h db`.
2. Repeat on the default bridge and watch the name fail.
3. Create a named volume, write a file from one container, read it in a second, then remove both containers and confirm the data remains.
4. Run `podman run --rm alpine id` and `podman unshare cat /proc/self/uid_map`.

## Key takeaways

- Drivers: bridge (default), host, none, overlay (multi-host, needs swarm mode), macvlan.
- Only user-defined bridges give automatic DNS by name (embedded DNS at 127.0.0.11); the default bridge does not.
- `docker network create/connect/disconnect/inspect/rm` manage networks; `-p` is only for outside access.
- Named volumes are Docker-managed and survive container removal; bind mounts use a host path; tmpfs is memory-only.
- `-v` creates a missing host directory, `--mount` errors; a bind mount hides image content.
- Rootless means the whole runtime runs as an unprivileged user via user namespaces; Podman does so by default.
