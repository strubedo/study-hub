## Application model

Compose describes a multi-container application in one YAML file and manages it as a **project**. The file follows the **Compose Specification**, implemented by the `docker compose` plugin (Compose v2; the old Python `docker-compose` v1 is retired history). The preferred file name is `compose.yaml`; `compose.yml`, `docker-compose.yaml` and `docker-compose.yml` are also found. Top-level elements:

| Element | Purpose |
|---|---|
| `services` | The containers (required): one entry per service |
| `networks` | Networks to create or reference |
| `volumes` | Named volumes |
| `configs`, `secrets` | Configuration and secret files |
| `name` | Optional project name |
| `version` | **Obsolete.** Ignored; Compose warns if present. The exam says "version 3 or later" because that was the file-format era; with the Compose Specification you simply omit it |

The project name defaults to the directory name (override with `-p` or `name:`). Containers are named `<project>-<service>-<number>`, and Compose creates a default network `<project>_default` that every service joins. Services reach each other by **service name** through the same embedded DNS as a user-defined bridge.

```yaml
# compose.yaml
services:
  web:
    image: registry.example.com/example/webshop:1.4.2
    ports:
      - "8080:80"
    environment:
      DB_HOST: db
    depends_on:
      db:
        condition: service_healthy
    networks: [front, back]
    restart: unless-stopped
  db:
    image: postgres:16
    volumes:
      - dbdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 10s
      timeout: 3s
      retries: 5
    networks: [back]
networks:
  front:
  back:
volumes:
  dbdata:
```

## Common service properties

| Key | Meaning |
|---|---|
| `image` | Image to run; `build` builds one instead (`build: ./app` or `context`, `dockerfile`, `args`, `target`). With both, `image` names the built result |
| `ports` | `"HOST:CONTAINER"` strings (quote them; unquoted `xx:yy` below 60 can be parsed as a base-60 number by YAML 1.1 parsers) |
| `expose` | Ports reachable only by other services |
| `environment` / `env_file` | Variables as a map or list / read from file(s) |
| `volumes` | Named volume (`dbdata:/path`), bind mount (`./site:/usr/share/nginx/html:ro`), or long syntax |
| `networks` | Networks the service joins; `aliases` for extra names |
| `depends_on` | Start-order dependencies |
| `command`, `entrypoint` | Override the image `CMD` / `ENTRYPOINT` |
| `restart` | `no`, `always`, `on-failure`, `unless-stopped` |
| `healthcheck` | `test`, `interval`, `timeout`, `retries`, `start_period` |
| `profiles` | Only start the service when the profile is enabled (`--profile debug`) |
| `deploy` | Resources and replicas (`deploy.resources.limits`) |
| `container_name` | Fixed name (prevents scaling) |

### depends_on

The short form `depends_on: [db]` only controls **start order**: `web` starts after `db`'s container has *started*, not after the database accepts connections. The long form adds a `condition`: `service_started` (default), `service_healthy` (waits for a passing `healthcheck`), `service_completed_successfully` (for one-shot init jobs). Applications still need retry logic.

> **Exam tip:** "depends_on does not wait for readiness" is the classic trap. Use `condition: service_healthy` plus a healthcheck.

### Networks and volumes

Top-level `networks:` and `volumes:` declare resources that Compose creates (prefixed with the project name). `external: true` references one that already exists and is never created or removed by Compose. A service that lists no `networks:` joins `default`. Services on different networks are isolated: in the example above, `web` reaches `db` via the shared `back` network only.

## Operating a project

```text
docker compose up -d              # create and start everything in the background
docker compose up -d --build      # rebuild images with a build: section first
docker compose ps                 # containers of this project and their state
docker compose logs -f web        # follow logs (all services if no name)
docker compose pull               # pull newer images for all services with image:
docker compose stop | start | restart
docker compose exec web sh        # run a command in a running service
docker compose run --rm web sh    # one-off new container
docker compose config             # render and validate the merged file
docker compose down               # stop, remove containers and networks
docker compose down -v            # ...and remove named volumes
```

Options: `-f file.yaml` (repeatable, later files override), `-p name`, `--profile`, `--env-file`. `docker compose down` keeps named volumes unless `-v`. Variables `${TAG:-1.4.2}` are interpolated from the shell and from a `.env` file next to the Compose file.

## Updating running containers

```text
docker compose pull
docker compose up -d
```

`up -d` compares the service's configuration and image with the running container and **recreates only the changed services**, keeping named volumes. Changing a tag in the file (`1.4.1` to `1.4.2`) and running `up -d` also works (it pulls a missing image). `docker compose up -d --pull always` forces a pull, `--force-recreate` recreates anyway. Compose does not do rolling updates; there is a short interruption while the container is replaced.

> **Watch out:** With a floating tag such as `:latest`, `up -d` does not notice a newer image on the registry until you `pull`.

## Podman Compose

`podman-compose` is a separate Python re-implementation that reads the same `docker-compose.yml`/`compose.yaml` and drives Podman. `podman compose` is a thin wrapper that runs an external provider (`docker-compose` or `podman-compose`). Podman can also serve its Docker-compatible socket so the real Compose client can talk to it. Behaviour in corner cases differs from Docker's Compose, so test it.

## Lab it yourself

1. Save the example (swap the web image for `nginx:1.27`), run `docker compose up -d`, then `docker compose ps`.
2. From `web`, run `docker compose exec web getent hosts db`.
3. Change the nginx tag, run `docker compose pull && docker compose up -d`, and note only `web` is recreated.
4. `docker compose down`, check `docker volume ls` still lists `<project>_dbdata`, then `down -v`.

## Key takeaways

- Compose Specification: `services`, `networks`, `volumes`, `configs`, `secrets`; top-level `version` is obsolete.
- Services find each other by service name over the project network; each project gets `<project>_default`.
- `depends_on` orders start, not readiness; use `condition: service_healthy` with a healthcheck.
- Core commands: `up -d`, `ps`, `logs`, `pull`, `down` (`-v` also removes named volumes).
- Update with `docker compose pull` then `docker compose up -d`: changed services are recreated, volumes kept.
- `podman-compose` and `podman compose` read the same file format for Podman.
