## Multimodal input

A **multimodal** model accepts more than one kind of input, or produces more than one kind of output. For an IT learner the useful inputs are:

- **Images and screenshots:** a photo of a rack, a screenshot of a firewall policy table, a diagram, a handwritten whiteboard.
- **Files:** PDFs, spreadsheets, text and code files, logs, exported configs.
- **Audio:** recordings or live voice, depending on the product.

What the vendors' own pages say, as of October 2026: Anthropic's models overview states that all current Claude models support text and image input and text output, with multilingual capability, vision and tool use. OpenAI's models page says the same for all its latest models (text and image input, text output, vision). Google's Gemini API documentation has dedicated sections for image, video and audio understanding and for audio transcription, and its Gemini app help page describes uploading and analysing files such as long documents and spreadsheets. Audio support, video support and the exact file types differ by product, by plan and by whether you are in the app or the API, so verify the specific input you need rather than assuming it is universal.

Practical points:

- **An image is turned into tokens too.** Large images and many pages consume context window budget.
- **Reading is not the same as understanding.** Models can misread small text in a screenshot, confuse similar-looking characters (`0` and `O`, `1` and `l`), or miss rows in a dense table. For exact values such as IP addresses and serial numbers, check the transcription or paste the text instead.
- **Prefer text when you have it.** Copying a config as text is almost always more accurate than a screenshot of the same config.
- **PDFs and spreadsheets may be processed in different ways.** An app may extract the text, render pages as images, or retrieve only relevant parts. If an answer seems to ignore half a document, ask the assistant what it actually read.
- **Strip secrets first.** Screenshots often contain more than you notice: hostnames, tokens, usernames in a terminal title bar. Domain 4 covers data handling.
- **Output can be multimodal as well.** Vendors list separate image-generation models (for example OpenAI's GPT-Image line and Google's Nano Banana models), realtime voice models, and text-to-speech. Those are specialized models, not the general text model.

## Consumer apps, APIs and workspace integrations

The same vendor model is reachable through different **surfaces**, and the surface decides what you can control.

| Surface | What it is | What you control | Typical user |
|---|---|---|---|
| **Consumer / prosumer app** (ChatGPT, Gemini app, Claude app) | Chat interface on web, desktop and mobile | Prompt, uploaded files, a model or mode picker, saved instructions, projects or custom assistants, memory | Individuals, knowledge workers |
| **API** | Programmatic access with an API key, billed by tokens | Exact model ID, system prompt, sampling and reasoning settings, tools, output limits, structured output | Developers, automation, internal tools |
| **Workspace / business integrations** | The assistant embedded in a company suite or offered on business and enterprise plans with admin controls | Whatever the admin allows; data handling is governed by the organization's agreement | Teams and companies |
| **Developer and agent tools** (command-line coding assistants such as Claude Code, Codex, Gemini CLI) | Agents that read and edit files and run commands | Permissions, project instructions | Engineers |

Key distinctions:

1. **Apps wrap the model with extras.** An app adds a hidden system prompt, tools (search, code execution, file reading), memory, limits and a UI. The same underlying model through the API can behave differently because you supply (or omit) those layers.
2. **The API gives control, and responsibility.** You choose the model ID, set reasoning effort, enforce a JSON schema, and handle errors and cost. You also build any conversation state yourself, since the API is stateless.
3. **Plans decide limits.** Usage caps, available models and file or context sizes depend on the subscription tier (Google's help page, for example, describes different context sizes by plan). Limits can change without notice.
4. **Data policies depend on the surface and the plan.** Consumer, business and API terms differ on retention and training use. Check them; never assume (domain 4.2).
5. **Custom assistant features have vendor-specific names, and they churn.** Anthropic's Claude has **Projects**: a workspace with project knowledge and instructions shared by chats in the project, with per-project memory, available on free accounts with a project limit. OpenAI's ChatGPT has had **Projects** and **custom GPTs**; its developer documentation for Codex now includes a "migrate custom GPTs to plugins" page, so verify the current state in the ChatGPT help centre. Google's Gemini has **Gems**, saved customized versions of the Gemini app with instructions and optional knowledge files; Google's pages state that Gems are being replaced by **skills**, with personal accounts moving in November 2026 and Workspace business, enterprise and nonprofit accounts in March 2027, and education in June 2027. Domain 3.2 covers these in depth.

> **Real world:** Two people can ask "ChatGPT" the same question and get different results because one is on a free plan with a smaller default model and tighter limits, and the other is on a business plan choosing a deeper reasoning mode. When comparing assistants, record the plan, the model or mode, and the date.

## Picking a model for a task

There is no universal best model, and "which assistant is best" is the wrong question. Use a short decision process instead.

1. **Define the task and the cost of an error.** Drafting a status email can tolerate small slips; generating a firewall change for production cannot, and needs checking whichever model you use.
2. **Start with the balanced tier.** It is usually good enough for writing, summarizing, code explanation and routine scripting.
3. **Move up to the flagship or a reasoning mode** when the task is multi-step, ambiguous, long-horizon or you have seen the balanced model fail at it: complex debugging, architecture trade-offs, long agentic coding sessions.
4. **Move down to the fast tier** for high-volume, well-defined work: classify 10,000 log lines, extract fields, route tickets. Test it against a sample, since cheaper models can fail on edge cases.
5. **Match the input.** Need to read a 300-page PDF, images, audio or video? Confirm that the model and the surface support that input and enough context.
6. **Check freshness needs.** If the task needs facts after the knowledge cutoff, you need search or supplied documents regardless of model.
7. **Check data and compliance.** If the data is sensitive, the right surface and plan matter more than the model name.
8. **Measure.** Run the same prompt on two candidates with a few test cases and compare (domain 4.3). Model rankings shift every few months; your own test cases do not.

| Task | Reasonable starting point | Why |
|---|---|---|
| Summarize a meeting or ticket | Balanced or fast tier | Low risk, text-only |
| Explain a configuration | Balanced tier | Moderate complexity |
| Root-cause a multi-device outage from logs | Flagship or reasoning mode | Many steps and conflicting evidence |
| Classify or tag thousands of records | Fast tier via API | Volume, cost and latency |
| Extract text from a screenshot | A model with image input; verify values | Vision accuracy varies |
| Answer about last month's firmware release | Any model with search or the release notes pasted | Beyond the knowledge cutoff |

## Try it yourself

1. Take a screenshot of any diagram or table you created (use made-up data) and upload it to two assistants. Ask each to transcribe it as a Markdown table. Compare mistakes, especially with look-alike characters.
2. Pick one task from the table above and run the same prompt on a fast option and on a deeper or reasoning option in each of two assistants. Write down which result you would trust and what you checked.
3. Find your plan's help page for each assistant you use and note: which models or modes are listed, the file upload limits, and whether the plan uses your data for training by default. Record the date.

## Key takeaways

- Multimodal models accept images, files and sometimes audio or video; support varies by product, plan and surface, so verify.
- Text you can paste is more accurate than a screenshot of the same content; remove secrets from anything you upload.
- Apps wrap models with system prompts, tools, memory and limits; APIs give exact model IDs and control but need you to build state and handle cost.
- Plans and surfaces change limits and data policies; business and API terms differ from consumer terms.
- Custom assistant features have vendor-specific names (Projects, custom GPTs, Gems) and change often; Google has announced Gems are being replaced by skills.
- Choose a model by task, risk, input type, freshness and data sensitivity, starting at the balanced tier.
- Test candidates on your own cases; do not rely on a general ranking.
