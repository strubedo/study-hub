## What a hallucination is

A **hallucination** is output that is fluent and confident but not true, or not supported by the sources the model was given. Typical examples for an IT audience:

- a CLI command or flag that does not exist (`show ip ospf neighbor detail brief`),
- a configuration keyword from the wrong platform (FortiOS syntax in an IOS answer),
- an invented RFC number, CVE ID, software version, URL or API function,
- a "summary" of a log that includes an event that is not in the log,
- a quotation attributed to a document that does not say that.

The word suggests a rare glitch. It is better understood as a built-in failure mode of the way these systems work, and it can be reduced but not eliminated.

## Why models hallucinate

Recall from the first lesson that the model produces the most plausible continuation, token by token. Plausible and true overlap heavily, which is why models are so useful, but they are not the same thing.

1. **Plausibility over truth.** Training rewards predicting likely text. A realistic-looking command that fits the pattern of real commands is a likely continuation even if no device accepts it.
2. **Gaps and thin coverage.** Obscure products, niche protocols, brand-new features and rarely discussed error messages appear few times (or never) in the training data. When the weights hold little, the model still has to emit something, and the pattern-completion instinct fills in a plausible guess.
3. **Reluctance to say "I don't know".** Training on human-written text and on human preference ratings can favour answers that sound complete and helpful over answers that admit uncertainty. Vendors work to reduce this, and newer models are better at declining, but it persists. A prompt that explicitly allows "I don't know" helps (domain 4).
4. **Early mistakes compound.** Because generation is left to right, a wrong detail early in an answer becomes context for the rest, so the model elaborates on its own error instead of correcting it.
5. **Missing or misread context.** If the answer depends on text that was never supplied, was trimmed out of a long conversation, or sits in a confusing format, the model fills the gap. Many "hallucinations" in practice are really missing information.
6. **Loose tokenization-level details.** Exact strings such as long hex values, serial numbers, or the count of letters or items in a list are easy to get slightly wrong because the model does not work on characters or compute precisely unless it uses a tool.

> **Watch out:** Confidence of tone tells you nothing about accuracy. A model gives a wrong command in the same calm voice as a right one. Verification has to come from outside the model: documentation, a lab device, a linter, a test.

## What makes hallucination more or less likely

| More likely | Less likely |
|---|---|
| Asking about very recent events or releases | Asking about well-documented, stable topics |
| Niche, vendor-specific or version-specific syntax | Widely used, widely documented commands |
| Open-ended requests with no source material | Tasks grounded in text you paste in |
| Requests that demand specifics (IDs, versions, citations) | Requests where the model may paraphrase supplied text |
| Long chats where key facts have scrolled out | Short, focused requests with the needed facts in view |
| Pressure phrased as "give me the exact command" with no allowance for doubt | Prompts that invite caveats and uncertainty |

Two mitigations preview later domains: **grounding** (put the source text in the prompt and tell the model to answer only from it) and **tools** (web search, retrieval from your documents, or code execution) that let the model look things up or compute instead of guessing. Tools reduce errors but do not remove them: the model can still misread a result or cite a source that does not say what it claims.

## Knowledge cutoffs

A model's **training data cutoff** is the point after which its training data contains little or nothing. Anything that happened later is simply not in its weights. Vendors also publish a **reliable knowledge cutoff** or similar, which is earlier than the point where data stops, because the last months of data are sparse and less reliably learned.

As of October 2026, the vendors' model pages show cutoffs in roughly the spring-to-summer of 2026 for current flagship models (Anthropic lists a reliable knowledge cutoff and training data cutoff of June 2026 for its current lineup; OpenAI's model page lists knowledge cutoff dates between April and June 2026 for its GPT-6 family). Those dates are model-specific and will change with each release.

Consequences:

- **The model does not know today's date or recent news** unless the app supplies them or a web search tool is used. Many chat apps insert the current date in a hidden system prompt; a raw API call usually does not.
- **Releases newer than the cutoff are invisible.** Ask about a firewall firmware version released after the cutoff and the model may describe an older version, or invent details. For fast-moving products such as FortiOS, PAN-OS or Cisco IOS XE, verify against current release notes.
- **A model may be wrong about its own cutoff or even its own name.** Models learn about themselves from training text, which may predate their own release. Use the vendor's model page, not the model's answer, for such facts.
- **Browsing or search is a workaround, not a cure.** With search enabled, the model can read current pages, but quality depends on what it finds and how well it uses it.

> **Real world:** A common IT failure: you ask for a "current best practice" and the answer reflects what was widely published before the cutoff, such as a deprecated cipher or an end-of-life configuration style. When the topic changes yearly, paste the current guidance into the prompt, or enable search and ask for sources you can open.

## Try it yourself

1. In two assistants, ask about something that does not exist: `Explain what the IOS command "show spanning-tree mood detail" does and give example output.` See whether each assistant corrects the premise or invents output. Then repeat with the instruction `If you are not sure a command exists, say so rather than guessing.`
2. Ask both assistants: `What is today's date, and what is the latest stable release of the Linux kernel you know about?` Compare how they handle the date and the uncertainty. Then ask the same with web search or browsing switched on if the assistant offers it, and compare.
3. Paste a short, made-up change ticket (placeholder data only) and ask for a summary. Then ask: `List any facts in your summary that are not stated in the ticket.` This practises spotting added details.

## Key takeaways

- A hallucination is fluent, confident output that is false or unsupported by the supplied sources.
- It arises because models predict plausible text, have knowledge gaps, tend not to admit uncertainty, and build on their own early errors.
- Tone and fluency are not evidence of accuracy; verification must come from outside the model.
- Niche, recent, specific (IDs, versions, syntax) and ungrounded requests carry the highest risk.
- Grounding in supplied text and using tools like search or code execution reduce, but do not eliminate, hallucination.
- A knowledge cutoff is the limit of what a model learned; later events and releases are invisible unless provided in the prompt or found by a tool.
- For fast-changing products, check current vendor documentation instead of trusting recalled facts.
