## Why fluent output can be wrong

A language model produces the most plausible continuation of your prompt. Plausible is not the same as true. When the model lacks the fact, it does not stop; it tends to produce something that reads like a fact. People call this a **hallucination**: output that is fluent and confident but factually wrong or unsupported by the context you gave it.

Anthropic's guide to reducing hallucinations is blunt about this: even very capable models can generate text that is incorrect or inconsistent with the supplied context, and the techniques it lists reduce hallucinations without eliminating them. Its closing advice is to validate critical information, especially for high-stakes decisions. Treat that as the baseline for the whole domain.

Hallucinations cluster in predictable places:

| Where it happens | Example | Why |
|---|---|---|
| Exact identifiers | A command flag, a log message ID, a CVE number, a firmware version | The shape is easy to imitate; the exact string is not |
| Obscure or new facts | A feature added to a platform last quarter | Training data is a snapshot |
| Specific numbers | A default timer, a port, a limit | Many similar values exist across vendors |
| Citations and quotes | A document title or a URL that looks right | Format is easy to produce |
| Your own environment | "Your trunk allows VLAN 30" when you never said so | The model fills gaps in the input |

> **Real world:** For a network engineer the dangerous case is the last one. A model asked "why is VLAN 30 not passing on this trunk?" with no config attached will happily invent a plausible config. Attaching the real output removes the invention.

## Technique 1: ground the answer in supplied sources

**Grounding** means giving the model the material to answer from and telling it to use that material. Three habits do most of the work.

1. **Supply the source.** Paste the config, the log excerpt, the vendor note or the policy text. Without it the model answers from memory.
2. **Restrict outside knowledge.** Anthropic lists *external knowledge restriction* among its basic strategies: instruct the model to use only the provided documents and not its general knowledge. The idea is that if the answer is not in the documents, the model should not supply one.
3. **Say what to do when the source is silent.** This leads straight into the "I don't know" technique below.

```text
<document>
[output of "show running-config interface GigabitEthernet1/0/12"]
</document>

Answer only from the document above. Do not use general knowledge about
what such ports usually look like. If the document does not contain the
answer, reply "Not in the supplied output" and name what you would need.

Question: Which VLANs are allowed on this port?
```

Delimiters matter here (Domain 2.3): tags keep the pasted data separate from your instructions, and they let the question refer to "the document".

> **Watch out:** Grounding reduces invention; it does not guarantee the model read the document correctly. It can still misquote, skip a line or merge two entries. The next two techniques make the check cheap.

## Technique 2: ask for quotes first

For long inputs, Anthropic recommends having the model extract **word-for-word quotes** relevant to the question before it does the analysis (its guide mentions documents above roughly 20,000 tokens, but the habit is useful at any length). The extraction step anchors the later reasoning in actual text, and you can read the quotes to see whether the model found the right part.

```text
<policy>...</policy>

Step 1: Extract the exact sentences that deal with remote access MFA.
Put them in <quotes> tags, numbered. If there are none, write
"No relevant quotes found."
Step 2: Using only the numbered quotes, say whether the policy requires
MFA for VPN. Refer to quotes by number.
```

This is a two-step prompt chain in one prompt. The structure also gives you an audit trail: every statement in step 2 should point to a quote that you can find with Ctrl+F.

## Technique 3: ask for claim-level citations and retractions

Anthropic describes a stronger version: ask the model to make its response *auditable* by citing a quote or source for each claim, and then to **verify each claim after drafting** by finding a supporting quote. If it cannot find one, it must retract the claim. In their press-release example, unsupported claims are removed and the gap is marked with empty brackets.

```text
Draft the incident summary. Then review each claim in your draft. For
every claim, find a supporting line in the <logs> block and cite its
line number. Remove any claim you cannot support and mark the spot with [].
```

Two cautions:

- A citation is a **claim about a source**, not proof. Models can attach a plausible citation to a wrong statement. Spot-check by opening the cited line or page yourself.
- If the assistant has a built-in search or file-citation feature, the references it shows come from a retrieval step; if you ask for citations with no sources supplied, the model may invent references. Check every URL and document title before using them.

## Technique 4: let the model say "I don't know"

Models are trained to be helpful, and an answer feels more helpful than a refusal. Giving explicit permission to be uncertain removes some of the pressure to guess. Anthropic's guide lists *allow Claude to say "I don't know"* as a basic strategy: tell the model that it is acceptable, and preferred, to admit when it lacks sufficient information.

Make the permission concrete and give it a format:

```text
If you are not confident, or the information is not in the material, say
"I don't know" and list what you would need to find out. Do not guess.
Label each statement Confirmed (supported by the document), Inferred
(reasoned from it) or Unknown.
```

The labelled version is better than a vague "be careful": it creates a place in the output where uncertainty has to be written down, and it separates what the document says from what the model concluded.

> **Exam tip:** "Allow the model to say it does not know", "quote first" and "restrict to the provided documents" are the standard answers for reducing hallucinations when a question is about prompt design. "Make the model more confident" and "use a bigger model" are not.

## Technique 5: compare and chain

Anthropic's guide also lists approaches that use extra calls:

- **Chain-of-thought verification.** Ask the model to explain its reasoning step by step before answering, so you can spot a bad step. Reasoning text is evidence you can inspect, not proof the answer is right.
- **Best-of-N comparison.** Run the same prompt several times and compare. If three runs give three different answers, treat the content as suspect. Agreement is weaker evidence than it looks, because runs share the same blind spots.
- **Iterative refinement.** Feed the output back and ask the model to verify or expand earlier statements, which can catch inconsistencies.

## Putting it together: a grounded prompt for a network engineer

```text
<task>
Review the access-list below for entries that permit management
protocols from outside 192.0.2.0/24.
</task>
<rules>
- Use only the text in <acl>. No assumptions about other devices.
- Quote each entry you flag, exactly as written, with its sequence number.
- If an entry is ambiguous, list it under "Needs human decision".
- If nothing matches, say "No matching entries found."
</rules>
<acl>
[paste of: show ip access-lists MGMT-IN]
</acl>
```

Notice what it does: sources are supplied, outside knowledge is restricted, quotes are required, and both "nothing found" and "ambiguous" are legitimate outputs.

## Try it yourself

Run these in two assistants (for example ChatGPT and Claude, or Gemini) and compare.

1. Ask each, with no document: "What is the default hold timer for BGP in Cisco IOS-XE, and where is it documented?" Then ask it to name the exact documentation page. Check the answer against Cisco's own documentation. Note what you could and could not verify.
2. Paste a short sanitized `show ip interface brief` and ask a question the output cannot answer ("Which interface connects to the core switch?"). First without permission to say "not stated", then with it. Compare.
3. Paste a policy paragraph and use the quote-first prompt above. Check that each quote exists verbatim.
4. Ask for the same grounded answer three times in a new chat each time. Do the quotes match?

## Key takeaways

- Hallucination means fluent output that is wrong or unsupported; it does not signal itself.
- Exact strings (commands, IDs, versions, URLs, quotes) are the highest-risk content.
- Ground the answer: supply the source, restrict outside knowledge, say what to do when the source is silent.
- For long documents, extract word-for-word quotes first; then answer from the quotes.
- Ask for claim-level citations and require retraction of anything unsupported, then spot-check the citations yourself.
- Explicitly allow "I don't know" and give a format (Confirmed / Inferred / Unknown).
- Comparing multiple runs and chaining a verification step help, but none of these techniques eliminate hallucinations.
- Validate critical information outside the model.
