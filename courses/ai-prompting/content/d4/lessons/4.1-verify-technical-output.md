## The model writes syntax; you own the consequences

A command that is wrong in a chat window costs you a minute. The same command pasted into a production firewall can drop a management session. Verification is therefore part of the workflow, not a polite extra. The goal of this lesson is a repeatable routine for checking technical output before it touches anything real.

## How technical answers go wrong

| Failure | What it looks like | Network example |
|---|---|---|
| **Invented command or option** | Plausible syntax that does not exist | A `show` sub-command or a PowerShell cmdlet that no vendor ships |
| **Wrong platform dialect** | Real syntax, wrong operating system | Cisco IOS ACL wildcard syntax in a FortiOS policy, or `show ip route` on PAN-OS (which uses `show routing route`) |
| **Wrong version** | Real on another release | A feature or keyword absent from your firmware |
| **Right syntax, wrong semantics** | It parses but does not do what you asked | An ACL entry that permits more than intended because a subnet mask was used where a wildcard mask belongs |
| **Missing context** | It ignores something it cannot see | A change that breaks a VLAN not mentioned in the prompt |
| **Dangerous but valid** | Correct, and destructive | `no switchport trunk allowed vlan` removing the restriction the way you did not intend, or a `reload` |
| **Confident wrong explanation** | Right command, false reason | A correct `show` command with an invented interpretation of the output |

> **Watch out:** The risky outputs are the ones that look professional. Ask yourself of every command: does this exist on **this platform and this version**, and what exactly will it change?

## Check three things separately

Splitting verification into three questions keeps you from stopping after the first.

1. **Syntax:** Is it valid on the target OS and release?
2. **Semantics:** Does it do what the change request says, and nothing else?
3. **Blast radius:** What breaks if it is wrong, and how do I undo it?

A script can pass the first check and fail the other two.

## Verify against primary sources

The model is not a documentation source. Use it to draft, and the vendor to confirm.

- **Built-in help.** On Cisco IOS, type the command and press `?` at each token. FortiOS and PAN-OS CLIs also offer `?` and tab completion. If the CLI does not accept it, the model was wrong.
- **Vendor documentation.** Search the exact command in the platform's command reference for your release.
- **Show before you change.** Capture the current state (`show running-config | section ospf`, `get router info routing-table all` on FortiOS, `show routing route` on PAN-OS) and compare it with what the proposed change assumes.
- **Dry-run modes.** PowerShell supports `-WhatIf` on many cmdlets that change state, and `Get-Help <cmdlet> -Full` and `Get-Command` show whether a cmdlet and its parameters exist. PAN-OS has a candidate configuration, so changes can be reviewed and validated (`validate full`) before `commit`. FortiOS configuration errors can be read back with `diagnose debug config-error-log read` after a bad paste.
- **A lab.** Cisco CML, GNS3, EVE-NG, Packet Tracer, a FortiGate-VM trial or a throwaway VM catches the "valid but not what I meant" class of problems that no reading will.

> **Real world:** On IOS, `reload in 10` before a risky change and `reload cancel` afterwards is a classic safety net for remote work. It is a human practice you apply to AI-drafted changes too; the model does not know your session is over the link being changed unless you say so.

## Verify code differently

For PowerShell and Python the model may write tens of lines at once.

1. **Read it.** If you cannot explain a line, ask the model to explain it, then check the explanation against the documentation. Do not run code you do not understand against production.
2. **Check that every function exists.** Hallucinated calls are common: a method name that sounds right on a library that has a different one. For Netmiko the real connection methods are `send_command` and `send_config_set`; there is no `send_cmd`. Run the script against a lab device and see.
3. **Lint and test.** `python -m py_compile script.py`, a linter such as ruff, and a few `pytest` cases for parsing functions. In PowerShell, run the script with `-WhatIf` or against a test OU or test device first.
4. **Make it read-only first.** Ask for a version that only collects data (`show` commands, `Get-` cmdlets) before one that changes anything.
5. **Check error handling.** Does the script stop on failure, or keep pushing config to 40 more devices?

## Ask the model to help you check, with limits

Self-verification prompts are useful, but they come from the same model with the same blind spots.

```text
Review your own answer. For every command, state (1) the platform and
release you assume, (2) whether you are certain it exists, and (3) what
the command changes. Put anything you are not certain about under
"Verify in the vendor docs".
```

This will often surface uncertain items, but it can also produce confident-sounding false reassurance. Treat the output as a worklist for you to check, not as a pass.

Other helpful moves:

- Ask for the **vendor documentation section title** to search for. Searching a real title is a quick test; a title that does not exist is a red flag.
- Run the prompt in a **second assistant** and diff the answers. Where they disagree, check the docs. Where they agree, you still check, because two models can share a mistake.
- Ask for **expected output**, run the command in your lab, and compare. A mismatch teaches you either that the command differs or that your understanding does.

## A verification routine

```text
1. Paste target platform + version into the prompt (state it, don't assume).
2. Ask for a read-only first pass and the rollback commands.
3. Check every command with ? / docs / lab.
4. Compare intended change with a diff of the real config.
5. Apply in a window, with a rollback timer or console access.
6. Verify with show commands afterwards (the same ones you used before).
```

> **Exam tip:** If a question describes a model-suggested command that looks right but is unverified, the best next step is almost never "run it and see" on production. It is checking the vendor documentation or built-in help, then testing in a lab or a safe mode.

## Try it yourself

1. Ask two assistants: "Give me the FortiOS CLI to create an address object for 192.0.2.0/24 and a firewall policy from port1 to port2 using it." Run the answer in a FortiGate-VM or compare against the Fortinet CLI reference. Mark each line as correct, wrong or unverifiable, and note the difference between the assistants.
2. Ask the same question for PAN-OS. Check whether the answer uses a commit workflow (`set` commands in configure mode followed by `commit`) rather than applying immediately.
3. Ask for a PowerShell script to list the IPv4 addresses of all network adapters. Check each cmdlet with `Get-Command` and `Get-Help`. Which parameters, if any, did not exist?
4. Add to the prompt: "Tell me which lines you are unsure about." Does the assistant flag the lines you found wrong?

## Key takeaways

- Technical answers fail by inventing commands, using the wrong platform or version, being valid but wrong, or lacking context you did not supply.
- Verify syntax, semantics and blast radius as three separate checks.
- Built-in CLI help, vendor documentation and a lab are the primary checks; the model is a drafter, not a reference.
- Prefer read-only first passes, dry-run modes (`-WhatIf`, candidate configs) and rollback plans.
- For code, read it, confirm every function exists, lint and test it, and check its error handling.
- Self-review prompts and second opinions from another model produce a worklist, not proof.
- State the platform, OS release and constraints in the prompt rather than letting the model assume.
