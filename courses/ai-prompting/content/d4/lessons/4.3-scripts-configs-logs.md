## Where assistants help most in infrastructure work

A model is strong at reading, explaining, reformatting and drafting, and weak at knowing your network. Use it where a wrong answer is cheap to detect: review, explanation, first drafts, translation between syntaxes, and structured summaries. Keep it away from unattended changes. Everything in this lesson assumes the habits from 4.1 and 4.2: ground the answer in what you paste, redact secrets, and verify before you apply.

## Writing scripts

A good script prompt states the language and version, the target platform, the input, the output, the safety behaviour and the failure behaviour.

```text
Write a Python 3.11 script using Netmiko (device_type "cisco_ios") that:
- reads device IPs (one per line) from devices.txt
- runs "show version" and "show ip interface brief" on each
- saves each output to ./out/<ip>_<command>.txt
- is READ-ONLY: it must never call send_config_set
- reads credentials from environment variables NET_USER and NET_PASS,
  never hard-coded and never printed
- continues to the next device on failure and prints a summary table of
  successes and failures at the end
Return the full script, then a list of assumptions I should verify.
```

Notice the constraints: version, library, read-only, secret handling, failure handling, and a request to list assumptions. Netmiko uses `device_type` values such as `cisco_ios`, `fortinet` and `paloalto_panos`, and `send_command` for show commands versus `send_config_set` for configuration. For PowerShell, state the version (Windows PowerShell 5.1 or PowerShell 7), ask for `[CmdletBinding(SupportsShouldProcess)]` so `-WhatIf` works, and ask for comment-based help.

Review checklist for generated code:

1. Does every called function, cmdlet and parameter exist? Check with `Get-Command`, `Get-Help` or the library docs.
2. Are credentials read from the environment, a vault or a prompt rather than written into the file?
3. Is it read-only by default, with changes behind an explicit flag?
4. What happens on a timeout or authentication failure?
5. Is the output parsed with a real parser (TextFSM, ntc-templates, `ConvertFrom-Json`) rather than fragile string slicing?
6. Test on one lab device before the list.

## Reviewing and explaining configs

Reviewing is one of the best uses because the input is real and the output is a checklist you can verify.

```text
You are reviewing a Cisco IOS-XE access switch config before a change window.
Use only the config in <config>. Do not assume anything about other devices.
Return a table: Line | Finding | Risk (High/Med/Low) | Suggested fix | Confidence.
Check: management-plane ACLs, SSH version and transport inputs, password
storage, SNMP, unused ports, native VLAN, STP protections, logging and NTP.
If a topic is absent from the config, list it under "Not present".
<config>
[sanitized running-config]
</config>
```

For other platforms keep the same structure and name the checks the platform cares about.

- **FortiOS (FortiGate):** policy order and implicit deny, logging enabled on policies, administrative `allowaccess` on interfaces, trusted hosts for admin accounts, address and service objects reused consistently, VIPs and NAT settings, SSL VPN or IPsec phase settings.
- **PAN-OS (Palo Alto):** rule order and shadowing, zones, application-based rules versus `any`, security profiles attached, log forwarding, commit state (candidate versus running), management interface restrictions.
- **Cisco IOS:** wildcard masks, ACL direction and placement, `no shutdown` on intended ports, trunk allowed VLANs, `enable secret` rather than `enable password`.

Typical failure: a wrong subnet mask in an ACL. IOS ACLs use **wildcard** masks, so `permit ip 192.0.2.0 255.255.255.0 any` is wrong, whereas `permit ip 192.0.2.0 0.0.0.255 any` matches the /24. Spot-check models for this class of error, as they sometimes confuse masks.

> **Watch out:** A model that "reviews" a config will not tell you what is missing unless you ask. Give it a list of expected controls so absence becomes a finding.

You can also ask for **translation** (for example, "express this ACL as a FortiGate firewall policy"), **explanation** ("what does this route-map do, line by line"), or **a diff review** ("here is a before and after; list every behaviour change"). For translation, always verify the output by reading the result back on the target platform, because dialects differ in small but critical ways.

## Troubleshooting with show output and logs

Give the model the evidence, not the question alone. Include the symptom, the time, what changed, what you already tried and the exact output.

```text
Symptom: users in VLAN 20 lose connectivity for ~30 seconds, twice today.
Context: Catalyst access switch, uplink Gi1/0/48, STP mode rapid-pvst.
Already checked: cabling is fine.
Task: from the logs below, build a timeline and list the top three
hypotheses ranked by how well the evidence supports them. For each, name
the next read-only show command to confirm it. Do not invent log lines.
<logs>
%SPANTREE-2-ROOTCHANGE: Root Changed for vlan 20: New Root Port is GigabitEthernet1/0/48
%LINK-3-UPDOWN: Interface GigabitEthernet1/0/48, changed state to down
%LINK-3-UPDOWN: Interface GigabitEthernet1/0/48, changed state to up
</logs>
```

Why this works: the task is a timeline and ranked hypotheses (not a single confident cause), the follow-up checks are read-only (`show spanning-tree vlan 20`, `show interfaces GigabitEthernet1/0/48`, `show logging`), and "do not invent log lines" attacks a known failure.

Useful troubleshooting patterns:

- **Explain, then hypothesise.** Ask first for a plain explanation of each message, then for hypotheses.
- **One layer at a time.** Ask it to follow the OSI order (physical, link, network and so on) and name the evidence for each layer.
- **Ask what is missing.** "What additional output would change your ranking?"
- **Compare before and after.** Paste output from before and after the change and ask for differences only.
- **Treat advice as hypotheses.** The model reasons from text. It cannot see a flapping SFP or an overheated cable.

On FortiGate, similar prompts work with `diagnose debug flow` output and `get router info routing-table all`; on Palo Alto, with `show session id` output and `test security-policy-match`; on Windows, with `Get-WinEvent` extracts. The structure of the prompt stays the same. Remember logs are *untrusted* text (4.2): a log line or ticket comment could contain an injected instruction, so keep the assistant to analysis.

> **Real world:** Logs often contain usernames, internal IPs and tokens in URLs. Redact them with a placeholder mapping before you paste, and map the answer back afterwards.

## Keep the human in charge

- The model proposes; **you** run the change in your window with a rollback.
- Use read-only commands and read-only accounts when an assistant has any tool access.
- Capture the model's reasoning with the ticket, so a reviewer can see what was assumed.
- If a suggestion is risky, ask for the failure mode and the rollback, then check both.

## Try it yourself

1. Take a sanitized switch config from your lab. Run the review prompt above in two assistants. List the findings that both found, those only one found, and any you can confirm are wrong.
2. Feed both the same 15 lines of syslog from a lab outage and compare timelines. Which one invented content? Did the "do not invent log lines" instruction help?
3. Ask each to write a read-only PowerShell script that lists each interface's name, status and link speed (`Get-NetAdapter`). Check cmdlets with `Get-Help`, then run with `-WhatIf` where it applies.
4. Ask for the same Netmiko script as above, then diff the two responses and test it against a lab router.

## Key takeaways

- Use assistants for review, explanation, drafting and translation; keep unattended changes away from them.
- Script prompts should state language and version, platform, inputs and outputs, read-only behaviour, secret handling and failure handling.
- Review generated code for non-existent functions, hard-coded secrets, unsafe defaults and weak error handling.
- Config-review prompts need a checklist of expected controls so missing items are reported.
- IOS ACLs use wildcard masks; masks and dialect differences are common model errors.
- For troubleshooting, supply the symptom, context, already-checked items and exact output; ask for a timeline and ranked hypotheses with read-only confirmation commands.
- Redact secrets and identifiers, treat logs as untrusted data, and keep a human approving every change.
