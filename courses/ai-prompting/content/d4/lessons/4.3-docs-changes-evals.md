## Documentation, change plans and runbooks

Writing is where assistants save the most time, and where careless use creates the quietest mistakes. A runbook that reads well but contains one invented command is worse than no runbook, because someone will trust it at 3 a.m. The pattern: you provide the facts, the model provides the structure and prose, and you verify every technical statement.

### Feed it facts, not requests

A vague request ("write a change plan for upgrading the firewall") gets a generic template with invented details. Supply the real inputs and a template.

```text
Draft a change plan from the facts below. Use ONLY these facts. Where a
field has no fact, write "TBD - owner to supply" instead of inventing one.

<facts>
Change: add VLAN 240 (guest-iot) to access switches SW-A1 and SW-A2 and the
uplink trunks to DIST-1. Platform: Catalyst, IOS-XE (version in ticket).
Window: Saturday 02:00-04:00 local. Risk: trunks carry production VLANs.
Rollback owner: network on-call.
</facts>

<template>
1. Purpose and scope
2. Pre-checks (read-only commands, expected results)
3. Implementation steps (exact commands, numbered)
4. Verification (commands and expected output)
5. Rollback (exact commands, trigger conditions, time limit)
6. Impact and communication
7. Open questions
</template>
```

Why this works: the facts are fenced, the template is fixed, and the "TBD" rule gives the model a legitimate alternative to inventing. The "Open questions" section converts uncertainty into a list for you.

Then use the verification routine from 4.1 on the **Implementation** and **Rollback** sections. Key checks:

- Does every command exist on the stated platform and release?
- Is the rollback the true inverse of the change, including `no` forms and trunk `allowed vlan` semantics (`add` versus replacing the whole list)?
- Do verification steps use commands that would actually show a failure (`show vlan brief`, `show interfaces trunk`, `show spanning-tree vlan 240`)?
- Is there a trigger and a time limit for rollback?

For a firewall change, ask the plan to include policy-order impact, a before/after rule list, commit or push steps (PAN-OS commit, FortiManager install) and a way to confirm hit counts or logs afterwards.

### Runbooks

A runbook is a step list for someone who is stressed and has not seen this problem for a year. Ask for that audience explicitly.

```text
Write a runbook for "WAN circuit down at a branch", for a junior on-call.
Format: numbered steps; each step has Command, Expected output, If not as
expected. Read-only steps first; mark any step that changes configuration
with [CHANGE]. End with escalation criteria. Use only the commands listed
in <allowed-commands>.
```

Constraining the command list is a strong technique: you control the allowed vocabulary, so the model cannot add an unverified command. Review every `[CHANGE]` step line by line, and run the whole runbook once in a lab.

### Other documentation jobs

- **Incident summaries** from a timeline you provide; ask for facts, impact, cause (stated as confirmed or suspected) and follow-ups, and for no invented timestamps.
- **Config comments and README files** from sanitized configs.
- **Stakeholder versions** of the same technical text: give the audience (manager, auditor, junior) and length.
- **Diagrams as text** (Mermaid or draw.io XML) that you then render and check against reality.

> **Watch out:** AI-written documentation inherits the model's assumptions. Mark who verified it and when. A reviewed-by line is a cheap control.

## Evaluating prompts: test cases and comparing outputs

You have been editing prompts by feel. For a prompt you will use repeatedly (a log classifier, a config reviewer, a ticket summariser), "it worked once" is not evidence. Evaluation means testing a prompt against a small set of cases with known good answers and scoring the results. Model output varies from run to run, so one lucky answer proves little.

### Step 1: define success

Write down what a good result is. For a syslog classifier: correct label, one word, no extra text. For a config reviewer: finds the planted problems, invents none, cites line numbers.

### Step 2: build a small test set

Start with 10 to 20 cases. Include:

| Type of case | Example |
|---|---|
| **Typical** | Ordinary link-down log line |
| **Edge** | Truncated log line; mixed vendors in one paste |
| **Adversarial** | Contains an injected instruction (4.2) |
| **Negative** | Nothing is wrong; the right answer is "no finding" |
| **Missing information** | The question cannot be answered from the supplied text; the right answer is "unknown" |
| **Known past failure** | Something that went wrong in production before |

Each case stores the input and the expected result, or the criteria for it.

### Step 3: score with a rubric

Where answers are exact (a label, a JSON field, a command), compare automatically with a script. Where they are prose, use a short rubric scored by you: accuracy, completeness, no invented content, format followed, safe (no unrequested changes). Use a 0/1 or 1-to-3 scale and add comments. A second model can serve as a judge, but check its scores against your own on a sample before trusting it, because judges have their own biases.

### Step 4: compare versions

Change one thing at a time: the wording, the examples, the model or the temperature setting. Run the full test set each time and keep a simple table.

| Version | Change | Accuracy | Invented content | Format ok | Notes |
|---|---|---|---|---|---|
| v1 | baseline | 12/20 | 4 cases | 18/20 | |
| v2 | added 3 few-shot examples | 16/20 | 2 cases | 20/20 | |
| v3 | v2 + "say Unknown if absent" | 17/20 | 0 cases | 20/20 | Over-uses "Unknown" in 2 cases |

Run each case more than once if the output varies, and record how often it passes. Keep a log of prompt versions, in a Git repository if you can, along with the test set and results.

### Step 5: re-run when things change

Re-run the test set when you change the prompt, switch models, or the vendor updates a model. Model behaviour changes with versions, and old prompts can regress. Add every real failure to the test set so it cannot quietly return.

A tiny script is enough:

```python
import csv, json

def score(case, answer):
    # exact-match check for a classifier; swap in a rubric for prose
    return case["expected"].strip().lower() == answer.strip().lower()

# cases.csv columns: id,input,expected
# call your assistant API (or paste manually) and fill the dict below
results = {}
with open("cases.csv", newline="") as f:
    cases = list(csv.DictReader(f))
passed = sum(score(c, results.get(c["id"], "")) for c in cases)
print(json.dumps({"passed": passed, "total": len(cases)}))
```

You can do the same by hand in a spreadsheet with no code.

> **Exam tip:** Strong answers to "how do you know the new prompt is better?" mention a fixed set of test cases (including edge and adversarial cases), a defined success criterion, changing one variable at a time and re-testing after model changes. "It sounded better" and "it worked on my one example" are weak.

## Try it yourself

1. Pick a prompt you use often. Write 10 test cases (inputs plus the answer you expect), including one with nothing to find and one with an injected instruction.
2. Run them through two assistants with the same prompt. Score each output 0/1 for accuracy and note any invented content.
3. Improve the prompt (add two examples or an "Unknown" rule) and re-run all 10. Record the change in a table like the one above.
4. Ask an assistant to write a change plan from a fact sheet using the template above. Mark every command and check it against the vendor docs or a lab. How many were wrong or unverifiable?

## Key takeaways

- Give the model facts and a template, and let it write "TBD" instead of inventing details.
- Verify every command in a change plan, the rollback in particular, and the verification steps.
- Constrain runbooks to an allowed-command list, mark change steps and test them in a lab.
- Always record who verified AI-written documentation.
- Prompt evaluation = success criteria, a test set (typical, edge, negative, unknown, adversarial, past failures), a rubric or exact-match score, one change at a time.
- Compare prompt versions in a table, run cases more than once when output varies, and verify any model-as-judge against your own scores.
- Re-run the test set when the prompt or the model changes, and add each real failure as a new test.
