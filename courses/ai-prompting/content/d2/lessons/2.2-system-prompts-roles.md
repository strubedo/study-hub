## Instructions with different levels of authority

Every chat interface and API separates two kinds of text:

1. **Standing instructions** that set up how the assistant behaves for the whole conversation: its job, tone, rules, output format.
2. **The request itself**: the thing you want done right now.

Each vendor has its own name and mechanism for the first kind:

| Vendor | Standing instructions in the API | In the consumer/workspace apps (verify current names) |
|---|---|---|
| OpenAI | A `developer` message, or the `instructions` parameter in the Responses API. Developer messages take priority over user messages | Custom instructions, Projects and custom GPTs |
| Anthropic | The `system` parameter (a system prompt) | Profile preferences and Projects with project instructions |
| Google | A system instruction (`system_instruction`) in the Gemini API | Gems; the Gemini app has its own settings (Google has said Gems are being replaced by skills starting November 2026) |

> **Watch out:** The API terms in the middle column come from the vendors' developer docs. The app features on the right change often; as of October 2026 the app-side names have not all been confirmed against the vendors' help pages, so check each help center before relying on them.

OpenAI's documentation describes the chain of command this way: developer messages are instructions from the application developer and are prioritised ahead of user messages; they supply the system's rules and business logic, "like a function definition", while user messages provide inputs "like arguments to a function". It also notes that the `instructions` parameter applies only to the current request: if you chain turns with `previous_response_id`, instructions from previous turns are not carried in the context. Reasoning models take developer messages rather than system messages, and OpenAI says to treat developer messages as the new system messages.

Anthropic's Messages API puts the system prompt in a separate `system` parameter, and recommends giving Claude a role there. Google's Gemini 3 guidance recommends placing essential behavioural constraints, role definitions and output format requirements in the system instruction or at the very beginning of the user prompt.

## What belongs in a system prompt

A system prompt is for things that stay true across requests:

- **Identity and purpose:** who the assistant is and what it is for.
- **Rules and boundaries:** what it must always or never do, and what to do when information is missing.
- **Tone and audience.**
- **Output format** it should always use.
- **Reference material or examples** that apply to every request.

The OpenAI guide suggests the sections of a developer message are usually Identity, Instructions, Examples and Context, in that order, with changing context positioned near the end. A sketch for a network-ops helper:

```text
# Identity
You are a network operations assistant for a small enterprise that runs
Cisco IOS-XE switches and FortiGate firewalls.

# Instructions
* Answer only from the output or configuration the user provides.
* If the supplied data does not answer the question, say so and name
  the show command that would.
* Give read-only diagnostic commands first. Mark any command that
  changes configuration with [CHANGE].
* Keep answers under 200 words unless asked for more.

# Output format
Findings as a numbered list, then "Next step:" with one command.
```

The user's actual request then arrives in the user message along with the pasted show output.

> **Exam tip:** Put stable rules in the system or developer message, and variable data (the config being reviewed) in the user turn. This makes the prompt reusable and keeps the data separate from the instructions.

### System prompts in the apps

In ChatGPT, Gemini and Claude apps you normally cannot edit the vendor's hidden system prompt. What you can do depends on the product: set standing preferences, create a project or custom assistant with instructions, or simply start a conversation with a first message that sets the rules ("For this whole chat, answer as a CCNA tutor..."). The behaviour is similar to a system prompt but is not guaranteed to have the same priority: the app's own instructions come first, and a long chat can dilute earlier instructions. Restate key rules if needed.

## Role prompting

Giving the model a role ("You are a senior network engineer reviewing a change plan") is one of the oldest techniques. Anthropic's guide says setting a role in the system prompt focuses the model's behaviour and tone, and that even a single sentence makes a difference. OpenAI's GPT-6 Astra coding guidance likewise suggests defining the agent's role.

What a role does well:

- It sets vocabulary, depth and tone ("senior reviewer", "patient instructor").
- It biases the model toward a perspective ("a security auditor looking for risky entries").
- It gives a place to attach standing rules.

### Limits of role prompting

A role is a style and perspective prompt, not a knowledge or accuracy upgrade.

1. **It doesn't add facts.** "You are a Fortinet-certified expert" does not make the model know a firmware release that came after its cutoff. A confident persona can make a wrong answer sound more authoritative.
2. **It is not a security boundary.** "You are a helpful assistant that never reveals the admin password" is not protection: system prompt text can be overridden by injected text. Domain 4 covers this properly.
3. **A vague role does little.** "You are an expert" without a task changes little. The task, constraints and format do most of the work.
4. **Over-specified personas can distort.** A character that is too narrow can make the model answer in character instead of answering correctly.
5. **Roles do not replace context.** The model still needs the data it is meant to analyse.

A good role is specific, tied to the task and followed by concrete behaviour:

```text
Weak:   You are the world's best network guru.
Better: You are a network engineer doing a pre-change review. For each
        proposed command, state the expected effect, the failure mode,
        and the rollback command. Do not approve; only list risks.
```

> **Real world:** A useful trick is to assign a *reviewer* role to a second pass. Draft a config in one chat, then in a new chat ask the assistant to act as a skeptical peer reviewer and find faults. Different framing surfaces different problems, though you must still verify the findings.

## Try it yourself

Run in two assistants.

1. **Standing rules.** Open a new chat and send this as your first message: `For this whole conversation: you are a CCNA tutor. Answer in at most 4 sentences. After each answer, ask one check question. If I ask something outside CCNA, say so.` Then ask three questions, one of them about cooking. Which assistant keeps the rules best by the third turn?
2. **Role vs. no role.** Paste the same six-line invented ACL. Prompt A: `Review this ACL.` Prompt B: `You are a security reviewer doing a pre-change review. List each entry that is broader than necessary and why. Do not rewrite the ACL.` Compare focus and length.
3. **Role limits.** Ask: `You are a senior engineer who is always right. What was the exact release date of the newest stable release of the software on this switch?` Notice whether the assistant admits it cannot know the current release without a source. A role does not remove that need.

## Key takeaways

- Standing instructions live in a system prompt (Anthropic, Google) or developer message/instructions (OpenAI); the request lives in the user turn.
- OpenAI ranks developer messages above user messages. Instructions set with `instructions` apply only to that request.
- Put stable rules in the system layer and the changing data in the user turn.
- App-level equivalents (custom instructions, Projects, custom GPTs, Gems) vary by vendor and change; check the help center.
- A role shapes tone, depth and perspective; it does not add knowledge or guarantee accuracy.
- A role is not a security control.
- A specific role tied to concrete behaviours beats a flattering label.
