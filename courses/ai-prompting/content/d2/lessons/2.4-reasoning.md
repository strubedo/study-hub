## Chain-of-thought prompting

**Chain-of-thought (CoT) prompting** asks a model to work through a problem in intermediate steps before giving the answer, instead of jumping straight to a result. For a model that writes one token at a time, the steps it writes become part of its context, so later tokens can build on earlier ones. On multi-step tasks such as arithmetic, subnet maths, logic puzzles and troubleshooting trees, that usually improves accuracy.

The classic forms:

- **Zero-shot CoT:** add a cue such as "Think through this step by step before answering."
- **Few-shot CoT:** include examples that show the reasoning followed by the answer (Lesson 2.2).
- **Structured CoT:** specify what to reason about: "First list the subnets, then compare prefixes, then give the answer."

A subnet example:

```text
Do 192.0.2.130/26 and 192.0.2.190/26 sit in the same subnet?
Work through it step by step: find the block size, the network
address of each host, and compare. Then give the answer on a final
line starting with "Answer:".
```

A /26 has a block size of 64, so both addresses fall in 192.0.2.128/26 (range .128 to .191) and the answer is yes. Without the working, a model may pattern-match instead of calculating.

### Separating reasoning from the answer

A reasoning dump makes output long and hard to extract. Ask for a clearly marked final answer ("Answer:" on the last line, or an `<answer>` tag) so you or your script can pick it out. Anthropic's guide uses exactly this in its manual CoT fallback: ask for step-by-step thinking and put the final answer in `<answer>` tags.

> **Watch out:** Written-out reasoning is not proof. A chain of steps can read convincingly and still contain an arithmetic slip or a wrong premise, and a model can produce a tidy explanation for a wrong answer. Check the final result independently (Domain 4).

## Reasoning models change the advice

A **reasoning model** (Lesson 1.2) already produces an internal chain of thought before it responds. That changes how you prompt:

| Model type | Vendor guidance | Practical advice |
|---|---|---|
| **OpenAI reasoning models** | The reasoning-model guidance says these models perform best with straightforward prompts; techniques like "think step by step" may not help (and can sometimes hinder); avoid chain-of-thought prompts because the models reason internally | Give a clear goal, constraints and success criteria; do not script the reasoning. Try zero-shot first |
| **OpenAI GPT (non-reasoning) models** | Benefit from precise instructions that explicitly provide the logic and data; compared to a junior colleague who needs explicit instructions, while reasoning models are like a senior co-worker given a goal | Spell out the procedure; asking for steps is reasonable |
| **Gemini 2.5 and 3** | Models automatically generate internal thinking, so it is generally not necessary to have them outline or detail reasoning steps in the response; for heavy reasoning, a simple request like "Think very hard before answering" can help at the cost of extra thinking tokens | Use the model's thinking setting; add a short nudge if needed rather than a long plan |
| **Claude with thinking** | Prefer general instructions over prescriptive steps: "think thoroughly" often beats a hand-written plan. Manual CoT is a fallback when thinking is off. On several newest models (Fable 5.1, Fable 5, Opus 5.5, Opus 5, Sonnet 5.5) rely on thinking; a prompt that asks the model to write out its reasoning in tags may be declined | Use adaptive thinking and the effort setting; keep the prompt goal-focused |

The shared theme: with a reasoning model, put your effort into the goal, the context and the success criteria, and let the model plan. With a standard model, or with thinking turned off, asking for step-by-step working still helps on multi-step tasks.

> **Exam tip:** "Think step by step" is not wrong in general. It is *unnecessary or counterproductive* on dedicated reasoning models, per OpenAI's guidance, and it is still a valid technique on standard models. Look at the model type in the question.

### Reasoning is a cost trade-off

Thinking uses extra tokens, which add latency and cost (Lesson 1.1). Both Anthropic and Google note this. Use it when the task is genuinely multi-step: debugging a routing loop, comparing designs, auditing a ruleset. Skip it for simple extraction or reformatting, where it adds delay and sometimes overcomplication. Anthropic even shows a prompt to steer a model away from thinking too often on simple queries: use thinking only when it will meaningfully improve answer quality, and when in doubt respond directly.

## Self-checking and verification

You can ask the model to check its own work. Anthropic suggests appending something like "Before you finish, verify your answer against [test criteria]" and says this catches errors reliably, especially in coding and math. It notes one exception: Claude Opus 5 verifies its own work well without being told, and added verification instructions can cause over-verification.

Patterns:

1. **Checklist verification.** "Before answering, check that every command is valid on IOS-XE, that no step drops the management session, and that a rollback is included. Fix anything that fails."
2. **Draft, critique, revise.** In one prompt or three: generate, review against criteria, rewrite. Anthropic calls this the most common chaining pattern.
3. **Independent reviewer.** Open a new chat and ask another assistant to find errors in the output. Different context gives different blind spots.
4. **Test it.** For code and configs, ask for test cases or expected output, then run them. This is stronger than the model's opinion of itself.
5. **Ask for evidence.** "Quote the line in the log that supports each conclusion."

The limit: a model reviewing its own output shares its blind spots. If it believes a command exists, it often confirms that it exists. Self-checking reduces some errors, but it is no substitute for running the command in a lab or reading the vendor documentation.

## Breaking a problem into steps

Complex tasks fail when one prompt tries to do too much. Decompose them.

**Inside one prompt:** number the steps (Lesson 2.1) or name the phases: "1. Extract the facts. 2. Identify the contradictions. 3. Propose the fix."

**Across prompts (prompt chaining):** make each step its own request, with the output of one feeding the next. Google's guide describes breaking down instructions into one prompt per instruction, chaining prompts in sequence, and aggregating parallel results. Anthropic says chaining is still useful when you need to inspect intermediate outputs or enforce a specific pipeline structure, even though adaptive thinking handles much multistep reasoning internally.

Example chain for a change request:

1. Extract: list every device and command mentioned in the plan.
2. Check: for each command, state the expected effect and the risk.
3. Assemble: write the final review in the ticket template.

Benefits: you can inspect and correct each step, each prompt is simpler, and you can use a fast model for easy steps and a stronger one for hard steps. Cost: more calls and the need to pass context between them. Domain 3 builds on this.

## Try it yourself

Run in two assistants, once on a standard/fast mode and once on a thinking or reasoning mode if the app offers one.

1. **CoT on or off.** Prompt A: `Which of these addresses are in 198.51.100.64/27: .70, .95, .100, .127? Answer only.` Prompt B: same question plus `Work out the range first, then answer.` Compare. Then repeat B on the reasoning mode with no step-by-step cue and see whether the answer quality changes.
2. **Self-check.** Ask for a 6-line ACL, then in the same chat: `Check your ACL against these criteria: ... Then list any errors and correct them.` Did the second pass find anything real? Verify manually.
3. **Decompose.** Take a messy invented change plan (about 15 lines). Run it as a single prompt: `Review this plan.` Then as a three-prompt chain (extract, assess, summarise). Which version caught more problems, and which was easier to check?

## Key takeaways

- Chain-of-thought asks for intermediate steps, which improves multi-step tasks on standard models.
- Mark the final answer separately ("Answer:" line or tag) so it is easy to extract.
- Written reasoning can still be wrong; verify the result independently.
- OpenAI says reasoning models do not need "think step by step" and may do worse with it; GPT (non-reasoning) models want explicit instructions.
- Gemini 2.5 and 3 think internally, so you need not spell out reasoning; a short nudge can help.
- Claude: prefer general instructions like "think thoroughly" over scripted steps; manual CoT is the fallback when thinking is off, and on the newest models rely on thinking.
- Self-check prompts help, but a model shares its own blind spots; use tests, evidence and an outside check.
- Break big tasks into numbered steps or a chain of prompts so intermediate results can be inspected.
