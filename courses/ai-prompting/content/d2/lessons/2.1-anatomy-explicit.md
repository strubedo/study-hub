## Why most bad answers start with bad prompts

A large language model can only work with the text it is given. It cannot see your network, your change ticket or your last meeting. Anthropic's prompting guide puts it this way: treat the model like a brilliant new employee who lacks context on your norms and workflows. Its suggested test is to show your prompt to a colleague who has no background on the task and ask them to follow it. If they would be confused, the model will be too.

Compare two prompts a network engineer might type:

```text
Weak:   Tell me about this ACL.
Better: Review the extended ACL below, which filters traffic into the
        management VLAN on a Cisco IOS switch. List every entry that
        permits more than SSH and SNMP from the 192.0.2.0/24 admin
        subnet, explain the risk in one sentence each, and give the
        corrected lines. Output a table with columns: line, risk, fix.
```

The second one is longer, and every added word removes a guess the model would otherwise make.

## The four building blocks

Most good prompts contain four things. The order below is a convenient checklist, not a law, and OpenAI's guide, for example, describes developer messages that combine identity, instructions, examples and context.

| Block | Question it answers | Example |
|---|---|---|
| **Context** | What situation or data is this about? | "This is the running-config of an access switch in a lab. The admin subnet is 192.0.2.0/24." |
| **Task** | What exactly should be done? | "Find entries that permit more than SSH and SNMP." |
| **Constraints** | What limits apply: scope, length, things to include or avoid, what to do when unsure? | "Only use the config below. If something cannot be determined from it, say so." |
| **Output format** | What shape should the answer take? | "A table with columns line, risk, fix." |

Gemini's own guide lists the same ideas under different names: instructions, constraints, response format, and optional context. The vendors agree on the substance even when their headings differ.

> **Exam tip:** If a question shows a prompt that gets a vague answer, check which block is missing. Missing context produces generic advice; a missing task produces a summary instead of an action; missing constraints produces scope creep or invented details; missing format produces prose you then have to reformat.

## Be explicit about what you want

Anthropic's guide says that current Claude models respond well to clear, explicit instructions and that if you want more than the task strictly requires, you should ask for it rather than expect the model to infer it. Two practical consequences:

1. **Say the verb you mean.** "Can you suggest some changes to this function?" may get suggestions, not edits. Anthropic's example contrasts that with "Change this function to improve its performance." For a switch config, "Review" and "Rewrite" are different jobs; "Fix" and "Explain" are too.
2. **Specify success.** OpenAI's guidance for reasoning models adds that you should give very specific parameters for a successful response. "Under 150 words", "no more than five findings", "ranked by severity", "using only commands valid on IOS-XE" all define done.

Where the task needs a procedure, number the steps. Anthropic recommends sequential steps in numbered lists or bullets when order or completeness matters:

```text
1. Parse the show interfaces output below.
2. List interfaces with input errors greater than zero.
3. For each, say whether CRC, runts or giants dominate.
4. Suggest one next diagnostic step per interface.
```

## Give the why

Instructions work better when the model knows the purpose. Anthropic's example: instead of "NEVER use ellipses", write that the response will be read aloud by a text-to-speech engine, so ellipses should be avoided because the engine cannot pronounce them. The model can then generalise: it will also avoid other symbols a speech engine would stumble over. A bare rule only covers the case you thought of.

For IT work this is easy to apply:

- "Keep commands to one line each **because** I will paste them into a console over a slow serial link."
- "Do not suggest reloading the device **because** this is a production core switch with no maintenance window."
- "Explain it simply **because** the reader is a help-desk analyst on their first week."

> **Real world:** The "why" also protects you from the model's helpfulness. If you say a change window is open only 15 minutes, a good answer will drop the elaborate migration plan and propose the smallest safe step.

## Say what to do when information is missing

A common failure is a model that fills gaps with plausible inventions. Add a rule for the gap:

```text
If the log does not contain enough information to name a root cause,
say "insufficient evidence" and list what additional output you would
need (for example show logging, show interface counters).
```

This does not make hallucination impossible (Domain 4 covers verification), but it gives the model a legitimate alternative to guessing.

## A worked rewrite

Before:

```text
Write a PowerShell script for DHCP.
```

After:

```text
Write a PowerShell 5.1 script for a Windows Server 2022 DHCP server.
Context: scope 198.51.100.0/24, lab environment, I run it manually.
Task: list every lease expiring in the next 24 hours.
Constraints: read-only (no changes to the server), use only built-in
DhcpServer module cmdlets, include comment-based help, handle the case
where the server is unreachable with a clear error message.
Output: the script in one code block, then three bullet points on how
to test it. No other commentary.
```

Notice the pieces: context (version, scope, environment), task, constraints (read-only, built-ins, error handling), and output format (code block plus three bullets). Also notice that the prompt names a safe default, read-only, which is a reasonable thing to demand of generated administrative code.

## Try it yourself

Run each pair in two assistants (for example ChatGPT and Claude, or Gemini and Claude). Use fresh chats so earlier context does not leak in.

1. **Vague vs specific.** Prompt A: `Explain OSPF.` Prompt B: `Explain OSPF to a CCNA candidate who already understands static routing. Cover only neighbor states from Down to Full, with one sentence per state, then a three-line example of a show ip ospf neighbor output using 192.0.2.1 and 192.0.2.2. Under 200 words.` Note which blocks B adds and how the answers differ in length and focus.
2. **The missing why.** Prompt A: `Never give me more than 10 lines.` Prompt B: `I read answers on a phone terminal that shows only 10 lines, so keep every answer within 10 lines; if more is needed, ask which part I want first.` Then ask a question whose honest answer is long. See how each assistant handles it.
3. **Permission to say unknown.** Paste an invented four-line syslog excerpt that does not show the root cause and ask `What caused this outage?` Then repeat adding the "insufficient evidence" instruction above. Compare whether the assistant invents a cause.

## Key takeaways

- Models only know what is in the prompt: supply context, not just a topic.
- A reliable checklist is context, task, constraints and output format.
- Use a precise verb (review, rewrite, list, explain): asking to "suggest" may get suggestions rather than action.
- Define success with measurable limits such as length, count, ranking and allowed sources.
- Explaining why an instruction exists lets the model generalise it correctly.
- Number the steps when order or completeness matters.
- Give the model a legitimate way to say "I can't tell from this" so it does not guess.
- Test: would a new colleague with no background understand your prompt?
