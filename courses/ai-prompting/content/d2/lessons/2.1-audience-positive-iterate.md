## Audience and tone

The same facts can be written for very different readers. Tell the model who will read the output and how it should sound. Compare:

```text
Summarize this incident for the VP of IT: two sentences, no jargon,
focus on business impact and expected time to restore.
```

```text
Summarize this incident for the on-call network engineer taking over
at shift change: bullet list, include device names, interface names,
the last command run and the next planned step.
```

Same incident, two outputs. Without an audience the model writes for an imagined average reader and satisfies nobody.

Useful audience and tone levers:

- **Reader's knowledge:** "assume the reader knows VLANs and trunking but not STP internals".
- **Purpose:** to decide, to execute, to learn, to audit.
- **Tone:** formal, plain, neutral, friendly, blunt. Name one.
- **Length and density:** "three sentences", "one paragraph", "exhaustive reference".
- **Vocabulary:** "define acronyms on first use" or "use the terms from the Cisco documentation".

> **Watch out:** Tone words are easy to over-apply. "Be extremely thorough and cover every possibility" can bury the one finding you needed. Anthropic's guide notes in several places that language tuned to push older models harder can make newer, more responsive models overdo things. Ask for the level you actually want, then adjust.

## Positive instructions versus "don't" lists

Telling the model what to do generally works better than listing what to avoid. Anthropic's formatting guidance gives a direct example: instead of "Do not use markdown in your response", try "Your response should be composed of smoothly flowing prose paragraphs." A negative instruction names the thing you don't want, which keeps that thing in play, and it leaves the model to guess the alternative.

| Instead of | Try |
|---|---|
| Don't write long answers. | Answer in three sentences or fewer. |
| Don't use jargon. | Write for a help-desk analyst; define any acronym on first use. |
| Don't make up commands. | Use only commands that appear in the supplied documentation; if one is missing, say so. |
| Don't use bullet points. | Write in complete paragraphs. |
| Never reboot the device. | Propose only non-disruptive diagnostic steps. |

Negative constraints are not forbidden. Gemini's guide says plainly that you can tell the model what to do and not to do, and a hard boundary such as "do not include real customer names; replace them with CUSTOMER-A" is a legitimate constraint. The lesson is about emphasis: pair every prohibition with the desired behaviour, and give the reason where you can. A long list of "don't" lines with nothing positive tends to produce evasive, hedged output.

Two further tips from the vendor guides:

1. **Match your prompt style to the output style.** Anthropic notes that the formatting of your prompt can influence the formatting of the response. A prompt full of bullets and bold tends to produce bullets and bold.
2. **Put critical constraints early.** Google's Gemini 3 guidance recommends placing essential behavioural constraints, role definitions and format requirements in the system instruction or at the very beginning of the user prompt.

## Iterating on a prompt

Your first prompt is a draft. The skill is iterating deliberately rather than rewriting at random.

A repeatable loop:

1. **Run it** on a realistic input, ideally two or three different inputs.
2. **Name the gap.** What exactly was wrong: missing context, wrong scope, wrong format, wrong tone, factual error? Write it down.
3. **Change one thing.** Add the missing block, tighten one constraint, add an example. One change at a time lets you see what helped.
4. **Re-run on the same inputs** and compare.
5. **Keep a note** of the version that worked, and the assistant, mode and date.

Two ways to iterate:

- **Within the chat:** follow up with a targeted correction: "Keep that structure, but cut the intro and put the risk first." This is quick, but the history stays in context, so a long thread can drift or carry old mistakes forward. When a chat gets messy, start fresh with the improved prompt.
- **By editing the original prompt:** better when you intend to reuse it. Edit, re-run in a clean chat, and compare.

Ask the model to help. Anthropic's guide suggests asking Claude to critique your examples, and the same idea works for the whole prompt: "Here is my prompt and the output I got. What is ambiguous in my prompt, and how would you rewrite it to get [the output I wanted]?" Treat the answer as a suggestion to test, not as truth. The model is guessing about itself.

OpenAI recommends two practices once a prompt matters: pin production applications to specific model snapshots because different snapshots in the same family can respond differently, and build tests and evaluations to monitor behaviour when you change the prompt or upgrade the model. Domain 4 comes back to evaluation; for now, the habit is to keep three or four test inputs, including one awkward edge case, and rerun them whenever you change a prompt.

> **Real world:** When a model "ignores" an instruction, check these first, in order: is it buried in a long paragraph, does another instruction contradict it, is it a prohibition that could be a positive instruction, and is the example (if any) showing something different? Fix the prompt before blaming the model.

## Common failure patterns and fixes

| Symptom | Likely cause | Fix |
|---|---|---|
| Generic, textbook answer | No context or audience | Add the situation and reader |
| Answer too long or too short | No length or depth limit | State count, length or depth |
| Wrong format | Format never specified, or contradicted by examples | State it; make examples match |
| Invented details | No source and no permission to say unknown | Supply the source; allow "not stated" |
| Does a different task | Verb or scope ambiguous | Use a precise verb; state what is out of scope |
| Ignores one instruction among many | Too many competing instructions | Number them; split the task; move key ones first |

## Try it yourself

Use two assistants and a fresh chat each time.

1. **Audience swap.** Paste an invented incident note (for example: `At 02:14 UTC, uplink Gi1/0/48 on sw-access-07 flapped for 3 minutes; STP reconverged; users on VLAN 20 lost connectivity.`). Ask for a summary for (a) an executive and (b) the next on-call engineer. Compare detail, vocabulary and structure.
2. **Negative to positive.** Prompt A: `Explain DNS. Don't be too technical, don't use long sentences, don't use lists.` Prompt B: `Explain DNS to a non-technical manager in short paragraphs of plain sentences, using one everyday analogy.` Which result better matches what you wanted?
3. **Three-round iteration.** Start with `Write a runbook for replacing a failed switch.` Run it, note the gap, then improve it in two rounds by adding one change each time (for example the reader and environment, then a format). Record each version and which assistant needed fewer rounds.

## Key takeaways

- Name the reader, their knowledge level, the purpose and the tone; otherwise the model writes for an average reader.
- Prefer positive instructions ("answer in prose paragraphs") over lists of prohibitions.
- Prohibitions are valid for hard boundaries; pair them with the desired behaviour and a reason.
- Your prompt's own style influences the response style.
- Put critical constraints and format requirements early.
- Iterate in a loop: run, name the gap, change one thing, re-run on the same inputs.
- Start a fresh chat once a long thread drifts, and keep your best prompt versions and test inputs.
- Different model snapshots can respond differently, so re-test prompts after model changes.
