## One job per prompt

Lesson 2.4 introduced decomposition. This lesson turns it into a working method. **Prompt chaining** means splitting a task into stages, running each stage as its own request, and feeding the output of one stage into the next. Instead of asking "review this change plan and write the ticket", you run something like extract, then assess, then draft.

Anthropic's documentation describes the same idea: breaking a task into sequential calls is still useful when you need to inspect intermediate outputs or enforce a specific pipeline structure, even though newer models can do a lot in a single request. That sentence is the whole decision rule. Chain when the intermediate results matter. Do not chain just because chaining sounds more advanced.

## Why chain

| Benefit | What it means in practice |
|---|---|
| **Focus** | Each prompt has one job, so instructions are short and less likely to conflict |
| **Inspection** | You can read the output of stage 2 before stage 3 consumes it, and fix it |
| **Different tools per stage** | A fast, cheap model for extraction; a stronger model for judgment; code (a regex or a script) for anything deterministic |
| **Testing** | You can test and improve one stage without rewriting the whole pipeline |
| **Control** | You can validate a stage's output (is the JSON valid? are all hostnames in the inventory?) and stop early on failure |

The costs are real: more requests, more latency, more tokens, and the work of passing context between stages. If a single clear prompt gets a correct result, a chain only adds overhead.

## A worked chain: change-request review

Suppose you paste a change plan and want a risk review in a ticket template.

```text
Stage 1 - Extract (fast model, structured output)
  Input:  <plan> the raw change plan </plan>
  Task:   List every device and every command in the plan.
  Output: JSON array of {"device": "...", "command": "..."}

Stage 2 - Assess (stronger model)
  Input:  <commands> the JSON from stage 1 </commands>
  Task:   For each command state the expected effect, the failure
          mode, and the rollback. Write "unknown" if you cannot tell.
  Output: Table: device | command | effect | risk | rollback

Stage 3 - Draft
  Input:  <assessment> the table from stage 2 </assessment>
          <template> your ticket template </template>
  Task:   Fill the template. Do not add commands that are not in
          the assessment.
```

Notice what the design does. The extraction stage is checkable: a person or a script can compare the command list with the original plan. The assessment stage works on a clean list instead of a messy document. The drafting stage is told to use only what the earlier stage produced, which limits invention.

## Pass data cleanly between stages

Most chain failures are hand-off failures, not model failures.

- **Wrap each stage's output in a delimiter** when you feed it forward (`<assessment>...</assessment>`), as in Lesson 2.3. The next prompt then treats it as data.
- **Use a structured format** (JSON, a table, a fixed template) for intermediate output you will parse or compare. Validate it in code before the next stage runs.
- **Pass only what the next stage needs.** Dragging the whole conversation forward wastes context and invites the model to re-do earlier work.
- **Keep the original source reachable.** If stage 3 only sees stage 2's summary, an error in stage 2 can never be caught. For high-stakes work, give the final stage the source as well and ask it to quote.
- **Say what to do with gaps.** Tell each stage to write "unknown" or "not stated" instead of guessing, and decide what your pipeline does when it sees that value.

> **Watch out:** Errors compound along a chain. A wrong hostname extracted in stage 1 is faithfully assessed in stage 2 and confidently written up in stage 3. Put a check after the stages where a mistake would be expensive.

## Common chain patterns

1. **Extract, then analyze, then write.** The change-review example above.
2. **Draft, critique, revise** (the self-correction pattern). Anthropic calls this the most common chaining pattern: generate a draft, have the model review it against explicit criteria, then have it refine based on the review. It works best when the critique prompt contains concrete criteria ("check every command against this list of banned commands") rather than "is this good?". The critic is still the same kind of model with the same blind spots, so for facts or code, test outside the model too.
3. **Classify, then route.** A first prompt labels a ticket (network, server, security); the label selects which specialist prompt runs next. This is a simple form of a workflow with branches.
4. **Map, then reduce.** Run the same prompt over many pieces (each log file, each page), then run one prompt to combine the results. The next lesson uses this for documents that are too large for one request.
5. **Generate, then verify with a tool.** The model writes a script or a config; you run a linter or a test; a final prompt receives the error output and repairs the code. The deterministic check is what makes this reliable.

## Chain or single prompt?

| Situation | Better choice |
|---|---|
| Short task, one clear output | Single prompt |
| Several distinct jobs with different formats | Chain |
| You need to approve or edit an intermediate result | Chain |
| Later steps depend on branching logic | Chain (or an agent, covered in the agents lesson) |
| Reasoning model with a well-specified multi-part task | Try a single prompt first; reasoning models plan internally |
| Output must be auditable step by step | Chain, saving every intermediate output |

A chain is also not the same as one long chat. In a chat, every earlier turn stays in context, which is convenient but can drift. In a designed chain, each stage gets exactly the input you choose.

## Chains in the chat apps versus code

You do not need code to chain. In an app you can do it by hand: run stage 1, read the result, paste the good parts into a fresh chat or a new message with delimiters, and continue. Starting stage 2 in a fresh chat avoids carrying along earlier misunderstandings. In code, an orchestration script calls the API once per stage and handles validation, retries and logging. Frameworks exist for this, but a plain script with three function calls is enough to learn the pattern.

> **Real world:** A network team that triages alerts may use a three-stage chain: one prompt summarizes the raw alert text, a second classifies severity from a fixed list, and a script (not a model) opens the ticket only if the severity value is one of the allowed strings. The model never gets to invent a severity because the script rejects anything outside the list.

## Try it yourself

Run these in two assistants (for example ChatGPT and Claude, or Gemini and Claude).

1. **Single versus chain.** Invent a 15-line change plan for two switches and a firewall rule (use `192.0.2.0/24` addresses and fake hostnames). First prompt: `Review this change plan for risk and write the result as a ticket.` Then run the three-stage chain above in three separate messages. Compare: which version found more problems, and which was easier to correct?
2. **Plant an error.** In the extraction stage, edit the model's JSON by hand to remove one risky command. Run stages 2 and 3. Notice that the final ticket never mentions it. This shows how compounding errors look.
3. **Draft, critique, revise.** Ask for a 6-step rollback procedure. In a second message give the critic prompt with three explicit criteria (for example "every step names a device, every step has a verification command, no step depends on a later one"). Then ask for a revision. Did the critique find real problems or invent trivial ones?

## Key takeaways

- Prompt chaining splits a task into sequential prompts, with each output feeding the next.
- Chain when you need inspection, different formats or models per stage, branching, or step-by-step testing; skip it when one clear prompt works.
- Delimit and validate the data passed between stages; use structured output for intermediate results.
- Errors compound along a chain, so check the stages where a mistake is costly and keep the source reachable.
- Draft, critique, revise is the most common chain, and its critique needs concrete criteria.
- Use code, not a model, for steps that are deterministic, such as validating allowed values.
- Reasoning models plan internally, so test a single prompt before building a chain.
