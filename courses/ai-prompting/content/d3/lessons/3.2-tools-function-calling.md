## Why models need tools

On its own, a language model only produces text from patterns in its training data and its context (Lesson 1.1). It cannot check today's weather, read your inventory database, run a Python script or open a ticket. **Tools** give it hands: the model decides it needs an outside capability, asks for it in a structured way, something else carries it out, and the result goes back to the model so it can continue.

The key fact to remember: **the model does not run anything itself.** It emits a structured request. Either your application or the vendor's servers execute it.

## Function calling (tool use)

All three vendors use the same basic loop. OpenAI calls it function calling (also known as tool calling), Anthropic calls it tool use (also described as function calling), and Google calls it function calling.

```text
1. You define tools: a name, a description, and a JSON Schema
   for the arguments.
2. You send the user's message plus the tool definitions.
3. The model replies with a TOOL CALL instead of final text:
      name = get_interface_status
      arguments = {"device": "core-sw1", "interface": "Gi1/0/48"}
4. YOUR code runs the function and gets a result.
5. You send the TOOL RESULT back to the model.
6. The model writes the final answer using the result
   (or makes another tool call).
```

Terms by vendor, as of October 2026:

| Concept | OpenAI | Anthropic | Google |
|---|---|---|---|
| Tool definition | function tool with a JSON Schema | tool with `input_schema` | function declaration |
| Model's request | a function call item in the output | a `tool_use` block, with `stop_reason: "tool_use"` | a function call part |
| Your reply | a `function_call_output` item matched by `call_id` | a `tool_result` block | a function response part |

You do not need to memorize field names. Know the shape: definition, call, result, final answer.

### A tool definition is a prompt

The model chooses a tool and fills in arguments based on what you wrote in the name, the description and the parameter descriptions. Treat those as prompt text.

```json
{
  "name": "get_interface_status",
  "description": "Return the admin and operational state and error counters for one interface on a managed switch. Use when the user asks whether a port is up, down or erroring. Read-only.",
  "input_schema": {
    "type": "object",
    "properties": {
      "device":    {"type": "string", "description": "Inventory hostname, e.g. core-sw1"},
      "interface": {"type": "string", "description": "Full interface name, e.g. GigabitEthernet1/0/48"}
    },
    "required": ["device", "interface"]
  }
}
```

Good tool definitions:

- Have a **clear, specific name** (`get_interface_status`, not `tool1`).
- Say **when to use it and when not to** in the description, and whether it is read-only or changes state.
- Describe each parameter with an example and allowed values (use `enum` for fixed sets).
- Keep the **number of tools modest**; many overlapping tools confuse selection. Both OpenAI and Anthropic now document a "tool search" approach for loading rarely-used tools only when needed.
- Return **compact, relevant results**. A 50,000-token tool result fills the context window.

### Safety rules for the code behind a tool

- **Validate arguments** in your code. The model's arguments are untrusted input, just like a web form.
- **Least privilege.** A read-only credential for a read-only tool. Do not expose a "run any CLI command" tool unless a human approves each command.
- **Separate reads from writes**, and require confirmation for writes.
- **Treat tool results as data.** A tool result can carry attacker-controlled text (a web page, a ticket body, a log line) that tries to give the model instructions. This is indirect prompt injection (Domain 4).
- **Log** every call with its arguments.

## Hosted (built-in) tools

Vendors also run some tools for you, so you do not write the function or execute it:

| Tool | What it does | Notes |
|---|---|---|
| **Web search** | Fetches current web content and returns an answer with cited sources | OpenAI web search (Responses API); Anthropic's web search tool is a server tool, run on Anthropic's infrastructure; Google offers grounding with Google Search |
| **File search** | Searches your uploaded files with retrieval (Lesson 3.1) | OpenAI's File Search uses vector stores and semantic plus keyword search |
| **Code execution** | Runs code the model writes in a sandbox and returns the output | Anthropic's code execution tool runs Bash commands and file edits in a sandbox; OpenAI and Google document code interpreter and code execution tools |
| **Image generation** | Creates or edits images from a prompt | OpenAI's image generation tool and Gemini's native image generation; see the next lesson |
| **Computer use** | Operates a graphical desktop with screenshots, mouse and keyboard | See the agent lesson |

Anthropic's documentation draws the clear line: **client tools** (your own functions, plus Anthropic-defined schemas such as `bash` and `text_editor`) run in your application, which returns the `tool_result`; **server tools** (such as `web_search`, `web_fetch`, `code_execution`) run on Anthropic's infrastructure, so you see the results directly.

## Web search in the apps

In the chat apps, search is usually a toggle or happens automatically when the model decides it needs current information. What to do:

1. **Ask for sources**, and open them. Citations show where a claim came from; they do not prove the page is right.
2. **Say when freshness matters** ("as of today", "check the vendor's current release notes").
3. **Be specific** about versions and platforms in the query ("FortiOS 7.4 SD-WAN rule order" is better than "SD-WAN rules").
4. **Watch for paraphrase errors.** Models may summarize a page inaccurately; for commands and numbers, read the source.
5. **Know the limits.** Search results can be low quality, out of date, or poisoned by hostile pages.

> **Exam tip:** Search (retrieval) improves currency and gives citations, but it does not eliminate hallucination. Verify against the cited source for anything that matters.

## Code execution

A code-execution tool lets the model write a program, run it and read the real output. This matters because models are weak at exact arithmetic, counting, sorting and parsing large data, and strong at writing code that does those things. Practical uses:

- Subnet calculations and CIDR summarization with Python's `ipaddress` module.
- Parsing a CSV or a long log and counting occurrences.
- Plotting latency or bandwidth data.
- Converting formats (CSV to JSON, YAML to a config template).

Prompt tips: ask the model to **show the code and the output**, ask it to check results with a second method, and state the input file and the desired output format. Remember that the sandbox is the vendor's, with no access to your network; it cannot reach `192.0.2.1` on your lab.

```python
# What a code-execution tool might run for a subnet question
import ipaddress
nets = ["198.51.100.0/26", "198.51.100.64/26", "198.51.100.128/26"]
print(list(ipaddress.collapse_addresses(map(ipaddress.ip_network, nets))))
```

> **Watch out:** Code the model writes can be wrong, and code run in a sandbox does not prove it is right for your environment. Read it before running it anywhere that matters.

## The Model Context Protocol (MCP)

Before MCP, each AI application needed custom code for each tool or data source. The **Model Context Protocol** is an open-source standard for connecting AI applications to external systems: data sources such as local files or databases, tools such as search engines or calculators, and workflows such as specialized prompts. The official introduction compares it to a USB-C port for AI applications: one standard connector.

- An **MCP server** exposes tools, data (resources) and prompts for some system (a ticket system, a file store, a database).
- An **MCP client** (inside an AI application, such as Claude Code, or other assistants) connects to servers and offers their tools to the model.
- The model's tool calls go through the client to the server, and results come back as tool results.

Anthropic's API documents an MCP connector for remote MCP servers from the Messages API, and OpenAI's documentation lists MCP servers under its tools. The benefit is reuse: one server can serve many clients. The risk is trust: an MCP server is code, and its tool descriptions and results are text that the model reads. Install servers you trust, give them the least access that works, and review what each tool can do.

## Choosing between tool types

| You need | Use |
|---|---|
| Current public information | Web search / grounding |
| Answers from your documents | File search / RAG / a Project or Gem |
| Exact calculation or data crunching | Code execution |
| Live data or actions in your systems | Function calling to your own API, or an MCP server |
| A common integration reused across assistants | MCP |

## Try it yourself

1. **Search or not.** In two assistants ask: `What is the latest stable release of <a software you use>? Give the source URL.` once with search enabled and once with it off. Compare the answers, check the URL, and note any differences or fabricated links.
2. **Arithmetic by code.** Ask: `Summarize these networks into the fewest CIDR blocks: 198.51.100.0/26, 198.51.100.64/26, 198.51.100.128/26, 198.51.100.192/26. Use code execution if available and show the code.` Verify against `198.51.100.0/24`. Then ask for the same without code and compare.
3. **Write a tool definition.** Design a read-only `get_arp_entry(device, ip)` tool with a good description, and a dangerous `run_cli(device, command)` tool. Ask an assistant to review both for safety problems and what it would check before running them.
4. **Trace the loop.** Paste your tool definition and a user request into an assistant and ask it to show, as JSON, the tool call it would make, then provide a fake result and ask for the final answer. Identify the model's request, the tool result and the final answer.

## Key takeaways

- A model cannot run tools. It emits a structured tool call; your code or the vendor's servers execute it and return a tool result.
- The loop is: define tools, send request, model returns a tool call, run it, return the tool result, get the final answer.
- Tool names, descriptions and parameter descriptions are prompts; make them specific and say when to use the tool.
- Treat tool arguments as untrusted input, apply least privilege and confirm writes; tool results are data and can carry injected text.
- Hosted tools include web search, file search, code execution, image generation and computer use; server tools run on the vendor's infrastructure.
- Web search adds currency and citations but not certainty; check sources.
- Code execution fixes the model's weakness at exact arithmetic and data crunching; read the code.
- MCP is an open standard for connecting assistants to tools and data; it is reuse plus a trust decision.
