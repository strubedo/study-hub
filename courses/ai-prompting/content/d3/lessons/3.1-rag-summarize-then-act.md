## The problem RAG solves

A model knows only its training data (frozen at a cutoff, Lesson 1.1) and whatever is in the current context window. Your internal runbooks, last week's change tickets and the vendor's newest release notes are in neither. You could paste them all in, but that costs tokens, hits the window limit, and buries the relevant lines in noise.

**Retrieval-augmented generation (RAG)** fixes this by splitting the job in two: first **retrieve** the few passages that are relevant to the question, then **generate** an answer from the question plus those passages. The model does not "learn" your documents. It reads the retrieved text, in the prompt, at the moment it answers.

## The RAG pipeline

```text
Preparation (done once, and again when documents change)
  1. Collect documents (runbooks, KB articles, configs)
  2. Split into chunks (for example a few paragraphs each)
  3. Convert each chunk to an embedding (a vector of numbers)
  4. Store chunks + embeddings in an index / vector store

Per question
  5. Convert the question to an embedding
  6. Search the index for the closest chunks
     (many systems combine semantic and keyword search)
  7. Put the top chunks in the prompt with the question
  8. The model answers from those chunks, ideally with citations
```

An **embedding** is a numeric representation of meaning; text with similar meaning lands close together, so a search for "link flapping" can find a chunk that says "interface repeatedly goes up and down" even though the words differ. **Keyword search** matches exact terms, which is better for part numbers, error codes and command names. OpenAI's File Search tool, for instance, retrieves from uploaded files using both semantic and keyword search over vector stores (as of October 2026).

## Where you already meet RAG

- **Projects and uploaded knowledge.** Anthropic's Projects help page says paid plans automatically use RAG when project knowledge approaches the context limit, expanding capacity so the project can hold more than fits in a window (as of October 2026).
- **Chat search over past conversations.** Claude's chat-search feature is described as using RAG, and the searches appear in the chat as tool calls.
- **Files in custom assistants** (next lesson) are commonly searched this way, though each product decides when it searches and when it loads a file whole.
- **Web search and grounding.** A web search tool is retrieval from the internet instead of from your files. Google calls this "grounding with Google Search": the model is connected to real-time web content and can cite sources beyond its knowledge cutoff.
- **Your own system.** Developers build RAG with a vector database and embeddings, or use a hosted file-search tool.

## RAG versus long context versus fine-tuning

| Approach | Best for | Weakness |
|---|---|---|
| **Paste everything into context** | One document or a few, one-off questions | Token cost, window limit, noise, context rot |
| **RAG** | Large or changing knowledge bases; questions that need a few facts | Can miss the right chunk or retrieve the wrong one; chunking loses context |
| **Fine-tuning** | Teaching a style, format or narrow behaviour | Poor for facts that change; not a way to keep a runbook current |

RAG is the standard answer to "keep answers current and grounded in our documents", because updating the index updates the answers without touching the model.

## What goes wrong in RAG

RAG reduces hallucination only when retrieval works. Failure modes:

1. **Retrieval miss.** The answer is in the corpus but the search did not return it, so the model answers from memory or says it does not know. You see a confident but ungrounded reply.
2. **Wrong chunk.** A similar-looking passage (the 2019 procedure instead of the 2025 one) is retrieved and the model faithfully uses it.
3. **Chunk without context.** A chunk saying "set the value to 30" loses the heading that said which setting and which platform.
4. **Stale index.** Documents changed but the index did not.
5. **Conflicting passages.** Two chunks disagree and the model blends them.
6. **Injected instructions.** A retrieved document contains text such as "ignore previous instructions". Retrieved text is data, not commands (Domain 4 covers prompt injection).

> **Exam tip:** RAG puts retrieved text into the prompt at answer time. It does not change the model's weights, and it does not guarantee a correct answer. Quality depends on retrieval quality.

## Prompting for RAG answers

Your prompt controls how the retrieved material is used.

```text
Answer using only the passages in <context>. Cite the document name
for each claim. If the passages do not contain the answer, reply
"Not found in the provided documents" and say what you would need.
Do not use outside knowledge.

<context>
  <passage source="runbook-core-failover.md">...</passage>
  <passage source="kb-0042-ospf-timers.md">...</passage>
</context>

Question: What is the documented procedure to fail over the core pair?
```

Key habits: demand citations, allow "not found", forbid outside knowledge when you need strict grounding, and ask for conflicts to be listed. Lesson 2.3 showed the delimiters.

## Summarize-then-act patterns

Many real workflows have a step that **does something**: opens a ticket, sends a message, edits a config, runs a command. A **summarize-then-act** pattern puts a condensing step before the action step.

```text
Stage 1 - Summarize: read the 200-line incident thread and produce
          a structured summary (impact, timeline, current status,
          open questions).
Stage 2 - Decide:    from the summary, propose the next action and
          list what must be true before doing it.
Stage 3 - Act:       draft the customer update / ticket / command,
          a human approves, then it is sent or run.
```

Why this order works:

- The summary shrinks a huge input into something the acting step can handle precisely.
- The summary is a **checkpoint** a human can read and correct before anything irreversible happens.
- The action prompt can be strict ("use only facts in the summary") because the facts are already extracted.

Why it can fail: the summary is lossy. If it drops a key detail (a maintenance window, an exception for one site), the action step never sees it. Mitigate by asking the summary to preserve specific fields (names, times, versions), by giving the act step access to the original when needed, and by keeping a human approval before side effects.

> **Watch out:** Summarizing and acting in one prompt hides the checkpoint. If the model misreads the thread and then sends the message, you have no chance to catch it. For anything that changes systems or contacts people, separate the stages and require approval for the act step.

Typical IT uses:

- **Alert triage.** Summarize the alert and recent related logs, classify severity, then draft the ticket.
- **Change review.** Summarize the plan's commands and impact, then generate the rollback checklist.
- **Handover.** Summarize the shift's tickets, then draft the handover note for the next engineer.
- **Meeting to tasks.** Summarize a call transcript, then extract action items with owners.

## Putting the pieces together

A solid workflow often combines everything in this domain: **retrieve** relevant runbook passages, **summarize** the incident, **chain** an assessment and a draft, and **hand off** the final action to a person or to a tool with a narrow permission. Each step has a clear input, a checkable output and a defined behaviour for missing data.

## Try it yourself

1. **Compare grounded and ungrounded.** Write three short invented runbook paragraphs (for example the failover steps for `core-sw1`/`core-sw2` with an unusual detail such as a 45-second delay). Ask an assistant a question about the procedure with no files. Then put the paragraphs in a Claude Project, a Gemini Gem, or a custom GPT (if your plan allows) and ask again. Note which version used your detail.
2. **Test "not found".** Ask something the runbook does not cover. Does the assistant say so, or invent? Add `If the documents do not contain the answer, say Not found` and repeat.
3. **Summarize-then-act.** Invent a 30-line incident thread with one buried detail (the vendor said not to reload before 22:00). Run a one-shot `Summarize and draft the customer update`. Then run the three-stage version. Check whether the detail survives in each summary.

## Key takeaways

- RAG retrieves relevant chunks from an index and puts them in the prompt so the model answers from them; it does not retrain the model.
- The pipeline is chunk, embed, index, retrieve by similarity (often plus keyword search), then generate with citations.
- RAG helps with private, large or changing knowledge, but fails when retrieval misses, returns the wrong chunk, or the index is stale.
- Prompt RAG answers to cite sources, allow "not found" and avoid outside knowledge.
- Web search and Google Search grounding are retrieval from the internet instead of your files.
- Summarize-then-act inserts a condensing, human-checkable step before any action.
- The summary is lossy, so preserve key fields and keep approval before side effects.
- Treat retrieved text as data; it can contain injected instructions.
