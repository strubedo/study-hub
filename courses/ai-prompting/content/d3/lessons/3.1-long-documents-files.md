## When the input is bigger than a paragraph

Network engineers feed assistants large things: a 4,000-line running config, a week of syslog, a vendor PDF, a spreadsheet of VLANs. Lesson 1.1 explained the context window and Lesson 2.3 showed how to lay out long prompts. This lesson covers what happens to **files and long documents** in practice and how to get reliable answers from them.

## What happens when you attach a file

An attachment is not magic. One of three things usually happens, depending on the product, plan and file type (Lesson 1.2):

1. **The whole file goes into the context window.** The model can see everything, but the file uses tokens and competes with your instructions, the chat history and the reply.
2. **Text is extracted first.** A PDF or spreadsheet may be converted to text, which can lose layout, tables, headers and diagrams. Scanned pages may need image or OCR handling.
3. **The file is stored and searched.** The app splits it into chunks and retrieves only the relevant chunks per question. That is retrieval, covered in the next lesson.

The app usually does not tell you which of these it chose. Anthropic's Projects documentation, for example, says that when project knowledge approaches the context limit, Claude enables a retrieval mode to expand capacity (this applies to paid plans, as of October 2026). Google's Gemini API has a separate Files API for uploading media and documents to reference in requests; its documentation says uploaded files are kept for a limited time (48 hours, as of October 2026) and are subject to size caps. These specifics change, so check the vendor page before relying on them. The stable lessons are: know that you cannot always see what the model saw, and test with a question whose answer is in the middle of the file.

> **Watch out:** If an answer seems to ignore a section you know is in the file, the file may have been truncated, chunked or poorly extracted. Ask the model to quote the exact lines it used. If it cannot quote them, it probably did not see them.

## Long context is not perfect recall

A large window lets you include more, but it does not guarantee the model attends equally to everything. Anthropic's context-window documentation calls out **context rot**: accuracy and recall can degrade as the amount of text grows, which makes curating what goes into context as important as how much room is available. In practice:

- **More is not always better.** Irrelevant material is noise that the model may latch onto.
- **Position matters.** The guidance from Lesson 2.3 stands: put long documents first and the question and instructions last.
- **Repeat hard rules at the end** of a very long input if they must not be missed.
- **Remove what you do not need.** Trimming a log to the relevant window with `grep` or a script before pasting often beats pasting everything.

## Techniques for long documents

### 1. Quote first, then answer

Ask the model to extract the relevant quotes into a tagged block, then answer from those quotes. This forces it to locate evidence and gives you something to verify.

```text
<documents>
  <document index="1">
    <source>core-sw1-running-config.txt</source>
    <document_content> ...config... </document_content>
  </document>
</documents>

Find every line that enables SNMP v2c community strings. Put the
exact lines in <quotes> tags with their line numbers. Then, based
only on those quotes, list the risks. If there are none, say so.
```

### 2. Make the scope explicit

"Summarize this" over a 60-page document returns a vague average. Say which sections, what for, and for whom: "Summarize only the failover section, for an engineer deciding whether to enable it."

### 3. Split, then combine (map-reduce)

When the material exceeds what fits, or the model's grip loosens, divide it. Run the same prompt over each piece (the **map** step), then run one prompt that merges the results (the **reduce** step). This is prompt chaining (previous lesson) applied to size.

```text
Map (once per log file):
  "List each distinct error signature in <log>, with first and
   last timestamp and count. Output JSON."

Reduce (once):
  "Merge these JSON lists. Combine identical signatures, sum the
   counts, and rank by count. Output a table."
```

Prefer asking for **structured, comparable** map output. Free-form summaries of each piece merge poorly.

### 4. Ask targeted questions, not "what's in here?"

Specific questions ("Which interfaces have `shutdown` configured?") are easier to verify than open ones ("Anything interesting?"). If you need a survey, ask for a list with a fixed schema.

### 5. Do arithmetic and counting outside the model

Models are unreliable at counting thousands of lines or summing columns. Use the model to write the script or formula, then run it yourself on the file.

### 6. Multiple documents

Wrap each in its own tags with source metadata, as in the example. When documents conflict (an old runbook and a new one), tell the model which wins, or ask it to list conflicts instead of silently blending them.

## Working with spreadsheets, PDFs and images of text

| Input | Typical issue | What to do |
|---|---|---|
| **CSV / spreadsheet** | Wide tables are hard to read as text; formulas and hidden sheets may be ignored | State the columns you care about; ask for a script (Python, PowerShell) rather than eyeballed totals |
| **PDF** | Multi-column layout and tables can scramble on extraction | Spot-check a table against the page; for key tables, paste the text or export to CSV |
| **Screenshot of a CLI** | OCR errors in addresses and masks (a `1` versus an `l`, `/27` versus `/21`) | Paste the text instead; if you must use the image, ask the model to transcribe first, then check the transcription |
| **Diagram** | Models can misread links and labels | Ask for a structured list of nodes and links, and verify it against the diagram |
| **Code repository** | Too big for a prompt | Use a coding assistant that searches the repository itself (Lesson on agents), or provide only the relevant files |

## Sensitive content in files

Anything you attach goes to the vendor's service. Running configs and logs often contain password hashes, SNMP communities, pre-shared keys, internal addresses and usernames. Sanitize before uploading, and read your plan's data policy (Domain 4 covers this in depth). For practice, use invented data.

> **Real world:** A trimmed, sanitized excerpt plus a precise question nearly always beats a full dump plus "find problems". The exercise of trimming forces you to decide what the question is.

## Try it yourself

Create two invented text files of about 300 lines each: a fake IOS-XE config for `sw-lab-01` (use `192.0.2.0/24` and `198.51.100.0/24`) and a fake syslog. Plant three facts you can check: one SNMP community string, one interface with `shutdown`, and one error that appears exactly 17 times.

1. **Needle in the middle.** Attach the config in two assistants. Ask: `Which interfaces are administratively shut down? Quote each line.` Compare accuracy and whether quotes are exact.
2. **Quote-first.** Repeat with `First list relevant quotes in <quotes> tags, then answer from them.` Does it change the result?
3. **Counting.** Ask each assistant how many times the planted error appears in the log. Then ask it to write a one-line `grep` or PowerShell command to count it, run that, and compare. Which is more reliable?
4. **Map-reduce.** Split the log into three parts and run the map and reduce prompts above. Compare the merged answer with the answer from the whole log.

## Key takeaways

- A file is handled by the app in one of three ways: loaded whole, extracted to text, or stored and searched; you often cannot tell which.
- Long context does not guarantee equal attention to everything; irrelevant text adds noise and recall can degrade.
- Put documents first, the question last, and repeat critical rules at the end of very long input.
- Ask for exact quotes before conclusions so you can verify the model actually used the file.
- For oversized material, run map-reduce: the same structured prompt on each piece, then one merge prompt.
- Do counting, sorting and arithmetic with a script the model writes, not in the model's head.
- PDFs, spreadsheets and screenshots can lose layout or introduce transcription errors; check key values.
- Sanitize files before upload; limits and retention for files change, so verify on the vendor page.
