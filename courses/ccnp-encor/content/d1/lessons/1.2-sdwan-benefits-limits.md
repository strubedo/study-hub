## The problem SD-WAN solves

A traditional enterprise WAN is a set of routers configured one by one: MPLS circuits to every branch, a few DMVPN or static IPsec tunnels over internet links, routing tuned per site, and policy written as ACLs and route maps on each box. That has three recurring problems:

1. **Cost and lead time.** MPLS circuits are expensive and slow to provision; branches want cheap broadband and LTE/5G as well.
2. **Traffic patterns changed.** Users now go to SaaS and IaaS, not only to the headquarters data center. Backhauling all of it over MPLS to a central internet exit adds latency and burns bandwidth.
3. **Operations.** Hundreds of individually configured routers drift apart, and a policy change means touching every one of them.

Catalyst SD-WAN answers with a centralized control and management plane (lesson 1.2, control and data plane elements) over a transport-independent IPsec overlay.

## Benefits

| Benefit | How Catalyst SD-WAN delivers it |
|---|---|
| **Transport independence** | Any IP transport (MPLS, broadband, LTE/5G, satellite) becomes a TLOC with a color; the overlay looks the same over all of them |
| **Centralized management** | SD-WAN Manager configures every WAN Edge from templates or configuration groups, upgrades software and shows the whole network in one place, with a REST API for automation |
| **Centralized policy** | Control and data policies are written once on the Manager and enforced by the Controllers and edges; topology (full mesh, hub and spoke, regional) is policy, not per-router configuration |
| **Application-aware routing** | BFD measures loss, latency and jitter on every tunnel; traffic for an application moves to a path that meets its SLA class, so a degraded (not just failed) link is avoided |
| **Active-active use of links** | All transports carry traffic, with ECMP or weighted load sharing, instead of an expensive backup link sitting idle |
| **Security built in** | Every device authenticated by certificate, every tunnel encrypted with IPsec, keys distributed by the Controllers and rekeyed automatically (default rekey interval 86,400 seconds); edges can run zone-based firewall, IPS and URL filtering for direct internet access |
| **Segmentation** | VPNs (VRFs) keep user groups separate end to end across the overlay |
| **Zero-touch provisioning** | A new WAN Edge is shipped to the branch, plugged in, finds its controllers through Cisco Plug and Play, and downloads its configuration; no engineer on site |
| **Cloud and SaaS optimization** | Direct internet access at the branch, SaaS path selection (Cloud OnRamp for SaaS) and virtual WAN Edges in public clouds (Cloud OnRamp for multicloud) |
| **Scale and resilience of the control plane** | Controllers are redundant and horizontally scalable; with OMP graceful restart, edges keep forwarding on cached routes and keys if all Controllers are unreachable |

## Limitations and trade-offs

Explaining the solution includes knowing where it hurts:

| Limitation | Detail |
|---|---|
| **Controller dependency** | New sites cannot join, policy cannot change and keys eventually expire if the controllers stay unreachable. Graceful restart (12 hours by default) and key lifetime buy time, not independence |
| **Public reachability of the Validator** | The Validator must have a public (or one-to-one NAT) address that every edge can reach; firewalls in front of controllers must allow the DTLS/TLS port ranges |
| **NAT traversal limits** | Direct tunnels between two edges that are both behind symmetric NAT may fail; traffic then has to go through a hub or a TLOC with a public address |
| **Overhead** | IPsec, UDP and SD-WAN headers reduce the effective MTU, and BFD probes on every tunnel of a full mesh add traffic and CPU load; large full meshes therefore usually become hub and spoke or regional designs |
| **Licensing and cost model** | Hardware plus a term-based software subscription; which advanced features (for example some security and analytics features) are available depends on the subscription tier |
| **Complexity and skills** | New concepts (OMP, TLOCs, colors, templates, centralized policy) and a different troubleshooting model; mistakes in a central policy affect every site at once |
| **Vendor lock-in** | OMP and the controllers are Cisco-specific; the overlay does not interoperate with another vendor's SD-WAN |
| **Feature parity** | Not every IOS XE feature is available in controller (SD-WAN) mode, or it must be added through CLI add-on templates |
| **Internet is still best effort** | Application-aware routing picks the best available path; it cannot create bandwidth or guarantee latency on the internet |

> **Exam tip:** "Which is a limitation" questions often offer a benefit dressed as a drawback. Encryption, zero-touch provisioning and transport independence are benefits; dependency on the controllers, overhead and a publicly reachable Validator are the real limitations.

## SD-WAN compared with a traditional WAN

| | Traditional WAN (MPLS plus DMVPN) | Catalyst SD-WAN |
|---|---|---|
| Configuration | Per device, CLI | Central templates and configuration groups |
| Control plane | Distributed (BGP, EIGRP, NHRP) on every router | Centralized Controllers with OMP |
| Path selection | Routing metrics; a link is used until it fails | Application-aware routing on measured loss, latency and jitter |
| Key exchange | IKE between each pair of peers | Keys distributed by the Controllers over OMP |
| New branch | Engineer on site or pre-staged router | Zero-touch provisioning |
| Visibility | Per device (SNMP, NetFlow) | Network-wide dashboards and APIs |

## Lab it yourself

Use the Cisco DevNet Catalyst SD-WAN sandbox (browser based, any OS):

1. Look at Configuration > Policies and find an application-aware routing policy with an SLA class (loss, latency, jitter thresholds). Note which applications it steers and the preferred color.
2. Open Monitor > Tunnels for one edge and compare the measured loss, latency and jitter of each tunnel with the SLA class.
3. List three benefits and three limitations you can see in the sandbox itself (for example: one dashboard for all sites; the controllers are a dependency; templates must be attached before a device is managed).

## Key takeaways

- SD-WAN solves cost, cloud traffic patterns and per-device operations of traditional WANs.
- Benefits: transport independence, central management and policy, application-aware routing, active-active links, built-in encryption, segmentation, zero-touch provisioning, cloud optimization.
- Application-aware routing reacts to degraded paths, not only failed ones, using BFD loss, latency and jitter.
- Limitations: dependency on the controllers, a publicly reachable Validator, NAT traversal limits, tunnel and BFD overhead, licensing, new skills, vendor lock-in.
- Graceful restart (12 hours default) keeps edges forwarding if controllers are lost, but no new changes or sites until they return.
