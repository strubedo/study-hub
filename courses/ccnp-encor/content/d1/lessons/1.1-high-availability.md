## What topic 1.1.b asks

"High availability techniques such as redundancy, FHRP and SSO." You need to explain what each technique protects against and how they fit together. Configuration of HSRP and VRRP is tested in depth under topic 3.3 (Domain 3); here the focus is the design view: which failure each mechanism covers, and how fast.

Think of availability in layers:

| Failure | Mechanism |
|---|---|
| A link fails | Redundant links: EtherChannel, ECMP routing, fast detection with BFD (RFC 5880) |
| A default gateway fails | First hop redundancy protocol (HSRP, VRRP, GLBP) |
| A supervisor or route processor fails inside a chassis | SSO plus NSF or NSR |
| A whole switch fails | Dual devices: FHRP pairs, StackWise, StackWise Virtual, dual-homed access |
| A power feed or fan fails | Redundant power supplies and fans, separate power circuits |

## Redundancy without loops

Adding a second device or link is easy; making the network *use* it fast and without loops is the design work:

- **EtherChannel** bundles parallel links into one logical link, so STP sees one port and a member failure costs only that member's bandwidth.
- **ECMP** in a routed design (routed access, fabric underlays) uses all equal-cost paths and fails over at IGP speed.
- **BFD** detects a dead neighbor in well under a second and tells the routing protocol, instead of waiting for hello and dead timers.
- Too much redundancy hurts: extra links add STP complexity, more adjacencies and longer convergence. Cisco designs aim for *two* of everything in the critical path, not three.

## First hop redundancy protocols

Hosts have one default gateway address. An FHRP lets two or more routers share a **virtual IP** and **virtual MAC**, so a gateway failure does not require any host change.

| | HSRP | VRRPv3 | GLBP |
|---|---|---|---|
| Standard | Cisco (v1 described in informational RFC 2281) | IETF, RFC 9568 (obsoletes RFC 5798) | Cisco |
| Roles | Active, standby, listen | Active (called master before RFC 9568), backup | One active virtual gateway (AVG), up to four active virtual forwarders (AVFs) |
| Load sharing per group | No (use several groups) | No (use several groups) | Yes: the AVG hands out different virtual MACs in ARP replies |
| Hello/advertisement | 3 s hello, 10 s hold (RFC 2281 defaults) | 1 s advertisement (100 centiseconds) | Cisco-defined timers |
| Transport | UDP 1985 to 224.0.0.2 (v1) | IP protocol 112 to 224.0.0.18 (IPv4) | UDP 3222 to 224.0.0.102 |
| Virtual MAC | `0000.0c07.acXX` (v1, XX = group in hex) | `0000.5e00.01XX` (IPv4, XX = VRID) | One per AVF, assigned by the AVG |
| Preemption by default | Off on Cisco IOS XE | On (RFC 9568 `Preempt_Mode` default True) | AVG preemption off; AVF preemption on (Cisco defaults) |

The higher priority wins (default 100); on a tie, the higher interface IP address wins. Object **tracking** lowers a router's priority when its uplink fails, so a router with a dead uplink hands over the gateway role; that only works if the peer is allowed to **preempt**.

> **Exam tip:** HSRP does not preempt unless you configure `standby <group> preempt`. A question where the "better" router never takes over after recovering is almost always a missing `preempt` (HSRP) or a VRRP group configured with `no preempt` (under `vrrp <group> address-family ipv4` in VRRPv3; `no vrrp <group> preempt` in the older VRRPv2 interface syntax), which is rare since preemption is on by default there.

> **Watch out:** HSRP version 2 uses 224.0.0.102 and a different virtual MAC range (`0000.0c9f.fXXX`) and supports groups 0 to 4095. Version 1 and version 2 do not interoperate on the same group.

## SSO: stateful switchover

A modular switch (Catalyst 9400, 9600) with two supervisors, a StackWise stack, a StackWise Virtual pair, or a router with dual route processors runs one **active** and one **standby** control plane. With **SSO** (stateful switchover) the active continuously synchronizes the running configuration and the state of SSO-aware features (interface states, Layer 2 tables, FHRP state, and so on) to the standby. When the active fails, the standby takes over without reloading the line cards and without resetting interfaces.

Earlier redundancy modes are worth recognizing: **RPR** (the standby is partly booted and must finish initializing, so line cards reload) and **RPR+** (standby fully booted but no state sync). SSO replaced both. The state is visible with `show redundancy states`; on a healthy pair the peer is `STANDBY HOT` and the operational mode is `sso`:

```text
R1#show redundancy states
       my state = 13 -ACTIVE
     peer state = 8  -STANDBY HOT
           Mode = Duplex
           Unit = Primary
        Unit ID = 48

Redundancy Mode (Operational) = sso
Redundancy Mode (Configured)  = sso
Redundancy State              = sso
     Maintenance Mode = Disabled
    Manual Swact = enabled
 Communications = Up
```

The mode is set with `redundancy` then `mode sso`. On many Catalyst 9000 platforms SSO is already the default when a standby is present; check the platform's high availability guide.

## NSF and NSR: keeping routing alive through a switchover

SSO keeps Layer 2 and the hardware forwarding tables, but routing protocol sessions live in the control plane. Two techniques cover them:

| | NSF (non-stop forwarding) with graceful restart | NSR (non-stop routing) |
|---|---|---|
| How | Hardware keeps forwarding on the last FIB while the new active rebuilds routing; neighbors are told a restart is happening and keep the restarting router's routes | The standby keeps a synchronized copy of routing protocol state and sessions, so it simply continues them |
| Neighbors | Must be **NSF-aware** (graceful restart helper) | Need no special support; they never notice |
| Standards | OSPF graceful restart (RFC 3623) and BGP graceful restart (RFC 4724), plus Cisco NSF for OSPF and EIGRP | Implementation feature, no protocol change |

Terminology to know: an **NSF-capable** router can itself restart gracefully (it has SSO); an **NSF-aware** router helps a neighbor that is restarting. On IOS XE, graceful restart is enabled per protocol (for example `nsf` or `nsf ietf` under `router ospf`, `bgp graceful-restart` under `router bgp`).

> **Watch out:** SSO alone is not enough for routing. Without NSF or NSR, the new active supervisor re-forms OSPF, EIGRP and BGP adjacencies from scratch and neighbors flush its routes in the meantime.

## StackWise and StackWise Virtual

- **StackWise** (Catalyst 9200, 9300): several switches joined by stacking cables behave as one switch with one management IP and one configuration. One member is active, one is standby (SSO between them), the rest are members. Interfaces are numbered `switch/module/port`, for example `GigabitEthernet2/0/1`.
- **StackWise Virtual** (Catalyst 9400, 9500, 9600): two chassis joined over ordinary Ethernet ports (the **StackWise Virtual link**, SVL) form one logical switch with one control plane and SSO. Downstream switches connect with a **multichassis EtherChannel** to both chassis, so there is no STP blocking and no FHRP needed between the pair. If the SVL fails, both chassis could become active; **dual-active detection** (DAD) links detect that and put one into recovery mode.

```text
DSW1#show stackwise-virtual
Stackwise Virtual Configuration:
--------------------------------
Stackwise Virtual : Enabled
Domain Number : 100

Switch  Stackwise Virtual Link  Ports
------  ----------------------  ------
1       1                       HundredGigE1/0/3
                                HundredGigE1/0/4
2       1                       HundredGigE2/0/3
                                HundredGigE2/0/4
```

| | FHRP pair (two independent switches) | StackWise Virtual pair |
|---|---|---|
| Control planes | Two | One (active plus SSO standby) |
| Gateway | Virtual IP shared by FHRP | One SVI on the logical switch |
| Access uplinks | STP blocks one unless routed | Multichassis EtherChannel, all links forward |
| Software upgrades | One switch at a time, independent | The pair is one system; plan upgrades for it |

## Lab it yourself

Most virtual images cannot model dual supervisors or StackWise Virtual, so lab the FHRP part and read the outputs for the rest. In CML, GNS3 or EVE-NG (Windows, Linux or an Intel Mac; on an Apple silicon Mac use a remote x86 server or a Cisco DevNet sandbox) build `DSW1` and `DSW2` (IOSvL2 or Catalyst 9000v) with a host on VLAN 10:

```text
DSW1(config)#track 1 interface GigabitEthernet0/1 line-protocol
DSW1(config)#interface Vlan10
DSW1(config-if)#ip address 10.1.10.2 255.255.255.0
DSW1(config-if)#standby version 2
DSW1(config-if)#standby 10 ip 10.1.10.1
DSW1(config-if)#standby 10 priority 110
DSW1(config-if)#standby 10 preempt
DSW1(config-if)#standby 10 track 1 decrement 20
```

Give `DSW2` `10.1.10.3` and the same group without a priority. Verify with `show standby brief`, shut `DSW1`'s `GigabitEthernet0/1` and watch the priority fall to 90 and `DSW2` take over; bring it back and watch `DSW1` preempt. Then repeat with VRRPv3 (`fhrp version vrrp v3`, `vrrp 10 address-family ipv4`, `address 10.1.10.1 primary`) and compare `show vrrp brief`.

## Key takeaways

- Match each technique to the failure it covers: links (EtherChannel, ECMP, BFD), gateways (FHRP), control planes (SSO with NSF or NSR), whole devices (dual devices, StackWise, StackWise Virtual).
- HSRP: Cisco, 3 s/10 s, no preemption by default, `0000.0c07.acXX` (v1). VRRPv3: RFC 9568, protocol 112, 224.0.0.18, 1 s, preempts by default. GLBP adds per-host load sharing.
- Priority default 100, highest wins, tie goes to the highest IP; tracking only moves the role if preemption is on.
- SSO keeps a hot standby control plane synchronized; `show redundancy states` should show `STANDBY HOT` and `sso`.
- NSF keeps forwarding and relies on NSF-aware neighbors (graceful restart); NSR keeps protocol sessions on the standby without neighbor help.
- StackWise Virtual turns two chassis into one logical switch with multichassis EtherChannel; DAD protects against a split.
