## The names first

Cisco renamed the SD-WAN components in 2023. The exam topics use the new names; CLI output, APIs and older documents still use the old ones, so know both:

| Current name | Former name | Plane |
|---|---|---|
| **Catalyst SD-WAN** | Cisco SD-WAN (Viptela) | The whole solution |
| **SD-WAN Manager** | vManage | Management |
| **SD-WAN Validator** | vBond | Orchestration |
| **SD-WAN Controller** | vSmart | Control |
| **WAN Edge** | vEdge (Viptela OS) and cEdge (IOS XE in controller mode: ISR 1000/4000, Catalyst 8000, Catalyst 8000V) | Data |

> **Watch out:** CLI output on the edges still prints `vmanage`, `vbond` and `vsmart` as peer types. Read them as Manager, Validator and Controller.

## The four planes

| Plane | Component | Job |
|---|---|---|
| **Management** | SD-WAN Manager | Single GUI and REST API: configuration (feature templates, configuration groups), software upgrades, certificates, monitoring and troubleshooting. Pushes configuration to the edges over NETCONF |
| **Orchestration** | SD-WAN Validator | First contact for every device. Authenticates devices, tells them where the Managers and Controllers are, and helps with NAT traversal by reflecting each edge's public address and port back to it. Needs a public IP (or a one-to-one NAT) that every edge can reach |
| **Control** | SD-WAN Controller | Brain of the overlay. Runs OMP with every WAN Edge, learns and reflects routes, TLOCs and data-plane keys, and applies centralized control and data policy. Does not forward user traffic |
| **Data** | WAN Edge | Forwards user traffic over IPsec tunnels to other WAN Edges, runs BFD in every tunnel, enforces policy, and connects to the LAN (service side) and the transports (transport side) |

The controllers can be hosted by Cisco in the cloud or on premises. None of them carries user traffic, which is the core idea: the control plane is centralized, the data plane is distributed.

## Control connections: DTLS or TLS

Every device builds secure **control connections** using certificates (each edge has a hardware or software identity, and the Manager holds an authorized serial number list that is distributed to the Validators and Controllers). The tunnels use **DTLS** by default, or **TLS** if configured:

| Protocol | Default ports |
|---|---|
| DTLS (UDP) | Base port **12346**. Controllers with several cores use additional ports in steps of 100 (12446, 12546 ...), so firewall rules for controllers usually open a range such as UDP 12346-13046 |
| TLS (TCP) | Base port **23456**, with additional ports per core in the same way (for example TCP 23456-24156) |

A WAN Edge can also shift its base port with a **port offset** (useful when two edges sit behind one NAT) and, by default, tries other ports (**port hopping**) if a connection fails.

Who connects to whom:

- WAN Edge to Validator: a transient connection to authenticate and learn the controllers' addresses, then torn down.
- WAN Edge to Manager: one persistent connection (configuration, monitoring).
- WAN Edge to Controllers: persistent connections on each transport, by default to two Controllers, carrying OMP.
- Controllers and Managers to Validators: persistent connections, so the Validators always know the current controller list.

## Overlay Management Protocol (OMP)

OMP is a BGP-like routing protocol that runs **inside** the DTLS/TLS control connections between WAN Edges and Controllers. Edges never run OMP with each other: the Controller acts like a BGP route reflector. OMP carries three route types:

| OMP route type | Contents |
|---|---|
| **OMP routes** (vRoutes) | Service-side prefixes learned on the LAN (connected, static, OSPF, EIGRP, BGP) per VPN, with the TLOC(s) to reach them |
| **TLOC routes** | Each edge's transport locators, with public and private IP and port, color, encapsulation, preference and weight |
| **Service routes** | Network services (firewall, IPS) available at a site, for service chaining |

OMP also distributes the **IPsec keys** each edge generates, so edges never run IKE with each other by default. Useful defaults from the configuration templates: hold time 60 seconds, graceful restart enabled with a 43,200-second (12-hour) timer, and up to 4 paths sent per prefix (send-path-limit) and installed (ECMP limit). Graceful restart is why WAN Edges keep forwarding on their last-known routes and keys if they lose all Controllers.

## TLOCs and colors

A **TLOC** (transport locator) identifies one transport attachment of one edge. It is the tuple **system IP + color + encapsulation**:

- **System IP**: a router-ID-like identifier for the device (not necessarily routable), unique per device.
- **Site ID**: identifies the site; edges at the same site share it, and by default edges do not build tunnels to edges with the same site ID.
- **Color**: a label for the transport, such as `mpls`, `biz-internet`, `public-internet`, `lte`, `metro-ethernet`, `gold`, `private1`. Colors decide whether tunnels use private or public (post-NAT) addresses, and the `restrict` option limits tunnels to the same color.
- **Encapsulation**: `ipsec` (default) or `gre`.

## Data plane: IPsec and BFD

Each WAN Edge builds a full mesh of tunnels by default (one per local TLOC to each remote TLOC it is allowed to reach); policy can restrict this to hub-and-spoke or partial mesh. Tunnels are IPsec ESP in UDP, sourced from the same port as the DTLS control connection (12346 plus offset), which helps NAT traversal.

**BFD** runs inside every tunnel. It is always on and does two jobs:

1. **Liveness**: default hello interval 1,000 ms and multiplier 7, so a tunnel is declared down after about 7 seconds without hellos.
2. **Path quality**: loss, latency and jitter are measured on every tunnel and averaged over a poll interval (default 600,000 ms, 10 minutes) and multiplier (default 6). **Application-aware routing** compares those numbers with SLA classes and steers each application to a tunnel that meets its SLA.

## VPNs (segmentation)

Catalyst SD-WAN segments traffic with VPNs, which are VRFs on IOS XE WAN Edges: **VPN 0** is the transport VPN (WAN interfaces, control connections), **VPN 512** is out-of-band management (`Mgmt-intf` VRF on IOS XE), and service VPNs (for example 1 to 511) carry user traffic. Each edge advertises a VPN label with its OMP routes (the LABEL column of `show sdwan omp routes`) and puts that label in the data-plane encapsulation, so the receiving edge knows which VPN a packet belongs to and segmentation is preserved end to end across the overlay.

## Lab it yourself

A full overlay needs controller images and licensing, so this lab is lighter: use the Cisco DevNet "Catalyst SD-WAN" reservable or always-on sandbox (browser based, any OS) and only read.

1. In SD-WAN Manager open Monitor > Devices and identify the Manager, Validator, Controller and WAN Edge devices and their system IPs and site IDs.
2. On a WAN Edge, open Real Time > Control Connections and match each row to the table above (peer type, DTLS, ports).
3. Open OMP TLOCs and BFD Sessions for the same edge and write out each TLOC as system IP + color + encapsulation.
4. On the CLI of an IOS XE edge run `show sdwan control connections`, `show sdwan omp peers`, `show sdwan omp tlocs` and `show sdwan bfd sessions`.

## Key takeaways

- Management = SD-WAN Manager (vManage), orchestration = SD-WAN Validator (vBond), control = SD-WAN Controller (vSmart), data = WAN Edge.
- Control connections use DTLS (UDP 12346 base) by default or TLS (TCP 23456 base), authenticated with certificates and an authorized serial list.
- The Validator authenticates and orchestrates, and helps with NAT traversal; it needs a reachable public address.
- OMP runs only between WAN Edges and Controllers and carries OMP routes, TLOC routes, service routes and IPsec keys; graceful restart keeps edges forwarding if Controllers are lost.
- A TLOC is system IP + color + encapsulation; colors control public or private addressing and tunnel building.
- Data plane = IPsec (or GRE) tunnels with BFD in each one: 1,000 ms x 7 for liveness, loss/latency/jitter for application-aware routing.
