## Two problems, two technologies

- **TrustSec** solves **segmentation at scale**. Writing ACLs by IP address breaks down when users move, addresses change and the same policy must be enforced on hundreds of switches. TrustSec classifies traffic by **group** instead, and enforces policy between groups.
- **MACsec** solves **confidentiality on the wire**. A tap on a cable, or a compromised device between two switches, can read and alter Ethernet frames. MACsec encrypts and authenticates each link.

They are often deployed together (Cisco documentation groups MACsec under TrustSec), and SD-Access uses the same group tags in its fabric.

## Cisco TrustSec

### Classification: give traffic a Security Group Tag

A **Security Group Tag (SGT)**, also called a Scalable Group Tag, is a **16-bit** number (so up to 65,536 values, a few reserved) representing a role: Employees, Contractors, Guests, PCI servers, IP cameras. Classification assigns an SGT to traffic where it enters the TrustSec domain:

- **Dynamic classification**: ISE returns the SGT as an authorization result after **802.1X, MAB or WebAuth**. The same user gets the same tag on any port, wired, wireless or VPN, regardless of IP address.
- **Static classification**: configured on a device for things that do not authenticate: an IP address or subnet to SGT mapping (common for servers), a VLAN to SGT mapping, or a port (Layer 2 or Layer 3 interface) to SGT mapping.

```text
SW1# show cts role-based sgt-map all
Active IPv4-SGT Bindings Information

IP Address              SGT     Source
============================================
10.20.1.15              4       LOCAL
10.20.1.16              5       LOCAL
10.50.0.0/24            10      CLI
10.60.0.20              8       SXP
```

`LOCAL` bindings were learned from a session authenticated on this switch, `CLI` bindings are static, and `SXP` bindings came from a peer (see below).

### Propagation: carry the tag to the enforcement point

The tag must reach the device that enforces policy, usually near the destination. Two methods:

- **Inline tagging**: the SGT travels in the frame itself, in the **Cisco Meta Data (CMD)** header inserted after the source MAC address (EtherType **0x8909**, 8 bytes when it carries only the SGT). Every hop must support it in hardware; it is configured per link (with `cts manual` or `cts dot1x` on the interface) and can be protected by MACsec. In SD-Access the SGT is carried in the VXLAN header instead.
- **SGT Exchange Protocol (SXP)**: a control-plane protocol that sends **IP-to-SGT bindings** from a **speaker** to a **listener** over a **TCP** connection (port 64999), protected with a password (TCP MD5 or, on newer releases, TCP-AO). SXP is used where some devices in the path cannot tag inline: an access switch that classifies but lacks the hardware sends its bindings to an enforcement device, which then knows the source SGT of each IP address. SXP scales less well than inline tagging because every binding is sent to every listener.

### Enforcement: SGACLs at egress

Policy is a **matrix**: source SGT down one side, destination SGT across the top, and in each cell a **Security Group ACL (SGACL)** such as "permit https" or "deny ip". ISE holds the matrix and downloads the relevant cells to the network devices.

Enforcement happens at **egress**, on the device next to the destination: it knows the **source SGT** (from the tag in the frame or an SXP binding) and the **destination SGT** (because the destination is attached to it or mapped statically), and applies the SGACL for that pair. Benefits:

- Policy is written once, between groups, not per IP address per switch.
- Adding a user or a server does not change any ACL; it only gets the right tag.
- The rule count grows with the number of groups, not the number of addresses.

Firewalls can also enforce on SGTs: Secure Firewall Threat Defense can use SGTs in access control rules (security group tag ACLs, SGFW).

> **Exam tip:** Classification at ingress, propagation inline or by SXP, enforcement at egress with SGACLs. SGTs are 16 bits; inline tags use the CMD header; SXP runs over TCP.

## MACsec (IEEE 802.1AE)

**MACsec** encrypts and authenticates Ethernet frames **hop by hop**: each link is a separate secure association, and each device decrypts on receipt, processes the frame in the clear (so it can switch, route, apply QoS or read an inline SGT), and encrypts again on the next MACsec link. That contrasts with IPsec, which protects end to end between two IP endpoints and leaves every hop in between unable to read the payload.

### What it adds to the frame

| Field | Size | Purpose |
|---|---|---|
| **SecTAG** (security tag) | 8 bytes, or **16 bytes** with the optional 8-byte Secure Channel Identifier (SCI) | EtherType **0x88E5**, a TCI/AN byte (flags and association number), a short-length byte, a 4-byte packet number for replay protection, and optionally the SCI |
| Encrypted payload | Original size | The original EtherType and payload, encrypted |
| **ICV** (integrity check value) | **16 bytes** | Authenticates the whole frame; a tampered frame is dropped |

The destination and source MAC addresses stay in the clear. With the SCI included, the overhead is **16 + 16 = 32 bytes** per frame (24 without the SCI), so links carrying full-size frames need an MTU large enough to absorb it; plan jumbo frames or an increased system MTU on uplinks.

The cipher suites are **GCM-AES-128** and **GCM-AES-256** (Galois/Counter Mode AES gives encryption and integrity in one pass), plus extended packet numbering versions (GCM-AES-XPN-128 / 256) for high-speed links where the 32-bit packet number would wrap too fast. Encryption runs in the port hardware at line rate on MACsec-capable switch models and line cards.

### Keys

| Key | Meaning |
|---|---|
| **CAK** (Connectivity Association Key) | The long-term master key shared by the peers; derived from 802.1X (the EAP session key) or configured as a pre-shared key |
| **CKN** (CAK Name) | Identifies which CAK is in use; both peers must use the same CKN and CAK |
| **SAK** (Secure Association Key) | The key that actually encrypts frames; generated by the elected key server, distributed encrypted with keys derived from the CAK, and rotated regularly |

Two key agreement protocols exist on Cisco switches:

- **MKA, the MACsec Key Agreement protocol**, defined in **IEEE 802.1X-2010**. Standards-based, and the one used for host links and most new switch-to-switch deployments. Peers exchange MKA messages (EAPOL frames), elect a key server and distribute SAKs. Supports GCM-AES-128 and 256.
- **Cisco SAP (Security Association Protocol)**, the older Cisco TrustSec key exchange used with `cts manual` or `cts dot1x` on switch-to-switch links. Cisco-proprietary; limited to 128-bit keys.

### Downlink versus uplink

| | Host-to-switch (downlink) | Switch-to-switch (uplink) |
|---|---|---|
| Endpoints | A PC with a MACsec-capable supplicant (for example Secure Client Network Access Manager) and an access switch | Two switches, or a switch and a router |
| Key agreement | MKA, with the CAK derived from 802.1X authentication against ISE | MKA with a pre-shared key (key chain), or SAP with Cisco TrustSec |
| Policy | ISE tells the switch whether MACsec is required ("must secure") or optional ("should secure") for that endpoint | Configured on both link ends |
| Main use | Protect access links in sensitive areas against taps | Protect links between buildings, through untrusted conduits or to a data centre; secure inline SGT tags |

## Lab it yourself

Most virtual switch images do not implement MACsec or inline tagging in their data plane, so practise with captures and configuration review:

1. In Cisco Modeling Labs, GNS3 or EVE-NG (Windows, Linux or an Intel Mac; on an Apple silicon Mac use a remote x86 server or a Cisco DevNet sandbox), configure static IP-to-SGT mappings on a Catalyst 9000v (`cts role-based sgt-map 10.50.0.0/24 sgt 10`) and check `show cts role-based sgt-map all`.
2. Configure SXP between two switches (speaker and listener) and verify with `show cts sxp connections brief` and the `SXP` source in the binding table.
3. On two Linux VMs, build a MACsec link with `ip link add ... type macsec` and capture it: identify EtherType 0x88E5, the SecTAG with the SCI flag set, and the 16-byte ICV, and confirm the 32-byte growth by comparing frame sizes with and without MACsec.
4. If you have physical Catalyst 9300 switches, configure MKA with a pre-shared key chain between them and check `show macsec summary` and `show mka sessions`.

## Key takeaways

- TrustSec: classify (dynamic from ISE after 802.1X / MAB / WebAuth, or static IP, VLAN or port mappings), propagate (inline CMD tag, EtherType 0x8909, or SXP over TCP 64999), enforce at egress with SGACLs from the ISE matrix.
- An SGT is a 16-bit group identifier; policy is written between groups, not IP addresses.
- MACsec (IEEE 802.1AE) is hop-by-hop Layer 2 encryption and integrity with GCM-AES-128 or 256.
- SecTAG (EtherType 0x88E5, 16 bytes with SCI) plus a 16-byte ICV: 32 bytes of overhead; MAC addresses stay in the clear.
- Keys: CAK (master), CKN (its name), SAK (encrypts traffic, from the key server). MKA is IEEE 802.1X-2010; SAP is the older Cisco protocol.
- Downlink MACsec uses 802.1X-derived keys and ISE policy; uplink MACsec usually uses MKA with pre-shared keys.
