## Why API security is network security

A REST API to Catalyst Center (formerly DNA Center), SD-WAN Manager or a RESTCONF-enabled router can do in one call what an administrator does in an hour of CLI work: change hundreds of devices, read every configuration, or erase them. An API is therefore a management plane, and it needs the same protection as SSH and TACACS+: an encrypted transport, strong authentication, least-privilege authorization, protected credentials and an audit trail.

## Transport: HTTPS with certificate validation

REST APIs carry credentials and tokens in HTTP headers, so they must run over **HTTPS (HTTP over TLS)**. TLS gives:

- **Confidentiality**: credentials, tokens and payloads are encrypted.
- **Integrity**: a request cannot be changed in transit.
- **Server authentication**: the client checks the server's certificate against a trusted certificate authority and checks that the name in it matches the host it called.

The last point is the one scripts break. Disabling verification (`verify=False` in Python `requests`, `curl -k`) still encrypts, but the client no longer knows **who** it is talking to, so a man-in-the-middle with any certificate can collect the credentials. The right fix for a self-signed lab certificate is to install the controller's CA certificate on the client and point the script at it (`verify="/path/to/ca.pem"`), not to switch verification off. On IOS XE, RESTCONF uses the HTTPS server (`ip http secure-server`), and you should give the device a certificate from your PKI rather than relying on the self-signed one.

## Authentication: proving who the caller is

| Method | How it works | Notes |
|---|---|---|
| HTTP Basic | `Authorization: Basic` followed by base64 of `username:password`, sent on every request | Base64 is encoding, not encryption: anyone who sees the header has the password. Acceptable only inside TLS |
| Token | Authenticate once (often with Basic), receive a token, send the token on later requests | The password is sent once; tokens expire and can be revoked |
| API key | A long random string issued to an application, sent in a header | Simple; usually no expiry or user identity, so rotate and scope them |
| OAuth 2.0 (RFC 6749) | An authorization server issues an **access token** to a client application, often on behalf of a user, with a limited **scope** and lifetime; the client sends it as `Authorization: Bearer` (RFC 6750) | Separates the identity provider from the API; the application never sees the user's password |
| Certificates (mutual TLS) | The client presents its own certificate during the TLS handshake | Strong, but needs a PKI |

OAuth 2.0 names four roles: the **resource owner** (the user), the **client** (the application), the **authorization server** (issues tokens) and the **resource server** (the API). For ENCOR you need the idea, not the grant-type details: the client gets a short-lived, scoped token instead of a password.

### Catalyst Center: Basic once, then a token

Catalyst Center's Intent API uses a token. The client sends a `POST` to **`/dna/system/api/v1/auth/token`** with HTTP Basic credentials, and the response body contains the token:

```text
POST https://catc.example.com/dna/system/api/v1/auth/token
Authorization: Basic <BASE64-OF-USERNAME:PASSWORD>

HTTP/1.1 200 OK
{"Token": "<TOKEN>"}
```

Every later request carries the token in the **`X-Auth-Token`** header:

```text
GET https://catc.example.com/dna/intent/api/v1/network-device
X-Auth-Token: <TOKEN>
```

Cisco's API documentation gives the token a lifetime of **60 minutes**; after that, requests return **401 Unauthorized** and the client must request a new token. Scripts should handle the 401 by re-authenticating, not by caching a token forever.

### RESTCONF on IOS XE: Basic on every request

RESTCONF (RFC 8040) on IOS XE uses **HTTP Basic authentication over HTTPS** on every request, checked against the device's local user database or AAA. The user needs **privilege level 15** to read and change the configuration:

```text
GET https://10.10.10.1/restconf/data/Cisco-IOS-XE-native:native/hostname
Authorization: Basic <BASE64-OF-USERNAME:PASSWORD>
Accept: application/yang-data+json
```

Because the password travels with every call, TLS and AAA (so the account is central, logged and can be disabled) matter even more here.

## Authorization: least privilege

Authentication says who the caller is; **authorization** says what it may do. Give each script or integration its **own** account with only the role it needs:

- **Role-based access control (RBAC)**: Catalyst Center and SD-WAN Manager let you build roles (observer or read-only, network operator, administrator) and assign users to them. A monitoring script that only reads inventory gets a read-only role; it can never push a template.
- On IOS XE, AAA authorization and privilege levels limit what an API user can change.
- OAuth **scopes** limit a token to specific operations.

A leaked read-only token is an incident; a leaked administrator token is a disaster.

### 401 versus 403

| Code | Meaning (RFC 9110) | What to fix |
|---|---|---|
| 401 Unauthorized | The request lacks valid authentication: no credentials, wrong password, expired or invalid token | Authenticate again or fix the credentials |
| 403 Forbidden | The server knows who you are (or does not care) and refuses: the role lacks permission for this resource or method | Ask for the right role; re-authenticating will not help |
| 429 Too Many Requests (RFC 6585) | The client exceeded a rate limit | Slow down; honour any `Retry-After` header |

The names are misleading: "401 Unauthorized" is really an **authentication** failure, and 403 is the **authorization** failure.

## Protecting secrets

Credentials and tokens in code end up in version control, chat logs and screenshots. Rules:

- **Never hard-code** usernames, passwords, API keys or tokens in scripts, and never commit them to Git (public or private).
- Read them from **environment variables**, a protected configuration file excluded from version control, or, best, a **secrets vault** (for example HashiCorp Vault or a cloud secrets manager) that issues them at run time and records who fetched them.
- Do not print tokens or passwords in logs or error messages.
- Rotate credentials and revoke tokens when people leave or a secret may have leaked.

```python
import os
import requests

CATC = "https://catc.example.com"
user = os.environ["CATC_USER"]          # set outside the script
password = os.environ["CATC_PASSWORD"]  # never in the source file

resp = requests.post(f"{CATC}/dna/system/api/v1/auth/token",
                     auth=(user, password), verify="/etc/ssl/certs/corp-ca.pem", timeout=10)
resp.raise_for_status()
token = resp.json()["Token"]
```

## Protecting the API itself

- **Rate limiting** protects the controller from runaway scripts and brute-force attempts; the server answers 429 and well-written clients back off.
- **Input validation**: the server must validate every field (types, lengths, allowed values) and reject anything else, so that a crafted request cannot inject commands or overload a parser. YANG models give RESTCONF and NETCONF a schema to validate against.
- **Logging and auditing**: record who called which endpoint, when, and with what result, and send it to a SIEM. Catalyst Center keeps audit logs of API and GUI changes.
- **Restrict where APIs are reachable from**: a management network or VRF, ACLs on the HTTPS server, and disabling the plain HTTP server (`no ip http server`) on devices.

> **Exam tip:** Expect "which practice improves REST API security" questions. Right answers: HTTPS with certificate validation, token-based authentication with expiry, RBAC and least privilege, secrets in environment variables or a vault, rate limiting, input validation and logging. Wrong answers: HTTP Basic over plain HTTP, `verify=False`, shared administrator accounts, and passwords in the script or the URL.

## Lab it yourself

Use the Cisco DevNet always-on or reservable Catalyst Center and IOS XE sandboxes (any host OS, including Apple silicon Macs), or a Catalyst 8000V in Cisco Modeling Labs, GNS3 or EVE-NG (Windows, Linux or an Intel Mac; on Apple silicon, a remote x86 server).

1. Request a Catalyst Center token with `curl -u` against `/dna/system/api/v1/auth/token`, then call `/dna/intent/api/v1/network-device` with `X-Auth-Token`. Repeat with a wrong token and read the 401.
2. Log in with a read-only account (if the sandbox offers one) and try a `POST`: expect 403.
3. On a Catalyst 8000V enable `ip http secure-server`, `restconf` and a privilege 15 local user, and read `/restconf/data/Cisco-IOS-XE-native:native/hostname`. Try a privilege 1 user and compare.
4. Rewrite a script so that it reads credentials from environment variables and verifies the certificate with a CA file.

## Key takeaways

- Treat APIs as a management plane: HTTPS, strong authentication, least privilege, protected secrets, logging.
- Never disable certificate validation; trust the right CA instead.
- Basic auth is base64, not encryption; tokens and OAuth 2.0 access tokens are scoped and expire.
- Catalyst Center: `POST /dna/system/api/v1/auth/token` with Basic auth returns a token, sent as `X-Auth-Token`; it expires after 60 minutes.
- RESTCONF on IOS XE: Basic auth over HTTPS on each request, privilege 15 user.
- 401 = not authenticated; 403 = authenticated but not allowed; 429 = rate limited.
- No hard-coded secrets: environment variables or a vault; rate limiting, input validation and audit logs protect the server side.
