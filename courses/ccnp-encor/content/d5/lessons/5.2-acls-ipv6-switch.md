## IPv6 ACLs

IPv6 ACLs are always **named** and always extended in style (there is no standard / extended split), and every entry has a sequence number:

```text
R1(config)# ipv6 access-list V6-EDGE-IN
R1(config-ipv6-acl)# sequence 10 permit tcp 2001:db8:10::/64 host 2001:db8:50::20 eq 443
R1(config-ipv6-acl)# sequence 20 permit icmp any any echo-request
R1(config-ipv6-acl)# sequence 30 deny ipv6 any any log
R1(config-ipv6-acl)# exit
R1(config)# interface GigabitEthernet0/0/1
R1(config-if)# ipv6 traffic-filter V6-EDGE-IN in
```

Differences from IPv4 that the exam likes:

- Applied with **`ipv6 traffic-filter NAME in|out`**, not `ip access-group`. On lines it is `ipv6 access-class NAME in`.
- Prefixes use prefix-length notation (`2001:db8:10::/64`), not wildcard masks.
- The `sequence` keyword comes **first** when you enter an entry, and `show` prints it **last**:

```text
R1# show ipv6 access-list V6-EDGE-IN
IPv6 access list V6-EDGE-IN
    permit tcp 2001:DB8:10::/64 host 2001:DB8:50::20 eq 443 (220 matches) sequence 10
    permit icmp any any echo-request (12 matches) sequence 20
    deny ipv6 any any log (4 matches) sequence 30
```

### The implicit entries at the end

Every IPv6 ACL ends with three implicit entries, not one:

```text
permit icmp any any nd-na
permit icmp any any nd-ns
deny ipv6 any any
```

IPv6 has no ARP; it resolves neighbours with ICMPv6 Neighbor Solicitation (NS) and Neighbor Advertisement (NA). The implicit permits keep neighbour discovery working through an ACL that does not mention it.

> **Watch out:** An explicit `deny ipv6 any any` (often added for `log`) sits **above** the implicit entries, so NS and NA are now denied too. Neighbour resolution fails after the cache entries age out, and the interface quietly stops forwarding. If you add an explicit final deny, add `permit icmp any any nd-na` and `permit icmp any any nd-ns` above it, and think about router solicitations and advertisements (`router-solicitation`, `router-advertisement`) if hosts use SLAAC through that interface.

## Three kinds of ACL on a switch

A Catalyst 9000 can filter traffic in three places, and each is configured differently.

| Type | Applied to | Filters | Configured with |
|---|---|---|---|
| Router ACL (RACL) | SVIs and routed ports (`no switchport`) | Traffic routed through that Layer 3 interface | `ip access-group NAME in|out` on the SVI or routed port |
| Port ACL (PACL) | A Layer 2 switch port (access or trunk) | All traffic entering the port, switched or routed | `ip access-group NAME in` on the Layer 2 interface (IPv4, IPv6 and MAC ACLs) |
| VLAN ACL (VACL), also called a VLAN map | A VLAN | All traffic in that VLAN, including traffic between two hosts in the same VLAN that a RACL never sees | `vlan access-map` plus `vlan filter` |

A RACL on an SVI cannot stop two hosts in the same VLAN talking to each other, because their traffic is bridged, never routed. A VACL or PACL can.

### Building a VACL

A VACL is a **map** with sequence-numbered entries. Each entry matches an ACL and takes an **action**. The ACL's `permit` only means "this traffic matches"; the map's `action` decides what happens to it.

```text
SW1(config)# ip access-list extended TFTP-TRAFFIC
SW1(config-ext-nacl)# permit udp any any eq tftp
SW1(config-ext-nacl)# exit
SW1(config)# vlan access-map VLAN20-POLICY 10
SW1(config-access-map)# match ip address TFTP-TRAFFIC
SW1(config-access-map)# action drop
SW1(config-access-map)# exit
SW1(config)# vlan access-map VLAN20-POLICY 20
SW1(config-access-map)# action forward
SW1(config-access-map)# exit
SW1(config)# vlan filter VLAN20-POLICY vlan-list 20
```

- Entry 10 drops TFTP in VLAN 20.
- Entry 20 has **no `match`**, so it matches everything left and forwards it.
- Without entry 20, every packet that matches no entry is **dropped**: a VLAN map ends in an implicit drop, just like an ACL ends in an implicit deny. Forgetting the final `action forward` blacks out the whole VLAN.
- If the ACL in a `match` uses `deny`, packets matched by that deny entry do not match the map entry; they move on to the next map entry.
- Verify with `show vlan access-map VLAN20-POLICY` and `show vlan filter`.

### Order of processing

For a packet that enters a switch port and is routed out of another VLAN, a Catalyst switch applies the filters in this order:

1. **PACL** inbound on the ingress port.
2. **VACL** of the ingress VLAN.
3. **RACL** inbound on the ingress SVI.
4. (Routing decision.)
5. **RACL** outbound on the egress SVI.
6. **VACL** of the egress VLAN.

A packet denied at any step is dropped and later filters never see it. Switched traffic that stays in one VLAN meets only the PACL and the VACL. Platform details (for example whether a PACL is supported outbound, and how PACLs interact with VACLs on the same port) vary by model and release, so check the configuration guide for your switch.

## Other ACL uses worth recognising

ACLs are also used for **classification**, not just filtering, and the meaning of `permit` and `deny` changes:

| Where | `permit` means | `deny` means |
|---|---|---|
| Interface filter (`ip access-group`) | Forward the packet | Drop it |
| Line filter (`access-class`) | Allow the session | Refuse it |
| QoS or CoPP class (`match access-group`) | The packet belongs to this class | It does not belong; try the next class |
| NAT (`ip nat inside source list`) | Translate | Do not translate |
| Route filtering (`distribute-list`) | Accept the route | Filter the route |
| Debug filter (`debug ip packet ACL`) | Show it | Skip it |

The CoPP lesson builds on the third row.

## Lab it yourself

Use one Catalyst 9000v (or IOSvL2) switch with two VLANs and an SVI each, plus three hosts, in Cisco Modeling Labs, GNS3 or EVE-NG. These run Cisco's x86 images on Windows, Linux or an Intel Mac; on an Apple silicon Mac use a remote x86 server or a Cisco DevNet sandbox. Not every virtual switch image programs every ACL type, so if a feature is missing in your image, note the configuration and verify it on hardware later.

1. Put H1 and H2 in VLAN 20, H3 in VLAN 30, with SVIs 10.20.0.1/24 and 10.30.0.1/24.
2. Apply a RACL inbound on SVI 20 that denies ICMP from H1 and permits everything else (without the final `permit ip any any` the implicit deny blocks all routed traffic from VLAN 20). Ping H3 from H1 (blocked) and H2 from H1 (still works: bridged traffic bypasses the RACL).
3. Remove it and build the VACL from this lesson, but drop ICMP instead of TFTP. H1 to H2 is now blocked. Remove sequence 20 and watch the whole VLAN go dark; put it back.
4. Apply a PACL on H1's port and confirm with `show ip interface` or `show running-config interface`.
5. Enable IPv6 on R1 or the SVIs and apply an IPv6 ACL that ends with `deny ipv6 any any log`. Clear the neighbour cache (`clear ipv6 neighbors`) and watch resolution fail; fix it by permitting `nd-na` and `nd-ns`.

## Key takeaways

- IPv6 ACLs are named, use prefix lengths, are applied with `ipv6 traffic-filter` (lines: `ipv6 access-class`), and show the sequence number at the end of each line.
- IPv6 implicit entries: `permit icmp any any nd-na`, `permit icmp any any nd-ns`, `deny ipv6 any any`; an explicit final deny overrides the ND permits.
- RACL filters routed traffic on SVIs and routed ports; PACL filters a Layer 2 port; VACL filters everything in a VLAN, including traffic within the VLAN.
- VACL: `vlan access-map NAME seq`, `match ip address ACL`, `action drop|forward`, then `vlan filter NAME vlan-list N`; implicit drop at the end, so finish with `action forward`.
- Inbound order on a switch: PACL, then VACL, then RACL.
- `permit` and `deny` mean match / no match when an ACL classifies traffic (QoS, CoPP, NAT, VACL).
