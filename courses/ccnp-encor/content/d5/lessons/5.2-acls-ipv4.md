## How an ACL is evaluated

An access control list is an ordered list of entries (ACEs). For each packet the device:

1. Compares the packet with the entries **top to bottom**, in sequence-number order.
2. Stops at the **first** entry that matches and applies its action, `permit` or `deny`.
3. If nothing matches, applies the **implicit `deny any`** at the end of every IPv4 ACL.

Three consequences follow, and most ACL questions test one of them:

- **Order matters.** A broad entry above a specific one hides it. `permit ip 10.1.0.0 0.0.255.255 any` followed by `deny ip host 10.1.1.10 any` never denies anything.
- **An ACL with only `deny` entries blocks everything**, because the implicit deny catches whatever the entries did not.
- **An empty or non-existent ACL applied to an interface permits everything** on IOS XE: the interface filter does nothing until the ACL has entries. (On the other hand, deleting entries from a live ACL takes effect immediately.)

## Standard, extended, numbered, named

| Kind | Matches on | Numbers |
|---|---|---|
| Standard IPv4 | Source address only | 1-99 and 1300-1999 |
| Extended IPv4 | Protocol, source and destination address, ports, flags, DSCP and more | 100-199 and 2000-2699 |
| Named (standard or extended) | Same as above | A name instead of a number |

Named ACLs are what you should write: they are self-documenting, and their configuration mode lets you insert and delete individual entries by sequence number. Numbered ACLs can be edited the same way by entering `ip access-list extended 110` (the number acts as a name).

```text
R1(config)# ip access-list standard MGMT-HOSTS
R1(config-std-nacl)# remark Network operations jump hosts
R1(config-std-nacl)# permit host 10.99.0.10
R1(config-std-nacl)# permit 10.99.1.0 0.0.0.255
R1(config-std-nacl)# exit
R1(config)# ip access-list extended EDGE-IN
R1(config-ext-nacl)# 10 permit tcp 10.1.10.0 0.0.0.255 host 10.50.0.20 eq 443
R1(config-ext-nacl)# 20 permit udp 10.1.10.0 0.0.0.255 host 10.50.0.53 eq domain
R1(config-ext-nacl)# 30 deny   ip any any log
```

The legacy global form `access-list 110 permit tcp ...` appends to the end of ACL 110 and cannot insert in the middle, which is the most common way an engineer adds a `permit` that never matches because it landed below a `deny`.

## Wildcard masks

A wildcard mask says which address bits to **ignore**: a 0 bit must match, a 1 bit is "don't care". For a contiguous block it is the inverse of the subnet mask, which you get by subtracting each octet of the mask from 255.

| Block | Subnet mask | Wildcard |
|---|---|---|
| 10.1.1.0/24 | 255.255.255.0 | 0.0.0.255 |
| 10.1.16.0/20 | 255.255.240.0 | 0.0.15.255 |
| 172.16.8.0/22 | 255.255.252.0 | 0.0.3.255 |
| 192.168.10.64/26 | 255.255.255.192 | 0.0.0.63 |
| 10.0.0.12/30 | 255.255.255.252 | 0.0.0.3 |

Shortcuts: `host 10.1.1.10` equals `10.1.1.10 0.0.0.0`, and `any` equals `0.0.0.0 255.255.255.255`. In a standard ACL a bare address such as `permit 10.1.1.10` is treated as a host.

To check whether an address matches `A W`, compare only the octets where the wildcard is not 255, and in the partial octet check the block: `10.1.16.0 0.0.15.255` covers third octets 16 to 31 (16 + 15). 10.1.31.200 matches; 10.1.32.1 does not.

> **Exam tip:** The block must start on a multiple of its size. `10.1.20.0 0.0.15.255` does not mean 10.1.20.0 to 10.1.35.255: IOS ignores the masked bits, so the entry really matches 10.1.16.0 to 10.1.31.255 (some releases display it rewritten as 10.1.16.0). Always compute the block yourself.

Non-contiguous wildcards are legal (for example `10.1.0.1 0.0.254.0` matches 10.1.x.1 for every even third octet) but rare outside exam questions.

## Extended entries: protocols, ports and flags

```text
permit tcp <source> [port-op] <destination> [port-op] [established] [log | log-input]
```

| Operator | Meaning |
|---|---|
| `eq 22` | Equal to |
| `neq 23` | Not equal to |
| `gt 1023` | Greater than |
| `lt 1024` | Less than |
| `range 20 21` | Inclusive range |

The **position** of the port decides whether it is a source or destination port: the operator after the source address applies to the source port, the operator after the destination address to the destination port. `permit tcp any eq 443 host 10.1.1.10` matches traffic **from** a web server's port 443, which is return traffic, not a connection to a web server. IOS accepts many port names (`www`, `domain`, `bootps`, `ftp-data`, `bgp`) and shows names in `show access-lists` even if you typed numbers.

**`established`** matches TCP segments with the ACK or RST bit set, meaning anything except the first SYN of a connection. Applied inbound on an internet edge, `permit tcp any 10.1.0.0 0.0.255.255 established` allows replies to sessions started inside while blocking new inbound TCP connections. It does not track state: an attacker can still send crafted ACK packets, and it does nothing for UDP or ICMP. A stateful firewall or zone-based firewall is the real solution; `established` is the simple router tool and an exam favourite.

## Sequence numbers and resequencing

Entries in named and numbered ACLs carry sequence numbers, 10, 20, 30 by default. Insert between two entries by giving a number in between, and remove one with `no 20`:

```text
R1(config)# ip access-list extended EDGE-IN
R1(config-ext-nacl)# 15 permit tcp 10.1.10.0 0.0.0.255 host 10.50.0.21 eq 22
R1(config-ext-nacl)# no 20
R1(config-ext-nacl)# exit
R1(config)# ip access-list resequence EDGE-IN 10 10
```

`ip access-list resequence NAME start increment` renumbers the entries (here 10, 20, 30, ...) so there is room for future inserts.

## The implicit deny and why you log an explicit one

The implicit `deny any` has no line in `show access-lists`, so it has **no hit counter**. When traffic is being dropped and you cannot see why, add the deny explicitly with logging as the last entry:

```text
R1(config-ext-nacl)# 1000 deny ip any any log
```

Now drops are counted, and the device sends rate-limited syslog messages (`%SEC-6-IPACCESSLOGP` for TCP and UDP, `%SEC-6-IPACCESSLOGDP` for ICMP) with the source, destination and ports. `log-input` adds the input interface and source MAC address. Logging is process-switched work, so keep it on deny entries and avoid `log` on high-volume permits.

## Applying ACLs and where to put them

```text
R1(config)# interface GigabitEthernet0/0/1
R1(config-if)# ip access-group EDGE-IN in
```

- **One ACL per interface, per direction, per protocol** (one IPv4 in, one IPv4 out, one IPv6 in, one IPv6 out). Applying a second IPv4 ACL in the same direction replaces the first.
- **Inbound** ACLs are checked before the routing decision; **outbound** ACLs after the packet has been routed to the egress interface.
- **Outbound ACLs do not filter traffic the router itself originates.** A ping, a routing update, a syslog or a TACACS+ request from R1 leaves through an outbound ACL unfiltered. To control what reaches the router, use an inbound ACL, `access-class` on the lines, or CoPP.
- Placement rule of thumb: **extended ACLs close to the source**, because they are precise and stop unwanted traffic before it crosses the network; **standard ACLs close to the destination**, because matching only the source address near the source would block that source from everything beyond the router.
- Inbound ACLs also see the router's own control traffic arriving on that interface. An inbound ACL ending in the implicit deny on a WAN link will drop OSPF, BGP or IKE packets unless you permit them.

## Time-based ACLs

An entry can be active only during a time range, based on the device clock (so synchronise it with NTP):

```text
R1(config)# time-range BUSINESS-HOURS
R1(config-time-range)# periodic weekdays 8:00 to 18:00
R1(config-time-range)# exit
R1(config)# ip access-list extended GUEST-IN
R1(config-ext-nacl)# 10 permit tcp 10.30.0.0 0.0.0.255 any eq 443 time-range BUSINESS-HOURS
R1(config-ext-nacl)# 20 deny ip 10.30.0.0 0.0.0.255 any
```

Outside the range, entry 10 is inactive and the traffic falls through to entry 20. `show time-range` shows whether each range is active.

## Verifying

```text
R1# show access-lists EDGE-IN
Extended IP access list EDGE-IN
    10 permit tcp 10.1.10.0 0.0.0.255 host 10.50.0.20 eq 443 (1842 matches)
    20 permit udp 10.1.10.0 0.0.0.255 host 10.50.0.53 eq domain (316 matches)
    30 deny ip any any log (27 matches)
```

```text
R1# show access-lists MGMT-HOSTS
Standard IP access list MGMT-HOSTS
    10 permit 10.99.0.10 (14 matches)
    20 permit 10.99.1.0, wildcard bits 0.0.0.255 (3 matches)
```

- `show access-lists` (or `show ip access-lists`) prints every entry with its sequence number and hit counter. `clear access-list counters NAME` resets the counters so that you can watch a test.
- `show ip interface Gi0/0/1` shows which ACLs are applied: `Inbound  access list is EDGE-IN` and `Outgoing access list is not set`.
- `show running-config | include access-group` lists every application at once.

On Catalyst 9000 switches ACLs are programmed into TCAM; the hit counters can differ from a router's, and hardware statistics are available with platform `show` commands.

> **Real world:** Before applying an ACL on a remote interface, add `reload in 10` or use a configuration archive and `configure replace` with a timer. A wrong inbound ACL on the interface you are managing through cuts your own session.

## Lab it yourself

In Cisco Modeling Labs, GNS3 or EVE-NG (Cisco's x86 images: Windows, Linux or an Intel Mac; on an Apple silicon Mac use a remote x86 server or a Cisco DevNet sandbox), build `PC1 (10.1.10.0/24) - R1 - R2 - SRV (10.50.0.0/24)` with OSPF and a Linux host or IOSv router as SRV running SSH and HTTPS (or use `ip http secure-server` on an IOSv).

1. On R1 create `EDGE-IN` from this lesson and apply it inbound on the PC1-facing interface. Test HTTPS and DNS from PC1 and watch the counters climb.
2. Try SSH from PC1: it fails and the `deny ... log` entry counts it and logs a `%SEC-6-IPACCESSLOGP` message. Insert entry 15 to allow it and run `ip access-list resequence EDGE-IN 10 10`.
3. Add the same rule with the legacy `access-list` global form to a numbered ACL that already ends in a deny, and see that it lands below the deny.
4. Apply an outbound ACL on R1 toward R2 that denies ICMP, then ping R2 from PC1 (blocked) and from R1 itself (not blocked).
5. Build `BUSINESS-HOURS`, change the router clock, and check `show time-range`.
6. Calculate wildcards for three subnets of your choice and verify them with `show access-lists` output and test pings.

## Key takeaways

- First match wins, top to bottom; every IPv4 ACL ends in an implicit deny that has no counter.
- Standard 1-99 and 1300-1999 (source only); extended 100-199 and 2000-2699; prefer named ACLs.
- Wildcard = 255 minus each mask octet; `host` = /32, `any` = everything; check the block boundary.
- Port operators `eq`, `neq`, `gt`, `lt`, `range`; the position decides source or destination port; `established` matches ACK or RST.
- Sequence numbers allow inserts and `no N`; `ip access-list resequence` renumbers.
- End with `deny ip any any log` to count and log drops.
- One ACL per interface, direction and protocol; outbound ACLs do not filter router-originated traffic; extended near the source, standard near the destination.
- Verify with `show access-lists` hit counters and `show ip interface`.
