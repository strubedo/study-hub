## From stateful firewall to NGFW

A **stateful firewall** tracks connections. It permits a TCP session that matches a rule, remembers its 5-tuple and state, and lets the return traffic back without a separate rule. That is a big step over a stateless ACL, but its decisions are still based on **addresses, protocols and ports**. "Permit TCP 443 to any" lets through web browsing, a file-sharing client, a remote-access tool and malware command-and-control alike, because they all use port 443.

A **next-generation firewall (NGFW)** keeps stateful inspection and adds context about **what** the traffic is, **who** sent it and **whether it is malicious**:

| Capability | What it adds | Example policy |
|---|---|---|
| Application visibility and control (AVC) | Identifies the application from the traffic itself, whatever the port | Allow Webex, block BitTorrent, even on 443 |
| User identity | Maps IP addresses to users and groups (from ISE, Active Directory, a captive portal or VPN logins) | Finance group may use the payroll application; contractors may not |
| Intrusion prevention (IPS) | Inspects payloads against signatures and anomalies, inline, and drops exploits | Block an exploit for a known server vulnerability |
| URL filtering | Categorises and scores URLs | Block gambling and newly registered domains |
| Malware inspection | Checks file reputation and sandboxes unknown files; can detect retrospectively | Block a malicious download; alert later if a verdict changes |
| TLS decryption | Decrypts and re-encrypts sessions so the features above can see inside | Inspect traffic to uncategorised sites; exempt banking and health sites |
| Threat intelligence | Reputation feeds for IPs, domains and URLs | Drop connections to known command-and-control servers |

Most traffic is encrypted, so without TLS decryption the IPS and malware engines see only the handshake. Decryption is powerful but costs performance, needs the firewall's CA certificate trusted by clients, and must respect privacy rules, so policies decrypt selectively.

> **Real world:** You will recognise these features from FortiGate (application control, web filtering, IPS and SSL deep inspection in security profiles) and Palo Alto Networks (App-ID, User-ID, Content-ID). The Cisco names differ; the concepts are the same.

## Cisco Secure Firewall Threat Defense

Cisco's NGFW software is **Cisco Secure Firewall Threat Defense (FTD)**, formerly **Firepower Threat Defense**. It combines the stateful firewall, NAT and VPN features that came from the ASA with the Snort-based inspection that came from Firepower (Sourcefire), in one image. It runs on the Cisco Secure Firewall hardware appliance families and as **Threat Defense Virtual** in private and public clouds.

### Management options

| Manager | Scope | Typical use |
|---|---|---|
| **Secure Firewall Management Center (FMC)**, formerly Firepower Management Center | Central management of many FTD devices, on an appliance or VM, or delivered from the cloud | Enterprises: shared policies, event correlation, reporting |
| **Secure Firewall Device Manager (FDM)** | On-box web manager for one device | Small sites with a single firewall |
| Cloud-delivered management | Cisco's cloud management service for firewalls | Managing from the cloud without an on-premises FMC |

A device is managed by one of these at a time; moving between FDM and FMC means re-registering it.

### Policy building blocks

- **Security zones** group interfaces (inside, outside, DMZ); access control rules match source and destination zones, networks, ports, applications, users, URLs and more. If you know FortiGate or Palo Alto zones, these are equivalent.
- **Access control policy**: the ordered rules, each with an action (allow, trust, block, monitor) and optional **intrusion** and **file/malware** policies attached to allowed traffic.
- **Prefilter policy**: fast decisions (block or fast-path) before deep inspection, useful for tunnels and trusted high-volume flows.
- **SSL (decryption) policy**, **identity policy** (which users to learn and how), and **NAT policy**.

### Snort

The inspection engine inside FTD is **Snort**, the open-source IPS originally developed by Sourcefire (acquired by Cisco). Current releases use **Snort 3**. Snort rules are written and updated by **Cisco Talos**, which is how new threat intelligence reaches the firewall's intrusion policy.

## Deployment modes

FTD can be inserted into the network in different ways. **Firewall mode** is chosen for the device; **IPS-only interface modes** can be configured on interfaces.

| Mode | What it does | Use it when |
|---|---|---|
| **Routed** (firewall mode, default) | Each interface is a Layer 3 hop with its own subnet; the firewall routes, runs NAT, VPN and dynamic routing | The firewall is a router between networks: internet edge, data centre segments |
| **Transparent** (firewall mode) | A Layer 2 "bump in the wire": it bridges between interfaces in a bridge group, invisible to routing, with the same subnet on both sides | You must add a firewall without readdressing hosts or changing gateways |
| **Inline set** (IPS interface mode) | A pair of interfaces in the traffic path that passes traffic like a wire while inspecting it; can drop | Add IPS inline in front of an existing firewall or router |
| **Passive** (IPS interface mode) | Receives a **copy** of traffic from a SPAN or tap port and only alerts | Visibility or IDS without any risk to traffic; it cannot block |
| Inline tap | Inline set that inspects a copy and does not drop | Trialling an inline deployment before enforcing |

> **Exam tip:** Passive means **detection only**: the firewall sees a copy, so it can alert but never drop the original packet. Blocking needs routed, transparent or inline set.

High availability is available as **active/standby failover** between two identical devices, and scale-out as **clustering** on supported models.

## Where the NGFW sits in the design

An NGFW is typically placed at the **internet edge** (outbound control and inbound protection of published services), at **data centre** boundaries (east-west segmentation between application tiers), at **branch** sites (local internet breakout, often combined with SD-WAN), and in **public cloud** as Threat Defense Virtual. It works with the other layers: ISE supplies user identity and SGTs, Talos supplies intelligence, and events go to the SIEM and to Secure Network Analytics.

## Lab it yourself

Threat Defense Virtual and the Management Center Virtual run as VMs (KVM, VMware) with an evaluation period and large resource needs. The practical options:

1. Reserve a Cisco DevNet Secure Firewall sandbox (any host OS, including Apple silicon Macs) and explore an access control rule that matches an application, a URL category and a user.
2. Or, on Windows, Linux or an Intel Mac with plenty of RAM, run Threat Defense Virtual managed by Device Manager in Cisco Modeling Labs (if your image set includes it), EVE-NG or a hypervisor; on Apple silicon use a remote x86 server.
3. Build three zones (inside, outside, DMZ), a NAT rule, and an allow rule with an intrusion policy attached; generate test traffic and read the connection and intrusion events.
4. Compare an allow rule written by port with one written by application, and note what each lets through.

## Key takeaways

- Stateful firewalls track sessions by address, protocol and port; NGFWs add application, user, IPS, URL, malware and TLS decryption.
- Cisco's NGFW is Secure Firewall Threat Defense (formerly Firepower Threat Defense): ASA firewall features plus Snort inspection.
- Manage many devices with Secure Firewall Management Center (formerly Firepower Management Center), one device with Device Manager, or from the cloud.
- Security zones group interfaces; access control rules match zones, networks, applications, users and URLs and attach intrusion and file policies.
- Routed and transparent are firewall modes; inline set and passive are IPS interface modes; passive cannot block.
- Snort (now Snort 3) is the inspection engine; Talos writes its rules.
