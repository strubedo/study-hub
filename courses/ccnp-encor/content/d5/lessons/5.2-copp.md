## Three planes, one CPU

Every packet a router or switch handles belongs to one of three planes:

| Plane | What it is | Examples |
|---|---|---|
| Data (forwarding) plane | Transit traffic: packets passing **through** the device | User traffic routed or switched in hardware (on routers, by CEF and the forwarding processors) |
| Control plane | Traffic the device needs to build its tables, addressed **to** it | OSPF, EIGRP, BGP, LDP, HSRP, STP BPDUs, LACP, ARP, CDP and LLDP |
| Management plane | Traffic used to operate the device, addressed **to** it | SSH, Telnet, SNMP, NTP, syslog, TACACS+ and RADIUS replies, NETCONF and RESTCONF |

Data-plane traffic is forwarded by hardware (Catalyst 9000 UADP ASICs) or by fast software paths (QFP on ISR 4000 and Catalyst 8000) without the route processor's general-purpose CPU. Some traffic must be **punted** to that CPU instead:

- Packets addressed to the device itself (control and management protocols, pings to its addresses).
- Packets with IP options, TTL expiring (the CPU sends ICMP time exceeded), or that need fragmentation with DF set.
- ARP requests for the device's addresses, glean traffic (packets to a connected host whose ARP entry is missing), and packets that need ICMP unreachables or redirects.
- Packets matching `log` ACL entries and other features that need software processing.

The CPU can handle far less traffic than the forwarding hardware. A flood of punted packets, malicious (a SYN flood at the SSH port, an ICMP flood at the loopback) or accidental (a loop, an ARP storm), starves the CPU, and the first casualties are the routing protocol hellos and keepalives. Adjacencies drop and the network melts down although the forwarding hardware was never busy.

**Control Plane Policing (CoPP)** protects the CPU by rate-limiting the traffic punted to it, class by class, so that a flood of one type cannot starve the others.

## CoPP on IOS XE routers: MQC applied to the control plane

On ISR 4000, Catalyst 8000 and other IOS XE routers, CoPP is a normal Modular QoS CLI (MQC) policy attached to a special interface called `control-plane`. There is no CoPP policy by default; you build it.

### Step 1: classify with ACLs and class maps

```text
R1(config)# ip access-list extended COPP-ROUTING
R1(config-ext-nacl)# permit ospf any any
R1(config-ext-nacl)# permit tcp any any eq bgp
R1(config-ext-nacl)# permit tcp any eq bgp any
R1(config-ext-nacl)# exit
R1(config)# ip access-list extended COPP-MGMT
R1(config-ext-nacl)# permit tcp 10.99.0.0 0.0.0.255 any eq 22
R1(config-ext-nacl)# permit udp 10.99.0.0 0.0.0.255 any eq snmp
R1(config-ext-nacl)# permit udp host 10.99.0.123 eq ntp any
R1(config-ext-nacl)# exit
R1(config)# ip access-list extended COPP-ICMP
R1(config-ext-nacl)# permit icmp any any
R1(config-ext-nacl)# exit
R1(config)# class-map match-all CM-COPP-ROUTING
R1(config-cmap)# match access-group name COPP-ROUTING
R1(config-cmap)# class-map match-all CM-COPP-MGMT
R1(config-cmap)# match access-group name COPP-MGMT
R1(config-cmap)# class-map match-all CM-COPP-ICMP
R1(config-cmap)# match access-group name COPP-ICMP
```

The two BGP lines catch both directions of a session (to port 179 when the neighbour initiated it, from port 179 when this router did).

> **Exam tip:** In a CoPP (or any QoS) class ACL, `permit` means "this packet belongs to the class" and `deny` means "it does not belong to this class". A `deny` entry **does not drop** anything: the packet simply moves on to the next class and, if nothing else matches, lands in `class-default`. To drop a type of traffic, match it with `permit` in a class whose action is `drop` (or a policer whose conform and exceed actions both drop).

### Step 2: police each class in a policy map

```text
R1(config)# policy-map PM-COPP
R1(config-pmap)# class CM-COPP-ROUTING
R1(config-pmap-c)# police 1000000 conform-action transmit exceed-action transmit
R1(config-pmap-c)# class CM-COPP-MGMT
R1(config-pmap-c)# police 512000 conform-action transmit exceed-action drop
R1(config-pmap-c)# class CM-COPP-ICMP
R1(config-pmap-c)# police 64000 conform-action transmit exceed-action drop
R1(config-pmap-c)# class class-default
R1(config-pmap-c)# police 256000 conform-action transmit exceed-action drop
```

- **`police RATE`** is in **bits per second** by default. `police rate 200 pps` polices in **packets per second**, which suits the CPU better: the cost of punting is per packet, not per bit. On IOS XE, a pps policer is only accepted in a policy applied to the control plane.
- **`conform-action`** applies to traffic within the rate, **`exceed-action`** to traffic above it (a three-color policer adds `violate-action`, for traffic beyond the excess burst of a single-rate policer or above the peak rate of a two-rate policer). Typical actions are `transmit` and `drop`.
- Routing protocols are often given `exceed-action transmit` and only monitored at first: you want to know they exceed the baseline, not drop hellos.
- **`class-default`** catches everything not matched by an earlier class, including traffic you forgot to classify. Police it, but not so hard that an unclassified but necessary protocol breaks.
- Queueing actions (`bandwidth`, `priority`, `shape`, `queue-limit`, `random-detect`) are rejected on the control plane: CoPP only polices, marks or drops.

### Step 3: attach it to the control plane

```text
R1(config)# control-plane
R1(config-cp)# service-policy input PM-COPP
```

CoPP is almost always applied **input**: it polices traffic arriving at the CPU.

## Verifying CoPP

```text
R1# show policy-map control-plane
 Control Plane

  Service-policy input: PM-COPP

    Class-map: CM-COPP-MGMT (match-all)
      18342 packets, 1617284 bytes
      5 minute offered rate 3000 bps, drop rate 0000 bps
      Match: access-group name COPP-MGMT
      police:
          cir 512000 bps, bc 16000 bytes
        conformed 18342 packets, 1617284 bytes; actions:
          transmit
        exceeded 0 packets, 0 bytes; actions:
          drop
        conformed 3000 bps, exceeded 0000 bps

    Class-map: CM-COPP-ICMP (match-all)
      52210 packets, 5534260 bytes
      5 minute offered rate 71000 bps, drop rate 7000 bps
      Match: access-group name COPP-ICMP
      police:
          cir 64000 bps, bc 2000 bytes
        conformed 47120 packets, 4994720 bytes; actions:
          transmit
        exceeded 5090 packets, 539540 bytes; actions:
          drop
        conformed 64000 bps, exceeded 7000 bps

    Class-map: class-default (match-any)
      2214 packets, 190412 bytes
      5 minute offered rate 0000 bps, drop rate 0000 bps
      Match: any
      ...
```

Read it per class: **offered rate** is what arrived, **conformed** and **exceeded** counters show how much fell into each action, and a non-zero **drop rate** tells you CoPP is actively discarding that class. Here ICMP arrives at about 71 kbit/s against a 64 kbit/s policer, so the excess (about 7 kbit/s, 5,090 packets so far) is dropped. A growing `exceeded` count in the management class is the usual explanation for "SSH to the router is slow or times out during an attack".

Build CoPP in stages: classify and police everything with `transmit` for both actions, watch the counters for a baseline over days, then set the rates and change exceed actions to `drop`.

## CoPP on Catalyst 9000 switches: the system policy

Catalyst 9000 switches handle CoPP differently, and the exam expects you to know the difference.

- CoPP is **on by default**. A system-defined policy named **`system-cpp-policy`** is attached to the control plane automatically and cannot be removed.
- The policy contains **system-defined classes** (for example `system-cpp-police-routing-control`, `system-cpp-police-protocol-snooping`, `system-cpp-police-data`, `system-cpp-police-sys-data`), each mapped to one or more CPU queues and policed by the switch hardware in **packets per second**.
- You **can** change the police rate of a system-defined class, for example to raise the rate for a busy protocol:

```text
SW1(config)# policy-map system-cpp-policy
SW1(config-pmap)# class system-cpp-police-protocol-snooping
SW1(config-pmap-c)# police rate 2000 pps
```

- You **cannot** delete the policy, attach a different policy of your own to the control plane, or change what the system classes match. Restoring the factory rates is done with `cpp system-default`.
- Verify with `show policy-map control-plane` (the class list and rates) and, for the hardware view of each CPU queue with its policer and drop counters, `show platform hardware fed switch active qos queue stats internal cpu policer`.

| | IOS XE routers (ISR, Catalyst 8000) | Catalyst 9000 switches |
|---|---|---|
| Default | No CoPP until you configure it | `system-cpp-policy` applied automatically |
| Policy | Your own MQC policy | Fixed system policy; rates adjustable |
| Classification | Your ACLs and class maps | System-defined classes and CPU queues |
| Rate units | bps by default, or `pps` | pps |
| Verification | `show policy-map control-plane` | `show policy-map control-plane` and `show platform hardware fed ... cpu policer` |

## CoPP versus CPPr

**Control Plane Protection (CPPr)** is an extension found on some IOS routers that splits the control plane into three sub-interfaces so that policies can be applied separately:

- `control-plane host`: traffic addressed to the device's own interfaces (routing protocols, management).
- `control-plane transit`: software-switched transit traffic.
- `control-plane cef-exception`: packets punted because of a CEF exception (TTL expiry, IP options, ARP, Layer 2 keepalives).

CPPr also adds a **port filter** (drop packets to closed TCP or UDP ports early) and **queue thresholds** (limit queued packets per protocol). CoPP, which polices the aggregate control plane, is the feature to configure on current IOS XE platforms; recognise CPPr as the finer-grained relative.

## Lab it yourself

Use two IOS XE routers (Catalyst 8000V) and a Linux host in Cisco Modeling Labs, GNS3 or EVE-NG. These run Cisco's x86 images on Windows, Linux or an Intel Mac; on an Apple silicon Mac use a remote x86 server or a Cisco DevNet sandbox. Policer accuracy in a virtual router is approximate; the configuration and counters are what you are practising.

1. Run OSPF between R1 and R2 and allow SSH to R1 from the host in 10.99.0.0/24.
2. Build the ACLs, class maps and `PM-COPP` from this lesson, but with `exceed-action transmit` everywhere, and attach it with `control-plane` / `service-policy input PM-COPP`.
3. Generate traffic: `ping 10.0.0.1 size 1400 repeat 100000 timeout 0` from R2 (an IOS rapid ping), or a flood ping from the Linux host. Watch `show policy-map control-plane` counters.
4. Change ICMP's exceed action to `drop` and lower the rate; watch the `exceeded` counter grow while OSPF stays up.
5. Add `deny icmp host 10.99.0.10 any` at the top of `COPP-ICMP` and confirm that pings from that host move to `class-default` instead of being dropped.
6. If you have a Catalyst 9000 (or a 9000v image), run `show policy-map control-plane` and `show platform hardware fed switch active qos queue stats internal cpu policer`, and change one system class rate.

## Key takeaways

- Data plane forwards transit traffic in hardware; control and management planes are traffic to the device, handled by the CPU.
- CoPP rate-limits punted traffic per class so one flood cannot starve routing protocols and management.
- Router CoPP: ACLs, `class-map` with `match access-group`, `policy-map` with `police RATE conform-action transmit exceed-action drop`, then `control-plane` and `service-policy input`.
- A `deny` in a CoPP class ACL means "not this class", never "drop"; unmatched traffic goes to `class-default`.
- `police` defaults to bps; `police rate N pps` polices packets and is the natural unit for CPU protection; queueing actions are not allowed on the control plane.
- Catalyst 9000: `system-cpp-policy` is applied by default and cannot be replaced; adjust class rates (pps), restore with `cpp system-default`.
- Verify with `show policy-map control-plane`: offered rate, conformed, exceeded and drop rate per class.
