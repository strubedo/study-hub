## What a data modeling language is for

CLI output is written for people: column positions shift between releases, and a script that screen-scrapes `show` output breaks when they do. A **data model** describes, once and precisely, what configuration and state a device has: the names, the hierarchy, the data type of every value, which values are keys, which can be written and which are read-only. **YANG** (RFC 7950 for YANG 1.1) is the language the industry uses to write those models. It is not a protocol and not an encoding: it is the schema that NETCONF, RESTCONF and gNMI all carry data for, in XML or JSON.

Benefits the exam expects you to describe:

- **Structured, typed data**: an MTU is a `uint16` with a range, not a column of text, so the device can **validate** a change before applying it and return a precise error.
- **One model, many protocols and encodings**: the same `ietf-interfaces` tree is read with NETCONF (XML), RESTCONF (XML or JSON) or gNMI.
- **Vendor-neutral automation** when standard models (IETF, OpenConfig) are used; the same script works on different platforms.
- **Machine-readable and discoverable**: devices advertise the modules they support (NETCONF hello capabilities, YANG library), and tools generate documentation, code and API stubs from the models.
- **Separation of configuration and operational state** in one consistent tree.

## Building blocks

```text
module example-vlans {
  yang-version 1.1;
  namespace "urn:example:vlans";
  prefix ev;

  revision 2026-01-15 {
    description "Initial revision.";
  }

  container vlans {
    list vlan {
      key "id";
      leaf id {
        type uint16 {
          range "1..4094";
        }
      }
      leaf name {
        type string;
      }
      leaf-list tagged-ports {
        type string;
      }
      leaf state {
        type enumeration {
          enum active;
          enum suspended;
        }
        config false;
      }
    }
  }
}
```

| Statement | Meaning | In the example |
|---|---|---|
| `module` | The unit of definition, with a globally unique `namespace`, a short `prefix` and dated `revision`s | `example-vlans` |
| `container` | Groups related nodes; has no value of its own; exactly one instance | `vlans` |
| `list` | A sequence of entries, each identified by its **key** leaf or leaves (like rows in a table) | `vlan`, keyed by `id` |
| `leaf` | A single value of one type | `id`, `name`, `state` |
| `leaf-list` | A sequence of simple values of one type | `tagged-ports` |
| `type` | Built-in types (`string`, `boolean`, `uint8`...`uint64`, `int8`...`int64`, `decimal64`, `enumeration`, `empty`, `union`, `leafref`, `identityref` and others) with restrictions such as `range`, `length` and `pattern`; `typedef` creates reusable types | `uint16` with `range "1..4094"` |
| `config true / false` | Configuration (read and write) versus operational state (read-only); `true` is the default and is inherited by children | `state` is state data |
| `grouping` / `uses` | A reusable block of nodes, inserted where `uses` names it | not shown |
| `rpc` and `action` | Operations a client can invoke, with `input` and `output` (an `action` is tied to a node in the tree) | not shown |
| `notification` | An event the server can send to subscribers | not shown |
| `augment` | Adds nodes from **another module** into an existing tree | `ietf-ip` adds `ipv4` and `ipv6` under each `ietf-interfaces` interface |
| `deviation` | A vendor declares where its implementation **differs** from a model (not supported, different range or default) | IOS XE ships `cisco-xe-openconfig-...-deviation` modules |

A **presence container** (`presence` statement) means something just by existing, like a feature switch; a normal container exists only to hold children.

## Reading a tree diagram

Engineers rarely read raw YANG; they read the tree that `pyang -f tree` (and tools such as Cisco YANG Suite) prints, in the notation of RFC 8340:

```text
module: example-vlans
  +--rw vlans
     +--rw vlan* [id]
        +--rw id              uint16
        +--rw name?           string
        +--rw tagged-ports*   string
        +--ro state?          enumeration
```

| Symbol | Meaning |
|---|---|
| `rw` | Configuration data (config true) |
| `ro` | State data (config false), or RPC output and notification content |
| `-x` / `-n` | An RPC or action / a notification |
| `*` after a name | A list or leaf-list (many entries) |
| `[id]` | The list's key leaf or leaves |
| `?` | Optional leaf |
| `!` | Presence container |
| `prefix:name` | Node added by augmentation from another module |

The real `ietf-interfaces` model (RFC 8343) begins like this:

```text
module: ietf-interfaces
  +--rw interfaces
     +--rw interface* [name]
        +--rw name                        string
        +--rw description?                string
        +--rw type                        identityref
        +--rw enabled?                    boolean
        +--rw link-up-down-trap-enable?   enumeration {if-mib}?
        +--ro admin-status                enumeration {if-mib}?
        +--ro oper-status                 enumeration
        ...
        +--ro statistics
           +--ro in-octets?            yang:counter64
           ...
```

(`{if-mib}?` marks a node that exists only if the server supports the `if-mib` feature.)

From it you can read off a RESTCONF URI (`/restconf/data/ietf-interfaces:interfaces/interface=GigabitEthernet1`, the key after `=`), a NETCONF subtree filter, and the fact that `oper-status` and `statistics` cannot be configured.

> **Exam tip:** In a tree, `*` plus `[key]` is a list, `*` alone is a leaf-list, `rw` is configuration, `ro` is state. The key leaf is mandatory, so it has no `?`.

## Native, IETF and OpenConfig models

| Model family | Written by | Example on IOS XE | Strength | Limitation |
|---|---|---|---|---|
| **Native** (vendor) | Cisco | `Cisco-IOS-XE-native` (configuration, mirrors the CLI), `Cisco-IOS-XE-interfaces-oper` (state) | Covers almost every feature the CLI has | Platform-specific; a script for IOS XE does not work on another OS |
| **IETF** | IETF working groups, as RFCs | `ietf-interfaces`, `ietf-ip`, `ietf-routing` | Standard, stable, vendor-neutral | Covers common features only |
| **OpenConfig** | Operator group (large network operators) | `openconfig-interfaces`, `openconfig-bgp` | Vendor-neutral, operationally focused, designed for streaming telemetry | Each vendor supports a subset, declared with deviations |

Devices often support all three for the same feature; a change made through one model shows up in the others and in the CLI. Cisco publishes its IOS XE models per release in the public `YangModels/yang` GitHub repository (`vendor/cisco/xe/<release>`).

## How YANG relates to the protocols and encodings

| Protocol | Transport | Encoding of YANG data | Typical use |
|---|---|---|---|
| NETCONF (RFC 6241) | SSH, TCP 830 | XML | Configuration with transactions, locks and candidate datastore |
| RESTCONF (RFC 8040) | HTTPS | JSON (RFC 7951) or XML | Simple CRUD with HTTP methods |
| gNMI | gRPC over HTTP/2 with TLS | JSON (JSON_IETF) or Protocol Buffers | Configuration and, above all, streaming telemetry |

The model is the contract; the protocol is the transport; XML or JSON is just how one instance of the model is written down. That is why lesson 4.6's NETCONF filter and RESTCONF URI for GigabitEthernet1 name the same module and the same list key.

## Lab it yourself

Reading models needs only a browser or Python 3 on any host, Apple silicon included; exercising them needs an IOS XE device (a Catalyst 8000V in CML, GNS3 or EVE-NG on Windows, Linux or an Intel Mac; on an Apple silicon Mac a remote x86 server or a DevNet IOS XE sandbox).

1. Browse `vendor/cisco/xe/` in the `YangModels/yang` GitHub repository and open `ietf-interfaces.yang` for your release. Find the `list interface`, its `key`, and a `config false` node.
2. Optionally install `pyang` (`python3 -m pip install pyang`) on your workstation and run `pyang -f tree ietf-interfaces.yang`; compare the output with the RFC 8343 tree above.
3. With RESTCONF enabled (lesson 4.6), `GET` `ietf-interfaces:interfaces`, then `Cisco-IOS-XE-native:native/interface`, then `openconfig-interfaces:interfaces` for the same port, and compare the three views.
4. Change a description through one model and read it back through the other two and with `show running-config interface`.

## Key takeaways

- YANG (RFC 7950) is a **data modeling language**: it defines structure, types, keys and config versus state; it is not a protocol or an encoding.
- Building blocks: module (namespace, prefix, revision), container, list with key, leaf, leaf-list, typedef and types, grouping/uses, rpc/action, notification, augment, deviation.
- Tree notation: `rw` config, `ro` state, `*` list or leaf-list, `[key]`, `?` optional, `!` presence container, `prefix:` augmented node.
- Native models cover everything on one platform; IETF and OpenConfig models are vendor-neutral but cover less; vendors publish deviations.
- NETCONF (XML over SSH), RESTCONF (JSON or XML over HTTPS) and gNMI (gRPC) all carry YANG-modelled data.
- Benefits: validation before commit, precise errors, consistent automation across platforms, discoverable capabilities.
