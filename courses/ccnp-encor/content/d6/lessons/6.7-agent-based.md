## Orchestration tools and the agent question

**Configuration management and orchestration tools** keep many systems in a defined state: you describe what each system should look like once, in files under version control, and the tool makes it so and keeps it so. Topic 6.7 compares them on one axis first: does the managed system run a piece of the tool's software (an **agent**), or does the tool reach in over protocols the system already has (**agentless**)? That choice drives everything else: who starts a change (push or pull), what has to be installed and opened in firewalls, and whether the tool suits network devices at all.

This lesson covers the agent-based tools, Puppet, Chef and SaltStack; the next covers the agentless ones, Ansible above all.

## Push, pull, declarative, procedural

| Term | Meaning |
|---|---|
| **Pull** | The agent on each node contacts the server on a schedule, asks for its desired state and applies it. Changes reach the node at the next check-in |
| **Push** | The control system connects to the nodes and sends the change now |
| **Declarative** | You state the end result ("NTP server 192.0.2.123 is configured"); the tool works out the steps and does nothing if the state is already right |
| **Procedural (imperative)** | You list the steps in order ("run this, then this"); the result depends on the order |
| **Idempotent** | Applying the same definition twice gives the same result and the second run changes nothing |

## Puppet

| | |
|---|---|
| Agent | Yes: the **Puppet agent** runs on every managed node |
| Server | **Puppet Server** (older material says Puppet master) |
| Model | **Pull**: by default each agent checks in every **30 minutes** |
| Transport | HTTPS on **TCP 8140** (the agent connects to the server), with certificates from Puppet's own CA |
| Language | **Manifests** (`.pp` files) in Puppet's **declarative DSL**, grouped into **modules**; data in Hiera |
| Flow | Agent sends its **facts** (from Facter) → server compiles a **catalog** for that node → agent applies it and sends a **report** |

```text
class ntp_client {
  package { 'chrony':
    ensure => installed,
  }
  service { 'chronyd':
    ensure  => running,
    enable  => true,
    require => Package['chrony'],
  }
}
```

The manifest says what must be true; if `chrony` is installed and running, a run changes nothing. Puppet is model-driven and strongly declarative, which suits large server estates. For devices that cannot run an agent, Puppet can manage them through a proxy that talks to the device on the agent's behalf, which gives up much of the agent model's advantage.

## Chef

| | |
|---|---|
| Agent | Yes: **Chef Infra Client** runs on every node |
| Components | **Chef Infra Server** (stores cookbooks, policies and node data), a **workstation** where engineers write and test code and upload it with `knife`, and the **nodes** |
| Model | **Pull**: the client contacts the server over **HTTPS (TCP 443)**; run as a daemon it checks in every 1,800 seconds (30 minutes) by default |
| Language | **Recipes** written in a **Ruby** DSL, grouped into **cookbooks**; recipes are collections of resources |
| Push | The **Chef Push Jobs** add-on let the server tell clients to run immediately over its own ZeroMQ channel (its server's default settings use TCP ports in the 10000 to 10003 range); its repository has since been archived, so treat it as legacy and do not rely on the port numbers |

```text
package 'chrony'

service 'chronyd' do
  action [:enable, :start]
end
```

Each resource in a recipe is declarative, but Chef runs resources **in the order they appear**, so Cisco's comparison tables usually call Chef **procedural**, and Puppet **declarative**. Its Ruby base gives engineers a full programming language where Puppet gives a restricted DSL.

## SaltStack (Salt)

| | |
|---|---|
| Agent | Yes, normally: the **Salt minion** runs on each node. **salt-ssh** is an agentless alternative over SSH |
| Server | **Salt master** |
| Transport | **ZeroMQ** over TCP **4505** (the master publishes commands) and **4506** (minions return results and request files); both are opened **on the master only**, because minions connect out to it |
| Model | Minions keep a persistent connection, so the master can **push** a command to thousands of minions at once; minions can also pull their state |
| Language | **States** in YAML files (`.sls`), usually templated with Jinja; **grains** are facts about a minion, **pillars** hold per-minion data |
| Network devices | **Proxy minions** run elsewhere and manage devices that cannot host a minion (over SSH, NETCONF or an API) |

```text
chrony:
  pkg.installed: []
  service.running:
    - name: chronyd
    - enable: true
    - require:
      - pkg: chrony
```

Salt's event bus also lets it react to events (a "reactor"), which makes it popular for event-driven automation at scale.

## What agents buy you, and what they cost

| Advantages | Disadvantages |
|---|---|
| Continuous enforcement: drift is corrected at every check-in, even if nobody runs anything | Software must be installed, upgraded and secured on every node |
| Scales well: nodes do the work and fetch their own configuration | The agent must be supported on the node's operating system and hardware |
| Works through NAT and firewalls that allow outbound connections only | Extra ports and certificates to manage (8140, 4505/4506) |
| Rich facts and reporting from every node | Changes are not immediate in a pull model unless you trigger a run |

> **Exam tip:** Associate each agent-based tool with its keywords: **Puppet** = agent, pull, manifests, declarative DSL, TCP 8140. **Chef** = agent, pull, recipes and cookbooks in Ruby, server / workstation / node, HTTPS to the server (TCP 443). **Salt** = minion (or agentless salt-ssh), master, ZeroMQ TCP 4505/4506, states in YAML.

## Lab it yourself

These tools manage servers first, so the easiest lab is two or three Linux VMs or containers on your own workstation (VirtualBox or VMware Workstation on Windows and Linux; UTM or VMware Fusion with ARM Linux guests on any Mac, Apple silicon included).

1. Install Puppet Server on one VM and the agent on another; sign the agent's certificate, apply the `ntp_client` class, then run `puppet agent -t` twice and compare the reports.
2. Install a Salt master and a minion, accept the minion key with `salt-key`, run `salt '*' test.ping`, then apply the `chrony` state with `salt '*' state.apply` twice.
3. On the master, check which ports are listening (`ss -tlnp`) and confirm 4505 and 4506; on the Puppet server, 8140.
4. Optional: try `salt-ssh` against a VM with no minion installed.

## Key takeaways

- Agent-based tools install software on every managed node; the agent normally **pulls** its desired state from a server on a schedule.
- **Puppet**: agent and Puppet Server, pull every 30 minutes by default, HTTPS on **TCP 8140**, declarative **manifests** in modules.
- **Chef**: Chef Infra Client, Chef Infra Server and a workstation; **recipes** and **cookbooks** in **Ruby**; pull over HTTPS (TCP 443); the legacy Push Jobs add-on could trigger an immediate run.
- **Salt**: minions and a master over **ZeroMQ TCP 4505/4506**; **states** in YAML; fast push to many minions; **salt-ssh** and proxy minions work without an agent.
- Agents give continuous drift correction and scale, at the cost of installing and maintaining software that most network devices cannot run.
