## What EEM is

The **Embedded Event Manager (EEM)** is automation that lives **on the device**. An **applet** waits for one **event** (a syslog message, a tracked object changing state, a timer, a CLI command, an SNMP value) and, when it fires, runs a list of **actions** (CLI commands, syslog messages, email, variable logic). No server, no SSH session and no Python are involved, so it keeps working when the network that would carry those things is down. EEM also supports Tcl policies; the exam and this course cover **applets**, which are configured entirely in the CLI.

Topic 6.6 asks you to **construct** applets for three jobs: changing configuration (this lesson), troubleshooting, and data collection (the next two lessons). The building blocks are the same for all three, so they come first.

## Anatomy of an applet

```text
R1(config)# event manager applet ISP1-DOWN
R1(config-applet)# event track 10 state down
R1(config-applet)# action 1.0 cli command "enable"
R1(config-applet)# action 2.0 cli command "configure terminal"
R1(config-applet)# action 3.0 cli command "interface GigabitEthernet0/0/2"
R1(config-applet)# action 4.0 cli command "no shutdown"
R1(config-applet)# action 5.0 cli command "end"
R1(config-applet)# action 6.0 syslog msg "ISP1 lost: backup link Gi0/0/2 enabled by EEM"
R1(config-applet)# end
```

| Part | Rule |
|---|---|
| `event manager applet NAME` | Creates the applet and enters applet configuration. Options on this line include `authorization bypass` and `trap` (send an SNMP trap when it runs) |
| `event ...` | **Exactly one** event detector per applet (EEM can correlate several with `event tag` and `trigger`, beyond this topic). Re-entering `event` replaces it |
| `action LABEL ...` | One action per line. The label is a **string**; actions run in **label sort order**, not in the order typed |

The applet registers as soon as it has an event and you leave the submode. It is part of the running configuration (save it like anything else).

### Why `enable` comes first

`cli command` actions run in a CLI session that EEM opens for the applet, and that session starts in **user EXEC mode**, like a fresh vty login. Without `action 1.0 cli command "enable"`, `configure terminal` and most `show` commands fail (the applet still runs, the commands just do nothing useful), so every applet that touches the CLI starts with `enable` and, to change configuration, `configure terminal`. End configuration with `end` so later `show` or `write memory` actions run in privileged EXEC.

### Label ordering

Labels are compared as **strings**, character by character, so `10.0` sorts **before** `2.0` (the first characters are `1` and `2`). An applet labelled `1.0, 2.0, ..., 9.0, 10.0` runs `10.0` second. Avoid the trap with a consistent scheme:

| Labels typed | Run order |
|---|---|
| `1.0, 2.0, 10.0` | 1.0, **10.0**, 2.0 |
| `1.0, 1.1, 1.2 ... 1.9, 2.0` | As intended |
| `010, 020, 100` | As intended (zero-padded, equal length) |

To insert an action between `1.0` and `2.0`, use `1.5`. Labels are unique within the applet; re-entering an existing label replaces that action.

> **Exam tip:** If an exhibit shows actions typed in one order but labelled out of sequence, the device runs them in **label order**. If labels mix `9.0` and `10.0`, sort them as text before you predict what happens.

## Event detectors

| Detector | Syntax example | Fires when |
|---|---|---|
| Syslog | `event syslog pattern "%LINEPROTO-5-UPDOWN.*GigabitEthernet0/0/1.*down"` [`occurs 3 period 60`] | A log message matches the regular expression (optionally N times within a period) |
| Track | `event track 10 state down` (`up`, `down` or `any`; default `any`) | Tracked object 10 changes to that state (for example an IP SLA from topic 4.4) |
| Timer | `event timer watchdog time 300` | Every 300 seconds, repeatedly |
| | `event timer countdown time 60` | Once, 60 seconds after registration |
| | `event timer cron cron-entry "0 2 * * *"` | On a cron schedule (minute hour day-of-month month day-of-week): here 02:00 every day |
| | `event timer absolute time ...` | Once at an absolute time |
| CLI | `event cli pattern "reload" sync no skip yes` | A user enters a command matching the pattern |
| None | `event none` [`sync yes`] | Only when an administrator runs `event manager run NAME` |
| Interface | `event interface name GigabitEthernet0/0/1 parameter input_errors entry-op ge entry-val 100 entry-type increment poll-interval 60` | An interface counter crosses a threshold |
| SNMP | `event snmp oid <OID> get-type exact entry-op ge entry-val 80 poll-interval 30` | A polled MIB object crosses a threshold |

`sync` and `skip` on `event cli`: with `sync no`, the policy runs asynchronously and `skip yes` means the matched command is **not executed** (skip is only allowed with `sync no`); `skip no` lets it run. With `sync yes`, the command waits for the applet, and the applet's exit status decides whether the command runs.

## Actions

| Action | Example | Does |
|---|---|---|
| `cli command` | `action 2.0 cli command "show ip route summary"` | Runs a command; its output is stored in `$_cli_result`. A `pattern "..."` option waits for a prompt such as `[confirm]`, answered by the next `cli command` |
| `syslog` | `action 3.0 syslog priority warnings msg "Gi0/0/1 flapped"` | Writes a log message (shown with the `%HA_EM-6-LOG:` prefix and applet name by default) |
| `mail` | `action 4.0 mail server "192.0.2.25" to "noc@example.com" from "r1@example.com" subject "R1 alert" body "$_cli_result"` | Sends email through an SMTP server |
| `set`, `increment`, `decrement`, `append` | `action 1.0 set count "0"`, `action 2.0 increment count` | Variables, referenced as `$count` |
| `if` / `elseif` / `else` / `end` | `action 5.0 if $_cli_result eq "..."` ... `action 7.0 end` | Conditions with `eq`, `ne`, `gt`, `ge`, `lt`, `le` |
| `regexp` | `action 4.0 regexp "Full" "$_cli_result"` | Regular-expression match, setting `$_regexp_result` |
| `foreach` / `while` | `action 3.0 foreach line "$output" "\n"` ... `end` | Loops |
| `wait` | `action 5.0 wait 10` | Pauses N seconds |
| `puts` | `action 6.0 puts "$_cli_result"` | Prints to the terminal of a user who ran the applet with `event manager run` (`event none sync yes`) |
| `reload`, `exit` | `action 9.0 reload` | Reloads the device / stops the applet |

### Built-in variables

| Variable | Holds |
|---|---|
| `$_cli_result` | Output of the most recent `cli command` action |
| `$_syslog_msg` | The syslog message that triggered a `event syslog` applet |
| `$_event_pub_time` | When the event was published |

Each detector publishes its own `$_...` variables; `show event manager detector <name> detailed` lists them on the device.

## Applets and AAA

On a device with **AAA command authorization** (`aaa authorization commands 15 default group tacacs+`), the commands in an applet are authorized like any other session's, but the EEM session has no user, so the TACACS+ server rejects them and the applet silently fails. Two fixes:

| Command | Effect |
|---|---|
| `event manager session cli username EEM-ADMIN` | Global: EEM CLI sessions run as this user, which the AAA server must authorize (the model also allows a `privilege` level) |
| `event manager applet NAME authorization bypass` | Per applet: its CLI actions skip AAA command authorization |

## Configuration automation examples

**Fail over to a backup link.** The `ISP1-DOWN` applet above pairs with an `ISP1-UP` applet that shuts Gi0/0/2 again when track 10 returns `up`. Track 10 follows an IP SLA probe (topic 4.4), so the router reacts to loss of reachability, not just to a link going down.

**Save the configuration on demand, answering the prompt:**

```text
event manager applet SAVE-NOW
 event none sync yes
 action 1.0 cli command "enable"
 action 2.0 cli command "copy running-config startup-config" pattern "Destination filename"
 action 3.0 cli command "startup-config"
 action 4.0 puts "$_cli_result"
```

Run it with `event manager run SAVE-NOW`. Action 2.0 waits for the `Destination filename [startup-config]?` prompt, and 3.0 answers it by typing the file name. (`write memory` saves without a prompt; the copy form is here to show `pattern`.)

**Re-apply a standard line after it is removed.** An applet triggered by `%SYS-5-CONFIG_I` can check `show running-config | include ^logging host` with `if` and re-add a removed line. Use this kind of self-healing sparingly: it hides changes from the people who made them.

> **Real world:** EEM changes have no change ticket and no peer review. Log every action with `syslog`, keep applets short, and test them with `event none` before giving them a live trigger.

## Verifying

| Command | Shows |
|---|---|
| `show running-config \| section event manager` | The applets as configured (actions listed in label order) |
| `show event manager policy registered` | Registered applets: class, event type, time registered, name and the event and actions |
| `show event manager history events` | When each applet ran and its result |
| `event manager run NAME` | Runs an `event none` applet now |
| `debug event manager action cli` | Each CLI action and the device's response (for example an error from a missing `enable`) |

## Lab it yourself

Use one or two Catalyst 8000V routers in Cisco Modeling Labs, GNS3 or EVE-NG on Windows, Linux or an Intel Mac; on an Apple silicon Mac use a remote x86 server or a Cisco DevNet IOS XE sandbox.

1. Configure an IP SLA ICMP echo to a neighbour's address and `track 10 ip sla 1 reachability` (lesson 4.4).
2. Build `ISP1-DOWN` and `ISP1-UP`. Shut the neighbour's interface and watch `%TRACK` and `%HA_EM` messages; confirm Gi0/0/2 came up.
3. Delete `action 1.0` from `ISP1-DOWN`, repeat, and read `debug event manager action cli` to see why nothing changed.
4. Relabel the actions `1.0` to `10.0` and run `show running-config | section ISP1-DOWN` to see the order EEM will use.
5. Build `SAVE-NOW` and run it with `event manager run SAVE-NOW`.

## Key takeaways

- An applet is `event manager applet NAME`, one `event` line, and `action LABEL` lines; it lives in the running configuration.
- Actions run in **string** order of their labels: `10.0` runs before `2.0`. Use `1.0, 1.1 ...` or zero-padded labels.
- CLI actions start in user EXEC: begin with `cli command "enable"`, then `"configure terminal"` for changes, `"end"` afterwards.
- Detectors: `syslog pattern`, `track N state`, `timer watchdog | countdown | cron | absolute`, `cli pattern ... sync ... skip ...`, `none` (`event manager run`), `interface`, `snmp`.
- Actions: `cli command` (output in `$_cli_result`), `syslog msg`, `mail`, `set`, `if`/`else`/`end`, `regexp`, `wait`, `puts`.
- With AAA command authorization, use `event manager session cli username` or `authorization bypass`.
- Verify with `show event manager policy registered`, `show event manager history events` and `debug event manager action cli`.
