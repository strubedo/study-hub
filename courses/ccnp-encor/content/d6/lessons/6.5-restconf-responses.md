## What RESTCONF adds to plain HTTP

RESTCONF (RFC 8040) uses ordinary HTTP status codes, but it ties each method to a precise meaning (lesson 4.6 covers the URIs and how to enable it on IOS XE). Its bodies are YANG data in `application/yang-data+json` or `application/yang-data+xml`, and its error bodies follow one fixed structure, `ietf-restconf:errors`, carried over from NETCONF's `<rpc-error>`. If you can read those two things, you can tell exactly what happened to any request.

## Which method returns which code

| Request | Success | Typical failures |
|---|---|---|
| `GET` / `HEAD` a resource | **200 OK** with the data | **404** the path does not exist or the node has no data; **400** a bad query parameter |
| `POST` to a parent, creating a child | **201 Created**, a `Location` header naming the new resource, **no body** | **409 Conflict** if the child already exists |
| `POST` to `/restconf/operations/<module>:<rpc>` | **200 OK** with output, or **204** if the RPC has no output | **400** bad input |
| `PUT` a resource | **201 Created** if it did not exist; **204 No Content** if it existed and was **replaced** | **400** body does not match the URI or the model |
| `PATCH` (plain merge) | **204 No Content** (200 if the server returns a body) | The target must already exist: PATCH never creates it |
| `DELETE` a resource | **204 No Content** | **404** (or 409 `data-missing`) if it does not exist |
| Any request | | **401** bad or missing credentials; **403** user not authorized; **405** method not supported on that resource; **406** `Accept` asks for an encoding the server cannot produce; **415** `Content-Type` of the body is not supported; **500** the server failed to apply it; **503** the service is unavailable |

> **Exam tip:** PUT is the one with two success codes: **201** means "created", **204** means "existed, replaced". POST is the one that fails with **409** on something that already exists. PATCH and DELETE succeed with **204** and an empty body.

## Reading a successful response

```text
GET /restconf/data/Cisco-IOS-XE-native:native/hostname HTTP/1.1
Host: 192.0.2.10
Accept: application/yang-data+json

HTTP/1.1 200 OK
Content-Type: application/yang-data+json

{
  "Cisco-IOS-XE-native:hostname": "R1"
}
```

```text
GET /restconf/data/ietf-interfaces:interfaces HTTP/1.1
Host: 192.0.2.10
Accept: application/yang-data+json

HTTP/1.1 200 OK
Content-Type: application/yang-data+json

{
  "ietf-interfaces:interfaces": {
    "interface": [
      {
        "name": "GigabitEthernet1",
        "description": "Link to ISP",
        "type": "iana-if-type:ethernetCsmacd",
        "enabled": true,
        "ietf-ip:ipv4": {
          "address": [
            {
              "ip": "203.0.113.2",
              "netmask": "255.255.255.252"
            }
          ]
        },
        "ietf-ip:ipv6": {}
      },
      {
        "name": "Loopback0",
        "type": "iana-if-type:softwareLoopback",
        "enabled": true,
        "ietf-ip:ipv4": {
          "address": [
            {
              "ip": "10.255.0.1",
              "netmask": "255.255.255.255"
            }
          ]
        },
        "ietf-ip:ipv6": {}
      }
    ]
  }
}
```

How to read it:

- **`Content-Type: application/yang-data+json`**: YANG data encoded as JSON (RFC 7951), not generic `application/json`.
- The **top-level key is module-qualified**: `"ietf-interfaces:interfaces"` names the YANG module and the node you asked for. Inside it, names are unqualified (`interface`, `name`) until a node from **another module** appears: `"ietf-ip:ipv4"` is added to each interface by the `ietf-ip` module.
- `interface` is a YANG **list**, so it is a JSON **array**; each entry is identified by its key, `name`.
- Identity values are qualified too: `"iana-if-type:ethernetCsmacd"`.
- Loopback0 has no description, so the `description` member is simply absent: RESTCONF omits leaves that have no value.

In Python, `r.json()["ietf-interfaces:interfaces"]["interface"][1]["ietf-ip:ipv4"]["address"][0]["ip"]` is `"10.255.0.1"`. Forgetting the module prefix on the first key is the most common `KeyError`.

## Reading an error response

For any 4xx code except 403, RFC 8040 says the server SHOULD send an error body built from the `yang-errors` template in the `ietf-restconf` module (servers often use the same body for 5xx errors too, such as 500 `operation-failed`):

```text
POST /restconf/data/Cisco-IOS-XE-native:native/interface HTTP/1.1
Host: 192.0.2.10
Content-Type: application/yang-data+json
Accept: application/yang-data+json

{"Cisco-IOS-XE-native:Loopback": [{"name": 100, "description": "Managed by RESTCONF"}]}

HTTP/1.1 409 Conflict
Content-Type: application/yang-data+json

{
  "ietf-restconf:errors": {
    "error": [
      {
        "error-type": "protocol",
        "error-tag": "data-exists",
        "error-message": "object already exists: /ios:native/ios:interface/ios:Loopback[ios:name='100']"
      }
    ]
  }
}
```

| Field | Meaning | Values |
|---|---|---|
| `error-type` | Which layer detected the error | `transport`, `rpc`, `protocol`, `application` |
| `error-tag` | The NETCONF-style error identifier, which maps to the status code | `data-exists`, `data-missing`, `invalid-value`, `access-denied`, `in-use`, `lock-denied`, `malformed-message`, `operation-not-supported`, `operation-failed`, `unknown-element` and others |
| `error-path` (optional) | The node in error | An instance identifier |
| `error-message` (optional) | Human-readable text | Varies by platform and release |

RFC 8040 maps error tags to codes, which lets you go from either one to the other:

| error-tag | Status |
|---|---|
| `malformed-message`, `unknown-element`, `bad-element`, `missing-attribute` | 400 |
| `invalid-value` | 400, 404 or 406 |
| `access-denied` | 401 or 403 |
| `operation-not-supported` | 405 or 501 |
| `in-use`, `lock-denied`, `resource-denied`, `data-exists`, `data-missing` | 409 |
| `operation-failed` | 412 or 500 |

(For a POST to an existing resource, RFC 8040's text names `resource-denied` while its own example shows `data-exists`; either with 409 means "it already exists".) (The body sends the new list entry as a one-element array, as RFC 8040's own POST example does.) Here the Loopback100 entry already existed, so the fix is `PUT` (create or replace) or `PATCH` (merge) on `.../interface/Loopback=100` instead of `POST`.

> **Watch out:** `lock-denied` (409) on RESTCONF usually means a NETCONF session holds a lock on the datastore. RESTCONF has no locks of its own, but it respects NETCONF's: check `show netconf-yang sessions` for a global lock.

## Diagnosing from code plus body

| You see | Most likely cause |
|---|---|
| 401, empty or short body | Wrong username or password, or `ip http authentication local` missing so the credentials are checked elsewhere |
| 403 | The user is not authorized at privilege 15 |
| 404 with `invalid-value` and a message about the URI | Module name or node misspelled, a key value wrong, or a `/` in an interface name not encoded as `%2F` |
| 400 with `malformed-message` | Invalid JSON in the body |
| 400 with `unknown-element` or `invalid-value` | Valid JSON, but a member name or value that does not fit the model (for example `"enabled": "yes"` where a boolean is required) |
| 405 | Method not supported on that resource (the response lists the allowed ones in an `Allow` header) |
| 406 | `Accept` asks for an encoding the server cannot send |
| 409 `data-exists` | POST of something that already exists |
| 409 `lock-denied` or `in-use` | Datastore locked by a NETCONF session |
| 415 | Body sent with an unsupported `Content-Type` (for example `text/plain`) |
| 500 `operation-failed` | Syntactically valid change that the device could not apply |
| Connection refused or reset | No error body at all: RESTCONF or the HTTPS server is not running (`restconf`, `ip http secure-server`) |

## Lab it yourself

Use a Catalyst 8000V with RESTCONF enabled (lesson 4.6) in Cisco Modeling Labs, GNS3 or EVE-NG on Windows, Linux or an Intel Mac; on an Apple silicon Mac use a remote x86 server or a DevNet IOS XE sandbox. Send requests with curl, Postman or Python 3 `requests` from any workstation (`-k` and `verify=False` are for the lab only, and the password is yours, not a value from this page).

1. `GET` the hostname and `ietf-interfaces:interfaces`; find the module-qualified top-level key and the `ietf-ip:ipv4` member.
2. `POST` Loopback100 to `Cisco-IOS-XE-native:native/interface`: expect 201 and a `Location` header. POST it again: read the 409 error body.
3. `PUT` Loopback101 twice: note 201 then 204. `PATCH` a description onto it: 204. `DELETE` it twice: 204, then an error.
4. Misspell the module (`ietf-interface:interfaces`), break the JSON with a trailing comma, and send a body with `Content-Type: text/plain`; record each status code and `error-tag`.
5. Log in with a privilege 1 user and compare the code with that for a wrong password.

## Key takeaways

- GET 200; POST create **201** (plus `Location`, no body) or **409** if it exists; PUT **201** created or **204** replaced; PATCH **204** (never creates); DELETE **204**.
- 400 malformed or invalid body, 401 authentication, 403 authorization, 404 path or key not found, 405 method, 406 `Accept`, 409 exists or locked, 415 `Content-Type`, 500 could not apply.
- Success bodies are `application/yang-data+json` with a **module-qualified top-level key** (`ietf-interfaces:interfaces`); members from other modules are qualified too (`ietf-ip:ipv4`); YANG lists are JSON arrays.
- Error bodies are `ietf-restconf:errors` → `error` array → `error-type`, `error-tag`, optional `error-path` and `error-message`.
- Read code and `error-tag` together: `data-exists` 409 means use PUT or PATCH; `invalid-value` 404 means check the URI.
