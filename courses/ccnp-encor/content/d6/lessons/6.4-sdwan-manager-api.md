## Where the API sits in Catalyst SD-WAN

In **Cisco Catalyst SD-WAN**, the **SD-WAN Manager** (formerly vManage) is the management plane: the GUI, the configuration database and the single API endpoint for the whole overlay. The **SD-WAN Controller** (formerly vSmart) runs OMP and distributes policy and routes, the **SD-WAN Validator** (formerly vBond) authenticates and orchestrates new devices, and the **WAN Edge** routers (Catalyst 8000, ISR 1000/4000 and older vEdge) forward traffic. Topic 1.2 covers that architecture.

Automation tools do not log in to each WAN Edge. They call SD-WAN Manager's **northbound REST API**; SD-WAN Manager then configures the controllers and WAN Edges **southbound** over its secure control connections and collects their state and statistics. One API call can therefore change or query hundreds of routers.

| | SD-WAN Manager API |
|---|---|
| Style | REST over HTTPS, JSON bodies |
| Base path | **`/dataservice/`**, for example `https://manager.example.com/dataservice/device` |
| Versioning | Classic resources such as `/dataservice/device` carry no version in the URL (Cisco documents an optional vendor `Accept` header, default version 1.0); newer configuration-group resources do, for example `/dataservice/v1/feature-profile/sdwan/...` |
| Main namespaces | `/dataservice/device` (inventory, device actions, real-time state), `/dataservice/template` (templates and policy), `/dataservice/statistics` and `/dataservice/data/device/statistics` (aggregated and bulk statistics), `/dataservice/system/device` (controllers and edges as configured) |
| Authentication | Session cookie plus XSRF token (classic), or JWT from release 20.18.1 |
| Documentation | Built into SD-WAN Manager (the API documentation page of your release) and published on DevNet |

## Session-based authentication (JSESSIONID and XSRF token)

This is the method most scripts, the Postman collections and the older SDKs use, and the one the exam describes.

1. **Log in**: `POST /j_security_check` with `Content-Type: application/x-www-form-urlencoded` and the body `j_username=<USERNAME>&j_password=<PASSWORD>`. On success the body is **empty** and the response sets a cookie **`JSESSIONID=<session hash>`**.
2. **Get the XSRF token**: `GET /dataservice/client/token` with the `JSESSIONID` cookie. The body is the token itself, as plain text.
3. **Call the API**: send the cookie on every request, and the token in the **`X-XSRF-TOKEN`** header (required for most `POST`, `PUT` and `DELETE` requests; optional on `GET`).
4. **Log out**: `POST /logout` with the cookie, to release the session.

```text
POST /j_security_check HTTP/1.1
Host: manager.example.com
Content-Type: application/x-www-form-urlencoded

j_username=apiuser&j_password=ExamplePass123

HTTP/1.1 200 OK
Set-Cookie: JSESSIONID=<SESSION-HASH>; Path=/; Secure; HttpOnly
Content-Length: 0
```

```text
GET /dataservice/client/token HTTP/1.1
Host: manager.example.com
Cookie: JSESSIONID=<SESSION-HASH>

HTTP/1.1 200 OK

<XSRF-TOKEN>
```

> **Watch out:** A failed `j_security_check` login does not necessarily return 401. Cisco documents that the response body then contains an **HTML login page**, so a script must check the body for `<html>` rather than trusting the status code. The password above is a placeholder.

Cisco documents a default session lifetime of 24 hours, a 30-minute inactivity timeout and a limit of 100 concurrent sessions, after which the least recently used session is dropped. Reusing one session for all calls (a `requests.Session()` object in Python keeps the cookie for you) is both faster and kinder to the server than logging in for every request.

## JWT authentication (newer releases)

From release 20.18.1, SD-WAN Manager also accepts **JSON Web Tokens**: `POST /jwt/login` with a JSON body containing `username`, `password` and an optional `duration` returns a `token` (default lifetime 1,800 seconds), a `refresh` token and a `csrf` value. Later requests send `Authorization: Bearer <TOKEN>` and, for changes, `X-XSRF-TOKEN: <csrf value>`. The session method remains supported for backward compatibility.

## Reading inventory

```text
GET /dataservice/device HTTP/1.1
Host: manager.example.com
Cookie: JSESSIONID=<SESSION-HASH>
Accept: application/json
```

Each device record includes fields such as `host-name`, `system-ip`, `site-id`, `device-type` and `personality` (`vedge` for WAN Edges, `vsmart`, `vbond`, `vmanage` for the controllers: the internal names did not change with the rebranding), `device-model`, `version`, `reachability`, `controlConnections`, `bfdSessionsUp` and `ompPeers`. Note the hyphenated names: in Python you read them as `dev["host-name"]`, never `dev.host-name`.

Most list resources return a **data block**: a JSON object with a `header` (generation time, column definitions and field types used by the GUI) and a **`data`** array holding the records. Scripts usually go straight to `resp.json()["data"]`.

Other examples: `/dataservice/system/device/controllers` lists the controllers; template and policy resources live under `/dataservice/template/...`; device actions and real-time monitoring calls under `/dataservice/device/...` take the device's **system IP** as `deviceId`. Long operations (attaching a template, a software upgrade) return an id that the client polls, the same accept-and-track pattern as Catalyst Center.

## Errors and limits

| Code | Meaning in SD-WAN Manager's documentation |
|---|---|
| 200 / 201 | Success / new resource created |
| 400 | Request invalid (malformed JSON, missing field) |
| 401 | Authentication missing or incorrect (no or expired session) |
| 403 | Understood but not allowed (for example a missing XSRF token on a POST, or a read-only user) |
| 404 | Resource not found (often a typo in the path) |
| 429 | Rate limit exceeded |
| 500 / 503 | Server error / service unavailable |

From release 20.6 Cisco documents rate limits of 100 requests per second for most APIs and 48 per minute for the bulk statistics API, plus at most two concurrent bulk statistics requests.

## Catalyst Center and SD-WAN Manager compared

| | Catalyst Center | SD-WAN Manager |
|---|---|---|
| Formerly | DNA Center | vManage |
| Manages | Campus and branch (switches, routers, SD-Access) | SD-WAN overlay (controllers, WAN Edges) |
| Base path | `/dna/intent/api/v1/...` | `/dataservice/...` |
| Login | `POST /dna/system/api/v1/auth/token`, Basic auth | `POST /j_security_check`, form fields `j_username` / `j_password` (or `/jwt/login`) |
| Carry the credential as | `X-Auth-Token: <token>` header | `Cookie: JSESSIONID=...` plus `X-XSRF-TOKEN` from `/dataservice/client/token` (or `Authorization: Bearer`) |
| Results in | `response` (and `version`) | `data` (and `header`) |
| Long operations | 202 plus `taskId`, poll `/task/{taskId}` | Returns an id to poll |

> **Exam tip:** Match the clue to the product: `j_security_check`, `JSESSIONID`, `X-XSRF-TOKEN` and `/dataservice` mean SD-WAN Manager; `auth/token`, `X-Auth-Token` and `/dna/intent` mean Catalyst Center.

## Lab it yourself

Use a Cisco DevNet Catalyst SD-WAN sandbox from any host operating system (Windows, macOS on Intel or Apple silicon, Linux) with curl, Postman or Python 3 and `requests` (Windows: `py`; macOS and Linux: `python3`). Use the sandbox's own credentials and keep them out of files you share.

1. `curl -k -c cookies.txt -X POST -H "Content-Type: application/x-www-form-urlencoded" -d "j_username=<USERNAME>&j_password=<PASSWORD>" https://<sandbox>/j_security_check`, then look at `cookies.txt` for `JSESSIONID`.
2. `curl -k -b cookies.txt https://<sandbox>/dataservice/client/token` and keep the token.
3. `curl -k -b cookies.txt https://<sandbox>/dataservice/device` and list `host-name`, `system-ip` and `personality` for each record in `data`.
4. Log in with a wrong password and read the body you get back.
5. In Python, use `requests.Session()` for the login and reuse it for the token and the device list; finish with `POST /logout`.

## Key takeaways

- SD-WAN Manager (formerly vManage) is the single northbound REST API for the Catalyst SD-WAN overlay; it configures controllers and WAN Edges southbound.
- Base path `/dataservice/`; examples `/dataservice/device`, `/dataservice/system/device/controllers`, `/dataservice/template/...`.
- Session login: `POST /j_security_check` with `j_username` / `j_password` (form-encoded) returns the **JSESSIONID** cookie; `GET /dataservice/client/token` returns the **XSRF token**, sent as `X-XSRF-TOKEN` on changes; `POST /logout` at the end.
- A failed `j_security_check` login returns an HTML login page; check the body.
- Release 20.18.1 adds JWT (`/jwt/login`, `Authorization: Bearer`).
- Results usually sit in `data`, with a `header` describing the columns; device fields use hyphenated names such as `host-name` and `system-ip`.
