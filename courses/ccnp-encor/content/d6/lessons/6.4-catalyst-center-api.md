## The four directions of the Catalyst Center platform

**Cisco Catalyst Center** (formerly Cisco DNA Center; the URLs still start with `/dna/`) exposes its functions to other software through APIs. Cisco describes them by direction, as if the controller sat in the middle of a compass:

| Direction | What it is | Used for |
|---|---|---|
| **Northbound**: Intent API | A REST API over HTTPS with JSON bodies, organised into domains and subdomains (Devices, Sites, Discovery, Configuration Templates, SWIM, Command Runner, Issues, Path Trace, Event Management and more) | Scripts, orchestrators and applications asking Catalyst Center to report or do something |
| **Eastbound**: events and notifications | Catalyst Center **pushes** events (Assurance issues, SWIM and other automation events, system events) to subscribers by email, syslog or a **webhook** (an HTTPS POST or PUT to your listener) | Reacting to events without polling |
| **Westbound**: integration API | Bundles that link Catalyst Center to IT service management (ITSM) such as ServiceNow, and to IPAM and reporting systems | Opening incidents, change approval, IP address management |
| **Southbound**: device management | How Catalyst Center talks to devices: SSH and CLI, SNMP, NETCONF, telemetry | Configuring and monitoring the network |

Cisco's earlier DNA Center material also described a southbound **multivendor SDK**: device packages that let Catalyst Center manage some third-party devices. Treat it as a high-level idea; the exam topic is the northbound API.

> **Exam tip:** **Northbound** is software talking **to** the controller (the Intent API); **southbound** is the controller talking **to** devices. A webhook is a callback: the controller calls you, so you need a listener reachable from Catalyst Center.

## The Intent API in practice

**Base paths.** Every request starts with `https://<catalyst-center>` and one of three prefixes:

| Prefix | Contents |
|---|---|
| `/dna/system/api/` | Platform functions, including authentication (`/dna/system/api/v1/auth/token`) |
| `/dna/intent/api/` | The Intent API: devices, sites, templates, tasks, events and so on |
| `/dna/data/api/` | Newer data and analytics resources (for example Assurance issues at `assuranceIssues`, aggregated health) |

**Authentication.** Token based, in two steps:

1. `POST /dna/system/api/v1/auth/token` with an HTTP **Basic** `Authorization` header (`base64(username:password)`). A successful reply is **200 OK** with the body `{"Token": "<TOKEN>"}`.
2. Send that string in the **`X-Auth-Token`** header of every later request. The token lasts **60 minutes**; after that, requests return **401 Unauthorized** and the client requests a new token. (Topic 5.3 covers protecting the credentials and token.)

```text
POST /dna/system/api/v1/auth/token HTTP/1.1
Host: cc.example.com
Authorization: Basic <BASE64-OF-USERNAME:PASSWORD>
Content-Type: application/json

HTTP/1.1 200 OK
Content-Type: application/json

{"Token": "example-token-not-real"}
```

```text
GET /dna/intent/api/v1/network-device?family=Switches%20and%20Hubs&limit=100&offset=1 HTTP/1.1
Host: cc.example.com
X-Auth-Token: example-token-not-real
Accept: application/json
```

**Methods.** Standard REST verbs: `GET` reads, `POST` creates or triggers, `PUT` updates, `DELETE` removes. Bodies are JSON in both directions.

**Example resources** (all under `/dna/intent/api/v1/`):

| Resource | Method | Purpose |
|---|---|---|
| `network-device` | GET | Device inventory; filters such as `hostname`, `managementIpAddress`, `family`, `platformId`, `reachabilityStatus`; `.*` works as a wildcard; paged with `limit` and `offset` (up to 500 records per page) |
| `network-device/count` | GET | Number of devices |
| `network-device/{id}` | GET, DELETE | One device by its UUID |
| `network-device` | POST | Add a device (asynchronous) |
| `site`, `site-health` | GET | Hierarchy and health |
| `network-device-poller/cli/read-request` | POST | Command Runner: run read-only `show` commands (asynchronous) |
| `task/{taskId}` | GET | Status of an asynchronous operation |
| `issues` | GET | Assurance issues |
| `event/subscription`, `event/webhook` | GET, POST, PUT | Event subscriptions and webhook destinations |

Results come back wrapped in a JSON object: the data is in **`response`** (an array for lists, an object for single items) next to a **`version`** string. Topic 6.5 reads these bodies in detail.

## Synchronous and asynchronous calls

Reads such as `GET network-device` are **synchronous**: the data is in the reply. Operations that take time (adding a device, starting a discovery, deploying a template, running Command Runner, distributing an image) are **asynchronous**:

1. The `POST` (or `PUT` / `DELETE`) returns **202 Accepted** at once, with a task reference:
   `{"response": {"taskId": "<UUID>", "url": "/dna/intent/api/v1/task/<UUID>"}, "version": "1.0"}`
2. The client polls `GET /dna/intent/api/v1/task/<taskId>`.
3. The task object reports `progress`, `isError`, `failureReason`, and an `endTime` once it has finished.

**202 means "accepted for processing", not "succeeded".** Cisco's own example: posting a discovery with a name that already exists returns 202, and the task then shows `"isError": true` with `"failureReason": "Discovery name is duplicate"`. A script that stops at the 202 reports success for a job that failed.

> **Watch out:** Some newer asynchronous APIs use a different task resource (`/dna/intent/api/v1/tasks/{id}`), and the Event Management API returns an `executionId` that you poll at `/dna/intent/api/v1/event/api-status/{executionId}`, but the pattern is the same: accept, return an id, poll.

## Events and webhooks

Instead of polling for problems, subscribe to events. In the GUI or through the Event Management API you choose events (for example a device becoming unreachable, or a SWIM image distribution failing) and a destination: an email address, a syslog server, or a **REST endpoint** (webhook). When the event fires, Catalyst Center sends an HTTPS POST (or PUT) with a JSON description of the event to that URL. Each event has a type (NETWORK, APP, SYSTEM, SECURITY, INTEGRATIONS), a category (INFO, WARN, ALERT, ERROR, TASK PROGRESS) and a severity from 1 to 5.

## Ways in besides raw HTTP

Cisco publishes a **Python SDK** (`catalystcentersdk`, successor to `dnacentersdk`), an **Ansible** collection, a **Terraform** provider, Postman collections and an always-on DevNet sandbox. They all call the same Intent API; the SDK handles the token, retries and rate limiting (HTTP 429 with a `Retry-After` header) for you.

## Lab it yourself

Use the Cisco DevNet Catalyst Center sandbox from any host operating system (Windows, macOS on Intel or Apple silicon, Linux), with a browser, curl or Postman, and Python 3 with `requests` (Windows: `py`; macOS and Linux: `python3`). Use the credentials the sandbox page gives you; never paste them into shared files.

1. Request a token with curl: `curl -k -X POST -u '<USERNAME>:<PASSWORD>' https://<sandbox>/dna/system/api/v1/auth/token`.
2. `GET /dna/intent/api/v1/network-device/count` and then `network-device?limit=5` with the `X-Auth-Token` header. Find `response` and `version` in the reply.
3. Repeat the GET with a deliberately wrong token and note the status code.
4. Open the API documentation in the sandbox GUI or on DevNet, find a `POST` that returns a task, and trace the `taskId` to `GET /dna/intent/api/v1/task/{taskId}` (in a reservable sandbox, where you may make changes).
5. Find the event subscription and webhook resources in the Event Management section.

## Key takeaways

- Catalyst Center APIs by direction: **northbound** Intent API (REST, JSON, HTTPS), **eastbound** events and webhooks, **westbound** ITSM and IPAM integration, **southbound** device protocols (plus a multivendor SDK in Cisco's earlier material).
- Authenticate with `POST /dna/system/api/v1/auth/token` and Basic auth; send the returned `Token` as **`X-Auth-Token`**; it expires after 60 minutes (then 401).
- Intent API paths are `/dna/intent/api/v1/...`, for example `network-device`, `site`, `task/{taskId}`, `issues`.
- Long operations are asynchronous: **202 Accepted** plus a `taskId`; poll the task and check `isError` and `failureReason`; 202 is not success.
- Webhooks push JSON events to your HTTPS listener; SDK, Ansible and Terraform wrap the same API.
- AI in the v1.2 blueprint lives in topic 4.5; the API exposes AI-driven issues through the `aiDriven` filter of `GET /dna/data/api/v1/assuranceIssues`.
