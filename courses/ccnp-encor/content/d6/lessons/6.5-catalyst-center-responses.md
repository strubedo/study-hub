## Two things to read in every reply

Every HTTP response gives you a **status code** (did the request work, and if not, whose fault was it) and usually a **body** (the data, or a description of the error). Topic 6.5 asks you to interpret both for Catalyst Center and for RESTCONF. This lesson does Catalyst Center; the next does RESTCONF.

Status codes come in classes defined by HTTP (RFC 9110):

| Class | Meaning | Whose problem |
|---|---|---|
| 2xx | Success (or accepted) | Nobody's |
| 3xx | Redirection | Follow the `Location` |
| 4xx | Client error: the request is wrong | Yours: fix the request, credentials or permissions |
| 5xx | Server error: the request may be fine | The server's: retry later, check the controller |

## Status codes as Catalyst Center uses them

The meanings below are those in Cisco's Catalyst Center SDK and API documentation.

| Code | Name | What it means for the Intent API | What the script should do |
|---|---|---|---|
| **200** | OK | Request succeeded and the body has content (a `GET`, and also the token request) | Parse `response` |
| **201** | Created | A new resource was created | Read the body or `Location` if provided |
| **202** | Accepted | The request was accepted for **asynchronous** processing; **not finished, not necessarily successful** | Take `response.taskId`, poll the task |
| **204** | No Content | Success with no body | Do not call `.json()` on it |
| **400** | Bad Request | Malformed JSON, missing required field, invalid value or parameter | Fix the body or parameters |
| **401** | Unauthorized | Missing, wrong or **expired** token (tokens last 60 minutes), or bad credentials on the token request | Get a new token |
| **403** | Forbidden | Authenticated, but the user's role is not allowed to do this | Use an account with the right role; a new token will not help |
| **404** | Not Found | Wrong URI, or the resource (such as a device id) does not exist | Check the path and the id |
| **405** | Method Not Allowed | The resource exists but not with that method (for example `PUT` where only `GET` is offered) | Use the documented method |
| **409** | Conflict | The request conflicts with the current state or an established rule | Read the error, resolve the conflict |
| **415** | Unsupported Media Type | Missing or unsupported `Content-Type` on a request with a body | Send `Content-Type: application/json` |
| **429** | Too Many Requests | Rate limited; a `Retry-After` header says how long to wait | Wait and retry |
| **500** | Internal Server Error | The server failed while handling the request | Retry, then check Catalyst Center health or open a case |
| **503** | Service Unavailable | Overloaded, starting up or in maintenance (for example the API service not yet up after a restart) | Wait and retry |

> **Exam tip:** **401 versus 403** is the classic pair. 401 = "I don't know who you are" (no or bad token). 403 = "I know who you are, and you may not do that" (role). And **202 is not success**: the answer to "did the template deploy?" is in the task, not the status line.

## Reading a list response

The Intent API wraps its data in an object with two members: **`response`**, holding the data, and **`version`**, a string. For a list resource `response` is an **array** of objects; for a single item it is an **object**; for a count it is a **number**.

```text
GET /dna/intent/api/v1/network-device?family=Switches%20and%20Hubs

HTTP/1.1 200 OK
Content-Type: application/json

{
  "response": [
    {"hostname": "SW1", "managementIpAddress": "10.10.20.11", "platformId": "C9300-48P",
     "softwareVersion": "17.12.4", "reachabilityStatus": "Reachable", "role": "ACCESS",
     "id": "3f0c1e9a-1111-4a6b-9c1d-000000000001"},
    {"hostname": "SW2", "managementIpAddress": "10.10.20.12", "platformId": "C9300-48P",
     "softwareVersion": "17.9.5", "reachabilityStatus": "Unreachable", "role": "ACCESS",
     "id": "3f0c1e9a-1111-4a6b-9c1d-000000000002"},
    {"hostname": "DSW1", "managementIpAddress": "10.10.20.2", "platformId": "C9500-24Y4C",
     "softwareVersion": "17.12.4", "reachabilityStatus": "Reachable", "role": "DISTRIBUTION",
     "id": "3f0c1e9a-1111-4a6b-9c1d-000000000003"}
  ],
  "version": "1.0"
}
```

(A real device record has about fifty fields, including `family`, `serialNumber`, `upTime`, `macAddress` and `collectionStatus`; this one is trimmed.)

What you can read straight off it: three switches; SW2 is unreachable from Catalyst Center; SW2 runs a different release from the others; DSW1 is in the distribution role; each device's `id` is the UUID you would use in `network-device/{id}` or in a template deployment. A script reads it the same way:

```python
devices = inventory["response"]          # inventory = resp.json()
print(len(devices), inventory["version"])
old = [d["hostname"] for d in devices if d["softwareVersion"] != "17.12.4"]
print(old)
print(devices[2]["role"], devices[-1]["managementIpAddress"])
```

```text
3 1.0
['SW2']
DISTRIBUTION 10.10.20.2
```

Other shapes you will meet:

| Request | `response` holds |
|---|---|
| `GET network-device/count` | A number: `{"response": 3, "version": "1.0"}` |
| `GET network-device/{id}` | One device object |
| `POST` of an asynchronous operation | `{"taskId": "...", "url": "..."}` |
| `GET task/{taskId}` | One task object |

An empty `response` array with **200** is not an error: the filter matched nothing (or the inventory is empty).

## Reading an asynchronous operation

```text
POST /dna/intent/api/v1/network-device-poller/cli/read-request
X-Auth-Token: example-token-not-real
Content-Type: application/json

{"name": "check-ospf", "commands": ["show ip ospf neighbor"],
 "deviceUuids": ["3f0c1e9a-1111-4a6b-9c1d-000000000003"]}

HTTP/1.1 202 Accepted

{
  "response": {
    "taskId": "8a2d61c4-7f0e-4c3b-9d55-0000000000aa",
    "url": "/dna/intent/api/v1/task/8a2d61c4-7f0e-4c3b-9d55-0000000000aa"
  },
  "version": "1.0"
}
```

The 202 says only that Command Runner accepted the job. The client then polls the task:

```text
GET /dna/intent/api/v1/task/8a2d61c4-7f0e-4c3b-9d55-0000000000aa

HTTP/1.1 200 OK

{
  "response": {
    "id": "8a2d61c4-7f0e-4c3b-9d55-0000000000aa",
    "serviceType": "Command Runner Service",
    "startTime": 1763890812345,
    "endTime": 1763890815012,
    "isError": false,
    "progress": "{\"fileId\":\"c1b2a3d4-0000-4e5f-8a9b-0000000000bb\"}",
    "version": 1763890815012
  },
  "version": "1.0"
}
```

| Field | How to read it |
|---|---|
| `isError` | `false`: the operation succeeded; `true`: it failed, and `failureReason` (and often `errorCode`) explain why |
| `endTime` | Present once the task has finished; absent while it is still running, so keep polling |
| `progress` | Human-readable progress text, or (as here) a small JSON document in a **string**, pointing at the result (Command Runner puts its output in a file you fetch next) |
| `startTime`, `endTime` | Epoch **milliseconds** (13 digits) |

A failed task still comes back with **200 OK** on the `GET task` call (the request for the task worked); the failure is in the body:

```text
{
  "response": {
    "serviceType": "Discovery Service",
    "isError": true,
    "progress": "Failed to create discovery",
    "failureReason": "Discovery name is duplicate",
    "errorCode": "Discovery name is duplicate",
    "startTime": 1763891000100,
    "endTime": 1763891000146,
    "id": "a8805e89-0000-4b00-a2b6-000000000001"
  },
  "version": "1.0"
}
```

That is Cisco's own documented example: the `POST /discovery` returned 202, and only the task shows the failure.

> **Watch out:** Two layers of success. The HTTP status tells you whether **the request** was handled; `isError` tells you whether **the operation** worked. A script that checks only `status_code == 202` will report a failed discovery or template deployment as a success.

## A checklist for any Catalyst Center reply

1. Status class: 2xx, 4xx or 5xx?
2. If 202: get `response.taskId`, poll `task/{taskId}` until `endTime` appears, then check `isError`.
3. If 200: is `response` a list, an object or a number? Count, filter, pick fields.
4. If 401: token missing or expired. If 403: role. If 404: path or id. If 400 or 415: body or headers. If 429 or 503: wait and retry.

## Lab it yourself

Use the DevNet Catalyst Center sandbox from any host OS, with curl, Postman or Python 3 and `requests` (Windows: `py`; macOS and Linux: `python3`).

1. `GET network-device`, `network-device/count` and `network-device/{id}` and note the type of `response` in each.
2. Send a GET without `X-Auth-Token`, then with a made-up token, and record the status codes.
3. Request `network-device/not-a-real-id` and a misspelled path; compare the codes and bodies.
4. In a sandbox where changes are allowed, run a Command Runner read request, poll the task until `endTime` appears, and follow the `fileId` in `progress` to the output.
5. Write a Python loop that polls a task every two seconds, stops when `endTime` is present, and prints `failureReason` if `isError` is true.

## Key takeaways

- 2xx success, 4xx your request, 5xx the server. 200 OK with data, 201 created, **202 accepted (asynchronous)**, 204 no body.
- 400 bad body or parameter, **401 no or expired token**, **403 role not allowed**, 404 wrong path or id, 405 wrong method, 409 conflict, 415 wrong `Content-Type`, 429 rate limited, 500 server failure, 503 unavailable.
- Intent API bodies wrap data in **`response`** (array, object or number) plus a **`version`** string.
- Asynchronous calls return `response.taskId` and `url`; poll `GET /dna/intent/api/v1/task/{taskId}`; finished when `endTime` appears; success only if `isError` is false; `failureReason` explains a failure.
- Times are epoch milliseconds; `progress` may be a JSON document inside a string.
