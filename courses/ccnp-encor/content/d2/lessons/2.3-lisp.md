## The problem LISP solves

In ordinary IP routing an address does two jobs at once: it says **who** a host is (its identity) and **where** it is attached (its location). Move the host, or give a site a second ISP, and its address either changes or has to be advertised from a new place, which is why the internet routing table keeps growing and why host mobility is hard.

The **Locator/ID Separation Protocol** (LISP; data plane RFC 9300, control plane RFC 9301) splits those jobs into two address spaces:

| Term | Meaning | Example |
|---|---|---|
| **EID** (Endpoint Identifier) | The address that identifies a host. It is what hosts use as source and destination, and it stays the same when the host moves | 10.1.1.10 in site A |
| **EID-prefix** | A block of EIDs owned by a site | 10.1.1.0/24 |
| **RLOC** (Routing Locator) | An address of a LISP router (an ETR) in the underlay, where an EID can be reached. One EID-prefix can map to several RLOCs (multihoming) | 203.0.113.1 |

The underlay core only routes RLOCs. EIDs are carried inside an encapsulation and looked up in a **mapping system**, much as DNS maps names to addresses. LISP is therefore a map-and-encapsulate protocol: look up the mapping, then tunnel to the RLOC.

## The roles

| Role | Job |
|---|---|
| **ITR** (Ingress Tunnel Router) | Receives packets from hosts in its site, looks up the destination EID, and **encapsulates** toward the destination RLOC. Keeps the results in a **map-cache** |
| **ETR** (Egress Tunnel Router) | Receives LISP packets from the core, **decapsulates** them and delivers to hosts. **Registers** its site's EID-prefixes with the map server and answers Map-Requests for them |
| **xTR** | A router doing both ITR and ETR, the normal case for a site edge router |
| **Map server (MS)** | Accepts **Map-Registers** from ETRs and holds the EID-to-RLOC registrations |
| **Map resolver (MR)** | Accepts **Map-Requests** from ITRs and resolves them through the mapping system; if the EID is not in any LISP site, it returns a **Negative Map-Reply** |
| **MS/MR** | Usually one device doing both jobs |
| **PITR** (Proxy ITR) | Acts as an ITR **for non-LISP sites**: attracts traffic from the non-LISP world toward LISP EIDs and encapsulates it |
| **PETR** (Proxy ETR) | Acts as an ETR **for LISP sites sending to non-LISP destinations**: ITRs encapsulate that traffic to the PETR, which decapsulates and forwards it natively |
| **PxTR** | One device doing both proxy roles |

> **Exam tip:** Remember the direction. The **PITR** is the way **in** to LISP sites from the non-LISP world; the **PETR** is the way **out** of LISP sites to it. The ITR always encapsulates; the ETR always decapsulates.

## Control plane: register, request, reply

LISP control messages use **UDP port 4342**.

1. **Map-Register**: each ETR periodically (RFC 9301 suggests every minute) sends a Map-Register to its map server listing its EID-prefixes and RLOCs, authenticated with a shared key. The map server can confirm with a **Map-Notify** if the ETR asks for one. Registrations that are not refreshed time out (three minutes in RFC 9301).
2. A host in site A sends a packet to 10.2.2.20. The ITR has no map-cache entry for it.
3. **Map-Request**: the ITR sends an encapsulated Map-Request to its **map resolver**.
4. The map resolver hands the request to the map server where 10.2.2.0/24 is registered, and the map server **forwards** it to the registered ETR (or answers itself if the ETR asked for **proxy Map-Reply**).
5. **Map-Reply**: the ETR for site B replies **directly to the ITR** with the EID-prefix, its RLOCs and their priority and weight.
6. The ITR caches the mapping (with a TTL) and encapsulates the traffic to the chosen RLOC.

While the first lookup is in progress the ITR drops or buffers the packets, so the first few packets of a new flow may be lost; that is normal pull-based behaviour.

The **priority and weight** in the mapping give LISP built-in ingress traffic engineering: the destination site, not the source, says which RLOC to use (lowest priority wins; equal priorities share load by weight). That is how a multihomed LISP site controls inbound traffic without BGP tricks.

## Data plane

The ITR adds an outer IP header (source = its RLOC, destination = the ETR's RLOC), a **UDP header with destination port 4341**, and an **8-byte LISP header**, then the original packet. Over IPv4 that is 20 + 8 + 8 = **36 bytes** of overhead (56 over IPv6), so the underlay MTU must allow for it. The LISP header can carry a 24-bit **Instance ID**, which keeps separate EID spaces (VRFs) apart in the same LISP deployment; this is how LISP supports multitenancy.

```text
[Outer IP: RLOC 203.0.113.1 -> 198.51.100.2][UDP dport 4341][LISP 8B][Inner IP: EID 10.1.1.10 -> 10.2.2.20][payload]
```

## Where you meet LISP

- **SD-Access**: the **control plane node** is a LISP map server/map resolver. Fabric edge nodes register endpoints (EIDs) as they connect, and look up destinations on demand. The SD-Access data plane, however, is **VXLAN** (with group policy), not the LISP data plane.
- **Host and VM mobility**: an endpoint keeps its EID when it moves; the new xTR registers it and the old mapping is updated.
- **Multihoming and IPv6 transition**: IPv6 EIDs can be carried over an IPv4 RLOC core and vice versa.

A minimal IOS XE xTR configuration looks roughly like this (exact syntax varies by release, and newer releases use the `instance-id` / `service ipv4` structure):

```text
router lisp
 instance-id 0
  service ipv4
   eid-table default
   database-mapping 10.1.1.0/24 203.0.113.1 priority 1 weight 100
   itr map-resolver 192.0.2.100
   itr
   etr map-server 192.0.2.100 key <LISP-SITE-KEY>
   etr
```

The map server side defines a `site` with its authentication key and the `eid-record` prefixes it accepts.

## Lab it yourself

In CML, GNS3 or EVE-NG (Windows, Linux or an Intel Mac; on an Apple silicon Mac use a remote x86 server or a Cisco DevNet sandbox) with four Catalyst 8000V or IOL-XE routers: xTR-A and xTR-B (each with a host LAN), MS/MR, and an underlay router connecting all three.

1. Route only the RLOC (underlay) addresses in the core with OSPF; do not advertise the host LANs anywhere.
2. Configure the MS/MR with a site for each xTR, then configure each xTR with its database mapping, map resolver and map server.
3. Ping from host A to host B: the first ping may lose a packet while the map-cache fills.
4. Verify with the LISP show commands on your release, for example `show lisp site` on the MS/MR (registrations) and the map-cache command on the ITR (`show ip lisp map-cache` on older releases, `show lisp instance-id 0 ipv4 map-cache` on newer). Capture on the underlay link to see UDP 4342 control and UDP 4341 data packets.

## Key takeaways

- LISP separates identity (EID) from location (RLOC); the core routes only RLOCs.
- ITR encapsulates, ETR decapsulates, an xTR does both; PITR brings non-LISP traffic in, PETR takes LISP traffic out.
- ETRs send Map-Registers to the map server; ITRs send Map-Requests to the map resolver; the ETR (or the map server as proxy) answers with a Map-Reply straight to the ITR.
- Control plane UDP 4342, data plane UDP 4341, 8-byte LISP header, 36 bytes overhead over IPv4.
- Priority and weight let the destination site steer inbound traffic; Instance IDs separate VRFs.
- SD-Access uses LISP as its control plane (the control plane node is the MS/MR) and VXLAN as its data plane.
