## Two meanings of "virtual switching"

On the ENCOR blueprint, virtual switching sits under device virtualization, so the main meaning is the **software switch inside a hypervisor host** that connects VMs. You should also recognise the switch-side meaning: **combining two physical Catalyst switches into one logical switch** (StackWise Virtual, and VSS before it). This lesson covers both, with the weight on the first.

## The hypervisor virtual switch

Every vNIC plugs into a port on a **virtual switch (vSwitch)** running in the hypervisor. The vSwitch has two kinds of ports:

- **Virtual ports** facing the VMs' vNICs.
- **Uplinks**: the host's physical NICs, which connect the vSwitch to the physical access or top-of-rack switch.

Traffic between two VMs on the same host and same VLAN is switched in memory and never touches the physical network, so a physical SPAN port or firewall never sees it. Traffic to anything else leaves through an uplink.

A vSwitch learns MAC addresses differently from a physical switch: the hypervisor already **knows** every vNIC's MAC because it assigned it, so the vSwitch does not need to flood to learn local addresses.

### Loop prevention without STP

A hypervisor vSwitch typically does **not run Spanning Tree** and does not send BPDUs. It avoids loops by design: a frame received on one uplink is never forwarded out another uplink, and the vSwitch is not a transit switch between physical ports. Multiple uplinks are used for redundancy and load sharing with **NIC teaming** policies (for example by originating virtual port, by source MAC, by IP hash with a static EtherChannel, or with LACP on a distributed switch).

> **Watch out:** The physical switch port facing a hypervisor host is an edge port. Configure it as a trunk with PortFast for trunks (`spanning-tree portfast trunk` on Catalyst IOS XE), and make the channel configuration match the teaming policy: IP-hash teaming needs a static EtherChannel (`channel-group N mode on`), and LACP teaming needs LACP on both sides. A mismatch causes MAC flapping and dropped traffic.

### VLANs on a virtual switch

VMs are grouped into **port groups** (VMware) or virtual network segments; each port group typically maps to a VLAN. VMware names three tagging models:

| Mode | Who tags | Physical switch port | Port group VLAN setting |
|---|---|---|---|
| External switch tagging (EST) | The physical switch | Access port | None (VLAN 0) |
| Virtual switch tagging (VST) | The vSwitch adds and removes 802.1Q tags | 802.1Q trunk | VLAN ID 1–4094 |
| Virtual guest tagging (VGT) | The guest OS tags its own frames | 802.1Q trunk | All VLANs (VLAN 4095 on a standard vSwitch, a VLAN trunk range on a distributed switch) |

VST is the common choice: one trunk carries all VLANs to the host and the vSwitch handles tagging.

## Common virtual switches

| Virtual switch | Where | Scope and features |
|---|---|---|
| VMware vSphere Standard Switch (vSS) | ESXi | Per host, configured on each host separately; basic VLANs, teaming, traffic shaping |
| VMware vSphere Distributed Switch (vDS) | ESXi with vCenter | One switch definition spanning many hosts, managed centrally; adds LACP, NetFlow/IPFIX, port mirroring, private VLANs, consistent policy for live migration |
| Hyper-V Virtual Switch | Hyper-V | External (bound to a physical NIC), internal (VMs and host only) or private (VMs only) |
| Linux bridge | KVM and other Linux hosts | Simple learning bridge in the kernel |
| Open vSwitch (OVS) | KVM, OpenStack, many SDN platforms | Open source multilayer switch: OpenFlow control, VXLAN and Geneve tunnels, port mirroring, NetFlow and sFlow |
| NFVIS internal bridges | Cisco NFVIS | Connect VNFs to each other (service chains) and to physical ports |

> **Exam tip:** "A single virtual switch configured once in vCenter and spanning all hosts in the cluster" is a **distributed** switch. "Configured per host" is a **standard** switch. "Open source, OpenFlow-capable, used by KVM and OpenStack" is **Open vSwitch**.

## Switch-side virtual switching: StackWise Virtual

**Cisco StackWise Virtual** (on Catalyst 9000 core and distribution models such as the 9500 and 9600) joins **two** physical switches into **one logical switch**:

- One **control plane** and one management IP: one switch is active, the other is hot standby with stateful switchover (SSO).
- Both switches **forward** traffic (data planes stay active on both).
- The two chassis connect over the **StackWise Virtual Link (SVL)**, an EtherChannel of high-speed ports carrying control traffic and data.
- A separate **dual-active detection (DAD)** link or method stops both switches becoming active if the SVL fails.
- Downstream access switches and servers connect with **multichassis EtherChannel (MEC)**: one port channel with members on both physical switches, so STP sees no loop and every link forwards.

Its predecessor on Catalyst 6500 and 4500 was the **Virtual Switching System (VSS)**. Nexus switches solve the same problem differently with **vPC**, which keeps two separate control planes.

> **Real world:** In a data centre the two meanings meet: VMs attach to a distributed vSwitch, whose host uplinks form an EtherChannel to a StackWise Virtual pair (or vPC pair) at the top of rack.

## Lab it yourself

Works on Windows, macOS or Linux with any type 2 hypervisor (VirtualBox, VMware Workstation or Fusion, UTM).

1. In the hypervisor's network settings, create a **host-only** or **internal** network. That is a virtual switch with no uplink.
2. Attach two Linux VMs to it, give them `10.20.0.11/24` and `10.20.0.12/24`, and ping between them. The traffic never leaves your computer.
3. Add a second adapter to one VM in **NAT** or **bridged** mode and compare: bridged puts the VM directly on your physical LAN through the host NIC (a vSwitch with an uplink).
4. Optional, in a Linux VM: `sudo apt install openvswitch-switch` (inside the VM), then `sudo ovs-vsctl add-br br0` and `sudo ovs-vsctl show`. Add an internal port with `sudo ovs-vsctl add-port br0 vlan10 tag=10 -- set interface vlan10 type=internal` to see VST-style tagging configured on the switch.
5. If you have CML, GNS3 or EVE-NG (Windows, Linux or an Intel Mac; on an Apple silicon Mac use a remote x86 server or a Cisco DevNet sandbox) with a Catalyst 9000v image, configure a trunk toward a Linux host and add `spanning-tree portfast trunk` on it, then check `show spanning-tree interface <if> portfast`.

## Key takeaways

- A hypervisor vSwitch connects vNICs to each other and, through uplinks, to the physical network; VM-to-VM traffic on one host never reaches the wire.
- Hypervisor vSwitches do not run STP; they never forward between uplinks, so the facing physical port is an edge trunk.
- Teaming policy must match the physical side: IP hash with a static EtherChannel, LACP with LACP.
- Standard vSwitch is per host; distributed vSwitch spans hosts under vCenter; Open vSwitch is the open-source, OpenFlow-capable option.
- VST (vSwitch tags, physical trunk) is the usual VLAN model.
- StackWise Virtual makes two Catalyst 9000 switches one logical switch with one control plane, an SVL, dual-active detection and MEC to neighbours.
