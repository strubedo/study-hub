## GRE in one paragraph

**Generic Routing Encapsulation** (RFC 2784, with the optional key and sequence-number fields from RFC 2890) wraps any network-layer packet in a new IP header plus a small GRE header. Over IPv4 the delivery header carries **IP protocol 47**; the basic GRE header is **4 bytes** (flags, version and a Protocol Type field, 0x0800 for an IPv4 payload). GRE adds no encryption, authentication or state, but it carries what plain IPsec tunnels historically could not: **multicast and routing protocol traffic** (OSPF, EIGRP, PIM), plus non-IP payloads. The tunnel is a point-to-point virtual interface you can route over like any link.

Topology used in this lesson:

```text
10.1.1.0/24 - R1 Gi0/0/0 203.0.113.1 ===== Internet ===== 198.51.100.2 Gi0/0/0 R2 - 10.2.2.0/24
                 Tunnel0 172.16.0.1/30 ................ 172.16.0.2/30 Tunnel0
```

## Configure a GRE tunnel

```text
R1(config)# interface Tunnel0
R1(config-if)# ip address 172.16.0.1 255.255.255.252
R1(config-if)# tunnel source GigabitEthernet0/0/0
R1(config-if)# tunnel destination 198.51.100.2
R1(config-if)# ip mtu 1400
R1(config-if)# ip tcp adjust-mss 1360
R1(config-if)# keepalive 10 3
R1(config)# ip route 10.2.2.0 255.255.255.0 Tunnel0
```

- `tunnel mode gre ip` is the **default** mode, so it does not appear in the running configuration.
- `tunnel source` can be an interface or an address; `tunnel destination` must be the far end's tunnel source. If either side's source and destination do not mirror each other, the far end drops the packets.
- The tunnel IP subnet (172.16.0.0/30) is the overlay; the 203.0.113.0 and 198.51.100.0 addresses are the underlay (transport).
- R2 mirrors this with source Gi0/0/0, destination 203.0.113.1 and 172.16.0.2/30. Instead of static routes you can run OSPF or EIGRP over Tunnel0.

### When is the tunnel up/up?

A GRE tunnel interface comes **up/up** as soon as it has a valid tunnel source (an interface that is up with an IP address) and a **route to the tunnel destination** that does not point through the tunnel itself. It does **not** check that the far end exists. Without keepalives, a tunnel can show up/up while the other router is powered off. `keepalive 10 3` (period in seconds, retries) makes the router send GRE keepalives and take the line protocol down after the retries are missed. A keepalive is a GRE packet with a reply already built inside it: the far end decapsulates it and routes the inner packet straight back, so it tests the round trip and the far end does not need keepalives configured. Each side decides only its own line-protocol state, so configure it on both.

### Verify

```text
R1# show interfaces Tunnel0
Tunnel0 is up, line protocol is up
  Hardware is Tunnel
  Internet address is 172.16.0.1/30
  MTU 9976 bytes, BW 100 Kbit/sec, DLY 50000 usec,
     reliability 255/255, txload 1/255, rxload 1/255
  Encapsulation TUNNEL, loopback not set
  Keepalive set (10 sec), retries 3
  Tunnel linestate evaluation up
  Tunnel source 203.0.113.1 (GigabitEthernet0/0/0), destination 198.51.100.2
  Tunnel protocol/transport GRE/IP
    Key disabled, sequencing disabled
    Checksumming of packets disabled
  Tunnel TTL 255, Fast tunneling enabled
  Tunnel transport MTU 1476 bytes
<output omitted>
```

Read it top to bottom: status, the overlay address, the source and destination, the mode (`GRE/IP`), and the **transport MTU 1476** (1500 minus 24 bytes of GRE and outer IP). The large interface `MTU` value is a platform-dependent tunnel maximum, not what IP uses; `show ip interface Tunnel0` shows the IP MTU. If the line protocol is down, the `Tunnel linestate evaluation down` line gives the reason, such as `no output interface` (no route to the destination). Also use `show ip interface brief`, `show ip route` and `ping 172.16.0.2`.

## Recursive routing

**Recursive routing** happens when the router learns the route to the **tunnel destination through the tunnel itself**. Typical cause: you run OSPF over Tunnel0 and also advertise the underlay (the 198.51.100.0 subnet) into it, so the best path to 198.51.100.2 becomes "via Tunnel0". To send a GRE packet the router must route the outer header to the destination, which points into the tunnel, which needs another outer header: a loop. IOS detects it and shuts the tunnel for a while:

```text
%TUN-5-RECURDOWN: Tunnel0 temporarily disabled due to recursive routing
```

The tunnel then flaps: it goes down, the overlay route disappears, the underlay route returns, the tunnel comes up, the routing protocol relearns the bad route, and the cycle repeats.

Fixes (any one that keeps the destination reachable via the underlay):

- Do not advertise underlay prefixes into the overlay routing process (tighten `network` statements, use passive or `ip ospf` per interface).
- A more specific static route to the tunnel destination via the physical next hop, or filtering with a distribute list.
- Put the underlay in a separate VRF (**front-door VRF**: `tunnel vrf INET` on the tunnel, with the physical interface in VRF INET), so the overlay can never influence the transport table.

> **Exam tip:** The symptom pair "tunnel flaps every minute or so" plus `RECURDOWN` in the log is recursive routing. The fix is about the route to the **tunnel destination**, not the tunnel's own IP address.

## MTU and TCP MSS

Every encapsulation steals bytes from a 1500-byte underlay MTU:

| Encapsulation | Overhead | Inner IP MTU | TCP MSS (MTU − 40) |
|---|---|---|---|
| GRE over IPv4 | 20 (IP) + 4 (GRE) = 24 | 1476 | 1436 |
| GRE with key | 28 | 1472 | 1432 |
| GRE over IPsec, or an IPsec VTI | Varies with the transform and mode (ESP header, IV, padding, ICV, outer IP) | Commonly set to 1400 | 1360 |

- `ip mtu` sets the largest packet the tunnel accepts before fragmenting (or before dropping and sending ICMP "fragmentation needed" when DF is set).
- `ip tcp adjust-mss` rewrites the MSS in TCP SYNs passing through the interface so hosts never send segments too big for the tunnel. This fixes the classic "ping works, small web pages load, large transfers hang" problem when PMTUD's ICMP messages are filtered.
- `tunnel path-mtu-discovery` lets the tunnel itself track the underlay path MTU.

> **Watch out:** Pinging the far end with default 100-byte packets proves nothing about MTU. Test with `ping 10.2.2.1 size 1400 df-bit` and step the size up.

## IPsec essentials

IPsec (architecture in RFC 4301) protects IP traffic with:

- **ESP** (Encapsulating Security Payload, RFC 4303, **IP protocol 50**): confidentiality, integrity and anti-replay. This is what site-to-site VPNs use.
- **AH** (Authentication Header, IP protocol 51): integrity only; it covers the outer IP header, so it breaks through NAT. Rarely used.
- **Tunnel mode** adds a new outer IP header (the whole original packet is encrypted); **transport mode** keeps the original IP header and protects the payload. GRE over IPsec usually uses transport mode because GRE already supplies an outer header, saving 20 bytes.

**IKEv2** (RFC 7296) negotiates keys and security associations over **UDP 500**, moving to **UDP 4500** when NAT is detected (NAT traversal also wraps ESP in UDP 4500). A normal setup takes **four messages**: `IKE_SA_INIT` (proposals, Diffie-Hellman values, nonces) and `IKE_AUTH` (identities, authentication and the first Child SA, which is the IPsec SA pair). Later `CREATE_CHILD_SA` exchanges add or rekey SAs, and `INFORMATIONAL` exchanges carry deletes and dead-peer checks.

## IKEv2 building blocks on IOS XE

```text
crypto ikev2 proposal IKEV2-PROP
 encryption aes-cbc-256
 integrity sha256
 group 19
crypto ikev2 policy IKEV2-POL
 proposal IKEV2-PROP
crypto ikev2 keyring IKEV2-KR
 peer R2
  address 198.51.100.2
  pre-shared-key <PRE-SHARED-KEY>
crypto ikev2 profile IKEV2-PROF
 match identity remote address 198.51.100.2 255.255.255.255
 authentication remote pre-share
 authentication local pre-share
 keyring local IKEV2-KR
crypto ipsec transform-set TS esp-aes 256 esp-sha256-hmac
 mode tunnel
```

| Block | Holds |
|---|---|
| Proposal | IKE SA algorithms: encryption, integrity (or PRF with GCM), DH group |
| Policy | Which proposals to use (optionally per local address or front-door VRF) |
| Keyring | Pre-shared keys per peer |
| Profile | Peer identity match, authentication methods, keyring: the glue |
| Transform set | IPsec (Child SA) algorithms and mode |

IOS XE also has IKEv2 "smart defaults" (a built-in proposal, policy and transform set), but explicit configuration is clearer and is what exam exhibits show. The keys and both sides' authentication methods must match, and the proposals must share at least one algorithm set.

## Option 1: crypto map (policy-based)

A crypto ACL defines the "interesting" traffic; the map is applied to the **physical** outside interface.

```text
ip access-list extended VPN-TRAFFIC
 permit ip 10.1.1.0 0.0.0.255 10.2.2.0 0.0.0.255
crypto map CMAP 10 ipsec-isakmp
 set peer 198.51.100.2
 set transform-set TS
 set ikev2-profile IKEV2-PROF
 match address VPN-TRAFFIC
interface GigabitEthernet0/0/0
 crypto map CMAP
```

The peer's ACL must be the mirror image (10.2.2.0 to 10.1.1.0). No tunnel interface exists, so you cannot run a routing protocol over it, and every new subnet means editing ACLs on both sides.

## Option 2: VTI with tunnel protection (route-based)

A **static virtual tunnel interface** puts IPsec directly on a tunnel interface. Anything routed into the tunnel is encrypted; there is no crypto ACL (the proxy identities are any-to-any).

```text
crypto ipsec profile IPSEC-PROF
 set transform-set TS
 set ikev2-profile IKEV2-PROF
interface Tunnel1
 ip address 172.16.1.1 255.255.255.252
 tunnel source GigabitEthernet0/0/0
 tunnel destination 198.51.100.2
 tunnel mode ipsec ipv4
 tunnel protection ipsec profile IPSEC-PROF
```

## Option 3: GRE over IPsec

Identical, but leave the tunnel in GRE mode (the default) so it can carry multicast and non-IP traffic, and use **transport mode** in the transform set:

```text
crypto ipsec transform-set TS-TRANSPORT esp-aes 256 esp-sha256-hmac
 mode transport
crypto ipsec profile GRE-PROF
 set transform-set TS-TRANSPORT
 set ikev2-profile IKEV2-PROF
interface Tunnel0
 tunnel protection ipsec profile GRE-PROF
```

| | Crypto map | VTI (`tunnel mode ipsec ipv4`) | GRE over IPsec |
|---|---|---|---|
| Traffic selection | Crypto ACL | Routing into the tunnel | Routing into the tunnel |
| Routing protocols over it | No | Yes (IP unicast and multicast for IPv4) | Yes |
| Non-IP payloads | No | No | Yes |
| Overhead | ESP tunnel mode (new IP header + ESP) | Same as a crypto map | ESP + 4-byte GRE header in transport mode (4 bytes more than a VTI); 24 more in tunnel mode |
| Applied to | Physical interface | Tunnel interface | Tunnel interface |

## Verify IPsec

```text
R1# show crypto ikev2 sa
 IPv4 Crypto IKEv2  SA

Tunnel-id Local                 Remote                fvrf/ivrf            Status
1         203.0.113.1/500       198.51.100.2/500      none/none            READY
      Encr: AES-CBC, keysize: 256, PRF: SHA256, Hash: SHA256, DH Grp:19, Auth sign: PSK, Auth verify: PSK
      Life/Active Time: 86400/417 sec
```

`READY` means the IKE SA is established. Then check that traffic is actually encrypted:

```text
R1# show crypto ipsec sa
interface: Tunnel0
    Crypto map tag: Tunnel0-head-0, local addr 203.0.113.1

   protected vrf: (none)
   local  ident (addr/mask/prot/port): (203.0.113.1/255.255.255.255/47/0)
   remote ident (addr/mask/prot/port): (198.51.100.2/255.255.255.255/47/0)
   current_peer 198.51.100.2 port 500
     PERMIT, flags={origin_is_acl,}
    #pkts encaps: 1520, #pkts encrypt: 1520, #pkts digest: 1520
    #pkts decaps: 1498, #pkts decrypt: 1498, #pkts verify: 1498
<output omitted>
```

Protocol **47** in the identities shows GRE over IPsec; a VTI shows 0.0.0.0/0.0.0.0 any-to-any; a crypto map shows the ACL's subnets. Encaps rising while decaps stay at zero points at the far side or the return path. `show crypto session` gives a one-line UP-ACTIVE or DOWN summary per peer, and `debug crypto ikev2` shows negotiation failures (proposal mismatch, authentication failure).

## Lab it yourself

In CML, GNS3 or EVE-NG (Windows, Linux or an Intel Mac; on an Apple silicon Mac use a remote x86 server or a Cisco DevNet sandbox), build three IOS XE routers (Catalyst 8000V or IOL-XE): R1 and R2 as sites, ISP in the middle with 203.0.113.0/30 and 198.51.100.0/30, and a loopback or host LAN behind each site.

1. Build the GRE tunnel above, add OSPF over Tunnel0 for the LANs only. Check `show interfaces Tunnel0`, `show ip ospf neighbor`, `ping 10.2.2.1 source 10.1.1.1`.
2. Break it: add the underlay subnet to OSPF so the route to the tunnel destination points into Tunnel0. Watch for `%TUN-5-RECURDOWN`, then fix it.
3. Add the IKEv2 blocks with `<PRE-SHARED-KEY>` replaced by a lab-only string, apply `tunnel protection ipsec profile GRE-PROF` on both sides, and verify with `show crypto ikev2 sa`, `show crypto ipsec sa` and `show crypto session`.
4. Shut down Tunnel0 on both routers, build Tunnel1 as in Option 2 (a new /30, `tunnel mode ipsec ipv4`, `IPSEC-PROF` with the tunnel-mode transform set `TS`) and move OSPF onto it. Compare the proxy identities in `show crypto ipsec sa` (0.0.0.0/0.0.0.0 instead of protocol 47).
5. Test MTU with `ping 10.2.2.1 source 10.1.1.1 size 1472 df-bit` and with smaller sizes.

## Key takeaways

- GRE is IP protocol 47 with a 4-byte header (RFC 2784/2890); it carries multicast and routing protocols but does not encrypt.
- `tunnel mode gre ip` is the default; the tunnel is up/up with a valid source and a route to the destination, so use keepalives to detect a dead far end.
- Recursive routing (route to the tunnel destination via the tunnel) causes `%TUN-5-RECURDOWN` and flapping; fix the underlay route.
- GRE leaves 1476 bytes (MSS 1436); with IPsec use about `ip mtu 1400` and `ip tcp adjust-mss 1360`.
- IKEv2: UDP 500/4500, IKE_SA_INIT plus IKE_AUTH (four messages) build the IKE SA and first Child SA. ESP is IP protocol 50.
- IOS XE IKEv2 blocks: proposal, policy, keyring, profile, then transform set; apply with a crypto map (ACL, physical interface) or an IPsec profile with `tunnel protection` (VTI or GRE over IPsec).
- Verify with `show crypto ikev2 sa` (READY), `show crypto ipsec sa` (encaps and decaps counters) and `show crypto session`.
