## What a VRF is

A **Virtual Routing and Forwarding (VRF)** instance is a separate routing table, with its own forwarding (CEF) table, inside one router or Layer 3 switch. Each routed interface belongs to exactly one VRF, or to the **global** table (the default). Packets that arrive on an interface are routed only with that interface's VRF table, so:

- Two VRFs can use **overlapping addresses** (both customers can have 10.1.1.0/24).
- Traffic **cannot cross** from one VRF to another unless you deliberately leak routes.
- Routing protocols run **per VRF**: an OSPF process or BGP address family is bound to one VRF.

It is the Layer 3 equivalent of a VLAN. Typical uses: separating guest, corporate and IoT traffic on a campus core; keeping a management network apart (IOS XE platforms ship with a management VRF, `Mgmt-vrf` on Catalyst 9000 switches and `Mgmt-intf` on the Catalyst 8000 and ISR routers); and isolating customers on a shared WAN edge.

**VRF-Lite** means VRFs **without MPLS**. Every router in the path carries the VRF, and each pair of routers needs a separate link per VRF, usually 802.1Q subinterfaces or SVIs on one physical link, with a routing adjacency per VRF on each. That is simple for a few VRFs and a few hops but grows quickly. **MPLS Layer 3 VPN** solves the scaling problem by carrying all VRFs across one core with MP-BGP (VPNv4 routes, route distinguishers and route targets) and labels; that is beyond this lesson, but you should know the difference.

| | VRF-Lite | MPLS L3VPN |
|---|---|---|
| Core transport | Per-VRF links (subinterfaces, SVIs) hop by hop | One shared MPLS core |
| Routing between devices | One IGP or BGP session per VRF per link | MP-BGP VPNv4/VPNv6 between PEs, one IGP in the core |
| Route distinguisher needed | No (optional) | Yes: makes overlapping prefixes unique in VPNv4 |
| Route targets | Not used unless you leak with BGP | Control import and export between VRFs |
| Scales to | A handful of VRFs and hops | Many VRFs and sites |

## Creating a VRF

IOS XE uses the **multiprotocol** syntax `vrf definition`. The older IPv4-only `ip vrf` command still exists on many releases, but new configurations should use `vrf definition`, and the two cannot have the same VRF name.

```text
R1(config)# vrf definition CUST-A
R1(config-vrf)# description Customer A
R1(config-vrf)# rd 65000:1
R1(config-vrf)# address-family ipv4
R1(config-vrf-af)# exit-address-family
R1(config-vrf)# address-family ipv6
R1(config-vrf-af)# exit-address-family
R1(config-vrf)# exit
```

- The **address-family** lines are what enable IPv4 and IPv6 routing in the VRF. A VRF with no `address-family ipv4` does not route IPv4, and `show vrf` lists no protocol for it.
- The **RD** (route distinguisher) is only meaningful when the VRF's routes go into MP-BGP. For pure VRF-Lite it is optional; many engineers set one anyway so the VRF is ready for BGP later.

## Putting interfaces into the VRF

```text
R1(config)# interface GigabitEthernet0/0/1
R1(config-if)# vrf forwarding CUST-A
% Interface GigabitEthernet0/0/1 IPv4 disabled and address(es) removed due to enabling VRF CUST-A
R1(config-if)# ip address 10.1.1.1 255.255.255.0
```

> **Watch out:** `vrf forwarding` **removes** any IPv4 and IPv6 addresses already on the interface. Always enter `vrf forwarding` first and the address second. When you paste a configuration in the wrong order the interface ends up with no address, and the one-line warning is easy to miss as the paste scrolls past. With the older syntax the command is `ip vrf forwarding NAME`.

On a Catalyst 9000 switch the Layer 3 interfaces are SVIs or routed ports (`no switchport`); a Layer 2 access or trunk port cannot be in a VRF, and `ip routing` must be enabled. Tunnel, loopback and subinterfaces all accept `vrf forwarding` the same way.

For VRF-Lite between two devices, one physical link usually carries all VRFs on subinterfaces:

```text
R1(config)# interface GigabitEthernet0/0/2.10
R1(config-subif)# encapsulation dot1Q 10
R1(config-subif)# vrf forwarding CUST-A
R1(config-subif)# ip address 172.16.10.1 255.255.255.252
R1(config)# interface GigabitEthernet0/0/2.20
R1(config-subif)# encapsulation dot1Q 20
R1(config-subif)# vrf forwarding CUST-B
R1(config-subif)# ip address 172.16.20.1 255.255.255.252
```

## Routing inside a VRF

Every routing source must name the VRF, or it lands in the global table.

| Source | Per-VRF syntax |
|---|---|
| Static route | `ip route vrf CUST-A 0.0.0.0 0.0.0.0 172.16.10.2` |
| OSPFv2 | `router ospf 10 vrf CUST-A` (one process per VRF), then `network` statements or `ip ospf 10 area 0` on the interface |
| EIGRP named mode | `router eigrp CORE` then `address-family ipv4 unicast vrf CUST-A autonomous-system 100` |
| EIGRP classic | `router eigrp 100` then `address-family ipv4 vrf CUST-A autonomous-system 100` |
| BGP | `router bgp 65000` then `address-family ipv4 vrf CUST-A`, with `neighbor ... remote-as` and `activate` inside it |

```text
R1(config)# router ospf 10 vrf CUST-A
R1(config-router)# router-id 10.255.0.1
R1(config-router)# network 10.1.1.0 0.0.0.255 area 0
R1(config-router)# network 172.16.10.0 0.0.0.3 area 0
R1(config)# router ospf 20 vrf CUST-B
R1(config-router)# router-id 10.255.0.1
R1(config-router)# network 10.1.1.0 0.0.0.255 area 0
R1(config-router)# network 172.16.20.0 0.0.0.3 area 0
```

Both processes can use the same router ID and both advertise 10.1.1.0/24, because each lives in its own table. A `network` statement in `router ospf 10 vrf CUST-A` only matches interfaces in CUST-A.

> **Exam tip:** An OSPF `network` statement that "should" match an interface but does not is often a VRF mismatch: the interface is in one VRF and the process in another (or in global). The interface simply never joins the process.

## Verifying

```text
R1# show vrf
Name                             Default RD            Protocols   Interfaces
CUST-A                           65000:1               ipv4,ipv6   Gi0/0/1
                                                                   Gi0/0/2.10
CUST-B                           <not set>             ipv4        Gi0/0/3
                                                                   Gi0/0/2.20
Mgmt-intf                        <not set>             ipv4,ipv6   Gi0
```

`show vrf` gives the one-glance view: name, RD, address families and member interfaces. `show vrf detail CUST-A` adds the table IDs, route targets and import or export maps. `show ip vrf interfaces` lists each IPv4 interface with its address, VRF and status.

```text
R1# show ip route vrf CUST-A

Routing Table: CUST-A
Codes: L - local, C - connected, S - static, R - RIP, M - mobile, B - BGP
       D - EIGRP, EX - EIGRP external, O - OSPF, IA - OSPF inter area
<legend lines omitted>

Gateway of last resort is not set

      10.0.0.0/8 is variably subnetted, 3 subnets, 2 masks
C        10.1.1.0/24 is directly connected, GigabitEthernet0/0/1
L        10.1.1.1/32 is directly connected, GigabitEthernet0/0/1
O        10.2.2.0/24 [110/2] via 172.16.10.2, 00:12:41, GigabitEthernet0/0/2.10
      172.16.0.0/16 is variably subnetted, 2 subnets, 2 masks
C        172.16.10.0/30 is directly connected, GigabitEthernet0/0/2.10
L        172.16.10.1/32 is directly connected, GigabitEthernet0/0/2.10
```

Plain `show ip route` shows only the **global** table; none of these routes appear there. Other useful VRF-aware commands: `show ip protocols vrf CUST-A`, `show ip arp vrf CUST-A`, `show ip cef vrf CUST-A`, `show ip bgp vpnv4 vrf CUST-A` (with BGP), and `show running-config vrf CUST-A`, which prints the VRF definition plus every interface and routing process in it.

Testing must also name the VRF:

```text
R1# ping 10.2.2.1
.....
Success rate is 0 percent (0/5)
R1# ping vrf CUST-A 10.2.2.1
!!!!!
Success rate is 100 percent (5/5), round-trip min/avg/max = 1/1/2 ms
R1# traceroute vrf CUST-A 10.2.2.1
```

The first ping fails because it looks up 10.2.2.1 in the global table, which has no route. This is the most common "VRF is broken" false alarm. The same rule applies to management traffic: `copy tftp:` or `ssh` from the router use the global table unless told otherwise (for example `ip tftp source-interface` in the management VRF or `ssh -vrf Mgmt-intf`).

## Leaking routes between VRFs

Strict isolation is the point, but shared services (DNS, internet) often sit in another VRF or in the global table. Options:

- **Static leak**: a static route in one table pointing at an interface or next hop in another. For example `ip route vrf CUST-A 0.0.0.0 0.0.0.0 203.0.113.1 global` sends CUST-A's default route to a next hop resolved in the global table; the return path needs a matching global route back to the VRF's prefixes (for example via a route pointing out the VRF interface).
- **MP-BGP route targets**: export a route target from one VRF and import it in another; with VRF-Lite this needs BGP running locally even without MPLS.
- **VRF-aware NAT** or a firewall between VRFs, which is the usual design for internet access.

> **Real world:** Leaking routes is where VRF designs break isolation by accident. Prefer a firewall between VRFs over broad route-target imports, and document every leak.

## Lab it yourself

In CML, GNS3 or EVE-NG (Windows, Linux or an Intel Mac; on an Apple silicon Mac use a remote x86 server or a Cisco DevNet sandbox), build two IOS XE routers (Catalyst 8000V or IOL-XE) and four small Linux or IOSv hosts.

1. Topology: `HostA1 - Gi2 R1 Gi4.10/.20 === Gi4.10/.20 R2 Gi2 - HostA2`, and `HostB1 - Gi3 R1` / `R2 Gi3 - HostB2`.
2. On both routers create `vrf definition CUST-A` and `CUST-B` with `address-family ipv4`.
3. Give **both** customers the same LANs: 10.1.1.0/24 behind R1 and 10.2.2.0/24 behind R2. Use subinterfaces .10 (CUST-A, 172.16.10.0/30) and .20 (CUST-B, 172.16.20.0/30) on the R1-R2 link. Enter `vrf forwarding` before `ip address` and note the warning if you get the order wrong.
4. Run `router ospf 10 vrf CUST-A` and `router ospf 20 vrf CUST-B` on both routers.
5. Prove it: `show vrf`, `show ip route vrf CUST-A`, `show ip route vrf CUST-B` (same prefixes, different next hops), `show ip route` (empty of customer routes), `ping 10.2.2.1` (fails), `ping vrf CUST-A 10.2.2.1` (succeeds).
6. Stretch: add a static leak so CUST-A reaches a loopback in the global table, and confirm CUST-B still cannot.

## Key takeaways

- A VRF is a separate routing and CEF table; interfaces belong to one VRF or the global table; overlapping addresses are allowed.
- IOS XE syntax: `vrf definition NAME`, `address-family ipv4` / `ipv6`, then `vrf forwarding NAME` on the interface.
- `vrf forwarding` removes the interface's IP addresses: configure it before `ip address`.
- Every routing source names the VRF: `ip route vrf`, `router ospf N vrf`, EIGRP and BGP `address-family ... vrf`.
- Verify with `show vrf`, `show ip route vrf NAME`, `ping vrf NAME` and `traceroute vrf NAME`; plain `ping` and `show ip route` use the global table.
- VRF-Lite needs a per-VRF link and adjacency hop by hop; MPLS L3VPN scales by carrying VRFs in MP-BGP. RDs matter only when routes enter BGP.
- Leak between VRFs deliberately (static with `global`, route targets, NAT or a firewall).
