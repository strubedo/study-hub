## A computer made of files

A **virtual machine** is a complete computer emulated in software: virtual CPU, memory, disks, network adapters and firmware (BIOS or UEFI). The guest operating system boots and runs as if it owned real hardware; it does not need to know it is virtualized. On disk, a VM is just a handful of files: a configuration file describing the virtual hardware, one or more virtual disk files, and saved state such as snapshots. That is what makes VMs easy to copy, back up and move.

## The virtual hardware

| Component | What it is | Notes |
|---|---|---|
| **vCPU** | A share of a physical core or hyperthread scheduled by the hypervisor | You can assign more vCPUs in total than the host has cores (overcommit); too much causes CPU-ready waiting |
| **Virtual memory (vRAM)** | Host RAM mapped into the guest | Hypervisors can overcommit with ballooning, page sharing or swapping, at a performance cost |
| **Virtual disk** | A file or LUN that appears as a disk | VMDK (VMware), VHDX (Hyper-V), qcow2 or raw (KVM); thick or thin provisioned |
| **vNIC** | A virtual network adapter with its own MAC address | Emulated (e1000, which almost every OS has a built-in driver for) or paravirtual (VMware vmxnet3, KVM virtio, Hyper-V synthetic), which is faster but needs a driver |
| **Firmware and devices** | BIOS or UEFI, virtual TPM, USB, serial console | Virtual routers usually expose a serial console you can reach through the hypervisor |

Every vNIC connects to a **virtual switch** port inside the host, which is the subject of the next lesson. From the network's point of view, each VM is simply another host with its own MAC and IP address behind the server's physical NIC.

## Lifecycle operations

| Operation | What it does | Network-engineer use |
|---|---|---|
| **Template** | A master image used to deploy identical VMs | Golden Catalyst 8000V or Linux jump-host images |
| **Clone** | A copy of a VM (full or linked) | Duplicate a lab router; clones need new MAC addresses and hostnames |
| **Snapshot** | Captures disk (and optionally memory) state at a point in time | Roll back before a risky upgrade in a lab. Not a backup: it lives on the same storage and grows over time |
| **Live migration** (vMotion, Hyper-V Live Migration, KVM live migration) | Moves a running VM to another host with no reboot | The VM keeps its IP and MAC, so its VLAN or segment must exist on both hosts: a classic reason for stretched Layer 2 or a VXLAN overlay |
| **High availability** | Restarts VMs on a surviving host after a host failure | A restart, not a hitless failover |

> **Exam tip:** Live migration keeps the VM's MAC and IP address. That requirement, "the same Layer 2 segment on the source and destination host", is the link between server virtualization and overlay technologies such as VXLAN later in this domain.

## VMs versus containers

A **container** packages an application and its libraries but shares the host's operating-system kernel. There is no guest OS to boot.

| | Virtual machine | Container |
|---|---|---|
| Isolation boundary | Hypervisor; each VM has its own kernel | Namespaces and cgroups on a shared kernel |
| Contents | Full guest OS plus applications | Application plus its dependencies |
| Size and start time | Gigabytes; boots in tens of seconds or minutes | Megabytes; starts in seconds or less |
| OS flexibility | Any OS the hypervisor supports (Linux guest on Windows host, and so on) | Must match the host kernel (Linux containers need a Linux kernel) |
| Typical Cisco example | Catalyst 8000V, ASAv, FTDv, SD-WAN controllers | IOx application hosting on Catalyst 9000 and IOS XE routers (for example the ThousandEyes agent) |

Containers and VMs are complementary: Kubernetes clusters usually run on VMs.

## Network functions virtualization

**NFV** replaces dedicated appliances (router, firewall, WAN optimizer, load balancer) with software **virtual network functions (VNFs)** running as VMs on standard x86 servers. The ETSI NFV architecture splits it into the NFV infrastructure (hardware plus hypervisor), the VNFs, and management and orchestration (MANO). Cisco's branch example is an NFVIS platform hosting a Catalyst 8000V, a firewall VNF and a WAN optimizer, chained together through internal virtual switches. Benefits: fewer boxes to ship, faster deployment, the ability to resize a function by giving it more vCPUs. Costs: performance depends on the server, and troubleshooting now includes the hypervisor and its virtual switching.

> **Watch out:** A VNF's throughput is bounded by its vCPUs, vNIC type and the host's packet path. A virtual router given emulated e1000 vNICs and one vCPU will not forward anywhere near what the same software does with paravirtual or SR-IOV interfaces and dedicated cores.

**SR-IOV** (single-root I/O virtualization) is worth knowing by name: a physical NIC presents several "virtual functions" that are passed directly into VMs, bypassing the hypervisor's virtual switch for near line-rate performance, at the cost of features such as live migration on many platforms.

## Lab it yourself

On any type 2 hypervisor from the previous lesson (VirtualBox, VMware Workstation or Fusion, UTM or Parallels):

1. Build one Linux VM, install it, then **convert it to a template** or simply keep it powered off as a master.
2. **Clone** it twice. Boot both clones and run `ip link` in each: confirm that the hypervisor gave each clone a different MAC address (choose the option to generate new MACs when cloning). Change their hostnames.
3. Take a **snapshot** of one clone, delete a file or install a package, then revert to the snapshot and confirm the change is gone.
4. Compare vNIC types: in the VM settings, look at the adapter model choices (for example Intel PRO/1000 versus a paravirtual virtio or vmxnet3 adapter) and check which driver the guest loaded with `ethtool -i <interface>`.
5. Optional: install Docker or Podman inside one clone and start a container (`docker run --rm -it alpine sh`). Run `uname -r` in the container and on the VM: the kernel version is the same, because containers share the host kernel.

## Key takeaways

- A VM is software hardware: vCPU, vRAM, virtual disk, vNIC and firmware, stored as files on the host.
- Paravirtual vNICs (vmxnet3, virtio) outperform emulated ones (e1000) but need guest drivers.
- Snapshots are point-in-time rollback, not backups. Templates and clones speed up deployment.
- Live migration keeps the VM's MAC and IP, so its segment must exist on both hosts.
- Containers share the host kernel; VMs each run their own kernel. IOx on Catalyst 9000 hosts containers.
- NFV runs network functions (routers, firewalls) as VNFs on standard servers; SR-IOV bypasses the virtual switch for speed.
