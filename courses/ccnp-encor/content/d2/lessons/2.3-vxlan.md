## Why VXLAN

Data centres and campus fabrics want two things that classic VLANs struggle to give: **more than 4094 segments**, and **Layer 2 segments stretched across a routed (Layer 3) underlay** so a VM can live-migrate or a user can roam without the network running Spanning Tree across the whole site. **Virtual Extensible LAN** (VXLAN, RFC 7348) does both by carrying Ethernet frames inside UDP/IP packets.

## The header and the VNI

A VXLAN packet is an ordinary IP/UDP packet whose payload is a complete Ethernet frame:

```text
[Outer Ethernet 14B][Outer IP 20B][Outer UDP 8B][VXLAN 8B][Inner Ethernet frame: dst MAC, src MAC, (802.1Q), type, payload]
```

| Field | Value |
|---|---|
| Outer UDP destination port | **4789** (IANA-assigned; some early implementations used other ports, so it is configurable) |
| Outer UDP source port | A hash of the inner frame's headers, recommended in 49152–65535, so ECMP in the underlay spreads different flows over different paths |
| VXLAN header | **8 bytes**: 8 bits of flags (the **I flag** must be 1 for a valid VNI), reserved bits, a **24-bit VNI**, and 8 reserved bits |
| VNI (VXLAN Network Identifier) | Identifies the segment, like a VLAN ID: 2^24 = about **16 million** segments versus 4094 VLANs |
| Outer IP addresses | Source and destination **VTEPs** (or a multicast group for flooded traffic) |

The UDP checksum is normally sent as zero, and the inner frame carries no FCS of its own.

### Overhead and MTU

Counting the headers added around the original frame: outer Ethernet 14 + outer IPv4 20 + UDP 8 + VXLAN 8 = **50 bytes** (54 if the outer frame has an 802.1Q tag; with an IPv6 underlay the outer IP header is 40 bytes, so 70).

For the underlay **IP MTU** the sum is: inner IP packet 1500 + inner Ethernet header 14 + VXLAN 8 + UDP 8 + outer IP 20 = **1550 bytes**. RFC 7348 says VTEPs must not fragment VXLAN packets and receivers may discard fragments, so the underlay must be configured larger. In practice fabrics use jumbo frames (for example 9100 or 9216 bytes on the physical interfaces) and stop worrying.

> **Exam tip:** "50 bytes" and "UDP 4789" are the two VXLAN numbers to know cold; "24-bit VNI, about 16 million segments" is the third.

## VTEPs

A **VXLAN Tunnel Endpoint (VTEP)** encapsulates and decapsulates. It can be a hypervisor (Open vSwitch, VMware NSX), a top-of-rack or campus switch (Catalyst 9000 and Nexus support VXLAN with BGP EVPN), or a router. On Cisco switches the VTEP is the **NVE** (network virtualization edge) interface, `interface nve1`, which takes its source address from a loopback. Each VTEP maps local VLANs to VNIs and keeps a table of remote MAC address to remote VTEP IP.

Underlay and overlay are separate: the **underlay** is a plain routed IP network (OSPF or IS-IS between leaf and spine, ECMP everywhere) that only needs to reach the VTEP loopbacks; the **overlay** is the set of VNIs carried between VTEPs.

## Learning and BUM traffic

The hard part of any Layer 2 overlay is **BUM** traffic: broadcast, unknown unicast and multicast (ARP requests being the most common). A VTEP has to deliver one frame to every VTEP that has hosts in that VNI. Three approaches:

| Method | How it works | Trade-off |
|---|---|---|
| **Underlay multicast** (RFC 7348 flood and learn) | Each VNI maps to an IP multicast group; VTEPs join the group and BUM frames are sent once to the group. The underlay runs PIM (for example PIM-SM or Bidir) | Efficient, but the underlay needs multicast routing |
| **Ingress (head-end) replication** | The source VTEP sends a separate unicast copy to every remote VTEP in the VNI's flood list (static or learned from BGP EVPN) | No multicast needed; load on the source VTEP and links grows with the number of peers |
| **Control plane (BGP EVPN)** | VTEPs advertise their hosts' MAC and IP addresses in BGP, so most unknown unicast disappears and ARP can be answered locally (ARP suppression). Remaining BUM still uses multicast or ingress replication | Most scalable; needs BGP EVPN |

In the original **flood and learn** model, a VTEP learns "MAC X is behind VTEP 10.0.0.2" from the source fields of decapsulated frames, exactly as a switch learns from source MACs. With **BGP EVPN** (RFC 7432 and RFC 8365), learning moves to the control plane: this is what Catalyst 9000 and Nexus VXLAN fabrics use. SD-Access is different again: it uses **LISP** as the control plane and VXLAN as the data plane, with an extension (VXLAN Group Policy Option) that carries the scalable group tag.

## Layer 2 and Layer 3 gateways

| Gateway | Does what | Example |
|---|---|---|
| **VXLAN Layer 2 gateway** | Bridges between a VLAN and a VNI in the **same** subnet: maps VLAN 10 to VNI 10010 so a physical server on VLAN 10 and a VM in VNI 10010 share one broadcast domain | A leaf switch with VLAN-to-VNI mapping |
| **VXLAN Layer 3 gateway** | **Routes** between different VNIs, or between a VNI and a non-VXLAN network: the default gateway for hosts in the overlay | An SVI on the leaf (distributed anycast gateway in EVPN, the same gateway IP and MAC on every leaf) or a central router or border |

In EVPN fabrics, inter-subnet routing between VTEPs uses an extra **Layer 3 VNI** per VRF, separate from the **Layer 2 VNIs** that represent each subnet. You can see both types in the output of `show nve vni` on a Catalyst 9000:

```text
Switch# show nve vni
Interface  VNI        Multicast-group VNI state  Mode  VLAN  cfg vrf
nve1       50001      N/A             Up         L3CP  N/A   CLI GREEN
nve1       10010      239.1.1.10      Up         L2CP  10    CLI N/A
nve1       10020      N/A             Up         L2CP  20    CLI N/A
```

VNI 10010 floods BUM to a multicast group, VNI 10020 shows no group (its BUM traffic does not use underlay multicast; ingress replication is the usual alternative), and VNI 50001 is the Layer 3 VNI for VRF GREEN. `show nve peers` lists the remote VTEPs per VNI.

## Lab it yourself

The cheapest accurate lab uses Linux, which is a full VTEP. Use two Linux VMs on a host-only network in any type 2 hypervisor (this works on every host, including an Apple silicon Mac with ARM Linux guests), or Linux nodes in CML, GNS3 or EVE-NG (Windows, Linux or an Intel Mac; on an Apple silicon Mac use a remote x86 server or a Cisco DevNet sandbox):

1. Two Linux nodes, `vtep1` 192.168.50.1 and `vtep2` 192.168.50.2, on one routed or bridged underlay network.
2. On vtep1 (as root, replacing `eth0` with the underlay interface name): `ip link add vxlan10 type vxlan id 10010 local 192.168.50.1 remote 192.168.50.2 dev eth0 dstport 4789`, then `ip link set vxlan10 up` and `ip addr add 10.10.10.1/24 dev vxlan10`. Mirror it on vtep2 with 10.10.10.2. Always set `dstport 4789`: if you leave it out, Linux uses a different, pre-standard port.
3. `ping 10.10.10.2` across the overlay, and capture on the underlay with Wireshark or `tcpdump -n udp port 4789`. Wireshark decodes the VXLAN header: note the I flag, VNI 10010 and the inner Ethernet frame.
4. Check the overhead: `ip link show vxlan10` should report an MTU 50 bytes below the underlay interface (1450 on a 1500-byte underlay), so `ping -M do -s 1472 10.10.10.2` fails while `ping -M do -s 1422 10.10.10.2` (1422 + 28 = 1450) works.
5. Optional: with Catalyst 9000v images in CML, build a two-leaf BGP EVPN fabric and compare `show nve peers` and `show nve vni`.

## Key takeaways

- VXLAN (RFC 7348) carries Ethernet frames in UDP/IP: destination port **4789**, source port from a flow hash for ECMP.
- 8-byte VXLAN header with a **24-bit VNI** (about 16 million segments); I flag set for a valid VNI.
- **50 bytes** of overhead; the underlay needs an IP MTU of at least 1550 for 1500-byte inner packets, and VTEPs must not fragment.
- VTEPs encapsulate and decapsulate; on Cisco switches the VTEP is the NVE interface sourced from a loopback.
- BUM traffic uses underlay multicast or ingress replication; BGP EVPN (or LISP in SD-Access) replaces flood and learn.
- Layer 2 gateway bridges VLAN to VNI in one subnet; Layer 3 gateway routes between VNIs or to outside networks.
