## What a debug really costs

A `debug` command tells IOS XE to generate a log message, at severity 7 (debugging), every time a chosen event happens: a packet processed, a routing protocol state change, an SNMP request. Those messages are built by the route processor's CPU and then handed to every logging destination that accepts severity 7. That is where the risk lies:

- **Console output is slow.** The console line runs at 9600 baud by default. When debug messages arrive faster than the console can print them, the CPU spends its time servicing the console, and the router can become unreachable for SSH, drop routing adjacencies or miss keepalives.
- **Some debugs are unbounded.** `debug all`, `debug ip packet` with no access list or `debug ip routing` on a router learning a full table can generate thousands of messages per second.
- **The output can outlive you.** If the debug locks up your SSH session, you may not be able to type `undebug all`, and the console may be just as busy.

The professional routine is therefore: check the CPU first (`show processes cpu sorted`, `show processes cpu history`), keep debug output off the console, narrow the debug before you enable it, and stop it as soon as you have what you need.

> **Watch out:** On a production device, never enable a broad debug from the console with console logging at its default level. Disable console logging (`no logging console`) or raise its threshold (`logging console warnings`) first, send debugs to the buffer, and read them with `show logging`.

## Where debug output goes

Every logging destination has its own severity threshold. A destination receives a message when the message's severity number is less than or equal to the threshold, so debug output (severity 7) only reaches destinations set to `debugging`.

| Destination | Command | Notes |
|---|---|---|
| Console | `logging console <level>` | Default threshold is debugging; the riskiest place for debug output |
| VTY (SSH/Telnet) sessions | `logging monitor <level>` plus `terminal monitor` in the session | `terminal monitor` is per session and is lost when you log out; `terminal no monitor` stops it |
| Memory buffer | `logging buffered <size> <level>` | Read with `show logging`; `clear logging` empties it. The safest place for debugs |
| Syslog servers | `logging host <ip>` plus `logging trap <level>` | `logging trap` defaults to informational, so debugs are not sent to servers unless you raise it |

A typical safe preparation before debugging over SSH:

```text
R1(config)# service timestamps debug datetime msec localtime show-timezone
R1(config)# logging buffered 128000 debugging
R1(config)# logging console warnings
R1(config)# end
R1# terminal monitor
```

`service timestamps debug datetime msec` puts a millisecond timestamp on every debug line, which you need to correlate events. With `terminal monitor` you also see the output live in your SSH session; leave it off and read the buffer if the volume is high.

> **Exam tip:** "I enabled a debug over SSH and see nothing" almost always means `terminal monitor` was not entered in that session (or `logging monitor` is set below debugging). The debug is running; its output is simply not being copied to your VTY.

## Narrowing a debug

### Debug with an access list

Some debugs accept an ACL that selects which packets generate output. The classic case is `debug ip packet`:

```text
R1(config)# ip access-list extended DBG-ICMP
R1(config-ext-nacl)# permit icmp any host 10.2.20.30
R1(config-ext-nacl)# permit icmp host 10.2.20.30 any
R1(config-ext-nacl)# end
R1# debug ip packet DBG-ICMP detail
IP packet debugging is on (detailed) for access list DBG-ICMP
```

The ACL selects ICMP to and from 10.2.20.30 only, whatever the other address. A sample of what it prints when R1 itself pings 10.2.20.30 (from its interface address 10.1.10.1) and has no route to it:

```text
*Nov 23 10:15:02.118 UTC: IP: s=10.1.10.1 (local), d=10.2.20.30, len 100, unroutable
*Nov 23 10:15:02.118 UTC:     ICMP type=8, code=0
```

`unroutable` means the routing table had no entry for the destination; a working path shows `sending` with the outgoing interface instead.

> **Watch out:** `debug ip packet` only sees packets that the route processor itself handles: traffic sourced by or destined to the router, and packets punted to the CPU (for example with IP options or expiring TTL). Transit traffic that is CEF-switched in the data plane (in hardware on a Catalyst 9000, in the QFP on an ISR 4000 or Catalyst 8000) never appears. An empty `debug ip packet` for a transit flow does not prove the flow is absent. Use Embedded Packet Capture, SPAN or NetFlow for transit traffic.

### Conditional debugging

Conditional debugging attaches a **condition** to debugs that support it, so only events matching the condition are printed. Conditions are set before or after the debug itself:

```text
R1# debug condition interface GigabitEthernet0/0/1
Condition 1 set
R1# debug condition ip 10.1.10.20
Condition 2 set
R1# debug ip ospf adj
R1# show debugging condition
```

Common condition types include `interface`, `ip` (an address), `username`, `mac-address` and `vlan`, depending on platform and feature. To remove them use `undebug condition <n>` or `no debug condition all`; remove conditions only after the debugs are off, or the unconditioned debug can suddenly print everything.

Not every debug honours conditions; protocol debugs that are not tied to an interface or address may ignore them. Always confirm with `show debugging` and watch the first few seconds of output.

> **Real world:** IOS XE routers (ISR 4000, Catalyst 8000) also offer data-plane conditional debugging for the packet processor: `debug platform condition ipv4 <address>/<len> both`, `debug platform packet-trace packet 64`, then `debug platform condition start` and `show platform packet-trace summary`. That traces transit packets that `debug ip packet` cannot see, including the drop reason. It is router-specific; Catalyst 9000 switches use different tools (`show platform software fed ...`, Embedded Packet Capture).

## Seeing and stopping debugs

| Command | Purpose |
|---|---|
| `show debugging` | Lists every debug currently enabled, plus conditions |
| `undebug all` (or `no debug all`) | Turns off every debug at once; `u all` is the usual abbreviation |
| `undebug ip packet` | Turns off one debug |
| `show logging` | Reads the buffer where debug output was stored |
| `show processes cpu sorted` | Confirms the CPU is recovering after the debug is off |

> **Exam tip:** Know that `undebug all` and `no debug all` are equivalent, that `show debugging` lists what is running, and that conditions or ACLs are the way to keep a debug safe. The exam favours "limit the debug and keep it off the console" over "run it and hope".

A useful habit is to pre-type the exit: open a second SSH session with `undebug all` ready to send, or schedule it. On IOS XE, `debug` commands do not time out by themselves.

## A diagnostic workflow with debugs

1. Define the question precisely (for example, "why does the OSPF adjacency to 10.1.12.2 on Gi0/0/1 not reach FULL?").
2. Check the non-intrusive evidence first: `show` commands, `show logging`, counters.
3. Check CPU headroom.
4. Prepare logging: buffer at debugging, console at warnings or off, timestamps with msec, `terminal monitor` if you want live output.
5. Set conditions or build an ACL that matches only the traffic or neighbour in question.
6. Enable the narrowest debug that answers the question (`debug ip ospf adj`, not `debug ip ospf events` plus `debug ip ospf packet`).
7. Reproduce the event (`clear ip ospf process` only if safe, `shutdown` / `no shutdown` on a lab link, a test ping).
8. `undebug all`, then read and save the buffer.

## Lab it yourself

Build two IOS XE routers (Catalyst 8000V or IOL-XE) in Cisco Modeling Labs, GNS3 or EVE-NG on Windows, Linux or an Intel Mac; on an Apple silicon Mac use a remote x86 server or a Cisco DevNet sandbox.

1. Topology: `R1 Gi2 (10.1.12.1/30) --- (10.1.12.2/30) Gi2 R2`, a loopback on each (10.255.0.1/32 and 10.255.0.2/32), OSPF area 0 on both.
2. Prepare logging on R1: `logging buffered 128000 debugging`, `logging console warnings`, `service timestamps debug datetime msec`.
3. Build `ip access-list extended DBG-ICMP` matching ICMP between the two loopbacks and run `debug ip packet DBG-ICMP`. Ping from R1 `ping 10.255.0.2 source Loopback0` and read `show logging`: the echo requests R1 sends and the replies it receives both appear. Then `ping 10.1.12.2` (not matched by the ACL) and confirm nothing new is logged.
4. `undebug all`. Set `debug condition interface GigabitEthernet2`, enable `debug ip ospf adj`, then bounce Gi2 on R2. Confirm that only Gi2 events print. Check `show debugging`.
5. Over SSH to R1, repeat step 4 without and then with `terminal monitor`.
6. Clean up: `undebug all`, `no debug condition all`, `show debugging` (nothing listed).

## Key takeaways

- Debug output is severity 7, built by the CPU, and copied to every destination whose threshold is debugging; the console is the slowest and most dangerous.
- Prepare first: check CPU, buffer the output (`logging buffered <size> debugging`), lower console logging, add `service timestamps debug datetime msec`.
- Over SSH, you see debugs only after `terminal monitor` (and with `logging monitor` at debugging).
- Narrow every debug: an ACL (`debug ip packet <acl> [detail]`) or conditions (`debug condition interface ...`, `debug condition ip ...`); verify with `show debugging` and `show debugging condition`.
- `debug ip packet` sees only traffic the route processor handles, never CEF- or hardware-switched transit traffic.
- `undebug all` or `no debug all` stops everything; remove conditions after the debugs are off.
