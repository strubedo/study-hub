## RESTCONF in one paragraph

**RESTCONF** (RFC 8040) gives HTTP access to the same YANG-modelled data as NETCONF. Each piece of configuration or state is a **resource** with a URI; you read it with `GET` and change it with `POST`, `PUT`, `PATCH` and `DELETE`, sending and receiving **JSON** or **XML**. It runs over **HTTPS**, so any language or tool that speaks HTTP (curl, Postman, Python `requests`) can manage the device without a NETCONF library. The trade-off: RESTCONF has no candidate datastore, locks or multi-operation transactions; each request is applied to the running configuration on its own.

## The URI structure

RFC 8040 lets a client discover the API root with `GET /.well-known/host-meta`; on IOS XE the root is `/restconf`. Under it:

| Resource | Contains |
|---|---|
| `/restconf/data` | The combined configuration and state data tree (the datastore) |
| `/restconf/operations` | RPC operations defined in YANG models |
| `/restconf/data/ietf-yang-library:modules-state` | Which YANG modules and revisions the device supports |

A data URI names the YANG **module** once, then follows the containers and lists of the model:

```text
https://192.0.2.10/restconf/data/<module>:<top-container>/<child>/<list>=<key>/<leaf>

https://192.0.2.10/restconf/data/Cisco-IOS-XE-native:native/hostname
https://192.0.2.10/restconf/data/Cisco-IOS-XE-native:native/interface/Loopback=100
https://192.0.2.10/restconf/data/ietf-interfaces:interfaces/interface=GigabitEthernet1
https://192.0.2.10/restconf/data/ietf-interfaces:interfaces/interface=GigabitEthernet1%2F0%2F1
https://192.0.2.10/restconf/data/Cisco-IOS-XE-native:native/interface?depth=2
```

- **List entries** are selected with `=key` (several keys separated by commas).
- Characters that are special in a URI must be **percent-encoded**: the `/` in `GigabitEthernet1/0/1` becomes `%2F`.
- **Query parameters** shape the reply: `depth=N` limits nesting, `content=config` or `content=nonconfig` selects configuration or state, `fields=` returns only some leaves.

> **Exam tip:** The pattern to recognise is `/restconf/data/` followed by `module:container`, for example `/restconf/data/ietf-interfaces:interfaces` or `/restconf/data/Cisco-IOS-XE-native:native`. The module name appears only on the first node (and wherever a node from another module is augmented in).

## Media types

| Media type | Use |
|---|---|
| `application/yang-data+json` | JSON encoding of YANG data |
| `application/yang-data+xml` | XML encoding of YANG data |
| `application/yang-patch+json` / `+xml` | YANG Patch (several edits in one PATCH), where supported |

Send the type you want back in the **`Accept`** header and the type of your body in **`Content-Type`**. In JSON, the top-level member is qualified with the module name: `{"Cisco-IOS-XE-native:hostname": "R1"}`.

## Methods and their NETCONF equivalents

| HTTP method | RESTCONF meaning | NETCONF equivalent (RFC 8040) | Success code |
|---|---|---|---|
| `GET` | Read a resource (config and state) | `<get-config>` / `<get>` | 200 OK |
| `HEAD` | Headers only | `<get-config>` / `<get>` | 200 OK |
| `POST` | Create a **child** resource under the URI; fails if it exists. Also invokes an RPC under `/operations` | `<edit-config>` with `create` | 201 Created (409 Conflict if it already exists) |
| `PUT` | Create or **replace** the resource at the URI | `<edit-config>` with `create`/`replace` | 201 Created (new) or 204 No Content (replaced) |
| `PATCH` | **Merge** the body into the existing resource (plain patch) | `<edit-config>` with `merge` | 204 No Content |
| `DELETE` | Delete the resource | `<edit-config>` with `delete` | 204 No Content (an error, typically 404, if it does not exist) |
| `OPTIONS` | Which methods the resource supports | none | 200 OK |

Common errors: **400** malformed body or wrong media type, **401** bad credentials, **403** user not authorized (for example not privilege 15), **404** the URI does not exist (often a typo in the module or a missing `%2F`), **405** method not allowed on that resource, **409** conflict (the resource already exists for POST, or a lock is held).

> **Watch out:** `PUT` replaces. A `PUT` to an interface URI with only a description in the body removes the interface's other settings (its IP address, for example). Use `PATCH` when you mean "add or change this leaf and leave the rest".

## Enabling RESTCONF on IOS XE

```text
R1(config)# aaa new-model
R1(config)# aaa authentication login default local
R1(config)# aaa authorization exec default local
R1(config)# username netops privilege 15 secret ExamplePass123
R1(config)# ip http secure-server
R1(config)# ip http authentication local
R1(config)# restconf
```

- `restconf` starts the RESTCONF service, which is served by the device's HTTPS server, so **`ip http secure-server`** is required (TCP 443 by default). Plain-HTTP `ip http server` is not needed and is better left off.
- `ip http authentication local` checks the HTTP basic-authentication credentials against the local user database (or use `aaa` with TACACS+/RADIUS); the user must be authorized at **privilege 15**, as for NETCONF. The secret here is a placeholder.
- RESTCONF and NETCONF can run together; both use the same YANG models and the same management processes.

Verify:

```text
R1# show running-config | include restconf|ip http
ip http authentication local
ip http secure-server
restconf
R1# show platform software yang-management process
confd            : Running
nesd             : Running
syncfd           : Running
ncsshd           : Running
dmiauthd         : Running
nginx            : Running
ndbmand          : Running
pubd             : Running
gnmib            : Not Running
```

`nginx` is the web server that fronts RESTCONF; if it is not Running, check `ip http secure-server` and the certificate (a self-signed trustpoint is generated automatically on many releases). `show ip http server status` shows the HTTP and HTTPS server state and port.

## Using RESTCONF with curl

```text
$ curl -k -u netops:ExamplePass123 \
    -H "Accept: application/yang-data+json" \
    https://192.0.2.10/restconf/data/Cisco-IOS-XE-native:native/hostname

{
  "Cisco-IOS-XE-native:hostname": "R1"
}
```

Changing the description of Gi1 with the IETF interfaces model, without touching anything else on the interface:

```text
$ curl -k -u netops:ExamplePass123 -X PATCH \
    -H "Accept: application/yang-data+json" \
    -H "Content-Type: application/yang-data+json" \
    -d '{"ietf-interfaces:interface": {"name": "GigabitEthernet1", "description": "WAN to ISP1"}}' \
    https://192.0.2.10/restconf/data/ietf-interfaces:interfaces/interface=GigabitEthernet1
```

`-k` skips certificate verification and is acceptable only in a lab; `-u` sends HTTP basic authentication; the credentials shown are examples.

## Using RESTCONF with Python requests

```python
import requests

BASE = "https://192.0.2.10/restconf/data"
AUTH = ("netops", "ExamplePass123")   # example only
HEADERS = {
    "Accept": "application/yang-data+json",
    "Content-Type": "application/yang-data+json",
}

# Read one interface (ietf-interfaces model)
url = f"{BASE}/ietf-interfaces:interfaces/interface=GigabitEthernet1"
r = requests.get(url, auth=AUTH, headers=HEADERS, verify=False, timeout=10)
print(r.status_code)
print(r.json())

# Create or replace Loopback100 (IOS XE native model)
loopback = {
    "Cisco-IOS-XE-native:Loopback": {
        "name": 100,
        "description": "Managed by RESTCONF",
        "ip": {
            "address": {
                "primary": {"address": "10.100.100.1", "mask": "255.255.255.255"}
            }
        },
    }
}
url = f"{BASE}/Cisco-IOS-XE-native:native/interface/Loopback=100"
r = requests.put(url, auth=AUTH, headers=HEADERS, json=loopback, verify=False, timeout=10)
print(r.status_code)   # 201 Created if new, 204 No Content if replaced
```

The `PUT` body names the same list entry as the URI (`Loopback=100` and `"name": 100`); a mismatch between the URI key and the body key is rejected with 400. `verify=False` disables certificate checks and belongs only in a lab.

## NETCONF versus RESTCONF

| | NETCONF | RESTCONF |
|---|---|---|
| Standard | RFC 6241 (SSH: RFC 6242) | RFC 8040 |
| Transport | SSH, TCP 830 | HTTPS, TCP 443 |
| Encoding | XML | JSON or XML |
| Operations | `get`, `get-config`, `edit-config`, `lock`, `commit` ... | HTTP methods on URIs |
| Datastores | running, candidate (optional), startup | One unified datastore (changes apply to running) |
| Transactions and locks | Yes (candidate + commit, lock) | No: each request stands alone |
| IOS XE enable | `netconf-yang` | `restconf` + `ip http secure-server` |
| Typical clients | ncclient, Ansible, NSO, Terraform IOS XE provider | curl, Postman, Python `requests`, web applications |

## Lab it yourself

Use a Catalyst 8000V in Cisco Modeling Labs, GNS3 or EVE-NG (Windows, Linux or an Intel Mac; on an Apple silicon Mac use a remote x86 server or the Cisco DevNet IOS XE sandbox), plus a workstation (Windows, macOS or Linux) with curl and Python 3 (`pip install requests`).

1. Enable RESTCONF as above and confirm `nginx : Running`.
2. `GET` the hostname, then `GET /restconf/data/ietf-interfaces:interfaces` and `GET /restconf/data/ietf-yang-library:modules-state?depth=2` (or the newer yang-library path your release supports) to see the models.
3. Run the Python script; check `show running-config interface Loopback100`. Run it again and compare the status code (201 versus 204).
4. After step 3, Loopback100 has a description and an IP address. `PATCH` `.../Cisco-IOS-XE-native:native/interface/Loopback=100` with a body holding only `name` and a new `description`, then `PUT` the same body to the same URI: compare `show running-config interface Loopback100` after each to see that `PUT` removed the IP address. Do not try this on GigabitEthernet1, which is usually the interface your RESTCONF session uses.
5. Request a URI with a typo in the module name and one with an unencoded `/` in an interface name, and read the 404 or 400 responses.

## Key takeaways

- RESTCONF (RFC 8040) exposes YANG data over HTTPS as URIs under `/restconf/data/<module>:<container>/...`; list entries are `=key`, special characters percent-encoded.
- Media types: `application/yang-data+json` and `application/yang-data+xml`, in `Accept` and `Content-Type`.
- GET reads; POST creates a child (409 if it exists); PUT creates or replaces (201 or 204); PATCH merges; DELETE removes.
- IOS XE: `restconf`, `ip http secure-server`, `ip http authentication local`, a privilege 15 user; verify `nginx` in `show platform software yang-management process`.
- RESTCONF has no candidate datastore or locks; NETCONF does. Both share the same YANG models.
