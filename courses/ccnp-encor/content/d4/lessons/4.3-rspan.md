## The problem RSPAN solves

Local SPAN needs the analyzer on the same switch as the traffic. In a campus the traffic you care about is often on an access switch in a closet, while the analyzer or IDS sensor sits in the data center. **Remote SPAN (RSPAN)** copies the source traffic into a dedicated VLAN, the **RSPAN VLAN**, which is trunked through the Layer 2 network to the switch where the analyzer is connected. That switch copies everything arriving in the RSPAN VLAN to its destination port.

```text
 Server --Gi1/0/5 [SW1 access] Te1/1/1 ===trunk=== Te1/1/1 [DSW1] Te1/1/2 ===trunk=== Te1/1/1 [SW3] Gi1/0/24 -- Analyzer
              source session                       carries VLAN 900                      destination session
              -> remote vlan 900                   (remote-span)                         remote vlan 900 ->
```

Three roles:

| Switch | Configures |
|---|---|
| Source switch (SW1) | The RSPAN VLAN, a session with the real source ports or VLANs and `destination remote vlan` |
| Intermediate switches (DSW1) | The RSPAN VLAN only, allowed on the trunks in the path |
| Destination switch (SW3) | The RSPAN VLAN, a session with `source remote vlan` and the real destination port |

## The RSPAN VLAN

The RSPAN VLAN is an ordinary VLAN number marked with `remote-span`:

```text
SW1(config)# vlan 900
SW1(config-vlan)# name RSPAN-IDS
SW1(config-vlan)# remote-span
```

Rules that follow from its job:

- **Create it with `remote-span` on every switch in the path**, including intermediate ones. Switches treat the VLAN differently: they disable MAC address learning in it and flood its frames out of every trunk that carries it, so the copies reach the destination switch whatever their original destination MAC.
- **Dedicate it**: no access ports, no SVI, no user traffic. The copies are flooded, so anything else in the VLAN would receive them.
- **Allow it on every trunk in the path** and keep it off trunks that do not lead to the destination, because the flooded copies consume bandwidth on every trunk where the VLAN is allowed.
- VLAN 1 and the reserved VLANs 1002 to 1005 cannot be RSPAN VLANs. VTP version 1 or 2 propagates the `remote-span` attribute for normal-range VLANs; extended-range RSPAN VLANs need VTP version 3 or manual configuration on each switch.

> **Watch out:** RSPAN traffic shares the trunks with production traffic. Mirroring `both` directions of a busy uplink can double the load on every trunk the RSPAN VLAN crosses. Size it like real traffic, or filter it at the source.

## Configuring RSPAN

### Source switch

```text
SW1(config)# vlan 900
SW1(config-vlan)# remote-span
SW1(config-vlan)# exit
SW1(config)# interface TenGigabitEthernet1/1/1
SW1(config-if)# switchport mode trunk
SW1(config-if)# switchport trunk allowed vlan add 900
SW1(config-if)# exit
SW1(config)# monitor session 1 source interface GigabitEthernet1/0/5 both
SW1(config)# monitor session 1 destination remote vlan 900
```

### Intermediate switch

```text
DSW1(config)# vlan 900
DSW1(config-vlan)# remote-span
DSW1(config-vlan)# exit
DSW1(config)# interface range TenGigabitEthernet1/1/1 - 2
DSW1(config-if-range)# switchport trunk allowed vlan add 900
```

No `monitor session` is needed on DSW1: it simply carries VLAN 900.

### Destination switch

```text
SW3(config)# vlan 900
SW3(config-vlan)# remote-span
SW3(config-vlan)# exit
SW3(config)# interface TenGigabitEthernet1/1/1
SW3(config-if)# switchport trunk allowed vlan add 900
SW3(config-if)# exit
SW3(config)# monitor session 5 source remote vlan 900
SW3(config)# monitor session 5 destination interface GigabitEthernet1/0/24
```

The session numbers on SW1 and SW3 are independent (1 and 5 here); what ties them together is VLAN 900. Source-side options work as in local SPAN: `rx` / `tx` / `both`, VLAN sources and `filter vlan` all belong on the source switch.

> **Exam tip:** Know which command goes where. `destination remote vlan` is on the **source** switch (the copies are sent into the VLAN); `source remote vlan` is on the **destination** switch (the copies are taken from the VLAN). Every switch in between needs only the VLAN with `remote-span` and the trunks.

## Verifying

On the source switch:

```text
SW1# show monitor session 1
Session 1
---------
Type                     : Remote Source Session
Source Ports             :
    Both                 : Gi1/0/5
Dest RSPAN VLAN          : 900
```

On the destination switch:

```text
SW3# show monitor session 5
Session 5
---------
Type                     : Remote Destination Session
Source RSPAN VLAN        : 900
Destination Ports        : Gi1/0/24
    Encapsulation        : Native
          Ingress        : Disabled
```

Also check on every switch:

| Command | What to confirm |
|---|---|
| `show vlan remote-span` | VLAN 900 is listed as a remote SPAN VLAN |
| `show vlan id 900` | The VLAN exists and has no access ports |
| `show interfaces trunk` | VLAN 900 is allowed and forwarding on the trunks in the path (not pruned, not STP-blocked) |
| `show monitor session all` | Session types and VLAN on source and destination switches |

Typical faults: the VLAN missing or not marked `remote-span` on an intermediate switch, VLAN 900 not allowed (or pruned) on one trunk, STP blocking the only path, or the two end switches using different VLAN numbers.

## RSPAN versus ERSPAN

| | RSPAN | ERSPAN |
|---|---|---|
| Transport | Layer 2: RSPAN VLAN over trunks | Layer 3: GRE over any IP path |
| Reach | Only inside one switched domain | Across routed cores, WANs, data centers |
| Configuration in the path | VLAN on every switch, trunks | None: just IP routing |
| Overhead | None beyond the copy | GRE + ERSPAN headers (50 bytes for type II) |

## Lab it yourself

In Cisco Modeling Labs, GNS3 or EVE-NG (Windows, Linux or an Intel Mac; on an Apple silicon Mac use a remote x86 server or a DevNet sandbox), chain three switches with 802.1Q trunks: `SW1 - DSW1 - SW3`. Put two Linux hosts in VLAN 10 on SW1 and a Linux analyzer on SW3 Gi1/0/24. As with local SPAN, some virtual switch images do not forward mirrored copies, so trust `show monitor` and the VLAN checks even if the capture stays empty.

1. Create VLAN 900 with `remote-span` on all three switches and allow it on the trunks.
2. Build the source session on SW1 and the destination session on SW3 as above. Ping between the hosts and capture on the analyzer.
3. Remove VLAN 900 from the DSW1-SW3 trunk and confirm the copies stop; check `show interfaces trunk` on DSW1.
4. Remove `remote-span` from VLAN 900 on DSW1 only, restore the trunk, and note what changes in `show vlan remote-span`.
5. Prove the final state with `show monitor session all` on SW1 and SW3 and `show vlan remote-span` on all three.

## Key takeaways

- RSPAN carries SPAN copies in a dedicated VLAN marked `remote-span` across trunks to the switch with the analyzer.
- Source switch: `monitor session N source ...` and `monitor session N destination remote vlan V`. Destination switch: `monitor session M source remote vlan V` and `destination interface ...`. Session numbers are local.
- Every switch in the path needs the VLAN with `remote-span` and the VLAN allowed on the trunks; the VLAN has no access ports or user traffic.
- MAC learning is disabled in the RSPAN VLAN and its frames are flooded on trunks that carry it, so copies consume trunk bandwidth.
- Verify with `show monitor session N` (Remote Source / Remote Destination Session), `show vlan remote-span` and `show interfaces trunk`.
- RSPAN stops at the Layer 2 boundary; use ERSPAN across routed networks.
