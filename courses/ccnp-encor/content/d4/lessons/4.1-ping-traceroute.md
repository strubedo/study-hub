## Ping: what it sends and what the symbols mean

`ping` sends ICMP **echo request** messages (type 8) and waits for **echo reply** messages (type 0), as defined in RFC 792. On IOS XE a plain `ping 10.2.2.2` sends five 100-byte echoes with a 2-second timeout and prints one character per probe:

```text
R1# ping 10.2.2.2
Type escape sequence to abort.
Sending 5, 100-byte ICMP Echos to 10.2.2.2, timeout is 2 seconds:
.!!!!
Success rate is 80 percent (4/5), round-trip min/avg/max = 1/1/2 ms
```

| Character | Meaning |
|---|---|
| `!` | Echo reply received |
| `.` | No reply within the timeout |
| `U` | ICMP destination unreachable received (a router said it cannot deliver) |
| `M` | ICMP "fragmentation needed and DF set" received (could not fragment) |
| `Q` | Source quench received |
| `&` | Packet lifetime exceeded (TTL expired) |
| `?` | Unknown packet type received |

The first probe failing (`.!!!!`) is normal when the router or the next hop has to resolve ARP first: the first packet is dropped while ARP completes. A steady `U` points at a router that has no route or an ACL with ICMP unreachables enabled; a steady `.` means the replies never arrive, which could be the forward path, the return path, or a filter.

> **Exam tip:** A ping succeeds only when the echo reaches the target **and** the reply comes back. "Ping fails but traceroute reaches the destination" or "ping from the router works but not from the host" usually means a return-route or source-address problem, not a forward-path problem.

## Extended ping

The one-line form takes keywords; the interactive form (`ping` with no arguments) prompts for every option.

```text
R1# ping 10.2.2.2 source Loopback0 repeat 100 size 1400 df-bit
R1# ping vrf CUST-A 10.40.0.1 source GigabitEthernet0/0/1
```

| Option | Why you use it |
|---|---|
| `source <interface or address>` | Tests the path back to that source. Pinging from the egress interface address hides a missing route to a LAN or loopback on the far side |
| `repeat <n>` | Many probes to catch intermittent loss or flapping |
| `size <bytes>` | Packet size; on IOS XE this is the whole IP datagram including the 20-byte IP header and 8-byte ICMP header |
| `df-bit` | Sets Don't Fragment, so oversize packets fail instead of being fragmented |
| `timeout <s>` | Longer wait for slow links |
| `tos <value>` | Sets the IP ToS byte to test QoS treatment |
| `validate` | Checks that the reply data matches what was sent |

### Finding the path MTU with a size sweep

With `df-bit`, a router whose egress MTU is smaller than the packet must drop it and return ICMP type 3 code 4 ("fragmentation needed and DF set"), which ping shows as `M`. The interactive extended ping can sweep through sizes:

```text
R1# ping
Protocol [ip]:
Target IP address: 10.2.2.2
Repeat count [5]: 1
Datagram size [100]:
Timeout in seconds [2]:
Extended commands [n]: y
Source address or interface: Loopback0
Type of service [0]:
Set DF bit in IP header? [no]: yes
Validate reply data? [no]:
Data pattern [0x0000ABCD]:
Loose, Strict, Record, Timestamp, Verbose[none]:
Sweep range of sizes [n]: y
Sweep min size [36]: 1470
Sweep max size [18024]: 1480
Sweep interval [1]: 1
Type escape sequence to abort.
Sending 11, [1470..1480]-byte ICMP Echos to 10.2.2.2, timeout is 2 seconds:
Packet sent with a source address of 10.255.0.1
Packet sent with the DF bit set
!!!!!!!MMMM
Success rate is 63 percent (7/11), round-trip min/avg/max = 1/1/2 ms
```

Seven sizes, 1470 to 1476, succeed and 1477 to 1480 fail with `M`: the path MTU is **1476 bytes**, the classic value for a GRE tunnel over a 1500-byte underlay (1500 minus the 20-byte outer IP header and 4-byte GRE header). If the failing sizes show `.` instead of `M`, the device that drops the packet is not sending ICMP unreachables back (or something filters them), which is exactly the condition that breaks Path MTU Discovery.

## Traceroute: how it works

IOS XE `traceroute` discovers the hops by exploiting the TTL:

1. It sends probes with **TTL 1**. The first router decrements the TTL to 0, drops the probe and returns ICMP **time exceeded** (type 11, code 0). Its source address is hop 1.
2. It repeats with TTL 2, 3 and so on, three probes per TTL by default, up to a maximum TTL of 30.
3. The probes are **UDP** datagrams to high destination port numbers (starting at 33434 and incrementing). When a probe finally reaches the destination, no application listens on that port, so the destination answers ICMP **port unreachable** (type 3, code 3), and traceroute stops.

Windows `tracert` uses ICMP echo requests instead of UDP, and Linux `traceroute` uses UDP by default (`-I` for ICMP, `-T` for TCP). This matters when a firewall permits one probe type and not another: the same path can look different from different tools.

```text
R1# traceroute 10.2.2.2 source Loopback0 numeric probe 3 timeout 1 ttl 1 15
Type escape sequence to abort.
Tracing the route to 10.2.2.2
VRF info: (vrf in name/id, vrf out name/id)
  1 10.1.12.2 1 msec 1 msec 1 msec
  2 10.1.23.3 2 msec 1 msec 2 msec
  3 10.1.34.4 2 msec 2 msec *
```

Keywords: `numeric` skips DNS lookups (always use it in a lab without DNS, or every hop waits for a lookup), `probe` sets probes per hop, `timeout` the wait per probe in seconds, `ttl <min> <max>` the TTL range, `source` the source address or interface, and `traceroute vrf NAME` the routing table. The interactive form (`traceroute` with no arguments) also offers the destination port and other options.

### Reading the symbols

| Output | Meaning |
|---|---|
| `nn msec` | Reply received; round-trip time |
| `*` | No reply to that probe within the timeout |
| `!H` | Host unreachable (ICMP type 3 code 1): the last router cannot reach the host, typically no ARP reply |
| `!N` | Network unreachable (type 3 code 0): a router has no route |
| `!P` | Protocol unreachable (type 3 code 2) |
| `!A` | Administratively prohibited (type 3 code 13, RFC 1812): an ACL or firewall denied the probe and said so |
| `Q` | Source quench |
| `?` | Unknown ICMP type |

Patterns worth recognising:

- **`* * *` on one hop, later hops answer**: that router does not send time-exceeded messages or rate-limits them. The path through it works; it is not the fault.
- **`* * *` from some hop to the end**: the probes or their replies are dropped there, or the destination never answers (a host firewall dropping UDP).
- **Last hop shows `1 msec 1 msec *`**: IOS rate-limits the ICMP unreachables it generates (by default one per 500 ms, `ip icmp rate-limit unreachable`), so the third port unreachable from a Cisco destination is often suppressed. Not a fault.
- **`!A`**: an ACL on that router (or the next one) denies the probes. With `no ip unreachables` on the filtering interface the same block shows as `*` instead.
- **Repeating pair of hops** (10.1.1.1, 10.1.1.2, 10.1.1.1, 10.1.1.2 ...): a routing loop; the TTL keeps expiring as the packet bounces.

> **Watch out:** Traceroute shows the **forward** path only. Each hop's address is the interface the time-exceeded message was sourced from (usually the ingress interface toward you), and the replies may return by a different path. A hop with high delay may simply be slow to generate ICMP while forwarding traffic normally.

## A diagnostic workflow with ping and traceroute

1. Ping the destination from the source that matters (`source Loopback0` or the LAN interface), not just from the nearest interface.
2. If it fails, traceroute with the same source to see where the path stops.
3. At the failing hop, check the routing table for the destination **and** for the return route to your source.
4. If small packets work but large ones fail, sweep with `df-bit` to find the path MTU, and look for `M` versus `.`.
5. Use `repeat 1000` (or IP SLA, lesson 4.4) for intermittent loss.

## Lab it yourself

In Cisco Modeling Labs, GNS3 or EVE-NG (Windows, Linux or an Intel Mac; on an Apple silicon Mac use a remote x86 server or a DevNet sandbox), chain four IOS XE routers: `R1 - R2 - R3 - R4`, /30 links in 10.1.0.0/16, loopbacks 10.255.0.N/32, OSPF area 0.

1. From R1: `traceroute 10.255.0.4 numeric` and `traceroute 10.255.0.4 source Loopback0 numeric probe 3 ttl 1 10`.
2. On R3, apply an inbound extended ACL on its R2-facing interface that denies UDP to R4's loopback and permits everything else. Traceroute again and note `!A`. Add `no ip unreachables` on that interface and note that `!A` becomes `*`.
3. Build a GRE tunnel between R1 and R4 (lesson 2.2), route a test loopback over it, and sweep `ping` with DF set from 1470 to 1480 bytes. Confirm the 1476-byte path MTU.
4. Remove R4's route back to R1's loopback (for example with a distribute list) and compare `ping 10.255.0.4` with `ping 10.255.0.4 source Loopback0`.
5. Prove each point with `show ip route`, `show access-lists` (match counters) and `show interfaces tunnel 0`.

## Key takeaways

- Ping uses ICMP echo request (type 8) and echo reply (type 0); IOS defaults are five 100-byte echoes and a 2-second timeout. Know `!`, `.`, `U`, `M`, `Q`, `&`, `?`.
- Always choose the source on purpose: `ping <ip> source <intf>` tests the return route to that source.
- `size` plus `df-bit` (or an extended-ping sweep) finds the path MTU; `M` means a router returned "fragmentation needed and DF set".
- IOS traceroute sends UDP probes to high ports with rising TTL; hops answer with time exceeded (type 11), the destination with port unreachable (type 3 code 3). Windows uses ICMP echo.
- `*` = no reply, `!H` host, `!N` network, `!P` protocol unreachable, `!A` administratively prohibited.
- A silent middle hop with answering hops beyond it is not a fault; traceroute shows only the forward path.
