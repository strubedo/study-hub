## "Traditional" workflows

The v1.2 topic contrasts **traditional** and **AI-powered** workflows. The traditional ones are the deterministic automation tasks Catalyst Center has always done: you define what you want, and it discovers, configures, upgrades and checks devices according to rules you set. Each is available in the GUI and through the Intent API (the API groups them into domains such as Discovery, Devices, Sites, Network Settings, Configuration Templates, Software Image Management (SWIM), Device Onboarding (PnP), Compliance and Command Runner).

## 1. Discovery and inventory

**Discovery** finds existing devices and adds them to the inventory:

- **Methods**: CDP or LLDP neighbor crawling from a seed device (with a hop limit), or an IP address range or list.
- **Credentials**: CLI (SSH username, password and enable password), SNMP (v2c read and write communities or SNMPv3 users), and optionally NETCONF (port 830) and HTTP(S). Credentials can be stored globally in Design settings and reused.
- Discovery logs in, collects the device's configuration, interfaces, modules and neighbors, and adds it to **Inventory**.

**Inventory** lists every device with its reachability and **manageability** status (for example Managed, or a reason it is not), role (access, distribution, core, border router), software version, site and last synchronization. Inventory is resynchronized periodically and on change notifications; a device that stops answering SSH or SNMP shows as unreachable, and its Assurance data stops.

## 2. Network hierarchy and network settings (Design)

The **network hierarchy** models the real world: **Global > Area > Building > Floor**, for example Global / US-East / NYC-HQ / Floor-3. Everything downstream hangs off it: devices are assigned to sites, and settings, profiles and images are set at a level and **inherited** by everything below, unless overridden at a lower level.

**Network settings** defined per hierarchy level include:

| Setting | Examples |
|---|---|
| Network servers | AAA (Cisco ISE), DHCP, DNS servers and domain, NTP, time zone |
| Telemetry | Syslog and SNMP trap receivers, NetFlow collector, and whether Catalyst Center itself is the receiver |
| Device credentials | CLI, SNMP, NETCONF credentials used for that site |
| IP address pools | Global pools and site reservations for management, fabric and client subnets |
| Banners and others | Message of the day, wireless settings (out of scope for v1.2) |

When a device is **provisioned** to a site, Catalyst Center pushes the inherited settings to it as configuration (for example `ntp server`, `logging host`, `snmp-server host` and AAA lines).

## 3. Templates

**Templates** carry configuration that network settings do not cover. They are written in the **Template Editor** (Template Hub on recent releases) using CLI lines with variables, in the **Velocity** or **Jinja2** template languages:

```text
interface $uplink
 description Uplink to $peer_name
 switchport mode trunk
 switchport trunk allowed vlan $allowed_vlans
```

- **Regular templates** contain the configuration; **composite templates** run several regular templates in order.
- **Day-0 templates** are used for Plug and Play onboarding (the first configuration of a new device); **Day-N templates** change devices already in the network.
- Templates are versioned and must be **committed** before use. They are attached to **network profiles**, which are assigned to sites, so the right template reaches the right devices during provisioning. Variables are filled from forms, from system variables (such as hostname or management IP) or from the API.

## 4. Software Image Management (SWIM)

SWIM upgrades IOS XE images at scale:

1. **Import** images into the image repository (from cisco.com, a URL or a file).
2. Mark a **golden image** per device family (and optionally per site and role). Devices running anything else are flagged as non-compliant with the golden image.
3. Run **readiness checks** (enough flash, configuration register, startup configuration saved, image compatibility).
4. **Distribute** the image to the devices (copy to flash), possibly in advance of the maintenance window.
5. **Activate** it (install and reload) on a schedule, with **pre-checks and post-checks** that compare state before and after (for example interface and neighbor counts, CPU, configuration).

## 5. Plug and Play (PnP) onboarding

**Plug and Play** delivers zero-touch deployment for a new device that arrives with no configuration:

1. The device boots with an empty configuration, gets an address by DHCP, and runs the PnP agent built into IOS XE.
2. It discovers the PnP server, which is Catalyst Center, through one of: **DHCP option 43** (a string carrying the server's IP), **DNS** (a lookup of `pnpserver.<domain>` in the domain learned from DHCP), or the cloud **Plug and Play Connect** portal that redirects devices to the right Catalyst Center by serial number.
3. The device appears in Catalyst Center as unclaimed. An operator **claims** it (or a rule claims it automatically by serial number) and assigns a site, a Day-0 template and, optionally, a golden image.
4. Catalyst Center upgrades the image if required, applies the Day-0 configuration, and adds the device to inventory as managed.

## 6. Provisioning, compliance and day-N operations

- **Provision**: assign a device to a site and push the site's settings, network profile templates and (for SD-Access) fabric roles. Provisioning previews the configuration before deployment on recent releases.
- **Compliance**: Catalyst Center compares each device's running configuration and image against what it intends (settings, templates, golden image, startup versus running configuration) and flags drift, for example someone changing NTP by CLI.
- **Configuration archive**: periodic backups of running and startup configurations with a diff view.
- **Command Runner**: run read-only `show` commands on many devices at once, through the GUI or the API.
- **Security advisories** and **end-of-life** reports: match inventory against published Cisco PSIRT advisories and EoX notices.

## Traditional versus AI-powered, briefly

Traditional workflows do exactly what you configure: a template pushes these lines, a golden image is this file, a threshold is this number. The AI-powered workflows in the next lesson add learned baselines and automated reasoning on top of the same inventory and telemetry: instead of a fixed threshold, the system learns what normal looks like for each site and explains deviations.

## Lab it yourself

Use a Cisco DevNet Catalyst Center sandbox from a browser on Windows, macOS or Linux (the reservable sandboxes include devices you can discover and provision; the always-on one is read-only).

1. In Design, create an area, building and floor, and set NTP and syslog servers at the building level. Check that the floor inherits them.
2. Look at a discovery job (or run one in a reservable sandbox) with CDP and an IP range; read the credentials it used and the devices it found.
3. Open Inventory and read the reachability, manageability and software columns.
4. In the Template Editor, create a regular template with two variables, commit it, and simulate it with sample values.
5. In the image repository, see which image is marked golden for a device family and which devices are flagged as outdated.
6. With the API documentation, find the endpoints for network devices, sites, templates, SWIM and PnP, and note which HTTP method each task uses.

## Key takeaways

- Traditional workflows are deterministic automation: discovery, inventory, hierarchy and settings, templates, SWIM, PnP, provisioning and compliance, all in the GUI and the Intent API.
- Discovery uses CDP or LLDP crawling or IP ranges, with CLI, SNMP and NETCONF credentials, and populates inventory.
- The hierarchy is Global > Area > Building > Floor; settings and images set at a level are inherited below it.
- Templates (Velocity or Jinja2, regular or composite, Day-0 or Day-N) are committed, attached to network profiles and pushed during provisioning.
- SWIM: import, mark golden, readiness check, distribute, activate, with pre- and post-checks.
- PnP: an unconfigured device finds Catalyst Center by DHCP option 43, DNS `pnpserver.<domain>` or the PnP Connect cloud, is claimed to a site and receives its Day-0 configuration and image.
