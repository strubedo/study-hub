## SNMP building blocks

Simple Network Management Protocol lets a **manager** (the NMS) read and change values held by an **agent** on each device, and lets the agent send unsolicited **notifications** to the manager.

- **MIB** (Management Information Base): the tree of objects an agent exposes, each identified by an **OID** such as `1.3.6.1.2.1.1.5.0` (sysName). Interface counters live in IF-MIB (`ifHCInOctets` and friends).
- **Agent** listens on **UDP 161**; the manager listens for notifications on **UDP 162** (RFC 3417).
- **PDUs** (RFC 3416): `GetRequest`, `GetNextRequest`, `GetBulkRequest` (efficient table walks, v2c and v3 only), `SetRequest`, `Response`, `SNMPv2-Trap` (a notification with no acknowledgment) and `InformRequest` (a notification that the receiver acknowledges with a `Response`).

### Traps versus informs

| | Trap | Inform |
|---|---|---|
| Acknowledged | No | Yes, by a Response PDU |
| Retransmitted if lost | No | Yes, until acknowledged or retries run out |
| Cost on the device | Sent and forgotten | Held in memory until acknowledged |
| Versions | v1, v2c, v3 | v2c, v3 |

Informs are the reliable choice for important events across a lossy WAN; traps are lighter. Both normally go to UDP 162 on the receiver.

## Versions and security

| Version | Authentication | Encryption | Notes |
|---|---|---|---|
| SNMPv1 | Community string in clear text | None | 32-bit counters only; traps only |
| SNMPv2c | Community string in clear text | None | Adds GetBulk, informs and 64-bit counters (`ifHC*`) |
| SNMPv3 | User-based (USM, RFC 3414): HMAC with MD5 or SHA (SHA-2 on newer releases) | Optional: DES, 3DES or AES (128, 192, 256) | Access control by groups and views (VACM, RFC 3415) |

SNMPv3 defines three **security levels** (RFC 3411):

| Level | IOS keyword | Authentication | Privacy (encryption) |
|---|---|---|---|
| noAuthNoPriv | `noauth` | No (username match only) | No |
| authNoPriv | `auth` | Yes | No |
| authPriv | `priv` | Yes | Yes |

> **Exam tip:** "Authenticated and encrypted" is **authPriv**, keyword `priv`. A v2c community string is a password sent in clear text in every packet; anyone who captures a packet can read it.

### Views, groups and users (VACM)

SNMPv3 access control has three layers:

- A **view** lists OID subtrees that are included or excluded (`snmp-server view NOC-VIEW iso included`).
- A **group** sets the security model and level and says which view is used for **read**, **write** and **notify** (`snmp-server group NOC-GRP v3 priv read NOC-VIEW`).
- A **user** belongs to a group and has the authentication and privacy algorithms and passwords.

A request is allowed only if the user's security level meets the group's level and the OID is inside the relevant view. If a group has no write view, Sets fail even though Gets work.

## Configuring SNMPv2c

```text
SW1(config)# ip access-list standard SNMP-MGRS
SW1(config-std-nacl)# permit 10.10.10.50
SW1(config-std-nacl)# exit
SW1(config)# snmp-server community <COMMUNITY> RO SNMP-MGRS
SW1(config)# snmp-server location Building-A IDF-2
SW1(config)# snmp-server contact noc@example.com
SW1(config)# snmp-server host 10.10.10.50 version 2c <COMMUNITY>
SW1(config)# snmp-server enable traps snmp linkdown linkup
SW1(config)# snmp-server trap-source Loopback0
```

- `RO` allows Gets only; `RW` also allows Sets. Avoid `RW` with v2c.
- The ACL after `RO` limits which managers may use the community. Without it any host that knows the string can poll the device.
- `snmp-server host ... version 2c <COMMUNITY>` sends **traps** by default; add the `informs` keyword (`snmp-server host 10.10.10.50 informs version 2c <COMMUNITY>`) for informs.
- `snmp-server enable traps` with no arguments enables every trap type the platform supports; listing types keeps the volume sane.
- `snmp-server trap-source` fixes the source address of notifications, so the NMS always sees the device as the same IP.

## Configuring SNMPv3

```text
R1(config)# snmp-server view NOC-VIEW iso included
R1(config)# snmp-server group NOC-GRP v3 priv read NOC-VIEW access SNMP-MGRS
R1(config)# snmp-server user nocuser NOC-GRP v3 auth sha <AUTH-PASSWORD> priv aes 128 <PRIV-PASSWORD>
R1(config)# snmp-server host 10.10.10.50 version 3 priv nocuser
R1(config)# snmp-server enable traps snmp linkdown linkup
R1(config)# snmp-server trap-source Loopback0
```

Order matters: create the view, then the group that references it, then the user that joins the group. The `access` option on the group (or on the user) applies a standard ACL of permitted managers.

Points that cause most SNMPv3 problems:

- **Users are not shown in the running configuration.** The passwords are converted into keys localized to the device's **engine ID** (RFC 3414 key localization) and stored separately. Verify users with `show snmp user`, and keep the user commands in your build documentation.
- **Changing the engine ID** (`snmp-server engineID local ...`) invalidates the localized keys; the users must be configured again.
- **The levels must line up.** A group defined with `priv` rejects a manager that polls with authNoPriv; a user created without `priv` cannot satisfy a `priv` group.
- **Traps versus informs with v3.** The example sends traps. For a v3 **inform** the receiving manager is the authoritative side (RFC 3414), so the keys must be localized to the manager's engine ID: configure `snmp-server engineID remote 10.10.10.50 <manager-engine-id>`, a matching `snmp-server user nocuser NOC-GRP remote 10.10.10.50 v3 auth ... priv ...`, and then `snmp-server host 10.10.10.50 informs version 3 priv nocuser`.

## Verifying

```text
R1# show snmp user

User name: nocuser
Engine ID: 800000090300AABBCC000100
storage-type: nonvolatile        active
Authentication Protocol: SHA
Privacy Protocol: AES128
Group-name: NOC-GRP
```

```text
R1# show snmp group
groupname: NOC-GRP                          security model:v3 priv
contextname: <no context specified>         storage-type: nonvolatile
readview : NOC-VIEW                         writeview: <no writeview specified>
notifyview: <no notifyview specified>
row status: active      access-list: SNMP-MGRS
```

| Command | Shows |
|---|---|
| `show snmp` | Packet counters: input, `Unknown community name`, `Illegal operation for community name supplied`, Get/Set/Trap PDUs, and the logging destinations |
| `show snmp community` | Configured communities and their ACLs |
| `show snmp user` | v3 users, engine ID, auth and priv protocols, group |
| `show snmp group` | Groups, security model and level, read, write and notify views |
| `show snmp view` | View definitions |
| `show snmp host` | Notification receivers, version, traps or informs |
| `show snmp engineID` | Local (and configured remote) engine IDs |
| `debug snmp packets` | Each request and response (use with care) |

Reading `show snmp` counters is a quick diagnosis: a rising **Unknown community name** counter means a manager is polling with the wrong string; **Illegal operation for community name supplied** means a Set arrived for an RO community.

## Diagnosing SNMP problems

| Symptom | Likely cause |
|---|---|
| NMS times out; `show snmp` input counter does not move | Packets never reach the device: wrong IP, UDP 161 filtered, or the agent is polled through the wrong VRF |
| Input counter rises, `Unknown community name` rises | Wrong community string on the NMS |
| Gets work, Sets fail | Community is `RO`, or the v3 group has no write view |
| v3 polls fail with an authentication error | Wrong auth password or algorithm, or the users were lost after an engine ID change |
| v3 polls fail only from one manager | That manager is not in the group or community ACL |
| Traps not received | No `snmp-server host`, traps not enabled for that event, wrong trap source address filtered at the NMS, or UDP 162 blocked |

## Lab it yourself

Use one IOS XE router or Catalyst 9000v in Cisco Modeling Labs, GNS3 or EVE-NG (Windows, Linux or an Intel Mac; on an Apple silicon Mac use a remote x86 server or a DevNet sandbox), plus a Linux VM running the Net-SNMP tools (`snmpget`, `snmpwalk`, `snmptrapd`).

1. Configure v2c RO with an ACL permitting only the Linux VM, then `snmpwalk -v2c -c <COMMUNITY> 10.0.0.1 1.3.6.1.2.1.1`. Try a wrong string and watch `Unknown community name` rise in `show snmp`.
2. Configure the v3 view, group and user above. Poll with `snmpget -v3 -l authPriv -u nocuser -a SHA -A <AUTH-PASSWORD> -x AES -X <PRIV-PASSWORD> 10.0.0.1 1.3.6.1.2.1.1.5.0`. Repeat with `-l authNoPriv` and confirm it is rejected.
3. Run `snmptrapd` on the VM, configure `snmp-server host` with traps, shut and re-enable a loopback, and confirm the linkDown and linkUp notifications arrive. Switch to `informs` and compare `show snmp host`.
4. Check `show running-config | include snmp-server`: the user line is absent. Confirm it with `show snmp user`.

## Key takeaways

- Agent on UDP 161, notifications to UDP 162; GetBulk and informs arrived with v2c; informs are acknowledged and retransmitted, traps are not.
- v1 and v2c authenticate with a clear-text community; protect it with an ACL and prefer `RO`.
- SNMPv3 levels: noAuthNoPriv (`noauth`), authNoPriv (`auth`), authPriv (`priv`, authentication plus encryption).
- Build v3 in order: view, group (`snmp-server group NAME v3 priv read VIEW`), user (`snmp-server user NAME GROUP v3 auth sha ... priv aes 128 ...`), host.
- v3 users are not in the running configuration and are tied to the engine ID; verify with `show snmp user` and `show snmp group`.
- `show snmp` counters separate "nothing arrives" from "wrong community" from "Set on an RO community".
