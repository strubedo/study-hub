## What IP SLA does

**IP SLA** (Service Level Agreement) operations make the device generate synthetic test traffic on a schedule and measure the result: reachability, round-trip time, jitter, packet loss, connection time or DNS and HTTP response times. Two uses dominate:

- **Measurement**: track latency, jitter and loss over time (to prove or disprove an SLA, or to feed an NMS through the IP SLA MIBs).
- **Reaction**: tie an operation to a **track object**, and tie the track object to a static route, an FHRP priority, policy-based routing or an EEM applet, so the network reacts when a path fails even though the interface stays up.

## Operation types

| Operation | Command under `ip sla N` | Measures | Needs a responder? |
|---|---|---|---|
| ICMP echo | `icmp-echo <ip> [source-interface X \| source-ip A]` | Reachability, RTT | No, any host that answers ping |
| UDP jitter | `udp-jitter <ip> <port> [num-packets n] [interval ms]` | RTT, one-way jitter and loss, MOS with a codec | Yes, a Cisco IP SLA responder |
| UDP echo | `udp-echo <ip> <port>` | RTT over UDP | Responder, or a UDP echo service |
| TCP connect | `tcp-connect <ip> <port>` | Time to complete the TCP three-way handshake | No for a real server port; a responder can answer on any port |
| HTTP | `http get <url>` | DNS, TCP connect and HTTP transaction time | No |
| DNS | `dns <name> name-server <ip>` | Time to resolve the name | No |

### The responder

Operations that need precise timestamps or arbitrary ports (UDP jitter above all) run against an **IP SLA responder**: a Cisco device configured with

```text
R2(config)# ip sla responder
```

The sender first contacts the responder's control port (UDP 1967) to tell it which port to open, and the responder timestamps the probes on arrival and departure, so its processing time is removed from the results. One-way jitter and loss figures require it, and one-way delay additionally needs synchronized clocks (NTP) on both ends.

## Frequency, timeout and threshold

Each operation has three timers, all with defaults:

| Setting | Command | Default | Meaning |
|---|---|---|---|
| Frequency | `frequency <seconds>` | 60 s | How often the operation runs |
| Timeout | `timeout <milliseconds>` | 5000 ms | How long to wait for a reply before declaring failure |
| Threshold | `threshold <milliseconds>` | 5000 ms | RTT above which the result is "over threshold" (used by reaction and by `state` tracking) |

They must make sense together: **threshold ≤ timeout ≤ frequency** (with the frequency converted to milliseconds). A timeout longer than the frequency would make the next run start before the previous one could finish, and IOS XE rejects or warns about such a combination; a threshold above the timeout could never be reached. A common tracking setup is `frequency 5`, `timeout 1000`, `threshold 500` for a fast reaction to a dead path.

The ICMP echo default request size is 28 bytes of data (`show ip sla configuration` shows it as `Request size (ARR data portion): 28`); change it with `request-data-size` when you need to test larger packets.

## Scheduling

An operation does nothing until it is scheduled:

```text
R1(config)# ip sla schedule 10 life forever start-time now
```

- `life forever` keeps it running; the default life is 3600 seconds, after which the operation stops by itself and anything tracking it stops changing. Forgetting `life forever` is a classic "worked for an hour" fault.
- `start-time now` starts immediately; without a start time the operation stays **pending**. Other options are an absolute time (`start-time 06:00`), `after hh:mm:ss`, and `recurring` for a daily schedule.
- With the schedule in place, most settings of the operation cannot be edited; remove the schedule (`no ip sla schedule 10`) or delete and re-create the operation to change it.

## Tracking: turning a measurement into a decision

A **track object** follows the operation's result:

| Command | Track state Up when |
|---|---|
| `track 1 ip sla 10 reachability` | The latest operation return code is OK **or** over threshold (the target answers) |
| `track 1 ip sla 10 state` | The latest return code is OK only (answers **and** below the threshold) |

Damping avoids flapping on single lost probes:

```text
R1(config)# track 1 ip sla 10 reachability
R1(config-track)# delay down 15 up 30
```

`delay down 15` waits 15 seconds of continuous failure before the track goes Down; `delay up 30` waits 30 seconds of success before it comes back Up.

### Example: failover of a default route

R1 has two ISPs. The primary default route must be removed when 203.0.113.1, the ISP's gateway, stops answering pings sourced from the primary WAN interface, and a floating static via the backup ISP must take over.

```text
R1(config)# ip sla 10
R1(config-ip-sla)# icmp-echo 203.0.113.1 source-interface GigabitEthernet0/0/0
R1(config-ip-sla-echo)# frequency 5
R1(config-ip-sla-echo)# timeout 1000
R1(config-ip-sla-echo)# threshold 500
R1(config-ip-sla-echo)# exit
R1(config)# ip sla schedule 10 life forever start-time now
R1(config)# track 1 ip sla 10 reachability
R1(config-track)# delay down 15 up 30
R1(config-track)# exit
R1(config)# ip route 0.0.0.0 0.0.0.0 203.0.113.1 track 1
R1(config)# ip route 0.0.0.0 0.0.0.0 198.51.100.1 10
```

While track 1 is Up, the primary static (administrative distance 1) is installed. When track 1 goes Down, IOS removes it and the floating static with distance 10 is installed. When the track returns Up, the primary route comes back.

> **Watch out:** Here the target, 203.0.113.1, is on R1's directly connected /30, so the connected route always keeps the probe on the primary link; the price is that a failure beyond the ISP's first router is not detected. Many designs probe something further away instead (for example a public server such as 192.0.2.1). Such a target is reached through the **default route**, so after failover the probe starts leaving through the backup ISP, may succeed, and brings the primary route back: the route flaps. Protect it with `source-interface` on the operation **and** a static host route for the target via the primary next hop (`ip route 192.0.2.1 255.255.255.255 203.0.113.1`), so the probe can only use the primary path.

### Example: lowering HSRP priority

```text
R1(config)# interface GigabitEthernet0/0/1
R1(config-if)# standby 1 ip 10.1.10.1
R1(config-if)# standby 1 priority 110
R1(config-if)# standby 1 preempt
R1(config-if)# standby 1 track 1 decrement 20
```

When track 1 goes Down, R1's priority drops to 90, below the standby router's 100, and (with preemption on the peer) the peer becomes active. The same track object can drive VRRP (`track 1 decrement 20` in the VRRPv3 group) and PBR (`set ip next-hop verify-availability ... track 1`).

## Lab it yourself

In Cisco Modeling Labs, GNS3 or EVE-NG (Windows, Linux or an Intel Mac; on an Apple silicon Mac use a remote x86 server or a DevNet sandbox), connect R1 to two "ISP" routers (ISP1 203.0.113.1/30, ISP2 198.51.100.1/30), both connected to an "Internet" router with a loopback 192.0.2.1/32.

1. Build the ICMP echo operation, schedule, track and the two default routes above. Check `show ip route 0.0.0.0`.
2. Make the probes fail while R1's interface stays up: on ISP1, apply an inbound extended ACL on its R1-facing interface with `deny icmp any any` and `permit ip any any`. Watch `show track 1` go Down after 15 seconds and the floating route appear; remove the ACL and watch the primary route return after 30 seconds.
3. Unschedule the operation (`no ip sla schedule 10`), re-create it with target 192.0.2.1 and no `source-interface`, and reschedule it. Shut ISP1's link toward the Internet router and note whether the default route flaps. Then add `source-interface GigabitEthernet0/0/0` and `ip route 192.0.2.1 255.255.255.255 203.0.113.1`, and repeat.
4. Configure `ip sla responder` on the Internet router and a `udp-jitter 192.0.2.1 16384 num-packets 20 interval 20` operation on R1; read `show ip sla statistics` for jitter and loss.
5. Change track 1 to `state` and set the threshold below the measured RTT: observe the difference between `reachability` and `state`.

## Key takeaways

- IP SLA operations (icmp-echo, udp-jitter, udp-echo, tcp-connect, http, dns) generate test traffic; udp-jitter needs `ip sla responder` on the far Cisco device (control port UDP 1967).
- Defaults: frequency 60 s, timeout 5000 ms, threshold 5000 ms, life 3600 s; keep threshold ≤ timeout ≤ frequency.
- Nothing runs until `ip sla schedule N life forever start-time now`; without `life forever` the operation stops after an hour.
- `track N ip sla M reachability` is Up for OK or over-threshold; `state` is Up only for OK. `delay down/up` damps flapping.
- Use the track with `ip route ... track N` plus a floating static, or `standby G track N decrement D`.
- Verify with `show ip sla summary`, `show ip sla statistics`, `show ip sla configuration`, `show track`.
