## What ERSPAN adds

**Encapsulated Remote SPAN (ERSPAN)** mirrors traffic like SPAN but wraps every copied frame in **GRE** and routes it as an ordinary IP packet to a destination anywhere on the network: a data-center analyzer, a cloud sensor, or another Cisco device that strips the encapsulation and sends the original frames out of a local port. Nothing in the path needs to know about the mirroring; it only needs IP reachability.

## The encapsulation

ERSPAN is a Cisco protocol, documented in the IETF informational draft draft-foschiano-erspan. The copy of the original Ethernet frame (without its FCS) is carried as:

```text
| Outer Ethernet 14 | Outer IPv4 20 (protocol 47) | GRE 8 | ERSPAN type II 8 | Original frame ... | FCS 4 |
```

| Field | Detail |
|---|---|
| IP protocol | 47 (GRE) |
| GRE protocol type | 0x88BE for ERSPAN type II, 0x22EB for type III |
| GRE header | 8 bytes for type II: the sequence-number bit is set and a per-session sequence number follows |
| ERSPAN header | Type II: 8 bytes with version, original VLAN, CoS, truncation bit and a **10-bit session ID** (the ERSPAN ID, 1 to 1023 in IOS XE). Type III: 12 bytes plus optional fields, adding a timestamp and more metadata |
| Overhead | 50 bytes for type II (14 + 20 + 8 + 8) on top of the original frame, plus the new FCS |

The **ERSPAN ID** identifies the session inside the GRE packets, so a destination can receive several ERSPAN streams and deliver each to the right port. The source and destination must use the **same ID**.

> **Watch out:** A full-size frame (a 1500-byte IP packet plus its 14-byte Ethernet header) becomes a 1550-byte IP packet once encapsulated (20 + 8 + 8 + 1514). If the path MTU is 1500, the copies are fragmented or dropped. Either raise the MTU on the path, accept truncated copies (the ERSPAN `mtu` setting truncates mirrored frames to that size), or mirror only the traffic you need.

## Configuring an ERSPAN source session

The source session lives on the device where the traffic is (a Catalyst 9000 switch or an ISR 4000 / Catalyst 8000 router). It uses the session type `erspan-source` and a nested `destination` submode:

```text
SW1(config)# monitor session 10 type erspan-source
SW1(config-mon-erspan-src)# description Copy server port to DC analyzer
SW1(config-mon-erspan-src)# source interface GigabitEthernet1/0/5 both
SW1(config-mon-erspan-src)# destination
SW1(config-mon-erspan-src-dst)# erspan-id 110
SW1(config-mon-erspan-src-dst)# ip address 10.50.0.10
SW1(config-mon-erspan-src-dst)# origin ip address 10.255.0.11
SW1(config-mon-erspan-src-dst)# exit
SW1(config-mon-erspan-src)# no shutdown
```

| Line | Meaning |
|---|---|
| `source interface ... [rx\|tx\|both]`, `source vlan ...` | What to mirror, as in local SPAN |
| `filter vlan`, `filter ip access-group` | Limit what is mirrored |
| `erspan-id 110` | Session ID carried in the ERSPAN header (1 to 1023) |
| `ip address 10.50.0.10` | **Destination** of the GRE packets: the analyzer, or the ERSPAN destination device |
| `origin ip address 10.255.0.11` | **Source** address of the GRE packets; normally a loopback on this device that the destination can route back to |
| Optional | `ip ttl`, `ip dscp` (mark the copies so QoS can deprioritize them), `mtu` (truncation size), `vrf` (route the copies in a VRF), `header-type 3` (type III, where supported) |
| `no shutdown` | ERSPAN sessions are created **shut down**; nothing is sent until you enable them |

> **Exam tip:** In the source session, `ip address` is where the copies **go** and `origin ip address` is where they **come from**. The `no shutdown` is easy to forget: a perfectly configured ERSPAN source session sends nothing while it is administratively disabled.

## Configuring an ERSPAN destination session

If the receiver is a capture appliance or Wireshark host, no destination session is needed: the analyzer receives the GRE packets on its own IP address and decodes ERSPAN directly. When the receiver is a Cisco device that should hand plain frames to a local analyzer port, configure an `erspan-destination` session there:

```text
R5(config)# monitor session 20 type erspan-destination
R5(config-mon-erspan-dst)# destination interface GigabitEthernet0/0/2
R5(config-mon-erspan-dst)# source
R5(config-mon-erspan-dst-src)# erspan-id 110
R5(config-mon-erspan-dst-src)# ip address 10.50.0.10
R5(config-mon-erspan-dst-src)# exit
R5(config-mon-erspan-dst)# no shutdown
```

Here the nested `source` submode describes the stream to accept: `ip address` is this device's own address that the source session sends to (it must match the source session's `ip address`), and `erspan-id` must match too. The device decapsulates the packets and sends the original frames out of Gi0/0/2.

Platform note: ERSPAN source sessions are widely supported on Catalyst 9000 switches and IOS XE routers; ERSPAN **destination** sessions are supported on IOS XE routers and only on some switch models and releases. Check the platform guide before designing a switch-to-switch ERSPAN.

## Verifying

On a router, the source and destination sessions look like this:

```text
R1# show monitor session 10
Session 10
----------
Type                   : ERSPAN Source Session
Status                 : Admin Enabled
Source Ports           :
    Both               : Gi0/0/1
Destination IP Address : 10.50.0.10
MTU                    : 1464
Destination ERSPAN ID  : 110
Origin IP Address      : 10.255.0.1
```

```text
R5# show monitor session 20
Session 20
----------
Type                   : ERSPAN Destination Session
Status                 : Admin Enabled
Destination Ports      : Gi0/0/2
Source IP Address      : 10.50.0.10
Source ERSPAN ID       : 110
MTU                    : 1464
```

`Status : Admin Disabled` means the session is still shut down. A Catalyst 9000 shows the same fields in its own layout; `show monitor session 10 detail` lists every option.

Further checks:

- `ping 10.50.0.10 source Loopback0` from the source device: the GRE packets follow the same route.
- A capture on the analyzer filtered on `ip proto 47` (or the Wireshark display filter `erspan`) shows the session ID in the ERSPAN header.
- ACLs or firewalls in the path must permit IP protocol 47 between the origin and destination addresses.

## SPAN, RSPAN and ERSPAN side by side

| | Local SPAN | RSPAN | ERSPAN |
|---|---|---|---|
| Copies carried by | Switch fabric | RSPAN VLAN on trunks | GRE (IP protocol 47) |
| Source command | `monitor session N source ...` | Same, plus `destination remote vlan V` | `monitor session N type erspan-source`, `source ...` |
| Destination command | `monitor session N destination interface ...` | `source remote vlan V` + `destination interface ...` on the far switch | `destination` submode: `erspan-id`, `ip address`, `origin ip address`; optional `type erspan-destination` on the receiver |
| Reach | One switch or stack | One Layer 2 domain | Any routed network |
| Typical gotcha | Destination oversubscribed | VLAN missing on one trunk | Session left shut down; MTU |

## Lab it yourself

In Cisco Modeling Labs, GNS3 or EVE-NG (Windows, Linux or an Intel Mac; on an Apple silicon Mac use a remote x86 server or a DevNet sandbox), use two Catalyst 8000V routers joined through a third router so the path is routed, with OSPF advertising their loopbacks. Put a Linux host behind R1 Gi2 and a Linux analyzer behind R5 Gi3.

1. On R1, build `monitor session 10 type erspan-source` copying Gi2 `both` to R5's loopback with ERSPAN ID 110 and origin Loopback0. Leave it shut down and check `show monitor session 10` (Admin Disabled), then `no shutdown`.
2. First, with no destination session, capture on R5's ingress interface (`monitor capture` on R5 or a capture on the link) and confirm GRE packets with ERSPAN ID 110.
3. Build `monitor session 20 type erspan-destination` on R5 delivering to Gi3, and capture plain frames on the analyzer with `tcpdump -n`.
4. Change the ERSPAN ID on one side only and confirm the copies stop reaching the analyzer.
5. With the transit links at the default 1500-byte MTU, send 1500-byte pings from the host with DF set: observe what happens to the copies, then try the `mtu` option on the source session.

## Key takeaways

- ERSPAN mirrors traffic inside GRE (IP protocol 47; GRE type 0x88BE for type II, 0x22EB for type III), so copies cross any routed network.
- Type II adds 50 bytes (outer Ethernet 14, IP 20, GRE 8, ERSPAN 8); mind the path MTU or let the session truncate copies.
- Source: `monitor session N type erspan-source`, `source interface ...`, then `destination` with `erspan-id`, `ip address` (where copies go) and `origin ip address` (where they come from), then `no shutdown`.
- Destination device (optional): `monitor session M type erspan-destination`, `destination interface ...`, `source` with matching `erspan-id` and its own `ip address`.
- Sessions start shut down; `show monitor session N` shows Admin Enabled or Disabled, the IPs, the ERSPAN ID and the MTU.
