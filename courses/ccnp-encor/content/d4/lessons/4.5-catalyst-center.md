## What Catalyst Center is

**Cisco Catalyst Center** (formerly **Cisco DNA Center**; the rename came in 2023, and the API still lives under `/dna/...` URLs) is Cisco's controller and management platform for enterprise campus and branch networks: Catalyst switches, routers and the wireless network. It runs as a dedicated appliance (single node or a three-node cluster for high availability) or as a virtual appliance, and it replaces box-by-box CLI work with a central, policy-driven system.

It does three jobs that the exam topic names directly:

- **Configuration**: build the network design once (sites, settings, templates, images) and push it to devices.
- **Monitoring**: collect telemetry from every device and client, score health, raise issues and help troubleshoot (Assurance).
- **Management**: inventory, software images, compliance, onboarding and lifecycle.

### How it talks to the network and to you

| Direction | Interfaces |
|---|---|
| **Southbound** (to devices) | SSH CLI, SNMP, NETCONF; devices stream telemetry, syslog, SNMP traps and NetFlow back for Assurance |
| **Northbound** (to people and programs) | The GUI, and the **Intent API**: a REST API with JSON bodies over HTTPS (`/dna/intent/api/v1/...`), with Python SDK, Ansible and Terraform support |
| **Eastbound** | Events and notifications (webhooks, email, syslog) when issues or tasks occur |
| **Westbound** | Integrations: Cisco ISE for identity and policy, IT service management (ITSM) systems such as ServiceNow, IPAM |

> **Exam tip:** "Northbound" is how applications and people talk **to** the controller (the Intent API); "southbound" is how the controller talks **to** devices. The Intent API is a REST API: HTTPS, standard verbs (GET, POST, PUT, DELETE), JSON, and a token obtained from `/dna/system/api/v1/auth/token` with basic authentication. Domain 6 of the exam covers the API in more depth.

## Intent-based networking and the workflow areas

Catalyst Center is Cisco's implementation of **intent-based networking**: the operator states the desired outcome ("guests get internet only, voice gets priority"), the controller translates it into device configuration, and Assurance continuously verifies that the network delivers it. The GUI is organized around that loop:

| Area | What you do there |
|---|---|
| **Design** | Build the **network hierarchy** (areas, buildings, floors), define **network settings** (AAA, DNS, DHCP, NTP, syslog and SNMP servers, banners), **IP address pools**, **image repository** and golden images, and network profiles that bind templates to sites |
| **Policy** | Define intent as policy: group-based access control with scalable groups (with Cisco ISE), virtual networks for SD-Access, application policies (QoS by business relevance), traffic copy policies |
| **Provision** | Discover and add devices, assign them to sites, push settings and templates, onboard new devices with Plug and Play, update software, build SD-Access fabrics |
| **Assurance** | Monitor health of network, devices, clients and applications; issues with suggested actions; troubleshooting tools such as path trace; AI-driven insights |
| **Platform** | The Intent API catalogue, bundles and integrations (ITSM, IPAM), event notifications, developer toolkit |

On recent releases the GUI menu groups these differently (for example Design, Policy, Provision, Assurance, Workflows, Tools, Platform, Activities and System), but the intent loop is the same and it is what the exam asks about.

## Assurance: monitoring and troubleshooting

Assurance is where the "monitoring" part of the exam topic lives. Devices send data (syslog, SNMP, streaming telemetry, NetFlow, wireless controller statistics), and Catalyst Center correlates it.

- **Health scores**: every device, client, site and application gets a score from 1 to 10. Scores 8 to 10 are **good**; lower scores fall into fair and poor ranges and are colored accordingly. The overall network health is the share of healthy devices, broken down by layer (access, distribution, core, router, wireless) and site. Health score thresholds are adjustable per device type.
- **Issues**: detected problems (an interface flapping, high CPU, an AP rebooting, clients failing to onboard) with priority (P1 to P4), status (active, resolved, ignored), the affected devices and clients, the root-cause description and **suggested actions**, often including CLI commands to run with one click.
- **Device 360** and **Client 360**: a single page per device or client with its health over time, issues, physical and logical neighbors, onboarding path (for a client: AP or switch port, VLAN, IP, authentication), and application experience. You can move back in time to see what a client experienced at a given moment.
- **Path trace**: enter a source and destination (and optionally protocol and ports), and Catalyst Center calculates the hop-by-hop path from its knowledge of the topology, routing and forwarding tables, and shows ACLs that could block it, with optional interface, QoS and device statistics along the path.
- **Application experience**: per-application health using NBAR and performance data.
- **Sensors** (wireless): synthetic client tests, mentioned for completeness; v1.2 has no wireless section.

> **Real world:** Assurance is only as good as its data. Devices must be **Managed** in inventory, reachable over SNMP and SSH (or NETCONF), and configured to send telemetry and syslog to Catalyst Center. Catalyst Center normally configures that telemetry itself when a device is assigned to a site and provisioned with the telemetry settings.

## How it differs from managing devices one by one

| Box-by-box (CLI) | Catalyst Center |
|---|---|
| Each device configured separately; consistency depends on the engineer | Settings and templates applied by site, inherited down the hierarchy |
| Monitoring by separate SNMP/syslog/NetFlow tools | One system correlating all telemetry into health and issues |
| Software upgrades scheduled and run per device | Golden image per device family and site, readiness checks, staged distribution and activation |
| New devices staged by hand | Plug and Play zero-touch onboarding |
| Troubleshooting from memory and show commands | Issues with root cause and suggested actions, path trace, Device and Client 360 |

## Lab it yourself

You cannot run Catalyst Center on a laptop (the appliance needs dozens of cores and hundreds of GB of RAM), so use the **Cisco DevNet always-on or reservable Catalyst Center sandboxes** from any browser on Windows, macOS or Linux.

1. Log in to the sandbox GUI and identify the Design, Policy, Provision, Assurance and Platform areas in the menu.
2. In Design, open the network hierarchy and note which settings each site inherits from its parent.
3. In Assurance, open the overall health dashboard, then a Device 360 page, and read one open issue with its suggested actions.
4. Run a path trace between two hosts in the sandbox topology and note which hops and ACLs it shows.
5. In Platform, open the API catalogue and find the network-device and site-health APIs.

## Key takeaways

- Catalyst Center (formerly DNA Center) is the controller for campus and branch: configuration, monitoring (Assurance) and management, on an appliance, cluster or virtual appliance.
- Southbound: SSH, SNMP, NETCONF and device telemetry. Northbound: the GUI and the REST **Intent API** (HTTPS, JSON, token authentication).
- Intent-based workflow areas: **Design** (hierarchy, settings, pools, images), **Policy** (group-based access, virtual networks, application policy), **Provision** (discover, assign, push, PnP, SWIM, fabric), **Assurance** (health, issues, 360 views, path trace), **Platform** (APIs and integrations).
- Health scores run 1 to 10, with 8 to 10 good; issues carry priority, root cause and suggested actions.
- Device 360, Client 360 and path trace replace much of the manual show-command troubleshooting.
