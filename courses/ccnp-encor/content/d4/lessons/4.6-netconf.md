## NETCONF in one paragraph

**NETCONF** (RFC 6241) is a protocol for reading and changing device configuration and state as **structured data** instead of CLI text. The data is described by **YANG** models (RFC 7950), encoded in **XML**, and carried over **SSH on TCP port 830** (RFC 6242). Because every request and reply is structured and validated against a model, a script can make a change, get an exact error if something is wrong, and use transactions, locks and a candidate configuration, none of which screen-scraping the CLI can offer.

## The four layers

RFC 6241 describes NETCONF as four layers:

| Layer | Contents | Example |
|---|---|---|
| Content | The configuration or state data, structured by YANG models | `<native xmlns="http://cisco.com/ns/yang/Cisco-IOS-XE-native"><hostname>R1</hostname></native>` |
| Operations | The actions | `<get>`, `<get-config>`, `<edit-config>`, `<lock>`, `<commit>` |
| Messages | Framing of requests, replies and events | `<rpc>`, `<rpc-reply>`, `<notification>` |
| Secure transport | The encrypted session | SSH (port 830) on IOS XE; TLS is also defined by the standards |

## Datastores

A datastore is a complete copy of the configuration that NETCONF can read or write:

| Datastore | Purpose | IOS XE |
|---|---|---|
| `running` | The active configuration | Always present; writable unless the platform says otherwise |
| `candidate` | A scratch copy; edits take effect only on `<commit>` | Optional: `netconf-yang feature candidate-datastore` |
| `startup` | Configuration loaded at boot | Not exposed as a datastore by default; save with `copy running-config startup-config` or Cisco's save-config RPC |

The **candidate** model gives transactions: several `<edit-config>` operations accumulate in the candidate, `<validate>` checks them, `<commit>` applies them together to running, and `<discard-changes>` throws them away. With the `:confirmed-commit` capability a commit can be automatically rolled back unless confirmed within a timeout, which protects against locking yourself out.

## Session start: the hello and capabilities

When the SSH session opens (the client requests the `netconf` SSH subsystem), **both sides immediately send a `<hello>`** listing their **capabilities**; the server's hello also carries the `session-id`. Capabilities tell the client which protocol versions, optional features and YANG modules the server supports.

```text
<?xml version="1.0" encoding="UTF-8"?>
<hello xmlns="urn:ietf:params:xml:ns:netconf:base:1.0">
  <capabilities>
    <capability>urn:ietf:params:netconf:base:1.0</capability>
    <capability>urn:ietf:params:netconf:base:1.1</capability>
    <capability>urn:ietf:params:netconf:capability:writable-running:1.0</capability>
    <capability>urn:ietf:params:netconf:capability:xpath:1.0</capability>
    <capability>urn:ietf:params:netconf:capability:validate:1.1</capability>
    <capability>urn:ietf:params:netconf:capability:rollback-on-error:1.0</capability>
    <capability>http://cisco.com/ns/yang/Cisco-IOS-XE-native?module=Cisco-IOS-XE-native&amp;revision=...</capability>
    <!-- several hundred more YANG module capabilities -->
  </capabilities>
  <session-id>24</session-id>
</hello>]]>]]>
```

- If both sides list `base:1.1`, they switch to **chunked framing** after the hello; with only `base:1.0`, every message ends with the `]]>]]>` delimiter.
- The `:candidate` capability appears only when the candidate datastore is enabled; check the hello before your script tries to `<commit>`.
- Each YANG module appears as a capability URI with `module=` and `revision=`; that is how a client discovers the models.

## Operations

| Operation | Does |
|---|---|
| `<get>` | Retrieves running configuration **and operational state** (counters, status), optionally filtered |
| `<get-config>` | Retrieves configuration only, from a named datastore (`running`, `candidate`), optionally filtered |
| `<edit-config>` | Loads configuration into a target datastore |
| `<copy-config>` | Replaces a whole datastore with another or with supplied content |
| `<delete-config>` | Deletes a datastore (never `running`) |
| `<lock>` / `<unlock>` | Takes or releases an exclusive lock on a datastore so no other session or CLI user changes it meanwhile |
| `<commit>` / `<discard-changes>` / `<validate>` | Candidate datastore operations |
| `<close-session>` / `<kill-session>` | Ends this session gracefully, or forces another session closed |

Filters are usually **subtree filters**: an XML skeleton of the part you want (`<native><hostname/></native>`). XPath filters are possible when the server advertises `:xpath`.

### edit-config operations

Inside `<edit-config>`, the `operation` attribute on an element says what to do with that part of the tree, and `<default-operation>` sets the default for the whole request (`merge` unless changed):

| `operation=` | Effect | If it already exists / does not exist |
|---|---|---|
| `merge` (default) | Merge the supplied data into the existing configuration | Updated / created |
| `replace` | Replace the related configuration with the supplied data only | Replaced / created |
| `create` | Add the data | Error `data-exists` / created |
| `delete` | Remove the data | Removed / error `data-missing` |
| `remove` | Remove the data | Removed / silently ignored |

> **Exam tip:** `create` and `delete` are strict (they fail with `data-exists` or `data-missing`); `merge`, `replace` and `remove` are tolerant. `replace` on an interface element removes any of that interface's settings that you did not include.

A reply is either `<ok/>` inside `<rpc-reply>` or an `<rpc-error>` with `error-type`, `error-tag` (for example `data-exists`, `access-denied`, `in-use`) and a message.

## Enabling NETCONF on IOS XE

```text
R1(config)# aaa new-model
R1(config)# aaa authentication login default local
R1(config)# aaa authorization exec default local
R1(config)# username netops privilege 15 secret ExamplePass123
R1(config)# ip domain name example.com
R1(config)# crypto key generate rsa modulus 2048
R1(config)# ip ssh version 2
R1(config)# netconf-yang
R1(config)# netconf-yang feature candidate-datastore
```

- `netconf-yang` starts the NETCONF server (the yang-management processes) on TCP 830. It takes a minute or two to come up after the command.
- NETCONF on IOS XE requires **`aaa new-model`** and a user who is authorized at **privilege level 15** (locally or through TACACS+/RADIUS). The password in this example is a placeholder: use your own secret.
- SSH must work (RSA keys, SSH version 2), because NETCONF runs as an SSH subsystem.
- `netconf-yang feature candidate-datastore` is optional; without it clients edit `running` directly. Once it is enabled, write through the candidate (lock, edit, commit) and check the new hello before assuming `running` is still a writable target; the sample script below edits `running`, so run it before enabling the feature.
- If NETCONF is reached through a management VRF or ACL, make sure TCP 830 is allowed.

| Command | Shows |
|---|---|
| `show netconf-yang status` | Enabled or not, candidate datastore, SSH port |
| `show platform software yang-management process` | The DMI processes: `confd`, `ncsshd` (NETCONF SSH), `dmiauthd`, `nginx` (RESTCONF), `syncfd` (keeps CLI and the data store in sync) and others; all needed ones must be Running |

| `show netconf-yang datastores` | `running`, plus `candidate` when enabled |

`gnmib : Not Running` is normal unless gNMI is configured.

## A Python client with ncclient

```python
from ncclient import manager

HOST = "192.0.2.10"           # R1 management address (documentation range)
USER = "netops"
PASSWORD = "ExamplePass123"   # example only: load real credentials from a vault

NATIVE = "http://cisco.com/ns/yang/Cisco-IOS-XE-native"

HOSTNAME_FILTER = f"""
<native xmlns="{NATIVE}">
  <hostname/>
</native>
"""

LOOPBACK_CONFIG = f"""
<config>
  <native xmlns="{NATIVE}">
    <interface>
      <Loopback>
        <name>100</name>
        <description>Managed by NETCONF</description>
        <ip>
          <address>
            <primary>
              <address>10.100.100.1</address>
              <mask>255.255.255.255</mask>
            </primary>
          </address>
        </ip>
      </Loopback>
    </interface>
  </native>
</config>
"""

with manager.connect(host=HOST, port=830, username=USER, password=PASSWORD,
                     hostkey_verify=False) as m:
    print("Session ID:", m.session_id)
    for cap in m.server_capabilities:
        if "candidate" in cap or "writable-running" in cap:
            print(cap)

    reply = m.get_config(source="running", filter=("subtree", HOSTNAME_FILTER))
    print(reply.xml)

    result = m.edit_config(target="running", config=LOOPBACK_CONFIG)
    print("edit-config ok:", result.ok)
```

What happens on the wire: SSH to port 830 and the `netconf` subsystem, hello exchange (the script prints two of the server's capabilities), a `<get-config>` with a subtree filter that returns only the hostname, then an `<edit-config>` with the default `merge` operation that creates or updates Loopback100. With the candidate datastore enabled you would instead lock it, `edit_config(target="candidate", ...)`, `commit()` and unlock. `hostkey_verify=False` is acceptable only in a lab.

## Lab it yourself

Use a Catalyst 8000V (or a Catalyst 9000v) in Cisco Modeling Labs, GNS3 or EVE-NG (Windows, Linux or an Intel Mac; on an Apple silicon Mac use a remote x86 server or the Cisco DevNet IOS XE always-on or reservable sandbox), plus a workstation (Windows, macOS or Linux) with Python 3 and `pip install ncclient`.

1. Apply the configuration above **without** the last line (`netconf-yang feature candidate-datastore`; step 5 adds it) and wait until `show platform software yang-management process` lists the processes as Running.
2. From the workstation run `ssh -p 830 netops@<router> -s netconf` and read the hello and note which `urn:ietf:params:netconf:capability:` lines it lists (you compare them again after step 5).
3. Run the ncclient script. Check `show running-config interface Loopback100` and `show netconf-yang sessions` while it runs.
4. Change the edit to `operation="create"` on the `Loopback` element and run it again: read the `data-exists` error. Then try `operation="delete"` twice and read `data-missing`.
5. Enable the candidate datastore with `netconf-yang feature candidate-datastore`, read the new hello (`:candidate` now appears; check whether `:writable-running` is still listed), and rewrite the script to lock, edit candidate, commit and unlock; confirm in `show netconf-yang sessions` that the lock appears while the script holds it.

## Key takeaways

- NETCONF (RFC 6241) = XML data modelled in YANG (RFC 7950), over SSH on TCP 830 (RFC 6242); layers are content, operations, messages and secure transport.
- Both sides send `<hello>` with capabilities first; the server adds the `session-id`; `base:1.1` on both sides switches to chunked framing.
- Operations: `get` (config and state), `get-config` (config from a datastore), `edit-config` (`merge` default, `replace`, `create`, `delete`, `remove`), `copy-config`, `lock`/`unlock`, `commit` with the candidate datastore, `close-session`.
- IOS XE: `aaa new-model`, a privilege 15 user, SSH, `netconf-yang`; optional `netconf-yang feature candidate-datastore`.
- Verify with `show netconf-yang status`, `show netconf-yang sessions`, `show platform software yang-management process`.
