## Severity levels

Every IOS XE log message carries a severity from 0 (most severe) to 7 (least severe). The numbers and meanings come from the syslog standard (RFC 5424, which keeps the values of the older BSD syslog, RFC 3164); IOS uses its own keyword for each level in commands.

| Level | RFC 5424 name | IOS keyword | Typical IOS XE example |
|---|---|---|---|
| 0 | Emergency | `emergencies` | System unusable |
| 1 | Alert | `alerts` | Immediate action needed, for example a temperature or power alarm |
| 2 | Critical | `critical` | Critical condition, for example a hardware failure |
| 3 | Error | `errors` | `%LINK-3-UPDOWN` interface physically down |
| 4 | Warning | `warnings` | `%IP-4-DUPADDR` duplicate address |
| 5 | Notice | `notifications` | `%LINEPROTO-5-UPDOWN`, `%OSPF-5-ADJCHG`, `%SYS-5-CONFIG_I` |
| 6 | Informational | `informational` | `%SEC-6-IPACCESSLOGP` ACL log entries |
| 7 | Debug | `debugging` | All `debug` output |

A logging threshold includes its own level and **everything more severe** (lower number). `logging trap warnings` sends levels 0 to 4; `logging buffered informational` stores 0 to 6. You can give the number instead of the keyword (`logging trap 4`).

A common memory aid for the order 0 to 7: "**E**very **A**wesome **C**isco **E**ngineer **W**ill **N**eed **I**ce cream **D**aily".

> **Exam tip:** Expect questions that give a message and a threshold and ask whether the message is sent. `%LINEPROTO-5-UPDOWN` is level 5, so it is **not** sent with `logging trap warnings` (level 4) but is sent with `logging trap notifications` or anything numerically higher.

## Message format

```text
000123: *Nov 23 10:14:55.871 UTC: %LINEPROTO-5-UPDOWN: Line protocol on Interface GigabitEthernet1/0/5, changed state to down
```

| Part | Meaning |
|---|---|
| `000123:` | Sequence number, present only with `service sequence-numbers` |
| `*Nov 23 10:14:55.871 UTC:` | Timestamp, format set by `service timestamps log ...`. A leading `*` means the clock is not authoritative (not synchronized, for example no NTP) |
| `%LINEPROTO` | **Facility**: the IOS component that raised the message (LINK, LINEPROTO, OSPF, SYS, SEC, IP ...) |
| `-5-` | Severity |
| `UPDOWN` | **Mnemonic**: a short code for the specific message |
| text | The description |

The pattern is `%FACILITY-SEVERITY-MNEMONIC: description`. Do not confuse the IOS **facility** in the message (the component, such as `OSPF`) with the syslog protocol **facility** that the device stamps on packets it sends to a server (`local7` by default on IOS, changeable with `logging facility local5`). The server uses that protocol facility to sort messages into files.

On the wire, the syslog header carries a priority value **PRI = facility x 8 + severity** (RFC 5424). With facility local7 (23), a severity 3 message has PRI 23 x 8 + 3 = 187, written `<187>` at the start of the message.

## Logging destinations and their thresholds

| Destination | Configure | Notes |
|---|---|---|
| Console | `logging console <level>` | On by default at debugging; turn it down or off on busy devices (`no logging console`) |
| VTY sessions | `logging monitor <level>` and `terminal monitor` per session | Without `terminal monitor` an SSH session shows nothing |
| Buffer (RAM) | `logging buffered [size] [level]` | Read with `show logging`; lost on reload; `clear logging` empties it |
| Syslog servers | `logging host <ip>` and `logging trap <level>` | `logging trap` defaults to informational |
| Persistent storage | `logging persistent ...` (platform-dependent) | Survives a reload |

## Configuring syslog

```text
R1(config)# service timestamps log datetime msec localtime show-timezone
R1(config)# service timestamps debug datetime msec localtime show-timezone
R1(config)# service sequence-numbers
R1(config)# logging buffered 64000 informational
R1(config)# logging console warnings
R1(config)# logging host 10.10.10.60
R1(config)# logging host 10.10.10.61 transport tcp port 1514
R1(config)# logging trap notifications
R1(config)# logging facility local6
R1(config)# logging source-interface Loopback0
R1(config)# logging origin-id hostname
```

- **`logging host <ip>`** sends to UDP 514 by default (the syslog-over-UDP port, RFC 5426). The `transport tcp port <n>` or `transport udp port <n>` options change it. Use `logging host <ip> vrf Mgmt-intf` when the server is reached through a management VRF.
- **`logging trap <level>`** applies to all configured hosts. Messages above the threshold (numerically higher) are not sent.
- **`logging source-interface Loopback0`** makes every message leave from the loopback address. Without it the source is the egress interface, which changes when routing changes and breaks server-side filters keyed on the device address.
- **`service timestamps log datetime msec localtime show-timezone`** uses the device clock with milliseconds and the time zone. The default form on many releases stamps messages with uptime or without milliseconds; datetime stamps are useless unless the clock is right, so pair them with NTP.
- **`service sequence-numbers`** numbers every message, so you can spot gaps (dropped or rate-limited messages) when comparing the buffer with the server.
- **`logging origin-id hostname`** adds the hostname to messages sent to the server.

> **Watch out:** UDP syslog has no acknowledgment and no retransmission. A message sent while the path to the server is down is simply lost. Keep a local buffer, use TCP transport where the server supports it, or forward critical events with SNMP informs too.

This excerpt shows only the UDP host; the block for the TCP host 10.10.10.61 (`tcp port 1514`) follows the same layout and is trimmed here. Read it top down: the threshold and count for each destination, then each server with its transport and port, then the source interface, then the buffer contents. `link up` against a host means the device has a route to it, not that the server is receiving.

Useful filters: `show logging | include %OSPF`, `show logging | begin Log Buffer`, and `show logging | section Trap`.

## Diagnosing with syslog

- **Interface flaps**: `%LINK-3-UPDOWN` (physical) followed by `%LINEPROTO-5-UPDOWN` (line protocol) with timestamps tells you whether Layer 1 or Layer 2 failed first.
- **Routing adjacencies**: `%OSPF-5-ADJCHG` and `%BGP-5-ADJCHANGE` give the neighbour, the state change and often the reason.
- **Configuration changes**: `%SYS-5-CONFIG_I: Configured from console by <user> on vty0 (10.10.10.5)` identifies who changed what and from where.
- **Correlation across devices** needs NTP and datetime timestamps everywhere; a `*` in front of timestamps means at least one device is not synchronized.

## Lab it yourself

Use two IOS XE routers in Cisco Modeling Labs, GNS3 or EVE-NG (Windows, Linux or an Intel Mac; on an Apple silicon Mac use a remote x86 server or a DevNet sandbox) and a Linux VM running `rsyslog` listening on UDP 514.

1. Configure R1 as above, but with `logging trap warnings`. Shut a loopback on R1: `%LINK-5-CHANGED` (administratively down) and `%LINEPROTO-5-UPDOWN` are level 5, so they appear in the buffer but not on the server. Re-enable it: `%LINK-3-UPDOWN` (level 3) does reach the server, while the level 5 `%LINEPROTO-5-UPDOWN` again does not. Raise to `logging trap notifications` and repeat.
2. Remove `logging source-interface` and watch the source address on the server change when you shut R1's preferred uplink.
3. Add `service sequence-numbers`, then compare numbers in `show logging` with what the server received.
4. Configure NTP from R2 to R1 and watch the `*` disappear from new timestamps once `show ntp status` reports synchronized.
5. Decode one received packet in a capture: check that the PRI equals facility x 8 + severity for your configured facility.

## Key takeaways

- Severities 0 to 7: emergencies, alerts, critical, errors, warnings, notifications, informational, debugging; a threshold includes its level and all lower numbers.
- Format: `seq: timestamp: %FACILITY-SEVERITY-MNEMONIC: text`; the IOS facility is the component, not the syslog protocol facility (`local7` by default, set with `logging facility`).
- Remote logging: `logging host <ip>` (UDP 514 by default, TCP optional), `logging trap <level>` (default informational), `logging source-interface Loopback0`.
- `service timestamps log datetime msec` and `service sequence-numbers` make logs usable; a `*` before the time means the clock is not authoritative.
- `show logging` shows each destination's level and counters, each server's transport and the buffer.
- UDP syslog is unacknowledged; keep a local buffer.
