## One best path per prefix

A BGP router can hold several paths to the same prefix: one from each neighbor that advertised it. It picks exactly **one best path** (unless BGP multipath is configured), offers that path to the routing table, and advertises only that path to its own neighbors. The choice is a fixed sequence of comparisons: the first step where the paths differ decides, and later steps are never reached.

## Before the comparison: is the path usable?

A path is considered only if:

- Its **next hop is reachable** in the routing table. An unreachable next hop leaves the path without the `*` (valid) flag. The classic case is iBGP: a route learned from an eBGP peer keeps the external next hop when passed to iBGP peers, so they need a route to that address (or the edge router uses `neighbor ... next-hop-self`).
- It is not suppressed, dampened or filtered by inbound policy, and its AS_PATH does not contain the router's own AS.

## The Cisco decision order

| Step | Prefer | Default and scope |
|---|---|---|
| 1 | Highest **weight** | Cisco-only; local to the router, never advertised. 32768 for locally originated paths, 0 for learned paths |
| 2 | Highest **local preference** | Default 100; carried to every iBGP peer in the AS, never to eBGP peers |
| 3 | **Locally originated** | Paths this router injected with `network` or `redistribute` (next hop 0.0.0.0), then `aggregate-address` |
| 4 | Shortest **AS_PATH** | Each AS counts once (an AS_SET counts as one); prepending lengthens it |
| 5 | Lowest **origin** | IGP (`i`) < EGP (`e`) < incomplete (`?`) |
| 6 | Lowest **MED** | Compared only between paths from the **same neighboring AS** (unless `bgp always-compare-med`); a missing MED counts as 0 |
| 7 | **eBGP over iBGP** | External paths beat internal ones |
| 8 | Lowest **IGP metric to the next hop** | "Hot potato": leave the AS at the nearest exit |
| 9 | **Oldest eBGP path** | The path received first is kept, to reduce churn (skipped with `bgp bestpath compare-routerid`) |
| 10 | Lowest **BGP router ID** of the advertising neighbor | Or the ORIGINATOR_ID when a route reflector is involved |
| 11 | Shortest cluster list | Route reflector designs only |
| 12 | Lowest **neighbor address** | The final tie-breaker: the peer address configured in `neighbor` |

Steps 4 to 8, 10 and 12 come from RFC 4271's tie-breaking rules and step 11 from route reflection (RFC 4456); local preference is RFC 4271's degree of preference for routes learned over iBGP; weight, the locally originated preference and the oldest-path rule are Cisco additions. A common memory aid for the start of the list: **W**e **L**ove **O**ranges **AS** **O**ranges **M**ean **P**ure **R**efreshment: Weight, Local preference, Originated locally, AS path, Origin, MED, Paths (eBGP over iBGP), Router ID (with IGP metric and oldest path between the last two).

> **Watch out:** "Higher is better" applies to weight and local preference only. Every later attribute is "lower or shorter is better": AS_PATH, origin, MED, IGP metric, router ID, neighbor address.

## Worked walk 1: local preference and weight

R1 is in AS 65001 with eBGP peers R2 (AS 65002, 10.0.12.2) and R3 (AS 65003, 10.0.13.3) and an iBGP peer R4 (10.255.0.4) at another exit of AS 65001.

```text
R1# show ip bgp
<header omitted>
     Network          Next Hop            Metric LocPrf Weight Path
 *>i 10.80.0.0/16     10.255.0.4               0    300      0 65004 i
 *                    10.0.13.3                0             0 65003 65004 i
 *                    10.0.12.2                              0 65002 65040 65004 i
```

1. **Weight**: all 0. Tie.
2. **Local preference**: R4's path carries 300 (R4 sets it inbound from its ISP and passes it over iBGP); the eBGP paths have the default 100 (shown blank). **R4's path wins here**, even though it is iBGP and the others are eBGP: local preference is compared long before eBGP versus iBGP.

Now the engineer adds on R1:

```text
R1(config)# router bgp 65001
R1(config-router)# neighbor 10.0.12.2 weight 100
R1(config-router)# end
R1# clear ip bgp 10.0.12.2 soft in
```

The path via 10.0.12.2 now has weight 100 and wins at **step 1**, despite its lower local preference and its longer AS path. Only R1 changes its choice: weight is never advertised, so R4 and the rest of AS 65001 still prefer R4's exit.

## Worked walk 2: MED and the later tie-breakers

```text
R1# show ip bgp
<header omitted>
     Network          Next Hop            Metric LocPrf Weight Path
 *   10.70.0.0/16     10.0.13.3                0             0 65003 64500 i
 *>                   10.0.12.2               50             0 65002 64500 i
 *                    10.0.15.5                              0 65005 64520 64500 i
```

1. Weight: all 0. 2. Local preference: all 100. 3. None is locally originated.
4. **AS_PATH**: 2, 2 and 3 ASes. The path via 10.0.15.5 is eliminated. Two remain.
5. Origin: both `i`. Tie.
6. **MED**: 0 versus 50, but the paths come from **different neighboring ASes** (65003 and 65002), so MED is **not compared**.
7. Both eBGP. 8. Both next hops are directly connected: IGP metric 0. Tie.
9. **Oldest eBGP path**: R1 learned the path via 10.0.12.2 first, so it stays best. (If 10.0.13.3's path had been older, it would be best; if the paths were the same age, for example after a reload, the lower router ID would decide.)

`show ip bgp 10.70.0.0/16` shows every path's attributes and marks the winner:

```text
R1# show ip bgp 10.70.0.0/16
BGP routing table entry for 10.70.0.0/16, version 31
Paths: (3 available, best #2, table default)
  Advertised to update-groups:
     1
  Refresh Epoch 1
  65003 64500
    10.0.13.3 from 10.0.13.3 (10.255.0.3)
      Origin IGP, metric 0, localpref 100, valid, external
  Refresh Epoch 1
  65002 64500
    10.0.12.2 from 10.0.12.2 (10.255.0.2)
      Origin IGP, metric 50, localpref 100, valid, external, best
  Refresh Epoch 1
  65005 64520 64500
    10.0.15.5 from 10.0.15.5 (10.255.0.5)
      Origin IGP, localpref 100, valid, external
```

The value in parentheses after "from" is the neighbor's BGP router ID, which step 10 uses.

> **Exam tip:** When an exhibit shows a path with a higher MED marked best, check the first AS in each AS_PATH. Different neighboring ASes mean MED was skipped and a later step decided.

## Influencing the choice

Think about direction. Attributes you set on routes you **receive** change how your AS sends traffic **out**. Attributes you set on routes you **advertise** try to change how other ASes send traffic **in**.

| Tool | Configure | Affects | Scope |
|---|---|---|---|
| **Weight** | `neighbor X weight N`, or `set weight N` in an inbound route-map | Outbound traffic from **this router only** | Never leaves the router |
| **Local preference** | `set local-preference N` in an inbound route-map from an eBGP peer; `bgp default local-preference N` | Outbound traffic for the **whole AS** | Carried in iBGP |
| **AS_PATH prepend** | `set as-path prepend 65001 65001` in an **outbound** route-map | **Inbound** traffic: other ASes see a longer path through this link | Travels across the Internet |
| **MED** | `set metric N` in an **outbound** route-map | **Inbound** traffic from one neighboring AS that has several links to you | Sent to the neighbor AS only; lower preferred; the neighbor may ignore it |

Example: prefer ISP-A (R2) for all outbound traffic and make ISP-B (R3) the inbound backup.

```text
R1(config)# route-map FROM-ISP-A permit 10
R1(config-route-map)# set local-preference 200
R1(config-route-map)# exit
R1(config)# route-map TO-ISP-B permit 10
R1(config-route-map)# set as-path prepend 65001 65001 65001
R1(config-route-map)# exit
R1(config)# router bgp 65001
R1(config-router)# address-family ipv4 unicast
R1(config-router-af)# neighbor 10.0.12.2 route-map FROM-ISP-A in
R1(config-router-af)# neighbor 10.0.13.3 route-map TO-ISP-B out
R1(config-router-af)# end
R1# clear ip bgp * soft
```

A route-map with no `match` clause matches everything; a route-map with only `deny` entries, or a missing final `permit`, drops every route that does not match, which is a common way to lose all prefixes from a neighbor. Policy changes apply only to updates processed afterwards, so refresh with a soft clear.

## Lab it yourself

Platform: Cisco Modeling Labs, GNS3 or EVE-NG on a Windows, Linux or Intel Mac host (on an Apple silicon Mac, a remote x86 server or a Cisco DevNet sandbox with CML), with four IOSv or Catalyst 8000v routers: R1 (AS 65001) peering with R2 (AS 65002) and R3 (AS 65003), and R4 (AS 64500) peering with both R2 and R3 and advertising 10.70.0.0/16 from a loopback with a Null0 static.

1. On R1, read `show ip bgp` and `show ip bgp 10.70.0.0/16`. Note which path is best and use the table above to name the deciding step (probably oldest path or router ID).
2. Clear the session to the current best neighbor and watch the best path move to the other one (oldest path).
3. On R2 add an outbound route-map with `set metric 50`; confirm R1 does not compare the MEDs. Configure `bgp always-compare-med` on R1, soft clear, and watch MED decide.
4. Set `neighbor 10.0.13.3 weight 100` on R1 and confirm weight overrides everything else.
5. Replace weight with an inbound `set local-preference 200` route-map, then with AS_PATH prepending on R4 toward R2, and predict each result before checking.

## Key takeaways

- Only paths with a reachable next hop are candidates; the first step where paths differ decides.
- Order: weight (high), local preference (high), locally originated, AS_PATH (short), origin (IGP < EGP < incomplete), MED (low, same neighbor AS only), eBGP over iBGP, IGP metric to next hop (low), oldest eBGP path, router ID (low), cluster list, neighbor address (low).
- Weight is Cisco-only and local to one router; local preference is shared across the AS through iBGP.
- Influence outbound traffic with weight or local preference on received routes; influence inbound traffic with AS_PATH prepending or MED on advertised routes.
- MED is compared only between paths from the same neighboring AS unless `bgp always-compare-med` is set.
- After a policy change, `clear ip bgp ... soft` re-evaluates without dropping the session.
