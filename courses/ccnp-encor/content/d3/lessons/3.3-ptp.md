## Why NTP is not enough

NTP over a LAN typically keeps clocks within about a millisecond, and its accuracy is limited by software: the timestamp is taken when the operating system handles the packet, after queuing, interrupts and scheduling have added an unknown, variable delay. Some applications need far better: audio and video over IP (AES67, SMPTE 2110), industrial automation and substation protection, mobile fronthaul, and trading systems that must timestamp orders. The **Precision Time Protocol (PTP)**, IEEE 1588, targets sub-microsecond accuracy, and achieves it only because:

1. **Hardware timestamping**: the network interface stamps the exact moment a PTP event message crosses the wire, removing software delay from the measurement.
2. **Network devices take part**: switches either act as clocks themselves (boundary clocks) or measure and report their own residence time (transparent clocks), so queuing inside the switch does not corrupt the result.

ENCOR v1.2 says "interpret" for PTP: recognise the roles and messages, and read a configuration and `show ptp` output. Versions: IEEE 1588-2002 is PTPv1; **IEEE 1588-2008 is PTPv2**, not backward compatible with v1, and the version Catalyst switches run; IEEE 1588-2019 is a compatible revision of v2. Newer texts use the alternative terms timeTransmitter and timeReceiver for master and slave; Cisco output uses MASTER and SLAVE.

## Clock types

| Clock | Role |
|---|---|
| **Grandmaster** (GM) | The best clock in the domain, elected by the BMCA; usually locked to GNSS. The root of the time tree |
| **Ordinary clock** (OC) | One PTP port: either a source (the grandmaster itself) or an end device synchronizing to the network |
| **Boundary clock** (BC) | Several PTP ports. Synchronizes its own clock on one port (slave) and acts as master on its other ports, so downstream devices synchronize to the switch, not across it. Each BC segment runs its own message exchange |
| **Transparent clock** (TC) | Does not synchronize to anyone. Forwards PTP messages and adds the time the message spent inside the switch (its residence time) to a correction field |
| End-to-end (E2E) TC | Corrects residence time for Sync and Delay_Req messages; delay is still measured end to end between master and slave |
| Peer-to-peer (P2P) TC | Also measures the delay of each link to its neighbour with Pdelay messages, so every hop's link delay is known separately |

## Messages

| Message | Class | Purpose |
|---|---|---|
| **Announce** | General | Carries the sender's grandmaster attributes; feeds the BMCA |
| **Sync** | Event (timestamped) | Master to slave: the departure time t1 |
| **Follow_Up** | General | Carries the precise t1 when the master could not put it in the Sync itself (two-step clock) |
| **Delay_Req** | Event | Slave to master: sent at t3 |
| **Delay_Resp** | General | Master to slave: when the Delay_Req arrived (t4) |
| Pdelay_Req, Pdelay_Resp, Pdelay_Resp_Follow_Up | Event / general | Peer delay measurement on one link (P2P TC and pdelay BC) |
| Management, Signaling | General | Configuration and negotiation (for example unicast grants) |

With t1 and t2 (Sync sent and received) and t3 and t4 (Delay_Req sent and received), the slave computes the mean path delay ((t2 − t1) + (t4 − t3)) / 2 and its offset from the master ((t2 − t1) − (t4 − t3)) / 2. Both assume the path is **symmetric**; an asymmetric path (different delay in each direction) shows up directly as an offset error, which is why PTP networks avoid devices that do not take part in PTP.

## Transport and domains

| Transport | Details |
|---|---|
| Ethernet (IEEE 802.3) | EtherType **0x88F7**; multicast 01-1B-19-00-00-00, peer delay messages to 01-80-C2-00-00-0E (link-local, never forwarded) |
| UDP over IPv4 | Event messages to **UDP 319**, general messages to **UDP 320**; multicast 224.0.1.129, peer delay 224.0.0.107 |
| UDP over IPv6 | FF0X::181, peer delay FF02::6B |

A **domain** (0–127 in the default profile, default **0**) is an independent set of clocks with its own grandmaster; clocks only synchronize with messages carrying their own domain number. **Profiles** (default, IEEE 802.1AS for AVB/TSN, ITU-T G.8275.1 for telecom, Power profile, SMPTE 2059-2) fix the options an application uses.

## Best Master Clock Algorithm (BMCA)

Every clock compares the Announce data it receives with its own and with each other, attribute by attribute, **lowest value wins**, stopping at the first difference:

| Order | Attribute | Notes |
|---|---|---|
| 1 | **priority1** | Administrative, 0–255, default **128**. Overrides everything below |
| 2 | **clockClass** | Traceability: 6 = locked to a primary reference such as GNSS; 7 = in holdover; 248 = default, 255 = slave-only |
| 3 | **clockAccuracy** | Enumerated accuracy (for example within 100 ns) |
| 4 | **offsetScaledLogVariance** | Stability estimate |
| 5 | **priority2** | Administrative tiebreaker, default **128** |
| 6 | **clockIdentity** | 64-bit identity built from the MAC address; lowest wins |

Each port then takes a state:

| Port state | Meaning |
|---|---|
| **MASTER** | Sends Sync and Announce downstream |
| **SLAVE** | Synchronizes to the best master heard on this port; one per boundary clock |
| **PASSIVE** | Hears a better or equal master on a second path; stays quiet to avoid a timing loop (compare STP blocking) |
| LISTENING, UNCALIBRATED, PRE_MASTER | Transitional |
| FAULTY, DISABLED, INITIALIZING | Not taking part (Cisco shows FAULTY for ports with no link) |

> **Exam tip:** an engineer who wants a backup grandmaster to take over only when the primary fails sets the same priority1 on both and lower priority2 on the primary. Lower priority1 on a poor-quality clock makes it grandmaster even if a GNSS-locked clock exists, because priority1 is compared before clockClass.

## Reading a Catalyst configuration and `show ptp`

On Catalyst 9000 switches that support it, the clock mode, priorities and domain are global commands, and per-port settings go under the interfaces (platform support and defaults vary by model and release, so check the configuration guide for your switch). The keywords in the IOS XE 17 data model include:

```text
SW1(config)# ptp mode boundary delay-req
SW1(config)# ptp priority1 100
SW1(config)# ptp priority2 120
SW1(config)# ptp domain 0
```

`ptp mode` selects the clock type: `boundary delay-req` (end-to-end delay mechanism), `boundary pdelay-req` (peer delay), `e2etransparent`, `p2ptransparent`; `ptp profile dot1as` selects the 802.1AS profile. Per-interface settings tune the message rates (`ptp announce interval`, `ptp announce timeout`, `ptp sync interval`, `ptp delay-req interval`), expressed as log2 of seconds (0 = 1 per second, −3 = 8 per second).

## PTP or NTP?

| | NTP | PTP |
|---|---|---|
| Typical accuracy | About 1 ms on a LAN, tens of ms on a WAN | Sub-microsecond with hardware support end to end |
| Timestamps | Software | Hardware at the PHY or MAC |
| Network role | Routers are clients and servers | Switches are boundary or transparent clocks |
| Selection | Stratum and the selection and clustering algorithms | BMCA on priority1, class, accuracy, variance, priority2, identity |
| Transport | UDP 123 | Ethernet 0x88F7 or UDP 319 / 320 |

Devices commonly run both: PTP for the application network and NTP for logging and management time.

## Lab it yourself

PTP needs hardware timestamping, which virtual routers and switches in Cisco Modeling Labs, GNS3 and EVE-NG do not provide, so this lab is a reading exercise plus a software demo. If you have Catalyst 9300 or 9500 switches, configure `ptp mode boundary delay-req` on two of them, connect a PTP grandmaster or a Linux host with a PTP-capable NIC, and compare `show ptp clock`, `show ptp parent` and `show ptp brief` on each before and after changing `ptp priority1`. Without hardware, on any Linux machine or a Linux VM on Windows or macOS, the open-source `linuxptp` package (`ptp4l`) can run software-timestamped PTP between two VMs; it shows the BMCA, port states and the offset and path delay values, at microsecond rather than nanosecond accuracy. Write down, for each output above, which clock is grandmaster and why.

## Key takeaways

- PTP (IEEE 1588-2008, PTPv2) reaches sub-microsecond accuracy through hardware timestamps and switches that take part as boundary or transparent clocks.
- Grandmaster, ordinary, boundary and transparent (end-to-end or peer-to-peer) clocks; a boundary clock has one SLAVE port and MASTER ports, a transparent clock only corrects residence time.
- Messages: Announce (BMCA), Sync and Follow_Up (t1), Delay_Req and Delay_Resp (t3, t4), Pdelay for per-link delay; event messages are timestamped.
- Transport: Ethernet EtherType 0x88F7, or UDP 319 (event) and 320 (general); clocks only interact within one domain number.
- BMCA order, lowest wins: priority1, clockClass, clockAccuracy, offsetScaledLogVariance, priority2, clockIdentity; priority1 and priority2 default to 128.
- Port states MASTER, SLAVE and PASSIVE (loop avoidance); `show ptp clock`, `show ptp parent`, `show ptp brief` and `show ptp port` tell you the role, the grandmaster and each port's state.
