## What PBR is for

Normal routing looks only at the destination address. **Policy-based routing (PBR)** lets a router forward selected packets by other criteria: source address, protocol, port, packet length. Typical uses:

- Send guest Wi-Fi traffic out a cheap broadband link while corporate traffic uses the MPLS link, although both go to the same destinations.
- Steer one application (for example backups to a cloud provider on TCP 443 from one server subnet) to a second ISP.
- Send selected traffic through a firewall, WAN optimizer or inspection appliance.
- Pick an exit by source for a dual-homed site that does not run BGP.

PBR is configured with a **route-map** applied to the **interface where the packets arrive**. It is static policy: it does not react to congestion on its own, which is what SD-WAN application-aware routing adds.

## Building the policy

```text
R1(config)# ip access-list extended GUEST-WEB
R1(config-ext-nacl)# permit tcp 10.20.0.0 0.0.255.255 any eq 443
R1(config-ext-nacl)# permit tcp 10.20.0.0 0.0.255.255 any eq 80
R1(config-ext-nacl)# exit
R1(config)# route-map PBR-GUEST permit 10
R1(config-route-map)# match ip address GUEST-WEB
R1(config-route-map)# set ip next-hop 198.51.100.1
R1(config-route-map)# exit
R1(config)# interface GigabitEthernet0/0/2
R1(config-if)# description Guest LAN 10.20.0.0/16
R1(config-if)# ip policy route-map PBR-GUEST
```

How the route-map is evaluated for each packet arriving on Gi0/0/2:

- Entries are checked in sequence order. `match ip address` takes ACLs (standard, extended or named); `match length MIN MAX` matches packet size.
- A packet that matches a **permit** entry is policy routed using that entry's `set` clauses.
- A packet that matches a **deny** entry, or matches no entry at all, is **routed normally** by the routing table. PBR never drops traffic by itself; a `deny` in a PBR route-map means "do not policy route".
- In the ACL, `permit` means "select for this entry" and `deny` means "do not select"; the ACL is used for matching only and never filters traffic.

## The set actions

| Set clause | Behavior |
|---|---|
| `set ip next-hop A.B.C.D [...]` | Forward to this next hop **before** consulting the routing table. The next hop must be directly connected (adjacent); if it is not reachable, the packet is routed normally. Several addresses are tried in order |
| `set ip next-hop recursive A.B.C.D` | Allows a next hop that is not directly connected, resolved through the routing table |
| `set ip next-hop verify-availability A.B.C.D SEQ track N` | Use the next hop only while tracked object N is up (typically an IP SLA probe); otherwise the next entry or normal routing |
| `set interface TYPE NUM` | Send out an interface; intended for point-to-point links (on Ethernet the router would still need the destination's ARP entry) |
| `set ip default next-hop A.B.C.D` | Route normally **first**; use this next hop only if the routing table has **no explicit route** for the destination (the default route does not count) |
| `set default interface TYPE NUM` | The same idea with an interface |

The order of operations follows from the table: `set ip next-hop` and `set interface` act **before** the routing table; `set ip default next-hop` and `set default interface` act **after** it, only when the lookup finds nothing more specific than a default route. With `set ip default next-hop`, a guest flow to an internal prefix that is in the table still goes the normal way, while Internet traffic that would have followed the default route takes the policy next hop.

> **Exam tip:** "Override the routing table" means `set ip next-hop`. "Only if there is no route" means `set ip default next-hop`.

## Tracking the next hop

A plain `set ip next-hop` keeps sending traffic toward the broadband router as long as the next hop is up on the LAN, even if the broadband line behind it is dead. Tie the policy to a reachability test:

```text
R1(config)# ip sla 10
R1(config-ip-sla)# icmp-echo 203.0.113.10 source-interface GigabitEthernet0/0/0
R1(config-ip-sla-echo)# frequency 10
R1(config-ip-sla-echo)# exit
R1(config)# ip sla schedule 10 life forever start-time now
R1(config)# track 10 ip sla 10 reachability
R1(config)# route-map PBR-GUEST permit 10
R1(config-route-map)# no set ip next-hop 198.51.100.1
R1(config-route-map)# set ip next-hop verify-availability 198.51.100.1 10 track 10
```

While track 10 is down, guest traffic falls back to normal routing. IP SLA itself is covered in Domain 4.

## Traffic the router originates

`ip policy route-map` applies only to packets **received** on that interface. Packets the router generates itself (pings and traceroutes from the CLI, SSH, syslog, routing protocol traffic, IP SLA probes) never arrive on an interface, so they are not policy routed. For those, apply a policy globally:

```text
R1(config)# ip local policy route-map PBR-MGMT
```

Keep its ACL narrow (for example only syslog and SNMP traps to one collector), because a broad local policy can capture routing protocol and management traffic.

## Where PBR sits in the forwarding path

For a packet arriving on an interface with a policy:

1. Input features such as the inbound ACL run first.
2. PBR evaluates the route-map. If a permit entry matches and a `set ip next-hop` or `set interface` target is usable, the packet is forwarded there; the routing table is not consulted.
3. Otherwise the normal routing table (CEF) lookup happens.
4. If that lookup finds no specific route and the matched entry has `set ip default next-hop` or `set default interface`, that target is used.
5. Output features (outbound ACL, NAT, QoS) apply on the chosen egress interface.

PBR is switched in CEF on routers and in hardware on Catalyst 9000 switches, so it does not punt traffic to the CPU. The supported `match` and `set` options differ by platform: switches generally support next-hop based actions, while some router-only options (`set interface` among them) may be unavailable. Check the platform guide before designing around a specific action.

## Verification

```text
R1# show ip policy
Interface      Route map
Gi0/0/2        PBR-GUEST

R1# show route-map PBR-GUEST
route-map PBR-GUEST, permit, sequence 10
  Match clauses:
    ip address (access-lists): GUEST-WEB
  Set clauses:
    ip next-hop 198.51.100.1
  Policy routing matches: 18342 packets, 9876210 bytes
```

- `show ip policy` lists every interface with a policy (and `local` for `ip local policy`). An empty list or the wrong interface is the most common fault.
- `show route-map` shows the match and set clauses and the **policy routing match counters**. Counters stuck at 0 while traffic flows mean the policy is on the wrong interface (egress instead of ingress), the ACL does not match the traffic, or the traffic is router-originated.
- `show access-lists GUEST-WEB` counters confirm whether the ACL matches.
- `debug ip policy` shows per-packet decisions ("policy match", "policy routed", "policy rejected -- normal forwarding"). Use it only with an ACL filter or in a lab, because it is per packet.
- `traceroute` from a host in the guest subnet proves the actual path; a traceroute from the router itself is not policy routed unless `ip local policy` is configured.

IPv6 works the same way with an IPv6 ACL, `match ipv6 address`, `set ipv6 next-hop` and `ipv6 policy route-map` on the interface.

## Lab it yourself

Platform: Cisco Modeling Labs, GNS3 or EVE-NG on a Windows, Linux or Intel Mac host (on an Apple silicon Mac, a remote x86 server or a Cisco DevNet sandbox with CML), with four IOSv or Catalyst 8000v routers and two hosts (Linux or IOSv acting as hosts).

1. R1 has a LAN (Gi0/0/2, 10.20.0.1/16, guest host) and a second LAN (Gi0/0/3, 10.30.0.1/16, corporate host), and two uplinks: Gi0/0/0 to ISP-A (198.51.100.1) and Gi0/0/1 to ISP-B (203.0.113.1). A default route points to ISP-B. Both ISP routers connect to R4, which holds a test loopback.
2. Build `PBR-GUEST` as above but sending guest traffic to 198.51.100.1, and apply it on Gi0/0/1 (the wrong place). Traceroute from the guest host and check `show route-map` counters: 0.
3. Move `ip policy route-map PBR-GUEST` to Gi0/0/2 and repeat; the guest host now exits via ISP-A while the corporate host still uses ISP-B.
4. Ping from R1 itself with source 10.20.0.1 and see that it is not policy routed; add `ip local policy route-map` with a narrow ACL and repeat.
5. Change the action to `set ip default next-hop 198.51.100.1` and let the guest ACL match all IP traffic. Guest traffic to R4's loopback (only the default route matches) still exits via ISP-A, while guest traffic to the corporate LAN 10.30.0.0/16 (an explicit connected route) is routed normally. Add a specific static route for R4's loopback via ISP-B and see guest traffic to it follow that route instead.
6. Add IP SLA, tracking and `verify-availability`; shut ISP-A's far side and watch guest traffic fall back.

## Key takeaways

- PBR forwards selected packets by source, protocol, port or length instead of destination only, using a route-map with `match ip address` and `set` clauses.
- Apply it with `ip policy route-map NAME` on the **ingress** interface; router-originated traffic needs `ip local policy route-map NAME`.
- Unmatched packets and packets matching a `deny` entry are routed normally; PBR does not drop traffic.
- `set ip next-hop` acts before the routing table and requires an adjacent, reachable next hop; `set ip default next-hop` acts only when there is no explicit route.
- `set ip next-hop verify-availability ... track N` withdraws the policy when a tracked object goes down.
- Verify with `show ip policy`, `show route-map` match counters, ACL counters, `debug ip policy` and traceroute from a real host.
