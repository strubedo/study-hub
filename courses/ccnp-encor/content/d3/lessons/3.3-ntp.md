## Why time matters, and what ENCOR asks

Log correlation, certificate validity, Kerberos and TACACS+ accounting, IP SLA one-way delay and the timestamps in every syslog message all depend on routers and switches agreeing on the time. Exam topic 3.3.a says **interpret** NTP and PTP configurations: given a configuration or a `show` output, you must say what the device is doing and why it is or is not synchronized. This lesson covers NTP; the next covers PTP.

NTPv4 is defined in RFC 5905. It runs over **UDP port 123** (source and destination) and IOS XE sends version 4 by default.

## Stratum

Stratum is the distance from a reference clock, carried in an 8-bit field:

| Stratum | Meaning (RFC 5905) |
|---|---|
| 0 | Unspecified or invalid in packets; reference clocks (GPS, atomic) conventionally sit "at" stratum 0 |
| 1 | Primary server, directly attached to a reference clock |
| 2–15 | Secondary server: one more than the server it synchronizes to |
| **16** | **Unsynchronized** |

A router that synchronizes to a stratum 2 server becomes stratum 3. Lower is better, and NTP will not synchronize to a source that is itself unsynchronized (stratum 16).

## Association modes

| Mode | IOS XE command | Behaviour |
|---|---|---|
| Client / server | `ntp server ADDRESS` | This device polls the server and can synchronize to it; the server never synchronizes to the client |
| Symmetric active / passive | `ntp peer ADDRESS` | Both sides can synchronize to each other; whichever is better becomes the source. Used between two core devices that both have upstream servers |
| Broadcast | `ntp broadcast` (interface, server side), `ntp broadcast client` (interface, client side) | The server sends periodic broadcasts on the segment; clients listen instead of polling. Less accurate (no round-trip delay measurement) |
| Local master | `ntp master [STRATUM]` | The device serves its own clock as authoritative, at stratum 8 by default (range 1–15) |

## Configuring a client and a local server

```text
R1(config)# ntp server 10.10.1.1 prefer
R1(config)# ntp server 10.10.1.2
R1(config)# ntp source Loopback0
R1(config)# ntp update-calendar
R1(config)# clock timezone EST -5 0
R1(config)# clock summer-time EDT recurring
```

- `prefer` makes that server the first choice when several are acceptable. It does not override the selection algorithm's sanity checks: a preferred server that is a falseticker is still rejected.
- `ntp server` also takes `key N` (authentication, below), `source INTERFACE` (per server), `version 1–4` (default 4); for a server in a VRF the VRF comes before the address (`ntp server vrf MGMT 10.10.1.1`). In the running configuration they appear on one line, for example `ntp server 10.10.1.1 key 1 prefer`.
- `ntp source Loopback0` sources all NTP packets from the loopback, so server ACLs and firewalls can permit one stable address.
- `ntp update-calendar` periodically writes NTP time to the hardware calendar (the battery-backed clock) on platforms that have one, so the time is roughly right after a reload, before NTP synchronizes.
- `clock timezone` and `clock summer-time` change only how the time is **displayed**. NTP itself always carries UTC.

On a device that must serve time with no upstream source (an isolated lab or an air-gapped plant network):

```text
DSW1(config)# ntp master 4
```

`ntp master` with no number uses stratum 8. The device then answers clients from its own clock, which is only as good as whatever set it. It appears in `show ntp associations` as the pseudo-address `127.127.1.1` with reference `.LOCL.` one stratum below the configured value (stratum 7 for the default 8). If a configured server with a better stratum is reachable, the device synchronizes to that instead.

## Authentication

NTP authentication proves that time came from a server holding the shared key. The device that **synchronizes** is the one that must trust the key:

```text
R1(config)# ntp authentication-key 1 md5 <SECRET>
R1(config)# ntp authenticate
R1(config)# ntp trusted-key 1
R1(config)# ntp server 10.10.1.1 key 1
```

| Command | Purpose |
|---|---|
| `ntp authentication-key N md5 KEY` | Defines key N. IOS XE 17 also offers stronger algorithms (`hmac-sha2-256`, `cmac-aes-128` and others) where both ends support them |
| `ntp authenticate` | Turns on authentication checking: the device will synchronize only to sources that authenticate with a trusted key |
| `ntp trusted-key N` | Marks key N as acceptable for synchronization |
| `ntp server ADDRESS key N` | Sends requests signed with key N to that server |

The server needs the **same key number and string** (`ntp authentication-key`) so it can sign its replies. `ntp authenticate` and `ntp trusted-key` on the server only matter for sources the server itself synchronizes to. For `ntp peer`, both peers synchronize from each other, so both need all four pieces.

> **Watch out:** the classic fault is a client with the key and `ntp authenticate` but no `ntp trusted-key`. Packets flow, but the client never synchronizes: `show ntp status` stays "unsynchronized, stratum 16". A key string mismatch has the same result.

## Restricting access: `ntp access-group`

`ntp access-group TYPE ACL` filters NTP by source address. The four types, from most to least permissive:

| Type | Allows |
|---|---|
| `peer` | Time requests, control queries, and synchronizing this device to the permitted source |
| `serve` | Time requests and control queries, but not synchronizing to the source |
| `serve-only` | Time requests only |
| `query-only` | Control queries only (monitoring tools such as `ntpq`), no time service |

IOS XE also accepts an address-family keyword (`ntp access-group ipv4 peer 11`, or `ipv6` with an IPv6 ACL name), and current releases may display the IPv4 form that way in the running configuration. Once any access group is configured, a source gets only what a matching group grants. A router that serves a user subnet with `serve-only` must still permit its own upstream servers with `peer`, or it stops synchronizing.

## Reading `show ntp associations`

```text
R1# show ntp associations

  address         ref clock       st   when   poll reach  delay  offset   disp
*~10.10.1.1       .GNSS.           1     37     64   377  0.812   0.214  0.940
+~10.10.1.2       10.10.1.1        2     12     64   377  1.104   0.388  1.012
x~10.10.1.3       .GNSS.           1     51     64   377  0.977 912.406  0.963
 ~10.10.1.4       .INIT.          16      -   1024     0  0.000   0.000 15937.
 * sys.peer, # selected, + candidate, - outlyer, x falseticker, ~ configured
```

| Marker / field | Meaning |
|---|---|
| `*` | **System peer**: the source R1 is synchronized to |
| `+` | Candidate: acceptable, combined with the system peer, ready to take over |
| `#` | Selected: passed the checks but is not currently used for synchronization |
| `-` | Outlier: rejected by the clustering step |
| `x` | **Falseticker**: its time disagrees with the majority, so it is discarded |
| `~` | Configured by a command (as opposed to learned dynamically) |
| ref clock | The source's own reference: an upstream address, or a code such as `.GNSS.`, `.GPS.`, `.LOCL.` (local `ntp master`), `.INIT.` (never synchronized) |
| st | The **source's** stratum. R1's stratum is the system peer's plus one: 2 here |
| when / poll | Seconds since the last reply; current poll interval in seconds (IOS XE default range 64 to 1024 s) |
| reach | 8-bit **shift register in octal**: shifted left at every poll, the low bit set when a valid reply arrives. 377 = 11111111 = the last eight polls all answered |
| delay / offset / disp | Round-trip delay, estimated clock offset from R1, and dispersion (error estimate), all in milliseconds |

Reading reach: 376 (11111110) means the most recent poll failed and the seven before it succeeded; 17 (00001111) means only four polls have ever succeeded, typical just after the server was configured; 0 means no reply at all. A falseticker such as 10.10.1.3 can have a perfect reach: it answers, but its offset (912 ms against 0.2 ms) disagrees with the others.

## `show ntp status` and `show clock detail`

```text
R1# show ntp status
Clock is synchronized, stratum 2, reference is 10.10.1.1
nominal freq is 250.0000 Hz, actual freq is 250.0004 Hz, precision is 2**23
ntp uptime is 9145600 (1/100 of seconds), resolution is 4000
reference time is EEAECA94.3C6A7EF9 (09:22:12.236 EST Mon Nov 23 2026)
clock offset is 0.2140 msec, root delay is 0.81 msec
root dispersion is 3.42 msec, peer dispersion is 0.94 msec
loopfilter state is 'CTRL' (Normal Controlled Loop), drift is -0.000001592 s/s
system poll interval is 64, last update was 37 sec ago.
```

The first line is the one to read: synchronized or not, this device's stratum, and its reference. An unsynchronized device shows `Clock is unsynchronized, stratum 16, no reference clock`.

```text
R1# show clock detail
09:22:15.104 EST Mon Nov 23 2026
Time source is NTP
```

A leading `*` before the time means the clock is not authoritative (never set, or not synchronized); a leading `.` means it was set and is believed accurate but NTP is not currently synchronized. No symbol means synchronized. Syslog timestamps show the same symbols.

## Troubleshooting checklist

| Symptom | Look at |
|---|---|
| reach 0, `.INIT.`, st 16 | UDP 123 blocked, no route to the server, wrong source address, an access group or a server-side ACL dropping the requests |
| reach 377 but never `*`, status unsynchronized | Authentication (missing `ntp trusted-key`, key mismatch), the server itself unsynchronized (st 16), or the server marked `x` |
| `x` on one of several servers | That server is wrong; with only two servers NTP cannot tell which one is wrong, so configure three or more |
| Time correct but displayed wrong | `clock timezone` / `clock summer-time`, not NTP |
| Large offset and slow convergence | NTP slews small offsets gradually; a large initial error takes time to step and settle |

## Lab it yourself

Platform: Cisco Modeling Labs, GNS3 or EVE-NG on a Windows, Linux or Intel Mac host (on an Apple silicon Mac, use a remote x86 server or a Cisco DevNet sandbox with CML), with three IOSv or Catalyst 8000v routers in a line: R1 – R2 – R3.

1. On R1: `ntp master 3`. On R2: `ntp server 10.0.12.1` (R1's link address). On R3: `ntp server 10.0.23.2`.
2. Watch `show ntp associations` on R2 as reach grows 1, 3, 7, 17, 37, 77, 177, 377, then check that R2 is stratum 4 and R3 stratum 5 with `show ntp status`.
3. Add authentication on R2 and R3 with a lab-only key (`ntp authentication-key 1 md5 Lab-Only-Key`), `ntp authenticate` and `ntp server ... key 1` on R3, but leave out `ntp trusted-key 1`. Confirm R3 stays unsynchronized, then add the trusted key.
4. On R2 configure `ntp access-group serve-only 10` with `access-list 10 permit 10.0.23.0 0.0.0.255` and watch R2 lose its own synchronization; fix it with a `peer` group permitting R1.
5. Set `clock timezone` on R3 and compare `show clock` with R2.

## Key takeaways

- NTPv4 (RFC 5905), UDP 123; stratum 1 = attached to a reference clock, 16 = unsynchronized; a client is one stratum above its source.
- `ntp server` = client/server, `ntp peer` = symmetric, `ntp broadcast` / `ntp broadcast client` = broadcast, `ntp master` = local clock at stratum 8 by default.
- Authentication: the synchronizing side needs `ntp authenticate`, the key, `ntp trusted-key` and `ntp server ... key N`; the server needs the same key to sign replies.
- `ntp access-group`: peer > serve > serve-only > query-only; permit your own upstream servers with `peer`.
- `show ntp associations`: `*` system peer, `+` candidate, `#` selected, `-` outlier, `x` falseticker, `~` configured; reach is an octal shift register, 377 = last eight polls answered.
- `show ntp status` line 1 gives synchronized or not, stratum and reference; `show clock detail` gives the time source; `*` before the time = not authoritative.
- `clock timezone` and `clock summer-time` only change the display; `ntp update-calendar` keeps the hardware calendar in step.
