## What a GPO actually is

A Group Policy Object has two halves that must stay in sync:

* **Group Policy Container (GPC)** — an AD object under `CN=Policies,CN=System,DC=contoso,DC=com`, named by GUID. Holds the version number, GPO status, the list of client-side extensions in use, the WMI filter link and permissions. (Links are *not* stored here — they live in the `gPLink` attribute of each site, domain or OU.) Replicates with **AD replication**.
* **Group Policy Template (GPT)** — a folder `\\contoso.com\SYSVOL\contoso.com\Policies\{GUID}` with `Machine` and `User` subfolders (`Registry.pol`, security templates, scripts, preference XML). Replicates with **DFSR**.

A GPO does nothing until it is **linked** to a site, domain or OU. One GPO can be linked in many places; deleting a *link* doesn't delete the GPO.

Clients apply **computer settings** at startup and **user settings** at sign-in, then refresh in the background every **90 minutes with a random offset of 0–30 minutes** (DCs every **5 minutes**). Some extensions — software installation, folder redirection, startup/logon scripts — apply only in the foreground (startup/sign-in). Security settings are additionally re-applied every 16 hours even if the GPO hasn't changed.

## Processing order: LSDOU

1. **L**ocal policy (on the machine)
2. **S**ite-linked GPOs
3. **D**omain-linked GPOs
4. **O**U-linked GPOs, from the top-level OU down to the OU that holds the object

Settings are cumulative; when two GPOs configure the **same** setting differently, the one applied **last wins** — so a GPO on the user's or computer's own OU beats one on the domain. Within one container, GPOs apply by **link order**: link order **1 has the highest precedence** (it's processed last).

Only the location of the **object** matters: computer settings come from GPOs in scope of the computer object's OU; user settings from GPOs in scope of the user object's OU (unless loopback is used — below).

### Changing inheritance

| Control | Set on | Effect |
|---|---|---|
| **Block Inheritance** | A domain or OU | GPOs linked *above* it no longer apply to objects in it… |
| **Enforced** (formerly *No Override*) | A GPO **link** | …except enforced links, which apply anyway **and** win over conflicting settings from GPOs lower in the tree |
| **Link enabled** | A GPO link | Clearing it stops that link from applying without deleting it |
| **GPO status** | The GPO | Disable the User or Computer half (`GpoStatus`), or all settings, for faster processing or emergency disable |

If two enforced links conflict, the one **higher** in the hierarchy (e.g. the domain) wins.

```powershell
PS C:\> New-GPO -Name 'Sec - Servers Baseline' | New-GPLink -Target 'OU=Servers,DC=contoso,DC=com' -LinkEnabled Yes
PS C:\> Set-GPLink -Name 'Sec - Servers Baseline' -Target 'OU=Servers,DC=contoso,DC=com' -Enforced Yes -Order 1
PS C:\> Set-GPInheritance -Target 'OU=Lab,DC=contoso,DC=com' -IsBlocked Yes
PS C:\> (Get-GPO 'Sec - Servers Baseline').GpoStatus = 'UserSettingsDisabled'
```

> **Exam tip:** "A setting from a domain-level GPO must apply to every computer, including those in an OU where an administrator enabled Block Inheritance" → set the domain link to **Enforced**. Don't remove Block Inheritance — the OU owner set it for a reason, and the question usually says you can't change OU settings.

### The two default GPOs

* **Default Domain Policy** — linked to the domain. Account policies for domain accounts (password, lockout, Kerberos) only take effect from GPOs linked at the **domain** level, so keep them here (or in another domain-linked GPO). Fine-grained password policies are the per-group exception.
* **Default Domain Controllers Policy** — linked to the *Domain Controllers* OU; user rights and audit settings for DCs.

Put everything else in new GPOs. `dcgpofix` recreates the two defaults if they're damaged.

## Filtering: who in scope actually applies it

### Security filtering

Every GPO's ACL by default grants **Authenticated Users** *Read* and *Apply group policy*. To target a subset, remove Authenticated Users from **Security Filtering** (Scope tab) and add a group. Since **MS16-072**, the computer retrieves *user* policy in its own security context, so the computer must still be able to **read** the GPO:

* Remove *Authenticated Users* from Security Filtering, add your target group, then on the **Delegation** tab add **Authenticated Users** (or **Domain Computers**) with **Read** only.
* To *exclude* a group, add it on the Delegation tab › Advanced with **Deny – Apply group policy**. Deny overrides allow.

```powershell
PS C:\> Set-GPPermission -Name 'Cfg - Sales Drives' -TargetName 'G-Sales' -TargetType Group -PermissionLevel GpoApply
PS C:\> Set-GPPermission -Name 'Cfg - Sales Drives' -TargetName 'Authenticated Users' -TargetType Group -PermissionLevel GpoRead -Replace
```

> **Watch out:** Security filtering only narrows **who in the linked scope** applies the GPO. Adding a group from another OU to Security Filtering doesn't make the GPO apply to users outside the OUs where it's linked.

### WMI filters

A **WMI filter** is a WQL query evaluated **on the client**; if it returns false, the GPO is skipped. Each GPO can have **one** WMI filter; a filter can be reused by many GPOs. Typical uses (`ProductType` is 1 for workstations, 2 for domain controllers, 3 for member servers):

| Target | WQL query |
|---|---|
| Member servers only | `SELECT * FROM Win32_OperatingSystem WHERE ProductType = "3"` |
| Windows Server 2025 (build 26100) servers and DCs | `SELECT * FROM Win32_OperatingSystem WHERE Version LIKE "10.0.26100%" AND ProductType <> "1"` |
| Computers with a battery (laptops) | `SELECT * FROM Win32_Battery` |

WMI filters cost processing time on every refresh; prefer OU design and security filtering, and keep queries simple.

### Loopback processing

Normally a user gets user settings from GPOs on the **user's** OU wherever they sign in. For Remote Desktop Session Hosts, kiosks and lab PCs you want user settings to depend on the **computer** instead. Enable **Configure user Group Policy loopback processing mode** (*Computer Configuration › Policies › Administrative Templates › System › Group Policy*) in a GPO that applies to the computers:

| Mode | User settings applied |
|---|---|
| **Merge** | The user's normal GPOs first, then the user settings from GPOs that apply to the **computer**; on conflict, the computer-side GPOs win |
| **Replace** | **Only** the user settings from GPOs that apply to the **computer**; the user's own GPOs are ignored |

> **Exam tip:** "When users sign in to RDS1, they must receive only the lockdown settings for RDS servers, regardless of which OU their account is in" → link a GPO with the **user** settings to the RDS servers' OU and enable **loopback in Replace mode** on those computers. "…in addition to their normal settings" → **Merge**.

## Administrative Templates and the Central Store

Administrative Template settings are defined by `.admx` files (language-neutral) and `.adml` files (per language). By default each admin workstation's GPMC reads `%SystemRoot%\PolicyDefinitions` — so two admins with different OS versions see different settings. Create a **Central Store** and every GPMC in the domain uses it automatically:

```text
C:\> mkdir \\contoso.com\SYSVOL\contoso.com\Policies\PolicyDefinitions
C:\> robocopy C:\Windows\PolicyDefinitions \\contoso.com\SYSVOL\contoso.com\Policies\PolicyDefinitions /E
```

Drop newer ADMX packs (for current Windows, Microsoft Edge, Office) into it — keep the `en-US` (and other language) subfolders for the ADML files.

## Starter GPOs, backup, restore and migration

* **Starter GPOs** are templates containing **Administrative Template settings only**. Create GPOs from them so baselines start consistent: `New-GPStarterGPO -Name 'Base - Workstations'`, then `New-GPO -Name 'Cfg - Floor3' -StarterGpoName 'Base - Workstations'`.
* **Backup and restore** in the same domain:

```powershell
PS C:\> Backup-GPO -All -Path \\FS1\GPOBackups
PS C:\> Restore-GPO -Name 'Sec - Servers Baseline' -Path \\FS1\GPOBackups
```

`Restore-GPO` puts back the GPO's **settings, security filtering and WMI filter link** with its original GUID. It does **not** restore **links** — they belong to the site/domain/OU, so re-link if the GPO was deleted. Note which OUs it was linked to (`Get-GPOReport`) before you delete anything.

* **Import** settings from a backup into a GPO in *another* domain or forest (or into a differently named GPO). A **migration table** (`.migtable`, created with the Migration Table Editor `mtedit.exe`) maps security principals and UNC paths that differ between environments:

```powershell
PS C:\> Import-GPO -BackupGpoName 'Sec - Servers Baseline' -Path \\FS1\GPOBackups `
          -TargetName 'Sec - Servers Baseline' -CreateIfNeeded -MigrationTable \\FS1\GPOBackups\fab.migtable
```

* `Copy-GPO` copies a live GPO, optionally across domains (`-SourceDomain`, `-TargetDomain`, `-MigrationTable`).

## Troubleshooting application

| Need | Tool |
|---|---|
| What *did* apply to this user on this computer? | `gpresult /r` (summary), `gpresult /h C:\rsop.html` (full HTML), or GPMC **Group Policy Results** |
| What *would* apply if I moved this user/computer? | GPMC **Group Policy Modeling** (simulated on a DC) |
| Report for a remote computer/user | `Get-GPResultantSetOfPolicy -Computer PC1 -User CONTOSO\aruiz -ReportType Html -Path C:\rsop.html` |
| Refresh now, locally | `gpupdate /force` (`/target:computer` or `/target:user`) |
| Refresh many computers remotely | `Invoke-GPUpdate -Computer PC1 -Force -RandomDelayInMinutes 0`, or right-click an OU in GPMC › **Group Policy Update** |
| Detailed processing log | Event Viewer › Applications and Services Logs › Microsoft › Windows › **GroupPolicy › Operational** |
| GPC and GPT versions in sync on every DC? | GPMC › GPO › **Status** tab (infrastructure status) |

`gpresult` run without elevation shows only user data; run elevated for computer settings. Remote refresh with GPMC or `Invoke-GPUpdate` works by creating a scheduled task on the target, so it needs the **Remote Scheduled Tasks Management** and WMI firewall rules open.

Common causes when "the GPO isn't applying":

1. Object is in a different OU than you think (`Get-ADComputer PC1 | Select DistinguishedName`).
2. GPO link disabled, GPO status has that half disabled, or Block Inheritance without Enforced.
3. Security filtering excludes the object, or computers can't **Read** the GPO (MS16-072).
4. WMI filter evaluates false.
5. Setting is in the **User** half but the GPO is linked to the computers' OU (and no loopback) — or vice versa.
6. Replication lag between DCs (version mismatch on the Status tab).

## Lab it yourself

```powershell
PS C:\> New-ADOrganizationalUnit RDS; New-ADOrganizationalUnit Kiosk
PS C:\> New-GPO 'Cfg - RDS Lockdown' | New-GPLink -Target 'OU=RDS,DC=contoso,DC=com'
PS C:\> Set-GPRegistryValue -Name 'Cfg - RDS Lockdown' -Key 'HKLM\Software\Policies\Microsoft\Windows\System' `
          -ValueName UserPolicyMode -Type DWord -Value 1   # loopback: 1 = Merge, 2 = Replace
PS C:\> Backup-GPO -Name 'Cfg - RDS Lockdown' -Path C:\GPOBackups
PS C:\> Remove-GPO 'Cfg - RDS Lockdown'; Restore-GPO -Name 'Cfg - RDS Lockdown' -Path C:\GPOBackups
PS C:\> Get-GPInheritance -Target 'OU=RDS,DC=contoso,DC=com'    # the link is gone after restore
```

Then move a test computer into the RDS OU, run `gpupdate /force` and `gpresult /h` on it, and read which GPOs were applied and denied (and why).

## Key takeaways

* A GPO = **GPC** in AD + **GPT** in SYSVOL; it does nothing until linked.
* **LSDOU**, last applied wins; within a container **link order 1** wins.
* **Enforced** beats Block Inheritance; Block Inheritance is set on the OU, Enforced on the link.
* Security filtering: keep **Read** for Authenticated Users or Domain Computers (MS16-072); use **Deny Apply** to exclude.
* One WMI filter per GPO, evaluated on the client; ProductType 1/2/3 = workstation/DC/server.
* **Loopback**: Replace = only computer-side user settings; Merge = both, computer-side wins.
* Central Store at `\\domain\SYSVOL\domain\Policies\PolicyDefinitions`; Starter GPOs hold Administrative Templates only.
* `Restore-GPO` doesn't restore links; `Import-GPO` + migration table moves settings across domains.
