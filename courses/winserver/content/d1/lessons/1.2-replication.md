## How AD DS replication works

AD DS replication is **multi-master** (any writable DC can originate a change), **pull-based** (a DC asks its partners for changes; partners only *notify*), and **store-and-forward** (a change hops DC to DC until all have it). What replicates is organised by **directory partition** (naming context):

| Partition | Replicates to |
|---|---|
| Schema | Every DC in the forest |
| Configuration (sites, services, partitions list) | Every DC in the forest |
| Domain (`DC=contoso,DC=com`) | Every DC in that domain; a partial, read-only copy to every GC in the forest |
| Application partitions — `DomainDnsZones`, `ForestDnsZones`, custom | Only the DCs that host a replica (for DNS: every DNS server DC in the domain or forest) |

### The bookkeeping

* **USN (update sequence number)** — a per-DC counter that increments on every change that DC writes. Each DC also has an **invocation ID** that identifies its database instance.
* **High-watermark vector** — per partner, per partition: "the highest USN I've already received from you".
* **Up-to-dateness vector (UTDV)** — per partition: "the highest *originating* USN I've seen from every DC in the forest". It prevents a DC from receiving the same change again via a different path (propagation dampening).
* **Attribute metadata** — version number, originating time, originating DC. **Conflicts** on the same attribute are resolved by highest **version**, then latest **timestamp**, then the originating DC's invocation ID (a GUID) as a final tie-breaker. Objects created with the same name in the same container get mangled to `CNF:` names.

```text
C:\> repadmin /showobjmeta DC1 "CN=User1,OU=Sales,DC=contoso,DC=com"
```

shows per-attribute version, originating DC and time — the fastest way to answer "who changed this and where?".

## Intrasite vs intersite

| | Intrasite | Intersite |
|---|---|---|
| Trigger | **Change notification**: the originating DC waits **15 seconds**, then notifies its first partner, then each next partner **3 seconds** apart | Schedule + interval on the **site link** (default every 180 min); notification only if enabled on the link |
| Compression | No | Yes |
| Topology | Bidirectional **ring** built by each DC's KCC, with extra shortcut connections so no DC is more than **3 hops** away | Spanning tree built by the **ISTG** in each site between bridgehead servers |
| Periodic safety net | Connection objects also pull on their own schedule (hourly by default) even without notifications | Site link schedule |

The **Knowledge Consistency Checker (KCC)** runs on every DC every **15 minutes** by default, recalculates the topology and creates, keeps or deletes automatic **connection objects** (always *inbound* — "DC2 replicates from DC1"). Connection objects you create by hand are never deleted by the KCC, which is why manual connections are usually a mistake left over from troubleshooting.

```text
C:\> repadmin /kcc DC2
C:\> repadmin /istg
```

> **Exam tip:** Changes made on a DC in the *same* site normally appear on other DCs in **seconds**. A change that takes up to three hours to reach a branch is just the **default site link interval** (180 min) — fix it by lowering the interval or enabling change notification on that link, not by forcing replication every time.

## Monitoring and forcing replication

### repadmin

| Command | Use |
|---|---|
| `repadmin /replsummary` | Forest-wide health: largest delta and failure counts per source and destination DC — start here |
| `repadmin /showrepl DC2` | Inbound partners of DC2 per partition, last attempt, last success, error |
| `repadmin /showrepl * /csv > repl.csv` | Every DC, exported for filtering |
| `repadmin /syncall DC1 /AdeP` | Push all partitions (`A`) from DC1 to all partners across sites (`e`), identifying DCs by DN (`d`) |
| `repadmin /replicate DC2 DC1 "DC=contoso,DC=com"` | Pull one partition to DC2 from DC1 now |
| `repadmin /queue DC2` | Pending inbound replication requests |
| `repadmin /showutdvec DC2 "DC=contoso,DC=com"` | DC2's up-to-dateness vector |
| `repadmin /replsingleobj DC2 DC1 <DN>` | Replicate one object |

Common result codes worth recognising:

| Code | Meaning | Usual cause |
|---|---|---|
| **1722** | The RPC server is unavailable | Source DC down, firewall blocking 135 or the dynamic RPC range, network path |
| **8524** | The DSA operation is unable to proceed because of a DNS lookup failure | Destination can't resolve the source's `<GUID>._msdcs.<forest>` CNAME — DNS client settings or missing records |
| **8453** | Replication access was denied | Permissions or secure channel problems on the source |
| **8614** | Directory service can't replicate because the time since last replication exceeds the tombstone lifetime | DC was isolated longer than the TSL — see below |

## Tombstones, lingering objects and strict consistency

Deleting an object doesn't remove it immediately: it becomes a **tombstone** (or, with Recycle Bin enabled, first a *deleted object*, then a *recycled object*) that replicates the deletion to every DC. Tombstones are garbage-collected after the **tombstone lifetime (TSL)** — **180 days** in every forest created on a currently supported Windows Server version. (Forests originally built on Windows 2000 or the RTM release of Windows Server 2003 may still have 60 days — the value doesn't change on upgrade.)

```powershell
PS C:\> (Get-ADObject "CN=Directory Service,CN=Windows NT,CN=Services,$((Get-ADRootDSE).configurationNamingContext)" `
          -Properties tombstoneLifetime).tombstoneLifetime
```

If a DC is cut off longer than the TSL, it misses deletions whose tombstones have since been purged. When it reconnects, objects it still holds would look new to everyone else — **lingering objects**.

* **Strict replication consistency** (on by default for forests created on Windows Server 2003 and later) makes a destination DC **refuse** updates to objects it doesn't have and block replication from that source, rather than re-creating deleted objects.
* DCs that haven't replicated for longer than the TSL stop replicating that partition (result **8614**).
* Remove lingering objects with **Lingering Object Liquidator** or `repadmin /removelingeringobjects <dest DC> <reference DC GUID> <partition> /advisory_mode` (advisory mode only lists them; rerun without it to delete).

> **Watch out:** A DC restored from a VM snapshot by a hypervisor **without** VM-Generation ID support can suffer a **USN rollback** — partners already have its "new" USNs in their high-watermarks and ignore its changes. The DC detects the rollback, stops inbound/outbound replication and pauses Netlogon. The supported fix is to demote (force-remove if necessary) and re-promote it — never "fix" it by editing registry values.

## SYSVOL replication with DFSR

`SYSVOL` (Group Policy templates and logon scripts) is not in the directory database; it's a file share replicated by **DFS Replication (DFSR)**. The old File Replication Service (FRS) is gone — Windows Server 2016 was the last version that supported it, and Windows Server 2019 or later DCs can't be promoted into a domain whose SYSVOL still uses FRS. If you inherit an old domain still on FRS, migrate it with `dfsrmig` *before* adding new DCs:

```text
C:\> dfsrmig /getglobalstate
Current DFSR global state: 'Eliminated'
Succeeded.
```

The four migration states are 0 *Start*, 1 *Prepared*, 2 *Redirected* and 3 *Eliminated*.

Monitor SYSVOL replication with the DFSR cmdlets, using the built-in replication group and folder names:

```powershell
PS C:\> Get-DfsrBacklog -GroupName "Domain System Volume" -FolderName "SYSVOL Share" `
          -SourceComputerName DC1 -DestinationComputerName DC3
PS C:\> Get-DfsrState -ComputerName DC3
```

A GPO that shows different versions in GPMC's **Status** tab (AD version vs SYSVOL version) usually means SYSVOL or AD replication is lagging on one DC. (Authoritative and non-authoritative SYSVOL restores are covered in the troubleshooting domain.)

## Lab it yourself

```powershell
PS C:\> New-ADUser ReplTest -Server DC1
PS C:\> repadmin /showobjmeta DC2 "CN=ReplTest,CN=Users,DC=contoso,DC=com"
PS C:\> Stop-Computer DC2 -Force      # or disconnect DC2's virtual NIC
PS C:\> repadmin /replsummary
PS C:\> Get-ADReplicationFailure -Target DC1
# reconnect DC2, then
PS C:\> repadmin /syncall DC1 /AdeP
PS C:\> repadmin /replsummary
```

Also try `repadmin /showrepl * /csv | ConvertFrom-Csv | Out-GridView` for an instant replication dashboard.

## Key takeaways

* Replication is multi-master, pull-based, per partition; GCs hold a partial copy of every domain.
* USNs, invocation IDs, high-watermark and **up-to-dateness vectors** prevent loops and duplicates; conflicts resolve by version, then time, then GUID.
* Intrasite: notify after **15 s**, then **3 s** between partners, ring with ≤3 hops, uncompressed. Intersite: site link schedule, compressed.
* KCC runs every **15 minutes**; one **ISTG** per site builds intersite connections.
* `repadmin /replsummary`, `/showrepl`, `/syncall /AdeP`, plus `Get-ADReplicationPartnerMetadata` and `Get-ADReplicationFailure`.
* TSL is **180 days**; DCs isolated longer cause lingering objects; strict replication consistency blocks them; result 8614.
* SYSVOL uses **DFSR** ("Domain System Volume" / "SYSVOL Share"); FRS must be migrated away with `dfsrmig`.
