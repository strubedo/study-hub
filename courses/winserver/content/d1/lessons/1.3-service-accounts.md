## The service account problem

Every Windows service and scheduled task runs as *something*. The classic answer — a normal domain user called `svc-sql` with "password never expires" — is one of the most common ways AD gets breached:

* Its password rarely changes and is often known to several admins or stored in scripts.
* If it has a **service principal name (SPN)**, any domain user can request a Kerberos service ticket for it and crack the password offline (*Kerberoasting*).
* It can usually log on interactively anywhere.

Managed accounts fix this by letting AD (or the local machine) generate and rotate long random passwords that no human knows.

## The options

| Account | Scope | Password managed by | Network identity | Introduced | Typical use |
|---|---|---|---|---|---|
| **LocalSystem** | One computer | n/a | Computer account (`CONTOSO\SERVER1$`) | — | OS services; far too privileged for apps |
| **NetworkService** | One computer | n/a | Computer account | — | Low-privilege services that need network access |
| **LocalService** | One computer | n/a | Anonymous | — | Low-privilege services with no network needs |
| **Virtual account** (`NT SERVICE\<service>`) | One computer | Windows | Computer account | 2008 R2 | Per-service isolation without AD objects (e.g. SQL Server default) |
| **Standalone MSA (sMSA)** | **One** domain computer | AD | Its own account (`CONTOSO\svc1$`) | 2008 R2 | A service on one server needing its own domain identity |
| **Group MSA (gMSA)** | **Many** computers | AD Key Distribution Service (KDS) | Its own account | 2012 | Server farms: IIS app pools, SQL Always On, AD FS, scheduled tasks |
| **Delegated MSA (dMSA)** | Specific machines | AD (KDS), keys bound to authorised machines | Its own account | **Windows Server 2025** | Replacing an existing legacy service account in place; resisting credential theft |

Selection logic the exam uses:

* **One server, no domain identity needed** → virtual account.
* **One server, needs its own domain identity** → sMSA (or gMSA, which also works on one server and is now the general recommendation).
* **Several servers share the identity** (load-balanced web farm, cluster) → **gMSA**.
* **Must migrate an existing user-based service account without reconfiguring permissions everywhere, and stop the old password from working** → **dMSA**.

## The KDS root key

gMSAs and dMSAs both derive their passwords from a **Key Distribution Service (KDS) root key**. It's created once and stored in the Configuration partition, so it serves the whole forest. Check for it first:

```powershell
PS C:\> Get-KdsRootKey
PS C:\> Add-KdsRootKey -EffectiveImmediately
```

Even with `-EffectiveImmediately`, DCs wait up to **10 hours** from the key's creation time before they use it, so the key can replicate to every DC first. In an isolated **lab only**, back-date it to skip the wait:

```powershell
PS C:\> Add-KdsRootKey -EffectiveTime ((Get-Date).AddHours(-10))
```

> **Watch out:** Creating a gMSA right after adding the KDS root key in production, then wondering why `Install-ADServiceAccount` fails on some servers, is a classic. Wait for the key to become effective and to replicate.

## Deploying a gMSA

1. **Create a group** for the servers that may use the account and add their computer objects.
2. **Create the gMSA**, naming who may retrieve its password:

    ```powershell
    PS C:\> New-ADGroup G-WebFarm -GroupScope Global
    PS C:\> Add-ADGroupMember G-WebFarm -Members WEB1$, WEB2$, WEB3$
    PS C:\> New-ADServiceAccount -Name gmsaWeb -DNSHostName gmsaWeb.contoso.com `
              -PrincipalsAllowedToRetrieveManagedPassword G-WebFarm `
              -ServicePrincipalNames http/web.contoso.com
    ```

    The password changes every **30 days** by default. You can set `-ManagedPasswordIntervalInDays` only when the account is created.

3. **Refresh the servers' group membership.** A computer's token includes its groups only from its last boot, so restart WEB1–WEB3 (or purge the system's Kerberos tickets with `klist -li 0x3e7 purge`).
4. **Install and test on each server** (needs the AD PowerShell module, `Install-WindowsFeature RSAT-AD-PowerShell`):

    ```powershell
    PS C:\> Install-ADServiceAccount gmsaWeb
    PS C:\> Test-ADServiceAccount gmsaWeb
    True
    ```

5. **Configure the service** to log on as `CONTOSO\gmsaWeb$` with a **blank password** (Services console, IIS application pool identity, SQL Server Configuration Manager). Note the trailing `$` — a gMSA is a special kind of computer-like account.

Scheduled tasks can run as a gMSA too, but only through PowerShell or `schtasks`, not the Task Scheduler GUI:

```powershell
PS C:\> $p = New-ScheduledTaskPrincipal -UserId 'CONTOSO\gmsaWeb$' -LogonType Password
PS C:\> Set-ScheduledTask -TaskName NightlyExport -Principal $p
```

### Troubleshooting a gMSA

| Symptom | Likely cause |
|---|---|
| `Test-ADServiceAccount` returns **False** | The server isn't in `PrincipalsAllowedToRetrieveManagedPassword` (directly or via a group), or it was added but hasn't rebooted |
| `Install-ADServiceAccount` errors that the key isn't available | KDS root key missing or not yet effective/replicated |
| Service starts on WEB1, fails on WEB3 | WEB3 isn't in the group, or has a stale token |
| Kerberos to the web app fails with gMSA identity | SPN still registered on the old user account (duplicate SPN) — move it to the gMSA |

```powershell
PS C:\> Get-ADServiceAccount gmsaWeb -Properties PrincipalsAllowedToRetrieveManagedPassword
PS C:\> Set-ADServiceAccount gmsaWeb -PrincipalsAllowedToRetrieveManagedPassword G-WebFarm, WEB4$
```

> **Exam tip:** `Set-ADServiceAccount -PrincipalsAllowedToRetrieveManagedPassword` **replaces** the whole list. To add one server, either include the existing entries or — better — just add the server to the group the gMSA already trusts.

## Standalone MSAs (briefly)

```powershell
PS C:\> New-ADServiceAccount -Name msaBackup -RestrictToSingleComputer
PS C:\> Add-ADComputerServiceAccount -Identity SERVER1 -ServiceAccount msaBackup
# on SERVER1
PS C:\> Install-ADServiceAccount msaBackup
```

An sMSA is tied to exactly one computer; a gMSA can do everything an sMSA does and more, so new designs usually use gMSAs.

## Delegated MSAs on Windows Server 2025

A **dMSA** looks like a gMSA (managed, random keys from the KDS root key) but adds two things:

* It can **supersede an existing service account**. During migration, the dMSA inherits the access of the old account; after migration completes, **the old account's password can no longer be used** — authentication attempts are redirected to the dMSA.
* Authentication is **tied to the machine identities** you authorise, which makes harvested credentials far less useful (it's designed to blunt Kerberoasting).

Requirements and limits:

* At least one **Windows Server 2025 DC** that clients can discover — extending the schema alone isn't enough.
* A **KDS root key**.
* **Domain Admins** or **Enterprise Admins** (or equivalent delegated rights) to create or migrate.
* Clients must have dMSA logons enabled: the policy **Computer Configuration › Administrative Templates › System › Kerberos › Enable Delegated Managed Service Account logons**, or the registry value `DelegatedMSAEnabled = 1` under `HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Policies\System\Kerberos\Parameters`.
* Every server that uses the legacy account must run a dMSA-capable OS (Windows Server 2025); a server that can't use dMSAs fails to authenticate once the old account is disabled.
* One legacy account per dMSA; you **can't migrate a gMSA or sMSA to a dMSA**; you can't force a dMSA password reset.
* No specific domain or forest functional level is required.

### Create a standalone dMSA

```powershell
PS C:\> New-ADServiceAccount -Name dmsaApp -DNSHostName dmsaApp.contoso.com `
          -CreateDelegatedServiceAccount -KerberosEncryptionType AES256
PS C:\> Set-ADServiceAccount dmsaApp -PrincipalsAllowedToRetrieveManagedPassword 'APP1$'
```

For standalone use (no account being superseded), Microsoft's procedure also sets the dMSA's `msDS-DelegatedMSAState` attribute to **3**; check it with `Get-ADServiceAccount dmsaApp -Properties msDS-DelegatedMSAState`.

### Migrate a legacy service account

```powershell
PS C:\> Start-ADServiceAccountMigration -Identity dmsaApp `
          -SupersededAccount 'CN=svc-app,OU=Service,DC=contoso,DC=com'
# restart the services that used svc-app so they pick up the dMSA, verify, then:
PS C:\> Complete-ADServiceAccountMigration -Identity dmsaApp `
          -SupersededAccount 'CN=svc-app,OU=Service,DC=contoso,DC=com'
```

* `Complete-ADServiceAccountMigration` **disables** the old account and moves its SPNs, delegation settings and authentication policy to the dMSA. Microsoft recommends staying in the started state for at least two ticket lifetimes (about 14 days) before completing, so every host has been learned.
* `Undo-ADServiceAccountMigration` backs out a migration started on the wrong account.
* `Reset-ADServiceAccountMigration` returns the pair to an unlinked state.
* **Never delete** the superseded account after completion — you might need to revert, and deleting it causes problems.

> **Real world:** In 2025 researchers showed that anyone able to create a dMSA in some OU could point its migration link at a privileged account (*BadSuccessor*). Microsoft fixed it in the August 2025 updates (CVE-2025-53779); patch every Windows Server 2025 DC and audit who can create objects in your OUs.

Events for migration, permission adds and key fetches are logged in **Applications and Services Logs › Microsoft › Windows › Security-Kerberos › Operational**, which is **disabled by default** — enable it before you troubleshoot.

## Lab it yourself

```powershell
PS C:\> Add-KdsRootKey -EffectiveTime ((Get-Date).AddHours(-10))     # lab only
PS C:\> New-ADGroup G-gMSA-Hosts -GroupScope Global
PS C:\> Add-ADGroupMember G-gMSA-Hosts -Members SRV1$
PS C:\> New-ADServiceAccount gmsaLab -DNSHostName gmsaLab.contoso.com -PrincipalsAllowedToRetrieveManagedPassword G-gMSA-Hosts
# On SRV1, after a restart
PS C:\> Install-WindowsFeature RSAT-AD-PowerShell
PS C:\> Install-ADServiceAccount gmsaLab; Test-ADServiceAccount gmsaLab
PS C:\> $a = New-ScheduledTaskAction -Execute cmd.exe -Argument '/c whoami > C:\Temp\whoami.txt'
PS C:\> $p = New-ScheduledTaskPrincipal -UserId 'CONTOSO\gmsaLab$' -LogonType Password
PS C:\> Register-ScheduledTask -TaskName gmsaTest -Action $a -Principal $p
PS C:\> Start-ScheduledTask gmsaTest; Get-Content C:\Temp\whoami.txt
```

(Grant `CONTOSO\gmsaLab$` the **Log on as a batch job** right in Local Security Policy first, and create `C:\Temp`.) The output file should read `contoso\gmsalab$`.

Then remove SRV1 from the group, restart it and watch `Test-ADServiceAccount` return False.

## Key takeaways

* Prefer managed accounts over user accounts with static passwords: **virtual** (local), **sMSA** (one server), **gMSA** (many servers), **dMSA** (2025, supersedes legacy accounts).
* gMSA and dMSA need a **KDS root key** (`Add-KdsRootKey`); it takes up to **10 hours** to become usable; back-dating is for labs only.
* gMSA deploy: group of hosts → `New-ADServiceAccount -PrincipalsAllowedToRetrieveManagedPassword` → reboot hosts → `Install-ADServiceAccount` → `Test-ADServiceAccount` → service logs on as `DOMAIN\name$`, blank password.
* `Set-ADServiceAccount -PrincipalsAllowedToRetrieveManagedPassword` replaces the list — manage via the group.
* dMSA: needs a **Windows Server 2025 DC**, `-CreateDelegatedServiceAccount`, client policy *Enable Delegated Managed Service Account logons*, and `Start-`/`Complete-ADServiceAccountMigration` to supersede an old account.
* You can't migrate a gMSA to a dMSA, and you never delete the superseded account.
