## Security principals in a nutshell

A **security principal** is anything that can authenticate and be granted access: users, computers, groups (security groups only), and managed service accounts. Each has a **SID** (domain SID + RID from the RID master's pool) that ACLs reference — which is why renaming an account never breaks permissions, but deleting and re-creating one with the same name always does.

Tools you'll use:

| Tool | Strength |
|---|---|
| **Active Directory Administrative Center (ADAC)** | Modern console; Recycle Bin and fine-grained password policy UI; **Windows PowerShell History** pane shows the cmdlet behind every click |
| Active Directory Users and Computers (ADUC) | Classic; turn on *View › Advanced Features* to see the Attribute Editor and object Security tabs |
| **ActiveDirectory PowerShell module** | Bulk and repeatable work — the exam's favourite |
| `csvde` / `ldifde` | Bulk export/import. `csvde` can't set passwords, so imported users are created disabled |
| `dsadd`, `dsmod`, `dsquery` | Legacy command-line tools, still present |

## Users

```powershell
PS C:\> $pw = Read-Host -AsSecureString 'Initial password'
PS C:\> New-ADUser -Name 'Ana Ruiz' -GivenName Ana -Surname Ruiz -SamAccountName aruiz `
          -UserPrincipalName aruiz@contoso.com -Path 'OU=Sales,DC=contoso,DC=com' `
          -AccountPassword $pw -ChangePasswordAtLogon $true -Enabled $true
```

Bulk creation from a CSV:

```powershell
PS C:\> Import-Csv C:\hr\newhires.csv | ForEach-Object {
          New-ADUser -Name $_.Name -SamAccountName $_.Sam -UserPrincipalName "$($_.Sam)@contoso.com" `
            -Department $_.Dept -Path 'OU=Staff,DC=contoso,DC=com' `
            -AccountPassword $pw -ChangePasswordAtLogon $true -Enabled $true }
```

ADUC's **Copy** on a template user (disabled, with group memberships, department, profile path) does the same for one-off hires: it copies memberships and selected attributes, but not the name or password.

### Everyday account maintenance

| Task | Cmdlet |
|---|---|
| Reset a password and force change | `Set-ADAccountPassword aruiz -Reset -NewPassword $pw` then `Set-ADUser aruiz -ChangePasswordAtLogon $true` |
| Unlock | `Unlock-ADAccount aruiz` |
| Find locked accounts | `Search-ADAccount -LockedOut -UsersOnly` |
| Find accounts inactive for 90 days | `Search-ADAccount -AccountInactive -TimeSpan 90.00:00:00 -UsersOnly` |
| Find expired / expiring accounts | `Search-ADAccount -AccountExpired` / `-AccountExpiring -TimeSpan 7.00:00:00` |
| Find passwords that never expire | `Search-ADAccount -PasswordNeverExpires` |
| Disable | `Disable-ADAccount aruiz` |
| Set an end date for a contractor | `Set-ADAccountExpiration aruiz -DateTime '2026-12-31'` |
| Change many at once | `Get-ADUser -Filter 'Department -eq "Sales"' -SearchBase 'OU=Staff,DC=contoso,DC=com' \| Set-ADUser -Office Chicago` |

> **Watch out:** `lastLogon` is **not replicated** — each DC keeps its own. `lastLogonTimestamp` **is** replicated but only updated when it's older than about 9–14 days, so it's accurate to within two weeks. That's precise enough for "inactive for 90 days" reports (what `Search-ADAccount -AccountInactive` uses), not for "did she log on this morning?".

## Computers

* Joining a computer creates its account in the default **Computers** container unless you pre-stage it or redirect the default with `redircmp "OU=NewPCs,DC=contoso,DC=com"` (`redirusr` does the same for users).
* By default any authenticated user can join up to **10** computers (`ms-DS-MachineAccountQuota`). Hardened domains set it to 0 and delegate the *Create computer objects* permission on an OU instead.
* **Pre-staging** — `New-ADComputer -Name PC-BR1-07 -Path 'OU=Branch1,DC=contoso,DC=com'` — puts the object in the right OU (and the right GPO scope) before the first boot.
* **Offline domain join** for machines that can't reach a DC during deployment:

```text
C:\> djoin /provision /domain contoso.com /machine PC-BR1-07 /machineou "OU=Branch1,DC=contoso,DC=com" /savefile C:\odj\pc-br1-07.txt
C:\> djoin /requestODJ /loadfile C:\odj\pc-br1-07.txt /windowspath %SystemRoot% /localos
```

## OUs

OUs hold users, computers and groups for **Group Policy targeting** and **delegation** — not for permissions on resources (you can't put an OU in an ACL). New OUs are protected from accidental deletion by default:

```powershell
PS C:\> New-ADOrganizationalUnit -Name Branch1 -Path 'OU=Sites,DC=contoso,DC=com'
PS C:\> Set-ADOrganizationalUnit 'OU=Branch1,OU=Sites,DC=contoso,DC=com' -ProtectedFromAccidentalDeletion $false
PS C:\> Remove-ADOrganizationalUnit 'OU=Branch1,OU=Sites,DC=contoso,DC=com' -Recursive
```

## Groups

### Type

* **Security** groups have a SID and can appear in ACLs and user rights. They can also be mail-enabled.
* **Distribution** groups have no use in access control — email only. Converting distribution → security is allowed (and easy to forget when a "group doesn't work" in an ACL).

### Scope

| Scope | Can contain | Can be used to grant access to | Replication of membership |
|---|---|---|---|
| **Domain local** | Users, computers, global and universal groups from **any domain in the forest or a trusted domain/forest**; domain local groups from the **same** domain | Resources in **its own domain** only | Domain partition only |
| **Global** | Users, computers and global groups from the **same domain** only | Resources in any domain in the forest or in trusting domains/forests | Domain partition only |
| **Universal** | Users, computers, global and universal groups from **any domain in the same forest** | Resources in any domain in the forest or in trusting domains/forests | **Membership stored in every GC** (forest-wide replication) |

The built-in groups in the **Builtin** container (Administrators, Backup Operators, Account Operators...) have a special **Builtin Local** scope: they behave like domain local groups, grant rights on the DCs, and their scope and type can't be changed.

### AGDLP — the pattern the exam expects

**A**ccounts go into **G**lobal groups (by role, per domain) → global groups go into **D**omain **L**ocal groups (by resource access) → domain local groups get **P**ermissions.

```text
CONTOSO\aruiz  →  G-Sales (global)  →  DL-FS1-Sales-Modify (domain local)  →  NTFS Modify on \\FS1\Sales
```

In multi-domain forests, insert universal groups: **AGUDLP** — global groups from each domain into a universal group, the universal group into the domain local resource group. Keep universal group membership stable (put *groups*, not users, in them), because every change replicates to every GC in the forest.

```powershell
PS C:\> New-ADGroup -Name G-Sales -GroupScope Global -GroupCategory Security -Path 'OU=Groups,DC=contoso,DC=com'
PS C:\> New-ADGroup -Name DL-FS1-Sales-Modify -GroupScope DomainLocal -Path 'OU=Groups,DC=contoso,DC=com'
PS C:\> Add-ADGroupMember -Identity G-Sales -Members aruiz, bchen
PS C:\> Add-ADGroupMember -Identity DL-FS1-Sales-Modify -Members G-Sales
PS C:\> Get-ADGroupMember DL-FS1-Sales-Modify -Recursive | Select-Object Name
PS C:\> Get-ADPrincipalGroupMembership aruiz | Select-Object Name, GroupScope
```

`Add-ADGroupMember` adds members **to a group**; `Add-ADPrincipalGroupMembership` adds **a principal to groups** (`Add-ADPrincipalGroupMembership aruiz -MemberOf G-Sales, G-VPN`).

> **Exam tip:** A user added to a group can't use the new access until they get a **new access token** — sign out and in (for file servers, a new SMB session), or `klist purge` for Kerberos tickets. "The user was added to the group five minutes ago and still gets Access denied" → have the user sign out and back in.

### Changing scope

| From → To | Allowed when |
|---|---|
| Global → Universal | The group is **not a member of another global group** |
| Domain local → Universal | The group **contains no other domain local groups** |
| Universal → Global | The group **contains no universal groups** (and no members from other domains) |
| Universal → Domain local | The group is **not a member of another universal group** |
| Global ↔ Domain local | **Not directly** — convert through universal |

```powershell
PS C:\> Set-ADGroup G-Sales -GroupScope Universal
```

### Time-limited membership

With the forest at the Windows Server 2016 functional level or higher, you can enable the **Privileged Access Management feature** (an irreversible optional feature) and then add members that expire automatically — their Kerberos tickets are limited to the remaining time:

```powershell
PS C:\> Enable-ADOptionalFeature 'Privileged Access Management Feature' -Scope ForestOrConfigurationSet -Target contoso.com
PS C:\> Add-ADGroupMember -Identity G-ServerAdmins -Members aruiz -MemberTimeToLive (New-TimeSpan -Hours 4)
```

(Securing privileged groups — Protected Users, AdminSDHolder, delegation — belongs to the AD DS security topic.)

## Lab it yourself

```powershell
PS C:\> $pw = Read-Host -AsSecureString 'Lab password'
PS C:\> 'Sales','Groups','Staff' | ForEach-Object { New-ADOrganizationalUnit $_ }
PS C:\> 1..5 | ForEach-Object { New-ADUser "Test$_" -Path 'OU=Staff,DC=contoso,DC=com' -AccountPassword $pw -Enabled $true }
PS C:\> New-ADGroup G-Test -GroupScope Global -Path 'OU=Groups,DC=contoso,DC=com'
PS C:\> Get-ADUser -Filter 'Name -like "Test*"' | ForEach-Object { Add-ADGroupMember G-Test -Members $_ }
PS C:\> Set-ADGroup G-Test -GroupScope Universal
PS C:\> Search-ADAccount -AccountDisabled -UsersOnly
```

Open ADAC, make a change in the GUI and look at the **Windows PowerShell History** pane to see the cmdlet it ran.

## Key takeaways

* Security groups go in ACLs; distribution groups are email-only.
* Domain local = permissions in its own domain, members from anywhere trusted; global = members from its own domain, usable anywhere; universal = members from the forest, membership in every GC.
* Use **AGDLP** (AGUDLP across domains); keep universal groups populated with groups, not users.
* Scope changes go through universal; global → universal requires it not be nested in another global group.
* `Search-ADAccount` finds locked, inactive, expired and never-expiring accounts; `lastLogonTimestamp` is replicated but lags up to ~14 days.
* New group membership needs a **new logon token**.
* OUs are for GPOs and delegation, protected from accidental deletion by default.
