## Sites model the physical network

Domains and OUs describe *administration*. **Sites** describe *the network*: an AD DS site is a set of IP subnets with fast, reliable connectivity between them — typically one office, one datacenter, or one Azure region. Sites are stored in the forest-wide Configuration partition, so every domain in the forest shares the same site topology.

Sites drive three things:

1. **DC location.** The DC Locator maps a client's IP address to a subnet, the subnet to a site, and returns a DC (and GC) in that site first. Without correct subnets, a Chicago user may log on against a DC in Singapore.
2. **Replication.** Inside a site, DCs replicate quickly using change notification. Between sites, replication follows **site links** with schedules and intervals, and data is compressed.
3. **Site-aware services.** DFS Namespaces referrals, SYSVOL/DFSR, Exchange and many applications use the site to pick the nearest server. You can even link GPOs to sites (rarely a good idea, because a site GPO lives in one domain's SYSVOL).

## Objects you work with

| Object | Lives in | Purpose |
|---|---|---|
| Site | `CN=Sites,CN=Configuration,...` | Container for servers and NTDS Site Settings |
| Subnet | `CN=Subnets,CN=Sites,...` | Maps an IP prefix (e.g. `10.20.0.0/16`) to one site |
| Server object | `CN=Servers,CN=<site>` | Represents a DC in a site; contains its **NTDS Settings** object and connection objects |
| Site link | `CN=IP,CN=Inter-Site Transports` | Connects two or more sites with a cost, schedule and interval |
| Site link bridge | Same container | Groups site links into a transitive path when automatic bridging is disabled |
| NTDS Site Settings | Inside each site | Holds ISTG identity and **universal group membership caching** settings |

A new forest starts with **Default-First-Site-Name** and **DEFAULTIPSITELINK** (cost 100, replicate every 180 minutes). Rename the default site rather than leaving it — renaming is harmless.

## Building the topology

```powershell
PS C:\> New-ADReplicationSite -Name Chicago
PS C:\> New-ADReplicationSite -Name Dallas
PS C:\> New-ADReplicationSubnet -Name 10.20.0.0/16 -Site Chicago -Location 'Chicago, IL'
PS C:\> New-ADReplicationSubnet -Name 10.30.0.0/16 -Site Dallas
PS C:\> New-ADReplicationSiteLink -Name CHI-DAL -SitesIncluded Chicago, Dallas `
          -Cost 100 -ReplicationFrequencyInMinutes 60
PS C:\> Get-ADDomainController DC5 | Move-ADDirectoryServer -Site Dallas
```

When a DC is **promoted**, it's placed in the site that matches its IP subnet (or the site you name with `-SiteName`). If you later re-IP a DC into another subnet, it does **not** move automatically — move the server object yourself (Sites and Services drag-and-drop or `Move-ADDirectoryServer`).

> **Exam tip:** Users in a new branch authenticate against a DC in the wrong site even though the branch has a DC. Check that the branch **subnet** exists and is associated with the branch site. Clients outside any defined subnet show up as `NO_CLIENT_SITE` entries in `%SystemRoot%\debug\netlogon.log` on the DCs.

## Site link properties

| Property | Meaning | Default / limits |
|---|---|---|
| **Cost** | Relative preference. The KCC picks the path with the **lowest total cost** | 100 |
| **Replication interval** | How often replication is attempted while the schedule is open | 180 minutes; minimum **15**, in 15-minute steps, maximum 10,080 (one week) |
| **Schedule** | Hours when replication is allowed | Always available |
| **Transport** | IP (RPC over IP) or SMTP | Use IP. SMTP can't carry the domain partition and is legacy |

Use cost to express bandwidth and reliability: give faster or more reliable links lower costs, and set higher costs on backup links so they're used only when the primary path fails.

```powershell
PS C:\> Set-ADReplicationSiteLink CHI-DAL -Cost 50 -ReplicationFrequencyInMinutes 15
PS C:\> Get-ADReplicationSiteLink -Filter * | Format-Table Name, Cost, ReplicationFrequencyInMinutes, SitesIncluded
```

### Change notification between sites

By default intersite replication is **scheduled** (pull every *interval* minutes). For a well-connected site pair you can make it behave like intrasite replication — notify partners as soon as a change happens — by setting bit 1 of the site link's `options` attribute:

```powershell
PS C:\> Set-ADReplicationSiteLink CHI-DAL -Replace @{options = 1}
```

Intersite traffic is still compressed. Use this only on links with real bandwidth.

> **Watch out:** **Urgent replication** (account lockouts, RID changes, changes to trust secrets) is pushed immediately *within* a site, but across sites it waits for the next scheduled cycle unless change notification is enabled on the link. Password changes are a separate mechanism: they're forwarded straight to the PDC emulator regardless of sites.

## Site link bridges and transitivity

By default, **Bridge all site links** is enabled on the IP transport, which makes site links **transitive**: if Chicago–Dallas and Dallas–Denver exist, the KCC may create a direct Chicago–Denver connection with a cost equal to the sum.

Turn bridging **off** when the network is *not* fully routed — for example, firewalls only allow branch sites to talk to the hub. Then create explicit **site link bridges** for the paths that do work:

```powershell
PS C:\> New-ADReplicationSiteLinkBridge -Name HUB-Bridge -SiteLinksIncluded CHI-DAL, CHI-DEN
```

(Clear the *Bridge all site links* check box on the **IP** container properties in Sites and Services.)

## Bridgehead servers and the ISTG

* In each site, one DC is the **Intersite Topology Generator (ISTG)**. Its KCC creates the intersite connection objects for the site.
* The DCs that actually replicate across a site link are **bridgehead servers**. By default the ISTG chooses them automatically, per directory partition, and spreads connections across eligible DCs.
* You can designate **preferred bridgehead servers** (server object › Properties › *Transports available for inter-site data transfer* › IP).

> **Watch out:** Once you designate any preferred bridgehead in a site, the ISTG uses **only** the preferred ones. If they're all down — or none of them hosts a given partition (for example, no preferred bridgehead is a GC or holds a particular domain partition) — that data **stops replicating** to and from the site. Prefer automatic selection unless a firewall forces your hand, and if you designate, cover every partition and designate at least two.

## Sites without a domain controller

A site with clients but no DC (for example, a tiny office) still needs a subnet object so clients get the **closest** DC. DCs perform **automatic site coverage**: a DC in the site with the lowest-cost link to the empty site registers its SRV records for that site too.

## Universal group membership caching

At logon, a DC must know the user's **universal group** memberships, which only a **global catalog** has. In a branch whose DC isn't a GC, every logon would cross the WAN to a GC — and if the WAN is down, logon fails for users of a multi-domain forest.

Two fixes:

| Option | Pros | Cons |
|---|---|---|
| Make the branch DC a **GC** | Fastest logons; supports GC-dependent apps (e.g. some Exchange lookups) | Replicates a partial copy of every domain in the forest over the WAN |
| Enable **universal group membership caching (UGMC)** on the site | No GC replication; logons work offline after the first one | The *first* logon per user still needs a GC; cache refresh every 8 hours by default from the refresh site |

```powershell
PS C:\> Set-ADReplicationSite -Identity Branch1 -UniversalGroupCachingEnabled $true `
          -UniversalGroupCachingRefreshSite HQ
```

In Sites and Services: site › **NTDS Site Settings** › Properties › *Enable Universal Group Membership Caching*. It's a **per-site** setting, so all DCs in the site participate.

> **Exam tip:** "Branch office with a single DC, small WAN link, users must be able to log on when the WAN fails, and you must **minimise replication traffic**" → **UGMC**, not a GC. "The branch runs an application that needs a global catalog" → make the branch DC a **GC**.

## Lab it yourself

```powershell
PS C:\> Rename-ADObject (Get-ADReplicationSite Default-First-Site-Name).DistinguishedName -NewName HQ
PS C:\> New-ADReplicationSite Branch1
PS C:\> New-ADReplicationSubnet 10.0.0.0/24 -Site HQ
PS C:\> New-ADReplicationSubnet 10.0.1.0/24 -Site Branch1
PS C:\> New-ADReplicationSiteLink HQ-Branch1 -SitesIncluded HQ, Branch1 -Cost 200 -ReplicationFrequencyInMinutes 15
PS C:\> Get-ADDomainController DC2 | Move-ADDirectoryServer -Site Branch1
PS C:\> Set-ADReplicationSite Branch1 -UniversalGroupCachingEnabled $true
PS C:\> repadmin /kcc DC2
PS C:\> Get-ADReplicationConnection -Filter * | Format-Table Name, ReplicateFromDirectoryServer, ReplicateToDirectoryServer
```

Give a client in `10.0.1.0/24` an address and run `nltest /dsgetsite` to see it land in Branch1.

## Key takeaways

* Sites = well-connected subnets; they drive DC location and replication. **Subnets** must map every client range to a site.
* Defaults: `DEFAULTIPSITELINK`, cost **100**, interval **180 min**; minimum interval **15 min**.
* Lowest **total cost** wins; use higher costs for backup links.
* **Bridge all site links** (transitivity) is on by default; disable it on non-fully-routed networks and create explicit bridges.
* Preferred bridgeheads are all-or-nothing per site — they can silently stop replication if they fail or miss a partition.
* `options = 1` on a site link enables change notification across sites.
* **UGMC** lets branch DCs log users on without a local GC (after the first logon) and avoids GC replication; it's set per site in NTDS Site Settings.
