## Trust vocabulary that trips people up

A **trust** is a relationship that lets a domain controller in one domain accept authentication done by a domain controller in another. Get the direction words straight first, because exam answers hinge on them:

* The **trusting** domain holds the **resources**. It trusts the other side to vouch for users.
* The **trusted** domain holds the **accounts**.
* The trust points from trusting → trusted; **access flows the opposite way** (users in the trusted domain reach resources in the trusting domain).
* In the New Trust Wizard, the *resource* domain creates an **outgoing** trust; the *account* domain creates the matching **incoming** trust. A **two-way** trust is simply both directions at once.

Memory hook: *"the resource domain trusts the account domain."* If fabrikam.com users need files on contoso.com servers, contoso.com must trust fabrikam.com — an outgoing trust from contoso.com, incoming at fabrikam.com.

**Transitivity** decides whether the trust extends beyond the two partners. If A trusts B transitively and B trusts C transitively, A trusts C.

## Trust types

| Type | Between | Direction | Transitive? | Created |
|---|---|---|---|---|
| **Parent-child** | A domain and its child in the same tree | Two-way | Yes | Automatically when the child domain is created; can't be removed |
| **Tree-root** | Forest root and the root of a new tree in the same forest | Two-way | Yes | Automatically |
| **Shortcut** | Any two domains in the **same forest** | One- or two-way | Yes | Manually — to shorten the referral path between deep domains |
| **External** | A domain in another forest (or a legacy NT domain) | One- or two-way | **No** | Manually — when you need access to *one* domain only |
| **Forest** | The **forest root domains** of two forests | One- or two-way | Yes **between the two forests only** (all domains in both) — not on to a third forest | Manually |
| **Realm** | An AD domain and a non-Windows Kerberos V5 realm (e.g. MIT Kerberos) | One- or two-way | Either (you choose) | Manually |

Key consequences:

* **Forest trusts are not transitive across forests.** If contoso.com has a forest trust with fabrikam.com, and fabrikam.com has one with adatum.com, contoso.com users still can't reach adatum.com. Create a direct trust.
* An **external trust** is the answer when you must limit access to a single domain of the other forest, or when the other side isn't the forest root. It uses NTLM (and Kerberos only in limited cases), so prefer a forest trust when both are the forest roots and you want Kerberos and UPN routing.
* A **shortcut trust** fixes slow authentication between two domains that are many hops apart in the same forest (e.g. `sales.emea.contoso.com` users accessing `eng.apac.contoso.com` servers). It doesn't grant anything that the default transitive trusts didn't already allow — it just shortens the Kerberos referral chain.

## Prerequisites for a forest trust

1. **Name resolution both ways.** Each forest's DNS must resolve the other's domain names and SRV records. Use **conditional forwarders** (or stub/secondary zones). If you store the conditional forwarder in AD, choose "All DNS servers in this forest" so every DC can resolve the partner.
2. **Network reachability** between DCs on the AD ports (53, 88, 135 + dynamic RPC, 389, 445, 464, 636, 3268).
3. **Rights:** Domain Admins in the forest root domain or Enterprise Admins in each forest (or someone on the other side to create their half with the same trust password).
4. Both forests at a functional level that supports forest trusts — every level a Windows Server 2025 DC can run in qualifies.

```powershell
PS C:\> Add-DnsServerConditionalZone -Name fabrikam.com -MasterServers 192.168.20.10 `
          -ReplicationScope Forest
```

## Creating and verifying a trust

The usual tool is **Active Directory Domains and Trusts** › domain properties › **Trusts** tab › **New Trust**. The wizard asks for the partner name, type (it offers *Forest trust* only when both are forest roots), direction, which sides to create (*This domain only*, or *Both this domain and the specified domain* if you have credentials for the other forest), the **authentication scope**, and whether to confirm the trust.

The ActiveDirectory PowerShell module can read trusts but has **no cmdlet to create them**:

```powershell
PS C:\> Get-ADTrust -Filter * | Format-Table Name, Direction, ForestTransitive, SelectiveAuthentication, SIDFilteringQuarantined
```

From the command line:

```text
C:\> nltest /domain_trusts
C:\> netdom trust contoso.com /domain:fabrikam.com /verify
```

`netdom trust ... /reset` resets the trust secret if the two sides have fallen out of sync. Trust passwords otherwise change automatically.

## Authentication scope: forest-wide vs selective

When you create an external or forest trust you choose how much of the trusting side the trusted users can **authenticate to**:

* **Forest-wide authentication** (domain-wide for an external trust): users from the trusted forest are treated like *Authenticated Users* everywhere in the trusting forest. They still need NTFS/share permissions, but anything granted to Authenticated Users or Everyone is open to them.
* **Selective authentication**: users from the trusted forest can't authenticate to **any** computer in the trusting forest unless you grant them the **Allowed to Authenticate** permission on that computer's object.

```text
ADUC (Advanced Features) › FS1 computer object › Properties › Security
  Add: FABRIKAM\Project-X-Users   Allow: Allowed to Authenticate
```

> **Exam tip:** "Users in fabrikam.com must access only **Server1** in contoso.com; the solution must prevent them authenticating to any other server" → enable **selective authentication** on the trust and grant **Allowed to Authenticate** on **Server1's computer object** (then normal share/NTFS permissions). Granting permissions on the share alone isn't enough to block authentication elsewhere.

You can change the scope later on the trust's **Authentication** tab, or with `netdom trust ... /selectiveauth:yes`.

## SID filtering

When a user from a trusted forest authenticates, their token can carry SIDs in **SID history** (from a migration) — and a malicious admin in the trusted forest could inject a privileged SID such as your Enterprise Admins. **SID filtering** strips SIDs that don't belong to the trusted domain/forest.

* On by default for **external** trusts (called *quarantine* — `netdom trust ... /quarantine:yes`).
* On by default for **forest** trusts, which filter any SID not from the trusted forest.
* During a migration you may temporarily allow SID history across a forest trust with `netdom trust contoso.com /domain:fabrikam.com /enablesidhistory:yes` — only if you trust the other forest's admins — then turn it off when the migration ends.

> **Watch out:** Never disable SID filtering on a trust to a forest run by a different organisation. Within one forest, there's no SID filtering at all — the forest is the security boundary, not the domain.

## Name suffix routing

A forest trust carries the list of **name suffixes** each forest owns (its DNS domain names and its **UPN suffixes**). A user who logs on as `alice@fabrikam.com` at a contoso.com computer is routed to the fabrikam.com forest because of that list. On the trust's **Name Suffix Routing** tab you can enable or disable suffixes — for example, if both forests claim the same UPN suffix, the conflict is shown and routing for it is disabled. If you add a new UPN suffix to a forest *after* the trust exists, check this tab on the other side and enable it if needed.

## Choosing the right trust (decision guide)

| Requirement | Trust |
|---|---|
| Two companies merge; all users in both forests need access across all domains, Kerberos, UPN logons | Two-way **forest** trust |
| Partner's users need one domain of ours only; limit exposure | One-way **external** trust (our domain trusts theirs), plus selective authentication if they need only some servers |
| Logons between two child domains deep in our forest are slow | **Shortcut** trust |
| Linux hosts in an MIT Kerberos realm must accept AD users | **Realm** trust |
| Partner forest users may only reach specific servers | Forest or external trust with **selective authentication** + **Allowed to Authenticate** |

## Lab it yourself

Build a second forest (`fabrikam.com`) with one DC on the same Hyper-V switch, then:

```powershell
# On DC1.contoso.com
PS C:\> Add-DnsServerConditionalZone -Name fabrikam.com -MasterServers 10.0.0.20 -ReplicationScope Forest
# On DC1.fabrikam.com
PS C:\> Add-DnsServerConditionalZone -Name contoso.com -MasterServers 10.0.0.10 -ReplicationScope Forest
```

Create a two-way forest trust with selective authentication in Active Directory Domains and Trusts (create both sides using fabrikam credentials), then run `Get-ADTrust -Filter *` and `netdom trust contoso.com /domain:fabrikam.com /verify`. Try to open `\\FS1.contoso.com\share` as a fabrikam user before and after granting **Allowed to Authenticate** on FS1.

## Key takeaways

* The **resource (trusting)** domain trusts the **account (trusted)** domain; access flows against the trust arrow.
* Parent-child and tree-root: automatic, two-way, transitive. Shortcut: manual, same forest, transitive, speeds referrals.
* External: non-transitive, single domain. Forest: between forest roots, transitive across both forests but **not** to a third.
* Forest trusts need two-way **DNS resolution** (conditional forwarders) and Enterprise Admin-level rights.
* **Selective authentication** + **Allowed to Authenticate** on computer objects restricts which servers trusted users can reach.
* **SID filtering** is on by default for external and forest trusts; `/enablesidhistory` relaxes it for migrations only.
* No PowerShell cmdlet creates trusts — use AD Domains and Trusts (or netdom); `Get-ADTrust`, `nltest /domain_trusts` and `netdom trust /verify` inspect them.
