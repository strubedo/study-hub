## Why single-master roles exist

AD DS is multi-master: any writable DC can originate most changes, and conflicts are resolved afterwards by version number and timestamp. A few operations can't tolerate a conflict — two DCs issuing the same RID, two admins extending the schema in incompatible ways — so exactly one DC in the scope performs them. Those are the **Flexible Single Master Operations (FSMO)** roles, also called operations masters.

| Role | Scope | What it does | Impact when it's offline |
|---|---|---|---|
| **Schema master** | Forest (one per forest) | Only DC that can write to the schema partition | Schema extensions (adprep `/forestprep`, Exchange, new attributes) fail. Day-to-day work is unaffected |
| **Domain naming master** | Forest | Adds and removes domains and application partitions (crossRef objects) | You can't add or remove domains or app partitions. Otherwise unnoticed |
| **RID master** | Domain (one per domain) | Hands each DC blocks (pools) of relative IDs used to build SIDs; also required for cross-domain object moves | DCs keep creating objects until their current and standby pools run out, then creation of users, groups and computers fails. New DCs can't get a first pool |
| **PDC emulator** | Domain | Time source for the domain (forest-root PDC is the top of the forest time hierarchy); receives password changes urgently; rechecks bad passwords before failing a logon; processes account lockout; default DC for editing GPOs | Noticed quickly: time drift, users locked out inconsistently, recently changed passwords rejected at other DCs, GPMC complains |
| **Infrastructure master** | Domain | Updates references to objects in *other* domains (phantoms) — e.g. the name/DN of a user from another domain who was renamed or moved and is a member of a local group | Cross-domain group memberships show stale names. Only matters in multi-domain forests |

Three phrases to remember: **forest-wide two** (schema, domain naming), **domain-wide three** (RID, PDC, infrastructure), and **only the PDC emulator is noticed in minutes**.

### RID master detail

Every security principal's SID is the domain SID plus a RID. The RID master gives each DC a pool (500 RIDs by default) and a standby pool; DCs request more as their pool is consumed. If the RID master is down for a while in a domain that creates many objects, DCs eventually can't create security principals. Check pool status with:

```text
C:\> dcdiag /test:ridmanager /v
```

### PDC emulator and time

Domain members sync time from DCs in their domain, DCs sync from the PDC emulator of their domain (or a DC higher in the hierarchy), and the **PDC emulator of the forest root domain** should be the only DC pointed at an external NTP source. If you move that role, reconfigure time on the new holder:

```text
C:\> w32tm /config /manualpeerlist:"time.windows.com,0x8" /syncfromflags:manual /reliable:yes /update
C:\> w32tm /resync
C:\> w32tm /query /source
```

Then set the old PDC emulator back to domain hierarchy: `w32tm /config /syncfromflags:domhier /update`.

> **Exam tip:** Kerberos tolerates only **5 minutes** of clock skew by default. A scenario where logons fail after a FSMO move and `w32tm /query /source` on the new forest-root PDC emulator shows `Local CMOS Clock` points straight to time configuration on the PDC emulator.

### Infrastructure master and the global catalog

A GC already has a partial copy of every object in the forest, so an infrastructure master that is also a GC never sees anything stale and **stops doing its job**. Placement rule:

* **Single-domain forest** — no cross-domain references, put it anywhere.
* **Every DC in the domain is a GC** — every DC already has current data, put it anywhere.
* **AD Recycle Bin enabled** — each DC maintains its own cross-domain references, so the role has no work to do.
* Otherwise — the infrastructure master **must not** be on a GC. A conflicting placement logs a warning in the Directory Service log.

Most modern forests make every DC a GC, which makes the rule moot — but the exam still asks it.

## Finding the role holders

```text
C:\> netdom query fsmo
Schema master               DC1.contoso.com
Domain naming master        DC1.contoso.com
PDC                         DC1.contoso.com
RID pool manager            DC1.contoso.com
Infrastructure master       DC1.contoso.com
The command completed successfully.
```

```powershell
PS C:\> Get-ADForest | Select-Object SchemaMaster, DomainNamingMaster
PS C:\> Get-ADDomain | Select-Object PDCEmulator, RIDMaster, InfrastructureMaster
PS C:\> Get-ADDomainController -Filter * | Select-Object Name, OperationMasterRoles
```

`dcdiag /test:knowsofroleholders` and `dcdiag /test:fsmocheck` check that each DC agrees on the holders and can reach them.

## Placement guidelines

* The first DC in a forest gets all five roles; the first DC in each new domain gets that domain's three.
* Keep the forest roles together on a reliable DC in the forest root domain.
* Put the PDC emulator on your best-connected, best-resourced DC — it does the most work of all the roles.
* Choose a **standby** operations master — a direct, same-site replication partner of each role holder — so that if you ever have to seize, the standby already has nearly all the data.
* RODCs **can't** hold FSMO roles.

## Transfer versus seizure

| | Transfer | Seizure |
|---|---|---|
| When | Current holder is online (maintenance, decommissioning, rebalancing) | Current holder is **permanently** lost or can't be repaired in time |
| What happens | Holder replicates its latest state to the target and hands over cleanly | Target simply rewrites the `fsmoRoleOwner` attribute; any changes the old holder hadn't replicated are lost |
| Afterwards | Old holder carries on as a normal DC | **Never bring the old holder back online** with its AD database. Clean up its metadata, then wipe and rebuild it |

### Transferring

GUI: **Active Directory Users and Computers** › right-click the domain › *Operations Masters* (RID, PDC, Infrastructure); **Active Directory Domains and Trusts** › *Operations Master* (domain naming); the **Active Directory Schema** snap-in (register it first with `regsvr32 schmmgmt.dll`) for schema master.

PowerShell — run from any domain-joined machine with RSAT; `-Identity` is the DC that **receives** the roles:

```powershell
PS C:\> Move-ADDirectoryServerOperationMasterRole -Identity DC2 `
          -OperationMasterRole PDCEmulator, RIDMaster, InfrastructureMaster
```

Rights needed: **Domain Admins** for the three domain roles, **Enterprise Admins** for domain naming master, **Schema Admins** for schema master.

### Seizing

Add `-Force`. The cmdlet still tries a graceful transfer first and seizes only if the holder can't be contacted:

```powershell
PS C:\> Move-ADDirectoryServerOperationMasterRole -Identity DC2 -OperationMasterRole SchemaMaster -Force
```

Or with `ntdsutil` on (or connected to) the new holder:

```text
C:\> ntdsutil
ntdsutil: roles
fsmo maintenance: connections
server connections: connect to server DC2.contoso.com
server connections: quit
fsmo maintenance: seize rid master
fsmo maintenance: quit
ntdsutil: quit
```

The ntdsutil keywords are `seize schema master`, `seize naming master`, `seize rid master`, `seize pdc` and `seize infrastructure master` (and `transfer ...` with the same names).

> **Watch out:** Before seizing, pick the DC with the **most up-to-date** copy of the relevant partition — ideally the standby that replicated directly with the dead holder. Check with `repadmin /showrepl` or `repadmin /showutdvec`.

> **Real world:** An outage of the schema, domain naming or infrastructure master can often wait for a repair. RID master can usually wait a few hours. The PDC emulator is the one to seize quickly if the holder won't be back today.

## Troubleshooting checklist

1. `netdom query fsmo` from two different DCs — do they agree? If not, replication of the role change hasn't converged (`repadmin /showrepl`).
2. A role points to a DC that no longer exists (shown as a mangled name or `CN=NTDS Settings\0ADEL:...`) — the DC was removed without demotion: seize to a healthy DC, then clean up metadata.
3. Object creation errors mentioning RIDs → `dcdiag /test:ridmanager /v`, confirm the RID master is reachable.
4. Time or lockout weirdness → confirm the PDC emulator is up and the forest-root PDC has a reliable external time source.

## Lab it yourself

```powershell
PS C:\> netdom query fsmo
PS C:\> Move-ADDirectoryServerOperationMasterRole -Identity DC2 -OperationMasterRole PDCEmulator
PS C:\> Get-ADDomain | Select-Object PDCEmulator
# Simulate a loss: shut down DC2, then from DC1
PS C:\> Move-ADDirectoryServerOperationMasterRole -Identity DC1 -OperationMasterRole PDCEmulator -Force
```

In a lab you can then demote DC2 with `Uninstall-ADDSDomainController -ForceRemoval` and re-promote it — exactly what you'd do in production after a seizure.

## Key takeaways

* Forest roles: **schema master**, **domain naming master**. Domain roles: **RID master**, **PDC emulator**, **infrastructure master**.
* The PDC emulator is the most visible: time, urgent password changes, bad-password rechecks, lockout, GPO editing.
* Forest-root PDC emulator is the only DC that should use an external NTP source.
* Infrastructure master must not be a GC unless single domain, all DCs are GCs, or Recycle Bin is enabled.
* `Move-ADDirectoryServerOperationMasterRole -Identity <new holder>` transfers; add `-Force` to seize. `ntdsutil roles` is the alternative.
* After a seizure, the old holder must never return with its database — metadata cleanup and rebuild.
* RODCs can't hold FSMO roles; keep a same-site standby DC for each role holder.
