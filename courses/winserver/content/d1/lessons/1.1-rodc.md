## What an RODC is for

A **read-only domain controller (RODC)** holds a read-only copy of the domain partition (plus a read-only GC and read-only DNS if you add those roles). It is designed for places where you can't guarantee physical security — a branch office closet, a factory floor, a less-trusted Azure VNet — but still want local logons that survive a WAN outage.

What makes it safer than a writable DC:

* **No originating writes.** Clients that try to write are referred to a writable DC; changes reach the RODC only by inbound replication. Replication is **one-way** — no writable DC ever pulls changes from an RODC, so a tampered RODC can't push bad data into the domain.
* **No secrets by default.** An RODC stores password hashes only for accounts its **Password Replication Policy (PRP)** allows, and only after they are requested.
* **Its own krbtgt.** Each RODC gets a unique `krbtgt_NNNNN` account. Tickets it issues are signed with that key, so a stolen RODC doesn't expose the domain-wide `krbtgt` key, and writable DCs can tell RODC-issued tickets apart.
* **Administrator role separation.** You can make a branch technician a local administrator of the RODC without giving them any domain rights.
* **Filtered attribute set.** Attributes marked in the RODC filtered attribute set (often application secrets) never replicate to RODCs.

| | Writable DC | RODC |
|---|---|---|
| Accepts directory writes | Yes | No — refers or forwards to a writable DC |
| Replication | Inbound and outbound | Inbound only |
| Password hashes stored | All accounts | Only accounts allowed by PRP that have been cached |
| Can hold FSMO roles | Yes | No |
| Local admin without domain rights | No (local admin of a DC = domain admin) | Yes — delegated administrator / `dsmgmt` local roles |
| DNS zone copy | Writable (AD-integrated) | Read-only; dynamic updates referred to a writable DNS server |

## Prerequisites

* At least one **writable DC** in the domain the RODC can replicate from — in practice a writable DC in the nearest site (hub), because the RODC replicates the domain partition from a writable DC in its own domain.
* For forests created before Windows Server 2008 you would run `adprep /rodcprep`; any forest that can host Windows Server 2025 DCs is far past that point.
* An AD site for the branch, with the branch subnet assigned.

## Deploying an RODC

### Direct deployment

A Domain Admin promotes the server in one step:

```powershell
PS C:\> Install-ADDSDomainController -DomainName contoso.com -ReadOnlyReplica `
          -SiteName Branch1 -InstallDns `
          -DelegatedAdministratorAccountName 'CONTOSO\Branch1-Admins' `
          -AllowPasswordReplicationAccountName 'CONTOSO\Branch1-Users','CONTOSO\Branch1-Computers'
```

`-SiteName` is mandatory with `-ReadOnlyReplica`. If you don't specify PRP parameters you get the defaults described below.

### Staged (two-step) deployment

Staging lets a Domain Admin do the privileged part centrally and lets a branch technician, who has no domain rights, finish the job on site.

1. **Pre-create the RODC account** (Domain Admin). In Active Directory Users and Computers right-click the *Domain Controllers* OU › **Pre-create Read-only Domain Controller account**, or:

    ```powershell
    PS C:\> Add-ADDSReadOnlyDomainControllerAccount -DomainControllerAccountName RODC1 `
              -DomainName contoso.com -SiteName Branch1 `
              -DelegatedAdministratorAccountName 'CONTOSO\Branch1-Admins'
    ```

2. **Attach the server** (delegated user). The server must have the same name (`RODC1`), be in a workgroup (not joined to the domain), and have the AD DS role installed. The delegated user runs:

    ```powershell
    PS C:\> Install-ADDSDomainController -DomainName contoso.com -UseExistingAccount `
              -Credential (Get-Credential CONTOSO\branchtech)
    ```

> **Exam tip:** "The branch technician must be able to install the RODC but must not be a member of Domain Admins" → **staged deployment** with the technician (or their group) as the **delegated administrator** of the pre-created account. Combine it with RODC **IFM** media (`ntdsutil ifm` › `create sysvol rodc`) when the WAN link is slow.

## Administrator role separation

The delegated administrator account you set on the RODC object (the `managedBy` attribute) gets **local** administrator rights on that RODC — equivalent to the server's local Administrators group, without becoming a member of Domain Admins or the domain's built-in Administrators group. They can patch, install drivers and reboot the server but have no rights on any other DC. You can also manage local roles on the RODC itself with `dsmgmt`:

```text
C:\> dsmgmt
dsmgmt: local roles
local roles: add CONTOSO\Branch1-Admins administrators
local roles: show role administrators
local roles: quit
dsmgmt: quit
```

## The Password Replication Policy (PRP)

The PRP is two lists stored on each RODC's computer object:

* **Allowed list** (`msDS-RevealOnDemandGroup`) — accounts whose passwords *may* be cached.
* **Denied list** (`msDS-NeverRevealGroup`) — accounts whose passwords must *never* be cached. **Deny wins** over allow.

### Default PRP of a new RODC

| Entry | Setting |
|---|---|
| Allowed RODC Password Replication Group | Allow (group starts **empty**) |
| Denied RODC Password Replication Group | Deny |
| Administrators, Server Operators, Backup Operators, Account Operators | Deny |

The **Denied RODC Password Replication Group** is pre-populated with high-value principals, including **Domain Admins, Enterprise Admins, Schema Admins, Cert Publishers, Group Policy Creator Owners, the domain-wide krbtgt account** and the domain controller groups. Don't remove those defaults.

So out of the box an RODC **caches no user passwords at all**. Two ways to change that:

* Add accounts to the domain-wide **Allowed RODC Password Replication Group** — affects *every* RODC in the domain.
* Add a branch-specific group to **that one RODC's** allowed list — the usual choice, because Branch1's RODC shouldn't cache Branch2's users.

```powershell
PS C:\> Add-ADDomainControllerPasswordReplicationPolicy -Identity RODC1 `
          -AllowedList 'Branch1-Users','Branch1-Computers'
PS C:\> Get-ADDomainControllerPasswordReplicationPolicy -Identity RODC1 -Allowed
PS C:\> Get-ADDomainControllerPasswordReplicationPolicy -Identity RODC1 -Denied
PS C:\> Remove-ADDomainControllerPasswordReplicationPolicy -Identity RODC1 -AllowedList 'Branch1-Users'
```

> **Watch out:** For a user to log on while the WAN is down, the RODC needs the password of the **user** *and* of the **computer** they log on from. Put branch workstations in an allowed group too.

### How caching happens

When a branch user first authenticates at the RODC, it has no hash, so it forwards the request to a writable DC. If the PRP allows the account, the RODC then asks the writable DC to replicate that single account's secrets. The *next* logon is handled locally. Accounts never seen by the RODC aren't cached — which is why you **prepopulate** before a site goes live or before a planned WAN outage:

```text
C:\> repadmin /rodcpwdrepl RODC1 DC1.contoso.com "CN=User1,OU=Branch1,DC=contoso,DC=com" "CN=PC-BR1-01,OU=Branch1,DC=contoso,DC=com"
```

The syntax is destination RODC(s), then the writable source DC, then one or more account **distinguished names**. The PowerShell equivalent is `Get-ADUser User1 | Sync-ADObject -Destination RODC1 -PasswordOnly`. Either way, the request fails for any account the PRP doesn't allow.

The **Advanced Password Replication Policy** dialog on the RODC object in Active Directory Users and Computers has a **Prepopulate Passwords** button that does the same.

### Auditing what is cached

| Question | Tool |
|---|---|
| Whose passwords are stored on RODC1 right now? (Revealed list) | `Get-ADDomainControllerPasswordReplicationPolicyUsage -Identity RODC1 -RevealedAccounts` |
| Who has authenticated through RODC1? (Authenticated-to list) | `Get-ADDomainControllerPasswordReplicationPolicyUsage -Identity RODC1 -AuthenticatedAccounts` |
| Would User1 be cached? (Resultant policy) | ADUC › RODC1 › Password Replication Policy › **Advanced** › *Resultant Policy* tab |
| Revealed list from the command line (always queries a writable DC) | `repadmin /prp view RODC1 reveal` |

The Authenticated-to list is useful for *building* the allowed list: let the site run for a while, see who authenticates, then allow those accounts.

## When an RODC is stolen or compromised

Because the RODC only holds the cached secrets, the blast radius is limited to the **Revealed list**. The response:

1. Export the list of revealed accounts first (you need it to know whose passwords to change).
2. **Delete the RODC's computer account** in the *Domain Controllers* OU. The deletion dialog offers to **reset all passwords for user accounts** that were cached and to **reset all passwords for computer accounts** that were cached, and to export the list to a file.
3. Clean up metadata if prompted, and replace the server.

Resetting forces those users to choose new passwords; the RODC's own `krbtgt_NNNNN` account is removed with it, invalidating tickets it issued.

> **Real world:** Keep RODC allowed groups small and branch-specific, and never add privileged IT staff accounts to them — give branch admins a separate low-privilege account for daily use.

## Lab it yourself

In the two-DC lab from the previous lesson, add a third VM named RODC1 in a workgroup:

```powershell
# On DC1
PS C:\> New-ADReplicationSite Branch1
PS C:\> New-ADGroup Branch1-Users -GroupScope Global
PS C:\> Add-ADDSReadOnlyDomainControllerAccount -DomainControllerAccountName RODC1 -DomainName contoso.com -SiteName Branch1
PS C:\> Add-ADDomainControllerPasswordReplicationPolicy -Identity RODC1 -AllowedList Branch1-Users
# On RODC1 (still a workgroup server)
PS C:\> Install-WindowsFeature AD-Domain-Services -IncludeManagementTools
PS C:\> Install-ADDSDomainController -DomainName contoso.com -UseExistingAccount -Credential (Get-Credential CONTOSO\Administrator)
# After reboot, on DC1
PS C:\> Get-ADDomainControllerPasswordReplicationPolicyUsage -Identity RODC1 -RevealedAccounts
```

Add a test user to Branch1-Users, prepopulate it with `repadmin /rodcpwdrepl`, and confirm it now appears in the revealed list.

## Key takeaways

* RODCs are read-only, replicate **inbound only**, can't hold FSMO roles and have their own `krbtgt_NNNNN`.
* `-SiteName` is required with `-ReadOnlyReplica`; staged deployment uses `Add-ADDSReadOnlyDomainControllerAccount` then `Install-ADDSDomainController -UseExistingAccount`.
* The delegated administrator gets **local** admin on that RODC only; `dsmgmt` › `local roles` manages it too.
* Default PRP caches nothing: Allowed group empty, Denied group plus Administrators/Server/Backup/Account Operators denied; **deny wins**.
* Cache both **users and their computers**; prepopulate with `repadmin /rodcpwdrepl` or the Prepopulate Passwords button.
* Audit with `Get-ADDomainControllerPasswordReplicationPolicyUsage -RevealedAccounts` / `-AuthenticatedAccounts`.
* Stolen RODC: export the revealed list, delete the RODC account and choose to reset cached user and computer passwords.
