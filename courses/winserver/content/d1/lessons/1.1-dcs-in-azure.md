## Why put a DC in Azure?

Once workloads move into Azure virtual networks, they still need Kerberos, LDAP and Group Policy. Sending every authentication back across a VPN or ExpressRoute circuit to on-premises DCs adds latency and makes Azure workloads depend on the WAN. Running your own DCs on Azure VMs ("IaaS DCs") extends the existing forest into Azure: same domain, same admins, same Group Policy, just another site.

The alternative is **Microsoft Entra Domain Services**, a managed domain. It is a different product with different trade-offs, and the exam likes to test which one fits a scenario.

| | DCs on Azure VMs (AD DS) | Microsoft Entra Domain Services |
|---|---|---|
| Who runs the DCs | You — patching, backup, monitoring | Microsoft (two DCs per replica set, you never sign in to them) |
| Part of your on-premises forest | Yes — they replicate with on-prem DCs | No — a separate standalone managed domain synchronised one way from Entra ID |
| Domain Admins / Enterprise Admins | Yes | No — you get the limited *AAD DC Administrators* group |
| Schema extensions, FSMO control, trusts you design | Yes | No schema extensions or FSMO control; forest trusts only (no external trusts), created from the Azure side |
| Typical use | Hybrid identity, DR for AD, apps that need full AD | Lift-and-shift apps that need LDAP/Kerberos/NTLM but no AD admin overhead |

If a scenario says "extend the on-premises domain", "the DCs must replicate with on-premises", "you need Domain Admins" or "you must extend the schema", it's IaaS DCs.

## Prerequisites: network first

An Azure DC must reach on-premises DCs to replicate, so hybrid connectivity (site-to-site VPN or ExpressRoute) and routing come first. Network security groups (NSGs) on the identity subnet must allow AD DS traffic between the Azure DCs, on-premises DCs and clients: DNS (53), Kerberos (88), RPC endpoint mapper (135) plus the dynamic RPC range, LDAP (389), SMB (445), kpasswd (464), LDAPS (636), GC (3268/3269) and NTP (123/UDP).

> **Watch out:** Never give a domain controller a **public IP address**. For administration use **Azure Bastion** (RDP over TLS from the portal, no public IP on the VM) or a management VM reached over the private network.

## VM configuration

### IP addressing

Set a **static private IP address on the Azure network interface** (the NIC resource), not inside Windows. The guest keeps using DHCP; the Azure DHCP service always hands it the reserved address. Hard-coding an IP inside the guest can cut the VM off if it doesn't match what Azure expects.

### Disks

* Put `NTDS.dit`, the logs and `SYSVOL` on a **separate managed data disk** with **host caching set to None**. The ESE database engine manages its own write ordering and needs writes to be truly durable; ReadWrite host caching can lose writes the database thinks are committed.
* Use a **persistent managed OS disk** — not an ephemeral OS disk — so the DC survives host maintenance without re-promotion.
* When you promote, point `-DatabasePath`, `-LogPath` and `-SysvolPath` at the data disk (for example `F:\NTDS` and `F:\SYSVOL`).

```powershell
PS C:\> Install-ADDSDomainController -DomainName contoso.com -SiteName Azure-EastUS `
          -DatabasePath F:\NTDS -LogPath F:\NTDS -SysvolPath F:\SYSVOL -InstallDns
```

### Availability

Deploy at least **two DCs in different availability zones** (or an availability set where the region has no zones). Give at least two of them the GC role so Azure clients never need to cross the WAN to log on.

## DNS for the virtual network

VMs in a VNet use **Azure-provided DNS** (the virtual IP `168.63.129.16`) by default. That resolver knows nothing about `contoso.com` AD zones, so a VM can't join the domain or find DCs through SRV records.

Fix it at the **VNet level**: set the VNet's **custom DNS servers** to the IP addresses of your Azure DCs (and, during the build, an on-premises DC). Every NIC in the VNet then receives those servers via Azure DHCP. Peering doesn't carry DNS settings across, so set the same custom DNS servers on each peered VNet whose VMs need AD. Existing VMs pick up the change after a DHCP renewal or restart.

```text
C:\> az network vnet update --resource-group RG1 --name VNet1 --dns-servers 10.10.1.4 10.10.1.5
```

On the DC's own DNS server role, configure a forwarder to `168.63.129.16` (or to on-premises DNS) so internet and Azure private DNS names still resolve.

> **Exam tip:** "VMs in VNet1 can't join contoso.com; nslookup shows the query going to 168.63.129.16" → change the **VNet DNS servers** to the DCs. Don't edit each VM's network adapter inside the guest — that doesn't scale and is overwritten by Azure DHCP anyway.

## Sites: model Azure honestly

Create an AD DS site for each Azure region (or VNet group), add the Azure subnets to it, and connect it to on-premises with a site link whose cost and interval reflect the WAN. Clients in Azure then find the Azure DCs first (DC Locator uses the client's subnet → site mapping), and replication across the WAN follows the site link schedule rather than intrasite change notification.

```powershell
PS C:\> New-ADReplicationSite -Name Azure-EastUS
PS C:\> New-ADReplicationSubnet -Name 10.10.0.0/16 -Site Azure-EastUS
PS C:\> New-ADReplicationSiteLink -Name HQ-Azure -SitesIncluded HQ, Azure-EastUS `
          -Cost 100 -ReplicationFrequencyInMinutes 15 -InterSiteTransportProtocol IP
```

An RODC is also an option in Azure if you treat the VNet as less trusted than the datacenter — the same Password Replication Policy rules apply as in a branch office.

## Operating DCs in Azure safely

**Shut down from inside the guest, not with Stop in the portal.** Stopping (deallocating) the VM from the portal or `az vm deallocate` changes the **VM-Generation ID** on the next start. The DC's safeguards then:

1. reset the **invocation ID** of its database (harmless, a bit of extra replication),
2. **discard its current RID pool** (wasteful; repeated often it contributes to RID exhaustion),
3. mark **SYSVOL as non-authoritative** so it re-syncs from a partner.

Item 3 becomes a real problem if *every* DC in the domain lives in Azure and they are all deallocated together — none has an authoritative SYSVOL to pull from, and you must perform an authoritative SYSVOL sync manually.

**Back up properly.** Use a system-state aware backup (Windows Server Backup or an Azure backup product that is AD-aware). Never "back up" a DC by copying its VHD — the database may be mid-write and unrecoverable.

**Don't clone or image a running DC.** Use cloning only through the supported VM-Generation ID process, never by capturing a generalized image of a DC.

## Lab it yourself

With a free Azure account (costs a few dollars a day — delete the resource group when done):

```text
C:\> az group create --name RG1 --location eastus
C:\> az network vnet create --resource-group RG1 --name VNet1 --address-prefix 10.10.0.0/16 --subnet-name Identity --subnet-prefix 10.10.1.0/24
C:\> az vm create --resource-group RG1 --name DC3 --image MicrosoftWindowsServer:WindowsServer:2025-datacenter-azure-edition:latest --size Standard_D2s_v5 --vnet-name VNet1 --subnet Identity --private-ip-address 10.10.1.4 --public-ip-address "" --admin-username azadmin --zone 1
C:\> az vm disk attach --resource-group RG1 --vm-name DC3 --name DC3-ntds --new --size-gb 32 --caching None
C:\> az network bastion create --resource-group RG1 --name Bastion1 --vnet-name VNet1 --public-ip-address BastionIP --location eastus
```

(Bastion needs a subnet named `AzureBastionSubnet` and a Standard public IP created first.) Connect through Bastion, initialise the data disk as `F:`, install the role and run `Install-ADDSForest` with `-DatabasePath F:\NTDS -SysvolPath F:\SYSVOL`. Finally set the VNet DNS servers to `10.10.1.4`, deploy a member VM and join it to the domain.

## Key takeaways

* IaaS DCs extend your own forest into Azure; **Entra Domain Services** is a separate managed domain with no Domain Admins and no schema extensions.
* Static IP goes on the **Azure NIC**; the guest stays on DHCP. No public IP — use **Azure Bastion**.
* NTDS.dit, logs and SYSVOL on a **data disk with host caching None**; persistent OS disk; two or more DCs across **availability zones**.
* Point the **VNet custom DNS servers** at the DCs; forward from the DCs to `168.63.129.16` for Azure names.
* Create an **AD site and subnets** for Azure and a site link to on-premises.
* Deallocating a DC VM resets VM-Generation ID: invocation ID reset, RID pool discarded, SYSVOL non-authoritative.
