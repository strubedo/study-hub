## Policies vs preferences

Every GPO has two branches in each half: **Policies** and **Preferences** (*Computer Configuration › Preferences* and *User Configuration › Preferences*). They behave very differently, and the exam asks you to pick the right one.

| | Policy settings (Administrative Templates, security settings) | Preferences |
|---|---|---|
| Where values are written | Policy registry keys (`...\Software\Policies\...`) or security database | The **normal** location the app or OS uses (any registry key, file, drive mapping, group membership...) |
| Can the user change it? | No — UI is greyed out | **Yes**, until the next refresh re-applies it (or never, with *Apply once*) |
| When the GPO no longer applies | Administrative Template settings under the Policies keys are **removed** (no tattooing); some security settings do persist | Setting **stays** (tattoos) unless you chose *Remove this item when it is no longer applied* |
| Needs an ADMX template? | Yes, for Administrative Templates | No — you can set anything |
| Targeting granularity | Whole GPO (links, security filtering, WMI filter) | **Per item** with **item-level targeting (ILT)** |

Rule of thumb: **enforce** with policies, **configure a sensible default** with preferences. If users must not be able to change something, it's a policy.

## Preference extensions

| Windows Settings | Control Panel Settings |
|---|---|
| Applications (user), **Drive Maps** (user), Environment, **Files**, Folders, Ini Files, Network Shares (computer), **Registry**, Shortcuts | Data Sources, Devices, Folder Options, Internet Settings (user), **Local Users and Groups**, Network Options, Power Options, **Printers**, Regional Options (user), **Scheduled Tasks**, **Services** (computer), Start Menu (user) |

Some exist in only one half (for example Drive Maps only under User Configuration, Services only under Computer Configuration).

## Actions: Create, Replace, Update, Delete

Most preference items take one of four actions. Getting these right is the core skill.

| Action | If the item doesn't exist | If it exists |
|---|---|---|
| **Create** | Creates it | Leaves it alone |
| **Replace** | Creates it | **Deletes and recreates** it with only the configured properties — anything else is reset |
| **Update** (default for most items) | Creates it | Modifies only the properties you configured; leaves the rest |
| **Delete** | Does nothing | Deletes it |

Typical choices:

* Map `S:` for Sales but let users reconnect it as they like → **Update**.
* Make sure a mapping always points at the new server even if a user changed it → **Replace**.
* Give users a default registry value only once, then let them own it → **Create** (or Update + *Apply once*).
* Remove an old mapping from everyone → **Delete**.

## The Common tab

Every item has a **Common** tab with options that change behaviour:

* **Stop processing items in this extension if an error occurs** — stops later items of the *same* extension in this GPO.
* **Run in logged-on user's security context (user policy option)** — user-side items normally run as SYSTEM; choose this for things like drive maps to paths only the user can reach.
* **Remove this item when it is no longer applied** — undoes the item when the GPO goes out of scope (e.g. the user moves OU or leaves the targeted group). Selecting it forces the action to **Replace**.
* **Apply once and do not reapply** — set it the first time, then let the user change it permanently.
* **Item-level targeting** — the filter for this one item.

> **Exam tip:** "When users are removed from the Finance group, the mapped drive must disappear automatically" → item-level targeting on the Finance group **plus** *Remove this item when it is no longer applied*. Targeting alone stops it being applied but leaves the existing drive mapping in place.

## Item-level targeting (ILT)

ILT lets one GPO hold many items, each with its own condition, evaluated on the client at every refresh. Targeting items include:

| Category | Targeting items |
|---|---|
| Identity | **Security Group**, **User**, **Computer Name**, **Organizational Unit**, **Domain**, **LDAP Query** |
| Network | **Site**, **IP Address Range**, MAC Address Range, Network Connection |
| Hardware | **Battery Present**, **Portable Computer**, RAM, CPU Speed, Disk Space |
| Software | **Operating System**, File Match, Registry Match, MSI Query, Language, Environment Variable, **WMI Query** |
| Session / time | Terminal Session, Processing Mode, Time Range, Date Match |

You can combine items with **AND / OR**, negate any of them with **Is Not**, and group them in **collections** (parentheses).

```text
Drive Map S: -> \\FS1.contoso.com\Sales   (Action: Update, Reconnect)
  Item-level targeting:
    the user is a member of the security group CONTOSO\G-Sales
    AND the computer is NOT a member of the site HQ-Lab
```

Compared with whole-GPO filtering:

| Mechanism | Granularity | Evaluated |
|---|---|---|
| Security filtering | Whole GPO | When determining which GPOs apply |
| WMI filter | Whole GPO | On the client, once per GPO |
| Item-level targeting | One preference item | On the client, per item |

> **Real world:** One "Drive Maps" GPO linked at the domain with ILT per department replaces a dozen logon scripts and a dozen GPOs. But every targeting item costs time at each refresh — LDAP and WMI queries the most. Prefer Security Group, OU and Site targets.

## Useful preference items in practice

### Local Users and Groups

Add a domain group to the local Administrators group on servers without touching existing members:

```text
Computer Configuration > Preferences > Control Panel Settings > Local Users and Groups
  New > Local Group
  Action: Update
  Group name: Administrators (built-in)
  Members: Add  CONTOSO\G-Server-Admins
```

The *Delete all member users* / *Delete all member groups* check boxes let it act like the *Restricted Groups* policy, which **replaces** the membership. Pick Update without those boxes to **add**; use Restricted Groups (a policy) or the delete options to **enforce exact** membership.

> **Watch out:** Don't use preferences to set **passwords**. Older GPP items (local users, services, scheduled tasks, mapped drives, data sources) could store a password in SYSVOL encrypted with a key Microsoft published, so any domain user could recover it. Security update MS14-025 removed the password fields. For local Administrator passwords use **Windows LAPS**; for services use **gMSAs**.

### Registry

Use the Registry Wizard to browse a reference machine and import keys, or script it:

```powershell
PS C:\> Set-GPPrefRegistryValue -Name 'Cfg - App Defaults' -Context User `
          -Key 'HKCU\Software\Contoso\App' -ValueName Theme -Value Dark -Type String -Action Update
PS C:\> Get-GPPrefRegistryValue -Name 'Cfg - App Defaults' -Context User -Key 'HKCU\Software\Contoso\App'
```

Registry preferences are the only preference type with dedicated GroupPolicy cmdlets; the others are configured in the Group Policy Management Editor.

### Files and folders

Copy a file from a share to each machine (for example a config file or a desktop shortcut target). For a *computer* item the **computer account** must be able to read the source share; for a user item, the user (or SYSTEM if not running in user context — again, the computer account on the network).

### Scheduled Tasks and Services

* **Immediate Task** runs once as soon as the GPO applies — handy for one-off fixes.
* **Services** sets startup type and recovery actions (but configure service accounts with gMSAs, not stored passwords).

### Printers and drive maps

* Drive maps support **Reconnect**, label, and *Hide/Show this drive*.
* Printer items can deploy shared printers per user with ILT on site or IP range, so roaming users get the printer of the office they're in.

## Troubleshooting preferences

* `gpresult /h` lists each preference extension and item that applied.
* Each extension writes to the **Application** log with a source such as *Group Policy Drive Maps* or *Group Policy Registry*; detailed processing is in the GroupPolicy Operational log.
* Preference items fail independently — one bad drive map doesn't stop a registry item unless *Stop processing items in this extension* is set on an earlier item of the same extension.
* An item that "keeps coming back" after users delete it is doing its job: **Update/Replace** re-apply at every refresh. Use **Apply once** if that's not what you want.

## Lab it yourself

1. In GPMC create **Cfg - Drive Maps** and link it to the domain.
2. *User Configuration › Preferences › Windows Settings › Drive Maps* › New mapped drive: `\\DC1\NETLOGON`, letter `N:`, action **Update**.
3. On the Common tab, enable **Item-level targeting**: *the user is a member of the security group* `G-Test`, and tick **Remove this item when it is no longer applied** (note the action switches to Replace).
4. Sign in as a member of G-Test: `N:` appears. Remove the user from the group, sign out and in, run `gpupdate`: `N:` disappears.
5. Add a registry preference with `Set-GPPrefRegistryValue` and confirm it with `gpresult /h C:\gp.html`.

## Key takeaways

* **Policies** enforce, don't tattoo and need ADMX; **preferences** set defaults users can change, tattoo, and can target anything.
* Actions: **Create** (only if missing), **Replace** (delete and recreate), **Update** (change configured properties), **Delete**.
* **Remove this item when it is no longer applied** cleans up when out of scope and forces Replace.
* **Item-level targeting** filters individual items by group, OU, site, IP range, OS, WMI and more, with AND/OR/NOT.
* Local Users and Groups with Update **adds** members; Restricted Groups policy **replaces** membership.
* Never store passwords in preferences (MS14-025) — use Windows LAPS and gMSAs.
* `Set-GPPrefRegistryValue` scripts registry preferences; other items are edited in the GPME.
