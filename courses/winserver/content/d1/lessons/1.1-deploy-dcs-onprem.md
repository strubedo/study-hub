## Where domain controllers fit

A domain controller (DC) is a Windows Server with the **Active Directory Domain Services** role that holds a writable (or, for an RODC, read-only) copy of the directory database `NTDS.dit` and the `SYSVOL` share. Every DC answers LDAP and Kerberos, most also run DNS, and by default every new DC is a **global catalog (GC)** server as well. AZ-802 expects you to build DCs quickly, choose the right promotion method, and keep the functional level story straight.

Installing a DC is a two-stage job:

1. **Add the role binaries** — `Install-WindowsFeature AD-Domain-Services -IncludeManagementTools`. This only copies files. Nothing about the server's identity changes yet.
2. **Promote** — run the Server Manager post-deployment wizard ("Promote this server to a domain controller") or one of the ADDSDeployment cmdlets. `dcpromo.exe` as an interactive wizard is gone; the wizard in Server Manager generates the same PowerShell you would type yourself (the **View script** button on the review page shows it).

## The three promotion cmdlets

| Goal | Cmdlet | Key parameters |
|---|---|---|
| New forest (first DC of the forest root domain) | `Install-ADDSForest` | `-DomainName`, `-DomainNetbiosName`, `-ForestMode`, `-DomainMode`, `-InstallDns` |
| New child or tree domain in an existing forest | `Install-ADDSDomain` | `-NewDomainName`, `-ParentDomainName`, `-DomainType ChildDomain` or `TreeDomain`, `-Credential` |
| Additional DC (writable or read-only) in an existing domain | `Install-ADDSDomainController` | `-DomainName`, `-SiteName`, `-InstallDns`, `-NoGlobalCatalog`, `-ReadOnlyReplica`, `-InstallationMediaPath` |

Each has a `Test-` twin (`Test-ADDSForestInstallation`, `Test-ADDSDomainInstallation`, `Test-ADDSDomainControllerInstallation`) that runs the prerequisite checks without changing anything. All of them prompt for the **Directory Services Restore Mode (DSRM)** password unless you pass `-SafeModeAdministratorPassword` as a secure string, and they reboot automatically unless you add `-NoRebootOnCompletion`.

```powershell
PS C:\> Install-WindowsFeature AD-Domain-Services -IncludeManagementTools
PS C:\> Install-ADDSForest -DomainName contoso.com -DomainNetbiosName CONTOSO -InstallDns
```

Adding a second DC to the same domain and placing it in a named site:

```powershell
PS C:\> Install-ADDSDomainController -DomainName contoso.com -SiteName HQ `
          -InstallDns -Credential (Get-Credential CONTOSO\Administrator)
```

Adding a child domain under the forest root:

```powershell
PS C:\> Install-ADDSDomain -NewDomainName emea -ParentDomainName contoso.com `
          -DomainType ChildDomain -InstallDns -Credential (Get-Credential CONTOSO\Administrator)
```

> **Exam tip:** Creating a new domain in an existing forest requires **Enterprise Admins** rights, because the domain naming master must create a new crossRef object in the Configuration partition. Adding a DC to an existing domain needs only **Domain Admins** in that domain (plus **Schema Admins** and **Enterprise Admins** the first time a newer Windows Server version has to extend the forest schema).

### Adprep is automatic now

When the first DC running a newer Windows Server version joins an older forest, the forest schema and the domain need preparing (`adprep /forestprep` and `adprep /domainprep`). Since Windows Server 2012 the promotion process runs these automatically if your account is in **Schema Admins** and **Enterprise Admins** (forest prep) and **Domain Admins** (domain prep). You can still run `adprep.exe` from the installation media `\support\adprep` folder in change-controlled environments where the schema team works separately. Schema changes are made on the **schema master**, so it must be online and reachable.

## Functional levels

Functional levels decide which features the DCs can use and therefore which operating systems can be DCs.

| Level | DCs allowed | Notes |
|---|---|---|
| Windows Server 2012 R2 | 2012 R2 – 2022 | **Not supported** for Windows Server 2025 DCs |
| Windows Server 2016 | 2016, 2019, 2022, 2025 | 2019 and 2022 never introduced a new level; 2016 is their highest |
| Windows Server 2025 | 2025 only | Required for the **Database 32k pages optional feature** |

The rules that bite on the exam:

* A **new forest** created on Windows Server 2025 must use at least the Windows Server 2016 domain and forest functional level.
* You can only promote a Windows Server 2025 DC into an **existing domain at the Windows Server 2016 domain functional level or higher**. A forest still at 2012 R2 has to be raised first — which means retiring or upgrading any DC older than 2016 first.
* To raise to Windows Server 2025, **every DC** in the domain (domain level) or in the forest (forest level) must run Windows Server 2025. Raising the forest level to 2025 when every DC in every domain already runs 2025 raises all the domain levels with it.
* Unattended answer files use `DomainLevel 10` / `ForestLevel 10` for the 2025 level. The `-ForestMode` parameter of `Set-ADForestMode` accepts `Windows2025Forest`.

```powershell
PS C:\> (Get-ADForest).ForestMode
Windows2016Forest
PS C:\> Get-ADDomainController -Filter * | Select-Object Name, OperatingSystem
PS C:\> Set-ADForestMode -Identity contoso.com -ForestMode Windows2025Forest
```

> **Watch out:** Raising a functional level needs **Domain Admins** (domain level) or **Enterprise Admins** (forest level), healthy replication and a recent backup of the DCs that hold the FSMO roles and GC. Treat it as a one-way change: once the level is raised, older DCs can never be promoted again.

> **Real world:** The 32k page database feature is an AD *optional feature* (the same mechanism as the Recycle Bin) — raising the level to 2025 does not turn it on. New 2025 DCs get a 32k-capable database running in 8k simulation mode, but a DC that was **upgraded in place** keeps its 8k database and blocks the feature until it is replaced or re-promoted. Check that your backup product supports 32k pages first: once enabled it can't be reverted, and older 8k backups become unusable for normal restores.

## Choosing how a new DC gets its data

| Method | How | When to use |
|---|---|---|
| Network replication | Default — the new DC pulls every partition from a source DC (`-ReplicationSourceDC` to pick one) | Normal case; LAN or decent WAN |
| **Install from Media (IFM)** | Create media on an existing DC with `ntdsutil`, carry it to the new server, promote with `-InstallationMediaPath` | Branch sites on slow links or large databases; only the changes since the media was created cross the WAN |
| **Virtual DC cloning** | Copy a prepared virtual DC's disks, drop in `DCCloneConfig.xml`, boot | Rapid scale-out in Hyper-V or another hypervisor that exposes **VM-Generation ID** |

### Install from Media

```text
C:\> ntdsutil
ntdsutil: activate instance ntds
ntdsutil: ifm
ifm: create sysvol full C:\IFM
ifm: quit
ntdsutil: quit
```

`create full` captures the database only; `create sysvol full` adds SYSVOL so it doesn't have to replicate either. Use `create rodc` or `create sysvol rodc` for RODC media — that media has secrets (passwords) stripped, so it is safer to ship to a branch. The media must be younger than the **tombstone lifetime** (180 days by default) or promotion refuses it. Then on the new server:

```powershell
PS C:\> Install-ADDSDomainController -DomainName contoso.com -SiteName Branch1 `
          -InstallationMediaPath D:\IFM -InstallDns
```

### Virtual DC cloning (summary)

Cloning relies on the hypervisor exposing a **VM-Generation ID**. When a DC boots and sees the ID has changed, it resets its invocation ID and discards its RID pool so it can't reuse USNs or issue duplicate SIDs. The steps: add the source DC to the **Cloneable Domain Controllers** group, check unsupported apps with `Get-ADDCCloningExcludedApplicationList`, run `New-ADDCCloneConfigFile` on the source, shut it down, copy the disks and boot the copy. The **PDC emulator** must be online during cloning. If `DCCloneConfig.xml` is present but the host provides no VM-Generation ID, the clone boots into DSRM rather than damaging the domain.

> **Watch out:** Restoring a DC from a plain VM snapshot on a hypervisor *without* VM-Generation ID support can cause a **USN rollback**: the DC reuses update sequence numbers its partners have already seen, so they ignore its new changes. Windows Server detects the rollback when it can and quarantines the DC (Netlogon paused, replication stopped), but it can't undo the divergence. VM-Generation ID safeguards are not a substitute for real system-state backups.

## Global catalog and DNS placement

* A GC holds a full replica of its own domain plus a **partial, read-only replica of every other domain** in the forest (the attributes in the partial attribute set). It is needed for universal group membership at logon, UPN logons and forest-wide searches.
* New DCs are GCs by default; use `-NoGlobalCatalog` to opt out or toggle it later in Sites and Services (NTDS Settings › **Global Catalog** check box).
* **AD-integrated DNS** zones live in the directory (DomainDnsZones / ForestDnsZones application partitions) and replicate with AD. A DC that runs DNS should point to another DC as preferred DNS and to itself (loopback) only as an alternate, to avoid an island after restart.

## Demoting and removing DCs

```powershell
PS C:\> Uninstall-ADDSDomainController -DemoteOperationMasterRole -Credential (Get-Credential)
```

* `-LastDomainControllerInDomain` removes the whole domain (with `-RemoveApplicationPartitions` if it held app partitions).
* `-DemoteOperationMasterRole` lets the demotion move any FSMO roles off the server for you.
* `-ForceRemoval` demotes a DC that can't contact any other DC (for example, after a long outage). It leaves its metadata behind in AD.

If a DC is dead and will never return, remove it with **metadata cleanup**: deleting the DC's computer object in Active Directory Users and Computers, or its server object in Active Directory Sites and Services, performs cleanup automatically on current Windows Server versions. The older `ntdsutil` › `metadata cleanup` route still works. Seize any FSMO roles it held first (see the FSMO lesson).

## Lab it yourself

On a Hyper-V host with two Windows Server 2025 evaluation VMs (DC1 and DC2) on an internal switch with static IPs:

```powershell
# On DC1
PS C:\> Rename-Computer DC1 -Restart
PS C:\> Install-WindowsFeature AD-Domain-Services -IncludeManagementTools
PS C:\> Install-ADDSForest -DomainName contoso.com -InstallDns
# After reboot, on DC2 (DNS client pointed at DC1)
PS C:\> Add-Computer -DomainName contoso.com -Restart
PS C:\> Install-WindowsFeature AD-Domain-Services -IncludeManagementTools
PS C:\> Test-ADDSDomainControllerInstallation -DomainName contoso.com
PS C:\> Install-ADDSDomainController -DomainName contoso.com -InstallDns -Credential (Get-Credential CONTOSO\Administrator)
# Verify
PS C:\> Get-ADDomainController -Filter * | Format-Table Name, Site, IsGlobalCatalog, OperatingSystem
```

Then create IFM media on DC1, demote DC2 with `Uninstall-ADDSDomainController`, and re-promote it with `-InstallationMediaPath` to see how much faster it is.

## Key takeaways

* Role install (`Install-WindowsFeature AD-Domain-Services`) and promotion (`Install-ADDSForest` / `Install-ADDSDomain` / `Install-ADDSDomainController`) are separate steps; `Test-ADDS*` cmdlets check prerequisites.
* Windows Server 2025 DCs need an existing domain at the **2016** functional level or higher; new forests on 2025 must be at least 2016.
* The **Windows Server 2025** functional level requires all-2025 DCs and unlocks the 32k page optional feature (enabled separately).
* **IFM** (`ntdsutil ifm`) saves WAN bandwidth; RODC media strips secrets; media must be younger than the tombstone lifetime.
* Cloning needs VM-Generation ID, the Cloneable Domain Controllers group, `DCCloneConfig.xml` and an online PDC emulator.
* New DCs are GCs by default; a DC's DNS client should prefer a partner DC and use loopback as an alternate.
* Use `Uninstall-ADDSDomainController` to demote; `-ForceRemoval` plus metadata cleanup for DCs that are gone for good.
