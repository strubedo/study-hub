## The problem: users here, resources there

In a single domain, AGDLP is easy. Add a second domain — say `contoso.com` with a child `emea.contoso.com` — or a second forest after an acquisition (`fabrikam.com`), and three questions appear:

1. Which **group scope** can hold members from the other domain or forest?
2. How do the PowerShell tools reach the other domain?
3. What happens to SIDs, names and logons when objects move?

## Which groups can hold whom

| Member comes from | Global group | Universal group | Domain local group |
|---|---|---|---|
| Same domain | Yes | Yes | Yes |
| Another domain in the **same forest** | **No** | Yes | Yes |
| A domain in a **trusted external forest** or external trust | No | **No** | **Yes** (as a foreign security principal) |

So:

* **Within a forest**: put accounts in global groups in their own domain, nest those global groups in a **universal** group (if many domains need the same role) or directly in the resource domain's **domain local** group.
* **Across forests**: only **domain local** groups (or direct ACL entries) can contain principals from the other forest. Universal groups are forest-scoped.

```text
FABRIKAM\G-Engineers (global, fabrikam.com)
   └─ member of → CONTOSO\DL-FS1-Eng-Read (domain local, contoso.com)
                      └─ NTFS Read on \\FS1.contoso.com\Eng
```

> **Exam tip:** "Users from fabrikam.com must get Read access to a share in contoso.com. A forest trust exists. You need to minimise administrative effort as fabrikam staff change." → Have fabrikam admins maintain a **global** group of the users in fabrikam.com, and add that group to a **domain local** group in contoso.com that has the permission. Neither a global nor a universal group in contoso.com can contain the fabrikam group.

## Foreign security principals (FSPs)

When you add a principal from a trusted *external* domain or forest to a domain local group, AD creates a **foreign security principal** object in the `CN=ForeignSecurityPrincipals` container of the resource domain. The FSP is named by the member's **SID** (for example `S-1-5-21-1844237615-...-1107`) and stands in for it, because the resource domain can't store the real object. ADUC shows the friendly name by resolving the SID across the trust; enable *View › Advanced Features* to see the container.

* FSPs are **not** created for members from other domains in the *same* forest — those are referenced directly (and tracked by the infrastructure master as phantoms).
* If the foreign account is deleted, its FSP becomes **orphaned** — it still appears in group membership as an unresolvable SID until you remove it.
* Well-known SIDs such as *Authenticated Users* also appear as FSPs when added to groups.

## Working with another domain from PowerShell

Every ActiveDirectory cmdlet targets your own domain by default. Point it elsewhere with `-Server` (a domain name or a DC FQDN) and, if needed, `-Credential`:

```powershell
PS C:\> Get-ADUser -Filter 'Department -eq "Finance"' -Server emea.contoso.com
PS C:\> New-ADGroup DL-EMEA-Share -GroupScope DomainLocal -Server emea.contoso.com `
          -Credential (Get-Credential EMEA\Administrator)
PS C:\> Add-ADGroupMember -Identity DL-EMEA-Share -Server emea.contoso.com `
          -Members (Get-ADGroup G-Finance -Server contoso.com)
```

To search the **whole forest** at once, query a **global catalog** on port 3268. A GC has every object in the forest, but only the attributes in the partial attribute set:

```powershell
PS C:\> Get-ADUser -Filter 'Surname -eq "Ruiz"' -Server DC1.contoso.com:3268 `
          -SearchBase 'DC=contoso,DC=com' | Select-Object Name, UserPrincipalName, DistinguishedName
```

(That search base covers `contoso.com` and every child domain beneath it in the tree.)

Rights follow the domain boundary: **Domain Admins** of `contoso.com` have no automatic rights in `emea.contoso.com`; **Enterprise Admins** (forest root) are added to the Administrators group of every domain in the forest.

## UPN suffixes and logon names

Users can sign in as `samAccountName` with a NetBIOS domain (`EMEA\aruiz`) or as a **user principal name** (`aruiz@contoso.com`). By default the UPN suffixes available are the DNS names of the domains in the forest. Add alternative suffixes — typically to match email addresses or a public domain verified in Microsoft Entra ID for hybrid sign-in — at the **forest** level:

```powershell
PS C:\> Set-ADForest -Identity contoso.com -UPNSuffixes @{Add = 'contoso.us', 'adatum.com'}
PS C:\> Get-ADUser -Filter * -SearchBase 'OU=US,DC=contoso,DC=com' |
          ForEach-Object { Set-ADUser $_ -UserPrincipalName "$($_.SamAccountName)@contoso.us" }
```

The GUI equivalent is **Active Directory Domains and Trusts** › right-click the top node › **Properties** › *Alternative UPN suffixes*.

In a **forest trust**, UPN suffixes are advertised to the partner forest and used for **name suffix routing**. If both forests claim the same suffix, routing for it is disabled on the trust until the conflict is resolved.

> **Real world:** UPNs must be unique in the forest. In hybrid identity, the UPN suffix usually needs to match a verified domain in Microsoft Entra ID; a `.local` suffix can't be verified, so organisations add a routable suffix and update users' UPNs before synchronising.

## Moving objects between domains

Within one forest, `Move-ADObject` can move a leaf object (user, computer, group) or an empty container **across domains** with `-TargetServer`. Both the source and destination DCs used must be the **RID master** of their domain — otherwise the move fails with *"the directory service is not the master for that type of operation"*:

```powershell
PS C:\> $rid = (Get-ADDomain emea.contoso.com).RIDMaster
PS C:\> Move-ADObject -Identity 'CN=Ana Ruiz,OU=Sales,DC=contoso,DC=com' `
          -TargetPath 'OU=Sales,DC=emea,DC=contoso,DC=com' `
          -Server (Get-ADDomain contoso.com).RIDMaster -TargetServer $rid
```

What changes and what doesn't:

* The object gets a **new SID** from the target domain (a new domain SID + RID), and its **old SID is kept in `sIDHistory`**, so existing ACLs that reference the old SID keep working.
* The **objectGUID stays the same**.
* Passwords move with user and computer objects.
* A user or computer that is still an explicit member of **global groups** in the source domain can't be moved (global groups can't hold members from another domain) — remove those memberships first. Global and domain local groups can be moved across domains only when they're empty.
* For workstations, the usual practice is simply to **re-join** them to the target domain (`Add-Computer -DomainName emea.contoso.com`), so the machine's own secure channel, DNS suffix and GPO scope all change cleanly.

**Across forests** you can't use `Move-ADObject`. You either re-create accounts in the target forest or use a migration tool that copies the old SID into `sIDHistory` — which only helps if the forest trust allows SID history (`netdom trust ... /enablesidhistory:yes`, see the trusts lesson).

## Multi-forest identity patterns (context)

* **Account forest / resource forest** — users live in one forest, applications in another; a one-way forest trust (resource trusts account) with selective authentication.
* **Merger** — two-way forest trust while migrating, then decommission one forest.
* **Hybrid** — Microsoft Entra Connect Sync or Entra Cloud Sync can synchronise several forests to one Entra tenant; that design work belongs to identity architecture rather than this exam.

## Lab it yourself

With the `contoso.com` / `fabrikam.com` lab forests and a forest trust from the trusts lesson:

```powershell
# On DC1.fabrikam.com
PS C:\> New-ADGroup G-Fab-Eng -GroupScope Global; Add-ADGroupMember G-Fab-Eng -Members fabuser1
# On DC1.contoso.com
PS C:\> New-ADGroup DL-Eng-Read -GroupScope DomainLocal
PS C:\> Add-ADGroupMember DL-Eng-Read -Members (Get-ADGroup G-Fab-Eng -Server fabrikam.com)
PS C:\> Get-ADObject -SearchBase "CN=ForeignSecurityPrincipals,DC=contoso,DC=com" -Filter * |
          Select-Object Name
PS C:\> New-ADGroup U-Test -GroupScope Universal
PS C:\> Add-ADGroupMember U-Test -Members (Get-ADGroup G-Fab-Eng -Server fabrikam.com)   # fails: wrong scope
```

## Key takeaways

* Global groups: same-domain members only. Universal: any domain in the **same forest**. Domain local: anything trusted, including **other forests**.
* Cross-forest access = other forest's global group → **domain local** group in the resource domain → permission.
* Members from other forests or external domains are represented by **foreign security principals** named by SID.
* Use `-Server` / `-Credential` to manage another domain; query a GC on **3268** to search the forest.
* Add UPN suffixes with `Set-ADForest -UPNSuffixes @{Add=...}`; forest trusts route logons by suffix.
* `Move-ADObject -TargetServer` moves objects between domains in a forest (RID masters both sides); new SID, old SID in **sIDHistory**, same GUID.
* Cross-forest moves need a migration tool and SID history allowed on the trust.
