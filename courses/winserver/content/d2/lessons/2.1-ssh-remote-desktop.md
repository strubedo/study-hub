## Two more remote-access paths

PowerShell remoting and Windows Admin Center cover most management, but AZ-802 also expects you to run **OpenSSH Server** on Windows Server and to manage **Remote Desktop** access safely - on-premises and for servers in Azure.

## OpenSSH on Windows Server

OpenSSH for Windows is Microsoft's fork of the open-source project, serviced through Windows Update. The install state differs by version:

| Version | OpenSSH Server state |
|---|---|
| Windows Server 2019 / 2022 | Not installed - add the optional feature (Feature on Demand) |
| **Windows Server 2025** | **Installed but not enabled** |

On Windows Server 2025, Server Manager > **Local Server** shows a **Remote SSH Access** property you can switch to Enabled. Windows Server 2025 also adds a local **OpenSSH Users** group for controlling which accounts may sign in over SSH.

```powershell
# Windows Server 2025 - just start it and make it automatic
PS C:\> Start-Service sshd
PS C:\> Set-Service -Name sshd -StartupType Automatic
PS C:\> Get-NetFirewallRule -Name 'OpenSSH-Server-In-TCP' | Select-Object Name, Enabled

# Windows Server 2022 - install first
PS C:\> Get-WindowsCapability -Online | Where-Object Name -like 'OpenSSH*'
PS C:\> Add-WindowsCapability -Online -Name OpenSSH.Server~~~~0.0.1.0
```

On 2019/2022 servers that use WSUS or have no internet access, `Add-WindowsCapability` can fail with `0x800F0954` because the Feature on Demand payload isn't on the update source. Point the **Specify settings for optional component installation and component repair** policy at Windows Update or install from a network FoD source.

### Components and files

| Item | Location / name |
|---|---|
| Server service | `sshd` (display name OpenSSH SSH Server), TCP **22** |
| Key agent service | `ssh-agent` |
| Server configuration | `%ProgramData%\ssh\sshd_config` |
| Host keys | `%ProgramData%\ssh\ssh_host_*_key` |
| Per-user keys | `%UserProfile%\.ssh\authorized_keys` |
| Keys for **administrators** | `%ProgramData%\ssh\administrators_authorized_keys` |
| Logs | Event Viewer > Applications and Services Logs > **OpenSSH** > Operational (or `%ProgramData%\ssh\logs` with `SyslogFacility LOCAL0`) |

`sshd` reads its config only at start-up, so **restart the service after every change**.

### Key-based authentication for admins

The default Windows `sshd_config` ends with:

```text
Match Group administrators
       AuthorizedKeysFile __PROGRAMDATA__/ssh/administrators_authorized_keys
```

So a user who is a member of the local Administrators group is **not** authenticated from their profile's `authorized_keys` file; their public key must be in `administrators_authorized_keys`, and that file's ACL must allow only **Administrators** and **SYSTEM**. Getting this wrong is the classic "key works for a normal user but an admin still gets a password prompt" problem.

```powershell
PS C:\> Add-Content -Path "$env:ProgramData\ssh\administrators_authorized_keys" -Value 'ssh-ed25519 AAAAC3Nza... admin1@laptop'
PS C:\> icacls.exe "$env:ProgramData\ssh\administrators_authorized_keys" /inheritance:r /grant "Administrators:F" /grant "SYSTEM:F"
```

Disable passwords once keys work by setting `PasswordAuthentication no` in `sshd_config` and restarting `sshd`.

### Who can connect, and with what shell

* `AllowUsers`, `AllowGroups`, `DenyUsers`, `DenyGroups` in `sshd_config` filter accounts. Names are lower case, and domain principals use the form `domain\user` or the pattern `user?domain*` (the `?` replaces `@` to avoid clashing with `user@host`).
* The default shell is `cmd.exe`. Change it with a registry value:

```powershell
PS C:\> New-ItemProperty -Path 'HKLM:\SOFTWARE\OpenSSH' -Name DefaultShell `
          -Value 'C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe' -PropertyType String -Force
```

* For PowerShell 7 remoting over SSH, add a subsystem line (the 8.3 short path avoids the space in Program Files) and restart `sshd`:

```text
Subsystem powershell c:/progra~1/powershell/7/pwsh.exe -sshs
```

Connecting from a client: `ssh contoso\admin1@server1.contoso.com`, or `ssh -i ~/.ssh/id_ed25519 admin1@server1`.

### SSH to Arc-enabled servers

Azure Arc also offers **SSH access through Azure**: the Arc agent creates an outbound reverse-proxy connection (the same Microsoft.HybridConnectivity endpoint used by Windows Admin Center in Azure), so you can run `az ssh arc --resource-group RG1 --name Server1` with no inbound port open. Allow the port with `azcmagent config set incomingconnections.ports 22`. OpenSSH Server must still be running on the machine.

## Remote Desktop

### Enabling RDP on a server

| Method | How |
|---|---|
| Server Manager | Local Server > **Remote Desktop** |
| SConfig (Server Core) | Option **7** (Remote desktop) |
| PowerShell / registry | `fDenyTSConnections = 0` plus the firewall group |
| Group Policy | Computer Configuration > Administrative Templates > Windows Components > Remote Desktop Services > Remote Desktop Session Host > Connections > **Allow users to connect remotely by using Remote Desktop Services** |

```powershell
PS C:\> Set-ItemProperty -Path 'HKLM:\System\CurrentControlSet\Control\Terminal Server' -Name fDenyTSConnections -Value 0
PS C:\> Enable-NetFirewallRule -DisplayGroup 'Remote Desktop'
PS C:\> Set-ItemProperty -Path 'HKLM:\System\CurrentControlSet\Control\Terminal Server\WinStations\RDP-Tcp' -Name UserAuthentication -Value 1   # require NLA
```

RDP uses TCP **3389** and, when available, UDP 3389 for better performance.

### Who may sign in

Two things must both be true:

1. The account has the **Allow log on through Remote Desktop Services** user right. By default it is granted to **Administrators** and **Remote Desktop Users**.
2. The account is not caught by **Deny log on through Remote Desktop Services**, which overrides the allow right.

So to let a help-desk group use RDP without admin rights, add it to the local **Remote Desktop Users** group (by Restricted Groups or Group Policy Preferences at scale). Without the Remote Desktop Session Host role and RDS CALs, Windows Server allows **two concurrent administrative sessions**; anything more is a Remote Desktop Services deployment, which is outside AZ-802.

**Network Level Authentication (NLA)** makes the client authenticate (CredSSP) before a full session is created, which blunts denial-of-service and pre-authentication exploits. Leave it on. The client then needs to reach a DC or have cached credentials, and an expired password must be changed some other way.

### Protecting admin credentials over RDP

A normal RDP sign-in sends your credentials to the remote host, where they can be harvested if that host is compromised. Two options avoid that:

| Option | Client command | What happens | Trade-off |
|---|---|---|---|
| **Restricted Admin mode** | `mstsc /restrictedAdmin` | Credentials never sent; you act as the **target computer** on onward network connections | Needs admin rights on the target; enabled on the server side by the `DisableRestrictedAdmin` registry value = 0 |
| **Remote Credential Guard** | `mstsc /remoteGuard` | Kerberos requests are redirected back to the client; onward access uses **your identity** | Kerberos only; both ends must support it |

Group Policy can force either on clients: **Restrict delegation of credentials to remote servers** (Computer Configuration > Administrative Templates > System > Credentials Delegation).

### RDP for servers in Azure

* **Never** expose 3389 to `0.0.0.0/0` with an NSG rule.
* Prefer **Azure Bastion** (browser or native client over TLS 443; the VM needs no public IP) or **JIT VM access** (temporary NSG allow rule from your IP). Both are covered in Domain 3.
* **Windows Admin Center in the Azure portal** includes a Remote Desktop tool for Arc-enabled servers and Azure VMs, again without inbound ports for Arc.
* You can sign in to Azure Windows VMs with Microsoft Entra ID accounts by deploying the **AADLoginForWindows** extension and assigning the *Virtual Machine Administrator Login* or *Virtual Machine User Login* role.

## Lab it yourself

1. On Windows Server 2025, enable **Remote SSH Access** in Server Manager, then from a client run `ssh administrator@server1` and confirm you land in `cmd.exe`.
2. Generate a key with `ssh-keygen -t ed25519`, put the public key in `administrators_authorized_keys`, fix the ACL with `icacls`, and confirm password-less sign-in. Then set `PasswordAuthentication no` and restart `sshd`.
3. Change the default shell to PowerShell with the registry command and reconnect.
4. On another server, enable RDP with the three PowerShell lines above, add a test user to Remote Desktop Users and sign in as that user.

## Key takeaways

* Windows Server 2025 ships OpenSSH Server installed but disabled; enable it in Server Manager (Remote SSH Access) or with `Start-Service sshd`. 2019/2022 need `Add-WindowsCapability`.
* `sshd_config` lives in `%ProgramData%\ssh`; restart `sshd` after changes.
* Members of Administrators authenticate with keys from `administrators_authorized_keys`, whose ACL must allow only Administrators and SYSTEM.
* Change the SSH default shell with `HKLM:\SOFTWARE\OpenSSH\DefaultShell`; add a `Subsystem powershell` line for PowerShell 7 remoting over SSH.
* Enable RDP with `fDenyTSConnections = 0` and the Remote Desktop firewall group; grant non-admins access through Remote Desktop Users; keep NLA on.
* Use Restricted Admin mode or Remote Credential Guard to keep admin credentials off the target; in Azure use Bastion, JIT or WAC in the portal instead of a public 3389.
