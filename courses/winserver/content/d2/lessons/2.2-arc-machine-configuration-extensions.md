## Two ways Azure changes things inside an Arc server

Once a server is Arc-enabled, Azure can reach *inside* the operating system in two distinct ways:

| | Machine Configuration | VM extensions |
|---|---|---|
| What it is | Azure Policy evaluating and enforcing **OS settings as code** (DSC under the hood) | Small Microsoft or partner packages that **install and configure software** |
| Typical use | "Password minimum length is 14", "SMBv1 is disabled", security baselines, drift correction | Azure Monitor Agent, Defender for Endpoint, Custom Script, Key Vault certificate sync, Hybrid Runbook Worker, WAC |
| Delivered by | `GCArcService` (built into the Arc agent) | `ExtensionService` (extension manager) |
| Assigned from | Azure Policy (definition + assignment), or a guest configuration assignment resource | Portal Extensions blade, `az connectedmachine extension`, `New-AzConnectedMachineExtension`, ARM/Bicep, Azure Policy DeployIfNotExists |

The blueprint calls the first one "implement device configuration by using Azure Arc" and the second "deploy Azure services with VM extensions on non-Azure machines".

## Machine Configuration

Machine Configuration was formerly **Azure Policy Guest Configuration** (you will still see `guestconfiguration` in resource provider names, endpoints and cmdlets). It lets Azure Policy look inside the guest: Azure Policy alone can only see ARM properties such as VM size or tags.

### Prerequisites

| Azure VMs | Arc-enabled servers |
|---|---|
| Install the **Machine Configuration extension** (`AzurePolicyforWindows`) | **Nothing to install** - the agent includes it |
| **System-assigned managed identity** on the VM | Arc servers always have one |
| Register `Microsoft.GuestConfiguration` | Same |

For Azure VMs, assign the initiative **Deploy prerequisites to enable Guest Configuration policies on virtual machines** to add the extension and identity at scale. For Arc servers, any machine configuration policy definition that includes the `Microsoft.HybridCompute/machines` type automatically covers Arc machines in the assignment scope.

### Audit or enforce

Every machine configuration assignment has an **assignment type**:

| Assignment type | Behaviour |
|---|---|
| `Audit` | Report compliance only |
| `ApplyAndMonitor` | Apply once, then report drift without correcting it |
| `ApplyAndAutoCorrect` | Apply and re-apply whenever drift is detected |

The policy effect that carries this is **AuditIfNotExists** (audit) or **DeployIfNotExists** (creates the guest configuration assignment so settings get applied). DeployIfNotExists policies need a **remediation task** for machines that already exist when the policy is assigned; new machines are handled automatically. The agent re-evaluates roughly every 15 minutes.

Built-in content covers common needs - Azure compute security baseline audits for Windows, required services, time zone, installed applications, certificate expiry. (The OSConfig-based Windows Server 2025 security baseline applied on the server itself is covered in Domain 6.)

### Custom configurations

Write a DSC configuration (PowerShell 7 and the **GuestConfiguration** module), compile it to a MOF, then package and publish it:

```powershell
PS C:\> Install-Module GuestConfiguration -Scope CurrentUser
PS C:\> New-GuestConfigurationPackage -Name 'TimeZone' -Configuration '.\TimeZone\localhost.mof' -Type AuditAndSet
PS C:\> Start-GuestConfigurationPackageRemediation -Path '.\TimeZone.zip'      # test locally
PS C:\> # upload TimeZone.zip to a storage account, then:
PS C:\> New-GuestConfigurationPolicy -PolicyId (New-Guid) -ContentUri $sasUri -DisplayName 'Set time zone' `
          -Description 'Enforces Central Standard Time' -Path '.\policies' -Platform Windows -PolicyVersion 1.0.0 -Mode ApplyAndAutoCorrect
```

`-Type AuditAndSet` allows the package to change settings; `Audit` packages only read. The resulting JSON policy definition is imported with `New-AzPolicyDefinition` and assigned like any other policy.

### Machine Configuration vs Group Policy

| | Group Policy | Machine Configuration |
|---|---|---|
| Targets | Domain-joined machines by site/domain/OU | Any Azure VM or Arc server by subscription/resource group/tag scope - domain-joined or not, Windows or Linux |
| Reporting | `gpresult` per machine | Azure Policy compliance dashboard across the estate |
| Enforcement | Refresh every 90 minutes +/- 30 | ApplyAndAutoCorrect drift correction |
| Dependency | Line of sight to a DC | Outbound HTTPS to Azure |

They overlap; many organisations keep GPOs for domain members and use Machine Configuration for audit/compliance reporting and for non-domain servers.

### Cost

On Azure VMs, Machine Configuration is free. On Arc-enabled servers it is billed per server per month (see Azure Policy pricing), unless the server is covered by **Windows Server Management enabled by Azure Arc** (explicitly attested Software Assurance/subscription licences, or Windows Server pay-as-you-go), in which case it is included.

## VM extensions on Arc-enabled servers

Arc servers support the same extension model as Azure VMs. Common Windows extensions:

| Extension (type) | Publisher | Purpose |
|---|---|---|
| `AzureMonitorWindowsAgent` | `Microsoft.Azure.Monitor` | Azure Monitor Agent - collects data per data collection rules |
| `MDE.Windows` | `Microsoft.Azure.AzureDefenderForServers` | Microsoft Defender for Endpoint onboarding (deployed by Defender for Servers) |
| `CustomScriptExtension` | `Microsoft.Compute` | Download and run a script |
| `KeyVaultForWindows` | `Microsoft.Azure.KeyVault` | Keep certificates synced from Key Vault |
| `HybridWorkerForWindows` | `Microsoft.Azure.Automation.HybridWorker` | Azure Automation Hybrid Runbook Worker |
| `AdminCenter` | `Microsoft.AdminCenter` | Windows Admin Center in the Azure portal |
| `WindowsOsUpdateExtension` | `Microsoft.SoftwareUpdateManagement` | Installed automatically by Azure Update Manager |

The legacy Log Analytics agent (MMA, `MicrosoftMonitoringAgent`) is retired; use the Azure Monitor Agent with data collection rules.

### Deploying

```powershell
PS C:\> New-AzConnectedMachineExtension -ResourceGroupName RG-Arc -MachineName Server1 -Location eastus `
          -Name AzureMonitorWindowsAgent -Publisher Microsoft.Azure.Monitor -ExtensionType AzureMonitorWindowsAgent `
          -EnableAutomaticUpgrade
```

```text
az connectedmachine extension create --resource-group RG-Arc --machine-name Server1 --location eastus \
   --name CustomScriptExtension --publisher Microsoft.Compute --type CustomScriptExtension \
   --settings '{"commandToExecute":"powershell.exe -c Get-Process > C:\\temp\\procs.txt"}'
az connectedmachine extension list --resource-group RG-Arc --machine-name Server1 -o table
```

At scale, use **Azure Policy** with a DeployIfNotExists definition (for example *Configure Windows Arc-enabled machines to run Azure Monitor Agent*), so every machine that joins the scope gets the extension. For Azure Monitor specifically, associating a **data collection rule** with a machine in the portal also deploys the agent.

Extensions download from Azure Storage over 443, are verified against a signed catalog, and run as **Local System**. Protected settings (keys, passwords) are encrypted locally and not persisted in Azure. **Automatic extension upgrade** applies new minor versions; `-EnableAutomaticUpgrade` or the portal toggle turns it on per extension.

**Run Command** on Arc servers (`az connectedmachine run-command create`) is a lighter alternative to the Custom Script Extension for one-off scripts.

### Local security controls

Because extensions run as Local System, a sensitive server's owner can restrict what Azure is allowed to install. These settings are made **locally** with `azcmagent config` and **cannot be overridden from Azure**, not even by a subscription Owner:

```text
C:\> azcmagent config set extensions.allowlist "Microsoft.Azure.Monitor/AzureMonitorWindowsAgent"
C:\> azcmagent config set guestconfiguration.enabled false
C:\> azcmagent config set extensions.blocklist "Microsoft.Compute/CustomScriptExtension"
C:\> azcmagent config set config.mode monitor
C:\> azcmagent config set extensions.enabled false
```

* An **allow list** blocks everything not listed (preferred - it also blocks extensions released later). A **block list** allows everything not listed.
* **Monitor mode** applies a Microsoft-managed allow list of monitoring and security extensions, disables Machine Configuration and remote connectivity (WAC/SSH through Arc), and locks the allow/block lists until you return to `config.mode full`.
* `config set` **replaces** a list value; add `--add` or `--remove` to append to or remove from an existing list.
* Existing extensions are not removed when you add a list; delete them from Azure. Delete requests are always allowed.
* An extension rejected by policy fails in Azure with an error that it is not allowed by the local agent configuration.

> **Exam tip:** "Domain controllers are Arc-enabled to send event logs to Azure Monitor. Ensure that no one in Azure can push scripts to them" - set an extension **allow list** containing only the Azure Monitor Agent (and disable guest configuration) on the DCs.

### Troubleshooting extensions

* Portal: machine > **Extensions** > status and *View detailed status*.
* On the server: `%ProgramData%\GuestConfig\extension_logs\<publisher.type>\` and `%ProgramData%\GuestConfig\ext_mgr_logs`.
* An extension stuck "Creating" while the machine is **Disconnected** is a connectivity problem, not an extension problem - fix the heartbeat first.
* A pending reboot can block extension operations.

## Lab it yourself

1. On an Arc-enabled lab server, deploy the Azure Monitor Agent with the `New-AzConnectedMachineExtension` command, then create a data collection rule that collects the System event log.
2. Run `azcmagent config set extensions.blocklist "Microsoft.Compute/CustomScriptExtension"` and try to deploy the Custom Script Extension from the portal - observe the failure.
3. Assign the built-in policy **Audit Windows machines that are not set to the specified time zone** to the resource group and wait for the compliance result.

## Key takeaways

* Machine Configuration (formerly Guest Configuration) audits or enforces OS settings via Azure Policy; Arc servers need no extension, Azure VMs need the extension plus a system-assigned identity.
* Assignment types: Audit, ApplyAndMonitor, ApplyAndAutoCorrect; existing resources need a remediation task for DeployIfNotExists.
* Custom content: DSC + GuestConfiguration module (`New-GuestConfigurationPackage`, `New-GuestConfigurationPolicy`).
* Extensions (AMA, MDE, Custom Script, Key Vault, Hybrid Worker, AdminCenter) deploy with `New-AzConnectedMachineExtension`, `az connectedmachine extension create`, or Azure Policy at scale.
* Local `azcmagent config` allow lists, block lists, monitor mode and `guestconfiguration.enabled false` cannot be overridden from Azure.
* The Log Analytics agent (MMA) is retired - use Azure Monitor Agent with data collection rules.
