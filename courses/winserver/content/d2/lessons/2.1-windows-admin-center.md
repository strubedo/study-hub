## What Windows Admin Center is (and is not)

Windows Admin Center (WAC) is a free, browser-based management console for Windows Server, Windows client, failover clusters, Hyper-V and Azure Local. It replaces most day-to-day use of Server Manager and the MMC snap-ins with one web UI. It is **not** a replacement for System Center or Configuration Manager: it manages machines one at a time (or one cluster at a time) and has no fleet-wide orchestration of its own.

The architecture has three parts:

* **Browser** - Microsoft Edge or Google Chrome. Other browsers are not in the test matrix.
* **Gateway** - the WAC service. It receives HTTPS from the browser and talks to managed machines.
* **Managed nodes** - the servers you manage. The gateway reaches them with **PowerShell remoting and WMI over WinRM** (TCP 5985, or 5986 for HTTPS). Nothing is installed on a managed node.

Because the gateway uses WinRM, every requirement you learn for PowerShell remoting (firewall rules, TrustedHosts in workgroups, Kerberos delegation) applies to WAC too.

## The modernized gateway (version 2410 and later)

For years WAC shipped as an `.msi` built on .NET Framework 4.6.2. Version **2410** (the release previewed as "vNext" or "v2") rebuilt the gateway, and every release since (2511, and 2606, the current GA release as of October 2026) uses that platform:

| Area | Legacy gateway (2311 and earlier) | Modernized gateway (2410+) |
|---|---|---|
| Runtime | .NET Framework 4.6.2, Katana web server | **.NET 8**, ASP.NET Core **Kestrel**, HTTP/2 |
| Process model | One monolithic process | A process manager plus task-specific subprocesses |
| Installer | `.msi` | `.exe` (supports `/VERYSILENT`, `/HTTPSPortNumber=`, `/CertificateThumbprint=`) |
| Start menu name | Windows Admin Center | **Windows Admin Center (v2)** |
| Default port on Windows Server | 443 | **443** |
| Default port on Windows client | 6516 | **6600** |
| Service name | ServerManagementGateway | **WindowsAdminCenter** |

Version 2410 shipped without high availability; **2511 restored the failover cluster (HA) deployment** through the `Deploy-GatewayV2Ha.Deploy.ps1` script. An HA gateway on 2311 or older cannot be upgraded in place - you uninstall and reinstall. Gateway plug-in extensions written for .NET Framework had to be rewritten for .NET 8, which is why some third-party extensions lagged behind.

> **Watch out:** WAC follows the **Modern Lifecycle Policy**. Only the latest release is serviced, and you must move to a new release within 30 days to stay supported. There is no LTSC channel for WAC.

### Install options

| Mode | Where | Typical use |
|---|---|---|
| Local client | Windows 11 | One admin managing a lab or a few servers |
| Gateway server | Windows Server 2016 or later | Shared gateway for a team, published in DNS |
| Managed server | Installed on the server it manages | Single-server management without a separate gateway |
| Failover cluster (HA) | 2+ node cluster with a CSV | Active-passive gateway that survives node loss |

**Installing WAC on a domain controller is not supported.** Put the gateway on a member server.

Server Core install, unattended:

```powershell
PS C:\> Start-BitsTransfer -Source https://aka.ms/WACdownload -Destination .\WindowsAdminCenter.exe
PS C:\> Start-Process -FilePath .\WindowsAdminCenter.exe -ArgumentList '/VERYSILENT' -Wait
PS C:\> Start-Service -Name WindowsAdminCenter
```

After install, the configuration module `Microsoft.WindowsAdminCenter.Configuration.psm1` (in `C:\Program Files\WindowsAdminCenter\PowerShellModules\`) changes settings such as the port: `Set-WACHttpsPort -WacPort 8443 -ServicePortRangeStart 6601 -ServicePortRangeEnd 6610`. If you change the port, open it in Windows Defender Firewall and update the DNS/URL your admins use.

Use a certificate from a trusted CA in production. The self-signed certificate the installer can generate is for testing only and triggers browser warnings.

### What it can manage

WAC is optimised for Windows Server 2025 and fully supports **Windows Server 2016 and later**. Windows Server 2012/2012 R2 work with limited functionality and need **WMF 5.1** installed. Windows Server 2008 R2 is not supported.

## Controlling access

Two layers of access control exist and the exam likes to mix them up.

**Gateway access** - who may open the WAC web page at all:

* **Gateway users** - can connect to the gateway and manage servers they have rights on.
* **Gateway administrators** - can also change gateway settings, install extensions and configure access.

Gateway identity can come from local groups, Active Directory groups, or **Microsoft Entra ID** (which adds Conditional Access and MFA in front of the gateway).

**Managed-node access** - what the user can do on each server. By default the user's own credentials are used, so they need local admin rights on the target. Optionally, WAC **role-based access control** deploys three JEA-backed roles onto the managed node: *Windows Admin Center Administrators*, *Windows Admin Center Hyper-V Administrators* and *Windows Admin Center Readers*. Users added to those local groups get only the matching capabilities, without being local administrators.

### Single sign-on and the double hop

Signing in to a gateway installed on Windows Server, then managing Server1, is a double hop: browser to gateway, gateway to Server1. For WAC to pass your Kerberos identity on, each managed node must trust the gateway for delegation. Microsoft's documented method is **resource-based constrained delegation**, configured on the managed node's computer object:

```powershell
PS C:\> Set-ADComputer -Identity (Get-ADComputer Server1) -PrincipalsAllowedToDelegateToAccount (Get-ADComputer WAC1)
```

Without it, users must re-enter credentials with **Manage as** for every node. A WAC install on Windows 11 (local client) needs no delegation because the browser and gateway are the same machine.

## Windows Admin Center in the Azure portal

WAC can also run **inside the Azure portal** for two kinds of machine:

* **Azure Arc-enabled servers** (Windows Server 2016+ on-premises or in another cloud)
* **Azure VMs** running Windows Server

You don't install a gateway. The portal deploys the **AdminCenter** VM extension (publisher `Microsoft.AdminCenter`), which installs a WAC instance on that one machine with a certificate managed by Microsoft. It manages only the machine it is installed on.

### Requirements for Arc-enabled servers

| Requirement | Detail |
|---|---|
| OS and size | Windows Server 2016 or later, at least **3 GB RAM** |
| Agent | Azure Connected Machine agent 1.13.21320.014 or later (avoid 1.35/1.36, which break the connection) |
| Resource provider | **Microsoft.HybridConnectivity** registered (the portal does this if you have `*/register/action`, included in Owner/Contributor) |
| Roles to install | Owner, Contributor or **Windows Admin Center Administrator Login** |
| Roles to connect | **Reader** + **Windows Admin Center Administrator Login** on the machine resource |
| Outbound network | HTTPS to `*.service.waconazure.com` (or the **WindowsAdminCenter** service tag), `pas.windows.net`, `*.servicebus.windows.net` |
| Inbound network | **None.** The Arc agent builds an outbound reverse-proxy session |
| Cloud | Public Azure regions only (not Azure Government or 21Vianet) |

The *Windows Admin Center Administrator Login* role uses dataActions, so it can be assigned at subscription, resource group or resource scope but **not management group**. Sign-in uses Microsoft Entra ID; you are not prompted for a local administrator password.

When you click **Install**, Azure registers the provider, creates a logical **endpoint** resource (`Microsoft.HybridConnectivity/endpoints/default`) on the Arc resource and installs the extension. When you click **Connect**, the provider opens a short-lived, session-specific route through a layer 4 SNI proxy to the WAC port on the machine. TLS terminates on the server itself.

> **Watch out:** Enabling WAC in Azure on an Arc server that already hosts a multi-server WAC gateway **replaces** that installation, and the old gateway stops working. Don't enable it on your shared gateway.

If **Connect** fails, check on the server that the WAC port is allowed for incoming Arc connections:

```text
C:\> azcmagent config list
...
incomingconnections.ports (preview): 6516
C:\> azcmagent config set incomingconnections.ports 6516
```

`config set` **replaces** the list. If SSH through Arc also uses the endpoint, list both ports (`azcmagent config set incomingconnections.ports 22,6516`) or append with `--add`.

Other quick checks: `Restart-Service himds`, confirm the AdminCenter extension shows *Succeeded*, and test outbound reachability with `Invoke-RestMethod https://<region>.service.waconazure.com`.

### Azure VMs

For a native Azure VM the same AdminCenter extension is used (installing it needs Owner or Contributor on the VM) and connecting needs the same Reader + Windows Admin Center Administrator Login roles, but the connection goes to the VM's **private IP** (you need network line-of-sight from your browser, for example over VPN or ExpressRoute) or to a **public IP** with an inbound NSG rule for the WAC port (6516 in the portal default). Restrict that rule to your management IPs. The VM also needs outbound access to the WindowsAdminCenter and AzureActiveDirectory service tags.

### Cost

WAC on-premises costs nothing beyond your Windows licence. WAC in the Azure portal has no charge of its own. For Arc-enabled servers, Microsoft lists *Windows Admin Center in Azure for Arc* among the benefits of **Windows Server Management enabled by Azure Arc**, and that documentation says the benefit is available only to servers attested for Software Assurance / Windows Server subscription licences or enrolled in Windows Server pay-as-you-go. Azure VMs don't need any attestation.

## Lab it yourself

1. On an evaluation Windows Server 2025 member server (not a DC), download and install WAC with the commands above, then browse to `https://<server>`.
2. Add a second server under **All connections**. Note that you are prompted for credentials. Then run the `Set-ADComputer ... -PrincipalsAllowedToDelegateToAccount` command on the second server's object, sign out and back in, and connect again with single sign-on.
3. Open **Settings > Access** and add an AD group as Gateway users.
4. If you have an Arc-enabled lab server, open it in the Azure portal, select **Windows Admin Center**, install on port 6516, then assign yourself *Windows Admin Center Administrator Login* and connect.

## Key takeaways

* The WAC gateway manages nodes with PowerShell remoting and WMI over WinRM; nothing is installed on managed nodes.
* Since 2410 the gateway runs on .NET 8/Kestrel, installs from an `.exe`, defaults to port 443 on Windows Server and 6600 on Windows client; 2511 restored HA deployment.
* Never install WAC on a domain controller; only the latest WAC release is supported (30-day upgrade window).
* Gateway users/administrators control access to the gateway; WAC RBAC roles (JEA-based) control what users can do on each node.
* SSO from a server-mode gateway needs Kerberos resource-based constrained delegation on each managed node's computer object.
* WAC in the Azure portal installs the AdminCenter extension per machine, needs no inbound ports for Arc servers, and requires the Windows Admin Center Administrator Login role (not assignable at management group scope).
