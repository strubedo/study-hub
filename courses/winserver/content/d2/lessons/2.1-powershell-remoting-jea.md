## PowerShell remoting basics

PowerShell remoting over **WinRM** (WS-Management) is the backbone of Windows Server management: Server Manager, Windows Admin Center, Azure automation and most scripts use it.

| Item | Value |
|---|---|
| Service | Windows Remote Management (`WinRM`) |
| Listener ports | TCP **5985** (HTTP) and **5986** (HTTPS) |
| Default state on Windows Server | Enabled (since 2012) with an HTTP listener and firewall rules for the domain/private profiles |
| Default endpoint | `microsoft.powershell` |
| Authentication | Kerberos in a domain; NTLM otherwise |

Even on HTTP, WinRM encrypts the session after authentication (message-level encryption negotiated by Kerberos or NTLM). HTTPS adds server authentication by certificate, which matters when Kerberos isn't available.

```powershell
PS C:\> Enable-PSRemoting -Force                       # re-enable if someone disabled it
PS C:\> Test-WSMan -ComputerName Server1               # is the listener answering?
PS C:\> Enter-PSSession -ComputerName Server1          # interactive 1:1
PS C:\> Invoke-Command -ComputerName Server1,Server2 -ScriptBlock { Get-Service WinRM }   # 1:many
PS C:\> $s = New-PSSession -ComputerName Server1       # persistent session
PS C:\> Copy-Item C:\Tools\app.msi -Destination C:\Temp\ -ToSession $s
```

### Workgroup and cross-domain targets

Kerberos needs both machines in the same forest (or trusted forests) and a name the KDC can resolve to an SPN. Connecting by IP address, or to a workgroup server, falls back to NTLM, which cannot prove the server's identity. The client then refuses unless either the target uses an **HTTPS listener** with a trusted certificate, or you add it to the client's **TrustedHosts** list:

```powershell
PS C:\> Set-Item WSMan:\localhost\Client\TrustedHosts -Value 'Server9.fabrikam.com,10.10.0.21' -Concatenate -Force
```

TrustedHosts is not a statement that the host is trustworthy; it only suppresses the error about not being able to authenticate the server. Prefer HTTPS where you can.

### PowerShell remoting over SSH

PowerShell 7 can also remote over **SSH** instead of WinRM, which works across Windows, Linux and macOS. The target needs OpenSSH Server and a `powershell` subsystem line in `sshd_config`; you then use `-HostName` (not `-ComputerName`):

```powershell
PS C:\> Enter-PSSession -HostName server1.contoso.com -UserName contoso\admin1
```

SSH remoting does not support WinRM features such as custom session configurations (and therefore JEA) or disconnected sessions.

## The second-hop problem

You sit at **ServerA**, open a remote session to **ServerB**, and inside that session try to read `\\ServerC\Share`. Access is denied. Kerberos and NTLM proved who you are to ServerB without giving ServerB anything it can reuse, so ServerB connects to ServerC anonymously (or as its computer account). That is the second hop.

Microsoft's options, from the PowerShell documentation's own ordering:

| Option | Configured on | Credentials cached? | Notes |
|---|---|---|---|
| **CredSSP** | Client (ServerA) and server (ServerB) | **Yes, on ServerB** | Easy; works with WinRM as the second hop; doesn't work for Protected Users; credential theft risk if ServerB is compromised |
| **Resource-based Kerberos constrained delegation (RBCD)** | The resource's object (ServerC) | No | No Domain Admin needed; works across domains/forests; **does not support WinRM as the second hop** |
| Classic Kerberos constrained delegation | ServerB's object | No | Needs Domain Admin; cross-domain limits |
| Unconstrained delegation | ServerB's object | Ticket forwarded | Not recommended |
| **JEA** | Each intermediate server (ServerB) | No (virtual account or gMSA) | Most secure; most configuration |
| PSSessionConfiguration with **RunAs** | ServerB | Stored RunAs credential | Simple; password maintenance |
| Pass `$Using:cred` inside the script block | Nothing | Supplied per call | Simplest; awkward code |

### CredSSP

```powershell
# On ServerA (client): allow delegating fresh credentials to ServerB
PS C:\> Enable-WSManCredSSP -Role Client -DelegateComputer 'ServerB.contoso.com' -Force
# On ServerB (server): accept CredSSP
PS C:\> Enable-WSManCredSSP -Role Server -Force
# Connect - CredSSP always requires explicit credentials
PS C:\> Enter-PSSession -ComputerName ServerB.contoso.com -Authentication CredSSP -Credential CONTOSO\Admin1
```

CredSSP is disabled by default on both roles. Because ServerB holds your reusable credentials for the life of the session, use it only to highly trusted hosts.

### Resource-based Kerberos constrained delegation

RBCD is configured on the **back-end** object - the computer that holds the resource - and lists the front-end accounts allowed to delegate to it. The parameter sets the `msDS-AllowedToActOnBehalfOfOtherIdentity` attribute.

```powershell
PS C:\> $ServerB = Get-ADComputer ServerB
PS C:\> Set-ADComputer -Identity ServerC -PrincipalsAllowedToDelegateToAccount $ServerB
PS C:\> Invoke-Command -ComputerName ServerB -ScriptBlock { klist purge -li 0x3e7 }   # clear the computer's ticket cache
PS C:\> Invoke-Command -ComputerName ServerB -ScriptBlock { Get-ChildItem \\ServerC\Share }
```

The KDC caches the earlier denial for about 15 minutes, which is why the example purges the system logon session's tickets (`-li 0x3e7`) on ServerB, or you can wait/restart. Accounts marked **Account is sensitive and cannot be delegated** (and members of Protected Users) are never delegated by any method.

> **Exam tip:** "Allow file share access on the second hop, no stored credentials, minimise privileges needed to configure it" points to **RBCD on ServerC**. "The second hop must itself be a PowerShell remoting session (WinRM)" rules RBCD out; CredSSP or JEA fit.

## Just Enough Administration (JEA)

JEA is a WinRM endpoint that exposes **only the commands you choose**, runs them under a **temporary privileged identity**, and records a **transcript**. Users don't need to be administrators; they don't even need to know an admin password. It is the strongest answer whenever a question says "help desk must restart the DNS service but must not get administrative rights".

JEA has two files:

| File | Extension | Created with | Purpose |
|---|---|---|---|
| Role capability file | `.psrc` | `New-PSRoleCapabilityFile` | *What* a role can do: visible cmdlets, functions, external commands, providers |
| Session configuration file | `.pssc` | `New-PSSessionConfigurationFile` | *Who* gets which role, the run-as identity, session type, transcripts |

### Role capability file

The `.psrc` must live in a **RoleCapabilities** subfolder of a PowerShell module in `$env:PSModulePath`, and it is referenced by file name (without extension).

```powershell
PS C:\> $mod = "$env:ProgramFiles\WindowsPowerShell\Modules\ContosoJEA"
PS C:\> New-Item -ItemType Directory -Path "$mod\RoleCapabilities" -Force
PS C:\> New-ModuleManifest -Path "$mod\ContosoJEA.psd1"
PS C:\> New-PSRoleCapabilityFile -Path "$mod\RoleCapabilities\DnsOperator.psrc" `
          -VisibleCmdlets 'Get-Service', @{ Name = 'Restart-Service'; Parameters = @{ Name = 'Name'; ValidateSet = 'DNS' } }, 'DnsServer\Clear-DnsServerCache' `
          -VisibleExternalCommands 'C:\Windows\System32\ipconfig.exe'
```

The hashtable form restricts a cmdlet to specific parameters and values: here `Restart-Service` works only with `-Name DNS`.

### Session configuration file

```powershell
PS C:\> New-PSSessionConfigurationFile -Path .\DnsOps.pssc -SessionType RestrictedRemoteServer `
          -RunAsVirtualAccount -TranscriptDirectory 'C:\JEA\Transcripts' `
          -RoleDefinitions @{ 'CONTOSO\DNS-Operators' = @{ RoleCapabilities = 'DnsOperator' } }
PS C:\> Test-PSSessionConfigurationFile -Path .\DnsOps.pssc
PS C:\> Register-PSSessionConfiguration -Name DnsOps -Path .\DnsOps.pssc -Force
```

Key fields:

* `SessionType = 'RestrictedRemoteServer'` - starts from a locked-down session (NoLanguage mode, only a handful of proxy commands). `Default` would expose everything - never use it for JEA.
* `RunAsVirtualAccount = $true` - a one-time local account that is a member of the local **Administrators** group (on a DC, **Domain Admins**) for the session's life. Narrow it with `RunAsVirtualAccountGroups`.
* `GroupManagedServiceAccount = 'CONTOSO\gmsaJEA'` - run as a gMSA instead. Use this when commands must reach **network resources**; a virtual account's network identity is the computer account.
* `RoleDefinitions` - maps users/groups to role capability names.
* `TranscriptDirectory` - over-the-shoulder transcript of every session.

`Register-PSSessionConfiguration` **restarts WinRM**, dropping every remote session on the server, so schedule it. After registration the `.pssc` file is no longer needed.

### Connecting and checking

```powershell
PS C:\> Enter-PSSession -ComputerName DNS1 -ConfigurationName DnsOps
PS C:\> Get-PSSessionCapability -ConfigurationName DnsOps -Username CONTOSO\User1   # what will User1 see?
PS C:\> Get-PSSessionConfiguration | Select-Object Name                             # list endpoints
```

A user who connects without `-ConfigurationName` hits `microsoft.powershell` and is refused unless they are an administrator - a common reason "JEA doesn't work".

### JEA and the double hop

Because JEA commands run as a privileged local identity, JEA can solve the second hop by design: configure the endpoint on ServerB with a **gMSA** that has rights on ServerC, and expose only the commands that touch ServerC.

## Lab it yourself

1. In a lab domain with Server1, Server2 and Server3, create a share on Server3 (`New-SmbShare -Name Lab -Path C:\Lab -FullAccess CONTOSO\Administrator`). From Server1 run `Invoke-Command -ComputerName Server2 { Get-ChildItem \\Server3\Lab }` and note the access-denied error.
2. Run `Set-ADComputer Server3 -PrincipalsAllowedToDelegateToAccount (Get-ADComputer Server2)`, purge tickets on Server2 with `Invoke-Command -ComputerName Server2 { klist purge -li 0x3e7 }`, and retry.
3. Build the `DnsOperator` JEA role above on a DNS server, register it, and connect as a non-admin member of the mapped group. Try `Stop-Service DNS` (not visible) and `Restart-Service -Name Spooler` (rejected by ValidateSet).
4. Open the transcript under `C:\JEA\Transcripts`.

## Key takeaways

* WinRM listens on 5985/5986 and is on by default on Windows Server; Kerberos needs names, not IP addresses, otherwise use HTTPS or TrustedHosts.
* CredSSP is configured on both client and server, caches credentials on the intermediate server, and fails for Protected Users.
* RBCD is configured on the resource (ServerC) with `-PrincipalsAllowedToDelegateToAccount`, stores no credentials, needs no Domain Admin, but can't make WinRM the second hop.
* JEA = `.psrc` (what, in a module's RoleCapabilities folder) + `.pssc` (who and as whom), registered with `Register-PSSessionConfiguration`, which restarts WinRM.
* Use `SessionType RestrictedRemoteServer`; virtual accounts are local admins (Domain Admins on a DC); use a gMSA for network access.
* Users must connect with `-ConfigurationName`; check effective commands with `Get-PSSessionCapability`.
