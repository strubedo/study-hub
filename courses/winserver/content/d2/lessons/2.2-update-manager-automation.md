## Azure Update Manager

**Azure Update Manager** is the patching service for Windows and Linux machines in Azure, on-premises and in other clouds (through Arc). It replaced **Automation Update Management**, which depended on the retired Log Analytics agent. Update Manager needs no Log Analytics workspace and no Automation account; it works through an extension the service installs automatically on first use (`WindowsOsUpdateExtension` on Arc servers, `WindowsPatchExtension` on Azure VMs).

Update Manager does not host updates itself. Windows machines still download from whatever source the Windows Update Agent is configured for - **Microsoft Update/Windows Update or a WSUS server**. Update Manager orchestrates *when* and *what*.

### Assessment

| Action | What it does |
|---|---|
| **Check for updates** (one-time assessment) | Scans the selected machines now |
| **Periodic assessment** | Automatic scan every **24 hours**; enable per machine or at scale with the Azure Policy *Configure periodic checking for missing system updates* (separate definitions for Azure VMs and Arc machines) |

Assessment results land in **Azure Resource Graph** tables, so you can query them across subscriptions:

```text
patchassessmentresources
| where type =~ "microsoft.hybridcompute/machines/patchassessmentresults"
| extend os = tostring(properties.osType), status = tostring(properties.status)
| project id, os, status, lastModified = properties.lastModifiedDateTime
```

Resource Graph keeps pending-update assessment data (`patchassessmentresources`) for 7 days and installation history (`patchinstallationresources`) for 30 days.

### Installing updates

* **One-time update / Install now** - choose classifications (Critical, Security, Update Rollup, Feature Pack, Service Pack, Definition, Tools, Updates), include or exclude specific KBs, set a maximum duration and a reboot option.
* **Scheduled patching** - recurring installs using a **maintenance configuration** with the scope **Guest (Azure VM, Arc-enabled VMs/servers)**.

A maintenance configuration contains:

| Setting | Notes |
|---|---|
| Schedule | Start time, time zone, recurrence (hourly, daily, weekly, monthly, e.g. "second Tuesday + 2 days"), maintenance window duration |
| Machines | Static list of machines |
| **Dynamic scopes** | Filter by subscription, resource group, location, resource type, OS type and **tags**; evaluated at run time |
| Updates | Classifications plus KB include/exclude |
| Reboot | **Reboot if required**, **Never reboot**, **Always reboot** |
| Events | Optional **pre- and post-maintenance events** through Event Grid (for example, run an Automation runbook to stop an app first) |

The window is enforced: Update Manager won't start installing a non-service-pack update with less than 15 minutes left, or a reboot with less than 10 minutes left (Windows). Windows registry policies for automatic updates can still trigger a reboot even when you choose **Never reboot**.

### Patch orchestration prerequisite (Azure VMs only)

For **Azure VMs**, scheduled patching requires the VM's patch orchestration mode to be **Customer Managed Schedules** (it sets `AutomaticByPlatform` plus `BypassPlatformSafetyChecksOnUserSchedule`). If you skip that, schedules fail to patch the VM. **Arc-enabled servers have no patch orchestration prerequisite** - associate a schedule and you are done. Automatic VM guest patching and Windows automatic updates modes are Azure VM features and don't apply to Arc servers.

### Pricing

| Machine | Charge |
|---|---|
| Azure VMs (and Arc-enabled Azure Local VMs created through the Arc resource bridge) | **No charge** |
| Arc-enabled servers | **Per server per month, prorated daily** - only for days the machine is Connected and actually managed (assessed, patched or associated with a schedule) |

An Arc-enabled server is **not charged** for Update Manager when any of these apply:

* It is enabled for **Extended Security Updates** through Arc.
* **Defender for Servers Plan 2** is enabled on its subscription.
* It is attested for **Windows Server Management enabled by Azure Arc** (Software Assurance or Windows Server subscription licences) or uses Windows Server pay-as-you-go through Arc.

### Hotpatch

Windows Server 2025 Standard/Datacenter machines that are Arc-enabled can subscribe to **Hotpatch**, managed by Update Manager. Monthly hotpatches install in memory without a restart; a restart is needed only for the quarterly baseline cumulative update.

## Azure Automation runbooks

**Azure Automation** runs scripts (runbooks) in Azure on a schedule, from a webhook, from an alert, or on demand. For AZ-802, the important part is running them **against on-premises servers** through a **Hybrid Runbook Worker**.

### Runbook types

| Type | Notes |
|---|---|
| **PowerShell** | Recommended. Supported runtimes are 5.1, 7.4 and 7.6 (7.1/7.2 runbooks lose support after September 30, 2026) |
| **Python** | Python 3.10 (2.7 and 3.8 are retired) |
| PowerShell Workflow | Legacy; not supported on PowerShell 7 runtimes |
| Graphical / Graphical PowerShell Workflow | Built in the portal's drag-and-drop editor; can't be converted to text |

**Runtime environments** define the language, version and module set a runbook uses, so different runbooks in one account can use different module versions.

### Lifecycle

1. **Create** the runbook (portal, VS Code extension, or `Import-AzAutomationRunbook`).
2. **Edit and Test** in the Test pane - the test runs the *draft*.
3. **Publish** - only published runbooks can be started by schedules, webhooks or other users.
4. **Start** - on demand, **schedule** (`New-AzAutomationSchedule` + `Register-AzAutomationScheduledRunbook`), **webhook**, or as an alert action.

```powershell
PS C:\> Import-AzAutomationRunbook -AutomationAccountName AA1 -ResourceGroupName RG1 `
          -Name Restart-Spooler -Path .\Restart-Spooler.ps1 -Type PowerShell -Published
PS C:\> Start-AzAutomationRunbook -AutomationAccountName AA1 -ResourceGroupName RG1 `
          -Name Restart-Spooler -RunOn HWG-Dallas -Parameters @{ ComputerName = 'Server1' }
```

`-RunOn` names a **Hybrid Runbook Worker group**; without it the job runs in the Azure sandbox.

### Authentication inside runbooks

Run As accounts were retired on **September 30, 2023**. Use the Automation account's **managed identity** (system- or user-assigned) for Azure resources:

```powershell
Connect-AzAccount -Identity
Get-AzVM -ResourceGroupName RG1 | Where-Object PowerState -ne 'VM running'
```

For on-premises credentials, store a **Credential asset** and retrieve it with `Get-AutomationPSCredential -Name 'ContosoAdmin'`. Variables (`Get-AutomationVariable`), certificates and connections are the other shared assets; encrypted assets can't be read back in the portal.

### Cloud sandbox limits

Cloud jobs run in a shared sandbox with **fair share**: a job running longer than **3 hours** is unloaded. A PowerShell runbook then starts again from the beginning (a workflow resumes from its last checkpoint), and a job that keeps hitting the limit is eventually stopped. Cloud jobs can't reach private on-premises resources, can't use locally installed modules, and have memory/socket limits. Those limits are the main reasons to use a Hybrid Runbook Worker.

### Hybrid Runbook Worker

A **User Hybrid Runbook Worker** is a machine - an Azure VM or an **Arc-enabled server** - that runs Automation jobs locally.

* Only the **extension-based** worker is supported. The **agent-based** worker (installed with the Log Analytics agent) was **retired on August 31, 2024**; new agent-based workers couldn't be created after November 1, 2023.
* Extension: publisher `Microsoft.Azure.Automation.HybridWorker`, type **HybridWorkerForWindows** / HybridWorkerForLinux.
* Requirements: the machine's **system-assigned managed identity**, outbound **443** to `*.azure-automation.net`, and membership in a **Hybrid worker group**. A machine can belong to only one group.
* Runbooks run as **Local System** by default; select **Custom** *Hybrid Worker credentials* on the group to run as a domain account.
* Modules a runbook uses must be **installed on the worker itself** (for example RSAT's ActiveDirectory module); the account's module gallery isn't copied to the worker.
* Microsoft strongly recommends never installing a Hybrid Worker on a domain controller, and it isn't supported on virtual machine scale sets.

Creating a group and adding an Arc server in the portal (Automation account > **Hybrid worker groups > Create**) registers the worker and installs the extension for you. In PowerShell the order is group, then worker registration, then extension:

```powershell
PS C:\> New-AzAutomationHybridRunbookWorkerGroup -AutomationAccountName AA1 -ResourceGroupName RG1 -Name HWG-Dallas
PS C:\> $arc = Get-AzConnectedMachine -ResourceGroupName RG-Arc -Name Server1
PS C:\> New-AzAutomationHybridRunbookWorker -AutomationAccountName AA1 -ResourceGroupName RG1 `
          -HybridRunbookWorkerGroupName HWG-Dallas -Name (New-Guid).Guid -VmResourceId $arc.Id
PS C:\> New-AzConnectedMachineExtension -ResourceGroupName RG-Arc -MachineName Server1 -Location eastus `
          -Name HybridWorkerExtension -Publisher Microsoft.Azure.Automation.HybridWorker `
          -ExtensionType HybridWorkerForWindows -TypeHandlerVersion 1.1 `
          -Setting @{ AutomationAccountURL = $hybridServiceUrl } -EnableAutomaticUpgrade
```

`$hybridServiceUrl` is the Automation account's `AutomationHybridServiceUrl` property. The machine's system-assigned managed identity must be enabled (always true for Arc servers).

> **Exam tip:** "A runbook must restart a service on an on-premises server that has no inbound internet access" - Arc-enable a server on that network, add it to a **Hybrid Runbook Worker group** (extension-based), and start the runbook with **Run on: Hybrid Worker**.

## Lab it yourself

1. In the Azure portal open **Azure Update Manager**, select an Arc lab server and choose **Check for updates**. Then enable **Periodic assessment** in *Update settings*.
2. Create a maintenance configuration with a dynamic scope on tag `PatchGroup = Lab`, reboot **If required**, and tag the server.
3. Create an Automation account, a hybrid worker group containing the same Arc server, and a PowerShell 7.4 runbook containing `Get-Service Spooler | Restart-Service -PassThru`. Publish it and start it with *Run on: Hybrid Worker*.

## Key takeaways

* Update Manager replaces Automation Update Management; no Log Analytics workspace or Automation account required; it orchestrates updates from Windows Update or WSUS.
* Periodic assessment scans every 24 hours; results are queryable in Azure Resource Graph (`patchassessmentresources`, 7 days; `patchinstallationresources`, 30 days).
* Scheduled patching uses maintenance configurations (Guest scope) with static machines and/or tag-based dynamic scopes and reboot options.
* Azure VMs need patch orchestration set to **Customer Managed Schedules**; Arc servers need nothing extra.
* Arc servers are billed per server per month (prorated daily) unless covered by ESU, Defender for Servers Plan 2, or Windows Server Management enabled by Azure Arc; Azure VMs are free.
* Runbooks authenticate with managed identities; cloud jobs stop at 3 hours; on-premises work runs on extension-based Hybrid Runbook Workers (agent-based retired August 31, 2024) with modules installed locally.
