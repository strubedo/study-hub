## How a Windows DNS server answers a query

When a query arrives that the server cannot answer from its own zones or cache, it has to go somewhere else. In order, a Windows DNS server checks:

1. Its authoritative zones (including zone scopes if DNS policies are in play).
2. Its cache.
3. **Conditional forwarders** that match the queried name (the longest match wins).
4. **Server-level forwarders**, if configured.
5. **Root hints**, unless "Use root hints if no forwarders are available" is turned off or recursion is disabled.

A **delegation** or **stub zone** is part of step 1: the server holds the delegation (NS records) or the stub's NS list and uses it to send iterative queries to the child or target zone's servers.

## Choosing the right tool

| Mechanism | What the server stores | Updates itself? | Best when |
|---|---|---|---|
| Forwarder | IP list for "everything else" | No | Send all external queries to an ISP, firewall or Azure resolver |
| Conditional forwarder | Domain name plus target IPs | No; you edit IPs manually | A partner namespace (`fabrikam.com`) whose server IPs rarely change, or an Azure Private Resolver inbound endpoint |
| Stub zone | SOA, NS and glue A records copied from the target zone | Yes, refreshes from the master servers | The target's name servers change and you want to follow them automatically |
| Delegation | NS (and glue) records in the parent zone | No | You own the parent zone and hand a child zone (`sales.contoso.com`) to other servers |
| Root hints | The 13 root server names and IPs | Rarely changes | Full internet recursion without forwarders |

> **Exam tip:** "The partner adds DNS servers frequently and you must minimise administrative effort" means **stub zone**, because a stub refreshes its NS list from the target. "Forward queries for one domain to specific IP addresses" means **conditional forwarder**. "Create a child domain hosted on other servers" means **delegation**.

> **Watch out:** A stub zone needs the target's servers to allow zone transfers of the SOA/NS/glue to your server (the stub loads by transfer). A conditional forwarder needs only normal recursive or authoritative query access.

### Configure them in PowerShell

```powershell
PS C:\> Set-DnsServerForwarder -IPAddress 10.50.0.4, 10.50.0.5 -UseRootHint $false
PS C:\> Add-DnsServerConditionalForwarderZone -Name "fabrikam.com" -MasterServers 172.16.10.10, 172.16.10.11 -ReplicationScope Forest
PS C:\> Add-DnsServerStubZone -Name "adatum.com" -MasterServers 192.168.40.10 -ReplicationScope Domain
PS C:\> Add-DnsServerZoneDelegation -Name "contoso.com" -ChildZoneName "sales" -NameServer "ns1.sales.contoso.com" -IPAddress 10.20.0.10
```

Storing a conditional forwarder in AD DS (`-ReplicationScope Forest` or `Domain`) means every DNS server on a DC in that scope gets it, so you configure it once. A file-based conditional forwarder lives only on the server where you created it.

### Recursion and forwarder timeouts

- Disabling recursion (`Set-DnsServerRecursion -Enable $false`) also disables forwarders and conditional forwarders for that server, because forwarding is a form of recursion. Use DNS policies with recursion scopes if you need recursion for some clients only (see the DNS policies lesson).
- Forwarders are tried in order. The default forwarder timeout is 3 seconds per server; if all forwarders fail and root hints are allowed, the server falls back to root hints.

## Name resolution inside Azure

Every Azure virtual network gets **Azure-provided DNS** at the virtual IP `168.63.129.16`. It resolves public names, resolves VM host names within the VNet under `internal.cloudapp.net`, and resolves any **Azure Private DNS zone** linked to the VNet.

Important properties of `168.63.129.16`:

- It is reachable **only from inside Azure**. On-premises servers, even over VPN or ExpressRoute, cannot query it. This single fact drives most hybrid DNS designs.
- If a VNet's DNS servers setting points at custom servers (for example, your DCs running in Azure), VMs use those servers instead, and private zones linked to the VNet are resolved only if those custom servers forward to Azure DNS.

### Azure Private DNS zones

A private DNS zone (for example `azure.contoso.com` or `privatelink.blob.core.windows.net`) is a global resource that answers only for VNets linked to it.

| Link type | Behaviour | Limits |
|---|---|---|
| Registration link (autoregistration on) | VM primary NIC A records are created, updated and removed automatically | A VNet can have **only one** registration zone |
| Resolution link | VMs can query the zone; nothing is auto-registered | A VNet can link to many zones |

Autoregistration covers VMs only, creates no PTR records, and uses only the primary NIC.

### Azure DNS Private Resolver

The Private Resolver is a managed service that removes the need for DNS forwarder VMs in Azure. It has two kinds of endpoint, each in its own **dedicated subnet delegated to `Microsoft.Network/dnsResolvers`** (at least /28):

| Component | Direction | What it does |
|---|---|---|
| Inbound endpoint | On-premises to Azure | Gets a private IP in the VNet. On-premises DNS servers use a **conditional forwarder** pointing to this IP to resolve private zones and Azure-provided names. |
| Outbound endpoint | Azure to on-premises (or other clouds) | The egress point for queries that match a forwarding ruleset. |
| DNS forwarding ruleset | Azure to on-premises | A set of rules (domain name, target IP and port). Associated with an outbound endpoint and **linked to the VNets** whose VMs should use the rules. |

Query paths in a typical hub-and-spoke design:

- **On-premises client resolves `vm1.azure.contoso.com`**: client, on-premises DC (conditional forwarder for `azure.contoso.com`), inbound endpoint IP, Azure DNS, private zone answer.
- **Azure VM resolves `fs1.contoso.com`**: VM uses Azure-provided DNS, the ruleset linked to its VNet matches `contoso.com`, the query leaves through the outbound endpoint to the on-premises DC IPs.

```powershell
PS C:\> Add-DnsServerConditionalForwarderZone -Name "azure.contoso.com" -MasterServers 10.100.0.4 -ReplicationScope Forest
PS C:\> Add-DnsServerConditionalForwarderZone -Name "privatelink.file.core.windows.net" -MasterServers 10.100.0.4 -ReplicationScope Forest
```

> **Exam tip:** On-premises servers must forward Azure private namespaces to the **inbound endpoint**, never to `168.63.129.16`. Azure VMs reach on-premises names through a **forwarding ruleset linked to their VNet** (outbound endpoint). Getting the direction backwards is the most common wrong answer.

> **Watch out:** For private endpoints, forward the `privatelink.<service>` zone (for example `privatelink.blob.core.windows.net`) rather than the public `blob.core.windows.net` zone. Forwarding the whole public zone can break resolution of storage accounts that do not have private endpoints, depending on how the target resolves them.

### Alternative: DCs as DNS in Azure

If you run DCs as VMs in Azure, a valid design is: set the VNet DNS servers to the Azure DCs (plus an on-premises DC as backup), and on those DCs configure a forwarder or conditional forwarder to `168.63.129.16` for private zones. That works because the DCs are inside Azure. It costs you VM management; the Private Resolver is the managed option.

## Troubleshooting hybrid resolution

| Symptom | Likely cause | Fix |
|---|---|---|
| On-premises clients get NXDOMAIN or timeout for a private zone | Conditional forwarder points to `168.63.129.16`, or the inbound endpoint is unreachable (NSG, routing, firewall on UDP/TCP 53) | Point the forwarder at the inbound endpoint IP; check the path |
| Azure VMs cannot resolve on-premises names | Ruleset not linked to the VM's VNet, or VNet uses custom DNS that bypasses Azure DNS | Link the ruleset to the VNet; review VNet DNS settings |
| Storage account resolves to a public IP from on-premises | No forwarder for the `privatelink` zone | Add the conditional forwarder for the privatelink zone |
| Large responses fail across VPN | Fragmentation or MTU problems drop UDP responses | Fix MTU/MSS; confirm TCP 53 is allowed |

Useful commands:

```powershell
PS C:\> Resolve-DnsName vm1.azure.contoso.com -Server 10.10.0.10
PS C:\> Resolve-DnsName vm1.azure.contoso.com -Server 10.100.0.4 -DnsOnly
PS C:\> Test-NetConnection 10.100.0.4 -Port 53
PS C:\> Get-DnsServerZone | Where-Object ZoneType -eq 'Forwarder'
PS C:\> Clear-DnsServerCache -Force
```

Querying the on-premises server and then the inbound endpoint directly tells you which hop is broken.

## Lab it yourself

With a free Azure subscription and a Windows Server 2025 VM on-premises connected by site-to-site VPN (or simply run the "Azure side" tests from a VM in the VNet):

```powershell
PS C:\> New-AzPrivateDnsZone -ResourceGroupName RG1 -Name "azure.contoso.com"
PS C:\> New-AzPrivateDnsVirtualNetworkLink -ResourceGroupName RG1 -ZoneName "azure.contoso.com" -Name "vnet1-link" -VirtualNetworkId (Get-AzVirtualNetwork -Name VNet1 -ResourceGroupName RG1).Id -EnableRegistration
```

Then create a DNS Private Resolver with an inbound endpoint in the portal (it needs its own /28 subnet), note the inbound IP, and add the on-premises conditional forwarder shown above. Without a VPN you can still practise the on-premises half in Hyper-V with two lab forests and conditional forwarders between them.

## Key takeaways

- Resolution order on a Windows DNS server: zones, cache, conditional forwarders, forwarders, root hints.
- Conditional forwarder = fixed IPs for one domain; stub zone = follows the target's NS records automatically; delegation = parent zone hands off a child.
- Store conditional forwarders in AD DS with Forest scope to configure them once for every DC.
- `168.63.129.16` is unreachable from on-premises; use a DNS Private Resolver **inbound endpoint** for on-premises to Azure.
- Azure to on-premises uses a **forwarding ruleset** associated with an **outbound endpoint** and linked to the VNets.
- A VNet can autoregister into only one private DNS zone, but can link to many zones for resolution.
- Forward `privatelink.*` zones for private endpoints.
