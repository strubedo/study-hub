## DNS policies: building blocks

DNS policies (Windows Server 2016 and later) let one DNS server give different answers, or no answer, depending on who is asking, how and when. A policy is made of three parts:

| Object | Cmdlet | What it is |
|---|---|---|
| Client subnet | `Add-DnsServerClientSubnet` | A named group of IPv4/IPv6 prefixes that queries come from |
| Zone scope | `Add-DnsServerZoneScope` | A second (third, fourth...) copy of a zone with its own records. Every zone has a default scope with the zone's own name. |
| Recursion scope | `Add-DnsServerRecursionScope` | A named recursion setting (on/off plus forwarders). The default recursion scope is named `.` |
| Policy | `Add-DnsServerQueryResolutionPolicy`, `Add-DnsServerZoneTransferPolicy` | Criteria plus an action (`ALLOW`, `DENY`, `IGNORE`) plus, for ALLOW, the scopes to use |

### Criteria and syntax

Criteria use the format `operator,value1,value2` with `EQ` or `NE`. Values after `EQ` are OR'd, values after `NE` are AND'd. Combine several criteria with `-Condition AND` (default) or `OR`.

| Parameter | Matches on |
|---|---|
| `-ClientSubnet` | Source IP of the query (by client subnet name) |
| `-ServerInterfaceIP` | Which local IP the query arrived on |
| `-Fqdn` | Queried name; wildcards allowed (`EQ,*.contoso.com`) |
| `-QType` | Record type (`EQ,A,AAAA`) |
| `-TransportProtocol` | `UDP` or `TCP` |
| `-InternetProtocol` | `IPv4` or `IPv6` |
| `-TimeOfDay` | Server local time ranges (`EQ,18:00-23:00`) |

Actions: **DENY** sends an error response (the cmdlet description says REFUSED; its `-Action` help text says SERVFAIL, so treat it simply as "the client gets an error"), **IGNORE** silently drops the query, **ALLOW** answers from the zone scopes listed in `-ZoneScope "scopeA,weight;scopeB,weight"`.

Processing order: server-level policies first (they can only DENY or IGNORE incoming queries), then zone-level policies for the zone that matches, then recursion policies. Within each level, `-ProcessingOrder` decides which policy is evaluated first; the first match wins.

## Scenario 1: geo-location (or site) based answers

Users in the London office should resolve `app.contoso.com` to the London server; everyone else gets the Seattle server.

```powershell
PS C:\> Add-DnsServerClientSubnet -Name "LondonSubnet" -IPv4Subnet "10.44.0.0/16"
PS C:\> Add-DnsServerZoneScope -ZoneName "contoso.com" -Name "LondonScope"
PS C:\> Add-DnsServerResourceRecord -ZoneName "contoso.com" -ZoneScope "LondonScope" -A -Name "app" -IPv4Address "10.44.1.20"
PS C:\> Add-DnsServerResourceRecord -ZoneName "contoso.com" -A -Name "app" -IPv4Address "10.20.1.20"
PS C:\> Add-DnsServerQueryResolutionPolicy -Name "LondonPolicy" -Action ALLOW -ClientSubnet "eq,LondonSubnet" -ZoneScope "LondonScope,1" -ZoneName "contoso.com"
```

The last record goes into the **default** scope (no `-ZoneScope`), which serves every client that no policy matches. No policy is needed for the default scope.

## Scenario 2: load balancing and time of day

Weights split answers between scopes. This policy sends 80 percent of evening queries to the cloud scope and 20 percent to on-premises:

```powershell
PS C:\> Add-DnsServerQueryResolutionPolicy -Name "EveningBurst" -Action ALLOW -TimeOfDay "EQ,18:00-23:00" -ZoneScope "CloudScope,4;OnPremScope,1" -ZoneName "contoso.com" -ProcessingOrder 1
```

## Scenario 3: split-brain DNS

Internal clients should get private IPs for `www.contoso.com` and external clients the public IP, from the **same** server. Create an internal zone scope and a policy keyed on the interface or client subnet:

```powershell
PS C:\> Add-DnsServerZoneScope -ZoneName "contoso.com" -Name "internal"
PS C:\> Add-DnsServerResourceRecord -ZoneName "contoso.com" -ZoneScope "internal" -A -Name "www" -IPv4Address "10.0.0.39"
PS C:\> Add-DnsServerQueryResolutionPolicy -Name "SplitBrainPolicy" -Action ALLOW -ServerInterfaceIP "EQ,10.0.0.56" -ZoneScope "internal,1" -ZoneName "contoso.com"
```

To allow recursion for internal clients only, disable recursion in the default recursion scope and create a scope that allows it:

```powershell
PS C:\> Set-DnsServerRecursionScope -Name . -EnableRecursion $false
PS C:\> Add-DnsServerRecursionScope -Name "InternalClients" -EnableRecursion $true
PS C:\> Add-DnsServerQueryResolutionPolicy -Name "InternalRecursion" -Action ALLOW -ApplyOnRecursion -RecursionScope "InternalClients" -ServerInterfaceIP "EQ,10.0.0.56"
```

> **Watch out:** Dynamic updates and scavenging work only in the **default** zone scope. Put the records that clients register dynamically in the default scope and the hand-maintained copies in extra scopes.

## Scenario 4: filtering and blocking

```powershell
PS C:\> Add-DnsServerQueryResolutionPolicy -Name "BlockMalware" -Action IGNORE -Fqdn "EQ,*.malicious.example"
PS C:\> Add-DnsServerClientSubnet -Name "BadNet" -IPv4Subnet "203.0.113.0/24"
PS C:\> Add-DnsServerQueryResolutionPolicy -Name "DropBadNet" -Action DENY -ClientSubnet "EQ,BadNet"
PS C:\> Add-DnsServerClientSubnet -Name "DRSubnet" -IPv4Subnet "10.99.0.0/24"
PS C:\> Add-DnsServerZoneTransferPolicy -Name "XfrOnlyFromDR" -Action IGNORE -ClientSubnet "NE,DRSubnet" -ZoneName "contoso.com"
```

Server-level policies have no `-ZoneName`; zone-level policies do.

> **Exam tip:** DNS policies and client subnets are stored **locally** on each DNS server; they are not replicated by AD DS even when the zone is AD-integrated. (Zone **scopes** and their records in an AD-integrated zone *do* replicate with the zone; only the policies and client subnets stay local.) Copy them with `Get-DnsServerQueryResolutionPolicy -ZoneName contoso.com -ComputerName DC1 | Add-DnsServerQueryResolutionPolicy -ZoneName contoso.com -ComputerName DC2`.

## DNSSEC: what it protects

DNSSEC lets a resolver prove that an answer really came from the zone owner and was not altered. It does **not** encrypt queries (that is DNS over HTTPS/TLS). The authoritative server signs records; a resolving server **validates** them using a trust anchor.

| Record | Role |
|---|---|
| DNSKEY | Public key of a KSK or ZSK, published in the zone |
| RRSIG | Signature over a record set |
| NSEC / NSEC3 | Authenticated denial of existence; NSEC3 hashes names to prevent zone walking |
| NSEC3PARAM | Parameters for NSEC3 lookups |
| DS | Hash of the child's KSK, placed in the **parent** zone to chain trust |

### Keys and defaults on Windows Server

| Key | Signs | Default algorithm / length | Default rollover |
|---|---|---|---|
| Key Signing Key (KSK) | Only the DNSKEY record set | RSA/SHA-256, 2048-bit | 755 days (double-signature method) |
| Zone Signing Key (ZSK) | All other record sets | RSA/SHA-256, 1024-bit | 90 days (prepublish method) |

One authoritative primary is the **Key Master**: it generates keys, performs rollovers and polls child zones for signed delegations. With AD-integrated zones the private keys can be replicated to the other DCs so any of them can sign dynamic updates. NSEC3 is the recommended denial method.

```powershell
PS C:\> Invoke-DnsServerZoneSign -ZoneName "secure.contoso.com" -SignWithDefault -PassThru -Force
PS C:\> Get-DnsServerSigningKey -ZoneName "secure.contoso.com"
PS C:\> Get-DnsServerResourceRecord -ZoneName "secure.contoso.com" -RRType DnsKey
PS C:\> Get-DnsServerTrustAnchor -Name "secure.contoso.com"
```

`-SignWithDefault` signs an unsigned zone with one KSK and one ZSK; `-DoResign` re-signs an already-signed zone with its existing parameters.

### Trust anchors

A validating (recursive) server needs a **trust anchor**: the DNSKEY or a DS for the zone (or for a parent such as the root). On domain controllers, enabling **trust anchor distribution** during signing stores the anchors in the forest-wide DNS partition so every DNS server on a DC in the forest can validate. Standalone servers keep anchors in `TrustAnchors.dns`, and you add them manually:

```powershell
PS C:\> Add-DnsServerTrustAnchor -Name "secure.contoso.com" -KeyProtocol DnsSec -Base64Data "AwEAAc..." -CryptoAlgorithm RsaSha256
```

For a chain of trust to a child zone, the parent must also be signed and must contain the child's **DS record**; Windows does not create the DS in the parent automatically.

### Making clients require validation: the NRPT

Windows DNS clients are non-validating stub resolvers. They rely on the DNS server to validate, and by default they do not care whether it did. The **Name Resolution Policy Table (NRPT)** tells clients to request DNSSEC (set the DO bit) and to **require** that the server validated the answer (the AD flag) for a namespace. If the server returns unvalidated data, the client treats the lookup as failed.

```powershell
PS C:\> Add-DnsClientNrptRule -GpoName "DNSSEC Clients" -Namespace ".secure.contoso.com" -DnsSecEnable -DnsSecValidationRequired
PS C:\> Get-DnsClientNrptPolicy
```

In Group Policy, NRPT lives under **Computer Configuration > Policies > Windows Settings > Name Resolution Policy**. A leading dot (`.secure.contoso.com`) matches the suffix; without the dot it is an exact FQDN.

> **Exam tip:** Signing the zone is not enough. Validation needs a **trust anchor on the resolving server**, and client enforcement needs an **NRPT rule** with "require validation". If the question says "ensure clients reject unvalidated responses", the answer is the NRPT.

> **Watch out:** If a signed zone's records are modified after signing on a server that is not the Key Master and has no private key, updates fail. Keep key replication enabled for AD-integrated zones unless you have a reason not to.

## Lab it yourself

On DC1 (Windows Server 2025 evaluation):

```powershell
PS C:\> Add-DnsServerPrimaryZone -Name "secure.contoso.com" -ReplicationScope Forest
PS C:\> Add-DnsServerResourceRecordA -ZoneName "secure.contoso.com" -Name "web" -IPv4Address 10.10.0.80
PS C:\> Invoke-DnsServerZoneSign -ZoneName "secure.contoso.com" -SignWithDefault -Force
PS C:\> Resolve-DnsName web.secure.contoso.com -Server DC1 -DnssecOk
```

You should see RRSIG records in the answer. Then create a client subnet and zone scope for a second lab subnet and confirm with `Resolve-DnsName` from each subnet that the policy returns different IPs.

## Key takeaways

- DNS policy = criteria (client subnet, interface, FQDN, QType, time of day, protocol) + action (ALLOW, DENY, IGNORE) + scopes.
- Records added without `-ZoneScope` go into the default scope, which answers unmatched queries; dynamic updates only work there.
- Recursion scopes plus `-ApplyOnRecursion` give recursion to some clients and not others.
- Policies are local to each server; copy them to every DNS server that hosts the zone.
- KSK signs the DNSKEY set (2048-bit, 755-day rollover by default); ZSK signs the rest (1024-bit, 90-day rollover).
- Resolvers need a trust anchor; AD trust-anchor distribution covers every DC DNS server in the forest.
- NRPT with `-DnsSecValidationRequired` makes clients reject unvalidated answers.
