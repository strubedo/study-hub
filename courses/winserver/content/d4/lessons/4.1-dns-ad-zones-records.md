## Why DNS and AD DS are joined at the hip

AD DS cannot function without DNS. Every domain controller registers SRV records (for example `_ldap._tcp.dc._msdcs.contoso.com` and `_kerberos._tcp.Default-First-Site-Name._sites.contoso.com`) so clients can find a DC in their site. That lookup process is called **DC Locator**. If those records are missing or point at a dead DC, logons, Group Policy and domain joins fail long before anything looks like a "DNS problem".

The Netlogon service registers the DC's records and keeps a copy in `%SystemRoot%\System32\config\netlogon.dns`. If records go missing, restart Netlogon or run `nltest /dsregdns` on the DC to re-register them.

```text
C:\> nltest /dsgetdc:contoso.com /force
C:\> nltest /dsregdns
C:\> dcdiag /test:dns /v
```

## Zone types

| Zone type | Stored where | Writable? | Typical use |
|---|---|---|---|
| Primary (file-backed) | `%SystemRoot%\System32\dns\<zone>.dns` | Yes, on one server only | Standalone DNS servers, DMZ |
| AD-integrated primary | AD DS partition | Yes, on every DC that hosts it (multimaster) | Internal AD namespaces |
| Secondary | Zone file, copied by zone transfer | No (read-only) | Extra copies on non-DC servers or third-party DNS |
| Stub | File or AD DS | No; holds only SOA, NS and glue A records | Keeping track of another zone's name servers |
| Reverse lookup | Either of the above | Depends | PTR records (`in-addr.arpa`, `ip6.arpa`) |

Key rules the exam likes:

- Only **primary** and **stub** zones (and conditional forwarders) can be stored in AD DS. A **secondary zone can never be AD-integrated**, because it is by definition a read-only transfer copy.
- AD-integrated zones replicate with normal AD replication, so you do not configure zone transfers between the DCs that host them.
- Read-only domain controllers (RODCs) hold a read-only copy of AD-integrated zones and refer dynamic updates to a writable DC.

## AD DS replication scopes

When you store a zone in AD DS you choose which partition holds it, and therefore which DCs get a copy.

| Scope (DNS Manager wording) | PowerShell `-ReplicationScope` | Partition | Who gets the zone |
|---|---|---|---|
| All DNS servers running on DCs in this forest | `Forest` | ForestDnsZones | Every DC in the forest that runs the DNS Server role |
| All DNS servers running on DCs in this domain | `Domain` | DomainDnsZones | Every DNS-running DC in the domain (default for new zones) |
| All DCs in this domain (for Windows 2000 compatibility) | `Legacy` | Domain partition | Every DC in the domain, DNS installed or not |
| All DCs in a specified application partition | `Custom` + `-DirectoryPartitionName` | Your own partition | Only DCs you enlist in the partition |

The `_msdcs.contoso.com` zone is created with **Forest** scope by default because every DC in every domain must be able to find forest-wide records such as global catalog SRV records and the DC GUID CNAMEs used by replication.

```powershell
PS C:\> Add-DnsServerPrimaryZone -Name "corp.contoso.com" -ReplicationScope Forest -DynamicUpdate Secure
PS C:\> Set-DnsServerPrimaryZone -Name "branch.contoso.com" -ReplicationScope Custom -DirectoryPartitionName "BranchDns.contoso.com"
PS C:\> ConvertTo-DnsServerPrimaryZone -Name "legacy.contoso.com" -ReplicationScope Domain -PassThru
```

> **Exam tip:** "Replicate the zone to every DNS server in the forest and minimise replication to DCs that do not run DNS" points to **Forest** (ForestDnsZones), not Legacy. Legacy puts the zone in the domain partition, which replicates to every DC in that one domain only.

> **Watch out:** A custom application partition must exist and each DC must be enlisted before the zone appears there. Use `Add-DnsServerDirectoryPartition` and `Register-DnsServerDirectoryPartition`.

## Dynamic updates and record ownership

Zones accept dynamic updates in one of three modes:

| Mode | Meaning |
|---|---|
| None | Only administrators can create records |
| Nonsecure and secure | Anyone who can reach the server can update any record (dangerous) |
| Secure only | Client must authenticate with Kerberos; available only on **AD-integrated** zones |

With secure updates, each record (strictly, each `dnsNode` object) gets an ACL. The computer that registered `server7.contoso.com` owns it, so a different computer cannot overwrite it. That protects against hijacking but creates a classic DHCP problem: if a DHCP server registers a record on behalf of a client and that DHCP server is later replaced, the new server is not the owner and cannot update or delete the record.

Two fixes:

1. Configure every DHCP server to use the **same dedicated user account** for DNS registration (`Set-DhcpServerDnsCredential`). This is the recommended fix.
2. Add the DHCP servers to the **DnsUpdateProxy** group. Records created by members of this group have no owner, so any authenticated computer can take them over. This is weaker. Never put a DHCP server that is also a DC into DnsUpdateProxy without a credential, because records it creates, including the DC's own, become unowned.

> **Real world:** Windows clients register their own A record and the DHCP server registers the PTR by default. Setting the DHCP option to "Always dynamically update DNS records" makes the DHCP server own both.

## Common resource records

| Record | Purpose | PowerShell |
|---|---|---|
| A / AAAA | Name to IPv4 / IPv6 | `Add-DnsServerResourceRecordA` / `...AAAA` |
| CNAME | Alias to a canonical name | `Add-DnsServerResourceRecordCName` |
| PTR | Address to name | `Add-DnsServerResourceRecordPtr` |
| MX | Mail exchanger with preference | `Add-DnsServerResourceRecordMX` |
| SRV | Service location: priority, weight, port, target | `Add-DnsServerResourceRecord -Srv` |
| NS / SOA | Authority for the zone | Created with the zone |
| TXT | Free text (SPF, domain verification) | `Add-DnsServerResourceRecord -Txt` |

```powershell
PS C:\> Add-DnsServerResourceRecordA -ZoneName "contoso.com" -Name "app1" -IPv4Address "10.10.5.20" -CreatePtr
PS C:\> Add-DnsServerResourceRecordCName -ZoneName "contoso.com" -Name "intranet" -HostNameAlias "app1.contoso.com"
PS C:\> Add-DnsServerResourceRecord -ZoneName "contoso.com" -Srv -Name "_sip._tcp" -DomainName "sip1.contoso.com" -Priority 10 -Weight 50 -Port 5060
PS C:\> Get-DnsServerResourceRecord -ZoneName "contoso.com" -Name "app1" -RRType A
```

`-CreatePtr` only works if the matching reverse zone already exists on that server. A CNAME cannot share a name with any other record type, and it should never be placed at the zone apex.

### GlobalNames zone

The **GlobalNames** zone resolves single-label names (for example `intranet`) forest-wide without WINS. Create a forest-scoped AD-integrated zone named `GlobalNames`, add CNAME records to it, then enable it on every DNS server with `Set-DnsServerGlobalNameZone -Enable $true`. It holds static records only; dynamic updates are not supported.

## Aging and scavenging

Dynamic clients leave stale records behind when they leave the network. Scavenging removes them, but only when three things line up:

1. **Aging is enabled on the zone**, which sets the no-refresh and refresh intervals.
2. **Scavenging is enabled on at least one server** that hosts the zone, which sets the scavenging period (how often the server looks).
3. The record has a **non-zero timestamp**. Manually created records have a zero timestamp by default and are never scavenged.

| Interval | Default | Meaning |
|---|---|---|
| No-refresh | 7 days | After a timestamp is written, refreshes that change nothing are ignored. This suppresses replication churn. Real changes (a new IP) are still accepted. |
| Refresh | 7 days | Starts when no-refresh ends. The client must refresh during this window. |
| Scavenging period | 7 days | How often the scavenging server runs a pass. |

A record becomes **eligible** when `timestamp + no-refresh + refresh` is in the past. It is actually deleted at the next scavenging pass. With defaults a dead record can linger for up to about 21 days.

```powershell
PS C:\> Set-DnsServerZoneAging -Name "contoso.com" -Aging $true -NoRefreshInterval 7.00:00:00 -RefreshInterval 7.00:00:00
PS C:\> Set-DnsServerScavenging -ScavengingState $true -ScavengingInterval 7.00:00:00
PS C:\> Set-DnsServerZoneAging -Name "contoso.com" -ScavengeServers 10.10.0.10
PS C:\> Start-DnsServerScavenging -Verbose
```

> **Watch out:** Keep `no-refresh + refresh` at least as long as your longest DHCP lease. If the sum is shorter, a client that is alive but only renews its record every few days can be deleted between refreshes.

> **Exam tip:** Scavenging is configured per zone (aging) **and** per server (scavenging). Restricting which servers may scavenge (`-ScavengeServers`) is the clean way to keep only one DC doing deletions, which simplifies troubleshooting.

When you first enable aging, the zone gets one refresh interval of grace before any record is considered, which gives live clients time to stamp their records.

## Zone transfers to secondaries

AD-integrated zones need no transfers between DCs. For a secondary on a non-DC or a third-party server, enable transfers on the primary and restrict them:

```powershell
PS C:\> Set-DnsServerPrimaryZone -Name "contoso.com" -SecureSecondaries TransferToSecureServers -SecondaryServers 192.168.50.10 -Notify NotifyServers -NotifyServers 192.168.50.10
PS C:\> Add-DnsServerSecondaryZone -Name "contoso.com" -ZoneFile "contoso.com.dns" -MasterServers 10.10.0.10
```

`-SecureSecondaries` accepts `NoTransfer`, `TransferAnyServer`, `TransferToZoneNameServer` and `TransferToSecureServers`. Windows DNS supports full (AXFR) and incremental (IXFR) transfers over TCP 53.

## Lab it yourself

On a Windows Server 2025 evaluation DC (DC1) in a lab forest:

```powershell
PS C:\> Add-DnsServerPrimaryZone -Name "lab.contoso.com" -ReplicationScope Forest -DynamicUpdate Secure
PS C:\> Add-DnsServerPrimaryZone -NetworkId "10.10.0.0/24" -ReplicationScope Domain
PS C:\> Add-DnsServerResourceRecordA -ZoneName "lab.contoso.com" -Name "web" -IPv4Address 10.10.0.50 -CreatePtr -AgeRecord
PS C:\> Set-DnsServerZoneAging -Name "lab.contoso.com" -Aging $true -NoRefreshInterval 0.01:00:00 -RefreshInterval 0.01:00:00
PS C:\> Get-DnsServerResourceRecord -ZoneName "lab.contoso.com" -Name web | Format-List HostName, RecordType, Timestamp
```

Short intervals let you watch a record become stale in a couple of hours. Run `Start-DnsServerScavenging -Verbose` after enabling scavenging on the server to see it deleted.

## Key takeaways

- AD-integrated zones are multimaster, replicate with AD and are the only zones that support **secure** dynamic updates.
- Replication scope: **Forest** (ForestDnsZones), **Domain** (DomainDnsZones, default), **Legacy** (domain partition, all DCs), **Custom** (application partition).
- Secondary zones cannot be stored in AD DS; primary, stub and conditional forwarders can.
- Use a shared DHCP DNS-update credential rather than DnsUpdateProxy to avoid record-ownership problems.
- Scavenging needs zone aging, server scavenging and non-zero timestamps; defaults are 7 + 7 days, with a 7-day scavenging period.
- Static records you create by hand are not scavenged unless you add them with `-AgeRecord`.
- Lock down zone transfers with `-SecureSecondaries TransferToSecureServers`.
