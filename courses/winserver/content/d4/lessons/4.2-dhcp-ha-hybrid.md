## High availability options for DHCP

| Option | How it works | Strengths | Weaknesses |
|---|---|---|---|
| **DHCP failover** | Two Windows DHCP servers share the same scope and replicate lease data over TCP 647 | Both servers know every lease; no address conflicts; works across sites | DHCPv4 only; exactly two servers per relationship; scope changes need manual replication |
| Split scope (80/20) | Two servers each own a non-overlapping part of the range | Simple, works with any server version, works for DHCPv6 | No lease sharing; the 20 percent server can run out; a client that moves servers gets a new address |
| Clustered DHCP | DHCP service as a failover cluster role on shared storage | One logical server | Needs a cluster and shared storage; single database; more complex |

> **Exam tip:** "Ensure clients keep the same address if a server fails, minimise administrative effort, two servers" means **DHCP failover**. "DHCPv6 scope must be highly available" cannot use failover; use split scope or two servers with identical stateless options.

## DHCP failover essentials

A **failover relationship** links two servers and contains one or more scopes. One server can have many relationships with different partners, but each relationship has exactly two members and each scope belongs to at most one relationship.

### Modes

| Setting | Load balance (default) | Hot standby |
|---|---|---|
| Who serves clients | Both, split by a hash of the client MAC (RFC 3074) | The active server only; standby serves when the active is unreachable |
| Key percentage | `LoadBalancePercent`, default **50** (50:50) | `ReservePercent`, default **5** (free addresses held for the standby) |
| Best fit | Both servers in the same site | A central server backing up a branch server |

### Timers and states

- **MCLT (Maximum Client Lead Time)**, default **1 hour**: the longest a server can extend a lease beyond what its partner knows about. When a server renews a lease while the partner is unreachable, it grants only an MCLT-length lease. After entering partner-down, a server waits MCLT before taking over the partner's entire free pool.
- **Auto state switchover interval** (`StateSwitchInterval`): if enabled, a server in **COMMUNICATION INTERRUPTED** moves automatically to **PARTNER DOWN** after this interval. It is **disabled by default** (`AutoStateTransition` is False); specifying `-StateSwitchInterval` turns it on. In the wizard, enabling it suggests 60 minutes.

| State | Meaning |
|---|---|
| NORMAL | Partners are talking; each serves its share |
| COMMUNICATION INTERRUPTED | Partner unreachable; the server cannot tell whether the partner is down or just isolated, so it is cautious (short MCLT leases, only its own pool, plus the partner's pool in load balance once its own is exhausted) |
| PARTNER DOWN | Administrator or the auto switchover declares the partner down; after MCLT the server owns the whole pool |
| RECOVER / RECOVER WAIT / RECOVER DONE | Partners resynchronise after communication returns |

```powershell
PS C:\> Add-DhcpServerv4Failover -ComputerName DHCP1 -Name "DHCP1-DHCP2" -PartnerServer DHCP2.contoso.com -ScopeId 10.1.10.0, 10.1.20.0 -LoadBalancePercent 50 -MaxClientLeadTime 01:00:00 -SharedSecret "Use-A-Long-Secret-Here" -Force
PS C:\> Add-DhcpServerv4Failover -ComputerName HQDHCP -Name "HQ-Branch7" -PartnerServer BR7DHCP.contoso.com -ScopeId 10.7.0.0 -ServerRole Standby -ReservePercent 10 -StateSwitchInterval 01:00:00
PS C:\> Get-DhcpServerv4Failover -ComputerName DHCP1
PS C:\> Set-DhcpServerv4Failover -Name "HQ-Branch7" -PartnerDown
PS C:\> Invoke-DhcpServerv4FailoverReplication -ComputerName DHCP1 -Name "DHCP1-DHCP2"
```

In the second example the local server (HQDHCP) is the **standby**, so the branch server is active and HQ only steps in when it cannot reach it.

### Requirements and gotchas

- **Time** on both partners must be within **one minute**; the wizard refuses to create the relationship otherwise. Each failover message also carries a UTC timestamp, and if a received message is more than a minute off, the receiver logs a critical "out of time synchronization" event (Event ID 20253).
- **Relay agents** must forward to **both** servers (two `ip helper-address` entries), or clients cannot reach the partner when the first server dies.
- **Configuration changes are not automatic.** New options, reservations or exclusions on one partner must be pushed with `Invoke-DhcpServerv4FailoverReplication` (or "Replicate scope" in the console). Replication overwrites the partner's copy, so always replicate **from** the server with the correct settings.
- Both partners should use the **same DNS dynamic-update credential**, otherwise a record created by one cannot be updated by the other.
- **Message authentication**: the console wizard has **Enable Message Authentication** checked by default and asks for a shared secret. With `Add-DhcpServerv4Failover`, authentication is turned on only when you pass `-SharedSecret`.
- Failover supports **DHCPv4 scopes only**; DHCPv6 scopes cannot be added to a relationship.

> **Watch out:** If a failover partner is a DHCP **cluster**, configure the relationship with the cluster's client access point name or IP, not a node name.

## IP addressing in Azure

Azure virtual networks run their own DHCP service on the host. A VM's IP address is **configured on the Azure network interface** (dynamic or static allocation), and the guest OS learns it by DHCP from the platform (the virtual IP `168.63.129.16` handles DHCP, DNS and health traffic for the VM).

What that means for administrators:

- **Do not configure a static IP inside a Windows VM's network adapter** unless a documented scenario requires it (for example, secondary IP configurations, which must be added in the guest by hand). If you need a fixed address, set the NIC's IP allocation to **Static** in Azure and leave the guest on DHCP. Setting the primary address inside the guest and getting it wrong (or changing the Azure NIC later) disconnects the VM, often requiring a network interface reset or the Serial Console to fix.
- **You cannot run your own DHCP server to hand out addresses to VMs in a VNet.** DHCP broadcasts from Azure VMs are handled by the platform and never reach a DHCP server VM. Microsoft documents only one supported use of a DHCP server VM in Azure: acting as a target for **on-premises** relay agents (it needs a loopback adapter with an IP also added as a secondary IP configuration on the Azure NIC, so relayed unicast packets are routed to it).
- DNS servers for VMs are set on the **VNet** (or per NIC), not by DHCP options you control.

### Reserved addresses per Azure subnet

Azure reserves five addresses in every subnet:

| Address (for 10.20.1.0/24) | Use |
|---|---|
| 10.20.1.0 | Network address |
| 10.20.1.1 | Default gateway |
| 10.20.1.2 and 10.20.1.3 | Azure DNS mapping to the VNet space |
| 10.20.1.255 | Broadcast address |

So a /29 gives only three usable VM addresses, and the first VM in a /24 normally gets `.4`.

## Troubleshooting IP addressing

### On-premises symptoms

| Symptom | Probable cause | Fix |
|---|---|---|
| Client has `169.254.x.x` (APIPA) | No DHCP response: relay missing, server unauthorized, service stopped, scope inactive, or switch port problem | Check `Get-DhcpServerInDC`, scope state, relay configuration |
| Clients in one VLAN only fail | Relay agent missing or pointing to the wrong IP on that SVI/router | Add helper addresses for both failover partners |
| "Address in use" or duplicate IP warnings | Static device inside the range | Exclude or reserve; enable conflict detection |
| Scope shows 100 percent in use | Pool exhausted | Shorter lease, extend range, add a superscope member |
| Clients get the wrong gateway | Server option overriding a missing scope option, or a policy matching | Check option levels with `Get-DhcpServerv4OptionValue -ScopeId ... -All` |
| Clients keep an MCLT-length lease | Failover in COMMUNICATION INTERRUPTED | Restore partner connectivity on TCP 647 or move to PARTNER DOWN |

```powershell
PS C:\> Get-DhcpServerv4ScopeStatistics -ComputerName DHCP1
PS C:\> Get-DhcpServerv4Lease -ScopeId 10.1.10.0 -ClientId "00-15-5D-0A-14-32"
PS C:\> Get-DhcpServerv4OptionValue -ScopeId 10.1.10.0 -All
PS C:\> Get-DhcpServerv4Failover | Format-List Name, State, Mode, PartnerServer
```

On the client:

```text
C:\> ipconfig /all
C:\> ipconfig /release
C:\> ipconfig /renew
C:\> ipconfig /registerdns
```

The DHCP server writes a daily audit log to `%SystemRoot%\System32\dhcp\DhcpSrvLog-<day>.log` that shows every lease, renewal, NACK and conflict.

### Hybrid symptoms

| Symptom | Cause | Fix |
|---|---|---|
| VPN or peering cannot be created, or routes are ignored | VNet address space overlaps an on-premises range | Re-address one side; plan non-overlapping space up front |
| Azure VM unreachable after "making its IP static" | Static IP set inside the guest does not match the Azure NIC | Reset the NIC from the portal or use Serial Console to return the adapter to DHCP; set static allocation on the Azure NIC |
| A new VM gets `.4` instead of `.1` | Azure reserves the first four addresses | Expected behaviour |
| VMs ignore DHCP option 006 you configured on an Azure DHCP VM | DHCP for VMs is the platform's; your server never sees their requests | Configure DNS servers on the VNet or NIC |
| On-premises clients relaying to a DHCP VM in Azure fail at T1 renew | Direct client-to-server unicast renewals (UDP 68 to 67) to Azure are not supported; renewal succeeds at T2 via the relay | Expected; ensure the relay path works |

## Lab it yourself

Two Windows Server 2025 VMs (DHCP1, DHCP2) on the same Hyper-V internal switch, both domain-joined and authorized:

```powershell
PS C:\> Add-DhcpServerv4Scope -ComputerName DHCP1 -Name Lab -StartRange 192.168.100.50 -EndRange 192.168.100.150 -SubnetMask 255.255.255.0
PS C:\> Add-DhcpServerv4Failover -ComputerName DHCP1 -Name LabFO -PartnerServer DHCP2 -ScopeId 192.168.100.0 -LoadBalancePercent 50
PS C:\> Get-DhcpServerv4Scope -ComputerName DHCP2
PS C:\> Stop-Service DHCPServer
```

Stop the service on DHCP1, renew a client and watch `Get-DhcpServerv4Failover -ComputerName DHCP2` move to CommunicationInterrupted. Then try `Set-DhcpServerv4Failover -ComputerName DHCP2 -Name LabFO -PartnerDown`.

## Key takeaways

- DHCP failover: two servers, DHCPv4 only, TCP 647, time within one minute, relay to both partners.
- Load balance default 50:50; hot standby reserve default 5 percent; MCLT default 1 hour.
- Auto switchover from COMMUNICATION INTERRUPTED to PARTNER DOWN is off unless you set `StateSwitchInterval`.
- Replicate scope changes manually with `Invoke-DhcpServerv4FailoverReplication`, from the correct server.
- Split scope is the fallback for DHCPv6 or mixed environments.
- Azure VMs get addresses from the platform; set static IPs on the Azure NIC, never in the guest.
- Azure reserves five IPs per subnet (.0, .1, .2, .3 and the last).
