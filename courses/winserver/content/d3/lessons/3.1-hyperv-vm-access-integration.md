## Getting into a VM: four paths

A Hyper-V administrator has four ways to reach a guest, and the exam tests when each one applies:

| Path | Transport | Needs guest networking? | Typical use |
|---|---|---|---|
| **VMConnect** (basic session) | VMBus video/keyboard/mouse | No | Console access, BIOS/boot, OS install |
| **VMConnect enhanced session** | RDP over VMBus | No | Clipboard, drive and USB redirection, resizable display |
| **PowerShell Direct** | PowerShell over VMBus (Windows guests) | No | Scripted configuration from the host |
| **SSH Direct** (`hvc ssh`) | SSH over Hyper-V sockets (Linux guests) | No (if the guest listens on vsock) | Shell access to Linux guests from the host |
| PowerShell remoting / SSH / RDP over the network | TCP/IP | Yes | Normal remote management from anywhere |

## Enhanced Session Mode

A basic VMConnect session only sends screen, keyboard and mouse. **Enhanced session mode** runs an RDP session over the VMBus, so you get:

* Clipboard copy/paste (text and files)
* Local drive, smart card, printer and USB device redirection
* Audio redirection and a resizable, multi-monitor display

It needs **two switches turned on**:

1. **Host policy** - Hyper-V Settings > Server > **Enhanced Session Mode Policy** > *Allow enhanced session mode*. It is **off by default on Windows Server** and on by default on Windows client.
2. **User preference** - Hyper-V Settings > User > *Use enhanced session mode* (on by default once the policy allows it).

```powershell
PS C:\> Set-VMHost -EnableEnhancedSessionMode $true
PS C:\> Get-VMHost | Select-Object EnableEnhancedSessionMode
```

The guest must support it: Windows 8.1 / Windows Server 2012 R2 and later have the RDP stack built in, and Microsoft lists **Remote Desktop enabled in the guest** as a requirement (Remote Desktop is off by default on Windows Server, so turn it on in the guest as well as on the host). The session travels over the VMBus rather than the guest's network, so the guest needs no IP connectivity to the host. Linux guests can use enhanced sessions through **xrdp** with the Hyper-V socket transport (the Ubuntu `linux-vm-tools` approach; Microsoft's own enhanced session documentation covers Windows guests), which you set on the VM:

```powershell
PS C:\> Set-VM -VMName Ubuntu1 -EnhancedSessionTransportType HvSocket
```

> **Exam tip:** "Copy files into a VM that has no network adapter with the least effort" - enhanced session mode (paste into the guest) or `Copy-VMFile`/PowerShell Direct. A basic session can't paste files.

## Managing VMs with PowerShell

The **Hyper-V module** runs on the host or remotely (`-ComputerName`, or within `Enter-PSSession` to the host):

```powershell
PS C:\> Get-VM -ComputerName HV1, HV2 | Where-Object State -eq 'Running'
PS C:\> New-VM -Name VM1 -Generation 2 -MemoryStartupBytes 4GB -NewVHDPath D:\VMs\VM1.vhdx -NewVHDSizeBytes 80GB -SwitchName External
PS C:\> Set-VMProcessor -VMName VM1 -Count 4
PS C:\> Start-VM -Name VM1; Stop-VM -Name VM1 -Force
```

Remote management of the host needs the normal WinRM path plus the right delegation if you then touch a second server (for example, storing VHDs on an SMB share), which is the same double-hop problem covered in Domain 2.

### PowerShell Direct

PowerShell Direct lets you run PowerShell **inside a Windows guest from its host**, over the VMBus, regardless of the guest's network, firewall or remoting configuration.

Requirements:

* Host: Windows 10 / **Windows Server 2016** or later.
* Guest: Windows 10 / **Windows Server 2016** or later.
* The VM must be **running locally on this host** - PowerShell Direct doesn't work from a remote management PC or against a VM on another host.
* You must be signed in to the host as a **Hyper-V administrator**.
* You must supply **valid credentials for the guest OS** (local or domain account). Host admin rights don't grant rights inside the guest.

```powershell
PS C:\> Enter-PSSession -VMName VM1 -Credential VM1\Administrator
PS C:\> Invoke-Command -VMName VM1 -Credential $cred -ScriptBlock { Rename-Computer -NewName WEB1 -Restart }
PS C:\> $s = New-PSSession -VMName VM1 -Credential $cred
PS C:\> Copy-Item -ToSession $s -Path C:\ISO\tools.zip -Destination C:\Temp\
PS C:\> Copy-Item -FromSession $s -Path C:\Logs\setup.log -Destination D:\Collected\
```

You can use `-VMId` instead of `-VMName` when names are duplicated. The guest-side service is the **Hyper-V PowerShell Direct Service** (`vmicvmsession`).

Classic uses: configure IP addressing on a brand-new VM, join it to the domain, fix a guest whose firewall blocks WinRM, or copy files into an isolated lab VM.

### SSH Direct for Linux guests

PowerShell Direct works only with Windows guests. For **Linux guests**, Hyper-V (Windows Server 2019 and later, Windows 10 1803 and later) includes **`hvc.exe`**, which can run SSH over Hyper-V sockets (AF_HYPERV on the host, AF_VSOCK in the guest) instead of TCP/IP:

```text
C:\> hvc list
C:\> hvc ssh admin1@Ubuntu1
```

The VM name replaces the host name. Under the covers `hvc ssh` starts the host's OpenSSH client (`ssh.exe`) with `hvc nc` as its proxy command, and `hvc nc` opens a Hyper-V socket to port 22 in the guest. Requirements:

* The VM runs on the **local host** and you're a Hyper-V administrator there; the OpenSSH client is present on the host.
* The guest kernel has Hyper-V socket support (`CONFIG_VSOCKETS` and `CONFIG_HYPERV_VSOCKETS`, standard in current distribution kernels).
* Something in the guest **listens on vsock port 22**. A stock sshd listens only on TCP, so this needs a systemd socket unit (`ListenStream=vsock::22`), a relay such as socat, or a distribution whose systemd binds sshd to vsock automatically (systemd 256 and later).

> **Watch out:** `hvc nc` tries vsock first and can fall back to a TCP/IP connection, so a successful `hvc ssh` while the guest network is healthy doesn't prove the vsock path works. Test it with the guest's network disconnected before you rely on it for recovery. `hvc` is documented mainly in its own built-in help (`hvc.exe` with no arguments), not on Microsoft Learn.

> **Watch out:** `Enter-PSSession -VMName` fails against a Linux guest even if PowerShell 7 is installed in it. Use `hvc ssh` (or normal SSH over the network) for Linux.

## Integration services

Integration services are the guest components that make a VM "enlightened": they talk to the host over the VMBus. Modern Windows and Linux guests receive them through the OS itself (Windows Update or the distribution's kernel) - you no longer install them from an ISO for Windows Server 2016 and later guests.

| Service (Get-VMIntegrationService name) | Default | What it does |
|---|---|---|
| **Heartbeat** | On | Reports that the guest OS is responsive (used by cluster VM monitoring and health checks) |
| **Shutdown** | On | Lets the host shut down the guest cleanly (`Stop-VM`, host shutdown actions) |
| **Time Synchronization** | On | Syncs guest clock from host; important after save/restore |
| **Key-Value Pair Exchange** | On | Exchanges registry key/values such as guest OS version and IP addresses shown in Hyper-V Manager |
| **VSS** (Backup / volume shadow copy) | On | Lets host-level backup and **production checkpoints** quiesce the guest |
| **Guest Service Interface** | **Off** | Enables `Copy-VMFile` from host to guest |

```powershell
PS C:\> Get-VMIntegrationService -VMName VM1
PS C:\> Enable-VMIntegrationService -VMName VM1 -Name 'Guest Service Interface'
PS C:\> Copy-VMFile -Name VM1 -SourcePath D:\Installers\agent.msi -DestinationPath C:\Temp\agent.msi -FileSource Host -CreateFullPath
```

Disabling a service on the host side stops the host from using it; the guest service may still be running. Inside a Windows guest the services appear as `vmic*` services (for example `vmicheartbeat`, `vmicshutdown`, `vmictimesync`, `vmickvpexchange`, `vmicvss`, `vmicguestinterface`, `vmicvmsession`).

`Get-VMIntegrationService` reports `PrimaryStatusDescription` (OK / No Contact / Lost Communication). "No Contact" for every service usually means the guest isn't running integration components at all (an unsupported or very old guest) or hasn't finished booting.

> **Real world:** Virtualised domain controllers synchronise time from the domain hierarchy (the PDC emulator in the forest root syncs from an external source). Many admins disable the *Time Synchronization* integration service's ongoing sync for DC VMs so the host clock can't fight the domain hierarchy; keep the host itself on accurate time either way.

## Lab it yourself

1. On a Windows Server 2025 Hyper-V host, run `Get-VMHost | Select EnableEnhancedSessionMode` (expect False), enable it, and reconnect to a Windows guest - note the display configuration dialog and local resources options.
2. Create a VM with **no network adapter**, then run `Invoke-Command -VMName VM1 -Credential (Get-Credential) { Get-NetAdapter }` to prove PowerShell Direct doesn't need networking.
3. Try `Copy-VMFile` before and after enabling **Guest Service Interface** and compare the error.
4. If you have an Ubuntu guest, run `hvc list` and try `hvc ssh <user>@<vmname>`.

## Key takeaways

* Enhanced session mode = RDP over VMBus; turn on the host policy (`Set-VMHost -EnableEnhancedSessionMode $true`, off by default on Windows Server), the user setting, and Remote Desktop in the guest.
* Linux enhanced sessions need xrdp and `Set-VM -EnhancedSessionTransportType HvSocket`.
* PowerShell Direct (`-VMName`/`-VMId`) needs Windows 10/Server 2016+ host and guest, the VM running locally, Hyper-V admin on the host and guest credentials.
* `Copy-Item -ToSession/-FromSession` over a PowerShell Direct session moves files without networking.
* `hvc ssh user@VMName` is SSH Direct for Linux guests over Hyper-V sockets; the guest needs vsock kernel support and an SSH listener on vsock port 22.
* Guest Service Interface is the only integration service off by default and is required for `Copy-VMFile`; VSS is needed for production checkpoints.
