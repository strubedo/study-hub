## Disks on an Azure Windows Server VM

Every Azure VM has:

| Disk | Letter (Windows) | Persistence | Notes |
|---|---|---|---|
| **OS disk** | C: | Persistent managed disk | Default 127 GiB for most Windows images; max **4,095 GiB**; MBR images can only use 2 TiB unless converted to GPT |
| **Temporary disk** | D: (most sizes) | **Not persistent** - lost on deallocation, redeploy, resize to another host or host maintenance | Page file and scratch data only. Some sizes (for example *Dsv5*) have no temp disk |
| **Data disks** | Your choice | Persistent managed disks | Count and total performance limited by the VM size |

> **Watch out:** Never store data on the temporary disk. And never put AD DS database/logs or SYSVOL on a data disk with host caching other than **None**.

### Managed disk types

| Type | Best for | Can be OS disk? | Host caching | Notes |
|---|---|---|---|---|
| **Ultra Disk** | Top-tier IO (SAP HANA, top SQL) | No | Not supported | IOPS/throughput adjustable independently of size |
| **Premium SSD v2** | Most production databases, sub-ms latency | No | Not supported | Performance set independently of size; billed per GiB/IOPS/MBps |
| **Premium SSD** | Production workloads, OS disks | Yes | ReadOnly / ReadWrite / None | Performance tied to the size tier (P10, P30...); needs a VM size with premium storage support (the "s" in Dsv5) |
| **Standard SSD** | Web servers, light production, dev/test | Yes | Yes | Consistent but lower IOPS |
| **Standard HDD** | Backups, infrequent access | Yes, but Standard HDD **OS disks retire on September 8, 2028** - use Standard SSD or better for new OS disks | Yes | Cheapest, variable latency; LRS only |

Redundancy: **LRS** (three copies in one datacenter) or **ZRS** (across three zones, for Premium SSD and Standard SSD). Ultra Disk and Premium SSD v2 support LRS only.

**Host caching** (Premium SSD, Standard SSD/HDD):

* **ReadOnly** - read-heavy data disks (SQL data files).
* **None** - write-heavy or write-through needs: logs, and **AD DS** database disks.
* **ReadWrite** - the OS disk default; only for apps that handle write-back caching.

Changing caching on a data disk briefly detaches/reattaches it; changing it on the OS disk restarts the VM.

### Encryption

* **Server-side encryption (SSE)** is always on for managed disks, with platform-managed keys or customer-managed keys in Key Vault (via a *disk encryption set*).
* **Encryption at host** extends encryption to the **temporary disk and disk caches** on the VM host - the recommended option for new VMs.
* **Azure Disk Encryption (ADE)** uses BitLocker inside the guest with keys in Key Vault. ADE is **retiring on September 15, 2028**; after that date, ADE-encrypted disks fail to unlock on reboot. Migrate to encryption at host (which needs new disks, not an in-place conversion).

### Adding and expanding disks

```text
az vm disk attach --resource-group RG1 --vm-name VM1 --name VM1-data2 --new --size-gb 512 --sku Premium_LRS --caching ReadOnly
az disk update --resource-group RG1 --name VM1-data2 --size-gb 1024
```

```powershell
PS C:\> $vm = Get-AzVM -ResourceGroupName RG1 -Name VM1
PS C:\> $vm = Add-AzVMDataDisk -VM $vm -Name VM1-data3 -CreateOption Empty -DiskSizeInGB 256 -Lun 2 -Caching None
PS C:\> Update-AzVM -ResourceGroupName RG1 -VM $vm
# inside the guest
PS C:\> Get-Disk | Where-Object PartitionStyle -eq 'RAW' | Initialize-Disk -PartitionStyle GPT -PassThru |
          New-Partition -AssignDriveLetter -UseMaximumSize | Format-Volume -FileSystem NTFS -NewFileSystemLabel Data3
```

**Expanding** rules:

* **Data disks** can usually be expanded **without deallocating** the VM ("expand without downtime"). Exception: a Standard HDD, Standard SSD or Premium SSD disk of **4 TiB or less** must be detached/the VM deallocated to grow **beyond 4 TiB**. Ultra Disk and Premium SSD v2 expand online at any size.
* **OS disks** generally require the VM to be **deallocated** to expand.
* **Shared disks** (`maxShares` > 1) can't be live-resized.
* **Shrinking** a managed disk isn't supported.
* After growing the disk, **extend the volume inside Windows** (Disk Management, `diskpart extend`, or `Resize-Partition`). Allow a few minutes (up to 10) or rescan for the new size to appear.

Changing a disk's **type** (for example Standard SSD to Premium SSD) is done on the disk's *Size + performance* page or with `az disk update --sku`; Premium requires a VM size that supports premium storage.

## Capacity: resizing VMs

```text
az vm list-vm-resize-options --resource-group RG1 --name VM1 --output table
az vm resize --resource-group RG1 --name VM1 --size Standard_D8s_v5
```

* Resizing **restarts** the VM.
* If the new size isn't available on the hardware cluster hosting the VM, it doesn't appear in the resize options (or the resize fails with an allocation error). **Deallocate** the VM first (`az vm deallocate`), and every size available in the region becomes possible.
* Check the target size supports what you use: premium storage, number of data disks and NICs, accelerated networking, a temp disk if the VM has one, and the VM generation.
* Resize doesn't change disk size or type.

### Virtual Machine Scale Sets

A **Virtual Machine Scale Set (VMSS)** manages a group of VMs that scale in and out together, typically behind Azure Load Balancer or Application Gateway.

| | Flexible orchestration (recommended) | Uniform orchestration |
|---|---|---|
| Instances | Standard VMs (`Microsoft.Compute/virtualMachines`) you can manage individually | Identical instances managed only through the scale set |
| Mixed sizes / OS | Yes | No |
| Max instances | 1,000 | 1,000 |
| Fault domain spreading | Max spreading, fixed 2-3, or zones | Fixed 2/3/5, or zones |
| Default outbound internet | **No** - add NAT gateway, load balancer outbound rules or public IPs | Only in older, non-private subnets. Default outbound access is retired: new VNets (API versions after March 31, 2026) use private subnets, so plan an explicit outbound method for either mode |

**Autoscale** (Azure Monitor autoscale settings):

* **Instance limits**: minimum, maximum and default count. Default applies when metrics are unavailable.
* **Metric rules**: e.g. *Percentage CPU > 70 % average over 10 minutes -> increase count by 2*; always pair a scale-out rule with a **scale-in** rule (e.g. CPU < 30 %).
* **Cool down** (default 5 minutes) prevents flapping.
* **Schedule-based** profiles: more instances during business hours.
* **Scale-in policy**: Default (balance across zones/FDs, then highest instance ID), NewestVM or OldestVM; **instance protection** shields specific instances from scale-in.

```text
az vmss create --resource-group RG1 --name WebVMSS --orchestration-mode Flexible --image MicrosoftWindowsServer:WindowsServer:2025-datacenter-azure-edition:latest \
   --instance-count 2 --vm-sku Standard_D2s_v5 --zones 1 2 3 --admin-username azadmin
az monitor autoscale create --resource-group RG1 --resource WebVMSS --resource-type Microsoft.Compute/virtualMachineScaleSets \
   --name WebAutoscale --min-count 2 --max-count 10 --count 2
az monitor autoscale rule create --resource-group RG1 --autoscale-name WebAutoscale --condition "Percentage CPU > 70 avg 10m" --scale out 2
az monitor autoscale rule create --resource-group RG1 --autoscale-name WebAutoscale --condition "Percentage CPU < 30 avg 10m" --scale in 1
```

## Availability sets and availability zones

| | Single VM | Availability set | Availability zones |
|---|---|---|---|
| Protects against | - | Rack/power/switch failure (**fault domains**) and planned maintenance (**update domains**) in one datacenter | Loss of a whole **datacenter** in the region |
| SLA | 99.9% with Premium SSD/Premium SSD v2/Ultra on all disks | **99.95%** (2+ VMs) | **99.99%** (2+ VMs in 2+ zones) |
| Limits | - | Up to **3 fault domains** (2 in some regions) and **20 update domains** (default 5) | Zones 1, 2, 3 (logical, per subscription) |
| Latency between VMs | - | Lowest | Slightly higher (separate datacenters) |

Rules that catch people out:

* A VM can be placed in an availability set **only at creation**. You can't add an existing VM to a set, move it to another set, or remove it - you must delete the VM (keeping disks) and recreate it.
* A VM can be in an availability set **or** a zone, not both. Moving a VM into a zone also means recreating it (or using the zonal move feature).
* Availability sets need **managed disks** to align disk fault domains with VM fault domains (a "managed"/Aligned set).
* Update domains are rebooted one at a time with 30 minutes to recover before the next.
* Zonal deployments need zonal or **zone-redundant** dependencies: **Standard SKU** public IPs and load balancers, and zonal or ZRS disks.
* Microsoft now recommends **VMSS Flexible** for new HA deployments - it spreads VMs across zones or fault domains and adds autoscale.

> **Exam tip:** "Two domain controllers in a region with availability zones; maximise availability" - put each DC in a **different zone**. "Region has no zones" - put them in one **availability set**.

## Lab it yourself

1. Create a Windows Server 2025 VM with a Standard SSD OS disk, attach a 128 GiB data disk with `az vm disk attach`, initialise it in the guest, then grow it to 256 GiB with `az disk update` while the VM runs and extend the volume.
2. Run `az vm list-vm-resize-options` and resize the VM; then deallocate and compare the list.
3. Create an availability set with 2 fault domains and 5 update domains, and try (and fail) to add your existing VM to it.
4. Create a Flexible scale set across zones and an autoscale rule; generate CPU load in an instance and watch the instance count.

## Key takeaways

* OS disk C:, temporary disk D: (non-persistent), data disks persistent; host caching None for AD DS and write-heavy logs, ReadOnly for read-heavy data.
* Ultra Disk and Premium SSD v2 can't be OS disks and have no host caching; Premium SSD needs a premium-capable ("s") size.
* Data disks usually expand online (except crossing 4 TiB on Standard/Premium SSD ≤ 4 TiB); OS disks need deallocation; shrinking isn't supported; extend the volume in Windows afterwards.
* ADE retires September 15, 2028 - use encryption at host.
* Resize restarts the VM; deallocate first if the size isn't offered on the current cluster.
* Availability sets (3 FD/20 UD, 99.95%) only at VM creation; zones give 99.99%; VMSS Flexible is the recommended scaling/HA building block.
