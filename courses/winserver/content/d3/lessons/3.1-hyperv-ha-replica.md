## Two different problems

* **High availability** keeps a VM running (or restarts it quickly) when a **host** fails or needs maintenance, inside one site. Tools: failover clustering, live migration, storage migration.
* **Disaster recovery** keeps a **copy** of the VM at another host or site so you can bring it up if the primary site is lost. Tool here: **Hyper-V Replica**. (Azure Site Recovery is the cloud DR service and is outside AZ-802's scope.)

## High availability for Hyper-V VMs

### Failover clustering

A Hyper-V failover cluster runs VMs as **clustered roles** whose files sit on shared storage - **Cluster Shared Volumes (CSV)** on SAN, iSCSI or Storage Spaces Direct, or an SMB 3 share on a Scale-Out File Server. If a node fails, the cluster **restarts** the VM on another node (unplanned failover is a restart, not a live move). For planned work, you **drain** a node and the cluster live-migrates its VMs away.

```powershell
PS C:\> Add-ClusterVirtualMachineRole -VirtualMachine VM1            # make an existing VM highly available
PS C:\> Suspend-ClusterNode -Name HV1 -Drain                          # live-migrate everything off HV1
PS C:\> Resume-ClusterNode -Name HV1 -Failback Immediate
PS C:\> Move-ClusterVirtualMachineRole -Name VM1 -Node HV2 -MigrationType Live
```

Cluster features that matter for VMs:

| Feature | What it does |
|---|---|
| **VM priority** (High/Medium/Low/No auto start) | Order in which VMs start after failover; Low can be preempted |
| **VM start order / sets** (`New-ClusterGroupSet`) | Start dependencies, e.g. SQL VMs before app VMs |
| **Preferred owners / possible owners** | Which nodes a VM should or may run on |
| **Anti-affinity** (`AntiAffinityClassNames`) | Keep two DCs or two SQL nodes on different hosts |
| **VM resiliency** | On a brief node isolation the VM keeps running as *Unmonitored* for `ResiliencyPeriod` (default 240 s) instead of failing over at once |
| **Node quarantine** | A node that flaps repeatedly is quarantined and drained |
| **VM monitoring** (`Add-ClusterVMMonitoredItem`) | Restart or fail over a VM when a monitored service in the guest fails (needs Heartbeat and guest firewall rule) |

Windows Server 2025 also supports **workgroup clusters** as a Hyper-V workload, including live migration: the nodes aren't domain members, an identical local account (same name and password) exists on every node, and the cluster authenticates migrations with self-signed PKU2U certificates instead of Kerberos. This helps at edge sites without AD. (Workgroup clusters existed since Windows Server 2016, but live migration in them is new in 2025.)

### Live migration outside a cluster

Live migration moves a running VM between hosts with only a brief pause at the final memory copy.

| Type | What moves | Requirements |
|---|---|---|
| Live migration (clustered) | Memory and state; storage stays on CSV/SMB | Cluster |
| **Shared-nothing live migration** | Memory, state **and** storage | Two standalone hosts in the same (or trusted) domain, network between them |
| Live migration with SMB storage | Memory and state; VHDX stays on an SMB 3 share | Share permissions for both hosts' computer accounts |
| **Storage migration** | VHDX/configuration only, VM keeps running on the same host | `Move-VMStorage` |

```powershell
PS C:\> Enable-VMMigration                                   # on both hosts
PS C:\> Set-VMHost -VirtualMachineMigrationAuthenticationType Kerberos -UseAnyNetworkForMigration $false
PS C:\> Add-VMMigrationNetwork 10.10.50.0/24
PS C:\> Set-VMHost -VirtualMachineMigrationPerformanceOption SMB -MaximumVirtualMachineMigrations 2
PS C:\> Move-VM -Name VM1 -DestinationHost HV2 -IncludeStorage -DestinationStoragePath D:\VMs\VM1
PS C:\> Move-VMStorage -VMName VM2 -DestinationStoragePath E:\VMs\VM2
```

**Authentication** for non-clustered live migration:

| Method | Works when | Setup |
|---|---|---|
| **CredSSP** (default up to Windows Server 2022) | You are **signed in on the source host** (console or RDP) | Nothing extra; started from Hyper-V Manager or `Move-VM -ComputerName` on a management PC it fails with "No credentials are available in the security package (0x8009030E)" |
| **Kerberos** | Started from any machine, including remotely | **Constrained delegation** on each host's computer account in AD for the **Microsoft Virtual System Migration Service** and **cifs** services to the other host |

> **Watch out:** Windows Server 2025 enables **Credential Guard by default** on domain-joined servers that aren't DCs, and Credential Guard blocks the credential delegation CredSSP needs. After an upgrade to 2025, CredSSP live migration breaks even from the source host's console - switch to **Kerberos with constrained delegation**.

**Performance options**: **TCP/IP**, **Compression** (default - uses spare CPU to compress memory) and **SMB** (uses SMB 3, can use SMB Direct/RDMA and SMB Multichannel - the fastest on RDMA networks).

**Processor compatibility**: to migrate between hosts with different CPU generations from the **same vendor**, enable processor compatibility on the VM while it is off: `Set-VMProcessor -VMName VM1 -CompatibilityForMigrationEnabled $true`. You can't live-migrate between Intel and AMD hosts at all.

> **Exam tip:** "Administrators run Move-VM from their workstations and get an authentication error, but it works when they sign in to the source host" - switch to **Kerberos** and configure **constrained delegation** (Virtual System Migration Service + cifs).

## Hyper-V Replica

Hyper-V Replica asynchronously replicates a VM's changes from a **primary** host to a **replica** host - standalone or clustered, in the same site or across a WAN - without shared storage.

### Configuring the replica server

```powershell
PS C:\> Set-VMReplicationServer -ReplicationEnabled $true -AllowedAuthenticationType Kerberos `
          -ReplicationAllowedFromAnyServer $true -DefaultStorageLocation 'D:\Replicas'
PS C:\> Enable-NetFirewallRule -DisplayName 'Hyper-V Replica HTTP Listener (TCP-In)'
```

| Authentication | Port | Encrypted in transit? | Use |
|---|---|---|---|
| **Kerberos (HTTP)** | **TCP 80** | No (Hyper-V Replica compresses but doesn't encrypt) | Same or trusted AD domains |
| **Certificate (HTTPS)** | **TCP 443** | Yes | Workgroup hosts, untrusted domains, or encryption required |

The Windows Defender Firewall rules for the listeners (HTTP or HTTPS) are **disabled by default** on the replica server - a classic reason initial replication fails. For a replica **cluster**, add the **Hyper-V Replica Broker** cluster role and configure replication settings on the broker; primaries point at the broker's client access point name.

### Enabling replication for a VM

```powershell
PS C:\> Enable-VMReplication -VMName VM1 -ReplicaServerName HV-DR1.contoso.com -ReplicaServerPort 80 `
          -AuthenticationType Kerberos -ReplicationFrequencySec 300 -RecoveryHistory 12 -VSSSnapshotFrequencyHour 4
PS C:\> Start-VMInitialReplication -VMName VM1
PS C:\> Measure-VMReplication -VMName VM1
```

| Setting | Options |
|---|---|
| **Replication frequency** | **30 seconds, 5 minutes (default), 15 minutes** |
| **Recovery points** | Latest only, or additional hourly recovery points (up to **24**) |
| **App-consistent snapshots** | VSS snapshot every 1-12 hours among the recovery points |
| **Initial replication** | Over the network (now or scheduled), **external media** (export, ship, import), or an **existing VM on the replica server** as the seed |
| **Excluded disks** | Leave out page-file or temp disks to save bandwidth |
| **Extended replication** | Replica host forwards to a third host; frequency 5 or 15 minutes only |

Monitor with `Measure-VMReplication` (State, Health, last replication time) or `Get-VMReplication`. Health *Warning* or *Critical* usually means replication missed too many cycles (network, firewall, storage space on the replica).

### Failover types

| Type | Run on | Primary VM state | Data loss | Use |
|---|---|---|---|---|
| **Test failover** | Replica | Keeps running | None | Creates a disconnected test VM (`Start-VMFailover -AsTest`), remove with `Stop-VMFailover` |
| **Planned failover** | Primary, then replica | **Must be shut down first** | **None** - pending changes are sent | Planned site moves, DR drills |
| **Unplanned failover** | Replica | Primary unavailable | Up to one replication interval | Real disaster |

Planned failover in PowerShell:

```powershell
# On the primary host
PS C:\> Stop-VM -Name VM1
PS C:\> Start-VMFailover -VMName VM1 -Prepare
# On the replica host
PS C:\> Start-VMFailover -VMName VM1
PS C:\> Set-VMReplication -VMName VM1 -Reverse
PS C:\> Start-VM -Name VM1
```

After an **unplanned** failover, choose a recovery point if needed, start the VM, and finish with `Complete-VMFailover` (which discards other recovery points) once you are satisfied. Reverse replication when the original site returns.

## Lab it yourself

1. With two standalone Windows Server 2025 lab hosts in a domain, run `Enable-VMMigration` on both, try `Move-VM -ComputerName HV1 ... -IncludeStorage` from a third machine with the authentication type left at CredSSP (it fails), then configure constrained delegation and Kerberos.
2. Enable the replica server role on the second host, enable the firewall rule, and replicate a small VM every 30 seconds. Watch `Measure-VMReplication`.
3. Run a **test failover**, boot the test VM on a private switch, then `Stop-VMFailover`.
4. Perform a **planned failover** with the PowerShell sequence above and reverse replication.

## Key takeaways

* Clustering restarts VMs on node failure and live-migrates them for planned drains; use priorities, anti-affinity and VM resiliency to control behaviour.
* Shared-nothing live migration moves VM and storage between standalone hosts; storage migration moves only files.
* CredSSP live migration must be started on the source host and doesn't work on Windows Server 2025 hosts (Credential Guard is on by default); remote initiation, and any 2025 host, needs Kerberos with constrained delegation (Virtual System Migration Service + cifs).
* Processor compatibility allows migration between CPU generations of the same vendor - never Intel to AMD.
* Hyper-V Replica: Kerberos/HTTP 80 or certificate/HTTPS 443; listener firewall rules are off by default; Replica Broker for clusters.
* Frequencies 30 s / 5 min / 15 min; up to 24 recovery points; planned failover requires the primary VM off and loses no data.
