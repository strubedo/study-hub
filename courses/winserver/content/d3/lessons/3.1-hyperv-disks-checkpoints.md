## Virtual hard disk formats

| | VHD | VHDX |
|---|---|---|
| Maximum size | **2,040 GB** | **64 TB** |
| Logical sector size | 512 bytes | 512 bytes or **4 KB** (`-LogicalSectorSizeBytes`); 4 KB physical sectors supported |
| Power-failure resilience | No | **Yes** - metadata updates are logged |
| TRIM/UNMAP | No | Yes - deleted space is returned to the host storage |
| Online resize (expand and shrink) | No | **Yes**, when attached to a SCSI controller |
| Generation 2 boot disk | No | **Yes (required)** |
| Portability | Older Hyper-V, Azure upload format | Hyper-V 2012 and later |

Use **VHDX** for everything on-premises. You meet VHD mainly when you move disks to or from Azure, because Azure managed disks are uploaded as **fixed-size VHD**.

### Disk types

| Type | Behaviour | When to use |
|---|---|---|
| **Fixed** | Allocates the full size at creation | Predictable performance; Azure uploads; workloads sensitive to fragmentation |
| **Dynamically expanding** | Grows as data is written, up to the maximum | Default; most workloads on modern storage |
| **Differencing** | Child disk that records changes against a read-only **parent** | Lab templates, pooled VDI; checkpoints use them internally |
| **Pass-through** (physical disk) | A physical disk taken **offline on the host** and given to the VM | Rare today; no checkpoints, no host-level backup of the disk |

Never modify the parent of a differencing disk - every child breaks. If a parent moves, reconnect the child with `Set-VHD -Path child.vhdx -ParentPath newparent.vhdx`.

### Shared virtual disks for guest clusters

A guest failover cluster needs shared storage between VMs. Use a **VHD Set (`.vhds`)** - the Windows Server 2016+ successor to "shared VHDX" - attached to each VM's SCSI controller. VHD Sets support **online resize** and host-based backup, which the old shared VHDX did not. (iSCSI or virtual Fibre Channel are the alternatives.)

### Managing disks with PowerShell

```powershell
PS C:\> New-VHD -Path D:\VMs\Data1.vhdx -SizeBytes 200GB -Dynamic
PS C:\> New-VHD -Path D:\VMs\Web2.vhdx -ParentPath D:\Templates\WS2025.vhdx -Differencing
PS C:\> Add-VMHardDiskDrive -VMName VM1 -ControllerType SCSI -Path D:\VMs\Data1.vhdx   # hot-add works on SCSI
PS C:\> Resize-VHD -Path D:\VMs\Data1.vhdx -SizeBytes 300GB                        # then extend the volume in the guest
PS C:\> Convert-VHD -Path D:\Old\App.vhd -DestinationPath D:\VMs\App.vhdx -VHDType Dynamic
PS C:\> Optimize-VHD -Path D:\VMs\Data1.vhdx -Mode Full                            # compact (VHD detached or read-only)
PS C:\> Get-VHD -Path D:\VMs\Data1.vhdx
PS C:\> Merge-VHD -Path D:\VMs\Web2.vhdx -DestinationPath D:\Templates\WS2025-copy.vhdx
```

Points the exam likes:

* **Resize-VHD while running** works only for **VHDX on a SCSI controller**. After growing the file, extend the partition inside the guest (`Resize-Partition`). To shrink, first shrink the partition inside the guest; `Resize-VHD -ToMinimumSize` shrinks to the smallest size the partitions allow.
* **Convert-VHD** creates a new file, so the disk must not be in use. It converts format (VHD/VHDX) and type (fixed/dynamic/differencing). There is no in-place conversion.
* **Optimize-VHD** compacts dynamic and differencing disks only; it does nothing for fixed disks. The disk must be detached or mounted read-only; for a full compaction of a VHDX, mount it read-only first (`Mount-VHD -ReadOnly`), because a detached VHDX silently gets the lighter *Prezeroed* mode.
* **Generation 1** VMs boot from **IDE**; **Generation 2** VMs boot from **SCSI** and require VHDX. You can't change a VM's generation after creation.

### Storage QoS per disk

You can cap or guarantee IOPS for a single virtual disk (normalised to 8 KB IOs):

```powershell
PS C:\> Set-VMHardDiskDrive -VMName VM1 -ControllerType SCSI -ControllerNumber 0 -ControllerLocation 1 -MinimumIOPS 200 -MaximumIOPS 1000
```

Centralised Storage QoS policies for Scale-Out File Server and Storage Spaces Direct are covered with storage in Domain 5.

## Checkpoints

A checkpoint captures a VM's state at a point in time so you can roll back. When you create one, Hyper-V stops writing to the current disk and starts a new **differencing disk (`.avhdx`)**; the original becomes read-only.

### Checkpoint types

| | Production checkpoint | Standard checkpoint |
|---|---|---|
| Mechanism | **VSS** inside Windows guests (file system freeze on Linux) - an application-consistent snapshot of the disks | Disk state **plus memory and device state** |
| Includes running memory? | No - restoring gives a VM that is **off**, as after a clean shutdown | Yes - the VM resumes exactly where it was |
| Safe for production apps (SQL, AD DS, Exchange)? | **Yes** (supported for DCs) | No - can cause inconsistency (for example USN rollback risks on DCs) |
| Needs | VSS integration service (Backup) enabled | Nothing |
| Default | **Yes** (with fallback to standard) | - |

Configure the type per VM:

```powershell
PS C:\> Set-VM -Name VM1 -CheckpointType Production       # production, fall back to standard if VSS fails (default)
PS C:\> Set-VM -Name VM1 -CheckpointType ProductionOnly   # fail instead of falling back
PS C:\> Set-VM -Name VM1 -CheckpointType Standard
PS C:\> Set-VM -Name VM1 -CheckpointType Disabled
```

> **Exam tip:** "Checkpoints of VM1 must never contain memory state; if an application-consistent checkpoint can't be taken, the checkpoint must fail" - **ProductionOnly**. Plain *Production* silently falls back to a standard checkpoint.

### Working with checkpoints

```powershell
PS C:\> Checkpoint-VM -Name VM1 -SnapshotName 'Before KB5048667'
PS C:\> Get-VMCheckpoint -VMName VM1
PS C:\> Restore-VMCheckpoint -VMName VM1 -Name 'Before KB5048667' -Confirm:$false
PS C:\> Remove-VMCheckpoint -VMName VM1 -Name 'Before KB5048667'      # merges the .avhdx back
PS C:\> Export-VMCheckpoint -VMName VM1 -Name 'Golden' -Path E:\Exports
PS C:\> Set-VM -Name VM1 -SnapshotFileLocation E:\Checkpoints
```

(`*-VMSnapshot` cmdlet names still work as aliases.)

* **Deleting** a checkpoint merges its differencing disk into the parent; that happens online. **Never delete `.avhdx` files by hand** - you lose every change made after the checkpoint and may break the chain. If files are orphaned, use `Merge-VHD` or Hyper-V Manager's Inspect/Edit Disk.
* **Automatic checkpoints** (created when you start a VM) are **disabled by default on Windows Server**: `Set-VM -AutomaticCheckpointsEnabled $false`.
* Checkpoints grow without limit and slow disk I/O as chains lengthen. They are **not backups**: they live on the same storage as the VM.
* VMs with **pass-through disks** can't have checkpoints of those disks; VMs with DDA devices don't support save/restore, so standard checkpoints (which capture saved state) aren't possible for them.
* Hyper-V Replica and backup software use their own VSS-based recovery points; don't confuse them with user checkpoints.

### Restoring a production checkpoint of a DC

Production checkpoints use VSS, and Windows Server's **VM-GenerationID** support means a DC that is restored from a checkpoint detects the rollback, discards its RID pool and resets its invocation ID, so replication stays consistent. Still, never use standard checkpoints for DCs, and never rely on checkpoints instead of system-state backups.

## Lab it yourself

1. Create a 20 GB dynamic VHDX, attach it to a running Gen 2 VM on SCSI, then `Resize-VHD` it to 30 GB while the VM runs and extend the volume in the guest with `Resize-Partition`.
2. Convert a VHD to VHDX with `Convert-VHD` and compare `Get-VHD` output (VhdFormat, LogicalSectorSize).
3. Set a VM to `ProductionOnly`, stop the **VSS** integration service with `Disable-VMIntegrationService -VMName VM1 -Name 'VSS'`, and try `Checkpoint-VM` - note the failure. Switch to `Production` and watch it fall back.
4. Create two checkpoints, look at the `.avhdx` files on disk, then delete the older checkpoint and watch the merge.

## Key takeaways

* VHDX: 64 TB, 4 KB sectors, power-failure resilient, online resize on SCSI, required for Gen 2 boot; VHD: 2,040 GB, used for Azure uploads (fixed VHD).
* Disk types: fixed, dynamically expanding, differencing (don't touch the parent) and pass-through (offline on host).
* Guest clusters use VHD Sets (`.vhds`), which support online resize and host backup.
* `Resize-VHD`, `Convert-VHD` (offline, new file), `Optimize-VHD` (dynamic/differencing only), `Merge-VHD`, `Set-VHD -ParentPath`.
* Production checkpoints use VSS and restore the VM powered off; standard checkpoints include memory; `ProductionOnly` refuses to fall back.
* Delete checkpoints with `Remove-VMCheckpoint` (merge) - never delete `.avhdx` files manually; checkpoints are not backups.
