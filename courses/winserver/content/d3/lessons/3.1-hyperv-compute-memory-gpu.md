## Compute features that change what a VM can do

This lesson covers four sub-bullets that all reshape a VM's virtual hardware: **nested virtualization**, **memory settings**, **Discrete Device Assignment (DDA)** and **GPU partitioning (GPU-P)**. Most of these settings can only be changed while the VM is **off** - remember that for "what should you do first" questions.

## Nested virtualization

Nested virtualization exposes the processor's virtualization extensions to a guest, so the guest can run Hyper-V (and Hyper-V isolated containers, Windows Sandbox, WSL2 and similar). Uses: labs, training, testing Azure Local or failover clustering on one physical box.

### Requirements

| Host CPU | Host OS | VM configuration version |
|---|---|---|
| Intel with **VT-x and EPT** | Windows Server 2016 / Windows 10 or later | **8.0** or higher |
| **AMD EPYC / Ryzen** or later | **Windows Server 2022** / Windows 11 or later | **9.3** or higher |

AMD support arrived with Windows Server 2022, so an AMD host running 2019 can't nest. On an AMD host, a VM imported from an older host at configuration version 8.0 must be upgraded (`Update-VMVersion`) first. Only Hyper-V is supported as the nested hypervisor; other hypervisors are likely to fail.

### Enabling it

```powershell
PS C:\> Stop-VM -Name LabHV1
PS C:\> Set-VMProcessor -VMName LabHV1 -ExposeVirtualizationExtensions $true
PS C:\> Get-VMNetworkAdapter -VMName LabHV1 | Set-VMNetworkAdapter -MacAddressSpoofing On
PS C:\> Start-VM -Name LabHV1
```

Then install the Hyper-V role inside the VM as usual.

* The VM must be **off** to change `ExposeVirtualizationExtensions`.
* **Networking for the nested VMs**: either turn on **MAC address spoofing** on the L1 VM's adapter (so frames from nested VMs with their own MAC addresses are forwarded), or build a NAT network inside the L1 VM. In Azure, MAC spoofing isn't possible, so NAT is the answer for nested VMs on an Azure VM.
* **Memory**: while Hyper-V is running inside the VM, its memory can't change - dynamic memory stops fluctuating and runtime memory resize fails. Give the L1 VM enough static memory.
* Give the L1 VM at least two virtual processors.
* In Azure, nested virtualization works on supported sizes (for example Dv5/Ev5 families) with **Security type: Standard** - not Trusted Launch.

## VM memory

### Static memory and runtime resize

With static memory the VM gets a fixed amount at start. Windows Server 2016 and later (and Windows 10+) guests also support **runtime memory resize**: you can raise or lower assigned memory on a running VM with static memory, within what the guest and host allow.

### Dynamic memory

Dynamic memory lets the host move memory between VMs according to demand.

| Setting | Meaning |
|---|---|
| **Startup RAM** | Memory the VM gets at boot (must be ≥ minimum) |
| **Minimum RAM** | The floor the host can reclaim down to |
| **Maximum RAM** | The ceiling (default 1 TB) |
| **Memory buffer** | Extra memory (percentage of current demand, default 20%) the host tries to keep assigned as headroom |
| **Memory weight** (priority) | Who wins when the host runs short |

```powershell
PS C:\> Set-VMMemory -VMName VM1 -DynamicMemoryEnabled $true -StartupBytes 2GB -MinimumBytes 1GB -MaximumBytes 8GB -Buffer 20 -Priority 80
PS C:\> Get-VM VM1 | Select-Object Name, DynamicMemoryEnabled, MemoryAssigned, MemoryDemand, MemoryStatus
```

Rules worth memorising:

* **Turning dynamic memory on or off requires the VM to be off.**
* While running, you can **increase the maximum** and **decrease the minimum**; you can't lower the maximum below current assignment or raise the minimum above it.
* Workloads that size their own caches at start-up (some database and Exchange roles) and VMs with **DDA** devices or running **nested Hyper-V** shouldn't (or can't) use it.
* **Smart Paging** covers only one case: a VM is *restarting*, its minimum is lower than its startup value, and the host doesn't have enough free memory to give it startup RAM. Hyper-V uses a smart paging file on disk temporarily so the VM can boot. It is not used for normal running.
* **NUMA spanning** (host setting) lets VMs use memory from other NUMA nodes; disabling it improves performance predictability but can stop VMs from starting when one node is short.

> **Exam tip:** Smart Paging helps only a running VM that **restarts**. A VM that starts from the **Off** state (for example, after the host itself rebooted), a VM that fails over in a cluster, and an oversubscribed running VM never use it. So "VM1 won't start after the host rebooted because there isn't enough memory" is fixed by lowering VM1's **startup** memory or freeing memory on the host, not by moving the smart paging file. "VM1 restarts slowly and a .slp file appears in its folder" points to Smart Paging; make sure the smart paging file location has free disk space.

## Discrete Device Assignment (DDA)

DDA passes an entire **PCIe device** - a GPU or an NVMe storage device - through to one VM. The guest uses the vendor's native driver and gets near bare-metal performance. One device, one VM.

Steps on the host (Windows Server 2016 or later):

```powershell
# 1. Prepare the VM (it must be off)
PS C:\> Set-VM -Name VM1 -AutomaticStopAction TurnOff
PS C:\> Set-VM -Name VM1 -GuestControlledCacheTypes $true -LowMemoryMappedIoSpace 3GB -HighMemoryMappedIoSpace 33280MB

# 2. Find the device's location path and disable it on the host
PS C:\> $dev = Get-PnpDevice -FriendlyName 'NVIDIA A16*' | Select-Object -First 1
PS C:\> $loc = ($dev | Get-PnpDeviceProperty DEVPKEY_Device_LocationPaths).Data[0]
PS C:\> Disable-PnpDevice -InstanceId $dev.InstanceId -Confirm:$false

# 3. Dismount from the host and assign to the VM
PS C:\> Dismount-VMHostAssignableDevice -LocationPath $loc -Force
PS C:\> Add-VMAssignableDevice -LocationPath $loc -VMName VM1
```

To return the device: `Remove-VMAssignableDevice`, then `Mount-VMHostAssignableDevice`, then re-enable it. Check hardware readiness with Microsoft's **SurveyDDA.ps1** script, and the host's BIOS needs IOMMU (Intel VT-d / AMD-Vi) and, for GPUs, often SR-IOV and "above 4G decoding" settings.

Limitations: the VM's **automatic stop action must be Turn off**; **no live migration**, save/restore or dynamic memory for that VM (and because the VM can't be saved, standard checkpoints, which capture saved state, aren't available either). Before Windows Server 2025 a VM with an assigned device also couldn't be made highly available. Windows Server 2025 **Datacenter** supports DDA GPUs in **failover clusters** through cluster **GPU pools**: after a failure or drain, the cluster *restarts* the VM on a node with a free matching GPU. Live migration of DDA VMs is still not supported.

## GPU partitioning (GPU-P)

GPU partitioning, available on **Windows Server 2025**, splits one physical GPU into **partitions** using SR-IOV, each assigned to a different VM with a hardware-enforced boundary. Where DDA gives one whole GPU to one VM, GPU-P shares a GPU among many VMs - ideal for VDI, inference and graphics workloads that don't need a whole card.

```powershell
PS C:\> Get-VMHostPartitionableGpu | Format-List Name, ValidPartitionCounts, PartitionCount
PS C:\> $gpu = Get-VMHostPartitionableGpu | Select-Object -First 1
PS C:\> Set-VMHostPartitionableGpu -Name $gpu.Name -PartitionCount 4
PS C:\> Add-VMGpuPartitionAdapter -VMName VM1
PS C:\> Get-VMGpuPartitionAdapter -VMName VM1 | Format-List InstancePath, PartitionId
```

Requirements and rules:

* **Host**: Windows Server 2025 with the Hyper-V role; the same GPU make/model on every host you will migrate between; virtualization and **SR-IOV** enabled in BIOS; GPU vendor host drivers (for NVIDIA, the vGPU software).
* **Supported GPUs** include NVIDIA A2, A10, A16, A40, L2, L4, L40, L40S and AMD Radeon PRO V710 (DDA supports a wider range).
* **Guests**: Windows 10 or later, Windows Server 2019 or later, and Ubuntu 18.04/20.04/22.04 LTS, with the vendor's guest driver. The VM needs configuration version **12.0** (the Windows Server 2025 default).
* A VM can have **one** GPU partition, and the same GPU can't be used for DDA and GPU-P at once.
* **Live migration** of VMs with GPU partitions is supported on Windows Server 2025 (it falls back to TCP/IP with compression, so it's slower and uses more CPU). It needs CPUs with IOMMU DMA bit tracking (for example AMD EPYC 7003 or 4th Gen Intel Xeon). Standalone hosts can live-migrate for planned maintenance; **failover clustering** for unplanned failover requires **Windows Server 2025 Datacenter**.
* Windows Admin Center (GPUs extension) can configure partitions as well as PowerShell.

| | DDA | GPU-P |
|---|---|---|
| Sharing | 1 device to 1 VM | 1 GPU split among several VMs |
| Device types | GPUs and NVMe | GPUs only |
| Host OS | Windows Server 2016+ | Windows Server 2025 |
| Live migration | No | Yes (2025) |
| Failover cluster | Yes (2025 Datacenter, GPU pools; restart, not live move) | Yes (2025 Datacenter) |

## Lab it yourself

1. On an Intel or AMD lab host, create a Gen 2 VM, check `Get-VM LabHV1 | Select Version`, enable `ExposeVirtualizationExtensions` while it's off, turn on MAC spoofing and install Hyper-V inside it.
2. Configure dynamic memory on another VM with `Set-VMMemory`, run a memory-hungry tool in the guest, and watch `MemoryDemand` and `MemoryAssigned` change in `Get-VM`.
3. Try to disable dynamic memory while the VM runs and read the error.
4. If your lab host has a spare NVMe or GPU, run SurveyDDA.ps1 to see whether it is assignable.

## Key takeaways

* Nested virtualization: Intel VT-x/EPT (config version 8.0+) or AMD EPYC/Ryzen on Windows Server 2022+ (config version 9.3+); `Set-VMProcessor -ExposeVirtualizationExtensions $true` with the VM off; MAC spoofing or NAT for nested VM networking.
* Dynamic memory: startup, minimum, maximum, buffer and weight; enable/disable only with the VM off; smart paging helps only during restart.
* Runtime memory resize works for static-memory VMs on Windows Server 2016+ guests.
* DDA passes a whole GPU or NVMe device to one VM: set AutomaticStopAction TurnOff, `Dismount-VMHostAssignableDevice`, `Add-VMAssignableDevice`; no live migration.
* GPU-P (Windows Server 2025) shares a GPU among VMs with `Set-VMHostPartitionableGpu` and `Add-VMGpuPartitionAdapter`; one partition per VM; supports live migration; clustering requires Datacenter.
