## Securing administrative access to Azure VMs

The default Azure VM wizard happily creates a public IP and an NSG rule allowing RDP 3389 from **Any**. That is the single most attacked configuration in Azure. AZ-802 expects you to replace it with **just-in-time (JIT) VM access**, **Azure Bastion**, or both.

| Requirement | Best fit |
|---|---|
| RDP/SSH from a browser or native client, **no public IP on the VM** | **Azure Bastion** |
| VM must keep a public IP, but management ports should be **closed except when needed** | **JIT VM access** |
| Full network access to the VNet for admins (not only RDP/SSH) | Point-to-site VPN (out of scope here) |
| No public IP anywhere, including the Bastion host | **Bastion Premium** private-only deployment |

## Just-in-time VM access

JIT is a feature of **Microsoft Defender for Cloud** and requires **Defender for Servers Plan 2** on the subscription.

How it works:

1. When you enable JIT on a VM, Defender for Cloud adds **deny** rules for the selected ports to the VM's NSG (and/or Azure Firewall rules). If rules already exist for those ports, they keep priority.
2. A user with the right Azure RBAC permissions **requests access** - in the portal (VM > **Connect** > *Request access*, or Defender for Cloud > Just-in-time VM access), with PowerShell (`Start-AzJitNetworkAccessPolicy`) or the REST API - specifying ports, source IP and duration.
3. Defender for Cloud inserts a higher-priority **allow** rule for that source IP and port.
4. When the time expires, the allow rule is removed. **Existing connections are not dropped**; new ones are blocked.

Defaults when you enable JIT from Defender for Cloud: ports **22, 3389, 5985 and 5986**, a **maximum request time of 3 hours**, source **Any** (requesters can narrow it to *My IP*). Enabling JIT from the VM's Configuration page uses just 3389 (Windows) or 22 (Linux).

Requirements and limits:

* The VM must have an **NSG** (on its NIC or subnet) or be protected by an **Azure Firewall** in the same VNet. JIT doesn't support Azure Firewalls managed by **Azure Firewall Manager** (Firewall Policy) - only classic rules.
* Resource Manager VMs only (not classic).
* Users need **Reader and Security Reader** to view JIT settings, plus specific `Microsoft.Security/locations/jitNetworkAccessPolicies/initiate/action` and related permissions to request access (Microsoft provides a script to create a least-privilege custom role).
* Every request is logged in the Activity log and in Defender for Cloud.

```powershell
PS C:\> $JitPolicy = @{ id = $vm.Id; ports = @(@{ number = 3389; protocol = '*'; allowedSourceAddressPrefix = @('*'); maxRequestAccessDuration = 'PT3H' }) }
PS C:\> Set-AzJitNetworkAccessPolicy -Kind Basic -Location eastus -Name default -ResourceGroupName RG1 -VirtualMachine @($JitPolicy)
```

> **Exam tip:** JIT reduces exposure but the VM still has a reachable public IP. If the requirement is "the VM must not have a public IP", JIT can't be the answer - use Bastion.

## Azure Bastion

Azure Bastion is a managed PaaS jump host deployed into your virtual network. Users connect to Bastion over **TLS on port 443** (from the Azure portal or a native client); Bastion connects to the VMs' **private IPs** over RDP 3389 or SSH 22. The target VMs need **no public IP** and no agent.

### SKUs

| Feature | Developer | Basic | Standard | Premium |
|---|---|---|---|---|
| Deployment | Shared infrastructure, **no AzureBastionSubnet** | Dedicated | Dedicated | Dedicated |
| Cost | Free | Paid | Paid | Paid |
| Concurrent connections / VMs | **One VM at a time** | Yes (2 fixed instances) | Yes, **host scaling 2-50 instances** | Same as Standard |
| VNet peering (hub-spoke) | No | Yes | Yes | Yes |
| RDP to Windows / SSH to Linux | Yes | Yes | Yes | Yes |
| RDP to Linux / SSH to Windows | No | No | Yes | Yes |
| **Native client** (`az network bastion rdp/ssh`) | No | No | **Yes** | Yes |
| Upload/download files (native client) | No | No | Yes | Yes |
| **Shareable links** | No | No | Yes | Yes |
| **IP-based connection** (on-premises or peered IPs) | No | No | Yes | Yes |
| Custom inbound port | No | No | Yes | Yes |
| **Session recording** | No | No | No | **Yes** |
| **Private-only** deployment (no public IP on Bastion) | No | No | No | **Yes** |
| Kerberos authentication | Yes | Yes | Yes | Yes |

### Deployment requirements

* A subnet named exactly **`AzureBastionSubnet`**, **/26 or larger** (Basic, Standard and Premium).
* A **Standard SKU public IP** (except Premium private-only and Developer).
* If you put an NSG on AzureBastionSubnet, it must allow, among others: inbound **443 from Internet** (users) and from **GatewayManager**, inbound 443 from **AzureLoadBalancer**, outbound **3389/22 to VirtualNetwork** (targets) and outbound 443 to **AzureCloud**. NSGs on the *target VM subnets* must allow 3389/22 **from the AzureBastionSubnet**.
* One Bastion in a **hub VNet** can reach VMs in **peered** spoke VNets (not the Developer SKU).

### Native client

With Standard or Premium and **Native client support** enabled on the Bastion resource:

```text
az network bastion rdp --name Bastion1 --resource-group RG-Hub --target-resource-id /subscriptions/<sub>/resourceGroups/RG1/providers/Microsoft.Compute/virtualMachines/VM1
az network bastion ssh --name Bastion1 --resource-group RG-Hub --target-resource-id <vm-id> --auth-type AAD
az network bastion tunnel --name Bastion1 --resource-group RG-Hub --target-resource-id <vm-id> --resource-port 3389 --port 55000
```

`az network bastion rdp` launches mstsc on Windows clients. Users need **Reader** on the VM, its NIC and the Bastion resource (plus the VM login roles if using Microsoft Entra sign-in).

## Azure VM network configuration

### NICs and IP addresses

* Every VM has at least one **network interface (NIC)**, the **primary NIC**. Each NIC has one or more **IP configurations**; each IP configuration has a private IP and optionally a public IP.
* **Private IPs** are **Dynamic** (Azure picks the next free address in the subnet; it survives restarts and deallocation and is released only when the NIC is deleted or moved to another subnet) or **Static** (you choose the exact address, released only when the NIC is deleted). Use Static whenever a specific address is required. The first four addresses and the last address of each subnet are reserved by Azure.
* **Set static IPs in Azure, never inside the guest.** Leave the Windows NIC on DHCP; Azure's DHCP always hands out the address you reserved. Hard-coding an IP in Windows that doesn't match the Azure configuration cuts the VM off. Domain controllers and DNS servers should get **static** private IPs this way.
* **Public IPs** use the **Standard SKU** (Basic public IPs were retired on September 30, 2025). Standard public IPs are static, **secure by default** (closed until an NSG allows traffic) and can be zonal or zone-redundant.

```text
az network nic ip-config update --resource-group RG1 --nic-name vm1-nic --name ipconfig1 --private-ip-address 10.1.0.10
az network public-ip create --resource-group RG1 --name VM1-pip --sku Standard --zone 1 2 3
az network nic ip-config update --resource-group RG1 --nic-name vm1-nic --name ipconfig1 --public-ip-address VM1-pip
```

### Multiple NICs

* The number of NICs is limited by the VM size.
* **Adding or removing NICs requires the VM to be stopped (deallocated)**; you can add IP configurations to an existing NIC while running.
* All NICs of a VM must be in the **same VNet** (they can be in different subnets).
* Only the **primary NIC** gets a default gateway from Azure DHCP; configure routes in Windows for traffic that must leave through a secondary NIC.

### DNS

DNS servers are set on the **VNet** (applies to all NICs) or overridden per **NIC**. A VM picks up changes after a DHCP renewal or restart. Pointing a VNet at your AD DS DCs (and keeping 168.63.129.16, Azure DNS, as their forwarder or via conditional forwarders) is the usual hybrid design - covered in Domain 4.

### Network security groups

* An NSG can be associated with a **subnet**, a **NIC**, or both. **Inbound** traffic is evaluated by the **subnet NSG first, then the NIC NSG**; **outbound** by the NIC NSG first, then the subnet NSG. Traffic must be allowed by **both** when both exist.
* Rules are processed by **priority** (100-4096, lower first); the first match wins. Default rules (65000+) allow VNet-to-VNet and Azure Load Balancer traffic and deny everything else inbound.
* **Application security groups (ASGs)** let you write rules such as "WebServers -> SqlServers TCP 1433" without IP addresses.
* Troubleshoot with **Effective security rules** on the NIC (`az network nic list-effective-nsg`) and Network Watcher **IP flow verify**.

### Performance and routing

* **Accelerated networking** (SR-IOV to the VM) lowers latency and CPU use; it needs a supported size and OS and is set per NIC (`az network nic update --accelerated-networking true`, with the VM deallocated).
* **IP forwarding** on a NIC (`--ip-forwarding true`) lets a VM act as a router or network virtual appliance; route tables (UDRs) then point traffic at it.
* **Effective routes** (`az network nic show-effective-route-table`) show what a NIC actually uses.

## Lab it yourself

1. Create VM1 with no public IP. Deploy Bastion **Basic** in the same VNet (create `AzureBastionSubnet` /26) and connect from the portal.
2. Upgrade Bastion to **Standard**, enable native client support, and connect with `az network bastion rdp`.
3. On another VM that has a public IP, enable Defender for Servers Plan 2 (trial), enable JIT, request access for *My IP* for 1 hour, and inspect the NSG rules before and after.
4. Change VM1's private IP to static in the NIC's IP configuration and confirm Windows still shows DHCP-assigned with the same address.

## Key takeaways

* JIT needs Defender for Servers Plan 2 and an NSG or classic-rule Azure Firewall; defaults 22/3389/5985/5986, 3-hour max; existing sessions survive expiry.
* Bastion: users connect on 443, Bastion reaches private IPs; AzureBastionSubnet /26+; Standard public IP.
* Bastion SKUs: Developer (free, one VM, no peering), Basic, Standard (native client, shareable links, IP-based connect, scaling), Premium (session recording, private-only).
* Set static private IPs in Azure, not inside Windows; public IPs are Standard SKU.
* Adding/removing NICs needs a deallocated VM; all NICs in one VNet; only the primary NIC gets a default gateway.
* NSGs on subnet and NIC are both evaluated (inbound: subnet then NIC); use effective security rules and IP flow verify to troubleshoot.
