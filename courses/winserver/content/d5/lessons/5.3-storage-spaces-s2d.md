## Storage Spaces on a single server

Storage Spaces pools physical disks and carves **virtual disks** (storage spaces) out of the pool, each with its own resiliency and provisioning type. It works with SATA, SAS and NVMe disks attached directly or through an HBA in pass-through mode; it does not support hardware RAID volumes underneath it, and it is not supported on iSCSI or Fibre Channel LUNs.

### Resiliency on a standalone server

| Resiliency | Copies / parity | Minimum disks | Tolerates | Use for |
|---|---|---|---|---|
| **Simple** | Striping, no redundancy | 1 | Nothing | Scratch, easily recreated data |
| **Two-way mirror** | 2 copies | 2 | 1 disk failure | Most workloads |
| **Three-way mirror** | 3 copies | **5** | 2 simultaneous disk failures | Critical, performance-sensitive data |
| **Parity** (single) | Data + parity | 3 | 1 disk failure | Sequential, archival, backup |
| **Dual parity** | Data + 2 parity | 7 | 2 disk failures | Large archival sets |

Mirrors are fast and capacity-hungry (50% efficiency two-way, 33% three-way). Parity is capacity-efficient but slow on random writes. Mirror spaces use dirty region tracking; parity spaces use a journal (ideally on SSD).

**Provisioning**: *fixed* allocates all capacity at creation; *thin* allocates as data is written and lets you over-commit the pool (monitor pool free space, because a full pool takes thin disks offline).

**Tiering**: on a standalone pool with SSD and HDD you can create a tiered virtual disk (SSD tier + HDD tier) and a scheduled optimization task moves hot data to SSD.

```powershell
PS C:\> $disks = Get-PhysicalDisk -CanPool $true
PS C:\> New-StoragePool -FriendlyName Pool1 -StorageSubSystemFriendlyName "Windows Storage*" -PhysicalDisks $disks
PS C:\> New-VirtualDisk -StoragePoolFriendlyName Pool1 -FriendlyName Data1 -ResiliencySettingName Mirror -NumberOfDataCopies 2 -ProvisioningType Thin -Size 2TB
PS C:\> Get-VirtualDisk -FriendlyName Data1 | Get-Disk | Initialize-Disk -PartitionStyle GPT -PassThru | New-Partition -UseMaximumSize -AssignDriveLetter | Format-Volume -FileSystem ReFS
```

`New-Volume` does the virtual disk, partition and format in one step.

### Replacing a failed disk

`Get-PhysicalDisk` shows a failed disk as `HealthStatus Unhealthy` or `Warning` with `OperationalStatus Lost Communication` or `Predictive Failure`; dependent virtual disks show `Degraded` / `Incomplete`.

```powershell
PS C:\> Add-PhysicalDisk -StoragePoolFriendlyName Pool1 -PhysicalDisks (Get-PhysicalDisk -CanPool $true)
PS C:\> Set-PhysicalDisk -FriendlyName PhysicalDisk4 -Usage Retired
PS C:\> Get-VirtualDisk | Where-Object HealthStatus -ne Healthy | Repair-VirtualDisk
PS C:\> Get-StorageJob
PS C:\> Remove-PhysicalDisk -StoragePoolFriendlyName Pool1 -PhysicalDisks (Get-PhysicalDisk -FriendlyName PhysicalDisk4)
```

(The `PhysicalDiskN` names assume you renamed the disks with `Set-PhysicalDisk -NewFriendlyName`; by default `FriendlyName` is the model string, so in practice you often select disks by `SerialNumber` or `UniqueId`.) Retiring stops new allocations on the disk; the repair rebuilds the missing copies on other disks; only then do you remove it from the pool. A **hot spare** (`-Usage HotSpare`) can be kept in the pool for automatic rebuilds.

## Storage Spaces Direct (S2D)

S2D builds the pool from the **local drives of 2 to 16 clustered servers** and mirrors or erasure-codes data **across servers** over SMB 3. Volumes are Cluster Shared Volumes (CSVFS), so every node sees them. Use it **hyperconverged** (Hyper-V VMs on the same cluster) or **converged/disaggregated** (a Scale-Out File Server in front of the S2D cluster serving Hyper-V hosts over SMB).

### Requirements

* **Windows Server Datacenter edition** on every node (S2D is not in Standard).
* Hardware certified for Windows Server (look for the SDDC AQs); the whole cluster must pass `Test-Cluster` including the **Storage Spaces Direct** tests.
* Drives **direct-attached to one server each**: SATA, SAS or NVMe, through an HBA in pass-through/simple mode. **Not supported**: RAID controller volumes, SAN (FC, iSCSI, FCoE) LUNs, shared SAS enclosures, MPIO.
* The same number and type of drives in every server; at least 4 capacity drives per server (plus at least 2 cache drives if you mix media). Cache devices must be at least 32 GB, and SSDs must have power-loss protection.
* Networking: 10 GbE or faster, **RDMA (iWARP or RoCE) strongly recommended**; 25 GbE+ for larger clusters.
* Memory: 4 GB of RAM per TB of cache capacity per server for metadata, on top of the workload.
* Two-node clusters need a witness: **cloud witness** (Azure storage account) or file share witness.

### The cache

When a server has more than one drive type, S2D automatically **binds the fastest type as cache** (NVMe over SSD over HDD) and the rest as capacity. With SSD/NVMe cache in front of HDD, the cache does reads and writes; in front of SSD it caches writes only. All-flash with a single drive type has no cache. You can see cache devices in `Get-PhysicalDisk` as `Usage = Journal`.

### Resiliency across servers

| Resiliency | Minimum fault domains (servers) | Tolerates | Efficiency |
|---|---|---|---|
| Two-way mirror | 2 | 1 failure | 50% |
| Three-way mirror | 3 | 2 failures | 33% |
| Dual parity | 4 | 2 failures | 50% (4 nodes) up to 80% (16 nodes) |
| Mirror-accelerated parity | 4 | 2 failures | Between mirror and parity |
| Nested two-way mirror / nested mirror-accelerated parity | 2 (exactly) | A server **and** a drive at the same time | 25% / about 35-40% |

Microsoft's guidance: use **three-way mirror** for performance-sensitive VMs and databases, **dual parity** or **mirror-accelerated parity** for archive and backup data, avoid single parity, and use **nested resiliency** on two-node clusters that must survive a node down for patching plus a drive failure.

### Deploying

```powershell
PS C:\> Test-Cluster -Node HV1, HV2, HV3, HV4 -Include "Storage Spaces Direct", Inventory, Network, "System Configuration"
PS C:\> New-Cluster -Name S2DCL1 -Node HV1, HV2, HV3, HV4 -NoStorage -StaticAddress 10.0.10.50
PS C:\> Enable-ClusterStorageSpacesDirect -CimSession S2DCL1
PS C:\> New-Volume -CimSession S2DCL1 -StoragePoolFriendlyName S2D* -FriendlyName VMs01 -FileSystem CSVFS_ReFS -ResiliencySettingName Mirror -Size 4TB
```

`-NoStorage` keeps the cluster from grabbing disks before S2D claims them. `Enable-ClusterS2D` is an alias. Drives must be empty (no partitions) to be claimed. Use `Get-StorageJob` to watch resyncs after a node reboot, and put a node into maintenance (`Suspend-ClusterNode -Drain`) before patching so the storage pauses cleanly.

## SMB Direct (SMB over RDMA)

SMB Direct lets SMB 3 move data with **Remote Direct Memory Access**: the NIC writes straight into the remote server's memory, bypassing most of the TCP/IP stack. Result: very high throughput, low latency and very low CPU use. It is used automatically, with no configuration in SMB itself, when both ends have RDMA-capable NICs (through **SMB Multichannel**).

| RDMA type | Transport | Switch requirements |
|---|---|---|
| **iWARP** | RDMA over TCP/IP | None special; works over standard Ethernet and routes |
| **RoCE / RoCEv2** | RDMA over Converged Ethernet (RoCE v1 is a layer 2 Ethertype; RoCEv2 is routable over UDP/IP, port 4791) | Needs a lossless fabric: **DCB with Priority Flow Control (PFC)** and usually ETS configured identically on hosts and switches |
| **InfiniBand** | Native IB fabric | IB switches |

```powershell
PS C:\> Get-NetAdapterRdma
PS C:\> Enable-NetAdapterRdma -Name "SMB1","SMB2"
PS C:\> Get-SmbClientNetworkInterface
PS C:\> Get-SmbMultichannelConnection
```

`Get-SmbMultichannelConnection` shows `Client RDMA Capable` and `Server RDMA Capable` per path; the *SMB Direct Connection* performance counters confirm actual RDMA traffic. For RoCE, the host side looks like this:

```powershell
PS C:\> Install-WindowsFeature Data-Center-Bridging
PS C:\> New-NetQosPolicy "SMB" -NetDirectPortMatchCondition 445 -PriorityValue8021Action 3
PS C:\> Enable-NetQosFlowControl -Priority 3
PS C:\> Disable-NetQosFlowControl -Priority 0,1,2,4,5,6,7
PS C:\> Enable-NetAdapterQos -Name "SMB1","SMB2"
PS C:\> New-NetQosTrafficClass "SMB" -Priority 3 -BandwidthPercentage 50 -Algorithm ETS
```

Watch-outs: RDMA is **not** supported on an LBFO NIC team; use **Switch Embedded Teaming (SET)** with RDMA-capable vNICs (`Enable-NetAdapterRdma "vEthernet (SMB1)"`). SMB Direct uses TCP 5445 for iWARP, so allow it alongside 445 in host firewalls. Windows Server 2022 and later can encrypt SMB Direct traffic with much less performance penalty than before.

## Storage QoS

Storage Quality of Service centrally manages IOPS for Hyper-V virtual disks stored on a **Scale-Out File Server** or on **Cluster Shared Volumes** (including S2D). Policies live on the storage cluster; Hyper-V hosts tag each VHDX with a policy ID. IOPS are **normalized to 8 KB** (a 32 KB I/O counts as 4).

| Policy type | Old name | Limits apply to |
|---|---|---|
| **Dedicated** | Multi-instance | **Each** virtual disk separately: every VHDX gets its own minimum and maximum |
| **Aggregated** | Single-instance | The **combined** set of virtual disks: they share one minimum and one maximum |

Example: a policy with MinimumIops 300 and MaximumIops 500 applied to five VHDX files. As **Dedicated**, each disk is guaranteed 300 and capped at 500. As **Aggregated**, the five together are guaranteed 300 and capped at 500 (roughly 100 each under equal load). The policy type cannot be changed after creation.

```powershell
# On the storage cluster (SOFS or the S2D/CSV cluster)
PS C:\> $p = New-StorageQosPolicy -Name Gold -PolicyType Dedicated -MinimumIops 500 -MaximumIops 2000 -MaximumIOBandwidth 200MB
# On the Hyper-V host
PS C:\> Get-VM -Name SQL* | Get-VMHardDiskDrive | Set-VMHardDiskDrive -QoSPolicyID $p.PolicyId
# Monitor
PS C:\> Get-StorageQosFlow | Sort-Object InitiatorIOPS -Descending | Select-Object -First 5
PS C:\> Get-StorageQosPolicy
```

Status **InsufficientThroughput** means a flow is asking for at least its minimum but not getting it (the storage is over-committed). **UnknownPolicyId** means the policy was deleted while VMs still reference it; recreate it with `New-StorageQosPolicy -PolicyId <same GUID>` or clear it from the disks. Keep Aggregated policies to about 20 disks or fewer.

> **Exam tip:** "Each VDI VM gets the same guaranteed floor and ceiling" = one **Dedicated** policy. "All VMs of tenant A together may not exceed 5,000 IOPS" = one **Aggregated** policy.

> **Watch out:** `Set-VMHardDiskDrive -MinimumIOPS/-MaximumIOPS` is the older per-host Hyper-V QoS. It is not Storage QoS and has no central policy or cluster-wide view.

## Lab it yourself

Storage Spaces is easy to lab: give a Windows Server 2025 VM six 10 GB virtual disks, then:

```powershell
PS C:\> New-StoragePool -FriendlyName Pool1 -StorageSubSystemFriendlyName "Windows Storage*" -PhysicalDisks (Get-PhysicalDisk -CanPool $true)
PS C:\> New-Volume -StoragePoolFriendlyName Pool1 -FriendlyName Mirror3 -ResiliencySettingName Mirror -NumberOfDataCopies 3 -FileSystem ReFS -Size 8GB -DriveLetter M
PS C:\> Get-VirtualDisk | Format-Table FriendlyName, ResiliencySettingName, NumberOfDataCopies, HealthStatus
```

Remove one virtual disk from the VM while it runs, observe `Degraded`, add a new disk and follow the replacement steps. For S2D, two or more Datacenter evaluation VMs (with nested virtualization if you want Hyper-V inside), each with several empty data VHDX files, will let you run `Enable-ClusterStorageSpacesDirect`; virtual drives report a single media type, so expect no cache tier.

## Key takeaways

* Standalone Storage Spaces: simple (1 disk), two-way mirror (2), three-way mirror (5), parity (3), dual parity (7); thin provisioning needs pool monitoring.
* Replace a failed pool disk: add the new disk, retire the failed one, `Repair-VirtualDisk`, then `Remove-PhysicalDisk`.
* S2D: 2-16 Datacenter nodes, direct-attached drives through pass-through HBAs, no RAID/SAN/shared SAS, fastest drive type becomes cache automatically.
* S2D resiliency: two-way mirror (2 nodes), three-way mirror (3), dual parity and mirror-accelerated parity (4), nested resiliency for two-node clusters.
* SMB Direct is automatic with RDMA NICs; iWARP needs nothing special, RoCE needs DCB/PFC end to end; no RDMA on LBFO teams, use SET.
* Storage QoS: Dedicated = per-disk limits, Aggregated = shared limits; policies on the storage cluster, applied with `Set-VMHardDiskDrive -QoSPolicyID`.
