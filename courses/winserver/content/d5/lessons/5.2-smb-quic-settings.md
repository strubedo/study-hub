## SMB versions in one table

| Dialect | First shipped | Notable for |
|---|---|---|
| SMB 1 | Windows NT era | Insecure and chatty; **not installed by default** since Windows Server 2019 / version 1709 |
| SMB 2.0.2 / 2.1 | Server 2008 / 2008 R2 | Larger reads/writes, leasing |
| SMB 3.0 / 3.0.2 | Server 2012 / 2012 R2 | Encryption (AES-128-CCM), Multichannel, SMB Direct, transparent failover |
| SMB 3.1.1 | Server 2016 | Pre-authentication integrity, AES-128-GCM, later AES-256, compression (2022), QUIC (2022 Azure Edition, 2025) |

`Get-SmbConnection` on the client shows the negotiated `Dialect` for each connection; `Get-SmbSession` on the server shows who is connected.

## SMB over QUIC

SMB over QUIC replaces TCP 445 with **QUIC over UDP 443**. Every packet is inside a **TLS 1.3** tunnel that the **server certificate** authenticates, so the SMB session, including the NTLM or Kerberos exchange, is never exposed on the wire. Think of it as an "SMB VPN" for laptops on the internet. SMB features such as signing, Multichannel and compression still work inside the tunnel.

### Requirements

| Item | Requirement |
|---|---|
| Server OS | **Windows Server 2025, any edition** (Standard or Datacenter). On Windows Server 2022 it was **Datacenter: Azure Edition only** |
| Client | Windows 11 (QUIC client); client access control needs Windows 11 24H2 or later |
| Certificate | Issued by a CA the client trusts; EKU **Server Authentication**; key usage digital signature; SHA-256 or better; RSA 2048+ or ECDSA P-256+; a **SAN DNS entry for every name clients use**; private key present; in the computer's Personal store |
| Network | Allow **UDP 443 inbound** to the server. Do not open TCP 445 to the internet |
| Identity | Domain-joined (recommended) or local accounts; the server needs a DC for authentication, but DCs never need internet exposure |

It is **opt-in**: the server administrator must enable it, and Windows clients still try TCP first unless you force QUIC.

### Configuring it

On Windows Server 2025 use PowerShell (Windows Admin Center's QUIC configuration page targets 2022 Azure Edition):

```powershell
PS C:\> $cert = Get-ChildItem Cert:\LocalMachine\My | Where-Object { $_.Subject -match "fsedge1.contoso.com" }
PS C:\> New-SmbServerCertificateMapping -Name fsedge1.contoso.com -Thumbprint $cert.Thumbprint -StoreName My
PS C:\> Get-SmbServerCertificateMapping
```

Map every external name (each SAN) that clients will use. Do **not** use IP addresses as names: an IP forces NTLM, and through NAT (for example an Azure VM's public IP) it does not work at all.

Clients connect normally, or force QUIC:

```text
C:\> NET USE Z: \\fsedge1.contoso.com\sales /TRANSPORT:QUIC
```

```powershell
PS C:\> New-SmbMapping -LocalPath Z: -RemotePath \\fsedge1.contoso.com\sales -TransportType QUIC
```

**KDC Proxy** (`kpssvc`) on the file server lets internet clients obtain Kerberos tickets over HTTPS instead of falling back to NTLMv2; you point clients at it with the Group Policy *Specify KDC proxy servers for Kerberos clients*.

When the certificate is renewed it gets a **new thumbprint**, so you must update the mapping (`Set-SmbServerCertificateMapping`) or QUIC stops working. Auto-enrolment does not fix this for you.

### Client access control (Windows Server 2025)

By default any client that trusts the server certificate chain may open a QUIC connection (it still has to authenticate to SMB). **Client access control** requires the client to present its **own certificate** (EKU Client Authentication) and checks it against an allow/deny list on the server before SMB even starts.

```powershell
# On the client: map its client-auth certificate for that server name
PS C:\> New-SmbClientCertificateMapping -Namespace fsedge1.contoso.com -Thumbprint $clientCert.Thumbprint -StoreName My

# On the server: turn on client certificate validation and access checks for the mapping
PS C:\> Set-SmbServerCertificateMapping -Name fsedge1.contoso.com -RequireClientAuthentication $true

# Then allow a single client cert (SHA256 hash) or a whole issuing CA
PS C:\> Grant-SmbClientAccessToServer -Name fsedge1.contoso.com -IdentifierType SHA256 -Identifier <sha256-hash>
PS C:\> Grant-SmbClientAccessToServer -Name fsedge1.contoso.com -IdentifierType ISSUER -Identifier "CN=Contoso Issuing CA, DC=contoso, DC=com"
PS C:\> Block-SmbClientAccessToServer -Name fsedge1.contoso.com -IdentifierType SHA256 -Identifier <sha256-hash-of-lost-laptop>
PS C:\> Get-SmbClientAccessToServer -Name fsedge1.contoso.com
```

Nothing is enforced until the server mapping has `-RequireClientAuthentication $true`; if you also set `-SkipClientCertificateAccessCheck $true`, the server validates the client certificate chain but skips the allow/block lists. Deny entries win: if any certificate in the chain is blocked the client is refused, and at least one must be allowed. Note the two hash formats: `New-SmbClientCertificateMapping` takes the normal (SHA-1) **thumbprint**, while the server access list uses the **SHA-256** hash (`$clientCert.GetCertHashString("SHA256")`).

Other controls: `Set-SmbServerConfiguration -EnableSMBQUIC $false` disables QUIC on a server; `Set-SmbClientConfiguration -EnableSMBQUIC $false` disables the client, optionally with `-DisabledSMBQUICServerExceptionList` for approved servers. Windows Server 2025 also supports **alternative ports** if UDP 443 is unavailable.

> **Exam tip:** "Remote users must reach file shares without a VPN and the firewall team will only open UDP 443" = SMB over QUIC. If the server is Windows Server 2022 Standard or Datacenter (not Azure Edition), the answer includes upgrading to Windows Server 2025 or moving to Azure Edition.

## SMB security settings

### Signing

Signing adds an integrity hash to every message, defeating tampering and NTLM relay. On Windows Server 2025 the **SMB client requires signing on all outbound connections by default** (previously it was only required for `SYSVOL` and `NETLOGON` on DCs). Windows 11 24H2 Enterprise/Pro/Education require it inbound and outbound. Domain controllers have long required inbound signing.

Consequences you must recognise:

* Third-party NAS devices that do not sign fail with errors like *STATUS_INVALID_SIGNATURE* / "The cryptographic signature is invalid".
* **Guest access stops working**, because guest sessions cannot be signed. Users see "You can't access this shared folder because your organization's security policies block unauthenticated guest access."

The right fix is to make the device support signing with a real account. Disabling the requirement (`Set-SmbClientConfiguration -RequireSecuritySignature $false`, or the policy *Microsoft network client: Digitally sign communications (always)*) works but is a security regression.

```powershell
PS C:\> Get-SmbClientConfiguration | Select-Object RequireSecuritySignature, EnableInsecureGuestLogons, RequireEncryption
PS C:\> Get-SmbServerConfiguration | Select-Object RequireSecuritySignature, EncryptData, RejectUnencryptedAccess, EnableSMB1Protocol
```

### Encryption

SMB 3 encryption (AES-128/256 GCM or CCM) protects confidentiality and also provides integrity, so an encrypted session does not need separate signing. Enable it **per share** (`Set-SmbShare -Name Finance -EncryptData $true`) or **server-wide** (`Set-SmbServerConfiguration -EncryptData $true`).

`RejectUnencryptedAccess` (default **True**) decides what happens to clients that cannot encrypt (SMB 2.x clients): with True they are refused; with False they are allowed in unencrypted. Encryption is **not** required by default on Windows Server 2025, but the 2025 client can now **mandate** it for every outbound connection (`Set-SmbClientConfiguration -RequireEncryption $true`, or the Lanman Workstation policy *Require encryption*), refusing servers that cannot encrypt.

### Other Windows Server 2025 hardening

| Feature | What it does | Default |
|---|---|---|
| SMB NTLM blocking (client) | `Set-SmbClientConfiguration -BlockNTLM $true` stops the client sending NTLM to remote servers, with an exception list | Off |
| Authentication rate limiter (server) | Inserts a delay after each failed NTLM/PKU2U logon to slow brute force | On |
| Dialect control | `Set-SmbServerConfiguration -Smb2DialectMin SMB311` (client equivalent on `Set-SmbClientConfiguration`) | Not set |
| Firewall hardening | New shares enable the **File and Printer Sharing (Restrictive)** rule group, which does not open NetBIOS ports 137-139 | On |
| Remote Mailslot | Disabled for SMB and DC locator | Disabled |
| Signing/encryption auditing | Logs clients or servers that do not support signing/encryption | Off until enabled |

### Removing SMB 1

SMB 1 is not installed on Windows Server 2019 and later unless someone added it. Before removing it from older or upgraded servers, find out who still uses it:

```powershell
PS C:\> Set-SmbServerConfiguration -AuditSmb1Access $true
PS C:\> Get-WinEvent -LogName Microsoft-Windows-SMBServer/Audit -MaxEvents 20
PS C:\> Set-SmbServerConfiguration -EnableSMB1Protocol $false
PS C:\> Uninstall-WindowsFeature FS-SMB1
```

> **Watch out:** Never try to fix an old-device problem by re-enabling SMB 1 on a server. It was the transport for WannaCry-class worms. Replace or upgrade the device.

### Day-to-day SMB management

* `Get-SmbShare`, `Set-SmbShare`, `Get-SmbShareAccess`, `Grant-/Revoke-/Block-SmbShareAccess` for shares.
* `Get-SmbOpenFile | Where-Object Path -like "*budget.xlsx" | Close-SmbOpenFile -Force` to clear a stale lock.
* `Get-SmbMultichannelConnection` to confirm Multichannel (and RDMA) use.
* SMB bandwidth limits: `Set-SmbBandwidthLimit -Category LiveMigration -BytesPerSecond 500MB` (needs the `FS-SMBBW` feature) to stop live migration starving other SMB traffic.
* Group Policy paths: *Computer Configuration\Administrative Templates\Network\Lanman Server* (server) and *Lanman Workstation* (client) hold QUIC, dialect, encryption and NTLM-blocking policies; signing lives under *Security Settings\Local Policies\Security Options*.

## Lab it yourself

Two Windows Server 2025 VMs are enough to see the defaults:

```powershell
PS C:\> Get-SmbClientConfiguration | Select-Object RequireSecuritySignature
PS C:\> New-Item -Path C:\Secret -ItemType Directory
PS C:\> New-SmbShare -Name Secret -Path C:\Secret -FullAccess Everyone -EncryptData $true
PS C:\> Get-SmbConnection   # on the client after opening \\SRV1\Secret: check Dialect
PS C:\> Set-SmbServerConfiguration -Smb2DialectMin SMB311 -Force
```

For SMB over QUIC, issue a certificate from a lab AD CS (or a self-signed certificate whose root you import into the client's Trusted Root store), map it with `New-SmbServerCertificateMapping`, allow UDP 443, and connect from a Windows 11 VM with `NET USE * \\name\share /TRANSPORT:QUIC`.

## Key takeaways

* SMB over QUIC = SMB inside TLS 1.3 over UDP 443, authenticated by a server certificate with SAN entries for each client-facing name; any edition of Windows Server 2025, Azure Edition only on 2022.
* Configure QUIC on 2025 with `New-SmbServerCertificateMapping`; re-map after certificate renewal because the thumbprint changes.
* Client access control adds client certificates and allow/block lists (`Set-SmbServerCertificateMapping -RequireClientAuthentication $true`, then `Grant-SmbClientAccessToServer` / `Block-SmbClientAccessToServer`).
* Windows Server 2025 requires outbound SMB signing by default, which breaks unsigned NAS devices and guest access.
* Encryption is per share or per server; `RejectUnencryptedAccess` controls whether non-encrypting clients are refused; 2025 clients can mandate encryption.
* Audit SMB 1 use with `AuditSmb1Access`, then disable and uninstall it; never re-enable it as a workaround.
