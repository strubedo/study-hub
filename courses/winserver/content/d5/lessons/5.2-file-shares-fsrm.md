## Two permission layers

Every SMB share on Windows Server is protected twice:

| Layer | Where it lives | Applies to | Granularity |
|---|---|---|---|
| **Share permissions** | The share definition (registry, `LanmanServer\Shares\Security`) | Network access only | Read, Change, Full Control for the whole share |
| **NTFS (or ReFS) permissions** | The file system ACL on every folder and file | Network **and** local access | Full control, Modify, Read & execute, List, Read, Write, plus advanced/special |

The effective right over the network is calculated in three steps:

1. **Within each layer, permissions are cumulative.** A user in two groups gets the union of both groups' allows (Read + Change = Change).
2. **Deny beats allow inside a layer** (an explicit deny overrides an allow at the same level; explicit permissions beat inherited ones).
3. **Across the layers, the most restrictive wins.** Effective = share result ∩ NTFS result.

Example: share grants `Sales` Change and `Managers` Full Control; NTFS grants `Sales` Modify and `Managers` Read & execute. User1 is in both groups. Share result = Full Control; NTFS result = Modify; effective = **Modify**. User1 can create, edit and delete files but cannot change permissions or take ownership over the network.

The modern recommendation is to set the share to **Everyone: Full Control** (or Authenticated Users: Full Control) and do real access control in NTFS, which has one place to troubleshoot. Windows Server's default for `New-SmbShare` without access parameters is **Everyone: Read**, so always state access explicitly.

```powershell
PS C:\> New-Item -Path D:\Shares\Sales -ItemType Directory
PS C:\> New-SmbShare -Name Sales -Path D:\Shares\Sales -FullAccess "CONTOSO\Domain Admins" -ChangeAccess "CONTOSO\Sales" -FolderEnumerationMode AccessBased
PS C:\> Grant-SmbShareAccess -Name Sales -AccountName "CONTOSO\Managers" -AccessRight Full -Force
PS C:\> Get-SmbShareAccess -Name Sales
```

NTFS ACLs are managed with Explorer, `icacls`, or `Get-Acl`/`Set-Acl`:

```text
C:\> icacls D:\Shares\Sales /grant "CONTOSO\Sales:(OI)(CI)M"
C:\> icacls D:\Shares\Sales
```

`(OI)(CI)` means the entry is inherited by files (object inherit) and subfolders (container inherit); `M` is Modify. The **Effective Access** tab in *Advanced Security Settings* calculates NTFS plus share permissions for a chosen user, which is the fastest troubleshooting tool.

### Access-based enumeration (ABE)

ABE hides files and folders that the user has no Read (List) permission for. It changes what users **see**, not what they can open, so it is a usability and information-disclosure control layered on top of correct ACLs.

```powershell
PS C:\> Set-SmbShare -Name Sales -FolderEnumerationMode AccessBased
```

`FolderEnumerationMode Unrestricted` turns it off. ABE is a per-share setting; on DFS Namespaces you enable it on the namespace (see the DFS lesson).

### Other share settings worth knowing

| Setting | Cmdlet parameter | Why |
|---|---|---|
| Continuous availability | `New-SmbShare -ContinuouslyAvailable $true` | Transparent failover on clustered file servers (Scale-Out File Server or general-purpose clustered file server) |
| Per-share encryption | `Set-SmbShare -EncryptData $true` | Encrypts SMB 3 traffic for just that share |
| Offline files (client-side caching) | `-CachingMode` (`None`, `Manual`, `Documents`, `Programs` or `BranchCache`) | Disable caching for application data |
| Concurrent user limit | `-ConcurrentUserLimit` | Licensing or app limits |
| Compression | `-CompressData $true` | SMB compression for large-file transfers (Windows Server 2022 and later) |
| Hidden share | Name ending in `$` | Not listed in browse lists; still reachable by path |

To see who is connected and what they have open: `Get-SmbSession`, `Get-SmbOpenFile`, and `Close-SmbOpenFile -FileId <id>` to break a stuck lock.

> **Exam tip:** "Users can see folders they cannot open and the company wants them hidden" = access-based enumeration. "Users cannot open a folder although NTFS allows Modify" = check the share permission layer.

## File Server Resource Manager (FSRM)

FSRM is a role service (`Install-WindowsFeature FS-Resource-Manager -IncludeManagementTools`) with five features. **FSRM supports NTFS volumes only**; you cannot manage quotas or screens on ReFS.

### Quotas

| Type | Behaviour |
|---|---|
| **Hard quota** | Blocks writes once the limit is reached |
| **Soft quota** | Never blocks; only raises notifications (email, event log, command, report) at thresholds |

FSRM quotas apply to a **folder path** and count all data in it regardless of owner. That is different from NTFS **disk quotas**, which are per user per volume and based on file ownership.

* **Quota templates** hold the limit, type and thresholds; editing a template can update all quotas derived from it.
* **Auto apply quotas** attach a template to a parent folder so that every existing **and future** subfolder gets its own quota: ideal for home folders.

```powershell
PS C:\> New-FsrmQuotaTemplate -Name "Home 10 GB" -Size 10GB
PS C:\> New-FsrmAutoQuota -Path D:\Home -Template "Home 10 GB"
PS C:\> New-FsrmQuota -Path D:\Shares\Projects -Size 500GB -SoftLimit
```

Nested quotas are cumulative: the most restrictive in the path wins. If a parent folder has 100 MB left, a child quota of 200 MB still shows only 100 MB available. *View Quotas Affecting Folder* in the console helps here.

### File screening

A file screen blocks (active) or only reports (passive) files whose **names match patterns** in a **file group** (for example `*.mp3`, `*.exe`). Screening is pattern-based on the name; it does not inspect content.

* **Active screen**: blocks the save and can notify.
* **Passive screen**: allows the save, notifies only (good for auditing before enforcing).
* **File screen exception**: on a subfolder, allows specified file groups that a parent screen blocks.

```powershell
PS C:\> New-FsrmFileGroup -Name "Video files" -IncludePattern @("*.mp4","*.mkv","*.avi")
PS C:\> New-FsrmFileScreen -Path D:\Shares -IncludeGroup "Video files" -Active
PS C:\> New-FsrmFileScreenException -Path D:\Shares\Marketing\Video -IncludeGroup "Video files"
```

> **Watch out:** On a server that also runs Azure File Sync, an active file screen that blocks files arriving from other endpoints causes repeated per-item sync failures.

### Classification and file management tasks

**File Classification Infrastructure (FCI)** assigns **properties** (for example `Confidentiality = High`) to files. Properties are defined in FSRM or centrally as resource properties in AD (for Dynamic Access Control). **Classification rules** set properties automatically by folder location, by content (string or regular expression), or by a PowerShell classifier, on a schedule or in real time.

**File management tasks** act on files that match conditions (location, property values, creation/modification/access dates): **expire** them (move to an archive path), apply **RMS encryption**, or run a **custom command**. Typical use: "move files not modified in 365 days from `D:\Projects` to `\\ARCHIVE1\Old`".

### Storage reports

Run on demand or on a schedule, delivered as DHTML, HTML, XML, CSV or text and optionally emailed. Reports include **Duplicate Files**, **Large Files**, **Least Recently Accessed Files**, **Most Recently Accessed Files**, **Files by Owner**, **Files by File Group**, **Files by Property**, **Folders by Property**, **Quota Usage** and **File Screening Audit**. The audit report only has data if *Record file screening activity in the auditing database* is enabled in FSRM options.

```powershell
PS C:\> New-FsrmStorageReport -Name "Dupes" -Namespace @("D:\Shares") -ReportType DuplicateFiles -Interactive
```

Email notifications for quotas, screens and reports need an SMTP server configured in FSRM options (`Set-FsrmSetting -SmtpServer smtp.contoso.com -AdminEmailAddress fsadmin@contoso.com`).

> **Real world:** Start with passive screens and soft quotas for a few weeks, read the reports, then switch to active and hard. Users notice blocks; they rarely notice reports.

## Lab it yourself

On a Windows Server 2025 evaluation VM with a second virtual disk formatted NTFS as D:

```powershell
PS C:\> Install-WindowsFeature FS-Resource-Manager -IncludeManagementTools
PS C:\> New-Item D:\Shares\Sales, D:\Home\User1, D:\Home\User2 -ItemType Directory
PS C:\> New-SmbShare -Name Sales -Path D:\Shares\Sales -FullAccess Everyone -FolderEnumerationMode AccessBased
PS C:\> New-FsrmQuotaTemplate -Name "Home 1 GB" -Size 1GB
PS C:\> New-FsrmAutoQuota -Path D:\Home -Template "Home 1 GB"
PS C:\> Get-FsrmQuota | Where-Object Path -like 'D:\Home\*'
PS C:\> New-FsrmFileScreen -Path D:\Shares\Sales -Template "Block Executable Files"
PS C:\> fsutil file createnew D:\Shares\Sales\test.exe 1024
```

The last command should fail with access denied because the built-in *Block Executable Files* template blocks `.exe`. Create a folder under `D:\Home` and confirm with `Get-FsrmQuota` that it receives a quota automatically.

## Key takeaways

* Network access = (cumulative share permissions) ∩ (cumulative NTFS permissions); the most restrictive layer wins, and explicit deny beats allow within a layer.
* `New-SmbShare` without access parameters grants Everyone Read; a common design is Full Control at the share and real control in NTFS.
* Access-based enumeration (`-FolderEnumerationMode AccessBased`) hides items a user cannot read; it is not a security boundary by itself.
* FSRM works only on NTFS. Hard quotas block, soft quotas notify; auto apply quotas cover new subfolders automatically.
* File screens match file-name patterns in file groups; active blocks, passive reports, and exceptions carve out subfolders.
* Classification rules tag files with properties; file management tasks expire, encrypt or run commands against matching files; storage reports find duplicates, large and stale files.
