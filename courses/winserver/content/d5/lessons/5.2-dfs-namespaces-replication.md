## Two separate role services

"DFS" is two independent technologies that are often deployed together:

| | DFS Namespaces (DFS-N) | DFS Replication (DFS-R) |
|---|---|---|
| Solves | One logical path for many shares on many servers | Keeping folder contents identical on several servers |
| Feature name | `FS-DFS-Namespace` | `FS-DFS-Replication` |
| Works without the other? | Yes (folder targets can be any SMB share, even Azure Files) | Yes (replicate folders that are not in any namespace) |
| Key objects | Namespace root, namespace servers, folders, folder targets | Replication group, replicated folders, members, connections |

Install both with management tools:

```powershell
PS C:\> Install-WindowsFeature FS-DFS-Namespace, FS-DFS-Replication -IncludeManagementTools
```

## DFS Namespaces

A namespace is a virtual tree. Users browse `\\contoso.com\Public\Sales` and the client receives a **referral**, an ordered list of real UNC paths (folder targets) such as `\\FS1\Sales` and `\\FS2\Sales`. The client tries the first target and falls through the list.

### Domain-based vs standalone

| | Domain-based | Standalone |
|---|---|---|
| Path | `\\contoso.com\Public` (domain name) | `\\FS1\Public` (server name) |
| Metadata stored in | AD DS (and cached on namespace servers) | Registry/memory of the single namespace server |
| High availability | Add more **namespace servers** (any domain member) | Host it on a **failover cluster** |
| Requires AD DS | Yes | No |
| Windows Server 2008 mode extras | Access-based enumeration on the namespace and much larger folder counts | ABE is supported; scale is per server |

Choose **domain-based in Windows Server 2008 mode** for almost everything: the path survives a server replacement, you get redundancy by adding a second namespace server, and you can enable ABE on the namespace. 2008 mode needs the domain at Windows Server 2008 functional level or higher, which any supported domain is.

```powershell
PS C:\> New-Item C:\DFSRoots\Public -ItemType Directory
PS C:\> New-SmbShare -Name Public -Path C:\DFSRoots\Public -FullAccess Everyone
PS C:\> New-DfsnRoot -Path \\contoso.com\Public -TargetPath \\FS1\Public -Type DomainV2
PS C:\> New-DfsnRootTarget -Path \\contoso.com\Public -TargetPath \\FS2\Public
PS C:\> New-DfsnFolder -Path \\contoso.com\Public\Sales -TargetPath \\FS1\Sales
PS C:\> New-DfsnFolderTarget -Path \\contoso.com\Public\Sales -TargetPath \\FS2\Sales
PS C:\> Set-DfsnRoot -Path \\contoso.com\Public -EnableAccessBasedEnumeration $true
```

### Referral ordering

Targets in the **client's own AD DS site are always listed first**, in random order (that is how the namespace load-balances). What happens to the rest depends on the ordering method, set on the root and inherited by folders:

| Method | Out-of-site targets | `Set-DfsnRoot` |
|---|---|---|
| **Lowest cost** (default for new namespaces) | Sorted by AD site-link cost, random within equal cost | `-EnableSiteCosting $true` |
| **Random order** | All remaining targets in random order, regardless of cost | Neither switch |
| **Exclude targets outside of the client's site** | Not returned at all; no in-site target means no access | `-EnableInsiteReferrals $true` |

**Target priority** overrides the ordering for one target:

* **First among all targets** / **Last among all targets**: global, ignores site cost. "Last among all" is the classic setting for a DR copy that should only be used if everything else is down.
* **First among targets of equal cost** / **Last among targets of equal cost**: only reorders inside the same cost group (usually the same site).

Global-priority targets are still returned even when "Exclude targets outside of the client's site" is on.

Other tuning knobs: **client failback** (return to a preferred, lower-cost target when it comes back instead of staying on the fallback), **referral cache duration** (clients cache root and folder referrals; lower values make changes visible faster), and **namespace polling** (optimize for consistency by polling the PDC emulator, or for scalability by polling the nearest DC in large deployments).

> **Exam tip:** "Users in Branch2 must never cross the WAN to reach a file server" = Exclude targets outside of the client's site. "Users must fail over to the nearest other site" = Lowest cost. "Server in DR site used only as a last resort" = target priority Last among all targets.

> **Watch out:** A namespace folder with several targets does **not** keep their contents in sync. Without DFS-R (or Azure File Sync), users referred to different targets see different data.

## DFS Replication

DFS-R is a multi-master, state-based replication engine that also replicates **SYSVOL** in every supported domain. It replicates on change (USN journal), compresses with **Remote Differential Compression (RDC)**, and respects schedules and bandwidth throttles.

### Building a replication group

```powershell
PS C:\> New-DfsReplicationGroup -GroupName "RG-Sales"
PS C:\> New-DfsReplicatedFolder -GroupName "RG-Sales" -FolderName "Sales"
PS C:\> Add-DfsrMember -GroupName "RG-Sales" -ComputerName FS1, FS2
PS C:\> Add-DfsrConnection -GroupName "RG-Sales" -SourceComputerName FS1 -DestinationComputerName FS2
PS C:\> Set-DfsrMembership -GroupName "RG-Sales" -FolderName "Sales" -ComputerName FS1 -ContentPath D:\Shares\Sales -PrimaryMember $true -Force
PS C:\> Set-DfsrMembership -GroupName "RG-Sales" -FolderName "Sales" -ComputerName FS2 -ContentPath D:\Shares\Sales -Force
```

`Add-DfsrConnection` creates a two-way connection by default. The **primary member** is authoritative only for **initial** replication: files on other members that differ are moved to `DfsrPrivate\PreExisting`. After initial sync, all members are equal. For very large data sets, **DFS-R database cloning** (`Export-DfsrClone` / `Import-DfsrClone`) pre-seeds a new member so initial replication only checks hashes.

Topologies: **full mesh** (every member to every member, fine up to roughly ten members) or **hub and spoke** (branches replicate only with one or two hubs; needs at least three members).

### Staging, conflicts and filters

| Item | Default | What it does |
|---|---|---|
| **Staging folder quota** | 4,096 MB per replicated folder | Holds compressed copies of files being sent or received. Too small = constant staging cleanup and slow replication; size it to at least the combined size of the **32 largest files** in the folder |
| **ConflictAndDeleted quota** | 660 MB | Stores conflict losers and (optionally) deleted files; oldest entries are purged when full |
| **File filter** | `~*, *.bak, *.tmp` | Files matching these names are not replicated |
| **RDC** | On for connections | Sends only changed blocks for files of 64 KB or larger (the default threshold, adjustable with `-MinimumRDCFileSizeInKB`); disable on fast LANs where CPU matters more than bandwidth |

```powershell
PS C:\> Set-DfsrMembership -GroupName "RG-Sales" -FolderName "Sales" -ComputerName FS1, FS2 -StagingPathQuotaInMB 32768 -Force
PS C:\> Set-DfsrConnection -GroupName "RG-Sales" -SourceComputerName FS1 -DestinationComputerName FS2 -DisableRDC $false
```

**Conflict resolution is last writer wins.** When the same file is changed on two members before replication, the version with the later write time is kept everywhere; the other copy is moved to `DfsrPrivate\ConflictAndDeleted` **on the member that resolved the conflict** and a conflict event is logged. DFS-R has **no distributed file locking**, so it suits user documents better than databases or files edited simultaneously at two sites.

### Read-only members

Mark branch copies read-only so users cannot change them locally (great for software distribution or published content):

```powershell
PS C:\> Set-DfsrMembership -GroupName "RG-Sales" -FolderName "Sales" -ComputerName BR1 -ReadOnly $true -Force
```

Azure File Sync must not use a read-only replicated folder as a server endpoint.

### Monitoring

* `Get-DfsrBacklog -GroupName RG-Sales -FolderName Sales -SourceComputerName FS1 -DestinationComputerName FS2` lists files waiting to replicate (`dfsrdiag backlog` is the older tool).
* `Write-DfsrHealthReport` produces an HTML health report; `Write-DfsrPropagationReport` with `Start-DfsrPropagationTest` measures end-to-end latency.
* The **DFS Replication** event log records initial replication completion, staging-space warnings, conflicts and database problems.

> **Real world:** Most "DFS-R is slow" tickets are an undersized staging quota (look for repeated staging cleanup warnings in the DFS Replication log) or antivirus scanning the staging folder. Fix the quota before touching the schedule.

## Where Azure File Sync fits

| Need | Choose |
|---|---|
| One stable UNC path over many servers | DFS-N |
| Keep two on-prem servers identical, no cloud | DFS-R |
| Sync many sites through the cloud, tier cold data, cloud backup | Azure File Sync (often behind DFS-N) |
| Replace DFS-R | Azure File Sync, following the DFS-R migration sequence |

## Lab it yourself

Two domain-joined Windows Server 2025 VMs (FS1, FS2) with D: data disks and a DC:

```powershell
PS C:\> Invoke-Command -ComputerName FS1, FS2 { Install-WindowsFeature FS-DFS-Namespace, FS-DFS-Replication -IncludeManagementTools; New-Item D:\Shares\Sales -ItemType Directory; New-SmbShare -Name Sales -Path D:\Shares\Sales -FullAccess Everyone }
```

Then run the namespace and replication commands above, create a file on FS1, and watch it appear on FS2. Edit the same file on both servers while the connection is disabled (`Set-DfsrConnection ... -DisableConnection $true`), re-enable it, and find the losing copy in `D:\Shares\Sales\DfsrPrivate\ConflictAndDeleted` (hidden system folder) on the member that resolved the conflict.

## Key takeaways

* DFS-N provides the path; DFS-R provides the copies. Multiple folder targets without replication show different data.
* Domain-based namespaces (2008 mode) give a server-independent path, redundancy through extra namespace servers, and namespace-level ABE; standalone namespaces need a cluster for HA.
* In-site targets are always first; Lowest cost orders the rest by site-link cost, Random ignores cost, Exclude targets outside the site removes them.
* Target priority "Last among all targets" keeps a DR target as a last resort.
* DFS-R: staging quota default 4 GB (size to the 32 largest files), ConflictAndDeleted 660 MB, RDC sends deltas, last writer wins, no file locking.
* Use read-only members for published content, and `Get-DfsrBacklog` to see what has not replicated yet.
