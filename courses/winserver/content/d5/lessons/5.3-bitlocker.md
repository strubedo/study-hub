## BitLocker on Windows Server

BitLocker Drive Encryption encrypts whole volumes (XTS-AES 128-bit by default on modern Windows; XTS-AES 256 is available by policy or parameter). On Windows Server it is an **optional feature** that must be installed first, and it requires a restart:

```powershell
PS C:\> Install-WindowsFeature BitLocker -IncludeAllSubFeature -IncludeManagementTools -Restart
```

What it protects against: someone stealing a disk, a whole server, a backup of a VHDX, or a decommissioned drive. What it does **not** protect against: anyone who can sign in to the running server, because an unlocked volume is transparent.

### Key protectors

The volume is encrypted with a **full volume encryption key (FVEK)**, which is encrypted by the **volume master key (VMK)**, which is in turn sealed by one or more **key protectors**. Any one protector can unlock the volume.

| Protector | Volume type | How it unlocks | Notes |
|---|---|---|---|
| **TPM** | OS | Automatically if the boot measurements match | Typical for servers; changes to firmware or boot configuration trigger recovery |
| **TPM + PIN** | OS | TPM plus a PIN typed at boot | Strong, but needs a person at the console on every restart (see Network Unlock) |
| **TPM + startup key** / TPM + PIN + startup key | OS | TPM plus a USB key file | Rare on servers |
| **Startup key** | OS | USB key file only | For hardware without a TPM |
| **Password** | Data / removable | Typed password | |
| **Recovery password** | Any | **48-digit** numerical password in eight groups of six (each group is a multiple of 11, so typos are caught as you type) | The key you store in AD DS or Entra ID |
| **Recovery key** | Any | `.BEK` file on removable media | |
| **AD DS account or group (SID)** | Data / CSV | Unlocks for that computer or group account | Used for Cluster Shared Volumes with the cluster name object |
| **Network Unlock (TpmCertificate)** | OS | Key from a WDS server on the wired corporate network | Supplements TPM + PIN |
| **Auto-unlock** | Data | Key stored on the encrypted OS volume | `Enable-BitLockerAutoUnlock -MountPoint E:` |

```powershell
PS C:\> Enable-BitLocker -MountPoint C: -EncryptionMethod XtsAes256 -UsedSpaceOnly -TpmProtector
PS C:\> Add-BitLockerKeyProtector -MountPoint C: -RecoveryPasswordProtector
PS C:\> Enable-BitLocker -MountPoint E: -RecoveryPasswordProtector
PS C:\> Enable-BitLockerAutoUnlock -MountPoint E:
PS C:\> Get-BitLockerVolume | Format-Table MountPoint, VolumeStatus, EncryptionPercentage, ProtectionStatus, LockStatus
```

`-UsedSpaceOnly` encrypts only the sectors in use (fast for new volumes; free space is encrypted as it is written). Full encryption also scrubs old data remnants from free space. The `manage-bde` equivalents:

```text
C:\> manage-bde -on C: -RecoveryPassword -UsedSpaceOnly
C:\> manage-bde -status
C:\> manage-bde -protectors -get C:
C:\> manage-bde -protectors -add E: -RecoveryPassword
```

### Suspend, don't decrypt, for maintenance

Firmware (UEFI/BIOS) updates, TPM firmware updates and some boot changes alter the measurements the TPM checks, so the next boot asks for the recovery key. Suspend protection first:

```powershell
PS C:\> Suspend-BitLocker -MountPoint C: -RebootCount 1
```

Suspension leaves the data encrypted but writes the key in the clear on the volume until the reboot count is reached (then protection resumes automatically). `-RebootCount 0` suspends until you run `Resume-BitLocker`. `manage-bde -protectors -disable C: -RebootCount 1` is the command-line form.

## Escrowing recovery information

You must be able to get recovery passwords back when a server enters recovery mode.

### AD DS

Group Policy under *Computer Configuration\Administrative Templates\Windows Components\BitLocker Drive Encryption* (separate sections for operating system, fixed data and removable data drives):

* **Choose how BitLocker-protected operating system drives can be recovered**: enable *Save BitLocker recovery information to AD DS*, choose *Store recovery passwords and key packages*, and tick **Do not enable BitLocker until recovery information is stored to AD DS** so encryption cannot start without escrow.

The recovery password is stored as an `msFVE-RecoveryInformation` child object of the **computer object**. Domain Admins can read it by default; reading access can be delegated. View it with the **BitLocker Recovery Password Viewer** (the *BitLocker Drive Encryption Administration Utilities* feature adds a *BitLocker Recovery* tab to computer objects in ADUC and a domain-wide search by password ID), or with PowerShell:

```powershell
PS C:\> $comp = Get-ADComputer FS1
PS C:\> Get-ADObject -Filter "objectClass -eq 'msFVE-RecoveryInformation'" -SearchBase $comp.DistinguishedName -Properties msFVE-RecoveryPassword | Select-Object Name, msFVE-RecoveryPassword
```

For volumes that were encrypted **before** the policy applied, escrow the existing protector manually:

```powershell
PS C:\> $id = ((Get-BitLockerVolume -MountPoint C:).KeyProtector | Where-Object KeyProtectorType -eq 'RecoveryPassword').KeyProtectorId
PS C:\> Backup-BitLockerKeyProtector -MountPoint C: -KeyProtectorId $id
```

`manage-bde -protectors -adbackup C: -id {GUID}` does the same from the command line.

### Microsoft Entra ID

Entra-joined (or hybrid-joined) devices can escrow to Entra ID with `BackupToAAD-BitLockerKeyProtector -MountPoint C: -KeyProtectorId $id`; the key then appears on the device object in the Entra admin center and Intune. Azure VMs normally use **Azure Disk Encryption** (BitLocker inside the guest, keys in **Azure Key Vault**) or encryption at host instead of manual escrow.

## Network Unlock

Servers protected with **TPM + PIN** cannot reboot unattended, which breaks patching windows. **Network Unlock** adds a protector that lets the boot manager obtain half of the key from the network when the server is on the **wired corporate LAN**; off the network, the PIN prompt appears as usual.

Requirements:

* Client (the server being unlocked): UEFI firmware (2.3.1 or later) in native mode with a **UEFI DHCP driver** and the network stack enabled, a **TPM**, and a TPM + PIN protector. The **first** network adapter must be the one that gets DHCP.
* A server running **Windows Deployment Services (WDS)** (the WDS service must be running) with the **BitLocker Network Unlock** feature (`Install-WindowsFeature BitLocker-NetworkUnlock`).
* A **DHCP server separate from the WDS server**.
* A Network Unlock certificate (2048-bit RSA key pair): private key on the WDS server, public certificate distributed to clients by Group Policy under *Public Key Policies\BitLocker Drive Encryption Network Unlock Certificate*, plus the policy **Allow network unlock at startup**.
* Optional `bde-network-unlock.ini` on the WDS server to restrict unlocking to specific subnets.

After the policy applies and the server reboots, `manage-bde -protectors -get C:` shows a protector of type **TpmCertificate** (Network (Certificate Based)).

## Recovering encrypted volumes

### Unlocking a locked data volume

A data volume can be locked after moving the disk to another server, or because auto-unlock was not configured.

```powershell
PS C:\> Unlock-BitLocker -MountPoint E: -RecoveryPassword "011550-462616-237875-693176-305921-139326-584089-418660"
PS C:\> Unlock-BitLocker -MountPoint E: -RecoveryKeyPath F:\
PS C:\> Unlock-BitLocker -MountPoint E: -Password (Read-Host -AsSecureString)
```

```text
C:\> manage-bde -unlock E: -RecoveryPassword 011550-462616-237875-693176-305921-139326-584089-418660
```

`Unlock-BitLocker` restores access but does not change protectors; `Lock-BitLocker` locks a data volume again.

### OS volume in recovery mode

The pre-boot recovery screen shows the **Key ID** (the first part of the recovery password's protector ID). Match it to the stored password in AD DS or Entra ID and type the 48 digits. Then find the cause (firmware update without suspending, TPM cleared, boot order or Secure Boot change, disk moved to another machine), fix it, and **rotate the recovery password** because it has now been disclosed: remove the old recovery password protector, add a new one, and escrow it.

### Severely damaged drives: repair-bde

If the volume metadata is corrupt and the recovery password alone no longer unlocks it, **`repair-bde`** decrypts what it can, block by block, onto a **different** drive that is at least as large (its contents are overwritten). It needs the **recovery password or recovery key** and usually the **key package**, which AD DS stores only if the policy saved *recovery passwords and key packages*. You can also export one in advance with `manage-bde -KeyPackage C: -id {GUID} -path D:\Keys`.

```text
C:\> repair-bde E: F: -rp 011550-462616-237875-693176-305921-139326-584089-418660 -kp D:\Keys
C:\> repair-bde E: F: -rk G:\RecoveryKey.bek -lf C:\Temp\repair.log
```

`repair-bde` cannot repair a volume that failed **during** encryption or decryption.

> **Exam tip:** Unlock a data volume = `Unlock-BitLocker` / `manage-bde -unlock`. Salvage data from a physically damaged encrypted disk = `repair-bde` with the key package. Back up an existing recovery password = `Backup-BitLockerKeyProtector` (AD DS) or `BackupToAAD-BitLockerKeyProtector` (Entra ID).

> **Watch out:** Removing all key protectors does not decrypt the volume; it leaves the key stored in the clear (the same state as suspension). Always keep at least one recovery password protector.

### EFS recovery in brief

EFS (file-level encryption) is separate from BitLocker. If a user's EFS key is lost, files can be recovered only by a **Data Recovery Agent (DRA)** defined in Group Policy (*Public Key Policies\Encrypting File System*) **before** the files were encrypted. `cipher /r:<name>` generates a DRA certificate and key pair; `cipher /u` updates existing files with current DRA keys.

## Lab it yourself

Create a **Generation 2** Hyper-V VM with a virtual TPM, then install and encrypt:

```powershell
PS C:\> Set-VMKeyProtector -VMName VM1 -NewLocalKeyProtector
PS C:\> Enable-VMTPM -VMName VM1
# inside VM1
PS C:\> Install-WindowsFeature BitLocker -IncludeAllSubFeature -IncludeManagementTools -Restart
PS C:\> Enable-BitLocker -MountPoint C: -TpmProtector -UsedSpaceOnly
PS C:\> Add-BitLockerKeyProtector -MountPoint C: -RecoveryPasswordProtector
PS C:\> manage-bde -protectors -get C:
```

Encrypt a data disk with a password protector, take it offline and online again (`Set-Disk -Number 1 -IsOffline $true`, then `$false`), and practise `Unlock-BitLocker` with the recovery password. If the VM is domain-joined and the GPO is linked, run `Backup-BitLockerKeyProtector` and find the password on the computer object.

## Key takeaways

* Install the BitLocker feature on Windows Server first; protectors include TPM, TPM+PIN, recovery password (48 digits), recovery key, password, AD account/group and Network Unlock.
* Suspend (`Suspend-BitLocker -RebootCount 1`) before firmware or TPM changes instead of decrypting.
* Escrow to AD DS with Group Policy ("do not enable until stored in AD DS"); back up existing protectors with `Backup-BitLockerKeyProtector`, or `BackupToAAD-BitLockerKeyProtector` for Entra ID.
* Network Unlock needs UEFI DHCP clients with TPM+PIN, a WDS server with the BitLocker Network Unlock feature, a separate DHCP server and a certificate deployed by GPO.
* `Unlock-BitLocker` or `manage-bde -unlock` reopens a locked data volume; rotate a recovery password after it has been used.
* `repair-bde` salvages data from damaged encrypted volumes to another drive and needs the recovery password or key plus, usually, the key package.
