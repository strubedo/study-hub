## Why Azure File Sync exists

Azure File Sync turns a Windows file server into a **cache** of an Azure file share. Users keep using `\\FS1\Data` over SMB on the LAN, while the authoritative copy lives in Azure Files. You get:

* **Multi-site sync** through the cloud, with no server-to-server WAN replication.
* **Cloud tiering**: only hot files stay on local disk; cold files become stubs that are recalled on access.
* **Fast disaster recovery**: build a new server, install the agent, add a server endpoint, and the namespace comes down immediately.
* A **cloud backup point** (share snapshots / Azure Backup) instead of local backup of every branch server.

The agent talks to Azure with the Azure File Sync REST and FileREST protocols over **HTTPS (TCP 443)**. SMB is never used between the server and Azure, so the port 445 problem disappears.

## Components

| Component | Where | What it is |
|---|---|---|
| **Storage Sync Service** | Azure resource | Top-level resource that holds registered servers and sync groups. Deploy it in the same region as the storage account |
| **Registered server** | Storage Sync Service | Trust relationship between one Windows Server (or one cluster) and **one** Storage Sync Service |
| **Sync group** | Storage Sync Service | Defines one sync topology: exactly **one cloud endpoint** plus one or more server endpoints |
| **Cloud endpoint** | Sync group | Pointer to an Azure file share. A given share can be the cloud endpoint of only one sync group |
| **Server endpoint** | Sync group | A path on a registered server, such as `D:\Data` or a volume root. Cloud tiering is configured here |
| **Agent** | Windows Server | `FileSyncSvc.exe` (the sync service) and `StorageSync.sys` (the file system filter that makes tiering and recall work) |

Rules that generate exam questions:

* A server can be registered to **only one** Storage Sync Service at a time, but can have server endpoints in many sync groups of that service.
* Within one sync group, a registered server can have **only one** server endpoint. To get two folders from the same server into one share, sync a common parent instead.
* Server endpoints must be on **NTFS** volumes. ReFS, FAT and FAT32 are not supported.
* The **system volume** cannot use cloud tiering. You can create a server endpoint there only with tiering off.
* Server endpoints cannot be nested; side-by-side on the same volume is fine.
* Supported OS: Windows Server **2016, 2019, 2022 and 2025** (Full and Server Core; not Nano). The agent package is OS-specific: before an in-place OS upgrade, uninstall the agent, upgrade, then install the agent for the new OS. Do **not** unregister the server, or tiered files are orphaned.
* Agents expire: major versions are supported for at least 12 months with warnings at least 3 months ahead. Auto-update installs either the latest agent or an update shortly before expiry (`Set-StorageSyncAgentAutoUpdatePolicy -PolicyMode InstallLatest` or `UpdateBeforeExpiration`). Downgrades are not supported.
* Changes made **directly in the Azure file share** are only detected by a change detection job that runs every 24 hours. `Invoke-AzStorageSyncChangeDetection` triggers it on demand.

## Deploying

The order of operations is fixed by dependencies: you need the service before you can register a server or create a sync group; you need a registered server and a sync group before you can add a server endpoint.

```powershell
# Azure side
PS C:\> New-AzStorageSyncService -ResourceGroupName RG1 -Name Sync1 -Location eastus
PS C:\> New-AzStorageSyncGroup -ResourceGroupName RG1 -StorageSyncServiceName Sync1 -Name SG-Data
PS C:\> New-AzStorageSyncCloudEndpoint -ResourceGroupName RG1 -StorageSyncServiceName Sync1 -SyncGroupName SG-Data -Name CE1 -StorageAccountResourceId $sa.Id -AzureFileShareName data

# On FS1, after installing the agent MSI
PS C:\> Register-AzStorageSyncServer -ResourceGroupName RG1 -StorageSyncServiceName Sync1

# Back in Azure: add the server path, with cloud tiering
PS C:\> $srv = Get-AzStorageSyncServer -ResourceGroupName RG1 -StorageSyncServiceName Sync1
PS C:\> New-AzStorageSyncServerEndpoint -ResourceGroupName RG1 -StorageSyncServiceName Sync1 -SyncGroupName SG-Data -Name FS1-Data -ServerResourceId $srv.ResourceId -ServerLocalPath D:\Data -CloudTiering -VolumeFreeSpacePercent 20
```

## Cloud tiering

When tiering is enabled, Azure File Sync keeps a **heatmap** of file access and turns the coldest files into tiered stubs (reparse points with the offline/recall-on-access attributes). Tiered files look normal in Explorer and recall transparently when opened.

Two policies decide what gets tiered:

* **Volume free space policy**: keep at least *x*% of the **volume** free. It applies per volume, not per endpoint. If several server endpoints share a volume, the **highest** percentage among them becomes the effective policy for all of them.
* **Date policy** (optional): tier anything not accessed in *x* days, even if space is plentiful.

The volume free space policy **always wins**. If honouring the date policy would leave less free space than the free-space target, Azure File Sync keeps tiering the coldest files until the target is met, even files "younger" than the date threshold. Policies are evaluated about **once an hour**. Lowering the free-space percentage or lengthening the date policy does **not** automatically recall files; you can force it with `Invoke-StorageSyncFileRecall -Path D:\Data` on the server.

A file can only be tiered after it has been uploaded to the Azure file share. Start with **date policy off, free space 10-20%**. When migrating onto a server smaller than the source data, temporarily set free space very high (for example 99%) so files tier as fast as they sync.

> **Watch out:** Antivirus or backup software that reads file contents will recall tiered files and drive up egress, unless it respects the offline attribute. Data Deduplication is supported alongside cloud tiering on Windows Server 2016 and later.

## Monitoring

Use three places:

1. **Azure Monitor metrics** on the Storage Sync Service (sent every 15 minutes): *Sync session result*, *Files not syncing*, *Files synced*, *Server online status*, *Cloud tiering recall size*, cache hit rate and others. Build **metric alert rules** on them with an action group; the *Agent version expiration information* signal lets you alert about 90 days before an agent expires.
2. **Portal health** per registered server and server endpoint (Healthy, Pending, No Activity, Error) and the *Errors + troubleshooting* section listing per-item errors.
3. **Event logs on the server**: *Applications and Services Logs\Microsoft\FileSync\Agent\Telemetry* (plus Operational and Diagnostic logs).

| Telemetry event | Meaning |
|---|---|
| 9102 | A sync session completed. `HResult` 0 = success; check `SyncDirection` (upload/download) and `PerItemErrorCount` |
| 9121 | One per per-item error after a session, with persistent and transient counts |
| 9302 | Progress of an active session, every 5-10 minutes |
| 9301 | The server polling the service for jobs (every 30 seconds); a non-zero status means it cannot reach the service |
| 9003, 9016, 9029 | Cloud tiering errors, ghosting results per volume, and tiering session details |

A session can have `HResult` 0 and still report per-item errors, so always look at both values. On the server, `Debug-StorageSyncServer -Diagnose` and `Test-StorageSyncNetworkConnectivity` (from `StorageSync.Management.ServerCmdlets.dll`) are the first troubleshooting steps, plus `fltmc` to confirm the `StorageSync` filter is loaded.

## Migrating DFS Replication to Azure File Sync

Azure File Sync and DFS-R are both multi-master replication engines, and in most designs Azure File Sync **replaces** DFS-R. Microsoft's migration sequence is:

1. Create a sync group that represents the DFS-R topology you are replacing.
2. On the DFS-R member that holds the **full data set**, install the agent, register the server, and create a server endpoint **without cloud tiering**.
3. Let all data upload to the Azure file share.
4. Install and register the agent on the remaining DFS-R members.
5. **Disable DFS-R.**
6. Create server endpoints on the remaining members, again without cloud tiering, and let them sync.
7. Test, then retire DFS-R.
8. **Now** enable cloud tiering where you want it.

Running both side by side is allowed only in limited cases (during migration, hub-and-spoke where branches cannot reach the internet). When they coexist, **cloud tiering must be disabled** on volumes that hold DFS-R replicated folders, and you must not put server endpoints on DFS-R **read-only** replicated folders. DFS **Namespaces** is fully compatible: keep the namespace and point its folder targets at the Azure File Sync servers so users never see a path change.

## Migrating file shares into Azure Files

| Tool | Path | Use it when |
|---|---|---|
| **Robocopy** | SMB, source to mounted Azure share (or to an Azure File Sync server) | The default: full fidelity (data, attributes, timestamps, ACLs, owner), repeatable catch-up passes |
| **Storage Migration Service** | Windows Admin Center, orchestrator server | Migrating a whole Windows/Samba/NetApp file server to a new **Windows Server** (on-premises or an Azure VM it can create), optionally taking over the old name and IP. It does **not** target Azure Files directly, but supports a destination running Azure File Sync with cloud tiering |
| **AzCopy** | REST over HTTPS | Scripted bulk copies and cloud-to-cloud; use `--preserve-permissions=true --preserve-info=true` for ACLs and SMB properties. Microsoft rates it "supported but not fully recommended" for Azure Files migrations: it uses REST rather than SMB, some file fidelity can be lost, `azcopy sync` is limited to 10 million files per job, and it removes files deleted at the source only if you add `--delete-destination` |
| **Azure Data Box** | Shipped device | Too much data for the network, then catch up with Robocopy |

The Microsoft-recommended Robocopy command line looks like this:

```text
C:\> robocopy \\FS1\Data Z:\ /MT:20 /R:2 /W:1 /B /MIR /IT /COPY:DATSO /DCOPY:DAT /NP /NFL /NDL /XD "System Volume Information" /UNILOG:C:\Logs\data.log
```

`/MIR` mirrors (copies changes **and** purges deleted items), `/COPY:DATSO` adds security (S) and owner (O) to the default data/attributes/timestamps, `/DCOPY:DAT` keeps directory timestamps, and `/B` (backup mode) requires an elevated prompt. Mount the Azure share with the **storage account key** or an admin-level RBAC role so permissions do not block the copy. Auditing information (U) cannot be stored in Azure Files.

Cut-over: one bulk pass, repeated catch-up passes, block user changes on the source (re-point the DFS-N target or change share permissions), a **final** pass, then redirect users.

> **Exam tip:** "Keep the same server name and IP after migration" points to Storage Migration Service cut-over. "Keep the same UNC path while the back end moves to Azure" points to DFS Namespaces in front of Azure File Sync.

> **Real world:** Robocopy onto an Azure File Sync server (not straight into the share) lets cloud tiering free space as data syncs, so 20 TB can pass through a 4 TB server.

## Lab it yourself

1. In your free subscription, create a storage account and share (see the previous lesson), then **Storage Sync Services** > Create.
2. On a Windows Server 2025 VM with a D: data volume, install the agent from the Microsoft Download Center, sign in during registration and pick your Storage Sync Service.
3. Create a sync group pointing at the share, add server endpoint `D:\Data` with cloud tiering at 50% free space.
4. Copy test files, then watch *Event Viewer > Applications and Services Logs > Microsoft > FileSync > Agent > Telemetry* for event 9102, and the metrics blade on the Storage Sync Service.
5. Add a file directly in the Azure portal and notice it does not appear until change detection runs. Trigger a share-wide scan with `Invoke-AzStorageSyncChangeDetection -ResourceGroupName RG1 -StorageSyncServiceName Sync1 -SyncGroupName SG-Data -Name CE1` (use the cloud endpoint's name, which is a GUID if the portal created it; `-Path` or `-DirectoryPath` limit the scan to at most 10,000 items).

## Key takeaways

* Azure File Sync = Storage Sync Service, registered servers, sync groups (one cloud endpoint, many server endpoints) and the agent; it uses HTTPS 443, never SMB, to reach Azure.
* One server registers to one Storage Sync Service; one server endpoint per server per sync group; NTFS only; no cloud tiering on the system volume.
* Cloud tiering: volume free space policy beats the date policy, is evaluated hourly, and the highest percentage on a shared volume applies to all endpoints there.
* Monitor with Azure Monitor metrics and alerts, portal health, and the Telemetry log (9102 session complete, 9121 per-item errors, 9302 progress).
* DFS-R migration: seed from the full member without tiering, disable DFS-R, add the other members, then enable tiering last.
* Robocopy (`/MIR /COPY:DATSO /DCOPY:DAT /B`) is the default migration tool; Storage Migration Service moves whole servers including identity; AzCopy is only "supported but not fully recommended" for migrations.
