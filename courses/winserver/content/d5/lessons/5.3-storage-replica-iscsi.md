## Storage Replica

Storage Replica (SR) replicates **volumes at the block level** between servers or clusters over SMB 3, for disaster recovery or stretch clusters. Because it works below the file system, it does not care about open files and it replicates any file system (NTFS or ReFS) or application data.

### Synchronous vs asynchronous

| | Synchronous | Asynchronous |
|---|---|---|
| Application write acknowledged | After the write is logged on **both** source and destination | After it is logged on the source only |
| Data loss on site failure (RPO) | **Zero** | Small, non-zero |
| Latency guidance | Average round trip **5 ms or less** with enough bandwidth for the write workload | No latency recommendation; suits long distances |
| Typical use | Stretch clusters, metro distances | Cross-region DR |

`New-SRPartnership` uses **synchronous** by default; add `-ReplicationMode Asynchronous` when the link is slower or farther.

### Topologies

| Scenario | What it is |
|---|---|
| **Server-to-server** | Two standalone servers, each with its own storage. Manual failover by reversing the direction |
| **Stretch cluster** | One failover cluster spanning two sites, each site with asymmetric storage; automatic failover |
| **Cluster-to-cluster** | Two separate clusters, one replicating to the other (for example S2D to S2D) |
| **Cross-region / Azure** | The same roles using Azure VMs reached by VPN or ExpressRoute |

### Requirements

* AD DS forest; at least 2 GB RAM and two cores per server.
* For each replicated volume on each side, a **data volume and a separate log volume**. Data volumes must be the **same size** on both sides, all data disks must share one sector size, and all log disks must share one sector size. Log volumes should be **faster than the data** (SSD/NVMe) and used for nothing else. Disks are **GPT**; the replicated volume cannot be the volume containing Windows.
* Firewall: ICMP, SMB (TCP 445, plus 5445 for SMB Direct) and WS-Management (TCP 5985) bidirectionally.
* Edition: **Datacenter** is unlimited. **Standard** (2019 and later) is limited to **one replicated volume** (one partnership with a single volume) **up to 2 TB**.

Windows Server 2025 adds an opt-in **Enhanced Log** format with better performance (`New-SRPartnership ... -LogType Raw`; the traditional CLFS-based log is `-LogType FileBased`). You choose the log type when you create the partnership; there is no migration path between the two formats later. Windows Server 2025 can also compress replication traffic (`-EnableCompression`).

### Deploying server-to-server

```powershell
PS C:\> Invoke-Command -ComputerName SR1, SR2 { Install-WindowsFeature Storage-Replica -IncludeManagementTools -Restart }
PS C:\> Test-SRTopology -SourceComputerName SR1 -SourceVolumeName D: -SourceLogVolumeName L: -DestinationComputerName SR2 -DestinationVolumeName D: -DestinationLogVolumeName L: -DurationInMinutes 30 -ResultPath C:\Temp
PS C:\> New-SRPartnership -SourceComputerName SR1 -SourceRGName RG01 -SourceVolumeName D: -SourceLogVolumeName L: -DestinationComputerName SR2 -DestinationRGName RG02 -DestinationVolumeName D: -DestinationLogVolumeName L: -LogSizeInBytes 8GB
PS C:\> (Get-SRGroup -Name RG02 -ComputerName SR2).Replicas | Select-Object DataVolume, ReplicationStatus, NumOfBytesRemaining
```

`Test-SRTopology` runs against the real workload for the duration you give it and produces an HTML report on bandwidth, latency, initial sync time and log sizing. Run it **before** creating the partnership. During initial sync the destination reports `InitialBlockCopy`; once in sync, `ContinuouslyReplicating`.

### Using the destination

The destination volume is **dismounted and inaccessible** while it is a replica: no drive letter browsing, no backups of it, no dedup jobs. To fail over (or switch direction for maintenance):

```powershell
PS C:\> Set-SRPartnership -NewSourceComputerName SR2 -SourceRGName RG02 -DestinationComputerName SR1 -DestinationRGName RG01
```

To test DR without breaking replication, Windows Server 2019 and later can **mount a writable snapshot of the destination** on a spare volume with `Mount-SRDestination` and later `Dismount-SRDestination`. `Remove-SRPartnership` followed by `Remove-SRGroup` on both sides ends replication.

> **Watch out:** Data Deduplication can run on the **source** volume only. Install the feature on both sides, but never enable it on the destination, which allows no local writes.

> **Exam tip:** Storage Replica is one-way per volume. You can replicate D: from SR1 to SR2 and E: from SR2 to SR1 at the same time, each with its own log volume, but not the same volume both ways.

Not to be confused with: **Hyper-V Replica** (per-VM, asynchronous, every 30 seconds to 15 minutes, free in any edition), **DFS-R** (file level, multi-master, last writer wins), or **Azure Site Recovery** (orchestrated VM DR to Azure, outside AZ-802).

## iSCSI

iSCSI carries SCSI commands over TCP (port **3260**). Windows Server includes both ends:

* **iSCSI Target Server** (`FS-iSCSITarget-Server` role service) publishes **iSCSI virtual disks**, which are VHDX files on the target, as LUNs.
* **iSCSI Initiator** (service `MSiSCSI`, built in) connects a server to targets, whether they are Windows or a SAN array.

Names are **IQNs**: Windows initiators use `iqn.1991-05.com.microsoft:<computer-FQDN>`, and a Windows target named *SQLData* on SAN1 gets `iqn.1991-05.com.microsoft:san1-sqldata-target`.

### Target side

```powershell
PS C:\> Install-WindowsFeature FS-iSCSITarget-Server -IncludeManagementTools
PS C:\> New-IscsiVirtualDisk -Path E:\iSCSIVirtualDisks\SQLData.vhdx -SizeBytes 500GB
PS C:\> New-IscsiServerTarget -TargetName SQLData -InitiatorIds "IQN:iqn.1991-05.com.microsoft:sql1.contoso.com"
PS C:\> Add-IscsiVirtualDiskTargetMapping -TargetName SQLData -Path E:\iSCSIVirtualDisks\SQLData.vhdx
```

`-InitiatorIds` is the access list: only listed initiators can log on and see the LUNs. Identifiers can be `IQN:`, `DNSName:`, `IPAddress:`, `IPv6Address:` or `MACAddress:`. For a failover cluster, list **every node's** IQN. Add **CHAP** (`Set-IscsiServerTarget -TargetName SQLData -EnableChap $true -Chap <PSCredential>`) for authentication, and **reverse CHAP** if the initiator must also verify the target.

### Initiator side

```powershell
PS C:\> Set-Service MSiSCSI -StartupType Automatic
PS C:\> Start-Service MSiSCSI
PS C:\> New-IscsiTargetPortal -TargetPortalAddress 10.10.20.5
PS C:\> Get-IscsiTarget
PS C:\> Connect-IscsiTarget -NodeAddress iqn.1991-05.com.microsoft:san1-sqldata-target -IsPersistent $true
PS C:\> Get-Disk | Where-Object BusType -eq iSCSI
```

`-IsPersistent $true` makes the connection come back after a reboot (the "Add this connection to the list of Favorite Targets" checkbox in `iscsicpl.exe`). Then bring the disk online, initialise and format it like any local disk. To use CHAP add `-AuthenticationType ONEWAYCHAP -ChapUsername <name> -ChapSecret <12-16 characters>`.

### Multipath I/O

Two NICs to two target portals give redundancy only if **MPIO** combines the paths into one disk. Without MPIO, Windows sees the LUN twice.

```powershell
PS C:\> Install-WindowsFeature Multipath-IO
PS C:\> Enable-MSDSMAutomaticClaim -BusType iSCSI
PS C:\> Connect-IscsiTarget -NodeAddress <iqn> -IsPersistent $true -IsMultipathEnabled $true -InitiatorPortalAddress 10.10.20.11 -TargetPortalAddress 10.10.20.5
PS C:\> Connect-IscsiTarget -NodeAddress <iqn> -IsPersistent $true -IsMultipathEnabled $true -InitiatorPortalAddress 10.10.21.11 -TargetPortalAddress 10.10.21.5
```

Best practices: dedicated storage VLANs or physical networks, jumbo frames end to end if you enable them anywhere, no default gateway on iSCSI NICs, and **do not team** iSCSI NICs (use MPIO, not LBFO).

> **Real world:** In a home lab, the Windows iSCSI target is the cheapest way to give a two-node failover cluster shared storage. In production, Storage Spaces Direct has largely replaced "Windows server as SAN" designs.

## Lab it yourself

Three VMs: SAN1 (target), NODE1 and NODE2 (initiators), all Windows Server 2025 evaluation:

1. On SAN1 run the target commands above with `-InitiatorIds "IQN:iqn.1991-05.com.microsoft:node1.contoso.com","IQN:iqn.1991-05.com.microsoft:node2.contoso.com"` and a 20 GB virtual disk.
2. On each node run the initiator commands, then `Get-Disk` to see the LUN. Bring it online on one node only (unless you build a cluster).
3. For Storage Replica, give two VMs each a 20 GB data disk and a 10 GB log disk (GPT, same sizes), install the feature, run `Test-SRTopology` for 5 minutes, create the partnership, and watch `(Get-SRGroup).Replicas` move from `InitialBlockCopy` to `ContinuouslyReplicating`. Install the Datacenter evaluation edition if you want to avoid the Standard edition single-volume, 2 TB limit (a 20 GB lab volume fits either way).

## Key takeaways

* Storage Replica = block-level, one-way per volume, synchronous (zero RPO, 5 ms RTT guidance) or asynchronous (long distance); default is synchronous.
* Each side needs a same-size data volume plus a dedicated, fast log volume, GPT disks, not the Windows volume.
* Standard edition: one volume, up to 2 TB; Datacenter: unlimited. Topologies: server-to-server, stretch cluster, cluster-to-cluster.
* Run `Test-SRTopology` first; `New-SRPartnership` creates it; `Set-SRPartnership` reverses direction; `Mount-SRDestination` tests DR; destination volumes are not accessible.
* iSCSI: target publishes VHDX-based LUNs to initiator IQNs listed in `-InitiatorIds` (TCP 3260); initiator uses `New-IscsiTargetPortal` and `Connect-IscsiTarget -IsPersistent $true`.
* Use CHAP for authentication and MPIO (`Enable-MSDSMAutomaticClaim -BusType iSCSI`) rather than NIC teaming for path redundancy.
