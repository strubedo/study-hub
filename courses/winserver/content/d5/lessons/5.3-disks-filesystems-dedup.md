## Disks: partition styles and disk types

| | MBR | GPT |
|---|---|---|
| Max disk size addressed | 2 TiB (with 512-byte sectors) | Effectively unlimited for Windows (volume size is limited by the file system) |
| Partitions | 4 primary (or 3 + extended) | 128 by default |
| Boot requirement | BIOS/legacy boot | UEFI boot (Generation 2 Hyper-V VMs, modern servers) |
| Resilience | Single partition table | Primary and backup partition table, CRC protected |

A 3 TB disk initialised as MBR shows roughly 2 TB usable and the rest unallocated and unusable. Converting an MBR **data** disk to GPT with Disk Management or `diskpart convert gpt` requires removing all partitions first; `mbr2gpt.exe` converts an **OS** disk in place for BIOS-to-UEFI migrations.

**Basic disks** with partitions are the norm. **Dynamic disks** (spanned, striped, mirrored, RAID-5 volumes) are deprecated for most purposes; use Storage Spaces for software resiliency instead.

### Storage cmdlets you should be fluent in

```powershell
PS C:\> Get-Disk | Where-Object PartitionStyle -eq 'RAW'
PS C:\> Initialize-Disk -Number 2 -PartitionStyle GPT
PS C:\> New-Partition -DiskNumber 2 -UseMaximumSize -DriveLetter E
PS C:\> Format-Volume -DriveLetter E -FileSystem ReFS -AllocationUnitSize 65536 -NewFileSystemLabel "VMs"
PS C:\> Get-PartitionSupportedSize -DriveLetter D
PS C:\> Resize-Partition -DriveLetter D -Size (Get-PartitionSupportedSize -DriveLetter D).SizeMax
PS C:\> Set-Disk -Number 3 -IsOffline $false
PS C:\> Set-Disk -Number 3 -IsReadOnly $false
```

After extending a virtual disk (VHDX, SAN LUN, Azure managed disk), rescan (`Update-HostStorageCache` or *Rescan Disks*) and then `Resize-Partition` into the new space. You can extend NTFS and ReFS online; only NTFS can **shrink**.

Volumes can be mounted to a drive letter or to an **empty NTFS folder** (mount point) with `Add-PartitionAccessPath -DiskNumber 2 -PartitionNumber 2 -AccessPath D:\Mounts\Logs`, which is how you go beyond 26 letters.

### Virtual hard disks

`New-VHD -Path D:\VHD\Data.vhdx -SizeBytes 200GB -Dynamic`, then `Mount-VHD` (Hyper-V module) or `Mount-DiskImage`, and initialise it like a physical disk. VHDX supports up to 64 TB and 4 KB logical sectors; VHD is limited to 2 TB.

## Choosing a file system: NTFS vs ReFS

ReFS (Resilient File System) is built for integrity and scale. It checksums metadata (and optionally file data with **integrity streams**), and on a **mirror or parity Storage Space** it repairs corrupt data online from the good copy. A background scrubber looks for latent corruption.

| Capability | NTFS | ReFS |
|---|---|---|
| Max volume / file size (Microsoft's ReFS comparison table) | 256 TB | 35 PB |
| Boot / system volume | Yes | **No** |
| Removable media | Yes | No |
| Shrink volume | Yes | **No** |
| NTFS **disk quotas** (per user) | Yes | **No** |
| **FSRM** quotas/screens/classification | Yes | **No** (NTFS only) |
| Azure File Sync server endpoint | Yes | **No** (NTFS only) |
| Offloaded Data Transfer (ODX), transactions, object IDs, short names | Yes | No |
| BitLocker, ACLs, USN journal, sparse files, hard links, mount points, volume snapshots | Yes | Yes |
| Data Deduplication | Yes | Yes (Windows Server 2019 and later) |
| **Block cloning** (metadata-only copies; fast VHDX checkpoint merge) | No | **Yes** |
| **Sparse VDL** (near-instant fixed VHDX creation) | No | **Yes** |
| Mirror-accelerated parity | No | Yes (Storage Spaces Direct) |
| File-level snapshots | No | Yes (2022 and later) |
| File system encryption (EFS) | Yes | Only on Windows Server 2025 |

Rules of thumb for the exam:

* **ReFS** for Hyper-V VHDX storage on Storage Spaces Direct (CSVFS_ReFS), backup targets, and very large data volumes. Block cloning makes checkpoint merges and VHDX copies dramatically faster.
* **NTFS** for the OS volume, general-purpose file shares that need FSRM, NTFS quotas or Azure File Sync, SAN LUNs that rely on ODX or thin-provisioning UNMAP, and anything that might need to shrink.
* ReFS cluster sizes are 4 KB (default, recommended for most) or 64 KB (large sequential I/O). NTFS defaults to 4 KB clusters on volumes up to 16 TB.
* There is no in-place conversion between NTFS and ReFS: you reformat and copy.

`Set-FileIntegrity -FileName E:\Data -Enable $true` turns on integrity streams for a folder (new files inherit it); `Get-FileIntegrity` reports the state.

> **Watch out:** On SAN-backed Cluster Shared Volumes, ReFS-formatted CSVs do not use Direct I/O (they redirect through the coordinator node). Microsoft's guidance is NTFS for CSVs on SAN, ReFS for CSVs on Storage Spaces Direct.

## Data Deduplication

Data Deduplication (`Install-WindowsFeature FS-Data-Deduplication`) is **post-process**: files are written normally, then scheduled jobs split them into variable-size chunks, store unique chunks once in the **chunk store** (`System Volume Information\Dedup`) and replace the file with a reparse point. Reads are transparent.

### Usage types

| Usage type | Tuned for | Key defaults |
|---|---|---|
| **Default** | General-purpose file servers: team shares, home folders, Work Folders, software shares | Background optimization; minimum file age 3 days; skips in-use and partial files |
| **HyperV** | **VDI** VHDX files on a file server or local storage | Minimum age 3 days; optimizes in-use and partial files |
| **Backup** | **Virtualized backup** applications such as DPM writing to VHDX | Priority optimization; minimum age 0 days; optimizes in-use files |

```powershell
PS C:\> Enable-DedupVolume -Volume E: -UsageType Default
PS C:\> Set-DedupVolume -Volume E: -MinimumFileAgeDays 1 -ExcludeFolder E:\Scratch
PS C:\> Start-DedupJob -Volume E: -Type Optimization
PS C:\> Get-DedupJob
PS C:\> Get-DedupStatus | Format-List Volume, SavedSpace, SavingsRate, OptimizedFilesCount, InPolicyFilesCount
```

### Jobs

| Job | Purpose | Default schedule |
|---|---|---|
| Optimization | Chunk and compress in-policy files | Background, hourly |
| Garbage collection | Remove chunks no longer referenced | Weekly |
| Integrity scrubbing | Find and repair chunk-store corruption (uses hot-spot copies and, with Storage Spaces mirrors, the mirror copy) | Weekly |
| Unoptimization | Undo dedup for the whole volume (`Start-DedupJob -Type Unoptimization`), before you disable it | Manual only |

### Where it is and isn't supported

* Supported on NTFS, and on **ReFS since Windows Server 2019**; on Storage Spaces Direct volumes (mirror or parity); with Failover Clustering if every node has the feature; with **Storage Replica** (enable it only on the **source**, never on the destination, because the destination is read-only); with Azure File Sync cloud tiering; with DFS-R.
* Not supported on the **system or boot volume**, on removable drives, on volumes with multiple storage tiers, or inside a VM that runs on a host with nested virtualization enabled. A **hard** FSRM quota on the volume root is also unsupported (soft root quotas and subfolder quotas are fine).
* Files smaller than 32 KB, files with extended attributes, and EFS-encrypted files are not optimized.
* Not recommended for always-busy workloads with no idle time, such as SQL Server databases or Exchange stores.

`Expand-DedupFile` rehydrates an individual file (for example before moving it to a volume without dedup). `ddpeval.exe` (installed with the feature) estimates savings on any volume before you enable it.

### ReFS deduplication and compression (Windows Server 2025)

Windows Server 2025 adds a separate, ReFS-native engine: `Enable-ReFSDedup -Volume E: -Type Dedup|DedupAndCompress|Compress` and `Start-ReFSDedupJob`. It uses block cloning to share identical blocks and is aimed at **active** workloads such as VDI on ReFS. It is not the same feature as classic Data Deduplication and the two are not enabled together on one volume.

> **Exam tip:** "Newly copied files show no savings yet" = they are younger than `MinimumFileAgeDays` (3 days by default for Default and HyperV). "Enable dedup on C:" = not supported, move the data to a data volume.

> **Real world:** Dedup savings on general file shares are typically 30-50%; software deployment shares and VHD libraries do much better. Run `ddpeval` first and plan garbage collection before you expect space back after mass deletes.

## Lab it yourself

On a Windows Server 2025 VM with two extra 20 GB virtual disks:

```powershell
PS C:\> Get-Disk | Where-Object PartitionStyle -eq RAW | Initialize-Disk -PartitionStyle GPT -PassThru | New-Partition -UseMaximumSize -AssignDriveLetter | Format-Volume -FileSystem NTFS -Confirm:$false
PS C:\> Install-WindowsFeature FS-Data-Deduplication
PS C:\> Enable-DedupVolume -Volume E: -UsageType Default
PS C:\> Set-DedupVolume -Volume E: -MinimumFileAgeDays 0
PS C:\> 1..20 | ForEach-Object { Copy-Item C:\Windows\System32\shell32.dll "E:\copy$_.dll" }
PS C:\> Start-DedupJob -Volume E: -Type Optimization -Wait
PS C:\> Get-DedupStatus -Volume E:
```

Format the other disk as ReFS and try `Resize-Partition` to a smaller size: it fails, illustrating that ReFS cannot shrink.

## Key takeaways

* MBR caps usable space at 2 TiB and four primary partitions; use GPT for data disks larger than 2 TB and for UEFI boot.
* `Initialize-Disk`, `New-Partition`, `Format-Volume`, `Resize-Partition` with `Get-PartitionSupportedSize` cover most disk tasks; NTFS can shrink, ReFS cannot.
* ReFS: integrity streams, online repair on mirror/parity spaces, block cloning and sparse VDL for Hyper-V; no boot, no disk quotas, no FSRM, no Azure File Sync endpoints.
* Dedup usage types: Default (file server), HyperV (VDI), Backup (virtualized backup); minimum file age defaults to 3 days except Backup.
* Dedup is unsupported on system/boot volumes; with Storage Replica enable it on the source only.
* Windows Server 2025 adds ReFS-native dedup and compression (`Enable-ReFSDedup`) for active workloads.
