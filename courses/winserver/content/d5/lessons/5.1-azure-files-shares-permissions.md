## What Azure Files is (and what it is not)

Azure Files is a managed file service: Microsoft runs the "file server" and you consume SMB (or NFS) shares that live inside an Azure storage account. For AZ-802 you care about the **SMB** side, because that is what Windows Server and Windows clients mount, what Azure File Sync syncs with, and what identity-based authentication applies to.

Things to keep straight from the start:

* The share is reached at `\\<account>.file.core.windows.net\<share>`. SMB means **TCP 445** from the client to Azure.
* There is no Windows Server to log on to. You manage the share with the Azure portal, Az PowerShell, or the `az` CLI, and you manage files/ACLs over SMB like any other share.
* A storage account supports **one identity source at a time** for SMB authentication.

## Creating shares: media tier, billing model, redundancy

Four decisions drive cost and capability.

| Decision | Options | Exam notes |
|---|---|---|
| Media tier | **SSD** (historically "premium") or **HDD** (historically "standard") | SSD gives consistent low latency; NFS shares require SSD |
| Billing model | **Provisioned v2**, provisioned v1, **pay-as-you-go** | Microsoft recommends provisioned v2 for new deployments |
| Redundancy | LRS, ZRS, GRS, GZRS | Geo options are HDD only |
| Resource model | Classic share in a storage account | The newer Microsoft.FileShares model is NFS-only, so not relevant for SMB |

### Provisioned v2

You provision **storage, IOPS and throughput independently** and pay for what you provision, not what you use. The storage account kind is **FileStorage**, with SKUs such as `PremiumV2_LRS` (SSD) or `StandardV2_LRS` / `StandardV2_GRS` (HDD). Increases take effect in minutes; a decrease is only allowed 24 hours after the last increase. This is the answer whenever a scenario says "predictable cost" or "provision IOPS separately from capacity".

### Pay-as-you-go access tiers (HDD only)

Pay-as-you-go shares live in a **StorageV2** account and you choose an access tier per share:

| Tier | At-rest price | Transaction price | Use for |
|---|---|---|---|
| Transaction optimized | Highest | Lowest | Transaction-heavy workloads, **and the initial migration** |
| Hot | Middle | Middle | General-purpose team shares |
| Cool | Lowest | Highest (plus data retrieval charges) | Archive-style data that is rarely read |

All three tiers run on the same HDD hardware: the tier changes the *price*, not the performance. A migration generates a burst of transactions, so Microsoft's guidance is to start in transaction optimized and move to hot or cool after you have seen a few weeks of real usage. Moving a share between tiers is billed as transactions on the data being moved (plus data retrieval when leaving cool), so do it once after you have usage data rather than repeatedly.

### Creating a share

```powershell
PS C:\> New-AzStorageAccount -ResourceGroupName RG1 -Name storage1 -Location eastus -SkuName Standard_LRS -Kind StorageV2
PS C:\> New-AzRmStorageShare -ResourceGroupName RG1 -StorageAccountName storage1 -Name share1 -QuotaGiB 1024 -AccessTier TransactionOptimized
```

The `az` equivalent is `az storage share-rm create --resource-group RG1 --storage-account storage1 --name share1 --quota 1024 --access-tier TransactionOptimized`.

Other share-management tasks you should recognise: **share snapshots** (read-only, point-in-time, browsable from *Previous Versions*), **soft delete** for shares (on by default for new accounts, 7 days), and changing the quota or provisioned size.

## Networking: the port 445 problem

On-premises clients frequently cannot reach Azure Files because ISPs and corporate firewalls block outbound TCP 445. Diagnose it first:

```powershell
PS C:\> Test-NetConnection -ComputerName storage1.file.core.windows.net -Port 445
```

`TcpTestSucceeded : False` means the path is blocked. Your options, in the order an exam usually prefers them:

1. **VPN (site-to-site or point-to-site) or ExpressRoute private peering** to a **private endpoint** for the storage account. SMB then rides inside the tunnel.
2. **Azure File Sync** on a local Windows Server, so users hit the local server over SMB and the server talks to Azure over **HTTPS 443**.
3. **SMB over QUIC through Azure File Sync**: Azure Files does not speak QUIC itself, but a Windows Server VM running Azure File Sync (any edition of Windows Server 2025, or Windows Server 2022 Datacenter: Azure Edition) can publish the data over UDP 443.
4. Ask the ISP or network team to open 445 outbound to Azure ranges.

Two other connection failures to recognise: clients that cannot do **SMB 3.x encryption** are rejected from outside the Azure region (and when *secure transfer required* is on), and clients forced to **NTLMv1** are rejected (Azure Files accepts NTLMv2 with the account key, or Kerberos).

## Authentication: account key vs identity-based

The **storage account key** is a superuser credential. Mounting with it bypasses share-level RBAC and NTFS ACLs, which is exactly why it is useful for one-time admin work (for example, running Robocopy with `/B` during migration) and why it is a poor choice for users.

```text
C:\> net use Z: \\storage1.file.core.windows.net\share1 /user:localhost\storage1 <storage-account-key>
```

For users, enable an **identity source** on the storage account:

| Identity source | Who authenticates | Client needs | Typical use |
|---|---|---|---|
| **On-premises AD DS** | Your DCs issue Kerberos tickets | Line of sight to a DC (on-prem or VPN) | Replacing an on-prem file server |
| **Microsoft Entra Domain Services** | Microsoft-managed DCs | Client joined to the managed domain | Lift-and-shift apps in Azure |
| **Microsoft Entra Kerberos** | Entra ID issues the Kerberos ticket | Entra joined or hybrid joined client; no DC line of sight needed | Hybrid users working from the internet; cloud-only identities (in preview) |

For AD DS you represent the storage account as a computer (or service logon) account in AD using the **AzFilesHybrid** module:

```powershell
PS C:\> Import-Module AzFilesHybrid
PS C:\> Join-AzStorageAccount -ResourceGroupName RG1 -StorageAccountName storage1 -DomainAccountType ComputerAccount -OrganizationalUnitDistinguishedName "OU=AzureFiles,DC=contoso,DC=com"
```

That AD account has a password tied to a storage account Kerberos key. If your domain expires that password, authentication breaks until you rotate it, so place it in an OU where expiry does not apply or schedule the rotation. `Debug-AzStorageAccountAuth` (also in AzFilesHybrid) runs a battery of checks when something fails.

For Entra Kerberos you enable it on the account (`Set-AzStorageAccount ... -EnableAzureActiveDirectoryKerberosForFile $true`), grant admin consent to the storage account's app registration, and configure clients to retrieve cloud Kerberos tickets. A classic gotcha: Entra Kerberos does **not** support MFA for the file share, so if a Conditional Access policy requires MFA for all cloud apps, mounting fails (for example with system error 1327) until you **exclude the storage account's app** from that policy.

## Authorization: two layers, like a Windows file server

Access is the intersection of two permission sets, exactly as on Windows Server.

1. **Share-level permission** = Azure RBAC role assigned to a Microsoft Entra identity (or a default for everyone).
2. **Directory/file-level permission** = Windows ACLs (NTFS-style) on the files, enforced against the AD identity.

### Share-level RBAC roles

| Role | Grants | Windows share equivalent |
|---|---|---|
| Storage File Data SMB Share Reader | Read | Read |
| Storage File Data SMB Share Contributor | Read, write, delete | No exact equivalent (Change without ACL edits) |
| Storage File Data SMB Share Elevated Contributor | Read, write, delete, **modify ACLs** | Change |
| Storage File Data Privileged Reader / Privileged Contributor | Read (or read/write/delete/ACL) **overriding** existing ACLs | No Windows equivalent |
| Storage File Data SMB Admin | Admin access equivalent to the account key, over SMB (can `takeown` and then fix ACLs) | Administrator-level access |

Roles are assigned at the share scope (`.../fileServices/default/fileshares/share1`) or above. Changes usually take effect within about 30 minutes, occasionally longer.

Because the RBAC assignment is made to an **Entra ID** object while the ACL is checked against the **AD** object, the users or groups you assign must be **synced** with Entra Connect Sync or Cloud Sync. Assign roles to synced groups rather than to individual users where you can.

### Default share-level permission

You can instead set one share-level role for **all authenticated identities** on the storage account. It defaults to **None** (no access). Use it when:

* Identities are **not synced** to Entra ID (gMSAs, sMSAs, computer accounts, or a forest that syncs to a different tenant).
* You want Windows ACLs to be the only real access control.

If a user has both an explicit role and the default, the **higher** permission wins.

```powershell
PS C:\> Set-AzStorageAccount -ResourceGroupName RG1 -Name storage1 -DefaultSharePermission StorageFileDataSmbShareContributor
```

### Windows ACLs

Configure ACLs over SMB with File Explorer or `icacls`. Mount the share with an identity that has an admin-level role (or the account key) first, otherwise you cannot change permissions you do not already own. With AD DS the client needs line of sight to a DC to resolve names. With Entra Kerberos for hybrid users, `icacls` still needs DC line of sight; File Explorer editing works if you supplied the domain name and GUID when enabling Entra Kerberos.

> **Exam tip:** "User has the correct NTFS permissions but gets Access is denied" almost always means no share-level permission: either no RBAC role is assigned to the synced identity, or the default share permission is still **None**.

> **Watch out:** Granting **Contributor** or **Owner** on the storage account is control-plane access (manage the resource). It does not give a user SMB data access to files. Use the Storage File Data SMB roles.

> **Real world:** Keep one share per storage account when you are on pay-as-you-go. Transaction metrics are reported per account, so mixing shares makes tier decisions guesswork.

## Lab it yourself

On a free Azure account and a Windows Server 2025 VM (or your workstation):

```powershell
PS C:\> Connect-AzAccount
PS C:\> New-AzResourceGroup -Name RG1 -Location eastus
PS C:\> New-AzStorageAccount -ResourceGroupName RG1 -Name stlab$(Get-Random -Maximum 99999) -Location eastus -SkuName Standard_LRS -Kind StorageV2
PS C:\> $sa = Get-AzStorageAccount -ResourceGroupName RG1 | Select-Object -First 1
PS C:\> New-AzRmStorageShare -ResourceGroupName RG1 -StorageAccountName $sa.StorageAccountName -Name share1 -QuotaGiB 100
PS C:\> Test-NetConnection -ComputerName "$($sa.StorageAccountName).file.core.windows.net" -Port 445
```

If the port test succeeds, copy the **Connect** script from the portal (share > Connect) and mount with the key. Then look at the **Access Control (IAM)** blade on the share to see the Storage File Data SMB roles, and at **Identity-based access** on the account to see the identity sources. Delete the resource group when finished.

## Key takeaways

* Provisioned v2 (FileStorage account) lets you provision storage, IOPS and throughput separately and is Microsoft's default recommendation; pay-as-you-go tiers are transaction optimized, hot and cool, priced differently on the same HDD hardware.
* Start a pay-as-you-go migration in transaction optimized, then pick hot or cool from real usage.
* SMB to Azure Files needs TCP 445; when it is blocked use VPN/ExpressRoute with a private endpoint, or Azure File Sync (HTTPS 443).
* Identity sources: AD DS, Entra Domain Services, or Entra Kerberos (hybrid identities; cloud-only in preview; no DC line of sight). Only one per storage account.
* Share-level access is Azure RBAC on synced Entra identities; file-level access is Windows ACLs. Effective access is the intersection.
* Default share-level permission starts at None and is the fix for non-synced identities such as gMSAs and computer accounts.
* The storage account key bypasses all permissions; reserve it for admin tasks.
