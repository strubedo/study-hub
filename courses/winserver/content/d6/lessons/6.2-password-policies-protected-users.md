## The domain password policy

Every AD DS domain has exactly **one** default password and lockout policy for domain accounts. It is read from the **Account Policies** section of a GPO linked at the **domain root** (normally the Default Domain Policy), and DCs store the result as attributes of the domain object.

| Setting (Default Domain Policy, out of the box) | Value |
|---|---|
| Enforce password history | 24 passwords |
| Maximum password age | 42 days |
| Minimum password age | 1 day |
| Minimum password length | 7 characters |
| Password must meet complexity requirements | Enabled |
| Store passwords using reversible encryption | Disabled |

```powershell
PS C:\> Get-ADDefaultDomainPasswordPolicy
PS C:\> Set-ADDefaultDomainPasswordPolicy -Identity contoso.com -MinPasswordLength 14 -LockoutThreshold 10 -LockoutDuration 00:15:00 -LockoutObservationWindow 00:15:00
```

`Set-ADDefaultDomainPasswordPolicy` writes the domain object directly. If the Default Domain Policy GPO defines the same settings, its values are written back at the next security policy refresh, so make lasting changes in the GPO.

> **Watch out:** Account Policies in a GPO linked to an **OU** do not change the policy for domain users. They apply to the **local** SAM accounts of computers in that OU. To give a subset of domain users a different policy, use a fine-grained password policy.

## Fine-grained password policies (PSOs)

A **Password Settings Object (PSO)** holds a complete password and lockout policy and is stored in `CN=Password Settings Container,CN=System,DC=contoso,DC=com`. PSOs require domain functional level 2008 or later (any supported Windows Server 2025 domain qualifies).

Rules to memorise:

- A PSO can be applied to **users** and **global security groups** only. It cannot be linked to an OU; use a group that mirrors the OU (a "shadow group") instead.
- Every PSO has a **precedence** value (`msDS-PasswordSettingsPrecedence`). **Lower number = higher priority.**
- A PSO linked **directly to the user** always beats PSOs that reach the user through groups, whatever the precedence numbers.
- If several PSOs apply the same way, the lowest precedence wins (ties are broken by the lowest object GUID).
- If no PSO applies, the domain policy applies.
- Each PSO must define every setting; there is no merging between PSOs or with the domain policy.
- `LockoutObservationWindow` cannot be longer than `LockoutDuration`.

```powershell
PS C:\> New-ADFineGrainedPasswordPolicy -Name "PSO-Admins" -Precedence 10 -MinPasswordLength 16 -ComplexityEnabled $true -PasswordHistoryCount 24 -MaxPasswordAge 60.00:00:00 -MinPasswordAge 1.00:00:00 -LockoutThreshold 5 -LockoutDuration 00:30:00 -LockoutObservationWindow 00:30:00 -ReversibleEncryptionEnabled $false
PS C:\> Add-ADFineGrainedPasswordPolicySubject -Identity "PSO-Admins" -Subjects "Tier0-Admins"
PS C:\> Get-ADFineGrainedPasswordPolicySubject -Identity "PSO-Admins"
PS C:\> Get-ADUserResultantPasswordPolicy -Identity Admin1
```

In Active Directory Administrative Center, the **Password Settings Container** shows PSOs, and right-clicking a user and selecting **View resultant password settings** shows the winning PSO.

> **Exam tip:** Given a table of PSOs, first look for one applied **directly** to the user; if there is one, it wins. Only when none is direct do you compare the **lowest precedence** among group-applied PSOs. Domain local and universal groups do not count; only global security groups do.

## Microsoft Entra Password Protection for AD DS

Complexity rules alone allow passwords like `Contoso2026!`. Microsoft Entra Password Protection checks new passwords against the **global banned password list** (maintained by Microsoft from attack data) and your **custom banned password list** (up to 1,000 terms such as company and product names), using normalisation and fuzzy matching so that `C0nt0s0!2026` is caught too.

It requires **Microsoft Entra ID P1 or P2** licensing for the users it protects.

### Components

| Component | Where it runs | What it does |
|---|---|---|
| **Proxy service** | One or more domain-joined member servers (two for high availability) with outbound HTTPS to Microsoft Entra ID | Downloads password policy from Entra ID on behalf of the DCs |
| **DC agent service** and password filter DLL | **Every writable** domain controller (RODCs forward password changes and do not need it) | Receives every password change/set, evaluates it against the locally cached policy, returns pass or fail |

- DC agents **never need internet access**. They find proxies through service connection point objects in AD and talk to them over RPC.
- The downloaded policy is cached in **SYSVOL** so every DC in the domain shares it. The domain must use **DFSR** for SYSVOL replication; the agent installs on an FRS domain but does not work properly there.
- Installing the DC agent requires a **restart** of each DC.
- It validates passwords only when they are **changed or reset**; existing passwords are not scanned.
- It works **in addition** to AD password policy and PSOs; a password must satisfy all of them.
- If a DC agent has no policy yet, it accepts passwords and logs a warning.

### Deployment order

1. Install the proxy on member servers and register it: `Register-AzureADPasswordProtectionProxy` (Global Administrator the first time in a tenant, Security Administrator afterwards).
2. Register the forest once: `Register-AzureADPasswordProtectionForest` (also needs Enterprise Admin rights on premises).
3. Install the DC agent on every writable DC and restart each (the filter DLL loads only at boot).
4. In the Microsoft Entra admin center (**Entra ID > Authentication methods > Password protection**), set **Enable password protection on Windows Server Active Directory** to **Yes** and **Mode** to **Audit**.
5. Review the DC agent **Admin** event log (`Applications and Services Logs\Microsoft\AzureADPasswordProtection\DCAgent\Admin`) to see which passwords would have been rejected.
6. Switch **Mode** to **Enforced**.

```powershell
PS C:\> Import-Module AzureADPasswordProtection
PS C:\> Register-AzureADPasswordProtectionProxy -AccountUpn admin@contoso.onmicrosoft.com
PS C:\> Register-AzureADPasswordProtectionForest -AccountUpn admin@contoso.onmicrosoft.com
PS C:\> Get-AzureADPasswordProtectionDCAgent
PS C:\> Test-AzureADPasswordProtectionProxyHealth -TestAll
```

The `AzureADPasswordProtection` module is installed with the proxy and, in current versions, with the DC agent too; on a DC, `Test-AzureADPasswordProtectionDCAgentHealth -TestAll` checks the filter DLL, forest registration, DFSR and connectivity.

| Mode | Weak password result |
|---|---|
| Audit (default) | Accepted, but logged as "would have been rejected" |
| Enforced | Rejected with the usual "does not meet the length, complexity, or history requirements" error |
| Enable on Windows Server AD = No | DC agents are quiescent; nothing is validated or logged |

> **Watch out:** In enforced mode, automation that sets weak passwords breaks, including DC promotion with a weak DSRM password and DC demotion with a weak local Administrator password. Run at least one promotion and demotion during the audit period.

> **Exam tip:** A DC agent log full of events saying it **cannot locate a proxy** (event 30017) means no proxy is registered yet or replication has not delivered the proxy's service connection point. Register the proxy and wait for or force AD replication.

## The Protected Users group

**Protected Users** (a global group in the Users container) applies non-configurable hardening to its members. You cannot turn individual protections off; you leave the group.

| Where | Protection |
|---|---|
| On the device the member signs in to | No CredSSP or WDigest plaintext caching; no NTLM NTOWF caching; Kerberos does not create DES/RC4 keys or keep long-term keys after the TGT; **no cached logon verifier, so no offline sign-in** |
| On domain controllers (DFL 2012 R2 or later) | Member **cannot use NTLM**; no DES or RC4 in Kerberos pre-authentication; **cannot be delegated** (constrained or unconstrained); **TGT lifetime 4 hours, not renewable** |

Who should be a member: highly privileged **user** accounts (Domain Admins, Enterprise Admins, tier 0 operators) after testing.

Who should **not** be a member:

- **Service accounts and computer accounts**: authentication fails ("the user name or password is incorrect") because their secrets live on the host and the group offers them no benefit. Use gMSAs or dMSAs instead.
- Accounts that must sign in **offline** (laptops away from a DC).
- Accounts used by applications that only support NTLM, or that rely on delegation.
- At least one break-glass account, so a misconfiguration cannot lock you out of every admin account.

Troubleshooting logs (disabled by default): `Applications and Services Logs > Microsoft > Windows > Authentication > ProtectedUser-Client` and `ProtectedUserFailures-DomainController`.

> **Real world:** If you need the "cannot be delegated" protection for an account that cannot join Protected Users, set **Account is sensitive and cannot be delegated** on the account instead. To enforce a 4-hour TGT for other accounts, use an **authentication policy**.

## Lab it yourself

On DC1 (Windows Server 2025 evaluation) with a test user Admin1 and a global group Tier0-Admins:

```powershell
PS C:\> New-ADFineGrainedPasswordPolicy -Name PSO-Test -Precedence 20 -MinPasswordLength 20 -ComplexityEnabled $true -PasswordHistoryCount 24 -MaxPasswordAge 90.00:00:00 -MinPasswordAge 1.00:00:00 -LockoutThreshold 5 -LockoutDuration 00:15:00 -LockoutObservationWindow 00:15:00
PS C:\> Add-ADFineGrainedPasswordPolicySubject -Identity PSO-Test -Subjects Tier0-Admins
PS C:\> Add-ADGroupMember Tier0-Admins -Members Admin1
PS C:\> Get-ADUserResultantPasswordPolicy Admin1
PS C:\> Add-ADGroupMember "Protected Users" -Members Admin1
```

Sign in as Admin1 on a member server and run `klist` to see the 4-hour TGT; then try `net use \\10.0.0.10\c$` (by IP, which forces NTLM) and watch it fail.

## Key takeaways

- Domain password and lockout policy comes from the GPO linked at the domain; OU-linked account policies affect local accounts only.
- PSOs apply to users and global security groups; directly linked PSOs win; otherwise the lowest precedence number wins.
- Entra Password Protection: proxy on member servers (internet), DC agent on every writable DC (no internet), policy cached in DFSR-replicated SYSVOL, needs Entra ID P1/P2.
- Start in Audit mode, review the DCAgent Admin log, then switch to Enforced.
- Protected Users: no NTLM, no DES/RC4, no delegation, 4-hour non-renewable TGT, no offline sign-in.
- Never add service or computer accounts to Protected Users; keep a tested break-glass account outside it.
