## Why domain controllers are special

Whoever controls a domain controller controls every identity in the forest: they can read every password hash, create accounts, edit Group Policy and forge Kerberos tickets. Everything that can **manage** a DC is therefore equally sensitive: the hypervisor hosting it, its backups, the accounts that can sign in to it and the software running on it. Microsoft's **enterprise access model** calls this the **control plane** (the older tier model called it **Tier 0**).

## Harden the domain controller itself

| Control | How |
|---|---|
| Single purpose | Run only AD DS, DNS and (if required) DHCP. No web servers, file shares for users, management agents you do not need, or browsing. |
| Server Core | Smaller attack surface and fewer patches; manage remotely with RSAT, PowerShell and Windows Admin Center. |
| Patching | Patch DCs first and fast; they are the highest-value target. |
| Security baseline | Apply the **DomainController** baseline: OSConfig scenario `SecurityBaseline/WindowsServer/2025/DomainController`, or the Security Compliance Toolkit DC GPO linked to the Domain Controllers OU. |
| Disable unneeded services | For example, Microsoft recommends disabling the **Print Spooler** service on DCs. |
| Protect secrets at rest | BitLocker on physical DCs and on virtual DC disks (with a virtual TPM); restrict who can copy DC VHDX files or backups. |
| Virtualisation hosts | Treat Hyper-V hosts and their administrators that run DCs as Tier 0. A Hyper-V admin can mount the DC's disk and extract `ntds.dit`. |
| Protocol hardening | Require SMB signing (default on Windows Server 2025 for outbound connections, and always required for SYSVOL/NETLOGON); require LDAP signing and LDAP channel binding; disable SMBv1. |
| Auditing | Use Advanced Audit Policy on DCs (Credential Validation, Kerberos Authentication Service and Service Ticket Operations, Directory Service Changes, Security Group Management) and forward events to a SIEM. |
| DSRM password | Manage it with Windows LAPS (AD backup, encrypted). |
| Branch offices | Use an RODC where physical security is weak, with a Password Replication Policy that caches only local users. |

> **Watch out:** Do not try to "harden" a DC with Credential Guard; it is not enabled by default on DCs, protects nothing in the AD database and can break DC-hosted applications.

## Restrict access to domain controllers

### User rights assignment

Set these in a GPO linked to the **Domain Controllers** OU (or in the Default Domain Controllers Policy):

| User right | Recommended |
|---|---|
| Allow log on locally | Administrators only (remove operator groups if they are not used) |
| Allow log on through Remote Desktop Services | Administrators only (this is the default on DCs) |
| Deny log on locally / through Remote Desktop Services / as a batch job / as a service | Tier 1 and Tier 2 admin groups, service accounts that do not belong on DCs, Guests |
| Access this computer from the network | Leave the default set; do not add accounts (clients need this right to reach SYSVOL, LDAP and Kerberos-authenticated services) |

The mirror image matters too. Tier 0 accounts must not sign in to lower-tier machines, where their credentials could be stolen. In a GPO linked to member server and workstation OUs, **deny** Domain Admins, Enterprise Admins and the built-in Administrator the rights **Deny access to this computer from the network**, **Deny log on as a batch job**, **Deny log on as a service**, **Deny log on locally** and **Deny log on through Remote Desktop Services**.

> **Exam tip:** "Prevent members of Domain Admins from signing in to member servers" = **Deny** user rights in a GPO linked to the member servers OU. "Prevent server administrators from signing in to DCs" = **Deny** rights in a GPO linked to the **Domain Controllers** OU. Deny always beats allow.

### Privileged access workstations and authentication silos

- Administer Tier 0 only from a **privileged access workstation (PAW)**: a hardened, dedicated device with no email or web browsing, ideally with Credential Guard, App Control and a separate admin account. Jump servers in the control plane are acceptable when they are managed as Tier 0.
- **Authentication policies and silos** (DFL 2012 R2+) can make Kerberos refuse a TGT for Tier 0 accounts unless the request comes from an approved device (a PAW or DC), and can set a short TGT lifetime. They require Kerberos armoring to know which device the user is on (see the authentication lesson).
- Protect Tier 0 user accounts with **Protected Users**, smart cards or FIDO2/Windows Hello for Business where supported, and separate admin and day-to-day accounts.

## Built-in administrative groups

| Group | Scope and reach | Recommendation |
|---|---|---|
| **Enterprise Admins** | Forest root domain; Administrators in every domain | Empty except while performing forest-wide changes |
| **Schema Admins** | Forest root domain; can modify the schema | Empty except during schema updates |
| **Domain Admins** | One domain; member of Administrators on every domain-joined computer by default | Very few members; used only to manage DCs and the domain |
| **Administrators** (built-in, domain) | Full control of DCs and the domain | Contains Domain Admins and Enterprise Admins; keep direct membership minimal |
| **Account Operators**, **Server Operators**, **Backup Operators**, **Print Operators** | Legacy delegation groups; can sign in to DCs locally by default and have powerful rights (Backup Operators can read any file, including `ntds.dit`) | **Keep empty**; use delegation on OUs instead |
| **DnsAdmins** | Manage DNS servers on DCs | Treat as Tier 0; members can configure the DNS service to load code that runs as SYSTEM on DCs |
| **Group Policy Creator Owners** | Can create GPOs | Limit membership; GPOs linked to the Domain Controllers OU run on DCs |
| **Protected Users** | Hardening for members | Add privileged user accounts after testing |

### The built-in Administrator account

The domain's built-in Administrator (RID 500) is the account of last resort. It is always exempt from authentication policies, even when assigned to a silo, so silos cannot fence it in. Give it a long random password stored in a vault, enable **Account is sensitive and cannot be delegated** and **Smart card is required for interactive logon** where practical, deny it sign-in to member computers with the rights above, and audit every use.

### AdminSDHolder and SDProp

Members of protected groups get special treatment:

- The object `CN=AdminSDHolder,CN=System,DC=contoso,DC=com` holds a template ACL.
- The **SDProp** process runs on the **PDC emulator** every **60 minutes** and stamps that ACL onto every protected account and group (members of Domain Admins, Enterprise Admins, Schema Admins, Administrators, the operator groups, Domain Controllers, krbtgt and others), sets **adminCount = 1** and **disables inheritance** on them.

Consequences you will see on the exam:

- Delegating "Reset password" on an OU does **not** let help desk reset passwords of admins in that OU, because their ACL comes from AdminSDHolder and does not inherit OU permissions. This is by design.
- Permissions you add directly to a protected account disappear within an hour.
- An account removed from all protected groups keeps `adminCount = 1` and a non-inheriting ACL until you clear them yourself.

```powershell
PS C:\> Get-ADUser -LDAPFilter "(adminCount=1)" | Select-Object Name, DistinguishedName
PS C:\> Get-ADGroupMember "Domain Admins" -Recursive | Select-Object Name, ObjectClass
PS C:\> Get-ADGroupMember "Account Operators"
```

> **Watch out:** Never "fix" AdminSDHolder behaviour by granting the help desk rights on the AdminSDHolder object itself; that gives them control over every privileged account. Use a separate process (or a privileged identity tool) for admin password resets.

## Monitoring privileged groups

- Alert on changes to Domain Admins, Enterprise Admins, Schema Admins, Administrators and the operator groups (Security Group Management auditing on DCs).
- Review membership regularly, including nested groups (`-Recursive`).
- Remove standing membership where possible and add people only when needed, then remove them again.

## Lab it yourself

On DC1 in a lab domain:

```powershell
PS C:\> New-ADOrganizationalUnit -Name "Tier0-Accounts"
PS C:\> New-ADUser -Name "T0-Admin1" -Path "OU=Tier0-Accounts,DC=contoso,DC=com" -AccountPassword (Read-Host -AsSecureString) -Enabled $true
PS C:\> Add-ADGroupMember "Domain Admins" -Members "T0-Admin1"
PS C:\> Get-ADUser T0-Admin1 -Properties adminCount, nTSecurityDescriptor | Select-Object Name, adminCount, @{n='InheritanceBlocked';e={$_.nTSecurityDescriptor.AreAccessRulesProtected}}
```

Run the last command immediately and again after an hour (or after forcing SDProp) to watch `adminCount` become 1 and inheritance become blocked. Then build a GPO on a member-server OU that denies Domain Admins every logon right, and confirm T0-Admin1 cannot sign in to a member server.

## Key takeaways

- Anything that can manage a DC (hosts, backups, admins, agents) is Tier 0 / control plane.
- Harden DCs: single role, Server Core, fast patching, the DomainController baseline, Print Spooler disabled, BitLocker, LDAP and SMB signing.
- Restrict DC sign-in with user rights on the Domain Controllers OU; deny Tier 0 accounts on lower tiers.
- Administer Tier 0 from PAWs; use authentication policy silos to bind Tier 0 accounts to Tier 0 devices.
- Keep Enterprise Admins, Schema Admins and the operator groups empty; treat DnsAdmins as Tier 0.
- SDProp (PDC emulator, every 60 minutes) applies the AdminSDHolder ACL and adminCount = 1 to protected accounts, which overrides OU delegation.
