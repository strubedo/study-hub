## Credential Guard

Credential Guard uses **virtualization-based security (VBS)** to move the secrets that LSASS normally holds (NTLM hashes, Kerberos TGTs and the keys that protect them) into an isolated process, **LsaIso.exe**, running in a separate virtual trust level. Even an attacker with SYSTEM or kernel access in the normal OS cannot read them, which defeats most pass-the-hash and pass-the-ticket tooling.

### Default enablement on Windows Server 2025

Starting with Windows Server 2025, Credential Guard is **on by default** (without UEFI lock) when **all** of these are true:

1. The server meets the license requirements.
2. The hardware and firmware meet the VBS requirements.
3. Credential Guard has not been **explicitly disabled** (an explicit disable set before the upgrade is preserved).
4. The server is **joined to a domain**.
5. The server is **not a domain controller**.

So a domain-joined Windows Server 2025 member server on capable hardware will usually be running Credential Guard after setup or upgrade, while DCs and workgroup servers will not. On DCs it adds no value anyway: it does not protect the AD database (`ntds.dit`), and it can break some applications that DCs host.

### Requirements

| Requirement | Notes |
|---|---|
| 64-bit CPU with virtualization extensions (Intel VT-x or AMD-V) and SLAT | Needed for VBS |
| UEFI firmware | Required for the UEFI lock option |
| Secure Boot | Recommended; not a hard requirement for VBS to start |
| TPM 1.2 or 2.0 | Recommended; protects the VBS keys |
| Hyper-V VMs | Generation 2 VM; enable a virtual TPM; Credential Guard then protects secrets inside the VM but not from a compromised host |

### Configure and verify

Group Policy: **Computer Configuration > Administrative Templates > System > Device Guard > Turn On Virtualization Based Security**, then **Credential Guard Configuration**:

| Value | Meaning |
|---|---|
| Enabled with UEFI lock | Settings are stored in firmware; turning it off remotely is not possible (needs local action at boot) |
| Enabled without lock | Can be turned off later by policy; this is what default enablement uses |
| Disabled | Explicitly off; prevents default enablement |

The registry equivalent is `HKLM\SYSTEM\CurrentControlSet\Control\Lsa\LsaCfgFlags` (1 = with UEFI lock, 2 = without lock, 0 = disabled).

```powershell
PS C:\> (Get-CimInstance -ClassName Win32_DeviceGuard -Namespace root\Microsoft\Windows\DeviceGuard).SecurityServicesRunning
1
PS C:\> Get-Process LsaIso
```

In `SecurityServicesRunning`, **1 = Credential Guard** and 2 = memory integrity (HVCI). `msinfo32` shows the same under **Virtualization-based security Services Running**.

### What Credential Guard breaks

| Blocked completely | Single sign-on blocked (user is prompted instead) |
|---|---|
| Kerberos **unconstrained delegation** | NTLMv1 |
| Kerberos **DES** encryption | MS-CHAPv2 (for example PEAP-MSCHAPv2 Wi-Fi or VPN) |
| PKINIT with RSA key exchange | Digest authentication |
| | CredSSP with saved or default credentials |

> **Watch out:** On Windows Server 2025, Hyper-V **live migration that uses CredSSP** fails from a source host that runs Credential Guard. Configure hosts to use **Kerberos constrained delegation** (or resource-based constrained delegation) for live migration instead of disabling Credential Guard.

What it does **not** protect: local accounts and Microsoft accounts, the AD database on DCs, keyloggers, credentials typed into an application that uses NTLM, Kerberos service tickets (the TGT is protected) and physical attacks.

> **Exam tip:** "Protect domain credentials on member servers from memory-scraping tools" = Credential Guard. "Do not send reusable credentials to the remote host during an RDP session" = **Remote Credential Guard** or Restricted Admin mode, which are RDP client features, not the same thing.

## Securing the OS with Group Policy

Most server hardening is still done with GPO **Security Settings** (Computer Configuration > Policies > Windows Settings > Security Settings).

| Area | Examples of what to set |
|---|---|
| Account Policies | Password, lockout and Kerberos policy. For **domain accounts** these only take effect in a GPO linked at the **domain** (normally the Default Domain Policy); at OU level they affect local accounts only |
| Local Policies > User Rights Assignment | Who may log on locally, through RDS, as a service or batch job; deny rights for privileged groups on lower tiers |
| Local Policies > Security Options | Rename the Administrator account, LAN Manager authentication level (send NTLMv2 only, refuse LM and NTLM), SMB signing, anonymous enumeration, UAC behaviour, NTLM restriction settings |
| Advanced Audit Policy Configuration | Granular subcategories such as Credential Validation, Kerberos Authentication Service, Directory Service Changes |
| Restricted Groups / Preferences: Local Users and Groups | Control membership of local Administrators |
| System Services, Registry, File System | Service start modes and ACLs |
| Windows Defender Firewall with Advanced Security | Profiles, rules, connection security rules |

When you use Advanced Audit Policy, also enable **Audit: Force audit policy subcategory settings (Windows Vista or later) to override audit policy category settings** so legacy category settings do not overwrite the subcategories. Check the effective result with `auditpol /get /category:*`.

Tools that help:

- **Security Compliance Toolkit**: Microsoft's baselines as GPO backups you can import, plus **Policy Analyzer** (compare GPOs and local policy) and **LGPO.exe** (apply to standalone servers).
- **Security templates** (`.inf`) with `secedit /analyze` and `secedit /configure` for standalone servers.
- `gpresult /h report.html` and **Resultant Set of Policy** to see which GPO won.

```text
C:\> secedit /analyze /db C:\Temp\check.sdb /cfg C:\Baselines\MemberServer.inf /log C:\Temp\check.log
C:\> gpresult /scope computer /h C:\Temp\gp.html
C:\> auditpol /get /category:"Account Logon"
```

## Windows Server 2025 security baselines with OSConfig

**OSConfig** is the security configuration platform built into Windows Server 2025. Microsoft ships the Windows Server 2025 security baselines as OSConfig **scenarios** in the **Microsoft.OSConfig** PowerShell module. Compared with a GPO baseline, OSConfig adds **drift control**: if someone changes a managed setting locally, OSConfig puts it back on its next refresh (every four hours by default).

```powershell
PS C:\> Install-Module -Name Microsoft.OSConfig -Scope AllUsers -Repository PSGallery -Force
PS C:\> Get-Module -ListAvailable -Name Microsoft.OSConfig
PS C:\> Set-OSConfigDesiredConfiguration -Scenario SecurityBaseline/WindowsServer/2025/MemberServer -Default
PS C:\> Restart-Computer
```

| Server role | Scenario |
|---|---|
| Domain controller | `SecurityBaseline/WindowsServer/2025/DomainController` |
| Domain member | `SecurityBaseline/WindowsServer/2025/MemberServer` |
| Workgroup server | `SecurityBaseline/WindowsServer/2025/WorkgroupMember` |
| Secured-core settings | `SecuredCore` |
| Microsoft Defender Antivirus | `Defender/Antivirus/WindowsServer/2025` |
| Windows LAPS (member servers) | `LAPS/WindowsServer/2025/MemberServer` |

Earlier versions of the module used shorter scenario names such as `SecurityBaseline/WS2025/MemberServer`; check the names your installed module exposes.

### Verify, customise and remove

```powershell
PS C:\> Get-OSConfigDesiredConfiguration -Scenario SecurityBaseline/WindowsServer/2025/MemberServer | Format-Table Name, @{Name='Status'; Expression={$_.Compliance.Status}}, @{Name='Reason'; Expression={$_.Compliance.Reason}} -AutoSize -Wrap
PS C:\> Set-OSConfigDesiredConfiguration -Scenario SecurityBaseline/WindowsServer/2025/MemberServer -Setting AuditDetailedFileShare -Value 3
PS C:\> Remove-OSConfigDesiredConfiguration -Scenario SecurityBaseline/WindowsServer/2025/MemberServer
```

- Applying or removing a baseline **requires a restart**.
- Customising a setting with `-Setting` and `-Value` keeps drift control, now enforcing **your** value.
- Removing a baseline does not guarantee that every setting returns to its previous value.
- Some settings prompt for input when customised (for example the new name for the Administrator account or the logon banner text).
- For **Azure Arc-enabled** servers, the same baselines can be assigned through Azure Policy machine configuration; if the server's role changes later (for example it is promoted to a DC), delete and reapply the assignment so the new role is detected.

> **Exam tip:** "Apply Microsoft's recommended security settings to a Windows Server 2025 member server and automatically correct local changes" = OSConfig with the `MemberServer` scenario. A GPO also re-applies settings at refresh, but the AZ-802 objective names OSConfig specifically for the Windows Server 2025 baseline.

> **Watch out:** Pick the scenario that matches the server's role. Applying the member server baseline to a DC, or the DC baseline to a member, gives the wrong user rights and audit settings.

## Lab it yourself

On a domain-joined Windows Server 2025 evaluation VM (Generation 2 with Secure Boot and a virtual TPM enabled). If VBS does not start inside the VM, check the VBS status first; the output below tells you whether VBS itself is running before you look at Credential Guard:

```powershell
PS C:\> (Get-CimInstance -ClassName Win32_DeviceGuard -Namespace root\Microsoft\Windows\DeviceGuard) | Format-List VirtualizationBasedSecurityStatus, SecurityServicesConfigured, SecurityServicesRunning
PS C:\> Install-Module -Name Microsoft.OSConfig -Scope AllUsers -Repository PSGallery -Force
PS C:\> Set-OSConfigDesiredConfiguration -Scenario SecurityBaseline/WindowsServer/2025/MemberServer -Default
```

Restart, check compliance, then change one managed setting by hand (for example with `secpol.msc`) and watch OSConfig revert it after its refresh.

## Key takeaways

- Credential Guard isolates NTLM hashes and Kerberos TGTs in LsaIso.exe using VBS.
- Windows Server 2025 enables it by default on **domain-joined, non-DC** servers that meet requirements, without UEFI lock, unless explicitly disabled.
- It blocks unconstrained delegation and DES, and breaks SSO for NTLMv1, MS-CHAPv2, Digest and CredSSP; use Kerberos constrained delegation for Hyper-V live migration.
- Verify with `Win32_DeviceGuard` (`SecurityServicesRunning` contains 1) or msinfo32.
- Domain password and lockout policy for domain accounts must be set at the domain level.
- OSConfig applies the Windows Server 2025 baselines by role, enforces them with drift control and needs a restart.
