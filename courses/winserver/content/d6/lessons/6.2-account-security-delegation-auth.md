## Security options on user accounts

The **Account** tab of a user in Active Directory Users and Computers (and `Set-ADUser` / `Set-ADAccountControl`) holds several flags that attackers look for.

| Option | PowerShell | Use it? |
|---|---|---|
| Account is sensitive and cannot be delegated | `Set-ADAccountControl -AccountNotDelegated $true` | **Yes** for every privileged account; stops services impersonating it |
| Smart card is required for interactive logon | `Set-ADUser -SmartcardLogonRequired $true` | Yes for admins with smart cards. Setting it gives the account a random password hash; at DFL 2016+ you can have DCs roll that NTLM secret automatically |
| This account supports Kerberos AES 128 / 256 bit encryption | `Set-ADUser -KerberosEncryptionType AES128,AES256` | Yes, especially for service accounts with SPNs |
| Do not require Kerberos preauthentication | `Set-ADAccountControl -DoesNotRequirePreAuth $true` | **No.** Anyone can request an AS-REP for the account and crack it offline (AS-REP roasting) |
| Store password using reversible encryption | `Set-ADUser -AllowReversiblePasswordEncryption $true` | **No.** Equivalent to storing the plaintext password |
| Use only Kerberos DES encryption types | `Set-ADAccountControl -UseDESKeyOnly $true` | **No.** DES is removed in Windows Server 2025 |
| Password never expires | `Set-ADUser -PasswordNeverExpires $true` | Avoid; use gMSAs/dMSAs for services |
| Trusted for delegation (unconstrained) | `Set-ADAccountControl -TrustedForDelegation $true` | Avoid; use constrained or resource-based constrained delegation |
| Logon Hours / Log On To | `Set-ADUser -LogonWorkstations "PAW01,PAW02"` | Useful for restricting admin accounts (Log On To relies on NetBIOS names; authentication policy silos are stronger) |

Finding risky settings:

```powershell
PS C:\> Get-ADUser -Filter 'DoesNotRequirePreAuth -eq $true' | Select-Object SamAccountName
PS C:\> Get-ADComputer -Filter 'TrustedForDelegation -eq $true' | Select-Object Name
PS C:\> Get-ADUser -Filter 'ServicePrincipalName -like "*"' -Properties ServicePrincipalName, msDS-SupportedEncryptionTypes, PasswordLastSet
PS C:\> Search-ADAccount -PasswordNeverExpires -UsersOnly
```

User accounts with **SPNs** and human-chosen passwords are targets for **Kerberoasting** (requesting service tickets and cracking them offline). Replace them with **group managed service accounts** or, on Windows Server 2025, **delegated managed service accounts**, whose passwords are long, random and rotated automatically.

## Delegating administration in AD DS

Delegation means granting a group specific permissions on an OU (or a container) so it can do one job without being a Domain Admin.

### Delegation of Control Wizard

Right-click an OU in ADUC, select **Delegate Control**, add a **group** and choose a common task (for example *Reset user passwords and force password change at next logon*, *Create, delete, and manage user accounts*, *Modify the membership of a group*, *Manage Group Policy links*) or build a custom task (object types plus specific permissions or properties).

Facts the exam checks:

- The wizard only **adds** permissions; it cannot show or remove what it granted. To review or remove, use the **Advanced Security Settings** of the OU or `dsacls`.
- Permissions are inherited by child objects according to the "Applies to" setting, **except** for protected accounts (adminCount = 1), whose ACL is controlled by AdminSDHolder.
- Delegate to **groups**, not users, at the **highest OU** that covers the job, with the **least** permissions needed.

### dsacls

`dsacls` views and edits AD ACLs from the command line. Syntax for granting: `/G "group:permissions;object_or_property;inherited_object_type"` with an inheritance flag.

```text
C:\> dsacls "OU=Branch1,DC=contoso,DC=com"
C:\> dsacls "OU=Branch1,DC=contoso,DC=com" /I:S /G "CONTOSO\Branch1-HelpDesk:CA;Reset Password;user"
C:\> dsacls "OU=Branch1,DC=contoso,DC=com" /I:S /G "CONTOSO\Branch1-HelpDesk:WP;pwdLastSet;user"
C:\> dsacls "OU=Branch1,DC=contoso,DC=com" /I:S /G "CONTOSO\Branch1-HelpDesk:WP;lockoutTime;user"
C:\> dsacls "OU=Branch1,DC=contoso,DC=com" /R "CONTOSO\Branch1-HelpDesk"
```

| Code | Meaning |
|---|---|
| `CA` | Control access (extended rights such as Reset Password) |
| `WP` / `RP` | Write / read property |
| `CC` / `DC` | Create / delete child objects |
| `GA`, `GR`, `GW` | Generic all, read, write |
| `/I:T`, `/I:S`, `/I:P` | Inherit to this object and subobjects, subobjects only, or one level only |
| `/R` | Remove all permissions for the principal |

The three help desk lines above are the classic "reset passwords, force change at next logon, unlock accounts" set: Reset Password extended right, write `pwdLastSet`, write `lockoutTime`.

> **Exam tip:** "Help desk must reset passwords for users in an OU; minimise permissions" = Delegation of Control Wizard (or dsacls) on **that OU** with the reset-password task. Adding help desk to **Account Operators** grants far more (including sign-in to DCs).

Delegation for Group Policy is separate: the GPMC **Delegation** tab (or `Set-GPPermission`) controls who can edit, link or create GPOs.

## Authentication protocols and methods

### Kerberos first, NTLM as fallback

Domain clients use **Negotiate**, which picks Kerberos and falls back to NTLM when Kerberos cannot be used (for example when connecting by IP address without an SPN, or to a non-domain host). All NTLM is deprecated. Windows Server 2025 **removes the NTLMv1 protocol**; LANMAN and NTLMv2 are deprecated but still work. Leftover NTLMv1-derived credentials (used for MS-CHAPv2 single sign-on, for example PEAP-MSCHAPv2) are controlled by the `BlockNtlmv1SSO` registry value in `HKLM\SYSTEM\CurrentControlSet\Control\Lsa\MSV1_0`: since the October 2026 security update the default, when the value is absent, is Enforce (block). Devices running Credential Guard already block that SSO.

### Kerberos encryption types

- Prefer **AES256** and AES128. **DES is removed** in Windows Server 2025, and **RC4** use in Kerberos is deprecated. The 2026 Kerberos updates for CVE-2026-20833 (audit from January, enforcement from April, final in July 2026) make DCs stop assuming RC4 for accounts with no `msDS-SupportedEncryptionTypes` value; accounts that explicitly allow only RC4 still get RC4 tickets until you change them.
- Control them with **Network security: Configure encryption types allowed for Kerberos** (Security Options) and per account with `msDS-SupportedEncryptionTypes`.
- After a suspected compromise of the domain, reset the **krbtgt** password **twice** (allowing replication between resets) to invalidate forged TGTs.

### Kerberos armoring (FAST)

Kerberos armoring (Flexible Authentication Secure Tunneling, RFC 6113) wraps the user's AS exchange in a tunnel protected by the **computer's** TGT. It defeats offline cracking of pre-authentication data, gives signed KDC errors and tells the KDC which device the user is on (needed by authentication policies and compound identity).

| Policy | Location | Values |
|---|---|---|
| **KDC support for claims, compound authentication and Kerberos armoring** | Computer Configuration > Administrative Templates > System > **KDC** (GPO linked to Domain Controllers) | Not supported, **Supported**, Always provide claims, **Fail unarmored authentication requests** |
| **Kerberos client support for claims, compound authentication and Kerberos armoring** | Computer Configuration > Administrative Templates > System > **Kerberos** (clients) | Enabled |
| Fail authentication requests when Kerberos armoring is not available | System > Kerberos (clients) | Enabled = the client refuses unarmored exchanges |

Roll out **Supported** on all DCs first, then client support, and use **Fail unarmored authentication requests** only when every client can armor.

### Authentication policies and silos

Available at DFL 2012 R2 and later, managed in **Active Directory Administrative Center > Authentication**:

- An **authentication policy** sets TGT lifetime for users, computers or services and conditions such as "users may only request a TGT from devices that are members of the PAWs group".
- An **authentication policy silo** groups accounts (users, computers, service accounts) and applies policies to them, so Tier 0 admins can authenticate only to and from Tier 0 hosts.
- Policies can be **audit only** first, then enforced.
- Device-based conditions need Kerberos armoring (DCs: Supported or higher; clients: client support enabled).

```powershell
PS C:\> New-ADAuthenticationPolicy -Name "Tier0-Users" -UserTGTLifetimeMins 240 -UserAllowedToAuthenticateFrom 'O:SYG:SYD:(XA;OICI;CR;;;WD;(Member_of_any {SID(S-1-5-21-1004336348-1177238915-682003330-3120)}))' -Enforce
PS C:\> New-ADAuthenticationPolicySilo -Name "Tier0" -UserAuthenticationPolicy "Tier0-Users" -ComputerAuthenticationPolicy "Tier0-Users" -ServiceAuthenticationPolicy "Tier0-Users" -Enforce
PS C:\> Grant-ADAuthenticationPolicySiloAccess -Identity "Tier0" -Account "T0-Admin1"
PS C:\> Set-ADAccountAuthenticationPolicySilo -Identity "T0-Admin1" -AuthenticationPolicySilo "Tier0"
```

The SID in the condition is an example group (the PAW computer group). The account must be both **granted access** to the silo and **assigned** to it.

### Auditing and restricting NTLM

Security Options under **Network security: Restrict NTLM** let you audit, then block, NTLM at each role:

| Role | Audit setting | Block setting |
|---|---|---|
| Client (outgoing) | Outgoing NTLM traffic to remote servers: **Audit all** | Outgoing NTLM traffic to remote servers: Deny all |
| Server (incoming) | **Audit Incoming NTLM Traffic** | Incoming NTLM traffic: Deny all domain accounts / Deny all accounts |
| Domain controller | **Audit NTLM authentication in this domain** | NTLM authentication in this domain: Deny ... |
| Exceptions | Add remote server exceptions (clients); Add server exceptions in this domain (DCs) | |

Audit and block events are written to **Applications and Services Logs > Microsoft > Windows > NTLM > Operational**. Always audit first, build exception lists, then deny.

Related settings:

- **Network security: LAN Manager authentication level** = *Send NTLMv2 response only. Refuse LM & NTLM* stops LM and NTLMv1 everywhere NTLM still runs.
- Windows Server 2025's SMB client can block NTLM for outbound SMB: `Set-SmbClientConfiguration -BlockNTLM $true` (or the Lanman Workstation **Block NTLM** policy).

### Stronger methods

Prefer passwordless or phishing-resistant methods for privileged users: **smart cards** (PKINIT), **Windows Hello for Business** and **FIDO2** security keys (with Microsoft Entra Kerberos for hybrid scenarios). Combine with Protected Users for admin accounts.

> **Watch out:** Turning on "Fail unarmored authentication requests" or denying NTLM without an audit phase is the fastest way to cause an outage: older devices, appliances and applications that connect by IP address will stop authenticating.

## Lab it yourself

On DC1:

```powershell
PS C:\> New-ADGroup -Name "Branch1-HelpDesk" -GroupScope Global -Path "OU=Branch1,DC=contoso,DC=com"
PS C:\> dsacls "OU=Branch1,DC=contoso,DC=com" /I:S /G "CONTOSO\Branch1-HelpDesk:CA;Reset Password;user"
PS C:\> Set-ADAccountControl -Identity T0-Admin1 -AccountNotDelegated $true
PS C:\> Get-ADUser -Filter 'DoesNotRequirePreAuth -eq $true'
```

Then enable **Network security: Restrict NTLM: Audit NTLM authentication in this domain** = *Enable all* in a GPO on the Domain Controllers OU, map a share by IP address from a member server and find the event in the NTLM Operational log on DC1.

## Key takeaways

- Mark privileged accounts "sensitive and cannot be delegated"; never enable "Do not require Kerberos preauthentication", reversible encryption or DES.
- Replace user-based service accounts with gMSAs or dMSAs to defeat Kerberoasting.
- Delegate to groups on OUs with the Delegation of Control Wizard or `dsacls`; the wizard cannot remove permissions.
- Protected (adminCount = 1) accounts ignore OU delegation because of AdminSDHolder.
- Kerberos armoring needs the KDC policy on DCs and the client policy on clients; enforce only after full support.
- Authentication policies and silos bind Tier 0 accounts to approved devices and shorten TGT lifetime.
- Audit NTLM, add exceptions, then restrict; NTLMv1 is removed in Windows Server 2025.
