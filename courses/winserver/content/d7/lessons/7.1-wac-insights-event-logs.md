## Windows Admin Center as a monitoring console

Windows Admin Center (WAC) is a browser-based management tool. It runs on a gateway (a Windows Server or Windows client) and talks to managed servers over WinRM/PowerShell remoting, so the managed servers need no agent. For monitoring, the tools you use most are:

| WAC tool | What it gives you |
|----------|-------------------|
| **Overview** | Live CPU, memory and network charts for the connected server, plus uptime and basic inventory |
| **Performance Monitor** | A browser version of PerfMon. You build **workspaces** of counters, choose Line, Report, Min-Max or Heatmap graphs, and save or export the workspace to reuse it on other servers |
| **Events** | Browse, filter and export event logs remotely |
| **Processes**, **Services**, **Storage** | Find the process using the resource, restart a service, check volume capacity |
| **System Insights** | View and manage the predictive capabilities described below |
| **Azure Monitor** / Azure hybrid services | Onboard the server to Azure Monitor and jump to alert configuration in the Azure portal |

### Alerts come from Azure Monitor, not from WAC

WAC itself does not have an alerting engine: it will not email you when a counter crosses a threshold. Persistent monitoring and alerts are delivered by **Azure Monitor**. From the server connection you onboard the server to Azure Monitor; WAC then helps you connect the server to a Log Analytics workspace and turn on monitoring, and the alert rules and action groups (email, SMS, webhook and so on) live in Azure Monitor. WAC's **Configure monitoring and alerts from the Azure portal** link simply takes you there; even the default email alerts WAC can offer during onboarding are Azure Monitor alert rules, not something the gateway evaluates.

> **Watch out:** Parts of Microsoft's WAC documentation still describe the Log Analytics agent (MMA). That agent was retired on 31 August 2024. For an on-premises server today, the supported monitoring path is **Azure Arc** (Connected Machine agent) plus the **Azure Monitor Agent** with a **data collection rule**. You can still use WAC to onboard the server to Arc, but any agent question on the exam should be answered with AMA, not MMA.

> **Exam tip:** If a question asks how to get *email alerts* for an on-premises server you manage with WAC, the answer involves Azure Monitor (alert rule + action group), not a WAC setting and not Performance Monitor.

## System Insights

System Insights is a predictive analytics feature built into Windows Server 2019 and later. It collects data locally, trains a model locally, and forecasts future usage. No cloud connection is required, though you can forward its events to Azure Monitor or System Center Operations Manager to see predictions across many servers.

### The four default capabilities

| Capability | Data analyzed (daily) |
|------------|----------------------|
| CPU capacity forecasting | `% Processor Time`, maximum 2-hour average per day |
| Networking capacity forecasting | `Bytes Total/sec` per adapter, maximum 2-hour average per day |
| Total storage consumption forecasting | Sum of local volume and disk usage, daily maximum |
| Volume consumption forecasting | Each volume's usage, daily maximum |

Key behaviours:

- These capabilities forecast **long-term trends**, not short spikes.
- With **0–5 days** of data, no prediction is made (status **None**). Until about three weeks of data exist, a simple linear trend is used; after that, an autoregressive model.
- Statuses: **Ok** (forecast stays within capacity), **Warning** (forecast exceeds capacity within **30 days**), **Critical** (exceeds capacity within **7 days**), **Error**, and **None**.
- Each capability runs on a schedule (by default daily at 3:00 AM) and can be invoked on demand.
- Each prediction writes an event to **Microsoft-Windows-System-Insights/Admin**; the event ID depends on the status (for example 148 for Warning and 150 for Critical).

### Managing System Insights with PowerShell

The `SystemInsights` module is installed with the feature.

```powershell
PS C:\> Get-InsightsCapability
PS C:\> Invoke-InsightsCapability -Name "Volume consumption forecasting"
PS C:\> Get-InsightsCapabilityResult -Name "Volume consumption forecasting"
PS C:\> Get-InsightsCapabilityResult -Name "CPU capacity forecasting" -History
PS C:\> Set-InsightsCapabilitySchedule -Name "CPU capacity forecasting" -Daily -DaysInterval 2 -At 4:00PM
PS C:\> Disable-InsightsCapability -Name "Networking capacity forecasting"
```

**Remediation actions** let System Insights run a PowerShell script automatically when a capability returns a given status:

```powershell
PS C:\> $cred = Get-Credential
PS C:\> Set-InsightsCapabilityAction -Name "Volume consumption forecasting" -Type Critical -Action "C:\Scripts\Cleanup-Volumes.ps1" -ActionCredential $cred
```

> **Exam tip:** "Automatically run a cleanup script when storage is forecast to run out within a week" maps to `Set-InsightsCapabilityAction -Type Critical`. "Within a month" maps to `-Type Warning`.

## Managing event logs

### Log types

- **Windows Logs** — Application, Security, Setup, System, and **ForwardedEvents** (the default destination for subscriptions).
- **Applications and Services Logs** — per-component logs such as `Directory Service` and `DFS Replication` on domain controllers, plus many Admin and Operational channels such as `Microsoft-Windows-WindowsUpdateClient/Operational`. Analytic and Debug channels are hidden until you enable *Show Analytic and Debug Logs*.

### Size and retention

Each log has a maximum size and a policy for when it is full:

| Policy | Behaviour |
|--------|-----------|
| Overwrite events as needed (oldest first) | Default; never stops logging but loses history |
| Archive the log when full, do not overwrite events | Saves the full log to a file and starts a new one; watch disk space |
| Do not overwrite events (clear logs manually) | Logging stops when full; for Security this can matter for compliance |

Ways to change them:

```text
C:\> wevtutil gl Security
C:\> wevtutil sl Security /ms:1073741824
C:\> wevtutil sl "Microsoft-Windows-TaskScheduler/Operational" /e:true
C:\> wevtutil epl System C:\Logs\System-Server1.evtx
C:\> wevtutil cl Application /bu:C:\Logs\App-before-clear.evtx
```

`/ms` is the maximum size in **bytes**. In Windows PowerShell 5.1, `Limit-EventLog -LogName System -MaximumSize 512MB -OverflowAction OverwriteAsNeeded` works for the classic logs. At scale, use Group Policy: **Computer Configuration > Administrative Templates > Windows Components > Event Log Service > (log name) > Specify the maximum log file size (KB)** and the retention settings beside it.

### Filtering and custom views

In Event Viewer, **Filter Current Log** narrows one log; a **Custom View** saves a filter across several logs (for example *all Critical and Error events from System and Application in the last 24 hours*) and can be exported as XML for other admins. In PowerShell, `Get-WinEvent -FilterHashtable` is fast because the filter runs in the event log service:

```powershell
PS C:\> Get-WinEvent -FilterHashtable @{ LogName='System'; Level=1,2; StartTime=(Get-Date).AddDays(-1) }
PS C:\> Get-WinEvent -ComputerName DC1 -FilterHashtable @{ LogName='Directory Service'; Id=2042 }
```

### Event forwarding and subscriptions

Windows Event Forwarding (WEF) uses WinRM to move events from **source** computers into a **collector**. Two subscription models exist:

| | Collector-initiated | Source-initiated |
|-|--------------------|------------------|
| Who lists the sources | The collector (you add each computer) | Sources find the collector via Group Policy |
| Best for | A handful of known servers | Many computers, or sources that change |
| Source configuration | WinRM enabled; collector's computer account added to **Event Log Readers** on each source | WinRM enabled; GPO **Configure target Subscription Manager** (Computer Configuration > Administrative Templates > Windows Components > Event Forwarding) pointing to `Server=http://collector.contoso.com:5985/wsman/SubscriptionManager/WEC,Refresh=60` |
| Collector configuration | `wecutil qc` (Windows Event Collector service) | `wecutil qc`, subscription allows the computer groups |

To forward the **Security** log from sources, the **NETWORK SERVICE** account must be a member of the **Event Log Readers** group on the source, because the forwarding runs as Network Service.

Delivery optimization options:

| Option | Mode | Batch timeout |
|--------|------|---------------|
| Normal | Pull | 15 minutes, 5 items per batch |
| Minimize Bandwidth | Push | 6 hours (heartbeat 6 hours) |
| Minimize Latency | Push | 30 seconds |

Check health on the collector with `wecutil gr <SubscriptionName>` (runtime status per source) and look in the source's **Microsoft-Windows-Forwarding/Operational** log for errors.

> **Real world:** Most WEF failures are WinRM failures: the collector name in the GPO doesn't resolve, TCP 5985 is blocked, or the source never refreshed policy. Run `winrm quickconfig` and `Test-NetConnection collector -Port 5985` from a source before anything else.

## Lab it yourself

1. Install WAC on a lab server (download the installer from Microsoft), connect to a second server, open **Performance Monitor** and save a workspace with CPU and memory counters.
2. On a Windows Server 2025 VM, run `Get-InsightsCapability` and `Invoke-InsightsCapability -Name "Volume consumption forecasting"`, then `Get-InsightsCapabilityResult` (expect **None** on a new VM: not enough data).
3. On a collector VM run `wecutil qc /q`; on a source VM run `winrm quickconfig -q` and add the collector's computer account to **Event Log Readers**. Create a collector-initiated subscription for System log Errors with **Minimize Latency**, then trigger an error with `eventcreate /t ERROR /id 999 /l SYSTEM /so LabTest /d "WEF test"` on the source.

## Key takeaways

- WAC gives agentless, browser-based monitoring (Performance Monitor workspaces, Events, Overview) but alerting is done by Azure Monitor alert rules and action groups.
- MMA is retired; on-premises servers reach Azure Monitor through Azure Arc plus the Azure Monitor Agent and a DCR.
- System Insights forecasts CPU, network, total storage and per-volume usage locally; Warning means capacity exceeded within 30 days, Critical within 7 days.
- `Set-InsightsCapabilityAction` runs a remediation script automatically for a chosen status.
- Use `wevtutil sl` (size in bytes), `Limit-EventLog` or Group Policy to set log sizes and retention.
- Collector-initiated subscriptions suit a few known sources; source-initiated subscriptions scale through Group Policy.
- Forwarding the Security log requires NETWORK SERVICE in Event Log Readers on the source; Minimize Latency delivers within about 30 seconds.
