## Why baselines come first

Every performance question on AZ-802 is really a question about *normal*. A counter value means nothing on its own: 70% CPU is healthy on a busy SQL host and alarming on an idle file server. The workflow the exam expects is:

1. Capture a **baseline** while the server is healthy (a typical business week, including peaks such as backups and month-end jobs).
2. When users complain, capture the **same counters** again.
3. Compare, identify the bottleneck subsystem (CPU, memory, disk, network), then drill into the process or driver responsible.

Performance Monitor (`perfmon.exe`) is the in-box tool for steps 1 and 2. Data collector sets (DCS) are how you make the capture repeatable, scheduled and unattended.

## Performance Monitor building blocks

| Term | Meaning | Example |
|------|---------|---------|
| Object | A resource or subsystem | `Processor`, `Memory`, `PhysicalDisk`, `Network Interface` |
| Counter | A measured value on an object | `% Processor Time`, `Available MBytes` |
| Instance | Which copy of the object | `_Total`, `0`, `C:`, a specific NIC |
| Counter path | Full name used by tools | `\\Server1\PhysicalDisk(0 C:)\Avg. Disk sec/Read` |

Performance Monitor has three views of live data: **Line** (default graph), **Histogram bar**, and **Report** (plain numbers, the easiest to read when you have many counters). The default sample interval in the live view is one second; for a long baseline you want a much longer interval (15–60 seconds) so the log stays a manageable size.

You can also open a saved log (`.blg`) in Performance Monitor by changing the data source from *Current activity* to *Log files*, and then choose a time range to zoom in on an incident.

### Counters worth knowing

The thresholds below are widely taught rules of thumb, not hard limits. Microsoft's own guidance varies by workload; treat them as "investigate if sustained", and always compare against your baseline.

| Subsystem | Counter | Investigate when (sustained) |
|-----------|---------|------------------------------|
| CPU | `Processor(_Total)\% Processor Time` | Above roughly 80–85% |
| CPU | `System\Processor Queue Length` | More than about 2 threads waiting per logical processor |
| CPU | `Processor(_Total)\% Privileged Time` / `% Interrupt Time` / `% DPC Time` | High kernel, interrupt or DPC time points at drivers or hardware rather than applications |
| Memory | `Memory\Available MBytes` | Below about 10% of installed RAM |
| Memory | `Memory\% Committed Bytes In Use` | Consistently above about 80% |
| Memory | `Memory\Pages/sec` | Sustained high values together with low available memory (paging to disk) |
| Disk | `PhysicalDisk\Avg. Disk sec/Read` and `sec/Write` | Latency above roughly 20–25 ms on spinning disks; SSD/NVMe should be in single-digit ms |
| Disk | `PhysicalDisk\Avg. Disk Queue Length` | Persistently high relative to the number of spindles or the array's capability |
| Network | `Network Interface\Bytes Total/sec` | Approaching about 70% of `Current Bandwidth` (multiply bytes by 8 first: `Current Bandwidth` is in bits per second) |
| Network | `Network Interface\Output Queue Length` | Persistently above 2 |

> **Exam tip:** Latency counters (`Avg. Disk sec/Read`, `sec/Write`) are the most reliable disk indicators on modern storage. Queue length is hard to interpret on SANs, Storage Spaces and NVMe, so exam answers usually pick latency when they ask "which counter shows the disk is slow".

> **Watch out:** `Pages/sec` alone does not prove a memory shortage; it includes paging for memory-mapped files. Pair it with `Available MBytes` and `% Committed Bytes In Use` before deciding to add RAM.

Inside a Hyper-V guest, `% Processor Time` reports the share of the *virtual* processors the guest got. To see whether the **host** is short of CPU, use the `Hyper-V Hypervisor Logical Processor(_Total)\% Total Run Time` counter on the host. Guest counters cannot see host contention.

### Get-Counter for quick checks and scripts

`Get-Counter` reads the same counters from PowerShell, locally or remotely, and is ideal for a quick look over a remote session or a scheduled script.

```powershell
PS C:\> Get-Counter -ComputerName Server1 -Counter '\Processor(_Total)\% Processor Time','\System\Processor Queue Length','\Memory\Available MBytes' -SampleInterval 5 -MaxSamples 12
PS C:\> Get-Counter -ListSet PhysicalDisk | Select-Object -ExpandProperty Paths
```

Use `-Continuous` to sample until you press Ctrl+C. To save samples to a log that Performance Monitor can open, pipe the results to `Export-Counter -Path C:\PerfLogs\snap.blg -FileFormat BLG` (Windows PowerShell 5.1).

## Data collector sets

A data collector set groups one or more **data collectors** with a schedule, stop conditions, a run-as account and an output folder. You find them in Performance Monitor under **Data Collector Sets**:

| Node | What it holds |
|------|---------------|
| User Defined | Sets you create |
| System | Built-in sets: **System Diagnostics** and **System Performance** (each produces a report as well as data) |
| Event Trace Sessions | Running ETW sessions |
| Startup Event Trace Sessions | ETW sessions that start at boot |

### Data collector types

When you create a set manually (**Create manually (Advanced)**), you choose which collectors to include:

| Collector type | Captures | Typical use |
|----------------|----------|-------------|
| Performance counter data collector | Counter samples at an interval | Baselines and incident captures (`.blg`, or CSV/TSV/SQL) |
| Event trace data collector | ETW events from providers | Deep driver/kernel or component tracing |
| System configuration information | Registry key values (and WMI/file info in some templates) | Recording configuration state alongside performance data |
| Performance counter alert | Compares a counter to a threshold | Take action when a threshold is crossed |

A **Performance Counter Alert** set is created as its own type: you specify the counter, the threshold (*above* or *below*), and the sample interval. On the alert's **Alert Action** tab you can log an entry to the Application event log and start another data collector set; on the **Alert Task** tab you can run a scheduled task. Alerts are local to the server; they do not send email by themselves.

> **Exam tip:** "Start a detailed capture only when CPU goes above 90%" is the classic alert scenario: create a performance counter alert whose alert action **starts a data collector set** that logs the detailed counters. This keeps log volume low the rest of the time.

### Templates, schedules and stop conditions

- **Templates** — create a set from the built-in *Basic*, *System Diagnostics* or *System Performance* templates, or export a set you built as XML (right-click > *Save Template*) and import it on other servers.
- **Schedule** — set a beginning date, an optional expiration date and launch days/times.
- **Stop condition** — overall duration (for example 1 day), maximum log size, and the option to restart the set when a limit is reached so you get one file per period.
- **Data Manager** — retention for the output folder: minimum free disk, maximum folders, maximum root path size, and the policy to delete the oldest or largest data first. Without it, a long-running set can fill the volume.
- **Run As** — the account the set runs under. Members of **Performance Log Users** can create and schedule data collector sets without being administrators; **Performance Monitor Users** can view counters but cannot create logs.

### logman: the same thing from the command line

`logman` creates and controls data collector sets locally or on remote servers, which is handy for building the same baseline on many machines.

```text
C:\> logman create counter Baseline-Web -s Server1 -c "\Processor(_Total)\% Processor Time" "\Memory\Available MBytes" "\PhysicalDisk(_Total)\Avg. Disk sec/Read" -si 00:00:30 -f bincirc -max 512 -o C:\PerfLogs\Baseline-Web
C:\> logman start Baseline-Web -s Server1
C:\> logman query -s Server1
C:\> logman stop Baseline-Web -s Server1
```

`-f bincirc` writes a circular binary log capped by `-max` (in MB), so the newest data overwrites the oldest. Use `relog` to convert a `.blg` file to CSV or to trim it to a time window:

```text
C:\> relog C:\PerfLogs\Baseline-Web_000001.blg -f csv -o C:\PerfLogs\baseline.csv
```

> **Real world:** Run a baseline set as a circular log permanently on important servers. When someone reports "it was slow at 2 PM yesterday", the data is already there.

## Lab it yourself

On a Windows Server 2025 evaluation VM:

1. Open **Performance Monitor**, add `Processor(_Total)\% Processor Time` and `Memory\Available MBytes`, and switch to **Report** view.
2. Create a baseline set from the command line:

```text
C:\> logman create counter LabBaseline -c "\Processor(_Total)\% Processor Time" "\Memory\Available MBytes" -si 00:00:10 -f bin -o C:\PerfLogs\LabBaseline
C:\> logman start LabBaseline
```

3. Generate CPU load in a second PowerShell window for a minute (`1..4 | ForEach-Object { Start-Job { while ($true) {} } }`), then stop it with `Get-Job | Stop-Job; Get-Job | Remove-Job`.
4. Run `logman stop LabBaseline`, open the `.blg` file in Performance Monitor and find the spike.
5. Create a **Performance Counter Alert** set on `% Processor Time` above 80 that writes to the Application log, repeat the load, and look for the alert event.

## Key takeaways

- Capture a baseline while the server is healthy; every threshold is interpreted against it.
- Use latency (`Avg. Disk sec/Read`/`Write`) for disk, `Available MBytes` plus `% Committed Bytes In Use` for memory, and `% Processor Time` plus `Processor Queue Length` for CPU.
- In a VM, guest CPU counters cannot show host contention; check the Hyper-V hypervisor counters on the host.
- Data collector sets combine performance counter, event trace, configuration and alert collectors with schedules, stop conditions and Data Manager retention.
- A performance counter alert can log an event, start another data collector set, or run a task; it does not email by itself.
- `logman` creates and controls sets remotely; `relog` converts and trims `.blg` files.
- Performance Log Users can create and schedule data collector sets without admin rights.
