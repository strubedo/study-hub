## The Azure Monitor data path

For AZ-802, think of Azure Monitor as a pipeline with four parts:

1. **Agent** — the **Azure Monitor Agent (AMA)** runs on the Windows Server. On an Azure VM it is a VM extension (`AzureMonitorWindowsAgent`). On an on-premises or other-cloud server you first connect the machine to **Azure Arc**, then install AMA as an Arc extension.
2. **Data collection rule (DCR)** — an Azure resource that says *what* to collect (which counters, which events) and *where* to send it. A DCR is linked to machines by a **data collection rule association (DCRA)**.
3. **Destination** — usually a **Log Analytics workspace** (queried with KQL); performance counters can also go to **Azure Monitor Metrics**, and the newer VM experience sends OpenTelemetry metrics to an **Azure Monitor workspace** (queried with PromQL).
4. **Consumers** — Log Analytics queries, workbooks, VM insights, and **alert rules**.

> **Watch out:** The Log Analytics agent (also called MMA or OMS) was retired on **31 August 2024**. Microsoft states that cloud ingestion for it can stop at any time after 2 March 2026. Any exam answer that installs MMA for a new deployment is wrong; AMA plus a DCR is the current design.

AMA on an Azure VM authenticates with a **managed identity** (system-assigned by default, or user-assigned). Installing the extension alone collects nothing: data only flows once at least one DCR is associated with the machine.

## Configuring data collection rules

You create a DCR in **Monitor > Data Collection Rules** (or from the VM/Arc server's monitoring blade). The portal wizard has three tabs that matter:

| Tab | What you set |
|-----|--------------|
| **Basics** | Name, subscription, resource group, region, platform (Windows/Linux) |
| **Resources** | The VMs, scale sets or Arc-enabled servers to associate. Adding a resource installs AMA on it if it is missing. |
| **Collect and deliver** | One or more data sources, each with its destination |

Common Windows data sources:

| Data source | Destination table (Log Analytics) | Notes |
|-------------|-----------------------------------|-------|
| Performance counters | `Perf` | Choose basic sets or custom counter paths and a sample rate |
| Windows event logs | `Event` (Security events go to `SecurityEvent` when collected through Microsoft Sentinel/Defender) | Filter by log and level, or use custom **XPath** queries |
| Text and JSON logs, IIS logs, Windows Firewall logs | Custom or specific tables | Text/JSON logs need a custom table in the workspace |

XPath queries keep ingestion (and cost) down by sending only the events you need:

```text
System!*[System[(Level=1 or Level=2)]]
Application!*[System[(EventID=1000 or EventID=1002)]]
Security!*[System[(EventID=4625)]]
Directory Service!*[System[(Level=1 or Level=2 or Level=3)]]
```

You can test an XPath expression locally before putting it in a DCR: `Get-WinEvent -LogName System -FilterXPath '*[System[(Level=1 or Level=2)]]'`.

DCRs also support **transformations** (a KQL `transformKql` statement such as `source | where EventID != 7036`) that filter or reshape data during ingestion.

Design guidance worth remembering:

- One DCR can be associated with many machines, and one machine can have several DCRs. Build DCRs by role (for example *baseline for all servers*, *extra for DCs*, *extra for IIS*) rather than one per server.
- Use **Azure Policy** initiatives to deploy AMA and associate DCRs automatically to new VMs and Arc servers.
- Keep a DCR in the same region as the Log Analytics workspace it sends to; Microsoft's VM insights guidance requires this.

```powershell
PS C:\> New-AzConnectedMachineExtension -Name AzureMonitorWindowsAgent -ExtensionType AzureMonitorWindowsAgent -Publisher Microsoft.Azure.Monitor -ResourceGroupName RG1 -MachineName Server1 -Location eastus -EnableAutomaticUpgrade
PS C:\> Get-AzDataCollectionRuleAssociation -ResourceUri "/subscriptions/<sub-id>/resourceGroups/RG1/providers/Microsoft.HybridCompute/machines/Server1"
```

### Verifying data arrives

AMA sends a heartbeat every minute to the `Heartbeat` table. These KQL queries are worth memorizing:

```text
Heartbeat
| summarize LastHeartbeat = max(TimeGenerated) by Computer
| where LastHeartbeat < ago(15m)

Perf
| where ObjectName == "LogicalDisk" and CounterName == "% Free Space" and InstanceName == "C:"
| summarize avg(CounterValue) by Computer, bin(TimeGenerated, 15m)

Event
| where EventLog == "System" and EventLevelName == "Error"
| summarize count() by Computer, Source, EventID
```

## Creating alerts

An **alert rule** has three parts: the **scope** (resource or workspace), the **condition** (signal plus logic), and the **actions** (an **action group**). Each rule also has a **severity** from Sev 0 (critical) to Sev 4 (verbose).

| Alert type | Signal | Typical Windows Server use |
|------------|--------|----------------------------|
| **Metric alert** | A platform or custom metric, evaluated near real time; supports static or **dynamic thresholds** (machine-learned baselines) | Azure VM `Percentage CPU`, `Available Memory Bytes`, disk IOPS consumed |
| **Log search alert** | A KQL query run on a schedule against Log Analytics | Missing heartbeat, specific event IDs, low disk free space from `Perf` |
| **Activity log alert** | An Azure Resource Manager operation, **Service Health** event or **Resource Health** change | Someone deleted a VM, a region incident, a VM became unavailable |
| Prometheus alert | PromQL against an Azure Monitor workspace | OpenTelemetry guest metrics |

**Action groups** define *who* and *what*: email, SMS, push, voice, and automated actions such as Azure Functions, Logic Apps, Automation runbooks, webhooks and ITSM. One action group can be reused by many rules.

**Alert processing rules** apply on top of rules: suppress notifications during a maintenance window, or add an action group to every alert in a resource group, without editing each alert rule.

> **Exam tip:** Choose the alert type by signal. Host metrics of an Azure VM (CPU, network, disk) are available without any agent, so a metric alert works immediately. Anything from inside the guest OS (event IDs, free space on drive D:, a stopped service) needs AMA plus a DCR, then a log search alert (or a metric alert if the DCR sends counters to Azure Monitor Metrics).

> **Exam tip:** An **on-premises** server has no Azure host metrics. To alert on it, connect it to Azure Arc, collect with AMA and a DCR, and use log search alerts against the workspace.

Azure VMs also offer **recommended alert rules** in the portal (for example CPU, available memory, data disk IOPS, network) that you enable with one click and attach to an action group.

## VM insights

VM insights is the curated monitoring experience for Azure VMs, scale sets and Arc-enabled servers. Enabling it:

- installs AMA and creates/associates a VM insights DCR (the portal gives VM insights DCRs an `MSVMI-` name prefix);
- collects a standard set of guest performance data into the **`InsightsMetrics`** table (for example `Namespace == "Processor"` / `Name == "UtilizationPercentage"`, `Memory` / `AvailableMB`, `LogicalDisk` / `FreeSpacePercentage`);
- optionally installs the **Dependency agent** to enable the **Map** feature (processes, listening ports and connections between machines, stored in tables such as `VMConnection` and `VMBoundPort`).

The **Performance** view shows top-N charts across many machines (CPU, memory, disk, network), and per-VM charts let you drill into one server. Workbooks provide further reports.

```text
InsightsMetrics
| where Origin == "vm.azm.ms"
| where Namespace == "Processor" and Name == "UtilizationPercentage"
| summarize P95 = percentile(Val, 95) by Computer
| top 10 by P95
```

Microsoft now also offers an OpenTelemetry-based metrics experience for VMs and Arc servers (stored in an Azure Monitor workspace and queried with PromQL; default metrics at no extra cost). The logs-based experience above is still the one to use when you need multi-VM VM insights workbooks, scale sets, or correlation with logs in one KQL query. Expect exam questions to describe the logs-based VM insights experience.

> **Watch out:** The Dependency agent is required **only** for the Map feature. Performance charts in VM insights work with AMA alone.

## Lab it yourself

With a free Azure account:

1. Create a Log Analytics workspace and a small Windows Server 2025 VM.
2. In the VM, open **Monitoring > Insights**, enable VM insights (logs-based) and point it to your workspace.
3. Create a DCR for the VM that collects `System` and `Application` events at Error and Critical levels.
4. On the VM run `eventcreate /t ERROR /id 999 /l APPLICATION /so LabTest /d "Alert test"`.
5. After a few minutes, run `Event | where EventID == 999` in the workspace, then create a log search alert from that query with an action group that emails you.
6. Optional: onboard a Hyper-V lab VM to Azure Arc, deploy AMA as an Arc extension and associate the same DCR.

## Key takeaways

- AMA plus a data collection rule replaces the retired Log Analytics agent; on-premises servers need Azure Arc first.
- A DCR defines sources (counters, events with XPath filters, text logs) and destinations; associations link it to machines, and nothing is collected until one exists.
- Performance counters land in `Perf`, Windows events in `Event`, agent health in `Heartbeat`, VM insights data in `InsightsMetrics`.
- Metric alerts are near real time with static or dynamic thresholds; log search alerts run KQL on a schedule; activity log alerts cover ARM operations, Service Health and Resource Health.
- Action groups say who is notified and what automation runs; alert processing rules suppress or add actions at scale.
- VM insights installs AMA and a DCR; the Dependency agent is needed only for the Map feature.
