## Troubleshooting Windows Update

### Where the evidence is

| Source | What it tells you |
|--------|-------------------|
| **Settings > Windows Update > Update history**, `Get-HotFix` | What installed and when |
| **Microsoft-Windows-WindowsUpdateClient/Operational** event log | Scan, download and install results with error codes |
| **WindowsUpdate.log** | Detailed client log. Since Windows 10/Server 2016 the client writes ETW traces to `C:\Windows\Logs\WindowsUpdate\*.etl`; run `Get-WindowsUpdateLog` to merge and decode them into a readable `WindowsUpdate.log` (on the desktop by default, or `-LogPath`) |
| `C:\Windows\Logs\CBS\CBS.log` | Component-Based Servicing: why a package failed to install, component store corruption |
| `C:\Windows\Logs\DISM\dism.log` | DISM operations |
| `HKLM\SOFTWARE\Policies\Microsoft\Windows\WindowsUpdate` | Whether policy points the client at WSUS (`WUServer`) and other GPO settings |

```powershell
PS C:\> Get-WindowsUpdateLog -LogPath C:\Temp\WindowsUpdate.log
PS C:\> Get-WinEvent -LogName Microsoft-Windows-WindowsUpdateClient/Operational -MaxEvents 20
PS C:\> gpresult /h C:\Temp\gp.html
```

### Common causes and fixes

| Symptom | Likely cause | Fix |
|---------|--------------|-----|
| Scan fails, log shows it can't reach the WSUS URL | Wrong `WUServer` in GPO, DNS, proxy, or firewall | Fix the GPO/URL, test with `Test-NetConnection wsus1 -Port 8530` (8531 for HTTPS) |
| Install fails with component store errors, `0x800f081f` (source files not found) in CBS/DISM logs | Corrupt component store | `DISM /Online /Cleanup-Image /RestoreHealth` (with `/Source:` and `/LimitAccess` if the server cannot reach Windows Update), then `sfc /scannow` |
| Downloads stuck or repeatedly corrupt | Damaged download cache | Stop `wuauserv`, `bits` and `cryptsvc`; rename `C:\Windows\SoftwareDistribution` (and `C:\Windows\System32\catroot2`); start the services |
| Update installs but reverts after reboot | A component fails during the reboot phase | Review CBS.log and the Setup event log; check free space on C: and third-party filter drivers |
| "Pending restart" never clears | A previous servicing operation is incomplete | Reboot; if still pending, check `DISM /Online /Get-Packages` for packages in *Install Pending* |

```text
C:\> DISM /Online /Cleanup-Image /ScanHealth
C:\> DISM /Online /Cleanup-Image /RestoreHealth /Source:WIM:D:\sources\install.wim:2 /LimitAccess
C:\> sfc /scannow
```

> **Exam tip:** Order matters: run **DISM RestoreHealth first** to repair the component store, then **SFC**, because SFC repairs protected files *from* the component store.

### Azure Update Manager

Azure Update Manager manages updates for Azure VMs and Azure Arc-enabled servers without any agent beyond the Arc agent (on-premises) or the VM agent (Azure). It installs its Windows OS update extension on demand.

- **Periodic assessment** checks for missing updates every 24 hours.
- **One-time update** installs now; **scheduled patching** uses **maintenance configurations** with dynamic scopes (subscription, resource group, tags, location).
- For **Azure VMs**, scheduled patching requires the patch orchestration setting **Customer Managed Schedules**, which sets `Patch mode = AutomaticByPlatform` and `BypassPlatformSafetyChecksOnUserSchedule = True`. Arc-enabled servers have no such prerequisite.
- Machines whose patching fails in Update Manager: check the machine is **Connected** (Arc), review the extension status, and read the extension log. On Arc-enabled Windows servers the logs are in `C:\ProgramData\GuestConfig\extension_logs\Microsoft.SoftwareUpdateManagement.WindowsOsUpdateExtension` (look at `WindowsUpdateExtension.log`).
- Registry-based Windows Update settings on the machine (for example automatic restart policies) can still cause reboots even if the schedule says *Never reboot*.

## Troubleshooting performance

Start with the symptom, confirm it with data, then narrow down:

1. **Task Manager / Resource Monitor** (`resmon`) — which process is consuming CPU, which file is causing disk I/O, which process holds network connections.
2. **Performance Monitor** — compare current counters against your baseline (see lesson 7.1).
3. **Windows Performance Recorder / Analyzer** (`wpr -start GeneralProfile`, `wpr -stop trace.etl`, analyze in WPA) — deep traces when you need call stacks or driver timing.
4. **Event logs** — disk errors, resource exhaustion warnings (Resource-Exhaustion-Detector), service crashes.

Typical diagnoses:

| Evidence | Diagnosis |
|----------|-----------|
| High `% Processor Time`, high `Processor Queue Length`, one process at the top | Application CPU bound; tune, scale up, or move the workload |
| High `% Privileged Time` or `% DPC Time` with no obvious process | Driver or hardware (NIC, storage filter, antivirus) |
| Low `Available MBytes`, high `% Committed Bytes In Use`, rising process private bytes | Memory leak or under-sized server |
| High `Avg. Disk sec/Read` and `sec/Write`, normal CPU | Storage bottleneck; move hot data, faster tier, check controller and cache |
| `Bytes Total/sec` near link speed, rising `Output Queue Length` | Network saturation; NIC teaming/SET, faster link, QoS |

### Virtualization-specific checks

- **Hyper-V host**: use `Hyper-V Hypervisor Logical Processor(_Total)\% Total Run Time` for real host CPU load; check **Dynamic Memory** pressure (`Hyper-V Dynamic Memory Balancer` counters) when guests feel slow; storage QoS limits on VHDX files can cap IOPS.
- **Azure VM**: the VM size caps IOPS and throughput at both disk and VM level. The platform metrics **Data Disk IOPS Consumed Percentage**, **OS Disk IOPS Consumed Percentage** and **VM Uncached IOPS Consumed Percentage** at or near 100% mean throttling; the fix is a larger disk or a VM size with higher limits. **B-series** VMs that exhaust **CPU Credits Remaining** are throttled to their baseline CPU.

> **Real world:** "The VM is slow every afternoon" on a B-series size is almost always CPU credits. Check the `CPU Credits Remaining` metric before tuning anything inside the guest.

## Troubleshooting VM and Azure Arc extension issues

### Azure VM extensions

Extensions on Azure VMs are delivered by the **Azure VM Agent** (services `WindowsAzureGuestAgent` and `RdAgent`). If the agent is not ready, no extension can install or update.

| Where | What to check |
|-------|---------------|
| Portal: VM > **Extensions + applications** | Provisioning state per extension (Succeeded, Failed, Transitioning) and the status message |
| `Get-AzVM -ResourceGroupName RG1 -Name VM1 -Status` | VM agent status and extension statuses |
| `C:\WindowsAzure\Logs\WaAppAgent.log` | Guest agent log: downloads, installs, enable/disable results |
| `C:\WindowsAzure\Logs\Plugins\<ExtensionName>\` | Per-extension logs |
| `C:\Packages\Plugins\<ExtensionName>\` | Extension settings and status files |

Typical fixes: restore outbound connectivity to Azure (the agent talks to the wire server at `168.63.129.16` and to storage), restart the guest agent service, **remove and reinstall** the failed extension, or **reapply** the VM state (`Set-AzVM -ResourceGroupName RG1 -Name VM1 -Reapply` / `az vm reapply`). For a VM you can't sign in to, use **Run Command**, **Serial Console** or **Boot diagnostics**.

### Azure Arc-enabled server extensions

On Arc-enabled servers the **Connected Machine agent** (`azcmagent`) manages extensions through its extension service.

```text
C:\> azcmagent show
C:\> azcmagent check
C:\> azcmagent logs --full
```

- `azcmagent show` displays **Agent Status** (Connected, Disconnected, Expired), last heartbeat, and **Dependent Service Status** for the agent service (`himds`), the guest configuration service (`gcarcservice`) and the **extension service** (`extensionservice`). If any of these (other than the Arc proxy) is stopped, start it before retrying extension operations.
- `azcmagent check` tests connectivity to each required Azure Arc endpoint (reachable, private, TLS, proxy).
- `azcmagent logs` zips all logs for analysis or support.
- Key log locations on Windows:

| Log | Path |
|-----|------|
| Agent (HIMDS) | `%ProgramData%\AzureConnectedMachineAgent\Log\himds.log` |
| azcmagent CLI | `%ProgramData%\AzureConnectedMachineAgent\Log\azcmagent.log` |
| Extension manager | `%ProgramData%\GuestConfig\ext_mgr_logs\gc_ext.log` |
| Individual extensions | `%ProgramData%\GuestConfig\extension_logs\<extension>\` |
| Extension status/settings | `C:\Packages\Plugins\` |

If an extension stays **Failed**, remove it (`Remove-AzConnectedMachineExtension` or `az connectedmachine extension delete`) and install it again. The agent's **managed identity certificate** is valid for 90 days and is renewed while the server is connected; a server left disconnected long enough for it to expire shows **Expired** and must be disconnected and re-onboarded. Extension allowlists/blocklists configured with `azcmagent config` can also block an extension; check `azcmagent config list`.

> **Exam tip:** Cloned servers built from an image that was already connected to Arc share one resource ID and identity, so they overwrite each other's status in Azure. Run `azcmagent disconnect --force-local-only` on each clone and connect it again.

## Lab it yourself

1. On a lab server, run `Get-WindowsUpdateLog -LogPath C:\Temp\WU.log` and search the file for `Agent` and `FATAL`.
2. Run `DISM /Online /Cleanup-Image /ScanHealth` followed by `sfc /verifyonly`.
3. Onboard a Hyper-V VM to Azure Arc (portal: **Azure Arc > Machines > Add/Create > Add a machine** generates a script), then run `azcmagent show` and `azcmagent check`.
4. Stop the extension service (`Stop-Service extensionservice`), try to install the Azure Monitor Agent extension from the portal, observe the failure, start the service and retry.

## Key takeaways

- `Get-WindowsUpdateLog` decodes the ETW traces into WindowsUpdate.log; CBS.log and DISM logs explain servicing failures.
- Repair the component store with `DISM /Online /Cleanup-Image /RestoreHealth` before running `sfc /scannow`.
- Resetting the update cache means stopping wuauserv/bits/cryptsvc and renaming SoftwareDistribution and catroot2.
- Azure Update Manager scheduled patching on Azure VMs needs Customer Managed Schedules; Arc servers do not.
- Use host-level counters for Hyper-V CPU, and IOPS-consumed and CPU-credit metrics for Azure VM throttling.
- Azure VM extensions depend on the VM agent; check WaAppAgent.log and plugin logs, then remove/reinstall or reapply.
- On Arc servers, `azcmagent show`, `check` and `logs` plus `gc_ext.log` and `extension_logs` cover most extension failures.
