## A layered method

Network problems on Windows Server are solved fastest bottom-up, the same way you would troubleshoot a router:

1. **Local configuration** — IP, mask, gateway, DNS servers, which network profile the adapter is in.
2. **Reachability** — can you reach the gateway, then the target IP?
3. **Name resolution** — does the name resolve, to the *right* address, from the *right* DNS server?
4. **Transport** — is the TCP port open end to end (firewalls, NSGs)?
5. **Application and authentication** — service running, Kerberos working, time in sync.

## Connectivity tools

| Tool | Use it for |
|------|-----------|
| `ipconfig /all`, `Get-NetIPConfiguration` | Addresses, gateway, DNS servers, DHCP state |
| `Get-NetConnectionProfile` | Whether the adapter is in the **DomainAuthenticated**, Private or Public profile |
| `Test-NetConnection` | ICMP plus TCP port tests, and `-TraceRoute` |
| `Get-NetFirewallRule`, `Get-NetFirewallProfile` | Which firewall rules and profiles are active |
| `pathping`, `tracert` | Hop-by-hop path and loss |
| `pktmon`, `netsh trace` | Built-in packet capture |
| `Get-NetTCPConnection`, `netstat -ano` | Listening ports and owning process IDs |

```powershell
PS C:\> Test-NetConnection -ComputerName DC1 -Port 389
PS C:\> Test-NetConnection -ComputerName FS1 -CommonTCPPort SMB
PS C:\> Test-NetConnection -ComputerName 10.20.0.4 -TraceRoute
```

`Test-NetConnection` reports `PingSucceeded` and `TcpTestSucceeded` separately. **Ping succeeds but TCP fails** means the host is up and routing works, so look at the service (not listening) or a firewall/NSG blocking that port. **Both fail** points at routing, a down host, or a firewall dropping everything including ICMP.

> **Watch out:** Many hardened servers block ICMP. A failed ping alone proves little; always test the actual TCP port the application uses.

### Network profiles and the firewall

Windows Firewall applies rules per profile. A domain-joined server should be in the **Domain** profile (`NetworkCategory : DomainAuthenticated`). Network Location Awareness (NLA) sets it by contacting a domain controller over LDAP. If the server boots before a DC is reachable, it can land in **Public**, where rules scoped to *Domain* do not apply and connections fail. Fix the underlying reachability, then restart the **Network Location Awareness** service (`Restart-Service NlaSvc -Force`) or disable/enable the adapter.

### Azure VM connectivity

For Azure VMs, add Azure-side checks:

- **Network security groups** on the NIC and the subnet are both evaluated; check **Effective security rules** on the NIC.
- **Network Watcher > IP flow verify** tells you whether a given 5-tuple is allowed and which NSG rule decided it; **Connection troubleshoot** tests a path from a VM to a destination.
- **Effective routes** on the NIC reveal user-defined routes sending traffic to an NVA or a firewall.
- Changing a VNet's custom DNS servers takes effect in a VM after it renews its DHCP lease (`ipconfig /renew`) or restarts.

## Name resolution

### The Windows resolution order

For a DNS name, the DNS Client service checks the local **DNS client cache**, which is preloaded with entries from the **hosts** file (`%SystemRoot%\System32\drivers\etc\hosts`), then queries the configured DNS servers in order. The **Name Resolution Policy Table (NRPT)** can send queries for specific namespaces to specific servers (for example DirectAccess or DNSSEC policies). Single-label names may also fall back to LLMNR or NetBIOS.

| Tool | Notes |
|------|-------|
| `Resolve-DnsName name -Server 10.0.0.10` | Uses the Windows resolver; `-Type SRV`, `-DnsOnly`, `-NoHostsFile`, `-CacheOnly` |
| `nslookup name server` | Talks to DNS servers directly; **ignores the hosts file and the client cache**, so it can disagree with what applications see |
| `Get-DnsClientCache`, `Clear-DnsClientCache` (`ipconfig /flushdns`) | Inspect or clear cached answers (including cached negative answers) |
| `Get-DnsClientServerAddress` | Which DNS servers each adapter uses |
| `Register-DnsClient` (`ipconfig /registerdns`) | Re-register the computer's A/PTR records |
| `Get-DnsClientNrptPolicy` | Effective NRPT rules |

> **Exam tip:** "nslookup returns the correct IP, but the application connects to the old server" usually means a **hosts file** entry or a stale **cache** entry, because nslookup bypasses both. `Resolve-DnsName` without `-DnsOnly` reflects what applications get.

### DNS for Active Directory

Clients locate domain controllers with SRV records such as `_ldap._tcp.dc._msdcs.contoso.com` and `_kerberos._tcp.contoso.com`. The Netlogon service registers these; the full list it tries to register is in `%SystemRoot%\System32\config\netlogon.dns`.

```powershell
PS C:\> Resolve-DnsName -Name _ldap._tcp.dc._msdcs.contoso.com -Type SRV
PS C:\> nltest /dsgetdc:contoso.com
PS C:\> dcdiag /test:dns /v
```

Fixes for missing SRV records: confirm the DC's NIC points to a DNS server that hosts (or forwards to) the zone, confirm dynamic updates are allowed (Secure only for AD-integrated zones), and restart Netlogon (`Restart-Service Netlogon`) to re-register.

Common server-side causes of resolution failure:

- A **conditional forwarder** or **stub zone** points to unreachable servers.
- A DC uses a public DNS server (or the ISP's) as its preferred server, so it cannot find internal records.
- An **Azure Private DNS zone** is not **linked** to the VNet that the client VM is in, or the VNet uses custom DNS servers that don't forward to Azure DNS (`168.63.129.16`).

## Windows Time service

### The domain hierarchy

Kerberos depends on time, so the domain has a built-in time hierarchy:

- Domain members (and member servers) sync from a DC in their domain (`Type = NT5DS`).
- Other DCs sync from a DC in their own domain (typically the **PDC emulator**); the PDC emulator of a child domain syncs from a DC in the parent domain.
- The **PDC emulator of the forest root domain** is the top of the hierarchy and should be the *only* machine configured to use an external, reliable source (`Type = NTP`).

Configure the forest root PDC emulator:

```text
C:\> w32tm /config /manualpeerlist:"0.pool.ntp.org,0x8 1.pool.ntp.org,0x8" /syncfromflags:manual /reliable:yes /update
C:\> net stop w32time && net start w32time
C:\> w32tm /resync /rediscover
C:\> w32tm /query /status
```

`/reliable:yes` makes the PDC advertise itself as a reliable time source. If you move the PDC emulator role, configure the new holder the same way and set the old one back to domain hierarchy with `w32tm /config /syncfromflags:domhier /reliable:no /update`.

> **Exam tip:** A Microsoft-documented way to handle PDC moves is a GPO for the time settings filtered by a WMI filter that matches the PDC emulator (`Select * from Win32_ComputerSystem where DomainRole = 5`), so whichever DC holds the role gets the external NTP configuration.

### Reading w32tm output

| Command | Shows |
|---------|-------|
| `w32tm /query /status` | Leap indicator, stratum, last successful sync, **Source** |
| `w32tm /query /source` | Just the current source |
| `w32tm /query /peers` | Each configured peer and its state (Active/Pending) |
| `w32tm /query /configuration` | Effective settings and whether they came from policy |
| `w32tm /monitor /domain:contoso.com` | Offset of each DC against the PDC |
| `w32tm /stripchart /computer:DC1 /samples:5 /dataonly` | Offset between this machine and a target |

Important source values:

- **Local CMOS Clock** — not synchronized (or, on the root PDC, free-running on its own clock). On a member or DC this is a problem.
- **VM IC Time Synchronization Provider** — time is coming from the Hyper-V (or Azure) host through the integration service.
- A DC name — normal domain hierarchy.

Useful events in the System log (source Microsoft-Windows-Time-Service): **event 12** on a forest root PDC that has no external source and is using its local clock, and **event 142** when the time service stops advertising as a time source because the local clock is not synchronized.

### Virtual domain controllers

The Hyper-V **Time Synchronization** integration service does two things: it sets the VM clock when the VM starts or resumes from a saved state, and it can provide ongoing samples through the `VMICTimeProvider`. The goal for a virtual DC is that it doesn't take its ongoing time from the host, so it follows the domain hierarchy (or, on the forest root PDC, an external NTP source). Microsoft documents two ways to do that:

- **Clear Time synchronization** under the VM's **Integration Services** settings. This is what Microsoft's current "virtualizing domain controllers with Hyper-V" guidance says.
- **Keep the integration service but disable only the provider** in the guest. The Windows Time and Hyper-V teams prefer this because the VM still gets a sane clock after a start or a saved-state resume:

```text
C:\> reg add HKLM\SYSTEM\CurrentControlSet\Services\W32Time\TimeProviders\VMICTimeProvider /v Enabled /t REG_DWORD /d 0 /f
C:\> net stop w32time && net start w32time
```

> **Watch out:** If the forest root PDC emulator is a VM and its Source shows **VM IC Time Synchronization Provider** while the Hyper-V host's own clock is wrong, the whole forest inherits the host's error. Disable the VMIC provider on the PDC and point it at a reliable NTP source. Also configure the Hyper-V hosts themselves to sync from a reliable source.

Azure VMs get host time from Azure infrastructure by default; DCs in Azure follow the same rule: use the domain hierarchy, and give the forest root PDC a defined source.

## Lab it yourself

1. On a lab DC holding the PDC emulator role: `w32tm /query /status` and `w32tm /query /peers`, then configure an external peer with the `w32tm /config` command above and query again.
2. On a member server, add a bogus line to the hosts file (`10.99.99.99 dc1.contoso.com`), compare `nslookup dc1.contoso.com` with `Resolve-DnsName dc1.contoso.com`, then remove the line and run `Clear-DnsClientCache`.
3. Run `Test-NetConnection DC1 -Port 389` and `Test-NetConnection DC1 -Port 9999` to see the difference between an open and a closed port.
4. Run `Get-NetConnectionProfile` and confirm `DomainAuthenticated`.

## Key takeaways

- Troubleshoot bottom-up: configuration, reachability, name resolution, port, application.
- `Test-NetConnection -Port` separates "host reachable" from "port open"; don't trust ping alone.
- A domain server in the Public profile won't apply Domain-scoped firewall rules; fix DC reachability and restart NLA.
- `nslookup` bypasses the hosts file and client cache; `Resolve-DnsName` reflects what applications see.
- DCs are located through `_msdcs` SRV records registered by Netlogon; `nltest /dsgetdc` and `dcdiag /test:dns` validate them.
- Only the forest root PDC emulator should use external NTP (`/syncfromflags:manual /reliable:yes`); everything else uses the domain hierarchy.
- On virtual DCs, stop the DC taking ongoing time from the host (clear the Time synchronization integration service, or disable just the VMICTimeProvider) so it follows the domain hierarchy.
