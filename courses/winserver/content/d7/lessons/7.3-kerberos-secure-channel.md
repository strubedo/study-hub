## How Kerberos fails

Kerberos authentication in AD DS has three moving parts that you can check in order:

1. **Time** — the client, the KDC (any DC) and the target server must be within the **maximum tolerance for computer clock synchronization**, **5 minutes** by default (Default Domain Policy > Account Policies > Kerberos Policy).
2. **Names** — the client asks the KDC for a ticket to a **service principal name (SPN)**, such as `HTTP/app1.contoso.com` or `MSSQLSvc/sql1.contoso.com:1433`. That SPN must exist on **exactly one** account in the forest, and it must be the account the service actually runs as.
3. **Keys and tickets** — the service decrypts the ticket with its own account's key. If the password (key) on the service account changed, or the ticket was encrypted for a different account, decryption fails.

Default ticket lifetimes: the TGT (user ticket) is valid for **10 hours** and renewable for **7 days**; service tickets also default to 10 hours (600 minutes).

### Error to cause

| Error / symptom | Cause | Fix |
|-----------------|-------|-----|
| `KRB_AP_ERR_SKEW` (0x25), "The time difference between the client and server is too large" | Clock skew above 5 minutes | Fix the time hierarchy (see 7.2); `w32tm /resync` on the client |
| `KDC_ERR_S_PRINCIPAL_UNKNOWN` | No account has the requested SPN, so the client may fall back to NTLM | Register the SPN on the service account with `setspn -S` |
| `KDC_ERR_PRINCIPAL_NOT_UNIQUE`, KDC event **11** "The KDC encountered duplicate names" in the System log | The same SPN is on two accounts | Find with `setspn -X` / `setspn -Q`, remove the wrong one with `setspn -D` |
| `KRB_AP_ERR_MODIFIED` | The ticket was encrypted with a key the service doesn't have: SPN on the wrong account, a DNS alias pointing at a different server, or the service account's password changed | Move the SPN to the right account, fix DNS, restart the service with the current password |
| `KDC_ERR_ETYPE_NOTSUPP` | Encryption type mismatch (for example an account allowed only RC4 when RC4 is disabled) | Align `msDS-SupportedEncryptionTypes` and the "Configure encryption types allowed for Kerberos" policy |
| Security event **4771** on the DC with failure code `0x18` | Kerberos pre-authentication failed: wrong password | User password / cached credential issue |
| Access works by IP or after hours, not by name | Accessing by IP address uses NTLM because there's no SPN for an IP | Use the DNS name |

> **Exam tip:** Duplicate SPNs are the classic "Kerberos fails, NTLM works" scenario. `setspn -X` searches for duplicate SPNs, `setspn -Q <SPN>` shows which account holds a specific SPN, `setspn -L <account>` lists an account's SPNs, and `setspn -S` adds an SPN **only after checking it isn't already used** (prefer it over `-A`).

```text
C:\> setspn -L CONTOSO\svc-web
C:\> setspn -Q HTTP/app1.contoso.com
C:\> setspn -X -F
C:\> setspn -D HTTP/app1.contoso.com CONTOSO\WEB1$
C:\> setspn -S HTTP/app1.contoso.com CONTOSO\svc-web
```

`-F` makes the query forest-wide instead of the current domain.

> **Watch out:** IIS is the classic exception to "the SPN goes on the account the service runs as". With kernel-mode authentication on (the default) and `useAppPoolCredentials` left at `false`, http.sys decrypts tickets with the **computer** account's key, so the HTTP SPN belongs on the computer account even when the application pool runs as a domain account. Put the SPN on the service account only when `useAppPoolCredentials` is `true` (or kernel-mode authentication is off).

### klist: tickets on the client

```text
C:\> klist
C:\> klist tgt
C:\> klist purge
C:\> klist get HTTP/app1.contoso.com
C:\> klist -li 0x3e7 purge
```

- `klist` shows cached tickets with the server (SPN), encryption type, start/end times and the **KDC called**.
- `klist purge` deletes the current user's tickets so new ones are requested, for example after adding the user to a group (group SIDs are in the ticket, so new membership is invisible until a new TGT is issued).
- `klist get <SPN>` requests a service ticket and is a quick SPN test.
- `klist -li 0x3e7 purge` purges the **computer's** (SYSTEM logon session) tickets, used after adding a *computer account* to a group so the machine picks up the new membership without a reboot (follow with `gpupdate /force` if a GPO is security-filtered on that group).

> **Watch out:** A user who was added to a group still gets *Access denied* until they sign out and back in, or until you run `klist purge` and they reconnect. This is expected Kerberos behaviour, not a replication fault, as long as the membership is visible on their DC.

### Other authentication checks

- **Account state** — locked out, disabled, expired, or *logon hours* / *log on to* restrictions. `Get-ADUser User1 -Properties LockedOut, Enabled, AccountExpirationDate, badPwdCount, LastBadPasswordAttempt`. Lockout events (**4740**) are logged on the **PDC emulator**, so search there to find the source computer.
- **Protected Users group** — members can't use NTLM, DES or RC4, can't be delegated, and don't cache credentials; legacy apps that need NTLM fail for them.
- **Delegation** — a front-end service that must reach a back end on the user's behalf needs constrained delegation (or resource-based constrained delegation set on the back-end account with `Set-ADComputer -PrincipalsAllowedToDelegateToAccount`).
- **Kerberos logging** — set `LogLevel = 1` (REG_DWORD) under `HKLM\SYSTEM\CurrentControlSet\Control\Lsa\Kerberos\Parameters` to log Kerberos errors in the System log; turn it off afterwards because it's noisy.

## Secure channel and computer account trust

Every domain member has a **computer account** with a password the machine changes automatically (every **30 days** by default). The Netlogon service uses that password to build a **secure channel** to a DC. If the password stored on the machine and the one in AD stop matching, users see *"The trust relationship between this workstation and the primary domain failed"* and domain logons fail.

Common causes:

- reverting a VM to an old checkpoint, or restoring an old image, after the machine had changed its password;
- two machines with the same name (one rejoined and reset the account);
- someone reset or deleted the computer account in AD;
- a DC restored with an old database (non-authoritatively it fixes itself, authoritatively it can roll back computer passwords).

### Testing

```powershell
PS C:\> Test-ComputerSecureChannel -Verbose
PS C:\> Test-ComputerSecureChannel -Server DC1.contoso.com
```

```text
C:\> nltest /sc_query:contoso.com
C:\> nltest /sc_verify:contoso.com
C:\> nltest /dsgetdc:contoso.com
```

`Test-ComputerSecureChannel` returns `True` or `False` and works on **member computers**; Microsoft notes it gives false results on DCs, so use `nltest` or `netdom` there. `nltest /sc_query` shows the trusted DC and the connection status; a healthy channel shows `NERR_Success`.

### Repairing without leaving the domain

You don't need to unjoin and rejoin (which loses the computer's group memberships and can break SIDs used in ACLs). Sign in with a **local administrator** account (domain logon is failing), then use one of:

```powershell
PS C:\> Test-ComputerSecureChannel -Repair -Credential CONTOSO\Admin1
PS C:\> Reset-ComputerMachinePassword -Server DC1 -Credential CONTOSO\Admin1
```

```text
C:\> netdom resetpwd /server:DC1 /userd:CONTOSO\Admin1 /passwordd:*
C:\> nltest /sc_reset:contoso.com
```

| Command | What it does |
|---------|--------------|
| `Test-ComputerSecureChannel -Repair` | Tests and, if broken, resets the machine password and rebuilds the channel |
| `Reset-ComputerMachinePassword` | Resets the machine account password locally and in AD (against `-Server`) |
| `netdom resetpwd` | Same reset; the usual tool on a **domain controller** whose own machine password is broken (stop the KDC service first and restart the DC afterwards) |
| `nltest /sc_reset:<domain>` | Re-establishes the secure channel, optionally to a specific DC (`/sc_reset:contoso.com\DC2`). It doesn't change the password, so it fixes channel/DC selection problems, not a password mismatch |
| `nltest /sc_change_pwd:<domain>` | Forces an immediate machine password change |

> **Exam tip:** For "trust relationship failed" on a member server, with minimal effort and without rejoining, the answer is `Test-ComputerSecureChannel -Repair` (or `Reset-ComputerMachinePassword`), run as a local administrator with domain credentials supplied.

> **Watch out:** If the computer account was **deleted** from AD, a reset can't work because there's nothing to reset. Restore the account from the AD Recycle Bin (so its SID and group memberships return) or rejoin the domain.

### Trusts between domains or forests

For forest or external trusts, test and repair with `netdom trust contoso.com /domain:fabrikam.com /verify` (and `/reset` to reset the trust password), or use **Active Directory Domains and Trusts > domain Properties > Trusts > Properties > Validate**. `Get-ADTrust -Filter *` lists the trusts and their attributes. Name resolution between the forests (conditional forwarders) and firewalls between DCs are the usual culprits; selective authentication also requires the *Allowed to authenticate* permission on target computers.

## Lab it yourself

1. On a lab member server, take a checkpoint, run `nltest /sc_change_pwd:contoso.com` (forces a password change), then apply the checkpoint. Try a domain logon to see the trust error.
2. Sign in as local administrator and run `Test-ComputerSecureChannel` (False), then `Test-ComputerSecureChannel -Repair -Credential CONTOSO\Administrator` (True). Sign in with a domain account again.
3. Create a service account, run `setspn -S HTTP/app1.contoso.com CONTOSO\svc-web`, then try `setspn -S` with the same SPN on another account and see it refused; use `setspn -A` to force a duplicate and find it with `setspn -X`.
4. Add your test user to a new group, run `klist`, `klist purge`, reconnect to a share and run `klist` again.

## Key takeaways

- Kerberos needs time within 5 minutes, a unique SPN on the right account, and matching keys.
- KDC event 11 and `KDC_ERR_PRINCIPAL_NOT_UNIQUE` mean duplicate SPNs: find with `setspn -X`/`-Q`, fix with `setspn -D`, add safely with `setspn -S`.
- `KRB_AP_ERR_MODIFIED` usually means the ticket was encrypted for the wrong account (SPN or DNS alias on the wrong server).
- `klist purge` (or `klist -li 0x3e7 purge` for the computer) forces new tickets after group membership changes.
- A broken secure channel is a computer password mismatch; repair with `Test-ComputerSecureChannel -Repair` or `Reset-ComputerMachinePassword` as a local admin, no rejoin needed.
- Use `nltest`/`netdom` on DCs; `Test-ComputerSecureChannel` is for members.
- A deleted computer account must be restored (Recycle Bin) or the machine rejoined.
