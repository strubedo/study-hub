## BitLocker on Windows Server

BitLocker is an optional feature on Windows Server. Install it (and the management tools) before you can encrypt, then restart:

```powershell
PS C:\> Install-WindowsFeature BitLocker -IncludeAllSubFeature -IncludeManagementTools -Restart
```

### Reading the status

Two tools show the same information. `manage-bde -status` is the classic view; `Get-BitLockerVolume` is the PowerShell view.

| Field | What it means for troubleshooting |
|-------|-----------------------------------|
| Conversion Status / VolumeStatus | `Fully Encrypted`, `Encryption in Progress`, `Decryption in Progress`, `Fully Decrypted`; a paused conversion shows as *Paused* |
| Protection Status | **On** means key protectors are active. **Off** on a fully encrypted volume means protection is **suspended** (the key is stored in the clear on the volume) |
| Lock Status | `Locked` volumes need unlocking before the data is readable |
| Key Protectors | TPM, TPM and PIN, Numerical Password (the 48-digit recovery password), External Key, AD account or group, and so on |
| Auto-unlock | Whether a data volume unlocks automatically once the OS volume is unlocked |

### Why a server boots into BitLocker recovery

At startup the TPM releases the volume master key only if boot measurements (PCRs) match what was sealed. Things that change those measurements trigger the recovery screen:

- a UEFI/BIOS firmware update or a change to firmware settings (boot order, Secure Boot state, TPM settings) made **without suspending BitLocker first**;
- booting from different media, or moving the disk to another machine;
- TPM cleared or replaced (for example after a motherboard swap);
- too many incorrect PIN attempts.

Prevent it during maintenance by suspending protection, which resumes automatically after the specified number of restarts:

```powershell
PS C:\> Suspend-BitLocker -MountPoint "C:" -RebootCount 1
PS C:\> Resume-BitLocker -MountPoint "C:"
```

> **Watch out:** `-RebootCount 0` suspends protection indefinitely, until you run `Resume-BitLocker`. A server that shows *Protection Off* weeks after patching was probably suspended with 0 (or with `manage-bde -protectors -disable C:`) and never resumed.

### Finding and backing up recovery passwords

Recovery depends on the 48-digit **recovery password** being stored somewhere you can reach. On-premises, store it in **AD DS**:

- Group Policy: **Computer Configuration > Administrative Templates > Windows Components > BitLocker Drive Encryption > Operating System Drives > Choose how BitLocker-protected operating system drives can be recovered**, with *Save BitLocker recovery information to AD DS* and optionally *Do not enable BitLocker until recovery information is stored to AD DS*.
- For volumes encrypted before the policy existed, back up the protector manually:

```powershell
PS C:\> $kp = (Get-BitLockerVolume -MountPoint C:).KeyProtector | Where-Object KeyProtectorType -eq 'RecoveryPassword'
PS C:\> Backup-BitLockerKeyProtector -MountPoint C: -KeyProtectorId $kp.KeyProtectorId
```

```text
C:\> manage-bde -protectors -get C:
C:\> manage-bde -protectors -adbackup C: -id {9C1B6A3E-0F4D-4C47-9C1A-6D2E7F5B2A11}
```

The recovery information is stored as `msFVE-RecoveryInformation` child objects of the computer account. Install the **BitLocker Recovery Password Viewer** (`RSAT-Feature-Tools-BitLocker-BdeAducExt`) to see a **BitLocker Recovery** tab in Active Directory Users and Computers and to search by the first eight characters of the recovery key ID shown on the recovery screen.

Unlock a data volume with the recovery password:

```powershell
PS C:\> Unlock-BitLocker -MountPoint "E:" -RecoveryPassword "123456-234567-345678-456789-567890-678901-789012-890123"
PS C:\> Enable-BitLockerAutoUnlock -MountPoint "E:"
```

Auto-unlock for data volumes requires the operating system volume to be BitLocker-protected.

### Other server scenarios

- **BitLocker Network Unlock** lets domain servers with a TPM+PIN protector boot unattended on the corporate network. It needs UEFI firmware with DHCP, a WDS server with the **BitLocker Network Unlock** feature, and a Network Unlock certificate deployed by GPO. When it fails, servers stop at the PIN prompt; check DHCP reachability on the boot network and the certificate.
- **Cluster Shared Volumes** — add the cluster name object as a protector so any node can unlock the CSV: `Add-BitLockerKeyProtector -MountPoint "C:\ClusterStorage\Volume1" -ADAccountOrGroupProtector -ADAccountOrGroup "CLUSTER1$"`.

### Azure VM disk encryption

Azure has several layers. Managed disks are always encrypted at rest by **server-side encryption** (platform-managed keys by default, or customer-managed keys through a disk encryption set). **Encryption at host** extends that to temp disks and caches. **Azure Disk Encryption (ADE)** runs BitLocker *inside* the guest with keys in **Azure Key Vault**.

> **Watch out:** Microsoft has announced that Azure Disk Encryption retires on **15 September 2028**; new VMs should use encryption at host. Existing ADE VMs still appear in troubleshooting scenarios.

Common ADE failures:

| Symptom | Cause |
|---------|-------|
| Extension fails immediately | The key vault isn't enabled for disk encryption (`az keyvault update --name kv1 --enabled-for-disk-encryption true`), or is in a different region/subscription from the VM |
| Extension times out | The VM can't reach Key Vault or Microsoft Entra endpoints (NSG, firewall, forced tunneling) |
| Encryption fails on the OS volume | Group Policy inside the VM conflicts with ADE (for example requiring a TPM+PIN startup protector on a VM) |

## Storage troubleshooting

### Physical disks and Storage Spaces

```powershell
PS C:\> Get-PhysicalDisk | Sort-Object Number
PS C:\> Get-PhysicalDisk -FriendlyName PhysicalDisk3 | Get-StorageReliabilityCounter | Format-List Temperature, ReadErrorsTotal, WriteErrorsTotal, Wear
PS C:\> Get-VirtualDisk
PS C:\> Get-StorageJob
```

| Object | HealthStatus | Typical OperationalStatus values |
|--------|--------------|-------------------------------|
| Physical disk | Healthy, Warning, Unhealthy | OK, **Lost Communication**, **Predictive Failure**, IO Error, Starting/Stopping |
| Virtual disk (space) | Healthy, Warning, Unhealthy | OK, **Degraded** (lost redundancy but online), **Incomplete** (more failures than resiliency allows), **Detached** (offline) |

Replacing a failed disk in a standalone storage pool:

1. Mark the failed disk retired so no new data lands on it: `Set-PhysicalDisk -FriendlyName PhysicalDisk3 -Usage Retired`.
2. Add the replacement: `Add-PhysicalDisk -StoragePoolFriendlyName Pool1 -PhysicalDisks (Get-PhysicalDisk -CanPool $true)`.
3. Rebuild resiliency: `Repair-VirtualDisk -FriendlyName Data1` (Storage Spaces Direct repairs automatically).
4. Watch progress with `Get-StorageJob` until the repair completes and the virtual disk returns to **Healthy**.
5. Remove the retired disk from the pool: `Remove-PhysicalDisk -StoragePoolFriendlyName Pool1 -PhysicalDisks (Get-PhysicalDisk -FriendlyName PhysicalDisk3)`.

> **Exam tip:** Don't remove the failed disk before the repair finishes on a two-way mirror that is already Degraded; you'd be one more failure away from **Incomplete**. Retire, add, repair, wait, then remove.

On Storage Spaces Direct clusters, `Get-HealthFault` and `Get-StorageSubSystem Cluster* | Debug-StorageSubSystem` summarize faults, and WAC shows the same health faults.

### Disks, volumes and file systems

| Symptom | Check / fix |
|---------|-------------|
| New SAN/iSCSI disk shows **Offline** | SAN policy (`Get-StorageSetting`); bring online with `Set-Disk -Number 2 -IsOffline $false`; clear read-only with `Set-Disk -Number 2 -IsReadOnly $false` |
| Copied VHD shows offline with a **signature collision** | Two disks have the same signature (a clone); bringing it online writes a new signature |
| NTFS corruption | `Repair-Volume -DriveLetter D -Scan` (online, no downtime), then `Repair-Volume -DriveLetter D -SpotFix` (brief offline) or `chkdsk D: /scan` and `chkdsk D: /spotfix` |
| ReFS volume errors | ReFS repairs itself from mirror copies when integrity streams are on; chkdsk does not apply. Check the ReFS events and the underlying space |
| iSCSI disk disappears after reboot | Target not set as favorite/persistent; `Get-IscsiSession`, reconnect with `Connect-IscsiTarget -NodeAddress <iqn> -IsPersistent $true`; check MPIO paths with `mpclaim -s -d` |
| Hyper-V VM fails to start: differencing disk chain broken | `Get-VHD -Path` on the child shows `ParentPath`; fix with `Set-VHD -Path child.avhdx -ParentPath parent.vhdx` after restoring the parent; `Test-VHD` validates the chain |

## Lab it yourself

1. In a Hyper-V VM with a virtual TPM (Gen 2 VM, **Security > Enable Trusted Platform Module**), install BitLocker and run `Enable-BitLocker -MountPoint C: -TpmProtector`, then `Add-BitLockerKeyProtector -MountPoint C: -RecoveryPasswordProtector`.
2. Run `manage-bde -status`, then `Suspend-BitLocker -MountPoint C: -RebootCount 1`, check *Protection Off*, reboot, and confirm it resumed.
3. Add four small VHDX files to a VM, create a pool and a two-way mirror, remove one VHDX from the VM settings, and watch `Get-PhysicalDisk` (Lost Communication) and `Get-VirtualDisk` (Degraded). Then follow the replacement steps above.

## Key takeaways

- *Protection Off* on a fully encrypted volume means BitLocker is suspended; `Resume-BitLocker` turns it back on.
- Suspend BitLocker (`-RebootCount 1`) before firmware updates; PCR changes force recovery mode.
- Store recovery passwords in AD DS via GPO, back up older volumes with `Backup-BitLockerKeyProtector` or `manage-bde -protectors -adbackup`, and use the Recovery Password Viewer to find them.
- ADE needs a key vault enabled for disk encryption in the VM's region and subscription; ADE retires in September 2028 in favor of encryption at host.
- Read both HealthStatus and OperationalStatus: Lost Communication or Predictive Failure on disks; Degraded or Incomplete on virtual disks.
- Replace a pool disk by retiring it, adding the new disk, repairing, waiting for `Get-StorageJob`, then removing it.
- Use `Repair-Volume -Scan` then `-SpotFix` for NTFS; ReFS self-heals and doesn't use chkdsk.
