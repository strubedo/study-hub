## Choosing a recovery method

When something disappears from Active Directory, pick the least disruptive tool that can bring it back:

| Situation | Best tool |
|-----------|-----------|
| A user, group, computer or OU was deleted, Recycle Bin is enabled, and the deletion is within the deleted object lifetime | **AD Recycle Bin** (`Restore-ADObject` or ADAC) — online, no reboot, all attributes and memberships restored |
| Recycle Bin not enabled, or the object is past its deleted object lifetime but still within a backup's lifetime | **Authoritative restore** from a system state backup in **DSRM** |
| Attributes were changed incorrectly (no deletion) | Authoritative restore of those objects, or fix forward; you can browse an older snapshot with `dsamain` to see old values |
| The database on one DC is damaged | **Non-authoritative restore** (or demote and re-promote) — the DC then catches up through replication |
| Group Policy files or logon scripts lost or corrupted | **SYSVOL** authoritative or non-authoritative synchronization |

## AD Recycle Bin

### Requirements and behaviour

- Forest functional level **Windows Server 2008 R2** or higher (any Windows Server 2016+ forest qualifies).
- Enabling it is **irreversible** and forest-wide. You need Enterprise Admins rights in practice.
- Once enabled, a deleted object becomes a **deleted object** that keeps all its attributes, including link values like group memberships, for the **deleted object lifetime** (`msDS-DeletedObjectLifetime`). When that expires it becomes a **recycled object** (most attributes stripped) for the **tombstone lifetime** and is then garbage-collected.
- If `msDS-DeletedObjectLifetime` is not set, it uses the value of `tombstoneLifetime`, which is **180 days** in forests created on Windows Server 2003 SP1 or later.
- Objects deleted *before* you enabled the Recycle Bin cannot be restored with it.

```powershell
PS C:\> Enable-ADOptionalFeature -Identity 'Recycle Bin Feature' -Scope ForestOrConfigurationSet -Target contoso.com
PS C:\> Get-ADOptionalFeature -Filter 'Name -like "Recycle*"' | Select-Object Name, EnabledScopes
```

In **Active Directory Administrative Center (ADAC)**, select the domain, then **Tasks > Enable Recycle Bin**; afterwards a **Deleted Objects** container appears, where you can filter and select **Restore** or **Restore To**.

### Restoring with PowerShell

```powershell
PS C:\> Get-ADObject -Filter 'samAccountName -eq "User1"' -IncludeDeletedObjects -Properties lastKnownParent, whenChanged
PS C:\> Get-ADObject -Filter 'samAccountName -eq "User1"' -IncludeDeletedObjects | Restore-ADObject
PS C:\> Restore-ADObject -Identity 5f6c2a8e-4d1b-4c38-9e7a-2b0f1c9d3e44 -TargetPath "OU=Staff,DC=contoso,DC=com"
```

Restoring an **OU tree** requires order: restore the parent OU first, then the children whose `lastKnownParent` points to it. A child cannot be restored into a parent that is still deleted. Filter deleted objects on `samAccountName` or `msDS-LastKnownRDN`, not `Name`: a deleted object's name is mangled to `Sales\0ADEL:<GUID>`, so `Name -eq "Sales"` finds nothing.

```powershell
PS C:\> Get-ADObject -Filter 'msDS-LastKnownRDN -eq "Sales" -and objectClass -eq "organizationalUnit"' -IncludeDeletedObjects | Restore-ADObject
PS C:\> Get-ADObject -SearchBase "CN=Deleted Objects,DC=contoso,DC=com" -Filter 'lastKnownParent -eq "OU=Sales,DC=contoso,DC=com"' -IncludeDeletedObjects | Restore-ADObject
```

ADAC restores only domain-partition objects. Objects deleted from other partitions (for example the Configuration partition) need `Restore-ADObject` with the right `-Partition`/`-Server` context.

Change the deleted object lifetime (value in days):

```powershell
PS C:\> Set-ADObject -Identity "CN=Directory Service,CN=Windows NT,CN=Services,CN=Configuration,DC=contoso,DC=com" -Partition "CN=Configuration,DC=contoso,DC=com" -Replace @{'msDS-DeletedObjectLifetime' = 365}
```

> **Exam tip:** If a question says the Recycle Bin was **enabled after** the deletion, the Recycle Bin can't help; the answer is an authoritative restore from backup.

> **Watch out:** Turning on **Protect object from accidental deletion** on OUs (the default for OUs created in ADUC/ADAC) prevents many of these incidents in the first place.

## Directory Services Restore Mode (DSRM)

DSRM is a special startup mode of a domain controller where AD DS is offline, so the database (`ntds.dit`) can be restored or repaired. You log on with the local **DSRM administrator** account (`.\Administrator`) and the DSRM password set at promotion.

Ways to get into DSRM:

```text
C:\> bcdedit /set {default} safeboot dsrepair
C:\> shutdown /r /t 0
REM ... after the restore, before the final reboot:
C:\> bcdedit /deletevalue {default} safeboot
```

You can also use **System Configuration (msconfig) > Boot > Safe boot > Active Directory repair**, or press F8 at boot on systems that still show the advanced boot menu.

If nobody knows the DSRM password, reset it while the DC is running normally:

```text
C:\> ntdsutil "set dsrm password" "reset password on server null" quit quit
```

> **Real world:** Since Windows Server 2008 you can also stop the **Active Directory Domain Services** service (*restartable AD DS*) for offline tasks such as defragmenting the database. A **system state restore** of a DC still requires DSRM.

### Non-authoritative vs authoritative restore

| | Non-authoritative | Authoritative |
|-|-------------------|---------------|
| What happens | The DC's database is put back to the backup state; on restart it gets a new invocation ID and **receives** every newer change from its partners | After the restore, chosen objects get their version numbers raised so they **win** replication and overwrite the partners' copies |
| Use when | A DC's database is corrupt; you want it to rejoin and catch up | Objects were deleted or damaged and the deletion has already replicated everywhere |
| Tools | `wbadmin start systemstaterecovery` in DSRM | Same restore, then `ntdsutil` **authoritative restore** *before* restarting |

Authoritative restore steps:

1. Restart the DC into DSRM and sign in as the DSRM administrator.
2. Restore system state from a backup taken before the deletion:

```text
C:\> wbadmin get versions
C:\> wbadmin start systemstaterecovery -version:10/27/2026-02:00
```

3. **Without restarting**, mark the objects authoritative:

```text
C:\> ntdsutil
ntdsutil: activate instance ntds
ntdsutil: authoritative restore
authoritative restore: restore subtree "OU=Sales,DC=contoso,DC=com"
authoritative restore: quit
ntdsutil: quit
```

Use `restore object "CN=User1,OU=Sales,DC=contoso,DC=com"` for a single object. ntdsutil writes a text file listing the restored objects and, when group memberships are involved, an `.ldf` file of **back-links**.

4. Restart normally and let the restored objects replicate out.
5. If the restored users were members of groups in **other domains** (or the restore didn't recover memberships), import the generated `.ldf` file with `ldifde -i -f <file>.ldf` on a DC so the memberships are re-added.

> **Exam tip:** Never restart between `wbadmin` and `ntdsutil authoritative restore`. If the DC boots normally first, it replicates in the deletions and the restore is wasted.

> **Watch out:** Restore only what you need (a subtree or object). Marking the whole database authoritative (`restore database`) rolls back every change, including password changes and computer account password changes, on every DC.

### Backups and tombstone lifetime

A backup older than the **tombstone lifetime** (or, with the Recycle Bin, the lower of the deleted object lifetime and tombstone lifetime) must not be restored: it would reintroduce objects other DCs have already purged (lingering objects). Take system state backups regularly with Windows Server Backup:

```text
C:\> wbadmin start systemstatebackup -backupTarget:E: -quiet
```

## Recovering SYSVOL (DFS Replication)

On Windows Server 2025 domain controllers, SYSVOL replicates with **DFS Replication (DFSR)**; FRS is no longer supported. DFSR SYSVOL is protected from DFS Management, so you control its initialization through AD attributes on each DC's **SYSVOL Subscription** object:

`CN=SYSVOL Subscription,CN=Domain System Volume,CN=DFSR-LocalSettings,CN=<DC name>,OU=Domain Controllers,DC=contoso,DC=com`

| Attribute | Meaning |
|-----------|---------|
| `msDFSR-Enabled` | `FALSE` disables the SYSVOL membership on that DC; `TRUE` re-enables it |
| `msDFSR-Options` | `1` marks that DC as the **primary (authoritative)** member for the next initialization |

### Non-authoritative sync (one DC with a bad SYSVOL)

Use this when one DC's SYSVOL is wrong but others are healthy (the DFSR equivalent of FRS "D2"):

1. On the bad DC's SYSVOL Subscription, set `msDFSR-Enabled = FALSE`.
2. Force AD replication (`repadmin /syncall /AdeP`) and run `dfsrdiag pollad` on that DC; DFSR event **4114** confirms SYSVOL is no longer replicated.
3. Set `msDFSR-Enabled = TRUE`, force AD replication, run `dfsrdiag pollad` again.
4. Events **4614** then **4604** confirm the DC performed an initial sync from a partner.

### Authoritative sync (SYSVOL wrong everywhere)

Use this when you have restored or repaired SYSVOL content on one DC (preferably the **PDC emulator**) and every other DC must take that copy (the equivalent of "D4"):

1. Stop the **DFS Replication** service on **all** DCs (set it to Manual).
2. On the authoritative DC: `msDFSR-Enabled = FALSE` and `msDFSR-Options = 1`.
3. On every other DC: `msDFSR-Enabled = FALSE`.
4. Force AD replication and confirm it succeeded on all DCs.
5. Start DFSR on the authoritative DC; event 4114 appears.
6. On the authoritative DC set `msDFSR-Enabled = TRUE`, force AD replication, run `dfsrdiag pollad`; event **4602** confirms SYSVOL was initialized as primary.
7. Start DFSR on the other DCs (event 4114 on each), set `msDFSR-Enabled = TRUE` on each, force AD replication, run `dfsrdiag pollad` on each; they sync from the authoritative DC.
8. Set DFSR back to Automatic everywhere.

When you restore a DC from system state backup and want its SYSVOL to be authoritative, `wbadmin start systemstaterecovery -version:<version> -authsysvol` does the same job during the restore.

> **Exam tip:** "Repair a single DC" means **non-authoritative**: change only that DC, don't touch the others. Authoritative sync is a domain-wide operation and requires all other DCs to be made non-authoritative at the same time.

> **Watch out:** DFSR's **content freshness** protection (`MaxOfflineTimeInDays`, default 60) stops a DC that hasn't replicated SYSVOL for that long; it logs event **4012**. The fix is a non-authoritative sync of that DC.

## Lab it yourself

1. In a lab forest, enable the Recycle Bin, delete an OU containing a user (clear accidental-deletion protection first), and restore it with the two-step PowerShell sequence above.
2. Run `wbadmin start systemstatebackup -backupTarget:E:` on a lab DC (add a second VHDX for E:).
3. Create a test user, take another backup, delete the user, wait for replication, boot into DSRM, restore and run `ntdsutil` authoritative restore on that user's DN, then restart and verify on another DC.
4. On a second DC, perform a non-authoritative SYSVOL sync with ADSI Edit and watch the DFS Replication log for 4114, 4614 and 4604.

## Key takeaways

- The Recycle Bin needs FFL 2008 R2+, is irreversible, and only restores objects deleted after it was enabled and within `msDS-DeletedObjectLifetime` (defaults to tombstone lifetime, 180 days).
- Restore OU trees parent first, then children by `lastKnownParent`.
- DSRM is required for a DC system state restore; reset its password with `ntdsutil "set dsrm password"`.
- Non-authoritative restore lets a DC catch up; authoritative restore with `ntdsutil` makes restored objects win, and must happen before the first normal reboot.
- Import the generated `.ldf` file with `ldifde` to rebuild cross-domain group memberships.
- DFSR SYSVOL is controlled with `msDFSR-Enabled` and `msDFSR-Options` on each DC's SYSVOL Subscription; non-authoritative fixes one DC, authoritative (Options = 1) resets all DCs from one copy.
- Never restore a backup older than the tombstone lifetime.
