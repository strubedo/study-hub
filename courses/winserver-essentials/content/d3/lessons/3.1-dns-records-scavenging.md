## Resource records you must recognize

A zone is a collection of **resource records**. You will create a few by hand and see many more registered automatically.

| Record | Maps | Notes |
|---|---|---|
| SOA | Zone start of authority | One per zone; serial number, refresh/retry/expire timers, primary server |
| NS | Zone or delegation to a name server | Needed for every server that is authoritative or delegated |
| A / AAAA | Name to IPv4 / IPv6 address | The workhorse records |
| CNAME | Alias to a canonical name | Cannot coexist with other records at the same name; cannot sit at the zone apex |
| PTR | IP address to name (reverse zone) | Needed by some logging, mail and security tools |
| MX | Mail exchanger for a domain | Has a preference value; lower is tried first |
| SRV | Service location (host, port, priority, weight) | AD uses these for DC and Kerberos discovery |
| TXT | Free text | SPF, domain verification |

Every record has a **TTL**, the number of seconds other resolvers may cache it. A shorter TTL lets you change an address quickly at the cost of more queries. Lower the TTL a day ahead of a planned IP change, make the change, then raise it again.

## Managing records

```powershell
# Create A record and the matching PTR in one step
Add-DnsServerResourceRecordA -ZoneName 'corp.example.com' -Name 'fs01' `
    -IPv4Address 10.0.0.20 -TimeToLive 01:00:00 -CreatePtr

# Alias
Add-DnsServerResourceRecordCName -ZoneName 'corp.example.com' -Name 'files' `
    -HostNameAlias 'fs01.corp.example.com'

# PTR by hand (reverse zone 0.0.10.in-addr.arpa, record name is the last octet)
Add-DnsServerResourceRecordPtr -ZoneName '0.0.10.in-addr.arpa' -Name '20' `
    -PtrDomainName 'fs01.corp.example.com'

# Query and remove
Get-DnsServerResourceRecord -ZoneName 'corp.example.com' -Name 'fs01'
Get-DnsServerResourceRecord -ZoneName 'corp.example.com' -RRType A
Remove-DnsServerResourceRecord -ZoneName 'corp.example.com' -Name 'oldhost' -RRType A -Force
```

`Add-DnsServerResourceRecordA` also has `-AgeRecord`, which stamps the record so scavenging can remove it later (more on that below). By default a record you add by hand is static: it has no timestamp and is never scavenged. Records in a zone with aging enabled that you create from the GUI get the *Delete this record when it becomes stale* option only if you tick it.

In **DNS Manager** you right-click the zone and choose **New Host (A or AAAA)**, **New Alias (CNAME)**, **New Mail Exchanger (MX)** or **Other New Records**. Tick **Create associated pointer (PTR) record** to build the reverse record at the same time.

Windows clients register their own A and PTR records through **dynamic update**, and domain controllers register their SRV records through the Netlogon service (`ipconfig /registerdns` and `nltest /dsregdns` re-trigger registration). A DHCP server can register records on behalf of clients that cannot, as covered in the DHCP lesson.

> **Watch out:** A secure-updates-only zone gives each dynamically created record an ACL that names the computer as owner. If the old owner is gone (a rebuilt machine with the same name), the new machine cannot overwrite the record and registration fails or the record keeps a stale address. Delete the stale record or add the new computer to the record's ACL.

## Stale records: why scavenging exists

Dynamic registration is easy; deregistration is not. A laptop that crashes, a VM that is deleted, or a client that changes its address leaves its old record behind. Stale A records send users to dead addresses, and stale entries pile up. **Aging and scavenging** removes records that have not been refreshed for a while.

Two settings must both be on, and neither is on by default:

1. **Aging on the zone.** Each dynamically registered record carries a **timestamp**. The zone settings decide how long a record is protected and when it is eligible for removal.
2. **Scavenging on a server.** A server is told to run a scavenging pass periodically; it then deletes eligible records in the zones it is responsible for scavenging.

### The two intervals

| Setting | Default | Meaning |
|---|---|---|
| **No-refresh interval** | 7 days | After a refresh, the timestamp is not updated again for this long. This prevents every refresh from generating AD replication traffic. |
| **Refresh interval** | 7 days | After the no-refresh period ends, the record may be refreshed. If no refresh arrives before this window closes, the record becomes eligible for scavenging. |

A record is eligible when the current time is later than *timestamp + no-refresh + refresh*, so 14 days with defaults. The scavenging pass itself runs at the **scavenging period** (the server's `ScavengingInterval`). When you enable scavenging in the DNS Manager GUI the period defaults to 7 days. So the worst case for a record that stopped refreshing is somewhat over 14 days before it actually disappears.

The Windows DNS client re-registers at start, at address change, and every 24 hours, so a live computer refreshes continuously. Because of the no-refresh interval, most of those refreshes change nothing in the directory.

> **Exam tip:** Aging and scavenging are **disabled by default**. A record is removed only if the zone has aging enabled **and** a server has scavenging enabled **and** the record has a timestamp. Static records (timestamp 0) never age out.

### Turning it on

```powershell
# Server: enable scavenging, run every 7 days, and apply to existing AD-integrated zones
Set-DnsServerScavenging -ScavengingState $true -ScavengingInterval 7.00:00:00 -ApplyOnAllZones

# Zone: enable aging and set the two intervals explicitly
Set-DnsServerZoneAging -Name 'corp.example.com' -Aging $true `
    -NoRefreshInterval 7.00:00:00 -RefreshInterval 7.00:00:00

# Designate which server(s) may scavenge this zone
Set-DnsServerZoneAging -Name 'corp.example.com' -ScavengeServers 10.0.0.10

# Verify and trigger an immediate pass
Get-DnsServerScavenging
Get-DnsServerZoneAging -Name 'corp.example.com'
Start-DnsServerScavenging
```

`ScavengingInterval` is a time span, and the server default is 0, which means scavenging is off. `-ScavengingState` controls whether newly created zones get aging turned on automatically. `-ApplyOnAllZones` pushes the settings to existing AD-integrated zones. Zone-level `ScavengeServers` limits scavenging for that zone to listed servers. On an AD-integrated zone, scavenging can run on any DNS server that holds it, so setting `ScavengeServers` to a single server avoids several servers repeating the work.

In the GUI, enable it in two places: right-click the **server**, **Set Aging/Scavenging for All Zones**, tick *Scavenge stale resource records*, set the intervals, and tick the option to apply to existing AD-integrated zones; then, on the server's **Advanced** tab, tick *Enable automatic scavenging of stale records* and set the period.

Per-record control: on a record in the GUI, **View > Advanced** shows the *Timestamp* and the option **Delete this record when it becomes stale**. `Set-DnsServerResourceRecordAging` resets a record's timestamp to now if you have records that should be treated as dynamic.

### Interaction with DHCP and lease times

Scavenging must be slower than DHCP leases. If a lease is 8 days and records are removed after 4, you delete the records of machines that are simply powered off for a long weekend. The default 14-day eligibility period comfortably exceeds the default Windows DHCP lease of 8 days. If you shorten the DNS intervals, keep them longer than the longest lease.

> **Real world:** Turn on scavenging only after a baseline. Scavenging also deletes records that were created dynamically but belong to devices that cannot re-register (some appliances, Linux hosts using `nsupdate` once). Recreate the ones you need as static records (add them without `-AgeRecord`) before you flip the switch, and review the DNS Server event log afterwards: event ID 2501 reports a scavenging cycle that removed records and 2502 one that removed none.

## Lab it yourself

**GUI**

1. In DNS Manager on DC01 select the `corp.example.com` zone, **New Host**, name `lab01`, address 10.0.0.99, tick **Create associated pointer record**. Then **View > Advanced** and open its properties: static records show *Timestamp: static*.
2. Right-click the server, **Set Aging/Scavenging for All Zones**. Tick *Scavenge stale resource records*, leave 7 and 7 days, apply to existing AD-integrated zones.
3. Open the server **Properties > Advanced** and enable automatic scavenging every 7 days.
4. Right-click the server and choose **Scavenge Stale Resource Records** to run a pass now.

**PowerShell**

```powershell
Add-DnsServerResourceRecordA -ZoneName corp.example.com -Name lab02 -IPv4Address 10.0.0.98 -AgeRecord
Get-DnsServerResourceRecord -ZoneName corp.example.com -Name lab02 | Select-Object HostName, Timestamp, TimeToLive
Set-DnsServerScavenging -ScavengingState $true -ScavengingInterval 7.00:00:00 -ApplyOnAllZones
Get-DnsServerZoneAging -Name corp.example.com
Start-DnsServerScavenging
```

Compare `lab01` (no timestamp) with `lab02` (has one). Only `lab02` can ever be removed.

## Key takeaways

- Know the record types: SOA, NS, A/AAAA, CNAME, PTR, MX, SRV and TXT; CNAMEs cannot share a name with other records.
- `Add-DnsServerResourceRecordA -CreatePtr` makes the reverse record; `Remove-DnsServerResourceRecord -RRType A -Force` deletes.
- Aging and scavenging are off by default and need both a zone setting and a server setting.
- Default no-refresh and refresh intervals are 7 days each, so a record is eligible after 14 days without a refresh.
- Static records have no timestamp and are never scavenged.
- `Set-DnsServerScavenging`, `Set-DnsServerZoneAging` and `Start-DnsServerScavenging` are the core cmdlets.
- Keep the scavenging window longer than the longest DHCP lease.
