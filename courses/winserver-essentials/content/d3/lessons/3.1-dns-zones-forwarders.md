## What the DNS Server role does

The DNS Server role answers two kinds of questions. For names it is **authoritative** for, it answers from its own zones. For everything else it acts as a **recursive resolver**: it asks other servers on the client's behalf and caches the answer. In an Active Directory domain, DNS is not optional. Domain controllers register SRV records so clients can find them, and the DNS role is normally installed on the DCs themselves.

Install it with `Install-WindowsFeature DNS -IncludeManagementTools` (or by promoting a DC, which offers to install it). Manage it with the **DNS Manager** console (`dnsmgmt.msc`) or the **DnsServer** PowerShell module. The service listens on UDP and TCP port 53.

## Zone types

A zone is the portion of the namespace a server is responsible for. Windows Server supports these types:

| Zone type | What it holds | Writable? | Typical use |
|---|---|---|---|
| Primary | Full set of records for the zone | Yes | The normal zone for `corp.example.com` |
| Secondary | A read-only copy pulled by zone transfer from a primary or another secondary | No | Extra query capacity, non-AD servers |
| Stub | Only the SOA, NS and glue A records of another zone | No | Keep delegation data current without a full copy |
| Conditional forwarder | A rule: send queries for this domain to these servers | n/a | Partner or acquired domains |

Any zone can be a **forward lookup zone** (names to addresses) or a **reverse lookup zone** (addresses to names, under `in-addr.arpa` for IPv4 and `ip6.arpa` for IPv6). A primary or stub zone can be stored in a text file under `%SystemRoot%\System32\dns`, or it can be **Active Directory-integrated**.

## AD-integrated zones and replication scope

An AD-integrated zone is stored in the Active Directory database instead of a file. That gives you three things: records replicate with normal AD replication (multi-master, so every DNS server holding the zone can accept updates), **secure dynamic updates** become possible, and you do not manage zone transfers. Only primary zones and stub zones can be AD-integrated. Secondary zones cannot.

You choose where the zone lives with the **replication scope**:

| Scope (`-ReplicationScope`) | Stored in | Replicated to |
|---|---|---|
| `Forest` | `ForestDnsZones` application partition | DNS servers on DCs anywhere in the forest |
| `Domain` | `DomainDnsZones` application partition | DNS servers on DCs in that domain |
| `Legacy` | The domain partition itself | All DCs in the domain, whether or not they run DNS |
| `Custom` | A custom application partition you created (`-DirectoryPartitionName`) | The DCs enrolled in that partition |

For a single-domain forest the practical difference between Forest and Domain is small. Forest scope is the right choice for the `_msdcs.corp.example.com` zone, because clients in any domain need to find DCs and the global catalog, and it is the default Microsoft uses for that zone. `Legacy` exists for compatibility with the original Windows 2000 behaviour and is rarely the right new choice.

> **Exam tip:** "Which replication scope replicates a zone to every DNS server in the forest?" is `Forest` (the `ForestDnsZones` partition). "Replicate only to DNS servers in this domain" is `Domain`. "To all domain controllers in the domain" is the legacy scope, the one that lives in the domain partition.

## Dynamic updates

Each zone has a dynamic update setting:

- **None**: only an administrator can change records.
- **Nonsecure and secure**: any client can register or overwrite records. Avoid it; anyone on the network can poison the zone.
- **Secure only**: only authenticated, authorized computers can create or change a record, and the record's ACL is set to the owner. Available only on AD-integrated zones.

In PowerShell the parameter is `-DynamicUpdate` with values `None`, `NonsecureAndSecure` and `Secure`.

## Creating zones

```powershell
# AD-integrated forward zone, secure updates only
Add-DnsServerPrimaryZone -Name 'corp.example.com' -ReplicationScope Domain -DynamicUpdate Secure

# AD-integrated reverse zone for 10.0.1.0/24
Add-DnsServerPrimaryZone -NetworkId '10.0.1.0/24' -ReplicationScope Domain -DynamicUpdate Secure

# Standard (file-backed) primary zone on a non-DC
Add-DnsServerPrimaryZone -Name 'lab.example.net' -ZoneFile 'lab.example.net.dns'

# Secondary zone: read-only copy pulled from the primary
Add-DnsServerSecondaryZone -Name 'lab.example.net' -ZoneFile 'lab.example.net.dns' -MasterServers 192.168.10.10

# Stub zone
Add-DnsServerStubZone -Name 'partner.example.org' -MasterServers 192.168.50.10 -ReplicationScope Forest
```

A secondary zone only receives data if the primary allows the **zone transfer**. On the primary, set it with `Set-DnsServerPrimaryZone -Name lab.example.net -SecureSecondaries TransferToSecureServers -SecondaryServers 192.168.10.20`. Leaving transfers open to any server lets anyone download your whole zone, a classic reconnaissance leak. A secondary polls the primary on the SOA refresh interval, and the primary can send a notify message to speed that up.

## Forwarders, conditional forwarders and root hints

When a server receives a recursive query for a name outside its zones, it resolves it in this order:

1. Its own authoritative zones (including delegations and stub zones) and its cache.
2. A **conditional forwarder** whose domain matches the name (the longest matching domain wins).
3. The server-level **forwarders**.
4. **Root hints**, the list of root servers it can walk down from, but only if the forwarders did not answer (or none exist) and the forwarder setting still allows root hints.

Server-level forwarders send everything not otherwise resolved to an upstream resolver, such as your ISP, a firewall or a public resolver. If the forwarder does not answer, the server falls back to root hints unless you turn that off. With `-UseRootHint $false` the server only asks its forwarders, which is the safer design when you want all external lookups to pass through a filtering resolver.

```powershell
Set-DnsServerForwarder -IPAddress 192.168.1.1, 1.1.1.1 -UseRootHint $false -Timeout 3
Get-DnsServerForwarder

# Conditional forwarder, AD-integrated so every DNS server in the forest gets it
Add-DnsServerConditionalForwarderZone -Name 'partner.example.org' -MasterServers 192.168.50.10 `
    -ReplicationScope Forest

Get-DnsServerRootHint
```

Conditional forwarders also have an advantage over stub zones in many mergers: they work even if the remote name servers' NS records are not reachable from your network, because you name the exact servers to ask. A stub zone, in contrast, follows the remote zone's own NS list and updates itself when it changes.

> **Watch out:** A DNS server that hosts a zone named `.` (the root zone) is treated as a root server and does not use forwarders or root hints. If forwarding "stops working" after someone created a `.` zone, delete the zone.

> **Real world:** Domain clients should point only at your internal DNS servers, never at a public resolver as a "second DNS server". The client treats all configured servers as equivalent, so it will eventually ask the public one for `_ldap._tcp.dc._msdcs.corp.example.com`, get NXDOMAIN and fail to find a DC. Put the public resolvers in the forwarders list instead.

## Lab it yourself

Use `DC01` (10.0.0.10) and `DC02` (10.0.0.11) from your Domain 2 lab, both running DNS.

**GUI**

1. Open **DNS Manager** on DC01. Expand **Forward Lookup Zones** and open the properties of `corp.example.com`. Confirm **Type** is *Active Directory-Integrated* and **Dynamic updates** is *Secure only*. Use **Change** next to *Replication* to view the scope options.
2. Right-click **Reverse Lookup Zones**, **New Zone**, make an AD-integrated primary zone for `10.0.0.0/24`.
3. Right-click the server name, **Properties**, **Forwarders** tab, add 1.1.1.1. Untick *Use root hints if no forwarders are available* and apply.
4. Right-click **Conditional Forwarders**, **New Conditional Forwarder**, and create one for `partner.example.org` pointing at 192.168.50.10. Tick *Store this conditional forwarder in Active Directory* and choose *All DNS servers in this forest*.

**PowerShell**

```powershell
Get-DnsServerZone | Format-Table ZoneName, ZoneType, IsDsIntegrated, ReplicationScope, DynamicUpdate
Get-DnsServerForwarder
Resolve-DnsName www.example.com -Server DC02
Get-DnsServerZone -Name 'partner.example.org'
```

Break something on purpose: set the forwarder to an unreachable address with `-UseRootHint $false`, run `Resolve-DnsName www.example.com -Server DC01`, and note the timeout. Flip `-UseRootHint $true` and watch it succeed through the root servers (provided the lab has internet access).

## Key takeaways

- Zone types are primary, secondary, stub and conditional forwarding; only primary and stub zones can be AD-integrated.
- Replication scope: `Forest` (ForestDnsZones), `Domain` (DomainDnsZones), `Legacy` (domain partition, all DCs) and `Custom` (your own application partition).
- Secure dynamic updates need an AD-integrated zone; nonsecure updates invite record poisoning.
- Resolution order for outside names: zones and cache, conditional forwarder, server forwarders, root hints.
- `Set-DnsServerForwarder -UseRootHint $false` stops the fallback to root servers.
- Restrict zone transfers to named secondaries.
- Domain clients should use only internal DNS servers; put public resolvers in forwarders.
