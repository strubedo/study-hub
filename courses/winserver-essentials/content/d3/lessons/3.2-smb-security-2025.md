## Why SMB security changed in Windows Server 2025

SMB is the protocol behind most Windows file sharing, and it is also a favorite path for relay attacks, password guessing and lateral movement. Windows Server 2025 and Windows 11 version 24H2 tightened several defaults and added controls. This lesson covers what Microsoft documents: required signing, NTLM blocking on the SMB client, the authentication rate limiter, dialect control, SMB over QUIC and the end of SMB1. The rule for every item below: know **what the default is**, **who it applies to** (server side or client side) and **how to change it**.

## SMB signing required by default

**SMB signing** adds a cryptographic signature to each SMB message, using the session key. A tampered or relayed message fails the signature check, which defeats man-in-the-middle and NTLM relay attacks. Before Windows Server 2025 signing was required by default only for connections to the `SYSVOL` and `NETLOGON` shares on domain controllers (that is, by clients of AD DCs). Starting with Windows Server 2025 and Windows 11 24H2, **signing is required by default for all outbound SMB connections**, so the machine acting as an SMB client refuses to talk to a server that cannot sign.

Two details matter:

- Microsoft's signing article says Windows Server 2025 requires **outbound** signing only. Windows 11 24H2 Enterprise, Pro and Education require both outbound and inbound signing, and Home edition requires neither. Domain controllers keep requiring signing on inbound connections. Read "required by default" as applying to the client role, then check the server role separately with `Get-SmbServerConfiguration`.
- Requiring signing also removes **guest fallback**. A guest or anonymous session cannot sign, so connections to shares that rely on guest access fail. The fix is to give users real credentials, not to turn signing off.

The settings live in both client and server:

```powershell
Get-SmbClientConfiguration | Select-Object RequireSecuritySignature, EnableSecuritySignature
Get-SmbServerConfiguration | Select-Object RequireSecuritySignature, EnableSecuritySignature

# Only if you have a documented, risk-accepted need:
Set-SmbClientConfiguration -RequireSecuritySignature $false
Set-SmbServerConfiguration -RequireSecuritySignature $true
```

In Group Policy these are *Computer Configuration > Windows Settings > Security Settings > Local Policies > Security Options*: **Microsoft network client: Digitally sign communications (always)** and **Microsoft network server: Digitally sign communications (always)**. The Windows Admin Center file-shares settings also offer a signing choice for the server.

> **Exam tip:** After an upgrade to 2025 or Windows 11 24H2, "access denied" or "the specified network name is no longer available" when connecting to a NAS, an old Samba box or a guest share is the signature symptom of required signing. The correct response is to enable signing on the remote device or replace it. The wrong response is disabling signing clients-wide.

Signing and encryption can use AES-based algorithms on SMB 3.1.1 (AES-128-GMAC for signing, AES-GCM or AES-CCM for encryption). SMB 3.1.1 also adds pre-authentication integrity, which protects the dialect negotiation from downgrade tampering. Windows Server 2025 adds **auditing** for signing and encryption so you can see which clients lack support before you enforce it everywhere.

## SMB encryption

**SMB encryption** (SMB 3.0 and later) protects the data itself from eavesdropping, and you can require it per share or for the whole server:

```powershell
Set-SmbShare -Name Finance -EncryptData $true -Force
Set-SmbServerConfiguration -EncryptData $true -Force   # all shares
```

Clients that do not support SMB 3.x encryption cannot reach an encrypted share unless you allow unencrypted access with `-RejectUnencryptedAccess $false`, which defeats the purpose. Encryption also covers signing's job on those connections. Choose it for untrusted network segments and sensitive shares; the CPU cost on modern hardware with AES acceleration is small.

## Blocking NTLM on the SMB client

NTLM is the older challenge-response authentication that falls back when Kerberos cannot be used (connecting by IP address, to a workgroup server, or to a host with no SPN). It is vulnerable to relay, pass-the-hash and offline cracking. Windows Server 2025 and Windows 11 24H2 add **NTLM blocking to the SMB client**, so outbound SMB connections cannot use NTLM at all.

Key facts:

- It is an **SMB client** feature. The destination server can be any operating system where Kerberos (or PKU2U) works.
- It is **off by default**; you opt in.
- Enable with `Set-SmbClientConfiguration -BlockNTLM $true`, or Group Policy *Computer Configuration > Administrative Templates > Network > Lanman Workstation > Block NTLM (LM, NTLM, NTLMv2)*.
- A **Block NTLM Server Exception List** policy in the same folder lists IP addresses, NetBIOS names and FQDNs of servers that may still use NTLM, such as an NAS that is not domain-joined. There is no dedicated cmdlet for the list; you set the policy or its registry value.
- You can block NTLM for a single mapping: `net use \\fs01\Finance /BLOCKNTLM` or `New-SmbMapping -RemotePath \\fs01\Finance -BlockNTLM $true`.

```powershell
Set-SmbClientConfiguration -BlockNTLM $true -Force
New-SmbMapping -LocalPath Z: -RemotePath \\fs01.corp.example.com\Finance -BlockNTLM $true
```

> **Watch out:** After enabling NTLM blocking, `\\10.0.0.20\Finance` (an IP address) fails because Kerberos needs a name that resolves to an SPN. Use `\\fs01.corp.example.com\Finance`. Missing SPNs and DNS aliases (CNAMEs that have no SPN) cause the same failure.

## Authentication rate limiter

Brute-force guessing against SMB sends many NTLM or PKU2U attempts per second. The **SMB authentication rate limiter** is an SMB *server* feature, **enabled by default** in Windows Server 2025 and Windows 11 24H2. It inserts a delay after each failed NTLM or PKU2U authentication; the default is 2 seconds (2000 ms). The value must be a multiple of 100 within 0 to 10000, and 0 disables it. It does not affect Kerberos, because Kerberos authenticates before SMB connects.

```powershell
Get-SmbServerConfiguration | Format-List InvalidAuthenticationDelayTimeInMs
Set-SmbServerConfiguration -InvalidAuthenticationDelayTimeInMs 4000 -Force
```

A Group Policy named **Enable authentication rate limiter** (*Network > Lanman Server*) switches it on or off; the delay value itself is set with PowerShell. It complements, and does not replace, account lockout and monitoring.

## Dialect control

Windows negotiates the highest SMB dialect both sides support, from 2.0.2 up to 3.1.1. Windows Server 2025 documents **SMB dialect management**: you can set a minimum and maximum SMB 2/3 dialect on the server and client.

```powershell
Set-SmbServerConfiguration -Smb2DialectMin SMB300 -Smb2DialectMax SMB311 -Force
Set-SmbClientConfiguration -Smb2DialectMin SMB311 -Smb2DialectMax SMB311 -Force
```

Dialect values include `SMB202`, `SMB210`, `SMB300`, `SMB302` and `SMB311`. Locking everything to 3.1.1 gets you pre-authentication integrity but can break older clients, so audit first.

## SMB over QUIC

**SMB over QUIC** tunnels SMB inside a **TLS 1.3**-encrypted QUIC session over **UDP port 443**, instead of TCP 445. That makes it suitable for mobile and branch users to reach a file server over the internet without a VPN, because the connection is encrypted and authenticated inside the tunnel, and NTLM exchanges happen only inside it.

Availability: before Windows Server 2025 the SMB over QUIC server needed Windows Server 2022 **Datacenter: Azure Edition**. Windows Server 2025 makes the server feature available in **both Standard and Datacenter**. The client requires Windows 11 or Windows Server 2025.

What you need:

- A server certificate whose subject alternative names match the names clients use, issued by a CA the client trusts, with a private key.
- UDP 443 inbound reachable; clients resolve the server's FQDN from DNS or a hosts file.
- On Windows Server 2025 you configure it with **PowerShell** (the Windows Admin Center method is not currently supported for 2025):

```powershell
$cert = Get-ChildItem Cert:\LocalMachine\My | Where-Object Subject -Match 'fs01.corp.example.com'
New-SmbServerCertificateMapping -Name 'fs01.corp.example.com' -Thumbprint $cert.Thumbprint -StoreName My
Get-SmbServerCertificateMapping

# Client-side test
New-SmbMapping -RemotePath \\fs01.corp.example.com\Finance -TransportType QUIC
net use \\fs01.corp.example.com\Finance /TRANSPORT:QUIC
```

Server 2025 adds **client access control**: the server can require a client certificate (`New-SmbServerCertificateMapping ... -RequireClientAuthentication $true`) and permit only certain clients or issuers with `Grant-SmbClientAccessToServer -Name <server> -IdentifierType SHA256|ISSUER -Identifier <value>`; clients map their certificate with `New-SmbClientCertificateMapping`. Administrators can disable the client side with `Set-SmbClientConfiguration -EnableSMBQUIC $false`, and the server with `Set-SmbServerConfiguration -EnableSMBQUIC $false`. Windows Server 2025 also supports **alternative SMB ports** for TCP, QUIC and RDMA (defaults 445, 443 and 5445), when the server is configured to listen on them.

## SMB1 status

SMB1 is deprecated and **not installed by default** on a clean install of Windows Server 2019 and later, including Windows Server 2025. Microsoft strongly recommends keeping it off; it has the weaknesses ransomware such as WannaCry abused. If a legacy device needs it, update or replace the device. Check and manage:

```powershell
Get-SmbServerConfiguration | Format-List EnableSMB1Protocol, AuditSmb1Access
Set-SmbServerConfiguration -EnableSMB1Protocol $false -Force
Set-SmbServerConfiguration -AuditSmb1Access $true -Force   # logs SMB1 use before you remove it
```

Related point: **remote mailslots** are disabled by default in Windows Server 2025.

## Lab it yourself

Use `FS01` and a Windows 11 24H2 or Server 2025 client in the Hyper-V lab.

**GUI**

1. On FS01 open **Group Policy Management** and create a GPO linked to the file server OU. Under *Security Options* open *Microsoft network server: Digitally sign communications (always)* and read the explanation.
2. In **Server Manager > Shares**, open the share properties, tick **Encrypt data access**.
3. In the client GPO editor go to *Administrative Templates > Network > Lanman Workstation* and read **Block NTLM (LM, NTLM, NTLMv2)** and **Block NTLM Server Exception List**.

**PowerShell**

```powershell
Get-SmbServerConfiguration | Format-List RequireSecuritySignature, EncryptData, InvalidAuthenticationDelayTimeInMs, EnableSMB1Protocol
Get-SmbClientConfiguration | Format-List RequireSecuritySignature, BlockNTLM, EnableSMBQUIC
Get-SmbConnection | Format-Table ServerName, ShareName, Dialect, Signed, Encrypted
```

Then connect to `\\10.0.0.20\Finance`, then `\\fs01.corp.example.com\Finance`, with `-BlockNTLM $true` enabled, and compare. Use `Get-SmbConnection` to confirm the dialect is 3.1.1 and the session is signed.

## Key takeaways

- Windows Server 2025 requires SMB signing for outbound connections by default; inbound signing is not required by default on the server edition, and signing also disables guest fallback.
- NTLM blocking is an SMB client feature in 2025 and Windows 11 24H2, off by default, enabled with `Set-SmbClientConfiguration -BlockNTLM $true`; use an exception list for non-Kerberos targets and connect by FQDN.
- The authentication rate limiter is a server feature, on by default, 2000 ms delay between failed NTLM or PKU2U attempts, set with `InvalidAuthenticationDelayTimeInMs` (0 disables).
- SMB dialect minimum and maximum are set with `-Smb2DialectMin` and `-Smb2DialectMax`.
- SMB over QUIC uses UDP 443 and TLS 1.3 with a certificate, and is available in Standard and Datacenter in 2025; configure it with `New-SmbServerCertificateMapping`.
- SMB1 is not installed by default and should stay off; audit with `AuditSmb1Access`.
- SMB encryption is optional (per share or server) and requires SMB 3.x clients.
