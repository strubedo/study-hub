## Moving and protecting VMs: the big picture

Three different features answer three different questions, and exams love to swap them:

| Feature | Question it answers | Downtime | Needs shared storage? |
|---|---|---|---|
| **Live migration** | Move a running VM to another host for maintenance or balancing | None (planned) | No (shared-nothing works) |
| **Storage migration** | Move a running VM's files to different storage | None | No |
| **Hyper-V Replica** | Keep an asynchronous copy for disaster recovery | Failover takes a restart of the replica VM | No |
| **Failover clustering** | Restart VMs automatically on another node after a host failure | Brief, unplanned | Yes (CSV or SMB share) |

## Live migration

Live migration moves a running VM between Hyper-V hosts with no perceptible downtime. It works between clustered nodes or between **standalone** hosts (the "shared-nothing" scenario copies memory and storage over the network). It is available only for Hyper-V on Windows Server, not on client Hyper-V.

Prepare each host:

```powershell
Enable-VMMigration
Set-VMMigrationNetwork 192.168.10.1
Set-VMHost -VirtualMachineMigrationAuthenticationType Kerberos
Set-VMHost -VirtualMachineMigrationPerformanceOption Compression   # default; also TCP, SMB
```

Then move a VM:

```powershell
Move-VM -Name APP01 -DestinationHost HV02 -IncludeStorage -DestinationStoragePath 'D:\Hyper-V\APP01'
```

Key decisions:

- **Authentication**. **Kerberos** lets you start the move from a remote console but requires **constrained delegation** on each host's computer account in Active Directory (delegate the `cifs` and `Microsoft Virtual System Migration Service` services of the partner host, using any authentication protocol). **CredSSP** needs no delegation but requires that you sign in to the source host, and the move back later requires signing in to the other host.
- **Windows Server 2025 changes the default story.** Credential Guard is now enabled by default on domain-joined servers that are not domain controllers, which blocks CredSSP-based live migration after an upgrade. Microsoft's guidance is to use Kerberos constrained delegation. The symptom is error 0x8009030E "No credentials are available in the security package".
- **Performance options**. *Compression* (the default) compresses memory over TCP/IP; *TCP/IP* sends it uncompressed; *SMB* uses SMB 3, benefiting from SMB Direct (RDMA) and SMB Multichannel.
- **Network**. Live migration traffic is not encrypted on the wire by default. Isolate it on a private network or VLAN.
- **Compatibility**. Different CPU generations from the same vendor need **processor compatibility mode** (`Set-VMProcessor -CompatibilityForMigrationEnabled $true`). In 2025 clusters, **dynamic processor compatibility** calculates the common feature set across nodes automatically. The destination needs the same virtual switch names, and the VM configuration version must be supported; shared VHDX disks cannot be migrated with standard methods.

> **Exam tip:** Live migration with Kerberos needs constrained delegation; with CredSSP it needs a sign-in to the source host. On a freshly upgraded 2025 server, a failing CredSSP live migration points to Credential Guard.

## Hyper-V Replica

Replica provides **asynchronous** replication of a VM's virtual disks from a primary host to a replica host, for disaster recovery without shared storage. Changes are tracked with resilient change tracking and shipped in `.hrl` log files at the interval you select.

| Setting | Options |
|---|---|
| Replication frequency | 30 seconds, 5 minutes or 15 minutes |
| Authentication | Kerberos over HTTP (port 80) for domain-joined hosts; certificate-based over HTTPS (port 443) for non-domain or encrypted traffic |
| Recovery points | Latest only (default), or up to 24 additional hourly points; optional VSS snapshots for application consistency |
| Initial copy | Over the network (immediately or scheduled up to seven days out), external media, or an existing restored VM |
| Extended replication | Replicate from the replica to a third site; only 5 or 15 minute frequency |
| Disks replicated | All by default; exclude page-file or scratch disks to save bandwidth |
| Clusters | Use the **Hyper-V Replica Broker** role as the receiving endpoint |

You configure the **receiving** host first, then enable replication per VM on the primary. The Windows Firewall rules (`Hyper-V Replica HTTP Listener (TCP-In)` for Kerberos and `Hyper-V Replica HTTPS Listener (TCP-In)` for certificate authentication) exist after the role is installed but are not enabled by default.

```powershell
# On the replica server (HV02)
Set-VMReplicationServer -ReplicationEnabled $true -AllowedAuthenticationType Kerberos `
  -ReplicationAllowedFromAnyServer $true -DefaultStorageLocation 'D:\Replica'
Enable-NetFirewallRule -DisplayName 'Hyper-V Replica HTTP Listener (TCP-In)'

# On the primary (HV01)
Enable-VMReplication -VMName APP01 -ReplicaServerName HV02.corp.example.com `
  -ReplicaServerPort 80 -AuthenticationType Kerberos -ReplicationFrequencySec 300
Start-VMInitialReplication -VMName APP01
Get-VMReplication
```

Failover types:

- **Test failover** creates a temporary VM from the replica on an isolated network; the production replication continues.
- **Planned failover** shuts down the primary, sends remaining changes with no data loss, and starts the replica. Use `Start-VMFailover -Prepare` on the primary, then `Start-VMFailover` on the replica.
- **Unplanned failover** starts the replica from its latest recovery point after a disaster. Some data since the last replication cycle may be lost.
- After a failover, **reverse replication** (`Set-VMReplication -Reverse`) sends changes back to the original host so it can resume as primary (failback).

> **Watch out:** Replica is disaster recovery, not high availability and not backup. Failover is a deliberate action (or scripted), the replica VM is offline until failover, and a 5-minute frequency means up to roughly five minutes of data loss. Azure Site Recovery, covered in the recovery topic, extends the same idea to Azure.

## GPU partitioning in Windows Server 2025

**GPU partitioning (GPU-P)** shares one physical GPU among many VMs, giving each VM a dedicated slice of the GPU's resources. It uses **SR-IOV**, which gives a hardware-backed security boundary and predictable performance for each VM. It is the density-oriented counterpart to **Discrete Device Assignment (DDA)**, which hands an entire GPU to a single VM. Windows Server 2025 adds **live migration of VMs that have a GPU partition**, which was not possible before.

Requirements and limits, from Microsoft's documentation:

- Host runs **Windows Server 2025** with the Hyper-V role. GPU-P is designed for **standalone servers**; for clustering (to handle unplanned downtime) you need **Datacenter**, as noted in the edition comparison in Domain 1.
- The same GPU make, model and size on every server, with the same partition count. Mixed vendors or mixed product families in one cluster are unsupported.
- Virtualization support and **SR-IOV** enabled in firmware.
- Live migration needs processors with **IOMMU DMA bit tracking** (Intel VT-d, AMD-Vi), for example AMD EPYC 7003 (Milan) or later and 4th Gen Intel Xeon Scalable. EPYC 7002 (Rome) supports GPU-P but not live migration with it. Without IOMMU-capable CPUs, VMs restart elsewhere on failover instead.
- Supported GPUs include NVIDIA A2, A10, A16, A40, L2, L4, L40, L40S, RTX Pro 6000 Blackwell Server Edition and AMD Radeon PRO V710. For NVIDIA, live migration needs the driver from NVIDIA vGPU software 18.x or later.
- Guest OS: Windows 10 or later, Windows 10 Enterprise multi-session or later, Windows Server 2019 or later, and Ubuntu 18.04, 20.04 and 22.04 LTS.
- Only **one** GPU partition per VM, and the VM and partition must be on the same host. A GPU is either a DDA device or a partitionable GPU, never both. You cannot choose which partition a VM gets.
- During live migration of a VM with a GPU partition, Hyper-V automatically uses **TCP/IP with compression**, which can raise host CPU use and lengthen the move.
- Install the vendor driver in the host and in each guest. Desktop-class hardware and client OS hosts are unsupported.

PowerShell workflow (Windows Admin Center's **GPUs** extension automates validation for clusters and is the recommended tool):

```powershell
Get-VMHostPartitionableGpu | Format-List Name, ValidPartitionCounts
Add-VMGpuPartitionAdapter -VMName AI01
Get-VMGpuPartitionAdapter -VMName AI01 | Format-List InstancePath, PartitionId, PartitionVfLuid
```

After you configure the partition count on the host GPU, start the VM and a GPU appears in Device Manager once the vendor driver is installed.

> **Exam tip:** Many VMs sharing one GPU is **GPU-P**; one VM owning the whole GPU is **DDA**. GPU-P live migration is new in Windows Server 2025 and relies on SR-IOV and IOMMU DMA tracking.

## Lab it yourself

Nested virtualization (`Set-VMProcessor -ExposeVirtualizationExtensions $true` on the outer VM, with MAC address spoofing on its adapter) lets you rehearse everything here with two virtual hosts on your laptop. GPU partitioning is the exception, since nested lab VMs have no SR-IOV GPU; for GPU-P read the output of the cmdlets in the documentation instead.

1. Build `HV01` and `HV02` as nested Hyper-V hosts on an internal switch with addresses 192.168.10.11 and 192.168.10.12, and join them to `corp.example.com` if you have DC01 (otherwise use certificate or CredSSP in a workgroup).
2. Run `Enable-VMMigration` and `Set-VMHost -VirtualMachineMigrationAuthenticationType Kerberos` on both. Configure constrained delegation for `cifs` and the migration service in Active Directory Users and Computers.
3. Create a small Generation 2 VM on HV01 and run `Move-VM -Name APP01 -DestinationHost HV02 -IncludeStorage -DestinationStoragePath D:\VMs\APP01`. Ping the VM during the move.
4. Configure HV02 as a replica server with `Set-VMReplicationServer`, enable the firewall rule, and replicate a VM from HV01 with `Enable-VMReplication`. Run a test failover from Hyper-V Manager.
5. Do a planned failover and then reverse replication.

## Key takeaways

- Live migration moves running VMs with no downtime and works between standalone hosts; Kerberos needs constrained delegation, CredSSP needs a source-host sign-in.
- In Windows Server 2025, default Credential Guard breaks CredSSP live migration; use Kerberos.
- Live migration traffic is unencrypted; isolate it. Compression is the default performance option.
- Hyper-V Replica is asynchronous DR: 30 s, 5 min or 15 min, Kerberos on 80 or certificates on 443, up to 24 extra hourly recovery points, optional extended replication.
- Replica is not HA and not backup; know test, planned and unplanned failover and reverse replication.
- GPU-P (new live migration in 2025) shares one GPU via SR-IOV across VMs; DDA gives a whole GPU to one VM.
- GPU-P live migration needs IOMMU DMA bit tracking CPUs, matching GPUs on all hosts, NVIDIA vGPU 18.x or later drivers, and falls back to compressed TCP/IP.
