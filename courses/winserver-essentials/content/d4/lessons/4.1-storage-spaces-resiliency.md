## What Storage Spaces does

**Storage Spaces** pools physical disks and presents resilient virtual disks carved out of the pool. You get software-defined redundancy without a hardware RAID controller. The model has three layers, and exam questions test whether you can name them in order:

1. **Physical disks** that are blank and poolable (`Get-PhysicalDisk -CanPool $true`).
2. **Storage pool**, a collection of physical disks, created with `New-StoragePool`.
3. **Virtual disk** (the "space"), created inside the pool with a resiliency type, provisioning type and size. From the virtual disk you then create one or more **volumes** (`New-Volume`), formatted NTFS or ReFS.

The same engine runs in two shapes. **Storage Spaces** on a single server uses the disks in that server or a JBOD. **Storage Spaces Direct (S2D)** pools local disks across clustered servers and needs Datacenter edition (Standard does not include it). This lesson focuses on the single-server model and states the S2D figures where the exam compares them. A storage space cannot host the Windows operating system.

## Resiliency types and minimum disks

Storage Spaces supports three primary resiliency types: **simple**, **mirror** and **parity**.

| Resiliency | What it does | Tolerates | Minimum physical disks (single server) | Usable capacity |
|---|---|---|---|---|
| Simple | Stripes data, no redundancy | Nothing; one disk failure loses the space | 1 | 100% |
| Two-way mirror | Two copies of every write | 1 disk failure | 2 | 50% (50% overhead) |
| Three-way mirror | Three copies | 2 simultaneous disk failures | 5 | About 33% |
| Parity (single) | Stripes data plus parity, like RAID 5 | 1 disk failure | 3 | Better than mirror; grows with disk count |

Microsoft's standalone deployment guide gives those minimums: at least two disks for a mirror to survive one failure, at least five to survive two, and at least three for parity. Mirror suits general file shares, VHD libraries and VM storage because it has the best write performance. Parity suits highly sequential workloads such as archives and backup targets; its writes are slower because parity must be calculated. A mirror space uses dirty region tracking to bring copies back into sync after an unclean shutdown, and parity uses journaling to protect against corruption in that case.

For S2D clusters the minimum is counted in **fault domains**, normally servers, not disks:

| S2D resiliency | Minimum servers | Failures tolerated | Storage efficiency |
|---|---|---|---|
| Two-way mirror | 2 | 1 | 50% |
| Three-way mirror | 3 | 2 | 33.3% |
| Single parity (discouraged) | 3 | 1 | Better than mirror |
| Dual parity (like RAID 6) | 4 | 2 | 50% at four servers, up to 80% at larger scale |
| Mirror-accelerated parity (mixed) | 4 | 2 | Between 33.3% and 80% |

Nested resiliency, for two-server clusters, survives two failures at once but is only about 25% efficient for nested two-way mirror. For two-way mirror the number of drives per server does not change which resiliency types you may use.

> **Exam tip:** "Capacity" questions are arithmetic. 12 TB of raw disks gives about 12 TB simple, 6 TB two-way mirror and 4 TB three-way mirror. Always check whether the question counts raw or usable space, and whether the minimum is in disks (standalone) or servers (S2D).

> **Watch out:** Microsoft discourages single parity in clusters, because it can only safely tolerate one failure at a time. With three servers it recommends three-way mirroring instead.

## Provisioning, columns and tiering

When you create a virtual disk you choose **thin** or **fixed** provisioning. Thin allocates pool capacity as data is written, so you can create virtual disks larger than the pool and add disks later; watch pool free space. Fixed allocates up front. PowerShell also exposes the **number of columns** (how many disks a stripe spans) and **interleave**, which affect performance. Virtual disks can be resized, and you can add disks to an existing pool to grow it.

Microsoft's Storage Spaces overview also describes **Storage Bus Cache**, which uses fast NVMe or SSD devices as a cache layer in front of slower HDDs in a Storage Spaces deployment.

## PowerShell workflow

```powershell
# 1. Find poolable disks
Get-PhysicalDisk -CanPool $true

# 2. Create the pool from all poolable disks
New-StoragePool -FriendlyName Pool1 `
  -StorageSubsystemFriendlyName 'Windows Storage*' `
  -PhysicalDisks (Get-PhysicalDisk -CanPool $true)

# 3. Create a two-way mirror virtual disk and a volume on it in one step
New-Volume -StoragePoolFriendlyName Pool1 -FriendlyName Data `
  -FileSystem ReFS -ResiliencySettingName Mirror `
  -ProvisioningType Thin -Size 500GB -DriveLetter E

# Check health
Get-VirtualDisk | Select FriendlyName, ResiliencySettingName, HealthStatus, OperationalStatus
Get-StoragePool -IsPrimordial $false
```

`-StorageSubsystemFriendlyName 'Windows Storage*'` points the pool at the local Windows storage subsystem. `-ResiliencySettingName` accepts `Simple`, `Mirror` and `Parity`. To get a three-way mirror or dual parity you set `-NumberOfDataCopies 3` or `-PhysicalDiskRedundancy 2` on `New-VirtualDisk`, and the pool must have enough disks. Replace a failed drive with `Add-PhysicalDisk` and `Remove-PhysicalDisk` after setting the old disk to retired, then watch the repair with `Get-StorageJob`.

Sample health output after a drive fails in a two-way mirror:

```text
PS C:\> Get-VirtualDisk | Select FriendlyName, ResiliencySettingName, HealthStatus, OperationalStatus

FriendlyName ResiliencySettingName HealthStatus OperationalStatus
------------ ---------------------- ------------ -----------------
Data         Mirror                 Warning      Degraded
```

A Degraded mirror is still online and serving data but has lost redundancy; a second failure before repair would be fatal. Add a replacement disk and let the repair job run.

## Choosing the right answer

- Scratch data or data the application already replicates: simple.
- VM storage, databases, general shares: mirror.
- Archive and backup targets where capacity matters more than write speed: parity.
- Two servers: two-way mirror (or nested resiliency). Three servers: three-way mirror. Four or more: dual parity or mirror-accelerated parity.
- Any need to protect the Windows boot volume itself: Storage Spaces cannot do it; use a hardware mirror or hypervisor storage.

## Lab it yourself

You need a Windows Server 2025 VM (inside Hyper-V on your laptop, with nested virtualization if you also want the Hyper-V lessons later) and five extra 10 GB virtual disks.

1. Attach five blank VHDX files to the VM and confirm `Get-PhysicalDisk -CanPool $true` lists them.
2. Create the pool with `New-StoragePool` as above.
3. Create a two-way mirror volume, then a parity volume, then try a three-way mirror with `New-VirtualDisk -ResiliencySettingName Mirror -NumberOfDataCopies 3 -UseMaximumSize`. Note which succeed with five disks.
4. Copy a file onto the mirror volume. On the host, power off the VM and detach one VHDX, start the VM, and run `Get-VirtualDisk`. The mirror should show Degraded but the file is still readable.
5. Reattach the disk (or add a new one) and run `Get-StorageJob` to watch the repair.

## Key takeaways

- Physical disks, then pool, then virtual disk, then volume. A storage space cannot host the OS.
- Simple (1 disk, no redundancy), two-way mirror (2 disks, 50%), three-way mirror (5 disks standalone, 33%), parity (3 disks).
- S2D minimums are servers: two-way 2, three-way 3, dual parity 4; S2D needs Datacenter.
- Mirror is for performance-sensitive and VM data; parity is for sequential archive and backup.
- Thin provisioning allocates on write and lets virtual disks exceed pool size; watch free space.
- `New-StoragePool`, `New-VirtualDisk`, `New-Volume`, `Get-VirtualDisk`, `Get-StorageJob` are the cmdlets that matter.
- Storage Bus Cache is the documented way to accelerate HDD pools with NVMe or SSD.
