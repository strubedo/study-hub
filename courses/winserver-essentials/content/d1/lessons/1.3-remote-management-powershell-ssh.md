## Pick the tool

| Tool | Where it runs | Best for | Transport |
|---|---|---|---|
| Server Manager | Console on a Desktop Experience server or Windows client with RSAT | Several servers in groups, roles and features, event/service status | WinRM |
| Windows Admin Center (WAC) | Browser to a gateway (server or client) | Modern GUI for servers, clusters, Hyper-V, files, certificates | HTTPS to gateway (443), WinRM to targets |
| PowerShell remoting | Any PowerShell session | Automation, scale, Server Core | WinRM (5985 HTTP, 5986 HTTPS) |
| OpenSSH | ssh client, or PowerShell 7 remoting | Cross-platform admins, key-based logins | SSH (22) |
| RDP | Remote Desktop client | Last resort GUI sessions | 3389 |

## Server Manager and remote server groups

Server Manager's **server pool** lists every server you have added. Add servers with **Manage > Add Servers** from Active Directory, DNS, or an imported file. Use **Manage As** when the server needs different credentials (workgroup or other domain). You can create **server groups** (custom collections such as "Web tier") so you can view events, services and best-practice results for a group at once and install roles to several servers in one wizard run.

Limits from Microsoft's documentation: Server Manager can manage servers running its own version **or older** (not a newer release than itself), and Microsoft's tests showed up to about **100 servers** with a typical workload; beyond that use System Center-class tooling. Server Manager can manage Server Core targets.

> **Exam tip:** A Server Manager from 2016 cannot manage a 2025 server. Run Server Manager (or RSAT) from a 2025 or Windows 11 machine.

## Windows Admin Center

WAC is a browser-based management tool, **free** with Windows Server licenses, downloaded separately. Install modes:

- **Gateway server:** installed on a Windows Server (not a domain controller; **installing on a DC is unsupported**). The installer's default is **port 443 (HTTPS)**, using a certificate you supply or a self-signed one for tests.
- **Local client:** installed on Windows 11 and reached at `https://localhost:6516`.
- **Managed server** and **failover cluster** (high availability, active-passive) modes also exist.

WAC fully supports managing **Windows Server 2016 and later**, with limited functionality for 2012 (it needs WMF 5.1). Use Edge or Chrome. Only the latest WAC release is supported; stay within 30 days of new releases. In Azure, **Windows Admin Center in Azure for Arc** reaches Arc-enabled servers without a VPN or inbound ports.

> **Real world:** WAC is Microsoft's preferred GUI for Server Core and 2025, but Server Manager and MMC snap-ins still work and some tasks remain easier there.

## PowerShell remoting over WinRM

PowerShell remoting uses **Windows Remote Management (WinRM)**, Microsoft's implementation of WS-Management. Facts:

- **Ports:** HTTP **5985**, HTTPS **5986**.
- **Enabled by default** on Windows Server 2012 R2 and later. `Enable-PSRemoting` restores the defaults (starts WinRM, sets it to automatic, creates a listener on any IP, enables the firewall exception, creates session configurations).
- On **server** versions the firewall rule for Public networks allows only the **same local subnet** until you change it; the Domain and Private profile rules allow all.
- By default only members of **Administrators** can connect. Sessions run as the connecting user.
- It is *not* the same as a cmdlet's `-ComputerName` parameter, which often uses RPC.

```powershell
# Interactive 1:1 session
Enter-PSSession -ComputerName FS01
[FS01]: PS C:\Users\jsmith\Documents> hostname
FS01
[FS01]: PS C:\Users\jsmith\Documents> Exit-PSSession

# One command on many servers, results tagged with PSComputerName
Invoke-Command -ComputerName FS01, HV01 -ScriptBlock { Get-Service WinRM }

# Reuse a session
$s = New-PSSession -ComputerName FS01
Invoke-Command -Session $s -ScriptBlock { Get-Date }
Remove-PSSession $s
```

Use `Enter-PSSession` to work on one machine; use `Invoke-Command` for automation and fan-out. Objects returned by `Invoke-Command` carry a `PSComputerName` property and are deserialized copies.

### Kerberos, workgroups and TrustedHosts

In a domain, the client authenticates to the server with **Kerberos** using the server's **name**. Using an IP address, or connecting from or to a workgroup machine, drops back to NTLM, which WinRM over HTTP does not accept unless the target is trusted:

```text
Connecting to remote server 192.168.10.21 failed with the following error message : The WinRM client cannot
process the request. If the authentication scheme is different from Kerberos, or if the client computer is not
joined to a domain, then HTTPS transport must be used or the destination machine must be added to the
TrustedHosts configuration setting.
```

Fixes: connect by FQDN from a domain-joined client, configure an **HTTPS listener** with a certificate, or (lab only) on the client run `Set-Item WSMan:\localhost\Client\TrustedHosts -Value 'FS01' -Force`. TrustedHosts only controls what the client will talk to; it does not encrypt anything.

Troubleshooting commands: `Test-WSMan FS01`, `Get-Service WinRM`, `Get-NetFirewallRule -Name 'WINRM*'`, `Get-WSManInstance winrm/config/listener -Enumerate`. To open Public-profile access from other subnets: `Set-NetFirewallRule -Name 'WINRM-HTTP-In-TCP-PUBLIC' -RemoteAddress Any` (the rule name can vary by version, so check first).

## OpenSSH server on Windows Server 2025

In earlier versions OpenSSH was an optional capability you installed. In **Windows Server 2025 the server component is installed by default but not enabled**. Server Manager adds a **Remote SSH Access** switch, and an **OpenSSH Users** group lets you allow or restrict users.

```powershell
Start-Service sshd
Set-Service -Name sshd -StartupType Automatic
Get-NetFirewallRule -Name 'OpenSSH-Server-In-TCP'   # inbound TCP 22
```

If a server is older or the capability was removed: `Add-WindowsCapability -Online -Name OpenSSH.Server~~~~0.0.1.0`.

Windows-specific points: configuration lives in `%ProgramData%\ssh\sshd_config`; administrators' public keys go in `%ProgramData%\ssh\administrators_authorized_keys` (permissions only for SYSTEM and Administrators); the default login shell is set with the `DefaultShell` value under `HKLM:\SOFTWARE\OpenSSH`.

**PowerShell remoting over SSH** needs PowerShell 7 (6 or later) on both machines and a `Subsystem powershell` line in `sshd_config`. Windows PowerShell 5.1 cannot use it. The cmdlets use `-HostName`, `-UserName` and `-KeyFilePath` instead of `-ComputerName`:

```powershell
Enter-PSSession -HostName FS01 -UserName jsmith
```

> **Watch out:** WinRM (5985/5986) and SSH (22) are separate transports with separate firewall rules. Opening one does not open the other.

## Lab it yourself

1. With two lab VMs (DC01 and FS01, or two workgroup VMs), run `Test-WSMan FS01` from the other.
2. Run `Enter-PSSession -ComputerName FS01`, then `Invoke-Command -ComputerName FS01, DC01 -ScriptBlock { $env:COMPUTERNAME }` and note `PSComputerName`.
3. If you are in a workgroup, reproduce the TrustedHosts error, then fix it with `Set-Item WSMan:\localhost\Client\TrustedHosts`.
4. On FS01 run `Start-Service sshd`, then from your PC `ssh jsmith@192.168.10.21`.
5. Install Windows Admin Center on the PC in local-client mode and add FS01.

## Key takeaways

- WinRM listens on 5985 (HTTP) and 5986 (HTTPS); remoting is on by default on servers and restored with `Enable-PSRemoting`.
- On servers the Public-profile firewall rule is limited to the local subnet.
- Kerberos needs names and a domain; workgroup clients need HTTPS or TrustedHosts.
- `Enter-PSSession` is one machine interactively; `Invoke-Command` fans out and tags objects with `PSComputerName`.
- Server Manager manages equal or older versions only; WAC gateway defaults to 443 and is unsupported on domain controllers.
- OpenSSH server is installed but not enabled in 2025: start `sshd`, set it automatic, port 22.
- PowerShell over SSH needs PowerShell 7 and a Subsystem entry.
