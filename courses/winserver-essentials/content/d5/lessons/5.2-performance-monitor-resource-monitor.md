## Which tool for which question

| Tool | Launch | Best for |
|---|---|---|
| **Task Manager** | `taskmgr` | A quick look at what is busy right now |
| **Resource Monitor** | `resmon` | Live, per-process drill-down into CPU, memory, disk and network |
| **Performance Monitor** | `perfmon` | Counters over time, logging to files, alerts, baselines |
| **Reliability Monitor** | `perfmon /rel` | Stability index and a timeline of crashes and installs |
| **PowerShell** | `Get-Counter`, `Get-Process` | Scripted and remote sampling |

A server is rarely slow for one reason. The standard approach: **establish a baseline** when the server is healthy, capture counters during the problem, and compare. Without a baseline "30% CPU" means nothing.

## Resource Monitor

Resource Monitor shows five tabs: **Overview, CPU, Memory, Disk, Network**. Its strengths over Task Manager:

- **CPU:** per-process and per-service CPU, plus *Analyze Wait Chain* to see what a hung process is waiting on.
- **Memory:** a bar of Hardware Reserved, In Use, Modified, Standby and Free memory, and per-process commit, working set, shareable and private bytes. Heavy *Hard Faults/sec* means paging to disk.
- **Disk:** which process reads or writes which file, with *Response Time (ms)* per disk and a *Disk Queue Length*.
- **Network:** per-process send/receive, TCP connections, and listening ports with their owning process, which is useful for confirming that a firewall rule matches something that is actually listening.

On Server Core there is no Resource Monitor; use PowerShell or connect Performance Monitor remotely.

## Performance Monitor

`perfmon` has three areas:

- **Performance Monitor** (the live graph): add counters and watch them.
- **Data Collector Sets:** the logging engine. *User Defined* sets that you create, and *System* sets that ship with Windows, including **System Performance** and **System Diagnostics** (the latter generates a report).
- **Reports:** results from data collector sets.

A counter is identified as **object, counter, instance**, for example `\Processor(_Total)\% Processor Time`. Instances are specific disks, processors, network adapters or processes; `_Total` is the aggregate.

### Core counters

| Resource | Counter | What to look for (rules of thumb, not hard limits) |
|---|---|---|
| CPU | `\Processor(_Total)\% Processor Time` | Sustained above ~85% |
| CPU | `\System\Processor Queue Length` | Consistently above about 2 per core |
| Memory | `\Memory\Available MBytes` | Persistently low; leaves no cache headroom |
| Memory | `\Memory\Pages/sec` | Sustained high values suggest paging pressure |
| Memory | `\Memory\Committed Bytes` vs commit limit | Approaching the limit means a leak or too little RAM/page file |
| Disk | `\PhysicalDisk(*)\Avg. Disk sec/Read` and `/Write` | Latency in tens of milliseconds, sustained, is slow for most workloads |
| Disk | `\PhysicalDisk(*)\Current Disk Queue Length` | Persistent queue beyond the number of spindles/lanes |
| Disk | `\LogicalDisk(*)\% Free Space` | Low free space |
| Network | `\Network Interface(*)\Bytes Total/sec` | Compare with link speed; close to capacity is saturation |
| Network | `\Network Interface(*)\Output Queue Length` | Persistently above 2 |

Always interpret counters together: high `% Processor Time` with a long processor queue is a CPU bottleneck; high paging plus low available memory points to memory; high disk latency with a deep queue points to storage.

> **Exam tip:** `PhysicalDisk` counts the physical device; `LogicalDisk` counts volumes. To check one volume's free space use `LogicalDisk`. To see disk latency use `PhysicalDisk\Avg. Disk sec/Read`.

### Data collector sets

A user-defined **data collector set** can hold performance counters, event trace data, configuration (registry keys) and performance counter *alerts*. To create one:

1. *Data Collector Sets > User Defined > New > Data Collector Set*.
2. Choose **Create manually**, then tick *Performance counter*.
3. Pick counters and a **sample interval** (default 15 seconds).
4. Set the location, schedule and a stop condition (duration or maximum size).

The output is a binary log (`.blg`) by default; you can also log to comma- or tab-separated text, or to a SQL database. Load it into Performance Monitor for analysis, convert it with `relog`, or analyze with PowerShell.

A **performance counter alert** data collector set triggers when a counter crosses a threshold (for example, `% Free Space` below 10) and can start another data collector set or run a task.

### Command line

```text
logman create counter BaselineSet -c "\Processor(_Total)\% Processor Time" "\Memory\Available MBytes" "\PhysicalDisk(_Total)\Avg. Disk sec/Read" -si 15 -o C:\PerfLogs\Baseline
logman start BaselineSet
logman stop  BaselineSet
logman query
relog C:\PerfLogs\Baseline_000001.blg -f csv -o C:\PerfLogs\baseline.csv
typeperf "\Processor(_Total)\% Processor Time" -sc 5
```

```powershell
Get-Counter -Counter '\Processor(_Total)\% Processor Time','\Memory\Available MBytes' -SampleInterval 5 -MaxSamples 6
Get-Counter -ListSet Memory | Select-Object -ExpandProperty Counter
Get-Counter -ComputerName FS01 '\Memory\Pages/sec'
```

`logman` manages data collector sets, `relog` converts and filters logs, `typeperf` writes counters to the console or a file, and `Get-Counter` is the PowerShell route. Remote collection requires the **Performance Log Users** or **Performance Monitor Users** group (read live counters) or administrative rights, plus firewall rules for remote performance logging.

### Reading a trend

For capacity planning, collect a week or more at a modest interval (for example 15 minutes), including month-end peaks, then trend averages and 95th percentile values. Short, tight intervals are for diagnosis; long runs at one-second intervals produce huge files.

> **Real world:** The CPU shown inside a VM can differ from the host's view. When a Hyper-V guest looks idle but is slow, check the host's `\Hyper-V Hypervisor Logical Processor(_Total)\% Total Run Time` and the guest's `\Hyper-V Hypervisor Virtual Processor(*)\% Guest Run Time`.

## Lab it yourself

1. On `FS01`, open `resmon`, start a large file copy over SMB from `DC01`, and watch which tab shows the load. Find the process with the most disk activity.
2. In `perfmon`, build a data collector set with processor, available memory, physical disk latency and network bytes counters, 15-second interval, and run it for 10 minutes during normal use. That is your baseline.
3. Run it again while copying files and compare the two reports.
4. Create an alert data collector set that fires when `\LogicalDisk(C:)\% Free Space` drops below 20 and logs an event; fill the disk with a dummy file to trigger it.
5. Repeat step 2 from PowerShell with `Get-Counter ... | Export-Counter -Path C:\PerfLogs\ps.blg -FileFormat BLG`.

## Key takeaways

- Resource Monitor is live per-process drill-down; Performance Monitor is long-term counters and data collector sets.
- Counters are object\counter(instance); `_Total` aggregates.
- Know CPU (`% Processor Time`, `Processor Queue Length`), memory (`Available MBytes`, `Pages/sec`), disk (`Avg. Disk sec/Read`, queue length) and network (`Bytes Total/sec`) counters.
- A baseline taken while healthy is what makes later numbers meaningful.
- Data collector sets log to `.blg` by default and support alerts; `logman`, `relog`, `typeperf` and `Get-Counter` are the command-line tools.
- `PhysicalDisk` is the device, `LogicalDisk` is the volume.
- Thresholds are rules of thumb, so judge counters in combination and against the baseline.
