## Credential Guard

**Credential Guard** uses virtualization-based security (VBS) to move derived domain credentials, specifically NTLM password hashes and Kerberos ticket-granting tickets (TGTs), out of the normal LSASS process and into an isolated process (`LsaIso`) that the operating system kernel cannot read. A tool such as Mimikatz that dumps LSASS memory finds nothing useful, which blunts pass-the-hash and pass-the-ticket attacks.

### Requirements

- **VBS**, which in turn needs hardware virtualization extensions and a 64-bit CPU with second-level address translation, and
- **Secure Boot** (on the older requirements list; Microsoft now says Secure Boot is not a hard prerequisite for VBS to run, though it is recommended).
- Recommended: a TPM (1.2 or 2.0) for binding secrets to the hardware, and **UEFI lock** to prevent an attacker from turning it off with a registry change.
- In a VM: a **Generation 2** Hyper-V VM, on a host with an IOMMU. Generation 1 VMs are not supported. Credential Guard in a guest protects against attacks *inside* the VM, not against the host.

### Default enablement in Windows Server 2025

Starting with **Windows Server 2025** (and Windows 11 22H2), Credential Guard is **enabled by default** when the server:

1. meets the license requirements,
2. meets the hardware and software requirements,
3. has not been **explicitly configured to disable** it,
4. is **joined to a domain**, and
5. is **not a domain controller**.

The default enablement is **without UEFI lock**, so an administrator can still turn it off remotely. An explicit setting always wins: if Credential Guard was explicitly disabled before an upgrade to 2025, it stays disabled. A standalone workgroup server and every domain controller do not get default enablement.

### Configure and verify

Configure through Group Policy at *Computer Configuration > Administrative Templates > System > Device Guard > Turn On Virtualization Based Security*, set *Credential Guard Configuration* to **Enabled with UEFI lock** or **Enabled without lock**, or through the registry/Intune (`LsaCfgFlags`: 0 disabled, 1 enabled with UEFI lock, 2 enabled without lock). Changes take effect after a reboot.

```powershell
(Get-CimInstance -ClassName Win32_DeviceGuard -Namespace root\Microsoft\Windows\DeviceGuard).SecurityServicesRunning
```

A value containing **1** means Credential Guard is running. `msinfo32.exe` shows the same under *Virtualization-based security Services Running*, and Event Viewer logs related events from the Wininit and Device Guard sources.

### What it breaks

Credential Guard blocks protocols that expose reusable passwords:

| Blocked | Effect |
|---|---|
| Kerberos **unconstrained delegation** | Both single sign-on and supplied credentials blocked |
| Kerberos PKINIT using RSA instead of Diffie-Hellman | Blocked |
| **NTLMv1**, **MS-CHAPv2**, **WDigest** | SSO blocked; users must type credentials |
| **CredSSP** delegation | Only supplied credentials can be used |

The 2025 headline consequence is **Hyper-V live migration**. CredSSP delegation was the default for live migration in Server 2022 and earlier; with Credential Guard on by default in 2025, a CredSSP-based source fails. The fix is **Kerberos constrained delegation** (or resource-based constrained delegation), which is compatible. Wi-Fi and VPN based on PEAP-MSCHAPv2 lose SSO; move to certificate-based EAP-TLS or PEAP-TLS.

> **Exam tip:** Credential Guard has no per-protocol or per-app policy; it is on or off. Disabling it to fix one application leaves stored domain credentials exposed everywhere on that server.

> **Watch out:** Microsoft documents that **Credential Guard protected machine accounts** (opt-in in 2025) is **temporarily disabled** since the April 2025 update due to a machine-password-rotation issue. Do not plan around it.

## Protected Users

The **Protected Users** security group is a domain-level control that complements Credential Guard. It is covered in the groups lesson in domain 2; the short version is that members cannot use NTLM, DES or RC4 for Kerberos, cannot be delegated, and get shortened TGT lifetimes. Put privileged accounts in it, but never service accounts (they will fail), and test sign-in on a lab account first.

## Security baselines and OSConfig

A **security baseline** is a vendor-recommended collection of hardened settings. Historically you imported Microsoft's Security Compliance Toolkit GPOs. **OSConfig** is the new Windows Server 2025 mechanism: a PowerShell module that applies a baseline locally and then **monitors for drift**, correcting settings that someone changes afterwards. OSConfig supports **Windows Server 2025 only**, not earlier versions.

### Install and apply

```powershell
Install-Module -Name Microsoft.OSConfig -Scope AllUsers -Force
Get-Module -ListAvailable -Name Microsoft.OSConfig

# Member server (domain-joined)
Set-OSConfigDesiredConfiguration -Scenario SecurityBaseline/WindowsServer/2025/MemberServer -Default
Restart-Computer
```

Scenario names include the role:

| Role | Scenario |
|---|---|
| Domain controller | `SecurityBaseline/WindowsServer/2025/DomainController` |
| Member server | `SecurityBaseline/WindowsServer/2025/MemberServer` |
| Workgroup member | `SecurityBaseline/WindowsServer/2025/WorkgroupMember` |
| Secured-core | `SecuredCore` |
| Defender Antivirus | `Defender/Antivirus/WindowsServer/2025` |
| Windows LAPS (member servers only) | `LAPS/WindowsServer/2025/MemberServer` |

Earlier module releases used shorter names such as `SecurityBaseline/WS2025/MemberServer`; use the names in the current documentation for your installed module version. The baseline ships inside the module, so `Update-Module Microsoft.OSConfig` plus reapplying the scenario moves a device to the newest baseline, and you are prompted to remove the previous version first.

| Task | Cmdlet |
|---|---|
| Apply | `Set-OSConfigDesiredConfiguration -Scenario ... -Default` |
| Verify / compliance | `Get-OSConfigDesiredConfiguration -Scenario ...` (pipe to `ft Name, @{n='Status';e={$_.Compliance.Status}}`) |
| Customize one setting | `Set-OSConfigDesiredConfiguration -Scenario ... -Setting AuditDetailedFileShare -Value 3` |
| Remove | `Remove-OSConfigDesiredConfiguration -Scenario ...` |

Applying or removing a baseline **requires a restart**. Removal cannot guarantee that settings return to their previous values.

### What the baseline does

Microsoft groups the baseline's effects into five areas: reducing network exposure (all firewall profiles on with default-deny inbound, SMB1 off with a minimum of SMB 3.0, LLMNR and NetBIOS off, TLS 1.2 minimum), resisting credential theft (Credential Guard, LSASS as a protected process, NTLMv2 only), preventing lateral movement (SMB signing required, remote UAC filtering, an account lockout of three failures for 15 minutes), blocking persistence and tampering (Secured-core protections, AutoRun off), and auditing (nearly all advanced audit subcategories, process-creation events with command line, and a Security log of at least 192 MB).

Expect side effects: the local Administrator password must be changed on first use (14-character minimum with complexity), TLS older than 1.2 stops working, **file copy over RDP is disabled** (reversible with `-Name RemoteDesktopServicesDoNotAllowDriveRedirection -Value 0`), and connections to non-Windows SMB servers need SMB 3.0. **Drift control** means a conflicting GPO fights OSConfig; remove one source.

At scale, Azure Policy machine configuration (with Azure Arc) reports compliance across servers; locally, OSConfig is the tool.

## Lab it yourself

1. On a **checkpointed** lab member server, check `SecurityServicesRunning` and note whether Credential Guard is already running. Compare a domain-joined server with a workgroup server.
2. Disable it with the GPO setting *Disabled* and verify after reboot; then set it to *Enabled without lock*.
3. Install the OSConfig module, apply `SecurityBaseline/WindowsServer/2025/MemberServer`, reboot, and pipe `Get-OSConfigDesiredConfiguration` to a compliance table.
4. Try copying a file into the RDP session (blocked), then apply the `-Value 0` override and retest.
5. Roll back with `Remove-OSConfigDesiredConfiguration` or revert the checkpoint.

## Key takeaways

- Credential Guard isolates NTLM hashes and Kerberos TGTs with VBS.
- 2025 default enablement: domain-joined, not a domain controller, supported hardware, not explicitly disabled; no UEFI lock.
- It blocks unconstrained delegation, NTLMv1, MS-CHAPv2, WDigest SSO and CredSSP defaults; use constrained delegation for live migration.
- Verify with `Win32_DeviceGuard` `SecurityServicesRunning` containing 1.
- OSConfig applies and drift-controls role-specific baselines on Server 2025 only.
- Apply with `Set-OSConfigDesiredConfiguration -Scenario SecurityBaseline/WindowsServer/2025/<Role> -Default`, then restart.
- The baseline hardens SMB, TLS, NTLM, auditing and firewall, and breaks RDP file copy by default.
