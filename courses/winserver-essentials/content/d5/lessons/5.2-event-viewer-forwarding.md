## Event Viewer and the Windows logs

**Event Viewer** (`eventvwr.msc`) reads the structured event logs that Windows and applications write. Logs are grouped:

| Group | Contains |
|---|---|
| **Windows Logs** | *Application*, *Security*, *Setup*, *System* and *Forwarded Events* |
| **Applications and Services Logs** | Per-component logs, such as *Microsoft > Windows > LAPS > Operational*, *DNS Server*, *Directory Service*, *Windows Firewall With Advanced Security* |
| **Custom Views** | Saved filters, including the built-in *Administrative Events* and *Server Roles* |
| **Subscriptions** | Event Forwarding subscriptions on a collector |

Each event has a **level** (Critical, Error, Warning, Information, Verbose), a **source** (provider), an **event ID**, a task category, keywords (for Security, *Audit Success* or *Audit Failure*), a user, a computer and a timestamp. You cannot judge an event by its ID alone: the same ID can mean different things in different providers, so always pair ID with log or source.

The **Security** log is the audit trail and needs the right audit policy (advanced audit policy or the OSConfig baseline) to record much. Reading it requires the *Manage auditing and security log* right or membership in **Event Log Readers**. Log size and retention are per log (*Properties*): when full the default is to overwrite as needed. A busy DC with a small Security log can lose evidence in hours, which is why the baseline sets it to at least 192 MB.

### Custom views

A **custom view** is a saved query across one or more logs. In Event Viewer choose *Action > Create Custom View*, filter by time, level, log, source, event IDs and user, and save. Under the hood it is an **XPath** query that you can edit in the XML tab, for example:

```xml
<QueryList>
  <Query Id="0" Path="Security">
    <Select Path="Security">*[System[(EventID=4740)]]</Select>
  </Query>
</QueryList>
```

Custom views can be exported to `.xml` and imported on other servers. A **Server Roles** view is created for each installed role. A view can also be built from *Filter Current Log* and then saved.

### The same from the command line

```powershell
# Last 10 failed logons in the Security log
Get-WinEvent -FilterHashtable @{ LogName='Security'; Id=4625 } -MaxEvents 10 |
  Select-Object TimeCreated, Id, Message

# Errors and critical events in System in the last day
Get-WinEvent -FilterHashtable @{ LogName='System'; Level=1,2; StartTime=(Get-Date).AddDays(-1) }

# Query a remote server
Get-WinEvent -ComputerName DC01 -FilterHashtable @{ LogName='Security'; Id=4740 }
```

```text
wevtutil el                                  list logs
wevtutil qe Security /q:"*[System[(EventID=4740)]]" /c:5 /rd:true /f:text
wevtutil gl Security                         show a log's configuration
wevtutil cl Application                      clear a log
wevtutil epl System C:\Temp\system.evtx      export a log
```

`Get-WinEvent -FilterHashtable` filters at the source and is far faster than piping everything to `Where-Object`. The older `Get-EventLog` only reads classic logs and does not exist in PowerShell 7.

> **Exam tip:** Clearing the Security log writes event **1102** (audit log cleared). Clearing any other log, including System, writes **104** in the System log. An attacker erasing traces creates a trace.

## Event IDs worth knowing

| Event ID | Log | Meaning |
|---|---|---|
| **4624** | Security | Successful logon (check **Logon Type**: 2 interactive, 3 network, 10 remote interactive/RDP) |
| **4625** | Security | Failed logon (check the Status/SubStatus code and logon type) |
| 4634 / 4647 | Security | Logoff / user-initiated logoff |
| 4648 | Security | Logon using explicit credentials |
| 4672 | Security | Special privileges assigned to a new logon (an admin logon) |
| 4688 | Security | Process created (command line only if that policy is enabled) |
| **4720** | Security | User account created |
| 4722 / 4725 / 4726 | Security | Account enabled / disabled / deleted |
| 4723 / 4724 | Security | Password change attempt / password reset attempt |
| 4728 / 4732 / 4756 | Security | Member added to a security-enabled global / local / universal group |
| **4740** | Security | Account **locked out** (the caller computer name shows the source) |
| 4767 | Security | Account unlocked |
| 4768 / 4769 / 4771 | Security | Kerberos TGT request / service ticket request / pre-authentication failure |
| 4776 | Security | NTLM credential validation |
| **1102** | Security | Audit log cleared |
| **104** | System | An event log was cleared |
| 41 | System (Kernel-Power) | Rebooted without a clean shutdown |
| 1074 | System | Shutdown or restart initiated by a process or user |
| 6005 / 6006 | System | Event Log service started / stopped (boot and clean shutdown markers) |
| 6008 | System | Previous shutdown was unexpected |
| 7045 | System | A new service was installed |

On a domain controller, **4740** is logged on the DC that holds the **PDC emulator** role as well as on the DC that processed the failure, which is why you search the PDC emulator first when chasing a lockout. 4625 with logon type 3 repeatedly from one IP suggests spraying; type 10 suggests RDP brute force.

## Windows Event Forwarding (WEF)

Instead of visiting each server, you can have sources **push** events to a central **collector** over WS-Management (WinRM). The collector stores them in the **Forwarded Events** log (or another log named in the subscription). There is no extra agent; it uses the Windows Remote Management and **Windows Event Collector** (`wecsvc`) services.

### Two subscription types

| | Collector-initiated | Source-initiated |
|---|---|---|
| Who defines sources | The subscription lists every source computer | Sources are configured by Group Policy and find the collector themselves |
| Scales to | Small, known sets of servers | Hundreds or thousands of clients |
| Source setup | Add collector's computer account to the source's local **Event Log Readers** group, run `winrm quickconfig` | GPO sets the **SubscriptionManager** value; `winrm quickconfig` |
| Typical use | A handful of servers | Whole domain (DCs, member servers) |

### Setup, source-initiated

On the **collector**:

```text
winrm quickconfig
wecutil qc /q
wecutil cs C:\Temp\dc-security.xml
wecutil es
wecutil gr "DC Security"
wecutil gs "DC Security"
```

- `wecutil qc` enables the ForwardedEvents channel, sets the Windows Event Collector service to delayed start, and starts it.
- `wecutil cs <file.xml>` creates a subscription from an XML file; `es` enumerates subscriptions; `gs` shows the configuration; `gr` shows the runtime status of each source; `rs` retries; `ds` deletes.

On the **sources**, run `winrm quickconfig` and apply a GPO: *Computer Configuration > Administrative Templates > Windows Components > Event Forwarding > Configure target Subscription Manager*, with a value like:

```text
Server=http://wec01.corp.example.com:5985/wsman/SubscriptionManager/WEC,Refresh=60
```

(An HTTPS form uses port 5986 and a certificate thumbprint for non-domain computers.) A source-initiated subscription's default allow-list is **Domain Computers** plus Network Service. To forward the **Security** log, add the collector's **NETWORK SERVICE** account to the source's **Event Log Readers** group. Events are not delivered until `DeliveryMaxItems` events (or the latency timer) are reached, which is why a test of one event can look stalled.

Delivery has three optimization modes in the subscription's advanced settings: *Normal*, *Minimize Bandwidth* and *Minimize Latency*. Use the **Forwarded Events** log (or custom views on it) as the single place analysts read.

> **Watch out:** After you create or change a subscription, sources only connect at their next refresh interval (the `Refresh` value in the SubscriptionManager string). Check `wecutil gr <name>` for each source's status before assuming forwarding is broken.

## Lab it yourself

1. In Event Viewer on `FS01`, build a custom view for Security events 4624 and 4625 in the last 24 hours; export it.
2. Lock out `jsmith` by entering a wrong password repeatedly at a lab member server and find event 4740 on `DC01`, noting the Caller Computer Name.
3. Make `FS01` the collector: `winrm quickconfig`, `wecutil qc /q`, create a subscription for System error events from `DC01`.
4. Add `FS01$` to `Event Log Readers` on `DC01` (collector-initiated), wait for the refresh, and check `wecutil gr` and the Forwarded Events log.
5. Run `wevtutil cl Application` and then query 104 or 1102 as appropriate to see the clearing event.

## Key takeaways

- Windows Logs hold Application, Security, Setup, System and Forwarded Events; component logs live under Applications and Services Logs.
- Custom views are saved XPath filters; `Get-WinEvent -FilterHashtable` is the scriptable equivalent.
- Memorize 4624/4625 (logon), 4720 (create), 4740 (lockout), 1102 (Security log cleared) and 104 (other log cleared).
- WEF pushes events over WinRM (5985 HTTP, 5986 HTTPS) to a collector's Forwarded Events log.
- Collector-initiated lists sources; source-initiated is driven by a Group Policy SubscriptionManager setting and scales better.
- Collector setup: `winrm quickconfig`, `wecutil qc`, `wecutil cs file.xml`; check with `wecutil gr`.
- Forwarding the Security log requires NETWORK SERVICE in Event Log Readers on the source.
