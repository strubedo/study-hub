## Backup concepts you need first

- **Backup** is a copy on separate media or storage that survives loss of the original. A **shadow copy** on the same volume is *not* a backup.
- **Recovery point objective (RPO)**: how much data you can afford to lose, which sets backup frequency. **Recovery time objective (RTO)**: how long recovery may take.
- **Full**, **incremental** and **differential** describe what is copied. Windows Server Backup uses VSS and block-level change tracking, so after the first full backup each later backup stores only changed blocks yet is presented as a full backup you can restore from.
- **System state** is the set of files that define a server's configuration. On a domain controller it includes Active Directory (`ntds.dit`), SYSVOL, the registry, boot files and COM+ registration database.
- **Bare-metal recovery (BMR)** restores the whole server (all critical volumes plus system state) to blank or replacement hardware.

## Windows Server Backup

**Windows Server Backup (WSB)** is the built-in, free backup feature. It is not installed by default. The feature name is **`Windows-Server-Backup`**, and it includes the snap-in (`wbadmin.msc`), the `wbadmin` command-line tool and the `WindowsServerBackup` PowerShell module.

```powershell
Install-WindowsFeature -Name Windows-Server-Backup
# Also install the management tools (snap-in):
Install-WindowsFeature -Name Windows-Server-Backup -IncludeManagementTools
```

### What it can protect and where it can write

You can back up the **entire server** (all volumes), **selected volumes**, **system state**, **bare-metal recovery** data, selected files and folders, and Hyper-V guest data when the Hyper-V VSS writer is available. Targets: a **dedicated local or external disk**, a **volume**, or a **remote shared folder**. It does not write to tape.

Behavior to know:

- A *scheduled* backup to a local disk **formats the disk and dedicates it** to backups, which then no longer shows a drive letter in Explorer. A *one-time* backup can use a volume or share.
- Backing up to a **remote shared folder** keeps only the latest backup there, because each new run replaces the previous one. For history, use a dedicated disk or Azure Backup.
- The destination of a critical-volume backup cannot be one of the volumes being backed up.
- Backup operators: membership in **Backup Operators** or **Administrators** is needed to run backups; only **Administrators** can schedule them.

### Backups with wbadmin

```text
wbadmin start backup -backupTarget:E: -include:D: -quiet
wbadmin start backup -backupTarget:E: -allCritical -quiet          bare-metal capable
wbadmin start systemstatebackup -backupTarget:E: -quiet
wbadmin enable backup -addtarget:{disk identifier} -schedule:21:00 -include:C: -allCritical -quiet
wbadmin get versions
wbadmin get items -version:03/15/2026-21:00
wbadmin get disks
wbadmin get status
```

Key parameters:

- `-backupTarget:` the volume or `\\server\share` that receives the backup.
- `-include:` volumes, folders or files to include; `-exclude:` the opposite.
- `-allCritical`: includes every volume containing OS state, which you need for BMR. It must be used with `-backupTarget`.
- `-systemState` adds system state to a regular backup; `start systemstatebackup` takes only system state.
- `-vssFull` does a full VSS backup (updates file history and may truncate application logs); the default, `-vssCopy`, takes a **copy** backup that leaves other backup products' history alone. Use `-vssFull` only if WSB is your only backup product.
- `-quiet` suppresses prompts. `get versions` shows the version identifiers (`MM/DD/YYYY-HH:MM`) that recoveries need.

The PowerShell equivalent builds a **policy** object:

```powershell
$p = New-WBPolicy
Add-WBBareMetalRecovery -Policy $p
Add-WBSystemState       -Policy $p
Add-WBVolume -Policy $p -Volume (Get-WBVolume -VolumePath D:)
$t = New-WBBackupTarget -VolumePath E:
Add-WBBackupTarget -Policy $p -Target $t
Set-WBSchedule -Policy $p -Schedule 21:00
Set-WBPolicy -Policy $p                # makes it the scheduled policy
Start-WBBackup -Policy $p              # run once now
```

### Recovery paths

| Need | How |
|---|---|
| Files or folders | Snap-in *Recover*, `wbadmin start recovery -itemType:File -items:D:\Data -version:... -recoveryTarget:...`, or `Start-WBFileRecovery` |
| A volume or application | `wbadmin start recovery -itemType:Volume` or `-itemType:App` |
| System state on a member server | `wbadmin start systemstaterecovery -version:<id>`; restart |
| System state on a domain controller | Boot to **Directory Services Restore Mode**, then run `wbadmin start systemstaterecovery`; the restore is **non-authoritative** unless you then mark objects authoritative with `ntdsutil` |
| Whole server (BMR) | Boot from Windows Server installation media (or WinRE) > **Repair your computer** > **Troubleshoot** > **System Image Recovery**, or from the Windows Recovery Environment `wbadmin start sysrecovery` |

`wbadmin start sysrecovery` is **only available in the Windows Recovery Environment** and is not shown in the normal wbadmin help. Its options include `-restoreAllVolumes` (otherwise only critical volumes return), `-recreateDisks` (recreates the original disk layout, **deleting data** on volumes that host OS components, so use it with care) and `-excludeDisks`. If you restore to different hardware, the disks must be at least as large as the originals.

If the backup catalog is damaged: `wbadmin restore catalog -backupTarget:...` rebuilds it from a backup, and `wbadmin delete catalog` removes it (last resort).

> **Exam tip:** "Restore a domain controller's AD from backup" means **DSRM plus system state recovery**; "authoritative" adds `ntdsutil`. "Rebuild a dead server on new hardware" means a **bare-metal** backup taken with `-allCritical`.

> **Watch out:** `-allCritical` requires `-backupTarget`. A scheduled backup configured without it will not give you a bare-metal restore.

## Volume Shadow Copy Service (VSS)

**VSS** coordinates *requesters* (backup software), *writers* (applications that quiesce their data), *providers* (the component that makes the snapshot) and the shadow copy itself. It is how WSB and most backup products can copy open files. A shadow copy is a point-in-time view; the default **system provider** records changed blocks in a *diff area* (shadow copy storage) on an NTFS volume.

Key facts (from Microsoft's VSS documentation):

- Up to **512** software shadow copies per volume can exist; by default only **64** are kept for *Shadow Copies of Shared Folders* (the `MaxShadowCopies` registry value governs it).
- Persistent shadow copies require **NTFS**.
- When the storage area fills, the **oldest shadow copies are deleted** first.
- A shadow copy without VSS-aware writers is *crash-consistent*; VSS writers make an application-consistent copy.

### Shadow Copies of Shared Folders (Previous Versions)

On a file server, enable shadow copies for a data volume (volume properties > **Shadow Copies** tab, or `vssadmin`/`wmic`/`Win32_ShadowCopy`). Users then right-click a file or folder on the share and choose **Previous Versions** to restore deleted or overwritten files themselves. The setting controls how much space copies can use and the schedule.

```text
vssadmin create shadow /for=D:                 Windows Server only
vssadmin list shadows
vssadmin list shadowstorage
vssadmin resize shadowstorage /for=D: /on=E: /maxsize=20%
vssadmin delete shadows /for=D: /oldest
vssadmin list writers
vssadmin list providers
```

`vssadmin create shadow` exists only on Windows Server, not on client Windows. `vssadmin list writers` is the first step when a backup fails: a writer in a **Failed** or **Waiting for completion** state is the usual culprit, and restarting the owning service often clears it.

> **Real world:** Shadow copies live on the same physical storage as the data. They protect against accidental deletion and bad edits, not against disk failure, ransomware that deletes shadows (`vssadmin delete shadows /all`), or site loss. Pair them with real backups.

## Lab it yourself

1. Add a 40 GB second disk to `FS01`. Run `Install-WindowsFeature Windows-Server-Backup`.
2. Back up D: and system state to a third disk: `wbadmin start backup -backupTarget:E: -include:D: -allCritical -quiet`. Review with `wbadmin get versions`.
3. Delete a folder on D:, then restore it with `wbadmin start recovery -itemType:File ...`.
4. Enable shadow copies on D:, create two with `vssadmin create shadow /for=D:`, change a file between them, and recover the older one through **Previous Versions**.
5. For BMR, attach the Windows Server ISO to a new VM and walk through the System Image Recovery wizard against the VHDX of the backup disk (read the options without finishing if you lack time).

## Key takeaways

- Feature name: `Windows-Server-Backup`; tool: `wbadmin`; module: `WindowsServerBackup`.
- Scheduled backups use a dedicated disk; a remote share keeps only the latest backup; no tape.
- `-allCritical` with `-backupTarget` gives a bare-metal-capable backup; `start sysrecovery` runs only in WinRE.
- System state on a DC is restored in DSRM; authoritative restore also needs `ntdsutil`.
- `-vssCopy` (default) leaves other products' history alone; `-vssFull` updates it.
- VSS: up to 512 copies per volume, 64 by default for shared folders, NTFS only, oldest deleted when storage fills.
- `vssadmin list writers` diagnoses failed backups; shadow copies are not backups.
