## Backup versus disaster recovery

Two different questions need two different tools:

| | Azure Backup | Azure Site Recovery (ASR) |
|---|---|---|
| Question answered | "Can I get back last Tuesday's version of this file, volume or server?" | "Can the workload keep running if the whole site is down?" |
| Mechanism | Point-in-time **backup copies** with retention | **Continuous replication** of VMs, then failover |
| Recovery goal | Restore data (RPO of hours to a day) | Restart workloads elsewhere (RPO of seconds to minutes) |
| Landing place | A **Recovery Services vault** in Azure | A replica in Azure storage; VMs created at failover |

Both are stored in a **Recovery Services vault**, the Azure resource that holds backup data and replication settings, and both sit alongside, not in place of, Windows Server Backup and VSS on the server.

## Azure Backup for Windows Server

For an on-premises Windows Server, the simplest path is the **Microsoft Azure Recovery Services (MARS) agent**, also called the Azure Backup agent.

What it does:

- Backs up **files and folders**, whole **volumes**, and **system state** directly to a Recovery Services vault.
- Is supported on **Windows Server 2025** (Standard, Datacenter, Essentials, Server IoT), and on 2022, 2019 and 2016. System state backup is supported on those servers but not on Windows client. It is **not supported on Server Core**.
- Backs up only local, fixed, writable, online, **NTFS** volumes that are unlocked if BitLocker-protected; network shares and removable media are not supported.
- Uses VSS to take a snapshot (only the Windows System Writer, so no application-consistent snapshots), then transfers compressed, encrypted changes. Initial backups of terabytes can be seeded offline; offline seeding is **not** available for system state.
- Encrypts with a **passphrase that you create and must not lose**. Without it, restore is impossible. You can store it in Azure Key Vault.

Setup outline:

1. Create a **Recovery Services vault** in the Azure portal.
2. Under Backup choose **On-premises**, then *Files and folders* and *System State*.
3. Download **MARSAgentInstaller.exe** and the **vault credentials** file.
4. Install the agent, register the server with the credentials file, set the encryption passphrase.
5. In the *Microsoft Azure Backup* console, schedule the backup and choose retention.

Restore options in the console include browsing a recovery point mounted as a drive (**Instant Restore**, suited to small recoveries), restoring a full volume, or restoring system state files and applying them with Windows Server Backup. A server can also restore to an **alternate server**.

Other Azure Backup architectures to recognize:

- **Azure VM backup** uses an extension in the VM and backs up the whole VM; MARS inside the VM can add file-level backup.
- **Microsoft Azure Backup Server (MABS)** and System Center **Data Protection Manager (DPM)** are on-premises backup servers that protect workloads such as Hyper-V, SQL Server and Exchange locally and can tier to a vault with the MARS agent.

> **Exam tip:** The agent is **MARS**, the container is a **Recovery Services vault**, and the secret you cannot recover is the **passphrase**. Server Core cannot run the MARS agent.

> **Real world:** Cost scales with the protected instance and the storage consumed, so keep retention tied to a policy rather than "forever", and test a restore on a schedule. A backup you have never restored is a hope.

## Azure Site Recovery overview

**Azure Site Recovery** orchestrates replication, failover and failback of machines. Sources include Azure VMs, **on-premises Hyper-V VMs**, VMware VMs and physical servers. For Hyper-V without System Center Virtual Machine Manager:

1. Create a Recovery Services vault and an Azure storage account and network.
2. Install the **Azure Site Recovery Provider** and the **Recovery Services agent** on each Hyper-V host (or cluster node). Nothing is installed inside the VMs.
3. Hosts are grouped into a **Hyper-V site**; create a **replication policy** (replication frequency, recovery point retention, app-consistent snapshot frequency).
4. Enable replication for each VM. Hyper-V replication to Azure can run as often as every **30 seconds**.
5. Add **recovery plans** that group VMs, order startup and add scripts.
6. Run a **test failover** (non-disruptive, into an isolated network) before you ever need a real one.
7. On disaster, **fail over** and **commit**. When the site returns, **fail back** (planned failover from Azure to on-premises), and **re-protect** by enabling reverse replication.

Details to know: VHDX is converted to VHD when failing over to Azure (and stays VHDX on failback); Generation 1 and Generation 2 VMs are both supported; **BitLocker must be disabled** on the VM before replication; replicated data is encrypted. A **planned** failover shuts the source down to prevent data loss; an **unplanned** failover assumes the primary is unreachable. The target Azure VM size must exist and meet requirements.

Do not confuse ASR with **Hyper-V Replica** (domain 4): Hyper-V Replica replicates VMs between Hyper-V hosts you own, while ASR targets Azure (or between Azure regions) and adds orchestration and recovery plans. Microsoft also documents an ASR configuration tool for Arc-enabled Windows Server hosts that automates agent and vault setup; it is described in the Windows Server Arc documentation with preview wording, so check its current status before depending on it.

## Putting it together

A common layered design: **VSS shadow copies** for user self-service restore, **Windows Server Backup** or MARS for local restore points, **Azure Backup** for off-site retention and ransomware resilience (backup data in the vault is separate from the server), and **ASR** for workloads that cannot wait for a restore.

## Lab it yourself

This lab needs an Azure subscription; a free trial is enough. If you do not have one, read the portal flows in the documentation and practice the on-premises steps in the previous lessons.

1. Create a Recovery Services vault named `rsv-corp-lab`.
2. In the vault, choose Backup > On-premises > Files and Folders + System State; download the agent and vault credentials.
3. Install the agent on `FS01` (Desktop Experience), register it, generate a passphrase and store it safely.
4. Schedule a daily backup of `D:\Data`, run *Back Up Now*, then restore one file through Instant Restore.

6. Delete the vault resources when done to avoid charges.

## Key takeaways

- Backup restores data from points in time; ASR keeps workloads running by replicating VMs and failing over.
- Both use a Recovery Services vault.
- The MARS agent protects files, folders, volumes and system state, supports Server 2025, and does not run on Server Core.
- The MARS passphrase encrypts the backup and cannot be recovered by Microsoft; offline seeding does not cover system state.
- ASR for Hyper-V installs the Provider and Recovery Services agent on hosts, with replication as frequent as 30 seconds.
- Test failover is non-disruptive; fail back and re-protect after the primary returns; BitLocker must be off.
- ASR is not Hyper-V Replica; layer VSS, WSB or MARS, and ASR.
