## What a GPO is

A **Group Policy Object (GPO)** is a bundle of settings in two halves: **Computer Configuration** (applied at startup and during background refresh) and **User Configuration** (applied at sign-in and during refresh). A GPO is stored in two places that must stay in sync:

- the **Group Policy Container (GPC)** in Active Directory (`CN=Policies,CN=System,DC=corp,DC=example,DC=com`), holding version and link metadata, replicated by AD replication;
- the **Group Policy Template (GPT)** in `SYSVOL\corp.example.com\Policies\{GUID}`, holding the actual files (registry.pol, scripts, preferences XML), replicated by DFS Replication.

A GPO does nothing until it is **linked** to a site, domain or OU. Two GPOs exist in every domain: **Default Domain Policy** (account policies such as password and lockout, linked to the domain root) and **Default Domain Controllers Policy** (linked to the Domain Controllers OU). Edit them only for what they are meant for, and put everything else in your own GPOs.

## LSDOU: processing order

GPOs are applied in this order, and a later application overrides an earlier one when settings conflict:

1. **L**ocal policy on the computer
2. **S**ite-linked GPOs
3. **D**omain-linked GPOs
4. **O**U-linked GPOs, parent OU first, then child OUs

The GPO nearest the object wins by default. Settings that are not configured in a later GPO do not cancel earlier ones; the effective policy is the *merge* of all GPOs, where only conflicting settings are overridden.

When several GPOs are linked to the same container, **link order** decides: the link with the **lowest number (1)** is processed last and wins. Order is set in GPMC on the container's **Linked Group Policy Objects** tab.

> **Exam tip:** Lowest link order number = highest precedence. Last writer wins in LSDOU, so the OU closest to the object wins.

Account policies for domain accounts (password, lockout, Kerberos) apply only when set in a GPO linked at the **domain** level. A password policy set on an OU does not affect domain users; it only affects local accounts on computers in that OU.

## Inheritance, enforcement and blocking

- **Inheritance**: GPOs flow down from site to domain to OUs. A child OU inherits its parents' GPOs.
- **Block Inheritance** is set on a *container* (domain or OU). It stops GPOs from higher in the tree applying there. It is all or nothing for that container, and it does not block **Enforced** links.
- **Enforced** is set on a *GPO link* (the older name is No Override). The link's settings cannot be overridden by lower GPOs, and it applies even through Block Inheritance. When several GPOs are Enforced, the one linked **highest** in the hierarchy wins, which reverses the usual order.

| Option | Set on | Effect |
|---|---|---|
| Link enabled | Link | A disabled link is not processed |
| Enforced | Link | Overrides lower-level conflicts and ignores Block Inheritance |
| Block Inheritance | Container | Blocks non-enforced GPOs from above |
| GPO status | GPO | Enable all, disable user configuration, disable computer configuration, or disable all. Disabling the unused half speeds processing |

> **Watch out:** The Default Domain Policy and Default Domain Controllers Policy links should not be removed. Block Inheritance on the Domain Controllers OU would not stop a domain-level Enforced link.

## Filtering: who and what a GPO applies to

### Security filtering

By default the GPO applies to **Authenticated Users**. Both the **Read** and **Apply group policy** permissions are needed on the GPO for it to apply. To scope a GPO to specific groups, replace Authenticated Users in GPMC's **Scope** tab, **Security Filtering** with your group (computer or user accounts).

> **Watch out:** Since MS16-072 (2016), the computer account must have **Read** permission on the GPO to retrieve it, even for user-targeted policy. If you remove Authenticated Users from filtering, add **Authenticated Users** or **Domain Computers** with only **Read** on the Delegation tab. The usual symptom of forgetting is a GPO that silently does not apply.

### WMI filtering

A **WMI filter** is a WQL query evaluated on the client; the GPO applies only if the query returns data. One WMI filter per GPO, and one filter can be linked to many GPOs. Namespace is normally `root\CIMv2`.

```text
SELECT * FROM Win32_OperatingSystem WHERE Version LIKE "10.%" AND ProductType = "1"
```

`ProductType` is 1 for client, 2 for domain controller, 3 for server. Filters add processing time, so prefer security filtering and OU design where you can.

### Loopback processing

Normally user settings come from the GPOs that apply to the *user's* OU. On kiosks, RDS hosts and lab PCs you want user settings determined by the *computer*. Enable **Configure user Group Policy loopback processing mode** (Computer Configuration, Administrative Templates, System, Group Policy) in a GPO linked to the computers' OU:

| Mode | Behavior |
|---|---|
| **Replace** | User settings from the user's own GPOs are ignored; only user settings from GPOs that apply to the computer are used |
| **Merge** | User settings from the user's GPOs are applied first, then the computer's user settings are applied on top, winning on conflict |

> **Exam tip:** Loopback is a *computer* policy setting that changes how *user* policy is chosen. The user must still have Read access to the GPO.

## When policy refreshes

- At computer startup (computer settings) and at user sign-in (user settings), in the **foreground**.
- Every **90 minutes** with a random offset of up to 30 minutes on workstations and member servers, and every **5 minutes** on domain controllers (Microsoft documents the 90 plus 30 default; the 5-minute DC figure is the standard default from the Group Policy documentation).
- On demand: `gpupdate /force`. Some extensions apply only at sign-in or startup: folder redirection and software installation never apply in a background refresh. `gpupdate /logoff` and `/boot` apply those after the refresh when needed.

Foreground processing can be synchronous (sign-in waits until policy is applied) or asynchronous; fast logon optimization makes it asynchronous on newer clients after the first sign-in.

## Planning an OU design for GPOs

- Separate OUs for **servers**, **workstations**, **users** and **groups**; do not link GPOs to the default `Users` and `Computers` containers because you cannot.
- Prefer a few focused GPOs with clear names (`SRV - Baseline Security`, `WKS - Drive Maps`) rather than one huge GPO or editing the Default Domain Policy.
- Use security filtering sparingly and always test with **Group Policy Modeling** (what-if, no risk) before linking in production.

## Lab it yourself

1. On DC01 open **Group Policy Management** (`gpmc.msc`). Create OUs `Workstations`, `Servers` under the domain. Create GPO `WKS - Test` and link it to `Workstations`.
2. In its settings, configure a harmless user setting such as a desktop wallpaper (Administrative Templates, Desktop). Link a second GPO `WKS - Test 2` with a different wallpaper to the same OU and use the up and down arrows to change link order; observe the winner.
3. Right-click `WKS - Test` link, choose **Enforced**; place a conflicting GPO on a child OU and confirm the enforced one wins.
4. Set a **Security Filtering** group on `WKS - Test`, remove Authenticated Users, and note that the GPO stops applying until you add **Domain Computers** with Read on the **Delegation** tab.
5. Create a **WMI filter** (`SELECT * FROM Win32_OperatingSystem WHERE ProductType = "3"`) and attach it to a server GPO. Check which machines it applies to with `gpresult /r`.
6. Enable loopback in Replace mode on a GPO linked to a lab OU and sign in as different users.
7. PowerShell: `New-GPO -Name 'WKS - Test'`, `New-GPLink -Name 'WKS - Test' -Target 'OU=Workstations,DC=corp,DC=example,DC=com' -LinkEnabled Yes -Order 1`, `Set-GPLink ... -Enforced Yes`.

## Key takeaways

- Order is local, site, domain, OU (parent to child); the last applied wins, and lowest link order number wins within a container.
- Enforced is set on a link and overrides Block Inheritance; Block Inheritance is set on a container.
- Domain account password policy only works from a domain-linked GPO (or a fine-grained policy).
- Security filtering needs Read and Apply; since MS16-072 the computer needs Read, so keep Authenticated Users or Domain Computers with Read.
- WMI filters are WQL, one per GPO, and cost time; loopback replace or merge changes how user policy is selected.
- Policy refreshes every 90 minutes with a 0 to 30 minute offset; `gpupdate /force` forces it.
