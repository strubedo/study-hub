## Creating and managing GPOs

Use the **Group Policy Management Console** (`gpmc.msc`; feature **Group Policy Management**, `Install-WindowsFeature GPMC`) and the **Group Policy Management Editor** that opens when you edit a GPO. The `GroupPolicy` PowerShell module covers the same ground:

```powershell
New-GPO -Name 'WKS - Security Baseline' -Comment 'Workstation baseline'
Set-GPRegistryValue -Name 'WKS - Security Baseline' -Key 'HKCU\Software\Policies\Microsoft\Windows\Control Panel\Desktop' `
    -ValueName ScreenSaveActive -Type String -Value 1
New-GPLink -Name 'WKS - Security Baseline' -Target 'OU=Workstations,DC=corp,DC=example,DC=com' -LinkEnabled Yes
Backup-GPO -All -Path C:\GPOBackup
Get-GPOReport -Name 'WKS - Security Baseline' -ReportType Html -Path C:\Temp\baseline.html
Restore-GPO -Name 'WKS - Security Baseline' -Path C:\GPOBackup
Invoke-GPUpdate -Computer FS01 -Force      # remote refresh, schedules gpupdate
```

`Copy-GPO` and `Import-GPO` migrate GPOs, and a **Starter GPO** is a template with only Administrative Templates settings. Back up GPOs before big changes;

## Common settings and where they live

### Password and lockout policy

Path: **Computer Configuration, Policies, Windows Settings, Security Settings, Account Policies**.

| Policy | What it controls |
|---|---|
| Enforce password history | Number of remembered passwords |
| Maximum / minimum password age | Days before forced change / before another change is allowed |
| Minimum password length | Minimum characters |
| Password must meet complexity requirements | Three of four character classes, no username in the password |
| Store passwords using reversible encryption | Keep off unless an application requires it |
| Account lockout threshold, duration, reset counter after | Bad-attempt lockout |

These settings only take effect for *domain* accounts when delivered by a GPO linked at the **domain** root (normally Default Domain Policy). Anything else is a fine-grained policy (below).

### Drive maps

Drive maps are a **Group Policy Preference**, not a policy: **User Configuration, Preferences, Windows Settings, Drive Maps**, then **New, Mapped Drive** with an action (Create, Replace, Update, Delete), a UNC path such as `\\FS01\Sales`, a drive letter and **Reconnect**. Use **Item-level targeting** (for example "Security Group CORP\Sales-Users") to map drives per group inside a single GPO. Unlike a policy, a preference sets a value once, can be changed by the user, and is not removed when the GPO stops applying unless you set the Delete action or "Remove this item when it is no longer applied".

> **Exam tip:** Preferences (drive maps, printers, registry, scheduled tasks, local users and groups) can be changed by the user and support item-level targeting. Policies (Administrative Templates, Security Settings) are enforced and grayed out.

```powershell
# One-off equivalent for testing, not a replacement for the GPP
New-PSDrive -Name S -PSProvider FileSystem -Root '\\FS01\Sales' -Persist
```

### Software restriction policies

**Software Restriction Policies (SRP)** are under **Computer or User Configuration, Windows Settings, Security Settings, Software Restriction Policies**. They define a default security level (**Disallowed**, **Basic User**, **Unrestricted**) and additional rules by hash, certificate, path or network zone. Know them for legacy environments, but Microsoft states that SRP has been deprecated since Windows 10 build 1803 (and applies to Windows Server 2019 and later) and tells you to use **AppLocker** or **Windows Defender Application Control (App Control for Business)** to control what software runs. In a new design, deploy AppLocker through GPO (Security Settings, Application Control Policies, AppLocker) or App Control policies instead.

### Other common settings

- **Security Options** (rename guest, interactive logon text), **User Rights Assignment** and **Restricted Groups**.
- **Administrative Templates**: thousands of registry-based settings, including the Windows Update, Remote Desktop, Windows Defender and Credential Guard ones. Add centrally stored `.admx` templates in `\\corp.example.com\SYSVOL\corp.example.com\Policies\PolicyDefinitions` (the central store) so every editor sees the same set.
- **Scripts** (startup, shutdown, sign-in, sign-out) and **Folder Redirection**.
- **Windows Firewall with Advanced Security** rules and **Public Key Policies** (certificate autoenrollment).

## Applying and checking policy

### gpupdate

```text
gpupdate /force                         re-apply all settings, not just changed ones
gpupdate /target:computer               refresh only computer settings
gpupdate /target:user
gpupdate /logoff                        sign out after refresh if a setting needs it
gpupdate /boot                          restart after refresh if a setting needs it
gpupdate /wait:0                        do not wait for processing to finish
```

### gpresult

```text
gpresult /r                              summary on the console (add /scope computer or /scope user)
gpresult /r /scope computer              needs an elevated prompt for computer data
gpresult /h C:\Temp\report.html          HTML report (add /f to overwrite)
gpresult /x C:\Temp\report.xml           XML report
gpresult /v                              verbose settings
gpresult /z                              super verbose
gpresult /s FS01 /user CORP\jsmith /h r.html   remote computer and user
```

The summary lists **Applied GPOs** and **The following GPOs were not applied because they were filtered out** with the reason (for example *Denied (Security)*, *Not Applied (Empty)*, a disabled GPO or link, or a failed WMI filter; the exact wording of the reason text varies, so read the reason rather than memorizing strings). The HTML report also shows **Winning GPO** for each setting, so you can see which GPO set it.

PowerShell offers `Get-GPResultantSetOfPolicy -ReportType Html -Path C:\Temp\rsop.html` and GPMC's **Group Policy Results Wizard**, which queries a remote computer and user and builds the same report. **Group Policy Modeling** predicts what would apply if an object moved to another OU or had a different group membership; it does not read the real client, it simulates from the directory.

### Troubleshooting checklist

1. Is the GPO **linked**, link **enabled**, and not blocked by Block Inheritance (unless Enforced)?
2. Are the right object in the right **OU**? A user policy linked to a computer OU does nothing without loopback.
3. **Security filtering** and Read permission (MS16-072) for the computer; **WMI filter** results.
4. **DNS and DC discovery**: the client must resolve the domain and reach a DC and SYSVOL (`nltest /dsgetdc:corp.example.com`).
5. **Replication**: AD and SYSVOL must agree. Compare the version in `Get-GPO`'s `Computer` and `User` version numbers with `gpresult` and check DFS Replication.
6. **Time skew** over five minutes breaks Kerberos.
7. Event Viewer: **Applications and Services Logs, Microsoft, Windows, GroupPolicy, Operational**.
8. Check the setting itself: it may need a restart, a sign-out, or is a preference with the wrong action.

> **Real world:** For a stuck machine, run `gpresult /h` on the client and `Get-GPO -Name X`, then fix the first red flag rather than re-running `gpupdate /force` repeatedly.

## Fine-grained password policies

A **fine-grained password policy (FGPP)** lets you apply a different password and lockout policy to some users or groups, using **Password Settings Objects (PSOs)** stored in the **Password Settings Container** (`CN=Password Settings Container,CN=System`). Requirements and rules, per Microsoft Learn:

- The **domain functional level must be Windows Server 2008 or higher** (not an issue on 2016+).
- A PSO applies only to **user objects** (or `inetOrgPerson`) and **global security groups**. It cannot be linked to an OU. To cover an OU, create a **shadow group** (a global security group whose members mirror the OU) and link the PSO to it.
- By default only **Domain Admins** can create PSOs, though the rights can be delegated.
- Each PSO has a **Precedence** integer; a **lower number wins**. A PSO linked directly to a user takes priority over PSOs linked through groups. If no PSO applies, the domain's GPO password policy is used.
- A PSO can set lockout settings as well as password settings. Its settings are the whole password policy for those users; they are not merged with the domain policy.

```powershell
New-ADFineGrainedPasswordPolicy -Name 'PSO-Admins' -Precedence 10 `
    -MinPasswordLength 16 -PasswordHistoryCount 24 -ComplexityEnabled $true `
    -MaxPasswordAge '30.00:00:00' -MinPasswordAge '1.00:00:00' `
    -LockoutThreshold 5 -LockoutDuration '00:30:00' -LockoutObservationWindow '00:30:00' `
    -ReversibleEncryptionEnabled $false
Add-ADFineGrainedPasswordPolicySubject -Identity 'PSO-Admins' -Subjects 'Domain Admins'
Get-ADFineGrainedPasswordPolicy -Filter *
Get-ADUserResultantPasswordPolicy -Identity jsmith
Get-ADFineGrainedPasswordPolicySubject -Identity 'PSO-Admins'
```

`Get-ADUserResultantPasswordPolicy` returns the PSO that applies to a user, or nothing when the domain policy applies. You can also manage PSOs in **ADAC** (navigate to **System, Password Settings Container**, or use the Fine-Grained Password Policy node) with a form for all settings and a **Directly Applies To** list.

> **Watch out:** Linking a PSO to the built-in **Domain Admins** group affects Domain Admins members immediately at the next password change, and the lockout settings can lock out your own admins. Test with a spare account and keep a break-glass account outside the PSO.

## Lab it yourself

1. Link `WKS - Security Baseline` to `OU=Workstations`. Add a drive-map preference for `\\FS01\Sales` with item-level targeting to `Sales-Users`.
2. Sign in on a client as `jsmith` and check the map. Run `gpresult /r /scope user` and `gpresult /h C:\Temp\r.html`; open the report and find the winning GPO.
3. Remove `Authenticated Users` from the scope, break the GPO on purpose, and use `gpresult /r` to find the *Denied (Security)* line. Fix it by adding `Domain Computers` with Read.
4. Create `PSO-Admins` as shown, apply it to a lab admin group, and run `Get-ADUserResultantPasswordPolicy` for a user in the group and one outside it.
5. Back up all GPOs with `Backup-GPO -All`, delete one, and `Restore-GPO` it.

## Key takeaways

- Password and lockout policy for domain accounts comes from a domain-linked GPO or from a PSO.
- Drive maps are Group Policy Preferences with Create, Replace, Update and Delete actions plus item-level targeting.
- SRP is deprecated per Microsoft; use AppLocker or App Control for Business.
- `gpupdate /force` refreshes; `gpresult /r`, `/h` and `/x` report what applied and why not; Modeling simulates.
- Check link, scope, filtering, Read permission, DNS, SYSVOL replication and time when a GPO does not apply.
- FGPP uses PSOs linked to users and global security groups (not OUs); lowest precedence wins; `Get-ADUserResultantPasswordPolicy` shows the result.
