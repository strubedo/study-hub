## Why not an ordinary service account

A service account that is a normal user has a password that people know, that rarely changes (because changing it breaks services), and that is a target for Kerberoasting. **Managed service accounts** move the password into Active Directory and rotate it automatically.

| Type | Scope | Password | Introduced |
|---|---|---|---|
| **sMSA** (standalone managed service account) | One computer | AD-managed, automatic | Windows Server 2008 R2 |
| **gMSA** (group managed service account) | Many computers | AD-managed, automatic, retrieved by authorized hosts | Windows Server 2012 |
| **dMSA** (delegated managed service account) | Bound to named machine identities | Fully randomized, derived from machine credentials; nobody sets or rotates it | **Windows Server 2025** |

Use gMSA for services on several servers (IIS farms, SQL Server instances, scheduled tasks); sMSA is limited to one host and is largely superseded by gMSA. Do not use any of them for interactive sign-in.

## Group managed service accounts (gMSA)

Requirements: at least one Windows Server 2012 or later DC, a **KDS root key** in the forest, and hosts that run Windows Server 2012 or later. The Key Distribution Service uses the root key to compute the account password on demand for authorized hosts.

```powershell
# Once per forest. -EffectiveTime backdated for a lab only; in production the key is valid after replication (about 10 hours)
Add-KdsRootKey -EffectiveTime ((Get-Date).AddHours(-10))

New-ADGroup -Name 'Web-Servers' -GroupScope Global -GroupCategory Security
Add-ADGroupMember 'Web-Servers' -Members 'FS01$'

New-ADServiceAccount -Name 'gmsa-web' -DNSHostName 'gmsa-web.corp.example.com' `
    -PrincipalsAllowedToRetrieveManagedPassword 'Web-Servers'
```

On each authorized server (restart the server, or purge its tickets, after adding it to the group):

```powershell
Install-ADServiceAccount gmsa-web
Test-ADServiceAccount gmsa-web          # True when this host can retrieve the password
```

Configure the service to log on as `CORP\gmsa-web$` and leave the password empty. The `$` suffix is part of the SAM name. The account lives in `CN=Managed Service Accounts` by default.

Facts that exam questions test:

- The password is rotated every **30 days** by default. The interval can be set only when the account is created (`-ManagedPasswordIntervalInDays`); you cannot change it later (Microsoft's service-accounts article).
- Administrators never know the password. Domain **Minimum password length** policy does not meaningfully apply to a gMSA.
- Authorized hosts are controlled by `-PrincipalsAllowedToRetrieveManagedPassword`, which holds computer accounts or a group of computer accounts.
- Without a KDS root key, `New-ADServiceAccount` for a gMSA fails.
- To change authorized hosts later: `Set-ADServiceAccount gmsa-web -PrincipalsAllowedToRetrieveManagedPassword 'Web-Servers'`.

> **Exam tip:** Passing `-PrincipalsAllowedToRetrieveManagedPassword` with a security group of computer accounts is the scalable pattern: add a new farm member to the group instead of editing the gMSA.

## Delegated managed service accounts (dMSA) in Windows Server 2025

A dMSA is a new Windows Server 2025 account type. Microsoft documents two ways to use it: a **standalone** account, or a **migration** target that supersedes an existing traditional service account. Authentication is tied to the device identity, so only the machine identities mapped in AD can use the account, which closes the credential-harvesting (Kerberoasting) hole of ordinary service accounts. dMSA uses Credential Guard concepts to bind tickets to the machine. Unlike a gMSA, its secret is machine-bound and cannot simply be stolen and reused elsewhere.

Prerequisites (from Microsoft Learn): at least one **Windows Server 2025 DC** that clients can discover, a KDS root key, membership in Domain Admins or Enterprise Admins (or equivalent), and clients enabled for dMSA (the `DelegatedMSAEnabled` Kerberos registry value, set to 1, on the machines that will use it).

```powershell
New-ADServiceAccount -Name dmsa-app -DNSHostName dmsa-app.corp.example.com `
    -CreateDelegatedServiceAccount -KerberosEncryptionType AES256
Set-ADServiceAccount dmsa-app -PrincipalsAllowedToRetrieveManagedPassword 'FS01$'
```

Migrating an existing account:

```powershell
Start-ADServiceAccountMigration    -Identity dmsa-app -SupersededAccount 'CN=svc-app,OU=Svc,DC=corp,DC=example,DC=com'
Complete-ADServiceAccountMigration -Identity dmsa-app -SupersededAccount 'CN=svc-app,OU=Svc,DC=corp,DC=example,DC=com'
# Undo-ADServiceAccountMigration and Reset-ADServiceAccountMigration back out
```

Key rules from the documentation:

- You **cannot migrate a gMSA or sMSA to a dMSA**. The source must be a traditional user-based service account.
- Each service account needs its **own dMSA**; several accounts cannot migrate into one.
- Migration disables the old account, but **do not delete** it, because it keeps forward and backward links to the dMSA and the service still names it until reconfigured.
- Allow time between start and complete (Learn recommends waiting at least two ticket lifetimes, equal to 14 days, and suggests keeping the start state for four ticket lifetimes) and make sure every machine that uses the old account supports dMSA, or they will fail after it is disabled.
- You cannot force a password reset on a dMSA.
- The migration cmdlets do not work against an RODC.

> **Watch out:** dMSA is new in 2025. Questions about "an account that tightens a service account to the device and replaces its password" mean dMSA; "one account shared by many servers with AD-managed password" means gMSA.

## Delegation of control

The **Delegation of Control Wizard** gives a group a limited set of rights on an OU without making them administrators. It writes ACEs on the OU object.

1. In ADUC right-click the OU (for example `Sales`), choose **Delegate Control**.
2. Add a group such as `HelpDesk`. Do not delegate to individual users.
3. Pick common tasks or build a custom task:
   - Create, delete and manage user accounts
   - Reset user passwords and force password change at next logon
   - Read all user information
   - Create, delete and manage groups
   - Modify the membership of a group
   - Manage Group Policy links
   - Generate Resultant Set of Policy (Planning / Logging)

Verify and audit through OU **Properties, Security, Advanced** (View, Advanced Features first), or with `dsacls`:

```text
dsacls "OU=Sales,DC=corp,DC=example,DC=com"
```

The wizard cannot undo its work. To remove delegation, delete the added ACEs in Advanced Security Settings. Delegating to groups, keeping the permissions at the OU level, and documenting each delegation prevents a slow drift of undocumented rights. Delegation of control in this sense is unrelated to **Kerberos delegation** (constrained, unconstrained, resource-based), which lets a service act on behalf of a user.

Other delegation points: the **GPMC Delegation tab** (who may edit or link a GPO), DNS administrators (DnsAdmins), and RODC role separation.

## Lab it yourself

1. On DC01 create the KDS root key with `Add-KdsRootKey -EffectiveTime ((Get-Date).AddHours(-10))` and confirm with `Get-KdsRootKey`.
2. Create `Web-Servers`, add FS01, create `gmsa-web`, then on FS01 run `Install-ADServiceAccount gmsa-web` and `Test-ADServiceAccount gmsa-web`. Create a scheduled task running as `CORP\gmsa-web$` with logon type **Password** left blank (use `New-ScheduledTaskPrincipal -UserId 'CORP\gmsa-web$' -LogonType Password`).
3. Inspect the account: `Get-ADServiceAccount gmsa-web -Properties msDS-ManagedPasswordInterval, PrincipalsAllowedToRetrieveManagedPassword`.
4. Create `dmsa-app` with `-CreateDelegatedServiceAccount` and read `msDS-DelegatedMSAState`. (You need a Windows Server 2025 DC; the lab DCs are 2025.)
5. Create `HelpDesk` group and use **Delegate Control** on `OU=Sales` to allow password resets. Sign in as a HelpDesk member, reset `jsmith`'s password, and confirm that creating a user in `OU=Sales` is refused.

## Key takeaways

- gMSA: many hosts, AD-managed password, 30-day default rotation set at creation, needs a KDS root key.
- sMSA is for one computer; dMSA is the Windows Server 2025 type, bound to machine identity, created with `-CreateDelegatedServiceAccount`.
- dMSA migration disables the old account, does not accept gMSA or sMSA as sources, and needs at least one 2025 DC.
- Use `Install-ADServiceAccount` and `Test-ADServiceAccount` on each host that uses a gMSA.
- Delegation of Control is done with the wizard on an OU; delegate to groups; undo by removing ACEs.
- Kerberos delegation is a different feature and not the same as delegation of control.
