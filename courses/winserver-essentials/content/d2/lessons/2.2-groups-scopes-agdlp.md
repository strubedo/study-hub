## Group types

Active Directory groups have two independent properties: a **type** and a **scope**.

| Type | Use | In ACLs and tokens? |
|---|---|---|
| **Security** | Assign permissions and user rights, and also usable as an email distribution list | Yes, has a SID |
| **Distribution** | Email lists only (Exchange and similar) | No, cannot be used for permissions |

You can convert between the two types at any time. The scope decides who can be a member and where the group can be used.

## Group scopes

| Scope | Members can come from | Can be used (assigned permissions) in | Typical role |
|---|---|---|---|
| **Domain local** | Accounts and global/universal groups from any domain in the forest or from trusted domains and forests; other domain local groups from the **same** domain | **Only its own domain** | Permissions on a resource (the "access" group) |
| **Global** | Accounts and other global groups from the **same** domain only | Any domain in the forest, and trusting domains and forests | Grouping people by job or department |
| **Universal** | Accounts, global groups and other universal groups from **any** domain in the forest | Any domain in the forest, and trusting forests | Cross-domain role groups in multi-domain forests |

> **Exam tip:** "Global groups hold people from one domain; domain local groups hold permissions in one domain; universal groups span the forest." Membership is restricted by scope: a global group cannot contain a user from a different domain, and a global group cannot contain a universal or domain local group.

### Nesting rules (which can be a member of which)

| Member | Can join a domain local | Can join a global | Can join a universal |
|---|---|---|---|
| User or computer account | Yes (any domain) | Yes (same domain only) | Yes (any domain in the forest) |
| Global group | Yes | Yes (same domain) | Yes |
| Universal group | Yes | No | Yes |
| Domain local group | Yes (same domain) | No | No |

### Converting the scope

- Global to Universal: only if the group is not a member of another global group.
- Domain local to Universal: only if it contains no other domain local group.
- Universal to Global: only if it contains no other universal group.
- Universal to Domain local: only if it is not a member of another universal group.
- Global to domain local, or the reverse, requires going through universal first.

```powershell
New-ADGroup -Name 'Sales-Users' -GroupScope Global -GroupCategory Security `
    -Path 'OU=Groups,DC=corp,DC=example,DC=com'
New-ADGroup -Name 'FS01-SalesShare-Modify' -GroupScope DomainLocal -GroupCategory Security `
    -Path 'OU=Groups,DC=corp,DC=example,DC=com'
Set-ADGroup 'Sales-Users' -GroupScope Universal       # conversion
```

## AGDLP

The best-practice nesting pattern is **A**ccounts into **G**lobal groups, global groups into **D**omain **L**ocal groups, and domain local groups get the **P**ermissions:

```text
jsmith (Account) -> Sales-Users (Global) -> FS01-SalesShare-Modify (Domain Local) -> NTFS Modify on D:\Shares\Sales (Permission)
```

Why it works: HR-style changes (a new hire) only touch the global group; resource owners only touch which global groups sit in the domain local access group; you never grant permissions to individual users. In a multi-domain forest the pattern becomes **AGUDLP**: the global groups from each domain are placed in one universal group, which is placed in the domain local group.

```powershell
Add-ADGroupMember -Identity 'Sales-Users' -Members jsmith, mlee
Add-ADGroupMember -Identity 'FS01-SalesShare-Modify' -Members 'Sales-Users'
Get-ADGroupMember 'FS01-SalesShare-Modify' -Recursive | Select Name
Get-ADPrincipalGroupMembership jsmith | Select Name, GroupScope
```

> **Watch out:** Universal group membership is stored in the global catalog and replicates forest-wide. Put *global groups* in universal groups instead of many individual users, so a membership change in a global group does not replicate across the forest. Group changes do not take effect on a user's existing sign-in; the user needs a new Kerberos ticket, usually by signing out and in.

## Built-in and special groups

- **Builtin container** (domain local groups): Administrators, Account Operators, Backup Operators, Server Operators, Print Operators, Remote Desktop Users and others.
- **Users container**: Domain Admins, Domain Users, Domain Computers, Enterprise Admins, Schema Admins, Group Policy Creator Owners, DnsAdmins and more.
- **Domain Users** contains every user in the domain; it is the primary group of a user account by default. **Domain Computers** contains domain-joined computer accounts.
- **Special identities** such as Everyone, Authenticated Users, Creator Owner and Batch are automatic and cannot be edited.
- **Protected Users** is a global security group whose members receive extra credential protections: no NTLM, no DES or RC4 in Kerberos pre-authentication, no credential caching, TGT lifetime limited to four hours. It is the right place for privileged accounts, but test applications first.

Administrative groups such as Domain Admins, Enterprise Admins, Schema Admins, Administrators, Account Operators and Backup Operators are *protected*: a background process (**AdminSDHolder** with SDProp, every 60 minutes by default) resets their permissions, so manual delegation on their members is overwritten.

> **Real world:** Keep Enterprise Admins and Schema Admins empty except while you use them. Add Domain Admins only for people who need to administer DCs, and delegate everything else.

## Local groups on member servers

Domain local groups are for AD-wide permissions. A member server also has its own **local groups** (Administrators, Remote Desktop Users). Adding a domain group to a server's local group works (`Add-LocalGroupMember -Group Administrators -Member 'CORP\Server-Admins'`) and is often done by Group Policy using **Restricted Groups** or Group Policy Preferences, which keeps membership consistent.

## Lab it yourself

1. In ADAC or ADUC create `OU=Groups`. Create global group `Sales-Users` (add `jsmith`, `mlee`) and domain local group `FS01-SalesShare-Modify`.
2. Nest `Sales-Users` inside `FS01-SalesShare-Modify`. On FS01 create `D:\Shares\Sales`, share it, and give `CORP\FS01-SalesShare-Modify` the Modify permission through **Security** (NTFS) and the share permissions.
3. Sign in as `jsmith` on a client, verify access, then remove `jsmith` from `Sales-Users` and sign out and in again to see access disappear.
4. Try adding the global group of another domain into `Sales-Users` (it will refuse, since global groups hold same-domain accounts only). Convert `Sales-Users` to universal with `Set-ADGroup` and try to nest it into a global group, then observe the restriction.
5. Add a test account to **Protected Users** and run `klist` after logging in; note that NTLM now fails for it.

## Key takeaways

- Group type (security or distribution) and scope (domain local, global, universal) are separate settings.
- Global groups: same-domain members, usable anywhere. Domain local: members from anywhere, usable only in their own domain. Universal: forest-wide on both sides.
- AGDLP: accounts into global groups into domain local groups that get permissions. Use AGUDLP across domains.
- Universal groups are stored in the GC; keep their members as global groups to limit replication.
- Scope conversions have restrictions: global and domain local convert to universal first.
- Protected Users and protected admin groups (AdminSDHolder) are special; do not rely on delegating permissions on them.
