## Four ways configuration flows from the FortiGate

Four operations move configuration from the FortiGate into FortiManager, and they are easy to confuse:

| Operation | Started by | What it updates | Creates a revision? | Touches the policy package? |
|---|---|---|---|---|
| **Retrieve** (Retrieve Config) | Admin, or FortiManager after a remote script | Device database from the running config | Yes, **if** the config differs from the latest revision | No. Package status becomes **Unknown** |
| **Auto-update** | **FortiGate**, when someone changes it locally | Device database, with the change merged in | Yes (`AutoUpdate`) | No. Device-level changes leave package status alone; policy/object changes can put the package in **Conflict** (Fortinet's package-status table calls a device-side policy change **Out of Sync**) |
| **Auto-retrieve** | **FortiManager**, as a fallback when the FortiGate didn't start an auto-update | Device database (full retrieve) | Yes (`AutoRetrieve`) | No. Package status **Unknown** |
| **Import** (Import Policy) | Admin | **ADOM database**: policies and objects into a policy package | No | Yes. Status **Imported** |

The pattern: **retrieve and auto-update bring device configuration into the device database. Only import brings policies and objects into the ADOM.** After a retrieve, the device database knows about a local policy change, but the policy package doesn't until you import.

## Retrieve

**Retrieve Config** is on the revision history toolbar and in the device's right-click menu. FortiManager reads the FortiGate's running configuration and:

- creates a new revision if it differs from the latest one (no change, no new revision)
- makes that revision the device database, with config status **Synchronized**
- leaves the ADOM database alone, so the policy package shows **Unknown** until you import or install

Use retrieve when:

- the device is **Out of Sync** and you want to **accept** the FortiGate's version
- you want to **discard pending FortiManager changes** (Modified) and start again from what's running
- you finished work on the FortiGate directly (maintenance by a local team, an RMA restore)

> **Watch out:** Retrieve overwrites uninstalled device database changes. If the device is **Modified** because a colleague staged template changes, a retrieve throws them away. Diff first.

## Auto-update and auto-retrieve

**Auto-update is on by default.** When an admin changes the FortiGate locally (GUI, CLI, API), and the change didn't come from a FortiManager install, the FortiGate sends the change to FortiManager over FGFM. FortiManager merges it into the device database, creates an `AutoUpdate` revision and shows **Auto-update** as the config status.

- **Device-level settings** (DNS, routes, interfaces): the policy package status doesn't change.
- **Policy-level settings** (a firewall policy or an object the package uses): the policy package can go to **Conflict**. The ADOM copy now disagrees with the device, so import the policy package (or reinstall it to overwrite the local change).

**Auto-retrieve** is the safety net. It runs only if the FortiGate fails to start an auto-update: when FortiManager detects a change on the FortiGate, it retrieves the **full** configuration itself. The revision is named `AutoRetrieve`. (`fgfm-auto-retrieve-timeout` in `config system dm`, default 1800 s, caps how long FortiManager waits for an auto-retrieve.)

**Turning auto-update off.** If you want an administrator to accept or refuse local changes:

```text
FMG-HQ # config system admin setting
FMG-HQ (setting) # set auto-update disable
FMG-HQ (setting) # end
```

With auto-update disabled, a local change leaves the device **Out of Sync**. The administrator then decides: **retrieve** to accept the change, or **install** from FortiManager to overwrite it. In the GUI the same choice is **System Settings > Advanced > Advanced Settings > Configuration Changes Received from FortiGate**: automatically accept (default) or prompt the administrator to accept.

> **Exam tip:** "A local admin changed the FortiGate and FortiManager already shows the change in a new revision" → auto-update. "FortiManager shows Out of Sync and no new revision" → auto-update is disabled or failed, so retrieve.

> **Real world:** Fortinet's own advice is to make changes on FortiManager, not on the FortiGate. Auto-update is a safety net, not a workflow. Local policy changes in particular leave the policy package in Conflict until someone imports them.

## Reverting to an earlier revision

Revert lets you roll the **device database** back to an older revision.

1. Open the revision history, right-click the revision (or select it and choose **More**) and click **Revert**. FortiManager reverts the device database immediately.
2. Nothing has reached the FortiGate yet: config status **Modified**, CLI `dev-db: modified; cond: pending`.
3. **Install** to push the reverted settings to the FortiGate. Config status returns to Synchronized.

| Step | Device config status | Policy package status |
|---|---|---|
| Before | Synchronized (`dev-db: not modified`, `cond: OK`) | Installed |
| After revert, before install | **Modified** (`dev-db: modified`, `cond: pending`) | Not touched by the revert, so it may no longer match the device database |
| After install | Synchronized | Realign it: Fortinet's guidance after a revert is to import the configuration to sync the policy package, then reinstall the package |

What revert does **not** do:

- It doesn't revert the **ADOM database**. The revert operation doesn't affect the policy package or other modules. A device revert doesn't restore an older policy package, and the next policy package install pushes the **current** package again. To roll back policies, use **ADOM revisions** (domain 3.2), or re-align with an import.
- It doesn't happen instantly on the FortiGate. You must install.

Other ways to restore a configuration:

- **Download Revision** and restore it on the FortiGate (`execute restore config ...` or the FortiGate GUI). This is a full restore that reboots the FortiGate. FortiManager then sees the change through auto-update or retrieve.
- **Import Revision** uploads a configuration file into the revision history. You can then revert to it like any other revision.
- **Capture Diff to a Script** (Revision Diff) turns the difference between two revisions into a CLI script. You can review it and run it as a FortiManager script for a surgical rollback.

## Fixing common configuration issues

| Situation | Fix |
|---|---|
| **Out of Sync**: local change, want to keep it | Retrieve. If policies changed, also import the policy package |
| **Out of Sync**: local change, want to remove it | Install from FortiManager (diff first: the install overwrites the local change) |
| **Modified**: staged changes you want | Install (Install Device Settings (only), or a full install) |
| **Modified**: staged changes you don't want | Retrieve or revert |
| **Auto-update** with policy package **Conflict** or **Out of Sync** | Import the policy package so the ADOM matches the device, or reinstall the package to undo the local change |
| **Conflict** | View Install Log on the new revision. Then either take the device's version (Retrieve Config, then re-import the policy package) or push FortiManager's version (Install Device Settings (only)) after fixing the failing command |
| **Unknown** | Restore FGFM connectivity (lesson 2.1 checklist), then Refresh Device |
| Need the exact differences | Revision Diff (Show Diff Only), or set `force-remote-diff enable` for installs |

## Lab it yourself

On the FortiManager-VM trial with your FortiGate-VM:

1. Change the hostname on the FortiGate CLI. Watch the `AutoUpdate` revision and the **Auto-update** status appear.
2. Disable auto-update (`set auto-update disable`), change the hostname again, and confirm the device goes **Out of Sync** with no new revision. Retrieve and confirm a new revision appears.
3. Revert to the revision before both changes. Check `diagnose dvm device list` (`dev-db: modified`, `cond: pending`), then install and verify the original hostname on the FortiGate.
4. Add a firewall policy on the FortiGate (you have three policies on the trial). Check the policy package status after the auto-update (it can go to Conflict or Out of Sync), then import the policy package to realign it.
5. Re-enable auto-update when finished.

## Key takeaways

- **Retrieve** = pull the running config into the device database. A new revision only if it differs. Package status becomes Unknown.
- **Auto-update** (default on) = the FortiGate pushes local changes. Revision `AutoUpdate`, status Auto-update. Policy changes can put the package in Conflict.
- **Auto-retrieve** = FortiManager's full-retrieve fallback when the FortiGate didn't auto-update. Revision `AutoRetrieve`.
- `config system admin setting` / `set auto-update disable` → local changes leave the device **Out of Sync** until an admin retrieves or installs.
- Only **import** updates the ADOM database (policy packages and objects).
- **Revert** loads an old revision into the device database (Modified), and an **install** pushes it. It doesn't roll back the ADOM's policy packages.
- Diff before you retrieve, install or revert. Each one overwrites one side.
