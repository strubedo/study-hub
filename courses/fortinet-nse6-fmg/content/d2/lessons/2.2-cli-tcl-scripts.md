## What scripts are for

FortiManager scripts make many repetitive changes in one run: add 40 address objects, set the same SNMP community on 300 branches, or collect `get` output from every FortiGate. Scripts live in **Device Manager > Scripts** and belong to the **ADOM** you're in. Global Database ADOM scripts are under **Policy & Objects** (Scripts, or Object Configuration > Advanced > Scripts; enable it in Feature Visibility if it's hidden). At least one FortiGate must be managed before you can use scripts. The 7.6 Administration Guide lists Scripts as an advanced option that's disabled by default and turned on with **Show Script** in System Settings > Settings, so check there if the menu is missing.

Three script types exist in 7.6:

| Type | Language | Runs on |
|---|---|---|
| **CLI Script** | FortiOS CLI (`config` / `edit` / `set` / `next` / `end`) | Device database, policy package or ADOM database, or the remote FortiGate directly (via CLI) |
| **TCL Script** | Tcl, sending CLI commands with `exec` | **Remote FortiGate Directly (via CLI) only** |
| **Jinja Script** | Jinja templating | **ADOM database only** |

In the **Global Database ADOM**, only CLI scripts are supported, and they run only on the policy package or ADOM database.

## Script configuration

Create New opens the script editor:

| Field | Notes |
|---|---|
| **Script Name** | Unique |
| **Comments** | Optional |
| **Type** | CLI Script, TCL Script, Jinja Script |
| **Run Script On** | The target (next section). It decides what the script changes and which run options exist |
| **Script Detail** | The script body. Type it or paste it in |
| **Validate**, **Validate on change**, **Validate device platform** | Syntax check against a chosen platform. **CLI scripts only** |
| **Format CLI script**, **Revert All Changes** | Editor helpers |
| **Advanced Device Filters** | Limit the script to a platform, build, device, hostname or serial number. Not available for Jinja, Global Database scripts, or the policy package/ADOM database target |

The toolbar also offers Run Script, Schedule Script (lesson 2.2 scheduling), Clone, Import CLI Script, Export Script (as `.txt`) and Delete. **CLI script groups** bundle several scripts so they run as one.

## Run Script On: the three CLI targets

This is the most tested part of the topic. The target decides **where the change lands first** and therefore which status changes.

| Run Script On | What happens | Device config status | Policy package status | Next step |
|---|---|---|---|---|
| **Device Database** | FortiManager edits its copy of the device's settings. Nothing touches the FortiGate yet | **Modified** | Unchanged | **Install Device Settings (only)** (or a full install) |
| **Policy Package or ADOM Database** | Edits the ADOM's objects and the selected policy package | Unchanged | **Modified** | **Install Policy Package & Device Settings** |
| **Remote FortiGate Directly (via CLI)** | FortiManager sends the commands to the FortiGate over FGFM, and they take effect immediately. FortiManager then **retrieves** the configuration into the device database, creating a new revision | **Synchronized** | **Unknown** (the ADOM copy wasn't updated; import if the script changed policies or objects) | Review the log. Import policy if needed |

After a remote run, FortiManager by default does a **full retrieve**. `config system dm` / `set conf-merge-after-script enable` merges the script's changes into the device database instead. Fortinet's guide adds that you can then **import** the configuration so the script's policy and object changes reach the ADOM database.

> **Watch out:** Some `config system central-management` fields (`fmg`, `fmg-source-ip`, `fmg-source-ip6`, `serial-number`, `type`, `vdom`) can't be changed by **database** scripts or CLI templates. The commit fails with `not allowed to change`. If you really must change them from FortiManager, use a CLI script on **Remote FortiGate Directly (via CLI)**.

> **Exam tip:** A device database script is "change it in FortiManager, install later". A remote FortiGate script is "change it on the box now, then FortiManager catches up with a retrieve". Policy changes made by a remote script leave the policy package out of step (Unknown) until you import.

Example: the same address object, run three ways.

```text
config firewall address
    edit "Srv-Payroll"
        set subnet 10.20.0.15 255.255.255.255
        set comment "added by script"
    next
end
```

- On the **device database** of FGT-Branch1, it becomes a device-level change. FGT-Branch1 shows Modified, and the object reaches the FortiGate at the next install.
- On the **ADOM database** of `Retail`, it becomes an ADOM object. It installs to any device whose policy package uses it.
- **Directly** on FGT-Branch1, it exists on the FortiGate immediately. The retrieve brings it into the device database, and the ADOM still doesn't know it until an import.

## Best practices for CLI scripts

1. **Use full keywords.** `set hostname`, not `set host`. Abbreviations work on a live FortiGate CLI, but the CLI reference states that scripts run on a **database** (device database, ADOM database or Global Database) must contain only complete commands, or they generate errors. The Administration Guide repeats it for the Global Database (`config system global`, not `conf sys glob`).
2. **Close every context.** Every `config` needs its `end`, and every `edit` its `next`. A missing `end` at the bottom of the script is a classic cause of failure.
3. **Keep scripts short and single-purpose.** Chain them in a script group, because short scripts are easier to troubleshoot.
4. **Nothing else on a command line.** Only a command and whitespace. No punctuation at the start or end of a line. Indent `next`/`end` for readability.
5. **Comment with `#`.** Use it to disable a suspect line while you test.
6. **Mind VDOMs.** On a VDOM-enabled FortiGate, a remote script must enter the right context: `config vdom` / `edit root` for VDOM settings, `config global` for global settings.
7. **Turn off paged output on the FortiGate.** With paging (`--More--`), FortiManager and the FortiGate can wait on each other until the session times out. Set `config system console` / `set output standard` on FortiGates that receive scripts. Also don't include `\r` (Windows line endings) in scripts.
8. **Back up first, test on one device**, then widen the target (filters or groups).
9. **Read-only commands (`get`, `show`, `diagnose`) only make sense on the remote FortiGate.** Their output appears in the script log. On a database target they return nothing useful.
10. **Housekeeping:** FortiManager limits how many scripts it stores, and the script log per device is capped (`script-logsize` in `config system dm`). Delete scripts you no longer need.

```text
# Good: full keywords, closed contexts, VDOM context explicit
config vdom
    edit root
        config router static
            edit 0
                set dst 172.16.50.0 255.255.255.0
                set gateway 10.1.1.254
                set device "port2"
            next
        end
    next
end
```

> **Watch out:** `edit 0` in a static route or policy script means "next free ID". That is fine on a live FortiGate, but think about repeat runs. Running the script twice creates two identical routes.

## Advanced use: Tcl scripts

Tcl adds logic that CLI scripts can't express: variables, loops, `if`, regular expressions on command output, and procedures.

**Enable it first.** The TCL option is hidden until you enable it in the CLI:

```text
FMG-HQ # config system admin setting
FMG-HQ (setting) # set show_tcl_script enable
FMG-HQ (setting) # end
```

Rules:

- The **first line must be `#!`**.
- Send CLI commands with `exec "<command>\n" "<prompt-to-wait-for>" <timeout>`. The `\n` makes the command execute, and the prompt pattern (usually `"# "`) tells Tcl when the output is complete.
- **Don't use `exit`**. It stops the script from running.
- A Tcl script doesn't use the FGFM channel directly like a CLI script does. It runs over **SSH tunneled through FGFM**, so the device needs **valid admin credentials** stored in Device Manager. Wrong or missing credentials make Tcl scripts fail while CLI scripts to the same device still work.
- Some standard Tcl commands are unavailable. File I/O works only in one directory on FortiManager (use a bare file name, not a path), with 10 MB of space for Tcl files.
- Tcl scripts can't be imported through the GUI's Import CLI Script (they'd become CLI scripts). Import them with `execute fmscript import` from the CLI.
- Output from `puts` lands in the script log.

A loop that creates five address objects:

```text
#!
proc do_cmd {cmd} {
    puts [exec "$cmd\n" "# " 15]
}
do_cmd "config firewall address"
for {set i 1} {$i <= 5} {incr i} {
    do_cmd "edit Lab-Host-$i"
    do_cmd "set subnet 10.10.$i.10 255.255.255.255"
    do_cmd "next"
}
do_cmd "end"
```

Using output in logic:

```text
#!
set status [exec "get system status\n" "# " 15]
if {[regexp {Version: (\S+) v([0-9.]+)} $status match model ver]} {
    puts "Model $model runs FortiOS $ver"
}
```

Tcl pitfalls: put braces around expressions that contain user input, and remember that a leading zero means octal (`0011` is 9). Use `catch` to handle errors yourself.

## Other scripted options

- **Jinja scripts** run only on the ADOM database and are mostly used for templated object or policy changes.
- **CLI templates** (provisioning templates, lesson 2.1) are the better choice for configuration that must stay applied. A script runs once. A template is reapplied at every install.

## Lab it yourself

1. In ADOM `Retail`, create a CLI script with the address object above, targeting **Device Database**. Run it on your FortiGate-VM and confirm the status goes to **Modified**. Then run **Install Device Settings (only)**.
2. Clone it, change the target to **Remote FortiGate Directly (via CLI)**, change the object name, and run it. Confirm the object exists on the FortiGate at once, that a new revision appears, and that the config status is **Synchronized**.
3. Enable `show_tcl_script`, check that the FortiGate admin credentials are correct in Device Manager, and run the Tcl loop above.
4. Add `get system status` to a remote CLI script and read the output in the log.

All of this fits the FortiGate-VM trial limits. Address objects and one static route are well under the caps.

## Key takeaways

- Script types: **CLI** (three targets), **Tcl** (remote FortiGate only), **Jinja** (ADOM database only). The Global Database ADOM accepts only CLI scripts, run on the policy package or ADOM database.
- Device database run → device **Modified** → install device settings.
- Policy package or ADOM database run → **policy package Modified** → install.
- Remote FortiGate run → change is live → automatic retrieve → **Synchronized**, policy package **Unknown**.
- Best practice: full keywords, close every `config` with `end`, short scripts, VDOM context, `set output standard` on the FortiGate console, test on one device first.
- Tcl needs `set show_tcl_script enable`, a `#!` first line, `exec "cmd\n" "# " 15`, no `exit`, and valid SSH admin credentials because it runs over SSH inside FGFM.
- Validate checks syntax for CLI scripts only.
