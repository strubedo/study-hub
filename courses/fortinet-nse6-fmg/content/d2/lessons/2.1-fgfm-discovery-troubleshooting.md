## FGFM in one page

**FGFM** (FortiGate-FortiManager protocol) is the management channel between a FortiGate and FortiManager. It carries everything Device Manager does to a device: discovery, authorization, retrieves, installs, scripts, firmware pushes and monitoring.

| Property | Value |
|---|---|
| Transport | **TCP 541**, encrypted with TLS |
| Authentication | Each side presents a Fortinet certificate whose subject carries the **serial number**. FortiManager checks that the serial number in the session matches the certificate and the device record |
| Who connects | **Either side.** FortiManager connects to the FortiGate for Discover Device. The FortiGate connects to FortiManager when `config system central-management` points at it. After the tunnel is up, both sides use it |
| Tunnel | After authentication, FortiManager and the FortiGate build a tunnel with **link-local addresses**. FortiManager's end is the `svr_fgfm` interface (169.254.0.1), and each FortiGate gets its own 169.254.x.x address |
| Liveness | Keepalives (next section) |

Because either side can open the session, FGFM copes with NAT. If FortiManager is behind NAT, the FortiGate calls in to the public address. If the FortiGate is behind NAT, it calls out (domain 5 covers the NAT scenarios in depth).

> **Exam tip:** "Which port must be open?" for FortiGate management is TCP 541. FortiGuard services from FortiManager use other ports (domain 4). Don't mix them up.

## Keepalives and timers

The FortiGate sends FGFM **keepalive** messages to FortiManager. By default that happens every **120 seconds**. Keepalives also tell FortiManager the device's firmware, platform, configuration checksum and AV/IPS versions. If FortiManager hears nothing for the socket idle timeout, it marks the device **down** (connection lost). The FortiGate has to set up the TLS session and tunnel again before management can continue.

Both timers live on **FortiManager**, in `config system dm`:

```text
FMG-HQ # config system dm
FMG-HQ (dm) # set fgfm_keepalive_itvl 120
FMG-HQ (dm) # set fgfm-sock-timeout 360
FMG-HQ (dm) # end
```

| Setting | Range | Value in a default `get system dm` |
|---|---|---|
| `fgfm_keepalive_itvl` (note the underscores) | 30–600 s | 120 |
| `fgfm-sock-timeout` | 90–1800 s | 360 |

Shorter values detect a dead device sooner but cost FortiManager CPU when it manages thousands of devices. Domain 5 (5.4) goes deeper into keepalives and recovery logic.

## FortiGate side: central management

```text
FGT-Branch1 # config system central-management
FGT-Branch1 (central-management) # set mode normal
FGT-Branch1 (central-management) # set type fortimanager
FGT-Branch1 (central-management) # set fmg "203.0.113.10"
FGT-Branch1 (central-management) # set fmg-source-ip 10.1.1.1
FGT-Branch1 (central-management) # set interface-select-method specify
FGT-Branch1 (central-management) # set interface "port2"
FGT-Branch1 (central-management) # end
```

| Attribute | Default | Notes |
|---|---|---|
| `mode` | `normal` | `normal` = managed by FortiManager. `backup` = managed locally, config backed up to FortiManager |
| `type` | `none` | `fortimanager`, `fortiguard` (management through FortiCloud, for example FortiManager Cloud) or `none` |
| `fmg` | (empty) | FortiManager IP or FQDN |
| `serial-number` | (empty) | The FortiManager serial number the FortiGate expects. FortiOS 7.6 offers to fetch and confirm it when you set `fmg`. Unset means an unverified connection |
| `fmg-source-ip` | `0.0.0.0` | Source IP for FGFM. Use it when the FortiGate has several interfaces and FortiManager (or a firewall in the path) expects one address, for example a loopback or the IPsec overlay address |
| `interface-select-method` | `auto` | `auto`, `sdwan` or `specify` (then set `interface`) |
| `vdom` | `root` | The VDOM whose routing reaches FortiManager. It must match the VDOM of the interface you use |
| `enc-algorithm` | `high` | `default`, `high`, `low`. It must be compatible with FortiManager's own setting |
| `allow-push-configuration`, `allow-push-firmware`, `allow-remote-firmware-upgrade`, `allow-monitor` | `enable` | Disabling them blocks FortiManager actions even with a healthy tunnel |
| `schedule-config-restore`, `schedule-script-restore` | `enable` | Allow FortiManager to restore config or scripts |

For **Discover Device** (FortiManager starts the connection), the FortiGate interface that FortiManager targets must allow FGFM. Add `fgfm` to the interface's `set allowaccess` list.

## FortiManager side settings that block devices

| Setting | Effect |
|---|---|
| `config system global` / `set fgfm-allow-vm enable` | FortiManager 7.6.3 and later (default disable): needed to accept new FortiGate-VMs and other VM models. Otherwise they're rejected with "Unsupported device model" |
| `config system global` / `set fgfm-deny-unknown enable` | Default disable. When enabled, devices with an **unknown serial number** can't register themselves as unauthorized devices. Only devices FortiManager already knows (added or modelled) get in |
| `config system global` / `set fgfm-peercert-withoutsn` (7.6.1; gone from the 7.6.3 CLI reference) | Controls whether the peer certificate's CN/SAN must carry the device serial number |
| A **local-in policy** on FortiManager | Can drop TCP 541 from a source it doesn't list |
| `config system global` / `set fgfm-ssl-protocol ...` and `enc-algorithm` | TLS version and cipher strength must overlap with the FortiGate (`ssl-min-proto-version`, central-management `enc-algorithm`) |
| Licence / device count | When the device count is used up (unregistered devices count too), new devices can't be added |

## The discovery and add process

What happens, in order, when a device is added:

1. **TCP connection** to port 541 (from whichever side starts).
2. **TLS handshake.** Both sides exchange certificates. A TLS-version or cipher mismatch fails here.
3. **Identity check.** The serial number in the request is compared with the certificate CN. A mismatch, an unknown issuer or a disallowed VM model is rejected.
4. **Device information.** FortiManager learns the model, firmware, HA mode and VDOMs.
5. **Authorization.** This is automatic for Discover Device after the admin logs in, for a model device with auto-link, or for a matching pre-shared key. Otherwise the device waits in Unauthorized Devices.
6. **Tunnel and session.** The FGFM tunnel comes up with link-local addresses, and the device shows **conn: up**.
7. **Device database.** FortiManager stores the device configuration as a revision. Optionally it imports policies into a policy package (Import Now).

## Basic discovery failure checklist

Work bottom-up, like any network problem:

1. **Reachability:** `execute ping` and `execute traceroute` to FortiManager from the FortiGate, using the same source as FGFM (`execute ping-options source <fmg-source-ip>`). Check `get router info routing-table details <FMG-IP>` for the right egress.
2. **TCP 541 open:** `execute telnet 203.0.113.10 541` from the FortiGate, or a sniffer on either side: `diagnose sniffer packet any 'port 541' 4`. Repeated SYNs with no SYN/ACK mean something in the path (or a FortiManager local-in policy) drops the traffic.
3. **Interface access:** for Discover Device, `fgfm` must be in the FortiGate's `allowaccess`.
4. **Credentials:** Discover needs a FortiGate admin who can approve the request, or a legacy username and password.
5. **TLS and encryption:** compare `ssl-min-proto-version`, `enc-algorithm` and `fgfm-ssl-protocol` on both sides.
6. **Certificates and serial numbers:** custom FGFM certificates must carry the FortiGate serial number. "serial number ... doesn't match subject CN" in the debug means they don't.
7. **VM and licence:** `fgfm-allow-vm` for VMs on FortiManager 7.6.3 and later; free licence slots (`diagnose dvm device list` shows the count).
8. **Path MTU:** a session that stalls right after the client hello can be an MTU problem. Test with `execute ping-options df-bit yes` and `data-size 1472`.
9. **NAT and addresses:** does the FortiGate reach the right public address? Is FortiManager advertising an address the FortiGate can reach?
10. **VDOM:** the `vdom` in central management must match the VDOM that owns the egress interface.

## Useful CLI commands

On **FortiManager**:

```text
FMG-HQ # diagnose dvm device list
--- There are currently 2 devices/vdoms managed ---
--- There are currently 2 devices/vdoms count for license ---

TYPE            OID    SN                 HA      IP              NAME           ADOM     IPS   FIRMWARE         HW_GenX
fmgfaz-managed  231    FGVM02TM24000111   -       198.51.100.11   FGT-Branch1    Retail   N/A   7.0 MR6 (3401)   N/A
                |- STATUS: dev-db: not modified; conf: in sync; cond: OK; dm: installed; conn: up
                |- vdom:[3]root flags:0 adom:Retail pkg:[installed]Branch-PP
fmgfaz-managed  232    FGVM02TM24000112   -       198.51.100.12   FGT-Branch2    Retail   N/A   7.0 MR6 (3401)   N/A
                |- STATUS: dev-db: modified; conf: in sync; cond: pending; dm: retrieved; conn: down
                |- vdom:[3]root flags:0 adom:Retail pkg:[modified]Branch-PP
```

`conn: up/down` is the FGFM connection. The rest of the STATUS line is the configuration state (lesson 2.3). The `vdom` line shows the ADOM and the policy package status. FortiManager prints the FortiOS release in its internal form, major `7.0` plus a maintenance-release number, so `7.0 MR6 (3401)` is FortiOS 7.6 build 3401 (7.0 MR2 = 7.2, 7.0 MR4 = 7.4). For an HA cluster the HA column shows the mode (for example `a-p`), and extra `HA cluster member:` lines list each member's serial, role and `conn` state.

```text
FMG-HQ # diagnose fgfm session-list
FGT-Branch1(231) sn(FGVM02TM24000111) ip(198.51.100.11) conn:0
        state(tunnel) tunnel(169.254.0.2) uptime:Wed Oct 28 08:14:02 2026
Session count = 1 (tunnel 1)
```

Only FGT-Branch1 has a session here. FGT-Branch2 (conn: down above) has no FGFM session, so look at the network path or the FortiGate.

| Command | Purpose |
|---|---|
| `diagnose dvm device list [<device>] [<vdom>]` | Devices, serials, IPs, ADOM, firmware, DB/config/connection status, licence count |
| `diagnose fgfm session-list` | Live FGFM sessions and the FortiGate tunnel IPs |
| `diagnose fmnetwork interface list` | FortiManager interfaces, including `svr_fgfm` (169.254.0.1) |
| `diagnose debug application fgfmsd 255 [<device>]` then `diagnose debug enable` | FortiManager FGFM daemon debug, optionally for one device |
| `execute fgfm reclaim-dev-tunnel <device>` | Tear down and rebuild a device's tunnel (for example after replacing hardware) |
| `diagnose dvm chassis list`, `diagnose dvm device lockinfo <device>` | Chassis inventory; device lock state |

On the **FortiGate**:

| Command | Purpose |
|---|---|
| `show system central-management` | Check `type`, `fmg`, `fmg-source-ip`, `vdom` |
| `diagnose fdsm central-mgmt-status` | `Connection status` (Handshake = FortiManager serial not verified yet, Up) and `Registration status` (Unknown, Unregistered = waiting for authorization, Registered), plus the FortiManager serial |
| `diagnose debug application fgfmd -1` + `diagnose debug console timestamp enable` + `diagnose debug enable` | FGFM client debug. Stop with `diagnose debug disable` |
| `execute telnet <FMG-IP> 541` | Quick TCP test |
| `fnsysctl killall fgfmd` | Restart the FGFM daemon to force a new connection attempt |

Typical FortiGate debug lines:

```text
FGT-Branch2 # diagnose debug application fgfmd -1
FGT-Branch2 # diagnose debug enable
FGFMs: connect error: Network is unreachable
```

`Network is unreachable` means the FortiGate has **no route** toward the FortiManager address. Look at routing, not certificates. By contrast, `FGFMs: Create session ...` after the `SSLv3/TLS write client hello` line means TLS succeeded and the FGFM session is being built.

> **Watch out:** Turn debugs off when you're done (`diagnose debug disable`, `diagnose debug reset`). Leaving fgfmsd at 255 on a busy FortiManager floods the console.

## Lab it yourself

With the FortiGate-VM managed by the FortiManager-VM trial:

1. Run `diagnose fgfm session-list` and `diagnose dvm device list` on FortiManager, and match the tunnel IP and OID.
2. On the FortiGate, set `fmg` to a wrong IP and run `diagnose debug application fgfmd -1` to see the failure. Then fix it.
3. Remove `fgfm` from the FortiGate interface `allowaccess` and try Discover Device from FortiManager. It fails, but a FortiGate-initiated connection still works, because that one only needs outbound access.
4. Run `diagnose sniffer packet any 'port 541' 4` on FortiManager while you run `fnsysctl killall fgfmd` on the FortiGate, and watch the reconnect.

## Key takeaways

- FGFM = **TCP 541**, TLS, serial-number certificates; either side can start the session, and the tunnel uses 169.254.x.x addresses.
- The FortiGate sends keepalives (default **120 s**). FortiManager sets `fgfm_keepalive_itvl` and `fgfm-sock-timeout` (360 s) in `config system dm`.
- `config system central-management` needs `type fortimanager` and `fmg`. `fmg-source-ip` and `interface-select-method specify` control the source.
- Discover Device needs `fgfm` in the FortiGate interface `allowaccess`. FortiGate-initiated registration only needs outbound TCP 541.
- Checklist: route → TCP 541 → allowaccess → credentials → TLS/ciphers → certificate/serial → VM/licence → MTU → NAT → VDOM.
- `diagnose dvm device list` (status, conn, licence count), `diagnose fgfm session-list` (tunnels), `fgfmsd`/`fgfmd` debugs, `execute fgfm reclaim-dev-tunnel`.
