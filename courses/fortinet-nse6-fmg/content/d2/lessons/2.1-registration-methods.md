## Why registration matters

FortiManager manages nothing until a device is **added and authorized**. A FortiGate that only points at FortiManager is not managed. It sits in a waiting list until an administrator accepts it, or until it matches a model device that is set to auto-link. Everything else in Device Manager depends on getting this step right: the device database, revisions, scripts, templates and policy package installs.

There are three main ways in, plus a few special cases.

| Method | Who starts it | When to use it | What the admin supplies |
|---|---|---|---|
| **Add Device > Discover Device** | FortiManager connects to the FortiGate | The FortiGate is online and FortiManager can reach its management IP | Management IP, then FortiGate admin login (and an Allow on the FortiGate) |
| **Request from the FortiGate** (unauthorized device) | FortiGate connects to FortiManager | FortiManager is reachable, but the FortiGate isn't (NAT, remote site), or local staff set it up | `config system central-management` on the FortiGate; Authorize on FortiManager |
| **Add Device > Add Model Device** | Nothing yet. The real device links later | Zero-touch or low-touch provisioning of a unit that isn't online yet | Serial number **or** pre-shared key, model, optional blueprint |

Also in the Add Device menu: FortiGate HA clusters (as model clusters), Security Fabric groups, FortiSASE, FortiGate CNF and FortiProxy. FortiManager 7.6.5 adds **automatic onboarding rules** (configured only in the root ADOM, for FortiGates on FortiOS 7.6.5 and later). They create a model device that auto-links and authorizes a matching FortiGate without a click. It's newer than the 7.6.1 exam baseline.

## Discover Device (FortiManager starts the connection)

Path: select the ADOM, then **Device Manager > Device & Groups > Add Device > Discover Device**.

1. Enter the FortiGate's **management IP** and click Next. FortiManager opens an FGFM connection to the FortiGate on TCP 541.
2. For FortiOS 7.x the wizard uses Security Fabric style authorization: you log in to the FortiGate and click **Allow** on its authorization request. For FortiOS 6.4 and earlier, it switches to **legacy login** automatically and asks for the FortiGate admin username and password. For FortiOS 7.0 and later you can still toggle **Use legacy login** when the browser pop-up can't reach the FortiGate.
3. FortiManager shows the discovered details (model, serial number, firmware, HA mode, VDOMs).
4. You set the **Name** (no spaces or special characters), optional description, **System Template**, **Add to Folder**, **Add to Device Group**, and optionally copy a device dashboard.
5. The wizard runs device checks, then offers **Import Now** or **Import Later**.

The import step (Import Now) pulls the FortiGate's policies and objects into an ADOM policy package (domain 3 covers the full import wizard). Before it finishes you choose:

- **Policy selection:** Import All, or Select Policies and Profile Groups to Import.
- **Object selection:** Import only policy dependent objects, or Import all objects.
- **Interface mapping:** device interfaces to normalized interfaces. "Add mappings for all unused device interfaces" is optional.

The last page shows the **import report**. It lists the objects that will be created or updated in the ADOM database and any conflicts. **You can download it only from that page.** If you close the wizard without downloading, the report is gone. Import Later finishes the wizard with the device registered but no policy package imported.

> **Watch out:** Offline mode (domain 1) blocks discovery and all FGFM communication with FortiGates. If Discover Device fails on a FortiManager that was just set up, check that offline mode is off.

> **Real world:** Discover fails when FortiManager can't reach the FortiGate (outbound-only branch, NAT, TCP 541 blocked toward the branch). Have the FortiGate call home instead.

## Request from the FortiGate (unauthorized devices)

The FortiGate starts the connection when its central management settings point at FortiManager:

```text
FGT-Branch1 # config system central-management
FGT-Branch1 (central-management) # set type fortimanager
FGT-Branch1 (central-management) # set fmg "203.0.113.10"
FGT-Branch1 (central-management) # end
```

On FortiOS 7.6, with no FortiManager `serial-number` set yet, the CLI offers to connect, shows the serial number from FortiManager's certificate and asks you to confirm it. Otherwise the connection stays unverified. The GUI (**Security Fabric > Fabric Connectors > Central Management**) shows a **Verify FortiManager Serial Number** pane.

The FortiGate opens FGFM to TCP 541 on FortiManager. FortiManager checks the peer certificate and serial number, then lists the unit under **Device Manager > Device & Groups > Unauthorized Devices** in the **root ADOM**, whatever the device's firmware version. An administrator selects it and clicks **Authorize**, choosing the target ADOM and device name. On the FortiGate, `diagnose fdsm central-mgmt-status` shows the progress: `Connection status: Handshake` (serial not yet verified), then `Up` with `Registration status: Unregistered` (waiting for authorization), then `Registered`.

Points to know:

- Unauthorized devices can be **hidden**. Hidden devices don't appear in the default list (show them with the display-hidden option) and **don't count** toward the license.
- An unregistered device in the root ADOM **does** count toward the device license (1 device = 1 license). This is why a full licence, or the 3-device trial, can refuse more discoveries.
- `execute central-mgmt register-device <fmg-serial-no> <pre-shared-key>` on the FortiGate registers it to FortiManager with a key. That is the FortiGate half of the pre-shared key method below.

## Model devices (zero-touch and low-touch)

A **model device** is a placeholder in the device database for a unit that isn't online yet. You build its configuration (templates, policy package, metadata variables) in advance. When the real FortiGate connects and matches, FortiManager **links** them and pushes the prepared configuration.

Add Model Device fields worth knowing:

| Field | What it does |
|---|---|
| **Name** | Must be unique in FortiManager, or the wizard fails |
| **Link Device By** | **Serial Number** (preferred when known) or **Pre-Shared Key** |
| **Device Model** | The hardware or VM model. When linking by serial number, enter the serial first |
| **Automatically Link to Real Device** | When enabled, FortiManager links and authorizes the real device automatically when it connects |
| **Enforce Firmware Version** | Upgrade or downgrade the real device to a chosen image (FortiGuard or local image) when it links |
| **Enforce Device Configuration** | Pushes the management interface settings from the model as-is. A mistake here can cut the device off from FortiManager |
| **Use Device Blueprint** | Takes firmware, group, folder, pre-run CLI template, policy package and provisioning templates from a blueprint instead of the wizard |
| Add to Device Group, Assign Policy Package, Provisioning Template, Metadata Variables | Prepare the configuration in advance |

**Link by serial number:** the FortiGate must reach FortiManager (central management configured locally, via FortiZTP/FortiDeploy, or DHCP-delivered settings). FortiManager matches the serial number in the FGFM certificate to the model device.

**Link by pre-shared key:** useful when you don't know which unit will ship to the site. Each model device gets a **unique** key. Someone at the site runs this on the FortiGate:

```text
FGT-Branch2 # execute central-mgmt register-device FMG-VMTM24000001 Br2-Key-7731
```

The first argument is the **FortiManager serial number**, the second is the key. FortiManager matches the key, authorizes the device and applies the model's configuration.

> **Watch out:** Add Model Device is meant for **new** deployments. After FortiManager authorizes the FortiGate (and checks its Internet Service database version), the model's configuration **overwrites** the real FortiGate's configuration. Nothing on the unit is preserved, so plan the management interface (see Enforce Device Configuration) before the device ships.

## Device blueprints and CSV import

A **device blueprint** is a reusable recipe for model devices. It holds: device model, Automatically Link to Real Device, Enforce Firmware Version (and whether the device may download the image from FortiGuard), Enforce Device Configuration, device groups, folder, Fabric Authorization Template, **Pre-Run CLI Template**, **policy package**, **provisioning templates** (system, IPsec, SD-WAN, static route, BGP, CLI, IPS, or a template group) and HA settings.

- You pick a blueprint when you add a model device, or when you **import many model devices from a CSV file**. The CSV needs at least the serial number, the blueprint name and the device name, and the blueprint must exist first.
- Changing a blueprint affects **only devices added after the change**. Existing model devices keep what they got.
- Typical use: hundreds of SD-WAN branches sharing one design, with per-site values in **metadata variables** (CSV columns can set them).

## Device count and FortiGate-VMs

License count rules (FortiManager-VM, hardware and Cloud):

| Situation | Counts as |
|---|---|
| FortiGate, VDOMs disabled | 1 |
| VDOMs enabled, only root | 1 (root) |
| VDOMs enabled | 1 per **traffic** VDOM. The admin-type VDOM and the global VDOM don't count |
| FortiGate HA cluster | The **secondary** units don't count |
| Unregistered device in root ADOM | 1 each (hidden devices don't count) |
| FortiAP, FortiSwitch, FortiExtender | Not counted |
| FortiAnalyzer managed by FortiManager | Counted (and devices synchronized between the two are counted on both) |
| FortiGate with a FortiManager Cloud (FMGC) entitlement | Not counted on FortiManager-VM; counted on FortiManager hardware |

`diagnose dvm device list` prints both numbers at the top: devices/VDOMs **managed** and devices/VDOMs **counted for license**. They can differ (for example, an admin-type VDOM is managed but not counted).

**FortiGate-VMs and FortiManager 7.6.3.** In FortiManager 7.6.0–7.6.2 (the 7.6.1 exam baseline included) there is no VM restriction. FortiManager **7.6.3** (and 7.4.7, 7.2.10) added `fgfm-allow-vm` under `config system global`, **disabled by default**. While it's disabled, FortiManager rejects FGFM connections from FortiGate-VM, FortiCarrier-VM, FortiProxy-VM, FortiFirewall-VM and FortiAnalyzer-VM serial numbers. FortiManager's FGFM debug shows `Unsupported device model`, and the VM never reaches the unauthorized list. VMs that were already managed before the upgrade keep working. To add new ones:

```text
FMG-HQ # config system global
FMG-HQ (global) # set fgfm-allow-vm enable
FMG-HQ (global) # end
```

Enabling it restarts the FGFM daemon, so all device tunnels reconnect briefly. The VM then registers normally.

> **Exam tip:** Know who starts each method. Discover = FortiManager starts, and you need FortiGate admin access. Unauthorized/request = FortiGate starts, and FortiManager only has to accept. Model device = nothing happens until the real unit connects and matches by serial number or key.

## Lab it yourself

Lab: FortiManager-VM trial (3 devices/VDOMs, 2 ADOMs) and one FortiGate-VM permanent trial.

1. On FMG-HQ (7.6.3 or later), run `config system global` / `set fgfm-allow-vm enable`, then check `diagnose dvm device list` (0 devices). On 7.6.0–7.6.2 the setting doesn't exist and isn't needed.
2. **Method 1:** Add Device > Discover Device with the FortiGate-VM's management IP. Make sure `fgfm` is in the FortiGate interface `allowaccess`. Choose Import Later.
3. Delete the device, then on the FortiGate configure `config system central-management` / `set type fortimanager` / `set fmg <FMG-IP>`. Watch it appear under **Unauthorized Devices** in root, and authorize it into a second ADOM.
4. **Method 3:** Delete it again. Create a model device with Link Device By = Serial Number, using the FortiGate-VM's serial and auto-link on, and watch it link when the FortiGate reconnects. (Tip: back up the FortiGate config first. ZTP overwrites it.)
5. Optional: repeat with a pre-shared key and `execute central-mgmt register-device`.

The trial's 3-device limit is enough, but an unauthorized device also takes a licence slot.

## Key takeaways

- Devices must be **added and authorized** before FortiManager manages them.
- **Discover Device**: FortiManager connects to the FortiGate (TCP 541), logs in and asks the FortiGate to Allow, then offers Import Now or Import Later.
- **FortiGate request**: `config system central-management` with `type fortimanager` and `fmg`; the unit appears in **Unauthorized Devices** (root ADOM) and must be authorized.
- **Model devices** link to the real unit by **serial number** or a **unique pre-shared key** (`execute central-mgmt register-device <fmg-sn> <key>`), and ZTP overwrites the real config.
- **Device blueprints** feed model devices and CSV imports. Edits apply only to devices added later.
- The import report is downloadable **only** on the last page of the import wizard.
- License: one per traffic VDOM; HA secondaries, admin VDOM, global and hidden devices aren't counted; unregistered root-ADOM devices are.
- From FortiManager 7.6.3, new FortiGate-VMs need `set fgfm-allow-vm enable` under `config system global` (default disable). Without it they're rejected with "Unsupported device model".
