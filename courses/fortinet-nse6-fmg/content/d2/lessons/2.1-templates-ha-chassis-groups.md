## Template provisioning

Templates let you define a setting once and push it to many devices. They live in **Device Manager > Provisioning Templates**, are stored in the **ADOM database**, and are assigned to devices or **device groups**. Once a template is linked, the settings it controls come from the template, not from what you edit in the device database. Assigning (or unassigning) a template sets the device's config status to **Modified**. At install time FortiManager copies the templates into each device's database in a fixed order (system template first, then CLI pre-VDOM-copy, threat weight, IPsec, static route, BGP, NSX-T, SD-WAN, AP/FortiSwitch/FortiExtender, the policy package, and finally CLI post-VDOM-copy templates). It then diffs that against the FortiGate and pushes only the difference.

| Template type | What it provisions |
|---|---|
| **System templates** | Common system settings: DNS, NTP, admin settings, SNMP, logging, FortiGuard and so on (see below) |
| **IPsec tunnel templates** | Site-to-site / hub-and-spoke VPN definitions |
| **SD-WAN templates** (and SD-WAN overlay templates) | SD-WAN members, zones, performance SLAs and rules |
| **Static route templates**, **BGP templates** | Routing |
| **IPS templates** | IPS sensor assignment |
| **CLI templates** (CLI or Jinja) | Anything else, written as CLI with metadata variables |
| **Certificate**, **Threat Weight**, **Fabric authorization**, **NSX-T service** templates | Certificate enrolment and specialised settings |
| **Template groups** | A bundle of templates assigned as one unit (also selectable in device blueprints) |

Templates use **metadata variables** (`$(variable)` placeholders) for per-device values. Fields that accept a variable show a magnifying-glass icon in the GUI. That is how one SD-WAN or system template serves 500 branches with different IP addresses. Domain 3 covers ADOM-level metadata variables in depth.

> **Exam tip:** "Template provisioning" in the blueprint means preparing configuration in templates before or after a device is added. It pairs with model devices and blueprints: the blueprint names the templates, and the model device gets them on day zero.

## System templates

A **system template** (also called a device profile) is a subset of a device configuration. You switch on the **widgets** you want to control and leave the rest alone:

| Widget | Contents |
|---|---|
| **DNS** | Primary and secondary DNS, local domain, interface selection method |
| **NTP Server** | Sync on/off, sync interval, servers, server mode, source IP |
| **Alert Email** | SMTP server and authentication |
| **Admin Settings** | HTTP/HTTPS/SSH ports, idle timeout, SCP, hostname, time zone, coordinates |
| **SNMP** | v1/v2c communities, v3 users |
| **Replacement Messages** | Custom replacement messages |
| **FortiGuard** | Update and rating server settings (override servers, often pointing at FortiManager) |
| **Log Settings** | FortiAnalyzer / FortiAnalyzer Cloud / FortiManager / syslog logging |
| **Interface** | Zone and interface settings (hidden by default) |

Working with system templates:

- **Create** an empty template or **More > Import** one from a managed device. The import reads that device's current values into the widgets. For replacement messages you pick the device and the objects.
- **Assign to Devices/Groups** links it. You can also pick a system template in the Discover Device wizard.
- A device has **one** system template at a time.
- Some widgets or fields depend on the ADOM version.

> **Watch out:** After you assign a template, edits to those settings in the device database (or on the FortiGate) are overridden by the template at the next install. If a setting keeps "coming back", check whether a template owns it.

## Copying system templates between ADOMs

Templates belong to one ADOM. They don't follow a device that you move to another ADOM. Two ways to copy them:

1. **GUI export/import.** Click the options icon next to Provisioning Templates and choose **Export Templates**, then pick the template categories. FortiManager saves an unencrypted JSON file to your computer. You can edit it offline, then use **Import Templates** in the target ADOM (or on another FortiManager). Some template settings depend on the ADOM version, so import into an ADOM of the same version where you can.
2. **CLI with `execute fmprofile`:**

```text
FMG-HQ # execute fmprofile list-profiles Retail
FMG-HQ # execute fmprofile export-profile Retail 10465 sys-tmpl-retail
FMG-HQ # execute fmprofile import-profile MSSP-CustomerA 5239 /tmp/sys-tmpl-retail
```

The profile ID is **per ADOM**. Create an empty template with the same name in the target ADOM, look up its ID (`execute fmprofile list-profiles MSSP-CustomerA`), and import into that ID. `import-profile` takes the full path of the exported file. The same command family has `import-from-device <adom> <device> <profile-id>` (fill a template from a device), `copy-to-device` and `delete-profile`.

## Wizards

The blueprint lists "Wizards" as its own bullet. In Device Manager you meet these:

| Wizard | Purpose |
|---|---|
| **Add Device** | Discover Device, Add Model Device, HA cluster, Fabric group and others (lesson 2.1 registration) |
| **Import Policy** (Import Configuration) | Pull policies and objects from a device into a policy package. Runs at the end of Add Device (Import Now) or later from the device |
| **Install** | Push the policy package and/or device settings (Install Policy Package & Device Settings, or Install Device Settings (only)) |
| **Re-install Policy** | Repeat a policy package install to the same targets |

Domain 3 covers import and install in detail. Here, know which wizard you need: **Add Device** registers, **Import** brings device policy into the ADOM, and **Install** pushes FortiManager changes to the device.

## Managing FortiGate HA clusters

FortiManager manages an FGCP cluster as **one device**:

- You register the cluster once. Add an operating cluster like a standalone device using the **primary's** IP address, or let the cluster call in. FortiManager detects the HA mode and lists the members (serial numbers, roles) under one device entry. The **HA** column in `diagnose dvm device list` (for example `a-p`) plus its `HA cluster member:` lines, and the device dashboard (HA Status widget, with Synchronized / Out of Sync / Unknown per member), show the cluster.
- The FGFM session runs to the **primary**. FortiManager installs to the primary, and FGCP synchronizes the configuration to the secondaries.
- After a **failover**, the new primary brings up the FGFM session. FortiManager already knows all member serial numbers, so management continues without re-registration. From the cluster's dashboard you can also **Promote** a secondary to primary.
- **Licence:** secondaries don't count.
- FortiManager **can't configure HA** on real FortiGates, and the HA Status widget of a real cluster is read-only. You build the cluster on the FortiGates first. HA settings changed through CLI templates or scripts land in the device database but are **not** pushed at install. A **model HA cluster** (Add Model HA Cluster, a blueprint's HA section, or a CSV with Cluster Id, Cluster Name, Priority and HA Mode columns) lets you pre-provision a pair for ZTP. The member with the higher priority becomes the primary when the pair comes up.

Considerations:

- Don't let the cluster use `ha-mgmt-interface` or `standalone-mgmt-vdom` for its FGFM connection.
- Settings that FGCP doesn't synchronize (non-HA-sync configuration such as HA settings, VDOM exceptions and some per-platform objects) are per member. By default an install skips them. FortiManager 7.6.3 added `config system dm` / `set handle-nonhasync-config enable` to install them to the cluster members.
- In public-cloud clusters (AWS, Azure), FortiManager can't push some device-level changes: `system ha`, `system interface`, `system sdn-connector nic` and `system sdn-connector route-table`. Make those on each FortiGate.
- FortiManager detects clusters in multi-version cluster (MVC) mode and blocks firmware upgrades to them.
- When you replace a member, the new serial number must be known to FortiManager. Domain 5 (5.4) covers replacing a managed FortiGate.

> **Exam tip:** The cluster is one managed device, one license and one device database. FortiManager talks to the primary. Configure HA on the FortiGates, not from FortiManager.

## Chassis management

Select FortiManager models can work with the **Shelf Manager** of FortiGate-5000 ATCA chassis (5050, 5060, 5140 and 5140B) to show the chassis itself: blades in their slots, power entry modules, fan trays (5140/5140B), the Shelf Manager and the shelf alarm panel.

1. Enable it: **System Settings > Advanced > Advanced Settings > Chassis Management**, and set the **Chassis Update Interval** (4–1440 minutes, default 15).
2. Add the chassis: in Device Manager > Device & Groups, right-click the tree and choose **Chassis > Add**. Enter a name, the chassis type, the Shelf Manager's IP address and its authentication (Anonymous, MD5 or Password).
3. Edit the chassis to assign blades to slots (FortiGate or FortiCarrier blades, FortiSwitch blades only in slots 1 and 2). Each chassis then has its own dashboard.

```text
FMG-HQ # diagnose dvm chassis supported-models
FMG-HQ # diagnose dvm chassis list
```

The blades are still managed as ordinary FortiGate devices through FGFM. Chassis management adds hardware visibility. It doesn't add a new way to configure the blades.

## Device groups

Device groups organize devices inside an ADOM (Device Manager > Device & Groups). Use them as targets:

- Provisioning templates and system templates (**Assign to Devices/Groups**)
- Scripts (run on a group; `execute fmscript run ... group <name>` on the CLI)
- Policy package installation targets
- Firmware upgrades and blueprint/model device placement (**Add to Device Group**)

A device can belong to more than one group, and groups can be **nested** (group A inside group B). A group can also carry **metadata variable mappings** that apply to all its members unless a device has its own per-device value. **Folders** are a separate way of organizing the device tree in **Folder View** (not available when the ADOM device mode is Advanced). They aren't the targets you pick when you run scripts or assign templates, so don't confuse "Add to Folder" with "Add to Device Group" in the wizards.

> **Real world:** Build groups around how you change things: region, hardware family, role ("SD-WAN spokes", "DC firewalls"). A script or template pushed to a group of 200 spokes is only as safe as the group membership. Check it before you run.

## Key takeaways

- Provisioning templates (system, IPsec, SD-WAN, routing, IPS, CLI, certificate, template groups) are per ADOM and use metadata variables for per-device values.
- Assigning a template sets the device to Modified. At install, templates are copied into the device database in a fixed order and the diff is pushed.
- System template widgets: DNS, NTP Server, Alert Email, Admin Settings, SNMP, Replacement Messages, FortiGuard, Log Settings, Interface.
- Copy templates between ADOMs with Export/Import Templates (JSON) or `execute fmprofile export-profile` / `import-profile`. Profile IDs are per ADOM.
- An HA cluster is one managed device: FGFM runs to the primary, secondaries aren't licensed, and HA is configured on the FortiGates, not from FortiManager.
- Chassis management adds shelf-manager hardware visibility (`diagnose dvm chassis list`).
- Device groups (nestable) are targets for templates, scripts, installs and firmware. Folders only organize the tree.
