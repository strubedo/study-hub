## Script scheduling

Scheduling is **hidden by default**. Turn it on from the FortiManager CLI before the GUI shows it:

```text
FMG-HQ # config system admin setting
FMG-HQ (setting) # set show_schedule_script enable
FMG-HQ (setting) # end
```

Then right-click a script or script group (or use the toolbar or More menu) and choose **Schedule Script**:

| Option | Meaning |
|---|---|
| **Devices** | Which devices the schedule applies to |
| **Enable Automatic execute after each device install** | Runs the script after every install to that device. If you select it, **no time schedule can be created** |
| **Enable Schedule** | Run at a set time |
| **Recurring** | One Time, Daily, Weekly or Monthly, with the date, day and time |

Restrictions to remember:

- **Scripts that target the Policy Package or ADOM Database can't be scheduled.**
- The two options above (automatic execute after install, and Enable Schedule) are **only** available when the target is **Remote FortiGate Directly (via CLI)**. In practice that means you schedule remote scripts (CLI or Tcl), not database scripts.
- `execute fmscript clean-sched` removes schedule entries for devices that no longer exist.

> **Real world:** Typical schedules are a nightly Tcl script that collects `get system performance status` from every branch, or a script that runs after each install and re-applies a setting a local team keeps changing. If you need that second case, a **CLI template** (lesson 2.1) is usually cleaner. It is applied as part of every install instead of as a separate run.

> **Exam tip:** "The Schedule Script option is missing" → `set show_schedule_script enable`. "The TCL Script type is missing" → `set show_tcl_script enable`. Both are under `config system admin setting`.

## Running a script and finding its log

Run Script asks for the target devices, groups or policy package (depending on the target type) and **Run Now**. You can also run a script from a device's right-click menu in Device & Groups. Each run is a task, and the progress window shows success or failure. Two places keep the results:

- **System Settings > Task Monitor**: expand the script task and choose **View Script Execution History** to open the log.
- The device dashboard: **Configuration and Installation** widget > **Script Status** > **Script Running History**, which also has a **Run Again** button.

On the CLI:

```text
FMG-HQ # execute fmscript list
FMG-HQ # execute fmscript run Retail 12 device FGT-Branch1
FMG-HQ # execute fmscript showlog FGT-Branch1
```

`run` takes `[adom] <script-id> <run_on> <device | group | package-id>`, where `run_on` is one of `device`, `group`, `devicedb`, `adomdb` or `globaldb`. `run-task` does the same asynchronously and returns a task ID.

### Reading a database-run log

```text
------- Executing time: 2026-10-28 10:02:11 ------
Starting log (Run on database)

config firewall address
edit "Srv-Payroll"
set subnet 10.20.0.15 255.255.255.255
next
end
Running script(Add-Payroll) on DB success
------- The end of log ----------
```

A database run echoes the commands. **"on DB success"** means FortiManager's database accepted every line (Fortinet's examples print it either as `Running script on DB success` or with the script name in brackets). Nothing has reached the FortiGate yet.

### Reading a remote-device log

```text
------- Executing time: 2026-10-28 10:05:40 ------
Starting log (Run on device)

FGT-Branch1 $ config firewall address
FGT-Branch1 (address) $ edit "Srv-Payroll"
new entry 'Srv-Payroll' added
FGT-Branch1 (Srv-Payroll) $ set subnet 10.20.0.15 255.255.255.255
FGT-Branch1 (Srv-Payroll) $ next
FGT-Branch1 (address) $ end
FGT-Branch1 $
------- The end of log ----------
```

A remote run shows the FortiGate's own prompts (with `$` in the log) and responses. FortiOS messages such as `new entry ... added`, `current vf=root:0` after `edit root`, or error text appear exactly as the FortiGate printed them. That makes this log the best place to debug.

## Common script execution errors

| Message | Usual cause | Fix |
|---|---|---|
| `command parse error` | The line isn't a valid FortiOS command for that context: a misspelled or **abbreviated** keyword, a command in the wrong `config` context, or a VDOM-enabled device without `config vdom` / `config global` | Use full keywords. Check the context and the ADOM/FortiOS version |
| `unknown action` | The **previous line didn't execute**, often the `config ...` line that should have opened the context | Fix the line before the one reported |
| `Device <name> failed-1` | Usually a problem with the **end of the script** (missing `end`). It can also appear when the device isn't synchronized | Close all contexts. Retrieve or refresh the device and retry |
| `entry not found in datasource` / `value parse error before '<name>'` / `Command fail. Return code -3` | A remote run referenced an object that **doesn't exist on the FortiGate** (for example an address that exists only in the ADOM) | Create the object first (in the same script, above the reference) or install it from FortiManager |
| Other `Command fail. Return code -<n>` | FortiOS rejected the command. The text above the return code says why | Read the line above. Test the command manually on the FortiGate |
| Script hangs, then times out | Paged console output (`--More--`) on the FortiGate | `config system console` / `set output standard` |
| Tcl script fails or prints nothing | Bad admin credentials stored in Device Manager (Tcl uses SSH through FGFM), an invalid command, `exit` in the script, or `\r` line endings | Fix credentials, remove `exit`, test commands by hand |

Example of the `-3` case in a remote log:

```text
FGT-Branch2 $ config firewall policy
FGT-Branch2 (policy) $ edit 7
FGT-Branch2 (7) $ set srcaddr "Branch-LAN"
entry not found in datasource

value parse error before 'Branch-LAN'
Command fail. Return code -3
```

`Branch-LAN` exists in the ADOM database but has never been installed to FGT-Branch2, so the FortiGate can't reference it. The remote target talks to the **FortiGate's** objects, not to the ADOM's.

## Troubleshooting scripts

1. **Read the log first.** The failing line and the FortiOS message usually explain the problem. For scheduled scripts, use the line number in the error.
2. **Check the target.** Does the script make sense on that target? `get`/`show` on a database target gives nothing useful. Policy changes on the device database don't belong there.
3. **Check the context.** Check VDOM mode, the FortiOS version (commands differ between releases) and the ADOM version.
4. **Validate** CLI scripts in the editor against the right device platform.
5. **Shrink the script.** Comment lines out with `#` until it runs, then add them back.
6. **Check the device state.** Is it connected (`diagnose dvm device list`, conn up)? Is it synchronized? Is it locked by another admin (`diagnose dvm device lockinfo <device>`)?
7. **For Tcl:** check the stored admin credentials and that `show_tcl_script` is enabled. Test each `exec` command by hand.
8. **Daemon-level debug** (last resort): `diagnose dvm debug enable dvmcmd` and `diagnose dvm debug trace`, then `diagnose dvm debug disable dvmcmd` when done.

## Useful CLI commands

| Command | Purpose |
|---|---|
| `execute fmscript list` | Scripts with ID, name, type |
| `execute fmscript run [adom] <id> <device\|group\|devicedb\|adomdb\|globaldb> <target>` | Run a script |
| `execute fmscript run-task ...` | Same, asynchronous, returns a task ID |
| `execute fmscript showlog <device>` | Last script log for a device |
| `execute fmscript copy <adom> <script-id> <target-adom> [<prefix>]` | Copy a script to another ADOM |
| `execute fmscript import ...` / `delete <id>` | Import a CLI or Tcl script from an FTP server (the GUI can't import Tcl) / delete |
| `execute fmscript list-tcl-files`, `export-tcl-files`, `clear-tcl-files` | Manage the files Tcl scripts wrote |
| `execute fmscript clean-sched` | Clean schedule entries for deleted devices |
| `config system admin setting` → `show_schedule_script`, `show_tcl_script` | Reveal scheduling and Tcl in the GUI |
| `config system dm` → `script-logsize`, `conf-merge-after-script` | Log size per device; merge instead of full retrieve after remote scripts |

## Lab it yourself

1. Enable `show_schedule_script`. Schedule a remote CLI script with `get system status` to run once, five minutes from now, on your FortiGate-VM. Check the log with `execute fmscript showlog <device>`.
2. Create a remote script that references an address that exists only in the ADOM database. Run it and find the `Return code -3` in the log.
3. Remove the final `end` from a database script and note the error. Then abbreviate `hostname` to `host` and run it on the device database.
4. Try to schedule a script whose target is Policy Package or ADOM Database and note that you can't.

## Key takeaways

- Script scheduling needs `config system admin setting` / `set show_schedule_script enable`.
- Policy Package or ADOM Database scripts can't be scheduled. Automatic execute after install and timed schedules are only offered for Remote FortiGate Directly scripts.
- Database logs end with `Running script(...) on DB success`. Remote logs show the FortiGate's prompts and messages.
- `command parse error` = bad or abbreviated keyword or wrong context. `unknown action` = the previous line failed. `failed-1` = end-of-script problem or unsynchronized device.
- `entry not found in datasource ... Return code -3` on a remote run = the object isn't on the FortiGate yet.
- `execute fmscript list | run | run-task | showlog | copy | clean-sched` are the CLI tools.
