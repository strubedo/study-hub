## Two databases, one FortiGate

FortiManager keeps the configuration of a managed FortiGate in two places:

| Database | Holds | Edited by |
|---|---|---|
| **Device database** (device DB, per device and VDOM) | Device-level settings: interfaces, routing, system settings, DNS, NTP, admin, HA and so on. Its saved snapshots are the **revisions** | Device Manager, system/provisioning templates, device database scripts, retrieves and auto-updates |
| **ADOM database** | Policy packages and the ADOM's shared objects | Policy & Objects, policy package or ADOM database scripts, policy import |

At install time FortiManager combines the policy package, the objects it uses and the device database into the configuration that it pushes to the FortiGate. This lesson is about the **device database** side and the revisions that track it. Domain 5 (5.3) compares the two databases in detail.

## Device configuration status

The **Config Status** column in Device Manager, and the **Configuration and Installation** widget on the device dashboard (Dashboard > Summary), show how the device database compares with the FortiGate:

| Status | Meaning | Usual action |
|---|---|---|
| **Synchronized** | The latest revision (from an install or a retrieve) is confirmed as what's running on the FortiGate | None |
| **Modified** | The device database was changed in FortiManager (GUI edit, template, device DB script, revert) and hasn't been installed | **Install** to push it, or **retrieve** to throw it away |
| **Auto-update** | Someone changed the FortiGate locally and FortiManager automatically took the change into the device database | Review it. Import if policies or objects changed |
| **Modified (recent auto-updated)** | Both at once: changes are pending in FortiManager **and** a local FortiGate change was auto-synced in | Review both sides, then install |
| **Out of Sync** | The FortiGate's configuration no longer matches the latest revision, and the change **wasn't** brought into FortiManager (for example, auto-update is disabled) | **Retrieve** (accept the device's version), or install (overwrite it). Diff first |
| **Conflict** | The install **failed**, or the configuration changed on **both** FortiManager and the FortiGate without an auto-sync | Fortinet's fix: retrieve the device's configuration and re-import the policy package, **or** push FortiManager's copy with Install Device Settings (only). Read the install log first |
| **Unknown** | FortiManager can't tell which revision is running: the connection is down, or there is no revision yet (for example, a model device) | Fix connectivity, then **Refresh** |

Click **Refresh** in the widget, or right-click the device and choose **Refresh Device**, to recheck in real time. FortiManager compares the FortiGate's configuration checksum with the checksum recorded for the latest revision.

The **policy package status** is a separate column with its own values: **Imported**, **Installed**, **Modified** (policies or objects changed in FortiManager), **Out of Sync** (policies or objects changed on the FortiGate), **Never Installed** and **Unknown**. A package is **Unknown** when the device's configuration was retrieved after the last import or install, for example right after a retrieve or auto-retrieve. Fortinet's auto-update description also says a policy-level local change can put the policy layer into **Conflict**. Domain 3 covers package status.

> **Exam tip:** Out of Sync and Auto-update both mean "someone changed the FortiGate directly". The difference is whether FortiManager already took the change in. Auto-update = yes, automatically. Out of Sync = no, a retrieve is still needed.

## Status from the CLI

`diagnose dvm device list` shows the same information as a STATUS line per device:

```text
FMG-HQ # diagnose dvm device list FGT-Branch1
--- There are currently 2 devices/vdoms managed ---
--- There are currently 2 devices/vdoms count for license ---

TYPE            OID    SN                 HA      IP              NAME           ADOM     IPS   FIRMWARE         HW_GenX
fmgfaz-managed  231    FGVM02TM24000111   -       198.51.100.11   FGT-Branch1    Retail   N/A   7.0 MR6 (3401)   N/A
                |- STATUS: dev-db: modified; conf: in sync; cond: pending; dm: retrieved; conn: up
                |- vdom:[3]root flags:0 adom:Retail pkg:[installed]Branch-PP
```

| Field | Read it as |
|---|---|
| `dev-db` | `modified` = the device database has changes that aren't installed. `not modified` = nothing pending |
| `conf` | `in sync` = the latest revision matches the FortiGate's running config. `out of sync` = the FortiGate changed and FortiManager didn't take it in |
| `cond` | Install condition: `OK`, `pending` (changes waiting to be installed), `unknown` (FortiManager can't tell, for example while the connection is down) |
| `dm` | The last device manager operation that set the revision: `installed`, `retrieved`, `autoupdated` |
| `conn` | FGFM connection `up` / `down` |
| `pkg:[...]` | Policy package status and name for that VDOM (`installed`, `imported`, `modified`, `never-installed`, `unknown`, ...) |

(Fortinet's older upgrade-guide example labels the first field `db:` and the device type `fmg/faz enabled`. Current 7.6 output, as in the 7.6 Administration Guide, uses `fmgfaz-managed` and `dev-db:`.)

In the exhibit, someone edited FGT-Branch1's device settings in FortiManager after the last retrieve (`dev-db: modified`, `cond: pending`). The FortiGate itself still matches the last revision (`conf: in sync`), and the policy package is already installed. **Install Device Settings (only)** would clear it.

## The revision history

The revision history repository stores **complete configuration** files for the device: the configuration FortiManager got when the device was added (revision 1), and new revisions from installs, retrieves and auto-updates. Open it from the device's **Configuration and Installation** widget (Total Revisions > **Revision History**).

| Column | Meaning |
|---|---|
| **ID** | Revision number (double-click to view) |
| **Date & Time** | When the revision was created |
| **Name** | Optional, set by an admin (Rename), or a system name such as `AutoUpdate` |
| **Created by** | The admin account, or `AutoUpdate` / `AutoRetrieve` |
| **Installation** | Install status of that revision. **N/A** = never sent to the device itself, usually because a later revision that contained it was installed |
| **Comments** | Comment added when you rename the revision, or a system comment |

Where revisions come from:

| Event | How it appears |
|---|---|
| Install from FortiManager | Admin name in Created by, installation status |
| Retrieve Config | A new revision **if** the running config differs from the latest one |
| Auto-update initiated by the FortiGate | Name and Created by `AutoUpdate`, comment "Auto update from device" |
| Auto-update requested by FortiManager | `AutoUpdate`, comment "Autoretrieve merged config" |
| Full auto-retrieve fallback | Name and Created by `AutoRetrieve`, comment "Retrieve" |
| Import Revision | A configuration file you uploaded |

Toolbar: **View Config**, **View Install Log**, **Revision Diff**, **Retrieve Config**. More menu (or right-click): **Download Factory Default**, **Revert**, **Delete**, **Rename**, **Import Revision**, **Download Revision**.

The number of revisions kept per device is set by `max-revs` in `config system dm` (1–250, default 100). Rename important revisions ("pre-SD-WAN-change") so you can find them later. Import Revision accepts files downloaded from FortiManager or from the FortiGate, but not encrypted FortiGate backups.

> **Real world:** **View Install Log** on the revision an install created is the first place to look when a device lands in Conflict. It shows the commands FortiManager sent and what the FortiGate replied.

## Revision Diff

Select a revision, click **Revision Diff**, choose what to compare it with (another revision, typically the previous one, or the factory default), and choose the output:

| Diff output | Result |
|---|---|
| **Show Full File Diff** | The whole configuration with the differences highlighted |
| **Show Diff Only** | Only the changed sections |
| **Capture Diff to a Script** | Downloads the differences as a CLI **script** (to your browser's downloads folder) that you can review and reuse, for example as a FortiManager CLI script |

A diff-only view of revision 14 against revision 13 might look like this:

```text
Revision 13 (2026-10-27 22:10, admin)          Revision 14 (2026-10-28 09:42, AutoUpdate)
config system dns                               config system dns
-    set primary 10.0.0.53                     +    set primary 192.0.2.53
end                                             end
config router static                            config router static
                                                +    edit 3
                                                +        set dst 172.16.99.0 255.255.255.0
                                                +        set gateway 10.1.1.254
                                                +        set device "port2"
                                                +    next
end                                             end
```

(The GUI shows colored highlights rather than `+`/`-`. The exhibit uses them so it reads as text.) Revision 14 was created by **AutoUpdate**, so the change was made on the FortiGate itself, not in FortiManager.

> **Watch out:** A diff between revision 1 (the configuration as first read from the FortiGate) and a revision committed in Device Manager can show far more changes than you made, because FortiManager orders the configuration differently from the FortiGate. Diffs between two later revisions show only the real changes.

> **Watch out:** A revision is a snapshot of the **device configuration**, policies included, as the FortiGate ran it. That's not the same as the policy package in the ADOM database. Seeing a policy in a revision doesn't mean the ADOM's package has it. Domain 3 (ADOM revisions) covers rollback of the ADOM side.

## Configuration issues to recognize

| Symptom | Likely cause |
|---|---|
| Out of Sync after a local admin's change | Auto-update disabled (or failed), so nothing was taken in |
| Modified right after you assigned a template, a metadata variable or a device DB script | Expected. Install it |
| Conflict after an install | The install failed (the FortiGate rejected a command, or verification found a mismatch). Read View Install Log |
| Unknown | No FGFM connection (check `conn` in `diagnose dvm device list`) |
| Policy package Out of Sync or Conflict after an auto-update | A local change touched policies or objects. Import the policy package |

An install doesn't push the whole device database. FortiManager copies the ADOM objects and templates into the device database, compares it with the FortiGate's configuration and installs only the **difference**. `config system dm` / `set force-remote-diff enable` (default disable) tells FortiManager to **always use the remote diff** when installing, that is, to compute the diff against the configuration retrieved from the FortiGate. Related: `verify-install` (default enable) verifies an install against the remote configuration afterwards.

## Lab it yourself

1. Note your FortiGate-VM's revision count, then change the DNS server **on the FortiGate** CLI. Watch FortiManager: Config Status goes to Auto-update and a new `AutoUpdate` revision appears.
2. Run Revision Diff between the two latest revisions with Show Diff Only, then try **Capture Diff to a Script** and open the downloaded file.
3. Change a system setting in the device database in FortiManager and check `diagnose dvm device list` (`dev-db: modified`, `cond: pending`). Then install and check again.

## Key takeaways

- Device database = device-level settings and revisions. ADOM database = policy packages and objects.
- Config status: **Synchronized**, **Modified** (FortiManager change not installed), **Auto-update** (local change taken in automatically), **Modified (recent auto-updated)** (both), **Out of Sync** (local change not taken in), **Conflict** (install failed, or both sides changed without an auto-sync), **Unknown** (connection down or no revision yet).
- CLI STATUS line: `dev-db`, `conf`, `cond`, `dm`, `conn`. The vdom line shows `pkg:[status]`.
- Revisions are full configuration snapshots, created by install, retrieve (only if different), auto-update (`AutoUpdate`) and auto-retrieve (`AutoRetrieve`).
- Revision Diff: Show Full File Diff, Show Diff Only, Capture Diff to a Script.
- `max-revs` limits stored revisions (default 100). `force-remote-diff` makes installs always use the remote diff against the FortiGate's configuration.
