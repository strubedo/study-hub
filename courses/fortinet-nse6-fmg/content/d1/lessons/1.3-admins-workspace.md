## Administrator profiles

Every administrator account has an **admin profile** that sets what it can see and change in the GUI, CLI and API. Profiles are managed under **System Settings > Admin Profiles**; only Super_User admins can manage them.

### Predefined profiles

| Profile | Access |
|---|---|
| **Super_User** | All system and device privileges. **Cannot be edited.** Required for ADOM creation/upgrade/deletion and ADOM-wide CLI tools such as `execute fmpolicy`, `execute fmscript`, `execute fmprofile`, `diagnose dvm device list`. |
| **Standard_User** | No system privileges, **read-write** on device privileges (Device Manager, Policy & Objects, installs). |
| **Restricted_User** | No system privileges, **read-only** on device privileges. |
| **Package_User** | Read-write on policy and objects (and installs), read-only on system and other settings. |
| **No_Permission_User** | No system or device privileges. |
| **Password_Change_User** | Can only change passwords via CLI or API; no GUI access. |

Predefined profiles cannot be deleted. Standard and restricted profiles can be edited, and you can clone or create new ones. Only Super_User admins manage profiles (Package_User can view the list).

### Profile types

| Type | Purpose |
|---|---|
| **System Admin** | The normal type. Each permission (System Settings, Device Manager, Policy & Objects, FortiGuard Center, Install, Lock/Unlock ADOM, Script Access, ...) is set to None, Read-Only or Read-Write. |
| **Restricted Admin** | For delegating **Web Filter, IPS and Application Control profiles** only. The admin works in a simplified *Restricted Admin Mode* GUI, edits only the profiles assigned to the account, and can install them to their ADOM if **Allow to Install** is enabled. Workflow mode is not supported for restricted admins. |
| **ADOM Scoped Admin** (new in 7.6.0) | Lets an ADOM's own administrator manage administrators **inside that ADOM only**. Available when the account's Administrative Domain is **Specify** and Admin Profile is **Single**. Set System Settings to None if they must not touch global settings. CLI: `set adom-admin enable` in the profile. |

A profile example in the CLI (attribute names match the GUI permissions):

```text
FMG-HQ # show system admin profile Retail_Ops
config system admin profile
    edit "Retail_Ops"
        set description "Store firewall operators"
        set system-setting none
        set adom-switch read-write
        set device-manager read-write
        set device-op read
        set policy-objects read-write
        set adom-policy-packages read-write
        set deploy-management read-write
        set adom-lock read-write
        set fgd_center none
        set script-access read
        set script-run none
    next
end
```

## Administrator accounts and multiple-admin security

Create accounts in **System Settings > Administrators > Create New**. For each account you decide:

| Setting | Options |
|---|---|
| Admin Type | LOCAL, RADIUS, LDAP, TACACS+, PKI, Group, SSO (and REST API Admin for API keys) |
| Administrative Domain | All ADOMs, All ADOMs except specified ones, or Specify (optionally limited to a **device group**) |
| Admin Profile | **Single** (one profile for every ADOM) or **Per-ADOM** (a different profile in each ADOM, listed as `ADOM:profile`) |
| Policy Package | All packages, or specific packages/folders |
| Policy Blocks | All or specific blocks |
| JSON API Access | None (default), Read, Read-Write |
| Trusted Hosts | Up to ten IPv4 and ten IPv6 |
| Two-factor | FortiToken Cloud (mobile, email, SMS), or PKI with password |

**Trusted hosts** apply to the GUI and to SSH; console access is unaffected. If *every* administrator has trusted hosts, FortiManager does not answer administrative access or ping from anywhere else. One unrestricted account re-opens access on every interface with administrative access enabled. To use the GUI's CLI Console with trusted hosts set, add `127.0.0.1/32` as a trusted host.

Other protections: the lockout after failed logins (`admin-lockout-threshold`, default 3; `admin-lockout-duration` 60 seconds), the password policy (7.6 adds **Enforce Password History**, 1 to 20 previous passwords), idle timeouts, and the rule that FortiManager returns a generic error on failed authentication without saying which field was wrong.

## External validation of non-local administrator logins

Remote authentication servers are defined first, then referenced by accounts.

* **RADIUS** (`config system admin radius`): server, secret, optional secondary server, authentication type (ANY by default tries all).
* **LDAP** (`config system admin ldap`): server, DN, bind type, optional group and `memberof-attr`.
* **TACACS+** (`config system admin tacacs`).
* **Groups** (`config system admin group`, CLI only): combine servers. Servers of the same type act as backups; servers of different types let one wildcard account cover all of them.
* **PKI**: certificate-based login, enabled with `config system global` → `set clt-cert-req enable`.
* **SAML SSO**: FortiManager as a service provider.

The **wildcard** account is the key idea. In the GUI it is *Match all users on remote server*:

```text
FMG-HQ # show system admin user RADIUS-Admins
config system admin user
    edit "RADIUS-Admins"
        set user_type radius
        set radius_server "NPS-1"
        set wildcard enable
        set profileid "Standard_User"
        set adom-access specify
        set adom "Retail"
        set ext-auth-group-match "FMG-Retail-Ops"
        set trusthost1 10.0.10.0 255.255.255.0
    next
end
```

Any user the RADIUS server accepts can log in with this account's profile and ADOM scope; `ext-auth-group-match` narrows that to members of one group. Two options let the server decide instead:

* `ext-auth-accprofile-override enable`: use the access profile supplied by the server.
* `ext-auth-adom-override enable`: use the ADOM supplied by the server (RADIUS vendor-specific attributes; Fortinet vendor ID 12365, attribute `Fortinet-Vdom-Name`).

Without `wildcard`, the FortiManager username must exactly match the remote username. For a remote account with a local password set, that password is used only when the remote server is unreachable.

> **Exam tip:** "Users authenticate on RADIUS but get the wrong ADOM or profile" points to the override options or group match. "Nobody can log in with RADIUS but `admin` works" points to the server definition, shared secret or reachability.

## Administrator session monitoring

* GUI: **Dashboard > System Information > Current Administrators > Current Session List**. It shows user name, source IP and login type (GUI, jsconsole or SSH), start time and timeout. Select sessions and **Delete** to disconnect them.
* CLI:

```text
FMG-HQ # diagnose system admin-session list
FMG-HQ # diagnose system admin-session status
FMG-HQ # diagnose system admin-session kill <sid>
```

* Idle timeouts live in `config system admin setting`: `idle_timeout` (SSH/console and others, 60 to 28800 seconds, default 900), `idle_timeout_gui` (default 900), `idle_timeout_api` (default 900), `idle_timeout_sso`.
* Disconnecting an admin also releases every lock they hold (see below), which is how you recover an ADOM someone forgot to unlock.

## Concurrent ADOM access and workspace mode

By default **workspace is disabled**, which means **concurrent ADOM access**: several administrators can edit the same ADOM at the same time, and the last save wins. To prevent that, enable workspace:

```text
FMG-HQ # config system global
FMG-HQ (global) # set workspace-mode normal
FMG-HQ (global) # end
```

| `workspace-mode` | Effect |
|---|---|
| `disabled` (default) | Concurrent access; no locking. |
| `normal` | **Workspace**: lock before you change. |
| `workflow` | Workspace plus a **session/approval** process before policy changes are installed. |
| `per-adom` | Choose Disable/Workspace/Workflow per ADOM in **System Settings > ADOMs > Edit**. |

Changing the mode ends your session. Disabling workspace warns that logged-in users may lose unsaved data.

### Effects of workspace mode

* Device Manager and Policy & Objects become **read-only** until you lock something.
* You can lock the whole **ADOM**, or individual **devices**, **policy packages**, **policies** (if `set per-policy-lock enable`), **objects** and **policy blocks**.
* Adding devices or policy packages, and creating scripts, require the **whole ADOM** to be locked. A script can still be *run* on a device when only that device is locked.
* AP Manager, VPN Manager, FortiSwitch Manager and Extender Manager need the ADOM lock.
* Individual devices cannot be locked when the device mode is **Advanced**.
* Changes are not live until you click **Save**; **Unlock** asks whether to save or discard.
* A green padlock means you hold the lock; red means another admin does.
* All your locks are released when you **log out** (or are disconnected).
* Only the admin who locked an ADOM can unlock it, unless **ADOM lock override** is enabled (`set lock-preempt enable` under `config system global`), which lets another admin break the lock and discard the holder's unsaved changes.
* Locking the ADOM automatically removes your own device and package locks inside it. If **another** admin holds a device or package lock, you can lock the ADOM only by disconnecting them.
* JSON API device-level changes do not need an ADOM lock.
* Restricted admins clicking the lock icon lock only their profiles, not the ADOM; when a normal admin locks the ADOM, restricted admins become read-only.

Domain 3 covers locks, workflow sessions and approvals in depth; for the exam's Domain 1 bullets, know the four `workspace-mode` values, the default, and the lock rules above.

## Lab it yourself

1. Create a custom System Admin profile `Retail_Ops` like the example and an account restricted to ADOM `Retail`.
2. Log in as that user in a private browser window; confirm the ADOM list shows only `Retail` and System Settings is hidden.
3. As `admin`, open **Current Session List** and disconnect the other session; run `diagnose system admin-session list` before and after.
4. `set workspace-mode normal`, log back in as two admins, lock `Retail` as one and look at the red padlock from the other.
5. Try `set lock-preempt enable` and break the lock from the second account.
6. If you have a RADIUS server (Windows NPS or FreeRADIUS), build the wildcard account and test `ext-auth-group-match`.

## Key takeaways

* Predefined profiles: Super_User (not editable), Standard_User (device RW), Restricted_User (device RO), Package_User, No_Permission_User, Password_Change_User.
* Profile types: **System Admin**, **Restricted Admin** (web filter/IPS/app control delegation), **ADOM Scoped Admin** (7.6: manage admins within their own ADOM).
* Remote admins: RADIUS, LDAP, TACACS+, PKI, SAML; a **wildcard** account matches all server users; group match and profile/ADOM override refine it.
* Sessions: Current Session List in the dashboard, `diagnose system admin-session list | kill`.
* Workspace is **disabled by default** (concurrent access); `workspace-mode normal | workflow | per-adom` enables locking.
* Locks are released at logout; `lock-preempt` lets another admin override an ADOM lock.
