## JSON-RPC over HTTPS

The FortiManager API is **JSON-RPC**: every request is an HTTPS `POST` to one endpoint, and the JSON body says what to do and to which resource.

```text
POST https://<fortimanager>/jsonrpc
Content-Type: application/json
```

Every request body has the same shape:

```json
{
  "method": "get",
  "params": [
    { "url": "/pm/config/adom/Retail/obj/firewall/address" }
  ],
  "session": "<session id>",
  "id": 1
}
```

| Field | Meaning |
|---|---|
| `method` | The operation (`get`, `add`, `set`, `update`, `delete`, `exec`, ...). |
| `params` | An array; each element names a `url` (the resource path inside FortiManager) and, for writes, a `data` object or array. Options such as `fields`, `filter`, `range`, `loadsub` go here too. |
| `session` | The session token from login. Not used with an API key. |
| `id` | Any number you choose; FortiManager echoes it so you can match responses to requests. |
| `verbose` | Optional. `"verbose": 1` returns option *names* (`"action": "accept"`) instead of internal index numbers. |

The URL is a FortiManager database path, not an HTTP path. A few you will see over and over:

| URL | Points at |
|---|---|
| `/sys/login/user` | Login (with `exec`). |
| `/sys/logout` | Logout (with `exec`). |
| `/sys/status` | System status. |
| `/dvmdb/adom` and `/dvmdb/adom/<adom>/device` | ADOM list and the devices in an ADOM. |
| `/pm/config/adom/<adom>/obj/firewall/address` | Firewall address objects in an ADOM. |
| `/pm/config/adom/<adom>/pkg/<pkg>/firewall/policy` | Policies inside a policy package. |
| `/pm/pkg/adom/<adom>` and `/pm/pkg/adom/<adom>/<pkg>` | Policy package list / one package, including its installation targets. |
| `/task/task/<id>` | A task's progress (for asynchronous operations). |
| `/sys/proxy/json` | Forward a FortiOS REST API call to managed FortiGates. |

## Supported methods

| Method | What it does |
|---|---|
| `get` | Read an object or a table. |
| `add` | Create a new object. Fails if an object with that name already exists. |
| `set` | Create-or-overwrite: behaves like `add` if missing, otherwise replaces the object's attributes. |
| `update` | Change only the attributes you send; existing child-table data is kept. |
| `replace` | Like `update`, but child-table content you did not send is removed. |
| `delete` | Remove an object (or, with `filter` and `"confirm": 1`, every object matching the filter). |
| `clone` | Copy an object (for example an ADOM or a policy package) under a new name. |
| `move` | Reorder an object, such as moving a policy before/after another. |
| `exec` | Run an action: login, logout, install, import, run a script and so on. |

> **Exam tip:** Login and logout are not `get`/`set`: they are **`exec`** calls on `/sys/login/user` and `/sys/logout`.

## Two ways to authenticate

### Session-based (login and logout)

1. Create an ordinary administrator, give it an admin profile with the permissions the automation needs, and set **JSON API Access** to Read or Read-Write (CLI attribute `rpc-permit`, default **none**).
2. Log in:

```json
{
  "method": "exec",
  "params": [
    {
      "url": "/sys/login/user",
      "data": { "user": "api-ops", "passwd": "S3cret!pass" }
    }
  ],
  "id": 1
}
```

3. FortiManager answers with a session string, which you put in the `session` field of every later request:

```json
{
  "id": 1,
  "result": [
    {
      "status": { "code": 0, "message": "OK" },
      "url": "/sys/login/user"
    }
  ],
  "session": "Dr9f0BKtQjv2c4Wb6Hk8yLmPq1sT3uVx..."
}
```

4. When finished, **log out** so the session slot is freed:

```json
{
  "method": "exec",
  "params": [ { "url": "/sys/logout" } ],
  "session": "Dr9f0BKtQjv2c4Wb6Hk8yLmPq1sT3uVx...",
  "id": 99
}
```

Fortinet's API best-practice guide stresses logout: sessions that are never closed pile up until the per-user limit (`login-max` on the admin, default 32) or the system-wide limit (`admin-login-max` under `config system admin setting`, default 256) is reached, and then that user (or everyone) is refused until the sessions expire or are killed. API sessions also time out on their own (`idle_timeout_api` under `config system admin setting`, default 900 seconds).

### Predefined API key (REST API Admin)

Go to **System Settings > Administrators > Create New > REST API Admin**. You choose the admin profile and JSON API access, and **at least one trusted host is mandatory**. FortiManager generates a permanent key and shows it **once**. A new key can be generated from the GUI (**Regenerate API Key**) or the CLI:

```text
FMG-HQ # execute api-user generate-key api-noc
```

The key goes in the HTTP header using the bearer scheme:

```text
Authorization: Bearer <api key>
```

With a key there is no login or logout; the account always shares the same session. Passing the key as an `access_token` query string is no longer supported from 7.4.7/7.6.2, so use the header. The CLI user type for this account is `user_type api`.

> **Watch out:** An API key is only as safe as its trusted hosts. The REST API Admin requires them for that reason. FortiManager also performs a source-IP check on JSON API requests by default (`api-ip-binding` under `config system global`, default enable).

## Status codes: two layers

The response has **two** places where something can go wrong, and the exam separates them.

**HTTP status code** (transport and access). Fortinet's 7.6 API best-practice guide lists:

| HTTP code | Meaning |
|---|---|
| 100 | Request headers received, waiting for the body. |
| 200 | Success (the request was processed; check the JSON status too). |
| 401 | Invalid session or token. |
| 403 | Permission denied. |
| 404 | Not found: the resource could not be located. |
| 405 | Method not allowed for this resource. |
| 500 | Internal error. |
| 503 | Service unavailable. |

**JSON-RPC status inside the body** (what happened to *your* operation). Each element in `result` has a `status` object. `code: 0` with `message: "OK"` is success; negative codes are errors. The public best-practice guide lists only the HTTP codes; the body codes below are the ones documented on the Fortinet Developer Network and seen in Fortinet community examples, so learn them by message rather than as an official exhaustive list:

| Code | Message |
|---|---|
| 0 | OK |
| -2 | Object already exists |
| -3 | Object does not exist |
| -6 | Invalid url |
| -10 | The data is invalid for selected url |
| -11 | No permission for the resource |

An HTTP 200 does **not** prove that the change worked: an `add` of an address that already exists comes back with HTTP 200 and `"code": -2` in the body. Scripts must check `result[n].status.code`.

```json
{
  "id": 3,
  "result": [
    {
      "status": { "code": -2, "message": "Object already exists" },
      "url": "/pm/config/adom/Retail/obj/firewall/address"
    }
  ]
}
```

## Use case: get the installation targets of a policy package

A policy package's installation targets are stored in its **`scope member`** attribute. Read the package:

```json
{
  "method": "get",
  "params": [ { "url": "/pm/pkg/adom/Retail/Branch-PP" } ],
  "session": "Dr9f0BKtQjv2c4Wb6Hk8yLmPq1sT3uVx...",
  "id": 5
}
```

```json
{
  "id": 5,
  "result": [
    {
      "data": {
        "name": "Branch-PP",
        "obj ver": 12,
        "oid": 4512,
        "package settings": { "central-nat": 0, "ngfw-mode": 0 },
        "scope member": [
          { "name": "FGT-Branch1", "vdom": "root" },
          { "name": "FGT-Branch2", "vdom": "root" }
        ],
        "type": "pkg"
      },
      "status": { "code": 0, "message": "OK" },
      "url": "/pm/pkg/adom/Retail/Branch-PP"
    }
  ]
}
```

A device target carries `name` and `vdom`; a device-group target carries only the group `name` (FortiManager treats an entry without `vdom` as a group). A package with no targets simply has no `scope member` key. Querying `/pm/pkg/adom/Retail` without a package name returns every package in the ADOM, each with its own `scope member` list.

> **Exam tip:** Notice the spaces in `"scope member"`, `"obj ver"` and `"package settings"`. FortiManager API attribute names often contain spaces; they are not typos.

## Good habits that show up as questions

* Use `fields`, `filter`, `range` and `loadsub: 0` to fetch only what you need instead of a whole table.
* Use the object's full URL (`.../obj/firewall/address/Server-01`) rather than reading the whole table and searching.
* URLs that support task creation (for example `/dvm/cmd/update/dev-list` to refresh several devices, or the add-device commands) accept `"flags": ["create_task", "nonblocking"]`; poll `/task/task/<id>` to see when they finish. If you log out while such a task runs, it can be reported as failed in Task Manager because the session is gone.
* Workspace locks: in workspace mode a GUI admin must lock the ADOM, but **device-level changes through the API do not require an ADOM lock**. Policy and object changes still follow the workspace rules (lock via the `/dvmdb/adom/<adom>/workspace/lock` URL).
* `execute fmpolicy` and similar ADOM-wide CLI tools need Super_User; an API user needs only the profile rights for its task, so build a dedicated profile.

## Lab it yourself

The trial FortiManager-VM supports the API.

1. Create admin `api-ops` with profile `Standard_User`, **JSON API Access: Read-Write**, trusted host = your Linux box.
2. From Linux: `curl -k -s https://<fmg>/jsonrpc -d '{"method":"exec","params":[{"url":"/sys/login/user","data":{"user":"api-ops","passwd":"..."}}],"id":1}'` and copy the session.
3. `get` `/dvmdb/adom` and `/pm/pkg/adom/root`. Add `"verbose": 1` and compare.
4. Try an `add` of an address that already exists to see `-2`, and a mistyped URL to see `-6`.
5. Log out. Then repeat step 3 with the old session to see the request rejected.
6. Optional: `config system global` → `set jsonapi-log all` and watch your calls appear in the event log.

## Key takeaways

* One endpoint: HTTPS `POST /jsonrpc`; the body carries `method`, `params[].url`, `data`, `session`, `id`.
* Methods: `get`, `add`, `set`, `update`, `replace`, `delete`, `clone`, `move`, `exec`. `add` fails on duplicates; `set` creates or overwrites.
* Login = `exec` on `/sys/login/user`; logout = `exec` on `/sys/logout`; always log out to free session slots.
* REST API Admin keys are permanent, shown once, sent as `Authorization: Bearer`, and require a trusted host.
* HTTP codes (200, 401, 403, 404, 405, 500, 503) describe the transport; `result[].status.code` (0, -2, -3, -6, -10, -11) describes your operation.
* Installation targets are in the package's `scope member` attribute at `/pm/pkg/adom/<adom>/<pkg>`.
