## What FortiManager is for

FortiManager is Fortinet's central management platform. One FortiManager (or an HA cluster of them) holds the configuration of every managed FortiGate, lets administrators build firewall policy once and install it on many devices, keeps a revision history of every configuration, upgrades firmware, and can act as a local FortiGuard server so that FortiGates do not each have to pull updates from the Internet. Fortinet positions it for medium and large enterprises and MSSPs; it scales to thousands of devices and VDOMs from one GUI.

The exam's "key features" list maps to these capabilities:

| Feature | What it gives you |
|---|---|
| Centralized management | Build configuration in one repository and push it to many devices. |
| Administrative domains (ADOMs) | Partition devices, policy and objects by customer, region, firmware or team. |
| Revision control | Every install and every change retrieved from a device is stored as a revision you can diff, revert or re-install. |
| Local FortiGuard service provisioning | FortiManager downloads AV/IPS packages and web/email filter databases once and serves them to devices on the LAN. |
| Firmware management | Store firmware images and upgrade devices individually, in groups or with firmware templates. |
| Scripting | CLI scripts (run on the FortiGate directly, on the device database, or on the policy package/ADOM database), Tcl scripts (FortiGate directly only) and, from 7.6.4, Jinja scripts (ADOM database only). |
| Security Fabric awareness | Recognises Fabric groups, shows physical/logical topology and Security Rating in Fabric View. |
| Logging and reporting (optional) | FortiAnalyzer features on the FortiManager itself, or a managed FortiAnalyzer shown inside FortiManager. |

## Inside FortiManager: modules and databases

Think of FortiManager as a set of modules sitting on top of two kinds of database.

**The device database (device layer).** When a device is added and FortiManager retrieves its configuration over the FortiGate-FortiManager protocol (FGFM), FortiManager creates a database holding that device's *complete* configuration. Device Manager edits it directly: hostname, interface IPs, routing, admin settings and other device-level items.

**The ADOM database (ADOM and policy layer).** Each ADOM has one common object database (addresses, services, security profiles) plus its policy packages, provisioning templates, AP profiles and FortiSwitch/FortiExtender templates. Policy & Objects, VPN Manager, AP Manager, FortiSwitch Manager and Extender Manager all write here.

**The global database ADOM (optional top layer).** Header and footer policies and global objects that can be assigned to policy packages in many ADOMs (Domain 4.3).

How a change reaches a FortiGate:

1. FortiManager copies the relevant ADOM-level items (policy package, objects, templates) into the target's device database. Fortinet calls this the *VDOM copy*; after it, the device shows **Modified** in Device Manager.
2. FortiManager retrieves the running configuration from the real FortiGate, compares it with the updated device database and installs only the **difference** over FGFM.

Two consequences that the exam likes:

* Changes made through the central modules (Policy & Objects and friends) **overwrite** the matching part of the device database at the next install. "Policy package changes overwrite device database changes."
* A CLI template line is not replayed literally on the FortiGate. Only the diff between device database and running config is sent.

The modules that talk to devices with their own protocol are **Device Manager** (FGFM, TCP 541), **FortiGuard** (the FortiGuard update and rating protocols) and the **FortiAnalyzer features** (logging protocol). The others feed the device database and rely on Device Manager to install.

> **Exam tip:** Device-level settings such as hostname and interface IP can only be edited in the device database (Device Manager). Policy-level settings come from the ADOM database. When you see "the change was lost after the next policy install", think "the setting is owned by the policy package, which overwrote the device database".

## Network topology and the ports you must know

A typical deployment puts FortiManager in a management or data-centre network, with FortiGates connecting to it across the WAN or Internet. FortiManager can sit behind NAT, the FortiGate can sit behind NAT, or both (Domain 5.1).

| Flow | Port | Notes |
|---|---|---|
| FGFM management tunnel | TCP 541 | Either side can initiate. Carries install, retrieve, auto-update, keepalives. |
| Administrator GUI / JSON API | TCP 443 (HTTPS) | API calls go to `https://<fmg>/jsonrpc`. |
| Administrator CLI | TCP 22 (SSH), console | |
| FortiGate AV/IPS updates from FortiManager (local FDS) | TCP 8890 (default) or TCP 443 | FortiGate `fmg-update-port`. |
| FortiGate web filter / email filter rating queries to FortiManager | UDP 53 or UDP 8888 (TCP 80/8888 also listed) | FortiGate `protocol`/`port` under `config system fortiguard`. |
| FortiGuard push notifications to FortiManager | UDP 9443 | Only if push updates are enabled. |
| FortiManager HA heartbeat and sync | TCP 5199 | Between cluster members. |

> **Watch out:** "Service Access" (FortiGate Updates, Web Filtering) is **not enabled on any FortiManager interface by default**. A FortiManager can be a perfectly healthy manager on port1 and still ignore every FortiGuard request until you enable the service on the interface the FortiGates use.

## ADOMs in one paragraph

ADOMs are disabled by default. When a Super_User enables them (`config system global` → `set adom-status enable`, or the toggle in the System Information widget), each ADOM gets its own Device Manager view, object database and policy packages, and administrators can be restricted to the ADOMs they own. Every ADOM has a version (7.2, 7.4 or 7.6 on FortiManager 7.6) that matches FortiOS syntax. Lessons 1.3 cover modes, versions, upgrade and moves in detail.

## FortiManager and FortiAnalyzer: two different integrations

The blueprint lists two separate ideas that are easy to mix up.

**FortiManager *with* FortiAnalyzer features.** FortiManager itself stores logs and runs the analytics modules: FortiView, Log View, Incidents & Events and Reports. You enable it in the System Information widget or with:

```text
FMG-HQ # config system global
FMG-HQ (global) # set faz-status enable
FMG-HQ (global) # end
```

The FortiManager **reboots** to apply the change. Log forwarding, log fetching and log aggregation are not supported on FortiManager even with the features on.

**FortiManager *managing* a FortiAnalyzer.** You add a real FortiAnalyzer (or FortiAnalyzer BigData) in Device Manager with **Add Device > Add FortiAnalyzer** (or, since 7.4.1, through a Fabric connection). Logs stay on the FortiAnalyzer and its storage settings are configured there; FortiManager reads the data remotely and shows FortiView, Log View, Incidents & Events and Reports in its own GUI. Adding a FortiAnalyzer turns the FortiAnalyzer features on automatically, and they cannot be disabled while it is managed.

Rules that make good exam distractors:

| Rule | Detail |
|---|---|
| Mutually exclusive with HA | FortiAnalyzer features must be **disabled** before you can form a FortiManager HA cluster. |
| Cannot add a FortiAnalyzer while FAZ features are on | The **Add FortiAnalyzer** option is hidden. |
| Not with advanced ADOM mode | You cannot add a FortiAnalyzer when ADOMs are enabled with ADOM mode **Advanced**. |
| Versions | FortiManager and FortiAnalyzer must run the same version. |
| Per ADOM | With ADOMs enabled, one FortiAnalyzer per ADOM; the same FortiAnalyzer can be added to several ADOMs. The ADOM name and logging devices must match on both sides (the wizard synchronizes them). |
| Device count | The FortiAnalyzer device limit must be at least the number of devices managed (or in the ADOM). |
| VM | FortiAnalyzer-VM is only recognised after you enable management of VM devices (`config system global` → `set fgfm-allow-vm enable`; off by default since 7.6.3). |

> **Real world:** After adding the FortiAnalyzer, remember that the FortiGates still need to *send* logs to it. Use the log settings in a system template so every FortiGate in the ADOM gets the same `config log fortianalyzer setting`.

## What changed in 7.6 that touches this topic

* From 7.6.3 the 7.6 ADOM can also add, import from and install to FortiOS 7.0 devices (it already handled 7.6, 7.4 and 7.2). The exact matrix changes between patches, so check the support table for your build (lesson 1.3).
* From 7.6.3, FortiManager no longer accepts **new VM devices** (FortiGate-VM, FortiAnalyzer-VM, FortiProxy-VM and others) until you run `set fgfm-allow-vm enable` under `config system global` (default disable). VMs already managed before an upgrade keep working.
* Configuration changes in Policy & Objects and the device level can be **previewed as JSON API or CLI** before install, which helps you learn the API.
* A new `set jsonapi-log {disable | request | response | all}` option under `config system global` writes API requests and responses to the event log (disabled by default).
* Starting in 7.6.5 (and 7.2.12 / 7.4.9), FortiManager needs its **own** valid FortiCare **Elite or Premium** support contract, registered in FortiCloud, to get object updates from FortiGuard; the 7.6.5 guide lists the same contract as a prerequisite for acting as a local FDS.

## Lab it yourself

The FortiManager-VM trial manages 3 devices/VDOMs, supports 2 ADOMs, and has **no FortiAnalyzer features and no built-in FDS**. That is enough to explore the architecture:

1. Log in, open the CLI console from the banner and run `get system status`. Note the version string (7.6 adds `.F` or `.M` for Feature or Mature builds), "Admin Domain Configuration" and "HA Mode".
2. Enable VM registration first (`config system global` → `set fgfm-allow-vm enable`; without it a new FortiGate-VM fails with "Unsupported device model"), add one FortiGate-VM (Domain 2), then open its device database in Device Manager and compare it with **Policy & Objects** for the ADOM.
3. Change a firewall address in Policy & Objects and watch the device's status change to **Modified** after you start the Install Wizard preview; cancel before installing to see that nothing reached the FortiGate.
4. Run `get system global` and find the `faz-status` and `adom-status` lines. The trial licence does not include FortiAnalyzer features, so treat enabling them as a paper exercise; on a full licence the change reboots the unit.

## Key takeaways

* FortiManager keeps a **device database** per device and an **ADOM database** per ADOM; installs copy ADOM data into the device database, then push only the diff.
* Device Manager uses **FGFM on TCP 541**; the GUI and JSON API use HTTPS; HA uses TCP 5199; local FDS uses TCP 8890/443 and UDP 53/8888.
* Service Access for FortiGuard is off on every interface until you enable it.
* **FortiAnalyzer features** (logs on FortiManager, `set faz-status enable`, reboot) and **managing a FortiAnalyzer** (logs on FortiAnalyzer) are different integrations.
* FortiAnalyzer features block FortiManager HA, and you cannot add a FortiAnalyzer in advanced ADOM mode.
* FortiManager 7.6 can preview changes as JSON or CLI and log API traffic with `jsonapi-log`.
