## ADOM upgrade

An ADOM's version cannot be edited, but it can be **upgraded** to the next version FortiManager supports (for example 7.4 → 7.6). The upgrade converts every object, policy package and template in the ADOM database to the new FortiOS syntax and changes the GUI to show the new version's features.

**Who and where.** Only a Super_User can upgrade. Go to **System Settings > ADOMs**, select the ADOM, then **More > Upgrade** (or right-click > Upgrade) and confirm. This is the *one-click ADOM upgrade*. If the ADOM is already at the highest version, the option is not offered.

**Recommended sequence:**

1. Run **More > ADOM Upgrade Readiness** on the ADOM. It checks devices in the ADOM for configuration that is missing or invalid in the new syntax and produces a report (export to CSV or PDF). It does not fix anything for you, so fix what it reports.
2. Confirm that the lowest FortiOS version in the ADOM is supported by the new ADOM version; upgrade any device that is not.
3. Immediately before the change, back up FortiManager (`execute backup all-settings ...`) or snapshot the VM so you can roll back.
4. Upgrade the ADOM.
5. Upgrade the FortiGates' firmware (from FortiManager or locally) and resynchronize them.

Several ADOMs **of the same version** can be upgraded together (select them, then More > Upgrade); you cannot upgrade a 7.2 and a 7.4 ADOM in the same operation. The same restriction applies to the readiness check.

> **Exam tip:** Upgrade order matters for the Global Database ADOM: upgrade **every local ADOM** that uses a global policy package **first**, then the Global Database. If one local ADOM cannot be upgraded, the Global Database cannot be either. This is one reason Fortinet suggests local policy blocks as an alternative to global packages.

Fortinet's documented procedure upgrades the ADOM and then the devices. Because ADOMs on FortiManager 7.6.5 can manage FortiOS 7.0 through 7.6, the two steps do not have to happen on the same night, and in practice devices sometimes run ahead of their ADOM for a while. Do not leave the mismatch permanently: you cannot use features whose syntax the ADOM does not know.

## Moving devices between ADOMs

### Registered device movement between ADOMs

A device already managed in one ADOM is moved by editing the **destination** ADOM:

1. **System Settings > ADOMs**, edit the target ADOM.
2. **Select Device**, pick the device (in Advanced mode you can pick individual VDOMs). The admin guide states that only devices with the same version as the ADOM can be added this way.
3. **OK**. The device is removed from the old ADOM and added to the new one.

What moves and what does not:

| Moves with the device | Stays behind in the old ADOM |
|---|---|
| The device database (its full configuration) | Policy packages and the ADOM object database |
| | VPN Manager settings, which are ADOM-specific (rebuild the VPN in the new ADOM) |

So after a move, the device has **no policy package** in the new ADOM. Run the **Import Configuration** (import policy) wizard in the new ADOM to build a package from the device's current configuration, or assign an existing package there. Fortinet does not recommend moving devices that use VPN Manager because the VPN settings belong to the ADOM.

### Upgraded device to a different ADOM

The common scenario: the 7.4 ADOM `Retail` contains a FortiGate that you have upgraded to FortiOS 7.6, and you want it managed with 7.6 features in ADOM `Retail-76`.

1. Upgrade the FortiGate's firmware; retrieve or refresh so the device database reflects 7.6.
2. Create (or use) a 7.6 ADOM.
3. Move the device into it (edit ADOM > Select Device).
4. Import the policy into the new ADOM and check object conflicts (the import wizard lets you keep FortiManager's definition or update it from the device).
5. Install, and confirm the package status is Synchronized.

If an import fails with a version message, the ADOM version and device firmware do not match the supported matrix: create an ADOM of the correct version and move the device there.

## FortiManager backups

A system backup (**all settings**) contains the FortiManager configuration and databases: device databases, ADOM databases, admin accounts and so on, plus the most recent ADOM revisions (how many is set by `adom-rev-max-backup-revisions` under `config system global`, default 5). It does **not** contain the downloaded FortiGuard databases (AV/IPS packages, web filter and antispam databases).

**GUI:** Dashboard > System Information > **System Configuration > Backup** (Backup Now, Schedule Backup, Backup History). An encryption password (up to 63 characters) protects the file; FortiManager uses AES-GCM.

**CLI, on demand:**

```text
FMG-HQ # execute backup all-settings sftp 10.0.1.60 /backups/FMG-HQ-2026-10-29.dat backupuser Str0ng! Encr7pt!
```

Syntax: `execute backup all-settings {ftp | scp | sftp} <ip:port> <path/filename> <username> <passwd> <ssh-cert> <crptpasswd>`. SCP uses an SSH certificate (`config system certificate ssh`) instead of a password. If the encryption password contains `\`, escape it or quote it with single quotes.

**CLI, scheduled:**

```text
FMG-HQ # config system backup all-settings
FMG-HQ (all-settings) # set status enable
FMG-HQ (all-settings) # set protocol sftp
FMG-HQ (all-settings) # set server 10.0.1.60
FMG-HQ (all-settings) # set user backupuser
FMG-HQ (all-settings) # set passwd Str0ng!
FMG-HQ (all-settings) # set directory /backups
FMG-HQ (all-settings) # set week_days monday thursday
FMG-HQ (all-settings) # set time 02:30:00
FMG-HQ (all-settings) # set crptpasswd Encr7pt!
FMG-HQ (all-settings) # end
```

Behaviour worth remembering:

* **One backup at a time.** A second backup started while one runs fails; the event log shows *Backup all settings fail (backup in progress)*. 7.6.2 also shows a GUI error saying another backup is in progress.
* Each backup writes an **MD5 checksum** and the filename to the event log so you can verify the file.
* Only successful backups appear in Backup History.
* Back up before every FortiManager firmware upgrade and every ADOM upgrade.

## Restoring the configuration

**GUI:** System Information > System Configuration > **Restore**. Options:

| Option | Meaning |
|---|---|
| Choose Backup File / Password | The file and its encryption password. |
| Overwrite current IP, routing and HA settings | Off: keep this unit's network and HA settings. On: take them from the file. |
| Restore in Offline Mode | Informational: the restore puts FortiManager in offline mode. |
| Migrate from a different platform | Use migration instead of a straight restore (below). |

**CLI:**

```text
FMG-HQ # execute restore all-settings sftp 10.0.1.60 /backups/FMG-HQ-2026-10-29.dat backupuser Str0ng! Encr7pt! keepbasic
```

`keepbasic` keeps the current IP and routing information. If the backup had no encryption password, pass `''`. The restore **disconnects all sessions and restarts** FortiManager, and the new settings replace the old ones, including admin accounts and passwords.

Before restoring an HA member, switch it to **Standalone**.

## Offline mode

Offline mode shuts down the protocol FortiManager uses to talk to managed devices (FGFM). While it is on, FortiManager **cannot communicate with FortiGates and cannot discover or add devices**.

```text
FMG-HQ # config system admin setting
FMG-HQ (setting) # set offline_mode enable
FMG-HQ (setting) # end
```

GUI: **System Settings > Advanced > Advanced Settings > Offline Mode**.

A restore **turns offline mode on automatically** as a safety measure: if the same devices are still managed by the original FortiManager, two managers must not both talk to them. When you are sure this FortiManager should take over, disable offline mode and the FGFM tunnels can come up.

Typical uses: restoring a backup on a lab or standby unit, building a replacement unit before cut-over, or examining a configuration without touching production.

> **Watch out:** "After restoring the backup to the new FortiManager, every device shows as down." Check offline mode before you start debugging FGFM.

## FortiManager configuration migration

**Restore** expects the same platform. **Migration** moves the configuration to a different FortiManager model or platform (for example hardware to VM, or one VM hypervisor to another).

1. Back up the source FortiManager.
2. On the target, if the source used ADOMs, **enable ADOMs first**.
3. GUI: Restore with **Migrate from a different platform**; or CLI:

```text
FMG-NEW # execute migrate all-settings sftp 10.0.1.60 /backups/FMG-HQ-2026-10-29.dat backupuser Str0ng! Encr7pt!
```

4. Re-enter the **system settings**, which are not migrated (copy them manually from the original unit, for example its network settings).
5. Re-establish the FGFM tunnels to the managed devices.
6. Export the FortiGuard packages and databases from the old unit and import them on the new one, since they are not in the backup.

## Lab it yourself

1. Back up the trial FortiManager to an SFTP server on Linux with an encryption password; check the MD5 in the event log against `md5sum` on Linux.
2. Start a second backup immediately and read the error.
3. Restore the backup with `keepbasic`; after the reboot confirm **Offline Mode** is enabled and your FortiGate-VM shows as down; disable offline mode and watch it reconnect.
4. In your two-ADOM lab, move the FortiGate from `root` to `Retail` and notice that it arrives without a policy package; import its policy.
5. Run **ADOM Upgrade Readiness** on a 7.4 ADOM if you have one. The trial allows only two ADOMs, so create `Retail` as a 7.4 ADOM for this exercise if you want to try it.

## Key takeaways

* ADOM upgrade: Super_User, System Settings > ADOMs > More > Upgrade; check readiness first; same-version ADOMs can be upgraded together; upgrade local ADOMs before the Global Database.
* Moving a device takes its device database; policy packages, objects and VPN communities stay; import policy in the new ADOM.
* `execute backup all-settings {ftp|scp|sftp} ...` with an encryption password; schedule with `config system backup all-settings`; one backup at a time; MD5 in the event log.
* FortiGuard databases are not in the backup.
* `execute restore all-settings ... [keepbasic]` replaces everything and reboots; HA units go Standalone first.
* A restore enables **offline mode** (`offline_mode` under `config system admin setting`), which stops all FGFM communication until you disable it.
* `execute migrate all-settings` moves a configuration to a different platform; system settings must be redone.
