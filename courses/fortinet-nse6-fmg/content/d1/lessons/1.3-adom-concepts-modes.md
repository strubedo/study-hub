## Understanding ADOMs

An administrative domain (ADOM) is a logical partition of FortiManager. Each ADOM has its own:

* set of managed devices (or VDOMs) in Device Manager,
* object database and policy packages in Policy & Objects,
* VPN Manager, AP Manager, FortiSwitch Manager and Extender Manager configuration,
* provisioning templates, scripts and revision history,
* version, which fixes the FortiOS syntax the ADOM uses.

Administrators are tied to one or more ADOMs (or "all except" some). When they log in they pick an ADOM and see only its devices. Super_User accounts such as `admin` see every ADOM.

ADOMs are **disabled by default** and only a Super_User can enable, create, edit or delete them. Enable them in the System Information widget (**Administrative Domain** toggle) or with:

```text
FMG-HQ # config system global
FMG-HQ (global) # set adom-status enable
FMG-HQ (global) # end
```

You are logged out and the login screen returns. To *disable* ADOMs later you must first move every device back to root and delete every non-root ADOM.

### Root and default ADOMs

* **root** is a FortiGate-type ADOM and always exists. With ADOMs disabled it is the only ADOM. **Unauthorized devices appear in root.**
* When ADOMs are enabled, FortiManager also creates **default device-type ADOMs** (for example FortiClient, FortiMail and FortiWeb). Non-FortiGate devices (other than FortiAnalyzer) are placed in their type's ADOM automatically and **cannot be moved**. A default ADOM becomes selectable only once it contains a device. Default ADOMs cannot be deleted.

### ADOM types

When you create an ADOM you pick a **type**, which decides what devices it accepts. The type cannot be changed later.

| Type | Accepts |
|---|---|
| FortiGate | FortiGate devices only |
| Fabric | FortiGate plus other Security Fabric devices |
| FortiCarrier | FortiCarrier only (FortiGate and FortiCarrier never share an ADOM) |
| FortiFirewall / FortiFirewallCarrier | Those devices only |
| FortiProxy | FortiProxy only (FortiProxy ADOMs cannot be upgraded or downgraded) |

## ADOM operation modes: Normal vs Backup

When creating an ADOM you choose its **Mode**.

| | Normal | Backup |
|---|---|---|
| Purpose | Manage and configure devices from FortiManager | Keep configuration backups; configure each device locally |
| Push config from FortiManager | Yes (installs, templates, policy packages) | **No** installs; you can still run **scripts** directly on devices and push existing **revisions** back |
| Policy packages | Yes | Import brings in **objects only, not policies** |
| How revisions arrive | Auto-update: the FortiGate checks its configuration every few seconds and sends a diff over FGFM after a change | Sent when a change is followed by **session timeout, logout or reboot**, or when the FortiGate admin makes a manual backup |
| Central VPN/AP/FortiSwitch management | Available | Not available |

In backup mode the FortiGate's GUI shows a **FortiManager Backup Objects** table where the local admin can import objects that exist on FortiManager (status *New*, *Conflicting*, *Local Only*). To let a FortiGate in a backup ADOM run configuration backups from its own CLI, FortiManager needs `config system global` → `set fcp-cfg-service enable`.

> **Exam tip:** "Operation mode" questions are about **Normal vs Backup ADOMs**. "Device mode" questions are about **Normal vs Advanced**. Read the stem carefully: they are two independent settings.

## ADOM device modes: Normal vs Advanced

The device mode is **global** (one setting for the whole FortiManager), found in **System Settings > Advanced > Misc Settings > ADOM Mode** or:

```text
FMG-HQ # config system global
FMG-HQ (global) # set adom-mode advanced
FMG-HQ (global) # end
```

| Normal (default) | Advanced |
|---|---|
| A FortiGate and all its VDOMs belong to **one** ADOM. | VDOMs of the same FortiGate can be assigned to **different** ADOMs. |
| Simple; recommended. | More complex; recommended only for experienced admins. |
| Individual devices can be locked in workspace mode. | Individual devices **cannot** be locked in workspace mode, and you cannot add a FortiAnalyzer. |

To return from Advanced to Normal, no FortiGate may have its VDOMs split across ADOMs. FortiManager also does not support splitting a device's VDOMs between ADOMs of different operation modes (normal and backup).

> **Real world:** An MSSP running one large FortiGate with a VDOM per customer is the classic case for Advanced mode: VDOM `cust-a` goes to ADOM `MSSP-CustomerA`, VDOM `cust-b` to `MSSP-CustomerB`, and each customer's admins see only their own VDOM.

## Supported ADOM versions

Each ADOM is created for a version and that version **cannot be edited**; you change it only with an ADOM upgrade. The version aligns the ADOM database with a FortiOS syntax: a 7.6 ADOM uses FortiOS 7.6 syntax and offers 7.6 features.

On FortiManager **7.6** you can create ADOMs of version **7.6, 7.4 and 7.2**. Which FortiOS versions each ADOM version can manage is published per build in the "FortiOS version support by ADOM version" table, and Fortinet warns that it changes between releases: a new ADOM version first supports only the matching FortiOS, and upgrade/downgrade support is usually added within one or two patches. As an example, the **7.6.5** table shows the 7.6, 7.4 and 7.2 ADOMs each able to add, import from and install to **FortiOS 7.6.x, 7.4.x, 7.2.x and 7.0.x** (the 7.6 ADOM gained 7.0 support in 7.6.3). Check the table and release notes for the build you run rather than memorising a matrix. FortiManager bridges the versions with an automatic upgrade/downgrade of CLI syntax:

* Installing to a **newer** FortiOS than the ADOM: syntax that is new in the newer release is not used; modified syntax is upgraded; deleted syntax is not installed.
* Installing to an **older** FortiOS: new syntax is discarded; modified syntax is reverted; deleted syntax is converted back using the older release's defaults.

It works on a best-effort basis. Fortinet's advice is to keep device firmware and ADOM version aligned and not to leave devices on different versions permanently, because you cannot use features (for example templates) that rely on syntax the ADOM does not know.

There are three versions to keep straight:

1. **FortiManager firmware** (7.6.x) decides which ADOM versions exist.
2. **ADOM version** (7.2/7.4/7.6) decides syntax and features.
3. **FortiOS version** on the device must be supported by the ADOM version.

> **Watch out:** Only devices running a version the ADOM supports can be assigned to it. If an import or add fails with a version error, check that the FortiGate's firmware is inside the ADOM's supported range.

## Organizing devices by ADOM

Fortinet suggests several ways to slice:

| Method | Example |
|---|---|
| Firmware version | All 7.4 FortiGates in one ADOM, 7.6 in another, upgrade ADOM by ADOM. |
| Geography | `EMEA`, `NA`, `APAC`. |
| Administrative responsibility | Separate teams each own an ADOM. |
| Customer | One ADOM per MSSP customer. |

Rules: a device can be in **only one ADOM** (in Normal device mode); ADOM names are unique; the maximum number of ADOMs depends on the model (VMs can add ADOM licences). With FortiAnalyzer features enabled, each ADOM also has its own log retention and disk quota.

## Use cases

### Retail

A retailer with 400 stores and a head office:

* ADOM `Retail` (FortiGate, 7.6, Normal) for all stores, one policy package `Branch-PP` installed to device groups by region.
* ADOM `HQ` for the head-office cluster and data-centre firewalls, with its own policy package.
* Workspace mode on, so a store change and an HQ change are not made by two people in the same ADOM at once.
* Store admins restricted to ADOM `Retail` and perhaps to a device group; HQ admins to `HQ`.
* Shared store standards (block lists, logging) could be global header/footer policies from the Global Database ADOM (Domain 4.3).

### MSSP

A managed security provider:

* One ADOM per customer: `MSSP-CustomerA`, `MSSP-CustomerB`. Customer policies and objects never mix.
* Customer administrators get accounts that see only their ADOM, possibly read-only or with a restricted profile.
* If customers live in VDOMs of a shared FortiGate, enable **Advanced** device mode.
* Provider-wide rules (management access, blocking threat feeds) go in the Global Database ADOM as header policies assigned to every customer ADOM.
* ADOMs on different versions let the MSSP upgrade one customer at a time.

## Lab it yourself

The FortiManager-VM trial allows **two ADOMs**.

1. `config system global` → `set adom-status enable`; log back in and note the ADOM selector.
2. **System Settings > ADOMs > Create New**: name `Retail`, type FortiGate, version 7.6, mode **Normal**. Switch the mode to **Backup** and back, and note which options change on the page.
3. Assign your FortiGate-VM to `Retail` (Edit ADOM > Select Device) and see it vanish from root.
4. `config system global` → `get` and confirm `adom-mode : normal`. Do not switch to Advanced on a lab you care about.
5. Try to disable ADOMs while `Retail` exists, and read the error.

## Key takeaways

* ADOMs are off by default; only Super_User can enable (`set adom-status enable`) and manage them.
* Unauthorized devices land in **root**; non-FortiGate devices go to fixed default ADOMs.
* ADOM **type** (FortiGate, Fabric, FortiCarrier, ...) and **version** cannot be edited after creation.
* Operation mode: **Normal** (manage) vs **Backup** (store revisions, no installs, scripts allowed, objects-only import).
* Device mode (global): **Normal** (one device, one ADOM) vs **Advanced** (split VDOMs across ADOMs).
* FortiManager 7.6 offers 7.2, 7.4 and 7.6 ADOMs; the FortiOS range each one manages is a per-build table (in 7.6.5: FortiOS 7.0 to 7.6 for all three) handled by best-effort syntax upgrade/downgrade.
