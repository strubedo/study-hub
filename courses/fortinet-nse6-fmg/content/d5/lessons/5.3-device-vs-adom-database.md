## Two layers of truth

FortiManager does not keep "the FortiGate configuration" in one place. It keeps two layers. Most device-level and ADOM-level issues come down to the two layers disagreeing.

| | **Device database** (device-level) | **ADOM database** (ADOM-level) |
|---|---|---|
| What it is | One complete FortiGate configuration file per managed device, as FortiManager believes it should be | Shared objects, policy packages, templates and profiles for every device in the ADOM |
| Where you edit it | Device Manager > device > Dashboard, Network, System, Router and so on. Also CLI scripts run on the device database | Policy & Objects, Provisioning Templates, script targets on the policy package or ADOM database |
| Typical content | Interfaces, zones, routing, system settings, admins, DNS, HA, VDOMs | Firewall policies, addresses, services, VIPs, IP pools, security profiles, users, normalized interfaces, dynamic mappings |
| Status shown as | **Config status**: Synchronized, Modified, Auto-update, Modified (recent auto-updated), Out of Sync, Conflict, Unknown | **Policy package status**: Imported, Synchronized, Modified, Out of Sync, Never Installed, Unknown |
| Who writes into it | Admin edits, **Retrieve**, **auto-update**, **Revert**, and the copy stage of an install | Admin edits, the **Import** wizard |

At install, ADOM objects are **copied into** the device database, then the diff goes to the FortiGate. The device database is therefore a superset: it contains everything the FortiGate has, including copies of the ADOM objects that device uses.

## How each operation moves data

| Operation | From → to | Touches the policy package? |
|---|---|---|
| **Install** (policy package + device settings) | ADOM DB → device DB → FortiGate | Yes, the package is the source |
| **Install device settings only** / Quick install (device DB) | device DB → FortiGate | No |
| **Retrieve** | FortiGate → device DB (new revision) | **No** |
| **Auto-update** (FortiGate change sent automatically) | FortiGate → device DB | Not its content. A policy-level change can flag the package status (see below) |
| **Import** policy | device DB → ADOM DB | **Yes**: creates or overwrites the package |
| **Revert** | stored revision → device DB | **No**. You must then import and reinstall to realign |

> **Exam tip:** Retrieve and Revert both change only the **device database**. If the change involves policies or ADOM objects, the package is now stale. The fix is **Import Policy** (device DB → ADOM DB) and then reinstall. Remember that sequence for "Retrieve vs Revert" questions.

### Retrieve vs revert

- **Retrieve** pulls the *current running configuration* from the FortiGate and saves it as a new revision in the device DB. Use it when the FortiGate is right and FortiManager is behind, for example after an emergency local change.
- **Revert** loads an *older stored revision* into the device DB. Nothing is sent to the FortiGate until you install. The revert does not update the policy package. Fortinet's documented follow-up is to **import the configuration** to resynchronize the package and then **re-install** the package.

## Why the layers drift apart

1. **A local change on the FortiGate.** With auto-update enabled (default `set auto-update enable` under `config system admin setting`), FortiManager receives the change and stores it in the device DB, with config status **Auto-update**. If the change was **device-level** (an interface IP, a route), the policy package status is unaffected. If it was **policy-level** (a policy, address, VIP, security profile, user, connector), the ADOM DB does not have it. The package status changes: the auto-update topic in the Administration Guide calls this a possible **Conflict**, and the policy package status table calls "policies or objects modified on the managed device" **Out of Sync**. Either way, the next install from the unchanged package **overwrites or deletes** the local change.
2. **Auto-update disabled.** The change is not accepted automatically. The admin must accept or refuse it, and until then the device shows **Out of Sync**. FortiManager detects the difference from the configuration checksum the FortiGate reports.
3. **A failed install.** Part of the diff was applied and the device DB and FortiGate disagree, so the config status becomes **Conflict**. (Conflict is also shown when both FortiManager and the FortiGate changed and the FortiGate change was not auto-synced.)
4. **A revert or retrieve** without the follow-up import.

## Comparing the device database with the ADOM database

In the GUI, the quickest comparison is **Install Preview**. It shows exactly what an install would change on the FortiGate, so local changes that would be overwritten appear as removals. **Revision History > Revision Diff** compares two device-DB revisions, for example "before the emergency change" against "after retrieve".

From the CLI, print the same object category from both layers:

```text
FMG-HQ # execute fmpolicy print-device-object <adom> <device> <vdom> <category> {<key> | list | all}
FMG-HQ # execute fmpolicy print-adom-object <adom> <category> {all | list}
```

The CLI reference names the arguments (ADOM, device, VDOM, category, and an optional output file, default `/tmp/pl`). The CLI's `?` help also lists numeric IDs, which the command accepts. The reference itself lists `3` as the ID of the `root` ADOM, and `diagnose dvm device list` shows the device OID. The example below uses IDs: ADOM `Retail` is 171, FGT-Branch1 is OID 193, VDOM root is 3, and category 145 is `user radius` (check the IDs on your own unit with `?`):

```text
FMG-HQ # execute fmpolicy print-device-object 171 193 3 145 all
config user radius
    edit "NPS-Backup"
        set server "10.20.0.12"
        set secret ********
    next
    edit "NPS-Primary"
        set server "10.20.0.11"
        set secret ********
    next
end

FMG-HQ # execute fmpolicy print-adom-object 171 145 all
config user radius
    edit "NPS-Primary"
        set server "10.20.0.11"
        set secret ********
        set _scope "FGT-Branch1"-"root"
    next
end
```

How to read it: the device DB has `NPS-Backup`, which someone created on the FortiGate and auto-update brought in. The ADOM DB does not have it. In the ADOM output, the `_scope` line shows which device and VDOM use the ADOM object. Device-DB output has no `_scope`, because it *is* that device. To bring `NPS-Backup` into the ADOM, **re-import** the policy package for FGT-Branch1, then install and compare again. Policies, addresses and groups, VIPs, services, IP pools, security profiles, connectors and users all follow this rule: a local change must be imported, or the next package install will fight it.

Related object-level tools in the same family are worth knowing by name. `execute fmpolicy copy-adom-object` copies an ADOM object into a device's DB. `link-adom-object` and `unlink-adom-object` manage the device-to-ADOM reference. `print-device-database <adom> <device> <output>` dumps a whole device DB to a file for diffing.

> **Real world:** The most common "FortiManager deleted my rule" story goes like this. Someone adds a policy on the FortiGate during an outage, auto-update stores it in the device DB, nobody imports, and the next routine package install removes it. Install Preview would have shown the deletion.

## Resolving the mismatch: pick a source of truth

| Situation | FortiGate is correct | FortiManager is correct |
|---|---|---|
| Device-level setting changed locally (interface, route) | Retrieve, or accept the auto-update. Nothing else needed | Install Device Settings (only) / Quick Install to push the DB value |
| Policy or ADOM object changed locally | Retrieve if needed → **Import policy** → install | Reinstall the policy package (it overwrites the local change) |
| Config status **Conflict** after a failed install | Retrieve Config from Revision History → re-import | Install Wizard → Install Device Settings (only), after fixing the cause |
| Reverted to an old revision | — | Import from the device → reinstall the package |

## Lab it yourself

1. In ADOM `Retail`, install `Branch-PP` to FGT-Branch1. On the FortiGate, add an address and a RADIUS server locally. Watch the config status change to Auto-update.
2. Run `execute fmpolicy print-device-object` and `print-adom-object` for the RADIUS category and compare them.
3. Open **Install Preview** for the package and note the deletions. Then run Import Policy, check the preview again, and install.

## Key takeaways

- The device DB holds a full per-device configuration. The ADOM DB holds shared objects and policy packages. Install copies ADOM to device, then sends the diff.
- Retrieve and Revert change only the device DB. Policy-level changes then need **Import** and then reinstall.
- Local device-level changes don't affect the policy package status. Local policy-level changes change it (Out of Sync / Conflict), and the next install overwrites them unless you import.
- Auto-update (default enabled) stores FortiGate changes in the device DB. With it disabled, the device shows **Out of Sync** until an admin accepts the change.
- Compare the layers with Install Preview, Revision Diff, or `execute fmpolicy print-device-object` vs `print-adom-object`. The `_scope` line shows which devices use an ADOM object.
- Choose the source of truth first, then retrieve and import, or reinstall.
