## Why deployment topology matters for troubleshooting

Almost every "the FortiGate shows as down in Device Manager" ticket starts with one question: **which side can open a TCP connection to the other?** FortiManager talks to its managed FortiGates over **FGFM** (FortiGate-to-FortiManager protocol), a TLS session on **TCP 541**. Once the session is up it carries everything: config retrieves and installs, scripts, firmware pushes, keepalives, even the FortiManager-side CLI and GUI proxy into the FortiGate. Inside the TLS session the two ends build a TUN-based tunnel, and FortiManager always sends management traffic through it. When the FortiGate is behind NAT, FortiManager allocates it a unique internal tunnel address and routes to it by serial number and address.

Either end can open the session:

| Who opens TCP 541 | Typical trigger | What it needs |
|---|---|---|
| FortiManager to FortiGate | **Add Device** wizard (discover mode), `execute fgfm reclaim-dev-tunnel` | FortiGate reachable on TCP 541, `fgfm` in the **FortiGate** interface `allowaccess` (GUI: *FMG-Access*), FortiGate admin credentials |
| FortiGate to FortiManager | `set fmg` under `config system central-management`, the central management connector under *Security Fabric > Fabric Connectors* in the FortiGate GUI, or Zero Touch / FortiCloud | FortiManager reachable on TCP 541. The device appears as **unauthorized** on FortiManager until an admin authorizes it, unless it was pre-registered as a model device |

After the session is up, the side that opened it does not matter much. All management traffic runs **inside** the established tunnel. What matters is **who can re-open it** after it drops.

> **Exam tip:** Questions on NAT always reduce to "who can initiate, and is the address it would use reachable?" Draw the NAT device, mark which side has a reachable address, and the answer usually falls out.

## Common deployment scenarios

1. **Same network or routed private network.** Both sides can reach each other. Either side can initiate. Nothing special to configure.
2. **FortiManager in a data center, FortiGates at branches over the internet.** This is the classic MSSP or enterprise case. One or both sides sit behind NAT, and the next three scenarios apply.
3. **FortiManager reached over a VPN.** Common for branches. FGFM runs inside the IPsec tunnel, so the FortiGate's **source address** matters. Set `fmg-source-ip` (or `interface-select-method specify` with `interface`) under `config system central-management` so the FortiGate sources FGFM from an address that FortiManager can route back to and that matches the VPN selectors.
4. **FortiManager HA or multiple FortiManager addresses.** The FortiGate can be given several FortiManager addresses. It tries them in order and uses only one at a time.

## Scenario A: FortiManager behind NAT, FortiGate public

FortiManager has a private address, for example `10.10.10.5`, published through a static 1:1 NAT or VIP as `203.0.113.5`. The FortiGate has a routable address.

- **FortiManager can initiate.** The Add Device wizard reaches the FortiGate's public address, and FGFM comes up.
- **The catch.** When FortiManager adds a device it normally writes its own IP into the FortiGate's `set fmg`. Behind NAT that would be the private `10.10.10.5`, which the FortiGate cannot reach. So FortiManager **does not set** `fmg` on the FortiGate at all in this case. The tunnel works, but if it drops, only FortiManager can bring it back, and the FortiGate never tries.
- **The fix.** Tell FortiManager its public identity. It then pushes that address to the FortiGate:

```text
FMG-HQ # config system admin setting
FMG-HQ (setting) # set mgmt-addr "203.0.113.5"
FMG-HQ (setting) # end
```

The FortiGate then ends up with:

```text
FGT-Branch1 # show system central-management
config system central-management
    set type fortimanager
    set fmg "203.0.113.5"
end
```

For more than one address (FortiManager HA, or two DNAT paths over two ISPs), use `mgmt-fqdn`, which takes several IPs or FQDNs. The FortiGate tries the first entry first. With FortiManager HA, the first entry is the primary and the second is the secondary. `mgmt-addr` documents a single IP or FQDN. The NAT device must also forward TCP 541 to FortiManager. Fortinet scopes this setting to a **static** public address (1:1 NAT). A dynamic public IP on the FortiManager side is not a supported design.

> **Watch out:** You can type `set fmg 203.0.113.5` on each FortiGate by hand instead, and Fortinet documents that as valid. It doesn't scale, though: every new device needs the same manual step, and a FortiGate that was added without it still has an empty `fmg`. Configuring `mgmt-addr` / `mgmt-fqdn` once on FortiManager makes it push the public address to every device it manages.

## Scenario B: FortiGate behind NAT, FortiManager public

The branch FortiGate has `192.168.1.99` behind an ISP router doing PAT. FortiManager is on `198.51.100.10`.

- **FortiManager cannot initiate.** Without a port forward for TCP 541 on the branch NAT device, Add Device to the FortiGate fails. The FortiGate's private address is not routable, and its public address belongs to the ISP router.
- **The FortiGate must initiate.** Configure `set fmg 198.51.100.10` on the FortiGate. It connects out, the session passes through the PAT, and the device appears under **unauthorized devices** on FortiManager. Authorize it into an ADOM.
- **NAT detection.** FortiManager compares the IP the FortiGate *declares* in its FGFM messages with the *source IP* it actually receives. A mismatch means NAT. FortiManager then allocates the device a unique internal tunnel address and routes its management traffic by serial number and address. Device Manager shows the NAT address as the device IP. Several branches behind the same PAT address all show the same IP and are still told apart by serial number.
- **Recovery.** If the tunnel drops, **only the FortiGate** re-establishes it. FortiManager treats a NATed FortiGate as unreachable for initiating. If that FortiGate loses its `fmg` setting, someone has to fix it locally.

```text
FMG-HQ # diagnose dvm device list
--- There are currently 2 devices/vdoms managed ---

TYPE            OID    SN               HA      IP              NAME          ADOM     (further columns trimmed)
fmgfaz-managed  193    FGVM02TM24000101 -       198.51.100.77   FGT-Branch1   Retail
               |- STATUS: dev-db: not modified; conf: in sync; cond: OK; dm: autoupdated; conn: up
               |- vdom:[3]root flags:0 adom:Retail pkg:[imported]Branch-PP
fmgfaz-managed  197    FGVM02TM24000102 -       198.51.100.77   FGT-Branch2   Retail
               |- STATUS: dev-db: not modified; conf: in sync; cond: OK; dm: autoupdated; conn: up
               |- vdom:[3]root flags:0 adom:Retail pkg:[imported]Branch-PP

```

Both branches above sit behind the same PAT address `198.51.100.77`. They are still separate devices with their own serial numbers and their own FGFM tunnels.

## Scenario C: both behind NAT

FortiManager and FortiGate are both on private networks, behind different NAT devices. Neither private address is reachable from the other side, so **one side must be published with a VIP / port forward on TCP 541**. In practice that is almost always the FortiManager side, which gives you one stable address for all branches:

1. On the data-center NAT device, forward TCP 541 from `203.0.113.5` to FortiManager `10.10.10.5`.
2. On FortiManager: `config system admin setting` → `set mgmt-addr "203.0.113.5"` (or `mgmt-fqdn`).
3. On each FortiGate: `set fmg "203.0.113.5"` (directly, or pushed by FortiManager once the first connection exists).
4. The FortiGate initiates, FortiManager detects that the FortiGate is NATed, and the FortiGate is responsible for re-establishing the tunnel.

Publishing the FortiGate instead is possible but rarely sensible. You would need a VIP per branch, and the FortiGate still could not reach a FortiManager whose private address it was given.

| Scenario | Who can initiate | Must configure | Who re-establishes after a drop |
|---|---|---|---|
| FortiManager behind NAT | FortiManager (Add Device). FortiGate too, once it has the public `fmg` | `mgmt-addr` / `mgmt-fqdn` on FortiManager + port forward 541 | FortiManager always. FortiGate only if `fmg` = public IP |
| FortiGate behind NAT | FortiGate only (unless a branch port forward exists) | `set fmg <FMG IP>` on FortiGate, then authorize | FortiGate |
| Both behind NAT | The side that targets a published VIP (normally FortiGate to FortiManager) | VIP / port forward on one side + `mgmt-addr` + `set fmg <public>` | FortiGate |

## FortiGate-side settings that break FGFM

```text
FGT-Branch1 # config system central-management
FGT-Branch1 (central-management) # set type fortimanager
FGT-Branch1 (central-management) # set fmg "203.0.113.5"
FGT-Branch1 (central-management) # set fmg-source-ip 10.1.1.1
FGT-Branch1 (central-management) # end
```

- `type` must be `fortimanager`. `fortiguard` means FortiGate Cloud.
- `fmg` is the address or FQDN the FortiGate connects to.
- `fmg-source-ip` (or `interface-select-method specify` + `interface`) fixes the source. Use it when FGFM must leave through a VPN or a specific interface, and keep it consistent with routing.
- `serial-number` can pin the expected FortiManager serial. A mismatch blocks the connection.
- On the **FortiGate**, `fgfm` in an interface's `allowaccess` (GUI *FMG-Access*) only matters when FortiManager initiates. FortiManager's own interfaces have **no** `fgfm` allowaccess option (the 7.6 list is `fabric`, `http`, `https`, `ping`, `snmp`, `soc-fabric`, `ssh`, `webservice`). On FortiManager, TCP 541 is filtered with `config system local-in-policy` (for example a `drop` entry for `dport 541`).
- **FortiGate-VM on FortiManager 7.6.3 and later.** FGFM connections from VM platforms are refused by default. Enable them with `config system global` → `set fgfm-allow-vm enable` (default `disable`). This matters for a lab built from FortiGate-VMs.

> **Real world:** With FortiManager behind NAT, check `mgmt-addr` first whenever FortiGates "randomly" go down after a FortiManager reboot or an ISP blip. A FortiGate with an empty `fmg` never calls home. It waits for FortiManager to reclaim it.

## Lab it yourself

You can build this with the FortiManager-VM trial and one FortiGate-VM permanent trial (the trial allows 3 devices and 2 ADOMs, so it is plenty). On FortiManager 7.6.3 or later, first run `config system global` → `set fgfm-allow-vm enable`, or the FortiGate-VM can't connect at all.

1. Put the FortiGate behind a Linux box or Cisco router that does PAT (`ip nat inside source list … overload`). Point the FortiGate at FortiManager with `set fmg`, and authorize it from the unauthorized devices list. Run `diagnose dvm device list` on FortiManager and note that the IP shown is the PAT address.
2. Try Add Device from FortiManager to the FortiGate's private address. It fails, because there is no route and no port forward.
3. Put FortiManager behind NAT with a static NAT for TCP 541. Add the FortiGate from FortiManager, then run `show system central-management` on the FortiGate. Do it without `mgmt-addr` first and then with it, and see when `fmg` gets populated.

## Key takeaways

- FGFM is TLS on TCP 541. Management traffic rides inside the established tunnel, whichever side opened it.
- FortiManager behind NAT does **not** set `fmg` on discovered FortiGates. Configure `mgmt-addr` (one address) or `mgmt-fqdn` (several) under `config system admin setting` so FortiManager pushes its public address.
- FortiGate behind NAT: only the FortiGate can initiate and re-establish. Configure `set fmg` and authorize the unauthorized device.
- FortiManager detects a NATed FortiGate by comparing the declared IP with the real source IP, then gives it a unique internal tunnel address and tracks it by serial number.
- Both behind NAT: publish one side (normally FortiManager) with a VIP / port forward on TCP 541.
- `fmg-source-ip` or interface selection controls the FortiGate's FGFM source, which is critical over VPNs.
- With several `mgmt-fqdn` entries, the FortiGate tries them in order and uses only one at a time.
