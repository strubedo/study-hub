## Why FortiManager databases get damaged

FortiManager keeps several databases on its local disk. The Device Manager database (DVM) holds devices, VDOMs, groups, ADOM membership and the task database. The configuration database (CDB) holds ADOM objects, policy packages, templates and dynamic mappings. The policy manager database (`pm2`) is a set of SQLite-style databases per ADOM, device, global, IPS, task and NCMDB. Damage comes from a small set of causes:

- **Power loss or a hard reset** in the middle of a write. This is the big one. Data can be half-committed.
- **An improper upgrade or downgrade path**, such as skipping a required step, downgrading without restoring a matching backup, or restoring a backup taken on a different version.
- **Disk-full conditions**. A full `/var` stops writes part-way.
- **Software defects** in a specific build. These get fixed by an upgrade or a TAC repair action.

## Best practices for database integrity

| Practice | Why |
|---|---|
| Always shut down with `execute shutdown` (or Dashboard > Unit Operation > Shutdown) before removing power. Reboot with `execute reboot` | A graceful stop flushes and closes the databases |
| Put hardware FortiManager on a **UPS**. Give FortiManager-VM storage that survives host failures | Prevents half-written databases |
| Schedule regular `execute backup all-settings …` to an external server, and take a backup **before every upgrade** and before any repair | The only recovery for some errors is restoring a known-good backup |
| Run the integrity checks **before upgrading** and after any unexpected shutdown | Errors carried into an upgrade get worse |
| Follow the documented upgrade path. Never "downgrade by flashing" without restoring that version's backup | A mismatched schema breaks the CDB |
| Keep disk usage under control (see 5.4) | A full disk corrupts writes |
| For FortiManager-VM, add at least one data disk before the first power-on and size it to the VM guide (7.6 minimum: 500 GB of storage). Never resize the OS disk. Grow the data volume with extra disks and `execute lvm extend` | The databases live on the LVM data volume, and a cramped volume fills up (see 5.4) |

> **Exam tip:** "What is the best way to protect FortiManager databases?" Graceful shutdown with `execute shutdown`, a UPS, and regular backups. Fortinet's own recovery advice after an unexpected power loss is to **restore a known-good backup** if the checks find damage.

## The integrity commands

Run these from the CLI with **only one administrator logged in**. Make sure **no ADOMs or objects are locked**, and if workspace mode is on, unlock all ADOMs first. Back up before answering **y** to any repair prompt.

### Policy manager database: `diagnose pm2 check-integrity`

```text
FMG-HQ # diagnose pm2 check-integrity all
...
Error: database disk image is malformed
pragma integrity_check fails: /var/pm2/adom153
>>> total: 10 failed: 1
```

You can check categories one at a time (`adom`, `device`, `global`, `ips`, `task`, `ncmdb`) or use `all`. A clean run prints `--- total: N ok.` for each category. **This command only detects. It cannot repair.** If it fails, Fortinet's documented answer is to restore from the last good backup. A `diagnose pm2 db-recover <db-category>` command exists for TAC-guided recovery of a corrupted category.

### Device Manager database: `diagnose dvm check-integrity`

```text
FMG-HQ # diagnose dvm check-integrity
[1/8] Checking object memberships       ... correct
[2/8] Checking device nodes             ... 0 change(s) will be made (263 error(s))
[3/8] Checking device vdoms             ... correct
[4/8] Checking duplicate device vdoms   ... correct
[5/8] Checking device ADOM memberships  ... correct
[6/8] Checking groups                   ... correct
[7/8] Checking group membership         ... correct
[8/8] Checking task database            ... correct
The above changes will be made to the database, however it is recommended to perform a backup first.
Do you want to continue? (y/n)
```

There are eight checks, from object memberships to the task database. When it finds problems it proposes changes and **asks before writing**. Back up, then answer `y`. For a damaged task database specifically, `diagnose dvm task repair` preserves what it can, and `diagnose dvm task reset` wipes all task history. Both reboot FortiManager.

### ADOM configuration: `diagnose cdb check adom-integrity`

```text
FMG-HQ # diagnose cdb check adom-integrity
General updating - adom MSSP-CustomerA     ... ..100%    Ready to update
General updating - adom Retail             ... ..100%    An error has occured: (errno=33):duplicate
```

`Ready to update` for every ADOM is the healthy result. The CLI reference describes the command as "check and repair", but the upgrade guide's advice for an error such as `errno=33` is to contact Fortinet Support, so treat it as a support case. You can name a single ADOM: `diagnose cdb check adom-integrity Retail`.

### Policy packages: `diagnose cdb check policy-packages`

```text
FMG-HQ # diagnose cdb check policy-packages Retail
Adom Retail
[1/4] Checking Scope                     ... correct
[2/4] Checking Dynamic mappings          ... 2 change(s) will be made
[3/4] Checking Policy package settings   ... correct
[4/4] Checking Undeleted objs            ... correct
The above change(s) will be made to the database, however it is recommended to perform a backup first.
Do you want to continue? (y/n)
```

There are four checks per ADOM: installation scope, dynamic mappings, package settings and undeleted objects. Like the DVM check, it can **repair after confirmation**.

### Pre-upgrade sweep: `diagnose cdb upgrade check`

`diagnose cdb upgrade check <action>` checks whether an upgrade-time repair is needed and runs it (object configuration integrity, reference integrity, invalid object sequences, duplicate UUIDs, missing VDOMs, invalid install targets and so on). Fortinet's upgrade guide uses `+all`, and a clean run prints `No error found.` after each check. `diagnose cdb upgrade summary` and `diagnose cdb upgrade log` show what happened during past upgrades, which is useful when a database problem started right after one.

| Command | Checks | Can it fix? |
|---|---|---|
| `diagnose pm2 check-integrity all` | Policy manager SQLite databases | **No**: detect only. Restore a backup |
| `diagnose dvm check-integrity` | Device Manager DB (8 checks) | Yes, after a y/n prompt |
| `diagnose cdb check adom-integrity [adom]` | ADOM configuration | Contact support on error |
| `diagnose cdb check policy-packages [adom]` | Scope, dynamic mappings, package settings, undeleted objects | Yes, after a y/n prompt |
| `diagnose cdb upgrade check +all` | Upgrade-time checks: object config and reference integrity, object sequence, duplicate UUIDs, missing VDOMs, invalid install targets | Checks and repairs where needed (several actions are fixes by name). `force-retry` re-runs an upgrade step from an earlier release, normally with TAC |

## Checking the file system after a power failure

The integrity commands look at the *databases*. Underneath them is an ext4 file system that can also be damaged by a power cut. FortiManager has a dedicated command:

```text
FMG-HQ # diagnose system fsck harddisk
```

It **checks and repairs the file system and then reboots** FortiManager, so plan a maintenance window. Expect a long boot on large disks. The companion `diagnose system fsck reset-mount-count` resets the disk's mount count on the next reboot. Signs that you need it: an unexpected power loss, kernel messages about ext4 errors in the logs, or a database check that fails right after an outage.

A sensible recovery order after an unexpected power loss:

1. Take a configuration backup if FortiManager is still usable.
2. Run `diagnose system fsck harddisk` and let it reboot.
3. Run the integrity checks: `pm2`, `dvm`, `cdb adom-integrity`, `cdb policy-packages`.
4. If `pm2` reports a malformed database, or CDB errors persist, restore the last known-good backup.

> **Watch out:** Don't confuse this with the **FortiGate**-side disk check. FortiOS shows "File System Check Recommended! Unsafe reboot may have caused inconsistency…" and asks for `execute disk scan`. FortiManager's firmware manager checks a FortiGate's disk before a firmware upgrade, controlled by `check-fgt-disk` under `config fmupdate fwm-setting`. That is about the managed FortiGate, not FortiManager's own disk.

## Lab it yourself

On the FortiManager-VM trial, with nothing locked and only you logged in:

1. `execute backup all-settings` to an SCP or FTP server in your lab.
2. Run all four integrity commands and save the clean output as your baseline.
3. Don't pull the virtual power cord on purpose. You only learn how long the next boot takes. If you want to see `diagnose system fsck harddisk`, run it in a quiet window and time the reboot.

## Key takeaways

- Power loss during writes is the main cause of database damage. Use `execute shutdown`, a UPS and scheduled backups.
- `diagnose pm2 check-integrity all` only **detects**. If it fails, restore a known-good backup.
- `diagnose dvm check-integrity` (8 checks) and `diagnose cdb check policy-packages` (4 checks per ADOM) can **repair after a y/n prompt**. Back up first.
- `diagnose cdb check adom-integrity` should show "Ready to update" for every ADOM. Errors go to Fortinet Support.
- Run checks with a single admin logged in and nothing locked. Unlock ADOMs in workspace mode.
- After a power failure, `diagnose system fsck harddisk` checks and repairs the file system and **reboots** FortiManager.
- Run the integrity checks before every FortiManager upgrade.
