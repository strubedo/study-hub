`get system performance` shows CPU per core (watch `%iowait` too, since high iowait means the disk is the bottleneck, not the CPU), memory, hard-disk use with I/O statistics, and flash. `get system status` adds the version, licence, HA mode and a disk-usage summary. Both are read-only and safe to run any time.

## High CPU and memory

FortiManager runs on Linux, and its CLI exposes the familiar tools:

| Command | Use |
|---|---|
| `execute top` | Live process view (procps `top`), sorted by CPU. Accepts top options, for example `execute top -b -n 1` for a single batch snapshot you can paste into a ticket. Press `M` to sort by memory, `q` to quit |
| `diagnose system process list` | List all processes with PID, user, VSZ (virtual memory), state and command |
| `diagnose system process kill -<signal> <pid>` | Send a signal to one process, for example `-9` or `-KILL` |
| `diagnose system process killall {Scriptmgr \| deploymgr \| fgfm}` | Kill all processes of one module. Those three are the only modules the 7.6 CLI reference lists |
| `diagnose system process fdlist <pid>` | List the file descriptors a process holds |
| `execute iotop` / `execute iotps` | Find processes doing heavy disk I/O |
| `diagnose dvm proc list` | DVM command process (`dvmcmd`) information |
| `diagnose debug crashlog read` | Crash and backtrace history. Repeated crashes of a daemon explain "random" restarts |

> **Watch out:** On FortiManager 7.6 the live process monitor is `execute top`. `diagnose sys top` is the **FortiGate** command and isn't in the FortiManager 7.6 CLI reference. On the exam, check which device the prompt belongs to.

```text
FMG-HQ # execute top -b -n 1
top - 10:23:11 up 41 days,  2:07,  0 users,  load average: 3.91, 3.62, 3.10
Tasks: 214 total,   3 running, 211 sleeping,   0 stopped,   0 zombie
%Cpu(s): 88.9 us,  4.3 sy,  0.0 ni,  6.8 id,  0.0 wa,  0.0 hi,  0.0 si,  0.0 st
MiB Mem :  15979.6 total,    412.7 free,   9630.3 used,   5936.6 buff/cache

  PID USER      PR  NI    VIRT    RES  %CPU  %MEM     TIME+ S COMMAND
 4127 root      20   0 2310.6m   1.9g 172.4  12.2 410:16.03 R securityconsole
 3388 root      20   0  412.0m 210.4m   8.1   1.3  51:02.77 S fgfmsd
 3412 root      20   0  301.9m 120.6m   2.0   0.8  12:44.10 S httpd
```

Reading it: one daemon is saturating two cores (`%CPU` above 100% means more than one core), and `wa` is 0, so this is CPU work, not disk wait. `securityconsole` does policy package work: preview, copy, install, policy consistency checks. The next step is to find out *what* it is doing. Look at the Task Monitor for a large install or an install to many devices, a scheduled install, or a huge policy package check. Only after that should you consider restarting it in a maintenance window. `securityconsole` is not one of the `killall` modules, so you would use `diagnose system process kill -9 <PID>` with the PID from `execute top` (4127 here).

Typical causes of high CPU or memory on FortiManager:

- Large concurrent installs or scripts. The limits are `concurrent-install-limit` and `concurrent-install-script-limit` under `config system dm`.
- Many devices with aggressive timers, such as a very short `fgfm_keepalive_itvl`.
- Data-heavy monitoring features (for example SD-WAN monitor history) on a FortiManager sized only for configuration management.
- Undersized FortiManager-VM resources versus the number of devices and ADOMs.
- A daemon stuck in a loop after a defect. The crash log and the release notes known issues point to it.

## High disk usage

```text
FMG-HQ # diagnose system print df
Filesystem           1K-blocks      Used Available Use% Mounted on
none                   1340996         0   1340996   0% /dev/shm
none                     65536       188     65348   0% /tmp
/dev/vda1               516040     97188    418852  19% /data
/dev/mdvg/mdlv        41280832  39333696   1947136  95% /var
/dev/mdvg/mdlv        41280832  39333696   1947136  95% /drive0
/dev/mdvg/mdlv        41280832  39333696   1947136  95% /Storage
/dev/loop0                9911      1121      8278  12% /var/dm/tcl-root
```

`diagnose system print df` is the FortiManager front end to `df`. The output above is the shape that matters. `/var`, `/drive0` and `/Storage` are the **same logical volume** (`/dev/mdvg/mdlv`), shown at three mount points, so 95% on one means 95% on all of them. That volume holds the databases, revisions, FortiGuard packages and firmware images. `/data` is a small separate partition. `/tmp` and `/dev/shm` are memory-backed. `diagnose system print df` accepts extra `df` arguments, so `diagnose system print df -i` checks **inodes**. A disk can be "full" with free space when inode use hits 100%.

Where FortiManager disk space goes, and what to do about it:

| Consumer | Control |
|---|---|
| FortiGuard packages and firmware images (Update Manager / local FDS) | `config fmupdate disk-quota` → `set value <MB>` (default 51200 MB). `diagnose fmupdate check-disk-quota {export-import \| fds \| fgd \| all}` checks the directory sizes and can clean the export/import directory. A VM disk barely larger than the quota fills up before the Update Manager quota is ever reached. Size the VM to the documented minimum (the 7.6 FortiManager-VM guide: 4 vCPU, 16 GB RAM, 500 GB of disk storage), or lower the quota |
| Configuration revisions per device | `max-revs` under `config system dm` (1–250, default 100). Delete old revisions you don't need |
| Task history | Task Monitor housekeeping. `diagnose dvm task reset` erases all task history (and reboots), a last resort |
| Script and install logs | `script-logsize` / `dpm-logsize` under `config system dm` |
| Logs, if FortiAnalyzer features are enabled | Log disk quotas. The VM trial has no FortiAnalyzer features |
| Crash and core files | `diagnose debug crashlog clear` |

`diagnose system disk usage <options>` reports usage by directory (`-h` for human-readable, `-d N` for depth, `-s` for a summary). It is the only `diagnose system disk` option available on FortiManager-VM. The SMART options (`health`, `errors`, `attributes`, `info`) apply to hardware models.

## FortiManager file system

FortiManager uses **ext4** (`get system status` shows `File System : Ext4`). On hardware models with several disks, the data volume sits on RAID (`diagnose system raid …`). On FortiManager-VM it sits on the logical volume built from the VM's data disk(s), and `execute lvm …` manages extending it after you add a virtual disk. If the file system itself is damaged after a power loss, `diagnose system fsck harddisk` checks and repairs it and reboots (see 5.2).

## Processes status

Healthy FGFM, installs and GUI need a small set of daemons. When one misbehaves:

1. Confirm it is running: `diagnose system process list` and look for the daemon (for example `fgfmsd`).
2. Check whether it is consuming resources: `execute top`.
3. Check whether it has crashed recently: `diagnose debug crashlog read`.
4. Restart it if needed: `diagnose system process killall fgfm` for the FGFM module (also `deploymgr` or `Scriptmgr`), or `diagnose system process kill -9 <pid>` for one process. The `fgfm` module serves every managed device, so expect device connections to flap while it restarts. Prefer a maintenance window.

`diagnose debug sysinfo` gathers a broad system snapshot in one command. It is useful to attach to a TAC case.

## Debug commands: the toolkit

```text
FMG-HQ # diagnose debug reset
FMG-HQ # diagnose debug application fgfmsd 255 FGT-Branch1
FMG-HQ # diagnose debug application depmanager 255
FMG-HQ # diagnose debug application securityconsole 255
FMG-HQ # diagnose debug timestamp enable
FMG-HQ # diagnose debug enable
   ... reproduce ...
FMG-HQ # diagnose debug disable
FMG-HQ # diagnose debug reset
```

| Target | Use it for |
|---|---|
| `fgfmsd <level> [device]` | Tunnel setup, certificates and serial checks, keepalives. Takes a device-name filter |
| `depmanager <level>` | Retrieve, reload and install communication with devices |
| `securityconsole <level>` | Policy package copy, preview and install |
| `diagnose debug service <svc> <level>` | Internal services, for example `cdb` (`diagnose debug service ?` lists them on your build) |
| `diagnose debug dpm comm-trace enable` / `conf-trace enable` | Deployment-manager to FortiGate communication and configuration traces. `diagnose debug dpm probe-device <ip>` checks a device's status |
| `diagnose dvm debug {enable \| disable} <channel>` | DVM debug channels (for example `dvm_db`, `dvm_dev`) |
| `diagnose debug info` | Show what debug is currently enabled |

The FortiGate side for the same problems: `diagnose debug application fgfmd -1`, `diagnose fdsm central-mgmt-status`, and `diagnose sys top` / `get system performance status` for FortiGate resources.

> **Exam tip:** Debug output prints in the CLI session where you enabled it. `diagnose debug info` shows which debug levels are active. Always `diagnose debug disable` and `diagnose debug reset` afterwards. A forgotten level-255 debug on a busy FortiManager is itself a CPU problem.

## Lab it yourself

On the FortiManager-VM trial: run `get system performance`, `diagnose system print df` and `diagnose system print df -i`, and note which mount points share a volume. Run `execute top -b -n 1` before and during an install to your FortiGate-VM, and watch which daemon spikes. Run `fnsysctl killall fgfmd` on the FortiGate with `diagnose debug application fgfmsd 255 <device>` enabled on FortiManager, and watch the tunnel come back.

## Key takeaways

- Start with `get system performance` (CPU per core and iowait, memory, disk I/O) and `get system status`.
- On FortiManager use `execute top` (for example `-b -n 1`) and `diagnose system process list` / `kill` / `killall` (`killall` modules: Scriptmgr, deploymgr, fgfm). `diagnose sys top` is FortiGate.
- `diagnose system print df` shows `/var`, `/drive0` and `/Storage` on one logical volume. Use `-i` for inodes.
- Disk hogs: FortiGuard packages and images (`config fmupdate disk-quota`, default 51200 MB), revisions (`max-revs`, default 100), tasks, logs, crash files.
- An undersized FortiManager-VM disk can stop FortiGuard cleanup and fill the disk.
- Debug with `diagnose debug application fgfmsd | depmanager | securityconsole`, then `diagnose debug enable`. Always disable and reset afterwards.
- `diagnose debug crashlog read` and `diagnose debug sysinfo` are the first things TAC asks for.
