## Two databases, two kinds of failure

Install errors make sense once you remember that FortiManager installs **in two stages**:

1. **Copy (ADOM DB to device DB).** FortiManager takes the policy package and the ADOM objects it uses, plus the assigned templates, and writes them into the **device database** of each target. The install task log shows this as *copy* steps. For a real (non-model) device the 7.6 Administration Guide gives a fixed order: system template, threat weight template, IPsec tunnel template, static route template, BGP template, NSX-T service template, SD-WAN template, AP profile, FortiSwitch template, FortiExtender template, then the **policy package**, and the **CLI template last**. (A *pre-run* CLI/Jinja template exists only for **model** devices. It is applied before any other provisioning template and then unassigned automatically.) Dynamic objects are resolved here: normalized interfaces, per-device mappings, metadata variables.
2. **Install (device DB to FortiGate).** FortiManager retrieves the FortiGate's current configuration, diffs it against the new device database, and pushes **only the difference** as CLI commands over FGFM. Then it verifies the result (`verify-install` under `config system dm`, default `enable`).

So there are two distinct failures:

| | **Copy failed** | **Install failed** |
|---|---|---|
| Where it breaks | Inside FortiManager, while it builds the device DB | On the FortiGate, while it applies the CLI diff |
| Has anything been sent to the FortiGate? | **No** | Yes, up to the failing command |
| Typical causes | Missing per-device mapping for a normalized interface or dynamic object. Object bound to an interface that doesn't exist on that device. Policy using an SD-WAN member instead of the SD-WAN zone. Duplicate names. ADOM version doesn't match the device | FortiGate rejects a command: object not valid in that field, syntax the FortiOS build doesn't accept, a referenced entry missing, a resource or table limit reached |
| Where to look | Install wizard / Task Monitor error text, **Install Preview** | Device **Revision History > View Install Log** (installation history) |
| Fix it on | FortiManager (mappings, objects, package) | Usually FortiManager (change what you push). Sometimes the FortiGate (a firmware mismatch, a local object) |

Examples of copy-stage messages (exact wording varies by build):

```text
Copy device global objects
error 42 - entry not exist
  dynamic interface "lan" mapping undefined for device FGT-Branch2
Copy failed
```

```text
error :131 - datasrc invalid. object: firewall policy 4.srcintf.
  "port1" cannot be used in system sdwan members interface
```

```text
version mismatched,adom:7.6; dev:7.4
```

The first message means the normalized interface `lan` has no per-device mapping for FGT-Branch2. Add the mapping (Policy & Objects > Object Configurations > Normalized Interface) or a default mapping, then reinstall. The second means the policy references an SD-WAN **member**. Use the SD-WAN zone instead. The third means the device's major version doesn't match the ADOM. Upgrade the ADOM, or keep the device on the ADOM's version.

> **Exam tip:** When an install fails at the copy stage, the FortiGate configuration is untouched. You don't need a rollback, and nothing on the FortiGate needs investigating. Fix the mapping or object on FortiManager and reinstall.

## Reading a failed installation log

The install log is the transcript of CLI commands FortiManager sent and what the FortiGate answered. Open it from the device database: **Dashboard > Configuration and Installation > Revision History > View Install Log**. The task in **System Settings > Task Monitor** also shows the per-device result.

```text
Starting log (Run on device)

Start installing
FGT-Branch1 $ config firewall policy
FGT-Branch1 (policy) $ edit 14
FGT-Branch1 (14) $ set name "Guest-Web"
FGT-Branch1 (14) $ set srcintf "port3"
FGT-Branch1 (14) $ set dstintf "port1"
FGT-Branch1 (14) $ set srcaddr "Guest-Net"
FGT-Branch1 (14) $ set dstaddr "Printer-MACs"
entry not found in datasource

value parse error before 'Printer-MACs'
Command fail. Return code -3
FGT-Branch1 (14) $ set action accept
...
```

How to read it:

- Each `$` line is a command FortiManager sent. Each indented answer is the FortiGate's reply.
- **`Command fail. Return code …`** marks the failing line. `entry not found in datasource` means the FortiGate has no object by that name that is valid **for that field**. FortiManager allowed the assignment, but FortiOS rejects it. A MAC-address group used as a destination address is a classic example.
- A *command parse error* (with its own negative return code) often means FortiManager sent syntax that this FortiOS build does not accept. That suggests an ADOM or FortiOS mismatch, or a known issue between FortiManager and FortiOS builds. Check the FortiManager release notes for supported FortiOS versions.
- After the install, the device's config status becomes **Conflict** (install failed), and the policy package status no longer shows synchronized.

### Resolution pattern

1. Find the first failing command in the install log, not the last line.
2. Decide which side is wrong. In most cases you **change what FortiManager pushes**: fix the object, mapping or policy in the package. For an unsupported command caused by a version mismatch, correct the ADOM version or the FortiOS version, or wait for a fixed build.
3. Re-run **Install Preview** to confirm the diff no longer contains the bad command.
4. Reinstall. If the device is now in Conflict because someone also edited the FortiGate locally, choose a direction. **Retrieve** from the device and then re-import the policy package, if the FortiGate's configuration is the truth. Or run **Install Device Settings (only)** / reinstall from FortiManager, if FortiManager's database is the truth.

> **Watch out:** A partially successful install leaves a FortiGate running some of the new commands. FortiManager's recovery logic (unset and roll back, or reboot when `rollback-allow-reboot` is enabled) only runs when the install **breaks the FGFM tunnel**. It does not undo every command after an ordinary command error. See topic 5.4.

Useful debugs while reproducing an install problem:

```text
FMG-HQ # diagnose debug application securityconsole 255
FMG-HQ # diagnose debug application depmanager 255
FMG-HQ # diagnose debug enable
```

`securityconsole` shows the copy and preview stage. `depmanager` shows the device communication.

## Import issues: understanding a failed import

The **Import Configuration** (import policy) wizard goes the other way: device DB to ADOM DB. It creates or overwrites a policy package from the FortiGate's policies and pulls the objects those policies use into the ADOM's shared object database. It **does not change the FortiGate**.

The wizard stops or produces a bad result for these reasons:

- **Interface mapping.** Each enabled FortiGate interface needs a mapping to a normalized interface (per-device or per-platform). Fortinet warns that a default or per-device mapping must exist or the later installation fails. An existing normalized interface already mapped differently for this device creates a mapping conflict.
- **Object selection.** The wizard offers *Import only policy dependent objects* or *Import all objects*. With the first choice, objects that no imported policy references never reach the ADOM database.
- **Object conflicts.** An object with the same type and name already exists in the ADOM with a **different value**. You must choose **FortiGate** or **FortiManager** for each conflict. You can view the conflicts and download a conflict file. Duplicates (same name, same value) are not imported twice.
- **Objects FortiManager can't represent.** Values unknown to the ADOM version, or leftovers that also break a reload. Import works from the device DB, so if the device DB is stale or the reload failed, import is working from the wrong data. Retrieve first.
- **Locks and workspace.** In workspace mode the ADOM or package must be locked by you.

### Impact of each conflict choice

| Choice | Effect |
|---|---|
| Use **FortiManager** value | ADOM object stays as it is. Devices already using it stay synchronized. On the next install to *this* FortiGate, FortiManager's value is pushed and overwrites the FortiGate's local value |
| Use **FortiGate** value | The ADOM object is updated. Every other FortiGate that references it becomes modified and needs an install. This is the same as editing the shared object by hand |

A failed or abandoned import leaves the FortiGate untouched and the ADOM unchanged, or the package only partly built. The policy package status shows the result. After a successful import it reads **Imported**. The import also removes policies with FortiManager-generated policy IDs (Fortinet's example is `1073741825`) that were previously learned from the device. Those IDs come from global header or footer policies, policy blocks or the VPN console. If you imported only policy-dependent objects, the first install after the import can **delete the unreferenced objects** on the FortiGate, so check Install Preview first.

### Resolution checklist

1. Make sure the device DB is current: Retrieve, and check that the retrieve did not hit a reload failure.
2. Fix interface mappings, or let the wizard *add mappings for all unused device interfaces*.
3. Resolve each object conflict deliberately. Download the conflict file for a change record.
4. Re-run the import. Then use **Install Preview** before the first install to see what FortiManager would change, especially deletions of unused objects.

## Lab it yourself

1. In ADOM `Retail`, create a normalized interface `lan` with a per-device mapping for one FortiGate only. Assign the package to a second FortiGate and install. Read the copy error, add the mapping, and reinstall.
2. Create an address `Printer-MACs` of type MAC and use it as a destination in a policy. Install and read the install log. (Depending on the FortiOS build it may be accepted in some fields and rejected in others. The point is to read the log.)
3. Change an address locally on the FortiGate, then run the import wizard and pick each conflict option in turn on a lab ADOM. Watch which devices become modified.

## Key takeaways

- An install is copy (ADOM to device DB) and then install (diff from device DB to FortiGate).
- **Copy failed** means nothing reached the FortiGate. Fix mappings, objects or the ADOM version on FortiManager.
- **Install failed** means the FortiGate rejected a command. Read **View Install Log** and find the first `Command fail. Return code`.
- `entry not found in datasource` means the FortiGate has no valid object of that name for that field. A *parse error* usually means a syntax or version mismatch.
- Import changes FortiManager only. On a conflict, choosing **FortiGate** updates the shared object and makes other devices modified. Choosing **FortiManager** keeps them synchronized.
- After an import, use Install Preview before the first install. FortiManager may delete unused objects.
- A failed install leaves the device in **Conflict**. Resolve by retrieving and re-importing, or by reinstalling from FortiManager.
