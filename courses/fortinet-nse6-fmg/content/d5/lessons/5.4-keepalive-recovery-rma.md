## Purpose of keepalive messages

An FGFM session can sit idle for hours between installs, and both ends need to know the other is still there. Firewalls and NAT devices along the path also drop idle TCP state. Keepalives solve both problems, and they carry status as well:

- **Liveness.** If keepalives stop, FortiManager marks the device's connection **down**. Device Manager shows it as offline, and `diagnose dvm device list` shows `conn: down`.
- **Keeping the path warm.** Regular traffic keeps NAT and firewall session entries open, which matters a lot for FortiGates behind PAT.
- **Status reporting.** Per Fortinet's FGFM protocol guide, each keepalive carries the FortiGate's current OS version, platform, **configuration checksum**, and AV and IPS database versions. The checksum is how FortiManager notices that the FortiGate configuration changed outside an install. It feeds the Out of Sync and Auto-update logic. FortiManager uses the versions to decide whether the FortiGate needs updates.

## FGFM keepalive timers

The timers live on **FortiManager** under `config system dm`, even though it is the **FortiGate** that sends the keepalives. FortiManager only receives them.

```text
FMG-HQ # config system dm
FMG-HQ (dm) # set fgfm_keepalive_itvl 120
FMG-HQ (dm) # set fgfm-sock-timeout 360
FMG-HQ (dm) # end
```

| Setting | Meaning | Range | Default (7.6) |
|---|---|---|---|
| `fgfm_keepalive_itvl` | FGFM keepalive interval, in seconds | 30–600 | **120** |
| `fgfm-sock-timeout` | Maximum idle time on the FGFM socket before it is considered dead, in seconds | 90–1800 | **360** |

Note the spelling. The keepalive setting uses **underscores** (`fgfm_keepalive_itvl`) and the socket timeout uses **hyphens** (`fgfm-sock-timeout`). With the defaults, the protocol guide describes the FortiGate sending a keepalive every 120 seconds. If FortiManager misses three consecutive keepalives (360 seconds, which matches the default socket timeout), it treats the device as offline. When the device comes back, the TLS session must be re-established before management can continue, and the side that can initiate (see the NAT scenarios in 5.1) does it.

Shorter intervals detect failures faster but cost FortiManager CPU when it manages thousands of devices. Longer intervals can let a NAT device age out the session.

> **Watch out:** A FortiGate showing "down" while it can obviously reach FortiManager is often a NAT or stateful-firewall timeout shorter than the keepalive interval, or asymmetric routing that drops the return path. Compare the path's idle timeout with `fgfm_keepalive_itvl`.

## Recovery logic: what happens when an install breaks management

A bad install can cut the management path: a wrong interface IP, a deleted route, a policy that blocks TCP 541, a changed `fmg-source-ip`. FGFM has a built-in safety net:

1. For each install, FortiManager sends the **set** commands that apply the change **and** the **unset** commands that would undo it.
2. The FortiGate applies the set commands **in memory only**. Nothing is written to its configuration file yet. Then it tests the FGFM connection to FortiManager.
3. If the connection does not come back, the FortiGate applies the **unset** commands, rolling the change back, and tests the connection again.
4. If it is **still** down, and only if `rollback-allow-reboot` is **enabled** on FortiManager, the FortiGate **reboots** to load its previous configuration from the saved config file, then tries to reconnect.

```text
FMG-HQ # config system dm
FMG-HQ (dm) # set rollback-allow-reboot enable
FMG-HQ (dm) # end
```

`rollback-allow-reboot` is **disabled by default**, because most organizations don't want a firewall rebooting on its own in production. With it disabled, recovery stops at the unset step. If the unset doesn't restore connectivity, someone has to fix the FortiGate locally, by console or out-of-band access, or use another path for `execute fgfm reclaim-dev-tunnel`.

Related install timers under `config system dm` are useful for exam recognition. `install-tunnel-retry-itvl` is the time to re-establish the tunnel during an install (10–60 s, default 60). `retry`, `nr-retry` and `retry-intvl` control automatic install retries.

> **Exam tip:** The sequence is apply in memory → test → **unset** → test → **reboot only if `rollback-allow-reboot` is enabled**. The reboot recovers the *previous saved configuration*. Questions often try to make you believe FortiManager reboots the FortiGate by default, or that FortiManager reinstalls the old revision.

## Replacing a managed FortiGate (RMA)

FortiManager verifies the **serial number** on every management connection. A replacement unit has a new serial number, so as far as FortiManager is concerned it is a stranger, even with the same hostname and IP. The supported approach is to keep the existing device entry, with its revision history, device database, package assignment and mappings, and **change the serial number** on it. The replacement must be the **same model**. A different model is added as a new device.

**GUI (7.2 and later, including 7.6):** Device Manager > Device & Groups > Managed FortiGate, select the device, **More > Swap Device**. Enter the new serial number and the admin name and password for the new unit. For an HA cluster, all members are listed. On the new FortiGate, set the FortiManager IP under Central Management. FortiManager then pushes the configuration to the new device.

**CLI:**

```text
FMG-HQ # diagnose dvm device list
...  193  FGVM02TM24000101 ... FGT-Branch1 ...
FMG-HQ # execute device replace sn FGT-Branch1 FGVM02TM24000199
```

The serial number is **case-sensitive**. Fortinet serials use capital letters. The same command fixes a model device that was added with a mistyped serial.

A typical sequence for a standalone unit:

1. Download the latest good revision of the old unit from Revision History, if you will restore it locally.
2. Prepare the new unit on the **same FortiOS version**, with basic reachability. If you restore the old config on it, remove `fmg` and `serial-number` from `central-management` first. That keeps the unit from calling in early and appearing as **unauthorized** before FortiManager knows its serial.
3. On FortiManager: **Swap Device** or `execute device replace sn <device> <new SN>`.
4. Point the new FortiGate at FortiManager (`set fmg`, optionally `set serial-number <FMG SN>`). If FortiManager must initiate, run `execute fgfm reclaim-dev-tunnel <device> force <admin> <password>`.
5. Confirm with `diagnose dvm device list` (new serial, `conn: up`), then install so the device DB is pushed to the new unit.

**HA cluster member:** you normally don't need to replace the serial. The cluster reports the new member to FortiManager. If the new member appears under unauthorized devices, delete it there so FortiManager can discover it as a cluster member. When a cluster member's licence is replaced, FortiManager may list the old member too. Delete the downed old member from the HA widget once the new one shows.

> **Real world:** If logs are kept on FortiAnalyzer, the new serial number means a new log device. Plan for log continuity separately from the FortiManager swap.

## Lab it yourself

You have one FortiGate-VM permanent trial per FortiCloud account. If you have two accounts, you can simulate an RMA: manage FortiGate A, shut it down, bring up FortiGate B with the same addressing, and run `execute device replace sn` with B's serial. Then test recovery logic. Push a change from a device-DB script that changes the FortiGate's FGFM-facing route, and watch the FortiGate roll it back. Keep console access ready, because this lab deliberately breaks management.

## Key takeaways

- Keepalives detect failures, keep NAT and firewall sessions alive, and carry the config checksum and versions, which is how FortiManager spots local changes.
- `config system dm`: `fgfm_keepalive_itvl` (30–600, default 120) and `fgfm-sock-timeout` (90–1800, default 360). Watch the underscore vs hyphen.
- Three missed keepalives (360 s with defaults) and the device is treated as offline.
- Recovery logic: apply in memory → test → unset → test → reboot to the saved config **only if** `rollback-allow-reboot` is enabled (default disabled).
- RMA: same model only. **Swap Device** in the GUI, or `execute device replace sn <device> <SN>` (case-sensitive). Then point the new unit at FortiManager and install.
- HA cluster members normally don't need a serial replacement. The cluster announces the new member.
