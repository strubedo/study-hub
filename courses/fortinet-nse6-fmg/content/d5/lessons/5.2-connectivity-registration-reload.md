## The processes behind the problems

To read debug output, you need to know which daemon owns which job.

| Side | Process / debug target | Job |
|---|---|---|
| FortiGate | `fgfmd` | FGFM client. Opens the TLS session to `fmg`, answers FortiManager requests, sends keepalives |
| FortiManager | `fgfmsd` | FGFM server. Accepts and opens sessions, authenticates certificates and serial numbers, keeps the tunnel table |
| FortiManager | `depmanager` (deployment manager) | Pushes configuration and retrieves and reloads it from devices |
| FortiManager | `securityconsole` | Policy package work: install preview, copy to device DB, install |
| FortiManager | `dvm` (`diagnose dvm …`) | Device Manager database: devices, VDOMs, ADOM membership, tasks |

FortiManager debugs use `diagnose debug application <name> <level>` and then `diagnose debug enable`. `fgfmsd` also accepts a device-name filter. Always finish with `diagnose debug disable` and `diagnose debug reset`.

```text
FMG-HQ # diagnose debug reset
FMG-HQ # diagnose debug application fgfmsd 255 FGT-Branch1
FMG-HQ # diagnose debug timestamp enable
FMG-HQ # diagnose debug enable
```

On the FortiGate:

```text
FGT-Branch1 # diagnose debug reset
FGT-Branch1 # diagnose debug application fgfmd -1
FGT-Branch1 # diagnose debug console timestamp enable
FGT-Branch1 # diagnose debug enable
```

To force a fresh handshake while you watch, restart the client with `fnsysctl killall fgfmd` on the FortiGate, or reclaim the tunnel from FortiManager with `execute fgfm reclaim-dev-tunnel <device_name>`.

## Connectivity first: a layered checklist

Work bottom-up. It is the same discipline as a Cisco `ping` → `traceroute` → `telnet <ip> <port>` walk.

1. **Routing and reachability.** On the FortiGate: `get router info routing-table details <FMG IP>`, `execute ping <FMG IP>`, `execute traceroute <FMG IP>`. Check the route to FortiManager, and check that the return path exists for the address the FortiGate sources from. That address comes from `fmg-source-ip` or the egress interface.
2. **TCP 541.** `execute telnet <FMG IP> 541` from the FortiGate shows whether anything answers on the port. On FortiManager, check `show system local-in-policy` for entries that drop or reject `dport 541`, or that accept it only from certain sources. FortiManager interfaces have no `fgfm` allowaccess option, so local-in policies (and anything in the path) are what block 541 there. In the other direction, FortiManager-initiated connections need `fgfm` in the FortiGate interface's `allowaccess`.
3. **Packets.** Sniff on both ends:

```text
FMG-HQ # diagnose sniffer packet any "port 541 and host 198.51.100.77" 3 0 a
```

If you see repeated SYNs arriving and nothing leaving, FortiManager is not answering. Suspect a local-in policy on FortiManager. If SYNs leave the FortiGate but never arrive, look at the path: an ISP filter, a missing NAT port forward, or a wrong `fmg`.

4. **TLS.** If the TCP handshake completes but TLS stalls, look at MTU or MSS along the path (test with `execute ping-options df-bit yes` and a large `data-size`) and at TLS version mismatches. FortiManager's minimum is `fgfm-ssl-protocol` under `config system global`, default `tlsv1.2`.
5. **Authentication and certificates.** FGFM verifies the peer certificate and the serial number. A FortiGate whose certificate CN does not match its serial number, or a missing CA certificate after you deploy custom FGFM certificates, shows up clearly in the `fgfmsd` debug.

## Diagnosing registration issues

Registration is the step where an unknown FortiGate becomes a managed device. These are the common failure patterns:

| Symptom | Likely cause | What to check / do |
|---|---|---|
| FortiGate configured with `set fmg`, never appears as unauthorized | TCP 541 blocked, wrong `fmg`, FortiManager set to deny unknown devices, or a FortiGate-VM on FortiManager 7.6.3+ | Sniffer. `fgfm-deny-unknown` under `config system global` on FortiManager (default `disable`. `enable` refuses unknown serial numbers). For VMs, `fgfm-allow-vm` under `config system global` (default `disable` from 7.6.3, so VM platforms are refused until you enable it) |
| Appears, but authorization fails | Wrong FortiGate admin credentials, ADOM version doesn't match the FortiOS version, or the device limit is reached (FMG-VM trial = 3 devices/VDOMs) | Task Monitor details. ADOM version. Licence |
| Add Device from FortiManager fails with a probe or connect error | FortiManager cannot reach the FortiGate (FortiGate behind NAT, or `fgfm` missing from the FortiGate interface `allowaccess`) | Use FortiGate-initiated registration instead, or fix the FortiGate's FMG-Access |
| `diagnose dvm device list` shows `conn: down` after it worked before | Tunnel dropped and the side that should re-open it can't (see the NAT scenarios) | Fix `fmg` / `mgmt-addr`. `execute fgfm reclaim-dev-tunnel` if FortiManager can reach the FortiGate |
| "A device with serial number … already exists" | Stale entry for the same serial in another ADOM, or an old model device | `diagnose dvm device list` to find it. Delete the stale entry |

The FortiGate end can also register itself when it knows the FortiManager serial number. Use `execute central-mgmt register-device <fmg-serial-no> …` (check `?` for the remaining arguments on your FortiOS build), and check the result with `diagnose fdsm central-mgmt-status`.

```text
FMG-HQ # diagnose dvm device list
--- There are currently 2 devices/vdoms managed ---
--- There are currently 2 devices/vdoms count for license ---

TYPE            OID    SN               HA      IP              NAME          ADOM     (IPS and further columns trimmed)
fmgfaz-managed  193    FGVM02TM24000101 -       198.51.100.77   FGT-Branch1   Retail
               |- STATUS: dev-db: modified; conf: in sync; cond: pending; dm: retrieved; conn: up
               |- vdom:[3]root flags:0 adom:Retail pkg:[modified]Branch-PP
fmgfaz-managed  197    FGVM02TM24000102 -       198.51.100.77   FGT-Branch2   Retail
               |- STATUS: dev-db: not modified; conf: in sync; cond: OK; dm: autoupdated; conn: down
               |- vdom:[3]root flags:0 adom:Retail pkg:[imported]Branch-PP
--- End device list ---
```

How to read it:

- `conn:` shows whether the FGFM tunnel is up right now.
- `dev-db:` shows whether the device database has changes not yet installed (`modified` / `not modified`). Fortinet's upgrade guide tells you to install pending changes when it reads `modified`.
- `conf:` compares the latest revision with the device.
- `cond:` `OK` means synchronized. `pending` means changes are waiting to install.
- `dm:` is the last deployment-manager action, for example `retrieved` or `autoupdated`.
- The `vdom` line shows the ADOM and the policy package status, for example `modified`, `imported` or `never-installed`.

> **Watch out:** The real output has more columns, starting with the IPS version. They are trimmed in these exhibits. The fields that matter for troubleshooting are on the `STATUS` and `vdom` lines. `conn: up` with `cond: pending` is a normal "changes not installed yet" state, not a fault.

## Failed reload

Whenever FortiManager **retrieves** a FortiGate configuration (first add, Retrieve Config, auto-retrieve), it has two jobs. First it **fetches** the file over FGFM. Then it **reloads** (parses) it into the device database. These are separate steps that fail for different reasons:

- **Fetch fails.** This is a connectivity or FGFM problem. The task usually times out, or shows the device unreachable.
- **Reload fails.** The file arrived, but FortiManager's parser rejected something in it. Typical causes are duplicate entries in a table, a value FortiManager's schema doesn't know (for example a FortiGuard category or a newer syntax the ADOM version doesn't support), or leftovers from an improper downgrade. The device database is not updated. Device Manager keeps the previous revision, or none for a brand-new device.

To find the exact failing line, look up the device OID and run the reload by hand. Log your SSH session, because the output can be long.

```text
FMG-HQ # diagnose dvm device list
...  193  FGVM02TM24000101 ... FGT-Branch1 ...
FMG-HQ # diagnose test deploymanager reloadconf 193
Retrieving configuration file from FGT...
Configuration file import succeeded.
Reloading configuration file...
Error: Configuration reload error.
---------------------------------
Failure info:
    edit 3
>       set url "files.example.com"   [duplicate]
cdb_parse_file: runtime error 33: duplicate
```

Here the fetch worked ("import succeeded"), but reload stopped on a duplicate URL-filter entry. **Fix it on the FortiGate**, by removing the duplicate there, and then retrieve again. Changing FortiManager does not help, because the bad data lives in the FortiGate configuration. Repeat until the reload is clean. Other tools: `diagnose test deploymanager getcheckin <devid>` shows the configuration check-in information. `diagnose debug application depmanager 255` traces the retrieve and reload from the FortiManager side.

> **Exam tip:** "Configuration file import succeeded" followed by a reload error means connectivity is fine. The problem is the **content** of the FortiGate configuration. Don't troubleshoot TCP 541 at that point.

## Reading an fgfmd failure

```text
FGT-Branch1 # diagnose debug application fgfmd -1
FGT-Branch1 # diagnose debug enable
FGFMs: Create session 0x7f3a2c10.
FGFMs: setting session 0x7f3a2c10 exclusive=0
FGFMs: connect error: Network is unreachable
```

`Network is unreachable` comes from the socket layer. The FortiGate has no route to the `fmg` address in the routing context it is using. A common cause is a dedicated management VDOM or interface (`set vdom` / `set interface` in `central-management`) that has no route to FortiManager. Compare that with a TLS-stage stall: client hello sent, nothing back for minutes, then a generic error. That points at the path (MTU, inspection, asymmetric NAT) rather than at routing.

## Lab it yourself

1. On FortiManager, add a `config system local-in-policy` entry with `set action drop`, `set protocol tcp`, `set dport 541` and `set src <FortiGate IP>/32`. Restart `fgfmd` on the FortiGate (`fnsysctl killall fgfmd`) and watch the sniffer: you see SYNs with no answer. Delete the entry afterwards. (On FortiManager 7.6.3+, `fgfm-allow-vm` must already be enabled for a FortiGate-VM.)
2. Break the route to FortiManager on the FortiGate (the permanent trial allows 3 static routes) and read the `fgfmd` debug.
3. Enable `fgfm-deny-unknown` on FortiManager, delete the FortiGate, re-point it, and confirm it no longer shows as unauthorized. Set it back to `disable`.

## Key takeaways

- `fgfmd` (FortiGate) and `fgfmsd` (FortiManager) own FGFM. `depmanager` and `securityconsole` own retrieves and installs.
- Troubleshoot in layers: route → TCP 541 (`execute telnet`, sniffer, FortiManager local-in policy, FortiGate FMG-Access for FortiManager-initiated connections) → TLS → certificate and serial.
- `diagnose dvm device list` shows `conn:` (tunnel), `dev-db:`, `conf:`, `cond:` and the policy package status in one place.
- FortiManager 7.6.3+ refuses FortiGate-VMs until `fgfm-allow-vm` is enabled under `config system global`.
- `fgfm-deny-unknown enable` stops unknown FortiGates from appearing as unauthorized devices.
- A failed reload is a content problem, not a connectivity problem. Use `diagnose test deploymanager reloadconf <OID>` to find the line, fix it on the FortiGate, and retrieve again.
- Always end a debug session with `diagnose debug disable` and `diagnose debug reset`.
