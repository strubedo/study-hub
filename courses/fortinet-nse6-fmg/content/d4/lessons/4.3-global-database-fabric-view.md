## Shared global policies and objects

Some rules belong in **every** policy package in **every** ADOM: block known-bad countries, allow the provider's monitoring systems, deny and log everything at the end. Writing them into dozens of ADOMs by hand invites drift. The **Global Database ADOM** lets you define them once and assign them everywhere.

The Global Database ADOM (shown as **Global Database** in the ADOM list once ADOMs are enabled) contains:

* **Global policy packages** with **header** and **footer** policies.
* **Global objects**: addresses, services, security profiles and other object types (Policy & Objects in the Global Database), usable by the global policies.
* **Header/Footer IPS**: IPS header and footer signatures/filters that are added to every IPS sensor in the assigned ADOMs.
* Global **policy blocks** and **CLI scripts** (scripts here run only on the Policy Package or ADOM Database).

Global database objects are **never installed to devices on their own**: they reach devices only when an assigned global package is installed from a local ADOM. A global policy licence is not needed, but not every FortiManager platform supports global policies (check the data sheet).

## Global database ADOM: policy types

| Policy type | Position in the local package | Typical use |
|---|---|---|
| **Firewall Header Policy** | Evaluated **before** every local policy | Provider/carrier must-have rules: block sanctioned countries, allow the NOC, block threat feeds. |
| **Firewall Footer Policy** | Evaluated **after** every local policy | Catch-all deny with logging, last-resort rules. |
| **Traffic Shaping Header/Footer Policy** | Before/after local traffic-shaping policies | Global shaping standards. |
| **Header/Footer IPS** | Once assigned to an ADOM, included in all new and existing IPS sensors in that ADOM | Mandatory signatures, global exemptions. |

When you build the global package, a block of the policy list is reserved for **Local Domain Policies**: at assignment, the ADOM's own policies are inserted into that block, so the result is header → local → footer. The global rules are maintained only in the Global Database; to change them you edit the global package and re-assign it. NGFW policy-based mode is **not supported** for global policy packages.

## Global policy package assignment to an ADOM

In the Global Database ADOM: **Policy & Objects > Policy Packages > [package] > Assignment**.

1. **Add ADOM**, select one or more ADOMs, and choose which of their packages receive the global package:
   * **All Policy Packages**
   * **Specify Policy Packages to Exclude**
   * **Specify Policy Packages to Include**
2. Select the ADOM row and **Assign Selected**. Choose whether to assign **only used objects** or **all objects**, and whether to **automatically install** policies to the ADOM's devices.
3. Install from the local ADOM (or let the auto-install do it). Every package changed by the assignment shows as modified until installed.

Rules:

* **One global policy package per policy package**, but different packages in the same ADOM can use different global packages.
* The Global Database version sets the FortiOS syntax for global policies and objects and limits which local ADOM versions can be selected for assignment; the **local** ADOM version controls which FortiOS versions the package can be installed on. The exact version matrix has changed between 7.6 patch releases of the documentation (the 7.6.5 guide lists 7.6, 7.4 and 7.2 in both directions), so check the guide for your build rather than memorising a matrix.
* Changing a global policy means **re-assigning** to push the change into the ADOMs, then installing.
* **Unassigning** a global package does not remove the policies from the FortiGates until you **install** again.
* Re-importing a device's configuration does **not** bring the global header/footer policies back into FortiManager ("Global policy and objects can not be retrieved from a managed device"); they exist only in the Global Database.
* Upgrade **local ADOMs first**, then the Global Database (see Domain 1.3).

> **Exam tip:** The admin profile has separate permissions: **Global Policy Packages & Objects** (`global-policy-packages`) and **Assign from Global ADOM** (`assignment`). Defaults: Super_User Read-Write / Read-Write; Standard_User Read-Write / **None**; Restricted_User None / None; Package_User Read-Write / Read-Only. Of the predefined profiles only Super_User can assign.

### Policy blocks as an alternative

Fortinet suggests **local policy blocks** as an alternative to global packages because they simplify ADOM upgrades: a local block lives in one ADOM, so it is upgraded with that ADOM alone. Policy blocks can also be used inside global policy packages, but then they are tied to the Global Database again. Moving from global header/footer policies to local policy blocks is a manual rebuild (recreate the rules in the local ADOM, then unassign the global package and install).

## Use case: global policy configuration with header policies

An MSSP manages ADOMs `MSSP-CustomerA` and `MSSP-CustomerB`, each with its own `default` package. The provider needs, on every customer FortiGate:

* Header policy 1: allow SNMP and SSH from the NOC subnet `198.51.100.0/24` to the FortiGates' management addresses.
* Header policy 2: deny traffic to the address group `Blocked-Countries` (geography objects) with logging.
* Footer policy: deny all with logging.

Steps:

1. Switch to **Global Database**, create objects `NOC-Net` and `Blocked-Countries`.
2. Create global package `MSSP-Global` with the two **Firewall Header Policies** and the **Firewall Footer Policy**.
3. **Assignment > Add ADOM**: both customer ADOMs, **All Policy Packages**.
4. **Assign Selected**, used objects only.
5. In each customer ADOM, open `default`: the header rules sit above the customer's policies and the footer below. Install.

A retail chain does the same with one ADOM per region: header rules for PCI segmentation, footer catch-all.

## Security Fabric views in FortiManager

FortiManager recognises a **Security Fabric group** (a root FortiGate and its downstream members) and can display it in Device Manager as one entity. **Fabric View** (ADOM version 6.0 and later) adds:

### Topology

* **Physical Topology**: devices in the Fabric and what they connect to, grouped by upstream device. Views: Device Traffic, Device Count, Device Operating System, Device Hardware Vendor, **Risk** (endpoints with medium/high/critical compromised-host, vulnerability or threat score), No Devices.
* **Logical Topology**: like physical, but shows the **interfaces** (logical or physical) used to connect devices, grouped by upstream interface.
* Metrics sorting: bytes, packets, bandwidth, sessions. **Upstream** options (with Device Traffic): Internet, Owner, IP Address, Country/Region. Search highlights matches and greys the rest.
* ISL-LAG links between FortiSwitches show as a thicker single line.
* Security Rating recommendations appear beside the affected device's icon.

### Security Rating

**Fabric View > Security Rating** shows Security Fabric Ratings for a Fabric group (select it in **Select a CSF**) or a single FortiGate (7.0+). Click **Run Now** to run the report from FortiManager.

* Three scorecards: **Security Posture**, **Fabric Coverage** and **Optimization**, each with a letter grade, sub-category breakdown and point score.
* Drill down into itemized results with links to **FSBP** and **PCI** controls; search and filter the report.
* The rating is built from the **FortiGates' own security rating reports**: if a FortiGate has none, its data is missing.
* A **Security Rating licence** is required to run checks across all Fabric devices and to submit/receive scores for percentile ranking.

### Fabric connectors

Fabric View also hosts **fabric connectors** (SDN, threat feeds, endpoint/identity connectors such as FortiClient EMS) whose objects can be used in policies.

## Lab it yourself

The trial allows two ADOMs, enough to see the Global Database work:

1. Enable ADOMs, create ADOM `Retail`, and switch to **Global Database**.
2. Create a global package with one header and one footer policy (any/any deny with logging is fine).
3. Assign it to `Retail` > All Policy Packages, used objects only.
4. Open `Retail` > `default` and confirm the header/footer placement around the local policies.
5. If you installed, unassign the package and check the FortiGate: the global policies stay until you install again.
6. Fabric View requires a Security Fabric group (two FortiGates); with one FortiGate-VM you can still open Fabric View > Security Rating to see the layout. Security rating checks across the Fabric need the licence.

## Key takeaways

* The **Global Database ADOM** holds global packages (header/footer firewall and shaping policies), global objects, Header/Footer IPS, global policy blocks and CLI scripts.
* Header policies are evaluated before local policies, footers after; local policies fill the reserved block.
* Assign per ADOM to all, all-except or specific packages; one global package per local package; used or all objects; optional auto-install.
* Unassigning needs an install to remove rules from devices; re-import never brings global rules back.
* Upgrade local ADOMs before the Global Database; policy blocks avoid that dependency.
* Fabric View: physical and logical topology, Security Rating (Security Posture, Fabric Coverage, Optimization; Run Now; based on FortiGate reports; licence needed).
