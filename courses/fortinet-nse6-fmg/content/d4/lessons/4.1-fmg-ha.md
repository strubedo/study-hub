## Why FortiManager HA

Almost everything FortiManager knows lives in its database on disk: device databases, ADOM databases, revisions, templates, scripts. FortiManager HA protects that data by continuously copying every database change from a **primary** unit to one or more **secondary** (backup) units, so that a secondary can take over if the primary fails.

Facts to know cold:

| Item | Value |
|---|---|
| Cluster size | Up to **5** units: 1 primary + up to **4** secondaries |
| Platforms | Same FortiManager series. VMs on different hypervisors can pair (KVM primary, ESXi secondary). Different licence types can pair; the licence with the **smallest** managed-device count applies. |
| Prerequisite | **FortiAnalyzer features disabled** on FortiManager |
| Heartbeat and synchronization | **TCP 5199** between the peer IPs |
| Location | Same site or geo-redundant (different networks, across a WAN/Internet), as long as the peers can reach each other |
| Where admins work | The **primary** GUI/CLI |
| Who managed devices talk to | The **primary** for management (install, auto-update, firmware). For FortiGuard (if FortiManager is their FDS) they can use the primary or a secondary. |

## HA synchronization

All database changes are saved on the primary and synchronized to the secondaries. The primary's system configuration is synchronized too, **except**:

* hostname
* system time and NTP server
* network settings (interfaces, routes)
* web proxy settings
* **HA settings**
* local certificates
* SNMP, mail server, syslog server
* SAML SSO settings
* remote authentication LDAP servers and LDAP admin users
* the FortiCloud account associated with the FortiManager
* the **FortiGuard databases** downloaded by FortiManager, and some FortiGuard settings

Two FortiGuard items **are** synchronized: the `config fmupdate service` settings (which built-in FDS services are enabled), and, from 7.6.2, the **To Be Deployed Version** selected in FortiGuard > Packages > Receive Status, so a chosen package version survives failover.

How a cluster comes up:

1. Each unit sends heartbeats to its configured peer IPs and listens for theirs. A heartbeat is accepted only if **cluster ID and group password** match.
2. When the primary receives heartbeats from **all** configured peers it marks the cluster **Up** and synchronizes its configuration and database to the secondaries. This can take minutes on a large database; changes made meanwhile are re-synchronized afterwards.
3. Normal operation: changes replicate continuously. The HA status pane shows **Module Data Synchronized** and **Pending Module Data** (bytes) per peer.

Failure detection time = `hb-interval` × `hb-lost-threshold`. Defaults are **10 s** and **30**, so **300 seconds (5 minutes)**. Shorter detection risks false failures when the primary is busy; longer delays alerting.

## Configuring HA

GUI: **System Settings > HA**. CLI on the primary:

```text
FMG-HQ # config system ha
FMG-HQ (ha) # set mode primary
FMG-HQ (ha) # set clusterid 15
FMG-HQ (ha) # set password HAgr0upPw
FMG-HQ (ha) # config peer
FMG-HQ (peer) # edit 1
FMG-HQ (1) # set ip 10.0.1.52
FMG-HQ (1) # set serial-number FMG-VM0A26000102
FMG-HQ (1) # next
FMG-HQ (peer) # end
FMG-HQ (ha) # end
```

and on the secondary `FMG-B`: `set mode secondary`, the same cluster ID and password, and a single peer entry pointing at the **primary's** IP and serial number.

| Setting | Notes |
|---|---|
| `mode` | `primary`, `secondary`, `standalone` (default). |
| `clusterid` | 1 to 64, default 1. Must match on all members; different clusters on one network need different IDs. |
| `password` | Group password, max 19 characters, must match on all members; each cluster on the same network needs a different password. |
| `config peer` | On the primary: up to four peers (IP or IPv6 + serial). On a secondary: only the primary. |
| `hb-interval` / `hb-lost-threshold` | 1 to 255, defaults 10 and 30. Configured on the primary only. |
| `file-quota` | 2048 to 20480 MB, default 4096. Not configurable on secondaries. |
| `failover-mode` | `manual` (default) or `vrrp`. |

## Failover modes

### Manual (default)

When the primary fails, the secondaries stop receiving heartbeats and the cluster is **down until you reconfigure it**. Units send SNMP traps and log messages. To recover:

1. On the surviving unit you choose, change `mode` to `primary` and add the remaining secondaries as peers.
2. On the other secondaries, point their peer entry at the new primary.

The new primary **keeps its own IP address**. FortiManager automatically updates the FortiManager IP registered on the managed FortiGates when the new primary is selected. If a secondary fails instead, remove its peer entry from the primary; the cluster continues with fewer units. Add units back the same way.

> **Watch out:** If the cluster is behind NAT and uses manual failover, configure the **management address** (`mgmt-addr`/`mgmt-fqdn` under `config system admin setting`) on the primary and secondary so FortiManager knows the public addresses to give the FortiGates. VRRP mode does not need this.

### Automatic (VRRP)

Added in FortiManager 7.2 (the 7.0 `config system ha` has no `failover-mode`). With `set failover-mode vrrp`, the secondary becomes primary automatically when the primary's **monitored interface** (or monitored IP) is down or unreachable.

```text
FMG-HQ # config system ha
FMG-HQ (ha) # set failover-mode vrrp
FMG-HQ (ha) # set mode primary
FMG-HQ (ha) # set clusterid 15
FMG-HQ (ha) # set password HAgr0upPw
FMG-HQ (ha) # set priority 200
FMG-HQ (ha) # set unicast enable
FMG-HQ (ha) # set vip 192.0.2.1
FMG-HQ (ha) # set vrrp-interface port1
FMG-HQ (ha) # config peer
FMG-HQ (peer) # edit 1
FMG-HQ (1) # set ip 203.0.113.10
FMG-HQ (1) # set serial-number FMG-VM0A26000102
FMG-HQ (1) # next
FMG-HQ (peer) # end
FMG-HQ (ha) # end
```

| VRRP setting | Notes |
|---|---|
| `priority` | 1 (lowest) to 253 (highest), default 1. Higher priority is primary when possible. |
| `vip` / `vrrp-interface` | The cluster virtual IP and the interface it lives on (port1 to port10), identical on all peers. In the geo-redundant example Fortinet calls it a dummy IP that is not used for deployment or management. |
| `unicast` | Default disable. **Mandatory for geo-redundant HA**, because the peers are not in the same Layer 2 domain. |
| `vrrp-adv-interval` | 1 to 30 s, default 3. |
| `monitored-interfaces`, `config monitored-ips` | What triggers failover. Only available in VRRP mode. |

The FortiGates must know **every** FortiManager address and serial number so they can follow the primary:

```text
FGT-Branch1 # config system central-management
FGT-Branch1 (central-management) # set type fortimanager
FGT-Branch1 (central-management) # set fmg "198.51.100.10" "203.0.113.10"
FGT-Branch1 (central-management) # set serial-number "FMG-VM0A26000101" "FMG-VM0A26000102"
FGT-Branch1 (central-management) # end
```

On FortiManager, list all addresses in `config system admin setting` → `set mgmt-fqdn 198.51.100.10 203.0.113.10` (up to 10 IPs/FQDNs) so they are written into `central-management` when FortiManager adds a device. The FortiGate learns the primary's serial automatically but you must add the secondary's serial yourself. After failover the FortiGate reconnects to the new primary; `get system central-management` lists both serials, with the current primary's serial first.

## Monitoring and diagnostics

| Command | Purpose |
|---|---|
| `get system ha-status` | Role, cluster ID, HA health status, synchronization state, heartbeat settings, primary uptime. |
| `get system ha` | The HA configuration (same information as the HA status pane). |
| `diagnose ha stats` | HA statistics. |
| `diagnose ha force-resync` | Force the configuration to re-synchronize. |
| `diagnose ha force-vrrp-election` | Trigger a new VRRP election (failover test). |
| `diagnose ha check-data {start | stop | status}` | Start, stop or check the status of the database hash and revision-file check. |
| `diagnose ha dump-datalog` | Dump the HA data log. |
| `diagnose sniffer packet <port> "vrrp"` | Confirm VRRP adverts (multicast or unicast). |
| `diagnose debug application ha <level>` (and `clusterd`) | HA debug. |
| `execute backup ha {ftp | scp | sftp} ...` | Back up HA logs (7.6.2 and later). |

> **Watch out:** `diagnose ha status` shows up in some older notes and community articles, but it is **not** in the FortiManager 7.6 CLI reference. The documented 7.6 `diagnose ha` subcommands are `check-data`, `data-check-report`, `dump-cloud-api-log`, `dump-datalog`, `force-resync`, `force-vrrp-election`, `stats` and `trace-client-req`; for status use `get system ha-status`.

In the GUI, the HA status appears in the banner and under System Settings > HA with **Cluster Status** (Up only when the unit hears all configured peers), **Mode**, **Module Data Synchronized** and **Pending Module Data**, plus **Download Debug Log**.

## FortiGate HA cluster management (managing FortiGate clusters from FortiManager)

A different topic that shares the blueprint bullet: FortiManager managing a **FortiGate** FGCP cluster.

* Add an operating cluster like a single device, using the **primary's** IP. FortiManager treats the cluster as **one managed device**, showing the members under Cluster Members on the device dashboard, with a **Promote** button to make a secondary the primary.
* **FortiManager cannot configure HA on real FortiGates.** The HA Status widget is read-only for real devices; configure HA on the FortiGates and import. HA changes made in CLI templates or scripts (including the priority) land in the device database but are **not pushed** at install.
* 7.6.3 added `config system dm` → `set handle-nonhasync-config {enable | disable}`. The default, **disable**, skips configuration items marked nonhasync (HA settings, vdom-exception and other member-specific items) at install; enabling it includes them. Leave it disabled unless you really mean to push member-specific settings.
* Model (offline) HA clusters can be pre-built with Add Model Device and their HA settings edited before they come online.
* FortiGates in a cluster should not use `ha-mgmt-interface` or `standalone-mgmt-vdom` for the FGFM connection.
* For clusters in Azure or AWS, device-level changes to `system ha`, `system interface` and SDN connector settings must be made on each FortiGate.
* 7.6 detects FortiGate clusters in multi-VDOM-config (MVC) mode and blocks cluster firmware upgrades with a warning.

## Lab it yourself

HA needs two FortiManagers; the trial licence ties one VM to one FortiCloud account and Fortinet does not document HA on trial licences, so treat this as a configuration-reading exercise unless you have two licensed VMs.

1. On the trial, run `get system ha-status` and `get system ha` and identify `standalone` mode and the 10/30 defaults.
2. Write out the primary and secondary configurations above in a text file for your own addressing, checking that cluster ID, password and peer serials line up. Do not apply them to a standalone lab unit.
3. With two licensed VMs: build a manual cluster, open the HA pane, watch Pending Module Data fall to zero, then shut the primary and promote the secondary.

## Key takeaways

* Up to 5 units (1 primary, 4 secondaries), same series, FortiAnalyzer features off; heartbeat and sync on **TCP 5199**.
* Cluster ID (1 to 64) and group password must match; the primary lists all secondaries as peers, each secondary lists only the primary.
* Default detection: 10 s × 30 = **300 s**.
* Not synchronized: hostname, time/NTP, network, HA settings, local certificates, SNMP, mail, syslog, SAML, LDAP servers, FortiCloud account, FortiGuard databases.
* **Manual** failover (default): reconfigure a secondary as primary; it keeps its IP. **VRRP**: automatic on monitored interface failure; use unicast for geo-HA; FortiGates need all FortiManager IPs and serials.
* `get system ha-status`, `diagnose ha stats`, `diagnose ha force-resync`, `diagnose ha force-vrrp-election`.
* FortiManager manages a FortiGate cluster as one device but cannot configure FortiGate HA on real units.
