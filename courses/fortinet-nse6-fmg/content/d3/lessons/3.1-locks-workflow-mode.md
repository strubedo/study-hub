## Why granular locks exist

With workspace mode enabled (lesson 3.3 covers turning it on and the ADOM lock itself), Device Manager and Policy & Objects are **read-only** until you take a lock. Locking the whole ADOM is simple but blocks everyone else in that ADOM. Granular locks let several administrators work in the **same unlocked ADOM** at the same time, each on their own piece.

| Lock | What it protects | How to take it |
|---|---|---|
| ADOM lock | Everything in the ADOM | Lock in the banner next to the ADOM name, or System Settings > ADOMs > Lock |
| Policy package lock ("policy lock") | One policy package | Policy & Objects > Policy Packages > right-click the package > Lock |
| Device lock | One device's database | Device Manager > Device & Groups > right-click the device > Lock |
| Per-policy lock | One policy inside a package | Edit the policy (per-policy lock must be enabled) |
| Object lock | One object | Right-click the object > Lock (after locking a package or policy) |
| Policy block lock | One policy block | Right-click the policy block > Lock |

A **green** padlock means you hold the lock; a **red** padlock means another administrator does. Hover over a per-policy padlock to see who locked it and when.

## Policy package lock

In workspace mode a package must be locked before it can be changed, either by locking the ADOM or by locking just that package.

* While you hold the package lock, other admins cannot change the package and **cannot lock the ADOM** unless they forcibly disconnect you.
* Click **Save** before unlocking. If you unlock or log out with unsaved changes, a dialog lets you save or discard them.
* All of your package locks are released when you log out.
* If you later lock the whole ADOM yourself, FortiManager removes your individual package and device locks (the ADOM lock covers them).

> **Watch out:** You can lock and edit an existing package without the ADOM lock, but **creating** a policy package or adding a device needs the **entire ADOM** locked.

## Device lock

A device lock protects one device's database (its interfaces, routing, system settings and so on in Device Manager).

* Other admins cannot change that device until you unlock it, log out, or they disconnect you while locking the ADOM.
* **Individual devices cannot be locked when the ADOM device mode is Advanced** (VDOMs split across ADOMs). In that mode, workspace changes to a device database are saved automatically and the Save button is greyed out.
* Creating a script needs the whole ADOM locked, but a script can be **run directly on a device** when only that device is locked.

## Per-policy lock

Per-policy locking is off by default. Turn it on globally:

```text
FMG-HQ # config system global
FMG-HQ (global) # set per-policy-lock enable
FMG-HQ (global) # end
```

(GUI: System Settings > Advanced > Workspace, with workspace mode enabled, toggle **Per-Policy Lock**.) The option only exists in workspace mode.

With it enabled, editing a policy locks just that policy. Other admins can then edit **other** policies in the same package, but they cannot modify your policy, cannot lock the package that contains it and cannot lock the ADOM. You can still escalate to a package or ADOM lock yourself (with a confirmation).

Two details are popular exam material:

* A policy that is used in a **policy block** cannot be locked individually. Lock the policy block instead.
* Adding or inserting two or more policies takes a **sequence lock** at the top of the table, so only one administrator controls policy order at a time. While someone holds it, others can still edit existing policies but cannot create or insert policies. Saving releases it.

```text
Policy & Objects > Policy Packages > Branch-PP > Firewall Policy   (viewed by admin "dana")

          Seq  Name            From  To    Action
[red]          (sequence lock held by "lee")
[red]     1    Guest-Out       guest wan1  ACCEPT
[green]   2    LAN-Out         lan   wan1  ACCEPT
          3    Mgmt-In         wan1  lan   ACCEPT
```

Here dana holds the lock on policy 2. Lee holds policy 1 and the sequence lock, so dana can edit policies 2 and 3 but cannot add or insert a new policy until lee saves.

## Object and policy block locks

When you lock the ADOM, every object in it is locked to you. To share the ADOM, lock a package (or a policy, with per-policy lock) and then right-click individual objects > **Lock**. Locking an object is optional while you are editing a locked package, but it prevents two admins from editing the same object at once. Other admins see a red padlock on the object.

Policy blocks can be locked individually in workspace mode, so you can create, edit or delete them without the ADOM lock. One admin cannot lock both a policy block and a package that contains it; that attempt fails with "Lock conflict with other types of locks".

## Workflow mode

Workflow mode adds **change approval** on top of locking. Its rules differ from workspace mode:

* Only the **whole ADOM** can be locked. No device, package or per-policy locks.
* After locking the ADOM you must **start a session** before changing policies or objects. Without a session (Continue Without Session) everything stays read-only.
* An **approval matrix** must exist for the ADOM before any session can start.
* While a session is in progress, **devices cannot be added or installed**.
* Workflow mode is not supported for restricted administrators.

Enable it for all ADOMs with System Settings > Advanced > Workspace > **Workflow (ALL ADOMS)** or:

```text
FMG-HQ # config system global
FMG-HQ (global) # set workspace-mode workflow
FMG-HQ (global) # end
```

For one ADOM only, set `workspace-mode per-adom`, log back in, then choose Workflow in that ADOM's Edit ADOM page. Changing the mode logs you out.

### Permissions and the approval matrix

The approval matrix (System Settings > Advanced > Workspace > Create New, or the ADOM's Edit page in per-ADOM mode) lists for one ADOM:

* Up to **eight approval groups**. **One approver from each group** must approve a session before it is accepted.
* Administrators to receive email notifications.
* The mail server. A mail server must be configured, and every approver needs a contact email address in their admin account.

Approvers can approve or reject straight from the email (Approve this request / Reject this request, or log in to FortiManager) or from the session list. FortiManager **cannot stop an administrator from approving their own session**, so build the groups with that in mind.

Separately, the administrator profile controls who may lock at all: **Lock/Unlock ADOM** (`adom-lock`) and **Lock/Unlock Device/Policy Package** (`device-policy-package-lock`), along with **Install Policy Package or Device Configuration** (`deploy-management`) and **Import Policy Package** (`import-policy-packages`).

### Session life cycle

```text
Policy & Objects > Sessions > Session List   (ADOM: Retail)

ID  Name                 User   Date Submitted        Approved/...  Status icon
7   Add-POS-VLAN         dana   2026-10-21 09:14:02   2/2           Approved
8   Block-Torrent        lee    2026-10-22 15:40:11   0/2           Rejected
9   Rework-Guest-Policy  dana   2026-10-23 08:02:57   1/2           Waiting for approval
```

| Action | Result |
|---|---|
| Create New Session | Starts a session (needs the ADOM lock; unavailable while another session is in progress or saved) |
| Save | Keeps the session for later; the ADOM stays locked to you; nobody can start a new session until it is submitted or discarded |
| Continue Session in Progress | Resumes a saved session |
| View Diff | Shows the session's changes (Details and CLI Diff, downloadable as CSV); works even when the ADOM is unlocked |
| Submit | Sends approval emails and **automatically unlocks the ADOM** |
| Approve / Reject | By approvers (from the email or from the session list, which needs the ADOM lock); sessions must be approved **in order**; a rejected session must be repaired or discarded before the next one can be approved |
| Repair | Creates and starts a **new** session (added to the top of the list) containing the rejected session's changes so they can be fixed |
| Discard | Deletes the session for good, **and every later session in the list** |
| Revert | Creates a new, automatically submitted session that undoes all changes made after the selected session |

In the list above (the status is the icon beside each name in the real GUI), session 9 cannot be approved until session 8 is repaired or discarded. If session 8 is discarded, session 9 is discarded with it, because discarding removes every later session.

> **Exam tip:** Approval only commits the changes to the ADOM database. Getting them onto the FortiGates is still an install. In the Global Database ADOM, assignments to ADOMs can only be made inside a session, and the assignment creates an automatically submitted session in the target ADOM that must also be approved.

## Lab it yourself

1. Enable workspace mode, then log in as two administrators in two browsers (use a private window for the second).
2. Admin A locks `Branch-PP`; admin B tries to lock the ADOM and sees it refused.
3. Enable `per-policy-lock`, have each admin edit a different policy in the same package, and watch the green and red padlocks and the sequence lock.
4. Switch the ADOM to workflow mode. Create an approval matrix with admin B as the only approver (you need a mail server entry; a lab SMTP relay on a Linux host is enough, and approval also works from the session list).
5. As admin A, start a session, change an address, submit; as B, reject it; as A, repair and resubmit.

## Key takeaways

* Workspace mode allows ADOM, package, device, per-policy, object and policy block locks; green padlock is yours, red is someone else's.
* Holding a package or device lock stops others from locking the ADOM unless they disconnect you; locking the ADOM yourself removes your granular locks.
* Creating packages, adding devices and creating scripts need the whole ADOM locked; device locks are not available in Advanced ADOM device mode.
* `per-policy-lock` (default disabled) locks single policies; policies in policy blocks cannot be locked individually; the sequence lock serializes policy creation and ordering.
* Workflow mode locks only whole ADOMs, needs an approval matrix and a session, and blocks device adds and installs while a session is open.
* Sessions are approved in order; one approver per group (up to eight groups); discard removes all later sessions; repair and revert create new sessions.
