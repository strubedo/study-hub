## Three versions to keep straight

| Version | What it is | What it decides |
|---|---|---|
| FortiManager firmware | The software running on FMG-HQ, for example 7.6.1 | Which ADOM versions you can create and which FortiOS builds are supported at all (see the release notes) |
| ADOM version (ADOM database version) | The FortiOS syntax the ADOM's database is built on, for example a **7.6 ADOM** | The policy types, object fields and GUI options available in Policy & Objects for that ADOM, and which FortiOS versions it can install to and import from |
| FortiOS version | The firmware on each FortiGate | What the device itself can do |

FortiManager 7.6 supports **7.6, 7.4 and 7.2 ADOM versions** (plus other ADOM types such as FortiCarrier, FortiProxy and Fabric). The type and version of a normal ADOM are chosen when you create it and **cannot be edited** afterwards; the way to move it forward is an ADOM upgrade. (The Global Database ADOM is the exception: its version can be changed on its Edit page as well as upgraded.)

### Mixed FortiOS versions in one ADOM

An ADOM can manage FortiGates on firmware other than its own version. FortiManager converts configuration on a best-effort basis:

* Installing to a **newer** FortiGate: syntax the newer version changed is upgraded; syntax that exists only in the newer version is not used; syntax the newer version deleted is not installed.
* Installing to an **older** FortiGate: syntax new to the ADOM version is discarded; changed syntax is converted back; deleted syntax is converted back using the older version's defaults.

The supported combinations are listed per FortiManager build in the "FortiOS version support by ADOM version" table, and Fortinet notes that they change between releases: a new ADOM version initially supports only the matching FortiOS version, and upgrade/downgrade support is typically added within one or two patch releases. As an example only, the 7.6.4 Administration Guide's table shows 7.6, 7.4 and 7.2 ADOMs each able to install to and import from FortiOS 7.6.x, 7.4.x, 7.2.x and 7.0.x. Do not memorize a matrix; check the table (and the release notes) for the build you run.

> **Watch out:** Mixed versions are a transition aid, not a design. The ADOM cannot use features of the newer FortiOS (for instance templates that reference 7.6-only syntax in a 7.4 ADOM), and Fortinet recommends not leaving devices on other versions permanently.

## Organizing devices by ADOM

Common ways to split devices:

* **By customer** (MSSP): `MSSP-CustomerA`, `MSSP-CustomerB`, each with its own admins, objects and packages. This also keeps one customer's object names from colliding with another's.
* **By region or business unit**: `Retail` for the stores, `DC` for the data centre firewalls.
* **By FortiOS version**: during a long migration, a 7.4 ADOM for devices not yet upgraded and a 7.6 ADOM for upgraded ones.

Rules that constrain the design:

* A device belongs to **one** ADOM. In **Normal** ADOM device mode the whole FortiGate (all its VDOMs) is in one ADOM; **Advanced** mode lets you place individual VDOMs in different ADOMs.
* FortiGate and FortiCarrier devices cannot share an ADOM.
* Only a **Super_User** administrator can create ADOMs and assign devices to them.
* An ADOM must be empty (devices moved to another ADOM or to root) before it can be deleted.

## ADOM upgrade

Upgrading an ADOM converts its database (policy packages, objects, templates) to the next version's format and changes its GUI to that version's features. Typical order for moving a fleet from 7.4 to 7.6:

1. Back up FortiManager (and take a VM snapshot if it is a VM).
2. Run **More > ADOM Upgrade Readiness** on the ADOM. It reports configuration that is missing or invalid for the new syntax and exports to CSV or PDF. It does **not** fix anything.
3. Confirm the **lowest** FortiOS version in the ADOM is supported by the new ADOM version; upgrade any device that is too old first.
4. System Settings > ADOMs, select the ADOM, **More > Upgrade** (or right-click > Upgrade), OK.
5. Upgrade the FortiGates' firmware and resynchronize them.

That single menu action is what the blueprint calls a **one-click ADOM upgrade**. If the ADOM is already at the newest version, the Upgrade option is not offered. You can select **several ADOMs of the same version** and upgrade them together (two 7.4 ADOMs, yes; a 7.2 and a 7.4 ADOM together, no). The readiness check has the same same-version rule.

> **Exam tip:** The **Global Database ADOM** is upgraded last, only after every ADOM that uses a global policy package has been upgraded to a supported version.

Only a Super_User administrator can upgrade an ADOM.

## Moving a registered FortiGate to another ADOM

Moving is done from the **destination** ADOM:

1. System Settings > ADOMs (with All ADOMs view), edit the destination ADOM (or create it).
2. Click **Select Device** and choose the FortiGate (or VDOMs, in Advanced mode). The admin guide states that only devices with the same version as the ADOM can be added this way.
3. Click OK. The device is removed from its old ADOM and added to the new one.

What moves and what does not:

| Moves with the device | Stays behind in the old ADOM |
|---|---|
| The device and its device-level configuration (device database) | Its policy package and the ADOM objects it used |
| | VPN Manager settings, which are ADOM-specific (Fortinet recommends not moving devices that VPN Manager already manages; otherwise rebuild the VPN in the new ADOM) |
| | Other ADOM-level content such as provisioning templates and metadata variable mappings |

So after the move, go to the new ADOM and **import the device's configuration** (Import Configuration wizard) to create a policy package and the objects there, or assign an existing package in the new ADOM and install it.

> **Watch out:** Do not import into an existing **shared** package that other devices use as a target. Importing replaces that package's contents with the single device's policy and its install targets. Import into a new package, then merge deliberately.

### The upgraded-device migration scenario

A common exam story: `FGT-Branch1` in a 7.4 ADOM is upgraded to FortiOS 7.6 ahead of the rest of the stores. You want it managed with 7.6 syntax without upgrading the whole `Retail` ADOM yet.

1. Create a 7.6 ADOM (for example `Retail-76`) if one does not exist.
2. Move FGT-Branch1 into it with Select Device.
3. Import its configuration to build a policy package and objects in the new ADOM (or assign an existing 7.6 package).
4. Install to bring Config Status and Policy Package Status back to green.

The alternative is to leave it in the 7.4 ADOM and rely on mixed-version support until the other stores catch up, then upgrade the ADOM once.

## Lab it yourself

The FortiManager-VM trial allows only 2 ADOMs, so use root plus one more.

1. Enable ADOMs (Dashboard > System Information > Administrative Domain). You will be logged out.
2. Create a 7.4 ADOM named `Retail` and register one FortiGate-VM into it (the FortiGate-VM can run 7.4 or 7.6; check which ADOM version the selector accepts).
3. Run More > ADOM Upgrade Readiness on it and read the report.
4. Make sure root has the same version as the FortiGate (Select Device only offers same-version devices), move the FortiGate into root with Select Device, and notice that its policy package did not follow; import it again in root.

## Key takeaways

* FortiManager firmware, ADOM version and FortiOS version are separate; the ADOM version is fixed at creation and only changes by upgrading.
* An ADOM can manage some older and newer FortiOS versions by converting syntax on a best-effort basis; the supported combinations change between builds, so check the support table for yours.
* Only Super_User admins create ADOMs, assign devices and upgrade ADOMs; a device (or VDOM in Advanced mode) is in one ADOM only.
* ADOM upgrade: back up, run readiness, check the lowest device version, More > Upgrade, then upgrade the FortiGates; same-version ADOMs can be upgraded together; Global Database last.
* Moving a device (Edit destination ADOM > Select Device, same-version devices only) leaves its policy package, objects and VPN Manager settings behind; import or assign a package in the new ADOM.
