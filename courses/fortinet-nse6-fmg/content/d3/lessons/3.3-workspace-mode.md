## The default: concurrent ADOM access

Out of the box FortiManager runs with workspace **disabled**, which means **concurrent ADOM access is enabled**: several administrators can log in to the same ADOM and change policies, objects and devices at the same time. Nothing stops two people editing the same address or installing the same package at once, and the last save wins.

```text
FMG-HQ # get system global
...
adom-mode : normal
...
adom-status : enable
...
workspace-mode : disabled
```

Workspace-related options such as `per-policy-lock` and `workspace-unlock-after-install` are only offered once workspace mode is on, so they do not appear while it is disabled.

**Workspace mode** turns concurrent access off. An administrator must take a lock before changing anything, and while one admin holds the lock the others have read-only access.

## The four workspace-mode values

```text
config system global
    set workspace-mode {disabled | normal | per-adom | workflow}
end
```

| CLI value | GUI (System Settings > Advanced > Workspace) | Effect |
|---|---|---|
| `disabled` (default) | Disable | Concurrent access; no locks |
| `normal` | Workspace (ALL ADOMS) | Locking required in every ADOM |
| `workflow` | Workflow (ALL ADOMS) | Locking plus sessions and approval in every ADOM (lesson 3.1) |
| `per-adom` | Workspace (Per-ADOM) | Each ADOM chooses Disable, Workspace or Workflow in its own Edit ADOM page |

Changing the mode **ends your session** and returns you to the login screen. Disabling workspace warns that logged-in users may lose unsaved data. In per-ADOM mode, set the global value first, log back in, then edit each ADOM's Workspace Mode setting.

> **Exam tip:** The setting is in `config system global` and the off value is `disabled` in the 7.6 CLI Reference (a few Administration Guide pages print it as `disable`; the CLI Reference syntax is `{disabled | normal | per-adom | workflow}`). "Workspace default" on the exam means concurrent access: workspace disabled.

## Effects of workspace mode

Once workspace (or workflow) is on:

* **Device Manager and Policy & Objects are read-only** until you lock the ADOM, a device or a policy package.
* The ADOM must be locked before changes in **AP Manager, VPN Manager, FortiSwitch Manager, Extender Manager and FortiClient Manager**, and for some System Settings and device-level actions such as **upgrading a device's firmware**.
* **Adding devices and creating policy packages** needs the whole ADOM locked.
* **Creating a script** needs the ADOM locked; running a script on a device needs only that device locked.
* In **Advanced** ADOM device mode, individual devices cannot be locked, and device database edits are saved automatically.
* Restricted administrators with read-only permissions do not see the lock icon.
* Through the **JSON API**, the ADOM does not need to be locked to make device-level changes.
* Changes are held until you click **Save**. Unlocking or logging out with unsaved changes prompts you to save or discard them.

> **Real world:** Turning on workspace mode is the cheapest fix for "two admins installed half-finished changes over each other". In an MSSP with a NOC and per-customer engineers, per-ADOM mode lets the busy customer ADOMs use workflow approval while lab ADOMs stay unlocked.

## Locking and unlocking an ADOM

**Lock**: click **Lock** in the banner beside the ADOM name, or System Settings > ADOMs > select the ADOM > Lock (you do not have to be in the ADOM). The padlock turns green for you and red for everyone else, both in the banner and in the All ADOMs list.

**Unlock**: click Save, then Unlock in the banner or System Settings > ADOMs. **Only the administrator who locked the ADOM can unlock it** (unless lock override is enabled).

Points to remember:

* Locking the ADOM removes any device and package locks you held in it.
* If another administrator holds a device, package or per-policy lock in the ADOM, you cannot lock the ADOM without disconnecting them.
* Logging out releases all your locks (with a save-or-discard prompt for unsaved work).

### Install and Unlock

Admins often forget to unlock after installing. This setting, available only in the CLI after workspace mode is on, adds an **Install and Unlock** option to the Install Wizard that releases the ADOM lock when the install completes:

```text
FMG-HQ # config system global
FMG-HQ (global) # set workspace-unlock-after-install enable
FMG-HQ (global) # end
```

### ADOM lock override

By default nobody can break someone else's ADOM lock. Enabling **ADOM lock override** (`lock-preempt`, default disable) lets an administrator unlock an ADOM locked by another admin; the other admin's **unsaved changes are discarded**. It only has an effect when workspace mode is on, because without workspace mode there are no locks.

```text
FMG-HQ # config system global
FMG-HQ (global) # set lock-preempt enable
FMG-HQ (global) # end
```

## Closing sessions with locked ADOMs

A lock lives as long as the admin's login session. When someone goes home with the ADOM locked (or their browser crashed and the session is still alive), you have three ways out:

1. **Ask them to unlock or log out.** Cleanest; they can save their work.
2. **Disconnect the session in the GUI.** Dashboard > System Information > Current Administrators > **Current Session List**, select the session and click **Delete**. The admin is logged out and their locks are released. Unsaved changes are lost.
3. **Kill the session in the CLI.**

```text
FMG-HQ # diagnose system admin-session list
*** entry 0 ***
session_id: 3121 (seq: 0)
username: lee
admin template: lee
from: GUI(10.10.5.23) (type 1)
profile: Standard_User
adom: Retail
session length: 22418 (seconds)
idle: 21907 (seconds)

*** entry 1 ***
session_id: 3188 (seq: 1)
username: admin
admin template: admin
from: GUI(10.10.5.40) (type 1)
profile: Super_User
adom: root
session length: 96 (seconds)
idle: 2 (seconds)

FMG-HQ # diagnose system admin-session kill 3121
```

Check the entry carefully before killing it; killing the wrong session interrupts a colleague. Lock override (`lock-preempt`) is the alternative when you only want the lock, not the whole login, ended. Session idle timeout (the admin idle timeout setting) also eventually logs a forgotten session out.

## Supported ADOM versions and device organization in workspace mode

Workspace mode is set for all ADOMs or per ADOM (with `per-adom`); it is not tied to the ADOM version, so ADOMs of different versions on the same FortiManager (7.6, 7.4 and 7.2 ADOMs on FortiManager 7.6) follow the same workspace rules. How you organize devices into ADOMs (lesson 3.2) decides how much locking contention you get: one big ADOM with many admins means many lock conflicts; ADOMs per customer or region spread the locks out, and per-ADOM workspace mode lets each one use the mode that suits it.

## Lab it yourself

1. Note the current value with `get system global` (look for `workspace-mode`).
2. Set Workspace (ALL ADOMS) in the GUI and confirm you are logged out.
3. Log in as two admins. As admin A, lock the ADOM; as admin B, confirm Policy & Objects is read-only and the padlock is red.
4. As admin B (Super_User), open the Current Session List and delete admin A's session; the ADOM unlocks.
5. Repeat with `diagnose system admin-session list` and `diagnose system admin-session kill <session_id>`.
6. Enable `workspace-unlock-after-install` and look for Install and Unlock in the Install Wizard.

## Key takeaways

* Default is `workspace-mode disabled`: concurrent ADOM access, no locks.
* `normal` = workspace for all ADOMs, `workflow` = approvals for all ADOMs, `per-adom` = choose per ADOM; changing the mode logs you out.
* In workspace mode Device Manager and Policy & Objects are read-only until you lock; AP, VPN, FortiSwitch and Extender Manager need the ADOM lock.
* Only the locking admin can unlock, unless `lock-preempt` (ADOM lock override, default disable) is enabled, which discards their unsaved changes.
* `workspace-unlock-after-install enable` adds Install and Unlock to the Install Wizard.
* Release a stale lock by disconnecting the admin in the Current Session List or with `diagnose system admin-session kill <id>`.
