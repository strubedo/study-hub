## Where policies live on FortiManager

A FortiGate keeps one configuration file. FortiManager splits what that file holds into two places, and most of Domain 3 is about keeping them in step:

| Layer | What it holds | Where you edit it |
|---|---|---|
| **ADOM database** (ADOM and policy layer) | Policy packages, ADOM-level objects (addresses, services, profiles, normalized interfaces, metadata variables), provisioning templates, AP profiles, FortiSwitch templates | Policy & Objects, provisioning templates, AP Manager, FortiSwitch Manager |
| **Device database** (device layer) | One complete configuration per managed FortiGate or VDOM: interfaces, routing, admin settings and the policies and objects last copied into it | Device Manager (the device's own pages and CLI configurations) |

An install never sends the ADOM database to a FortiGate directly. FortiManager first copies what the device needs from the ADOM database into that device's database (Fortinet calls this the **VDOM copy**), then compares the device database with the configuration it pulls from the real FortiGate, and pushes only the **difference**.

The copy follows a fixed order. For a real device: system template, CLI template (pre-VDOM copy), threat weight template, IPsec tunnel template, static route template, BGP template, NSX-T service template, SD-WAN template, AP profile, FortiSwitch template, FortiExtender template, **policy package**, then CLI template (post-VDOM copy). Model devices add a pre-run CLI template at the very start.

> **Exam tip:** When an install includes a policy package, the package's policies and objects overwrite the matching settings already in the device database. If someone changed a policy locally on the FortiGate and you retrieved that change, the next package install still replaces it with the FortiManager version.

## The policy workflow

Fortinet describes two jobs an administrator does with policies.

**Provisioning a new device or VDOM**

1. Add the device (or create the VDOM) in Device Manager.
2. Optionally assign a system template.
3. In Policy & Objects, create the dynamic object mappings the new device needs (per-device address values, normalized interface mappings, metadata variable values).
4. Decide whether the device gets its own policy package or joins one that already exists.
5. Run the Install Wizard, or create a new package first.
6. If it joins an existing package, add the device to that package's installation targets.

**Day-to-day management**

1. Add, edit or delete objects such as addresses, services and security profiles.
2. Add, edit, delete or reorder policies in packages.
3. Install the changes to the devices.

A practical rule follows from this: once a FortiGate's policies are imported, make every policy and object change on FortiManager. A change made on the FortiGate itself forces you to re-import (or overwrite it with an install) to bring the two back into line.

## Policy packages

A **policy package** is a container for the policy tables a FortiGate or VDOM receives: IPv4/IPv6 or consolidated firewall policies, proxy policies, central SNAT and DNAT when Central NAT is enabled, virtual wire pair policies, and so on. Packages can sit in folders, and a folder can contain more folders.

When you create a package (Policy & Objects > Policy Package > New) you choose:

| Setting | Notes |
|---|---|
| Name | Unique in the ADOM. |
| Central NAT | Adds Central SNAT and Central DNAT tables instead of per-policy NAT. |
| NGFW Mode | Profile-based (default) or Policy-based. |
| SSL/SSH Inspection | Only when NGFW mode is Policy-based. |
| Consolidated Firewall Mode | One table for IPv4 and IPv6. Turning it off later hides the consolidated policies. Not available in the Global Database. |
| Policy Offload Level | Full Offload is for hyperscale policies. |
| In Folder | Optional folder. |

Objects are **not** stored inside a package. Addresses, services and profiles are ADOM-level objects shared by every package in the ADOM. That is why one object edit can mark several packages as Modified at once.

Each managed device or VDOM has **one** assigned policy package at a time. One package can, however, be assigned to many devices, which is the normal way to keep a fleet of branches identical.

Every change to a package is recorded in its Revision History at the bottom of the policy pane; select a revision and click View Diff to see what changed. That history is per package, and it is different from ADOM revisions (lesson 3.2).

> **Real world:** Retail and MSSP designs usually use one shared package for many identical branches (for example `Branch-PP` for every store) and rely on dynamic mappings and metadata variables to cover the per-store differences. A package per device scales badly.

## Installation targets

### Package-level targets

Open the package and select **Installation Targets** in its tree. The pane lists each target (device, VDOM or device group) with its connection, **Config Status**, **Policy Package Status** and any scheduled install. From here you can Add or Delete targets and start the Install Wizard or Re-install Policy for a selected target.

Adding a device to a package's targets is what assigns the package to the device. Removing a target breaks that assignment, and the device's policy package status can fall back to **Never Installed**.

### Per-policy targets: Install On

Sometimes one package must serve devices that are not quite identical: a FortiWiFi and a FortiGate, or a hub and its spokes. Instead of cloning the package you can restrict individual policies:

1. In Policy & Objects > Policy Packages, select the package.
2. Column Settings > **Install On** to show the column.
3. In a policy's Install On cell (default value **Installation Targets**, meaning every target of the package), pick only the devices that should receive that policy.

Policies left at the default go to every package target. A policy restricted to `FGT-Branch1` is skipped when the package is installed to `FGT-Branch2`.

```text
Branch-PP  (Installation Targets: FGT-Branch1, FGT-Branch2)

Seq  Name              From      To     Install On
1    Guest-WiFi-Out    guest     wan1   FGT-Branch1
2    LAN-Out           lan       wan1   Installation Targets
3    Mgmt-In           wan1      lan    Installation Targets
```

Here FGT-Branch1 receives policies 1, 2 and 3; FGT-Branch2 receives 2 and 3 only.

> **Watch out:** Install On only filters which policies a package target receives. It does not install the package to a device that is not one of the package's installation targets; add the device to Installation Targets for that.

## Feature Visibility

Policy & Objects hides many policy types and object categories by default so the GUI stays short. If you cannot find the menu for, say, metadata variables, a policy type or a security profile type, it is usually switched off in **Policy & Objects > Tools > Feature Visibility**.

* Tick an option (or a whole category, or Check All) to show it; untick to hide it. Reset to Default restores the defaults.
* Some options are always on and cannot be cleared.
* Hiding a feature only hides it in the GUI. It does not delete objects of that type that already exist.
* By default visibility is **per ADOM**: every administrator in that ADOM sees the same set. It can be made per administrator:

```text
FMG-HQ # config system global
FMG-HQ (global) # set gui-feature-visibility-mode per-admin
FMG-HQ (global) # end
```

The same mode also governs the Feature Visibility setting for provisioning templates.

Related layout setting: **Classic Dual Pane** (Tools menu, or System Settings > Advanced > Misc Settings) shows the policy package tree and the object configuration tree at the same time.

## Policy consistency check

The **policy check** (Policy Package > Policy Check, then Perform Policy Consistency Check) examines all the packages in the ADOM and reports four kinds of problem:

| Finding | Meaning |
|---|---|
| Duplication | Two objects with identical definitions. |
| Shadowing | A higher-priority object completely covers another of the same type, so the lower one can never match. |
| Overlap | One object partially covers another of the same type. |
| Orphaning | An object is defined but not used anywhere. |

The algorithm evaluates the policies' source and destination interfaces, source and destination addresses, services and schedules. Results can be exported to PDF, and **View Last Policy Consistency Check Result** reopens the previous run without repeating it. The results window also includes a Policy Hit Count Report that can be exported to CSV or PDF.

You can also make the check automatic. In the ADOM settings (System Settings > ADOMs > Edit), **Perform Policy Check Before Every Install** runs a check during each install, but only on policies that were added or modified, which keeps it fast. **Action When Conflicts Occur During Policy Check** is either **Continue Installation** or **Stop Installation**.

> **Exam tip:** The consistency check never changes anything. It reports duplicates, shadowing, overlap and orphans. Fixing them is your job, for example with Find Duplicate Objects > Merge (next lesson).

## Lab it yourself

The FortiManager-VM trial allows 3 devices/VDOMs and 2 ADOMs, which is enough for this.

1. Register two FortiGate-VM trials (`FGT-Branch1`, `FGT-Branch2`) in one ADOM and import FGT-Branch1's policies.
2. Rename the imported package `Branch-PP`, then add FGT-Branch2 to its Installation Targets.
3. Show the Install On column and restrict one policy to FGT-Branch1.
4. Run the Install Wizard to FGT-Branch2 and use Install Preview to confirm that the restricted policy is absent. (The FortiGate-VM trial allows only 3 firewall policies, so keep the package small.)
5. Create two address objects with identical subnets and run a policy check to see the duplication finding.

## Key takeaways

* The ADOM database holds packages and shared objects; the device database holds each FortiGate's full configuration. Installs copy ADOM data into the device database, then push only the diff.
* Objects are ADOM-level and shared by all packages; one object change can mark many packages Modified.
* A device or VDOM has one assigned package at a time; a package can have many installation targets.
* Install On narrows individual policies to a subset of the package's targets; the default is Installation Targets.
* Feature Visibility (Tools menu) hides or shows policy types and objects, per ADOM by default or per admin with `gui-feature-visibility-mode`.
* The policy check reports duplication, shadowing, overlap and orphaning, and can run automatically before every install with a continue or stop action.
