## Two status columns, two layers

Device Manager's table view (and each package's Installation Targets pane) shows two independent statuses for every device. Mixing them up is the most common mistake on this topic.

* **Config Status** compares the **device database** on FortiManager with the real FortiGate's configuration (device-level settings).
* **Policy Package Status** compares the **policy package** (ADOM database) with what was last imported from or installed to the device.

### Config status

| Config status | Icon | Meaning |
|---|---|---|
| Synchronized | Green check | Device database and FortiGate match |
| Modified | Yellow triangle | Changed on FortiManager, not yet installed |
| Auto-update | Green check | Changes made on the FortiGate were automatically synced into FortiManager |
| Modified (recent auto-updated) | Yellow triangle | Changed on FortiManager, and changes from the FortiGate were also auto-synced |
| Out of Sync | Red X | Changed on the FortiGate and not synced to FortiManager |
| Conflict | Red X | An install failed, or both sides changed and the FortiGate change was not auto-synced |
| Unknown | Gray question mark | Connection is down, or no revision exists yet (for example a model device) |

A config **Conflict** is resolved one of two ways: keep the FortiGate's version (Revision History > **Retrieve Config**, then re-import the policy so the package matches) or keep FortiManager's version (Install Wizard > **Install Device Settings (only)**).

### Policy package status

| Policy package status | Icon | Meaning |
|---|---|---|
| Imported | Green check | Policies and objects were imported from this device into FortiManager |
| Installed / Synchronized | Green check | The package was installed and matches the device (Device Manager labels it Installed; the Installation Targets pane labels it Synchronized) |
| Modified | Yellow triangle | Policies or objects used by the package were changed **on FortiManager** and not yet installed |
| Out of Sync | Red X | Policies or objects were changed **on the managed FortiGate** |
| Unknown (with package name) | Gray question mark | The device's configuration was **retrieved** after the package was imported or installed, for example a retrieve after a FortiOS upgrade |
| Never Installed | Yellow triangle | The assigned package did not come from importing this device, and it has not been installed since it was assigned |

The package name is shown with the status, for example `Modified (Branch-PP)`.

> **Watch out:** **Conflict** is not in the 7.6 policy package status tables, but it can still appear on the policy side. The 7.6 Administration Guide notes that when auto-update brings a **policy-level** change from the FortiGate into FortiManager, the policy layer status might change to Conflict (a device-level change leaves it unchanged), and Fortinet support articles list Conflict as a package status for that case. Treat it like Out of Sync: decide which side wins, then re-import or install.

```text
Device Manager > Device & Groups > Managed FortiGate (ADOM: Retail, table view)

Device Name   Connection  Config Status   Policy Package Status       Firmware
FGT-Branch1   up          Synchronized    Modified (Branch-PP)        v7.6.1
FGT-Branch2   up          Modified        Never Installed (Branch-PP) v7.6.1
FGT-HQ-DC     up          Out of Sync     Out of Sync (DC-PP)         v7.4.5
```

Reading it: someone changed an object or policy that Branch-PP uses (Branch1 needs an install); Branch2 was just added to Branch-PP's targets and also has pending device-setting changes; on FGT-HQ-DC somebody edited the FortiGate locally.

> **Exam tip:** "Modified" means FortiManager is ahead of the device: install. "Out of Sync" means the device is ahead of FortiManager: decide whether to keep the device's change (retrieve and re-import) or overwrite it (install). Changing an object such as a normalized interface mapping makes every package that uses it Modified.

Where statuses come from in practice:

* Editing a shared object turns every package that uses it to **Modified**.
* Installing objects with **Install Object(s)** (partial install) leaves the packages **Modified** until the next full package install.
* Removing a device from a package's installation targets can bring back **Never Installed**.
* When a device with agentless FSSO (`user fsso-polling`) is imported, packages referencing those objects show **Modified**, because FortiManager sends all fsso-polling objects to every device using agentless FSSO.

The same information is in the CLI:

```text
FMG-HQ # diagnose dvm device list
--- There are currently 2 devices/vdoms managed ---

TYPE            OID    SN                HA      IP            NAME          ADOM     ...
fmgfaz-managed  167    FGVM02TM24000101  -       10.10.1.1     FGT-Branch1   Retail   ...
               |- STATUS: dev-db: not modified; conf: in sync; cond: OK; dm: installed; conn: up
               |- vdom:[3]root flags:0 adom:Retail pkg:[modified]Branch-PP
fmgfaz-managed  171    FGVM02TM24000102  -       10.10.2.1     FGT-Branch2   Retail   ...
               |- STATUS: dev-db: modified; conf: in sync; cond: pending; dm: retrieved; conn: up
               |- vdom:[3]root flags:0 adom:Retail pkg:[never-installed]Branch-PP
--- End device list ---
```

`dev-db` and `cond` describe the device database (pending device-setting changes), `conf` compares the latest revision with the FortiGate, and `pkg:[...]` is the policy package status for each VDOM. (The IPS, FIRMWARE and HW_GenX columns are trimmed here; the status lines are what matter. In 7.6 the TYPE column of a managed FortiGate reads `fmgfaz-managed`; older material shows `fmg/faz enabled`.)

## The Import Configuration wizard

Importing copies a FortiGate's policies and policy-related objects from the **device database** into the **ADOM database**, creating a policy package that mirrors the FortiGate. **It does not change the FortiGate.** You import once when you onboard a device (the Add Device wizard can do it for you), and again whenever you deliberately accept changes made locally on the FortiGate.

In 7.6, right-click the device in Device Manager > **Import Configuration** (some views still say Import Policy), choose **Import Policy Package**, then:

### 1. Policies and objects

| Field | Options |
|---|---|
| Policy Package Name | Optional; type a name for the new package |
| Folder | Optional; default `root` |
| Policy Selection | **Import All**, or **Select Policies to Import** (policies and policy groups) |
| Object Selection | **Import only policy dependent objects** (only what the imported policies reference), or **Import all objects** |

### 2. Interface map

Every **enabled** FortiGate interface needs a mapping. For each one:

| Column | Meaning |
|---|---|
| Device Interface | The FortiGate's enabled interface or zone |
| Mapping Type | **Per-Device** or **Per-Platform** |
| Normalized Interface | The ADOM normalized interface it maps to (an existing one, or a new one created by the wizard) |
| Add mapping for all unused device interfaces | Also create mappings for interfaces no imported policy uses |

### 3. Object conflicts

The wizard compares the FortiGate's objects with ADOM objects of the **same type and name**. Identical duplicates are simply not imported again. When the definitions differ, you must choose for each conflict:

| Choice | Effect on the ADOM | Effect on devices |
|---|---|---|
| **Use FortiGate value** | The ADOM object is updated to the FortiGate's definition | Every other device whose package uses that object now has a pending change (Modified) and will receive the new value at its next install |
| **Use FortiManager value** | The ADOM object is kept as it is | This FortiGate stays consistent with FortiManager; its next install pushes FortiManager's definition, changing the object on this FortiGate |

**View Conflict** shows each conflict's details; **Download Conflict File** saves them.

```text
Import Device - FGT-Branch2 [root] - Object Conflicts

Category          Name          FortiGate Value              FortiManager Value           Choice
firewall address  Web-Srv       10.2.20.10/32                10.1.20.10/32                Use FortiManager Value
firewall service  TCP-8443      TCP/8443                     TCP/8443-8444                Use FortiGate Value
firewall addrgrp  Store-Nets    Store-LAN, Store-POS         Store-LAN                    Use FortiManager Value
```

With these choices, `TCP-8443` changes in the ADOM for every package that uses it; `Web-Srv` and `Store-Nets` keep their ADOM definitions, so the next install to FGT-Branch2 rewrites its local `Web-Srv` to 10.1.20.10/32. If Branch2 really needs its own value, the right fix is a per-device mapping on `Web-Srv`, not either choice alone.

### 4. Object list and import

The next page lists the objects that will be imported. Click Next to run the import, and the **summary** page appears. **Download Import Report** saves a report of what was imported. Objects go into the shared ADOM database and policies into the chosen package; the device becomes the package's installation target and its status becomes **Imported**.

Details to remember:

* The import removes policies with **FortiManager-generated policy IDs** (for example 1073741825) that the device had learned earlier from global header/footer policies, policy blocks or the VPN console.
* Importing the FortiClient EMS connector configuration from a FortiGate is not supported.
* ADOM version matters: the ADOM must support the device's FortiOS version for import (see the support table, lesson 3.2).
* AP profiles and FortiSwitch templates use the same wizard with the **Import AP Profiles or FortiSwitch Templates** choice; central management for those must be enabled in the ADOM.

### The first install after an import

Two surprises are normal:

* With **Import only policy dependent objects**, objects that no policy used were never imported. The first install can therefore **delete those unused objects** from the FortiGate. FortiManager does not keep unused objects; reference them in a policy if you need them back.
* FortiManager may **reorder** policies on the first install, grouping policies by interface pair to match the order shown in the GUI. It does not change the order of policies within an interface pair.

Always read Install Preview on that first install.

## Lab it yourself

1. Make a local change on a managed FortiGate-VM (edit an address used in a policy) and watch the Policy Package Status turn Out of Sync.
2. Re-import with Import Configuration and choose **Use FortiGate value** for the conflict; check that another device using the same package goes Modified.
3. On a fresh device import, choose Import only policy dependent objects, then open Install Preview and look for `delete` lines for unused objects.
4. Run `diagnose dvm device list` before and after each step and match `pkg:[...]` to the GUI.

## Key takeaways

* Config Status tracks the device database versus the FortiGate; Policy Package Status tracks the package versus the device.
* Package statuses: Imported, Installed/Synchronized, Modified (FortiManager changed), Out of Sync (FortiGate changed), Unknown (retrieved after import/install), Never Installed (assigned but not installed and not from import).
* Import copies device-database policies and objects into the ADOM; it never changes the FortiGate.
* Import options: Import All or Select Policies; policy dependent objects or all objects; every enabled interface needs a per-device or per-platform mapping.
* Use FortiGate value updates the shared ADOM object (other devices go Modified); Use FortiManager value keeps the ADOM object and overwrites the FortiGate at the next install.
* The first install after an import can delete unused objects and reorder policies by interface pair; check Install Preview.
