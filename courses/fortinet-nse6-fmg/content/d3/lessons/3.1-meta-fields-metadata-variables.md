## Two features with confusingly similar names

FortiManager 7.6 has two separate features whose names both start with "meta". The exam expects you to keep them apart.

| | Meta fields | ADOM-level metadata variables |
|---|---|---|
| Purpose | Extra **descriptive attributes** on objects and administrators (store number, contact, site code) | **Values that change per device** and are substituted into templates, scripts and object fields |
| Where configured | System Settings > Advanced > **Meta Fields** | Policy & Objects > Advanced > **Metadata Variables** (enable it in Tools > Feature Visibility first) |
| Scope | FortiManager-wide definitions, values set on each object | Per ADOM: each ADOM has its own list |
| Can be used as a variable in scripts or provisioning templates | **No** | **Yes**, with `$(name)` |
| Per-device values | Some object types allow a per-device value | Default value plus per-device or per-device-group mapping; per-ADOM mapping in the Global Database |

> **Exam tip:** The 7.6 Meta Fields page states that meta fields cannot be used as variables in scripts or provisioning templates and points you to ADOM-level metadata variables instead. Older releases used device meta fields as template variables, and a few template pages in the 7.6 guide still carry that older wording (for example static route templates with Device VDOM meta fields). For the exam, per-device substitution in scripts and templates means **metadata variables**.

## Meta fields

A meta field adds a labelled field to one object type. You can make it **Required** or **Optional**.

To create one: System Settings > Advanced > Meta Fields > Create New, then set:

| Setting | Options |
|---|---|
| Object | Administrative Domain, Central NAT, Device, Device Group, Device VDOM, Firewall Address, Firewall Address Group, Firewall Policy, Firewall Service, Firewall Service Group, System Administrator |
| Name | The label; FortiManager derives a variable-style name from it automatically |
| Length | 20, 50 or 255 characters |
| Importance | Required or Optional |
| Status | Enabled (default) or Disabled; only offered for non-firewall objects |

The Object and Name cannot be changed later; delete and recreate the field if you got them wrong.

**What "Required" does.** When a required meta field exists for an object type, administrators must enter a value when they create that kind of object. For devices, Device Manager's table view automatically gains a column for each required device meta field. A device with no value shows an **exclamation mark** in that column; right-click the device, choose Edit and fill it in.

```text
Device Manager > Device & Groups > Managed FortiGate (table view)

Device Name   Config Status    Policy Package Status       storenumber
FGT-Branch1   Synchronized     Installed (Branch-PP)       148
FGT-Branch2   Synchronized     Installed (Branch-PP)       (!)
```

Typical uses: storing a store number or region on every device, making admins record a ticket number on every firewall policy, or tagging address objects with an owner.

## ADOM-level metadata variables

A metadata variable is a named placeholder with a **default value** and optional **mapped values** for individual devices or device groups. You reference it once in a shared resource, and each device receives its own value at install time. Metadata variables can be used in fields of:

* CLI scripts and Jinja scripts
* Provisioning templates (system, IPsec tunnel, SD-WAN overlay, CLI templates and others)
* Firewall addresses, address groups, IP pools and VIPs
* Normalized interfaces and virtual wire pairs
* FortiAP SSIDs and FortiSwitch VLANs
* FortiClient EMS and EMS Cloud connectors

Fields that accept a variable carry the metadata variable icon. Typing `$` in such a field opens the list of variables available in the ADOM. In scripts, templates and fields without the selector, type the reference yourself as **`$(variable_name)`**.

### Creating a metadata variable

Policy & Objects > Advanced > Metadata Variables > Create New:

| Field | Meaning |
|---|---|
| Name / Description | Name is what you reference in `$(name)` |
| Type | **Text** (plain) or **Password** (stored encrypted; the value cannot be revealed after saving; useful for template passwords) |
| Default Value | Used for any device that has no mapping |
| Per-Device Mapping | Device or device group plus value (not available in the Global Database ADOM) |
| Per-ADOM Mapping | Only in the Global Database ADOM: one value for all devices in a chosen ADOM |

You can also set a device's values from **Device Manager**: right-click the device > **Edit Variable Mapping** shows each variable's default and the device's mapping value, which you can edit. Device groups have the same option, and their value applies to every device in the group. The More menu on the Metadata Variables page clones, groups, imports and exports variables (JSON or CSV) and shows where each variable is used. When you add many model devices from a CSV, extra columns can carry each device's metadata variable values.

### Using a metadata variable

A system template interface action for every store:

```text
Interface: port2
IP/Netmask: 192.168.$(storenumber).254/24
```

A CLI template that builds an IPsec tunnel to the hub:

```text
config vpn ipsec phase1-interface
    edit "HUB1"
        set interface $(wan_intf)
        set localid $(store_id)
        set remote-gw 203.0.113.10
    next
end
```

An address object `Store-LAN` with subnet `$(store_net)`.

At install time FortiManager resolves each variable for the target device: a per-device value if one exists, otherwise the value mapped to a device group the device belongs to, otherwise the default value. (The admin guide states that devices with their own per-device value use it instead of the device group value.) **Install Preview shows the resolved real value**, which is the fastest way to confirm the mapping is right.

```text
Metadata Variables (ADOM: Retail)

Name          Type   Default Value    Per-Device Mapping
storenumber   Text   0                FGT-Branch1 = 148
                                      FGT-Branch2 = 152
wan_intf      Text   wan1             FGT-Branch2 = port1
store_id      Text   store-000        Group Retail-East = store-east
```

With this table, FGT-Branch2 resolves `$(wan_intf)` to `port1`, while FGT-Branch1 (no mapping) uses the default `wan1`.

> **Watch out:** All metadata variables used in a Jinja script must have default values defined in the ADOM database. More generally, give every variable a sensible default: a device without its own mapping silently receives the default, so a forgotten mapping shows up as a wrong value on the FortiGate rather than an obvious error. Check Install Preview before installing.

### Global Database variables

In the Global Database ADOM you can create metadata variables too. Instead of per-device mapping they use **per-ADOM mapping**: one value applied to every device in the selected ADOM. This suits global header and footer policies (Domain 4) that need, for example, a different management subnet in each customer ADOM.

## Lab it yourself

1. Turn on Metadata Variables in Policy & Objects > Tools > Feature Visibility.
2. Create `storenumber` with default `0` and per-device values for FGT-Branch1 and FGT-Branch2.
3. Create an address object whose subnet is `10.$(storenumber).0.0/24`. Keep every mapped value a valid octet (0-255), because FortiManager substitutes the text as-is.
4. Use the address in `Branch-PP` and compare Install Preview for each device.
5. Create a Required meta field for Device called `storenumber` (Length 20) and watch the new column and the exclamation mark in Device Manager.

## Key takeaways

* Meta fields are extra attributes on objects and admins (System Settings > Advanced > Meta Fields); they can be Required or Optional but are not script or template variables in 7.6.
* A required device meta field adds a Device Manager column; a missing value shows an exclamation mark.
* Metadata variables are per ADOM and hold a default value plus per-device or per-device-group values.
* Reference metadata variables as `$(name)`; typing `$` in supported fields opens a picker.
* A per-device value beats a device-group value, and either beats the default; Install Preview shows the resolved value.
* In the Global Database, metadata variables use per-ADOM mapping instead of per-device mapping.
