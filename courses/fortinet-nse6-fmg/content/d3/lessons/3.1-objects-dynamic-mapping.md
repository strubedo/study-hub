## Object configurations

Policy & Objects > Object Configurations holds every reusable object in the ADOM: firewall objects (addresses, address groups, services, schedules, VIPs, IP pools), security profiles, user and authentication objects, Security Fabric connectors, normalized interfaces and advanced objects such as metadata variables and CLI configurations. If a category is missing, turn it on in Tools > Feature Visibility.

Objects belong to the **ADOM**, not to a package. Every policy package in the ADOM can reference them, and every FortiGate that receives a package gets the objects that package uses. Three consequences show up on the exam:

* Editing an object marks **every** package that uses it as Modified, and each of those packages must be installed for the change to reach the devices.
* FortiManager installs the objects that the package's policies reference (plus a few documented exceptions that are installed without a direct reference, such as FSSO polling objects, address and profile groups and CA certificates). Objects nobody uses stay in the ADOM database and are not pushed, and unreferenced objects already on the FortiGate can be removed by the install.
* Objects imported from FortiGates land in this one shared database. Two FortiGates that both had an address called `Web-Srv` with different subnets cannot both keep their value under that single name (see the import lesson for how conflicts are resolved).

Each object edit opens an editor with a **Preview** button that shows the JSON API request and the equivalent CLI script for the change, which is handy when you are learning the API or scripting.

> **Exam tip:** Objects with the `g-` prefix are FortiGate global objects (for example a global IPS sensor on a multi-VDOM FortiGate). When imported they become ADOM-level objects, and when a package references them FortiManager installs them to the FortiGate's global VDOM. Objects shared across ADOMs come from the Global Database ADOM instead (Domain 4).

## Used objects

There are two quick ways to see whether an object is in use:

* The **Used** column in the object list shows whether each object is referenced.
* Right-click the object and choose **Where Used**. The window lists the policy packages, policies and other objects that reference it.

When you delete an object that is in use, FortiManager warns you and offers **Where Used** or **Delete Anyway**. Whether forced deletion is possible is controlled by an admin setting that is enabled by default:

```text
FMG-HQ # config system admin setting
FMG-HQ (setting) # set objects-force-deletion disable
FMG-HQ (setting) # end
```

With `disable`, FortiManager refuses to delete objects that are still referenced.

## Unused and duplicate objects

Both tools are in the Policy & Objects **Tools** menu:

| Tool | What it finds | What you can do |
|---|---|---|
| Find Unused Objects | Objects not referenced by any policy or object | Review them and delete what you do not need |
| Find Duplicate Objects | Objects with the **same definition but different names** (for example `Srv-10.1.20.10` and `WebServer` with the same /32) | Review each group and click **Merge** to collapse the group into one object; references move to the surviving object |
| Find Unused Policies | Policies with a zero hit count (hit counts are collected from the FortiGates) | Review them, then delete or disable them from the Unused Policies window |

Merging is the clean-up step after a policy check reports duplication. Unused objects are also what the policy check reports as **orphaning**.

> **Real world:** Imports from several FortiGates almost always create duplicates (each firewall admin named the same server differently). Run Find Duplicate Objects after onboarding a batch of devices, before you build shared packages on top of the mess.

## Dynamic objects and per-device mapping

A shared package only works across many branches if some values can differ per branch. FortiManager solves that with **dynamic mapping** on objects that support it:

* **Per-Device Mapping**: a value for a specific device and VDOM.
* **Per-Platform Mapping**: a value for a FortiGate model (available on some object types).
* **Default value**: the object's own base configuration, used for every device that has no matching mapping.

Objects documented with dynamic mapping include addresses, IP pools, VIPs, normalized (dynamic) interfaces and zones, and dynamic device objects such as local certificates and VPN tunnels. In the GUI, expand **Per-Device Mapping** (or Per-Platform Mapping) in the object editor and click Create New.

For example, the address `Store-LAN` can be `10.1.0.0/24` by default but `10.2.0.0/24` on FGT-Branch2. When the shared package is installed, FGT-Branch2 gets 10.2.0.0/24 and every other target gets 10.1.0.0/24.

In a CLI script, the mapping is a `dynamic_mapping` table inside the object, keyed by device name and VDOM. Such scripts must be run against a **policy package** (ADOM database), not against the device database:

```text
config firewall address
    edit "Store-LAN"
        set subnet 10.1.0.0 255.255.255.0
        config dynamic_mapping
            edit "FGT-Branch2"-"root"
                set subnet 10.2.0.0 255.255.255.0
            next
        end
    next
end
```

Per-platform values use `platform_mapping` where the object supports it.

> **Watch out:** The default mapping is used **only** when there is no per-device mapping for that device. An object used in a package must have either a per-device mapping for the target or a default value, otherwise the installation fails. When you import a policy package, FortiManager usually adds a per-device mapping automatically for objects that the FortiGate already uses.

Metadata variables (next lesson) are the other way to vary values per device. They plug into individual fields (`$(store_net)` in an address subnet, for example) rather than replacing the whole object value.

## Interface mapping and normalized interfaces

Firewall policies on FortiManager never reference a FortiGate's physical port directly. They reference a **normalized interface**, an ADOM object whose mapping rules say which real interface or zone it becomes on each device. (In the CLI, JSON API and older documentation the same object is called a **dynamic interface**, and the GUI still says "dynamic interface" in a few places.)

A normalized interface can contain:

| Mapping | Matches on | Example |
|---|---|---|
| Per-device mapping rule | A specific device and VDOM | `LAN` → `port3` on FGT-Branch1 |
| Per-platform mapping rule | A FortiGate model | `LAN` → `internal` on every FortiGate-60F |
| Wildcard (a toggle on the normalized interface, with a pattern) | Interface names that match the pattern | `port*` matches every interface whose name starts with port |

**Per-device mappings take priority over per-platform mappings**, and the first matching rule is used.

When an ADOM is created FortiManager adds a set of **default normalized interfaces** with per-platform rules for all FortiGate models (for example `port1` maps to `port1`). These defaults let you install policies before you build any custom mappings. You can delete default normalized interfaces or remove their per-platform rules. If you try to create your own per-platform rule for a physical interface name that a default rule already covers, FortiManager reports that the dynamic-interface default mapping has been used; delete the default rule first.

Other details worth knowing:

* Zones are created in Device Manager (per device) and can be mapped to normalized interfaces like any interface.
* Wildcard rules use `.` for one alphanumeric character and `*` for zero or more characters. At install, all matching interfaces are installed.
* The Mapped Interface Name field accepts metadata variables, typed as `$(variable_name)`.
* **More > Normalized Interface Preview** shows, per device or per platform, which normalized interfaces map to what, and lists the device's **unmapped** interfaces at the bottom.
* **Where Used** on a normalized interface shows which packages reference it.
* Changing a mapping rule modifies the object, so every package that uses it becomes **Modified** and must be reinstalled.

### When the import wizard creates mappings

The import wizard (lesson 3.4) requires a mapping for every **enabled** FortiGate interface. For each one you choose a mapping type, **Per-Device** or **Per-Platform**, and the normalized interface it maps to. **Add mapping for all unused device interfaces** creates mappings even for interfaces that no imported policy uses, which saves work if you later add policies on those interfaces.

> **Exam tip:** If a package uses a normalized interface that has no mapping for the target device (no per-device rule, no matching per-platform rule), the install for that device fails during validation. The fix is to add the mapping, not to edit the policy.

## Lab it yourself

1. In a test ADOM, open Policy & Objects > Normalized Interface and look at the default entries and their per-platform rules for FortiGate-VM64.
2. Create a normalized interface `LAN` with a per-device mapping to `port2` on FGT-Branch1 and `port3` on FGT-Branch2. Use it in one policy of a shared package.
3. Create an address `Store-LAN` with a default subnet and a per-device mapping for FGT-Branch2.
4. Use Install Preview for each device: the same policy should show different interface and subnet values.
5. Create two identical addresses with different names, run Tools > Find Duplicate Objects and merge them.

## Key takeaways

* Objects are ADOM-wide and shared by all packages; only referenced objects are installed.
* Used column and Where Used show references; `objects-force-deletion` (enabled by default) controls Delete Anyway.
* Find Unused Objects lists unreferenced objects; Find Duplicate Objects groups same-definition, different-name objects for Merge.
* Dynamic mapping gives an object per-device or per-platform values; the default value applies only when no per-device mapping exists.
* Normalized (dynamic) interfaces map policy interfaces to real ports or zones; per-device beats per-platform, first match wins.
* A missing mapping for a target device makes that device's install fail.
